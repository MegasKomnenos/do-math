**P01. 같은 Claude 세션의 여러 결과를 정확하게 수집한다.**

실패한 첫 계산 실행의 원본 JSONL을 현재 `claude_adapter.parse_jsonl`에 다시 넣었다. 같은 `session_id`에서 `system/init` 3개와 `result` 3개가 나왔고, 뒤의 두 결과에는 `origin.kind=task-notification`이 있었다. 현재 수집기는 시작과 결과가 각각 하나이며 결과가 마지막 사건이어야 한다고 요구한다. 재생 결과는 `invalid_session_start`, `invalid_terminal_count_or_position`이었다. 즉 실제 CLI가 낸 사건의 배열과 수집기가 허용하는 배열이 달랐다. 다만 그 작업의 계산 코드에도 오류가 있었으므로, 스트림을 읽을 수 있다는 사실을 연구 완료로 승격해서는 안 된다.

`claude_adapter.py`와 `claude_worker.py`가 하나의 결과 선택 함수를 공유하도록 고친다. 세션 경계, 사용자 요청에 대한 결과, 백그라운드 알림에서 생긴 후속 결과를 구분하고 모든 사건을 보존한다. 마지막 JSON 객체를 무조건 채택하거나 결과가 여러 개면 무조건 첫 결과를 채택하는 규칙은 쓰지 않는다. 설치된 CLI로 대표 사례를 재현하고 관측한 사건 배열을 근거로 후속 결과의 대체 조건과 충돌 시 미완료로 남길 조건을 정한다. 선택 근거를 원본 행 번호와 함께 반환한다. worker가 마지막 사건만 보고 파일을 만드는 현재 경로도 같은 규칙을 써야 한다.

긴 계산의 실행 절차도 함께 고친다. 예상 시간에 맞춰 도구 timeout을 지정하고 계산 파일과 체크포인트를 먼저 남긴다. 백그라운드 작업이 생기면 실제 제공되는 완료 조회 도구로 결과를 회수하고 제출한다. 현재 로그에서는 약 157초 계산이 기본 도구 대기 범위를 넘긴 뒤 알림이 추가됐다. 작업 AI가 완료를 기다리며 잘못된 감시 도구 호출이나 반복 sleep을 시도한 경로도 있었다. 따라서 공통 실행 문서에 제공 도구별 대기·회수 방법을 명시한다. 공식 문서 역시 print 실행의 백그라운드 작업이 종료와 추가 응답에 영향을 준다고 설명한다. 다만 공식 문서는 이번 세 결과의 우선순위를 직접 규정하지 않는다. 그 부분은 설치 버전 재현으로 확인해야 한다. 검증은 원 스트림 재생, 알림만 뒤따르는 정상 결과, 후속 알림에 대한 응답이 이전 구조화 결과를 수정하는 경우, 서로 충돌하는 결과, 서로 다른 세션의 혼합, 잘린 JSON, 오류 결과, 최종 파일 불일치를 포함한다. 과거 로그가 새 파서에서 읽히더라도 검증되지 않은 결과를 연구 정본에 소급 수락하지 않는다. 여러 result의 사용량이 누적값인지 구간값인지 확인한 뒤 집계한다. 현재 runner는 사용량 배열의 마지막 값만 취하므로 다중 결과 지원과 함께 이 의미도 정해야 한다.

현재 작업자는 제출 JSON을 파일에 써서 사전 검사한 뒤 같은 내용을 최종 응답으로 다시 출력한다. 긴 JSON을 다시 생성하는 데 드는 모델 출력량과 중단 위험이 수집기 수정 뒤에도 문제로 남으면, 검사된 파일의 경로·해시를 명시적으로 최종 제출하는 작은 반환 계약을 별도 검토한다. 이 변경은 P01의 필수 선행조건이 아니다. 파일 존재만으로 수락하지 않고 실행 ID, 입력 snapshot, 명시적 제출, 중앙 재검증을 결박해야 한다. 기존 직접 JSON 반환도 유지한다.

재개는 단순 상태 표지만으로 구현할 수 없다. 해제 시각에 실제로 깨어나는 실행 주체가 필요하다. 연구 실행기는 한도 대기로 종료하기 전에 다음 재관찰 시각을 저장하고 기존 Windows 예약 기능에 한 번의 재관찰을 등록한다. 등록 실패나 비정상 종료로 예약이 빠지면 독립 운영의 Python 진입부가 저장된 시각과 실제 예약을 대조해 복구한다. 이 대조와 재관찰에는 새 AI 운영 판단을 필수로 두지 않는다. 로컬 동시 세션 부족과 공급자 한도는 상태 표시의 `waiting_reason`으로 구분한다. 대기 중인 작업은 슬롯을 점유하지 않는다. 재관찰 시 HOLD·사용자 정지·종결·모델 정책·최신 계약을 다시 확인한 뒤 동일 행동을 한 번만 재개한다. 해제 시각을 모르면 지수적으로 늘리되 상한이 있는 간격을 사용하고, 최초 간격과 상한은 기존 운영 설정과 맞춰 명시한다.

검증은 가짜 시계와 공급자 대역으로 한다. 세 실행이 동시에 같은 오류를 반환해도 재개 예약은 하나여야 한다. 엔진 재시작 뒤에도 대기가 보존돼야 하며, 알려진 해제 전 호출은 0회여야 한다. 해제 뒤 한 번의 재시도가 가능하고 다시 제한되면 새 근거로 대기해야 한다. 사용자 정지가 있으면 자동 재개는 0회다. Lean처럼 해당 공급자를 쓰지 않는 허가된 작업의 처리도 별도로 확인한다. 실제 한도를 일부러 소진하는 검증은 필요하지 않다.

**P04. 실제 남은 시간과 관측 가능한 진행을 작업자에게 전달한다.**

14:07에는 2시간 실행기 기한에 걸려 진행 중 실행 세 개가 종료됐다. 앞의 정지·시간 초과 5건 중 나머지 두 건은 연구 시작을 설정하던 대화형 AI 비서가 설정 수정 중 정지한 실행 1건과 약 600초에 종료된 후보 준비 1건이다. 후보 준비는 운영 예산에 속하며 공통 `call_timeout_seconds=600` 제한을 받는다. 연구 수행은 작업 예산에 속하며 그 제한 대신 부모 실행기의 기한을 사용한다. 그런데 입력의 `execution_limits`에는 원 설정값만 있어 실제 실행에 남은 시간이 드러나지 않는다. 입력에서 적용 제한과 실제 기한을 함께 설명해야 한다.

`engine.py`에서 최종 배정 시점의 `effective_deadline_at`, `remaining_seconds_at_dispatch`, 적용되는 제한의 종류를 전달한다. 작업 준비에 시간을 쓴 뒤에도 이 값이 맞아야 한다. 공통 실행 문서의 예시는 운영·연구 수행을 구별한다. 실제 기한 전에 체크포인트와 제출을 요청하고, 남은 시간이 부족한 새 작업은 다음 운전으로 남기는 종료 준비 단계를 둔다. 기존 hard timeout의 의미를 조용히 무한 대기로 바꾸지 않는다. graceful 종료에 실패하면 현재의 강제 종료·부분 회수 경로를 유지한다.

진행 관찰도 별도 검토가 필요하다. `observations.py`는 120초 동안 완성된 사건이나 체크포인트가 없으면 운영 점검을 요청한다. 최대 점검 수는 관찰 대상 실행 하나당 이미 3회다. 긴 생각·큰 최종 응답·실행 중인 도구 때문에 조용한 경우와 실제 정체를 구별하도록 최근 바이트 수신, 미완료 도구, 체크포인트 시각을 함께 제공한다. 관찰기가 완성된 응답을 기다리는 대신 생성 중인 텍스트 조각도 받는 방안을 시험할 수 있다. 이때 연결 생존만 알리는 ping을 작업 진전으로 취급하면 실제 정체를 놓칠 수 있으므로 신호 종류를 구분한다. 단순히 idle 기준을 늘리는 것으로 끝내지 않는다.

검증에는 기한 직전 착수, 종료 예고 후 정상 제출, 무응답 강제 종료, 긴 도구 호출, 천천히 생성되는 최종 응답, 계속 ping만 보내는 정체, 사용자 즉시 정지를 포함한다. 현재 사용자 정지를 더 긴 drain 절차 때문에 늦추지 않는다. 다음 운전은 미완료 행동과 부분 결과를 보존해 이어져야 한다.

**P05. 사용자 질문, 내부 연구 질문, 실패 안내를 정확한 대상에 연결한다.**

과거 snapshot의 `questions`는 문자열 79개, 서로 다른 문자열 68개였다. 내부 연구 질문, 사용자 판단, 실패 안내가 함께 있었다. 현재 수신 코드에는 한 역할의 성공 뒤 그 역할의 오류 접두어를 가진 질문을 모두 지우는 경로가 있다. 예를 들어 과제 A의 계약 검토 성공이 과제 B의 계약 검토 실패 안내까지 제거할 수 있다. 이는 코드에서 확인한 위험이며 이번 실행에서 실제 안내 유실이 발생했다고 확정한 것은 아니다.

첫 수정은 실패 안내의 제거를 해소한 action·execution에 한정하는 것이다. 이후 질문에 ID, 소유자, 원인 실행·과제, 열린 상태·해소 상태, 해소 근거를 부여한다. 과거 문자열은 유실 없이 수입하고 소유자가 불명확한 것은 미분류로 남긴다. 기존 텍스트 조회와 입력 호환은 유지한다. 실패 안내를 기존 행동·대기 기록에서 계산해 보여 줄 수 있으면 별도의 중복 저장을 늘리지 않는다.

계획자는 내부 수학 질문을 후속 과제로 검토하고, 운영 담당은 구현·자료·공급자 문제를 처리한다. 사용자에게는 목표·필수조건·예산·외부 허가처럼 사용자만 바꿀 결정을 보낸다. 질문이 하나라도 있다는 이유만으로 빈 대기열의 연구를 멈추는 현재 분기는 질문의 소유와 실제 차단 범위를 따르도록 고친다. 한도 실패 이후 20:02 조회에서는 실패 행동들이 보류된 채 연구가 `waiting`이었고 실행기도 멈춰 있었다. 그 대기가 질문 분기 때문에 생겼다고까지 확인한 것은 아니다. 이후 20:19의 정지는 별도의 명시적 사용자 요청이다.

20:02 운영 보고는 한도 처리 수리 여부를 사용자 질문으로 올렸다. 독립 운영 계약은 허용 범위 안의 로컬 수리를 이미 맡긴다. 따라서 기술적 불확실성과 사용자 권한의 부재를 구별하는 사례를 계약에 추가한다. 수리가 그 실행의 시간이나 검증 범위를 넘으면 근거와 후속 수정 작업으로 넘긴다. 목표나 예산을 바꿔야 하는 경우에는 계속 사용자 결정을 요구한다.

검증은 같은 역할·다른 과제 A/B의 실패, A만 성공, B의 안내와 대기 유지, 실제 사용자 질문의 보존, 해소된 내부 질문의 재등장 방지, 과거 문자열 변환을 포함한다.

**P06. 입력량과 반복 판단은 의미를 보존한 채 줄인다.**

준비 28회, 계획 52회, 계약 검토 34회, 내부 운영 점검 33회에 비해 연구 수행은 16회였다. 여기에 동일성 검토 4회를 더하면 모델 실행 167건이다. 이것만으로 검토가 낭비였다고 판단할 수는 없다. 먼저 `input.txt`를 공통 문서, 현재 과제, 전체 목록, 이력, 원 보고, 복구 자료로 나눠 실제 중복 바이트와 CLI 보고 사용량을 측정한다. 캐시 생성·캐시 읽기·출력 사용량도 구별한다. 벽시계 구간이 겹치는 실행들의 시간을 단순 합산해 총 경과 시간으로 표시하지 않는다.

기존 `context_store.py`의 원문 외부화와 manifest를 재사용한다. 역할의 판단에 필요한 요약·정확한 참조를 직접 주고, 나머지 원문은 고정 snapshot과 해시로 회수하게 한다. 계약 검토가 다른 과제와의 충돌을 볼 수 있는 범위, 계획자가 전체 배정 후보를 비교할 수 있는 범위, 동일성 검토의 동료 결과 비공개를 유지한다. 공통 문서를 줄일 때는 각 의무가 다음 역할에 실제로 전달되는지 확인한다.

8개 무선택 계획은 사건·입력·요약을 대조해 구분한다. 새 판단이 필요했던 실행은 유지한다. 아직 시작하지 않은 동일 목적의 요청만 기존 병합 경로에서 합치고, 시작한 실행의 입력을 뒤에서 바꾸지 않는다. 새 반환 결과·사용자 결정·계약 반려는 병합 대기 때문에 막지 않는다. 같은 snapshot이라는 이유만으로 계획을 생략하지 않는다. 시간·자원·외부 입력의 변화도 판단 전제가 될 수 있다.

후보 준비에는 요청한 의무가 기존 과제로 충족되는지, 새 후보로 충족되는지, 아직 남는지를 반환하게 할 수 있다. 문자열이 비슷하다는 이유로 의무를 해소하지 않는다. 먼저 이번 준비 요청 표본으로 기존 산출 필드가 충분한지 확인한 뒤, 부족할 때만 최소 필드를 추가한다.

완료 기준은 동일한 판단 자료와 의무를 보존하면서 입력의 중복 또는 불필요한 재호출이 줄었다는 비교 증거다. 임의의 절감률이나 모델 호출 횟수 상한을 연구 품질보다 먼저 목표로 세우지 않는다.

**P07. 과제의 전제·완료 기준·남은 증명 의무를 연결한다.**

이번 계약 검토는 “제안 제출”과 “중앙 검증 완료”의 혼동, 정의 사이의 등식 증명 누락, 이미 알려진 반례보다 좁은 검산 범위, 잘못된 로그오목성 전제, 구간 표현의 모호함을 찾아냈다. 이것은 검토가 작동한 증거다. 동시에 후보 준비가 기존 지식의 반례와 적용 범위를 더 일찍 확인하도록 개선할 여지가 있다.

후보 준비 문서는 질문, 적용 범위, 근거, 시도해야 할 방법, 실패했을 때 반환할 증거, 완료 판정의 주체를 일관되게 쓰게 한다. 단봉성처럼 열린 문제에서는 실패한 접근을 보고하는 과제가 유효하다. 다만 필수 증명을 요구한 계약을 수행 뒤 임의로 “시도했으니 완료”로 바꾸지 않는다. 일반 증명, 정확 계산, 근사 계산, 경험적 관찰은 보고에서 서로 구별한다.

연구 계획에는 현재 목표를 뒷받침하는 결과와 아직 필요한 조건의 관계를 유지한다. 이번 연구에서는 작은 이동 거리의 일부에서 증가를, 큰 이동 거리의 일부에서 감소를 보였지만, 두 범위 사이를 연결하는 증명이 남았다. 한편 새로운 충분조건을 증명하면 그 빈 범위를 다루는 기존 과제 일부를 대체할 가능성도 제안됐다. 계획자는 이 공백과 대체 가능성을 함께 읽어야 한다. 모든 가능한 보조정리를 미리 과제로 만드는 고정 계획표를 요구하지 않는다. 새 결과가 생길 때 연결·공백·경쟁 경로를 갱신한다.

새 전제는 이미 보존된 반례·정확 계산·증명 범위와 먼저 대조한다. 유한 표본 통과를 일반 정리의 승인으로 삼지 않는다. 기존 산출 필드와 관계 기록으로 표현할 수 있으면 새 스키마를 만들지 않는다. 구조화할 필요가 확인된 경우에만 결과별 근거 수준과 남은 의무의 연결을 추가한다.

검증은 이번에 반려·개정된 계약을 평가 표본으로 삼는다. 이미 있는 반례를 놓치지 않는지, 부분 완료가 남은 증명 의무를 지우지 않는지, 정상적인 탐색 과제를 과도하게 금지하지 않는지 비교한다. 자연어 판단의 품질은 정적 문자열 시험만으로 입증할 수 없으므로 실제 계약 검토 표본이 필요하다. 해당 호출은 Opus 5만 사용한다.

**P08. 생산자가 유효한 출처와 Lean 선언 이름을 제출할 수 있게 한다.**

출처 참조 오류는 2건이었다. `used_sources`에는 입력에 제공됐거나 보존된 근거를 가리키는 참조가 필요하다. 실행 ID나 action ID를 아는 것과 그 ID가 제출 가능한 근거인 것은 다르다. 현재도 `available_input_refs`와 사전 검사 도구가 있다. 따라서 새 검사기를 만들기보다 입력 참조의 종류·사용 위치·오류 메시지에 실제 허용값을 연결한다. 실패 실행을 인용해야 하면 복구 자료가 제공하는 정확한 근거 경로를 사용하게 한다.

`formal.py`의 `_ident`는 알파벳·숫자·밑줄만 허용하므로 Lean이 받는 `sumTo_succ'` 같은 이름을 거부한다. 이전 점검에서 해당 이름을 쓴 작은 정리는 실제 Lean에서 통과했다. 이 함수가 Lean 소스 생성의 안전 경계에도 쓰이므로 단순히 임의 문자를 허용하지 않는다. 현재 지원하는 qualified identifier의 문법을 명시하고 최소한 후행 prime을 지원한다. 더 넓은 escaped identifier 지원은 필요 범위와 안전한 생성 방법을 확인한 뒤 결정한다.

검증은 실제 허용 출처의 제출·미제공 ID의 거부, 사전 검사와 중앙 검사의 동일 판정, prime·네임스페이스·Unicode 이름의 지원 범위, 공백·개행·명령 삽입 형태의 거부를 포함한다. 중앙 Lean·공리 검사는 그대로 유지한다.

**P09. 모델 제한과 사전 검사를 실제 호출 경로에 맞춘다.**

`claude_only_assigned_model`은 코드에 있지만 스킬의 Markdown에서 설명을 찾지 못했다. README, CLI 실행 계약, 모델과 실행예산 문서에 옵션의 기본값, 인스턴스 범위, 전체 모델 ID 요구, 내부 보조 모델 제한, 운영 담당이 변경할 수 없는 경계를 적는다. 이번 인스턴스는 모든 역할의 배정과 작업·운영 슬롯이 Opus 5다. 이를 전역 기본값으로 바꾸지 않는다.

기존 `do_math.py profile`은 설치된 CLI가 필요한 명령 옵션을 제공하는지 확인하는 점검 명령이며 그 한계를 문서에 밝히고 있다. 이 점검이 모든 연구 호출을 보증한다고 확대하지 말고 별도 실행 사전 검사를 둔다. 실제 역할 스키마, 구조화 출력, 파일 제출, 학술 도구 연결, 정상 종료와 정지, 모델 사용량을 함께 확인한다. 모든 역할에 비싼 실호출을 반복할 필요는 없다. 스키마 전건의 정적 보존 검사와 대표 실제 역할 호출, 원 로그 재생을 결합한다.

미래 CLI 버전이나 보고하지 않는 내부 사용까지 현재 시험이 보증하지는 않는다. 실행마다 CLI 판본·배정·잠금 옵션·보고된 `modelUsage`를 연결한다. 허용하지 않은 모델이 실제 보고되면 추가 배정을 중단하고 원인을 기록한다. 이미 발생한 소비를 사후 검사로 되돌릴 수는 없으므로 호출 전 제한도 유지한다.

**P10. 운영 AI의 코드 수리를 검증된 판본으로 마무리한다.**

수리 보고의 원인 집계도 검증해야 한다. P03에서 원 운영 보고의 32건 분류와 세부 판본 대조가 다르다는 사실을 확인했다. 진단에는 실행 ID별 입력·거부 판본과 변경 필드, 원인 분류를 연결한다. 사건 수와 겹치는 원인 수를 구별해 집계하고 요약 보고의 수치를 그 표와 대조한다. “자기 대상 과제의 계약 변화 없음”을 모든 인용 계약의 불변으로 확대하지 않는다. 대표 실패 재현의 통과와 전체 거부 사례의 원인 분류도 별도 검증한다.

현재 작업 트리에는 14:02 운영 담당이 만든 8개 변경 파일이 남아 있다. 앞의 수정 현황 표와 P03에서 설명한 인용 과제의 현재성 수리이며, 정본 4개와 그 생성 사본 4개다. 원 재현 로그에는 기존 코드에서 실패한 시험과 수정 후 전체 회귀가 있다. `Ran 457`, `OK (skipped=1)`은 456개 실행 통과와 1개 미실행이다. 이 사실은 현재 미커밋 변경 전체를 무검토로 확정할 근거가 아니다.

착수 시 기존 diff와 해시를 보존하고 변경의 목적·소비자·시험을 읽는다. 정본 `.claude/skills/do-math`를 고친 뒤 생성기로 `.agents` 사본을 맞춘다. 수정 단위별 관련 시험을 통과하고, 통합 판본을 고정해 필요한 전체 회귀를 수행한다. 검증 결과와 실제 배포 판본의 해시를 연결하고 커밋·사본 동기화까지 마친다. 커밋에는 변경 이유와 남은 의무를 적은 `기억/layer1/M-####.md` 문서도 함께 남긴다. 검증 중 정본이 바뀌면 그 결과를 새 판본의 성공으로 사용하지 않는다.

독립 운영 계약에는 기술 수리를 반환할 때의 완료 조건을 분명히 한다. 완료됐으면 수정·검증·버전 기록을 남기고, 미완료면 남은 diff의 소유와 다음 행동을 기록한다. 공유 스킬을 다른 활성 인스턴스도 쓰는 경우에는 그 실행에 판본이 섞이지 않는 배포 경계를 먼저 확인한다. 이번 실행에서 다른 연구를 실제로 손상시켰다는 증거는 없다.

이번 계획 문서의 커밋에는 그 8개 코드 파일을 섞지 않는다. 다음 구현 작업이 기존 수리를 검토해 별도 단위로 확정하도록 남긴다.

**P11. 사람이 읽는 상태와 실제 실행 상태를 함께 보여 준다.**

과제 `performing`이 남았어도 프로세스는 이미 끝날 수 있다. `completed` 과제도 모든 n의 수학 목표를 해결했다는 뜻은 아니다. 기존 status가 주는 자료를 이용해 과제 단계, 활성 실행, 마지막 산출, 수학적 근거 수준, 다음 행동과 대기 이유를 한눈에 연결한다. 우선 기존 상태 자료를 정확하게 조합해 표시하는 방법을 개선한다.

실행 원장에는 입력 snapshot, 시작·종료 KST/UTC, 배정 모델과 실제 보고 모델, 제출·수락·거부, 실패 종류, 재시도 부모, 거부 전제, 기한, 다음 재관찰 시각을 연결한다. 이번에 만든 [시간축](../../../research/problem-selection-2026-09-15/progress-2026-09-18/timeline.html)과 CSV를 기본 내보내기로 발전시킬 수 있다. 초기 구현은 JSON·CSV와 사람이 읽는 요약이면 충분하다.

검증은 동일 snapshot에서 표·JSON·CSV의 건수와 시각·상태가 일치하는지 확인한다. 단계별 실행 수와 사용량을 구별하고, 공급자가 보고하지 않은 비용을 추정값 없이 확정 비용으로 표시하지 않는다. 총 연구 진행률을 임의의 퍼센트로 만들지 않는다.

**P12. 문헌 접근 실패와 부분 대응을 다음 조사에 남긴다.**

한 문헌 조사에서 arXiv 호출 8회 중 성공은 2회였고 429·접근 실패가 있었다. 이는 스킬 자체의 오류나 해당 문헌의 부재를 증명하지 않는다. 기존 학술자료 활용 계약은 검색과 원문 판독, 오류와 무결과를 구별한다. 그 계약을 실제 후속 작업으로 연결하는 것이 개선 목표다.

확보한 원문·버전·해시·읽은 범위를 재사용하고, 자료원 제한은 자료원별 재관찰 시각과 연결한다. 초록만 확인한 항목, 원문을 읽었지만 부분 대응만 확인한 항목, 필요한 원문을 아직 얻지 못한 항목을 구별한다. 신규성은 “있음/없음” 두 값으로만 닫지 않는다. 일부가 알려진 식이고 일부 변환이 필요한 경우 그 차이를 다음 판단에 제공한다.

검증은 보존 자료가 중복 다운로드를 줄이면서도 다른 판본을 같은 원문으로 섞지 않는지, 429가 검색 무결과로 기록되지 않는지, 필수 원문 미확보가 일반적인 “못 찾음” 결론으로 사라지지 않는지 확인한다. 접근 불가능한 자료를 반드시 찾아야 한다는 무한 반복은 만들지 않는다.

실행 집계와 원 보고의 진입점은 [기존 상세 분석](../../../research/problem-selection-2026-09-15/progress-2026-09-18/analysis.md)이다. 이번 [evidence.json](evidence.json)은 고정 판본 집계, 입력 파일 크기, 무선택 계획의 요약, 원 스트림 재생 결과, 한도 이벤트, 20:02 운영 보고, 정지 snapshot과 검토 코드 해시를 연결한다. 원 로그 전체는 `.skill-workspace/parking-unimodality-opus5-20260918/`에 있는 로컬 보관이며 주 저장소 Git 제외 대상이다. 해당 폴더를 정리하면 원 로그는 사라질 수 있다.

코드 위치는 스킬 정본의 `scripts/do_math/` 아래 각 단위에 적힌 모듈이다. 현행 문서와 충돌할 때 이 계획을 구현 계약으로 자동 적용하지 않는다. 구현 단계에서 관련 정본 계약을 함께 개정하고 시험해야 한다. 현재 작업에서 한 검사는 집계·원 로그·코드 대조와 스트림 재생이다. 새 수정의 회귀, 독립 수학 검증, 새 연구의 완주는 아직 수행하지 않았다.
