이 계획은 do-math의 실사용에서 확인한 문제를 고치기 위한 구현 제안이다. 중심은 **바뀔 전제에 의존하는 작업을 미리 기다리게 하고, 그대로 유효한 전제에 대한 결과는 받아들이며, 이미 받은 승인도 실제 사용할 때 같은 기준으로 확인하는 것**이다. 여기에 출력 수집, 공급자 한도, 재시도, 질문과 기한의 연결을 보완한다. 연구의 의미를 판단하는 역할과 기계 실행기가 그 판단을 적용하는 역할은 유지한다.

이 문서에서 **과제**는 계약과 결과를 가진 연구 의무이고 **action**은 역할 실행 요청이다. 실제 호출 한 번은 **실행**이며 action의 재시도는 새 실행 ID를 받는다. **K**는 필요한 형식·동일성 관문을 통과한 형식 정본이고, 현재 사용 가능성은 별도 효력 검사까지 만족해야 한다. **수학 제안**은 Lean 원문과 수학 해설을 한 판본으로 고정한 검토 대상이다. **검토 자리**는 특정 검토자의 논리적 담당, **단계**는 초기 검토·쟁점 정리·답변·판정의 구분, **회차**는 이의 왕복 횟수, **검토 계보**는 그 제안과 수정 판본들의 검토 이력이다. 전건 검토는 해당 판본의 필수 범위 전체를 대조한다는 뜻이다.

기본 운전은 모델별 동시 세션 수를 제한한다. 별도로 남아 있는 **구 실행횟수 모드**는 누적 호출 시도 수를 제한하며 순차 실행한다. 아래의 ‘호환 실행’과 ‘구 모드’는 이 방식을 가리킨다. provider는 모델을 실제 호출하는 공급자다. 테스트의 대역 실행기는 실제 모델을 호출하는 대신 미리 정한 반환과 실행 순서를 제공하여 기계 상태 전이를 검사한다.

**먼저 전체 흐름에서 수정의 위치를 본다.**

```mermaid
flowchart LR
    P[후보 준비와 개정 요청] --> C[독립 계약 검토]
    C --> R[승인 전제와 착수 조건 검사]
    R --> S[연구 계획의 선택]
    S --> D[미시작 요청의 충돌·가용성 검사]
    D --> W[모델 실행]
    W --> A[종료 확인·원 출력과 파일 보존]
    A --> V[현재성·권한·대상 적용 조건 검사]
    V --> N[결과·후속 요청의 일괄 반영]
    N --> P
    N --> K[형식 검사·독립 동일성 검토]
    K --> G[목표 감사·학술 후속]
```

아래의 ‘현재성’은 입력 파일의 최신 여부만을 뜻하지 않는다. **그 판단에 쓰인 내용과 사용 효력이 아직 유효한가**를 뜻한다. ‘적용 조건’은 그 판단으로 지금 대상 상태를 바꿀 수 있는가를 뜻한다. 예컨대 읽은 계약 본문이 같더라도 이미 닫힌 과제를 다시 선택할 수는 없다. 두 검사를 나누어야 무관한 상태 변화는 허용하면서 실제로 잘못된 적용은 막을 수 있다.

**01. 예정된 개정과 그 전제에 의존하는 실행의 순서를 정한다.**

현행 [scheduler.py](../../../.claude/skills/do-math/scripts/do_math/scheduler.py:209)의 `_dispatchable`은 동일 요청·동일 과제의 중복, 준비·계획의 역할별 동시 실행 제한, 모델 슬롯을 검사한다. [planning.py](../../../.claude/skills/do-math/scripts/do_math/planning.py:225)의 `task_ready`는 선행 결과와 입력·계약 승인을 확인한다. 그러나 지금 어떤 실행이 필수 전제를 고치려는지 비교하지 않는다. 또 [engine.py](../../../.claude/skills/do-math/scripts/do_math/engine.py:2241)의 `_apply_plan`은 선택 직후 과제를 `performing`으로 바꾼다. 따라서 준비 상태 계산과 실제 파견 직전 검사 양쪽을 고쳐야 한다.

아래에서 A는 개정될 기존 기록, B는 A를 필수 전제로 쓰는 작업, C는 그 변경과 무관한 작업이다. action은 아직 시작하지 않았거나 특정 실행에 배정된 역할 요청을 뜻한다.

수정에 필요한 새 정보는 **이번 요청이 고칠 기존 기록의 목록**이다. 모든 파일과 필드에 잠금을 거는 체계 대신 기존 action에 `revision_targets`를 추가한다. 값은 기존 과제·지식 ID를 키로 하고 입력의 본문 판본 근거를 값으로 갖는 객체다. 과제는 `revision`·`contract_sha256`, 지식은 `revision`·아래 02의 `content_sha256`으로 고정한다. `{}`는 기존 기록을 개정하지 않는다는 뜻이다. 새 후보·새 지식을 추가하는 일, 진행 상태 변경, 검토 결과 추가는 이 목록의 개정과 구별한다.

| 정보가 생기는 곳 | 구체적인 수정 | 누가 어떻게 사용하는가 |
|---|---|---|
| 계약 반려와 운영 점검의 `revise` | `engine._apply`와 실행 종료 후 처분에서 대상 과제 ID를 준비 action의 `revision_targets`에 넣는다. 현재 이유 문자열만 전달하는 `revise` 경로도 같은 방식으로 바꾼다. | 실행기는 준비 AI를 부르기 전부터 변경 대상 A를 안다. 준비 AI는 고칠 계약의 판본을 정확히 받는다. |
| 사용자 `task_scope=revise` | `governance.apply_decision`이 만드는 준비 요청에 같은 정보를 넣는다. 사용자 결정의 출처와 `revision_requested`를 유지한다. | 사용자 요청을 단순 선택 가능한 추천으로 낮추지 않고 A의 개정 의무로 유지한다. |
| 계획·수행·일반 준비에서 새 개정 필요를 발견 | `submission.extension_schema`에 `revision_requests`를 추가한다. 항목은 `{record_ids, reason}`이고 실제 제공된 과제·지식만 지목한다. 실행기가 입력 판본에서 해시를 결합해 준비 action을 만든다. | 준비 action에 이미 대상이 결합된 경우에는 그 준비 호출에서 바로 개정안을 작성한다. 실행 도중 처음 발견한 미선언 대상은 다음 준비에 맡기므로 다른 작업이 모르는 사이 변경하지 않는다. |
| 실행 중인 준비의 공개 업무 정보 | `engine._context`의 `ongoing_preparation`에 `revision_targets`를 추가한다. | 계획자는 무엇이 개정 중인지 알 수 있다. 준비자의 초안이나 잠정 결론은 제공하지 않는다. |

기존 `preparation_requests: string[]`는 새 후보 탐색과 일반 준비 설명에 그대로 쓴다. **기존 기록의 변경을 요청할 때는 구조화된 `revision_requests`를 사용한다**고 [연구 계획 계약](../../../.claude/skills/do-math/계약/연구-계획.md:71)에 명시한다. 계획 계약에는 같은 의무를 두 필드에 중복 제출하지 않도록 적는다. 문자열의 의미 중복을 제출 검사기가 판정한다고 가정하지 않는다. 구조 검사는 `revision_requests` 안의 ID 중복·제공 여부를 확인하고, 기존 문자열 요청의 중복 여부는 계획자가 설명한 의미로 판단한다. 새 필드를 모든 역할에 허용하지 않는다. 일반 후보 준비·연구 계획·연구 수행·과제 기반 보충 조사만 요청할 수 있으며, 평가만 보충하는 준비와 검토 자리의 고정 질문 조사는 기존 권한을 유지한다.

모든 새 실행에서 `revision_targets`를 지급하고, 개정하지 않는 실행에는 빈 객체를 준다. `candidates[].revises_task_id`와 `knowledge_changes[].id`는 그 실행의 `revision_targets` 안에 있어야 한다. `submission.payload_issues`가 생산자의 고정 입력에서 이를 검사하고, `engine._apply`·`_apply_extensions`가 적용 직전에 판본을 다시 검사한다. 새 기록의 추가는 허용한다. 역할 계약에는 미선언 개정을 우회하려고 같은 연구 의무를 다른 제목의 새 과제로 복제하지 말라고 적는다. 이 의미 중복은 후보 준비·계약 검토가 판단하며 기계 ID 검사만으로 탐지된다고 주장하지 않는다. 필요한 개정을 처음 발견한 경우에는 새 요청을 남기는 경로가 있다.

지식 개정에 새 증명·장기간 조사가 필요하면 운영 예산의 준비 AI가 대신 수행하지 않는다. 준비자는 작업 과제를 만들고 `task_conditions[].knowledge_revision_targets`에 기존 지식 ID를 선언한다. 실행기는 이 목록을 작업 계약 해시와 검토에 포함하고, 선택한 수행 action의 `revision_targets`로 결합한다. 실행기는 준비 결과를 수락해 새 과제를 만드는 시점에 원 개정 요청을 그 과제에 연결한다. `waiting_actions`는 보류한 역할 요청을 action ID별로 보존하는 기존 객체다. 원 요청은 여기에 `kind=revision_dependency`, `delegated_to_task_id`, 미해소 `revision_targets`를 가진 항목으로 남고, 과제에는 `revision_request_action_id`를 저장한다. 이 새 kind는 실행 실패가 아니라 과제에 넘긴 개정 의무다. 일반 `resume`은 이 항목을 queue로 되살리지 않고, `_resolve_failed_actions`도 일반 후속 성공으로 삭제하지 않는다. `blocked_actions`와 `pending_revisions`에는 위임 대상·미해소 대상을 공개한다. 검토 대기 검사는 이 항목을 실패한 검토 자리로 세지 않는다. 위임받은 수행의 수락된 `revision_resolutions`와 명시적 철회 처분만 원 항목을 갱신한다. 후속 수행이 반환되면 실제 지식 개정이 반입된 대상만 원 요청에서 해소한다. 수행 실패·보류는 원 요청도 미해소로 유지하며, 지식 개정을 맡은 과제 D가 철회됐을 때에는 지식 A의 개정 의무까지 닫았다고 추정하지 않고 계획에 후속 처분을 돌려준다. 얕은 문면 정정은 기존에 허용된 준비 역할이 직접 저작할 수 있다. 수행자는 선언된 대상의 `knowledge_changes`만 제출하며, 자기 개정 대상의 원문을 읽는 일은 자기 자신과의 충돌로 세지 않는다.

기다림을 끝내는 조건도 반환 계약에 넣는다. 대상이 선언된 준비 또는 지식 개정 수행에 `revision_resolutions` 확장을 제공하고, 각 대상에 `{record_id, disposition, reason}`을 요구한다. 지식 대상은 이 항목으로만 처분한다. 과제 대상은 이 항목 또는 기존 `task_dispositions`의 철회 항목 중 정확히 하나로 처분한다. 두 경로를 합쳐 지정 대상 전건을 덮어야 한다. `disposition`은 `revised`, `unchanged`, `deferred`, `delegated`다. `delegated`는 새 연구가 필요한 지식 개정을 같은 준비 결과의 작업 과제로 넘기는 처분이며, 유일한 `task_title`을 추가로 지정한다. 실행기는 바로 앞 문단의 대기 요청·새 과제 연결을 같은 반영 단위로 만든다. `revised`는 실제 개정 산출과 대응해야 한다. 개정 대상 자체가 과제 A이고 그 A를 기존 `task_dispositions`로 철회한 경우에는 이력을 보존한 채 A의 개정 요청도 종료한다. 지식 A를 고치도록 맡긴 별도 과제 D의 철회와는 다른 경우다. 사용자 학술 요구를 이 경로에서 철회할 수는 없다. `unchanged`는 검토 결과 개정 제안이 불필요하다는 판단이며, 사용자에게서 온 필수 개정이나 미해소 계약 반려를 취소할 수 없다. 그런 경우는 이유와 다음 조건을 가진 `deferred`로 남긴다. `deferred` 대상을 같은 `waiting_actions`에 남기고, `delegated` 대상은 다음 작업 과제에 연결된 미해소 의무로 남긴다. 의존 작업 B의 대기 이유는 이 미해소 대상에서 계산하므로 해당 대상의 처분이 끝나면 재검사할 수 있다. 이 정보는 실행기가 근거 없이 ‘빈 후보이므로 수리 완료’로 해석하지 않게 한다.

새 충돌 검사는 `planning.py`의 순수 함수와 `scheduler.py`의 얇은 연결로 구현한다. 함수는 과제의 `inputs`·`reuse`·`dependencies`, 착수 시 만족해야 할 조건식인 `occurrence_condition`에서 읽는 기록 ID, 기존 승인에서 실제로 사용한 기록 ID를 모은다. 과제·지식의 명시적 의존은 방문 집합을 두고 따라가되 본문 문자열에서 숨은 의존을 추측하지 않는다. 작업 계약 검토의 읽기 집합에는 검토 대상 과제를 넣는다. 동일성 검토와 그 고정 질문 조사의 읽기 집합에는 검토 대상 제안과 지정된 근거를 넣는다. 동일성 검토의 결과 추가는 제안 본문 개정으로 넣지 않는다.

| 파견 상황 | 제안하는 처리 |
|---|---|
| A 개정 요청이 있고 미시작 B가 A의 필수 전제를 사용 | B를 슬롯 예약 전에 대기시킨다. A 개정 결과와 필요한 사용 조건이 갖춰진 뒤 다시 검사한다. |
| A를 고칠 실행을 시작하려는데 이미 B가 A를 읽으며 실행 중 | 새로운 B는 막고, A 개정 실행은 이미 시작한 B의 종료를 기다린다. 이 기다림은 슬롯을 점유하지 않는다. 사용자 권한 회수·실제 전제 변경의 즉시 정지는 별도 기존 제어를 따른다. |
| 계획이 이미 실행 중인데 새 A 개정 요청이 접수됨 | 그 계획의 고정 입력을 유지하고 A 개정 실행을 기다리게 한다. 계획의 선택을 적용할 때 개정 대상을 사용한 미시작 수행은 다시 대기한다. |
| A 개정 실행이 실제로 진행 중인데 새 일반 계획을 시작하려 함 | 계획은 전체 후보·결과를 비교하므로 개정 실행의 종료 뒤 현재 입력으로 시작한다. |
| A 개정이 실패해 기술 수리를 기다림 | 실패 기록을 읽는 계획·운영 진단은 실행할 수 있다. A를 전제로 실제 수행·승인하는 작업은 미해소 변경 의무가 남아 있는 동안 대기한다. |
| 같은 고정 제안의 독립 검토 둘 | 기존 자리·단계·회차의 병렬 실행을 허용한다. 동료 반환 때문에 상대 슬롯을 막지 않는다. |
| 관련 없는 C의 수행 | 계속 파견할 수 있다. |

충돌 계산 함수는 `planning.action_read_ids`와 `planning.revision_waits`로 나누어 읽는 기록과 대기 이유를 계산하도록 제안한다. 실행기는 단순 bool뿐 아니라 `contract_revision`, `user_decision`, `provider_limit`, `capacity`의 원인과 차단 ID를 보존한다. `_run_parallel`의 마지막 상태 결정이 모든 queue 대기를 `capacity_waiting`으로 표시하지 않도록 이 원인을 읽게 한다. 구 실행횟수 모드의 `_run_executor`도 첫 막힌 요청에서 끝내지 않고 같은 대기 검사를 통과하는 뒤의 개정·독립 요청을 찾는다. 권한·예산이 실제로 없는 경우의 대기는 유지한다.

개정 요청을 접수한 대상 과제 A가 이미 선택됐지만 아직 실행되지 않았으면, 실행기는 A의 옛 수행 요청을 취소 이력에 남긴 뒤 개정 준비를 시작할 수 있는 상태로 돌린다. 그렇지 않으면 `performing` 상태 때문에 현행 개정 적용 검사가 개정안을 거부한다. 실제 실행 중인 A는 먼저 종료·회수한다. 대상 A의 기존 선택 취소와, A를 읽는 별도 B의 일시 파견 대기를 구별한다. 같은 응답이 A의 개정과 A의 수행 선택을 동시에 요구하면 제출 검사에서 충돌을 알린다.

지식 A를 고치도록 위임받은 과제 D와 D의 계약 검토는 A 개정 의무를 수행하기 위한 선행 절차다. `revision_request_action_id`로 연결된 이 두 요청은 원 개정 의무 자체 때문에 차단하지 않는다. 실제로 다른 실행이 A를 쓰는 동안에는 여전히 충돌 검사를 한다. 교정 대상의 원문을 입력으로 읽는 일과 그 주장을 참인 지식으로 `reuse`하는 일도 구별한다. 수정할 주장의 기존 검증을 새 수행의 필수 전제로 잘못 요구하지 않는다. 계획 입력에는 queue·waiting_actions·위임 과제에서 계산한 `pending_revisions` 보기를 추가하고 `context_store`에서도 보존한다. 이렇게 해야 준비 이외의 연구 수행이 맡은 개정도 계획자가 볼 수 있다.

대기 중인 개정과 실제로 실행 중인 개정을 구별하는 이유는 복구 가능성 때문이다. 계획까지 모든 미해소 개정에 막히면, 개정 실패의 취소·재설계·다음 준비를 정할 역할도 실행할 수 없다. 따라서 **실제 변경 실행과 계획의 동시 수행은 막되, 실패한 변경 의무의 처분을 판단하는 계획은 열어 둔다.** 이때 실행기는 계획의 준비·복구 판단을 받으며, 영향을 받는 수행을 곧바로 시작하지 않는다.

`_refresh_readiness`는 개정 의존 대기를 `task_readiness`의 이유와 차단 요청 ID로 표시한다. `_dispatchable`은 이미 `performing`으로 선택됐지만 프로세스가 없는 작업까지 검사한다. `_call_steps`는 입력 준비와 제어 처리 뒤, 슬롯을 확보하기 직전에 같은 검사를 다시 한다. 단순 개정 대기이면 action을 queue에 유지한다. 실제 계약이 달라져 옛 선택의 근거가 없어졌다면 해당 미시작 action을 취소 이력에 남기고, 그 과제의 현행 계약에 대해 승인을 다시 확인한 뒤 ready 또는 waiting을 계산하며, 새 연구 계획 요청을 넣는다. 실행기가 다른 과제를 임의로 선택하지 않는다.

`_enqueue`는 미시작 요청을 합칠 때 개정 대상과 출처를 합친다. 같은 ID에 서로 다른 본문 판본이 들어오면 현재 판본에 맞는 요청을 유지하고 옛 요청과 그 이유·사건 참조를 `superseded` 이력으로 연결한다. 옛 요청의 의무가 새 개정으로 해소됐다고 자동 선언하지 않고 그 의무를 새 준비 입력에 함께 전달한다. `context_store.fit_context`의 action 축소에서도 미해소 대상만 남은 현행 `revision_targets`를 직접 제공한다. 요청 취소·철회·종결·재시도 때에는 연결된 개정 대기 이유를 제거하거나 새 요청으로 이전한다. 요청 전체가 끝났다는 이유로 미처리 대상까지 해소하지 않는다.

동일성 검토 계보는 대기 때문에 전체를 잠그지 않는다. 현재 `_defer_review_for_research`처럼 검토 실행은 끝내고 보충 조사 결과를 같은 자리로 돌려준다. 수학 제안의 개정 요청 때문에 새 검토를 막은 경우, 개정 실행은 이미 실행 중인 해당 검토·조사의 종료까지만 기다린 뒤 시작한다. 개정을 반영할 때 기존 `_apply_extensions`가 이전 계보를 미해결로 닫고 남은 조사를 취소하는 절차를 사용한다. 새 제안은 중앙 형식 검사와 새 판본의 전건 동일성 검토로 연결한다. 구 판본의 승인 자동 승계는 하지 않는다.

이 설계는 시작 전에 알고 있는 변경 충돌을 예방한다. 이미 실행을 시작한 뒤 생긴 사용자 변경이나, 실행 중 처음 발견한 의존까지 없애지는 못한다. 그런 결과는 02의 수신 검사와 03의 현재 전제 재판정으로 연결한다. 이 한계는 예방 장치가 불필요하다는 뜻이 아니라 적용 범위다.

완료 검증은 실제 세션 모드의 스케줄러에 제어 가능한 대역 실행기를 넣어 순서를 확인한다. A 개정 중 B가 시작되지 않음, C는 시작됨, A 반입 뒤 B가 새 판본을 받음, 개정 실패 뒤 계획·진단은 가능함, 취소 뒤 대기가 해소됨, 합쳐진 요청 중 미처리 대상은 남음, 슬롯 점유가 없는 대기임을 확인한다. 같은 제안의 두 독립 검토는 동시에 시작하고 한쪽 반환 뒤에도 다른 쪽이 정상 수락돼야 한다. 보충 조사 대기와 제안 개정이 만났을 때에도 프로세스가 없는 검토 자리 때문에 교착하지 않아야 한다.

**02. 결과 수신과 승인 재사용에 같은 ‘판단 전제’ 검사를 연결한다.**

현재 [knowledge.capture_basis/validate_basis](../../../.claude/skills/do-math/scripts/do_math/knowledge.py:56)는 기록 전체의 해시와 상태를 비교한다. 기존 미커밋 수리는 **반환에서 추가로 인용한 과제**에만 `planning.task_reference_basis`를 사용한다. 착수 때 선언된 의존에는 여전히 전체 해시 검사가 적용된다. 이 차이를 없애기 위해 새 `decision_basis`를 실행의 시작·반환·승인 재사용에서 공통으로 사용한다. 기존 엄격한 `knowledge.validate_basis`를 전역적으로 느슨하게 바꾸지는 않는다. 신뢰 환경 전환과 수학 관계의 양끝 등 정확한 전체 판본을 요구하는 소비자는 기존 계약을 유지한다.

`input_basis.py`에 `capture_decision_basis(instance, runtime, refs)`와 `decision_basis_changes(basis, instance, runtime)`를 추가한다. 반환은 `version=1`, 과제·지식별 근거 배열과 원자료 근거를 가진다. 과제 내용의 투영은 `planning.py`, 지식 내용의 투영은 `knowledge.py`가 소유하고 이 함수가 결합한다. `knowledge.py`가 이미 `input_basis.py`를 사용하므로 새 비교 함수에서 필요한 모듈은 함수 안에서 가져오거나 비교값을 인자로 받아 순환 import를 만들지 않는다. 비교 결과에는 참조 ID, 바뀐 부분, 이전·현재 해시와 다음 처분을 담고, 단순 오류 문자열에서 다시 원인을 추측하지 않게 한다.

| 근거 종류 | 비교할 내용 | 허용하는 동시 변화와 남길 검사 |
|---|---|---|
| 다른 과제의 내용 | 계약 해시, 입력 당시 결과 개수 n과 results[0:n] 전체의 해시 | 검토·보류 사유·진행 표시·새 결과의 뒤 추가는 내용 인용을 무효화하지 않는다. 기존 결과의 수정·삭제와 계약 변경은 검출한다. |
| 지식의 내용 | ID·revision, 저작된 본문과 정의·범위·의존·출처의 해시 | 검토 이력 추가와 시각·실행 좌표만의 변화는 내용 변경으로 세지 않는다. 주장·해설·요약·Lean·선언·가정·범위·의존의 변경은 검출한다. |
| 지식의 사용 효력 | 입력 당시의 검증 상태·사용 정지와 현재 사용 조건 | 본문·출처가 같고 `reviewing → verified`로 승인이 추가된 경우는 허용한다. 철회·사용 정지·부정 판정·신뢰 근거 변경은 재판정 대상으로 남긴다. 원래 K로 사용 가능했던 근거는 현재도 `assess_use`를 통과해야 한다. |
| 원자료 | 기존 `capture_sources/sources_current`의 이름·해시 | 실제 사용한 원자료의 교체는 검출한다. 미사용 원자료 추가는 무효화 사유가 아니다. |
| 이번 행동의 대상 | 선택·완료 판정·개정·검토 자리별 적용 조건 | 내용 인용이 유효하더라도 이미 닫힌 대상의 재선택, 다른 판본의 계약에 대한 승인, 끝난 검토 자리의 결과 적용은 허용하지 않는다. |

`content_sha256`은 지식 본문의 해시다. 비교 대상은 `knowledge_io._KNOWLEDGE_FIELDS` 중 id를 제외한 저작 필드(kind, title, statement, explanation, summary, lean_code, declaration_names, dependencies, origin_refs, source_refs, confirmed_scope, epistemic_status, selection_relevance, uncertainty_assessment, relation_claim), `research_insights` 확장으로 보존한 통찰에 해당 필드가 있으면 information_state·evidence_ids도 비교한다. 향후 스키마에 저작 필드를 추가할 때는 이 비교 목록도 같은 변경으로 갱신한다. 알 수 없는 저작 필드는 조용히 제외하지 않고 비교에 포함하거나 지원 불명으로 반환한다. `knowledge.validate_changes`의 실행기 소유 필드, `history`·검토 기록·검증 실행 좌표·시각을 분리한 한 공통 투영을 사용한다. 임의로 ‘제목만 같으면 같다’거나 ‘revision만 같으면 같다’고 판단하지 않는다. 새 저작 필드를 추가하는 구현은 이 투영에도 반영해야 한다. 이번 변경에서 내용이 그대로인 상태 전이의 허용은 `reviewing → verified`로 한정한다. 다른 상태 전이를 허용하려면 그 의미와 소비자의 적용 조건을 별도로 검증해야 하며, 모든 상태값에 임의의 높고 낮음을 매겨 승계하지 않는다.

과제의 종결 여부는 내용 인용과 행동 적용을 분리한다. 과제 A의 기존 결과를 읽은 B는 A가 완료됐다는 이유만으로 내용을 다시 연구할 필요가 없다. 반면 A를 선택·보류·완료 판정하는 계획은 A의 실제 처분을 확인해야 한다. 따라서 기존 `task_reference_changes`의 일괄 `task_ended` 거부를 제거하는 변경은 아래 대상 검사와 같은 커밋 단위로 반영한다. 이 검사를 먼저 삭제하고 대상 검사를 나중으로 미루지 않는다.

수신에서 실행할 순서는 다음과 같다.

1. `engine._call_steps`의 입력 준비에서 자기 계약과 선언된 `inputs/reuse/dependencies`의 `decision_basis`를 포착한다. `should_stop`도 같은 비교 규칙을 사용하여 정상적인 진행 표시의 변화만으로 실행이 중단되는 일을 막는다. 사용자 정지·권한 회수·목표·정책 변경은 기존 별도 검사에 남긴다.
2. 반환에서는 `submission.reported_references`가 실제 사용 참조를 모으고 **원 입력 snapshot**에서 근거를 추가한다. 현재 누락된 `task_conditions`의 의존·발생 조건 참조, 개정 대상, 선택·완료 판정 대상도 구조 필드에서 회수한다. 새 후보의 임시 제목과 현재 기록 ID, 역사적 artifact 참조는 서로 구별한다.
3. 내용·출처·효력이 그대로면 역할별 적용 조건을 검사한다. 계획의 선택·보류는 입력 모집단을 정확히 덮어야 하고, 선택은 현재 `task_ready`를 통과해야 한다. 완료 판정은 대상의 계약 해시와 **판정할 결과 집합**이 원 입력과 같아야 한다. 새 결과가 같은 대상에 추가됐다면 그 대상의 완료 판단을 현재 자료에서 다시 받는다. 단순 참고 인용에 허용한 결과 추가를 완료 판정에도 자동 허용하지 않는다.
4. 여러 과제를 처분하는 계획의 일부 대상이 종결되었거나 판단 대상의 계약이 바뀌었으면, 영향을 받은 위치를 밝혀 원 역할에 현재 입력의 재판정을 요청한다. 실행기는 낡은 항목을 삭제한 나머지를 부분 적용하지 않는다. 반면 연구 수행·계약 검토 action이 가리키는 과제가 이미 `completed` 또는 `closed`이거나, 동일성 검토·고정 질문 조사 action이 가리키는 자리가 더 이상 유효하지 않으면 그 action을 종료하고 원 결과만 보존한다. 이 경우 새 재판정 요청을 자동 생성하지 않는다.
5. 주 산출과 확장이 모두 유효하면 기존처럼 한 적용 단위로 반영한다. 어느 단계에서 실패해도 원 출력·파일·체크포인트를 보존하며, 이전 상태로 되돌리는 현재의 원자적 적용 구조를 유지한다.

계약 승인의 재사용도 같은 전제를 검사해야 한다. [engine._apply의 계약 검토 분기](../../../.claude/skills/do-math/scripts/do_math/engine.py:2031)는 현재 검토 출력과 자기 계약 근거만 과제의 `reviews`에 넣는다. 여기에 승인 실행의 `decision_basis`와 `source_basis`, 입력 snapshot, 검사 정책 판본을 결합한다. 저작 AI가 해시를 만들어 제출하게 하지 않는다.

`lifecycle_engine._refresh_readiness`와 `planning.task_ready`는 공통 `contract_review_current` 판단을 사용한다. 자기 계약·목표·정책이 같아도 승인에 사용한 A의 본문이나 효력이 달라졌으면 B의 승인을 현재 사용하지 않는다. 과거 승인은 보존하고 `inputs_current=false`, 변경 근거를 기록하며 **B의 계약을 자동 개정하지 않고 새 독립 계약 검토**를 요청한다. 새 검토가 개정 필요를 판정하면 그때 후보 준비로 보낸다. 이미 선택되어 queue에 있는 B도 파견 직전 같은 검사를 받는다.

동일한 B 계약의 재검토는 의존 근거가 다르므로 요청 식별에 `review_basis_key`를 추가한다. 값은 자기 계약 근거와 새 `decision_basis`의 해시다. `_enqueue`, `_dispatchable`, `_refresh_readiness`의 `blocked_review` 판정, 실패 해소는 이 키를 함께 사용한다. 그래야 옛 전제에서 실패한 대기 검토가 새 전제의 검토를 막거나, 두 검토의 결과를 같은 승인으로 합치지 않는다. 구 승인에 필요한 근거가 없으면 현재 승인을 임의 생성하지 않는다. 정확한 과거 입력과 실행 출력으로 복원할 수 있는 경우만 복원하고, 그렇지 않으면 근거 부족으로 새 검토가 필요하다고 기록한다.

상태 변경 뒤의 연결도 확인한다. 과제 개정·원자료 교체·지식 개정 또는 무효화·목표와 정책 변경은 승인 재사용과 queued 수행을 다시 평가하는 사건이 되어야 한다. `knowledge._propagate`, `_invalidate_goal_currentness`, `_solution_basis`와 `_ensure_academic_followup`는 기존 사용 정지·완료 이력 보존의 의미를 유지한다. 새 비교 함수를 이곳에 무차별 치환하지 않는다. 과제 완료 판정의 현재 효력이 없어지면 그 완료를 필수 의존으로 쓰는 후속은 기다리고, 이미 완료·닫힌 과제의 이력은 다시 열지 않는다.

검증은 ‘허용해야 할 변화’와 ‘막아야 할 변화’를 짝으로 둔다. 계약 불변인 리뷰 추가·선택 상태 변화·일반 인용의 결과 추가는 수락한다. 계약 변경·기존 결과 수정·원자료 교체·사용 정지·신뢰 환경 무효화는 막는다. A 개정 뒤 B의 과거 승인은 사용하지 않되, A의 보류 이유만 바뀌면 재검토하지 않는다. 같은 판본의 동료 검토는 계속 수락하고, 새 제안 판본은 전건 검토한다. 목표 감사·수학 관계·신뢰 전환·학술 후속의 기존 엄격한 검사도 유지되는지 회귀 확인한다.

기존 분석의 35건은 전제 기록 변경을 이유로 상태 적용이 거부된 AI 실행 35회다. 계획 17회·계약 검토 5회·후보 준비 5회·운영 점검 8회이며 연구 수행 반환은 없다. 그 26/6/3 변경 분류를 이 검증의 표본 원천으로 사용한다. 이것은 각각 ‘계약·기존 결과·종결 불변의 변화’, ‘인용 계약 변경’, ‘지식 검증 상태 상승’이며, 3건 중 2건에는 과제 종결도 겹친다. 이 수치만으로 26건 전부나 그 26건에 검증 상태 상승 3건을 더한 29건 전부를 수락할 수 있었다고 선언하지 않는다. **각 출력의 실제 선택·승인·완료 판정과 위 적용 조건까지 대조한 뒤** 보존 가능한 판단과 필요한 재판정을 기록한다.

**03. 형식 수리, 전제 재판정, 공급자 대기를 서로 다른 복구로 연결한다.**

현행 `_call_steps`는 수신·적용 예외를 대부분 `output validation`으로 묶어 출력 수리, 운영 진단, 재시도로 연결한다. 정상 상태 변화의 오거부는 02에서 없앤다. 실제 전제 변경이 남으면 이미 무엇이 바뀌었는지 기계가 알므로, 그 사실을 다시 진단하는 AI 호출보다 원 역할의 현재 판단으로 바로 연결하는 편이 간단하다.

실행 결과의 `error_kind`를 `output_validation`, `currentness_changed`, `provider_limit`, `execution_failure`로 구별하고 상세에는 원 증거와 변경 위치를 넣는다. 정지·대상 종결은 현재의 보존 outcome을 유지한다. 이 분류는 수학 판정값을 바꾸지 않는다. 슬롯 반환과 원 자료 보존을 마친 뒤 복구 분기를 선택한다.

| 실패 종류 | 새 후속 | 반복 한계와 해소 |
|---|---|---|
| 주 JSON·필드·참조 형식 오류 | 기존 `max_output_repairs` 안에서 출력 수리 | 같은 오류의 한도 소진은 기존 운영 진단으로 보낸다. |
| 실제 판단 전제 변경 | 변경 근거와 이전 결과를 받은 동일 역할의 새 판단 | 동일 action 계보에 자동 갱신 1회를 허용한다. 재충돌이면 보류하고 계획·운영 담당이 충돌 구조를 판단한다. 새 ID로 한도를 초기화하지 않는다. |
| 이미 끝난 대상·자리 | 보존 후 해당 요청 종료 | 옛 대상을 되살리는 출력 수리를 열지 않는다. |
| 확인된 공급자 한도 | 05의 공통 대기 | 한도 중 같은 공급자의 운영 진단을 만들지 않는다. |
| 원인 미확정 호출·환경 실패 | 기존 운영 진단 | 진단 후 재시도 제한과 명시적 새 진단 경로를 유지한다. |

`currentness_changed`에서는 새 `action.refresh`에 `{execution_id, changes, attempt}`를 둔다. `_context`의 이전 실행 선택은 현재 `repair/recovery`뿐 아니라 `refresh.execution_id`도 읽게 한다. 원 출력, 이전 확장, 보존 파일, 체크포인트, 새 입력과 변경표를 제공한다. 계약 검토는 새 `review_basis_key`를 받고, 계획은 새 ready 모집단과 판정 대상 집합을 받는다. 이전 내용 중 무엇을 재사용할지는 해당 AI가 판단하되 **최종 응답 전체**를 기존 제출 검사와 현재 적용 검사로 다시 확인한다. 새로운 부분 적용 장치는 만들지 않는다.

재시도의 동일 의무를 나타내는 `action.lineage_id`를 처음 요청할 때 부여하고, 수리·현재성 갱신·진단 재시도에서 유지한다. 여러 미시작 요청을 합쳤다면 `merged_action_ids`와 요청별 사건·개정 대상도 보존한다. `_resolve_failed_actions`는 역할·대상만 같다는 이유로 다른 실패를 지우지 않고 이 계보와 검토 자리·판본, 실제 처리한 개정 대상까지 대조한다. 새 일반 준비가 과거의 다른 준비를 대체하려면 계획·운영 판단의 명시적인 대체 근거가 있어야 한다. 미소비 사건은 현재처럼 다시 배정 가능하게 남긴다.

`waiting_actions`의 기존 `kind=execution_failure`를 유지하고 `failure_kind`로 상세 원인을 붙이는 방식을 기본으로 삼는다. 새 kind를 추가하면 `resume`, `_resolve_failed_actions`, `blocked_actions`와 검토 자리의 보류 검사도 그 kind를 알아야 한다. 기존 kind 안에 원인을 붙이면 이 소비자들의 기본 대기·해소 경로를 재사용할 수 있다. 현재성 전용 재판정 요청과 공급자 대기는 각 분기의 명시적 전이가 해소하며, 일반 `resume`은 그것을 무조건 재실행하지 않는다.

`계약/운영-점검.md`의 종료 뒤 진단 절에는 이 분류와 사용 범위를 적는다. `references/공통-실행.md`의 실패·수리 절에는 이전 결과 중 유효한 근거를 재사용하고 변경된 판단만 다시 하되 전체 응답을 다시 제출한다는 실행 지시를 넣는다. 운영 점검 자체가 실패한 경우의 재귀 방지와 고정 질문 조사를 원 자리로 돌려주는 `_finish_failed_investigation`도 각 분기에서 빠짐없이 호출한다.

완료 조건은 형식 오류에는 수리가, 전제 변경에는 새 입력의 판단이, 한도에는 대기가 선택됨을 실행 원장으로 확인하는 것이다. A 실패 뒤 A의 계보가 성공하면 A만 해소하고, 같은 역할의 B 실패는 남아야 한다. 실패 안내의 제거도 이 정확한 해소 사건을 사용한다. 원 응답과 이전 실패 이력은 어떤 분기에서도 삭제하지 않는다.

**04. Claude의 여러 응답 구간을 하나의 실제 CLI 실행으로 수집한다.**

현행 [claude_adapter.parse_jsonl](../../../.claude/skills/do-math/scripts/do_math/claude_adapter.py:12)은 init과 result가 각각 하나라고 요구한다. [claude_worker.run](../../../.claude/skills/do-math/scripts/do_math/claude_worker.py:79)은 마지막 사건에서만 `structured_output`을 꺼낸다. 원 실패 로그에는 같은 세션의 응답 구간 3개가 있다. 첫 구간은 계산이 아직 끝나지 않았다고 보고했고, 뒤 구간은 계산이 `gzip.open(mtime=0)` 오류로 끝났음을 반영했다. 따라서 첫 응답을 무조건 선택하면 마지막에 확인된 실패를 잃는다.

새 `claude_stream.py`에 외부 의존 없는 `parse_stream(raw)`를 두어 worker와 adapter가 같은 해석을 사용하게 한다. worker 직접 실행의 fallback import도 이 모듈을 포함한다. 다음 규칙을 설치 CLI 판본과 원 재현 로그에 결박한 지원 계약으로 채택한다.

1. JSON 객체·중복 키·비유한 수·완전한 행을 검사하고 모든 원 사건을 보존한다. 하나의 실제 invocation 안에서 `session_id`는 일관돼야 한다.
2. 첫 init에서 시작한 구간과 뒤의 알림 후속 구간을 구분한다. 뒤 구간은 같은 세션의 init이며 결과의 `origin.kind=task-notification`으로 식별되는 실제 관측 형식을 지원한다. 구간마다 결과는 하나여야 한다. 같은 구간의 중복 terminal, 새 구간이 없는 임의 assistant 후속, 다른 세션 혼합, 잘린 끝은 허용하지 않는다.
3. 성공한 구조화 응답을 가진 **마지막으로 완결된 유효 구간**을 제출 후보로 삼는다. 후속 구간이 아무 모델 작업·도구·새 출력도 없는 성공 알림(`num_turns=0`)이면 앞의 제출을 유지할 수 있다. 후속 구간에서 새 작업이 있었는데 구조화 제출이 없거나 오류·미완료로 끝났으면 옛 제출로 성공을 덮지 않는다.
4. 반환에는 선택한 결과의 행 번호·구간·해시와 대체한 이전 결과를 남긴다. worker의 `final.txt`는 그 선택값으로 만들고 adapter는 같은 값과 비교한다. 마지막 구간을 선택한다는 사실이 앞뒤 수학 내용의 자동 병합이나 의미 승인인 것은 아니다.
5. `LocalCLIAdapter.collect`의 입력·스키마 영수증, 정상 종료, 로컬 Job 종료 확인과 중앙 역할 스키마·확장·파일 검사는 유지한다. 로그에 성공 JSON이 있다는 이유로 이 검사를 건너뛰지 않는다.

이 규칙은 최종 결과의 선택을 명시한 제안이며, 실제 CLI 호환을 이미 검증한 구현은 아니다. 구현 때 원 3구간 로그와 ‘알림만 추가’, ‘후속 정정’, ‘후속 실패’, ‘후속 작업 뒤 무제출’, ‘다른 세션’, ‘중복 결과’, ‘잘린 JSON’, ‘final 불일치’를 재생한다. 대표 Opus 실행으로 일반 제출과 백그라운드 완료 알림 뒤 정정 제출을 확인한다. 관측 형식과 다른 정상 구간이 나오면 그 원 로그에서 지원 규칙을 확장하고, 임의의 마지막 JSON 채택으로 해결하지 않는다.

사용량도 구간과 실행을 나눈다. 원 로그의 첫 두 `modelUsage`와 `total_cost_usd`는 같고 세 번째는 증가했다. 이 로그에서 세 번째 outputTokens 25,128은 첫 값 19,203과 후속 구간 output_tokens 5,925의 합이다. 이 로그에서 `modelUsage`는 누적값으로 보이며 각 `usage`는 구간값이다. `model_runner.run`은 현재처럼 마지막 구간 `usage`만 실행 전체 사용량으로 내놓지 않고 `usage_segments`, 마지막 `model_usage_reported`, `usage_scope`를 보존한다. 알려진 구간형 usage의 정해진 숫자 항목만 합산하고 누적 modelUsage는 다시 더하지 않는다. 이 로그에서 구간 합계와 modelUsage의 inputTokens는 서로 일치하지 않으므로 서로 대체하지 않는다. 가격표 기준 추정 비용은 실제 청구액으로 표시하지 않는다.

긴 계산은 `references/공통-실행.md`의 도구·제출 절과 `계약/연구-수행.md`에 연결한다. 예상 시간에 맞는 도구 timeout, 긴 계산 전 체크포인트, 실제 제공된 대기·결과 회수 도구 사용, 백그라운드 작업의 ID·종료·출력 확인을 명시한다. 존재하지 않는 감시 도구나 반복 sleep으로 완료 확인을 대신하지 않는다. 계산이 끝나지 않으면 `partial`과 남은 범위를 제출한다. 검사한 큰 JSON을 파일 참조 하나로 제출하는 새 반환 형식은 이번 필수 변경에서 제외한다. 수집기 수정 뒤 실제 재출력 비용과 실패가 남는 경우에만 별도 제안한다.

**05. 공급자 한도를 두 호출 입구에서 공유하고 실제 재관찰까지 연결한다.**

연구 실행기와 [scheduled_operator.check](../../../.claude/skills/do-math/scripts/do_math/scheduled_operator.py:207)는 각각 모델을 호출한다. 작업·운영 슬롯이 나뉘어 있어도 같은 Claude 이용 한도에 걸릴 수 있다. 이번 원 실행에서는 원 작업 8건 뒤 그 실패를 진단한 8건도 한도에 걸렸다. 이 경우 기술 원인을 다시 판단하는 모델 호출부터 억제해야 한다.

04의 파서는 원 `rate_limit_event`의 `status=rejected`, `rateLimitType`, `resetsAt`, 제한 창을 구조화한다. `allowed_warning`은 안내만 남긴다. scholarly 도구의 429나 문헌 접근 실패는 Claude 공급자 한도 사건으로 해석하지 않는다. `model_runner`는 최종 실패가 공급자 한도임을 확인한 경우 `failure={kind:"provider_limit", provider, observed_at, retry_at, limit_windows, evidence_ref}`를 반환한다. 해제 시각을 확정할 수 없으면 null과 원문을 보존한다.

두 프로세스의 호출 전 검사는 기존 `session_slots/<instance>/slots.sqlite3` 안의 작은 `provider_waits` 테이블을 공유한다. 이는 연구 지식이나 판단의 새 저장소가 아니라 **공급자 호출 가능 시각과 단일 재관찰 소유권**을 저장한다. key는 이 인스턴스의 provider이며, 현재 구성처럼 한 provider의 인증 문맥 하나를 사용한다는 범위를 명시한다. 여러 계정·인스턴스를 묶는 전역 예산으로 확대하지 않는다. 작업·운영 슬롯의 용량과 분리는 그대로 유지한다.

테이블에는 `provider`, `generation`, `state`, `retry_at`, `evidence_ref`, `probe_owner`, `probe_started_at`을 둔다. state는 `waiting`, `checking`, `available`이다. `SessionSlots.acquire`와 같은 SQLite 트랜잭션 안에서 가용성 및 슬롯 예약을 검사해, 한도 확인과 호출 시작 사이에 중복 재관찰이 생기지 않게 한다. 세션 예산이 아닌 호환 실행도 provider 검사 부분을 재사용할 수 있어야 한다. `snapshot`과 `status`는 슬롯 부족과 공급자 대기를 분리해 표시한다.

첫 확정 제한 뒤 새 호출을 기다리게 하고 이미 진행 중인 실행은 개별 종료·반환을 회수한다. 기존 호출 하나의 한도 실패만으로 다른 실행의 정상 결과를 폐기하지 않는다. `engine._call_steps`, 구 모드의 `_run_inline_review`, `scheduled_operator.check`는 모두 호출 직전에 같은 provider 검사를 한다. 두 입구의 결과 처리도 한도 정보를 기록한다. 한도를 진단하려는 같은 공급자의 AI는 열지 않는다.

실패한 원 행동은 `waiting_actions`의 기존 실행 실패 항목에 `failure_kind=provider_limit`, 해당 generation, 다음 시각을 붙여 보존한다. 부분 파일·체크포인트는 기존 수집을 마친다. 해제 뒤 재시도는 새 실행 ID와 원 `lineage_id`, `recovery.execution_id`를 받아 `_context`가 기존 파일·원 결과·외부 operation을 복원하게 한다. 검토 자리의 고정 질문은 한도 대기를 최종 조사 포기로 오인해 `_finish_failed_investigation`으로 닫지 않는다. 실제 재시도를 포기한 경우에만 기존 미완료 인계로 마친다.

재관찰은 시각 저장에서 끝내지 않는다. `scheduled_operator.schedule`, `cli.build_parser/execute`, `operator_schedule.ps1`에 **모델을 부르지 않는 `operator wake` 진입점과 해당 인스턴스의 일회성 wake 예약**을 추가한다. 기존 정기 운영 예약과 연구 예약은 유지하고, wake 예약은 공급자 generation별로 하나만 등록·갱신한다. `operator status/uninstall/hold`도 이 예약을 조회·정리·차단해야 한다. HOLD나 사용자 정지 뒤 이미 예약된 wake가 실행돼도 연구와 모델을 시작하지 않는다.

`retry_at`이 지나면 두 호출 입구는 먼저 실제로 수행할 허가된 action이 있는지 검사한다. 연구 실행기는 현재 권한·계약·대기 조건을 통과하는 queue의 가장 앞 action을, 독립 운영은 정기 점검 도래나 명시적 운영 요청이 있을 때 그 운영 action을 대상으로 한다. 실행할 action이 있는 프로세스 중 SQLite에서 먼저 `waiting → checking` 전이에 성공한 하나가 재관찰 소유자가 된다. 두 입구 사이에 별도의 우선순위는 두지 않는다. wake는 연구 실행기가 없고 사용자 차단이 없으면 기계 진입점을 시작해 이 검사를 하게 할 뿐, 독립 운영의 호출이나 새 연구 판단을 만들어내지 않는다. 실제 action이 없으면 모델을 부르지 않고 다음 사건을 기다린다. 소유권 확인과 해당 호출의 예약은 같은 gate 트랜잭션으로 결박한다. 별도의 의미 없는 모델 ping을 먼저 소비하지 않는다. 동일 provider의 다른 호출은 이 한 번의 응답이 올 때까지 기다린다. `checking → available` 전이는 같은 generation의 지정 probe_owner만 수행할 수 있고, 그 사이 새 제한이 등록되어 generation이 바뀌었으면 옛 정상 응답으로 새 대기를 해소하지 않는다. 정상 응답 또는 한도 외의 확정된 응답이면 provider 차단은 해소하되 해당 action의 형식·현재성 문제는 03으로 보낸다. 다시 한도면 새 근거와 다음 시각을 기록한다. 소유 프로세스가 사라졌으면 기존 소유 잠금·Job 종료 확인을 거쳐 재관찰 권한을 회수한다.

알려진 제한 창들이 동시에 호출을 막으면 모두 해제되는 시각을 사용한다. 시각이 없으면 제안 기본값 `provider_retry_initial_seconds=300`, `provider_retry_max_seconds=7200`의 유한 지수 대기를 사용하고 실제 반영값은 인스턴스 설정에 남긴다. 이 수치는 공급자가 해제될 시각의 예측이 아니라 재확인 간격이다. 300초는 현재 관찰 간격, 7,200초는 현재 정기 운영 간격과 맞춘 제안 기준이며 성능 평가로 최적화된 값은 아니다. 설정 검사는 최대 간격이 최초 간격 이상인지도 확인한다. 원장의 시각과 예약이 다르거나 예약 등록에 실패하면 정기 운영의 **Python 진입부**가 모델 호출 전에 예약을 재조정한다. 연구 실행 프로세스를 시작해도 되는지 검사하는 `engine_start_guard`에는 provider wake의 진입 조건을 추가한다. runtime이 공급자 때문에 waiting이고 `retry_at`이 도래했으면, 다른 사용자 차단이 없는 경우 재관찰을 수행할 연구 실행기를 시작할 수 있다. 이때 provider를 available로 미리 바꾸지 않는다. 실행기 안에서 한 action만 checking 소유권을 얻고 실제 응답으로 가용성을 판정한다. 일반 사용자 대기와 paused는 이 분기로 풀리지 않는다.

외부 행동이 `unknown`인 경우 provider가 풀렸다는 이유로 재전송하지 않는다. 기존 external 원장과 안정된 논리 요청 ID를 이어받는다. 전체 연구 종료·사용자 정지·허가 철회·변경된 계약은 재관찰보다 먼저 검사한다. `--watch` 실행기는 Claude를 호출하지 않는 허가된 Lean 검사 등 기계 action을 계속 처리할 수 있다. 여러 provider를 명시적으로 배정한 다른 인스턴스에서는 한도에 걸리지 않은 provider의 기존 배정도 진행할 수 있다. 이 연구는 Opus 5만 배정하므로 다른 provider로 우회하지 않는다.

완료 검증은 가짜 시계·공급자 대역·실제 SQLite 다중 프로세스 경쟁·예약 어댑터 대역을 결합한다. 제한 전파 뒤 새 호출 0회, warning은 차단하지 않음, 자료원 429는 전파하지 않음, 동시 실패에도 재관찰 1개, 재시작 뒤 대기 보존, wake 시 단일 실제 action, 재제한 시 재대기, HOLD 중 호출 0회, 복원된 부분 자료와 남은 질문의 전달을 확인한다. 실제 공급자 한도를 고의로 소진할 필요는 없다.

**06. 실제 기한, 마무리 예고, 관찰 신호를 서로 구별한다.**

현재 `_context`의 `execution_limits`는 설정값만 주고 `_call_steps`는 입력 준비 뒤 실제 기한을 정한다. 작업 예산에는 부모 run 기한이, 운영 예산에는 부모 기한과 `call_timeout_seconds` 중 이른 것이 적용된다. 또한 기한 도래는 즉시 종료 조건이다. 작업자가 남은 시간을 알고 정상 제출하도록 하려면 실제 기한을 전달하고 종료보다 먼저 마무리를 요청해야 한다.

`_call_steps`에서 입력 준비 시작 때 run의 단조 시계 기한을 전달하고, 입력 준비·저장 뒤 최종 실행 기한을 계산한다. 고정 프롬프트에는 시간 한도의 종류와 실행 공간의 `execution-window.json` 위치를 넣는다. 모델 runner가 일시 중단 상태의 Windows Job을 만든 뒤 `on_started` 콜백을 호출하는 시점에 이 파일을 한 번 원자적으로 기록한다. 이 콜백이 끝난 다음 Job을 처음 재개하기 전에 기한·정지를 다시 확인한다. 파일에는 `{execution_id, effective_deadline_at, remaining_seconds_at_start, deadline_source, finish_notice_at}`을 남긴다. 모델이 실행을 시작할 때 읽고, 긴 도구를 시작하기 전 다시 읽게 한다. 고정 제출 검사 입력에 오래된 ‘남은 초’를 진실인 것처럼 넣지 않는다. 단조 시계가 제어 기준이고 UTC 시각은 설명·기록용이다.

마무리 예고 구간의 상한으로 `finish_notice_seconds=60`을 제안한다. 실제 run의 예고 구간은 `min(finish_notice_seconds, run_timeout_seconds/10)`이고, 운영 실행에는 여기에 `call_timeout_seconds/10`도 적용해 작은 값을 쓴다. 기본 run 7,200초·운영 호출 600초에서는 60초이며, run이 30초라면 3초다. 남은 시간이 그 실행의 실제 예고 구간 이하이면 `finish-request.json`을 한 번 기록한다. 이 파일은 확보한 결과·근거·부분 완료·남은 의무를 정리해 정상 제출하라는 안내이며 실행 권한 회수가 아니다. `stop-request.json`, `stop_requested`, `after_stop`를 재사용하지 않는다. 현재 `_call_steps`는 정지 뒤 정상 응답을 보존만 하므로, 두 파일을 합치면 예고의 목적을 달성하지 못한다. `execution-window.json`에는 계산한 `effective_notice_seconds`도 기록한다. 짧은 run에서도 최초 착수부터 막히지 않아야 하며, 하드 기한을 늘리지는 않는다.

스케줄러는 run 종료 예고 구간에 새 일반 action을 시작하지 않고, 이미 시작한 실행의 결과 회수와 필요한 기계 제어만 계속한다. 시작 전에 남은 시간이 해당 run의 계산된 마무리 구간보다 짧으면 요청을 다음 run에 남긴다. 이는 수학 과제의 예상 완료 시간을 기계가 판정하는 규칙이 아니라, 시작하자마자 정리해야 할 호출을 피하는 운전 규칙이다. 실행 중인 작업을 대상으로 하는 내부 운영 점검(`live_review`)을 새로 열 필요가 있을 때도 남은 시간·운영 한도를 적용하며 사용자 정지·권한 회수는 모델 점검을 기다리지 않는다.

하드 기한에는 기존 Job 종료와 부분 파일·체크포인트 회수를 수행한다. 마무리 예고 뒤 하드 기한 전에 제출된 정상 응답은 수락 대상이고, 실제 사용자 정지·권한 회수 뒤 반환은 기존처럼 보존 대상이다. 슬롯은 실제 종료를 확인한 뒤 반환한다. 독립 운영의 timeout과 Windows 예약 작업의 실행 상한도 이 기한·회수 여유와 모순되지 않게 `scheduled_operator.schedule` 및 `operator_schedule.ps1`에서 대조한다.

관찰은 [model_runner의 observe](../../../.claude/skills/do-math/scripts/do_math/model_runner.py:64)와 [ObservationTracker.observe](../../../.claude/skills/do-math/scripts/do_math/observations.py:104)를 함께 고친다. 새 바이트가 왔지만 JSONL 한 행이 아직 끝나지 않은 경우를 `transport_bytes_received` 관측으로 보내고, 완성된 모델 텍스트·도구 시작·도구 완료·체크포인트·연결 신호를 구별한다. 현재처럼 모든 tick 외 사건을 같은 활동으로 세지 않는다. 원 관측에는 마지막 전송 시각과 마지막 의미 있는 작업 사건 시각을 따로 보존한다.

`pending_tools`에는 도구 ID와 시작 시각·관측 가능한 종료 한도를 유지한다. 정상적인 장시간 도구 또는 생성 중인 응답은 일반 idle만으로 반복 점검하지 않고 `tool_wait`·`output_streaming` 상태와 다음 재관찰 시각을 제공한다. 무기한 면제하지 않으며 기존 관찰 간격으로 한 번의 상태 확인을 요청하고 동일 근거의 중복 요청은 합친다. `blocked/no_progress` 체크포인트와 계약의 관찰 규칙은 계속 반영한다. 전송 증가나 ping을 수학적 진전으로 승격하지 않는다.

`references/공통-실행.md`에는 시작 시 실행 창 읽기, 긴 도구 전 시간 확인, 예고 때 실제 부분 결과 제출, 실제 정지 때 새 연구 중단을 인접한 문단으로 설명한다. `계약/운영-점검.md`에는 전송 중·도구 대기·무응답의 구별과 점검 한도를 적는다. 생산자가 쓰는 `checkpoint.json`의 의미와 수집 방식은 유지한다.

검증은 기한 직전 착수 보류, 입력 준비가 오래 걸린 경우의 실제 잔여 시간, 예고 후 정상 수락, 하드 기한 회수, 사용자 정지 우선, Job 미종료의 슬롯 유지, 부분 JSONL 수신, 오래 걸리는 도구, ping만 반복하는 경우를 포함한다. 오인 점검 감소는 원 관측을 재생해 전후 호출 사유와 횟수를 비교한 뒤 보고한다. 문구와 타이머가 추가됐다는 사실만으로 운영 비용 절감을 확정하지 않는다.

**07. 질문과 실패 안내를 정확한 소유자·해소 근거에 연결한다.**

현행 `runtime.questions`는 문자열 목록이다. `_apply`가 여러 역할의 질문을 모으고, `_run_parallel`과 구 실행 루프는 queue가 비었을 때 질문이 하나라도 있으면 기다린다. `_controls`의 새 사용자 입력은 목록 전체를 지우며, 역할 하나의 성공 뒤에는 그 역할 이름으로 시작하는 실패 안내를 일괄 제거한다. 질문에 표시용 ID만 붙여서는 이 소비 경로가 바뀌지 않는다.

실패 안내는 `waiting_actions`에서 계산한다. 별도의 질문 문자열로 다시 저장하지 않는다. 기존 `_resolve_failed_actions`가 03의 정확한 요청 계보를 해소하면 그 안내도 사라진다. 계약 반려의 세부 질문은 과제의 `reviews`, 동일성 검토의 질문은 `review_cycles`, 수행의 남은 질문은 과제 결과에 이미 보존되므로 그 원문을 정본으로 사용한다. 원문을 새 질문 저장소에 복제하여 두 군데서 수정하게 만들지 않는다.

질문을 현재 후속과 연결하는 `runtime.question_links`를 추가한다. 항목은 `{id, origin_execution_id, origin_field, owner, target_ids, status, resolution_ref}`다. `origin_field`는 원 출력의 `questions/0`처럼 실제 문장을 가리킨다. owner는 `user`, `research`, `operations`, `unclassified`이며 status는 `open`, `resolved`, `superseded`다. 같은 문장이라도 다른 과제·실행에서 생긴 질문을 문자열만 보고 합치지 않는다. ID는 실행기가 부여한다.

모든 역할에 복잡한 새 질문 객체를 강제하지 않는다. 기존 `questions: string[]`는 유지한다. 의도 해석의 `needs_clarification=true`와 외부 grant 요청처럼 소유자가 명확한 기계 경로는 실행기가 연결한다. 그 밖에 AI가 사용자 결정이나 운영 수리를 명시적으로 요청할 때는 `question_routes` 확장에 `{question_index, owner, target_ids, reason}`을 쓴다. owner는 이 제출에서는 `user|research|operations`다. 인덱스는 같은 주 응답의 질문, 대상은 제공된 기록이어야 한다. 라우팅이 없는 일반 연구 질문은 원 역할과 연구 후속에 남기며, 사용자 답이 필요하다고 자동 추정하지 않는다.

이 확장은 일반 내부 역할에 제공하되 평가 보충과 검토 자리의 고정 질문 조사는 기존 제한을 유지한다. 평가 보류는 `model_assessment_deferrals`에서 연결한다. 동일성 검토의 미공개 질문은 원 계보 안에 유지하며, 계보가 공개되는 `_publish_identity_review_result`에서만 일반 후속으로 연결한다. 검토 질문을 사용자 질문으로 바꾸어 독립 심사나 고정 질문 조사를 우회하지 않는다.

실행의 차단은 질문의 존재가 아니라 **실제 필요한 조건**이 맡는다. 사용자 결정이 필요한 대상으로 명시된 과제·action만 기다리게 하고, 독립 작업은 계속한다. 내부 연구 질문은 기존 계획·준비 사건으로 한 번 배정한다. 운영 수리 질문은 해당 실패 요청·독립 운영의 다음 행동으로 연결한다. 새 사건·새 입력·명시한 재관찰 시각 없이 같은 질문 때문에 빈 계획이나 준비를 즉시 다시 열지 않는다.  `max_cycles`, 정기 탐색, HOLD와 권한 검사는 유지한다.

`input`은 질문을 지우지 않고 `responds_to`라는 선택적 질문 ID 목록을 받아 보존한다. 사용자 자유 문장만 온 경우에도 원문을 저장하고 의도 해석이 어떤 질문에 답했는지 제안하며, `intent_interpretation`의 독립 대조 단계(`stage=check`)가 그 대응을 대조한다. 구조화 `decision`에는 선택적 `resolves_questions`를 넣고 실제 적용된 결정과 대상에 결박한다. AI가 사용자 질문을 스스로 ‘답변됨’으로 만들지는 못한다. 연구·운영 질문은 원 소유자의 수락된 결과가 `question_resolutions` 확장으로 `{question_id, disposition, evidence_refs, reason}`을 반환해 해소한다. disposition은 `resolved|superseded`이며 source와 권한을 대조한다. `question_resolutions`는 연구·운영 소유 질문만 그 역할의 권한 안에서 해소한다. user 소유 질문은 수락된 의도 대조와 실제 적용된 사용자 결정에 결박될 때만 해소하며, 일반 AI 확장의 해결 선언으로 닫지 않는다. 질문 해결은 과제 완료·수학 승인과 별개다.

수정 위치는 `engine._apply/_controls/_resolve_failed_actions/_run_executor`, `scheduler._run_parallel/_initial_plan_waits`, `review_engine._publish_identity_review_result`, `governance.apply_decision/interpretation_schema`, `submission.extension_schema/payload_issues`, `cli`의 input·decision 경계다. `status.questions`는 열린 사용자 질문의 문자열 보기로 유지하고, 상세 `question_links`와 실패 안내·연구 후속을 따로 제공한다. `_context`는 역할에 필요한 공개 질문만 원문 참조와 함께 제공한다. `context_store`에는 새 목록의 고정 참조 외부화를 연결한다.

아래는 구 인스턴스를 변환해 계속 사용할 경우의 호환 처리다. 과거 snapshot의 질문 79개 문자열을 자동으로 의미 분류하지 않는다. 원 실행 출력·대기 항목과 정확히 연결되는 것은 출처를 복원하고, 그렇지 않은 것은 `unclassified`로 보존한다. 미분류 상태를 임의의 사용자 승인으로 해소하거나 모두 전역 차단으로 승격하지 않는다. 이번에는 새 연구를 만들 예정이므로 이 구 목록을 새 runtime으로 복사할 필요가 없다.

완료 검증은 같은 역할의 A·B 실패 중 A만 성공했을 때 B가 남는지, 무관한 사용자 입력이 기존 질문을 지우지 않는지, 한 질문에 답한 결정이 다른 질문을 닫지 않는지, 내부 연구 질문이 후속 계획을 한 번 열고 독립 작업을 막지 않는지 확인한다. 검토자의 비공개 질문이 다른 동료 입력에 노출되지 않아야 한다. 기존 문자열 보기와 상세 목록은 같은 원문·출처를 가리켜야 한다.

**08. 요청 병합과 입력 구성은 현재의 손실 없는 전달 방식을 보완한다.**

입력 최대 463,641바이트와 무선택 계획 8건은 측정할 신호다. 자동으로 낭비량으로 집계하지 않는다. `contracts.render_prompt`, `engine._context/_planning_history/_input_artifacts`, `context_store.fit_context`에 구성별 바이트 계측을 추가한다. 공통 문서, 역할 계약, 스키마, 현행 과제, 전체 목록, 과거 이력, 복구 자료를 구분하고, 실행에는 전체 바이트·구성별 바이트·축소 조치·입력 준비 시간만 기계적으로 기록한다. 토큰은 CLI가 보고한 값이며 바이트에서 환산해 확정하지 않는다.

현재 `fit_context`는 한도 초과 뒤 큰 객체를 고정 원문 참조로 바꾼다. 우선 적용할 단순 개선은 `tasks`의 오래된 results·reviews·revision_history와 과거 repair 원문을 **역할에 필요한 현행 계약·결과 목차와 정확한 원문 참조**로 분리하는 것이다. 현재 과제 본문, 계획의 ready 전건과 assessing 전건, 진행 중 개정 대상, 필요한 실패 의무는 직접 남긴다. 동일성 검토의 현행 제안 전문·자기 메시지·공개 시점 규칙은 유지한다. 공통 규칙을 파일로 이동할 경우 `SKILL.md`의 역할 읽기 대응표를 함께 바꾸고 실제 prompt·manifest의 지급 결과를 검사한다. 파일이 존재한다는 사실만으로 전달됐다고 하지 않는다.

기계가 새 자연어 요약을 만들어 원문을 대체하지 않는다. 기존 생산자가 쓴 summary와 고정 필드의 목차를 사용하고, 내용 판단 전에 필요한 원문을 읽게 한다. `submission.install_tools`에는 여전히 완전한 고정 검사 입력을 제공한다. 프롬프트의 축소 보기와 제출 검사기가 검증하는 모집단이 달라지지 않게 같은 원 집합에서 생성한다.

요청 병합은 `_enqueue`와 `_refresh_readiness`의 사건 배정을 한 규칙으로 맞춘다. 현재 `_refresh_readiness`가 직접 `event_refs`를 덧붙이는 경로도 개정 대상·질문·실패 계보를 잃지 않게 한다. 병합은 아직 실행되지 않은 동일 역할·판단 범위에만 적용한다. `assessment_targets`, `review_basis_key`, 검토 자리·단계·회차, 목표 감사 basis가 다르면 서로 다른 요청이다. `reasons`, `event_refs`, `requested_by_refs`, 개정 대상과 미해소 의무는 합쳐 보존한다. 이미 시작한 실행의 입력에는 추가하지 않는다.

빈 계획을 생략하는 고정 규칙은 추가하지 않는다. 8건 각각에 대해 입력 사건, 대기열, 결과 요약, 질문·처분을 대조하여 ‘새 정보가 없는 동일 판단 반복’인지 분류한다. 그 원인이 중복 사건이면 그 사건의 생성·소비를 고치고, 실제 대기 판단이었다면 보존한다. `same snapshot`만으로 중복을 판정하지 않는다. 슬롯 반환·시각 도래·외부 입력은 같은 기록 내용에서도 행동 가능성을 바꿀 수 있다.

검증은 축소 전후 동일 ready·assessing 집합, 모든 필요한 원문 회수·해시, 권한·문서 지급, 검토 비공개, 미소비 사건 보존을 먼저 확인한다. 그다음 같은 고정 사례의 입력 바이트와 회수 횟수·실제 CLI 사용량·정상 수락률을 비교한다. 필요한 자료 회수가 더 어려워지거나 판단 누락이 증가하면 그 축약은 채택하지 않는다. 관측만 추가한 단계와 실제 절감한 단계를 보고에서 구별한다.

**09. 후보 준비의 계약 품질과 남은 수학 의무를 기존 역할에 연결한다.**

이번 계약 검토가 잘못된 전제·빠진 등식 증명·완료 기준의 혼동을 찾아낸 것은 유지할 성과다. 현행 후보 준비와 계약 검토 문서에도 이미 범위·양화·실패 분기·선행관계 대조가 있다. 같은 규칙을 더 길게 반복하는 대신 이번에 놓친 구체적 경우를 기존 판단 위치에 넣는다.

| 수정 문서·위치 | 추가·조정할 지시 | 후속에서 확인할 효과 |
|---|---|---|
| `계약/후보-준비.md`의 ‘현재 질문과 남은 차이’, 후보 작성 절 | 새 계약의 전제를 기존 반례·정확 계산·부정 결과와 대조한다. 유한 범위의 확인과 전칭 증명을 구별하고, 이미 반박된 강화 명제를 필수 전제로 재사용하지 않는다. | 계약 검토가 같은 반례를 다시 찾아 반려하는 반복을 줄일 수 있다. |
| 같은 문서의 inputs·reuse·선행관계 설명 | `inputs`는 필요한 자료, `reuse`는 적용할 기존 내용, `dependencies`는 선행 완료·사용 가능성이 필요한 관계임을 예와 함께 구별한다. 실제 선행 완료가 필요하면 `task_conditions`에 쓴다. | references가 있다는 이유만으로 완료 순서가 이미 제어된다고 오해하지 않는다. |
| `계약/작업-계약-검토.md`의 입력·완료 기준·선행관계 절 | 기존 반례와 모순하는 전제, 두 정의의 동일성을 사용하는데 연결 증명이 없는 경우, 구간 끝점과 빈 구간, 부분 결과·중앙 검증의 완료 주체를 대조한다. 통과한 항목은 통과로 판정한다. | 검토의 의무를 늘리는 대신 실제 수행의 오해를 만드는 결함을 먼저 찾는다. |
| `계약/연구-수행.md`의 report·remaining_work, `references/지식-저작과-재사용.md`의 남은 차이 절 | 목표에 제공한 내용, 사용 조건, 실제 증명·정확 계산·근사 계산·경험적 관찰, 아직 필요한 연결을 구분해 쓴다. | 후속 계획이 부분 결과를 다시 찾거나 일반 증명으로 과장하지 않는다. |
| `계약/연구-계획.md`의 완료 판정과 다음 준비 절 | 실제 결과가 닫은 의무와 남은 의무를 연결하고, 경쟁하는 충분조건·접근이 어떤 기존 과제를 대체할 수 있는지 근거로 판단한다. | 새 과제 수를 늘리는 대신 목표의 공백을 다루고 불필요해진 과제를 기존 철회 경로로 처분한다. |

수학적 의미를 정규식으로 검사하는 새 스키마는 만들지 않는다. 기존 `expected_result`, `completion_criteria`, `criteria_results.evidence`, `report`, `remaining_work`와 관계를 먼저 사용한다. 01의 지식 개정 수행 과제가 필요한 경우에는 그 과제가 쓸 입력과 바꿀 지식, 완료 기준을 정련하며 운영 준비 안에서 증명을 대신하지 않는다. 개정 때 기존 dependencies·발생 조건이 그대로 필요한지 다시 저작하게 한다. 현행 코드는 개정 계약의 기본 dependencies를 빈 배열로 만들므로, 유지할 조건도 `task_conditions` 확장에 명시해야 한다는 지시와 회귀 사례를 넣는다.

품질 평가는 이번 실제 반려 계약을 입력 판본과 함께 고정하고, 수정 전후 준비 산출을 독립 계약 검토에 대조한다. 비교 항목은 이미 주어진 반례를 반영했는지, 완료 판정이 가능해졌는지, 필요한 선행관계를 표현했는지, 유효한 탐색·부분 성과를 금지하지 않는지다. 평가 호출은 Opus 5만 사용한다. 반려 수 자체를 최소화하거나 같은 모델의 선호 점수만으로 개선을 선언하지 않는다. 기계 배선의 통과와 자연어 계약 품질의 향상은 별도 결과다.

**10. 출처 제출, Lean 선언명, 문헌 인계를 생산자와 수신자에 함께 반영한다.**

출처는 `engine._available_inputs`만 보고 허용 집합을 따로 만들지 않는다. 실제 제출 허용 범위는 [submission._reference_ids/validate_reference](../../../.claude/skills/do-math/scripts/do_math/submission.py:140)가 과제·실행·source·제공 locator·수집 파일을 함께 검사한다. 이 검사에서 `reference_catalog`를 만들어 입력과 오류 안내에 제공한다. 항목은 허용값, 종류, 고정 원문 위치, 현재 내용 의존인지 역사적 증거인지를 나타낸다. 오류에는 역할별로 실제 사용할 수 있는 가까운 참조 경로를 제시하되 존재하지 않는 ID를 자동 교체하지 않는다.

`reported_references`와 이 catalog는 같은 별칭 정규화를 사용한다. input 지식 경로를 인용한 경우 해당 ID의 원 입력 판본으로 묶고, 과거 artifact 경로는 역사적 바이트로 유지한다. 검토 자리의 source 집합은 `_research_source_spec`·`validate_research_reference`의 제한을 따르며 다른 검토자의 비공개 실행을 catalog에 추가하지 않는다. 생산자의 `check_submission.py`와 중앙 수신은 같은 코드 ZIP의 검사 규칙을 사용한다.

Lean은 [formal._ident](../../../.claude/skills/do-math/scripts/do_math/formal.py:18)를 고친다. 첫 구현은 현재 지원하는 점으로 나눈 이름의 각 부분에 **끝의 작은따옴표 `'` 하나 이상**을 추가 허용한다. 각 부분에서 끝의 prime을 제거한 본체는 현재의 시작 문자·문자/숫자/밑줄 규칙을 충족해야 한다. 이름 전체가 prime이거나 중간 공백·개행·따옴표 문자열·세미콜론·괄호를 포함하면 거부한다. 전체 Lean 식별자 문법을 완전히 지원한다고 주장하지 않는다. `sumTo_succ'`, `N.foo''`, 지원 범위의 Unicode 이름을 실제 컴파일과 공리 출력 파싱으로 확인한다.

미리보기 `formal_preview.main`과 중앙 `engine._formal`은 같은 `verify_lean`을 사용하므로 별도 이름 검사기를 만들지 않는다. 자동으로 붙이는 `#check/#print axioms`와 시그니처 경계 문자열도 prime 이름에서 정확히 대응하는지 검사한다. `sorryAx` 거부, 허용 공리·정확한 소스 해시·도구체인 검사는 유지한다. 연구 수행 계약과 CLI 지원 범위에 이름 문법을 설명한다.

문헌은 기존 `references/학술자료-활용.md`의 조사·보존 절에 **다음 실행이 이어 읽을 인계 기록**을 명시한다. 수행 보고 또는 수집 파일에 자료원, query/target, 요청 판본·범위, 실제 응답 상태, 확보한 component, 로컬 경로·해시, 실제 읽은 쪽·식, 미확인 범위, 다음 재조회 조건을 남긴다. 429는 검색 무결과나 문헌 부재로 바꾸지 않는다. Retry-After 등 자료원 근거가 있으면 그 자료원 재조회 시각으로 기록하고, 없으면 같은 조건의 즉시 반복을 피할 다음 행동을 설명한다.

이 기록의 다음 소비자는 `_context`가 복원한 `task-results`를 읽는 수행자·후보 준비·연구 계획이다. 이전 서버의 `scholarly://` URI만 넘기지 않고 보존된 바이트를 먼저 사용한다. 새 판본을 얻었으면 다른 자료로 식별한다. 원문을 읽지 못한 상태, 초록만 확인한 상태, 원문을 읽고 부분 대응을 찾은 상태를 보고에서 구별한다. 필수 원문이 필요하면 다음 과제·대기 조건으로 연결한다. scholarly MCP 서버 자체의 자료원 재시도 정책이나 이 작업 밖의 서비스 코드는 수정 대상으로 넣지 않는다.

검증은 원 출처 오류 2건의 참조를 재생해 올바른 제공값은 통과하고 미제공 ID는 거부하는지 확인한다. Lean은 두 소비 경로에서 같은 이름의 같은 소스를 확인한다. 문헌은 429·부분 component·기존 원문 재사용·판본 변경 사례에서 다음 역할이 실제 파일을 회수하고 미확인 범위를 유지하는지 점검한다. 문헌 조사의 성공률 향상은 이 전달 검증만으로 입증되지 않는다.

**11. 모델 정책과 운영 수리를 검증한 설치본으로 마무리한다.**

이번 연구의 모델 설정은 상·중·하 모두 `claude-opus-5`, 작업·운영 각각 해당 모델 3슬롯, `claude_only_assigned_model=true`다. 기존 잠금 구현은 유지하고 README·CLI 실행 계약·모델과 실행예산 문서에 옵션의 기본값 false, 인스턴스 범위, 전체 모델 ID 요구, 내부 보조 모델 제한, 운영자가 바꿀 수 없는 경계를 적는다. 다른 연구의 전역 기본 모델을 바꾸지 않는다. 모델 평가 등급도 보존하되 이 인스턴스에서는 어느 등급도 다른 모델로 연결되지 않는다.

`claude_only_assigned_model`은 Claude 내부 선택을 잠그는 옵션이며 모든 provider를 Claude로 제한하는 옵션은 아니다. 따라서 전용 연구의 사전 검사는 tier와 실제 배정·독립 운영 배정까지 모두 Opus인지 확인한다. `model_runner`의 각 결과에는 배정 모델과 파서가 읽은 `modelUsage`를 함께 남긴다. 허용하지 않은 실제 모델이 보고되면 후속 배정을 일시 정지하고 원 증거를 보존한다. 보고되지 않는 내부 소비를 관측했다고 주장하지 않는다.

현재 `profile`은 명령 표면 검사다. 그 의미는 유지한다. `scripts/probe_codex.py`를 provider를 선택할 수 있는 설치·대표 호출 도구로 확장하거나 공통 로직을 작은 `probe_cli.py`로 분리하여, 모든 역할·동적 검토·의도 해석·독립 운영 스키마의 정적 검사와 대표 Opus 실호출을 연결한다. 필수 검증은 스키마 주석 제거 뒤 제약 보존, 구조화 출력 수집, 파일·체크포인트·scholarly 지급, 정상 종료·정지, 보고 모델 대조다. 모든 역할에 같은 실호출을 반복할 필요는 없으며 프로토콜·권한 경계별 대표 호출과 대역 검사를 결합한다. 다른 provider의 회귀는 대역으로 확인한다.

독립 운영의 구현 수리는 [계약/독립-운영.md](../../../.claude/skills/do-math/계약/독립-운영.md:48)의 수리·반환 절을 보완한다. 종료 보고에는 원 실패의 재현, 수정 파일, 정본·사본 동기화, 검증한 설치 manifest, 통과·실패·미실행, 커밋 또는 미완료 diff의 소유와 다음 행동을 필수로 남긴다. 이미 허용된 로컬 수리를 다시 사용자 결정으로 올리지 않는다. 목표·필수조건·예산·외부 권한을 바꾸는 경우만 그 범위의 결정을 요청한다.

실행 시 `engine._installation_manifest`가 파이썬 모듈과 지급 문서를 고정하는 현재 방식은 유지한다. 운영 수리의 검증은 편집 중인 정본이 아니라 고정 사본에서 수행한다. 실제 사용할 정본과 생성 사본의 해시가 검증 판본과 일치해야 한다. 같은 설치본을 쓰는 활성 인스턴스가 있으면 각 실행을 회수하거나 별도 고정 설치본을 사용해 변경 판본이 섞이지 않게 한다. 이번 연구의 기존 HOLD는 수리 완료로 자동 해제하지 않는다.

운영 진단의 수치에는 execution ID별 원표를 붙인다. 입력 snapshot, 거부 시점 snapshot, 변경된 기록·필드, 실패 계보, 배타적 주분류와 겹치는 부원인을 기계적으로 기록한다. ‘자기 대상 계약 불변’을 ‘인용한 모든 계약 불변’으로 확대하지 않으며, 재현 시험 한 건의 통과를 35건의 의미 판정으로 사용하지 않는다. 이를 위해 추가 운영 검토 역할을 만들 필요는 없다. 독립 운영의 기존 증거 경로와 12의 내보내기를 사용한다.

현재 남은 8개 미커밋 파일은 14:02 운영 담당의 과제 인용 현재성 수리다. 정본 4개와 생성 사본 4개를 먼저 별도 diff로 보존한다. 구현자는 기존 diff의 동작과 시험을 검토하고, 02의 통합 변경에 필요한 부분을 반영하거나 대체한 근거를 남긴 뒤 커밋한다. 기존 diff를 무검토로 그대로 확정하지 않는다. 이미 커밋된 모델 잠금·스키마 호환과 초기 준비 대기·Git 저장 비용 수리는 새 결함으로 다시 구현하지 않는다. 이번 계획 문서의 커밋에는 기존 실행기 diff와 다른 작업의 scholarly 서비스 변경을 섞지 않는다.

**12. 상태와 타임스탬프를 원장에서 계산해 보여 준다.**

`ResearchEngine.status`와 `cli._human_status`의 출력을 확장한다. 과제별로 현재 계약 판본·업무 단계, 선택된 미시작 요청, 실제 활성 실행 ID, 마지막 수락 결과, 미해소 의무, 대기 이유·차단 대상, 다음 소유자·재관찰 시각을 함께 표시한다. `performing`을 실제 프로세스 생존으로, `completed` 과제를 목표 해결로 바꾸어 보여 주지 않는다. 수학적 근거 수준은 생산자가 보존한 분류·판정에서 읽으며 기계가 파일 이름으로 추측하지 않는다.

새 내보내기 `timeline --snapshot OID --format json|csv --timezone Asia/Seoul`을 `cli.py`와 원장 투영 함수로 제공한다. UTC 원시 시각을 보존하고 KST 표시에는 날짜와 UTC+09:00을 함께 쓴다. 내부 실행, 별도 독립 운영, 작업·운영 예산, 공급자 사용량은 집계 단위를 구별한다. 실행마다 입력 snapshot, action·lineage, 역할·대상, 배정·보고 모델, 시작·종료·기한, outcome·failure_kind, 보존 자료, 다음 행동을 내보낸다. 존재하지 않는 과거 시각은 null로 남긴다.

연구 snapshot과 로컬 슬롯·공급자 대기는 원자적으로 같은 시점의 자료가 아니다. status에는 각각의 조회 시각과 저장 근거를 적는다. 역사 timeline은 고정 snapshot의 내부 실행을 대상으로 하고, 독립 운영 로그를 합치면 별도 파일 해시·관측 시각을 함께 기록한다. 겹친 실행 시간의 합계를 실제 경과 시간으로 쓰지 않는다. 공급자 가격표 기준 추정과 실제 청구액, 입력 바이트와 토큰을 구분한다.

계획을 구현하기 전의 역사 기준은 다음과 같다. 이는 새 코드의 운영 성과가 아니다.

| 시각, 모두 2026-09-18 KST | 사건과 의미 |
|---|---|
| 12:16:22~12:22:50 | 첫 정확 계산의 다중 구간 결과 수집 실패 |
| 14:02~14:38 | 독립 운영이 과제 인용 현재성 검사를 부분 수리 |
| 14:07 | 부모 실행기 기한에 따라 진행 중 실행 3건 종료 |
| 15:34:08~15:37:25 | 원 작업 8건과 진단 8건이 공급자 한도로 미완료 |
| 18:20 | CLI가 안내한 한도 해제 시각. 실제 복구 성공을 관측한 시각은 아님 |
| 20:02~20:11 | 독립 운영이 실패를 대조하고 진단 요청·연구 재시작을 연결 |
| 20:19:17 | 사용자 정지 적용 |

이번 읽기에서도 동일한 정지 snapshot, 활성 실행 없음, 두 예약 비활성을 재확인했다. 정확한 재확인 시각과 읽은 코드 해시는 [implementation-evidence.json](implementation-evidence.json)에 남긴다. 이번 문서·원문 검산은 [implementation-verification.json](implementation-verification.json)에 기록하며, 제안한 구현의 시험 통과와 구별한다. 새 대시보드나 별도 상태 저장소는 필수 변경이 아니다. JSON·CSV와 사람이 읽는 상태가 같은 원장의 건수·시각·후속을 표시하면 목적을 달성할 수 있다.

**전체 절차에 대한 영향 판정과 추가로 연결할 지점**

위 변경을 구현하는 사람이 각 파일을 따로 고친 뒤 연결이 완성됐다고 판단하지 않도록, 주요 소비 경로의 최종 처분을 아래에 정리한다.

| 경로 | 필요한 대응 | 이 수정만으로 바꿀 이유가 없는 부분 |
|---|---|---|
| 후보 → 계약 → 모델 평가 | 지식 개정 대상과 선행조건을 계약에 포함하고, 새 계약 해시로 평가·검토를 결박한다. 평가 보충의 확장 제한은 새 가족 추가 뒤에도 유지한다. | 난이도·중요도 판단, 작업·운영 분리, 모델 등급 체계 |
| 계약 승인 → ready → 선택 → 실제 실행 | 외부 승인 전제, 개정 대기, 선택 판본을 세 지점에서 같은 규칙으로 확인한다. | 후보 전건의 AI 비교와 선택 권한 |
| 미시작 요청 병합 → 실패 → 새 시도 | 대상·판본·사건·계보·미해소 질문을 보존하고 해소 범위를 명시한다. | 살아 있는 실행의 입력 불변성 |
| 수신 → 역할 적용 → 확장 적용 | 전제 검사와 대상 검사를 구별하고 전체 결과를 원자적으로 적용한다. | 기계가 수학 의미를 병합하거나 선택을 대신하지 않는 경계 |
| 검토 → 보충 조사 → 같은 자리 복귀 | 본문 개정 대기와 슬롯 해제를 연결한다. 공급자 한도는 조사 포기로 처리하지 않는다. | 동료 결과 비공개, 자리·단계·회차, 새 판본의 전건 검토 |
| 지식 변경 → K → 목표 감사 → 학술 요구 | 실제 효력 변경의 전파를 유지하고 승인 재사용 검사와 회귀한다. | Lean·공리·동일성·목표·학술 판정의 분리와 완료 이력 보존 |
| provider 한도 → 독립 운영 → wake | 두 모델 입구의 동일 차단, 단일 재관찰, 실제 예약과 원 행동 복원을 연결한다. | 사용자 정지·외부 허가, 다른 인스턴스의 모델·예산 |
| 사용자 질문 → 입력·결정 → 다음 작업 | 답변 대상과 적용된 결정에 해소를 결박하고 영향 범위만 기다리게 한다. | 의도 해석의 독립 대조, 명시되지 않은 사용자 선호를 만들지 않는 경계 |
| 기한 예고 → 제출 또는 실제 정지 | 예고의 정상 제출과 권한 회수 후 보존을 분리하고 종료 장벽 뒤 슬롯을 반환한다. | 원격 종료를 관측했다고 주장하지 않는 한계 |
| status·timeline → 사람·운영 AI | snapshot·관측 시각·업무 단계·실행 상태·실패 원인·다음 행동을 함께 전달한다. | 조회가 연구 정본이나 새 승인이라는 오해 방지 |

연결을 끝내기 위해 다음 세부도 같은 수정 범위에 포함한다.

- **개정의 요청과 실제 저작자는 구별한다.** 후보 준비에 요청된 지식 변경이 새 연구를 요구하면 작업 과제에 넘긴다. `task_conditions[].knowledge_revision_targets`는 `planning.CONTRACT_FIELDS`에 포함되는 과제 필드로 저장하고, `engine._apply_plan`이 실제 수행 action에 판본 근거를 결합한다. `revision_resolutions`의 `delegated`에는 같은 준비 결과의 유일한 `task_title`을 요구하고 새 task ID에 결박한다. 이후 그 과제의 수행·철회·보류 결과가 원 개정 요청을 해소하거나 계속 보류하게 한다. 새 수행이 원 요청의 자기 차단에 걸리지 않도록 자기 쓰기 대상과 의무 소유권을 함께 검사한다.
- **개정 선행관계의 순환은 정상 대기로 숨기지 않는다.** A 개정이 B를, B 개정이 A를 기다리는 순환을 새 충돌 계산에서 발견하면 관련 요청 ID와 간선을 기록하고 계획·준비에 재설계를 요청한다. 기계가 임의로 간선을 지우지 않는다. 함께 성립해야 할 개정은 준비자가 한 실행의 여러 `revision_targets`로 묶거나 계약을 재정련할 수 있다. 선행 과제의 `dependencies`에 자기 의존이나 명시적 순환이 생기는 경우도 `submission.payload_issues`와 준비 반영에서 알려야 한다.
- **선택·완료 판정 대상은 `used_sources`에 적혔는지와 무관하게 결박한다.** 계획 출력의 대상 ID에서 원 입력 계약·결과를 포착한다. 선택의 판본과 `review_basis_key`를 수행 action에 저장한다. `_call_steps`가 단순히 현행 과제를 `ready`로 복사해서 통과시킬 수 없게 한다. 대상이 여전히 수행 가능해 보여도 선택 당시와 계약이 달라졌으면 새 계획으로 돌린다.
- **질문의 차단 검사는 표시 코드 밖에 둔다.** `planning.task_ready`, `_dispatchable`, `_call_steps`가 열린 사용자 질문의 `target_ids`와 현재 행동의 의존 대상을 확인한다. `question_routes`에서 user를 지정할 때는 영향을 받는 제공 대상 ID를 하나 이상 요구한다. 연구 전체의 목표·정책 결정이면 입력에 제공한 instance ID를 대상으로 명시한다. 그 외 질문은 원장에 보존하되 전역 차단으로 해석하지 않는다. goal 변경·완료의 기존 `questions=[]`도 출처 있는 해소·대체 이력으로 바꾼다.
- **새 필드의 생산자 검사와 중앙 검사는 같은 판본을 사용한다.** `submission.install_tools`의 ZIP·context·schemas, `contracts.render_prompt`와 동적 `review_cycle.stage_schema/research_schema`, `governance.interpretation_schema`, 독립 운영 스키마를 함께 대조한다. 검토 전용 questions의 수학적 미해결 의미를 일반 사용자 질문의 수명으로 바꾸지 않는다.
- **독립 운영 실패는 공유 gate까지 남긴다.** 운영 보고만 저장하고 끝내지 않도록 `scheduled_operator.check`가 provider 실패 기록과 다음 예약을 먼저 갱신한다. 원 연구 상태의 변경은 계속 CLI와 writer가 맡는다. 구 실행횟수의 inline 운영 호출도 같은 gate를 검사하지만 존재하지 않는 세션 용량을 요구하지 않는다.
- **예고 파일은 입력 전달과 보존 양쪽에서 다룬다.** `execution-window.json`과 `finish-request.json`은 실행기가 쓰는 제어 자료다. source 인용의 수학 근거로 오인하지 않도록 공통 실행 문서에서 구분하고, 종료 때 실행 증거로 보존한다. 검사 ZIP의 정지 확인은 여전히 `stop-request.json`을 사용한다.

**구현 순서와 고정할 완료 기준**

작은 독립 수정부터 진행하되, 서로 같은 불변식을 지키는 변경은 분리 출시하지 않는다. 특히 01의 대기만 적용하고 02의 승인 재사용을 빼거나, 02의 전체 해시 검사를 없앤 뒤 대상 검사를 나중에 붙이는 배포는 하지 않는다.

| 묶음 | 구현할 범위 | 검증·출시 조건 |
|---|---|---|
| A. 기준과 실패 자료 고정 | 기존 diff·연구 snapshot·원 JSONL·35건 비교표, 입력 구성 기준값을 보존 | 실행·파일 해시·집계 단위와 재현 범위가 연결됨. 연구 정지 유지 |
| B. 출력 경계 | 04, 10의 출처·Lean, 11의 잠금 문서·실호출 경계 | 정상 구간 수집과 오류 거부, prime의 실제 검사, 동일 검사기·Opus 배정 확인 |
| C. 전제와 파견 | 01·02·03을 연결해 구현 | 선행 개정·의존 작업·무관한 작업의 파견 순서, 기존 승인 재확인, 독립 검토 병렬, 대상 검사·전체 적용·복구 계보 통합 통과 |
| D. 운전과 대기 | 05·06·07, 그 상태를 보여 주는 12 | 한도 중 호출 억제·단일 wake·사용자 정지, 기한 예고·종료·복구, 정확한 질문 해소 통과 |
| E. 연구 판단과 효율 | 09·10의 문헌 인계, 08의 계측과 채택할 축약 | 계약·문헌 전달 사례의 개선 확인. 축약은 동일 의무 보존과 실제 효과를 확인한 부분만 채택 |

현행 새 인스턴스의 기능 판본은 3이다. 개정 대상·승인 전제·질문 연결을 새 의미로 해석하므로 이번 변경이 저장하는 상태는 기능 판본 4로 식별한다. 옛 실행기가 새 필드를 무시한 채 운전하는 일을 막기 위한 구분이다. `initialize`, `_upgrade_runtime`, `_installation_manifest`, `state_checks`의 판본 검사와 README·CLI 문서를 함께 바꾼다. 새 인스턴스는 필요한 새 필드를 처음부터 갖는다. 구 기록을 조회·내보내는 데 새 의미를 만들어 넣지는 않는다. 실행을 이어야 하는 구 인스턴스의 변환은 기존의 설치 판본 전환 기록과 writer 경로에서, 살아 있는 실행이 없는 상태에 한정해 처리한다. 원 입력·원 응답으로 근거를 정확히 복원할 수 있는 승인·요청만 결박하고, 나머지는 `unclassified` 질문 또는 입력 결박이 필요한 대기 요청으로 보존한다. 변환 자체가 사용자 정지를 해제하거나 과거 거부를 소급 수락하지 않는다. 동일한 변환을 다시 수행해도 추가 의무·질문이 중복되지 않아야 한다.

이번 목표는 고친 뒤 **새 연구를 시작하는 것**이므로 구 인스턴스의 자동 변환·재개는 필수 작업이 아니다. 구 인스턴스를 계속 운전하려면 변환 검사까지 통과해야 한다는 경계를 코드와 문서에 둔다. 과거 수학 산출을 새 연구에서 재사용하는 일과 과거 queue·승인·대기를 통째로 복사하는 일을 구별한다. 재사용할 산출은 정확한 출처·실제 증명 수준·남은 조건을 가진 입력으로 전달한다. 새 연구 시작은 구현·검증 완료 뒤 별도 실행 단계이며, 이번 계획 작성으로 시작하지 않는다.

초기 29항목의 분석 뒤 추가 검토에서 확인한 **파견 충돌, 기존 승인 재사용, 검토자 병렬과 보충 조사, 의미가 다른 요청의 해소, 새 입력의 질문 일괄 삭제, 종료 예고와 권한 회수의 차이**도 각각 01~03·07·06에 포함했다. [이전 수정 계획](plan.md)의 P01~P12를 사용하는 구현자는 다음 대응을 따른다: P01→04, P02→05, P03→01~03, P04→06, P05→07, P06→08, P07→09, P08→10, P09·P10→11, P11→12, P12→10.

설계 검토 결과, 위 연결을 포함하면 확인된 구현 결함에 대한 수정 범위는 정해진다. 남은 입증은 구현 후의 동작이다. 공급자 프로토콜의 실호환, 계약 품질, 입력·호출 절감량은 지정한 실제 사례에서 확인해야 한다. 필요하지 않은 추가 절차를 먼저 만들 이유는 없으며, 모든 거부나 모든 재검토를 없애는 것을 완료 기준으로 삼지도 않는다. 정확한 목표는 **피할 수 있는 충돌과 오거부를 줄이고, 필요한 재판정에는 기존 성과와 정확한 다음 행동을 전달하는 것**이다.
