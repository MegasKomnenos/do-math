# do-math 정적 워크스루 후속 수리안

이 문서는 2026-09-23 정적 검토에서 보고한 8개 문제 중 **2~8번의 수리안**이다. 작성 뒤 사용자가 자율적인 수리 진행을 승인했다. 아래 수정안과 검증안은 제안 당시의 설계와 확인 항목을 보존하며, 실제 반영 내용과 검증 범위는 [수리 결과](정적-워크스루-수리결과-2026-09-23.md)에서 구분한다. 앞서 별도로 승인받은 1번의 `run` 기한 제거도 유지한다.

구현에서 달라진 주요 선택은 3번의 별도 AI 기술 보류 허용·소비 장치를 채택하지 않은 것이다. 실제 `repetition_hold` 생성 경로는 횟수 한도뿐이었으므로, 사용자 계속 결정과 기존 운영 처분의 중복 방지로 수리했다. 아래 3번의 해당 구상은 당시 제안의 기록이며 현행 실행 계약이 아니다.

수리의 중심은 기존 생산자와 소비자의 계약을 연결하는 것이다. 입력 복원 실패는 해당 검토 자리의 대기로 처리하고, 반복 제어는 실제 재저작·수신 결과·복구 처분을 따라 작동하게 한다. 새 상태 관리 체계나 별도 카운터 저장소를 만들지 않는다. 기존 실행 원장·활동·요청·수신 결과·공개 이력으로 해결한다.

## 적용 순서와 범위

| 순서 | 원 지적 | 바꿀 핵심 | 완료를 판단할 결과 |
|---|---|---|---|
| 1 | 2. 입력 복원 유예 중 예외 | 준비 실행 종료와 활동 대기의 순서 | 복원 실패가 다른 실행을 종료시키지 않음 |
| 2 | 3. 반복 문턱 이후 재개 단절 | 운영 처분·사용자 결정과 정확한 후속 실행의 연결 | 승인한 후속만 한 번 시작하며 재처리는 중복을 만들지 않음 |
| 3 | 4. 수입 재저작 계보 불일치 | 생산자가 실제 만드는 계보로 집계·착수 검사 | 반려·재저작이 한도에 반영되고 검사 단계와 섞이지 않음 |
| 4 | 5. 선택 실패 분류 소실 | 수신 오류의 원인 보존과 연속 실패 집계 | 수신 실패가 누락되지 않고 전제 변경·자원 대기와 구별됨 |
| 5 | 7. 보충 성공의 무산출 오분류 | 후보 저작과 평가·규칙 보충의 결과 구분 | 유효한 보충이 무산출 횟수를 늘리거나 고갈 계획을 열지 않음 |
| 6 | 6. 재생성 시각 생산 경로 부재 | 후보 스키마·계약·수신 결과의 시각 연결 | 계약을 보존하지 못한 회차의 고갈 재생성이 지정 시각을 따름 |
| 7 | 8. 계획 중복 개설 | 일괄 지식 수입과 바깥 결과 적용기의 책임 구분 | 한 연구 결과의 비형식 지식 여러 건이 계획 한 건으로 환류됨 |

3번을 먼저 고쳐야 4·5번의 집계가 정상화되어 문턱에 도달했을 때 복구 불능을 새로 드러내지 않는다. 7번을 먼저 고쳐야 6번에서 평가 전용 실행에 불필요한 재생성 시각을 요구하지 않는다. 2번과 8번은 다른 항목과 분리해 적용할 수 있다.

공통 보존 조건은 다음과 같다.

- 사용자 목표·필수조건·허가·예산을 수리 과정에서 새로 만들거나 넓히지 않는다.
- 과거 실패, 독립 검사, 이미 수락된 편입 묶음과 원문은 보존한다. 과거 실패를 새 코드로 소급 성공 처리하지 않는다.
- 보류·재시도는 해당 의무에 적용한다. 관련 없는 연구나 검토는 계속할 수 있어야 한다.
- 새 요청·허용 근거·후속 계보를 서로 다른 저장 갱신으로 흩어 놓지 않는다. 하나의 적용 결과로 함께 공개한다.
- 테스트는 실제 생산자와 소비자의 연결을 거친다. 테스트가 만들어 넣은 허용 영수증이나 대체한 호출부만으로 연결 완료를 주장하지 않는다.

## 2. 검토 입력 복원 실패를 해당 자리의 대기로 처리한다

**현재 문제.** `ResearchEngine._call_steps()`는 새 실행을 `queued`로 등록하고 활동에 배정한 뒤 입력을 구성한다. `ReviewPreparationDeferred`를 받으면 아직 그 실행이 미종료인데 `activities.wait_for()`를 호출한다. 이 함수는 활동의 배정 실행이 모두 `ended`일 때만 대기를 허용하므로 예외가 난다. 뒤에 있는 `_discard_prepared_input()`에 도달하지 못하고 전체 스케줄러의 오류 처리로 번진다.

근거: [engine.py](../../.claude/skills/do-math/scripts/do_math/engine.py)의 `_call_steps`, `_discard_prepared_input`, `_settle_activity`; [activities.py](../../.claude/skills/do-math/scripts/do_math/activities.py)의 `wait_for`; [review_engine.py](../../.claude/skills/do-math/scripts/do_math/review_engine.py)의 `_prepare_review_context`, `_record_review_recovery`.

**수정안.** 유예 예외 처리에서 활동을 먼저 대기시키는 호출을 제거한다. 복원 실패의 자리·단계·회차, 실제 오류, 재시도 가능 여부와 다음 소유자를 기존 `waiting_actions`와 검토 복구 기록에 먼저 연결한다. 미시작 요청은 배정 큐에서 빼고, `_discard_prepared_input()`의 기존 준비 종료 경로로 이번 시도를 종료한다. 이 함수가 부르는 `_settle_activity()`가 남은 실행과 요청을 확인해 활동을 정리하도록 한다.

다음 소유자는 `_prepare_review_context()`가 반환한 `recovery.next_owner`를 그대로 연결한다. 일시적 I/O 실패로 같은 자료의 복원을 다시 시도할 수 있으면 `review_recovery`, 기록 연속성의 소실로 대체 승인이 필요하거나 현재 대체 권한이 거부됐으면 `governance`다. 예외 처리부가 오류 문장을 해석해 다른 담당자를 새로 정하지 않는다.

활동에 다른 실행이 없으면 `queued → ended`와 복원 대기를 같은 상태 공개에 보존한다. 형제 검토 실행이 남아 있으면 그 활동은 계속 작업 중이고, 실패한 자리의 대기 의무만 남긴다. 마지막 형제 실행이 끝날 때 기존 활동 정산이 그 의무를 보고 활동 대기를 확정한다. `wait_for()`의 사전조건을 완화하여 미종료 실행이 있는 활동을 대기 상태로 허용하는 방식은 쓰지 않는다.

대기 종류는 `review_input_restoration` 또는 `review_authority`로 유지하고 실제 오류는 별도 상세에 보존한다. 다음 배정의 복원 대기 판별과 `_release_review_wait()`가 같은 종류·대상을 읽도록 맞춘다. 아직 공개하지 않은 로컬 입력을 정리할 때에도 이미 검증된 복원 자료나 다른 실행의 폴더를 삭제하지 않는다.

**검증안.** 공개 실행 경로에서 검토 입력 파일의 읽기 실패 또는 해시 불일치를 발생시킨다. 해당 준비 실행은 시작되지 않고 종료되며, 복구 기록과 대기 요청은 저장돼야 한다. 동시에 실행 중인 다른 검토는 정상 결과를 제출할 수 있어야 한다. 복원 재시도와 대체 승인 경로를 각각 거쳐 같은 자리의 후속이 한 번만 열리는지도 확인한다. 준비 종료 도중 저장 실패가 나면 원 시도와 복구 의무가 재시작 후에도 남아야 한다.

주 검증 위치는 `test_review_engine.py`, `test_machine_parallel.py`와 실행기 통합 테스트다. `_prepare_review_context()`만 직접 호출한 테스트로 끝내지 않는다.

## 3. 반복 문턱의 승인과 실제 후속 실행을 연결한다

**현재 문제.** `authorize_repetition_repair()`는 `repetition_repair_authorized` 기록을 만들지만 실제 운영 처분 경로에서 호출되지 않는다. `retry`·`resume`으로 요청을 만들어도 문턱 검사에 필요한 허용 근거가 없다. 또 실제 후속은 원 action ID를 보존하는데, 허용 함수는 그 ID로 과거 실행이 존재하면 거부한다. 사용자 계속 결정을 검사하는 코드는 있지만 공개 결정 적용기는 `repetition_continue`를 지원하지 않는다.

근거: [revisions.py](../../.claude/skills/do-math/scripts/do_math/revisions.py)의 `action_repetition_waits`, `authorize_repetition_repair`, `record_repetition`; [engine.py](../../.claude/skills/do-math/scripts/do_math/engine.py)의 `_complete_operational_disposition`; [activities.py](../../.claude/skills/do-math/scripts/do_math/activities.py)의 `continue_activity`; [governance.py](../../.claude/skills/do-math/scripts/do_math/governance.py)의 `apply_decision`.

**식별자 수정안.** action ID는 계속 같은 의무를 가리키게 둔다. 재시도마다 새 실행 ID를 부여하고 `continuation_of`로 종료된 이전 실행을 잇는 현재 구조를 유지한다. 허용 근거는 반복 계보, 현재 hold의 근거 사건, 운영 처분 ID, action ID와 **이어받을 이전 실행 ID**를 함께 결박한다. 과거에 같은 action ID를 쓴 적이 있다는 이유만으로 거부하지 않는다. 대신 허용 근거를 이미 소비한 후속 실행이 있는지 검사한다.

운영 점검이 수락된 뒤 `_complete_operational_disposition()`이 후속을 만들 때, 현재 hold와 처분의 대상·독립성·재생 안전성을 대조하여 기존 허용 함수를 호출한다. 후속 요청, 처분의 적용 상태, 한 번의 실행 허용 근거를 같은 저장 갱신으로 공개한다. 새 실행의 등록을 공개할 때 사용한 허용 근거와 새 실행 ID를 기존 원장·이력에 결박한다. 같은 처분을 재처리하면 이미 연결된 후속을 반환하고 두 번째 실행을 만들지 않는다.

이때 운영 처분의 `execution_id`는 대상 실패 실행과 달라야 하며, 실제 `operational_review` 실행으로 종료·수락된 기록이어야 한다. `target_execution_id`는 이어받을 실패 실행과 같고 처분의 `basis_refs`는 현재 hold의 근거를 포함해야 한다. `resume`의 체크포인트는 보존된 정확한 참조·바이트와 대조한다. `retry`의 `scope`·`replay_safety`는 이미 편입된 묶음과 완료한 외부 효과를 반복하지 않는 범위를 설명해야 하며, 외부 효과가 `unknown`이면 기존 외부 행동의 대조·재전송 허가 절차를 먼저 거친다. 설명문 자체를 재전송 권한으로 사용하지 않는다.

한 번의 기술적 수리 허용은 누적 실패 횟수를 초기화하지 않는다. 그 후속도 실패하면 기존 계보와 문턱이 남으며, 새 진단이나 적격한 사용자 결정이 필요하다. 새 action ID를 만들어 횟수·보류를 우회하는 방식은 허용하지 않는다.

**사용자 결정 수정안.** 공개 `decision` 경로에 `repetition_continue`를 연결한다. 결정은 정확한 `lineage`, `lineage_id`, `hold_event_ref`, 허용할 후속 범위를 결박한다. 제안·계약 판본 계보에서는 현재 판본과 일치하는 `baseline_revision`도 검사한다. 현재 hold가 아니거나 이미 다른 내용으로 처리한 결정, 범위를 넓힌 후속은 거부한다. 계속 결정과 hold 해소·후속 요청을 함께 적용하며 이전 실패와 판본 이력은 남긴다.

권한 구분은 명시한다. 통합 설계 13.1.1절은 정해진 반복 한도 뒤 추가 계속에 사용자 결정을 요구한다. 현행 GLOSSARY의 반복 교정 절과 운영 점검 계약은 기존 권한 안의 기술 수리를 AI가 처리하고 사용자 목표·필수조건·허가 변경을 사용자에게 돌리도록 설명한다. 수리안은 두 권한을 구별한다. 기술적 진단·수리가 허용됐다는 사실만으로 사용자의 계속 승인이 필요한 문턱을 해제하지 않는다.

`hold.owner`는 원 요청을 작성한 주체가 아니라 해당 보류를 해소할 권한의 소유자에 맞춰 기록한다. 사용자 계속 승인이 필요한 문턱은 `user`이며 `repetition_continue`로만 해제한다. 현재 권한 안의 기술적 수리 보류가 `ai`이면 독립 운영 처분으로 동일 의미의 후속 한 번을 허용할 수 있다. 이 구분을 hold 생성부·허용 함수·역할 문서에 함께 반영한다. 이미 존재하는 사용자 승인 의무를 포괄적인 AI 소유 표지로 바꿔 없애지 않는다.

**검증안.** 실제 계약 개정 등으로 hold를 만든 뒤 운영 점검의 반환을 중앙 접수·적용 경로로 처리한다. 같은 action의 새 실행 한 번은 시작되고 같은 처분의 재전달로 두 번째 실행은 생기지 않아야 한다. 허용 후 재시작, 후속 실패, 오래된 hold 승인, 다른 계보의 승인, 사용자 정지·허가 만료, 이미 적용된 묶음이 있는 수리를 각각 확인한다. 사용자 계속 결정은 공개 CLI 요청부터 실행기 적용까지 거쳐 검사한다.

이 변경은 `revisions`, `governance`, 운영 처분 적용기와 저장 스키마를 함께 다루는 한 단위로 적용한다. 재시도 허용 함수의 단위 테스트만 통과한 상태로 완료하지 않는다.

## 4. 실제 수입 재저작 계보를 세고 그 다음 실행을 제한한다

**현재 문제.** 재저작 요청은 `previous_import_id`·`intent_repair`를 생성하지만 집계기는 `rework_of`를 찾는다. 반복 착수 검사도 `intent_interpretation` 역할 전체를 제외한다. 의미 검토의 반려가 반복되어도 해당 한도에 연결되지 않는다.

근거: [governance_engine.py](../../.claude/skills/do-math/scripts/do_math/governance_engine.py)의 `_queue_intent_rework`; [revisions.py](../../.claude/skills/do-math/scripts/do_math/revisions.py)의 `bind_repetition_bases`, `record_execution_outcome`, `action_repetition_waits`; [의도 해석 계약](../../.claude/skills/do-math/계약/의도-해석.md).

**수정안.** 기존 `intent_repair`·`previous_import_id`와 실행의 `continuation_of`를 사용하여 최초 해석, 독립 검사, 재저작을 구분한다. 같은 뜻의 `rework_of` 필드를 추가로 만들지 않는다. 계보의 기준은 새 해석 묶음 ID가 아니라 보존된 원입력과 그 해석 활동이다. 묶음·action·실행 ID가 새로 생겨도 같은 원입력의 재저작 횟수가 초기화되지 않아야 한다.

재저작 횟수는 새 재저작 실행이 원장에 등록되는 시점에 실행 ID별로 한 번 기록한다. 결과 수락 시점에만 세면 시작 실패나 출력 오류로 끝난 시도가 빠지므로, 등록된 재저작의 실패도 그 계보에 남긴다. 최초 해석과 별도 독립 검사 자체는 재저작 횟수로 세지 않는다. 독립 검사 응답의 형식 수리와 원 해석 내용을 다시 쓰는 시도도 구별한다.

구분 기준은 문장의 유사도가 아니라 `action.stage`와 수정 대상이다. `stage=check`의 수리는 검사자의 응답만 고치며 검사 대상 해석 묶음의 해시를 유지하므로 재저작으로 세지 않는다. 원 해석을 바꿔야 하면 검사자는 `revision_required`를 반환하고 새 `stage=interpret` 실행이 저작한다. 이미 시도한 해석 응답을 고치는 `stage=interpret`의 후속은 형식 오류 수리도 새 재저작 실행으로 센다. 검사가 원 해석을 직접 수정하는 우회는 허용하지 않는다.

착수 검사에서는 의도 해석 전체 면제를 없애고 재저작 대상에 해당 hold를 적용한다. 최초 입력 해석, 독립 검사, 사용자 답변의 해석과 해당 hold의 해소를 위한 적법한 처리는 자기 자신을 막지 않게 구분한다. 한도에 도달한 다음 재저작만 보류하며, 다른 사용자 입력이나 연구는 계속 처리한다. 계속·수리는 3번의 실제 허용 경로를 사용한다.

**검증안.** 원입력 하나에 독립 검사가 연속 `revision_required`를 반환하는 흐름을 실행한다. 최초 해석·검사·재저작 각각의 집계가 기대와 맞고, 한도 다음 재저작이 시작되지 않아야 한다. 출력 오류로 끝난 재저작, 같은 결과의 재접수, 재시작, 새 묶음 ID, 차단 질문의 답변, 다른 원입력도 확인한다. 테스트에서만 `rework_of`를 만들어 넣는 기존 표본은 실제 생산자 필드로 교체한다.

## 5. 계획 수신 실패의 원인을 보존하고 집계에 연결한다

**현재 문제.** 편입 묶음의 반환 사유가 `output_validation` 하나로 합쳐지고, 반복 기록기는 이를 `parse_failure`로 취급하여 선택 실패 횟수에서 제외한다. 의미상 거부를 구분하는 분기는 실제 생산자가 사용하지 않는다.

근거: [engine.py](../../.claude/skills/do-math/scripts/do_math/engine.py)의 `_receive_submission`; [integration.py](../../.claude/skills/do-math/scripts/do_math/integration.py)의 `apply_bundles`; [revisions.py](../../.claude/skills/do-math/scripts/do_math/revisions.py)의 `record_execution_outcome`; [task_contracts.py](../../.claude/skills/do-math/scripts/do_math/task_contracts.py)의 `repetition_lineages`; [통합 설계](통합-설계.md) 13.1.1절.

**수정안.** 실패를 처음 판정한 단계에서 원인을 정하고 수신 영수증까지 보존한다. JSON 파싱·출력 스키마 오류, 계약상 부적격한 계획, 전제 변경, 용량·공급자 대기, 저장 공개 실패를 구분한다. 중앙이 알고 있는 검사 단계·규칙 ID·예외 종류를 사용하고, 최종 오류 문자열을 다시 분석하여 원인을 추측하지 않는다.

선택 실패 집계는 원 설계의 수신 검사 실패 기준에 맞춘다. 정상적인 최종 응답을 받았지만 문법·출력 형식·계약상의 이유로 거부했다면 그 선택 회차의 실패를 기록한다. 전제 변경, 자원 부족, 입력·출력 한도 때문에 별도 결정으로 넘긴 경우는 선택 실패로 세지 않는다. 정상 수신 검사 통과는 연속 실패 구간을 끝낸다. 구체적 오류 종류와 출력 수리 횟수는 이 집계와 별도로 보존한다.

한 실행에서 여러 검사 문제가 나와도 회차는 한 번만 센다. 같은 봉인 후보의 재접수·편입 재처리도 중복 집계하지 않는다. 새 action ID만으로 연속 실패를 초기화하지 않으며, 과거 기록의 넓은 `output_validation` 값을 근거 없이 새 의미 분류로 소급 변환하지 않는다.

**검증안.** 올바른 JSON이지만 모집단을 누락한 계획, 지정 판정 근거 없이 완료를 선언한 계획, JSON·스키마 오류를 각각 실제 수신 경로로 거부한다. 실패가 한 번씩 집계되고, 성공한 계획으로 연속 구간이 종료돼야 한다. 전제 변경·공급자 대기·저장 공개 실패는 별도 사유로 남는지 확인한다. 동일 제출 재접수와 출력 수리 뒤의 재제출도 비교한다. 문턱에 도달한 뒤에는 3번의 후속 허용까지 이어서 검증한다.

## 7. 평가·관찰 규칙 보충의 성공을 별도로 판정한다

**현재 문제.** `assessment_targets` 또는 `observation_rule_targets`가 있는 준비는 새 후보를 만들지 않는 것이 계약이다. 그런데 결과 기록기는 모든 준비에 대해 그 실행이 생산한 계약이 있는지만 검사한다. 평가만 성공적으로 보충하여 `producer_execution`이 바뀌지 않은 경우에도 `exhaustion_empty`를 기록한다.

근거: [후보 준비 계약](../../.claude/skills/do-math/계약/후보-준비.md)의 기존 과제 보충 절; [scheduler.py](../../.claude/skills/do-math/scripts/do_math/scheduler.py)의 `_finish_assessment_preparation`; [model_policy.py](../../.claude/skills/do-math/scripts/do_math/model_policy.py)의 `preparation_only`; [revisions.py](../../.claude/skills/do-math/scripts/do_math/revisions.py)의 `record_execution_outcome`.

**수정안.** 기존 `preparation_only(action)` 판별을 결과 기록에도 사용한다. 후보 저작을 맡지 않은 보충 실행은 계약 생성의 성공·무산출 연속 횟수를 늘리거나 초기화하지 않는다. 보충의 성공·부분 보류·실패는 배정 대상의 평가·규칙 적용 결과와 기존 보류 기록으로 남긴다.

평가만 달라지면 평가 이력을, 관찰 규칙 변경으로 계약 판본이 달라지면 실제 계약 개정 이력을 유지한다. 무산출 집계에서 제외한다는 이유로 실제 계약 개정 횟수까지 없애지 않는다. 보충 성공이 독립 계약 검토 승인을 대신하지 않으며, 부족한 입력 때문에 남은 보충 의무도 지우지 않는다.

**검증안.** 평가만 보충하는 성공, 규칙만 보충하는 성공, 둘을 함께 보충하는 성공과 일부 대상 보류를 실제 준비 수신 경로로 확인한다. 이 실행들은 무산출 횟수를 바꾸지 않고 무산출을 이유로 한 계획도 열지 않아야 한다. 반대로 일반 후보 준비가 빈 후보를 반환하거나 제안한 계약이 전부 거부된 경우에는 무산출 집계가 유지돼야 한다.

## 6. 후보 준비가 재생성 시각을 제출할 수 있게 한다

**현재 문제.** 수신자는 `regenerate_after`를 읽지만 후보 준비의 출력 스키마는 그 필드를 허용하지 않는다. 고갈 판정은 재생성 시각을 적용하는 대신 시각 누락의 판단을 계획 역할로 넘긴다.

근거: [contracts.py](../../.claude/skills/do-math/scripts/do_math/contracts.py)의 후보 준비 스키마; [revisions.py](../../.claude/skills/do-math/scripts/do_math/revisions.py)의 준비 결과 기록; [planning.py](../../.claude/skills/do-math/scripts/do_math/planning.py)의 `exhaustion_state`; [통합 설계](통합-설계.md) 9.2.1절.

**수정안.** 일반 후보 준비의 주 응답에 `regenerate_after`를 추가하고 역할 계약에 그 목적을 설명한다. 값은 기계가 지급한 `observed_at`보다 뒤인, 시간대가 명시된 재생성 시각이다. 제출 검사와 중앙 수신이 같은 시각 검사를 사용한다. 관찰 시각 자체는 이미 지급·보존된 기계 값을 사용하여 생산자가 다시 전사하지 않게 한다. 이 기계 결속 방식도 설계의 생산·수신 설명에 맞춘다.

계약을 제안한 응답도 예비 시각을 낸다. 수신자가 실제로 보존한 신규·정련 계약이 하나도 없을 때만 그 시각을 고갈 대기에 사용한다. 계약을 하나 이상 보존했다면 예비 시각은 다음 준비를 제한하지 않는다. 7번의 평가·규칙 보충 실행에는 이 필드를 요구하지 않는다.

기존 `record_execution_outcome()`과 `exhaustion_state()`를 연결하고 별도 타이머나 예약 원장을 만들지 않는다. 시각 도래 뒤 기존 재관찰 경로가 한 번의 준비를 열게 한다. 정기 탐색은 고갈의 재생성 가드와 독립적으로 유지한다. 응답을 파싱하지 못해 시각도 확보하지 못한 경우에는 시간을 임의로 만들지 않고 기존 출력 수리·진단 경로를 따른다.

과거의 시각 없는 무산출 기록은 수정하지 않는다. 현재 계획이 그 누락을 진단하고 필요한 준비를 요청할 수 있는 기존 경로를 유지하되, 다음 유효한 일반 준비 결과부터 시각을 보존한다. 새 시각을 과거 실행이 작성했던 값처럼 기록하지 않는다.

**검증안.** 빈 후보, 후보 전부 거부, 후보 일부 보존, 평가 전용 보충을 구별한다. 재생성 시각 직전에는 고갈 준비가 열리지 않고 시각 도래 후에는 한 번만 열려야 한다. 주기적 탐색은 그 전에도 자기 조건에 따라 열릴 수 있어야 한다. 잘못된 시간대·과거 시각은 생산자와 중앙에서 같은 이유로 거부하고, 과거 시각 누락 기록과 파싱 실패의 후속도 확인한다.

## 8. 한 연구 결과의 계획 개설을 한곳에서 맡긴다

**현재 문제.** `knowledge_io.import_candidate()`가 비형식 지식마다 지식 ID를 대상으로 한 계획을 열고, 바깥 연구 결과 적용기가 일반 계획을 하나 더 연다. 각 요청의 `target`이 달라 병합되지 않는다.

근거: [knowledge_io.py](../../.claude/skills/do-math/scripts/do_math/knowledge_io.py)의 `import_candidate`; [engine.py](../../.claude/skills/do-math/scripts/do_math/engine.py)의 `_import_research_records`, `_apply`, `_apply_extensions`, `_enqueue`.

**수정안.** 일괄 연구 결과에서는 바깥 결과 적용기가 계획 개설을 맡는다. 지식 수입 함수에 비형식 결과의 계획 개설 여부를 지정하는 작은 인자를 추가하고, 기존 독립 호출의 기본 동작은 유지한다. `_import_research_records()`와 이미 계획을 여는 부수 통찰 수입 경로는 그 인자를 꺼서 항목별 계획을 억제한다. 이 인자는 비형식 지식의 계획 개설만 제어하며 필요한 형식 검사·동일성 검토는 그대로 요청한다.

바깥 적용기는 수락된 지식들의 ID·후속 사유를 보존하여 기존 `_enqueue('research_plan', ...)`를 한 번 호출한다. 지식이 0건이어도 미종결 과제의 `results`에 수락된 수행 보고가 추가되어 `returned_task_ids()`의 판정 대상이 되면 계획을 연다. 실행 실패로 보존만 한 자료는 이 수락 결과와 구별하여 기존 진단·수리 경로로 보낸다. 이미 시작한 계획의 고정 입력을 바꾸지 않으며, 그 뒤 도착한 결과는 다음 계획의 사유로 남긴다. 서로 다른 권한·검토 범위의 요청을 단순히 역할 이름이 같다는 이유로 병합하지 않는다.

독립적인 편입 묶음이 일부만 수락되면 수락한 내용만 후속 사유에 넣는다. 반환된 묶음을 나중에 고쳐 수락하면 그 새 결과가 다음 계획을 열 수 있다. 실패한 후보의 지식 ID를 이미 이용할 수 있는 근거로 전달하지 않는다.

**검증안.** 다른 대기 계획이 없는 상태에서 비형식 지식 0·1·3건을 가진 연구 응답을 수신한다. 정상 수신된 응답은 보고 판정과 지식 환류를 위한 계획 한 건으로 이어져야 한다. 독립 CLI 지식 수입에서는 필요한 계획이 여전히 열리는지, 형식·비형식 혼합 응답에서는 형식 검사 요청이 빠지지 않는지 확인한다. 일부 편입·재시도와 이미 실행 중인 계획이 있는 경우에는 누락·중복 없이 다음 입력에 연결돼야 한다.

## 적용과 검증의 종료 기준

수리는 정본인 `.claude/skills/do-math`에서 한다. 역할 계약·주 응답·확장·저장 스키마·실행기 중 변경되는 계약의 생산자와 소비자를 같은 작업 단위에서 수정한다. 저장된 원문·판정의 해시를 일괄 바꾸어 새 계약에 맞춘 것으로 처리하지 않는다. 기존 기록의 읽기와 새 기록의 생성 조건을 각각 검사한다.

각 항목은 고치기 전의 실제 경로에서 결함을 드러내는 검사를 확보하고, 고친 뒤 같은 검사가 통과하는지 확인한다. 이어 정상 경로와 사용자 정지·권한 회수·재시작·재접수·독립 작업의 지속을 검증한다. 변경 중인 정본과 구별된 고정 사본에서 실행하고 실패한 첫 검사도 보존한다.

코드·문서가 완결되면 생성기로 `.agents/skills/do-math`를 재생성하고 드리프트 검사를 통과시킨다. 실제 모델·Lean을 사용한 연구 효능은 대역을 사용한 상태 전이 검증과 별개이며, 실시하지 않은 검증을 완료 근거로 쓰지 않는다.

기존 미커밋 변경과 이번 수리의 경계는 적용 전에 보존한다. 각 수리 단위의 목적·실제 변경·검증 범위를 기록하고, 독립적으로 검증한 작업만 커밋 단위로 묶는다. 구현 완료와 실제 검사 결과는 수리 결과 및 그 검증 원장을 기준으로 판단한다.
