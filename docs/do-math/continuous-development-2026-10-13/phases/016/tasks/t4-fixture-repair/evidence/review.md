RealJobObservation은 의미 schema에 boolean ok를 선언하고, 실제 Codex 전송 정의의 CODEX_OUTPUT_KEY를 사용해 같은 최종 값을 문자열 봉투로 보낸다. stream과 final 파일은 동일 봉투이며 실제 runner/collector가 의미 값을 받아 ok=true와 completed를 검사한다. 종료 뒤 지연 batch 적용, 종료 barrier, operational_review 비발동 및 정확 네 observation fact 단언은 그대로다. 외부 공급자는 결정적 로컬 Python 자식이며 실제 모델 호출은 아니다.

WriterLock child는 자기 환경으로 real_ports를 구성해 ResearchRepository의 필수 backend/clock을 전달한다. 부모가 실제 잠금을 보유할 때 LockError와 acquired 부재를 확인하고, 해제 뒤 새 child가 acquired를 출력하는 정상 대조를 추가했다. Archive child는 sys.path의 zip을 먼저 지정한 뒤 자기 환경과 real_ports를 만든다. 같은 archive formal의 identity 검사와 errors=[]를 유지하고 child exit0을 추가 확인한다. 두 fixture의 NameError/TypeError를 정상 기대값으로 바꾸지 않았다.

## Windows 핸들 인과 대조

일반 도구 자식에서 실행한 control/original은 둘 다 exit0이었다. 세 표준 핸들은 관측 전후 유효했다. 정확 공식 격리 ID는 다시 WinError6으로 failed였다. 실제 WindowsJob에서 같은 자기 진단을 실행했을 때 control의 stdin은 null 그대로이고 Git 저장은 exit0이었다. 원 관측은 null stdin을 AttachConsole/FreeConsole 뒤 유효하지 않은 nonnull 핸들로 바꾸며, 저장의 update-ref에서 DuplicateHandle WinError6으로 exit1이었다. stdout/stderr의 파일 핸들은 계속 유효했다. 이 조건별 원프로그램·핸들·child receipt/stderr는 os-control, os-original, os-job-control, os-job-original에 있다.

진단 launcher는 child가 완료한 뒤 존재하지 않는 exit_code 메서드를 호출하여 마지막 행정 출력에서 AttributeError가 났다. control/original 각각의 이미 작성된 실제 exit와 핸들·stderr 원자료는 보존했다. 추가 fixture audit에서도 WindowsJob에 subprocess의 poll 메서드가 있다고 잘못 가정하여 OS child의 실행 완료 뒤 마지막 종료 조회가 실패했다. audit의 이미 완결된 실제 11094파일 기록·metadata 불변·원바이트 표본과 합성 2파일 전수 해시 대조는 fixture-audit.json에 보존하고 audit 묶음 자체는 exit1이다. 수리 후 OS child의 실제 exit는 별도 os_repaired_final.py가 GetExitCodeProcess(process_handle), inspect의 root_signaled/active0/빈PID로 새로 확인한다. 초기 행정 실패를 성공으로 다시 꾸미지 않는다.

제품 Git은 콘솔을 붙이거나 해제하지 않는다. 수리는 시험 관측의 AttachConsole/FreeConsole만 별도 pythonw child로 옮긴다. 실제 Git 프로세스와 자손은 원래 command/kwargs로 실행하며, 부모가 EnumWindows와 psutil로 실제 family/visible 상태를 읽는다. Git이 batch request에 응답하는 동안 별도 관측자가 같은 PID들의 콘솔을 검사한다. hidden CREATE_NEW_CONSOLE 양성 대조, 실제 Git 이름, 콘솔 없음, visible=[] 및 bytes(range(256))+CRLF의 저장/재읽기를 유지한다. 관측 전후 저장 프로세스의 stdin 슬롯 동등 단언을 추가한다. 무조건 retry/skip이나 runtime I/O 변경은 없다.

bootstrap-info의 초기 WinError5 원인은 이 작업에서도 판명하지 않았다. 현재 두 정확 ID의 동결·원설치·정확 manifest·manifest 부재 반려가 통과한다는 범위만 인정한다. 과거 실패를 transient나 성공으로 소급 분류하지 않는다.

## 미러와 후속 책임

공식 생성기의 transform/build_target을 기준으로 예상 변경과 writes를 대조한 뒤 생성한다. 최초 보조 계획은 manifest의 JSON 값을 정확히 비교했지만 LF와 Windows write_text의 CRLF를 혼동하여 행정 assertion에 실패했다. 원계획을 남기고 실제 생성기의 native 개행으로 계산한 새 계획이 바이트 불변을 확인한 뒤 생성했다. 이 오류에서는 제품을 수정하지 않았다. 양쪽 지정 회귀 뒤에는 비용 캐시만 공식 재동기화하며 --check/skill-only를 확인한다.

015의 12개 제품 경로와 이번 fixture 변경을 구분한다. runtime·runner/adapter 측정·실호출 입력·corpus 원바이트·도구 SHA 및 index/pseudo/T3-store의 보존은 verification.json이 실제 최종 파일과 대조한다. 기존 실호출은 불변 경로/도구와 이전에 승인한 성질만 재사용한다. 새 유료 공급자·실예약·학술 검색·설치 신뢰 승인·기존 연구 재개·graphify·Git 행정 마감은 수행하지 않는다.

이 작업의 성공은 지정 회귀와 fixture/OS 수리다. P10/P11 입력 준비 task의 결과를 읽거나 기다리지 않았으며 두 exact-baseline 비교, 양쪽 전체 T4, 전체 일반/fresh 전체 T3/대상 함수 전체 변이와 최종 review는 수행하지 않는다. manager가 독립 두 task를 검수한 뒤 후속 단일 연결 작업을 배정해야 한다. bootstrap 과거 WinError5의 원인 한계와 초기 진단/행정 실패도 보존한다.
