# do-math

do-math는 연구 책임자가 정한 수학적 질문을 지속적으로 탐구하는 AI 연구 체계다. 기존 지식을 읽고 적용할 내용을 찾으며, 증명·반례 탐색·계산·문헌 조사에서 얻은 결과를 보존하여 다음 연구를 선택한다. 연구의 주 산출물은 사람이 읽는 수학 해설이다. 수학 해설은 독자가 무엇을 정의하거나 증명했는지, 어떤 가정이 필요한지, 논증이 어떻게 이어지는지를 이해할 수 있어야 한다.

## 이 문서를 읽는 실행의 역할

기계 실행기가 `action.role`과 실행 입력을 제공한 내부 AI 실행은 [역할 읽기 대응표](#역할-읽기-대응표)의 순서와 배정된 계약을 따른다. 설치 복구 AI는 실행기가 만든 고정 복구 프롬프트와 제공된 복구 입력을 따르며, [독립 운영 계약](계약/독립-운영.md)은 그 경계를 운영자에게 설명한다.

사용자 대화에서 인스턴스 초기화를 운전할 때는 [GLOSSARY.md](GLOSSARY.md) 전문을 먼저 읽고, README의 [운전 책임과 실행 구조](README.md#operating-model)를 읽은 뒤 [새 연구를 시작하고 인계하기](README.md#start-guide)를 수행한다. 같은 대화에서 현행 판본을 이미 읽었다면 그 내용을 재사용한다. 기존 연구의 상태·권한도 같은 용어집의 정의로 해석한다. 긴 문서는 출력 한도 안의 연속 구간으로 읽는다. 온전히 받은 연속 접두 구간의 다음부터 읽거나, 명시한 구간별 수신을 확인해 중간의 누락 구간을 모두 회수한다. 개별 도구 결과와 최종 합산 출력의 절단을 각각 확인하고, 잘렸으면 구간 크기나 동시에 출력하는 결과 수를 줄인다. 긴 한 행의 일부 문자만 받았으면 그 행을 온전히 받은 것으로 세지 않는다. 마지막에 보이는 꼬리·끝표지, 종료 코드 0, 파일 열기 성공이나 해시는 전문 수신·독해의 근거가 아니다. 모든 구간을 온전히 받은 뒤 다음 문서로 간다.

일반적인 연구 시작 요청은 초기화를 완료하고 별도 연구 프로세스로 인계하는 작업이다. 운전 중의 작업 선택과 종료는 이 목적에 대한 진전과 README의 [책임·인계 판단 기준](README.md#handoff-judgment)을 따른다. 인계 조건과 실제 시작을 확인하고 인스턴스 식별자·현재 상태·남은 책임과 조회 방법을 보고하면 이 대화의 시작 작업을 마친다. 이후 연구와 의미 검토는 실행기가 배정한 AI 역할이 수행한다. 수학적 목표 충족은 독립 목표 감사가 판정하고, 기계 실행기는 판정을 검사·적용한다. 연구 헌장에 학술 검증 요구가 있으면 그 요구의 완료도 별도로 판단한다.

사용자 대화는 요청에 따라 다음 절차를 선택한다.

- 새 연구 시작: README의 [시작 절차](README.md#start-guide)를 순서대로 수행한다.
- 기존 연구 조회·입력·정지·재개: README의 [기존 연구 조회·제어](README.md#existing-control)에서 해당 절차를 수행하고 효과를 확인한다.
- 정해진 범위의 직접 실행: README의 [직접 전진·수동 운전](README.md#manual-run)에서 적용 조건과 요청 범위를 확인한다.
- 스킬 자체 변경: [AGENTS.md](AGENTS.md)의 개발 원칙을 따른다.

## 연구의 목적과 공통 정의

연구에서는 목표의 해답뿐 아니라 부분 결과, 실패한 접근, 아직 답하지 못한 질문도 중요하다. 이러한 결과를 실제 확인 범위와 근거를 갖춰 남기면 다음 연구가 같은 시도를 반복하지 않고 더 나은 질문과 방법을 선택할 수 있다. do-math는 이 지식의 축적·탐색·환류가 이어지도록 연구 수행과 검토, 계획을 서로 연결한다.

이 문서는 do-math의 목적, 전체 연구 흐름, 역할별 읽기 순서를 설명한다. 공통 용어의 뜻은 [GLOSSARY.md](GLOSSARY.md)에 한 번 정의한다. 각 역할은 그 정의를 사용하여 자기 입력을 읽고 판단하며, 역할마다 용어의 뜻을 바꾸지 않는다.

## 스킬의 구성과 입력

스킬 자체를 개발할 때에는 [AGENTS.md](AGENTS.md)를 따른다. 프리알파 단계에서는 현재 계약 하나만 유지하며, 이전 구현·설정·저장 형식의 호환 경로를 남기지 않는다.

do-math의 배포 단위는 이 문서가 있는 스킬 폴더 전체다. 공통 정의, 역할 계약, 실행 절차, 명령 사용법과 실행 코드를 이 폴더 안에 함께 둔다. 스킬의 규칙을 이해하거나 실행하기 위해 별도의 프로젝트 맥락 문서나 설계 문서를 읽을 필요는 없다.

AI 역할은 GLOSSARY.md의 용어, 실제 지급된 공통 문서·역할별 참조 문서와 자기 역할 계약, 실행별 입력·출력 스키마를 따른다.

모델 없는 예약 감독은 코드를 실행한다. 설치 복구 AI의 지시는 실행기가 만든 고정 프롬프트이며, 이 AI에는 내부 연구 역할의 읽기 대응표를 적용하지 않는다. 그 입력과 권한의 경계는 [독립 운영 계약](계약/독립-운영.md)이 운영자에게 설명한다.

연구마다 달라지는 목표·정책·허가·원자료와 기존 결과는 연구 인스턴스의 입력으로 받는다. 이 입력은 스킬의 공통 정의와 실행 지원을 새로 정하지 않는다. 실행에 필요한 Python, Git, 사용할 모델의 Codex CLI 또는 Claude CLI와 Lean의 준비 및 사용 조건은 README.md와 CLI 실행 계약에 설명한다. 스킬을 다른 위치에 설치할 때는 폴더 전체를 복사하고, 명령 예시의 스킬 경로를 실제 설치 경로로 바꾼다.

새 연구의 예약 감독은 기본으로 활성화된다. 활성 여부와 주기는 인스턴스 설정으로 바꿀 수 있으며, 기본값은 [CLI 실행 계약의 설정 목록](references/CLI-실행-계약.md#config-list)을 따른다. 정상 감독은 모델을 호출하지 않고 HOLD·사용자 정지·현재 상태·예약 작업과 실행기 시작 조건을 대조한다. 보존된 실행기 시작 실패 또는 수락된 운영 진단의 설치 결함이 있을 때 설치 복구 AI를 열며, 그 실행은 운영 역할과 같이 작업 슬롯을 예약하지 않는다.

인스턴스는 모델별 동시 세션 예산을 작업 역할에만 적용한다. 연구 수행·보충 조사·작업 계약 검토·동일성 검토·목표 감사는 배정된 모델의 작업 슬롯을 예약한 뒤 시작한다. 후보 준비·연구 계획·의도 해석·운영 점검·유지보수 같은 운영 역할은 슬롯을 예약하지 않고 역할별 최소 등급과 대상의 요구로 고른 모델에 바로 배정되므로, 작업 슬롯이 모두 차도 계획·점검·복구가 멈추지 않는다. 기본 모델 대응과 모델별 작업 슬롯 수는 [모델과 실행예산의 모델 표](references/모델과-실행예산.md#model-table)에 있으며, 인스턴스마다 모델 대응과 용량을 바꿀 수 있다. 난이도·중요도에 따른 배정과 자원 대기도 [모델과 실행예산](references/모델과-실행예산.md)을 따른다.

예약 감독은 사용자 대화와 별도의 기계 작업이다. 정상 경로에서는 연구 의미를 판단하거나 새 권한을 만들지 않고, 실행기가 필요한 연구·검토·운영 역할을 자기 계약으로 수행하게 한다. 설치 복구 AI는 실행기 자체가 시작하지 못한 경우나 운영 점검이 설치 결함을 확인한 경우에 고정 복구 계약 안에서 최소 수리와 설치 검사를 수행한다. 실행기 안의 진행 관찰·운영 점검은 계속 작동하며, 사용자 대화는 요청·승인·정지와 결과 조회를 맡는다. 설치·시작·복구의 정확한 경계는 README와 [독립 운영 계약](계약/독립-운영.md)을 따른다.

연구 책임자가 목표와 정책, 자원과 외부 행동의 허용 범위를 정한다. AI 역할은 배정받은 판단과 연구를 수행하며, 기계 실행기는 그 결과를 검사하고 현재 전제에 맞게 적용한다. 구현의 사용법을 읽는 일이나 실행을 시작하는 일 자체가 연구 책임자의 결정을 새로 만드는 것은 아니다.

## 연구를 이어 가는 방식


=== N01-006 repo:.claude/skills/do-math/SKILL.md 53-60 ===
### 축적한 지식에서 질문을 만든다

연구를 시작하거나 다시 계획할 때는 현재 목표와 기존 연구 기록을 함께 읽는다. 형식 정본 K에 이미 목표를 충족할 결과가 있을 수도 있고, 가시 연구 프런티어 F에 유망한 질문이나 아직 해결하지 못한 장애물이 있을 수도 있다. 현재 기록만으로 어떤 접근을 택할지 분명하지 않다면, 그 불확실성을 새로운 조사 대상으로 구체화할 수 있다.

기존 결과를 찾았다는 사실만으로 이번 질문에 적용할 수 있는 것은 아니다. 결과의 가정과 결론, 실제 확인한 범위, 연결된 판정의 사용 효력을 이번 질문과 대조해야 한다. 연구 기록 사이의 관계도 이 대조를 돕는 근거로 사용한다. 이러한 지식 재사용의 절차는 역할 읽기 대응표가 공통으로 제공하는 「지식 저작과 재사용」을 따른다.

탐색과 집중 활용은 모두 연구 계획의 판단 대상이다. 새로운 질문을 드러낼 필요와 기존 후보를 더 깊게 연구할 필요를 현재 근거로 비교한다. 일정한 비율이나 후보 수를 채우는 일로 이 판단을 대신하지 않는다. 미지 지평 U를 먼저 열거하거나, F의 모든 후보를 작업 계약으로 만드는 일도 연구의 선행조건이 아니다.


=== N01-007 repo:.claude/skills/do-math/SKILL.md 61-76 ===
### 질문을 수행할 수 있는 과제로 정련한다

후보 준비는 축적한 지식에서 연구 후보와 작업 제안을 저작한다. 그중 실제 수행을 제안할 내용에는 질문, 포함·제외 범위, 필요한 입력, 기대 산출과 연구 변화, 증거가 결박된 진전 기준, 안정된 ID·판정자·필요 증거를 가진 완료 의무, 프로필·권한·생성 근거를 구체적으로 적는다. 작업 계약은 최종 증명 방법을 미리 확정하는 문서가 아니다. 무엇을 조사하고 어떤 증거로 각 의무를 처분하면 그 조사를 마쳤다고 판단할 수 있는지를 정하는 문서다.

아직 그 정도로 정련하지 못한 질문도 연구 후보로 보존할 수 있다. 가정과 장애물을 깊이 조사해야 다음 작업을 정할 수 있다면, 그 조사를 별도 과제로 제안한다. 후보 준비와 연구 계획은 이미 확보한 자료로 판단하고, 새로운 근거를 얻기 위한 연구 수행에는 작업 예산을 사용한다.

후보마다 난이도·중요도 평가를 하나씩 작성한다. 제출 전에는 후보마다 계약의 기호와 결과 갈래를 스스로 점검하고, 인용한 다른 과제와의 경계를 계약 자기점검에 선언한다. 이 평가와 자기점검의 작성 방법은 후보 준비 계약을 따른다.

실행기가 사용자의 학술 요구로부터 자동 생성한 과제와 평가 없는 기존 과제에는 후보 준비가 평가와 관찰 규칙을 보충하며, 준비가 갖춰진 판본은 독립 계약 검토를 받는다. 이 보충의 배정·반환·보류는 후보 준비 계약의 기존 과제 보충 절이 정한다.

후보 준비의 응답이 기계 검사를 통과했다는 사실은 독립 계약 검토의 승인을 대신하지 않는다.

작업 계약 검토는 계약을 작성하지 않은 별도 AI 실행이 맡는다. 기계 실행기가 정련된 계약을 전달하면, 검토자는 과제를 실제로 수행할 수 있는지와 완료 기준이 판정 가능한지를 살핀다. 수정이 필요하면 부족한 내용을 후보 준비에 돌려준다. 계약 검토의 승인은 실제 수행할 과제의 선택과 배정에 앞선 판단이다.

사용자가 정한 목표와 필수조건을 유지하면서 AI가 만든 개별 과제의 범위와 완료 기준은 자율적으로 재설계할 수 있다. 새 계약은 이전 문장을 누적하지 않고 전체 현행 문면으로 교체하며 다시 독립 검토한다. 더 진행하지 않을 미완료 과제는 근거를 남겨 철회하고 부분 결과와 이력을 보존한다. 과제 철회는 그 과제나 연구 목표의 완료가 아니다.

### 준비된 과제 중 다음 연구를 선택한다

기계 실행기는 현재 계약 검토, 입력, 발생 조건과 허가를 확인하여 배정 후보를 계산한다. 연구 계획은 제공된 배정 후보 전건을 비교하고 각각을 `selected`, `not_selected`, `not_assessable` 중 하나로 처분한다. 선택한 과제 사이의 병행 관계와 기대 연구 변화, 미선택의 재검토 사건, 판정 불가의 누락 입력과 다음 소유자를 함께 남긴다. 후보를 저작한 실행과 최종 선택을 판단하는 실행을 구별하는 이유는, 제안을 만들었다는 사실만으로 그 제안의 수행이 당연해지지 않게 하기 위해서다.

선택할 때는 목표와의 관계, 얻을 수 있는 정보, 불확실성, 기존 결과와의 중복·보완·의존, 사용할 수 있는 자원을 함께 고려한다. 보류한 과제에는 이유를 남기고, 새로운 정련이 필요하면 후보 준비에 무엇이 필요한지 설명한다. 기계 실행기는 선택을 적용하기 직전에도 그 판단이 기댄 전제의 현재성을 확인한다.

초기화 관문을 모두 통과하면, 현재 지식 기록이 있는 경우 최초 연구 계획을, 없는 경우 최초 후보 준비를 연다. 활성 인스턴스에서 학술 요구를 포함한 헌장 변경이 적용되면 그 결정의 사건과 현재 기록을 다음 계획·준비에 전달한다. 일반 계획은 배정 후보가 없어도 변경된 요구와 부족한 입력을 판단할 수 있다. 기존 기록을 개정하지 않는 준비와 계획은 병렬로 진행할 수 있으며, 실제 개정 중인 기록의 독자는 해당 개정의 종료를 기다린다.

최초 역할은 활성화까지의 초기화 사건도 함께 읽고 수락된 결과로 소비한다. 이미 선택한 과제의 정상적인 실행 점유는 기록하되 그 사실만으로 새 계획을 열지 않는다. 점유 중에도 계약·원자료·권한의 실제 상실은 다음 판단으로 전달한다.

계획이 열린 뒤의 정산은 별도다. 대기 중이거나 실행 중인 계약 검토가 있으면 실행기는 그 종료를 설정의 `plan_settle_seconds`까지 기다린다. 몇 분 간격으로 승인되는 과제를 한 계획에서 함께 비교하기 위해서다. 이 상한이 지나면 남은 검토와 무관하게 시작하며, 사용자 또는 명시적인 `operator` 출처 제어가 직접 요청한 계획은 기다리지 않는다.

### 변경될 전제와 이미 유효한 판단을 구별한다

기존 과제나 지식의 개정은 실행 전에 대상을 선언한다. 과제·지식 기록 A를 고칠 예정이고 작업 B가 A를 필수 전제로 읽으면, 아직 시작하지 않은 B의 실행을 기다리게 한다. 이미 A를 읽는 실행이 있으면 그 실행이 끝난 뒤 A를 고친다. 관련 없는 작업은 병렬로 진행할 수 있다. 같은 고정 제안을 읽는 독립 검토끼리도 병렬로 진행한다. 개정이 실패하거나 다른 과제에 위임돼도 대상별 의무를 보존하고, 이를 진단·재설계할 계획과 운영 판단은 계속할 수 있다.

결과를 적용할 때는 실제 판단에 사용한 내용과 사용 효력을 확인한다. 무관한 진행 표시나 검토 기록이 추가됐다는 이유만으로 같은 연구를 반복하지 않는다. 실제 전제가 바뀌면 실행기는 원 산출을 보존하고 달라진 기록·필드를 적은 변경표를 제공한다. 같은 역할의 새 실행은 이 변경표, 이전 결과와 현재 입력으로 판단을 갱신한다. 이미 받은 계약 승인도 실제 착수할 때 같은 현재성을 확인한다.

한 응답의 결과는 편입 묶음 단위로 적용된다. 기존 기록을 개정하거나 과제를 철회하는 응답, `action.revision_targets`로 개정 대상을 배정받은 실행, 일부 편입 뒤의 재시도에서는 생산자가 `integration_bundles`로 묶음·영향·이전 근거를 선언한다. 그 밖의 응답은 실행기가 한 묶음으로 구성하며, 구성원의 독립성을 추측해 나누지 않는다. 선언이 필요한 정확한 조건과 형식은 「공통 실행」의 「주 응답의 의미와 보존」 절이 정한다. 실행기는 각 묶음의 구조·권한·현재성·실제 영향을 확인해 적용하거나 반환하며, 구조 검사의 통과를 묶음 사이의 수학적 독립성에 대한 인증으로 취급하지 않는다.

질문은 발생 원문, 소유자, 영향 대상과 해소 근거를 연결한다. 사용자 답변이 필요한 대상은 기다리되 독립 작업은 계속한다.

공급자 한도는 같은 공급자를 쓰는 작업 역할과 운영 역할의 새 호출을 모두 기다리게 한다. 정해진 시각 뒤 허가된 실제 작업 하나로 사용 가능 여부를 재관찰한다.

기한 전에 결과 정리와 제출을 요청하는 마무리 예고는 실제 정지와 구별한다. 예고 뒤에도 기한 내 정상 부분 제출을 받을 수 있다. 각 역할의 구체적인 선언·처분·질문·복구 형식은 「공통 실행」과 실행별 스키마를 따른다.

### 실제 수행 범위와 근거를 남긴다

연구 수행은 배정받은 작업 계약의 질문을 탐구한다. 수행 방법은 질문과 현재 근거에 따라 선택하되, 사용한 지식의 적용 조건과 새로 확인한 사실을 구별한다. 결과가 예상과 다르거나 유망한 방법을 찾지 못했더라도 실제 시도와 그 한계를 남긴다. 그래야 후속 연구가 무엇을 다시 검토해야 하고 무엇을 이미 배제할 수 있는지 판단할 수 있다.

진행 중에는 공통 실행 절차에 따라 체크포인트를 공개한다. 다른 활동의 결과나 사용자 결정 없이는 더 진행할 수 없으면, 이미 얻은 결과와 남은 질문, 필요한 입력을 보존하고 실행을 끝낸다. 대기 중인 연구 의무는 과제와 활동의 기록으로 이어지며, 대기를 위해 실행을 계속 점유하지 않는다.

기계 실행기는 종료를 확인한 뒤 산출 묶음을 보존한다. 그 결과를 연구 계획, 수학 검토, 사용자 대화 등 다음 소유자에게 전달한다. 과제의 완료 여부는 지정된 판정자가 작업 계약의 완료 기준과 실제 산출을 대조하여 판단한다.

문헌 조사와 원문 대조에는 [학술자료 활용](references/학술자료-활용.md)의 scholarly 호출·원본 판독·근거 보존 절차를 적용한다. 실제 도구가 제공되지 않으면 실행 구성의 수리로 연결하고, 자료원 응답 실패를 문헌 부재로 해석하지 않는다. 역할 산출의 출력 수리가 반복 실패하면 해당 실행 요청과 오류를 보존해 진단하고, 현재 입력에 맞는 후속을 정한다. 독립적으로 진행 가능한 다른 작업은 계속한다.

### 수학적 주장과 목표 충족을 각각 검토한다

수학 제안은 형식 결과와 수학 해설, 해설 요약의 연결을 검토할 수 있게 작성한다. 형식 검사는 고정한 신뢰 환경에서 Lean 표현을 검사하고, 독립 동일성 검토는 그 표현과 해설의 의미가 일치하는지를 판단한다. 형식 타당성, 해설 동일성, 목표 충족, 행동 허가와 실행 상태는 각각 자기 근거로 판단한다.

동일성 검토에서 이의가 제기되면, 이의의 근거를 정리하고 독립 심사와 원 검토자의 답변으로 이어간다. 같은 검토 자리의 대화를 이어받는 일과 같은 단계의 동료 결과를 미리 보는 일을 구별한다. 필요한 판단을 끝내지 못하면 그 범위와 근거를 미해결로 보존하여 다음 연구 계획에 돌려준다. 이 절차의 단계별 책임은 「동일성 검토」 계약이 설명한다.

목표 완료로 더 배정하지 않을 요청은 원 요청과 중단 이유, 남은 의무와 다음 담당을 보존하고 소유 활동을 정산한다. 아직 해석하지 않은 사용자 입력은 미처리 사실을 알린다. 실행 중인 활동은 실제 실행이 끝난 뒤 정산하며, 이 정산을 과제의 성공이나 보류된 산출의 편입으로 해석하지 않는다.

형식 정본 K에 정확한 결과를 보존한 뒤에도 목표에 남은 차이가 있을 수 있다. 목표 감사는 현재 목표와 사용할 형식 결과, 해설, 동일성 판정을 대조한다. 연구 책임자가 별도로 정한 학술 검증 요구가 있다면 수학적 해결 뒤에도 그 요구를 수행하고 완료 여부를 판단한다.

### 결과를 다음 연구 판단에 반영한다

후보 준비와 연구 계획은 이전에 기대한 연구 변화와 실제 결과를 비교한다. 새 결과 때문에 어떤 접근이 가능해졌는지, 어떤 가정이 여전히 남아 있는지, 보류한 질문을 다시 볼 이유가 생겼는지를 판단한다. 사용할 지식이나 판정의 효력이 바뀌었다면 실제로 그 근거에 의존한 판단을 다시 살핀다.

이 과정에서 연구 진전은 목표에 상대적으로 판단한다. 새 후보나 형식 결과가 늘었다는 사실, 파일이 생성됐다는 사실, 실행이 오래 지속됐다는 사실만으로 진전을 확정하지 않는다. 정확한 결과의 보존 가치와 현재 목표에 기여하는 정도도 구별하여 기록한다.

## 같은 연구에서 구별해야 하는 결과

목표가 조건 없는 P의 증명인데, H를 가정한 H → P를 얻었다고 하자. H와 적용 범위를 정확히 밝힌 형식 결과와 수학 해설은 검토를 거쳐 K에 편입될 수 있다. 그러나 H가 아직 입증되지 않았다면 이 결과만으로 목표 P가 해결됐다고 판단할 수는 없다. 다음 연구 계획은 H의 입증이나 제거, 다른 접근의 가능성을 비교한다.

이 과제의 완료 기준이 검토할 수 있는 제안의 제출과 실제 수행 범위의 보고였다면, 그 기준을 충족한 과제는 완료될 수 있다. 수학적 해결은 여전히 별도 판단이다. 반대로 작업 계약이 인증까지 요구했다면 그 검토도 끝나야 과제 완료가 가능하다. 완료의 의미는 실제 작업 계약에서 읽는다.

또한 검토에서 미해결이 나왔다고 해서 확보한 논증과 반례, 조사 결과가 사라지는 것은 아니다. 어느 범위를 확인했고 무엇을 확정하지 못했는지를 보존하여 다음 연구에 전달한다. 과제 완료, 활동 종료, 실행 종료와 수학적 해결을 구별하면 부분 결과를 과장하지 않으면서도 연구에 다시 사용할 수 있다.

## 역할 읽기 대응표

기계 실행기가 배정한 내부 AI 실행은 공통 문서를 아래에 적힌 순서로 읽고, 이어 자기 역할에 배정된 참조 문서와 계약을 읽는다. 공통 개념의 정의는 GLOSSARY.md에서, 실제 공통 절차는 references의 지정 문서에서 회수한다. 역할 계약은 그 정의와 절차를 자기 판단에 어떻게 적용할지 설명한다.

모든 내부 역할은 「공통 실행」의 「최종 응답을 전달하고 필요한 오류를 수리한다」 절이 정한 제출·수리 절차를 따른다. 정상 CLI 완료나 기계 검사의 통과는 형식 타당성·해설 동일성·목표 충족·과제 완료를 대신하지 않는다.

다음 표가 역할별 문서 목록과 읽는 순서를 정한다. 모든 역할은 common 행의 문서를 받고, 판단에 쓰는 역할만 추가 참조 문서를 받는다. 「모델과 실행예산」은 모델 평가를 작성·갱신·검토하는 후보 준비·연구 계획·작업 계약 검토만, 「자기 점검」은 자기 점검을 수행하는 연구 수행과 그 실행을 진단하는 운영 점검만 받는다. 기계 실행기는 이 표에서 문서를 선택해 입력에 제공한다. 실행에 실제로 제공된 문서의 경로와 해시는 역할이 입력 문맥의 `implementation_documents`에서 확인하며, 실행기는 같은 목록을 입력 manifest에 보존한다. 실행별 목표, 정책, 과제, 원자료와 이전 결과는 이 구현 문서들과 구별해 같은 입력으로 제공된다.

이 표는 기계 실행기가 배정하는 내부 AI 역할에 적용한다. 예약 감독은 모델 없는 기계 경로이며 이 표의 역할이 아니다. 실행기 시작 실패 또는 수락된 설치 결함 진단이 있을 때 열리는 설치 복구 AI의 범위와 현재 구현 프롬프트는 `계약/독립-운영.md`가 설명한다.

`action.role`이 아래 행을 고르고 `action.stage`는 그 역할 안의 실행 단계를 정한다. 의도 해석의 독립 검사는 같은 `intent_interpretation` 역할의 `stage=check`이며, 동일성 검토의 범위 계획은 `identity_review` 역할의 `stage=scope`다. 단계마다 별도의 역할 문서 목록을 만들지 않는다.

# do-math CLI 운영 안내

초기화의 구조 검사, 신뢰 환경의 툴체인 기록과 확인, 결과 적용, 정상 정비와 단계별 시간 조회는 [초기화 효율과 정비](references/초기화-효율과-정비.md)를 따른다. 설치 교체 전에는 `quiesce`로 정산하고 실제 종료를 확인한다. 신뢰 환경 등록은 공유 툴체인 기록의 기준 항목에 결박된 비활성 후보의 보존이며, 현재 판본 식별과 지문의 대조는 활성화 기계 작업과 형식 검사가 수행한다.

이 스킬은 프리알파이며 현재 판본 하나만 지원한다. 이전 코드·설정·저장 형식과의 호환성이나 마이그레이션을 제공하지 않는다. 계약 변경 뒤에는 새 인스턴스로 실험한다. 개발 시 [AGENTS.md](AGENTS.md)의 원칙을 따른다.

사용자 대화의 선행 읽기와 역할은 SKILL.md의 [진입 절차](SKILL.md#이-문서를-읽는-실행의-역할)를 따른다. 아래 [운전 책임과 실행 구조](#operating-model)를 바탕으로 요청에 맞는 경로를 선택한다.

- [직접 전진·수동 운전](#manual-run): 해당 절의 적용 조건을 확인한 뒤 허가된 범위를 직접 실행한다.

## 운전 책임과 실행 구조

사용자 대화가 연구 시작 요청을 받았을 때의 작업은 승인된 연구가 실제로 수행될 조건을 마련하고, 독립 실행으로 이어졌는지 확인하는 것이다. 연구 목표는 인스턴스가 계속 소유한다. 대화는 공개 CLI를 통해 사용자의 요청·결정과 실제 환경의 증거를 연결하며, 지금 수행하는 준비·진단·수리가 연구 시작을 어디까지 전진시키는지 판단한다. 운전 중 직접 얻은 증명이나 계산 결과는 그 자체로 초기화·실행·인계의 상태를 바꾸지 않는다.

인스턴스에는 프로세스가 끝난 뒤에도 목표, 권한, 연구 기록과 미완료 의무가 남는다. 기계 실행기는 현재 입력·권한·프로필·자원이 허용하는 요청을 AI 역할이나 기계 작업에 배정하고, 산출을 검사하여 기록과 후속 처리에 연결한다. 요청을 기록한 사실, 실행이 시작된 사실, 결과가 적용된 사실은 각각 그 다음 처리가 어디까지 가능해졌는지를 설명하는 근거다. 프로세스가 없더라도 보존된 의무와 재개 조건이 있을 수 있으며, 프로세스가 살아 있어도 특정 후속 요청이 배정됐다는 뜻은 아니다.

예약 감독은 연구 실행기와 별도 수명으로 동작하면서 현재 상태와 시작 조건을 대조하고, 시작 가능한 연구 실행기를 깨운다. 실제 연구 배정은 실행기가 맡는다. 대화 이후에도 이 연결이 이어지려면 승인된 대화 소실 정책과 유효한 허가, 실제 예약·실행 경로가 갖춰져 있어야 한다. 설치 복구 AI도 보존된 실패 또는 수락된 설치 결함 진단과 정해진 관문에서 열린다. 감독의 존재만으로 미완료 준비나 임의의 오류가 자동 처리되지는 않는다. 정확한 감독·복구 범위는 [독립 운영 계약](계약/독립-운영.md)을 따른다.

따라서 남은 일을 누가 이어받았는지는 그 일을 소유하는 실제 기록과 처리 경로로 판단한다. 오류 응답의 `next_owner`나 보고서의 담당 명칭은 진단상 책임을 가리킬 수 있지만, 후속 요청의 접수·배정·실행을 증명하지는 않는다. 사용자 대화는 현재 상태에서 다음 행동이 무엇에 의해 일어날 수 있는지, 필요한 입력과 권한이 어디에 있는지, 이 대화 이후에도 그 경로가 유지되는지를 근거로 [계속 수행·인계·종료를 판단한다](#handoff-judgment). 주체와 상태의 뜻은 [GLOSSARY.md](GLOSSARY.md)의 공통 정의를 그대로 사용한다.

### 1. 요청과 설정 확정

사용자의 목표와 제약을 포함한 전체 원문을 보존하고, 생성에 필요한 경로·모델·설정을 확정한다. 수학 목표와 전체 요청이 다르면 `--goal` 또는 `--goal-file`에 수학 목표를, `--request-text` 또는 `--request-text-file`에 전체 원문을 전달한다. 기존에 승인된 결정은 재사용한다. 사용자만 정할 중요한 결정이 빠져 있으면 해당 항목을 질문하며, 이후 채택 단계에서 확정할 항목과 구별한다.

새 인스턴스는 아래의 기본 운영 구성을 사용한다. 사용자 제약과 실제 실행 환경 때문에 필요한 항목을 변경하고 이유를 기록한다. 모델 상한은 사용할 모든 등급의 모델 대응과 작업 슬롯 설정에 반영하며, 운영 역할과 설치 복구 AI가 쓰는 모델도 포함한다. 예약 감독과 문헌 조사 도구인 scholarly의 설정 변경은 별도로 판단한다. 문제의 난이도만으로 수동 운영을 선택하지 않는다.

#### 실행 환경과 초기 설정

아래 명령 예시는 Codex 설치 경로인 `.agents/skills/do-math/`를 사용한다. 이 저장소에서 Codex로 운전할 때는 이 경로를 쓴다. 다른 위치에 설치한 경우에는 예시의 스킬 경로를 실제 설치 폴더로 바꾸고, 그 폴더의 문서와 코드를 함께 사용한다.

Windows에서 Python 3.12, Git과 사용할 모델의 CLI를 준비한다. Codex 모델에는 로그인된 Codex CLI, Claude 모델에는 로그인된 Claude CLI가 필요하다. Python 의존성은 `requirements.txt`에 고정돼 있으며 현재 직접 의존성은 `jsonschema==4.26.0`이다.

현재 Windows 구현은 배정된 모델에 따라 `codex exec` 또는 `claude --print`를 호출하고 각 CLI의 기존 로그인을 사용한다. 별도의 API 키를 요구하지 않는다. 두 CLI 모두 같은 모델별 작업 슬롯 예산과 역할 계약을 따른다.

```powershell
python -m pip install -r .agents/skills/do-math/requirements.txt
codex --version
git --version
python .agents/skills/do-math/scripts/do_math.py profile
```

`profile`은 설치된 Codex CLI의 명령 표면을 조사한다. 종료 코드 0과 `verified=true`는 그 조사 항목이 확인됐다는 뜻이다. 연구 역할의 품질, Lean 설치, 파일 격리나 원격 공급자 상태까지 보증하지 않는다.

Claude를 사용할 때에는 `claude auth status`로 로그인 상태를 확인하고 `python .agents/skills/do-math/scripts/do_math.py profile --provider claude`로 필요한 명령 표면을 검사한다. CLI는 `PATH`에서 찾으며 `CLAUDE_CONFIG_DIR`로 지정한 로그인 설정 위치도 전달한다. API 키나 별도 API 공급자로 자동 전환하지 않는다. 외부 Claude CLI의 `claude --bare` 모드는 구독 로그인을 사용하지 않으므로 이 실행 경로에서는 사용하지 않는다.

형식 검사에는 Lean이 필요하다. `setup_lean.py`는 이 머신의 인스턴스들이 함께 쓰는 Lean 4.32.0 툴체인과, 같은 판본의 Mathlib 태그에 고정한 Lake 프로젝트를 저장소 루트의 `.skill-workspace/do-math-toolchains/`에 준비한다.

```powershell
python .agents/skills/do-math/scripts/setup_lean.py
```

툴체인이 없으면 Lean 배포본을 내려받고, Mathlib을 복제한 뒤 미리 빌드된 캐시를 받는다. 수 GB의 디스크와 네트워크를 사용하며, 이미 끝난 단계는 다시 실행해도 건너뛴다. 마지막에 판정 파일(커널이 적재하는 `.olean`과 Lean 런타임 라이브러리)의 지문과 내용 해시를 계산하고 검사기가 실제로 쓸 명령으로 `import Mathlib` 파일을 컴파일한다. 성공했을 때에만 툴체인 기록(`.skill-workspace/do-math-toolchains/records/<기록 ID>.json`)을 쓰고 준비 표지를 남기며, 그 명령을 JSON의 `lean_command`로 출력한다. 같은 판본의 기록이 이미 있고 현재 지문이 그 기준과 같으면 다시 컴파일하지 않는다. 컴파일이 끝날 때까지 기다리며 실행 시간으로 중단하지 않는다. 컴파일이 실패하면 표지를 지우고 종료 코드 1로 끝나며, 이때 실행기는 이 프로젝트를 선택하지 않는다.

준비 표지가 있으면 `lean_command`를 생략한 인스턴스는 이 프로젝트를 거쳐 Lean을 실행하므로 제출 소스에서 Mathlib을 import할 수 있다. 설정에 명시한 `lean_command`는 언제나 이 탐색보다 우선한다. 준비 전과 후에는 탐색되는 명령이 다르므로 검사 결과에 기록되는 toolchain도 달라진다.

사전 빌드 캐시를 사용할 수 있으며 클린 빌드는 요구하지 않는다. 준비 완료 출력에는 툴체인 기록의 경로·ID와 현재 기준의 결박(`binding`)이 들어간다. `--trust-file <새 JSON 경로>`를 함께 지정하면 그 기록을 인스턴스에 결박하는 등록 요청을 생성한다. 대표 검사의 원문·명령·출력·종료 코드는 툴체인 기록에 들어가고, 증거 파일은 `.skill-workspace/do-math-toolchains/validation/`의 고유 디렉터리에 보존한다. 대표 검사의 통과는 Mathlib import와 대표 증명 검사의 통과를 뜻하며 전체 라이브러리 재검증을 뜻하지 않는다. 이미 설치된 환경은 `setup_lean.py --inspect-only`로 판본 식별만 관측할 수 있으며, 별도 명령은 `--command-file`로 지정한다. 이 관측은 기록이나 채택이 아니다. 재기록(`--rerecord`, 사용자·운전자 전용)과 선택적 전수 점검(`--check-contents`)은 [초기화 효율과 정비](references/초기화-효율과-정비.md)를, 실제 등록은 [초기화 운전](references/초기화-운전.md)을 따른다.

이미 설치한 환경은 다음 명령으로 내려받지 않고 기록해 등록 요청을 얻는다. `--evidence-dir`는 선택 사항이며 대표 컴파일 증거를 둘 상위 경로를 바꾼다. 이 경로는 Lean 설치와 Lake 프로젝트 밖에 둔다.

```powershell
python .agents/skills/do-math/scripts/setup_lean.py --verify-only --trust-file .skill-workspace/my-math/trust-register.json
```

명시적인 명령은 `--command-file`로 지정할 수 있다. 이 기록은 신뢰 환경 등록·사용자 채택을 자동 수행하지 않는다. 등록과 전환은 [초기화 운전](references/초기화-운전.md)을 따른다.

연구를 시작하기 전에 다음 경로를 정한다.

- `--repository`: 인스턴스의 권위 있는 상태와 산출 묶음을 저장할 Git 저장소다. `--create-repository`를 쓰려면 경로가 없거나 빈 디렉터리여야 한다.
- `--workspace`: 실행별 작업 공간, 제어 inbox와 복구 자료를 둘 로컬 경로다. Git 정본과 다른 역할을 하며, 작업 공간 파일만으로 공용 기록이 되지는 않는다.
- `--goal` 또는 `--goal-file`: 연구 헌장의 현재 목표가 될 원문이다. 둘 중 하나만 사용한다.
- 목표는 수학적 질문이다. 형식 결과·동일성 판정·목표 감사를 거쳐 `mathematically_solved`를 판단한다. 그 목표를 위한 문헌 조사·계산·비형식 과제도 사용할 수 있다.

초기화 때 원자료와 설정을 함께 넣을 수 있다. 정책은 [초기화 운전](references/초기화-운전.md)의 통치 채택 요청에 헌장과 함께 기록으로 넣는다. `--source`는 여러 번 지정할 수 있다. `--effort`는 설정 파일의 추론 노력보다 우선하며, 생략한 필드는 코드의 기본값을 사용한다.

관찰 설정의 `tool_review_window_seconds`와 `self_check_response_window_seconds`에는 제품 기본값이 없다. 프로필을 채택하기 전에 사용할 두 값을 확정하여 `init --config-file`이나 `configure --config-file`로 전달한다. 이미 승인된 설정에 있으면 그대로 사용한다. 주기·사건 관찰에는 도구 검토 window와 관찰 주기가 필요하고, 연구 수행에는 자기 점검 응답 window도 필요하다. 누락되거나 유효하지 않은 값은 역할·프로필 ID·필드와 함께 반환되며 연구 활성화가 완료되지 않는다. 구체적인 설정 보충과 능력 재관측은 [초기화 운전](references/초기화-운전.md)의 1단계와 4단계를 따른다.

모델 대응·역할별 최소 등급·모델별 동시 세션 예산은 설정 파일의 `tier_models`, `role_tiers`, `session_limits`로 정한다. 구체적인 설정은 아래 「모델과 동시실행 예산 설정」을 따른다. 모든 설정의 기본값과 허용 값은 [CLI 실행 계약의 설정 목록](references/CLI-실행-계약.md#config-list)에 있다.

독립 운영은 기본으로 활성이며, 활성 여부와 감독 주기의 기본값은 설정 목록을 따른다. 기본 모델 대응과 모델별 작업 슬롯 수는 [모델과 실행예산의 모델 표](references/모델과-실행예산.md#model-table)에 있다. 이 표와 배정 기준을 확인하고, 다른 용량이나 수동 운영이 필요하면 설정 파일에 지정한다. `init`은 독립 운영이 활성일 때 정상 감독과 연구 엔진을 맡는 두 숨김 Windows 예약 작업을 등록하며, 그 자체로 모델이나 연구 실행을 시작하지는 않는다. 첫 정기 감독은 등록 후 설정한 주기에 도래한다. 정상 감독은 저장 상태와 예약 상태를 모델 없이 검사하고 필요할 때 연구 엔진 작업만 요청한다. 연구 작업에는 고정 반복 주기를 두지 않는다. 엔진을 읽을 수 없는 실제 실패가 보존됐거나 운영 점검의 설치 결함 진단이 수락됐을 때 별도 설치 복구 AI 경로를 열 수 있다.

scholarly는 기본 활성이다. `scholarly_server`에 `command`·`args`를 직접 지정하거나, 초기화 명령의 작업 위치에서 상위로 찾은 `.codex/config.toml`의 scholarly 항목을 사용한다. 프로젝트 설정이 없으면 Codex 사용자 설정에서 같은 항목을 찾는다. 실행에 필요한 서버 경로는 고정해 인스턴스 설정에 보존하고, 하위 실행에는 이 MCP 설정만 명시적으로 전달한다. 서버 설정을 찾지 못한 것과 외부 자료원 접근 실패는 다르다. 사용 가능한 도구는 각 실행에서 확인한다.

#### 모델과 동시실행 예산 설정

모델의 기본 대응과 배정 기준은 [모델과 실행예산](references/모델과-실행예산.md)에 있다. 아래 형식의 JSON을 설정 파일로 저장해 `init --config-file` 또는 `configure --config-file`에 전달하면 모델 대응과 모델별 작업 슬롯 수를 명시할 수 있다. 작업 역할의 과제는 난이도·중요도에 맞춘 모델의 작업 슬롯이 없으면 대기한다.

```json
{
  "tier_models": {"high": "gpt-6-astra", "medium": "gpt-5.6-sol", "low": "gpt-5.6-terra"},
  "session_limits": {
    "work": {"gpt-6-astra": 3, "gpt-5.6-sol": 3, "gpt-5.6-terra": 3}
  }
}
```

`session_limits`에는 작업 슬롯의 `work` 맵 하나만 둔다. 슬롯은 실행이 끝나면 다음 실행이 재사용한다. 모델 이름을 바꾸면 `work` 맵에도 `tier_models`의 모든 모델을 명시한다. 후보 준비·연구 계획·의도 해석·운영 점검·유지보수 같은 운영 역할은 슬롯을 예약하지 않고, 역할별 최소 등급과 대상의 요구로 정한 모델에 바로 배정된다.

Claude를 배정하려면 `claude:opus`, `claude:sonnet`, `claude:haiku`처럼 `claude:` 뒤에 CLI 모델 이름이나 별칭을 적는다. `claude-`로 시작하는 전체 모델 ID도 사용할 수 있다. 다른 이름은 Codex로 전달한다. 같은 등급·모델 선택 규칙을 연구·검토·운영 역할에 적용한다. 정상 예약 감독은 모델을 호출하지 않는다. 엔진 실패 뒤 허용된 live 설치 수리를 수행하는 복구 AI는 운영 역할과 마찬가지로 슬롯을 예약하지 않는다.

[Claude·Codex 혼합 설정 예시](examples/claude-codex-sessions.json)는 상 등급에 `claude:opus`, 중 등급에 `gpt-5.6-sol`, 하 등급에 `claude:haiku`를 배정하고 각 모델의 작업 슬롯 수를 명시한다. `init --config-file`이나 `configure --config-file`에 이 파일을 전달할 수 있다. 예시를 적용할 때에만 해당 모델과 용량을 사용하며, 적용하지 않으면 모델 표의 기본 구성을 사용한다. 각 등급에는 모델 하나를 지정한다. 모델별 예산의 식별자는 설정 문자열이므로 `tier_models`와 `work` 맵의 표기를 일치시키고, 같은 모델을 별칭과 전체 ID로 중복 등록하지 않는다.

두 CLI를 함께 쓸 때 공통 `effort`에는 `low`, `medium`, `high`, `xhigh`를 사용할 수 있다. Claude의 `operator_effort`는 이 값들과 `max`를 지원하며 `minimal`·`ultra`는 지원하지 않는다. 지원하지 않는 노력 수준이나 사용할 수 없는 모델로 호출하면 실패로 기록하고 자동으로 다른 모델이나 수준을 선택하지 않는다. Claude 별칭은 CLI가 현재 제공하는 모델로 해석하므로 판본을 고정하려면 사용 가능한 전체 ID를 지정한다.

### 2. 인스턴스 생성

아래 예시는 새 Git 저장소와 작업 공간을 만들고 수학 목표를 시작한다. PowerShell에서 현재 디렉터리는 저장소 루트라고 가정한다.

```powershell
python .agents/skills/do-math/scripts/do_math.py init `

  --workspace .skill-workspace/my-math/work `

  --title "자연수 덧셈의 오른쪽 항등원" `

```

### 3. 초기화 완료

`init`은 입력 문자열의 코드 포인트열과 그 UTF-8 바이트 해시·크기를 `immutable_input.text/sha256/bytes`에 한 번만 보존하고 설정·초기 source를 고정한다. 이름과 원문을 정규화하거나 별도 원문 사본으로 바꾸지 않는다. 첫 commit에는 실행 grant나 연구 queue가 없다. 이후 [초기화 운전](references/초기화-운전.md)의 공개 명령과 요청 예시를 순서대로 따른다. 그 문서는 통치·권한 채택, 현행 프로필의 능력 관측과 채택, 신뢰 환경과 최초 의도 해석·검사·적용을 설명한다. 이미 채택한 기본값은 같은 승인 근거를 재사용한다. 초기화 실행에는 `run --until-active`를 사용한다. 이 명령은 활성화 관문이 충족되면 연구 역할을 배정하기 전에 반환하며, 남은 관문이 있으면 그 상태를 보고한다.

초기화의 독립 검사와 실제 적용, 현재 능력·신뢰·복구 관문이 모두 충족된 경우에만 연구가 활성화된다. 초기화 운전의 마지막 절에 따라 현재 인스턴스의 승인 원문, 독립 검사와 수입 적용 기록을 확인한다. 미완료 관문을 내부 함수 호출이나 저장 파일 편집으로 우회하지 않는다.

독립 인계에는 `conversation_loss_policy=continue_authorized`가 승인·적용되어 있는지도 확인한다. 이 정책에서는 대화의 attach·heartbeat 없이 허가된 연구를 계속할 수 있다. 초기화 관문은 `pause` 정책도 허용하므로, 활성화만으로 대화 종료 후의 지속 실행을 보장하지 않는다. 기존 승인 근거를 재사용하고, 다른 정책이 승인되어 있으면 그 결정을 임의로 바꾸지 않는다. 새 사용자 결정이 필요한 경우에는 그 조건의 영향과 대기 범위를 명시한다. 사용자 정지·HOLD·허가 만료와 철회는 계속 적용된다.

초기화 관문 전건과 실제 적용 기록, 독립 인계의 정책 조건을 확인하면 [4단계](#start-engine)로 간다. 수동 운영으로 정한 인스턴스는 [직접 전진·수동 운전](#manual-run)으로 이어 간다.

### 4. 독립 실행 시작과 관측

먼저 `operator status`와 `status --json`으로 대상 인스턴스의 예약 작업과 연구 상태를 읽는다. 같은 인스턴스의 연구 프로세스가 이미 실행 중이면 그 실행을 확인한다. 실행 중이 아니고 시작 조건이 충족되면 다음 명령으로 별도 연구 예약 작업을 시작한다.

```powershell
python .agents/skills/do-math/scripts/do_math.py operator start `
  --repository .skill-workspace/my-math/repo --instance RI-...
```

Windows 로그인, 켜져 있고 절전하지 않는 PC, 네트워크와 배정된 모델 CLI의 유효한 인증이 필요하다. 화면 잠금과 로그아웃은 다르다. 놓친 예약은 실행 가능한 상태에서 처리하도록 등록한다. 연구 실행의 내부 관찰·점검과 `operator_interval_seconds`의 주기마다 수행하는 모델 없는 예약 감독은 별도로 유지된다. 감독은 HOLD·정지·종결·완료·모델 정책 위반과 엔진 작업 상태를 읽고, 실행 가능할 때 엔진 작업을 요청한다.

`operator start-operator`는 별도 정상 감독 작업을 즉시 요청한다. 정상 감독은 모델을 호출하지 않으며, 실패 시 설치 복구 AI가 열리는 조건은 [독립 운영 계약](계약/독립-운영.md)을 따른다.

시작 요청 뒤 다음 관측을 수행한다. 시작 관측 구간은 30초로 두고, 그 안에 필요한 근거를 얻으면 보고 단계로 간다. 이 구간은 대화의 시작 확인 범위이며, 연구 프로세스나 계산을 종료하는 시간 제한이 아니다.

1. 명령의 반환 내용을 확인한다. `operator start`는 시작 조건이 충족되지 않으면 `held`, `paused`, `not_started` 등의 결과와 종료 코드 0을 반환할 수 있다. 예약 시작 요청이 수행된 반환과 조건에 따른 비시작 반환을 구별한다.
2. `operator status`로 연구·감독 작업을 조회한다. 감독의 등록·활성 상태·주기·다음 실행 시각을 확인한다. 연구 작업의 `Running` 상태는 bootstrap 실행도 포함하므로, 대상 저장소와 인스턴스 ID의 실제 연구 명령이 실행 중인지 호스트 프로세스 정보와 대조한다.
3. `status --json`으로 사용자 정지·대기 이유·현재 연구 상태를 읽는다. 호스트 관측과 저장 상태는 관측 시각이 다르므로 각각의 시각을 남긴다. AI 작업이 아직 배정되지 않았다는 사실만으로 연구 실행기의 시작을 부정하지 않는다.

```powershell
python .agents/skills/do-math/scripts/do_math.py operator status `
  --repository .skill-workspace/my-math/repo --instance RI-...
python .agents/skills/do-math/scripts/do_math.py status `
  --repository .skill-workspace/my-math/repo --instance RI-... --json
```

Windows에서는 `Get-CimInstance Win32_Process`의 `ProcessId`, `ParentProcessId`, `CommandLine`으로 대상 인스턴스의 프로세스를 대조할 수 있다. 연구 예약 작업은 bootstrap을 거쳐 `do_math.py run --repository <대상 저장소> --instance <대상 ID> --watch`를 실행한다. 이미 실행 중이던 같은 인스턴스의 프로세스는 현재 관측으로 확인하고, 종료된 과거 실행 기록을 새로운 시작의 근거로 쓰지 않는다.

시작 조건을 통과한 실행의 기록은 `<workspace>/operator/engine/<실행 디렉터리>/`에 있다. `result.json`의 `outcome=running`은 자식 프로세스 생성 전에 기록되므로 단독 시작 증거가 아니다. 이후 실행·종료 결과는 해당 디렉터리와 `<workspace>/operator/latest-engine.json`에 보존된다. 다른 실행기가 writer lock을 보유해 `run`이 재시도 가능한 도구 오류로 끝나면 `outcome=engine_busy`로 기록한다. 이 기록은 설치 복구를 열지 않으며, 다음 감독이 시작 조건을 다시 확인한다. 시작 조건에 따른 정상 비시작 반환에서는 두 기록이 새로 생성되지 않을 수 있고, 시작 조건 조회의 예외는 `latest-engine.json`에만 기록될 수 있다. 새 기록의 부재만으로 성공이나 실패를 추측하지 않는다.

관측 전에 실행이 끝났으면 이번 시작에 대응하는 종료 기록과 현재 연구 상태를 읽는다. 종료 코드 0이나 `outcome=completed`는 프로세스 종료 사실이며 수학적 목표 완료를 뜻하지 않는다. [보고 단계](#report-handoff)에서 관측한 상태를 구별한다.

### 5. 인계 결과 보고

<a id="handoff-judgment"></a>

#### 계속 수행·인계·종료의 판단 기준

이번 대화의 성과는 승인된 연구의 준비·실행·후속 처리가 실제로 어디까지 연결됐는지로 판단한다. 계속할 작업의 가치는 현재 권한 안에서 무엇을 확인하거나 바꿀 수 있고, 그것이 시작을 막는 조건이나 불확실성을 어떻게 해소하는지에 있다. 실패 횟수나 같은 명령의 반복 자체는 복구 가능성 또는 불가능성의 근거가 아니다. 아직 확인하지 못한 사항과 실제로 확인한 차단 조건을 구별한다.

인계 판단에는 남은 의무의 대상과 수신 주체, 그 주체가 읽을 보존 자료, 실제 요청·배정의 상태, 현재 또는 재개 조건 충족 뒤 작동할 실행 경로가 함께 필요하다. 이 근거로 준비 중인 인계, 접수된 후속, 실행 중인 처리와 미배정 의무를 구별한다. 인계가 성립했다고 설명하려면 이 대화가 끝나도 누가 어떤 조건과 근거로 남은 일을 처리할 수 있는지 밝혀져 있어야 한다. 최초 연구 시작의 인계 완료는 앞 단계에서 확인한 초기화·정책·예약 조건과 실제 연구 실행을 근거로 한다.

대화를 마치는 판단은 남은 의무가 어떻게 보존되고 처리될지 설명할 수 있어야 한다. 추가 작업을 이 대화에서 수행할 수 있는 범위, 이미 이어진 처리 경로, 사용자 결정이나 외부 입력에 의존하는 범위를 함께 평가한다. 실제 수신이나 실행 경로가 확인되지 않은 의무는 미인계로 남긴다. 대기와 관측 불확실성을 설명하는 일은 이미 승인된 독립 작업까지 중단할 이유가 되지 않는다. 사용자 정지와 권한 경계는 이 판단에 계속 적용된다.

#### 시작 요청의 결과를 전달한다

최종 보고는 독립 실행 인계의 결과와 현재 연구 상태, 남은 의무를 먼저 설명한다. 시작을 확인하지 못했거나 초기화가 미완료인 범위도 이 중심 결과에 포함한다. 이어 인스턴스 ID와 저장소·작업 공간, 적용한 모델 제한, 시작 관측 시각과 근거, 감독 상태·주기, 실제 후속 담당과 재개 조건, 조회 방법을 제시한다. 관측하지 못한 값과 아직 배정되지 않은 담당은 그 사실대로 적는다.

이번 프로세스의 종료 상태와 연구 목표의 해결 상태는 각 근거로 보고한다. 수학적 목표 완료는 목표 감사와 적용되는 학술 요구의 근거를 확인한다. 운전 과정에서 별도로 얻은 증명·계산·Lean 검사 결과는 확인 범위를 밝힌 부수 결과로 전달한다. 그러한 결과의 획득을 이유로 시작 요청의 성과나 남은 운전 책임을 바꾸지 않는다. 사용자에게 전달할 중심 결과가 수학 풀이로 옮겨가지 않도록 보고의 분량과 순서도 이 목적에 맞춘다.

## 직접 전진·수동 운전

이 절은 독립 운영을 끈 인스턴스를 수동으로 운전할 때, 또는 `operator status`와 `status`로 예약 연구 작업이 실행 중이 아님을 확인한 뒤 허가된 범위를 정해 직접 전진시킬 때 사용한다. 초기화 중 제한 실행은 [초기화 운전](references/초기화-운전.md)이 지정한 단계와 적용 결과를 따른다.

독립 운영이 활성인 인스턴스의 지속 연구는 [독립 실행 절차](#start-engine)가 확인한 연구 예약 작업이 맡는다. 사용자 대화는 그 예약 작업이 실행 중일 때 `run`을 함께 실행하지 않는다. 대화가 `run --watch`를 붙잡으면 연구 진행이 대화의 수명에 묶이고, 뒤에 시작한 예약 작업은 writer lock을 얻지 못해 실패로 끝난다.

`run`에는 전체 실행 시간 제한이 없다. 실행기는 현재 권한·입력·자원이 허용하는 연구와 검토를 배정하고 결과를 회수한다. 작업 예산 AI와 이미 시작한 Lean 계산은 경과 시간만으로 종료하지 않는다. 운영 AI에는 `call_timeout_seconds`가 정하는 개별 호출 기한을 적용한다. 중앙의 일반 형식 검사와 신뢰 환경 전환 검사는 두 종류의 동시 실행 수를 합해 인스턴스당 최대 한 건으로 제한한다. 사용자 정지·종결·권한 회수·필수 전제 변경과 수락된 운영 처분은 해당 실행의 종료·회수 경로를 따른다.


=== N01-026 repo:.claude/skills/do-math/README.md 269-288 ===
### 정해진 수만큼 전진시킨다

```powershell
python .agents/skills/do-math/scripts/do_math.py run `
  --repository .skill-workspace/my-math/repo `
  --instance RI-... `
  --max-steps 5
```

`--max-steps`는 이번 `run` 호출이 처리할 action 수의 상한이다. 수학 연구 단계나 모델 호출 수와 항상 같지는 않는다. 형식 검사·외부 행동 같은 기계 action도 한 step으로 처리될 수 있고, 하나의 AI 실행 안에서 모델 CLI가 수행한 내부 동작 수를 세지 않는다.

`--max-steps`는 새 action 시작 수의 상한이며 이미 시작한 실행을 시간으로 끊지 않는다. 생략하면 실행기는 queue와 현재 설정이 허용하는 동안 진행한다. `--watch`를 함께 쓰면 CLI 상태가 `waiting`이어도 제어 inbox, 대화 lease와 관찰 사건을 계속 확인한다. 사용자 정지·종결·목표 완료 또는 지정한 시작 수에 따른 회수가 끝나면 반환한다. 사용자 결정을 자동으로 만들거나 waiting 과제의 조건을 임의로 해소하지 않는다.

```powershell
python .agents/skills/do-math/scripts/do_math.py run `
  --repository .skill-workspace/my-math/repo `
  --instance RI-... `
  --watch
```


=== N01-027 repo:.claude/skills/do-math/README.md 289-299 ===
### 반환 상태를 다시 확인한다

`run`은 마지막 status JSON을 반환한다. 다음 경우에는 세부 기록을 읽고 다음 행동을 정한다.

- `ready`: 처리할 action이 남았거나 다음 `run`에서 계속할 수 있다.
- `waiting`: `questions`, 대기 과제 또는 외부 사건을 확인한다. 입력·결정 없이 같은 `run`을 반복해도 조건이 바뀌지 않는다.
- `capacity_waiting`: 작업 역할 요청이 배정된 모델의 작업 슬롯이나 호스트 용량을 기다린다. 같은 인스턴스의 점유와 설정을 확인하고, 반환 뒤 `run` 또는 `run --watch`로 이어간다.
- `paused`: 사용자 정지, 실행기 복구, 설치 문서 변경이나 인스턴스 전체의 중단 사유를 확인한다. `resume` 전에 `check`, status의 questions와 최근 실행 기록을 읽는다. 개별 실행의 실패는 해당 요청을 보류하고 운영 점검으로 연결하며, 독립 작업은 계속한다.
- `completed`: 현재 CLI가 목표와 적용되는 학술 요구의 완료 조건을 충족했다고 계산한 상태다. 정확한 목표 감사, K·해설·동일성 판정과 학술 근거를 별도로 읽는다.
- `closed`: 사용자가 인스턴스를 종결했다. `resume`으로 다시 열 수 없다.


=== N01-028 repo:.claude/skills/do-math/README.md 300-311 ===
## 역할 산출과 실패 처리

모든 내부 작업자에게 실행별 주 JSON·확장 스키마, 고정 입력과 `submission_contract.command`를 제공한다. 작업자는 스키마를 만족하는 완전한 JSON 값 하나를 최종 응답으로 반환한다. 중앙은 정상 완료한 native stream의 정확한 최종 바이트와 로컬 종료 뒤 작업 공간 산출을 같은 접수 절차로 포착해 검사·봉인한다. 실행 중 결과를 먼저 봉인하려면 `.scratch/submission.json` 같은 초안 경로를 `--submit` 또는 `submit_draft`에 넘길 수 있다. 이 명시 제출은 선택적 조기 전달이며, 이미 접수된 봉인 후보가 있으면 뒤의 다른 최종 응답으로 대체하지 않는다. 명령의 무옵션 로컬 검사와 preview도 오류를 미리 찾는 선택적 진단이며, 그 결과를 최종 접수 증거로 제출하지 않는다. `.scratch/`와 그 아래 `.scratch/.execution-temp/`는 버릴 중간 파일용이며 산출·근거로 수집하지 않는다. 검사 범위, 파일 한도와 정확한 제출 절차는 [공통 실행](references/공통-실행.md)을 따른다. 검사 통과나 정상 CLI 완료는 수학적 승인, 과제 완료 또는 수신 시점의 현재성 승인이 아니다.

신규·개정 후보에는 모델 평가가 하나씩 있어야 한다. 기존 미평가 과제는 평가를 보충하고, 학술 과제는 관찰 규칙도 준비한 뒤 독립 계약 검토를 받는다. 필요한 입력이 없으면 해당 보충을 보류한다. 평가와 규칙을 같은 실행에 배정할 수 있지만 사용자 질문·범위·완료 의무는 바꾸지 않는다. 구체적인 반환과 재개 조건은 [후보 준비 계약](계약/후보-준비.md)의 기존 과제 보충 절과 [모델과 실행예산](references/모델과-실행예산.md)을 따른다.

출력 수리나 진단 후 재시도까지 실패한 요청은 원 출력·오류·체크포인트와 함께 보류한다. 일반 `resume`은 이를 다시 실행하지 않는다. 연구가 활성화된 인스턴스에서는 실제 원인을 수리한 뒤 `request --role operational_review --target EX-...`로 해당 실패 실행의 진단을 명시적으로 요청할 수 있다. 이 진단이 `retry`를 선택하면 새 입력에서 한 번 더 실행하며, 다시 실패하면 재차 보류한다.

초기화 중 최초 원입력의 의도 해석이 기술적 실행 실패로 끝났다면 원인을 고친 뒤 `request --retry-action AC-... --request-id UC-...`로 그 해석을 다시 요청한다. 실행기는 전 실행의 로컬 종료와 예약 회수, 불변 원입력, 현재 채택 프로필과 초기 운영 권한을 확인한다. 같은 action과 활동을 이어 간다. 정상 종료한 native 최종 응답이 정확한 실행 근거와 함께 보존돼 있으면 새 모델 실행 없이 그 응답을 중앙에서 다시 처리하며, 원 실행의 종료 시각·결과 참조·실패 이력을 보존한다. 재사용할 정상 응답이 없으면 실패 실행을 선행 기록으로 연결한 새 실행을 배정한다. 아직 시작하지 않은 해당 실패의 운영 진단은 재시도로 대체한 이력에 남긴다. 이 요청은 새로운 연구를 열거나 의미를 승인하지 않는다.

`input_overflow`로 보류된 입력은 설치나 필수 입력을 수리했거나 사용자가 현재 설정을 적법하게 바꾼 뒤 `request --retry-action AC-... --request-id UC-...`로 정확한 action 하나를 명시적으로 다시 포장할 수 있다. 이 요청은 원 activity와 action ID를 유지하면서 현재 grant와 현재 채택 프로필을 다시 검사할 뿐, 입력 초과가 해소됐다고 선언하거나 새 권한을 만들지 않는다. 재시도에 따른 자동 질문 해소는 실제 포장이 현재 한도 안에 들어온 사실에 근거한다. 이미 적법한 결정으로 해소된 질문은 그 해소 근거를 유지한다. 다시 넘치면 원 실패와 질문은 이력으로 보존되고 새 실패와 새 질문이 같은 activity를 이어받는다. 같은 `request-id`의 재전송은 최초 효과만 재생한다.

=== N01-037 repo:.claude/skills/do-math/README.md 408-439 ===
## 정지, 재개와 종결

```powershell
python .agents/skills/do-math/scripts/do_math.py pause `
  --repository .skill-workspace/my-math/repo `
  --instance RI-... `
  --reason "정책 변경 전 상태를 검토합니다."
```

제어 명령은 먼저 workspace의 inbox에 요청을 기록한다. 같은 인스턴스의 writer lock을 얻을 수 있으면 즉시 적용하고, 다른 실행기가 lock을 보유하면 `effect="pending engine processing"`, `lock="busy"`를 반환한다. 이 경우 현재 실행기나 다음 `run`이 요청을 적용한다.

같은 내용의 제어 명령을 다시 보내면 최초 영수증을 재생하며 효과를 반복하지 않는다. 정지와 재개는 상태를 오가므로, 키 없이 보낸 정지·재개는 마지막으로 접수된 반대 제어와 함께 식별된다. 그래서 재개 뒤 같은 이유로 다시 정지하면 키 없이도 새 요청으로 적용된다. 이전 설정을 새로 적용하는 것처럼 같은 내용을 새 결정으로 다시 적용하려면 명령에 새 `--idempotency-key`를 붙이고, 그 요청을 재전송할 때는 같은 키를 유지한다. `replayed=true` 응답의 상태·snapshot은 최초 처리 시점의 값이므로 현재 상태는 `status`로 확인한다. 직접 요청 ID를 지정하는 방법과 전체 적용 범위는 [CLI 실행 계약](references/CLI-실행-계약.md)의 공통 반환 절을 따른다.

AI 실행 중 pause·close, grant 철회, 필수 입력·목표·정책의 현재성 변경 또는 그 AI 실행에 적용된 기한 도래가 확인되면 실행기는 관리 디렉터리 `.control/`에 정지 요청을 기록한다. 작업자는 새 연구나 외부 행동을 시작하지 않고 이미 얻은 사실과 가능한 제출·체크포인트를 남긴다. 중앙은 정지 전에 미리 접수한 봉인 후보가 있으면 그 원문만 회수한다. 정지 뒤 도착한 native final이나 파일은 보존 자료일 수 있지만 새 의미 후보로 승인하지 않는다. 실행기는 로컬 Job의 종료를 확인한 뒤 예약을 반환한다. 현재 구현이 관찰하지 못한 원격 종료와 공급자 내부 호출은 `unknown` 범위로 남는다.

정지 판단은 실행기의 주 루프가 한다. 정지 사유가 되는 변경은 모두 상태 게시를 거치며, 실행기는 게시 직후와 기한·허가 만료·대화 lease 만료 같은 시각이 지났을 때 실행 중인 호출의 정지 사유를 평가해 호출별 정지 신호를 세운다. 모델·Lean·환경 계산은 그 신호만 읽으므로, 정지 요청부터 계산 중단까지는 주 루프 한 바퀴와 그 계산의 신호 확인 간격(모델 실행 약 0.2초, Lean 대기 약 0.02초)의 합을 넘지 않는다. 모델 실행의 관찰 묶음은 기다리지 않고 쌓이며, 실행기는 한 실행의 관찰을 순서대로 모두 적용한 뒤 그 실행의 결과를 회수한다. 관찰을 적용하지 못하면 그 오류를 정지 사유로 기록하고 해당 실행만 멈춘다.

```powershell
python .agents/skills/do-math/scripts/do_math.py check `
  --repository .skill-workspace/my-math/repo `
  --instance RI-...

python .agents/skills/do-math/scripts/do_math.py resume `
  --repository .skill-workspace/my-math/repo `
  --instance RI-... `
  --reason "검사 결과와 남은 범위를 확인했습니다."
```

`resume`은 `closed`와 `completed` 상태를 다시 열지 않는다. 거부된 출력이나 진단에서 대기로 남긴 실패 행동과 `input_overflow`를 일반 재개로 실행 대기열에 되살리지 않는다. 먼저 원인을 고치고 운영 점검의 재시도, `request --retry-action`, 또는 현재 입력의 새 역할 요청으로 이어 간다. 새 실행은 필요한 결과·체크포인트를 재사용하되 과거의 잘못된 판정을 현재 상태로 복사하지 않는다.

`close`는 queue를 비우고 인스턴스를 종결한다. 진행 중 실행의 회수 기록은 남길 수 있지만 새 연구를 시작하지 않는다.

### 독립 운영의 설정과 정지

`operator status`는 실제 예약 작업을 조회한다. `operator install`은 현재 인스턴스 설정으로 정상 감독·연구 엔진 작업을 다시 맞추고 `operator uninstall`은 그 인스턴스의 연구·정기 감독·일회성 wake 예약을 제거한다. 독립 운영의 활성 여부·주기·기한은 `configure`의 `operator_enabled`, `operator_interval_seconds`, `operator_timeout_seconds`로 바꾼다. 실패 시 설치 복구 AI에는 `operator_effort`, `tier_models`와 `role_tiers.recovery`가 적용된다. 이 값들은 `configure`가 새로 만드는 복구 프로필에 들어가므로 바꿔도 예약을 다시 맞출 필요가 없다. 정상 감독에는 모델 배정이 없다. 예약 작업의 주기와 기한은 예약을 설치할 때 현재 설정에서 읽어 등록하며, 다른 예약 동작은 이 값을 다시 읽지 않는다. 활성 여부·주기·기한의 변경이 즉시 적용되면 CLI가 예약에 반영한다. 제어가 아직 대기 중이면 운전자는 적용을 확인한 뒤 같은 인스턴스에서 `operator install`로 예약을 재조정한다. 비활성화나 예약 제거가 이미 실행 중인 연구까지 정지했다는 뜻은 아니다.

연구 예약의 Windows 실행 제한은 무제한을 뜻하는 `PT0S`다. 운영 담당 예약에는 `operator_timeout_seconds`에 종료 여유를 더한 유한 제한을 적용한다. 여유의 크기는 [CLI 실행 계약](references/CLI-실행-계약.md#config-list)의 독립 운영 설정 설명을 따른다. 기존 설치를 갱신할 때는 같은 인스턴스에서 `operator install`을 사용하고 `operator status`의 `execution_limit`을 확인한다. 재설치는 기존 예약의 Disabled 상태를 보존하며 HOLD나 사용자 정지를 해제하지 않는다.

사용자가 연구와 자동 운영을 함께 멈출 때는 `operator hold`를 쓴다. 이 명령은 고유 ID의 HOLD를 만들고 사용자 정지를 요청한다. `operator release`는 그 HOLD를 해제하며, 현재 사용자 정지가 정확히 같은 HOLD에서 왔을 때만 재개한다. 이후의 다른 사용자 정지는 그대로 유지한다.

독립 운영 경로가 보내는 자동 제어는 `--origin operator`로 표시한다. 이 경로는 사용자 정지를 해제하거나 목표·정책·학술 요구·외부 행동·신뢰 판정을 만들지 못한다. 사용자 제어의 기본 출처는 `user`다. 출처 구별과 복구 지시는 같은 사용자 OS 권한 안의 실행 계약이며 인증된 호출자 경계나 보안 격리 장치가 아니다.

설치 감독을 읽기 전용으로 시험하려면 `operator probe`를 사용한다. 이 명령은 상태·기록을 모델 없이 읽고 연구나 예약 상태를 변경하지 않으며, 엔진 읽기 실패가 있어도 복구 AI를 시작하지 않고 실패 증거만 반환한다. 정상 `operator check`는 같은 감독 뒤 실행 가능한 엔진 작업을 요청할 수 있고, 엔진 시작 실패의 실제 증거나 수락된 설치 결함 진단이 있을 때 복구 AI를 연다.

예약 작업이 실행하는 bootstrap은 예약 어댑터 `scripts/operator_schedule.ps1` 옆의 `operator_bootstrap.py`를 설치 시점의 파일 manifest와 해시에 고정한 복사본이다. bootstrap은 재분석 지점·파일 해시와 경로를 검사하고, 실행 중인 live 설치와 구별된다. 첫 검사는 전 파일을 해시하고 정착한 파일 지문을 manifest 옆에 기록한다. 이후 기동에서는 지문이 바뀐 파일만 다시 해시한다. 복구 AI는 writer lock과 별도 설치 유지보수 lock, 종료된 선행 실행, 고정 복구 프로필과 현재 능력 증거, 공급자 대기와 설정된 호스트 자원의 착수 조건을 모두 확인한 뒤 live 설치만 수리할 수 있다. 연구 기록·사용자 전역 설정·예약 작업·사용자 결정을 고치지 않는다. 두 lock은 복구 호출이 끝나면 결과와 관계없이 놓는다. 엔진 재시작은 수리 뒤 설치본의 `probe_cli.py --skill-only`가 통과하고 복구 AI의 로컬 종료를 확인한 경우에만 요청한다. 종료를 확인하지 못한 복구 실행이 끝날 때까지 연구 실행기는 새 연구를 배정하지 않는다. 이는 지시 기반 경계이며 다른 사용자 권한·파일·네트워크·자격 증명 접근을 OS가 차단한다는 뜻이 아니다. 실행별 근거와 결과는 `<workspace>/operator/` 아래에 보존되며 이 대화로 자동 알림이 전송되지는 않는다.

## 운영 제어 명령의 용도

| 명령 | 사용할 때 | 중요한 경계 |
|---|---|---|
| `configure --config-file` | 모델 대응·역할 등급·세션 한도, 시간, 검토·관찰·산출 한도를 바꿀 때 | 목표·정책·학술 요구·외부 허가는 설정이 아니다 |
| `request --role ...` | 지원하는 후보 준비·연구 계획·보충 조사·운영 점검·유지보수 action을 명시적으로 열 때 | 요청 생성은 모델 실행이나 결과 승인이 아니다 |
| `request --retry-action AC-...` | 수리 뒤 입력 초과를 다시 포장하거나, 기술적 실패로 끝난 초기 원입력의 의도 해석을 다시 시도할 때 | 같은 action·활동과 원 실패를 보존하며, 해소 선언이나 새 승인·범위 변경을 만들지 않는다 |
| `knowledge --file` | candidate·종류 정의·관계를 수입하거나 기존 지식을 개정·무효화할 때 | candidate 수입은 K 편입이 아니다 |
| `trust --file` | 신뢰 환경을 등록·전환·무효화할 때 | 전환 성공은 무관한 의미·의존 정지 원인을 해소하지 않는다 |
| `external --file` | grant에 결박된 HTTP 행동을 준비하거나 unknown을 대조하고 알려진 실패를 재시도할 때 | `confirmed`와 HTTP 성공 여부는 별도다 |
| `conversation --file` | 대화 연결 세대·lease·소실 정책을 기록할 때 | 대화 연결은 실행 권한이 아니다 |
| `check` | 저장·참조·상태 불변식과 보존 artifact 해시를 검사할 때 | 자연어 의미와 수학적 타당성을 새로 판정하지 않는다 |

구조화 JSON의 전체 형식과 예시는 CLI 실행 계약을 따른다.

## 현재 지원 범위

현행 구현은 인스턴스별 Git ref와 writer lock, 기록군 저장, 활동·다중 실행 수명, 불변 프로필, 구조화 작업 의무·처분, 편입 묶음, 독립 동일성 검토의 범위 계획과 자기 점검 규칙을 정의한다. 각 명령과 역할의 성공은 그 소비자가 실제로 검사·적용한 범위에만 효력이 있다. 스키마 적합, 로컬 생산자 검사, 중앙 미리보기, 제출 의도 접수, 저장 적용, 형식 검사와 독립 의미 판정은 서로 다른 증거다.

새 인스턴스의 AI 예산은 작업 역할 실행이 모델별 작업 슬롯을 점유하는 로컬 동시 점유로 계산하며, 운영 역할은 슬롯 없이 배정된다. Codex의 turn usage와 Claude의 최종 result usage는 보존하지만 공급자 내부 호출별 ID·예약·원격 종료를 보증하지 않는다. 현재 기본 Windows 실행은 Codex의 `danger-full-access`·승인 정책 `never`, Claude의 `bypassPermissions`로 기존 사용자 권한을 쓴다. Windows Job은 로컬 프로세스 수명과 자손 종료를 관리하지만 모든 host 파일·network·credential 접근을 차단하지 않는다. 별도 세션·작업 공간과 동료 결과 비제공은 입력 경계를 만들지만 통계적 독립성이나 강한 OS 격리의 증거가 아니다.

## 저장 계약과 결과의 시각을 확인한다

저장소는 세분된 기록군과 사건을 권위 있는 Git 상태로 공개한다. 구현·저장 계약을 바꾸면 현행 계약으로 새 인스턴스를 초기화한다. 필요한 과거 산출은 정확한 출처·실제 확인 범위를 가진 새 입력으로 제공한다. 이전 runtime·queue·승인·질문을 변환해 재개하거나 옛 거부를 소급 수락하지 않으며, 설치본 수리로 기존 HOLD를 해제하지 않는다.

`status --json`은 한 Git snapshot에서 과제 단계, 선택된 미시작 요청, 저장된 실행·예약, 마지막 수락 결과, 미해소 의무와 대기 이유를 함께 재구성한다. 슬롯 예산·`provider_waits`처럼 조회 순간에 관측하는 필드는 그 snapshot 위에 덧붙인 현재 관측이다. snapshot은 저장된 원장 상태를 일관되게 보여 주지만 조회 순간의 호스트 프로세스나 공급자의 현재 상태를 원자적으로 관찰한 값은 아니다. 실제 프로세스·예약 작업·별도 운영 로그를 함께 볼 때에는 각 관측 시각과 범위를 구별한다. 열린 사용자 질문은 `questions`, 출처·소유·대상·해소는 `question_links`, 실패 의무는 `waiting_actions`에서 확인한다.

고정 snapshot의 실행 시각과 계보는 다음 명령으로 내보낸다. JSON은 원시 UTC와 현지 날짜·UTC offset을 함께 보존하고 CSV도 같은 실행 행을 사용한다. 과거에 기록하지 않은 시각은 null 또는 빈 셀이다.

```powershell
python .agents/skills/do-math/scripts/do_math.py timeline --repository <repo> --instance <RI-ID> --snapshot <OID> --format json --timezone Asia/Seoul
```

`--include-operations`는 작업 공간 `operations/`의 로컬 운영 단계 기록도 별도 집계 단위로 포함한다. 각 행에는 원 파일의 해시와 관측 시각이 붙으며 그 내용이 해당 연구 snapshot에 포함됐다는 뜻은 아니다. 겹친 실행 시간의 합계를 실제 경과 시간으로 사용하지 않는다. 운영 계측의 범위는 [초기화 효율과 정비](references/초기화-효율과-정비.md)를 따른다.

# 초기화에서 연구 활성화까지

현행 검사·저장·정비 경계는 [초기화 효율과 정비](초기화-효율과-정비.md)에 정의한다. 등록은 머신이 공유하는 툴체인 기록을 인스턴스에 결박하고, 전환 뒤 `trust_activate`가 현재 판본 식별과 지문을 그 기록과 대조해 활성화한다. 이 차이를 등록 성공과 환경 활성화 성공의 보고에 반영한다. 큰 payload의 원문을 읽을 때에는 물리 파일의 `payloads` 참조와 논리 레코드를 구별한다.

이 문서는 사람 운영자가 인스턴스의 원입력·승인·프로필·신뢰 환경을 공개 CLI로 연결하는 절차다. `init` 성공은 입력을 보존한 상태이며 연구 시작의 승인이 아니다. 아래 JSON은 요청 형식을 보여 주는 예시다. 목표·정책·허가 범위·만료 시각·환경과 증거는 실제 사용자가 정하거나 실제 측정에서 얻어야 한다. 예시를 문서에서 읽었다는 사실은 승인이 아니다.

이 절차는 README의 [초기화 완료 단계](../README.md#activate-instance)에서 이어진다. 선행 읽기는 SKILL.md의 [사용자 대화 진입 절차](../SKILL.md#이-문서를-읽는-실행의-역할)를 따른다.

아래 명령은 저장소 루트에서 실행한다. `$dmRepository`와 `$dmInstance`를 실제 값으로 정하고 현재 디렉터리는 바꾸지 않는다. `--file`은 UTF-8 JSON 객체 하나를 읽는다. 요청마다 반환의 `effect`를 확인한다. `accepted=true`만 있고 처리가 대기 중이면 해당 요청이 적용될 때까지 다음 의존 단계를 진행하지 않는다.

```powershell
$dmCli = '.agents/skills/do-math/scripts/do_math.py'
$dmRepository = '.skill-workspace/my-math/repo'
$dmInstance = 'RI-실제-init-응답-ID'
python $dmCli status --repository $dmRepository --instance $dmInstance --json
```

## 1. 보존된 입력과 설정을 확인한다

README의 `init`으로 생성한 ID와 첫 snapshot을 사용한다. `query --files`로 등록된 경로를 찾고 `read --path`로 정확한 snapshot을 읽을 수 있다. 연구 저장 파일은 직접 고치지 않는다.

```powershell
python $dmCli query --repository $dmRepository --instance $dmInstance --files --prefix research/ --limit 1000
python $dmCli query --repository $dmRepository --instance $dmInstance --files --prefix runtime/ --limit 1000
```

CLI의 JSON 조회 결과는 최상위 `result` 안에 있다. 그 안의 `next_cursor`가 있으면 같은 조건에 `--cursor`를 추가해 다음 쪽도 읽는다. 각 조회의 `result.snapshot`을 후속 `--snapshot`에 지정하면 같은 판본을 대조할 수 있다. 경로 조회의 실제 `result.items[].path`를 복사해 다음처럼 읽는다. <!-- do-math fields: result=query_result -->

```powershell
python $dmCli read --repository $dmRepository --instance $dmInstance --snapshot '<조회 snapshot>' --path '<조회한 lifecycle 또는 config 파일 경로>'
```

원입력은 `lifecycle.immutable_input`의 `text`, `sha256`, `bytes`에 하나의 정확한 표현으로 보존된다. 모델 상한·새 연구·절차 요구도 원문의 일부다. 목표 문장보다 요청이 넓으면 생성 때 `--request-text-file`로 전체 원문을 별도로 넣는다. `text`는 사용자가 준 문자열의 코드 포인트열이고, 해시와 크기는 그 문자열의 UTF-8 바이트에 대해 계산한다. 이름과 원문을 NFC로 바꾸거나 Base64 원문을 별도로 만들지 않는다. 이 세 필드는 바이트 보존을 증명하지만, 해석·검토·승인이 그 원문을 실제로 사용했다는 뜻은 아니므로 뒤 단계의 `user_request.text`와 소비 근거를 별도로 대조한다.

설정 변경이 실제로 필요하면 승인된 변경만 `configure --config-file`로 적용한다. 그대로 쓸 기본값은 뒤의 채택 요청에서 현행 설정으로 결박한다. 이미 사용자에게 채택받은 값을 다시 새로운 의미 승인 대상으로 만들 필요는 없다. 위임 범위에서 운영자가 선택한 초 단위 관찰값과 허가 기간은 원요청의 근거와 선택 이유를 운영 기록에 남긴다. 그 선택을 사용자가 직접 지정한 값이라고 표현하지 않는다. 예시의 만료일이나 수치를 승인 근거 없이 그대로 복사하지 않는다. 모델·effort·용량·관찰 window가 바뀌면 새 프로필 판본과 새 설정 해시가 생기므로 4단계의 probe와 채택을 새 해시로 다시 한다.

능력 관측·채택 전에 `tool_review_window_seconds`와 `self_check_response_window_seconds`가 설정에 있는지 확인한다. 두 값에는 제품 기본값이 없다. 빠져 있으면 해당 연구에서 사용할 양의 초 값을 확정하고, 두 키와 확정한 값을 담은 JSON 객체를 `observation-settings.json`으로 저장한다. 이미 승인된 값이 있으면 그 값을 재사용한다. 주기·사건 관찰의 `observation_interval_seconds`도 유효해야 한다. 이 단계는 프로필의 관찰 설정을 준비하는 단계이며, 아직 생성되지 않은 과제의 개별 관찰 규칙을 요구하지 않는다.

도구 검토 창은 대표 검사의 소요 시간보다 넉넉히 둔다. 한 도구 호출이 이 창보다 오래 돌면 운영 점검이 열리므로, 컴파일 한 번보다 짧은 창은 작업자가 막을 수 없는 운영 점검을 연다. 자기 점검 응답 창은 컴파일 시간에 묶이지 않는다. 연구 도구 호출이 도는 동안에는 응답 기한이 멈추기 때문이다(「자기 점검」). 소요 시간은 5절의 `setup_lean.py --verify-only` 출력의 `representative_check_seconds`다. 같은 판본의 기록이 이미 있으면 이 명령은 다시 컴파일하지 않고 기록된 값을 보여 주므로, 값을 정하기 전에 `--trust-file` 없이 실행해 확인할 수 있다. 첫 컴파일은 캐시가 데워진 뒤보다 훨씬 오래 걸릴 수 있으며, 기록된 값은 그 기준 항목을 만들 때의 한 번이다. 채택과 등록의 결과는 도구 검토 창이 이 값보다 짧으면 `observation_window_warnings`로 알린다. 경고는 채택이나 등록을 막지 않으므로, 경고를 받으면 창을 늘릴지 판단하고 늘리면 설정을 보충한 뒤 4단계의 probe부터 새 설정 해시로 다시 진행한다.

```powershell
python $dmCli configure --repository $dmRepository --instance $dmInstance --config-file observation-settings.json
```

적용 응답을 확인한 뒤 4단계에서 `status`가 보고하는 현재 설정의 해시(`config_sha256`)로 `operation=probe`를 보내 현행 프로필의 능력을 관측하고, 같은 해시를 실은 채택 요청으로 현행 설정과 그 설정의 역할별 현행 프로필을 함께 채택한다. 누락된 관찰 설정은 역할·프로필 ID·필드로 표시되며 채택 또는 활성화를 막는다. 이 경우 같은 인스턴스에서 설정을 보충하고, 바뀐 해시로 probe부터 다시 진행한다. 원입력과 과거 프로필은 보존되며 이미 유효한 사용자 승인·권한을 새로 만들지 않는다.

## 3. 초기화 권한과 연구 권한을 나눈다

초기화 grant는 `intent_interpretation`·`maintenance` 안의 역할 범위, 명시적 만료와 `reuse="reusable"`을 요구한다. 두 역할은 운영 역할이므로 작업 슬롯을 예약하지 않으며, grant에 예산 종류를 적는 필드는 없다. 연구 grant는 다른 ID를 사용한다. 초기화 grant의 ID를 연구 grant로 다시 채택하지 않는다.

다음 만료 시각은 형식 예시다. 실제 허가 기간으로 바꾸고, 역할 목록과 재사용 범위를 사용자가 승인한 대로 정한다. `task_ids=[]`는 열거한 역할의 모든 과제를 허용하므로 특정 과제로 제한할 때에는 실제 과제 ID를 넣는다. HTTP 등 외부 효과는 별도 grant가 필요하다.

`02-initial-grant.json`:

```json
{
  "kind": "grant",
  "grant": {
    "id": "GR-initial-01",
    "kind": "local",
    "roles": ["intent_interpretation", "maintenance"],
    "task_ids": [],
    "reuse": "reusable",
    "expires_at": "<허가 범위에 맞게 확정한 UTC 만료 시각>"
  }
}
```

`03-research-grant.json`:

```json
{
  "kind": "grant",
  "grant": {
    "id": "GR-research-01",
    "kind": "local",
    "roles": ["research_preparation", "research_plan", "research_work", "supplemental_research", "task_contract_review", "formal_check", "identity_review", "goal_audit", "operational_review", "intent_interpretation", "maintenance"],
    "task_ids": [],
    "reuse": "reusable",
    "expires_at": "<허가 범위에 맞게 확정한 UTC 만료 시각>"
```

```powershell
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 02-initial-grant.json
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 03-research-grant.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind grant --limit 1000
```

초기화 중 grant를 등록하는 일은 연구 계획이나 연구 과제를 열지 않는다. 이 단계에서는 이후 활성화에 사용할 서로 다른 초기화·연구 허가를 보존하고 채택할 뿐이다. 최초 후보 준비 또는 연구 계획은 원입력 해석·독립 검사·신뢰 환경·프로필 능력·복구를 포함한 활성화 관문 전건이 통과해 lifecycle이 `active`가 될 때 열린다. 활성화 뒤 grant가 추가·교체되면 그 사용자 결정의 `decision_id`가 재계획 사유가 된다. 새 `grant_id`는 이후 실행을 허가할 수 있는 권한 참조이지 계획을 연 근거 ID가 아니다.

## 4. 현행 프로필의 능력을 관측하고 채택한다

실행기는 설정이 바뀔 때마다 모든 역할의 실행 프로필 판본을 새로 만들고, 그 참조를 역할별 현행 목록 `research/role_profile_refs/state.json`에 둔다. 활성화 뒤의 배정은 이 목록에서 역할 하한과 과제 평가에 맞는 판본 하나를 고르고, 고른 판본의 현재 능력 증거를 요구한다. 그래서 채택은 프로필을 하나씩 고르는 절차가 아니다. 채택 요청이 현행 설정을 결박하면, 그 설정으로 만든 역할별 현행 프로필 전건도 함께 채택된다. 활성화 관문은 이 전건의 관찰 설정과, AI 프로필마다의 현재 능력 증거를 확인한다. 등록부에 남은 과거 판본은 이미 고정된 과제·실행의 근거로 보존될 뿐 채택 대상이 아니다. 과제에 이미 고정된 프로필은 설정 변경만으로 교체되지 않으며, 새 프로필을 쓰려면 해당 과제를 재준비하고 독립 계약 검토를 받아야 한다.

probe와 채택은 대상 설정을 `config_sha256`으로 지정한다. 이 값은 `status` 결과의 `result.config_sha256`, 곧 현재 설정의 내용 해시다. 실행기는 요청의 값이 현재 설정의 해시와 다르면 요청을 거부한다. 그래서 운영자가 확인한 설정과 다른 설정의 프로필이 관측되거나 채택되지 않는다. 설정을 바꾸면 해시도 바뀌므로, 설정을 보충한 뒤 다시 보내는 probe와 채택은 앞의 요청을 재생하지 않고 새 요청으로 적용된다. 설정은 같은데 CLI나 어댑터가 바뀌어 능력을 다시 관측할 때처럼, 같은 내용의 probe를 새로 적용하려면 새 `--idempotency-key`를 붙인다. <!-- do-math fields: result=status -->

먼저 현재 설정의 해시를 읽고 능력을 관측한다. `profile_ref`나 `profile_refs`를 생략한 probe는 그 설정의 역할별 현행 AI 프로필 전건을 관측한다. 과제에 고정된 과거 판본처럼 현행 목록 밖에 있는 프로필의 증거가 필요하면, 그 참조를 `profile_refs`에 명시해 관측한다. 프로필 참조는 등록된 기록 본문의 `id`, `revision`, `sha256` 세 값을 그대로 묶은 객체다.

```powershell
$dmStatus = python $dmCli status --repository $dmRepository --instance $dmInstance --json | ConvertFrom-Json
if ($LASTEXITCODE -ne 0 -or $null -eq $dmStatus.result.config_sha256) { throw '상태 조회 실패: CLI 종료 상태와 반환 본문을 확인한다.' }
$dmConfigSha256 = $dmStatus.result.config_sha256
$dmProbeJson = @{kind='initialization'; operation='probe'; config_sha256=$dmConfigSha256} | ConvertTo-Json -Depth 10
[System.IO.File]::WriteAllText((Join-Path $PWD '04-probe.json'), $dmProbeJson, [System.Text.UTF8Encoding]::new($false))
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 04-probe.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind capability_evidence --limit 1000
```

`probe` 호출은 관측하는 프로필의 어댑터 `describe()`를 공급자마다 한 번 실제로 실행하고, 그 결과로 프로필마다 능력 증거를 만든다. 프로필·호스트·CLI 판본과 관측 시각에 결박된 증거이며, 능력 식별은 `{cli_path, cli_sha256, module_sha256, host}` 모양이다. `module_sha256`은 어댑터가 지정한 식별 모듈마다 그 파일의 해시를 담는다. Codex 어댑터의 식별 모듈은 `cli_worker`, `codex_worker`, `control_transport`, `file_io`, `windows_job`, `scholarly`, `codex_adapter`이고, Claude 어댑터는 여기에 `claude_worker`, `claude_adapter`, `claude_stream`을 더한다. 이 모듈 가운데 하나라도 바뀌면 기존 능력 증거는 현재 증거로 쓰이지 않는다. 증거는 `supported/unsupported/unknown`의 범위를 그대로 읽는다. 정적 `profile` 명령이나 시험용 fake CLI의 통과를 모든 실행 능력의 증거로 바꾸지 않는다. 실제 시작 실패의 증거는 단순 help/version 재관측으로 지워지지 않는다.

다음은 채택 요청의 예시다. 이 예시는 초기화 뒤 실행기가 대화와 독립적으로 승인된 연구를 계속하고, 외부 효과는 허용하지 않는 운전이다. `conversation_loss_policy='continue_authorized'`에서는 대화의 attach·heartbeat가 연구의 선행조건이 아니다. 사용자 정지·HOLD·허가 만료와 철회는 계속 적용된다. `external_policy`는 실제 허가에 맞추며, `adopt_default_review_policy`는 현재 `config.reviewers`와 `config.review_rounds`로 기본 검토 방침을 생성·채택하고 실제 내용 해시를 저장한다. 명시적인 `review_policy`를 함께 제공하면 그 객체를 사용한다. `config_sha256`에는 probe에 쓴 값을 그대로 쓴다. 그 사이에 설정이 바뀌었으면 채택은 거부되므로, 새 해시로 probe부터 다시 진행한다.

```powershell
$dmAdoptJson = @{
  kind='initialization'; operation='adopt'
  config_sha256=$dmConfigSha256; adopt_current_governance=$true
  conversation_loss_policy='continue_authorized'; external_policy='disabled'
  adopt_default_review_policy=$true
  initial_grant_ids=@('GR-initial-01'); research_grant_ids=@('GR-research-01')
} | ConvertTo-Json -Depth 10
[System.IO.File]::WriteAllText((Join-Path $PWD '05-adopt.json'), $dmAdoptJson, [System.Text.UTF8Encoding]::new($false))
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 05-adopt.json
python $dmCli select-profile --repository $dmRepository --instance $dmInstance --role intent_interpretation
```

역할별 현행 프로필 가운데 관찰 설정이 빠진 것이 있으면, 채택은 역할·프로필 ID·필드와 함께 거부된다. 채택은 `profile_refs`를 받지 않는다. `initial_profile_ref`를 생략하면 실행기가 실제 배정과 같은 선택 규칙으로 초기 해석 프로필을 정한다. 위의 `select-profile` 조회는 그 선택(`result.selection.profile_ref`)과 프로필 원문을, 실행이나 채택 없이 보여 준다. 과제에 쓸 프로필은 `--task TK-...`를 더해 같은 규칙으로 확인한다. 채택 뒤에 설정을 바꾸면 새 판본과 새 해시가 생기므로 probe와 채택을 새 해시로 다시 한다. <!-- do-math fields: result=selection_result -->

## 5. 툴체인 기록을 등록한다

`setup_lean.py --verify-only --trust-file <새 경로>`는 설치된 환경의 툴체인 기록을 만들거나 확인하고, 그 기록의 현재 기준으로 등록 요청을 새 파일에 쓴다. Lean이 없으면 먼저 인자 없는 `setup_lean.py`로 설치한다. 설치에도 `--trust-file`을 줄 수 있다. 준비 표지나 `--inspect-only`의 판본 식별만으로 등록 요청을 만들지 않는다.

```powershell
$dmTrustFile = '.skill-workspace/my-math/06-trust-register.json'
$dmRecorded = python .agents/skills/do-math/scripts/setup_lean.py --verify-only --trust-file $dmTrustFile | ConvertFrom-Json
if ($LASTEXITCODE -ne 0 -or $dmRecorded.status -ne 'recorded') { throw '툴체인 기록 실패: 출력의 status와 reason을 확인한다.' }
python $dmCli trust --repository $dmRepository --instance $dmInstance --file $dmTrustFile
```

같은 판본의 기록이 이미 있고 현재 지문이 그 기록의 현재 기준과 같으면, `setup_lean.py`는 새로 컴파일하지 않고 그 기록을 다시 사용한다. 어느 경우든 출력의 `representative_check_seconds`는 현재 기준 항목의 대표 검사가 걸린 시간을 초 단위로 올림한 값이다. 기록이 없으면 판정 파일 전건의 지문과 내용 해시를 계산한다. 그다음 구성된 명령으로 `import Mathlib`, 자연수 덧셈의 항등원, 실수 `norm_num` 예제를 소유된 Windows Job에서 컴파일한다. 임의의 시간 상한으로 컴파일을 자르지 않으며, 진행은 증거 디렉터리의 `operations/live/`에서 볼 수 있다. 컴파일이 실패하면 기록을 만들지 않고 `status=failed`, 종료 코드 1로 끝난다. `--command-file`로 프로젝트 없는 Lean 명령을 지정하면 자연수 항등원과 `True`의 core 예제를 검사한다.

`status=rerecord_required`는 판정 파일 전건의 내용 해시가 같은 판본의 기존 기록과 같은데도 그 기록을 다시 사용할 수 없는 상태다. 원인은 둘 중 하나다. 파일 메타데이터가 그 기록의 마지막 기준 항목(현재 기준)과 달라졌거나, 현재 기준에 대한 전수 점검이 `mismatch`를 남긴 뒤 파일을 복구해 내용이 다시 같아졌다. 설치 명령은 기존 기록에 기준을 덧붙이지 않는다. 사용자나 운전자가 [초기화 효율과 정비](초기화-효율과-정비.md)의 `지문 불일치와 재기록`에 따라 `--rerecord` 여부를 정한다.

등록 요청은 `operation`, `toolchain`, `allowed_axioms`, `toolchain_record`, `binding` 다섯 필드만 갖는다. `toolchain`은 툴체인 기록의 판본 식별과 같은 객체다. `toolchain_record`는 기록 파일의 절대 경로와 기록 ID이고, `binding`은 결박할 기준 항목의 번호와 그 항목의 지문 다이제스트, 내용 해시 다이제스트, 대표 검사 요약 해시다. `allowed_axioms`는 `propext`, `Classical.choice`, `Quot.sound`다. 생성 경로는 새 파일이어야 하며 요청을 손으로 조립하지 않는다.

등록은 툴체인 기록 파일을 읽는다. 기록의 ID와 판본 식별이 요청과 같고, 요청이 결박한 기준 항목의 다이제스트가 기록의 해당 항목과 같으며, 현재 기준의 대표 검사가 성공했고 현재 기준에 대해 `mismatch`로 끝난 전수 점검 결과가 없을 때만 등록한다. 설치 파일은 읽지 않는다. Lake가 구성한 검색 경로 `toolchain.project.search_paths`가 Lean 설치와 Lake 프로젝트 밖에 있으면 등록을 거부한다. Lake 프로젝트를 쓰지 않는 명령의 `toolchain.project`는 `null`이다. Lean 관련 검색 경로 환경 변수는 호스트에서 상속하지 않는다.

대표 검사의 source·명령·출력·종료 코드·시각은 툴체인 기록에 있고, 인스턴스는 그 요약 해시를 결박한다. 인스턴스의 환경 기록과 등록 요청에는 설치 파일 목록이 들어가지 않는다. 한 머신의 여러 인스턴스는 같은 툴체인 기록을 함께 등록할 수 있으며, 등록할 때 지문이나 내용 해시를 다시 계산하지 않는다.

등록 성공은 비활성 후보 보존이다. 다음 조회로 실제 ID를 얻어 전환 요청에 넣는다.

```powershell
python $dmCli query --repository $dmRepository --instance $dmInstance --kind trust-environment --limit 1000
```

`07-trust-transition.json`:

```json
{"operation":"transition","env_id":"TE-실제-조회-ID"}
```

```powershell

python $dmCli status --repository $dmRepository --instance $dmInstance --json
```

활성화 기계 작업은 툴체인 기록을 다시 읽고, 현재 판본 식별과 판정 파일의 지문을 결박한 기준과 대조한다. 지문이 다르거나 기록이 불일치 점검을 담고 있으면 활성화하지 않는다. 처리는 [초기화 효율과 정비](초기화-효율과-정비.md)의 `지문 불일치와 재기록`을 따른다. 초기 원문 해석과 독립 검사는 현재 초기 권한 안에서 이 환경 준비와 독립적으로 진행할 수 있다.

`--until-active`는 초기화 관문이 모두 충족되면 연구 역할을 새로 배정하기 전에 반환한다. 관문이나 사용자 입력이 부족하면 status의 `operating_summary.primary_blocker`와 lifecycle을 확인하고 그 입력을 보충한다. 원입력 해석·검사의 완료와 실제 적용은 다음 절에서 확인한다. 대표 환경 예제의 통과는 전체 라이브러리 재증명이나 연구 목표 해결이 아니다.

## 6. 최초 해석·독립 검사·실제 적용을 확인한다

초기 원입력의 해석·독립 검사가 기술적 실행 실패, 제출 처리 실패 또는 실행기 소실로 끝나면 실패 실행과 원입력을 보존하고 유지보수 진단을 요청한다. 진단은 현재 초기화 권한이 허용할 때만 실행된다. `retry` 판정을 낸 유지보수 실행이 종료되고 그 판정이 수락되면 중앙은 같은 원입력·활동의 후속을 한 번 처리한다. 필요한 권한이나 자료가 없으면 그 부족과 다음 담당자를 남기고 기다린다.

운전자가 원인을 해소한 뒤에는 보류된 action ID를 `request --retry-action AC-... --request-id UC-...`에 지정해 명시적으로 재시도할 수도 있다. 실행기는 자동 진단 후속과 공개 재시도 모두에서 전 실행의 로컬 종료·예약 회수, 원입력·활동 계보, 현재 초기 운영 권한·채택 프로필을 확인한다. 일반 `resume`은 이 실패를 재시도하지 않는다. 정상 종료한 native 최종 응답이 정확한 원문·실행 근거와 함께 보존돼 있으면 그 응답을 중앙 접수·편입에 재사용한다. 이 경우 새 모델 실행을 만들지 않으며 원 실행의 종료 시각·원 결과 참조·실패 이력을 보존한다. 재사용 조건을 충족하는 정상 응답이 없으면 같은 활동을 잇는 새 실행을 배정한다. 기존 봉인 후보를 다른 final로 대체하거나 오류·중단 응답을 정상 응답으로 취급하지 않는다. 새 입력으로 원문을 대체하거나 인스턴스를 다시 만들 필요는 없다.

초기 프로필과 운영 grant가 채택되고 능력 관문을 통과하면 초기 원입력의 `intent_interpretation`이 열린다. `run`이 해석과 별도 검사 실행을 처리한다. 의도 해석 AI는 원문 범위를 `import_units`에 전건 배정하며 각 단위의 payload를 해당 종류의 저장·적용 영역에 연결한다. 이 영역을 payload의 소유자라고 부르며, 헌장·권한·설정 등 각 종류의 적용을 담당한다. 질문이 남아 있어도 확인 가능한 범위의 독립 검사는 생략하지 않는다.

차단 질문이 남은 해석은 그 질문의 답변을 기다리며 같은 원문으로 반복 실행하지 않는다. 답변이 검사·승인·적용되어 해당 차단 질문이 모두 해소되면, 원문과 해석 계보를 유지한 재해석에서 답변을 반영한다.

정상 종료한 최종 응답의 JSON·출력 형식 오류는 원문과 중앙 검사 결과를 보존해 같은 의도 해석 역할의 제한된 수리로 연결한다. 수리가 한도에 이르면 초기화 권한이 허용하는 유지보수가 원 실패를 진단한다. 유지보수의 `retry` 판정은 같은 의무에 한 번의 후속 수리를 열고, `wait` 또는 후속 수리의 재실패는 원인과 소유자를 보존해 기다린다. 새 권한을 만들거나 초기화에서 허용하지 않는 운영 점검 역할을 실행하지 않는다. 응답을 정상 접수한 사실만으로 사용자 승인·답변 대기를 해소하지 않는다.

질문에는 `input --text` 또는 `input --file`과 실제 `--responds-to QU-ID`로 답한다. 해당 답의 수입·독립 검사 뒤 해소된 질문만 닫힌다. 답변은 별도의 grant를 자동 생성하지 않는다.

```powershell
python $dmCli input --repository $dmRepository --instance $dmInstance --file actual-answer.txt --responds-to QU-실제-질문-ID
python $dmCli run --repository $dmRepository --instance $dmInstance --until-active
```

독립 검사가 승인해도 사용자 권한이 필요한 payload의 적용은 별도다. 검사된 수입 기록에서 `id`, `sha256`, `check.sha256`, 비어 있지 않은 payload 전건의 `unit_id`와 정규 의미 해시를 확인한다. 이미 승인된 기록과 동일한 의미·권한이면 그 승인 근거를 재사용한다. 새로운 목표·허가를 예시나 모델의 추천으로 승인하지 않는다. <!-- do-math fields: check=import_check -->

현행 공개 CLI는 승인 JSON을 한 번 읽은 payload와 같은 정확한 원문으로 control에 전달한다. `decision`의 `kind=import_approval`은 이 경로에서 `apply_import_control`로 간다. 먼저 같은 snapshot에서 검사된 수입을 조회하고 정확한 record를 읽는다.

```powershell
python $dmCli query --repository $dmRepository --instance $dmInstance --kind intent_imports --limit 1000
python $dmCli read --repository $dmRepository --instance $dmInstance --snapshot OID-위-조회-응답의-snapshot --id IM-실제-조회-ID
```

다음 명령은 조회한 snapshot의 독립 검사와 현재 전제를 확인하고, 수입·검사 해시와 비어 있지 않은 payload 전건의 정규 내용 해시를 담은 승인 초안을 새 파일로 만든다. 해시는 수신기와 같은 정규화 함수로 계산한다. 명령은 승인이나 적용을 하지 않는다. 파일의 제안 내용을 실제 사용자 승인 범위와 대조한 뒤 `decision`에 전달하며, 전달한 정확한 파일 원문이 승인 근거로 보존된다.

```powershell
python $dmCli prepare-import-approval --repository $dmRepository --instance $dmInstance --snapshot OID-위-조회-응답의-snapshot --import-id IM-실제-조회-ID --output 08-import-approval.json
```

생성되는 결정 객체의 형식은 다음과 같다.

```json
{
  "kind": "import_approval",
  "import_id": "IM-실제-조회-ID",
  "bundle_sha256": "검사된-묶음-해시",
  "check_sha256": "검사-해시",
  "unit_hashes": {
    "IU-실제-단위-ID": "그-payload의-canonical-hash"
  }
}
```

```powershell
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 08-import-approval.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind intent_imports --limit 1000
python $dmCli read --repository $dmRepository --instance $dmInstance --snapshot OID-위-조회-응답의-snapshot --id IM-실제-조회-ID
python $dmCli status --repository $dmRepository --instance $dmInstance --json
```

적용기는 사용자 출처, 승인 종류, 수입 묶음·검사·unit 해시의 정확한 일치와 비어 있지 않은 승인 원문을 확인한 뒤 그 봉인 묶음만 적용한다. 적용 뒤 수입 record와 그 안의 검사·적용 결과를 위 조회로 읽는다. 이를 위해 초기 원문 해석이나 독립 검사를 다시 열지 않는다. 반대로 하나라도 달라지거나 원문이 없으면 적용되지 않는다. 해시를 계산하거나 기록에서 회수하는 행위는 사용자 결정이 아니다. 내부 함수를 직접 호출하거나 저장 JSON을 편집해 관문을 우회하지 않는다.

정확한 원문 의미에도 같은 확인이 필요하다. 초기 입력은 `immutable_input.text`의 코드 포인트열과 그 UTF-8 바이트의 해시·크기로 하나만 보존하며 NFC 사본이나 Base64 중복 원문을 만들지 않는다. 이 보존만으로 초기 해석·원문 피복·독립 검사·승인이 그 원문을 실제로 읽었다고 보증할 수는 없다. `user_request.text`로 제공된 값과 각 소비자가 사용한 원문을 대조해, 코드 포인트 차이가 뜻을 바꾸는 입력도 같은 원문에 결박됐는지 확인한다.

완료는 `active_trust_environment`의 존재 하나가 아니라 초기화 관문 전건과 실제 수입 적용 기록으로 판단한다. 미완료 항목은 lifecycle 기록·가용성·대기 요청에서 확인한다. 전건을 통과한 활성화가 lifecycle을 `active`, 실행 상태를 `ready`로 바꾸며, `knowledge` 기록군에 보존된 기록이 하나라도 있으면 최초 연구 계획을, 비어 있으면 최초 후보 준비를 연다. 이 분기는 사용 가능한 K만 세는 조건이 아니다. 기록의 존재는 `query --kind knowledge`로 확인한다. 이 분기는 기록의 검증 통과를 뜻하지 않으며, 수학적 사용 가능성은 해당 기록의 형식 결과·동일성 판정·현재성으로 따로 판단한다. 초기화 중 앞서 등록한 grant 자체는 이 작업을 열지 않는다.

활성화 때까지 보존된 미소비 초기화 사건은 이 최초 역할의 `event_refs`에 함께 배정한다. 후보 준비가 진행 중이라는 이유만으로 같은 초기화 사건을 다시 계획에 배정하지 않는다. 사건은 그 고정 입력을 읽은 응답이 수락될 때만 소비한다. 이후 새 사용자 결정이나 전제 상실은 별도의 사건으로 처리하며 이미 시작한 입력에 덧붙이지 않는다.

일반적인 독립 실행 인계 경로에서는 README의 [초기화 완료 단계](../README.md#activate-instance)에 있는 대화 소실 정책 조건까지 확인하고, [독립 실행 시작과 관측](../README.md#start-engine)으로 돌아간다. 수동 운영으로 정한 인스턴스는 [직접 전진·수동 운전](../README.md#manual-run)으로 이어 간다. 초기화의 `run --until-active`는 기계·의도 해석 작업의 실제 결과를 적용하며 활성화 직후 반환한다. 인계 때 ID·저장소·workspace·모델 제한·관측 시각과 프로세스 근거·감독 주기·지속 정책·grant 만료·남은 의무의 다음 소유자를 함께 보고한다.

## 신뢰 환경 확인의 개요

신뢰 환경 확인은 형식 검사에 쓰는 Lean·Mathlib·검사기가 채택한 판본 그대로이고 채택 뒤 우발적으로 바뀌지 않았음을 보이려고 한다. 우발적 변경은 업데이트, 재설치, 동기화, 실수, 디스크 손상에 따른 변경이다. 같은 사용자 권한을 가진 사람이나 AI가 툴체인이나 do-math 코드를 의도적으로 바꾸는 일은 막지 않는다.

확인은 두 값으로 한다. 두 값과 그 기준을 담는 파일의 정의는 다음과 같으며, 구성의 세부는 아래 「판정 파일, 판본 식별과 지문」과 「툴체인 기록과 인스턴스 결박」이 정한다.

- 판본 식별은 형식 검사가 어떤 Lean 명령·Lake 프로젝트·검사기를 쓰는지 고정하는 값이다. 형식 결과가 어느 환경에서 검사됐는지와, 게시 시점의 설치가 그 환경과 같은지를 이 값으로 판정한다.
- 지문은 커널이 적재하는 `.olean`과 Lean 런타임 라이브러리의 파일마다 (상대 경로, 크기, 수정 시각, 생성 시각)을 모은 메타데이터 목록과 그 다이제스트다. 파일 내용을 읽지 않으므로 싸게 대조할 수 있고, 업데이트·재설치·손상처럼 메타데이터를 바꾸는 우발적 변경을 탐지한다. 세 값을 모두 보존한 내용 변경은 탐지하지 못하며, 그런 변경은 내용 해시 기준과 대조하는 선택적 전수 점검만 찾는다. 프로젝트의 git 트리·diff 해시인 프로젝트 소스 식별과 다른 개념이다.
- 툴체인 기록은 한 머신의 인스턴스들이 함께 쓰는 Lean·Mathlib 설치 하나의 판본 식별과 기준 이력, 점검 이력을 담은 파일이다. 기준 항목은 지문 기준, 판정 파일 전건의 내용 해시 기준과 대표 검사 결과로 이루어진다. `setup_lean.py`만 이 파일을 쓰며, 기준 항목의 추가는 사용자와 운전자만 하는 재기록이다. 인스턴스는 읽기만 한다. 판본이나 판정 바이트가 다른 설치는 다른 기록이다. 인스턴스의 신뢰 환경은 툴체인 기록 하나를 가리키고 그 기록의 기준 항목 하나에 결박된다.

`setup_lean.py`는 설치할 때 기준을 만들고, 인스턴스는 활성화와 형식 검사 직전에 기준을 현재 파일과 대조한다. 파일 내용 전체의 해시는 사용 경로에서 계산하지 않는다. 설치·재기록·요청한 전수 점검 때에만 계산한다.

| 형식 검사 1건, 전환의 기존 K 재검사 | 컴파일 전에 기록 확인과 현재 지문을 대조한다. 이어서 검사기가 구성된 명령, 실행 파일의 해석 경로, 판본 식별 파일을 대조한 뒤 컴파일한다. 컴파일 뒤에는 다시 관측하지 않는다. | 활성화와 같음 |

| 선택적 전수 점검: `setup_lean.py --check-contents` | 현재 기준의 내용 해시와 판정 파일 전건의 대조 | 판정 파일 전건의 내용 |

게시 관문이 지문을 다시 보지 않는 이유는 비용과 효과의 차이다. 지문은 형식 검사 직전에 대조했고, 검사와 게시 사이에 설치가 우연히 바뀌는 일은 드물다. 그런 변경은 다음 형식 검사의 지문 대조에서 드러난다. 판본 식별은 싸므로 게시 때도 확인한다. 게시할 형식 결과의 `toolchain`이 환경의 판본 식별과 같은지는 K 사용 판정(`formal_usable`)이 확인한다. 같은 원문과 판본 식별이 유지되면 동일성 판정의 편입은 기존 형식 검사 결과를 재사용하며 Lean을 다시 실행하지 않는다.

형식 검사는 컴파일 전 확인의 결과를 형식 결과의 `environment_check`에 남긴다. 여기에는 판본 식별 다이제스트, 관측한 지문 다이제스트, 사용한 결박이 들어간다. 이 기록은 추적용이며 게시 판정에는 쓰지 않는다. `status`와 상태 조회는 저장된 기록만 보고하고 설치 파일을 읽지 않는다.

## 지문 불일치와 재기록

현재 지문이 결박한 기준과 다르면 활성화는 환경을 활성화하지 않고, 형식 검사는 컴파일을 시작하지 않는다. 활성화는 전환 실패로 끝나고 이전 환경이 계속 효력을 가진다. 전환의 기존 K 재검사는 실패 결과로 기록되므로 그 전환은 활성화되지 않는다. 형식 검사는 달라진 파일 목록(`environment_check.changed_files`)의 앞 50개와 전체 변화 개수(`changed_file_count`)를 보존하고 `formal_environment` 대기로 멈춘다. 이 목록은 지문 불일치 분기에만 있다. 성공과 재결박, 기록 부재·파손이나 판본 식별 오류로 먼저 반려된 검사에는 목록과 개수 필드가 없고, 각 반려 사유는 `errors`에 남는다. 지문이 같아도 검사기가 컴파일 직전에 승인된 판본 식별과 다른 점을 찾으면 형식 검사는 같은 대기로 멈춘다. 이때 도구 모음이나 프로젝트 입력 파일이 달라졌으면 그 목록(`identity_errors`)을 함께 보존하고, 실행 명령이나 실행 파일 경로가 달라졌으면 그 사유만 보존한다. 이 대기의 다음 담당은 `trust_governance`이며, 다음 담당은 원인을 둘로 나눈다.

1. **판본 식별도 다르다.** 툴체인이 실제로 바뀌었다. `setup_lean.py`로 새 툴체인 기록을 만들고 `trust register`와 `trust transition`으로 옮긴다. 기존 K는 전환의 재검사를 거친다.
2. **판본 식별은 같고 지문만 다르다.** 재설치, 캐시 재다운로드, 복원처럼 같은 바이트를 다시 깐 경우가 대부분이다. 사용자나 운전자가 `setup_lean.py --rerecord`를 실행해 판단한다.

재기록은 사용자와 운전자만 실행한다. 설치 복구 AI를 포함한 AI 역할은 재기록하지 않는다. 형식 검사와 활성화 검사는 기준과 현재 파일을 대조할 뿐 기준 항목을 기록하지 않는다. 검사가 기준을 자동으로 새로 기록하면 우발적 변경을 탐지하는 목적이 사라지기 때문이다. 그래서 예상하지 못한 지문 변화는 사람이 재기록할 때까지 연구를 멈추게 하고, 반드시 사람에게 알려진다.

`--rerecord`는 판정 파일 전건의 내용 해시를 새로 계산해 현재 기준의 내용 해시와 대조한다.

- 내용이 모두 같으면 메타데이터만 바뀐 것이다. 대표 컴파일을 다시 수행하고, 통과하면 새 지문·같은 내용 해시·새 대표 검사 결과로 기준 항목을 기준 이력에 덧붙인다. 바이트가 같으므로 전환이나 K 재검사를 요구하지 않는다.
- 내용이 하나라도 다르거나 현재 판본 식별이 기록과 다르면 재기록을 거부하고 다른 파일 목록을 출력한다. 판정에 쓰는 바이트가 바뀌었으므로 1번과 같이 새 기록과 전환이 필요하다.

인스턴스는 다음 활성화나 형식 검사에서 덧붙은 기준을 스스로 따라간다. 이를 **재결박**이라 한다. 재결박은 세 조건이 모두 성립할 때만 일어난다. 현재 지문이 툴체인 기록의 현재 기준과 같고, 그 기준이 인스턴스가 결박한 기준과 다르며, 판본 식별이 기록과 현재 파일 모두에서 인스턴스 기록과 같아야 한다. 실행기는 결박을 새 기준으로 바꾸고 `trust_environment_rebound` 사건에 이전·새 결박과 그 기준 항목의 기록 시각을 남긴 뒤 검사를 계속한다. 현재 지문이 기록의 현재 기준과도 다르면 재기록이 아직 없는 것이므로 위의 판별로 돌아간다.

멈춘 작업은 별도 제어 없이 다시 진행한다. 실행기는 `run`의 주 루프를 한 번 돌 때마다 `formal_environment` 대기를 살펴, 툴체인 기록 파일이 바뀌었거나(재기록이나 점검 결과의 추가) 활성 환경이 바뀌었으면 같은 활동의 후속으로 다시 배정한다. 실행기는 이 변화가 원인을 해소했는지 판단하지 않는다. 다시 배정된 형식 검사가 같은 확인을 수행하며, 원인이 남아 있으면 같은 대기로 돌아간다. 같은 순회는 형식 검사의 다른 두 대기도 다시 배정한다. 활성 환경이 없거나 허가가 없어 컴파일 전에 멈춘 `formal_authority` 대기와, 컴파일 도중 일시 정지·허가 변화·환경 변화·입력 변화로만 멈춘 `formal_stopped` 대기는, 활성 환경이 형식 검사를 받고 허가가 그 검사를 허용할 때 다시 배정된다. 이 조건은 형식 검사가 컴파일 전에 거는 관문과 같다. 명시적 실행 정지로 멈춘 검사는 대기에 남는다. 게시 관문에서 판본 식별이 달라 편입하지 못한 봉인 결과도 원문을 보존한 채 `submission_publication` 대기로 같은 변화를 기다린다. 변화가 생기면 모델을 다시 부르지 않고 같은 결과의 편입을 다시 시도한다. 변화가 없으면 같은 입력으로 재시도하지 않는다.

## 선택적 전수 점검

`setup_lean.py --check-contents`는 요청할 때만 실행한다. 예약 감독은 이 점검을 주기적으로 실행하지 않는다. 점검은 현재 판정 파일 전건의 내용을 해시해 현재 기준의 내용 해시와 대조하고, 결과를 툴체인 기록의 점검 이력에 덧붙인다. 결과는 `passed` 또는 `mismatch`와 다른 파일 목록이며, 툴체인 기록에만 남고 인스턴스의 연구 상태에는 쓰지 않는다. 인스턴스는 다음 활성화나 형식 검사에서 기록을 읽어, 현재 기준에 `mismatch`가 있으면 멈춘다.

현재 기준에 대해 `mismatch`가 기록되면 그 툴체인 기록을 쓰는 인스턴스는 다음 활성화나 형식 검사에서 멈춘다. 파일을 복구한 뒤 `--rerecord`가 새 기준 항목을 덧붙이면 다시 진행한다. 점검은 연구 실행기와 별개의 명령이며, 인스턴스는 기록을 읽기만 하므로 점검하는 동안에도 연구 실행은 막히지 않는다.

## 판정 파일, 판본 식별과 지문

판정에 들어가는 파일만 확인한다.

- 구성된 Lean 명령의 첫 실행 파일과 인자 가운데 `.exe`·`.dll` 파일
- Lake 프로젝트의 `lean-toolchain`, `lake-manifest.json`, lakefile과 프로젝트 root의 `.lean` 입력
- Lean 설치와 Lake 프로젝트 아래의 `.olean`과 Lean 런타임 공유 라이브러리(`.dll`, `.so`, `.dylib`). Lean 커널은 `lean.exe`가 아니라 이 라이브러리에 들어 있다.
- 형식 검사기 `formal.py`

`.lake` 안의 `.lean` 소스, `.ilean`, `.trace`, `.hash`, `.c`, `.ir`, git 메타데이터는 커널 판정에 들어가지 않으므로 확인하지 않는다.

**판본 식별**은 `inspect_toolchain`이 관측한 `toolchain` 객체다. `lean --version` 출력, 구성된 명령과 첫 실행 파일의 경로·SHA-256, 명령 인자의 `.exe`·`.dll` SHA-256, 검사기 `formal.py`의 경로·SHA-256을 담는다. 실행 중인 검사기는 경로가 아니라 적재한 모듈 바이트의 SHA-256으로 판본 식별의 검사기와 대조한다. 그래서 작업 공간 미리보기처럼 zip에서 적재한 같은 바이트도 같은 검사기다. 기록된 경로의 파일은 그 SHA-256과 계속 대조한다. Lake 프로젝트를 쓰면 `lean-toolchain`·`lake-manifest.json`·lakefile의 SHA-256, **프로젝트 소스 식별**(`project.source_identity`: 프로젝트의 추적된 git 트리, 작업 트리 diff, 추적되지 않은 입력의 해시), Lake가 구성한 검색 경로도 담는다. 프로젝트 소스 식별에는 추적된 트리와 diff의 해시, 추적되지 않은 입력의 개수와 이름·내용 해시의 다이제스트가 들어간다. `.lake`의 소스와 빌드 산출물은 이 입력에서 제외한다. Lake 프로젝트를 쓰지 않으면 프로젝트 값은 `null`이다. 검색 경로는 Lean 설치와 Lake 프로젝트 안에 있어야 한다. 판본 식별 다이제스트는 이 객체의 정규 JSON SHA-256이다.

**지문**은 Lean 설치와 Lake 프로젝트를 root로 삼아 `os.scandir(...)`로 판정 모듈과 런타임 라이브러리를 열거한 목록이다. 파일마다 root 이름을 앞에 붙인 `/` 구분 상대 경로, 크기, 수정 시각(ns), 생성 시각(ns)으로 한 행을 만든다. 두 시각은 JSON 안전 정수 범위를 넘으므로 십진 문자열로 적는다. 지문 다이제스트는 행을 상대 경로 순으로 정렬한 정규 JSON의 SHA-256이다. 지문을 만들 때 파일 내용은 읽지 않는다.

## 툴체인 기록과 인스턴스 결박

툴체인 기록은 `.skill-workspace/do-math-toolchains/records/<기록 ID>.json`에 있고 `schema` 값은 `do-math-toolchain-record/1`이다. 인스턴스는 기록을 읽을 때마다 JSON Schema로 검증하며, 다른 스키마 판본의 기록은 읽지 않는다. 기록은 다음을 담는다.

- `identity`: 판본 식별. 한 기록 파일 안에서 바뀌지 않는다.
- `baselines`: 기준 이력. 마지막 항목이 현재 기준이다. 항목 하나는 지문 기준(행 목록과 다이제스트), 내용 해시 기준(같은 파일 전건의 SHA-256 목록과 다이제스트), 대표 검사 결과, 기록 시각으로 이루어진다.
- `checks`: 점검 이력. 항목 하나는 점검 시각, 대조한 기준 항목 번호, 결과, 다른 파일 목록이다.

대표 검사 결과는 Mathlib 프로젝트면 `import Mathlib`, `n + 0 = n`, 실수 `norm_num` 예제를, 프로젝트가 없는 명령이면 core 예제를 구성된 명령으로 컴파일한 결과다. source, 명령, 종료 코드, 출력, 시각을 담는다. 시작·종료 시각의 차가 대표 검사의 소요 시간이며, `setup_lean.py` 출력의 `representative_check_seconds`와 채택·등록 결과의 관찰 창 경고가 이 값을 쓴다. 대표 검사의 요약 해시는 명령, source SHA-256, 종료 코드, 표준 출력, 표준 오류, 시작·종료 시각을 담은 객체의 정규 JSON SHA-256이다. 대표 검사의 통과는 전체 라이브러리 재검증이나 연구 목표의 해결이 아니다.

기록 ID는 판본 식별 다이제스트와 첫 기준 항목의 내용 해시 다이제스트를 함께 해시한 값이다. 판본이나 판정 바이트가 달라진 설치는 새 ID의 새 기록 파일을 얻고, 옛 기록 파일은 그대로 남는다. 한 기록 파일에 허용하는 변경은 기준 항목의 추가(재기록)와 점검 결과의 추가 둘뿐이다.

인스턴스의 환경 기록(`trust_environments[<환경 ID>]`)에는 판본 식별(`toolchain`), 허용 공리, 채택 출처, 툴체인 기록의 절대 경로와 ID(`toolchain_record`), 상태와 활성화 검사 결과(`validation_receipt`)가 들어간다. 설치 파일 목록은 넣지 않는다. 인스턴스가 받아들인 기준 항목은 환경 기록 밖의 `runtime.trust_bindings[<환경 ID>]`에 **결박**으로 둔다. 결박은 기준 항목 번호와 그 항목의 지문 다이제스트, 내용 해시 다이제스트, 대표 검사 요약 해시다. 재결박은 이 결박만 바꾸므로 환경 기록과, 환경 기록에 기댄 형식 결과·동일성 검토의 전제는 바뀌지 않는다. 인스턴스는 툴체인 기록 파일의 바이트 해시에 결박하지 않는다. 재기록이 기록 파일을 다시 써도 판본 식별이 같은 한 인스턴스는 계속 그 기록을 읽는다.

## `setup_lean.py`의 모드

| 명령 | 동작 | 종료 코드 |
|---|---|---|
| 인자 없음 | Lean과 Mathlib 캐시를 설치하고 툴체인 기록을 만들거나 확인한 뒤 준비 표지를 쓴다. | 0 성공, 1 대표 컴파일 실패 또는 재기록 필요, 2 실행 오류 |
| `--verify-only` | 내려받지 않고 설치된 명령의 툴체인 기록을 만들거나 확인한다. 명령은 `--command-file`로 지정할 수 있다. | 위와 같음 |
| `--rerecord` | 사용자와 운전자만 실행한다. 위 `지문 불일치와 재기록`의 절차로 기준 항목을 덧붙인다. | 0 기록, 1 거부, 2 실행 오류 |
| `--check-contents` | 선택적 전수 점검 | 0 통과, 1 불일치, 2 실행 오류 |
| `--inspect-only` | 판본 식별만 관측하고 기록하지 않는다. | 0 성공, 2 실행 오류 |

설치와 `--verify-only`는 먼저 판본 식별이 같은 기록들을 찾아, 현재 기준의 지문이 현재 지문과 같고 불일치 점검이 없는 기록이 있으면 그 기록을 다시 사용한다. 그런 기록이 없으면 판정 파일 전건의 내용 해시로 기록 ID를 계산한다. 그 ID의 기록 파일이 이미 있으면(같은 판본·같은 내용이지만 지문이 다르거나 불일치 점검이 있는 경우) 기준을 덧붙이지 않고 `rerecord_required`로 끝나고, 없으면 대표 컴파일을 거쳐 새 기록을 만든다. `--rerecord`와 `--check-contents`는 `--record <기록 ID>`로 대상을 지정한다. 생략하면 현재 판본 식별의 기록이 정확히 하나일 때 그 기록을 쓴다. `--records-dir`는 기록 디렉터리를, `--evidence-dir`는 대표 컴파일 증거의 상위 디렉터리를 바꾼다. 증거 디렉터리는 Lean 설치와 Lake 프로젝트 밖에 있어야 한다. `--trust-file <새 경로>`는 설치·`--verify-only`·`--rerecord`가 성공한 뒤 결과 기록의 현재 기준으로 등록 요청을 새 파일에 쓴다.

모든 모드는 결과를 표준 출력에 JSON 객체 하나로 출력한다. 설치의 내려받기 안내와 Lake 진행 출력은 표준 오류로 나간다. `status`는 `observed`, `recorded`, `passed`, `mismatch`, `failed`, `refused`, `rerecord_required`, `error` 가운데 하나다. `observed`는 `--inspect-only`의 결과이며 관측한 `lean_command`와 판본 식별 `toolchain`을 담는다. 기록을 만들거나 점검한 모드가 성공하면 `record_path`, `record_id`, `binding`을, 거부나 불일치면 `reason`과 다른 파일 목록(`mismatched`)을 함께 담는다. Lean 명령을 찾지 못하거나 toolchain root가 없는데 기록 디렉터리를 받지 못한 것도 실행 오류이므로 `status: error`, 종료 코드 2로 끝난다. 기록을 쓰는 모드는 `records/.lock`의 OS 잠금으로 서로 배제하고, 기록을 읽고 이력을 덧붙인 뒤 원자적으로 교체한다. 다른 작성자가 잠금을 쥐고 있으면 기다리지 않고 `status: error`, 종료 코드 2로 끝난다. 잠금은 그 프로세스가 끝나면 OS가 풀므로 사람이 지울 파일은 없다. 인스턴스는 잠금을 잡지 않는다.

## 남는 위험

- 크기, 수정 시각, 생성 시각을 모두 보존한 채 내용이 바뀌는 손상(비트 부패 등)은 사용 경로에서 탐지하지 못한다. 선택적 전수 점검만 찾으며, 누군가 점검을 요청할 때까지 드러나지 않을 수 있다.

- 의도적 변조는 다루지 않는다. 현행 계약은 같은 OS 사용자 권한의 작업자를 격리하지 않는다.

## 불변 payload와 조회

큰 불변 값과 큰 불변 문자열은 저장 코덱에서 내용 주소형 artifact로 한 번 보존한다. 레코드 파일의 `payloads`는 JSON 좌표, artifact 경로, SHA-256, 바이트 수를 결박한다. 해당 좌표의 물리 표현은 null이며, 읽기는 정확한 artifact를 검사해 논리 값을 복원한다. 한 프로세스가 같은 저장소에서 이미 대조한 artifact는 불변이므로 다시 해시하지 않는다. 작은 값은 인라인으로 저장한다. 이것은 현행 인코딩이며 옛 대형 인라인 상태를 자동 변환해 읽는 호환 경로가 아니다.

`read --path`는 실제 파일 바이트를 반환한다. 레코드 조회는 복원된 논리 레코드를 반환하며, 외부 payload가 있으면 `payload_refs`와 `json_pointer_scope=decoded_record`로 차이를 표시한다. 파일 해시와 논리 레코드 해시를 혼동하지 않는다. 사용자 원문의 코드 포인트와 UTF-8 바이트는 바꾸지 않는다.

한 프로세스는 같은 Git OID·계약 판본의 검증 결과를 저장소 객체 사이에서 공유한다. 이 프로세스가 게시한 head는 게시 전에 후보로 검증한 상태를 그 head의 검증 결과로 삼고 다시 읽어 검증하지 않는다. 기동 때 읽은 head나 CAS 충돌 뒤 다른 기록자가 게시한 head처럼 밖에서 온 head는 처음 읽을 때 전체를 검증한다. 후보 검증은 부모와 같은 레코드의 레코드 단위 검사를 되풀이하지 않고, 관계·식별·의미 규칙은 상태 전체에 적용한다. 반환되는 가변 레코드는 분리하고 큰 payload는 변경할 수 없는 값으로 공유한다. 변경하려면 새 값을 저작한다. 최종 expected-head CAS, 참조·권한·불변 기록 검사는 계속 적용한다. writer lock을 쥔 동안에는 최종 CAS가 ref의 유일한 비교다. 저장소의 물리 경계(재분석 지점, 볼륨, 최종 경로)는 저장소를 열 때 확인하고, Git 오류가 나면 다시 확인한다.

현재 레코드가 더 이상 참조하지 않는 payload도 Git에는 불변 원문으로 남는다. 나중에 같은 내용을 다시 참조하면 기존 바이트를 대조해 재사용한다. 상태 코덱과 별도 artifact가 같은 경로를 제시하면 바이트가 일치해야 하며, 검증 뒤 다른 바이트로 덮어써 게시하지 않는다.

역할 입력 생성기는 큰 과거 제어 요청을 같은 고정 입력의 상세 파일로 보존하고 `request_source_ref`를 제공한다. 이 변환은 참조 목록과 제출 검사 문맥을 만들기 전에 수행한다. 요청 종류·ID·원문 좌표와 미결 의무는 유지한다. 상세 원문은 기존 source 읽기 도구로 읽는다. 단순히 prompt의 끝을 자르거나 불편한 실패 기록을 지우지 않는다.

## 시작과 종료

배정할 로컬 실행에는 프로세스를 만들기 전에 `launch_ticket`을 기록한다. ticket은 실행·프로필, 소유 실행기의 host/session·PID·정확한 생성 FILETIME, 유일한 Job 이름과 시작 단계를 결박한다. native 실행은 그 이름으로 Job을 독점 생성한다. 기존 이름과 충돌하면 다른 Job에 붙거나 그것을 종료하지 않는다.

ticket 공개 → suspended root 생성 → 시작 정체성 공개 → 현재 권한 확인 → resume 순서를 지킨다. adapter가 명확하게 프로세스를 만들지 못한 경우와, 시작 정보가 단지 없는 경우를 구별한다. `not_started`는 실제 시작 실패 결과이며 메타데이터 부재에서 추측하지 않는다.

복구는 이전 소유 실행기가 더 이상 시작할 수 없는지, 같은 host/session의 알려진 Job이 비었는지 확인한다. 다른 호스트·세션, 접근 실패, 살아 있는 이전 owner는 종료 확인이 아니다. PID 재사용은 생성 FILETIME으로 구별한다. 종료 확인 전에는 슬롯을 반환하거나 후속 실행을 시작하지 않는다. 원격 공급자의 종료는 별도 unknown 범위다. 옛 ticket 없는 미확정 실행의 종료를 소급 확정하지 않는다.

## 정상 정비

사용자 대화/운전자는 다음 공개 명령으로 정비 fence를 만든다. 내부 연구 역할이 이 명령으로 스스로 권한을 바꾸지 않는다.

```powershell
python .agents/skills/do-math/scripts/do_math.py quiesce --repository <repo> --instance <RI-ID> --reason "설치 교체"
python .agents/skills/do-math/scripts/do_math.py status --repository <repo> --instance <RI-ID> --json
```

`effect=applied`는 새 배정을 막는 정비 fence가 정본에 적용됐음을 뜻한다. 기존 실행의 종료와 자원 정산은 별도로 확인한다. `maintenance_fence.state`가 `quiescent`이고 실제 실행기 프로세스가 끝나 writer lock을 놓은 것을 확인한 뒤 설치를 교체한다. `draining`은 진행 중 계산·시작·회수를 정산하는 상태다. `blocked`에는 미종료 실행과 미반환 예약이 표시된다. 이 상태에서 프로세스가 없을 것이라고 추측해 넘어가지 않는다.

fence는 새로운 배정을 막고 기존 실행을 정상 정산한다. 오래 걸린다는 이유만으로 연구 계산을 강제 종료하지 않는다. 종료를 요구할 때는 기존 권한·체크포인트·정지 절차를 사용한다. 로컬 실행이 끝난 뒤 남은 봉인 제출물은 보존하고 정비 후 다시 현재성을 확인해 편입한다.

```powershell
python .agents/skills/do-math/scripts/do_math.py release-quiesce --repository <repo> --instance <RI-ID> --fence <만든-제어-ID> --reason "설치 검증 완료"
python .agents/skills/do-math/scripts/do_math.py operator start --repository <repo> --instance <RI-ID>
```

해제는 지정한 현재 fence에만 효력이 있다. 사용자 pause나 HOLD를 해제하지 않는다. operator 출처는 user 출처의 정비 fence를 해제할 수 없다. 예약 감독도 fence가 있으면 연구를 새로 시작하지 않는다. 계약·저장 형식을 변경한 프리알파 설치는 새 인스턴스로 검증하며, 기존 기록을 임의 변환하지 않는다.

운영 단계는 고정 연구 snapshot과 다른 로컬 관측으로 표시하며 파일 해시·관측 시각을 함께 둔다. 완료하지 못한 span의 종료 시각을 채우지 않는다. 겹친 span의 시간을 합쳐 실제 경과 시간이라고 하지 않는다. 파일마다 Git commit을 만들지 않고 진행 기록은 제한된 주기로 갱신한다. 계측 장애는 알려 주되 새로운 연구 권한이나 수학적 승인을 만들지 않는다.

운영 계측 오류는 `operations/errors/`의 실행별 제한된 기록에 실패 연산·상대 경로·예외 유형·errno/winerror·최초/최근 시각·횟수를 보존한다. 오류 문구에 원 요청·명령·크리덴셜은 싣지 않는다. `operation_progress.telemetry_errors`에서 이 진단을 볼 수 있다.

로컬 상태·제어·보고 파일은 임시 파일을 완성한 뒤 같은 디렉터리의 이름을 원자적으로 교체한다. Windows의 공통 읽기는 삭제 공유를 허용하고, 교체는 `FileRenameInfoEx`의 `REPLACE_IF_EXISTS | POSIX_SEMANTICS`를 사용한다. 이 기능을 지원하는 Windows 파일 시스템이 필요하다. 이미 열린 독자는 이전 파일을 끝까지 읽고 새로 연 독자는 새 파일을 읽는다. 접근·공유·잠금 오류(WinError 5·32·33)에는 같은 이름 교체만 최대 여섯 번 시도하며, 연구 실행이나 제어 요청을 재수행하지 않는다. 실패가 계속되면 오류와 임시 파일을 보존한다. Git 정본·입력 파일의 기존 물리 경계 검사는 유지한다. 계측 오류 기록 자체는 교체 장애를 남길 수 있도록 별도 기록하며, 불완전한 진단은 읽기 실패이지 정본 상태가 아니다.
