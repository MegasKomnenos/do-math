source-start/source-end의 2,675개 전건 SHA가 025 manager source-inspected와 같아 제품 쓰기 0이다. input-read/end-protection은 배정 원자료·공용 문서·추가 정본/과거 근거를 구별해 보존한다. 공식 제품 시험, 모듈 실행, 미러 생성, 학술/Lean/유료/OS/예약 호출, Git 상태 변경 및 graphify 갱신은 수행하지 않았다. Python 보조 분석은 -B와 표준 라이브러리만 쓰며 자기 evidence에만 기록했다.

## 현재 이름의 소유와 조합

공통 실행의 입력 이름은 CoreEngineMixin._context와 context_store.prepare_role_input의 최종 역할 입력에 연결한다. implementation_documents의 논리 path/복원 local_path/sha256/bytes와 manifest documents의 artifact_ref는 P02의 실제 바이트 결속을 재사용한다. submission_contract/record_map.read_tool/formal_verifier.preview는 P03의 설치 후 지급 경계다. 전체 execution_profiles와 role_profile_refs의 source_ref, 직접 task와 다른 tasks의 참조 대체, 계획/준비의 recent_history와 다른 역할의 runtime history[-8:]를 섞지 않는다. task_catalog의 결과 수와 실행 ID는 원문 목차다. source_ref를 읽지 못한 것을 빈 목록으로 처리하는 해석은 허용하지 않는다.

record_map/record_index/families/ledger/blocked_keys/read_tool은 context_store의 현재 입력 범위와 input_tool.read_main의 명령/실제 반환에 연결한다. 가족 표의 첫 항목 이후 이름은 같은 root의 산문 단축이고 별도의 경로가 아니다. 싣기/지도/차단, supplied_only/readable과 연구 정본 goal_judgments 차단을 실제 input_scope/BLOCKED_KEYS/readable_record_index/readable_snapshot_path에 연결했다. --list와 --family는 결합하고 --output은 단일 --path에만 결합하며 input/ 쓰기를 거부한다. 이 원문 읽기 경계와 제출 인용 권한을 구별한다. 사용자가 논문·기록을 실제로 읽었다는 인증은 이 정적 검토의 범위가 아니다.

check는 공통 제출에서 submission_check의 passed이며 입력 소비자 검사에서 import_check의 sha256과 다른 소유자다. payload는 사용자 import_payload와 자기점검 전달 worker_feedback의 별도 소유자다. record는 governance record, candidate record, 읽기 도구 복원 record로 문맥이 다르다. checkpoint는 수행 주 응답 문자열과 작업공간 checkpoint.json 및 관리 파일의 서로 다른 경계다. deadline_offset_ms는 전달 당시 payload와 갱신된 중앙 의무에서 의미가 다르다. doc_code의 line-local owner와 별도 실제 boundary 검사를 유지한다.

과제 착수조건 표는 planning.CONDITION_FIELDS 11개, RECORD_FAMILIES 21개, EXPOSED_FIELDS의 18가족과 직접 대조했다. family의 singular/hyphen 이름과 저장 family의 plural/underscore 이름을 혼동하지 않는다. relation_exists 입력은 subkind/from_id/to_id이고 관계 산출 source/target으로 대체할 수 없다. decision_value_is의 null/부재·bool/int·특정 task 범위와 /usable_as_k의 계산 효력은 실제 evaluate_condition과 기존 직접 단언을 읽어 확인했다. 두 JSON 예제는 현재 문법과 예시 ID/제목 결박을 사용하는 예제이며 실제 KN-A를 생성하거나 이 조건의 현재 readiness를 실행해 본 것은 아니다.

모델 표의 세 tier/model/3슬롯은 model_policy.MODELS/LIMITS, 역할 하한은 ROLE_TIERS와 selection/validate_policy에 연결한다. difficulty/importance 높은 축, 미평가 work의 high, task profile allowlist와 계약검토자의 역할 profile, 현행 capacity와 고정 profile 판본을 구별한다. model_assessments의 일반 준비 task_title와 계획 selected task_id는 assessment_key/validate_assessments와 실제 metadata receiver의 소비다. 허용 profile/능력 요구를 슬롯 부족으로 낮추거나 다른 모델로 우회하는 해석을 승인하지 않는다. session_limits.work는 동시 로컬 작업 실행 용량이며 토큰·금액·운영 역할 호출수 예산이 아니다. 서비스의 개발 담당 모델 변경 지시는 제품 인스턴스 기본 모델 표의 변경 지시가 아니다. Claude 잠금/구간 usage_segments/누적 model_usage_reported와 provider_limit 원장의 이름은 해당 생산/소비자에 연결했으며 공급자의 미보고 내부 소비를 관측했다는 주장은 없다.

입력 소비자는 governance.validate_import_units의 실제 등록 kind/비빈 payload.kind/owner_ref와 control_contracts.validate_decision_shape 및 도메인 적용 경계에 연결한다. governance content 표는 validate_governance_record의 종류별 필드다. grant/delegation의 새 ID와 사용자 승인·원문을 적용기가 결합하는 필드, task_scope의 정확 판본/권한, question_answer의 공개 질문/미해결 대상, configuration의 해당 instance owner, research_record/evidence의 후보 저작 필드를 구별한다. 이름 evidence가 형식 검증/동일성 승인으로 승격되지 않는다. 빈 payload는 무변경이지 kind 누락이 있는 비빈 payload의 허용이 아니다.

관찰 연산 6개의 operator/subject_kind/source/unit은 observations.OPERATORS와 동일하다. 규칙 목록/교체 객체/최초 $execution·현재 ID를 validate_rules/bind_task_rules/task_rules_from_execution에 연결했다. 자기점검의 응답 필드는 control_protocol.SELF_CHECK_RESPONSE_SCHEMA, 전달 및 수신은 control_server/control_transport/ObservationTracker다. safety_boundary는 의무 응답·인지 근거와 다르다. request_id는 제어 envelope, self_check_id는 전달 의무, obligation_id는 응답 본체에서 같은 의무를 가리킨다. successful exact poll/응답 전 새 command/전달 전 시작한 부분 행/기한 정지에 대한 현재 시험의 직접 단언을 확인했다. 일반 checkpoint 갱신으로 응답을 대체하지 않는다.

지식 저작/관계는 contracts의 역할별 wire와 knowledge.AUTHORED_FIELDS/knowledge_io.BUILTIN_DEFINITIONS 및 submission.extension_schema에 연결한다. 저자 summary와 verified_summaries의 현재 연결, formal_valid와 usable_as_k, 주 relations의 4필드와 확장 relations의 FR/IA 근거는 별도 경계다. derived_from/generated_from은 source=H,target=P다. formally_implies는 추가 형식/판정 증거를 요구하며 인수분해 H만으로 가분성 P를 승인하지 않는다. 수학 예시의 n/H/P는 모델이 저작할 필드 이름이나 현재 기록 ID가 아니다. 가정/전사/범위/효력 대조의 연구 절차를 새로운 코드 API나 전 기능 재감사 요구로 바꾸지 않는다.

학술 이름은 실제 services/scholarly-mcp/server.py의 등록 list_sources/describe_source/search/fetch/extract와 ToolResult의 status enum으로 확인했다. 과거 lexical pending이었던 describe_source/not_implemented/restricted는 현재 정본에 정의된다. search는 source/query/options/start/limit/cursor/export, fetch는 source/target/parts, extract는 ref/fields/start/count/selection/render를 소비하며 자동으로 다른 source로 바꾸지 않는다. 이미지 ref 저장과 MCP 이미지 전달, 모델의 실제 판독은 다른 성질이다. scholarly.configured와 tool:scholarly는 설정 전달/허용 참조이지 노출·호출 완료가 아니다. 014의 list_sources 성공 완료는 그 한 경계만 유효하며 search/fetch/논문 전사·이미지 판독의 실제 성공으로 확대하지 않는다.
