# role-contract-names 판정

시작과 끝은 025 manager가 검사한 `.claude/skills`, `.agents/skills`, `.agents/diff` 전건을 같은 제외 규칙(`__pycache__`, `.pyc`)으로 대조한다. 판정 대상은 역할 계약 11문서 1,299행이다. 144개 N03 required_slices를 현재 제목으로 연결했다. 현재 인라인 출현은 1,287회이며 문서별 이름 쌍은 779개, JSON 펜스 예시는 2개다. 이 수는 찾아보기와 좌표 검산 수이지 의미 검증 완료율이 아니다. 역사 후보 1,167회/451토큰과의 차이를 소스 변경으로 해석하지 않는다. 역사 목록이 제외했던 dotted/file/code 표기가 현재 추출에 들어오며 44개 절의 이름 집합 차이는 slice-map.json에 보존했다.

decisions.json은 문서·절·이름·현재 행·문맥 소유자·유지/비코드 제외/교정 판정을 담는다. 반복 이름은 같은 절·같은 소유자로 묶고 원문 행을 보존했다. 서로 다른 객체의 summary와 역할별 decision은 별도로 판정했다. 판정 근거의 현재 정의·실제 소비·시험 본문과 SHA는 source-profiles.json, 펜스의 정확 JSON과 키 경로는 fence-decisions.json, 읽기용 표는 decision-table.md에 있다. 이 보조 산출의 coverage 검사는 선언한 소유자가 의미상 옳다는 자동 인증이 아니다.

## 문서별 핵심 판정

- 독립-운영: quiesce와 operator install/probe는 cli_contract.build_parser의 실제 명령/mode다. repair_report_schema는 supervision의 외부 복구 응답이며 내부 maintenance 응답과 다르다. operator/HOLD.json과 bootstrap 주소 경로, inventory 제외 이름은 파일/집합 규칙이다. model_called=false의 무조건 반환처럼 읽히는 문장 한 곳은 분기 조건을 붙이는 교정을 반환한다. 나머지 이름은 유지한다.
- 동일성-검토: stage_schema의 scope/initial/organize/answer/judge를 따로 연결했다. scope_assessment의 initial_slots와 role_review의 retained_reviewer_slots 등 입력을 구별했다. organize의 finding_refs와 answer_role_slot_id는 output.issues[]의 필드이며 output.decision은 없다. judge의 issue_verdicts[].decision과 제안 전체 decision은 각각 다른 열거다. scope 계산의 U+N+4/U+2N+7은 minimum_scope_executions의 실제 두 분기와 같다. assessment_reassessment의 판정 의미와 identity_assessments/assessment_uses도 일반 제안 편입과 구별해 유지한다.
- 목표-감사: goal/goal_revision/policies, eligible_knowledge의 proposal·formal_result·identity_assessments는 _context의 생산이다. formal_result.verification은 같은 지식의 검사 결과다. 추가 감사의 audit_ref/assessor/verdict/input_hashes는 additional_audit_input/ additional_audit_schema와 evaluate_goal_audits의 소비에 연결했다. content.assessor의 line-local governance_content 별칭을 유지한다. satisfied와 scope_complete는 다른 판단 축이다.
- 보충-조사: 검토 자리의 고정 질문은 research_schema, 과제 조사는 supplemental_research의 일반 schema다. answer/answered/scope_complete/evidence_refs를 일반 outcome/report/knowledge/relations에 차용하지 않았다. sources[].ref는 해당 문장의 명시 별칭 review_sources 원소이며 일반 연구 sources의 id와 다르다. 고정 조사 확장은 extension_schema에서 전부 비허용이고 질문 범위 확대를 허가하지 않는다.
- 연구-계획: 입력 ready_task_ids/returned_task_ids와 output dispositions/task_assessments를 별도로 연결했다. task_catalog.assessment_current 및 assessment_invalidated_reason은 prepare_role_input의 투영이며 저장 task의 직접 필드처럼 취급하지 않는다. completed/incomplete/closed, item_dispositions의 fulfilled/open/waived/transferred는 task_contracts의 실제 소비 조건을 따른다. model_assessments는 선택 과제의 확장이며 academic_resolutions.id는 external_rejections[].id다. goal_judgments.current와 현재 목표의 해결 보증은 다르다. 022~024에서 검수한 입력 초과/개정/운영 처분 문장 성과는 유지한다.
- 연구-수행: work schema의 outcome/report/knowledge/relations/remaining_work/checkpoint를 연결했다. knowledge.summary와 주 응답 summary는 다른 소유자다. kind_definitions는 등록된 종류의 입력 목록이고 knowledge_metadata는 별도 확장이다. declaration_names의 prime 예시는 설치된 실제 정리 이름의 주장이 아니라 lean_evidence.is_lean_identifier의 지원 문법 예시다. observation-feedback.json은 지급 feedback_path의 basename, checkpoint.json과 .control/stop-request.json은 파일 이름이다. 자기점검 rule_proposal/normal/defect/indeterminate와 운영 disposition.continue/중앙 알림 decision=checkpoint를 구별해 유지한다.
- 운영-점검: 주 응답 disposition의 continue/repair/resume/retry/task_disposition/user_decision 여섯 분기를 연결했다. next_review의 {at,reason}와 repair_target/meaning_preserving/verification, checkpoint_ref/scope/replay_safety는 각 분기의 필드다. basis_refs는 admissible_basis_refs에 결박되고 used_sources와 다르다. operational_evidence와 recovery_materials는 같은 checkpoint_source 이름을 사용해도 서로 다른 실제 생산 객체다. 이 P01 성과는 008~009 및 현재 source/025 rows 범위에서 재사용했다. task_disposition에는 현재 _response_schema가 연구 계획의 task_assessments를 조건부로 추가한다.
- 유지보수: 일반 report/remaining_work, 초기 실패 진단의 initial_submission_diagnosis.decision/guidance, kind_definition_check, impact_review는 각각 실제 동적 _response_schema/action_schema에 연결했다. record_map.ledger의 readable은 context_store의 읽기 범위이다. 영향 검토의 확장 비허용, 권한 없는 recovery=true의 부정 예시와 설치 repair_target의 의미를 유지한다. S0·영향 계획·후보 전건 적용 전체를 새로 감사한 것은 아니다.
- 의도-해석: import_unit/question_detail은 interpretation_schema의 import_units/question_details 배열 원소를 가리키는 산문 단수형이므로 필드 추가나 개명이 필요 없다. source_range.start/end, owner_kind/owner_ref/payload, question_index/target_ids/source_unit_ids/options는 해당 원소에 연결했고 validate_import_units의 원문 피복·대상·질문 소비를 대조했다. check 분기의 decision/bundle_sha256/unit_ids/question_ids와 interpret repair 계보를 분리했다. delegation_judgment는 _response_schema의 동적 별도 분기다. 검사 승인·사용자 승인·적용은 별도다. P06/P10의 023 검수 성과는 재구현하지 않는다.
- 작업-계약-검토: task의 저장 계약과 후보 wire를 구별했다. CONTRACT_REVIEW_ITEMS의 다섯 item_id 표는 정확히 같고 item_reviews[].decision만 반환한다. 전체 decision 금지 문장은 올바르다. 계약 basis/review_basis_key와 producer_execution은 input action/task의 기계 값이다. completion_obligations의 judges와 전문 판정 적용은 task_contracts/planning의 소비에 연결했다. 잘못된 기준 문구 두 인용은 비코드 반례이므로 필드로 등록하지 않는다.
- 후보-준비: candidates.items의 표는 TASK_CANDIDATE/PROGRESS/OBLIGATION/PROFILE_REF와 맞고 description/evidence_requirements는 선택 필드다. 과제 ID와 판본은 task_candidate_record가 부여한다. contract_checks의 다섯 규칙은 submission이 발생시키며 TK-/KN-/TK-W와 τ 구간은 문면 참조/수학 예시다. 모델/규칙 보충은 일반 준비와 별도이며 model_assessments는 task_id, 후보 평가에는 task_title을 쓴다. regenerate_after는 일반 준비에서만 요구된다. 두 JSON 펜스는 전체 주 응답이 아니라 정확한 확장 부분 객체/배열 원소 예시이므로 그 소유자로 유지했다.

## 인라인 밖의 이름과 비코드 범위

독립-운영 21행의 backtick 없는 installation_root, snapshot_root, manifest, bootstrap.main, scheduled_operator.main은 현재 operator_bootstrap.main의 manifest[installation_root] 또는 snapshot_root 선택과 scheduled_operator.main의 installation_root 인자에 연결한다. 이 문장은 008에서 교정했고 009가 관련 회귀를 해소했다. 현재 문장은 같은 성질이며 LIVE_INSTALLATION_ROOT를 복원하거나 추가하지 않는다. 008 원보고의 BootstrapInfo 두 passed row를 reused-rows.json에 정확히 보존했다. 008 당시 전체 Python과 현재 판본은 서로 다르므로 당시 전체 회귀를 현재 전체 성공으로 주장하지 않는다.

후보-준비 JSON 펜스의 backtick 없는 task_id/revision/boundary/independent_of_next_revision과 model_assessments/model_assessment_deferrals 배열 원소의 task_id/difficulty/importance/reason은 fence-decisions.json에 전부 열거했다. 같은 field 이름의 무관한 역할 존재로 승인하지 않고 submission.extension_schema의 해당 역할·보충 분기 또는 contract_checks 원소에 연결한다. true/false/null, 수학 변수와 구간, 예시 TK-one/TK-two/TK-W, 파일 확장자·디렉터리는 실재 product field의 새 이름으로 세지 않는다. 선언명 예시의 문법은 lean_evidence.is_lean_identifier와 현재 boundary.test_knowledge_lean_verifier의 prime 시험이 소유하며 실제 컴파일을 새로 수행하지 않았다.

## 재사용과 정확한 남김

reused-rows.json은 025 c2의 현재875 Python과 전건 SHA 동일 및 structure.test_doc_code의 정확33 passed rows를 확인한다. 023의 문서 rows, 008의 BootstrapInfo 두 rows는 당시 판본과 현재 차이를 함께 보존하고 manager 검수의 지정 성질만 재사용한다. 이 rows의 통과는 새 단독 이름·JSON 예제를 검사했다는 증거가 아니다. source-profiles의 현재 시험 본문을 읽은 일도 새로운 시험 실행과 다르다.

PR24/B110~B114의 명시 owner/line-local alias/진단/배열 구별과 019~025의 지정 실제 반환 교체 성과만 유지한다. history-reuse.json에서 존재하는 원보고7개 SHA를 대조했다. AST producer 추론 helper는 재구축하지 않는다. 이 조사에서 다른 PR24 hunk나 N01/N02 전체를 완료 처리하지 않는다. N03 이름 판정의 유지 가능한 부분과 repair-candidates.json의 정확 문구/검사 공백만 다음 manager에게 반환한다.

024 F2의 conversation_loss_policy/disconnect_policy/model_policy/external_policy/adopt_default_review_policy 전체 의미는 policy-semantics의 별도 경계다. 그 task 결과를 읽거나 기다리지 않았다. L01 Q1/Q2의 운전 host·단위 선택, UTF-8 출력byte 요구 및 실제 읽기/준수 미충족은 그대로다. 일반 전체/freshT3/변이/G7 최종 판본 연결/최종 review는 실행하거나 종결하지 않았다. 제품 writes는 없고 원보고와 공용 정보는 바꾸지 않았다.
