## 과거 공백과 현재 질문

K-27의 역사 `strength-gap` 뒤에는 B36의 binding/정확 영수증 수리가 있고, K-38·K-72에는 B37의 명시 Lean 사실과 실제 저장 reload 수리가 있다. K-75는 이 두 수리 및 B80의 준비 경로 보존과 함께 판정한다. 현재 성질을 대조하지 않은 채 이 네 항목을 확정 결함으로 되돌리지 않는다. 각 항목의 JSON 질문은 정상 bound 응답과 의도한 반려, 두 기본 Lean 소스의 전체 선언/의존 사실, 실제 receiver/reload 등 확인할 대상을 지정한다.

P2 A-31의 `plan1/Stage2필수` 기록은 B21과 B107~B109 이전 상태다. 빈 준비 plan0은 현재 본문에서 확인했다. reason-only dispatch 반례와 원래 두 양성 ID까지 연결하는 의미 판정은 남겨 뒀다. B-32의 필수 입력 분류도 B72/B73의 후속 기록을 먼저 읽는다. 의도적으로 필수인 goal의 overflow를 잘못된 동작으로 바꾸지 않는다. A-42는 capacity=0과 work_calls 누적 소진을 구별한 원 반례 대응 근거가 부족하므로 독립 운영풀의 실제 배정 여부 하나를 질문한다.

역사 timeout, SHARDS, 메모리 저장 대역 이름은 유지해야 할 동작과 구별했다. 최신 사용자 정정은 시험/변이의 시간 강제종료를 폐기한다. 실제 임대·사건 시각·호출 국면 의미는 별개다. 폴더 기반 수집과 실제 ResearchRepository를 이전 구현으로 되돌릴 이유도 없다. 각 관련 K/의무/P2 행에 적용 해석을 적었다.

1-A도 원문 인용의 필수 필드와 현행 설계 A20의 필수+선택 필드 전체를 구별했다. 원문을 재작성하지 않고, 역방향 대조 질문에 현행 계약의 더 넓은 범위를 적용한다. A22의 필드 이름 존재만으로 실제 생산/저장 도달을 입증하지 않는다.

## 이전 작업 검토의 재사용과 배정

25영역의 B01~B109 매핑은 빠짐없지만, 실제 상태는 PR23 완료, PR06 부분 완료, 나머지 23영역 미검토다. PR06의 완료 부분은 B116에서 검토한 B22다. `prior-review-state.json`은 모든 영역에 각 B의 실제 commit/hunk 진입점, 현재 파일, 원보고 selector, 끝나는 질문 및 함께 배정할 기존 요구 작업을 기록했다. 파일이 없는 역사 seed나 디렉터리는 유효한 파일 참조로 꾸미지 않았다.

PR23의 원보고 111/113/128 통과와 앞선 red/fixture 실패는 실제 파일·SHA와 결과를 확인했다. B107의 planning.py, B109의 최종 lifecycle 경로 등은 현재 코드와 대조했고, 이전 commit 이후 달라진 파일은 `pr23-current-diff.txt`에 실제 git diff로 보존했다. B107 뒤 B108/B109가 같은 시험/수명 코드를 보강한 이력과 이후 known_defects 변경을 구별한다. 이 차이를 모든 과거 판단의 무효나 새 전체 검토 완료로 처리하지 않는다.

B115 문서 검토의 유지/교체 판정도 재사용한다. 스키마 소유자·배열·이름 검사는 유지 가치가 있으며, AST 대입 수집은 삭제/재대입 후 없는 필드를 통과시키고 동작이 같은 dict 생성 표현에는 실패하는 반례가 있다. 따라서 남은 실제 반환 결속의 교체는 확정된 검사기 수리다. 실제 제품 반환값이 잘못됐다는 판정은 아니다. 현재 문서/생산자별 packet은 같은 phase의 document-closeout 책임이며 이 task는 그 중간 결과를 읽지 않았다.

같은 파일을 다시 읽는 재검토는 요구 작업에 합친다. 예를 들어 PR06과 R01/R05/R06/R07·저장 보존, PR04와 템플릿/모델 제출 보존, PR10과 대기/표시, PR17과 역할 변형, PR18과 평가자 쌍, PR19와 시간 국면을 묶을 수 있다. PR23은 별도 재감사 없이 LINK-11-B 입력으로 재사용한다. PR05의 옛 ID 처분과 기반 이행도 migration 파일별로 해당 소비자와 대조하며, 25영역 전체 완료를 모든 구현의 선행 조건으로 만들지 않는다.

## 가까운 선택과 선행 관계

1. manager가 document-closeout의 실제 남은 소유자 목록을 검수해, **_context/REVIEW/TRUST 중 그 보고가 한정한 다음 반환 묶음**을 배정할 수 있다. 이미 입증된 AST 거짓 통과를 제거해 G3와 13-C를 줄이는 작업이다. PURE/CLI 완료 부분과 산출 문서 이름·정책 의미·읽기 한도 질문을 혼합하지 않는다.
2. gate-readiness의 실제 환경 결론은 지금 G7의 외부 의존 판단에 반영한다. 본 task의 9-B 남김은 실제 quota 거부·복수 결과/종료 정리·역할 스키마·등록된 triggerless 예약 및 parser×지원 판본 연결이다. 이 자료 취득이나 경계 수리가 최종 판본을 바꿀 수 있으므로 **최종 일반/T3/변이보다 앞선다**. 여기서 실환경 성공이나 도구 이용 가능성을 대신 선언하지 않는다.
3. 그 외 다음 work는 분류표의 **한 종료 질문**과 겹치는 PR slice를 합쳐 배정한다. 예를 들면 R18의 현행 호출 지점과 기존 정적 검사 대응, 또는 KEEP-MODEL-SUBMIT의 K-27 정상/반려 계약과 B36의 현재 소비자 대응이다. 답이 충분하면 재구현하지 않고 최종 판본 연결로 넘긴다. 새 공백이 확인됐을 때만 그 원소/입력축/단언을 고친다.
4. 의미 질문과 필요한 수리·실경계 자료를 끝낸 뒤 G4 전체 일반 → G5 fresh `--tier T3 --full` → G6 현재 대상 함수 전건과 정상 기준/변이를 연결한다. 기존 변이 17분할은 분모가 아니다. G7의 실제 호출·말뭉치 판본을 함께 연결하고, G8의 제품 변경 없는 최종 review에서 모든 원문/발견 처분과 인도를 대조한다.

## 확인한 근거 한계와 경로 교정

준비 baseline의 원자료 6·실행기 4·제품 파일 969개, 합계 979개는 모두 현재 bytes와 같다. 현재 HEAD는 `77b8f132c056bcb222e7b6ee431742aa4dc1f27e`이며 준비 시점 HEAD와 다른 사실을 제품 변경으로 오독하지 않는다. 비교 출력과 파일별 해시는 `source-comparison.json`에 있다.

원보고 파일 100개는 기록된 SHA와 일치하고, 이 중 판단에 필요한 39개는 실제 결과/선택/소스 판본까지 읽었다. 이 둘은 의미 검토와 다르다. 외부 임시 원보고를 가리키는 **246개 위치 레코드, 236개 고유 경로**는 현재 파일이 없다. `evidence-catalog.json`의 `historical_report_locations`에 해당 B와 정확한 보드 위치를 보존했다. 과거 counts만으로 red/green 검증을 인증하지 않는다. 후속 PR slice에서 필요해진 원보고만 저장소/보존 자료에서 찾거나 현재 코드·같은 반례의 근거로 다시 판단한다. 모든 임시 보고 복구를 일괄 선행 장벽으로 두지 않는다.

R05/R06의 `flows/test_provider_close_native_storage.py`는 없는 과거 경로다. 현재 파일은 `flows/test_provider_native_storage.py`, 클래스는 NativeStorageTests, 메서드는 `test_native_numbers_and_public_blocks_survive_actual_runner_and_repository`다. 현재 정의 위치와 B129의 실제 ID/pass를 확인하여 이번 분류표에서 연결을 교정했다. 기존 공용 계약이나 과거 작업판은 수정하지 않았다.

B129의 전체 결과는 selected 3990, passed 3988, failed 1, skipped 1, successful=false다. 그 뒤 repair 2개 통과를 더해 성공으로 바꾸지 않는다. B129와 현재 사이에는 시험/지원 파일 8개가 달라졌으며 catalog에 좌표가 있다. 따라서 최종 실행은 별도로 필요하다. 제품 시험·T3·변이·공급자 호출은 이번 배정에 따라 실행하지 않았다.

재현 명령은 프로젝트 루트에서 bootstrap의 Python으로 `evidence/build_mapping.py`, 이어 `evidence/validate_mapping.py`를 실행하는 것이다. 첫 작성 시 수동 질문 목록에 K-24가 빠져 생성기가 실패했고, 그 원출력은 `build-attempt-1.txt`에 남겼다. 항목을 보완한 뒤 독립 검사기가 원래 ID 집합·중복·원문·파일 참조·해시·109 추적 항목·25영역 대응을 검사했다. 생성 도구의 이 실패는 제품 시험 실패가 아니다.
