# 사용자 지시: 남은 문서 작업의 배정 방식 개선

2026-10-14 사용자는 문서 작업을 한 phase에서 병행하지 않는 이유를 물었고, 공유 수정 지점별로 구현을 묶으며 독립적인 조사만 병렬화하자는 설명에 대해 **“그렇게 전달”**이라고 지시했다. 이 문서는 운영자가 다음 manager에게 전달하는 현재 사용자 지시다. 현재 phase 021의 실행·완료 조건을 바꾸거나 작업을 다시 시작하라는 뜻은 아니다.

## 다음 manager가 적용할 사항

1. 021 결과를 검수한 뒤 남은 P06~P11 및 관련 N 항목을 문서 번호마다 자동으로 한 phase씩 배정하지 않는다. 기존 followup-packets와 현재 코드에서 실제로 함께 바꾸는 helper·소비 시험·문서·미러의 경계를 기준으로 묶는다. 이미 끝난 P01~P05는 새 반례 없이 다시 열지 않는다. 021에서 미완료가 남으면 그 정확한 범위는 보존한다.
2. 같은 doc_code.py·engine_context.py·직접 소비 시험을 수정하는 가까운 작업들은 한 작업자가 소유하는 유한한 묶음으로 배정한다. 공통 수정 뒤 최종 판본에서 관련 검사를 통합 실행하여, 작은 문서 항목마다 같은 회귀·미러 생성·manager 마감을 반복하는 비용을 줄인다. 진단에 필요한 좁은 검사는 유지하며 개별 기존 단언이나 증거를 생략하지 않는다.
3. 병렬화는 고정된 입력의 서로 독립적인 조사 또는 실제 쓰기 파일이 겹치지 않는 작업에 한한다. 조사 결과는 각자의 report/evidence에 쓰고 같은 phase의 다른 task가 그 미완성 결과에 의존하지 않게 한다. 조사와 구현의 입력 판본이 충돌하면 선후 단계로 나눈다. 병렬 인원이나 task 수 자체를 목표로 삼지 않는다.
4. 공유 코드 통합·미러 생성·공식 검사는 한 담당자가 맡는다. 기존 검사 중 소스 고정, 한 검사 묶음씩, 총 worker 3 이하 규칙을 유지한다. 격리 없는 동시 수정을 허용하거나 새로운 병렬 실행 프레임워크를 만들지 않는다.
5. 묶음은 한 새 세션에서 원문 확인·수정·관련 검증·보고를 끝낼 수 있는 크기로 정한다. 압축 없이 끝내기라는 원래 목표를 유지하며, 무조건 남은 전부를 한 task에 넣거나 batching 판단 자체를 장기 감사 작업으로 만들지 않는다.
6. 다음 plan과 manager decision에 선택한 묶음, 병렬 가능한 독립 조사 유무, 공유 파일과 필요한 검사, 종료 조건을 짧고 구체적으로 남긴다. 병렬화 이득이 없으면 그 이유와 통합한 반복 작업을 명시한다. 구현 배정을 위해 사용자에게 같은 승인을 다시 묻지 않는다.

## 판단 근거와 범위

019와 020의 실제 report.changes 교집합은 22경로다(정본 11·미러 11, 비용 캐시 포함). 공통 doc_code/engine_context와 직접 소비 시험들이 포함되므로 현재 분할 그대로 동시 구현하면 충돌한다. 동시에 이 겹침은 각 문서 묶음마다 같은 수정·검사·마감을 반복하는 비용을 줄일 여지가 있다는 근거다. 이전 로그 기반 manager 시간 약 31%는 검수·문서·독해·기억·커밋·배정을 합한 근사치이며 순수 낭비 시간으로 판정하지 않는다.

이 지시는 작업 배정 방식을 개선한다. 원래 G1~G8, 요구·보존 모집단, 모델 설정(task gpt-6.1-sol/high, manager gpt-6-astra/xhigh), 시간의 소프트 제약, 파일 소유와 원증거 보존은 유지한다. 현재 작업자에게 새 구현을 중간 삽입하지 않고 다음 manager부터 적용한다.
