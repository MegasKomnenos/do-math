# 전체 완료로 이어지는 현재 계획

이 파일은 현재 남김과 다음 판단을 관리한다. 상세한 과거 이력은 sources와 기존 repo 자료에 연결하고 여기에 반복 복사하지 않는다. 상태·근거·구체적 다음 질문 없이 '추가 감사 필요'만 적지 않는다.

## 첫 phase: 001

코드를 더 수정하기 전에 독립적인 세 질문을 함께 닫는다. 모두 writes=[]이며 무거운 검사·T3·변이·실호출은 시작하지 않는다.

| task | 끝낼 질문 | 산출물과 사용처 |
|---|---|---|
| closure-map | 원래 30의무·61보존·P2 12 각각에서 이미 입증한 성질, 확정 공백, 확인 질문, 최종 재실행을 구별할 수 있는가? | 자기 evidence의 requirement-state.json과 과거 검토 처분. manager가 현재 backlog와 우선순위를 결정 |
| document-closeout | 13-C의 현재 실제 문서와 검사기에서 남은 연결을 어떻게 유한하게 끝내는가? 최근 수정은 유지할 가치와 충분한 근거가 있는가? | 실제 문서/생산자/기존 시험별 결속 목록, 유지·교체·제거 판정, 한 문맥에서 끝나는 구체적 packet 후보 |
| gate-readiness | 현재 전체 일반/T3/변이/T4/T5를 어떤 실제 도구·선택·환경·증거로 실행해야 하는가? | gate-readiness.json과 실행 절차. 막힌 외부 조건을 마지막에 처음 발견하지 않게 함 |

세 task는 서로의 중간 결과를 읽지 않는다. 같은 구판 작업표를 각 관점에서 읽는 것은 허용하지만 서로 같은 전수 코드 검토를 반복하지 않는다. closure-map은 현재 상태의 근거 연결, document-closeout은 문서 검사기의 실제 코드, gate-readiness는 실행기·환경 경계를 책임진다. 각 task의 report는 판단 가능한 산문과 원자료 좌표를 담는다.

## 첫 manager가 결정할 것

세 보고와 그 형식 검사를 읽은 뒤 결정에 필요한 원증거를 대조한다. 요구별 원문과 현재 코드가 달라진 경우 둘을 구별한다. report에서 'evidence-only'로 볼 수 있다는 의견은 source 판본·검사 성질이 맞는 범위에서만 수용한다. 매핑만 끝난 과거 재검토 영역은 완료로 바꾸지 않는다.

다음 단계는 고정된 109개 task를 그대로 재파견하는 것이 아니다. 기존 목록의 의미를 보존하면서 다음 상태로 현재 backlog를 정리한다.

- 검토된 성질이 있어 최종 판본 연결만 필요한 항목: 다시 구현하지 않고 해당 G의 최종 증거 대기로 둔다.
- 실제 결함/공백이 확인된 항목: 원문 요구, 재현 입력, 수정 파일, 관련 검증, 끝나는 조건을 붙여 한 work task로 배정한다.
- 사실 하나를 확인해야 하는 항목: 답할 질문·입력·산출물·판정 뒤 행동을 지정한 조사/검토 task로 둔다.
- 최종 관문: 대상·선행 조건·실제 명령·출력·판본을 준비하고 이후 고정판에서 실행한다.

manager는 다음 purpose에서 '이 task가 끝나면 더 할 필요가 없어지는 일'과 '어느 G의 남김이 제거되는지'를 명시한다. 동일 소유자를 계속 하나씩 발견하는 식으로 범위를 늘리지 않는다. 읽기나 보고가 다음 판단을 바꾸지 못하면 더 넓은 조사를 자동으로 이어가지 않는다.

## 구현과 기존 작업 재검토

확인된 공백과 관련 과거 변경을 같은 한정 단위에서 처리한다. 25개 재검토 영역 전체의 완료를 모든 구현의 선행 장벽으로 만들지 않는다. 기존 실제 코드·시험을 재사용하고 source/diff/원보고가 입증한 성질은 계약 변경이나 새 반례가 있을 때만 다시 연다.

전체 범위는 다음 네 묶음으로 남겨 둔다. 첫 보고의 구체적 의존과 위험에 따라 가까운 순서를 확정하며 무관한 발견으로 방향을 바꾸지 않는다.

1. 대기·계수·관측·정산: 모든 지정 상태 공간의 생성, 유지, 해소, 담당자, 후속 호출과 실제 표시.
2. 입력·평가·근거: 역할 변형, 실제 생산/수신, 판정 함수와 교란 축, 원래 평가자 쌍·보존/P2 기대값.
3. 소유자·시간·발동: 실패 격벽, 타 단위 진행, 시간 규칙의 국면, 대상·사건별 실제 발동/비발동.
4. 기동·문서·경계·규모: 설치/기동 판본, 문서 실제 계약, 필수 자료·읽기/출력 한도, 입력 규모와 읽기·해시·복사 비용, 실제 경계/말뭉치.

문서 검사기는 source-owner 전부를 임의로 지원하는 새 추론기로 키우지 않는다. 현재 원문이 참조하는 계약을 실제 반환/공유 계약에 연결하고, 불필요한 결속이나 중복은 제거 후보로 판정한다. DOC-RETURN-ROLE의 _context, REVIEW, TRUST와 이름·정책·읽기 한계는 서로 구분해 종료한다. AST 제거 개수는 전체 완료율이 아니다.

새 API/공유 계약을 병렬 개발하려면 먼저 seams에 실제 정본·의미·오류·공유 검사와 실제 연결 책임을 정의한다. 그 전에는 같은 phase의 미완성 구현에 기대는 검사를 배정하지 않는다. 반복 검증의 명확한 병목이 있으면 같은 경로·단언의 전후 근거로 그 좁은 병목을 개선할 수 있다. 예산만 맞추려는 우회는 하지 않는다.

## 최종 관문과 완료 review

필요한 실제 경계 호출·녹화와 코드 수리를 먼저 끝내 최종 판본을 고정한다. G4 전체 일반 → G5 fresh T3 → G6 정상 기준/현재 함수 전체 극단 변이의 근거를 확보하고 G7의 실제 경계·녹화 판본을 연결한다. 측정/변이의 실제 전체 모집단은 현재 코드에서 확정한다. 오래된 함수 수나 분할 개수를 성공의 분모로 사용하지 않는다.

후속 변경이 생기면 어떤 기존 증거가 무효화됐는지 기록하고 그 범위의 검증을 교체한다. 최종 동일 판본 조건이 필요한 전체 관문은 필요한 시점에 다시 완결한다. 중간 부분 통과를 합산하지 않는다. 유효한 기존 실제 경계 결과의 재사용은 코드·도구 판본과 성질을 대조해 판단한다.

완성됐다고 판단하면 review kind의 phase를 배정한다. 고정된 제품을 대상으로 요구 충족/검출력·기존 개선 보존/실환경·인도 증거를 독립적으로 검토할 수 있다. 모든 G를 충족하는 근거와 미해결 finding의 처분을 manager가 확인해야 next:null을 제출한다. 문제를 발견하면 정확한 work task 뒤 다시 review한다. 검토 인원이나 반복 횟수 자체를 종료조건으로 삼지 않는다.
