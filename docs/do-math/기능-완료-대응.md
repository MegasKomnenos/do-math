# do-math 기능 판본 5 완료 대응

이 문서는 최종 보고서와 통합 설계의 기능 목적을 2026-09-20 공유 작업 트리의 구현·소비·증거에 대응한다. 함수·schema·시험 파일의 존재를 완료로 세지 않는다. 생산자, 저장, 다음 소비자가 같은 의미를 사용하고 그 범위의 실행 증거가 있을 때만 `연결·검증`으로 기록한다.

## 설치 문서 정합화의 확인 범위

DOCS는 최종 보고서·독해 합의와 2026-09-21 구현 사본의 조사 결과를 현행 생산자·소비자와 대조했다. CLI의 초기화·예산/판본·관찰·단일 제출·접수와 편입·복구 설명을 같은 정상 흐름으로 다시 구성했다. 예시의 사용자 선택·실측값을 승인 사실과 구별한다. 최종 전체 독해·합의 대조와 설치 사본 미러는 MAIN이 맡는다.

운영 수리의 현행 경로는 응답 편입 뒤 `repair_execution.complete_repair`가 종료된 실행의 봉인 catalog/detail 입력을 Git 원문으로 복원·해시 검증하고 명시적 후속을 여는 것이다. 임시 maintenance 수리·독립 AI 검증 단계는 제거됐다. 지원하지 않는 수리와 남은 의미 판단은 실제 다음 소유자에게 돌아가며 기동 불능의 설치 복구 launcher는 별도로 유지된다.

문서 자기 점검 시점의 남은 연결은 다음과 같다. 이후 담당 결과의 완료 통지만으로 닫지 않고 최종 코드와 실행 증거를 다시 대조한다.

- 공개 `decision --file`은 JSON 파일을 한 번 읽어 payload를 `config.change`로, 같은 정확한 원문을 control text로 전달한다. `kind=import_approval`은 `GovernanceEngineMixin._governance_control`을 거쳐 `governance.apply_import_control`로 전달된다. 적용기는 사용자 출처·정확한 수입 묶음·검사·unit 해시와 비어 있지 않은 승인 원문을 대조하고, 적용 뒤 초기화의 다음 action을 연다. 이 연결은 현재 코드 대조 결과이며, 공개 CLI 경로의 최종 회귀 증거는 별도로 붙인다.
- 새 저장 계약은 schema 2의 `immutable_input.text/sha256/bytes` 하나로 정확한 코드 포인트열과 UTF-8 해시·크기를 보존하며 이름·키·원문을 정규화하거나 Base64 중복 원문을 만들지 않는다. 정식 생성 뒤 v9 오프라인 검사 84개가 통과하고 과거 `source_conflicts` 고정 출력이 제거됐지만, 통합 저장 회귀는 아직 확인하지 않았다. `.agents`는 치환 생성물이며 원시 미러 동일성은 규칙이 아니다.
- 현행 IMPACT 소비는 같은 S0의 묶음 전체·변경별 계획과 지정 검토만 제외한 자기 영향 계산, 승인 합집합의 단일 적용, 선택적 정규 KN ULID `replacement_id`, 후보 전건 뒤의 명시적 형제 참조 검사를 연결한다. `submission_contract.command --new-knowledge-id`는 형제 참조에 쓸 canonical KN ID만 생성하며 예약·권한·공개 효과는 없다. 최종 편입은 전역 중복과 CAS를 계속 검사한다. 집중 검사 6개는 통과했지만 전체 편입·CAS 회귀는 미실행이다.
- 원 판정 재심사는 일반 K 동일성 검토와 구별된 정확한 원 IA·전제·정책·독립 계보를 요구한다. KNOWLEDGE의 소유 API와 중앙 진입·반환·유한 활동 종결의 연결은 별도 완료 조건이다.
- 신뢰 전환의 변경 결과는 staged 검토의 실제 봉인된 결과를 소비해야 한다. LIFECYCLE의 요청·수신과 KNOWLEDGE의 runtime 결박 활성화가 같은 원자 적용 계약인지 확인한다.
- 연구 관찰은 `{source,operator,subject_kind,unit}` 항목의 `observation.rule_bindings`와 필수 window를 요구한다. 첫 tick의 미측정을 0이나 즉시 운영 호출로 바꾸지 않고 첫 관찰 구간 뒤의 미측정만 진단한다. 관찰 52개·형식 16개 검사와 실 Windows Job probe는 통과했지만 lifecycle 공개 시험 두 건은 멈췄으므로 전체 결과는 `PARTIAL`이다.
- 현행 FLOW API는 `submit_draft(draft_path, preview?, wait_seconds?)`와 CLI `--output/--submit/--preview/--wait-seconds`다. 최종 경로는 `draft_path`만 보내고 중앙이 바이트를 한 번 포착해 검사·봉인하며, 로컬 검사·preview는 선택적 진단이다. `.control/` 관리 경로와 봉인 없는 provider final의 진단 전용 처리를 대조했고 `PublicGitFlow`는 실제 Windows Job으로 시작·종료를 확인한다. 집중 검사 85개 중 84개가 통과하고 symlink 1개가 skip됐지만 전체 공개 흐름은 미검증이다.

문서의 JSON 문법·실제 검사기 대조와 링크 확인은 제품 공개 활성화, 실제 AI·Lean 환경, 연구 효능의 검증과 구별한다. 상세 근거와 수정 문서 해시는 `임시/do-math-implementation-20260920/results/DOC_REBUILD.json`에 남긴다.

## 증거 상태

- `구현`: 소유 모듈에 현재 계약을 표현하는 코드가 있다.
- `소비`: 실제 중앙 생산자·수신자·후속 소비자가 같은 ID·판본·해시·권한·범위를 사용한다.
- `검증`: 고정 판본, 명령, 입력, 결과와 실도구·대역 범위를 확인했다.
- `부분`: 구현이나 소비·검증의 일부만 확인했다.
- `미평가`: 성공·실패를 판단할 실행 증거가 없다.
- `역사`: 과거 동결 판본에만 상대적인 증거다.

현재 전체 판정은 `PARTIAL`이다. FLOW·IMPACT·EXECUTION 담당의 `complete`는 각 소유 범위의 구현과 집중 검증에 한정되며 전체 통합 완료를 뜻하지 않는다. D10의 계약 식별자 선택도 전체 구현 완료를 뜻하지 않는다. D08은 v9 규범 묶음의 오프라인 검사 통과만으로 닫지 않고, D09의 연구 효능 비교는 `미평가`로 둔다.

## 설계 17.3절의 워크스루

기존 열두 워크스루는 위 기능 목적 표와 별개의 역사적 검증 집합이다. 최신 EVIDENCE 고정 사본은 그 판본에서 32건 중 29건 통과·3건 실패였고, 열두 흐름 가운데 열 개가 지정한 도메인 경로에서 통과했으며 두 개는 다음 소비자의 실제 계약 결함에서 실패했다. 17.3절에는 이후 단일 제출과 같은-S0 편입 흐름이 추가됐으므로 이 수치를 현행 전건 통과로 옮기지 않는다. 모델·외부 서비스 응답은 대역이며 추가 미실행 범위는 `implementation-v5/traceability.json`의 `walkthroughs.gaps`와 최종 통합 결과가 소유한다.

V45·V112·V82를 포함한 벡터 대응은 시험 이름이나 파일 존재로 통과 처리하지 않는다. 최신 대응표에는 59개 gap과 186개 partial이 남아 있다. 실제 CLI·Lean·OS를 사용한 단계와 대역 단계를 합치지 않으며, 자연적인 PID 재사용·모든 시작 실패 시점·실제 장기 부하의 제어 응답성은 전건 입증하지 않았다.

## 규범 묶음, 실행 검증과 연구 효능

v9 규범 명세의 오프라인 검증은 `validation-report.json`이 고정한 input basis에서 schema·레지스트리·생성물·예제·원천 대응을 검사한다. 이 통과를 다음과 혼동하지 않는다.

- 설치 실행기의 실제 역할 입력과 소비 API가 같은 의미를 쓰는지
- V·Q 전건을 실제 실행했는지
- 공개 CLI가 새 인스턴스부터 전체 연구 흐름을 완주하는지
- 실제 모델·Lean·Windows·원격 효과가 필요한 능력을 제공하는지
- 연구 성능이나 수학 판단이 더 정확하고 비용 효율적인지

앞 네 항목은 D08과 기능 판본 5 검증에 남아 있고, 마지막 항목은 D09의 별도 비교 연구다.

## 전체 완료 조건

다음 전건이 충족되기 전에는 기능 판본 5를 `DONE`으로 바꾸지 않는다.

1. 남은 생산자-저장 schema와 중앙 callback 접점을 해소하고 현재 소스를 동결한다.
2. 공개 init→active→prepare→review→plan→work→assessment→next-plan과 정지·재개·수리·조회 흐름을 실제 임시 Git에서 완주한다.
3. 관련 전체 회귀, 설치 구조, 필요한 실제 Lean·Windows Job·process·provider 검증을 같은 판본에서 실행한다.
4. 열두 워크스루와 벡터 대응표의 실패·partial·gap을 실제 assertion과 증거가 생긴 범위에서만 갱신한다.
5. `.claude` 정본과 설치 사본, 입력 manifest, 문서와 코드의 해시·계약 판본을 대조한다.
6. 메인의 전체 독립 독해와 최종 보고서 합의 대조를 통과한다.

## 최종 통합 대응을 붙일 자리

MAIN은 모든 변경을 합친 같은 Git snapshot에서 schema 2 저장, 단일 제출의 봉인·접수·수신, 같은-S0 영향 검토·결합 적용, Windows Job 회수, 전체 회귀의 실제 명령과 결과를 이 표에 연결한다. 실제 모델·Lean·장기 재시작과 연구 효능은 별도 관찰로 유지한다. 아직 제공되지 않은 값은 완료로 쓰지 않는다.

현재 판정은 `PARTIAL`이다. 규범 묶음의 오프라인 통과, 소유 시험의 통과, 공개 기능의 검증과 연구 효능 평가는 서로 대체하지 않는다.
