### L1-01 — 복구가 원장 신뢰를 확인하기 전에 원장 쓰기를 요구한다

**종류와 결론: 문면 충돌, 높음.** 14.2절의 첫 복구 행위는 7.4절과 14.3절의 쓰기 전제보다 앞서 있어, 중앙 원장이 손상된 정상 복구 입력에서는 규칙 전건을 함께 지킬 수 없다.

**근거.** 7.4절은 실행기가 “자기 쓰기 전에” 원장이 가리키는 연구 커밋과 연구 ref를 검사하고, 영구 불일치가 있으면 공용 적용을 중지한다고 정한다(405–407행). 14.2절은 새 실행기가 잠금을 얻은 뒤 먼저 새 `engine_id`를 “기록”하고 배정을 닫은 다음, 복구 검사 1번에서 두 Git 사슬과 연구 커밋을 확인하게 한다(757–764행). 14.3절은 중앙 원장 신뢰가 깨졌으면 새 쓰기를 중지한다고 다시 정한다(783–785행). `engine_id`의 영속 위치는 `runtime` 가족으로 지정돼 있다(893–896행).

**성립하는 시간선과 영향.** 이전 실행기 소실 뒤 runtime ref의 커밋이나 `state.json`의 연구 커밋 포인터가 훼손됐다고 하자. 새 실행기는 잠금을 얻는다. 14.2절의 순서를 따르면 아직 두 사슬과 포인터를 확인하지 않은 상태에서 불신 가능한 runtime 사슬에 `engine_id`를 쓴다. 이후 1번 검사에서 훼손을 발견하면, 이미 7.4절의 쓰기 전 검사와 14.3절의 쓰기 금지를 위반했다. 반대로 먼저 검사하면 14.2절의 명시 순서를 어긴다. 손상된 부모 위에 복구 시작 커밋을 추가하면 원래 손상과 새 복구 사실의 경계도 흐려진다.

**반박 검토.** 3.1절의 독점 잠금은 동시 작성자를 막을 뿐 원장 내용의 신뢰를 복원하지 않는다(107–118행). `engine_id`를 메모리에만 둔다고 읽으면 16.4절의 runtime 필드와 “기록”의 영속 효과가 사라지고, 메모리는 정본을 대신하지 못한다는 7.1절과도 맞지 않는다(323–332행). 따라서 다른 절이 이 순서 충돌을 해소하지 않는다.

**개선 방향.** 복구를 두 단계로 닫는다. 잠금 획득 뒤에는 배정을 프로세스 내부에서 닫고 두 ref·커밋·`state.json`을 읽기 전용으로 최소 검증한다. 검증을 통과한 경우에만 `engine_id`와 `recovery_started`를 첫 runtime 변경으로 원자 기록한다. 검증에 실패하면 정본에는 쓰지 않고, 정본 밖의 진단 출력과 정확한 OID·오류를 보존한 뒤 저장 복구로 상신한다. 이 변경은 새 권한을 만들지 않고 쓰기 순서만 일치시킨다.

### L1-02 — 공통 실행 요청의 필수 필드가 작업 AI, 운영 AI, 기계 작업 사이에서 닫히지 않았다

**종류와 결론: 필드 계약 미정, 높음.** `actor_kind`별로 달라야 하는 `budget kind`, 다음 운영 검토 시각, 실행 기한과 프로필 필드의 존재 조건이 정의되지 않았다. 이 문제는 기술 선택의 미정이지, 기계 작업에 AI 예산을 실제로 쓰라고 한 논리적 결론은 아니다.

**근거.** 6.1절은 `actor_kind=machine`도 공통 상태를 사용하지만 AI 예산을 예약하지 않고, 모델·tokenizer·원격 모델 ID가 부재하며 도구 manifest와 호스트 한계를 대신 쓴다고 한다(247–251행). 바로 다음 문단은 조건 없이 모든 요청이 예산 종류, 실행 프로필, “다음 운영 검토 시각”을 고정한다고 한다(253행). 반면 12.1절은 다음 운영 검토 시각을 작업 예산 AI에만 두고, 운영 AI와 기계 작업에는 실행 기한과 도구 실패 검사를 적용하며 운영 실행을 위한 재귀 점검은 열지 않는다고 한다(656–660행). 16.2절도 작업 AI의 다음 검토 시각과 운영 AI·기계 작업의 실행 기한을 별도 프로필 항목으로 구분한다(845–855행). 필드 부재와 `null`은 스키마가 하나의 의미를 정했을 때만 허용한다(381–385행).

**성립하는 정상 시간선과 영향.** 10.3절의 긴 Lean 검사를 `actor_kind=machine` 실행으로 만든다고 하자(509–522행). 이 요청에는 AI 예약이 없어야 하고 운영 AI의 재귀 점검도 없어야 한다. 그러나 6.1절의 요청 필드를 그대로 검사하면 예산 종류와 다음 운영 검토 시각이 필요하다. 구현자는 의미 없는 값을 발명하거나, 필드를 누락해 공통 요청 검사를 실패시키거나, 기계 작업에 AI 예산·운영 점검을 잘못 붙이는 셋 중 하나를 택해야 한다. 운영 AI도 다음 점검 시각을 넣으면 12.1절의 재귀 점검 금지와 충돌하고, 빼면 6.1절의 무조건 필드 목록과 충돌한다.

**반박 검토.** 6.1절은 모델 관련 필드의 기계 작업 부재만 명시한다. 예산 종류와 다음 검토 시각의 조건부 부재는 명시하지 않는다. 실행 기한이 다음 검토 시각을 대신한다고 읽을 수도 있지만, 12.1절과 16.2절은 둘을 서로 다른 제어로 이름 붙인다. 따라서 구현자가 임의로 조건을 만들지 않고는 닫히지 않는다.

**개선 방향.** 공통 요청 스키마에 판별 공용체를 둔다. `actor_kind=ai`일 때만 `budget_kind`를 요구하고, 그중 작업 예산 AI에만 `next_operational_review_at`을 요구한다. 운영 AI와 기계 작업에는 `execution_deadline`을 요구한다. 기계 작업은 정확한 도구/호스트 프로필을 요구하고 AI 전용 필드는 금지한다. 각 분기에서 부재와 `null` 중 하나를 정규 표현으로 택한다.

### L1-03 — 실제로 호출하는 두 AI 활동의 영속 소유자와 스키마가 없다

**종류와 결론: 경로 누락, 높음.** 작업 계약 검토와 의도 해석은 필수 AI 활동으로 정의되지만, 공통 실행의 직접 소유자 및 16.4절의 닫힌 스키마 가족으로 어떻게 표현하는지 정하지 않았다.

**근거.** 3.2절은 작업 계약 검토와 의도 해석을 각각 작업·운영 예산의 AI 활동으로 두고 모든 AI 활동에 공통 실행 계약을 적용한다(120–135행). 5.4절은 작업 계약 검토가 `approved`, `revision_required`, `unresolved`를 판정한다고 한다(236–240행). 13.1절과 초기화 3단계는 의도 해석 실행과 독립 대조를 실제로 요구한다(700–708행, 743–755행). 그런데 실행 요청은 대상 과제·검토 ID를 고정하고(253행), 실행마다 직접 후속을 소유하는 “과제·검토·계획 기록 하나”를 요구한다(312–318행). runtime은 `activities/<id>`에 계획·검토·점검을 저장한다고만 한다(347–357행). 객체 필드를 닫는 16.4절의 가족 목록에는 `plan`, 수학 `review-activity`, `operational-review`, `assessment`, `decision`은 있지만 작업 계약 검토 활동이나 의도 해석 활동의 활동 가족은 없다(888–923행).

**성립하는 정상 시간선과 영향.** 새 인스턴스가 14.1절 3단계에 도달해 첫 의도 해석 AI를 요청한다. 이는 아직 연구 계획이 아니고, 연구 수행 과제도 아니며, 수학 검토나 운영 복구 점검도 아니다. 실행 요청을 만들려면 어떤 ID를 대상으로 하고 어떤 기록이 후속을 소유하는지 정해야 하지만 문서에는 선택 기준이 없다. `decision`은 해석 활동의 산출 후보를 담을 수 있어도 실행의 단계·미완료·재개를 소유하는 활동 기록은 아니다. 작업 계약 검토도 같은 문제가 생기며, 판정값 셋을 어느 닫힌 `assessment` 종류로 저장할지 정의되지 않았다. 실패 뒤 6.6절의 반환 대상도 결정할 수 없다.

**반박 검토.** “검토”를 넓게 읽어 두 활동을 모두 `review-activity`에 넣을 수는 있다. 그러나 11.4절의 `review-activity`는 수학 제안 판본, 필수 관점, 보충 조사와 최종 판정 단계를 소유하며 이 두 활동의 입력·결과와 맞지 않는다(588–619행). `assessment`의 “동일성·목표 등”을 개방적 예시로 읽더라도 활동 생명주기와 직접 후속 소유권의 매핑은 생기지 않는다. 이 지적은 열거를 닫게 읽어서 만든 것이 아니라, 문서가 실제로 명령한 정상 초기화 실행을 현재 필드로 구성할 수 없다는 지적이다.

**개선 방향.** 가장 단순한 안은 공통 `activity` 봉투를 추가해 `activity_kind`, 대상 참조, 단계, 직접 후속 소유자, 실행 목록, 결과·남은 범위를 소유하게 하고, `intent_interpretation`과 `task_contract_review`의 닫힌 결과값과 하위 필드를 정의하는 것이다. 기존 가족을 재사용하려면 두 활동이 어느 가족과 owner 종류를 쓰는지, 실행 요청의 target ID 공용체와 실패 반환 위치까지 명시해야 한다.

### L1-04 — 외부 행동의 `prepared` 이후 중단·복구 경로가 상태 집합에 없다

**종류와 결론: 실패 후 복귀 경로 누락, 높음.** 외부 행동을 원장에 준비한 뒤 실제 호출 전 정지되거나, 호출 시작 여부를 알 수 없는 채 실행기가 소실되는 경우의 전이와 다음 소유자가 닫히지 않았다.

**근거.** 외부 행동은 실행 전에 요청·허가·재시도 규칙을 기록하고, 상태를 `prepared`, `confirmed`, `failed`, `unknown`으로 닫는다(718–724행). 전송 뒤 결과 기록 전에 끊긴 경우만 `unknown` 전이를 설명한다(722–724행). 권한 철회는 새 행동을 막고 종료를 예약하며(710–716행), `stopping`에서는 새 실질 행동과 도구 요청을 금지한다(261–265행, 290–296행). 복구는 진행 중 외부 행동의 마지막 기록을 확인하고(757–769행), 외부 행동 원장을 재개 입력에 포함한다(689–695행, 724행). 그러나 `prepared` 상태에서의 복구·취소 규칙은 없다.

**성립하는 시간선과 영향.** 실행기가 `prepared`를 커밋한 직후 외부 호출 전에 사용자가 허가를 철회했다고 하자. 호출은 금지되지만 `confirmed`도 `unknown`도 아니다. `failed`를 “실제로 호출했으나 실패함”과 “호출하지 않고 취소함” 중 어느 뜻으로 쓸지 정의되지 않았고 `cancelled`/`not_sent` 상태도 없다. `prepared`를 그대로 두면 이후 복구가 같은 행동을 계속할지 영구 보류할지 판단할 수 없다. 또 `prepared` 커밋 직후 실행기가 소실되면 새 실행기는 호출이 시작되지 않았는지, 외부로 나갔으나 영수증만 없는지 원장만으로 구별하지 못할 수 있다. V30은 “외부 전송 뒤”라는 사실이 이미 알려진 경우만 시험하므로 이 경계 창을 덮지 않는다(971–974행).

**반박 검토.** action ID, 멱등성 키, 외부 조회는 중복 재전송을 막는 근거를 준다. 그러나 조회가 “호출 안 됨”을 입증했을 때 같은 action을 이어갈 조건, 허가가 사라졌을 때의 종결 상태, 호출 시작 여부 자체가 불명일 때 `prepared → unknown`으로 옮기는 주체와 시점을 정하지 않는다. 실행 종료의 `cancelled`는 execution 상태이지 `external-action` 상태이므로 대신 쓸 수 없다.

**개선 방향.** `prepared → confirmed | failed | unknown | cancelled` 전이표를 둔다. 복구 시 외부 호출이 시작되지 않았음을 어댑터가 입증하고 허가가 여전히 유효하면 같은 action ID로 승인된 재시도 규칙을 계속 적용한다. 시작 여부나 결과를 입증하지 못하면 `unknown`으로 옮기며, 시작되지 않았고 허가가 철회됐거나 실행이 취소됐으면 `cancelled`로 닫는다. `failed`는 외부 효과가 없다는 확정 실패 영수증이 있는 경우로 경계를 정한다. 각 상태에 다음 소유자와 재관찰 조건을 붙인다.

### L1-05 — `tree_record_ref`가 봉인된 판정의 정확한 입력을 후속 커밋에서 다시 결박할 수 있다

**종류와 결론: 참조 계약 충돌, 높음.** `tree_record_ref`에 대상 파일 해시가 없어서, 같은 ID의 대상 기록이 후속 연구 커밋에서 수정되면 봉인된 판정의 참조 의미가 바뀔 수 있다. 이는 정확한 판본 결박과 봉인 규칙을 깨뜨린다.

**근거.** 동일성 판정은 정확한 형식 산출물·해설·검토 방침 판본을 연결해야 한다(64–68행). `record_ref`는 커밋 OID와 파일 SHA-256을 가지지만 `tree_record_ref`는 같은 트리의 기록 ID만 가지며, 참조를 담은 기록과 같은 커밋 트리에서 해석한다(361–373행). 새 기록끼리 같은 후보 묶음에서 참조할 때 이 형식을 쓰게 한다(373행). 판정의 본문과 입력은 봉인 뒤 수정하지 않는다(539–541행, 637–639행). 한편 공용 변경은 기존 기록의 수정·철회를 지원한다(503–507행).

**성립하는 시간선과 영향.** 연구 커밋 C1에서 새 해설 E1과 동일성 판정 A1을 함께 편입하고, A1이 E의 ID를 `tree_record_ref`로 가리킨다고 하자. 후속 커밋 C2가 같은 E ID의 파일 바이트나 lifecycle을 수정하고 A1 파일은 그대로 운반한다. C1의 A1은 E1을 가리키지만 C2 트리에서 읽은 동일한 A1 바이트는 E2를 가리킨다. 그러면 봉인된 A1의 입력이 바뀌며, C2의 A1을 정확히 참조한 소비자가 과거 `match`를 E2에 대한 판정으로 읽을 수 있다. 의미가 보존된 표기 수정이라도 판정은 “정확한 해설 판본”에 대한 것이므로 바이트 재결박은 허용되지 않는다.

**반박 검토.** C1의 과거 커밋은 보존되므로 A1을 항상 C1의 `record_ref`로 참조하면 E1을 복원할 수 있다. 영향 처리도 변경된 의존의 사용을 정지시킬 수 있다(524–528행). 그러나 문서는 이후 소비자가 A1의 탄생 커밋만 참조해야 한다고 요구하지 않고, `tree_record_ref` 자체를 권위 참조로 허용한다. 영향 처리는 사용 효력을 다룰 뿐 봉인된 판정 기록의 입력 정체성이 C2에서 달라지는 일을 막지 않는다. “의미가 바뀌면 새 ID” 규칙도 질문·정의·명제의 의미 변화에 초점을 두며(361–364행), 정확한 해설 바이트나 lifecycle 변경의 재결박을 일반적으로 금지하지 않는다.

**개선 방향.** `tree_record_ref`에 대상 기록 ID와 대상 파일 SHA-256을 함께 넣는다. 같은 후보 트리에서는 커밋 OID 없이도 대상 바이트를 정확히 결박할 수 있고, 후속 커밋에서 대상이 바뀌면 기존 참조가 조용히 재결박되지 않고 참조 폐쇄 검사에 실패한다. 판정·계약·허가처럼 봉인 대상은 탄생 커밋의 정확한 `record_ref`로만 재사용하도록 소비 규칙도 명시한다.

### L1-06 — 운영 점검의 일부 처분은 제안 뒤 적용 주체와 복귀 좌표가 없다

**종류와 결론: 권한·절차 경로 미정, 중간.** 운영 점검이 제안할 수 있는 `과제 변경·종결`과 의미를 바꾸는 입력·환경 수리에 대해, 누가 어떤 활동으로 검토·적용하고 실패 뒤 어디로 돌려보내는지가 12.4절에 없다.

**근거.** 운영 점검자는 계속, 입력·환경 수리, 체크포인트 재개, 처음부터 재시도, 과제 변경·종결, 사용자 결정 요청을 “제안”한다(674–687행). 적용 절은 계속과 다음 시각, 의미 보존 수리의 직접 적용을 정하고, 재개·재시작에는 다른 운영 검토의 확인을 요구하며, 목적·권한·외부 효과 변경에는 사용자 허가를 요구한다(689–695행). 그러나 사용자 권한 변경까지는 아니지만 과제 의미를 바꾸는 수정이나 과제 종결을 누가 확정하는지는 쓰지 않는다. 작업 계약 변경은 변경안 반환과 새 판본을 요구하고(214–216행), `closed`는 정당한 처분과 잔여 범위·이전 근거를 요구한다(218–234행). 실행기는 수학적·의미 판정을 직접 하지 않는다(105–107행).

**성립하는 시간선과 영향.** 운영 점검이 현재 체크포인트로는 계약의 일부 범위가 수행 불가능하다고 확인하고, 기존 사용자 허가 안에서 범위를 후속 과제로 이전한 뒤 현재 과제를 닫자고 제안한다고 하자. 사용자 허가를 새로 요구할 목적·권한·외부 효과 변경은 없을 수 있다. 실행기가 곧바로 적용하면 운영 점검의 “제안”을 과제 의미 판정으로 승격한다. 적용하지 않으면 새 계약 판본을 작성할 주체, 작업 계약 검토를 열 주체, 현재 과제를 `waiting`으로 돌릴지 여부와 재개 사건이 없어 후속이 끊긴다.

**반박 검토.** 6.6절의 “다음 소유자”와 9절의 연구 계획은 일반적인 환류 장치를 제공한다. 그러나 12.4절은 해당 처분을 계획으로 반환한다고 말하지 않으며, 어떤 상태와 대기 종류를 기록하는지도 정하지 않는다. 일반 환류의 존재만으로 권한 있는 적용 경로가 한 가지로 정해지지 않는다.

**개선 방향.** 처분별 적용 표를 완성한다. 과제 의미·완료 기준·범위를 바꾸거나 닫는 제안은 현재 실행을 안전하게 끝낸 뒤 해당 과제를 `waiting`으로 두고, 정확한 제안·근거를 작업 계약 작성자와 독립 계약 검토 또는 연구 계획에 보낸다. 그 판정이 새 revision이나 `closed` 처분을 원자 적용한다. 사용자 결정이 필요한 분기는 `user_decision`, 기술·검증 입력을 기다리는 분기는 해당 `wait_kind`와 재관찰 사건을 기록한다.

## 검증을 통과한 중요한 부분

- 과제 상태, 실행 상태, 실행 종료 종류, 수학 판정과 목표 상태를 서로 다른 축으로 둔 구분은 문서 전체에서 대체로 유지된다. 특히 `output_accepted`를 수학적 승인으로 읽지 않고, `execution_incomplete`에 허위 의미 판정을 넣지 않는 규칙이 후속 검토·편입과 일치한다(218–276행, 493–501행, 603–635행).
- 정상 AI 실행의 `queued → starting → running → stopping → ended` 흐름과 제출 의도·권한 회수·종료 장벽·예약 반환 순서는 상태와 권한의 선후를 일관되게 분리한다(255–310행). V08–V13과 V43도 주요 소실 창을 다시 검사한다(949–956행, 986행).
- 작업·운영 AI 예산의 분리, 다중 공급 제약에서의 전건 원자 예약, 종료 확인 전 예약 유지 규칙은 정상 시간선과 원격 종료 미확인 시간선에서 서로 맞는다(150–188행). L1-02는 이 예산 원리 자체가 아니라 기계·운영 실행 요청 필드의 조건부 표현 문제다.
- 형식 타당성, 해설 동일성, 목표 충족, 사용자 허가와 실행 상태를 분리한 권위 계약은 수학 검토의 `match/mismatch/unresolved`, 목표 감사와 판정 사용 정지에 걸쳐 유지된다(52–68행, 603–651행). 판정 불일치를 곧바로 확정 불일치나 승인으로 바꾸지 않는 V21도 집계표와 맞는다.
- 두 ref의 일관된 읽기 쌍, 공용 편입의 예상 OID 트랜잭션, 오래된 원장으로 진행 실행을 덮지 않는 규칙은 정상 편입과 동시 원장 사건을 구별한다(403–407행, 509–522행). L1-01은 정상 편입이 아니라 중앙 원장이 이미 불신 가능한 복구 시작 경로에 한정된다.

## 남은 불확실성과 읽지 않은 범위

L1-02, L1-03, L1-04, L1-06은 문서가 선택해야 할 스키마·전이·소유권이 비어 있다는 판정이다. 특정 구현이 반드시 오작동한다고 단정하지 않는다. 다만 0절이 구현자에게 원문 밖 의미 선택을 추가하지 말라고 요구하므로, 이 빈칸을 구현자가 임의로 채운 상태는 구현 완료로 판정할 수 없다(20행).

실제 Windows Job, Git ref 트랜잭션, 모델 어댑터와 JSON Schema의 구현 가능성은 검사하지 않았다. 기존 설계와 사용자 대화에 비추어 이 초안이 의도에 충실한지도 검사하지 않았다. 다른 원천이 위 설계 의도를 설명할 수는 있지만, 이 보고서의 내부 정합성 반례를 해소하려면 최종 계약 문면에도 그 조건이 들어와야 한다.
