# do-math 통합 설계 초안

작성일: 2026-09-06

개정: 일곱 렌즈 적대적 검토 후 2차 초안. 지적별 채택·반박과 원문 근거는 [종합 판정](종합-판정.md)에 기록한다.

<a id="d00"></a>
## 0. 문서의 지위와 구현 범위

이 문서는 수학 연구를 지속적으로 수행하는 do-math의 새 설계 초안이다. 사용자와 검토한 오버뷰를 실행 계약으로 구체화한다. 현행 `통합-설계.md`를 대체하거나 기존 인스턴스에 새 권한을 부여하지 않는다. 초안이 정본으로 채택되기 전에는 이 문서의 필드·상태·명령을 기존 구현의 계약으로 사용하지 않는다.

이 초안은 다음 선택을 채택한다.

- 기계 실행기 하나가 인스턴스의 실행권한, 예산과 정본 갱신을 소유한다.
- 연구 수행·수학 검증의 작업 예산과 배정·점검·복구의 운영 예산을 분리한다.
- 모든 AI 활동에 같은 실행 생명주기를 적용한다.
- 연구 후보는 연구 기록으로 남기고, 실행할 일이 정해졌을 때 작업 계약을 만든다.
- 과제의 대기·완료, AI 실행의 종료, 산출물의 공개와 인증을 각각 판정한다.
- 인증 활동은 확인된 동일성·불일치·미해결을 구분해 종료하고 남은 연구를 환류한다.
- 원자료는 보존하고, AI 입력은 이번 판단에 필요한 범위로 구성한다.

독자는 구현자와 후속 설계 검토자다. 이 문서는 구조와 행동의 계약이다. 권한·판정·전이의 의미는 그대로 구현하며, 실제 JSON Schema·명령 입력·정규 바이트는 16.4절의 규범 스키마 작성 단계에서 확정한다. 가족 표만으로 기계 명세가 완성됐다고 보지 않는다. 구현 중 새로운 의미 선택이 필요하면 도구가 임의로 정하지 않고 해당 계약과 검토 근거를 먼저 개정한다.

초기 구현은 한 Windows 호스트와 하나의 Git 객체 데이터베이스를 사용한다. 여러 컴퓨터의 공동 운전과 기존 인스턴스의 자동 변환은 포함하지 않는다. 기존 기록은 원래 계약과 함께 보존하고, 변환이 필요하면 별도 변환 계획을 검증한다. 새로운 스키마나 명령이 이미 구현돼 있다는 주장은 이 문서에 없다.

새 이름의 해석을 분리하기 위해 초안 스키마의 이름공간은 `do-math-draft/<family>/2`로 한다. 정본 채택 때 계약 식별자를 확정하며, 초안과 현행 스키마를 같은 판본으로 취급하지 않는다.

### 0.1 이 단계에서 확정하지 않는 값

다음 값은 실제 인스턴스 생성 때 사용자의 승인 범위와 실행 환경으로 정한다. 값이 없으면 초기화 상태에서 보고하고 해당 실행을 시작하지 않는다.

| 항목 | 필요한 결정 또는 사실 |
|---|---|
| 연구 헌장 | 목표, 포함·제외 범위, 부분 성과와 목표 해결의 기준 |
| 실행 허가 | 허용 기간·자원·외부 효과, 정지 조건 |
| 대화 소실 정책 | 대화 세션 소실 뒤 승인된 연구를 계속할지 정지할지 |
| 예산 | 실제 공급 제약별 작업·운영 용량과 프로필별 소비 제약 |
| 실행 프로필 | 실제 호출 가능한 모델·노력, 입출력 한도, tokenizer와 어댑터 판본 |
| 신뢰 환경 | Lean·Mathlib·기초 프로필의 정확한 판본과 해시 |
| 검토 방침 | 필요한 관점과 독립 검토의 구성, 검토 활동의 실행 한계 |
| 외부 행동 | 전송·공개·유료 자원·계정별 허용 범위와 재시도 조건 |

선택 가능한 값의 동작은 본문이 정한다. 값이 없다는 이유로 초안 저작을 멈추지는 않지만, 실운전에서 임의의 기본 권한을 만들어 사용하지 않는다.

<a id="d01"></a>
## 1. 목적과 신뢰 경계

do-math는 사용자가 승인한 범위에서 수학적 질문을 탐구하고, 실제 결과를 다음 연구 판단에 반복해서 반영한다. AI는 방법과 탐색 방향을 판단한다. 기계 실행기는 그 판단이 기대는 입력, 권한, 실행 상태와 자원 배정을 지킨다.

이 문서에서 K는 정확한 신뢰 환경에 결박한 형식 수학 결과의 집합이다. F는 현재 명시한 질문·가설·정의 후보·방향·장애물·부분 결과다. U는 아직 명시하지 못한 연구 가능성을 가리킨다. U의 전건 목록을 만들어야 연구를 시작할 수 있다는 조건을 두지 않는다. F의 후보를 모두 실행 계약으로 바꿀 의무도 없다.

탐색과 집중 활용의 비율은 고정하지 않는다. 연구 계획은 양쪽을 고려하고, 확인된 근거·추론·가설·직감을 구분한다. 결과 없음과 유용한 실패도 실제 수행 범위와 근거를 갖추면 연구 기록으로 남긴다. 작업 수, 파일 수, 토큰 소비량은 수학적 진전의 판정값이 아니다.

### 1.1 서로 대신할 수 없는 다섯 판단

| 판단 | 판정자 | 효력 |
|---|---|---|
| 형식 타당성 | 고정 환경의 Lean 커널 검사·공리 감사 | 해당 형식 표현을 그 환경에 상대적으로 사용할 수 있음 |
| 해설 동일성 | 판본화된 방침에 따른 독립 검토 | 정확한 해설 판본과 형식 표현의 연결을 사용할 수 있음 |
| 목표 충족 | 독립 목표 감사 | 헌장의 해당 목표 해결 상태를 바꿀 수 있음 |
| 행동 허가 | 사용자 결정과 명시된 적용 범위 | 지정 행동을 실행할 수 있음 |
| 실행 상태 | 기계 실행기와 실행 어댑터 | 프로세스·예산·권한의 다음 전이를 적용할 수 있음 |

형식 타당성은 자연어 의도를 보증하지 않는다. 해설 동일성은 목표 충족을 보증하지 않는다. 실행 종료는 연구 성공이 아니다. 사용자 승인은 수학적 타당성을 대신하지 않는다.

이 설계의 `mathematically_solved`는 Lean 형식 결과·동일성·목표 감사가 갖춰진 수학적 해결이다. 문헌 조사·추측 생성·자연어 초안 같은 비형식 과제도 수행하고 계약상 완료할 수 있지만 이 상태를 대신하지 않는다. 다른 최종 보증 경로의 추가는 별도 제품·신뢰 계약 변경이다.

### 1.2 산출물의 세 연결

형식 산출물, 해설, 동일성 판정은 별도 객체다. 동일성 판정은 정확한 형식 산출물·해설·검토 방침의 판본을 연결한다. 한 형식 결과에는 여러 해설과 동일성 판정이 연결될 수 있다. 목표 감사는 실제로 사용한 동일성 판정까지 참조한다.

해설 하나가 철회돼도 독립적으로 유효한 다른 해설과 형식 결과를 함께 철회하지 않는다. 형식 환경이 무효화되면 그 환경을 전제로 한 사용을 정지한다. 영향의 전파는 실제 의존 참조를 따른다.

### 1.3 권위의 적용 순서

현재 적용되는 사용자 결정과 연구 헌장·정책은 연구의 목적과 허가를 정한다. 실행 계약은 그 범위 안에서 이번 일을 구체화한다. 연구 기록과 과거 사례는 판단의 근거이며 새 허가를 만들지 않는다.

기계가 처리할 수 없는 새 권한 종류를 사용자가 승인하면 계약 확장이 필요하다는 사실을 기록한다. 기존 동작으로 그 권한을 비슷하게 실행하지 않는다. 새 승인이 없는 실행은 마지막으로 유효한 허가 범위 안에서만 진행한다.

## 2. 전체 연구 흐름

### 2.1 정상 흐름

1. 사용자의 입력을 내부에 보존하고 연구 헌장·정책·실행 허가를 확정한다.
2. 이미 있는 K 결과가 목표를 충족할 수 있으면 목표 감사에 보낸다. 확인된 해결이 없으면 연구 계획 활동을 연다.
3. 연구 계획 AI가 필요한 원자료를 읽고 실행할 작업과 보류할 질문을 제안한다.
4. 작업 계약의 입력·범위·완료 기준·권한을 검사하고, 실행 가능한 계약에 실행 요청을 만든다.
5. 기계 실행기가 해당 예산으로 AI 실행을 시작한다. 작업자는 자기 공간에서 연구하고 체크포인트를 공개한다.
6. 실행이 산출물 또는 대기 요청을 제출한다. 실행기는 공통 종료 절차를 수행하고 불변 산출 묶음을 보존한다.
7. 연구 자료 공개, 수학 인증, 목표 감사, 사용자 질문 등 필요한 후속 활동을 연다.
8. 확인된 결과와 미해결 사항을 연구 계획의 다음 입력으로 돌려준다.

각 단계의 AI 실행은 자기 일을 끝내거나 추가 입력이 필요하다는 결과를 반환한다. 다른 AI나 사용자의 응답을 기다리는 동안 자기 프로세스를 유지하지 않는다. 과제와 후속 활동의 상태는 실행 원장이 보존한다.

### 2.2 부분 정리의 예

목표가 P인데 H를 가정한 H → P를 얻었다고 하자. 형식 검사와 동일성 검토를 통과한 H → P는 K에 들어갈 수 있다. 목표 감사가 무조건 P의 해결을 확인하지 못하면 목표는 미해결이다. H의 입증·제거 또는 다른 접근은 다음 연구 계획이 선택한다.

검토가 가정 누락을 확인하면 불일치와 근거를 반환한다. 판단이 끝나지 않으면 미해결 쟁점을 반환한다. 어느 경우에도 실행이 종료됐다는 이유로 목표를 해결로 기록하지 않는다.

### 2.3 사용자 결정 대기의 예

작업자가 남은 범위에 새로운 외부 전송 허가가 필요함을 확인하면, 수행한 결과·남은 범위·요청할 허가를 봉인하고 끝낸다. 과제는 결정 대기이며 활성 실행과 예산 점유는 없다. 사용자 답변이 들어오면 현재 계약과 허가를 대조해 같은 과제의 새 실행을 열거나 계획을 변경한다. 실제 범위를 나눌 필요가 없으면 과제를 분할하지 않는다.

## 3. 주체와 소유권

### 3.1 기계 실행기

인스턴스마다 기계 실행기 프로세스 하나를 둔다. 실행기는 연구 정본과 실행 원장의 유일한 작성자다. AI가 제안한 문면을 대신 저작하거나 수학 판정을 하지 않는다.

실행기는 다음 일을 한다.

- 실행·예산 예약·대기·종료 상태의 전이와 기록.
- 프로세스 격리와 권한 회수, 종료 확인.
- 입력과 산출물의 고정·검사·보관.
- 승인된 변경의 적용 전 검사와 원자적 편입.
- 예정된 운영 검토와 준비된 후속 활동의 개설.
- 사용자 질문의 전달과 승인 범위에 맞는 적용.

한 실행기는 운영체제의 독점 잠금 handle을 인스턴스 수명 동안 보유한다. 같은 인스턴스의 두 번째 실행기는 쓰기를 시작하지 않는다. PID나 heartbeat 시각만으로 잠금을 탈취하지 않는다. 잠금이 해제된 뒤 시작한 실행기도 [복구 절차](#d14)를 마쳐야 새 실행을 배정한다.

초기 잠금은 승인한 로컬 데이터 루트의 인스턴스 ID별 lock 파일을 공유 허용 없이 여는 OS handle이다. 실행기는 최종 물리 경로와 volume을 확인해 같은 인스턴스의 경로 별칭이 같은 파일을 가리키게 한다. 파일의 존재 자체는 잠금이 아니다. handle 보유와 확인된 파일 정체성이 잠금의 근거이며 프로세스 소실 때 OS가 해제한다.

### 3.2 AI 활동

AI 활동의 기본 책임은 다음과 같다. 활동 이름은 별도 영속 프로토콜을 뜻하지 않는다. 모든 활동은 [공통 실행 계약](#d06)을 사용한다.

| 활동 | 책임 | 예산 |
|---|---|---|
| 연구 계획 | 다음 작업 집합, 후보 정련과 재검토 조건 제안 | 운영 |
| 연구 수행 | 작업 계약의 질문을 탐구하고 산출물 제출 | 작업 |
| 작업 계약 검토 | 선택된 계약의 실행 가능성과 완료 기준 판정 | 작업 |
| 수학 검토·추가 조사 | 해설·형식·원문·목표의 지정 범위 검증 | 작업 |
| 운영 점검·복구 검토 | 실행의 실제 상태와 복구 제안 판정 | 운영 |
| 의도 해석 | 사용자 입력의 의미·효과와 미결정 확인 | 운영 |

연구 계획 활동은 새 수학 내용을 입증하는 장기 조사를 내부에서 수행하지 않는다. 그런 조사가 필요하면 작업 예산의 활동으로 제안한다. 운영 점검의 추가 조사도 같은 원칙을 적용한다.

산출물을 작성한 실행은 그 산출물의 독립 검토자일 수 없다. 같은 검토 단계의 독립 판정자는 다른 판정자의 이번 결과를 받기 전에 자기 결과를 봉인한다. 병렬 실행은 필수가 아니다. 미리 정의한 운영·검토 활동의 입력·출력은 구현 계약이 소유하며, 그 활동 자체에 재귀적인 착수 검토를 붙이지 않는다.

### 3.2.1 활동의 영속 상태

과제는 연구 의무를 소유하고 `activity`는 그 의무를 수행하거나 판정하는 한 업무를 소유한다. 모든 실행은 `owner_activity_id` 하나를 갖는다. 활동은 `id`, `activity_kind`, `owner_ref`, 정확한 입력 참조, 상태, 종류별 단계, 배정 실행 ID, 결과 참조, 미결 사항과 후속 목록을 가진다. `owner_ref`는 인스턴스·과제·상위 활동 중 하나이며 소유 관계는 순환하지 않는다.

활동 상태는 `ready`, `working`, `waiting`, `finished`다. ready에서 실행을 배정하면 working, 추가 입력이 필요하고 소유 실행이 모두 종료됐으면 waiting, 대기 조건이 해소되면 ready로 간다. 결과 또는 정당한 중단 처분과 후속을 봉인하면 finished다. finished는 다시 열지 않으며 추가 업무는 이전 결과를 참조한 새 활동이다. waiting은 대상·재관찰 사건 또는 시각·다음 소유자를 필수로 가진다.

| activity_kind | 대상·단계 | 결과와 직접 후속 |
|---|---|---|
| `research_plan` | 인스턴스의 planning | plan; 계약 생성·정련·보류를 실행기에 반환 |
| `research_work` | 과제의 performing | 산출 묶음·범위 보고; 과제의 완료 판정·대기·검증으로 반환 |
| `task_contract_review` | 과제 revision의 assessing | approved·revision_required·unresolved; 과제와 다음 연구 계획에 반환 |
| `identity_review` | 제안의 planning·reviewing·clarifying·judging | assessment; 편입 또는 남은 연구로 반환 |
| `goal_audit` | 목표 판본의 assessing | satisfied·not_satisfied·unresolved; 목표 상태와 계획으로 반환 |
| `operational_review` | 실행의 diagnosing·checking_recovery | 점검 처분; 12.4절의 적용·계약 개정·결정 대기로 반환 |
| `intent_interpretation` | 수입의 interpreting·checking | 변경안과 미결정; 사용자 확인 또는 승인된 적용으로 반환 |
| `supplemental_research` | 지정 질문의 investigating | 근거·답·미해결; 요청한 상위 활동에 반환 |
| `maintenance` | 초기화·편입·신뢰 전환·마이그레이션의 해당 단계 | 기계 결과와 필요한 AI 판단 요청; 호출 절차로 반환 |

`intent_interpretation`의 checking은 최초 해석 실행과 다른 실행이 수행하며 결과는 approved·revision_required·unresolved다. 이 결과는 사용자 허가 자체가 아니다. 수학 검토의 하위 실행은 상위 identity_review가 할당한 단계·범위를 따르며 별도 재귀 검토를 만들지 않는다.

실행 종료 종류, 활동의 단계·결과·후속 목록, 소비한 사건 cursor와 예약 반환은 하나의 상태 공개로 기록한다. 같은 결과를 재수신하면 이 기록을 반환한다. 소실이 이 공개 전이면 결과를 다시 대조하고, 공개 뒤이면 기록된 후속만 수행한다. 문서의 일반적인 '다음 소유자'는 이 owner_ref와 후속 목록을 뜻한다.

### 3.3 사용자 대화

대화 세션은 사용자의 요청·답변을 전달하고 결과를 설명한다. 대화 프로세스가 실행권한을 소유하지 않는다. 사용자의 명시적인 정지 요청은 연구 계획이나 수학 검토의 완료를 기다리지 않고 실행기에 전달한다.

인스턴스의 `conversation_loss_policy`는 `continue_authorized` 또는 `pause`다. 전자는 대화 소실 뒤에도 기존 허가 범위의 운전을 계속한다. 후자는 소실 사건을 받으면 인스턴스를 정지한다. 값은 생성 때 승인하며 기본값을 추측하지 않는다.

대화 어댑터는 conversation_id와 connection_generation을 등록하고 연결·명시적 종료·생존 신호를 전달한다. pause 프로필은 생존 신호 주기와 유예를 승인값으로 가진다. 명시적 종료는 즉시, 신호 소실은 유예 만료 때 lost 사건을 만든다. 연결 복구는 같은 대화 ID와 새 세대로 확인하며, 이전 세대의 늦은 신호가 정지를 취소하지 않는다. 중복 사건은 사건 ID로 한 번만 적용한다.

실행기 재시작 때 pause 연결의 생존을 확인하지 못하면 배정을 닫은 채 재연결을 기다린다. 모델 thread의 무활동·구독 해제와 사용자 대화 소실을 같은 사건으로 추측하지 않는다. 이 관찰을 제공하지 못하는 대화 어댑터에는 pause 프로필을 활성화하지 않는다. 단순 UI 부재를 이유로 continue_authorized 허가를 새로 만들지도 않는다.

### 3.4 저장소와 작업 공간의 권한

AI 실행은 자기 입력 사본, 허용된 조회 결과와 자기 작업 공간만 사용한다. 연구 정본·실행 원장·다른 실행의 비공개 검토 결과를 직접 수정하거나 읽을 권한은 없다. 연구 기록 조회는 고정한 읽기 판본과 공개 범위를 검사하는 실행기 도구를 거친다.

실행 ID 문자열만으로 권한을 인정하지 않는다. 실행 어댑터는 요청자의 실제 실행 인스턴스와 허가를 결박한다. 중앙 Git 데이터베이스와 원장에 대한 쓰기 차단, 다른 검토 결과의 읽기 차단을 실제로 보장하지 못하는 어댑터는 활성화 검사를 통과하지 못한다. 지침문에 금지를 적는 것으로 이 검사를 대체하지 않는다.

Job Object는 프로세스 수명 경계다. 파일·네트워크·비밀의 접근 경계는 제한된 OS identity, ACL과 인증된 실행기 통신이 따로 제공한다. 임의 연구 프로그램은 중앙 저장소·다른 실행·주변 크리덴셜에 접근할 수 없고 외부 통신은 승인된 broker를 거친다. 프로필은 직접 소켓·다른 프로세스·파이프·환경 비밀과 자식 handle 접근의 실제 거부를 검사한다. 이 능력이 없는 환경은 제한을 프롬프트로 대체해 지원한다고 선언하지 않는다.

## 4. 예산과 배정

### 4.1 분리된 예산

예산의 단위는 동시에 활성인 AI 실행이다. 동시성 제약은 `constraint_id`, `work_slots`, `operations_slots`, `total_slots`, `source`를 가진다. source는 로컬 승인 상한인 local_budget 또는 실제 공급자에게 확인한 provider_verified다. 여러 모델이 공유하는 공급자 제약도 같은 ID로 센다. 실행 프로필의 capacity_refs가 소비 제약 전건을 고정한다.

각 제약은 다음 조건을 만족해야 한다.

```text
work_slots >= 0
operations_slots >= 0
work_slots + operations_slots <= total_slots
```

활성화에는 운영 활동을 수행할 수 있는 프로필의 제약 전건에 운영 용량이 하나 이상 있어야 한다. 연구 수행을 허용하는 인스턴스는 필요한 작업 프로필의 제약 전건에도 작업 용량을 가져야 한다. 실행 하나의 예약은 자신이 소비하는 제약 전건에서 동시에 성공해야 하며 하나라도 실패하면 어느 예약도 적용하지 않는다. 같은 계정 상한을 모델별로 중복 할당하지 않는다.

이 분리는 확인한 동시 실행 용량에 대한 보장이다. 속도·사용량 제한과 공급자 장애는 별도의 가용성 조건으로 프로필에 기록한다. 실행기 밖에서 소비하는 같은 계정의 자원은 이 원장이 통제한다고 주장하지 않는다.

작업 실행은 작업 예산만 예약하고 운영 실행은 운영 예산만 예약한다. 두 예산 사이에 자동 차용을 허용하지 않는다. 사용하지 않는 운영 용량을 작업으로 채우지 않는다. 예산 재배치는 별도의 승인된 설정 변경이다.

### 4.2 예약과 반환

예약은 실행 원장의 단일 트랜잭션에서 수행한다. `starting`, `running`, `stopping` 실행과 종료가 아직 확인되지 않은 실행은 해당 예약을 점유한다. `queued`는 예약하지 않는다.

예약 반환 조건은 로컬 Job 종료와 모델 실행 종료가 모두 확인된 것이다. 모델 호출이 원격에서 계속될 수 있는 어댑터는 원격 실행 ID와 종료·취소 확인을 제공해야 한다. 로컬 래퍼를 죽였다는 이유로 원격 예약을 반환하지 않는다. 종료 여부가 미확인이면 실행을 `stopping`에 두고 기계 대조를 계속한다.

어댑터는 원격 상태 보존 기간, 정상 대조 수단과 지원하는 복구 공백을 선언한다. 조회가 영구히 불가능해지면 단순 네트워크 대기와 구분해 해당 예약을 unrecoverable로 표시하고 사용자에게 보고한다. 예약을 지우지 않으며 영향받지 않은 제약은 계속 사용할 수 있다. 해당 제약의 복원은 공급자의 종료 영수증, 전역 실행 대조 또는 이전 실행이 더는 용량을 소비하지 않음을 입증하는 공급자 보장으로만 한다. 사용자의 확인만으로 공급자 사실을 참으로 바꾸지 않는다. 독립성이 입증된 새 공급자 제약으로의 전환은 별도 승인된 설정 변경이다.

상태 보존 기간을 넘는 복구를 지원한다고 검증하지 못한 어댑터에는 그 한계를 표시한다. 취소 API나 평시 조회의 존재만으로 무기한 복구 가능을 선언하지 않는다.

추가 AI 조사나 사용자 결정이 필요하다는 결과를 반환한 실행은 정상 종료 절차를 밟는다. 후속 입력을 기다리는 과제와 검토 활동은 예산을 점유하지 않는다.

### 4.3 배정 순서

기계 실행기는 준비된 실행을 각 예산 안에서 배정한다. 권한 회수·정지·중앙 신뢰 보호는 AI 운영 큐를 기다리지 않는 기계 제어다. AI가 필요한 통상 점검·복구안 확인·의도 해석·계획은 하나의 FIFO 운영 큐를 사용한다. 실행별 중복 요청은 합치되 최초 큐 진입 시각을 보존한다. 새로운 점검이 먼저 기다린 계획을 계속 앞지르지 못하게 한다.

작업 예산은 연구 계획이 승인된 범위에서 정한 배정 순서를 따른다. 독립 검토 활동은 이미 수락한 검증 요청의 생성 순서로 배정하되, 계획이 변경한 순서는 근거와 함께 기록한다. 실행기가 임의의 수학 점수를 만들어 순서를 정하지 않는다.

예산이 부족하면 요청을 대기시키고 현재 점유와 반환 조건을 보고한다. 용량 확보를 위해 연구 실행을 정지하는 별도 회수 절차는 두지 않는다. 공급자의 가용 한도가 줄면 새 배정을 막고, 이미 허가한 실행에 대한 처분은 실제 공급 상태와 승인된 정지 정책을 따른다.

### 4.4 설정 변경

상한을 현재 사용량 아래로 줄이는 승인은 새 배정의 중지를 뜻한다. 이미 실행 중인 일을 강제로 종료하는 권한까지 포함하지 않는다. 실행 종료도 원하는 경우 그 대상과 효과를 승인 기록에 명시한다. 운영 용량을 전부 없애는 설정은 활성 운전에 적용하지 않고 정지된 인스턴스에서만 보관할 수 있다.

### 4.5 동시성 외의 실제 제약

동시성 슬롯, 누적 허가량과 공급자의 시간창 한도는 별도 의미다. 원장의 resource_reservation은 제약 ID, 단위, 적용 허가, 실행 또는 공급자 호출 ID, 예약량, 확정 소비량과 정산 근거를 가진다. 지원 단위는 실제 어댑터가 계량·상한 집행을 제공하는 것만 활성화한다. 토큰·요청 수·고정 통화 단위·도구 시간·저장량 중 사용자 허가가 제한한 차원을 빠뜨리지 않는다.

공급자 호출 또는 외부 행동을 보내기 전에 그 호출의 최대 소비를 관련 허가 전건에서 예약한다. 입력과 최대 출력 또는 승인된 가격표로 상한을 계산할 수 없으면 해당 하드 한도를 지원한다고 주장하지 않는다. 실제 소비가 확인되면 예약을 정산하고 남은 몫을 해제한다. 소비 미확인은 예약을 유지하며 실행 종료로 사용량을 0으로 만들지 않는다. 무제한은 명시된 허가의 값이고 필드 누락의 뜻이 아니다.

RPM·TPM 같은 시간창 제약은 window·limit·reset 근거를 가진다. 제한 응답은 새 호출을 재전송하기 전에 이 상태를 갱신한다. 허용한 재시도 시각까지 기다릴 수 없거나 실행 기한에 맞지 않으면 현재 실행은 부분 결과를 반환하고 종료한다. 공급자의 동시 실행 수가 공개되지 않았으면 로컬 설정값을 확인된 공급자 상한으로 기록하지 않는다.

기계 작업도 공유 호스트 제약을 예약한다. 초기 호스트 프로필은 동시에 실행할 무거운 기계 작업 수와 각 작업의 강제 가능한 메모리·CPU 한계로 시작한다. AI 실행 안의 도구도 같은 공유 제약을 소비한다. 실행기 제어 경로의 여유를 남긴 부하 시험을 통과한 값만 사용하며, 개별 Job 한계의 합이 안전하다고 추측하지 않는다.

허가의 expires_at에는 기계 만료 사건을 예약한다. 만료 시 새 배정을 막고 허가가 정한 정지·마무리 효과를 적용한다. 이 사건은 AI 점검 시각을 기다리지 않는다. 누적 한도가 차면 이미 예약한 호출만 범위 안에서 마무리할 수 있고, 허가 밖의 새 행동은 열지 않는다.

<a id="d05"></a>
## 5. 연구 후보와 작업 계약

### 5.1 후보

F의 질문·방향·장애물과 연구 계획의 보류 기록이 후보를 보존한다. 후보마다 미래 실행의 필수 입력·도구·완료 기준을 미리 완성할 의무는 없다. 사용자의 결정이나 다른 결과를 기다리는 확정 과제는 후보와 구별해 작업 원장에 남긴다.

후보를 정련하는 활동과 작업을 선택하는 활동은 한 연구 계획에서 수행할 수 있다. 독립 탐색 작업은 서로 다른 관점의 후보를 생산할 수 있다. 계획자는 자기 이전 선택과 실제 결과를 대조하고, 관심 범위 밖에 남은 후보와 불확실성을 기록한다.

### 5.2 작업 계약

실행할 일이 정해지면 `task` 기록을 만든다. ID는 생성 때 부여한다. 계약은 다음 필드를 가진다.

| 필드 | 의미 |
|---|---|
| `id`, `revision` | 과제 정체성과 계약 판본 |
| `question` | 답할 질문 또는 수행할 일 |
| `scope`, `excluded_scope` | 필수 범위와 제외 범위 |
| `required_inputs` | 이번 실행 전에 확보할 정확한 입력 참조 |
| `expected_outputs` | 산출물의 종류·범위 |
| `completion_criteria` | 과제 완료를 판정할 조건과 판정자 |
| `authority_refs` | 허용 행동의 근거 |
| `execution_profile_ref` | 도구·모델·환경 요구 |
| `basis_refs` | 생성 근거와 관련 연구 기록 |
| `remaining_scope` | 아직 충족하지 않은 계약 범위 |

계약은 방법을 필요 이상으로 고정하지 않는다. 내부 방법 변경이 질문·범위·권한을 바꾸지 않으면 작업자가 판단한다. 실제 범위나 성공 기준을 바꾸어야 하면 변경안을 반환하고 계약 판본을 갱신한 뒤 수행한다.

같은 F 질문을 서로 다른 접근으로 탐색할 때는 그 질문을 공통 basis_ref로 가진 별도 과제를 만들 수 있다. 계획은 각 과제의 구별되는 접근, 의도한 중복과 결과 비교를 기록한다. 한 과제의 단일 연구 실행 규칙은 같은 질문의 병렬 탐색을 금지하지 않는다.

### 5.3 과제 상태

과제 상태는 `planned`, `active`, `waiting`, `completed`, `closed`다.

| 전이 | 조건 |
|---|---|
| `planned → active` | 해당 계약의 첫 연구 수행 실행 요청을 확정함. `queued`부터 포함 |
| `planned/active → waiting` | 필수 입력·결정·검증 결과를 기다리고 활성 실행이 없음 |
| `waiting → active` | 대기 조건을 해소하고 현재 계약의 새 연구 수행 실행 요청을 확정함 |
| `planned/active/waiting → completed` | 지정 판정자가 완료 기준 전건의 충족을 확인함 |
| `planned/active/waiting → closed` | 철회·대체·분할 등 계속하지 않을 정당한 처분을 적용함 |

`waiting`은 `wait_kind`, 대상 ID, 재관찰 시각 또는 사건, 다음 행동의 소유자를 가진다. `wait_kind`는 `user_decision`, `research_input`, `validation`, `external_event`, `execution_repair`다. 재관찰이나 소유자가 없는 대기를 만들지 않는다.

한 과제의 연구 수행 실행은 `queued`를 포함해 미종료 실행이 최대 하나다. 이 연결을 실행 요청 생성과 같은 원장 변경으로 기록한다. 별도 수학 검토·운영 점검은 자기 활동 기록의 실행이며 해당 과제의 연구 수행 실행이 아니다. `active`는 현재 프로세스의 생존을 뜻하지 않고, `waiting`인 과제의 산출물을 별도 검토하는 것은 가능하다. `completed`·`closed`는 자기 연구 수행 실행이 전부 `ended`인 뒤에만 적용한다.

`completed`와 `closed`는 흡수 상태다. 새로운 연구 의무가 생기면 근거를 가진 새 과제를 만든다. 프로세스 실패·사용자 답변 대기만으로 기존 과제를 닫지 않는다. `closed`는 실제 수행·잔여 범위와 철회·이전·대체의 근거를 모두 가진다.

### 5.4 착수 검사와 완료 판정

실행기는 계약 스키마, 입력의 존재·해시, 허가 범위, 실행 프로필과 완료 판정자의 배정을 검사한다. 선택된 계약의 질문·범위·완료 기준이 수행 가능한지는 작성자와 다른 작업 계약 검토 활동이 판정한다. 결과는 `approved`, `revision_required`, `unresolved`다. 입력을 읽지 못한 실행은 이 판정을 만들지 않는다.

정련 전 후보에는 이 검토를 요구하지 않는다. 검토 결과가 승인되지 않은 계약은 연구 계획에 결함·남은 질문을 돌려준다. 같은 입력으로 새 검토를 자동 반복하지 않는다.

과제 완료는 범위 항목마다 `fulfilled`, `waived`, `transferred`, `open`을 기록해 판정한다. `completed`에는 `open`과 `transferred`가 없어야 한다. `waived`는 원래 완료 기준 또는 권위 있는 범위 변경의 좌표를 요구한다. `closed`의 `transferred`는 후속 과제와 옮긴 범위를 가리킨다.

### 5.5 계약 개정과 범위 처분

연구 수행자·운영 점검자는 개정안을 제안할 수 있다. 연구 계획 활동이 현재 헌장 안에서 질문·범위·완료 기준의 개정 문면과 잔여 의무를 저작하고, 다른 작업 계약 검토 활동이 새 revision을 승인한다. 원래 사용자 목표·허가·총자원·외부 효과를 바꾸는 부분은 사용자 결정이 먼저 필요하다. 표현 정규화처럼 계약의 의미·필수 범위·판정 조건을 바꾸지 않는 수리는 재검토를 요구하지 않는다.

실행 요청은 계약 revision 하나에 고정된다. 의미 개정은 같은 과제의 미종료 연구 실행이 없는 상태에서만 적용한다. 기존 실행이 남아 있으면 현행 허가의 정지 절차로 끝내고, 결과·잔여 범위와 개정안을 보존한 뒤 새 revision을 적용한다. 이미 끝난 실행의 계약을 새 문면으로 덮지 않는다.

`waived`는 최초 완료 기준에 명시된 면제 조건의 충족, 또는 위 절차가 승인한 범위 변경만 근거로 삼는다. 연구 수행자가 자신의 완료 기준을 줄여 스스로 면제하지 않는다. 목표의 필수 의무를 남긴 채 현재 과제를 닫으려면 후속 과제로 이전하거나 사용자의 의무 철회 결정을 받아야 한다.

<a id="d06"></a>
## 6. 모든 AI 활동의 공통 실행 계약

### 6.1 실행 요청

하나의 실행 요청은 하나의 `execution_id`를 생성 때 부여받는다. 재시도는 새 실행 ID를 사용한다. 같은 과제·검토 활동을 이어가는 관계는 `continuation_of`와 정확한 재개 자료로 표현한다. 별도의 가변 논리 세션을 권한의 원천으로 두지 않는다.

요청의 `actor_kind`는 `ai` 또는 `machine`이다. 긴 Lean 빌드·해시 검사 같은 기계 작업도 같은 격리·권한 회수·종료 상태를 사용하되 AI 예산을 예약하지 않는다. 기계 작업의 모델·tokenizer·원격 모델 ID 필드는 부재하며 부재는 비AI 작업을 뜻한다. 기계 작업에는 승인된 도구 manifest와 호스트 자원 한계를 대신 적용한다.

요청은 실행 ID·owner_activity_id·활동 단계·정확한 입력 manifest·출력 스키마·허가 참조·작업 공간을 공통으로 고정한다. 나머지 필드는 다음 분기대로 작성한다. 금지한 필드는 null로 채우지 않고 부재해야 한다.

| 분기 | 필수 필드 | 금지 필드 |
|---|---|---|
| AI·작업 예산 | model_profile_ref, budget_kind=work, capacity_refs, next_operational_review_at | 운영 실행만의 execution_deadline |
| AI·운영 예산 | model_profile_ref, budget_kind=operations, capacity_refs, execution_deadline | next_operational_review_at |
| 기계 작업 | tool_profile_ref, host_capacity_refs, execution_deadline | budget_kind, model_profile_ref, tokenizer, 원격 모델 ID, next_operational_review_at |

한 AI 실행이 만드는 공급자 호출은 provider_operation_id 목록으로 별도 기록한다. thread·turn·response 중 무엇을 실행 ID와 결박하는지는 어댑터 대응표가 소유하며 한 실행과 원격 response 하나가 같다고 가정하지 않는다. 필수 입력이 아직 없으면 실행 요청을 만들지 않고 소유 활동의 대기로 보존한다.

### 6.2 실행 상태

실행 상태는 `queued`, `starting`, `running`, `stopping`, `ended`다.

| 상태 | 허용 행동 |
|---|---|
| `queued` | 입력·허가 재검사와 예산 대기. 프로세스 없음 |
| `starting` | 예산 예약 뒤 격리 환경과 정지 프로세스 준비 |
| `running` | 부여한 범위의 연구·검토·체크포인트·제출 |
| `stopping` | 새 실질 행동 금지. 종료·산출 회수·종료 대조만 |
| `ended` | 상태 변경과 AI 쓰기 금지. 보존한 결과의 후속 처리만 |

허용 전이는 `queued → starting → running → stopping → ended`, `queued → ended`, `starting → stopping → ended`다. 한 실행을 다시 `running`으로 만들지 않는다. 정상 종료에서도 `stopping`을 거친다.

종료 종류는 다음으로 닫는다.

- `output_accepted`: 실행이 제출한 산출물의 형식·입력 결속을 수신자 검사가 통과했다. 산출물의 수학적 판정값과 독립이다.
- `execution_incomplete`: 실행했지만 요구한 산출과 검사 범위를 끝내지 못했다.
- `cancelled`: 명시적인 권한 회수·정지로 끝났다.
- `start_failed`: 첫 실질 행동 전에 시작을 완료하지 못했다.

종료 기록은 원인, 실제 검사 범위, 부분 산출물, 다음 소유자와 미완료 범위를 가진다. `execution_incomplete`를 의미 판정의 기각이나 이의 없음으로 사용하지 않는다.

실질 행동은 모델 요청의 외부 전송, 연구·검토 프로그램의 실행, 연구 내용 파일의 쓰기, 허용 도구 호출 또는 외부 행동 요청이다. 준비는 실행기가 수행하는 격리 공간·고정 입력 사본·정지 루트 생성·허가 자기검사다. 종료용 상태 조회·수집은 새 연구 행동이 아니다. 어댑터가 첫 실질 행동 전이었다는 사실을 입증하지 못하면 start_failed로 분류하지 않는다.

### 6.3 시작 순서

1. 고정 입력·프로필·허가와 해당 예산을 재검사한다.
2. 단일 원장 변경으로 예산을 예약하고 `starting`을 기록한다.
3. 허용 입력 사본과 새 작업 공간을 준비한다. 이전 공간을 살아 있는 프로세스와 공유하지 않는다.
4. 실행 ID별 Job Object를 만들고, 자식의 이탈과 handle 상속을 차단한다.
5. 루트를 정지 상태로 만들고 프로세스 handle·생성 시각을 기록한 뒤 Job에 편입한다.
6. `running`과 실행 허가를 원장에 기록한다. 이 기록 전에는 루트를 재개하지 않는다.
7. 루트를 재개한다. 래퍼는 첫 실질 행동 전에 자기 허가와 입력·도구 판본을 다시 확인한다.

준비가 실패하면 실행한 준비 범위와 OS 상태를 기록하고 공통 종료 절차로 간다. 예산 예약 기록 전에 모델 실행을 시작하지 않는다.

### 6.4 실행 중 권한

허가는 실행 ID, 입력 범위, 도구 범위와 쓰기 범위에 결박한다. 허가의 유효 조건은 해당 실행이 `running`이고 인스턴스의 실행 허가가 유효한 것이다. 체크포인트가 생겼다는 이유로 허가 식별자를 교체하지 않는다.

도구 요청은 실행기에서 실제 실행 인스턴스와 허가를 확인한 뒤 처리한다. `stopping` 이후 새 쓰기·도구 요청을 거부한다. 늦게 도착한 완료 통지는 진단 기록으로 수신할 수 있으나 종료된 실행을 재허가하지 않는다. 권한 회수는 실행기 경유 요청과 정본 반영을 즉시 막는다는 뜻이다. 이미 동작 중인 로컬 프로그램은 종료 장벽까지 자기 공간을 바꿀 수 있으므로 그 공간을 다른 실행에 넘기지 않는다.

작업자는 자기 프로그램과 실험 코드를 만들 수 있다. 실행권한·프로세스 격리·정본 편입을 우회하는 대체 제어 도구를 만들 수는 없다.

### 6.5 제출과 종료

1. 생산자가 제공된 출력 생성기·검사기로 산출물과 입력 manifest의 결속을 검사하고 고친다.
2. 생산자가 최종 제출 의도와 파일 manifest를 보내고 새 실질 행동을 끝낸다. 래퍼는 제출 의도가 원장에 기록됐다는 수신 확인을 받은 뒤 종료한다.
3. 실행기가 제출 의도·manifest와 `stopping`을 같은 원장 변경으로 기록해 권한을 회수하고 수신 확인을 보낸다. 수신 확인은 출력 검사를 통과했다는 뜻이 아니다. 정상 종료를 기다릴 수 있는 기간은 승인된 실행 프로필이 정한다.
4. 잔존 프로세스에는 Job 종료를 적용한다. process handle·Job 구성원·모델 호출의 종료를 대조한다.
5. 종료 장벽 뒤 작업 공간과 제출 파일을 회수해 불변 산출 묶음을 만든다. 요청 manifest와 바이트가 다르면 차이를 보존하고 유효한 최종 산출로 추측하지 않는다.
6. 같은 판본의 수신자 검사기를 별도 호출해 입력·출력·허가·파일 해시를 검사한다.
7. 종료 종류와 산출 묶음, 다음 행동을 같은 원장 변경으로 기록하고 AI 예약을 반환한다. 기계 작업은 모델 종료 대조와 AI 반환이 없고 로컬 작업의 종료·호스트 자원 회수만 확인한다.

종료 장벽을 완료하지 못하면 `stopping`과 예약을 유지한다. 작업 공간을 넘기거나 청소하지 않는다. 실행기는 로컬·원격 대조로 확인할 수 있는 사실을 먼저 확인하고, 판단이 필요한 부분은 운영 점검에 보낸다.

실행 중 체크포인트는 실행기 도구에 제출한 불변 사본만 공개된 것으로 센다. 작업자가 계속 쓸 수 있는 파일 경로를 체크포인트 정본으로 사용하지 않는다. 같은 체크포인트 요청을 재전송하면 기록한 결과를 반환하고 중복 보관하지 않는다.

### 6.6 실패와 재실행

실행 요청은 owner_activity_id가 가리키는 활동에 모든 종료 결과를 반환한다. 다음 표가 새 실행의 근거를 정한다. 명령 오류 코드, 실행 종료 종류와 수학적 판정은 서로 대신하지 않는다.

| 이전 종료 | 새 실행의 근거 |
|---|---|
| output_accepted | 소유 활동의 다음 단계 또는 판정이 요구한 수정·추가 조사. 이전 실행의 실패로 기록하지 않음 |
| execution_incomplete | 수정된 필수 입력, 확인한 환경 복구, 또는 근거를 가진 재시도 결정 |
| start_failed | 시작 전제의 복구와 현재 허가·프로필의 재검사 |
| cancelled | 여전히 유효한 재개 허가 또는 새 사용자 결정, 취소 원인 해소 |

같은 일을 이어가는 새 실행에는 continuation_of와 이전 결과·원인·실제 범위가 필수다. 새 독립 과제는 생성 근거로 이전 결과를 가리키되 실행 재시도로 위장하지 않는다.

새 실행의 필수 입력에는 이전 실패의 규칙·좌표·입력 차이, 이미 완료한 외부 행동, 재개할 체크포인트와 남은 범위가 포함된다. 같은 검사기를 쓴다는 이유로 실패 정보를 제외하지 않는다.

의미를 바꾸지 않는 정규화와 파생 보기 재생성은 도구가 수리하고 기록한다. 깨진 참조나 수학 내용을 추측해 고치지 않는다. 실행 재시도는 수정된 입력, 확인된 환경 복구 또는 명시적인 재시도 결정 중 하나를 근거로 한다. 동일한 실패 상태를 아무 변화 없이 자동 재파견하지 않는다.

## 7. 저장과 참조

### 7.1 하나의 권위 있는 상태 머리

같은 Git 객체 데이터베이스에 인스턴스의 권위 있는 가변 ref 하나를 둔다.

```text
refs/heads/do-math/<instance_id>
```

각 상태 커밋은 research와 runtime 하위 트리를 함께 가진다. 사슬은 단일 부모이며 기계 실행기만 ref를 갱신한다. 연구 상태와 실행 상태의 소유 내용은 분리하되 별도 가변 머리를 동기화하지 않는다. runtime만 바뀌면 research 하위 트리의 OID는 그대로다.

이 문서의 '원장 변경' 또는 '상태 공개'는 이전 ref OID를 검사해 새 상태 커밋 하나로 ref를 바꾸는 원자적 공개 단위다. 같은 변경의 기록은 그 커밋에서 함께 보인다. 작업용 index·파일·만들었지만 ref가 가리키지 않는 커밋은 현재 상태가 아니다. 커밋은 자기 OID를 본문에 넣지 않는다.

research 하위 트리는 다음을 소유한다.

```text
instance.json
governance/                 헌장·정책·허가·사용자 결정
knowledge/                 F·자료·근거·관계·연구 맥락
formal/                    형식 결과·해설·동일성 판정·목표 감사
trust/                     신뢰 환경 manifest와 검증 기록
lean/                      활성 정본 Lean 소스와 환경 잠금
integrations/              공용 변경의 근거와 입력
indexes/                   결정론적으로 재생성하는 탐색용 보기
```

runtime 하위 트리는 다음을 소유한다.

```text
state.json                 인스턴스 운전·복구 상태
tasks/<id>/                작업 계약·상태·범위 원장
executions/<id>/           요청·상태·프로세스·예약·종료 기록
activities/<id>/           계획·검토·점검의 단계와 후속 소유권
artifacts/<bundle_id>/     불변 입력·출력·체크포인트 묶음
actions/<action_id>.json   적용·종료·외부 행동의 실행 기록
events/<event_id>.json     의미 있는 상태 전이와 관찰 근거
```

원장의 artifacts는 새 디렉터리만 추가한다. 기존 묶음의 파일은 수정·삭제하지 않는다. 현재 원장 트리와 부모 사슬이 그 바이트를 도달 가능하게 보존하므로, JSON 안에만 적힌 OID를 보관 ref의 대체로 사용하지 않는다. 작업 공간의 파일을 회수한 뒤에만 청소한다.

### 7.2 식별자와 참조

장기 객체는 종류 접두사와 충돌 없는 ULID로 식별한다. ID는 생성기가 먼저 부여한다. 제목과 경로는 정체성이 아니다. 종류별 접두사는 스키마 레지스트리가 소유한다. 인스턴스·과제·실행·산출 묶음·판정·결정·공용 편입·신뢰 환경은 각각 별도 ID를 쓴다. 질문·정의·명제의 의미가 바뀌어 기존 관계를 그대로 사용할 수 없으면 새 ID를 부여한다.

권위 참조는 다음 세 형태로 닫는다.

| 참조형 | 필드와 의미 |
|---|---|
| `record_ref` | `space`가 research 또는 runtime, 해당 커밋 OID, 기록 ID, 기록 파일 SHA-256. 정확한 판본 |
| `artifact_ref` | bundle ID, 그 안의 상대 경로, 파일 SHA-256. 실행 원장의 불변 자료 |
| `tree_record_ref` | 같은 트리 안 기록의 ID. 이 참조를 담은 기록과 같은 커밋 트리에서 해석 |

현재 판본을 묵시적으로 읽는 참조는 탐색 보기에서만 쓴다. record_ref의 commit은 인스턴스 상태 커밋이고 space는 그 안의 research 또는 runtime이다. tree_record_ref는 같은 space 안의 구조적 연결에만 쓴다. 후보와 편입 뒤 모두 참조를 담은 정확한 트리에서 해석한다.

판정 입력, 허가 근거, 검토 방침, 계약의 고정 입력에는 tree_record_ref를 금지한다. 같은 공용 변경에 처음 들어가는 해설·판정도 이미 봉인한 산출 묶음의 artifact_ref로 바이트를 결박한다. 후속 커밋이 구조적 링크의 대상을 고쳐도 과거 판정의 입력은 바뀌지 않는다. 일반 연결에 대상 해시를 일괄 추가해 순환 참조의 해시 고정점을 요구하지 않는다. 본문 링크에서 권위 관계를 추출하지 않는다.

파일 경로는 기준 루트에 상대적인 POSIX 경로다. 절대 경로, 상위 이동, 빈 경로와 루트 밖 해석을 거부한다. 외부 URL과 문헌 좌표는 출처이며 평시 실행의 파일 참조가 아니다. 실제 사용한 원자료는 내부 묶음으로 보존한다.

Windows 물리 경로는 별도 해석한다. 초기 데이터 루트는 승인한 로컬 고정 NTFS이며, 경로 segment의 역슬래시·콜론·끝 점/공백·예약 장치 이름과 대소문자 충돌을 거부한다. 열기·회수·청소 때 reparse point를 따라 루트 밖으로 나가지 못하도록 handle 기준으로 최종 경로와 volume을 확인한다. manifest의 문자열 prefix 검사만으로 경계를 판정하지 않는다.

### 7.2.1 시각과 기한

영속 시각은 밀리초 정밀도의 UTC RFC 3339 문자열이고 사건 순서는 상태 커밋 사슬과 그 안의 event_seq가 소유한다. ULID의 시각과 순서를 권위 있는 시계로 쓰지 않는다. 살아 있는 실행기의 기간 측정은 단조 시계로 수행하며 대응 UTC 관찰 시각을 남긴다.

실행기 재시작 뒤에는 만료 시각과 현재 UTC를 대조한다. 과거 시계 기준보다 뒤로 이동해 허가·기한을 확정할 수 없으면 새 행동을 보류하고 시계 대조를 요구한다. 남은 기간을 재시작 때부터 다시 부여하지 않는다. 운영 AI·기계 작업의 이미 지난 기한은 공통 종료로 처리하며, 재관찰 시각이 지났으면 사건 하나를 합쳐 연다. 절전 복귀·시계 보정에서도 같은 규칙을 적용한다.

### 7.3 지식 문서와 기계 기록

F·자료·근거·관계·연구 맥락·연구 기억은 Markdown 본문과 YAML frontmatter를 가진다. 공통 필드는 `id`, `kind`, `schema_version`, `title`, `lifecycle`, `origin_refs`다. 기계가 읽을 종류별 필드만 스키마에 더한다. 새 F·관계 종류는 기존 필드와 효력 안에서 종류 정의 데이터로 추가할 수 있다. 새 기계 필드·권한·효력을 데이터가 만들 수는 없다.

본문은 정확한 주장·범위·근거·불확실성을 설명한다. YAML은 JSON 호환 자료형을 사용한다. 문자열·불리언·정수·목록·매핑의 의미를 구별하며, 문자열로 위장한 불리언을 같은 값으로 읽지 않는다. 중복 키, 태그, 별칭·앵커, 병합 키와 다중 문서는 거부한다. 빈 목록은 `[]`, 빈 매핑은 `{}`를 정규 표현으로 허용한다.

필드의 부재와 `null`은 스키마가 각각 하나의 의미를 명시한 경우에만 허용한다. 미조사와 조사 결과 없음이 중요한 필드는 `assessment=unassessed` 또는 `assessment=assessed`와 실제 목록을 사용한다. 빈 목록을 미조사로 읽지 않는다.

실행·예산·허가·판정 manifest는 정규 JSON을 사용한다. UTF-8·BOM 없음·LF·두 칸 들여쓰기·파일 끝 개행 하나로 출력한다. 키와 기계 문자열은 NFC로 정규화하고 중복 원문 키와 정규화 충돌을 객체 구성 전에 거부한다. 키는 코드 포인트 순서다. 수는 정수만 사용하고 -0은 0으로 출력한다. 자료형의 범위는 스키마가 정하며 정확한 소수·큰 수는 단위와 문법이 정해진 문자열로 쓴다. 문자열은 따옴표·역슬래시·제어 문자만 JSON 규칙으로 escape하고 나머지 Unicode는 그대로 출력한다. 짧은 제어 escape가 있는 b·f·n·r·t는 그 표기를, 나머지 제어 문자는 소문자 네 자리 u escape를 쓴다. 배열의 의미 순서와 집합 정렬 키는 스키마가 소유한다.

YAML은 1.2의 JSON 호환 scalar 해석을 사용하는 고정 파서를 채택한다. 문자열 값은 큰따옴표, 불리언·정수는 그 자료형 표기로 생성한다. 날짜처럼 보이는 문자열도 문자열로 고정한다. frontmatter는 파일 첫 줄의 ---부터 닫는 ---까지이고 본문 앞에 빈 줄 하나를 둔다. 생성기는 키 정렬·블록 들여쓰기와 빈 []·{} 표현을 고정하며 본문 의미를 재작성하지 않는다. 정규 바이트 예와 거부 예는 규범 스키마 묶음의 golden vectors로 확정한다.

생성기와 검사기는 같은 판본의 직렬화 규칙과 스키마를 사용한다. YAML 파서·정규화기·JSON Schema 검사기는 실행 프로필의 구현 manifest가 판본으로 고정한다. 도구가 본문 의미를 고쳐 정규화하지 않는다.

초기 `kind`는 `frontier`, `evidence`, `relation`, `context`, `memory`다. 공통 `lifecycle`은 `active`, `superseded`, `withdrawn`이며 자료의 현재 사용 상태를 뜻한다. 같은 필드로 수학적 타당성을 판정하지 않는다. 초기 종류별 필드는 다음과 같다.

| kind | 추가 필드 | 소비자와 의미 |
|---|---|---|
| frontier | `subkind`, `epistemic_status` | 계획·조회가 질문·가설·방향을 구별한다. 상태는 open·supported·challenged·resolved·refuted이며 저자의 연구 판단이다. K 편입 관문으로 사용하지 않는다 |
| evidence | `subkind`, `source_refs` | source·observation·computation·argument·hypothesis·failure를 구별한다. source_refs는 실제 원문·데이터·코드·실행 결과의 정확한 내부 참조다 |
| relation | `subkind`, `from_ref`, `to_ref`, `evidence_refs`, 조건부 `assessment_refs` | 의존·지지·반박 등의 방향과 근거를 조회하고 영향 집합을 계산한다. 수학적 연결을 주장하는 종류에는 대응 형식 결과·판정 참조가 필수다 |
| context | `avoid_terms`, `related_refs` | 용어 경계와 연결된 정의·해설을 찾는다. 정확한 정의는 본문 또는 참조한 형식 결과가 소유한다 |
| memory | `information_status`, `scope`, `excluded_scope`, `source_refs` | fact·inference·heuristic·hypothesis를 구별해 과거 판단을 재사용한다. 원자료 없이 권한이나 수학적 사실을 확정하지 않는다 |

위 필드는 해당 kind에서 필수이고, 관계의 `assessment_refs`만 종류 정의가 필요 여부를 정한다. 목록이 비었으면 연결한 대상이 없다는 뜻이며 미조사로 해석하지 않는다. 미조사·불확실성의 구분이 필요한 기록은 공통 선택 필드 `uncertainty_assessment`에 `assessment`와 `items`를 함께 둔다. `assessment=unassessed`이면 items는 비어 있고, `assessed`이면 실제 불확실성 목록이며 빈 목록은 조사 결과 없음을 뜻한다. 필드 부재는 불확실성 조사를 기록하지 않음이다.

F와 관계의 `subkind`는 종류 정의 기록이 의미와 허용 상태·근거 요구를 소유한다. 초기 F 토큰은 `question`, `conjecture`, `definition_candidate`, `proof_candidate`, `research_direction`, `obstacle`, `partial_result`다. 초기 관계 토큰은 연구 근거·계보를 나타내는 `supports`, `challenges`, `generated_from`, `supersedes`와 수학 판정의 연결을 요구하는 `solves`, `refutes`, `partially_addresses`다. 후자에는 해당 형식 결과와 판정의 `assessment_refs`가 필수다. 다른 구체 종류가 필요하면 같은 후보에서 종류 정의를 먼저 검증하고 사용한다. 종류 정의는 자동 실행권한이나 새로운 상태 전이를 추가하지 않는다. 기계적인 효력은 실행·인증·허가 계약만 소유한다.

### 7.4 일관된 읽기

조회는 인스턴스 상태 커밋 하나를 고정하고 그 안의 space별 하위 트리를 읽는다. AI 입력은 snapshot_commit과 실제 동봉한 파일을 해시로 결박한다. 연구 자료의 캐시는 research 하위 트리 OID로 재사용할 수 있지만 새로운 실행권한을 그 캐시에서 추측하지 않는다.

실행기는 자기 쓰기 전에 현재 ref·부모·필수 트리·상태의 무결성을 검사한다. 다른 주체의 쓰기나 저장 손상이 있으면 적용을 중지하고 저장 복구를 연다. 과거 판정의 상태 커밋은 현재 머리와 같을 필요가 없다. 보존한 커밋과 입력 바이트의 실재·해시를 확인한다.

### 7.5 보존과 청소

자료 보존의 단위는 판단·권한·재현이 기대는 원자료다. 채택된 결과의 의존 원자료, 실패를 진단하는 종료 기록과 사용자 결정 원문을 조용히 없애지 않는다. 보존 정책을 적용할 때는 참조 폐쇄와 사용자 승인 범위를 먼저 검사한다.

캐시·임시 파일·종료된 작업 공간의 청소 실패는 이미 수신한 결과와 공용 편입을 무효화하지 않는다. 원자료가 보관됐고 프로세스 종료가 확인된 정확한 경로만 청소한다. 일상 poll에서 아무 상태도 바뀌지 않았으면 새 영구 사건을 만들지 않는다. 판정을 내렸다면 그 판정이 읽은 관찰 스냅샷을 보존한다.

<a id="d08"></a>
## 8. AI 입력과 원자료 회수

### 8.1 입력 묶음

실행 요청의 입력 manifest는 다음을 가진다.

- 이번 질문, 활동의 범위와 출력 계약.
- 해당 활동의 공통 실행 규칙과 필요한 역할 지침.
- 적용 허가·헌장·정책의 정확한 참조와 이번 판단에 직접 필요한 문면.
- 지정 대상의 정확한 판본과 필수 근거.
- 이전 실패·판정·미결 사항 가운데 이번 활동이 처리할 항목.
- 원자료를 조회할 읽기 스냅샷과 허용 범위.

역할 지침은 필요한 정의를 직접 제공하거나 읽을 위치와 시점을 지정한다. 모든 역할에게 전체 용어집과 전체 도구 문서를 무조건 동봉하지 않는다. 필수 읽기 범위는 출력 판정 전에 확보됐는지 검사할 수 있게 manifest에 명시한다.

### 8.2 두 종류의 완전성

지정 대상의 필수 범위는 전건 검사한다. 예를 들어 해설 동일성 검토의 할당 수학 항목이나 사용자 허가의 대상 행동은 빠뜨리지 않는다.

연구 저장소의 탐색은 조회로 수행한다. K·F·전체 후보·전체 이력의 목차를 매 실행에 전부 넣지 않는다. 조회는 필터·안정된 정렬·페이지 cursor·전체 수·실은 수를 반환하며 잘림을 숨기지 않는다. cursor는 고정한 읽기 스냅샷에서만 유효하다.

계획자는 탐색한 범위와 보류한 질문을 기록한다. 저장소 전부를 읽지 않았는데 전수 검토로 보고하지 않는다. 작업 배정이 이미 약속된 대기 과제는 실행기가 별도 원장으로 보존하고 도래 사건에 맞춰 재검토하므로, 탐색에서 보지 못했다는 이유로 사라지지 않는다.

### 8.3 토큰 예산

입력 생성기는 실제 실행 프로필의 tokenizer로 system·도구·직접 입력을 계산하고, 해당 실행에 예약한 최대 출력과 환경 여유를 뺀 한도에 맞춘다. 고정 비율만으로 통과시키지 않는다.

필수 범위가 맞지 않으면 생성기가 그 범위를 임의로 요약·삭제하지 않는다. 독립적으로 판정할 수 있는 부분으로 분해하고 의존 판정을 받는 계획을 제안하거나, 그 실행의 입력 불가를 반환한다. 분해할 때는 항목의 덮개뿐 아니라 부분 사이의 정의·가정·양화·결론 연결을 확인할 활동을 배정한다.

이전 대화 전문은 감사 자료로 보존할 수 있지만 다음 실행의 필수 입력이 아니다. 후속 실행은 판본화된 쟁점·답변·판정·재개 기록과 필요한 원자료를 받는다. 역할 연속성을 비공개 모델 상태나 전체 transcript 복원에 의존시키지 않는다.

반복 쟁점은 issue_state에 현재 주장·살아 있는 반박·현재 처분·원자료 참조를 기록한다. 해소된 쟁점도 원자료는 보존하되 현재 판단을 바꾸지 않는 과거 전문을 직접 입력으로 누적하지 않는다. 어떤 반박이 더는 적용되지 않는다는 결론은 해당 의미 검토의 근거를 필요로 한다. 현재 쟁점의 새 요약을 기준 입력으로 사용하려면 독립 대조가 누락·범위·가정 보존을 확인해야 한다. 그 요약이 원자료의 권위를 대신하지는 않는다.

현재 필수 쟁점도 분해하거나 컨텍스트에 넣을 수 없으면 활동은 unresolved로 종료하고 범위 재구성·추가 조사·다른 지원 프로필의 선택을 다음 계획에 반환한다. 같은 초과 입력을 자동 반복하지 않는다.

### 8.4 검색과 재개 자료의 품질

query는 정확한 ID·종류·관계 이웃·출처·본문 질의를 지원하고 사용한 필터·정렬·페이지 범위를 돌려준다. 계획자는 용어·표기 변이와 관련 맥락을 탐색 후보로 사용할 수 있지만 그 자체로 수학적 동의성을 확정하지 않는다. 한 질의의 빈 결과를 저장소 전체의 부재로 보고하지 않는다.

큰 도구 결과의 수신, 중요한 보조정리·가정의 채택, 주요 접근의 폐기, 다른 실행으로의 인계와 정지 준비에는 현재 주장·근거·시도한 경로의 결과·남은 질문·다음 행동을 체크포인트에 남긴다. 비공개 사고 과정의 전문을 요구하지 않는다. 이미 자동 보존한 자료는 정확한 참조로 연결하고 중복 전사하지 않는다.

<a id="d09"></a>
## 9. 연구 계획과 후속 활동

### 9.1 계획을 여는 사건

실행기는 다음 사건을 받으면 계획 요청을 보존한다.

- 최초 허가와 연구 상태가 준비됨.
- 연구 결과·검토 결과·사용자 결정이 다음 선택을 바꿀 수 있게 됨.
- 대기 과제의 입력이나 외부 사건이 도래함.
- 이전 계획이 지정한 재검토 시각이 도래함.
- 사용자가 연구 계획의 재검토를 요청함.

한 인스턴스에는 실행 중인 연구 계획 활동 하나만 둔다. 그동안 도래한 사건은 다음 계획의 입력으로 합친다. 계획이 결과를 반환하면 이번에 소비한 사건 cursor와 남은 사건을 원자적으로 기록한다. 처리하지 않은 사건을 완료로 옮기지 않는다.

현재 계획의 목표·허가를 사용자가 명시적으로 대체하면 실행기는 그 입력을 사용하는 계획 실행을 공통 취소 경로로 끝내고 새 입력으로 계획한다. 무관한 결과 도착마다 계획을 취소하지 않는다. 일반 결과는 다음 계획에 합친다. 단일 계획이 만드는 지연은 연구 효능 검증에서 측정하며, 그 근거 없이 다중 계획 조정 프로토콜을 추가하지 않는다.

### 9.2 계획의 산출

계획 결과는 다음을 가진다.

- 비교한 연구 목표와 현재 결과.
- 탐색한 후보·원자료의 범위.
- 선택할 새 작업 계약과 기존 과제의 다음 활동.
- 작업 예산 안의 배정 순서와 병행 관계.
- 각 선택의 기대, 근거의 정보 상태와 불확실성.
- 보류한 사항과 재검토 사건 또는 시각.
- 실제 새 결과와 과거 기대의 차이.

아무 작업도 선택하지 않은 결과도 유효하다. 이 경우 보류 이유와 다음 재검토 조건이 필수다. 빈 선택을 낡음이나 실패로 분류하지 않는다. 입력·권한·판정 대상이 바뀌지 않았으면 동일한 빈 선택을 즉시 다시 요청하지 않는다.

계획은 모델 용량을 모두 채울 의무가 없다. 탐색과 집중 활용, 후보 간 중복·보완, 과거 실제 결과와 대기 이력을 고려한다. 고정 점수나 발견 개수만으로 연구 가치를 계산하지 않는다.

### 9.3 적용 전 확인

계획 결과는 고정한 입력에 대한 판단이다. 적용 직전 실행기는 선택된 작업마다 현재 계약·입력·허가와 미점유를 검사한다. 무관한 원장 전진이나 다른 작업의 체크포인트는 폐기 이유가 아니다.

선택은 실행별로 적용한다. 함께 성립해야만 의미가 있는 일은 한 작업 계약의 내부 단계로 묶거나, 앞 결과를 뒤 계약의 필수 입력으로 연결한다. 여러 OS 프로세스의 실질 행동 시작을 원자적으로 보장하는 배정 그룹은 초기 구현에 두지 않는다.

기계가 검사한 참조·해시·허가의 변화에 의미 판단이 필요하면 해당 선택의 적용을 보류하고 변경된 근거를 다음 계획에 넘긴다. 의미가 바뀌었는지와 기존 선택을 유지할지는 그 AI 활동이 판정한다. 실행기가 선택 내용을 임의로 바꾸어 대체 작업을 시작하지 않는다.

### 9.4 해결 이후

목표 감사가 해결을 확인하면 새 연구 생산 과제의 배정을 멈추고 헌장이 요구하는 학술 검증을 계획한다. 이미 승인된 실행의 종료 여부는 기존 실행 허가의 정지 조건을 따른다. 외부 검토의 거부는 외부 사건으로 기록하며, 그 자체로 Lean 결과의 형식 타당성을 바꾸지 않는다.

형식·동일성·목표 근거의 결함이 확인되면 목표 해결의 근거를 철회하거나 정지한다. 다시 연구할 권한이 현재 허가에 남아 있으면 미해결 상태에서 계획을 재개한다. 허가가 끝났으면 새 허가를 요청한다. 목표의 사실 상태를 바꾸기 위해 사용자가 틀린 해답을 승인하거나 반려할 때까지 기다리지 않는다.

<a id="d10"></a>
## 10. 산출물 공개와 공용 편입

### 10.1 산출물과 공용 기록

`output_accepted` 실행의 산출물은 불변 묶음이다. 공용 기록으로 편입되기 전에도 후속 계획과 검토가 명시된 정보 상태로 읽을 수 있다. 그 접근은 인증 승인을 뜻하지 않는다.

연구 자료의 공용 편입은 출처·참조·정보 상태·허가와 저장 형식을 검사한다. 일반 연구 기록의 판단은 저자의 주장으로 보존하며, 형식 타당성·동일성·목표 해결의 권위를 부여하지 않는다. 그 권위가 필요한 소비자는 해당 판정 기록을 요구한다.

Lean 정본 편입, 해설의 인증된 연결, 목표 해결의 선언은 각각 [수학 검증](#d11)의 관문을 요구한다. 어느 관문도 일반 연구 기록의 상태 문자열만으로 통과하지 않는다.

### 10.2 변경 제안

공용 변경 제안은 integration_id, base_snapshot_commit, 변경할 연구 기록의 이전 해시, 신규·수정·철회 기록, 필요한 판정·허가, 영향받는 실제 의존 집합을 가진다. 삭제·외부 효과는 별도 권한을 요구한다. 제안의 저작자가 영향 근거를 작성한다.

한 변경 묶음은 함께 의미가 성립하는 최소 단위다. 서로 의존하는 정의·정리·연결 기록은 함께 검사한다. 독립적인 연구 기록은 각각 편입할 수 있다. 과제의 모든 산출물이 같은 편입에 들어가야 한다는 조건을 두지 않는다.

### 10.3 편입 순서

1. 제안의 입력·산출 바이트와 생성·판정·허가의 출처를 검사한다.
2. 현재 상태 커밋의 research 트리에서 바꾸는 기록의 이전 해시와 적용 전제를 대조한다.
3. 동일 기록의 이전 해시·참조·권한이 어긋나면 그 변경만 보류하고 작성자 또는 지정 검토에 반환한다. 의미 충돌의 유무와 해소는 그 AI 활동이 판정한다. 실행기가 수학적 병합을 추측하지 않는다.
4. 후보 연구 트리에 변경을 적용하고 스키마·ID·종류·참조 폐쇄·판정·허가·영향 범위를 검사한다.
5. 인덱스와 파생 보기를 재생성한다. Lean 편입이면 활성 신뢰 환경에서 최종 형식 검사를 수행한다.
6. 후보 research 트리와 최신 runtime 트리에 편입 결과·과제·판정·권한·후속 활동을 함께 반영한다. 편입 기록에는 자기 커밋 OID를 넣지 않는다.
7. 현재 상태 커밋을 유일한 부모로 하는 새 상태 커밋을 만든다.
8. 예상한 이전 OID를 검사해 인스턴스 ref 하나를 새 커밋으로 갱신한다.

조건부 ref 갱신이 실패하면 편입과 후속 상태의 효력을 적용하지 않는다. 외부 OS·서비스 행동은 이 Git 갱신 안에서 일어난 것으로 취급하지 않는다. [외부 행동 계약](#d13)을 따른다.

긴 검사와 Lean 빌드는 고정 입력의 기계 작업으로 실행하며 실행기의 정지·조회 처리를 막지 않는다. 쓰기 직렬화는 실제 상태 적용 구간에만 걸린다. 검사 중 새 사건이 생겼으면 최신 상태를 부모로 만들고 관련 적용 전제만 다시 대조한다. 오래된 runtime 사본으로 진행 중 실행과 예산을 덮어쓰지 않는다.

### 10.4 영향 처리

제안 작성 AI가 실제 영향을 받는 입력·허가·인증 의존과 처분을 기록한다. 목적·권한·신뢰·완료 기준에 영향을 주는 변경은 해당 분야의 독립 검토가 이 범위와 처분을 확인한다. 기계는 기록된 참조와 기계적 의존 폐쇄를 대조한다. 무관한 기록의 갱신을 전역 낡음으로 전파하지 않는다. 실행 중인 일의 허용 행동을 바꾸면 같은 원장 변경에서 해당 실행의 다음 처분을 기록한다.

권한이 사라지는 변경은 실행 중인 해당 실행을 `stopping`으로 바꾸어 새 행동부터 막고, 예약 전 요청은 취소한다. 해설·목표의 근거만 바뀌면 필요한 검토·계획을 예약한다. 정보가 부족해 영향 범위를 확정할 수 없으면 변경을 적용하지 않는다. 보수적 범위의 사용 정지와 조사는 독립 검토가 그 범위와 권한을 확인한 별도 처분으로 적용할 수 있다.

### 10.5 수리와 실패 반환

표기 정규화·파생 보기 재생성은 의미를 보존하는 도구 수리다. 도구는 변경 전후 해시와 규칙을 자동 기록한다. 깨진 참조, 다른 명제, 누락된 근거를 유사한 것으로 채우지 않는다.

반환 결과는 실패 항목 전건과 원문 좌표, 이전 검사와 다른 입력, 수리한 항목, 남은 범위와 다음 소유자를 가진다. 후속 실행은 이를 필수 입력으로 받고 항목마다 조치 또는 남은 이유를 반환한다. 해결되지 않은 의미 충돌을 형식 수리로 표시하지 않는다.

## 11. 수학적 결과의 검증

### 11.1 형식 결과·해설·판정

형식 결과는 선언 이름·정규 타입·본문·의존 폐쇄·신뢰 환경을 고정한다. 해설은 파일 바이트와 수학 항목을 고정한다. 동일성 판정은 둘의 정확한 판본과 적용 검토 방침을 참조한다. 판정의 본문과 입력은 봉인 뒤 수정하지 않는다.

수학 제안은 다음을 포함한다.

- 새 형식 결과 또는 기존 형식 결과의 정확한 참조.
- 해설의 정의·가정·명제·양화·증명 단계·범위·결론별 항목 ID와 anchor.
- 각 수학 항목과 Lean 선언·타입의 binder·부분식·명명한 보조정리의 대응.
- 해설이 실제로 사용하는 문헌·데이터 원문의 내부 보존 사본과 해시·anchor.
- 해설이 수학 사실로 주장하지 않는 동기·역사·비유의 구분.
- 목표 연결을 주장하면 해당 헌장 항목과 주장 범위.

기존 형식 결과를 새 해설로 설명하는 제안은 새 Lean 선언과 새 K 객체를 요구하지 않는다. 해당 결과에 새 해설과 동일성 판정을 연결한다. Mathlib의 정의·정리를 외부 수학 의미로 직접 사용하는 최초 해설도 그 선언과 해설의 연결을 검토한다.

### 11.2 기계 예비 검사

검토 전에 지정된 도구가 다음을 검사한다.

1. 제안·해설 항목·대응·근거 manifest의 스키마와 참조 폐쇄.
2. 항목·anchor·선언의 유일성과 할당 범위의 덮개.
3. 명시한 양화 순서·영역·의존을 연결하는 좌표의 존재.
4. 고정된 환경에서의 Lean 빌드·커널 수락·전이적 공리 감사.
5. 포함 선언의 의존 폐쇄와 실제 소스·도구·환경 해시.

기계는 자연어 문장 전체가 빠짐없이 수학 항목화됐는지 판단하지 않는다. 항목화의 의미적 누락과 부정확한 대응은 독립 검토가 판정한다. 기계 검사가 좌표의 존재만 확인한 것을 동일성 확인으로 표시하지 않는다.

예비 검사 실패는 형식·입력 결함으로 반환한다. 그 입력으로 동일성 검토를 시작하지 않는다. 기존 형식 결과만 참조하는 제안은 해당 결과와 현재 사용할 신뢰 환경의 유효성을 확인하며 선언을 중복 생성하지 않는다.

### 11.3 검토 방침과 범위

검토 방침은 정확한 판본으로 승인해 사용하며 다음을 가진다.

| 필드 | 의미 |
|---|---|
| `required_perspectives` | 반드시 볼 관점과 각 관점의 독립 실행 수 |
| `final_judges` | 최종 독립 판정자의 수와 자격·프로필 |
| `execution_limit` | 범위 계획·초기 검토·보충·최종 판정·재시도를 합친 이번 활동의 AI 실행 총수 상한 |
| `scope_rule` | 수학 항목의 분할, 의존 경계와 전체 일관성을 확인할 방법 |
| `required_evidence` | 판정별 필수 근거 |
| `independence_rules` | 금지한 저작·컨텍스트 계보, 같은 단계의 결과 비노출, 요구 관점·자격 |

필수 관점 목록은 비어 있을 수 없고 각 관점의 실행 수와 최종 판정자 수는 양수다. 전체 실행 한도는 필수 범위 계획·검토·판정을 수행할 수 있어야 한다. 필수 판정자가 없어서 만장일치 조건이 공허하게 참이 되는 방침은 거부한다.

독립 검토는 대상의 저작 실행과 그 저작을 이어받은 실행에서 나온 컨텍스트를 resume·fork하지 않는다. 입력은 허가한 원자료와 검토 기록으로 새로 구성한다. 배정은 producer_execution_ids, continuation_of, context_origin과 입력 manifest를 대조한다. 같은 모델·계정의 사용은 그 자체로 독립성 위반도 오류 독립성의 증거도 아니다. 모델·도구·관점의 다양성 요구는 방침 값으로 명시하고 실제 오류 검출·오탐·미해결률로 평가한다.

이 초안의 권고 출발 구성은 논증 재구성·범위 반박·의미 동일성 관점의 독립 검토 각 하나와 최종 독립 판정자 셋이다. 실제 적용 구성은 승인한 방침이 소유한다. 구성 축소를 이 초안의 단순화에서 자동 도출하지 않는다.

문헌 전사가 있으면 원문 충실성 관점을 요구한다. 전문 분야의 검토가 필요한지는 작성자 선언과 독립 범위 계획이 정한다. 필요한 관점을 수행할 수 없으면 범위를 빠뜨린 승인을 만들지 않고 미해결로 끝낸다.

큰 제안은 수학 항목과 의존 경계를 기준으로 나눌 수 있다. 각 할당은 읽을 항목·정의·가정·의존 판정을 명시한다. 전체 제안의 범위·가정·결론 연결을 확인할 할당도 반드시 둔다. 부분 결과의 합집합이 항목 ID를 덮는다는 기계 검사만으로 전체 동일성을 승인하지 않는다.

### 11.4 유한한 검토 활동

검토 활동 하나는 제안 판본 하나에 대해 다음 단계만 수행한다.

1. **범위 고정.** 예비 검사와 검토 방침을 대조해 할당·독립성·필수 입력을 고정한다.
2. **초기 독립 검토.** 각 실행은 자기 범위 전건과 필요한 원자료를 읽고 확인한 사항·불일치 주장·미해결 질문을 반환한다.
3. **보충 계획.** 초기 결과의 쟁점과 남은 예산을 기록하고, 지정된 범위 계획자가 판정을 바꾸는 질문을 선택한다. 이 선택에 AI 실행을 사용하면 같은 전체 실행 한도에 센다. 최종 필수 판정의 몫을 먼저 남긴다.
4. **예산 안의 보충 조사.** 답을 받은 뒤 후속 질문을 만들 수 있다. 각 조사·질문 정리·재시도는 같은 activity의 execution_limit에 포함하며 자식 활동 ID로 한도를 다시 얻지 못한다. 한도 안에서 일부 질문만 조사할 수 있지만 미조사·미해결 목록을 보존하고 전건 완료로 보고하지 않는다. 필요한 판단이 정해지거나 예산이 끝나면 다음 단계로 간다.
5. **최종 독립 판정.** 판정자는 원래 제안, 초기 검토, 보충 결과와 원자료를 대조한다. 다른 최종 판정자의 이번 결과를 보기 전에 자신의 판정을 봉인한다.
6. **집계와 종료.** 아래 집계표를 적용하고 결과·남은 질문·다음 소유자를 원장에 기록한다.

검토 중 제안 바이트를 수정하지 않는다. 수정이 필요하면 그 요구를 반환하고 새 제안 판본의 새 활동으로 다룬다. 범위가 독립적으로 나뉘어 과거 판정을 재사용할 수 있으면 아래 승계 조건을 적용한다.

승계 가능한 판정은 자신이 읽은 수학 항목·정의·가정·의존·검토 방침을 scope_manifest에 해시로 고정한 것이다. 새 활동의 범위 계획은 변경 항목·그 역의존·전체 연결 할당을 검토하고, 입력과 전제가 같은 불변 할당만 정확한 이전 판정 참조로 승계한다. 범위·의존이 충분히 봉인되지 않은 과거 판정이나 전체 해설 해시 하나만 가진 판정은 국소 변경을 이유로 승계하지 않는다. 새 제안의 전체 연결 판정은 따로 수행한다.

필수 검토 실행이 산출을 끝내지 못하면 그 실행은 `execution_incomplete`다. 이미 정상 봉인한 다른 검토는 보존한다. 수정된 입력이나 확인된 실행 환경 복구가 있으면 빠진 실행만 새 ID로 다시 수행할 수 있다. 그런 근거가 없으면 검토 활동을 미해결로 종료한다. 미완료 실행에 판정값을 만들어 넣지 않는다.

재시도도 execution_limit에 포함한다. 필수 판정을 끝낼 예산이 없으면 실제 완료 범위와 남은 쟁점을 갖춘 unresolved로 활동을 끝낸다. 이 상태가 다음 연구의 존재를 금지하지는 않지만 같은 활동의 한도를 무시한 계속 실행은 허용하지 않는다.

### 11.5 판정과 집계

최종 판정자는 `match`, `mismatch`, `unresolved` 중 하나를 낸다.

이 값은 해당 판정자의 근거 있는 주장이다. 개별 mismatch를 제출했다는 사실만으로 그 반례의 타당성이 시스템 전체에서 입증된 것은 아니다. 집계는 판정자의 주장을 사실로 바꾸는 도구가 아니라 적용한 검토 방침의 결과다.

- `match`: 할당된 필수 범위를 모두 대조했고 동일성을 확인했다.
- `mismatch`: 정확한 좌표와 논증으로 하나 이상의 의미 불일치를 확인했다.
- `unresolved`: 입력을 읽고 정해진 검토를 수행했지만 필요한 판단을 확정하지 못했다.

최종 집계는 다음과 같다.

| 조건 | 활동 결과 | 다음 행동 |
|---|---|---|
| 필수 범위·경계 검토가 완결되고 최종 판정 전건이 `match` | `match` | 최종 기계 검사와 편입 검사로 이동 |
| 최종 판정 전건이 `mismatch`이고 각 판정의 필수 근거가 유효 | `mismatch` | 불일치 전건을 연구 계획·수정 활동에 반환 |
| 판정이 갈리거나 하나라도 `unresolved`, 또는 필수 실행·범위가 미완료 | `unresolved` | 실제 완료 범위와 남은 질문을 다음 계획에 반환 |

상한 도달이나 의견 불일치를 불일치의 입증으로 바꾸지 않는다. `unresolved`는 인증 승인이 아니다. 미해결 활동은 실행·예산을 점유하지 않고 끝나며, 다음 연구 계획이 추가 조사·범위 변경·다른 접근·보류를 판단한다.

집계가 unresolved여도 개별 불일치의 주장·좌표·논증·반박을 삭제하거나 일반적인 불확실성 한 문장으로 대체하지 않는다. 결과는 disputed_findings와 아직 검증하지 않은 범위를 구분해 후속 계획에 준다. 이미 별도의 적격 검사로 확인한 결함은 그 검사 근거를 유지한다.

### 11.6 최종 검사와 K 편입

동일성 `match` 뒤 도구는 제안·해설·대응·근거와 환경의 해시를 다시 대조하고 활성 신뢰 환경에서 최종 형식 검사를 수행한다. 정확한 형식 결과·해설·판정의 연결을 공용 변경으로 편입한다.

봉인한 제안 파일이 예기치 않게 바뀌면 저장 무결성 결함으로 차단한다. 그 변화를 새 제안으로 정당화하지 않는다. 작성자가 내용을 의도적으로 수정하려면 이전 묶음을 보존하고 새 판본을 제출한다. 환경이 바뀌었으면 [신뢰 전환](#d15)이 정한 재검증을 수행한다.

형식 결과는 목표와 무관한 정확한 부분 결과여도 편입할 수 있다. 아직 기록하지 않은 논리적 귀결을 자동으로 K 객체로 만들지 않는다. F와의 해결·반박·부분 대응 관계는 실제로 확인한 의미와 판정 근거를 갖춘 별도 관계다.

### 11.7 목표 감사

목표 감사는 현재 헌장의 목표·범위·성공 기준과 실제 사용할 K 결과·해설·동일성 판정을 비교한다. 감사자는 해당 해답을 작성한 실행과 독립이다.

결과는 `satisfied`, `not_satisfied`, `unresolved`다. 전건의 필수 감사가 현재 판본에서 `satisfied`일 때만 목표를 `mathematically_solved`로 기록한다. 그 밖의 목표 상태는 `unsolved`이며, 미감사·조건 미충족·근거 정지·범위 변경의 이유를 별도로 표시한다. `unsolved`는 수학적으로 해결 불가능하다는 판정이 아니다.

목표 감사가 실패해도 정확한 부분 결과는 유지한다. 해설이 결과를 과장했으면 동일성·범위 검토로 반환한다. 목표가 바뀌면 과거 감사는 그 대상에 대한 기록으로 보존하고 새 목표에 자동 적용하지 않는다.

### 11.8 재심사와 사용 효력

판정의 봉인된 내용은 고치지 않는다. 사용 효력은 별도 기록의 `active`, `suspended`, `withdrawn`으로 관리한다.

일반 결함 제보는 검토 입력으로 접수한다. 제보만으로 판정의 사용 효력을 바꾸지 않는다. 결정론 검사로 확인한 결함 또는 정식 독립 검토 활동이 제출한 구체적 의미 이의가 있으면 해당 판정의 사용을 `suspended`로 바꾸고 유한한 재심사를 연다. 새 목표 해결·새 인증의 전제로 사용할 수 없지만 원자료를 삭제하지 않는다.

| 재심사 결과 | 효력 |
|---|---|
| 현재 대상의 동일성을 다시 `match`로 확인 | 그 새 판정과 근거를 연결하고 사용을 복원 |
| `mismatch` | 기존 잘못된 연결을 `withdrawn`으로 만들고 영향 처리 |
| `unresolved` 또는 실행 미완료 | `suspended` 유지, 남은 질문의 소유 과제와 재검토 조건 기록 |

미해결 재심사도 활동 자체는 종료한다. 인증 상태를 닫을 수 없다는 이유로 실행이나 과제 점유를 붙잡지 않는다. 동일 내용의 제보로 완료한 재심사를 자동 반복하지 않는다. 새 근거·변경된 대상·명시적 재검토 결정이 있어야 새 활동을 연다.

철회·정지는 실제로 해당 판정을 사용한 목표·해설 연결·후속 판정에만 전파한다. 형식 타당성이 유지되는 Lean 결과는 보존한다. 독립적으로 유효한 다른 연결은 별도로 판정한다.

<a id="d12"></a>
## 12. 운영 관찰과 복구 판단

### 12.1 관찰의 소유자

기계 실행기는 작업 예산의 AI 실행 시작 때 다음 운영 검토 시각을 정한다. 주기는 승인된 실행 프로필의 범위 안에 있어야 한다. 작업자가 자신의 관찰을 무기한 미루는 조건을 작성하지 않는다.

운영 예산의 AI 활동과 기계 작업에는 프로필이 고정한 실행 기한과 도구 실패 검사를 적용한다. 운영 실행의 점검을 위해 다른 운영 실행을 재귀적으로 열지 않는다. 운영 실행이 기한을 넘거나 도구 실패로 끝나면 기계 실행기가 공통 종료를 수행하고 부분 결과를 보존한다. 원인 판단이 필요하면 종료·예약 반환 뒤 후속 운영 활동을 연다. 원격 종료 미확인처럼 예약을 반환할 수 없는 경우에는 모델을 새로 호출하지 않는 어댑터 대조를 먼저 수행한다.

실행기는 실제 프로세스 상태, 진행 중 도구 호출, 마지막 공개 체크포인트, 자원 사용과 허가를 관찰한다. 판단에 사용한 관찰은 시각·실행 ID·파일 해시와 함께 불변 스냅샷으로 보존한다. 작업자의 자기 평가는 그 스냅샷에 포함되는 자료이며 운영 상태의 정본이 아니다.

작업자는 상태·시도·근거·현재 장애물·다음 방법을 공개하고 더 이른 점검을 요청할 수 있다. 진전 보고의 횟수와 산출량만으로 수학적 진전을 판정하지 않는다.

### 12.2 점검을 여는 조건

작업 예산 실행의 예정 시각 도래, 실행기의 프로세스·권한·저장 불일치 발견, 작업자의 점검 요청, 필수 입력·권한의 변화, 후속 실행을 위한 복구 필요가 점검을 연다. 운영 예산 실행 자체의 실패는 12.1절의 종료 뒤 처리 규칙을 따른다.

한 실행에는 열려 있는 운영 점검 활동 하나만 둔다. 점검 중 새 사건이 오면 그 입력으로 쌓거나 다음 점검에 넘기고 같은 목적의 점검을 중복 개설하지 않는다. 예정 시각을 갱신한 뒤까지 바뀌지 않은 사실만으로 새 점검을 즉시 열지 않는다.

도구 호출 중 작업자가 응답할 수 없으면 그 호출 상태와 공개 자료로 판단한다. 응답 불가능을 수학적 무진전이나 불성실로 판정하지 않는다. 실제 실행권한의 정지 요청은 도구 호출 여부와 무관하게 적용되며 종료 유예를 넘기면 공통 종료 절차가 강제 종료한다.

### 12.3 점검 결과

점검자는 실제 작업 자료·코드·로그·체크포인트·프로세스·허가를 읽고 다음 가운데 하나를 제안한다.

| 처분 | 필요한 근거 |
|---|---|
| 계속 | 현재 실행을 계속할 이유와 다음 검토 시각 |
| 입력·환경 수리 | 바꿀 대상, 의미 보존 여부와 검증 방법 |
| 체크포인트 재개 | 사용할 정확한 자료와 재실행할 범위 |
| 처음부터 재시도 | 이전 외부 효과와 재생 안전성, 다시 수행할 범위 |
| 과제 변경·종결 | 완료·잔여 범위와 권한 근거 |
| 사용자 결정 요청 | 기존 허가로 정할 수 없는 선택과 실제 효과 |

계속 여부는 경과 시간이나 무진전 보고 횟수만으로 정하지 않는다. 실제 시도와 남은 가능성, 계약·환경의 적합성을 대조한다. 추가 수학 조사가 필요하면 작업 예산의 활동을 요청하고 점검 실행은 끝난다.

### 12.4 처분 적용

실행기는 처분을 적용하기 직전에 같은 실행인지, 권한과 실제 상태가 여전히 처분의 전제를 만족하는지 확인한다. 새로운 유효 산출이나 종료가 점검의 전제를 바꾸었으면 적용하지 않고 변경 사실을 반환한다. 전체 원장 OID가 바뀌었다는 사실만으로 판정을 폐기하지 않는다.

정본 용어는 운영 점검이다. 예약된 관찰과 사건 진단은 같은 operational_review 활동의 diagnosing 단계다. 재개·재시작의 안전 확인은 그 활동의 checking_recovery 단계이며, 최초 진단 실행과 다른 새 운영 실행이 수행한다. 같은 대상의 운영 점검 활동 하나라는 제한은 두 단계 전체에 적용한다.

| 제안 | 의미 승인과 적용 경로 |
|---|---|
| 계속·다음 점검 시각 | 진단 결과와 현재 전제가 맞으면 실행기가 적용 |
| 의미 보존 수리 | 도구 소유자의 허용 수리와 검사 결과로 적용 |
| 재개·재시작 | checking_recovery가 범위·체크포인트·외부 효과의 재생 안전성을 확인한 뒤 새 실행으로 적용 |
| 과제 질문·범위·완료 기준 변경·종결 | 5.5절의 연구 계획 저작과 독립 계약 검토로 반환; 사용자 목표·허가 변경이면 결정부터 수입 |
| 사용자 권한 필요 조치 | 의도 해석 활동과 결정 대기로 반환; 승인 전 효과 없음 |

실행기만 바이트를 쓴다는 사실이 의미 승인 권한은 아니다. 활동 결과는 새 계약·재개·결정의 실제 다음 소유자와 대기 조건을 함께 기록한다.

이미 허가가 회수됐거나 프로세스가 종료된 실행은 다시 허가하지 않는다. 복구를 승인하면 새 실행에 정확한 체크포인트·실패 기록·외부 행동 원장을 입력으로 준다. 공유 도구의 결함은 해당 도구 판본의 소유자가 수정하며, 연구 작업자가 같은 이름으로 다른 도구를 끼워 넣지 않는다.

<a id="d13"></a>
## 13. 사용자 결정과 외부 행동

### 13.1 수입과 승인

입력은 내부 불변 묶음으로 복사해 출처와 바이트 해시를 기록한다. 이후 판단은 그 사본을 사용한다. 새로운 문헌·데이터의 수입과 사용자의 규범·허가 수입을 구분한다.

의도 해석 활동은 사용자 입력에서 목표·범위·허가·선호를 추출하고, 원문 좌표와 내부 변경안을 연결한다. 원문이 이미 정한 값을 다시 미결정으로 만들지 않고, 남은 중요한 선택은 질문한다. 원문을 새로운 헌장·정책의 의미로 해석하는 최초 작성과 변경은 다른 의도 해석 실행이 원문과 대조해 누락·왜곡·창작된 선호를 검사한다. 이미 제시한 정확한 구조화 변경에 대한 직접 승인은 새 의미 해석 활동을 요구하지 않는다.

사용자에게 제시한 정확한 변경에 명시적 승인을 받았으면 그 답과 대상을 연결해 결정 기록을 만든다. 해석 과정에서 새로운 값·범위·효과 선택이 생겼으면 그 부분을 평이한 문면으로 확인한다. 명확한 승인을 보편적으로 두 번 받게 하지 않는다.

사용자는 제시한 선택지 밖의 답도 할 수 있다. 답을 현행 계약으로 표현할 수 없으면 필요한 변경이나 남은 해석을 설명하고 다시 확정한다. 닫힌 선택지에 맞도록 사용자 답의 의미를 바꾸지 않는다.

### 13.2 허가와 사례

허가 기록은 허용 주체, 행동 종류, 대상·범위, 자원 한계, 효력 기간·종료 조건, 외부 효과, 재생 허용 여부와 원문을 가진다. 자동 적용은 그 명시 범위 안에서만 가능하다.

과거 사례는 추천·해석의 근거다. 사례의 유사성을 판정한 AI 결과 자체가 새 권한은 아니다. 사용자가 일반 적용 범위를 승인했다면 그 허가를 직접 참조한다. 적용 범위가 불명확하거나 서로 충돌하면 해당 행동을 수행하기 전에 사용자에게 묻는다.

허가의 철회·축소는 새 결정으로 기록한다. 관련 실행의 새 행동부터 막고 종료·영향 처리를 예약한다. 과거에 실행한 외부 행동이 취소된 것처럼 이력을 바꾸지 않는다.

### 13.3 외부 효과의 원장

외부 전송·공개·결제·계정 작업처럼 되돌릴 수 없거나 재생에 주의가 필요한 행동은 승인된 도구 어댑터를 통해서만 수행한다. 어댑터는 실행 전에 `action_id`, 허가 참조, 정확한 요청, 재시도 규칙과 외부 식별자를 원장에 기록한다.

행동 상태는 prepared, confirmed, failed, unknown, cancelled다. prepared는 실행 전에 요청과 허가를 보존한 상태이며 전송 사실의 증거는 아니다. 실제 호출 직전에 현재 허가를 다시 검사한다.

| 조건 | 전이·다음 행동 |
|---|---|
| 성공 효과를 영수증으로 확인 | prepared 또는 unknown에서 confirmed |
| 실패와 효과 부재를 확정 | prepared 또는 unknown에서 failed |
| 호출 전임을 입증했고 허가가 철회됐거나 행동을 취소 | prepared에서 cancelled |
| 소실 뒤 호출 시작 여부 또는 결과를 확정할 수 없음 | prepared에서 unknown, 재전송 금지 |
| unknown에서 효과 부재가 입증되고 현재 허가·멱등 재시도 조건이 유효 | 같은 action_id의 기록된 시도로 재개 |

호출되지 않았다고 입증하지 못하면 취소 요청만으로 cancelled를 만들지 않는다. 실패 영수증이 일부 효과 가능성을 남기면 failed가 아니라 unknown이다. 복구와 행동 소유 활동이 각 미결 행동의 조회 조건·다음 담당을 기록한다.

멱등성이나 결과 조회가 없는 효과의 `unknown`은 사용자에게 올린다. AI가 성공·실패를 추측해 재전송하지 않는다. 이 원장은 재개 입력에 반드시 들어간다.

### 13.4 크리덴셜

기록에는 값 대신 `secret_ref`, 허용 도구·주체·목적을 둔다. 어댑터가 실행 직전에 승인된 저장소에서 값을 읽는다. 값은 AI 프롬프트, Git 기록, 로그와 산출물에 들어가지 않는다.

비밀 값은 실행기 또는 신뢰한 모델·외부 서비스 broker만 보유한다. 연구 코드가 실행되는 프로세스와 자식 환경에는 모델 API key나 주변 계정 비밀을 넣지 않는다. 초기 프로필은 비밀 저장소의 읽기 주체·ACL·전달 방식·회전 뒤의 미종료 호출 처분을 고정한다. 모놀리식 CLI가 자식 도구에 비밀을 노출하지 않음을 입증하지 못하면 그 배치를 활성화하지 않는다.

크리덴셜 부재는 입력의 수학적 타당성 결함이 아니다. 해당 행동 또는 실행을 대기시키고 필요한 공급자·허가를 기록한다. 다른 계정이나 공개 자원으로 임의 대체하지 않는다.

### 13.5 일시 정지

인스턴스 운전 상태는 `initializing`, `active`, `paused`다. `initializing` 또는 `active`에서 정지하면 `paused`와 이전 상태를 나타내는 `resume_lifecycle`을 함께 기록한다. 이미 정지 상태인 인스턴스를 다시 정지해도 복귀 상태를 바꾸지 않는다.

정지 요청은 새 배정을 막는다. `queued` 요청은 예약·프로세스 없이 `ended/cancelled`로 닫고, `starting`·`running` 실행은 `stopping`으로 옮긴다. 기존 `stopping`은 종료를 계속하고 `ended`는 바꾸지 않는다. 종료가 확인될 때까지 `paused` 상태와 종료 진행 목록을 함께 보고한다. `paused`라는 값만으로 모든 프로세스가 종료됐다고 표시하지 않는다.

재개는 복구 검사와 복귀 단계가 요구하는 현재 허가·예산·신뢰 환경 검사를 통과해야 한다. `resume_lifecycle=initializing`이면 아직 만들지 않은 신뢰 환경을 요구하지 않고 14.1절의 남은 단계로 복귀한다. `active`이면 활성화 전건을 검사한다. 이미 끝난 실행은 새 ID로 시작한다. 현재의 목표 상태와 재개 허가를 구분한다.

<a id="d14"></a>
## 14. 초기화·실행기 복구·계약 변경

### 14.1 초기화

초기화 입력은 인스턴스 이름, 내부 저장 위치, 원문 입력, 초기 운영을 허용한 프로필·예산·크리덴셜 참조와 대화 소실 정책을 가진다. 초기 운영 허가는 입력 해석·검증·신뢰 환경 준비에 필요한 범위를 정한다. 이 값이 없으면 새 AI 실행을 시작하지 않고 필요한 항목을 보고한다.

1. 저장 위치·Git 객체 형식·경로 안전과 독점 잠금을 확인한다.
2. 원문 사본을 runtime의 불변 입력 묶음으로 만들고, initializing 상태와 최소 research 트리를 가진 부모 없는 첫 상태 커밋을 만든다. 인스턴스 ref가 없을 때만 생성한다.
3. 초기 운영 예산으로 의도 해석과 필요한 독립 대조를 수행한다. 이미 승인한 정확한 값은 그 좌표로 가져온다.
4. 헌장·정책·실행 허가·예산·검토 방침의 실제 적용 문면을 확정하고 필요한 사용자 결정을 받는다.
5. 신뢰 환경을 준비하고 실행 어댑터·도구·격리·종료·입력 한도 검사를 수행한다.
6. 참조 폐쇄, 승인 대상의 해시, 운영 용량, 활성 신뢰 환경과 실행기 복구 상태를 검사한다.
7. 전건이 유효할 때 원장을 `active`로 바꾸고 첫 계획 활동을 예약한다.

실패한 단계는 입력·결과·남은 항목을 보존한다. 재개는 끝난 단계를 다시 실행하지 않고 기록에서 남은 단계를 계산한다. 새로운 사용자 선택이나 수정된 입력이 없는데 같은 해석 실패를 자동 반복하지 않는다.

### 14.2 복구 순서

새 실행기는 독점 잠금을 얻은 뒤 프로세스 내부에서 배정을 닫고, ref·커밋·필수 트리·최소 runtime 상태를 먼저 읽기 전용으로 검사한다. 이 검사가 통과해야 새로운 engine_id와 복구 시작을 첫 상태 변경으로 기록한다. 실패하면 정본에 쓰지 않고 외부 진단 출력에 OID·실패 근거를 남긴다. 그 뒤 다음을 확인한다.

1. 인스턴스 상태 사슬과 research·runtime 트리의 무결성.
2. 실행 프로필·구현·스키마·도구·입력·산출물의 정확한 판본.
3. 모든 미종료 실행의 로컬 프로세스와 원격 모델 상태.
4. 예산 예약과 실제로 종료가 확인되지 않은 실행의 일치.
5. 진행 중 공용 적용과 외부 행동의 마지막 기록.
6. 작업 공간·체크포인트·불변 묶음의 보존 상태.
7. 대기 과제와 후속 활동의 소유자·재관찰 조건.

모델 실행의 대조는 모델을 새로 호출하지 않는 어댑터 기능으로 수행해야 한다. 원격 실행을 확인할 수 없는데 새 실행을 만들어 진단하지 않는다.

### 14.3 상태별 복구

| 마지막 상태 | 확인한 실제 상태 | 처분 |
|---|---|---|
| `queued` | 실행·예약 없음 | 입력·허가를 다시 검사한 뒤 대기 유지 |
| `starting` | 실제 모델 실행 전임이 확인됨 | 준비 자원 종료·회수, `start_failed`, 예약 반환 |
| `starting` | 실행 시작 여부를 확정할 수 없음 | `stopping`, 상태 대조·부분 산출 회수, 시작 전 실패로 추측하지 않음 |
| `running` | 이전 실행기가 소실됨 | 남은 권한을 회수하고 `stopping`, 로컬·원격 종료 대조 |
| `stopping` | 종료 미확인 | 예약과 작업 공간 유지, 종료·외부 상태 대조 |
| `stopping` | 종료 확인 | 산출 회수·검사 뒤 `ended`, 한 번만 예약 반환 |
| `ended` | 후속 기록 또는 청소 미완료 | 실행을 다시 열지 않고 기록한 후속·청소만 수행 |

실행기 소실은 보유 Job handle의 종료 정책으로 로컬 자식을 정지시킨다. 실제 종료와 원격 모델 종료는 새 실행기가 다시 확인한다. 고아 프로세스가 없을 것이라는 기대를 확인 결과로 사용하지 않는다.

중앙 원장의 신뢰가 깨졌으면 새 쓰기·배정을 중지한다. 한 실행의 상태만 불확실하면 그 실행의 예약과 공간을 보존하고, 다른 실행의 권한·자원 판단이 독립적으로 가능한 범위는 계속 처리한다.

### 14.4 공용 편입 복구

인스턴스 ref 갱신 전이면 만들어진 후보 커밋은 비권위다. 갱신됐으면 해당 상태 커밋의 편입 ID·action 결과·후속 상태를 확인한다. 같은 편입 ID를 다시 받으면 기록한 결과를 반환한다.

과거 편입의 상태 커밋과 현재 머리를 같다고 요구하지 않는다. 과거 커밋의 도달 가능성과 기록한 바이트·판정·허가를 확인한다. 현재 사슬·트리의 무결성 실패는 외부 쓰기 또는 저장 훼손으로 다룬다.

### 14.5 구현·스키마 변경

실행 프로필은 구현 커밋, 스키마 묶음, 도구·역할 지침 manifest를 고정한다. 실행 중 설치 파일을 조용히 교체하지 않는다. 새 계약으로 기존 원장을 쓸 수 있는지는 명시적인 변환 검사가 판정한다.

전환은 인스턴스 정지, 미종료 실행의 종료 대조, 현재 상태 커밋과 원자료 보존, 격리된 변환 시험, 의미·권한 차이 검토, 승인된 ref 전환 순서다. 읽기만 호환되는 구현은 보고와 변환 계획만 만들 수 있다. 전환 뒤 결함은 새 교정 변경으로 기록한다.

## 15. Lean 신뢰 환경

신뢰 환경은 기초 프로필·허용 공리·Lean 소스와 바이너리·도구체인·Mathlib 소스와 빌드 산출·검사 도구·재현 명령의 정확한 판본을 가진다. 초기 기초 프로필은 `propext`, `Quot.sound`, `Classical.choice`만 허용한다. `sorryAx`, 사용자 정의 추가 공리와 컴파일러 계산을 신뢰 주입하는 경로는 금지한다. 실제 검사 도구가 그 경로를 검출하는지는 활성화 검증 대상이다.

Mathlib 기반은 신뢰 환경 생성 때 깨끗하게 빌드하고 해시로 봉인한다. 개별 제안은 봉인한 기반의 무결성을 확인하고 해당 정본·후보를 검증한다. 형식 표현의 의미를 최신 도구체인으로 묵시적으로 옮기지 않는다.

외부 전문 라이브러리는 연구 자료로 참고할 수 있다. 초기 정본의 직접 의존은 승인한 Lean·Mathlib 기반으로 제한한다. 다른 기반의 결과는 별도 비교 자료이며, 활성 기반으로 옮기려면 그 기반에서의 증명 또는 명시적인 해석·보존 결과와 동일성 검증이 필요하다.

### 15.1 계획된 전환

1. 승인된 전환 제안으로 새 환경을 준비한다.
2. 전환 대상 K 집합을 고정하고 새 Lean 정본 편입을 잠시 대기시킨다. 일반 연구 기록의 공개와 승인된 연구 수행은 계속할 수 있다.
3. 새 환경에서 기반과 대상 K를 전건 검증한다.
4. 타입·본문·전이 의존·공리·해설·대응이 보존됐는지 비교한다. 하나라도 달라지거나 비교할 수 없으면 필요한 새 동일성 검토를 수행한다.
5. 목표·진행 과제·대기 제안의 영향과 다음 행동을 기록한다.
6. 전건이 충족되면 활성 환경과 검증된 연결을 공용 편입으로 전환하고 대기한 편입을 재검사한다.

전환이 실패하면 유효한 기존 환경을 유지하고 편입 대기를 해제한다. 새 환경 일부만 활성화하지 않는다. 이미 무효화된 환경은 실패 시 복귀 대상으로 사용할 수 없다.

### 15.2 무효화

결정론적으로 확인한 커널·공리·저장 환경 결함은 근거를 보존하고 영향받는 형식 결과의 사용을 정지시킨다. 개별 파일·결과의 결함인지 환경 전체의 신뢰 결함인지 확인해 정지 범위를 정한다. 범위를 좁힐 근거가 없으면 그 환경을 전제로 하는 사용을 보수적으로 정지한다.

작업자 실행을 무조건 모두 폐기하지 않는다. 해당 형식 환경을 사용하는 행동은 막고, 보존·진단·환경과 독립인 자료 정리는 허가 범위에서 수행할 수 있다. 새 환경과 영향 재검증이 끝난 뒤에만 정지한 형식 사용을 복원한다.

## 16. 구현 인터페이스와 스키마

### 16.1 실행 어댑터의 필수 기능

초기 구현은 어댑터 하나를 먼저 검증한 뒤 지원 목록에 올린다. 어댑터의 계약은 다음과 같다.

| 기능 | 반환해야 할 사실 |
|---|---|
| `describe` | 지원 모델·노력, 입력·출력·동시성 제한, 도구·격리·취소·조회 능력과 판본 |
| `start` | 실행 ID에 결박한 로컬 프로세스·thread/turn과 공급자 호출 ID 목록, 실제 주입한 입력 manifest |
| `inspect` | 로컬·원격 실행·미정산 사용량, 진행 중 도구 호출, 응답·종료 여부와 상태 보존 기간의 근거 |
| `stop` | 권한 회수 뒤 정지 요청의 수신과 취소 결과. 요청 성공과 종료 완료를 구별 |
| `collect` | 실제 모델 출력·도구 결과·산출 파일·종료 상태와 수집 범위 |
| `verify_isolation` | 중앙 정본·다른 비공개 결과·공간 밖 쓰기·직접 네트워크·주변 비밀·IPC 위장·자식 권한의 거부 결과 |

`start`의 실제 입력 주입, 실제 모델·노력 선택, 실행별 도구·파일 권한, 원격 호출 종료 확인을 제공하지 못하면 그 어댑터는 미지원이다. 사용 가능한 듯한 CLI 이름만으로 지원을 선언하지 않는다. 기능 검증 전에는 역할을 모사한 fixture로 상태 기계만 시험할 수 있으며 실운전 가능으로 보고하지 않는다.

도구의 로컬 자식은 해당 실행의 Job 안에 있어야 한다. WSL·컨테이너·서비스·원격 쓰기처럼 Job 밖 효과가 있는 도구는 동일한 권한 회수·전체 종료·상태 조회를 제공하는 어댑터가 승인됐을 때만 사용한다.

실행 어댑터와 별도로 대화 어댑터는 register·heartbeat·disconnect·reconnect 사건과 확인 응답을 제공한다. 3.3절의 대화 ID·세대·유예와 실제 연결 사건을 검증한다. 단순한 모델 turn 종료를 사용자 대화 종료로 대체하지 않는다.

첫 어댑터의 선택은 능력 검증 뒤 확정한다. Codex의 thread/turn과 직접 API response는 같은 단위가 아니다. 어댑터 대응표는 한 실행의 모든 모델 호출·도구·취소·수집·소실 복구를 덮어야 한다. CLI help에서 명령이 보인다는 사실은 이 검증의 완료가 아니다.

### 16.2 실행 프로필

프로필은 다음을 고정한다.

- 모델·노력·공급자·동시성 제약과 어댑터 판본.
- 정확한 tokenizer, 컨텍스트 한도, 실행별 출력 예약과 환경 여유.
- 허용 도구와 역할별 읽기·쓰기 범위.
- 작업 예산 AI의 다음 운영 검토 시각 범위, 운영 AI·기계 작업의 실행 기한과 공통 종료 유예.
- 로컬 도구의 호스트 자원 한계와 강제 정지 가능성.
- 원격 모델 종료·사용량 확인 방법, 보존 기간·최대 지원 복구 공백, 크리덴셜 저장·전달·회전과 로그 비밀 제거 규칙.
- 입력·출력·도구·스키마·지침 묶음의 해시.

AI 동시성 예약은 호스트 CPU·메모리의 응답성을 보증하지 않는다. 도구 부하 중에도 실행기가 권한 회수와 종료 대조를 수행할 수 있는지 별도로 시험한다. 확인하지 않은 호스트 한계를 숫자로 추측해 활성화하지 않는다.

### 16.3 도구 표

아래 명령은 새 구현의 제안 인터페이스다. 기계 실행기가 쓰기 명령의 유일한 집행자이며, AI는 자기 허가 안에서 요청을 제출한다.

| 명령 | 요청 주체 | 입력 | 결과·효과 |
|---|---|---|---|
| `do-math init` | 사용자 | 초기 허가·프로필·원문 | 초기화와 검사 보고 |
| `do-math run` | 사용자 | 인스턴스·유효 허가 | 독점 실행기 시작·복구·운전 |
| `do-math pause` | 사용자·정지 정책 | 대상 인스턴스 | 배정 중지·공통 권한 회수 |
| `do-math resume` | 사용자·유효 재개 허가 | 인스턴스 | 복구 검사 뒤 재개 |
| `do-math status` | 사용자·허가된 실행 | 읽기 스냅샷 | 같은 원자료의 JSON·사람 보고 |
| `do-math query` | 허가된 실행 | 스냅샷·필터·cursor | 범위가 표시된 페이지 |
| `do-math read` | 허가된 실행 | 정확한 기록·산출물 참조 | 원문·해시·허용 범위 |
| `do-math record` | 생산자 | 기록 종류·입력·내용 | ID를 가진 초안과 기계 검사 |
| `do-math check` | 생산자·실행기 | 검사 종류·정확한 입력 | 실제 범위·실패·미검사·수리 기록 |
| `do-math checkpoint` | 실행 중 생산자 | 파일 manifest·상태 | 불변 체크포인트와 수신 결과 |
| `do-math submit` | 실행 중 생산자 | 최종 manifest·결과 또는 대기 요청 | 공통 종료·수신 검사·후속 예약 |
| `do-math decide` | 사용자 대화 어댑터 | 원문·대상 변경·허가 범위 | 결정 봉인·허용 효과 적용 |
| `do-math apply` | 실행기 | 승인된 공용 변경 | 인스턴스 상태 ref의 조건부 갱신 |
| `do-math trust` | 실행기 | 승인된 환경 제안 | 준비·검사·전환·무효화 |
| `do-math recover` | 실행기 | 상태 커밋·프로필 | 읽기 검증 후 실제 상태 대조와 복구 보고 |
| `do-math migrate` | 실행기 | 승인된 새 계약·변환 | 격리 시험·전환 결과 |

일회성 명령은 정규 JSON 입력 하나와 정규 JSON 출력 하나를 사용하고 로그는 별도 채널로 보낸다. 종료 코드 0은 요청 처리 성공이며 결과의 의미 판정과 독립이다. 2는 입력 결함, 3은 적용 전제 변경, 4는 허가·자원·필수 조건의 차단, 5는 도구·환경 실패다. 결과에는 실제 검사 범위와 다음 소유자를 포함한다.

쓰기 요청은 요청 ID로 멱등 처리한다. 같은 요청 ID와 같은 입력이면 이전 결과를 반환하고, 같은 ID의 다른 입력은 거부한다. 실행기와 통신하는 구체 운송 방식은 호출자의 실행 인스턴스를 인증할 수 있어야 하며 영속 정본을 대신하지 않는다.

각 명령은 `--describe`로 입력·출력 스키마, 권한, 효과와 재시도 규칙을 반환한다. 역할 지침에는 실제 사용할 명령과 실패 뒤 행동을 적는다. 권한이 없는 AI에 쓰기 명령의 이름을 알려 줬다는 사실만으로 실행을 허용하지 않는다.

### 16.4 스키마 가족과 소유 절

각 가족은 `do-math-draft/<family>/2`로 작성한다. 아래 표는 소유 관계이며 실제 required·자료형·oneOf·정렬·부재 의미의 완결된 정의는 규범 스키마 묶음이 소유한다. 스키마 작성자는 본문의 각 의미를 구체 필드와 전이 pre/postcondition으로 옮기고, 권한·결과를 바꾸는 새 선택은 이 문서에 먼저 반영한다. 구현 코드보다 스키마·명령 계약·golden vectors를 먼저 검토한다. 구현한 도구의 --describe를 그 도구 자신의 선행 정당화로 사용하지 않는다.

| 가족 | 소유 내용 |

활동별 의미 판정은 해당 가족의 닫힌 값만 쓴다. 실행 미완료는 `execution`의 종료 종류가 소유하고, 산출물에 허위 판정값을 넣어 대신하지 않는다. `status`는 파생 보기이며 자기 판단 권한을 갖지 않는다.

### 16.5 구현 파일과 지침

구현은 진입 스킬, 공통 실행 규칙, 활동별 지침, 스키마와 도구를 가진다. 공통 정의와 각 판정의 의미는 한 소유 문서에 두고 다른 문서는 필요한 지점에서 참조한다. 기계 값·명령 목록은 실제 스키마·도구에서 생성해 대조한다.

이 초안의 규칙이 실제 지침·스키마·도구의 어느 위치로 구현됐는지 대응표를 생성한다. 의미 판정 기준은 자동 생성만으로 충실성을 보증할 수 없으므로 원문과 실제 역할 입력을 사람이거나 지정 검토 활동이 대조한다. 경로 링크가 존재한다는 검사와 의미가 일치한다는 검토를 구분한다.

### 16.6 사람용 상태와 공동 탐색

status의 JSON과 사람 보고는 같은 snapshot_commit을 사용한다. 사람 보고는 현재 목표·성공 기준, 가장 강한 결과와 보증 수준, 중요한 미해결·정지·철회, 실행 중 시도와 다음 검토, 동시 용량·누적 소비·미정산·남은 한도, 사용자 결정과 그 효과를 순서대로 설명한다. 단순한 상태 코드 나열로 다른 종류의 정체를 같은 것으로 보이게 하지 않는다. 각 결론은 정확한 기록으로 내려갈 수 있어야 한다.

사용자에게 권한을 묻는 질문과 수학적 정보·조언을 요청하는 질문을 구별한다. 후자는 새 권한을 만들지 않으며 답을 주장·원자료로 수입한다. 자율 허가 안의 독립 작업은 선택적인 조언을 기다린다는 이유로 멈추지 않는다. 필수 정보가 없으면 해당 과제만 대기로 두고, 전체 정지가 필요한 경우에만 그 근거를 명시한다.

## 17. 검증과 구현 순서

### 17.1 첫 구현에서 확인할 것

첫 구현은 실제 연구를 시작하기 전에 실행 어댑터의 능력을 입증한다. 입력·모델·노력·도구 권한·파일 격리·로컬 및 원격 종료를 확인하는 작은 실행으로 시작한다. 이 관문이 실패하면 원인을 해소하기 전까지 연구 역할 전체를 만들지 않는다.

그다음 공통 활동·실행 상태, 분리 예산, 단일 상태 ref의 적용과 복구를 구현한다. AI 역할은 fixture 산출로 먼저 구동하고, 아래 상태 벡터를 통과한 뒤 실제 AI 활동을 연결한다. 마지막으로 Lean·동일성·목표 검증과 전체 연구 워크스루를 붙인다.

### 17.2 필수 상태·시간선 벡터

### 17.3 연구 워크스루

다음 네 흐름을 실제 입력과 산출물로 재생한다.

1. 기존 K 결과가 목표를 충족해 새 연구 수행 없이 감사로 해결을 확인하는 경우.
2. 조건부 정리 H → P를 보존하고 H 제거·입증을 다음 연구로 선택하는 경우.
3. 계산에서 반례 후보를 얻고 별도 형식 검증·동일성·목표 감사를 거쳐 반증으로 해결하는 경우.
4. 미해결 검토와 사용자 결정 대기가 동시에 생겨도 다른 승인된 연구가 계속되는 경우.

실제 AI 연결 전에는 fixture로 절차를 검증한다. 실제 연결 뒤에는 원자료 충실성, 검토 범위와 결과 환류를 확인한다. fixture의 성공을 실제 모델·도구의 수행 능력 증거로 보고하지 않는다.

### 17.4 구현 완료

구현 완료는 다음 전건을 요구한다.

- 스키마·도구·역할 입력이 이 초안에서 채택한 계약과 일치한다.
- 실제 실행 어댑터의 필수 능력이 해당 호스트에서 검증됐다.
- 필수 시간선 벡터와 연구 워크스루를 전건 수행했다.
- 권한·형식 타당성·동일성·목표·실행 상태를 서로 대신하지 않는다.
- 원자료가 회수되고, 미완료·미해결·실패·무결과가 구분된다.
- 구현 중 새로 정한 의미 선택이 문서 개정과 승인 범위로 닫혔다.

성공한 테스트, 실행 환경, 실제 검사 범위와 남은 제한을 불변 보고로 남긴다. 연구 성과의 향상과 검토 강도의 실효성은 이 구현 완료와 구분해 후속 운용으로 평가한다.

연구 효능 평가는 알려진 의미 오류의 탐지·오탐·미해결률, 다른 표기의 관련 결과 회수, 불필요한 재증명, 새 근거 뒤 계획 반응, 중단 뒤 중복 시도와 맥락 누락을 대표 과제에서 비교한다. 같은 계열 판정 반복을 통계적 독립성으로 보고하지 않는다. 이 평가 결과를 보증 수준과 지원 문제군의 설명에 사용하되, 근거 없이 일반 연구 전체에 대한 성능 보장이나 새로운 사용자 승인 절차를 만들지 않는다.

| D04 | 초기 검토 구성·총예산이 충분한 신뢰와 운용성을 주는가 | 검토 방침의 승인자와 연구 검증 담당이 확인, 방침 채택 전 필수 |
| D05 | 크기가 큰 수학 제안의 분할과 경계 검토를 실제 사례에서 수행할 수 있는가 | 수학 검증 담당이 대표 제안으로 검증, 해당 규모 지원 선언 전 필수 |
| D06 | 보편 도메인 정의 정본과 이 초안의 K·F·U·과제·판정 의미가 일치하는가 | 원자료 대조를 허용한 후속 검토에서 확인, 정본 채택 전 필수 |
| D07 | 승인·거절·미해결이 이미 판정된 쟁점을 새 활동이 재검토할 때 근거를 충실히 승계하는가 | 연구 검증 담당이 판정 기록 중심 입력을 실제 반복 검토로 시험, 역할 입력 확정 전 필수 |
| D08 | 규범 JSON Schema·명령 wire 계약·정규 codec의 실제 파일과 golden vectors가 완결됐는가 | 구현 전 스키마 작성·대조 단계에서 닫음. 가족 표와 --describe 이름만으로 완료하지 않음 |

현재 초안은 위 능력의 실운전 시험을 통과했다는 보고가 아니다. 이번 적대적 검토에서는 로컬 명령·공식 API 문서와 설계 원문을 대조했지만 실제 모델·격리·복구 시험은 하지 않았다. 특히 D01·D02가 실패하면 설명만 보완해 활성화하지 않고 지원 경계를 다시 정한다. 보편 정의 정본은 새로 읽지 않았다. 최초 저작 검토는 [초안 검토 기록](../통합-설계-초안-검토.md), 이번 51개 지적의 판정과 수정은 [종합 판정](종합-판정.md)이 소유한다.
