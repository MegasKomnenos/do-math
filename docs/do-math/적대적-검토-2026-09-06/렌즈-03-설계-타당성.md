## 총평

초안의 핵심 분리는 대체로 이유가 있다. 수학적 타당성·해설 동일성·목표 충족·행동 허가·실행 상태를 서로 대신하지 않는 구조, 실행을 기다림과 분리해 예산을 반환하는 구조, 실패 정보와 부분 산출물을 후속 실행에 넘기는 구조, 전역 낡음과 전역 차단을 피하는 구조는 각각 실제 소비자 전제를 보호한다. 규칙이 많다는 이유만으로 제거할 장치는 아니다.

그러나 현재 초안은 가장 간단하면서 충분한 실행 계약에는 이르지 않았다. 두 정본 머리는 같은 목적을 더 단순한 단일 원자 상태로 달성할 수 있는데 별도 머리의 실익이 제시되지 않았다. 반대로 허가 자원의 누적 소진, 기계 작업의 공유 호스트 용량, AI 활동의 영속 생명주기, 반복 이력의 입력 성장, 운영 큐의 기아, 대화 소실 감지는 목적을 달성하는 데 필요한데 실행 계약이 닫히지 않았다.

## 발견

### L3-01 — 설계 제안: 두 가변 정본 머리는 현재 문면에서 필요한 복잡성으로 입증되지 않았다

**결론.** 초안은 연구 정본과 실행 원장을 개념적으로 분리해야 한다는 점은 입증하지만, 둘을 별도의 가변 Git ref로 유지해야 한다는 점은 입증하지 않는다. 이는 확인된 고장이라기보다 더 단순한 구조와 비교해야 할 설계 제안이다.

**근거와 소비자 전제.** 실행기는 유일한 작성자다(초안 3.1절, 107–118행). 그런데 7.1절은 연구와 실행에 각각 가변 ref를 두고(323–359행), 읽을 때는 실행 원장 커밋과 그 `state.json`이 가리키는 연구 커밋을 쌍으로 고정하며 두 현재 머리를 따로 읽지 못하게 한다(403–407행). 편입은 연구 커밋과 원장 커밋을 따로 만든 뒤 두 ref를 한 트랜잭션으로 바꾸고(509–522행), 초기화·복구·변환도 두 사슬과 불일치를 별도로 다룬다(747–755행, 757–797행). 구현 순서도 두 ref의 원자 적용과 복구를 기반 기능으로 둔다(934–938행). 실제 소비자의 전제는 “연구 상태와 그때의 실행 상태가 한 원자 스냅샷으로 읽힌다”는 것이다. 별도 가변 머리 자체에 기대는 소비자는 문서에 제시되지 않는다.

**정상 시간선과 영향.** 실행 상태만 바뀌는 회차에는 원장 ref만 전진하고, 연구 편입 회차에는 연구 커밋과 원장 커밋을 만든 뒤 두 ref를 원자 갱신한다. 이 구조 때문에 구현자는 교차 포인터, 두 예상 OID, 영구 불일치, 두 사슬 복구와 V14 같은 고유 실패 상태를 구현해야 한다. 단일 작성자라는 전제 아래 하나의 권위 ref가 `research/`와 `runtime/` 트리를 함께 소유하면 실행 상태만 바뀔 때 연구 subtree를 그대로 재사용하고, 편입 때 두 subtree를 한 커밋에서 바꿀 수 있다. 소비자가 원하는 원자 스냅샷은 한 head 비교로 성립하며 교차-ref 불일치라는 문제 자체가 사라진다.

**반박 검토.** 연구 이력과 운영 이력을 분리해 읽거나 내보내려는 목적은 타당할 수 있다. 그러나 초안은 그 분리를 요구하는 사람·도구, 별도 ref가 아니면 깨지는 전제, 한 ref의 subtree·파생 보기로는 부족한 이유를 적지 않는다. 같은 객체 데이터베이스와 단일 실행기를 쓰고 AI 조회도 실행기 도구를 거치므로(22행, 143–147행), 현재 문면만으로는 별도 쓰기 권위 두 개의 비용을 정당화하지 못한다.

**개선 방향.** 기본안은 가변 권위 ref 하나와 그 안의 연구·실행 subtree 하나씩이다. `record_ref`의 연구 판본은 권위 커밋과 연구 subtree OID를 함께 고정하거나, 기록 파일 해시와 subtree OID로 고정할 수 있다. 깨끗한 연구 전용 사슬이 실제 하류 요구라면 그 소비자와 파손을 먼저 적고 두 ref를 유지한다. 그렇지 않으면 단일 ref로 합쳐 7.4절, 10.3절, 14.2–14.5절과 관련 상태 벡터를 줄이는 편이 목적을 보존하면서 실패 조합을 실제로 없앤다.

### L3-02 — 문면 누락: 허가의 기간·누적 자원 한계를 집행할 원장이 없다

**결론.** 사용자가 승인하는 실행 허가는 기간과 자원 한계를 가진다고 규정하지만, 예산 계약은 동시 실행 수만 센다. 따라서 누적 토큰·비용·실행 횟수·총 시간처럼 허가가 정할 수 있는 소진 자원과 만료를 실행기가 어떻게 막는지가 정의되지 않았다.

**근거와 소비자 전제.** 초기 결정에는 “허용 기간·자원·외부 효과, 정지 조건”이 있고(26–39행), 허가 기록에도 자원 한계와 효력 기간·종료 조건이 있다(710–716행). 반면 4.1절은 예산 단위를 “동시에 활성인 AI 실행”으로 명시하고 슬롯만 정의한다(152–168행). 실행 프로필의 토큰 규칙은 한 실행의 입력 적합성과 최대 출력 예약이다(439–445행, 845–855행). 초안도 이 분리가 동시 실행 용량만 보장하며 사용량 제한은 별도 가용성 조건이라고 한정한다(164–166행). 실행 시작 때 허가를 재검사하고 실행 중 허가 유효성을 요구하지만(278–292행), 누적 사용을 예약·차감·정산하는 상태나 만료 시각에 여는 기계 사건은 없다. 사용자는 승인한 자원·기간 안에서만 자동 운전된다는 전제에 기대고, 실행기는 그 전제를 집행해야 한다.

**정상 시간선과 실제 파손.** 사용자가 “이 기간 동안 최대 N 토큰 또는 C 비용”을 승인했다고 하자. 각 실행은 슬롯 상한과 실행별 출력 한도를 지키며 정상 종료한다. 계획은 새 결과를 받아 다음 실행을 계속 연다. 누적 사용량을 줄이는 전이가 없으므로 N이나 C를 넘은 뒤에도 다음 실행의 동시성 검사는 통과한다. 기간 만료 중 장기 모델 호출이 진행되는 경우도 만료 시각 자체가 정지 사건을 연다는 규칙이 없어 다음 운영 점검까지 행동이 이어질 수 있다. 각 규칙을 위반하지 않고도 승인 범위를 넘는 비용이나 작업이 발생한다.

**반박 검토.** 공급자 속도·사용량 제한은 사용자의 허가 한계와 같지 않고, 공급자 장애로 나타날 뿐 정확한 승인 소진을 집행하지 않는다. 사용자가 수동으로 `pause`할 수 있다는 사실도 사전에 승인한 상한을 기계적으로 지킨다는 전제를 대신하지 않는다. 18절 D02는 공급자의 공유 동시 한도를 닫을 뿐 누적 허가 자원을 닫지 않는다(1024–1027행).

**개선 방향.** 자원 한계가 오직 동시성만 뜻한다면 0.1절과 13.2절의 “자원 한계”를 그 뜻으로 좁혀 과도한 보장을 제거한다. 누적 한계를 허용하려면 허가별로 실제 선택된 측정 단위, 상한, 남은 양, 만료 시각을 실행 원장에 두고 시작 전에 최악 소비를 원자 예약한 뒤 수집 결과로 정산한다. 만료는 poll에 기대지 않는 예약 사건으로 만들고, 새 시작 거부와 이미 실행 중인 일의 처분을 허가 문면에서 정한다. 모든 공급자에 같은 비용 필드를 강제할 필요는 없으며, 해당 허가가 실제 제한한 차원만 닫힌 제약으로 표현하면 된다.

### L3-03 — 문면 누락: 기계 작업은 공유 호스트 용량을 예약하지 않아 실행기 자체를 굶길 수 있다

**결론.** 긴 Lean 빌드와 해시 검사도 공통 실행으로 다루지만 AI 예산을 예약하지 않는다. 개별 Job의 호스트 한계는 있어도 여러 기계 작업이 함께 소비하는 공유 호스트 용량과 배정 순서가 없다.

**근거와 소비자 전제.** 예산은 활성 “AI 실행”의 슬롯이다(152–168행). 기계 작업은 같은 실행 상태를 사용하되 AI 예산을 예약하지 않고 도구 manifest와 호스트 자원 한계를 적용한다(247–253행). 긴 검사와 Lean 빌드는 실행기를 막지 않는 별도 기계 작업으로 실행한다(520–522행). 프로필은 로컬 도구의 호스트 자원 한계를 고정하지만(845–855행), 초안은 AI 동시성 예약이 CPU·메모리 응답성을 보장하지 않는다고 인정하고 부하 시험을 요구할 뿐이다(857행). 실행기와 운영 점검의 소비자는 호스트가 정지·조회·권한 회수에 계속 응답한다는 전제에 기대고 있다.

**정상 시간선과 실제 파손.** 여러 제안이 동시에 최종 Lean 검사를 열면 각 기계 작업은 자기 Job 한계 안에서 정상이다. 그러나 기계 작업 전건이 소비하는 CPU·메모리·디스크 I/O의 합이나 동시 빌드 수를 예약하는 관문이 없으므로 모두 시작할 수 있다. 합계가 호스트를 포화시키면 실행기의 정지·복구 응답이 늦어지고, 12절의 운영 관찰과 13.5절의 정지가 가장 필요한 순간에 작동하지 않는다. 개별 작업의 준수와 전체 시스템의 안전이 갈라진다.

**반박 검토.** Job별 상한은 한 작업의 폭주를 막지만 여러 정상 상한의 합을 막지 않는다. V33의 부하 시험(976행)은 특정 시험 구성을 검증할 뿐 이후 준비된 기계 작업 수를 제한하지 않는다. “실행기가 막히지 않는다”는 10.3절의 요구도 스케줄러나 예약 없이 그 결과를 만들지 못한다.

**개선 방향.** AI와 기계를 별도 예외로 나누기보다 모든 실행이 자신이 소비하는 공유 제약을 원자 예약하게 한다. AI 실행은 공급자 슬롯과 필요한 호스트 제약을, 기계 작업은 호스트 CPU·메모리·I/O 또는 더 단순한 `machine_jobs` 제약을 예약한다. 실제로 동시에 강제할 수 없는 세부 수치를 창작하지 말고, 첫 구현에서는 동시 기계 작업 수와 실행기용 보존 용량처럼 검증 가능한 최소 제약으로 시작한다. 이는 기존 `capacity_refs` 발상을 일반화해 예산 예외와 새 스케줄러를 각각 만드는 것보다 단순하다.

### L3-04 — 문면 충돌: 공통 실행 생명주기 아래의 영속 활동 생명주기가 닫히지 않았다

**결론.** 초안은 모든 AI 활동에 공통 실행 생명주기를 적용한다고 선언하지만, 여러 실행을 소유하거나 후속을 여는 영속 `activity`의 공통 상태·전이가 없다. 종류별 규칙도 연구 계획·수학 검토·운영 점검·의도 해석·작업 계약 검토를 모두 덮지 않는다.

**근거와 소비자 전제.** 2.1절은 과제와 후속 활동 상태를 실행 원장이 보존한다고 하고(79–90행), 3.2절은 여섯 AI 활동 종류와 공통 실행 계약을 정한다(120–135행). 저장 구조에는 `activities/<id>/`가 계획·검토·점검의 단계와 후속 소유권을 가진다(347–357행). 그러나 실행 요청의 대상은 “과제·검토 ID”이고(247–253행), 실패의 직접 소유자는 “과제·검토·계획 기록”이라서 목록도 서로 다르다(312–318행). 연구 계획은 사건 cursor, 수학 검토는 6단계 활동, 운영 점검은 실행별 열린 활동 하나라는 부분 규칙을 가지지만(452–474행, 588–601행, 666–695행), 의도 해석과 작업 계약 검토의 영속 상태·종료·대기 전이는 없다. 16.4절의 스키마 가족에도 공통 `activity`는 없고 `plan`, `review-activity`, `operational-review`만 따로 있다(888–923행).

**정상 시간선과 실제 파손.** 작업 계약 검토 실행이 `revision_required`를 정상 제출하고 `ended`가 됐다고 하자. 5.4절은 결함과 남은 질문을 연구 계획에 돌려주라고 하지만(236–240행), 어느 활동 기록을 어떤 완료 상태로 바꾸고 어떤 사건을 원자적으로 만들어야 하는지는 없다. 실행기가 그 사이 소실되면 구현자가 임의로 “검토는 끝났고 사건은 아직” 또는 “검토가 열려 있다”고 해석해야 한다. 전자는 후속을 잃고, 후자는 같은 결과를 중복 처리할 수 있다. 의도 해석 결과를 사용자 질문으로 넘기는 경로에도 같은 틈이 있다. 실행 상태가 정확해도 업무 상태와 다음 소유권은 확정되지 않는다.

**반박 검토.** 각 실행의 종료 기록이 다음 소유자와 미완료 범위를 가진다는 규칙(269–276행)은 유용하지만, 그 기록만으로 여러 실행을 묶는 검토 활동의 단계나 “한 활동만 열림” 불변식, 기다림과 재개를 표현하지 못한다. 수학 검토처럼 종류별로 완성된 절차는 이 문제를 일부 해소하지만 모든 활동의 공통 계약은 아니다.

**개선 방향.** 과제의 연구 범위 생명주기는 그대로 두고, 모든 비과제 AI 업무에 최소 공통 `activity` 봉투를 둔다. 필요한 공통 필드는 활동 ID·종류·소유자, 정확한 입력 근거, `ready/running/waiting/ended` 같은 닫힌 상태, 현재 실행, 결과, 다음 소유자·재관찰 조건이다. 실행 종료와 활동 결과·후속 사건 생성을 한 원장 변경으로 묶고, 종류별 스키마는 payload와 의미 판정만 소유하게 한다. 대안은 여섯 활동 각각의 상태 기계를 모두 쓰는 것이지만 중복과 누락 가능성이 더 크다. 공통 봉투는 이미 선언한 “모든 AI 활동의 공통 실행 계약”을 실제 영속 계약으로 완성하는 가장 작은 구조다.

### L3-05 — 장기 입력 결함: 전역 저장소 성장은 다루지만 반복 쟁점의 필수 입력 성장은 다루지 않는다

**결론.** K·F·전체 이력을 매번 동봉하지 않는 설계는 타당하다. 그러나 같은 과제·제안이 실패·반박·재심사를 반복할 때 반드시 승계할 쟁점과 답변의 크기가 계속 자라는 경로에는 창·목차·검증된 압축·종료 처분이 없다.

**근거와 소비자 전제.** 후속 실행은 이전 실패의 규칙·좌표·입력 차이·외부 행동·체크포인트·남은 범위를 필수 입력으로 받는다(312–318행). 입력 묶음은 이번 활동이 처리할 이전 실패·판정·미결 사항을 포함하고(418–429행), 후속 실행은 판본화된 쟁점·답변·판정·재개 기록을 받는다(439–445행). 필수 범위가 컨텍스트에 맞지 않으면 생성기가 임의 요약·삭제하지 않고 독립 판정 가능한 부분으로 분해하거나 입력 불가를 반환한다(441–445행). V48은 기존 쟁점의 반박 근거나 답변을 빼고 검토 완료를 선언하지 못하게 하고(991행), D07은 반복 검토에서 그 승계 충실성을 아직 시험해야 한다고 남긴다(1030행). 후속 검토자는 살아 있는 반박과 답변이 누락되지 않았다는 전제에 기대고 있다.

**정상 시간선과 실제 파손.** 큰 제안이 `unresolved`로 끝나 수정되고, 새 검토에서 새 쟁점과 이전 쟁점의 반박이 추가되는 회차를 반복한다고 하자. 각 회차는 유한하게 끝나고 같은 입력을 무변화 재실행하지 않는 규칙도 지킨다. 그러나 현재 의미를 판정하려면 과거 반박들이 서로 연결돼 있어 독립 분해가 불가능할 수 있다. 필수 이력은 회차마다 자라고 어느 순간 한 입력 한도를 넘는다. 생성기는 임의 요약을 할 수 없고 분해도 못하므로 `입력 불가`만 반환한다. 더 큰 모델이 없으면 해당 제안은 영구 정지한다. 저장소 전건 페이지 조회는 이 결합된 논증의 필수 덮개를 줄이지 않는다.

**반박 검토.** “이번 활동이 처리할 항목”만 고르는 것은 관련 없는 과거를 빼는 데 유효하다. 그러나 어떤 과거 반박이 더는 관련 없는지를 권위 있게 닫는 처분과 그 충실성을 검증하는 절차가 없다. 판본화는 보존을 해결할 뿐 현재 입력의 크기를 줄이지 않는다. 8.3절의 분해는 가능한 경우의 해법이지 불가한 경우의 다음 소유자·종료 조건이 아니다.

**개선 방향.** 쟁점마다 현재 주장, 살아 있는 반박, 처분, 정확한 원자료 참조를 가진 정본 상태를 두고 전체 과거 본문은 참조로 보존한다. 입력 상한 전에 별도 압축 활동이 현재 판정에 필요한 논증을 새 체크포인트로 만들고, 독립 검토가 열린 반박·가정·양화·결론을 보존했는지 확인한 경우에만 후속 입력의 기준점으로 삼는다. 그 압축조차 한도에 맞지 않으면 새 검토를 열지 말고 현재 활동을 `unresolved`로 끝내 범위 축소·과제 분리·사용자 상신 중 하나를 계획하게 한다. 이는 원자료 보존을 포기하지 않으면서 매 회차 전체 이력을 직접 입력하는 문제를 없앤다.

### L3-06 — 절차 결함: 운영 우선순위는 정지·복구를 살리지만 정상 계획과 의도 해석을 영구 기아시킬 수 있다

**결론.** 작업과 운영 용량을 분리하는 것은 작업이 감독을 굶기지 않게 하는 실익이 있다. 다만 운영 큐 내부의 고정 우선순위와 최소 활성 조건만으로는 낮은 순위의 의도 해석·연구 계획이 결국 실행된다는 전제가 성립하지 않는다.

**근거와 소비자 전제.** 활성화는 운영 활동을 수행할 수 있는 프로필 제약마다 운영 용량 하나 이상만 요구한다(154–164행). 운영 배정은 정지·복구 점검, 도래한 운영 검토, 의도 해석, 연구 계획 순서이고 같은 종류만 생성 순서를 따른다(178–184행). 모든 작업 예산 실행은 시작 때 다음 운영 검토 시각을 받으며(654–664행), 예정 시각·상태 불일치·작업자 요청 등이 점검을 연다(666–672행). 실행별 열린 점검 하나라는 제한은 있지만 인스턴스 전체의 도래율과 운영 처리율 관계나 낮은 우선순위의 최대 대기 시간은 없다. 사용자 답과 연구 결과의 소비자는 의도 해석과 계획이 결국 실행된다는 전제에 기대고 있다.

**정상 시간선과 실제 파손.** 작업 슬롯이 여러 개이고 운영 슬롯이 하나인 정상 구성을 생각할 수 있다. 장기 작업마다 점검이 주기적으로 도래하고 점검 평균 처리 시간이 도래 간격의 합보다 길면, 두 번째 우선순위 큐가 비지 않는다. 운영 실행의 기한과 실행별 중복 금지를 모두 지켜도 새 점검이 계속 들어온다. 의도 해석과 연구 계획은 영구 대기한다. 명시적 정지는 즉시 전달되지만, 사용자의 새 허가·답변은 적용되지 않고 완료된 연구 결과도 다음 작업으로 환류되지 않는다. 시스템은 안전 점검을 계속하면서 연구 목적은 진행하지 않는 정상 규칙 교착에 빠진다.

**반박 검토.** 운영 실행 기한은 한 실행이 슬롯을 영구 점유하지 못하게 하지만 도착률이 서비스율보다 큰 큐를 해소하지 않는다. 운영 슬롯을 더 두면 특정 배치에서는 완화되지만 활성화 계약은 필요한 수를 계산하지 않는다. 작업별 점검 하나만 여는 규칙도 작업 수가 여러 개인 경우의 기아를 막지 않는다.

**개선 방향.** 정지·권한 회수·중앙 신뢰 복구처럼 안전 전제를 지키는 사건만 최상위 즉시 처리로 남긴다. 통상 점검·의도 해석·계획에는 FIFO와 aging 또는 종류별 최대 대기를 둔다. 동시에 작업 실행을 시작할 때 그 실행이 만드는 점검 의무를 현재 검증된 운영 처리 용량이 감당할 수 있는지 입장 제어한다. 단순히 우선순위 단계를 더 늘리기보다 “안전 긴급 큐 + 공정한 일반 운영 큐” 두 층과 입장 제어 하나가 더 작고 판정 가능하다.

### L3-07 — 지원 누락: `pause` 대화 소실 정책을 발동할 관찰 인터페이스가 없다

**결론.** `conversation_loss_policy=pause`는 대화 소실 사건이 신뢰성 있게 관찰·전달될 때만 실익이 있다. 초안은 그 능력을 검증 대상이라고 선언하지만 필수 어댑터 기능·명령·미결 관문에 넣지 않았다.

**근거와 소비자 전제.** 3.3절은 `continue_authorized`와 `pause`를 닫힌 값으로 두고, 연결 생존 판정 방법과 소실 사건 전달을 실행 어댑터의 검증 대상으로 삼는다(137–141행). 그러나 16.1절의 필수 실행 어댑터 기능은 모델 실행의 describe/start/inspect/stop/collect/isolation뿐이며 대화 연결이나 소실 사건을 반환하지 않는다(828–843행). 도구 표의 대화 어댑터는 사용자 결정을 봉인하는 `do-math decide`만 제공한다(859–886행). V31·V32는 소실 사건이 이미 주어진 뒤의 기대 처분만 검사하고(974–975행), D01도 모델 실행 어댑터의 입력·격리·취소·원격 종료 조회만 채택 관문으로 둔다(1024행). `pause`를 선택한 사용자는 대화가 실제로 소실되면 자동 운전이 멈춘다는 전제에 기대고 있다.

**정상 시간선과 실제 파손.** 사용자가 `pause`를 선택하고 대화 클라이언트나 중계 세션이 사라져도, 어느 구성요소가 얼마 동안 어떤 신호를 보고 “소실”로 확정하며 사건을 재전송하는지가 없다. 실행기는 사건을 받지 못한 채 기존 허가 범위 운전을 계속할 수 있다. 반대로 구현자가 임의의 짧은 연결 끊김을 소실로 정하면 일시적 네트워크 흔들림마다 전체 인스턴스를 정지할 수 있다. 정책 값은 닫혀 있지만 그것이 기대는 관찰 전제가 열려 있다.

**반박 검토.** 3.3절 한 문장의 “검증 대상”은 구현자에게 목적을 알려 주지만 검사할 인터페이스·성공 조건·사건의 소유자·재전송 규칙을 주지 않는다. 명시적 정지 요청 경로는 사용자가 요청할 수 있는 동안에는 유효하지만, 대화 소실 자체를 자동 감지하는 정책을 대신하지 않는다.

**개선 방향.** 신뢰할 수 있는 소실 감지를 제공할 수 없다면 초기 구현에서 `pause` 값을 제거하고 명시적 정지만 보장한다. 제공할 수 있다면 대화 어댑터에 세션 정체성, 생존/소실의 관찰 기준, 유예, 사건 ID, 전달 확인과 재생 규칙을 추가하고 실제 연결 소실을 주입하는 활성화 벡터와 채택 관문을 둔다. 두 선택 중 어느 것이 맞는지는 실제 대화 환경 능력과 사용자가 원하는 위험 허용도에 달려 있으므로 구현자가 추측해서는 안 된다.

## 검증을 통과한 중요한 부분

- **판정 경계.** 형식 타당성·해설 동일성·목표 충족·허가·실행 상태의 소비자와 효력을 분리한 1.1–1.2절은 각 전제가 깨질 때의 영향도 실제 의존으로 좁힌다(52–68행). 이 분리는 제거 대상이 아니다.
- **기다림과 실행 종료.** 사용자·연구 입력을 기다리는 과제는 실행을 끝내 예약을 반환하고, `waiting`에 재관찰 조건과 다음 소유자를 남긴다(170–176행, 218–234행). 장기 논리 작업과 살아 있는 프로세스를 분리한 구조는 정상 시간선을 단순하게 만든다.
- **실패 후 위임.** 종료 기록에 실제 범위·부분 산출·다음 소유자를 두고, 새 실행에 실패 좌표·입력 차이·외부 행동·체크포인트·남은 범위를 넘긴다(269–318행). 같은 실패 상태의 무변화 재파견도 금지한다. 이는 세션 교체 뒤 맥락 소실과 되풀이를 직접 막는다.
- **현재성과 차단 반경.** 계획 적용은 선택된 작업의 계약·입력·허가·미점유만 다시 확인하고 무관한 원장 전진으로 폐기하지 않는다(478–484행). 변경·판정 철회·복구·신뢰 환경 결함의 영향도 실제 의존이나 불확실한 실행으로 제한한다(524–528행, 637–651행, 771–785행, 819–823행). 전역 차단보다 목적에 맞다.
- **검토 활동의 국소 종료.** 한 검토 활동의 보충 조사 수와 단계는 유한하고, 미해결을 불일치나 승인으로 만들지 않으며 활동과 예산을 종료한다(568–619행). 권고 검토자 수 자체는 승인된 방침의 값이고 D04에서 실효성을 검증하게 했으므로, 숫자가 크다는 이유만으로 결함이라 판정하지 않았다.
- **저장소 탐색의 성장 처리.** 전체 K·F·이력을 매 입력에 넣지 않고 고정 스냅샷의 페이지 조회와 잘림 표기를 쓰는 8.2절은 전역 저장소 성장에 적합하다(431–437행). L3-05는 이 장치를 부정하지 않고, 논리적으로 결합된 반복 쟁점이라는 별도 성장 경로만 지적한다.

## 남은 불확실성과 읽지 않은 범위

이 보고서는 설계 초안의 구조적 충분성과 단순성만 검토했다. 실제 Git ref 트랜잭션, Windows Job, 실행 어댑터, 공급자 과금·사용량 API, 대화 연결 감지, 스키마와 생성기 구현은 배정 범위에 없어서 시험하지 않았다. 따라서 L3-02·L3-03·L3-07의 환경 능력은 미확인 사실이며, 지적의 핵심은 그 능력을 아직 구현 계약과 채택 관문으로 닫지 않았다는 문면상의 결과다. L3-01의 단일 ref 대안도 구현 시험을 거치지 않은 설계 제안이다. 별도 연구 ref에 기대는 미기재 외부 소비자가 있다면 그 전제를 추가한 뒤 다시 비교해야 한다.
