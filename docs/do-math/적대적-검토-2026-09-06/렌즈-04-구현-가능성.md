## 발견

### L4-01 — 공급자 상태가 먼저 소멸하면 원격 종료 확인 계약은 끝낼 수 없다

**종류와 결론: 조건부 구현 불가능.** 초안 4.2절 174행은 로컬 Job과 모델 실행의 종료가 모두 확인돼야 예약을 반환하고, 미확인이면 `stopping`에서 계속 대조하라고 한다. 6.5절 308행과 14.2절 769행도 같은 요구를 반복한다. 그러나 공급자가 원격 실행 상태를 보존하는 기간보다 실행기 중단이 길면 대조할 사실 자체가 사라질 수 있다.

OpenAI Responses API는 원격 응답 ID의 조회와 background 응답의 취소를 제공하므로 정상 시간선에는 이 요구를 구현할 수 있다. 다만 공식 문서는 `background=true`인 응답만 취소할 수 있다고 명시하고, ZDR 프로젝트의 background 응답은 `store=false`로 실행되며 대략 10분의 polling 기간 뒤 삭제된다고 한다. MAM에서도 `store=true`를 명시하지 않은 background 응답은 같은 방식으로 삭제된다. 일반 `store=true` 응답은 기본적으로 적어도 30일 보존되지만 무기한 관찰 보장은 아니다. 근거는 [Cancel a response](https://developers.openai.com/api/reference/cli/resources/responses/methods/cancel), [Background mode](https://developers.openai.com/api/docs/guides/background), [Data controls](https://developers.openai.com/api/docs/guides/your-data)다.

성립 시간선은 다음과 같다. 실행기가 background 응답 ID를 원장에 기록한 뒤 소실된다. ZDR 또는 `store=false` 프로필에서 polling 보존 기간이 지나 새 실행기가 복구한다. 로컬 Job 종료는 확인해도 공급자 조회는 삭제된 ID만 반환한다. 이때 ‘원격 종료 확인’도 ‘아직 실행 중’도 입증할 수 없으므로 초안대로라면 예약은 영구히 `stopping`에 남는다. 예약을 추측으로 반환하면 174행을 어기고, 반환하지 않으면 인스턴스 가용성이 회복되지 않는다.

18절 D01은 원격 종료 조회 능력을 미결로 둬 무지원 어댑터 활성화를 막는다. 이는 결함을 숨기지 않는 장점이지만, 단발 기능 시험이 성공해도 보존 기간을 넘긴 복구 시간선은 해결하지 않는다.

가장 단순한 개선은 실행 프로필에 `remote_observation_retention`, `store_mode`, 데이터 보존 정책, 허용 최대 복구 공백을 넣고, 최대 공백 동안 조회가 보장되는 프로필만 활성화하는 것이다. ZDR처럼 이를 만족할 수 없는 프로필은 현재 종료 계약에서 지원 불가로 닫아야 한다. 그런 프로필도 지원하려면 `remote_state_unrecoverable` 같은 별도 격리 상태, 공급자 용량을 더는 정확히 셀 수 없을 때의 사용자 승인·재활성 조건을 새 계약 결정으로 추가해야 한다. 이 후자는 현재 ‘확인 전 반환 금지’ 보장을 약화시키므로 구현자가 임의로 넣을 수 없다.

### L4-02 — 실제 실행 어댑터와 원격 실행의 단위가 아직 정해지지 않았다

**종류와 결론: 실제 지원 미확인.** 초안 16.1절 830–843행은 `describe/start/inspect/stop/collect/verify_isolation`을 요구하고 18절 D01도 이를 첫 수직 구현에서 검증하도록 한다. 그러나 CLI 프로세스, App Server의 thread/turn, Responses API의 response 중 어느 객체를 초안의 `execution_id`와 결박할지 정하지 않았다. 16.1절의 `start`는 단일 ‘모델 실행 ID’를 반환하는 모양인데, 도구 호출을 포함한 에이전트 실행은 여러 모델 응답과 로컬 도구 프로세스를 순차·병렬로 만들 수 있다.

로컬 Codex 0.153.4의 `codex exec --json`은 JSONL 사건을 내고 모델·sandbox·출력 스키마를 고를 수 있다. 공식 비대화형 문서도 `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*` 사건을 설명한다. App Server는 `turn/start`, `turn/interrupt`와 최종 `turn/completed`를 제공하고, `turn/interrupt` 요청 성공과 최종 `interrupted` 상태를 구분한다. Responses API는 response ID, `retrieve`, background `cancel`, 상태 값과 입력 토큰 계수 API를 제공한다. 따라서 후보 기술은 존재한다. 근거는 [Codex non-interactive mode](https://developers.openai.com/codex/noninteractive/), [Codex App Server](https://developers.openai.com/codex/app-server/), [Retrieve a response](https://developers.openai.com/api/reference/cli/resources/responses/methods/retrieve), [Count input tokens](https://developers.openai.com/api/reference/cli/resources/responses/subresources/input_tokens)다.

그러나 확인한 CLI 도움말에는 공급자 response ID의 영속 노출, CLI 소실 뒤 그 원격 응답의 재부착·조회·취소 완료가 보이지 않았다. App Server 공식 문서에는 살아 있는 turn의 interrupt와 저장 thread의 resume는 있지만, App Server 자체가 소실된 뒤 진행 중 provider operation에 재부착하는 보장은 확인하지 못했다. 이 부재는 ‘지원하지 않는다’는 입증이 아니라 D01이 아직 닫히지 않았다는 근거다.

개선하려면 첫 어댑터를 하나로 고정하고 다음 대응표를 구현 계약에 넣어야 한다. `execution_id` 대 `thread_id/turn_id/response_id[]`, 한 turn 안에서 새 response가 생길 때의 원자 기록 시점, live interrupt와 provider cancel의 차이, 도구 대기 중 상태, 래퍼·App Server·네트워크가 각각 소실된 복구 절차, 실제 주입 prompt·도구·모델·노력의 증거, 수집 완료 조건이 필요하다. Plain `codex exec`를 쓸 수 있다는 사실만으로 D01을 통과시키지 말고, App Server나 직접 Responses 어댑터가 이 표와 L4-01의 보존 시간선까지 통과한 뒤 지원을 선언해야 한다.

### L4-03 — Job Object와 `verify_isolation` 사이의 실제 보안 경계가 비어 있다

**종류와 결론: 계약 불충분.** 초안 6.3절 283–286행은 정지 프로세스를 Job에 넣은 뒤 재개하고, 6.4절 292–296행은 실행별 파일·도구·쓰기 권한을 요구한다. 3.4절 145–147행과 16.1절 839행은 중앙 Git 쓰기, 다른 비공개 결과 읽기, 작업 공간 밖 쓰기를 실제로 거부해야 한다고 한다. 하지만 Job 구성원 관리와 파일 접근 통제, 네트워크 통제, 실행기 IPC 인증을 수행할 구체 수단은 없다.

Windows Job Object로 프로세스 트리를 묶고 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`로 마지막 handle 종료 때 구성원을 종료하는 것은 가능하다. 현재 Windows 11은 중첩 Job도 지원한다. 반면 Microsoft 문서는 Vista 이후 Job의 보안 제한을 Job 자체가 아니라 각 프로세스에 따로 적용해야 한다고 설명한다. restricted token은 별도의 접근 토큰 검사로 securable object 접근을 줄인다. 즉 Job만으로 중앙 저장소 읽기·쓰기 거부를 얻는다는 해석은 성립하지 않는다. 근거는 [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [Restricted Tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens)다.

현재 Codex의 공식 Windows sandbox는 이 간극을 채울 수 있는 한 후보다. `elevated` 모드는 별도 저권한 사용자·파일 권한 경계·방화벽 규칙·private desktop을 사용하고, `unelevated`는 restricted token과 ACL을 사용하지만 네트워크 격리가 더 약하다고 명시한다. 로컬 `codex sandbox --help`도 restricted-token sandbox와 network disable 표면을 보인다. 근거는 [Codex Windows sandbox](https://learn.chatgpt.com/codex/windows/windows-sandbox)다. 다만 이 호스트에서 elevated sandbox가 실제 준비됐는지는 시험하지 않았고, 초안은 어느 모드가 통과 조건인지 정하지 않았다.

또한 3.4절 147행은 실행 ID 문자열을 권한으로 인정하지 말라고 하면서 16.3절 884행은 ‘구체 운송 방식’이 실제 실행 인스턴스를 인증해야 한다고만 한다. 구현자는 named pipe ACL, 상속한 capability handle, client process handle·생성 시각·Job membership 확인 중 무엇을 신뢰할지 새로 정해야 한다. 잘못 고르면 다른 실행이 요청 ID를 재생하거나 중앙 실행기 쓰기 API를 호출할 수 있다.

개선 방향은 프로세스 수명 경계와 권한 경계를 분리해 규범화하는 것이다. 첫 Windows 프로필에 최소 OS 버전, Job 설정과 breakaway 금지, restricted identity 또는 dedicated sandbox user, 중앙 저장소·다른 workspace의 ACL, 네트워크 기본 거부와 허용 endpoint, private desktop 여부, 자식 handle allowlist를 명시한다. 실행기 IPC는 실행기만 만드는 per-execution pipe/handle과 ACL을 쓰고, 서버가 요청 때 process handle·생성 시각·Job membership·현재 원장 상태를 함께 확인하도록 닫아야 한다. `verify_isolation`은 경로 별칭·자식 생성·다른 실행 토큰 재생·네트워크·중앙 Git 직접 접근을 포함한 음성 테스트 묶음과 실제 거부 오류를 보존해야 한다.

### L4-04 — Windows 경로 안전과 인스턴스 잠금의 정체성이 정해지지 않았다

**종류와 결론: 계약 불충분.** 초안 7.2절 375행은 상대 POSIX 경로만 허용하고 절대 경로·상위 이동·루트 밖 해석을 거부한다. 3.1절 118행과 14.1절 747행은 OS 독점 잠금 handle과 ‘경로 안전’을 요구한다. 그러나 논리 Git 경로를 Windows 물리 경로로 바꾸는 규칙, reparse point 처리, 대체 데이터 스트림, 대소문자·짧은 이름·device name 별칭, 잠금 객체의 유일한 이름과 ACL이 없다.

Windows에서 `..`가 없는 상대 경로도 중간 디렉터리의 junction·symlink 같은 reparse point를 따라 루트 밖으로 갈 수 있다. NTFS는 `file:stream` 문법의 대체 데이터 스트림도 지원한다. Microsoft 공식 설명은 reparse point가 파일을 열 때 별도 필터 동작을 일으키며, NTFS 파일에는 기본 스트림 외의 alternate stream이 있을 수 있다고 한다. 근거는 [Reparse Points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points), [Files and Clusters](https://learn.microsoft.com/en-us/windows/win32/fileio/files-and-clusters), [Streams](https://learn.microsoft.com/en-us/sysinternals/downloads/streams)다.

잠금 자체는 구현 가능하다. `CreateFile`을 share mode 0으로 성공시키면 handle이 열린 동안 충돌하는 후속 open을 막을 수 있다. 근거는 [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)다. 하지만 초안은 lock file인지 named mutex인지, 같은 인스턴스를 path alias로 연 두 호출이 같은 잠금을 쓰는지, 다른 Windows session·사용자에 걸친 namespace와 security descriptor가 무엇인지 정하지 않았다. 현재 C:가 고정 NTFS라는 사실은 이 호스트 후보에 유리하지만, 초기화 입력은 임의의 ‘내부 저장 위치’를 받으므로 같은 보장이 자동으로 따라오지 않는다.

가장 단순한 개선은 첫 구현의 저장 위치를 로컬 고정 NTFS의 승인된 루트로 제한하고, 인스턴스 ID에서 유일하게 도출한 lock file 또는 `Global\` named object와 명시적 ACL을 규범화하는 것이다. 논리 POSIX 경로와 물리 Windows 경로를 다른 형식으로 두고, manifest segment에서 `\`, `:`, 빈 segment, trailing dot/space, reserved device name을 거부해야 한다. 회수·쓰기 때 문자열 prefix 비교 대신 root handle에서 reparse를 통제해 열고 최종 handle 경로·volume을 확인해야 한다. trusted engine만 reparse point를 만들 수 있게 ACL을 두는 것도 함께 필요하다. ‘경로 안전 검사’라는 이름만으로 이 선택을 구현자에게 넘기면 안 된다.

### L4-05 — 스키마 가족 표와 직렬화 문면은 기계 계약으로 옮기기에 부족하다

**종류와 결론: 계약 불충분.** 0절 20행은 구현자가 문서 조건을 기계적으로 옮기고 원문에 없는 의미를 추가하지 말라고 한다. 그러나 5.2절 201–215행의 task 필드 표, 6.2절의 상태 값, 16.4절 888–923행의 28개 스키마 가족 표는 소유 의미만 설명한다. 실제 객체별 required/optional 필드, 자료형·범위, enum 판본, `oneOf` 분기, 참조형, 추가 필드 거부, 전이별 pre/postcondition과 원자 변경 묶음이 없다. 구현자가 실제 JSON Schema와 상태 전이 검사기를 만들려면 이 의미를 새로 정해야 한다.

7.3절 381–387행의 바이트 규약도 완결되지 않았다. JSON 키의 코드 포인트 정렬만으로 수 표현(`1`, `1.0`, `-0`), 문자열 escape, 단일 비NFC 문자열, BOM, 파일 끝 LF를 정하지 못한다. YAML은 사용할 판본과 scalar schema가 없어 날짜처럼 보이는 scalar, 정수 범위, 인용하지 않은 문자열의 해석이 parser마다 달라질 수 있다. ‘생성기와 검사기가 같은 판본’이라는 조건은 한 구현 안의 일치만 보장할 뿐, 그 판본이 어떤 바이트를 내야 하는지는 정하지 않는다.

반박으로 16.4절은 객체 필드를 닫고 기계 값 목록을 실제 스키마·도구에서 생성하라고 하며, 17.4절은 새 의미 선택을 문서 개정과 승인으로 닫도록 한다. 따라서 이 초안은 미완성을 인식한다. 문제는 18절의 미결 목록에 ‘규범 스키마와 canonical codec 확정’이 없고, 현재 문면만 읽으면 무엇을 구현해야 D 완료인지 추적할 ID가 없다는 점이다.

개선하려면 구현 전에 `schema bundle 1`을 별도 정본으로 만들고 이 문서의 각 필드·상태·명령 행을 schema `$id`와 전이 검사 함수에 대응시켜야 한다. JSON은 숫자 범위·escape·Unicode 정규화·BOM·끝 줄을 포함한 canonical byte grammar와 golden vectors를 둔다. YAML은 판본·허용 scalar schema·frontmatter delimiter·정수 범위를 닫고, parser 출력이 canonical JSON형 AST로 왕복되는 실패 벡터를 둔다. V01–V48 외에 객체별 최소/최대/잘못된 분기와 codec round-trip 벡터가 있어야 ‘기계적으로 옮겼다’를 판정할 수 있다.

### L4-06 — 슬롯 예산은 실제 공급자의 시간창 한도를 표현하지 못한다

**종류와 결론: 실제 지원 미확인 및 계약 불충분.** 4.1절 154–166행은 공급자가 함께 세는 동시성마다 `provider_slots`를 둔다. 속도·사용량 제한은 별도의 가용성 조건으로 프로필에 기록한다고 하지만, 4.3절 배정과 6절 실행 상태에는 그 한도를 소비·회복시키는 규칙이 없다. 한 `execution`이 도구 루프에서 여러 Responses 요청을 내는 경우도 슬롯 하나로만 센다.

확인한 OpenAI 공식 project rate-limit API가 노출하는 값은 모델별 RPM, TPM, 일별 요청, 이미지·오디오 한도, batch queue limit 등이다. 검사한 공식 스키마에는 초안의 `provider_slots`에 바로 넣을 동시 실행 수가 보이지 않았다. 이는 OpenAI에 어떤 동시성 제한도 없다는 주장이 아니라, 현재 공식 표면에서 D02의 값을 직접 회수하지 못했다는 뜻이다. 근거는 [List project rate limits](https://developers.openai.com/api/reference/ruby/resources/admin/subresources/organization/subresources/projects/subresources/rate_limits/methods/list_rate_limits)와 [Modify project rate limit](https://developers.openai.com/api/reference/python/resources/admin/subresources/organization/subresources/projects/subresources/rate_limits/methods/update_rate_limit)이다. 로컬 `codex exec-server --concurrent-requests`의 값은 로컬 서버 처리 상한이지 공급자 계정의 동시 한도라는 증거가 아니다.

예를 들어 work slot 하나를 가진 실행이 짧은 모델 호출을 연속해서 보내 TPM을 넘기면 슬롯 불변식은 모두 통과하지만 공급자는 요청을 거부한다. 초안은 이때 실행을 즉시 실패시킬지, `running`에서 backoff할지, 예약을 유지할지, Retry-After를 누가 신뢰할지 정하지 않는다. 여러 모델이 같은 project TPM을 공유할 때 `capacity_refs`를 어떻게 연결할지도 `provider_slots`만으로 표현할 수 없다.

18절 D02는 공유 동시 한도를 확인하게 하지만 이 간극을 완전히 닫지 않는다. 개선하려면 `provider_slots`를 ‘공급자가 확인한 동시성’이 아니라 ‘로컬에서 승인한 동시 실행 상한’으로 이름과 효력을 좁히거나, 실제 제공되는 동시성 값이 있는 backend에만 사용해야 한다. 별도로 시간창 quota를 `constraint_id`, 측정 단위, window, limit, observed usage, refresh source, retry policy로 모델링한다. 실행이 생성한 provider operation 전건을 계수하고 429·Retry-After·부분 응답 때의 상태 전이와 예약 유지 조건을 정해야 한다.

### L4-07 — 대화 소실 정책은 사건을 만들어 내는 인터페이스가 없다

**종류와 결론: 계약 불충분.** 3.3절 141행은 `conversation_loss_policy` 값을 닫고 ‘연결 생존의 판정 방법과 소실 사건 전달’을 실행 어댑터 검증 대상으로 둔다. 그러나 16.1절 실행 어댑터 기능에는 대화 연결 관찰이 없고, 16.3절 명령 표에도 대화 session 등록·heartbeat·detach 사건이 없다. 14.1절 745행은 정책 값만 초기화 입력으로 받는다. D03도 사용자가 continue/pause 중 무엇을 고르는지만 닫는다.

현재 Codex App Server에는 transport subscription과 thread 상태 사건이 있지만 이것을 사용자 대화 소실로 바로 읽을 수 없다. 공식 문서는 마지막 subscriber가 사라져도 활동이 없어진 뒤 30분 동안 thread를 유지하고, 그 뒤 `notLoaded`와 `thread/closed`를 보낸다고 설명한다. transient WebSocket 끊김, UI 종료, 사용자 로그아웃, daemon 소실, 단순 무활동은 서로 다른 사건이다. 근거는 [Codex App Server](https://developers.openai.com/codex/app-server/)의 thread subscription/status 절이다.

`pause`를 선택한 시간선에서 네트워크가 잠깐 끊겼을 때 즉시 모든 실행을 `stopping`으로 보낼지, 재접속 유예를 둘지에 따라 외부 효과와 연구 비용이 달라진다. 반대로 App Server의 `notLoaded`만 기다리면 사용자가 대화를 잃은 뒤 30분 이상 운전할 수 있다. 이는 회복 가능한 구현 세부가 아니라 사용자가 승인한 정책의 실제 효과다.

개선하려면 사용자 대화 어댑터를 실행 어댑터와 분리해 `conversation_id`, 관찰 source, `connected/disconnected/lost`의 판정 조건, 유예, heartbeat, 재접속 시 동일성, 중복 사건 ID를 규범화해야 한다. 정책 승인 화면은 각 사건이 언제 `pause`를 발생시키는지 평문으로 보여 줘야 한다. 선택한 ChatGPT/Codex surface가 해당 사건을 제공하지 않으면 `pause` 정책을 지원한다고 선언하지 않아야 한다.

### L4-08 — 모델 크리덴셜을 작업자에게 노출하지 않는 실행 토폴로지가 없다

**종류와 결론: 계약 불충분.** 13.4절 728–730행은 기록에 값 대신 `secret_ref`를 두고, 어댑터가 실행 직전에 값을 읽으며, 비밀을 AI prompt·Git·로그·산출물에 넣지 말라고 한다. 16.2절 854행도 credential ref와 로그 제거 규칙을 프로필에 넣는다. 그러나 secret store 종류·ACL·복호화 주체·프로세스 전달 방법·회전·폐기와 crash dump 정책은 없다. 16.4절에도 credential-store 또는 secret-access 기록 가족이 없다.

Codex CLI를 worker 프로세스로 넣는 단순 구현은 특히 위험하다. 모델 접속 credential을 같은 프로세스 환경에 넣고 Codex가 AI 선택 도구를 자식으로 실행하면, 환경 상속을 제대로 줄이지 않는 한 도구가 credential을 읽을 수 있다. OpenAI 공식 자동화 지침도 repository-controlled code나 untrusted code가 같은 process environment에서 실행되는 경우 `OPENAI_API_KEY`/`CODEX_API_KEY`를 job-level 환경 변수로 두지 말고, Codex 호출에만 제한하라고 경고한다. 근거는 [Codex non-interactive mode](https://developers.openai.com/codex/noninteractive/)의 automation authentication 절이다. Windows의 `CreateProcess` 공식 지침도 상속 handle을 allowlist하지 않으면 민감 자원이 자식에게 새어 나갈 수 있다고 경고한다. 근거는 [Create processes](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes)다.

초안의 비노출 목표는 타당하지만 ‘어댑터가 읽는다’만으로는 어떤 프로세스의 메모리·환경에 값이 존재하는지 닫히지 않는다. 개선 방향은 실행기 또는 별도 model broker만 비밀을 보유하고 sandbox worker는 인증된 IPC로 모델 작업을 요청하게 하는 것이다. Codex 자체를 worker로 써야 한다면 정확한 Codex 판본의 credential 전달과 자식 환경 scrub을 어댑터 계약으로 고정하고, worker가 실행한 `env`·PowerShell·자식·오류 덤프·로그에서 값과 파생 bearer가 나오지 않는 음성 시험을 해야 한다. secret store 선택, ref 해석 권한, 회전 후 미종료 실행 처분도 초기 구현 결정으로 추가해야 한다.

### L4-09 — 영속 시간선의 시계 계약이 없다

**종류와 결론: 계약 불충분.** 5.3절 230행은 대기의 재관찰 시각, 9.1절 457행은 계획 재검토 시각, 12.1–12.3절 658–680행은 운영 점검 시각과 관찰 시각, 13.2절 712행은 허가 효력 기간, 16.4절 917행은 runtime-event 시각을 사용한다. 그러나 timestamp 형식·timezone·정밀도, 지속 시간과 절대 시각의 구분, 벽시계가 앞뒤로 이동할 때의 처리, 같은 시각 사건의 순서를 정하지 않는다.

시계가 뒤로 조정되면 운영 점검이 승인 범위를 넘어 늦어질 수 있고, 앞으로 조정되면 허가·재관찰이 조기 만료될 수 있다. 재시작 뒤에는 monotonic clock 값을 그대로 복원할 수 없으므로 wall-clock 시각만 저장하는 구현과 deadline+남은 duration을 함께 저장하는 구현이 다르게 동작한다. 이는 수학 의미는 아니지만 정지·허가·예산에 실제 효과가 있는 운영 의미다.

개선하려면 영속 시각은 UTC RFC 3339의 고정 정밀도, 사건 순서는 원장 commit과 명시적 sequence로 정한다. 프로세스 생존 중 timeout은 monotonic clock으로 재고, 각 deadline의 UTC 관찰값과 당시 monotonic 기준을 함께 기록한다. 재시작·절전·wall-clock 이동 때 ‘기한을 이미 넘긴 것으로 보수적으로 처리’, ‘사용자에게 판정 불가 보고’ 등 필드별 규칙을 닫아야 한다. ULID의 시간 부분을 권위 있는 사건 순서나 허가 시계로 사용하지 않는다는 조건도 명시하는 편이 안전하다.

## 검증을 통과한 중요한 부분

1. **두 Git ref의 조건부 일괄 갱신은 현재 Git으로 구현 가능하다.** 설치된 Git 2.50.0의 `update-ref --stdin`은 `start/prepare/commit/abort` transaction을 지원한다. 공식 문서는 모든 ref를 기대 old OID로 동시에 잠글 수 있으면 모두 갱신하고, 그렇지 않으면 아무것도 갱신하지 않는다고 한다. 다만 동시 독자는 갱신 일부만 잠깐 볼 수 있다고도 한다. 초안 7.4절 405행이 runtime commit 하나를 먼저 고정하고 그 `state.json`이 가리키는 research commit을 읽도록 한 방식은 이 한계를 피하는 올바른 방향이다. 소비자가 두 ref의 현재 머리를 별도로 읽지 않는다는 조건을 테스트해야 한다. 근거는 [git-update-ref](https://git-scm.com/docs/git-update-ref.html)다.

2. **Windows Job 기반 시작·종료 순서는 구현 가능하다.** `CREATE_SUSPENDED`로 primary thread를 멈춘 채 만들고 Job에 할당한 뒤 `ResumeThread`할 수 있다. Job은 기본적으로 CreateProcess 자식을 포함하고, breakaway를 허용하지 않으며 `KILL_ON_JOB_CLOSE`를 설정하면 마지막 handle 종료 때 구성원을 종료한다. Windows 11 호스트는 중첩 Job을 지원한다. 따라서 6.3절의 ‘정지 생성 → Job 편입 → 원장 running 기록 → 재개’ 순서와 14절의 crash recovery 골격은 실현 가능하다. 다만 L4-03의 별도 권한 경계가 필요하다. 근거는 [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)와 [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)다.

3. **API가 제공하는 사실과 의미 판정을 분리한 방향은 실제 인터페이스와 맞는다.** Responses API는 response ID, 상태, 사용량과 입력 토큰 수를 반환하고, Codex App Server는 interrupt 요청 수락과 최종 turn 상태를 구분한다. 초안이 ‘stop 요청 성공’과 ‘종료 완료’, ‘출력 수신’과 ‘수학적 승인’을 분리한 것은 구현 가능한 구분이다.

4. **현재 호스트가 실운전 준비를 마쳤다는 주장은 하지 않았다.** 실제로 `lean`, `lake`, `do-math`가 없으므로 지금 이 호스트에서 15절의 신뢰 환경이나 17절 워크스루를 통과했다고 볼 수 없다. 0절과 18절이 새 구현·어댑터 지원을 주장하지 않는 것은 실제 상태에 충실하다. 이는 설계 결함이 아니라 아직 수행하지 않은 구현·검증 상태다.
