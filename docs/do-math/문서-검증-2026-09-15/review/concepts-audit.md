# do-math 문서 자산 개념·설계 감사

## 판정과 범위

**완료.** 이 보고서는 정본을 수정하지 않은 개념 감사다. 읽은 원본은 `docs/do-math/통합-설계.md`의 0~3절(1~356행), 7~11절(699~1347행)과 용어 전달 계약을 직접 정하는 16.5절(1865~1888행), 루트 `CONTEXT.md` 전문(1~499행)이다. 대조 대상은 `.claude/skills/do-math/GLOSSARY.md`, `SKILL.md`, `계약/`의 10개 역할 계약 전문이다. 정의의 실제 소비를 확인하기 위해 `scripts/do_math/contracts.py`의 문서 주입·프롬프트·출력 스키마(17~132행), `engine.py`의 역할 입력 구성·확장 처리(588~747, 1147~1303행), `knowledge_io.py`의 종류 레지스트리(13~110행)만 제한적으로 확인했다.

적용한 문서 설계 원리는 `.claude/skills/domain-modeling/SKILL.md`와 `CONTEXT-FORMAT.md`, `.claude/skills/writing-great-skills/GLOSSARY.md`, `.claude/skills/write-for-reader/SKILL.md` 및 `references/명료한_산문.md`, `references/AI_프롬프트.md`, `references/절차문.md`에서 회수했다. 핵심 원리는 같은 개념에 같은 낱말을 쓰고, 정의·경계·피해야 할 동의어를 한 정본에 모으며, 공통 정의와 역할별 행동을 분리하고, 필수 자료의 포인터가 실제 읽기 전에 발동되게 하며, 상태·분기의 완료 기준을 관찰 가능하게 쓰는 것이다. 이 원리는 통합 설계가 이미 정한 소유 구조를 바꾸는 근거로 사용하지 않았다.

현재 문서는 검증을 통과하지 못한다. 핵심 결함은 세 가지다.

1. 런타임 역할은 루트 `CONTEXT.md`를 받지 않고 `SKILL.md`, `GLOSSARY.md`, 자기 역할 계약만 받는데, GLOSSARY는 루트의 보편 개념 약 100개 가운데 17개 묶음만 다룬다. 역할 계약이 실제로 쓰는 `연구 맥락`, `종류 정의`, `온톨로지`, `시맨틱 레이어`, `지식 재사용`, `후보 목차`, `K 목차`, `정확한 참조`, `현재성`, `봉인`, `검토 방침`, `검토 계획`, `이의`, `판정 사용 효력` 등의 뜻과 관계를 역할 입력만으로 복원할 수 없다.
2. 일부 축약은 생략을 넘어 원뜻을 바꾼다. `K(검증된 수학 지식)`, `정보 상태`, `인스턴스 상태`, `검토 자리와 주기`, `외부 작업`은 루트 정본의 명칭·경계와 다르거나 여러 독립 축을 합친다. 특히 CLI의 편의 상태를 보편 상태처럼 정의해 통합 설계의 상태 기계와 충돌한다.
3. `SKILL.md`는 16.5절이 단독 소유자로 지정한 목적·전체 흐름을 설명하지 않고 명령과 공통 주의사항 중심으로 축약돼 있다. 동시에 실제 역할 판단에 필요한 의미 규칙은 `contracts.py`의 영문 프롬프트 문자열에도 흩어져 있다. 독자는 문서만 읽어 실제 역할 계약을 알 수 없고, 한 뜻을 한 곳에서 고치는 구조도 아니다.

## 정본과 전달 경로

정의 위치를 새로 설계할 필요는 없다. 통합 설계가 다음 소유권과 전달 경로를 이미 닫았다.

| 원문 좌표 | 확정된 소유와 전달 |
|---|---|
| 통합 설계 0절 8~10행 | 통합 설계는 전체 설계 정본이다. 보편 개념 정의는 루트 `CONTEXT.md`가 소유하고 구현 `GLOSSARY.md`는 그 정의를 저작 원천으로 삼는다. |
| 통합 설계 0.3절 75~110행 | 같은 개념은 낱말 하나로 부른다. 표는 낱말과 요지를 제공하고 상세 규정은 각 소유 절이 가진다. `봉인`처럼 소유 절이 0.3인 말만 이 표 자체가 정의다. |
| 통합 설계 0절 36~40행 | 권한·판정·전이의 의미는 주제별 본문 절이, 기계 자료 형식은 스키마 묶음이 소유한다. 이름·필드·스키마 통과는 실행 능력이나 의미 승인을 대신하지 않는다. |
| 통합 설계 1.4절 181~190행 | 연구 헌장·정책·맥락·설정은 서로 다른 의미를 소유한다. 특히 연구 맥락은 용어 정의와 경계를 맡고, 형식 정의를 복제하지 않고 형식 결과와 인증 해설을 연결한다. |
| 통합 설계 1.5절 194~208행 | 온톨로지는 종류 정의·연구 맥락·K의 형식 정의와 해설이 분담하고, 시맨틱 레이어는 기록의 의미·확인 범위·근거·효력을 조회·해석·재사용에 연결한다. 별도 지식 정본이나 판정 권한을 만들지 않는다. |
| 통합 설계 7.3절 766~795행 | 지식 문서의 기록 가족, 구체 종류, 정보 상태, 확인 범위, 효력, 종류 정의와 관계 제약을 소유한다. 가변 종류 토큰과 제약은 종류 정의 레지스트리에서 읽는다. |
| 통합 설계 7.3.1절 797~815행 | 생산자가 저작할 대상 연결, 확인 범위, 원자료·계보, 관계, 후속 판단 변화와 남은 질문의 위치를 정한다. |
| 통합 설계 7.3.2절 817~831행 | 반복 관계의 템플릿과 수학 관계의 방향·증명 의무를 정한다. 템플릿은 실제 관계 기록이나 착수 조건이 아니다. |
| 통합 설계 8.1절 848~869행 | 모든 역할은 `SKILL.md`·`GLOSSARY.md` 전문, 자기 계약·참조 전문과 적용 통치 문면을 실질 판단 전에 받는다. 공통 정의를 발췌로 대신하거나 입력 초과 때 조용히 생략하지 않는다. |
| 통합 설계 8.4절 934~944행 | 조회가 종류 정의·연구 맥락·관계 방향·근거·정보 상태·확인 범위·판정 효력을 회수해야 하며, 준비·계획·수행·보충 조사가 지식 적용과 남은 차이를 판단해 산출에 남긴다. |

실제 소비 코드도 이 경로를 확인한다. `contracts.py` 91~102행은 역할마다 `SKILL.md`, `GLOSSARY.md`, 역할 계약 하나만 읽는다. 130~132행은 이 세 문서 뒤에 인스턴스 입력과 출력 스키마를 붙인다. 루트 `CONTEXT.md`는 역할 프롬프트에 들어가지 않는다. 따라서 루트 정의를 알고 있는 문서 작성자에게만 이해되는 축약은 런타임 계약으로 충분하지 않다.

## 실제 필요한 개념 가족과 관계

아래 가족은 새 분류가 아니라 루트 `CONTEXT.md`의 기존 절 구성을 그대로 따른다. 각 항목의 “필수 의미”는 GLOSSARY가 루트 정의를 왜곡하지 않고 전달해야 할 최소 관계다. 역할별 적용 행동은 뒤의 역할 계약에 둔다.

### 1. 주체·통치·권위

`AI 연구 체계`, `연구 책임자`, `연구 운영자`, `기계 실행기`, `AI 활동`, `사용자 대화`, `연구 인스턴스`가 주체와 지속 단위를 구분한다(`CONTEXT.md` 25~63행). 이 구분은 누가 의미를 저작하는지, 누가 바이트를 쓰는지, 누가 승인하는지를 분리하기 위해 필요하다. 기계 실행기의 쓰기 권한은 수학 판정이나 문면 저작 권한이 아니며, 사용자 대화는 전달 채널이지 실행 권한의 소유자가 아니다.

`연구 헌장`, `연구 정책`, `연구 맥락`, `연구 설정`은 통치 기록의 네 축이다(65~79행). 헌장은 목적·성공 기준, 정책은 규범, 맥락은 인스턴스 고유 용어, 설정은 기존 목적과 정책 안의 운용값을 소유한다. 역할이 “목표”, “정책”, “맥락”, “설정”을 서로 대신하면 사용자 승인 범위와 변경 절차가 달라진다. 현재 GLOSSARY에는 이 가족 전체가 없다.

`허가`, `사례 기반 위임`, `사용자 결정`, `결정 질문`은 행동 가능 범위와 결정의 재사용을 구별한다(345~350, 397~403행). 사용자 결정은 모든 행동의 포괄 권한이 아니며, 사례 기반 위임은 명시된 결정 종류와 적용 범위에서만 재사용된다. 현행 GLOSSARY 13행의 `허가와 권한` 한 항목은 이 경계를 설명하지 못한다.

### 2. 수학 상태와 연구 공간

`형식 정본(K)`, `Lean 정본`, `형식 결과`, `형식 타당성`, `신뢰 환경`, `기초 프로필`은 형식 수학과 그 신뢰 기준을 분리한다(`CONTEXT.md` 83~105행). K는 “검증된 수학 지식”이라는 일반 집합이 아니라, 유효한 활성 신뢰 환경에서 편입 관문을 통과해 Lean 정본에 보존된 형식 객체의 집합이다. 각 객체가 외부 수학 의도와 같은지는 연결된 동일성 판정 범위에서 별도로 성립한다. 형식 결과의 형식 사용 효력과 해설 판정의 사용 효력도 별도 축이다.

`가시 연구 프런티어(F)`, `미지 지평(U)`, `탐색`, `집중 활용`, `연구 진전`, `진전 신호`, `수학적 해결`, `K 편입`은 후보 생성부터 목표 해결까지 서로 다른 효과를 구별한다(107~137행). F는 현재 명시한 후보와 부분 결과이고 U는 아직 명시하지 못한 가능성이다. 탐색은 U 일부를 F로 드러내며, 집중 활용은 근거 있는 F를 입증 가능한 결과로 전진시킨다. 후보 발견, K 확장, 진전 신호, 과제 완료, 수학적 해결은 서로 대신하지 않는다. 이 가족이 없으면 후보 준비와 연구 계획은 “새 후보를 만드는 일”과 “현재 후보를 증명하는 일”, “일을 끝낸 것”과 “목표에 가까워진 것”을 같은 말로 처리하게 된다.

### 3. 기록·온톨로지·시맨틱 레이어

`연구 정본`, `실행 원장`, `상태 공개`, `기록 ID`, `정확한 참조`, `읽기 스냅샷`, `현재성`, `봉인`은 기록의 위치, 정체성, 판본, 적용 시점을 구분한다(141~171행). 정확한 바이트가 보존됐다는 사실은 승인이나 현재 사용 가능성을 뜻하지 않는다. 고정 스냅샷에서 내린 판단은 적용 직전에 실제 의존 전제의 현재성을 다시 검사해야 한다.

`지식 문서`, `F 객체`, `자료·근거`, `관계`, `연구 기억`, `종류 정의`, `온톨로지`, `시맨틱 레이어`, `항해 색인`, `지식 재사용`은 지식 축적과 재사용의 핵심 가족이다(173~210행). 관계는 방향·양끝·근거를 가진 독립 기록이고 본문 링크나 검색 경로가 아니다. 연구 관계는 수학적 함의를 주지 않으며 수학 관계는 형식 결과와 동일성 판정을 요구한다. 종류 정의는 F 또는 관계 종류의 의미와 제약을 소유한다. 지식 재사용은 현재 질문의 대상·가정·필요 결론을 기존 내용·확인 범위·근거·효력에 대조해 적용 조건과 남은 차이를 남기는 행위다.

온톨로지와 시맨틱 레이어의 관계는 특히 중요하다. 온톨로지는 “무슨 종류의 대상과 연결인가”를 표현하고, 시맨틱 레이어는 그 의미를 “어떤 범위에서 어떤 근거와 효력으로 지금 재사용할 수 있는가”에 연결한다. 검색이나 목차는 발견 수단일 뿐 적용 판정이 아니다. 현행 GLOSSARY에는 `원자료와 관계`라는 결합 항목만 있고, 이 체계를 구성하는 나머지 개념이 전부 빠져 있다.

### 4. 후보·과제·계획과 인계

`연구 후보`, `과제`, `작업 계약`, `진전 기준`, `발생 조건`, `작업 계약 검토`, `배정 후보`, `과제 대기`, `범위 처분`은 아이디어에서 지속 연구 의무와 착수 가능성까지를 구별한다(`CONTEXT.md` 215~249행). 연구 후보는 아직 계약이 아니며, 과제 생성은 실행 약속이 아니다. 작업 계약은 질문·범위·입력·산출·진전·완료·판정자·허가·프로필을 고정한다. 계약 검토의 승인은 최종 선택이 아니며, 배정 후보는 기계가 현재 착수 전제를 검사한 파생 결과다. 과제 완료에는 완료 기준과 범위 처분이 필요하다.

`후보 준비`, `고갈`, `연구 계획`, `계획 입력`, `후보 목차`, `K 목차`, `정기 탐색`, `반복 교정 문턱`은 준비와 선택의 분리를 설명한다(251~280행). 후보 준비는 제안을 저작하고, 별도 연구 계획은 제공된 배정 후보를 선택한다. 후보 목차는 거친 F 전건이 아니라 작업 계약 목록이며, K 목차는 형식 정본 객체의 현재 판정·효력·검증된 해설 요약을 보여 주는 기본 입력이다. 목록은 원문이나 의미 적용 판정을 대신하지 않는다.

인계는 별도 새 개념이 아니라 이 관계의 시간선이다. 통합 설계 2.4절 260~271행과 9.2.1절 1020~1034행은 `후보 준비 → 작업 계약 검토 → 기계 착수 검사 → 연구 계획 선택 → 연구 수행 → 후보 준비·연구 계획`을 정한다. 준비가 계약을 만들기 위한 새 근거를 얻어야 하면 연구 수행 과제를 제안한다. 그 조사 과제가 계약대로 완료돼도 원래 후보의 계약 완성이나 배정은 자동으로 성립하지 않는다. 이 전달을 각 역할 계약이 자기 입력·산출·다음 소유자로 설명해야 한다.

### 5. 실행·자원·관찰

`유지보수`, `실행`, `연구 수행`, `기계 작업`, `실행 프로필`, `실행 어댑터`, `작업 예산`, `운영 예산`, `자원 예약`, `공급자 호출`, `종료 장벽`, `산출 묶음`, `작업 공간`, `체크포인트`, `정지 직전 기록`은 활동을 실제 한 번 수행하는 단위와 자원·종료·인계를 구별한다(285~343행). 과제·활동·실행은 계층 관계이고, 한 실행이 여러 공급자 호출을 만들 수 있다. 실행 종료는 원격 정산이나 과제 완료가 아니다. 체크포인트는 재개와 다음 소유자가 쓸 공개 인계 기록이지 임시 파일이나 완료 선언이 아니다.

`관찰 규칙`, `자기 점검 의무`, `안전 제어 경계`, `자기 점검`, `운영 점검`, `점검 발동 조건`, `운영 처분`은 관찰과 의미 판단의 주체를 구분한다(355~381행). 시간·로그·프로세스 생존은 수학 진전이 아니다. 발동 조건은 검토 의무를 열 뿐 자동 중단이나 결함 판정이 아니며, 운영 점검이 실제 근거로 처분을 제안하고 실행기가 현재 전제를 검사해 적용한다.

### 6. 수입·외부 효과·검증·복구

`프로젝트 입력`, `수입`, `의도 해석`, `외부 행동`, `크리덴셜`은 외부 원문 보존과 내부 의미 편입, 행동 권한을 나눈다(385~410행). `외부 행동`이 정본 명칭이다. HTTP는 가능한 어댑터 한 종류일 뿐 정의의 범위가 아니다.

`수학 해설`, `수학 제안`, `해설 요약`, `검토 방침`, `검토 계획`, `동일성 검토`, `검토 자리`, `이의`, `동일성 판정`, `판정 사용 효력`, `보충 조사`, `목표 감사`, `추가 감사`, `학술 검증`, `공용 편입`은 형식 결과와 사람이 읽는 의미를 연결하는 검증 가족이다(415~473행). 검토 방침은 규범, 검토 계획은 한 제안의 배치 기록, 검토 자리는 회차를 넘어 대화를 잇는 논리적 자리, 이의는 좌표·논증을 가진 검토자 주장, 동일성 판정은 활동의 최종 결과다. 이들의 경계가 없으면 초기 이의, 심사 결과, 최종 판정, 판정의 현재 사용 효력이 뒤섞인다.

`일시 정지`, `실행기 복구`, `계약 전환`, `실행 능력 검증`, `연구 효능 평가`, `상태 검사`는 운전·복구와 보증 범위를 구별한다(477~499행). 작은 실행 성공이나 상태 검사 통과는 연구 효능을 보증하지 않는다.

## SKILL과 역할 계약의 실제 결함

### SKILL.md

통합 설계 16.5절 1867행은 SKILL을 “목적·전체 흐름과 역할 읽기 대응표의 단독 소유자”로 정한다. 현행 SKILL 8행은 “역할별 AI 실행을 준비하고 결과를 연결한다”는 한 문장만 주고, 10~20행은 CLI 명령과 구현 제한, 22~29행은 읽기 순서, 31~43행은 공통 산출 주의사항이다. 정상 흐름인 `헌장 확정 → 기존 K 확인 → 후보 준비 → 계약 검토 → 배정 후보 계산 → 연구 계획 선택 → 연구 수행 → 지식 저작·공개 → 형식·동일성 검토 → K 편입 → 목표 감사 → 다음 계획`을 설명하지 않는다(통합 설계 2.1절 215~228행). 역할 대응표 47~58행도 각 역할의 명사형 입력·산출만 나열해 선행 조건과 다음 소비자를 보여 주지 않는다.

따라서 SKILL 재작성은 다음 관계를 설명해야 한다.

- 기계 실행기는 실행·기록·권한을 소유하고 AI 역할은 의미·판정·이유를 저작한다.
- 후보 준비는 제안을 저작하고 계약 검토는 배정 가능할 만큼 판정 가능한지 검토하며, 기계가 현재 착수 조건을 계산하고 별도 연구 계획이 최종 선택한다.
- 연구 수행의 결과는 과제 완료와 별개로 보존되고, 지식 저작·수학 검토·목표 감사·다음 준비·계획으로 갈라진다.
- 형식 타당성, 동일성 판정, 목표 감사, 행동 허가, 실행 상태는 서로 대신하지 않는다.
- 각 역할 행에는 진입 조건, 핵심 판단, 직접 산출, 다음 소비자를 적고, 상세 절차는 역할 계약이나 공용 reference로 보낸다.

### 역할 계약별 누락

**후보 준비**는 가장 큰 공백이다. 통합 설계 16.5절 1875행이 요구하는 8.4절 지식·관계 탐색, 8.5절 목차·선택/준비 이력, F·계약 생성·정련·개정·요지, 작성·검토·선택 인계, 탐색·활용·렌즈, 주기·고갈·반복 문턱이 현행 17행에 거의 없다. 5행의 “K·F·근거·관계·맥락”은 정의되지 않은 명사 목록이고, 실제로 무엇을 대조해 어떤 생성 근거와 남은 차이를 남기는지 없다. 17행의 “상위 과제 결과와 K의 현재 사용 효력이 충족돼야 배정”은 모든 의존 과제에 적용되는 일반 규칙처럼 읽히지만, 통합 설계는 작업 계약의 정확한 발생 조건과 필수 입력에 따라 판단한다. 조건 없는 보편 선행조건으로 쓰면 안 된다.

**연구 계획**은 구현 배열 채우기에는 구체적이지만 연구 판단 계약이 부족하다. 통합 설계 9.2절 1003~1016행의 목표·실제 결과, 탐색·집중 활용, 정보 가치·불확실성, 중복·보완·의존, 기아 위험, 실제 재사용 지식과 남은 차이, 과거 기대와 실제 결과의 변화가 빠져 있다. 9행의 `ready 후보`는 보편 `배정 후보`와 CLI 상태 `ready`를 구별하지 않는다. 통합 설계의 처분은 `selected·not_selected·not_assessable`인데 현행 출력은 `selections·deferred`만 있어 `not_assessable`의 의미와 현재 구현에서의 반환 방법을 문서로 알 수 없다. 이 차이는 코드 지원 여부를 확인해 계약에 사실대로 적어야지 문장으로 없는 출력을 약속하면 안 된다.

**연구 수행**은 작업 범위와 Lean 후속은 설명하지만, 16.5절 1877행이 요구하는 7.3.1절 저작, 8.4절 지식 재사용·인계, 관찰 적응·발동 소비·사건별 자기 점검, 정지 직전 기록과 남은 의무를 충분히 설명하지 않는다. `지식`, `정보 상태`, `부수 산출`이 어떤 기존 개념과 필드에 대응하는지도 없다. 연구 관계와 수학 관계를 구별하고, 실제 사용한 지식의 적용 조건·남은 차이와 새 관계의 근거를 어디에 남길지 설명해야 한다.

**작업 계약 검토**는 16.5절 1878행의 항목을 한 문장으로 압축했다. `approved`, `revision_required`, `unresolved`의 경계, 공통 판단 전제와 프로필별 전제, 유효한 승인 재사용과 현재성 검사, 의미 결함을 후보 준비로 돌리는 인계를 구체화해야 한다. 현행 계약 15행은 `validity basis`를 요구하지만 실제 기본 출력 스키마는 `decision`과 문자열 `findings`만 제공한다(`contracts.py` 61행). 문서가 요구하는 항목별 근거를 실제 출력이 보존할 수 있는지 별도 구현 대조가 필요하다.

**동일성 검토**는 다른 계약보다 상세하지만, 공통 개념이 GLOSSARY에서 빠져 있어 자체 문서가 정의와 절차를 함께 떠안는다. `action.stage` 값은 계약 표에서 `initial·organize·answer·judge`인데 통합 설계의 stage는 `planning·reviewing·clarifying·judging`, output phase는 `initial·organize·answer·judge`다(11.3.2절 1236~1248행). 현행 구현 계약의 필드 이름이 다르면 보편 단계와 CLI 필드의 대응을 명시해야 한다. `검토 자리와 주기` 같은 새 합성어로 덮으면 안 된다.

**목표 감사**는 목표·범위·성공 기준 대조는 말하지만, 정확한 목표 판본과 현재성, 실제 사용한 동일성 판정과 효력, 부분 결과·남은 차이, 추가 감사의 프로젝트 판정과 효과를 충분히 설명하지 않는다. `eligible_knowledge`가 구현상 선별된 입력이라는 사실과 K 전체의 정의도 구별해야 한다.

**보충 조사**는 검토 자리의 고정 질문 절차는 비교적 충분하다. 다만 일반 과제형 보충 조사와 검토 귀속 보충 조사를 같은 이름으로 쓰므로 공통 정의와 두 진입 계약의 관계를 첫머리에서 분명히 해야 한다. `answered`는 질문의 답이지 수학 승인이나 상위 검토 완료가 아니라는 경계는 유지할 가치가 있다.

**운영 점검**은 관찰·복구 개념이 거의 모두 GLOSSARY에 없고, 계약도 실제 상태 대조를 15행으로 줄였다. 통합 설계 16.5절 1882행의 발동과 중단 구별, 결정론 검사로 확인할 복구 전제와 AI 의미 판단의 구별, 처분 권한, 재생 안전성을 설명해야 한다. `live_review`, `continue·checkpoint·revise·wait·stop`과 실패 진단의 `retry·revise·wait·stop`이 보편 운영 처분에 어떻게 대응하는지도 역할 계약이 소유해야 한다.

**의도 해석**은 사용자 원문을 내부 소유자로 나누는 목적을 말하지만 실제 `proposed_changes`를 goal·policy·none으로만 한정한다. 통합 설계와 루트 정의는 헌장·정책·맥락·설정·허가·F·자료·기억·과제 등 의미 단위의 내부 소유자를 구별한다. 코드가 현재 목표·정책만 적용한다면 계약은 그 지원 범위를 명시하고 나머지를 다음 소유자·미지원으로 반환해야 한다. 지원하지 않는 소유자를 문서만으로 이미 처리한다고 쓰면 안 된다.

**유지보수**는 초기화·편입·전환·복구를 한 문단에 합쳐 각 절차의 정확한 진입 조건, 변경 권한, 결과, 실패 시 복귀 좌표가 없다. 긴 공유 절차를 `references/`에 두고 역할 계약이 어떤 action에서 어느 절차를 읽는지 연결하는 것이 16.5절의 구조와 맞는다.

## 정의와 설명의 경계

경계는 다음처럼 적용해야 한다. 이는 새 소유 구조가 아니라 통합 설계 16.5절의 실행 규칙이다.

| 위치 | 여기서 한 번 소유할 내용 | 여기서 반복하지 않을 내용 |
|---|---|---|
| 루트 `CONTEXT.md` | 보편 개념의 정본 이름, 뜻, 경계, 피할 동의어. 현재 약 100개 정의가 이미 존재한다. | CLI 필드명, 역할별 단계, 상태 전이의 세부 검사. |
| 구현 `GLOSSARY.md` | 루트 정의를 원천으로 런타임 모든 역할이 알아야 할 공통 개념·판정의 충실한 구현 투영. 같은 정본 이름을 쓰고, 필요한 경우 루트의 `_Avoid_`와 이웃 개념을 보존한다. CLI 고유 상태·필드가 보편 개념과 다르면 별도 이름으로 사상을 명시한다. | 역할별로 무엇을 제출하는지, 긴 절차, 한 역할만 쓰는 schema 필드의 사용법. 루트 뜻을 새로 축약·재정의하지 않는다. |
| `SKILL.md` | do-math의 목적, 전체 연구 순환, 주체별 책임의 큰 경계, 모든 역할의 읽기 순서와 역할 대응표. 대응표는 각 역할의 진입·판단·산출·다음 소비자를 보여 준다. | 개념 사전의 재정의, 역할별 세부 출력 필드, 모든 예외 절차. |
| 역할 계약 | 그 역할이 공통 개념을 어떤 입력에서 어떻게 대조하고, 무엇을 판단·산출하며, 실패·미완료·대기 때 누구에게 무엇을 돌려주는지. 역할 고유 필드와 단계의 의미. | K·F·현재성·봉인 같은 공통 개념의 새 정의, 다른 역할의 절차 전문. |
| `references/` | 둘 이상의 역할이 실제로 함께 쓰는 긴 절차. 예: 지식 조회·적용·저작·인계, 체크포인트와 정지 직전 인계, 공통 수리·실패 반환처럼 본문이 지정한 공유 절차. 정의를 분리하면 GLOSSARY가 정확한 포인터를 갖고 사용하는 역할의 읽기 목록이 전문을 배정해야 한다(통합 설계 8.1절 859행). | 역할 하나의 짧은 판단 규칙, 단순히 문서를 짧게 만들기 위한 임의 분할. |
| `kind_definitions`와 관계 템플릿 | 인스턴스에서 허용하는 구체 F/관계 종류 토큰, 의미, 방향, 양끝, 근거·수학 판정 요구. 템플릿은 비활성 저작 틀이라는 지위. | 온톨로지·관계·근거·수학적 연결이 무엇인지에 대한 보편 정의. |
| 출력 스키마·검사기 | 정확한 필드, 자료형, 닫힌 값, 누락 표현, 기계 결속과 수신 검사. | 자연어 판단 기준이나 수학 의미의 충분성을 스키마 존재로 대신하는 설명. |

공통 정의를 매 역할 계약에 복사하지 않는다. 역할 계약은 “`지식 재사용`의 공통 정의에 따라 A·B·C를 대조하고 D를 남긴다”처럼 이미 정의한 낱말을 사용해 구체 행동만 추가해야 한다. 반대로 역할이 처음 접하는 구현 전용 필드인 `ready_universe_ids`, `review_cycle_id`, `proposal_digest`, `live_review`는 역할 계약에서 그 필드가 어떤 공통 개념의 어느 판본·단계를 표현하는지 설명해야 한다.

`CONTEXT-FORMAT.md`의 “1~2문장”은 이 저장소의 확정된 통합 설계보다 우선하는 분량 상한이 아니다. 루트 CONTEXT는 이미 경계와 관계를 충분히 정의한다. 런타임 GLOSSARY를 줄이는 목표보다, 역할이 같은 뜻으로 판단할 수 있는 충분성이 우선한다. 긴 공유 절차는 progressive disclosure를 적용하되, 모든 경로에 필요한 정의를 약한 포인터 뒤에 숨기지 않는다.

## 코드 소비에서 확인한 문서 밖 의미와 구현 어휘 차이

이 절은 코드로 문서 공백을 정당화하지 않고, 문서가 주장할 수 있는 현재 기능 범위를 제한하기 위한 확인이다.

1. `contracts.py` 114~128행은 문서 외부의 공통 프롬프트에 연구 계획 ID 규칙, 후보 준비 개정, 지식 입력 참조, Lean 제출, 확장 파일 가족, 종류 정의와 수학 관계, 관찰 규칙을 직접 적는다. 이들은 단순 전달 외피가 아니라 역할의 판단·행동을 바꾸는 의미 규칙이다. 같은 내용이 SKILL·역할 계약과 중복되거나 문서에는 아예 없어 single source of truth를 위반한다. 최종 재작성에서는 의미 규칙을 통합 설계가 정한 문서 소유자에 모으고, 렌더러는 문서·입력·스키마를 결합하는 최소 실행 외피만 가져야 한다. 코드 변경 여부는 상위 작업 범위에서 결정하되 문서만 고쳐 중복을 남기면 감사 결함이 해소되지 않는다.
2. `contracts.py` 48~53행의 지식 스키마는 `kind`, `title`, `statement`, `explanation`, `summary`, Lean 필드와 dependencies만 받고, 통합 설계 7.3.1절이 요구하는 확인 범위·근거·연결은 확장 파일에 흩어진다. `engine.py` 770행과 125행 프롬프트 문자열이 `knowledge_metadata`, `relations`, `research_insights`를 따로 안내한다. 어느 역할이 어떤 저작 단위를 함께 제출해야 하는지 역할 계약에 연결되지 않았다.
3. `knowledge_io.py` 34~68행은 종류 family를 `knowledge`와 `relation`으로 정의하고 `definition·theorem·observation` 등을 추가한다. 통합 설계 7.3절 781~789행은 family를 `frontier`와 `relation`으로, 초기 F 종류를 `question·conjecture·definition_candidate·proof_candidate·research_direction·obstacle·partial_result`로 정한다. 추가 종류는 가능하지만 기존 종류 정의를 먼저 검증해 추가해야 한다. 현재 구현 어휘가 계약상 확장인지 CLI 투영인지 문서에 없다. GLOSSARY가 이를 새 보편 정의로 흡수해서는 안 되며, 실제 종류 정의 기록·검증 경로와 함께 정합성을 확인해야 한다.
4. `engine.py` 1192~1211행은 부수 통찰을 `information_state=hypothesis`인 `knowledge`로 만든다. 루트에는 F 인식 상태, 연구 기억 정보 상태, 계획의 근거 성격이 분리돼 있다. 현재 GLOSSARY의 `정보 상태`가 이 구현 필드를 정당화하지 않는다. 어느 기록 가족의 어떤 상태인지 구현 계약을 명확히 해야 한다.
5. `engine.py` 641~667행은 각 역할에 goal, policies, tasks, knowledge catalog, relations, recent history, resources, kind definitions 등을 넣지만 루트 연구 맥락·설정 전문을 독립 문면으로 넣는 구조는 확인되지 않는다. 통합 설계 8.1절 859행은 후보 준비와 최종 선택에 헌장·활성 정책·설정 전문을 기본 제공하라고 한다. 이름이 비슷한 JSON 필드가 있다는 사실로 그 전문과 의미를 제공했다고 선언하면 안 된다.

## 독자가 이해했는지 확인할 시나리오

아래 시나리오는 정의를 암송하는 검사가 아니라, 새 상황에서 개념을 구별하고 올바른 다음 소유자를 선택할 수 있는지 확인한다. 재작성 후 문서만 제공한 역할에게 적용할 수 있다.

### 시나리오 1: 부분 정리와 목표 해결의 구별

입력은 목표 `P`, 인증된 결과 `H → P`, 아직 입증되지 않은 `H`다. 독자는 `H → P`가 K에 편입될 수 있고 그 해설·요약은 H와 적용 범위를 보존해야 하지만, 목표 감사가 무조건 P를 충족했다고 판정할 수 없음을 설명해야 한다. F에는 P와 남은 H 질문, 부분 결과의 실제 관계가 남는다. 다음 계획은 H의 입증·제거 또는 다른 접근을 고른다. 과제 완료·실행 종료·K 편입·수학적 해결을 각각 구별해야 통과다. 근거는 통합 설계 2.2절 231~248행이다.

### 시나리오 2: 선행 조사의 인계

F에 질문 P가 있으나 작업 계약을 만들 만큼 접근 범위와 근거가 없다. 후보 준비는 조사 질문·범위·필수 입력·기대 산출·완료 기준을 가진 연구 수행 제안을 만든다. 조사자는 지정 범위를 모두 조사했지만 유망한 접근을 찾지 못하고 실제 시도·확인 범위·장애물·남은 질문을 반환한다. 독자는 조사 과제가 계약상 완료될 수 있지만 P가 해결되거나 원래 계약이 자동 완성된 것은 아니며, 결과가 다시 후보 준비와 별도 연구 계획으로 간다고 판정해야 한다. 근거는 통합 설계 2.4절 260~271행과 9.2.1절 1020~1034행이다.

### 시나리오 3: 검색 결과와 지식 재사용

질의에서 A에서 B로 가는 `supports` 관계 하나와 B의 형식 결과가 발견됐다. A에 B의 결론을 적용하려면 가정 하나가 더 필요하고, 관계의 확인 범위는 작은 유한 사례뿐이다. 독자는 `supports`가 수학적 함의가 아니며 검색 경로도 적용 증명이 아님을 말해야 한다. B의 원문·해설·판정 효력과 가정·범위를 대조하고 남은 차이를 산출에 남긴다. 필요하면 `formally_implies`를 입증할 새 과제를 제안하며 기존 관계를 자동 승격하지 않는다. 근거는 통합 설계 7.3절 776~789행, 8.4절 936~942행이다.

### 시나리오 4: 새 관계 종류와 실제 관계 기록

역할 입력의 템플릿에 `formally_reduces_to`가 있지만 A→B 관계 기록은 없다. 독자는 템플릿 설치만으로 관계가 존재하거나 착수 조건이 참이라고 판정하지 않아야 한다. 실제 환원의 변환·해답 복원·범위·보존 성질을 형식 결과와 동일성 판정으로 입증하고, 정확한 양끝·근거를 가진 관계를 저작해야 한다. 새 사용자 정의 종류라면 종류 정의를 같은 후보 트리에서 먼저 검증한다. 근거는 통합 설계 7.3.2절 817~831행이다.

### 시나리오 5: 후보 목차와 최종 선택

최종 선택 입력에 ready 후보 3개와 K 목차가 있고, 한 후보의 상세 원문을 읽지 못했다. 독자는 후보 목차 전건을 각각 선택·미선택·판정 불가로 처분하고, 읽기 실패를 빈 결과나 후보 부재로 바꾸지 않아야 한다. 추가 조회로 찾은 목차 밖 작업을 즉시 배정하지 않고 다음 준비·선택 입력에 넣도록 요청한다. K 목차의 요약은 인증 해설 일부이며 K 전체의 추가 주장이나 목표 해결 판정이 아니다. 근거는 통합 설계 8.5절 946~972행과 9.2절 1001~1018행이다.

### 시나리오 6: 상태 이름의 충돌

CLI 화면에 인스턴스 `ready`, 과제 `ready`, 활동 `active`, 실행 `running`이 보인다. 독자는 보편 계약에서 인스턴스 운전 상태가 `active`이고 과제의 `ready`는 현재 배정 후보가 된 구현 단계이며, 활동과 실행은 별도 단위라고 설명할 수 있어야 한다. 실행이 `ended`여도 활동·과제·목표가 끝난 것은 아니다. 이 대응을 문서만으로 말할 수 없다면 GLOSSARY의 구현 사상이 불충분하다.

### 시나리오 7: 검토 이의와 최종 판정

초기 검토자 하나가 양화 순서 불일치를 제기했고 다른 초기 검토자는 match다. 원 검토자가 답변한 뒤 세 쟁점 판정자가 두 명 rejected, 한 명 unresolved를 냈고 마지막 회차다. 독자는 초기 mismatch를 최종 확정 결함으로 승격하지 않고, 마지막 회차의 분열·unresolved에 따라 활동 결과를 unresolved로 남겨야 한다. 이의 주장·좌표·논증·반박은 보존한다. 검토 자리의 자기 메시지와 이번 단계의 동료 결과 비노출도 구별해야 한다. 근거는 통합 설계 11.4.1절 1271~1281행과 11.5절 1283~1305행이다.

### 시나리오 8: 판정과 사용 효력

동일성 판정의 값은 match지만 그 판정 사용 효력이 suspended이고, 형식 결과의 formal_use는 active다. 독자는 Lean 문면의 형식 사용과 해당 해설 연결을 새 인증·목표 감사에 쓰는 일을 구별해야 한다. 판정 효력 active는 판정값 match라는 뜻도 아니다. 재심사는 원 판정의 정확성과 현재 전제를 별도로 확인한다. 근거는 통합 설계 11.1절 1135행과 11.8절 1325~1347행이다.

### 시나리오 9: 체크포인트와 정지

연구 수행 중 정지 요청이 오고 이미 계산 결과와 사용한 정리, 실패한 접근이 있다. 독자는 체크포인트에 현재 주장·근거·적용 범위·남은 질문·다음 행동을 남기되 새 문헌 조회나 실험을 시작하지 않는다. 종료 장벽이 성립해도 원격 사용량 정산과 과제 완료는 별도다. 이 시나리오는 체크포인트, 정지 직전 기록, 종료 장벽, 산출 묶음의 관계를 이해했는지 본다.

### 시나리오 10: 외부 행동과 허가

학술 검증 과제가 원고 제출을 요구하지만 현재 허가는 자료 준비만 허용한다. 독자는 원고를 산출 묶음에 준비할 수 있으나 외부 전송을 실행했다고 주장하지 않고, 정확한 행동·대상·효과에 대한 허가와 외부 행동 원장을 요구해야 한다. HTTP 응답 수신, HTTP 성공, 학술 요구 완료, 수학적 해결을 각각 구별해야 한다.

### 시나리오 11: 원문 없는 역할 입력

루트 `CONTEXT.md` 없이 현재 런타임과 동일하게 SKILL·GLOSSARY·후보 준비 계약만 준다. “기존 `supports` 관계와 한 F의 `partial_result`를 재사용해 새 조사 계약을 제안하라”고 요청한다. 독자가 F·관계·확인 범위·정보 상태·K와의 차이, 조사 결과가 돌아갈 다음 소유자를 문서만으로 설명하지 못하면 공통 정의 전달이 실패한 것이다. 현재 문서 묶음은 이 검사에서 실패한다.

### 시나리오 12: 같은 뜻의 반복 사용

문서 전건에서 `형식 정본(K)`, `외부 행동`, `검토 자리`, `연구 맥락`, `배정 후보`, `지식 재사용`을 검색한다. 같은 개념이 각각 `검증된 수학 지식`, `외부 작업`, `검토 주기`, 단독 `맥락`, `ready 후보`, `재사용 근거`로 독립 정의되면 실패다. 별칭이 구현 필드 때문에 필요하면 첫 정의가 정본 이름·범위·대응을 밝히고 이후에는 같은 낱말을 반복 사용해야 한다.

## 재작성의 우선순위와 통과 기준

1. 먼저 GLOSSARY의 의미 변경을 고친다. 루트 정본의 이름과 경계를 그대로 회수하고, CLI 상태·필드는 보편 개념과 다른 구현 투영으로 명시한다.
2. 모든 역할이 실제로 만나는 공통 개념을 GLOSSARY 또는 필수 긴 정의 참조로 전달한다. 특히 온톨로지·시맨틱 레이어·지식 재사용과 준비·계획·인계 가족을 우선한다.
3. SKILL에 전체 연구 순환과 역할 간 직접 후속을 복원한다. 목적과 흐름은 다른 파일이나 코드 프롬프트에 중복 정의하지 않는다.
4. 역할 계약은 공통 용어를 재사용해 입력·판단·산출·실패·다음 소유자를 구체화한다. 후보 준비, 연구 계획, 연구 수행, 작업 계약 검토의 공백이 먼저다.
5. `contracts.py`의 의미-bearing 영문 프롬프트와 확장 파일 지시를 문서 소유 구조와 대조한다. 문서와 코드 중 한쪽만 바꿔 두 정본을 남기지 않는다.
6. 위 12개 시나리오를 새 문서 묶음만으로 판정하고, 각 답이 원문 좌표·실제 출력 필드·소비 코드와 일치하는지 확인한다.

통과는 용어 수나 문서 길이로 판정하지 않는다. 한 개념은 한 정본 이름과 한 의미를 가지며, GLOSSARY의 구현 투영이 루트 정의를 바꾸지 않고, SKILL이 전체 흐름을 설명하고, 각 역할이 자기 입력만으로 정확한 판단과 다음 인계를 선택하며, 실제 코드에 없는 필드·상태·기능을 이미 제공한다고 쓰지 않을 때 통과다.
