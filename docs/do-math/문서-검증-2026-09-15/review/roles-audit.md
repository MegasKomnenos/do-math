# do-math 역할 계약 의미 전달 감사

## 판정

완료. `.claude/skills/do-math/계약/`의 역할 계약 10개를 모두 읽고, 각 계약의 입력, 판단, 산출, 실패와 후속이 상위 원문의 의미와 이유를 실제 문면으로 전달하는지 대조했다. 지적은 지정된 원문에서 입증되는 경우에만 기록했다. 문제가 없는 내용도 계약별로 통과 항목에 남겼다.

이 감사는 정본의 수정안을 확정하지 않는다. 특히 공통 개념의 정의 위치와 정의 방식은 `docs/do-math/통합-설계.md` 16.5절이 정하는 현재 소유 관계를 전제로 했다. 역할 계약을 같은 짧은 틀에 맞추는 것도 전제로 삼지 않았다. 각 역할의 판단과 후속을 정확히 수행하는 데 필요한 의미가 문면에 있는지를 기준으로 삼았다.

## 실제 읽은 범위

- 상위 원문: `docs/do-math/통합-설계.md` 3.2절(293–337행), 5절(427–576행), 6.6절(679–696행), 7.3.1절(797–815행), 8.4–8.5절(934–972행), 9절(975–1074행), 10.5절(1120–1124행), 11절(1127–1347행), 12절(1350–1472행), 13절(1475–1611행), 16.5절(1865–1888행)
- 보편 정의: 루트 `CONTEXT.md` 1–499행 전문
- 현재 연결 문서: `.claude/skills/do-math/SKILL.md` 1–58행, `GLOSSARY.md` 1–23행, `references/CLI-실행-계약.md` 전문
- 역할 계약: `후보-준비.md`, `연구-계획.md`, `연구-수행.md`, `작업-계약-검토.md`, `동일성-검토.md`, `목표-감사.md`, `보충-조사.md`, `운영-점검.md`, `의도-해석.md`, `유지보수.md` 전문
- 작문·검토 준거: `.claude/skills/write-for-reader/SKILL.md`, `references/명료한_산문.md`, `references/AI_프롬프트.md`, `references/절차문.md` 전문과 `.claude/skills/critique-text/SKILL.md` 전문

구현 코드는 읽지 않았고, 코드 동작이나 감사자의 수학 지식으로 문서의 빠진 뜻을 보충하지 않았다. 현재 CLI에서 실제로 쓰는 필드와 상태의 의미는 위 세 연결 문서에 명시된 범위에서만 참조했다.

## 판정 방법

통합 설계 16.5절 1867행은 역할 계약이 각 역할의 입력·판단·산출·실패 행동을 소유한다고 정한다. 1873–1884행은 역할별로 반드시 전달해야 할 판단 내용을 다시 열거한다. 따라서 다음 네 질문을 계약마다 적용했다.

1. 역할은 무엇을 실제 입력으로 받고, 어떤 판본·범위·효력을 확인해야 하는가?
2. 역할은 무엇을 어떤 근거로 판단하며, 그 판단이 왜 다른 역할과 구별되는가?
3. 산출은 어떤 의미를 가지며, 어느 다음 소유자가 무엇을 하기 위해 받는가?
4. 판단을 끝내지 못하거나 실행이 실패했을 때 무엇을 보존하고, 어느 상태와 다음 소유자에게 넘기는가?

`SKILL.md` 22–29행이 공통 문서와 역할 계약의 읽기 순서를 정하고, 31–43행이 공통 산출·정지·입력 부족의 기본 행동을 제공한다는 점은 각 판정에 반영했다. 그러나 공통 규칙은 역할마다 다른 판단 대상·후속·실패 의미까지 대신하지 않는다. 반대로 역할 계약에 같은 공통 규칙을 반복하지 않았다는 이유만으로 지적하지 않았다.

## 전체 계약 집합에서 먼저 고칠 문제

### C-01. 통합 설계와 현재 CLI 문서가 서로 다른 상태 어휘를 쓰지만, 역할 계약은 어느 어휘가 어느 층의 것인지 설명하지 않는다

- 현재 문면: `GLOSSARY.md` 14–17행과 `CLI-실행-계약.md` 13–17행은 현재 CLI의 인스턴스·과제·활동·실행 상태를 정의한다. 예를 들어 과제에는 `ready`, `needs_revision`, `performing`, `assessing`이 있고 활동에는 `active`, `finished`, `unresolved`가 있다.
- 상위 원문: 통합 설계 3.2.1절 322–334행은 활동 상태를 `ready`, `working`, `waiting`, `finished`로 정하고, 5.3절 477–493행은 과제 상태를 `planned`, `active`, `waiting`, `completed`, `closed`로 정한다. `CONTEXT.md` 41–42행과 219–220행도 이 뜻을 보편 정의로 설명한다. 통합 설계 16.5절 1869행은 GLOSSARY와 역할 계약이 이 정의를 소비하도록 정한다.
- 문제: 현재 CLI 계약이 특정 구현 계약으로 다른 상태 표현을 채택했을 수는 있다. 그러나 역할 계약들은 `ready`, `assessing`, `waiting`, `finished`, `unresolved`를 사용하면서 이 값이 보편 개념의 어느 상태나 결과에 대응하는지 설명하지 않는다. 특히 `research_plan`은 `ready`를 과제 상태처럼 읽고, 통합 설계는 `ready`를 기계 계산한 배정 후보 결과로 설명한다.
- 독자가 잘못 할 상황: 계획자가 `tasks[].state=ready`만 보고 발생 조건·계약 검토·현재성을 이미 모두 통과한 것으로 해석하거나, 활동의 `unresolved`를 아직 진행 중인 상태로 해석해 종료된 미해결 활동을 다시 열 수 있다.
- 보존해야 할 의미: 현재 CLI의 닫힌 값 자체를 숨기지 말고, 각 값이 보편 개념의 상태·판정·파생 보기 중 무엇을 표현하는지 밝혀야 한다. 과제 상태, 활동 상태, 실행 결과, 배정 후보 판정을 서로 대신하지 않는다는 뜻을 유지해야 한다.

### C-02. 공통 실패 규칙은 있으나 역할별 실패 뒤 다음 소유자가 대부분 빠져 있다

- 현재 문면: `SKILL.md` 43행은 필수 입력이 없거나 충분하지 않으면 실제 범위·확인 사실·미확인 이유·다음 소유자·대기 조건을 반환하도록 한다. 그러나 `목표-감사.md`와 `의도-해석.md`에는 실패 절이 없고, `유지보수.md`는 실패·미검사 범위를 남기라는 일반문만 둔다. 다른 짧은 계약들도 역할별 후속을 한두 문장으로 압축했다.
- 상위 원문: 통합 설계 3.2절 297–308행은 모든 역할의 결과와 직접 후속을 구별한다. 16.5절 1867행과 1886행은 역할 계약이 실패 행동과 실패 정보의 다음 소유자를 명시하도록 정한다.
- 문제: 공통 계약 덕분에 사실을 꾸미지 않는 행동은 알 수 있지만, 실패한 판단을 후보 준비·연구 계획·같은 검토 자리·사용자 결정·복구 판단 중 어디로 돌릴지는 역할마다 다르다. 이 차이가 문면에 없는 파일에서는 실행자가 일반 `unresolved`를 반환한 뒤 필요한 후속을 열지 않을 수 있다.
- 독자가 잘못 할 상황: 목표 감사가 필요한 K 원문을 읽지 못하고 `unresolved`만 반환한다. 다음 소유자가 연구 계획인지 입력 수리인지 알 수 없어 인스턴스가 대기 조건 없이 멈춘다.
- 보존해야 할 의미: 역할별로 실패 종류, 실제 완료 범위, 보존할 근거, 다음 소유자와 재개 조건을 연결해야 한다. 공통 실행 종료, 활동 종료, 과제 완료, 수학적 해결을 계속 구별해야 한다.

### C-03. 기계 필드 이름이 역할의 목적과 인과관계를 대신하는 곳이 많다

- 현재 문면: 여러 계약은 `criteria_results`, `academic_resolutions`, `formal_verifier`, `live_review`, `research_request_contract` 같은 필드를 곧바로 제시한다. 출력 스키마가 필드·자료형의 정본이라는 공통 규칙은 `SKILL.md` 35행과 동일성 계약 7행에 있다.
- 상위 원문: 통합 설계 16.5절 1867행은 스키마와 역할 계약의 소유 내용을 구별한다. `write-for-reader`의 `AI_프롬프트.md` 104–115행도 기계 형식과 사람이 판단할 의미를 구별한다.
- 문제: 필드명이 정확하더라도 그 값을 왜 만들고 어느 후속이 어떻게 소비하는지 설명하지 않으면 역할 계약의 판단 의미가 스키마에 묻힌다. 이 문제는 영어를 썼다는 사실이 아니라 필드가 책임 설명을 대신한다는 데 있다.
- 독자가 잘못 할 상황: 연구 계획자는 `academic_resolutions` 배열의 형식만 맞추고, 그 판정이 현재 해결 근거와 요구 판본에 결박돼야 한다는 이유를 놓친다.
- 보존해야 할 의미: 스키마가 소유하는 닫힌 필드·자료형은 그대로 참조하되, 역할 계약은 필드가 표현하는 판단, 근거, 효과와 다음 소비자를 설명해야 한다.

## 계약별 감사

### 1. 후보 준비 — `.claude/skills/do-math/계약/후보-준비.md`

#### 통과한 의미

- 3–5행은 후보 준비가 현재 K·F·근거·관계·맥락에서 질문과 정련 가능한 작업 제안을 만든다고 밝혀 역할의 중심 대상을 전달한다.
- 5행과 9행은 모든 F를 계약으로 만들지 않고, 이미 완결된 계약을 다시 저작하지 않는다고 한다. 이는 통합 설계 5.1절 431–435행과 맞는다.
- 11행은 해결 뒤 학술 요구를 현재 증명 작업의 선행조건으로 넣지 않는다. 통합 설계 9.4절 1052–1070행과 현재 CLI 계약의 목표·학술 분리를 보존한다.
- 15행은 새 과제와 같은 의무의 개정, 미완료 기준 보존, 의무 이전·철회를 구별하고 승인·선택·예약을 직접 만들지 않는다. 5.5절 519–534행과 9.2.1절 1022–1034행의 역할 분리는 통과한다.

#### P-01 [누락] 지식·관계의 재사용 판단과 생성 근거가 이름만 남아 있다

- 현재 좌표: 5–9행, 15행
- 원문 좌표: 통합 설계 8.4절 936–944행, 9.2.1절 1024–1026행, 16.5절 1871·1875행; `CONTEXT.md` 209–210행과 251–252행
- 문제: 현재 문면은 K·F·근거·관계를 입력으로 언급하고 `재사용 근거`를 산출 필드로 요구하지만, 현재 질문의 대상·가정·필요한 결론을 기존 지식의 내용·확인 범위·근거·효력에 대조하는 판단을 설명하지 않는다. 실제로 적용한 조건, 남은 차이, 새 질문을 도출한 이유도 산출에 명시하지 않는다.
- 독자가 잘못 할 상황: 관계 이웃에서 비슷한 K를 찾은 뒤 그 관계 경로만으로 새 작업의 전제를 충족한다고 적거나, 기존 결과가 다루지 않은 범위를 밝히지 않은 채 `재사용 가능`으로 계약을 만든다.
- 보존해야 할 의미: 검색 결과와 관계 경로는 탐색의 단서이고 적용의 증명이 아니다. 실제 사용한 판본·내용·조건·효력과 새 질문에 남은 차이를 생성 근거에 남겨야 한다.

#### P-02 [누락] 운영 예산의 정련과 작업 예산의 깊은 조사 사이 인계 이유가 충분하지 않다

- 현재 좌표: 7–9행
- 원문 좌표: 통합 설계 3.2절 310–312행, 5.1절 433–437행, 16.5절 1875행; `CONTEXT.md` 251–252행, 309–314행
- 문제: 9행은 새 입증이 필요하면 `research_work`를 제안한다고 하지만, 깊은 문헌 재해석·장기 조사·새 수학 내용 입증이 왜 후보 준비의 운영 예산 판단을 넘는지 설명하지 않는다. 선행 조사 결과를 받은 뒤 후보 준비가 계약을 다시 정련하고 별도 연구 계획이 선택한다는 인계도 빠져 있다.
- 독자가 잘못 할 상황: 후보 준비가 장기 문헌 조사까지 자기 실행에서 계속하거나, 선행 조사 과제가 끝났다는 이유로 원 후보 계약이 자동 완성·배정됐다고 처리한다.
- 보존해야 할 의미: 후보 준비는 확보된 자료로 정련한다. 깊은 재해석과 새 입증은 작업 예산의 별도 과제로 제안하고, 결과가 돌아오면 후보 준비가 계약을 저작한 뒤 계약 검토와 별도 선택을 거친다.

#### P-03 [누락] 계획 입력과 준비 이력을 읽어야 하는 이유와 범위가 없다

- 현재 좌표: 3–9행
- 원문 좌표: 통합 설계 8.5절 948–972행, 9.2.1절 1024–1030행, 16.5절 1875행; `CONTEXT.md` 263–268행
- 문제: 후보 목차, 진행 중 작업, K 목차, 최근 선택의 기대와 실제 결과, 이전 준비 회차의 미편입·검사 실패를 기본 입력으로 삼는다는 내용이 없다. 이전 실패를 제외하지 않고 같은 자료·같은 접근을 새 후보처럼 반복하지 않아야 하는 이유도 전달되지 않는다.
- 독자가 잘못 할 상황: 직전 준비 회차에서 같은 계약이 참조 오류로 반려됐는데 그 기록을 읽지 않고 같은 제안을 새 ID로 다시 제출한다.
- 보존해야 할 의미: 제공된 계획 입력의 실제 범위를 읽고, 이전 기대와 결과·미편입 사유를 새 정련 판단에 반영해야 한다. 목차는 상세 원문 전건 열람을 뜻하지 않으므로 필요한 원자료는 정확한 참조로 회수해야 한다.

#### P-04 [누락] 탐색·집중 활용·구조적 렌즈와 정기 탐색·고갈·반복 문턱이 연결되지 않는다

- 현재 좌표: 3–9행
- 원문 좌표: 통합 설계 5.1절 437–439행, 9.1절 977–999행, 9.2절 1003–1018행, 13.1.1절 1519–1535행, 16.5절 1875행; `CONTEXT.md` 115–120행, 251–280행

- 보존해야 할 의미: 구조 수리는 같은 할당의 원 출력을 근거로 하고, 의미 변경은 같은 자리의 새 반환이다. 실행 미완료는 개별 의미 판정으로 꾸미지 않으며 빠진 자리 복구 또는 활동의 미완료 범위로 남긴다.

### 6. 목표 감사 — `.claude/skills/do-math/계약/목표-감사.md`

#### 통과한 의미

#### GA-01 [누락] 추가 감사 계약의 입력·판정 어휘·효과를 실제로 판단하는 방법이 없다

- 보존해야 할 의미: 감사 실행은 해답 저작 계보와 독립하고, 현재 목표와 실제 사용할 K·해설·판정·감사 계약의 정확한 판본과 효력을 대조해야 한다.

#### GA-03 [산출·후속 누락] 부분 결과와 부정·미해결 판정의 다음 연구 처분이 없다

- 보존해야 할 의미: 정확한 부분 결과는 K로 보존될 수 있다. 감사는 충족되지 않은 헌장 항목, 남은 가정·제외 범위, 미감사·근거 정지·범위 변경을 구별해 목표 상태와 다음 계획에 반환해야 한다.

#### GA-04 [실패] 필수 원문 미열람과 판단 미확정의 처분이 없다

- 현재 좌표: 실패 절 없음; 11행의 `unresolved`만 존재

- 독자가 잘못 할 상황: 최종 판정 원문을 회수하지 못하고 초기 요약만 읽은 뒤 `unresolved`를 내며, 원문 회수 실패와 수학적 미해결을 같은 이유로 기록한다.
- 보존해야 할 의미: 미열람·읽기 실패·판단 미확정을 구별하고, 실제 완료 범위와 필요한 원자료·다음 소유자를 남겨야 한다.

- 독자가 잘못 할 상황: 유용한 조사 결과가 없었다는 이유만으로 `no_result`를 과제 실패로 처리하거나, 반대로 필수 원자료를 읽지 못한 실행을 계약상 조사 완료로 처리한다.
- 보존해야 할 의미: 산출의 긍정성, 계약 범위 수행, 실행 완결을 구별하고 각 결과에 실제 범위·남은 의무·대기 조건·다음 소유자를 붙여야 한다.

### 8. 운영 점검 — `.claude/skills/do-math/계약/운영-점검.md`

#### 통과한 의미

#### OR-01 [입력 누락] 점검자가 실제로 읽어야 할 원자료 집합이 없다

- 현재 좌표: 3–9행

- 문제: `action`과 `보존된 진단 근거`만 언급한다. 작업 계약·계약 검토·진전 기준, 실제 자료와 코드의 반복·종료 조건, 로그·체크포인트·프로세스·허가·도구 및 외부 서비스 상태·이전 점검을 읽는 책임이 없다.

#### OR-02 [구조·오해 위험] `live_review`와 실패 진단의 두 갈래가 상위 처분 체계를 충분히 설명하지 않는다

- 현재 좌표: 11–15행

- 문제: 현재 계약은 실행 중이면 `continue`·`checkpoint`·`revise`·`wait`·`stop`, 실패 뒤에는 `retry`·`revise`·`wait`·`stop`을 사용한다. 상위 원문은 계속, 입력·환경 수리, 체크포인트 재개, 처음부터 재시도, 과제 변경·종결, 사용자 결정 요청을 근거별로 구별한다. 현재 값이 상위 처분의 어떤 경우를 표현하고 무엇을 할 권한이 있는지 설명이 없다.

- 보존해야 할 의미: 점검 발동은 검토 의무이지 자동 중단이 아니다. 처분은 바꿀 대상·재개 범위·권한·다음 소유자와 함께 구별되어야 한다.

#### OR-03 [중대한 누락] 결정론 복구와 별도 의미 판단의 경계가 없다

- 현재 좌표: 15행의 한정 재시도 설명
- 원문 좌표: 통합 설계 12.4절 1451–1468행, 16.5절 1882행; `CONTEXT.md` 371–372행, 379–380행
- 문제: 이전 실행의 종료 장벽, 입력·허가·프로필, 외부 행동과 재생 조건을 결정론 검사로 전건 확인할 수 있으면 실행기가 적용하고, 재개 범위·인계 충분성·재생 안전성의 의미 판단이 남으면 최초 진단과 다른 `checking_recovery` 실행이 맡는다는 경계가 없다.

- 보존해야 할 의미: 기계로 닫히는 전제와 독립 의미 판단을 구별한다. 복구 판단은 작업 선택을 대신하지 않으며 research_work 재개는 계약 검토·선택·착수 요건을 다시 충족해야 한다.

#### OR-04 [누락] 재생 안전성과 적용 직전 현재성 검사가 빠져 있다

- 현재 좌표: 13–15행

#### OR-05 [실패·후속] 점검 자체의 미완료와 권한 밖 처분의 다음 소유자가 없다

- 문제: 운영 예산이 없거나 점검이 실패해도 상한이 유지된다는 말은 있지만, 실제 미검사 범위와 다음 점검·입력 수리·계약 개정·사용자 결정의 소유자를 반환하는 법이 없다.

### 9. 의도 해석 — `.claude/skills/do-math/계약/의도-해석.md`

#### 통과한 의미

#### II-01 [누락] 자료 수입과 지식 저작의 경계가 없다

- 현재 좌표: 문서 전반
- 원문 좌표: 통합 설계 13.1절 1481–1483행, 16.5절 1883행; `CONTEXT.md` 181–210행, 385–394행
- 문제: 외부 원문을 보존하는 일과 그 내용을 F·자료·근거·관계·연구 기억으로 저작하는 일을 구별하지 않는다. 외부 분류·요약·관계가 출처의 주장일 뿐 내부 수학 관계의 근거·판정을 대신하지 않는다는 뜻도 없다.

- 보존해야 할 의미: 원문 보존, 사용자 규범의 의미 수입, 연구 지식 저작은 서로 다른 책임이다. 자료 수입 자체가 새 의도 승인 절차나 수학적 권위를 만들지 않는다.

#### II-02 [판단·산출 누락] 의미 단위별 정확한 좌표·소유자 하나·영향 집합과 질문 계약이 약하다

- 독자가 잘못 할 상황: 같은 사용자 문장을 헌장과 정책에 각각 복제하거나, 무엇이 바뀌는지 설명하지 않은 `진행할까요?` 질문을 만든다.
- 보존해야 할 의미: 한 의미 단위의 현행 소유자는 하나이고 다른 기록은 정확한 참조로 연결한다. 질문은 사용자가 결과를 바꿀 결정을 내릴 수 있을 만큼 선택과 효과를 보여야 하며 선택지 밖 답도 허용한다.

#### II-03 [정합성 문제] 대조 결과 어휘가 보편 정의와 다르다

- 현재 좌표: 11행은 `match`, `mismatch`, `unresolved`

- 문제: 현재 계약은 동일성 검토의 판정 어휘와 같은 `match`·`mismatch`를 사용한다. 현재 CLI 스키마의 의도된 값이라면 보편 결과와 대응을 밝혀야 하지만 그런 설명이 없다.
- 독자가 잘못 할 상황: `match`를 사용자 승인으로 읽거나, `mismatch`를 해석문 수정 요구가 아니라 사용자 원문과 내부 기록 사이의 사실 충돌로만 읽는다.
- 보존해야 할 의미: 의미 대조의 통과는 사용자 허가가 아니다. 현재 CLI 값이 승인·수정 필요·미해결 중 무엇에 대응하며 어떤 후속 효과를 갖는지 분명히 해야 한다.

#### II-04 [독립성 누락] 일반 의미 수입과 사례 기반 위임 적용의 두 대조 절차가 구별되지 않는다

- 현재 좌표: 9–13행
- 원문 좌표: 통합 설계 13.1절 1494–1500행, 13.2절 1541–1550행, 16.5절 1883행; `CONTEXT.md` 349–350행, 393–394행
- 문제: `check` 실행은 항상 `interpretation_to_check`를 본다고 한다. 일반 수입 대조에서는 해석 묶음을 검토해야 하지만, 사례 기반 위임 적용의 checking 실행은 첫 해석 실행의 이번 판정문을 보지 않고 같은 현재 사례·제안 효과·허가·원 결정·원자료에서 독립 판단을 봉인해야 한다. 두 용례가 한 문면에 섞여 있다.
- 독자가 잘못 할 상황: 사례 기반 위임의 두 번째 실행이 첫 실행의 `범위 안 적용` 결론을 보고 그 결론에 맞춰 대조해 독립성을 잃는다.
- 보존해야 할 의미: 일반 의미 수입의 묶음 검토와 사례 기반 위임의 독립 적용 대조를 분기별 입력·산출로 구별해야 한다. 후자는 두 실행이 모두 범위 안 적용을 지지하고 현재성이 있을 때만 효과가 생긴다.

#### II-05 [실패] 읽지 못한 범위와 다음 소유자의 반환이 없다

- 현재 좌표: 실패 절 없음

- 문제: `unresolved`는 있으나 원문 일부 미열람, 의미 미확정, 사용자 결정 필요, 내부 소유자 불명확을 구별하지 않는다.
- 독자가 잘못 할 상황: 사용자만 결정할 빈 값을 단순 `unresolved`로 남기고 결정 질문을 열지 않거나, 읽기 실패를 사용자의 모호한 의도로 오해한다.
- 보존해야 할 의미: 확인 가능한 사실은 직접 확인하고, 미열람과 의미 미확정을 구별하며, 사용자 결정이 필요한 경우 질문·영향·대기 조건과 다음 소유자를 남겨야 한다.

### 10. 유지보수 — `.claude/skills/do-math/계약/유지보수.md`

#### 통과한 의미

- 5행은 유지보수를 지정된 초기화·검사·편입·전환·변환·복구 절차에 종속시킨다.

#### MT-01 [구조·중대한 누락] 한 문단이 여러 절차의 입력·판단·산출·실패를 대신한다

- 현재 좌표: 7–9행
- 원문 좌표: 통합 설계 16.5절 1867·1884·1886행; `CONTEXT.md` 285–298행
- 문제: 유지보수는 여러 절차가 요청하는 기계 작업과 AI 판단의 공통 진입 역할인데, 현재 계약에는 이번 호출 절차와 단계, 정확한 대상·입력·권한, 수행 분기, 산출과 성공 조건, 실패 종류, 다음 소비자를 확인하는 순서가 없다. `대조한다`는 한 동사가 모든 판단을 압축한다.
- 독자가 잘못 할 상황: 신뢰 환경 전환용 유지보수 실행이 복구 절차의 입력을 사용하거나, 검사 결과를 어느 호출 절차에 반환해야 하는지 모른 채 일반 성공으로 끝낸다.
- 보존해야 할 의미: 각 배정은 호출한 절차의 정확한 단계·대상·권한·입력·출력·성공 조건과 다음 단계를 따라야 한다. 공통 진입 계약은 절차별 차이를 지우지 않아야 한다.

#### MT-02 [누락] 기계 작업과 AI 판단의 권한·예산·판정 경계가 충분하지 않다

- 현재 좌표: 9행
- 원문 좌표: 통합 설계 3.2절 308행, 12.4절 1455–1467행, 16.5절 1884행; `CONTEXT.md` 285–298행, 309–314행
- 문제: 두 종류를 구별한다고만 한다. 기계 작업은 결정론 검사와 호스트 자원을 사용하고 AI 예산이 없으며, AI 판단은 운영 예산에서 기계로 닫히지 않는 의미만 판단한다는 이유와 적용 경계가 없다.
- 독자가 잘못 할 상황: 결정론 검사를 AI 승인으로 대신하거나, AI가 반환한 `가능` 판단만으로 상태를 바꾼다.
- 보존해야 할 의미: 기계 검사와 AI 의미 판단의 증거 범위를 구별하고, 실제 적용은 호출 절차의 수신 검사와 현재성 확인을 거쳐야 한다.

#### MT-03 [오해 위험] `maintenance`라는 활동 이름이 정지 중 권한을 만들지 않는다는 설명이 부족하다

- 현재 좌표: 9행
- 원문 좌표: 통합 설계 13.5.1절 1603–1611행, 16.5절 1884행; `CONTEXT.md` 285–286행, 477–478행
- 문제: 승인된 절차를 확인한다고는 하지만, 활동 이름이나 소유 관계만으로 정지 중 실행 허가가 생기지 않고 각 하위 요청까지 승인 범위에 속해야 한다는 규칙이 없다. 유지보수 성공이 일반 연구 재개를 뜻하지 않는다는 후속도 빠져 있다.
- 독자가 잘못 할 상황: paused 인스턴스에서 maintenance 활동이 있다는 이유만으로 일반 연구 수행이나 추가 도구 실행을 열거나, 변환 성공 뒤 자동으로 active로 바꾼다.
- 보존해야 할 의미: 정지 중에는 정확히 승인된 변환·복구의 대상·범위·허가에 속한 실행만 허용한다. 유지보수 완료와 일반 연구 재개는 별도 판정이다.

#### MT-04 [실패·후속 누락] 새 정지·허가 철회 뒤 현재 실행과 남은 작업을 어떻게 처리할지 없다

- 현재 좌표: 9행
- 원문 좌표: 통합 설계 13.5.1절 1607–1611행, 16.5절 1884·1886행
- 문제: 후속 배정을 열지 않는다고만 한다. 미종료 실행에 공통 종료를 적용하고 남은 작업·재개 조건을 소유 활동에 보존하며, 이전 허가만으로 다시 시작하지 않는다는 행동이 없다.
- 독자가 잘못 할 상황: 새 배정은 막았지만 이미 running인 변환을 계속 두거나, 허가가 다시 생겼는지 확인하지 않고 중단 지점에서 자동 재개한다.
- 보존해야 할 의미: 권한 변화는 현재 실행에도 적용하고, 실제 완료 범위·남은 작업·재개 조건을 보존한다. 재개는 정지 원인의 해소와 현재 허가를 다시 확인한 새 실행이어야 한다.

#### MT-05 [실패] 결과 상태와 미검사 범위의 다음 소비자가 없다

- 현재 좌표: 9행
- 원문 좌표: 통합 설계 3.2절 308행, 16.5절 1884·1886행
- 문제: 기계 작업이 입력·출력·실패·미검사 범위를 남긴다고 하지만 어떤 결과가 성공·부분 완료·실패이며, 호출 절차가 무엇을 검사한 뒤 다음 단계로 가는지 설명하지 않는다.
- 독자가 잘못 할 상황: 일부 파일만 검사한 변환을 전체 성공으로 처리하거나, 미검사 범위가 있는데도 신뢰 환경 전환의 다음 단계를 연다.
- 보존해야 할 의미: 실제 검사 범위와 미검사·실패를 구별하고, 호출 절차의 완료 조건을 충족한 경우에만 다음 단계로 넘겨야 한다.

## 보존 가치가 큰 현재 문면

전면 개정에서 다음 내용은 짧다는 이유로 지우지 않아야 한다.

- `후보-준비.md`의 모든 F를 계약화하지 않는 원칙, 완결 계약의 재저작 금지, 학술 요구의 순환 선행조건 금지, 미완료 의무의 판본 간 보존
- `연구-계획.md`의 수행 전 완료 판정 금지, 파일 원문 직접 확인, 결과 없음·실패한 방법도 계약 범위를 실제로 끝냈으면 완료 가능하다는 구별, 목표 감사와 계획 권한의 분리
- `연구-수행.md`의 실제 범위·가정·장애물·부분 결과 구별, 중앙 형식 검사의 시점, 외부 행동 허가와 외부 원장의 분리
- `작업-계약-검토.md`의 저작자와 다른 실행, 형식 도구 설정과 성공의 구별, 계약 직접 수정·최종 선택 금지
- `동일성-검토.md`의 전건 검토, 대화 복원과 같은 단계 결과 비노출, 이의와 제안 전체 판단의 구별, 고정 질문 보충 조사, 새 판본 전면 재검토, 사용 효력과 판정값의 구별
- `목표-감사.md`의 초기 이의와 최종 판정 구별, 예정 문장과 후속 검사 시점 대조, K 없는 수학 목표 해결 금지, 수학적 해결과 학술 요구 완료의 분리
- `보충-조사.md`의 실제 원자료 파일 열람, 질문 범위 고정, `answered`와 `unresolved`의 엄격한 경계, 출처 참조의 실재 확인, 같은 검토 자리로의 반환과 독립성
- `운영-점검.md`의 시간·도구 수·무응답만으로 진전 부재를 판정하지 않는 규칙, 재시도의 원인·목적·재개 조건 기록
- `의도-해석.md`의 해석과 별도 대조, 원문에 없는 허가 확장 금지, 정보 제공과 실행 승인 구별
- `유지보수.md`의 지정 절차 종속, 수학 의미·사용자 허가 창작 금지, 최신 원장·원자료·미정산 보존

## 개정 시 전체 문서를 다시 대조할 지점

1. 열 계약 모두에서 입력 → 판단 → 산출 → 실패·후속의 인과관계가 이어지는지 본다. 같은 제목 수나 문단 수를 맞출 필요는 없다.
2. 통합 설계의 보편 역할 단계와 현재 CLI의 실제 필드·상태가 다르면 대응을 명시한다. 한 문서 안에서 둘을 같은 값처럼 사용하지 않는다.
3. GLOSSARY가 정의한 공통 개념을 역할 파일마다 다시 정의하지 않는다. 반대로 역할별 판단 책임을 필드 이름이나 GLOSSARY 포인터만으로 대체하지 않는다.
4. 각 역할의 실패에서 입력 부재, 미열람, 실행 미완료, 판단 미확정, 계약상 부정 결과를 구별한다. 실제 범위·다음 소유자·재개 조건을 남긴다.
5. 후보 준비·연구 계획·연구 수행·보충 조사는 모두 8.4절의 지식 재사용을 자기 판단과 산출에 연결한다. 같은 문구를 복사하기보다 각 역할이 재사용 결과로 무엇을 결정하는지 설명한다.
6. 운영 점검과 유지보수는 처분을 제안하는 AI, 결정론 검사를 수행하는 기계, 현재성을 확인하고 적용하는 실행기의 권한을 섞지 않는다.
7. 동일성 검토는 현재 상세 문면을 보존하면서 범위 계획, stage/phase 대응, 전문 적재 불가, 실행 미완료의 경로를 복원한다.
8. 독자가 파일 하나와 공통 읽기 순서로 역할을 수행할 수 있는지 다시 읽는다. 구현 코드나 과거 실행 지식이 있어야만 뜻이 채워지는 문장은 미완료로 본다.
