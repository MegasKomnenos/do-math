# do-math 수리안의 목적·단순성·영향 범위 재검토

대상: [전체 수리안](정적-검토-수리안-2026-09-23.md). 날짜: 2026-09-23.

방법: `simplify`의 네 질문과 현재 소스의 호출·반환·저장·복구 경계를 대조했다. 검토 대상은 실제 코드에 적용하기 전의 계획이다. do-math·테스트·모델·Lean·예약 작업은 실행하지 않았으며, 수리안과 이 기록만 변경했다.

**판정**

재검토 전 계획은 그대로 구현하기에 충분하지 않았다. 정상 입력/반환에서는 타당해 보이는 수정이 저장 후 중단과 고정 프로필의 자원 판본에서 잘못 작동할 수 있었다. 기본 방향을 유지할 항목은 1·2·3·8번이고, 4·7번은 기능 경계를 보완했다. 5번은 불필요한 전체 이력 재검사를 줄였으며 6번은 호출이 없어지는 작은 도우미까지 정리했다.

수정된 계획은 아래의 구체적인 반례와 소비 경로를 포함한다. 이 판정은 정적 계약 검토 결과이며 회귀 테스트 통과나 실환경 동작 검증을 뜻하지 않는다. 구현 완료의 기준은 수리안의 실제 입력·편입·저장·복구 사례를 통과하는 것이다.

**simplify의 네 질문에 대한 답**

1. 하려는 일은 정상 근거의 참조·처분, 감사 결과 환류·이력 보존, 정확한 운전 상태와 불필요한 복사 제거다. 새 필드·상태·도우미의 개수가 목적이 아니다.
2. 가장 단순한 방법은 각 판단의 소유자가 하나가 되게 하는 것이다. 제공 과제는 기존 검사 입력으로, 전건 처분은 명시 모집단으로, 자원 허용/거부는 실제 예약기로, 이미 공개된 산출의 마무리는 기존 제출 재처리기로 처리한다.
3. 이전 계획의 일부는 그 원칙을 어겼다. scheduler가 자원 계산을 다시 만들고, 감사 중복 제거가 제출 마무리까지 맡으며, 현재 사용하지 않는 역사 판정을 매 순회 다시 판단했다. 해당 부분을 수정했다.
4. 정확성을 위해 필요한 추가 구조는 실패한 제약의 좌표와 이미 공개된 감사 생산자의 식별이다. 반면 별도 전체 과제 필드·새 감사 원장·전역 캐시·새 수명주기·대규모 성능 조합 검사는 현재 수리에 실익이 부족해 추가하지 않는다.

**확인한 결함과 반영한 수정**

|---|---|---|
| 감사 생산자와 중복 실행의 혼동 | GJ와 integration 영수증은 CAS로 저장됐지만 EX의 output_accepted가 저장되기 전 중단될 수 있다. ‘GJ가 있으면 queue/wait 삭제’는 원 생산자의 마무리 의무까지 없앤다 | GJ→EX→integration→봉인본을 결박하고 기존 publication 재처리로 같은 EX를 마무리. 원 result_ref 보존 |

주요 소스 근거는 다음과 같다.

- `engine._apply_submission_bundles`와 `integration.apply_bundles`: 도메인 변경·편입 영수증의 CAS가 실행 결과 정산보다 먼저 공개될 수 있다.
- `engine._receive_submission`, `_retry_submission_publications`, `_recover_disappeared`: 봉인본을 재소비하는 경로와 일반 실행기 소실 수집 경로가 다르다. 이미 편입된 감사의 result_ref를 checkpoint로 덮지 않도록 해야 한다.
- `governance_engine._apply_governance_goal_audit`: GJ는 role 없이 execution_id/basis/slot/required를 보존한다.
- `session_slots.acquire`: actual profile의 capacity_refs/usage_constraint_ids와 그 판본의 제약을 사용한다. 최신 role_profile_refs의 요약인 snapshot/usage_snapshot과 같은 계산이 아니다.
- `budget._check_concurrency/_check_host/_check_usage`: 실제 거부를 만드는 세 지점이다. 여기의 수식은 바꾸지 않고 좌표만 반환한다.
- `task_scope.designated_judgment`: 과거 감사가 실제 완료 의무의 증거로 쓰이는 경계다. 전체 이력 순회 대신 이 경계의 현재성 검사를 보강한다.
- `knowledge.plan_impact/apply_impact`, `engine._apply_bundle_candidate`: 철회는 단일 과제 도우미뿐 아니라 영향·후속 무효화·원자적 편입을 거친다. 이 경로를 생략한 테스트만으로 2번을 완료 처리하지 않는다.

이 표의 각 칸은 변경 여부뿐 아니라 유지해야 하는 계약도 포함한다. 검사와 저장이 이어진다는 이유로 권한·수학적 승인·로컬 종료를 대신했다고 보지 않는다.

**추가해야 하는 검증의 핵심 반례**

1. 정상 감사 응답을 저장한 직후, 실행 결과 정산 저장 직전에 중단한다. 재시작 후 같은 EX와 원 봉인본으로 마무리되고 추가 모델/GJ/환류 사건이 없어야 한다.
2. 위 원 생산자의 publication wait와 다른 EX의 중복 요청을 같이 둔다. 후자만 정리되고 전자의 마무리는 보존돼야 한다.
3. 한 활동에 중복 요청 외의 미해소 의무 또는 미정산 예약을 둔다. 중복 제거가 그 활동 전체의 완료로 번지면 안 된다.
4. 새 설정은 cumulative 11, action은 기존 cumulative 10 프로필, 이미 사용한 횟수는 10으로 둔다. 사전 진단과 실제 acquire가 같은 옛 제약의 소진을 보고해야 한다. 프로필을 몰래 교체해 통과시키지 않는다.
5. 공급자 재관찰 시각에 read-only admission_check를 실행한다. 원장의 probe_owner/예약/EX는 그대로이고 실제 acquire에서만 바뀌어야 한다.
6. B 철회와 B를 읽는 A를 함께 둔다. 명시 영향과 실제 영향, 독립 영향 검토, A의 현재성, 후속 배정까지 중앙 편입 경로로 확인한다.
7. 옛 satisfied GJ의 stored current가 true인 채 목표·정책 또는 원자료 판본을 바꾼다. 실제 인용 경계가 이를 거부하고, 현행 성공 집단은 관계없는 옛 판정 때문에 해소되지 않아야 한다.
8. task 대상이 없는 준비/계획의 예산을 소진한다. JSON뿐 아니라 사람용 출력에도 이유·고정 프로필 제약·다음 소유자가 보여야 한다.

새 테스트뿐 아니라 `_dispatchable`의 기존 직접 호출, BudgetConflict 메시지, machine host admission, provider wait, 설치 복구, submission publication 재처리를 함께 검증한다. 실제 입력 생성기·공유 검사기·원자적 편입·Git 재로드를 거치는 사례와 순수 함수 테스트를 구별한다.

**검토 범위와 남은 확인**

현재 원문에서 위 연결과 실제 소비자를 확인했고 계획의 누락을 반영했다. 남은 것은 실행 결과를 가정하는 추가 설계가 아니라, 구현 후 이 명세의 회귀 사례·입력 불변성·저장 경합·실제 비용을 확인하는 일이다. 현 단계에서 테스트 통과, Windows 동작, 연구 효능, 성능 향상을 주장하지 않는다.
