# 실행기와 조각: `run_tests.py`, `test_categories.py`

| 항목 | 값 |
|---|---|
| 원문 | `.claude/skills/do-math/scripts/run_tests.py` (356행), `.claude/skills/do-math/scripts/test_categories.py` (83행) |
| 시험 프레임워크 | 표준 라이브러리 `unittest`. pytest를 쓰지 않는다 |
| 실행 방식의 정본 | `scripts/tests/시험-지침.md` 1–3절 |
| 실행기 자체의 시험 | `tests/test_test_runner.py` ([모듈 문서](../모듈/test_test_runner.md)) |

do-math의 시험은 모두 `unittest.TestCase`의 하위 클래스다. 두 파일이 이 시험들을 실행 단위로 묶는다. `test_categories.py`는 시험 모듈을 여섯 **조각**(shard)으로 나누는 목록과, 실제 Lean을 부르거나 실제 프로세스 수명·자원을 다루는 시험에 붙이는 **격리 표지**를 정의한다. 실제 외부 자원을 쓰는 시험이 모두 이 표지를 다는 것은 아니다([총론](../README.md) 5.2). `run_tests.py`는 그 정의에 따라 시험을 고르고, 조각 순서대로 돌리며, 표지가 붙은 시험은 별도 프로세스를 Windows Job에 가두어 제한 시간 안에서 돌린다. 이 문서는 두 파일의 구조와 판정 규칙을 행 좌표와 함께 적는다.

## 1. `test_categories.py`: 조각과 격리 표지

### 조각 목록 `SHARDS` (행 16–56)

`SHARDS`는 조각 이름을 키로, 모듈 이름의 `frozenset`을 값으로 가진 사전이다. 원문은 조각마다 모듈 이름을 공백으로 나열한 문자열을 적고, 사전 내포식이 그 문자열을 `split()`해 집합을 만든다. 사전의 삽입 순서는 `foundation`, `host`, `lifecycle`, `research`, `review`, `academic`이다. `run_tests.py`는 이 순서대로 조각을 돈다.

| 조각 | 모듈 | 테스트 | 격리 시험 | 묶인 모듈의 성격 |
|---|---:|---:|---:|---|
| `foundation` | 69 | 1,039 | 10 | 대부분 순수 함수나 대역 위의 규칙. 저장소·계약·지식·거버넌스·관찰·실행 프로필 |
| `host` | 18 | 173 | 18 | 실제 프로세스, Windows Job, Lean, 운영자 예약, 호스트 자원 |
| `lifecycle` | 20 | 378 | 1 | 엔진 구동, CLI, 제어 명령, 역할 입력, 수명 관문 |
| `research` | 4 | 121 | 0 | 목적 시나리오를 끝까지 모는 연구 흐름, 스케줄러, 복구 |
| `review` | 8 | 179 | 0 | 동일성 검토, 제출 흐름과 도구 |
| `academic` | 3 | 41 | 0 | 학술 요건, 모델 평가 |
| 합계 | 122 | 1,931 | 29 | |

모듈 수와 테스트 수는 2026-09-28 판본에서 `run_tests.py --list`의 수집 결과를 센 값이다. 격리 시험 수는 같은 수집 결과에 `isolation_for`를 적용해 센 값이다. 조각에 어떤 모듈이 들어가는지의 정본은 이 목록뿐이다. `시험-지침.md`는 목록을 옮기지 않고 `--list`로 확인하라고 정한다.

조각의 시간 목표는 두 가지다. 조각 하나를 단독으로 돌려 120초 안에 끝나야 하고, 모든 조각을 차례로 돌려 300초 안에 끝나야 한다(`시험-지침.md` 1절). 이 목표가 현재 판본에서 충족되는지는 이 지도의 범위 밖이다. 작업 기억(L-0020)에는 전면 정리 뒤 조각 단독 시간이 측정되지 않았다고 기록되어 있다.

### 등록 검사 `unregistered_modules(tests_dir)` (행 61–64)

디스크의 `tests/test_*.py` 파일 이름 집합과 `SHARDS`에 적힌 모듈 이름 집합을 비교한다. 반환값은 두 목록의 짝이다. 앞 목록은 디스크에 있으나 등록되지 않은 모듈이고, 뒤 목록은 등록되었으나 디스크에 없는 모듈이다. `run_tests.py`는 두 목록 가운데 하나라도 비어 있지 않으면 시험을 돌리지 않는다(아래 2.1). 새 시험 모듈을 만들면 반드시 조각에 등록하라는 규칙(`시험-지침.md` 4절 규칙 9)을 이 검사가 강제한다.

이 검사가 잡지 못하는 경우가 하나 있다. 같은 모듈이 두 조각에 적힌 경우다. 역사전 `_SHARD_OF`(행 58)는 `SHARDS`를 차례로 훑으며 만들어지므로, 뒤에 나온 조각이 앞의 것을 덮어쓴다. 그 모듈은 두 번 돌지 않고, 뒤 조각에 조용히 배정된다. 현재 `SHARDS`에는 이런 중복이 없다(모듈 122개가 조각별 합계 122와 같다). `test_test_runner`의 조각 등록 시험도 이 경우를 검출하지 않는다([모듈 문서](../모듈/test_test_runner.md)).

### 격리 표지 `test_group(label)` (행 67–73)

`LABELS`(행 57)는 `('lean', 'resource')`다. `test_group(label)`은 두 값 가운데 하나를 받는 데코레이터 공장이다. 다른 값을 받으면 `ValueError('unknown test label: ...')`를 던진다. 반환된 데코레이터는 대상(클래스나 메서드)에 속성 `do_math_test_group = label`을 달기만 한다.

- `lean`: 실제 Lean 도구 모음을 부르는 시험.
- `resource`: 실제 프로세스 수명이나 자원 한도를 다루는 시험.

표지를 다는 시험 모듈 11개 가운데 8개는 이 함수를 `from test_categories import test_group as category`로 가져와 `@category('lean')`처럼 쓴다. 나머지 3개(`test_live_observation`, `test_machine_parallel`, `test_schedule_lifetime`)는 `test_group`이라는 이름 그대로 쓴다. 그래서 원문에서 `test_group(`만 검색하면 표지의 일부만 찾는다. 표지가 붙은 시험은 `lean` 20개, `resource` 9개다.

### 판정 함수 `isolation_for(test)`와 `shard_for(test)` (행 76–83)

`isolation_for`는 시험 인스턴스의 메서드(`_testMethodName`으로 찾은 것)에 붙은 표지를 먼저 보고, 없으면 시험 클래스의 표지를 본다. 반환값은 `'lean'`, `'resource'`, `None` 가운데 하나다. 클래스 표지는 `getattr(type(test), ...)`로 읽으므로, 상속받은 하위 클래스에도 적용된다. 메서드 표지는 클래스 표지를 덮어쓴다. 모듈 docstring은 모든 메서드가 격리를 요구하면 클래스에 표지를 붙이고, 그렇지 않으면 해당 메서드에 붙이라고 정한다.

`shard_for`는 시험 클래스가 정의된 모듈 이름의 마지막 성분을 `_SHARD_OF`(행 58, 모듈에서 조각으로 가는 역사전)에서 찾는다. 등록되지 않은 모듈의 시험이면 `KeyError`가 난다. 실행기는 등록 검사를 먼저 하므로 정상 경로에서는 이 오류가 나지 않는다.

## 2. `run_tests.py`: 선택, 실행, 보고

### 2.1 `main(argv=None)`의 흐름 (행 264–352)

| 인자 | 뜻 |
|---|---|
| 위치 인자 `tests` | 시험 ID나 모듈 이름. 시험 ID가 인자와 같거나 `인자 + '.'`로 시작하면 선택된다. 따라서 모듈, 클래스, 메서드 수준이 모두 된다 |
| `--shard 이름` | 조각 선택. 여러 번 줄 수 있다. 값은 `SHARDS`의 키로 제한된다 |
| `--match glob` | 시험 ID에 대한 `fnmatchcase` 패턴. 여러 번 주면 어느 하나에 맞는 것 |
| `--list` | 실행하지 않고 `조각<TAB>시험 ID`를 출력 |
| `--timeout 초` | 격리 실행의 단계별 제한 시간. 기본 300. 유한한 양수가 아니면 인자 오류 |
| `--output 폴더` | 결과 폴더. 새 폴더이거나 비어 있어야 한다 |
| `--worker 폴더` | 숨은 인자. 격리 작업자 프로세스가 자신을 이 모드로 다시 부른다 |

실행 순서는 다음과 같다.

1. `--worker`가 있으면 `_worker`로 가고 끝난다.
2. `--timeout`을 확인한다.
3. `unregistered_modules(TESTS)`를 확인한다. 두 목록 가운데 하나라도 비어 있지 않으면 `scripts/test_categories.py SHARDS is out of date` 메시지와 함께 종료 코드 2로 끝난다.
4. `_edition()`으로 실행 전 판본을 기록한다(2.6).
5. `unittest.TestLoader().discover(TESTS, pattern='test_*.py')`로 수집한다. 로더에 import 오류(`loader.errors`)가 있으면 그 내용을 출력하고 종료 코드 2로 끝난다. 모듈 하나의 import 실패가 조용한 누락이 되지 않게 하는 장치다.
6. 조각, 위치 인자, `--match` 세 조건을 모두 만족하는 시험을 고른다. 주지 않은 조건은 통과로 친다.
7. 위치 인자 가운데 어떤 수집된 시험에도 맞지 않는 것이 있으면 `No test matches:`를 출력하고 종료 코드 2로 끝난다. 원문 주석은 이유를 "오타 난 ID가 조용히 빠져 통과로 읽히는 것을 막는다"고 밝힌다. 작업 기억 L-0001은 이 규칙이 생긴 계기를 기록한다. 없는 ID가 있는 ID와 섞이면 조용히 버려져 거짓 통과가 날 수 있었다.
8. 고른 시험이 0개면 `No tests selected; no pass was established.`를 출력하고 종료 코드 2로 끝난다. 0건을 통과로 세지 않는 규칙이다.
9. `--list`면 목록을 출력하고 종료 코드 0으로 끝난다.
10. 결과 폴더를 정한다. `--output`이 없으면 `tempfile.mkdtemp(prefix='do-math-tests-')`를 쓴다. 폴더가 이미 있고 비어 있지 않으면 인자 오류로 끝난다. 이전 증거를 덮어쓰지 않기 위해서다.
11. `SHARDS` 순서대로 조각을 돈다. 조각마다 다음을 한다.
    - 격리 표지가 없는 시험은 이 프로세스 안에서 `_run_suite`로 한 번에 돈다. 결과는 `<폴더>/<조각>/`에 쓴다.
    - 표지가 있는 시험은 클래스별로 묶는다. 묶음마다 `_isolated`를 한 번씩 부르고, 결과는 `<폴더>/<조각>-isolated-<번호 세 자리>/`에 쓴다.
    - 조각 시간 `shard_seconds[조각]`을 소수 첫째 자리까지 기록한다.
    - 그때까지의 `report.json`을 `complete: False`로 다시 쓴다. 중간에 끊겨도 진행분이 남는다.
12. `_edition()`을 다시 계산해, 실행 중 바뀐 파일 목록 `changed`를 만든다.
13. 최종 `report.json`을 쓰고, 요약 JSON 한 줄과 가장 느린 20개 시험을 출력한다. 바뀐 파일이 있으면 통과가 아니라고 표준 오류에 출력한다. 마지막 줄은 `Report: <경로>`다.
14. `successful`이면 종료 코드 0, 아니면 1을 돌려준다.

### 2.2 최종 `report.json`의 필드

| 필드 | 뜻 |
|---|---|
| `complete` | 모든 부분 보고가 `complete`인가 |
| `successful` | 실행 중 바뀐 파일이 없고, 모든 부분 보고가 `successful`인가 |
| `selected`, `discovered` | 고른 시험 ID 목록, 수집된 시험 수 |
| `shards`, `tests` | 인자로 준 조각과 위치 인자 |
| `shard_seconds`, `total_seconds` | 조각별 시간과 그 합 |
| `counts`, `fixture_counts` | 결과별 개수. 시험 행과 준비 단계 행(아래 `fixture`)을 따로 센다 |
| `source_sha256`, `changed_during_run` | 실행 전 판본의 파일별 해시, 실행 중 바뀐 파일 |
| `reports` | 조각별·격리 묶음별 부분 보고 |
| `slowest` | 시간이 긴 시험 행 20개 |

조각 시간 해석에는 한 가지 주의가 있다. `restore_template`의 시작 상태 템플릿은 프로세스마다 한 번 만들어져 그 프로세스 안에서 재사용된다. 그래서 여러 조각을 한 실행에서 돌리면 뒤 조각은 앞 조각이 만든 템플릿의 빌드 비용을 치르지 않는다. `시험-지침.md` 2절이 조각 시간은 조각 하나만 준 실행으로 재라고 정한 이유다.

### 2.3 결과 기록기 `TimedResult` (행 56–137)

`unittest.TextTestResult`를 상속해 시험마다 행 하나(`id`, `outcome`, `seconds`, `details`)를 기록한다.

- `outcome`의 값은 `running`, `passed`, `failed`, `error`, `skipped`, `expected_failure`, `unexpected_success`다. `_run_suite`와 `_isolated`가 여기에 `not_run`과 `timeout`을 더한다.
- `startTest`가 행을 `running`으로 만들고, `stopTest`가 경과 시간을 적는다.
- `_outcome`(행 77–89)은 시작하지 않은 ID의 결과가 오면 `fixture: True`인 행을 새로 만든다. `setUpClass`나 `setUpModule`이 실패하면 `unittest`는 `setUpClass (모듈.클래스)` 같은 가짜 ID로 오류를 보고하는데, 그런 준비 단계의 결과가 이 표시로 시험 결과와 구별된다.
- 결과가 `failed`, `error`, `unexpected_success`이면 즉시 그 묶음의 결과 폴더(`<폴더>/<조각>/` 또는 격리 묶음 폴더) 아래 `failures/<시험 ID의 sha256>.json`에 `complete: False`인 실패 증거를 쓰고, 그 경로를 출력한다. 원문 주석은 목적을 이렇게 밝힌다. 다음의 긴 시험이 시작되기 전에 실패를 게시하려는 것이고, 이 파일은 진단 증거이지 묶음의 완료 결과가 아니다.
- 하위 시험(`subTest`)의 실패는 부모 시험 행에 `failed` 또는 `error`로 기록되고, 하위 시험 설명이 세부에 붙는다. 하위 시험의 건너뜀은 부모 행의 `skipped_subtests`에 쌓인다. 부모 행이 아직 `running`이면 `skipped`로 바뀐다.
- `checkpoint=True`(격리 작업자에서만)이면 시험이 시작하고 끝날 때마다 두 가지를 한다. `result.json`을 `complete: False`로 다시 쓰고, `progress-<일련번호 여섯 자리>.json`을 새 파일로 쓴다. 진행 파일은 덮어쓰지 않는 불변 파일이다. 원문 주석은 이유를 이렇게 밝힌다. 부모 프로세스가 읽고 있을 수 있는 파일을 Windows에서 교체하는 일을 피하려는 것이다.

### 2.4 묶음 실행 `_run_suite(tests, directory, *, checkpoint=False)` (행 140–158)

`TextTestRunner(verbosity=2)`에 `TimedResult`를 끼워 시험 목록을 돈다. 실행 뒤에는 보고되지 않은 시험을 찾는다. 준비 단계가 실패하면 그 클래스나 모듈의 시험은 아예 시작되지 않기 때문이다. 해당 클래스의 `setUpClass`나 모듈의 `setUpModule` 준비 행이 `skipped`이면 그 시험을 `skipped`로, 아니면 `not_run`으로 적는다. `not_run`의 세부는 "A fixture failed before this test could run."이다. `successful`은 두 조건을 모두 요구한다. `unittest`가 성공으로 판정해야 하고, 모든 행이 `passed`, `skipped`, `expected_failure` 가운데 하나여야 한다.

### 2.5 격리 실행: `_isolated`, `wait_for_worker`, `_worker` (행 161–256)

격리 표지가 붙은 시험 클래스 하나의 시험들은 다음 순서로 돈다.

1. `_isolated`(행 203–245)가 묶음 폴더를 새로 만든다. 요청 ID 목록을 `requested.json`에 쓰고, `scratch/` 폴더를 만든다.
2. 환경변수 `TMP`, `TEMP`, `TMPDIR`를 `scratch/`로 바꾼 환경으로, 제품의 `do_math.windows_job.WindowsJob`을 써서 `python -B run_tests.py --worker <묶음 폴더>`를 띄운다. Job 이름은 `do-math-tests-<uuid>`다. 작업자의 임시 파일은 모두 이 `scratch/` 아래에 생긴다. 그래서 강제 종료로 정리되지 않은 Lean 입력·출력도 그곳에 남는다.
3. 작업자 프로세스의 `_worker`(행 248–256)가 시험 폴더를 `sys.path` 앞에 넣는다. 표준 출력과 표준 오류는 묶음 폴더의 `stdout.txt`, `stderr.txt`로 돌린다. 그다음 요청 ID를 `loadTestsFromNames`로 적재해 `checkpoint=True`로 `_run_suite`를 돈다. 종료 코드는 성공이면 0, 아니면 1이다.
4. 부모 프로세스에서는 `wait_for_worker`(행 178–200)가 기다린다.
   - 0.05초마다 가장 최근의 `progress-*.json`을 읽는다. 그런 파일이 하나도 없으면 대체 경로 `progress.json`을 읽는다(행 184–185). 일련번호가 바뀌면 그 단계의 마감을 `지금 + timeout`으로 다시 잡는다. 따라서 제한 시간은 실행 전체가 아니라 시험 하나, 또는 준비·종료 단계 하나에 걸린다.
   - Job이 끝나고 Job 안에 프로세스가 하나도 남지 않으면 `None`을 돌려준다.
   - 마감을 넘기면 `job.terminate()`로 Job 전체(자식 프로세스 포함)를 끝낸다. 그 뒤 최대 10초 동안 비워지기를 기다리고, 마지막 진행 기록에 `timeout_seconds`, `observed_seconds`, `termination_confirmed`를 더해 돌려준다.
   - 시계와 대기 함수는 인자로 주입할 수 있다. `test_test_runner`는 이 주입점을 써서 가짜 시계로 이 함수를 시험한다.
5. 작업자가 끝나면 `_exit_code`(행 166–175)가 `GetExitCodeProcess`로 종료 코드를 읽는다. 작업자의 `result.json`에 종료 코드를 합쳐 판정한다.
   - 시간 초과가 있었으면 전체를 미완료·실패로 둔다.
   - 시간 초과에 걸린 시험은 `timeout`이 된다.
   - 준비 단계의 건너뜀으로 돌지 않은 시험은 `skipped`가 된다.
   - 그 밖에 끝나지 않은 시험은 `not_run`이 된다. 세부는 "Worker did not complete this test; inspect retained logs."다.
   - 실행 중 예외가 나면 `worker_error`를 남긴다.
6. 결과는 `worker-report.json`에 쓴다.

이 격리 제한 시간은 시험 실행기의 운영 값일 뿐이다. 모듈 docstring은 "이 실행기는 제품의 Lean 시간 한도를 결코 바꾸지 않는다"고 밝힌다. 격리하지 않는 시험에는 프로세스 수준의 시간 상한이 없다(`시험-지침.md` 1절).

### 2.6 판본 봉인 `_edition()` (행 259–261)

`scripts/` 아래 모든 `.py` 파일(`__pycache__` 제외)의 상대 경로별 SHA-256을 계산한다. 실행 전후 값이 다르면 `changed_during_run`에 적고 `successful`을 거짓으로 만든다. 대상은 `.py` 파일뿐이다. 역할 문서나 `references/` 같은 Markdown이 실행 중에 바뀐 것은 이 봉인이 잡지 않는다. 엔진이 실행 중 설치 코드나 역할 문서의 변경을 감지하고 멈추는 제품 쪽 동작은 따로 있다(`시험-지침.md` 3절 규칙 2).

## 3. 시험 모듈이 제품 코드를 찾는 방식

시험 모듈과 픽스처 모듈은 모두 `scripts/tests/`에 있고, 제품 패키지 `do_math`는 한 단계 위인 `scripts/do_math/`에 있다. 경로는 세 방식으로 잡힌다.

- **실행기**: `python scripts/run_tests.py`로 돌리면 파이썬이 스크립트 폴더인 `scripts/`를 `sys.path[0]`에 넣는다. 그래서 `do_math`와 `test_categories`를 import할 수 있다. `discover`는 시험 폴더를 시작 폴더로 삼아 `sys.path`에 넣으므로 `research_fixtures` 같은 픽스처 모듈도 이름만으로 import된다.
- **모듈 머리**: 시험 모듈 118개는 스스로 `scripts/`를 `sys.path` 앞에 넣는다. 117개는 `sys.path.insert(0, ...)`로, `test_trust_continuation`은 `sys.path[:0] = [scripts, scripts/tests]`로 넣는다. `test_test_runner`는 `run_tests`와 `test_categories`를 직접 import하기 위해 같은 머리를 쓴다.
- **경로 머리가 없는 모듈**: `test_design_walkthroughs`, `test_knowledge_import_engine`, `test_knowledge_io`, `test_schedule_pythonw` 4개는 경로를 스스로 넣지 않는다. 실행기나 먼저 import된 다른 시험 모듈이 넣어 둔 경로에 기댄다. 이 가운데 `test_schedule_pythonw`는 `do_math`를 import하지 않는다. `test_design_walkthroughs`는 파일을 직접 실행하면 `engine_fixtures`를 import하는 단계에서 `ModuleNotFoundError: No module named 'do_math'`로 실패한다.

`python -m unittest discover -s scripts/tests -p "test_*.py"`로도 시험을 돌릴 수 있다. 다만 조각 선택, 시간 보고, 격리와 외부 프로세스 종료 관리가 없다. 시험 모듈 122개 가운데 119개에 `if __name__ == '__main__'` 블록이 있다. 블록이 없는 3개(`test_initialization_probe_batch`, `test_launch_recovery`, `test_schedule_pythonw`)는 파일을 직접 실행해도 시험을 시작하지 않는다. 경로 머리가 없는 `test_design_walkthroughs`, `test_knowledge_import_engine`, `test_knowledge_io`는 블록이 있지만 직접 실행하면 import 단계에서 실패한다. `시험-지침.md` 1절이 파일별 종료 코드만으로 회귀 검사를 마쳤다고 판단하지 말라고 경고하는 이유다.

## 4. 실행기의 판정 규칙 요약

실행기는 다음 경우에 통과를 세우지 않는다. 각 규칙은 거짓 통과(실제로는 확인되지 않았는데 통과로 읽히는 결과)의 한 경로를 막는다.

| 상황 | 결과 | 막는 거짓 통과 |
|---|---|---|
| 조각에 등록되지 않은 모듈, 또는 등록되었으나 없는 모듈 | 종료 코드 2, 실행 안 함 | 어느 조각에도 속하지 않아 전체 실행에서 빠지는 모듈 |
| 수집 중 import 오류 | 종료 코드 2 | import가 깨진 모듈의 시험이 0개로 사라짐 |
| 위치 인자 ID가 어떤 시험에도 맞지 않음 | 종료 코드 2 | 오타 난 ID가 조용히 빠짐 |
| 고른 시험 0개 | 종료 코드 2 | 빈 선택을 통과로 읽음 |
| 비어 있지 않은 출력 폴더 | 인자 오류 | 이전 실행의 증거와 섞임 |
| 준비 단계 실패로 시작하지 않은 시험 | `not_run`, 실패 | 준비 실패가 시험 수 감소로만 보임 |
| 격리 작업자의 시간 초과나 미완료 | `timeout`·`not_run`, 실패 | 끝나지 않은 시험이 빠진 채 통과 |
| 실행 중 `.py` 파일 변경 | `successful: False` | 어느 판본의 결과인지 정할 수 없는 통과 |

실행기의 이 규칙들 가운데 어느 것이 `test_test_runner`로 검사되는지는 [그 모듈 문서](../모듈/test_test_runner.md)에 있다.
