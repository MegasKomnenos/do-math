# 시험 재편의 목적, 재개 판단과 남은 완료 조건

Claude 세션 `16d62671-b86c-420b-ad51-2d857f6fa9e7`은 마지막 옮기기 묶음 `knowledge.3`과 `submission.3`을 파견한 직후 공급자 API 한도로 중단됐다. 재개 기준은 main의 `9672dbac`이다. 이 문서는 원문 대화, 설계·진행·조사 문서와 코드를 대조한 재개 판단의 기록이다. 설계 정본은 [설계.md](설계.md), 최신 통합 실행·커밋·단계별 상태의 정본은 [진행.md](진행.md)다. 이 문서의 관찰이 제품 코드에 관한 과거 조사와 다르면 현재 코드를 우선한다.

진행 중인 1단계는 제품 동작을 보존하는 재편이다. 하위 단계 1e는 결함 범주에서 도출한 시험 의무 19개를 새 체계에 구현하는 작업이다. 1f는 옛 시험 1,932개를 새 체계로 옮기거나 근거를 갖춰 은퇴시키고, 필수 보존 지식 61개의 도착지를 처분표에 기록하는 작업이다. 두 하위 단계는 영역마다 함께 진행한다. 이번 재개에서는 중단된 두 옮기기 묶음과, 메인에 남겨진 실행기 옛 시험 11개를 우선 통합한다.

## 재편이 막아야 하는 실패

사용자가 요구한 것은 모든 기능과 경로를 실제로 확인하면서, 이전 개발의 세밀한 개선과 시행착오를 보존하는 시험 체계다. 직접적인 계기는 반복 검증을 통과한 코드에 실제 연구를 멈추는 결함이 남아 있었던 것이다. 조사 원장은 137건 중 정지급 64건을 식별했고, 그중 62건은 실제 모델·Lean·외부 프로세스 없이도 잡을 수 있었다. 따라서 외부 호출을 늘리는 일만으로 이 실패를 해결할 수 없다. 결함 지점의 제품 코드를 시험이 실제로 실행하게 하고, 알려진 사례와 같은 기제의 다른 사례도 일반 시험으로 검사해야 한다.

세 유출 경로와 대응은 구체적으로 다음과 같다.

| 유출 경로 | 실제 사례와 놓친 이유 | 재편의 대응과 남은 확인 |
|---|---|---|
| 대역이 제품의 판정을 대신함 | 옛 저장 대역은 닫힌 저장 스키마의 검증을 실행하지 않았다. 신뢰 재결속 사건의 네 필드가 거부되는 KD-0006은 그 저장 경계에서 드러난다. | 시험도 실제 `ResearchRepository`로 게시하고, 대역은 그 아래 Git 객체·참조만 맡는다. 저장 필드 구조 검사와 T3의 쓰기 분기 도달을 함께 본다. KD-0006은 현재 열린 결함이며 시험이 발견했다는 사실과 수리가 끝났다는 사실을 구분한다. |

이 대응은 서로 다른 확인을 맡는다. 분기에 도달했다는 기록은 그 결과를 제대로 단언했다는 증거가 아니다. 따라서 제품 함수의 본문을 `return None`, `pass` 또는 생성기 조기 종료로 무력화했을 때 시험이 실패하는지도 본다. 이 검사를 극단 변이라 부른다. 변이체마다 적어도 한 시험이 실패해야 하고, 살아남으면 그 결과를 확인하는 단언을 보강한다. 의사 시험됨 목록 `tests/pseudo_tested.json`은 시험이 실패하지 않은 함수·변이·사유를 기록한다. 1f에서 살아남은 변이체를 이 목록의 사유로 남길 수 있는 경우는 `None` 반환이나 빈 본문이 원래 동작과 같아서 시험으로 구별할 수 없는 경우뿐이다. 반대로 변이를 죽이는 시험이라도 결함 동작을 정답으로 고정할 수 있다. 일반 시험의 기대값을 계약·스키마·불변식에서 도출하고, 1e를 닫을 때 계약 문서와 맞대는 이유가 여기에 있다.

## 실제 코드가 도는 경계

1층은 같은 입력의 순수 계산, 2층은 판단·상태 변환·저장, 3층은 실행 순서·병행·수명·배선이다. 경계 어댑터는 외부 자원의 규약을 포트 연산으로 번역한다. `do_math/layers.py`와 구조 검사는 제품 Python 모듈의 층과 효과 API·import 방향을 판정한다. 허용할 예외가 있으면 그 API나 import를 쓰는 제품 코드 행에 `# layer: 사유`를 적는다. 층 표를 채운 수는 목적의 달성 여부를 대신하지 않는다.

포트는 시계·ID, Git 백엔드, 병렬 호출, Job, 예약, HTTP, 호스트 관찰의 일곱이다. 제품은 `Ports`를 받고 시험은 같은 프로토콜의 대역 묶음을 넘긴다. `Sim`은 실제 `ResearchEngine`을 세우며 엔진이나 저장소를 복제하지 않는다. Job 대역은 공급자·Lean 작업자를 프로세스 안에서 실행하고, 작업자의 `spawn` 이음매에서만 외부 프로그램을 대신한다. 그러므로 러너의 어댑터 선택, 요청 조립, 작업자 검사, 상태 기록, 수집기 해석이 실제 코드로 돈다.

실행 중 관찰과 정지는 `FakeJobs.live`로 만든다. 작업자와 러너가 차례를 주고받으며, 엔진 상태를 변경·게시하는 소유 스레드는 그 사이 순회를 한 바퀴 돌 수 있다. 이 경로를 러너가 곧바로 합성 결과를 돌려주는 경로로 바꾸면 제출·관찰·정지의 순서를 검증할 수 없다. 또한 `Sim.restart()`가 새 엔진만 세우고 제품의 모듈 수준 캐시를 남기는 현행 빈틈은 이음매 장부 21의 미해결 사항이다. 재시작의 문언만으로 모든 프로세스 메모리가 폐기됐다고 주장할 수 없다.

## 빠른 확인과 닫기 판정

T0는 선택 색인의 측정 당시 파일 내용과 현재 내용을 비교해, 바뀐 함수를 실행한 시험을 고른다. 색인은 시험별로 들어간 함수와 읽기 위해 연 입력 파일을 기록한다. 함수 밖의 코드가 바뀌거나, 색인에 그 파일을 읽은 시험이 기록되지 않은 비코드 입력이 바뀌면 더 넓은 폴더의 시험을 고른다. T0는 편집 확인의 비용을 줄이는 수단이며 전체 통과 판정은 T2와 흐름 실행이 맡는다.

T2는 구조·단위·대역 계약·짧은 `Sim` 시험 전체다. 역할 호출을 길게 잇는 `flows`는 T2에서 빠지므로 통합자는 병합 때 함께 실행한다. 작업자가 시험을 한 프로세스에서 순차 실행한 시간이나 다른 작업자의 부하가 섞인 시간으로 T2 예산을 판정하지 않는다. 부하 없는 main에서 `--jobs 3`으로 잰 전체 시간의 예산은 300초다.

T3는 T2와 흐름 폴더의 분기를 측정해 1·2·3층 관문을 판정한다. A29는 관문의 모듈별 분기 합집합과 선택·변이의 시험별 함수 기록을 분리했다. 일상 T3는 시험 파일이 바뀌었거나, 그 시험이 실행한 제품 함수의 몸체·위치 또는 읽은 입력 파일이 바뀌면 해당 시험 모듈을 다시 측정한다. 나머지 모듈의 측정 자료는 재사용한다. 제품의 모듈·클래스 수준 코드나 실행기가 바뀌면 전체를 다시 측정한다. 시험 결과는 캐시하지 않는다. 영역과 하위 단계를 닫는 판정은 `--full`의 재사용 없는 전체 측정으로 낸다. 일상 예산은 720초, 모든 모듈을 다시 재는 예산은 `T3_full` 2,400초다.

재개 직전 전체 T3는 1,990초에 끝나 main의 T3 저장소와 선택 색인을 만들었다. 통과 1,981·예상 실패 17·건너뜀 1이었지만, 제품 모듈 121개 중 98개에 빈틈이 있어 관문은 실패했다. 이것은 T3 도구의 구축이 끝났다는 근거이며 1f 완료의 근거는 아니다. 영역 마감은 그 빈틈에 결과를 단언하는 시험을 쓰고 해당 영역의 모든 함수를 변이하는 작업이다(A24).

빈틈은 새 체계 인프로세스 시험에서 실행되지 않은 제품의 분기나 행이다. 제외할 수 있는 방어 분기는 어떤 실제 호출자도 그 조건을 참으로 만들 수 없는 경우다. 해당 행에 호출자 좌표와 사유를 단 `# pragma: no cover`를 붙인다. 입력을 만들기 어렵거나 지금의 공개 경로에서 닿지 않는다는 이유만으로 제외하지 않는다.

이 저장소를 지금 복사하면 첫 실행부터 증분으로 돌지는 못한다. 저장소의 `records.json`은 `6d121082`의 `run_tests.py`를 기록했지만 `9672dbac`에서 실행기 예산 판정 코드가 바뀌었다. `t3_store.plan`은 실행기 내용이 달라지면 전체를 다시 측정한다. 메인은 실행기 변경이 정리된 상태에서 전체 T3로 최신 저장소를 만든 뒤 영역 마감 작업자에게 넘겨야 한다. 저장소의 기록된 내용 표식을 수동으로 덮어써 이 재측정을 피하지 않는다.

## 지켜야 할 결정과 이행 순서

원본 로그의 사용자 발화는 다음 결정을 확인한다. 행 번호는 JSONL의 1부터 시작하는 물리 행 번호다. 로그는 `C:\Users\wogud\.claude\projects\C--math\16d62671-b86c-420b-ad51-2d857f6fa9e7.jsonl`에 있는 Git 제외 로컬 자료이며, 이 문서와 설계의 U1~U9·A29가 추적되는 재개 근거다.

- 9행의 목표는 개별 함수와 결합 경로의 실제 검증, 결함 범주의 예방, 이전 디테일의 보존이다.
- 368행은 충분히 빠른 개발을 위해 실행 일정과 시간을 합리적으로 배정하라고 요구한다. 457행은 부류가 실제 목적과 실익을 구현해야 한다고 명시한다.
- 474·484행은 예산에 맞추려고 AI가 시험을 약하게 만드는 위험과, 그 방어 자체가 너무 비싸지는 위험을 함께 지적한다. 정확성을 지키되 실행 층·가상 시간·시작 템플릿을 조정한다.
- 522행은 나머지 결정과 수행을 AI에게 위임하고, 3300행은 실질과 원칙에 더 부합하는 개정을 재량에 맡긴다. 이 위임은 기능 목적이나 검증 보증의 임의 축소를 허가하지 않는다.
- 11482행은 병렬 단계 진행을, 18272행은 독립 조사에 따른 A29 개정과 전체 T3 재실행을 승인했다. 재개할 때 이 승인을 다시 미결정으로 만들지 않는다.

현재는 동작을 보존하는 1단계의 1e·1f다. 시험이 실제 경로에서 제품 결함을 드러내면, 입력과 대역이 옳은지 확인한 뒤 원장과 재현 시험에 기록한다. 원장 결함의 예상 실패 표시는 그 결함의 재현 시험과, 처분 장부가 같은 결함 번호로 연결한 옮긴 시험에만 붙일 수 있다. 표시된 시험의 예상 밖 성공은 실패로 센다(A28). 결함의 교정과 설계 변경은 2단계다.

이행 순서는 다음과 같다.

1. 마지막 두 옮기기 묶음과 메인의 실행기 시험 11개의 단언·입력·실제 경로를 전수 강도 검토한다. `note`·은퇴·남김의 사유는 현재 코드로 확인한다. 새 시험·처분표·옛 시험 삭제를 같은 변경으로 합치고 T2와 흐름을 확인한다.
2. 옮기기 묶음이 제출한 공통 제품 이음매 구현 요청(상신)은 이미 모였다. 메인은 장부와 남은 옛 시험을 대조해 공통 이음매를 설계·연결하고 해당 옛 시험을 옮긴다. 단순히 공개 경로를 대체하는 인자로 우회하지 않고 필요한 배선도 검증한다. 호출자가 포트를 모두 넘기게 되면 이행 중에 OS 시계·호스트 기본값을 채우던 `migration_defaults`와, 포트 인자가 None이면 옛 구현을 쓰는 대체 분기를 삭제한다. 공유 기반 변경이 정리된 뒤 최신 전체 T3로 저장소와 색인을 제공한다.
3. 영역마다 옮기기가 합쳐진 뒤 아래 표의 의무를 구현하고 분기·변이를 마감한다. 메인은 영역 마감 작업자에게 줄 프롬프트를 생성한다. 별도 검토자가 그 프롬프트의 의무 절을 [조사/결함-범주.md](조사/결함-범주.md) 5절의 모집단·입력·성질·검산 표와 대조한 뒤, 메인은 첫 영역 마감 작업자를 실행한다.
4. 메인은 보존 지식 61개의 처분, 7-A·2-D 상태 기계 속성 시험과 11-A 역할 호출 수, 일반 시험과 계약의 대조를 마친다. 1f의 닫기에는 옛 모음 은퇴·처분표 완비·T2·T3 관문·극단 변이가 모두 필요하다.
5. 2단계에서 열린 원장과 결함을 정답으로 고정한 시험을 교정하고, 3단계에서 T4·T5, 녹화 갱신, 시험 지침과 배포 사본을 확정한다. 현재 커밋 절차의 미러 동기화는 이미 수행하는 반면, 3단계의 실환경·배포 완료 판정은 아직 남아 있다.

현재 사용자가 지정한 파견 방식은 `codex exec`이며 에이전트 수에는 별도 상한을 두지 않는다. 기계 전체에서 동시에 실행하는 시험은 3개 이하다. 에이전트 수와 시험 실행 수는 서로 다른 자원이다. graphify는 명시적 구축·갱신 요청이 없으므로 갱신하지 않는다.

## 이번 재개의 확인 결과

재개한 두 worktree는 `9672dbac`에서 깨끗한 상태였다. 따라서 미커밋 변경을 복원하거나 기준선을 다시 계산하지 않고, 각각의 기존 파견문으로 계속했다. 마지막 두 묶음과 메인 실행기 몫에서 옛 시험 40개를 새 체계로 옮겼다. `knowledge.3`은 18개, `submission.3`은 11개, 실행기는 11개다. main 처분표는 1,932개 중 1,859개(옮김 1,856·은퇴 3)를 기록하며, 남은 옛 시험은 73개다. 보존 지식 61개는 아직 처분 전이다. 이 수치는 처분 장부에서 다시 센 값이며 전체 1e·1f 완료 판정이 아니다. 후속 작업자는 읽는 시점의 최신 통합 실행과 커밋 결과를 진행 원장에서 확인한다.

`knowledge.3`의 첫 강도 검토는 18개 중 두 약화를 찾았다. 고정 명령·지문 시험의 `execution_incomplete`가 옛 `failed`가 아니라 실제 컴파일 전 `rejected`에 대해서만 검사됐고, 정확한 산출물 시험에는 승인 명령과 다른 설정 명령 입력이 빠졌다. 교정은 옛 Python 명령·실패 사전·지문·공리·정산 값을 실제 준비·수신 단계의 단위 시험에 보존하고, 실제 검증기·작업자·저장 배선에서 나온 `failed`도 같은 정산 값을 단언하게 했다. 산출물 시험의 unit과 Sim에는 승인 명령과 다른 설정 명령을 각각 복원했다. 독립 수정 확인은 두 지적이 해소됐다고 판정했다. 실제 컴파일러 대역의 출력 해석으로 난 실패와, 옛 시험이 돌려준 `{"status": "failed", ...}` 결과 객체의 필드·바이트 보존은 서로 다른 증거이며, 같은 옛 ID의 처분이 두 새 시험을 연결한다.

실행기의 성공 JSON·비정상 종료 시험은 실제 Windows Job 자식이 성공 보고서를 쓴 뒤 `atexit`에서 종료 코드 7로 끝나게 옮겼다. 원본 JSON의 성공과 최종 보고의 실패를 함께 확인하며 Job·대기·종료 코드 함수를 패치하지 않는다. 실행기 11개와 제출 묶음의 옮긴 11개는 각각 전수 강도 검토에서 유지 판정이다. 지식 묶음은 첫 감사와 교정 확인을 모두 보존한다.

마지막 두 묶음에서 새 체계로 옮기지 못해 남긴 옛 시험은 셋이다. 캐시 시험 둘은 `install_tools`가 설치한 코드의 경로를 `__file__`로 고정하는 경계에 막혔다. 다른 하나는 일시 정지한 Lean 검증을 재개할 때 검사할 Lean 원문·등록된 도구 사슬 신뢰 환경·로컬 검증 권한 부여 중 하나가 바뀌었으면 검증기를 다시 호출하지 않는지 확인한다. 원문은 세 대상을 각각 하나씩 바꾼 하위 사례 셋을 실행한다. 신뢰 사례는 현재 활성 신뢰 환경 레코드의 `status` 필드에 현재 저장 열거 밖인 `inactive`를 넣으므로 실제 저장이 거부한다. 메인은 실제 설치 사본 등 현행 경로로 같은 성질을 시험할 수 있는지 먼저 확인하고, 필요한 이음매나 현행 입력 교정을 정해야 한다. 세 시험은 원문 그대로 남겼으며 정상 저장 검사를 우회하는 예외는 넣지 않았다.

원문 재독은 이음매 장부의 누락도 찾았다. 원본 로그 18598행은 운영자 엔진 자식 기동, `probe_cli`의 포트 없는 러너, 설치 위치에 기대는 Lean 탐색을 장부 27~29번으로 삽입하려 했고, 진행 원장은 그 번호를 참조한다. 그러나 실제 장부는 26번에서 끝났다. 현재 코드의 `scheduled_operator.run_engine`, `probe_cli.run_case`, `formal.toolchain_root`에서 해당 경계를 확인하고 장부에 복구했다. 소스 파일을 읽었다는 보고와 실제 삽입이 이뤄졌다는 사실은 구분해야 한다. 이 누락을 보완했어도 각 이음매의 구현은 후속 작업이다.
