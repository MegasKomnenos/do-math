# do-math 시험·코드 재편 설계

## 0. 이 문서의 지위

이 문서는 do-math 스킬(`.claude/skills/do-math/`)의 시험과 제품 코드를 재편하는 작업의 기준 문서다. 재편을 구현하거나 세션을 넘어 재개하는 AI는 이 문서를 처음부터 읽고, 자기가 맡은 단계의 작업과 완료 조건을 여기서 정한다. 진행 상태는 같은 폴더의 `진행.md`에 기록하며, 이 문서는 설계가 바뀔 때만 고친다.

기준 시점은 2026-09-29, 기준 판본은 커밋 `3552607`다. 문서 안의 각 결정에는 출처를 붙였다. `[사용자 결정]`은 사용자가 대화에서 확정한 것이고, `[AI 결정]`은 사용자가 결정을 AI에 위임한 뒤 AI가 정한 것이다. 절 제목에 붙은 표지가 그 절 내용의 출처이며, 절 안에서 출처가 다른 결정은 그 자리에 따로 표시한다. 사용자 결정은 그 결정이 세운 원칙을 더 잘 구현하는 개정이면 AI가 고칠 수 있다(U9). 고치면 10절에 근거를 남기고 사용자에게 보고한다. 원칙 자체를 바꾸려면 사용자에게 다시 묻는다. AI 결정은 더 나은 근거가 생기면 고칠 수 있으며, 고치면 10절의 결정 기록에 이유를 남긴다.

결함 근거의 원문은 `조사/`에 있다. 종합은 `조사/결함-범주.md`이고, 기간별 기록은 `조사/결함-A.md`·`결함-B.md`·`결함-C.md`, 현행 시험 대역의 사각지대는 `조사/대역-사각지대.md`, 제품 코드의 외부 경계와 효과 전파는 `조사/코드-구조.md`다. 이 문서의 요약과 원문이 다르면 원문이 옳고, 코드에 대한 사실은 현재 코드가 옳다.

## 1. 왜 재편하는가

### 1.1 결함이 새어 나간 방식

2026-09-14부터 09-28까지의 기억 노드, 검증런 장부, 수리 문서, 시험 인스턴스 기록에서 결함 137건을 한 기준으로 기록했다. 그 가운데 사람의 개입 없이 연구를 멈추는 정지급 결함은 64건이다. 인스턴스 전체를 멈추는 것이 41건, 과제 하나를 멈추는 것이 23건이다. 실제 운전에서 멈춤을 일으킨 것은 13건이고, 2026-09-24 첫 검증런 시점의 판본에는 정지급 결함 29건이 함께 들어 있었다.

재편의 근거가 되는 사실은 두 가지다. 첫째, 정지급 64건 가운데 62건은 모델, Lean, 실제 외부 프로세스 없이 도는 시험으로 잡을 수 있었다. 실제 운전에서 멈춤을 일으킨 13건 가운데 8건은 그 코드를 이미 검토한 검증런을 지나 운전에서야 드러났는데, 그 8건 가운데 7건도 그렇다. 둘째, 그런데도 시험과 검증런이 놓친 이유는 대부분 구조적이었다. 시험 대역이 결함 지점의 실제 코드를 대신했거나(저장 대역, 러너 대역), 결함이 있는 입구와 분기를 지나는 시험이 아예 없었거나, 대역이 만든 입력이 실제와 모양이 달랐다. 코드를 읽는 정적 검증런은 이런 결함을 범위 안에 두고도 놓쳤다. 9/24~25 기간의 검증런 일곱 번이 새로 찾은 정지급 결함 수는 차례로 1·5·5·3·0·2·2건이었고, 모두 첫 검증런 이전부터 있던 코드였다.

### 1.3 과정 결함

코드가 아니라 개발 과정이 결함을 통과시킨 기제가 여덟 가지 확인되었다. 대응은 7.3절에 있다.

- P1 검증런이 결함을 정확히 지적했는데 수리안의 형식을 이유로 기각하고 결함을 추적하지 않았다.
- P2 시험이나 fixture가 결함 동작을 기대값으로 고정했다(12건).
- P3 잡을 시험이 있었는데 수리 뒤 실행하지 않았다.
- P4 재현한 결함을 회귀 시험으로 남기지 않아 같은 결함이 다시 들어왔다.
- P5 사례만 고치고 기제를 두어 같은 기제가 라운드마다 재발했다.
- P6 수리와 경량화가 새 정지급 결함을 들여왔다.
- P7 정적 검증런과 통합 시험이 같은 대역과 합성 입력을 써서 같은 사각을 가졌다.
- P8 실제 외부 운전의 확인이 드물었다.

## 2. 제품 구조: 층과 포트

### 2.1 네 층과 판별 질문 `[사용자 결정]`

제품 코드의 함수는 네 층 가운데 하나에 속한다. 한 함수의 층은 아래 질문을 위에서부터 차례로 묻고 처음 "예"인 곳으로 정한다.

1. 같은 입력에 늘 같은 출력을 내고 바깥에 닿지 않는가? → **1층 원시**
2. 외부 프로그램이나 OS의 규약을 포트 연산으로 번역만 하는가? → **경계 어댑터**
3. 도메인의 판단이나 상태 변환을 하고, 외부에는 포트로만 닿는가? → **2층 인터페이스 요소**
4. 언제, 어디서, 무엇과 함께 실행할지(순서, 병행, 수명, 재시도, 회수)만 정하는가? → **3층 배선**

한 함수가 두 질문에 걸리면 그 함수를 나눈다. 나누는 기준은 하나다. 판단은 2층으로, 시점과 순서는 3층으로 보낸다.

| 층 | 담는 것 | 금지 |
|---|---|---|
| 1층 원시 | 규칙 판정, 스키마와 검사기, 직렬화·해시, 외부 출력의 해석 | 입출력, 시계·난수 직접 호출, 프로세스, 스레드, 가변 전역 상태 |
| 2층 인터페이스 요소 | 상태 전이, 역할 입력 조립, 제출 수신, 제어 적용, 저장 게시 | `subprocess`, `ctypes`, `threading`, `time`·`datetime.now`·`os.urandom`·`uuid.uuid4`의 직접 사용. 외부 효과는 포트로만 |
| 3층 배선 | 실행 루프, 병렬 호출, 작업자 기동과 회수, 관찰 배선, CLI, 예약 운영자 | 도메인 판정. 판정은 2층 함수로 옮긴다 |
| 경계 어댑터 | 포트의 실제 구현. 병렬 실행 포트와 호스트 관찰 포트는 예외로 3층에 둔다(A11, A18) | 해석과 판정. 해석은 1층으로 옮긴다 |

금지는 효과 API의 직접 사용에만 걸린다. 1·2층 코드는 그 밖의 파이썬 표현을 자유롭게 쓴다. 효과 API의 사용이든 3.3절의 import 방향이든, 꼭 필요한 예외는 그 행에 `# layer: 사유`를 달아 허용하고, 구조 검사가 예외 수를 집계해 보고한다.

### 2.2 포트 `[사용자 결정]`

**뜻.** 포트는 2·3층 코드가 바깥 자원에 닿을 때 반드시 거치는, 좁게 정의된 호출 창구다. 포트의 뜻은 네 요소로 이루어진다. 첫째, 포트는 연산의 집합이다. 연산 목록은 외부 도구의 기능 전체가 아니라 do-math가 실제로 쓰는 것으로 정한다. 둘째, 같은 포트에 실제 구현(경계 어댑터)과 시험 구현(포트 대역)을 끼울 수 있다. 셋째, 안쪽 코드는 구현을 스스로 만들지 않고 생성자 인자로 받는다. 넷째, 1층 함수에는 포트가 아니라 효과의 결과값(`now`, 새 ID)을 넘긴다.

**창구의 위치.** 포트의 창구는 외부 프로그램이나 OS로 실제로 넘어가기 직전에 둔다. 창구가 안쪽에 있을수록 대역이 실제 코드를 대신하는 몫이 커지고, 그 몫에 결함이 숨는다. 현행 시험의 러너 대역이 작업자 요청 조립을 건너뛰어 결함(B-35)을 가린 것이 그 예다.

**연산의 크기.** 연산은 do-math가 필요로 하는 의미 단위로 정한다. 예를 들어 Git 백엔드는 `update_ref(참조, 새 값, 옛 값)`처럼 원자적 비교 후 교체를 한 연산으로 둔다. `run_git(args)`처럼 명령 인자를 넘기는 연산은 두지 않는다. 그런 연산의 대역은 git 명령어를 해석해야 하므로 실제의 복제가 된다.

**일곱 포트.** 설계 대화에서는 여덟 포트를 정했으나, 1b에서 코드의 실제 병목에 맞춰 여섯으로 바꿨고(10절 A11~A13), 1d에서 호스트 관찰 포트를 더해 일곱이 되었다(A17, A18). 표의 "도입 이전"은 조사 시점의 코드 상태다.

| 포트 | 실제 구현 | 대역 | 도입 이전(`조사/코드-구조.md` 5절) |
|---|---|---|---|
| 시계·ID | `system_clock.SystemClock`: 벽시계, 단조 시계, 대기, ULID 난수원 | 시험이 움직이는 가상 시계, 결정적 ID | 주입되지 않음. `file_io.now` 66곳, `repository.new_id` 64곳, `governance.timestamp` 22곳이 직접 부름 |
| 병렬 실행 | `parallel.ThreadCalls`(스레드의 `ModelCalls`, 3층) | `ModelCalls`의 하위 클래스로, 소유자가 대기할 때 호출을 하나씩 소유자 스레드에서 실행 | `scheduler._run_parallel`이 직접 생성 |
| Git 백엔드 | `git_process.GitProcess`(객체는 프로세스 안에서 느슨한 객체로 쓰고, 읽기와 참조 이동은 git 자식 프로세스와 출력 해석) | 쓴 객체를 메모리에 두고, 메모리와 디스크의 느슨한 객체와 참조 파일을 읽는 인프로세스 구현(A25) | `ResearchRepository`가 내부에서 직접 생성 |
| Job | `windows_job.WindowsJobs`(Windows Job) | argv가 가리키는 작업자 모듈을 프로세스 안에서 실행하는 프로그램 표 | 공급자 어댑터와 `formal._job_run`이 `WindowsJob`을 직접 생성 |
| 예약 | `scheduled_operator.PowerShellScheduler`(작업 스케줄러 어댑터 스크립트) | 작업 보기 셋을 흉내 내는 메모리 표와 호출 기록 | `schedule(runner=)` 인자가 있으나 쓰이지 않음 |
| HTTP | `external.UrllibHttp` | URL 경로별 응답 표, 제품의 요청 검사와 리다이렉트 거부 | `execute_operation(transport=)` 인자가 있으나 쓰이지 않음 |
| 호스트 관찰 | `local_host.LocalHost`(3층, A18): 설정이 Lean 명령을 비웠을 때의 Lean 탐색, 승인된 도구 사슬 식별의 현재 관찰, 프로필이 쓰는 공급자 CLI의 식별과 명령 표면 | 시험이 선언한 Lean 명령, 도구 사슬 관찰 결과, CLI 식별과 능력을 답하는 가짜 호스트 | 2층 모듈(`execution_profiles`, `trust_validation`, `initialization`)이 3층의 관찰 코드(`formal.discover_lean`, `formal.toolchain_identity_errors`, 공급자 어댑터)를 직접 부름 |

**작업자와 외부 프로그램.** 공급자 CLI와 Lean은 같은 구조로 돈다. Windows Job 안의 작업자 파이썬 모듈(`codex_worker`, `claude_worker`, `formal._worker`)이 외부 프로그램(공급자 CLI, Lean)을 `Popen`한다. 그래서 Job 포트 하나가 작업자의 기동을 맡고, 작업자가 외부 프로그램을 여는 자리(`cli_worker.run_cli`, 두 작업자의 `run`, `formal._worker`)는 작업자의 이음매로 둔다. 시험에서는 Job 대역이 작업자 모듈을 프로세스 안에서 실행하고, 작업자의 이음매에 모델 대역이나 Lean 대역을 꽂는다. 그러면 `ModelRunner`의 어댑터 선택, `LocalCLIAdapter`의 요청 조립, 작업자의 요청 검사와 상태 기록, 수집기의 출력 해석이 모두 실제 코드로 돈다. 작업자 이음매는 `subprocess.Popen`과 같은 모양의 호출 가능 객체를 받는 `spawn` 인자다(`cli_worker.run_cli(..., spawn=)`, `codex_worker`와 `claude_worker`의 `run(request_path, *, spawn=)`, `formal._worker(request_path, *, spawn=)`, 기본값은 `subprocess.Popen`). Job 대역의 프로그램 표는 작업자 argv를 알아보면 그 작업자 모듈의 `run`을 요청 경로와 대역 `spawn`으로 부른다. 이 이음매는 그것을 쓰는 모델 대역과 함께 1d에서 넣는다.

**소유자 질의.** 발사권(`launch`)이 쓰는 소유자 질의(`owner_identity`, `owner_ended`, `named_job_empty`)는 Job 포트의 연산이다(A13 개정). 뒤 프로세스가 앞 발사의 종료를 판정하는 재시작 복구가 이 질의를 거치므로, `Sim.restart()`가 이전 소유자의 종료를 만들려면 포트에 있어야 한다. 발사권의 Job 이름은 시계 포트의 `random_hex`로 만든다.

Git 백엔드 포트는 저장 대역이 아니다. 저장 계약 검증과 봉인 대조와 게시 원자성은 실제 `ResearchRepository`가 한다. 대역이 대신하는 것은 Git이라는 외부 자원, 곧 객체 저장소와 참조뿐이다. 객체 쓰기(`write_object`)도 포트의 연산이다(A25). 대역은 쓴 객체를 메모리에 두므로 시험이 객체마다 파일 쓰기, `fsync`, 복사, 삭제를 치르지 않는다.

**포트로 두지 않는 것.** 파일 시스템은 임시 폴더 위에서 빠르고 결정적이므로 포트로 두지 않는다. Windows 전용 원자 교체(`file_io.atomic_replace`)만 경계 계약 시험으로 본다. 환경변수와 호스트 이름은 3층 진입점에서 한 번 읽어 설정 값으로 넘긴다.

**넘기는 방식.** 일곱 포트는 `do_math/ports/__init__.py`의 데이터클래스 `Ports` 하나에 묶는다. 필드 하나가 포트 하나다. `do_math/ports/`는 프로토콜과 `Ports`만 담는 1층 모듈이며 어떤 구현도 import하지 않는다. 실제 구현을 골라 `Ports`를 채우는 조립 함수 `real_ports(설정)`는 3층 모듈 `do_math/wiring.py`에 둔다. `ResearchEngine`, CLI, 예약 운영자는 `Ports`를 생성자 인자로 받고, 운전 진입점(3층)이 `real_ports`로 만든 묶음을 넘긴다. 시험은 대역 묶음을 넘긴다.

### 2.3 층 분리에서 손대는 구조

- 길이 520행의 생성기 `engine._call_steps`(`engine.py` 2935~3455행)를 셋으로 나눈다. 앞쪽의 행동 판정과 입력 준비, 뒤쪽의 결과 수신은 2층 함수로 뺀다. 생성기에는 러너, 시계, 추적기 배선만 남긴다.
- 경계 어댑터 모듈이 함께 담은 순수 해석 함수를 1층 모듈로 옮긴다. 대상 모듈은 `codex_adapter`, `claude_stream`, `formal`, `git_store`, `windows_job`, `file_io`, `cli_worker`다.
- 엔진 믹스인은 2층으로 둔다. 믹스인이 쓰는 저장은 실제 `ResearchRepository`이며, 그 아래 Git 백엔드만 포트다.
- 이 작업은 모두 동작을 바꾸지 않는 1단계에 속한다. 대기 종류 등록부, 소유 루프의 단위별 실패 격벽, 규칙 정본 함수처럼 동작을 바꾸는 설계 변경은 2단계에서 들인다.

## 3. 부류의 틀 `[사용자 결정]`

### 3.1 원리

포트와 그 밖의 설계 요소는 부류로 존재한다. 부류를 두는 판정 기준은 하나다.

> 어떤 부류든, 그 부류의 모든 구성원을 자동으로 순회하는 시험이 적어도 하나 있을 때만 둔다.

이 기준이 부류의 실익을 구체적인 사건으로 만든다. 새 구성원을 선언하면 그 부류의 일반 시험이 새 구성원에도 적용되고, 선언이 불완전하면 완비 검사가 실패한다. 지금 체계에서는 새 외부 경계나 새 입구를 더한 개발자가 알아서 시험을 써야 했고, 과거의 "시험 없음" 유출이 그렇게 생겼다. 순회하는 시험이 없는 부류는 형식일 뿐이므로 만들지 않는다.

부류를 미리 다 정하지 않는다. 처음에는 결함 기록이 필요를 증명한 것만 세우고, 나머지는 해당 의무 시험을 구현할 때 같은 기준이 성립하면 추가한다.

### 3.2 부류가 정하는 다섯 항목

| 항목 | 뜻 |
|---|---|
| 선언 위치 | 구성원을 선언하는 한 곳 |
| 필수 구성요소 | 구성원 하나가 갖춰야 할 것 |
| 일반 시험 | 부류의 모든 구성원을 자동 순회하는 시험 |
| 완비 검사 | 필수 구성요소 누락을 잡는 메타 시험 |
| 추가 절차 | 새 구성원을 넣는 단계 |

### 3.3 1단계 부류 다섯

**층.** 선언 위치는 `do_math/layers.py`의 표다. 제품 모듈마다 층과 책임 한 줄을 적는다. 일반 시험은 `tests/structure/test_layers.py`이며, 표에 선언된 층으로 모든 제품 모듈을 AST 검사한다. 검사하는 것은 import 방향과 2.1절의 효과 금지다. import 방향 규칙은 제품 모듈 사이의 import에만 적용되고, 표준 라이브러리와 외부 패키지의 import는 2.1절의 효과 금지로만 판정한다. import 방향은 다음과 같다. 1층은 1층만 import한다(포트 프로토콜 포함). 경계 어댑터는 1층과 다른 경계 어댑터를 import한다. 공급자 CLI 실행 어댑터가 Windows Job 어댑터를 쓰는 것처럼, 한 포트의 실제 구현이 다른 외부 경계를 구현 세부로 쓸 수 있기 때문이다. 2층은 1·2층을 import하고 경계 어댑터는 import하지 않는다. 2층은 포트의 프로토콜만 알고 실제 구현을 모른다. 3층은 모든 층과 경계 어댑터를 import할 수 있으며, 실제 구현을 고르는 조립은 3층에서만 한다. 완비 검사는 표에 없는 제품 모듈을 실패로 판정한다. 제품 모듈의 모집단은 `scripts/do_math/` 아래의 모든 `.py`(하위 패키지와 `__init__.py` 포함)와 `scripts/` 바로 아래의 `.py`에서 시험 실행기(`run_tests.py`, `test_categories.py`)를 뺀 것이다. 이행 중에는 표에 `PENDING` 목록을 두어, 아직 층 규칙을 지키지 못하는 모듈을 올린다. `PENDING`에도 없는 모듈은 즉시 실패이고, 1c 단계의 완료 조건은 `PENDING`에 A17의 환경 관찰 이음매 셋(Lean 탐색, 도구 사슬 관찰, 공급자 CLI 식별)만 남는 것이다(셋은 1d에서 비운다).

**포트.** 선언 위치는 `Ports` 데이터클래스의 필드 목록이다. 필수 구성요소는 다섯이다. `do_math/ports/<이름>.py`의 `typing.Protocol` 클래스, 실제 구현(경계 어댑터 층, 병렬 실행과 호스트 관찰만 3층), `tests/support/fakes/<이름>.py`의 대역, 계약 시험(기반 클래스와 대역 쪽 하위 클래스는 `tests/contracts/test_port_<이름>.py`에, 실제 구현 쪽 하위 클래스는 `tests/boundary/test_port_<이름>.py`에 둔다. 배치의 이유는 8절), `Ports` 필드와 `real_ports`의 실제 구현 연결이다. 완비 검사(`tests/structure/test_ports.py`)는 모든 필드에 대해 프로토콜의 존재, 실제 구현과 대역이 모든 연산을 같은 서명으로 갖는지(`inspect.signature` 비교), 두 구현 각각의 계약 시험 하위 클래스의 존재를 확인한다. 일반 시험은 계약 시험 모음과, `Ports` 대역 묶음으로 엔진을 세우는 3층 하네스(4.1절)다. 새 포트를 넣는 절차는 프로토콜, 실제 구현과 대역, 계약 시험, `Ports` 필드, 호출 지점 전환의 순서다. 계약 시험을 빠뜨리면 완비 검사가 실패하므로, 대역이 실제와 갈라지는 출발점(P7)이 구조적으로 막힌다.

**입구.** 외부에서 들어온 입력을 받아 상태에 반영하는 함수다. 결함 기록이 확인한 입구는 다섯 무리다. 공개 제어 action 14종(`control_contracts`), 작업 공간 제출 검사와 중앙 수신 검사(`submission`, `integration`), 공급자 사건 기록(`claude_stream`, `codex_adapter`의 해석을 거쳐 엔진이 적용하는 지점), 관찰 적용(`observations`), 제어 수송의 영수증 조회(`control_transport`)다. 1e 단계에서 표를 만들 때 각 무리의 처리 함수를 코드에서 확정한다. 선언 위치는 시험 쪽 `tests/support/ingress.py`이며, 입구마다 이름, 입력 스키마, 처리 함수, 반려 형식, 소비 판정을 둔다(결정 A21). 소비 판정은 그 입구에서 "항목이 처리되었음"을 관찰하는 방법이다(예: 제어 요청이면 inbox에서 사라지고 영수증이 남음, 제출이면 거부 영수증이 남고 같은 제출이 다시 검사되지 않음). 일반 시험은 두 층에 있다. 1·2층 시험(`tests/unit/test_ingress_rejection.py`)은 검사 함수에, 3층 시험(`tests/sim/test_ingress_consumption.py`)은 `Sim`의 소유자 순회에 입력을 넣는다. 두 시험은 모든 입구에 스키마에서 생성한 잘못된 모양(비객체, `None`, 빈 목록, 잘못된 형, 열거 밖 값, 경로 이탈 값)을 넣고 세 가지를 단언한다. 입구는 표에 적힌 반려 형식(구조화된 이슈 목록이나 거부 영수증)으로만 거부하고 그 밖의 예외를 내지 않는다. 반려된 항목은 정확히 한 번 소비된다. 소비는 표의 소비 판정으로 관찰한다. 뒤이은 정상 입력은 처리된다. 입구 부류에는 완전한 완비 검사가 없다. 코드에서 입구를 기계적으로 전부 찾을 수 없기 때문이다. 그래서 두 가지로 누락을 줄인다. 첫째, 이미 중앙 목록이 있는 입구는 그 목록에서 표를 만든다. 공개 제어 action은 `control_contracts`의 목록에서, 제출 검사가 받는 확장 기록의 종류(연구 출력과 함께 제출되는 지식·관계·확장 행의 종류)는 `integration` 모듈의 목록에서 만들므로 목록에 추가된 항목은 자동으로 등록된다. 둘째, 목록 밖의 입구는 반려 분기가 어떤 시험에서도 실행되지 않으면 분기 도달 관문(5.5절)에 미도달로 드러난다. 다른 시험이 그 반려 분기를 우연히 실행하면 미등록이 드러나지 않는다. 이 한계는 11절에 적는다.

**계약 쌍.** 생산자 함수가 만든 값을 수신 검사가 받아야 하는 쌍이다. 선언 위치는 `tests/contracts/pairs.py`의 표이고, 제품 코드에는 선언을 더하지 않는다. 필수 구성요소는 생산자, 생산자 입력의 분기 표본(설정 선택지 전건, 공급자 전건, 다중도 0·1·여럿, 선택 필드 있음·없음), 수신 검사다. 일반 시험은 모든 쌍에 대해 두 방향을 단언한다. 생산자 출력이 수신 검사를 통과한다. 수신 검사가 아는 필드(필수와 선택)마다 그 필드를 쓰는 생산자 분기가 있다(결정 A20). 수신 검사가 필드를 이름으로 모르는 쌍(직렬화기 등)은 표에 면제를 명시한다. 결함 기록이 확인한 쌍은 여섯 가지다(저장 가족 × 저장 계약 검증, 작업자 요청 조립 × 작업자 요청 검사, 신뢰 manifest 조립 × 신뢰 환경 검사, 관찰 추적기 기록 × 저장 스키마, 조건 문법의 상태 어휘 × 스키마 열거, 러너 영수증 × JSON 출력). 저장 가족을 뺀 다섯 가지(작업자 요청, 신뢰 manifest, 관찰 추적기 기록, 조건 문법, 러너 영수증)를 쌍 표에 처음 등록하며, 조건 문법처럼 한 가지가 열거마다 여러 쌍으로 나뉠 수 있다. 저장 가족은 쌍 표에 두지 않고 제품 전체를 보는 구조 검사 둘로 대신한다(결정 A22).

**말뭉치 항목.** 외부 도구의 실제 출력을 녹화한 항목이다(4.5절). 선언 위치는 `tests/corpus/manifest.json`이다. 일반 시험은 모든 항목을 1층 해석 함수에 넣어 녹화 때 확인한 판정과 대조한다.

### 3.4 2단계 부류 여섯

대기 종류, 판정 규칙, 판정 함수, 시간 규칙, 발동 규칙, 역할 입력 요구 표는 2단계에서 해당 설계 변경과 함께 추가한다. 각각 3.2절의 다섯 항목을 따른다. 부류와 의무의 대응은 7.2절 표에 있다.

### 3.5 결합도·응집도의 판정

| 성질 | 판정 수단 |
|---|---|
| 층 사이 결합도가 낮다 | import 방향 검사, 1·2층의 효과 직접 사용 0건, 2·3층이 포트가 맡는 외부 자원(파일 시스템 제외, 2.2절)에 닿는 길이 `Ports`뿐 |
| 시험과 제품의 결합도가 낮다 | 새 시험 폴더에서 제품 이름 `patch` 0건(6.2절). 시험은 포트, 공개 진입점, 1·2층 함수에만 닿는다 |
| 층 안의 응집도가 높다 | 모듈마다 층 하나. 섞인 모듈은 나눈다. `# layer:` 예외 수를 관찰한다 |
| 추가·수정이 쉽다 | 새 구성원은 선언과 필수 구성요소. 누락은 완비 검사가 실패로 알린다 |

## 4. 시험 기반 `[사용자 결정]`

### 4.1 `Sim` 하네스

`tests/support/sim.py`의 `Sim`이 3층 시험과 대부분의 2층 시험의 기반이다. `Sim`은 `Ports`에 일곱 대역을 끼우고, Job 대역의 프로그램 표에 작업자 모듈과 모델·Lean 대역을 등록한 뒤, 제품의 공개 생성자로 실제 `ResearchEngine`을 세운다. 저장은 실제 `ResearchRepository`이고, 그 아래 Git 백엔드만 인프로세스 대역이다.

모든 조작은 사건 주입이다.

| 조작 | 뜻 |
|---|---|
| `sim.control(action, ...)` | 공개 제어 경로로 요청을 넣는다 |
| `sim.step()` | 엔진 루프를 한 바퀴 돌린다 |
| `sim.run_until(조건, 최대_단계)` | 조건이 성립할 때까지 돌린다 |
| `sim.advance(초)` | 가상 시간을 전진시킨다. 벽시계와 단조 시계를 따로 움직일 수 있다 |
| `sim.complete(호출, 결과)` | 병렬 실행 대역의 호출을 완료시킨다 |
| `sim.restart()` | 프로세스 메모리 상태를 모두 버리고 같은 저장소에서 엔진을 다시 세운다 |

병렬 실행 대역은 계산마다 스레드를 두지만, 한 번에 하나만 돌도록 계산과 소유자가 차례를 주고받는다(A19). 소유자는 대기할 때 계산 하나에 차례를 넘기고, 계산은 두 자리에서만 차례를 돌려준다. 시작 콜백을 소유자에게 맡길 때와, 소유자를 기다리며 `owner_turn()`을 부를 때다. 여기서 계산은 러너에서 작업자와 모델 대역까지 이어지는 한 호출 전체다. 모델 대역이 작업자 이음매에서 스스로 답하므로, 호출은 이 두 자리 말고는 멈추지 않고 끝난다. 그래서 작업자가 제어 요청을 내고 영수증을 기다리는 동안 소유자가 한 바퀴 돌아 그 요청을 처리하는 실제 순서가 결정적으로 재현된다. `sim.complete`는 시험이 호출의 완료 시점과 결과를 직접 정해야 할 때 쓰는 조작이며, 첫 의무 시험이 요구할 때 넣는다. `Sim`의 가짜 벽시계는 먼 해에 두고, `Sim`이 도는 동안의 실제 시각이 게시된 상태에 들어갔는지 검사한다. 층 검사는 3층의 시계 사용을 허용하므로, 3층 코드가 시계 포트를 건너뛴 자리는 이 동적 검사가 잡는다. 결정성의 범위는 사건 열과 시계·ID 포트에서 온 값까지다. 파일 시스템은 실제이므로 신뢰 기록의 지문(파일 생성 시각 포함)과 그에서 파생된 해시와 Git 객체 ID는 실행마다 다르다.

`run_until`은 상한 안에 조건에 도달하지 못하면 실패하고, 실패 메시지에 현재 대기 항목과 그 종류를 모두 싣는다. 정지급 결함이 끝나지 않는 시험이 아니라 멈춘 자리가 적힌 실패로 드러난다. `sim.restart()`는 강제 종료 뒤의 이어받기와 재시작 복구를 실행하는 유일한 수단이다.

`Sim` 위의 시험은 엔진 메서드나 저장을 바꿔 끼우지 않는다. 현행 시험의 제품 이름 대체 1,174건 가운데 엔진 내부 메서드 대체 265건과 상태 직접 주입 224건은 이행 때 `Sim`의 사건 주입이나 1·2층 함수 직접 호출로 바뀐다.

### 4.2 모델 대역

모델 대역은 술어로 경우를 고르고, 답은 실제 역할 입력에서 만든다. 역할 입력은 한 호출에 약 15만 토큰이고 식별자, 판본, 해시, 시각을 담으므로, 입력 전체를 키로 답을 찾는 표는 제품의 비본질적 변경에도 모두 어긋난다.

```python
sim = Sim.activated()
sim.model.on("contract_review", task="A").reply(reject("완료 기준이 측정 불가"))
sim.model.on("contract_review", task="A").reply(approve())
sim.model.on("research", task="B").reply(raw({"result": None}))
sim.run_until(lambda s: s.task("A").state == "approved", max_steps=50)
```

`on(역할, 대상 조건)`이 술어이고, `reject`, `approve`, `raw`는 답 빌더다. 답 빌더는 실제 입력에서 과제 ID, 판본, 봉인 참조를 복사해 스키마에 맞는 답을 만든다. 한 조건에 답을 여러 번 걸면 차례로 쓴다. 지정하지 않은 호출에는 기본 응답기가 유효한 최소 답을 낸다. 기본 응답기는 현행 `ScriptedRunner`와 `PurposeRunner`(`tests/runner_fixtures.py`, `tests/purpose_fixtures.py`)가 역할 입력에서 최소 유효 답을 만드는 논리를 옮겨 쓴다. 함께 옮길 재현 지식이 둘 있다. 후보 결속(`research_fixtures.bind_candidates`)은 과제 후보에, 그 후보를 작성한 모델 역할(후보 준비)에게 실제로 제공된 작업 프로필과 현재 유효한 권한 부여만 참조로 붙이는 작업자의 동작이다. 응답 봉인(`research_fixtures.seal_response`)은 함께 제출되는 조각(출력 전체, 지식·관계 행, 확장 행)의 목록을 선언하고 그 내용 해시로 `IN-` 식별자를 만드는 동작이다.

모델 대역은 제출 전에 스스로 스키마 검증을 하지 않는다. 검증은 엔진의 수신 검사가 한다. 그래야 시험이 일부러 잘못된 답을 넣어 수신 쪽 반려 경로를 실행할 수 있다. 답은 녹화 말뭉치에서 가져온 실제 스트림의 사건 구조(init, 한도 알림, 도구 사건, 결과의 순서) 위에 실린다.

### 4.3 저장 검증의 상시화

`Sim`과 1·2층 단위 시험은 저장이 필요하면 인프로세스 Git 백엔드 위의 실제 `ResearchRepository`를 쓴다. 메모리 저장 대역(`StateStore`), 쓰기 거부 대역(`NoRepository`), `_save` 대체는 새 체계에 두지 않는다. 모든 게시가 실제 저장 계약 검증을 지나므로, 인스턴스 정지 11건을 낸 범주 1의 주된 유출 경로가 구조로 닫힌다.

### 4.4 시작 상태

기본 출발점은 공개 경로다. `Sim` 위에서는 git 프로세스와 Job 기동이 없으므로 공개 `initialize`와 `activate`를 제어로 끝까지 도는 비용이 작다. 공개 경로를 기본으로 두면 "출발 상태가 경로를 건너뜀" 유출과, 제품 기본값과 다른 고정값을 가진 합성 활성 상태가 사라진다. 공개 경로 빌드가 시험 예산을 넘는 것으로 측정되면 그때 `restore_template` 방식(프로세스당 한 번 빌드, 같은 절대 경로로 복원)을 되살리고 그 지식을 옮긴다. 측정 전에는 만들지 않는다.

1d의 측정에서 `Sim` 위 공개 활성화는 6.3~7.8초로 3층 시험 예산 2초를 넘었다. 대부분은 저장 게시의 `fsync`와 상태 복사였다. 그래서 템플릿을 되살렸다. `Sim.activated()`는 프로세스마다 한 번 공개 경로로 활성화까지 만들고, 이후 그 사본을 같은 절대 경로로 복원한다. 복원 한 번은 약 1.1초다. 가짜 시계와 Job 대역처럼 파일 밖에 있는 대역 상태도 함께 복원한다. 신뢰 도구 사슬은 복사하지 않는 공유 폴더에 둔다. 신뢰 기록이 그 파일들의 생성 시각을 지문으로 적는데, 복사하면 생성 시각이 바뀌기 때문이다. 공개 경로 자체는 처음부터 활성화하는 시험 하나가 계속 검증한다.

### 4.5 녹화 말뭉치

`tests/corpus/`에 외부 도구의 실제 출력을 보존한다. 항목은 공급자 CLI 스트림(Codex JSONL, Claude stream-json), 작업자의 상태·최종 파일, Lean 검증 결과(선언 서명과 서명 해시 포함), 예약 작업 조회 출력이다. `manifest.json`이 항목마다 원 바이트의 경로, 종류, 도구 판본, 녹화 일시, 명령, 역할, 출처, 녹화 때 확인한 판정을 적는다. 첫 원천은 이미 보존된 실제 출력이다(`.skill-workspace/nat-add-zero-20260927-01`의 실행 기록, 보존된 Codex 출력). 말뭉치는 1층 해석 함수 시험, 모델 대역의 사건 구조, Lean 대역의 불변식(서명과 서명 해시의 일치 등)에 쓰인다. 스킬 안에 있어 Codex 사본에도 복제되므로 전체 크기 상한(초기 5MB, 조정 가능)을 두고, 큰 스트림은 형식을 대표하는 부분만 잘라 둔다.

### 4.6 1·2층 시험의 입력

입력 자료는 실제 생산자 함수로 만드는 빌더로 만든다. 빌더는 기본값을 가지고 시험은 의미 있는 필드만 바꾼다. 현행 `record_fixtures`처럼 손으로 쓴 사전 기록은 수신 쪽 계약에 맞춰져 생산자 결함을 가렸다. 예외는 잘못된 모양의 입력이며, 이것은 입구 부류의 일반 시험이 스키마에서 생성한다.

### 4.7 시험 전용 의존

coverage.py와 Hypothesis를 `requirements-test.txt`에 둔다. 제품 설치(`requirements.txt`)에는 넣지 않는다. Hypothesis의 `RuleBasedStateMachine`은 범주 7의 상태 기계 속성 시험에 쓰며, 규칙이 `Sim`의 사건 주입과 대응하고 실패한 사건 열을 최소 반례로 축소한다. 시험 기반은 표준 라이브러리 `unittest` 위에 유지한다.

### 5.2 시험 하나의 예산

1층 단위 50ms, 2층 단위 200ms, 3층 시뮬레이션 2초, 경계 계약 30초다. 예산을 넘는 시험은 매 실행 보고의 예산 초과 목록에 오르고 실패로 만들지 않는다. 실행 층(T0~T5)마다의 전체 시간, 곧 5.1절의 전체 예산은 보고와 단계 완료 조건으로 강제한다. 실행기는 예산을 넘어도 실행을 중단하지 않고 시험 결과의 통과 판정도 바꾸지 않는다. 대신 보고서 첫 줄에 예산 초과를 표시한다. 하위 단계를 닫을 때 T2나 T3의 실행 층 전체 시간이 예산을 넘은 상태로 남아 있으면 그 단계의 완료 조건을 충족하지 못한 것으로 보고, 꼬리 시험을 옮기거나 가볍게 한 뒤 닫는다. 수치는 한 설정 파일(`tests/budgets.json`)에 조정 가능한 값으로 두고, 0단계 기준선과 1d 단계의 첫 측정 뒤 재보정한다. 설정 파일은 시험 하나의 예산을 시험 폴더마다 하나씩 둔다. 1층과 2층의 단위 시험이 함께 있는 `unit` 폴더의 값은 2층의 200ms이므로, 1층의 50ms는 지금 따로 강제되지 않는다. 실행기는 새 체계 시험 가운데 자기 폴더의 예산을 넘은 것과, 요청한 실행 층의 전체 시간을 보고서 첫머리에 적는다. 옛 모음은 은퇴할 때까지 예산 밖에 둔다.

1d의 재보정은 수치를 바꾸지 않았다. 측정은 다음과 같다. T0(구조 검사)은 3~4초, T2의 새 체계 전체는 24초로 예산 300초 안이다. 3층 시험의 예산 2초는 템플릿 복원(약 1.1초)과 짧은 시나리오에 맞는다(소유자 한 바퀴 약 0.1초, 제어 하나의 처리 약 0.4초). 예산을 넘는 시험은 공개 경로를 처음부터 도는 활성화 시험, 두 번의 복원을 보는 템플릿 시험, 실행기 전체를 도는 보고 시험 셋이다. 셋 모두 넘는 비용이 시험 대상 자체이므로 6.1절에 따라 docstring에 시간과 이유를 적고 받아들였다. 템플릿의 빌드 비용(약 7초)은 그것을 쓰는 시험 모듈의 준비 단계(`setUpModule`)에서 치르므로 시험 하나의 시간에 들지 않는다.

### 5.3 선택 색인

T3 실행이 시험별 동적 문맥(어느 시험이 어느 행을 실행했는가)을 기록해 선택 색인을 갱신한다. 색인은 측정한 파일마다 그때의 내용(Git blob)을 함께 기록한다. T0은 그 내용과 현재 내용을 비교해 바뀐 행을 구하고 그 행을 실행한 시험만 고른다(결정 A23). 바뀐 행이 교체나 삭제면 옛 문장을 실행한 시험을, 순수 삽입이면 앞뒤 문장을 실행한 시험을 고른다. 빈 줄, 주석, docstring만의 변경은 선택을 움직이지 않는다. 커버리지 기반 선택이 놓치는 경우는 규칙으로 보완한다.

| 바뀐 것 | 고르는 것 |
|---|---|
| 시험 파일 자체 | 그 파일 전체 |
| 새 제품 파일, 색인이 모르는 행 | 그 모듈 층의 시험 전체 |
| 스키마, 역할 문서, 설정 같은 비코드 입력 | 그 입력을 읽는 시험 전체. T3 실행이 파이썬 감사 훅(`sys.addaudithook`의 `open` 사건)으로 시험마다 연 파일 경로를 기록해 색인에 넣는다 |
| 색인이 없거나 오래됨 | T1과 같은 모듈 단위 선택. 색인은 자기가 만들어진 커밋을 기록하며, 그 커밋이 현재 HEAD의 조상이 아니면 오래된 것으로 본다 |

선택은 속도를 위한 것이고 관문이 아니다. 선택이 놓친 것은 T2의 전체 실행이 거둔다. 작업자는 자기 worktree의 분기에서 T1을 통과한 뒤 그 분기에 커밋해 넘기고, 통합자는 병합한 결과가 T2를 통과해야 주 작업 트리에 커밋한다.

### 5.4 실행기와 폴더

기존 `scripts/run_tests.py`를 확장해 `--tier T0~T5`를 받게 한다. 현행 판정 규칙(모르는 시험 ID 거부, 빈 선택 거부, 실행 중 파일 변경 감지, 실패 즉시 게시, 결과 캐시 없음)은 유지한다. 시험의 층은 폴더로 정한다.

| 폴더 | 내용 |
|---|---|
| `tests/structure/` | 구조 검사(층, 포트, 입구, 냄새, 원장, 문서·코드 대응) |
| `tests/unit/` | 1·2층 단위 시험 |
| `tests/sim/` | 3층 시뮬레이션 시험 |
| `tests/flows/` | 시나리오 자체가 3층 시험 하나의 예산(2초)보다 긴 3층 시뮬레이션 시험(역할 호출 흐름을 끝까지 도는 것 등). T3와 기본 전체 실행에서 돌고, 통합자는 작업자 분기를 합칠 때 T2와 함께 돌린다(A26) |
| `tests/contracts/` | 포트 계약 시험의 기반과 대역 쪽, 계약 쌍 |
| `tests/boundary/` | 포트 계약 시험의 실제 구현 쪽 |
| `tests/smoke/` | T5 |
| `tests/support/` | `Sim`, 대역, 빌더, 원장 표시 |
| `tests/corpus/` | 녹화 말뭉치 |

병렬 묶음은 직전 실행의 시험별 시간 기록으로 자동 균형을 잡는다(가장 긴 시험부터 가장 가벼운 묶음에 넣는 LPT 규칙). 조각 목록 `test_categories.SHARDS`의 수동 관리는 없앤다. 조각 등록 누락 거부는 "모듈이 조용히 빠지는 것"을 막으려던 규칙인데, 폴더로 층이 정해지면 모든 시험 파일이 반드시 어느 층에 속하므로 그 실패 부류가 사라진다. 현행 시험 모듈 122개와 시험 1,931개(이하 옛 모음)는 이행 기간 동안 `tests/test_*.py`에 그대로 두고, 은퇴할 때까지 현행 조각 방식으로 돌린다.

### 5.5 분기 도달 관문

T3는 1·2·3층 모듈의 모든 분기가 적어도 한 시험에서 실행되었는지 판정한다. 경계 어댑터 모듈은 T3 관문에서 뺀다. 경계 어댑터의 외부 호출 분기는 인프로세스 시험에서 원리상 실행되지 않기 때문이다. 경계 어댑터의 분기 도달은 T4 실행에서 따로 측정해 보고하며 관문으로 쓰지 않는다. 어댑터가 담던 해석 함수는 1c 단계에서 1층으로 옮겨지므로 관문 안에 든다. 저장이 들어가는 분기는 실제 저장 검증이 켜진 시험에서 실행되어야 하며, 4.3절에 따라 새 체계의 모든 시험이 그렇다. 의도적으로 도달하지 않는 분기는 `# pragma: no cover`로 제외하되, 같은 행에 사유를 적어야 한다. 구조 검사가 사유 없는 제외 표지를 실패로 판정하고, T3 보고가 제외 수를 집계한다.

구조 검사, 실행기, 극단 변이 스크립트의 세부 판정 규칙(서명 비교의 정규화, 단언 도우미의 등록 형식, 변이 대상 함수의 세부 범위 등)은 1a 단계에서 도구를 만들 때 정하고, 도구의 docstring과 `시험-지침.md`에 적는다. 이 문서는 각 도구의 목적과 판정 대상을 정한다.

## 6. 시험의 실효 방어 `[사용자 결정]`

개발은 대부분 AI가 맡는다. 시간 예산의 압박 아래에서 통과하되 아무것도 확인하지 않는 시험이 생길 위험이 있고, 과거 기록에도 그런 시험이 있다(이름보다 약한 단언, 사유를 고정하지 않는 음성 시험, 늘 참인 단언). 방어는 세 겹이며, 셋 다 한 번 만들어 두면 기계가 매번 적용한다.

### 6.1 압박을 줄이는 규칙

시험의 정확성이 시간 예산보다 우선한다. 시험 하나의 예산 초과는 실패가 아니다. 예산을 넘었을 때 허용되는 대응은 세 가지다. 시험을 더 드문 층으로 옮긴다. 가상 시간, 포트 대역, 더 싼 시작 상태로 바꾼다. 그래도 넘으면 시간과 이유를 시험 docstring에 한 줄로 적고 받아들인다. 금지하는 대응은 네 가지다. 단언을 지우거나 약하게 만들기, 입력을 줄여 검사할 경로를 건너뛰기, 제품 내부를 패치해 경로를 끊기, 시험을 건너뛰기. 이 규칙은 `시험-지침.md`와 파견문의 공통 조항에 들어간다.

### 6.2 시험 냄새의 정적 검사

`tests/structure/test_test_smells.py`가 새 체계의 시험 파일을 AST로 검사한다. T0부터 돈다.

| 검사 | 실패 조건 |
|---|---|
| 단언 없는 시험 | `assert*`, `raises`, 등록된 단언 도우미 호출이 하나도 없다 |
| 사유 없는 음성 시험 | `assertRaises(유형)`만 있고, 이슈 코드의 정확한 일치나 `assertRaisesRegex`의 고유 문구가 없다 |
| 제품 이름 패치 | `do_math.*`를 `patch`한다. 대역은 포트로만 꽂는다 |
| 고정 대기 | `time.sleep`이 있다 |
| 사유 없는 건너뛰기 | 사유 문자열 없는 `skip`, `skipIf`, `skipUnless` |
| 넓은 예외 삼킴 | 시험 안의 `except Exception:`나 맨 `except:` |
| 사유 없는 커버리지 제외 | 제품의 `# pragma: no cover`에 사유가 없다 |

### 6.3 바뀐 함수의 극단 변이

하위 단계(9.1절 표의 한 행)에서 본문이 바뀌었거나 새로 생긴 제품 함수마다 변이체를 하나 만든다. 비교 기준점은 그 하위 단계를 연 커밋이며, 하위 단계를 시작할 때 `진행.md`에 적는다. 작업자가 T1에서 돌릴 때는 자기 worktree의 분기점 커밋을 기준점으로 쓴다. T1의 결과는 작업자의 자기 점검이고, 하위 단계를 닫는 판정은 T3가 하위 단계를 연 커밋을 기준으로 한 결과로 한다. 변이 규칙은 본문의 모양으로 정한다. 본문에 값을 돌려주는 `return 식`이 있으면 본문 전체를 `return None`으로 바꾼다. 없으면(상태를 바꾸는 함수) 본문 전체를 `pass`로 바꾼다. 생성기는 첫 문장 앞에 `return`을 넣는다. 반환형 주석은 보지 않는다. 선택 색인에서 그 함수를 실행한 시험만 돌리고, 변이체마다 적어도 한 시험이 실패해야 한다. 아무 시험도 실패하지 않은 함수는 의사 시험됨 목록 `tests/pseudo_tested.json`에 오른다. 항목은 함수의 모듈과 이름, 변이 규칙, 기준점 커밋, 사유다. `None` 반환이 원래 동작과 같아 어떤 시험도 실패할 수 없는 함수도 이 목록에 오르며, 사유 칸에 그 사정을 적는다. 이 목록의 사유 없는 항목이 0이어야 하위 단계를 닫는다. 변이는 작업 트리가 아니라 임시 사본에서 한다. 구현은 표준 라이브러리 `ast`로 본문을 치환하고 선택 시험을 도는 스크립트 하나이며, T3에 붙는다. 작업자는 T1에서 자기가 바꾼 함수에만 선택적으로 돌릴 수 있다.

이 검사는 커버리지가 보지 못하는 것, 곧 실행은 하되 결과를 확인하지 않는 시험을 잡는다. 분기 도달 관문을 채우려고 경로만 지나가는 시험이 여기서 걸린다.

1f는 제품 함수를 거의 바꾸지 않고 옮긴 시험과 새 시험으로 관문을 채우는 단계여서, 바뀐 함수만 변이하면 옮긴 시험이 결과를 확인하는지 거의 보지 못한다. 그래서 1f에서는 제품 영역마다 그 영역의 제품 모듈에 속한 모든 함수를 같은 규칙으로 변이한다(스크립트의 `--every`, 결정 A24). 살아남은 함수는 그 변이체에서 실패할 단언을 더하는 것이 원칙이고, 의사 시험됨 목록의 사유는 `None` 반환이나 빈 본문이 원래 동작과 같은 함수에만 쓴다.

### 6.4 남는 위험

결함 동작을 정답으로 적은 시험(P2)은 세 겹 모두 잡지 못한다. 그런 시험도 변이를 죽이기 때문이다. 이 위험은 두 가지로 줄인다. 손으로 쓴 기대값을 줄이고, 부류의 일반 시험처럼 기대값이 스키마·계약·불변식에서 나오는 시험을 중심으로 둔다. 일반 시험과 불변식 목록은 하위 단계를 닫을 때 메인 세션이 계약 문서와 대조해 검토하고 사용자에게 보고한다.

## 7. 결함 원장과 의무 배치

### 7.1 알려진 결함 원장 `[AI 결정]`

1단계는 동작을 바꾸지 않으므로, 의무 시험이 드러낸 현행 결함을 1단계에서 고칠 수 없다. 이 결함들은 원장으로 관리한다.

- 원장 `tests/known_defects.json`의 항목은 ID(`KD-0001` 형식), 한 줄 설명, 결함 범주, 재현 시험 ID, 발견 경위, 놓친 부류, 상태(열림·닫힘)를 가진다.
- 재현 시험에 `@known_defect("KD-0001")`을 붙이면 그 시험의 실패는 알려진 결함으로 센다.
- 표시된 시험이 성공하면 실패로 판정한다. 결함이 고쳐졌으면 표시와 원장 항목을 함께 닫아야 한다. 고쳐진 뒤 표시가 남으면 결함이 되살아나도 "예상대로 실패"로 통과해 회귀를 가리기 때문이다.
- 구조 검사가 표시와 원장의 일대일 대응을 판정한다. 원장에 없는 ID의 표시, 재현 시험이 없는 열린 항목은 실패다.
- 실행 보고는 열린 결함 수를 첫 줄에 적는다.
- 결함을 닫을 때 "놓친 부류" 칸에 그 부류의 일반 시험이 왜 놓쳤는지 적고, 일반 시험이나 부류를 보강한다.

2단계는 원장의 열린 항목을 닫는 작업이다. 재편의 완료는 원장이 비었거나 남은 항목마다 사용자가 승인한 보류 사유가 있을 때다.

## 8. 경계 층 `[AI 결정]`

**포트 계약 시험의 실제 쪽.** 3.3절의 배치대로 계약 기반 클래스와 대역 쪽 하위 클래스는 `tests/contracts/`에, 실제 구현 쪽 하위 클래스는 `tests/boundary/`에 둔다. 폴더를 나누는 이유는 실행 층이 다르기 때문이다. 대역 쪽은 인프로세스 시험이므로 T1·T2에서 돌고(T0에서는 선택 색인이 고를 때만), 실제 쪽은 외부 도구가 필요하므로 T4에서 돈다. T4의 포트 계약 실제 쪽 대상은 일곱 포트 모두다: 운영체제 시계, 스레드 병렬 실행, git 프로세스, Windows Job, 루프백 HTTP, 예약 어댑터의 `status`, 이 기계의 Lean 탐색과 공급자 CLI 관찰. 예약 어댑터의 동작 가운데 OS의 작업 목록을 바꾸는 것(`install`, `uninstall`, `schedule-wake`, `cancel-wake`, `start-*`)은 실제 쪽을 T5에만 두고, 목록을 읽기만 하는 `status`는 T4에서 본다.

**포트가 아닌 경계의 시험.** 포트로 두지 않았지만 OS 동작에 기대는 함수가 있다. `file_io.atomic_replace`(열린 독자가 있는 파일의 교체)가 그 예다. 실제 Lean도 여기에 든다. Lean은 포트가 아니라 작업자의 외부 프로그램이므로, 실제 Lean으로 `formal._worker`와 `verify_lean`을 도는 시험(휴대용 컴파일러. Mathlib 컴파일은 따로 표시해 선택 실행)은 경계 시험이다. 이런 시험은 대역 없이 실제 OS와 외부 프로그램으로 도는 경계 시험이며 `tests/boundary/`에 포트 계약 실제 쪽과 함께 두고 T4에서 돌린다. 포트 계약은 두 구현의 동치를 보고, 이 경계 시험은 한 구현의 OS 가정을 본다.

**말뭉치의 갱신.** T5가 실제 출력을 녹화하고, T4가 새 녹화와 옛 녹화의 형식 차이를 보고한다. 형식 차이는 외부 도구 판본 변화의 감지 수단이다.

**T5 스모크.** `run_tests.py --tier T5` 하나로 돈다. 공급자마다 실제 역할 스키마로 짧은 호출을 1~2회 하고, Job 작업자 연쇄, Lean, 시험 이름의 예약 작업 등록·pythonw 발화·해제를 확인하며 결과를 녹화한다. 확인하는 것은 모델 답의 품질이 아니라 실제 환경이 do-math의 가정대로 동작하는지다. 과거의 CLI 샌드박스 쓰기 거부(A-01), 실제 CLI의 스키마 거부(A-21), pythonw 부모 아래의 출력 미수집(B-01)이 이 부류이며, 대역은 작성자가 몰랐던 이런 동작을 흉내 낼 수 없다. 3단계에서 구현을 마치면 동작 확인과 말뭉치 갱신을 위해 한 번 실행한다.

### 9.2 실행 방식

구조 이동(1b, 1c)은 다른 모든 변경과 충돌하기 쉬우므로 메인 세션이 직렬로 한다. 포트 도입은 추상화를 통한 분기로 진행한다. 포트를 먼저 끼우고 기존 구현을 그 뒤로 옮긴 다음, 호출 지점을 하나씩 넘긴다. 여러 곳이 부르는 함수(`file_io.now` 등)는 병행 변경(새 경로를 추가하고, 호출자를 옮기고, 옛 경로를 지움)으로 옮긴다. 모든 중간 커밋에서 옛 모음이 통과한다.

이음새가 확정된 뒤의 대량 작업(1e, 1f)은 1d를 닫은 뒤에 시작한다. 1e와 1f 사이에는 선행 관계가 없으며, 단계 표의 순서는 선행 관계를 뜻하지 않는다. 병렬화의 축은 하위 단계가 아니라 제품 영역이다. 두 작업은 `.claude/agents/gp-matrix/`의 서브에이전트에 병렬로 나눈다. 분할 단위는 시험 지도(`docs/do-math/시험-지도-2026-09-28/README.md` 6절)의 제품 영역이며, 한 작업자가 한 영역의 1e 의무와 1f 이행을 함께 맡는다. 영역 사이에 걸치는 의무(예: 7-A 상태 기계 시험)는 메인 세션이 맡는다. 각 작업자는 별도 worktree에서 일하고, 파견문에는 6.1절의 허용·금지 대응을 공통 조항으로 넣는다. 기계 전체에서 동시에 도는 시험 실행은 셋 이하다.

### 9.3 동작 보존 판정의 한계

1단계의 동작 보존은 옛 모음과 새 의무 시험의 통과로 판정한다. 판정의 강도는 옛 모음의 강도를 넘지 못하며, 옛 모음에는 `조사/대역-사각지대.md`가 보인 사각지대가 있다. 그래서 1단계의 보고는 "옛 모음과 새 의무 시험이 통과한다"로 한정한다. 이 한계를 줄이려고 두 가지를 지킨다. 1단계의 리팩터는 기계적 변환(이동, 인자화, 추출)으로 좁힌다. 의무 시험은 1e에 들어가므로 1b·1c의 리팩터보다 뒤에 온다. 그래서 1b·1c의 동작 보존은 옛 모음과 포트 계약 시험으로 판정하고, 1c에서 동작을 크게 옮기는 절단(`engine._call_steps`)만은 그 경로의 특성 시험을 절단 전에 둔다.

### 9.4 커밋과 진행 원장

각 하위 단계를 닫을 때 `commit-harness`로 커밋하고 기억 노드를 남긴다. 푸시는 사용자의 지시가 있을 때만 한다. `진행.md`는 단계별 상태, 실행한 검증과 보고서 경로, 확정한 결정, 남은 작업과 재개 지점을 적는다.

**AI 결정.**

- A1 결함 원장과 엄격 규칙, 의무의 단계 배치(7절).
- A2 경계 층(8절)과 이행 단계(9절).

- A7 범용 의존성 주입 컨테이너, 플러그인 자동 탐색, 포트 추상 기반 클래스의 상속 강제를 두지 않는다. 데이터클래스 하나, 표 셋, 구조적 프로토콜과 서명 비교로 같은 보장을 얻는다.
- A8 T5는 3단계 구현 뒤 한 번 실행한다(공급자마다 1~2회 호출).
- A9 설계 대화의 4.2절에서 의무 9-C를 1단계로 적었으나, T5를 3단계에서 구현하므로 3단계로 옮겼다. 1단계 의무 수는 19개다.
- A10 경계 어댑터가 다른 경계 어댑터를 import하는 것을 허용한다(3.3절). 처음 규칙은 "경계 어댑터는 1층만 import한다"였으나, 1a에서 층 검사를 구현하며 공급자 CLI 실행 어댑터(`codex_adapter`)가 Windows Job 어댑터(`windows_job`)를 쓰는 것이 2.2절이 인정한 구현 세부임을 확인했다.
- A11 병렬 실행 포트의 실제 구현(`parallel.ThreadCalls`)은 경계 어댑터가 아니라 3층에 둔다. 스레드는 외부 프로그램이 아닌 배선이고, `ModelCalls`는 3층 추적 모듈을 쓴다. 대역은 제품 `ModelCalls`의 하위 클래스로 두어 판정·관찰·회수 논리를 복제하지 않는다.
- A12 설계 대화의 "공급자 CLI 실행", "Lean", "프로세스·Job" 세 포트를 Job 포트 하나와 작업자의 외부 프로그램 이음매로 바꾼다. 제품이 `WindowsJob`을 만드는 곳은 두 곳뿐이고 둘 다 "Job 안의 작업자가 외부 프로그램을 `Popen`"하는 같은 구조여서, 포트 수가 줄고 작업자 코드까지 실제 코드로 도는 대역이 된다(2.2절).
- A13(1c 개정) `launch`의 소유자 질의는 Job 포트의 연산이다(2.2절). 1b에서는 포트 밖에 두고 "재시작 시뮬레이션이 이전 소유자의 종료를 만들어야 할 때 옮긴다"고 적었는데, 1d의 `Sim.restart()`가 그 조건이어서 1c에서 옮겼다(포트 수정 절차: 양쪽 계약 시험을 먼저 고침).

A12와 A13은 사용자 결정 절(2.2절의 여덟 포트 표)을 바꾼 것이어서 사용자에게 확인을 요청했고, U9로 확인되었다.

- A14 파일 시스템 도우미 `file_io`와 Git 저장 논리 `git_store`는 2층이다. 파일 시스템은 포트가 아니므로(2.2절) 2층이 직접 쓰며, Windows 파일 API(ctypes·msvcrt)와 공유 위반 재시도 대기처럼 파일 시스템 자체를 구현하는 행만 `# layer:` 사유로 허용한다. 두 모듈이 담던 순수 값 규칙(JSON 직렬화·해시, SHA-256 모양, 텍스트·경로 조각 검사, 시각 해석)은 1층 `values`로, 식별자 모양(`is_new_id`, `oid_shape`)은 1층 `ids`로, 저장 배치 상수 `ARTIFACT_ROOT`는 1층 `state_contract`로 옮긴다. 물리 경계 `PhysicalBoundary`는 파일 시스템의 정체 확인이므로 `file_io`로 옮긴다. Git 커밋 시각은 시계 포트에서 받는다.
- A15 여러 곳이 부르는 1·2층 함수의 시계·ID 이전은 병행 변경으로 한다(9.2절). 새 ID나 현재 시각을 만드는 함수는 판별 질문상 2층이며 `clock`(시계 포트)을 인자로 받고, 제품 호출자는 `self.ports.clock`을 넘긴다. 비교에만 시각이 필요한 순수 함수는 시각 값을 받고, 호스트 이름을 비교하는 검사는 `host_id` 값을 받는다(2.2절: 호스트 이름은 3층 진입점에서 값으로 넘긴다). 인자가 없을 때 운영체제로 되돌아가는 경로는 옛 시험과 아직 값을 넘기지 않는 진입점을 위한 것이며, 2층 모듈 `migration_defaults` 한 곳(`clock_or_system`, `host_or_local`)에 모으고 1f에서 지운다. 시계 포트에는 시드용 난수 연산 `random_hex`를 더했다(포트 수정 절차: 프로토콜, 두 구현, 양쪽 계약 시험).
- A16 층 표의 재분류 원칙. 현행 규칙은 셋이다.
  1. 함수의 층은 판별 질문(2.1절)이 정한다.
  2. 모듈에는 한 층의 코드를 둔다. 예외는 1층 순수 함수를 2층 도메인 모듈에 함께 두는 것 하나이며, 한 도메인의 어휘를 층별 모듈로 흩지 않으려는 것이다. 그 모듈은 2층으로 선언한다. 3층으로 선언할 모듈이 판정을 담으면 판정과 배선으로 나눈다. 2.1절의 표가 3층에 도메인 판정을 금지하고 3.5절이 섞인 모듈을 나누게 하기 때문이다. 판정을 3층에 두면 그 코드가 2층 효과 금지의 강제에서 빠져, 가상 시간의 일관성이 층 검사가 아니라 현재 코드의 우연에 기대게 된다.
  3. 경계 어댑터는 포트의 실제 구현만이다. 어댑터가 담던 해석·검사 함수와 상수는 1층 모듈로 나눈다. T3 관문이 어댑터를 빼고 말뭉치 부류(9-B)가 해석 함수를 1층에서 부르기 때문이다.

  이 밖의 적용 규칙은 넷이다. 2층이 3층을 import하면 재분류가 아니라 이동으로 고친다. 원격 측정의 구간 API(`measured`, `phase`)는 결과를 바꾸지 않는 횡단 관심사이므로 2층의 import 행에 사유를 달아 허용한다. 값 인자에 이행 기본값을 둔 모듈은 제 층을 유지하고 `migration_defaults` import 행에 사유를 단다. 새 믹스인 모듈은 `*_engine.py`로 이름 짓는다. 제품은 작업자 작업 공간에 제출 검사와 입력 읽기 도구를 실으면서 공유 검사 코드만 압축해 싣고, 중앙에서만 도는 엔진 모듈은 파일 이름(`engine.py`와 `*_engine.py`)으로 가려 뺀다(`submission.install_tools`).

  경위와 단위별 적용은 다음과 같다. 단위는 한 하위 단계 안의 커밋 하나이며, `진행.md`의 1c 절에 차례로 적혀 있다.
  - 첫째·둘째 단위: 처음에는 "모듈의 층은 그 모듈의 함수와 import가 요구하는 가장 높은 층"으로 정했다. 2층 도메인 모듈의 이름(상태 열거, 검사기)을 import하는 비어댑터 모듈은 2층으로 선언했다. 경계 어댑터의 해석은 1층으로 나눴다(`formal` → `lean_evidence`, 저장 값 영역의 직렬화 → `canonical`). 작업 공간 도구의 명령행 진입점(`submission_tool`, `input_tool`)은 3층 모듈로 나눴다.
  - 셋째 단위: 작업자 셋(`cli_worker`, `codex_worker`, `claude_worker`), 공급자 어댑터 둘(`codex_adapter`, `claude_adapter`), `formal`을 3층으로 재분류하고, 경계 어댑터를 포트 구현 넷(`git_process`, `http_transport`, `system_clock`, `windows_job`)으로 줄였다. 순수한 해석과 어휘는 1층으로 나눴다(`codex_stream`, `claude_stream`, `http_request`, `scholarly`의 모양 규칙, `control_protocol`). 2층이 3층을 import하던 곳은 옮겨 고쳤다(`supervision`, `trace_report`, 운영자 깨움 등록, `scholarly_config`, `external`). 이때 "작업자의 요청 검사가 T3 관문 안에 든다"를 3층 선언의 이점으로 적었으나, 관문은 1·2층도 똑같이 덮으므로 이점이 아니었다.
  - 넷째 단위: 설계 원문과 합의 대화를 다시 읽고 첫 규칙의 적용 범위를 좁혀 현행 규칙 2가 되었다. `_call_steps` 절단의 판정 부분(준비, 시작 알림, 정지 판정, 결과 수신)은 2층 `call_engine`으로 옮겼다.
  - 다섯째 단위: `engine`의 판정을 2층 `core_engine`으로, `scheduler`의 판정(디스패치, 모델 선택, 정지와 상태 판정)을 2층 `dispatch_engine`으로 옮겼다. 3층에는 공개 진입점, 기본 구현의 조립, 소유자 루프만 남았다. 셋째 단위에서 3층으로 재분류한 나머지 모듈도 같은 기준으로 나눴다. 작업자의 요청 규칙과 명령 조립은 1층 `worker_request`, 수집기의 판정은 2층 `cli_execution`, 러너와 병렬 실행의 판정은 2층 `model_call`, `formal`의 순수 규칙은 1층 `lean_evidence`, 감독자의 판정은 2층 `supervision`, 설치 복구의 판정은 2층 `repair_execution`, CLI의 명령 계약은 2층 `cli_contract`로 갔다. 예약 포트의 실제 구현(`PowerShellScheduler`)은 경계 어댑터 `powershell_scheduler`로 떼어내 경계 어댑터가 다섯이 되었다. 예외 하나를 두었다: 예약 작업의 진입점 `operator_bootstrap`은 패키지 코드를 믿기 전에 스스로 검증해야 하므로, 판정을 제자리에 두고 3층으로 남긴다.
- A17 호스트 환경을 관찰하는 세 이음매는 1d에서 `Sim`의 대역과 함께 정한다: 설정의 Lean 명령을 비웠을 때의 Lean 탐색(`execution_profiles`가 `formal.discover_lean`을 부름), 신뢰 환경 검사의 도구 사슬 관찰(`trust_validation`이 `formal.toolchain_identity_errors`를 부름), 능력 탐침의 공급자 CLI 식별(`initialization.adapter_for`). 셋 다 2층이 3층의 관찰 코드를 부르는 방향 위반이다. `migration_defaults`에 함수를 하나 두고 그 안에서 3층 관찰 코드를 import하면 층 검사는 통과하지만, 그것은 빈 인자를 채우는 기본값이 아니라 import를 한 단계 숨기는 것일 뿐이다. 이음매의 모양(포트 연산이나 주입하는 관찰자)은 `Sim`이 가짜 호스트의 Lean, 도구 사슬, CLI 능력 증거를 어떻게 만드는지에 달렸으므로 그때 정한다. 그때까지 세 모듈은 `PENDING`에 이 사유로 남고, 1c는 이 셋만 남은 상태로 닫는다. 셋 가운데 첫째(Lean 탐색)는 엔진에도 호출 지점이 하나 더 있다. 2층 `core_engine`의 판정이 3층 `engine`의 `_lean_discovered`를 `self`로 부른다. import가 아니라서 층 검사가 보지 못하므로 여기에 적어 두고, 셋과 함께 1d에서 정한다. 1d에서 세 관찰과 이 호출 지점을 모두 호스트 관찰 포트로 옮겼다(A18).
- A18 호스트 관찰 포트(1d). A17의 세 관찰을 포트 하나의 연산 다섯으로 둔다: Lean 탐색(`discover_lean`), 도구 사슬 식별의 현재 관찰(`toolchain_identity_errors`), 공급자 CLI의 관찰 키·식별·명령 표면(`cli_observation_key`, `cli_identity`, `cli_describe`). 셋 다 호스트라는 바깥 자원을 읽으므로 포트의 뜻(2.2절)에 맞고, 포트 부류에 넣으면 양쪽 계약 시험과 완비 검사가 대역과 실제의 어긋남을 막는다. 2층 코드는 포트를 인자(`host`)나 `self.ports.host`로 받고, 엔진의 Lean 탐색도 2층 `core_engine`에서 포트를 부른다. 실제 구현 `LocalHost`는 병렬 실행 포트처럼 3층에 둔다(A11). 관찰 코드가 3층 모듈(`formal`, 공급자 어댑터)에 있고, 그것을 경계 어댑터로 옮기려면 `formal`의 Lake 프로젝트 식별 기구까지 옮겨야 한다. 그 이동은 시험의 실익 없이 구조만 흔든다. `LocalHost`는 관찰 코드를 모듈 속성으로 불러서, 그 이름을 패치하던 옛 시험이 그대로 닿는다. 이행 기본값은 두지 않았다. 2층은 3층의 실제 구현을 import할 수 없기 때문이다. 이것은 이행 중의 호출 규칙일 뿐 제품 동작의 변경이 아니다. 제품의 호출자는 모두 포트를 넘기고, 포트 없이 부르는 것은 옛 시험뿐이다. 그런 호출에서 프로필 조립(`build_profiles`)은 Lean을 탐색하지 않는다. 공개 진입점 `initialize`와 `control`은 `ports`를 받는다. `Sim`이 대역 묶음을 넘기는 자리다.
- A19 병렬 실행 대역의 차례 모형(1d). 1b의 결정적 대역은 호출을 소유자 스레드에서 끝까지 돌렸다. 그래서 결속된 역할의 작업자가 제출하고 영수증을 기다리면 그 요청을 처리할 소유자가 돌지 못해 멈췄다. 새 대역은 호출마다 스레드를 두되 소유자와 번갈아 하나씩만 돌게 한다. 전환은 두 자리에서만 일어난다. 하나는 시작 콜백이다. 제품처럼 소유자가 자기 스레드에서 실행하고 답한다. 다른 하나는 계산이 소유자를 기다리며 부르는 `owner_turn()`이다. 그 호출은 소유자의 다음 대기에서 다시 이어지므로 그 사이에 소유자 한 바퀴가 돈다. 대기는 준비된 호출 가운데 `choose`가 고른 것에 차례를 주고, 준비된 호출이 없으면 시계를 제한 시간만큼 움직인다. 모델 대역은 제출 뒤 영수증이 최종이 될 때까지 `owner_turn()`을 부른다.
- A20 계약 쌍의 역방향(1e). 3.3절의 처음 문언은 "수신 검사가 필수로 요구하는 필드마다 그 필드를 쓰는 생산자 분기가 있다"였다. 이 방향은 순방향(생산자 출력이 수신 검사를 통과한다)이 통과하면 저절로 참이어서 아무것도 더 확인하지 않는다. 이 의무가 겨냥한 결함(B-02)은 조건에 따라서만 요구되는 필드를 생산자가 만들지 않은 것이었으므로, 역방향의 대상을 수신 검사가 아는 필드 전체(필수와 선택)로 넓혔다. 이를 위해 작업자 요청 검사의 공급자별 필수·선택 필드를 모듈 상수로 올렸다(동작 같음).
- A21 입구 부류의 자리(1e). 3.3절의 처음 문언은 선언 위치를 제품의 `do_math/ingress.py`, 일반 시험을 `tests/structure/`로 두었다. 입구의 처리 함수와 소비 판정은 `Sim`과 대역이 필요한 시험 절차여서, 제품 쪽 표에는 이름만 남아 `control_contracts`의 목록을 되풀이하게 된다. 구조 층(T0)은 정적 검사의 자리다. 그래서 표와 잘못된 모양의 생성기는 `tests/support/ingress.py`에 두고, 일반 시험을 검사 함수의 층(단위)과 소유자 순회의 층(`Sim`)으로 나눴다. 구성원은 제품의 중앙 목록에서 생성한다. 1e 커널이 등록한 무리는 공개 제어 action, 제어 수송의 배달 파일, inbox 봉투다. 나머지 세 무리(작업 공간 제출과 중앙 수신, 공급자 사건 기록, 관찰 적용)는 같은 모양의 표와 시험으로, 1e·1f를 제품 영역별로 나눠 하는 병렬 작업(9.2절)에서 해당 영역이 등록한다.
- A22 저장 가족 쌍의 모양(1e). 저장 가족마다 모든 생산자의 표본을 등록하면, 생산자 대부분이 엔진 믹스인이라 표본마다 엔진 구동이 필요하고, 생산자 목록이 기계로 닫히지 않는다. 생산 분기가 실제 저장 검증을 지나는지는 저장 검증의 상시화(4.3절)와 T3 분기 도달 관문(의무 1-B)이 구조로 맡는다. 그래서 쌍 대신 제품 전체를 한 번에 보는 구조 검사 둘(`tests/structure/test_storage_fields.py`)을 둔다. 하나는 모든 수명 사건 기록 호출의 필드가 닫힌 사건 스키마 안에 있는지 본다. 다른 하나는 닫힌 가족의 스키마 필드를 스키마 모듈 밖의 제품 코드가 이름으로 쓰는지 본다. 둘째는 이름 수준이어서 흔한 이름의 생산자 부재를 잡지 못한다(11절).
- A23 T0 선택의 비교 기준(1e). 5.3절의 처음 문언은 T0이 `git diff`로 바뀐 행을 구한다고 했다. T3는 보통 커밋 전의 작업 트리에서 돌므로, HEAD 기준 diff의 행 번호는 색인이 측정한 행 번호와 어긋난다. 그래서 색인이 측정 때의 파일 내용(Git blob)을 기록하고, T0은 그 내용과 현재 내용을 비교한다. 색인의 오래됨 판정은 처음 문언대로 기록한 커밋이 HEAD의 조상인지로 한다. 색인은 Git이 추적하지 않으므로 worktree마다 따로 생기며, 새 worktree는 그곳에서 T3를 한 번 돌리기 전까지 모듈 단위 선택으로 돈다.
- A24 1f의 극단 변이 범위(1e 커널을 닫으며). 6.3절의 처음 문언은 하위 단계에서 바뀐 함수만 변이했다. 1f에서는 제품 코드가 거의 바뀌지 않으므로 이 범위로는 옮긴 시험이 경로만 지나는지 가려내지 못한다. 설계 6.3의 목적(관문을 채우려고 경로만 지나가는 시험을 잡음)이 1f에서 가장 필요하므로, 영역마다 그 영역 제품 모듈의 모든 함수를 변이한다. 옛 영역 시험이 죽인 변이체와 새 시험이 죽인 변이체를 비교하는 방식도 검토했으나, 선택 색인에 옛 시험이 없어 도구를 크게 늘려야 하고 비용이 두 배가 되어 버렸다. 새 시험만으로도 살아남은 함수마다 단언을 더하거나 사유를 적게 하면 같은 결함 부류를 막는다.
- A25 Git 객체 쓰기를 Git 포트의 연산으로 옮긴다(1f 시범 뒤 속도 단위, A14를 부분적으로 다시 엶). A14는 "파일 시스템은 포트가 아니므로 `git_store`가 객체를 직접 쓴다"로 정했다. 1f 시범에서 `Sim` 시험 시간의 약 3분의 2가 파일 시스템이었고, 그 중심이 Git 객체였다. 객체마다 `fsync`(한 시험 모듈 23개에서 1,926번, 5.2초), 템플릿 복원의 복사, 정리의 권한 변경과 삭제가 들었고, 복원된 인스턴스 파일의 79%가 객체였다. 객체 저장소는 일반 파일이 아니라 Git이라는 외부 자원의 형식이고, 포트는 이미 객체 읽기를 맡고 있었다. 그래서 `write_object(repository, kind, body)`를 포트에 더했다. 실제 구현은 `git_store`의 느슨한 객체 쓰기(압축, `fsync`, 읽기 전용 권한, 원자적 이름 바꾸기)를 그대로 옮긴 것이어서 제품 동작은 같다. 객체 폴더와 형식은 `describe`의 결과를 어댑터가 기억해 쓰므로, 게시가 git 프로세스를 더 띄우지 않는다(옛 `test_git_store`가 이를 지킨다). 대역은 쓴 객체를 Git 디렉터리별 메모리 사전에 두고, `Sim` 템플릿은 복원마다 그 사전의 사본을 넘긴다(객체는 바뀌지 않으므로 바이트는 공유). 포트 수정 절차대로 양쪽 계약 시험을 먼저 더해 실패를 확인했다. 효과: 시범 뒤의 `sim` 묶음이 108.4초에서 44.9초, T2가 130.9초에서 64.0초로 줄었다. A14의 나머지(`file_io`, 파일 시스템은 포트가 아님)는 그대로다.
- A26 흐름 폴더(1f 속도 단위 2). 6.1절은 시험 하나가 예산을 넘을 때의 첫째 허용 대응으로 "시험을 더 드문 층으로 옮긴다"를 둔다. 1f의 옮기기 묶음 여섯을 합친 뒤 T2의 시험 729개 가운데 2초 이상인 39개가 시간의 63%(372초 가운데 233초)를 썼고, 비용이 역할 호출 흐름을 끝까지 도는 몇몇 모듈에 몰렸다. 같은 비율이면 1f를 마쳤을 때 T2가 병렬로도 예산 300초를 넘는다. 그래서 시나리오 자체가 3층 시험의 예산보다 긴 모듈을 `tests/flows/`로 옮기고, 이 폴더를 T2에서 빼 T3와 기본 전체 실행에 넣었다. 첫 이동은 2초 이상 시험의 시간 비중이 75% 이상인 모듈 넷이다(엔진 흐름, 신뢰 수명, 초기 진단, 관찰 적용). 흐름의 회귀는 통합자가 작업자 분기를 합칠 때 T2와 함께 이 폴더를 돌려 잡는다. 대가는 작업자의 반복 확인(T2)에서 흐름 시험이 빠지는 것이며, 작업자가 자기 흐름 모듈을 따로 돌린다. 5절이 사용자 결정 절이지만, "개발 속도가 충분히 빠르도록 실행 일정과 시간을 합리적으로 배정"(U2)의 원칙을 더 잘 구현하는 개정이어서 U9에 따라 정했다. 같은 단위에서 T2의 병렬 묶음(5.4절이 정한 LPT)을 실행기의 `--jobs`로 구현했다. 효과(작업자 없는 main): T2 차례 약 420초 → 병렬 88.5초, 흐름 폴더 병렬 117초. T3는 분기 측정이 한 프로세스를 전제해 차례로 돌며, 흐름을 더하면 예산 12분을 넘을 수 있다(11절).

## 11. 남은 한계와 미결정

- 동작 보존 판정은 옛 모음의 강도에 묶인다(9.3절).
- 결함 동작을 정답으로 적은 시험은 기계 검사로 잡히지 않는다(6.4절).
- 시간 예산 수치는 1d에서 새 체계의 첫 시험으로 측정해 확인했다(5.2절). 1e·1f에서 시험이 늘면 실행 층 전체 시간을 다시 본다.
- 공개 경로 시작 상태는 약 7초가 들어 템플릿 복원을 되살렸다(4.4절).
- `nat-add-zero-20260927-01` 인스턴스는 2단계에서 저장 계약 판본이 오르면 새 판본으로 재개할 수 없다. 재개가 필요하면 그 전에 사용자에게 묻는다.
- T3의 분기 측정은 러너 프로세스 안의 코드만 본다. 자식 프로세스에서 실행된 제품 코드는 관문과 색인에 잡히지 않는다. 지금의 새 체계 시험은 모두 프로세스 안에서 돌지만, 자식 프로세스를 쓰는 새 시험이 생기면 그 코드의 도달은 따로 확인해야 한다.
- T3는 분기 측정 때문에 한 프로세스로 돌고, 흐름 폴더(A26)가 들어가 예산 12분을 넘을 수 있다. 커버리지의 병렬 측정(자식 프로세스마다 측정해 합침)이 다음 과제다.
- 저장 한 번에 상태 전체를 두 번 깊이 복사한다(호출자와 저장소 캐시를 떼어 냄). 상태가 클수록 매 저장에 들며, 시험의 흐름 비용과 제품의 실행 속도에 함께 걸린다. 2단계 후보다.
- 저장 필드의 생산 검사(A22)는 필드 이름이 제품 코드 어디에든 쓰이면 생산된 것으로 판정하므로, 흔한 이름을 가진 필드의 생산자 부재를 잡지 못한다.
- 입구 부류는 중앙 목록 밖의 입구를 완전하게 찾지 못한다. 목록 밖 입구의 반려 분기를 다른 시험이 실행하면 미등록이 드러나지 않는다(3.3절).
- 결함 범주의 검산에서 시험 의무로 잡히지 않는 기록이 하나 있다(B-20, 운전 AI가 잘린 문서를 전문으로 여긴 절차 문제). 소프트웨어 시험 대상이 아니며 의무 13-C가 발생 조건만 경고한다.
