## 요지

1. **외부 프로그램 호출은 소수의 병목 함수에 모여 있다.** 하위 프로세스를 띄우는 지점은 14곳이다. 그 가운데 do-math 수명 주기에서 반복해서 도는 경로는 다섯 병목을 지난다. 저장소의 git 호출(`GitStateStore._git`), Windows Job 생성(`WindowsJob._create_suspended_root`의 `CreateProcessW`), Job 안 작업자의 공급자 CLI 실행(`cli_worker.run_cli`), Lean 실행(`formal._job_run`→`formal._worker`), 예약 운영자의 세 지점(`scheduled_operator.schedule`, `run_engine`, `recovery`)이다. 네트워크 호출은 `external._http` 하나로 모인다(부트스트랩 `setup_lean` 제외).
2. **포트 후보의 뼈대는 이미 있다.** `ResearchEngine`은 `runner`와 `formal_verifier`를 생성자로 받는다. `store`, `_transport`, `lifecycle_clock`, `lifecycle_monotonic`은 속성으로 교체된다. 시험도 이 이름들에 가장 많이 기댄다(8번). 반면 `scheduled_operator.schedule(runner=)`과 `external.execute_operation(transport=)`의 주입 인자는 제품도 시험도 쓰지 않는다. 시험은 이 두 경로에서 인자 대신 `subprocess.run`과 `_http`를 패치한다.
3. **3층의 외부 효과를 포트 뒤로 보내려면 주입되지 않는 협력자 셋을 먼저 다뤄야 한다.**
   - 시계와 ID가 앰비언트하게 쓰인다. `file_io.now`는 66개 함수, `repository.new_id`는 64개 함수, `governance.timestamp`는 22개 함수가 직접 부른다. `time.monotonic`·`time.time`·`time.sleep`도 엔진·스케줄러·세션 슬롯에서 직접 불린다.
   - 저장소의 읽기와 쓰기가 모두 git 자식 프로세스를 띄운다. 그래서 상태를 적재하거나 게시하는 엔진 함수는 모두 프로세스 효과를 갖는다.
   - `ModelCalls` 스레드 풀, 엔진의 `ObservationTracker` 시계, 운영자 복구의 `ModelRunner()`는 호출 지점에서 직접 생성된다.
4. **효과 분류는 c(프로세스·시간·OS 효과 포함)가 크다.** 1,419개 함수 가운데 순수(a)는 738, 파일·저장소 효과만(b)은 76, c는 544, 판정 불가(d)는 61이다. c 가운데 171개는 시계·난수만으로 c가 되었다. 반사실 계산에서 시계·ID 도우미와 저장소, 러너·어댑터·Job·Lean·스레드·추적·전송을 포트로 끊으면 c는 166까지 줄어든다(3.4절).
5. **시험 대체는 1,174건이다.** 시험 모듈 100개에서 제품 이름 302종을 바꾼다. 가장 많은 목적은 엔진 내부 메서드 대체(265건)와 엔진 메모리 상태 주입(224건)이다. 저장(180건), 프로세스·OS(135건), 모델 호출(128건)이 그 뒤를 잇는다. 포트 대역 방식으로 흡수될 수 있는 쪽은 저장·프로세스·모델·시계·네트워크 대체다. 엔진 내부 메서드 대체는 포트와 무관하게 남는다(8번).

## 방법과 한계

추출은 `extract.py`가 제품 모듈을 import하지 않고 `ast`로만 읽어 수행했다. 부류별 호출 판정, 호출 그래프 해석, 효과 분류는 다음 규칙을 따른다.

**이름 해석.** 모듈 수준 import 별칭, 함수 안 import, 상대 import를 해석한다. 작업자 스크립트가 패키지 없이 쓰는 맨 이름 import(`from file_io import …`)는 `do_math.file_io`로 해석한다. 호출 간선은 다음 순서로 해석한다.

1. 같은 모듈 함수와 import한 제품 함수로 해석한다.
2. `self.메서드`는 그 클래스를 MRO에 담는 말단 클래스의 MRO에서 찾는다. 그래서 믹스인 안의 `self._save`는 `ResearchEngine._save`로 해석된다.
3. `self.속성.메서드`는 클래스 안에서 그 속성에 대입된 생성자 호출로 속성 형을 추론해 찾는다. 예를 들어 `self.store = ResearchRepository(…)`에서 `self.store`의 형을 얻는다.
4. 지역 변수와 인자는 생성자 대입과 형 주석으로 형을 추론한다.
5. 여기까지 해석되지 않은 속성 호출의 메서드 이름이 제품 클래스에 정의되어 있으면, 그 이름을 가진 모든 제품 메서드로 간선을 둔다. 이것이 이름 기반 클래스 계층 근사(CHA)이며 간선 117개, 호출 지점 102곳이다.

**해석 불가 간선.** 115개가 남았다. 종류별로는 인자로 받은 호출 가능 객체 57, 해석 못 한 메서드 이름 33, 식으로 정해지는 호출 대상 9(`(transport or _http)(…)`, `handlers[kind]["apply"](…)` 등), `self.속성` 호출 가능 객체 8, 지역 호출 가능 객체 7, 미바인딩 이름 1이다. 해석된 간선은 4,017개다. 내장 메서드 이름과 제품 메서드 이름이 겹쳐 내장으로 가정한 약한 간선이 9개 더 있다.

**휴리스틱.** 수신자 형을 모르는 속성 호출은 이름과 수신자 모양으로 판정했다.
- `Path` 메서드: `write_text`, `mkdir`, `resolve`, `exists` 등.
- 파일 스트림 메서드: 수신자 이름에 `stream`, `handle` 등이 들어간 `.write`, `.read`.
- 프로세스 메서드: `.communicate`, `.kill`.
- 동시성 메서드: `.set`, `.result`, `.wait` 등.

2번 표의 "휴리스틱" 열이 이렇게 판정한 지점의 수다. `Path.resolve`처럼 파일 시스템을 조회하는 순수해 보이는 호출도 fs_read로 셌다. `reporting.timeline_csv`는 `csv` 작성기의 `writerow`가 fs_write로 잡혔지만, 원문에서는 메모리 버퍼에 쓴다. 이런 거짓 양성이 fs 부류에 섞여 있다.

**효과 분류.** 부류 가운데 subprocess, winapi, clock, concurrency, network, env, random, os_misc 가운데 하나라도 전이적으로 닿으면 c로 분류했다. c가 아닐 때 해석 불가 간선에 닿으면 d, fs_read·fs_write·stdio만 있으면 b, 아무 효과도 없으면 a다. 전이 효과는 해석된 간선과 CHA 간선을 따라 고정점까지 전파했다. c는 해석 불가와 무관하게 확정된다. 해석 불가 간선이 효과를 더할 수는 있어도 뺄 수는 없기 때문이다. CHA는 과대 근사다. 그래서 CHA 간선을 해석 불가로 돌린 판본도 함께 계산했다(3.1절).

**양성 대조.** 부류마다 원문 grep으로 확인한 알려진 호출이 결과에 잡히는지 확인했다. 결과는 다음 표와 같다. 네트워크처럼 건수가 적은 부류는 합성 표본 파일(`socket`, `urllib.request`, `http.client`, `os.environ` 쓰기, `ctypes.windll`, `msvcrt` 등)로 추출기가 대상을 찾는지 먼저 확인했다. 합성 표본의 아홉 부류는 모두 기대 건수 이상이 잡혔다. 건수가 0인 부류는 없다.

### 1.2 엔진 공개 표면

`cli`는 엔진을 두 형태로 쓴다. 하나는 모듈 함수이고, 다른 하나는 `ResearchEngine` 인스턴스 메서드다.

- **모듈 함수**: `initialize`(`engine.py:149`), `control`(`engine.py:252`), `query_records`(`engine.py:379`), `read_record`(`engine.py:429`).
- **생성자**: `ResearchEngine.__init__`(`engine.py:446`)은 저장소를 열고 상태를 적재한 뒤 `ControlTransport`를 만든다.
- **메서드**: `run`, `status`, `process_controls`, `control_result`, `check`가 CLI에서 불린다. `governance_owner_handlers`(`governance_engine.py`)는 CLI의 `prepare-import-approval`이 부른다.

실행 루프는 `run` → `_run_executor`(`engine.py:1465`) → `SchedulerMixin._run_parallel`(`scheduler.py:277`)이다(4번). 다른 호출자로는 예약 운영자의 `scheduled_operator.read_status`(`scheduled_operator.py:218`)가 있다. 이 함수는 `ResearchEngine(...).status()`를 함수 안 import로 부른다.

### 3.3 c를 만드는 원인

c 함수 544개의 전이 효과 조합 가운데 가장 흔한 것은 다음과 같다. 시계+난수 94, 시계 71, 시계+병행+환경+난수+하위 프로세스+Windows API 57, Windows API 54, 여기에 프로세스 정보가 더해진 조합 50이다. 효과 부류별로 그 효과에 전이적으로 닿는 함수 수는 다음과 같다.

| 부류 | 닿는 함수 수 |
|---|---|
| clock | 411 |
| fs_read | 405 |
| winapi | 341 |
| random | 281 |
| fs_write | 218 |
| env | 199 |
| subprocess | 189 |
| concurrency | 137 |
| os_misc | 98 |

이 분포를 만드는 원인은 셋이다.

### 4.3 실행 루프와 작업자 기동·회수의 위치

- **실행 루프**: `ResearchEngine.run`(:1457)이 `_executor_running`을 켜고 `_run_executor`(:1465)를 부른다. `_run_executor`는 쓰기 잠금 아래에서 적재·제어·복구·초기화 활성화·게시를 한 뒤 `SchedulerMixin._run_parallel`(`scheduler.py:277`)을 부른다. `_run_parallel`은 `ModelCalls`를 **직접 생성**한다(`scheduler.py:281`). 매 회전마다 다음을 수행한다.
  - 정지 판정: `_settle_stops`
  - 제어: `_controls`
  - 반환 수거: `self._calls.collect()`
  - 설치 확인: `_check_installation`
  - 준비 갱신: `_refresh_readiness`
  - 배정 가능 판정: `_dispatchable`
  - 대기: `self._calls.wait(OWNER_POLL_SECONDS)` 또는 `time.sleep(OWNER_POLL_SECONDS)`
- **AI 작업자 기동**: `_run_parallel`이 `_call_steps(action)` 생성기를 한 단계 진행해 러너 인자를 얻는다. 그다음 `self._calls.start_call(generator, self.runner.run, arguments, …)`(`scheduler.py:363`)으로 스레드에서 `ModelRunner.run`을 돌린다. 이 호출은 여러 단계를 거쳐 외부 프로세스에 닿는다.
  1. `ModelRunner.run`이 공급자 어댑터를 고른다(`model_runner.py:49`).
  2. `LocalCLIAdapter.start`(`codex_adapter.py:181`)가 `WindowsJob`(`:213`)으로 `python codex_worker.py`나 `claude_worker.py`를 띄운다.
  3. 작업자는 Job 안에서 공급자 CLI를 `Popen`한다.
  4. 공급자 CLI는 제어 MCP 서버(`control_transport.py mcp`)를 띄운다.
- **기계 작업 기동**: 형식 검사는 `FormalEngineMixin._formal`(`formal_engine.py:309`)이 맡는다. 신뢰 검사·활성화(`:136`, `:206`)도 같은 경로를 쓴다. 이들은 `SchedulerMixin._run_machine_steps`(`scheduler.py:103`)를 거쳐 `ModelCalls.start_call(generator, calculator or self.formal_verifier, …)`로 돈다. 계산 함수는 `trust_validation.verify_formal`이다. 이 함수가 `LifecycleEngineMixin._lean_machine_call`(`lifecycle_engine.py:~720`)이 넘긴 `verifier=self.formal_verifier`를 부르고, 그 끝에서 `formal.verify_lean` → `_job_run` → `WindowsJob` → `formal._worker` → Lean `Popen`에 닿는다. 외부 HTTP 작업은 `ExternalEngineMixin._run_external_action`이 `external.execute_operation`을 부른다.
- **회수**:
  - 스레드 반환은 `ModelCalls.collect`(`parallel.py:167`)가 소유자 스레드에서 거두고, `on_returned=self._local_call_returned`(`scheduler.py:32`)를 부른다.
  - 생성기는 `result = yield arguments`(`engine.py:3311`)로 러너 결과를 받아 `_call_steps` 후반에서 제출을 수신한다.
  - 실행 중 관찰은 러너의 `on_observation` 콜백을 거쳐 `_observe_running`(`engine.py:2672`)이 추적기에 적용한다.
  - 제출된 결과는 `_collect_submitted_result`(`:2781`)와 `_capture_native_submission`(`:2843`)이 거둔다.
  - 재시작 뒤에 사라진 실행은 `_recover_disappeared`(`:1510`)가 처리한다. 이 함수는 `launch`의 발사표와 `windows_job.named_job_empty`·`owner_ended`로 로컬 종료를 확인한다.
  - 예외가 나면 `_abort_parallel_calls`(`scheduler.py:113`)가 호출을 정리한다.
- **관찰 추적기**: `_call_steps`가 `ObservationTracker(execution_id, workspace, observation_config)`(`engine.py:3214`)를 시계 인자 없이 만든다. 따라서 엔진 경로의 추적기는 기본값 `time.monotonic`을 쓴다.

### 4.4 `_init_process_state`가 초기화하는 프로세스 한정 상태

`_init_process_state(self, *, transport=None)`(`engine.py:454-480`)는 저장소가 담지 않는 소유자 상태를 만든다. 문서화 문자열에 따르면 저장소 없이 만든 시험 엔진도 이 함수에서 시작한다.

- 준비와 실행: `_task_readiness`, `_live_execution_ids`, `_executor_running`, `_calls`(None, `_run_parallel`이 채움), `_preparing_input`.
- 설치 확인 주기: `_next_installation_check`, `_next_lean_discovery`, `_lean_found`.
- 제어 전송: `_transport`(인자), `_transport_bindings`, `_feedback_delivered`.
- 관찰: `_trackers`.
- 정지와 시계: `_stop_deadlines`, `_stop_clock`, `_clock_anchor`, `_clock_failure`, `lifecycle_clock`(None이면 벽시계), `lifecycle_monotonic`(`time.monotonic`).
- 메모: `_retrying_publication`, `_goal_audit_contract`, `_goal_basis_memo`, `_scan_head`, `_scan_at`.

`cached_property`로 첫 사용 때 채워지는 `_documents`와 `_installation`도 프로세스 한정 상태다.

### 7.3 시안에서 드러난 구조상 사실

- **2층의 대부분이 엔진 믹스인 메서드다.** 믹스인은 `self.store`와 `self._save`를 직접 부른다. 따라서 저장 포트는 모듈 함수 인자가 아니라 엔진 객체의 속성이다. 믹스인 메서드를 개별로 시험하면 엔진 객체(또는 그 대역)가 필요하다.
- **1층 후보 모듈의 순수성을 막는 것은 주로 시계·ID다.** 1층 후보 모듈(7.1 표의 첫 두 행)의 c는 두 함수를 빼면 모두 `now`, `new_id`, `timestamp`와 직접 `datetime.now` 두 곳에서 온다. 두 함수는 저장소를 읽는 `academic.stored_evidence`와 호스트 이름을 읽는 `governance.register_configuration_owner`다.
- **경계 어댑터 모듈은 모두 순수 해석 함수를 함께 담는다.** 경계 어댑터 모듈은 `codex_adapter`, `formal`, `git_store`, `windows_job`, `file_io`, `cli_worker`다. 순수 해석 함수에는 출력 해석, 형식 검사, 경로 규칙, 자원 한도 검사가 있다.

## 8. 시험이 기대는 이음매

대상은 `scripts/tests/`의 파이썬 파일 131개(`*_fixtures.py` 9개 포함)다. 추출 방식은 다음과 같다.

- **추출한 호출**: `patch`(문자열 대상), `patch.object`, `patch.dict`, `patch.multiple`, `monkeypatch.setattr`, `create_autospec`, `setattr`, 속성 대입(`X.attr = …`)이다.
- **속성 대입의 인정 범위**: 수신자가 제품 모듈·클래스이거나, 대입하는 속성 이름이 제품 클래스의 메서드나 인스턴스 속성인 경우만 셌다. 시험 객체 자신의 `self.x = …`는 제외했다.
- **반복문 안의 동적 이름**: `for name in (…): setattr(engine, name, …)`처럼 이름이 반복문 리터럴로 정해지면 이름마다 펼쳤다.
- **`create_autospec`의 계산**: 대입이나 `setattr`의 값으로 쓰인 `create_autospec`은 그 대입 한 건으로 셌다. 독립 사용 18건만 따로 셌다.

### 8.1 합계

- 대체 행 1,174건, 바뀌는 제품 이름 302종, 대체가 1건 이상인 시험 모듈 100개다.
- 기제별로는 속성 대입 609, `patch.object` 283(+반복 펼침 4), `patch` 194, `setattr` 반복 펼침 52와 직접 2, 독립 `create_autospec` 18, `patch.dict` 10이다. `monkeypatch`와 `patch.multiple`은 0이다.

### 8.4 설계 후보와 맞댄 관찰

- **포트 대역과 겹치는 대체**: 러너(`runner` 43, `ModelRunner.run` 9, `ModelRunner` 7), 형식 검사기(16), 저장(`store` 29, `_save` 39, `ResearchRepository` 33), 수명 주기 시계(13+11)는 이미 주입 지점 이름을 바꾼다. 포트 대역 방식과 같은 방향이다.
- **주입 인자가 있는데 쓰지 않는 대체**: `scheduled_operator.subprocess.run` 9건은 `schedule(runner=)` 인자를 두고 모듈 속성을 바꾼다. `external._http` 11건도 `execute_operation(transport=)` 인자를 두고 모듈 함수를 바꾼다.
- **주입 지점이 없어 패치하는 대체**: `formal._job_run`(14), `windows_job.named_job_empty`(17), `GitStateStore._git`(11), `initialization.adapter_for`(41), `scheduled_operator.read_status`(19)와 `schedule`(14), `file_io.RACY_NS`(10). 이 이름들은 모두 5번의 "주입되지 않는 협력자"이거나 그 호출자다.
- **포트와 무관한 대체**: 엔진 내부 메서드 265건과 도메인 함수 90건은 외부 자원이 아니라 제품 논리의 일부를 끊는다. 상태 주입 224건은 저장 포트 대역(메모리 저장소)이 있으면 게시된 상태로 대신할 수 있는 몫과, 시험이 상태를 직접 조작하는 몫이 섞여 있다. 이 문서는 두 몫을 가르지 않았다.
