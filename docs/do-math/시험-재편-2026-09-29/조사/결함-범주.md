### 2.1 영향: 결과와 근거의 두 축

영향은 두 축으로 적는다. 결과 축은 결함이 발동했을 때 무엇이 일어나는가이고, 근거 축은 그 결함이 실제로 발현한 것을 무엇으로 확인했는가다. 운전에서 발현하지 않은 결함도 발동했을 때의 결과로 적고, 발현 여부는 근거 축에 담는다. 그래서 원 서식의 `잠재`는 결과 값이 아니다. 원 판정이 잠재였던 두 기록(B-13, B-15)은 발동했을 때의 결과인 저하로 적었다.

**결과 축의 값.**

- **인스턴스 정지**: 사람의 개입 없이는 인스턴스 전체가 더 전진하지 못한다. 실행기의 비정상 종료나 같은 원인의 반복 종료, 상태 게시의 전건 거부, 초기화 미완료, 전역 관문(신뢰 전환, 설치 수리 대기, 예산 상태, 제어 수송)의 영구 차단이 여기에 든다. 목표 달성에 반드시 지나는 공통 경로(모든 지식이 지나는 동일성 검토, 목표 감사, 형식 검사 전건)가 현실적인 입력 전반에서 막히는 경우도 든다.
- **과제 정지**: 사람의 개입 없이 풀리지 않는 멈춤이 특정 과제·지식·의무·대기 항목에 국한되고, 다른 작업은 진행한다.
- **저하**: 인스턴스는 진행하지만 결과가 틀리거나, 자료를 잃거나, 비용·시간이 늘어난다. 예약 운영 AI가 정상 업무(진단 요청, 재관찰)로 푸는 멈춤도 저하다.
- **무해**: 연구 인스턴스의 동작에 영향이 없다. 문서 불일치, 호출되지 않는 경로, 시험 기반 자체의 결함이 여기에 든다.

**경계 판정 규칙.** 담당들의 판정이 갈린 경계는 다음 규칙으로 맞췄다.

1. **운영 AI의 개입.** 예약 운영 AI가 정상 업무로 푼 멈춤은 저하다(A-24). 운영 AI가 스킬 코드를 고쳐야 풀린 멈춤은 정지다(A-08). 두 판정 모두 담당 A의 판단을 따랐다.
2. **조건부 발동.** 선택 설정이나 특정 환경에서만 발동하는 결함은 발동했을 때의 결과로 적고, 조건을 비고에 적는다. 해당 기록은 Claude 공급자 프로필(B-46), PATH로 찾은 Lean(B-49), 비ASCII 학술 요구 ID(B-41), `claude_only_assigned_model` 설정(B-35), 정비 fence(C-16)다. 기본 설정에서 결과가 다른 B-37은 발동 조건에서의 결과(과제 정지)를 쓰고 기본 결과(저하)를 비고에 적었다.
3. **전파 끝 미확정.** 예외가 실행기를 끝내는지 과제만 막는지 원자료가 확정하지 않으면, 확정되는 가장 좁은 멈춤으로 적는다(B-33, B-48 → 과제 정지). C-27은 과제 단위의 해석이 없다. 제어 수송 전체가 같은 요청에서 반복 실패하므로 A-02와 같이 인스턴스 정지로 적고, 전파 끝 미확정을 비고에 남겼다.
4. **경로 단위의 멈춤.** 과제 하나의 영구 대기는 과제 정지다(B-38, B-42, C-08). 담당 B가 지적한 조사자 사이의 불일치(B 관찰 4.5)는 이 규칙으로 해소된다.

**근거 축의 값.**

- **운전 관측**: 결함이 실제 운전에서 발현했다. 실제 모델로 연구 인스턴스를 초기화·운전하는 경우와, 구현 중의 실제 실행(실제 CLI, 실제 자식 프로세스, 실제 예약 probe)이 여기에 든다. 결과 등급의 판정에 코드 추적이 섞이면 비고에 적었다.
- **재현**: 결함이 시험, 재현 스크립트, 실행에서 실제로 발현했으나 연구 운전에서는 발현하지 않았다.
- **추론**: 발현하지 않았고, 코드 경로 추적으로 판정했다.

### 2.4 재판정의 표시와 재판정하지 못한 것

원 판정 `정지`를 인스턴스 정지와 과제 정지로 나눈 것은 값의 세분이다. 그래서 표에서 원 판정을 따로 적지 않는다. 원 판정과 결과가 다른 재판정은 네 건이며 표에 "(원 …)"으로 적었다.

- **C-03: 정지 → 저하.** 제어 통로로 온 자기 점검 응답과 안전 경계 제출이 모두 거부됐다. 그러나 담당 C의 기록 자체가 "연구 수행 자체는 이어졌다"고 적는다. 거부의 결과는 의무 셋이 열린 채 남고 운영 점검 계보가 열린 것이다. 서식의 "필수 역할 출력의 전건 거부"는 역할 실행의 산출을 말한다. 자기 점검 응답은 역할 산출이 아니라 제어 메시지이므로 그 예시에 들지 않는다.
- **A-13: 정지 → 저하.** 예약 운영 CLI가 bytes가 든 영수증을 JSON으로 쓰지 못했다. M-0295는 이를 "실제 예약 probe에서 관찰"했다고 적는다. 연구 엔진이 멈췄다는 기술은 원자료에 없다. 운영 감독 경로의 실패로 보아 저하로 적었다.
- **B-13: 잠재 → 저하.** 정본에서 사본을 다시 만들면 운전 중 수리가 사라지고, 수리 전의 느림이 돌아온다.

이 기록들은 원 판정을 쓰되, 담당이 적은 결과 기술(예: "과제가 멈춘다", "실행기가 매 run 같은 예외로 멈춘다")에 따라 인스턴스 정지와 과제 정지로만 나눴다.

## 5. 범주별 절

각 절의 "구성 기록" 표에서 결과·층·유출 원인 칸의 "(원 …)"은 재판정 전 담당의 값이다. "포착 등급"은 2.7절의 등급이다. "검증런" 칸의 값은 다음 뜻이다.

- 범위 안 놓침: 결함 코드가 그 검증런의 독해 범위에 있었으나 찾지 못함.
- 검증런이 찾아 적용: 결함이 검증런에서 발견되어 반영됨. 앞선 검증런이 놓친 경우를 포함한다.
- 찾았으나 기각: 검증런이 지적했으나 수리안이 기각됨. 뒤에 다른 경로로 반영됐을 수 있다.
- 해당 없음: 검증런 전에 발견·수리됐거나, 검증런 뒤에 들어왔거나, 정적 감사·시험 실행이 발견함.

### 5.1 생산자와 수신자의 모양 불일치

**기제.** 한 구성요소가 만든 값을 다른 구성요소가 받거나 저장할 때, 두 쪽이 기대하는 모양이 다르다. 모양에는 필드 집합, 자료형, 값 영역, null의 처리, 순서가 들어간다. 생산자와 수신자는 모두 do-math 코드이거나, 생산자가 외부(공급자 사건, 사용자 입력)이고 수신자가 내부 저장 계약이다. 결함은 생산자의 특정 분기가 실제로 실행될 때 활성화된다. grant 없는 외부 요청(C-17), Claude 공급자 프로필(B-46), 목표 근거가 바뀐 뒤의 무효화(C-22), 관계 주장이 있는 지식(B-34)이 그 예다. 형태는 일곱이다.

- (a) 닫힌 저장 스키마 대 생산자 필드: B-34, B-46, C-03, C-17, C-22.
- (b) 수신자가 요구하나 생산자가 만들지 않는 필드·값: B-02, B-41, C-25.
- (c) 명시 null 대 키 부재: B-48, C-21.
- (d) 외부 값 영역 대 저장 정규화기: B-45, A-13.
- (e) 코덱·저장 왕복: B-30, B-28, B-40.
- (f) 공유 가변 노드: C-23.
- (g) 요청 생산자 대 작업자 수신 스키마: B-35.

**시험 의무.**

- **1-A 실제 생산자 → 실제 수신 검사.**
  - 모집단: 코드 안의 모든 (생산자, 수신 검사) 쌍. 지금 확인된 쌍은 여섯 종류다. ① 저장 가족 × `StateContract` 검증, ② 작업자 요청 조립(`ModelRunner`, `CodexModelRunner`) × `codex_worker.load_request`와 Claude 작업자의 요청 검사, ③ 신뢰 manifest 조립(`setup_lean`) × `trust_environment_errors`, ④ 관찰 추적기의 기록 × 저장 스키마, ⑤ 조건 문법의 상태 어휘 × 저장 스키마 enum, ⑥ 러너 결과 영수증 × JSON 출력.
  - 입력: 손으로 만든 fixture가 아니라 실제 생산자 함수의 출력. 생산자의 입력은 분기마다 하나 이상이다. 설정 불리언 선택지 전건, 공급자 전건, 관계 다중도 0·1·여럿, 선택 필드 있음·없음을 포함한다.
  - 성질: 생산자 출력이 수신 검사를 오류 없이 통과한다. 역방향으로, 수신 검사가 필수로 요구하는 필드마다 그 필드를 쓰는 생산자가 하나 이상 있다.
  - 층: 1층(스키마·검사기)과 2층(생산 함수).
- **1-B 저장 대역의 검증 보존과 쓰기 분기 도달.**
  - 모집단: 시험이 쓰는 모든 저장 대역(`StateStore`, `NoRepository`, `_save` 대체, `ReviewFakeEngine`의 저장, `Host._save`).
  - 성질: 대역도 게시 시점에 실제 `StateContract` 검증을 실행하고, 검증 실패를 시험 실패로 드러낸다. 저장 가족에 필드를 쓰는 생산 분기마다, 이 검증이 켜진 시험이 최소 하나 지난다. 판정은 쓰기 지점 단위의 분기 커버리지로 한다. 검증이 켜진 시험이 한 번도 실행하지 않은 쓰기 지점이 0이어야 한다.
  - 층: 2층 저장 인터페이스(포트)의 인프로세스 대역.
- **1-C 값 영역과 null 경계.**
  - 모집단: 외부·사용자·모델 값이 저장·해시·직렬화로 들어가는 경계(공급자 사건, 사용자 학술 요구 ID, 러너 영수증, 모델 확장 필드)와, 생산자가 명시 null을 쓰는 모든 필드.

### 5.2 반려 경계 밖 예외와 처리 불능 항목의 반복

**기제.** 소유 루프(엔진 실행 루프, 제어 수송 pump, 관찰 적용, 제출 검사)가 처리할 수 없는 입력이나 상태를 만나면 두 가지 가운데 하나가 일어난다. 반려 경로가 잡지 않는 종류의 예외(`AttributeError`, `IndexError`, `UnboundLocalError` 등)가 루프 밖으로 새어 실행기가 죽는다. 또는 그 항목을 반려·소비하는 분기가 없어 항목이 그대로 남는다. 어느 쪽이든 항목이 소비되지 않으므로, 재시작해도 같은 항목에서 같은 실패를 되풀이한다. 원인은 세 무리다.

- (a) 모양을 확인하기 전에 타입 의존 연산을 한다: B-29, B-43, B-44.

### 5.3 한 규칙의 사본 분기(광고·입력·관문·분류)

**기제.** 같은 판단이나 같은 허용 집합을 두 곳 이상이 따로 계산하거나 서술한다. 한쪽이 바뀌거나 처음부터 다르게 쓰이면, 한 곳이 약속한 것을 다른 곳이 거부한다. 세 형태가 있다.

- (a) **광고 대 수락.** 역할 입력, 출력 스키마, 오류 안내가 모델에게 알린 것과 수신 검사가 받는 것이 다르다: A-04, A-10, A-28, B-08, B-42, C-06, D-01. 모델에게 필요한 어휘(대상 상태, 정확한 ID, 허용 참조, 누락 자료를 지목하는 형식)를 입력이 광고하지 않거나, 수신 검사가 광고된 원소를 거부한다.
- (b) **역할 계약 대 입력 생산자.** 역할 계약 문서가 판단 근거로 요구하는 자료를 입력 생성기가 싣지 않는다: A-05, A-35, B-07.
- (c) **관문 대 관문, 분류 대 분류.** 같은 조건을 두 관문이나 두 분류기가 다르게 판정한다. 해당 기록과 사본은 다음과 같다.

### 5.5 판정 근거의 범위 오설정

**기제.** 현재성, 완료, 검토 개설, 신뢰 검증 같은 판정이 보는 사실의 범위가 판정의 의미와 다르다. 어긋남은 세 방향이다.

- **범위가 넓다(과잉).** 관리 정보의 변화가 판정을 무효화한다. A-25는 인용 기록 전체를 해시했다. B-09는 검토 계보 ID와 형식 수락 표지까지 해시했다. A-36에서는 형제 과제의 승인이 실행 중 검토의 기준 키를 바꿨다.

- **시점이 틀리다.** 입력 시점에 정당했던 근거를 적용 시점 기준으로 다시 판정한다. C-07이다.

활성화 조건은 두 가지다. 병렬 실행이 흔해져 판정 도중 인용 기록이 바뀌는 것(A-25, A-36, C-07)과, 실제 규모의 입력(B-14)이다. fixture가 결함 패턴을 정상으로 담은 경우가 많다. B-14·B-15의 `trust_fixture`는 합성 파일 여섯 개와 자유 문자열 증거로 manifest를 만들었다. B-09의 시험은 과잉 무효화를 기대값으로 단언했다.

### 5.6 시간·기한 규칙의 적용 국면 오류

**기제.** 타이머, 기한, 유예, 관찰 창이 실행의 엉뚱한 국면에 적용되거나, 사건이 일어난 시각 대신 처리한 시각으로 판정한다. 국면은 입력 준비 중, 모델 시작 전, 도구 실행 중, 응답 전의 새 도구, 종료 뒤, 종료 뒤 밀린 사건의 재생이다. 사례는 일곱이다.

- A-37: 작업 예산 실행에 운영 호출 기한을 적용했다.
- A-19: 모델 시작 전 정지에 체크포인트 유예를 적용했다.
- A-26: run 기한 직전에 착수했고, 기한을 작업자에게 전달하지 않았다.
- A-27: 선언 timeout 안의 도구 대기를 경과 시간만으로 점검했다.
- B-06: 늦게 처리한 과거 사건을 새 행동으로 판정했다.
- C-04·C-05: 도구 실행 중 열린 자기 점검 의무의 기한이 틀렸다.

시험은 짧은 run과 짧은 대역 작업을 썼다. 그래서 기한 도래 시점의 진행 중 실행, 도구 실행 중의 의무 개설 같은 국면 조합이 만들어지지 않았다(A-26, C-05). A-27에서는 타이머 동작을 기대값으로 고정한 시험이 있었다.

### 5.7 전이 순서·조합에서 깨지는 상태 불변식

**기제.** 각 전이는 따로 시험되어 옳지만, 특정 순서나 조합에서 전역 불변식이 깨진다. 불변식은 세 무리다.

- (a) **사용자·운영 제어의 우선.** 사용자 정지가 후속 처분에 덮인다(A-06). 종결 인스턴스가 다시 열린다(A-03). HOLD 해제와 정지 적용이 경합한다(A-15). 정비 정지가 이미 끝난 결과의 권한을 없앤다(B-12).
- (b) **파생·보조 상태와 요청의 경계 정리.** 종결 과제의 readiness 투영이 남는다(A-08). 병합된 요청이 은퇴와 함께 사라진다(A-34). 목표 변경이 무관한 행동을 지운다(A-38). 설정 변경 뒤에도 대기 행동이 옛 배정과 옛 용량 제약을 쓴다(A-43, D-09). 개정이 옛 기준과 합쳐 저장된다(A-07). 목표 판정 이력이 덮인다(D-05).
- (c) **국소 실패·경합의 전역 확산과 중복 소유.** 수리 소진 실패가 인스턴스를 멈추고, 재개가 같은 실패를 되살린다(A-09). 한 예산 풀의 소진이 다른 풀을 막는다(A-42). 미시작 개정끼리 서로 기다린다(A-33). 운영 retry와 자동 후속이 같은 계보를 둘로 소유하려다 설치 수리로 승격된다(B-17). 봉인된 감사 자리를 다시 요청한다(D-04).

시험이 놓친 사정은 공통이다. 단계별 시험은 있었으나 순서와 조합은 없었다(A 관찰 4.1.5). 시작 상태가 비어 있어 경로가 비교 대상 없이 지나갔다(A-38: `queue: []`). 결함 동작을 기대값으로 고정한 시험도 있었다(A-42의 `budget_exhausted` 단언).

**시험 의무.**

- **7-A 상태 기계 속성 시험.**
  - 모집단: 2층 전이의 사건 알파벳.
    - 공개 제어: pause, resume, HOLD와 해제, quiesce와 해제, close, configure, limited_recovery, 목표·요구 변경.
    - 결과 편입: 역할별 판정값 전건.
    - 개정 요청과 은퇴.
    - 계획 적용: 선택, 철회, 감사 요청.
    - 운영 처분: continue, retry, revise, repair.
    - 설치 수리.
    - 실행 국면 사건: 시작, 도구, 정상·실패·시간 초과 종료, 결과 완성 뒤 미접수.
  - 입력: 무작위 사건 열(씨앗 고정, 길이 상한)과 회귀 씨앗. 회귀 씨앗은 이 문서의 기록이 보인 순서를 고정 열로 만든 것이다. 실행 환경은 대본 러너, 가짜 시계, 실제 계약 검사를 도는 메모리 저장이다.

    - (b) `task_readiness`의 키 ⊆ 배정 가능 과제다. 모든 대기 행동의 모델 배정과 용량 제약은 현재 설정으로 다시 계산한 값과 같거나, 명시적 재평가 대기에 있다. 병합과 은퇴 전후로 요청 이유의 합집합이 대기열과 이력에 보존된다. 목표 변경은 목표와 무관한 행동을 지우지 않는다. 개정 저장은 교체 의미다(현행은 제출값, 옛값은 이력). 판정·결정 이력은 추가만 된다.
    - (c) 개정·의존 대기 그래프에 순환이 없다. 같은 (계보, 자리, 계약)에 살아 있는 실행·대기 행동은 하나다. 한 행동이나 한 예산 풀의 실패·소진은 독립 행동의 배정을 막지 않는다. 재개는 입력 변경 없이 실패 행동을 되살리지 않는다. 운영 처분은 도달 가능한 모든 상태에서 방어 오류 없이 정산된다(후속이 있으면 superseded).

### 5.8 소유 루프의 진행과 반환 시 정산

**기제.** 3층 소유 루프가 한 원천에 묶여 다른 일을 못 하거나(진행성), 반환하면서 해야 할 정산을 빠뜨린다. 사례는 넷이다.

- B-05: 관찰 사건마다 동기 callback과 전체 상태 저장을 기다려, 완료된 결과의 회수가 수십 분 늦어졌다.
- C-24: 관찰 행을 상한 없이 비워, 계속 덧붙이는 호출 하나에 루프가 묶였다.
- B-31: 단계 상한에 걸린 반복이 방금 회수한 완료를 적용하지 않고 끝났다.
- C-26: 시작 전에 정지된 형식 검사가 발사표를 반환 표시하지 않아 종료 장벽에 걸렸다.

활성화 조건은 큰 상태와 많은 사건(B-05), 연속 관찰(C-24), 초기화 운전이 쓰는 `run --max-steps`(B-31), 정지 시점(C-26)이다. 시험은 작은 상태로 callback을 즉시 처리했고(B-05), 적용 함수를 직접 불러 실행 루프의 종료 조건을 거치지 않았다(B-31). 결함을 잡은 통합 시험은 있었으나 선택 실행에서 빠졌다(B-31).

- **9-B 녹화 재생.**
  - 모집단: 외부 출력을 해석하는 순수 함수 전건 × 지원 판본. Codex JSONL, Claude `stream-json`, 공급자 실패 분류, Lean 출력과 선언명, 예약 조회 JSON, scholarly·codex 설정 파일, 능력 탐침 출력이 대상이다.
  - 입력: 실제 외부 도구에서 녹화한 원자료 말뭉치. 정상과 경계를 함께 담는다. init 앞의 rate_limit 사건, 한 세션의 여러 결과 구간과 task-notification, 종료 정리 사건, 한도 초과, 작은따옴표 선언명, timeout 키가 있는 실제 설정, 실제 역할 스키마 전건이 들어간다.
  - 성질: 해석 결과가 녹화할 때 확인한 판정(수락·거부, 추출값)과 같다. CLI·Lean 판본이 바뀌면 말뭉치를 다시 녹화한다.

- **9-C 실환경 스모크 관문.**
  - 모집단: 인프로세스로 흉내 낼 수 없는 실외부 동작. 채택한 샌드박스 프로필로 작업 폴더에 쓰기(비대화 부모), pythonw 부모에서 PowerShell 설치 분기의 출력 수집, trigger 없는 예약 작업 조회, 열린 독자가 있는 파일 교체, PATH·PATHEXT로 찾은 Lean의 식별, 실제 CLI의 역할 스키마 수용과 `modelUsage`, 설정한 MCP 서버 도달(scholarly `list_sources`), 대표 컴파일 소요와 관찰 창의 비교가 들어간다.
  - 성질: 각 스모크가 기대 결과를 낸다.
  - 실행 시점: 설치, 판본 갱신, 공급자 CLI 판본 변경 때. 운전 시작 전 관문으로 두며 시험 묶음 밖이다.
  - 층: 3층과 경계 어댑터(실제 외부).

**제품 쪽 전제와 현재 성립 여부.**

### 5.11 판단 대상 없는 실행의 발동

**기제.** 사건·발동 규칙이 판단할 것이 없는 상태에서 모델 실행(주로 연구 계획)을 연다. 사례는 넷이다.

## 6. 과정 결함

이 절은 코드가 아니라 개발 과정이 결함을 통과시킨 기제를 모은다. 기제마다 해당 기록과, 시험 체계(시험 선택 규칙, 실행기, 지침)가 이를 막으려면 무엇을 해야 하는지를 적는다. 대역-사각지대 3부의 보존 규칙(K-xx)과 겹치는 곳은 그 번호를 적는다.

### P1. 검증런이 지적한 결함을 수리안의 형식·품질 사유로 기각하고 결함 자체를 추적하지 않음

**사실.** 검증런 장부의 처분은 수리안의 품질을 판정했다. 결함 존재가 반박되지 않은 항목도 후속 추적 없이 닫혔다(A 관찰 4.1.2).

- A-07: R1-65가 상신 형식이라는 이유로 1/3 기각됐다. 다음 날 운전에서 세 과제를 멈췄다.
- A-18: R1-05가 수리안 부작용 때문에 기각됐다. 다음 날 운전에서 관찰됐다.
- A-42: 1/3 기각됐고, 다음 검증런에서 반영됐다.
- A-44: 상신으로 기각됐고, 사용자가 직접 수리를 지시했다.
- A-09·A-27: 인접 지적이 기각됐다.
- B-33: 1/3 기각 뒤 사용자 지시로 직접 수리됐다.
- C-15: 1/3 기각(문서 조각) 뒤 세션이 코드 조각을 반영했다.
- C-18: 2/3 기각(시험 도우미 배치) 뒤 직접 처리됐다.
- C-20: 2/3 기각(범위 과잉) 뒤 좁혀 반영됐다.
- C-22: 0/3 기각(조각 좌표 형식) 뒤 추가 반영됐다.

**시험 체계가 할 일.**

- 검증런의 판정을 두 단계로 나눈다. 하나는 결함 실재의 판정이고, 다른 하나는 수리안의 채택 판정이다.
- 실재가 인정된 결함은 수리안이 기각돼도, 그 결함을 재현하는 실패 시험을 "알려진 결함"으로 등록한다. 실행기는 이 시험을 통과로 세지 않고 "열린 알려진 결함" 수로 따로 보고한다. 닫으려면 그 시험이 통과해야 한다.
- 이렇게 하면 기각된 결함이 다음 운전까지 조용히 남는 것을 실행기 보고가 막는다.

### P2. 시험·fixture가 결함 동작을 기대값으로 고정함

**사실.** 해당 기록은 A-11(부분), A-23, A-27, A-31, A-42, B-02, B-09, B-14, B-15, B-32, C-03, C-19, C-20이다. 이 밖에 9/15 검증런 R2-09가 "시험 다섯 곳이 그 동작을 기대값으로 고정함"을 지적했다(A 2.1절). M-0357은 이를 "승인된 설계 변경이 옛 성질 시험을 남긴다"로 기록했다(C 관찰 3). `4b156be`는 `test_engine.py`의 `assertEqual(..., "capacity_waiting")`를 `assertIn(..., {"capacity_waiting", "waiting"})`로 완화했다(D-11). 이런 시험은 결함을 드러내지 못할 뿐 아니라 수리를 회귀 실패로 보이게 만든다(A 관찰 4.1.3).

**시험 체계가 할 일.** 지침에 네 규칙을 둔다.

- 첫째, 단언의 기대값은 계약 문서, 설계표, 실제 생산자 출력에서 오고, 현재 구현의 출력을 복사하지 않는다.
- 둘째, 생산자가 있는 값은 fixture에서도 생산자로 만든다. 수신 검사를 통과시키려고 손으로 채운 필드를 금지한다(K-51·K-67의 확장).
- 셋째, 설계나 계약이 바뀔 때 옛 성질을 단언하는 시험을 먼저 검색해 목록화한다(K-74).
- 넷째, 시험의 단언을 완화하는 변경은 그 이유가 계약 변경임을 커밋에 적게 한다.

범주 의무의 선언값(예: 11-A의 호출 수, 7-A의 불변식)이 이 규칙의 "계약 쪽 기대값"을 제공한다.

### P3. 있는 시험·검사를 변경 뒤 실행하지 않음

**사실.**

- C-23: `379a171`이 사용자 결정으로 시험을 돌리지 않고 커밋됐다.

**시험 체계가 할 일.**

- 실행기 보고에 "선택 밖에 남은 영향 시험 수"를 적는다.
- 수집 검사(K-01, K-03)를 유지하고, 모듈 끝 블록 뒤의 시험 정의도 잡도록 넓힌다.
- 전체 실행의 완주 기록을 주기적으로 남긴다. 기존 규칙 K-60은 병합 뒤 통합 확인에서 전체를 한 번 돌리라고 정한다. 그 완주 없이 커밋한 경우를 실행기가 표지로 남긴다.

### P5. 사례만 고치고 기제를 고치지 않아 같은 기제가 라운드마다 재발함

- 지침 K-63("같은 성질의 시험이 있으면 단언을 더한다")은 사례 단위 규칙이다. 그 위에 범주 단위 규칙이 필요하다.

### P7. 정적 검증런과 통합 확인이 같은 대역·합성 입력을 공유해 같은 사각을 가짐

**사실.**

**시험 체계가 할 일.**

**재판정의 한계.**

- 결과 축의 인스턴스·과제 구분은 담당이 적은 결과 기술을 읽고 나눈 것이다. 전파 끝이 미확정인 B-33·B-48·C-27에는 2.1절 규칙 3을 적용했다.
- C-01을 인스턴스 정지로 적은 것은 2.1절의 공통 경로 규칙에 따른 것이다. 관측된 인스턴스는 루프를 계속 돌았고, 연구 계획이 작은 재제안으로 우회를 시도했다. 그 우회가 성공했을지는 알 수 없다.
- 가장 싼 포착 시험의 등급은 담당이 적은 시험을 따랐다. 그 시험 가운데 일부는 결함이 드러난 뒤에야 알게 된 외부 동작 지식을 쓴다(예: A-21은 CLI가 `$schema`를 거부한다는 지식). 녹화 재생 등급은 그 지식을 얻는 녹화가 한 번 필요하다는 점을 반영했지만, 녹화 대상을 미리 알 수 있었는지는 판정하지 않았다.

**범주와 검산의 한계.**

- 범주는 이 문서의 판정이다. 부 범주는 주요한 것만 적었고 전수가 아니다.
- 검산의 "잡음"은 시험을 실행한 결과가 아니라, 의무를 기록이 적은 기제에 대입한 판정이다. 일부는 입력 생성의 선택이나 제품 전제의 해소를 조건으로 한다(표에 "조건"으로 적었다).
- 의무의 모집단은 알려진 사례에서 넓혀 정한 것이다. 같은 기제의 모르는 사례가 모집단 밖에 있을 수 있다. 그래서 여러 범주가 모집단을 닫는 제품 쪽 전제(등록부, 정본 함수, 근거 필드 선언)를 요구한다. 이 전제가 채워지기 전에는 모집단이 열거 가능한 만큼만 닫힌다.
- 검산에서 `못 잡음`으로 남은 것은 B-20 하나다. 소프트웨어 시험의 대상이 아닌 운전 AI의 절차 준수 문제다.

**계수의 한계.**

- 저하는 개별 기록 대상이 아니어서 건수가 과소하다(4.1절).
- 4.2절 4번 읽기의 공존 수는 담당 기록이 적은 주입·수리 시점을 맞춘 계산이다. A 기간 결함과 주입 시점이 미확정인 C-01·C-02는 넣지 않았다. 그래서 공존 수의 하한이다.
- 시험 의무의 전제 판정은 기준 커밋 `3552607`의 `코드-구조.md` 관찰에 근거한다. 코드가 바뀌면 현재 원문이 우선한다.
