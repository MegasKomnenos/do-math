# 완료 경로를 다시 통제하기 위한 작업 방식 재검토

2026-10-03 사용자가 중구난방인 진행 방식과 미완료를 지적하여, 새 제품 구현과 시험 실행을 하지 않고 원문·현재 파일·기존 실행 보고를 대조했다. 현재 실행 중인 run_tests/변이 Python 프로세스는 없다. 목표 도구의 상태는 paused다. 이 문서는 재개 시 따를 구체적인 운영안이며 전체 목표나 완료 기준을 줄이지 않는다.

## 1. 판단

현재 방식의 핵심 실패는 **국소 실패를 다음 작업 선택의 기준으로 삼고, 전체 완료 조건을 작업 선택과 묶음 종료의 기준으로 쓰지 않은 것**이다. 실제 결함을 수리했고 부분 검증도 유효하지만, 작업량·검증비용·검토할 변경이 계속 늘었다. 이전 작업 방식 검토에서 이미 같은 문제를 지적했는데 운영에 충분히 적용하지 않았다.

‘관련 시험 N개 통과’와 ‘전체 관문은 남았다’를 반복해서 보고하는 것은 개별 결과에는 정확해도, 사용자가 끝까지 맡긴 작업을 관리하는 데 충분하지 않았다. 미완료를 정직하게 표시하는 것과 완료 경로를 통제하는 것은 별개다.

## 3. 무엇이 잘못됐는가

1. **모집단을 고정하기 전에 가족별 코드를 계속 늘렸다.** waiting_actions22종을 선언했지만4-A 원문은 과제·활동·수명·질문·반복 보류·공급자/설치·사건·역할 판정도 요구한다. 한 부분을 오래 보강해도 전체4-A/4-B가 얼마나 남았는지 관리되지 않았다.
2. **설명과 callable 존재를 실제 출구의 근거처럼 먼저 적었다.** submission_failure와 영향 변경/반려에 `_apply_action_resolutions`를 해소자로 적었지만 현재 수신자는 output_validation/execution_failure만 허용한다. 나중에 코드 대조로 바로잡았다. 앞으로 등록은 실제 허용 입구·소비 조건·소유자 연결을 먼저 확인해야 한다.
3. **시험 입력의 계약을 확인하기 전에 실행으로 알아냈다.** 영향 검토의 과제가 직접 tasks에 없다는 점, 원문이 task_catalog로 제공된다는 점, returned_task_ids가 비어 있는데 과제 평가를 제출할 수 없다는 점을 연속 실행으로 발견했다. 마지막 실패는 원 판단이 수신 계약에서 unexpected TK-impact로 반려된 것이다. 이를 곧바로 제품 결함으로 단정하거나 검사를 약화해서는 안 된다. 정상 역할 입력 생산자와 허용 산출 경로부터 다시 추적해야 한다.
4. **실제 경로를 보존한다는 원칙을 비용 개선을 미루는 이유처럼 사용했다.** 초기화·worker·저장·원문 읽기는 유지해야 한다. 그렇다고 같은 준비를 중복하거나 검사 범위를 매번 넓히는 비용까지 정당화되는 것은 아니다. 300초 T2와3300초 full T3는 완료 조건이며 현재 비용에서 빠진 작업으로 취급해야 한다.
5. **변경을 검토 가능한 단위로 확정하지 않았다.** 별도 트리는 좋은 선택이지만 많은 미커밋 변경과 새 지원 모듈이 누적돼 현재 통과 판본과 실험 중 판본의 경계가 흐려졌다. 실패 초안이 있는 판본 전체를 성공 후보로 취급하면 안 된다.
6. **근거 파일과 진행 기록을 작업 제어 장치로 쓰지 못했다.** 세밀한 이력은 필요하지만 각 묶음마다 새 파일과 ‘다음은…’ 문단을 더하는 것으로는 남은 일의 순서·규모·종료 조건이 확정되지 않는다.

## 5. 실제 운용 규칙

- 한 번에 열린 구현 묶음은 하나다. 작업 전에 요구 ID·정확한 모집단·파일 범위·시험 명령·종료 기준을 전환표에 적는다. 새 결함은 그 묶음의 필수 진입/완료에 영향이 있을 때 즉시 수리하고,그렇지 않으면 원장과 다음 묶음에 연결한다. 범위 밖 수리를 연쇄로 시작하지 않는다.
- 같은 입력 구성 실패가 두 번 반복되면 세 번째 같은 규모 실행 전에 정상 생산자·계약·실패 원문을 직접 검수한다. 필요할 때만 가설 하나를 가르는 가장 작은 실행을 한다. 실제 런/상태 관측을 먼저 확보하고 오류를 감출 catch나 허용값 확대를 넣지 않는다.
- 최소 검사→변경 영역 전체1회→고정판 전체 관문으로 진행한다. 부분 검사 숫자를 누적해 전체 완료율로 표현하지 않는다. 실패 후 제품이 안 바뀌고 기대값만 교정됐다면 실패 관련 검증으로 충분한지 명시하고 원 전체 보고를 보존한다.
- 기존 시험에 같은 성질을 보강하는 것을 우선한다. 새 모듈·지원 정의는 기존 경로로 표현하기 어려운 실제 모집단/공통 소비자가 있을 때만 추가한다. 일반 검사에 선언 목록을 순회하는 것만으로 의미 검증이 되는지 반드시 검수한다.
- 종료 기준을 만족한 묶음은 diff·근거 판본·원문 모집단을 검수해 별도 커밋 가능한 checkpoint로 확정한다. 미검증 초안이 섞인 채 통째로 커밋하거나 main에 복사하지 않는다. 기존 커밋/기억/미러 규칙도 함께 지킨다.
- ‘현재 무엇을 하는가’는 전환표 한 곳에 둔다. 진행 기록은 완료된 묶음과 판정 변경만 기록하고 매번 남은 전체 목록을 복제하지 않는다. 상세 실패는 기존 원장/기존 근거에 추가하며 이력을 삭제하지 않는다.
- 보고는 현재 묶음,닫힌 요구,남은 요구,다음 종료 조건으로 한다. 일정의 근거가 없으면 완료 시간을 추정으로 포장하지 않는다. 과정의 도구/토큰 사용량도 통제 대상으로 삼는다.

## 6. 바로 다음에 해야 할 일

재개 시 첫 행동은 실패한 영향 검토 시험을 또 고치는 것이 아니다. **전환표를 현재 판본의 작업판으로 바꾸고,보존 대비136파일의 변경을 검수해 확정 가능한 묶음과 미검증 초안을 분리하는 것**이다. 여기서 전건 남김과 비용 병목을 확정한 뒤 위 네 기능 묶음의 순서를 정한다. 완비 감사 자체도 요구 표를 갱신하는 데 필요한 범위로 제한하며 새 감사 문서를 계속 늘리지 않는다.

이 재검토는 목표의 최종 완료를 입증하지 않는다. 현재 목표 paused 상태를 유지하며,재개하면 이 운영안을 적용한다.
