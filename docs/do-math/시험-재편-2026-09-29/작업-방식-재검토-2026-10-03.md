### 원인: 계획이 행동을 바꾸지 못한 구조

**1. 개별 변경의 종료와 프로젝트의 종료를 연결하지 않았다.**

커밋 하나를 끝내는 절차는 개선됐지만, 그 변경으로 원래 의무의 어느 성질이 끝났고 어느 성질만 남았는지는 작업 선택에 반영되지 않았다. ‘부분 N개 통과, 전체는 미완료’는 과장 없는 보고지만 다음 행동을 정하지 못한다. 구현이 이미 있는 항목도 계속 일반적인 감사 대상으로 남으니, 재개할 때 다시 검수하는 편이 자연스러운 상태가 됐다.

현행 전환표는 1503310바이트이며 `active_change`는 B01, `next_change`는 B02, 실제 현재 작업은 별도 `current_focus`에 있다. 과거 상세 보존 자체가 문제는 아니다. 현재 행동과 역사 기록이 같은 이름 아래 공존하고, 기존 필드가 현재를 대표하지 않는 것이 문제다. 자세한 이력 저장소와 현재 작업판이 같은 역할을 할 수 있다고 가정했다.

**2. 다음 행동의 선택 폭이 너무 넓었다.**

‘의존관계에 따라 다음 변경 하나’, ‘남은 원문 의무를 검수’라는 문장은 합리적으로 들리지만, 실제 다음 항목·막는 이유·끝나는 질문이 없으면 거의 모든 관련 독해와 수리를 허용한다. 현재 작업은 하나였어도 미래 후보와 미완료 감사는 계속 늘 수 있었다. 진행 중 구현 수만 하나로 제한한 것으로 전체 진행 중 일을 통제했다고 착각했다.

**3. 증거를 보수적으로 취급하는 원칙을 재조사의 근거로 과도하게 확장했다.**

기존 관련 검사의 통과가 최종 전체 통과는 아니다. 그렇다고 그 관련 검사가 입증한 성질까지 계속 미확인인 것은 아니다. ‘최종 판본 재확인 대기’와 ‘무엇을 검증해야 하는지 아직 모름’을 합치면 완료한 의미 검토도 반복된다. B84 감사에서 1-D·11-A·B-32·2-C·8-A 등에 이미 필요한 검사가 있다는 결론이 나왔는데, 상위 상태는 그대로다. 정직한 미완료 표시가 완료한 부분을 인정하지 않는 방식으로 굳었다.

**4. 원칙·운영 선택·당시 상태를 같은 강도로 물려받았다.**

사용자가 요구한 정확성과 효율은 원칙이다. 실행 층 배정, 검사 간격, 임시 시간 제한은 운영 선택이다. 특정 시점의 ‘전체 실행 중’은 상태다. 그런데 과거 문서의 하드 예산 문구, 목표 본문의 오래된 ‘먼저 B78’, 살아 있지 않은 실행의 `running` 기록이 후속 작업의 명령처럼 기능할 위험이 있었다. timeout 문제는 이 층위를 구별하지 못한 구체적 사례다. 30279행의 최신 사용자 지시는 이 문제를 명시적으로 바로잡았고, 더 오래된 문구로 되돌릴 여지는 없다.

**5. 사용자 지적을 받을 때 일관된 재평가보다 즉시 새 설명을 내놓았다.**

35040행의 번복이 가장 명확하다. ‘왜 하는가’에 먼저 답하고, 합의된 목적에 맞는 실행인지 판단했어야 한다. ‘미완료 구현이 있으므로 전체 검사는 이르다’는 기준은 중간 통합 검증을 사실상 없애고 모든 결합 오류 발견을 마지막으로 미룬다. 그 전에 제가 지적했던 문제를 다시 만드는 답변이다. 사용자가 더 상세하게 지시하지 않아서 생긴 문제가 아니다. 이미 충분한 목적·비용 원칙과 재량이 주어졌다.

**6. 대기 시간을 새 조사로 채우는 것이 작업 확장의 통로가 됐다.**

소스를 고정하는 것은 실행 증거의 일관성을 위한 조건이다. 그러나 기다리는 동안 반드시 새로운 감사 산출물을 만들어야 하는 것은 아니다. 독립 작업의 종료 질문을 미리 정하지 않아 전 범위 재감사로 번졌다. 동시에 ‘실행 중이므로 뒤에 반영’된 자료는 실제 작업판과 분리됐다. 다음 재개에서는 그 자료를 다시 읽어야 해 복구 비용도 늘었다.

**7. 도구 사용 자체의 반복 비용도 줄이지 못했다.**

이번 분석에서도 첫 로그 추출이 자동 목표 메시지를 제외하지 않아 불필요하게 큰 출력을 냈고, 몇몇 문서 읽기는 출력이 잘렸다. 필터와 범위를 좁혀 필요한 구간을 회수했지만, 이는 과거 검토가 지적한 원문 회수 비용의 재발이다. ‘원문을 확인한다’는 이유로 큰 출력을 무작정 읽는 방식은 정확성도 효율도 보장하지 않는다. 필요한 질문과 좌표를 먼저 정해야 한다.

이 원인들은 관찰한 작업 방식에 대한 판단이다. 내부 심리나 모든 토큰의 사용 이유를 추정한 것은 아니다. 30853~35035행에는 최상위 도구 호출 449건, 그중 `write_stdin`을 포함한 호출 171건이 있지만, 이를 그대로 불필요한 호출 수나 낭비 시간으로 환산하지 않는다.

3. **시험 입력의 계약을 확인하기 전에 실행으로 알아냈다.** 영향 검토의 과제가 직접 tasks에 없다는 점, 원문이 task_catalog로 제공된다는 점, returned_task_ids가 비어 있는데 과제 평가를 제출할 수 없다는 점을 연속 실행으로 발견했다. 마지막 실패는 원 판단이 수신 계약에서 unexpected TK-impact로 반려된 것이다. 이를 곧바로 제품 결함으로 단정하거나 검사를 약화해서는 안 된다. 정상 역할 입력 생산자와 허용 산출 경로부터 다시 추적해야 한다.
4. **실제 경로를 보존한다는 원칙을 비용 개선을 미루는 이유처럼 사용했다.** 초기화·worker·저장·원문 읽기는 유지해야 한다. 그렇다고 같은 준비를 중복하거나 검사 범위를 매번 넓히는 비용까지 정당화되는 것은 아니다. 300초 T2와3300초 full T3는 완료 조건이며 현재 비용에서 빠진 작업으로 취급해야 한다.
5. **변경을 검토 가능한 단위로 확정하지 않았다.** 별도 트리는 좋은 선택이지만 많은 미커밋 변경과 새 지원 모듈이 누적돼 현재 통과 판본과 실험 중 판본의 경계가 흐려졌다. 실패 초안이 있는 판본 전체를 성공 후보로 취급하면 안 된다.
6. **근거 파일과 진행 기록을 작업 제어 장치로 쓰지 못했다.** 세밀한 이력은 필요하지만 각 묶음마다 새 파일과 ‘다음은…’ 문단을 더하는 것으로는 남은 일의 순서·규모·종료 조건이 확정되지 않는다.

## 4. 재개 후 순서와 종료 조건

아래 순서는 실행 계획이다. 아직 수행하지 않은 감사를 완료로 표시하지 않는다. 정확한 소요 시간은 현재 판본의 비용을 확인하기 전까지 약속할 수 없다.

| 순서 | 할 작업 | 닫는 조건 |
|---|---|---|
| 1 현재 판본 정리 | 최근 실패 영향 초안을 ‘미검증’으로 분리해 기록. 보존 대비136파일 diff를 구현/회귀시험/검증도구/문서로 검수. 기존 전환표를 현재 상태로 갱신 | 원문19의무·61보존·11수리의무·P2 원래12항목 각각에 모집단,현재 코드,검사,근거 판본,구체적 남김과 종료 기준이 있음. 변경 묶음별 reviewable checkpoint가 있음 |
| 2 기능 완비를 묶음으로 구현 | 아래 네 기능 묶음을 원문 모집단으로 확정하고 각 묶음 하나씩 작업 | 일반 순회와 완비 검사,실제 생산자/수신자/owner 경로,그 묶음의 전체 관련 검사와 diff 검수 완료. 다음 가족을 임의로 붙이지 않음 |
| 3 검증 비용 개선 | 기존 비용 조사와 현재 일반 보고의 상위 비용을 사용. 정상 T2와 T3 계측 비용을 구별하여 가장 큰 병목 하나씩 개선 | 동일 입력·단언·실제 경로를 보존하는 전후 측정과 회귀 근거. 목표 예산에 이르는 근거가 없으면 작업 묶음은 닫히지 않음 |
| 4 고정판 최종 관문 | 제품/시험 후보를 고정하고 T2+flows→fresh full T3→현재 함수 모집단 전체 변이. 예산·미도달·미실행을 별도 판정 | 현재 동일 판본의 전체 결과,0미도달 또는 검수된 정당 제외,모든 대상 함수 실제 변이,시간 예산 충족. 실패는 원 의무에 되돌려 한 묶음으로 수리 |
| 5 실환경·배포·통합 | T4/T5 최소 실제 공급자 호출·말뭉치·최종 지침·미러/check·main 변경 충돌 검수 | 최종 검증한 내용과 실제 통합 산출물이 일치하고 main에서도 필요한 통합 확인 완료. 푸시·graphify 갱신·연구 인스턴스 재개/삭제는 범위 밖 |

기능 묶음은 전건을 빠뜨리지 않도록 다음처럼 나눈다.

- **대기/계수/관측:** 4-A/4-B/4-C/13-B. 행동22종을 포함한 모든 상태 공간의 선언·생성·해소·정당 계수·실제 표시를 한 모집단에서 추적한다. 영향 대기의 단순 target 폐기만으로 필요한 후속 판단의 출구를 대체하지 않는다.
- **입력/평가/근거:** 3-B/3-C/5-A. 모든 역할 변형의 요구 입력과 정확 참조,원래11평가자 쌍,판정 함수 전건의5교란 축을 함께 대조한다. 원문 회수 경로와 수신자가 실제 허용하는 산출을 먼저 확인한다.
- **소유자/시간/발동:** 2-B/6-A/11-B. 실제 소유자 단계별 단위 오류와 포트 실패 격벽,현재 시간 규칙×국면,판단 대상 유무×사건 발동을 검증한다. 폐기한 run 기한을 원문 목록에 있다는 이유로 부활시키지 않고 현재 계약을 연결한다.
- **기동/문서/보존 회수:** 12-A/13-C 및1e/1f 잔여·61보존·P2 원래12항목. 정본/설치/기동·문서 이름/읽기 한계와 각 원래 개선 지식이 현행 경로에서 실제 유지되는지를 검증한다. P2 추가 사례와 원래12항목을 구별한다.

순서3을 무조건 기능 전체 뒤로 미루지는 않는다. 순서1에서 현재 반복 검증을 지배하는 비용이 확정되면 그 좁은 병목을 먼저 고쳐 이후 기능 작업의 되먹임을 줄인다. 기능 완비와 비용 개선 두 작업을 동시에 열어 서로 판본을 흔들지는 않는다.

## 5. 실제 운용 규칙

- 한 번에 열린 구현 묶음은 하나다. 작업 전에 요구 ID·정확한 모집단·파일 범위·시험 명령·종료 기준을 전환표에 적는다. 새 결함은 그 묶음의 필수 진입/완료에 영향이 있을 때 즉시 수리하고,그렇지 않으면 원장과 다음 묶음에 연결한다. 범위 밖 수리를 연쇄로 시작하지 않는다.
- 같은 입력 구성 실패가 두 번 반복되면 세 번째 같은 규모 실행 전에 정상 생산자·계약·실패 원문을 직접 검수한다. 필요할 때만 가설 하나를 가르는 가장 작은 실행을 한다. 실제 런/상태 관측을 먼저 확보하고 오류를 감출 catch나 허용값 확대를 넣지 않는다.
- 최소 검사→변경 영역 전체1회→고정판 전체 관문으로 진행한다. 부분 검사 숫자를 누적해 전체 완료율로 표현하지 않는다. 실패 후 제품이 안 바뀌고 기대값만 교정됐다면 실패 관련 검증으로 충분한지 명시하고 원 전체 보고를 보존한다.
- 기존 시험에 같은 성질을 보강하는 것을 우선한다. 새 모듈·지원 정의는 기존 경로로 표현하기 어려운 실제 모집단/공통 소비자가 있을 때만 추가한다. 일반 검사에 선언 목록을 순회하는 것만으로 의미 검증이 되는지 반드시 검수한다.
- 종료 기준을 만족한 묶음은 diff·근거 판본·원문 모집단을 검수해 별도 커밋 가능한 checkpoint로 확정한다. 미검증 초안이 섞인 채 통째로 커밋하거나 main에 복사하지 않는다. 기존 커밋/기억/미러 규칙도 함께 지킨다.
- ‘현재 무엇을 하는가’는 전환표 한 곳에 둔다. 진행 기록은 완료된 묶음과 판정 변경만 기록하고 매번 남은 전체 목록을 복제하지 않는다. 상세 실패는 기존 원장/기존 근거에 추가하며 이력을 삭제하지 않는다.
- 보고는 현재 묶음,닫힌 요구,남은 요구,다음 종료 조건으로 한다. 일정의 근거가 없으면 완료 시간을 추정으로 포장하지 않는다. 과정의 도구/토큰 사용량도 통제 대상으로 삼는다.

## 6. 바로 다음에 해야 할 일

재개 시 첫 행동은 실패한 영향 검토 시험을 또 고치는 것이 아니다. **전환표를 현재 판본의 작업판으로 바꾸고,보존 대비136파일의 변경을 검수해 확정 가능한 묶음과 미검증 초안을 분리하는 것**이다. 여기서 전건 남김과 비용 병목을 확정한 뒤 위 네 기능 묶음의 순서를 정한다. 완비 감사 자체도 요구 표를 갱신하는 데 필요한 범위로 제한하며 새 감사 문서를 계속 늘리지 않는다.

이 재검토는 목표의 최종 완료를 입증하지 않는다. 현재 목표 paused 상태를 유지하며,재개하면 이 운영안을 적용한다.
