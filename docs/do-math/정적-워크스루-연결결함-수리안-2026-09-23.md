이 문서는 [정적 검토 보고서](review-evidence/2026-09-23-static/report.md)의 8건을 현행 코드에서 수리하기 위한 제안이다. 사용자가 요청한 산출은 구체적인 수리안과 그 기록이다. 아래 변경은 아직 구현하지 않았으며 do-math나 그 테스트도 실행하지 않았다. 구현 단계의 확인 사례를 이미 통과한 검사로 읽지 않는다.

기준은 2026-09-23에 다시 읽은 `.claude/skills/do-math` 작업 트리이며 [파일 해시](review-evidence/2026-09-23-static/repair-source-basis.json)를 기록했다. 원 보고서의 근거 17개 파일과 비교하면 `GLOSSARY.md`와 `engine.py`가 변경됐지만, 이번 8건의 직접 원인은 유지돼 있다. 별도의 [기존 수리 결과](정적-워크스루-수리결과-2026-09-23.md)가 다루는 2~8번은 다른 검토의 번호다. 이 문서는 혼동을 피하도록 원 보고서의 1~8번을 F1~F8로 부른다.

최근 수정된 다음 동작은 그대로 보존한다. 운영 재시도는 원 action ID와 소유 활동을 유지하고 새 execution의 `continuation_of`로 선행 실행을 연결한다. 사용자 소유 반복 보류를 기술 수리로 우회하지 않는다. 체크포인트는 실제 보존 artifact에 결박하며, 부수 통찰은 실제 수입된 지식 ID를 다음 계획에 전달한다. 이번 수리는 이 경로 위에 얹는다.

핵심은 기존 기록을 소비하는 경로를 완성하는 것이다. 형식 검사에는 기존 실행 계보를, 검토 종료에는 기존 cycle·활동·후속 계획을, 제출에는 기존 묶음 적용기를 사용한다. 별도의 복구 원장이나 범용 정책 엔진을 만들지 않는다. 아래 함수명 가운데 새로 제안하는 이름은 구현 위치를 설명하기 위한 것이며, 실제로 존재하는 함수와 구별해 표시했다.

**F1. 일시 정지된 형식 검사를 같은 의무의 후속으로 유지한다.**

변경 위치는 [engine.py](../../.claude/skills/do-math/scripts/do_math/engine.py)의 `_formal_steps`, `_continue_prepared_action`, `_settle_activity`와 [lifecycle_engine.py](../../.claude/skills/do-math/scripts/do_math/lifecycle_engine.py)의 재개 경로다. 기존 [activities.py](../../.claude/skills/do-math/scripts/do_math/activities.py)의 `continue_activity`가 원 action ID·활동과 새 실행의 계보를 연결한다.

현재 `_formal_steps`는 모든 `stopped` 결과를 `formal_stopped` 대기로 옮기고 action을 제거한다. 이를 정지 원인별로 나눈다. 검사 반환의 일반 문구만 사용하지 말고, `_formal_steps`의 `stop` 콜백이 읽는 runtime의 사용자 정지·종결 상태, 해당 execution의 정지 요청, 실제 허가 판정과 입력·신뢰 환경의 변경을 근거로 남긴다. 정지 원인이 겹치면 함께 보존하며, 종료 실행의 `result_disposition`과 원 입력 manifest로 후속이 대조할 수 있게 한다. 종료된 검사의 `execution_id`도 후속에서 찾을 수 있게 보존한다.

| 종료 조건 | 수리 후 처리 |
|---|---|
| 사용자 pause 또는 HOLD로 정지했고 인스턴스가 미종결 | 로컬 검사 프로세스 종료와 예약 반환을 확인한 뒤 실행을 끝낸다. 원 action을 queue에 유지하고 `continuation_of`를 종료 실행에 연결한다. lifecycle이 paused인 동안 새 검사는 배정하지 않는다. |
| 명시적 resume 또는 해당 HOLD의 정상 release | 기존 lifecycle 재개 절차를 따른다. 배정 직전에 현재 허가, 동일한 제출 소스·선언명, 신뢰 환경, 사용 중인 활동과 중복 요청을 검사하고 새 execution으로 검사를 다시 시작한다. |
| 허가 철회·만료, 제출 소스 또는 신뢰 환경 변경 | 사용자 일시 정지 해제로 취급하지 않는다. 원 실행과 결과를 보존하고 실제 결함의 담당자에게 반환한다. 변경된 전제로 옛 검사를 자동 승인하지 않는다. |
| close 또는 목표 완료 | 새 검사를 배정하지 않고 종료·회수만 끝낸다. |

구현은 일시 정지 분기에서 action을 지우기 전에 기존 후속 연결 함수를 사용하도록 한다. 이미 queue에 같은 action이 있으므로 `_continue_prepared_action`으로 계보를 붙일 수 있다. queue가 없는 복구 사례에서는 `continue_activity`로 한 번만 되살린다. `_settle_activity`가 남은 후속을 보고 활동을 조기에 `finished`로 만들지 않는지도 함께 확인한다. 재개는 컴파일러의 중간 메모리를 복원하는 기능이 아니라 같은 입력의 새 검사 시도다.

이미 저장된 `formal_stopped` 기록은 읽을 수 있게 유지한다. 실행 ID가 빠진 옛 대기는 같은 action·소유 활동에 속한 종료 실행과 원 산출이 하나로 식별되는 경우에만 연결을 복구한다. 후보가 여러 개이거나 로컬 종료가 불명확하면 현재 기록을 유지하고 기존 유지보수 경로로 진단한다. ID나 종료 사실을 추측해 채우지 않는다.

완료 확인은 공개 pause → 종료·회수 → resume → 새 형식 검사 → 동일성 검토 요청까지 이어져야 한다. 재개를 두 번 적용해도 후속은 하나여야 하며, 이전 실행은 ended로 남아야 한다. 같은 사례에서 허가 철회, 환경 변경, close를 각각 넣으면 새 검사가 시작되지 않아야 한다.

**F2. 검토 한도를 계산하고, 수행할 수 없는 검토를 다음 판단으로 반환한다.**

변경 위치는 [review_policy.py](../../.claude/skills/do-math/scripts/do_math/review_policy.py)의 `validate_scope_assessment`, [review_cycle.py](../../.claude/skills/do-math/scripts/do_math/review_cycle.py)의 실행 몫·종료·증거 재생, [review_engine.py](../../.claude/skills/do-math/scripts/do_math/review_engine.py)의 `_admit_review_execution`와 후속 전달, `engine.py`의 `_register_execution`이다.

먼저 범위 계획의 실행 하한을 같은 순수 계산 함수로 검사한다. N은 제안된 초기 자리 수, U는 이번 범위 계획 실행을 포함하여 해당 검토에 실제 귀속된 AI 시도 수다. [통합 설계의 11.3.1절](통합-설계.md)에 따라, 심사 한 회차를 허용하면 `U + N + 1 + 3`, 두 회차 이상이면 `U + N + 1 + N + 6` 이상이어야 한다. 이는 모든 허용 회차를 끝낼 충분한 예산을 뜻하지 않으며, 추가 정리·보충·복구는 별도로 소비한다. 기계 실행은 AI 횟수에서 제외한다.

두 식의 첫 N은 초기 독립 검토, 1은 쟁점 정리 한 번, 3은 독립 심사자 셋의 한 회차다. 두 번째 식의 추가 N은 초기 검토자 자리별 답변 한 번이며 6은 답변 전후의 심사 두 회차다. 예를 들어 U=1, N=3이면 하한은 각각 8회와 14회다. 실제 정책의 회차 한도 1과 2 이상을 구별하며, 사용자가 정한 실행 상한을 이 계산으로 올리지 않는다.

범위 계획 입력에는 중앙이 계산한 U와 정책·필수 몫을 제공한다. 생산자 검사와 수신자가 이 고정 입력에 같은 함수를 적용하고, 실제 배정에서도 최신 소비를 검사한다. 생산자가 소비 실행 ID나 합계를 새로 저작하게 하지 않는다. `activity_execution_limit=1`에 초기 자리 둘을 넣는 예는 정확한 부족량과 함께 범위 계획 오류로 반환돼야 한다.

도중에 실제 한도가 소진됐을 때에는 새로운 `review_policy` 대기를 만들고 끝내지 않는다. 다음 처리를 맡는 작은 공통 함수 `request_review_resource_disposition`과 종료 후 정산 함수 `settle_review_resource_disposition`을 `review_engine.py`에 추가하는 안을 제안한다. 두 함수는 F3에서도 사용한다. 새 최상위 원장은 만들지 않고 기존 cycle의 `history`·`followup`과 활동의 `unresolved`·`followups`를 사용한다.

1. cycle ID, 고정 제안 해시, 정책과 한도, 실제 소비 실행 ID, 수행하지 못한 필수 자리, 사유와 근거를 한 번 기록한다. 같은 cycle·같은 종료 사유의 재처리는 같은 기록을 사용한다.
2. 해당 cycle의 새 검토·보충 배정을 막는다. 이미 배정한 실행은 보존·정지 요청으로 회수하고, 로컬 종료·예약 반환이 확인되기 전에는 활동을 finished로 만들지 않는다. 다른 cycle과 연구의 실행은 계속할 수 있다.
3. 정책의 `overflow_disposition=unresolved`이면 회수 뒤 cycle을 unresolved/ended로 닫고 실제 결과·미완료 자리·다음 소유자를 남긴다. 실패한 실행이 의미 판정을 내렸다고 꾸미지 않는다. 필수 판정이 없는 경우에는 새 동일성 판정 기록(IA)을 합성하지 않고 미완료 검토의 활동 결과를 전달한다.
4. 정책이 `defer`이면 stage와 실제 결과를 유지한 채 활동을 waiting으로 둔다. 이 경우에도 같은 미완료 근거를 연구 계획에 실제로 전달한다. 기다릴 조건은 해당 제안의 재구성 또는 권한 있는 후속 결정이다. 경과 시간이나 빈 슬롯만으로 소비한 실행 한도를 다시 주지 않는다. 이후 제안 개정·철회가 실제로 수락되면 그 전이에서 옛 검토를 미완료로 정산한 뒤 후속 제안을 처리한다.
5. 계획 요청에는 병합돼도 사라지지 않는 `event_refs`·`evidence_refs`로 cycle과 종료 근거를 연결한다. 계획 입력에 `review_followups`를 제공하고 큰 원문은 기존 참조 파일로 전달한다. 참조 검사기도 이 지급된 cycle·근거 참조를 인식하게 한다. 계획은 실제 완료 범위를 읽고 준비 요청·재구성·필요한 사용자 결정을 정한다.

종료 상태만 직접 덮는 방법은 채택하지 않는다. `validate_sealed_review`와 상태 검사가 새 기계 종료 사건을 재구성할 수 있어야 한다. 기존의 AI 최종 판정과 이번 자원 사유의 종료를 구별하고, 기록된 소비·미완료 범위·종료 증거가 맞지 않으면 거부한다. 재시작 후에도 종료 정산과 계획 요청이 중복되지 않아야 한다.

같은 검토 엔진을 쓰는 두 경로도 빠뜨리지 않는다. 신뢰 환경 전환 중 검토가 미완료로 끝나면 전환을 성공시키지 않고 이전 환경을 유지한 채 전환 담당에게 근거를 돌린다. 원 판정 재심사가 미완료로 끝나면 원 판정의 정지된 사용 효력을 자동 복원하거나 철회하지 않고, 재심사 후속으로 연결한다. 이 분기는 `_publish_identity_review_result`, `_publish_assessment_reassessment`, `_finish_trust_transition`의 소비 계약에 맞춘다.

완료 확인에는 범위 계획 하한의 경계값, 실제 재시도로 한도 소진, 실행 중 동료가 있는 상태의 회수, unresolved와 defer 각각의 후속, 신뢰 전환·재심사, 재시작 뒤 같은 후속의 중복 방지를 포함한다. 새 정책이나 더 큰 예산의 채택은 사용자 결정이며 이번 수리가 그 값을 자동으로 바꾸지 않는다.

**F3. 검토 제안의 입력 초과를 연구 재구성으로 연결한다.**

변경 위치는 [context_store.py](../../.claude/skills/do-math/scripts/do_math/context_store.py)의 `prepare_role_input`과 `defer_input_overflow`, `engine.py`의 입력 초과 분기, F2의 검토 후속 처리다. 현행 원인 분류를 그대로 사용하고 분류기를 하나 더 만들지 않는다.

`identity_review`에서 원인이 `current_proposal_or_required_sources`이고 `suggested_disposition=unresolved_to_review_plan`이면, 일반 사용자 차단 질문을 만들기 전에 F2의 검토 미완료 처리로 보낸다. 고정 제안·필수 원자료, 실제 입력 바이트, 프로필 한도, 원인, 준비 실행의 ID와 검토 자리를 근거로 남긴다. 모델을 호출하지 않고 `execution_lifecycle.end_preparation(..., stage="packing", cancelled=True)`으로 queued 준비 실행을 종료한다. 같은 활동의 다른 실행이 있으면 그 회수가 끝난 뒤 활동을 정산한다.

다음 계획은 `review_followups`에서 이 측정과 정확한 제안 원문을 받는다. 작성 과제가 미완료이고 같은 의무를 이어가면 기존 `revision_requests`로 정련을 요청하고, 완료·닫힘 과제이거나 다른 연구 의무면 기존 결과에 근거한 새 준비를 요청한다. 제안을 나누는 의미 판단은 계획·준비가 맡으며 입력 생성기가 문자열을 잘라 자동 분해하지 않는다. 실제로 더 큰 프로필이나 허가가 필요한 경우에만 그 결정을 사용자 질문으로 연결한다.

`restored_dialogue`와 `common_documents_or_governance`에는 위 제안 재구성 처분을 적용하지 않는다. 전자는 같은 검토 자리의 복원·허가된 프로필 변경 문제로, 후자는 공통 입력·설치·설정 문제로 보존한다. F3는 이 원인들을 수학 제안의 결함으로 바꾸지 않는다. 이미 `research_work`에 연결된 `input_overflow_requests`와 허용 프로필 선택은 유지한다.

완료 확인은 제안 초과 시 새 사용자 차단 질문이 생기지 않고 실제 계획 입력에 측정·원문·남은 의무가 들어가는지까지 한다. 대화 이력만 큰 경우와 공통 문서만 큰 경우에는 제안 재구성으로 잘못 보내지 않아야 한다. 여러 검토 후속이 한 계획에 병합돼도 전건의 참조가 남아야 한다.

**F4. 선택 모집단을 유지하면서 의무 이전의 수신 과제를 대조한다.**

변경 위치는 `engine.py`의 `_apply_plan`, [decision_engine.py](../../.claude/skills/do-math/scripts/do_math/decision_engine.py)의 `_apply_task_plan`, [task_scope.py](../../.claude/skills/do-math/scripts/do_math/task_scope.py)의 `apply_task_assessments`다.

계획 수신의 모집단 검사는 지금처럼 고정 입력의 `tasks`, `ready_task_ids`, `returned_task_ids`를 사용한다. 여기에 모든 과제를 넣어 고치면 선택·완료 판정의 전건 계약까지 바뀌므로 그 방법은 사용하지 않는다.

대신 `apply_task_assessments`에 판본 대조용 전체 과제 입력을 별도로 전달한다. 이름은 `reference_tasks`로 제안한다. 이 값은 실행의 `input_snapshot`에 있는 과제 중, 실제 지급된 `task_catalog`의 ID와 원문 참조에 결박된 기록으로 구성한다. 의무를 넘겨받을 과제의 계약 판본·해시 확인만 이 집합으로 수행한다. 선택 후보 검사는 기존 집합으로 계속 수행한다. 원문을 읽으라는 계획자 지침도 유지한다.

수신 과제의 현재 미종결 상태, 실제 실행 부재, 사용자 이전 결정, 새 의무 ID의 비충돌을 확인한 뒤 기존 전이로 의무를 추가한다. 계약 판본을 올리고 기존 승인·배정을 무효화하여 새 독립 계약 검토를 받는 동작은 유지한다. 이후 원 과제의 이전 기록과 수신 과제의 의무는 같은 저장 갱신에 남아야 한다.

완료 확인의 중심은 A의 결과를 판정하면서 아직 계약 검토 중인 B로 승인된 의무를 이전하는 사례다. 반대로 B의 계약 변경, B의 실행 시작, 종료된 B, 권위 없는 이전, 입력 snapshot에 없던 B는 계속 거부해야 한다. B가 선택 모집단에 없다는 이유만으로 전체 선택 처분에 B를 추가하도록 요구해서도 안 된다.

**F5. 보충 조사 참조 검사를 실제 호출하고 두 소비자를 맞춘다.**

변경 위치는 [submission.py](../../.claude/skills/do-math/scripts/do_math/submission.py)의 `_payload_issues`와 `review_engine.py`의 `_apply_review_research`다. 먼저 `check(..., source)`를 `source()` 정의 바깥, 참조 반복문 안으로 옮긴다.

허용 집합은 배정된 고정 원자료의 `ref`와 이번 실행에서 보존되는 `workspace:<상대 경로>`다. 단순히 다른 지급 자료나 전체 지식 목록에 존재한다는 이유로 고정 조사에 허용하지 않는다. `used_sources`와 `evidence_refs` 모두를 같은 조건으로 확인하고 오류에는 실제 필드·색인을 표시한다.

최종 수신자가 다시 검사하는 조건은 유지하되, 허용 여부 계산을 작은 공통 함수로 묶어 생산자와 중앙이 사용하게 한다. 파일의 실제 보존 정보는 호출자가 지급한다. 최종 적용기는 그 정보로 artifact 참조를 연결하며, 로컬 경로가 존재한다는 사실만으로 보존 성공을 주장하지 않는다.

완료 확인은 유효한 고정 참조, 수집 가능한 workspace 파일, 다른 지급 지식 ID, 없는 파일, 제외 폴더, 경로 이탈을 각각 포함한다. 특히 `evidence_refs`는 유효하지만 `used_sources` 하나만 허용 범위 밖인 응답이 생산자 검사·중앙 검사 모두에서 같은 이유로 거부돼야 한다.

**F6. 봉인 가능한 원문과 구성원 전건의 검사 통과를 구분한다.**

변경 위치는 `submission.py`의 `payload_issues`, `seal_submission`, `read_sealed_submission`, `summarize_snapshot_checks`와 preview·CLI 반환, [integration.py](../../.claude/skills/do-math/scripts/do_math/integration.py)의 `inspect_bundles`·`apply_bundles`, `engine.py`의 `_stage_submission_capture`, `_capture_native_submission`, `_preview_submission`, `_receive_submission`이다. 이 변경은 하나의 단위로 적용한다.

`check.passed`는 앞으로도 전체 구조 검사에 문제가 없다는 뜻으로 유지한다. 오류가 있는데 true로 바꾸지 않는다. 그와 별개로 중앙이 계산하는 `capture_eligible`을 검사 기록에 추가하는 안을 제안한다. 이는 정확한 주 응답, `activity-extensions.json`의 확장 데이터, 수집 파일을 한 후보로 봉인하여 묶음 적용기에 넘길 수 있다는 뜻이며 각 묶음의 수락이나 수학적 승인을 뜻하지 않는다. 오류를 포함한 후보의 봉인은 기존 계약이 독립 분할을 허용하는 일반 연구 응답에서만 허용한다.

분할 자격은 기존 `integration._split_research(context)`를 사용한다. 현재 조건은 역할이 `research_work` 또는 `supplemental_research`이고, `review_cycle_id`와 비어 있지 않은 `revision_targets`가 없는 경우다. 여기에 생산자가 유효한 `integration_bundles`를 명시하고 실제 독립 묶음이 둘 이상이라는 조건을 적용한다. 선언 생략으로 구성한 기본 단일 묶음이나 검토·개정의 단일 판단 응답에 부분 봉인을 적용하지 않는다.

| 검사 결과 | capture_eligible | 후속 |
|---|---|---|
| JSON 해독 실패, 전체 응답 형식 결함, 구성원 소유·참조 결속을 확정할 수 없는 선언, 필수 파일 보존 실패 | false | 원문과 오류를 보존하고 전체 반환 |
| 독립 분할을 허용한 응답이고 공통 조건이 유효하며, 국소 오류가 없는 묶음이 하나 이상 남아 있음 | true | 원문 전체를 한 번 봉인하고 각 묶음의 오류를 적용기에 전달 |
| 단일 판단 묶음에 오류가 있거나 모든 묶음에 구조 오류가 있음 | false | 기존 전체 반환 유지. 조기 제출자는 같은 실행에서 초안을 고쳐 다시 제출 가능 |
| 검사 문제가 없음 | true | 같은 봉인·적용 경로 사용 |

국소 오류로 분류하려면 해당 구성원의 좌표와 유일한 소유 묶음이 확정돼 있어야 한다. 생산자가 출력한 오류 분류나 독립성 주장만 믿지 않는다. 단순히 `integration_id`가 붙었다는 이유로 모든 오류를 국소 오류로 바꾸지 않는다. 공통 형식·소유·참조 결속을 먼저 확인하고, 이미 있는 묶음별 검사 결과를 사용한다.

봉인 후보의 정체성은 원 응답·확장·파일 바이트와 해시를 그대로 사용한다. 정상 묶음을 추출해 새 JSON을 만든 뒤 그것을 원 응답처럼 봉인하지 않는다. `apply_bundles`가 기존 방식으로 정상 묶음을 수락하고 오류 묶음만 반환한다. 전부 반환된 경우에도 원문·오류와 수리 계보는 남긴다. `output_accepted`와 부분 편입의 구분은 유지한다.

함께 바꿀 소비자는 다음과 같다.

- `read_sealed_submission`은 무조건 `check.passed`를 요구하지 않고, 봉인 영수증·정확한 바이트·공통 조건과 중앙의 capture_eligible 판정을 대조한다. 잘못된 후보를 단순 플래그 하나로 통과시키지 않는다.
- `summarize_snapshot_checks`와 상태 검사는 accepted 영수증을 구성원 전건의 passed와 같은 것으로 해석하지 않는다. 접수된 후보, 검사 오류, 실제 편입 결과를 각각 보고한다.
- 정상 native final과 명시적 조기 제출은 같은 판정을 사용한다. `delivery.state=accepted`는 후보가 고정됐다는 뜻이며, 국소 오류와 향후 반환 가능성을 응답·문서에 명시한다. 접수 뒤 다른 final로 대체할 수 없다는 규칙은 유지한다.
- preview도 같은 복사본 적용 경로를 사용한다. 로컬 `--output` 진단의 passed/종료 코드는 전체 검사 결과를 계속 나타내고, 중앙 접수의 delivery 결과와 혼동하지 않도록 CLI 문서를 맞춘다.
- 부분 수락 후 수리는 수락된 integration ID와 주 응답의 해시를 유지하고 반환 묶음만 다룬다. 현재 `accepted_response`, `accepted_integration_ids`, `repair_responses` 검사를 재사용한다.

과거의 성공 검사에는 새 필드가 없으므로, 기존 accepted 영수증과 `passed=true`, 빈 issues가 모두 맞는 경우 기존 의미로 읽는다. 과거에 거부된 결과를 새 규칙으로 소급 접수하지 않는다. 새 필드와 소비 규칙의 변경은 검사 계약 문서에 명시하고, 재열람 검사와 영수증 해시를 함께 확인한다.

완료 확인은 독립 A·B 중 B의 지식 의존 참조만 틀린 응답을 실제 중앙 포착 경로에 넣는 사례다. A는 한 번 편입되고 B만 반환돼야 한다. 같은 사례를 native final, 조기 제출, preview에 각각 적용하고 preview는 저장을 바꾸지 않아야 한다. B 수리·재접수와 저장 실패 뒤 재시작에서도 A를 중복 적용하면 안 된다. 전체 JSON 파손과 묶음 결속 파손은 계속 전체 거부돼야 한다. 단일 판단 묶음의 오류나 정상 묶음이 하나도 없는 조기 제출은 접수하지 않아야 한다.

**F7. 호스트 자원 설정을 공개 진입점에 연결한다.**

변경 위치는 `engine.py`의 `validate_config`·`initialize`, [governance_engine.py](../../.claude/skills/do-math/scripts/do_math/governance_engine.py)의 `_configure_candidate`, [execution_profiles.py](../../.claude/skills/do-math/scripts/do_math/execution_profiles.py)의 호스트 계약 생성, [session_slots.py](../../.claude/skills/do-math/scripts/do_math/session_slots.py)의 `configure`와 승인 결박, 저장 설정 스키마다.

`host_resources`를 허용 키에 연결하되 현재 양의 정수만 받는 `OPTIONAL_CONFIG` 반복문에 그대로 넣지 않는다. 구조화 설정으로 구별하여 기존 `validate_host_constraint`, 역할별 demands 검사와 동일한 규칙을 사용한다. 승인 객체의 ID 계산은 기존 `host_constraint`를 재사용하며 한도·운영 예비 자원·역할별 요구의 실제 숫자는 사용자 승인 입력에서 받는다. 임의 기본 상한을 만들지 않는다.

공개 설정은 기존 생성기가 읽는 `host_resources={constraint, demands_by_role}` 구조를 사용한다. `constraint`는 `host_constraint(host_id, limits, control_reserve, authority_refs)`가 생성하는 다음 객체이며 ID를 임의 문자열로 바꾸지 않는다.

| 필드 | 의미·단위 |
|---|---|
| `constraint.id`, `kind`, `scope`, `host_id` | 내용으로 계산한 CP 식별자, `host`, `instance_on_host`, 실제 대상 호스트 식별자 |
| `constraint.max_jobs` | 같은 호스트에서 이 인스턴스가 허용한 동시 Job 수 |
| `constraint.memory_bytes` | 이 인스턴스에 승인한 메모리 바이트. Job 검사는 committed memory를 다루며 RSS와 구별 |
| `constraint.cpu_rate_basis_points` | CPU 비율의 1/10000 단위, 기존 검사 범위 0~10000 |
| `constraint.control_reserve` | `jobs`, `memory_bytes`, `cpu_rate_basis_points`별 제어용 예비 자원. 각 승인 한도 이하이며 작업이 차용하지 않음 |
| `constraint.authority_refs` | 사용자가 승인한 해당 제약의 근거 참조 |
| `demands_by_role[역할]` | `jobs=1`, 양의 `memory_bytes`, 1~10000의 `cpu_rate_basis_points`로 나타낸 역할별 실행 요구 |

필수 역할 목록은 별도 상수로 복제하지 않고 `build_profiles`가 만드는 역할에서 얻는다. 기존 생성기가 요구하는 역할별 선언과 아래의 Lean 적용 예외를 함께 검사한다. 승인 한도 값이나 호스트 이름을 예시의 숫자·문자열로 자동 채우지 않는다.

호스트 제약은 사용자 소유 자원 설정이므로 `_configure_candidate`의 operator 변경 금지 목록에도 넣는다. 선택 설정이 없는 기존 인스턴스도 읽을 수 있도록 이 항목의 변경 비교에는 `candidate.get('host_resources')`와 `current.get('host_resources')`를 사용한다. `init`과 사용자 configure, 독립 검사를 거친 configuration 수입은 같은 설정 검사·프로필 생성 경로를 사용한다. 공개 CLI의 설정 설명과 예시에 필드 구조, 단위, 호스트 식별자와 사용자 채택 절차를 적는다.

첫 채택과 기존 호스트 제약의 변경·해제는 실행기가 정지하고 미종료 execution과 점유 예약이 없는 경우에 적용하는 안을 권고한다. 실행 중 Job의 상한을 소급 변경하는 기능은 만들지 않는다. 변경 요청이 inbox에서 나중에 처리될 때도 이 조건을 적용 시점에 확인한다. 이미 승인된 같은 값을 재적용하는 요청은 멱등하게 처리한다.

해제를 지원하려면 공개 설정의 `host_resources=null`을 명시적 해제로 정의하고 저장 스키마도 nullable로 맞춘다. 이 경우에도 같은 사용자 권한과 정지·무점유 조건을 요구한다. 호스트 설정을 생략하는 부분 configure는 기존 값을 유지한다. 적용기는 실행횟수 모드와 동시 세션 모드 모두에서 생성 결과의 `host_capacity_ref`를 저장하거나 해제하고, 이전 프로필·제약 기록은 이력과 종료 실행의 근거로 보존한다.

새 프로필이 생성되면 현재 역할 참조와 미시작 기본 배정을 갱신한다. 기존 과제에 고정된 프로필을 조용히 바꾸지 않으며 필요한 재준비·계약 검토와 실제 능력 관측을 거친다. `formal_check`, `trust_check`, `trust_activate`에 호스트 상한을 붙이지 않는 현행 Lean 계약은 유지한다. 다른 AI 실행과 외부 기계 역할에 대한 기존 적용 범위를 임의로 넓히거나 줄이지 않는다.

완료 확인은 공개 init와 configure가 올바른 구조를 저장하고 해당 프로필·예약을 만드는 것부터 수행한다. operator 출처 변경, 잘못된 단위·숫자·호스트, 누락된 역할 요구, 실행 중 변경은 거부해야 한다. 실행횟수 모드와 동시 세션 모드, 동일 값 재적용, 명시적 해제, 과거 프로필을 사용한 종료 실행의 예약 반환과 새 배정까지 확인한다. 실제 Job 상한 검사는 승인된 값의 적용 사실만 입증하며 호스트 전체 격리의 증거로 확대하지 않는다.

**F8. 기한 없는 연구 실행의 자체 형식화 조건을 고친다.**

변경 위치는 [연구 수행 계약](../../.claude/skills/do-math/계약/연구-수행.md)의 같은 실행 내 형식화 조건이다. 작업 예산의 무기한 실행과 기초 정의 재사용, 먼저 계약 질문에 답하기, 형식화를 과제 완료 조건과 분리하는 기존 결정은 유지한다.

현재의 마지막 조건을 다음 의미로 교체하는 안을 권고한다. 이는 제안 문구이며 아직 적용하지 않았다.

> 계약 질문에 대한 산출을 보존한 뒤, 형식화로 얻을 추가 검증·재사용의 이익이 추가 작업에 비해 있다고 판단한다. 현재 실행에 종료 기한이 적용되면 그 안에 필요한 검사와 제출을 마칠 수 있는지도 확인한다. 기한이 없으면 기한의 부재를 보류 사유로 삼지 않고, 앞의 형식화 조건과 이익 판단에 따라 착수한다. 진행 중에는 기존 관찰·정지 규칙을 따른다.

형식화가 막혔을 때 비형식 결과와 이유를 반환하는 규칙은 유지한다. 새 시간 상한이나 고정 시도 횟수는 추가하지 않는다. 문서 확인은 기한 없는 정상 실행, 명시적 기한이 있는 실행, 질문에 아직 답하지 못한 실행, 필요한 기초 정의가 없는 실행을 비교하여 의도대로 읽히는지 본다.

**적용 순서와 확인 단위**

구현 시에는 F1, F2→F3, F4·F5, F6, F7 순서로 서로 구분되는 변경을 만든다. F8과 각 항목의 역할·CLI 설명은 해당 동작 변경과 함께 맞춘다. F2의 공통 미완료 처리가 F3의 선행 작업이다. F6은 봉인·재열람·집계·preview·두 제출 경로를 분리해서 배포하지 않는다. 그 밖의 독립 항목을 하나의 큰 상태 재설계로 묶지 않는다.

| 변경 | 우선 보강할 기존 검사 파일 | 실제로 이어 확인할 경계 |
|---|---|---|
| F1 | `test_machine_scheduling.py`, `test_lifecycle_engine.py` | pause·회수·재개·새 formal execution·검토 요청 |
| F2·F3 | `test_review_scope_wire.py`, `test_review_engine.py`, `test_review_research.py`, `test_input_recovery.py` | 입력·배정 거부부터 활동 정산·다음 계획의 실제 입력·재시작 |
| F4 | `test_task_scope.py`, `test_planning.py` | 실제 계획 입력 선별부터 이전·계약 재검토·Git 재열람 |
| F5 | `test_submission_tools.py`, `test_review_research.py` | 공유 검사와 최종 소비자의 같은 참조 판정 |

표의 파일은 모두 `.claude/skills/do-math/scripts/tests/` 아래에 있다. 함수에 임의 상태를 직접 주는 검사만으로 완료하지 않고, 문제를 만들었던 실제 입력 생성기와 공개 수신 경로를 포함한다. 모델 응답을 대역으로 정한 검사와 실제 Git·프로세스·Lean·모델 실행은 증거 범위를 나눠 기록한다. 저렴한 구조·전이 검사로 먼저 결함을 드러내고, 수정한 프로세스 경계에 필요한 실제 실행만 추가한다. 이미 통과한 검사를 새로운 변경이나 실패 이유 없이 반복하지 않는다.

구현을 마칠 때는 수정 항목의 검사와 결합 회귀, 저장된 판본의 재열람, 이전 성공 영수증의 호환성을 확인한다. 정본 변경을 `.agents/skills/do-math` 생성 사본에 반영하고 드리프트도 검사한다. 별도 검증 없이 과거 연구 인스턴스의 HOLD를 풀거나 기록을 변환하지 않는다. 커밋·푸시를 수행하는 작업이라면 그 시점의 `commit-harness`를 따른다.

이 제안의 완료 조건은 8건마다 수정 위치·전이·소비자·확인 사례가 구체화되고 현재 변경과 충돌하지 않는 것이다. 구현 완료 조건은 각 후속 의무가 실제 소비자까지 한 번 전달되고, 반대로 허가·현재성·종료 증거가 부족한 경우에는 실행이나 수락이 일어나지 않는 것이다. 현재 기록은 전자의 산출이며 후자의 검증 결과가 아니다.
