## 요약

do-math는 같은 사실을 여러 단계에서 반복해 확인하고, 그 확인의 상당수를 AI의 의도적 변조에 대비한 강도로 수행한다. 이번 설계는 두 가지를 바꾼다.

첫째, 위협 모델을 우발적 변경으로 좁힌다. 우발적 변경은 업데이트, 재설치, 동기화, 실수, 디스크 손상을 말한다. AI의 의도적 변조는 고려하지 않는다.

둘째, 모든 검사를 "무엇을 막으려고 존재하는가"로 분류한다. 의도적 변조에만 의미가 있는 검사와 같은 사실을 반복하는 재관측은 사용 경로에서 없앤다. 우발적 변경을 막는 검사는 사건이 일어날 때 기준을 만들고, 사용할 때는 값싼 메타데이터로 대조하는 형태로 바꾼다.

이 원칙을 적용하면 세 곳이 크게 달라진다.

- **신뢰 환경**: 설치 전체 137,272개 파일·약 11.0GB의 전 바이트 해시를 사용 경로에서 없앤다. 대신 툴체인 판본 식별과 `.olean` 약 11,000개의 메타데이터 지문으로 확인한다. 지문 대조 한 번은 실측으로 약 1.2초가 걸린다.
- **취소 확인**: 계산 스레드가 실행기 메인 루프를 왕복해 약 1초씩 기다리던 구조를 없앤다. 실행기가 판단을 계산해 플래그로 알리고, 계산 스레드는 플래그만 읽는다.
- **상태 검증**: 실행기가 방금 검증해 게시한 상태를 다시 전부 검증하지 않는다. 새로 들어온 것만 검사한다. 44MB manifest도 연구 상태에서 뺀다.

목표는 초기화 10분대(AI 판단 시간이 지배), 결과 1건당 환경 확인 수 초다. 이번 초기화는 활성화 검사 하나만으로 7시간 이상이 예상되어 중단했다. 남는 위험은 파일의 메타데이터를 바꾸지 않는 우발적 손상(비트 부패 등)이며, 이는 선택적 전수 점검으로만 잡는다.

설계 과정에서 열려 있던 세 사항(재기록 권한, 전수 점검 시점, 기존 인스턴스 처리)은 연구 책임자가 결정했다. 결정은 1.1의 D5~D7이다.

## 2. 검사 분류 원칙

모든 검사를 존재 이유에 따라 다섯 기능 가운데 하나로 분류하고, 기능마다 정해진 처분을 적용한다. 개별 항목의 처분은 모두 이 표에서 나온다.

| 기능 | 정의 | 처분 |
|---|---|---|
| 식별 | 어떤 판본·바이트를 가리키는지 고정한다. 정확한 참조, 봉인 해시, 입력 manifest가 여기에 속한다. | 생성 시점에 한 번 계산해 기록한다. 같은 바이트를 다시 해시해 같은 값을 확인하는 재계산은 없앤다. 다른 기록과의 대조(기록값 == 기록값)는 유지한다. |
| 우발 탐지 | 업데이트·재설치·동기화·실수·손상에 따른 변경을 탐지한다. | 사건(설치·교체·전환) 때 기준을 만들고, 사용 시에는 메타데이터 지문으로 대조한다. 지문이 다를 때에만 내용을 확인한다. |
| 변조 방어 | 같은 사용자 권한의 행위자가 의도적으로 바꾸는 것을 막거나 탐지한다. | 없앤다(D1). 그 검사가 우발적 변경도 함께 막고 있었다면, 우발 탐지에 필요한 가장 싼 형태만 남긴다. |
| 의미 현재성 | 연구 전제·계약·입력의 내용이 바뀌었는지를 판정해 연구 의미를 지킨다. | 유지한다. 다만 같은 상태 판본(head 또는 변경 세대)에 대해서는 한 번만 계산하고, 결과를 재사용한다. 계산 위치는 4절을 따른다. |
| 기타 | CAS, 더티 검사, 도구 탐지 등 위 넷에 속하지 않는 것 | 기능별로 판단한다. 같은 판정을 반복하는 것은 한 번으로 줄인다. |

기능이 둘 이상으로 해석되는 검사는 다음 규칙으로 판정한다. **그 검사가 탐지하는 사건이 의도적 행위 없이 일어날 수 있는가**를 묻는다. 일어날 수 없으면 변조 방어로 보고 없앤다. 일어날 수 있으면 우발 탐지로 보고 사건 기반 기준과 지문 대조로 바꾼다. 예를 들어 저장소 경로가 다른 볼륨으로 바뀌는 일은 재마운트나 이동으로 우연히 일어날 수 있다. 반면 열린 파일을 경로 교체 경쟁으로 바꿔치는 일은 의도 없이 일어나기 어렵다.

"같은 사실의 반복 확인"은 기능과 무관하게 없앤다. 실행기가 방금 검증해 게시한 바이트를 같은 프로세스가 다시 검증하는 경우가 그렇다. 이미 계산해 반환된 해시를 같은 원문에서 다시 계산하는 경우도 여기에 해당한다.

## 3. 신뢰 환경 재설계

### 3.1 무엇을 보장하는가

신뢰 환경이 보장해야 하는 것은 "형식 검사에 쓴 Lean·Mathlib이 채택한 바로 그 판본이며, 채택 이후 우발적으로 바뀌지 않았다"는 것이다. 이 판단에 들어가는 파일은 다음과 같다.

- Lean 실행 파일(`lean.exe`, `lake.exe`)
- 판본을 고정하는 파일: `lean-toolchain`, `lake-manifest.json`, lakefile
- 커널이 import할 때 적재하는 `.olean`: Mathlib과 의존 패키지 약 8,652개(1.88GB), Lean 코어 약 2,433개
- do-math의 형식 검사기 코드(`formal.py`)

나머지 파일은 판정에 들어가지 않는다. `.lean` 소스, `.ilean`, `.trace`, `.hash`, `.c`, `.ir`, git 메타데이터가 그렇다. 이 파일들이 현행 관측 대상 137,272개의 대부분을 차지한다.

### 3.2 새 구성

**툴체인 기록.** 툴체인은 머신의 인스턴스들이 공유하는 `.skill-workspace/do-math-toolchains/` 아래의 설치다. 기록은 `.skill-workspace/do-math-toolchains/records/<기록 ID>.json` 파일로 둔다. 기록 ID는 판본 식별과 첫 기준 항목의 내용 해시 다이제스트를 함께 해시한 값이다. 따라서 판본 식별이나 판정 바이트가 바뀐 설치는 새 ID의 새 파일을 얻고, 옛 기록 파일은 그대로 남는다. 옛 기록을 결박한 인스턴스는 전환 전까지 옛 기록을 읽는다. `setup_lean.py`가 설치하거나 교체할 때 만들며, 인스턴스는 이 기록을 참조만 한다. 기록에 담는 내용은 다음과 같다.

| 항목 | 내용 | 기존 구현과의 관계 |
|---|---|---|
| 판본 식별 | `lean --version` 출력, 구성된 Lean 명령(`lake.exe --dir <프로젝트> env lean.exe`)의 인자 가운데 `.exe`·`.dll` 파일 전부의 SHA-256(현행 `inspect_toolchain`의 `executables`, `formal.py:369-370`), `lean-toolchain`·`lake-manifest.json`·lakefile의 SHA-256, 프로젝트 소스 식별(git tree·diff 해시), Lake 검색 경로 | `formal.py`의 `inspect_toolchain`(`:354-374`)과 `_project_identity`(`:324-351`)가 이미 계산한다. 그대로 쓴다. |
| 검사기 식별 | `formal.py`의 SHA-256과 경로 | `inspect_toolchain`의 `verifier_sha256`·`verifier_path`를 그대로 쓴다. |
| 기준 이력 | 기준 항목의 목록. 항목 하나는 `.olean` 지문 기준, 내용 해시 기준, 대표 검사 결과, 기록 시각으로 이루어진다. 마지막 항목이 현재 기준이다. | 새로 만든다. |
| 점검 이력 | 선택적 전수 점검 결과의 목록. 항목 하나는 점검 시각, 대조한 기준 항목의 번호, 결과(`passed` 또는 `mismatch`), 불일치 파일 목록으로 이루어진다. 현재 기준 항목 이후에 `mismatch` 항목이 하나라도 있으면, 새 기준 항목이 덧붙을 때까지 그 기록을 쓰는 활성화와 형식 검사를 멈춘다. | 새로 만든다. |

기준 항목의 세 구성은 다음과 같다.

- **`.olean` 지문 기준**: 판정 관련 `.olean` 전건의 지문 목록과 그 다이제스트
- **내용 해시 기준**: 같은 파일 전건의 SHA-256 목록과 그 다이제스트. 선택적 전수 점검과 재기록이 이 기준과 대조한다.
- **대표 검사 결과**: `n + 0 = n`과 `norm_num` 예제를 실제 명령으로 컴파일한 결과(명령, 종료 코드, 출력, 시각). 현행 `verify_environment`의 대표 컴파일을 그대로 쓴다. 컴파일 전후의 전수 inventory는 없앤다.

내용 해시 기준은 설치·교체와 재기록 때에만 계산한다. 대상은 지문 대상과 같은 약 11,000개 파일(약 2.3GB)이다. 과거 실측(8.55GB에 약 159~199초, M-0341)에 비추어 1분 안팎으로 예상하지만 측정하지 않았다. 이 값은 설치 비용을 가늠하는 계획치이며 9절의 완료 기준에 넣지 않는다. 이 비용은 툴체인 설치에 붙으며, 인스턴스 초기화에는 들어가지 않는다.

**지문의 정의.** 지문은 `os.scandir`가 추가 시스템 호출 없이 돌려주는 값만으로 만든다.

- 파일 하나의 지문 행은 (상대 경로, `st_size`, `st_mtime_ns`, `st_birthtime_ns`)다. 세 값은 `DirEntry.stat(follow_symlinks=False)`에서 얻는다. `st_birthtime_ns`는 생성 시각이며, Python 3.12의 Windows `scandir`가 제공한다(현 머신에서 확인).
- 상대 경로는 기준 root(툴체인 디렉터리 또는 Mathlib 프로젝트 디렉터리)에 대한 경로다. 구분자를 `/`로 바꾸고 대소문자는 그대로 둔다. root 이름을 앞에 붙여 두 root의 행을 구별한다.
- 지문 다이제스트는 행들을 상대 경로 순으로 정렬해 정규 JSON(`canonical_json`)으로 직렬화한 바이트의 SHA-256이다.

Windows에서 `DirEntry.stat()`은 파일 ID(`st_ino`)를 0으로 돌려준다. 파일 ID를 넣으려면 파일마다 `os.stat`을 불러야 한다. Mathlib `.lake`의 `.olean` 8,652개로 잰 결과, `scandir`만 쓰면 0.8초, 파일마다 `os.stat`을 더하면 약 8초였다(실측). 3.3에서 말하는 지문 대조 약 1.2초는 여기에 Lean 코어 `.olean` 2,433개(0.4초)를 더한 값이다. 대신 생성 시각을 넣는다. 파일을 새로 만들어 교체하면서 수정 시각만 보존하는 경우(예: 압축 해제)를 생성 시각이 잡아내므로, 파일 ID의 역할을 대신한다. NTFS의 시각 해상도는 100ns다.

**인스턴스 기록.** 인스턴스의 신뢰 환경 기록에는 전체 파일 목록을 넣지 않는다. 다음만 둔다. 크기는 수 KB 수준이다.

- 판본 식별과 검사기 식별(툴체인 기록에서 복사한 값)
- 툴체인 기록 파일의 경로
- 결박한 기준 항목의 지문 다이제스트, 내용 해시 다이제스트, 대표 검사 결과의 요약 해시. 요약 해시는 대표 검사 결과의 `command`, `source_sha256`, `exit_code`, `stdout`, `stderr`, `started_at`, `finished_at`을 담은 객체를 정규 JSON(`canonical_json`)으로 직렬화한 바이트의 SHA-256이다.

현행 44MB manifest의 `scope`와 `files`는 없앤다.

**인스턴스가 툴체인 기록에서 확인하는 것.** 인스턴스는 툴체인 기록 파일의 바이트 해시에 결박하지 않는다. 확인할 때마다 기록 파일을 읽어 다음을 본다.

1. 기록의 구조가 스키마에 맞는가. 툴체인 기록은 `schema` 필드에 `do-math-toolchain-record/1`을 담는다. 스키마는 툴체인 기록 모듈(8절 1단계에서 다시 쓰는 `trust_inventory.py`)에 JSON Schema로 정의하고, 기록을 읽을 때마다 검증한다. 판본이 다른 기록은 읽지 않는다(프리알파 원칙).
2. 기록의 판본 식별과 검사기 식별이 인스턴스 기록과 같은가
3. 기록의 현재 기준 항목이 성공한 대표 검사 결과를 갖는가
4. 현재 기준 항목 이후의 점검 이력에 불일치가 없는가

툴체인 기록에 허용하는 변경은 두 가지다. 기준 이력에 항목을 덧붙이는 것(3.4의 재기록)과 점검 이력에 결과를 덧붙이는 것이다. 한 기록 파일 안에서 판본 식별이나 검사기 식별이 바뀌는 일은 허용하지 않는다. 그런 파일을 읽으면 활성화와 형식 검사를 멈춘다. 실제 설치가 바뀌었으면 `setup_lean.py`가 새 ID의 기록을 만들고, 인스턴스는 3.4의 1번 경로(등록과 전환)로 그 기록에 옮겨 간다. 이렇게 하면 재기록이 기록 파일을 다시 써도, 판본 식별이 같은 한 인스턴스가 깨지지 않는다.

**형식 검사의 확인 결과를 게시에서 쓰는 방식.** 형식 검사는 컴파일 전에 확인한 판본 식별 다이제스트와 기준 항목의 지문 다이제스트를 형식 결과 기록에 남긴다. 게시 관문은 두 가지를 확인한다. 첫째, 형식 결과에 남긴 판본 식별 다이제스트가 인스턴스 기록의 판본 식별 다이제스트와 같은가. 둘째, 실제 파일에서 게시 시점에 새로 계산한 판본 식별 다이제스트도 인스턴스 기록의 것과 같은가. 지문 다이제스트는 추적용으로만 남기고 게시 판정에는 쓰지 않는다. 형식 검사와 게시 사이에 실행기가 재시작해도 기록이 상태에 남아 있으므로 효력은 같다. 그사이 3.4의 재결박이 일어나도 마찬가지다. 재결박은 판본 식별이 같을 때만 일어나고, 게시 판정은 판본 식별로 하기 때문이다.

형식 결과를 기록하는 단계는 지금도 파일을 관측하지 않는다(`engine.py:4492`, `:4599`의 `verify_files=False`). 따라서 전수 관측이 붙은 사용 관문은 형식 검사 전후, 동일성 `match` 게시, 목표 감사 적용의 셋이다.

형식 검사 뒤의 관문(게시·감사)에서 지문을 다시 대조하지 않는 이유가 있다. 검사와 게시 사이에 툴체인이 우연히 바뀌는 사건은 드물고, 바뀌었더라도 다음 형식 검사에서 드러난다. 판본 식별은 싸기 때문에 게시 때도 확인한다.

### 3.4 지문 불일치와 재기록

지문이 기준과 다르면 형식 검사를 시작하지 않고 원인을 둘로 나눈다.

1. **판본 식별도 다른 경우**: 툴체인이 실제로 바뀐 것이다. 새 툴체인 기록을 만들고, 현행 `trust register`와 `trust transition` 흐름으로 옮긴다. 기존 K의 재검사도 이 흐름에 포함된다.
2. **판본 식별은 같고 지문만 다른 경우**: 재설치, 캐시 재다운로드, 복원처럼 같은 바이트를 다시 깐 경우가 대부분이다. 이 경우 새 재기록 모드(`setup_lean.py --rerecord`)가 다음을 수행한다. 종료 코드는 기록 성공 0, 거부(내용 불일치 또는 대표 컴파일 실패) 1, 실행 오류 2이며, 결과는 JSON으로 출력한다.
   - 지문 대상 전건의 내용 해시를 새로 계산해 현재 기준의 내용 해시와 대조한다.
   - **내용이 모두 같으면** 메타데이터만 바뀐 것이다. 대표 컴파일을 다시 수행하고, 통과하면 기준 이력에 새 항목(새 지문, 같은 내용 해시, 대표 검사 결과)을 덧붙인다. 파일 교체는 기존 원자적 교체 경로(`file_io`)를 쓴다. 바이트가 같으므로 전환이나 K 재검사를 요구하지 않는다.
   - **내용이 하나라도 다르면** 재기록을 거부하고 다른 파일 목록을 보고한다. 판본 식별이 같아도 판정에 쓰이는 바이트가 바뀌었으므로, 1번과 같이 새 환경으로 다룬다. 새 툴체인 기록을 만들고 전환과 기존 K 재검사를 거친다.

각 인스턴스는 다음 활성화 검사나 형식 검사 때 스스로 새 기준에 다시 결박한다. 재결박은 기준을 만들지 않는다. 재기록 명령이 이미 명시적으로 덧붙인 기준을 인스턴스가 따라가는 것뿐이다. 조건은 셋이다. 첫째, 현재 파일의 지문이 툴체인 기록의 현재 기준과 같다. 둘째, 그 기준은 인스턴스가 결박한 기준과 다르다. 셋째, 판본 식별은 인스턴스 기록과 같다. 세 조건이 모두 성립하면 실행기는 결박 다이제스트를 새 기준으로 바꾸고, 그 사실을 사건으로 기록한 뒤 계속 진행한다. 사건에는 이전·새 다이제스트와 기록 이력의 해당 항목을 담는다. 여러 인스턴스가 같은 툴체인을 쓰면 각자 다음 확인 때 이 절차로 따라온다. 현재 파일의 지문이 툴체인 기록의 현재 기준과도 다르면 재기록이 아직 이루어지지 않은 것이므로 1·2의 판별로 돌아간다.

툴체인 기록을 쓰는 명령(`setup_lean.py`의 설치·`--rerecord`·`--check-contents`)은 `records/` 디렉터리의 잠금 파일로 서로 배제한다. 쓰기는 기록을 읽고, 이력에 항목을 덧붙이고, 원자적으로 교체하는 순서로 한다. 인스턴스는 기록을 읽기만 하므로 잠금을 잡지 않는다.

형식 검사나 활성화 검사는 기준을 자동으로 새로 쓰지 않는다. 이것은 확정 사항이다. 자동으로 쓰면 우발적 변경을 탐지하는 목적이 사라지기 때문이다. 재기록 명령은 사용자와 운전자만 실행한다(D5). 설치 복구 AI는 재기록하지 않는다. 지문 불일치로 멈춘 연구는 사람이 재기록할 때까지 기다리며, 그래서 예상하지 못한 지문 변화는 반드시 사람에게 알려진다.

활성화 기계 작업(`trust_activate`)과 전환 흐름, 기존 K의 재검사, 동일성 재검토의 승계 규칙은 유지한다. 전환이 원자적으로 새 환경을 적용한다는 계약도 그대로다.

## 4. 취소·관찰 콜백

### 4.1 현행 구조와 문제

`parallel.py:45-47`의 `start_call`은 계산 함수에 넘기는 세 콜백을 감싼다. 대상은 `should_stop`, `on_started`, `on_observation`이다. 감싼 콜백은 계산 스레드에서 호출되면 이벤트 큐에 요청을 넣고, 실행기 메인 스레드가 처리할 때까지 멈춘다(`:21-33`). 메인 스레드는 요청을 루프 한 바퀴에 한 번 처리한다(`collect()` 끝의 `pump()`, `:106`). 따라서 콜백 한 번의 비용은 루프 한 바퀴 시간이다. 이번 활성화에서 `should_stop` 2,340회의 중앙값은 1.005초였다.

한 바퀴가 긴 이유는 루프가 매번 여러 비싼 확인을 하기 때문이다. 설치본 재해시(R1), 능력 증거의 CLI 전 바이트 해시(R22), 새 head 전체 검증(R3) 등이 여기에 해당한다. 게다가 콜백 안의 판단 자체도 무겁다. AI 실행의 `should_stop`(`engine.py:3502-3543`)은 제어 적용, 권한, 전제 변경, 원자료 현재성을 모두 다시 계산한다. 형식 검사의 `stop`(`engine.py:4539-4560`)은 신뢰 환경 전체를 비교한다. 계산 쪽은 이 콜백을 매우 자주 부른다. 모델 실행은 0.2초마다, Lean 실행 대기는 0.02초마다 부르고, 파일 해시는 1MiB마다, 출력 파싱은 줄마다 부른다.

### 4.2 새 구조

판단(무엇이 멈춤 사유인가)과 신호(멈춰라)를 분리한다.

1. **실행마다 정지 플래그 하나를 둔다.** `threading.Event`를 쓴다. 계산 함수는 `should_stop` 대신 이 플래그를 읽는다. 읽기는 원자 연산이라 호출 빈도와 무관하게 비용이 없다.
2. **판단은 실행기 메인 스레드가 한다.** 새 계약은 다음과 같다. 정지 사유가 되는 상태 변경은 모두 게시를 거친다. 메인 스레드는 상태를 게시한 직후(`engine.py`의 `_save` 게시 지점) 상태 기반 사유를 한 번 평가한다. 게시되지 않은 메모리상의 변경은 정지 사유로 평가하지 않는다. 상태 기반 사유는 권한, 전제 변경, 원자료 현재성, 학술 요구, 계약 해시, 목표 판단 근거, 신뢰 환경 동등성, 정지·종결 요청이다. 현행 AI 실행의 `should_stop`(`engine.py:3502-3543`)이 확인하는 사유와 그 변경 경로는 아래 표와 같다. 표의 "평가 방식" 열에서 "게시 직후"로 적은 행은, 그 사유를 바꾸는 경로가 게시로 끝난다는 설계 판단에 기댄다. 이 판단은 아직 코드로 확인하지 않았다. 8절 구현 순서의 3단계에서 행마다 사유를 바꾸는 시험을 하나씩 두어 확인한다. 게시하지 않고 사유를 바꾸는 경로가 나오면 그 경로에 게시를 추가한다.

   | 사유 (현행 좌표) | 바뀌는 경로 | 평가 방식 |
   |---|---|---|
   | 실행별 정지 요청, pause·close (`_execution_stop_requested`, `:3525`) | 사용자·운영 제어 적용(`_controls`) | 게시 직후 |
   | 권한 (`governance.authorize`, `:3509`) | grant 결정 제어 | 게시 직후. 만료는 시간 기반 |
   | 통치 판본 (`_governance_revisions`, `:3510`) | 헌장·정책 결정 제어 | 게시 직후 |
   | 결정 근거 변경 (`decision_basis_changes`, `:3511`) | 지식·과제·결과 적용 | 게시 직후 |
   | 실행 요구 조건 (`_execution_requirement_changes`, `:3512`) | 설정 변경, 프로필·능력 증거 변경 | 게시 직후 |
   | 목표 감사 근거 (`_goal_basis_key`, `:3513`) | 지식·형식 결과·환경·과제 변경 | 게시 직후 |
   | 원자료 현재성 (`sources_current`, `:3517`) | `source` 제어 | 게시 직후 |
   | 학술 요구 (`:3518`) | 헌장 결정 제어 | 게시 직후 |
   | 계약 해시·과제 종결 (`:3520-3522`) | 후보 준비·연구 계획 결과 적용 | 게시 직후 |
   | 관찰 대상 종료 (`_obsolete_action_reason`, `:3507`, 운영 점검 전용) | 대상 실행의 종료 적용 | 게시 직후 |
   | 조기 제출 (`submission_intent`, `:3525`) | 제어 수신(transport) | 수락 시 (5항) |
   | 호출 기한 (`call_deadline`, `:3527`), 마무리 예고 (`request_finish`, `:3529`) | 시간 경과 | 시간 기반 (3항) |
   | 대화 lease (`_check_conversations`, `:3505`) | 시간 경과, 대화 제어 | 시간 기반과 게시 직후 |
3. **시간 기반 사유는 싼 시각 비교로 한다.** 호출 기한, 허가 만료, 대화 lease 만료, clock guard, 제한 복구 만료, 마무리 예고가 여기에 해당한다. 루프마다 다음 만료 시각과 현재 시각만 비교한다.
4. **실행기가 종료할 때**(`ModelCalls.close`) 모든 플래그를 세운다. 현재 stop 콜백이 종료 중에 참을 돌려주는 동작과 의미가 같다.
5. **작업자의 조기 제출**이 수락되면 해당 실행의 플래그를 세운다. 지금은 제어 수신(transport pump)이 콜백 경로에서만 돈다. 메인 루프 맨 위의 호출(`scheduler.py:500`)은 `self._controls(pump=False)`여서 수신을 돌리지 않는다. 콜백을 없애면 수신이 멈추므로, 이 호출을 `self._controls(pump=True)`로 바꿔 매 반복 transport 수신을 돌린다.
6. **판단이 참으로 바뀌는 순간의 부수 효과**는 메인 스레드의 평가 함수 안에서 전환 시 한 번만 수행한다. `stop_requested` 설정, 현재성 변경 기록, stopping 전이, 체크포인트 요청, 형식 검사의 정지 사유 누적이 그 예다. 지금은 이 효과들이 콜백이 참을 반환하는 호출 안에서 일어난다(`engine.py:3507-3542`, `:4559`).
7. **`on_started`는 동기 왕복을 유지한다.** 실행 식별자를 재개 전에 게시해야 하기 때문이다(`model_runner.py:59-60`, `engine.py:724`). 실행당 한 번이라 비용이 작다.
8. **`on_observation`은 응답을 기다리지 않는 큐로 바꾼다.** 관찰 자료는 메인 스레드가 처리해야 하지만, 러너는 반환값을 쓰지 않는다. 큐 항목에는 실행 ID를 붙인다. 순서는 다음과 같이 정한다. 러너는 한 실행의 관찰 항목을 그 실행의 종료(계산 함수의 반환)보다 먼저 큐에 넣는다. 메인 스레드는 끝난 호출을 회수(`collect`)하기 전에 그 실행의 큐 항목을 모두 처리한다. 따라서 "실행이 아직 끝나지 않았다"는 것은 메인 스레드가 그 실행의 종료를 아직 회수하지 않았다는 뜻이다. 지금은 콜백 예외가 러너로 전파되어 Job을 중단시킨다(`model_runner.py:208-212`). 새 구조에서 메인 스레드가 관찰 처리 중 오류를 만나면 다음과 같이 처리한다.
   - 그 실행이 아직 끝나지 않았으면 그 실행의 플래그를 세우고, 오류를 실행의 중단 사유로 기록한다. 러너는 플래그를 읽고 Job을 정지한다.
   - 플래그가 선 뒤 도착한 결과는 기존의 "정지 뒤 도착한 결과는 보존만 하고 수락하지 않는다" 규칙으로 처리한다.

   위 순서 규칙에 따라 관찰 항목은 언제나 그 실행의 종료를 회수하기 전에 처리된다. 따라서 메인 스레드가 종료를 이미 회수한 실행의 관찰 항목을 처리하는 경우는 생기지 않는다. 계산 함수가 반환한 뒤에도 회수 전이라면 그 실행은 "아직 끝나지 않은" 실행으로 다룬다.

   지금과 다른 점은 중단이 즉시가 아니라 러너의 다음 플래그 확인 때 일어난다는 것뿐이다. `on_observation`을 쓰는 것은 모델 실행이고, 모델 러너는 0.2초마다 플래그를 확인하므로(`model_runner.py:198-201`) 지연은 최대 약 0.2초다. 오류 뒤의 결과를 수락하지 않는다는 결과는 같다.

신뢰 환경 쪽의 두 stop(`lifecycle_engine.py:1233-1235`, `environment_checks.py:66-70`)과 `trust_check`의 `should_stop`(`lifecycle_engine.py:1373-1386`)도 같은 방식으로 바꾼다. 신뢰 환경의 전수 스캔이 없어지면 앞의 둘은 대부분 사라진다.

응답성은 두 간격의 합으로 정해진다. 정지 요청이 게시되면 메인 루프가 그 반복 안에서 플래그를 세우고, 계산 스레드는 다음 플래그 확인 때 멈춘다. 따라서 정지 요청부터 계산 중단까지의 상한은 "메인 루프 한 바퀴 + 그 계산 경로의 플래그 확인 간격"이다. 확인 간격은 모델 실행 0.2초, Lean 실행 대기 0.02초다. 5절의 경량화로 한 바퀴는 지금의 약 1초보다 짧아진다.

### 7.4 새로 필요한 시험

- **판본 식별**: `lean --version` 출력, `lean-toolchain`, `lake-manifest.json`, 실행 파일 해시 각각이 바뀌었을 때 탐지되는가
- **지문 경계**: 크기, 수정 시각, 생성 시각 가운데 하나라도 바뀌면 탐지하는가. 같은 이름으로 삭제 후 재생성하면 탐지하는가. 세 값을 모두 보존한 채 내용만 바뀐 경우는 탐지하지 않는다는 한계를 시험으로 명시한다.
- **재기록**: 판본 식별이 같고 지문만 다르면 재기록 뒤 활성 상태가 유지되는가. 판본 식별이 다르거나, 판본 식별이 같아도 내용 해시가 하나라도 다르면 재기록을 거부하고 전환을 요구하는가. 각 인스턴스가 재결박의 세 조건에서만 새 기준으로 옮겨 가는가
- **선택적 전수 점검**: 내용만 바꾼 파일(크기·시각 보존)을 내용 해시 기준 대조로 찾아내는가
- **툴체인 기록 공유**: 두 인스턴스가 같은 기록을 참조하고, 인스턴스 초기화가 지문을 다시 계산하지 않는가
- **활성화 프로필 구조**: `execution_profiles.py`의 `trust_activate` 프로필은 지금 `full_environment_scan` 계약을 강제하지만, 이를 직접 단언하는 시험이 하나도 없다. 새 구조를 고정하는 시험을 추가한다.
- **정지 응답**: 계산 도중 정지를 요청하면 계산 스레드가 메인 루프 한 바퀴 안에 멈추는가
- **선택적 전수 점검**: 사용 경로를 막지 않고, 결과가 연구 상태에 섞이지 않는가

### 7.5 5절 항목의 시험

5절의 처분(R1~R48)과 관련된 기존 시험은 조사하지 않았다. 일부 시험이 옛 동작을 단언하고 있을 수 있다. `control_transport.py:223-224`의 주석이 "같은 크기와 수정 시각으로 바꾼 파일도 탐지해야 한다"고 적는 것이 그런 예다. 구현할 때 항목마다 다음 순서를 따른다.

1. 해당 함수와 주석의 문구로 시험을 찾는다.
2. 옛 동작만 단언하는 시험은 삭제하고, 유지하는 의도는 새 수단으로 다시 쓴다.
3. 무거운 재확인이 다시 들어오면 실패하는 시험을 하나 둔다. 예를 들어 자기 게시분을 게시한 뒤 같은 head의 전체 검증이 다시 일어나지 않는지, 호출 횟수로 확인한다.

시험 그룹은 기존 표지를 따른다. `test_environment_validation.py`는 unit, `test_machine_parallel.py`의 `MachineSchedulerTests`는 unit, `CallManagerTests`는 resource, 실제 Lean을 쓰는 시험은 lean, 나머지는 integration이다.

## 8. 구현 순서

각 단계는 앞 단계가 끝난 뒤 시작한다. 같은 단계 안의 항목은 병행할 수 있다.

1. **툴체인 기록과 지문**: `trust_inventory.py`를 툴체인 기록 생성·검증 모듈로 다시 쓴다. `setup_lean.py`의 검증을 판본 식별 + 기준 항목(지문, 내용 해시, 대표 컴파일)으로 바꾸고, 재기록 모드와 선택적 전수 점검 명령을 추가한다.
2. **신뢰 환경 사용 경로**: 등록·활성화·형식 검사·게시 관문을 3.3에 맞춘다. `environment_checks.py`의 관측 대기와 `recheck` 연산을 없애고, 상태 스키마에서 manifest의 `scope`·`files`를 뺀다.
3. **취소·관찰 콜백**: 4절 구조로 바꾼다. 메인 루프가 제어 수신을 직접 돌리게 한다.
4. **상태 검증과 실행 준비**: 5.1·5.2의 처분을 적용한다.
5. **운영과 설치본**: 5.3의 처분을 적용한다.
6. **계약 문서**: 6절을 적용한다. 코드와 같은 변경에 포함한다.
7. **시험**: 7절을 적용한다.
8. **사본과 검사**: `build_skill_mirrors.py`로 `.agents` 사본을 다시 만들고, `probe_cli.py --skill-only`와 관련 시험 그룹을 실행한다.

## 9. 검증과 완료 조건

기능 검증은 다음 순서로 한다.

1. `run_tests.py`의 unit·integration 그룹 전체, 그리고 lean 그룹. 삭제한 시험과 새 시험은 7절을 따른다.
2. 새 시험이 제품 변경을 실제로 검사하는지 확인한다. 변경을 되돌렸을 때 실패해야 한다.
3. `probe_cli.py --skill-only`

성능 목표는 기능 시험으로 판정할 수 없으므로, 다음 측정으로 판정한다.

| 측정 | 방법 | 완료 기준 |
|---|---|---|
| 초기화 | 새 인스턴스를 현 머신에서 `init`부터 `run --until-active` 반환까지 초기화한다. 단계별 시간은 `timeline --include-operations`로 기록한다. 툴체인 기록은 이미 있는 상태에서 잰다. | AI 판단(의도 해석·검사)을 뺀 기계 단계의 합이 1분 이내 |
| 형식 검사 1건의 환경 확인 | `n + 0 = n` 제출물의 형식 검사에서 컴파일 전 확인에 걸린 시간 | 10초 이내 |
| 게시 관문 | 동일성 `match` 게시와 목표 감사 적용 각각의 환경 확인 | 각 1초 이내 |
| 정지 응답 | 실행 중 `pause`를 보낸 시각부터 계산 중단까지 | 5초 이내 |
| 우발 변경 탐지 | 판정 관련 `.olean` 하나를 복사로 교체한 뒤 형식 검사 | 컴파일을 시작하지 않고 지문 불일치로 멈춤 |

측정 결과는 실행 판본, 머신, 반복 횟수와 함께 보존한다. 한 번의 측정을 일반 성능으로 확대하지 않는다.

## 10. 남는 위험

- **메타데이터를 바꾸지 않는 손상**: 비트 부패처럼 크기와 시각을 그대로 둔 채 내용이 바뀌는 우발적 손상은 사용 경로에서 탐지하지 못한다. 선택적 전수 점검이 내용 해시 기준과 대조해야 잡는다. 점검은 요청할 때만 실행하므로(D6), 이런 손상은 누군가 점검을 요청할 때까지 드러나지 않을 수 있다.
- **판정 무관 파일의 변경**: `.lake` 안의 패키지 소스(`.lean`)와 부산물(`.ilean`, `.trace`, `.hash`, `.c`, `.ir`)이 바뀌어도 탐지하지 않는다. 이 파일들은 커널 판정에 들어가지 않으므로 형식 결과에 영향이 없다. 반면 프로젝트 루트의 추적 파일(`.lake` 밖의 `.lean`과 lakefile 등)이 바뀌면 판본 식별의 프로젝트 소스 식별(git tree·diff 해시)이 달라지므로 탐지한다.
- **의도적 변조**: D1에 따라 고려하지 않는다. 같은 사용자 권한의 AI 작업자가 툴체인이나 do-math 코드를 의도적으로 바꾸면 이 설계는 막지 못한다. 현행 계약도 OS 격리를 보증하지 않는다.
- **응답 지연**: 정지 요청에 대한 반응은 메인 루프 주기에 달린다. 5절이 적용되지 않은 채 4절만 적용하면 지연이 남는다.

## 결정의 근거

1.1의 D5~D7은 다음 비교에 따라 정했다.

- **D5 재기록 권한**: 설치 복구 AI에게 허용하면 무인 운영 중 재설치 뒤에도 연구가 이어진다. 그러나 예상하지 못한 지문 변화가 사람에게 알려지지 않은 채 지나간다. 이 머신에서 툴체인은 사람이 설치·교체할 때만 바뀌는 것이 보통이므로, 멈춤의 비용보다 알림의 가치가 크다고 판단했다. 재기록의 안전 조건(내용 해시 일치)은 실행 주체와 무관하게 기계가 확인한다.
- **D6 전수 점검 시점**: 주기 점검은 메타데이터를 보존한 손상을 최대 하루 안에 드러내지만, 예약 감독에 작업을 추가해야 한다. 이런 손상은 드물고, 손상된 `.olean`은 대개 Lean이 적재할 때 오류를 낸다. 그래서 요청할 때만 실행한다. 이 결정에 따라 조용한 손상은 누군가 점검할 때까지 드러나지 않을 수 있다(10절).
- **D7 기존 인스턴스**: 새 계약에서 재개할 방법이 없으므로, 활성 예약을 남길 이유가 없다. 측정 근거인 로그와 저장소는 종결 뒤에도 파일로 남는다(이 작업 공간은 뒤에 경량화 2라운드의 사용자 결정 1(M-0349)로 삭제됨). 적용 결과는 다음과 같다. `close`는 `effect=applied`였고, 상태는 `closed`(snapshot `c2023090cc06c52603924ecea4db3c7a68b80ed6`)다. `operator uninstall` 뒤 작업 스케줄러에 남은 예약 작업(`DoMath-Engine-5a8a61f4daa1`, `DoMath-Operator-5a8a61f4daa1`)은 0개다.
