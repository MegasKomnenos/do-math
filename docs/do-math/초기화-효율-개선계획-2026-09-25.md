**do-math 초기화 효율·복구 개선 계획 — 조사 결과와 기존 수리 검토**

2026-09-25. 이 문서는 구현에 앞선 계획이다. 신뢰 환경의 범위는 유지한다. 이번에 사용한 56,230개 파일·약 8.55GB를 작은 환경으로 바꾸거나 일부 파일만 확인하는 접근은 포함하지 않는다. 정확한 입력·권한·현재성·형식 검사·독립 검토·종료 장벽도 유지한다.

사용자가 지정한 방향은 안전한 실행기 교체·복구(1), 같은 범위의 신뢰 환경 처리 개선(2), 중복 검사 제거(3), 분리의 복잡도 대비 실익 검토(4), 상태 조회·역할 입력 개선(5), 단계별 계측(6)이다. 앞서 적용한 수리 자체의 품질도 함께 검토했다.

**조사의 근거와 적용 범위**

graphify의 정본 그래프는 조회 시점에 `current`였다. 파일 231개, 노드 6,237개, 관계 21,913개이며 `semantic_pending`은 비어 있었다. 이번에는 조회만 수행했다. 그래프를 갱신하거나 의미 추출 모델을 호출하지 않았다.

`trust_environment_errors`, `require_trust_environment`, `activation_requirements`, `_recover_disappeared`, `_run_parallel`, `CodexModelRunner.run`, `save_with_state`, `prepare_role_input`, `timeline`의 관계와 파일 영향 조회로 탐색한 뒤 현재 코드를 대조했다. 넓은 affected 조회 일부와 input preparation 조회는 40개 노드에서 잘렸으므로 전수 호출 그래프라고 주장하지 않는다. 핵심 경계는 좁힌 exact 조회와 실제 호출부 검색으로 보충했다. 정적 그래프가 표현하지 못한 mixin·callback 연결도 소스로 확인했다.

중요한 배포 차이가 있다. 그래프는 `.claude/skills/do-math`를 대상으로 하지만 앞선 수리 5개 파일은 `.agents/skills/do-math`에만 있다. 두 폴더는 링크가 아니다. `build_skill_mirrors.py --check --target .agents`도 정확히 이 5개 파일의 드리프트를 보고했다. 생성기는 `.claude/skills`를 정본으로 삼고 `.agents/skills`를 생성물로 취급한다. 따라서 이전 수리를 생성 사본에만 적용한 것은 정식 반영 절차상 결함이다. 정본을 먼저 고치지 않고 사본을 재생성하면 수리가 사라진다.

추가 차등 검사에서는 정본의 수리 전 구현과 실행 사본의 수리 후 구현을 비교했다. 참조 목록 입력 120개, 개별 참조 1,200건, 파일 수 6·32·33·80 및 정상·변경·누락·중복·상대 경로를 포함한 환경 검사 40건에서 결과 차이가 없었다. 이는 고정된 합성 입력의 결과 동일성 확인이다. 동시 파일 변경, 프로세스 강제 종료, 메모리 상한, 실제 Windows 시작 복구까지 확인한 결과는 아니다.

Python 3.12의 `Executor.map`은 작업 전체를 먼저 제출한다. 따라서 현재 `max_workers=8`은 동시 실행 수만 제한하며 56,230개의 대기 Future를 제한하지 않는다. `read_bytes()`도 파일을 통째로 메모리에 올리므로, 8개의 큰 파일을 동시에 읽을 때의 메모리 상한이 정의돼 있지 않다. `Path.resolve()` 예외가 발생하면 executor 종료 과정에서 이미 제출한 다른 작업들을 기다릴 수 있다. 이러한 한계 때문에 두 번째 수리는 새 검사 실행 구조 안으로 옮겨야 한다.

공급자별 관측 재사용은 현재 `adapter_for(profile)`이 공급자마다 하나의 CLI 선택 경로를 사용하기 때문에 성립한다. 오늘의 코드에서 이것을 곧바로 오인증 버그라고 판단할 근거는 없다. 다만 이 전제를 명시하지 않고 향후 여러 CLI 경로·worker·adapter가 추가되면 공유 범위를 잘못 넓힐 수 있다. 재사용 키는 파일의 전체 해시를 매번 계산해 만드는 대신, 먼저 고정한 adapter 선택과 실제 CLI 경로 등으로 구성하고 그 선택에 대한 실제 identity 관측을 한 번 수행해야 한다.

앞서 통과한 검사 55개와 실제 파일 대조는 해당 수정의 근거다. 그것을 전체 시작·종료·복구 체계의 완성 증거로 확대하지 않는다. 특히 `starting` 도중 원장에 시작 정보가 공개되지 않은 상태의 복구 문제는 세 수리로 해결되지 않았다.

입력 비대화의 실제 사례도 확인했다. 중단된 독립 검사 실행의 고정 입력에서 `recent_history[6].request.config.manifest.files`가 56,230개 파일을 담고 있었다. JSON 재직렬화 기준 최근 이력 필드는 약 35.6MB, 파생 참조 목록은 약 23.6MB였고 참조 항목은 56,271개였다. 이 값은 필드별 재직렬화 크기이지 모델에 직접 전달된 prompt 크기가 아니다. prompt가 뒤에서 작아지더라도 앞선 validation context와 catalog 구성 비용은 이미 발생했다. `decisions` 필드는 이 사례에서 약 9KB였으므로, 큰 자료가 들어온 직접 경로는 최근 제어 이력이었다.

**작업 0 — 기준선과 정본 정리**

기존 5개 변경의 diff·해시·검사 결과를 먼저 보존한다. 참조 목록 최적화는 정본 반영 후보로 유지하고, 환경 병렬화와 관측 재사용은 아래 설계에 맞춰 보완한다. 생성 사본을 정본으로 덮어쓰거나 드리프트를 자동 삭제하지 않는다.

구현은 실행 중 연구와 분리한 작업 트리·설치 경로에서 진행한다. 현재 실행 중인 설치 파일을 바꾸면서 재시작해 검증하지 않는다. 설치 전환은 작업 1의 정비 절차와 연결한다. 현행 프리알파 원칙에 따라 상태 계약을 바꾸면 새 계약·스키마·fixtures·문서를 함께 적용하고 새 인스턴스로 검증한다. 과거의 시작 정보 부재를 새 필드로 소급 채우지 않는다.

기준선은 정본 구현과 앞선 수리가 적용된 실행 사본을 구별해 기록한다. 실제 범위의 파일 목록, 총 바이트, 프로필 수, 단계별 full scan 수, 읽은 바이트, 저장 횟수, callback 대기, 메모리 최고치를 비교한다. 운영 중인 환경의 캐시를 강제로 비우지 않고 최초 관측과 연속 재관측 조건을 구분한다.

**작업 1 — 안전한 실행기 교체와 시작 중 복구**

현재 `codex_adapter.start`는 임의의 Job 이름을 만들어 suspended root를 생성한다. 그 다음 `model_runner.run`이 `on_started` callback을 중앙에 보내고, 중앙 기록 후에 root를 resume한다. 중앙이 다른 긴 검사를 수행하면 이 callback이 대기할 수 있다. 이때 실행기가 사라지면 원장의 `starting` 기록에 Job 이름이 없을 수 있다. `named_job_empty`는 이름을 알고 있어야 실제 종료를 확인할 수 있다.

제안은 프로세스 생성 전에 `launch_ticket`을 원장에 고정하는 것이다. ticket에는 실행·시도 ID, 유일한 Job 이름, host/session 및 실행기 세대, 고정 프로필·입력·허가 참조가 들어간다. 상태 전이의 세부 phase는 기존 실행 상태에 결박하며 독립된 두 번째 실행 원장을 만들지 않는다. 로컬 시작 영수증은 중앙 기록이 아직 완료되지 않았을 때의 회수를 위한 정확한 근거다.

시작 순서는 ticket 공개 → Job·suspended root 생성 → 정확한 프로세스 정체성 회수·공개 → 현재 권한 재확인 → resume 순서로 고정한다. Job 이름 충돌을 탐지하고 기존의 타인 Job에 결합하지 않는다. 이름·PID만으로 판정하지 않고 세대·생성 시각·host/session을 함께 결박한다.

복구는 먼저 이전 실행 주체가 더 이상 새 시작을 할 수 없는지 확인한다. 살아 있거나 판정 불가이면 새 시도를 열지 않는다. 그 뒤 알려진 Job을 조회하고 필요하면 허가된 종료를 요청하며, 종료 장벽을 확인한 뒤에만 자원을 반환한다. 확인된 미착수, 진행된 로컬 시작, 종료, 관찰 불가를 구별한다. 같은 요청을 재처리해도 슬롯 반환과 후속 생성은 한 번만 수행한다. 새 ticket이 없는 과거 미확정 실행은 완료로 바꾸지 않는다.

정비용 공개 제어는 기존 사용자 pause·HOLD와 구별되는 정비 사유·소유자·fence를 기록한다. 새 배정을 멈추고, 진행 중 시작·제출·종료를 정산하며, 실행기가 writer lock을 놓은 사실을 확인한 뒤 설치를 교체한다. drain이 오래 걸린다고 연구 작업을 시간만으로 강제 종료하지 않는다. 필요한 종료·체크포인트는 기존 권한과 운영 처분을 따른다. 정비 해제는 같은 fence에만 효력을 가지며 사용자 정지·HOLD를 해제하지 않는다. 예약 감독도 이 fence를 확인한다.

주 변경: `engine.py`, `execution_lifecycle.py`, `model_runner.py`, `codex_adapter.py`, `windows_job.py`, `scheduler.py`, `provider_engine.py`/`session_slots.py`, `repair_execution.py`, `scheduled_operator.py`, `cli.py`, `record_schemas`. 공통 runner를 쓰는 Claude 경로도 함께 검증한다. 로컬 영수증 코드가 커지면 작은 `launch_journal.py` 모듈로 책임을 분리한다.

완료 조건은 실제 Windows 프로세스를 이용한 각 경계의 강제 종료·재시작 검사다. ticket 전후, Job 생성 후 시작 정보 공개 전, 공개 후 resume 전, resume 후, 정상 종료 후 슬롯 반환 전을 모두 다룬다. 중복 실행·잘못된 슬롯 반환·사용자 정지 해제는 없어야 한다. 단순 mock 종료 관측만으로 완료하지 않는다.

**작업 2·3 — 범위 전체를 유지하는 환경 처리와 중복 검사 제거**

검사를 세 책임으로 분리한다. `manifest 구조 검사`는 저장된 정확한 문면과 해시·형식을 확인한다. `installed-files 검사`는 범위 전체의 실제 파일 경로·바이트를 확인한다. `apply`는 결과가 고정했던 환경·설정·허가·전환 대상이 지금도 적용 가능한지 확인한다. 이 구분을 작은 `trust_validation.py` 모듈에 모으고 `initialization.py`는 관문 조합을 맡게 한다.

첫 구현에서 권장하는 호출 배치는 다음과 같다. 이는 등록의 성공 의미를 명시적으로 정리하는 계약 변경이며, 문서를 그대로 두고 검사를 몰래 빼는 변경이 아니다.

| 경계 | 처리 |
|---|---|
| manifest 작성 | 동일한 전체 범위를 열거·해시한다. 기존 정확한 manifest를 재사용할 수 있으면 원문과 출처를 재사용한다. |
| 등록 | 정확한 manifest·검증 증거·사용자 채택 근거를 구조 검사하여 비활성 후보로 보존한다. 등록을 live 파일의 현행 인증으로 표시하지 않는다. |
| 전환 요청 | 환경·전환 대상·허가를 고정하고 검증 작업을 만든다. 같은 파일 전체를 요청 접수 자체에서 다시 읽지 않는다. |
| 신규 환경 활성화, 기존 K 없음 | 중앙이 소유한 전체 파일 검사를 한 번 수행하고 그 결과를 같은 활성화 적용에 사용한다. |
| 초기화의 나머지 관문 | 그 활성화 영수증·정확한 결속·효력을 확인한다. 같은 활성화 직후 파일을 다시 전수 읽지 않는다. |
| 기존 K를 가진 환경 전환 | 기존 형식 결과 재검사와 필요한 동일성 검토를 유지한다. 긴 전환 뒤 최종 활성화의 현재성 검사도 별도로 필요하다. 신규 초기화의 단일 검사 횟수를 강제하지 않는다. |
| 이후의 독립 형식 사용·중요한 적용 | 해당 경계에서 요구하는 실제 환경 확인을 유지한다. 과거 active 표지만으로 통과시키지 않는다. |
| status·일반 준비 상태 조회 | 저장된 판정과 그 관측 시각·효력만 표시한다. 새 live 검사를 했다고 주장하지 않는다. |

같은 신규 초기화에서 등록·전환 접수·활성화·관문 재평가가 동일한 전체 읽기를 중복 수행하지 않도록 하는 것이 1차 목표다. manifest 초안 작성 자체가 필요할 때의 읽기와 최종 실제 대조는 목적이 다르므로 별도 계측한다. 새 목록을 만드는 최초 준비까지 무조건 전체 읽기 한 번으로 끝난다고 약속하지 않는다.

manifest는 전체 바이트를 불변 artifact에 한 번 보존하고 환경 기록에는 정확한 참조·해시·크기·항목 수를 둔다. 사용자 입력 원문이 다른 직렬화이면 그 원문도 정확히 한 번 보존하고 참조한다. 각 control·history·상태 JSON에 같은 원문과 파싱 객체를 다시 넣지 않는다. 기존 불변 artifact 저장과 해시 검사 경로를 재사용한다. 단순 경로 문자열이나 외부의 원본 파일을 그대로 참조해 이후 변경되게 두지 않는다.

검증 결과에는 환경 ID, manifest·toolchain·검사기 판본, 실제 범위, 시작·종료 시각, 결과, 불일치 근거를 결박한다. 적용 전에는 manifest·환경 상태·허가·관련 전환 판본이 바뀌었는지 다시 확인한다. 바뀐 경우 결과를 보존하되 편입하지 않는다. 취소·부분 읽기·파일 접근 실패를 성공이나 빈 결과로 처리하지 않는다.

전체 파일 검사는 스트리밍 해시와 제한된 in-flight 큐로 바꾼다. 동시에 실행되는 수와 제출 대기 수를 모두 제한한다. 파일 순서와 진단 순서는 안정적으로 유지하되 진행량은 실제 완료량으로 집계한다. 파일별·청크별 취소 확인, 검사 전후 파일 관측, 읽는 동안의 변경·교체를 실패 또는 재검증 필요로 처리하는 규칙을 둔다. 메모리를 `worker 수 × 파일 전체 크기`로 사용하지 않는다.

독립 명령이나 이후 실행까지 live 검사 결과를 재사용하려면 신뢰 가능한 환경 변경 경계가 필요하다. 현재 코드에는 그 전제를 입증하는 환경 전체의 쓰기 차단·세대 관리가 없다. 따라서 이번 1차 구현에 mtime 기반 영구 캐시나 이름만 content-addressed인 장기 신뢰 캐시는 넣지 않는다. 공통 환경의 manifest·정적 증거는 공유할 수 있지만, 과거 관측이 현재 파일을 자동 인증하지는 않는다.

주 변경: `initialization.py`, `lifecycle_engine.py`, `formal.py`의 호출 경계, `knowledge.py`의 환경 전환 기록, `record_schemas`, `repository.py`, `state_checks.py`, `engine.py`의 control 적용. `governance_engine.py`·`review_engine.py`의 형식 사용/편입 관문은 빠뜨리지 않고 대조한다. 환경 작성 자동화는 `setup_lean.py`에 정확한 전체 범위와 출력 manifest를 보존하는 기능으로 연결한다.

**작업 4 — 중앙 제어와 긴 계산 분리의 실익 판단**

현재 이미 `ModelCalls`가 worker에서 blocking call을 실행하고 중앙에서 callback과 generator continuation을 처리한다. `_run_machine_steps`는 이 구조로 formal check와 trust check를 수행한다. 반면 trust activation과 활성화 관문의 전체 파일 검사는 중앙 호출 스택에서 수행된다.

기존 `ModelCalls`만 사용하는 작은 실험에서 200ms 계산을 중앙에서 수행하면 시작 통지 응답이 약 200ms 대기했고, 기존 worker 경로로 보내면 약 0.2–0.3ms 안에 처리됐다. 두 경우 상태 callback의 실행 스레드는 중앙이었다. 이는 순수 primitive의 통제 실험이며 실제 파일 검사·Git 저장·Windows Job까지 포함한 성능 측정은 아니다.

| 선택 | 얻는 이익 | 비용·한계 | 판단 |
|---|---|---|---|
| 동기 경로에서 중복만 제거 | 호출 수와 총 읽기량 감소 | 한 번의 긴 검사 동안 시작·정지 callback이 계속 대기할 수 있음 | 반드시 먼저 적용하되 이것만으로 응답성 완료를 주장하지 않음 |
| 검사 안에서 임의로 중앙 pump 호출 | 변경량이 작아 보임 | 검사 도중 재진입·상태 변경·입력 현재성이 얽힘 | 일반적인 해결책으로 권장하지 않음 |
| 기존 `ModelCalls`에 순수 환경 검사를 배치 | 중앙 응답성을 확보하면서 단일 writer 유지 | 고정 요청·결과·취소·재시작 결속을 추가해야 함 | 제한된 PoC 후 채택을 권장 |
| 별도 검증 서비스·새 실행기·별도 writer | 프로세스 단위 분리 가능 | IPC·배포·감독·장애 복구 체계가 크게 증가 | 현재 근거로는 도입하지 않음 |

권장 PoC는 실제 `trust_activate` 한 경로만 기존 기계 continuation 구조에 연결하는 것이다. worker에는 고정된 검증 요청을 전달하고, instance/runtime/Git 상태를 직접 고칠 수 없게 한다. 결과 적용은 중앙이 현재성을 다시 대조해 수행한다. 전체 환경 검사 동시성도 제한한다. 중첩된 worker pool마다 무제한 작업을 만드는 구조는 피한다.

채택 판단 전에 느린 검사와 `on_started`·사용자 정지·허가 회수·출력 수신을 겹쳐 실행한다. 중앙 callback 대기가 전체 검사 시간에 비례하지 않는지 확인한다. 실패 시 늦게 돌아온 성공 결과가 적용되지 않아야 한다. 파일 변경·엔진 종료·CAS 실패에서도 새 상태 변경 주체가 생기면 안 된다.

목표 응답성은 통제 실험에서 callback과 정지 접수 p95 1초 이내를 제안한다. 실제 파일 I/O·저장 장치에 대한 보장으로 먼저 선언하지 않는다. 상태 저장 자체가 오래 걸리면 worker 분리만으로 이 목표를 달성할 수 없으므로 작업 5와 함께 측정한다. 이 실험과 복구 검사를 통과하지 못하면 별도 서비스로 확대하지 않고 원인을 다시 정한다.

**작업 5 — 상태 조회·역할 입력·저장 처리**

상태 조회는 고정 Git snapshot의 기록 검사와 새 호스트 환경 검사를 분리한다. `record_schemas`와 `state_checks`가 부르는 구조 검사는 원문 구조·해시·참조를 확인하는 순수 함수로 만든다. lexical path 규칙은 여기서 검사하되, 실제 경로 별칭·재분석 지점·파일 정체성은 전체 환경 검사에서 확인하고 그 결과에 결박한다. `resolve()`만 삭제해 그 검사가 사라지게 하지 않는다. status는 마지막 live 관측의 시각과 범위를 표시하고 필요 시 별도 명령으로 실제 검사를 요청한다.

`repository.save_with_state`는 매번 부모 snapshot을 다시 읽고 검증하며 후보를 깊게 복사하고 인코딩한다. 먼저 큰 불변 manifest·control 원문을 별도 artifact로 옮겨 정상 상태 객체를 작게 만든다. 그 다음 동일 명령 안에서 한 번 검증한 부모 snapshot과 정확한 원 바이트를 보관해 재사용한다. 재사용 키는 저장소·OID·계약 판본에 결박한다. 가변 `instance`를 캐시의 근거로 사용하지 않고, CAS 충돌이나 전제가 바뀌면 재조회한다. 최종 expected-head CAS와 의미 불변식 검사를 유지한다.

역할 입력에서는 raw control request가 최근 이력에 통째로 복제되는 경로를 우선 고친다. 사건 종류·대상·적용 결과·정확한 원문 참조를 전달하고 상세 원문은 같은 고정 snapshot에서 회수하게 한다. 이 변환은 `submission.install_tools`와 reference catalog 구성 이전에 수행한다. prompt 축소만 뒤에서 수행하는 방식으로는 해결되지 않는다.

기존 `source_ref`, `preserve_detail`, `read_source` 계약을 재사용한다. 사용자 원문과 필수 판단 자료의 범위를 줄이지 않는다. 실패·미결 사항도 원문 참조와 소유자를 유지한다. producer와 중앙 검사는 같은 참조 해석 규칙을 사용하며, catalog에 문자열이 들어갔다는 이유로 권한을 추가하지 않는다.

주 변경: `engine._context`·이력 생성, `context_store.py`, `submission.py`, `repository.py`, `git_store.py`, `state_checks.py`, `record_schemas`, `reporting.py`·`cli.py`의 조회 경로. `input_recovery.py`, `retention.py`, `formal_preview.py`는 참조 이동의 소비 경계로 검사한다.

완료 조건은 전체 manifest가 보존·회수 가능하면서도 단순 status가 설치 파일을 읽지 않고, 원문 독립 검사 입력에 환경 파일 수만큼의 참조를 자동 복제하지 않는 것이다. 큰 blob 변경, 누락, 잘못된 해시, CAS 경쟁, 입력 파일 변조, alias와 정확한 과거 참조의 차이를 계속 검출해야 한다.

**작업 6 — 비용이 작은 단계별 계측과 보고**

기존 실행 생성·시작·종료와 `input_preparation_milliseconds`, `ObservationTracker`, `timeline`을 확장한다. 연구 진전 신호와 운영 성능 계측은 같은 판정으로 취급하지 않는다. 별도 작은 `operation_trace.py`가 필요하면 운영 계측만 담당한다.

계측 단위는 CLI 요청/작업 ID, 부모 span, 단계, 원인, UTC 시작·종료, monotonic 경과 시간, 정확한 환경·입력 참조다. 파일 검사에는 대상·완료 파일 수, 실제 읽고 해시한 바이트, 활성 worker·대기 수, 재사용 여부와 근거를 기록한다. 모델 실행에는 준비·시작 통지 대기·모델 실행·결과 회수·검사·저장 시간을 구별한다. bootstrap부터 실제 연구 프로세스 생성까지도 같은 시작 요청에 연결한다.

단계는 manifest 작성, 구조 검사, live 검사, capability 관측, 입력 복사/참조 구성, 직렬화, Git 읽기·검증·공개, callback 대기, 실제 모델 실행, 정산으로 구분한다. 총 경과 시간과 병렬 span의 합을 구별하고, 프로세스 누적 I/O를 현재 단계의 진행률로 쓰지 않는다.

진행 기록은 실행기 소유 sidecar에 제한된 주기로 기록하고, 단계 경계에서 근거를 묶어 보존한다. 파일 하나마다 Git commit이나 중앙 저장을 수행하지 않는다. 원문·자격 증명·제어 capability를 로그에 중복 기록하지 않는다. 계측 실패나 미관측을 성공/0으로 바꾸지 않으며, 계측 자체가 권한 또는 시간 기반 강제 종료를 만들지 않는다.

status에는 현재 단계, 실제 완료량, 경과 시간, 대기 원인·다음 소유자를 간단히 표시한다. 세부 보고는 `timeline`의 실행/단계 행과 별도 operator 관측으로 제공한다. 과거에 기록하지 않은 시간은 null로 남긴다.

**검증·실행 순서와 완료 기준**

순서는 정본·기준선 정리 → 최소 계측 → 안전한 시작/정비/복구 → 큰 불변 자료의 참조화와 구조 검사 분리 → 신뢰 환경 관문 정리 → 제한된 비동기 PoC 평가 → 전체 연결 검증을 권장한다. 계측을 처음부터 넣어 각 변경의 효과를 비교한다. 작업 4의 분리는 관문·상태 객체를 가볍게 만든 뒤 실익을 다시 확인해 채택한다.

성능의 1차 완료 조건은 시간 숫자보다 작업량으로 정한다. 신규 초기화의 최종 live 활성화 검사는 같은 단계 안에서 한 번만 수행하고, status는 설치 파일을 읽지 않으며, capability의 공통 관측은 같은 관측 단위에서 한 번만 수행한다. in-flight 작업 수와 메모리는 정의한 한도를 지켜야 한다. 별도 독립 형식 사용이나 긴 기존 K 전환의 마지막 현재성 확인을 이 숫자에 맞추려고 생략하지 않는다.

실제 56,230개 파일·8.55GB로 마지막 통합 검증을 수행한다. 수리 전 정본, 앞선 수리판, 최종 후보의 호출 수·바이트·시간·메모리·응답성을 구분해 보고한다. 작은 합성 시험 결과를 실제 초기화 전체 성능으로 환산하지 않는다. 실제 모델이 필요한 최종 smoke 실행은 기존 사용자 상한인 gpt-6-sol 이하를 유지한다.

관련 그룹 검사가 통과한 뒤 `probe_cli.py --skill-only`, 실제 Windows 복구 검사, 전체 초기화·예약 시작 smoke를 수행한다. 문서에서는 `README.md`, `references/초기화-운전.md`, `references/CLI-실행-계약.md`, `계약/독립-운영.md`, 필요한 공통 용어·실행 예산 설명을 같은 계약으로 맞춘다. 정본 반영 뒤 미러를 생성하고 `--check`로 차이를 확인한다. graphify 갱신은 별도의 명시적 요청이 있을 때 수행한다.

이 계획의 성공은 같은 신뢰 범위를 더 작은 비용으로 처리하면서도, 중단된 실행의 정체성과 종료를 확인할 수 있고, 중앙 제어가 긴 검사에 묶이지 않으며, 어느 단계에서 비용이 발생했는지 사용자가 확인할 수 있게 되는 것이다.
