# 초기화 검토 후속 수리

사용자의 종료·커밋 요청에 따라 현재 변경을 보존했다. 전체 통합 검사는 미완료이며, 일부 시험의 실패 원인과 수정 후 재검증이 남아 있다. 순차 진단은 시험용 지식 승인까지 완료됐지만 동시 배정 진단은 진행 중에 중단됐다. 무한 대기나 throttling을 확정하지 않았다. 종료 시점의 통과·실패·미완료 내역과 정적 성능 검토 후보는 동명 JSON의 `closure`와 `static_performance_candidates`에 남겼다. 이 커밋을 전면 검증 통과로 해석하지 않는다.

수학 연구 인스턴스 `RI-01M3BXA1GTK78NEXX9DAW13H67`는 재개하지 않았다. 초기화 검토에서 확인한 문제를 신뢰 환경, 착수 조건, 복구 소유권, 공개 운전 절차와 로컬 파일 게시의 공통 경계에서 고쳤다. 이 문서는 구현 내용과 검증 범위를 설명한다. 실행별 결과와 판본 해시는 같은 디렉터리의 `initialization-repairs-20260925.json`에 보존한다.

원 저장소는 `C:\math\.skill-workspace\nat-add-zero-20260925-181056\repo`, 작업 공간은 같은 상위 경로의 `work`다. 이전 실행기는 보존된 bootstrap으로 조회했다. 현재 설치에 맞추려고 원 연구의 manifest나 기록을 변환하지 않았다. 이번 검증은 별도 시험 저장소·작업 공간에서 수행했다. 실제 환경 등록용 시험 인스턴스 `RI-01M3C5117S490GJPPV4CFNT5P1`도 검증 후 공개 `close`로 닫았다. 원 수학 목표는 여전히 미해결이다.

## 신뢰 환경과 형식 검사의 범위

`setup_lean.py --trust-file`은 채택할 root 아래의 파일을 전부 열거하고 SHA-256을 계산한다. `.git`, `__pycache__`, `.pyc`, 준비 완료 표지는 정해진 제외 규칙을 따른다. 같은 규칙을 이후 관측에도 적용한다. root 중첩, 경로 식별 충돌, reparse 경로, 읽기 실패와 등록 목록의 추가·누락을 거부한다. 파일 역할 이름은 완전성 검사의 대체물이 아니다.

검증 record에는 실제 소스, 명령, 종료 코드와 출력, 시작·종료 시각, 전후 toolchain, 전체 inventory의 해시가 들어간다. 프로젝트가 있으면 Mathlib import와 대표 증명을, 없으면 Lean core 예제를 검사한다. 상속된 Lean·Lake·Elan 환경 변수를 제거하고, 관측한 검색 경로가 채택한 설치 범위 안에 있는지 확인한다. 변경된 Lake 프로젝트는 환경 검색을 위해 실행하기 전에도 정체성을 대조한다.

준비 때의 증거는 등록 후보의 근거다. 등록 성공과 실제 환경 활성화는 다르며, `trust_activate`가 파일 전건을 별도로 관측해야 활성화된다. 이 해시와 record는 채택·일관성 검사의 근거이며 같은 사용자 권한의 악의적 조작을 막는 외부 인증 장치는 아니다.

실제 설치에서는 137,271개 파일과 10,463,602,438바이트를 관측한 활성화 영수증을 얻었다. 시험 인스턴스에 저장된 실행은 `trust_activate` 기계 실행 한 개였다. 처음 검증 스크립트는 `execution_attempts.operations=1`을 모델 호출로 잘못 해석해 assert에 실패했다. 저장 실행의 `actor_kind=machine`과 실행 전건을 확인해 모델 호출 0회로 바로잡았으며, 원 실패와 정정 근거를 함께 남겼다.

이 실제 등록 증거는 검사 당시 설치 판본에만 대응한다. 후속 파일 게시 수정과 생성 미러 갱신 뒤에도 같은 인증이 유효하다고 주장하지 않는다. 별도 실제 Lean 검사는 서로 다른 유니코드 선언 이름이 보존되는지, `True` 증명의 의존성에 `True.intro`가 있는지, 실행기가 검증 결과를 형식 결과 기록으로 수락하는지 확인했다. 컴파일 후 시험용 검사기 사본의 파일을 바꾸면 형식 결과가 후보로 남고, 승인 환경의 출처를 바꾸면 결과를 적용하지 않는 것도 확인했다. 시험의 합성 승인·저장 대역과 실제 컴파일러 실행은 결과 자료에 구분한다.

## 수정한 전제와 제외한 구현

처음에는 후속 실행이 있으면 과거의 retry/resume뿐 아니라 설치 repair도 모두 지나간 문제로 처리하려 했다. 구체적인 소비 경로를 확인한 뒤 이를 철회했다. 후속 시도의 존재는 중복 재시도를 막는 근거지만 설치 결함 자체의 해소 근거는 아니다. 설치 수리와 그 검증을 유지하고, 수리가 끝났을 때 이미 후속이 있으면 또 다른 연구 시도를 만들지 않는다. 관련 회귀 검사는 종료된 후속과 실행 중인 후속을 나눠 검사하고, 실제 Git 저장·재시작 뒤에도 기존 후속이 보존되는지 확인한다.

Windows 오류의 원인도 경고 문자열만 보고 확정하지 않았다. 실제 검사에서 JSON 보고서의 원자 교체가 WinError 5로 실패했고, 삭제 공유를 허용한 독자만 추가해도 기존 `MoveFileEx` 교체는 실패했다. 공통 교체는 `FileRenameInfoEx`의 `REPLACE_IF_EXISTS | POSIX_SEMANTICS`를 사용하도록 바꿨다. 이미 열린 독자는 이전 파일을, 새 독자는 새 파일을 읽는 실제 핸들 검사를 수행했다. 구조체의 가변 파일명 버퍼, 긴 경로와 유니코드 이름도 검사했다. 이 동작과 지원 조건의 근거는 [Microsoft의 FILE_RENAME_INFO 문서](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)다.

공통 문서를 광범위하게 줄이는 안은 의미 보존의 실익을 입증하지 못해 채택하지 않았다. 반복되는 프로필 본문만 정확한 참조로 분리했다. 읽었다는 영수증으로 이해까지 보증하는 새 체계도 만들지 않았다. 필수 원문을 잘리지 않게 읽는 절차와 실제 독해 대조를 사용했다. 이미 위임받은 기술 선택을 다시 승인받는 절차는 추가하지 않았다.

## 비용 측정과 검증 자료

같은 37개 프로필을 전달하는 직접 입력은 60,381바이트에서 12,529바이트로 줄었고, 전문 내용과 판본은 같았다. 원 연구의 고정 snapshot 1,043파일 export는 17번의 blob 묶음 읽기와 총 19번의 Git 호출로 완료됐다. 파일 바이트가 모두 같은지 대조했다. 약 48.40초는 병행 검사 부하 아래의 관측값이며 전후 속도 배율이나 전체 모델 요금 절감의 증거로 쓰지 않는다.

검증 결과는 판본별 원 보고서를 합쳐 관리한다. 고정 사본의 넓은 회귀와 최종 코드에서 다시 검사한 변경 영역을 구별하며, 같은 테스트를 여러 번 실행한 수를 합산하지 않는다. 구조 검사와 생성 미러 일치는 설치 계약 확인이고, 합성 모델 응답을 사용하는 통합 검사는 실제 연구 모델의 수학적 판단을 검증하지 않는다. 원 수학 연구의 완주나 목표 해결도 이번 수리의 통과 조건으로 대신 주장하지 않는다.

상세 원 보고서·실행 로그·원 신뢰 manifest는 `C:\math\.skill-workspace\initialization-fixes`, 독해 세션은 `C:\math\.codex\writing-flow` 아래에 남는다. 이 대용량 로컬 자료는 Git 제외다. 커밋에는 이 문서와 요약 JSON, 정본 `.claude/skills/do-math`, 그 정본에서 생성한 `.agents/skills/do-math`, 작업 맥락을 보존한 `기억/layer1/M-0346.md`와 색인을 포함한다. graphify는 갱신하지 않았다.
