## 항목 판정

### O2-01: 부분 타당

- 근거: 통합-설계 §6.9(638~649행)에서 네 영문 값이 정의된 뒤 실제 값 이름을 다시 읽는 곳은 `no_effect`의 허용 조건(647행)뿐이고, §10.2(956~968행)는 다음 선택 입력을 무조건 전문으로 구성하며 §18.4(1530~1544행)는 작업 종결 편입을 전건 재검사한다. 따라서 값별 기계 소비가 빈약하고 §8.4의 「현재 공용 머리 재검증 요구」도 소비자가 명시되지 않았다는 핵심은 성립한다. 그러나 컨텍스트.md §5.4(193~199행)는 네 처분을 사람이 감사할 수 있는 시점별 의미로도 사용한다. 이를 불리언과 자유 산문으로 바꾸면 닫힌 기계 분류와 `no_effect`·`apply_on_next_selection`·`revalidate_before_integration`의 감사 의미가 사라지므로 동일 기능 보존이라고 단정할 수 없다. 값별 소비 규칙을 추가하거나, 폐기할 세 값의 감사 기능도 구조화해 옮기는 교정이 필요하다.

### O2-02: 기각

- 근거: 통합-설계 §7.5(763~777행)는 착수 가능성 결과를 정의하고 §7.6(781~789행)은 한 JSON 안에 전수 평가 기록과 `ready` ID 목록을 함께 둔다. 그러나 CONTEXT.md 103~105행과 컨텍스트.md §6.3(223~227행)은 실행 껍질의 외연을 착수 가능성 판정을 통과한 ID로 명시하며 미래·차단 작업을 제외한다. 따라서 §10.2·§10.5·§11.1의 「실행 껍질에 있음」은 `ready` 목록으로 해석되며, JSON 컨테이너가 감사용 전수 결과도 담는다는 사실이 외연을 둘로 만들지 않는다. 제안한 필드 명료화는 선택 가능한 편집이지만 점유 관문이 두 의미로 열린다는 지적은 원자료로 성립하지 않는다.

### O2-03: 부분 타당

- 근거: 통합-설계 §7.4(748~759행)의 입력 실재와 도구·권한 가용 항목은 §7.5(763~777행), §24.1(1954~1972행), §24.4(2008~2014행)의 기계 검사와 겹친다. 다만 §8.2(817~827행)는 검토 기록이 입력·출력 기계 검사 결과를 함께 보존하게 하므로, 사람 검토가 같은 검사를 다시 구현해야 한다고 단정할 수는 없다. 또한 아직 입력이 없는 씨앗은 현재 검토에서 승인되지 않더라도 입력이 생긴 뒤 같은 씨앗 판본에 새 검토 실행을 열 수 있으므로 「영구히 거짓」이거나 「절대 `ready`가 될 수 없다」는 결론은 §7.4에서 나오지 않는다. 시점 의존 항목을 의미적 충분성 판정으로 좁히는 대안은 유용하지만, 현재 설계와의 영구 충돌 주장은 삭제해야 한다.

### O2-04: 부분 타당

- 근거: 통합-설계 §6.1(496~497행)은 `policy_root_ids`와 `context_root_ids`를 두지만 §6.3(521~540행)은 정책·맥락의 부모, 포함 또는 루트 구조를 정의하지 않고 §21.1(1816~1842행)은 그 루트를 검사하라고만 한다. 루트 의미가 빠졌다는 지적은 타당하다. 그러나 §6.1 501행은 중복 나열하지 않을 대상을 F·자료·작업·관계로 한정하므로 정책·맥락 루트를 두는 원칙과 자기모순이라는 주장은 성립하지 않는다. 또한 공통 외피의 `lifecycle.value`는 역할별 값일 뿐 「유효한 기록 전부」가 현행 집합이라는 규칙이 아니므로, 두 필드를 삭제하는 대안은 활성 집합 지정 기능을 잃을 수 있다. 루트 구조와 활성 집합 계산을 정의하는 쪽으로 고쳐야 한다.

### O2-05: 부분 타당

- 근거: 통합-설계 §6.4(558~560행)는 종류별 허용 상태와 필수 필드를 규범으로 두지만 §21.1(1818~1831행)의 닫힌 검사 목록과 §26의 시험에는 이를 직접 검사하는 항목이 없다. 종류 의존 제약의 검사 소유자가 드러나지 않는다는 지적은 성립한다. 그러나 설계 정본은 구현 전 계약이고 §27.1·§29는 해당 스키마와 도구 구현을 요구하므로 「현재도 막지 못한다」는 이유로 두 제약을 지우면 명시 기능을 실제로 제거한다. 보고가 제시한 선택지 (2), 즉 상태 검사기와 테스트에 강제를 결선하는 것은 기능 보존 교정이지만, 더 간단하다고 선택한 (1)은 동일 기능 보존 대안이 아니다.

### O2-06: 부분 타당

- 근거: 통합-설계 §6.7(608~620행)의 21종 가운데 이름이 다른 절에 직접 다시 나오는 종류는 제한적이고, `task_*`와 작업·종결 필드 사이의 소유 경계가 명시되지 않았다는 지적은 성립한다. 그러나 §7.3의 일반 `relation_exists` 연산자, §6.7의 관계 기록·종류 정의, §10.2의 현재 관계 입력, §21.1의 관계 검사기는 이름을 하드코딩하지 않고 등록된 관계 종류 전부를 소비한다. 따라서 13종이 「어느 절차도 참조하지 않는다」는 결론은 전수 검색 결과보다 강하다. 초기 표준 어휘를 사용 시점 템플릿으로 늦추는 방안도 종류를 먼저 공용 편입해야 하는 §23.3(1948~1950행) 때문에 같은 종결 묶음에서 즉시 관계를 만들 수 있는지 추가 계약이 필요하다. 직접 사용 빈도와 일반 소비를 구분하고 지연 편입 순서를 닫아야 한다.

### O2-07: 타당

- 근거: 통합-설계 §7.3(733행·738행)은 `record_exists`를 기록 ID·종류에 대한 존재 검사로, `canon_entry_exists`를 K 객체 존재 검사로 정의한다. §6.5(564~580행)의 K 객체는 `do-math/canon-entry/1` 핵심 기록이고 `canon_entry_exists`에 활성 신뢰 시대나 추가 유효성 의미는 없다. 따라서 후자는 전자의 `record_kind=canon_entry` 특수 사례이며, 삭제 대안은 현재 명시 기능을 보존한다.

### O2-08: 부분 타당

- 근거: 통합-설계 §5.1(399~401행)과 §25.4(2089행)는 목표 상태에 따라 연구 생산 또는 학술 검증 배정을 제한하지만 §7.5의 다섯 항, §7.6의 산출 규칙과 §10의 선택 검사에는 그 제한을 소유한 항목이 없다. 소유자가 빠졌다는 핵심은 타당하다. 그러나 `record_field_equals`는 기록 ID를 인수로 받고 `instance.json`에는 핵심 기록 `record_id`가 정의되지 않았으므로, 보고가 제안한 조건식은 그대로 실행 가능하지 않다. 또한 연구 생산 조건을 단순히 「`mathematically_solved`가 아님」으로 두면 `solution_invalidated`에서 정확한 `unsolved` 반영 뒤 재개하라는 §5.1 401행보다 일찍 열릴 수 있다. 착수 가능성 식 또는 명시적 작업 종류와 목표 상태 관문을 결합하는 대안이 필요하다.

### O2-09: 부분 타당

- 근거: 통합-설계 §6.3(523행)은 정책이 우선순위를 가진다고 하면서 값 공간·방향·동률·적용 범위 겹침을 정의하지 않은 채 「명시된 우선순위가 없으면」 차단한다고 하고, §21.1에는 정책 충돌 검사가 없다. 발동 조건이 불완전하다는 지적은 타당하다. 그러나 모든 활성 정책에 전역 유일 정수 전순서를 강제하면 서로 무관하거나 의도적으로 비교 불가능한 정책까지 순위를 매기고, 의미상 충돌을 사용자 또는 전례로 해소하는 권한 관문을 우선순위로 덮을 수 있다. 이는 동일 기능 보존 대안이 아니다. 적용 범위와 부분 우선순위, 동률·비교 불가 시의 기존 차단을 명시해야 한다.

### O2-10: 기각

- 근거: 통합-설계 §6.6(584~590행)은 이 필드를 진위의 단일 인식 상태가 아니라 자료·근거의 닫힌 정보 종류로 제시한다. `source`, `observation`, `computation`, `argument`, `hypothesis`도 모두 순수한 인식 확실성 값이 아니라 출처·생성·논증의 기록 용도이며, `failure_record`만 다른 축이라고 볼 원문 근거가 없다. 실패한 계산의 재현 자료를 `failure_record`로 기록하고 계산 방법을 별도 필드에 보존하는 해석도 계약과 양립한다. 더구나 컨텍스트.md §2.1(37행)과 §5.2(174행)은 실패를 자료·근거가 소유하게 하므로 이를 삭제하고 아직 정의되지 않은 결과 필드나 `challenges` 관계로 대신하는 대안은 명시 기능을 줄인다.

### O2-11: 타당

### O2-12: 타당

### O2-13: 타당

- 근거: 컨텍스트.md §2·§5·§6의 K·F·U, 역할 디렉터리, 영향 처분, 작업 생명주기·발생 조건·착수 가능성·네 인터페이스는 CONTEXT.md와 통합-설계의 대응 절에 반복된다. 반면 컨텍스트.md §6.4(229~237행)의 작업 경계 기준은 통합-설계 §7.4가 판정 항목으로 요구하면서도 구현 정본 안에 기준을 두지 않는다. 유일 소유 기준을 통합-설계로 옮긴 뒤 반복 문면을 정확한 참조로 바꾸는 대안은 문서의 진입 기능을 유지하면서 동기화 표면을 줄인다. 다만 참조 전환은 보고가 밝힌 대로 유일 소유 문면의 이관을 먼저 검산해야 한다.

### O2-14: 부분 타당

- 근거: 통합-설계 §7.7 6단계(804행)는 「원자료 검토」의 결과 어휘·기록·실패 처리를 정의하지 않으므로 §0.3(42~50행)의 판정 계약과 어떻게 결선되는지 불분명하다. 이 불명확성 지적은 성립한다. 그러나 원자료 검토는 생성 근거와 제안 의미의 충실성을 확인할 수 있고, §7.4의 여덟 항목은 생성 원자료와 제안의 의미 일치를 직접 판정하지 않는다. 스키마·좌표 존재 검사는 그 의미 일치를 대신할 수도 없다. 따라서 원자료 검토를 기계 검사로 전부 대체하는 대안은 기능을 줄인다. 검토 목적·처분·기록을 정의하거나 착수 명세 검토에 생성 근거 충실성 항목을 명시적으로 합쳐야 한다.

- 근거: 통합-설계 §5.2.1(419~431행)의 수입 대응표는 의미 단위의 누락·중복·의미 보존을, §5.3(433~443행)의 제거 시험은 평시 외부 의존을, §2.4(177~193행)는 활성 파일 참조의 경로·해시 경계를 각각 검사한다. 한 장치의 통과가 다른 두 실패를 함의하지 않으므로 세 장치를 서로 다른 방어로 본 판정이 맞다.

### 인스턴스 흡수 상태와 재시작 시 새 ID: 부분 타당

- 근거: 통합-설계 §5.1(395행), §5.6(464~470행), §5.7(472~476행)은 `archived`를 흡수 상태로 두고 재시작에 새 instance ID와 `resumes_from`을 명시하므로 보고의 설계 기술은 정확하다. 다만 같은 ID를 다시 쓰면 곧바로 §0.3과 §2.1을 깬다는 논증은 과하다. 판정과 기록은 `record_id + public_commit`으로 판본화되고, 재시작이 반드시 질문·가정·범위를 바꾸는 것도 아니다. 새 ID는 불변 보관과 새 운용 이력을 단순하게 분리하는 타당한 선택이지만, 보고가 주장한 두 조항 위반만으로 유일한 대안이라고 입증되지는 않는다.

### 보관의 단일 ref 트랜잭션: 타당

- 근거: 통합-설계 §5.7(474~476행)은 후보 공용 커밋과 새 archive ref를 하나의 예상 OID 기반 트랜잭션으로 적용하고, 둘의 동일 OID와 manifest ref 실재를 완료 조건으로 둔다. 이는 공용 상태 변경과 불변 보관 좌표가 갈라지는 실패를 Git의 원자 ref 갱신으로 막으며, 별도 가변 상태나 자체 트랜잭션 기제를 추가하지 않는다.

### 네 작업 인터페이스의 분리: 타당

- 근거: 통합-설계 §8.1~§8.4와 컨텍스트.md §6.5(239~248행)는 씨앗, 독립 착수 검토, 실행 상태, 종결 기록의 작성 역할·판본·저장 위치를 분리한다. §4.3(334~344행)은 여러 세션이 한 가변 결과 파일이나 ref를 공동 수정하지 못하게 한다. 네 책임을 한 파일로 합치면 이 소유권과 실행 ref의 고빈도 변경 경계가 무너지므로 현재 분리는 목적에 필요한 복잡성이다.

### 발생 조건 연산자와 비단락 평가: 타당

- 근거: 통합-설계 §7.3(726~744행)은 관계 질의, task ID에서 종결 처분 확인, 권위 있는 결정의 원자료 결속 검사와 artifact 무결성처럼 단순 필드 동일성으로 환원되지 않는 연산자를 둔다. §7.5(773~775행)는 정상 거짓과 평가 오류를 구분하고 §26.2 S03(2168행)은 다른 참 조건이 있어도 오류를 보존한다. `canon_entry_exists`를 제외한 전용 연산자와 비단락 오류 전파의 필요성 판정이 성립한다. 저장된 JSON Pointer를 마이그레이션 입력으로 명시해야 한다는 잔여 위험도 §23.2(1941행)의 포괄 검사만으로는 재작성 책임이 분명하지 않아 타당하다.

### 작업 기록의 단일 ID와 승급 없는 생명주기: 타당

- 근거: 통합-설계 §7.1~§7.2와 컨텍스트.md §6.1(203~211행)은 씨앗과 실제 작업이 같은 `task_id`를 쓰고, 준비·점유·실행은 공용 생명주기가 아니라 파생 상태와 run ref가 소유하게 한다. 복원 시 새 검토를 요구하는 규칙은 §7.4의 씨앗 판본 결박과 §26.2 S08에 맞는다. 별도 승급 객체·ID·전이를 만들지 않는 현재 구조를 단순화된 설계로 본 판정이 타당하다.

### 사용자 결정 기록의 원자료 결속: 타당

- 근거: 통합-설계 §0.1(13~20행)은 사용자 결정 기록을 최상위 정본으로 두고 §6.10(651~663행)은 질문·선택지·답변·필수 문맥과 구조화 결정값을 함께 봉인한다. `decision_value_is`도 이 결속과 스키마가 유효할 때만 참이다. 요약만 남기면 결정값의 사용자 유래와 적용 범위를 재검증할 수 없으므로 원자료 결속은 권한 기능에 필요하다.

### 고정 규칙 없는 적응형 포트폴리오: 타당

- 근거: 컨텍스트.md §2.1(31~37행)과 §2.2(39~45행)은 U를 직접 열거할 수 없고 현재 최선만 반복하는 전략의 최적성 근거도 없다고 명시한다. 통합-설계 §10.3은 고정 점수·비율 대신 고려 의무와 재량을 주고, §10.5~§10.6은 판단 내용이 아니라 입력 완전성·권한·현재성·용량을 이중 검사한다. 추가 점수 함수 없이 결과 환류를 택한 것이 불필요한 기제를 만들지 않은 결정이라는 판정이 성립한다.

### O2-A: 타당

- 근거: 컨텍스트.md §0(5~11행)은 단일 진입점과 세션 종결 시 일괄 정본 갱신 규약을 소유하고, §1·§12·§14는 지도 운영과 P vs NP 고유 계약을 소유한다. 따라서 문서를 폐지하면 그 기능의 새 소유자를 정해야 하며 단순한 동일 기능 보존 정리가 아니다. 보고가 이를 기능 절충으로 분리하고 O2-13의 보수적 참조 정리를 먼저 권한 것은 원자료의 소유권 경계와 맞다.

### 범위 외 관찰 1 — 사용자 결정과 전례의 원자료 봉인 중복: 타당

- 근거: 통합-설계 §6.10(653~663행)은 사용자 결정에 질문·선택지·답변·문맥을 봉인하고, §17.1~§17.2(1430~1448행)는 사용자 승인 뒤 전례에 질문·선택지·답변을 다시 보존한다. 전례가 권위 있는 사용자 결정 기록을 참조하고 사례·일반 적용 범위만 추가하게 하면 사용자 유래 권한을 유지하면서 중복 봉인을 줄일 수 있다는 관찰이 성립한다.

### 범위 외 관찰 2 — `academic_validation_status`의 파생 가능성: 부분 타당

- 근거: 통합-설계 §25.5(2093~2103행)의 상태 조건 대부분은 목표 상태, 헌장·정책, 학술 검증 작업 점유와 완료 기록에서 계산할 수 있으므로 저장 축과 파생 사실이 겹친다는 핵심은 성립한다. 다만 외부 거부 원문은 §6.6의 자료·근거 기록이나 공용 변경의 산출물로 보존할 수 있어 §29에 전용 「외부 반론」 스키마가 없다는 사실만으로 소유자가 전혀 없다고 단정할 수 없다. 또한 현재 판본에 적용되는 의무 전건과 해소되지 않은 반론의 계산 규칙을 새로 정의하지 않으면 축을 파생 보기로 바꾸는 대안은 아직 완결되지 않는다.

### 범위 외 관찰 3 — `lean/proposals/`의 공용 트리 누락: 기각

- 근거: 통합-설계 §4.1(271~315행)은 공용 트리를 정의하고 §19.1은 정본 편입 제안을 작업 브랜치에 둔다. 작업 브랜치는 공용 트리의 현재 상태가 아니며, §19.1의 명시적 경로 허용이 §4.1 목록에 다시 나타날 필요는 없다. 보고도 공용 트리 밖이 맞다고 인정하므로, §4.1만으로 작업 브랜치 경로를 판정하기 어렵다는 사실은 설계 결함이나 유효한 누락 관찰이 아니다.

### 범위 외 관찰 4 — 담당 규칙의 테스트 벡터 누락: 타당

- 근거: 통합-설계 §26(2142~2291행)에는 §6.9의 영향 처분 값별 소비, §6.4의 종류별 허용 상태·필수 필드, §6.3의 정책 충돌·우선순위, §6.1의 `do_math_contract` 구성에 직접 대응하는 벡터가 없다. 해당 규칙을 유지한다면 구현 완료 조건 §27-14의 문서·스키마·도구·테스트 정합성을 입증할 벡터를 추가해야 한다는 관찰이 타당하다.
