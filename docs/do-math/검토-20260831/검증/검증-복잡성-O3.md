## 항목 판정

### O3-01: 부분 타당

- 근거: 통합-설계 §13.1~§13.3은 named pipe를 비권위 통지·응답 통로로 한정하고 양쪽이 Git 상태를 다시 읽게 한다. §24.1도 지속 실행 프로토콜로 named pipe와 Git ref 사건을 모두 허용한다. 따라서 Git ref 폴링으로 통지 표면을 줄일 수 있다는 핵심은 성립한다.
- 교정: 제안한 임차는 §13.5의 연결 또는 호스트 프로세스 종료 감지를 만료 감지로 바꾼다. 이는 같은 기능의 단순 치환이 아니다. 임차 기간 동안 작업자는 외부 도구를 계속 호출할 수 있으므로 손실이 계산 낭비에만 한정된다고 단정할 수도 없다(§24.4). 임차 갱신 시계, 만료 오판, handoff 중 소유자, controller·감독기 재시작 대조를 닫아야 기능 보존 대안이 된다.

### O3-02: 부분 타당

- 근거: 통합-설계 §2.1·§14.5는 관찰 의무만 정규 JSON 파일 바이트의 SHA-256으로 식별한다. `execution_id`와 `observation_generation_id`의 닫힌 복합 문자열도 §14.5의 결정론과 중복 방지를 보존할 수 있으므로 단순화 방향은 성립한다.
- 교정: 정규 JSON 생성이 달라지는 경우는 §3.1을 위반한 구현 결함이지 현행 명세가 스스로 동일성 불변식을 깨는 경우는 아니다. 또한 복합 ID도 ULID가 아니므로 §2.1의 관찰 의무 예외는 사라지지 않는다. 대안은 고정 폭 문법과 정규식을 별도로 닫아야 한다.

### O3-03: 타당

- 근거: 통합-설계 §4.3은 비작업 역할 요청을 portfolio `request.json`, certification·operations `state.json`, controller `state.json`의 네 위치에 둔다. §9.0·§10.1·§12.2·§13.2는 이 배치를 따라 라우팅과 권한 분기를 반복한다. 요청별 전용 ref와 공통 `request.json`으로 통일하고, 워크플로 상태와 함께 움직여야 하는 전이는 `git update-ref --stdin` 트랜잭션으로 묶는 대안은 현재 권한·CAS·불변 출력 요구를 보존한다. 보고도 ref 증가와 보존 정책 변경을 한계로 명시했다.

### O3-04: 타당

- 근거: 전례와 관계는 공용 트리의 `precedents/`·`relations/`에 있고(§4.1), 전례 전용 runtime ref는 없다(§1.2). 따라서 §17.4의 읽은 ref OID 전건 재대조를 공용 머리 OID 대조로 구현하면 전례와 무관한 공용 편입도 판정을 낡게 만든다. §2.5의 정확한 기록 판본과 내용 해시, 형식 필터가 읽은 활성 후보 집합을 봉인하는 대안은 §26.6 C08이 요구하는 실제 전례 집합 변경을 계속 잡으면서 무관한 공용 변경을 제외한다.

### O3-05: 타당

- 근거: §10.6은 수신자 검사 자체가 실패한 분기를 정하지 않는다. 반면 컨텍스트.md §11.4는 같은 선택 세션에 재작성을 요청한다. 그러나 §4.3은 완료 요청을 되돌리지 않고 재시도마다 새 request·execution·output ID를 만들게 하며, §10.5는 output ref를 한 번 봉인한다. 수신자 검사 실패 결과를 보존하고 새 선택 회차를 여는 대안은 이 상태 기계와 매 회차 새 선택 세션이라는 컨텍스트.md §11.3을 함께 만족한다.

### O3-06: 타당

- 근거: 컨텍스트.md §9는 도구 manifest의 `max_observation_response`와 열린 실행에서의 결함 처리만 적는다. 통합-설계 §14.5·§24.1은 도구 호출 밖 조건에 `execution_environment_max_observation_response`를 쓰고, 두 종류의 값을 작업 파견 전에 검사한다. 루트 CONTEXT.md의 「관찰 응답 조건」도 실행 환경과 도구 유형을 함께 든다. 보고가 제시한 문면 동기화는 새 기능을 추가하지 않고 세 정본의 불일치를 없앤다.

### O3-07: 부분 타당

- 근거: 역할별 `gpt-5.6-sol max`·`high` 리터럴이 통합-설계와 컨텍스트.md에 반복되고, `high` 예외 때문에 §9.1의 용량 원장이 별도 조합을 관리해야 한다는 관찰은 맞다. 역할 배정의 단일 소유자를 두어 반복을 제거할 필요도 성립한다.
- 교정: §6.3이 현재 설정에 맡긴 값은 모델·노력별 동시 세션 상한이지 역할별 모델 배정이 아니다. §23.3의 이동 규칙도 프로젝트별 하드코딩에 관한 것이므로 보편 판정 역할의 최소 모델을 설정으로 옮기는 직접 근거가 되지 않는다. 그대로 설정화하면 인스턴스 설정이 판정 신뢰 경계를 바꿀 수 있고, 보고가 제안한 역할별 최소 노력 하한이라는 새 계약도 필요하다. 기능을 확실히 보존하려면 우선 §9.1에 불변 역할 배정표를 한 번 정의하고 다른 절이 그 표를 참조하게 하거나, 설정 변경의 승인 권한과 계약 소유 하한을 함께 닫아야 한다.

### O3-08: 타당

- 근거: 컨텍스트.md §11.3과 테스트 P04가 요구하는 것은 운영체제 난수 seed, 회차별 무작위 순서, seed·실제 순서 보존과 같은 seed의 재현성이다. 통합-설계 §10.2의 HMAC 스트림·64비트 분할·거부 표집은 이 요구보다 좁고 상세한 구현을 고정한다. 안정된 후보 ID를 `HMAC-SHA256(seed, candidate_id)`로 정렬하고 동률을 후보 ID로 푸는 대안은 요구한 재현성과 순서 무작위화를 보존하며 알고리즘 표면을 줄인다.

### O3-09: 타당

- 근거: §10.2는 `context_overflow` 사건에 입력 manifest 해시를 이미 기록하면서 후보 집합·선택 계약·도구·system 입력을 다시 개별 변경 조건으로 열거한다. 전체 packet 입력을 덮는 manifest 해시, 적용한 모델 컨텍스트 한도, 생성 도구·스키마 판본을 함께 봉인해 비교하면 현재 열거뿐 아니라 packet의 다른 입력 변경도 포착한다. 보고가 한계에서 manifest 포괄 범위와 도구·스키마 판본을 명시해야 한다고 보완했으므로 기능 보존 조건도 닫혀 있다.

### O3-10: 기각

- 근거: §14.2의 `iteration_gte`는 작업 진전 계약이 정의한 값이고 `checkpoint_count_gte`는 공개 상태에서 도출한 값이다. 두 연산자를 `counter_gte`로 바꾸어도 검사기는 작업자 공개 카운터와 결정론적 파생 카운터를 서로 다른 출처에서 만들고 검증해야 한다. 보고의 대안은 이 분기를 판본화된 카운터 종류·출처 레지스트리로 이동하고 새 출처 필드와 닫힌 ID 정의를 추가한다. 같은 수치 비교는 구현 내부에서 공통화할 수 있으므로 현행 외부 연산자를 없애야 얻는 순복잡성 감소가 입증되지 않는다.

### 타당-01 — §11.2 프로세스 기대 상태의 별도 축: 타당

- 근거: 통합-설계 §8.3은 프로세스 기대 상태를 `not_created`·`running`·`terminating`·`absent_expected`로 닫고, §11.2·§12.2는 실행 제어와 별도로 전이시킨다. `revoked/terminating`과 `revoked/absent_expected`를 구별해야 종료 진행 중과 종료 완료를 나누고, §15.2의 예상 밖 소실과 E14의 예상된 부재를 구별할 수 있다.

### 타당-02 — §12.2의 14단계 시작 순서: 타당

- 근거: §12.2는 권한 원문 확인, Job 보안 속성, 정지 생성, Job 편입, 감시 원장 개설, 권한 CAS, 재개와 첫 행동 전 재확인을 순서대로 닫는다. E02·E03·E04·E04a·E15는 주요 실패 경계에서 사용자 코드가 권한 또는 감시 없이 실행되지 않는지 검사한다. 단계 수에는 API 인자와 실패 처분이 각각 포함되므로 이를 재량 단계 14개로 해석할 이유도 없다.

### 타당-03 — `monitor_started` 장벽: 타당

- 근거: §12.2 11항과 §15.3은 현재 `preparing` run OID를 참조하는 원장을 먼저 만들고, 그 일치 뒤에만 `authorized` 전이와 루트 재개를 허용한다. E15도 원장이 없을 때 정지 루트 종료와 권한 전이 부재를 요구한다. 이 장벽을 없애면 §15의 외부 감시가 시작되지 않은 실행 구간이 생긴다.

### 타당-04 — §12.5 종료 장벽의 여섯 전건: 부분 타당

- 근거: `TerminateJobObject` 반환만으로 실제 프로세스 종료가 끝났다고 볼 수 없고, §12.5의 handle 신호·exit 기록·Job 활성 수·PID 목록·외부 호출 대조를 함께 쓰는 장벽은 E09와 worktree 인계 안전을 뒷받침한다. 완료 포트 단독 판정을 금지한 결론도 §12.3과 일치한다.
- 교정: “전건 중 하나라도 빼면” 안전이 깨진다는 주장은 입증되지 않았다. §12.2 8항이 루트 process handle을 보존하고 §12.5가 보유 handle 전부의 종료 신호를 이미 요구하므로, §12.5 마지막 항목의 루트 래퍼 종료 확인 부분은 그 사실과 겹친다. 복수 신호를 쓰는 장벽의 필요성은 타당하지만 현재 여섯 문구가 모두 독립 최소 조건이라는 판정은 낮춰야 한다.

### 타당-05 — §14.2의 작업자·감시기 이중 평가와 정보 차단: 타당

- 근거: §14.2~§14.3은 같은 판본의 검사기를 두 주체가 독립 실행하고 작업자가 감시 스냅샷과 결과를 읽지 못하게 한다. 이는 구현 두 벌이 아니라 독립 관찰 두 번이며, 자기 점검이 감시 결과 복사가 되는 것을 막는다. 시간 조건의 관찰 시각 차이는 다음 안전 제어 경계와 §14.5의 응답 기한으로 닫힌다.

### 타당-06 — §14.5의 도구별 최대 응답 기간과 최소값: 타당

- 근거: §14.5는 도구 완료 조건에는 도구 manifest 값을, 다른 조건에는 실행 환경 값을 적용한다. 한 세대의 여러 조건은 의무 하나를 열기 때문에 가장 짧은 후보를 택해야 어느 도래 조건의 응답 한계도 느슨하게 만들지 않는다. §24.1의 파견 전 전건 검사는 누락값에 임의 기본값을 적용하는 경로도 막는다.

### 타당-07 — §10.5·§10.6의 이중 기계 검사: 부분 타당

- 근거: 수신자 검사는 실제 output 커밋을 별도 프로세스에서 다시 검사하므로 생산자의 `producer-check.json`을 권위 근거로 쓰지 않는다. 이 검사는 선택자 자기 신고를 적용 근거로 쓰지 않기 위해 필요하다.
- 교정: 생산자 검사는 같은 세션에서 결함을 고쳐 재선택 비용을 줄이는 최적화다. 보고도 생산자 검사를 제거했을 때의 손실을 왕복 비용 증가로만 적었다. 따라서 두 검사가 신뢰를 위한 “최소 구성”이라는 판정은 강하다. 수신자 검사만으로도 자기 신고 적용은 막을 수 있으나 운영 비용이 증가한다.

### 타당-08 — §15.1의 권한 축소와 §15.3의 append-only 원장: 타당

- 근거: §15.1은 감시기를 결정론적 평가와 operations 사례 발동으로 한정하고 run ref·작업 브랜치 쓰기와 수학·처분 판단을 금지한다. §15.3의 단일 부모 사건 사슬과 기존 사건 수정 금지는 관찰 입력과 처분의 사후 재구성을 보존한다. 재량 판단을 §16의 새 운영 점검 세션으로 넘기는 경계와도 일치한다.

### 타당-09 — §15.4·§16.4·§10.6의 낡음 처리: 타당

- 근거: 세 절은 각각 관찰의 기준 run OID, 점검 시작 run OID, 포트폴리오의 공용·controller·run ref와 모델 용량을 적용 전에 다시 고정한다. 이는 §0.3의 현재성 규칙을 각 쓰기 경계에 적용한 것이다. 실행 껍질이 공용 커밋에 의존하므로 포트폴리오에서 공용 머리까지 대조하는 범위도 정당하다.

### 타당-10 — §17.1~§17.3의 전례 관문 2단 판정: 타당

- 근거: §17.1은 고영향 처분을 사용자에게 묻지 않고 적용할 권한을 사용자 유래 전례에만 부여한다. §17.3의 단방향 형식 배제, 독립 1차 판정, 1차가 `applicable`일 때만 여는 독립 2차 판정과 만장일치는 잘못된 자동 권한 확대 위험에 대응한다. 역할 비겸임과 선행 결과 차단도 이 독립성을 구현한다.

### 타당-11 — §9.2 heartbeat 단일 실행과 pending 병합: 타당

- 근거: §9.2는 동시 heartbeat를 하나로 제한하고, 수행 중 도래한 사건을 pending 목록에 합친 뒤 회차 하나를 즉시 연다. 이 규칙은 재진입과 사건 유실을 함께 막는다. 외부 안전 사건을 정기 주기와 분리한 것도 §15의 즉시 안전 발동 요구와 맞는다.

### 타당-12 — §10.2 packet 전문 봉인과 컨텍스트 초과 차단: 타당

- 근거: §10.2와 컨텍스트.md §11.3은 후보·연결 자료 전문을 선택 입력으로 요구하고 실제 한도를 넘으면 요약 없이 차단한다. 이는 §0.3의 원자료 우선과 선택 세션의 독립 판단을 보존한다. 정확한 tokenizer, 출력 예약량과 안전 여유를 함께 계산해야 전문 수록 가능 여부를 재현할 수 있다.

### 타당-13 — §12.4의 비일반 실행 경로 금지: 타당

- 근거: 일반 자식이 아닌 실행은 Job Object의 자동 편입·종료 보장을 우회한다. §12.4는 그런 경로를 초기 구현에서 금지하고, 향후 어댑터가 실행 ID·권한 무효화·종료 장벽·원장·재시작 대조를 제공할 때만 열 수 있게 한다. 현행에는 어댑터가 없으므로 이 다섯 요건이 별도 런타임 상태를 만들지 않는다.

### 제안-1 — 고영향 처분의 2층 분리: 부분 타당

- 근거: §16.3은 실행 인수·체크포인트 재개·처음부터 재시작과 작업 종결·중대한 자원 변경을 같은 고영향 목록에 두고, §17.1은 모두 전례 또는 사용자 상신 관문에 건다. 보고는 이 관문을 앞의 세 실행 계층 처분에서 제거하면 사용자 권한 경계가 좁아진다고 명시했으므로 기능 절충 제안으로 올바르게 분류했다. “중대한 모델·자원 변경”이 기계 판정 가능한 경계 없이 남은 문제도 §27 14항과 맞지 않는다.
- 교정: 실행 인수·재시작의 영향이 보존된 자료 위의 계산 낭비에만 한정된다는 설명은 좁다. 실행 종료는 진행 중 계산을 잃고, 외부 도구 호출이 멱등하지 않으면 재실행 효과도 중복될 수 있다. 사용자가 선택할 손실에는 자동 실행 종료·반복과 외부 효과 위험도 포함해야 한다.

### 범위 외-01 — §18 공용 편입의 반복 재검증: 타당

- 근거: §9.3 5단계는 적용 가능한 작업을 하나씩 최신 공용 머리에 편입하고, §18.5는 검증 중 공용 머리가 바뀌면 새 머리를 merge한 뒤 §18.4 전건을 다시 검사하게 한다. 같은 heartbeat에서 종결 작업이 여러 개면 뒤 작업마다 앞 편입을 반영한 전건 재검증이 생긴다는 관찰은 맞다. 보고의 묶음 검증 예시는 작업별 중간 커밋에도 의미 검증이 성립하는지 별도 입증해야 하므로, 보고가 적은 대로 O4가 판정할 탐색안이지 검증된 대안은 아니다.

### 범위 외-02 — §19 세션 연속성과 요청 상태 기계의 접합: 타당

- 근거: §19.5·§19.7·§19.8과 §22.5는 회차 사이 프로세스를 종료한 뒤 같은 `agent_session_id`와 정확한 transcript를 복원하라고 요구한다. §4.3은 새 execution·output ID를 만들 수 있게 하지만 transcript의 봉인 형식과 복원 도구를 정의하지 않는다. §24 필수 도구와 §29 스키마 레지스트리에도 그 계약이 명시되지 않았다는 관찰이 맞다.

### 범위 외-03 — 승인된 어댑터 호출의 종료 조건: 타당

- 근거: 컨텍스트.md §7.4는 승인된 어댑터의 외부 도구 호출 종료·취소를 장벽 조건으로 두지만, 통합-설계 §12.4는 초기 구현의 어댑터를 전부 금지한다. 따라서 초기 구현에서 이 조건은 적용 사례가 없다. §23.3이 향후 어댑터를 판본화된 종류와 스키마로 추가하게 하므로 현행 결함은 아니지만, 어댑터를 실제로 추가하는 계약 판본에는 종료 장벽 시험도 함께 추가해야 한다는 관찰은 타당하다.
