## 항목 판정

### O1-01: 타당

- 근거: 통합-설계 §4.3(336~344행)은 비작업 역할 요청을 portfolio `request.json`, certification·operations `state.json`, controller `state.json`의 네 위치와 두 컨테이너 이름에 나누고, 연구 작업자는 run ref 상태 조합을 사용하게 한다. §9.0(873행)과 §10.1(926~952행)은 같은 요청 상태 어휘를 다시 적으며, §12.2(1122~1134행)와 §13.2(1213행)는 작업자와 비작업 역할을 반복 분기한다. 제안한 request ref 일반화는 작업자/비작업자 경계는 유지하면서 `expected_domain_state_oid` 대조와 다중 ref 트랜잭션으로 도메인 상태 결박을 보존할 수 있으므로 동일 기능 대안으로 성립한다.

### O1-02: 타당

- 근거: §3.2(230~238행)는 모든 기계 문서의 판본화된 스키마를 요구하고 §29(2342~2411행)는 실제로 64종을 닫지만, 도구 manifest(§6.3 532행, §24.1 1970행), `--describe` JSON(§24.2 2002행), `input-manifest.json`(§10.1 930행), 공통 output JSON(§4.3 342행), 후보별 블록 manifest(§10.2 968행)의 스키마 ID는 표에 없다. `producer-check.json`과 `do-math/machine-check/1`의 대응도 소유 절 문언만으로 확정되지 않는다. 스키마 묶음에 기계 판독 레지스트리와 소유 anchor를 두고 양방향 검사를 추가하는 대안은 닫힌 목록과 문서 추적성을 모두 보존한다.

### O1-03: 부분 타당

- 근거: `stale`은 portfolio 결과(§10.6 1025행), monitor 사건(§15.4 1367행), 전례 판정(§17.4 1466행), 감사(§19.13 1758행)에 실제로 쓰이고, §16.4(1426행)와 §19.11(1734행)은 같은 현재성 실패를 산문으로 표현한다. 각 기록의 어느 필드가 현재성 근거와 처분을 소유하는지는 닫힌 스키마 계약에서 충분히 정해지지 않았으므로 공통 현재성 구조를 두자는 핵심은 성립한다. 다만 §22.5(1917행)는 §10.6의 복구 재진술이라 별도 절차가 아니고, 제안한 여섯 참조 스키마 중 `reviewer-result`는 §19.11의 최종 형식 검사 소유자와 맞지 않으며 `operational-disposition`도 §16.4의 점검 현재성 대상을 정확히 표현하지 않는다. 적용 스키마 목록을 실제 소유 기록에 맞춰 다시 정해야 한다.

### O1-04: 부분 타당

- 근거: §4.1(275~311행)의 그림은 하위 구조를 일부 역할에만 표시하고, §19.13(1756행)은 그림에 명시되지 않은 `reports/audits/`를 직접 규정한다. 작업 진전 계약·종결 기록·전례 묶음 등의 `record_kind → 역할·경로` 사상이 명시되지 않아 §21.1(1820행)의 “역할별 디렉터리 스키마”를 완전히 구현하기 어렵다는 핵심은 맞다. 그러나 §4.1(314행)은 모든 기록 파일명과 역할별 `documents`·`artifacts` 위치를 일반 규칙으로 이미 열어 두므로, F 산문·작업 산문·결정 원문 등의 위치가 전혀 없다는 주장과 “닫힌 트리이면 모두 위반”이라는 단정은 과하다. 대안은 일반 규칙과 실제 예외의 경계를 기계화하는 범위에서 채택해야 한다.

### O1-05: 부분 타당

- 근거: §26 서두(2144행)는 바이트 재현 대상을 “정규 JSON과 결정론적 기계 결과”로 한정하므로 I01~I03의 난수 ULID·관찰 시각을 포함한 전체 상태를 매번 바이트 비교한다는 보고의 보편 해석은 성립하지 않는다. 반면 §25.1 단계 12(2040행)와 I04·I04a(2153~2154행)는 외부 입력 제거 전후의 “재개·실행 껍질 결과”를 바이트로 비교하면서, 재개 보고와 연결될 수 있는 `status.json`에는 검사 시각이 들어간다(§21.2 1846~1849행). 이 비교의 정확한 산출물·투영 또는 고정 시계 입력이 정해지지 않은 국소적 모호성은 남으므로, 지적은 I04 비교 계약으로 좁혀 채택해야 한다.

### O1-06: 부분 타당

- 근거: 루트 `CONTEXT.md`는 `K`·`F`·`U`를 정의하고, 지도 컨텍스트 §0(11행)은 보편 용어의 소유자를 루트 문서로 정한다. 그런데 지도 컨텍스트 §2.1(23~33행)과 통합-설계 §0.4(54~60행)·§1.1(72~78행)이 정의를 반복하고 “현재 신뢰 시대”와 “유효한 신뢰 시대”를 달리 쓰므로 단일 소유자로 수렴하자는 대안은 타당하다. 다만 신뢰 무효화 때 두 표현이 반드시 서로 다른 `K` 집합을 만든다는 결론은 확정되지 않는다. §20.1(1781행)과 §20.5(1810~1812행)는 활성 시대를 없애고 관련 K의 사용을 차단하면서 과거 객체를 이력으로 보존하므로, 두 표현 모두 활성 K가 없고 과거 객체만 보존된다는 해석도 가능하다. 또한 통합-설계 §0 자체는 세 문서를 정본으로 묶는다고 명시하지 않으므로 보고가 제안한 소유 문장을 실제로 추가해야 한다.

### O1-07: 부분 타당

- 근거: §23.3(1950행)은 새 F 종류·관계 종류와 감사 계약·실행 어댑터를 한 문장에 묶어 “종류 정의와 스키마”를 먼저 추가하게 하지만, §6.4(558~562행)는 새 F 종류를 기존 `frontier-kind` 스키마의 공용 기록으로 추가하는 경로를 별도로 둔다. §29 마지막 문단(2411행)은 스키마 추가·삭제와 닫힌 어휘 변경에만 계약 판본 인상과 마이그레이션을 요구하므로 두 확장 급을 분리하자는 핵심은 맞다. 다만 §6.4가 새 종류 자체에는 마이그레이션을 요구하지 않는다고 이미 명시적으로 읽히므로 “F 종류 하나마다 §23.2가 반드시 발동한다”는 단정은 과하고, “감사 플러그인”도 실행 코드를 뜻한다고 확정할 수 없어 §7.3·§15.2와의 정면 충돌로 단정할 수 없다. 모호한 용어와 확장 급을 분리하는 편집으로 한정해 채택해야 한다.

### O1-08: 타당

- 근거: §4.3(336행)은 여섯 runtime ref 계열의 허용 트리를 직접 파일명, 스키마 위임, 절 위임의 세 방식으로 기술한다. §10.1(926~935행)은 portfolio 첫 커밋의 파일 넷과 output ref 파일은 열거하지만, 다음 portfolio 상태 커밋이 유지·변경할 정확한 트리를 닫지 않는다. 따라서 알 수 없는 파일을 거부하라는 §4.3의 마지막 규칙과 §21.1(1829행)의 사슬 검사를 구현할 단일 기계 원천이 부족하다. ref 종류별 트리 선언을 스키마 묶음의 레지스트리에 두는 대안은 허용 파일 집합을 줄이지 않고 검사를 단일화한다.

### O1-09: 기각

- 근거: §2.4(179~189행)는 `artifact_role`을 문자열 필드로 정의하지만 닫힌 열거라고 하지 않는다. §3.2(230행)가 닫는 것은 알 수 없는 필드·연산자·판정 값·자료형이며 모든 의미 문자열을 enum으로 만들라는 요구가 아니고, §21.1(1822행)의 검사도 파일 존재·SHA-256·미디어 형식이지 기록 종류별 산출물 역할 완전성 판정이 아니다. 보고가 예시한 네 역할과 `required`의 새 의미는 원자료에서 도출되지 않으며, 새 산출물마다 스키마 판본을 올리게 해 오히려 확장 비용을 추가한다. 기록별 필수 산출물 계약이 별도로 필요하다는 지적은 가능하지만 이 보고의 결론과 대안은 원자료가 지지하지 않는다.

### O1-C1: 타당

- 근거: 루트 `CONTEXT.md`의 「핵심 기록」은 기준·프런티어·자료·연구 작업·관계·공용 편입 기록을 들지만, 통합-설계 §0.1(15~20행)은 헌장·정책, 역할별 핵심 기록, 자료·기억을 서로 다른 우선순위 층으로 나눈다. §3.3(242~263행)은 핵심 기록이 공통 외피와 `data`를 갖는다고 하나, 명시적으로 `data`를 쓰는 것은 F 객체(§6.4), Lean 정본 객체(§6.5), 작업 기록(§7.1)이고 수입·자료·관계·기억·결정·전례·신뢰 시대는 평면 필드 문언이다. §29의 `core-envelope`와 개별 스키마가 어떤 합성 관계인지도 닫히지 않아 `additionalProperties: false` 구현 형상이 갈린다는 지적이 성립한다.

### O1-C2: 타당

- 근거: §0.1(13~20행)은 사용자 결정과 헌장·정책을 스키마·도구 계약보다 상위에 두면서 표현 어휘·상태·전이의 확장 한계를 두지 않는다. 반면 §3.2(230행)는 알 수 없는 판정 값을 거부하고 §29(2411행)는 닫힌 어휘 변경에 계약 판본 인상과 §23 마이그레이션을 요구한다. §6.3(540행)과 §20.1(1779행)에 개별 보호 규칙은 있으나 일반 해소 규칙은 없으므로, 상위 의미 결정은 계약 변경 절차를 열되 현행 스키마를 직접 넓히지 못한다는 문장이 필요하다.

### O1-C3: 타당

- 근거: §12.3(1139~1162행)은 프로세스 항목과 대조 방법을 정의하고 §29(2380행)는 `process-entry` 스키마를 등록하지만, §1.2(90~98행)의 runtime ref, §4 저장 배치, §6.3(538행)의 runtime 루트 어디에도 원장 위치가 없다. 지도 컨텍스트 §8(290~300행)은 감독기 메모리가 정본이 아니며 새 감독기가 프로세스 원장과 OS 상태를 전수 대조해야 한다고 명시하고, 통합-설계 §22.6(1921~1925행)도 같은 지속 원장을 전제한다. 저장 위치와 쓰기 권한을 추가로 닫아야 복구 계약이 구현 가능하다.

### O1-C4: 타당

- 근거: §27의 완료 조건 2(2298행)와 11(2307행)에 대응하는 `--describe` 및 기계/사람 보고 일치 벡터가 §26에 없다. §21.1의 결과 네 값 가운데 §26은 `blocked` 사례만 명시하고 `degraded`·`incomplete` 산출과 `incomplete` 오분류 방지 사례가 없으며, §5.6~§5.7(464~476행)의 인스턴스 보관 2-ref 트랜잭션도 T09의 작업 종결 보관 ref 경합과 다른데 별도 벡터가 없다. 네 보강 지점이 모두 실재한다.

### 타당-1 — §1.2 runtime ref 계열 7개: 부분 타당

- 근거: run과 monitor를 분리해야 하는 이유는 §14.3(1291행)·§15.1(1337행)의 읽기·쓰기 경계와 일치하고, output ref를 가변 요청 상태와 분리해야 하는 이유도 §4.3(342~344행)의 단일 작성·불변 봉인 계약과 일치한다. 다만 controller·portfolio·certification·operations를 정확히 네 최상위 ref 계열로 나누는 것이 신뢰 경계의 유일한 최소라는 근거는 없다. 서로 다른 개별 ref와 스키마를 유지한 채 판본화된 공통 workflow 계열 아래 종류를 구분하는 대안도 같은 CAS·권한 경계를 보존할 수 있으므로 “계열 7개가 경계 수와 같다”는 최소성 주장은 교정해야 한다.

### 타당-2 — §2.5 기록 참조: 타당

- 근거: §2.5(195~206행)는 안정된 객체 정체성인 `record_id`와 정확한 공용 상태인 `public_commit`을 함께 요구한다. §2.3(173~175행)은 OID를 불투명한 상태 세대로 규정하므로 별도 판본 번호·단조성·충돌 규칙 없이 객체와 판본을 함께 식별한다는 보고의 결론이 성립한다.

### 타당-3 — §2.3 OID 길이 비하드코딩: 타당

- 근거: §2.3(175행)은 저장소 객체 형식의 실제 길이를 검사하고, §11.1(1044~1048행)은 null OID도 저장소 객체 형식에 맞게 도구가 생성하도록 한다. SHA-1 40자를 고정하지 않는 규칙은 다른 객체 형식에서도 같은 상태 계약을 유지하는 작은 검사이므로 단순화할 이유가 없다.

### 타당-4 — §3.1 정규 JSON: 부분 타당

- 근거: 파일 해시(§2.4), 스키마 묶음 해시(§3.2), 선택 계약·manifest 해시(§10.1), 해설·대응표 해시(§19.1) 때문에 의미가 같은 JSON의 바이트 안정성이 필요하다는 결론은 맞다. 그러나 비용이 키 정렬과 부동소수점 금지뿐이라는 평가는 부정확하다. §3.1(212~226행)은 NFC 정규화 전후 중복 탐지, 배열 순서 의미, 문자열·이름 정규화, 원문 순서 보존 판독까지 요구하며 이들도 생성기·판독기의 실질 구현 표면이다. 필요성은 채택하되 비용 평가는 보정해야 한다.

### 타당-5 — §3.4 `null`과 판정·실행 분리: 타당

- 근거: §0.3(44~50행)과 §3.4(265~267행)는 결과 없음·미검사·읽기 실패·부분 완료를 구별하고 스키마가 의미를 정한 때만 `null`을 허용한다. §7.5의 `evaluation_error`, §21.1의 `incomplete`, §4.3의 `execution_incomplete`, §19.5의 `review_execution_incomplete`, §16.3의 `review_incomplete`는 실제로 서로 다른 후속 행동을 열므로 이 구분은 기능 요구다.

### 타당-6 — §4.2 브랜치를 `refs/heads/` 아래 두는 선택: 타당

- 근거: §4.2(316~332행)는 실제로 checkout해 작업하는 작업 브랜치와 임시 편입 브랜치를 정의한다. Git의 이름 있는 로컬 브랜치는 `refs/heads/` 아래에 있고, 별도 임시 브랜치는 §18.4(1530~1544행)의 원 작업 동결·최신 공용 머리 merge·재검증을 표준 Git 작업 흐름으로 수행하게 한다. detached worktree와 별도 custom ref로도 구성할 수 있지만 더 많은 상태 결박을 요구하므로 더 간단한 동일 기능 대안이 아니다.

### 타당-7 — §4.4 불변 보관 ref: 부분 타당

- 근거: §4.4(348~369행), §11.4(1095~1097행), §18.6과 §23.2는 보관 대상 커밋의 도달 가능성과 조건부 생성 좌표를 ref로 보존하며, 이는 `git for-each-ref`로 직접 감사할 수 있다. 다만 Git ref 자체가 불변성을 제공하는 것은 아니다. 이동·삭제 금지 정책, 쓰기 도구의 거부, 사용자 승인 경계가 함께 있어야 불변이다(§4.4 369행). 결론은 유지되지만 보고가 이 집행 표면을 “ref가 불변성을 준다”로 축약한 부분은 교정해야 한다.

### 타당-8 — §23.1 읽기/쓰기 호환 분리: 타당

- 근거: §23.1(1929~1933행)은 설치 구현이 다를 때 호환성 검사 후 읽기 호환 구현에는 보고·마이그레이션 계획만 허용하고, 쓰기 호환 판본만 ref를 바꾸게 한다. 인스턴스가 구현 커밋·스키마 묶음·도구 manifest를 고정한다는 전제와 결합하면 판본 불일치에서 상태 훼손을 막는 단일 관문으로 충분하다.

### 타당-9 — §26 벡터 102개 밀도: 타당

- 근거: §26에는 실제로 102개 벡터가 있고, 특히 §26.4의 17개 Windows 벡터는 Job 편입 실패, 허가 CAS 실패, `ResumeThread` 실패, PID 재사용, 감독기·메인 소실처럼 서로 다른 실패 폐쇄 경계를 각각 검사한다. 기존 벡터 사이에서 동일 기능을 잃지 않고 합칠 명백한 중복은 확인되지 않았다. O1-C4의 누락은 새 벡터를 더해야 한다는 근거이지 기존 102개가 과잉이라는 근거는 아니다.

### 범위 외-1 — 고영향 운영 처분의 직렬 판정 세션: 기각

- 근거: §16.3(1413~1422행)과 §17.3(1450~1458행)을 합치면 운영 점검자·처분 심사자·전례 1차·2차까지 최대 네 AI 세션이 직렬화될 수 있다는 사실은 맞다. 그러나 활성 전례가 없으면 형식 필터의 후보가 0건이고 전례 AI 판정 세션은 열리지 않은 채 §17.1(1432~1434행)에 따라 바로 사용자 상신으로 간다. “활성 전례가 하나 이상일 때만 형식 필터를 연다”는 제안은 이미 후보 없음으로 달성되는 동작을 다시 적을 뿐 세션 수나 모델 용량을 줄이지 않는다.

### 범위 외-2 — `shuffle-v1` 전문의 인라인 배치: 기각

- 근거: §10.2(968행)의 알고리즘은 같은 seed에서 같은 순서를 내기 위한 규범 명세이고, 통합-설계는 §0(5행)에 따라 구현 정본이자 §24의 도구 계약을 포함한다. 전문을 별도 `portfolio-pack` 계약으로 옮겨도 구현·검증해야 할 알고리즘 복잡성은 줄지 않고 새 정본 포인터가 생긴다. 중복된 별도 도구 계약이 원자료에 존재하지 않으므로 위치 이동만으로 동일 기능의 더 간단한 설계가 된다는 결론은 성립하지 않는다.

### 범위 외-3 — §19.10의 새 제안 판본 재구성: 타당

- 근거: §19.10(1716~1720행)은 승인 이의가 하나라도 있으면 새 실행·새 제안 판본을 만들고 기계 예비 검사, 새 검토 계획, 새 검토단과 새 심사단으로 처음부터 시작하며 이전 판정을 승계하지 않게 한다. §19.5(1662행)와 §19.7(1692행)이 같은 판본 안에서는 세션 ID와 transcript를 유지하는 것과 대조된다는 보고도 정확하다. 판본 사이 승계 범위의 최소성은 O4가 별도로 판정해야 한다는 한정까지 포함해 타당하다.

## 누락 관찰

- **§21.1 상태 검사와 §5.4 재개가 output ref 검사를 명시하지 않는다.** §1.2(90~98행)는 `outputs`를 runtime ref 계열로 두고 §4.3(342~344행)은 각 output ref에 입력 manifest, 원본 산출물, 작성자 검사 결과를 불변 봉인한다. 그러나 §21.1(1818~1831행)의 명시 검사 목록은 controller·monitor·portfolio·certification·operations 사슬만 들고 output ref의 유일성·허가된 요청과의 결박·봉인 파일·해시를 적지 않으며, §5.4(449~456행)의 재개 전수 대조 목록도 outputs를 생략한다. 비작업 역할 판정이 output ref를 통해서만 인증·운영 상태에 연결되므로, 고아 output·잘못된 요청 결박·깨진 봉인을 재개와 상태 검사에서 탐지하는 규칙이 필요하다.
