### O1-01 같은 역할 요청 레코드를 네 곳에 서로 다른 모양으로 저장한다

- 좌표: 통합-설계 §4.3(338~344행), 근거로 §9.0(873행), §10.1(926~952행), §12.2(1122행), §13.2(1213행), §26.4 E16
- 현재 설계와 복잡성 비용: §4.3은 연구 작업자를 제외한 모든 하위 AI 실행이 “공통 역할 요청 레코드”를 가진다고 정하고, 필드 집합(request ID, 역할, `execution_id`, `agent_session_id`, 선택적 task ID, 입력 manifest 해시, output ref·output ID, 권한 ref, 요청 상태)과 닫힌 상태 기계(`ready → authorized → completed`, `ready → start_failed`, `authorized → start_failed`)를 하나로 정의한다. 그런데 저장 위치는 넷으로 나뉜다. 포트폴리오 선택은 portfolio ref의 파일 `request.json`, 동일성 검토·이의 심사·부분 전문 검토는 certification `state.json`의 배열 `role_requests`, 운영 점검·처분 심사·전례 판정은 operations `state.json`의 배열 `role_requests`, 나머지는 controller `state.json`의 배열 `controller_role_requests`다. 연구 작업자는 다섯째 모양으로, 레코드 없이 run ref의 `control=preparing`·`worker_phase=not_started`·`not_created` 조합을 시작 권한으로 쓴다. 비용은 다음과 같다. 첫째, 감독기는 §13.2의 `target_authority_ref`를 역할별로 네 가지 경로 해석기로 풀어야 하고, §12.2 단계 1·10·12·13이 매번 “연구 작업자 / 그 밖의 역할” 분기를 다시 쓴다. 둘째, 같은 상태 어휘가 §4.3·§9.0·§10.1에 세 번 그대로 재기술돼 있다(“요청 상태는 `ready`, `authorized`, `start_failed`, `completed`”). 셋째, 컨테이너 이름이 `role_requests`와 `controller_role_requests`로 갈려 같은 스키마 `do-math/role-request/1`이 두 이름으로 삽입된다. 넷째, 실패 처리도 §12.2 단계 10·13에서 역할별로 두 갈래(run ref 상태 갱신 대 요청 상태 갱신)로 갈린다.
- 동일 목적·기능 보존 대안: 비작업 역할 요청 하나에 ref 하나를 준다. `refs/do-math/requests/<instance_id>/<request_id>`가 `request.json`을 소유하고, 포트폴리오처럼 입력 묶음이 필요한 역할은 같은 커밋에 `input-manifest.json`·계약 파일·`packet/`을 함께 둔다. 즉 §10.1의 portfolio ref 패턴을 모든 비작업 역할로 일반화하고 portfolio ref 계열을 이 계열로 대체한다. 요청 레코드에 `domain_state_ref`와 `expected_domain_state_oid`를 추가해 certification·operations·controller 워크플로 상태와의 결박을 유지하고, 요청 생성과 워크플로 상태 전진은 §18.6·§5.7이 이미 쓰는 `git update-ref --stdin` 단일 트랜잭션으로 함께 적용한다. 결과로 감독기의 `target_authority_ref`는 run ref(작업자)와 request ref(그 밖의 전부) 두 모양으로 줄고, §4.3의 배치 문장·§9.0·§10.1의 상태 어휘 재기술이 사라지며, §12.2의 분기가 절반으로 준다. ref 계열 수는 늘지 않는다(portfolio → requests로 대체).
- 대안의 위험·한계: 요청과 워크플로 상태가 서로 다른 ref에 놓이므로 “워크플로 상태가 낡으면 대기 중인 시작 요청도 무효”라는 성질이 자동으로 성립하지 않는다. `expected_domain_state_oid`의 명시 대조로 대신해야 하고, 그 대조를 빠뜨리면 낡은 워크플로 위에서 세션이 시작될 수 있다. 또한 요청 ref 하나당 커밋 사슬이 생기므로 §5.4 재개의 전수 대조 대상이 요청 단위로 늘어난다. 두 비용 모두 이미 존재하는 수단(예상 OID 대조, 범위 지정 검사)으로 흡수할 수 있고, 제거하는 네 갈래 저장·검증 표면보다 작다.

### O1-02 §29의 64행 스키마 레지스트리를 손으로 닫는다

- 좌표: 통합-설계 §29(2342~2411행), §3.2(230~238행), 대조로 §4.3(342행), §6.3(532행), §10.1(930행), §10.2(957행), §24.1(1970행), §24.2(2002행)
- 현재 설계와 복잡성 비용: §3.2는 “모든 기계 문서는 JSON Schema Draft 2020-12에 대응하는 판본화된 스키마를 가진다”를 요구하고, §29는 “초기 구현의 기계 문서 종류는 다음 목록으로 닫는다”면서 64행 표를 산문으로 유지한다. 이 표는 실제 스키마 디렉터리(`.agents/skills/do-math/schemas/<schema-family>/<version>.schema.json`), §2.1의 ID 종류 34개, §4.1의 저장 트리, 각 절의 필드 정의와 손으로 동기화해야 하고, §21.1의 검사 목록과 §26의 벡터 어디에도 그 동기화를 확인하는 항목이 없다. 이미 다음 다섯 기계 문서가 표에서 빠져 §3.2와 §29가 충돌한다. (1) 도구 manifest — §6.3이 설정 항목으로, §23.1이 인스턴스 고정 대상으로, §24.1과 §14.5가 `max_observation_response`의 정본으로 쓰지만 `do-math/tool-manifest/*`가 없다. 이 값이 없으면 §24.1에 따라 작업을 파견하지 못하므로 실행 개시 경로의 필수 문서다. (2) `--describe` 출력 — §24.2가 “기계 JSON으로 반환한다”고 정하고 §27의 완료 조건 2가 그 계약을 요구하지만 스키마 ID가 없다. (3) `input-manifest.json` — §10.1이 portfolio ref 첫 커밋의 파일로 명시하고 §7.6·§21.2가 그 해시를 쓴다. (4) §4.3의 “output JSON”(역할·회차·`agent_session_id`·`execution_id`를 기록) — §10.4의 `selection.json` 필드 목록에는 이 네 값이 없으므로 별개 문서이고, 스키마가 없다. (5) §10.2의 “후보마다 하나의 닫힌 블록 manifest”. `producer-check.json`(§10.5)도 `do-math/machine-check/1`에 대응할 것으로 보이나 §29는 그 소유 절로 19.3·19.11·24만 적어 매핑이 선언돼 있지 않다.
- 동일 목적·기능 보존 대안: 레지스트리의 정본을 스키마 묶음으로 옮긴다. §3.2가 이미 경로 규약과 `instance.json`의 묶음 해시 고정을 정하므로 추가 장치가 필요 없다. §29를 (a) “레지스트리는 고정된 스키마 묶음이며 그 해시가 판본이다”라는 불변식, (b) `스키마 ID ↔ 소유 절 anchor`를 담은 생성 부록, (c) 두 방향 검사로 바꾼다. 검사는 §21.1에 “사용 중인 모든 `schema_version`이 고정 묶음에 실재한다”와 “묶음의 모든 스키마가 이 문서의 소유 절 anchor를 가진다”를 추가하고, §26.1에 대응 벡터 하나를 넣는다. 이 검사는 위 다섯 누락을 기계적으로 잡아낸다.
- 대안의 위험·한계: 생성 부록도 생성기를 돌리지 않으면 낡는다. 이 위험은 §27의 완료 조건 1을 “모든 JSON 문서에 닫힌 스키마가 있다”에서 “위 두 방향 검사가 통과한다”로 바꿔 흡수한다. 또한 소유 절 anchor를 문서에 심어야 하므로 절 번호를 바꿀 때 anchor를 함께 옮겨야 한다. 지금은 절 번호가 표의 오른쪽 열에 손으로 적혀 있어 같은 비용을 이미 치르고 있다.

### O1-03 현재성 상실 상태 `stale`이 다섯 절차에 임시 표현으로 흩어져 있다

- 좌표: 통합-설계 §0.3(50행), §3.3(242~263행), §29, 사용처 §10.6(1025행), §15.4(1367행), §17.4(1466행), §19.13(1758행), §22.5(1917행), §16.4(1426행), §19.11(1734행), 벡터 P07·O08·C08
- 현재 설계와 복잡성 비용: §0.3은 “현재 상태를 적용하기 직전에 결박한 Git OID가 여전히 현재인지 다시 확인한다”를 공통 규칙으로 세우고, 다섯 절차가 그 재확인에 실패한 산출물을 보존한다. 그런데 그 상태를 부르는 이름이 둘로 갈린다. 코드 표기 `stale`은 §10.6·§15.4·§17.4·§19.13·§22.5에, 한국어 “낡은 …”은 §15.4 제목·§16.4·§19.11·C08에 쓰인다. 더 중요한 문제는 소유가 없다는 점이다. §3.3의 공통 외피에는 현재성 필드가 없고, §29의 어느 스키마도 이 값을 소유하지 않으며, 각 절이 정의한 닫힌 어휘에도 들어 있지 않다. `do-math/portfolio-request/1`의 요청 상태는 `ready|authorized|start_failed|completed`뿐이고, `do-math/precedent-applicability/1`의 결과는 §17.3의 `applicable|not_applicable|indeterminate`뿐이며, 감사 판정값은 §19.13에서 감사 계약이 닫는다. 따라서 §3.2의 “알 수 없는 필드와 판정 값을 거부한다”를 지키는 구현자는 `stale`을 기록할 자리를 스스로 발명해야 하고, 이는 §27의 완료 조건 14(“구현자 선택지가 없다”)를 깬다. 다섯 절차가 각자 다른 자리를 발명하면 §21.1이 “낡은 산출물이 적용되지 않았음”을 한 방법으로 검사할 수 없다.
- 동일 목적·기능 보존 대안: 공유 정의 `currency`를 하나 만든다. 구조는 `{ "basis": [{ "ref": …, "oid": … }], "reverified_at": …, "verdict": "current" | "stale" }`이고, 판정 결과 필드와 분리해 둔다. `portfolio-result`, `observation-evaluation`, `operational-disposition`, `precedent-applicability`, `audit`, `reviewer-result`의 여섯 스키마가 이 정의를 `$ref`로 참조한다. 각 절은 자기 기준 ref 집합(§10.6은 공용·controller·run ref와 모델 용량, §15.4는 기준 run OID, §17.4는 전례 효력 집합과 기준 run OID, §19.13은 헌장·대상 판본·계약 해시)만 열거하고 재확인 의미론은 §0.3 한 곳에서 정의한다. 한국어 “낡은 …”은 판정 상태를 가리킬 때 `stale`로 통일한다.
- 대안의 위험·한계: 여섯 스키마에 공통 정의를 넣으면 “현재성 판정을 아직 수행하지 않음”과 `current`를 구분해야 한다. §3.4의 `null` 규칙이 이미 그 구분을 요구하므로 `verdict`에 세 번째 값을 넣지 말고 필드 부재를 “아직 재확인하지 않음”으로 스키마가 정의하면 된다. 이 결정을 명시하지 않으면 §0.3이 금지한 상태 혼동이 그대로 재현된다.

### O1-04 §4.1의 저장 트리를 손으로 그려 놓았고 필요한 위치의 절반이 빠져 있다

- 좌표: 통합-설계 §4.1(271~314행), 대조로 §5.2.1(421행), §5.7(474행), §6.4(550행), §6.10(653행), §7.1(688행), §8.1(813행), §8.4, §17.2, §19.13(1756행), §21.1(1820행)
- 현재 설계와 복잡성 비용: §4.1은 17개 최상위 디렉터리를 ASCII 트리로 그리고 “각 기록 파일명은 `<record_id>.json`”, “긴 문서는 해당 역할의 `documents`나 `artifacts` 아래 ID 디렉터리에 둔다”를 덧붙인다. 그런데 `documents`를 실제로 그린 역할은 charter·policy·context 셋뿐이고, `artifacts`는 evidence 하나뿐이며, tasks는 `records`·`reviews`만 가진다. 반면 설계는 다음 문서와 기록의 저장을 요구하면서 위치를 그리지 않았다. F 객체의 `statement_ref` 산문(§6.4), 작업 씨앗의 긴 질문·절차 Markdown(§8.1), 작업 진전 계약 기록 `PG-<ULID>`(§7.1, `do-math/progress-contract/1`), 작업 종결 기록(§8.4, `do-math/task-termination/1`), 사용자 결정의 질문·답변 원문 파일(§6.10), 전례의 요약 없는 원자료 묶음(§17.2). 반대로 §19.13은 트리에 없는 `research/<instance_id>/reports/audits/<AU-ULID>.json`을 규범으로 쓴다. 그 결과 §21.1의 검사 항목 “역할별 디렉터리 스키마”가 무엇을 대조하는지 정해지지 않는다. 트리를 닫힌 목록으로 읽으면 `reports/audits/`가 위반이고, 열린 예시로 읽으면 검사할 대상이 없다.
- 동일 목적·기능 보존 대안: 트리 그림 대신 균일 규칙 하나를 규범으로 삼는다. “모든 역할 디렉터리는 `<role>/records/<record_id>.json`을 가진다. 그 역할의 긴 산문은 `<role>/documents/<record_id>/`, 이진·데이터 산출물은 `<role>/artifacts/<record_id>/`에 둔다.” 그리고 `record_kind → role` 사상을 스키마 묶음에서 읽는다(O1-02의 레지스트리와 같은 원천). 규칙에서 벗어나는 자리는 `lean/`, `explanations/`, `provenance/imports`·`provenance/archives`, `reports/`처럼 이름을 붙인 예외로 열거하고, `reports/audits/`를 그 예외 목록에 넣는다. 그러면 §21.1의 검사는 “모든 파일이 `record_kind → role` 사상 또는 선언된 예외에 속하고 파일명이 `record_id`와 일치한다”로 기계화된다.
- 대안의 위험·한계: `provenance/imports`와 `provenance/archives`는 역할이 둘인데 상위 디렉터리를 공유하므로 예외 목록에 남는다. 예외가 늘면 균일 규칙의 이득이 준다. 현재 예외 후보는 다섯이고 모두 이미 문서에 등장하므로 관리 가능하다.

### O1-05 §26 서두의 무조건 바이트 동일성 요구가 ID·시각 규칙과 충돌한다

- 좌표: 통합-설계 §26 서두(2144행), §2.1(165행), §2.2(171행), §5.3(433~443행), §21.2(1848행), §21.3(1873행), §25.1 단계 12(2040행), 벡터 I01·I04·I04a
- 현재 설계와 복잡성 비용: §26 서두는 “동일 입력은 정규 JSON과 결정론적 기계 결과가 같은 바이트인지 비교한다”를 모든 테스트에 건다. 그런데 §2.1은 ULID를 “운영체제 암호학적 난수와 UTC 밀리초”로 생성하게 하고 결정론적 주입 지점을 주지 않으며, §2.2는 지속 기록에 관찰 UTC 시각을 남기게 한다. 따라서 기록을 새로 만드는 벡터(I01, I02, I03)는 두 번 실행하면 바이트가 다르다. 더 구체적인 충돌은 외부 입력 제거 시험이다. §5.3은 “평시 재개”와 “실행 껍질”의 결과가 같아야 한다고 하고, §25.1 단계 12와 I04는 그 비교를 바이트 비교로 규정한다. 그런데 §5.4 단계 8이 만드는 재개 보고는 §21.3에 따라 생성 도구 판본과 입력 OID를 머리에 표시하고, 같은 입력에서 생성되는 `status.json`은 §21.2에 따라 검사 시각을 담는다. 비교 대상 투영이 정의돼 있지 않으므로 구현자는 (a) I04를 항상 실패시키거나 (b) 임의의 제외 규칙을 발명해야 한다. §27의 완료 조건 9는 이 시험의 통과를 요구하므로 실패는 흡수되지 않는다.
- 동일 목적·기능 보존 대안: 바이트 동일성 요구를 설계가 이미 정의한 순수 함수 산출로 한정한다. 대상은 §3.1의 정규 JSON 직렬화, §7.5·§7.6의 착수 가능성·실행 껍질(§7.6의 필드 목록에는 시각이 없다), §10.2의 `shuffle-v1` 순서, §14.5의 관찰 의무 ID 해시, 입력 manifest 해시다. §5.3의 제거 시험에는 비교 투영을 명시한다. “실행 껍질 JSON 전체와, 재개 보고에서 §21.3이 머리에 두는 생성 좌표와 관찰 시각을 뺀 본문”처럼 제외 필드를 열거하면 된다.
- 대안의 위험·한계: 투영을 정의하면 투영 밖 필드의 회귀를 잡지 못한다. 대안으로 §2.1에 테스트용 결정론적 ID·시계 주입 지점을 두는 방법이 있으나, 그 주입 지점은 평시 실행에서 ULID의 난수 원천을 바꿀 수 있는 표면이 되므로 §2.1의 생성 규칙과 §24.3의 대체 도구 금지에 새 예외를 요구한다. 투영 명시가 더 작은 변경이다.

### O1-06 `K`·`F`·`U`의 정의가 네 곳에 기술돼 있고 이미 문면이 갈렸다

- 좌표: 통합-설계 §0.4(54~60행)와 §1.1(72~78행), `CONTEXT.md` 「인증 수학 영역 (`K`)」(24행)·「가시 연구 프런티어 (`F`)」(40행)·「미지 지평 (`U`)」(44행), 컨텍스트.md §2.1(23~33행), 소유 규칙은 컨텍스트.md §0(11행)
- 현재 설계와 복잡성 비용: 컨텍스트.md §0은 “루트 `CONTEXT.md`는 구현 세부를 제외한 보편 도메인 용어를 소유한다”고 정한다. 그런데 같은 세 용어의 정의가 컨텍스트.md §2.1과 통합-설계 §0.4·§1.1에 다시 쓰여 있고, 신뢰 시대 수식어가 이미 갈렸다. 통합-설계 §0.4는 “현재 신뢰 시대의 Lean 정본에 실제로 보존된”이라 쓰고, 같은 문서 §1.1은 “유효한 신뢰 시대에서 Lean 정본에 실제 편입된”이라 쓴다. `CONTEXT.md`는 `K`에 “현재 신뢰 시대”를, 같은 파일의 「Lean 정본」과 「Lean 정본 객체」에는 “유효한 신뢰 시대”를 쓴다. 컨텍스트.md §2.1은 “유효한”이다. 이 차이는 실제 상태를 가른다. §20.1은 신뢰 무효화 시 `active_trust_era_id`를 `null`로 만든다. “현재 신뢰 시대” 문면을 그대로 적용하면 그 순간 `K`는 공집합이 되고 §21.2가 보고하는 `K` 수는 0이 된다. “유효한 신뢰 시대” 문면과 §0.4의 “모든 형식 판단은 자신이 속한 정확한 신뢰 시대에서 해석한다”, §20.5의 “관련 K를 새 인증의 전제로 사용하지 않고”·“과거 객체·검사 기록을 삭제하지 않고 해당 시대에 상대적인 이력으로 보존한다”를 적용하면 `K` 객체는 남고 사용만 막힌다. 설계의 나머지 절차는 후자를 전제한다.
- 동일 목적·기능 보존 대안: 세 용어의 정의는 `CONTEXT.md`만 소유한다. 컨텍스트.md §2.1과 통합-설계 §0.4는 정의를 다시 쓰지 않고 각자에게 고유한 내용만 남긴다. 컨텍스트.md §2.1은 탐색·집중 활용과 연구 진전의 구별을, 통합-설계 §0.4는 개방형 연구의 출발점 논증과 Lean 신뢰 경계의 귀결을 남긴다. 통합-설계 §1.1은 구현이 실제로 쓰는 세 사실(“새 Lean 정본 객체의 편입만 `K`를 넓힌다”, “F 객체와 Lean 정본 객체는 다른 ID를 가진다”, “관계 기록으로만 연결한다”)만 남긴다. 그리고 `CONTEXT.md`의 `K` 정의에서 “현재 신뢰 시대”를 “유효한 신뢰 시대”로 고쳐 같은 파일의 「Lean 정본」·「Lean 정본 객체」와 일치시킨다.
- 대안의 위험·한계: 통합-설계를 단독으로 읽는 구현자가 `K`의 뜻을 알려면 `CONTEXT.md`를 함께 읽어야 한다. §0의 문서 계약이 이미 세 문서를 정본으로 묶고 있고, 파견 계약도 세 문서 전문을 전제하므로 실질 비용은 없다. 다만 통합-설계 §0에 “보편 도메인 용어의 정의는 `CONTEXT.md`가 소유한다”는 한 문장을 넣어야 한다.

### O1-07 §23.3이 데이터 수준 확장과 계약 수준 확장을 한 문장에 묶었다

- 좌표: 통합-설계 §23.3(1948~1950행), 대조로 §6.4(558~562행), §6.7(604행), §7.3(744행), §15.2(1355행), §19.13(1748~1756행), §29 마지막 문단(2411행)
- 현재 설계와 복잡성 비용: §23.3은 “새 F 종류, 관계 종류, 감사 계약과 실행 어댑터는 버전된 종류 정의와 스키마를 먼저 추가한다”로 네 대상을 한 문장에 묶는다. 그런데 넷은 두 급으로 나뉜다. F 종류와 관계 종류는 §6.4·§6.7에 따라 이미 있는 스키마(`do-math/frontier-kind/1`, `do-math/relation-kind/1`)를 따르는 새 기록일 뿐이고, §6.4는 “새 종류는 유효한 종류 정의 기록을 먼저 공용 편입한 뒤 사용한다”고 명시한다. 반대로 감사 계약과 실행 어댑터는 §29의 닫힌 레지스트리에 없는 새 스키마를 요구하고, §29 마지막 문단은 “스키마를 추가·삭제하거나 닫힌 판정 어휘를 바꾸면 `do-math` 계약 판본을 올리고 23절의 마이그레이션 절차를 적용한다”고 정한다. §23.3을 문면대로 읽으면 F 종류 하나를 늘릴 때마다 §23.2의 8단계(인스턴스 일시 정지, 전 Job 종료 장벽, 전 ref manifest, 보존 ref, 격리 dry run, 의미 변화 검사, 사용자 승인, 원자 전환, 전체 재검사)가 필요해지고, §6.4의 공용 편입 경로와 모순한다. 연구 중 새 F 종류가 생기는 빈도를 생각하면 이 해석 차이의 운영 비용은 크다. 같은 문단의 마지막 문장은 “감사 플러그인”을 유일하게 한 번 등장시키는데, 이 용어는 §19.13의 “정책 기록의 규칙 ID·판본·스키마로 식별하는 감사 계약” 모형과 다르고, §7.3의 “플러그인 코드를 인스턴스 데이터에 넣지 않는다”, §15.2의 “인스턴스 데이터가 실행 코드를 추가하지 못한다”와 정면으로 어긋난다.
- 동일 목적·기능 보존 대안: §23.3을 두 문단으로 나눈다. 첫 문단은 데이터 수준 확장이다. “새 F 종류와 관계 종류는 기존 종류 정의 스키마를 따르는 기록이며, 공용 편입으로 추가하고 마이그레이션을 요구하지 않는다.” 둘째 문단은 계약 수준 확장이다. “새 감사 계약 스키마와 실행 어댑터 스키마는 §29의 레지스트리를 바꾸므로 계약 판본을 올리고 §23.2를 적용한다.” 마지막 문장의 “감사 플러그인”은 §19.13의 표현인 “판본화된 감사 계약”으로 바꾼다.
- 대안의 위험·한계: §6.4는 종류 정의가 새 `data` 필드·상태·관계 종류를 만들지 못하게 이미 막고 있으므로, 데이터 수준 경로를 명시해도 종류 정의가 계약을 우회하지 못한다. 관계 종류 정의가 §6.7의 “상태 효과”를 정할 수 있다는 점은 이 경계를 흐릴 수 있으므로, 첫 문단에 “종류 정의가 정하는 상태 효과는 기존 스키마가 이미 정의한 상태 안에서만 선택한다”를 함께 적어야 한다. 이 확인은 §6.7 소유이므로 O2 범위와 겹친다.

### O1-08 상태 커밋의 허용 트리를 다섯 갈래로 서술했고 그중 하나는 실제로 닫히지 않았다

- 좌표: 통합-설계 §4.3(336행), 대조로 §10.1(926~935행), §15.3(1359행), §21.1(1829행)
- 현재 설계와 복잡성 비용: §4.3의 한 문장이 다섯 규칙을 담는다. 실행 ref는 `state.json` 하나, controller ref는 `state.json` 하나, monitor ref는 “monitor 사건 스키마가 허용한 닫힌 파일 목록”, portfolio ref는 “10.1절이 닫는다”, certification·operations ref는 각각 `state.json` 하나다. 표현 방식이 세 가지(문자열 직접 지정, 스키마 참조, 절 참조)로 갈려 검사기가 세 경로로 구현된다. 그리고 위임 하나가 실제로는 닫히지 않는다. §10.1은 portfolio ref의 **첫** 커밋 파일 넷(`request.json`, `input-manifest.json`, `selection-contract.md`, `packet/`)만 열거하고, 결과 상태 커밋에 대해서는 “권한 있는 결과 수집 도구만 … 다음 portfolio 상태 커밋을 조건부로 추가한다”라고만 쓸 뿐 그 커밋의 파일 목록을 정하지 않는다. §4.3의 마지막 문장 “알 수 없는 파일이 있으면 상태를 적용하지 않는다”를 구현하려면 그 목록이 필요하다.
- 동일 목적·기능 보존 대안: 규칙을 하나로 줄인다. “모든 상태 ref의 커밋 트리는 그 ref의 소유 스키마가 선언한 파일 집합만 가진다.” 각 스키마가 자기 커밋 종류별 파일 목록을 선언하고, §10.1은 결과 상태 커밋의 파일 목록을 명시한다. 그러면 §21.1의 “controller·monitor·portfolio·certification·operations ref 사슬” 검사가 스키마 하나만 읽는 단일 경로로 구현된다.
- 대안의 위험·한계: 파일 목록을 JSON Schema로 표현할 수 없으므로 스키마 옆에 트리 선언을 두는 별도 필드나 파일이 필요하다. O1-02의 스키마 묶음을 레지스트리로 삼으면 그 선언을 같은 묶음에 두어 추가 원천을 만들지 않을 수 있다.

### O1-09 `artifact_role`이 어휘를 닫지 않은 자유 문자열이다 (경미)

- 좌표: 통합-설계 §2.4(179~189행), 대조로 §3.2(230행), §3.3(244행), §6.7(604행), §21.1(1822행)
- 현재 설계와 복잡성 비용: §2.4의 파일 참조는 `artifact_role`을 첫 필드로 두고 예시로 `mathematical_explanation`만 든다. 허용 값 집합을 정한 곳이 없다. §3.3의 공통 외피는 `artifacts`를 배열 하나로 두므로, 한 기록의 여러 산출물을 구별하는 유일한 수단이 이 값이다. §3.2는 “알 수 없는 필드, 연산자, 판정 값과 자료형을 거부한다”를 요구하고 §6.7은 “임의 문자열 관계를 바로 쓰지 않는다”를 요구하는데, 산출물 역할만 이 규율 밖에 있다. 결과로 §21.1의 “내부 파일 참조·SHA-256·미디어 형식” 검사는 “이 기록 종류가 요구한 역할의 산출물이 실제로 있는가”를 판정할 수 없다.
- 동일 목적·기능 보존 대안: `artifact_role`의 허용 값을 기록 종류별 스키마가 닫는다. 예를 들어 `do-math/canon-proposal/1`은 `mathematical_explanation`·`identity_map`·`lean_source`·`machine_check`만 허용한다. 필수 여부는 스키마의 배열 제약으로 표현하고, §2.4의 `required` 필드는 “참조한 파일이 없을 때 기록을 무효로 볼지”만 뜻한다는 점을 한 문장으로 명시한다.
- 대안의 위험·한계: 역할 어휘를 기록 종류별로 닫으면 새 산출물 종류를 추가할 때 스키마 판본을 올려야 한다. §29가 이미 같은 규율을 다른 어휘에 적용하고 있으므로 새 비용은 아니다.

## 정합성 지적

### O1-C1 §3.3 공통 외피의 적용 범위가 정해지지 않았다 (중대)

`CONTEXT.md`의 「핵심 기록」은 “기준, 프런티어, 자료·근거, 연구 작업, 관계와 공용 편입 기록”으로 여섯 갈래를 든다. 통합-설계 §6은 제목이 「공용 핵심 기록」이면서 §6.8 공용 연구 기억과 §6.10 사용자 결정 기록을 포함한다. §0.1의 우선순위 사다리는 헌장·정책을 2위, “역할별 핵심 기록”을 4위, 자료·근거·기억을 6위로 서로 다른 층에 놓아 셋째 외연을 만든다. 이 불일치는 문면 문제로 끝나지 않는다. §3.3은 “핵심 기록은 다음 공통 외피와 역할별 `data`를 가진다”를 정하는데, `data` 구조로 기술된 절은 §6.4(F 객체), §6.5(Lean 정본 객체), §7.1(작업 기록) 셋뿐이다. §6.6 자료·근거, §6.7 관계, §6.8 기억, §6.10 사용자 결정, §5.2.1 입력 수입, §5.7 보관 manifest, §17.2 전례, §20.1 신뢰 시대는 모두 “기록은 다음 필드를 가진다” 형식의 평면 목록으로 기술돼 외피 필드(`record_id`, `record_kind`, `lifecycle`, `provenance`, `artifacts`, `schema_version`)가 나타나지 않는다. 따라서 구현자는 `do-math/decision/1`이나 `do-math/precedent/1`이 `core-envelope/1`을 포함하는지 판정할 수 없고, `additionalProperties: false` 아래에서 그 선택은 저장 형식을 실제로 바꾼다. 해소: §3.3에 “다음 스키마가 공통 외피를 포함한다”는 명시 목록을 넣거나, `record_kind`를 가진 모든 공용 트리 기록이 외피를 포함한다고 정하고 §5.2.1·§5.7·§6.6~§6.10·§17.2·§20.1의 필드 목록을 “`data`가 가진다”로 고친다. 후자를 택하면 `CONTEXT.md`의 「핵심 기록」 정의와 §0.1의 4위 항목도 같은 외연으로 맞춰야 한다.

### O1-C2 §0.1의 우선순위 사다리에 닫힌 어휘를 넘지 못한다는 한계가 없다

§0.1은 사용자 결정(1위)과 헌장·정책(2위)을 “`do-math` 스키마·도구 계약”(3위)보다 위에 놓는다. 적용 범위를 제한하는 문장이 없으므로, 헌장이나 사용자 결정이 §3.2가 닫은 판정 어휘 밖의 값을 요구하면 사다리는 그 요구가 이긴다고 읽힌다. 그러나 §3.2는 알 수 없는 값을 기계적으로 거부하고, §29는 어휘 변경에 계약 판본 인상과 §23.2 마이그레이션을 요구한다. 두 규칙이 만나면 해소 절차가 없는 교착이 된다. 설계는 개별 사례에서만 이 교착을 막아 놓았다. §20.1은 “허용 목록 변경은 새 신뢰 시대와 사용자 승인을 요구한다”로 공리 목록에 대해, §6.3은 “설정 변경이 목적·정책·신뢰·외부 효과를 바꾸면 단순 설정 변경으로 적용하지 않는다”로 설정에 대해 막는다. 일반 규칙이 없으므로 나머지 어휘(예: §18.1의 종결 처분, §6.6의 정보 상태, §21.1의 검사 결과)에는 같은 보호가 없다. 해소: §0.1에 “1·2위는 3위가 닫은 어휘·상태·전이를 넓히지 못한다. 그런 요구는 §23의 계약 변경 절차를 연다”를 한 문장 추가한다.

### O1-C3 프로세스 원장의 저장 위치가 어디에도 정해지지 않았다 (중대)

§29는 `do-math/process-entry/1`을 소유 절 12.3으로 등록하고 §12.3은 항목의 필드를 정한다. 그런데 그 원장이 어디에 사는지는 §1.2의 runtime ref 목록(controller·runs·monitor·portfolio·certification·operations·outputs)에도, §4의 저장 배치에도, §6.3의 런타임 루트(`cache`, `tmp`, `worktrees`)에도 없다. 원장은 감독기 메모리에 둘 수 없다. 컨텍스트.md §8이 “감독기 메모리는 연구 정본이 아니다”라고 정하고, 같은 절과 §22.6이 새 감독기의 시작 절차로 “프로세스 원장과 실제 OS 프로세스 상태를 전수 대조”를 요구하기 때문이다. §21.1도 “모델 용량 원장과 실제 하위 세션”을 검사 항목으로 들어 원장 판독을 전제한다. 위치가 없으면 감독기 소실 복구(§13.3, §22.6)와 상태 검사가 구현되지 않는다. 해소: `refs/do-math/supervisor/<instance_id>` 같은 ref 계열을 §1.2에 추가하고 §4.3의 허용 트리 규칙에 넣거나, 원장을 controller `state.json`의 필드로 편입한다. 후자를 택하면 감독기가 controller ref에 쓰게 되므로 §13.1의 권한 모형(감독기는 결과를 예상 OID에 조건부로 기록한다)과 §9.0의 controller 소유권을 함께 손봐야 한다.

### O1-C4 §26의 벡터가 §27의 완료 조건 일부를 덮지 않는다

§27은 완료 조건 14개를 열거하고 §26은 벡터 102개를 준다. 다음 조건에는 대응 벡터가 없다. 완료 조건 2(필수 CLI의 `--describe` 계약) — §24.2의 `--describe` 반환을 검사하는 벡터가 없다. 완료 조건 11(기계 상태와 사람 보고가 같은 입력에서 일치) — §21.2와 §21.3의 일치를 검사하는 벡터가 없다. §21.1의 검사 결과 어휘(`healthy`·`degraded`·`blocked`·`incomplete`) 자체를 판정하는 벡터도 없다. I07과 M03이 `blocked`를 결과로 쓰지만 `degraded`와 `incomplete`를 산출하는 상황은 벡터에 없고, §21.1은 “`incomplete`를 healthy나 blocked로 추측하지 않는다”를 명시적으로 요구한다. §5.6~§5.7의 인스턴스 보관 트랜잭션(공용 브랜치와 인스턴스 보관 ref의 동시 갱신, 부분 실패 시 둘 다 불변)에도 벡터가 없다. T09는 작업 종결 트랜잭션의 보관 ref 충돌만 다룬다. 해소: 이 네 자리에 벡터를 추가한다. 이 지적은 §26의 복잡성이 과하다는 뜻이 아니다. 판정은 아래 「타당 판정」의 마지막 항목이다.

## 타당 판정

### §1.2 runtime ref 계열 7개: 쓰기 권한 경계가 요구한다

ref 계열을 합치면 신뢰 경계가 깨진다. §15.1은 외부 감시기가 run ref와 작업 브랜치를 바꾸지 못하게 하고, §14.3은 작업자가 관찰 스냅샷과 감시 결과를 읽지 못하게 한다. monitor를 run ref에 합치면 두 금지가 동시에 무너진다. §4.3은 공용 작업대를 수정하지 않는 세션이 자기 output ref만 만들 수 있게 하고 “여러 세션이 하나의 가변 결과 파일이나 ref를 공동 수정하지 않는다”를 요구한다. outputs를 요청 ref에 합치면 결과 봉인과 요청 상태 전이가 같은 사슬에서 경합한다. 계열 7개는 이 경계 수와 같고, 각 계열의 커밋은 단일 부모 사슬이라 CAS 경합이 계열 안으로 국한된다.

### §2.5 기록 참조 = `record_id` + `public_commit`

판본 번호를 따로 할당하면 그 번호의 유일성·단조성·충돌 해소를 새로 구현해야 한다. Git 커밋 OID는 이미 불변 스냅샷을 주고, §2.3이 그 OID를 “단조 증가하는 권한 세대 번호가 아니라 불투명한 상태 세대 식별자”로 못박아 잘못된 대소 비교를 막는다. 두 필드는 이 기능을 얻는 최소 표현이다.

### §2.3 OID 길이를 하드코딩하지 않는 규칙

비용은 검사 코드 한 줄이고, 저장소가 SHA-256 객체 형식이면 하드코딩된 40자 검사가 전 상태 기록을 무효로 만든다. §11.1이 null OID를 “저장소 객체 형식에 맞는” 값으로 도구가 생성하게 한 것도 같은 규율이다.

### §3.1 정규 JSON

이 설계의 모든 참조는 해시로 고정된다(§2.4의 파일 SHA-256, §3.2의 스키마 묶음 해시, §10.1의 계약 해시, §19.1의 해설·대응표 해시). 바이트 안정성은 선호가 아니라 전제다. 실제 부담을 지는 규칙은 키 정렬과 부동소수점 금지 둘이고, 나머지(UTF-8, LF, 두 칸 들여쓰기, 파일 끝 개행)는 생성기 상수다. §3.1이 NFC 정규화 전에 원문 멤버 이름 중복을 먼저 거부하도록 순서를 못박은 것은 정규화가 서로 다른 키를 조용히 합치는 사고를 막는다.

### §3.4 `null` 규칙과 §0.3의 판정·실행 분리

“미검사, 읽기 실패, 해당 없음, 결과 없음”을 하나의 `null`로 줄이면 §7.5의 `evaluation_error`, §21.1의 `incomplete`, §4.3의 `execution_incomplete`, §19.5의 `review_execution_incomplete`, §16.3의 `review_incomplete`가 모두 표현 불가능해진다. 장기 자율 운전에서 “검사하지 못했다”를 “문제 없다”로 접는 것이 가장 큰 실패 양식이므로, 이 구분은 기능 그 자체다.

### §4.2 작업·임시 편입 브랜치를 `refs/heads/` 아래 두는 선택

`git worktree`가 체크아웃하는 브랜치는 `refs/heads/` 아래에 있어야 한다. 실행마다 별도 임시 편입 브랜치를 만드는 것은 §18.4의 “원 작업 브랜치는 종결 준비에서 동결하고 rebase나 merge로 바꾸지 않는다”를 지키면서 최신 공용 머리를 반영할 유일한 방법이다. 두 결정 모두 Git의 기본 성질에서 나온 것이지 새 추상이 아니다.

### §4.4 불변 보관 ref

ref는 도달 가능성(GC 방지)과 불변성을 동시에 주는 Git의 가장 값싼 원시 수단이다. 별도 보관소나 인덱스 커밋 방식은 더 영리하지만 감사자가 `git for-each-ref` 하나로 확인할 수 있는 성질을 잃는다. 증가량은 실행당 4~5개이고 packed-refs가 흡수한다. §24.2의 `do-math check`가 “전체 또는 지정 범위”를 받으므로 전수 검사 비용의 탈출구도 있다.

### §23.1 읽기 호환과 쓰기 호환의 분리

설치된 구현이 인스턴스가 고정한 판본과 다를 때 보고·계획만 허용하고 쓰기를 막는 관문 하나가, 판본 불일치가 상태를 훼손하는 전 경로를 닫는다. §3.2의 묶음 해시 고정이 이미 있으므로 추가 장치는 비교 한 번이다.

### §26 벡터 102개의 밀도

스키마 64종, ref 계열 14개(runtime 7 + archive 7)와 `refs/heads/` 브랜치 계열 3개, 닫힌 상태 기계 여섯(요청 상태, 실행 제어, 작업자 단계, 프로세스 기대 상태, 작업 공용 생명주기, 종결 처분)에 대해 벡터 102개는 과잉이 아니다. 각 벡터가 상태 하나 또는 실패 양식 하나에 대응하고, 특히 §26.4의 Windows 실행 17개는 Job Object 편입 실패·`ResumeThread` 실패·PID 재사용처럼 다른 방법으로 관찰할 수 없는 경계를 덮는다. 이 영역에서 줄일 것은 없고, 위 O1-C4의 빈자리를 채우는 편이 옳다.

## 범위 외 관찰

- **고영향 운영 처분 하나에 판정 세션이 최대 넷 직렬로 붙는다** (§16~§17, O3 범위). 감시기 발동 → 운영 점검자 → 운영 처분 심사자 → 전례 형식 필터 → 전례 1차 판정 → 전례 2차 판정 순서다. 그런데 §17.1은 “전례로 자동 적용한 사례는 새 전례가 되지 않는다”, “사용자가 적용을 승인하면 … 새 전례로 기계 봉인한다”고 정하므로 인스턴스 초기에는 전례 집합이 비어 있고 전례 경로 전체가 항상 사용자 상신으로 귀결한다. 초기 구현에서 전례 판정 단계를 켜는 조건(활성 전례가 하나 이상 있을 때만 형식 필터를 연다)을 명시하면 초기 운전의 세션 수와 모델 용량 점유가 줄어든다. O3가 판정할 사항이다.
- **§10.2의 `shuffle-v1` 전문이 설계 본문에 인라인돼 있다** (O3 범위). HMAC-SHA256 기반 난수 생성, 64비트 값 넷 추출, 거부 표집 한계, Fisher–Yates 하향 순회까지 알고리즘 전체가 한 문단에 들어 있다. 재현성을 위해 정확한 명세가 필요하다는 점은 타당하나, 이 내용의 소유는 `do-math portfolio-pack`의 도구 계약이 맞다. 설계 본문에는 알고리즘 ID와 seed 기록 의무만 남길 수 있다.
- **§19.10의 새 제안 판본이 검토단·심사단을 전면 재구성한다**(O4 범위). 승인 이의 하나가 나올 때마다 기계 예비 검사, 새 검토 계획, 새 검토단(최소 3), 새 심사단(3)을 처음부터 다시 연다. §19.5·§19.7이 같은 판본 안에서는 `agent_session_id`와 transcript를 유지하도록 세심하게 설계된 것과 대비되므로, 판본 사이의 승계 불가 범위가 실제로 필요한 최소인지 O4의 판정이 유용하다.

## 미검사

없다. 담당 범위의 모든 절을 읽고 판정했다.
