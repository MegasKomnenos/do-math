## 과잉 지적

### O3-01 named pipe 제어 채널 전체가 권한 없는 지연 최적화다

- 좌표: 통합-설계 §12.1(1109행 구조도), §13.1(1195~1197행), §13.2(1201~1213행), §13.3(1217행), §13.4(1221~1229행), §13.5(1233행), §24.1(1972행), §24.2(1989행), §29 `do-math/supervisor-request/1`(2381행). 컨텍스트.md §8(292~296행).
- 현재 설계와 복잡성 비용: §13.1이 "권위 있는 요청은 Git 상태 사슬에 먼저 기록한다. 로컬 Windows named pipe는 요청 좌표를 알리는 통지 통로다. pipe 메시지만으로 상태 변경을 수행하지 않는다"고 못 박는다. §13.2에서 감독기는 pipe 메시지를 받은 뒤에도 "controller ref, `target_authority_ref`, request ID, execution ID와 허용 상태 전이를 직접 읽어 검사"하고, §13.3은 "pipe 응답은 결과 OID와 해시만 반환한다. 메인 세션은 실제 결과 커밋을 읽는다"고 한다. 즉 pipe는 요청·응답 어느 방향으로도 권위를 나르지 않으며, 양쪽 모두 Git 재판독이 이미 의무다. 그럼에도 pipe 하나가 다음 표면을 만든다. (1) DACL 구성, 32비트 little-endian 길이 접두사, 1,048,576바이트 상한의 자체 프레이밍 프로토콜(§13.1). (2) 전용 스키마 `do-math/supervisor-request/1`(§29). (3) 재전송 의미론 — "같은 request ID와 같은 내용의 재전송은 기존 결과를 반환한다. 같은 ID에 다른 내용은 무결성 오류다"(§13.2). (4) 두 종류의 연결과 그 구별 규칙 — "장기 제어 연결이나 그 연결을 소유한 호스트 프로세스의 종료를 메인 소실로 본다. 개별 요청 pipe의 연결 종료는 소실이 아니다"(§13.5). (5) handoff 5단계 중 2단계(후속 제어 연결 등록)와 5단계(기존 연결 닫기)는 순전히 연결 관리다(§13.4). 실패 모드도 늘어난다. pipe가 살아 있으나 메인이 멈춘 경우와 pipe가 끊겼으나 메인이 살아 있는 경우가 Git 상태와 독립으로 존재하며, 전자는 §13.5의 소실 정의로는 탐지되지 않는다.
- 동일 목적·기능 보존 대안: pipe를 제거하고 감독기를 Git ref 폴링으로 운전한다. §24.1이 이미 "이후 판본화된 named pipe 또는 Git ref 사건 프로토콜을 사용한다"로 두 선택지를 열어 두었으므로 후자만 남기면 된다. (a) 통지 — 감독기는 `refs/do-math/controller/<instance_id>`와 자기 담당 권한 ref 집합을 설정된 짧은 주기(예: `PT1S`)로 읽는다. 로컬 저장소의 유한한 ref 집합 조회 비용은 무시할 수 있고, 이 설계의 어느 절차도 초 이하 지연을 요구하지 않는다(§9.2 기본 heartbeat `PT5M`, §9.2 "정상 작업 완료는 감독기 원장에 기록하고 다음 heartbeat에서 처리한다"). (b) 메인 생존 — §9.0의 controller 상태가 이미 "heartbeat 세대·다음 시각"을 보존하므로, 이를 갱신 의무가 있는 임차(lease)로 규정하고 만료를 메인 소실로 정의한다. 갱신 주기는 heartbeat 주기와 독립한 설정값으로 둘 수 있다. 이 판정은 pipe 연결 생존보다 강하다. 연결을 붙든 채 멈춘 메인도 임차 만료로 잡힌다. (c) 응답 — §13.3이 이미 요구하는 대로 메인이 결과 커밋을 읽는다. (d) 재전송 — 요청이 ref 상태 하나뿐이면 중복 전송 자체가 없어 §13.2의 idempotency 규칙이 사라진다. §13.4는 "controller ref를 예상 OID로 새 controller ID에 갱신 → 감독기가 새 OID 확인 → `active`"의 3단계로 줄고, "기존 메인의 늦은 요청은 controller OID 불일치로 거부한다"는 현행 규칙이 그대로 권한 판정을 담당한다. 제거되는 것: 스키마 1개, 프레이밍·DACL 규격, 재전송 규칙, 두 연결 종류의 구별, handoff 2단계. 추가되는 것: 폴링 주기 설정값 하나와 controller 임차 필드의 의미 규정 한 줄.
- 대안의 위험·한계: 메인 소실 탐지가 연결 종료의 즉시성에서 임차 주기 단위로 늦어진다. 그 구간에 작업자는 계속 일하지만 작업자 쓰기는 자기 worktree와 run ref에 갇혀 있고(§4.3, §12.1), 후속 메인은 어차피 "각 작업을 운영 점검한 뒤 새 execution ID로 재개한다"(§13.5)이므로 손실은 낭비된 계산뿐이다. 폴링 주기를 짧게 잡으면 감독기가 유휴 시에도 CPU를 조금 쓴다. §1.2가 "서로 다른 clone이나 컴퓨터 사이의 중앙 조건부 갱신은 확장 기능이며 초기 구현 범위 밖"이라고 닫았으므로 원격 push 채널 필요성은 현 범위에서 발생하지 않으나, 그 확장을 실제로 열 때는 통지 채널을 재검토해야 한다.

### O3-02 관찰 의무의 SHA-256 해시 ID가 정규 JSON 바이트 일치에 정체성을 결박한다

- 좌표: 통합-설계 §14.5(1305행), §2.1(126행과 `OO-<SHA256HEX>` 항목), §3.1(212~224행), §26.5 O01·O01a(2218~2219행). 컨텍스트.md §9(310행). CONTEXT.md 「관찰 의무」(167~169행).
- 현재 설계와 복잡성 비용: §14.5는 "의무 ID는 `OO-`에 SHA-256 해시의 64자리 소문자 16진수를 붙인다. 해시 입력은 `execution_id`와 `observation_generation_id` 두 키만 가진 JSON 객체를 3.1절의 정규 JSON 규칙으로 직렬화한 파일 바이트 전건이며 파일 끝 개행도 포함한다"고 정한다. 이 때문에 §2.1은 "관찰 의무를 제외한 모든 장기 객체와 실행 기록은 종류 접두사와 ULID로 식별한다"는 예외를 별도로 둔다. 비용은 정체성이 §3.1 정규 JSON의 바이트 계약 전체(키 코드 포인트 오름차순, 두 칸 들여쓰기, LF, NFC 정규화, 파일 끝 개행 하나)에 의존한다는 점이다. ID 생성은 §14.2가 요구하는 대로 작업자와 외부 감시기가 각자 수행하는데, 두 실행 중 어느 하나라도 직렬화가 한 바이트 어긋나면 서로 다른 의무 ID가 나온다. 그 결과는 조용한 오류다. 감시기는 자기 ID로 의무를 열고, 작업자는 다른 ID를 참조하는 자기 점검을 공개하며, 감시기는 §14.5의 "의무 ID … 를 결정론적으로 검사"에서 불일치를 보고 `violated`로 기록해 운영 점검을 연다. 즉 "같은 실행·세대에서 의무는 하나"라는 불변식을 지키려고 도입한 장치가, 자신이 도입한 바이트 일치 요구 때문에 그 불변식을 깨는 경로를 새로 만든다. 해시가 대가로 사는 것도 없다. 입력은 비밀이 아니고, 길이가 가변이지도 않으며(둘 다 26자 Crockford Base32), 개수도 둘로 고정이다.
- 동일 목적·기능 보존 대안: 의무 ID를 두 ID의 복합 문자열로 둔다. `OO-<execution_id>-<observation_generation_id>`(예: `OO-E-01J…-OG-01J…`). 보존되는 성질은 전부다. (1) 결정론 — 같은 두 ID는 언제나 같은 의무 ID를 낸다. (2) 작업자 측 도출 가능성 — 작업자는 감시 원장을 읽지 않고도(§14.3 "작업자는 이 스냅샷과 감시 결과를 읽지 않는다") 자기 execution ID와 활성 세대 ID만으로 의무 ID를 만들 수 있다. 해시 ID가 실제로 사려던 성질이 이것인데, 복합 ID는 문자열 결합만으로 같은 성질을 준다. (3) 중복 방지 — "monitor 원장 전건에서 의무 하나만 열린다"는 §14.5의 조건부 생성 규칙은 ID가 어떤 형태든 그대로 작동하고, O01·O01a 테스트도 그대로 통과한다. (4) 경로 안전 — 대문자 Crockford Base32와 하이픈뿐이므로 §2.1의 정규식·`git check-ref-format` 검사를 통과한다. 길이는 56자로 현행 67자보다 짧다. 추가로 얻는 것: 사람과 도구가 의무 ID만 보고 어느 실행·세대의 의무인지 조회 없이 안다. 이는 컨텍스트.md §9의 "도래는 `실행 ID + 조건 세대 ID`로 식별하는 관찰 의무를 열 뿐"과 CONTEXT.md의 "`실행 ID + 조건 세대 ID`로 식별해 여는 자기 점검 요구"라는 두 정본 정의를 문면 그대로 실현한다. 현행 해시 ID는 같은 정의를 불투명하게 인코딩한 것이다. §2.1의 예외 문장도 함께 사라져 ID 규칙이 단일해진다.
- 대안의 위험·한계: 의무 ID 문자열이 하이픈 세 개를 포함하므로 ID를 파싱하는 도구는 접두사 `OO-`를 떼고 남은 문자열을 `E-<26>`과 `OG-<26>`의 고정 폭으로 잘라야 한다. 고정 폭이므로 모호성은 없지만 정규식을 정확히 써야 한다. 기존 인스턴스가 이미 해시 ID로 의무를 만들었다면 §23의 마이그레이션 대상이 된다. 현 시점에는 인스턴스가 없으므로 비용이 발생하지 않는다.

### O3-03 하나의 역할 요청 개념이 네 곳에 서로 다른 물리 형태로 흩어져 있다

- 좌표: 통합-설계 §9.0(873행 `controller_role_requests`), §10.1(926~952행 portfolio ref의 `request.json`), §12.2 1단계(1122행), §13.2(1213행), §21.1(1829행), §4.3(338~344행, O1 범위이나 이 분산의 원천), §29 `do-math/role-request/1`(2374행).
- 현재 설계와 복잡성 비용: §29는 역할 요청 스키마를 `do-math/role-request/1` 하나로 이미 통일해 두었는데, 그 기록이 사는 곳은 넷이다. 포트폴리오 선택은 portfolio ref의 독립 파일 `request.json`, 동일성 검토·이의 심사·부분 전문 검토는 certification `state.json`의 `role_requests`, 운영 점검·처분 심사·전례 적용 판정은 operations `state.json`의 `role_requests`, 나머지 비작업 요청은 controller `state.json`의 `controller_role_requests`다. 연구 작업자는 다섯 번째 형태로, 요청 레코드 없이 run ref의 `control=preparing`·`worker_phase=not_started`·프로세스 기대 `not_created`를 시작 권한으로 쓴다(§4.3). 같은 상태 기계(`ready → authorized → completed`, `ready → start_failed`, `authorized → start_failed`)가 네 스키마 위치에 각각 박히고, 그 위에 세 종류의 파생 비용이 붙는다. (1) 라우팅 규칙 — 어떤 역할의 요청이 어디 사는지를 §4.3이 한 문단으로 열거해야 한다. (2) 감독기의 이중 분기 — §12.2 1단계는 "연구 작업자는 run ref가 … 그 밖의 하위 AI는 4.3절이 정한 역할 요청이 `ready`이고"로, §13.2는 "연구 작업자의 `target_authority_ref`는 run ref여야 한다. 그 밖의 역할의 `target_authority_ref`는 12.2절이 정한 역할별 요청 상태 ref여야 한다"로 각각 같은 분기를 반복한다. (3) 상태 검사기 — §21.1이 "controller·monitor·portfolio·certification·operations ref 사슬"을 전부 걸어야 요청 정합성을 볼 수 있다. 또 세 상태 스키마(`controller-state`, `certification-state`, `operations-state`)가 저마다 역할 요청 배열을 품어, 워크플로 상태와 파견 상태라는 두 관심사가 한 CAS 사슬에 섞인다.
- 동일 목적·기능 보존 대안: 비작업 역할 요청을 요청당 전용 ref 하나로 통일한다. `refs/do-math/requests/<instance_id>/<request_id>`가 `request.json` 하나(포트폴리오는 여기에 `input-manifest.json`·`selection-contract.md`·`packet/`을 같은 커밋에 동봉)를 가진 상태 사슬을 소유한다. 이렇게 하면 (1) §4.3의 네 갈래 라우팅 문단이 "비작업 역할 요청은 자기 request ref가 소유한다" 한 줄로 줄고, (2) §13.2의 분기는 "작업자는 run ref, 그 밖은 request ref"라는 같은 모양의 두 경우로 정규화되며(현행처럼 역할마다 다른 부모 문서 안의 배열 원소를 지목할 필요가 없다), (3) certification·operations `state.json`은 워크플로 상태만 소유해 관심사가 분리되고, (4) portfolio ref 네임스페이스가 request ref 네임스페이스에 흡수돼 ref 종류가 하나 준다. 요청과 워크플로 상태를 원자적으로 함께 옮겨야 하는 자리(예: 이의 루프의 다음 회차 개시와 새 심사 요청 개설)는 §18.6이 이미 쓰는 `git update-ref --stdin` 다중 ref 트랜잭션으로 처리한다. 새 기구가 필요 없다. 동시성도 나빠지지 않는다. §9.0이 이미 "모델 예약과 반환 … 은 controller ref의 예상 OID 기반 갱신으로 직렬화한다"고 정해 모든 하위 세션이 controller ref를 두 번 건드리므로, 요청 상태를 요청별 ref로 흩는 편이 controller 경합을 늘리지 않는 선택이다.
- 대안의 위험·한계: ref 개수가 요청 수만큼 늘어난다. 다만 §4.3이 이미 세션 회차마다 output ref를 하나씩 만들고 있어 증가 차수는 같고, §4.4의 보관 ref들도 같은 성질이다. 요청 ref의 보존·정리 정책을 §4.4 수준으로 명시해야 한다(현행 portfolio ref에도 같은 공백이 있으므로 새로 생기는 부채는 아니다). §5.4 재개 4단계와 §21.1의 ref 전수 대조 목록에 `requests` 네임스페이스를 넣어야 한다.

### O3-04 전례 적용 판정의 낡음 기준이 무관한 공용 편입 하나에도 두 판정 세션을 폐기시킨다

- 좌표: 통합-설계 §17.4(1466행), §17.3(1452~1458행), §16.4(1424~1426행), §2.5(196~206행), §1.2(84~98행 runtime ref 목록), §4.1(273~312행 공용 트리), §26.6 C08(2241행).
- 현재 설계와 복잡성 비용: §17.4는 "전례 적용 판정은 형식 필터가 읽은 활성 전례·대체·폐기·비적용 관계의 ref OID 전건과 기준 run OID를 봉인한다. 고영향 처분을 적용하기 직전에 그 ref OID 전건과 기준 run OID를 다시 대조한다. 하나라도 달라지면 판정은 `stale`로 보존하고 … 형식 필터와 1·2차 판정을 새로 실행한다"고 정한다. 그런데 전례 기록은 §4.1의 공용 트리 `precedents/` 아래에 있고, 대체·폐기·비적용 관계는 `relations/`에 있으며, §1.2의 runtime ref 목록에 전례 전용 ref는 없다. 따라서 "그 ref OID"가 실제로 가리킬 수 있는 것은 인스턴스 공용 브랜치 ref 하나다. 그러면 판정이 진행되는 동안 다른 작업이 §18.6의 종결 트랜잭션으로 공용 머리를 한 번만 옮겨도 — 그 편입이 전례와 아무 관련이 없어도 — 판정 전건이 `stale`이 된다. 대가는 크다. 형식 필터 재실행에 더해 §17.3의 1차 판정과, 1차가 applicable일 때 2차 판정까지 최대 두 개의 `gpt-5.6-sol high` 세션을 다시 태워야 하고, 그동안 고영향 처분 적용은 계속 막힌다. 공용 머리는 작업이 종결될 때마다 움직이므로(§18.6) 동시 작업자가 여럿인 정상 운전에서 이 충돌은 예외가 아니라 상시 조건이다. 게다가 이 넓은 기준은 §16.4가 운영 점검에 적용한 좁은 기준("점검자는 시작 run OID를 고정한다")과 어긋나고, §26.6 C08의 문면("전례 집합이 판정 뒤 변경 → 낡은 판정, 재실행")보다도 넓다. 테스트는 전례 집합의 변경을 조건으로 말하는데 규범 문면은 공용 머리의 변경을 조건으로 말한다.
- 동일 목적·기능 보존 대안: 봉인 대상을 ref가 아니라 실제로 읽은 기록의 판본으로 좁힌다. §2.5가 이미 "공용 객체의 정확한 판본은 `{record_id, public_commit}`으로 참조한다"는 기구를 제공하므로 새 장치가 필요 없다. 형식 필터는 (a) 자기가 열거한 활성 전례 ID 집합과 (b) 읽은 전례·대체·폐기·비적용 기록 각각의 `{record_id, public_commit, sha256}`을 봉인한다. 적용 직전 재대조는 현재 공용 머리에서 같은 record ID들을 다시 해석해 (a)의 집합과 (b)의 내용 해시가 모두 같은지 본다. 같으면 판정은 유효하고, 하나라도 다르면 현행대로 `stale`로 보존하고 재실행한다. 기준 run OID 대조는 §16.4와 같이 유지한다. 이렇게 하면 전례 효력 집합이 실제로 바뀐 경우에만 재실행이 일어나 C08의 문면과 정확히 일치하고, 무관한 작업 종결로 인한 재실행이 사라진다. 안전성은 약해지지 않는다. 판정이 의존한 입력이 하나라도 바뀌면 여전히 낡음으로 처리된다.
- 대안의 위험·한계: 활성 전례 집합의 열거 자체가 봉인 대상에 들어가야 한다. 그렇지 않으면 새 전례가 추가된 경우를 놓친다(위 (a)가 이를 담당한다). 재대조가 ref OID 한 번 비교에서 record 수만큼의 경로 해석과 해시 비교로 늘어나지만, 대상은 형식 필터를 통과한 소수의 전례와 그 관계 기록뿐이고 비교는 Git 객체 조회이므로 비용은 무시할 수 있다. §17.4의 문면을 바꾸므로 O4 범위인 §18과의 정합은 별도 확인이 필요하지만, §18은 전례 판정을 참조하지 않는다.

### O3-05 포트폴리오 수신자 검사 실패 분기가 정의되지 않았고, 컨텍스트.md의 처방이 §4.3 상태 기계와 양립하지 않는다

- 좌표: 통합-설계 §10.6(1021~1027행), §10.5(1019행), §10.1(952행), §4.3(340행), §9.1(893행), §27 14항(2310행). 컨텍스트.md §11.4(396행).
- 현재 설계와 복잡성 비용: §10.6은 세 갈래 중 둘만 닫는다. 현재성 대조 실패는 "결과를 `stale`로 보존하고 새 선택을 연다", 전부 통과는 "선택된 순서대로 작업 점유를 시도한다". 남는 갈래 — 상태는 그대로인데 메인이 다시 돌린 검사기가 구체적 결함을 낸 경우 — 의 처분이 §10 어디에도 없다. 이는 §27 14항 "문서·스키마·도구·테스트 사이에 알 수 없는 상태나 구현자 선택지가 없다"는 자기 완료 조건에 대한 위반이다. 한편 컨텍스트.md §11.4는 그 갈래를 명시한다. "구체 결함이면 같은 선택 세션에 재작성을 요청하고, 상태가 달라졌으면 낡은 선택으로 보존한 뒤 새 세션을 연다." 그런데 이 처방은 통합-설계의 상태 기계로 표현할 수 없다. §10.5는 선택 세션이 산출물을 "자기 output ref에 한 번 봉인하고 산출 OID·해시만 반환한다"고 하고, §10.1은 결과 수집과 상태 기록이 끝나면 요청을 "`completed`로만 바꾼다"고 하며, §4.3은 허용 전이를 `ready → authorized → completed` 등으로 닫고 "재시도는 기존 요청을 되돌리지 않고 새 request ID·execution ID·output ID를 만든다"고 못 박는다. §9.1은 세션이 "결과를 봉인하고 세션 종료가 확인될 때까지" 용량을 점유한다고 하여 봉인 시점에 세션이 끝남을 전제한다. 즉 `completed` 요청을 되돌려 "같은 선택 세션에 재작성을 요청"할 자리가 없다. 두 정본이 같은 사건에 서로 다른 처방을 준다.
- 동일 목적·기능 보존 대안: 갈래를 하나로 줄여 양쪽을 동시에 해소한다. §10.6에 "수신자 검사가 실패하면 현재 상태가 같더라도 결과를 결함 근거와 함께 보존하고 새 선택 회차를 연다"를 명시하고, 컨텍스트.md §11.4의 "같은 선택 세션에 재작성을 요청하고" 절을 같은 문면으로 맞춘다. 근거는 세 가지다. (1) §10.5가 이미 생산자 검사와 그 안에서의 자체 수정을 요구하므로("검사 실패는 같은 선택 세션 안에서 수정한다"), 수신자 검사까지 실패했다는 것은 생산자 자체 검사가 통과했다고 주장한 산출물이 실제로는 불합격이라는 뜻이다. 그 세션에 다시 맡길 근거가 오히려 약하다. (2) 포트폴리오 선택은 §19.5·§19.8의 검토자·심사자와 달리 회차 간 누적 대화를 유지할 이유가 없다. 선택은 매 회차 독립이며(컨텍스트.md §11.3 "매 선택 회차마다 새 `gpt-5.6-sol max` 세션 하나를 열고"), 입력은 packet 전문으로 완결된다. (3) 이 선택은 §10에서 세션 연속성 기구(`agent_session_id` 고정, transcript 복원)를 아예 배제해 §10의 상태 기계를 `ready → authorized → completed` 한 줄로 유지시킨다. 연속성이 필요하다는 판단을 내린다면 대안은 §4.3이 이미 가진 "같은 논리 세션이 여러 회차에 참여하면 회차마다 새 output ID와 새 execution ID를 만든다"를 §10.6에 명시적으로 원용하는 것이다. 어느 쪽이든 현재의 미정의 갈래와 문서 충돌은 사라진다.
- 대안의 위험·한계: 새 선택 회차는 packet 재생성 비용(§10.2의 전문 묶음과 토큰 계산)과 세션 하나를 다시 쓴다. 다만 이 갈래는 정상 운전에서 드물어야 하고(생산자 검사가 통과했는데 수신자 검사가 실패하는 경우), 잦다면 그것 자체가 도구 결함 신호로 §24.3의 대상이 된다. 두 정본 문면을 함께 고쳐야 하므로 컨텍스트.md §0의 일괄 갱신 절차를 거쳐야 한다.

### O3-06 컨텍스트.md §9의 관찰 응답 한계 규정이 실행 환경 값과 파견 전 검사를 누락한다

- 동일 목적·기능 보존 대안: 컨텍스트.md §9의 해당 문장을 통합-설계 §14.5의 후보·최소값 규칙과 파견 전 관문을 반영해 갱신한다. 최소 변경으로 충분하다. ### O3-07 역할별 모델·노력 배정이 보편 계약에 하드코딩돼 있고 그 예외 하나가 별도 용량 버킷을 만든다

- 좌표: 통합-설계 §9.1(891행), §7.7 4항(801행), §10.1(947행), §17.3(1454행), §19.4(1644행), §19.5(1648·1660행), §19.7(1682행), §19.8(1696행), §19.9(1714행), §6.3(527~537행), §23.3(1950행). 컨텍스트.md §11.1(364행), §13(432~434행).
- 현재 설계와 복잡성 비용: §9.1이 "메인 세션, 포트폴리오 선택, 연구 작업, 씨앗 생성·착수 검토, 운영 점검·처분 심사, 동일성 검토·이의 심사·부분 전문 검토와 목표 감사는 `gpt-5.6-sol max`를 사용한다. 전례 적용 1·2차 판정만 `gpt-5.6-sol high`를 사용한다"로 역할→(모델, 노력) 대응을 계약 문면에 박고, 같은 리터럴이 통합-설계 안에서 10곳(위 좌표), 컨텍스트.md에서 5곳에 반복된다. 이 하드코딩은 설계 자신의 소유권 규칙과 어긋난다. 컨텍스트.md §5.2는 "연구 설정은 모델 용량, 도구와 실행 환경 매개변수를 소유한다"고 하고, §23.3은 "프로젝트별 하드코딩은 연구 헌장·정책·종류 정의나 감사 플러그인으로 이동한다"고 한다. 그런데 §6.3의 설정 기록 목록에는 "모델·노력별 동시 하위 세션 상한"만 있고 역할→모델 대응은 없다. 그래서 모델 배정 하나를 바꾸려면 `do-math` 계약 판본을 올리고 §23의 마이그레이션을 밟아야 하며(§29 말미의 규칙), 15곳의 리터럴을 빠짐없이 고쳐야 한다. 어느 하나를 놓치면 §0.1의 정본 우선순위로도 해소되지 않는 내부 모순이 남는다. 예외 하나가 만드는 별도 비용도 있다. 전례 적용 판정만 `high`이므로 §9.1의 "모델·노력 조합별 동시 하위 AI 세션 상한"이 초기 구현에서부터 두 버킷을 유지해야 하고, `high` 버킷이 소진됐는데 `max` 버킷이 놀고 있는 상태에서 고영향 처분이 §17.1의 적용 관문 앞에 대기하는 기아 상호작용이 생긴다. 그 예외의 편익은 문서 어디에도 근거가 없다. 오히려 §17.1이 정한 대로 전례 적용 판정은 사용자 우회를 허용할지 결정하는 자리이므로, 착수 명세 검토 같은 일상 판정보다 낮은 노력을 배정할 위험 근거가 제시되지 않았다.
- 동일 목적·기능 보존 대안: 역할→(모델, 노력) 대응을 §6.3 연구 설정의 명시 필드(예: `role_model_assignments`)로 옮기고, §9.1은 "각 역할의 모델·노력은 연구 설정의 역할 배정표가 정한다. 배정이 없거나 허용 목록 밖이면 그 역할의 세션을 열지 않는다"만 규범으로 남긴다. 나머지 절(§7.7·§10.1·§17.3·§19.4~19.9)의 리터럴은 "해당 역할의 배정 모델·노력"으로 대체한다. 이렇게 하면 (1) 15곳의 리터럴이 배정표 한 곳으로 모여 불일치 가능성이 사라지고, (2) 모델 교체가 계약 판본 상승·마이그레이션이 아니라 설정 변경이 되며, (3) 초기 인스턴스가 모든 판정 역할을 같은 (모델, 노력)으로 배정하면 용량 원장이 버킷 하나로 시작해 §9.1·§9.3 7단계·§21.2의 "모델별 상한·사용·예약·잔여량" 계산이 그만큼 단순해진다. 안전 경계는 약해지지 않는다. §6.3이 이미 "설정 변경이 목적·정책·신뢰·외부 효과를 바꾸면 단순 설정 변경으로 적용하지 않는다"는 관문을 갖고 있으므로, 인증 검토자의 모델을 낮추는 변경은 그 관문에서 걸린다. 배정표에 "이 역할의 최소 노력" 하한을 함께 두면 관문을 기계적으로도 지킬 수 있다.
- 대안의 위험·한계: 설정으로 옮기면 배정 오류가 계약 검토가 아니라 설정 검토에서 걸러져야 한다. §6.3의 위 관문과 배정표 하한이 그 역할을 하되, 하한 자체는 계약이 소유해야 한다(그렇지 않으면 설정이 자기 하한을 낮출 수 있다). 컨텍스트.md §13과 §11.1도 함께 갱신해야 하며, 그 문서는 "판정 세션 안에서 Codex `ultra`의 내부 다중 에이전트 운전을 사용하지 않는다" 같은 모델 사용 방식 제약도 함께 담고 있으므로 그 제약은 계약에 남겨야 한다.

### O3-08 `shuffle-v1`의 전용 난수 스트림·거부 표집 명세가 요구보다 무겁다

- 좌표: 통합-설계 §10.2(968행), §10.1(948행 "후보 shuffle seed와 알고리즘 판본"), §26.3 P04(2184행). 컨텍스트.md §11.3(384행).
- 현재 설계와 복잡성 비용: §10.2는 후보 블록 섞기를 위해 한 문단에 걸쳐 자체 DRBG와 셔플을 규정한다. 32바이트 seed를 HMAC key로 쓰고, 0부터 시작하는 unsigned 64-bit counter를 8바이트 big-endian 메시지로 인코딩해 `HMAC-SHA256` digest를 만들며, 각 digest를 unsigned 64-bit big-endian 값 넷으로 읽고, Fisher–Yates를 `i = n-1`부터 내려가며 `m = i+1`, `limit = floor(2^64 / m) * m`으로 두고 `x >= limit`이면 버리고 다음 값을 읽으며 아니면 `j = x mod m`으로 교환하고, 값 넷을 다 쓰면 counter를 1 늘린다. 요구는 그보다 작다. 컨텍스트.md §11.3은 "운영체제 난수로 만든 seed에 따라 매 회차 무작위 순서로 제공한다. seed와 실제 순서를 보존한다. 순서는 우선순위를 뜻하지 않는다"뿐이고, P04는 "같은 shuffle seed → 같은 후보 순서"만 요구한다. 비용은 이 명세가 서로 독립인 divergence 지점을 최소 넷 만든다는 점이다. counter 시작값, counter와 값 읽기의 endianness, digest당 값 개수와 소진 규칙, 거부 경계 `limit`의 계산. 어느 하나라도 구현이 어긋나면 같은 seed에서 다른 순서가 나오고, 그 불일치는 P04에서만 잡히거나 §10.6의 재대조에서 원인 불명의 불일치로 나타난다. 이 명세는 문서 안에서 유일하게 산술 수준까지 내려간 알고리즘이며, 다른 결정론 요구는 모두 기존 표준(정규 JSON, SHA-256, Git OID)에 위임돼 있다.
- 동일 목적·기능 보존 대안: 키 정렬 셔플로 바꾼다. "후보 블록을 `HMAC-SHA256(seed, candidate_block_id)`의 바이트 오름차순으로 정렬하고, 값이 같으면 후보 ID 바이트 오름차순으로 정렬한다. seed와 최종 순서를 기록한다." 보존되는 것은 전부다. Windows CNG 256비트 seed, seed로부터의 완전한 재현성(P04), 기록된 최종 순서, 위치 편향 제거, 블록 내부 원자료 순서 불변. §10.2가 이미 "후보마다 하나의 닫힌 블록 manifest를 만든다"고 하여 안정된 블록 식별자가 존재하므로 정렬 키의 입력이 갖춰져 있다. 사라지는 것은 counter 인코딩, digest 분할, 소진 규칙, 거부 표집 경계 — 즉 위 네 divergence 지점 전부다. 남는 원시 연산은 이미 문서 전체가 의존하는 SHA-256 계열 하나와 바이트 사전식 정렬뿐이다.
- 대안의 위험·한계: 키 정렬은 해시 충돌이 없다는 전제에서만 균등하다. 256비트 출력에서 후보 수가 수천 이하인 이 용도의 충돌 확률은 무시할 수 있고, 동률 시 후보 ID 정렬이라는 결정론적 파훼 규칙이 있어 결과가 미정의로 남지도 않는다. 균등성이 후보 ID와 상관될 여지도 HMAC key가 매 회차 새 seed이므로 없다. 다만 이 변경은 알고리즘 ID를 바꾸므로 §10.1의 "알고리즘 판본" 값과 §26.3 P04의 기대 벡터를 함께 갱신해야 한다.

### O3-09 `context_overflow` 재시도 조건이 이미 봉인한 해시로 표현할 수 있다

- 좌표: 통합-설계 §10.2(970행), §26.3 P03(2183행).
- 현재 설계와 복잡성 비용: §10.2는 packet이 컨텍스트 한도를 넘으면 "controller 상태에 차단 사건과 입력 manifest 해시를 기록한다"고 한 뒤, 재시도 조건을 "후보 집합, 선택 계약, 도구·system 입력이나 모델 컨텍스트 한도가 달라진 다음 heartbeat에서만 packet 생성을 다시 시도하며, 그전 heartbeat는 같은 차단 사건을 보고한다"로 정한다. 이 네 분류는 구현자에게 각각 "달라짐"을 판정할 방법을 요구한다. 후보 집합의 변경(실행 껍질 재계산 결과 비교), 선택 계약 판본 비교, 도구·system 입력 변경 탐지, 모델 한도 변경 탐지. 그런데 앞의 셋은 모두 packet 입력이므로 같은 문장이 이미 기록하라고 지시한 입력 manifest 해시에 흡수된다. 즉 규범이 자기가 만든 요약값을 쓰지 않고 그 요약값이 덮는 집합을 다시 열거한다.
- 동일 목적·기능 보존 대안: "차단 사건에 입력 manifest 해시와 적용한 모델 컨텍스트 한도를 함께 봉인한다. 다음 heartbeat는 현재 입력 manifest 해시나 현재 적용 한도가 봉인값과 다를 때만 packet 생성을 다시 시도하고, 같으면 같은 차단 사건을 보고한다." 판정이 두 값의 동등 비교로 줄고, 후보 집합·선택 계약·도구·system 입력의 변경은 manifest 해시가 자동으로 포착한다. 모델 한도는 packet 입력이 아니라 판정 기준이므로 별도 값으로 남긴다. 결과는 현행 규칙과 동일하되, 열거에서 빠진 입력(예: 헌장·정책 전문 변경, §10.2 packet 목록의 "후보별 연결 자료·근거·작업·실패·기억 기록 전문")이 바뀐 경우까지 정확히 포함해 오히려 현행보다 정확하다.
- 대안의 위험·한계: 입력 manifest 해시가 packet에 들어가는 모든 입력을 실제로 덮어야 한다. §10.1이 "전체 입력 manifest 해시"와 "생성 도구·스키마 판본"을 요청에 고정하고 §7.6이 실행 껍질에 "전체 입력 manifest 해시"를 두므로 이 전제는 이미 성립하지만, manifest의 포괄 범위를 §10.2에 한 줄로 명시해 두는 편이 안전하다. 도구 판본 변경도 재시도 사유이므로 봉인값에 도구·스키마 판본을 포함시켜야 한다.

### O3-10 관찰 조건 연산자 여덟 중 둘은 이미 존재하는 카운터 레지스트리의 특수화다

- 좌표: 통합-설계 §14.2(1262~1274행), §14.1(1241~1252행), §15.2(1355행 "조건 목록은 스키마 판본으로 확장할 수 있다").
- 현재 설계와 복잡성 비용: §14.2의 초기 관찰 연산자는 여덟이며 그중 `counter_gte`는 "등록된 단조 카운터가 한계 이상"으로 이미 카운터 레지스트리를 전제한다. 그런데 같은 표에 `iteration_gte`("작업 계약이 정의한 반복 단위 수 이상")와 `checkpoint_count_gte`("공개 체크포인트 수 이상")가 별도 연산자로 들어 있다. 둘 다 단조 증가하는 정수를 한계와 비교하는 같은 판정이며, 전자는 작업 진전 계약이 정의하는 카운터, 후자는 공개 상태에서 도출되는 카운터다. 비용은 크지 않지만 구체적이다. 조건 검사기가 같은 비교를 세 갈래로 구현하고, 스키마가 세 벌의 인수 형태를 닫으며, `do-math watch`와 작업자가 함께 쓰는 검사기(§14.2 "같은 판본의 조건 검사기를 각자 실행한다")의 표면이 그만큼 넓어진다. 연산자 집합은 §15.2와 §7.3의 규칙상 확장할 때마다 스키마 판본을 올려야 하는 자산이므로, 초기 집합을 필요 최소로 닫아 두는 이득은 누적된다.
- 동일 목적·기능 보존 대안: `iteration_gte`와 `checkpoint_count_gte`를 제거하고 `counter_gte`의 등록된 카운터 ID로 표현한다. 카운터 레지스트리에 출처 구분(작업 진전 계약이 정의해 작업자가 공개하는 카운터 / 작업자 공개 상태에서 결정론적으로 도출하는 카운터)을 한 필드로 두고, 초기 레지스트리에 `iteration`과 `checkpoint_count`를 등록한다. 표현력은 동일하고, 현재 암묵적으로만 존재하던 두 종류의 카운터 출처가 명시된다는 부수 이득이 있다. 연산자는 여섯으로 닫힌다. `active_duration_gte`는 §14.3의 감시 스냅샷이 고정하는 시간 값이고 `wall_time_reached`는 절대 시각이므로 카운터로 접지 않는다. `tool_call_completed`는 §14.5가 그 호출의 도구 manifest로 응답 기간을 정하는 데 도구 식별을 쓰므로 `event_recorded`와 합치지 않는다.
- 대안의 위험·한계: 이득의 크기가 작다. §14.2가 작업자와 감시기에게 "같은 판본의 조건 검사기"를 쓰라고 하므로 구현은 한 벌이고, 줄어드는 것은 그 한 벌 안의 분기 둘과 스키마 변형 둘이다. 레지스트리에 출처 필드를 더하므로 순수한 제거가 아니라 치환이다. 카운터 ID가 자유 문자열이 되지 않도록 §7.3의 "자유 문자열 연산자나 플러그인 코드를 인스턴스 데이터에 넣지 않는다"에 준해 레지스트리를 판본화된 종류 정의로 닫아야 한다.

## 타당 판정

### §11.2 프로세스 기대 상태를 실행 제어와 별도 축으로 둔 것: 권한과 사실을 섞지 않기 위해 필요하다

`not_created`·`running`·`terminating`·`absent_expected` 네 값은 실행 제어에서 도출되지 않는다. `revoked`는 `terminating`(종료 장벽 진행 중)과도, `absent_expected`(장벽 통과 완료)와도 짝지어진다(§11.2·§12.2 10·13항·§18.6). 이 구별이 없으면 §15.2의 "실행 Job Object 또는 루트 프로세스의 예상 밖 종료"를 판정할 수 없고, §26.4 E14("closing 작업자의 Job 종료 뒤 `absent_expected` → 프로세스 소실 경보 없이 인증 진행")가 기대하는 동작이 성립하지 않는다. 두 축을 합치려면 실행 제어에 프로세스 사실을 섞어야 하는데 이는 §0.3의 "판정 결과와 실행 상태를 섞지 않는다"에 정면으로 걸린다.

### §12.2의 14단계 시작 순서: 각 단계가 특정 실패 벡터를 닫는다

`CREATE_SUSPENDED` → Job 편입 → 권한 공개 → `ResumeThread`의 순서는 편입 전에 사용자 코드가 한 명령도 실행하지 못하게 하고(E02), 편입 실패 시 authorized 전이가 생기지 않게 하며(E03), authorized CAS 실패 시 Job 전체를 종료시키고(E04), 권한 공개 뒤 `ResumeThread`가 실패한 경우까지 별도로 닫는다(E04a). 14단계가 길어 보이지만 2~5단계(이름 없는 Job, 상속 불가 handle, `KILL_ON_JOB_CLOSE`, breakaway 금지)는 Win32 호출 인자 수준의 사실 진술이고, 판단이 개입하는 단계는 1·10·11·12·13뿐이다.

### §12.2 11항과 §15.3의 `monitor_started` 장벽: 감시 없는 실행 구간을 원천 차단한다

`preparing` run OID를 참조하는 부모 없는 `monitor_started` 사건을 만들고 감독기가 그 일치를 확인한 뒤에만 루트를 재개하므로, 작업자가 감시기 없이 도는 구간이 존재하지 않는다. 이 장벽이 없으면 감시기 기동 실패가 조용한 무감시 실행으로 나타나고 §15의 외부 안전 조건 전체가 무력해진다. E15가 이 성질을 시험한다. 실패 폐쇄 방향("루트를 일시 정지 상태로 유지해 Job Object를 종료")도 올바르다.

### §12.5 종료 장벽의 여섯 전건: 완료 포트 단독 판정을 금지한 것이 핵심 가치다

"completion port의 `ACTIVE_PROCESS_ZERO` 메시지만으로 완료하지 않는다"와 `TerminateJobObject` 성공·handle 종료 신호·exit code 기록·`ActiveProcesses == 0`·빈 PID 목록·외부 도구 호출 종료 확인의 결합은, 종료가 완료되지 않은 상태에서 worktree를 다음 실행에 넘기는 사고를 막는다. §11.4와 §22.3이 worktree 인계를 이 장벽에 결박하므로 전건 중 하나라도 빼면 부분 종료 상태의 worktree 위에서 새 작업자가 돌 수 있다. E09가 이를 시험한다. 완료 포트 자체는 §12.3의 자식 프로세스 원장 보강(운영 점검이 §16.1에서 "프로세스·Job Object·하위 프로세스"를 읽는 입력)에 기여하므로 보조 입력으로 유지하는 판단도 타당하다.

### §14.2의 작업자·감시기 이중 평가와 정보 차단: 중복이 아니라 독립성 요구다

같은 판본의 검사기를 두 주체가 각자 실행하고 작업자는 감시기의 스냅샷·결과를 읽지 않는다(§14.3). 코드가 두 벌인 것이 아니라 실행이 두 번이며, 작업자가 감시기의 판정을 읽으면 자기 점검이 자기 상태 보고가 아니라 감시 결과의 복사가 된다. 시간 기반 조건에서 두 평가가 일시적으로 어긋나도 시각은 단조 증가하므로 작업자는 다음 안전 제어 경계에서 반드시 도래를 관측하며, 어긋남은 안전한 방향으로 자기 교정된다.

### §14.5의 도구별 최대 응답 기간과 최소값 규칙: 작업 종류에 무관한 고정 시한을 피하는 유일한 방법이다

Lean 전체 빌드와 해시 계산에 같은 응답 시한을 적용하면 전자는 상시 위반이 되고 후자는 사실상 무감시가 된다. 도구 manifest의 필수 필드로 두고 기본값을 금지한 것(§24.1 "어느 값이든 없거나 형식이 틀리면 작업을 파견하지 않고")은 임의의 안전 기본값이 조용히 감시 강도를 결정하는 사태를 막는다. 한 세대에 여러 조건이 도래할 때 "가장 짧은 기간을 사용한다"는 규칙은 의무 하나의 마감을 유일하게 정하기 위해 필요하다(§14.2가 세대를 OR로 묶어 의무를 하나만 열기 때문이다).

### §10.5·§10.6의 이중 기계 검사: 생산자 자기 신고를 통과 근거로 쓰지 않기 위한 최소 구성이다

생산자 검사는 같은 세션 안에서 결함을 고치게 해 왕복을 줄이고, 수신자 검사는 그 결과를 신뢰하지 않고 "실제 결과 커밋의 전문을 읽고 같은 검사기를 별도 프로세스에서 다시 실행한다". 선택자는 AI 세션이므로 `producer-check.json`의 통과 주장 자체는 증거가 아니다. 둘 중 하나를 빼면 왕복 비용이 늘거나(생산자 검사 제거) 검사가 자기 신고가 된다(수신자 검사 제거).

### §15.1의 감시기 권한 축소와 §15.3의 append-only 원장: 감시가 판단으로 번지는 것을 막는다

감시기가 "수학적 진전, 방법의 실질적 차이, 장기 실행의 합리성과 운영 처분 타당성을 판단하지 않는다"고 못 박고 run ref·작업 브랜치 쓰기를 금지한 것은, 결정론적 스크립트가 재량 판정을 흉내 내는 실패를 구조적으로 배제한다. 판단이 필요한 지점은 전부 §16의 운영 점검(새 AI 세션)으로 넘어간다. 단일 부모 사슬과 기존 사건 수정 금지는 사후 감사에서 관찰 이력을 재구성 가능하게 만든다.

### §15.4·§16.4·§10.6의 낡음(stale) 처리: 처분 적용 직전 재고정이 이 설계의 유일한 동시성 안전장치다

§0.3의 "현재 상태를 적용하기 직전에 결박한 Git OID가 여전히 현재인지 다시 확인한다"를 각 절차가 자기 좌표로 구현한 것이다. 감시는 기준 run OID, 운영 점검은 시작 run OID, 포트폴리오는 공용·controller·run ref 집합. 포트폴리오가 공용 머리까지 포함하는 것은 실행 껍질이 공용 커밋의 함수이기 때문이며(§7.5), 따라서 공용 머리 변경은 실제로 후보 집합을 바꿀 수 있다. 넓은 기준이 정당한 자리다(§17.4가 정당하지 않은 자리라는 것이 O3-04다).

### §17.1~§17.3의 전례 관문 2단 판정: 사용자 우회를 허용하는 결정에 비례한다

전례 적용은 사용자에게 묻지 않고 고영향 처분을 적용해도 되는지를 정하는 유일한 관문이다(§17.1). 잘못된 `applicable` 하나가 사용자가 승인한 적 없는 행위를 자동 실행시키므로, 형식 필터로 확실한 배제만 먼저 걷어내고(§17.3 "통과는 유사성이나 적용 가능성을 뜻하지 않는다") 독립 2인 만장일치를 요구하는 구조는 위험에 비례한다. 1차가 applicable일 때만 2차를 여는 순차 구성은 이미 비용을 아끼는 선택이며, "판정자는 운영 점검자·심사자와 역할을 겸하지 않고 자기 결과 봉인 전 다른 전례 적용 판정을 보지 않는다"는 독립성 조건도 이 관문의 목적에 필수다.

### §9.2의 heartbeat 단일 실행과 pending 병합: 재진입을 막는 최소 규칙이다

"heartbeat는 동시에 하나만 실행한다 … 중복 실행을 열지 않고 pending 플래그와 사건 목록을 합친다. 현재 회차가 끝난 뒤 pending 회차 하나를 즉시 연다"는 세 문장이 재진입·사건 유실·무한 누적을 함께 닫는다. 외부 안전 사건만 주기를 기다리지 않게 예외를 둔 것도 정확하다. 안전 절차가 최대 `PT5M` 지연되면 그 시간 동안 위험 상태가 지속되기 때문이다.

### §10.2의 packet 전문 봉인과 컨텍스트 초과 차단: 요약 금지 원칙의 직접 귀결이다

후보 전문·연결 자료 전문을 넣고 넘치면 "요약 없이 `context_overflow`"로 차단하는 것은 컨텍스트.md §11.3의 "실제 한도를 넘으면 조용히 요약·절단하지 않고 선택을 중단한다"와 §0.3의 "요약과 파생 보기는 원자료를 대신하지 않는다"의 귀결이다. 저장 비용도 우려만큼 크지 않다. packet 파일 대부분이 회차 간 동일하므로 Git blob 수준에서 중복 제거되고, 회차마다 실제로 늘어나는 것은 manifest와 순서 기록뿐이다. 정확한 tokenizer로 계산하는 것도 정당하다. 보수적 상한 추정은 1M 컨텍스트의 큰 몫을 낭비시켜 전문 수록 요구와 충돌한다.

### §12.4의 비일반 실행 경로 금지: 금지 자체가 일을 하고 어댑터 계약은 런타임 표면이 없다

WMI·서비스·작업 스케줄러·WSL·컨테이너·원격 서비스의 worktree 쓰기를 금지하고(E07), 어댑터가 갖춰야 할 다섯 요건을 적은 뒤 "초기 Windows 구현에는 이런 어댑터가 없으므로 해당 실행을 금지한다"로 닫았다. 금지가 없으면 Job Object의 격리·종료 보장이 우회되므로 §12 전체가 무의미해진다. 다섯 요건은 미래 계약의 문서화일 뿐 구현·검증 표면을 만들지 않으므로, 명세되지 않은 확장점을 남기는 것보다 값싸다.

## 기능 절충 제안

### 제안 1: 고영향 처분을 비가역성 기준으로 두 층으로 나눠 전례·상신 관문의 적용 대상을 좁힌다

- 현재 설계: §16.3은 여섯 처분(권한 무효화와 실행 인수, 검증된 체크포인트 재개, 처음부터 재시작, 분할 종결, 운영 실패 종결, 중대한 모델·자원 변경)을 하나의 고영향 등급으로 묶고, §17.1은 그 전부에 "승인돼도 자동 적용 권한이 바로 생기지 않는다. 현재 사례에 적용 가능한 사용자 유래 전례가 있을 때만 자동 적용한다"를 적용한다. 결과적으로 작업자 하나가 멈춘 흔한 사건 하나를 처리하는 데 운영 점검자 → 운영 처분 심사자 → 형식 필터 → 전례 1차 판정자 → 전례 2차 판정자까지 최대 네 개의 AI 세션이 직렬로 붙고, 전례가 없으면 사용자 상신으로 막힌다.
- 절충안: (a) 실행 계층 처분(권한 무효화·인수, 검증된 체크포인트 재개, 처음부터 재시작)은 운영 처분 심사 승인만으로 적용하고, (b) 작업 계약을 끝내거나 자원 배정을 바꾸는 처분(분할 종결, 운영 실패 종결, 모델·자원 변경)에만 현행 전례·상신 관문을 유지한다. (a)를 고르는 근거는 이 설계 안에 있다. §11.4의 실행 교체 도구가 새 실행을 열기 전에 run·work·monitor 보관 ref를 먼저 만들고, §22.3이 "가치 판단 없이 `reset --hard`, 삭제나 덮어쓰기를 하지 않는다"를 요구하므로, 실행을 끊고 다시 여는 행위의 최악 결과는 이미 전부 보관된 자료 위에서 낭비된 계산이다. 공용 머리는 §18.6의 종결 트랜잭션에서만 움직이므로 (a)의 어느 처분도 공용 상태를 바꾸지 않는다.
- 무엇을 잃는가: 사용자 권한 경계가 좁아진다. 컨텍스트.md §13은 "사용자 절충이 필요한 결정"을 상신 대상에 넣고, §9는 "실행 인수·재시작"을 명시적으로 고영향 심사 대상으로 열거하며 §17.1의 관문을 그 전부에 건다. 계산 자원의 대량 소모를 사용자 절충으로 볼 여지가 있고(다만 컨텍스트.md §11.1은 "개별 작업에 토큰·시간·비용 예산을 배정하지 않는다"고 하여 작업 단위 비용 절충을 명시적으로 배제한다), 반복 재시작이 누적되면 실질적으로 연구 방향의 자원 배분을 바꾼다는 논거도 가능하다. 이 제안은 그 판단을 사용자에게 되돌리는 것이며, 채택 여부는 사용자 소관이다.
- 함께 해소되는 정밀도 문제: §16.3의 고영향 목록에서 "중대한 모델·자원 변경"의 "중대한"은 이 문서에서 유일하게 정의되지 않은 정도 한정어이며, 닫힌 권한 목록 안에 있으면서도 §27 14항의 "알 수 없는 상태나 구현자 선택지가 없다"를 만족하지 못한다. 계층을 다시 그을 때 이 항목을 "연구 설정의 모델 용량 상한 변경"처럼 기계 판정 가능한 조건으로 닫으면 같은 작업으로 해소된다. 계층 재구성을 채택하지 않더라도 이 정의 공백은 별도로 메워야 한다.

## 범위 외 관찰

- §18.4·§18.5와 §9.3 5단계의 상호작용(O4 범위와 접함): §9.3 5단계는 "적용 가능한 종결 공용 편입을 한 작업씩 최신 공용 머리에 적용한다"고 하고, §18.5는 "공용 머리가 검증 중 바뀌면 새 머리를 임시 편입 브랜치에 merge하고 전건 재검증한다"고 한다. §18.4의 재검증 전건에는 "Lean 빌드·커널·공리·동일성 인증"이 들어 있으므로, 같은 heartbeat에서 종결한 작업이 `n`개면 최악의 경우 `n`회의 직렬 전건 재검증이 필요하고 뒤로 갈수록 앞선 편입 때문에 재검증이 반복된다. 동시 작업자 상한이 8인 설정에서는 이것이 heartbeat 주기를 크게 넘길 수 있다. §18.0의 "`task_terminal_integration`만 연구 작업 하나와 일대일 대응"과 CONTEXT.md의 "연구 작업 하나와 공용 편입 하나가 대응"을 유지하면서 비용을 줄이는 방향(예: 검증은 묶어 한 번 수행하되 검증된 트리에서 작업별 단일 부모 커밋 `n`개를 만들어 하나의 ref 트랜잭션으로 적용)이 있는지는 §18을 소유한 검토가 판정해야 한다.
- §19.5·§19.8의 세션 연속성과 §4.3 요청 상태 기계의 접합(O4 범위): 검토자·심사자는 "같은 `agent_session_id`와 누적 대화 기록을 유지"하고 회차마다 새 `execution_id`를 받는다. 이는 §4.3의 요청 상태 기계와 정합하지만, 회차 사이에 프로세스를 종료해 용량을 반환한 뒤 "봉인된 입력·출력 transcript를 그대로 복원"하는 능력이 실제 실행 어댑터에 존재하는지는 §24의 도구 계약이 명시하지 않는다. transcript 복원은 §29의 스키마 목록에도 대응 항목이 없다. O3-05에서 지적한 포트폴리오 재작성 경로의 공백과 같은 종류의 접합 문제이므로 함께 판정하면 좋다.
- 컨텍스트.md §7.4의 종료 장벽 조건 중 "해당 실행이 승인된 어댑터에 맡긴 외부 도구 호출도 종료되거나 취소됐음을 확인한 뒤에만"은 §12.4가 초기 구현에서 어댑터를 금지하므로 현재 공허하게 참이다. 결함은 아니나, 어댑터 도입 시점까지 이 조건이 검증되지 않은 채 남는다는 사실을 §27의 구현 완료 조건이 인지하고 있는지는 확인 대상이다.
