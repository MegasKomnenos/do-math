# 충실성 검토 F6 — 세션 M 전반부(M1): 종결 계약부터 인증 루프까지의 설계 확정 국면

## 처분 요약

- 읽은 세션: M1(`M1-2026-08-30T23-27.md` 전문), 이슈-18.md 전문, 세션-분류.md
- 판정 집계: 반영 15 / 부분 반영 11 / 누락 0 / 왜곡 0 / 구간 내 대체 0 / 후속 구간 확인 필요 1

주의: 파견 계약의 구간표는 M1을 「전면 검증 라운드 운전 세션 전반부」로 소개하지만, 실제 M1 추출의 내용은 검증 라운드가 아니라 댓글 4가 남긴 종결 계약 질문에서 재개한 설계 확정 대화다. 검증 라운드 운전은 후반부(M2)의 몫으로 보인다. 이 보고는 실제 내용을 기준으로 판정했다.

또 하나의 전제: 이슈 18 본문은 댓글 5가 밝히듯 검증 라운드 14부터 최종 설계에 동기화된 상태로 덤프되었다. 본문은 범위 목록(1~21)과 불변 입력 목록으로 구성된 계약 문서이므로, M1 확정 사항의 세부 어휘·절차가 본문에 없더라도 해당 결정의 본질이 범위·불변 입력에 나타나면 `반영`, 영역만 지정되고 결정의 고유 내용이 없으면 `부분 반영`으로 판정했다. 세부의 정본은 `docs/do-math/통합-설계.md`이나 이 파견의 판정 대상이 아니다.

## 구간 서사 (10문장 이내)

세션 M은 사용자의 `$wayfinder 6` 지시로 시작해 댓글 4가 남긴 미결정인 「연구 작업의 종결 처분과 수학적·연구 결과의 두 축 분리」에서 작업을 재개했다. 사용자는 두 축과 네 종결 처분, 원자적 종결 적용, 잔여 범위 보존, 실행 교체와 운영 실패 종결의 경계를 차례로 확정했다. 이어 worktree 소유를 실행별로 나누려던 제안을 사용자가 단순화 질문으로 되돌려, 작업당 worktree 하나와 Windows Job Object 격리·종료 장벽 계약을 채택했고 `fencing`을 「옛 실행 권한 무효화」로 고쳐 불렀다. Git 점유 선행 시작 순서, `state.json` 상태 분리, 씨앗·작업 동일 기록과 작업 실행의 분리, 공용 작업 생명주기 4값, 실행 종료의 원인·효과 분리를 확정했다. 사용자 제안으로 메인 세션 총괄 아래 중앙 프로세스 감독기가 Job Object handle을 보유하는 구조와 Git 선기록·named pipe 통지 상호작용, 메인 세션 소실 시 안전 정지를 확정했다. 사용자는 프로젝트 입력을 일회성 초기화로 한정하고 내부 정본(연구 헌장 등)이 의미를 영구 소유하는 구조를 요구해 확정했다. 포트폴리오는 사용자가 두 층 분리안을 물리치고 단일 고성능 AI 세션 + 종합 맥락 + 결과 환류 방식을 택했으며, (모델, 상한) 작업자 예산, heartbeat 주기 운전, 별도 선택 세션과 양측 기계 검사를 확정했다. 인증에서는 assistant가 기존 계약을 무시하고 새로 설계하자 사용자가 교정해 「검토자는 이의를 생성하고 심사자는 이의만 심사한다」는 원 구조를 복원했고, 만장일치 이의 루프·검토자 3인+조건부·심사자 3인·부분 전문 검토자·심사 미완료를 확정하며 교착 예외 체계는 실익이 없다고 불채택했다. M1은 assistant가 최종 Lean 관문 순서를 확정할지 묻는 데서 끝나며, 그 답은 M2에 있다.

- 판정: 반영
- 이슈 18 좌표와 근거: 본문 범위 7 「운영 실패와 수학적 실패의 구별」이 두 축 분리를 명시하고, 범위 4가 「작업당 종결 공용 편입 한 번과 완료 기준」을 소유한다. 댓글 4의 「현재 미결정과 첫 질문」이 이 제안 전문(4값과 경계 규칙 포함)을 보존하며, M1의 승인으로 미결정이 닫혔고 댓글 5가 설계 전건 승인을 확인한다.

- 판정: 반영

### F6-05 작업당 worktree 하나와 Windows Job Object 격리 채택

- 원 진술: M1 — 「연구 작업 하나가 하나의 worktree를 가지게 하고 새 작업자의 파견은 언제나 옛 작업자가 모두 정리된 상태에서 이루어지게 하면 문제가 될까? fencing이 뭐지?」, 「그냥 죽이면 되는거잖아 그 프로세스를」, Job Object 활용 방법 검토 요청(execution_id·정지 생성·breakaway 금지·TerminateJobObject 등) 뒤 「채택」
- 종류: 사용자 결정 + 확정 계약
- 판정: 반영
- 이슈 18 좌표와 근거: 불변 입력 Job Object 단락이 「고유 execution_id의 Windows Job Object」, 「breakaway를 허용하지 않고 KILL_ON_JOB_CLOSE를 사용한다」를 명시하고, 범위 6이 「프로세스 격리와 … 작업별 쓰기 소유권」을 소유한다. 용어 교정도 반영됐다: 본문은 `fencing` 대신 「옛 실행의 권한을 무효화한다」를 쓴다(댓글 2·3의 fencing은 과거 handoff 기록으로 남은 것).

### F6-12 메인 세션–감독기 상호작용: Git 선기록·named pipe 통지·OID 재검사·controller ref

### F6-13 계획된 handoff 유지 vs 메인 세션 소실 시 안전 정지 후 전체 종료

- 원 진술: M1 — 「그렇게 하자」 (계획 handoff에는 실행을 유지하고, 예기치 않은 메인 세션 소실에는 체크포인트 시도 뒤 모든 Job Object를 종료하는 제안에 대한 승인)

### F6-14 프로젝트 입력의 일회성 수입과 내부 정본(연구 헌장) 중심 구조

- 판정: 반영
- 이슈 18 좌표와 근거: 불변 입력 「프로젝트 초기화 입력을 인스턴스 생성 시 한 번 읽고 자기 연구 인스턴스 상태로 전수 수입한다. 평시 재개는 초기화 입력을 다시 읽지 않는다」와 「일반 입력 스키마로 받아 그 밖을 포함한 올바른 내부 소유자에게 빠짐없이 나눠 수입한다」, 범위 1 「프로젝트 입력의 1회 수입」이 본질을 명시한다. `연구 헌장` 등 내부 소유자 명칭은 없으나 소유자 분배 계약으로 반영됐다.

### F6-16 단일 AI 선택 세션 포트폴리오와 별도 세션 분리·양측 기계 검사

### F6-21 검토자·심사자 원 구조의 복원 교정

## 미검사·한계

- M1 추출은 tool-use·reasoning을 제외한 표상이므로, assistant가 「확정했습니다」라고 답한 내용과 실제 정본 반영 사이의 일치는 이 파견에서 검증할 수 없다. 판정은 이슈 18 문면과의 대조로 한정했다.
- M1의 확정 다수는 세부 어휘(상태 값, 처분 값, 기수)가 이슈 18이 아니라 `docs/do-math/통합-설계.md`에 반영될 성질이다. `부분 반영` 판정 11건은 이슈 문면 부재의 사실 기록이며, 결함 여부의 최종 판단(설계 문서가 소유하면 족한지)은 F8·검증 세션의 몫이다.
- M2(라운드 운전·최종 승인)가 M1 확정을 라운드 교정으로 수정했을 가능성은 이 구간만으로 배제할 수 없다. 다만 이슈 18 덤프가 최종 동기화 상태이고 M1 확정과 모순되는 문면이 없으므로 `왜곡`은 0건이다.
