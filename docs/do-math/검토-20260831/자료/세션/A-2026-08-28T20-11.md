Lean 검증도 사용한 공리와 형식화의 정확성에 의존합니다. 따라서 세 검증 경로를 하나의 강도 순서로 배열하면 의미가 왜곡됩니다.

## ASSISTANT

제가 현재 이해한 세 용어는 같은 축의 등급이 아닙니다.

| 용어 | 뜻 | 검증하는 범위 |
|---|---|---|
| 문헌 공인 | 학계 문헌에 제시된 기존 증명을 원문에서 회수해 검토하는 경로 | 문헌의 논증이 해당 결론을 뒷받침하는가 |
| 자체 증명 | 이 연구 과정에서 새로 생산한 증명을 검토하는 경로 | 새 증명의 모든 논증 단계가 타당한가 |
| Lean 검증 | 형식화된 명제와 증명 항을 Lean 커널로 검사하는 방법 | 형식 명제가 선언된 공리와 정의에서 도출되는가 |

문헌 공인은 단순히 “논문에 실렸다”는 뜻이 아닙니다. 다음 절차까지 마쳐야 문헌 공인으로 이해합니다.

1. 원 증명 실물을 확보합니다.
2. 정의, 가정, 보조정리와 논증 단계를 복원합니다.
3. 검토자가 논증을 직접 따라가며 타당성을 확인합니다.
4. 검토자가 결함을 발견하면 오독과 관례적 생략 가능성을 먼저 재검토합니다.
5. 재검토를 통과한 실제 결함만 결함으로 기록합니다.

학계 문헌이라는 사실은 높은 사전 신뢰를 줍니다. 그러나 그 사실만으로 연구 지도 객체를 `확실`로 바꾸지는 않습니다. 이 내용은 사용자가 이미 확정했습니다.

자체 증명은 이 연구의 에이전트나 사용자가 새로 만든 증명입니다. 자체 증명에는 학계 문헌이 주는 사전 신뢰가 없습니다. 따라서 증명을 만든 주체와 독립된 검토자가 정의, 가정, 각 추론, 경계 사례를 적대적으로 검사해야 한다고 이해합니다. P vs NP에 관한 주장은 상대화, 자연 증명, 대수화 장벽과의 관계도 설명해야 합니다.

다만 독립 검토자의 수, 검토 라운드, 반례 탐색 절차와 승인 정족수는 아직 확정되지 않았습니다. 그 기준을 정하는 일이 현재 티켓의 일부입니다.

Lean 검증은 출처가 아니라 검증 방법입니다. Lean 커널은 형식화된 명제에 대해 증명 항이 선언된 정의와 공리에서 도출되는지 검사합니다. 이 검사는 형식 체계 안의 잘못된 추론을 강하게 차단합니다.

그러나 Lean 검증만으로 다음 사항이 자동 보장되지는 않습니다.

- 형식 명제가 사람이 의도한 수학 명제와 같은지
- 사용한 정의가 연구 지도의 정의와 같은지
- 숨은 공리나 불필요하게 강한 가정이 없는지
- 원래의 비형식 증명을 형식화하면서 의미를 바꾸지 않았는지

따라서 Lean 검증에는 명제 대응 검토, 정의 대응 검토와 공리 감사가 함께 필요합니다.

세 용어는 서로 배타적이지 않습니다. 문헌 공인 증명을 Lean으로 형식화할 수 있습니다. 자체 증명도 Lean으로 검증할 수 있습니다. 그러면 한 증명은 `문헌 공인 + Lean 검증` 또는 `자체 증명 + Lean 검증`이라는 두 경로를 함께 가집니다.

이 때문에 저는 `문헌 공인·자체 증명`을 증명의 출처로 보고, `수동 검토·Lean 검증`을 검증 방법으로 분리해야 한다고 이해합니다. 현재 정본의 세 항목은 이 두 축을 한 목록에 섞고 있습니다.

## ASSISTANT

제가 추천한 방법을 적용하면, 기존 결정을 바꾸지 않고 모호한 부분을 서로 다른 결정 문제로 분리합니다. 다만 앞서 쓴 `입증 프로필`은 다음과 같이 더 정확히 정의해야 합니다.

각 연구 지도 객체는 `확실` 또는 `불확실` 상태를 가집니다. 각 객체에는 상태의 근거인 하나 이상의 **입증 기록**을 붙입니다. 입증 기록은 다음 정보를 서로 다른 필드로 기록합니다.

- 증명의 출처: `문헌` 또는 `자체 생산`
- 사람이 수행한 검토와 결과
- 독립 검토자의 수와 판정
- Lean 검증 여부와 결과
- 사용한 정의, 가정과 공리
- 원문, 증명과 검증 산출물의 좌표
- 적용한 승인 기준과 승인 결과

따라서 `문헌 공인`, `자체 증명`, `Lean 검증`을 서로 경쟁하는 세 등급으로 두지 않습니다.

지금까지 확정된 내용에는 다음 의미가 생깁니다.

1. `확실/불확실` 이진 상태는 그대로 유지됩니다.

입증 기록이 많아져도 중간 상태는 생기지 않습니다. 검토 중인 객체는 `불확실`입니다. 정해진 승인 기준을 통과한 객체만 `확실`입니다.

2. 문헌에 있다는 사실과 문헌 검토 결과를 분리합니다.

문헌에서 가져온 객체는 처음에는 `불확실`입니다. `문헌`이라는 출처는 높은 사전 신뢰만 부여합니다. 사용자가 확정한 다음 절차를 통과해야 `확실`로 바꿀 수 있습니다.

- 원 증명 확보
- 논증 구조 분석
- 검토자의 자체 타당성 확인
- 발견한 결함에 대한 재검토
- 오독, 관례적 생략과 실제 결함의 구별

따라서 현재의 `문헌 공인`은 실제로 다음 두 정보를 합친 말이 됩니다.

- `공인 문헌에서 가져옴`: 출처에 관한 사실
- `문헌 검토 기준을 통과함`: 확실 판정에 관한 사실

입증 기록은 두 정보를 분리해 보존합니다.

3. 자체 생산 증명에는 별도 승인 기준을 적용합니다.

자체 생산 증명은 학계 문헌이라는 사전 신뢰가 없습니다. 증명을 작성했다는 사실만 기록한 상태에서는 객체가 `불확실`입니다. 현재 티켓이 정할 적대 검증 기준을 통과해야 `확실`로 바뀝니다.

4. Lean 검증은 추가 검증 결과가 됩니다.

Lean 검증은 문헌 증명과 자체 생산 증명 모두에 붙을 수 있습니다. Lean 검증이 없는 입증 기록도 승인할 수 있는지는 아직 결정하지 않았습니다.

Lean 검증이 성공해도 다음 검토는 별도로 남습니다.

- 형식 명제가 의도한 명제와 일치하는가
- 형식 정의가 연구 지도의 정의와 일치하는가
- 사용한 공리와 가정이 허용되는가

따라서 Lean 성공만으로 `확실` 전이를 허용할지도 아직 결정하지 않았습니다.

5. 표현 체계가 지켜야 할 요구가 하나 늘어납니다.

[「연구 지도 표현 체계를 확정한다」](https://github.com/MegasKomnenos/math/issues/9)는 객체 상태만 표현해서는 부족합니다. 선택한 표현 체계는 다음 연결을 보존해야 합니다.

`연구 지도 객체 → 입증 기록 → 증거 좌표와 검토 결과`

상태를 `확실`로 바꿀 때는 승인된 입증 기록을 반드시 지정해야 합니다. 다만 입증 기록의 자료구조와 상태 전이 구현은 표현 체계 티켓이 결정합니다.

아직 정해지지 않은 내용은 다음과 같이 선명하게 남습니다.

- 문헌 검토를 몇 명이 수행하는가
- 문헌에서 결함을 발견했을 때 누가 어떤 절차로 재판정하는가
- 자체 생산 증명에 몇 명의 독립 검토자가 필요한가
- 독립 검토자가 서로의 판단을 언제까지 보지 않아야 하는가
- 반례 탐색과 장벽 검토를 어떤 순서로 수행하는가
- 어떤 정족수로 자체 생산 증명을 승인하는가
- Lean 검증이 필수인지 선택인지
- Lean 검증만으로 확실 판정이 가능한지
- 공리 감사와 명제 대응 검토를 누가 수행하는가
- 여러 입증 기록이 충돌하면 상태를 어떻게 처리하는가
- 승인된 입증이 나중에 무효화되면 상태를 어떻게 되돌리는가

추천 방법은 이 질문들에 답하지 않습니다. 대신 서로 다른 질문을 `입증 등급`이라는 한 표현에 섞지 않게 합니다.

구체적인 결과는 다음과 같습니다.

- 문헌의 Cook–Levin 증명을 수집하면 출처만 기록하고 `불확실`로 둡니다.
- 사용자가 확정한 문헌 검토 절차를 통과하면 `확실`로 바꿀 수 있습니다.
- 같은 증명을 Lean으로 형식화하면 기존 입증 기록에 Lean 검증 결과를 추가합니다.
- 연구 과정에서 새 보조정리를 만들면 `자체 생산` 입증 기록을 만듭니다.
- 새 보조정리는 자체 증명 승인 기준을 통과하기 전까지 `불확실`로 둡니다.
- Lean이 새 보조정리를 검사해도 명제 대응과 공리 감사를 통과하기 전에는 자동으로 `확실`로 바꾸지 않습니다.

즉, 확정된 이진 상태와 문헌 검토 원칙은 유지됩니다. 현재 티켓은 각 출처와 검증 방법에 적용할 승인 기준을 결정하게 됩니다. 표현 체계 티켓은 그 결정을 기계적으로 기록하고 집행하는 구조를 결정하게 됩니다.

## 확정된 바깥 순서

1. 학술 자료를 광범위하게 탐색하고 수집합니다.
2. 수집한 자료를 정리합니다.
3. 정리한 자료를 사용해 연구 지도를 구축합니다.
4. 연구 지도를 반복해서 확장하고 수정합니다.

수집 범위와 규모는 [「문헌 수집 확장을 설계한다」](https://github.com/MegasKomnenos/math/issues/13)가 정합니다. 문헌을 문제풀이에 활용하는 방법은 [「문헌 활용 메타 전략의 요건을 확정한다」](https://github.com/MegasKomnenos/math/issues/12)가 정합니다.


- 정의와 개념에서 무엇을 입증해야 하는지 미정입니다.
- 기법에서 무엇이 `확실`하다는 뜻인지 미정입니다.
- 기법의 적용 범위와 효력을 별도 명제로 분리할지 미정입니다.

## 추천 구조

기초 체계는 **기초 프로필**로 기록합니다. 기초 프로필은 적어도 다음 내용을 가집니다.

- 논리 체계
- 공리 목록
- 추론 규칙
- 원시 정의
- 신뢰하는 검증기와 버전
- 기초 프로필을 채택한 결정의 좌표

기초 프로필을 `F`라고 하면, 입증 기록이 확정하는 내용은 단순한 `P`가 아닙니다.

```text
F에서 P가 도출된다
```

형식적으로는 `F ⊢ P`입니다. 따라서 연구 지도의 `확실`은 “아무 전제 없이 절대적으로 참이다”라는 뜻이 아닙니다. “명시된 기초 프로필에서 판정 명제가 입증되었다”라는 뜻입니다.

## 공리 객체의 판정 명제

공리 `A`의 판정 명제를 `A는 참이다`로 두면 안 됩니다. 같은 체계 안에서 공리의 참을 입증하려 하면 무한한 기초 후퇴가 생깁니다.

공리 객체의 판정 명제는 다음과 같이 둡니다.

```text
A는 기초 프로필 F가 명시적으로 채택한 공리다.
```

이 판정 명제는 문서와 기초 프로필을 대조해 확정할 수 있습니다. 그러나 공리 `A`의 수학적 내용은 증명된 것이 아니라 가정된 것입니다.

따라서 공리 객체에는 두 정보를 분리해 표시합니다.

- 역할: `기초 가정`
- 상태: `F의 기초 가정이라는 판정 명제가 확실`

상태가 `확실`하다는 말은 공리의 내용이 절대적으로 참이라는 뜻이 아닙니다. 공리가 기초 프로필에 속한다는 사실이 확실하다는 뜻입니다.

## 정리 객체의 판정 명제

정리 `P`의 판정 명제는 다음과 같습니다.

```text
P는 기초 프로필 F에서 도출된다.
```

입증 기록은 다음 사항을 함께 보여야 합니다.

- 증명이 실제로 `F`의 공리와 추론 규칙만 사용하는가
- 숨은 추가 가정이 없는가
- 증명한 형식 명제가 의도한 `P`와 일치하는가
- 사용한 정의가 연구 지도에서 지정한 정의와 일치하는가

이 요건을 통과하면 정리 객체는 `F`에 대해 `확실`합니다.

## 추가 가정과 추측

승인된 기초 프로필에 없는 가정 `H`를 사용해 `P`를 증명했다면 `P`를 그대로 확실하게 만들 수 없습니다. 다음 조건부 명제를 별도 판정 대상으로 둡니다.

```text
F에서 H이면 P이다.
```

즉 `F ⊢ H → P`를 입증합니다. `H`는 불확실 상태를 유지할 수 있습니다. 그러나 조건부 명제 `H → P`는 `F`에 대해 확실할 수 있습니다.

이 구별은 추측을 공리처럼 몰래 사용하는 일을 막습니다.

## Lean 검증

Lean 입증 기록도 기초 프로필을 명시해야 합니다. Lean 검증은 다음 사실을 확인합니다.


Lean 검증에는 공리 의존성 감사가 필요합니다. `sorry`나 승인하지 않은 추가 공리가 들어가면 입증 기록을 승인하지 않습니다.

그러나 Lean 커널도 기초 공리의 진리를 증명하지는 않습니다. Lean은 공리를 받아들였을 때 증명 항이 올바른지만 검사합니다.

## 모순 가능성

기초 프로필이 모순되면 모든 명제가 도출될 수 있습니다. 따라서 기초 프로필에는 별도의 감사가 필요합니다.

## 추천 규칙

1. 증명을 검토하기 전에 **논증 의무 목록**을 만듭니다.

논증 의무 목록에는 다음 항목을 전부 넣습니다.

- 사용한 정의
- 명시한 가정
- 외부 의존 결과
- 각 논증 단계
- 논증 단계 사이의 추론
- 결론과 판정 명제의 대응

2. **전체 검토자**는 논증 의무를 전부 검토합니다.

전체 검토자는 일정 부분집합만 검토하지 않습니다. 각 전체 검토자는 원문에서 전체 증명을 독립적으로 재구성합니다.

3. **전문 검토자**만 일정 부분집합을 검토할 수 있습니다.

전체 검토자가 특정 논증 의무에서 결함, 공백 또는 전문성 부족을 기록하면 전문 검토자를 추가합니다. 전문 검토자의 부분 검토는 전체 검토를 대체하지 않습니다.

4. 검토는 **연속 두 번의 깨끗한 전체 검토**가 나올 때까지 반복합니다.

깨끗한 전체 검토는 다음 조건을 모두 충족한 검토입니다.

- 모든 논증 의무를 검토했습니다.
- 모든 논증 의무를 통과로 판정했습니다.
- 새 결함이나 공백을 제기하지 않았습니다.
- 판단 불가 항목을 남기지 않았습니다.

어느 전체 검토자가 새 문제를 발견하면 깨끗한 검토의 연속 횟수를 0으로 되돌립니다. 문제를 해결한 뒤 새 전체 검토자를 투입합니다. 따라서 전체 검토자 수에는 상한이 없습니다.

5. 검토자는 다른 검토 기록을 보기 전에 자기 기록을 봉인합니다.

검토자는 최신 증명과 논증 의무 목록을 받습니다. 검토자는 이전 검토자의 판단과 기록을 보지 않습니다. 이 규칙은 정박 편향과 판단 모사를 줄입니다.

6. 검토자 한 명은 **검토 실행 하나당 기록 하나**를 남깁니다.

검토 기록은 자유로운 통과 선언이 아닙니다. 검토 기록은 각 논증 의무에 다음 정보를 붙입니다.

- 판정: `통과`, `반대` 또는 `판단 불가`
- 판정 근거
- 직접 확인한 원문 좌표
- 재구성한 추론
- 발견한 결함이나 공백
- 사용한 정의와 가정

검토자가 이전 기록을 고치면 기존 기록을 덮어쓰지 않습니다. 새 기록이 기존 기록을 대체한다고 표시합니다.

7. 검토 기록의 타당성을 절대적으로 보장한다고 주장하지 않습니다.

검토 기록을 다시 입증하고, 그 입증 기록을 다시 입증하는 절차는 무한히 후퇴합니다. 따라서 검토 오류를 완전히 방지할 수는 없습니다.

대신 다음 장치로 오류 가능성을 줄이고 발견된 오류를 교정합니다.

- 모든 전체 검토자가 전체 증명을 독립적으로 재구성합니다.
- 단순 통과 선언을 금지하고 단계별 근거를 남깁니다.
- 연속 두 번의 깨끗한 전체 검토를 요구합니다.
- 가능한 논증 단계에는 기계 검증을 추가합니다.
- 검토 기록을 나중에 다시 실행할 수 있게 원문과 추론 좌표를 보존합니다.
- 검토 기록의 오류가 드러나면 해당 검토 기록을 폐기합니다.
- 폐기한 검토 기록에 의존한 입증 기록도 승인 상태를 잃습니다.
- 다른 승인된 입증 기록이 없으면 객체를 `불확실`로 되돌립니다.

## 그대로 활용할 수 있는 부분

`verify-rounds`는 문헌 증명을 정리한 **입증 문서의 결함을 찾고 고치는 절차**로 사용할 수 있습니다.

입증 문서는 다음 내용을 가진 완성된 산출물이어야 합니다.

- 원문의 판정 명제
- 연구 지도의 판정 명제
- 두 명제의 대응
- 기초 프로필
- 정의와 가정
- 외부 의존 결과
- 모든 논증 단계
- 원문과 증거 좌표
- 결함과 공백에 대한 기존 검토 결과

동결문의 불변식은 이 항목들의 완전성과 수학적 타당성을 고정합니다. 수리자는 입증 문서에서 결함을 찾습니다. 심사자는 각 결함 주장과 수정안이 타당한지 독립적으로 판정합니다.

라운드에서 수정이 발생하면 새 라운드가 새 검토자를 투입합니다. 그래서 전체 검토자 수는 고정되지 않습니다.

## 그대로 활용할 수 없는 부분

현재 `verify-rounds`는 다음 명제를 판정하지 않습니다.

```text
이 증명은 판정 명제를 타당하게 입증한다.
```

현재 심사자가 판정하는 대상은 다음 명제입니다.

```text
수리자가 제기한 결함 주장과 수정안이 타당하다.
```

두 판정은 다릅니다. 모든 수리자가 결함을 놓치면 심사자에게는 판정할 항목이 없습니다. 라운드는 `적용 0건`으로 끝날 수 있습니다. 그러나 이 종료는 증명이 타당하다는 적극적 확인이 아닙니다.

현재 절차에는 다음 한계도 있습니다.

- 수리자를 영역별로 나누면 각 수리자는 증명의 일부만 책임집니다.
- 관점 담당 수리자도 모든 논증 단계에 통과 판정을 남기지는 않습니다.
- 심사자는 원래 증명의 모든 논증 단계를 검토하지 않습니다.
- 심사자는 수리 항목만 검토합니다.
- 심사자는 Lean이나 다른 검사기를 실행할 수 없습니다.
- 라운드 상한에 도달해도 런은 종료합니다.
- 라운드 상한 종료는 미해결 결함의 부재를 보장하지 않습니다.
- 기본 `mixed` 모델 배정은 연구 작업자로 금지된 `gpt-5.6-terra`를 사용합니다.

마지막 문제 때문에 이 지도에서는 기본 모델 배정을 그대로 쓸 수 없습니다. 구체적인 대체 배정은 [「연구 작업자 모델 배정을 확정한다」](https://github.com/MegasKomnenos/math/issues/11)가 정해야 합니다.

## 추천하는 활용 구조

두 단계를 분리하는 방식을 추천합니다.

### 1단계: 입증 문서 검증런

현재 `verify-rounds`를 사용합니다.

- 산출물은 완성된 입증 문서입니다.
- 모든 수리자를 영역 담당이 아니라 관점 담당으로 둡니다.
- 각 수리자는 입증 문서 전건을 볼 수 있습니다.

## Lean 검증이 하는 일

사람이나 에이전트가 다음 내용을 Lean 코드로 작성합니다.

1. 수학적 대상을 정의합니다.
2. 증명할 명제를 정확한 형식 명제로 작성합니다.
3. 그 명제를 증명하는 증명 코드나 증명 항을 작성합니다.
4. Lean의 커널이 증명 항을 검사합니다.

간단한 예는 다음과 같습니다.

```lean
theorem add_zero (n : Nat) : n + 0 = n := by
  exact Nat.add_zero n
```

Lean 커널은 `Nat`과 덧셈의 정의를 기준으로 `n + 0 = n`이 실제로 도출되는지 검사합니다. 증명 단계가 성립하지 않으면 Lean은 코드를 받아들이지 않습니다.

전술이라는 자동화 기능을 사용할 수도 있습니다. 전술은 최종적으로 증명 항을 만듭니다. Lean 커널은 자동화 기능의 주장 자체를 신뢰하지 않고, 생성된 증명 항을 다시 검사합니다.

## 연구 지도에서 말하는 Lean 검증

우리의 입증 절차에서 Lean 검증은 다음 작업 전건을 뜻합니다.

1. 판정 명제를 Lean 명제로 형식화합니다.
2. 사용한 정의와 기초 프로필을 Lean 환경에 형식화합니다.
3. 증명을 Lean 코드로 작성합니다.
4. Lean 커널로 증명 항을 검사합니다.
5. 증명이 사용한 공리를 감사합니다.
6. Lean 버전, 라이브러리 버전과 코드 좌표를 입증 기록에 남깁니다.

단순히 Lean 코드처럼 보이는 문서를 작성하는 것은 Lean 검증이 아닙니다. 실제 Lean 환경이 코드를 오류 없이 검사해야 합니다.

## Lean 검증이 잘 잡는 오류

Lean은 형식화된 범위에서 다음 오류를 잡습니다.

- 성립하지 않는 추론
- 필요한 가정의 누락
- 정의와 맞지 않는 대상 사용
- 증명하지 않은 보조정리 사용
- 빠진 경우
- 타입이 맞지 않는 표현
- 순환하거나 불완전한 증명

예를 들어 증명에서 “따라서 명백하다”라고 생략한 단계가 실제로 앞선 가정에서 도출되지 않으면 Lean 검증이 실패합니다.

## Lean 검증이 보장하지 않는 것

Lean이 증명 코드를 받아들였다고 해서 사람이 의도한 수학 명제가 자동으로 증명되는 것은 아닙니다.

- 판정 명제를 잘못 형식화했습니다.
- `P`나 `NP`를 의도와 다르게 정의했습니다.
- 필요한 결론보다 약한 명제를 형식화했습니다.
- 지나치게 강한 가정을 공리로 넣었습니다.
- 모순된 기초 프로필을 사용했습니다.
- 문헌의 명제와 다른 명제를 형식화했습니다.

이 경우 Lean은 작성된 형식 명제를 정확히 검사했지만, 형식 명제가 원래 판정 명제를 잘못 표현했습니다.

```text

Lean으로 작성한 형식 명제
```

## `sorry`와 공리

Lean에는 아직 증명하지 않은 자리를 임시로 통과시키는 `sorry`가 있습니다. `sorry`가 남은 정리는 완성된 Lean 검증으로 인정할 수 없습니다.

Lean에서 공리를 직접 선언할 수도 있습니다. Lean은 공리의 수학적 내용을 증명하지 않습니다. 공리를 받아들인 뒤 그 공리에서 증명 항이 도출되는지만 검사합니다.

따라서 Lean 검증에는 다음 감사가 필요합니다.

- `sorry`가 없는가
- 어떤 공리를 사용했는가
- 그 공리가 승인된 기초 프로필에 들어 있는가
- 형식 정의가 연구 지도의 정의와 같은가

요약하면 다음과 같습니다.

> Lean 검증은 형식 명제가 명시된 정의와 공리에서 올바르게 도출되는지 컴퓨터가 검사하는 일이다. Lean 검증은 형식 명제가 사람이 의도한 명제와 같은지까지 자동으로 보장하지 않는다.

| 형식화·공리 감사 검토자 | Lean 명제가 판정 명제를 올바르게 옮겼고 허용된 공리만 사용했는가 |

## Lean 검증의 입력

Lean은 다음 내용을 입력으로 받습니다.

- Lean으로 작성한 판정 명제
- Lean으로 작성한 정의
- 기초 프로필에 대응하는 공리
- Lean 증명 코드
- 사용하는 라이브러리

Lean 커널은 이 입력으로 생성된 증명 항을 검사합니다.

## Lean 검증이 성공하면

Lean 검증 성공은 다음 사실의 근거가 됩니다.

> 지정한 Lean 환경에서는 형식 명제가 명시된 정의와 공리에서 도출된다.

성공 결과에는 다음 정보를 붙입니다.

- Lean 버전
- 라이브러리 버전
- 형식 명제의 코드 좌표
- 증명 코드의 좌표
- 사용한 공리
- 커널 검사 결과

이 결과는 입증 기록에 추가됩니다. 그러나 객체를 자동으로 `확실`로 바꾸지는 않습니다.

전체 검토단은 여전히 만장일치로 승인해야 합니다.

## 형식화·공리 감사 관점

Lean 검증을 사용하면 검토단에 `형식화·공리 감사` 관점을 추가합니다. 이 관점의 전체 검토자는 다음 대응을 확인합니다.

- Lean 형식 명제와 연구 지도의 판정 명제가 같은가
- Lean 정의와 연구 지도 정의가 같은가
- 형식화 과정에서 가정이 추가되거나 빠지지 않았는가
- 사용한 공리가 기초 프로필에 포함되는가
- `sorry`나 승인하지 않은 공리가 없는가

Lean 커널은 이 대응을 자동으로 검사하지 않습니다. 그래서 사람이 별도로 감사합니다.

## 형식화 작성자의 역할

형식화를 작성한 사람이나 에이전트는 **입증 생산자**입니다. 형식화 작성자는 같은 판본의 독립 전체 검토자로 계산하지 않습니다.

`형식화·공리 감사` 관점은 형식화 작성자와 다른 검토자가 맡습니다.

## Lean 검증이 실패하면

Lean 실패는 사람 증명이 틀렸다는 판정이 아닙니다. 실패 원인은 여러 가지일 수 있습니다.

- 사람 증명의 추론이 성립하지 않습니다.
- 형식화가 사람 증명을 잘못 옮겼습니다.
- 필요한 정의나 보조정리가 Lean에 없습니다.
- 사용한 라이브러리와 코드가 맞지 않습니다.
- Lean 코드가 불완전합니다.

따라서 실패는 다음 질문을 생성합니다.

> 실패 원인이 사람 증명의 결함인가, 형식화의 결함인가, 형식 환경의 결손인가?

이 질문이 해결되지 않으면 `예외`로 남깁니다. 해당 입증 기록은 승인하지 않습니다. 부분 전문 검토자가 실패 원인을 분석하고, 결과를 새 입증 문서 판본에 반영합니다.

## 사람 증명과 Lean이 충돌하면

사람 검토단이 승인했지만 Lean 형식화가 실패하면 입증 기록을 승인하지 않습니다.

Lean은 성공했지만 사람이 형식 명제의 대응이나 공리를 기각해도 입증 기록을 승인하지 않습니다.

두 검증 경로가 충돌하면 어느 쪽을 자동으로 우선하지 않습니다. 충돌 원인을 해결하고 새 판본을 다시 검토합니다.

## Lean 검증이 없으면

제 제안에서는 Lean 검증이 필요조건이 아닙니다. 따라서 Lean 형식화가 없어도 나머지 검토 기준을 통과하면 입증 기록을 승인할 수 있습니다.

Lean 검증이 충분조건도 아닙니다. Lean만 성공하고 전체 검토단이 승인하지 않으면 입증 기록을 승인할 수 없습니다.

한 문장으로 정리하면 다음과 같습니다.

> Lean은 증명의 형식 추론을 재현 가능하게 검사한다. 전체 검토단은 Lean 형식화가 원래 수학적 의미와 일치하는지 검사한다. 두 결과가 모두 있을 때 서로 다른 오류 부류를 잡는다.

- 추론 단계가 실제로 전제에서 도출되지 않는 오류
- 숨은 가정
- 빠진 경우
- 정의가 요구하는 조건의 누락
- 보조정리의 잘못된 적용
- 증명 의존 관계의 누락
- 사용한 공리의 은폐
- 증명 수정 뒤 생기는 연쇄 불일치

전체 검토자는 자연어 증명을 읽고 판단합니다. 여러 전체 검토자가 같은 관습적 생략이나 같은 잘못된 직관을 공유할 수 있습니다.

Lean 커널은 형식 증명 항을 검사합니다. 그래서 언어 모델들의 공통 편향과 다른 오류 검출 경로를 제공합니다.

## 입증 기록에 주는 실익

Lean 검증은 입증 기록을 다음과 같이 강화합니다.

- 정확한 형식 명제를 남깁니다.
- 사용한 정의를 코드로 고정합니다.
- 사용한 보조정리의 의존 관계를 계산할 수 있습니다.
- 사용한 공리를 감사할 수 있습니다.
- 같은 버전과 환경에서 검증을 다시 실행할 수 있습니다.
- 의존 정리가 무효화되면 영향을 받는 입증 기록을 찾을 수 있습니다.
- 자연어 증명 변경과 형식 증명의 불일치를 검사할 수 있습니다.

이 장점은 여러 세션과 에이전트가 장기간 연구 지도를 갱신할 때 커집니다.

## Lean이 만들 수 있는 거짓 확신

Lean 검증에는 별도의 거짓 통과 위험이 있습니다.

예를 들어 P와 NP를 의도와 다르게 정의하면, Lean은 잘못 정의한 명제의 증명을 정확히 검사할 수 있습니다. 지나치게 강한 공리를 넣어도 같은 문제가 생깁니다.

따라서 Lean 성공만 보고 `확실`로 바꾸면 다음 오류가 생깁니다.

```text
잘못 형식화한 명제의 올바른 증명
```

이 위험 때문에 `형식화·공리 감사` 관점이 필요합니다. Lean이 검사한 명제와 사람이 의도한 판정 명제의 대응을 사람이 검토해야 합니다.

## 현재 저장소에서 발생하는 준비 작업

현재 저장소에는 다음 Lean 실행 기반이 없습니다.

- 설치된 `lean` 명령
- 설치된 `lake` 명령
- 추적 중인 `.lean` 파일
- `lean-toolchain`
- `lakefile`

따라서 지금 당장 Lean 검증을 실행할 수는 없습니다. 도구체인, 라이브러리, 기초 프로필과 검증 절차를 먼저 구축해야 합니다.

[도구 지형 실사](C:\math\docs\wayfinder\pvsnp-재설계\도구-지형-실사.md)는 다음 범위도 확인했습니다.

- Mathlib에는 계산 가능성, Turing 기계와 일부 시간 복잡도 기초가 있습니다.
- Mathlib 자체에는 표준 P, NP와 Cook–Levin 체계가 없습니다.
- Complexitylib과 DescriptiveComplexity에는 P, NP와 완전성 결과가 있습니다.
- 두 라이브러리는 계산 모형, 부호화와 환원 정의가 서로 다릅니다.

따라서 외부 라이브러리의 정리 이름만 가져올 수 없습니다. 연구 지도에서 선택한 정의와 각 라이브러리의 정의가 같은지 먼저 입증해야 합니다.

## 적용 범위별 실익

| 적용 대상 | 실익 |
|---|---|
| 영역 뭉텅이와 연결 가설 | 거의 없음 |
| 문헌 목록과 원문 전사 | 낮음 |
| 정의와 계산 모형의 정합성 | 중간 |
| 기존 Lean 정리와 정확히 대응하는 문헌 명제 | 높음 |
| 작고 독립적인 새 보조정리 | 높음 |
| P vs NP 최종 입증에 직접 쓰이는 명제 | 매우 높음 |
| 연구 지도의 모든 확실 객체 | 형식화 부담과 의미 대응 위험이 과도함 |

Lean은 탐사 단서나 문헌 이해를 검증하지 못합니다. 반면 최종 증명의 논리적 연결을 검사하는 데는 강한 실익이 있습니다.

## 기존 제안의 문제

제가 제안한 “필요조건도 충분조건도 아닌 보강 증거”는 방향은 맞지만 적용 기준이 없습니다.

선택적으로 사용한다고만 정하면 다음 문제가 생깁니다.

- 어려운 증명일수록 Lean 형식화를 생략할 수 있습니다.
- 간단한 증명에만 Lean 기록이 붙습니다.
- 가장 중요한 최종 주장에는 Lean이 없을 수 있습니다.
- 담당자마다 적용 기준이 달라집니다.

따라서 단순한 선택 사항으로 두는 것은 충분하지 않습니다.

## 수정한 추천

Lean을 **일반 객체에는 보강 증거로 두고, 최종 입증 경로에는 필요조건으로 두는 방식**을 추천합니다.

Lean 검증을 필수로 요구하는 범위는 다음과 같습니다.

- P vs NP 문제 노드를 `확실`로 바꾸는 최종 판정 명제
- 최종 판정 명제의 Lean 증명 항이 직접 의존하는 자체 생산 명제
- 해당 의존 관계를 연결하는 환원과 번역 명제
- 위 명제들이 사용하는 정의와 기초 프로필

기존 라이브러리에 같은 명제의 Lean 정리가 있으면 그 정리와 공리 감사를 입증 기록에 연결합니다. 같은 정리가 없으면 최종 입증 경로에 필요한 범위까지 형식화합니다.

그 밖의 연구 지도 객체에는 Lean을 필요조건으로 두지 않습니다. Lean 검증을 붙였을 때는 보강 증거로 기록합니다.

Lean은 어느 경우에도 충분조건이 아닙니다. 전체 검토단의 만장일치와 형식화·공리 감사가 함께 필요합니다.

## 최종 평가

- 모든 연구 지도 객체에 Lean을 요구하면 실익보다 형식화 범위가 커집니다.
- Lean을 완전한 선택 사항으로 두면 가장 중요한 증명에서 생략될 수 있습니다.
- 최종 P vs NP 입증 경로에 요구하면 Lean의 오류 검출력과 재현성을 필요한 자리에 집중할 수 있습니다.

따라서 제 추천은 다음과 같습니다.

> Lean 검증은 일반 객체에는 선택적 보강 증거다. P vs NP 문제 노드의 최종 확실 전이와 그 형식 증명 의존 경로에는 필요조건이다. Lean 검증만으로는 어느 객체도 확실하게 만들 수 없다.

## Lean을 전체 정본으로 삼을 때의 이점

Lean을 먼저 작성하면 다음 정보가 처음부터 엄밀해집니다.

- 수학적 정의
- 판정 명제
- 정리와 보조정리
- 증명 의존 관계
- 사용한 공리
- 기초 프로필
- 형식 증명

자연어 명제를 만든 뒤 Lean으로 다시 번역하지 않으므로 내부 번역 오류도 줄어듭니다. 연구 지도 화면과 문서는 Lean 선언에서 생성할 수 있습니다.

## Lean만으로 전체 지도를 표현할 때의 문제

연구 지도에는 형식 증명 이외의 정보도 있습니다.

- 불확실 객체
- 영역 뭉텅이
- 끝점이 없거나 하나뿐인 연결 가설
- 문헌 출처와 원문 좌표
- 검토단 판정
- 이의와 이의 심사
- 예외와 미해결 상태
- 비활성 이력
- 객체의 분화·대체·제거 이력
- 작업 우선순위와 실패 환류

Lean 자료구조를 새로 만들면 이 정보도 표현할 수는 있습니다. 그러나 Lean 커널은 해당 정보의 연구 의미를 자동으로 검사하지 않습니다. 별도의 스키마와 상태 전이 검사기를 Lean 안에 다시 만들어야 합니다.

특히 불확실 명제를 Lean의 `axiom`으로 선언하면 안 됩니다. 불확실 명제를 공리로 선언하면 그 명제를 이용해 다른 정리를 증명할 수 있기 때문입니다.

불확실 명제는 증명 없이 가정하는 Lean 공리가 아니라, 연구 지도 데이터로 표현해야 합니다.

| 정보 | 정본 |
|---|---|
| 형식 가능한 수학적 정의와 판정 명제 | Lean 선언 |
| 형식 증명과 증명 의존 관계 | Lean 증명 항 |
| 공리 의존성과 기초 프로필 | Lean 환경과 공리 감사 기록 |
| 확실·불확실 상태 | 연구 지도 스키마 |
| 문헌 출처와 입증 기록 | 연구 지도 스키마 |
| 검토·이의·예외·미해결 | 연구 지도 스키마 |
| 뭉텅이와 연결 가설 | 연구 지도 스키마 |
| 이력과 상태 전이 | 연구 지도 스키마와 결정론 검사기 |

이 구조에서는 같은 정보를 두 정본에 복제하지 않습니다.

- Lean은 수학적 내용의 정본입니다.
- 연구 지도 스키마는 인식론적 상태와 연구 과정의 정본입니다.
- 연구 지도 객체는 Lean 선언의 정확한 좌표를 참조합니다.

## 예시

연구 지도에는 다음 객체가 있을 수 있습니다.

```text
객체 ID: claim-017
유형: 명제
상태: 확실@F
Lean 선언: Complexity.SAT.NPComplete_language
입증 기록: evidence-042
```

명제의 정확한 형식 내용은 Lean 선언이 정본입니다. 연구 지도는 그 명제를 다시 자연어로 정의하지 않습니다. 자연어 설명은 Lean 선언에서 사람이 이해할 수 있게 만든 표시입니다.

반면 상태, 출처와 검토 기록은 연구 지도가 정본입니다. Lean 정리 자체에는 “이 문헌을 세 검토자가 어떻게 검토했는가”가 들어가지 않습니다.

## 불확실 명제의 표현

Lean으로 표현할 수 있는 불확실 명제는 증명 없이 명제의 내용만 정의할 수 있습니다.

```lean
def p_ne_np : Prop := P ≠ NP
```

이 선언은 `P ≠ NP`가 참이라고 주장하지 않습니다. 형식 명제의 내용을 이름으로 고정할 뿐입니다.

다음과 같이 쓰면 안 됩니다.

```lean
axiom p_ne_np_proof : P ≠ NP
```

두 번째 선언은 `P ≠ NP`를 증명 없이 가정합니다. 이 선언을 확실한 증거처럼 사용할 수 있으므로 연구 지도의 불확실 의미와 충돌합니다.

## 이 방식에서 Lean의 역할 변화

Lean을 수학적 내용의 정본으로 두면 Lean 검증은 선택적으로 덧붙이는 부가 기능이 아닙니다.

형식화된 객체에는 다음 규칙이 생깁니다.

- 판정 명제는 Lean 선언이 정본입니다.
- 확실 판정에 쓰는 형식 증명은 Lean 커널을 통과해야 합니다.
- 연구 지도는 Lean 선언과 증명 결과를 참조합니다.
- 전체 검토단은 Lean 선언이 문헌이나 연구 의도와 대응하는지 검토합니다.
- 형식화되지 않은 객체는 자연어 또는 별도 구조로 남고 `불확실` 상태를 유지할 수 있습니다.

따라서 앞서 제안한 “Lean은 일반적으로 선택적 보강 증거”라는 지위도 다시 검토해야 합니다. 표현 체계가 Lean 중심 혼합 정본으로 정해지면, 형식화된 판정 명제에는 Lean 검증이 필요조건이 됩니다.

## 현실적인 준비 상태

따라서 Lean 중심 정본을 채택하려면 먼저 다음을 정해야 합니다.

- 사용할 계산 모형
- P와 NP의 정식 정의
- 환원과 완전성의 정의
- 기본 기초 프로필
- 외부 Lean 라이브러리의 채택 범위
- 라이브러리 사이의 정의 대응
- 불확실 객체를 담는 연구 지도 스키마
- Lean 선언과 연구 지도 객체를 연결하는 안정 식별자

형식화 작성자는 다음 작업을 합니다.

- 판정 명제를 Lean 명제로 작성합니다.
- 정의와 기초 프로필을 Lean 환경에 연결합니다.
- Lean 증명 코드를 작성합니다.

## 전체 검토자의 변경

Lean을 사용하지 않는 판본에서는 변경이 없습니다.

Lean을 정본이나 보강 증거로 사용하는 판본에서는 논증 의무에 다음 항목을 추가합니다.

- Lean 형식 명제가 판정 명제와 일치합니다.
- Lean 정의가 연구 지도 정의와 일치합니다.
- 형식화 과정에서 가정이 추가되거나 빠지지 않았습니다.
- 사용한 공리가 기초 프로필과 일치합니다.
- `sorry`와 승인하지 않은 공리가 없습니다.
- 지정한 Lean 버전과 라이브러리에서 커널 검사가 성공했습니다.
- 입증 기록의 선언 좌표와 코드 버전이 실제 검사 대상과 일치합니다.

모든 전체 검토자는 추가된 논증 의무도 판정합니다.

검토단에는 이미 정한 `형식화·공리 감사` 관점을 추가합니다. 해당 관점의 전체 검토자는 Lean 코드, 커널 결과와 공리 의존성을 직접 대조하는 추가 책임을 집니다. 그러나 해당 검토자도 논증 의무 전건을 검토합니다.

## 이의 심사자의 변경

- 심사자는 세 명입니다.
- 세 심사자는 이의 전건을 판정합니다.

Lean과 관련된 이의가 심사 대상에 추가될 수 있습니다.

- 형식 명제가 판정 명제와 다릅니다.
- 정의 대응이 틀렸습니다.
- 승인하지 않은 공리를 사용했습니다.
- 커널 검사 결과가 재현되지 않습니다.
- 사람 증명과 Lean 형식 증명이 서로 다릅니다.

`문맥 대조` 관점의 이의 심사자는 Lean 선언, 정의, 공리와 판정 명제의 대응을 직접 대조합니다. 그러나 나머지 두 심사자도 Lean 관련 이의 전건을 판정합니다.

Lean 관련 이의 때문에 심사자를 네 명으로 늘리지는 않습니다.

## 부분 전문 검토자의 변경

Lean 관련 판정 근거를 확보하지 못하면 `예외`가 발생할 수 있습니다. 예외가 만든 서로 다른 후속 질문마다 부분 전문 검토자 한 명을 배정합니다.

예를 들면 다음 질문입니다.

- 이 커널 오류가 사람 증명의 오류인가
- 형식화가 자연어 증명을 잘못 옮겼는가
- 필요한 보조정리가 라이브러리에 없는가
- 공리 감사 결과가 올바른가

부분 전문 검토자는 원인을 분석하고 필요한 근거를 생산합니다. 부분 전문 검토자는 입증을 승인하지 않습니다. 결과는 새 입증 문서 판본에 포함되고 새 전체 검토단이 다시 검토합니다.

## 판정에 미치는 영향
