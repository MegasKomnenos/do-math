### 왜 필요한가

수학 연구 작업은 실행 시간이 크게 다릅니다. Lean 빌드처럼 비교적 예측 가능한 작업도 있지만, 증명 탐색처럼 완료 시점을 예측하기 어려운 작업도 있습니다. 따라서 일정 시간이 지났다는 이유만으로 작업을 실패 처리하거나 다른 작업자에게 넘기면 다음 문제가 생깁니다.

- 정상적으로 오래 걸리는 연구를 중단할 수 있습니다.
- 원래 작업자와 새 작업자가 동시에 같은 작업을 계속할 수 있습니다.
- 유효한 미커밋 변경이나 체크포인트를 잃을 수 있습니다.
- 단순한 무응답과 실제 교착을 구별하지 못합니다.

반대로 아무 점검 기준도 두지 않으면 소실된 프로세스나 무한 반복이 점유를 영구히 붙잡을 수 있습니다. 제안은 이 둘 사이에서 **자동 중단 대신 자동 점검**을 선택합니다.

### 계약에 들어가는 정보

정확한 JSON 필드명은 후속 설계에서 정하지만, 의미상 다음 네 요소가 필요합니다.

| 요소 | 의미 | 강제하지 않는 것 |
|---|---|---|
| 예상 소요 | 정상 실행을 판단할 때 참고할 시간 범위 | 완료 마감 |
| 진전 신호 | 실행이 살아 있고 의미 있는 상태 변화를 남기는지 확인할 관찰 대상 | 수학적 성공 판정 |
| 무진전 한계 | 진전 신호가 관찰되지 않았을 때 점검을 시작할 기준 | 자동 실패·중단 |
| 외부 대기 조건 | 사람, 원격 계산, 외부 도구 등을 기다리는 정상 상태와 재관찰 조건 | 무기한 대기 허가 |

예를 들어 진전 신호는 단순 heartbeat만으로 충분하지 않을 수 있습니다. 프로세스는 살아 있지만 같은 상태를 무한 반복할 수 있기 때문입니다. 작업 성격에 따라 다음과 같은 신호를 지정할 수 있습니다.

- 새 체크포인트가 유효하게 봉인됨
- 처리한 입력 범위가 증가함
- Lean 의무의 상태가 변함
- 실패한 접근과 그 근거가 구조화되어 기록됨
- 외부 작업의 상태가 지정된 사건으로 바뀜

이 신호는 “증명이 좋아지고 있다” 같은 막연한 주관적 평가가 아니라, 점검자가 실제 파일·로그·체크포인트에서 확인할 수 있는 것이어야 합니다. 다만 신호가 나타났다는 사실만으로 수학적 진전을 확정하지는 않습니다.

### 생명주기

```text
작업 씨앗의 제안
    ↓

    ↓

    ↓

운영 점검 실행
    ↓
계속 / 추가 기록 요구 / 고영향 처분 심사
```

1. **작업 씨앗이 제안합니다.**  
   작업의 성격을 가장 잘 아는 씨앗 작성 단계에서 예상 소요, 진전 신호, 무진전 한계와 외부 대기 조건을 제안합니다.

2. **착수 명세 검토가 점검 가능성을 확인합니다.**  
   검토자는 “이 신호를 실제로 관찰할 수 있는가”, “정상적인 장기 작업을 곧바로 이상으로 오인하지 않는가”, “외부 대기가 무기한 방치로 변하지 않는가”를 확인합니다. 점검할 방법이 없는 작업은 착수 전에 계약을 보완합니다.

3. **작업 실행을 열 때 계약을 고정합니다.**  
   실행은 정확한 작업 씨앗 판본과 점검 계약에 결박됩니다. 이후 작업 씨앗이 바뀌더라도 이미 시작한 실행의 기준이 소급해서 바뀌지 않습니다. 그래야 당시 실행과 점검 처분을 재현할 수 있습니다.

4. **한계 초과는 운영 점검만 발동합니다.**  
   실행 ref를 삭제하거나 작업을 실패 처리하거나 다른 작업자에게 넘기지 않습니다. 운영 점검자가 실제 브랜치, diff, 체크포인트, 로그, 프로세스와 외부 상태를 읽어 정상 장기 실행인지, 교착인지, 소실인지 판단합니다.

5. **계속하기로 하면 새 관찰 계약을 덧붙입니다.**  
   기존 계약의 시간을 뒤로 고쳐 쓰지 않습니다. 점검자는 “다음에는 언제 무엇이 관찰되어야 하는가”를 새 불변 기록으로 남깁니다. 이후에는 원래 계약과 연결된 최신 유효 기록에서 현재 점검 조건을 계산합니다. 반복 연장이 있었는지와 각 연장의 근거가 모두 남습니다.

### 1. 예상 소요는 필수 계약으로 삼기 어렵습니다

개방형 수학 연구에서는 완료 시간을 신뢰성 있게 예측하기 어렵습니다. 같은 질문도 접근법, 발견되는 장애물, Lean 형식화 난도에 따라 소요가 크게 달라집니다. 근거 없는 예상 시간을 필수로 요구하면 작업자는 임의의 숫자를 채우고, 운영 체계는 그 숫자에 거짓 정밀성을 부여하게 됩니다.

따라서 다음처럼 고치는 것이 좋습니다.

- **완료 예상은 선택 정보**로 둡니다.
- 기계 빌드, 유한 입력 검사처럼 근거 있는 경우에만 범위와 산정 근거를 기록합니다.
- 완료 예상은 우선순위와 자원 계획에 참고할 수 있지만, 점검·실패·중단을 직접 발동하지 않습니다.
- 완료 예상이 없어도 작업을 무감시 상태로 두지는 않습니다. 대신 **다음 관찰 조건**을 반드시 둡니다.

다음 관찰 조건은 완료 시각을 예측하지 않습니다. “언제 현재 상태를 다시 드러내야 하는가”만 정합니다. 조건은 작업에 따라 다음처럼 표현할 수 있습니다.

- 특정 작업 단위나 탐색 범위를 처리한 뒤
- 새 체크포인트가 만들어졌을 때
- 외부 사건이 발생했을 때
- 정해진 자원량을 사용한 뒤
- 최대 무소식 시간이 지났을 때

시간은 이 가운데 하나일 뿐입니다. 시간 조건도 “그때까지 끝내라”가 아니라 “그때까지 관찰 가능한 상태가 없으면 점검하라”는 뜻입니다.

### 2. 진전 신호는 외부 감시용 계기가 아닙니다

외부 점검자만 진전 신호를 알고 작업자는 자기 나름대로 일한다면, 말씀대로 올바른 소통 계약이 아닙니다. 작업자는 무엇이 진전으로 인정되고 어떤 증거로 나타나야 하는지 모른 채 사후 평가를 받게 됩니다.

따라서 상위 개념을 **작업 진전 계약**으로 두고 다음을 함께 포함하는 것이 좋습니다.

| 구성 | 의미 |
|---|---|
| 진전 의미 | 이 작업에서 어떤 연구 상태 변화가 실제 진전인지 |
| 진전 증거 | 그 상태 변화를 어떤 파일·Lean 결과·체크포인트·기록으로 확인하는지 |
| 진전 생산 방식 | 작업자가 어떤 작업 방식으로 그 상태 변화를 만들거나 시험할지 |
| 자기 점검 | 작업자가 진행 중 계약과 실제 상태를 대조하고 방식을 조정하는 시점 |
| 외부 점검 | 같은 증거를 운영 점검자가 관찰하고 부재·정체를 조사하는 조건 |

작업자는 실행을 시작할 때 이 계약을 입력으로 받아야 합니다. 작업의 내부 절차도 계약에 나타난 진전을 실제로 생산하거나, 그 진전 가능성을 시험하도록 설계해야 합니다. 체크포인트는 단순 상태 보고가 아니라 다음 세 가지를 드러내야 합니다.

- 지금까지 어떤 진전을 목표로 어떤 행동을 했는가
- 어떤 연구 상태가 실제로 달라졌는가
- 기대한 변화가 없었다면 무엇을 배웠고 작업 방식을 어떻게 바꿀 것인가

예를 들어 증명 탐색의 진전은 완성된 증명만을 뜻하지 않습니다. 다음도 작업 목적에 실제로 기여한다면 진전일 수 있습니다.

- 보조정리 하나를 입증함
- 후보 접근이 성립하지 않는 정확한 장애물을 확인함
- 반례로 추측의 범위를 좁힘
- 여러 후보 가운데 재검토할 가치가 없는 경로를 근거와 함께 제거함
- 모호한 아이디어를 판정 가능한 명제로 정련함
- 새로운 후보를 기존 가시 연구 프런티어와 구별해 기록함

반대로 heartbeat, 소비한 토큰, 늘어난 로그 분량, 근거 없는 메모와 단순 파일 변경은 실행의 생존 신호일 수는 있어도 진전 신호는 아닙니다.

### 3. 신호 생산이 대리 목표가 되면 안 됩니다

작업 방식이 진전 신호 생산에 초점을 둔다는 원칙에는 한 가지 보호 조건이 필요합니다. 작업자가 수학적 목적보다 측정 가능한 신호의 수를 최적화하면 안 됩니다.

따라서 계약은 다음을 함께 명시해야 합니다.

- 진전 신호는 작업 목적에서 도출된 연구 상태 변화의 증거다.
- 신호의 개수나 보고 빈도 자체는 진전이 아니다.
- 진전이 없으면 신호를 꾸며내지 않고, 실패·정체·불확실성과 그 근거를 드러낸다.
- 예상한 진전 신호가 실제 작업에 부적합하다고 발견하면 작업자가 조용히 계약을 바꾸지 않는다. 불일치를 기록하고 점검 또는 재검토를 발동한다.
- 운영 점검자는 신호의 존재뿐 아니라 신호가 지정된 상태 변화를 실제로 입증하는지 원자료와 대조한다.

즉 작업자는 신호를 “보고용 산출물”로 생산하지 않습니다. 작업자는 실제 진전을 만들도록 일하고, 그 진전이 작업자 자신과 외부 점검자 모두에게 같은 의미로 보이도록 증거를 함께 남깁니다.

외부 감시기 자체는 **결정론적 스크립트**로 두는 것이 맞습니다. 도구를 활용하는 AI 세션은 그다음 단계인 **운영 점검 실행**을 맡습니다.

| 역할 | 구현 | 판정 범위 |
|---|---|---|
| 외부 감시기 | 결정론적 스크립트 | 관찰 조건 도래, 프로세스 소실, ref 불일치, 기록 부재·스키마·무결성 오류 |
| 운영 점검 실행 | 도구를 활용하는 AI 세션 | 실제 진전의 의미, 교착 원인, 체크포인트 가치, 계속·재개·분할·종결 제안 |
| 운영 처분 심사 | 별도의 AI 세션 | 고영향 처분의 타당성을 원자료로 재검토 |

외부 감시기는 시계, 프로세스 표, Git ref와 공유 기록을 하나의 관찰 스냅샷으로 고정한 뒤 닫힌 규칙을 실행합니다. 같은 스냅샷과 같은 계약 판본에서는 반드시 같은 `미도래·도래·평가 오류`를 내야 합니다.

외부 감시기가 할 수 있는 일은 다음으로 제한됩니다.

- 다음 관찰 조건 평가
- 외부 안전 발동 조건 평가
- 자기 점검 기록의 존재·스키마·참조·무결성 검사
- 조건이 성립하면 운영 점검 실행을 원자적으로 하나만 생성
- 평가 기록과 사용한 관찰 스냅샷 보존

외부 감시기는 다음을 판단하지 않습니다.

- 진전 신호가 수학적으로 의미 있는 진전인지
- 새 방법이 이전 방법과 실질적으로 다른지
- 작업이 앞으로 성공할 가능성이 있는지
- 어떤 고영향 처분을 적용할지

이런 의미 판단이 필요하면 스크립트가 운영 점검을 발동하고, 운영 점검 AI가 실제 코드·로그·체크포인트·연구 내용을 도구로 읽습니다. AI 판단을 관찰 조건 평가 안에 넣으면 작업자와 외부 감시기가 같은 입력에서 같은 결과를 재현한다는 방금 확정한 원칙이 깨집니다.

따라서 권장 경계는 **“외부 감시기 = 결정론적 스크립트, 운영 점검 = 도구를 활용하는 AI 세션”**입니다. 이 경계를 확정할까요?

## ASSISTANT

관찰 조건 평가는 **판본화된 조건식과 공유 관찰 스냅샷을 결정론적 검사기에 넣는 방식**으로 이루어집니다. AI가 “이제 점검할 때인 것 같다”고 판단하는 방식이 아닙니다.

다만 자세히 보면 `미도래·도래·평가 오류`만으로는 부족합니다. 조건이 도래한 순간 작업자가 자기 점검을 작성하기도 전에 외부 감시기가 운영 점검을 열 수 있기 때문입니다. 따라서 **조건 평가**와 **도래 뒤 생기는 관찰 의무**를 분리해야 합니다.

### 1. 조건식

작업 진전 계약에는 닫힌 연산자로 구성한 조건 세대를 둡니다. 예를 들면 다음과 같습니다.

```json
{
  "condition_generation": "obs-004",
  "mode": "any",
  "clauses": [
    {
      "id": "attempt-count",
      "op": "counter_gte",
      "source": "records/attempts.json",
      "value": 5
    },
    {
      "id": "active-time",
      "op": "active_elapsed_gte",
      "seconds": 5400
    },
    {
      "id": "solver-result",
      "op": "record_exists",
      "record_id": "external-solver-result"
    },
    {
      "id": "wait-fallback",
      "op": "wall_time_gte",
      "instant": "2026-08-30T18:00:00+09:00"
    }
  ]
}
```

`mode: any`이므로 다음 중 하나만 성립해도 관찰 조건이 도래합니다.

- 시도 기록이 5개에 도달함
- 활성 실행 시간이 90분에 도달함
- 외부 계산 결과가 기록됨
- 외부 결과가 없어도 재관찰 시각에 도달함

“충분히 연구했다”, “유망한 생각이 생겼다”처럼 구조화된 공유 기록에서 판정할 수 없는 연산자는 허용하지 않습니다.

### 2. 공유 관찰 스냅샷

검사기는 조건을 계산하기 전에 입력을 한 시점의 스냅샷으로 고정합니다.

```json
{
  "execution_id": "run-17",
  "execution_ref_oid": "abc123...",
  "contract_version": "contract-008",
  "condition_generation": "obs-004",
  "observed_at": "2026-08-30T16:32:00+09:00",
  "active_elapsed_seconds": 5520,
  "counters": {
    "attempt-count": 4
  },
  "existing_records": [
    "checkpoint-31"
  ]
}
```

작업자와 외부 감시기는 같은 검사기와 같은 스냅샷을 사용합니다. 작업자가 가진 내부 정보는 먼저 체크포인트나 공유 기록으로 외부화해야 스냅샷에 들어갈 수 있습니다.

### 3. 결정론적 평가

검사기는 다음 순서로 전건을 평가합니다.

1. 계약 판본, 조건 세대와 실행 ref 좌표를 검사합니다.
2. 조건식의 스키마와 연산자 판본을 검사합니다.
3. 참조한 공유 기록의 존재·자료형·무결성을 검사합니다.
4. 모든 조건 절을 평가합니다.
5. 결과를 다음 우선순위로 냅니다.

   - 하나라도 평가할 수 없으면 `평가 오류`
   - 오류가 없고 하나라도 참이면 `도래`
   - 오류가 없고 모두 거짓이면 `미도래`

오류보다 참을 우선하면, 다른 조건 하나가 참이라는 이유로 깨진 참조나 알 수 없는 연산자가 숨을 수 있습니다. 따라서 `평가 오류`가 우선합니다. 평가 오류는 운영 점검을 발동합니다.

평가 기록에는 입력 스냅샷 해시, 각 조건의 결과와 최종 결과를 모두 남깁니다.

### 4. 도래는 즉시 운영 점검이 아닙니다

`도래`는 작업자에게 **관찰 의무**가 열렸다는 뜻입니다. 관찰 의무의 ID는 실행과 조건 세대로부터 결정론적으로 정합니다.

```text
관찰 의무 ID = 실행 ID + 조건 세대 ID
```

작업자와 외부 감시기는 독립적으로 계산해도 같은 관찰 의무를 가리킵니다. 작업자는 이 의무를 참조하는 작업 자기 점검을 작성합니다.

관찰 의무의 상태는 별도로 다음처럼 진행됩니다.

```text
응답 대기 → 충족
         ↘ 위반
```

- `응답 대기`: 조건은 도래했지만 자기 점검 응답 기회가 남아 있음
- `충족`: 유효한 자기 점검 기록이 해당 관찰 의무를 참조함
- `위반`: 응답 조건까지 유효한 자기 점검이 없음

따라서 외부 감시기는 조건이 도래했다는 이유만으로 즉시 운영 점검을 열지 않습니다. 계약에 정한 짧은 응답 조건까지 자기 점검을 기다립니다. 응답 조건은 완료 마감이 아니라 이미 도래한 관찰 요구에 응답할 운영 한계입니다.

`평가 오류`와 프로세스 소실 같은 외부 안전 발동 조건에는 정상적인 자기 점검 응답을 기대할 수 없으므로 곧바로 운영 점검을 엽니다.

### 5. 자기 점검 뒤 조건 세대를 교체합니다

작업 자기 점검이 유효하면 다음 관찰 조건을 새 세대로 기록합니다.

```text
obs-004 도래
  → 자기 점검 self-check-12
  → obs-004 충족
  → 새 조건 세대 obs-005 활성
```

이렇게 해야 `active_elapsed ≥ 90분` 같은 과거 조건이 영원히 참인 채 반복 발동하지 않습니다. 과거 조건과 자기 점검은 이력으로 남고, 실행 ref에 연결된 가장 최근의 유효 조건 세대 하나만 활성화합니다.

### 6. 경합 처리

평가를 마친 뒤 작업자가 실행 ref를 갱신했을 수 있습니다. 따라서 자기 점검 요구나 운영 점검을 적용하기 직전에 스냅샷의 `execution_ref_oid`가 여전히 현재인지 다시 확인합니다.

- 같으면 평가 결과를 적용합니다.
- 다르면 결과를 낡은 관찰로 보존하고 새 ref에서 다시 평가합니다.

외부 감시기는 작업자의 새 체크포인트를 과거 상태에 대한 평가로 덮어쓰지 않습니다.

결국 경계는 다음과 같습니다.

```text
공유 스냅샷
  → 결정론적 조건 평가
  → 미도래
     또는 관찰 의무 생성 → 자기 점검 → 다음 조건 세대
     또는 평가 오류 → 운영 점검 AI
```

이처럼 **조건 평가와 관찰 의무의 생명주기를 분리하는 모형**으로 확정하는 것이 정확합니다. 이 모형을 승인할까요?

다음으로 닫아야 할 것은 관찰 의무의 **응답 조건**입니다. 조건이 도래해도 작업자가 긴 도구 호출이나 모델 실행 중이면 즉시 자기 점검을 작성할 수 없으므로, 단순한 고정 시간만 사용하면 정상 실행과 경합합니다.

추천은 응답 조건을 두 부분으로 구성하는 것입니다.

- **첫 안전 제어 경계**: 도구 호출 반환, 모델 턴 종료, 반복 단위 종료처럼 작업자가 다음 실질적 행동을 선택할 수 있게 된 첫 시점입니다.
- **최대 응답 시각**: 안전 제어 경계가 오랫동안 나타나지 않을 때 외부 점검을 보장하는 벽시계 한계입니다.

관찰 의무가 열리면 다음 규칙을 적용합니다.

1. 작업자가 안전 제어 경계에 도달하면 다음 실질적 행동을 시작하기 전에 자기 점검을 기록합니다.
2. 안전 제어 경계는 실행·도구 상태 기록에서 외부 감시기도 확인할 수 있어야 합니다.
3. 경계가 오기 전에 최대 응답 시각이 지나면 관찰 의무를 `위반`으로 바꾸고 운영 점검을 엽니다.
4. 최대 응답 시각은 연구 완료 예상이 아닙니다. 관찰 요구를 인지할 기회가 생기지 않는 상태를 조사하기 위한 운영 한계입니다.
5. 최대 응답 시각이 지나도 작업을 자동 중단하지 않습니다. 운영 점검 AI가 장기 도구 호출, 교착, 외부 대기와 정상 진행을 원자료로 구별합니다.
6. 프로세스 소실이나 실행 ref 불일치 같은 외부 안전 발동 조건은 응답 조건을 기다리지 않습니다.
7. 응답 조건의 정확한 시간값은 수학 작업의 예상 난도가 아니라 실행 환경과 도구 호출 유형에서 도출합니다.

다음 결정은 작업자와 외부 감시기가 만드는 실행 중 기록을 **어디에 저장하고 어떻게 경합 없이 공개할지**입니다. 외부 감시기가 작업 브랜치를 직접 수정하면 작업자 소유권을 침범하고, 양쪽이 서로 다른 ref를 정본으로 가지면 어느 상태가 최신인지 다시 조정해야 합니다.

추천은 기존 Git 실행 ref가 하나의 **실행 상태 매니페스트 연쇄**를 가리키게 하는 것입니다.

```text
Git 실행 ref
    ↓
실행 상태 매니페스트 M3
    ├─ 이전 매니페스트 M2
    ├─ 작업 브랜치 머리
    ├─ 최신 체크포인트
    ├─ 작업 진전 계약 판본
    ├─ 활성 관찰 조건 세대
    ├─ 관찰 평가·관찰 의무
    └─ 최신 작업 자기 점검
```

운전 규칙은 다음과 같습니다.

- 작업 브랜치와 worktree는 계속 작업자만 수정합니다.
- 작업자와 외부 감시기는 실행 중 공유 상태를 바꿀 때 새 불변 매니페스트를 만듭니다.
- 새 매니페스트는 직전 매니페스트와 새 기록·산출물 좌표를 참조합니다.
- 양쪽 모두 Git 실행 ref를 `기대한 이전 OID → 새 매니페스트 OID`로 조건부 갱신합니다.
- 조건부 갱신에 성공한 변경만 현재 실행 상태가 됩니다.
- 경합에서 실패한 쪽은 현재 ref를 다시 읽고 자기 변경이 아직 필요한지 재판정합니다.

예를 들어 외부 감시기가 관찰 의무를 게시하는 순간 작업자가 자기 점검을 게시하면 둘 중 하나만 먼저 성공합니다.

- 작업자가 먼저 성공했다면 감시기는 새 자기 점검을 읽고 관찰 의무가 이미 충족됐는지 다시 계산합니다.
- 감시기가 먼저 성공했다면 작업자는 새 관찰 의무를 읽고 이를 참조하는 자기 점검을 작성합니다.
- 어느 경우에도 한쪽 기록이 다른 쪽 기록을 덮어쓰지 않습니다.

이 구조에서는 실행 ref가 세 역할을 함께 가집니다.

- 작업 점유의 현재 세대
- 최신 실행·체크포인트 좌표
- 작업자와 외부 감시기가 합의한 실행 중 공유 상태의 선형 이력

공용 Git 머리는 여전히 종결 공용 편입만 소유합니다. 실행 상태 매니페스트는 공용 작업대 판본이 아니며, 외부 감시기는 작업 브랜치 내용을 수정하지 않습니다. 별도 데이터베이스나 두 번째 실행 상태 정본도 필요하지 않습니다.

## ASSISTANT

지금 문제는 “파일을 어디에 둘까”보다 먼저, **작업자와 외부 감시기가 동시에 실행 상태를 바꿀 때 서로의 변경을 잃지 않게 하는 방법이 아직 없다**는 것입니다. 현재 장애가 발생한 것은 아니고, 방금 확정한 감시 체계를 구현하려면 닫아야 하는 설계 문제입니다.

### 이미 확정된 세 영역

현재 구조에는 다음 영역이 있습니다.

| 영역 | 소유자 | 들어가는 것 |
|---|---|---|
| 공용 Git 머리 | 공용 편입 절차 | 종결된 작업의 공유 결과 |
| 작업 브랜치·worktree | 작업자 | 작업 중 코드, 메모, 산출물과 체크포인트 |
| Git 실행 ref | 실행 제어 | 작업 점유와 최신 실행 좌표 |

공용 머리는 작업이 끝날 때만 바뀝니다. 외부 감시기가 공용 머리에 관찰 기록을 쓸 수는 없습니다.

작업 브랜치는 작업자가 자유롭게 수정하는 공간입니다. 외부 감시기가 여기에 파일을 직접 쓰면 작업자 소유권과 격리가 깨집니다.

그런데 새로 확정한 관찰 체계에는 **작업 도중 양쪽이 공유해야 하는 상태**가 생겼습니다.

- 작업자가 만드는 것

  - 체크포인트
  - 작업 자기 점검
  - 다음 관찰 조건 세대
  - 진전 신호와 증거 좌표

- 외부 감시기가 만드는 것

  - 공유 관찰 스냅샷
  - 관찰 조건 평가
  - 관찰 의무
  - 외부 안전 발동 기록
  - 운영 점검 실행의 생성 좌표

이 상태는 공용 머리에도, 작업자만의 비공개 공간에도 둘 수 없습니다. 양쪽이 실행 중에 즉시 읽을 수 있어야 하기 때문입니다.

### 실제로 생길 수 있는 경합

현재 실행 상태를 `A`라고 하겠습니다.

```text
작업자 ── A를 읽음
감시기 ── A를 읽음
```

그 직후 관찰 조건이 도래합니다.

- 작업자는 이미 조건 도래를 알아차리고 자기 점검 `S`를 준비합니다.
- 외부 감시기도 같은 조건을 평가하고 관찰 의무 `O`를 준비합니다.

```text
작업자: A를 바탕으로 S 작성
감시기: A를 바탕으로 O 작성
```

둘이 같은 `latest-state.json` 같은 파일을 각자 갱신하면 다음 일이 생길 수 있습니다.

```text
작업자: A → S 반영
감시기: A → O 반영
```

감시기는 작업자의 `S`가 생기기 전 상태인 `A`에서 출발했습니다. 감시기 변경이 나중에 저장되면 `S`가 사라질 수 있습니다. 반대로 작업자 변경이 나중에 저장되면 `O`가 사라질 수 있습니다. 이것이 **갱신 유실**입니다.

결과적으로 다음 오류가 가능합니다.

- 자기 점검이 이미 있는데 감시기가 없다고 판단해 운영 점검을 엽니다.
- 관찰 의무가 열렸는데 작업자가 이를 모르고 다음 행동을 계속합니다.
- 감시기가 발견한 ref 불일치가 작업자의 새 체크포인트에 덮입니다.
- 작업자와 감시기가 서로 다른 관찰 조건 세대를 현재라고 생각합니다.
- 오래된 작업자가 새 점유자의 실행 상태를 덮습니다.

### 양쪽에 별도 파일이나 ref를 주어도 문제가 남습니다

작업자용 ref와 감시기용 ref를 따로 만들 수도 있습니다.

```text
작업자 ref → 자기 점검 S
감시기 ref → 관찰 의무 O
```

그러면 변경 유실은 줄지만, 이번에는 “현재 실행 상태가 무엇인가”가 두 곳으로 갈립니다. 이후 판정자는 항상 두 ref를 읽어 결합해야 합니다.

그 사이 한쪽만 바뀌면 다음 질문이 다시 생깁니다.

- 작업자 ref의 자기 점검은 어느 감시기 상태에 응답한 것인가?
- 감시기 ref의 관찰 의무는 어느 작업 체크포인트를 기준으로 열렸는가?
- 두 ref를 읽는 사이 하나가 바뀌면 어떤 조합이 유효한가?

즉 별도 ref 방안도 결국 두 상태를 원자적으로 결합하는 새로운 조정 규칙을 요구합니다.

### 해결책이 만족해야 하는 조건

구체적인 저장 형식을 고르기 전에 다음은 반드시 보장해야 합니다.

1. 작업자는 자기 브랜치의 유일한 작성자로 남는다.
2. 외부 감시기는 작업 브랜치를 수정하지 않는다.
3. 양쪽은 상대가 공개한 최신 실행 상태를 읽을 수 있다.
4. 동시에 갱신해도 한쪽 변경이 사라지지 않는다.
5. 어떤 변경이 먼저였는지 하나의 순서로 복원할 수 있다.
6. 오래된 상태를 기준으로 만든 변경은 현재 상태에 적용되지 않는다.
7. 실행 중 기록이 공용 작업대의 새 판본으로 오인되지 않는다.

제가 앞서 제안한 “단일 실행 ref와 매니페스트 연쇄”는 이 문제를 해결하는 한 방법입니다.

여기서 매니페스트는 작업 산출물 자체가 아니라 다음 좌표만 담는 작은 실행 상태 표지입니다.

```text
현재 작업 브랜치 머리
현재 체크포인트
현재 관찰 조건 세대
열린 관찰 의무
최신 자기 점검
직전 매니페스트
```

작업자와 감시기는 기존 상태가 여전히 `A`일 때만 자기 새 상태로 포인터를 바꿀 수 있습니다. 한쪽이 먼저 바꾸면 다른 쪽의 변경은 실패하고, 다른 쪽은 새 상태를 다시 읽어야 합니다. 그래서 서로의 변경을 덮을 수 없습니다.

즉 지금 해결하려는 문제는 다음 한 문장입니다.

> 작업자와 결정론적 외부 감시기가 서로 다른 소유 영역을 유지하면서, 실행 중 공유 상태를 동시에 갱신해도 변경을 잃거나 서로 다른 현재 상태를 만들지 않게 해야 한다.

아직 이 문제의 해결책은 확정하지 않았습니다. 앞서 제안한 매니페스트 모형도 승인 전 상태입니다.

“작업자와 외부 감시기가 같은 기준으로 판정한다”는 말은 같은 기록을 서로 주고받는다는 뜻이 아닙니다. 다음을 뜻합니다.

- 작업자가 자기 실행 상태를 외부에서 읽을 수 있게 공개한다.
- 작업자와 외부 감시기가 같은 판본의 결정론적 검사기를 사용한다.
- 외부 감시기는 작업자가 공개한 특정 실행 ref OID를 입력으로 판정을 재현한다.

흐름은 기본적으로 한 방향입니다.

```text
작업자
  │
  ├─ 체크포인트
  ├─ 관찰 조건 세대
  ├─ 작업 자기 점검
  └─ 실행·도구 상태
       │
       ▼
외부 감시기
  │
  ├─ 관찰 스냅샷
  ├─ 조건 평가
  └─ 관찰 의무 이행 판정
       │
       ▼
운영 점검 AI
```

작업자는 자기 관찰 조건이 도래했는지 같은 검사기로 스스로 계산합니다. 외부 감시기도 작업자가 공개한 상태를 독립적으로 다시 계산합니다. 외부 감시기가 관찰 의무를 작업자에게 “발송”할 필요도 없습니다. 관찰 의무 ID는 `실행 ID + 조건 세대 ID`에서 결정되므로 양쪽이 독립적으로 같은 ID를 계산할 수 있습니다.

외부 감시기가 만든 다음 기록은 감시기 전용 감사 이력으로 두면 됩니다.

- 감시기가 읽은 실행 ref OID

- 작업자가 코드나 메모를 커밋할 때마다 실행 제어 상태까지 바뀐 것처럼 보입니다.

- 어느 작업 커밋이 외부 감시기에 공개된 체크포인트인지 구별하기 어렵습니다.
- 작업 산출물과 실행 제어 정보의 소유권이 섞입니다.

추천은 실행 ref가 작업 브랜치 자체가 아니라 작은 불변 **실행 상태 기록**을 가리키게 하는 것입니다.

```text
Git 실행 ref
    ↓
실행 상태 기록
    ├─ 직전 실행 상태 기록
    ├─ 실행 ID와 점유 세대
    ├─ 작업자
    ├─ 기준 공용 커밋
    ├─ 작업 브랜치 머리
    ├─ 공개한 최신 체크포인트
    ├─ 작업 진전 계약 판본
    ├─ 활성 관찰 조건 세대
    ├─ 최신 작업 자기 점검
    └─ 적용된 실행 제어 세대
```

작업자의 실제 코드·메모·산출물은 계속 작업 브랜치에 있습니다. 실행 상태 기록은 그 가운데 외부에 공개하기로 한 좌표와 실행 제어만 가리킵니다.

작업자가 상태를 공개하는 절차는 다음과 같습니다.

1. 작업 브랜치에 체크포인트와 자기 점검을 완결된 커밋으로 기록합니다.
2. 스키마·참조·무결성을 검사합니다.
3. 그 커밋을 가리키는 새 실행 상태 기록을 만듭니다.
4. 실행 ref가 여전히 기대한 이전 기록을 가리킬 때만 새 기록으로 조건부 갱신합니다.

확정된 운영 처분도 같은 실행 상태 기록을 사용하되 작업 브랜치를 수정하지 않습니다. 기존 작업 좌표를 그대로 유지하면서 실행 제어 세대만 바꾼 새 기록을 만들고 실행 ref를 조건부 갱신합니다.

작업자와 운영 처분 실행이 동시에 갱신하면 하나만 성공합니다.

- 작업자가 먼저 성공하면 운영 처분은 새 작업 상태에 아직 적용 가능한지 다시 검사합니다.
- 운영 처분이 먼저 성공하면 작업자의 오래된 공개는 실패하고, 작업자는 새 제어 상태를 읽은 뒤 다시 판단합니다.

외부 감시기는 이 ref를 읽을 뿐 갱신하지 않습니다. 감시 기록 원장은 이 실행 상태 기록과도 분리됩니다.

즉 정할 내용은 다음과 같습니다.

> Git 실행 ref는 작업 브랜치 머리를 직접 가리키지 않고, 작업자가 공개한 작업 좌표와 권위 있는 실행 제어 상태를 결합한 불변 실행 상태 기록을 가리킨다.

  ### 가장 간단한 Git-native 구조

  작업 브랜치

        └─ 부모 S1

  실행 상태 커밋에는 작은 state.json 하나만 둡니다.

  {
    "execution_id": "run-17",
    "worker": "...",
    "base_commit": "...",
    "work_head": "...",
    "checkpoint": "...",
    "progress_contract": "...",
    "observation_generation": "...",
    "self_check": "...",
    "control": "running"

  - 실행 상태 커밋의 부모가 직전 상태를 나타냅니다.

  ### 갱신도 Git 기본 연산을 사용합니다

  작업자가 이전 상태 S2를 읽고 새 상태 S3를 만들었다면 다음 의미로 갱신합니다.

  git update-ref <실행-ref> <S3> <S2>

  현재 ref가 여전히 S2일 때만 S3로 바뀝니다. 그사이 승인된 운영 처분이 ref를 바꿨다면 갱신은 실패합니다. Git 공식 문서가 이 기존 OID 확인 방식과 여러 ref의 트랜잭션 갱신을 직접 지원합니다. git-
  update-ref 문서

  따라서 별도의 잠금 파일, 세대 카운터, 데이터베이스나 compare-and-swap 구현이 필요하지 않습니다.

  ### 왜 작업 브랜치 하나만 쓰지 않는가

  작업 브랜치에 state.json까지 넣는 방법이 표면적으로는 더 단순합니다. 하지만 승인된 운영 처분이 중단·계속 같은 제어 상태를 바꾸려면 작업자가 checkout한 브랜치의 ref를 외부에서 갱신해야 합니다. 그러
  면 worktree와 branch tip이 어긋날 수 있습니다.

  그래서 역할을 둘로만 나누는 것이 가장 작고 건전합니다.

  - 작업 브랜치: 작업자가 실제 연구 내용을 소유
  - 실행 상태 ref: 공개한 작업 좌표와 실행 제어 상태를 소유

  외부 감시기는 둘 다 읽기만 합니다.

  ### Git notes는 더 단순하지 않습니다

  Git notes는 기존 커밋을 바꾸지 않고 메타데이터를 붙이는 Git-native 기능입니다. 그러나 notes도 실제로는 refs/notes/... 아래의 별도 ref에 저장됩니다. 현재 제어 상태, 이전 상태와의 순서, 조건부 갱신을
  다시 설계해야 하므로 여기서는 구조가 줄지 않습니다. git-notes 문서

  ### 추천 결론

  물리 구조는 다음이면 충분합니다.

  refs/do-math/runs/<연구 인스턴스 ID>/<작업 ID>
      → state.json 하나를 가진 실행 상태 커밋
      → 부모 커밋이 이전 실행 상태

  문서에서는 이를 어렵게 “ref 기반 매니페스트 연쇄”라고 부르지 않고 실행 상태 이력이라고 설명하면 됩니다.

  - ref: 현재 실행 상태를 가리키는 포인터
  - 커밋: 한 시점의 불변 실행 상태
  - 부모 관계: 실행 상태 이력
  - 커밋 OID: 상태 세대와 경합 검사 값
  - git update-ref … <old-oid>: 원자적 조건부 갱신

### 통과한 부분

- `refs/do-math/runs/<인스턴스>/<작업>`이 현재 실행 상태 커밋을 가리키고, 각 상태 커밋이 직전 상태를 부모로 갖는 구조는 Git-native합니다. 커밋은 부모를 가질 수 있으므로 별도의 `previous_state` 연결 구조가 필요하지 않습니다. [git-commit-tree 공식 문서](https://git-scm.com/docs/git-commit-tree)
- `git update-ref <ref> <new-oid> <old-oid>`는 현재 값이 예상 OID와 같을 때만 갱신합니다. 공식 문서와 임시 저장소 실측 모두 첫 갱신만 성공하고 같은 옛 OID를 사용한 두 번째 갱신은 실패했습니다. 별도 잠금 파일이나 데이터베이스는 필요하지 않습니다. [git-update-ref 공식 문서](https://git-scm.com/docs/git-update-ref)
- 성공한 상태 커밋만 ref의 선형 부모 이력에 남았습니다. 경쟁에서 진 커밋은 현재 이력에 들어오지 않았습니다.
- Git notes가 더 단순하지 않다는 판단도 맞습니다. notes 역시 별도 ref와 커밋 이력을 가지므로 현재 상태 순서와 조건부 갱신 문제를 없애지 않습니다. [git-notes 공식 문서](https://git-scm.com/docs/git-notes)
- reflog를 정본으로 삼지 않는 판단도 맞습니다. 실측상 사용자 정의 `refs/do-math/...` ref에는 reflog가 기본 생성되지 않았습니다. 상태 커밋의 부모 이력을 정본으로 삼는 편이 안전합니다.

따라서 용어도 `매니페스트 연쇄`보다 다음처럼 쓰는 편이 낫습니다.

- **실행 ref**: 현재 실행 상태를 가리키는 포인터
- **실행 상태 커밋**: 한 시점의 불변 실행 상태
- **실행 상태 이력**: 실행 상태 커밋의 단일 부모 이력

### 수정점 1: OID는 일반적인 fencing 토큰이 아닙니다

커밋 OID는 훌륭한 **상태 세대 식별자이자 예상 상태 토큰**입니다. 그러나 보통 분산 시스템에서 말하는 fencing 토큰처럼 단조 증가하며 크기를 비교할 수는 없습니다.

OID가 stale 작업자를 막는 범위는 다음과 같습니다.

- 모든 실행 상태 갱신이 현재 ref OID와 예상 OID의 일치를 검사한다.
- 작업 종결·공용 편입 같은 하류 변경도 기준 실행 OID가 여전히 현재인지 확인한다.
- 오래된 작업자는 실행 ref 갱신 실패 뒤 결과를 현재 상태로 공개할 수 없다.

반면 작업자가 실행 ref를 거치지 않고 외부 자원이나 공용 상태를 직접 바꿀 수 있다면 OID만으로는 막을 수 없습니다.

따라서 문서에서는 다음처럼 표현하는 것이 정확합니다.

> 실행 상태 커밋 OID는 실행 상태 세대의 불투명한 식별자이자 조건부 갱신의 예상 상태 토큰이다. 모든 권위 있는 실행 변경이 현재 OID 일치를 검사할 때 stale 실행을 fencing한다.

`fencing token`이라고 단독으로 부르기보다는 이 조건을 함께 써야 합니다.

### 수정점 2: `state.json`의 OID 문자열은 작업 커밋을 보존하지 않습니다

이것이 가장 중요한 결함입니다.

임시 저장소에서 `state.json`에 다음처럼 작업 커밋 OID를 문자열로 기록했습니다.

```json
{"work_head":"<작업 커밋 OID>"}
```

실행 상태 ref가 이 JSON을 포함한 상태 커밋을 가리키고 있어도, Git은 문자열 속 OID를 객체 관계로 해석하지 않았습니다. `git rev-list`에서 작업 커밋은 실행 상태 ref의 도달 가능 객체가 아니었고, `git fsck --unreachable`도 그 작업 커밋을 도달 불가로 판정했습니다.

Git은 ref에서 실제 Git 객체 관계로 도달 가능한 객체를 보존합니다. JSON 문자열은 그 관계가 아닙니다. [Git 저장소 구조 공식 문서](https://git-scm.com/docs/gitrepository-layout)

따라서 활성 실행 동안에는 다음이 반드시 성립해야 합니다.

- 작업 브랜치 ref가 `work_head`와 체크포인트 커밋을 실제로 가리킨다.
- 실행 상태 검사기는 `state.json`의 `work_head`가 존재하고 해당 작업 브랜치의 허용된 이력에 속하는지 검사한다.
- 작업 브랜치를 삭제하기 전에 필요한 작업 커밋과 실행 상태 이력을 별도의 보존 ref 또는 종결 보관 구조로 옮긴다.

실행 ref가 삭제되면 실행 상태 커밋 이력 자체도 다른 ref가 보존하지 않는 한 GC 대상이 될 수 있습니다. 따라서 실행 ref 삭제 전 보관 절차는 별도로 결정해야 합니다.

### 수정점 3: 같은 Git ref 데이터베이스를 공유할 때만 로컬 원자성이 성립합니다

`git update-ref`는 한 Git 저장소의 ref를 안전하게 갱신하는 명령입니다. 현재 저장소의 여러 worktree는 공통 Git 디렉터리와 ref 데이터베이스를 공유하므로 이 설계를 적용할 수 있습니다.

하지만 작업자와 운영 처분 실행이 서로 다른 clone이나 컴퓨터에서 각자의 로컬 ref를 갱신한다면 이 원자성은 공유되지 않습니다. 그 경우 중앙 bare 저장소나 서버 측 조건부 push 계약이 별도로 필요합니다.

따라서 현행 설계에는 다음 전제를 명시해야 합니다.

> 한 연구 인스턴스의 작업자, 외부 감시기와 운영 처분 실행은 같은 공통 Git 객체·ref 데이터베이스를 공유한다.

나중에 분산 실행을 지원하려면 별도 전송·서버 원자성 설계로 확장해야 합니다.

- 최초 실행 상태 커밋은 부모가 없고, 이후 커밋은 직전 실행 상태 커밋 하나만 부모로 가져야 합니다.

- 여러 ref를 함께 바꾸는 `update-ref --stdin` 트랜잭션은 작성자 관점에서는 전부 적용되거나 전부 실패하지만, 공식 문서상 동시 독자는 일부 갱신만 관찰할 수 있습니다. 다중 ref 종결 절차에는 재검증 규칙이 필요합니다. [git-update-ref 공식 문서](https://git-scm.com/docs/git-update-ref)

추천은 종결 시 활성 ref를 삭제하기 전에 불변 보관 ref를 만드는 것입니다.

```text
활성 상태
refs/do-math/runs/<인스턴스>/<작업>
    → 최종 실행 상태 커밋

종결 뒤
refs/do-math/archive/runs/<인스턴스>/<작업>/<실행>
    → 최종 실행 상태 커밋

refs/do-math/archive/work/<인스턴스>/<작업>/<실행>
    → 최종 작업 브랜치 머리
```

종결 절차는 다음과 같습니다.

1. 최종 실행 상태 커밋을 만듭니다.

   - 상태는 `terminal`
   - 종결 처분과 작업 종결 기록
   - 최종 작업 머리와 체크포인트
   - 공용 편입 후보 커밋
   - 만들 보관 ref 좌표

2. 공용 머리와 활성 실행 ref가 여전히 예상 OID인지 확인합니다.

3. 하나의 Git ref 작성 트랜잭션으로 다음을 수행합니다.

   - 공용 머리를 작업당 편입 커밋으로 갱신
   - 최종 실행 상태 커밋을 가리키는 실행 이력 보관 ref 생성
   - 최종 작업 머리를 가리키는 작업 이력 보관 ref 생성
   - 활성 실행 ref 삭제

4. 트랜잭션이 하나라도 실패하면 어느 변경도 적용하지 않고 새 공용 머리와 실행 상태에서 다시 판단합니다.

5. 보관 ref가 생성된 뒤에만 작업 worktree와 활성 작업 브랜치를 정리합니다. worktree 제거는 ref 트랜잭션과 별도로 수행하되, 실패해도 보관된 객체와 공용 편입은 잃지 않습니다.

6. 감시 기록 원장은 실행·작업 보관 ref와 별도로 그대로 보존합니다.

보관 ref는 생성 뒤 이동하거나 덮어쓰지 않습니다. 실행 ID가 경로에 있으므로 같은 작업의 다른 실행과 충돌하지 않습니다. 자동 보존 기간을 두어 삭제하지 않고, 삭제·압축은 별도의 명시적 보존 정책이나 사용자 승인으로만 수행하는 것을 추천합니다.

- 작업자가 실제 연구 중 만든 결과
- 작업 종료 뒤 공용 편입자가 추가한 동기화와 충돌 해결

- 작업 B가 의존한 핵심 기록의 의미

- `분할 종결`: 즉시 공유할 독립 결과까지 현재 작업을 완료하고, 남은 범위를 새 작업 씨앗으로 옮겼습니다.

- `운영 실패 종결`: 프로세스·도구·자료 접근 등 운영 문제 때문에 계약을 완료하지 못했고, 운영 점검과 처분을 거쳐 현재 실행을 종결했습니다.

`중단`, `외부 대기`, `체크포인트 보존`과 `재시도 대기`는 종결 처분이 아니라 재개 가능한 실행 상태로 둡니다.

작업이 무엇을 알아냈는지를 별도 필드로 기록합니다. 이 어휘는 작업 종류에 따라 달라질 수 있으므로 하나의 범용 상태로 닫지 않습니다.

- 후보 경로 강화
- 후보 경로 배제
- 반례나 장애물 발견
- 불확실성 감소

이 목록은 열린 예시입니다. 실제 결과는 근거와 범위를 함께 기록합니다.

# Handoff — `do-math` 통합 설계: 연구 작업 종결 계약에서 재개

## 다음 세션의 목적

[「보편 수학 연구 스킬 do-math의 통합 설계를 확정한다」](https://github.com/MegasKomnenos/math/issues/18)의 HITL 설계를 계속한다. 작업 진전·관찰·운영 점검 계약과 Git 실행 상태의 핵심 구조는 이번 연속 작업에서 진전했다. 다음 세션의 첫 결정은 **연구 작업의 종결 처분과 수학적·연구 결과를 서로 다른 두 축으로 둘지** 정하는 것이다. 사용자는 이 제안에 답하기 전에 handoff를 요청했다.

이 handoff는 일반 `$wayfinder 6` 호출이 지도와 진행 티켓을 적재하고 지도 Notes의 정본·스킬 절차를 제공한다는 전제에서 그 일반 절차를 반복하지 않는다. 아직 `docs/do-math/통합-설계.md`를 작성하거나 후행 구현을 시작하거나 진행 티켓을 닫지 않는다.

## 이번 연속 작업의 추가 지시

- `기억/`은 별도로 읽지 않는다.
- 문서는 읽기 전에 크기를 확인하고, 크기에 맞춰 전문 또는 분할 읽기를 선택한다.
- handoff와 요약을 원자료 대신 사용하지 않는다. 실제 파일·Git·이슈 본문과 댓글을 다시 대조한다.
- 사용자는 결정마다 파일과 이슈를 고치지 말고, 남은 설계 결정을 닫은 뒤 **한 번에 정합적으로 갱신**하라고 지시했다. 다음 세션은 그 최종 갱신 시점 전까지 정본·이슈 본문을 증분 수정하지 않는다.
- 질문은 해결책부터 제시하지 말고, 먼저 어떤 상태에서 무슨 문제가 왜 발생하는지 구체적으로 설명한다. 사용자가 이해하거나 추가 질문을 마친 뒤 결과를 바꾸는 결정 하나만 묻는다.
- 사용자가 다른 세션에서 가져온 분석이나 설계를 제시하면 그 설명을 권위로 받아들이지 않는다. 원자료와 직접 실측으로 검증하고, 통과한 부분과 수정할 부분을 분리한다.

이번 세션 초반에는 위 세 원천을 결정마다 증분 갱신했다. 현재 파일과 이슈 본문에는 아래 내용까지 반영돼 있다.

- 완료 예상은 근거 있게 산정할 수 있을 때만 두는 선택 정보이며 점검·실패·중단을 직접 결정하지 않는다.
- 작업 진전 계약은 목적에 기여하는 상태 변화, 진전 신호, 작업자의 내부 생산·자기 점검 의무와 다음 관찰 조건을 함께 정한다. 진전 신호는 외부 보고량이 아니라 실제 상태 변화의 증거다.
- 작업 자기 점검은 `진전·무진전·계약 부적합`으로 닫았다. 근거 있는 첫 무진전에는 계약이 허용하고 방법이 실질적으로 다를 때 내부 적응 한 번을 허용한다.
- 다음 관찰 조건은 판본화된 관찰 조건 세대, 결정론적 `미도래·도래·평가 오류` 판정, `응답 대기·충족·위반` 관찰 의무와 연결된다. 한 조건이라도 평가할 수 없으면 다른 조건이 참이어도 평가 오류다.
- 관찰 응답 조건은 관찰 의무가 열린 뒤 첫 안전 제어 경계와 실행 환경·도구 유형에서 정한 최대 응답 시각 가운데 먼저 도래하는 한계다. 최대 응답 시각은 완료 마감이 아니다.
- 외부 감시기는 작업자 공개 상태를 읽는 결정론적 스크립트다. 운영 점검은 도구로 원자료를 읽는 별도 AI 실행이다.
- 감시는 단방향이다. 작업자는 외부 감시기의 스냅샷·평가·의무 이행 기록을 읽지 않는다. 역방향 전달은 확정된 운영 처분 실행이 적용하는 실행 제어 상태에만 허용한다.

이 내용의 상세를 handoff에서 다시 정본화하지 않는다. 실제 파일과 현행 이슈 본문을 읽는다.

현재 세 원천은 증분 편집의 결과이므로 최종 일괄 갱신 때 문서 전체의 중복과 용어 경계를 다시 감사해야 한다. 특히 `CONTEXT.md`는 구현 세부를 제외한 보편 용어집이어야 하지만 현재 diff에는 `실행 ref`, OID와 결정론적 스크립트 같은 구체 운전 문면이 섞여 있다. 최종 갱신은 보편 개념만 root 용어집에 남기고 Git·JSON·ref 구현 계약은 지도 컨텍스트와 통합 설계로 이동할지 전건을 검토한다. 새 결정을 기존 문면 뒤에 덧붙이지 말고 대체된 문장을 삭제·교체한다.

## 확정됐지만 아직 정본에 반영하지 않은 결정

사용자가 일괄 갱신을 지시한 뒤 아래 결정을 확정했다. 현재 파일에는 일부 선행 개념이나 비슷한 문장이 있어도, 아래의 완성된 경계와 물리 구조는 아직 반영되지 않았다. 최종 일괄 갱신에서 실제 현행 문면과 대조해 통합한다.

### 1. 정상 감시가 인정하는 작업자 공개 상태

- 외부 감시기의 정상 관찰 입력은 현재 Git 실행 ref가 가리키는 변경 불가능하고 스키마·참조·무결성 검사를 통과한 실행 기록뿐이다.
- 작업자는 체크포인트, 작업 자기 점검, 새 관찰 조건 세대와 필요한 증거를 작업 브랜치의 완결된 커밋으로 만든 뒤 실행 상태 기록에서 그 좌표를 공개한다.
- 미커밋 worktree, 쓰는 중인 JSON과 부분 파일은 정상 관찰 조건 평가의 입력이 아니다. 체크포인트 사이의 비공개 작업으로는 허용한다.
- 운영 점검 AI는 이상이 발동한 뒤 진단을 위해 미커밋 변경, 부분 로그와 프로세스 상태까지 읽을 수 있다. 이 자료는 정상 진전 신호나 결정론적 관찰 입력으로 승격되지 않는다.
- 승인된 운영 처분이 실행 ref를 먼저 바꿨으면 오래된 기대 OID에 결박한 작업자 공개는 실패한다. 작업자는 새 제어 상태를 읽고 다시 판단한다.

### 2. Git-native 실행 상태 이력

사용자가 다른 세션에서 가져온 단순화안을 공식 Git 문서와 임시 저장소로 적대 검증한 뒤 수정해 확정했다.

```text
refs/do-math/runs/<연구 인스턴스 ID>/<작업 ID>
    → state.json 하나를 가진 현재 실행 상태 커밋
    → 부모는 직전 실행 상태 커밋 하나
```

- 최초 실행 상태 커밋은 부모가 없고 이후 커밋은 직전 실행 상태 커밋 하나만 부모로 가진다. Git 부모 관계가 실행 상태 이력이다. 별도의 매니페스트 연결 구조와 세대 카운터를 만들지 않는다.
- 실행 ref의 끝이 현재 실행 상태다. 외부 감시기는 읽기만 하고, 작업자와 확정된 운영 처분 실행만 조건부 갱신 경로를 사용한다.
- 실행 상태 커밋 OID는 불투명한 상태 세대 식별자이자 예상 상태 토큰이다. 단조 증가하는 일반적 fencing 토큰은 아니다. 모든 권위 있는 실행 변경이 현재 OID 일치를 검사할 때 stale 실행을 차단한다.
- 갱신은 `git update-ref <실행-ref> <새 OID> <예상 이전 OID>`를 사용한다. 별도 잠금 파일, 데이터베이스나 사용자 구현 CAS 원시 연산을 두지 않는다. 경합에서 실패한 후보 커밋은 재사용하지 않고 현재 ref를 다시 읽어 새 부모로 새 상태 커밋을 만든다.
- 물리 실행 ref 이름은 현행 정본의 `refs/do-math/claims/...`가 아니라 더 넓은 소유 의미를 드러내는 `refs/do-math/runs/<인스턴스>/<작업>`으로 확정했다. 최종 일괄 갱신에서 옛 이름을 전건 교체한다.
- `state.json`은 판본화하며 적어도 스키마 판본, 연구 인스턴스·작업·실행 ID, 작업자, 기준 공용 커밋, 공개한 작업 머리·체크포인트, 작업 진전 계약, 관찰 조건 세대, 최신 자기 점검과 실행 제어를 가진다. 정확한 스키마는 아직 후속 결정 대상이다.
- ref 경로의 ID는 정규화해 `git check-ref-format`을 통과시킨다.
- 이 원자성은 한 연구 인스턴스의 주체가 같은 공통 Git 객체·ref 데이터베이스를 공유한다는 전제에서 성립한다. 현재 저장소의 worktree들은 이 전제를 충족한다. 서로 다른 clone·컴퓨터로 확장하면 중앙 저장소의 조건부 갱신 계약을 새로 설계해야 한다.

검증 근거:

- 설치 Git: `2.50.0.windows.2`.
- `refs/do-math/runs/instance-1/task-1`은 `git check-ref-format`을 통과했다.
- 같은 이전 OID에서 만든 경쟁 상태 둘 가운데 첫 `update-ref`는 성공했고 두 번째는 예상 OID 불일치로 종료 코드 128을 냈다. ref의 `git log`에는 승리한 단일 부모 이력만 남았다.
- `state.json`에 작업 커밋 OID를 문자열로 넣어도 그 작업 커밋은 실행 ref에서 도달 가능한 객체가 되지 않았고 `git fsck --unreachable`에 잡혔다.
- 사용자 정의 실행 ref에는 reflog가 기본 생성되지 않았다. reflog는 정본이 아니다.
- 임시 검증 저장소는 제거했다.
- 공식 근거: [git-update-ref](https://git-scm.com/docs/git-update-ref), [git-commit-tree](https://git-scm.com/docs/git-commit-tree), [gitrepository-layout](https://git-scm.com/docs/gitrepository-layout), [git-notes](https://git-scm.com/docs/git-notes).

중요한 귀결: JSON 안의 `work_head` OID 문자열은 실제 작업 커밋을 보존하지 않는다. 활성 작업 브랜치 ref가 작업 커밋의 도달 가능성을 별도로 보존해야 한다.

### 3. 종결 뒤 실행·작업 이력의 영구 보존

사용자는 종결 뒤에도 전체 실행 상태 이력과 전체 작업 브랜치 이력을 감사·복구용으로 보존한다고 확정했다.

```text
refs/do-math/archive/runs/<인스턴스>/<작업>/<실행>
    → 최종 실행 상태 커밋

refs/do-math/archive/work/<인스턴스>/<작업>/<실행>
    → 최종 작업 브랜치 머리
```

- 실행 상태 이력과 작업 이력은 별도 Git 객체 그래프이므로 보관 ref 둘을 둔다.
- 최종 실행 상태 커밋은 종결 처분, 최종 작업 머리·체크포인트, 작업 종결 기록과 공용 편입 후보 좌표를 보존한다.
- 공용 편입 성공 시 공용 머리 갱신, 실행 이력 보관 ref 생성, 작업 이력 보관 ref 생성과 활성 실행 ref 삭제를 예상 OID 기반 ref 작성 트랜잭션으로 묶는다.
- 보관 ref가 생긴 뒤에만 worktree와 활성 작업 브랜치를 정리한다. worktree 제거 실패는 이미 보관한 객체나 공용 편입을 무효화하지 않는다.
- 감시 기록 원장은 실행·작업 보관 ref와 별도로 보존한다.
- 보관 ref는 생성 뒤 이동·덮어쓰기하거나 자동 만료로 삭제하지 않는다. 삭제·압축은 별도 명시적 보존 정책이나 사용자 승인으로만 수행한다.

### 4. 최신 공용 머리에 대한 임시 편입 브랜치와 단일 편입 커밋

작업이 시작한 공용 커밋 뒤로 다른 작업이 먼저 편입될 수 있다. 사용자는 다음 방식으로 현재 공용 상태를 반영한다고 확정했다.

- 원 작업 브랜치는 실제 실행 이력이므로 최종 작업 머리에서 동결하고 merge·rebase로 바꾸지 않는다.
- 원 작업 머리에서 임시 편입 브랜치를 만든 뒤 현재 공용 머리를 그 브랜치에 merge한다. 공용 커밋을 하나씩 cherry-pick하지 않는다.
- 임시 편입 브랜치에서 텍스트 충돌을 해결하고 작업의 입력·가정·완료 기준, 핵심 기록 의미, 현행 스키마·무결성·Lean·인증 검사를 다시 수행한다. 깨끗한 Git merge는 의미 정합성의 증거가 아니다.
- 임시 편입 브랜치를 공용 머리에 직접 merge하지 않는다. 임시 편입 결과의 최종 트리로 현재 공용 머리 하나만 부모로 갖는 작업 전용 공용 편입 커밋 하나를 만든다. 내부 작업·체크포인트·임시 merge 커밋은 공용 머리의 조상이 되지 않는다.
- 공용 머리가 여전히 검증한 기대 OID일 때만 편입한다. 그사이 바뀌었으면 새 공용 머리를 임시 편입 브랜치에 다시 반영하고 재검증한다.
- 원 작업 브랜치와 임시 편입 이력은 감사·복구용으로 보존한다.

## 현재 미결정과 다음 질문

다음 제안은 사용자에게 아직 승인되거나 기각되지 않았다.

### 결정 주제

연구 작업의 **절차적 종결 처분**과 그 작업이 낸 **수학적·연구 결과**를 독립된 두 축으로 둘지.

### 현재 추천안

종결 처분은 실행 절차가 어떻게 끝났는지를 나타내며 다음 넷으로 닫는다.

- `완료`: 약정한 범위를 수행하고 산출물과 완료 기준을 충족했다.
- `분할 종결`: 즉시 공유할 독립 결과까지 현재 작업을 완료하고 남은 범위를 새 작업 씨앗으로 옮겼다.
- `취소`: 목적 변경, 중복 제거나 선행 결과의 대체처럼 권위 있는 결정으로 완료 전에 작업을 끝냈다.
- `운영 실패 종결`: 프로세스·도구·자료 접근과 같은 운영 문제 때문에 계약을 완료하지 못했고, 운영 점검과 처분을 거쳐 현재 실행을 종결했다.

`중단`, `외부 대기`, `체크포인트 보존`과 `재시도 대기`는 종결 처분이 아니라 재개 가능한 실행 상태로 둔다.

수학적·연구 결과는 작업이 무엇을 알아냈는지를 별도 필드와 근거·범위로 기록한다. 명제 입증·반증, 조건부·제한 범위 결과, 후보 경로 강화·배제, 반례·장애물, 불확실성 감소, 새 발견 후보, 지정 범위에서 결과 없음과 판정 불가는 열린 예시이며 범용 상태 하나로 닫지 않는다.

핵심 경계:

- 긍정적인 수학 결과가 없어도 작업 계약을 충족하면 `완료`일 수 있다.
- 유용한 부분 산출물이 있어도 운영 문제로 계약을 완료하지 못했으면 `운영 실패 종결`이다.
- `취소`는 실패 판정이 아니라 작업 필요성이 권위 있게 사라지거나 철회된 상태다.
- `분할 종결`은 중간 공용 편입이 아니다. 현재 작업을 실제로 종결하고 잔여 범위를 새 작업으로 옮긴다.
- 네 종결 처분 모두 실제 결과·한계·부분 산출과 후속 작업 씨앗을 기록하고 종결 공용 편입 한 번을 수행한다.
- 수학적 해결 여부는 작업 종결 처분이 아니라 Lean 정본 편입과 프로젝트 성공 기준이 별도로 판정한다.

다음 세션은 먼저 이 분리가 필요한 이유를 구체적인 실패·부정 결과 사례로 설명하고, 위 두 축과 네 종결 처분을 확정할지 질문 하나만 한다. 사용자 답을 대신 확정하거나 답을 받기 전에 파일·이슈를 수정하지 않는다.

## 이번 세션에서 확정·반영한 결정 경위

### 1. 예상 소요 중심 계약을 작업 진전 계약으로 교체

직전 handoff가 제안한 작업별 예상 소요는 개방형 수학 연구에서 신뢰성 있게 예측하기 어렵다는 사용자 지적을 받았다. 완료 예상은 합리적인 근거가 있을 때만 기록하는 선택 정보로 낮췄고, 점검·실패·중단을 직접 결정하지 않게 했다.

사용자는 진전 신호가 외부 감시용 표지가 아니라 작업자 자신이 명시적으로 알고 작업 방식을 그 생산에 맞추는 내부 계약이어야 한다고 확정했다. 이에 따라 작업 진전 계약은 다음을 함께 소유한다.

- 작업 목적에 기여하는 연구 상태 변화
- 그 변화를 확인할 진전 신호와 근거
- 작업자가 해당 변화를 생산하거나 시험하도록 내부 절차를 구성하는 의무
- 자기 점검과 다음 관찰 조건

heartbeat, 시간·토큰 소비, 로그·메모·파일 변경량과 보고 빈도는 그 자체로 진전 신호가 아니다. 실패한 시도도 정확한 장애물, 반례, 범위 축소나 후속 선택을 바꾸는 근거를 남기면 계약이 정한 상태 변화의 증거가 될 수 있다. 신호 수를 작업 목적 대신 최적화하거나 진전 부재를 신호로 꾸미지 않는다.

### 2. 작업 자기 점검과 내부 적응 경계

다음 관찰 조건이 도래하면 작업자는 변경 불가능한 작업 자기 점검을 만든다. 결과는 `진전`, `무진전`, `계약 부적합` 셋으로 닫았다.

- `진전`: 계약이 정한 진전 신호와 원자료가 있다. 전체 연구 진전 판정과는 다르다.
- `무진전`: 진전 신호는 없지만 시도한 방법, 확인한 사실, 실패 원인과 다음 방법을 근거 있게 기록했다.
- `계약 부적합`: 현재 신호나 관찰 조건으로 실제 작업을 올바르게 운전·판정할 수 없다.

근거 있는 첫 무진전에는 기존 계약이 허용하고 다음 방법이 실질적으로 다를 때 내부 적응 한 번을 허용한다. 다음 관찰도 무진전이거나 내부 적응을 이미 사용했거나 계약 부적합이면 운영 점검을 발동한다. 기록 부재·무결성 결함과 증거 없는 진전 주장도 운영 점검 사유다. 형식 검사는 스키마·참조·증거 존재만 판정하고 실제 진전 의미와 방법 차이는 운영 점검이 원자료로 판정한다.

### 3. 공동 관찰 조건과 외부 안전 발동 조건

사용자는 작업자가 계약상 알 수 있는 모든 관찰 계기를 외부 감시기도 같은 작업자 공개 상태에서 재현할 수 있어야 한다고 확정했다. 외부 감시기만 프로세스 소실, 외부 실행 중단과 실행 소유권 변경 같은 외부 안전 발동 조건을 추가로 사용할 수 있다. 작업자의 비공개 인상은 기록으로 외부화되기 전에는 관찰 조건이 아니다.

관찰 조건은 판본화된 일회성 세대로 묶고 하나라도 먼저 도래하면 관찰 의무를 연다. 조건 평가는 `미도래`, `도래`, `평가 오류`로 닫으며 한 조건이라도 평가할 수 없으면 다른 조건이 참이어도 평가 오류다. 도래는 즉시 운영 점검이 아니라 `실행 ID + 조건 세대 ID`로 식별하는 관찰 의무를 연다. 관찰 의무는 `응답 대기`, `충족`, `위반`으로 닫았다.

관찰 응답 조건은 의무가 열린 뒤 첫 안전 제어 경계와 실행 환경·도구 유형에서 정한 최대 응답 시각 가운데 먼저 도래하는 한계다. 작업자는 도구 호출 반환·모델 턴 종료·반복 단위 종료 같은 첫 안전 제어 경계 뒤 다음 실질적 행동 전에 자기 점검을 기록한다. 최대 응답 시각은 완료 마감이 아니며, 위반해도 자동 중단하지 않고 운영 점검을 연다. 평가 오류와 외부 안전 발동 조건은 자기 점검 응답을 기다리지 않는다.

### 4. 결정론적 외부 감시와 단방향 정보 흐름

외부 감시기는 작업자 공개 상태를 관찰 입력 스냅샷으로 고정해 닫힌 조건과 관찰 의무 이행을 평가하는 결정론적 스크립트다. 의미 판단을 하지 않고, 이상이 성립하면 실제 원자료를 도구로 조사하는 별도 운영 점검 AI를 원자적으로 하나만 연다.

사용자는 외부 감시기의 기록을 작업자가 읽을 필요가 없다고 교정했다. 이에 따라 정상 흐름은 단방향이다.

```text
작업자 공개 상태 → 외부 감시기 → 감시 기록 원장 → 운영 점검·심사
```

작업자는 감시기의 스냅샷·평가·의무 이행 기록을 읽지 않는다. 역방향 전달은 운영 점검·심사·전례 관문이나 사용자 결정을 통과한 **확정된 운영 처분**에만 허용한다. 운영 처분 실행이 필요한 실행 제어 상태만 조건부로 바꾸며 감시 기록을 작업자에게 복제하지 않는다.

정상 감시가 인정하는 작업자 공개 상태는 현재 Git 실행 ref가 가리키며 스키마·참조·무결성 검사를 통과한 변경 불가능한 실행 기록뿐이다. 미커밋 worktree와 부분 기록은 정상 관찰 입력이 아니다. 운영 점검 AI만 이상 진단을 위해 이 자료를 직접 읽을 수 있다.

### 5. Git-native 실행 상태 이력의 단순화와 검증

사용자가 다른 세션에서 가져온 Git-native 단순화안을 공식 문서와 격리된 임시 저장소로 적대 검증했다. 별도의 “매니페스트 연쇄” 대신 다음 구조를 확정했다.

```text
refs/do-math/runs/<연구 인스턴스 ID>/<작업 ID>
    → state.json 하나를 가진 현재 실행 상태 커밋
    → 부모는 직전 실행 상태 커밋 하나
```

Git 부모 관계가 실행 상태 이력이다. 최초 상태 커밋은 부모가 없고 이후 커밋은 직전 상태 커밋 하나만 부모로 가진다. 현재 커밋 OID는 불투명한 상태 세대 식별자이자 예상 상태 토큰이다. OID는 단조 증가하는 일반적인 fencing 토큰이 아니며, 모든 권위 있는 실행 변경이 현재 OID 일치를 검사할 때 stale 실행을 차단한다.

작업자와 확정된 운영 처분 실행은 `git update-ref <ref> <new> <old>` 조건부 갱신만 사용한다. 경합에서 진 후보 커밋을 재사용하지 않고 현재 ref를 다시 읽어 새 부모로 상태를 만든다. 외부 감시기는 실행 ref와 작업 브랜치를 바꾸지 않는다. 이 원자성은 같은 공통 Git 객체·ref 데이터베이스를 공유한다는 전제에서 성립하며, 서로 다른 clone·컴퓨터로 확장하면 중앙 저장소 계약을 새로 설계한다.

검증 결과:

- 설치 Git `2.50.0.windows.2`에서 실행 ref 이름이 `git check-ref-format`을 통과했다.
- 같은 이전 OID에서 만든 경쟁 상태 둘 가운데 첫 `update-ref`만 성공하고 두 번째는 예상 OID 불일치로 실패했다.
- ref의 `git log`에는 승리한 단일 부모 상태 이력만 남았다.
- `state.json`에 작업 커밋 OID를 문자열로 넣어도 그 작업 커밋은 실행 ref에서 도달 가능해지지 않았고 `git fsck --unreachable`에 잡혔다.
- 사용자 정의 실행 ref에는 reflog가 기본 생성되지 않았다. reflog는 정본이 아니다.
- 임시 검증 저장소는 제거했다.

공식 근거: [git-update-ref](https://git-scm.com/docs/git-update-ref), [git-commit-tree](https://git-scm.com/docs/git-commit-tree), [gitrepository-layout](https://git-scm.com/docs/gitrepository-layout), [git-notes](https://git-scm.com/docs/git-notes).

중요한 귀결은 JSON의 `work_head` 문자열이 작업 커밋을 보존하지 않는다는 점이다. 활성 작업 브랜치 ref가 작업 머리와 체크포인트의 도달 가능성을 별도로 보존한다.

### 6. 종결 뒤 실행·작업·임시 편입 이력 보존

사용자는 종결 뒤에도 전체 실행 상태 이력과 전체 작업 이력을 감사·복구용으로 보존한다고 확정했다. 실행 상태 이력, 원 작업 이력과 임시 편입 이력은 서로 다른 Git 객체 그래프이므로 각각 불변 보관 ref를 둔다.

```text
refs/do-math/archive/runs/<인스턴스>/<작업>/<실행>
refs/do-math/archive/work/<인스턴스>/<작업>/<실행>
refs/do-math/archive/integration/<인스턴스>/<작업>/<실행>
```

보관 ref는 생성 뒤 이동·덮어쓰기하거나 자동 만료로 삭제하지 않는다. 삭제·압축은 별도 보존 정책이나 사용자 승인을 요구한다. 보관 ref를 만든 뒤에만 worktree와 활성 작업 브랜치를 정리하며, worktree 제거 실패는 이미 보존한 객체와 공용 편입을 무효화하지 않는다. 감시 기록 원장은 별도로 보존한다.

### 7. 최신 공용 머리를 반영한 임시 편입과 단일 공용 커밋

작업이 시작한 뒤 다른 작업이 공용 머리를 먼저 바꿀 수 있다. 사용자는 공용 머리의 후속 커밋을 작업 쪽에 반영한 뒤 그 결과를 편입하는 방향을 제안했다. 원 작업 브랜치를 직접 rebase하거나 merge하면 실제 실행 이력이 바뀌거나 편입 과정과 섞이므로 다음 경계로 확정했다.

- 원 작업 브랜치는 최종 작업 머리에서 동결한다.
- 원 작업 머리에서 임시 편입 브랜치를 만들고 현재 공용 머리를 merge한다.
- 텍스트 충돌뿐 아니라 바뀐 입력·가정·완료 기준, 핵심 기록 의미와 현행 스키마·무결성·Lean·인증 기준을 다시 검사한다. 깨끗한 merge는 의미 정합성의 증거가 아니다.
- 임시 편입 브랜치를 공용 머리에 직접 merge하지 않는다. 검증한 최종 트리로 현재 공용 머리 하나만 부모로 갖는 작업 전용 공용 편입 커밋 하나를 만든다.
- 공용 머리가 그사이 바뀌면 새 머리를 임시 편입 브랜치에 다시 반영하고 재검증한다.
- 원 작업·임시 편입·실행 상태 이력은 각각 보관한다.

종결 적용은 `terminal` 실행 상태 커밋, 단일 공용 편입 커밋, 세 보관 ref 생성과 활성 실행 ref 삭제를 예상 OID에 결박한 ref 작성 트랜잭션으로 묶는다. 동시 독자는 여러 ref의 일부 조합을 잠시 읽을 수 있으므로 terminal 기록의 좌표와 공용 머리·보관 ref 전건을 다시 대조한다.

### 현재 추천안

종결 처분은 실행 절차가 어떻게 끝났는지를 나타내며 다음 넷으로 닫는다.

- `완료`: 약정한 범위를 수행하고 산출물과 완료 기준을 충족했다.
- `분할 종결`: 즉시 공유할 독립 결과까지 현재 작업을 완료하고 남은 범위를 새 작업 씨앗으로 옮겼다.
- `취소`: 목적 변경, 중복 제거나 선행 결과의 대체처럼 권위 있는 결정으로 완료 전에 작업을 끝냈다.
- `운영 실패 종결`: 프로세스·도구·자료 접근과 같은 운영 문제 때문에 계약을 완료하지 못했고, 운영 점검과 처분을 거쳐 현재 실행을 종결했다.

`중단`, `외부 대기`, `체크포인트 보존`과 `재시도 대기`는 종결 처분이 아니라 재개 가능한 실행 상태로 둔다.

수학적·연구 결과는 작업이 무엇을 알아냈는지를 별도 필드와 근거·범위로 기록한다. 명제 입증·반증, 조건부·제한 범위 결과, 후보 경로 강화·배제, 반례·장애물, 불확실성 감소, 새 발견 후보, 지정 범위에서 결과 없음과 판정 불가는 열린 예시이며 범용 상태 하나로 닫지 않는다.

핵심 경계:

- 긍정적인 수학 결과가 없어도 작업 계약을 충족하면 `완료`일 수 있다.
- 유용한 부분 산출물이 있어도 운영 문제로 계약을 완료하지 못했으면 `운영 실패 종결`이다.
- `취소`는 실패 판정이 아니라 작업 필요성이 권위 있게 사라지거나 철회된 상태다.
- `분할 종결`은 중간 공용 편입이 아니다. 현재 작업을 실제로 종결하고 잔여 범위를 새 작업으로 옮긴다.
- 네 종결 처분 모두 실제 결과·한계·부분 산출과 후속 작업 씨앗을 기록하고 종결 공용 편입 한 번을 수행한다.
- 수학적 해결 여부는 작업 종결 처분이 아니라 Lean 정본 편입과 프로젝트 성공 기준이 별도로 판정한다.

다음 세션은 먼저 이 분리가 필요한 이유를 구체적인 실패·부정 결과 사례로 설명하고, 위 두 축과 네 종결 처분을 확정할지 질문 하나만 한다. 사용자 답을 대신 확정하거나 답을 받기 전에 정본·이슈를 수정하지 않는다.
