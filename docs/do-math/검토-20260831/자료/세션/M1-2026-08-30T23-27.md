제가 재구성한 현재 작업은 다음과 같습니다.

`do-math`는 특정 문제의 풀이법이 아니라 수학 연구 전체를 운전하는 보편 체계입니다. 인증되어 Lean 정본에 편입된 수학은 인증 수학 영역 `K`, 아직 입증되지 않았지만 연구 대상으로 표현된 내용은 가시 연구 프런티어 `F`, 아직 표현조차 되지 않은 가능성은 미지 지평 `U`에 속합니다. 탐색은 `U`의 일부를 `F`에 드러내고, 집중 활용은 `F`의 후보를 입증 가능한 결과로 전진시킵니다. 인증과 Lean 검사를 모두 통과한 결과만 `F`에서 `K`로 이동합니다. 이 체계가 최적화하는 것은 작업량이나 정본의 크기가 아니라 연구 목표에 가까워지는 실제 연구 진전입니다.

연구 생산의 실행 단위는 장기 연구 프로그램이나 DAG가 아니라 연구 작업입니다. 미래 작업은 미리 만들지 않고 `F`의 작업 씨앗으로 보존합니다. 특정 공용 커밋에서 착수 가능성 판정을 통과한 씨앗만 깊이 1 실행 껍질에 나타납니다. 씨앗, 실행 껍질의 항목과 실제 연구 작업은 같은 ID를 유지합니다. 적응형 연구 포트폴리오는 준비된 작업 가운데 탐색과 집중 활용을 함께 보존하도록 실행 대상을 고릅니다.

각 작업은 공용 작업대에서 분기한 별도 브랜치와 worktree에서 자유롭게 연구합니다. 공용 작업대는 안정된 핵심 기록과 그 기록에서 다시 만들 수 있는 파생 보기로 구성됩니다. 작업은 체크포인트를 여러 번 만들 수 있지만 공용 작업대는 종결 공용 편입 한 번으로만 바꿉니다. 예상하지 못한 독립 결과를 즉시 공유해야 하면 현재 작업을 분할 종결하고 잔여 범위를 새 작업 씨앗으로 옮깁니다.

Git은 공용 판본, 배타적 점유와 실행 제어를 맡습니다. 작업 브랜치는 실제 연구 내용과 체크포인트를 보존합니다. Git 실행 ref는 단일 부모 실행 상태 커밋을 가리키며, 조건부 ref 갱신으로 오래된 실행의 쓰기를 막습니다. 작업자가 공개한 완결 상태만 결정론적 외부 감시기의 정상 입력이 됩니다. 감시 기록은 작업자에게 돌아가지 않으며, 실제 실행 변경은 심사와 전례 관문을 통과한 운영 처분만 수행합니다. 종결 뒤에는 실행 상태, 원 작업과 임시 편입 이력을 각각 불변 보관 ref로 남깁니다.

수학 내용에는 별도의 신뢰 경계가 적용됩니다. 연구 작업공간과 Lean 형식화 작업공간은 Lean 정본이 아닙니다. Lean 표현의 의도 대응을 인증하고, 정확한 신뢰 시대에서 커널 검사와 공리 감사를 통과한 내용만 Lean 정본에 들어갑니다. 형식 타당성과 외부 수학적 의도는 서로 다른 축이며, `do-math`는 어느 판정도 임의로 바꿀 수 없습니다.

추천은 **잔여 범위 보존 불변식**을 두는 것입니다. 모든 종결 기록은 착수 때 고정한 작업 계약의 각 필수 범위를 다음 중 어디에 두었는지 근거와 함께 밝혀야 합니다.

- 실제로 수행하고 확인한 범위
- 수행하지 않았지만 완료 기준상 필요하지 않다고 확인한 범위
- 권위 있는 결정으로 철회되거나 다른 대상이 대체한 범위
- 후속 작업 씨앗으로 넘긴 범위

종결 처분별 귀결은 다음과 같습니다.

- `완료`: 필수 범위를 모두 수행했거나, 수행하지 않은 부분이 완료 기준상 필요하지 않음을 입증해야 합니다.

제안의 핵심은 타당합니다. 다만 Windows Job Object가 실제로 보장하는 범위와, 프로세스 원장이 보조 기록에 그치는 지점을 Microsoft 공식 문서에 대조해 보겠습니다. 특히 중첩 Job Object, 자식의 자동 편입 예외, 종료 완료 확인, 감독기 자체가 죽는 경우를 확인하겠습니다.

## ASSISTANT

검토 결과, 제안의 핵심은 타당합니다. 이 방식이면 연구 작업마다 worktree 하나를 안전하게 재사용할 수 있습니다. 다만 종료 완료 확인, 감독기 소실, Job Object 밖에서 생성되는 프로세스와 프로세스 원장의 권한을 보완해야 합니다.

### 항목별 판정

1. **실행마다 `execution_id` 생성 — 통과**

   `execution_id`는 작업 실행의 안정된 논리 식별자로 사용합니다.

2. **같은 ID의 Job Object 생성 — 수정 권장**

   실행마다 Job Object 하나를 만드는 것은 맞습니다. 다만 Job Object의 커널 이름까지 `execution_id`로 만들 필요는 없습니다. 이름이 같으면 `CreateJobObjectW`가 기존 Job Object를 열 수 있고, 다른 종류의 커널 객체와 이름 공간도 공유합니다. 기본안은 이름 없는 Job Object를 만들고 감독기가 `execution_id → Job Object handle` 대응을 소유하는 것입니다.

   이름이 필요하면 `Local\do-math-<인스턴스 ID>-<execution_id>`처럼 만들고, `ERROR_ALREADY_EXISTS`는 명시적인 복구 절차가 아닌 한 충돌로 처리해야 합니다. [Microsoft `CreateJobObjectW`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-createjobobjectw)

3. **루트 프로세스를 일시 정지 상태로 생성 — 통과**

   `CREATE_SUSPENDED`는 새 프로세스의 주 스레드가 `ResumeThread` 전까지 실행되지 않게 합니다. 따라서 Job Object 편입 전에 일반 자식 프로세스가 생기는 경합을 막습니다. [Microsoft Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)

4. **Job Object 편입 뒤 실행 재개 — 통과**

   정확한 순서는 다음과 같습니다.

   1. Job Object를 생성한다.
   2. 빠져나가기 금지와 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`를 설정한다.
   3. 완료 포트를 연결한다.
   4. 루트 프로세스를 `CREATE_SUSPENDED`로 만든다.
   5. `AssignProcessToJobObject`를 호출한다.
   6. 편입에 실패하면 루트 프로세스를 종료하고 실행 생성을 실패로 끝낸다.
   7. 편입과 초기 기록이 성공한 뒤에만 `ResumeThread`를 호출한다.

5. **Job Object에서 빠져나가기 금지 — 통과**

   `JOB_OBJECT_LIMIT_BREAKAWAY_OK`와 `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`를 설정하지 않습니다. 실행 프로세스도 `CREATE_BREAKAWAY_FROM_JOB`을 사용할 수 없게 합니다.

   다만 실행기가 이미 다른 Job Object 안에 있으면 새 Job Object가 중첩될 수 있습니다. Windows 8 이후에는 유효한 계층이고 UI 제한이 충돌하지 않으면 중첩이 가능하지만, 조건이 맞지 않으면 편입이 실패합니다. 이때 빠져나가기 옵션으로 우회하지 않고 환경 결함으로 보고 실행을 열지 않는 것이 안전합니다. [Microsoft `AssignProcessToJobObject`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [Microsoft Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs)

6. **일반 자식의 자동 편입 — 조건부 통과**

   일반적인 `CreateProcess` 자식은 자동으로 같은 Job Object 계층에 들어갑니다. 그러나 Microsoft 문서에는 `Win32_Process.Create`로 만든 프로세스가 자동 편입되지 않는다는 예외가 명시돼 있습니다. Windows 서비스, 작업 스케줄러, WMI, WSL, 컨테이너나 별도 실행 서비스에 일을 위임하면 그 실제 작업 프로세스도 일반 자식이 아닐 수 있습니다. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

   따라서 작업 파일을 쓸 수 있는 프로세스는 다음 중 하나여야 합니다.

   - 실행 Job Object에 실제로 속한 프로세스
   - 별도 격리·종료 계약을 가진 승인된 실행 어댑터

   그 밖의 우회 실행은 금지합니다. Job Object는 프로세스 생명주기를 묶을 뿐, 다른 프로세스의 worktree 접근 자체를 막는 파일 권한 체계는 아니라는 경계도 명시해야 합니다.

7. **`TerminateJobObject`로 전체 종료 — 보완 후 통과**

   `TerminateJobObject`는 해당 Job Object와 하위 Job Object의 현재 프로세스를 모두 종료합니다. 각 프로세스가 종료를 거부하거나 미룰 수 없습니다. [Microsoft `TerminateJobObject`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject)

   다만 함수가 성공했다고 즉시 worktree를 넘기면 안 됩니다. 내부적으로 사용하는 `TerminateProcess` 계열 종료는 비동기이므로 실제 종료를 기다려야 합니다. [Microsoft `TerminateProcess`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)

   종료 장벽은 다음 전건을 모두 요구합니다.

   - `TerminateJobObject`가 성공했다.
   - 감독기가 보유한 프로세스 handle 전부가 종료 신호를 냈다.
   - 종료 코드와 종료 시각을 기록하고 해당 handle을 닫았다.
   - `QueryInformationJobObject`의 `ActiveProcesses`가 0이다.
   - Job Object의 프로세스 ID 목록이 비었다.
   - 진행 중인 작업 실행의 외부 도구 호출도 종료 또는 취소 완료됐다.

   완료 포트의 `ACTIVE_PROCESS_ZERO` 메시지는 빠른 통지에 사용할 수 있지만 유일한 증거로 사용하지 않습니다. Microsoft는 대부분의 Job Object 완료 포트 메시지 전달을 보장하지 않습니다. [Microsoft `JOBOBJECT_ASSOCIATE_COMPLETION_PORT`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_associate_completion_port)

### 감독기가 죽는 경우

`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`를 반드시 설정합니다. Job Object handle은 감독기만 소유하고 자식에게 상속하거나 복제하지 않습니다. 그러면 감독기가 비정상 종료되어 마지막 handle이 닫혀도 Job Object의 프로세스가 종료됩니다. [Microsoft `CreateJobObjectW`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-createjobobjectw)

이 보장은 다음 조건을 요구합니다.

- Job Object handle은 상속 불가다.
- 작업자에게 Job Object를 열거나 종료할 권한을 주지 않는다.
- 감독기 이외의 수호 프로세스가 handle을 계속 보유하지 않는다.

### 실행 ID의 사람용 표시

제안한 위치는 모두 유용합니다.

- 루트 래퍼 명령줄
- 상속 환경 변수
- 로그와 작업 실행 JSON
- 터미널 제목
- 감독기 화면

다만 이 값들은 찾기 편하게 하는 표지일 뿐 권한의 근거가 아닙니다. 프로세스가 환경 변수나 제목을 바꿀 수 있기 때문입니다. 권위 있는 대응은 감독기가 보유한 Job Object handle, Git 실행 ref와 작업 실행 JSON입니다.

### 프로세스 원장

`PID + 생성 시각`을 함께 쓰는 판단은 맞습니다. PID는 프로세스 객체가 해제된 뒤 재사용될 수 있고, `GetProcessTimes`가 64비트 `FILETIME` 생성 시각을 제공합니다. 살아 있는 동안에는 PID보다 열린 process handle이 더 강한 식별자입니다. [Microsoft `PROCESS_INFORMATION`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi/process_information), [Microsoft `GetProcessTimes`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)

원장은 다음처럼 보완하는 편이 좋습니다.

```json
{
  "process_instance_id": "01K...-18420-134...",
  "execution_id": "01K...",
  "pid": 18420,
  "creation_time_filetime": "134...",
  "started_at": "...",
  "image_path": "C:\\...\\lean.exe",
  "parent_process_instance_id": "01K...-9124-134... 또는 null",
  "observation_source": "root_create | job_notification | job_query",
  "exited_at": null,
  "exit_code": null
}
```

핵심 보정은 다음과 같습니다.

- `creation_time_filetime`은 정밀도가 손실되지 않도록 정수 문자열로 보존합니다. `started_at`은 사람이 읽는 파생 표현입니다.
- `image`는 모호하므로 정규화한 `image_path`로 바꿉니다.
- `parent_pid`만 저장하지 않고 가능하면 부모의 프로세스 인스턴스 ID를 저장합니다.
- 종료 뒤 `exit_code`를 기록합니다.
- 완료 포트 알림은 누락되거나 이미 재사용된 PID를 전달할 수 있으므로 `observation_source`를 남깁니다.
- 프로세스 원장은 감사와 진단 자료입니다. 원장이 모든 짧은 자식 프로세스를 빠짐없이 열거했다는 사실에 종료 권한을 의존하지 않습니다. 실제 격리와 종료의 정본은 Job Object입니다.

결론적으로, 이 방법은 채택할 가치가 있습니다. 수정된 계약은 **작업 실행마다 Job Object 하나를 만들고, 빠져나가기를 금지하며, 루트 프로세스를 편입한 뒤에만 실행하고, Job Object 전체 종료와 종료 장벽이 끝난 뒤 같은 연구 작업의 worktree를 다음 실행에 넘기는 방식**입니다.

채택했습니다. Windows 실행은 Job Object와 종료 장벽으로 격리하며, 연구 작업 하나의 worktree를 여러 작업 실행이 순차적으로 이어받습니다.

다음 결정 영역은 **Git 작업 점유와 Windows 프로세스 시작의 순서**입니다. 이를 먼저 정해야 중복 작업자와, 상태에는 없지만 실제로 실행 중인 프로세스를 막을 수 있습니다.

추천은 작업 시작을 다음 두 단계로 나누는 것입니다.

1. **점유**

   - 포트폴리오가 작업 씨앗을 선택한 뒤 착수 가능성을 최신 공용 커밋에서 다시 검사합니다.
   - 새 `execution_id`를 만듭니다.
   - 작업 계약 판본, 기준 공용 커밋과 `execution_id`를 담은 `준비 중` 실행 상태 커밋을 만듭니다.
   - 작업별 Git 실행 ref가 없을 때만 이 커밋을 가리키도록 원자적으로 생성합니다.
   - ref 생성에 실패하면 다른 실행이 먼저 점유한 것이므로 프로세스를 만들지 않습니다.

2. **실행 허가**

   - 점유에 성공한 뒤 작업 브랜치와 worktree를 만들거나 이전 실행에서 정리된 상태인지 검사합니다.
   - Job Object를 구성하고 루트 프로세스를 일시 정지 상태로 만듭니다.
   - 루트 프로세스를 Job Object에 넣고 프로세스 원장에 기록합니다.
   - 작업 계약, 작업 머리, Job Object의 논리 식별자, 루트 프로세스 인스턴스와 최초 관찰 조건 세대를 담은 `실행 허가` 상태를 예상 OID 기반으로 공개합니다.
   - 이 상태 공개가 성공한 뒤에만 루트 프로세스를 재개합니다.
   - 루트 래퍼도 첫 행동 전에 실행 ref가 자신에게 발급된 정확한 `실행 허가` OID를 가리키는지 확인합니다.

어느 준비 단계에서든 실패하면 루트 프로세스를 재개하지 않습니다. 이미 Job Object에 넣었다면 Job Object 전체를 종료하고 종료 장벽을 확인합니다. 실패 원인과 worktree 상태를 기록한 뒤 같은 점유 안에서 재시도하거나 운영 점검으로 보냅니다. 준비 실패를 숨기려고 실행 ref를 무기록으로 삭제하지 않습니다.

이 순서를 쓰면 프로세스를 먼저 시작해 중복 실행이 생기는 경우와, 권한 공개에 실패한 프로세스가 worktree를 바꾸는 경우를 모두 막을 수 있습니다.

작업 시작을 **`Git 점유 → 정지된 프로세스 준비 → 실행 허가 상태 공개 → 프로세스 재개`** 순서로 확정할까요?

## ASSISTANT

확정했습니다. 작업 실행은 Git 점유가 먼저 성립하고, 정지된 프로세스가 Job Object에 편입된 뒤 실행 허가가 공개돼야 시작합니다.

다음 결정 영역은 `state.json`의 실행 상태를 어떻게 나눌지입니다. 하나의 `status`에 작업자의 현재 활동, 실행 권한, 외부 감시 결과와 연구 작업의 종결을 함께 넣으면 서로 다른 사실이 하나의 값으로 덮입니다.

추천은 다음 세 가지를 분리하는 것입니다.

1. **실행 제어**

   현재 작업 실행에 허용된 행동을 나타내는 권위 있는 값입니다.

   - `준비`: 실행 환경만 만들 수 있고 연구 작업은 시작할 수 없다.
   - `실행 허가`: 현재 실행이 연구 작업과 상태 공개를 수행할 수 있다.
   - `일시 정지`: 점유는 유지하지만 새 연구 행동은 시작할 수 없다. 안전 제어 경계에서 체크포인트와 자기 점검만 남길 수 있다.
   - `종결 준비`: 새 연구 행동은 시작할 수 없고 종결 기록·재검증·공용 편입만 수행할 수 있다.
   - `권한 무효`: 해당 실행은 더 이상 어떤 권위 있는 상태도 공개할 수 없다.

2. **작업자 단계**

   작업자가 마지막으로 공개한 자기 활동 상태입니다.

   - `미시작`
   - `작업 중`
   - `외부 대기`
   - `일시 정지 완료`
   - `종결 준비 중`

   이 값은 마지막 보고이므로 실제 프로세스가 살아 있다는 보장이 아닙니다.

3. **외부 관찰**

   프로세스 생존, Job Object 상태, 관찰 조건 평가, 관찰 의무와 운영 점검 상태는 `state.json`의 작업자 단계를 덮어쓰지 않습니다. 외부 감시기가 감시 기록 원장에 별도로 기록합니다.

이에 따라 다음 경계도 분명해집니다.

- Git 실행 ref의 존재가 연구 작업의 현재 점유를 나타냅니다. 별도의 `점유됨` 상태를 중복 저장하지 않습니다.
- `권한 무효`는 작업 실행 하나의 권한이 끝났다는 뜻이며 연구 작업의 종결이 아닙니다.
- `완료`, `분할 종결`, `취소`, `운영 실패 종결`은 공용 종결 기록과 원자적 종결 적용이 소유합니다. 실행 상태 값으로 사용하지 않습니다.
- 외부 감시기가 프로세스 소실을 발견해도 작업자 단계를 `실패`로 바꾸지 않습니다. 감시 기록을 만들고 운영 점검을 엽니다.

1. 새 작업 씨앗은 `열림`으로 생성됩니다.

5. `열림`에서 `종결됨`으로의 전이는 원자적 종결 적용만 수행합니다.

## 1. 작업 씨앗에서 실행 껍질까지

작업 씨앗은 `F`에 있는 판본화된 핵심 기록입니다. 질문, 범위, 기대하는 연구 상태 변화, 입력, 발생 조건, 예상 산출물, 완료 기준과 생성 근거를 가집니다.

착수 명세 검토와 발생 조건 평가가 끝나도 별도의 연구 작업 객체를 만들지 않습니다. 특정 공용 커밋에서 착수 가능성 판정을 통과하면 같은 `task_id`가 깊이 1 실행 껍질에 나타납니다.

따라서 다음 값은 작업 씨앗의 고정 생명주기 상태가 아니라 공용 판본마다 다시 계산하는 결과입니다.

- 착수 가능 또는 불가능
- 실행 껍질 포함 여부
- 우선순위
- 현재 점유 가능 여부

실행 껍질은 작업의 저장소가 아니라 현재 실행할 수 있는 `task_id` 목록을 보여 주는 파생 보기입니다.

## 2. 포트폴리오 선택에서 첫 작업 실행까지

포트폴리오가 실행 껍질의 `task_id`를 선택하면 착수 가능성을 최신 공용 커밋에서 다시 검사합니다. 통과하면 새 `execution_id`를 만들고 작업별 Git 실행 ref를 원자적으로 생성합니다.

이 ref 생성이 연구 작업의 점유입니다. 이때 실행할 작업 계약의 정확한 판본과 기준 공용 커밋을 고정합니다. 점유 뒤에 계약의 질문·필수 범위·예상 산출물·완료 기준을 조용히 바꿀 수 없습니다.

첫 작업 실행은 다음 순서로 시작합니다.

1. Git 실행 ref가 `준비` 상태를 가리키며 작업을 점유한다.
2. 연구 작업이 소유하는 작업 브랜치와 worktree를 준비한다.
3. 실행별 Windows Job Object를 구성한다.
4. 루트 프로세스를 일시 정지 상태로 만들고 Job Object에 넣는다.
5. `실행 허가` 상태를 Git 실행 ref에 공개한다.
6. 루트 프로세스를 재개한다.

연구 작업은 Git 점유 시점부터 다른 포트폴리오 선택에서 제외됩니다. 실제 연구 행동은 `실행 허가` 뒤에 시작됩니다.

## 3. 연구 작업과 작업 실행의 관계

연구 작업 하나에는 작업 실행이 없거나, 하나 있거나, 시간에 따라 여러 개 있을 수 있습니다. 동시에 쓰는 실행은 하나뿐입니다.

```text
연구 작업 T
├─ 작업 계약: 전체 생명주기 동안 동일
├─ 작업 브랜치·worktree: T가 하나 소유
├─ Git 실행 ref: T의 현재 점유와 실행 제어를 소유
│
├─ 작업 실행 E1
├─ 작업 실행 E2
└─ 작업 실행 E3
```

각 작업 실행은 다음을 독립적으로 가집니다.

- `execution_id`
- 작업자와 모델
- Windows Job Object
- 프로세스 원장
- 시작·종료 시각
- 실행 제어와 작업자 단계
- 사용한 체크포인트
- 실패·중단·인수 근거

작업 실행이 실패하거나 작업자가 교체돼도 연구 작업은 자동으로 끝나지 않습니다. 같은 작업 계약을 계속 수행할 수 있으면 다음 실행이 같은 `task_id`, 작업 브랜치와 worktree를 이어받습니다.

실행 교체 순서는 다음과 같습니다.

1. 옛 실행의 Git 권한을 무효화한다.
2. 옛 실행의 Job Object 전체를 종료한다.
3. 프로세스가 모두 끝났음을 종료 장벽으로 확인한다.
4. 부분 파일과 미커밋 변경을 검사하고 필요한 내용을 보존한다.
5. worktree를 승인된 체크포인트나 재시작 좌표에 맞춘다.
6. 새 `execution_id`를 만들고 새 작업 실행을 허가한다.

옛 실행을 종료하거나 새 실행을 여는 동안에도 작업별 Git 실행 ref는 유지됩니다. 따라서 해당 연구 작업은 다른 포트폴리오 실행이 중복 점유할 수 없습니다.

## 4. 작업 실행 상태와 연구 작업 상태의 분리

작업 실행의 `state.json`은 두 사실만 소유합니다.

- 실행 제어: `준비`, `실행 허가`, `일시 정지`, `종결 준비`, `권한 무효`
- 작업자 단계: `미시작`, `작업 중`, `외부 대기`, `일시 정지 완료`, `종결 준비 중`

프로세스 생존, 관찰 조건과 운영 점검은 감시 기록 원장이 별도로 소유합니다. `완료`, `분할 종결`, `취소`, `운영 실패 종결`은 연구 작업의 종결 기록이 소유합니다.

따라서 작업 실행이 `권한 무효`가 되어도 연구 작업은 계속될 수 있습니다. 반대로 연구 작업이 종결되려면 작업 실행 상태만 바꾸는 것으로는 부족합니다.

## 5. 연구 작업의 종결

마지막 작업 실행이 계약을 끝낼 수 있다고 판단하면 `종결 준비`로 들어갑니다. 이때 다음을 고정합니다.

- 절차적 종결 처분
- 수학적·연구 결과와 근거
- 실제 수행 범위
- 수행하지 않은 범위와 그 처분
- 부분 산출물
- 후속 작업 씨앗
- 공용 작업대에 적용할 변경 묶음

최신 공용 머리를 임시 편입 브랜치에 반영하고 현행 기준으로 재검증합니다. 검증에 실패하면 연구 작업은 종결되지 않습니다. 같은 실행이나 새 실행에서 재작업할 수 있습니다.

검증이 통과하면 하나의 Git ref 트랜잭션이 다음 변경을 모두 적용합니다.

- 공용 머리 갱신
- 실행·작업·임시 편입 이력 보관
- 활성 실행 ref 삭제

이 전건이 모두 성공한 때에만 연구 작업이 종결됩니다. 작업 씨앗으로 시작한 같은 핵심 기록에 종결 처분과 결과가 연결됩니다.

## 6. 종결 뒤의 환류

종결한 작업은 사라지지 않습니다. 같은 `task_id`로 질문, 계약, 실행 이력, 결과와 종결 처분을 복원할 수 있습니다.

종결 결과가 후속 작업을 요구하면 새 `task_id`를 가진 작업 씨앗을 만듭니다.

- `분할 종결`은 잔여 필수 범위 전부를 후속 씨앗으로 옮깁니다.
- `운영 실패 종결`은 권위 있는 철회 결정이 없는 한 미완료 필수 범위를 복구·재시도 씨앗으로 옮깁니다.
- 예상하지 못한 발견은 새 `F` 객체나 작업 씨앗이 될 수 있습니다.

이 새 씨앗들은 바로 실행되지 않고 다시 착수 명세 검토와 착수 가능성 판정을 거칩니다.

## 아직 확정하지 않은 부분

앞서 제안한 `열림`, `대체됨`, `철회됨`, `종결됨`은 아직 확정하지 않았습니다. 위 연계를 기준으로 보면 이 값들은 작업 씨앗과 연구 작업에 각각 따로 붙는 두 생명주기가 아니라, **같은 `task_id`를 가진 핵심 기록의 공용 생명주기**가 됩니다.

작업 실행에는 이 생명주기를 붙이지 않습니다. 작업 실행은 별도의 `execution_id`와 실행 제어 이력을 가지며, 여러 실행이 하나의 공용 작업 생명주기 안에 들어갑니다.

이처럼 **작업 씨앗과 연구 작업을 같은 핵심 기록의 서로 다른 국면으로 보고, 작업 실행만 별도 객체로 두는 해석**이 의도와 맞는지 먼저 확인하면 됩니다.

4. `철회됨`은 권위 있는 철회 결정과 철회 범위를 기록합니다.
5. 질문·범위·산출물·완료 기준의 의미가 같은 작업이면 명시적인 복원 결정으로 `대체됨`이나 `철회됨`을 `열림`으로 되돌릴 수 있습니다. 기존 착수 명세 검토는 효력을 잃고 새 판본을 다시 검토합니다.

메인 세션은 프로세스 감독기에게 명령하기 전에 먼저 예상 OID 기반으로 제어 요청을 이 사슬에 기록합니다. 이 Git 기록이 실제 권한입니다.

### 2. named pipe 통지 통로

메인 세션은 로컬 named pipe로 프로세스 감독기를 호출합니다. 연결을 계속 유지할 필요는 없습니다. 요청마다 연결하고 응답을 받은 뒤 닫을 수 있습니다.

메시지는 실제 명령 내용을 중복하지 않고 Git 요청의 좌표만 전달합니다.

```json
{
  "schema_version": 1,
  "request_id": "01K...",
  "instance_id": "01K...",
  "controller_id": "01K...",
  "controller_state_oid": "abc123...",
  "target_run_ref": "refs/do-math/runs/...",
  "request_state_oid": "def456..."
}
```

프로세스 감독기는 메시지를 받으면 Git을 직접 읽어 다음을 검사합니다.

- 현재 인스턴스 제어 ref가 `controller_state_oid`를 가리키는가
- 현재 제어자가 `controller_id`인가
- 대상 실행 ref가 `request_state_oid`를 가리키는가
- 요청의 `execution_id`와 현재 실행이 일치하는가
- 요청 스키마와 상태 전이가 허용되는가
- 같은 `request_id`가 이미 처리됐는가

하나라도 다르면 아무 Windows 작업도 수행하지 않습니다.

## 상태 변경 절차

```text
메인 세션
  │
  │ 1. Git에 제어 요청을 먼저 기록
  ▼
Git 실행 ref
  │
  │ 2. named pipe로 요청 좌표 통지
  ▼
프로세스 감독기
  │
  │ 3. Git 원문과 현재 OID 재검사
  │ 4. Windows 작업 수행
  │ 5. 결과 상태를 예상 OID로 Git에 기록
  ▼
Git 실행 ref
  │
  │ 6. pipe 응답 또는 Git 재조회
  ▼
메인 세션
```

프로세스 감독기의 pipe 응답은 편의를 위한 빠른 응답입니다. 성공 여부의 정본은 감독기가 Git 실행 상태 사슬이나 감시 기록 원장에 남긴 결과입니다.

## 실행 시작

1. 메인 세션이 `execution_id`를 만들고 `준비` 상태로 실행 ref를 점유합니다.
2. 메인 세션이 그 상태 OID를 프로세스 감독기에 통지합니다.
3. 감독기가 Job Object와 정지된 루트 프로세스를 준비합니다.
4. 감독기가 현재 실행 ref가 여전히 같은 `준비` OID인지 확인합니다.
5. 감독기가 `실행 허가` 상태 커밋을 만들고 실행 ref를 조건부 갱신합니다.
6. 갱신이 성공한 뒤에만 루트 프로세스를 재개합니다.
7. 갱신에 실패하면 Job Object 전체를 종료하고 시작 실패를 기록합니다.

## 권한 무효화와 종료

1. 메인 세션이나 승인된 운영 처분 실행이 실행 ref를 `권한 무효` 상태로 조건부 갱신합니다.
2. 이 갱신으로 옛 작업자의 예상 OID가 즉시 낡습니다.
3. 메인 세션이 새 상태 OID를 감독기에 통지합니다.
4. 감독기가 현재 Git 상태를 확인한 뒤 `TerminateJobObject`를 호출합니다.
5. 종료 장벽을 통과하면 감독기가 프로세스 원장과 실행 결과 상태를 기록합니다.
6. 메인 세션이 worktree를 검사하고 `작업 유지` 또는 `작업 종결 연계` 절차를 계속합니다.

프로세스 감독기는 Git에 `권한 무효`가 기록되기 전에 pipe 메시지만 받고 프로세스를 종료하지 않습니다. 긴급한 외부 안전 조건으로 감독기가 먼저 종료해야 하는 예외는 감시 기록을 남기고 운영 점검을 여는 별도 경로로 둡니다.

## 읽기와 관찰

평상시 상태 확인은 메인 세션이 Git 실행 ref와 감시 기록 원장을 직접 읽습니다. 현재 OS 상태가 필요할 때만 감독기에 읽기 요청을 보냅니다.

읽기 요청은 다음 내용을 반환할 수 있습니다.

- 살아 있는 Job Object 수
- 실행별 활성 프로세스 수
- 루트 프로세스 상태
- Job Object 제한과 완료 포트 상태
- 종료 진행 여부

판단이 필요한 결과는 감독기가 내리지 않습니다. 감독기는 관찰한 원시 사실만 반환하거나 감시 기록 원장에 남깁니다.

## 중복 요청과 감독기 재시작

모든 상태 변경 요청에는 `request_id`와 정확한 요청 상태 OID가 있습니다.

- 같은 요청이 다시 오고 이미 완료됐다면 기존 결과를 반환합니다.
- 같은 `request_id`가 다른 내용과 연결되면 무결성 오류로 거부합니다.
- 요청 상태가 현재 ref가 아니면 낡은 요청으로 거부합니다.
- 감독기가 Windows 작업 뒤 결과를 기록하기 전에 죽으면 새 감독기는 Git의 미완료 요청과 실제 OS 상태를 대조합니다.
- 감독기 소실로 Job Object가 종료됐다면 작업을 자동 재실행하지 않고 그 사실을 기록해 운영 점검을 엽니다.

따라서 pipe 통지 유실은 요청 유실이 아닙니다. 메인 세션은 같은 요청을 다시 알릴 수 있고, 새 감독기는 시작할 때 Git에 남은 미완료 요청을 전수 검사합니다.

## 메인 세션 handoff

handoff는 Job Object handle을 옮기지 않습니다. 프로세스 감독기는 그대로 유지합니다.

1. 기존 메인 세션이 인스턴스 제어 ref에 handoff 준비를 기록합니다.
2. 후속 메인 세션이 정본을 읽고 인수 조건을 검사합니다.
3. 제어 ref를 예상 OID 기반으로 새 `controller_id`에 갱신합니다.
4. 프로세스 감독기는 이후 새 제어 상태 OID를 가진 요청만 받습니다.
5. 기존 메인 세션의 늦은 요청은 제어 상태 OID 불일치로 거부됩니다.

이 구조에서 프로세스 감독기는 자연어를 읽지 않고 연구 결정을 하지 않습니다. Git에 이미 승인된 구조화 요청을 기계적으로 실행할 뿐입니다.

정리하면 권위의 흐름은 다음과 같습니다.

```text
메인 세션의 결정

→ named pipe 통지
→ 감독기의 OID 재검사
→ Windows 작업
→ Git에 결과 기록
→ 메인 세션의 후속 판단
```

이 **원문 묶음과 구조화된 프로젝트 계약을 함께 불변 수입하고, 평시 재개에서는 외부 원본을 다시 읽지 않으며, 이후 변경은 별도 승인된 외부 변화로만 반영하는 방식**을 확정할까요?

## USER

가능하면 나는 프로젝트 입력이 단지 연구 인스턴스의 상태를 초기화하는 용도로만 쓰일 뿐 이후에는 연구 인스턴스의 상태를 구성하는 요소들, 즉 Lean 정본, 그에 대한 산문 번역본, 작업공간, 작업 씨앗 및 그 외 우리가 지금까지 결정했던 것들 등등이 그 상태의 정본으로서 기능하게 하고 싶어. 별도의 문서에 대해 의존성을 가지게 하기보단. 하지만 지금 상태에서 그렇게 하면 프로젝트 입력에 담긴 사용자의 핵심 목표, 이 프로젝트를 통해 이루고자 하는 그 근원이 되는 의도가 사라질 수 있다는 생각은 들어. 맥락, 정책, 지침, 설정, 기억 등이 연구 전체에 공용으로 어떻게 저장되어 보관될 수 있는지에 대한 구체화가 필요할 것 같은데. 그걸 구체화하고, 프로젝트 입력에 대한 의존성을 제거하는 것은 어떨까?

## ASSISTANT

그 방향이 더 적합합니다. 프로젝트 입력은 연구 인스턴스를 만드는 **일회성 초기화 입력**으로만 사용하고, 생성 뒤에는 연구 인스턴스 내부 상태가 모든 현행 의미를 소유하게 해야 합니다.

핵심 목표가 사라지는 문제는 프로젝트 입력을 계속 참조해서 막기보다, 사용자의 근원 의도를 연구 인스턴스 내부의 **연구 헌장**으로 수입해서 해결하는 편이 낫습니다.

## 연구 인스턴스의 공용 정본

```text
연구 인스턴스 공용 머리
├─ 연구 인스턴스 기준 기록
├─ 연구 헌장
├─ 연구 정책
├─ 연구 맥락
├─ 신뢰 시대·기초 프로필
├─ 연구 설정
├─ Lean 정본
├─ 수학 해설
├─ 가시 연구 프런티어 F
├─ 자료·근거
├─ 작업 기록
├─ 관계·공용 편입 기록
├─ 사용자 결정·전례
└─ 공용 연구 기억
```

Git 공용 커밋이 이 기록 전체의 한 판본을 고정합니다. 연구 작업은 착수할 때 기준 공용 커밋을 고정하므로, 당시의 헌장·정책·맥락·Lean 정본과 기억을 같은 판본으로 읽습니다.

### 의미별 소유자

| 의미 | 내부 정본 | 경계 |
|---|---|---|
| 연구를 왜 하는가 | 연구 헌장 | 기억이나 작업 결과가 바꿀 수 없다 |
| 무엇을 해결하려 하는가 | 연구 헌장 | 작업 씨앗이 목표를 새로 만들 수 없다 |
| 프로젝트 전체에 적용할 규칙 | 연구 정책 | 설정값이나 작업별 지시와 구별한다 |
| 현행 용어와 해석 | 연구 맥락 | 수학적 진리를 대신하지 않는다 |
| 형식 수학 내용 | Lean 정본 | 다른 산문이 덮어쓸 수 없다 |
| Lean 내용을 사람이 읽는 의미 | 수학 해설 | 정확한 Lean 객체와 판본에 결박한다 |
| 미입증 후보와 연구 방향 | `F` | Lean 정본의 사실이 아니다 |
| 문헌·실험·실패와 증거 | 자료·근거 기록 | 주장 자체의 인증을 대신하지 않는다 |
| 실행할 연구 계약 | 작업 기록 | 연구 헌장과 정책을 바꿀 수 없다 |
| 사용자 권한과 과거 결정 | 사용자 결정·전례 | AI 요약이 권한을 넓히지 못한다 |
| 재사용할 경험과 교훈 | 공용 연구 기억 | 현행 정책이나 수학 정본을 대신하지 않는다 |
| 모델·도구·자원 매개변수 | 연구 설정 | 목적·정책·신뢰 경계를 바꿀 수 없다 |

## 연구 헌장

연구 헌장은 프로젝트 입력에서 사라지면 안 되는 근원 의도를 소유합니다.

- 연구를 시작한 이유
- 핵심 연구 대상과 목표
- 원하는 최종 결과
- 성공 기준과 부분 성과의 의미
- 포함 범위와 제외 범위
- 연구 선택의 목적과 우선순위
- 사용자가 원하는 방향과 피하려는 방향
- 수학적 해결 뒤 요구하는 학술 검증
- 사용자에게 남겨 둔 결정 권한
- 장기 중단·종결의 의미

연구 헌장은 작업 지시서나 입력 원문의 요약이 아닙니다. `do-math`가 연구 전체를 운전할 때 계속 보존해야 하는 현재 목적의 정본입니다.

사용자가 목표를 바꾸면 외부 프로젝트 입력을 다시 읽는 것이 아니라, 승인된 외부 변화가 연구 헌장의 새 판본을 만듭니다. 과거 헌장은 Git 이력과 변경 기록에 남습니다.

## 연구 정책·맥락·설정의 구별

**연구 정책**은 프로젝트 전체에서 반드시 지킬 규칙입니다. 프로젝트별 검증 요구, 사용자 개입 경계의 추가 조건, 허용·금지 자원과 보존 정책이 여기에 속합니다.

**연구 맥락**은 현재 연구를 같은 의미로 읽기 위한 용어와 해석입니다. 연구 주제의 고유 개념, 목표 표현과 영역 경계를 설명합니다. Lean에 들어갈 정의나 정리는 Lean 정본이 소유하고, 연구 맥락은 그 외부 의미와 용어를 소유합니다.

**연구 설정**은 이미 정해진 목적과 정책 안에서 바꿀 수 있는 운용 값입니다. 모델 배정, 병렬 기수, 자원 한도, 도구 경로와 실행 환경 선택이 예입니다. 설정 변경이 신뢰 경계나 사용자 절충을 바꾸면 단순 설정 변경으로 처리하지 않습니다.

별도의 범용 `지침` 문서는 두지 않습니다.

- 보편 연구 방법은 `do-math` 스킬이 소유합니다.
- 연구 인스턴스 전체의 규범은 연구 정책이 소유합니다.
- 연구 작업 하나의 지시는 작업 계약이 소유합니다.
- 운영 처분의 지시는 운영 처분 기록이 소유합니다.

## Lean 정본과 수학 해설

Lean 정본은 형식 수학 내용의 정본입니다.

수학 해설은 Lean 정본의 사람이 읽는 번역과 설명을 소유하는 별도 내부 정본입니다. 각 해설은 다음 좌표에 결박합니다.

- 정확한 Lean 선언
- Lean 정본 커밋
- 신뢰 시대
- 설명하는 외부 수학적 의도
- 의도 대응 인증 상태

수학 해설은 권위 있는 번역이지만 형식 수학의 진위를 덮어쓰지 않습니다. Lean 표현과 해설이 어긋나면 형식 타당성이 유지되는 Lean 객체는 그대로 두고 해설과 의도 대응을 교정합니다.

## 공용 연구 기억

공용 연구 기억은 자유롭게 고친 하나의 장문 요약이 아닙니다. 각 기억을 출처와 적용 범위가 있는 판본화된 기록으로 둡니다.

한 기억은 다음을 가집니다.

- 무엇을 관찰하거나 배웠는가
- 어느 작업·자료·실패·결정에서 나왔는가
- 사실, 추론, 경험 법칙과 가설 중 무엇인가
- 어느 연구 대상과 조건에 적용되는가
- 현재 유효한가, 대체됐는가
- 후속 작업 선택에 어떤 영향을 줄 수 있는가

기억은 후보 선택과 작업 설계를 도울 수 있지만 다음 내용을 바꿀 수 없습니다.

- 연구 헌장
- 연구 정책
- Lean 정본의 수학적 판단
- 사용자 결정과 전례
- 작업 완료 기준

결정 경위는 결정 기록이, 실제 연구 내용은 자료·근거와 `F`가, 현행 목적은 연구 헌장이 소유합니다. 공용 연구 기억은 이 의미들을 복제하지 않고 재사용할 경험과 연결만 소유합니다.

## 프로젝트 입력의 일회성 수입

초기화는 프로젝트 입력의 문장을 하나의 `project.json`에 다시 모으지 않습니다. 각 의미를 실제 소유자에게 분해해 넣습니다.

1. 프로젝트 입력과 사용자 대화를 전부 읽습니다.
2. 결과를 바꾸는 미결정을 초기화 전에 닫습니다.
3. 입력의 각 의미 단위를 연구 헌장·정책·맥락·설정·초기 `F`·자료·근거·사용자 결정 가운데 정확한 소유자에 배정합니다.
4. 같은 의미를 여러 정본에 복제하지 않습니다.
5. 입력 전건에 대해 내부 수입 좌표를 기록한 **수입 대응표**를 만듭니다.
6. 대응되지 않은 내용, 두 곳이 동시에 소유한 내용과 의미가 달라진 내용을 검사합니다.
7. 내부 정본끼리 충돌하지 않는지 검사합니다.
8. 초기 Lean 정본, 공용 작업대와 작업 씨앗을 함께 구성합니다.
9. 전건이 검증된 최종 트리로 최초 공용 커밋과 연구 인스턴스 ref를 원자적으로 만듭니다.

수입 대응표는 초기화가 빠짐없이 이루어졌음을 검증하는 기록이지 평시 운전 정본이 아닙니다.

## 외부 입력 의존성 제거

초기화가 끝난 뒤에는 다음 조건을 모두 만족해야 합니다.

- 평시 재개가 외부 프로젝트 입력 파일을 읽지 않는다.
- 작업 씨앗이나 작업 계약이 외부 프로젝트 입력 경로를 참조하지 않는다.
- 연구 목적과 정책을 판정하는 데 수입 대응표나 입력 원문을 읽을 필요가 없다.
- 원래 입력 파일이 이동·변경·삭제돼도 같은 공용 커밋의 재개 결과가 바뀌지 않는다.
- 활성 내부 기록의 참조 폐쇄가 연구 인스턴스 내부와 고정된 `do-math` 판본 안에서 끝난다.

입력 원문은 감사와 수입 오류 교정을 위해 연구 인스턴스 안에 불변 출처 자료로 보존할 수 있습니다. 그러나 현행 의미를 얻기 위해 읽어야 하는 의존성은 아닙니다. 원문을 삭제한 시험 복제에서도 평시 재개, 실행 껍질 계산과 작업 입력 구성이 동일해야 합니다.

## 이후 변화

사용자가 새 목표·정책·맥락을 제공하면 프로젝트 입력을 다시 의존 대상으로 삼지 않습니다.

```text
새 외부 입력
→ 의미별 내부 소유자 판정
→ 기존 내부 정본과 차이·영향 계산
→ 필요한 사용자 승인
→ 내부 기록의 새 판본
→ 영향받는 씨앗·실행·검토 재평가
```

외부 입력은 이 변경을 시작하는 사건으로만 쓰입니다. 변경이 공용 편입된 뒤에는 다시 내부 상태만이 정본입니다.

따라서 프로젝트 입력은 **초기 연구 상태를 만드는 일회성 재료**이고, 그 뒤에는 연구 헌장과 다른 내부 기록들이 의미를 나누어 영구 소유합니다. 핵심 의도는 외부 입력 의존성으로 보존하는 것이 아니라 연구 헌장으로 보존합니다.

이 **연구 헌장 중심의 내부 정본 구조와 일회성 수입 뒤 외부 프로젝트 입력 의존성을 제거하는 계약**을 확정할까요?

## USER

그렇게 하자

## ASSISTANT

확정했습니다. 프로젝트 입력은 초기화 뒤 현행 정본에서 빠지고, 연구 헌장과 역할별 내부 기록이 그 의미를 영구 소유합니다.

다음 결정은 이 공용 기록들이 바뀔 때 **이미 열린 작업 씨앗과 실행 중인 연구 작업에 어떻게 반영할지**입니다. 모든 작업이 최신 상태를 실시간으로 읽게 하면 실행 중 계약이 흔들리고, 반대로 종결 때까지 아무 영향도 주지 않으면 폐기된 목표나 깨진 신뢰 경계를 계속 따를 수 있습니다.

추천은 각 공용 변경에 **영향 판정**을 붙이는 것입니다.

## 변경 기록

공용 작업대를 바꾸는 모든 편입은 다음 내용을 가진 변경 기록을 만듭니다.

- 변경 전·후 공용 커밋
- 바뀐 핵심 기록 ID와 역할
- 실제로 달라진 의미
- 변경 근거와 권한
- 직접 참조하는 작업 씨앗과 실행 중인 작업
- 관계를 따라 영향을 받을 수 있는 다른 기록
- 각 대상에 적용할 영향 처분
- 판정하지 못한 영향과 그 이유

파일 경로가 바뀌었다는 사실만으로 의미 변경을 추론하지 않습니다. 같은 ID의 문면·범위·정책·신뢰 의미가 실제로 달라졌는지 판정합니다.

## 영향 처분

| 처분 | 의미 | 실행 중 작업 |
|---|---|---|
| `영향 없음` | 현재 계약과 결과 판정이 달라지지 않는다 | 그대로 계속 |
| `다음 선택부터 적용` | 이후 포트폴리오 선택·새 실행·새 작업에만 영향을 준다 | 현재 실행은 그대로 계속 |
| `편입 전 재검증` | 현재 작업을 계속할 수 있지만 결과를 최신 상태에 다시 대조해야 한다 | 종결 공용 편입 전에 재검증 |
| `즉시 운영 점검` | 계속 작업하면 목적·신뢰·권한을 어길 수 있다 | 새 행동 전에 일시 정지하고 점검 |

이 네 값은 영향에 대한 처분입니다. 변경 자체가 옳은지에 대한 승인이나 연구 작업의 종결 처분과는 다릅니다.

## 즉시 운영 점검이 필요한 경우

고정된 문서 종류가 아니라 실제 효과로 판정합니다. 다음은 열린 예시입니다.

- 연구 목표, 성공 기준이나 필수 범위가 달라졌다.
- 현재 작업이 의존한 정의·가정·입력이 철회되거나 다른 의미로 대체됐다.
- 신뢰 시대, 기초 프로필, 공리 허용이나 Lean 정본의 유효성이 달라졌다.
- 현재 행동이 새 정책에서 금지되거나 사용자 승인을 요구하게 됐다.
- 현재 작업 계약을 유지하면 이미 바뀐 사용자 의도와 다른 연구를 수행하게 된다.

즉시 운영 점검은 작업을 자동 취소하지 않습니다. 실행을 `일시 정지`시키고 원자료를 대조한 뒤 다음 중 하나를 결정합니다.

- 같은 계약으로 계속
- 새 공용 판본에서 새 실행으로 재개
- 작업 진전 계약만 교체
- 분할 종결
- 취소
- 그 밖의 근거 있는 처분

## 작업이 공용 변경을 읽는 방식

연구 작업은 착수할 때 고정한 공용 기준 커밋을 계속 사용합니다. 공용 머리가 바뀌었다는 이유만으로 작업자가 입력을 자동 교체하지 않습니다.

- `다음 선택부터 적용`은 새 포트폴리오 계산과 이후 실행에 반영합니다.
- `편입 전 재검증`은 현재 작업의 종결 준비 때 최신 공용 머리를 반영해 검사합니다.
- `즉시 운영 점검`만 현재 실행에 제어 상태 변경을 전달합니다.
- 작업자가 새 공용 내용을 자발적으로 사용하려면 그 내용을 새로운 입력으로 채택한 사실과 계약 영향을 기록해야 합니다. 계약 의미가 바뀌면 같은 실행에서 조용히 채택하지 않습니다.

## 영향 판정 실패

결정론적 스크립트가 특정 시점의 입력을 고정합니다.

입력 묶음에는 manifest를 둡니다. manifest는 요구한 기록의 ID, 판본, 크기, 해시와 실제 포함 여부를 전건 대조합니다. 하나라도 빠졌거나 잘렸으면 AI 세션을 시작하지 않습니다.

### 하나의 선택 세션

매 선택 시점마다 새 `gpt-5.6-sol max` 세션 하나를 엽니다. 이전 세션의 숨은 대화 맥락에 의존하지 않고 고정된 종합 맥락 묶음만 제공합니다.

선택 세션은 다음 일을 모두 수행합니다.

1. 후보 전건을 읽는다.
2. 각 후보의 기대 상태 변화와 근거를 비교한다.
3. 목표 기여, 탐색·집중 활용, 다양성, 중복, 정보 가치, 대기 이력과 자원을 종합한다.
4. 현재 병렬 자원 안에서 실행할 작업 집합을 고른다.
5. 선택하지 않은 후보 전건에도 이유를 남긴다.
6. 근거가 부족한 판단과 불확실성을 밝힌다.
7. 다음 선택에서 다시 봐야 할 조건을 기록한다.

하나의 종합 점수나 고정 비율은 요구하지 않습니다. AI가 전체 상태를 보고 질적으로 비교합니다.

### 최소 기계 검사

기계 검사는 작업을 대신 고르지 않습니다. 다음 형식적 결함만 막습니다.

- 입력 manifest의 누락·절단
- 실행 껍질 밖 작업의 선택
- 이미 점유된 작업의 선택
- 자원 한도 초과
- 같은 작업의 중복 선택
- 필수 출력 누락
- 후보 일부를 검토하지 않음
- 근거 좌표가 존재하지 않음
- 입력 공용 커밋이나 실행 ref가 그사이 바뀜

검사에 실패하면 작업을 배정하지 않습니다. 검사 결과를 같은 선택 세션에 돌려주어 수정하게 할 수 있습니다. 같은 세션에서도 고치지 못하면 해당 선택 시도를 실패로 기록합니다.

## 선택 결과

선택 기록은 다음을 보존합니다.

- 정확한 모델과 노력
- 프롬프트 판본
- 입력 묶음 전체의 manifest와 해시
- 검토한 후보 전부
- 선택한 후보와 배정 자원
- 선택하지 않은 후보별 이유
- 탐색·집중 활용과 다양성 판단
- 대기 후보와 기아 위험
- 근거와 불확실성
- 기계 검사 결과
- 실제 점유 성공·실패

같은 선택을 다시 계산해 재현하려 하지 않습니다. 당시 AI가 정확히 무엇을 받고 어떤 결정을 냈는지를 재현합니다.

## 허용해야 하는 절충

이 방식을 채택하면 기존 요구의 `결정론`은 다음처럼 좁혀야 합니다.

> 같은 공용 상태에서 후보 집합·종합 맥락 묶음·형식 검사는 결정론적으로 생성된다. AI의 의미 판단과 최종 선택은 결정론적이라고 가정하지 않는다. 한 번 봉인된 선택 결과와 그 적용은 변경하지 않으며, 상태가 바뀌면 새 선택을 수행한다.

기아 방지도 우선 지침과 전건 설명 의무로 운용합니다. 실제 선택 기록에서 같은 실행 가능한 후보나 탐색 방향이 근거 없이 반복해서 밀리는 현상이 확인되면, 그때 명시적인 기아 방지 규칙을 추가합니다.

따라서 이전의 평가자와 결정론적 스케줄러 분리안은 초기 기본안으로 채택하지 않는 편이 사용자의 단순성 선호에 맞습니다.

이 **종합 맥락 묶음과 단일 `gpt-5.6-sol max` 선택 세션을 포트폴리오 알고리즘으로 사용하고, 바깥에는 입력 완전성·자원·점유를 확인하는 최소 기계 검사만 두는 초기 설계**로 확정할까요?

## USER

방금 위에 적은 것에 하나 덧붙이자면, 내가 왜 이 방법을 택하고 싶은지 이유는 다음과 같아. 고성능 AI 세션에 올바른 맥락, 재량을 올바르게 발휘할 수 있도록 도와주는 절차, 규칙과 도구들을 제공하고, 재량을 마음껏 발휘해서 결정을 내리게 하고 이후 그 결정의 결과를 실제로 다시 피드백으로 받아 새로운 결정을 내리는 과정을 반복하면 그 결정의 품질이 점점 나아질 것이고 최종적으로는 어떠한 고정된 규칙으로 제약하는 것 보다 더 우수한 결과로 이어질 수 있을 것이란 기대가 있기 때문.

## ASSISTANT

그 이유를 설계 원리로 삼는 것이 맞습니다. 목표는 고정 규칙이 AI의 판단을 대신하게 만드는 것이 아니라, 고성능 AI가 충분한 맥락과 도구를 바탕으로 넓은 재량을 행사하고 실제 결과에서 계속 배우게 만드는 것입니다.

이를 **경험 환류형 재량 포트폴리오**로 부를 수 있습니다.

> 각 선택 회차의 AI는 현재 연구 상태 전체와 과거 선택의 실제 결과를 받아 자유롭게 작업·예산·병행 구성을 결정한다. 이후 실제 결과를 다음 선택 회차에 다시 제공한다. 기계 규칙은 판단 방식을 고정하지 않고 입력 완전성, 권한, 자원 상한과 상태 무결성만 지킨다.

선택 품질이 반드시 단조롭게 좋아진다고 보장할 수는 없지만, 정확한 결과 환류가 없는 일회성 판단이나 고정 규칙보다 경험에 따라 판단을 교정할 가능성을 높이는 구조입니다.

## 후보 순서

후보를 안정된 ID 순서로 주겠다는 제안은 철회하겠습니다. 무작위 순서가 고정된 위치와 ID에 따른 편향을 줄이는 데 더 적합합니다.

- 전역 맥락과 선택 계약은 앞에 고정합니다.
- 각 후보와 그 후보에 연결된 자료를 하나의 블록으로 만듭니다.
- 후보 블록들의 순서만 매 선택 회차 새로 섞습니다.
- 운영체제의 난수 생성기로 `shuffle_seed`를 만듭니다.
- 사용한 seed와 실제 후보 순서를 선택 기록에 보존합니다.
- 후보 블록 내부의 원자료 순서는 바꾸지 않습니다.
- AI에게 후보 순서는 우선순위나 추천을 나타내지 않는다고 명시합니다.

따라서 순서는 실제로 무작위이지만 당시 입력은 정확히 재구성할 수 있습니다.

## 1M 컨텍스트

초기 설계에서는 1M 컨텍스트 모델을 전제로 전문 입력을 사용하겠습니다. 검색·요약·여러 평가 단계는 먼저 도입하지 않습니다.

다만 입력 묶음 생성기는 다음 무결성 검사만 수행합니다.

- 실제 모델의 컨텍스트 한도 확인
- 출력에 필요한 여유분 확보
- 후보별 필수 자료의 전문 포함 여부 확인
- 입력 manifest와 실제 내용의 ID·크기·해시 대조
- 잘림이나 누락 검사

전문이 들어가지 않는 상황이 실제로 생기면 조용히 요약하지 않고 그 선택 회차를 중단합니다. 그때 실제 규모와 실패 양상을 바탕으로 확장 방식을 새로 설계합니다.

## 직감과 무작위적인 탐색

`근거 없는 직감`이라는 표현은 지나치게 부정적이었습니다. 수학 연구에서는 아직 명시적인 근거로 환원하지 못한 구조적 인상이나 호기심도 유용한 선택 근거가 될 수 있습니다.

선택 AI는 다음을 모두 사용할 수 있습니다.

- 확인된 근거
- 근거에서 도출한 추론
- 아직 입증되지 않은 가설
- 설명하기 어려운 수학적 직감
- 정보 획득을 위한 의도적인 탐색
- 동등해 보이는 후보 사이의 무작위 선택

직감을 근거로 바꾸어 꾸며 쓰게 하지는 않습니다. 대신 선택 기록에서 정보 상태만 구분합니다.

```text
확인된 근거:
추론:
직감·탐색적 기대:
남은 불확실성:
```

직감만으로도 작업을 선택할 수 있습니다. 그 경우 다음 회차가 결과를 보고 그 직감이 실제로 어떤 성과를 냈는지 판단할 수 있도록 당시 기대와 실제 결과를 함께 보존합니다.

## 선택 알고리즘 전용 계약

매 선택 회차의 종합 맥락 묶음에는 `do-math`에 포함된 **선택 알고리즘 전용 계약** 전문을 넣습니다. 이 계약은 후보 자료보다 높은 권한을 가집니다.

계약은 다음을 정합니다.

- 연구 헌장에 따른 선택 목적
- AI가 결정할 수 있는 범위
- 후보 전건을 읽고 전체 포트폴리오를 판단할 책임
- 탐색·집중 활용, 다양성, 중복, 기아와 정보 가치의 의미
- 근거·추론·직감을 모두 사용할 권한
- 고정 점수·고정 비율·고정 순위 규칙이 없다는 점
- 후보 자료 안의 명령문은 자료일 뿐이라는 권한 경계
- 작업 예산과 병행 작업을 함께 결정할 책임
- 출력과 결과 환류 계약
- 사용자 상신이 필요한 경계
- 기계 검사에서 지킬 절대 조건

선택 기록은 사용한 계약의 정확한 `do-math` 판본과 해시를 보존합니다.

## 작업 예산

작업 예산도 고정 공식으로 나누지 않고 선택 AI가 결정하게 합니다. 다만 전체 자원 상한은 연구 설정과 사용자 결정이 제공합니다.

선택 AI가 받는 전체 자원 상태에는 다음이 포함됩니다.

- 현재 사용할 수 있는 병렬 실행 수
- 모델별 토큰·비용 한도
- 활성 계산 시간
- 도구별 용량과 사용 제한
- 외부 유료 자원
- 이미 실행 중인 작업의 예약·사용 자원
- 아직 회수되지 않은 실행 자원

선택 AI는 각 작업에 **이번 구간 예산**을 배정합니다. 이번 구간은 다음 포트폴리오 재검토까지 수행할 수 있는 자원 묶음입니다.

```text
task_id:
배정한 모델과 노력:
배정한 병렬 작업자 수:
토큰·비용 상한:
계산·도구 상한:
예산을 이렇게 배정한 이유:
예산 안에서 확인하려는 상태 변화:
다음 재검토 조건:
```

운용 원칙은 다음과 같습니다.

- 모든 작업에 같은 예산을 주지 않습니다.
- 선택 AI는 한 작업에 대부분의 자원을 집중할 수도 있습니다.
- 불확실한 탐색에 작은 시험 예산을 줄 수도 있습니다.
- 사용할 가치가 없다고 판단하면 병렬 슬롯을 비워 둘 수 있습니다.
- 전체 예약 예산은 사용 가능한 전체 자원을 넘을 수 없습니다.
- 작업자는 자기 예산을 다른 작업으로 넘기지 못합니다.
- 사용하지 않은 예산은 공용 자원으로 돌아갑니다.
- 예산 소진은 작업 실패나 종결이 아닙니다.
- 예산이 끝나기 전 안전 제어 경계에서 체크포인트와 자기 점검을 남기고 새 선택 회차를 엽니다.
- 새 선택 AI는 실제 결과를 보고 같은 작업에 예산을 더 주거나, 다른 작업으로 옮기거나, 운영 점검을 제안할 수 있습니다.

기계 검사는 총예산과 동시 실행 수만 검사합니다. 어떤 작업에 얼마를 줄지는 AI의 재량입니다.

## 병행 작업의 주제

선택 AI는 후보를 개별적으로 순위화한 뒤 위에서부터 채우지 않습니다. 실행할 **작업 집합 전체**를 한 번에 구성합니다.

AI는 다음을 자유롭게 선택할 수 있습니다.

- 서로 다른 분야를 병렬 탐색
- 같은 문제에 서로 다른 방법을 적용
- 같은 방법을 독립적으로 반복해 검증
- 한 후보를 집중 활용하면서 다른 후보를 탐색
- 정보 가치가 높은 작은 시험들을 여러 개 실행
- 하나의 핵심 작업에 모든 현재 자원을 집중
- 일부 슬롯을 의도적으로 비워 두기

같은 주제를 병행하는 것도 금지하지 않습니다. 중복이 낭비인지, 독립 검증인지, 다른 접근의 경쟁인지 AI가 현재 맥락에서 판단합니다.

선택 기록은 병행 집합에 대해 다음을 설명합니다.

- 왜 이 작업들을 동시에 수행하는가
- 서로 겹치는 범위가 있다면 그 중복의 목적은 무엇인가
- 서로 다른 방향이 어떤 다양성을 제공하는가
- 결과가 서로 독립적이어야 하는 작업은 무엇인가
- 한 작업의 결과를 기다려야 하는 의존성이 없는가
- 전체 예산 배분이 현재 연구 상태에 왜 적합한가
- 어떤 결과가 나오면 병행 구성을 다시 바꿀 것인가

병행 작업은 서로의 미공개 worktree를 읽지 않습니다. 독립성이 필요하면 결과가 봉인될 때까지 다른 작업의 판단에 노출하지 않습니다. 한 작업의 중간 결과를 다른 작업이 반드시 사용해야 한다면 둘을 동시에 실행하지 않습니다. 공유 가치가 있는 중간 결과까지를 먼저 별도 작업으로 종결·공용 편입한 뒤 다음 작업을 엽니다.

## 결과 환류

다음 선택 회차에는 이전 선택 당시의 판단과 실제 결과를 함께 제공합니다.

- 당시 선택한 작업과 예산
- 선택 이유와 직감
- 선택하지 않은 후보의 이유
- 기대한 연구 상태 변화
- 실제 사용 자원
- 실제 작업 자기 점검
- 종결 처분
- 새로 얻은 `K`·`F` 객체와 자료
- 실패·장애물·반례
- 기대와 달랐던 부분
- 새로 열린 경로와 닫힌 경로
- 병행 구성이 실제로 보완적이었는지 중복이었는지

다음 AI는 이전 판단을 따라야 할 의무가 없습니다. 실제 결과를 보고 앞선 판단을 유지하거나 파괴할 수 있습니다. 고정 보상 점수나 자동 학습률은 두지 않습니다.

선택 회차는 다음 사건에서 다시 엽니다.

- 연구 인스턴스 초기화
- 작업 종결 공용 편입
- 병렬 슬롯의 해제
- 작업 예산 구간 종료
- 선택에 영향을 주는 공용 변경
- 메인 세션의 명시적 재검토

## 남는 기계 규칙

기계 검사는 선택의 우수성을 판단하지 않습니다. 다음만 막습니다.

- 입력 누락·절단
- 실행 껍질 밖 작업 선택
- 중복 점유
- 전체 예산·병렬 수 초과
- 작업별 최소 실행 조건 미충족
- 후보 일부를 읽지 않은 출력
- 낡은 공용 커밋이나 실행 ref에 대한 적용
- 잘못된 출력 형식

탐색 비율, 주제 다양성, 후보별 최대 대기와 선택 순서는 기계 규칙으로 고정하지 않습니다. 선택 AI가 전체 이력과 실제 결과를 보고 판단합니다. 따라서 엄격한 선택 결정론과 형식적인 기아 방지는 포기하고, 무작위 순서·AI 재량·결과 환류를 의도적으로 채택합니다.

이 **무작위 후보 순서, 1M 전문 맥락, 직감을 포함한 넓은 AI 재량, AI가 정하는 작업별 예산과 병행 주제, 실제 결과의 반복 환류로 구성한 단일 세션 포트폴리오 방식**을 확정할까요?

## USER

나머진 좋은데, 예산은 간단하게 그냥 (모델, 상한) 단위로 구성하고, 각 작업에는 별도 예산을 할당하지 말자. 자원의 집중은 단지 어느 방향의 작업 씨앗들에 보다 많은 작업자를 할당하는지 여부로 정해지게 하고. 실행할 작업 집합 전체를 한 번에 구성하는 것은 나쁘지 않다고 생각하는데. 일정 주기마다 heartbeat을 메인 세션에 할당해서 완료된 실행을 모두 적절하게 처리하고 이후 그렇게 새로 완료를 통해 풀린 자원을 포함해 남은 작업 예산이 얼마나 되는지를 계산해 상한으로 삼아 새로운 작업 집합을 다시 파견하는 것을 그 주기마다 반복하게 하자. 나머지는 괜찮아 보여. 기계 검사는 AI 세션을 보충, 보조해주는 역할. 결정론적으로, 기계적으로 수행될 수 있고 그렇게 되어야 하는 작업들에 대해 AI 세션이 매번 새로운 도구를 임의로 발명해 사용하게 하는 대신 미리 저작된, 고품질의 도구와 그 활용법을 제공해서 AI 세션이 더욱 효과적으로 기능할 수 있게 도와주는 것이 그 존재목적.

## ASSISTANT

좋습니다. 예산을 작업별 자원량이 아니라 **모델별 동시 작업자 수**로 단순화하겠습니다. 완료된 실행이 자원을 다시 풀어 준다는 설명과도 이 해석이 맞습니다.

```json
{
  "worker_budget": [
    {
      "model": "gpt-5.6-sol",
      "effort": "max",
      "max_active_workers": 8
    }
  ]
}
```

작업마다 토큰·시간·비용 예산을 따로 배정하지 않습니다. 작업자는 작업 진전 계약과 관찰 조건에 따라 수행하며, 메인 세션은 주기적인 포트폴리오 heartbeat에서 계속 여부와 새 배정을 다시 판단합니다.

## 자원 집중의 의미

연구 작업 하나에는 동시에 작업자 하나만 붙습니다. 작업 하나가 worktree 하나를 배타적으로 사용하기 때문입니다.

특정 방향에 자원을 집중하려면 그 방향에 속한 서로 다른 작업 씨앗을 더 많이 선택합니다.

```text
방향 A
├─ 작업 씨앗 A1 → 작업자 1
├─ 작업 씨앗 A2 → 작업자 2
└─ 작업 씨앗 A3 → 작업자 3

방향 B
└─ 작업 씨앗 B1 → 작업자 4
```

같은 질문에 여러 작업자를 붙일 가치가 있다면 하나의 작업을 공동 수행하게 하지 않습니다. 독립 접근, 교차 검증이나 의도적 중복이라는 서로 다른 계약을 가진 작업 씨앗을 만듭니다. 각 작업은 자기 worktree와 결과를 가집니다.

선택 AI는 다음을 자유롭게 결정합니다.

- 어느 방향에 몇 개의 작업 씨앗을 배정할지
- 같은 주제의 독립 작업을 여러 개 실행할지
- 여러 분야로 넓게 분산할지
- 현재 상한을 전부 사용할지 일부를 비워 둘지
- 어떤 모델을 요구하는 작업을 먼저 실행할지

기계 검사는 모델별 활성·준비 중 작업자 수가 상한을 넘지 않는지만 확인합니다.

`준비` 상태로 Git 실행 ref를 점유한 실행부터 자원을 사용한 것으로 셉니다. Job Object 종료 장벽이 끝난 실행은 자원을 반환합니다. 실행 ref는 남아 있지만 프로세스가 없는 일시 정지·인계 대기 작업은 모델 예산을 사용하지 않습니다.

## 메인 세션의 포트폴리오 heartbeat

heartbeat는 작업자의 진전 신호나 생존 보고가 아닙니다. **메인 세션에 포트폴리오를 다시 운전할 기회를 주는 정기 실행**입니다.

각 heartbeat는 앞선 heartbeat와 겹치지 않고 하나씩 수행합니다.

```text
heartbeat 시작
→ 완료·종료된 실행 수집
→ 각 실행의 결과와 worktree 처리
→ 가능한 공용 편입 적용
→ 실행 중·대기 중 상태 재조정
→ 모델별 남은 작업자 수 계산
→ 종합 맥락 묶음 구성
→ 메인 AI가 새 작업 집합 선택
→ 기계 검사
→ Git 점유와 작업자 파견
→ heartbeat 기록
```

### 1. 완료된 실행 처리

미처리 실행 전부를 먼저 다룹니다.

- Job Object 종료 장벽 확인
- 실행 종료 원인과 작업 효과 확인
- `작업 유지`이면 실행 이력 보관과 재개 좌표 확정
- `작업 종결 연계`이면 종결 기록과 최신 공용 머리 재검증
- 공용 편입이 가능한 결과는 한 작업씩 적용
- 충돌이나 판정 불가가 있는 결과는 운영 점검이나 재작업 상태로 이동
- worktree의 미커밋·부분 자료 검사
- 프로세스가 모두 끝난 모델 자원 반환

모든 문제를 그 heartbeat 안에 최종 해결해야 한다는 뜻은 아닙니다. 각 완료 실행을 다음 행동이 분명한 상태로 옮기면 처리된 것입니다.

### 2. 남은 작업자 수 계산

결정론적 도구가 모델별 현재 사용량을 계산합니다.

```text
남은 작업자 수
= max_active_workers
- 준비 중인 실행
- 실행 허가를 받은 실행
- 살아 있는 일시 정지 실행
```

종료 장벽이 끝난 실행과 프로세스 없는 재개 대기 작업은 빼지 않습니다.

### 3. 새 작업 집합 선택

메인 세션 자체가 포트폴리오 선택 AI 역할을 맡습니다. 별도의 평가자나 결정론적 스케줄러를 두지 않습니다.

메인 세션은 다음을 포함한 종합 맥락 묶음을 받습니다.

- `do-math` 선택 알고리즘 전용 계약
- 연구 헌장·정책·맥락·설정
- 최신 `K·F`
- 무작위 순서의 실행 가능한 작업 씨앗 전부
- 후보별 전체 자료와 기록
- 실행 중·재개 대기 작업
- 방금 처리한 실행 결과
- 과거 선택과 실제 결과
- 모델별 상한·사용량·남은 작업자 수
- 후보 사이의 관계와 의도적 중복
- 탐색·집중 활용과 이전 자원 집중의 경위

메인 세션은 남은 모델별 작업자 수를 넘지 않는 새 작업 집합을 고릅니다. 각 작업에 별도 예산은 주지 않습니다.

출력은 다음 정도면 충분합니다.

```text
선택한 task_id:
배정할 모델과 노력:
이 작업을 지금 고른 이유:
다른 선택 작업과의 관계:
이 병행 구성이 현재 상태에 적합한 이유:
직감·탐색적 기대와 불확실성:
```

선택하지 않은 후보도 전건을 검토했다는 사실과 중요한 보류 이유를 남깁니다.

### 4. heartbeat 밖의 즉시 사건

정기 heartbeat를 기다리면 안 되는 외부 안전 사건은 기존 계약대로 즉시 처리합니다.

- 프로세스 감독기 소실
- Job Object 이상
- 관찰 조건 평가 오류
- 관찰 의무 위반
- 메인 세션의 예기치 않은 소실
- 신뢰 경계를 깨는 공용 변경

작업의 정상 완료는 다음 heartbeat까지 기다릴 수 있습니다. 필요하면 감독기가 heartbeat를 앞당겨 달라는 사건을 기록할 수 있지만, 여러 heartbeat를 동시에 열지는 않습니다.

정확한 heartbeat 주기는 이후 연구 설정으로 정합니다.

## 기계 도구의 역할

기계 검사는 AI의 선택을 제한하는 별도 판단자가 아닙니다. 목적은 AI가 반복해서 수행할 필요가 없는 결정론적 작업을 고품질 도구로 제공하는 것입니다.

`do-math`는 최소한 다음 도구를 미리 구현하고 사용법을 선택 계약에 포함합니다.

- 공용 상태와 실행 ref 일관성 검사
- 완료 실행 수집
- Job Object·프로세스 원장 대조
- 종료 장벽 검사
- worktree와 Git 작업 상태 검사
- 모델별 사용량·남은 작업자 수 계산
- 실행 껍질 생성
- 후보 종합 맥락 묶음 생성
- 후보 블록 무작위 배열과 seed 기록
- 컨텍스트 크기·누락·해시 검사
- AI 선택 결과의 스키마 검사
- 모델별 상한과 중복 점유 검사
- 예상 OID 기반 작업 점유·파견
- 실행·작업·편입 이력 보관
- 사람이 읽는 상태 보고 생성

도구는 수학적 유망성, 직감, 탐색 가치나 좋은 병행 구성을 판단하지 않습니다. 그 판단에 필요한 정확한 상태를 만들고, AI의 결정을 안전하게 적용합니다.

`do-math` 운용에 반복해서 필요한 결정론적 작업에 이미 도구가 있으면 메인 세션이 임의의 일회성 스크립트를 다시 만들지 않습니다. 필요한 도구가 없거나 결함이 있으면 숨은 우회 구현을 만들지 않고 도구 결함으로 기록해 고칩니다.

다만 개별 수학 연구가 새로운 계산 프로그램이나 실험 도구를 만들어야 하는 경우는 다릅니다. 그것은 연구 산출물이므로 작업자가 자기 작업 계약 안에서 만들 수 있습니다.

## 수정된 포트폴리오 원리

최종적으로 선택 구조는 다음과 같습니다.

- 메인 세션이 주기적 heartbeat마다 전체 상태를 다시 본다.
- 완료 결과를 먼저 공용 상태와 재개 상태에 반영한다.
- 모델별 동시 작업자 상한에서 현재 사용량을 빼 남은 수를 계산한다.
- 무작위 순서의 전체 후보와 과거 결과를 바탕으로 새 작업 집합을 자유롭게 고른다.
- 자원 집중은 특정 방향의 서로 다른 작업 씨앗에 더 많은 작업자를 배정하는 방식으로 표현한다.
- 기계 도구는 맥락 구성, 상태 계산, 검사와 안전한 적용을 맡는다.
- 실제 결과는 다음 heartbeat의 판단 자료가 된다.

이때 `(모델, 상한)`의 `상한`은 **해당 모델·노력 조합으로 동시에 실행할 수 있는 최대 작업자 수**로 해석합니다.

이 모델별 동시 작업자 상한과 주기적 메인 heartbeat 중심의 포트폴리오 운전을 확정할까요?

## USER

아니, 포트폴리오 선택 AI는 별도 세션이어야 해. 안 그러면 메인 세션 컨텍스트가 너무 빠르게 차오를거야. 별도 세션을 메인 세션이 호출한 다음 정해진 규격에 따라 산출물이 생산되면 그걸 읽고 처리하게 하자. 당연히 작성하는 세션과 받는 세션 모두 기계적으로 검사 돌려야 할 것이고. 나머진 확정.

## ASSISTANT

수정했습니다. 포트폴리오 선택은 메인 세션이 직접 하지 않고, heartbeat마다 새로 여는 **별도 선택 세션**이 맡습니다. 모델별 동시 작업자 상한, 작업별 예산 없음, 주기적 heartbeat, 무작위 후보 순서, 넓은 재량과 결과 환류, 기계 도구의 보조 역할은 모두 확정합니다.

## heartbeat의 수정된 흐름

```text
메인 세션 heartbeat
→ 완료 실행 처리
→ 공용 상태와 모델별 남은 작업자 수 확정
→ 기계 도구로 종합 맥락 묶음 생성
→ 별도 포트폴리오 선택 세션 파견
→ 선택 세션이 산출물 작성·자체 검사·봉인
→ 메인 세션이 원본 산출물 직접 읽기
→ 메인 세션이 같은 기계 검사 독립 실행
→ 현재 상태 재확인
→ 작업 점유와 파견
```

메인 세션은 전체 후보 자료를 자기 컨텍스트에 적재하지 않습니다. 선택 세션의 결론·근거·불확실성과 기계 검사 결과만 읽으므로 장기 총괄 컨텍스트를 보존할 수 있습니다.

## 별도 선택 세션

선택 세션은 새 `gpt-5.6-sol max` 세션 하나입니다. 내부에서 다른 AI 세션을 만들지 않습니다. 제공된 도구는 사용할 수 있습니다.

쓰기 권한은 자기 선택 산출물로 한정합니다. 다음 대상은 수정하지 못합니다.

- 공용 머리
- 작업 씨앗
- Git 실행 ref
- 작업 브랜치와 worktree
- controller 상태

`selection.json`은 최소한 다음 내용을 가집니다.


선택 세션은 작성 뒤 출력 검사 도구를 실행합니다. 결함이 있으면 같은 세션 안에서 고치고 다시 검사합니다. 통과한 전문과 검사 결과를 봉인한 뒤 메인 세션에는 정확한 산출물 좌표와 해시만 반환합니다. 반환 요약은 정본이 아닙니다.

## 제안의 경계

편입 제안은 **서로 함께 검토해야 의미가 완성되는 최소한의 의존 폐쇄 변경 묶음**입니다.

- 정의 하나와 그 정의를 사용하는 핵심 정리가 함께 있어야 의도를 판정할 수 있으면 같은 제안에 둡니다.
- 여러 선언을 서로 독립적으로 승인·수정·재시도할 수 있으면 제안을 나눕니다.
- 같은 빌드를 사용한다는 이유만으로 무관한 선언을 한 제안에 섞지 않습니다.
- 파일 수나 코드 길이로 제안 경계를 정하지 않습니다.
- 제안 안의 선언이 외부 Lean 후보에 의존하면 그 의존도 같은 제안에 포함하거나 이미 Lean 정본에 있어야 합니다.

검토가 시작된 제안은 수정하지 않습니다. 결함을 고치면 새 제안 판본을 만들고 이전 제안과 대체 관계를 기록합니다. 모든 검토와 Lean 검사는 같은 후보 커밋과 같은 제안 해시를 사용합니다.

- 의존 결과와 공리 사용
- 후보 변경이 기존 Lean 정본과 수학 해설에 미치는 영향

## 판정

각 인증 의무의 판정은 다음 세 값으로 닫습니다.

- `승인`: 해당 의무가 충족됐음을 확인했다.
- `기각`: 구체적인 결함이나 불일치를 확인했다.
- `판정 불가`: 필요한 사실·자료·논증이 없어 승인이나 기각을 확인할 수 없다.

제안 전체는 두 세션이 모든 인증 의무를 `승인`했을 때만 인증됩니다.

- 한 세션이라도 `기각`하면 해당 제안 판본은 편입하지 않습니다.
- `기각`은 없지만 하나라도 `판정 불가`이면 자료를 보충하거나 제안을 명확히 해야 합니다.
- 다수결이나 평균 점수는 사용하지 않습니다.
- 한 역할의 승인이 다른 역할의 기각·판정 불가를 덮지 못합니다.
- 검토자는 자신이 작성하거나 수정한 제안을 검토하지 않습니다.
- 두 검토 세션은 서로의 판단에 노출되지 않습니다.

결함을 고치거나 설명을 보충하면 기존 제안을 수정하지 않고 새 제안 판본을 만듭니다. 새 판본은 새 인증 검토자와 심사자가 처음부터 전건을 다시 검토합니다. 이전 승인을 새 판본에 옮기지 않습니다.

검토·심사 루프는 간단히 다음 조건까지 계속합니다.

1. 검토자가 각 심사자의 피드백에 답하거나 해당 이의를 철회한다.
2. 답변·수정 이의·새 이의를 같은 심사자들이 다시 심사한다.
3. 각 이의는 심사자 전원의 승인으로 `승인됨`이 되거나 검토자가 `철회됨`으로 만든다.
4. 처리 중인 이의가 없어질 때까지 반복한다.
5. 승인된 이의가 없으면 제안을 승인한다.
6. 승인된 이의가 있으면 작성자가 이를 반영한 새 제안 판본을 만들고 새 검토단·심사단으로 다시 시작한다.

기계 검사는 각 피드백에 답변이나 철회가 있는지, 이의 판본과 심사 판본이 맞는지만 확인합니다. 대화가 충분히 진전했는지를 별도로 판정하지 않습니다.

세션이나 도구가 실제로 끊기면 검토 루프의 특별 상태를 만들지 않고 일반 작업 실행의 체크포인트와 재개 절차를 사용합니다.

이제 인증 루프 뒤의 최종 Lean 관문을 정하면 됩니다. 추천 순서는 다음과 같습니다.

```text
제안 작성
→ 예비 Lean 빌드·스키마·금지 공리 검사
→ 검토자·심사자 루프
→ 승인된 정확한 제안 판본의 새 환경 빌드
→ Lean 커널 검사와 전이적 공리 감사
→ 프로젝트별 추가 감사
→ Lean 정본 원자적 편입
```

예비 검사는 검토할 수조차 없는 제안을 미리 걸러낼 뿐 인증을 대신하지 않습니다. 검토 루프가 승인한 뒤에는 같은 후보 커밋을 깨끗한 환경에서 다시 검사합니다. 검토 뒤 파일이나 환경이 달라졌으면 승인을 사용할 수 없습니다.
