
- 범위 차분 감사나 학술 검증이 직접 참조할 선언

해설은 다음을 포함합니다.

- 자연어 수학 문면
- 정의와 기호
- 가정과 적용 범위
- 결론
- 증명의 구조
- Lean 선언과 항목별 대응
- 무엇을 입증하지 않았는가
- 관련 출처와 인증 상태

## 내부 보조 선언

독립적인 외부 수학 주장으로 사용하지 않는 내부 보조 선언은 하나의 증명 묶음 해설에서 함께 설명할 수 있습니다.

묶음 해설은 다음을 가져야 합니다.

- 포함하는 선언의 닫힌 목록
- 각 선언이 증명에서 맡는 역할
- 외부 의미가 있는지 여부
- 상위 정리와의 관계
- 개별 의도 대응 기록의 좌표

여러 선언을 한 묶음에 넣었다는 이유로 각 선언의 의도 대응을 생략하지 않습니다. 다만 같은 설명을 선언마다 복제하지 않습니다.

## Mathlib 선언

고정 Mathlib 판본 전체의 내부 보조 선언에는 별도 수학 해설을 만들지 않습니다.

연구가 외부에 직접 주장하거나 우리 정의와의 의미 대응에 사용하는 Mathlib 정의·정리는 최초 사용 시 독립적인 의도 대응과 필요한 해설을 추가합니다. 단순히 Lean 증명 내부에서 사용하는 Mathlib 보조정리는 형식 의존과 공리 감사만 기록합니다.

## 수정된 편입 단위

정본 편입 제안은 다음 셋을 하나의 불변 묶음으로 고정합니다.

1. **수학 해설 후보**

   사람이 읽는 정의, 명제, 증명, 가정, 적용 범위와 결론입니다. 이것이 연구의 주 산출물입니다.

2. **Lean 형식화 후보**

   수학 해설 후보에 대응하는 정확한 Lean 정의, 정리와 증명 항입니다.

3. **해설–형식 동일성 명세**

   수학 해설의 각 의미가 어느 Lean 표현과 같은지를 연결합니다.

```text
수학 해설의 정의 D
↔ Lean 선언 D

수학 해설의 명제 P
↔ Lean 정리의 타입 P

수학 해설의 증명 단계와 의존 결과
↔ Lean 보조정리·증명 항·형식 의존

수학 해설의 가정·범위
↔ Lean 매개변수·전제·양화
```

## 판정 절차

```text
수학 해설 후보 + Lean 형식화 후보 작성
→ Lean 빌드·커널 검사·공리 감사
   ├─ 실패 → 형식화 작업공간에서 수정
   └─ 통과
        ↓
해설–형식 동일성 검토
        ↓
검토자가 동일성에 관한 이의를 생성
        ↓
심사자들이 각 이의를 승인·기각
        ↓
동일성 인증
        ↓
Lean 형식 표현을 Lean 정본에 편입
+ 인증된 자연어 산문을 수학 해설에 보존
```

Lean 커널 검사를 통과하지 못한 후보는 동일성 검토에 보낼 필요가 없습니다. 형식 표현 자체가 아직 성립하지 않기 때문입니다.

동일성 검토 뒤에도 같은 Lean 후보가 유지되는지 확인하기 위해 최종 빌드와 해시 대조는 다시 수행합니다. 이는 Lean 증명을 AI가 재심사하는 일이 아니라 검토한 판본과 편입할 판본이 같다는 기계 검사입니다.

## 검토자와 심사자의 대상

검토자는 다음과 같은 이의를 찾습니다.

- 자연어 정의가 Lean 정의보다 넓거나 좁다.
- 자연어 명제의 양화나 가정이 Lean 타입과 다르다.
- 자연어에서는 무조건 결과라고 썼지만 Lean에서는 조건부 정리다.
- 자연어에서는 일반 모형을 주장하지만 Lean에서는 제한 모형만 다룬다.
- 자연어 증명의 한 단계가 Lean 증명에서 다른 가정에 의존한다.
- Lean에서는 입증하지 않은 설명을 자연어가 수학적 사실처럼 주장한다.
- Lean에 존재하는 중요한 범위 제한을 수학 해설이 누락했다.
- 수학 해설과 Lean 형식 표현이 서로 다른 정의를 같은 이름으로 사용한다.

검토자는 커널이 이미 승인한 증명 항의 형식적 유효성을 다시 판정하지 않습니다. 심사자도 Lean 증명 전체를 심사하지 않고, 검토자가 제기한 **동일성 이의**가 타당한지만 판정합니다.

따라서 기존 검토 관점도 다음처럼 읽습니다.

- **논증 재구성**: 자연어 논증이 Lean에서 실제로 형식화된 논증과 같은가
- **적대 검토**: 자연어가 Lean보다 더 강하거나 넓은 주장을 하는 지점이 있는가
- **의미 대응**: 정의·명제·증명의 의미가 항목별로 같은가
- **원문 충실성**: 문헌을 전사했다면 수학 해설이 원문의 실제 주장을 보존하는가
- **분야 전문성**: 자연어와 형식 표현의 대응을 해당 분야의 정확한 의미로 읽었는가

기존의 **형식화·공리 감사 검토자**는 별도 AI 검토 관점에서 제거합니다. 형식 빌드와 공리 의존은 미리 작성한 기계 도구가 검사합니다. 다만 공리 감사 결과를 수학 해설이 정확히 설명하는지는 동일성 검토 대상입니다.

## 편입 뒤의 지위

두 결과를 서로 다른 정본으로 보존합니다.

- Lean 정본은 정확한 형식 수학 내용을 소유합니다.
- 수학 해설은 그 Lean 내용과 동일하다고 인증된 사람이 읽는 수학을 소유합니다.
- 인증 기록은 둘의 정확한 판본과 동일성 관계를 소유합니다.

연구가 외부에 수학 결과로 주장하는 내용은 인증된 수학 해설입니다. 그 주장의 형식 근거는 연결된 Lean 정본입니다.

Lean 후보가 커널을 통과했지만 동일성 인증을 받지 못하면 Lean 형식화 작업공간에 남습니다. 연구 소유 결과로 Lean 정본에 편입하지 않습니다.

나중에 동일성 결함을 발견하면 다음처럼 처리합니다.

- Lean 표현의 형식 타당성은 그대로 유지될 수 있습니다.
- 잘못된 수학 해설과 동일성 인증을 철회합니다.
- Lean 객체는 자기 형식 문면의 의미로 남습니다.
- 올바른 자연어 해설을 새로 작성해 다시 동일성 인증을 받을 수 있습니다.
- 잘못된 해설에 의존한 목표 연결과 학술 주장은 재평가합니다.

## 다음으로 닫을 동일성의 해상도

수학 해설과 Lean 코드를 줄마다 대응시키면 사람이 읽는 해설이 형식 코드의 번역문으로 변해 버립니다. 반대로 결론만 대응시키면 자연어 증명에 숨은 범위 차이를 놓칠 수 있습니다.

다음 수준을 추천합니다.

- 정의, 명제, 가정, 양화, 적용 범위와 결론은 전부 명시적으로 대응합니다.
- 자연어 증명의 수학적으로 의미 있는 각 주장과 의존 결과를 Lean 선언이나 증명 의무에 대응합니다.
- 전술 호출, 커널 축약과 통상적인 형식 세부를 줄마다 설명하지 않습니다.
- 자연어에서 생략한 형식 세부는 새로운 가정·주장·범위 차이를 숨기지 않아야 합니다.
- 설명을 위해 넣은 비유·동기·역사는 수학적 주장과 구별하며 동일성 인증 대상에서 제외합니다.

## 수학 해설 후보

수학 해설은 자연스러운 Markdown 산문으로 작성합니다. 각 수학적 구성물에는 안정된 `math_item_id`를 붙입니다.

- 정의
- 가정
- 명제·정리·보조정리
- 반증 결과
- 중요한 증명 단계
- 범위 제한
- 조건부 결과
- 정본 연결 관계

ID는 문단 번호나 파일 줄 번호가 아닙니다. 제목·배치가 바뀌어도 같은 수학적 의미이면 같은 ID를 유지합니다. 의미가 바뀌면 새 ID를 만듭니다.

설명 목적의 동기, 역사, 비유와 문서 길잡이는 수학적 주장과 구별합니다. 다만 예시나 직관 설명이 실제 수학적 사실을 주장하면 대응 대상에 포함합니다.

## 동일성 대응표

별도 JSON이 수학 해설과 Lean 후보의 대응을 기계 판독 가능하게 기록합니다.

각 항목은 다음을 가집니다.

```json
{
  "math_item_id": "MATH-...",
  "kind": "definition | assumption | statement | proof_step | scope",
  "prose_anchor": "해설 안의 안정된 좌표",
  "lean_declarations": ["Namespace.name"],
  "relation": "same_definition | same_statement | realizes_proof_step | states_scope",
  "assumptions": ["MATH-..."],
  "depends_on": ["MATH-..."],
  "notes": "대응을 읽는 데 필요한 최소 설명"
}
```

대응 관계의 이름은 정확한 의미를 구별하는 닫힌 어휘로 정합니다. 정의와 명제의 동일성, 증명 단계의 형식적 실현과 범위 설명을 같은 `related_to` 관계로 뭉치지 않습니다.

## 증명 단계의 대응

수학 해설에서 후속 추론이 의존하는 중요한 중간 주장은 Lean에서도 이름 있는 보조정리나 명시적인 형식 의무로 드러냅니다.

다음은 허용하지 않습니다.

```text
자연어의 핵심 증명 단계
→ Lean 파일 전체
```

다음처럼 정확한 좌표가 필요합니다.

```text
자연어의 핵심 증명 단계 MATH-L17
→ Lean 보조정리 `Project.lemma17`
```

반면 단순한 식 정리, 타입 변환, 커널 축약과 이미 명시한 보조정리의 직접 적용은 상위 증명 항에 포함할 수 있습니다. 자연어 해설이 독립된 수학 주장으로 제시하지 않는 형식 세부마다 별도 보조정리를 만들 필요는 없습니다.

## 기계 검사

동일성 검토 전에 도구가 다음을 검사합니다.

- 모든 `math_item_id`가 유일하다.
- 모든 수학적 해설 항목이 대응표에 있다.
- 대응표의 모든 자연어 좌표가 실제로 존재한다.
- 참조한 Lean 선언이 정확한 후보 환경에 존재한다.
- 선언의 종류와 대응 관계가 형식상 양립한다.
- 중요한 증명 단계에 정확한 Lean 좌표가 있다.
- 대응표에만 있고 해설이나 Lean에 없는 고아 항목이 없다.
- 제안·해설·대응표·Lean 후보의 해시가 서로 결박돼 있다.

도구는 두 표현의 의미가 실제로 같은지는 판정하지 않습니다. 그 판정은 검토자와 심사자 사슬이 수행합니다.

- 연결된 Lean 선언의 타입
- 사용한 정의와 가정
- 전이적 Lean 의존

## 두 판정

### Lean 정본 편입

다음 조건만 판정합니다.

- Lean 형식 표현이 커널을 통과했다.
- 전이적 공리 의존이 허용 목록 안에 있다.
- 수학 해설과 Lean 형식 표현의 동일성이 인증됐다.
- 편입할 판본이 인증받은 판본과 같다.
- 신뢰 시대가 현재 유효하다.

이 조건을 통과하면 정확히 입증한 내용으로 Lean 정본에 들어갈 수 있습니다.

### 연구 목표 해결

편입 후보가 연구 헌장의 핵심 목표를 실제로 해결하는지 별도로 판정합니다.

- 같은 정의와 대상인가
- 같은 양화와 가정인가
- 같은 계산 모형과 자원 측정인가
- 후보 결과가 목표와 동일한가
- 동일하지 않다면 등가나 충분성이 입증됐는가
- 조건부·제한 범위 결과인가
- 아직 해소하지 못한 차이가 있는가

목표 해결 판정은 Lean 정리 자체의 형식 타당성을 바꾸지 않습니다.

## P vs NP 범위 차분 감사

P vs NP에서는 기존에 확정한 처분을 사용합니다.

- `동일`
- `등가 입증`
- `충분성 입증`
- `범위 축소`
- `범위 확장`
- `조건부`
- `미해결`

`동일`, `등가 입증`, `충분성 입증`만 P vs NP의 수학적 해결과 양립합니다.

다른 처분도 정확한 수학 결과일 수 있습니다. 수학 해설이 실제 범위를 정확히 말하고 동일성 인증을 통과했다면 Lean 정본에 편입합니다. 다만 P vs NP를 해결했다는 상태는 만들지 않습니다.

## 종결 절차

```text
동일성 인증
+ Lean 커널·공리 감사
          ↓
Lean 정본 편입 가능
          ↓
목표 해결을 주장하는가?
  ├─ 아니요 → 실제 부분 결과로 편입
  └─ 예 → 프로젝트별 목표 감사
             ├─ 해결 조건 충족 → 수학적 해결
             └─ 불충족 → 실제 범위의 결과로 편입
```

목표 해결 감사에서 더 좁은 결과가 드러나면 제안을 무조건 폐기하지 않습니다.

- 수학 해설이 이미 그 좁은 범위를 정확히 말한다면 그대로 부분 결과로 편입합니다.
- 수학 해설이 핵심 목표 해결이라고 과장했다면 해설–형식 동일성이나 목표 관계 기록을 고쳐 새 제안 판본으로 다시 인증합니다.
- 후보 Lean 정리가 정확하지만 목표 관계만 잘못됐다면 Lean 형식 결과 자체를 버리지 않습니다.

## 보편 확장 지점

`do-math`는 프로젝트별 감사를 다음 인터페이스로 받습니다.

- 비교할 연구 헌장 항목
- 필요한 입력과 원자료
- 판정 어휘
- 각 판정의 효과
- 어떤 판정이 목표 해결을 허용하는가
- 어떤 판정이 Lean 정본 편입까지 막는가

기본적으로 목표와의 거리나 범위 차이는 Lean 정본 편입을 막지 않습니다. 공리·신뢰·동일성처럼 수학적 사실 자체의 정당성을 깨는 감사만 편입을 막을 수 있습니다.

따라서 앞서 말한 “프로젝트별 추가 감사 뒤 Lean 정본 편입”은 다음처럼 고칩니다.

> 추가 감사마다 통제하는 판정을 명시한다. P vs NP 범위 차분 감사는 목표 해결 판정을 통제하며, 정확한 부분 결과의 Lean 정본 편입은 막지 않는다.

이렇게 **수학적 사실의 Lean 정본 편입과 연구 헌장의 목표 해결 판정을 분리하고, 목표 감사에 실패한 정확한 결과도 실제 범위로 정본에 보존하는 방식**을 확정할까요?

## USER

## ASSISTANT

이제 `F`의 후보와 Lean 정본의 수학 객체가 어떤 정체성을 공유하는지 정해야 합니다. 같은 명제를 입증할 때 새 객체를 만들면 연구 계보가 끊기고, 실제 문면이 달라졌는데 같은 ID를 유지하면 잘못된 관계가 승계됩니다.

## 수학 객체 ID

재사용 가능한 정의·명제·정리·반증 결과에는 전역적으로 안정된 `math_object_id`를 둡니다.

이 ID는 다음 표현을 연결합니다.

```text
F의 수학 후보
↔ 수학 해설의 수학 항목
↔ 동일성 대응표
↔ Lean 정본 선언
```

수학 해설 안의 `math_item_id`는 다음 둘 중 하나입니다.

- 독립된 수학 객체이면 `math_object_id`를 직접 사용한다.
- 특정 증명 안에서만 쓰는 국소 단계이면 해당 해설에 속한 국소 ID를 사용한다.

## 같은 ID를 유지하는 경우

다음 내용이 그대로이면 `F`의 후보와 Lean 정본 객체가 같은 `math_object_id`를 사용합니다.

- 정의 또는 명제의 정확한 의미
- 양화
- 가정
- 적용 범위
- 사용하는 계산 모형
- 결론

후보에 근거·해설·Lean 증명을 추가하고 정본에 편입하는 것은 같은 객체의 지식 상태가 바뀌는 일입니다.

```text
F의 미입증 후보
→ 수학 해설·Lean 형식화
→ 동일성 인증·커널 검사
→ 같은 math_object_id가 K에 편입
```

공용 작업대의 F 기록은 삭제하지 않습니다. `인증됨` 상태와 Lean 정본 좌표를 기록하고 활성 미입증 프런티어에서 제외합니다. 과거 후보 판본과 생성 계보는 그대로 남습니다.

## 새 ID를 만드는 경우

다음 중 하나라도 바뀌면 새 `math_object_id`를 만듭니다.

- 명제 문면
- 정의
- 가정
- 적용 범위
- 계산 모형
- 양화
- 조건부 여부

예를 들어 원래 후보보다 좁은 정리를 입증하면 그 좁은 정리는 새 객체입니다.

```text
원래 F 후보 P               ← 여전히 미해결일 수 있음
새 Lean 정리 Q              ← 실제 입증한 좁은 결과
관계: Q는 P의 제한 결과
```

`Q`가 `P`를 해결한다는 형식 관계가 별도로 입증되면 그 관계도 Lean 정본 객체로 편입합니다. 이름이 비슷하거나 연구자가 그렇게 의도했다는 이유만으로 같은 객체로 합치지 않습니다.

## 반증

`¬P`를 입증하면 `P`와 `¬P`는 서로 다른 수학 객체입니다.

- `¬P`는 새 `math_object_id`로 Lean 정본에 들어갑니다.
- `P`는 반증된 후보라는 현재 처분을 가집니다.
- `P`와 `¬P` 사이의 부정 관계를 기록합니다.
- `P`의 과거 문면·근거·작업 이력을 삭제하지 않습니다.

좁은 부정 결과 `Q`가 `¬P`를 뜻하지 않으면 `P`를 반증 상태로 바꾸지 않습니다. `Q`를 별도 객체로 편입하고 실제 관계만 기록합니다.

## 예상하지 못한 결과

작업 시작 때 `F`에 없던 결과가 작업 중 발견되고 같은 작업 안에서 형식화·인증까지 끝날 수 있습니다.

이 경우에도 생성 계보를 생략하지 않습니다.

```text
U에서 발견
→ 작업별 작업대의 발견 후보
→ 새 math_object_id
→ 수학 해설·Lean 형식화·인증
→ 공용 편입에서 F 발견 기록과 K 편입을 함께 보존
```

공용 판본에 미입증 F 상태가 따로 존재했던 적은 없어도, 작업 내부에서 `U → F → K`를 거친 생성 계보를 종결 기록에 남깁니다.

## 자동 귀결 금지

한 정리를 Lean 정본에 편입했다고 해서 그 논리적 귀결을 모두 K 객체로 자동 생성하지 않습니다.

- 실제 Lean 선언과 증명 항으로 명시한 결과만 K에 들어갑니다.
- 폐쇄 계산이나 파생 보기는 후보 생성에 사용할 수 있습니다.
- 파생된 귀결을 외부 수학 결과로 쓰려면 수학 해설·Lean 표현·동일성 인증을 거쳐 명시적으로 편입합니다.

이렇게 **정확한 수학적 의미가 같을 때만 F와 K가 같은 `math_object_id`를 유지하고, 문면·가정·범위가 달라지면 새 ID와 명시적 관계를 만드는 방식**을 확정할까요?

## 관계

예를 들면 다음과 같습니다.

- `해결함`
- `반증함`
- `부분적으로 다룸`
- `조건부로 다룸`
- `범위를 좁힘`
- `정의 후보를 정식화함`
- `후속 작업의 근거가 됨`
- `발견의 출발점이 됨`

이 목록은 닫힌 관계 어휘가 아닙니다. 각 관계는 정확한 의미와 근거를 가져야 합니다.

한 F 객체가 여러 Lean 정본 결과를 낼 수 있고, 하나의 Lean 정본 결과가 여러 F 객체에 영향을 줄 수도 있습니다. 공통 ID보다 명시적인 다대다 관계가 이 구조를 자연스럽게 표현합니다.

## F 객체의 처분

Lean 정본 결과가 생겨도 F 객체를 삭제하지 않습니다.

- 완전히 해결됐으면 활성 프런티어에서 제외하고 해결 관계를 기록합니다.
- 부정이 입증됐으면 반증 관계와 이전 후보 상태를 보존합니다.
- 더 좁은 결과만 얻었으면 부분 관계를 기록하고 원래 F 객체를 계속 열어 둘 수 있습니다.
- 연구 가치가 사라졌으면 별도의 비활성화 근거를 기록합니다.
- 관계를 확정하지 못했으면 Lean 결과와 F 객체를 억지로 연결하지 않습니다.

따라서 `F → K`는 객체 하나가 장소를 옮긴다는 뜻이 아닙니다.

> F의 연구를 통해 새로운 Lean 정본 객체가 생기고, 그 결과에 따라 F의 연구 상태가 바뀐다는 지식 상태 전이입니다.

## 공통 구조

각 핵심 기록은 한 JSON 안에서 공통 정보와 역할별 내용을 구분합니다.

```json
{
  "schema_version": "do-math/frontier-object/1",
  "record_id": "F-01K...",
  "record_kind": "frontier_object",
  "provenance": {
    "cause_kind": "task_integration",
    "cause_id": "T-01K...",
    "source_refs": []
  },
  "lifecycle": {
    "value": "open",
    "reason_ref": "..."
  },
  "artifacts": [],
  "data": {}
}
```

- `schema_version`: 해당 역할의 정확한 스키마
- `record_id`: 안정된 논리 식별자
- `record_kind`: 기록 역할
- `provenance`: 생성 원인과 원자료
- `lifecycle`: 그 역할의 스키마가 허용하는 생명주기
- `artifacts`: 긴 실제 내용의 좌표
- `data`: 역할별 기계 정보

`lifecycle`이라는 필드 이름은 공통이지만 허용 값은 역할마다 다릅니다. 서로 다른 역할의 상태를 하나의 범용 어휘로 합치지 않습니다.
