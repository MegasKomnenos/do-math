- `script`는 모델을 호출하지 않는 결정론적 작업입니다.

- `workflow`는 스크립트가 여러 headless 하위 실행을 정해진 순서로 운전합니다.

`검증` 노드는 `workflow` executor를 사용합니다. workflow 자체는 의미 판단을 하지 않습니다.

```text

  ↓

  ├─ 독립 심사 세션들을 실행
  ├─ 심사 결과 문서를 각각 검산
  ├─ 정족을 기계적으로 집계
  └─ validation_result.json 작성
```

구체적인 계약은 다음과 같습니다.

- 검토자와 심사자는 작업 DAG 노드가 아니라 검증 노드의 하위 실행입니다.
- 하위 실행은 모두 새 headless 세션입니다.
- 하위 세션은 다른 세션을 파견하지 않습니다.
- 검토 결과를 “정리”한다는 말은 순서 정렬·ID 부여·묶음 생성을 뜻합니다.
- workflow 스크립트는 검토 내용을 요약하거나 제거하지 않습니다.
- 모든 하위 세션은 지정 경로에 결과 문서를 쓰고 직접 검산합니다.
- workflow 스크립트도 각 결과 문서를 다시 검산합니다.
- 심사자는 검토 결과 전건을 받지만 다른 심사자의 판정은 받지 않습니다.
- workflow 스크립트는 정족 규칙만 적용합니다.
- 의미 검증이 기각되면 검증 노드는 `rejected` 결과로 정상 완료합니다.
- 운전기는 기각 결과를 입력으로 새 전개 노드를 만듭니다.
- 운영 실패는 검증 노드를 완료하지 않습니다.

## 이 티켓에서 만드는 것

`do-math`는 수학 연구 인스턴스의 전체 생명주기를 운전하는 분야 독립적이고 자기충족적인 수학 연구 스킬이다. `do-math`는 `do-dag`의 다세션 작업 DAG 운전 원리와 `verify-rounds`의 독립 검토·심사 원리를 수학 연구 절차 안에 통합한다. 두 스킬을 순서대로 호출하는 래퍼는 아니다.

현재 티켓은 실제 `do-math` 스킬 파일을 만들지 않는다. 현재 티켓은 구현 세션이 추가 설계 없이 스킬·계약·전거·스크립트·스키마와 테스트를 만들 수 있는 구현 도면을 완성한다. 실제 스킬 자산은 후행 구현 티켓이 만든다.

설계 대화는 추상 원칙만 합의하는 과정이 아니다. 건축 도면처럼 실제 파일, 데이터, 상태 전이, 역할, 도구와 실패 처리를 구현 가능한 수준으로 정한다. 에이전트는 결과 품질을 바꾸지 않는 파일명·기계 세부·단순 구현 선택을 스스로 정한다. 목표, 신뢰 경계, 외부 효과 또는 품질이 동등한 방안 사이의 사용자 절충만 질문한다.

산문과 설계에는 다음 일곱 기준을 함께 적용한다.

- 간결성
- 간단성
- 명확성
- 정확성
- 정합성
- 충분성
- 충실성.

간결성을 높이려고 명확성·충분성·정확성을 줄이면 안 된다. 새 결정은 과거 문면 뒤에 작업 일지처럼 덧붙이지 않는다. 현행 정본의 관련 절을 직접 다시 써서 현재 설계 하나만 남긴다.

## 현재까지 확정한 구조

상세 계약은 `docs/do-math/통합-설계.md`가 소유한다. 다음 목록은 다음 세션이 문서를 읽을 때 찾을 좌표만 제공한다.

- 연구 인스턴스 하나는 최상위 수학 연구 목적 하나를 소유한다. 각 인스턴스는 `C:\math\instances\<인스턴스-ID>\`의 독립 Git 저장소다. 루트 `.gitignore`는 `/instances/`를 무시한다.
- 인스턴스는 `.do-math/`, `project-input/`, `research/`, `formalization/`과 `canon/`을 분리한다.
- 상주 LLM 오케는 두지 않는다. 메인 세션은 사용자 접점만 맡고, PowerShell headless 운전기가 Claude·Codex 프로세스와 상태 전이를 운전한다.
- executor는 `headless`, `script`, `workflow`로 구분한다. `workflow`는 결정론적 스크립트가 여러 독립 headless 하위 실행을 운전한다.
- 작업 노드는 독립 JSON 정본을 가진다. 준비 상태, 64비트 정수 우선순위, hard blocker, 입력 해시, executor, 시도와 결과 포인터를 기록한다.
- 운전기는 최대 `N`개의 headless 세션을 실행한다. 빈 슬롯마다 준비 노드 중 우선순위가 가장 높은 노드를 원자적으로 추출·점유한다. 종료된 슬롯은 즉시 다시 채운다.
- 우선순위 배분 알고리즘은 값만 쓴다. 운전기는 탐색·집중 활용의 의미를 해석하지 않는다. 실제 우선순위 계산 규칙은 아직 설계하지 않았다.
- 모든 작업 세션은 지정 경로에 `result.json`과 부속 산출물을 저장한다. 세션은 공식 도구로 자기 결과를 검산한 뒤 종료한다. 운전기는 같은 결과를 다시 검산한다.
- 작업 노드 완료는 원하는 수학 결과의 획득이 아니다. 한 세션 크기의 작업을 수행하고 검증된 결과 문서를 남겼다는 뜻이다. 증명에 실패해도 정확한 장애·부분 결과·후속 제안을 남기면 정상 완료할 수 있다.
- 검토와 심사는 `검증` workflow 노드 하나의 내부 단계다. 검토자와 심사자는 DAG 노드가 아니라 새 headless 하위 실행이다. workflow 스크립트는 결과를 변형하지 않고 묶고 정족만 기계 집계한다.
- 일반 작업 노드는 DAG를 직접 고치지 않는다. 전개 노드가 `dag_patch.json`을 만든다. 패치는 구조 검사와 의미 검증을 모두 통과한 뒤 별도 적용 노드가 반영한다.
- 구조 검사나 의미 검증이 실패하면 기존 전개를 고치지 않는다. 실패 근거를 입력으로 받은 새 전개 노드를 만든다. 실패한 패치와 검증 결과는 이력으로 남긴다.
- 전거는 절차보다 먼저 작성하는 최소 공통 의미 핵이다. 한 사실을 파일 하나에 두고, 스크립트가 필요한 절차 문서의 생성 구간에 축자 전사한다.
- 모든 파견은 `SKILL.md` 전문, `계약/공통.md`와 역할별 계약을 읽는다. `계약/공통.md`의 첫 지시는 `SKILL.md` 전문 통독이다.

## 다음 세션이 유지해야 할 설계 방식

설계는 보편 원칙과 구체 구현을 별개의 층으로 나누는 작업이 아니다. 건축 도면처럼 실제 구현이 어떤 구성물과 연결을 가져야 하는지 정한다. 다만 품질을 바꾸지 않는 임의의 상수와 단순 구현 선택까지 사용자에게 묻지는 않는다.

에이전트는 다음 세부를 직접 채운다.

- 파일과 필드의 이름
- 기계적으로 하나로 정할 수 있는 상태 전이
- 원자 쓰기, 해시 대조와 검사 순서
- 오류 코드와 스키마의 기계적 제약
- 기존 결정에서 하나로 따라 나오는 구현 선택.

사용자에게 가져갈 결정은 다음 범위로 좁힌다.

- 연구 목적·성공 기준·범위를 바꾸는 결정
- Lean 정본·기초 프로필·검증 독립성 같은 신뢰 경계를 바꾸는 결정
- 외부 공개·유료 자원·크리덴셜·복구 불가능한 삭제 같은 외부 효과
- 결과 품질이 동등한 여러 최종 상태 사이에서 사용자 선호가 필요한 결정.

사용자 질문은 한 번에 하나만 한다. 질문 전에 구현 가능한 추천안을 완성한다. 사용자가 선택해야 할 이유를 “에이전트가 정하기 어렵다”로 설명하지 않는다. 각 선택을 적용한 최종 상태와 장기 영향을 비교한다.

새 결정은 기존 문서 끝에 연대기처럼 덧붙이지 않는다. `docs/do-math/통합-설계.md`와 `docs/wayfinder/pvsnp-재설계/컨텍스트.md`의 관련 절을 직접 다시 쓴다. 현재 효력이 있는 문면 하나만 남긴다. 컨텍스트 정본의 미커밋 문면도 과거이기 때문에 보존해야 하는 대상이 아니다.

산문은 간결성·간단성·명확성·정확성·정합성·충분성·충실성을 함께 높인다. 특히 간결성을 이유로 독자가 상태 전이, 책임 주체, 실패 영향과 재개 위치를 추론하게 만들지 않는다.

## 이번 세션 초기에 겪었고 다시 반복하면 안 되는 시행착오

### 1. `do-math`의 정체성보다 저장 구조를 먼저 묻지 않는다

초기에는 연구 인스턴스의 Git 경계부터 사용자에게 질문했다. 사용자는 먼저 `do-math`가 무엇인지 확정하라고 교정했다. 다음 세션은 이미 확정한 정체성을 다시 열거나, 새 세부를 정체성보다 앞에 놓지 않는다.

`do-math`는 수학 연구 인스턴스의 전체 생명주기를 운전하는 분야 독립적이고 자기충족적인 수학 연구 스킬이다. `do-dag`의 다세션 작업 DAG 운전 원리와 `verify-rounds`의 독립 검토·심사 원리를 수학 연구 절차 안에 통합한다. 두 스킬을 순서대로 호출하는 래퍼는 아니다.

### 2. 작은 구조 결정을 매번 사용자 승인으로 보내지 않는다

초기에는 전거 분류, 전거 파일 형식과 저장 세부를 한 조각씩 질문했다. 사용자는 중요한 뼈대만 함께 세우고, 나머지는 일곱 저작 기준에 따라 에이전트가 채우라고 교정했다. 다음 세션은 기계적 세부마다 확인을 받지 않는다.

### 3. 추상 원칙을 사례에서 귀납하는 별도 단계로 만들지 않는다

초기에는 P vs NP 사례를 만든 뒤 보편 규칙을 도출하겠다고 기록했다. 사용자는 통합 설계 자체가 구체적인 구현 도면이어야 한다고 교정했다. 사례는 완성된 설계가 실제 주제에서 작동하는지 검증할 때 사용한다. 사례를 먼저 만든 뒤 규칙을 추측하는 방식으로 설계하지 않는다.

### 4. `do-dag`의 현재 모양을 그대로 복사하지 않는다

`do-dag`의 전거는 이미 작성된 절차의 중복을 사후 추출한 결과다. 그래서 항목이 크고 절차 문면을 많이 품는다. `do-math`는 전거의 역할과 원자성부터 정하고 `전거 → 절차` 순서로 작성한다.

전거에는 `요지`와 `전문`을 두지 않는다. 한 사실은 파일 하나에 정본 문면 하나만 가진다. 전거는 에이전트가 직접 읽는 절차가 아니다. 전사 스크립트가 필요한 사실을 실제 절차 문서의 생성 구간에 축자 전사하고, 에이전트는 그 절차 문서를 읽는다.

### 5. 상주 LLM 오케를 전제로 하지 않는다

처음에는 메인 세션이나 별도 LLM 오케가 장기 운전을 맡는 구조를 검토했다. 현행 설계는 상주 LLM 오케를 두지 않는다. PowerShell headless 운전기가 Claude·Codex 프로세스, 슬롯, 상태와 Git 전이를 운전한다. 의미 판단은 작업 세션이 하고, 운전 스크립트는 판단 결과의 형식과 상태 전이만 처리한다.

### 6. 준비 노드를 무차별 병렬 실행하거나 포트폴리오를 직접 고르지 않는다

현행 외부 인터페이스에서 모든 노드는 준비 상태와 우선순위 값을 가진다. 배분 알고리즘은 우선순위 값만 쓴다. 운전기는 최대 `N`개의 headless 세션을 실행하며, 빈 슬롯마다 가장 높은 우선순위의 준비 노드를 원자적으로 추출·점유한다. 세션이 끝나면 다음 노드를 즉시 넣는다.

탐색·집중 활용의 의미는 배분 알고리즘이 우선순위에 반영한다. 운전기는 그 의미를 다시 해석하지 않는다. 실제 우선순위 계산 규칙은 아직 정하지 않았다.

### 7. 검토와 심사를 별도 DAG 노드로 만들지 않는다

현행 설계에서 `검증`은 `workflow` executor를 쓰는 노드 하나다. workflow 스크립트가 독립 검토 headless 세션들을 실행하고 결과를 변형 없이 묶는다. 그 뒤 독립 심사 headless 세션들을 실행하고 정족을 기계적으로 집계한다.

검토자와 심사자는 DAG 노드가 아니라 검증 노드의 하위 실행이다. 각 하위 세션은 전역 동시 세션 예산 `N`의 슬롯 하나를 사용한다. 이 구조 때문에 일반 노드와 workflow 하위 실행 사이의 슬롯 중재가 아직 해결되지 않은 핵심 예외다.

### 8. 짧은 예외 색인으로 충분하다고 보지 않는다

첫 예외 원장은 265개 상황을 표 한 줄씩 적었다. 사용자는 발생 과정과 영향이 복원되지 않는다고 반려했다. 현행 `docs/do-math/예외-원장.md`는 각 예외를 `의도된 동작·발생 상황·영향·현재 처리`로 다시 설명한다. 다음 세션은 다시 짧은 표로 압축하지 않는다.

## 현재 설계의 구체적인 뼈대

상세 정본은 `docs/do-math/통합-설계.md`다. 아래 내용은 문서를 읽을 때 유지해야 할 연결을 설명한다.

### 연구 인스턴스와 저장소

연구 인스턴스 하나는 최상위 수학 연구 목적 하나를 소유한다. 인스턴스는 `C:\math\instances\<인스턴스-ID>\`의 독립 Git 저장소다. 루트 저장소는 `/instances/`를 무시한다.

인스턴스는 실행 상태 `.do-math/`, 1회 수입한 `project-input/`, 연구 작업공간 `research/`, 편입 전 Lean 작업공간 `formalization/`과 Lean 정본 `canon/`을 분리한다. 실제 초기화·재개·종결·보관 상태 기계는 아직 작성하지 않았다.

### 작업 노드·시도·결과

작업 노드는 독립 JSON 정본을 가진다. 노드에는 ID, 목적, 상태, 준비 상태, 64비트 정수 우선순위, hard blocker, 입력 해시, executor, 시도와 결과 포인터가 있다. executor는 `headless`, `script`, `workflow` 셋이다.

모든 작업 세션은 지정 경로에 구조화한 `result.json`을 쓴다. 긴 논증, 문헌 판독과 Lean 파일은 별도 artifact로 저장하고 결과 JSON이 경로와 SHA-256을 소유한다. 세션은 공식 도구로 자기 결과를 검산한 뒤 종료한다. 운전기는 같은 결과를 다시 검산한다.

노드 완료는 원하는 정리·반례·해법의 획득이 아니다. 한 세션 크기의 작업을 수행하고 계약을 충족하는 결과를 남겼다는 뜻이다. 증명에 실패해도 시도한 논증, 정확한 장애, 부분 결과와 후속 제안을 남기면 정상 완료할 수 있다. 이 결정 때문에 “완료”와 “후행 작업에 필요한 의미 결과”를 분리해야 한다.

### DAG 변경

일반 작업 노드는 DAG를 직접 바꾸지 않는다. 결과의 후속 제안은 즉시 노드가 되지 않는다. 전개 노드가 현재 DAG와 미소비 제안을 읽고 `dag_patch.json`을 만든다.

패치는 먼저 결정론적 구조 검사를 받는다. 구조 검사를 통과하면 검증 workflow가 목적·노드 크기·실제 차단 관계·중복·탐색 범위·신뢰 경계를 의미 검증한다. 승인 패치만 별도 적용 노드가 반영한다.

구조 실패나 의미 기각이 생기면 기존 전개와 결과를 덮어쓰지 않는다. 실패 근거를 받은 새 전개 노드를 만든다. 실패한 패치와 검증 하위 결과는 이력으로 남는다. 새 전개에 어떤 파일·해시·DAG 판본을 정확히 지급할지는 아직 정하지 않았다.

### 전거·계약·도구

`SKILL.md`는 모든 세션이 읽는 최상위 절차다. 모든 파견은 `계약/공통.md`와 역할별 계약을 함께 받는다. `계약/공통.md`의 첫 지시는 `SKILL.md` 전문 통독이다.

전거는 여러 절차와 스크립트가 같은 문면으로 소비하는 사실의 유일한 정본이다. 한 사실을 파일 하나에 둔다. 실제 전거 파일과 전사 도구는 후행 구현 티켓이 만든다.

## 왜 `do-math`를 설계하고 있는가

이 저장소는 P vs NP를 장기간 연구하려 한다. 기존 `do-dag`는 명세가 이미 있는 유한 작업을 여러 세션에 나누어 완주하는 데 적합하다. 기존 `verify-rounds`는 완성된 산출물에서 결함과 수리안을 찾고, 독립 심사를 거쳐 승인된 수정만 적용하는 데 적합하다.

수학 연구에는 두 스킬만으로 다루지 못하는 상태가 있다.

- 무엇을 조사해야 할지 연구 결과에 따라 계속 달라진다.
- 유망한 경로를 깊게 진행하면서 전혀 다른 경로도 계속 탐색해야 한다.
- 증명에 실패한 작업도 정확한 장애와 부분 결과를 남기면 다음 연구의 입력이 된다.
- 자연어 아이디어, 미완성 Lean 코드와 승인된 Lean 정본은 서로 다른 신뢰 상태를 가진다.
- 한 연구 결과가 새 작업을 만들고, 그 새 작업이 다시 연구 방향을 바꾼다.
- 연구는 한 에이전트 컨텍스트보다 오래 지속되므로 모든 재개 정보가 파일과 Git 이력에 있어야 한다.

`do-math`는 이 공백을 담당한다. `do-math`는 수학 연구 목적 하나를 여러 세션에 걸쳐 수행하고, 연구 작업을 동적 작업 DAG로 관리하며, 검증된 수학 결과를 Lean 정본에 축적하는 보편 스킬이다. `do-dag`와 `verify-rounds`를 차례로 호출하는 래퍼가 아니다. 두 스킬의 유효한 원리를 수학 연구의 전체 생명주기 안에 다시 설계한다.

현재 지도에서 이 티켓은 `do-math`의 구현 도면을 만든다. [P vs NP 핵심 Lean 정의를 완성하고 검증한다](https://github.com/MegasKomnenos/math/issues/20)와 [P vs NP 문헌 포괄·처리·활용 체계를 확정한다](https://github.com/MegasKomnenos/math/issues/21)는 별도 선행 티켓이다. 세 티켓이 모두 끝난 뒤 [보편 수학 연구 스킬 do-math를 구현하고 검증한다](https://github.com/MegasKomnenos/math/issues/19)가 실제 스킬·계약·스크립트·스키마와 테스트를 만든다.

현재 티켓은 실제 스킬 파일을 만들지 않는다. 완료 산출물 `docs/do-math/통합-설계.md`가 백지 구현 세션에 필요한 의미·파일·상태 전이·권한·실패 처리와 테스트를 모두 정해야 한다.

## 이 인계에서 사용하는 용어

| 용어 | 정확한 뜻 |
|---|---|
| 연구 인스턴스 | 최상위 수학 연구 목적 하나를 여러 세션에 걸쳐 수행하고 재개하는 영속 실행 단위 |
| 프로젝트 입력 | 연구 인스턴스를 만들 때 한 번 수입하는 주제·원하는 결과·범위·방향의 사용자 입력 |
| 연구 작업공간 | 질문, 아이디어, 문헌 판독, 실패, 자연어 논증과 연구 계획을 보존하는 비정본 공간 |
| Lean 형식화 작업공간 | 정본 편입 전 Lean 정의·명제·증명 후보를 보존하는 공간 |
| Lean 정본 | 의도 인증과 Lean 검사를 통과한 정의·증명·반증 결과만 들어가는 권위 있는 Lean 프로젝트 |
| 작업 DAG | 앞으로 수행할 작업 노드와 실제 차단 관계를 담은 하나의 동적 비순환 그래프 |
| 작업 노드 | 한 번의 정해진 연구·형식화·도구·전개·검증 작업을 표현하는 JSON 정본 |
| 시도 | 한 노드를 실행하기 위해 Claude·Codex 세션이나 스크립트를 한 번 실행한 기록 |
| 결과 문서 | 시도 결과를 구조화한 `result.json`; 긴 논증·Lean 파일은 해시로 연결한 별도 artifact에 둠 |
| 완료 | 원하는 정리를 얻었다는 뜻이 아니라, 노드가 요구한 한정된 작업을 수행하고 유효한 결과 문서를 남겼다는 상태 |
| 의미 결과 | `proved`, `not_proved`, `approved`, `rejected`처럼 결과 내용이 무엇인지 나타내는 값; 아직 정확한 공통 구조는 미정 |
| 차단 관계 | 선행 작업이 충족되기 전에는 후행 작업을 실행할 수 없다는 관계 |
| 준비 상태 | 현재 상태·차단 관계·입력·계약이 노드 실행을 허용한다는 기계 계산 결과 |
| 우선순위 | 준비 노드 중 무엇을 먼저 실행할지 배분 알고리즘이 쓰는 64비트 정수 |
| headless 세션 | 대화형 터미널 없이 CLI로 실행하고 파일에 결과를 남긴 뒤 종료하는 Claude·Codex 세션 |
| 운전기 | PowerShell 프로세스; 준비 노드 선택, 세션 실행, 결과 검산, 상태 변경과 Git 커밋을 맡음 |
| workflow executor | 스크립트가 여러 독립 headless 하위 세션을 정해진 순서로 실행하는 합성 실행기 |
| 검증 노드 | workflow executor가 검토 세션들을 실행한 뒤 심사 세션들을 실행하고 하나의 검증 결과를 만드는 작업 노드 |
| 전개 노드 | 작업 결과의 후속 제안을 읽고 DAG 변경안 `dag_patch.json`을 만드는 작업 노드 |
| 전거 | 여러 절차와 스크립트가 같은 문면으로 소비할 `do-math` 사실의 유일한 원본; 에이전트용 절차 자체는 아님 |

## 현재 설계에서 연구 한 건이 흐르는 방식

다음 흐름은 현재 통합 설계가 의도하는 정상 경로다. 다음 세션은 개별 필드를 읽기 전에 이 전체 연결을 먼저 유지해야 한다.

### 1. 연구 인스턴스를 만든다

연구 인스턴스는 `C:\math\instances\<인스턴스-ID>\`에 독립 Git 저장소로 둔다. 루트 저장소 `C:\math`는 `/instances/`를 무시한다.

인스턴스 저장소는 다음 다섯 영역을 가진다.

```text
<연구 인스턴스>/
├─ .do-math/        운전 상태, 노드, 시도, 결과, 결정과 보고
├─ project-input/   생성 시 한 번 수입한 프로젝트 입력
├─ research/        자연어 연구와 문헌 작업
├─ formalization/   정본 편입 전 Lean 작업
└─ canon/           승인된 Lean 정본
```

현재 설계는 이 저장 경계만 정했다. 초기화·재개·일시정지·종결·보관의 상태 기계는 아직 작성하지 않았다.

### 2. 운전기가 실행할 노드를 고른다

상주 LLM 오케는 없다. 메인 세션은 사용자 결정의 접점만 맡는다. PowerShell headless 운전기가 장시간 실행을 맡는다.

모든 노드는 준비 상태와 우선순위 값을 가진다. 운전기는 최대 `N`개의 headless 세션을 동시에 실행한다. 빈 슬롯이 있으면 준비 노드 중 우선순위가 가장 높은 노드 하나를 스크립트로 원자적으로 추출·점유한다. 슬롯이 찰 때까지 반복한다. 세션 하나가 끝나면 결과를 회수하고 다음 준비 노드를 즉시 넣는다.

배분 알고리즘은 우선순위 값만 할당한다. 운전기는 왜 값이 높은지 해석하지 않는다. 탐색과 집중 활용의 균형은 나중에 설계할 배분 알고리즘이 우선순위에 반영한다.

### 3. 작업 세션이 노드 하나를 수행한다

노드의 executor는 다음 셋 중 하나다.

- `headless`: Claude 또는 Codex 세션 하나가 의미 작업을 수행한다.
- `script`: 모델 판단이 필요 없는 결정론적 스크립트 하나가 수행한다.
- `workflow`: 스크립트가 여러 headless 하위 세션을 순서대로 운전한다.

일반 headless 작업 세션은 다른 세션을 파견하지 않는다. 세션은 고정된 입력 파일, 역할 계약, 쓰기 범위와 결과 JSON Schema를 받는다.

세션은 지정 경로에 `result.json`을 쓰고, 공식 검산 도구로 스키마·입력 해시·artifact 경로·쓰기 범위를 검사한다. 검산에 성공한 뒤에만 종료한다. 운전기는 세션의 성공 주장을 신뢰하지 않고 같은 파일을 다시 검산한다.

### 4. 노드 완료와 수학적 성공을 구별한다

노드 하나는 한 세션으로 수행 가능한 범위를 가져야 한다. 노드가 “접근법 A로 보조정리 L을 조사한다”라면, 증명을 얻지 못해도 다음 정보를 정확히 남길 수 있다.

- 실제로 시도한 논증과 계산
- 확인한 정의와 가정
- 진행을 막은 정확한 단계
- 얻은 부분 결과와 반례 후보
- 다음에 수행할 작업 제안.

이 결과가 계약을 충족하면 노드는 `completed`가 된다. 보조정리 L은 여전히 미해결일 수 있다. 프로세스 오류, 결과 문서 결손과 스키마 실패는 연구 결과가 아니므로 노드를 완료하지 않는다.

이 구별은 현재 설계의 가장 중요한 미해결 문제를 만든다. 후행 노드가 선행 노드의 `completed`만 보면 “작업을 수행했다”와 “필요한 정리를 증명했다”를 구별하지 못한다.

### 5. 결과에서 새 작업 후보를 만든다

일반 작업 결과는 `followups`에 후속 작업을 제안할 수 있다. 제안은 아직 DAG 노드가 아니며 실행 효력이 없다.

미소비 제안이 생기면 운전기가 고정 템플릿으로 전개 노드를 만든다. 전개 노드는 현재 DAG, 원 결과와 후속 제안을 읽고 `dag_patch.json`을 쓴다. 패치는 노드·차단 간선의 추가, 미실행 노드의 취소·대체와 생성 관계를 제안한다.

### 6. DAG 패치를 두 관문으로 검증한다

첫 관문은 구조 검사다. 스크립트가 JSON Schema, ID, 순환, 경로 충돌, 역할 계약과 허용 변경을 검사한다.

두 번째 관문은 의미 검증이다. 구조 검사를 통과한 패치에 대해 검증 노드 하나를 만든다. 검증 노드는 `workflow` executor를 사용한다.

workflow의 내부 순서는 다음과 같다.

1. 독립 검토 headless 세션들을 실행한다.
2. 각 검토 결과를 스키마 검사한다.
3. 결과를 요약하거나 삭제하지 않고 정렬·ID 부여해 묶는다.
4. 독립 심사 headless 세션들을 실행한다.
5. 각 심사 결과를 검사한다.
6. 정족 규칙을 기계적으로 집계한다.
7. 하나의 검증 결과를 쓴다.

검토자와 심사자는 별도 DAG 노드가 아니다. 검증 노드의 하위 실행이다. 각 하위 실행은 전역 세션 예산 `N`의 슬롯 하나를 사용한다. 검토 관점 수, 심사 기수와 정족은 아직 확정하지 않았다.

### 7. 승인 패치만 적용한다

구조 검사와 의미 검증을 통과한 패치는 별도 적용 노드가 DAG에 반영한다. 일반 작업 세션과 전개 노드는 DAG JSON을 직접 고치지 않는다.

구조 검사가 실패하거나 의미 검증이 패치를 기각하면 기존 전개 노드의 결과를 덮어쓰지 않는다. 운전기는 실패 근거를 입력으로 받은 새 전개 노드를 만든다. 실패한 패치와 검토·심사 결과는 이력으로 보존한다.

그러나 새 전개에 정확히 어떤 파일과 해시를 전달할지는 아직 정하지 않았다. 원 패치, 구조 검사 보고, 검토·심사 원문, 원 결과, 후속 제안과 현재 DAG 판본을 어디까지 한 입력 패키지로 묶을지가 미해결이다.

## 절차 문서를 만드는 방식

`SKILL.md`는 모든 `do-math` 세션이 읽는 최상위 절차다. 모든 파견은 `계약/공통.md`와 역할별 계약도 받는다. 공통 계약의 첫 지시는 `SKILL.md` 전문 통독이다.

세부 절차보다 먼저 전거를 작성한다. 전거에는 용어·상태·권한·판정·불변식처럼 여러 소비자가 같은 문면으로 써야 하는 사실을 둔다. 사실 종류는 닫지 않는다. 포함 여부는 “둘 이상의 소비자가 같은 문면 전체를 필요로 하는가”로 판정한다.

전거 파일 하나는 독립적으로 바꿀 수 있는 사실 하나만 담는다. `요지`와 `전문`을 따로 만들지 않는다. 전사 스크립트가 전거 본문을 `SKILL.md`와 계약의 생성 구간에 축자 복사한다. 에이전트는 전거 파일을 직접 절차로 읽지 않고, 전사된 실제 절차 문서를 읽는다.

현재 티켓은 이 구조와 의미를 정한다. 실제 전거·계약·스크립트는 후행 구현 티켓이 만든다.

## 왜 지금 예외 원장을 먼저 만들었는가

첫 구현 도면은 정상 경로를 설명하지만, 자연스러운 중단·경합·기각·판본 변경을 충분히 다루지 못했다. 검토 기수와 우선순위 알고리즘을 더 정하면 미해결 상태 위에 새 규칙을 쌓게 된다. 사용자는 다음 단계로 가기 전에 현재 요소 전부의 예외를 먼저 드러내라고 지시했다.

처음 작성한 예외 원장은 265개 상황을 표 한 줄씩 적었다. 그 표는 예외 이름만 알려 주고, 어떻게 생기며 무엇을 망가뜨리는지 설명하지 못했다. 사용자는 명확성과 충분성 부족으로 반려했다.

현행 `docs/do-math/예외-원장.md`는 109개 상세 예외를 다시 설명한다. 각 예외는 다음 네 내용을 모두 갖는다.

1. 정상일 때 무엇이 일어나야 하는가
2. 예외가 실제로 어떻게 발생하는가
3. 방치하면 어떤 상태·산출·판정이 잘못되는가
4. 현재 설계가 어디까지 처리하는가.

원장 끝에는 개별 예외 여러 개를 동시에 닫아야 하는 교차 불변식 6개가 있다. 원장은 836줄, 약 68KB다. 상세 예외 109개가 네 필드를 모두 갖는지 기계적으로 검사했다.

사용자가 직접 제시한 예외는 다음 좌표에 있다.

- `EXP-08`, `EXP-09`: 실패·기각된 패치의 정보를 새 전개에 어떻게 온전히 전달하는가
- `SCHED-06`, `SCHED-07`, `SCHED-08`: 검증 노드가 하위 세션 슬롯을 얻지 못하거나 영구 기아할 수 있는가.

## 다음 세션이 처음 수행할 설계 작업

다음 세션은 검토 기수·심사 정족이나 우선순위 계산으로 돌아가지 않는다. 예외를 더 짧게 다시 나열하지도 않는다. `docs/do-math/예외-원장.md`의 교차 불변식부터 하나씩 닫는다.

첫 작업 후보는 `CROSS-01 완료 상태와 의미 효력의 분리`다. 관련 상세 항목은 `NODE-03`, `ATT-12`와 `VAL-11`이다.

현재 설계를 상태 예로 쓰면 다음 모순이 생긴다.

```text
연구 노드 A
  state = completed
  outcome = not_proved

형식화 노드 B
  blocked_by = [A]

현재 준비 계산
  A가 completed이므로 B를 ready로 만듦

실제 의미
  B는 A가 증명에 성공했을 때만 실행 가능함
  A는 조사만 완료했고 증명은 얻지 못했으므로 B를 열면 안 됨
```

검증에서도 같은 문제가 생긴다.

```text
검증 노드 V
  state = completed
  outcome = rejected

패치 적용 노드 P
  blocked_by = [V]

현재 준비 계산
  V가 completed이므로 P를 ready로 만듦

실제 의미
  P는 V가 approved일 때만 실행 가능함
```

다음 세션은 이 문제를 예외문 하나로 막지 않는다. 다음 네 요소를 하나의 상태 모델로 다시 설계한다.

- 노드 `state`가 말하는 실행 생명주기
- 결과 `outcome`이 말하는 의미 결과
- 간선이 요구하는 선행 outcome 조건
- 후행 노드를 미리 만들지, 결과 뒤에 만들지의 규칙.

다음 세션이 이 단계에서 만들어야 할 구체 산출은 다음 셋이다.

1. 수정된 노드 JSON과 차단 간선 JSON 예시
2. 준비 상태를 계산하는 의사코드
3. 증명 실패·검증 기각·승인·운영 실패를 넣은 상태 전이 표.

구조가 기계적으로 하나로 우수하면 에이전트가 직접 선택한다. 신뢰 경계나 동등한 최종 구조가 둘 이상 남을 때만 사용자에게 추천안을 포함한 질문 하나를 올린다.

결정 뒤에는 `docs/do-math/통합-설계.md`의 노드·준비·검증·DAG 변경 절을 함께 다시 쓴다. `docs/wayfinder/pvsnp-재설계/컨텍스트.md`에는 다른 티켓도 알아야 할 의미 결정만 반영한다. 예외 원장의 관련 항목을 다시 읽어 처분이 실제로 닫혔는지 확인한다. 마지막으로 새 상태 모델이 다른 예외를 만들지 설계 전체를 역대조한다.

그다음 후보는 다음 다섯 교차 불변식이다. 순서는 아직 사용자 결정이 아니다.

- `CROSS-02`: 검증 workflow 하위 실행과 일반 노드 사이의 전역 슬롯 중재
- `CROSS-03`: 실패한 전개가 새 전개에 넘기는 입력 패키지

- `CROSS-06`: 사용자 결정이 준비·실행·완료 노드에 미치는 영향.

## 다음 세션이 반복하면 안 되는 작업 방식

- `do-math`의 정체성, 인스턴스 경로와 headless 운전 구조를 처음부터 다시 묻지 않는다. 이미 확정된 문면을 실제 파일에서 확인하고 이어간다.

## 2. `do-math`를 만드는 이유

기존 `do-dag`는 명세가 이미 있는 유한 작업을 여러 세션에 나누어 완주한다. 기존 `verify-rounds`는 완성된 산출물의 결함과 수리안을 찾고, 독립 심사를 거쳐 승인된 수정만 적용한다.

장기 수학 연구에는 두 스킬이 소유하지 않는 문제가 있다.

1. 연구 결과가 다음 작업 자체를 계속 바꾼다.
2. 유망한 경로를 깊게 진행하면서 먼 분야와 새 경로도 탐색해야 한다.
3. 증명 실패도 장애·부분 결과·후속 질문을 남기면 유효한 연구 결과다.
4. 자연어 연구, 미완성 Lean 작업과 승인된 Lean 정본은 서로 다른 신뢰 상태다.
5. 연구는 한 에이전트 컨텍스트보다 오래 지속된다. 재개 정보는 파일과 Git 이력에 있어야 한다.

`do-math`는 이 전체 생명주기를 소유한다. `do-dag`와 `verify-rounds`를 순서대로 호출하는 래퍼가 아니다. 두 스킬의 유효한 원리를 수학 연구에 맞는 하나의 절차로 다시 설계한다.

현재 티켓은 실제 스킬 파일을 만들지 않는다. 백지 구현 세션이 추가 설계 없이 파일·상태·계약·스크립트·스키마와 테스트를 만들 수 있는 도면을 완성한다.

## 3. 시스템 전체 구조

```text
사용자
  │ 목표·신뢰 경계·외부 효과에 관한 결정
  ▼
메인 세션
  │ headless 운전기 시작·중단, 사용자 결정 중계
  ▼
PowerShell headless 운전기
  ├─ 준비 노드 계산·우선순위 추출·점유
  ├─ Claude/Codex headless 세션 실행
  ├─ 결과 파일 재검산
  ├─ workflow 하위 세션 슬롯 중재       ← 아직 미설계
  └─ 상태 변경·worktree 병합·Git 커밋   ← 아직 미설계
       │
       ▼
연구 인스턴스 Git 저장소
  ├─ .do-math/       실행 상태·DAG·시도·결과·결정·보고
  ├─ project-input/  생성 때 한 번 수입한 프로젝트 입력
  ├─ research/       자연어 연구·문헌·실패·계획
  ├─ formalization/  정본 편입 전 Lean 작업
  └─ canon/          인증과 Lean 검사를 통과한 Lean 정본
```

연구 인스턴스 하나는 최상위 수학 연구 목적 하나를 소유한다. 각 인스턴스는 `C:\math\instances\<인스턴스-ID>\`의 독립 Git 저장소다. 루트 저장소 `C:\math`는 `/instances/`를 무시한다.

## 4. 핵심 용어

| 용어 | 뜻 | 다른 개념과의 경계 |
|---|---|---|
| 연구 인스턴스 | 수학 연구 목적 하나를 여러 세션에 걸쳐 수행·재개하는 영속 단위 | 저장소 하나와 대응함 |
| 작업 DAG | 앞으로 수행할 작업 노드와 실제 차단 관계를 담은 동적 비순환 그래프 | Lean 선언의 수학 의존을 복제하지 않음 |
| 작업 노드 | 연구·형식화·도구·전개·검증 작업 하나의 JSON 정본 | 한 번의 원하는 수학 결과와 같지 않음 |
| 시도 | 노드를 수행하려고 세션이나 스크립트를 한 번 실행한 기록 | 노드 하나에 여러 운영 재시도가 있을 수 있음 |
| 완료 | 정해진 작업과 결과 문서 계약을 충족한 노드 상태 | 증명 성공이나 승인과 같지 않음 |
| 의미 결과 | `proved`, `not_proved`, `approved`, `rejected`처럼 결과 내용이 무엇인지 나타내는 값 | 정확한 공통 구조는 아직 미정 |
| 준비 상태 | 상태·차단 관계·입력·계약이 실행을 허용한다는 기계 계산 결과 | 우선순위와 별개임 |
| 우선순위 | 준비 노드의 실행 순서를 정하는 64비트 정수 | 탐색·집중 활용의 해석은 배분 알고리즘이 담당함 |
| headless 세션 | CLI로 비대화식 실행하고 파일 결과를 남긴 뒤 종료하는 Claude·Codex 세션 | 상주 LLM 오케가 아님 |
| 운전기 | PowerShell 프로세스; 준비 노드 선택, 세션 실행, 결과 검산, 상태 변경과 Git 커밋을 맡음 |
| workflow executor | 스크립트가 여러 독립 headless 하위 세션을 정해진 순서로 실행하는 합성 실행기 | 스크립트 자체는 의미 판단을 하지 않음 |
| 검증 노드 | workflow executor가 검토 세션들을 실행한 뒤 심사 세션들을 실행하고 하나의 검증 결과를 만드는 작업 노드 | 검토자·심사자는 별도 DAG 노드가 아님 |
| 전개 노드 | 후속 제안을 읽고 DAG 변경안 `dag_patch.json`을 만드는 노드 | DAG를 직접 수정하지 않음 |
| 전거 | 여러 절차·스크립트가 같은 문면으로 소비할 `do-math` 사실의 유일한 원본 | 에이전트가 직접 수행할 절차가 아님 |

## 6. 정상 실행 흐름

### 6.1 노드 선택과 실행

1. 운전기는 노드 파일 전건에서 준비 상태를 계산한다.
2. 빈 headless 슬롯이 있으면 priority가 가장 높은 준비 노드를 추출·점유한다.
3. 동률이면 오래 준비된 노드, 그다음 노드 ID 순서로 고른다.
4. 운전기는 노드 executor에 따라 headless 세션이나 스크립트를 실행한다.
5. 실행 중 새 고우선순위 노드가 생겨도 기존 노드를 선점 중단하지 않는다.
6. 세션 하나가 끝나면 결과를 정산하고 빈 슬롯을 즉시 채운다.

### 6.2 작업 결과와 완료

1. 작업 세션은 고정된 입력·역할 계약·쓰기 범위·결과 JSON Schema를 받는다.
2. 세션은 긴 논증·Lean 파일을 artifact로 쓰고 `result.json`에 경로와 SHA-256을 기록한다.
3. 세션은 공식 도구로 자기 결과를 검산한 뒤 종료한다.
4. 운전기는 결과 파일과 실제 변경 범위를 다시 검산한다.
5. 결과 계약을 충족하면 노드는 `completed`가 될 수 있다.
6. 프로세스 오류·결과 결손·스키마 실패는 운영 실패이므로 노드를 완료하지 않는다.

증명을 얻지 못해도 시도한 논증, 정확한 장애, 부분 결과와 후속 제안을 계약대로 남기면 정상 완료할 수 있다. 이 완료 의미와 후행 작업의 수학적 전제 사이의 연결은 아직 미설계다.

### 6.3 후속 제안에서 DAG 패치까지

1. 일반 결과의 `followups`는 후속 작업을 제안한다. 아직 DAG 노드가 아니다.
2. 운전기는 미소비 제안을 입력으로 전개 노드를 만든다.
3. 전개 노드는 현재 DAG와 관련 결과를 읽고 `dag_patch.json`을 쓴다.
4. 스크립트가 ID·순환·경로·계약을 구조 검사한다.
5. 구조 검사를 통과하면 검증 workflow가 패치를 의미 검증한다.
6. 승인 패치만 별도 적용 노드가 DAG에 반영한다.

구조 검사나 의미 검증이 실패하면 기존 전개 결과를 덮지 않는다. 실패 자료를 입력으로 받은 새 전개 노드를 만든다. 실패 자료의 정확한 전달 묶음은 아직 미설계다.

### 6.4 검증 workflow 내부

1. workflow는 검증 대상 경로와 해시를 확인한다.
2. 독립 검토 headless 세션들을 실행한다.
3. 검토 결과를 각각 스키마 검사한다.
4. 검토 결과를 삭제·요약하지 않고 정렬·ID 부여해 묶는다.
5. 독립 심사 headless 세션들을 실행한다.
6. 심사 결과를 각각 검사한다.
7. workflow는 정족 규칙만 기계적으로 적용한다.
8. 하나의 검증 결과 문서를 쓴다.

검토자와 심사자는 별도 DAG 노드가 아니다. 각 하위 세션은 전역 `N`에서 슬롯 하나를 사용한다. 검토 관점 수·심사 기수·정족과 하위 슬롯 중재는 아직 미설계다.

## 7. 예외 원장의 현재 상태

정상 흐름만 더 확장하면 중단·경합·기각·판본 변경이 미정인 상태에서 새 규칙을 쌓게 된다. 사용자는 다음 설계 단계 전에 현재 요소 전부의 예외를 먼저 드러내라고 지시했다.

첫 예외 원장은 265개 상황을 한 줄 표로 적었다. 사용자는 발생 과정과 손상을 알 수 없다고 반려했다. 현행 `docs/do-math/예외-원장.md`는 다음 구조로 다시 작성했다.

| 항목 | 값 |
|---|---|
| 문서 크기 | 836줄, 약 68KB |
| 상세 예외 | 109개 |
| 교차 불변식 | 6개 |
| 상세 예외의 필수 필드 | 의도된 동작·발생 상황·영향·현재 처리 |
| 기계 검산 | 상세 예외 109개가 네 필드를 모두 갖는지 확인 |

사용자가 직접 제시한 예외는 다음 위치에 있다.

- `EXP-08`, `EXP-09`: 실패·기각된 패치의 정보를 새 전개에 어떻게 온전히 전달하는가
- `SCHED-06`, `SCHED-07`, `SCHED-08`: 검증 workflow가 하위 세션 슬롯을 얻지 못하거나 영구 기아할 수 있는가.

예외를 아직 해결하지 않았다. 원장은 해결할 범위를 드러내는 현행 감사 결과다.

## 8. 다음 세션의 정확한 시작 작업

다음 세션은 검토 정족이나 우선순위 배분 알고리즘으로 돌아가지 않는다. 원장 14절의 교차 불변식부터 하나씩 해결한다.

첫 후보는 `CROSS-01 완료 상태와 의미 효력의 분리`다. 함께 읽을 상세 항목은 `NODE-03`, `ATT-12`와 `VAL-11`이다.

### 8.1 현재 모순

```text
연구 노드 A
  state = completed
  outcome = not_proved

형식화 노드 B
  blocked_by = [A]

현재 준비 계산
  A가 completed이므로 B를 ready로 만듦

실제 요구
  B는 A가 proved일 때만 실행 가능함
```

검증에서도 같은 모순이 있다.

```text
검증 노드 V
  state = completed
  outcome = rejected

패치 적용 노드 P
  blocked_by = [V]

현재 준비 계산
  V가 completed이므로 P를 ready로 만듦

실제 요구
  P는 V가 approved일 때만 실행 가능함
```

### 8.2 함께 다시 설계할 요소

- 노드 `state`: 실행 생명주기에서 어디까지 왔는가
- 결과 `outcome`: 수학적·검증 의미가 무엇인가
- 차단 간선의 만족 조건: 어떤 state와 outcome이 후행을 여는가
- 후행 노드 생성 시점: 결과 전에 만들지, 필요한 outcome 뒤에 만들지.

### 8.3 다음 세션이 만들어야 할 산출

1. 수정한 노드 JSON 예시
2. outcome 조건을 포함한 차단 간선 JSON 예시
3. 준비 상태 계산 의사코드
4. 증명 성공·증명 미달·검증 승인·검증 기각·운영 실패의 상태 전이 표.

기계적으로 우수한 구조가 하나면 에이전트가 직접 선택한다. 신뢰 경계나 동등한 최종 구조가 둘 이상 남을 때만 사용자에게 추천안을 포함한 질문 하나를 올린다.

결정 뒤에는 다음 파일을 함께 갱신한다.

| 파일 | 반영할 내용 |

| 예외를 한 줄 표로 압축 | 발생 과정·영향·현재 처리를 모두 설명 | 새 세션이 예외의 뜻을 복원할 수 있어야 함 |
| 예외 처분 전 검토 정족·배분 알고리즘 논의 | 교차 불변식부터 해결 | 결함 있는 상태 모델 위에 규칙을 쌓지 않기 위해 |

문서를 수정할 때 과거 문면을 보존하려고 덧붙이지 않는다. `docs/do-math/통합-설계.md`와 컨텍스트 정본의 관련 절을 직접 다시 쓴다. 현재 효력이 있는 문면 하나만 남긴다.

질문은 한 번에 하나만 한다. 파일명·필드명·원자 쓰기 순서처럼 기계적으로 정할 세부는 질문하지 않는다. 목표·신뢰 경계·외부 효과 또는 품질이 동등한 최종 상태 사이의 사용자 절충만 질문한다.

간결성·간단성·명확성·정확성·정합성·충분성·충실성을 함께 적용한다. 간결성을 이유로 상태 전이, 책임 주체, 실패 영향과 재개 위치를 생략하지 않는다.

## 10. 파일과 워크트리 상태

| 경로 | 현재 역할·상태 |
|---|---|
| `docs/do-math/통합-설계.md` | 370줄; 현재까지 확정한 정상 구조 |
| `docs/do-math/예외-원장.md` | 836줄; 상세 예외 109개와 교차 불변식 6개 |
| `docs/wayfinder/pvsnp-재설계/컨텍스트.md` | 티켓 사이의 현행 결정·소유권 정본; 세션 시작 전부터 큰 미커밋 개정이 있었음 |
| `.gitignore` | `/instances/` 규칙을 추가함 |

검증한 내용은 다음과 같다.

- `git check-ignore -v instances/probe`로 `/instances/` 무시를 확인했다.
- 통합 설계의 JSON 예제들을 PowerShell `ConvertFrom-Json`으로 판독했다.
- 예외 원장의 상세 항목 109개가 필수 필드 네 개를 모두 갖는지 검사했다.

현재 브랜치는 `main`이다. 마지막으로 확인한 HEAD는 `4675b28de8bde675d154d913131c4cf297a9ef1e`이다. 이 세션은 커밋하거나 push하지 않았다.

워크트리에는 위 네 경로 밖의 기존 변경과 미추적 파일도 있다. 그것들은 다른 작업이나 사용자의 소유다. 전체 워크트리를 정리·되돌리거나 범위 밖 파일을 커밋하지 않는다. 실제 작업 전에 `git status`와 관련 diff를 다시 측정한다.

컨텍스트 정본을 HEAD 판본으로 되돌리지 않는다. 미커밋이라는 이유만으로 옛 문면을 보존하지도 않는다. 현행 설계와 맞게 관련 절을 직접 고친다.

## 11. Suggested skills

상위 지도 Notes가 지정한 `grilling`, `domain-modeling`과 `write-for-reader`를 적용한다. 스킬 구조를 판단할 때 `skill-creator`와 `writing-great-skills`를 함께 사용한다.

- `grilling`은 모든 세부를 사용자에게 묻는 절차가 아니다. 중대한 사용자 결정만 한 번에 하나씩 묻는다.
- `write-for-reader`는 글을 짧게 줄이는 절차가 아니다. 다음 구현 세션이 상태·책임·처분을 추론하지 않도록 명확성과 충분성을 먼저 보존한다.
