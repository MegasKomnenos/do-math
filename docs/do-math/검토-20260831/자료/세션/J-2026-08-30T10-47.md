질문을 연구하려면 무엇이 필요한지 확인합니다.

- 필요한 `K`의 객체와 판본
- 필요한 문헌과 원자료
- 선행 보조정리·정의·형식화
- 계산 도구와 데이터
- 다른 프로그램이 생산해야 할 결과

선행 요소가 없으면 질문 자체를 폐기하지 않습니다. 필요한 요소를 별도 프런티어 객체나 선행 작업으로 만듭니다.

## 5. 필요하면 사전 탐사를 수행한다

바로 장기 프로그램을 열기 전에 값싼 탐사로 다음을 확인할 수 있습니다.

- 질문이 이미 해결됐거나 기존 후보와 중복되는가
- 정의가 실제로 구성 가능한가
- 작은 사례에서 즉시 반례가 나오는가
- 필요한 문헌이나 데이터에 접근 가능한가
- 알려진 장벽이 제안한 방법에 실제로 적용되는가

사전 탐사도 막연하게 수행하지 않습니다. 입력과 산출이 분명한 **정련 프로그램**으로 실행합니다. 정련 프로그램은 수학 문제를 해결하는 대신 아이디어를 착수 가능한 질문으로 만들거나, 만들 수 없는 이유를 기록하는 것이 목적입니다.

## 6. 프로그램 착수 명세를 만든다

정련 결과가 충분하면 다음 내용을 갖춘 프로그램 착수 명세를 만듭니다.

- 출발한 프런티어 객체와 공용 판본
- 프로그램이 답할 정확한 질문
- 담당 범위와 제외 범위
- 입력과 선행 의존성
- 기대하는 공용 작업대의 변화
- 만들 산출물
- 성공·실패·부분 완료·판정 불가의 기준
- 다른 프로그램과 겹치는 범위와 그 중복이 필요한 이유
- 중단하거나 재설계해야 하는 조건

이 명세가 완성되어야 **착수 가능** 상태가 됩니다.

## 7. 착수 가능과 실제 착수를 구분한다

착수 가능한 프로그램을 모두 즉시 실행하지는 않습니다. 적응형 연구 포트폴리오가 다음을 비교해 실제로 시작할 프로그램을 선택합니다.

- 목표에 대한 예상 기여
- 새로운 정보를 얻을 가능성
- 기존 프로그램과의 중복과 다양성
- 필요한 자원과 선행 의존성
- 실패해도 남을 재사용 가능한 결과

따라서 흐름은 `아이디어 → 프로그램`이 아니라 다음과 같습니다.

```text

→ 정련된 질문
→ 착수 명세
→ 착수 가능한 프로그램 후보
→ 포트폴리오가 선택한 실제 프로그램
```

### 프런티어 정련 작업이 맡는 범위

앞서 말한 단계 중 1~4와 6을 기본적으로 하나의 정련 작업이 맡습니다.

- 관련 `K`, 프런티어 객체와 프로그램을 찾는다.
- 아이디어를 하나 이상의 판정 가능한 질문으로 바꾼다.
- 각 질문의 범위와 성공·실패 기준을 정한다.
- 필요한 입력과 의존성을 찾는다.
- 프로그램 착수 명세 초안을 작성한다.

정련 작업의 목적은 수학 문제를 푸는 것이 아니라, **풀어 볼 수 있는 정확한 연구 계약을 만드는 것**입니다.

### 사전 탐사는 별도 작업으로 분리한다

단계 5에서 필요한 조사가 작고 즉시 끝난다면 정련 작업 안에서 수행할 수 있습니다. 그러나 다음처럼 독립적인 산출물이 필요하면 별도 작업으로 분리합니다.

- 여러 문헌의 원문을 조사해야 한다.
- 반례 계산이나 실험이 필요하다.
- Lean 정의가 실제로 작성 가능한지 시제품이 필요하다.
- 알려진 장벽이 적용되는지 수학적 분석이 필요하다.
- 다른 프런티어 객체의 결과를 기다려야 한다.

각 사전 탐사 작업은 자기 입력·산출물·완료 조건을 가집니다. 탐사 결과는 공용 편입할 수 있으며, 정련 작업은 그 결과를 받아 재개합니다.

### 착수 가능성 관문은 정련 작업과 분리한다

정련 작업자가 자기 초안을 그대로 승인하지 않습니다. 착수 가능성 관문은 다음을 검사합니다.

- 질문이 실제로 판정 가능한가
- 범위와 제외 범위가 모순되지 않는가
- 필요한 입력과 차단 의존성이 빠지지 않았는가
- 산출물과 완료 기준이 서로 대응하는가
- 기존 프로그램과의 중복이 설명됐는가
- 프로그램이 실패해도 무엇을 보존할지 정했는가

통과하지 못하면 새 연구 프로그램을 만들지 않습니다. 결함을 명시해 같은 정련 작업으로 돌려보내거나 필요한 사전 탐사 작업을 추가합니다.

### 포트폴리오 선택은 그 뒤에 일어난다

관문 통과는 “실행할 수 있다”는 뜻일 뿐 “지금 실행한다”는 뜻이 아닙니다. 적응형 연구 포트폴리오가 착수 가능한 후보 사이에서 실제로 자원을 받을 프로그램을 선택합니다.

## 구체적인 예

프런티어 객체 `F-17`에 “대수적 기법이 제한 회로 하계에 연결될 수 있다”는 아이디어가 있다고 가정하겠습니다.

1. `do-math`가 `F-17@공용커밋C`를 입력으로 정련 작업을 연다.
2. 정련 작업이 아이디어를 구체적인 질문 둘로 분화한다.
3. 한 질문은 관련 장벽 적용 여부를 알 수 없어 문헌 탐사 작업을 만든다.
4. 다른 질문은 정의의 실현 가능성을 확인하기 위해 Lean 시제품 작업을 만든다.
5. 두 작업의 결과가 공용 편입된다.
6. 정련 작업이 결과를 읽고 프로그램 착수 명세를 완성한다.
7. 별도 착수 가능성 관문이 명세를 검사한다.
8. 통과한 명세가 프로그램 후보 목록에 들어간다.
9. 포트폴리오가 선택하면 그때 프로그램 ID와 프로그램 작업대를 만든다.

따라서 정확한 답은 다음과 같습니다.

> 1~6은 `do-math`가 소유하는 프런티어 정련 절차다. 기본 분석은 하나의 정련 작업이 맡고, 실질적인 조사·실험·형식화가 필요하면 별도 사전 탐사 작업으로 분기한다. 착수 가능성 판정과 실제 프로그램 선택은 정련 작업 밖에서 수행한다.

## “공용 작업대와 직접 상호작용한다”는 정확한 의미

각 작업이 공용 작업대의 현재 파일을 직접 동시에 수정하게 하지는 않습니다. 과거에 공유 Git index와 작업 트리에서 실제 경합이 발생했기 때문입니다.

대신 각 작업은 다음 방식으로 공용 작업대와 직접 연결됩니다.

1. 공용 작업대의 특정 커밋을 입력 기준으로 고정한다.
2. 작업 전용 브랜치와 worktree에서 실행한다.
3. 작업 결과 중 공유할 내용을 공용 편입 묶음으로 만든다.
4. 공용 머리와 다시 대조해 편입한다.
5. 편입된 새 공용 판본을 다음 작업들이 입력으로 사용한다.

따라서 의미상으로는 각 작업이 공용 작업대에서 직접 출발하고 직접 결과를 돌려줍니다. 물리적으로는 동시 쓰기를 막기 위해 격리된 작업대를 사용합니다.

## 연구 방향의 연속성은 프로그램 없이 보존한다

연구 프로그램을 없앤다고 장기 연구 방향까지 없애지는 않습니다. 장기 방향은 실행 컨테이너가 아니라 다음 기록으로 표현합니다.

- 연구 방향을 나타내는 프런티어 객체
- 그 방향을 선택한 근거
- 관련 작업과 산출물의 관계
- 선행·후속 작업의 계보
- 해당 방향이 목표에 기여한 실제 효과
- 강화·약화·중단된 이유

파생 보기는 같은 연구 방향에 연결된 작업들을 하나의 흐름으로 보여 줄 수 있습니다. 이 보기는 편의를 위한 묶음일 뿐, 별도 브랜치·작업대·DAG를 소유하지 않습니다.

## 얇은 실행 껍질의 의미

실행 껍질의 깊이 `N`은 **현재 공용 상태에서 어느 정도 앞까지 작업으로 구체화할 것인가**를 뜻합니다.

- 깊이 1: 지금 바로 실행할 수 있는 작업
- 깊이 2: 깊이 1 작업의 결과나 완료를 기다리는 직접 후속 작업
- 깊이 3 이상: 그 뒤의 명시된 후속 작업

`N=1`이면 준비된 작업만 실제 작업으로 만듭니다. 그 너머의 가능성은 `F`에 탐색 방향이나 작업 제안으로 남깁니다.

고정된 `N`보다는 상황에 따라 깊이를 조절하는 방식을 추천합니다. 결과의 불확실성이 크면 `N=1`로 유지하고, 선행 결과와 무관하게 후속 질문이 이미 정확하다면 더 깊게 구체화할 수 있습니다. 실행 껍질은 정본을 하나 더 만드는 것이 아니라 핵심 기록에서 계산하는 파생 보기입니다.

- 발견한 작업과 그 작업의 기준 커밋
- 발견을 낳은 실제 자료·관찰·논증
- 최초로 공용 편입된 커밋

공용 커밋 `C`에서 실행 껍질 `S(C)`는 다음 조건을 모두 만족하는 작업만 포함합니다.

- 입력과 필요한 자료가 현재 공용 작업대에 존재한다.
- 아직 충족되지 않은 선행 조건이 없다.
- 질문, 산출물과 완료 기준이 확정됐다.
- 현재 공용 판본에서 실행해도 의미가 있다.
- 다른 작업이 이미 같은 범위를 점유하지 않았다.

즉, 실행 껍질에는 **지금 시작할 수 있는 작업만** 있습니다. 미래에 수행할 수도 있지만 아직 조건이 충족되지 않은 일은 작업으로 만들지 않습니다.

## DAG의 기능을 무엇으로 대체하는가

| 작업 DAG가 맡던 기능 | 깊이 1 구조의 대체물 |
|---|---|
| 미래 작업 보존 | `F`의 작업 씨앗과 조건부 탐색 방향 |
| 선행 작업과 차단 간선 | 작업 씨앗의 명시적인 입력·발생 조건 |
| 준비 노드 계산 | 현재 공용 상태에서 실행 껍질 재계산 |
| 작업 우선순위 | 적응형 포트폴리오 |
| 작업 계보 | 완료 작업과 공용 편입의 생성 관계 |
| 장기 연구 경로 | `F` 객체·작업 씨앗·완료 작업을 잇는 파생 보기 |
| 순환 금지 | 반복 감지와 연구 진전 판정 |

여기서 **작업 씨앗**은 아직 실행 작업이 아닙니다. 예상 질문, 필요한 조건, 가능한 산출과 생성 근거를 `F`에 표현한 대상입니다. 조건이 충족되고 작업 계약이 완성될 때만 실행 껍질의 실제 작업으로 바뀝니다.

## 구체적인 작동 방식

```text
공용 작업대 판본 C
        │
        ▼
작업 씨앗과 F를 검사
        │
        ▼
현재 착수 가능한 작업만 물질화
        │
        ▼
실행 껍질 S(C)
        │
        ▼
포트폴리오가 작업 선택
        │
        ▼
작업별 작업대에서 실행
        │
        ▼
결과·발견 후보·새 작업 씨앗을 공용 편입
        │
        ▼
공용 작업대 판본 C'
        │
        └── 실행 껍질 S(C') 재계산
```

예를 들어 미래 작업 `B`가 현재 작업 `A`의 특정 결과를 필요로 한다면 `B`를 차단된 작업으로 미리 만들지 않습니다. `F`에 다음과 같은 작업 씨앗을 둡니다.

> `A`가 조건 `R`을 입증하거나 충분한 자료를 생산하면 질문 `Q`를 조사한다.

`A`의 결과가 공용 편입되어 조건 `R`이 실제로 충족되면, 그때 `B`의 작업 계약을 완성하고 실행 껍질에 넣습니다. `A`가 다른 결과를 내면 `B`는 존재하지 않으며 작업 씨앗을 수정·대체·비활성화합니다.

## 포트폴리오가 미래를 보는 방법

깊이 1이라고 해서 포트폴리오가 현재 작업의 즉시 산출만 보는 것은 아닙니다. 각 작업은 다음 정보를 통해 바깥 가능성을 보여 줍니다.

- 영향을 줄 `F` 객체
- 구체화할 수 있는 작업 씨앗
- 결과에 따라 열리거나 닫힐 조건부 방향
- 예상하지 못한 발견을 만들 탐색 방법
- 다른 준비 작업과의 중복·보완 관계
- 실패해도 줄 수 있는 정보

포트폴리오는 실제로 존재하는 작업만 선택하지만, 작업이 열 수 있는 후속 공간도 가치 판단에 사용합니다. 미래 작업을 미리 실행 객체로 만들 필요는 없습니다.

## 알려진 절차는 상태 전이로 표현한다

인증이나 Lean 정본 편입처럼 순서가 명확한 절차도 DAG로 미리 펼치지 않습니다.

예를 들어 현재 상태가 `의도 명세 완료`가 되면 전체 검토 작업을 만들고, 전체 검토가 승인되면 Lean 검사 작업을 만듭니다. 각 단계가 끝날 때 다음 상태에 맞는 작업을 하나씩 생성합니다. 절차 규칙은 보존하지만 미래 작업 인스턴스는 미리 만들지 않습니다.

## 이 구조의 장점

- 아직 결과를 모르는 연구에서 허위로 정밀한 장기 계획을 만들지 않습니다.
- 완료 결과에 따라 후속 작업을 매번 새로 구성할 수 있습니다.
- 차단 작업과 낡은 의존 간선을 계속 관리하지 않아도 됩니다.
- 연구의 반복과 되돌아가기를 억지로 비순환 그래프에 넣지 않아도 됩니다.
- 모든 실제 작업이 현재 공용 상태에서 착수 가능하므로 포트폴리오 선택이 단순해집니다.

대신 실행 껍질을 비우지 않는 **생존 조건**이 필요합니다. 목표가 미해결이고 자원을 계속 사용할 수 있는데 실행 껍질이 비면, `do-math`는 남아 있는 `F`와 탐색 방향에서 정련·탐색 작업을 만들어야 합니다. 아무 작업도 만들 수 없다면 그 이유와 다시 작업을 만들 수 있는 조건을 명시해야 합니다.

이 결정은 현행 “단일 작업 DAG” 원칙을 단순히 보완하는 것이 아니라 폐기·대체합니다. 두 구조를 함께 유지하지 않습니다.

**단일 작업 DAG를 없애고, 현재 착수 가능한 작업만 담는 깊이 1의 실행 껍질과 `F`의 작업 씨앗·발생 조건으로 실행 체계를 대체할까요?**

## USER

## ASSISTANT

순서가 명확한 절차는 기본적으로 하나의 작업으로 묶는 편이 좋습니다. 단계마다 별도 작업을 만들면 실행 껍질과 공용 편입 기록이 지나치게 잘게 쪼개질 수 있습니다.

다만 “순서가 정해져 있다”는 사실만으로 항상 한 작업에 묶을 수 있는 것은 아닙니다. 작업 경계는 단계 수보다 **독립적으로 배정·검증·재시도·공유할 필요가 있는가**로 정해야 합니다.

## 하나의 작업으로 묶는 경우

다음 조건을 모두 만족하면 여러 단계를 한 작업의 내부 절차로 둡니다.

- 전체 절차가 하나의 연구 상태 변화를 목표로 한다.
- 모든 단계의 입력을 작업 착수 시 확보할 수 있다.
- 중간 단계의 결과를 다른 작업이 먼저 사용할 필요가 없다.
- 포트폴리오가 중간에서 계속할지 다시 선택할 필요가 없다.
- 같은 작업자가 같은 권한과 신뢰 경계 안에서 수행할 수 있다.
- 실패 후 내부 체크포인트에서 안전하게 재개할 수 있다.
- 성공·실패·부분 완료의 최종 판정 기준이 하나로 닫힌다.

예를 들어 다음 절차는 하나의 작업으로 묶을 수 있습니다.

```text
문서 확보
→ 해시 확인
→ 본문 추출
→ 형식 정규화
→ 출처 좌표 생성
→ 판독 입력 패키지 완성
```

각 단계는 하나의 “판독 가능한 문헌 패키지 생성”이라는 결과를 만들며, 중간 산출물을 포트폴리오가 따로 선택할 필요가 없습니다.

## 별도 작업으로 나누는 경우

순서가 명확해도 다음 중 하나가 성립하면 작업을 나눕니다.

- 중간 결과를 다른 작업이 재사용할 수 있다.
- 다음 단계의 수행 여부를 결과를 본 뒤 포트폴리오가 판단해야 한다.
- 서로 다른 독립 검토자나 판정 권한이 필요하다.
- 중간 산출물을 공용 편입해 다른 작업에 알려야 한다.
- 한 단계만 별도로 재시도하거나 취소할 실익이 크다.
- 외부 응답이나 장기 계산을 기다려야 한다.
- 단계들이 병렬로 수행될 수 있다.
- 뒤 단계의 실패가 앞 단계의 유효한 결과까지 묻히게 된다.

예를 들어 다음 절차는 순서가 정해져 있어도 나누어야 합니다.

```text
증명 작성
→ 독립 전체 검토
→ 이의 심사
→ Lean 커널 검사
→ Lean 정본 편입
```

각 단계의 권한과 판정 의미가 다릅니다. 증명 작성자가 자기 증명을 독립 검토할 수 없으며, 검토 승인과 Lean 커널 통과도 서로 다른 판정입니다. 앞 단계의 결과는 그 자체로 보존·감사할 가치가 있습니다.

이 경우 미래 작업을 미리 만들지는 않습니다. 현재 단계의 공용 편입이 끝나면 절차 상태 규칙이 다음 착수 가능한 작업 하나를 생성합니다. 따라서 작업 DAG 없이도 깊이 1을 유지할 수 있습니다.

## 큰 작업은 실행과 분리한다

작업이 한 에이전트 세션보다 길어질 수 있다는 문제는 작업을 무조건 쪼개지 않고 **작업과 작업 실행**을 구분해 해결할 수 있습니다.

- 작업: 변하지 않는 입력·목적·산출물·완료 계약
- 작업 실행: 한 작업을 수행하는 개별 시도나 재개 구간
- 체크포인트: 다음 실행이 이어받을 검증된 내부 상태

하나의 작업은 여러 실행에 걸쳐 재개할 수 있습니다. 그러나 각 실행이 임의로 목표를 바꾸지는 못합니다. 작업이 반복될수록 질문이나 산출물이 계속 달라진다면 그 작업은 처음부터 너무 넓게 정의된 것이므로 분화해야 합니다.

## 가장 간단한 경계 검사

내부 단계 하나를 두고 다음과 같이 묻습니다.

> 이 단계를 다른 단계와 별도로 배정하거나, 검증하거나, 재시도하거나, 취소하거나, 공용 편입하고 싶은 합리적인 상황이 있는가?

없으면 같은 작업의 내부 단계로 둡니다. 하나라도 있으면 별도 작업으로 분리합니다.

따라서 권장 구조는 다음과 같습니다.

```text
실행 껍질의 작업
  ├─ 내부의 순차 절차
  ├─ 재개 가능한 체크포인트
  └─ 여러 작업 실행

        │
        ▼

```

- 운영 점검 실행: Git 실행 ref와 시간·프로세스 사건이 직접 발동함
- 연구 작업 종결: 공용 편입으로 끝남
- 운영 점검 종결: 점검 보고서와 조건부 실행-ref 처분으로 끝남

운영 점검 실행은 네 작업 인터페이스와 유사한 구조화 JSON·근거·로그를 사용하되, 공용 작업대의 `F` 객체나 연구 작업으로 가장하지 않습니다. 이 구별은 운영 사건을 억지로 수학 연구 프런티어에 넣는 오류를 막습니다.

운영 처분 심사는 점검자와 다른 실행이 점검 보고서·원자료·대상 ref를 대조합니다. 심사가 승인한 뒤에도 대상 ref가 점검 당시 값과 같을 때만 처분을 원자적으로 적용합니다.

사용자에게는 기존 개입 경계를 그대로 적용합니다. 처분이 연구 목적·신뢰 경계·외부 또는 비가역 상태를 바꾸거나 사용자 절충을 요구할 때만 상신합니다. 단순한 프로세스 재시작이나 체크포인트 인수는 충분한 근거가 있으면 `do-math`가 자율적으로 처리할 수 있습니다.

## Git 연속성 검사

현재 작업 트리에는 이번 티켓에서 확정한 결정이 아직 커밋되지 않은 채 보존돼 있다. 다음 상태를 직접 확인한다.

- 브랜치: `main...origin/main [ahead 2]`
- 현재 HEAD: `277be4a14d574ff5bc5ece5eba8fe636ec726d83`
- `origin/main`: `4675b28de8bde675d154d913131c4cf297a9ef1e`
- 수정 파일:
  - `CONTEXT.md`: 156행 추가
  - `docs/wayfinder/pvsnp-재설계/컨텍스트.md`: 216행 추가, 22행 삭제
- `git diff --check`: 통과. Windows 줄바꿈 변환 경고만 있음
- 커밋·푸시: 수행하지 않음

다음 명령으로 실제 상태를 대조한다.

```powershell
git status --short --branch
git diff -- CONTEXT.md docs/wayfinder/pvsnp-재설계/컨텍스트.md
git diff --check
```

위 상태와 다르면 기억이나 이 handoff를 근거로 내용을 재작성하지 않는다. 실제 diff와 이슈 상태를 대조하고 손실·경합을 사용자에게 보고한다.

## 정본과 지위

- `CONTEXT.md`는 구현 세부를 제외한 보편 도메인 용어집이다.
- `docs/wayfinder/pvsnp-재설계/컨텍스트.md`는 이번 지도의 현행 결정, 구체 운전 계약과 미결정의 고해상도 정본이다.
- 지도, 진행 설계 티켓과 후행 구현 티켓의 본문은 이번 세션의 확정 결정에 맞게 갱신됐다.
- 진행 티켓의 이전 handoff 댓글은 프로그램별 작업대와 단일 작업 DAG가 아직 유지되던 과거 상태를 담는다. 현재 설계를 판정할 때 그 댓글을 사용하지 않는다.
- 정확한 현행 문면은 작업 트리의 두 파일과 현재 이슈 본문에서 직접 읽는다.

이 handoff의 아래 서술은 결정 경위와 대체 관계를 보존한다. 정확한 실행 계약을 handoff 문장만으로 복원하지 않는다.

## 이번 세션의 설계 전개

### 1. 공용 작업대의 판본 정본을 Git으로 확정

세션 시작 시 가장 가까운 미결정은 공용 작업대의 지속 판본을 Git이 소유하는지였다.

확정한 내용:

- 공용 작업대의 지속 내용, 공개된 현재 판본과 이력은 Git이 소유한다.
- 과거 공개 판본은 Git 커밋 이력으로 보존한다.
- 연구 실행은 공용 기준 커밋에서 격리된 브랜치와 worktree로 분기한다.
- Git을 판본 정본으로 사용한다는 결정만으로 별도 서비스·데이터베이스·실시간 조정층을 도입하지 않는다.

이 결정의 근거에는 과거 병행 세션이 하나의 Git index를 공유하면서 다른 세션의 변경이 커밋에 섞인 실측이 있었다. 관련 근거는 `기억/layer1/M-0013.md`와 `기억/layer1/M-0034.md`다.

### 2. 연구 작업대의 의미를 저장 영역보다 넓게 확정

처음에는 사용자가 말한 작업대가 기존의 비정본 연구 작업공간과 같은지, `F·U`를 포함하는 더 넓은 구조인지 불분명했다.

사용자가 의도한 작업대는 책·목차·메모·칠판·수식·도구와 여러 완성도의 아이디어가 공존하는 messy하고 fuzzy한 연구 표면이었다.

확정한 해석:

- 연구 작업대는 별도의 네 번째 저장 영역이나 수학 정본이 아니다.
- 관련 `K` 판본의 참조, Lean 형식화 초안에 대한 접근, 명시된 `F` 후보, 문헌·메모·실패·실험·도구와 탐색 장치를 한 연구 맥락에서 다루는 운영 표면이다.
- 각 내용의 기존 소유권과 신뢰 경계는 유지한다.
- `U`는 정의상 아직 표현되지 않은 가능성이므로 작업대에 직접 들어갈 수 없다.
- 모호한 단서라도 기록되는 순간 `F`의 객체가 된다.
- 작업대는 `U`를 저장하지 않고, 탐색을 통해 `U`의 일부를 `F`로 드러낸다.

이 구별은 이후 예상하지 못한 발견을 표현하는 방식의 기초가 됐다.

### 3. 공용 작업대를 핵심 기록과 파생 보기로 구성

공용 작업대의 내부 구조는 다음 제1원리에서 도출됐다.

- 수학적 진실과 연구 상태를 분리한다.
- 내용은 모호할 수 있지만 정체성·출처·판본·상태 경계는 명확해야 한다.
- 공유 상태는 명시적인 상태 전이로만 바꾼다.
- 원자료와 재생성 가능한 보기를 구별한다.
- 모호한 후보를 성급하게 형식화하지 않고 점진적으로 정련한다.

확정한 구조:

- 공용 작업대의 핵심 기록은 기준, 프런티어, 자료·근거, 연구 작업, 관계와 공용 편입 기록을 소유한다.
- 프런티어 현황, 실행 상태, 중복 가능성, 연구 흐름과 편입 대기 상태는 핵심 기록에서 만드는 파생 보기다.
- 파생 보기는 독립 정본이 아니며 핵심 기록에서 다시 생성할 수 있어야 한다.
- Lean이 입증할 수학적 관계, 근거가 후보를 지지·반박하는 연구 관계와 실행 관계를 같은 종류의 간선으로 취급하지 않는다.

### 4. 핵심 기록의 정체성과 판본

핵심 기록 객체의 제목이나 경로가 바뀔 때 관계가 끊기지 않도록 안정된 ID를 도입했다.

확정한 내용:

- ID는 순서나 저장 위치를 나타내는 인덱스 번호가 아니라 객체의 논리적 정체성이다.
- 특정 객체 판본은 `핵심 기록 ID + 공용 작업대 판본`으로 식별한다.
- 제목·파일 경로가 바뀌어도 같은 객체라면 ID를 유지한다.
- 같은 명제·질문·정의에 근거·설명·산출물을 추가하면 같은 ID의 새 판본이다.
- 명제 문면, 질문, 정의, 가정이나 적용 범위가 달라져 기존 관계를 그대로 적용할 수 없으면 새 ID를 만든다.
- 분화·대체·정교화와 실제로 성립하는 관계를 기존 객체와 새 객체 사이에 기록한다. 이 관계 예시는 닫힌 목록이 아니다.
- 객체를 조용히 삭제하거나 같은 ID에 다른 의미를 덮어쓰지 않는다.

Git은 전체 공용 작업대 판본을 소유하므로 별도 객체 버전 카운터는 두지 않는다. 이 구현 세부는 지도 컨텍스트 정본에만 있고 root `CONTEXT.md`에는 추상 판본 개념만 남겼다.

### 5. 공통 외피와 역할별 기록 내용을 분리

처음에는 모든 핵심 기록에 하나의 범용 `status`를 두는 방안이 가능했지만, 이는 서로 다른 사실을 혼합한다는 문제가 드러났다.

예를 들어 Lean 코드가 실행된다는 사실은 수학적 의미가 인증됐다는 뜻이 아니고, 작업 완료도 그 작업이 낸 명제가 참이라는 뜻이 아니다.

확정한 내용:

- 모든 핵심 기록은 공통 외피와 역할별 내용으로 구성한다.
- 공통 외피는 ID, 객체 역할, 출처·생성 근거, 생명주기, 관계와 실제 자료 좌표를 가진다.
- 프런티어, 자료·근거, 연구 작업, 공용 편입과 관계는 자기 역할에 맞는 내용과 상태를 가진다.
- 수학적 확인 상태, 자료 완성도와 실행 상태를 하나의 범용 상태로 합성하지 않는다.

### 6. 장기 연구 프로그램을 폐기하고 작업 중심 구조로 전환

세션 초반에는 자기완결 연구 프로그램이 각자 작업대·브랜치·상태를 소유하고, 포트폴리오가 프로그램에 자원을 배정하는 구조를 검토했다.

사용자는 다음 근본 질문을 다시 열었다.

> 공용 작업대가 불완전한 결과도 정확한 상태로 보존할 수 있다면, 별도의 장기 프로그램 없이 모든 실행을 작업으로 분할하고 각 작업이 공용 작업대와 직접 상호작용할 수 있지 않은가?

이 재검토로 이전 프로그램 구조를 폐기했다.

확정한 현재 구조:

- 연구 프로그램은 실행·상태·작업대·DAG의 소유 단위가 아니다.
- 입력, 기대하는 연구 상태 변화, 산출물과 완료 기준이 닫힌 연구 작업이 연구 생산의 유일한 실행 단위다.
- 장기 연구 방향은 `F` 객체, 관련 작업·산출물의 관계와 파생 보기로 표현한다.
- 포트폴리오는 프로그램이 아니라 현재 착수 가능한 작업을 직접 선택한다.
- 작업은 공용 기준 판본에서 격리된 작업별 작업대를 사용하고, 종결 결과를 공용 작업대에 돌려준다.

프로그램 구조가 해결하려던 국소 변경 자유·중복 조정·의존 최신성은 작업별 격리, 공용 편입과 포트폴리오가 각각 맡는다.

### 7. 작업 DAG를 폐기하고 깊이 1 실행 껍질로 전환

작업 중심 구조를 확정한 뒤 사용자는 미래 작업을 DAG로 미리 보존할 필요가 있는지 다시 물었다.

확정한 내용:

- 작업 DAG를 사용하지 않는다.
- 실행 껍질의 깊이는 1로 고정한다.
- 실행 껍질은 현재 공용 작업대 판본에서 지금 착수할 수 있는 작업만 나타내는 파생 보기다.
- 미래에 수행할 수 있지만 조건이 충족되지 않은 일은 차단된 작업으로 만들지 않는다.
- 미래 가능성은 작업 씨앗과 `F`의 방향·조건으로 보존한다.
- 알려진 순차 절차도 미래 작업을 미리 만들지 않고, 현재 단계 결과가 다음 발생 조건을 충족할 때 다음 작업을 실행 껍질에 나타낸다.
- 완료 작업의 계보와 `F` 관계가 장기 연구 흐름을 보여 준다.
- 연구 반복은 비순환 그래프에 억지로 넣지 않고 반복 감지와 연구 진전 판정으로 통제한다.

이 결정으로 현행 이슈 본문에 있던 “단일 작업 DAG”도 작업 씨앗과 실행 껍질 구조로 교체했다.

### 8. 예상하지 못한 `U → F` 발견

사용자는 작업이 시작될 때 `F` 어디에도 없던 개념·아이디어·방향을 발견할 수 있다는 점을 지적했다.

확정한 표현:

- 작업의 착수 전 연결 목록은 열린 목록이다.
- 탐색 작업은 아직 모르는 결과 객체를 미리 가리키지 않는다.
- 탐색 영역·생성 방법·새 후보를 구별하는 기준과 기록 방법만 미리 명시한다.
- 작업 중 예상하지 못한 대상을 발견하면 작업별 작업대에 발견 후보로 기록한다.
- 발견 후보는 내용, 발견 과정, 기존 `F`와의 차이, 확인한 범위·남은 추측과 증거를 가진다.
- 공용 편입을 통과하면 새 핵심 기록 ID를 가진 `F` 객체가 된다.
- 기존 `F`와의 관계를 아직 확인하지 못했다면 생성 계보만 가진 독립 객체로 둘 수 있다.
- 이것은 `U → F`인 탐색이며, 인증과 Lean 정본 편입을 통한 `F → K` 프런티어 확장과 다르다.

### 9. 순차 절차의 작업 경계

깊이 1 실행 껍질에서는 순서가 명확한 절차를 단계마다 작업으로 쪼개면 작업 수가 과도하게 늘 수 있다는 문제가 제기됐다.

확정한 경계:

- 하나의 연구 상태 변화를 만들고 중간 결과를 독립적으로 배정·검증·재시도·취소·공용 편입할 실익이 없으면 여러 순차 단계를 한 작업의 내부 절차로 묶는다.
- 단계 수나 한 에이전트 세션보다 길다는 이유만으로 작업을 분할하지 않는다.
- 중간 결과를 다른 작업이 재사용하거나, 포트폴리오가 계속 여부를 다시 선택해야 하거나, 독립 역할·판정 권한·별도 재시도·외부 대기·병렬 수행이 필요하면 별도 작업으로 나눈다.
- 작업은 여러 작업 실행과 비공개 체크포인트에 걸쳐 재개할 수 있다.
- 반복할수록 질문이나 산출물이 바뀌면 같은 작업을 연장하지 않고 새 작업으로 분화한다.

실무 경계 질문은 다음과 같다.

> 이 단계를 별도로 배정·검증·재시도·취소·공용 편입할 합리적인 상황이 있는가?

### 10. 작업 하나당 종결 공용 편입 한 번

처음에는 작업 도중 독립적인 중간 결과를 공용 편입하는 구조를 추천했다. 사용자는 애초에 그런 결과가 예상된다면 작업이 처음부터 잘못 나뉜 것 아니냐고 지적했다.

이 교정으로 중간 공용 편입을 폐기했다.

확정한 내용:

- 하나의 연구 작업은 종결할 때 공용 편입을 한 번만 수행한다.
- 계획된 중간 산출물이 독립적인 공유 가치가 있으면 착수 전에 작업을 분할한다.
- 내부 체크포인트는 비공개이며 공용 작업대나 다른 작업의 입력이 아니다.
- 예상하지 못한 중요한 산출물을 즉시 공유해야 하면 현재 작업을 분할 종결한다.
- 현재까지의 결과를 종결 공용 편입하고, 남은 범위를 새 작업 씨앗으로 만든다.
- 한 작업의 종결 결과, 공용 편입과 공용 커밋을 일대일로 대응시키며 여러 작업 결과를 한 편입 커밋에 섞지 않는다.

### 11. 작업 씨앗의 생성 근거

사용자는 새 작업이 기존 작업 결과에서 자라나는 얇은 껍질 구조를 제안했다. 이를 엄격한 “부모 작업만 허용”으로 닫으면 초기화·외부 변화·빈 껍질 회복을 표현하지 못한다는 문제가 있었다.

확정한 네 생성 근거:

1. 연구 인스턴스 초기화
2. 작업 종결 공용 편입
3. 핵심 기록에 먼저 반영된 승인된 외부 변화
4. 목표 미해결·빈 실행 껍질에서 현재 `F`를 정련·탐색하는 생존 규칙

모든 작업 씨앗은 실제 생성 근거의 핵심 기록 ID와 공용 판본을 가리킨다. 포트폴리오는 작업 씨앗을 창작하지 않고, 착수 가능한 씨앗 가운데 실행할 대상을 선택한다.

### 12. 작업 씨앗과 연구 작업의 동일 ID

처음에는 씨앗을 실제 작업으로 “승급”하거나 새 객체를 만들 가능성이 있었다. 사용자는 ID와 판본의 역할을 명확히 확인했고, 별도 승급은 불필요하다고 확정했다.

현재 구조:

- 작업 씨앗은 안정된 하나의 핵심 기록 객체다.
- `작업 씨앗 ID + 공용 작업대 판본`에서 착수 가능성 판정을 계산한다.
- 통과하면 같은 ID가 실행 껍질에 나타난다.
- 포트폴리오가 선택하면 같은 ID에 작업 실행을 연다.
- 새 작업 ID, 승급 상태나 승급 커밋을 만들지 않는다.
- 선택 전에 공용 상태가 바뀌어 조건이 깨지면 실행 껍질에서 사라지지만 씨앗 자체는 `F`에 남는다.
- 실행을 시작하면 선택 당시 공용 판본을 기준으로 고정한다.

### 13. 네 작업 인터페이스

착수 가능성을 결정론적으로 계산하려면 정해진 인터페이스가 필요하다는 사용자의 지적에서 네 인터페이스를 확정했다.

- 작업 씨앗: 질문, 범위, 기대 상태 변화, 입력, 발생 조건, 산출물, 종결 기준, 관계·탐색 방향, 모델·도구·권한·자원 요구
- 착수 명세 검토: 특정 씨앗 판본에 대한 질문·범위·입력·산출물·완료 기준별 판정, 결함, 승인·판정 불가와 검토자 기록
- 작업 실행: 기준 판본, 작업자·점유, 실행 시도, 브랜치·worktree, 체크포인트·재개, 모델·도구·자원과 상태
- 작업 종결: 실제 수행 범위, 결과·한계, 산출물·증거, 발견 후보, `F` 변경, 새 작업 씨앗, 관계 효과와 정확한 공용 변경 묶음

씨앗 작성자와 다른 역할이 착수 명세를 검토한다. 씨앗의 의미가 바뀌면 이전 검토 승인은 새 판본에 사용할 수 없다.

### 14. 발생 조건식과 착수 가능성 판정

사용자는 조건을 정해진 인터페이스로 표현해야 결정론적으로 검사할 수 있다고 확인했다.

확정한 구조:

- 발생 조건은 판본화된 닫힌 선언형 연산자로 표현한다.
- 조건식은 해당 공용 작업대 판본의 핵심 기록만 읽는다.
- 임의 코드, 실시간 외부 상태와 새 수학 판단을 실행하지 않는다.
- 외부 사건은 먼저 핵심 기록에 반영한 뒤 조건식이 그 기록을 참조한다.
- 실시간 작업자 수나 예산은 발생 조건이 아니라 포트폴리오 선택의 입력이다.
- 조건 결과는 `참`, `거짓`, `평가 오류`를 구별한다.
- 거짓은 정상적인 미충족이고, 평가 오류는 알 수 없는 연산자·깨진 참조·자료형 오류 같은 인터페이스 결함이다.
- 평가 오류를 거짓으로 숨기지 않는다.

착수 가능성은 구조화된 기록에서 다음을 검사한다.

```text
씨앗 스키마 유효
∧ 현재 씨앗 판본의 착수 명세 검토 승인
∧ 발생 조건 참
∧ 필수 입력 존재
∧ 씨앗 활성
```

### 15. 인터페이스 물리 형식

저장소를 직접 확인한 결과 별도 의존성 파일이나 일반 YAML 검증 라이브러리는 없었고, 구조화 산출물과 Python 스크립트는 이미 표준 JSON을 사용하고 있었다.

확정한 형식:

- 네 작업 인터페이스의 기계 정본은 판본화된 JSON 스키마를 따르는 독립 UTF-8 JSON 문서다.
- 긴 산문, 문헌 판독, Lean 코드, 계산 자료와 증거는 별도 파일에 둔다.
- JSON은 경로와 무결성 정보만 참조하며 산출물 본문을 복제하지 않는다.
- 알 수 없는 필드·연산자·자료형을 조용히 무시하지 않는다.
- UTF-8, LF, 고정 들여쓰기, 결정론적인 키 순서와 파일 끝 개행을 사용한다.
- 같은 의미의 입력은 같은 JSON 바이트를 만든다.
- 구체적인 디렉터리와 파일명, JSON 스키마 검증 도구는 아직 미정이다.

root `CONTEXT.md`에는 JSON·Git 같은 구현명을 두지 않고, 구현 계약은 지도 컨텍스트 정본에만 둔다.

### 16. 공용 머리·Git 실행 ref·작업 브랜치의 분리

작업 실행 인터페이스를 어디에 저장할지 검토하면서 계약 충돌이 드러났다.

- 점유·실행 시작을 공용 머리에 기록하면 종결 전 공용 상태가 바뀐다.
- 작업 브랜치에만 기록하면 다른 실행이 현재 점유를 볼 수 없다.

확정한 해결:

- 공용 Git 머리는 공용 작업대 판본과 종결 공용 편입만 소유한다.
- `refs/do-math/claims/<연구 인스턴스 ID>/<작업 씨앗 ID>` 실행 ref가 작업 점유와 최신 실행·체크포인트 좌표를 가리킨다.
- 작업 브랜치와 worktree가 진행 중 실행 JSON, 체크포인트와 산출물을 소유한다.
- ref가 없을 때만 원자적으로 생성한 실행이 작업을 점유한다.
- 실행 껍질은 공용 커밋만으로 계산한다.
- 포트폴리오는 실행 껍질 계산 뒤 실행 ref를 확인해 이미 점유된 작업을 제외한다.
- 종결 공용 편입에서는 공용 머리 갱신과 실행 ref 제거를 기대값 기반의 원자적 ref 트랜잭션으로 묶는다.
- 기대 공용 머리나 실행 ref가 달라지면 전건을 적용하지 않는다.

Git이 연구 의미·우선순위·수학적 판정을 결정하는 것은 아니다. Git ref는 배타적 점유와 실행 좌표만 소유한다.

### 17. 시간 만료 대신 진단 우선 운영 점검

작업자가 사라지거나 오래 걸리는 경우를 처음에는 lease·heartbeat·fencing으로 자동 회수하는 방안을 검토했다.

사용자는 시간 초과만으로 인수하지 말고 별도 점검 작업이 실제 코드·내용·로그·상태를 읽어 원인과 현실적인 종료 가능성을 판정하자고 제안했다.

자동 lease 회수안은 채택하지 않았다.

확정한 현재 구조:

- 프로세스 소실, 응답·heartbeat 부재, 작업별 시간·진전 한계 `N` 초과, 반복 상태와 부분 종결 흔적은 점검 발동 조건이다.
- `N`은 모든 작업에 같은 값으로 강제하지 않고 작업별 예상 소요와 진전 신호에 맞춘다.
- 발동 조건은 실행 ref를 자동 만료·삭제하거나 점유를 넘기지 않는다.
- 운영 점검 실행은 연구 작업·`F`·실행 껍질·포트폴리오와 분리한다.
- 운영 점검은 실제 씨앗·기준 판본·실행 JSON·ref·브랜치·diff·미커밋 변경·체크포인트·로그·프로세스·자원·외부 도구와 코드 종료 조건을 직접 읽는다.
- 점검자는 원인, 실제 진전, 시간의 합리성, 교착·무한 반복·외부 대기 가능성, 현실적 종결 가능성, 유효 체크포인트와 부분 산출물 가치를 판정한다.
- 점검을 시작할 때 대상 실행 ref를 고정한다.
- 처분 적용 시 ref가 달라졌으면 점검 결과를 낡은 관찰로 기록하고 아무 처분도 적용하지 않는다.
- 대상 ref가 그대로이고 인수·중단 처분이 승인됐을 때만 ref 세대를 바꿔 기존 실행을 fencing한다.
- 운영 점검은 구조화된 JSON 근거와 처분 기록을 남기지만 연구 작업 종결 공용 편입을 가장하지 않는다.

## 아직 정본화되지 않은 현재 미결정

진단 우선 운영 점검까지는 확정돼 정본에 기록됐다. 다음 제안은 사용자가 아직 승인하거나 기각하지 않았다.

### 결정 주제

운영 점검자가 자기 점검 결과를 직접 확정·집행할 수 있는 범위.

### 현재 추천안

운영 점검자가 직접 확정할 수 있는 영향이 작은 처분:

- 현재 실행 계속
- 다음 점검 시각 지정
- 추가 로그나 체크포인트 요구
- 대상 실행 상태가 그사이 바뀌어 점검 결과가 낡았다는 무처분 판정

점검자와 다른 운영 처분 심사가 필요한 실행 변경:

- 기존 실행 fencing
- 다른 작업자의 체크포인트 인수
- 처음부터 재시작
- 작업 분할 종결
- 운영 실패 종결
- 자원 배정의 큰 변경

운영 처분 심사는 점검 보고서와 실제 원자료를 다시 대조한다. 승인 뒤에도 대상 실행 ref가 점검 당시 값과 같을 때만 처분을 원자적으로 적용한다.

사용자 개입 경계는 기존 계약을 유지한다. 처분이 연구 목적·신뢰 경계·외부 또는 비가역 상태를 바꾸거나 사용자 절충을 요구할 때만 상신한다. 근거가 충분한 단순 재시작이나 체크포인트 인수는 `do-math`가 자율 처리할 수 있다는 추천이다.

### 다음 세션의 첫 질문

먼저 다음을 분명히 설명한다.

- 지금 결정하는 것은 운영 점검의 진단 방법이 아니라 처분 승인 권한이다.
- 이 결정을 먼저 닫아야 운영 점검 JSON, 자동 처분과 상신 필드를 설계할 수 있다.
- 점검자가 고영향 처분까지 자기 승인하면 오진이 즉시 실행 중단으로 이어질 수 있다.
- 모든 처분에 별도 심사를 요구하면 단순 계속·재점검에도 불필요한 지연이 생긴다.

그 뒤 위 권한 분리를 확정할지 질문 하나만 한다. 사용자 답을 대신 정하거나, 승인 전에 정본 문면을 수정하지 않는다.

## 그다음에 보이는 미결정

첫 질문을 닫은 뒤에만 선행 관계를 다시 계산한다.

- 운영 점검 JSON의 정확한 스키마와 증거 좌표
- 작업별 시간·진전 한계와 점검 시점 산정
- 운영 점검 실행 자체의 점유·중단·재시도·실패 회수
- 작업 브랜치·worktree·실행 ref의 보관·회수·마이그레이션
- 네 작업 인터페이스의 디렉터리·파일명 배치
- JSON 스키마의 검증 정본과 구현 도구
- 공용 편입 검사, 기준 판본 대조와 충돌 처분
- 적응형 포트폴리오의 평가 축·집계·선택 규칙

이 목록은 닫힌 작업 순서가 아니다. 현재 답이 선행 관계를 바꾸면 다음 질문을 다시 정한다.

## 사용자 협업 방식

- 제1원리와 전체 작동 구조를 먼저 확정한 뒤 세부 기제를 도출한다.
- 질문 전에 현재 결정 주제와 지금 먼저 닫는 이유를 분명히 쓴다.
- 추천, 근거와 다른 선택이 바꾸는 결과를 구분한다.
- 결과를 바꾸는 질문은 한 번에 하나만 한다.
- 한 세션에서 이미 전문을 읽은 규약은 짧은 확인 답변마다 반복해 읽거나 출력하지 않는다.
- 더 단순하고 우수한 구조가 드러나면 이미 승인한 결정을 도그마로 보존하지 않는다. 바뀌는 범위와 하류 영향을 밝히고 다시 검토한다.
