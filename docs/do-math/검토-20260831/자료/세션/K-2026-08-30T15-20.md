이 handoff는 결정 경위와 재개 좌표를 보존한다. 아래 요약을 정확한 실행 계약 대신 사용하지 않는다.

## 이번 세션의 설계 전개

### 1. 운영 점검자와 운영 처분 심사의 권한을 분리

운영 점검자는 현재 실행 계속, 다음 점검 시각 지정, 추가 로그·체크포인트 요구와 낡은 관찰의 무처분처럼 실행 정체성·점유·종결을 바꾸지 않는 저영향 처분을 직접 확정한다.

기존 실행 fencing, 체크포인트 인수, 처음부터 재시작, 분할 종결, 운영 실패 종결과 중대한 자원 변경처럼 실행 정체성·점유·종결 또는 중대한 자원 배정을 바꾸는 처분은 점검자와 다른 운영 처분 심사를 거친다. 심사자는 보고서뿐 아니라 원자료를 다시 대조한다.

### 2. 점검 기록과 심사 기록을 분리

- 운영 점검 실행과 운영 처분 심사는 각각 변경 불가능한 개별 JSON 기록을 만든다.
- 저영향 직접 처분은 점검 기록에 남고 별도 심사 기록을 만들지 않는다.
- 고영향 처분의 심사는 정확한 점검 기록과 대상 실행 ref를 참조한다.
- 재점검·재심사는 기존 기록을 고치지 않고 새 기록을 만든다.
- 운영 처분 심사의 판정은 `승인·기각`으로 닫았다.
- 필수 원자료나 근거가 부족하면 세 번째 판정을 만들지 않고 실행 상태를 `심사 미완료`로 끝낸다. 미완료는 적용·대응·전례 관문을 열지 않으며 근거 보충 뒤 새 심사를 수행한다.

### 3. 심사 승인 뒤의 자율 적용을 전례 관문으로 교체

처음 확정했던 “심사 승인 뒤 필수 상신 사유가 없으면 자율 적용” 규칙은 사용자의 전례 제안으로 대체됐다. 심사 승인은 처분안의 타당성 판정일 뿐 적용 권한이 아니다.

- 승인된 처분은 적용 가능한 전례가 있어야 자동 적용한다.
- 전례가 없거나 적용 가능성을 확정할 수 없으면 사용자에게 상신한다.
- 사용자가 승인하면 현재 결정과 사례가 새 적용 전례가 된다.
- 사용자가 반려하면 `대응` 경로로 들어간다.
- 적용 가능한 전례는 목적·신뢰 경계·외부·비가역 효과·사용자 절충에 관한 상신도 전례가 위임한 범위에서 생략할 수 있다.
- 전례에 따른 자동 적용은 새 전례를 만들지 않는다.

### 4. `재처분`을 폐기하고 `대응`을 확정

사용자는 기각 뒤 반드시 새 처분안을 만드는 것이 아니라, 사소한 결함을 고쳐 적용하거나 새 처분안을 만들거나 더 넓은 작업을 여는 등 실제로 필요한 후속 경로 전체를 뜻한다고 정정했다.

> 기각된 처분에 대해 정확히 어떠한 대응을 할 것인가.

현행 `대응`은 운영 처분안이 심사에서 기각되거나 상신 뒤 사용자에게 반려됐을 때 사례를 다음 상태로 옮기고 후속 행위를 정하는 실행 계약이다. 대응 자체와 실제 수행인 대응 실행을 구별한다.

### 5. 사용자 결정 사례를 전례로 삼고 음성 사례를 함께 축적

- 전례는 추상 규칙이 아니라 사용자 결정과 그 결정이 내려진 실제 사례를 함께 보존한 사례 기반 위임이다.
- AI는 전례 생성 시 일반 적용 규칙을 창작하지 않는다. 사용자가 명시한 일반 적용·제외 조건만 추가한다.
- 전례 적용 판정으로 하나의 자동 결정을 확정할 수 없으면 사용자에게 상신한다.
- 사용자의 새 결정과 현재 사례는 새 전례가 된다.
- 사용자가 명시적으로 배제한 기존 후보에만 `전례 비적용 관계`를 만든다. 다른 결정을 골랐다는 사실만으로 모든 후보를 배제하지 않는다.
- 비적용 관계의 기본 범위는 현재 사례 하나다. 일반 제외 조건은 사용자가 직접 명시할 때만 만든다.

### 6. 형식 검사를 단방향 배제 필터로 제한

사용자는 형식 검사의 역할을 다음처럼 확정했다.

> 의미론적 판단 없이도 무조건 매우 확실하게 속하지 않는다고 판단할 수 있는 전례들을 배제하는 필터

따라서 형식 검사는 명시된 구조화 사실과 닫힌 결정 절차만으로 확실하게 적용 불가능한 전례만 제거한다. 통과는 유사성이나 적용 가능성을 뜻하지 않는다. 확실히 배제할 수 없는 후보는 AI의 전례 적용 판정으로 넘긴다. 평가 오류를 적용 불가로 바꾸지 않는다.

### 7. 전례 적용 판정을 비대칭 이중 판정으로 확정

- 전례마다 독립 1차 판정을 수행한다.
- 1차가 `적용 불가` 또는 `판정 불가`이면 그 결과가 최종이고 2차를 열지 않는다.
- 1차가 `적용 가능`일 때만 독립 2차가 같은 원자료를 새 컨텍스트에서 다시 판정한다.
- 둘 다 적용 가능일 때만 최종 적용 가능이다.
- 결과가 다르거나 2차가 판정 불가이면 별도 충돌 상태를 만들지 않고 최종 `판정 불가`로 처리한다.
- 판정자는 같은 사례의 운영 점검자·운영 처분 심사자와 역할을 겸임하지 않고 다른 판정을 보기 전에 자기 결과를 봉인한다.
- 1·2차 판정자는 각각 별도의 `gpt-5.6-sol high` 에이전트다. 형식 검사는 결정론적 검사기가 수행한다.

### 8. 전례를 원자료 봉인으로 자동 활성화

사용자는 AI가 전례를 다시 서술하고 별도 인증을 요청하는 절차 대신 다음 방향을 확정했다.

> 따로 사용자에게 다시 어떻게 전례로서 기록될 것인지 인증 받을 필요 없는 형식으로 전례를 바로 작성해 보관

`do-math`는 현재 사례, 점검·심사·처분안 또는 대응의 좌표, 사용자에게 제시한 질문·선택지, 사용자 답변과 당시 근거를 의미 추가 없이 기계적으로 봉인한다. 질문과 답변을 함께 읽어도 결정이 모호하면 전례 인증을 묻는 것이 아니라 같은 결정 대화에서 원래 결정을 명확히 한다. 스키마·참조·무결성 검사를 통과하면 전례와 사용자가 명시한 비적용 관계를 자동 활성화한다. 검색 태그·요약은 권한 없는 파생 보기다.

### 9. 전례의 대체·폐기와 실행 직전 재검사

- 전례는 제자리에서 수정하지 않는다.
- 교정은 새 전례와 대체 관계를 만들고, 철회는 폐기 기록을 만든다.
- 대체·폐기된 전례는 미래 후보에서 제외하지만 원자료와 과거 효력 이력을 보존한다.
- 효력 변경은 과거 자동 적용을 소급해 무효화하지 않는다. 과거 적용의 문제는 별도 운영 점검과 대응으로 처리한다.
- 형식 검사와 전례 적용 판정은 시작 공용 커밋과 활성 전례·비적용·대체·폐기 집합에 결박한다.
- 자동 적용 또는 대응 실행 직전에 같은 집합과 관련 실행 ref가 현재인지 다시 검사한다. 바뀌었으면 기존 판정을 낡은 판정으로 보존하고 새 판본에서 다시 수행한다.

## 대체됐거나 복원하면 안 되는 제안

- 심사 승인 뒤 전례 없이 자율 적용하는 규칙은 폐기됐다.
- 목적·신뢰 경계·외부·비가역 효과·사용자 절충은 어떤 경우에도 반드시 다시 상신한다는 규칙도 폐기됐다. 적용 가능한 전례가 위임한 범위에서는 생략할 수 있다.
- `재처분`은 현행 용어가 아니다. `대응`을 사용한다.
- 형식 검사를 엄격한 동일성·유사성 판정으로 만들지 않는다.
- 전례 적용 판정 결과 불일치를 별도 충돌 상태로 만들지 않는다. 최종 판정 불가다.
- 전례를 `gpt-5.6-sol max`로 판정하지 않는다. 현행 역할은 독립된 `gpt-5.6-sol high`다.
- 사용자 결정 뒤 전례 문면을 별도로 재승인받지 않는다. 원자료 봉인과 기계 검사를 사용한다.
- 기존 전례나 심사 기록을 제자리에서 수정하지 않는다.

## 현재 미결정과 다음 질문

가장 가까운 미결정은 **작업별 시간·진전 한계의 성격과 고정 시점**이다. 다음 제안은 아직 사용자에게 승인되거나 기각되지 않았다.

> 작업별 시간·진전 한계를 마감이 아니라 판본화된 점검 발동 계약으로 둔다. 작업 씨앗은 예상 소요, 관찰 가능한 진전 신호, 무진전 한계와 외부 대기 조건을 제안하고 착수 명세 검토가 점검 가능성을 확인한다. 작업 실행을 열 때 해당 실행의 계약을 고정한다. 모든 작업에 같은 한계를 적용하지 않는다. 완료 시간을 예측하기 어려운 작업도 다음 관찰 시점이나 사건 기반 진전 신호를 명시한다. 한계 초과는 운영 점검만 발동한다. 점검자가 계속을 결정하면 다음 점검 시점과 필요한 진전 신호를 새 불변 기록으로 추가하고 기존 계약은 수정하지 않는다.

다음 세션은 이 결정 영역, 지금 먼저 닫는 이유와 답이 바꿀 후속 계약을 설명한 뒤 위 제안을 확정할지 질문 하나만 한다. 사용자의 답을 대신 정본화하지 않는다.

그 뒤에 보이는 미결정은 다음과 같다. 이 목록은 닫힌 순서가 아니며 현재 답에 따라 선행 관계를 다시 계산한다.

- 운영 점검 JSON의 정확한 스키마와 증거 좌표
- 작업별 점검 시점 산정과 발동 계약의 갱신 형식
- 운영 점검 실행 자체의 점유·중단·재시도·실패 회수
- 형식 검사의 닫힌 연산자와 평가 오류 복구
- 전례 적용 판정의 세부 기준과 여러 전례 결과의 양립성 판정
- 전례·비적용·대체·폐기 기록의 정확한 스키마
- 작업 브랜치·worktree·실행 ref의 보관·회수·마이그레이션
- 네 작업 인터페이스의 디렉터리·파일명과 JSON 스키마 검증 도구
- 공용 편입 검사, 기준 판본 대조와 충돌 처분
- 적응형 포트폴리오의 평가 축·집계·선택 규칙

## 사용자 협업 방식

- 제1원리와 전체 작동 구조를 먼저 확정한 뒤 세부 기제를 도출한다.
- 질문 전에 현재 결정 영역, 지금 먼저 닫는 이유와 답이 바꾸는 하류 계약을 설명한다.
- 기술적 추천과 사용자 결정을 구분한다.
- 결과를 바꾸는 질문은 한 번에 하나만 한다.
- 확정된 결정은 `CONTEXT.md`와 지도 컨텍스트 정본에 즉시 반영하고 `git diff --check`로 검증한다.
- 문서는 읽기 전에 크기를 확인하고, 큰 문서는 출력 누락을 검증하며 분할해 전문을 읽는다.
- 이 연속 작업에서는 `기억/`을 별도로 읽지 않는다.
- 짧은 확인 답변마다 이미 읽은 스킬과 참조 전문을 반복 적재하지 않는다.
- 예시 열거를 문언과 맥락의 근거 없이 닫힌 목록으로 축소하지 않는다.

## 범위와 금지

- 현재 티켓은 `docs/do-math/통합-설계.md`와 테스트 벡터를 확정하는 설계 작업이다.
- 후행 구현을 시작하지 않는다.
- 진행 티켓을 닫거나 지도 `Decisions so far`를 갱신하지 않는다.
- 현재 미커밋 두 파일을 되돌리거나 덮어쓰지 않는다.
- 커밋·푸시를 수행하지 않는다. 티켓 종료 커밋을 수행할 때만 `commit-harness`를 먼저 적용한다.
- 과거 handoff의 대체된 프로그램·DAG·전례 이전 자율 적용 구조를 복원하지 않는다.

## Suggested skills

- `wayfinder` — 지도와 진행 티켓을 적재하고 점유·해결 절차를 지킨다.
- `grilling` — 결과를 바꾸는 사용자 결정을 한 번에 하나씩 확정한다.
- `domain-modeling` — 운영 점검, 전례, 대응, 판정과 효력 관계의 경계를 유지하고 확정 즉시 용어 정본을 갱신한다.
- `write-for-reader` — 독립 설계 문서와 AI가 판단·행동할 계약을 작성·퇴고한다.

### 운영 처분 권한에서 전례 관문으로

운영 점검자의 저영향 직접 처분과 별도 운영 처분 심사가 필요한 고영향 처분을 먼저 분리했다. 그 뒤 사용자는 심사 승인만으로 자율 적용하는 구조를 전례 관문으로 교체했다. 현행 심사 승인은 처분안의 타당성 판정일 뿐 적용 권한이 아니다. 적용 가능한 전례가 없으면 사용자에게 상신하고, 사용자 결정과 실제 사례가 새 전례가 된다.

운영 처분 심사의 판정은 `승인·기각`이다. 원자료나 근거가 부족하면 세 번째 판정을 만들지 않고 실행 상태를 `심사 미완료`로 끝낸다. 미완료는 적용·대응·전례 관문을 열지 않는다.

### `재처분`에서 `대응`으로

사용자는 기각 뒤 반드시 다른 처분안을 만든다는 해석을 거부하고 다음 의미를 확정했다.

> 기각된 처분에 대해 정확히 어떠한 대응을 할 것인가.

현행 `대응`은 기각 또는 사용자 반려 뒤 사례를 다음 상태로 옮기고 후속 행위를 정하는 실행 계약이다. 사소한 결함의 수정·적용, 새 처분안, 추가 작업이나 더 넓은 조치 등을 포함할 수 있으며 이 예시는 닫힌 목록이 아니다.

### 사례 기반 전례와 음성 사례

전례는 AI가 만든 추상 규칙이 아니라 사용자 결정과 그 결정이 내려진 실제 사례를 함께 보존한 사례 기반 위임이다. 자동 적용·대응은 새 전례를 만들지 않는다.

여러 전례에서 자동 결정을 확정할 수 없으면 사용자에게 상신한다. 사용자 결정은 새 전례가 된다. 사용자가 명시적으로 배제한 기존 후보에만 `전례 비적용 관계`를 만든다. 다른 결정을 골랐다는 사실만으로 모든 후보를 배제하거나 한 음성 사례를 일반 제외 조건으로 확장하지 않는다.

### 형식 검사와 AI 판정의 경계

사용자는 형식 검사의 역할을 다음처럼 확정했다.

> 의미론적 판단 없이도 무조건 매우 확실하게 속하지 않는다고 판단할 수 있는 전례들을 배제하는 필터

따라서 형식 검사는 확실하게 적용 불가능한 전례만 제거하는 단방향 필터다. 통과는 유사성이나 적용 가능성을 뜻하지 않는다. 남은 후보는 독립된 AI의 전례 적용 판정으로 보낸다.

전례 적용 판정은 `적용 가능·적용 불가·판정 불가`다. 1차가 적용 가능일 때만 독립 2차를 수행하고 둘 다 적용 가능일 때만 최종 적용 가능이다. 결과가 다르면 별도 충돌 상태가 아니라 최종 판정 불가다. 두 판정자는 각각 별도의 `gpt-5.6-sol high` 에이전트이며 운영 점검·운영 처분 심사 역할과 겸임하지 않는다. 형식 검사는 결정론적 검사기가 수행한다.

### 전례 원자료 봉인과 효력 변경

사용자는 별도의 전례 문면 인증을 추가하지 않는 방향을 확정했다.

> 따로 사용자에게 다시 어떻게 전례로서 기록될 것인지 인증 받을 필요 없는 형식으로 전례를 바로 작성해 보관

`do-math`는 사례 원자료, 사용자에게 제시한 결정 문면과 답변을 의미 추가 없이 기계적으로 봉인한다. 원래 결정이 모호할 때만 같은 결정 대화에서 명확히 한다. 스키마·참조·무결성 검사를 통과하면 전례와 사용자가 명시한 비적용 관계를 자동 활성화한다. AI 요약·태그는 권한 없는 파생 보기다.

전례는 제자리에서 수정하지 않는다. 교정은 새 전례와 대체 관계, 철회는 폐기 기록으로 남긴다. 효력 변경은 과거 적용을 소급해 무효화하지 않는다. 자동 적용 직전에 활성 전례·비적용·대체·폐기 집합과 관련 실행 ref를 다시 확인하고, 바뀌었으면 기존 판정을 낡은 이력으로 보존한 뒤 새 판본에서 다시 판정한다.

## 이번 세션에서 결정 경계가 바뀐 과정

### 1. 운영 점검자의 진단과 처분 승인 권한을 분리

이번 세션은 앞선 handoff가 남긴 “운영 점검자가 자기 진단에 따른 처분을 어디까지 직접 확정할 수 있는가”에서 시작했다. 첫 추천은 점검자가 영향이 작은 처분을 직접 확정하고 실행의 정체성·점유·종결을 바꾸는 처분은 별도 역할이 심사하도록 분리하는 것이었다. 사용자는 이 추천을 확정했다.

현행 구조에서 점검자는 현재 실행 계속, 다음 점검 시각 지정, 추가 로그나 체크포인트 요구와 관찰 대상 ref가 이미 달라졌다는 무처분처럼 실행 자체를 바꾸지 않는 처분을 직접 확정한다. 기존 실행 fencing, 다른 작업자의 체크포인트 인수, 처음부터 재시작, 분할 종결, 운영 실패 종결과 중대한 자원 변경처럼 실행 정체성·점유·종결 또는 중대한 자원 배정을 바꾸는 처분은 점검자와 다른 **운영 처분 심사**를 거친다. 심사자는 점검 요약을 승인하는 역할이 아니라 점검 기록이 가리키는 원자료를 다시 대조하는 역할이다.

이 분리는 오진 하나가 곧바로 실행 중단이나 점유 이전으로 이어지는 것을 막되, 단순 계속·재점검까지 불필요한 심사로 지연하지 않으려는 결정이다.

### 2. 운영 점검과 운영 처분 심사의 기록·판정을 분리

권한을 분리한 뒤에는 두 역할이 같은 가변 기록을 수정하면 책임과 판정 이력이 섞인다는 문제가 드러났다. 사용자는 다음 기록 경계를 차례로 확정했다.

- 운영 점검 실행 하나는 변경 불가능한 점검 기록 하나를 만든다.
- 저영향 직접 처분은 점검 기록에 남는다.
- 고영향 처분의 운영 처분 심사는 정확한 점검 기록과 대상 실행 ref를 참조하는 별도 불변 기록을 만든다.
- 재점검과 재심사는 기존 기록을 고치지 않고 새 기록을 만든다.

사용자는 심사의 판정 어휘를 `승인·기각`으로 닫았다. 다만 필수 원자료를 읽지 못했거나 근거가 부족한 상황에서 억지로 둘 중 하나를 고르는 것은 이 이분법의 의미를 훼손한다. 이를 해소하기 위해 판정과 심사 실행 상태를 분리했다. 근거가 부족하면 판정을 내리지 않고 실행 상태를 **심사 미완료**로 끝낸다. 심사 미완료는 세 번째 판정도, 기각도 아니며 처분 적용·대응·전례 관문을 열지 않는다. 부족한 근거를 보충한 뒤 새 심사 기록을 만든다.

### 3. 승인 뒤 자율 적용 규칙을 사용자 유래 전례 체계로 교체

권한 분리 직후의 추천은 고영향 처분이 심사에서 승인되고 기존 사용자 개입 경계에 해당하지 않으면 `do-math`가 적용하는 구조였다. 사용자는 이를 더 보수적이면서도 경험에 따라 자율 범위가 커지는 전례 체계로 다시 열었다.

사용자의 핵심 제안은 다음과 같았다.

> 판정은 승인, 기각으로 하고. 이후 어느 방향으로 그 판정에 따라 어느 결정이 내려지게 되는지가 '전례'에 의해 결정되는거지. 만약 승인일 경우 결정은 적용 혹은 상신이 되고. 적용은 오직 그와 충분히 유사하다 판단되는 처분이 이미 승인 후 적용된 전례가 존재하는 경우 자동으로 되고, 이 경우 이는 전례로 기능하지 못해. 만약 그러한 전례가 없는 경우 이는 상신이 되고 사용자에 의해 승인 혹은 반려가 될 때까지 적용이 미루어지게 돼.

이 제안으로 심사 승인의 의미를 처분안의 타당성 판정으로 한정했다. 승인은 그 자체로 적용 권한을 만들지 않는다. 승인된 처분은 적용 가능한 **적용 전례**가 있을 때만 자동 적용한다. 전례가 없거나 적용 가능성을 확정하지 못하면 사용자에게 상신한다. 사용자가 승인하면 현재 결정과 실제 사례가 새 전례가 되고, 사용자가 반려하면 후술한 `대응` 경로로 들어간다. 기존 전례를 따라 자동 적용한 사례는 새 전례를 만들지 않으므로 자동화가 자기 결과를 근거로 권한 범위를 연쇄 확장하지 못한다.

처음에는 연구 목적·신뢰 경계·외부·비가역 효과·사용자 절충에 해당하면 전례와 무관하게 다시 상신하는 예외를 남겼다. 사용자는 적용 가능한 전례가 있으면 이 상신도 생략할 수 있게 하자고 제안했다. 최종적으로 전례는 단순한 과거 기록이 아니라, 보존된 사례와 의미론적으로 유사한 미래 사례에 사용자의 결정을 재사용할 수 있게 하는 범위 한정 위임이 됐다. 현재 사례가 전례 사례와 중대한 차이가 없고 사용자가 명시한 추가 조건을 충족할 때는 네 사용자 개입 범주도 전례로 넘을 수 있다.

### 4. `재처분`이라는 좁은 모형을 버리고 `대응`을 확정

초기 전례 흐름은 기각 뒤 “재처분”을 선택하는 것으로 표현했다. 사용자는 이 표현이 다음 행동을 또 하나의 처분안으로 좁힌다고 지적하고 의도를 다시 설명했다.

> 재처분이란 표현이 지금 보니 부적절했던 것 같아. 재처분이 아니라, 무슨 용어가 적절할진 모르겠지만 그 의미는 이런 것인걸로 하자. 기각된 처분에 대해 정확히 어떠한 대응을 할 것인가. 예를 들어 그냥 기각 사유와 함께 다시 새로 운영 처분을 작업으로 만들기만 할 것인가. 아니면 그냥 사소한 문제만 바로 수정하고 적용할 것인가. 아니면 보다 근본적이고 더 큰 범위에서의 다른 대응이 필요한 것인가. 등등.

사용자는 최종 용어를 짧게 `대응`으로 정했다. 대응은 운영 처분안이 심사에서 기각되거나, 심사 승인을 받았지만 상신 뒤 사용자에게 반려됐을 때 해당 사례를 다음 상태로 옮기고 후속 행위를 정하는 권위 있는 실행 계약이다. 대응은 한정된 결함을 고쳐 적용하거나, 새 처분안을 만들거나, 추가 점검·작업을 열거나, 더 근본적이고 넓은 조치를 선택하거나, 아무 처분도 적용하지 않는 경로를 표현할 수 있다. 이 예시는 닫힌 목록이 아니다. 대응이라는 계약과 그 계약을 실제로 수행하는 대응 실행은 구별한다.

### 5. 사례 전례와 전례 비적용 관계로 양성·음성 경계를 함께 축적

처음에는 여러 적용 가능한 전례가 서로 다른 결정을 지시하거나 판정 불가가 남으면 단순히 사용자에게 상신하고 끝내는 방안을 제안했다. 사용자는 상신 결과를 다음 유사 사례의 경계 학습에도 사용하자고 제안했다.

> 이러한 경우 사용자에게 상신을 하고, 사용자가 내린 결정을 새로운 전례로, 그리고 선택된 전례들에는 이러한 처분에 대해서는 이 전례가 대응하지 않는다는 추가 정보를 붙여 기록하는 식으로 처리하는게 어떨까?

`대응`이 이미 별도 용어가 됐으므로 기존 전례가 현재 사례에 권한을 주지 않는 관계는 **전례 비적용 관계**로 이름 붙였다. 사용자 상신 뒤 현재 결정과 실제 사례는 새 전례가 된다. 기존 후보 가운데 사용자가 현재 사례에 적용되지 않는다고 명시한 후보에만 비적용 관계를 추가한다. 사용자가 다른 결정을 골랐다는 사실만으로 나머지 전례도 부적합하다고 추론하지 않는다. 여러 전례가 동시에 타당할 수 있기 때문이다.

비적용 관계는 기존 전례를 수정하지 않고 기존 전례·현재 사례·처분안 또는 대응·비적용 사유·사용자 결정 좌표를 잇는 별도 불변 기록이다. 기본 범위는 현재 사례 하나다. AI는 한 음성 사례에서 일반 제외 규칙을 창작하지 않는다. 사용자가 일반 제외 조건을 직접 명시할 때만 그 범위를 넓힌다.

### 6. 전례를 추상 규칙이 아니라 실제 사용자 결정 사례로 고정

전례가 미래 자동 적용 권한을 주려면 사용자 결정에서 일반 범위를 어떻게 뽑을지가 문제가 됐다. AI가 한 사례를 보고 “앞으로 모든 X에 적용한다”는 규칙을 만들면 사용자가 부여하지 않은 권한이 생긴다. 사용자는 기본 전례를 실제 사례 자체로 두는 방향을 확정했다.

새 전례는 사용자 결정, 그 결정을 받은 질문과 선택지, 당시 사례의 사실·처분안 또는 대응·효과·근거를 함께 보존한다. 전례의 기본 범위는 이 실제 사례다. 미래 사례에서는 형식 검사와 AI의 의미론적 전례 적용 판정으로 유사성을 판단한다. 일반 적용 조건과 일반 제외 조건은 사용자가 명시할 수 있지만 AI가 전례 생성 시 임의로 만들지 않는다.

이 구조에서 전례는 단순한 과거 사례가 아니다. 사용자가 이 체계에서 결정을 내리면 그 실제 사례와 의미론적으로 유사한 미래 사례에 그 결정을 재사용하도록 위임한다는 의미를 함께 가진다.

### 7. 형식 검사의 역할을 유사성 판정이 아닌 단방향 배제 필터로 축소

전례 적용을 형식 검사와 AI 판단으로 나누는 초안에서는 형식 검사가 전례의 효과 범위·제외 조건·입력 충분성까지 확인한다고 표현했다. 사용자는 그 가운데 의미론적 판단 없이 실제로 확인할 수 있는 것이 무엇인지 물었다. 검토 결과, 구조화된 필드의 존재·자료형·참조·닫힌 조건식은 기계적으로 검사할 수 있지만, 실제 효과가 빠짐없이 기록됐는지, 자연어 제외 조건이 현재 사례에 해당하는지, 근거가 의미상 충분한지는 AI 판단 없이는 확인할 수 없다는 점을 분리했다.

그 뒤 사용자는 형식 검사의 역할을 다음 한 방향으로 확정했다.

> 의미론적 판단 없이도 무조건 매우 확실하게 속하지 않는다고 판단할 수 있는 전례들을 배제하는 필터

현행 형식 검사는 명시된 구조화 사실과 닫힌 결정 절차만으로 현재 사례에 적용될 수 없다고 확실하게 판정할 수 있는 전례만 제거한다. 통과는 유사성이나 적용 가능성을 뜻하지 않는다. 확실히 배제할 수 없는 후보는 모두 AI 판단으로 넘긴다. 입력 누락·알 수 없는 연산자·깨진 참조 같은 평가 오류도 적용 불가로 바꾸지 않는다. 형식 검사의 구체 연산자와 평가 오류 복구는 아직 미정이다.

### 8. AI 전례 적용 판정을 독립된 비대칭 이중 판정으로 구성

형식 검사를 통과한 각 전례는 현재 사례와 전례 원자료를 직접 대조하는 **전례 적용 판정**으로 간다. 판정은 `적용 가능·적용 불가·판정 불가`로 닫았다. 적용 가능은 사용자 결정을 바꿀 중대한 차이가 없고 권한 범위와 검증 조건 안임을 확인한 결과다. 적용 불가는 중대한 차이나 범위 이탈을 확인한 결과다. 판정 불가는 사실이나 근거가 부족해 어느 쪽도 확인하지 못한 결과다.

같은 에이전트가 처분의 타당성을 승인하고 그 처분을 자동 적용할 권한까지 판단하지 못하도록 전례 적용 판정자는 운영 점검자·운영 처분 심사자와 다른 역할로 분리했다. 판정자는 다른 판정 결과와 현재 사례에 대한 미래 사용자 결정을 보기 전에 자기 기록을 봉인한다.

판정 기수는 모든 후보를 무조건 두 번 판단하는 대칭 구조가 아니다. 1차가 적용 불가 또는 판정 불가이면 그 결과를 최종으로 두고 2차를 열지 않는다. 자동 권한을 여는 1차 적용 가능에만 독립된 2차를 붙인다. 두 판정이 모두 적용 가능일 때만 최종 적용 가능이다. 사용자는 두 결과가 다를 때 별도 충돌 상태를 만들지 말고 다른 판정 불가와 똑같이 처리하자고 정했다.

처음에는 두 판정자에 `gpt-5.6-sol max`를 추천했지만 사용자는 `high`를 제안했다. 이 판단은 새로운 수학 생산이 아니라 제한된 두 사례의 효과·근거·권한 범위를 대조하는 운영 의미 판정이고, 독립 이중 판정과 보수적인 판정 불가 경로가 있으므로 최종 모델은 1·2차 모두 별도의 `gpt-5.6-sol high`로 확정했다. 형식 검사는 AI가 아니라 결정론적 검사기가 수행한다.

### 9. 별도 사용자 인증 없이 원자료 봉인으로 전례를 자동 활성화

사례 전례를 만들 때 AI가 구조화한 전례 문면을 사용자에게 다시 확인받는 방안을 한때 추천했다. 사용자는 이미 내린 결정을 전례로 기록하기 위해 별도 인증을 반복하지 않는 방법을 요구했다.

> 따로 사용자에게 다시 어떻게 전례로서 기록될 것인지 인증 받을 필요 없는 형식으로 전례를 바로 작성해 보관하는 방법은 없을까?

이를 위해 전례를 AI가 다시 서술한 문서가 아니라 원자료를 기계적으로 봉인한 묶음으로 만들었다. 묶음은 현재 사례, 운영 점검·심사·처분안 또는 대응의 정확한 좌표, 사용자에게 제시한 질문과 선택지, 사용자 답변, 당시 이미 기록된 효과·근거와 관련 전례를 보존하거나 참조한다. 문맥 의존적인 “그렇게 하자” 같은 답도 그 답이 가리키는 질문 전문과 함께 봉인한다.

기계적 생성은 스키마 조립, 참조 연결과 무결성 계산만 수행하며 사용자 결정을 요약·확장·일반화하지 않는다. 질문과 답변을 함께 읽어도 결정이 모호하면 전례 문면을 인증받는 것이 아니라 같은 결정 대화에서 원래 결정을 명확히 한다. 결정이 명확하고 스키마·참조·무결성 검사를 통과하면 별도 확인 없이 전례와 사용자가 명시한 비적용 관계를 활성화한다. AI 검색 태그·특징·요약은 원자료에서 재생성하는 비권위 파생 보기이며 권한을 넓히거나 자동 적용을 승인할 수 없다.

### 10. 전례 효력 변경과 실행 직전 재검사

전례와 비적용 관계가 축적되면 판정 도중 사용자가 전례를 교정·철회하는 경합을 처리해야 한다. 사용자는 불변 이력 방식을 확정했다.

전례는 제자리에서 수정하지 않는다. 교정은 교정된 새 전례와 기존 전례의 대체 관계를 만들고 기존 전례를 미래 후보에서 제외한다. 철회는 폐기 기록을 만들고 기존 전례를 미래 후보에서 제외한다. 기존 전례의 원자료와 과거 효력 이력은 삭제하지 않는다.

대체·폐기는 과거 자동 적용을 소급해 무효화하지 않는다. 과거 적용이 잘못됐다고 판단하면 별도 운영 점검과 대응으로 실제 영향을 조사한다. 형식 검사와 전례 적용 판정은 시작 공용 커밋의 활성 전례·비적용·대체·폐기 집합에 결박한다. 자동 적용 또는 대응 실행 직전에 같은 집합과 관련 실행 ref가 현재인지 다시 확인한다. 바뀌었으면 기존 판정은 낡은 판정 이력으로 보존하되 적용하지 않고 새 판본에서 다시 수행한다.
