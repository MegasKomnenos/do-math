설계는 다음 결정을 불변 입력으로 사용한다.

- 수학 내용의 정본은 Lean이다.
- Lean 정본에는 승인된 기초 프로필, 인증된 보존적 정의와 입증·반증 결과만 들어간다.
- 활성 기초 프로필은 하나다.
- 공리 허용 목록은 `{propext, Quot.sound, Classical.choice}`다.
- 고정된 Mathlib 판본을 초기 Lean 정본 기반으로 수용한다.
- 연구 작업공간, Lean 형식화 작업공간과 Lean 정본을 분리한다.
- 작업 DAG를 사용하지 않는다. 깊이 1 실행 껍질은 특정 공용 판본에서 지금 착수 가능한 `task_id`만 나타내는 파생 보기이며, 미래 가능성은 `F`와 작업 씨앗에 보존한다.
- 공용 머리는 종결 공용 편입만 소유하고, 작업 브랜치는 실제 연구 내용과 체크포인트를 소유한다. `refs/do-math/runs/<연구 인스턴스 ID>/<작업 ID>` 실행 ref는 `state.json` 하나와 직전 상태 하나의 부모 관계를 가진 현재 실행 상태 커밋을 가리킨다. 커밋 OID는 불투명한 상태 세대 식별자이자 예상 상태 토큰이며 작업자와 확정된 운영 처분 실행은 `git update-ref <ref> <new> <old>` 조건부 갱신만 사용한다. 이 계약은 같은 공통 Git 객체·ref 데이터베이스 안에서 성립한다.
- 메인 세션이 파견하는 모든 하위 AI 실행은 연구 작업자뿐 아니라 포트폴리오 선택자, 동일성 검토자·이의 심사자·부분 전문 검토자와 운영 판단 역할까지 고유 `execution_id`의 Windows Job Object 안에서 돈다. 결정론적 중앙 프로세스 감독기가 Job Object handle을 물리적으로 보유한다. 루트 프로세스는 일시 정지 상태로 생성해 Job Object 설정·편입과 권위 있는 실행 허가 공개를 마친 뒤에만 재개하며, breakaway를 허용하지 않고 `KILL_ON_JOB_CLOSE`를 사용한다.
- 외부 감시기의 정상 관찰 입력은 현재 실행 ref가 가리키며 스키마·참조·무결성 검사를 통과한 변경 불가능한 작업자 공개 상태뿐이다. 미커밋 worktree와 부분 기록은 정상 관찰 입력이 아니지만 운영 점검 AI는 이상 진단을 위해 직접 읽을 수 있다. `state.json`의 OID 문자열은 작업 커밋을 보존하지 않으므로 활성 작업 브랜치 ref가 작업 이력의 도달 가능성을 별도로 보존한다.
- 종결 뒤 실행 상태·원 작업·임시 편입·monitor 이력을 각각 `refs/do-math/archive/runs/<인스턴스>/<작업>/<실행>`, `refs/do-math/archive/work/<인스턴스>/<작업>/<실행>`, `refs/do-math/archive/integration/<인스턴스>/<작업>/<실행>`, `refs/do-math/archive/monitor/<인스턴스>/<작업>/<실행>`에서 불변으로 보존한다. 인증 기록이 있으면 `refs/do-math/archive/certification/<인스턴스>/<작업>/<제안>`도 같은 종결 트랜잭션에서 불변으로 보존한다. 자동 만료로 삭제하지 않으며 삭제·압축은 별도 보존 정책이나 사용자 승인을 요구한다.
- 작업 종결 시 원 작업 브랜치를 동결하고 그 머리에서 임시 편입 브랜치를 만든 뒤 최신 공용 머리를 merge해 충돌과 현행 스키마·무결성·Lean·인증 기준을 재검증한다. 통과한 최종 트리로 현재 공용 머리 하나만 부모로 갖는 작업 전용 공용 편입 커밋 하나를 만들며 작업·체크포인트·임시 merge 커밋을 공용 머리의 조상으로 넣지 않는다. 공용 머리가 바뀌면 새 머리를 다시 반영해 재검증한다.
- 각 연구 작업은 목적에 기여하는 연구 상태 변화, 그 변화를 확인할 진전 신호, 작업자가 그 변화를 생산·점검하도록 내부 절차를 구성하는 의무와 다음 관찰 조건을 판본화된 작업 진전 계약으로 가진다. 완료 예상은 근거 있게 산정할 수 있을 때만 선택적으로 기록하며 점검·실패·중단을 직접 결정하지 않는다. 외부 안전 발동 조건과 작업 진전 계약의 점검 발동 조건은 자동 점유 상실이 아니라 운영 점검 실행을 발동한다. 점검한 ref가 여전히 현재이고 인수·중단 처분이 승인됐을 때만 옛 실행의 권한을 무효화한다.
- 관찰 의무가 열리면 작업자는 해당 의무를 참조하는 변경 불가능한 작업 자기 점검을 `진전`, `무진전` 또는 `계약 부적합`으로 기록한다. 유효한 `진전`은 작업을 계속한다. 근거 있는 `무진전`은 계약이 허용하고 다음 방법이 실질적으로 다를 때 내부 적응 한 번을 허용하며, 다음에도 무진전이면 운영 점검을 발동한다. 기록 부재·무결성 결함·증거 없는 진전·계약 부적합도 운영 점검을 발동한다. 형식 검사는 결정론적 검사기가 수행하고 의미 판단은 운영 점검이 원자료로 수행한다.
- 작업 진전 계약에서 작업자가 사용할 수 있는 모든 다음 관찰 조건은 외부 감시기도 같은 판본과 작업자가 공개한 같은 실행 상태에서 재현할 수 있어야 한다. 조건은 판본화된 일회성 관찰 조건 세대로 묶고 하나라도 먼저 도래하면 관찰 의무를 연다. 외부 사건 조건에는 재관찰 시점을 함께 두며 완료 예상은 평가에 참여하지 않는다. 관찰 조건 평가는 전건을 검사해 `미도래`, `도래`, `평가 오류`로 닫고 한 조건이라도 평가할 수 없으면 다른 조건이 참이어도 평가 오류다.
- 관찰 조건의 `도래`는 `실행 ID + 조건 세대 ID`로 식별하는 관찰 의무를 열며 즉시 운영 점검을 뜻하지 않는다. 관찰 의무 상태는 `응답 대기`, `충족`, `위반`으로 닫는다. 관찰 응답 조건은 의무가 열린 뒤 첫 안전 제어 경계와 실행 환경·도구 유형에서 정한 최대 응답 시각 가운데 먼저 도래하는 한계다. 작업자는 안전 제어 경계 뒤 다음 실질적 행동 전에 자기 점검을 기록한다. 최대 응답 시각까지 유효한 자기 점검이 없으면 의무를 위반으로 판정해 운영 점검을 발동하되 작업을 자동 중단하지 않는다. 평가 오류와 외부 안전 발동 조건은 응답을 기다리지 않는다. 유효한 자기 점검은 새 조건 세대를 활성화하고, 처분 직전 실행 ref가 달라졌으면 낡은 관찰로 보존한 뒤 새 스냅샷에서 다시 평가한다.
- 외부 감시기는 작업자가 공개한 실행 상태를 관찰 입력 스냅샷으로 고정해 닫힌 조건과 관찰 의무 이행을 평가하는 결정론적 스크립트다. 관찰 입력 스냅샷·평가·의무 이행·운영 점검 발동 근거는 감시 기록 원장에만 쓰고, 작업자는 이 감시 기록을 읽지 않는다. 외부 감시기는 실행 ref와 작업 브랜치를 바꾸지 않으며 프로세스 소실·실행 ref 불일치 같은 외부 안전 발동 조건으로 운영 점검을 원자적으로 하나만 연다. 운영 점검은 도구로 실제 실행 원자료를 읽고 진단·처분을 제안하는 별도 AI 실행이다.
- 역방향 전달은 확정된 운영 처분에만 허용한다. 운영 처분 실행이 현재 실행 ref를 기대값 기반으로 조건부 갱신해 필요한 실행 제어 상태만 적용하고, 작업자는 안전 제어 경계에서 새 제어 세대를 읽는다. 감시 기록과 실행 제어 상태는 서로 다른 정본이며 감시 기록을 작업자에게 복제하지 않는다.

## 이 세션에서 추가된 사용자 원문과 전후 맥락

아래 사용자 원문은 기존 이슈·문서·커밋에 전문으로 보존되지 않은 이번 세션의 직접 의도 원천이다. 원문 안의 제안이 모두 확정됐다는 뜻은 아니다. 각 항목의 직후 맥락과 위 미커밋 정본 diff를 대조해 확정 여부를 판정한다.

### 1. 근본 설계를 먼저 하라는 순서 교정

직전 맥락: 논의가 단일 조정자, 병렬 노드 작업자의 원자적 변경과 같은 동시성 구조로 먼저 내려갔다. 사용자는 그 순서가 너무 낮은 층위에서 시작한다고 교정했다.

사용자 원문:

> 이것보단 좀 더 근본적인 층위에서 우리가 어떻게 돌아가는 무엇을 만들지를 먼저 논의하는게 중요할 것 같아. 예를 들어 rust 같은 경우는 borrow-checker를 통해 compile time에 memory safety를 보장하는 언어라고 근본적인 층위에서 설명이 되잖아. 목표와 그 목표를 어떻게 달성할 것인지에 대한 것을 우선 전체 근본 층위에서 먼저 정하고 그로부터 가지를 뻗어나가는 방식은 어떨까?

직후 맥락: 동시성·저장·트랜잭션 논의를 하위 후보로 되돌리고, `do-math`의 목적·핵심 작동 원리·보장을 먼저 확정하는 순서로 바꿨다. 다음 세션도 낮은 구현 기제를 앞세우지 않는다.

### 2. `do-math`를 만들려는 목적

직전 맥락: 목표 문제 해결과 인증 지식 확장 중 어느 것을 최상위 목적으로 둘지 논의하고 있었다. 사용자는 두 항을 단순 병렬 목표로 놓는 대신, 인증 수학의 프런티어를 확장해 미지를 건너 목표에 닿는다는 생성 원리를 제시했다.

사용자 원문:

> 아래 목적을 반영해 새로 검토해줘: 이 스킬을 내가 만들고 싶은 목적은 다음과 같아. known mathematics의 영역이 있다고 하자. 그 영역은 꽤 porous할 것이고 또한 여러 층위에서 frontier를 가지고 있을 것이야. 편의를 위해 이러한 known mathematics의 영역이 lean으로 표현되어 있다고 하자. 명제, 정의, 증명, 관계 등등. 만약 우리가 풀고자 하는 문제가 이미 그 영역의 안에 있다면 그 문제를 푸는 것은 trivial하겠지. 하지만 그게 아니라면 그는 그 영역과 우리가 풀고자 하는 문제, 즉 목적지까지의 사이에 unknown이 장벽으로 가로막고 있다는 것이야. 그리고 우리는 그 unknown을 어떻게 건널 수 있을지 몰라. 알면 이미 frontier 안에 포함되어 known mathematics의 영역에 속해있을테니까. 따라서 우리가 문제를 풀고자 하면 그 unknown을 건너야만 해. 새로운 명제, 새로운 정의, 새로운 증명, 새로운 관계를 하나씩 쌓아 올려 frontier를 확장하면서. frontier의 확장은 곧 새로운 것을 known mathematics의 영역으로 편입시키는 것을 뜻하기에 엄밀한 기준과 검증이 요구되는 것이고. frontier가 확장할 수 있는 방향, 즉 unknown 의 범위는 무한히 거대하기에 선택과 집중이 필요한 것이고. 또한 그러나 greedy한 탐색이 곧 optimal한 탐색인 것이 아니기에 오직 선택과 집중만을 하는 것이 아니라 그에 탐색 역시 섞어야 하는 것인거지. 최종적으로 풀고자 하는 문제에 닿을 때까지 frontier를 확장하기 위해서.

직후 맥락: 이 목적에서 `인증 수학 영역 K`, `가시 연구 프런티어 F`, `미지 지평 U`, `U → F → K`, 적응형 연구 포트폴리오와 목표 상대적 연구 진전이 차례로 도출됐다. 사용자는 각 결정을 명시적으로 확정했고 그 결과가 위 두 파일의 미커밋 diff에 기록됐다. `K`는 모든 추상적 논리 귀결이 아니라 실제로 명시·검증된 Lean 내용이라는 해석도 확정됐다.

### 3. Lean 형식 타당성과 의도 대응의 분리

직전 맥락: 인증 수학 영역을 불변 이력 위의 교정 가능한 활성 영역으로 볼지 논의했다. 사용자는 교정 대상이 Lean 형식 객체 자체인지, 그 객체와 외부 수학적 의도의 대응인지 구분했다.

사용자 원문:

> 그렇게 하자. 하지만 lean으로 표현된 어떠한 명제나 증명 등이 lean 커널의 검증을 통과했다는 것은, 기초 프로필과 도구체인을 신뢰할 수 있다면, 그와 연결된 다른 객체들하고의 관계 설정이 올바르게 이루어졌음을 반드시 시사하고, 문제의 핵심은 그 lean 표현이 실제 그에 담고자 한 '의도'와 완전히 일치하는지 여부가 인증 절차에도 불구하고 완전히 보장되지 못한다는 점에 있다고 생각해. 그리고 의도와 완전히 일치하지 않다고 해도 어찌 되었건 lean 커널에 의해 통과된 그 명제나 증명 등은 그 표현 자체로서의 엄밀한 의미는 타당하게 보유할 것이란 점을 명시하고 싶고. 오직 기초 프로필과 도구체인 등의 업데이트나 그러한 것 등이 명시적으로 있을 때만 명시적으로 업데이트가 이루어지게 되는 것이란 점을 명시하고 싶어(내가 틀릴 수도 있음)

이 handoff의 아래 서술은 결정 경위와 대체 관계를 보존한다. 정확한 실행 계약을 handoff 문장만으로 복원하지 않는다.

## 이번 세션의 설계 전개

### 1. 공용 작업대의 판본 정본을 Git으로 확정

세션 시작 시 가장 가까운 미결정은 공용 작업대의 지속 판본을 Git이 소유하는지였다.

확정한 내용:

- 공용 작업대의 지속 내용, 공개된 현재 판본과 이력은 Git이 소유한다.
- 과거 공개 판본은 Git 커밋 이력으로 보존한다.
- 연구 실행은 공용 기준 커밋에서 격리된 브랜치와 worktree로 분기한다.
- Git을 판본 정본으로 사용한다는 결정만으로 별도 서비스·데이터베이스·실시간 조정층을 도입하지 않는다.

이 결정의 근거에는 과거 병행 세션이 하나의 Git index를 공유하면서 다른 세션의 변경이 커밋에 섞인 실측이 있었다. 관련 근거는 `기억/layer1/M-0013.md`와 `기억/layer1/M-0034.md`다.

### 2. 연구 작업대의 의미를 저장 영역보다 넓게 확정

처음에는 사용자가 말한 작업대가 기존의 비정본 연구 작업공간과 같은지, `F·U`를 포함하는 더 넓은 구조인지 불분명했다.

사용자가 의도한 작업대는 책·목차·메모·칠판·수식·도구와 여러 완성도의 아이디어가 공존하는 messy하고 fuzzy한 연구 표면이었다.

확정한 해석:

- 연구 작업대는 별도의 네 번째 저장 영역이나 수학 정본이 아니다.
- 관련 `K` 판본의 참조, Lean 형식화 초안에 대한 접근, 명시된 `F` 후보, 문헌·메모·실패·실험·도구와 탐색 장치를 한 연구 맥락에서 다루는 운영 표면이다.
- 각 내용의 기존 소유권과 신뢰 경계는 유지한다.
- `U`는 정의상 아직 표현되지 않은 가능성이므로 작업대에 직접 들어갈 수 없다.
- 모호한 단서라도 기록되는 순간 `F`의 객체가 된다.
- 작업대는 `U`를 저장하지 않고, 탐색을 통해 `U`의 일부를 `F`로 드러낸다.

이 구별은 이후 예상하지 못한 발견을 표현하는 방식의 기초가 됐다.

### 3. 공용 작업대를 핵심 기록과 파생 보기로 구성

공용 작업대의 내부 구조는 다음 제1원리에서 도출됐다.

- 수학적 진실과 연구 상태를 분리한다.
- 내용은 모호할 수 있지만 정체성·출처·판본·상태 경계는 명확해야 한다.
- 공유 상태는 명시적인 상태 전이로만 바꾼다.
- 원자료와 재생성 가능한 보기를 구별한다.
- 모호한 후보를 성급하게 형식화하지 않고 점진적으로 정련한다.

확정한 구조:

- 공용 작업대의 핵심 기록은 기준, 프런티어, 자료·근거, 연구 작업, 관계와 공용 편입 기록을 소유한다.
- 프런티어 현황, 실행 상태, 중복 가능성, 연구 흐름과 편입 대기 상태는 핵심 기록에서 만드는 파생 보기다.
- 파생 보기는 독립 정본이 아니며 핵심 기록에서 다시 생성할 수 있어야 한다.
- Lean이 입증할 수학적 관계, 근거가 후보를 지지·반박하는 연구 관계와 실행 관계를 같은 종류의 간선으로 취급하지 않는다.

### 4. 핵심 기록의 정체성과 판본

핵심 기록 객체의 제목이나 경로가 바뀔 때 관계가 끊기지 않도록 안정된 ID를 도입했다.

확정한 내용:

- ID는 순서나 저장 위치를 나타내는 인덱스 번호가 아니라 객체의 논리적 정체성이다.
- 특정 객체 판본은 `핵심 기록 ID + 공용 작업대 판본`으로 식별한다.
- 제목·파일 경로가 바뀌어도 같은 객체라면 ID를 유지한다.
- 같은 명제·질문·정의에 근거·설명·산출물을 추가하면 같은 ID의 새 판본이다.
- 명제 문면, 질문, 정의, 가정이나 적용 범위가 달라져 기존 관계를 그대로 적용할 수 없으면 새 ID를 만든다.
- 분화·대체·정교화와 실제로 성립하는 관계를 기존 객체와 새 객체 사이에 기록한다. 이 관계 예시는 닫힌 목록이 아니다.
- 객체를 조용히 삭제하거나 같은 ID에 다른 의미를 덮어쓰지 않는다.

Git은 전체 공용 작업대 판본을 소유하므로 별도 객체 버전 카운터는 두지 않는다. 이 구현 세부는 지도 컨텍스트 정본에만 있고 root `CONTEXT.md`에는 추상 판본 개념만 남겼다.

### 5. 공통 외피와 역할별 기록 내용을 분리

처음에는 모든 핵심 기록에 하나의 범용 `status`를 두는 방안이 가능했지만, 이는 서로 다른 사실을 혼합한다는 문제가 드러났다.

예를 들어 Lean 코드가 실행된다는 사실은 수학적 의미가 인증됐다는 뜻이 아니고, 작업 완료도 그 작업이 낸 명제가 참이라는 뜻이 아니다.

확정한 내용:

- 모든 핵심 기록은 공통 외피와 역할별 내용으로 구성한다.
- 공통 외피는 ID, 객체 역할, 출처·생성 근거, 생명주기, 관계와 실제 자료 좌표를 가진다.
- 프런티어, 자료·근거, 연구 작업, 공용 편입과 관계는 자기 역할에 맞는 내용과 상태를 가진다.
- 수학적 확인 상태, 자료 완성도와 실행 상태를 하나의 범용 상태로 합성하지 않는다.

### 6. 장기 연구 프로그램을 폐기하고 작업 중심 구조로 전환

세션 초반에는 자기완결 연구 프로그램이 각자 작업대·브랜치·상태를 소유하고, 포트폴리오가 프로그램에 자원을 배정하는 구조를 검토했다.

사용자는 다음 근본 질문을 다시 열었다.

> 공용 작업대가 불완전한 결과도 정확한 상태로 보존할 수 있다면, 별도의 장기 프로그램 없이 모든 실행을 작업으로 분할하고 각 작업이 공용 작업대와 직접 상호작용할 수 있지 않은가?

이 재검토로 이전 프로그램 구조를 폐기했다.

확정한 현재 구조:

- 연구 프로그램은 실행·상태·작업대·DAG의 소유 단위가 아니다.
- 입력, 기대하는 연구 상태 변화, 산출물과 완료 기준이 닫힌 연구 작업이 연구 생산의 유일한 실행 단위다.
- 장기 연구 방향은 `F` 객체, 관련 작업·산출물의 관계와 파생 보기로 표현한다.
- 포트폴리오는 프로그램이 아니라 현재 착수 가능한 작업을 직접 선택한다.
- 작업은 공용 기준 판본에서 격리된 작업별 작업대를 사용하고, 종결 결과를 공용 작업대에 돌려준다.

프로그램 구조가 해결하려던 국소 변경 자유·중복 조정·의존 최신성은 작업별 격리, 공용 편입과 포트폴리오가 각각 맡는다.

### 7. 작업 DAG를 폐기하고 깊이 1 실행 껍질로 전환

작업 중심 구조를 확정한 뒤 사용자는 미래 작업을 DAG로 미리 보존할 필요가 있는지 다시 물었다.

확정한 내용:

- 작업 DAG를 사용하지 않는다.
- 실행 껍질의 깊이는 1로 고정한다.
- 실행 껍질은 현재 공용 작업대 판본에서 지금 착수할 수 있는 작업만 나타내는 파생 보기다.
- 미래에 수행할 수 있지만 조건이 충족되지 않은 일은 차단된 작업으로 만들지 않는다.
- 미래 가능성은 작업 씨앗과 `F`의 방향·조건으로 보존한다.
- 알려진 순차 절차도 미래 작업을 미리 만들지 않고, 현재 단계 결과가 다음 발생 조건을 충족할 때 다음 작업을 실행 껍질에 나타낸다.
- 완료 작업의 계보와 `F` 관계가 장기 연구 흐름을 보여 준다.
- 연구 반복은 비순환 그래프에 억지로 넣지 않고 반복 감지와 연구 진전 판정으로 통제한다.

이 결정으로 현행 이슈 본문에 있던 “단일 작업 DAG”도 작업 씨앗과 실행 껍질 구조로 교체했다.

### 8. 예상하지 못한 `U → F` 발견

사용자는 작업이 시작될 때 `F` 어디에도 없던 개념·아이디어·방향을 발견할 수 있다는 점을 지적했다.

확정한 표현:

- 작업의 착수 전 연결 목록은 열린 목록이다.
- 탐색 작업은 아직 모르는 결과 객체를 미리 가리키지 않는다.
- 탐색 영역·생성 방법·새 후보를 구별하는 기준과 기록 방법만 미리 명시한다.
- 작업 중 예상하지 못한 대상을 발견하면 작업별 작업대에 발견 후보로 기록한다.
- 발견 후보는 내용, 발견 과정, 기존 `F`와의 차이, 확인한 범위·남은 추측과 증거를 가진다.
- 공용 편입을 통과하면 새 핵심 기록 ID를 가진 `F` 객체가 된다.
- 기존 `F`와의 관계를 아직 확인하지 못했다면 생성 계보만 가진 독립 객체로 둘 수 있다.
- 이것은 `U → F`인 탐색이며, 인증과 Lean 정본 편입을 통한 `F → K` 프런티어 확장과 다르다.

### 9. 순차 절차의 작업 경계

깊이 1 실행 껍질에서는 순서가 명확한 절차를 단계마다 작업으로 쪼개면 작업 수가 과도하게 늘 수 있다는 문제가 제기됐다.

확정한 경계:

- 하나의 연구 상태 변화를 만들고 중간 결과를 독립적으로 배정·검증·재시도·취소·공용 편입할 실익이 없으면 여러 순차 단계를 한 작업의 내부 절차로 묶는다.
- 단계 수나 한 에이전트 세션보다 길다는 이유만으로 작업을 분할하지 않는다.
- 중간 결과를 다른 작업이 재사용하거나, 포트폴리오가 계속 여부를 다시 선택해야 하거나, 독립 역할·판정 권한·별도 재시도·외부 대기·병렬 수행이 필요하면 별도 작업으로 나눈다.
- 작업은 여러 작업 실행과 비공개 체크포인트에 걸쳐 재개할 수 있다.
- 반복할수록 질문이나 산출물이 바뀌면 같은 작업을 연장하지 않고 새 작업으로 분화한다.

실무 경계 질문은 다음과 같다.

> 이 단계를 별도로 배정·검증·재시도·취소·공용 편입할 합리적인 상황이 있는가?

### 10. 작업 하나당 종결 공용 편입 한 번

처음에는 작업 도중 독립적인 중간 결과를 공용 편입하는 구조를 추천했다. 사용자는 애초에 그런 결과가 예상된다면 작업이 처음부터 잘못 나뉜 것 아니냐고 지적했다.

이 교정으로 중간 공용 편입을 폐기했다.

확정한 내용:

- 하나의 연구 작업은 종결할 때 공용 편입을 한 번만 수행한다.
- 계획된 중간 산출물이 독립적인 공유 가치가 있으면 착수 전에 작업을 분할한다.
- 내부 체크포인트는 비공개이며 공용 작업대나 다른 작업의 입력이 아니다.
- 예상하지 못한 중요한 산출물을 즉시 공유해야 하면 현재 작업을 분할 종결한다.
- 현재까지의 결과를 종결 공용 편입하고, 남은 범위를 새 작업 씨앗으로 만든다.
- 한 작업의 종결 결과, 공용 편입과 공용 커밋을 일대일로 대응시키며 여러 작업 결과를 한 편입 커밋에 섞지 않는다.

### 11. 작업 씨앗의 생성 근거

사용자는 새 작업이 기존 작업 결과에서 자라나는 얇은 껍질 구조를 제안했다. 이를 엄격한 “부모 작업만 허용”으로 닫으면 초기화·외부 변화·빈 껍질 회복을 표현하지 못한다는 문제가 있었다.

확정한 네 생성 근거:

1. 연구 인스턴스 초기화
2. 작업 종결 공용 편입
3. 핵심 기록에 먼저 반영된 승인된 외부 변화
4. 목표 미해결·빈 실행 껍질에서 현재 `F`를 정련·탐색하는 생존 규칙

모든 작업 씨앗은 실제 생성 근거의 핵심 기록 ID와 공용 판본을 가리킨다. 포트폴리오는 작업 씨앗을 창작하지 않고, 착수 가능한 씨앗 가운데 실행할 대상을 선택한다.

### 12. 작업 씨앗과 연구 작업의 동일 ID

처음에는 씨앗을 실제 작업으로 “승급”하거나 새 객체를 만들 가능성이 있었다. 사용자는 ID와 판본의 역할을 명확히 확인했고, 별도 승급은 불필요하다고 확정했다.

현재 구조:

- 작업 씨앗은 안정된 하나의 핵심 기록 객체다.
- `작업 씨앗 ID + 공용 작업대 판본`에서 착수 가능성 판정을 계산한다.
- 통과하면 같은 ID가 실행 껍질에 나타난다.
- 포트폴리오가 선택하면 같은 ID에 작업 실행을 연다.
- 새 작업 ID, 승급 상태나 승급 커밋을 만들지 않는다.
- 선택 전에 공용 상태가 바뀌어 조건이 깨지면 실행 껍질에서 사라지지만 씨앗 자체는 `F`에 남는다.
- 실행을 시작하면 선택 당시 공용 판본을 기준으로 고정한다.

### 13. 네 작업 인터페이스

착수 가능성을 결정론적으로 계산하려면 정해진 인터페이스가 필요하다는 사용자의 지적에서 네 인터페이스를 확정했다.

- 작업 씨앗: 질문, 범위, 기대 상태 변화, 입력, 발생 조건, 산출물, 종결 기준, 관계·탐색 방향, 모델·도구·권한·자원 요구
- 착수 명세 검토: 특정 씨앗 판본에 대한 질문·범위·입력·산출물·완료 기준별 판정, 결함, 승인·판정 불가와 검토자 기록
- 작업 실행: 기준 판본, 작업자·점유, 실행 시도, 브랜치·worktree, 체크포인트·재개, 모델·도구·자원과 상태
- 작업 종결: 실제 수행 범위, 결과·한계, 산출물·증거, 발견 후보, `F` 변경, 새 작업 씨앗, 관계 효과와 정확한 공용 변경 묶음

씨앗 작성자와 다른 역할이 착수 명세를 검토한다. 씨앗의 의미가 바뀌면 이전 검토 승인은 새 판본에 사용할 수 없다.

### 14. 발생 조건식과 착수 가능성 판정

사용자는 조건을 정해진 인터페이스로 표현해야 결정론적으로 검사할 수 있다고 확인했다.

확정한 구조:

- 발생 조건은 판본화된 닫힌 선언형 연산자로 표현한다.
- 조건식은 해당 공용 작업대 판본의 핵심 기록만 읽는다.
- 임의 코드, 실시간 외부 상태와 새 수학 판단을 실행하지 않는다.
- 외부 사건은 먼저 핵심 기록에 반영한 뒤 조건식이 그 기록을 참조한다.
- 실시간 작업자 수나 예산은 발생 조건이 아니라 포트폴리오 선택의 입력이다.
- 조건 결과는 `참`, `거짓`, `평가 오류`를 구별한다.
- 거짓은 정상적인 미충족이고, 평가 오류는 알 수 없는 연산자·깨진 참조·자료형 오류 같은 인터페이스 결함이다.
- 평가 오류를 거짓으로 숨기지 않는다.

착수 가능성은 구조화된 기록에서 다음을 검사한다.

```text
씨앗 스키마 유효
∧ 현재 씨앗 판본의 착수 명세 검토 승인
∧ 발생 조건 참
∧ 필수 입력 존재
∧ 씨앗 활성
```

### 15. 인터페이스 물리 형식

저장소를 직접 확인한 결과 별도 의존성 파일이나 일반 YAML 검증 라이브러리는 없었고, 구조화 산출물과 Python 스크립트는 이미 표준 JSON을 사용하고 있었다.

확정한 형식:

- 네 작업 인터페이스의 기계 정본은 판본화된 JSON 스키마를 따르는 독립 UTF-8 JSON 문서다.
- 긴 산문, 문헌 판독, Lean 코드, 계산 자료와 증거는 별도 파일에 둔다.
- JSON은 경로와 무결성 정보만 참조하며 산출물 본문을 복제하지 않는다.
- 알 수 없는 필드·연산자·자료형을 조용히 무시하지 않는다.
- UTF-8, LF, 고정 들여쓰기, 결정론적인 키 순서와 파일 끝 개행을 사용한다.
- 같은 의미의 입력은 같은 JSON 바이트를 만든다.
- 구체적인 디렉터리와 파일명, JSON 스키마 검증 도구는 아직 미정이다.

root `CONTEXT.md`에는 JSON·Git 같은 구현명을 두지 않고, 구현 계약은 지도 컨텍스트 정본에만 둔다.

### 16. 공용 머리·Git 실행 ref·작업 브랜치의 분리

작업 실행 인터페이스를 어디에 저장할지 검토하면서 계약 충돌이 드러났다.

- 점유·실행 시작을 공용 머리에 기록하면 종결 전 공용 상태가 바뀐다.
- 작업 브랜치에만 기록하면 다른 실행이 현재 점유를 볼 수 없다.

확정한 해결:

- 공용 Git 머리는 공용 작업대 판본과 종결 공용 편입만 소유한다.
- `refs/do-math/claims/<연구 인스턴스 ID>/<작업 씨앗 ID>` 실행 ref가 작업 점유와 최신 실행·체크포인트 좌표를 가리킨다.
- 작업 브랜치와 worktree가 진행 중 실행 JSON, 체크포인트와 산출물을 소유한다.
- ref가 없을 때만 원자적으로 생성한 실행이 작업을 점유한다.
- 실행 껍질은 공용 커밋만으로 계산한다.
- 포트폴리오는 실행 껍질 계산 뒤 실행 ref를 확인해 이미 점유된 작업을 제외한다.
- 종결 공용 편입에서는 공용 머리 갱신과 실행 ref 제거를 기대값 기반의 원자적 ref 트랜잭션으로 묶는다.
- 기대 공용 머리나 실행 ref가 달라지면 전건을 적용하지 않는다.

Git이 연구 의미·우선순위·수학적 판정을 결정하는 것은 아니다. Git ref는 배타적 점유와 실행 좌표만 소유한다.

### 17. 시간 만료 대신 진단 우선 운영 점검

작업자가 사라지거나 오래 걸리는 경우를 처음에는 lease·heartbeat·fencing으로 자동 회수하는 방안을 검토했다.

사용자는 시간 초과만으로 인수하지 말고 별도 점검 작업이 실제 코드·내용·로그·상태를 읽어 원인과 현실적인 종료 가능성을 판정하자고 제안했다.

자동 lease 회수안은 채택하지 않았다.

확정한 현재 구조:

- 프로세스 소실, 응답·heartbeat 부재, 작업별 시간·진전 한계 `N` 초과, 반복 상태와 부분 종결 흔적은 점검 발동 조건이다.
- `N`은 모든 작업에 같은 값으로 강제하지 않고 작업별 예상 소요와 진전 신호에 맞춘다.
- 발동 조건은 실행 ref를 자동 만료·삭제하거나 점유를 넘기지 않는다.
- 운영 점검 실행은 연구 작업·`F`·실행 껍질·포트폴리오와 분리한다.
- 운영 점검은 실제 씨앗·기준 판본·실행 JSON·ref·브랜치·diff·미커밋 변경·체크포인트·로그·프로세스·자원·외부 도구와 코드 종료 조건을 직접 읽는다.
- 점검자는 원인, 실제 진전, 시간의 합리성, 교착·무한 반복·외부 대기 가능성, 현실적 종결 가능성, 유효 체크포인트와 부분 산출물 가치를 판정한다.
- 점검을 시작할 때 대상 실행 ref를 고정한다.
- 처분 적용 시 ref가 달라졌으면 점검 결과를 낡은 관찰로 기록하고 아무 처분도 적용하지 않는다.
- 대상 ref가 그대로이고 인수·중단 처분이 승인됐을 때만 ref 세대를 바꿔 기존 실행을 fencing한다.
- 운영 점검은 구조화된 JSON 근거와 처분 기록을 남기지만 연구 작업 종결 공용 편입을 가장하지 않는다.

## 아직 정본화되지 않은 현재 미결정

### 결정 주제

운영 점검자가 자기 점검 결과를 직접 확정·집행할 수 있는 범위.

### 현재 추천안

운영 점검자가 직접 확정할 수 있는 영향이 작은 처분:

- 현재 실행 계속
- 다음 점검 시각 지정
- 추가 로그나 체크포인트 요구
- 대상 실행 상태가 그사이 바뀌어 점검 결과가 낡았다는 무처분 판정

점검자와 다른 운영 처분 심사가 필요한 실행 변경:

- 기존 실행 fencing
- 다른 작업자의 체크포인트 인수
- 처음부터 재시작
- 작업 분할 종결
- 운영 실패 종결
- 자원 배정의 큰 변경

운영 처분 심사는 점검 보고서와 실제 원자료를 다시 대조한다. 승인 뒤에도 대상 실행 ref가 점검 당시 값과 같을 때만 처분을 원자적으로 적용한다.

사용자 개입 경계는 기존 계약을 유지한다. 처분이 연구 목적·신뢰 경계·외부 또는 비가역 상태를 바꾸거나 사용자 절충을 요구할 때만 상신한다. 근거가 충분한 단순 재시작이나 체크포인트 인수는 `do-math`가 자율 처리할 수 있다는 추천이다.

### 다음 세션의 첫 질문

먼저 다음을 분명히 설명한다.

- 지금 결정하는 것은 운영 점검의 진단 방법이 아니라 처분 승인 권한이다.
- 이 결정을 먼저 닫아야 운영 점검 JSON, 자동 처분과 상신 필드를 설계할 수 있다.
- 점검자가 고영향 처분까지 자기 승인하면 오진이 즉시 실행 중단으로 이어질 수 있다.
- 모든 처분에 별도 심사를 요구하면 단순 계속·재점검에도 불필요한 지연이 생긴다.

그 뒤 위 권한 분리를 확정할지 질문 하나만 한다. 사용자 답을 대신 정하거나, 승인 전에 정본 문면을 수정하지 않는다.

- handoff나 요약을 원자료 대신 사용하지 않는다. 실제 파일·Git·이슈 상태를 다시 대조한다.

## Git 연속성

초안 작성 시점의 실제 상태는 다음과 같다.

- 브랜치: `main...origin/main [ahead 2]`
- 현재 HEAD: `277be4a14d574ff5bc5ece5eba8fe636ec726d83`
- `origin/main`: `4675b28de8bde675d154d913131c4cf297a9ef1e`
- 수정 파일:
  - `CONTEXT.md`: 188행 추가
  - `docs/wayfinder/pvsnp-재설계/컨텍스트.md`: 285행 추가, 25행 삭제
- `git diff --check`: 통과. Windows의 LF→CRLF 변환 경고만 있음
- 커밋·푸시: 수행하지 않음

정확한 현행 계약은 `CONTEXT.md`와 `docs/wayfinder/pvsnp-재설계/컨텍스트.md`의 3.2절·3.11절·3.12절·용어집에 있다. `docs/do-math/통합-설계.md`는 아직 존재하지 않는다. 위 diff가 사라졌거나 상태가 다르면 이 handoff에서 복원하지 말고 실제 상태를 대조해 사용자에게 손실·경합을 보고한다.

## 이번 세션에서 결정 경계가 바뀐 과정

### 1. 운영 점검자의 진단과 처분 승인 권한을 분리

이번 세션은 앞선 handoff가 남긴 “운영 점검자가 자기 진단에 따른 처분을 어디까지 직접 확정할 수 있는가”에서 시작했다. 첫 추천은 점검자가 영향이 작은 처분을 직접 확정하고 실행의 정체성·점유·종결을 바꾸는 처분은 별도 역할이 심사하도록 분리하는 것이었다. 사용자는 이 추천을 확정했다.

현행 구조에서 점검자는 현재 실행 계속, 다음 점검 시각 지정, 추가 로그나 체크포인트 요구와 관찰 대상 ref가 이미 달라졌다는 무처분처럼 실행 자체를 바꾸지 않는 처분을 직접 확정한다. 기존 실행 fencing, 다른 작업자의 체크포인트 인수, 처음부터 재시작, 분할 종결, 운영 실패 종결과 중대한 자원 변경처럼 실행 정체성·점유·종결 또는 중대한 자원 배정을 바꾸는 처분은 점검자와 다른 **운영 처분 심사**를 거친다. 심사자는 점검 요약을 승인하는 역할이 아니라 점검 기록이 가리키는 원자료를 다시 대조하는 역할이다.

이 분리는 오진 하나가 곧바로 실행 중단이나 점유 이전으로 이어지는 것을 막되, 단순 계속·재점검까지 불필요한 심사로 지연하지 않으려는 결정이다.

### 2. 운영 점검과 운영 처분 심사의 기록·판정을 분리

권한을 분리한 뒤에는 두 역할이 같은 가변 기록을 수정하면 책임과 판정 이력이 섞인다는 문제가 드러났다. 사용자는 다음 기록 경계를 차례로 확정했다.

- 운영 점검 실행 하나는 변경 불가능한 점검 기록 하나를 만든다.
- 저영향 직접 처분은 점검 기록에 남는다.
- 고영향 처분의 운영 처분 심사는 정확한 점검 기록과 대상 실행 ref를 참조하는 별도 불변 기록을 만든다.
- 재점검과 재심사는 기존 기록을 고치지 않고 새 기록을 만든다.

사용자는 심사의 판정 어휘를 `승인·기각`으로 닫았다. 다만 필수 원자료를 읽지 못했거나 근거가 부족한 상황에서 억지로 둘 중 하나를 고르는 것은 이 이분법의 의미를 훼손한다. 이를 해소하기 위해 판정과 심사 실행 상태를 분리했다. 근거가 부족하면 판정을 내리지 않고 실행 상태를 **심사 미완료**로 끝낸다. 심사 미완료는 세 번째 판정도, 기각도 아니며 처분 적용·대응·전례 관문을 열지 않는다. 부족한 근거를 보충한 뒤 새 심사 기록을 만든다.

### 3. 승인 뒤 자율 적용 규칙을 사용자 유래 전례 체계로 교체

권한 분리 직후의 추천은 고영향 처분이 심사에서 승인되고 기존 사용자 개입 경계에 해당하지 않으면 `do-math`가 적용하는 구조였다. 사용자는 이를 더 보수적이면서도 경험에 따라 자율 범위가 커지는 전례 체계로 다시 열었다.

사용자의 핵심 제안은 다음과 같았다.

> 판정은 승인, 기각으로 하고. 이후 어느 방향으로 그 판정에 따라 어느 결정이 내려지게 되는지가 '전례'에 의해 결정되는거지. 만약 승인일 경우 결정은 적용 혹은 상신이 되고. 적용은 오직 그와 충분히 유사하다 판단되는 처분이 이미 승인 후 적용된 전례가 존재하는 경우 자동으로 되고, 이 경우 이는 전례로 기능하지 못해. 만약 그러한 전례가 없는 경우 이는 상신이 되고 사용자에 의해 승인 혹은 반려가 될 때까지 적용이 미루어지게 돼.

이 제안으로 심사 승인의 의미를 처분안의 타당성 판정으로 한정했다. 승인은 그 자체로 적용 권한을 만들지 않는다. 승인된 처분은 적용 가능한 **적용 전례**가 있을 때만 자동 적용한다. 전례가 없거나 적용 가능성을 확정하지 못하면 사용자에게 상신한다. 사용자가 승인하면 현재 결정과 실제 사례가 새 전례가 되고, 사용자가 반려하면 후술한 `대응` 경로로 들어간다. 기존 전례를 따라 자동 적용한 사례는 새 전례를 만들지 않으므로 자동화가 자기 결과를 근거로 권한 범위를 연쇄 확장하지 못한다.

처음에는 연구 목적·신뢰 경계·외부·비가역 효과·사용자 절충에 해당하면 전례와 무관하게 다시 상신하는 예외를 남겼다. 사용자는 적용 가능한 전례가 있으면 이 상신도 생략할 수 있게 하자고 제안했다. 최종적으로 전례는 단순한 과거 기록이 아니라, 보존된 사례와 의미론적으로 유사한 미래 사례에 사용자의 결정을 재사용할 수 있게 하는 범위 한정 위임이 됐다. 현재 사례가 전례 사례와 중대한 차이가 없고 사용자가 명시한 추가 조건을 충족할 때는 네 사용자 개입 범주도 전례로 넘을 수 있다.

### 4. `재처분`이라는 좁은 모형을 버리고 `대응`을 확정

초기 전례 흐름은 기각 뒤 “재처분”을 선택하는 것으로 표현했다. 사용자는 이 표현이 다음 행동을 또 하나의 처분안으로 좁힌다고 지적하고 의도를 다시 설명했다.

> 재처분이란 표현이 지금 보니 부적절했던 것 같아. 재처분이 아니라, 무슨 용어가 적절할진 모르겠지만 그 의미는 이런 것인걸로 하자. 기각된 처분에 대해 정확히 어떠한 대응을 할 것인가. 예를 들어 그냥 기각 사유와 함께 다시 새로 운영 처분을 작업으로 만들기만 할 것인가. 아니면 그냥 사소한 문제만 바로 수정하고 적용할 것인가. 아니면 보다 근본적이고 더 큰 범위에서의 다른 대응이 필요한 것인가. 등등.

사용자는 최종 용어를 짧게 `대응`으로 정했다. 대응은 운영 처분안이 심사에서 기각되거나, 심사 승인을 받았지만 상신 뒤 사용자에게 반려됐을 때 해당 사례를 다음 상태로 옮기고 후속 행위를 정하는 권위 있는 실행 계약이다. 대응은 한정된 결함을 고쳐 적용하거나, 새 처분안을 만들거나, 추가 점검·작업을 열거나, 더 근본적이고 넓은 조치를 선택하거나, 아무 처분도 적용하지 않는 경로를 표현할 수 있다. 이 예시는 닫힌 목록이 아니다. 대응이라는 계약과 그 계약을 실제로 수행하는 대응 실행은 구별한다.

### 5. 사례 전례와 전례 비적용 관계로 양성·음성 경계를 함께 축적

처음에는 여러 적용 가능한 전례가 서로 다른 결정을 지시하거나 판정 불가가 남으면 단순히 사용자에게 상신하고 끝내는 방안을 제안했다. 사용자는 상신 결과를 다음 유사 사례의 경계 학습에도 사용하자고 제안했다.

> 이러한 경우 사용자에게 상신을 하고, 사용자가 내린 결정을 새로운 전례로, 그리고 선택된 전례들에는 이러한 처분에 대해서는 이 전례가 대응하지 않는다는 추가 정보를 붙여 기록하는 식으로 처리하는게 어떨까?

`대응`이 이미 별도 용어가 됐으므로 기존 전례가 현재 사례에 권한을 주지 않는 관계는 **전례 비적용 관계**로 이름 붙였다. 사용자 상신 뒤 현재 결정과 실제 사례는 새 전례가 된다. 기존 후보 가운데 사용자가 현재 사례에 적용되지 않는다고 명시한 후보에만 비적용 관계를 추가한다. 사용자가 다른 결정을 골랐다는 사실만으로 나머지 전례도 부적합하다고 추론하지 않는다. 여러 전례가 동시에 타당할 수 있기 때문이다.

비적용 관계는 기존 전례를 수정하지 않고 기존 전례·현재 사례·처분안 또는 대응·비적용 사유·사용자 결정 좌표를 잇는 별도 불변 기록이다. 기본 범위는 현재 사례 하나다. AI는 한 음성 사례에서 일반 제외 규칙을 창작하지 않는다. 사용자가 일반 제외 조건을 직접 명시할 때만 그 범위를 넓힌다.

### 6. 전례를 추상 규칙이 아니라 실제 사용자 결정 사례로 고정

전례가 미래 자동 적용 권한을 주려면 사용자 결정에서 일반 범위를 어떻게 뽑을지가 문제가 됐다. AI가 한 사례를 보고 “앞으로 모든 X에 적용한다”는 규칙을 만들면 사용자가 부여하지 않은 권한이 생긴다. 사용자는 기본 전례를 실제 사례 자체로 두는 방향을 확정했다.

새 전례는 사용자 결정, 그 결정을 받은 질문과 선택지, 당시 사례의 사실·처분안 또는 대응·효과·근거를 함께 보존한다. 전례의 기본 범위는 이 실제 사례다. 미래 사례에서는 형식 검사와 AI의 의미론적 전례 적용 판정으로 유사성을 판단한다. 일반 적용 조건과 일반 제외 조건은 사용자가 명시할 수 있지만 AI가 전례 생성 시 임의로 만들지 않는다.

이 구조에서 전례는 단순한 과거 사례가 아니다. 사용자가 이 체계에서 결정을 내리면 그 실제 사례와 의미론적으로 유사한 미래 사례에 그 결정을 재사용하도록 위임한다는 의미를 함께 가진다.

### 7. 형식 검사의 역할을 유사성 판정이 아닌 단방향 배제 필터로 축소

전례 적용을 형식 검사와 AI 판단으로 나누는 초안에서는 형식 검사가 전례의 효과 범위·제외 조건·입력 충분성까지 확인한다고 표현했다. 사용자는 그 가운데 의미론적 판단 없이 실제로 확인할 수 있는 것이 무엇인지 물었다. 검토 결과, 구조화된 필드의 존재·자료형·참조·닫힌 조건식은 기계적으로 검사할 수 있지만, 실제 효과가 빠짐없이 기록됐는지, 자연어 제외 조건이 현재 사례에 해당하는지, 근거가 의미상 충분한지는 AI 판단 없이는 확인할 수 없다는 점을 분리했다.

그 뒤 사용자는 형식 검사의 역할을 다음 한 방향으로 확정했다.

> 의미론적 판단 없이도 무조건 매우 확실하게 속하지 않는다고 판단할 수 있는 전례들을 배제하는 필터

현행 형식 검사는 명시된 구조화 사실과 닫힌 결정 절차만으로 현재 사례에 적용될 수 없다고 확실하게 판정할 수 있는 전례만 제거한다. 통과는 유사성이나 적용 가능성을 뜻하지 않는다. 확실히 배제할 수 없는 후보는 모두 AI 판단으로 넘긴다. 입력 누락·알 수 없는 연산자·깨진 참조 같은 평가 오류도 적용 불가로 바꾸지 않는다. 형식 검사의 구체 연산자와 평가 오류 복구는 아직 미정이다.

### 8. AI 전례 적용 판정을 독립된 비대칭 이중 판정으로 구성

형식 검사를 통과한 각 전례는 현재 사례와 전례 원자료를 직접 대조하는 **전례 적용 판정**으로 간다. 판정은 `적용 가능·적용 불가·판정 불가`로 닫았다. 적용 가능은 사용자 결정을 바꿀 중대한 차이가 없고 권한 범위와 검증 조건 안임을 확인한 결과다. 적용 불가는 중대한 차이나 범위 이탈을 확인한 결과다. 판정 불가는 사실이나 근거가 부족해 어느 쪽도 확인하지 못한 결과다.

같은 에이전트가 처분의 타당성을 승인하고 그 처분을 자동 적용할 권한까지 판단하지 못하도록 전례 적용 판정자는 운영 점검자·운영 처분 심사자와 다른 역할로 분리했다. 판정자는 다른 판정 결과와 현재 사례에 대한 미래 사용자 결정을 보기 전에 자기 기록을 봉인한다.

판정 기수는 모든 후보를 무조건 두 번 판단하는 대칭 구조가 아니다. 1차가 적용 불가 또는 판정 불가이면 그 결과를 최종으로 두고 2차를 열지 않는다. 자동 권한을 여는 1차 적용 가능에만 독립된 2차를 붙인다. 두 판정이 모두 적용 가능일 때만 최종 적용 가능이다. 사용자는 두 결과가 다를 때 별도 충돌 상태를 만들지 말고 다른 판정 불가와 똑같이 처리하자고 정했다.

처음에는 두 판정자에 `gpt-5.6-sol max`를 추천했지만 사용자는 `high`를 제안했다. 이 판단은 새로운 수학 생산이 아니라 제한된 두 사례의 효과·근거·권한 범위를 대조하는 운영 의미 판정이고, 독립 이중 판정과 보수적인 판정 불가 경로가 있으므로 최종 모델은 1·2차 모두 별도의 `gpt-5.6-sol high`로 확정했다. 형식 검사는 AI가 아니라 결정론적 검사기가 수행한다.

### 9. 별도 사용자 인증 없이 원자료 봉인으로 전례를 자동 활성화

사례 전례를 만들 때 AI가 구조화한 전례 문면을 사용자에게 다시 확인받는 방안을 한때 추천했다. 사용자는 이미 내린 결정을 전례로 기록하기 위해 별도 인증을 반복하지 않는 방법을 요구했다.

> 따로 사용자에게 다시 어떻게 전례로서 기록될 것인지 인증 받을 필요 없는 형식으로 전례를 바로 작성해 보관하는 방법은 없을까?

이를 위해 전례를 AI가 다시 서술한 문서가 아니라 원자료를 기계적으로 봉인한 묶음으로 만들었다. 묶음은 현재 사례, 운영 점검·심사·처분안 또는 대응의 정확한 좌표, 사용자에게 제시한 질문과 선택지, 사용자 답변, 당시 이미 기록된 효과·근거와 관련 전례를 보존하거나 참조한다. 문맥 의존적인 “그렇게 하자” 같은 답도 그 답이 가리키는 질문 전문과 함께 봉인한다.

기계적 생성은 스키마 조립, 참조 연결과 무결성 계산만 수행하며 사용자 결정을 요약·확장·일반화하지 않는다. 질문과 답변을 함께 읽어도 결정이 모호하면 전례 문면을 인증받는 것이 아니라 같은 결정 대화에서 원래 결정을 명확히 한다. 결정이 명확하고 스키마·참조·무결성 검사를 통과하면 별도 확인 없이 전례와 사용자가 명시한 비적용 관계를 활성화한다. AI 검색 태그·특징·요약은 원자료에서 재생성하는 비권위 파생 보기이며 권한을 넓히거나 자동 적용을 승인할 수 없다.

### 10. 전례 효력 변경과 실행 직전 재검사

전례와 비적용 관계가 축적되면 판정 도중 사용자가 전례를 교정·철회하는 경합을 처리해야 한다. 사용자는 불변 이력 방식을 확정했다.

전례는 제자리에서 수정하지 않는다. 교정은 교정된 새 전례와 기존 전례의 대체 관계를 만들고 기존 전례를 미래 후보에서 제외한다. 철회는 폐기 기록을 만들고 기존 전례를 미래 후보에서 제외한다. 기존 전례의 원자료와 과거 효력 이력은 삭제하지 않는다.

대체·폐기는 과거 자동 적용을 소급해 무효화하지 않는다. 과거 적용이 잘못됐다고 판단하면 별도 운영 점검과 대응으로 실제 영향을 조사한다. 형식 검사와 전례 적용 판정은 시작 공용 커밋의 활성 전례·비적용·대체·폐기 집합에 결박한다. 자동 적용 또는 대응 실행 직전에 같은 집합과 관련 실행 ref가 현재인지 다시 확인한다. 바뀌었으면 기존 판정은 낡은 판정 이력으로 보존하되 적용하지 않고 새 판본에서 다시 수행한다.

## 이번 세션에서 확정한 설계

### 1. 작업 진전 계약

앞선 handoff는 작업마다 예상 소요 시간과 관찰 가능한 진전 신호를 정하고, 일정 시간 동안 진전이 없으면 운영 점검을 시작하는 방안을 제안했다. 논의를 이어가던 중 사용자는 개방형 수학 연구의 완료 시점을 미리 신뢰성 있게 예측하기 어렵다고 지적했다. 또한 진전 신호는 외부 감시 기준에 머물러서는 안 되며, 작업자가 그 의미를 명시적으로 알고 실제 작업 방법을 필요한 진전의 생산에 맞추어야 한다고 요구했다.

> 예상 소요 시간은 예측이 어렵지 않을까? 그리고 진전 신호에 대한 계약은 단순히 외부에서 관찰할 때만 쓰이는 것이 아니라 그 작업 내부에서도 그것에 대한 명시적 인지를 가지고 있고, 작업 방식 역시 그 진전 신호의 필요한 생산에 실제로 초점이 충분히 주어지는 방식으로 설계되어야 한다는 점이 명시되어야 할 것 같아. 안 그러면 올바른 소통이 아닐테니까

이 교정에 따라 완료 예상과 관찰 조건을 서로 다른 개념으로 두었다. 완료 예상은 기계 빌드나 유한 입력 검사처럼 합리적인 근거가 있을 때만 기록하는 선택 정보다. 완료 예상은 작업의 착수 가능성, 실패, 중단이나 점유 상실을 직접 결정하지 않는다. 완료 시간을 예측하기 어려운 작업도 다음 관찰 조건은 가져야 한다. 다음 관찰 조건은 “이때까지 끝내라”는 마감이 아니라, 어떤 사건이 발생하거나 일정한 작업 단위·자원량·무관찰 구간에 도달했을 때 현재 상태를 다시 드러내라는 조건이다. 외부 계산이나 사람의 응답을 기다리는 작업은 기다리는 사건뿐 아니라 그 사건이 오지 않을 때 다시 상태를 확인할 시점도 함께 정한다.

작업 진전 계약은 외부 감시기의 판정표가 아니라 작업자와 감시기가 공유하는 운전 계약이다. 계약은 다음 내용을 함께 정한다.

- 이 작업의 목적에 기여하는 연구 상태 변화가 무엇인지
- 그 변화가 실제로 일어났음을 어떤 진전 신호와 근거로 확인하는지
- 작업자가 그 변화를 생산하거나 그 가능성을 시험하도록 내부 절차를 어떻게 구성하는지
- 작업자가 언제 자기 상태를 점검하고 외부에 드러내는지

프로세스가 살아 있다는 heartbeat, 사용한 시간이나 토큰, 로그·파일·보고의 양은 그 자체로 진전 신호가 아니다. 반대로 원하는 정리를 얻지 못한 시도라도 정확한 장애물, 반례, 범위 축소나 후속 선택을 바꾸는 근거를 남기면 계약이 정한 진전이 될 수 있다. 작업자는 측정 가능한 신호의 수를 실제 연구 목적 대신 최적화해서는 안 되며, 진전이 없을 때 보고용 산출물을 만들어 진전이 있는 것처럼 보여서도 안 된다.

### 2. 작업 자기 점검과 관찰 조건

작업 진전 계약을 작업자의 내부 운전에 사용하려면, 관찰 시점마다 작업자가 자신의 상태를 어떤 말로 기록하고 그 뒤 무엇을 할 수 있는지도 정해야 했다. 진전 신호가 한 번 없을 때마다 외부 운영 점검을 열면 탐색 작업이 작은 실패마다 끊긴다. 반대로 작업자가 계속 “조금 더 해보겠다”고 선언할 수 있으면 같은 방법을 반복하면서 점유를 유지할 수 있다.

이 두 위험 사이의 경계로 작업 자기 점검을 도입했다. 다음 관찰 조건이 도래하면 작업자는 실제 상태와 원자료를 작업 진전 계약에 대조해 변경 불가능한 자기 점검을 만든다. 결과는 다음 세 값으로 닫았다.

- `진전`: 계약이 정한 진전 신호와 그 근거가 있다. 이 값은 작업 국소의 판정이며, 전체 연구가 전진했다거나 수학적 내용이 인증됐다는 뜻은 아니다.
- `무진전`: 진전 신호는 없지만 시도한 방법, 확인한 사실, 실패 원인과 다음 방법을 근거 있게 기록했다.
- `계약 부적합`: 현재 계약의 진전 신호나 관찰 조건으로는 실제 작업을 올바르게 운전하거나 판정할 수 없다.

첫 `무진전`에는 내부 적응 한 번을 허용한다. 다만 기존 계약이 내부 적응을 허용해야 하고, 다음 방법이 앞선 방법과 실질적으로 달라야 한다. 다음 자기 점검도 무진전이거나 계약 부적합이면 운영 점검을 연다. 자기 점검이 없거나 무결하지 않은 경우와 `진전`이라고 기록했지만 계약이 요구한 근거가 없는 경우도 운영 점검 사유다.

결정론적 형식 검사는 자기 점검의 스키마, 필수 참조, 무결성과 증거의 존재만 판정한다. 진전 신호가 실제로 계약이 말한 상태 변화를 입증하는지, 새 방법이 이전 방법과 실질적으로 다른지는 의미 판단이므로 운영 점검이 원자료를 읽고 판정한다. 작업자가 계약 부적합을 발견해도 계약을 조용히 고칠 수는 없다. 그 불일치 자체를 기록하고 운영 점검이나 새 착수 명세 검토로 보낸다.

작업자가 사용하는 관찰 조건은 외부 감시기도 같은 작업자 공개 상태에서 재현할 수 있어야 한다. 사용자는 이 원칙과 예외를 다음과 같이 직접 정리했다.

> 즉. 작업자가 알 수 있는 모든 관찰 계기는 외부 감시기도 알 수 있어야 하며, 외부 안전 발동 조건 같이 외부 감시기만 알 수 있는 관찰 계기가 그에 추가로 더 외부 감시기에게 있을 수 있다. 이런거지? 그렇다면 승인

이 결정은 작업자와 외부 감시기가 모든 사실을 같은 방식으로 직접 본다는 뜻이 아니다. 작업자가 “충분히 탐색했다”거나 “생각이 막혔다”고 느낀 사실은 그 자체로 관찰 조건이 될 수 없다. 탐색한 범위, 시도한 방법, 확인한 장애물과 체크포인트처럼 외부 감시기도 읽을 수 있는 기록으로 상태를 드러내야 한다. 반면 프로세스 소실, 외부 실행 중단이나 실행 소유권 변경처럼 작업자가 직접 알 수 없는 사건은 외부 감시기만 사용하는 안전 조건이 될 수 있다.

다음 관찰 조건은 판본화된 일회성 세대로 묶는다. 같은 세대에 사건, 처리한 작업 단위, 자원량, 활성 실행 시간이나 외부 상태 변화를 함께 둘 수 있다. 그중 하나라도 먼저 도래하면 관찰 의무를 연다. 조건 평가는 `미도래`, `도래`, `평가 오류`로 닫았다. 알 수 없는 연산자, 깨진 참조나 읽을 수 없는 상태 때문에 조건 하나라도 평가하지 못하면 다른 조건이 참이어도 전체 결과는 평가 오류다. 참 조건 뒤에 계약 결함이 숨는 것을 막기 위해서다.

`도래`는 곧바로 운영 점검을 시작한다는 뜻이 아니다. 조건 도래와 운영 점검을 바로 연결하면 작업자가 자기 점검을 작성할 기회를 얻기 전에 감시기가 위반으로 처리할 수 있다. 따라서 도래 시 `실행 ID + 조건 세대 ID`로 식별하는 관찰 의무를 먼저 연다. 관찰 의무의 상태는 `응답 대기`, `충족`, `위반`이다.

작업자는 첫 안전 제어 경계에 도달한 뒤 다음 실질 행동을 시작하기 전에 자기 점검을 기록한다. 안전 제어 경계는 도구 호출이 반환되거나 모델 턴·반복 단위가 끝나는 것처럼, 작업자가 다음 행동을 선택할 수 있고 외부에서도 확인할 수 있는 시점이다. 끝나지 않는 도구 호출처럼 안전 경계가 오랫동안 나타나지 않을 수 있으므로 실행 환경과 도구 유형에 맞는 최대 응답 시각도 둔다. 최대 응답 시각은 작업 완료 마감이 아니다. 그 시각이 지나도 작업을 자동 중단하지 않고 운영 점검을 열어 장기 정상 실행, 교착, 외부 대기와 소실을 구별한다. 평가 오류와 외부 안전 발동 조건은 정상적인 자기 점검 응답을 기대할 수 없으므로 이 응답 조건을 기다리지 않는다.

### 3. 외부 감시와 운영 점검

관찰 조건을 결정론적으로 평가하는 역할과 실제 실행의 의미를 진단하는 역할을 하나의 AI에게 맡기면, 같은 입력에서 같은 관찰 결과를 재현한다는 원칙이 깨진다. 사용자는 외부 감시기의 구현 주체를 먼저 확인했다.

> 먼저 질문. 외부 감시기는 도구를 활용하는 AI 세션인가 아니면 결정론적 스크립트인가?

외부 감시기는 결정론적 스크립트로 확정했다. 외부 감시기는 작업자 공개 상태를 한 관찰 입력으로 고정하고, 닫힌 관찰 조건과 관찰 의무의 이행만 평가한다. 진전의 의미, 새 방법의 실질적 차이, 장기 실행의 합리성이나 부분 산출의 가치는 판단하지 않는다. 이상이 성립하면 실제 코드·로그·체크포인트·프로세스와 도구 상태를 읽는 운영 점검 AI를 원자적으로 하나만 연다. 운영 점검 AI가 의미 판단과 처분 제안을 맡는다.

처음에는 작업자와 외부 감시기가 하나의 실행 상태를 함께 갱신하는 방안도 검토했다. 그러나 사용자는 외부 감시기가 만든 관찰 기록을 작업자가 소비해야 한다는 전제 자체를 다시 열었다.

> 외부 감시기가 만든 것을 애시당초 작업자가 읽을 필요가 있나? 작업자가 만든 것을 외부 감시기가 읽는 방향은 당연히 있어야겠지만

이 교정에 따라 정상 감시는 단방향으로 정리됐다.

```text
작업자 공개 상태 → 외부 감시기 → 감시 기록 원장 → 운영 점검·심사
```

외부 감시기는 작업자 공개 상태를 읽고 관찰 입력·평가·의무 이행 판정과 점검 발동 근거를 감시 기록 원장에 쓴다. 작업자는 이 감시 기록을 읽지 않는다. 외부 감시기도 실행 ref나 작업 브랜치를 바꾸지 않는다. 역방향 전달은 운영 점검·심사·전례 관문이나 사용자 결정을 통과한 운영 처분이 실제 실행 제어를 바꿀 때만 허용한다.

작업자 공개 상태는 작업자가 외부 관찰에 내놓기로 확정한 실행 상태다. 작업자는 실제 연구 내용과 체크포인트를 작업 브랜치의 완결된 커밋으로 만든다. 그 좌표를 담은 실행 기록이 스키마·참조·무결성 검사를 통과하고 실행 ref로 공개된 뒤에만 정상 관찰 입력이 된다. 미커밋 변경과 쓰는 중인 부분 기록은 작업자 공개 상태가 아니다. 운영 점검 AI가 이상을 진단할 때는 읽을 수 있지만 정상 진전이나 관찰 입력으로 사용하지 않는다.

운영 처분이 작업자보다 먼저 실행 상태를 바꾸면 작업자가 기억하는 기대 상태는 낡는다. 그 상태에 결박한 공개 시도는 실패한다. 작업자는 안전 제어 경계에서 새 제어 상태를 읽고 자기 변경을 다시 적용할지, 중단할지, 처분이 지시한 다른 행동을 할지 판단한다.

### 4. Git 실행 상태

작업 브랜치는 실제 연구 파일과 여러 체크포인트를 소유한다. 실행 제어까지 같은 브랜치에 넣으면 운영 처분이 작업 내용을 건드리지 않은 채 중단·계속·인수 상태만 바꾸기 어렵다. 사용자가 다른 세션에서 가져온 제안은 작업 내용과 실행 제어를 분리하면서도 별도 데이터베이스나 잠금 계층을 만들지 않는 Git-native 구조를 제시했다.

> 이건 내가 다른 세션에서 질문해서 가져온 결과인데 이것도 검토해줘; 다만 앞선 설계는 용어와 구조를 더 단순하게 만들 수 있습니다.
>
> 실행 상태 커밋에는 작은 state.json 하나만 둡니다.
>
> 이 구조에서는 별도의 “매니페스트 연쇄”를 설계할 필요가 없습니다.
>
> git update-ref <실행-ref> <S3> <S2>
>
> - 작업 브랜치: 작업자가 실제 연구 내용을 소유
> - 실행 상태 ref: 공개한 작업 좌표와 실행 제어 상태를 소유

외부 제안을 그대로 채택하지 않고 공식 Git 문서와 격리된 임시 저장소로 검증했다. 수정 뒤 확정한 구조는 다음과 같다.

```text
refs/do-math/runs/<연구 인스턴스 ID>/<작업 ID>
    → state.json 하나를 가진 현재 실행 상태 커밋
    → 부모는 직전 실행 상태 커밋 하나
```

최초 실행 상태 커밋은 부모가 없다. 이후 상태 커밋은 직전 상태 커밋 하나만 부모로 가진다. 이 부모 관계가 별도 매니페스트 연결 필드 없이 실행 상태 이력을 이룬다. 작업 브랜치는 실제 연구 내용과 체크포인트를 소유하고, 실행 상태 ref는 외부에 공개한 작업 좌표와 실행 제어를 소유한다. `state.json`은 긴 산출물을 복제하지 않고 그 좌표와 무결성을 참조한다.

현재 실행 상태 커밋 OID는 상태 세대 식별자이자 예상 상태 토큰이다. 단조 증가하는 일반적 fencing 토큰은 아니다. 모든 권위 있는 쓰기가 현재 OID를 확인할 때 오래된 실행의 쓰기를 막을 수 있다. 작업자와 확정된 운영 처분 실행은 다음 조건부 갱신만 사용한다.

```text
git update-ref <ref> <new> <old>
```

현재 ref가 예상한 `<old>`와 다르면 갱신은 아무것도 바꾸지 않고 실패한다. 실패한 후보 상태 커밋은 현재 이력으로 재사용하지 않는다. 현재 ref를 다시 읽고 그 상태를 부모로 새 커밋을 만든다. 외부 감시기는 실행 ref를 읽기만 한다.

이 원자성은 한 연구 인스턴스의 작업자·감시기·운영 처분 실행이 같은 공통 Git 객체·ref 데이터베이스를 공유한다는 전제에서 성립한다. 현재 저장소의 여러 worktree는 이 전제를 충족한다. 서로 다른 clone이나 컴퓨터에서 실행하도록 확장하려면 중앙 저장소의 조건부 갱신 계약을 따로 설계해야 한다.

직접 검증한 결과는 다음과 같다.

- Git `2.50.0.windows.2`에서 실행 ref 이름이 `git check-ref-format`을 통과했다.
- 같은 이전 OID에서 만든 경쟁 갱신 둘 가운데 첫 갱신만 성공했고, 두 번째는 예상 OID 불일치로 실패했다.
- `git log`에는 승리한 단일 부모 상태 이력만 남았다.
- `state.json`에 작업 커밋 OID를 문자열로 기록해도 그 작업 커밋은 실행 ref에서 도달 가능한 객체가 되지 않았고 `git fsck --unreachable`에 잡혔다.
- 사용자 정의 실행 ref에는 reflog가 기본 생성되지 않았다.
- 임시 검증 저장소는 제거했다.

이 검증에 따라 작업 브랜치 ref가 실제 작업 머리와 체크포인트의 도달 가능성을 별도로 보존해야 한다. 실행 상태 이력은 reflog가 아니라 상태 커밋의 부모 관계를 정본으로 사용한다. Git notes는 별도 ref와 이력 문제를 줄이지 않았고, 태그도 자주 이동하는 현재 실행 상태의 의미에 맞지 않았다.

공식 근거: [git-update-ref](https://git-scm.com/docs/git-update-ref), [git-commit-tree](https://git-scm.com/docs/git-commit-tree), [gitrepository-layout](https://git-scm.com/docs/gitrepository-layout), [git-notes](https://git-scm.com/docs/git-notes).

### 5. 최신 공용 머리에 대한 편입

병렬 작업은 서로 같은 공용 커밋에서 시작할 수 있다. 작업 B가 `C10`에서 시작한 뒤 작업 A가 먼저 편입돼 공용 머리가 `C11`이 되면, B의 결과는 여전히 `C10`의 입력과 가정에 결박돼 있다. B를 그대로 편입하면 A의 변경을 덮거나 낡은 기준을 통과시킬 수 있다. 반대로 원 B 브랜치를 rebase하면 체크포인트와 실행 상태가 가리키는 커밋 OID가 바뀌어 실제 실행 이력을 보존할 수 없다.

사용자는 공용 머리의 후속 변경을 작업 B 쪽에 먼저 반영하는 방안을 제시했다.

> 작업 B의 브랜치에 자신이 시작한 커밋과 공용 머리 사이의 모든 커밋들을 적용한 다음 그 브랜치를 공용 머리에 적용하는 것은 문제가 있을까?

현재 공용 머리를 merge하면 그 조상 커밋 전건이 함께 들어오므로 하나씩 cherry-pick할 필요는 없다. 다만 원 작업 브랜치는 실제 실행 이력으로 보존해야 하고, 내부 실험·체크포인트 커밋을 공용 이력에 그대로 넣어서도 안 된다. 따라서 편입을 별도 임시 브랜치에서 수행한다.

1. 원 작업 브랜치를 최종 작업 머리에서 동결한다.
2. 그 머리에서 임시 편입 브랜치를 만든다.
3. 현재 공용 머리를 임시 편입 브랜치에 merge한다.
4. 텍스트 충돌뿐 아니라 바뀐 입력·가정·완료 기준, 핵심 기록의 의미와 현행 스키마·무결성·Lean·인증 기준을 다시 검사한다.
5. 검증한 최종 트리로 현재 공용 머리 하나만 부모로 갖는 작업 전용 공용 편입 커밋 하나를 만든다. 임시 편입 브랜치를 공용 머리에 직접 merge하지 않는다.
6. 검증 중 공용 머리가 다시 바뀌면 새 머리를 임시 편입 브랜치에 merge하고 재검증한다.

Git이 텍스트 충돌 없이 merge했다는 사실은 작업 B의 수학적·의미적 가정이 현재 상태에서도 유효하다는 뜻이 아니다. 작업 B가 직접 수정하지 않은 정의, 스키마, Lean 정본, 기초 프로필이나 완료 기준이 작업 A에 의해 바뀌었을 수 있다. 이 의미 충돌을 유일하게 해소할 수 없으면 자동으로 편입하지 않는다. 종결 결과를 보존하고 재검토·재작업으로 보낸다.

검증을 통과한 최종 트리만 공용 머리의 새 판본이 된다. 원 작업 브랜치, 임시 편입 과정과 실행 상태 이력은 공용 커밋의 조상으로 넣지 않고 별도로 보존한다.

### 6. 종결 이력 보존

활성 실행 중에는 실행 ref가 실행 상태 이력을, 작업 브랜치가 실제 연구 이력을 보존한다. 종결 뒤 점유를 해제하려고 실행 ref를 삭제하고 worktree·작업 브랜치를 제거하면, 공용 편입에 선별되지 않은 실행 상태·실패·체크포인트는 어떤 ref에서도 도달하지 못할 수 있다. Git GC는 이런 객체를 나중에 제거할 수 있다.

또한 `state.json`에 작업 머리 OID를 문자열로 기록해도 Git은 그 문자열을 객체 관계로 따라가지 않는다. 실행 상태 이력만 보존해서는 실제 작업 이력이 보존되지 않는다. 임시 편입 과정도 원 작업과 다른 Git 이력이다. 사용자는 실행 상태, 원 작업과 임시 편입의 세 이력을 모두 감사·복구용으로 보존한다고 확정했다.

```text
refs/do-math/archive/runs/<인스턴스>/<작업>/<실행>
refs/do-math/archive/work/<인스턴스>/<작업>/<실행>
refs/do-math/archive/integration/<인스턴스>/<작업>/<실행>
```

보관 ref는 데이터를 세 벌 복사하지 않는다. 각 이력의 마지막 커밋을 가리키고, 부모 관계가 나머지 이력을 보존한다. 보관 ref는 생성 뒤 이동하거나 덮어쓰지 않고 자동 만료로 삭제하지 않는다. 삭제나 압축은 별도 보존 정책이나 사용자 승인을 요구한다.

종결 적용은 다음 변경을 예상 공용 머리와 실행 상태 OID에 결박한 하나의 ref 작성 트랜잭션으로 묶는다.

- `terminal` 실행 상태 커밋을 확정한다.
- 단일 공용 편입 커밋으로 공용 머리를 갱신한다.
- 실행 상태·원 작업·임시 편입 보관 ref를 만든다.
- 활성 실행 ref를 삭제해 점유를 해제한다.

기대 OID가 하나라도 달라졌거나 만들 보관 ref가 이미 존재하면 트랜잭션 전건을 적용하지 않는다. 동시 독자는 여러 ref 가운데 일부가 바뀐 조합을 잠시 볼 수 있으므로, `terminal` 상태가 기록한 좌표와 현재 공용 머리·보관 ref 전건을 다시 대조한다.

보관 ref가 생긴 뒤에만 worktree와 활성 작업 브랜치를 정리한다. worktree 청소가 실패해도 이미 보존한 이력과 공용 편입은 무효화하지 않는다. 청소 실패는 후속 작업으로 기록한다. 감시 기록 원장은 세 보관 ref와 별도로 보존한다.

### 7. 정본 갱신 시점

이번 세션 초반에는 사용자 결정을 받을 때마다 `CONTEXT.md`, 지도 컨텍스트와 진행 티켓 본문을 수정했다. 이 방식은 대화 중간 상태를 파일에 계속 쌓는다. 뒤의 결정이 앞의 결정을 대체하면 같은 개념의 문면이 여러 곳에 남거나 서로 모순할 수 있다. 사용자는 정본 갱신을 세션 종결 시점에 한 번으로 모으라고 지시했다.

> ## 이번 연속 작업의 추가 지시 는 지우고, 일괄 적용은 지금 하고, 그에 맞춰서 댓글도 수정하고, 앞으로 CONTEXT.md와 컨텍스트.md의 수정은 핸드오프 및 티켓 종료 등을 이유로 세션이 종결될 때 한 번에 모아서 하도록 지침을 명시.

이 절차를 [지도 Notes](https://github.com/MegasKomnenos/math/issues/6)의 상시 지침으로 반영했다. 같은 티켓을 이어가는 세션은 결정마다 두 컨텍스트 파일을 고치지 않는다. handoff·티켓 종료 등 세션이 끝날 때 그 세션의 확정 결정을 원자료와 대조해 일괄 갱신한다. 새 결정이 대체한 옛 문면과 중복도 함께 제거한다. 티켓 종료 세션은 이 일괄 갱신을 커밋한다.

이번 일괄 갱신에서는 증분 편집으로 root `CONTEXT.md`에 들어간 Git·JSON·ref·OID 문면도 감사했다. root 파일에는 보편 도메인 개념만 남기고 물리 구현 계약은 지도 컨텍스트와 진행 티켓 본문으로 옮겼다. handoff는 결정 경위를 보존하지만 현행 실행 문면을 중복 소유하지 않는다.

## 현재 미결정과 첫 질문

다음 제안은 아직 승인되거나 기각되지 않았다.

연구 작업의 **절차적 종결 처분**과 그 작업이 낸 **수학적·연구 결과**를 독립된 두 축으로 둔다. “작업 절차를 약속대로 끝냈는가”와 “그 작업에서 무엇을 알아냈는가”는 서로 다른 질문이기 때문이다.

예를 들어 지정한 후보 기법을 충분히 조사한 끝에 적용할 수 없다는 근거를 얻었다면, 작업은 계약을 충족했으므로 `완료`다. 그 작업의 연구 결과는 후보 경로 배제다. 반대로 프로세스 소실로 계약을 끝내지 못했지만 유용한 부분 증명을 남겼다면, 종결 처분은 `운영 실패 종결`이고 연구 결과에는 그 부분 증명과 한계를 기록할 수 있다. 두 정보를 한 상태에 넣으면 “실행이 실패했는가”와 “연구적으로 얻은 것이 없는가”를 구별할 수 없다.

종결 처분은 실행 절차가 어떻게 끝났는지를 나타내며 다음 네 값으로 닫는다.

- `완료`: 약정한 범위·산출물·완료 기준을 충족했다.
- `분할 종결`: 즉시 공유할 독립 결과까지 현재 작업을 완료하고 잔여 범위를 새 작업 씨앗으로 옮겼다.
- `취소`: 목적 변경·중복 제거·선행 결과 대체 같은 권위 있는 결정으로 완료 전에 끝냈다.
- `운영 실패 종결`: 운영 문제로 계약을 완료하지 못해 운영 점검과 처분 뒤 현재 실행을 끝냈다.

`중단`, `외부 대기`, `체크포인트 보존`, `재시도 대기`는 재개 가능한 실행 상태이며 종결 처분이 아니다.

수학적·연구 결과는 별도 필드에 근거와 실제 범위를 함께 기록한다. 입증·반증, 조건부·제한 범위 결과, 후보 경로 강화·배제, 반례·장애물, 불확실성 감소, 새 발견 후보, 지정 범위에서 결과 없음과 판정 불가는 열린 예시다. 하나의 범용 결과 상태로 닫지 않는다.

다음 경계를 함께 적용한다.

- 긍정적인 수학 결과가 없어도 작업 계약을 충족하면 `완료`일 수 있다.
- 유용한 부분 산출물이 있어도 운영 문제로 계약을 완료하지 못했으면 `운영 실패 종결`이다.
- `취소`는 실패 판정이 아니라 작업 필요성의 권위 있는 철회다.
- `분할 종결`은 중간 공용 편입이 아니다. 현재 작업을 실제로 종결하고 잔여 범위를 새 작업으로 옮긴다.
- 모든 종결 처분은 실제 결과·한계·부분 산출과 후속 작업 씨앗을 기록하고 종결 공용 편입 한 번을 수행한다.
- 수학적 해결은 작업 종결 처분이 아니라 Lean 정본 편입과 프로젝트 성공 기준이 판정한다.

다음 세션은 이 두 축과 네 종결 처분을 확정할지 질문 하나만 한다. 사용자 답을 받기 전에 정본과 이슈를 수정하지 않는다.

## 그다음에 가까이 보이는 미결정

첫 질문을 닫은 뒤 선행 관계를 다시 계산한다. 현재 가까이 보이는 범위는 다음과 같다.

- 종결 처분별 공용 편입·후속 씨앗·실행 상태·보관 ref의 정확한 전이
- 실행·감시·진전·관찰·자기 점검 기록의 정확한 JSON 스키마
