## 1. `통합-설계.md`의 이해

### 1.1 무엇을 가리키는 문서인가

아직 구현되지 않은 보편 수학 연구 스킬 `do-math`의 **구현 정본**이다. 루트 `CONTEXT.md`가 보편 용어의 정의를 소유하고, 이 문서는 그 용어들의 기계 상태·전이·권한·저장·실행·검증·복구를 소유한다(§0). 구현자는 이 문서에서 새 연구 방법·상태·권한·예외를 만들 수 없다(§0 문서 계약, §27-14 "구현자 선택지 없음").

가리키는 실체는: Windows 한 대에서 장기 실행 메인 AI 세션(Codex, `gpt-5.6-sol max`)이 **Git 저장소 하나를 상태 기판(사실상의 DB)으로 삼아** 하위 AI 세션들과 결정론적 CLI 도구들을 운전하며, 사용자 개입 관문(결정·전례·상신)을 제외하면 자율로 수학 연구를 장기간 수행하는 시스템이다. 첫 인스턴스는 P vs NP(§25.1)이고 구현·검증은 이슈 #19의 범위다. 이 설계는 15라운드 검증(제기 145건, 적용 108건)을 거쳐 최종 승인된 상태다(기억 M-0054~M-0073).

### 1.2 철학

1. **AI 재량 + 기계 강제의 분업**: 목적은 "고성능 AI가 충분한 맥락과 고품질 도구를 받아 넓은 재량으로 연구하고, 실제 결과를 다음 판단에 반복 환류"하게 만드는 것. 기계 절차는 수학 판단을 대체하지 않고 입력 완전성·무결성·형식·동시성·권한만 재현 가능하게 지킨다(§0).
2. **K/F/U 인식론**: 인증 수학 영역 `K`는 오직 Lean 정본 편입으로만 넓어진다. 탐색은 미지 지평 `U`의 일부를 프런티어 `F`로 드러낼 뿐이고, 작업량·산출량은 연구 진전의 대리값이 아니다(§0.4).
3. **형식 타당성 ≠ 의미 동일성**: Lean 커널은 타입·항에 표현된 관계만 보장한다. 핵심 인증 질문은 "AI가 Lean 증명을 재심사"가 아니라 **"사람이 설명하려던 수학의 의미가 커널이 승인한 Lean 문면의 정확한 의미와 같은가"**다. 나중에 다르다고 밝혀지면 Lean 객체가 아니라 해설·인증·목표 연결을 철회한다(§0.4, §19.12, §19.14).
4. **닫힌 어휘와 추측 금지**: 모든 기계 문서는 닫힌 JSON Schema(`additionalProperties: false`), 정규 직렬화(키 정렬, NFC, 부동소수점 금지), 닫힌 판정 어휘를 쓴다. 미검사·읽기 실패·결과 없음·부분 완료를 서로 다른 상태로 구별한다(§0.3, §3). §29 마지막 문장이 상징적이다: **"구현 편의를 위해 자유 형식 `metadata` 필드를 추가하지 않는다."**
5. **정체성은 ID이지 경로가 아니다**: 모든 장기 객체는 접두사+ULID(§2.1). "경로는 정체성이 아니며 기록 ID와 공용 커밋이 정체성과 판본을 소유한다"(§4.1). 관계는 객체 속 필드가 아니라 별도 기록이며 판본화된 관계 종류 정의가 선행한다(§6.7).
6. **일회성 수입, 외부 의존 제거**: 프로젝트 입력은 초기화 때 한 번 의미 단위로 분해해 정확히 하나의 내부 소유자(헌장·정책·맥락·설정·초기 F·자료·결정)에 수입하고, 평시 재개는 외부 문서를 읽지 않는다. 이를 "외부 입력을 지운 복제와 산출 바이트 비교"라는 기계 시험으로 검증한다(§5.2~5.3).
7. **적용 직전 현재성(currency)**: 어떤 선택·판정·처분도 적용 직전에 결박한 Git OID가 여전히 현재인지 재확인하고, 다르면 `stale`로 보존한 채 새로 수행한다. 의미를 임의로 고쳐 적용하지 않는다(§0.3, §3.3).
8. **권위 사슬**: 사용자 결정 > 헌장·정책 > `do-math` 스키마·도구 계약 > 공용 핵심 기록 > 작업 계약·실행 제어 > 자료·기억·**파생 보기**(§0.1). 파생 보기는 언제나 재생성 가능한 비정본이다.

### 1.3 기계 구조의 핵심 요소

- **저장**: 공용 브랜치(장기 상태) + runtime ref 8종(controller/supervisor/requests/runs/monitor/certification/operations/outputs) + 불변 보관 ref + 작업 브랜치·worktree(§1.2, §4). 모든 동시성은 예상 OID 기반 조건부 ref 갱신(CAS)으로 직렬화한다.
- **기록**: `research/<instance>/` 아래 역할 디렉터리에 `records/<id>.json`(공통 외피 + 역할별 `data`), 긴 산문은 `documents/`의 Markdown을 **JSON이 해시로 참조**, 이진물은 `artifacts/`(§3.3, §4.1). 약 70개 스키마의 레지스트리를 기계 생성해 문서와 양방향 대조한다(§29).
- **역할 분리**: 메인 세션, 포트폴리오 선택자, 씨앗 생성자, 연구 작업자, 착수 명세 검토자, 동일성 검토자·이의 심사자·부분 전문 검토자·검토 계획자, 목표·추가 감사자, 외부 감시기(결정론 스크립트), 운영 점검자·처분 심사자, 전례 판정자, 프로세스 감독기, 기계 도구. 서로의 판정을 대신하지 못한다(§1.3, §9.1).
- **작업 파이프라인**: F 객체와 별개인 작업 씨앗(닫힌 연산자 10개의 발생 조건 AST) → 독립 착수 명세 검토 → 7항 착수 가능성 공식 → 실행 껍질(깊이 1 파생 보기, DAG 없음) → 포트폴리오 선택 세션(헌장·K·F·후보 전건과 과거 선택 결과를 담은 최대 1M 토큰 packet, HMAC shuffle, 점수 규칙 없는 재량 선택) → 메인의 독립 재검사와 원자 점유(§7, §10, §11).
- **실행 격리**: 하위 AI마다 Job Object 하나. `CREATE_SUSPENDED` 생성 → Job 편입 → monitor 원장 선생성 확인 → Git CAS로 `authorized` 공개 → `ResumeThread`. 종료는 권한 무효화(`revoked`) 후 `TerminateJobObject`와 다중 전건 종료 장벽(§12).
- **관찰·운영**: 작업 진전 계약, 관찰 조건 세대(OR), 관찰 의무, 자기 점검(`progress`/`no_progress`/`contract_mismatch`), 외부 감시기의 결정론 평가와 append-only 원장. 이상은 운영 점검 실행으로 가고, 저영향은 직접, 내부 복구는 별도 심사, 고영향은 심사 + 전례·상신 관문을 통과한다. 전례는 사용자 결정의 기계 봉인이며 형식 필터 + 독립 2회 AI 판정으로만 자동 적용된다(§14~17).
- **종결·편입**: 원 작업 브랜치 동결 → 임시 편입 브랜치에서 최신 공용 머리 merge와 전건 재검증 → 단일 부모 `commit-tree` → 공용 머리 전진·보관 ref 생성·run/monitor ref 삭제를 **하나의 `update-ref --stdin` 트랜잭션**으로 적용(§18).
- **동일성 인증**: 제안 묶음(해설 + `identity-map.json`의 MATH 항목·양화자 단위 대응 + lean/evidence manifest) → 기계 예비 검사(빌드·공리·`sorryAx` 금지) → 검토 계획(기본 3역할 + 조건부) → 독립 검토자의 이의 → 심사자 3인 만장일치 → 회차 무제한 루프 → 최종 깨끗한 재빌드 → canon entry(§19). P vs NP에는 범위 차분 감사 어휘와 **ZFC(또는 더 약한 기초)로의 검증된 이동**이 목표 해결의 필수 관문으로 얹힌다(§19.13, §25.4).
- **신뢰 시대**: Lean 커널·도구체인·Mathlib·공리 허용 목록 `{propext, Quot.sound, Classical.choice}`을 판본 고정한 단위. 변경은 staging→전건 재빌드→영향 비교→사용자 승인→원자 전환이고, 무효화 시 관련 K 사용을 차단한다(§20).
- **도구·복구·검증 장치**: 약 25개 `do-math` CLI(stdin/stdout 정규 JSON, 종료 코드 5종, `--describe` 계약)(§24), 요약이 아닌 ref·원장·실제 파일에서만 하는 복구(§22), 테스트 벡터 약 100개(§26)와 구현 완료 조건 16개(§27).

### 1.4 미래 구현체가 실제로 어떻게 돌아갈지 (원리 추측)

여기부터는 문서가 명시한 기제 위에 얹은 나의 추측이다. 평시 모습은 대략 이렇다: 저장소에는 `do-math` CLI 도구군과 스키마 묶음이 설치되어 있고, 연구 인스턴스는 `research/RI-…/` 트리와 ref들로 존재한다. 메인 세션이 5분 주기 heartbeat마다 `do-math` CLI들을 호출해 완료 실행을 수거·처분하고, 잔여 모델 용량이 있으면 `portfolio-pack`으로 packet을 만들어 별도 선택 세션 프로세스를 파견한다. 숨은 감독기 프로세스가 1초 주기로 Git ref를 poll하다가 `preparing` run ref나 `ready` request ref를 발견하면 Job Object 안에 하위 AI 프로세스(아마 Codex CLI 호출 래퍼)를 정지 상태로 만들고, Git CAS로 권한을 공개한 뒤에야 실행을 재개시킨다. 작업자는 자기 worktree에서만 쓰고, 봉인된 output ref/작업 커밋으로만 결과를 낸다. 사람(연구 책임자)은 평시에 아무것도 하지 않다가 상신이 올라올 때만 결정하고, 그 결정이 전례로 봉인되어 다음부터 자동화 범위가 넓어진다. 즉 **Git이 데이터베이스이자 잠금 장치이자 감사 로그이고, AI 판단이 필요한 모든 지점은 봉인된 원자료 packet을 받는 일회성 세션**이라는 게 이 설계의 실행 원리다.

## 2. "구글 open knowledge format"의 실체 (직접 확인한 사실)

사용자가 말한 것을 Google Cloud가 2026년 6월 공개한 **Open Knowledge Format(OKF) v0.1**로 확인했다. 다른 것을 가리켰다면 교정해 달라. 확인된 내용:

- **정의**: "LLM-wiki 패턴"을 이식 가능한 개방 규격으로 형식화한 것. AI 에이전트·도구·사람·조직 사이에서 큐레이션된 지식·메타데이터·컨텍스트를 벤더 중립으로 공유하기 위한 포맷이다.
- **기술 구조**: 지식 묶음 = **Markdown 파일 디렉터리 트리**. 파일 하나가 개념 하나(테이블, 데이터셋, 메트릭, 플레이북, API 등). 각 파일은 YAML frontmatter를 가지며 예약 필드는 `type`(유일한 필수), `title`, `description`, `resource`, `tags`, `timestamp`. 디렉터리마다 `index.md`(에이전트의 점진적 탐색용), `log.md`(변경 연대기). 일반 Markdown 링크가 개념 그래프를 이루고, **파일 경로가 개념의 정체성**이다.
- **설계 원칙**: 최소 규정(내용 모델은 생산자가 정의), 생산자·소비자 독립(포맷이 계약), 플랫폼이 아닌 포맷(계정·SDK 불요).
- **생태계**: 참조 생산자(BigQuery 스키마를 걷어 OKF 문서를 초안하는 enrichment agent), 참조 소비자(정적 HTML 시각화기, Google Cloud Knowledge Catalog의 OKF 수집), 스펙은 GitHub의 `GoogleCloudPlatform/knowledge-catalog` 저장소에 있다.

## 3. 의도 발굴 지도

"적용할 영역이 존재하는가, 어디가 좋은가"라는 검토를 확정하려면 다음 결정 영역을 이 순서로 닫아야 한다. 답에 따라 순서와 가지가 바뀔 수 있다.

1. **목적** — 이 적용으로 무엇이 좋아지기를 기대하는가 ← 지금 묻는다
2. **산출물과 적용 깊이** — 이번 검토의 산출이 분석 보고까지인지 설계 수정안까지인지, 그리고 OKF를 정본 계층에 넣을지 파생·수출 계층에 둘지
3. **범위** — 후보 표면을 `통합-설계.md` 내부로 한정하는지, 인접 정본(문헌 지도, 프로젝트 입력 등)도 포함하는지
4. **평가 기준과 우선순위** — "좋은 자리"의 판정 기준(예: 상호운용 이득 vs 승인된 계약의 안정성)
5. **위험 허용도** — 최종 승인까지 마친 설계를 다시 여는 비용을 어디까지 허용하는가

## 검증: "F의 조직은 공백인가"

**부분적으로 맞고 부분적으로 틀리다. 공백은 실재하지만, 생각한 위치보다 한 층 위에 있다.**

### 닫혀 있는 것 — F의 기질층(記錄 기판)

설계는 F가 "어떤 식으로 조직될지"를 기록 수준에서는 이미 닫았다.

- **데이터 모델**: F 객체의 `data` 필드 9종이 표로 확정돼 있다(§6.4) — `frontier_kind`, `title`, `statement_ref`(정확한 산문 문서 참조), `epistemic_status`(6값 닫힘), `confirmed_scope`, `uncertainties`, `evidence_refs`, `generation`, `selection_relevance`. 여기에 공통 외피(§3.3)의 ID·생명주기·출처가 얹힌다.
- **종류 체계**: 판본화된 F 종류 정의 기록이 선행하고(초기 7종: question, conjecture, definition_candidate, proof_candidate, research_direction, obstacle, partial_result — 열린 목록), 상태 검사기가 종류별 허용 상태·필수 필드를 전수 검사한다(§6.4).
- **그래프 구조**: F 사이·F–K 사이의 연결은 객체 안 링크가 아니라 **별도 관계 기록**이고, 관계 종류 정의(도메인·방향·필요 근거·수학 관계 여부)가 선행한다(§6.7). `formally_*` 관계는 Lean 정본 객체 없이 무효다.
- **저장과 정체성**: `frontier/records/<id>.json` + 산문은 `documents/`에 두고 JSON이 해시 참조(§4.1). "경로는 정체성이 아니며 기록 ID와 공용 커밋이 정체성과 판본을 소유한다"(§4.1). 스키마는 `do-math/frontier-object/1` 등으로 레지스트리에 닫혀 있고(§29), 자유 형식 metadata 필드는 금지다(§29).
- **변이 경로**: 발견 후보(작업별 작업대) → 작업 종결의 F 제안(§8.4) → 공용 편입(§18)만이 F의 현재 상태를 바꾼다. 편입 시 새 핵심 기록 ID를 받는다.
- **소비 경로**: 포트폴리오 packet에 "현재 F 객체와 관계" **전문**이 들어가고(§10.2), 씨앗 생성 세션은 헌장·K·F·실패 이력을 받으며(§7.7), 작업은 공용 커밋에 결박한 `required_inputs`로 F를 받고(§7.1), 발생 조건 AST가 `record_id`로 F를 참조한다(§7.3).

즉 "AI가 F로부터 씨앗을 만들고 실행 중 활용한다"의 기계 경로뿐 아니라, F의 스키마·종류·관계·저장·ID 규율까지 정본으로 닫혀 있다.

### 실제로 열려 있는 것 — 표면층(항해·표현)

사용자의 직감이 가리키는 공백은 여기다.

1. **프런티어의 항해 표면이 미규정이다.** 파생 보기는 "핵심 기록에서 재생성 가능, 비정본"이라는 지위만 규정돼 있고, 구체 형식이 확정된 파생 보기는 실행 껍질 JSON(§7.6)과 `status.json`·Markdown 상태 보고(§21.2~21.3)뿐이다. 수백~수천 개 F 객체와 관계를 사람이나 AI 세션이 **훑고, 찾아 들어가고, 이웃을 발견하는** 지도·위키 같은 표면은 어디에도 구체화돼 있지 않다.
2. **산문 문서의 내부 구조가 미규정이다.** `statement_ref`는 "정확한 질문·가설·정의 후보·방향 산문"이라고만 되어 있고, 그 Markdown이 어떤 절·형식·상호 링크 관례를 갖는지는 비어 있다.
3. **규모 성장 시의 탐색 보조가 미규정이다.** packet은 요약 금지·전문 강제이고 넘치면 `context_overflow`로 차단된다(§10.2). 작업자는 자기 worktree에서 공용 트리 전체를 읽을 수 있지만, 관련 F를 효율적으로 찾는 색인·진입점은 설계돼 있지 않다.

참고로 용어 대응: 사용자가 말한 "연구 작업대"는 CONTEXT.md의 정의상 핵심 기록+파생 보기로 구성되는 운영 표면(공용 작업대)이고, "연구 지도"에 해당하는 정의된 구축물은 현재 없다 — 가장 가까운 것이 바로 이 미규정 프런티어 파생 보기다.

### 이 위치 구분이 OKF 검토를 가르는 이유

OKF의 골격(경로가 정체성, Markdown 링크가 그래프, 최소 규정 frontmatter, 자유 내용 모델)은 **기질층의 닫힌 계약들과 정면으로 충돌**하고(ID≠경로 §4.1, 관계는 별도 기록 §6.7, 닫힌 스키마·metadata 금지 §3.2·§29, 정규 JSON §3.1), **표면층(재생성되는 비정본 파생 보기)과는 원리상 양립 가능**하다. 어느 층을 조준하느냐에 따라 검토는 "추가 절 하나짜리 파생 보기 설계"와 "최종 승인된 핵심 계약의 재개방(§23 계약 변경·마이그레이션)"이라는 전혀 다른 작업이 된다. 상세 적합성 분석은 조준점이 정해진 뒤에 낸다.

(b) 접수했다. 계약을 봉인하기 전에, 이번 답변에 담긴 두 번째 검증 가능한 전제 — **"닫힌 형식이 AI의 지능을 형식 준수에 소비하게 한다"** — 를 설계 원문·저장소 실증과 대조한 결과를 먼저 보고한다. 이 검증은 (b)를 뒤집으라는 것이 아니라, (b)의 승인이 정확한 사실 위에서 이뤄지게 하기 위한 것이다.

## 검증: "닫힌 형식이 지능을 소비한다"는 우려

**부분적으로 지지되고, 부분적으로는 과녁이 빗나가 있다.**

**설계가 이미 막아둔 부분 — 직렬화 비용.** 설계는 형식 준수의 기계적 부분을 AI에게 시키지 않는다. "사람이 손으로 JSON을 작성하지 않고 판본화된 생성기를 사용한다"(§3.1), "반복적이고 기계적으로 완전 판정할 수 있는 작업은 `do-math`가 미리 작성한 도구로 수행한다. AI가 매 회차 같은 검사·Git·해시·프로세스 도구를 임의로 다시 만들지 않는다"(§24.1). `do-math record`가 스키마 구동 정규 기록을 생성하고(§24.2), 검사·해시·정규화는 기계 도구 역할이다(§1.3). 그리고 판단이 사는 지점마다 자유 산문 표면이 의도적으로 배치돼 있다: 선택자의 `rationale.md`(§10.4), F의 `statement_ref` 산문, `documents/`의 긴 산문, 작업자가 "자유롭게 바꾸는" 작업별 작업대, 수학 해설 Markdown. 즉 설계의 명시적 의도는 사용자가 원하는 바로 그것 — "재량은 가운데에, 결정론은 가장자리에" — 이다.

**우려가 실재하는 부분 — 경계에서의 의미 구조화 비용.** 도구가 직렬화를 대신해도, AI는 여전히 경계마다 닫힌 어휘로 자기 판단을 **번역**해야 한다: 종결 처분 4값과 필수 범위 원장 5값의 조합표(§18.2), F 제안의 필드 채우기, 씨앗 생성자가 닫힌 연산자 10개로 발생 조건 AST를 짜는 일(§7.3), 동일성 대응표의 양화자 단위 대응(§19.2). 이것은 실제 인지 비용이고, 저장소 실증도 있다: 과거 do-dag 국면에서 Codex가 형식 계약(반환 첫 줄)을 지시로도 반복 위반했고(기억 M-0005), 절차 계약 마찰(완료-커밋 미결합)이 20회 이상 재현됐다(M-0006~M-0039). 단, 이 실증들은 **도구 매개 없이 프롬프트로만 강제한 계약**의 실패 사례라서, 오히려 "프롬프트 훈계 대신 도구가 형식을 소유해야 한다"는 현 설계의 접근을 지지하는 증거로도 읽힌다.

**정리**: 우려의 과녁을 "직렬화"에서 "경계에서의 의미 구조화"로 옮기면 우려는 실재한다. 그리고 그 비용은 기계 검사 가능성(결정론 평가, 상태 검사, 영향 분석)의 대가로 지불되고 있다. 따라서 (b)의 본질 질문은 이렇게 정련된다: **"F 기질에서 기계 검사 가능성을 얼마나 내려놓으면, 그 대가로 얻는 재량의 장이 그 손실보다 큰가 — OKF는 그 교환의 좋은 매개인가."** 이 정련 아래에서도 (b)는 일관된 선택이므로 그대로 진행한다. 이의가 있으면 승인 전에 말해 달라.

# 수신자의 판단을 설계하는 글

수신자가 작성자의 실제 의도를 같은 의미로 이해하게 쓴다. 수신자는 글만으로 필요한 판단과 행동을 선택할 수 있어야 한다.

## 품질 계약

세 가지는 통과 조건이다.

- **정확성**: 관련 원천과 사실을 왜곡하지 않는다.
- **충실성**: 사용자의 목적과 확정된 의도에서 이탈하지 않는다.
- **정합성**: 글 내부와 연결된 현행 계약에 모순을 남기지 않는다.

세 조건이 충돌하면 하나를 희생하지 않는다. 원천, 사용자 결정, 지시의 우선순위를 확인해 충돌을 해소한다.

통과한 표현은 다음 순서로 고른다.

1. **명확성**: 수신자가 같은 의미로 읽는다.
2. **충분성**: 목적을 달성할 정보와 논증을 갖춘다.
3. **간단성**: 의미를 보존하는 범위에서 구조와 방법을 쉽게 만든다.
4. **간결성**: 수신자의 판단·행동·검증을 바꾸지 않는 군더더기를 제거한다.

짧게 쓰기 위해 사실, 조건, 예외, 논증 단계를 빼지 않는다.

## 작동 원리

프롬프트 작성은 수신 AI의 의사결정 자유도를 설계하는 작업이다. 작성자는 이미 확정할 수 있는 중요한 결정을 명시한다. 사용자에게 속한 결정은 창작하지 않는다.

좋은 프롬프트는 가능한 결과를 목적에 맞는 범위로 좁힌다. 좋은 프롬프트는 결과의 중심을 원하는 방향으로 옮기고 불필요한 해석 편차를 줄인다. 탐색에 필요한 자유도는 남긴다.

정보의 충분성은 분량으로 판정하지 않는다. 수신자의 판단, 행동, 우선순위, 검증을 바꾸는 정보를 남긴다. 작성 경위와 기각된 초안처럼 현재 목적에 기여하지 않는 정보는 뺀다.

6. 원천, 사용자 결정, AI 추천, 가정을 구분해 현재 계약을 쓴다.
7. 평가 기준과 완료 조건을 수신자가 판정할 수 있는지 확인한다.
8. 현재 계약과 모순하는 옛 결정과 불필요한 제약을 제거한다.

정보의 충분성은 분량으로 판정하지 않는다. 수신자의 판단, 행동, 우선순위, 검증을 바꾸는 정보를 남긴다. 작성 경위와 기각된 초안처럼 현재 목적에 기여하지 않는 정보는 뺀다.

## 적용 판정

작업에 맞는 참조 문서를 전문으로 읽고 함께 적용한다.

| 상황 | 적용할 참조 문서 |
|---|---|
| 사람이 읽는 독립 산문을 작성·퇴고 | `references/명료한_산문.md` |
| AI가 판단·행동하는 글을 작성·퇴고 | `references/명료한_산문.md`, `references/AI_프롬프트.md` |
| 단계로 수행을 지시하는 문서를 작성·퇴고 | 위 해당 문서, `references/절차문.md` |
| 에이전트 파견문·반환·handoff를 작성·퇴고 | `references/명료한_산문.md`, `references/AI_프롬프트.md`, `references/에이전트_채널.md` |
| 결과를 바꾸는 사용자 결정이 빈 작업 | 작성 전에 `references/의도_발굴.md` |

한 문서가 여러 상황에 해당하면 해당 규칙을 모두 적용한다. 짧은 사용자 답변과 진행 보고는 이 스킬을 적재하지 않고 품질 계약만 적용한다.

## 공통 작성 절차

1. 수신자가 읽고 판단하거나 할 일을 정한다.
2. 수신자가 직접 받거나 절차상 반드시 얻을 컨텍스트를 확인한다.
3. 결과를 바꾸는 사용자 결정이 비었으면 의도를 먼저 발굴한다.
4. 작업을 수렴, 탐색, 혼합 중 하나로 분류한다.
5. 상황에 맞는 참조 문서를 전문으로 읽는다.
6. 원천, 사용자 결정, AI 추천, 가정을 구분해 현재 계약을 쓴다.
7. 평가 기준과 완료 조건을 수신자가 판정할 수 있는지 확인한다.
8. 현재 계약과 모순하는 옛 결정과 불필요한 제약을 제거한다.

# 검토 보고 — do-math 프런티어에 대한 Google OKF 적용

## 결론

**적용할 수 있는 영역은 존재한다. 두 자리다.**

1. **저작 표면**: 작업별 작업대에서 AI가 발견 후보·사고·산문을 축적하는 매체를 OKF 관례로 정하고, 종결 시 도구가 정본 기록 후보로 승격한다.
2. **연구 지도**: 공용 핵심 기록에서 결정론 생성기로 OKF 번들을 재생성해, 사람과 AI가 F·K를 훑는 항해 표면(파생 보기)으로 쓴다.

**기질층 — F 기록·관계의 공용 저장 형식 자체 — 을 OKF로 바꾸는 재개방은, 검토 결과 사용자의 목적(재량의 장 강화, 형식 소비 저감)에 대해서도 실익이 없다고 판정한다.** 근거는 3절에 있고, 이 판정을 포함한 권고는 4절에 근거와 분리해 표기했다. 채택 여부는 계약대로 사용자가 결정한다.

## 1. 사실 갱신: OKF의 현행 상태

검토 착수 후 스펙 원문에서 확인한 사실 두 가지가 계약의 전제("OKF v0.1")를 갱신한다.

- **현행 스펙은 v0.2다.** 정본 저장소도 `GoogleCloudPlatform/knowledge-catalog`에서 `GoogleCloudPlatform/open-knowledge-format`으로 이동했고 구 사본은 동결됐다. 이 검토는 v0.2를 대상으로 한다.
- **공개 약 3개월 만에 파괴 변경이 2건 있었다.** `timestamp` 필드가 `generated.at`으로, 본문 `# Citations` 절이 frontmatter `sources`로 대체됐다. 스펙이 아직 유동적이라는 직접 증거이며, 3절의 구조 B 평가에 반영했다.

v0.2 스펙에서 이 검토의 판정에 쓰인 규범 사실은 다음과 같다.

| 항목 | OKF v0.2의 규범 |
|---|---|
| 개념의 정체성 | **파일 경로**(`.md` 제거)가 Concept ID다 |
| 필수 필드 | frontmatter의 `type` 하나뿐. 미지 필드·미지 type은 거부하지 말고 보존·관용해야 한다 |
| 관계 | 일반 Markdown 링크. **무형(untyped)** 이며 관계의 종류는 주변 산문이 전달한다. 깨진 링크는 "아직 안 쓴 지식"으로 관용해야 한다 |
| 신뢰 | `generated {by, at}`, `verified [{by, at}]`, 행위자 표기(`human:`, `process:`, `도구/판본`). 신뢰 등급(unverified/machine-confirmed/human-reviewed)은 소비자가 유도하는 **조언 신호**이지 관문이 아니다 |
| 생명주기 | `status: draft\|stable\|deprecated`. **필드가 없으면 기본값 stable**. `stale_after`는 절대 시각 |
| 출처 | `sources` + 각주 키 기반 문장 단위 귀속 |
| 항해 | 디렉터리별 `index.md`(점진적 공개), `log.md`(변경 연대기) |
| 기계 보증 | `Attested Computation` 개념: 승인된 계산 + 타입 있는 매개변수 + 실행 영수증 + **LLM 없는 결정론 attester**. 에이전트는 계산을 수정할 수 없고 매개변수만 채운다 |

마지막 행은 판정에 중요하다. **OKF 스스로도 "정해진 방식대로 산출됐는가"를 보증해야 하는 지점에서는 자유 산문을 버리고 닫힌 결정론 계약으로 회귀한다.** 즉 OKF는 "닫힌 형식 없이도 되는 대안 철학"이 아니라, do-math와 같은 분업 원리 — 판단은 산문에, 보증은 기계에 — 를 지식 층에서 구현한 이웃이다.

## 2. 사용자 전제 2건의 판정

**전제 1 — "F의 조직·상호작용은 공백이다": 부분 성립.** 기질층(F 객체 스키마·종류 체계·관계 기록·저장·ID 규율·변이/소비 경로)은 설계가 닫았다(§6.4, §6.7, §4.1, §7.3, §8.4). 열려 있는 것은 표면층 셋 — F를 훑는 항해 표면(구체화된 파생 보기는 실행 껍질과 상태 보고뿐), `statement_ref` 산문의 내부 관례, 규모 성장 시의 탐색 보조 — 이다. 이 판정의 상세 근거는 앞선 대조 보고와 같다.

**전제 2 — "닫힌 형식이 AI 지능을 형식 준수에 소비하게 한다": 강형 불성립, 약형 성립.**

- 강형(직렬화·검사 비용을 AI가 진다)은 설계 문면과 어긋난다. 정규 JSON은 판본화된 생성기가 만들고 사람·AI가 손으로 쓰지 않으며(§3.1), 검사·Git·해시·프로세스 작업은 미리 작성된 도구가 소유한다(§24.1~24.2). 판단이 사는 지점에는 자유 산문 표면이 배치돼 있다(선택자의 `rationale.md` §10.4, F 산문, 작업별 작업대 전체).
- 약형(경계에서 자기 판단을 닫힌 어휘로 번역하는 인지 비용)은 실재한다. 종결 처분×필수 범위 조합표(§18.2), 발생 조건 AST 작성(§7.3), 동일성 대응표의 양화자 단위 대응(§19.2)이 그 지점이고, 프롬프트로만 강제한 형식 계약이 반복 위반된 저장소 실증(기억 M-0005 등)이 비용의 존재를 뒷받침한다.
- 다만 이 비용의 처방에 대해, OKF 자신의 Attested Computation 설계가 보여주듯 **기계 보증이 필요한 자리의 닫힌 계약은 제거 대상이 아니라 비용의 대가다.** 처방은 형식을 여는 것이 아니라, AI가 사고하는 매체와 닫힌 경계 사이의 다리(관례 + 승격 도구)를 놓는 것이다. 이것이 구조 C다.

## 3. 네 구조의 비교

비교 대상 네 구조와 총평이다. 상세는 표 아래에 있다.

| 구조 | 내용 | 기계장치 손실 | 목적(재량·소비 저감) 이득 | 판정 |
|---|---|---|---|---|
| A. 전면 대체 | F·관계를 OKF 파일로만 저장, 경로=정체성, 링크=관계 | 전면적 | 외견상 큼, 실질 작음 | 부적합 |
| B. 프로필 혼성 | OKF 파일 형식 + do-math 엄격 프로필(닫힌 frontmatter) | 없음(재구축 비용 큼) | 작음 | 교환비 나쁨 |
| C. 저작 표면 | 작업별 작업대의 저작 관례를 OKF로, 종결 시 도구가 승격 | 없음 | **큼 — 과녁 적중** | 적합 |
| D. 연구 지도 | 핵심 기록 → 결정론 생성 OKF 번들(파생 보기) | 없음 | 중간 — 공백 1 직접 충전 | 적합 |

### 구조 A — 전면 대체: 부적합

기질을 OKF로 바꾸면 다음 기계장치가 죽거나 재발명 대상이 된다.

- **발생 조건 AST와 착수 가능성의 결정론**(§7.3, §7.5): `record_field_equals`는 JSON Pointer를, `relation_exists`는 형식 있는 관계 기록을 전제한다. OKF의 관계는 무형 링크이고 종류는 산문이 전달하므로 결정론 평가가 성립하지 않는다. "같은 task_id+공용 커밋 → 같은 결과"(§7.5)가 무너지면 실행 껍질(§7.6)과 생존 절차(§7.7)가 연쇄로 무너진다.
- **상태 검사**(§21.1, §6.4): F 종류별 필수 필드·허용 상태 검사는 닫힌 스키마를 전제한다. OKF는 미지 필드·미지 type의 **관용을 소비자에게 의무화**하므로, 검사를 유지하려면 결국 닫힌 프로필을 다시 얹어야 한다(그러면 구조 B가 된다).
- **정체성과 참조**(§2.1, §2.5, §4.1): "같은 논리 객체는 제목과 경로가 바뀌어도 ID를 유지한다"는 규율과 경로=Concept ID는 정면 충돌한다. F는 대체·분화·비활성이 일상이라 경로 정체성은 참조를 계통적으로 깨뜨린다. `{record_id, public_commit}` 참조(§2.5), 편입 영향 분석의 닫힌 집합(§6.9), 참조 폐쇄 검사(§21.1)가 함께 죽는다.
- **의미 대조 가능한 병합**(§18.4): 정규 직렬화·필드 해시가 없으면 "핵심 기록 의미와 관계"의 재검증이 산문 대조로 퇴화한다.
- **누락≠값 규율**(§3.4): OKF에서 `status` 부재는 stable을 뜻한다. 미검사와 안정을 구별하는 설계 원칙과 충돌한다.
- 테스트 벡터의 I05·I13, S계열 전부, D02 등과 구현 완료 조건 §27-1·5가 무효화된다.

그리고 결정적으로, **A가 주는 자유는 사용자의 목적이 실제로 사는 곳에 놓이지 않는다.** 공용 F는 어차피 공용 편입으로만 바뀐다(공용 작업대 정의). AI가 자유롭게 쓰는 곳은 작업별 작업대이고, 그곳은 이미 자유다. A는 자유가 필요 없는 합의 층의 검증 능력을 지불하고, 자유가 필요한 층에는 아무것도 더해주지 않는다.

### 구조 B — 프로필 혼성: 실행 가능하나 교환비 나쁨

OKF는 생산자 정의 확장 필드를 허용하므로, frontmatter에 `record_id`·종류·닫힌 상태·관계를 넣은 엄격 프로필은 **OKF 적합(conformant)** 이다. 검사기·발생 조건을 frontmatter 위에 재구현하면 기계장치를 살릴 수 있다. 그러나:

- **정규 YAML 직렬화를 발명해야 한다.** 바이트 재현·NFC·중복 키 거부(§3.1)를 YAML에서 다시 세워야 하고, YAML의 형 강제·앵커·스타일 다양성 때문에 JSON보다 어렵다. 이미 풀린 문제를 안 풀린 문제로 바꾸는 일이다.
- **F 계열 스키마·외피·레지스트리(§3.3, §29)와 관련 테스트의 재작업**이 따른다. 기록 JSON과 산문 문서를 한 파일로 합치면 산문 수정이 기계 필드의 해시 봉인과 결합돼 변경 파급이 커진다.
- **v0.x 스펙에 정본 기질을 결박**하게 된다. 3개월 만에 파괴 변경 2건이 난 스펙이다.
- 이 비용으로 사는 이득은 "한 파일 가독성"과 "OKF 소비 도구가 정본을 직접 읽음" 정도인데, 소비 측은 packet·role-pack이 이미 전문을 조립해 주고(§10.2), 저작 측 이득은 구조 C가 기질을 건드리지 않고 동일하게 준다.

### 구조 C — 저작 표면: 적합 (전제 2의 과녁을 직접 조준)

작업별 작업대는 정의상 "연구 작업이 자유롭게 바꾸는 격리된 국소 작업대"이고, 발견 후보는 그곳에 기록되며(CONTEXT.md), 종결 시 F 제안으로 구조화된다(§8.4). 이 자유 공간의 **저작 관례**를 OKF로 정한다:

- 작업자·씨앗 생성 세션은 작업 공간에 개념당 한 파일(`type: 발견 후보`·`question`… — F 종류와 대응), 무형 링크, `index.md`, `sources` 각주 귀속으로 사고를 축적한다. OKF가 애초에 "에이전트가 계속 고쳐 쓰는 위키"로 설계된 용법 그대로다.
- 종결 시 `do-math record` 계열 도구(§24.2 — "스키마 구동 정규 기록·원자료 결속 후보 생성"의 확장)가 frontmatter+산문을 F 제안·관계 후보로 승격한다. AI는 경계 어휘 번역의 상당 부분을 도구에 넘기고, 실행 중에는 형식을 생각하지 않는다.
- **실패가 봉쇄돼 있다.** 관례는 프롬프트 수준이라 위반될 수 있으나(M-0005 실증), 위반의 결과는 승격 도구의 파싱 실패 → 종결 시 수동 정리이지, 공용 상태 오염이 아니다. 편입 검사(§18.4)가 그대로 최종 관문이다.
- 잃는 기계장치: 없음. 추가물: 저작 관례 문서 한 절 + 승격 도구 하나.

### 구조 D — 연구 지도: 적합 (공백 1을 직접 충전)

공용 핵심 기록에서 결정론 생성기가 OKF 번들을 재생성한다: F 객체·K 객체·작업이 개념 문서(frontmatter는 외피 투영 — `type`←종류, `generated`←생성 계보, K 객체의 `verified`←동일성 인증 사건, 확장 키로 `record_id`·`epistemic_status`), 관계 기록이 "supports → [대상]" 형태의 산문+링크(OKF의 "종류는 산문이 전달" 관례와 정확히 합치), 역할·종류별 `index.md`가 진입점, `log.md`가 공용 커밋 이력 투영.

- 지위는 파생 보기다 — 재생성 가능, 비정본(§0.1). 상태 보고(§21.3)와 같은 계열이라 설계 철학과 충돌이 없다.
- 소비자: 사람은 OKF 참조 시각화기로 훑고, 작업자는 자기 worktree의 고정 커밋에서 같은 번들로 항해한다. packet의 전문 계약(§10.2)은 그대로 두므로 충돌 없음 — 번들은 선택 입력이 아니라 항해 보조다.
- 잃는 기계장치: 없음. 추가물: 생성기 도구 하나 + 산출 스키마·재생성 시점 규정 + "정본 오독 금지" 명시(이미 §0.1이 방어).
- `record_id`가 frontmatter에 있으므로 경로 정체성 문제는 발생하지 않는다(경로는 항해용, ID가 참조용).

## 4. 권고 (근거와 분리된 AI 추천)

1. **구조 C와 D를 함께 채택하라.** C가 "재량의 장 강화·형식 소비 저감"의 실질을, D가 "F 조직·상호작용 공백"의 실질을 각각 최소 비용·무손실로 충족한다.
2. **기질층 재개방(A·B)은 하지 마라.** A는 목적 자체에 비효율이고, B는 같은 이득을 훨씬 비싸게 산다.
3. 채택하더라도 OKF 판본을 v0.2로 **잠그고**, 스펙 추종은 명시적 갱신 결정으로만 하라(파괴 변경 이력 때문).

이 권고는 사용자 결정을 대신하지 않는다. 특히 "그래도 기질을 열겠다"는 선택은 3절 A·B의 비용표를 수용하는 사용자 결정으로 가능하다.

## 5. 채택 시 다음 단계

현재 do-math는 미구현이고 활성 인스턴스가 없으므로, §23의 실인스턴스 마이그레이션은 불필요하다. 필요한 것은 설계 문서 수정뿐이다.

1. 이슈 18을 재개방하고 `통합-설계.md`에 두 절을 추가: ① 작업별 작업대 저작 관례(OKF v0.2 잠금, F 종류↔`type` 대응, 승격 도구 계약), ② 연구 지도 파생 보기(생성기·스키마·재생성 시점·레지스트리 선언·비정본 명시).
2. 도구 표(§24.2)에 생성기 추가, `do-math record`의 승격 입력 확장. 스키마 묶음 판본 상승(§23.3 계약 수준 확장).
3. 테스트 벡터 추가: 같은 공용 커밋 → 같은 번들 바이트(D05 계열), 승격 도구의 파싱 실패 처분.
4. 수정안의 검증(verify-rounds 등)과 컨텍스트 정본 갱신은 기존 절차를 따른다.

- 모델의 형식 처리 비용에 대한 정량 증거는 없다. 전제 2 판정은 설계 문면 + 저장소 실증(프롬프트 계약 마찰 사례들) + OKF 스펙 자체의 설계 선택이라는 정성 근거에 선다.

# 심화 검토 — A-최적 대 구조 C (구축 비용 제외)

## 결론

**비용을 계산에서 빼도 C가 이긴다. 다만 이유가 바뀐다.** 앞선 보고에서 A의 기각 근거 일부는 재구축 비용이었다. 비용을 제거하면 남는 것은 구조적 성질 둘이고, 이 둘이 비용과 무관하게 A-최적을 가로막는다.

1. **수렴 정리**: A-최적에 현행 수준의 건전성을 요구하면, 재건된 각 장치가 닫힌 계약으로 되돌아와 A는 B(프로필 혼성)로 수렴한다. 건전성을 요구하지 않으면 A는 비용이 아니라 **보증을 지불**한다.
2. **주의 분산 정리**: 닫힌 경계를 없애는 것은 형식에 쓰는 주의를 없애지 않고 **전 표면에 확산**시킨다. 사용자의 목적 2(형식 소비 저감)에 대해 A-최적은 C보다 오히려 나쁘다.

그리고 A-최적이 이기는 조건도 존재하며, 그것은 기술 선택이 아니라 사용자 결정이다(§5에 명시).

---

## 1. A-최적의 성실한 설계

"무너지는 부분을 OKF의 방식으로 다시 채운" A를 최강으로 세우면 이렇다.

- **저장**: 공용 F·관계가 OKF 번들 그 자체다. 개념당 한 파일, frontmatter(`type`←F 종류, `status`, `stale_after`, `generated`, `verified`, `sources`), 본문 산문, 링크 그래프, `index.md` 항해, `log.md` 연대기.
- **정체성**: 경로가 Concept ID. 대체·분화는 `status: deprecated` 묘비 문서와 후속 링크로 처리한다.
- **관계**: 산문 링크(사람·OKF 소비자용) + frontmatter 확장 배열(`supports: [/f/x.md]`, 기계용). OKF 적합이다(미지 키 허용).
- **게이트 재건**: 발생 조건·착수 가능성을 frontmatter 위의 결정론 평가기로 재구현한다(`frontmatter_field_equals`, `concept_exists`, `link_exists`). 고정된 파서를 쓰면 평가 자체의 결정론은 성립한다.
- **편입**: 절차는 유지된다. 제안이 닫힌 JSON 묶음이 아니라 **개념 파일의 편집**이 되고, 편입 검사가 그 편집을 재검증한다.

이 설계가 **정말로 얻는 것**을 먼저 인정한다.

1. **단일 표현**. AI가 읽는 것, 쓰는 것, 기계가 검사하는 것, 사람이 훑는 것이 같은 파일이다. C+D의 승격 도구·지도 생성기·투영 계층이 통째로 사라진다. 구성요소 수로는 A-최적이 가장 적다.
2. **경계 번역의 소멸**. 작업 공간의 파일이 그대로 공용 파일로 승격된다. 종결 시 형식 전환이 원리상 없다 — 사용자 비전의 최대치다.
3. **항해의 내장**. D가 생성기로 만들던 연구 지도가 A에서는 기질 그 자체다.
4. **문장 단위 출처 귀속**. `sources` + 각주 키는 현행 `evidence_refs`(객체 단위)보다 세밀한 표현력이다. (단, 이 표현력은 C의 저작 관례와 D의 투영에도 채택 가능하므로 A의 전유물은 아니다.)

## 2. 수렴 정리 — 건전성 등가를 요구하면 A는 B가 된다

A-최적의 재건 목록을 하나씩 끝까지 밀어보면, 각각이 닫힌 계약의 재발명으로 끝난다.

| 죽는 장치 | "OKF 방식" 재건의 종착 | 남는 본질적 문제 |
|---|---|---|
| 발생 조건·착수 결정론(§7.3·7.5) | 고정 파서 + 닫힌 연산자를 frontmatter 위에 재구현 | 재건 성공 = **닫힌 연산자·닫힌 필드의 부활**. OKF 자신도 기계 보증이 필요하자 Attested Computation(타입 매개변수 + 결정론 attester, "에이전트는 계산을 수정 못 함")을 만들었다 — 같은 회귀다 |
| 상태 검사(§21.1·6.4) | 종류별 필수 필드·허용 상태를 frontmatter에 강제 | 강제하는 순간 "미지 키·미지 type 관용" 철학을 버린 **닫힌 프로필 = B** |
| 부재 의미(§3.4) | OKF는 `status` 부재=stable, `verified` 부재=소비 가능 | 미검사와 정상을 구별하려면 필수 필드를 늘려야 함 → 프로필 강화 → B. 관용을 유지하면 "검사 안 함"이 "안정"으로 읽히는 **거짓 GREEN 계열**의 의미론을 기질에 심는다 |
| 관계의 형식·근거(§6.7) | frontmatter 배열(기계) + 산문 링크(사람) | 같은 관계의 **이중 기입이 한 파일 안에서** 발생, 표류 검사기가 또 필요. 현행은 단일 기입(관계 기록) + 생성 투영이라 표류 축이 없다 |
| 정체성(§2.1·4.1) | 경로 + 묘비 + 후속 링크 | 대체·분화가 일상인 F에서 참조 갱신이 연쇄됨. `record_id`를 frontmatter에 넣어 풀면 — 그게 B다 |
| 깨진 참조 = 평가 오류(§7.5) vs 깨진 링크 = 미래 지식(OKF 규범) | "게이트 읽기는 엄격, 항해 읽기는 관용" 이중 규율 선언 | 규율 자체는 선언 가능하나, **같은 표기가 문맥에 따라 결함이기도 하고 정상이기도 한 기질**이 영구히 남는다 |

정리하면: 건전성 등가라는 제약 아래에서 A-최적의 극한은 B이고, B는 이미 비교를 마쳤다(같은 이득을 더 무거운 구조로). 제약을 풀면 A-최적은 비용이 아니라 보증 — 결정론 게이트, 부재≠정상, 참조 폐쇄, 병합 시 의미 재검증의 입자 — 을 지불한다. **즉 "충분한 노력"으로도 A와 C는 같은 지점에 도달하지 않는다. 노력이 사는 것은 비용 축이지 보증 축이 아니기 때문이다.**

## 3. 주의 분산 정리 — A-최적은 목적 2에 역행한다

사용자의 우려는 "AI가 핵심 작업 대신 형식에 지능을 쓴다"였다. 두 구조에서 그 주의가 어디에 놓이는지 보자.

- **C**: 매체는 완전 자유(관례는 조언 수준, 위반해도 아무것도 오염되지 않음). 형식이 필요한 곳은 종결 경계 하나로 응집되고, 그 경계의 번역을 승격 도구가 흡수한다. AI는 "지금은 자유, 저기서만 정형"이라는 단순한 지도를 가진다.
- **A-최적**: 경계는 사라지지만, 이제 **산문 곳곳이 하중을 진다**. 어떤 frontmatter 키는 착수 판정의 입력이고, 어떤 링크는 관계 배열과 일치해야 하며, 어떤 문장은 그냥 산문이다 — 겉보기로는 구별되지 않는다. 산문을 고치다 게이트를 깨뜨릴 수 있으므로, AI는 쓰는 내내 "이 부분이 기계에 읽히는가"라는 지도를 머리에 들고 있어야 한다. 형식 주의가 소멸한 것이 아니라 **국소 경계에서 전 표면으로 번진 것**이다.

이 판단의 근거는 셋이다. (i) 저장소 실증 — 프롬프트 수준 형식 계약은 반복 위반됐다(M-0005 계열). C에서 그 위반은 승격 실패(연성)로 끝나지만, A-최적에서는 하중 있는 산문의 위반이 게이트 오류·의미 표류(경성)로 나타난다. (ii) OKF 자신의 선택 — 보증이 필요한 자리에서 자유 산문을 격리하고 "에이전트는 매개변수만 채운다"로 좁혔다. (iii) 두 구조 모두에서 제거 불가능한 의미 작업(인식 상태 판정, 확인 범위의 정밀 진술, 관계 종류 선택)은 동일하게 남는다 — 이 부분은 형식 비용이 아니라 연구 내용 그 자체다. 차이는 제거 가능한 부분의 처리인데, C는 도구로 제거하고 A-최적은 전 표면 상시 주의로 대체한다. (i)(ii)는 실증이고, 이 결론 자체는 실증에 기반한 판단임을 명시한다.

## 4. C의 복잡도 실측

"C를 택하면 복잡도가 얼마나 느는가"를 현행 설계 대비 추가물 전수로 답한다.

| 추가물 | 규모 | 성격 |
|---|---|---|
| 저작 관례 절 | 설계 문서 한 절(약 1쪽) | **비규범(조언)**. 위반 시 효율만 잃음 |
| 승격 도구 | 도구 1개 — 기존 `do-math record`("스키마 구동 정규 기록·원자료 결속 후보 생성", §24.2)의 입력 확장으로 구현 가능 | 출력은 기존 종결·F 제안 스키마. **새 공용 스키마 0** |
| 도구 manifest 항목·계약 판본 | +1 항목, 판본 +1 | 기계적 |
| 테스트 벡터 | 2~3개(표준 번들 승격, 파싱 실패의 연성 처분) | 기존 §26 형식 |
| 새 상태 축·ref·생명주기 | **0** | — |

실패 양식: 승격 파싱 실패 → 작업자가 종결 시 수동 구조화(= 현행 그대로). 즉 C의 최악 경우가 현행의 평시다. 장기 표류 축도 없다 — 작업 공간은 실행 종료 시 보관되는 일시 자료이고, 승격은 종결에 한 번 일어나며, 편입 검사(§18.4)가 최종 관문으로 그대로 있다. 잔여 비용은 승격 도구가 추론할 수 없는 의미 판정뿐인데, §3에서 본 대로 그것은 A-최적에서도 동일하게 남는 연구 내용이다.

## 6. 권고 (근거와 분리)

**권고 유지: C(+D). 비용 제외 비교에서도 결론이 바뀌지 않으며, 근거는 비용에서 구조(§2·§3)로 옮겨져 오히려 강해졌다.**

단, A-최적이 이기는 세계의 조건을 명시한다. 이것은 기술 판단이 아니라 사용자가 내릴 수 있는 가치 결정이다.

1. 공용 상태의 기계 관문(결정론 착수 판정, 상태 검사, 영향 분석)을 **조언 수준으로 낮춰도 되는** 연구 체계를 원한다 — 즉 거짓 GREEN 위험을 AI 판단력으로 감수한다.
2. 동시 다작업·세밀 병합보다 **단일 흐름·에이전트 친화 매체**를 우선한다.
3. OKF 생태계 호환을 포기하고 스펙을 영구 고정하는 것을 받아들인다.

셋을 모두 승인한다면 A-최적은 일관된 체계이고, 그때는 사실상 do-math의 검증 철학 자체를 바꾸는 결정이므로 이 설계 문서의 §0 재개방으로 다뤄야 한다. 셋 중 하나라도 승인하지 않는다면 C(+D)가 종국 상태로도 우월하다.

## 사용자

구조 A와 B는 하나의 통합된 시스템으로 작동하고 구조 C와 D는 두 개의 서로 다른 시스템 사이의 복잡성이 발생한다 생각해. 그리고 구조 A와 B의 경우에 결국 단점으로 드는 것이 주로 재작업이 필요해진다, 혹은 스펙에 결박이 된다 등인데, 스펙이야 특정 버전으로 고정시키면 되는 것이고 재작업이야 그냥 시간과 비용을 들여 하면 되는 것이고 발명이야 새로 하면 되는거지. 기계론적 검사에 실익이 있다는 주장과 그러니 기존 do-math 설계의 모든 기계론적 검사를 유지할 수 있는 방식을 택해야만 한다는 주장은 서로 다른 주장이라 생각하고, 필요한, 실제로 실익이 존재하는 기계론적 검사가 어떠한 것이 있고 그 유지가 구조 B에서 어떻게 되는지를 검토할 필요가 있다고 생각해

## 어시스턴트

지적 두 가지가 실제로 유효한지 먼저 검증했고, **둘 다 유효하다.** 그 결과를 반영해 요청한 검사 단위 분석을 수행했다.

**인정 1 — 비용 가중의 오류.** 이전 판정에서 B를 기각한 근거의 상당 부분(재작업, 재발명, 재검증)은 일회성 구현 비용이다. 이 저장소의 결정 원칙은 "기술적 결정을 내릴 때 그 구현에 드는 비용을 고려하지 않는다. 품질, 간결성, 건전성, 스케일 가능성, 장기 유지 가능성을 최대화한다"이고, 나는 이를 위반해 비용을 판정에 섞었다. 비용을 제외하면 B의 평가는 달라진다.

**인정 2 — 주장의 혼동.** "기계 검사에 실익이 있다"에서 "현행 검사 전부를 현행 형태로 유지해야 한다"로 비약했다. 옳은 질문은 사용자가 정식화한 대로다: 실익이 실재하는 검사는 무엇이고, 그것이 B에서 유지되는가.

# 심화 검토 — 실익 있는 기계 검사의 목록과 구조 B에서의 유지

## 1. 검토 대상 B의 정밀화: B*

"B에서 유지되는가"는 B를 정확히 고정해야 답할 수 있다. 이하의 B*는 이전 보고의 B를 다음과 같이 구성한 것이다.

- F·관계 등 지식층 기록은 OKF 개념 문서(.md, frontmatter+본문)로 저장한다. frontmatter가 현행 공통 외피+`data` 필드를 담는 **엄격 프로필**이다(OKF는 확장 키를 허용하므로 적합).
- **정규 투영**: 판본 잠금된 엄격 YAML 부분집합 파서(앵커·별칭·형 강제 금지, 스칼라는 문자열)가 frontmatter를 정규 JSON 투영으로 변환한다. 스키마 검사·조건 평가·해시 봉인은 파일 바이트가 아니라 이 투영 + 본문 해시 위에서 수행한다.
- 사람·AI가 파일을 직접 편집할 수 있고, 판본화된 정규화기(formatter)가 커밋·편입 전에 형태를 정규화한다. "생성기만 쓴다"(§3.1)를 "정규화기를 통과한다"로 대체한다.
- 정체성·참조는 frontmatter의 `record_id`가 소유하고, 경로·Markdown 링크는 항해용 비권위 표현이다.
- 관계는 형식 있는 별도 기록으로 유지한다(같은 .md 프로필로 저장 가능). 본문 링크는 장식이다.
- OKF v0.2의 명시된 부분집합을 `do_math_contract`에 잠근다.
- 실행·제어층(run·request·monitor·selection 등 기계 전용 문서)은 현행 정규 JSON을 유지한다. B*의 범위는 지식층이다.

각 검사에 대해 ① 막는 실패(실익), ② 실익 실재 판정, ③ B*에서의 유지 방식을 적는다.

**결론: 실익이 실재하는 검사 중 B*에서 구조적으로 유지 불가능한 것은 없다.** 이전 보고에서 "죽는다"고 판정한 것들은 vanilla OKF(무프로필)에 대한 판정이었고, B*에서는 전부 산다.

## 3. 실익이 죽는 지점 — B*가 OKF에서 채용하면 안 되는 것

유일하게 실익이 실제로 죽는 경우는 B*가 OKF의 **네이티브 관례를 권위 층에** 들일 때다. 이 선이 B*의 비양보 조건이다.

1. **경로 정체성을 참조에 쓰지 않는다.** F는 대체·분화가 일상이라 경로 참조는 계통적으로 깨진다. 경로는 항해용이다.
2. **본문 링크를 권위 있는 관계로 쓰지 않는다.** 무형 링크가 관계 정본이 되는 순간 #2·#4·#6이 연쇄로 죽는다.
3. **부재 기본값(status 없음=stable)을 채용하지 않는다.**
4. **조건 평가·검사·봉인을 자유 YAML 위에서 하지 않는다.** 반드시 잠근 파서의 정규 투영 위에서 한다.
5. **스펙 추종을 자동화하지 않는다.** v0.2 부분집합을 계약에 잠그고, 갱신은 명시적 계약 변경으로만 한다(3개월 내 파괴 변경 2건의 실측 근거).

이 다섯을 지키면 B*는 "OKF를 컨테이너로, do-math를 프로필로" 쓰는 하나의 정합적 설계다.

## 1. 정규 JSON 투영 대신 "규칙을 따르는 YAML"로 충분한가

**충분하다. 그리고 봉인 관점에서는 내 투영안보다 우월하다. 사용자안 채택을 권고하고 B*를 수정한다.**

기능을 분해하면 명확해진다. 정규성이 필요한 자리는 둘이다.

- **봉인·비교** (해시, 변조 검출, 같은 의미=같은 바이트): 바이트 수준의 유일 형태가 필요하다.
- **평가·검사** (스키마 검사, `record_field_equals`): 파싱된 자료 구조가 필요하다. 이건 형식과 무관하다 — **현행 정규 JSON도 평가할 때는 파싱한다**(§3.2가 검사기를 도구 manifest에 잠그는 이유다). JSON Pointer는 텍스트가 아니라 파싱된 맵·배열·문자열 구조 위에 정의되므로, 정규 YAML을 파싱한 구조에도 §7.3이 문면 그대로 적용된다.

내 투영안은 "AI가 자유 형태 YAML을 쓴다"를 전제하고 의미 해시로 헤지한 것인데, 그 대가로 **파서가 해시 경로에 들어온다**(파서 결함=봉인 결함). 사용자안 — 판본화된 정규화기가 유일 형태를 강제하고, 검사기가 `정규화(파일)==파일`의 바이트 비교로 준수를 기계 판정 — 은 파일 바이트를 그대로 해시할 수 있게 하여 **파서를 해시 경로에서 제거한다.** 이는 현행 정규 JSON과 같은 건전성 등급이다. 이전 보고에서 B*의 건전성 열위로 꼽은 "파서의 신뢰 기반 편입"이 평가 경로(현행과 동등)에만 남고 봉인 경로에서 사라지므로, 그 열위 지적을 철회한다.

필요한 명세물은 §3.1의 YAML 동형이다: 키 코드포인트 정렬, NFC, 중복 키 거부, 고정 인용 규율(스칼라는 전부 인용된 문자열 — YAML의 형 강제 함정 `no`→false 등을 원천 차단하고 형은 스키마가 소유), 블록 스타일 고정·2칸 들여쓰기, 앵커·별칭·태그·다중 문서 금지, LF·끝 개행 하나, **봉인 대상에서 코멘트 금지**(같은 의미의 두 파일이 코멘트 차이로 다른 해시를 갖는 것을 막기 위해서다. 초안에선 허용하고 편입 정규화 시 거부해 작성자가 필드·본문으로 옮기게 한다). 정규화기는 멱등이어야 하고(`정규화∘정규화=정규화` 테스트 벡터), 부분집합 밖 구성물은 조용히 고치지 않고 거부한다. 작업 공간 초안은 자유형을 허용하고, 공용 트리·봉인 대상만 정규형을 요구한다.

## 2. ID를 버리고 경로를 정체성으로 쓰는 안

**부분 인정, 최종적으로는 절충안을 권고한다.** 먼저 인정 두 가지.

- **한 판본 안의 폐쇄는 성립 가능하다.** 공용 트리는 공용 편입으로만, 한 작업씩 직렬로 바뀐다(§9.3). Git 커밋은 트리 전체를 원자로 바꾸므로, "이름 변경 = 모든 유입 참조를 같은 커밋에서 재작성하는 절차"로 규정하면 커밋 후 깨진 참조 없음을 검사기가 기계 판정할 수 있다. 이 점에서 사용자 추론은 옳다.
- **찾기 문제의 실체 정정**: 현행 설계에서 기계의 ID→파일 해석은 이미 자명하다 — 파일명이 ID다(§4.1 `records/<record_id>.json`). 실재하는 고통은 기계가 아니라 **사람·AI의 가독성**이다. `F-01J8ZK3M9QXYZ.md`라는 경로는 아무것도 말해주지 않고, 위키에서 링크를 쓰고 읽는 데 나쁘다. 이 고통은 진짜다.

그러나 경로=정체성에는 절차로 해소되지 않는 구조적 비용 세 개가 남는다.

1. **시간 횡단 정체성.** 이 체계의 참조는 한 판본 안에 갇혀 있지 않다. `{record_id, public_commit}` 결박(§2.5), 전례의 봉인·재대조(§17.4), 인증·감사·씨앗 발생 조건·관계의 양끝이 전부 "과거 커밋에서 알던 그 객체의 **현재** 판본"을 물어야 한다(currency 검사의 본질). 경로가 정체성이면 이 질문은 개명 이력 추적을 요구한다. Git의 rename 감지는 유사도 휴리스틱이라 정체성 근거가 못 되므로 명시적 개명 원장이 필요해지는데, **그 원장이 곧 안정 ID 체계다** — 더 나쁜 자리에 재발명한.
2. **사용자 자신의 목적과 충돌한다.** 목적은 AI가 지식의 장을 자유롭게 재조직하는 것이다. 재조직은 곧 경로 변경이다. 경로=정체성 아래에서는 재조직할수록 개명 원장이 부풀고 모든 시간 횡단 검사가 원장을 관통해야 한다. 자유를 늘리려는 선택이 자유에 세금을 매긴다. §2.1의 계약 — "같은 논리 객체는 제목과 경로가 바뀌어도 ID를 유지한다. 의미가 달라지면 새 ID를 만든다" — 은 정확히 이 문제를 겨눈 것이다: **정체성은 의미를 따라가야 하고 위치를 따라가면 안 된다.**
3. **병행성.** ULID는 병렬 작업 실행들이 조정 없이 충돌 없는 ID를 만들게 한다(§2.1). 경로 정체성은 편입 시점의 경로 중재(직렬이라 가능은 하다)에 더해, 개명 시 유입 참조 전면 재작성이 트리 전역을 건드려 병행 작업과의 임시 편입 충돌(§18.4)을 증폭시킨다. ID 방식에서 개명은 옮겨진 파일 하나만 건드린다.

**권고(절충)**: 경로에서 정체성이 아니라 **가독성**을 취한다. ① 파일·디렉터리 이름은 의미 있는 이름으로 하고 자유 재조직을 허용한다(현행 ULID 파일명 관례의 폐기 — 이건 현행 설계의 갱신점이다). ② 정체성은 frontmatter의 `record_id`가 소유한다. ③ ID→경로 색인은 frontmatter 전수 스캔으로 재생성하는 파생 보기 하나로 제공한다(유일성은 검사기가 강제). 이러면 사용자가 원한 실익 — 보이는 경로, 위키다운 링크, 쉬운 발견 — 을 개명 원장 없이 얻고, 재조직의 자유와 참조 안정성이 서로를 방해하지 않는다. 산문 링크는 경로를 쓰고 깨지면 `degraded`로 관용한다(OKF 관례와 §21.1 등급이 합치).

## 3. 본문 링크를 권위 있는 관계로 쓸 때 생기는 문제 (상세)

전제: 별도 관계 기록을 없애고 산문 속 Markdown 링크가 관계의 정본이 되는 경우다.

1. **무형성.** 링크에는 종류가 없다. OKF 스펙 스스로 "관계의 종류는 주변 산문이 전달하고, 소비자는 링크를 무형 방향 간선으로 취급한다"고 명시한다. 그런데 이 설계의 관계 종류 구별 — `supports`(연구상 지지)와 `formally_implies`(Lean이 입증한 함의) — 은 장식이 아니라 **거짓 확신을 막는 인식론적 경계**다. 기계가 종류를 읽으려면 산문을 해석해야 하고, 그 순간 결정론이 끝난다. "링크 앞에 `supports:`를 쓴다" 같은 관례를 발명하면 산문 안에 미소 형식을 지은 것인데, 이는 3번 문제로 이어진다.
2. **언급≠주장.** 연구 산문의 링크는 대부분 주장이 아니라 언급이다. "상대화하는 기법으로는 [P vs NP]를 풀 수 없다", "[A]가 [B]를 반박한다는 주장은 틀렸다", "혹시 [C]가 성립한다면" — 부정·인용·가정·역사 서술 속 링크를 간선 추출기는 주장과 구별할 수 없다. 관계 기록은 주장만 담고, 산문은 자유롭게 언급한다. 이 분리를 없애면 언급이 간선으로 오염되고, 그 간선 위에 선 모든 소비자가 함께 오염된다.
3. **관계 자신의 메타데이터가 살 곳이 없다.** §6.7의 관계 기록은 근거 참조, 확인 상태와 판정자, 수학적 관계일 때의 대응 Lean 객체, 생성·대체·비활성 이력을 가진다. 관계는 자기 생명주기를 가진다 — 반례가 나오면 양끝 객체는 살아 있는 채 `supports` 관계만 철회된다. 링크로는 철회가 "문장 삭제"가 되어 철회의 기록도 사유도 남지 않는다.
4. **`formally_*` 게이트의 소실.** "Lean 정본 객체 없는 formally_implies는 무효"(§6.7)는 관계가 필드를 가진 기록이라서 검사 가능하다. 산문 링크로는 함의 주장을 게이트할 수 없고, 앞선 검토에서 실익 실재로 판정한 주장 인플레이션 차단(#4)이 무너진다.
5. **결정론 소비자의 소실.** `relation_exists`(§7.3)로 관계 상태에 조건화된 씨앗 발생, 형식 간선 위에서 닫힌 영향 집합을 계산하는 편입 영향 분석(§6.9), 도메인·코도메인 검사(§21.1), 종류별 그래프 파생 보기가 전부 입력을 잃는다.
6. **제3자 간선을 표현할 수 없다.** 링크의 암묵적 출발점은 "이 문서"다. 그러나 연구 산문은 "[A]가 [B]를 반박한다"처럼 남의 간선을 흔히 서술한다. 관계 기록은 from/to를 명시하므로 문서 위치와 간선 구조가 독립이다.
7. **병합의 침묵 충돌.** 병행 작업 둘이 모순된 관계 변경을 내면, 기록 방식에서는 §18.4 재검증이 두 기록 변경의 충돌을 본다. 산문 방식에서는 텍스트 병합이 "지지한다" 문장과 "반박한다" 문장을 나란히 살려둘 수 있고 기계는 모순을 보지 못한다.

**중간안의 공정한 검토**: 링크 대신 **frontmatter 구조 관계**(`relations: [{kind, to, evidence, status}]`)는 형식성을 살리므로 위 문제 대부분을 피한다. 별도 기록 대비 남는 손실은 — 관계의 독립 생명주기·이력이 양끝 객체의 판본 churn에 묻히고, 간선의 단독 소유가 모호해지며(어느 끝이 소유하는가, 중복 소유 금지 원칙 §6.7과 긴장), 판정자·근거 메타데이터가 객체를 비대하게 한다. 단순 계보 간선(`generated_from` 류)에는 고려할 만하고, 판정을 받는 연구·수학 관계에는 별도 기록이 우세하다. 이 세분화는 설계 수정 시점에 정하면 된다.

링크의 정당한 자리는 남는다: 항해, 언급, "아직 안 쓴 지식"(깨진 링크 관용), 그리고 파생 보기에서 관계 기록을 산문 링크로 **렌더**하는 것(기록→링크의 단방향 투영은 안전하다. 위험한 것은 링크→기록의 역방향이다).

## 4. 부재 기본값의 문제 (상세)

OKF는 `status` 필드가 없으면 `stable`로 읽는다. OKF의 맥락에서는 합리적 선택이다 — 조언적 소비(신뢰 등급도 관문이 아니라 신호), 사람이 큐레이션한 문서, "필드 하나만 있어도 적합"이라는 포용 우선. 잘못된 기본값의 비용이 낮다.

이 체계에서는 상태값이 **행동을 게이트**한다(착수 가능성, 편입, 선택, 인증). 그 차이가 다음 다섯 문제를 만든다.

1. **부재의 다의성 붕괴 — 그것도 가장 안전해 보이는 값으로.** 필드 부재는 다섯 가지를 뜻할 수 있다: 아직 판정 안 함, 판정 결과 "없음", 작성자 누락, 도구 결함으로 탈락, 구판 스키마. 기본값은 이 다섯을 침묵으로 하나에 합치는데, 하필 `stable` — 건강해 보이는 값 — 에 합친다. 결함이 안정으로 위장하는 구조, 즉 거짓 GREEN이다. 설계가 §0.3·§3.4에서 "결과 없음, 검사하지 않음, 검사 실패, 부분 완료를 서로 다른 상태로 표현한다"고 못 박은 이유다.
2. **강제 기능의 소실.** `epistemic_status`가 필수면 작성자는 판단을 내려야만 기록을 낼 수 있다. 부재=stable이면 미기입이 통과하는 최소 저항 경로가 되고, 부하 상태의 AI 작성자는 그 경로로 흐른다. 스키마의 "필수"는 검사 규칙이기 전에 판단 강제 장치다.
3. **게이트 오염.** `record_field_equals`로 상태에 조건화된 씨앗, 상태로 거르는 선택 입력을 생각하라. 도구 결함으로 상태 필드가 떨어져 나간 F는, 기본값 아래에서는 조건을 조용히 충족하거나 조용히 불충족한다. 설계가 원하는 결과는 둘 다 아니라 `evaluation_error`다(§7.5: 깨진 참조는 거짓이 아니라 오류다). 기본값은 오류를 값으로 바꿔 오류 전파 체계 전체를 우회한다.
4. **판본 간 의미 드리프트.** 기본값은 스펙 판본의 소유물이라, 스펙이 바뀌면 **파일은 한 바이트도 안 바뀌었는데 의미가 바뀐다.** OKF가 3개월 만에 `timestamp`→`generated.at` 전환과 소비자 측 fallback 의무를 만든 실측이 그 위험의 현물이다. 명시값은 판본에 강건하다.
5. **규율의 정확한 형태.** 이것은 "선택 필드 금지"가 아니다. §3.4가 이미 허용하듯, 스키마가 부재의 의미를 **정확히 하나로** 정의하면 필드는 생략 가능하다. 금지되는 것은 게이트에 참여하는 필드의 부재가 stable 같은 긍정 상태로 읽히는 것이다. 게이트 필드는 필수이거나, 부재가 "미판정"을 뜻하며 보수적으로(차단 또는 오류로) 작동해야 한다.

미니 예시: AI가 `epistemic_status`를 빠뜨린 F 하나. OKF 기본값 아래 — 연구 지도에 안정으로 표시되고, "이의 없는 후보" 필터에 들어가 포트폴리오 입력이 된다. 아무 경보도 없다. 프로필 아래 — 편입의 스키마 검사가 실패하고 작성자가 판단을 채워야 한다. 막은 실패가 구조적으로 눈에 안 보이는 종류라서, 이 규칙은 사소해 보이지만 하중을 받는다.

실무 처리는 싸다: B* 프로필은 게이트 필드를 필수로 하고, 외부 OKF 소비자용 표면(파생 지도)에는 항상 명시값을 써서 내보낸다. 외부의 남의 번들을 읽을 일이 생기면 그때만 OKF 기본값 규칙으로 읽는다.

## 1. 산문 링크의 ID화

### 색인 파일의 정확한 지위 (제안의 전제 조건)

사용자가 말한 "기계적으로 항상 최신이 유지되도록 절차가 요구하는 파일"은 다음과 같이 설계하면 설계 원칙과 충돌 없이 성립한다.

- **진실의 원천은 각 기록의 frontmatter `record_id`다.** 색인은 정본이 아니라 **커밋된 파생 보기**다(§0.1의 파생 보기 원칙 유지). 이중 소유를 만들지 않기 위해서다 — 색인이 권위를 가지면 frontmatter와 색인이 서로 어긋날 수 있는 두 정본이 된다.
- 공용 트리의 유일한 변경 경로는 공용 편입이고 편입은 직렬이므로(§9.3), **모든 편입이 같은 커밋 안에서 색인을 결정론 재생성**하도록 규정한다. 재생성은 frontmatter 전수 스캔의 정렬 출력이라 바이트 재현이 된다.
- 상태 검사기가 `재생성(스캔) == 커밋된 색인`을 바이트 대조하고, 불일치는 `blocked`다. ID 유일성 위반도 여기서 잡는다.

이 세 규칙이면 색인은 "절차가 최신성을 강제하는 파일"이 되고, 낡은 색인은 존재할 수 없는 상태가 아니라 **기계가 즉시 잡는 결함**이 된다.

### ID 링크가 경로 링크보다 나은 이유 (개명 파급의 산정)

경로 링크를 유지하면 개명 시 유입 링크를 전부 재작성해야 한다. 그 재작성의 파급은 링크 문제를 넘어간다.

- F 하나를 옮기면 그것을 링크한 모든 파일의 **바이트가 바뀐다**. 바뀐 파일들은 의미가 그대로인데도 해시가 바뀌므로, `{record_id, public_commit, sha256}`로 봉인된 참조(전례 §17.4, 입력 manifest, 재검증 §18.4의 "기준 뒤 바뀐 입력" 검사)가 전부 "변경됨"을 낸다. 재조직 한 번이 무의미한 stale 재검사를 체계 전체에 살포한다 — 보수적이라 안전하지만, 소음이 "입력이 바뀌었다" 신호의 가치를 갉아먹는다.
- 병행 작업 브랜치가 편집 중인 파일에 개명 재작성이 겹치면 임시 편입(§18.4)의 텍스트 충돌이 늘어난다.

ID 링크에서는 개명이 **옮겨진 파일 + 색인, 두 파일만** 바꾼다. 재조직의 자유(사용자의 목적)와 참조 안정성이 완전히 분리된다. 부수 이득: 기계 참조와 산문 링크의 관용구가 하나로 통일되고, 링크 검사가 "경로 존재"가 아니라 "ID 실재"라는 정확한 판정이 된다.

### 잔여 비용과 처리 두 가지

**① 표준 렌더러의 항해 상실.** `[상대화 장벽](F-01J8ZK…)`는 GitHub·VS Code·OKF 시각화기에서 클릭되지 않는다. AI에게는 문제가 아니다 — 트리 안의 색인 한 파일이면 ID→경로 해석이 자명하다. 사람과 외부 OKF 소비자를 위해서는 **파생 지도 렌더에서 ID→경로 치환**을 한다. 이 치환은 색인을 사전으로 쓰는 문자열 대치 수준이라, 이전에 기각한 C+D의 "형식 간 번역" 이음새와는 등급이 다르다 — 상태의 제2 표현이 아니라 마크다운→HTML 같은 일회성 렌더다. (제3안으로 파일 안에 경로를 병기하는 방식 — reference-style 정의 블록이나 redirect 스텁 — 도 있으나, 정본 파일 안에 경로 실체화가 남아 개명 churn이 되돌아오고, Windows에서 Git 심링크가 취약해 비권고한다.)

**② 초안 단계의 공백.** ID는 편입에서 부여된다(발견 후보 → 새 핵심 기록 ID). 따라서 작업 공간에서 **아직 ID가 없는 신규 객체끼리는 ID 링크를 쓸 수 없다.** 관례를 이렇게 닫는다: 초안 내부의 신규 객체 간 링크는 상대 경로로 쓰고(작업 공간 위키의 자연스러운 방식), 기존 공용 기록을 가리킬 때는 ID로 쓴다. 편입 승격이 신규 객체에 ID를 부여하면서 초안 내부의 경로 링크를 ID 링크로 기계 재작성한다. 이는 설계가 이미 가진 2단계 정체성(후보 → 편입 시 새 ID)과 동형이라 새 원리가 아니다.

## 2. 부재 기본값의 재정의

**가능하다.** 이전 답의 "불채용"은 "부재에 의미를 주지 말라"가 아니라 "OKF 스펙의 기본값을 상속하지 말라"다. §3.4가 이미 재정의의 도구다: "선택 필드는 스키마가 명시한 경우에만 누락할 수 있다." 즉 부재의 의미는 **우리의 판본화된 스키마가 필드별로 소유**하면 된다. 건전한 재정의의 조건은 네 개다.

1. **부재는 정확히 하나를 뜻한다.** 그 하나를 스키마가 문서화한다. 독자·스펙·도구가 각자 추측하지 않는다.
2. **게이트에 참여하는 필드의 부재는 보수 방향으로만 작동한다.** 부재는 권한·안정·승인을 **부여할 수 없고 거부만 할 수 있다.** "미판정"으로 읽혀 차단하거나 오류를 내는 것은 허용, "stable"로 읽혀 통과시키는 것은 금지.
3. **부재와 명시적 '없음'을 구별한다.** 부재가 "미판정"이면, "판정 결과 없음"은 반드시 쓰인 값이어야 한다(§7.1 "빈 배열과 필드 누락은 구별한다"와 같은 규율). 같은 상태의 표현이 두 가지가 되지 않게 한다.
4. **재정의는 우리 계약 판본에 속한다.** OKF 판본이 바뀌어도 우리 부재 의미는 움직이지 않는다(v0.1→v0.2에서 `timestamp` 의미가 이동한 실측이 이 조건의 근거다).

이 조건으로 보면 OKF 자신 안에 좋은 예와 나쁜 예가 나란히 있다. **`verified` 부재 = unverified(최저 신뢰 등급)** 는 부재가 신뢰를 거부하는 보수 방향이라 그대로 채용해도 건전하다. **`status` 부재 = stable** 은 부재가 안정을 부여하는 긍정 방향이라 재정의 대상이다. 문제는 "부재 기본값"이라는 장치가 아니라 **기본값의 방향**이다.

프로필의 재정의 예시:

| 필드 | 부재의 재정의 | 근거 |
|---|---|---|
| `epistemic_status` | 부재 금지(필수) — 편입 스키마 검사 실패 | 게이트 참여 필드, 작성자 판단 강제 |
| `verified`류 | 부재 = 확인 기록 없음, 최저 신뢰 | 보수 방향, OKF 정의 그대로 채용 |
| `status`류 | 부재 = 미판정, 게이트에서 stable로 읽지 않음 (또는 필수화) | 조건 2 |
| `stale_after` | 부재 = 기한을 선언하지 않음 | 부재에 게이트 효과 없음, 안전 |
| `uncertainties` | 부재 ≠ `[]`. 부재 = 미조사, `[]` = 조사했고 없음 | 조건 3 |

외부 상호운용은 싸게 처리한다: 파생 지도를 내보낼 때는 항상 명시값을 기록해서, OKF 기본값 규칙으로 읽는 외부 소비자도 같은 진실을 읽게 한다. 남의 번들을 읽을 일이 생기면 그때만 OKF 원래 기본값으로 읽는다.

- 산문 링크·기계 참조 모두 **ID 링크**로 통일. 색인은 편입마다 결정론 재생성되는 커밋된 파생 보기이고, 검사기가 바이트 대조로 최신성을 강제(불일치=blocked). 사람·외부용 렌더는 ID→경로 치환.

- 기존 유지: 정규 YAML형+바이트 해시, 의미 경로+frontmatter ID, 형식 있는 관계, v0.2 부분집합 잠금.

## 어시스턴트

"지식층 일반화 범위"는 다음 결정이다: **B*의 개념 문서 형식(정규 YAML frontmatter + 산문 본문 + ID 링크)을 F·관계 외에 어떤 기록 종류까지 적용하고, 스키마 레지스트리의 저장 분류 선을 어디에 긋는가.** 설계상 모든 기록 종류는 레지스트리에서 정확히 하나의 저장 분류를 받으므로(§3.3, §29), 이 결정은 결국 레지스트리의 한 줄 — "어떤 종류가 개념 문서 분류에 속하는가" — 를 정하는 일이다.

## 판별 기준

어떤 기록 종류가 개념 문서 형식에 적합한지는 네 기준으로 갈린다.

1. **산문이 의미의 주 담체인가.** 기록의 본질이 사람·AI가 읽고 쓰는 산문(진술, 판독, 주장, 정의)이면 "frontmatter 외피 + 본문"이 자연스럽다. 기계 필드뿐인 기록을 개념 문서로 만들면 JSON을 더 나쁜 옷에 입힌 것에 불과하다.
2. **연구 중에 항해되는 대상인가.** AI·사람이 연구의 장에서 훑고 연결하고 되돌아오는 기록이면 위키 형식과 ID 링크의 이득이 실재한다. 특정 관문에서 도구만 읽는 기록이면 이득이 없다.
3. **변경 경로가 연구 저작인가.** 작업→편입 경로로 사람·AI가 쓰는 기록인가, 도구·감독기가 CAS로 고속 갱신하는 상태인가. 후자는 후보가 아니다(runtime ref들은 애초에 공용 트리 밖이다, §1.2).
4. **게이트 밀도가 낮은가.** 조건 평가·검사·봉인에 참여하는 필드가 frontmatter로 충분히 담기는가, 아니면 기록 전체가 기계 입력인가.

## 계층 2의 개별 논점 — 왜 자연 후보인가

**자료·근거.** 문헌 판독, 관찰, 계산 결과, 실패 기록이 사는 곳이다. 정보 상태 어휘(`source | observation | computation | argument | hypothesis | failure_record`)와 무결성·재현 조건은 frontmatter로, 판독 내용·윤곽은 본문으로 정확히 갈라진다. 외부 출처의 기술과 출처 신호는 OKF가 설계된 본거지 그 자체다(`sources`, 신빙성 신호). 그리고 결정적으로 — **F가 반쪽 위키가 되는 것을 막는다.** F 객체의 `evidence_refs`가 가리키는 곳이 자료·근거다. F만 개념 문서이고 근거가 JSON이면, 항해자는 링크를 따라가다 장의 경계에서 형식 벽에 부딪힌다. 사용자의 목적(장으로서의 프런티어)은 F와 그 근거가 같은 매체일 때 완성된다.

**공용 연구 기억.** 주장 + 정보 상태(`fact | inference | heuristic | hypothesis`) + 적용·제외 범위 + 효력 — frontmatter와 본문의 분업이 그대로 맞는다. "원자료 없이 요약만 남기는 기억을 만들지 않는다"(§6.8)는 규율은 OKF의 `sources` 규율과 동형이다.

**연구 맥락.** 용어·정의·경계·피해야 할 동의어의 용어집이다. 본질이 산문이고, "수학적 정의가 Lean 정본에 들어가면 복제하지 않고 Lean 정본 객체와 인증된 해설을 가리킨다"(§6.3)는 요구를 ID 링크가 자연스럽게 구현한다. `instance.json`의 활성 맥락 집합 검사(§6.1)는 frontmatter 효력 필드로 유지된다.

## 계층 3의 명명된 위험 — 왜 유보 대상인가

**수학 해설.** 이미 Markdown이므로(§19.1 `explanation.md`) 형식 거리는 가장 가깝다. 그러나 동일성 인증 기제가 해설의 **안정된 anchor와 전체 해설 해시**에 결박돼 있다(§19.2). frontmatter를 얹으면 해시 범위·anchor 안정성·정규화기의 상호작용이 §19 전체의 재검증 범위로 번진다. 이득(장의 통일성)보다 결합 위험이 크므로 1단계에서 제외하고, F층 운용 경험 뒤 별도 결정을 권한다.

**K 항목.** 항해 가치는 높다 — "우리가 무엇을 아는가"를 훑는 페이지들이다. 그러나 고유 위험이 있다: K 기록에 자유 산문 본문을 허용하면 **인증되지 않은 제2의 해설 채널**이 생긴다. 해설–형식 동일성 규율은 "이 Lean 객체가 무엇을 뜻하는가"의 산문을 인증 사슬이 소유하게 했는데, K 개념 문서의 본문이 그 옆에서 비인증 의미 서술을 축적하면 규율이 우회된다. 포함하려면 프로필이 K의 본문을 금지하거나 생성 전용(인증된 해설에서 렌더)으로 못 박아야 한다. 이 위험 관리가 필요하므로 조건부다. 실용적 대안: K의 항해 페이지는 파생 지도 렌더로 제공하고 정본 K 기록은 JSON으로 남긴다.

**연구 헌장·정책.** 형식상으론 가능하다(헌장 산문은 이미 별도 Markdown, §6.2). 그러나 변경이 사용자 권한·영향 전건 계산과 결합된 저빈도 기록이라 위키화의 이득이 작고, 정책은 override 경로·적용 범위의 그래프 검사(§6.3)가 기계 중심이다. 이득 소, 위험 소 — 미뤄도 잃는 것이 없다.

## 선택지와 효과

1. **최소 (계층 1만)**: F·관계만 개념 문서. 효과: 장이 반쪽 위키가 된다 — F에서 근거·기억으로 가는 링크가 형식 경계를 넘는다. 항해 목적이 절반만 달성된다.
2. **지식층 (계층 1+2)**: F·관계·자료·근거·기억·맥락 — "연구 지식의 장" 전체가 한 매체. 인증(해설·K)과 권한(헌장·정책·결정·전례)과 실행(작업·runtime)은 현행 유지. 형식 경계가 "지식 대 판정·제어"라는 의미 있는 선과 일치한다.
3. **전면 (계층 1~3 이상)**: 계층 3의 결합 위험을 1단계부터 안는다. 계층 4까지 가면 산문 없는 봉인 기계까지 형식을 바꾸는 것이라, 앞선 실익 분석 기준으로 이득 없는 변경이다.

## 권고 (근거와 분리된 AI 추천)

# 수신자의 판단을 설계하는 글

수신자가 작성자의 실제 의도를 같은 의미로 이해하게 쓴다. 수신자는 글만으로 필요한 판단과 행동을 선택할 수 있어야 한다.

## 품질 계약

세 가지는 통과 조건이다.

- **정확성**: 관련 원천과 사실을 왜곡하지 않는다.
- **충실성**: 사용자의 목적과 확정된 의도에서 이탈하지 않는다.
- **정합성**: 글 내부와 연결된 현행 계약에 모순을 남기지 않는다.

세 조건이 충돌하면 하나를 희생하지 않는다. 원천, 사용자 결정, 지시의 우선순위를 확인해 충돌을 해소한다.

통과한 표현은 다음 순서로 고른다.

1. **명확성**: 수신자가 같은 의미로 읽는다.
2. **충분성**: 목적을 달성할 정보와 논증을 갖춘다.
3. **간단성**: 의미를 보존하는 범위에서 구조와 방법을 쉽게 만든다.
4. **간결성**: 수신자의 판단·행동·검증을 바꾸지 않는 군더더기를 제거한다.

짧게 쓰기 위해 사실, 조건, 예외, 논증 단계를 빼지 않는다.

## 작동 원리

프롬프트 작성은 수신 AI의 의사결정 자유도를 설계하는 작업이다. 작성자는 이미 확정할 수 있는 중요한 결정을 명시한다. 사용자에게 속한 결정은 창작하지 않는다.

좋은 프롬프트는 가능한 결과를 목적에 맞는 범위로 좁힌다. 좋은 프롬프트는 결과의 중심을 원하는 방향으로 옮기고 불필요한 해석 편차를 줄인다. 탐색에 필요한 자유도는 남긴다.

정보의 충분성은 분량으로 판정하지 않는다. 수신자의 판단, 행동, 우선순위, 검증을 바꾸는 정보를 남긴다. 작성 경위와 기각된 초안처럼 현재 목적에 기여하지 않는 정보는 뺀다.

## 지식층 일반화 범위 — 무엇을 정하는 결정인가

### 1. 결정의 정확한 내용

B* v3은 지금까지 **F 객체와 관계**에 대해서만 "정본 저장 형식을 개념 문서 형식(frontmatter+산문 본문의 .md)으로 바꾼다"고 확정했다. 그런데 같은 논리 — 본문이 산문인 기록은 개념 문서가 자연스럽다 — 는 F 말고도 여러 기록 종류에 적용될 수 있다. **일반화 범위란, 공용 핵심 기록 중 어디까지를 개념 문서 형식으로 전환하고 어디부터를 현행 정규 JSON으로 남길지의 경계선이다.**

혼동을 막는 구분 두 가지를 먼저 둔다.

- **저장 형식 전환 대상 ≠ 연구 지도에 보이는 대상.** 파생 보기인 연구 지도는 K 객체든 작업이든 무엇이든 개념 문서로 **렌더**할 수 있다. 일반화 범위는 렌더가 아니라 **정본 자체의 저장 형식**을 무엇으로 하느냐만 정한다.
- **runtime 상태는 애초에 무관하다.** run·request·monitor·supervisor 등은 공용 트리 밖의 ref에 사는 기계 상태라, 어떤 범위를 골라도 정규 JSON 그대로다. 이 결정은 `research/<instance>/` 아래 공용 핵심 기록에만 걸린다.

### 2. 판정 기준 네 개

기록 종류 하나를 전환할지 판단하는 기준은 네 개다.

1. **산문 중심성** — 본문 산문을 지우면 기록이 무의미해지는가. 그렇다면 개념 문서가 자연스럽고, 기록이 좌표·해시·상태값의 묶음이라면 JSON이 자연스럽다.
2. **항해 가치** — 연구 중에 AI·사람이 이 기록을 위키처럼 훑고, 링크를 따라 이웃으로 건너가는 것이 연구에 기여하는가.
3. **게이트 하중** — 발생 조건 평가, 착수 가능성, 자동 적용 같은 결정론 기계가 이 기록의 필드를 얼마나 읽는가. 전환 자체는 어느 기록이든 가능하지만(평가가 파싱 구조 위에서 도니까), 하중이 클수록 전환 결함의 파급과 재검증 부담이 커진다.
4. **권위 민감도** — 이 기록을 쓰는 주체가 AI 연구 역할인가, 사용자 권위인가. 사용자 권위의 봉인 기록은 형식 실험보다 봉인의 단순성이 우선한다.

### 3. 공용 핵심 기록의 전수 분류

설계의 기록 종류를 이 기준으로 분류하면 세 무리로 갈린다.

**명백한 후보 — 산문이 본체이고, AI가 연구 중에 계속 만들고 고치는 지식**

| 기록 | 내용 | 판정 이유 |
|---|---|---|
| F 객체·관계 (+종류 정의) | 질문·가설·방향의 산문과 형식 간선 | 이미 B* 범위. 종류 정의도 의미 Markdown이 본체라 같이 가는 것이 자연스럽다 |
| 연구 맥락 | 용어, 정의, 경계, 피해야 할 동의어 | 용어집은 개념 문서의 원형 그 자체다. 게이트 하중 낮음 |
| 공용 연구 기억 | 경험·교훈 주장, 정보 상태, 적용 범위, 효력 | 본문=주장 산문. 선택 packet이 산문으로 소비. 게이트 하중 낮음 |
| 자료·근거 | 조사·관찰·계산·논증·실패의 서사와 출처·확인 범위 | 본문=조사 서사. OKF의 `sources`·신뢰 가족과 구조가 그대로 맞는다. 이진 산출물은 지금처럼 `artifacts/` 파일 참조로 유지 |

**경계 — 산문은 있으나 다른 성질이 우세**

| 기록 | 성질 | 판정 이유 |
|---|---|---|
| 연구 헌장 | 산문은 이미 별도 Markdown이고 JSON이 해시 참조(§6.2) | 개정이 드물고 사용자 권위 경로다. 읽기 경험은 이미 산문이라 전환의 추가 이득이 작다 |
| 연구 정책 | 규범 문면(산문) + 기계 판독 적용 범위·override 그래프(§6.3) | 산문 반, 게이트 반. override 전수 검사가 걸려 있어 전환 위험이 후보군보다 크다 |
| 작업 기록 | 질문·범위 산문은 이미 별도 문서(§8.1) + 발생 조건 AST·필수 입력·완료 기준 | **게이트 최중량.** 착수 가능성 공식과 실행 껍질의 직접 입력이라, 전환이 사는 이득(항해 가치)은 작고 위험은 가장 크다 |

**명백한 비대상 — 산문 본체가 없어 개념 문서가 줄 것이 없는 기록**

| 기록 | 이유 |
|---|---|
| 사용자 결정·전례 | 권위 봉인 기록. 기계 봉인의 단순성이 본질이다 |
| Lean 정본 객체(canon-entry) | 좌표 기록이다. 지식 본문은 수학 해설과 Lean 파일에 있다 |
| 수학 해설 | **전환 불요** — 이미 Markdown이다. frontmatter를 얹는 것은 §19 인증 기계(anchor·해시 봉인)와의 접촉면만 늘린다 |
| 신뢰 시대·연구 설정 | 판본·해시 manifest와 운용 값. 순수 기계 기록 |
| 공용 편입·변경 영향·감사·수입/보관 manifest | 트랜잭션·판정 기록 |

### 4. 선택지와 그 결과

**범위 1 — 최소 (F·관계·종류 정의만).** 검토의 원래 목적만 충족한다. 결과: 지식의 장 안에 형식 이음새가 남는다 — F를 위키로 읽다가 그 근거(evidence)로 건너가는 순간 JSON+별도 문서 형식으로 떨어진다. 항해 경험의 단일성이 깨지는 지점이 지식층 **내부**에 생긴다.

**범위 2 — 연구 지식 전체 (범위 1 + 맥락·기억·자료·근거).** "AI가 연구 중에 계속 생산·개정하는 지식"이 전부 한 형식이 된다. F→근거→기억→용어를 오가는 항해가 끊기지 않는다. 전환 접촉면은 기준 3·4가 낮은 기록에만 닿는다.

**범위 3 — 산문 있는 핵심 기록 전체 (범위 2 + 헌장·정책).** 권위 문서까지 개념 문서가 된다. 추가 이득은 작다 — 헌장·정책의 산문은 이미 별도 문서라 읽기 경험이 산문이고, 개정 빈도가 낮으며, packet 조립은 형식과 무관하게 전문을 싣는다. 추가 위험은 정책의 override 검사 접촉이다.

**범위 4(작업·결정·전례까지)는 선택지로 두지 않는다.** 비대상 무리는 산문 본체가 없어 기준 1에서 탈락한다. 전환해도 항해 가치가 생기지 않고 게이트·봉인 위험만 산다.

### 5. 이 결정의 되돌림 가능성

지금은 미구현·무인스턴스 상태라 어느 범위를 골라도 설계 문서 수정일 뿐이다. 구현 뒤에는 저장 분류를 뒤집는 것이 §23의 계약 판본 절차가 되어 마이그레이션 비용이 생긴다. 따라서 자연스러운 손절선은 "확실한 후보는 지금 전환하고, 경계 무리는 남겨 두었다가 프로필이 실전에서 증명되면 뒤집는다"이다. 저장 분류는 스키마 레지스트리가 종류별로 하나씩 배정하는 기존 장치(§3.3)라, 혼합 재고는 새 복잡성이 아니다.

### 6. 권고 (근거와 분리된 AI 추천)

**범위 2를 권고한다.** 산문 중심성과 항해 가치를 만족하면서 게이트 하중과 권위 민감도가 낮은 기록의 최대 집합이고, 지식 항해의 단일성이 지식층 내부에서 끊기지 않으며, 최중량 게이트(작업 기록)와 권위 봉인(결정·전례)에는 손대지 않는다. 헌장·정책은 남겨 두고, 프로필이 증명된 뒤의 확장 후보로 기록해 두면 된다.

## 1. 판정 원리: 직접 읽기가 대체할 수 있는 것과 없는 것

파생 보기 하나를 놓고 이렇게 묻는다: **"이 보기를 지우고 정본을 직접 읽으면 같은 정보를 얻는가?"**

- 얻는다면 그 보기는 **재표현 보기**다 — 정본 내용을 다른 모양으로 다시 보여줄 뿐이다. JSON 정본 시절에는 재표현이 필수였다(사람도 AI도 원자료를 그대로 읽기 나빴다). B*에서 정본이 개념 문서가 되면서 이 부류의 존재 이유가 소멸했다. 사용자의 직관이 맞는 지점이다.
- 얻지 못한다면 그 보기는 **계산 보기**다 — 내용의 재표현이 아니라 **전건 평가의 결과**를 담는다. F 파일을 아무리 읽어도 "이 커밋에서 어느 씨앗이 착수 가능한가"는 나오지 않는다. 그건 발생 조건을 평가해야 나오는 판정이다. 이 부류는 정본의 형식과 무관하게 남는다.

그 사이에 작은 세 번째 부류가 있다: **항해 보조** — 원리상 직접 읽기로 대체 가능하지만(전수 훑기), 대체 비용이 반복적으로 발생하는 것.

## 2. 직접 읽기의 실익 (이제 기본값이 되는 이유)

- **드리프트가 원천 소멸한다.** 보기는 정본과 어긋날 수 있는 표상이고, 표상의 자기 기술을 믿지 말라는 것이 이 저장소의 검증 원칙이다. 읽는 것이 곧 정본이면 어긋날 사본 자체가 없다.
- **항상 현행이다.** 보기 재생성 시점이라는 개념이 사라진다.
- **도구가 필요 없다.** worktree의 작업자는 고정 커밋에서 트리를 그냥 연다. 렌더러도 변환기도 없다.
- **권위 혼동 위험이 준다.** "파생 보기를 정본으로 오독"하는 결함 부류(§0.1이 방어하는)는 보기가 적을수록 표면이 좁아진다.

작업자의 기본 모드는 이미 직접 읽기다 — 작업별 작업대는 고정 공용 커밋의 트리 전체이고, B*는 그 트리를 읽기 좋게 만든 것이다.

## 4. 혼동 주의: packet은 보기가 아니다

포트폴리오·검토 역할이 받는 종합 맥락 묶음(§10.2)은 파생 보기가 아니라 **입력 봉인**이다. 기능이 다르다 — 읽기 편의가 아니라, "이 판정 세션이 정확히 무엇을 읽었는가"를 manifest 해시로 닫는 증거 폐쇄다. 직접 열람은 이것을 대체할 수 없다(자유 열람은 판정의 증거 기반을 기록하지 않는다). 다만 B* 덕에 packet **조립은** 단순해진다: 개념 문서가 그대로 들어간다.

## 5. 결론 — 구조 D의 지위 갱신

2. **주문형 렌더 하나** — 사람·외부 소비자용 ID→경로 치환. 필요할 때만.
3. **기존 계산 보기** — 실행 껍질·status·사람 보고. 정본 형식과 무관한 존재 이유를 가진다.

# 수신자의 판단을 설계하는 글

수신자가 작성자의 실제 의도를 같은 의미로 이해하게 쓴다. 수신자는 글만으로 필요한 판단과 행동을 선택할 수 있어야 한다.

## 품질 계약

세 가지는 통과 조건이다.

- **정확성**: 관련 원천과 사실을 왜곡하지 않는다.
- **충실성**: 사용자의 목적과 확정된 의도에서 이탈하지 않는다.
- **정합성**: 글 내부와 연결된 현행 계약에 모순을 남기지 않는다.

세 조건이 충돌하면 하나를 희생하지 않는다. 원천, 사용자 결정, 지시의 우선순위를 확인해 충돌을 해소한다.

통과한 표현은 다음 순서로 고른다.

1. **명확성**: 수신자가 같은 의미로 읽는다.
2. **충분성**: 목적을 달성할 정보와 논증을 갖춘다.
3. **간단성**: 의미를 보존하는 범위에서 구조와 방법을 쉽게 만든다.
4. **간결성**: 수신자의 판단·행동·검증을 바꾸지 않는 군더더기를 제거한다.

짧게 쓰기 위해 사실, 조건, 예외, 논증 단계를 빼지 않는다.

## 작동 원리

프롬프트 작성은 수신 AI의 의사결정 자유도를 설계하는 작업이다. 작성자는 이미 확정할 수 있는 중요한 결정을 명시한다. 사용자에게 속한 결정은 창작하지 않는다.

좋은 프롬프트는 가능한 결과를 목적에 맞는 범위로 좁힌다. 좋은 프롬프트는 결과의 중심을 원하는 방향으로 옮기고 불필요한 해석 편차를 줄인다. 탐색에 필요한 자유도는 남긴다.

정보의 충분성은 분량으로 판정하지 않는다. 수신자의 판단, 행동, 우선순위, 검증을 바꾸는 정보를 남긴다. 작성 경위와 기각된 초안처럼 현재 목적에 기여하지 않는 정보는 뺀다.

# 수신자의 판단을 설계하는 글

수신자가 작성자의 실제 의도를 같은 의미로 이해하게 쓴다. 수신자는 글만으로 필요한 판단과 행동을 선택할 수 있어야 한다.

## 품질 계약

세 가지는 통과 조건이다.

- **정확성**: 관련 원천과 사실을 왜곡하지 않는다.
- **충실성**: 사용자의 목적과 확정된 의도에서 이탈하지 않는다.
- **정합성**: 글 내부와 연결된 현행 계약에 모순을 남기지 않는다.

세 조건이 충돌하면 하나를 희생하지 않는다. 원천, 사용자 결정, 지시의 우선순위를 확인해 충돌을 해소한다.

통과한 표현은 다음 순서로 고른다.

1. **명확성**: 수신자가 같은 의미로 읽는다.
2. **충분성**: 목적을 달성할 정보와 논증을 갖춘다.
3. **간단성**: 의미를 보존하는 범위에서 구조와 방법을 쉽게 만든다.
4. **간결성**: 수신자의 판단·행동·검증을 바꾸지 않는 군더더기를 제거한다.

짧게 쓰기 위해 사실, 조건, 예외, 논증 단계를 빼지 않는다.

## 작동 원리

프롬프트 작성은 수신 AI의 의사결정 자유도를 설계하는 작업이다. 작성자는 이미 확정할 수 있는 중요한 결정을 명시한다. 사용자에게 속한 결정은 창작하지 않는다.

좋은 프롬프트는 가능한 결과를 목적에 맞는 범위로 좁힌다. 좋은 프롬프트는 결과의 중심을 원하는 방향으로 옮기고 불필요한 해석 편차를 줄인다. 탐색에 필요한 자유도는 남긴다.

정보의 충분성은 분량으로 판정하지 않는다. 수신자의 판단, 행동, 우선순위, 검증을 바꾸는 정보를 남긴다. 작성 경위와 기각된 초안처럼 현재 목적에 기여하지 않는 정보는 뺀다.

record_kind 를 type으로 대체하고 record_id 를 그냥 id 라고 하고, 그 외에도 OKF의 포맷을 받아들일 것은 받아들이는 것은 어떨까? 즉, 기존 자산의 '형식 보존'에는 큰 비중을 두지 말고 필요하다면 OKF의 형식으로 '기능 대체'를 해서 '기능 보존'에 초점을 두는 것

## 어시스턴트

타당하다 — 그리고 한 가지 가드를 붙여야 안전하다. 판정부터 요약하고 수정안에 반영한다.

**동의하는 근거**: 미구현·무인스턴스 상태라 기존 필드 이름에는 이전 비용도 호환 부채도 없다. "형식 보존"이 지켜주던 것은 사실상 없고, 지켜야 할 것은 기능(닫힌 어휘, 정체성, 검사 가능성)뿐이다. 특히 `record_kind`→`type` 대체는 이득이 실질적이다: 외부 OKF 소비자가 읽는 바로 그 필드에 우리의 종류 어휘가 실리고, 병렬 필드 둘(`type`+`record_kind`)이 어긋날 드리프트 표면 자체가 사라진다. OKF가 "type은 중앙 등록되지 않는다"고 한 자리에 우리의 종류 정의 기록이 등록 기제로 정확히 맞물린다. `record_id`→`id`도 손실 없다 — 루트 CONTEXT.md의 개념 "핵심 기록 ID"는 필드 이름을 고정하지 않으므로 개념은 불변이고 직렬화 이름만 짧아진다.

**필요한 가드 하나**: "받아들일 것은 받아들인다"의 판별 기준을 명시해야 한다 — **예약 이름은 값 의미까지 일치할 때만 쓴다.** 반례가 실제로 있다: 우리 역할별 생명주기 값(active/superseded/…)을 OKF `status`라는 이름에 실으면, draft/stable/deprecated를 기대하는 외부 소비자가 오독한다. 의미가 다른 곳에 예약 이름을 점거하면 상호운용이 확장 필드를 쓸 때보다 오히려 나빠진다. 같은 기준으로 `generated {by, at}`(저작 주체·시각)는 기능이 일치해 채용 가능하지만, 생성 근거(cause — §7.7의 허용 근거 좌표)는 OKF에 대응물이 없으므로 확장 필드로 남는다. `verified`는 관계의 확인 상태·판정자(§6.7) 표현에 잘 맞고, `sources`는 자료·근거의 외부 출처 좌표에 맞는다. `stale_after`는 대응 기능이 없어 채택하지 않는다.

**대체가 드러내는 위임 결정 하나**: `type`이 종류를 소유하면 "기록 가족(F 객체) 대 구체 종류(question/conjecture)"의 계층을 어떻게 접을지가 남는다(F의 `frontier_kind`도 `type`에 흡수할지). 이건 수행 세션 재량으로 두되, 가족 판별이 필요하면 파일 안 중복 필드보다 레지스트리·종류 정의 해석을 우선하라는 제약을 달았다.

수정안에 반영한다.

## 어시스턴트

제안을 채택해 수정안에 반영했다. 반영 내용:

**§4.2 — 기능 대체 원칙 신설 (확정 결정)**. "형식 보존에 독립 가치를 두지 않는다"를 명문화하고 세 규칙으로 닫았다: ① 기능이 일치하면 OKF 이름·형태를 그대로 쓴다 ② OKF에 없는 기능은 확장 필드로 ③ **값 의미가 다른 곳에 OKF 예약 이름을 점거하지 않는다** — 예약 이름을 쓰면 값 의미까지 OKF를 따른다. 세 번째가 이번에 추가한 가드다(생명주기 값을 `status`에 싣는 오독 유발형 대체를 차단).

확정 적용으로: `record_id`→**`id`**(개념 "핵심 기록 ID"와 ULID 값은 불변, 직렬화 이름만 변경), `record_kind`→**`type`**(병렬 필드 제거, 닫힌 어휘를 type이 소유, 종류 정의 기록이 등록 기제), `title` 채용, `description` 권장 채용(index.md 원천), `generated`/`verified`/`sources`는 기능 일치 자리에 채용 가능(생성 근거는 대응물이 없어 확장 필드 유지). 적용 경계도 명시했다 — 비전환 JSON 기록의 필드 이름은 무수정 영역이고, 같은 개념이 두 형식에서 다른 필드 이름을 가짐을 개편 문면에 한 번 적는다.

**연쇄 수정**: §3 채용 태도에 필드 수준 대체 한 문장, §4.4의 `record_id`·`record_kind` 언급을 `id`·`type`으로, §6 위임 표의 사상 행을 두 행으로 교체(type의 종류 계층 — `frontier_kind` 흡수 여부 포함 — 과 기능 일치 필드 채용 세부), §7 잔존 구절 검색어에 `record_id`·`record_kind` 추가, §8 완료 기준에 기능 대체 원칙 반영.

대체가 드러낸 위임 결정 하나 — `type`이 기록 가족(F 객체)을 담을지 구체 종류(question/conjecture)를 담을지 — 는 수행 세션 재량으로 두되 "가족 판별이 필요하면 파일 내 중복보다 레지스트리 해석 우선" 제약을 달았다.

남은 사항은 이전과 같다: 커밋 미수행(지시 대기), 수정안 자체의 검증 실행 여부.

## 어시스턴트

`type` 위임 결정의 실체를 설명한다. 이것은 이름 문제가 아니라, 현행 설계가 가진 **종류의 2층 구조**를 한 필드에 어떻게 접을 것인가의 문제다.

## 1. 현행 설계의 종류 2층 구조

통합-설계의 기록 종류는 두 층으로 되어 있고, 두 층은 하는 일이 다르다.

**1층 — 기록 가족** (현행 `record_kind`): frontier_object, relation, evidence, research_memory, context… 이 값이 결정하는 것:

- 어느 JSON Schema로 이 기록을 검증하는가 (§3.2, §29 레지스트리 사상)
- 어느 역할·저장 분류에 속하는가 (§4.1 — 개편 후에는 frontmatter 기반 역할 판정의 입력)
- "모든 F 객체를 순회한다" 같은 가족 단위 기계 동작(packet 조립, 생존 절차의 F 전수 검사)의 선별 기준

**2층 — 구체 종류** (가족 안의 분류): F 객체의 `frontier_kind`(question, conjecture, obstacle…)와 관계의 `relation_kind_id`(supports, refutes, formally_implies…). 이 값이 결정하는 것:

- 그 객체에 허용되는 상태·필수 필드 (§6.4: 종류 정의 기록이 소유)
- 관계라면 도메인·코도메인·필요 근거·수학 관계 여부 (§6.7)

두 층은 **확장 방식도 다르다.** 1층은 스키마 레지스트리에 닫혀 있어 바꾸려면 계약 판본 변경이다. 2층은 데이터 수준으로 열려 있다 — 새 종류 정의 기록을 편입하면 계약 변경 없이 새 종류를 쓸 수 있다(§23.3). 이 개방성은 연구가 자라며 새 F 종류를 만들 수 있게 하는 실익이므로 어떤 선택에서도 보존해야 한다.

참고로 2층이 있는 가족은 F 객체와 관계뿐이다(자료·근거의 정보 상태 6종을 2층으로 볼지는 해석의 여지가 있다). 연구 맥락·연구 기억은 1층만 있다 — 이 질문은 그들에게는 자명하다.

## 2. 왜 type 대체가 이 질문을 만드는가

기능 대체 원칙으로 `record_kind`라는 별도 필드가 사라지고 OKF `type` 하나가 종류를 소유하게 됐다. 그런데 type은 필드 하나이고 종류는 두 층이다. 그래서 **type에 어느 층을 실을 것인가**가 남는다. 선택지는 셋이다.

## 3. 세 선택지

표기는 예시이며 정확한 값은 수행 세션 재량이다.

**A — type = 가족.** 사실상 record_kind의 개명이다.

```yaml
type: "frontier_object"      # 가족
frontier_kind: "question"    # 구체 종류는 별도 필드로 존속
```

- 해석 경로: type → 레지스트리 행 → 스키마·역할. 구체 종류 검증은 현행 그대로 frontier_kind → 종류 정의 기록. 기계적으로 가장 보수적이다.
- 약점: 대체의 목적을 절반만 이룬다. 외부 OKF 소비자가 읽는 type에는 모든 F 파일에 똑같이 "frontier_object"가 찍히고, 정작 정보가 있는 분류(question인지 conjecture인지)는 외부 도구가 모르는 확장 필드에 남는다. OKF의 권고("생산자는 서술적이고 자명한 type 값을 고른다" — 참조 번들의 type은 "Metric", "BigQuery Table"처럼 구체 종류다)와 어긋나는, 적법하되 비관용적인 사용이다. 파일에는 종류 필드가 여전히 둘이다.

**B — type = 구체 종류.** OKF 관용에 가장 충실하다.

```yaml
type: "question"    # 구체 종류가 곧 type. frontier_kind 필드는 소멸
```

- 위키·외부 그래프에서 가장 읽기 좋다. 파일의 종류 필드가 정확히 하나다. 자료·근거도 `type: "observation"`처럼 정보 상태를 type으로 실을 수 있다.
- 새로 필요한 것 둘. ① **가족 유도의 간접화**: "이 파일은 F 객체인가"를 알려면 type 값을 레지스트리(고정 종류)와 활성 종류 정의 기록(확장 종류)에서 찾아 가족을 역산해야 한다. 결정론적이고 고정 커밋 위에서 가능하지만, 가족 단위 동작마다 조회가 한 단계 낀다. ② **전 가족 통합 이름공간의 유일성 불변식**: 현행에는 frontier_kind와 relation_kind_id가 서로 다른 이름공간이라 충돌이 구조적으로 불가능한데, 둘이 type 하나로 합쳐지면 누군가 "supports"라는 새 F 종류를 편입하려 할 때 관계 종류 "supports"와 충돌한다. 종류 정의 편입 시 전역 유일성 검사를 상태 검사기에 추가해야 한다(위반은 편입 거부로 봉쇄되므로 위험은 유한하다).

**C — type = 가족/구체 합성.** 한 값에 두 층을 접두로 싣는다.

```yaml
type: "frontier/question"    # 접두가 가족, 나머지가 구체 종류
```

- 가족 유도가 레지스트리 조회 없이 값 파싱으로 끝나고, 유일성은 현행처럼 가족 안에서만 지키면 되며, 파일의 종류 필드는 하나다. B의 두 추가 요구가 모두 사라진다.
- 약점: 외부 소비자에게 "frontier/question"은 "question"보다 덜 자연스럽다. OKF가 금지하지는 않는다(서술적 문자열이면 된다).

## 4. 이 선택이 닿는 기계장치

- 스키마 선택과 상태 검사기의 검증 경로 (§21.1)
- frontmatter 기반 역할·저장 분류 판정 (수정안 4.4)
- 종류 정의 기록의 검증 대상 식별과 편입 시 유일성 검사 범위
- `record_exists`(§7.3)의 종류 인수 — 다만 이 연산자는 특정 ID의 무결성 교차 확인이라 어느 층을 쓰든 적응 가능하고, 선택지를 가르는 요인이 아니다
- 가족 전수 순회(packet의 "현재 F 객체 전문", 생존 절차) — A·C는 필터/파싱, B는 레지스트리 역산
- index.md·외부 소비에서 보이는 분류의 정보량

## 5. 수정안에 단 제약의 정확한 의미

"가족 판별이 필요하면 파일 내 중복 필드보다 레지스트리 해석을 우선"이라는 제약은 세 선택지를 모두 열어 둔 채 **네 번째 나쁜 모양 하나만 배제한다**: type에 구체 종류를 싣고서 가족 필드를 별도로 또 두는 것. 그 모양에서 가족 필드는 type에서 유도 가능한 값의 중복이라, 대체가 없앤 이중 필드 드리프트 표면을 되살린다. A는 이에 해당하지 않는다 — A의 두 필드는 서로 다른 층이라 중복이 아니다.

## 6. 권고 (분리 표기)

내 판단으로는 **C가 건전성 대비 단순성에서 가장 유리하고, 외부 관용을 더 중시하면 B(전역 유일성 불변식 수용 조건)도 정당하다.** A는 안전하지만 대체의 목적 절반을 반납한다. 위임으로 남긴 이유는 이 셋이 모두 제약 안에서 성립하고 확정 결정의 본질을 바꾸지 않기 때문인데, 지금 이 자리에서 사용자가 직접 닫고 싶으면 그렇게 하라 — 그 경우 수정안 6절의 해당 위임 행을 확정 결정으로 옮기면 된다.

## 어시스턴트

`@`는 된다 — 그리고 검토해 보니 `/`보다 두 가지 실질 이점이 있다. C를 `@` 합성 표기로 확정해 수정안에 반영했다.

**`@`가 `/`보다 나은 점**

1. **충돌 표면이 없다.** 이 체계에서 `/`는 이미 경로의 문자다. 의미 있는 경로가 정본의 항해 축이 된 마당에, type 값 안의 `/`는 순진한 도구·AI가 경로 조각으로 오독할 여지를 만든다. 또 type 값이 파일명이나 URL 경로 세그먼트로 흘러가는 경우(종류별 렌더 페이지 등) `/`는 이스케이프가 필요하지만 `@`는 Windows·Unix 파일명과 URL 경로 세그먼트에서 모두 적법하다.
2. **관용이 방향을 잡아준다.** `@`는 user@host, pkg@version처럼 "X at/in Y"로 읽히므로 자연 어순이 **`구체종류@가족`**(`question@frontier`, `supports@relation`)이 된다. 정보량이 많은 토큰이 앞에 와서 사람이 훑을 때 유리하다 — 선택지 B의 가독 이점을 C가 회수하는 셈이다. `/`였다면 어순이 가족 우선(frontier/question)으로 기울었을 것이다.

**확인한 무해성 한 가지**: YAML 1.2는 plain 스칼라의 **첫 문자** `@`를 예약하는데, 우리 정규형은 모든 스칼라를 큰따옴표로 감싸고, 합성 표기상 `@`는 값의 중간에만 오므로(가족 단독이면 `@` 없음) 초안의 비인용 표기에서도 문제가 없다.

**닫은 해석 규칙** (수정안 4.2에 확정으로 반영):

- 구체 종류가 있는 가족(F 객체, 관계)은 `구체종류@가족`, 없는 가족은 가족 토큰 단독(예: `memory`).
- 세그먼트 안에 `@` 금지 → 값의 `@`는 0개 또는 1개. 1개면 앞=구체 종류·뒤=가족, 0개면 전체=가족. 가족 판별은 이 파싱만으로 끝난다.
- F의 `frontier_kind`·관계의 `relation_kind_id` 별도 필드는 `type`에 흡수. 구체 종류의 유일성은 현행처럼 가족 안에서만 요구(전역 유일성 불변식 불요 — B의 추가 비용 회피 유지).

**수정안 갱신 내역**: §4.2에 합성 표기 결정 추가, §6 위임 표에서 종류 계층 행을 제거하고 남은 재량(가족·구체 토큰의 정확한 표기, 자료·근거 정보 상태를 `observation@evidence`로 볼지 `evidence`+별도 필드로 볼지)으로 교체, §7 잔존 검색어에 `frontier_kind`·`relation_kind_id` 추가, §8 완료 기준 문면 갱신.

## 재작성의 핵심

"무엇을 만들 것인가"의 각 항목이 이제 "어떠한 것을 만들 것인가"까지 답하도록, 추상 명명과 위임으로 남겨뒀던 자리를 전부 구체값으로 채웠다.

- **종류별 필드 사상표 (4.2.4)** — 현행 §6.4/6.6/6.7/6.8/6.3의 필드 전건이 새 형식의 정확히 어디로 가는지(type 흡수 / frontmatter 필드 / 본문 / 외피 흡수)를 일곱 기록 종류마다 표로 닫았다. 이 표가 "기능 보존"의 증명 대상이다.
- **공통 frontmatter 규범 (4.2.3)** — `id`, `type`, `title`, `description`, `lifecycle {value, reason}`, `cause {id, kind}`, `generated`, `sources`, `artifacts`, `schema_version`의 필수 여부와 의미, 행위자 표기(`execution:E-…`)까지.
- **`@` 합성 표기 확정 (4.2.2)** — 가족 토큰 7종 표기, 해석 규칙, YAML 선행 `@` 무해성 근거 포함. (직전 턴에 보고만 되고 미적용이던 내용이 여기 반영됐다.)
- **축자 예시 (4.2.6, 4.9)** — F 객체와 관계의 완전한 개념 문서 2건(정규형 규칙 — 키 정렬·인용·블록 스타일 — 을 스스로 준수하는 표본)과 index.md 항목 예시.
- **구체 경로·이름** — `knowledge/` 루트와 초기 하위 구조, `id-index.json`, `docs/do-math/okf/SPEC-v0.2.md`, 저장 분류 `knowledge_record`, 도구 4종(`knowledge-fmt`/`knowledge-index`/`record` 확장/`knowledge-render`).
- **승격 5단계, 초안 표지(= `id` 부재), 정규형 추가 세목(`null` 불허, 본문 무변경)** 등.

## 검토 편의 장치

옛 "위임 재량" 절을 **§6 결정의 유래 구분**으로 바꿨다: ① 대화에서 명시 승인된 골격, ② **AI가 채운 세부 16건의 목록**(검토 시 이 목록을 우선 훑으면 된다), ③ 수행 세션에 남는 잔여 재량. 채운 것 중 특히 판단이 갈릴 수 있는 항목: 자료·근거의 정보 상태는 `type` 흡수하되 연구 기억의 정보 상태는 필드로 남긴 비대칭(불변적 종류 대 승급하는 상태라는 근거), F의 `generation` 필드를 외피 `cause`로 흡수, 관계 `from`/`to`를 커밋 미고정 맨 ID로(트리 동판본성 근거), 생성 파일 `index.md`만 경로 링크 예외.

정정 보고: 직전 턴에서 `@` 편집을 적용했다고 보고했으나 실제로는 도구 호출 없이 보고만 나간 상태였다. 이번 재작성에 전부 포함해 바로잡았다.
