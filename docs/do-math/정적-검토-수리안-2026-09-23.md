# do-math 정적 검토의 전체 수리안

작성일: 2026-09-23. 대상: `.claude/skills/do-math/`.

상태: **구현 검토용 명세. 구현 변경·테스트·do-math 실행은 하지 않았다.** 앞선 검토의 1~7번과 별도 비용 개선 사항을 모두 다룬다. 이 문서의 새 함수·필드·코드 조각은 실제로 적용할 변경의 명세이며 아직 구현되지 않았다. 1번은 simplify 재검토 결과, 2~8번은 후속 구체화 결과다.

전체 계획 재검토 결과를 반영했다. 주요 정정은 4번의 원 생산자 제출 마무리 보호, 5번의 불필요한 과거 판정 전건 순회 제거, 7번의 실제 예약 계산과 대기 진단 통합이다. 검토 근거·영향 범위·추가 반례는 [수리안 재검토 기록](정적-검토-수리안-재검토-2026-09-23.md)에 남긴다.

목표는 제공된 근거를 정상적으로 참조·처분할 수 있게 하고, 목표 감사의 결과와 이력이 다음 연구에 이어지게 하며, 문서·조회·실행 조건을 같은 계약으로 맞추는 것이다. 현재성·권한·독립 검토·종료 장벽을 통과하는 기존 경로 안에서 수리한다.

**1. 전체 과제 참조와 직접 비교 모집단을 분리한다 — simplify 재검토 반영**

이 절은 최초 기록의 지연 원문 조회 함수안과 대화에서 뒤이어 제안한 `task_reference_records` 추가안을 대체한다. 기존 구조의 유지나 변경량 최소화를 전제하지 않고, 입력 표현의 통합까지 비교한 결과다. 아직 코드에는 적용하지 않았다.

문제의 본질은 ‘근거로 제공한 기록 집합’과 ‘이번에 처분할 대상 집합’을 같은 크기로 만든 것이다. 필요한 것은 두 책임의 구별이다. 두 번째 전체 과제 필드를 추가하는 것 자체가 목적은 아니다.

| 비교한 방법 | 이득 | 추가 비용·영향 | 선택 |
|---|---|---|---|
| catalog 원문을 읽는 공통 resolver | 필요 기록만 지연 회수 가능 | 독자용 원문에 복원 경로가 추가되므로 저장 원문의 결과 해시와 달라질 수 있음. 원문/표시 정보 분리까지 해야 정확해짐 | 현재 수리에는 채택하지 않음 |
| 별도 `task_reference_records` 전체 사본 추가 | 검사기에 저장 원문을 확실하게 지급 | 기존 검사 입력 `tasks`도 이미 저장 원문이므로 두 필드의 중복·일치 책임이 추가됨 | 제거 |
| 기존 검사 입력 `tasks`의 범위를 전체 제공 과제로 정정 | 경계·철회·의존성 검사가 같은 과제 조회표를 사용. 새 조회 계층이 필요 없음 | 검사 파일은 기존보다 커짐. 계획 모집단 경계를 별도로 고정해야 함 | 이번 수리안 |
| 원본 기록 하나 + 별도 파일 위치표 + 역할별 투영으로 입력 전반 통합 | 독자와 검사기의 변형 원문 문제를 공통으로 해소하고 중복 보존을 줄일 수 있음 | 작업 결과 복원, 재개, 원문 참조, manifest, 역할 문서의 소비 계약을 함께 바꿔야 함 | 더 넓은 입력 재설계의 대안으로 남김 |

가장 일반적인 안을 금지하지 않는다. 현재 확인된 결함에서는 기존 검사 입력의 잘못된 범위만 고쳐도 여러 소비자가 함께 정상화된다. 입력 전반의 통합안은 별도의 기능 이득·반복 결함·보존 비용이 그 변경 범위를 정당화할 때 선택한다.

**1-A. 입력 생성 변경: 기존 필드 하나의 범위를 바로잡는다.**

`context_store.prepare_role_input`의 `validation_context = deepcopy(value)` 바로 뒤에서 다음 블록만 교체한다. 실행 대상은 기존과 같이 후보 준비와 연구 계획 두 역할이다.

```python
# 현재
if role in {'research_preparation', 'research_plan'}:
    validation_context['tasks'] = [
        deepcopy(runtime['tasks'][row['id']]) for row in value['tasks']
    ]

# 교체안
if role in {'research_preparation', 'research_plan'}:
    validation_context['tasks'] = [
        deepcopy(runtime['tasks'][identifier])
        for identifier in sorted(runtime['tasks'])
    ]
```

`runtime`은 이 입력을 생성하는 snapshot의 원래 기록이다. 역할 입력 생성 초반의 `set(reader_tasks) == set(runtime['tasks'])` 검사도 유지하므로, catalog로 제공하지 않은 다른 과제를 검사에만 추가하는 경로를 만들지 않는다.

모델에 렌더링되는 `value['tasks']`는 그대로 둔다. `validation_context`는 기존 `install_tools`가 `input/submission/context.json`으로 봉인하는 검사 입력이다. 두 문맥은 이미 별도 객체이며, 검사 문맥의 `tasks` 전체를 프롬프트 본문으로 복사하지 않는다. 생성된 참조 목록에 기존 제공 기록의 참조가 추가되는 크기 변화는 별도로 측정한다.

저장 원문의 결과에는 독자용 파일 복원 경로를 덧붙이지 않는다. 따라서 `results_sha256`·기존 assessment 대조에 독자용 자료를 역변환하는 알고리즘이 필요 없다. snapshot과 검사 문맥의 결박은 기존 입력 보존·중앙 수신 검사를 그대로 따른다.

**1-B. 계획 검사 변경: 기록 조회표에서 판정 모집단만 골라 전달한다.**

현재 `planning.validate_plan_submission(output, tasks, ready_ids)`의 시그니처는 유지하고 본문을 다음으로 교체한다.

```python
def validate_plan_submission(output: dict, tasks: dict, ready_ids: list[str]) -> None:
    from .task_contracts import returned_task_ids, validate_plan_dispositions
    comparison_ids = set(ready_ids) | set(returned_task_ids(tasks))
    comparison_tasks = {
        identifier: task for identifier, task in tasks.items()
        if identifier in comparison_ids
    }
    validate_plan_dispositions(output, comparison_tasks, ready_ids)
```

여기서 `returned_task_ids(tasks)`는 최신 저장소를 읽는 함수가 아니다. 전달된 고정 snapshot의 원래 과제 기록에서 반환 판정 대상을 계산하는 기존 순수 함수다. 입력 생성도 전체 `runtime['tasks']`에 동일 함수를 적용해 모델에 `returned_task_ids`를 제공한다. 따라서 전건 판정 대상이 달라지지 않는다.

이 제한은 `parallel_task_ids` 검사도 기존 범위로 유지한다. 전체 조회표를 직접 `validate_plan_dispositions`에 전달하면 그 검사에서 허용하는 과제 ID 범위까지 넓어질 수 있으므로, wrapper에서 비교 집합을 한 번 정한다. 존재하지 않는 ready ID는 기존 검사에서 계속 거부된다.

이 wrapper는 제출 검사와 중앙의 `_apply_task_plan` 양쪽에서 호출된다. `engine._apply_plan`이 봉인된 검사 입력의 전체 과제를 input snapshot에서 회수해도, 실제 처분 모집단은 이 공통 함수가 정한다. `task_scope.apply_task_assessments`는 응답의 assessment 항목만 적용하고 최신 결과·계약과 대조하므로 전체 조회표 자체가 새 처분 권한을 만들지 않는다.

**1-C. 그대로 사용하는 소비자와 별도 문제의 경계.**

- `submission._payload_issues`의 기존 `tasks` 조회표는 이제 전체 저장 원문을 받는다. `contract_check_errors`, 철회 대상 조회, 기존 과제 제목 확인, 후보 의존성 순환 검사에 별도 resolver를 넣지 않는다.
- `revisions.submission_errors`의 `revision_targets` 검사는 유지한다. 참고할 수 있는 과제가 늘어났다고 미선언 개정이 허용되지는 않는다.
- `integration.inspect_bundles/apply_bundles/preview_bundles`의 인터페이스를 이 수리에서 바꾸지 않는다. 최초 안의 선택적 원문표 주입은 제거한다. 이 함수는 과제 기록에 `content_sha256`이 없으면 해당 사전 해시 비교를 생략하는 기존 동작이며, 원래의 catalog 거부 원인이 아니다. 중앙 적용의 `previous_hashes`·실제 영향·현재성 대조는 그대로 수행한다. 파일 해시를 의미 해시로 대신 넣지 않는다.
- 2번의 `active` 철회 상태 불일치는 독립된 장벽이다. 1번만 수정한 상태에서 그 철회까지 해결됐다고 보고하지 않는다.

**1-D. 실제 생성 입력을 통한 검증 사례.**

공통 fixture에 `TK-ready`, `TK-returned`, `TK-completed`, `TK-waiting` 네 과제를 둔다. 마지막 과제는 결과가 없고 실제 대기 조건이 있어 ready에도 returned에도 속하지 않게 만든다. 모델의 계획 입력은 앞의 두 과제만 직접 비교하고, catalog와 검사 입력은 네 과제를 포함해야 한다.

| 사례 | 정확한 기대 |
|---|---|
| 후보가 완료된 `TK-completed`의 정확한 판본·경계를 인용 | 자기점검 통과. 같은 선언의 틀린 revision은 거부 |
| 모델에 ready 하나·returned 하나를 지급 | `dispositions`는 ready 하나, `task_assessments`는 returned 하나를 정확히 요구 |
| 완료·대기 과제를 dispositions 또는 assessments에 추가 | 전건 검사에서 거부 |
| 비교 집합 밖의 과제를 parallel_task_ids에 추가 | 기존과 같이 거부 |
| `TK-waiting`의 적격 철회 | 참조 부재 오류가 사라짐. 보호 의무와 중앙 현재성 검사는 계속 적용 |
| 결과 파일에 독자용 local_path가 추가됨 | 검사 입력의 results는 원래 runtime 기록과 같고 기존 assessment 해시 대조가 유지됨 |
| 미선언 기존 계약 개정·의존성 순환·보호 과제 철회 | 기존 권한·순환·보호 검사가 거부 |
| 같은 fixture의 로컬 검사·preview·조기 제출·native final | 공유 구조 검사의 결론이 일치. 수신 시점 변경은 중앙 현재성 검사에서 별도 거부 |

`test_redesign_SURFACE.py`, `test_contract_checks.py`, `test_submission_tools.py`, `test_submission_boundaries.py`, `test_task_scope.py`에 관련 사례를 연결한다. 핵심 fixture는 반드시 `prepare_role_input`으로 생성한 `input/submission/context.json`을 사용한다.

**1-E. 비용과 완료 범위.**

새 전체 과제 필드와 원문 역변환·지연 조회 계층은 추가하지 않는다. 기존 검사 파일의 과제 수가 일부에서 전체로 늘어나는 만큼 직렬화·보존·검사 비용은 증가한다. 프롬프트의 직접 비교 본문은 유지하되 참조 목록의 변화까지 포함해 실제 바이트를 확인한다. 이 비용을 0이라고 보거나 성능 개선이라고 주장하지 않는다. 구현 후 기존 두 소비자의 역할 구별과 위 회귀 사례가 통과하면 1번 수리를 완료로 판정한다.

**2. 미시작 active 과제의 철회 조건을 공통화한다 — 구현 명세**

변경 파일은 `task_scope.py`, `submission.py`와 관련 테스트다. 1번에서 공급한 전체 과제 저장 원문을 사용한다. 실행기의 `active`는 선택된 상태도 포함하므로 상태와 실제 미종료 실행을 별도로 검사한다.

`validate_withdrawal_scope(task, snapshot_task, *, proposed_assessment=None)`의 시그니처는 유지한다. 기존 보호 의무 검사와 `if not task.get('results'): return`보다 앞에 다음 코드를 넣는다.

```python
if task.get('status') not in _WITHDRAWABLE_STATES:
    raise ValueError('withdrawal requires an unfinished task')
if proposed_assessment is not None and proposed_assessment.get('decision') != 'incomplete':
    raise ValueError('withdrawal cannot follow a terminal task assessment')
```

`_WITHDRAWABLE_STATES = {'planned', 'waiting', 'active'}`는 이 모듈이 소유한다. completed 과제에 proposed incomplete를 붙여 다시 여는 것은 첫 검사에서 거부한다. 결과가 있으면 기존 함수의 계약·결과 해시와 incomplete 의무 처분 검사를 그대로 수행한다. 결과가 없는 과제는 이 공통 검사 뒤 반환할 수 있다.

`submission._payload_issues`의 `task_dispositions` 검사에서는 약 817~819행의 `incomplete → needs_revision` 변환과 독자적인 허용 상태 목록을 삭제한다. 기존 공통 함수 호출 뒤 아래 조건을 추가한다. `ongoing_work`가 없는 과거/독립 검사 문맥에서는 이 사전 관측만 생략하고 중앙 검사를 유지한다.

```python
live_states = {'queued', 'starting', 'running', 'stopping'}
live = [row for row in context.get('ongoing_work', [])
        if row.get('target') == entry['task_id']
        and row.get('status') in live_states
        and row.get('execution_id') != context.get('execution_id')]
require(not live, 'task has another live execution')
```

`ongoing_work`에는 끝난 실패 실행을 가리키는 대기 요청도 있으므로 `status != 'ended'`로 검사하지 않는다. 실제 미종료 상태가 명시된 행만 해당한다. 같은 응답에서 선택·개정하면서 철회하는 금지 조건도 유지한다.

중앙 `_validate`는 다음 시그니처로 바꾼다.

```python
def _validate(task, snapshot_task, runtime, task_id, instance=None, *, actor_execution_id):
```

`apply_task_dispositions`의 유일한 호출에서 `actor_execution_id=execution_id`를 전달한다. `_validate`의 중복 상태 검사는 공통 함수로 옮기고, 생성 계보·현재 assessment·snapshot 계약 검사를 유지한다. 미종료 실행 검사에서는 **이 처분을 실제로 적용 중인 실행 ID 하나**만 제외한다. 제외 전 `runtime['executions'][actor_execution_id]['role']`이 `research_preparation` 또는 `research_plan`인지 확인한다. 다른 준비·계획·작업·계약 검토 실행은 종전처럼 모두 차단한다.

이 예외는 구체화 중 발견한 필요한 연결 수정이다. 후보 준비가 자기 `action.target` 과제의 철회를 결정하면, 편입 중인 자기 실행은 아직 `stopping`일 수 있다. 현재 코드는 그 판단 실행 자체 때문에 철회를 거부할 수 있다. ID와 역할을 확인한 자기 실행 하나의 제외가 이 충돌을 해소한다. 작업 실행을 일반적으로 제외하는 규칙은 만들지 않는다.

적용 순서는 기존대로 `주 응답의 task_assessments 적용 → task_dispositions 적용 → queue 처분`이다. 결과가 있는 과제의 현재 incomplete 판정, 원래 계약·결과, 철회 사유·미시작 요청 삭제 이력은 기존 `scope_disposition`에 남긴다. 새 저장 필드는 없다. 후보 상태 검사나 CAS가 실패하면 철회와 queue 삭제를 모두 공개하지 않는다.

| 테스트 ID 접두사 | 구성·행동 | 기대 |
|---|---|---|
| `test_withdraw_active_unstarted` | 선택돼 active이나 작업 실행은 없음 | 검사·편입 성공, 과제 closed, 해당 미시작 요청만 제거 |
| `test_withdraw_authorizing_preparation` | 철회를 제출한 준비 실행만 target에 붙어 stopping | 자기 실행을 이유로 거부하지 않음 |
| `test_withdraw_other_live_execution` | 다른 작업/준비/검토가 queued 또는 running | 사전 및 중앙 거부, 원 상태 유지 |
| `test_withdraw_started_after_input` | 입력에는 미시작, 적용 직전 작업 시작 | 로컬 통과 가능, 중앙 거부, 실행을 강제 종료하지 않음 |
| `test_withdraw_partial_after_assessment` | 같은 응답에 전건 incomplete 판정과 철회 | 판정 이력·남은 의무를 보존해 closed |
| `test_withdraw_protected_or_terminal` | 사용자 필수·학술·이전 의무·completed/closed | 모두 거부 |
| `test_withdraw_with_dependents_and_impact_review` | 의존 과제가 있는 B를 명시 묶음·previous_hashes·impact_set으로 철회 | 중앙의 영향 비교/필요한 독립 영향 검토를 거친 후에만 적용. 의존 과제의 기존 판정을 무효화하고 stale 선택을 실행하지 않음. 중간 실패는 과제/queue를 부분 변경하지 않음 |

**3. 부정·미해결 목표 감사 집단을 다음 계획에 전달한다 — 구현 명세**

감사 집단의 식별자는 현재처럼 `basis`, 자리의 식별자는 `(basis, slot)`이다. 별도 감사 관리 원장을 추가하지 않는다. `governance_engine.py`의 `GovernanceEngineMixin`에 다음 내부 함수 하나를 추가한다.

```python
def _record_goal_audit_followup(self, basis: str, judgments: list[dict]) -> str:
    judgment_ids = sorted(row['id'] for row in judgments)
    for event in self.runtime['events']:
        if (event['kind'] == 'goal_audit_completed'
                and event.get('basis_sha256') == basis
                and event.get('judgment_ids') == judgment_ids):
            return event['id']
    event = self._lifecycle_event(
        'goal_audit_completed', target=self.instance['id'],
        basis_sha256=basis, judgment_ids=judgment_ids,
        outcome='not_established', next_owner='research_plan')
    return event['id']
```

이 함수는 사건을 생성하거나 기존 사건 ID를 돌려준다. 기존 사건이 이미 소비됐으면 `pending_events`에 다시 넣지 않는다. `_lifecycle_event`가 새 사건에만 ID·시각을 부여하고 pending 목록에 넣는다. 사용한 필드는 현행 사건 스키마에 이미 등록돼 있으므로 새 기록군·판본 변경은 없다. `not_established`는 새 수학 판정이 아니라 집단이 목표 보증을 만들지 못했다는 운영 결과다. 각 감사자의 `decision`, `reason`, `scope_complete`는 GJ 원문에 그대로 남는다.

`_apply_governance_goal_audit`의 끝을 아래 순서로 고친다.

1. append 전에 action의 required가 bool이 아닌 양의 int이고 slot도 bool이 아닌 int로 `0 <= slot < required`인지 확인한다. 현행 basis·중복 슬롯·추가 감사 검사도 먼저 수행한다.
2. 기존 행과 새 판정으로 prospective 집단을 만들고 required 일치·slot의 동일 범위·중복 부재를 확인한 뒤 새 판정을 append한다. 유효하지만 일부 슬롯만 있으면 반환한다. `len == required`이고 `slot 집합 == set(range(required))`일 때만 집단을 완결로 처리한다.
3. 기존의 `satisfied` 계산을 그대로 한다. 참이면 기존 신뢰 환경 확인·`apply_goal_assurance`·학술 후속 경로를 탄다. 그 경로의 실패를 부정 감사의 정상 완료로 바꾸지 않는다.
4. `satisfied`가 거짓인 완결 집단에서만 `_record_goal_audit_followup(action['basis'], judgments)`를 호출한다.

마지막 GJ와 사건은 `_apply_bundle_candidate`가 가진 같은 후보 상태에 추가하고, 기존 `integration.apply_bundles → publish`의 **한 CAS**로 공개한다. 이 함수 안에서 `_save`를 따로 호출하지 않는다. 저장 직전 실패면 둘 다 미공개, 저장 후 재처리면 편입 영수증과 사건 검색이 중복을 막는다.

후속 연결은 기존 `_refresh_readiness`가 맡는다. 이 함수는 `research_reconsider_due` 이외의 미소비 사건을 연구 계획에 배정하므로 새 dispatch 경로가 필요 없다. 계획 입력의 `events`에는 이 사건이, 이미 지급하는 `goal_judgments`에는 해당 GJ들이 들어간다. 참조로 축소됐으면 기존 원문 회수 지침을 따른다. 수락된 계획만 `_consume_action_events`에서 사건을 소비한다.

| 상황 | 사건·요청 동작 |
|---|---|
| 두 자리 중 첫 판정만 수락 | 후속 사건 없음 |
| 마지막 판정이 부정/미해결이고 집단 수락 | 사건 하나, 다음 refresh에서 계획 요청 |
| 한 감사 실행이 실패해 GJ가 없음 | 완결 사건 없음, 기존 실패 수리/보류 유지 |
| 집단 전건 satisfied이나 신뢰 확인이 실패 | 정상 완결로 포장하지 않고 기존 제출 실패 처리 |
| 사건 공개 뒤 엔진이 중단 | 재시작 시 pending 사건으로 계획을 준비 |
| 계획 출력 수리·실패 | 사건 미소비, 해당 요청/수리 계보가 소유 |
| 계획 수락 뒤 같은 집단 재확인 | 기존 사건 ID만 반환, 새 계획을 자동 반복 생성하지 않음 |
| 사용자 정지/종결 | 기존 수신·배정 관문 적용, 정지를 해제하지 않음 |

`test_goal_audit_followup_last_slot`, `test_goal_audit_followup_publication_retry`, `test_goal_audit_followup_plan_failure`를 `test_governance_engine.py`에 추가한다. 두 감사와 후속 계획의 실제 편입 경로를 모사 모델로 연결하고, CAS 실패를 주입한 전후 snapshot의 GJ·사건·pending 목록까지 비교한다.

**4. 목표 감사 배정은 미처리 슬롯만 대상으로 한다 — 구현 명세**

배정 조정과 감사 결과 소비는 구별한다. 이 수리는 이미 봉인된 판정을 다시 실행하지 않게 하며, 판정을 현재 해결 보증으로 채택하는 일은 기존 3·5번 경로에 남긴다.

`GovernanceEngineMixin`에 `_ensure_goal_audit_requests(self, basis: str, request_execution_id: str) -> dict`를 추가한다. `engine._apply_plan`의 `for slot in range(...): _enqueue(...)`를 이 함수 한 번의 호출로 교체한다. 함수는 호출 시 `_goal_basis_key() == basis`를 확인하고, 불일치면 `ValueError('goal audit request basis changed')`로 해당 계획의 편입을 거부한다.

`required = config['goal_auditors']`이고 각 slot은 `0..required-1`이다. **GJ에는 role 필드가 없으므로** GJ 목록에서는 basis·slot·required로 찾고, 그 execution_id의 실행이 goal_audit인지 대조한다. queue·waiting·execution의 action에서는 role·basis·slot·required를 대조한다. 판정과 action에 같은 조회 조건을 무작정 적용하지 않는다. 다음 순서로 처분한다.

| 먼저 성립한 조건 | 반환 행의 state | 실행 효과 |
|---|---|---|
| 같은 basis·slot의 GJ 존재, current가 false가 아님 | `sealed` | judgment_id만 기록, 새 요청 없음 |
| GJ 존재, current=false | `sealed_unusable` | 새 요청 없음, next_owner=research_plan·무효 이유 기록. 재승인하지 않음 |
| 해당 슬롯의 미종료 실행 존재 | `running` | execution_id 기록, 새 요청 없음 |
| 해당 슬롯의 queue action 존재 | `queued` | action_id 기록, 새 요청 없음 |
| 해당 슬롯의 waiting action 존재 | `waiting` | action_id·기존 kind/next_owner 기록, 자동 재시도하지 않음 |
| 위 조건 없음 | `queued_new` | AC ID를 한 번 만들고 기존 `_enqueue`로 요청 |

새 요청은 다음 기존 필드만 사용한다.

```python
action_id = new_id('AC')
self._enqueue('goal_audit', id=action_id, basis=basis, slot=slot,
              required=required, requested_by=request_execution_id,
              reason='Complete the unsealed slot of the requested goal audit')
```

반환 형태는 `{'basis': basis, 'required': required, 'slots': [처분 행...]}`다. 각 행에는 `slot`, `state`와 위 표에 해당하는 실제 ID만 쓴다. 이를 `runtime.history`에 `kind='goal_audit_request'`, `execution_id=request_execution_id`와 함께 한 번 append한다. 이 이력과 새 AC들은 계획 응답의 같은 CAS로 보존한다. 이력의 state는 슬롯 관리 원장이 아니라 그 계획을 적용했을 때 한 행동의 기록이다.

`sealed_unusable`는 같은 basis의 옛 판정을 덮어쓸 권한을 만들지 않는다. 이미 계획에 제공된 무효 판정과 원인을 근거로 다음 연구/권한 조치를 정해야 한다. 새 입력이나 실제 전제 변화로 basis가 바뀌면 새 집단을 정상 배정한다. 임의 nonce를 basis에 붙여 새 감사 몫을 얻는 방식은 금지한다.

**원 판정의 저장 후 마무리와 중복 요청을 먼저 구별한다.** GJ가 저장됐어도 그 생산 실행의 output_accepted 정산이 아직 저장되지 않았을 수 있다. 이 상태에서 원 queue·publication wait를 없애면 수리 자체가 복구 경로를 끊는다.

`GovernanceEngineMixin`에 `_committed_goal_audit(self, execution_id: str) -> dict | None`을 둔다. 해당 EX가 goal_audit이고, GJ의 execution_id와 그 EX의 action basis·slot·required가 일치하며, `runtime.integrations`에 같은 execution_id와 `output` member를 가진 영수증이 있을 때 그 GJ를 반환한다. GJ만 있고 생산 실행·편입 영수증이 없거나 서로 충돌하면 None으로 정상 취급하지 않고 상태 오류로 남긴다. 이 함수는 판정의 수학적 현재성을 승인하지 않고 **이미 공개된 원 제출의 정체성**만 확인한다.

`engine._recover_disappeared`에는 다음 두 연결을 추가한다. 별도의 모델 재실행 경로를 만들지 않는다.

- 시작 시 이미 ended지만 output_accepted가 아닌 EX 중 위 결박과 기존 봉인 제출이 있고 local_termination=confirmed인 건을 `waiting_actions[action.id]`의 `submission_publication`으로 연결한다. EX·action ID는 원 것을 유지하며 이전 wait가 바뀌면 그 원문을 history에 보존한다. 봉인본이 손상된 건은 기존 submission_failure 경로에 남긴다.
- 미종료 EX를 대조하는 기존 루프에서는 실제 로컬 종료 확인 **뒤**, workspace를 다시 수집해 result_ref를 덮기 **전에** 위 결박을 확인한다. 이미 편입된 원 제출이면 기존 종료·예약 정산을 마친 후 같은 submission_publication 대기로 연결하고, 기존 result_ref·input_bundle·submission_intent를 보존한다. 종료가 확인되지 않으면 여전히 정산·후속 적용을 보류한다.

복구 후 기존 `_retry_submission_publications`가 `preserved=True`로 같은 EX의 봉인본을 소비한다. `integration.apply_bundles`는 같은 payload의 영수증을 `already_accepted`로 반환하고 `_receive_submission`은 실행 정산을 마친다. 새 GJ·모델 호출·감사 사건은 만들지 않는다. 원 제출의 마무리 실패는 중복 요청이라고 삭제하지 않는다.

**실제 중복의 정리.** `_retire_sealed_goal_audit_requests(self) -> bool`은 `_refresh_readiness`의 active 경로에서 호출하되, 아래 보호 조건을 먼저 적용한다.

- 미종료 실행 또는 미정산 예약이 붙은 action은 제거하지 않는다.
- GJ를 만든 원 EX의 action ID이며 그 EX의 제출 마무리가 끝나지 않은 경우는 제거하지 않는다. 같은 EX의 publication/impact/submission_failure 대기는 자기 소유 경로에 남긴다.
- 이미 finished인 활동은 갱신하지 않는다. 같은 활동에 다른 queue·waiting·미종료 실행이 있으면 활동 전체를 닫지 않는다.

그 뒤 다음만 처리한다.

1. GJ로 이미 봉인된 `(basis, slot)`을 가리키는 queue·waiting action을 찾는다. 해당 action ID의 미종료 실행이 있으면 건드리지 않는다.
2. 미시작 요청과 같은 ID의 대기 항목을 제거한다. `history`에는 `kind='goal_audit_request_superseded'`, 원 action, 제거한 waiting 항목, 해당 `judgment_id`를 보존한다. GJ의 current=false 여부와 관계없이 ‘이미 봉인돼 같은 자리에 다시 제출할 수 없음’ 때문에 제거한다.
3. 그 action의 소유 활동에 이 슬롯 이외의 미해소 의무가 없는 경우에만 `activities.finish_activity`로 기술적 정리를 한다. assigned EX들의 action이 모두 같은 goal_audit/basis/slot인지 확인하고, unresolved/obligations에 다른 action_id·execution_id 또는 소유가 불명확한 항목이 있으면 활동 정리를 생략한다. `result_refs`는 기존 값을 유지하고 실행 result_ref와 해당 GJ ID를 중복 없이 더한다. 기존 unresolved·followups를 지우지 않고 superseded_request 후속을 추가한다. GJ가 current=false이면 그 무효 이유도 unresolved에 추가한다. 과거 실패 실행을 output_accepted로 바꾸거나 활동의 다른 미해소를 완료로 간주하지 않는다.
4. 제거가 있었으면 True를 반환한다. 자체 `_save` 없이 refresh의 기존 저장 경계에서 공개한다. 과거 실행의 outcome·종료 시각·실패 원문은 바꾸지 않는다.

`_obsolete_action_reason(self, action, *, execution_id=None)`에 goal_audit의 봉인 슬롯 검사를 추가한다. `_call_steps`에서 실행 전 호출은 execution_id=None이고, 모델 반환 뒤의 두 호출에는 실제 execution_id를 전달한다. 봉인 GJ의 생산자가 그 execution_id와 같으면 자신의 이미 공개된 결과이므로 obsolete가 아니다. 다른 EX의 늦은 결과는 보존만 한다. 실행 전 원 생산자의 미완료 제출은 위 publication 경로로 보내고 새 모델을 시작하지 않는다. 수신자의 중복 슬롯 거부와 역사적 실패 진단은 유지한다.

**5. 목표 감사 이력을 유지하고 현재 해결 집단만 선택한다 — 구현 명세**

핵심 변경은 `academic.apply_goal_assurance` 마지막 대입의 한 필드를 제거하는 것이다. 함수의 인자와 검증 로직은 유지한다.

```python
# 교체 후 마지막 세 문장
result = deepcopy(instance)
result.update(goal_status=decision, goal_assessment_basis=deepcopy(basis))
return result
```

`judgments` 인자는 새 목록으로 덮어쓸 값이 아니라, 이미 보존된 전체 목록에서 이번 basis로 선택한 정확한 집단인지 검증할 값이다. `current != judgments` 대조, 전건 scope_complete·추가 감사·독립 자리·형식 결과 확인을 그대로 둔다. 집단의 순서를 이 수리에서 새로 정렬하지 않는다. 전체 목록과 선택 집단을 혼동해 기존의 정확한 비교가 실패하지 않게 한다.

소비자는 아래 계약으로 고정한다.

| 소비자 | 변경 여부·동작 |
|---|---|
| `academic_engine._solution_basis` | 이미 goal_assessment_basis로 필터하므로 유지 |
| `governance_engine._apply_governance_goal_audit` | action.basis의 집단만 모으는 기존 필터 유지 |
| `lifecycle_engine._invalidate_goal_currentness` | 기존 선택 집단의 현재성·해결 해소 처리 유지. 과거 이력 전건을 매 refresh마다 재평가하지 않음 |
| `state_checks`의 목표 보증 검사 | 선택된 집단의 크기·효력 검사 유지 |
| `task_scope.designated_judgment` | 인용된 GJ의 값·current·과제 결과 연결·근거 현재성에 현재 통치 판본·원자료 대조를 추가 |
| `query_records`, 계획 입력 `goal_judgments` | 전체 목록을 제공. 현재 선택 basis와 과거 판정의 뜻을 문서에 명시 |

원 목록의 행·ID·순서를 유지하므로 저장 계약이나 migration은 필요 없다. 이미 과거 구현이 현재 목록에서 제외한 GJ는 자동 합성·복구하지 않는다. 과거 snapshot에서의 복원은 이 전향적 버그 수정과 별개다.

이력을 남긴 뒤 옛 판정이 잘못 사용되는 것은 **실제 사용하는 경계에서** 막는다. 앞선 안의 `for judgment in judgments` 전건 순회는 제거한다. 이력 보존을 위해 매 scheduler refresh마다 모든 과거 판정의 전제를 재계산할 필요는 없다. 현재 해결에 쓰는 집단의 무효화는 기존 `_invalidate_goal_currentness`가 맡고, 과거 GJ를 전문 판정으로 인용하는 별도 소비자는 아래의 사용 검사를 수행한다. 이력의 current 표시는 저장 당시의 기록이며 사용 시점 검사 자체를 대신하지 않는다고 조회·역할 문서에 명시한다.

`task_scope.designated_judgment`의 goal_audit 분기에는 `planning.governance_revisions(instance)`의 각 필드와 GJ의 같은 필드가 정확히 일치하고, `input_basis.sources_current(judgment.get('source_basis', []), instance)`가 참이라는 조건을 추가한다. 현재성 표시를 갱신하기 전의 호출도 옛 목표·정책·원자료의 판정을 사용할 수 없게 한다. GJ가 전체 목록에 있다는 사실을 과제 완료 의무 충족으로 해석하지 않는다.

`test_goal_judgment_history_preserved_on_success`는 A=부정, B=미해결, C=성공 집단을 가진 실제 저장 fixture를 만든다. C의 보증을 적용한 뒤 현재 query에서 A/B/C의 ID와 원문이 모두 나오고 `_solution_basis`에는 C만 반영되는지 검사한다. 재로드 후 같은 조건을 확인한다. `test_goal_judgment_history_does_not_restore_assurance`에서는 C의 실제 근거를 무효화하고 unsolved가 되며 A/B가 자동으로 해결 근거가 되지 않는지 확인한다. 입력 instance가 함수 호출로 변경되지 않는지도 함께 확인한다. 별도 `test_goal_judgment_history_old_judge_rejected`에서 과거 목표의 satisfied GJ를 보존한 채 인용해도 현행 과제의 goal_audit 의무 근거로 사용할 수 없음을 검사한다.

**7. 공개 상태와 대기 원인을 정리한다 — 구현 명세**

수명주기 값은 늘리지 않는다. 누적 예산 소진과 동시 용량 대기는 action의 `dispatch_wait`로 구별한다. 현행 `record_schemas/domains.py`는 이 필드를 `EVIDENCE` 객체로 허용하므로 아래 구조를 넣기 위해 저장 판본이나 등록 스키마를 바꿀 필요가 없다.

**7-A. 대기 진단은 실제 예약 계산에서 나온다.**

앞선 `_ai_resource_wait(pool, model, resources)` 안은 삭제한다. 최신 설정의 모델별 합계와 action의 고정 프로필이 가리키는 제약 판본은 다를 수 있다. 최신 합계에는 한도가 남아 있어도 옛 프로필의 실제 예약은 누적 한도 때문에 거절될 수 있다. 같은 판단을 scheduler에 다시 구현하지 않는다.

`budget.py`의 `BudgetConflict`에 실패 제약의 기계 좌표만 추가한다. 수식·제약 순서·허용/거부 결과는 바꾸지 않는다.

```python
class BudgetConflict(RuntimeError):
    def __init__(self, message, *, constraint_id=None, constraint_kind=None):
        super().__init__(message)
        self.constraint_id = constraint_id
        self.constraint_kind = constraint_kind
```

기존 세 raise 지점의 메시지는 유지하고 keyword 인자만 추가한다. `_check_concurrency`는 kind=concurrency, `_check_host`는 host, `_check_usage`는 해당 constraint의 kind(cumulative/window)를 전달한다. 모두 constraint_id는 그 함수가 실제 검사한 `constraint['id']`다. 오류 문자열을 파싱해 제약 종류를 추정하지 않는다. 잘못된 입력은 기존 `BudgetInputError`로 남는다.

`GitSessionSlots`에는 ephemeral 속성 `admission_wait: dict | None`을 두고 acquire 시작에 None으로 초기화한다. `admission_reason`은 `(admission_wait or {}).get('kind')`를 반환하는 읽기 property로 유지해 두 상태값을 따로 저장하지 않는다. 기존 provider gate와 BudgetConflict catch에서만 아래 진단을 작성한다.

| 실제 실패 지점 | wait.kind | next_owner |
|---|---|---|
| provider waiting/checking | provider_limit | scheduler |
| cumulative 제약 | budget_exhausted | user |
| concurrency 제약 | capacity | scheduler. 해당 제약의 pool 슬롯 또는 total_slots가 0이면 user |
| host 제약 | host_capacity | operations |
| window 제약 | budget_window | operations. 고정 window의 해제 시각은 추정하지 않음 |
| 제약 좌표가 없는 외부/모사 BudgetConflict | resource_unclassified | operations. 용량 대기라고 단정하지 않음 |

자원 실패 wait에는 `kind`, `budget_kind`, 실제 `model`(기계이면 null), `profile_ref`, `constraint_id`, `constraint_kind`, `reason=str(error)`, `next_owner`를 넣는다. 제약 좌표가 없으면 두 constraint 필드는 null이다. 별도로 limit/used/available을 재계산해 쓰지 않는다. 숫자 상세는 식별된 제약과 예약 원장에서 회수한다. 공급자 실패에는 constraint 두 필드 대신 `provider`와 원장의 `retry_at`을 기존 UTC 표시 함수로 변환해 넣는다. 새로운 retry 시각을 만들지 않는다.

이미 존재하는 `admission_available(profile)`의 detached acquire 구조를 다음 인터페이스로 확장한다.

```python
def admission_check(self, profile, *, current_time=None) -> dict:
    from copy import deepcopy
    from .repository import new_id
    runtime = {
        'executions': {},
        'reservations': deepcopy(self.runtime.get('reservations', {})),
        'provider_waits': deepcopy(self.runtime.get('provider_waits', {})),
    }
    candidate = {'id': new_id('EX'), 'role': profile['role'], 'status': 'queued'}
    slots = GitSessionSlots(runtime, self.instance)
    allowed = slots.acquire(
        candidate['id'], profile['budget_kind'], profile.get('ai', {}).get('model'),
        profile=profile, execution=candidate, current_time=current_time)
    return {'allowed': allowed, 'wait': deepcopy(slots.admission_wait)}

def admission_available(self, profile):
    return self.admission_check(profile)['allowed']
```

기존 `admission_available`의 reservations/provider_waits deepcopy와 임시 candidate 생성 코드를 옮겨, 임시 slots 객체의 acquire bool과 wait를 반환한다. 실제 원장·provider probe_owner·실행·예약은 바뀌지 않는다. 이 read-only 검사는 실제 예약 영수증이 아니다. 이 과정의 예약 원장 복사 비용은 8번의 전체 scheduler 측정에 포함한다. 자원 계산을 세 번 구현하는 대신 한 구현을 호출하지만 그 비용이 0인 것은 아니다.

**7-B. 배정·실제 예약·전체 상태 집계.**

1. `_dispatchable(self, action)`로 시그니처를 좁히고 resources 인자를 제거한다. 유일한 운영 호출인 `_run_parallel`의 인자와 그 직전 전역 resources 계산도 제거한다. 테스트의 인위적인 resources dict 대신 실제 고정 profile/constraint/reservation fixture를 사용한다.
2. 함수 진입에서 이전 dispatch_wait를 제거한다. 기존 생명주기·과제·개정·중복·모델·능력 관문을 통과한 AI는 `profile = self._execution_profile(action)`으로 고정 action 참조의 프로필을 회수하고 `GitSessionSlots(self.runtime, self.instance, observer=True).admission_check(profile)`를 호출한다. 종전의 별도 provider 상태 분기와 모델 합계/누적 합계 분기는 제거한다. 허용이면 True, 거부이면 그 wait를 그대로 action에 기록하고 False다.
3. machine 분기의 호스트 admission도 같은 결과를 사용한다. formal_check/trust_check 간 최대 한 건 제한은 기존 별도 관문으로 유지한다. 실제 기계 예약 실패를 다루는 `engine._register_execution` 역시 고정 문자열 host_capacity 대신 실제 slots.admission_wait를 기록한다.
4. `_call_steps`의 preliminary `used = sum(...)`, `_budget_available(...)` 차단 블록을 삭제한다. 최종 권위 있는 자원 관문은 이미 있는 `_provider_admit → acquire`다. 여기에서 실패하면 기존처럼 새 모델을 시작하지 않고 준비 실행을 종료·정리한다. 같은 ID의 원 queue 항목에도 실제 admission_wait를 복사해, 준비 action 사본에만 사유가 남지 않게 한다. 임의의 전역 status/availability 덮어쓰기를 추가하지 않는다.
5. `_provider_admit`는 거절 시 slots.admission_wait를 그대로 전달한다. 기존 activity_wait 보조 정보는 **provider_limit인 경우에만** 생성한다. 자원 부족에 공급자 재시도 간격을 붙이지 않는다. `_hold_provider_action`의 실제 공급자 실패 처리는 그대로 둔다.
6. 설치 복구의 `scheduled_operator.recovery`도 acquire 실패 응답에 `wait=deepcopy(slots.admission_wait)`를 추가한다. 기존 reason 문자열은 property에서 나온 같은 kind다. 조사용 검사, 기계 배정, AI 배정, 복구가 다른 자원 판정을 하지 않도록 한다.
7. `_budget_available`는 검토 활동의 미래 여러 실행에 대한 기존 총예산 조회에서 계속 사용한다. 이것은 개별 고정 프로필의 실제 예약 허가가 아니며 실제 배정은 위 acquire가 다시 검사한다. 다중 실행을 미리 예약하는 새 기능은 만들지 않는다.
8. 실행 가능한 action도 진행 중 future도 없을 때 `_run_parallel`의 상태 집계를 아래로 바꾼다. 한 action이 막혀도 다른 action 검색을 계속한다. paused·drain·완료 처리의 기존 위치는 유지한다.

```python
capacity_kinds = {'capacity', 'host_capacity'}
only_capacity = bool(self.runtime['queue']) and all(
    action.get('dispatch_wait', {}).get('kind') in capacity_kinds
    for action in self.runtime['queue'])
if self.runtime['status'] != 'paused':
    self.runtime['status'] = 'capacity_waiting' if only_capacity else 'waiting'
```

이유가 없는 queue를 용량 대기라고 추측하지 않는다. budget_exhausted와 capacity가 섞이면 waiting이고 각 action의 이유를 보여 준다. 작업 예산만 소진됐어도 운영 예산의 가능한 요청을 처리할 수 있다. `run --watch`는 waiting에서 종전처럼 제어를 기다릴 수 있으며 새로운 모델 진단을 자동 생성하지 않는다.

**7-C. 설정 변경 뒤 다시 배정되는 경로.**

`governance_engine._configure_candidate`의 끝에서 기존 protected 설정 항목의 값이 바뀌었는지 계산한다. 이 함수에는 이미 protected tuple과 current/candidate가 있다.

```python
resources_changed = any(candidate.get(key) != current.get(key) for key in protected)
if state.get('status') in {'waiting', 'capacity_waiting'} and resources_changed:
    live_action_ids = {row.get('action', {}).get('id')
                       for row in state['executions'].values()
                       if row['status'] != 'ended'}
    for action in state['queue']:
        if (action.get('id') not in live_action_ids
                and action.get('dispatch_wait', {}).get('kind')
                    in {'budget_exhausted', 'capacity', 'host_capacity'}):
            action.pop('dispatch_wait', None)
    if state['queue']:
        state['status'] = 'ready'
```

이 ready는 재평가 요청이며 허가·모델·입력 관문 통과를 뜻하지 않는다. paused/closed/completed는 변경하지 않는다. 같은 설정의 재전송으로 waiting을 깨우지 않는다. 이 변경이 없으면 누적 예산 소진을 waiting으로 정확히 표시한 뒤에도 한도를 늘려 재시작할 연결이 빠질 수 있다.

기존 action이나 과제에 고정된 `profile_ref`는 여기서 삭제·교체하지 않는다. 용량 설정 변경은 새 프로필 판본을 만들 수 있으므로, 옛 프로필이 현행 허용 목록과 맞지 않으면 재평가 결과가 기존 lifecycle/profile 관문의 대기로 바뀔 수 있다. 그 경우 한도 확대만으로 실행됐다고 보고하지 않는다. 과제의 재준비·독립 계약 검토, 필요한 프로필 능력 관측 등 기존 채택 경로를 거친 후에만 배정한다. 이 수리에 자동 프로필 전환 권한을 추가하지 않는다.

`scheduled_operator.engine_start_guard`는 수정하지 않는다. 자원 설정 변경이 공개돼 ready가 되면 기존 경로로 시작을 요청하고, 그대로 waiting이면 기존 공급자·연구 사건 조건만 본다. HOLD·사용자 정지·모델 정책 위반 검사는 유지한다.

**7-D. 조회 계약과 문서의 정확한 변경.**

`reporting.task_status`의 `status`는 저장값 `planned/active/waiting/completed/closed`를 계속 반환한다. 이 함수의 readiness는 `include_scheduling_waits=False` 평가이므로, 이것만으로 해당 과제가 지금 선택 모집단이라고 설명하지 않는다. 다음 변경을 적용한다.

- 함수 시작에서 `pending_assessments = set(task_contracts.returned_task_ids(runtime['tasks']))`를 한 번 계산하고 각 행에 `assessment_pending: identifier in pending_assessments`를 추가한다. 저장 필드가 아닌 snapshot 기반 파생값이다.
- queue의 대기 이유를 모을 때 capacity/provider_limit/budget_exhausted/host_capacity/budget_window/resource_unclassified를 포함한다. 실제 입력 오류 예외를 이 목록의 resource_unclassified로 바꾸지는 않는다.
- `next_owner` 우선순위는 사용자 질문, next_owner=user인 자원 대기, 계약 검토, 실제 dispatch_wait의 next_owner, 첫 queue 역할, None 순서로 한다. host/window의 operations 소유자를 과제 역할로 덮지 않는다.
- `cli._human_status`의 과제 행에 `assessment_pending=true|false`를 출력한다. JSON의 waits 사유와 같은 의미를 쓴다.

작업 대상이 없는 후보 준비·계획의 예산 대기도 조회할 수 있어야 한다. `reporting.py`에 `dispatch_waits(runtime) -> list[dict]`를 추가한다. 현재 queue 중 같은 action ID의 미종료 실행이 없고 dispatch_wait가 있는 행에 대해 `{'action_id','role','target','model_selection','wait'}`를 반환하며, 값은 deepcopy한다. 새 시각이나 대기 이유를 추정하지 않는다. `engine.status`와 `reporting.snapshot_report`에 이 파생 목록을 동일하게 추가한다. 기존 `engine.status['capacity_waiting']`는 기존 행 형태를 유지하되 이 목록 중 wait.kind가 capacity/host_capacity인 것만 담도록 좁힌다. 새로운 이력 저장이나 스키마 변경은 없다.

사람용 출력에서도 target이 과제 목록에 없는 dispatch_wait는 별도 행에 action_id·role·kind·constraint_id(공급자는 provider)·next_owner를 표시한다. task 행에서 이미 보여 준 사유는 반복 출력하지 않는다. status.budget은 현행 설정의 요약이고, 특정 요청의 대기 사유는 그 요청의 고정 profile_ref/constraint_id 기준임을 설명한다. 과거 snapshot 조회에서는 새 admission_check를 실행하지 않고 보존된 사유만 읽는다.

**8. 반복 착수조건 평가의 전체 복사를 줄인다 — 구현 명세**

이번 변경은 `lifecycle_engine._refresh_readiness`의 한 호출부다. 관련 함수의 전체 알고리즘을 캐시하거나 다른 저장/preview 복사까지 줄이는 작업으로 확대하지 않는다.

```python
# 현재
evaluation = task_ready(deepcopy(task), deepcopy(query_instance), deepcopy(self.runtime),
                        action={'role': 'research_work', 'target': task_id,
                                'budget_kind': 'work', 'actor_kind': 'ai'},
                        evaluation_context=evaluation_context)

# 교체안
evaluation = deepcopy(task_ready(task, query_instance, self.runtime,
    action={'role': 'research_work', 'target': task_id,
            'budget_kind': 'work', 'actor_kind': 'ai'},
    evaluation_context=evaluation_context))
```

입력을 빌려 읽고 결과만 소유하도록 바꾼다. 결과 복사는 필요하다. 예를 들어 `task_ready`가 `waits=[task['waiting']]`을 반환하는 분기에서는 결과 내부가 원본과 같은 객체일 수 있고, `_record_readiness`는 반환을 깊게 복사하지 않는다. 결과 deepcopy를 남겨 이 별칭을 끊는다.

읽기 경로로 대조한 소유권은 다음과 같다.

| 경로 | 입력 변경 여부·결과 소유 |
|---|---|
| `validate_task_contract`, `contract_review_current`, `capture_task_basis` | 입력을 검사/해시하고 새 결과를 생성 |
| `planning._records`, `revision_waits`, `questions.user_waits` | 새 조회표·대기 목록 생성. 원본 기록을 갱신하지 않음 |
| `assessment_current`, `assess_research_use`, `authorize` | 현재 기록을 읽어 판단. 효력을 변경하는 적용 함수는 호출하지 않음 |
| `evaluate_condition` | 새 basis/errors/result 생성. artifact 분기는 고정 snapshot의 read_artifact·형식 검사 콜백만 호출 |
| `_evaluation_context_for`의 실제 콜백 | 저장 artifact 읽기와 `_artifact_format_valid`. 제어 inbox를 처리하거나 runtime을 바꾸지 않음 |
| `_record_readiness` | 평가가 반환된 뒤 파생 캐시만 갱신 |

기존 루프는 과제 사이에서 검토 요청과 사건을 추가할 수 있다. 이를 순회 전체의 옛 snapshot으로 동결하지 않는다. 각 `task_ready` 호출 시점의 동일한 현재 상태를 읽는 기존 순서를 유지하고, 그 호출 안에서 엔진 제어 처리를 추가하지 않는다. 기존 `now`와 evaluation_context도 유지한다.

`test_readiness_borrowed_inputs_equivalent`에서 준비된 정상 상태와 권한 만료·필수 원자료 부재·미완료 의존·개정 대기·정지 질문·형식 환경 불일치·조건 오류를 각각 만든다. 고정 시각/동일 artifact reader로 종전의 ‘입력 복사 후 평가’ 결과와 교체안의 결과가 같고, 호출 전후 원 instance/runtime 바이트가 같은지 확인한다. `test_readiness_result_does_not_alias_state`는 반환된 waits의 중첩 필드를 수정해도 원 과제 waiting이 바뀌지 않는지 확인한다.

비용 측정은 T=10인 작은 fixture와 T=100·과제당 이력 10건인 대표 fixture 두 개로 한정한다. 두 호출 방식의 결과를 먼저 대조하고 같은 프로세스·고정 입력에서 각각 3회 측정해 중앙값 경과 시간과 `tracemalloc` 최대 메모리를 기록한다. 여기에 7번의 입장 검사까지 포함한 모델 미호출 scheduler 한 순회의 비용을 따로 기록한다. 성능상 새 우려가 드러나지 않으면 500개 과제와 다수 이력 조합을 전수 측정하지 않는다. 모델·Lean·HTTP는 호출하지 않으며, 고정 속도 비율을 성공 조건으로 삼지 않는다. 제거 대상은 과제 평가의 입력 전체 복사이고 남은 조회·예약 진단 비용까지 사라진다고 주장하지 않는다.

위 새 클래스에는 표의 그룹을 기존 `test_group` 데코레이터로 명시한다. 임시 Git 저장과 엔진 연결은 integration, 순수 함수·저장된 dict의 조회만 하는 것은 unit이다. 8번의 5회 측정은 테스트 성공을 판정하는 assertion과 분리해 로그에 기록한다.

테스트는 실제 입력 생성기와 실제 공유 검사기를 거치는 연결 사례를 우선한다. 모델 산출은 fixture로 공급하고 실제 모델·Lean·scholarly·HTTP·예약 작업을 호출하지 않는 경계를 명시한다. 실행·종료 어댑터까지 확인하는 경우에는 기존 모사/로컬 Job 검사의 보증 범위를 구별한다. 이번 요청에서는 이 검사들도 실행하지 않았다.

예정 실행은 기존 `scripts/run_tests.py`의 `--match`로 위 클래스를 선택하고 결과 디렉터리에 원 로그·선택 범위·통과/실패/미실행을 보존하는 방식이다. 아래는 2~8번의 새 클래스를 선택하는 명령이며 아직 실행하지 않았다. 1번의 실제 생성 입력 연결 검사는 A 묶음에서 기존 표에 지정한 파일에 추가해 함께 실행한다.

```powershell

  --match '*.GoalAuditFlowRepairTests.*' `
  --match '*.GoalAuditHistoryRepairTests.*' `
  --match '*.InitialPlanContractRepairTests.*' `
  --match '*.DispatchResourceRepairTests.*' `
  --match '*.DispatchWaitReportingRepairTests.*' `
  --match '*.DispatchWaitOperatorRepairTests.*' `
  --match '*.ReadinessCopyRepairTests.*' `
```

관련 사례가 통과한 뒤 기존 인접 회귀 검사를 수행한다. 새 실패나 미해결 우려가 없으면 같은 검사를 반복하지 않는다. 기록/필드 스키마가 바뀌는 항목은 현재 판본 5의 기존 snapshot 읽기와 재시작을 확인하고, 과거에 없던 확인·권한을 만들어 넣지 않는다.

최종 완료 조건은 다음과 같다.

- 제공한 catalog 원문을 정상적으로 참조하면서 선택·완료 판정의 모집단은 정확히 유지된다.
- 미시작 과제의 철회는 통과하고, 실제 실행 중·보호 의무·낡은 입력의 철회는 거부된다.
- 부정·미해결 감사는 계획으로 이어지고, 같은 봉인 집단을 재요청해도 모델 실행·사건·수리 루프가 늘지 않는다.
- 성공 뒤에도 이전 감사 기록을 현재 snapshot에서 조회할 수 있고, 현재 해결 보증에는 선택된 집단만 쓰인다.
- 초기화·상태 문서와 실제 공개 반환값이 일치하며 누적 예산과 동시 용량 대기를 구별한다.
- 비용 개선 전후의 의미 판정과 입력 불변성이 같고, 감소한 복사 비용을 측정 근거로 설명할 수 있다.
- 실행한 검사·미실행 범위·실제 변경 파일을 결과 보고에 남긴다. 그래프 갱신은 별도의 명시적 요청이 있을 때 수행한다.
