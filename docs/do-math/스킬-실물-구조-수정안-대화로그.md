# 스킬-실물-구조 수정안 — 대화 로그

`스킬-실물-구조-수정안.md`의 결정들을 확정한 대화의 기록이다. 사용자와 assistant의 발화 문면만 싣고, 도구 호출·도구 결과·시스템 주입문·스킬 전개문은 제외했다. 스킬 호출로 전달된 발화는 지시문 본문만 실었고, 첫 발화는 두 스킬 호출에 중복 수록된 같은 지시문을 한 번만 실은 것이다.

## 사용자

@docs/do-math/통합-설계.md 에는 아직 구현이 되지 않은 do-math 스킬의 설계도면이 담겨 있어. 나는 이 설계도면에 한 가지 아이디어를 적용하는 것을 검토해보고 싶어. 우선은 해당 설계도면을 읽고 @docs/wayfinder/pvsnp-재설계/컨텍스트.md 와 @CONTEXT.md 를 참고하여 그 내용, 그것이 가리키는 대상, 그 철학, 그 핵심 요소들, 그것의 실제 미래 구현체가 정확히 어떻게 구체적으로 작동할지에 대한 원리 추측 등을 포함해서, 적혀 있는 것을 적혀 있는 그대로, 중립적이고 기계적으로 심도 있게 이해해줘. 수정안, 검토-20260831과 기억은 읽지 말아줘. 그리고 위 문서들로부터 구축한 이해를 바탕으로 다음 화두를 나와 같이 검토해줘: 이 설계도면에는 do-math가 어떠한 스킬이어야 하는지는 상세하게 담겨 있어. 그런데 그 스킬 디렉토리 구조가 정확히 어떻게 구성되어야 하는지, 그 스킬의 진입점은 어떻게 될 것이고 서로 다른 역할들은 해당 스킬의 절차들의 어떤 부분집합을 어떤 방식으로 읽어야 하는지 등에 대한 검토가 부재해 있어. 즉, 그 스킬이 실제로 그 사용자들에 의해 정확히 어떤 방식으로 활용되어야 하는지, 그러니까 그 효과가 아니라 말 그대로 그걸 어떻게 읽어야 그 안에 담긴 내용을 각 역할의 세션들이 올바르게 파악할 수 있을 것이며 그러한 읽기를 어떠한 디렉토리 구조로 지원할 것인지에 대한 고려가 없어. 이 설계도면에 그러한 요소를 채워넣어 차후 통합-설계를 바탕으로 실제로 구현될 do-math 스킬에 그러한 고려사항이 잘 반영되어 있으면 좋겠어. 또한 설계도면에 담긴 설계를 '전거' 중심으로 하고 싶어. 그 설계도면을 바탕으로 구현될 do-math 스킬이, 전거 디렉토리 내에 서로 다른 개념들을 각자 다른 .md 문서로 정의한 다음 스킬 나머지에서는 그러한 개념들을 각자 반복해서 정의하는 대신 정해진 형식에 따라 참조만 하고 그러면 스크립트가 단 번에 전거 디렉토리에서 해당하는 개념을 가져와 내용물을 렌더링하는 방식을 택하도록 통합-설계에 설계하는거지. @.agents/skills/do-dag/전거\ 참고. 다만 do-dag의 전거와 아주 같은 방식은 아니야. do-dag의 전거는 같은 내용이 여러 곳에 흩뿌려져 있어 하나를 수정하면 다른 것들도 모두 수정해야 하기에 내부의 정합성을 유지하며 내부 절차를 수정하는 것이 매우 어려웠어. 그래서 이미 작성된 절차를 바탕으로 겹치는 부분들을 전거에 모았는데. 그 목표는 같다고 해도 do-dag 처럼 탑다운 방식이 아니라 아예 전거를 먼저 구축하고 그를 바탕으로 나머지 스킬 절차를 작성하는 바텀업 방식을 택하고 싶어. 또한 요지 전문 구별 없이 하고 싶고, 하나의 파일이 하나의 개념에 해당하게 하고 싶어. 참고로, 명확히 말하는데, 이 스킬은 아직 구현되지 않았어. 통합-설계는 차후 스킬의 구현에 사용될 설계도면이야.

## 1. 설계도면의 이해

**지위와 대상.** 이 문서는 아직 구현되지 않은 보편 수학 연구 스킬 `do-math`의 구현 정본이다. 루트 `CONTEXT.md`가 보편 도메인 용어(K·F·U, 작업 씨앗, 실행 껍질, 관찰 의무 등)의 정의를 소유하고, 이 문서는 그 용어의 기계 상태·전이·권한·저장·검증을 소유한다. 구현자는 두 문서와 지정된 스키마·도구 계약을 함께 적용하며, 구현 중에 새 연구 방법·상태·권한·예외를 만들 수 없다. 즉 이 문서는 "구현자 선택지가 남지 않은 닫힌 계약"을 지향하고, §27.13이 그것을 완료 조건으로 명시한다.

**철학.** 목적문이 설계 전체를 지배한다: 고성능 AI가 충분한 맥락과 고품질 도구를 받아 넓은 재량으로 연구하고, 실제 결과를 다음 판단에 반복 환류한다. 기계 절차는 AI 판단을 대체하지 않고 입력 완전성·상태 무결성·형식 검사·동시성·자원 상한·권한 경계만 재현 가능하게 지킨다. 이 원리가 도처에서 반복된다 — 포트폴리오 선택은 점수 규칙이 아니라 별도 고성능 세션의 재량이고(고려 의무만 있고 고정 비율·순서 규칙이 없다), 씨앗 생성 회차는 생성량 상한·큐레이션 의무가 없으며, 이의 루프는 회차 상한·다수결이 없다. 반대로 기계가 맡는 것은 전부 결정론이다: 발생 조건 AST(닫힌 10연산자), 관찰 조건(닫힌 8연산자), 착수 가능성 식, 정규 직렬화와 닫힌 스키마, 예상 OID 기반 조건부 ref 갱신. 인식론의 축은 둘이다: Lean 커널은 타입·항에 표현된 형식 관계만 신뢰 시대에 상대적으로 보장하고, "사람이 설명하려던 수학적 의미가 커널이 승인한 Lean 표현의 정확한 의미와 같은가"는 해설–형식 동일성 인증 사슬(검토자–이의–심사단 3인 루프)이 별도로 판정한다.

**기계 구조.** 지속·실행 상태 전부가 Git 하나에 산다. 인스턴스 공용 브랜치 + runtime ref 8종(controller·supervisor·requests·runs·monitor·certification·operations·outputs) + 불변 보관 ref. 모든 동시성·권한이 "예상 OID를 검사하는 조건부 ref 갱신" 한 가지 원리로 닫힌다. 공용 트리의 지식층은 7종 지식 기록(F 객체·F 종류·관계·관계 종류·자료근거·기억·맥락)을 OKF v0.2 부분집합 프로필의 개념 문서(정규 YAML frontmatter + 자유 본문)로 저장하고, `id-index.json`·`index.md`는 편입마다 결정론 재생성하는 파생 보기다. 실행층은 Windows Job Object 격리, 상주 감독기(PT1S poll), 작업자별 감시기(watch), 실행 제어 5값과 관찰 의무–자기 점검–운영 점검–처분 심사–전례/상신의 단계적 권한 사다리다. 종결은 임시 편입 브랜치에서 전건 재검증한 뒤 terminal 상태 커밋과 공용 머리 갱신·보관 ref 생성·run/monitor ref 삭제를 하나의 `update-ref --stdin` 트랜잭션으로 적용한다.

**미래 구현체의 작동 추측.** 스킬 실물은 `.agents/skills/do-math/` 아래 스키마 묶음(§3.2가 유일하게 경로를 명시)과 판본화된 `do-math` CLI 약 28종으로 구성될 것이다. 사람이 메인 세션을 열면 메인이 `do-math resume`로 상태를 재구성하고 PT5M heartbeat마다 §9.3의 11단계를 돈다. 하위 AI 세션은 request ref로 파견되어 Job Object 안에서 실행되고, 입력은 도구(`portfolio-pack`·`role-pack`·`identity-pack`)가 조립한 packet으로 받으며, 출력은 자기 output ref에 봉인한다. 인스턴스의 `do_math_contract`가 정확한 do-math 구현 커밋, 스키마 묶음·레지스트리 해시, 도구 manifest 묶음 해시, 선택 계약·씨앗 계약의 판본·해시, OKF 스펙 해시를 고정하므로, 스킬 실물의 판본 결박 장치는 이미 설계에 존재한다. 이 그림에서 "스킬을 읽는 주체"는 세 부류로 갈린다: 메인 세션(자기 운전 절차를 직접 적재해야 함), 연구 작업자(저장소 전체 worktree를 가짐), 그 외 AI 역할(packet에 동봉된 계약 전문만 받음 — 세션이 스킬 디렉토리를 탐색하지 않음).

## 2. 화두 전제의 검증

지적한 공백은 실재하고, 실측으로 확인했다. 설계도면 전체에서 "전거"는 0회, "스킬"은 2회(§0의 자기 서술, §28의 이슈 제목)만 나타난다. 설계가 스킬 실물에 대해 고정하는 것은 네 가지뿐이다.

- §3.2: 스키마 경로 `.agents/skills/do-math/schemas/…`
- §24: CLI 이름·stdin/stdout 계약·exit code·`--describe`
- §6.1: 선택 계약과 씨앗 계약이 저장소 상대 경로·판본·해시를 가진 파일로 존재하고, §7.7·§10.2가 이를 해당 세션 입력에 전문 동봉
- §29: 문서의 레지스트리 표는 손 정본이 아니며 `contract-check`가 재생성해 대조

고정하지 않는 것: 스킬 디렉토리의 전체 구조, 진입점(SKILL.md)의 존재와 내용, 메인 세션이 자기 절차를 적재하는 방식, 연구 작업자가 저작 관례(§4.2.1)·자기 점검(§14.6)·종결 준비(§18.3)·제안 작성(§19.1–19.2)을 어떤 문서로 받는지, §19.5의 "검토 계약"의 소재와 판본 결박(선택·씨앗 계약과 달리 `do_math_contract`에 없다), 운영 점검자·처분 심사자·전례 판정자의 절차 문서, 그리고 역할→읽을 문서의 대응표(§9.1의 모델·노력 표 같은 단독 소유 표가 없다).

한 가지 유리한 사실도 확인했다. 설계 내부 규율이 이미 전거의 철학을 손으로 실천하고 있다 — §6.1 "다른 절은 이 필드를 참조하고 구성 목록을 다시 쓰지 않는다", §9.1 "다른 절은 역할 이름만 참조하고 모델 리터럴을 반복하지 않는다", §29 "이 표를 손으로 별도 정본으로 유지하지 않는다". 제안하신 전거는 이 "사실 하나에 소유자 하나, 나머지는 참조" 규율을 스킬 산문 전반에 도구로 기계화하는 것이므로, 설계의 기존 철학과 충돌하지 않고 오히려 그 연장선에 있다.

## 3. do-dag 전거의 실물과 확정된 차이

실물 메커니즘: `전거/` 등록소의 파일 하나에 여러 항목이 살고(【ID】 헤딩 + `요지:` 줄 + 선택적 `기계값:` 줄 + 본문), 소비 자리는 세 형태(인라인 【ID】→요지 치환, ```전거 ID``` 블록→요지+본문 전사, 파이썬 생성 블록→기계값)로 인용한다. `dag_facts.py --render`가 소비 자리에 내용을 전사해 커밋하고 `--check`가 어긋남을 잡는다. 런타임 적재가 없으므로 읽는 세션은 렌더된 사본이 담긴 파일을 그냥 읽는다.

확정된 차이로 받은 것: ① 탑다운(절차 먼저, 겹침을 사후 수집)이 아니라 바텀업(전거를 먼저 구축하고 그 위에 절차 저작), ② 요지/전문 구별 폐지, ③ 1파일 = 1개념.

내 독해 하나를 명시한다: 렌더 방식 자체 — 정본은 전거에 있고, 소비 파일에는 스크립트가 전사한 사본이 커밋되며, 검사가 어긋남을 막는다 — 는 유지된다고 읽었다("정해진 형식에 따라 참조만 하고 그러면 스크립트가 단 번에 … 렌더링"). 이 독해가 맞다면 중요한 귀결이 있다: **역할이 읽는 문서가 렌더로 자기충족이 된다.** 각 역할 문서는 저작 시점엔 참조의 나열이지만 렌더 뒤엔 필요한 개념 전문을 물리적으로 담으므로, packet 동봉이든 직접 읽기든 "한 파일을 읽으면 끝"이 된다. 이는 화두의 역할별 읽기 문제와 정확히 맞물린다. 이 독해가 틀렸다면 바로잡아 달라.

## 4. 검토 지도

grilling 절차에 따라, 결과를 바꾸는 결정을 선행 관계 순으로 하나씩 묻는다. 전체 지도는 다음과 같고, 답에 따라 순서와 가지가 바뀔 수 있다.

1. **전거의 외연** — 스킬 실물에서 '개념 하나'의 단위가 어디까지인가. 이후 모든 구조를 좌우하는 사용자 비전이다.
2. **참조 형식** — 전문 전사형 하나로 가는가, 이름만 딛는 언급형이 병존하는가. ①에 종속되며, 확정된 목표에서 추천을 도출할 수 있다.
3. **기계 정본과의 경계** — 스키마의 닫힌 어휘, `CONTEXT.md`의 보편 용어, 통합-설계 자신과 전거 사이의 소유권·이중 정본 방지. 추천을 준비하겠다.

1. **스키마 파일** — 설계는 모든 기계 문서에 JSON Schema를 두게 한다(`.agents/skills/do-math/schemas/…`). 실행 상태 스키마에는 "control 필드의 허용값은 이 다섯 개"가 기계 형식으로 적혀 있고, **도구들이 실제로 이 파일로 검사한다.** 여섯 번째 값을 쓴 상태 파일은 스키마 검사에서 거부된다. 이래서 스키마가 "기계 정본"이다 — 실행 시 실제로 강제되는 쪽.
2. **GLOSSARY.md** — 역할 세션이 읽는 산문. "실행 제어" 항목은 당연히 이 다섯 값과 각각의 의미를 설명할 것이다.

**위험이 뭔가.** 나중에 누가 스키마에 값을 하나 추가하거나 이름을 바꾸면서 GLOSSARY 갱신을 잊으면(또는 그 반대), **역할이 읽는 규칙과 기계가 강제하는 규칙이 조용히 갈라진다.** 세션은 "다섯 값이 있다"고 읽고 행동하는데 기계는 여섯 값을 받는 상태가 된다. 이 어긋남은 어떤 편집 시점에도 오류를 내지 않는다 — 그래서 조용한 병이다.

**"대조"가 뭔가.** GLOSSARY에 이런 값 목록을 실을 때 자유 산문이 아니라 기계가 알아볼 수 있는 고정 표기로 싣자는 것이다. 예를 들면:

````markdown
## 실행 제어

작업 실행에 허용되는 행동의 범위를 정하는 상태값. …산문 설명…

```어휘 do-math/execution-state/1 control
preparing | authorized | pause_required | closing | revoked
```
````

설계가 이미 계획한 검사 도구 `do-math contract-check`가 GLOSSARY를 훑어 이렇게 표기된 블록을 찾고, 블록이 단 스키마 ID(`do-math/execution-state/1`)의 실제 스키마 파일을 열어 허용값을 꺼내 **바이트 단위로 비교**한다. 다르면 검사가 실패하고, 구현자는 어느 한쪽을 고칠 때까지 진행하지 못한다. 즉 "산문과 기계가 일치하기를 바란다"를 "일치하지 않으면 실패한다"로 바꾸는 장치다.

이건 새 발명이 아니라 설계도면 자신의 기존 패턴이다. §29의 스키마 목록 표에 대해 설계는 이렇게 말한다: 이 표는 손으로 유지하는 정본이 아니고, `contract-check`가 실제 스키마 파일들에서 표를 재생성해 문서와 다르면 구현을 실패시킨다. 조항 2는 같은 원리를 용어집의 닫힌 값 목록에 연장하는 것뿐이다. 비용은 GLOSSARY 저작 시 값 목록에 위 표기를 쓰는 것과, 이미 만들 contract-check에 검사 항목 하나가 늘어나는 것이다.

**확정된 사용자 결정**:

- ① **개념층 외연**: 정의 중심 — 객체·상태·판정 어휘·불변식·용어의 정의, 그리고 반복 활용되는 절차의 정의. 한 자리에서만 수행되는 순서는 절차 문서가 소유.
- ② **GLOSSARY.md 채택**: 전거 디렉토리·렌더 기구 대신 용어집 한 파일. 짧은 정의는 GLOSSARY.md가 소유하고, 길이가 나가는 반복 절차 정의는 `references/` 별도 문서로 분리. 바텀업 저작 순서(용어집 먼저 → 그 위에 절차 문서)는 유지.
- ③ **자기충족과 링크**: GLOSSARY는 `CONTEXT.md`의 보편 개념을 포함하는 자기충족 용어집. 기계 대조는 하지 않고, 밖에 정본이 있는 사실(스키마의 닫힌 어휘, `CONTEXT.md`의 보편 용어)에는 양방향 경로 링크를 배치해 한쪽을 고치는 주체가 반대쪽을 함께 고친다.
- ④ **역할 읽기 계약**: 역할마다 진입 문서 하나(`계약/`), 역할→읽기 목록 대응표는 SKILL.md 단독 소유, 전달은 세 경로(파견 역할은 packet 동봉과 입력 manifest 해시 결박 · 작업자는 worktree 직접 읽기와 점유 직전 판본 일치 검사 · 메인은 설치 스킬 직접 읽기와 §23.1 호환성 검사), `do_math_contract`에 스킬 문서 묶음 해시를 추가하고 선택·씨앗 계약 개별 핀을 흡수. 공통 선행 읽기는 **SKILL.md + GLOSSARY.md** 둘이며, SKILL.md는 스킬의 일반 내용을 담아 모든 역할이 숙지하는 기본 문서다.
- ⑤ **디렉토리 구조**: `SKILL.md · GLOSSARY.md · 계약/ · references/ · schemas/ · scripts/`.
- ⑥ **규범화**: 통합-설계는 스킬의 정본이 아니라 설계도면이다. 설계도면↔스킬 문서, `CONTEXT.md`↔GLOSSARY 사이 의미 충돌은 우선순위로 중재할 대상이 아니라 존재해서는 안 되는 결함이며, 바텀업 도출과 양방향 링크로 일치를 만들고 유지한다. 바텀업 구축 순서를 새 절에 규범으로 적고 §27에 완료 조건을 추가한다. 배치는 새 §30 + 기존 절 접점 수정(§6.1, §10.2, §11.1, §19.5, §27).
- ⑦ **산출 경로**: 수정안 문서 작성. verify-rounds 적용과 통합-설계 반영은 이 세션 범위 밖의 후속 단계다.
