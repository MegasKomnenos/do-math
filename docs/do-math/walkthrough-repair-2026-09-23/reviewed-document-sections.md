# GLOSSARY.md

### 가시 연구 프런티어 (`F`)

현재 명시한 질문, 가설, 정의 후보, 증명 후보, 연구 방향, 장애물과 부분 결과의 집합이다. F 객체의 존재와 연구 가치는 그 내용이 인증된 수학이라는 뜻이 아니다. 모든 F를 작업 계약으로 만들거나 즉시 선택할 의무도 없다.

### 반복 교정 문턱

이미 수입한 자료의 재저작, 선택 실패, 무산출 준비, 제안·계약 개정을 반복할 때 동일 시도의 후속을 다시 판단하는 경계다. 채택된 각 계보의 횟수 한도에 도달하면 그 계보의 보류 소유자는 `user`이며, 공개 `repetition_continue` 결정이 현재 보류와 정확한 후속 범위를 승인해야 계속할 수 있다. 이 결정은 기존 실패를 삭제하지 않고 새 집계 구간을 연다. 새 ID나 이름만 바꾸어 같은 문턱을 우회하지 않으며, 다른 독립 작업은 계속할 수 있다.

입력·환경의 기술적 실패는 기존 운영 점검과 수리 요청으로 처리한다. 수락된 `retry`·`resume` 처분의 후속 요청은 원 action ID를 재사용한다. 실제 재실행에는 새 execution ID를 부여하고 `continuation_of`에 종료된 선행 execution ID를 기록한다. 같은 처분을 다시 처리해도 후속을 중복 생성하지 않는다. 기술 수리로 후속 요청을 만들었다는 사실은 반복 횟수를 초기화하거나 사용자 계속 승인을 대신하지 않는다. 반복 한도 보류가 남으면 그 요청도 착수를 기다린다. `repetition_hold`의 `owner`는 원 요청의 작성자가 아니라 해소 권한자인 사용자다. 과거 원문에 `owner=ai`가 남아 있어도 현행 판단에서는 사용자 소유로 해석한다.

반복 여부를 판단할 때는 현재 action에 연결된 실행 결과와 실패 기록을 먼저 읽는다. 그다음 해당 역할의 입력 계약과 아래 표에서 그 절차에 해당하는 근거를 확인한다. 반복 문턱은 이 모든 절차에 공통인 정수 설정 하나가 아니다.

| 반복하는 절차 | 확인할 근거 |
|---|---|
| 출력 수리 | 그 실행의 `repair_responses`와 수신 결과 |
| 진단 재시도 | 그 명령의 재시도 한도 |
| 계약 수정 | 계약 검토의 `item_reviews`와 revision 기록 |
| 연구 재판단 | 현재 계획 입력의 사건·전제·과제 조건 |

`import_rework`는 최초 해석 뒤 같은 원입력을 다시 저작하려고 등록한 실행을 센다. 별도 독립 검사와 검사 응답만의 수리는 제외한다. `selection_failure`는 정상 최종 응답의 파싱·스키마·계약 검사 실패를 실행별로 한 번 세고 정상 수신으로 연속 구간을 끝낸다. 전제 변경·자원 대기·입력 한도·공급자 실패·저장 공개 대기는 이 실패 횟수에 넣지 않는다. `exhaustion_empty`는 일반 후보 준비가 계약을 보존하지 못한 회차를 세며, 평가·관찰 규칙만 보충하는 실행은 횟수를 늘리거나 초기화하지 않는다. 제안·계약 판본과 출력 수리 횟수도 각각의 이력을 사용한다.

#### 반복 보류의 계속 결정

채택된 반복 한도 뒤의 계속은 `decision --file`에 `kind=repetition_continue`인 JSON을 제출한다. 필수 값은 `lineage`, `lineage_id`, `hold_event_ref`, `allowed_action`이다. `lineage`는 `import_rework`, `selection_failure`, `exhaustion_empty`, `proposal_version`, `contract_revision` 중 하나다. 현행 `repetition_hold`의 계보와 근거 사건을 그대로 사용한다. 제안·계약 판본 계보에서는 현재 집계 이력의 마지막 판본을 `baseline_revision`으로 함께 지정한다.

`allowed_action`은 승인할 현재 큐 또는 대기 action의 범위 객체다. 그 action에 존재하는 `id`, `role`, `target`, `stage`, `owner_activity_id`, `continuation_of`, `revision_targets`, `repetition_bases`, `import_id`, `previous_import_id`, `intent_repair`, `review_cycle_id`, `grant_id`, `assessment_targets`, `observation_rule_targets`만 값 그대로 복사한다. 없는 필드는 추가하지 않는다. `reason`과 배정 캐시처럼 범위를 바꾸지 않는 나머지 필드는 복사하지 않는다. 실행기는 이 객체를 현재 요청과 정확히 대조하고 다른 계보·과거 보류·넓어진 범위·이미 실행 중인 시도를 거부한다.

수락한 결정은 과거 이력을 보존한 채 해당 보류를 해소하고 새 집계 구간을 연다. 같은 `decision_id`·보존 원문 참조·결정 내용의 재처리는 중복 적용하지 않는다. 사용자 정지·grant·입력 복원 등 다른 대기는 그대로 검사한다. AI의 기술 수리 처분은 반복 한도 보류를 해제하거나 이 사용자 결정을 대신하지 않는다.

정상 수신된 무산출 준비가 `exhaustion_empty` 문턱에 도달했고 같은 계보의 다음 요청이 아직 없으면, 계속 결정과 새 요청을 함께 만들 수 있다. 이 경우의 `allowed_action`은 `{"id":"아직 사용하지 않은 AC 식별자","role":"research_preparation","repetition_bases":{"exhaustion_empty":"현재 lineage_id"},"revision_targets":{}}` 형식이다. 같은 계보에 큐 또는 대기 요청이 이미 있으면 그 기존 요청의 범위를 승인한다. 무산출 준비 실행이 수신 실패로 끝났다면 현재 큐 또는 대기에 보존된 수리 요청의 정확한 범위를 승인한다. 이 경우 계속 결정으로 새 일반 준비 요청을 만들 수 없다. 이 결정은 사용자가 명시적으로 요청한 준비이며 자동 고갈 재생성 시각만으로 열린 준비와 구별한다.



# 계약/후보-준비.md

## 입력 부족, 무산출과 중단

필수 원문을 읽지 못했거나 현재 입력만으로 질문·범위·완료 기준을 정할 수 없으면 추측한 계약을 만들지 않는다. `summary`에 확인한 범위와 읽지 못한 자료를 적고, `questions`에 필요한 결정이나 원자료를 구체적으로 남긴다. 후속 조사가 먼저 필요하면 현재 근거로 정할 수 있는 조사 과제를 제안하되, 그 조사 결과를 이미 확보했다고 쓰지 않는다.

적합한 새 계약을 찾지 못한 회차도 유효할 수 있다. 이때 `candidates`는 빈 배열이고, 무엇을 살폈는지, 같은 제안을 반복하지 않은 이유, 남은 F와 다음 재검토 사건을 `summary`에 남긴다. 자료가 없어서 판단하지 못한 상태와 실제로 검토했지만 새 계약이 없었던 상태를 구별한다. 무산출을 연구 완료나 목표 해결로 바꾸지 않는다.

일반 후보 준비의 주 응답에는 `regenerate_after`를 쓴다. 입력의 기계 관찰 시각 `observed_at`보다 뒤인 시각을 시간대가 포함된 ISO 8601 문자열로 정한다. 후보를 제안했어도 모두 수신 거부될 수 있으므로 후보 유무와 관계없이 작성한다. 생산자 제출 검사와 중앙 수신 검사는 같은 입력 시각에 대조한다. 작성자가 `observed_at`을 새로 만들거나 출력에 복사할 필요는 없다.

실행기는 실제로 계약을 한 건도 보존하지 못했을 때만 이 시각을 고갈 재생성의 다음 관찰 시점으로 기록한다. 시각이 도래해도 현재 고갈·권한·반복 보류 조건을 다시 검사한다. 정기 탐색 사건은 자기 조건에 따라 따로 처리한다. `assessment_targets` 또는 `observation_rule_targets`를 받은 보충 전용 실행은 `regenerate_after`를 작성하지 않으며 후보 생성의 성공·무산출 집계를 바꾸지 않는다. 보충 요청에는 후보 생성의 무산출 보류를 적용하지 않는다. 관찰 규칙 보충으로 계약 판본을 바꾸는 경우에는 해당 계약의 개정 이력과 개정 보류를 적용한다.

정지 요청을 받거나 실행을 끝내지 못하면 공통 실행 문서에 따라 이미 얻은 근거와 후보 초안, 남은 의무와 바로 이어갈 위치를 체크포인트에 보존한다. 새 연구나 새 원자료 조회를 시작하지 않는다. 스키마에 맞는 응답을 제출할 수 있으면 실제 범위만 반환하고, 제출할 수 없으면 다음 실행이 체크포인트와 실패 원인을 이어받게 한다.



# 계약/의도-해석.md

## 독립 검사

독립 검사는 `action.role=intent_interpretation`, `action.stage=check`로 배정되는 별도 실행이다. 검사자는 같은 고정 원문·상태·원천과 검사 대상 묶음을 받되, 해석자의 숨은 맥락이나 미고정 작업물을 근거로 삼지 않는다. 검사 본문은 다음을 포함한다.

- `decision`: `approved`, `revision_required`, `unresolved` 중 하나
- `findings`: 발견한 누락·왜곡·소유권·질문·적용 위험
- `scope_complete`: 원문 전건 피복과 범위 처분이 완전한지
- `bundle_sha256`: 검사한 해석 묶음의 정확한 해시
- `unit_ids`: 검사한 모든 가져오기 단위 식별자
- `question_ids`: 검사한 모든 질문 식별자

검사는 구간이 원문을 정확히 피복하는지, 해석이 원문 의미를 보존하는지, 모든 단위와 질문이 등록된 소비자 및 실제 대상에 연결되는지, `decision_refs`가 현행 판본인지, 질문 없이 창작한 사용자 결정이 없는지를 확인한다. `bundle_sha256`, `unit_ids`, `question_ids`가 검사 대상과 정확히 맞지 않으면 승인할 수 없다. `approved`는 해석 묶음이 적용 후보가 될 수 있다는 뜻일 뿐, 사용자 승인이나 실제 적용을 대신하지 않는다.

## 재저작과 반복 보류

원 해석이 잘못되어 `revision_required`를 반환하면 새 `stage=interpret` 실행이 원입력을 다시 해석한다. 실행기는 `previous_import_id`·`intent_repair`로 기존 묶음과 검사 결과를 연결하고, 같은 원입력의 재저작 시도를 등록할 때 한 번 센다. 해석 실행의 형식 오류를 고치는 후속도 재저작에 포함되며, 새 묶음 ID로 횟수가 초기화되지 않는다. `stage=check`의 형식 수리는 검사 응답만 고치고 검사 대상 묶음의 해시를 유지한다. 원 해석을 바꾸어야 하면 검사자가 직접 수정하지 않고 반려한다.

채택된 재저작 한도 뒤에는 그 원입력의 다음 재저작이 보류된다. 최초 해석, 독립 검사와 별도 사용자 답변의 해석은 그 보류의 적용 대상과 구별한다. 보류 해소는 GLOSSARY의 반복 교정 문턱과 공개 계속 결정 계약을 따른다.



# 계약/운영-점검.md

## 실패 유형별 판단

`output_parse`·`output_schema`·`output_contract`는 각각 파싱·출력 스키마·계약 수신 실패다. 주 응답·확장·편입 묶음의 정확한 문제를 읽고 의미 보존 수리 가능성을 판단한다. 과거의 `output_validation` 기록은 상세 검사 근거를 읽되 새 분류로 소급 확정하지 않는다. 이미 수락된 묶음을 바꾸거나 재소유하지 않고 반환된 묶음만 수리한다. `currentness_changed`이면 변경표와 실제 읽기 의존을 대조한다. `publication_failure`는 중앙의 저장 재대조 대상이며 작업자의 의미 오류로 처리하지 않는다. 공급자 한도는 허용 시각과 원 실패를 보존하며 같은 제한을 확인하려고 새 모델 진단을 반복하지 않는다. scholarly 자료원의 429를 모델 공급자 한도로 바꾸지 않는다.

입력의 `repetition_holds`에서 대상 계보의 현행 반복 한도 보류를 확인한다. 이 보류는 사용자 계속 승인이 필요하며 기술 수리 처분만으로 해제할 수 없다. 기술적 복구를 위한 `retry`·`resume`을 제안하면 중앙은 수락된 처분과 종료된 대상 실행을 확인하고 같은 의무의 후속 요청을 연결한다. 체크포인트로 재개할 때에는 보존 참조와 원문 바이트도 대조한다. 같은 처분의 재처리는 이미 연결한 후속을 반환하며 요청을 중복 생성하지 않는다. 반복 한도 보류가 남으면 후속 요청도 착수를 기다린다. 기술 수리 처분을 수락했다는 이유로 누적 실패를 지우지 않는다.

프로세스 시작 실패·중첩·PID 재사용 의심·제어 무응답은 실제 자식 프로세스와 원장·Job 영수증의 범위에서 판단한다. PID 값만 같다는 이유로 같은 실행이라고 보거나, 부모 하나의 종료로 자손 종료를 확정하지 않는다. 현재 Windows Job이 입증하는 로컬 프로세스 수명과 자손 종료를 모든 호스트 자원 격리로 확대하지 않는다.

## 계속 승인과 복구의 연결

채택된 횟수 한도를 넘는 계속은 사용자 결정이다. `repetition_hold`를 만드는 실제 경로는 이 횟수 문턱뿐이므로, 과거 원문에 `owner=ai`가 남아 있어도 현재 효력은 사용자 소유로 계산한다. 과거 기록 자체는 다시 쓰지 않는다. 사용자 결정은 현재 계보·보류 사건·정확한 후속 범위를 대조하며, 평가 대상과 관찰 규칙 대상도 범위에 포함한다.

준비 결과는 정상 수신됐지만 새 계약·개정 계약을 한 건도 보존하지 못해 한도에 도달할 수 있다. 그 계보에 다음 큐·대기 요청이 없다면 사용자가 계속 결정의 `allowed_action`으로 새 일반 준비 요청을 지정한다. 실행기는 승인한 요청을 결정과 함께 저장한다. 제출이 실패한 경우에는 현재 큐·대기에 보존된 수리 요청의 범위를 승인한다.

수리안에서 제안했던 별도의 AI 기술 보류 허용·소비 장치는 구현의 생산 경로를 확인한 뒤 폐기했다. 그런 보류를 만드는 경로가 없는데 허용 원장을 더하면 쓰이지 않는 상태 관리가 남기 때문이다. 호출되지 않던 `authorize_repetition_repair()`도 제거했다. 기술적 복구는 기존 운영 처분과 수리 요청으로 처리한다. `retry`·`resume`의 후속은 원 action ID를 재사용하고 배정 시 새 execution ID를 받는다. 처분의 `continuation_action_id`에는 재사용한 action ID를 기록하여 후속의 중복 생성을 막는다. 수락된 처분과 후속 요청은 같은 저장 갱신으로 공개한다.

기술 수리를 이유로 선택 실패나 무산출 횟수를 초기화하지 않는다. 계획의 정상 수신은 연속 선택 실패 구간을 끝내고, 실제 계약을 보존한 일반 준비는 무산출 구간을 끝낸다. 제안·계약 판본과 의도 재저작은 각각의 기록으로 계속 집계한다. 반복 한도 보류는 이 집계와 구별되며 공개 사용자 계속 결정으로 해소한다.

재개용 체크포인트는 수집한 원문 바이트의 해시가 맞을 때 저장 참조를 연결한다. `resume`은 그 참조와 바이트를 다시 대조한다. 재시도 계보에 결과가 `unknown`인 외부 행동이 있으면 공개 외부 행동의 `reconcile` 절차로 전송 결과를 먼저 확인해야 한다. 같은 operation ID·요청 해시·멱등 키에 묶인 관찰 근거로 성공·효과 부재·미전송 중 해당 사실을 확정한다. 실제 외부 재전송은 그 뒤에도 별도의 기존 재시도 허가를 검사한다. 사용자 정지·grant·현재성·이미 수락된 편입 묶음의 보존 조건도 계속 적용한다.

공개 결정의 입력 형식은 [CLI 실행 계약의 반복 보류 절](../../.claude/skills/do-math/references/CLI-실행-계약.md)에 기록했다. 생산자의 변경 의무는 GLOSSARY와 후보 준비·의도 해석·운영 점검 계약에 함께 반영했다.

## 검증 근거와 한계

검사는 편집 중인 정본과 분리한 고정 사본에서 수행했다. [검증 원장](walkthrough-repair-2026-09-23/verification.json)에 각 실행의 대상·판본·실제 결과와 원보고서 위치를 보존한다. 여러 실행에 같은 검사가 포함되므로 실행별 건수를 합산해 독립 검사 수로 쓰지 않는다. 최초 실패도 후속 통과로 덮어쓰지 않는다.

수정 전 사본에서는 검토 입력 복원 실패 뒤 `activities.wait_for()`가 미종료 실행을 이유로 예외를 냈다. 같은 사본에서 비형식 지식 3건을 받은 연구 결과는 계획 요청 4건을 만들었다. 수정 사본에서는 복구 대기 저장·재개와 계획 요청 한 건을 각각 확인했다. 관련 회귀에는 공개 사용자 계속 결정, 정상 최종 응답의 원문 포착부터 수신 실패 집계까지, 운영 처분의 수락부터 중복 없는 후속 생성과 사용자 한도 검사까지, 보충의 집계 제외, 재생성 시각 도래와 중복 방지가 포함된다.

결과 참조를 연결하면서 드러난 영향 전파 오류도 고쳤다. 기존 전파기가 실행·활동에 저장 계약에 없는 `input_current`·`use_history`를 추가하여 원자료 변경의 저장을 거부했다. 이 두 기록은 기존 입력 현재성 검사와 영향 전파 이력으로 다루므로, 소비하지 않는 필드를 새로 저장하도록 스키마를 넓히지 않았다. 실행·활동의 원래 결과를 보존하고 영향받은 기록 목록을 이력에 남긴다. 해당 원자료 변경 검사의 최초 오류와 재검증 결과도 검증 원장에 구별한다.

모델 응답과 수학 검사 결과는 명시적인 대역을 사용했다. Git·파일·등록·수신·활동 전이·후속 요청은 검사에 따라 실제 구현을 통과했다. 문서 독해는 변경한 절의 전문과 필요한 공통 규정을 대상으로 했으며, 변경하지 않은 문서 전체의 의미 검증이나 실제 연구 모델·Lean·연구 성과의 검증을 뜻하지 않는다. 전체 저장소의 모든 회귀를 통과했다는 주장도 하지 않는다.

## 변경의 보존 범위

정본은 `.claude/skills/do-math`이며 `.agents/skills/do-math`를 생성기로 갱신하고 드리프트 검사를 통과시켰다. 이번 수리 전부터 같은 파일들에 선행 구현의 미커밋 변경이 있었다. [수리 패치](walkthrough-repair-2026-09-23/source-changes.patch)는 그 작업 시작 상태와 이번 결과 사이의 차이를 보존한다. 패치와 검증 원장은 선행 구현 전체를 이번 작업의 산출로 취급하지 않는다. 기존 변경을 함께 포함하는 소스 커밋·푸시는 수행하지 않았다.
