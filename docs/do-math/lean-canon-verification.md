# do-math Lean canon: verification

do-math runs unattended mathematical research with sessions of six roles. In the redesign recorded in [the design record](lean-canon-design.md), the knowledge of a research instance is a Lean library from its first session on: every assertion the research keeps is a Lean declaration with a written record beside it, and sessions find their work, publish their results and read earlier results through that library. The redesign is implemented in the canonical skill, `.claude/skills/do-math/`.

This document records what was run to check that implementation, what each run showed, and what no run has shown. It is written for two decisions: how far the implementation can be relied on as it stands, and what has to be checked or decided before the first real research is started with it.

## What was agreed, and where it stands

The agreement that preceded the implementation fixed three conditions for calling the work complete. The tests pass. A small proposition runs from its Lean root to a dependency map and to the PDF of a paper. The guides pass independent reading.

All three are met. The first is met in the sense that the table states.

| Condition | State | Where this document reports it |
|---|---|---|
| The tests pass | Met: each of the sixteen test modules passed in its last run. The runtime was changed several times after the last run of the whole suite, and the suite was not run as a whole again. The section says which modules were run after which change; three modules were not run after any of them, and the two modules that the later revision of the guides changed have not been run in their present form | "Automated tests", "The revision of the guides after the rounds" |
| A small proposition runs from the Lean root to the dependency map and the paper's PDF | Met: the map was drawn, and one command produced the paper as a LaTeX manuscript and its PDF | "A research run by real sessions", "The dependency map and the paper" |
| The guides pass independent reading | Met: the design record and the final guides were read independently, and two rounds of review and repair followed. The guides were revised afterwards; that revision was compared with the text it replaced and was not read independently from the beginning | "Independent reading and the review rounds", "The revision of the guides after the rounds" |

Three limits qualify these results, and each has a section of its own. The research that real sessions ran was one small research, so it exercised the paths that one small research takes and no others. The tests replace the Lean compiler by a stand-in, so they do not show how the real compiler behaves. And nothing was run at the scale of a research that imports Mathlib.

The table gives the number of tests each module holds now.

**What the tests do not show.** The tests do not run Lean. A stand-in program, `tests/canon_lean.py`, takes the compiler's place: it reads a small subset of Lean and prints the rows that the index extraction prints. Scripted programs take the place of the AI sessions. The tests therefore show that the runtime does what it should with the outputs it is given. They do not show that the real compiler gives those outputs, and in particular the Lean program that extracts the structural index is exercised only by the runs with the real compiler described next.

The difference has already hidden one defect. The extraction file imported only the modules a change had touched, so the real compiler could not confirm a record's claim that a new declaration proves or refutes a statement declared in a module that the module of the new declaration does not import. The stand-in sees every module at once and confirmed the claim. In the research described below, a peer met the refusal while it prepared its candidate, before the candidate was handed to review, and worked around it. The review rounds found the cause in that session's record and repaired both the extraction and the stand-in.

## Runs with the real compiler

Lean 4.32.0 was used, without Mathlib.

A scripted research, the one `test_pipeline` runs, was run once against the real compiler in place of the stand-in. It finished in 579 seconds with the root formally proved. Creating the instance took 41.7 seconds. The run included the step that the research by real sessions did not reach: the root first receives a proof written in words, and its Lean declaration names the lemma that proof rests on and ends in `sorry`. The proof of the same declaration is then replaced in place by a complete Lean proof, and an import is added to the root's module. The five compiles that extract the index had a median of 57 seconds, and each was charged about 2.1 GB against the memory that Windows had promised to processes, its commit charge, on the machine while another research instance was running on it.

The measurements that the design rests on are in section 12 of the design record. One of them corrects an expectation of the design and matters for cost: replacing a proof leaves the compiled public output of its module unchanged only when the new proof makes the elaborator generate the same auxiliary declarations as the old one. Otherwise the modules that import it are compiled again.

## A research run by real sessions

One research was run from start to finish by real AI sessions and the real compiler. The proposition was that the sum of the first n odd natural numbers is n squared. The operator's part followed the guide: the root in words, a definition and the root statement in Lean in two modules, a record for each declaration, and a check of the definition on six known values as a theorem with a complete proof. The instance is kept at `.skill-workspace/do-math-e2e-20261122/instance`, a local folder outside version control.

The runner launched six sessions, all on the same model (`claude/opus`, effort high): an attempt, an exploration, a peer for each, and a review for each candidate. The following happened.

- The attempt found a complete Lean proof of the root by induction and left it as the text of the root's declaration. Its peer made the candidate: the proof in place of `sorry`, the root's record with the written proof and an explanation, an approach entry, and one new element stating that the recursive definition equals the literal sum for every n.
- The review compiled the candidate itself, read the axioms (`propext` and `Quot.sound`), confirmed and accepted the proof. The runner built the candidate on the canon, installed it and committed. The root was formally proved 863 seconds after the attempt started, and the instance counted as complete from then on.
- The exploration was assigned the root question. Its peer published, 2,377 seconds after the attempt started, nineteen further elements with complete Lean proofs and the first understanding text of the root question. Among them are a second proof of the root's statement as a separate declaration, and two proofs that review confirmed as correct and did not yet accept, giving its reason. Such a proof is published and can be used, and its statement stays marked as work that remains. This is the second of review's two judgments at work.
- The runner then ended. Once the root is formally proved it launches no further attempts or explorations, and the sessions that were running had been carried through to publication. The two statements whose proofs are held back stay marked as work that remains.

The canon at the end holds 23 elements: three definitions, eighteen statements whose proofs are accepted and two whose proofs are correct and held back. Twenty statements are formal.

**What this run did not exercise.** The first proof of the root was already a complete Lean proof, so no formalizer was launched. Two publications were too few for an organizer. No candidate failed to build, so no replacement peer was needed. No candidate offered a new proof to be put in the place of a proof the canon already held, so review never had to decline such a replacement, and no concern or contested statement led to a comprehensive review. No statement was refuted. These paths are covered by the tests and, for the formalizer's replacement in place, by the scripted run with the real compiler. No real session has yet followed the guides along them.

## The dependency map and the paper

Both commands were run on the instance of the previous section.

`depmap.py` drew the map after the first publication, when the canon held four elements. The map shows the units, the elements whose record marks them as results one would name when describing how the proof goes; the other elements are steps and are folded into the lines. Two of the four are units, the definition of the sum and the root, and the map joins them by one line. It wrote the SVG drawing, the page for a browser and the JSON file from which the map can be drawn again. A map this small shows that the command runs on a real canon. It does not test the layout, which the tests exercise on larger canons made by hand.

`paper.py` was run twice. The first run was made while the machine had no TeX. It went through every stage except the typesetting, with real sessions: one planned the paper, two wrote its two sections, the manuscript passed the machine checks, two sessions read it with nothing but the manuscript before them, a repair session followed each reading, and one session compared the paper's one numbered statement with the statement of its element and found them the same. The eight sessions took 591 seconds. The command then stopped with exit code 3, as it is meant to when no TeX command is available, leaving the manuscript `paper.tex`, the plan, the correspondence file and the log under `.skill-workspace/do-math-e2e-20261122/out/paper`.

**The first typesetting.** After the user approved the installation of TeX, that manuscript was typeset with Tectonic 0.15.0, a single program that fetches the TeX packages it needs when it first uses them. The program was taken from the release page of its project and is kept in a local folder outside version control, `.skill-workspace/do-math-toolchains/tectonic-0.15.0/bin`; it is not on the PATH, and the paper command is given its path with `--tex`. This was the first time that the LaTeX which the script itself writes, the preamble and the command that typesets the Lean statement, went through TeX. TeX reported no error, and the printed pages showed three defects that no check had been able to see.

- On the even pages the running head showed the title with its variable n as a capital N. The manuscript names no author, and the `amsart` class then takes the title for that head and puts it in capitals a second time, the letters of its formulas included. The script now sets the running head itself.
- In the Lean statement the character `^` came out as an accent, because the script wrote it as `\^{}`. It now writes the character, and the method tells the sessions that write the paper to do the same.
- One displayed formula was 69 points wider than the text block and stood out into the margin. TeX reports such a line as a warning and typesets the paper all the same, and the script looked only at errors. It now reads these warnings from the log of TeX and sends a line that is more than five points too wide to a repair session. If the line is still there after the repairs, the paper is typeset with it and the command reports it.

**The run that produced the PDF.** The manuscript of the first run could not be typeset by the command itself. `--typeset-only` reads the correspondence file that the earlier run left, and that file had been written before the review rounds added a field to it. So the command was run once more from the start, with the three repairs in place. Eight sessions took 780 seconds: one planned the paper, two wrote its sections, two read it, a repair followed each reading, and one compared the numbered statement with the statement of its element and found them the same. The manuscript was assembled three times, after the writing and after each repair, and each time TeX typeset it without an error and without a line too wide. The command ended with exit code 0 and left `paper.pdf`, of three pages, beside the manuscript under `.skill-workspace/do-math-e2e-20261122/out/paper-tex`. The pages were looked at afterwards: the running heads show the title as it stands, and the Lean statement shows its characters.

The readings of both runs raised the same point, which no repair could settle because it is not a matter of wording: the paper says that its main theorem has been verified in Lean, and a reader has no way to reach the Lean source. Where that source is published, and how the paper refers to it, is for the user to decide.

## Independent reading and the review rounds

The design record was read fifteen times by a reader that received the manuscript and a description of its reader and nothing else, and it was revised after each reading until the reading reconstructed what had been agreed.

The guides were read in three stages. The agents that wrote them had fresh readers read their drafts. After the runtime had stopped changing, four readers read the final guides as the sessions of the roles and the operator receive them, first alone and then against the code. This second stage found what the first could not: places where guides written at the same time by different authors said different things about one matter, and places where the code had come to behave otherwise than a guide said. They were corrected before the first commit.

The third stage was two rounds of review and repair over the guides, the runtime and the tests, 68 files. In each round six repairers, five with an area of files and one following the design's decisions and the guides' promises into the code, wrote findings with complete repairs, and three judges decided each finding independently; a repair was applied only when all three approved it. The record of the rounds is `임시/do-math-lean-canon_검증_20261122/장부.md` with its closing report `종료보고.md` beside it.

| Round | Findings | Applied | Rejected | Left to the user |
|---|---|---|---|---|
| 1 | 29 | 25 | 3 | 1 |
| 2 | 21 | 19 | 0 | 2 |

The rounds ended after the second on the user's instruction, so they did not run until a round found nothing. The second round still found defects of substance, which is a reason to expect that some remain.

Among the repairs that changed behaviour: the broker's gate on free memory now subtracts the memory still owed to compiles that have started and not yet loaded their imports, where before compiles started a fraction of a second apart all passed on the same free memory; the paper command no longer reports a manuscript with open findings as complete when it is typeset later; the index extraction can confirm a claim across modules; approach entries of a statement whose proof is accepted go to the history by every path; and two formalizers are no longer sent to one statement.

The three findings of the first round that were rejected named real defects with a flawed repair. Two were found again and repaired in the second round. The third, that a refutation is not counted when the negation of a statement is settled through a proof held by another declaration of that negation, was repaired afterwards, outside the rounds, with a test.

Three findings proposed a choice that belonged to the user, and the rounds left them as they were. The user has since decided all three. The next section says what was decided and what the implementation now does.

## Three decisions made after the rounds

Each of the three decisions changes something that the design record states, and the design record is kept as it was written. Where the two differ, the guides and the code follow the decisions below.

**A research that ends with the root refuted.** The dependency map drew what the proof of the root rests on. A refuted root has no settled proof, so its map showed the root alone. The user's decision was that such a research has a result, the refutation, and that the map shows it. The root's card now says that the root is refuted. A settled statement that refutes the root is drawn even where its record marks it as a step and not as a unit, a line of a kind of its own joins it to the root, and the map includes what that statement rests on. A statement that would refute the root and is not settled refutes nothing yet, and the map leaves it out. When every unit of the canon is asked for, such a statement is drawn if its record marks it as a unit. This adds one kind of line to those that section 13.1 of the design record describes.

**Snapshots of Lean's state after import.** Section 12 of the design record adopts two things: the broker saves Lean's state after the import of a file's header and starts later compiles with the same header from it, and a compile that used such a snapshot and failed is run again without it. As implemented, the reuse served only compiles whose imports are all external, which leaves out every compile that imports a module of the canon. The rule also needed an exception. Sessions submit many files that Lean rejects, and running each of them a second time would have cost more than the snapshot saved, so a compile that was rejected after loading a snapshot which an earlier compile had shown to be sound was not run again. Under that exception a snapshot damaged later could have made the broker report a correct file as rejected. The user judged that the saving did not justify these rules, and the reuse was removed: the broker's code for it, the setting `lean.header_snapshots`, its tests and the passages of two guides. Every compile now loads its imports in full. For a file that imports the Lean metaprogramming library this is the 9.7 seconds measured without a snapshot, where a compile started from one took 2.8.

**A statement that supersedes a settled statement.** By rule 3 of section 10.3 of the design record, a better statement enters under a new name, and the proof of the old statement becomes one line that derives it from the new one. For an old statement that was already settled nothing carried this out: a session replaces the proof only of a statement it has registered as its work, and a settled statement can no longer be registered. The user's decision starts from an observation. A new statement that is not yet settled is not a better statement than a settled one, because deriving the settled statement from it would make an established result rest on one that is not established. The rule is therefore that the proof of a settled statement is replaced only by a proof under which the statement stays settled. A candidate that adds the new statement leaves the old proof as it is. Once the new statement is settled, the one-line derivation can take the place of the old proof, and no registration is asked for it. Conditions are set on the derivation where the old proof is the only one through which the statement is settled, or the only one through which it is formal; a proof is formal when it is complete in Lean and rests, through everything of the canon it uses, only on the allowed axioms. The check of the peer's candidate then accepts the derivation when it is complete in Lean and every statement it names is settled, and, where the statement would otherwise stop being formal, when the statements it names have formal proofs as well. Review has to confirm and accept the derivation, since under any other verdict the old proof stays. Where another proof keeps the statement settled, and formal if it was formal, none of these conditions is set, and review judges the new proof as it judges any other replacement. No session is launched to take this second step. A peer whose work comes to the old statement can take it, and until one does the old proof remains.

The first and the third decision came with tests: one of the map of a refuted root, and five of the rule, of which four are of the checks on a peer's and a review's output and one carries the three publications out in order. The removal took the 14 tests of the snapshots with it.

## The revision of the guides after the rounds

After the three decisions the guides were revised once more. Before the revision a session received passages that only another role acts on, and it received some explanations several times, once in each of several documents. The purpose was that each role receive what it acts on, and receive it once. The revision also changed the runtime in two places. One of the two changes something that the design record states, and the design record is again kept as it was written.

**What each role receives.** The guides a session receives at launch are joined into one document, its pack. Two references are new, and both were made from passages that every role received before in the common introduction, the tools guide and the canon guide. `sections.md` says how a section is stated, how broad it should be and when it is registered, and gives the commands of the lease; it goes to attempts and peers, the roles that register sections. `records.md` gives the formats of the record, of the approach entry and of the understanding text, and the criteria for the weight of an element; it goes to peers, reviewers and organizers, the roles that write those texts or judge them. The commands with which an explorer takes a question moved into the explorer's guide. What `commands.prepare` and `commands.verify` do, and what their builds compile, now stands in the guide to the candidate change, which the roles that run those commands receive. Explorers, formalizers, reviewers and organizers therefore no longer receive the guidance on stating and registering a section. Attempts, explorers and formalizers no longer receive the formats of the written texts, the weight criteria or the account of those two commands, and only explorers receive the question commands.

Inside a pack, a passage was removed in three cases only: where it restated an explanation whose body stands in another document of the same pack, where it repeated something within one document, and where it joined two passages without adding to them. No explanation was shortened.

Two other changes to the same files entered with that commit and add text: a new rule for when a question counts as resolved, about 4 kB for an explorer and less for the other roles, and guidance on choosing imports, about 2.5 kB for every role.

**The order of the pack.** Section 8 of the design record lists what a session receives at launch and names the guides first. The pack now begins with the root, in words and in Lean, and with the session's assignment. The guides follow, so that they are read with both in mind. The views of the research, the user's conditions and the commands come after the guides, as they did before. `test_context` was changed to expect this order.

**A statement of the paper that a repair changes after its comparison.** The paper command compares every numbered statement of the manuscript with the statement of its element. When a manuscript is typeset later with `--typeset-only`, a failure of the typesetting goes to a repair session, and the statements are not compared again. Such a repair could change a numbered statement. The correspondence file then marked the statement as not compared, and the command still ended with exit code 0. The command now reports every numbered statement whose present text has no verdict of the comparison as an open finding, and ends with exit code 2. The operator's guide says so in the table of exit codes, and one test of it was added to `test_paper`.

**How the revision was checked.** The check was a comparison of the revised text with the committed text, in three parts.

- A reader on a different model from the one that had revised a guide received the committed text and the revised text and classed every sentence that had been removed or reworded: preserved in the same pack, weakened, lost, or changed in meaning. Seven such comparisons were made: one for each role's guide with the references particular to that role, and one for the two operator documents. One found nothing. The other six found seventeen points in all, and all were repaired. Two examples: the sentence that a peer is neither a translator nor a checker of the producer's mathematics had been left to the common introduction, which says it of an attempt only, and it was restored to the peer's guide; a summary of what `init` refuses had widened to conditions that `init` does not check, and the committed wording was restored.
- The shared references were compared by a script. It took each sentence of the committed common introduction, tools guide, canon guide, writing guide, Lean guide, retained-work guide and literature guide and searched the revised guides for it. Eighty-eight sentences no longer occur word for word, six of them in the passage on imports that the other change rewrote. Each of the remaining eighty-two was traced to its present wording or to the passage that now carries its content. One had no such passage, that the builds of the two commands wait in the same queue as a session's other compiles, and it was restored. The script also lists the sentences that a role received before and no longer receives; they are the passages named above under "What each role receives".
- While the guides were compared with the code, more than twenty statements that disagreed with it were corrected: for example which failures give the dependency-map command its exit code 2, which errors the runner records in `last_error`, and which checks the preparation of a candidate makes.

**What was not checked.** No test was run after the revision, as the section on the tests says. Both changed test files were imported without error, and the changed function of `paper.py` was called by itself with stand-in rows and returned the exit codes expected. Neither is a run of the tests, and `test_context` and `test_paper` should be run before the first real research. The revised packs were not read from the beginning by an independent reader, as the guides before them were, and no session has worked from them. The comparisons show that what the committed guides said is still said to the roles that act on it. They do not show how a session works with the new arrangement.

## What has not been measured

No research that imports Mathlib has been run with this implementation, and the quantities that decide its cost at that scale are unknown: how long the import takes in each compile, how often a replaced proof changes the public output of its module and sets off compiles downstream, how long a publication waits for its build while other compiles hold the memory, and how many publications an hour the single publication queue carries. Section 16 of the design record lists what to observe in the first real run. On Windows the page file bounds how many compiles run at once, since a Lean process is charged for the whole size of the library files it maps; the operator's guide gives the measurement and the recommendation, and the change is the user's to make.

## Installation and scope

Only the canonical skill was changed. The generated copy `.agents/skills/do-math` was not regenerated, by the user's decision, because a running research instance uses it. The two now differ by a whole generation. The new runtime refuses an instance that was not created by it, so regenerating the copy while that research is still being run would leave its runner unable to start again. The copy is to be regenerated when that research has been ended.
