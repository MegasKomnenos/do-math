# do-math 기능 판본 5 구현 진행

이 문서는 2026-09-20 공유 작업 트리의 구현·연결·검증 상태를 기록한다. 제품 사용 계약은 [README](../../.claude/skills/do-math/README.md), 구체 인터페이스는 [CLI 실행 계약](../../.claude/skills/do-math/references/CLI-실행-계약.md), 기능 목적별 대응은 [기능 완료 대응](기능-완료-대응.md)이 소유한다.

## 설치 문서 정합화의 확인 범위

DOCS는 최종 보고서·독해 합의와 2026-09-21 구현 사본의 조사 결과를 현행 생산자·소비자와 대조했다. CLI의 초기화·예산/판본·관찰·단일 제출·접수와 편입·복구 설명을 같은 정상 흐름으로 다시 구성하고, 사람용 `references/초기화-운전.md`에 공개 요청의 순서·객체·프로필 참조 조회와 실제 증거의 출처를 정리했다. 예시의 사용자 선택·실측값을 승인 사실과 구별한다. 최종 전체 독해·합의 대조와 설치 사본 미러는 MAIN이 맡는다.

운영 수리의 현행 경로는 응답 편입 뒤 `repair_execution.complete_repair`가 종료된 실행의 봉인 catalog/detail 입력을 Git 원문으로 복원·해시 검증하고 명시적 후속을 여는 것이다. 임시 maintenance 수리·독립 AI 검증 단계는 제거됐다. 지원하지 않는 수리와 남은 의미 판단은 실제 다음 소유자에게 돌아가며 기동 불능의 설치 복구 launcher는 별도로 유지된다.

문서 자기 점검 시점의 남은 연결은 다음과 같다. 이후 담당 결과의 완료 통지만으로 닫지 않고 최종 코드와 실행 증거를 다시 대조한다.

- 공개 `decision --file`은 JSON 파일을 한 번 읽어 payload를 `config.change`로, 같은 정확한 원문을 control text로 전달한다. `kind=import_approval`은 `GovernanceEngineMixin._governance_control`을 거쳐 `governance.apply_import_control`로 전달된다. 적용기는 사용자 출처·정확한 수입 묶음·검사·unit 해시와 비어 있지 않은 승인 원문을 대조하고, 적용 뒤 초기화의 다음 action을 연다. 이 연결은 현재 코드 대조 결과이며, 공개 CLI 경로의 최종 회귀 증거는 별도로 붙인다.
- 새 저장 계약은 schema 2의 `immutable_input.text/sha256/bytes` 하나로 정확한 코드 포인트열과 그 UTF-8 해시·크기를 보존하고, 이름·키·원문을 NFC로 바꾸거나 Base64 중복 원문을 만들지 않는다. 정식 생성 뒤 v9 오프라인 검사 84개가 통과했고 과거 `source_conflicts` 고정 출력도 제거됐지만, 이 결과는 규범 묶음의 검사다. 통합 저장 회귀와 기존 schema 1 자료의 호환 또는 명시적 거부는 아직 확인하지 않았다. `.agents`는 의도된 치환을 거친 생성물이며 원시 미러 동일성은 규칙이 아니다.
- 현행 `bundle_impact_request`와 `apply_reviewed_knowledge_changes`는 같은 S0의 묶음 전체·변경별 계획, 지정된 같은 요청의 검토 실행만 제외하는 자기 영향 계산, 승인 합집합의 단일 적용과 한 후보의 대체 기록 전건을 연결한다. 선택적 정규 KN ULID `replacement_id`가 없으면 중앙이 발급하고 명시한 형제 참조만 후보 전건 뒤 검사한다. `submission_contract.command --new-knowledge-id`는 형제 참조에 쓸 canonical KN ID만 생성하며 예약·권한·공개 효과는 없다. 최종 편입은 전역 중복과 CAS를 계속 검사한다. IMPACT 집중 검사 6개는 통과했지만 전체 편입·CAS 회귀는 아직 실행하지 않았다.
- 원 판정 재심사는 일반 K 동일성 검토와 구별된 정확한 원 IA·전제·정책·독립 계보를 요구한다. KNOWLEDGE의 소유 API와 중앙 진입·반환·유한 활동 종결의 연결은 별도 완료 조건이다.
- 신뢰 전환의 변경 결과는 staged 검토의 실제 봉인된 결과를 소비해야 한다. LIFECYCLE의 요청·수신과 KNOWLEDGE의 runtime 결박 활성화가 같은 원자 적용 계약인지 확인한다.
- 연구 관찰은 `{source,operator,subject_kind,unit}` 항목의 `observation.rule_bindings`와 필수 window를 사용하고 실행 ID·카운터 이름은 실행 문맥에서 결박한다. 첫 tick의 미측정을 0이나 즉시 운영 호출로 바꾸지 않고 첫 관찰 구간 뒤에도 없는 신호를 진단한다. EXECUTION 결과에는 관찰 52개·형식 16개 검사와 실 Windows Job probe의 통과가 기록됐지만 lifecycle 공개 시험 두 건은 멈췄다. 공급자 내부 호출·원격 종료·과금은 계속 `unknown` 가능 범위이고 전체 통합 결과는 `PARTIAL`이다.
- 현행 `submit_draft(draft_path, preview?, wait_seconds?)`와 CLI `--output/--submit/--preview/--wait-seconds`를 대조했다. 최종 제출은 `draft_path`만 보내고 중앙이 바이트를 한 번 포착해 검사·봉인한다. 로컬 `producer_check`와 preview는 선택적 진단이며 상태는 각각 `check.passed`, `delivery.state=previewed`, 최종 접수는 `delivery.state=accepted`다. 관리 파일은 `.control/` 아래 있고 봉인 없는 provider final은 편입하지 않는다. `PublicGitFlow`는 실제 Windows Job으로 시작·종료를 확인한다. FLOW 결과의 85개 중 84개 통과·symlink 1개 skip과 선택 compile 통과는 이 집중 범위의 증거이며 전체 공개 흐름은 아직 미검증이다.

문서의 JSON 문법·실제 검사기 대조와 링크 확인은 제품 공개 활성화, 실제 AI·Lean 환경, 연구 효능의 검증과 구별한다. 상세 근거와 수정 문서 해시는 `임시/do-math-implementation-20260920/results/DOC_REBUILD.json`에 남긴다.

## 현재 판정

기능 판본 5 전체는 `PARTIAL`이다. FLOW·IMPACT·EXECUTION 담당은 각자의 최종 결과를 `complete`로 반환했지만, 그 판정은 각 소유 범위의 구현과 집중 검증에 한정된다. 소유 모듈과 중앙 실행기의 주요 연결은 구현됐어도, 현재 판본 전체를 동결한 공개 초기화→활성화→연구→검토→적용→다음 계획 흐름과 전체 회귀는 끝나지 않았다. 실제 연구 효능도 평가하지 않았다.

설계 D10의 계약 가족은 영속 기록 `do-math-state/5`, 역할 응답 `do-math-cli/5`로 유지한다. 최신 저장 의미는 schema 2의 손실 없는 단일 원문 표현으로 합의됐으며, 통합 코드·manifest·기존 schema 1 자료의 명시적 호환 또는 거부가 같은 판본에서 확인되기 전에는 전환 완료로 쓰지 않는다. v9 draft 규범 묶음은 별도 설계 명세이며 실행 기록과 혼용하지 않는다.

D08은 남아 있다. v9 규범 묶음의 최신 `validation-report.json`과 오프라인 검사는 그 보고가 고정한 본문·생성물·예제·벡터 대응 범위를 통과했다. 이는 판본 5 실행기의 실제 schema·generator·관계 검사·역할 입력·소비자, V237~V254와 Q23~Q25, 공개 CLI와 실호스트 능력을 전건 검증한 결과가 아니다. D09의 실제 연구 효과·비용 비교도 `not_evaluated`다.

## 실행 증거의 범위

현재 주요 증거는 다음처럼 읽는다.

- `ENGINE`: 고정 사본의 재설계 시험 19건이 통과했다. 실제 임시 Git에서 초기화·저장·읽기와 권한 없는 run 경계를 사용했지만 공급자·Lean·실예약 작업은 대역 또는 미실행이다. 별도 44건 실행은 40건 통과·4건 오류를 보존한다. 최종 현행 소스 전체의 공개 흐름 증거는 아니다.
- `CORE_TESTS`: 여러 이관 시험은 통과했지만 공개 초기화 흐름은 150초와 600초 실행에서 timeout이었다. 31개 선택 사례는 실행됐으나 163개 전체를 대표하지 않는다. timeout을 성공이나 확정된 기능 결함으로 바꾸지 않는다.
- `LIFECYCLE`: 소유 고정 사본 84건은 통과했다. 당시 공개 활성화 시험 두 건은 `queue.model_selection` 저장 schema에서 오류였고, 이 필드는 이후 별도 현행 검사에서 통과했다. `execution.input_preparation` 접점과 최종 공개 재실행이 남아 있다.
- `REVIEWS`: 소유 시험 73건과 여섯 검토 경계 시나리오는 통과했다. 실제 초기화에서 검토 발동까지 간 진단은 90초에 끝나 중앙 공개 완주는 입증하지 못했다.
- `GOVERNANCE`: 소유 범위 78건은 통과했다. 일반 종류의 사례 위임, 정확한 원결정·승인·원천, 두 독립 범위 판단을 검사했지만 한 장시간 사례는 판정 없이 중지됐고 공개 Git 전체 흐름은 미완료다.
- `PROFILES`: 프로필·input seal·기계 도구·공급자 관찰·모델 없는 감독과 실패 복구의 소유 시험이 통과한 범위가 있다. 공개 초기화 두 건은 당시 registry 불일치로 오류였고, 실제 모델 호출·예약 등록·live 수리는 실행하지 않았다.
- `CONTRACTS`: 최신 고정 사본에서 재설계 49건과 제출 경계·도구·계약 검사 묶음이 통과했다. 실제 로컬 IPC·임시 Git을 쓴 범위가 있지만 중앙 검사 이력 사건과 snapshot 보고의 마지막 소비는 남아 있다.
- `STORAGE`: 현재 결과는 `PARTIAL`이다. 여러 실제 임시 Git·경로·CAS 시험 묶음이 통과했지만 최종 생산자 delta와 공개 활성화의 동결 검증은 결과 작성 시점에도 진행 중이었다.
- `KNOWLEDGE`: 실제 portable Lean와 제한된 Mathlib 모듈 compile 증거가 있다. 기본 Lake의 전체 `import Mathlib`은 제한 시간 안에 끝나지 않았고, 공개 전체 지식 흐름은 미검증이다.
- `EVIDENCE`: 고정 사본 32건 중 29건 통과·3건 실패다. 워크스루 열 개는 지정 도메인 범위에서 통과했고 두 개는 실제 다음 소비자 결함에서 실패했다. 대응표에는 59개 gap과 186개 partial이 남아 있다.
- 설치 구조의 `probe_cli.py --skill-only` 통과는 역할 문서·정적/동적 schema 구조만 확인한다. 제품 실행, 문서 의미, 연구 품질, Lean·공급자·Windows 능력의 통과가 아니다.

시험 이름이나 파일 존재만으로 지원을 기록하지 않는다. 같은 시험이 여러 요구를 입증할 수 있고 한 요구에 여러 증거가 필요할 수 있다. 고정 사본과 계속 바뀐 원본, 단위·대역·임시 Git·실호스트, 과거와 현행 판본을 각각 구별한다.

## 역사 증거와 경계

2026-09-14 기능 판본 2의 [구현 검증](구현-검증-2026-09-14/feature2/)과 2026-09-15 [문서 검증 기록](문서-검증-2026-09-15/README.md)은 당시 동결 소스와 사례에만 상대적이다. 이후 판본의 통과로 이동하지 않는다.

무인 수리의 기존 승인 목적은 유지한다. 사용자가 승인한 연구의 의미와 권한을 바꾸지 않고 설치·도구 결함만 복구한다. 역할 지침, 별도 작업 공간, 동료 결과 비공개와 Windows Job은 행동·입력·로컬 프로세스 수명의 경계다. 모든 host 파일·network·credential 접근을 차단하는 OS 격리나 동일 사용자 호출자의 강한 인증으로 표현하지 않는다.

## 완료 조건

기능 판본 5를 완료로 바꾸려면 다음이 모두 필요하다.

1. schema 2의 원문·이름 보존과 생산자·닫힌 저장 schema의 남은 접점을 합의하고 전체 공개 init→active→prepare→review→plan→work→assessment→next-plan을 동결 소스에서 완주한다.
2. 제출 검사 이력·snapshot 보고, 입력 초과, 검토 입장·대화 복구, 운영 수리와 설치 복구의 실제 중앙 소비를 회귀로 확인한다.
3. 관련 전체 회귀와 설치 구조 검사를 같은 판본에서 실행하고, 필요한 실제 Lean·Windows Job·프로세스·provider 경로를 대역과 구별한다.
4. EVIDENCE의 실패·gap·partial을 실제 구현과 직접 assertion이 생긴 범위에서만 갱신한다. 실제 연구 효능은 별도 D09 평가로 남긴다.
5. `.claude` 정본을 설치 사본에 동기화하고 문서·코드·manifest 해시가 같은 판본인지 확인한다.
6. 메인의 전체 독립 독해와 최종 보고서 합의 대조를 통과한다.

## 최종 통합 결과를 붙일 자리
