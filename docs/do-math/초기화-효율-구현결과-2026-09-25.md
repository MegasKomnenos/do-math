# do-math 초기화 효율 개선 구현·검증 기록

신뢰 환경의 범위는 유지했다. 이번 변경은 `.claude/skills/do-math/` 정본에서 등록·파일 관측·적용·저장·역할 입력·실행 복구를 함께 고친다. 생성본의 다섯 임시 변경은 정본으로 옮겨 검토했다. 과거에 계측하지 않은 단계의 시간을 역산해 확정하지 않는다.

## 작업별 결과와 영향 범위

| 작업 | 구현과 판단 | 주요 영향 영역 |
|---|---|---|
| 1. 시작·정비·복구 | 시작 전에 실행·프로필·owner PID/FILETIME·Job 이름을 기록한다. 이름 충돌은 기존 Job에 붙지 않고 거부한다. owner와 Job의 종료를 확인한 뒤 용량을 반환한다. 공개 quiesce/release-quiesce와 감독기의 fence 확인을 추가했다. | launch, windows_job, session_slots, model_runner, formal, scheduler, scheduled_operator, engine, CLI, 실행·정비 스키마 |
| 2. 전체 환경 처리 | 파일 범위 그대로 스트리밍 해시, worker 4개, in-flight 최대 8개, 프로세스당 동시 전체 스캔 1개. 취소와 읽는 동안의 변경·실제 경로 중복을 확인한다. | trust_validation, initialization, lifecycle_engine, 환경·실행 프로필 |
| 3. 중복 관측 제거 | 등록과 전환 접수는 구조 검사, 활성화는 전체 파일 관측 후 적용으로 구분했다. 활성화 이후 단순 관문 조회에서 같은 전수 읽기를 반복하지 않는다. 형식 계산과 중요한 결과 편입의 독립 관측은 유지한다. CLI 기능 관측은 공급자뿐 아니라 실제 도구·어댑터 조합으로 묶고 각 프로필의 증거를 따로 검사한다. | initialization, lifecycle_engine, execution_profiles, Codex/Claude 어댑터 |
| 4. 검사 실행 분리 | 별도 서비스는 만들지 않았다. 기존 ModelCalls가 계산을 맡고 중앙 writer가 결과를 적용한다. 제출물 편입은 환경 관측 대기로 보존한 뒤 같은 봉인 제출물로 재시도한다. 별도 서비스의 IPC·인증·복구·배포 복잡도를 늘릴 실익이 없었다. | parallel, environment_checks, scheduler, integration, review_engine, governance_engine |
| 5. 저장·조회·입력 | 큰 불변 manifest와 문자열은 내용 주소형 payload로 한 번 저장한다. 논리 레코드와 물리 바이트의 출처를 구별한다. 검증한 부모는 OID·계약·검증기 판본으로 재사용한다. 큰 과거 제어 원문은 참조 목록 생성 전에 상세 파일로 옮긴다. | payloads, repository, state_contract, context_store, submission, 조회 출처 |
| 6. 계측 | 초기화, 실행기 시작, 제어 처리, 역할 입력, 입력 복사, 상태 읽기·검증·직렬화·공개, capability 관측, 모델 실행, callback 대기, 파일 관측을 span으로 기록한다. 실행기 시작과 자식 실행 로그는 operation ID로 연결한다. | operation_trace, engine, scheduled_operator, repository, git_store, context_store, 어댑터, reporting, CLI |

새 manifest 작성 전용 CLI는 추가하지 않았다. 기존의 정확한 범위·원문을 재사용하면서 중복 인코딩과 재검사를 제거하는 것이 이번 병목에 직접 효과가 있었다. 목록 작성기를 하나 더 유지하는 것은 이 효과를 늘리지 않는다.

## 임시 수리 검토에서 바뀐 부분

- 참조 목록을 한 번 구성해 조회하는 변경은 유지했다. 현재 원문 참조·alias 판단을 보존하는 차등 검사와 관련 회귀 검사를 적용했다.
- 파일마다 전체 `read_bytes()`를 제출하는 8-thread 변경은 최종안으로 삼지 않았다. 스트리밍과 제한된 대기열, 취소, 안정성 관측까지 함께 구현했다.
- 공급자 이름만으로 관측을 묶는 방식은 도구가 다른 프로필을 혼동할 수 있어 실제 어댑터·도구 정체성까지 결박했다.
- 시작 정보가 없으면 실행되지 않았다고 추측하는 복구는 채택하지 않았다. 공개된 launch ticket, 정확한 owner 관측, 실제 시작 실패 영수증을 사용한다.
- 최종 검토에서 컴파일 후 환경 확인이 중앙 스레드에 남아 있음을 발견했다. 이 검사를 없애지 않고 worker로 옮겼다. 컴파일 전후 전체 범위의 확인과 중앙의 현재 권한·환경 판본 대조를 모두 유지한다. 환경 실패는 수학 풀이 실패와 구별해 trust_governance에서 명시적 recheck를 기다린다.

## 검증·배포 기록

안정된 판본의 기본 검사와 이후 변경의 영향 검사 결과를 각각 보존했다. 테스트 ID별 최신 유효 결과는 **671개 통과, 1개 생략, 미해결 실패 0개**다. 전체 저장소 테스트를 한 번에 동일 판본으로 실행했다는 의미는 아니다. 실패한 테스트 결과와 도중 소스가 바뀐 실행을 통과 건수에 넣지 않았으며, 중간 실패는 수정 후 해당 테스트를 재실행했다. `validation-summary.json`에 개별 결과, 마지막 실행 묶음, 원 보고서 해시를 기록했다.

검증은 실제 Windows Job 수명·이름 충돌·owner 종료, 실제 Lean, Git CAS·payload 원문·검증기 판본 변경, 공개 CLI, 정지·권한 철회, 봉인 제출물의 비동기 편입을 포함한다. 심볼릭 링크 생성 권한이 필요한 Windows 검사 1개는 생략됐다. 모델 응답은 테스트 대역이며 이번 구현 검증에서 실제 모델을 추가 호출하지 않았다.

새 검사기와 기존 Lake/Lean 명령으로 `setup_lean.py --verify-only`를 실행해 `import Mathlib` 검증도 통과했다. 다운로드나 연구 환경 채택은 수행하지 않는 명령이다. 결과와 원문 근거는 `environment-verification.json`, `environment-verification/`에 보존했다.

graphify는 변경 전 영향 지도와 원문 확인에 사용했다. 그래프는 사용자의 갱신 요청 없이 재생성하지 않았다. 변경 이후에는 과거 그래프를 현재 코드의 증거로 취급하지 않는다.

기존 연구 인스턴스 `RI-01M3AB8E1KYF02E3T0G7BFEVAC`에는 operator 출처의 공개 pause를 제출하고 자동 재시작 예약을 제거했다. 이전 설치 231개 파일은 해시 대조 후 `preserved-installation/do-math/`에 보존했다. 연구 snapshot `6abb6ed150a65f8c6de41326e991894206372fb4`는 paused이며, 모든 실행은 ended, 활성 실행 목록은 비어 있다. 기존 연구 실행기의 종료 및 writer lock 해제를 확인한 뒤 생성본을 갱신했다. 별도 고정 판본의 bootstrap 프로세스도 이후 종료된 것을 확인했다. 근거는 `old-research-maintenance-complete.json`, `old-research-process-exit.json`, `old-research-schedule-removal.json`이다.

이 기존 연구는 현재 정지·보존 상태다. 새 저장 계약으로 자동 이관하지 않았다. 과거 기록은 보존한 판본으로 읽어야 하며, 재개 시에는 해당 판본의 프로필·검사기 경로·신뢰 환경을 공개 절차로 다시 결박해야 한다. 수학 목표가 완료됐다는 보고는 아니다.

정본에서 `.agents` 생성본을 다시 만들고 드리프트·설치 구조를 확인했다. 생성본의 별도 폐기 가능한 인스턴스에서 init → quiesce → status → release-quiesce → close가 모두 종료 코드 0으로 통과했다. 원래 연구의 상태를 바꿔 smoke test로 사용하지 않았다. 최종 생성본 결과는 `mirror-smoke-final/summary.json`에 있다.
