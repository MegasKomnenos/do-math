## 1. 파일 메타데이터 지문 (S1)

**정본**: `do_math/file_io.py`

- `stat_fingerprint(st)`는 `(st_size, st_mtime_ns, st_birthtime_ns)`를 돌려준다. `os.stat`, `os.fstat`, `os.DirEntry.stat(follow_symlinks=False)`의 결과를 모두 받는다. 값 구성은 설계 3.2의 지문 정의와 같다. Windows에서 `DirEntry.stat()`의 `st_ino`는 0이므로 파일 ID는 넣지 않고, 생성 시각이 그 역할을 대신한다.
- `file_fingerprint(path)`는 `stat_fingerprint(os.stat(path))`다.
- `fingerprint_json(fp)`는 지문의 저장 형식 `[크기, "수정 시각 ns", "생성 시각 ns"]`를 돌려준다. 나노초 시각은 `canonical_json`의 안전 정수 한도(2^53)를 넘으므로 문자열로 둔다. 지문을 JSON에 기록하거나 기록된 지문과 대조하는 곳은 모두 이 함수를 쓴다. 툴체인 기록, 동결 사본 manifest(R41), 정리 표지(R43)가 여기에 해당한다.
- 한계: NTFS 터널링 때문에 같은 이름을 지우고 약 15초 안에 다시 만들면 생성 시각이 보존된다. 그래서 크기와 수정 시각까지 보존한 교체는 지문으로 잡히지 않는다(G1 실측).
- `fingerprint_settled(fp)`는 지문의 수정 시각과 생성 시각이 모두 `RACY_NS`(2초)보다 오래됐을 때 참이다. Windows 파일 시각은 약 15.6ms 단위로 움직인다. 그래서 읽은 직후 같은 크기로 다시 쓰면 지문이 같게 남을 수 있다(racy-git 문제). 지문이 같다는 이유로 내용 읽기를 건너뛰거나 캐시를 재사용하는 곳은, 기준으로 삼은 지문이 정착(settled)했을 때만 그렇게 한다. `cached_sha256`은 이 규칙을 이미 적용한다.

**규칙**:

- 파일이 바뀌었는지를 메타데이터로 판정하는 모든 새 코드는 이 두 함수를 쓴다. `(st_size, st_mtime_ns)` 같은 튜플을 모듈 안에서 따로 만들지 않는다.
- 기존의 로컬 stat 서명은 각 소유자가 자기 범위를 고칠 때 이 함수로 교체한다. `context_store.py:88`(R24, 읽는 도중 변경 감지)은 G3, `observations.py:446`(R15)은 G4, `trust_validation.py:136`은 G1이 교체한다. G1은 이 함수를 삭제하는 경우 교체하지 않아도 된다.
- G1의 `.olean` 지문 행은 `(상대 경로, *stat_fingerprint(entry.stat(follow_symlinks=False)))`로 만든다. 다이제스트 규칙(정렬, `canonical_json`, SHA-256)은 설계 3.2를 따른다.
- 지문이 같으면 내용도 같다고 보는 것은 D1(우발적 변경만 다룸)에서만 성립하는 판정이다. 이 한계는 설계 10절에 공개돼 있다. 한계를 명시하는 시험은 커널의 `test_file_io.FingerprintTests`에 있다.

## 2. 전 바이트 해시 (S2)

**정본**: `do_math/file_io.py`

- `sha256_file(path)`: 파일 전 바이트의 SHA-256(1MiB 단위 스트리밍, `shared_reader` 사용)
- `cached_sha256(path)`: 지문이 바뀐 경우에만 다시 계산하는 SHA-256. 프로세스 전역 캐시이고, 키는 정규화한 절대경로다. 읽는 도중 파일이 바뀌면 캐시에 넣지 않는다.

**어느 쪽을 쓰는가**:

- **`cached_sha256`**: 사용 경로에서 바뀔 수 있는 파일의 식별값을 반복해서 얻는 곳. 다음이 해당한다.
  - G4: 설치본(R1·R2·R34·R42), CLI 실행 파일(R21·R22), 동결 사본(R41)
  - G1: 판본 식별의 실행 파일(`lean.exe`, `lake.exe`와 인자의 `.exe`·`.dll`), `lean-toolchain`, `lake-manifest.json`, lakefile, 검사기 `formal.py`
- **`sha256_file`**: 설계가 새 내용 확인을 명시한 곳. 다음이 해당한다.
  - `setup_lean.py`의 설치 기준, `--rerecord`, `--check-contents`의 내용 해시
  - `check` 명령(R40)
  - 사건 때 기준을 처음 만드는 곳
- 메모리에 있는 바이트는 지금처럼 `hashlib.sha256(raw).hexdigest()`로 해시한다.

**규칙**:

- 파일 해시 도우미를 모듈 안에 새로 만들지 않는다.
- 기존의 로컬 파일 해시 도우미는 각 소유자가 자기 범위를 고칠 때 위 두 함수로 교체한다. `codex_adapter._file_sha256`은 G4 소유다. `formal._file_hash`는 1MiB마다 취소 콜백을 부르는데, G1 소유다.
- 해시 도중 취소가 필요한 큰 파일은 G1의 `setup_lean.py` 경로뿐이다. 그 경로는 G1이 판단한다.

### 2.1 JSON 값의 digest

JSON 값의 digest는 두 정본만 쓴다. 통합 단계 G5가 기존 복제 도우미를 모두 이 두 정본으로 바꿨다.

- **상태 저장 값**(연구 상태에 들어가는 값)의 식별: `repository.exact_content_hash(value)`. 이 함수는 `sha256(canonical_json(value))`이며, 들여쓰기 판이고 저장 값 영역을 검사한다.
- **저장 값 영역 밖의 JSON**(소수가 들어 있는 공급자 응답, transport 파일 등): `file_io.json_digest(value)`. 이 함수는 압축 JSON에 `allow_nan=False`를 적용한 SHA-256이다. `repository`가 아니라 `file_io`에 둔 이유는 두 가지다. 첫째, worker 쪽 모듈(`control_transport`, `claude_stream`)이 Windows Job 안에서 패키지 없이 직접 적재되기 때문이다. 둘째, worker 능력 식별의 파일 범위가 `control_transport`와 `file_io`이기 때문이다.
- 모듈 안에 `_digest`·`_hash`·`digest` 같은 도우미를 새로 만들지 않는다. 바이트 해시는 `hashlib.sha256(raw).hexdigest()`로 직접 쓴다.
- 두 정본과 바이트가 다른 기존 변종은 값이 저장되고 다시 대조되므로 규칙을 바꾸지 않았다. 해당하는 것은 다음과 같다.
  - `formal`의 ASCII 이스케이프 3곳
  - `scheduled_operator`의 기본 구분자 2곳. 실패 하나당 자동 복구를 한 번으로 제한하는 데 쓴다.
  - `observations` 규칙 digest. 모듈의 `_raw_json`으로 통일했다.

  이 변종들의 직렬화 규칙을 바꾸면 저장된 digest와 비교가 어긋난다.
- `request_sha256`은 transport 영수증과 엔진 control 영수증에서 서로 다른 값을 가리킨다. 그러나 두 값을 서로 비교하는 곳이 없으므로 이름은 가르지 않았다(G5 판정).

## 3. 검증된 불변 artifact (S3)

**정본**: `do_math/repository.py`

- `VERIFIED_ARTIFACTS`: 이 프로세스가 저장된 바이트를 이미 대조한 artifact 행을 담는다. 형태는 `(git 디렉터리, artifact 경로, sha256)` 키에서 대조한 바이트 길이로 가는 dict다. `artifact_verified(git_dir, path, sha256, size=None)`는 `size`가 주어지면 길이까지 같아야 참을 돌려준다. 이 형태는 G3가 확정했다. 크기를 선언한 증거 행이 크기 대조를 잃지 않게 하려는 것이다. 이미 대조가 성립한 행을 기록하는 도우미는 통합 단계에서 `mark_artifact_verified(git_dir, path, sha256, size)` 하나로 둔다. `payloads.decode`와 `_remember_published`가 키를 직접 조립하던 부분도 이 도우미로 바꾼다. 기존 artifact 번들은 바뀌지 않으므로(`git_store.py`의 번들 불변 검사, 현 396-397행) 한 번 대조한 행은 프로세스가 끝날 때까지 유효하다. 저장소가 다르면 같은 경로라도 별개로 다룬다.
- `verify_artifact(git_dir, path, raw, sha256, size=None)`: 바이트가 봉인 행과 다르면 `ValueError`를 낸다. 같으면 행을 집합에 넣는다.
- `artifact_verified(git_dir, path, sha256)`: 이미 대조했는가를 돌려준다.
- `ResearchRepository.git_dir`: 키에 쓰는 저장소 식별이다. 엔진에서는 `self.store.git_dir`로 얻는다.
- `sealed_bytes(git_dir, path, sha256, size, read, *, raw, needed, error)`: 아래 소비 규칙("이미 대조했으면 생략, 아니면 대조")의 정본이다. 호출자는 이 함수를 부르고 규칙을 다시 구현하지 않는다. 메모 키는 `artifact_key(git_dir, path, sha256)`가 만든다(2라운드).

**규칙**:

- G3는 `_validate_artifact_evidence`(R4)와 `payloads.decode`의 바이트 대조(R8)를 이 집합으로 바꾼다. 부모 head의 검증 집합을 따로 승계하는 구조를 새로 만들지 않는다. 이 집합이 곧 승계다. 후보 검증(`_validate_candidate`)에서 대조한 행도 넣는다. 그 결과, 실행기가 기동 때 읽은 head와 자기가 게시한 head가 참조하는 모든 행이 집합에 들어 있게 된다.
- G4는 artifact 바이트를 git에서 다시 읽어 해시를 비교하던 지점(R25 `planning.artifact_valid`, R29·R30·R44)에서 다음 순서를 따른다. `artifact_verified`가 참이면 해시를 비교하지 않는다. 바이트 자체가 필요한 곳(문맥 구성, 형식 검사)은 바이트를 읽되 해시하지 않는다. 거짓이면 `verify_artifact`로 한 번 대조한다. 로컬 `hashlib` 비교나 별도 캐시를 만들지 않는다.
- R25의 형식 검사(`validate_artifact`) 결과를 메모이즈해야 하면 키는 `(git_dir, path, sha256)`로 같게 둔다.
- 상태 기록끼리의 대조(기록한 봉인 해시 == 참조 행의 해시)는 식별이므로 유지한다.

## 4. 상태 판본 키와 head 이동 (S4)

- **head 키 메모이즈**: 게시된 상태에서 계산한 파생값은 `self.head`(커밋 ID)를 키로 메모이즈할 수 있다. head가 같으면 게시된 상태 전체가 같기 때문이다. 해당하는 것은 G1의 R26, G2의 R27이고, 다른 범주에서도 같은 필요가 있으면 이 규칙을 따른다.
- **메모리 상태에는 head 키를 쓰지 않는다**: 저장되지 않은 메모리 상의 변경을 읽는 계산은 `self.head`로 메모이즈하지 않는다. 엔진은 게시 전에 `self.instance`·`self.runtime`을 직접 고치므로, head가 같아도 메모리 상태는 다를 수 있다. 메모리 상태를 읽는 계산을 메모이즈해야 하면 입력값 자체를 키로 쓴다. 예를 들어 `lean_code` 해시는 `lean_code` 문자열로 캐시한다.
- **head 이동 훅의 소유**: head가 움직이는 곳은 다음과 같다(좌표는 기준 커밋).
  - `engine.py:891`(`_save`)
  - `engine.py:2313`(묶음 게시)
  - `engine.py:1331` 부근(재적재)
  - `lifecycle_engine.py:602`(거부 후보 보존)
  - 밖에서 온 head의 채택

  이 지점들에 부착하는 게시 직후 처리는 G2의 정지 사유 평가 하나다. G2는 모든 head 이동 지점이 한 평가 함수를 지나게 한다. G1과 G3는 이 지점들에 자기 훅을 추가하지 않는다. head 키 메모이즈는 키가 바뀌면 자동으로 무효화되므로 훅이 필요 없다.
- **R3 캐시 채우기의 위치**: G3는 R3의 캐시 채우기를 `repository.save_with_state` 안(저장소 층)에서 한다. `engine._save`에서 하지 않는다.
- **변경 세대 카운터(R12)**: G3가 구현한다면 이름은 `self._state_generation`이고, 쓰는 곳은 `_save`의 무변경 판정뿐이다. 다른 범주는 이 카운터에 의존하지 않는다.

## 5. 취소 콜백 (S5)

계산 함수가 받는 취소 콜백의 호출 형태는 인자 없는 callable로 유지한다(G2 소유). 계산 쪽 코드는 `should_stop()`·`stop()`을 지금처럼 부른다.

G2의 신뢰 환경 동등성 사유는 지금처럼 판정한다. 인스턴스의 `active_trust_environment` ID가 같고, 해당 환경 기록 dict도 같은지를 비교한다. G2는 G1의 새 기록 형태나 함수에 의존하지 않는다. G1은 기록 형태를 바꾸더라도 `instance["active_trust_environment"]`와 `instance["trust_environments"][id]`의 위치를 유지한다. 위치를 바꿔야 하면 반환에 적는다.

## 6. 신뢰 환경 기록과 시험 픽스처 (S6)

- 인스턴스 신뢰 환경 기록과 툴체인 기록의 형태는 G1만 정의한다.
- G2·G3·G4의 시험에서 신뢰 환경이 필요하면 `tests/research_fixtures.py`의 `trust_fixture()`·`validation_fixture()`만 호출한다. manifest나 `files` 목록을 시험 안에서 직접 만들지 않는다. G1이 픽스처를 새 형태로 바꾸면 병합 뒤 그대로 통과하게 하려는 규칙이다.
- G1은 픽스처의 호출 시그니처(인자 이름)를 가능한 한 유지한다. 바꾸면 반환에 적는다.

## 7. 용어와 이름 (S7)

- **지문(fingerprint)**: 새 코드에서 식별자 `fingerprint`는 1절의 메타데이터 지문에만 쓴다.
- 같은 낱말을 다른 뜻으로 쓰는 기존 식별자는 소유자가 정리한다.
  - `formal.project_fingerprint` → `project_source_identity`, 툴체인 기록의 `project.fingerprint` → `project.source_identity`: G1(설계 6절)
  - `payloads.fingerprint`(값 투영, `engine._state_signature`만 사용): G3. R12로 사용처가 없어지면 삭제하고, 남으면 뜻에 맞는 이름으로 바꾼다.
  - `repair_execution.installation_fingerprint`(전체 SHA-256): G4. R42 처리 때 실제 뜻에 맞게 이름을 바꾸거나 R1의 설치본 식별로 대체한다.
- **GLOSSARY의 "지문"·"툴체인 기록"·"판본 식별" 항목**은 G1이 쓴다. 다른 범주의 문서는 이 용어를 GLOSSARY 정의로 가리키고, 재정의하지 않는다.
- **새 설정 키, 사건 종류, 상태 필드, CLI 인자**를 추가할 때는 같은 뜻의 기존 이름이 있는지 grep으로 먼저 확인한다. 추가한 것은 모두 반환의 `추가한 이름` 항목에 적는다.

## 9. 커밋 전 자기 점검 (S9)

각 범주는 커밋 전에 자기 diff(`git diff do-math-check-kernel`)에서 다음을 확인한다. 통합 책임자는 병합 때 같은 검사를 전체에 다시 한다.

1. `def .*(sha256|_hash|digest)`로 새로 추가한 파일 해시 도우미가 있는가. 있으면 2절의 함수로 바꾼다.
2. `st_mtime_ns|st_size`로 1절 밖의 새 stat 튜플이 있는가. 있으면 1절의 함수로 바꾼다.
3. `hashlib.sha256(` 옆에 git artifact를 읽는 코드가 있는가. 있으면 3절을 따른다.
4. `_cache|cache =|lru_cache`로 새로 만든 캐시가 있는가. 있으면 키와 무효화 조건이 2~4절과 겹치지 않는지 확인한다.
