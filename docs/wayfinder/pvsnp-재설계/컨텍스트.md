# 컨텍스트 정본 — wayfinder 지도 「P vs NP 연구 체계 재설계」

## 0. 이 문서의 지위

이 문서는 wayfinder 지도 [「P vs NP 연구 체계 재설계」](https://github.com/MegasKomnenos/math/issues/6)의 현행 컨텍스트 정본이다. 지도 아래의 어느 티켓을 수행하든 착수 전에 전문을 읽는다.

이 문서에는 현재 공유 결정, 사실과 소유권만 둔다. 결정 경위, 대체된 설계와 세션별 논의는 Git 이력, 티켓 해결 댓글과 handoff에 둔다. 현재 문면과 과거 기록이 다르면 현재 문면을 적용하되, 중요한 판단은 연결된 원자료를 다시 읽어 대조한다.

같은 티켓을 이어가는 세션은 결정마다 이 문서와 루트 `CONTEXT.md`를 고치지 않는다. handoff, 티켓 종료나 사용자가 명시한 정본 동기화 시점에 그 세션의 확정 결정을 원자료와 대조해 한 번에 반영한다. 새 결정이 대체한 문면과 중복을 함께 제거한다.

루트 `CONTEXT.md`는 구현 세부를 제외한 보편 도메인 용어를 소유한다. 이 문서는 P vs NP 재설계의 구체 운전 계약과 티켓 사이의 소유권을 소유한다. 열린 작업의 정본은 GitHub 하위 이슈와 차단 관계다.

## 1. 목적, 산출물과 범위

이 지도의 종착은 P vs NP 연구 체계를 재설계하고 보편 수학 연구 스킬 `do-math`를 구현·검증해 실제 연구를 시작할 수 있는 상태다.

이 지도는 `do-math` 설계·구현·검증을 실행 범위에 포함한다. 실제 문헌 수집, Lean 연구 정본 구축과 P vs NP 증명·반증 시도는 범위 밖이다.

## 2. 연구의 근본 모형

### 2.1 인증 수학 영역, 가시 연구 프런티어와 미지 지평

`do-math`는 인증 수학 영역 `K`, 가시 연구 프런티어 `F`와 미지 지평 `U`를 구별한다.

`K`는 매끈하게 닫힌 지식 덩어리가 아니라 여러 분야와 추상 수준에서 구멍이 있고 서로 다른 깊이의 프런티어를 가진다. 목표의 해결이 이미 `K`에 정확한 결과로 들어 있으면 목표와 그 결과의 동일성·충분성을 확인하면 된다. 그렇지 않으면 현재 `K`와 목표 사이에는 아직 어떤 경로로 건너야 할지 모르는 미지가 있다.

- `K`는 유효한 신뢰 시대에서 Lean 정본에 실제로 편입된 보존적 정의, 입증·반증 정리, 증명 항과 형식 관계의 명시적 집합이다. 아직 Lean 선언과 증명 항으로 보존하지 않은 논리적 귀결은 포함하지 않는다.
- `F`는 `K` 밖에서 질문, 가설, 정의 후보, 증명 후보, 연구 방향, 장애물과 부분 결과로 명시된 다층 연구 상태다. 객체 유형과 층위를 닫힌 목록으로 제한하지 않는다.
- `U`는 아직 후보나 작업으로 표현되지 않아 연구 체계가 직접 관리하거나 배분할 수 없는 가능성의 범위다.

탐색은 `U`의 일부를 명시적 후보로 만들어 `F`에 드러낸다. 이 전이는 가능성을 넓히지만 `K`를 넓히지 않는다. 집중 활용은 근거가 있는 `F` 후보를 입증·인증 가능한 결과까지 전진시킨다.

연구는 새로운 정의, 명제, 증명과 관계를 하나씩 만들고 검증해 `K`의 프런티어를 확장한다. `U`는 직접 열거할 수 없을 만큼 크므로 선택과 집중이 필요하지만, 현재 가장 좋아 보이는 방향만 반복하는 탐욕적 선택이 최적이라는 근거도 없다. 실제 결과를 다음 선택에 환류하며 탐색과 집중 활용을 함께 고려한다.

프런티어 확장은 새 Lean 정본 객체가 편입돼 `K`가 넓어지는 상태 변화다. 연구 진전은 현재 상태가 연구 헌장의 인증된 목표 해결에 더 유리해졌다는 목표 상대적 효과다. 작업 완료량, 문헌 수, 파일 수와 `K`의 크기는 연구 진전의 대리값이 아니다.

실패한 시도는 그 사실만으로 `K`를 넓히지 않는다. 실패에서 반례, 불가능성, 조건이나 범위 축소를 입증하면 그 정확한 결과를 새 정본 편입 후보로 만들 수 있다. 그 밖의 실패는 자료·근거와 공용 연구 기억에 보존해 후속 선택에 사용한다.

### 2.2 적응형 연구 포트폴리오 원리

연구 선택은 현재 근거가 있는 방향을 결과까지 전진시키는 집중 활용과, 보이지 않던 방향을 드러내는 탐색을 함께 고려한다. 탐색은 무작위 작업과 같지 않고 집중 활용은 최고 점수 후보 하나만 반복하는 탐욕적 선택과 같지 않다.

`do-math`는 고정 비율, 단일 점수나 고정 순위 규칙으로 포트폴리오를 결정하지 않는다. 고성능 AI 선택 세션이 충분한 맥락, `do-math`의 선택 계약, 도구와 과거 결과를 받아 넓은 재량으로 작업 집합을 고른다. 실제 결과는 다음 선택 회차의 입력이 된다.

선택 품질이 단조롭게 좋아진다고 보장하지 않는다. 설계 목표는 판단을 고정 규칙으로 대체하는 것이 아니라, 판단과 실제 결과의 반복 환류가 재량의 품질을 교정할 수 있게 하는 것이다.

### 2.3 F 객체와 Lean 정본 객체

F 객체와 Lean 정본 객체는 서로 다른 객체와 식별자를 가진다. F 객체가 Lean 정본 객체로 변환되거나 같은 ID를 공유하지 않는다.

새 Lean 정본 결과가 F 객체를 해결·반증·부분적으로 다루거나 생성의 출발점으로 사용했으면 별도 관계 기록으로 연결한다. 한 F 객체가 여러 Lean 정본 결과와 연결될 수 있고 하나의 Lean 정본 결과가 여러 F 객체에 영향을 줄 수 있다.

`F → K`는 객체 하나가 장소를 옮긴다는 뜻이 아니다. F에서 수행한 연구가 새 Lean 정본 객체를 만들고, 그 결과에 따라 관련 F 객체의 연구 상태가 바뀐다는 지식 상태 전이다.

## 3. Lean 정본, 수학 해설과 신뢰 경계

### 3.1 세 수학 영역과 Lean 정본

연구 작업공간, Lean 형식화 작업공간과 Lean 정본을 논리적으로 분리한다.

- 연구 작업공간은 아이디어, 질문, 문헌 판독, 실패, 목표와 연구 계획을 보존한다. 그 내용은 수학적 사실의 정본이 아니다.
- Lean 형식화 작업공간은 정본 편입 전의 Lean 정의, 명제, 관계, 증명 초안과 검사 자료를 보존한다. 기존 Lean 정본은 의존할 수 있지만 Lean 정본이 이 공간에만 있는 선언을 의존할 수는 없다.
- Lean 정본은 유효한 신뢰 시대에서 편입 관문을 통과한 형식 수학 내용만 보존한다.

주 수학 흐름은 다음 단방향을 따른다.

```text
연구 작업공간
→ 수학 해설 후보와 Lean 형식화 후보
→ 커널 검사·공리 감사
→ 해설–형식 동일성 인증
→ Lean 정본
```

작업별 작업대는 이 세 영역의 소유권을 바꾸는 네 번째 저장 영역이 아니다. 특정 공용 커밋의 관련 K 판본, 연구 자료와 Lean 후보를 한 작업 맥락에서 함께 다루는 격리 표면이다.

수학적 사실의 형식 정본은 Lean이다. 연구 목표와의 관련성이나 중요성이 아니라 수학적으로 타당하고 엄밀한지가 Lean 정본 편입의 보편 기준이다. 목표보다 좁거나 목표와 무관한 결과도 정확한 의미로 입증되면 편입할 수 있다.

Lean 정본은 승인된 기초 프로필, 보존적 정의, 입증·반증 정리와 정본 연결 정리로 구성한다. 미해결 명제를 공리로 넣지 않는다. 추가 가정 `H`가 필요하면 조건부 정리 `H → P`로 표현한다.

활성 기초 프로필은 하나다. 공리 허용 목록은 `{propext, Quot.sound, Classical.choice}`로 닫는다. `sorryAx`, `Lean.trustCompiler`, 사용자 정의 공리와 허용하지 않은 외부 공리는 금지한다. 큰 계산은 결과가 아니라 커널이 검사할 인증서를 생산한다.

### 3.2 형식 타당성과 해설–형식 동일성

형식 타당성은 정확한 신뢰 시대에서 Lean 커널과 공리 감사가 선언이나 증명 항을 받아들인 상태다. Lean 커널은 형식 표현 자체의 타당성을 통과 또는 거부로 기계 판정한다. 검토자와 심사자가 Lean 증명의 형식적 타당성을 다시 판정하지 않는다.

신뢰할 수 있는 환경에서 커널이 `p : P`를 받아들이면 `P`와 `p`의 타입·항에 실제로 표현된 관계는 타당하다. 자연어 설명, 선언 이름, 연구 관계와 외부 수학적 의도처럼 타입과 항 밖의 의미까지 보장하지는 않는다.

수학 해설은 정의, 명제와 증명을 사람이 읽는 자연어 수학으로 제시하는 연구의 주 산출물이다. 검토·심사 사슬의 대상은 수학 해설과 대응하는 Lean 형식 표현이 같은 수학적 의미를 담는다는 해설–형식 동일성이다.

연구 소유 Lean 후보는 커널 검사와 공리 감사를 통과하고 해설–형식 동일성을 인증받은 뒤 Lean 정본에 편입한다. 커널은 통과했지만 동일성 인증을 받지 못한 후보는 Lean 형식화 작업공간에 남는다.

나중에 동일성 결함을 발견해도 형식 타당성이 유지되는 Lean 객체는 자기 형식 문면의 의미로 유효할 수 있다. 잘못된 수학 해설과 동일성 인증을 철회하고, 영향을 받은 목표 관계와 학술 주장을 재평가한다.

Lean 객체를 조용히 최신 환경의 의미로 바꾸지 않는다. 기초 프로필·도구체인·Mathlib 변경과 기존 신뢰를 깨는 결함은 모두 명시적 새 신뢰 시대 또는 신뢰 무효화로 처리한다.

### 3.3 정본 편입 제안

정본 편입 제안은 수학 해설 후보, Lean 형식화 후보와 동일성 대응표를 같은 판본으로 고정한 최소한의 의존 폐쇄 변경 묶음이다.

수학 해설은 자연스러운 Markdown 산문으로 작성한다. 정의, 가정, 명제, 중요한 증명 단계와 범위에는 안정된 `math_item_id`를 붙인다. 동일성 대응표는 각 항목을 정확한 Lean 선언·증명 의무와 연결한다.

정의, 명제, 가정, 양화, 적용 범위와 결론은 전부 명시적으로 대응한다. 자연어 증명의 수학적으로 의미 있는 주장과 의존 결과는 이름 있는 Lean 보조정리나 명시적 형식 의무에 연결한다. 전술 호출, 커널 축약과 통상적인 형식 세부를 줄마다 번역하지 않는다.

수학 해설, 대응표 또는 Lean 후보 가운데 하나라도 바뀌면 새 제안 판본을 만든다. 검토가 시작된 판본은 수정하지 않는다. 같은 제안에 함께 있어야 의미가 완성되는 선언만 묶고 독립적으로 승인·수정할 수 있는 내용은 제안을 나눈다.

### 3.4 동일성 검토·심사 사슬

제안은 먼저 기계적인 Lean 빌드, 커널 검사, 공리 감사와 스키마·참조 검사를 통과해야 한다. 통과한 정확한 판본만 동일성 검토에 보낸다.

제안 판본마다 기본 검토자 셋을 서로 결과를 보지 않는 `gpt-5.6-sol max` 세션으로 배정한다. 논증 재구성 검토자는 자연어 논증이 Lean에서 형식화된 논증과 같은지 보고, 적대 검토자는 자연어가 Lean보다 넓거나 강한 주장과 숨은 가정을 찾으며, 의미 대응 검토자는 정의·명제·가정·증명의 항목별 동일성을 본다.

문헌에서 전사한 제안에는 원문 충실성 검토자를, 여러 전문 분야를 결합한 제안에는 필요한 분야 전문 검토자를 추가한다. 형식화와 공리 의존 자체는 기계 검사 대상이므로 별도 AI 형식화·공리 감사 검토자를 두지 않는다.

각 검토자는 제안 전건을 읽고 이의를 찾는다. 검토자 전원이 이의를 제기하지 않으면 제안을 승인한다. 하나라도 이의가 있으면 이의 전건을 심사자 셋에게 보낸다.

심사자 셋은 각각 이의 성립, 이의 반박과 문맥 대조를 주된 관점으로 삼지만 모든 이의를 판정한다. 각 심사자는 같은 회차의 다른 심사 결과를 보기 전에 정확한 이의 판본에 `승인` 또는 `기각`을 봉인한다. 심사자는 전달받은 이의만 판정하고 제안 전건에서 새 이의를 찾거나 제안을 승인하지 않는다.

세 심사자가 만장일치로 승인한 이의는 승인된 이의가 된다. 그렇지 않은 이의의 심사 결과와 사유는 원 검토자에게 돌아간다. 검토자는 피드백을 받아 이의를 철회하거나, 각 피드백에 답하고 수정 이의·분화한 이의·새 이의를 다시 보낸다. 같은 심사자들이 이전 피드백과 답변을 읽고 새 회차를 독립 심사한다.

모든 이의가 승인되거나 철회될 때까지 회차 제한 없이 이 루프를 계속한다. 검토 루프 전용 무진전·교착 상태나 최대 회차를 만들지 않는다. 세션·도구의 실제 중단은 일반 작업 실행의 체크포인트와 재개 절차로 처리한다.

승인된 이의가 없으면 제안을 승인한다. 승인된 이의가 하나라도 있으면 제안 작성자가 승인된 이의를 반영한 새 제안 판본을 만든다. 새 판본에는 새 검토단과 새 심사단을 배정하며 이전 판정은 승계하지 않는다.

부분 전문 검토자는 검토자와 심사자의 판단에 부족한 좁은 수학적 근거만 조사한다. 제안이나 이의를 승인·기각하지 않고 근거와 불확실성을 검토자에게 반환한다. 제안에 없는 새 정의·정리·증명을 만들어야 하면 인증 절차 안에서 대신 생산하지 않고 같은 연구 작업을 재개해 새 제안 판본을 만든다.

필수 입력을 읽지 못하거나 도구·세션 오류로 심사하지 못한 실행은 판정을 만들지 않고 심사 미완료로 기록한다. `승인·기각` 외의 세 번째 심사 판정으로 세지 않는다.

### 3.5 최종 편입과 목표 판정

동일성 검토·심사 사슬이 승인한 뒤 같은 해설·대응표·Lean 후보 해시를 깨끗한 환경에서 다시 빌드하고 커널 검사와 공리 감사를 최종 수행한다. 프로젝트별 추가 감사가 요구하는 판정도 수행한다. 검토한 판본과 편입할 판본이 다르면 승인을 사용할 수 없다.

인증은 Lean 정본 변경을 제안한 원 연구 작업의 종결 하위 절차다. 별도 작업 씨앗으로 만들지 않는다. 승인된 이의가 생기면 같은 `task_id`를 새 작업 실행으로 재개해 같은 worktree에서 제안을 수정한다. 최종 인증 결과는 원 연구 작업의 단 한 번의 종결 공용 편입에 포함한다.

Lean 정본 편입과 연구 헌장의 목표 해결은 별도 판정이다. 정확한 부분·조건부·제한 결과는 목표 해결 감사를 통과하지 않아도 Lean 정본에 편입할 수 있다. 목표 감사는 결과를 해답으로 부를 수 있는지와 연구 성공 상태만 통제한다.

## 4. 신뢰 시대와 외부 Lean 기반

신뢰 시대는 기초 프로필, Lean 커널·도구체인, Mathlib·형식 환경의 정확한 판본과 공리 허용 목록을 함께 고정한다. 형식 객체와 검사 기록은 정확한 신뢰 시대에 결박한다.

고정한 Mathlib 판본을 초기 Lean 정본 기반으로 수용한다. 소스에서 다시 빌드하고 수용 대상의 공리 의존과 `sorryAx`를 검사한다. Mathlib 전체는 한 번의 초기 기반 수용 대상으로 다루되, 연구가 외부 수학적 의미로 직접 주장하는 Mathlib 정의·정리는 최초 사용 시 별도 해설–형식 동일성을 인증한다. 내부 증명에만 쓰는 Mathlib 보조정리는 별도 자연어 주장을 만들지 않는다.

Complexitylib, DescriptiveComplexity와 그 밖의 전문 외부 라이브러리를 Lean 정본이 직접 의존하지 않고 영구 어댑터를 두지 않는다. 필요한 수학 내용은 연구 인스턴스가 소유하는 Lean 언어로 다시 작성한다. 형식화 작업공간에서 임시 참고·실험에 사용하는 것은 허용한다.

Lean, Mathlib, 기초 프로필이나 형식 환경을 바꾸면 새 신뢰 시대를 별도로 준비한다. 새 환경에서 Mathlib과 기존 Lean 정본 전건을 다시 빌드하고 선언별 타입·의존·공리·동일성 영향을 검사한다. 사용자 승인과 원자적 공용 변경으로만 새 시대를 활성화하며 두 시대를 동시에 활성화하지 않는다.

현재 커널 결함, 금지 공리나 환경 훼손처럼 기존 신뢰를 깨는 사실을 확인하면 신뢰 무효화 기록을 만들고 복구 전까지 관련 Lean 정본을 새 인증과 편입의 전제로 사용하지 않는다. 영향받는 실행 중 작업은 즉시 운영 점검으로 보낸다.

## 5. 연구 인스턴스의 내부 정본

### 5.1 프로젝트 입력의 일회성 수입

외부 프로젝트 입력은 연구 인스턴스를 초기화하는 일회성 재료다. 평시 연구 상태의 정본이나 지속 의존성이 아니다.

초기화는 입력의 의미 전건을 연구 헌장, 연구 정책, 연구 맥락, 연구 설정, 초기 F 객체, 자료·근거와 사용자 결정의 실제 소유자에 나누어 수입한다. 입력의 각 의미가 어느 내부 기록에 들어갔는지 수입 대응표로 검사한다. 누락, 중복 소유와 의미 변화가 있으면 인스턴스를 부분 생성하지 않는다.

연구 헌장은 연구를 시작한 이유, 핵심 목표, 원하는 결과, 성공 기준, 범위, 우선순위와 사용자 권한을 소유한다. 연구 정책은 인스턴스 전체의 규범과 검증 요구를, 연구 맥락은 고유 용어와 해석을, 연구 설정은 이미 확정된 경계 안의 모델·도구·운용 값을 소유한다.

공용 연구 기억은 출처, 정보 상태, 적용 범위와 효력이 명시된 경험과 교훈을 소유한다. 헌장·정책, Lean 정본, 사용자 결정이나 실제 자료를 대신하지 않는다.

초기화 뒤 평시 재개는 외부 프로젝트 입력을 다시 읽지 않는다. 외부 파일이 이동·변경·삭제돼도 같은 공용 커밋의 재개 결과가 바뀌지 않아야 한다. 입력 원문은 감사와 수입 오류 교정을 위한 불변 출처 자료로 내부 보존할 수 있지만 현행 의미의 의존성은 아니다.

후속 사용자 입력은 승인된 외부 변화 사건으로 수입해 내부 소유 기록의 새 판본을 만든다. 최초 입력 묶음을 수정하거나 외부 문서를 다시 현행 정본으로 삼지 않는다.

### 5.2 역할별 소유권

- 연구 헌장은 목적·목표·성공·범위와 최종 사용자 의도를 소유한다.
- 연구 정책은 프로젝트 전체의 규범과 권한 경계를 소유한다.
- 연구 맥락은 현행 용어와 외부 의미를 소유한다.
- 연구 설정은 모델 용량, 도구와 실행 환경 매개변수를 소유한다.
- Lean 정본은 형식 수학 내용을 소유한다.
- 수학 해설은 인증된 사람이 읽는 수학 결과를 소유한다.
- F는 미입증 후보와 연구 방향을 소유한다.
- 자료·근거는 문헌, 실험, 실패와 재현 자료를 소유한다.
- 작업 기록은 작업 씨앗과 연구 작업 계약을 소유한다.
- 사용자 결정과 전례는 사용자에게서 온 권한을 소유한다.
- 공용 연구 기억은 재사용할 경험과 교훈을 소유한다.

하나의 의미를 여러 정본이 공동 소유하지 않는다. 보편 연구 방법은 `do-math` 스킬이, 인스턴스 전체 규범은 연구 정책이, 작업 하나의 지시는 작업 계약이 소유한다. 별도 범용 지침 문서를 두지 않는다.

### 5.3 공용 브랜치와 저장 위치

연구 인스턴스마다 전용 공용 브랜치 `refs/heads/do-math/<instance_id>`를 둔다. 장기 상태는 그 브랜치의 `research/<instance_id>/` 아래에 둔다.

최상위 역할 디렉터리는 `charter`, `policy`, `context`, `settings`, `trust`, `lean`, `explanations`, `frontier`, `evidence`, `tasks`, `relations`, `integrations`, `decisions`, `precedents`, `memory`, `provenance`와 `reports`다. `instance.json`이 인스턴스 ID, 생명주기, 고정 `do-math` 판본, 최초 수입, 현행 헌장·설정·신뢰 시대와 저장 배치를 가리킨다.

핵심 기록 객체와 관계는 역할별 디렉터리에 독립 JSON 파일 하나로 둔다. JSON의 안정된 ID가 정체성이며 객체 판본은 `record_id + 공용 Git 커밋`으로 식별한다. 긴 산문, Lean 코드, 데이터와 증거는 별도 파일에 두고 JSON이 경로·미디어 형식·해시를 참조한다.

기계 JSON은 UTF-8, LF, 고정 들여쓰기, 결정론적 키 순서와 파일 끝 개행을 사용한다. 알 수 없는 필드와 자료형, 깨진 참조를 조용히 무시하지 않는다. 생성·검사는 `do-math`의 판본화된 도구가 수행한다.

메인 제어, 포트폴리오 선택, 작업 실행, 감시, 인증 진행과 프로세스 상태처럼 자주 변하거나 동시에 쓰이는 내용은 공용 머리에 넣지 않고 전용 Git ref와 불변 상태 커밋이 소유한다. 같은 Git 객체·ref 데이터베이스를 공유한다는 전제에서 원자적 조건부 갱신을 사용한다.

### 5.4 공용 변경의 영향 처분

공용 변경은 바뀐 의미, 근거·권한, 영향받는 기록과 작업별 처분을 기록한다. 영향 처분은 `영향 없음`, `다음 선택부터 적용`, `편입 전 재검증`, `즉시 운영 점검`으로 닫는다.

연구 작업은 착수할 때 고정한 공용 커밋을 사용하며 공용 머리 변경을 자동으로 자기 입력에 섞지 않는다. 목적·신뢰·권한이나 필수 입력을 깨는 변경만 즉시 작업을 멈춰 점검하고, 그 밖의 변경은 다음 선택이나 종결 재검증에서 반영한다.

영향 범위를 계산할 수 없으면 영향 없음으로 처리하지 않는다. 범위를 특정할 수 있으면 그 범위를 즉시 운영 점검으로 보내고, 범위 자체를 특정할 수 없으면 공용 변경 적용을 막는다.

## 6. 작업 기록, 작업 씨앗과 실행 껍질

### 6.1 작업 기록의 생명주기

작업 씨앗과 실제 연구 작업은 하나의 안정된 `task_id`와 공용 작업 기록을 공유한다. 별도 작업 객체, 승급 상태나 승급 커밋을 만들지 않는다.

공용 작업 생명주기는 `열림`, `대체됨`, `철회됨`, `종결됨`으로 닫는다. 실행 가능, 점유, 실행 중과 종결 준비는 생명주기에 넣지 않고 파생 상태와 실행 ref에서 계산한다.

실행 ref가 없을 때 `열림` 작업을 대체하거나 철회할 수 있다. 같은 논리적 작업이 다시 필요하면 명시적 복원 결정으로 열림으로 되돌리고 착수 명세를 새로 검토한다. 의미가 바뀌었으면 새 `task_id`를 만든다. 종결된 작업은 다시 열지 않고 새 작업 씨앗과 관계를 만든다.

실행 중인 작업을 없애거나 다른 작업으로 바꾸려면 공용 생명주기를 직접 바꾸지 않고 분할 종결이나 취소 처분을 사용한다.

### 6.2 작업 씨앗과 발생 조건

작업 씨앗은 질문, 포함·제외 범위, 기대하는 연구 상태 변화, 입력, 발생 조건, 예상 산출물, 완료 기준, 관련 F 객체·작업·탐색 방향, 모델·도구·권한 요구와 작업 진전 계약 제안을 가진다.

작업 씨앗은 연구 인스턴스 초기화, 작업 종결 공용 편입, 핵심 기록에 먼저 반영한 승인된 외부 변화 또는 목표 미해결·빈 실행 껍질의 생존 규칙에서만 생성한다.

발생 조건은 공용 커밋의 핵심 기록만 읽는 판본화된 선언형 조건식이다. 임의 코드, 현재 시각, 네트워크 응답, 실시간 작업자 수나 새 수학 판단을 실행하지 않는다. 외부 사건은 먼저 핵심 기록에 편입한다.

발생 조건 평가는 같은 조건식과 공용 커밋에서 `참`, `거짓`, `평가 오류`를 결정론적으로 낸다. 거짓은 정상적인 미충족이고 평가 오류는 인터페이스 결함이다.

### 6.3 착수 가능성과 실행 껍질

착수 가능성은 씨앗 스키마 유효, 현재 씨앗 판본의 착수 명세 검토 승인, 발생 조건 참, 필수 입력 존재와 작업 생명주기 열림을 모두 요구한다.

실행 껍질은 특정 공용 커밋에서 착수 가능성 판정을 통과한 `task_id`의 깊이 1 파생 보기다. 미래 작업과 차단된 작업을 만들지 않는다. 포트폴리오는 실행 껍질 밖의 작업을 선택하거나 새 작업 씨앗을 창작하지 않는다.

### 6.4 작업 경계와 체크포인트

연구 작업은 입력, 기대 상태 변화, 산출물과 완료 기준이 닫힌 연구 생산의 유일한 실행 단위다. 장기 방향은 F 객체와 관계·계보로 표현하며 별도 연구 프로그램을 만들지 않는다.

중간 결과를 별도로 배정·검증·재시도·취소·공용 편입할 합리적 필요가 없으면 순차 단계를 한 작업의 내부 절차로 묶는다. 다른 작업이 재사용하거나 포트폴리오가 계속 여부를 다시 선택해야 하거나, 독립 역할·외부 대기·병렬 수행이 필요하면 별도 작업으로 나눈다.

한 작업은 여러 작업 실행에 걸쳐 이어질 수 있다. 같은 질문·범위·산출물·완료 기준을 유지하는 검증된 내부 상태는 작업 체크포인트로 보존한다. 반복할수록 질문이나 산출물이 바뀌면 새 작업으로 분화한다.

계획된 중간 결과를 작업 도중 공용 편입하지 않는다. 연구 작업 하나는 종결 공용 편입을 한 번만 수행한다. 예상하지 못한 독립 결과를 즉시 공유해야 하면 현재 작업을 분할 종결하고 잔여 범위를 새 작업 씨앗으로 옮긴다.

### 6.5 네 작업 인터페이스

작업 생명주기는 하나의 거대한 작업 파일이 아니라 네 개의 판본화된 인터페이스로 표현한다.

- 작업 씨앗 인터페이스는 안정된 ID, 생성 근거, 질문, 범위, 기대 상태 변화, 입력, 발생 조건, 예상 산출물, 완료 기준, 관계, 모델·도구·권한 요구와 작업 진전 계약 제안을 보존한다.
- 착수 명세 검토 인터페이스는 정확한 `task_id + 씨앗 판본`, 질문·범위·입력·산출물·완료 기준과 진전 계약의 판정, 결함, 검토자와 승인 여부를 보존한다. 씨앗 작성자와 다른 역할이 작성한다.
- 작업 실행 인터페이스는 기준 공용 커밋, 실행 ID, 작업자, 작업 브랜치·worktree, 체크포인트, 진전 계약, 관찰 조건 세대, 모델·도구와 실행 상태를 보존한다.
- 작업 종결 인터페이스는 종결 처분, 실제 수행 범위, 결과·한계, 산출물·증거, 발견 후보, F 변경, 새 작업 씨앗, 관계 효과, 잔여 범위와 공용 변경 묶음을 보존한다.

네 인터페이스의 기계 정본은 서로 다른 판본화된 JSON 스키마를 따르는 독립 UTF-8 JSON 문서다. 긴 질문, 논증, 문헌, Lean 코드와 데이터는 별도 파일에 두고 정확한 경로와 해시를 참조한다. 한 인터페이스의 필드가 다른 인터페이스의 책임을 대신하지 않는다.

## 7. 작업 실행과 Windows 프로세스 격리

### 7.1 실행 상태

작업 실행은 한 연구 작업 계약을 수행하는 개별 작업자 구간이다. 각 실행은 고유 `execution_id`를 가지며 한 작업에는 동시에 쓰는 실행 하나만 있다.

실행 제어는 `준비`, `실행 허가`, `일시 정지`, `종결 준비`, `권한 무효`로 닫는다. 작업자 단계는 `미시작`, `작업 중`, `외부 대기`, `일시 정지 완료`, `종결 준비 중`으로 닫는다. 외부 관찰과 연구 작업 종결 처분은 이 값에 섞지 않는다.

첫 실행은 새 `execution_id`와 부모 없는 실행 상태 커밋을 만들고 작업별 Git 실행 ref가 없을 때만 원자적으로 생성해 점유한다. 작업 브랜치·worktree, 정지된 프로세스와 Job Object를 준비한 뒤 `실행 허가` 상태를 예상 OID로 공개하고 나서만 프로세스를 재개한다.

작업 실행의 물리적 종료 원인과 연구 작업에 미치는 효과를 구별한다. 실행 종료의 작업 효과는 `작업 유지`와 `작업 종결 연계`로 닫는다. 프로세스 소실·시작 실패·정상 인계·강제 종료는 별도 종료 원인이다.

### 7.2 작업 브랜치와 worktree

연구 작업 하나가 작업 브랜치와 worktree 하나를 소유한다. 여러 작업 실행은 옛 실행이 완전히 종료되고 worktree가 복구·검사된 뒤 같은 작업대와 계약을 순차적으로 이어받는다.

실행을 교체할 때 옛 실행의 Git 권한을 먼저 무효화하고, 해당 Job Object 전체를 종료하며 종료 장벽을 확인한다. 마지막 권위 있는 작업 머리, 미커밋·부분 자료와 체크포인트를 검사해 보존 또는 제외한 뒤 선택한 재개 좌표에 worktree를 맞춘다. 그 뒤에만 새 `execution_id`와 실행을 연다.

질문·필수 범위·예상 산출물이나 완료 기준이 바뀌어야 하면 같은 작업의 재시도로 처리하지 않는다. 현재 작업을 종결하고 새 작업 씨앗을 만든다. 작업 진전 계약만 부적합하면 같은 작업 의미를 유지한 새 계약 판본을 독립 검토한 뒤 새 실행에 적용할 수 있다.

### 7.3 실행 상태 Git ref

작업별 Git 실행 ref `refs/do-math/runs/<instance_id>/<task_id>`는 `state.json` 하나를 가진 현재 실행 상태 커밋을 가리킨다. 최초 커밋은 부모가 없고 이후 커밋은 직전 상태 커밋 하나만 부모로 가진다. 실행이 교체돼도 같은 단일 부모 사슬을 이어 간다.

커밋 OID는 불투명한 상태 세대 식별자이자 예상 상태 토큰이다. 권위 있는 쓰기는 조건부 갱신만 사용한다. 현재 OID가 다르면 쓰지 않고 새 상태에서 다시 판단한다.

### 7.4 Windows Job Object

메인 세션이 파견하는 모든 하위 AI 실행은 고유 `execution_id`와 그 ID에 대응하는 Windows Job Object 하나를 가진다. 연구 작업자 실행의 `execution_id`는 작업 실행 ID와 일대일로 연결한다. Job Object는 이름 없이 만들고 프로세스 감독기가 `execution_id → handle` 대응을 보유한다.

Job Object에는 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`를 설정하고 breakaway를 허용하지 않는다. 루트 프로세스는 일시 정지 상태로 만들고 Job Object에 넣은 뒤 실행 허가 OID를 공개하고 재개한다. 일반 `CreateProcess` 자식은 같은 Job Object 계층에 들어간다.

WMI `Win32_Process.Create`, 서비스, 작업 스케줄러, WSL, 컨테이너나 외부 실행 서비스처럼 일반 자식이 아닌 실행이 worktree에 쓰는 것은 금지한다. 필요하면 별도 격리·종료 계약을 가진 승인된 어댑터를 설계한다.

종료는 PID별 종료가 아니라 `TerminateJobObject`를 사용한다. 감독기가 보유한 프로세스 handle의 종료 신호, 종료 코드·시각, Job Object의 활성 프로세스 0과 빈 프로세스 목록을 확인한 뒤에만 종료 장벽을 통과한다. 완료 포트 알림만 종료 증거로 사용하지 않는다.

프로세스 원장은 PID와 원시 Windows 생성 `FILETIME`, 실행 ID, 이미지 경로, 부모 프로세스 인스턴스, 관찰 출처와 종료 정보를 보존한다. PID만 신뢰하지 않으며 Job Object 자체가 격리와 종료의 정본이다.

## 8. 메인 세션과 프로세스 감독기

연구 인스턴스마다 메인 세션에 딸린 결정론적 프로세스 감독기 하나가 연구 작업자·선택자·검토자·심사자와 그 밖의 모든 하위 AI 세션 Job Object handle을 물리적으로 보유한다. 메인 세션은 실행을 논리적으로 총괄하고 감독기는 Windows 생명주기만 수행한다. 감독기 메모리는 연구 정본이 아니다.

메인 제어권은 `refs/do-math/controller/<instance_id>`의 상태 사슬이 소유한다. 상태 변경 요청은 작업 실행 ref나 controller ref에 먼저 기록한다. named pipe 메시지는 요청 ID, controller OID와 실행 상태 OID를 전달하는 통지일 뿐 권한의 정본이 아니다.

감독기는 현재 Git ref와 요청 OID, 실행 ID, 스키마와 허용 전이를 다시 검사한 뒤 Windows 작업을 수행하고 결과를 예상 OID로 기록한다. 같은 요청의 재전송은 기존 결과를 반환하며, 상태가 달라졌으면 낡은 요청으로 거부한다.

계획된 메인 세션 handoff에서는 후속 제어 연결을 먼저 등록하고 controller ref를 새 controller ID로 조건부 갱신한 뒤 기존 연결을 해제한다. Job Object handle은 감독기가 계속 보유한다.

메인 세션이 handoff 없이 사라지면 새 배정과 실행을 막고 활성 실행에 일시 정지를 요청한다. 작업자는 첫 안전 제어 경계에서 체크포인트와 자기 점검을 남긴다. 일시 정지가 확인되면 감독기가 Job Object를 종료한다. 응답 조건 안에 정지하지 않으면 강제 종료한다. 후속 메인 세션은 자동 재실행하지 않고 운영 점검으로 재개 좌표를 정한다.

감독기 자체가 죽으면 마지막 Job Object handle이 닫혀 모든 활성 실행이 실패 폐쇄 방식으로 종료된다. Git 상태와 작업대는 남으며 새 감독기와 메인 세션이 원자료를 대조한다.

## 9. 작업 진전, 관찰과 운영 점검

각 연구 작업은 목적에 기여하는 상태 변화, 진전 신호, 작업자가 그 변화를 생산·시험하도록 내부 절차를 구성할 의무와 다음 관찰 조건을 담은 판본화된 작업 진전 계약을 가진다.

프로세스 생존, 시간·토큰 소비, 로그·파일·보고량은 그 자체로 진전 신호가 아니다. 실패도 정확한 장애물, 반례, 범위 축소나 후속 선택을 바꾸는 근거를 남기면 진전 신호가 될 수 있다.

다음 관찰 조건은 작업자가 상태와 진전 증거를 다시 공개해야 하는 사건·작업 단위·자원량 또는 시간 조건이다. 작업자가 사용하는 모든 조건은 외부 감시기도 같은 공개 상태에서 재현할 수 있어야 한다. 외부 감시기는 프로세스 소실 같은 외부 안전 조건을 추가로 사용한다.

조건은 일회성 관찰 조건 세대로 묶는다. 평가 결과는 `미도래`, `도래`, `평가 오류`다. 하나라도 평가할 수 없으면 평가 오류이며 운영 점검을 발동한다. 도래는 `실행 ID + 조건 세대 ID`로 식별하는 관찰 의무를 열 뿐 즉시 운영 점검을 뜻하지 않는다. 관찰 의무 상태는 `응답 대기`, `충족`, `위반`으로 닫는다.

관찰 의무가 열리면 작업자는 첫 안전 제어 경계 뒤 다음 실질 행동 전 또는 실행 환경·도구 유형이 정한 최대 응답 시각 가운데 먼저 도래하는 한계까지 해당 의무를 참조하는 변경 불가능한 작업 자기 점검을 기록한다. 유효한 자기 점검이 없으면 의무를 위반으로 판정해 운영 점검을 발동하되 작업을 자동 중단하지 않는다. 평가 오류와 외부 안전 발동 조건은 응답을 기다리지 않는다. 유효한 자기 점검은 새 관찰 조건 세대를 활성화한다. 처분 직전 실행 ref가 바뀌면 관찰을 낡은 관찰로 보존하고 새 스냅샷에서 다시 평가한다.

작업 자기 점검의 결과는 `진전`, `무진전`, `계약 부적합`이다. 첫 근거 있는 무진전에는 계약이 허용한 실질적으로 다른 내부 적응 한 번을 허용하고, 반복 무진전·계약 부적합·기록 결함은 운영 점검을 발동한다.

외부 감시기는 작업자 공개 상태를 읽어 관찰 입력 스냅샷, 조건 평가, 관찰 의무와 발동 근거를 감시 기록 원장에 쓴다. 작업자는 감시 기록을 읽지 않는다. 역방향 전달은 확정된 운영 처분이 실행 제어 상태를 바꿀 때만 일어난다.

운영 점검은 실제 씨앗, 기준 커밋, 실행 상태, 작업 diff·미커밋 자료, 체크포인트, 프로세스·하위 프로세스, 로그, 도구와 자원을 직접 읽는 별도 AI 실행이다. 현재 실행 계속·다음 점검·추가 체크포인트 요구처럼 정체성을 바꾸지 않는 처분은 점검자가 확정할 수 있다. 실행 인수·재시작·분할·운영 실패 종결과 중대한 자원 변경은 다른 역할의 운영 처분 심사를 거친다.

운영 처분 심사의 판정은 `승인·기각`이다. 필수 원자료를 읽지 못해 판정하지 못한 실행은 심사 미완료이며 처분 적용이나 대응을 열지 않는다.

고영향 처분의 승인만으로 적용 권한이 생기지 않는다. 적용 가능한 사용자 유래 전례가 있으면 자동 적용하고, 없거나 충돌하거나 적용 가능성을 확정할 수 없으면 사용자에게 상신한다. 전례 적용 판정은 별도의 `gpt-5.6-sol high` 1차 세션과, 1차가 적용 가능일 때만 여는 독립 2차 세션이 모두 적용 가능일 때 확정한다.

전례는 사용자 결정과 실제 사례의 원자료를 의미 추가 없이 기계적으로 봉인한다. AI가 일반 범위를 창작하지 않는다. 대체·폐기·비적용 관계는 불변 기록으로 만들고 과거 적용을 소급 무효화하지 않는다.

## 10. 연구 작업의 종결과 공용 편입

### 10.1 종결 처분과 결과

절차적 종결 처분과 수학적·연구 결과를 별도 축으로 둔다.

종결 처분은 `완료`, `분할 종결`, `취소`, `운영 실패 종결`로 닫는다. 입증·반증, 조건부·제한 결과, 후보 강화·배제, 반례·장애물, 불확실성 감소, 발견 후보, 결과 없음과 판정 불가는 별도 결과·근거 필드에 기록한다.

긍정 결과가 없어도 계약을 충족하면 완료일 수 있고 유용한 부분 산출물이 있어도 계약을 끝내지 못했으면 운영 실패 종결일 수 있다. `중단`, `외부 대기`, `체크포인트`, `재시도 대기`는 재개 가능한 실행 상태이며 종결 처분이 아니다. 수학적 해결도 작업 종결 처분이 아니라 Lean 정본과 연구 헌장이 판정한다.

### 10.2 잔여 범위 보존

모든 종결 기록은 착수 때 고정한 필수 범위가 실제 수행, 불필요 확인, 권위 있는 철회·대체, 후속 씨앗 이전 또는 판정 불가 중 어디에 놓였는지 근거와 함께 밝힌다.

완료는 필수 범위가 모두 충족됐음을, 분할 종결은 잔여 범위 전부가 새 씨앗에 들어갔음을 요구한다. 취소는 권위 있는 결정과 잔여 범위 처분을, 운영 실패 종결은 부분 산출과 미완료 범위의 복구·재시도 씨앗을 요구한다. 별도 권위 결정이 필요 자체를 없앤 경우에만 후속 씨앗을 만들지 않는다.

### 10.3 종결 적용

작업자가 종결 제안을 고정하면 실행은 비종결 `종결 준비` 상태로 들어간다. 원 작업 머리에서 임시 편입 브랜치를 만들고 최신 공용 머리를 merge한다. 텍스트 충돌뿐 아니라 바뀐 입력·가정·완료 기준, 핵심 기록 의미, 스키마·무결성·Lean·인증 기준을 다시 검사한다.

검증에 실패하면 종결은 효력을 얻지 않고 작업 점유를 유지한 채 재작업이나 운영 점검으로 보낸다. 검증한 최종 트리로 현재 공용 머리 하나만 부모로 갖는 작업 전용 공용 편입 커밋 하나를 만든다. 작업·체크포인트·임시 merge 커밋을 공용 머리 조상으로 넣지 않는다.

원자적 ref 트랜잭션이 `terminal` 실행 상태 커밋 확정, 공용 머리 갱신, 실행·작업·임시 편입 보관 ref 생성과 활성 실행 ref 삭제를 모두 성공시킨 때에만 종결 처분이 효력을 얻는다. `terminal` 상태가 기록한 공용 편입·보관 ref 좌표는 현재 공용 머리와 보관 ref 전건과 다시 대조한다. 기대 OID나 보관 ref 전건이 다르면 아무 변경도 적용하지 않는다.

```text
refs/do-math/archive/runs/<instance>/<task>/<execution>
refs/do-math/archive/work/<instance>/<task>/<execution>
refs/do-math/archive/integration/<instance>/<task>/<execution>
```

보관 ref는 이동·덮어쓰기하거나 자동 만료로 삭제하지 않는다. 보관 뒤에만 worktree와 활성 작업 브랜치를 정리한다.

## 11. 포트폴리오 선택과 모델 용량

### 11.1 모델 용량

자원 예산은 `(모델, 추론 노력, 동시 하위 AI 세션 상한)`으로만 구성한다. 개별 작업에 토큰·시간·비용 예산을 배정하지 않는다.

상한에는 연구 작업자, 포트폴리오 선택자, 인증 검토자·심사자·부분 전문 검토자, 운영 점검·심사자와 전례 적용 판정자를 포함한다. 장기 메인 세션 하나, 결정론적 스크립트, Lean 빌드와 프로세스 감독기는 포함하지 않는다.

특정 연구 방향에 대한 자원 집중은 같은 작업에 여러 작업자를 붙이는 방식이 아니라 그 방향의 서로 다른 작업 씨앗을 더 많이 선택하는 방식으로 표현한다. 의도적인 독립 접근이나 중복 검증은 별도 `task_id`와 worktree를 사용한다.

### 11.2 메인 포트폴리오 heartbeat

메인 세션은 설정한 주기마다 하나의 heartbeat를 직렬 실행한다. heartbeat는 작업자의 생존·진전 신호가 아니다.

heartbeat는 완료 실행을 전건 처리해 공용 편입·재개·점검 상태로 옮기고, 종료 장벽이 끝난 세션의 모델 용량을 반환하며, 모델별 남은 동시 세션 수를 계산한다. 그 뒤 필요한 경우 별도 포트폴리오 선택 세션을 연다.

외부 안전 사건은 정기 heartbeat를 기다리지 않는다. 여러 heartbeat를 동시에 열지 않으며 이미 수행 중이면 사건을 한 다음 회차에 합친다.

### 11.3 별도 선택 세션

포트폴리오 선택은 메인 세션이 직접 수행하지 않는다. 매 선택 회차마다 새 `gpt-5.6-sol max` 세션 하나를 열고 내부 하위 AI를 사용하지 않는다.

입력에는 `do-math`의 판본화된 선택 계약, 연구 헌장·정책·맥락·설정, 현재 K·F, 실행 껍질 후보 전부와 연결 자료 전문, 실행·재개 대기 작업, 과거 선택과 실제 결과, 모델 용량과 후보 관계를 넣는다. 1M 컨텍스트 모델을 전제로 하며 실제 한도를 넘으면 조용히 요약·절단하지 않고 선택을 중단한다.

후보 블록은 운영체제 난수로 만든 seed에 따라 매 회차 무작위 순서로 제공한다. seed와 실제 순서를 보존한다. 순서는 우선순위를 뜻하지 않는다.

선택 세션은 확인된 근거, 추론, 가설, 수학적 직감, 정보 획득을 위한 탐색과 무작위 선택을 모두 사용할 수 있다. 직감을 근거로 꾸미지 않고 정보 상태를 구분한다. 탐색·집중 활용, 다양성, 중복, 기아, 정보 가치와 과거 결과를 고려하지만 고정 비율·점수·기아 상한은 두지 않는다.

선택 세션은 실행할 작업 집합 전체와 각 작업의 모델·노력을 고른다. 같은 주제의 병행, 독립 검증, 다양한 분야 탐색, 한 방향 집중과 일부 용량 미사용을 재량으로 결정한다. 병행 작업은 서로의 미공개 worktree를 읽지 않는다.

### 11.4 선택 산출물과 이중 기계 검사

메인 세션은 정확한 공용·controller·실행 ref 스냅샷과 입력 manifest를 만들고 별도 선택 세션에 제공한다. 선택 세션은 입력 검사를 직접 수행하고 `selection.json`과 판단 산문을 작성한 뒤 출력 검사기를 실행해 봉인한다.

메인 세션은 반환 요약이 아니라 실제 산출물 전문을 읽고 같은 판본의 기계 검사기를 별도 실행한다. 입력 완전성, 후보 전건 처리, 실행 껍질 포함, 중복 점유, 모델 상한, 참조와 현재 OID를 검사한다.

양쪽 검사를 통과하고 현재 상태가 같으면 메인 세션은 선택을 임의로 고치지 않고 적용한다. 구체 결함이면 같은 선택 세션에 재작성을 요청하고, 상태가 달라졌으면 낡은 선택으로 보존한 뒤 새 세션을 연다. 점유 중 하나라도 실패하면 남은 후보를 임의 보충하지 않고 새 선택 회차를 연다.

기계 도구는 AI 판단을 대체하지 않는다. 반복되는 결정론적 상태 수집, manifest·해시·스키마 검사, 무작위 배열, 모델 용량 계산, 작업 점유·파견과 보고를 고품질의 판본화된 도구로 제공해 AI가 임의 도구를 매번 다시 만들지 않게 한다.

## 12. P vs NP 프로젝트 계약

### 12.1 주제 선호와 소유권

P vs NP의 프로젝트 입력은 `research/pvsnp/연구-주제-선호.md`, `research/pvsnp/핵심-정의-명세.md`, `research/pvsnp/문헌-체계-명세.md` 세 문서로 구성된다. 첫 문서는 전체 연구 주제, 원하는 결과, 범위와 방향을, 둘째 문서는 P와 NP의 정확한 수학 정의와 연결 정리 의무를, 셋째 문서는 문헌 연구의 구체적 주제와 깊이를 소유한다.

`do-math` 연구 인스턴스가 생성되면 세 외부 문서의 의미를 내부 연구 헌장·정책·맥락·설정, 초기 `F` 객체, 자료·근거, 사용자 결정과 그 밖의 실제 소유자에게 빠짐없이 나눠 수입하고 평시에는 세 문서를 다시 읽지 않는다. 세 문서가 서로 다른 주제를 지시하면 주제 선호가 완성되지 않은 상태이므로 한 문서를 임의로 우선해 차이를 숨기지 않는다.

P vs NP 핵심 정의 명세와 문헌 체계 명세는 각각 자기 문서가 정한 주제 내용을 소유한다. `do-math` 통합 설계는 두 명세의 주제 내용을 선결정하지 않고 일반 입력·실행 인터페이스를 제공한다.

### 12.2 핵심 목표와 성공

핵심 P와 NP 정의는 이진 문자열 언어, 결정론적 단일 테이프 Turing 기계의 최악 경우 `n^k+k` 시간과 다항 길이 증명서를 검사하는 결정론적 다항시간 검증자를 뼈대로 사용한다. 다른 표준 정의·기계·부호화는 우리 Lean 언어로 작성한 정본 연결 정리로 핵심 정의에 연결한다.

수학적 해결은 핵심 정의의 `P = NP` 또는 `P ≠ NP` 증명 항이 해설–형식 동일성, 커널 검사, 공리 감사, 범위 차분 감사와 필요한 프로젝트 관문을 통과해 Lean 정본에 편입된 상태다.

조건부 정리, 제한 모형 분리, 장벽 결과와 부분 성과는 정확한 수학 결과지만 P vs NP 해결이 아니다. 시간·토큰·비용 한도와 새로운 접근을 찾지 못한 상태도 해결이 아니다. 미해결 상태와 재개 좌표를 보존한다.

범위 차분 감사의 처분은 `동일`, `등가 입증`, `충분성 입증`, `범위 축소`, `범위 확장`, `조건부`, `미해결`이다. 앞의 셋만 목표 해결과 양립한다. 다른 처분도 수학적으로 타당하고 엄밀하면 실제 범위로 Lean 정본에 편입한다.

수학적 해결 뒤 사람이 읽는 증명, Lean과 자연어의 대응, 재현 환경, 외부 독립 검토, 결함 제보·수정, 적격 출판과 공동체 검토를 학술적 검증으로 수행한다. 외부 공개·출판은 사용자 개입 경계를 따른다.

### 12.3 문헌 방향

P vs NP 문헌 포괄은 확장 가능한 `분야 × 깊이` 관점으로 관리한다. P vs NP에 가까운 자료만 수집하지 않고 현대 수학의 기초부터 최신 전선, 형식 증명·공개 데이터와 코드까지 포함한다. 분야 목록은 탐색 결과에 따라 확장한다.

공인 문헌은 높은 사전 신뢰를 가지지만 문헌에 있다는 사실만으로 Lean 정본에 들어가지 않는다. 원 증명을 확보하고 전제·논증 단계·구성을 구체적으로 재구성한다. 결함으로 보이는 지점은 실제 결함, 허용 가능한 생략과 검토자 오독을 구별한다.

사용자가 원 임무에서 허용한 경북대학교 학술 DB `kudos.knu.ac.kr` 접근과 Playwright 사용은 문헌 체계 티켓의 입력이다. 크리덴셜 좌표는 `.credentials/kudos.md`이며 값은 어떤 산출물·로그·프롬프트에도 복제하지 않는다. 실제 소스 조합과 접근 절차는 문헌 체계 명세가 결정한다.

## 13. 모델, 사용자 개입과 외부 경계

수학 연구, 증명·반증, 반례, 문헌 논증 재구성, Lean 형식화, 동일성 검토·이의 심사, 범위 감사와 부분 전문 검토처럼 수학 판단을 생산하는 개별 AI 세션은 `gpt-5.6-sol max`를 사용한다.

전례 적용 판정은 별도의 `gpt-5.6-sol high` 세션을 사용한다. 파일 수집, 해시, 직렬화, 스키마, Lean 빌드, 공리 추출과 상태 검사는 스크립트나 충분한 경량 모델을 사용할 수 있다. 모든 AI 실행은 모델·노력·역할과 입력·산출 좌표를 기록한다.

`do-math`가 병렬화를 직접 운전하며 연구 작업과 판정 세션 안에서 Codex `ultra`의 내부 다중 에이전트 운전을 사용하지 않는다.

`do-math`는 연구 헌장과 정책 안에서 자율적으로 운전한다. 연구 목적, 신뢰 경계, 외부·비가역 효과나 사용자 절충을 바꾸는 결정은 사용자 결정 또는 현재 사례에 적용 가능한 사용자 유래 전례가 필요하다.

외부 공개·출판, 유료 자원, 크리덴셜·계정, 복구 불가능한 삭제, 장기 연구 종결과 대규모 정본 무효화는 열린 예시다. 실제 효과로 경계를 판정한다. 세 범주에 해당하지 않고 현행 계약이 허용 결과를 정하면 `do-math`가 자율 결정한다.

## 14. 과거 자료와 현재 소유권

새 연구 체계는 종결한 `pvsnp-탐사-1`의 상태, 작업 부채, 완료 판정, 자료구조와 규칙을 승계하지 않는다. 과거 문헌 판독, 출처 원장, 기각 지도, 검증 기록과 보존 산출은 필요한 사실·근거·실패 경위와 원자료 좌표를 확인할 때만 읽는 참고 자료다.

과거 자료의 완료와 검증 판정은 새 체계에 전이되지 않는다. 같은 문헌이나 내용을 선택하면 현행 절차로 다시 처리한다. 과거 자료는 원래 좌표에 보존하고 현재 정본에 중복 복사하지 않는다.

주요 원자료 좌표는 다음과 같다.

- P vs NP 문제 정본과 선행연구: `research/p-vs-np-statement-and-prior-work.md`
- P vs NP 주제 선호 초기 입력: `research/pvsnp/연구-주제-선호.md`
- 도구 실사: `docs/wayfinder/pvsnp-재설계/도구-지형-실사.md`
- 과거 입증 검토 조사: `docs/wayfinder/pvsnp-재설계/입증-검토-운용-논의.md`
- 과거 Lean 혼합 정본 논의: `docs/wayfinder/pvsnp-재설계/Lean-중심-혼합-정본-논의.md`
- 트래커 규약: `docs/agents/issue-tracker.md`

과거 입증 검토 문서의 수리자·심사자 구조와 이 문서의 현행 동일성 검토·심사 사슬을 혼합하지 않는다. 현행 핵심은 검토자가 동일성 이의를 만들고 심사자 셋은 전달된 각 이의만 만장일치로 판정하며, 비만장일치 피드백은 검토자와 같은 심사자들 사이의 반복 루프로 돌아간다는 것이다.
