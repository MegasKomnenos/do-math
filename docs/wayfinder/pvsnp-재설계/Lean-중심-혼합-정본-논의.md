# Lean 중심 혼합 정본 확정 방향과 구현 논의

## 1. 문서의 지위

이 문서는 wayfinder 지도 [「P vs NP 연구 체계 재설계」](https://github.com/MegasKomnenos/math/issues/6)의 표현 체계 확정 방향과 남은 구현 결정을 보존한다. 사용자는 2026-08-28에 Lean 중심 혼합 정본을 채택했다. [「연구 지도 표현 체계를 확정한다」](https://github.com/MegasKomnenos/math/issues/9)는 이 방향을 전제로 정확한 표현 체계와 검사 책임을 결정한다.

[「'확실' 판정 기준을 확정한다」](https://github.com/MegasKomnenos/math/issues/10)는 형식화된 판정 명제와 입증에 Lean 검증을 필요조건으로 적용한다. Lean 검증은 전체 검토단을 대체하지 않으며 단독으로 입증 기록을 승인하지 못한다.

## 2. 용어

- **Lean 선언**: Lean 코드로 작성한 정의, 형식 명제 또는 정리.
- **Lean 증명 항**: 형식 명제가 선언된 정의와 공리에서 도출됨을 Lean 커널이 검사할 수 있는 항.
- **수학적 내용**: 정의, 판정 명제, 정리, 증명과 증명 의존 관계.
- **인식론적 상태**: 연구 지도 객체의 `확실` 또는 `불확실` 상태와 그 상태의 근거.
- **연구 과정 정보**: 문헌 출처, 입증 기록, 검토, 이의, 예외, 미해결, 비활성 이력과 작업 상태.
- **Lean 중심 혼합 정본**: 수학적 내용은 Lean 선언과 증명 항을 정본으로 삼고, 인식론적 상태와 연구 과정 정보는 별도 연구 지도 스키마를 정본으로 삼는 구성.

## 3. Lean을 먼저 쓰는 방안의 실익

Lean을 수학적 내용의 정본으로 먼저 작성하면 자연어 판정 명제를 나중에 형식 명제로 번역하는 단계를 줄일 수 있다. 다음 정보가 처음부터 기계가 읽는 형태로 고정된다.

- 수학적 정의
- 판정 명제
- 정리와 보조정리
- 증명 의존 관계
- 사용한 공리
- 기초 프로필
- 형식 증명.

연구 지도 화면과 사람이 읽는 설명은 Lean 선언에서 생성할 수 있다. 형식화된 객체의 정확한 수학적 내용은 Lean 선언 한 곳에서만 고친다.

## 4. Lean만으로 전체 지도를 표현할 때의 한계

연구 지도에는 형식 증명 이외의 정보가 있다. 불확실 객체, 영역 뭉텅이, 끝점이 없거나 하나뿐인 연결 가설, 문헌 출처, 검토단 판정, 이의 심사, 예외, 미해결 상태, 비활성 이력과 실패 환류가 그 정보다.

이 정보를 Lean의 사용자 자료구조로 표현할 수는 있다. 그러나 Lean 커널은 그 자료구조가 연구 지도에서 의도한 의미를 지키는지 자동으로 검사하지 않는다. 확실 전이, 비활성 이력, 연결 가설의 끝점 수와 같은 규칙에는 별도의 결정론 검사기가 필요하다.

Lean 소스만 지도 저장소로 사용하면 동적 질의, 불완전 객체, 이력, 동시 편집과 작업 큐를 위한 기능도 직접 만들어야 한다. Lean을 쓴다는 사실만으로 이 기능이 생기지 않는다.

## 5. 불확실 명제와 공리의 경계

형식화할 수 있는 불확실 명제는 Lean에서 명제의 내용만 정의할 수 있다.

```lean
def p_ne_np : Prop := P ≠ NP
```

이 선언은 `P ≠ NP`가 참이라고 가정하지 않는다. 형식 명제의 내용을 이름으로 고정한다.

불확실 명제를 다음처럼 공리로 선언하면 안 된다.

```lean
axiom p_ne_np_proof : P ≠ NP
```

두 번째 선언은 `P ≠ NP`를 증명 없이 사용할 수 있게 한다. 불확실 명제가 확실한 정리의 증명에 스며들 수 있으므로 연구 지도의 상태 의미와 충돌한다.

## 6. 확정한 정본 경계

Lean 중심 혼합 정본은 정보 종류마다 정본을 하나씩 둔다.

| 정보 | 정본 |
|---|---|
| 형식 가능한 정의와 판정 명제 | Lean 선언 |
| 형식 증명과 증명 의존 관계 | Lean 증명 항 |
| 공리 의존성과 형식 기초 프로필 | Lean 환경과 공리 감사 기록 |
| 확실·불확실 상태 | 연구 지도 스키마 |
| 문헌 출처와 입증 기록 | 연구 지도 스키마 |
| 검토·이의·예외·미해결 | 연구 지도 스키마 |
| 뭉텅이와 연결 가설 | 연구 지도 스키마 |
| 상태 전이와 이력 | 연구 지도 스키마와 결정론 검사기 |

연구 지도 객체는 형식화되었으면 정확한 Lean 선언을 참조한다. 참조는 저장소, 커밋, 모듈과 선언 이름을 식별해야 한다. 형식화하지 않은 객체는 별도 스키마에 수학적 문면과 불확실 상태를 보존한다.

자연어 설명은 사람이 읽는 표시다. 형식화된 객체에서 자연어 설명과 Lean 선언이 충돌하면 Lean 선언이 수학적 내용의 정본이다. 다만 Lean 선언이 원문과 연구 의도를 올바르게 표현하는지는 전체 검토단의 `의미 대응`과 `형식화·공리 감사` 관점이 검토한다.

## 7. 기초 프로필과 외부 라이브러리

Lean 자체는 하나의 형식 기초를 제공하지만 연구 지도는 기본 기초 프로필과 대안 기초 프로필을 허용한다. Lean 중심 표현 체계는 각 프로필을 별도 모듈, 매개변수화한 이론 또는 명시한 공리 집합으로 어떻게 표현할지 결정해야 한다. 한 프로필의 증명을 다른 프로필의 확실 판정으로 자동 전이하면 안 된다.

Mathlib에는 계산 가능성, Turing 기계와 일부 시간 복잡도 기초가 있다. Mathlib 자체에는 표준 P, NP와 Cook–Levin 체계가 없다. Complexitylib과 DescriptiveComplexity에는 P, NP와 완전성 결과가 있지만 계산 모형, 부호화와 환원 정의가 서로 다르다.

따라서 외부 Lean 정리를 연구 지도 객체에 연결하기 전에 정의와 기초 프로필의 대응을 입증해야 한다. 정리 이름이 같다는 사실은 대응의 근거가 아니다.

## 8. 현재 준비 상태

2026-08-28 현재 저장소에는 추적 중인 `.lean` 파일, `lean-toolchain`과 `lakefile`이 없다. 실행 환경에도 `lean`과 `lake` 명령이 설치되어 있지 않다. Lean 중심 혼합 정본을 채택하면 도구체인, 라이브러리, 기초 프로필, 안정 식별자와 검증 절차를 새로 구축해야 한다.

이 준비 상태는 방안의 품질을 낮추는 논거가 아니다. 이 준비 작업의 범위와 결과는 표현 체계 선택의 하류 영향을 판단하는 입력이다.

## 9. 표현 체계 티켓이 결정할 질문

[「연구 지도 표현 체계를 확정한다」](https://github.com/MegasKomnenos/math/issues/9)는 Lean 중심 혼합 정본을 전제로 다음 질문을 결정한다.

- 어떤 객체의 수학적 내용을 Lean 정본으로 요구하는가
- 형식화되지 않은 명제를 어떤 스키마로 보존하는가
- 불확실 명제가 공리로 증명에 스며들지 않도록 어떻게 검사하는가
- Lean 선언과 연구 지도 객체의 안정 식별자를 어떻게 연결하는가
- 기본 기초 프로필과 대안 기초 프로필을 Lean에서 어떻게 분리하는가
- 외부 라이브러리 정의와 연구 지도 정의의 대응을 어떤 판정 명제로 표현하는가
- Lean 빌드, 공리 감사와 연구 지도 상태 전이를 어떤 검사기가 연결하는가
- 자연어 표시를 Lean 선언에서 어떻게 생성하고 드리프트를 어떻게 검사하는가.

이 티켓은 연구 지도 스키마, 결정론 검사기, Lean 모듈 구성과 외부 도구의 역할을 비교한다. 비교 결과는 Lean 중심 혼합 정본의 확정 경계를 유지해야 한다.

## 10. 확실 판정 티켓에 미치는 영향

형식화된 판정 명제와 입증에는 Lean 커널 검사, 형식 명제 대응, 정의 대응과 공리 감사가 필요하다. 판정 명제와 입증을 Lean으로 형식화하지 않은 객체는 `확실` 상태로 바꿀 수 없다.

Lean 검증은 전체 검토단을 대체하거나 검토단 규모를 줄이지 않는다. Lean 검증만으로 입증 기록을 승인할 수 없다. 검토단은 `형식화·공리 감사`를 공통 관점으로 둔다.
