# P vs NP 연구 지도 도구 지형 실사

기준일: 2026-08-28

## 문서의 지위

이 문서는 [「연구 지도 도구 지형을 실사한다」](https://github.com/MegasKomnenos/math/issues/8)의 해결 보고서다. 사실 진술은 9절의 고정 커밋과 기준일에 상대적이다. 이 문서는 현행 연구 구조나 도구를 선택하지 않는다.

초기 보고서는 `확실·불확실` 연구 지도와 노드·간선 스키마를 비교 기준으로 사용했다. 후속 결정은 그 구조를 Lean 정본, 세 작업 영역과 단일 작업 DAG로 대체했다. 초기 스키마에 관한 비교는 역사적 조사 문맥이며 현행 구현 요구가 아니다.

[「보편 수학 연구 스킬 do-math의 통합 설계를 확정한다」](https://github.com/MegasKomnenos/math/issues/18)는 작업·검증 도구의 사용 범위를 정한다. [「P vs NP 핵심 Lean 정의를 완성하고 검증한다」](https://github.com/MegasKomnenos/math/issues/20)는 외부 Lean 라이브러리의 수학 내용을 참고할 범위를 정한다.

## 1. 결론

조사한 도구 하나만으로는 형식 수학 검증, 연구 과정 상태와 작업 운전을 모두 직접 제공할 수 없다. 도구마다 제공하는 구성은 다르다. Lean은 형식 명제의 입증을 검사한다. Verso Blueprint는 Lean 선언에서 진행 상태를 추출한다. Equational Theories는 결과 원장과 폐쇄 계산을 가진다. MMT는 여러 형식 체계의 이론 그래프를 연결한다.

이 보고서는 도구를 선택하지 않는다. 현행 티켓은 각 도구의 직접 지원, 규약 인코딩과 검증 강도를 구별해 필요한 구성만 선택한다.

최초 컨텍스트 정본에 있던 도구 진술은 다음 사실과 맞지 않았다.

- Lean 생태계의 계산 복잡도 범위를 “얇다”라고 묶을 수 없다. Mathlib 자체의 자원 제한 계산 이론은 작다. 그러나 별도 Lean 4 라이브러리인 Complexitylib과 DescriptiveComplexity는 `P`, `NP`, SAT의 NP-완전성, 계층 정리, 회로 결과까지 형식화했다.
- leanblueprint의 `\leanok`는 사람이 붙이는 표지다. `checkdecls`는 연결한 Lean 선언의 존재만 검사한다. 따라서 leanblueprint의 상태를 Lean 증명에서 자동으로 도출한 상태로 설명하면 안 된다.
- Equational Theories의 일반 마그마 그래프는 현재 4,694개 법칙의 순서쌍 22,033,636개를 모두 분류한다. 다만 Lean 커널은 명시적 증명과 반례 정리를 검사한다. 나머지 상태는 프로젝트의 폐쇄 계산기가 도출한다.

주요 도구가 제공하는 구성은 서로 다르다.

- Verso Blueprint는 라벨, 두 종류의 의존 관계, 소유자, 우선순위, 출처 좌표, Lean 선언 상태를 한 기계 판독 원장으로 내보낸다.
- Equational Theories는 명시적 증명·명시적 반증·추론된 결과·추측·미해결을 구별한다. 명시적 결과와 폐쇄 계산을 분리한다.
- Lean은 형식 명제의 증명 항을 커널로 검사한다. Lean은 모호한 뭉텅이와 끝점이 정해지지 않은 관계의 연구 의미를 직접 제공하지 않는다.

현행 설계는 도구별 직접 지원과 규약 인코딩을 구별해야 한다. 또한 표현 가능성과 검사 강도를 따로 판정해야 한다. 규약으로 넣은 연구 의미는 원도구가 검사하지 않는다.

## 2. 판정 어휘

아래 비교표는 지원 강도를 세 값으로 구별한다.

- **직접**: 공식 스키마나 코드가 해당 대상을 별도 필드나 생성자로 표현한다.
- **규약**: 기존 필드에 사용자 정의 유형, 메타데이터, 또는 가상 노드를 넣으면 표현할 수 있다. 도구가 연구 의미를 검사하지는 않는다.
- **미확인**: 읽은 공식 자료에서 지원 근거를 확인하지 못했다.

“해당 없음”은 도구의 목적상 비교 대상이 생기지 않는 경우에만 쓴다. 기능 부재는 닫힌 코드 범위를 확인한 경우에만 단정한다.

## 3. Lean 4와 계산 복잡도 라이브러리

### 3.1 Lean 4의 검증 경계

Lean은 의존형 이론으로 쓴 명제와 증명 항을 커널이 검사한다. 커널 통과는 현재 파일과 import가 선언한 정의·정리·공리로부터 해당 형식 명제가 따른다는 뜻이다. 자연어 문장과 형식 명제의 의미 일치는 별도 검토 대상이다. 공식 검증 안내는 `lake build`, `#print axioms`, `lean4checker --fresh`가 보장하는 범위를 따로 설명한다. [Lean 공식 검증 안내](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)

Lean의 전제는 연구 지도의 “확실”보다 좁고 강하다. Lean은 형식 명제의 증명 여부를 검사한다. Lean은 문헌 이해, 자연어와 형식문의 대응, 탐사 가치, 또는 불확실한 관계의 존재 가능성을 판정하지 않는다.

### 3.2 Mathlib 자체의 현행 범위

Mathlib의 `Mathlib/Computability` 하위 29개 Lean 파일을 전수 검색했다. 이 닫힌 하위 트리에는 `P`, `NP`, `NPComplete`, `NPHard`, Cook–Levin 선언이 없다. [Mathlib `Computability` 공식 소스 트리](https://github.com/leanprover-community/mathlib4/tree/master/Mathlib/Computability)

Mathlib에는 자원 제한 계산의 기초가 있다. `FinTM2`는 유한한 스택·라벨·상태를 가진 TM2 기계를 묶는다. `TM2OutputsInTime`은 최대 스텝 수를 기록한다. `TM2ComputableInPolyTime`은 입력 길이에 자연수 계수 다항식을 적용한 시간 상한과 출력 정확성 증명을 함께 묶는다. 이 파일이 열거하는 다항시간 계산 정리는 항등 함수의 `idComputableInPolyTime`이다. [Mathlib `TuringMachine.Computable` API](https://leanprover-community.github.io/mathlib4_docs/Mathlib/Computability/TuringMachine/Computable.html)

Mathlib의 `ManyOneReducible`과 `OneOneReducible`은 계산 가능한 환원을 정의한다. 이 환원은 다항시간 환원이 아니다. 같은 파일은 환원의 반사성·추이성, 동치, many-one degree를 증명한다. [Mathlib `Computability.Reduce` API](https://leanprover-community.github.io/mathlib4_docs/Mathlib/Computability/Reduce.html)

Mathlib은 `ComputablePred`, `REPred`, Rice 정리, 정지 문제의 재귀 열거 가능성과 비결정 가능성을 형식화한다. [Mathlib `RE` API](https://leanprover-community.github.io/mathlib4_docs/Mathlib/Computability/RE.html) [Mathlib `Halting` API](https://leanprover-community.github.io/mathlib4_docs/Mathlib/Computability/Halting.html)

알고리즘 분석 쪽에는 Akra–Bazzi 재귀와 점근 상·하한 및 세타 정리가 있다. 이 결과는 복잡도 계급의 정의가 아니라 분할 정복 재귀의 점근 분석이다. [Mathlib `AkraBazzi` API](https://leanprover-community.github.io/mathlib4_docs/Mathlib/Computability/AkraBazzi/AkraBazzi.html)

따라서 Mathlib만으로 고전적 P vs NP 명제와 표준 완전성 이론을 바로 작성할 수는 없다. 반면 Turing 기계, 실행 시간, 계산 가능성, 재귀 열거 가능성, 계산 가능한 환원, 점근 분석은 재사용할 수 있다.

### 3.3 Complexitylib

Complexitylib은 Mathlib 위에 세운 계산 복잡도 전용 Lean 4 라이브러리다. 공식 문서는 결정적·비결정적·확률적 다중 테이프 Turing 기계, 점근 표기, 시간·공간 계급, 환원, 회로를 공개 표면으로 열거한다. [Complexitylib 공식 저장소](https://github.com/SamuelSchlesinger/complexitylib)

`P`는 다항식 시간 `DTIME`의 합집합이다. `NP`는 다항식 시간 `NTIME`의 합집합이다. `coNP`, `NPSPACE`, `FP`, `PSPACE`, 확률 계급, 비균일 계급도 별도 정의를 가진다. [Complexitylib `P` API](https://samuelschlesinger.github.io/complexitylib/Complexitylib/Classes/P.html) [Complexitylib `NP` API](https://samuelschlesinger.github.io/complexitylib/Complexitylib/Classes/NP.html) [Complexitylib 계급 집계 API](https://samuelschlesinger.github.io/complexitylib/Complexitylib/Classes.html)

공식 정리 색인은 다음 결과를 선언한다.

- `Complexity.SAT.NPComplete_language`: SAT는 `NPComplete`다.
- `Complexity.P_subset_NP`: (P \subseteq NP)다.
- `Complexity.time_hierarchy_weak`와 `DTIME_pow_ssubset`: 결정적 시간 계층의 엄격한 포함을 준다.
- `P/poly`, 무작위 계급 포함, Shannon 계수 하한, XOR 하한, Valiant 깊이 축소, Barrington 정리를 포함한다.

공식 문서는 공개 정리에 `sorry`나 사용자 공리가 없다고 설명한다. CI의 `AxiomGuard`는 Lean의 표준 공리 셋을 넘는 의존을 검사한다. [Complexitylib 정리 색인](https://samuelschlesinger.github.io/complexitylib/Complexitylib.html) SAT 모듈은 CNF 의미론과 인코딩, 결정적 검증기, 비결정적 추측-검증 구성, Cook–Levin 조립을 분리한다. [Complexitylib SAT API](https://samuelschlesinger.github.io/complexitylib/Complexitylib/SAT.html)

Complexitylib은 P vs NP 연구의 형식 기반으로 직접 쓸 수 있다. 그러나 연구 지도의 불확실 객체, 작업 상태, 문헌 증거, 반쪽 관계를 관리하는 도구는 아니다.

### 3.4 DescriptiveComplexity

DescriptiveComplexity는 Mathlib의 `ModelTheory` 위에 세운 Lean 4 라이브러리다. 결정 문제를 유한 관계 구조의 동형사상 불변 성질로 표현한다. 소속은 논리 정의 가능성으로, 난해성은 일차 논리 환원으로, 완전성은 두 성질의 결합으로 표현한다. [DescriptiveComplexity 공식 저장소와 결과표](https://github.com/PierreSenellart/descriptive-complexity)

공식 결과표는 `L`, `NL`, `PTIME`, `NP`, `coNP`, 다항 계층, `PSPACE`, 지수 계급, `RE`를 정의한다. SAT의 NP-완전성, HORN-SAT의 PTIME-완전성, Karp의 21개 문제, 기계 수용 문제와 논리 계급의 동치, Immerman–Vardi 정리를 Lean 정리로 제공한다.

이 라이브러리의 Cook–Levin은 논리로 정의한 `NP`를 SAT로 보내는 정리다. 기계 계급과의 연결은 별도 정리다. 라이브러리는 알고리즘 비용 모형, 미세 복잡도, 일반 문자열 부호화와 유한 구조 사이의 고전적 동치를 형식화하지 않았다고 명시한다. 또한 (P=NP)나 (P\ne NP)를 판정하지 않는다. [DescriptiveComplexity 범위 절](https://github.com/PierreSenellart/descriptive-complexity#scope)

두 전용 라이브러리는 Mathlib 자체의 빈자리를 크게 줄였다. 하지만 두 라이브러리는 서로 다른 계산 모형과 환원을 쓴다. 연구 지도는 정리 이름만 합치지 말고, 각 명제의 모형·부호화·환원 개념을 함께 기록해야 한다.

## 4. leanblueprint

### 4.1 기본 대상과 관계

leanblueprint는 LaTeX로 쓴 형식화 설계서를 HTML/PDF와 의존 그래프로 만드는 plasTeX 플러그인이다. 기본 그래프 노드는 `definition`, `lemma`, `proposition`, `theorem`, `corollary` 환경이다. `\uses{label,...}`가 진술 또는 증명의 선행 노드를 가리킨다. `\proves{label}`는 떨어져 있는 증명 환경을 진술에 연결한다. [leanblueprint 공식 README](https://github.com/PatrickMassot/leanblueprint)

내부 `DepGraph`는 노드 집합, 진술 간선 집합, 증명 간선 집합을 따로 보관한다. 모든 간선은 해소된 소스 노드와 대상 노드의 쌍이다. 찾지 못한 `\uses` 라벨은 오류를 기록하고 간선 집합에 넣지 않는다. 기본 출력은 추이적으로 중복된 간선을 줄인다. [plastexdepgraph 공식 구현](https://github.com/PatrickMassot/plastexdepgraph/blob/master/plastexdepgraph/Packages/depgraph.py)

### 4.2 상태 모델

상태는 진술 축과 증명 축으로 나뉜다.

- `\leanok`는 둘러싼 진술 또는 증명에 `leanok = true`를 기록한다.
- `\notready`는 진술이 아직 형식화 준비가 안 됐다고 기록한다.
- `can_state`는 진술 선행 노드가 모두 `leanok`이고 `notready`가 아닐 때 계산된다.
- `can_prove`는 진술과 증명의 선행 노드가 모두 `leanok`일 때 계산된다.
- `proved`는 연결된 증명 환경이 `leanok`일 때 계산된다.
- `fully_proved`는 해당 노드와 모든 조상의 증명이 형식화됐을 때 계산된다. 정의는 이 조상 검사에서 증명 완료 대상으로 보지 않는다.
- `\mathlibok`는 Mathlib 병합 표지를 추가한다.

이 계산과 색상 우선순위는 플러그인 코드에 직접 정의돼 있다. [leanblueprint 상태 계산 코드](https://github.com/PatrickMassot/leanblueprint/blob/master/leanblueprint/Packages/blueprint.py)

### 4.3 검사 강도

`\leanok`는 자동 검사 결과가 아니라 작성자의 주장이다. 플러그인은 이 명령을 만나면 Boolean 값을 설정한다. `\lean{...}`는 자연어 노드와 Lean 선언 이름을 연결한다.

`leanblueprint checkdecls`는 연결된 이름이 빌드된 Lean 환경에 존재하는지만 검사한다. 검사기 코드는 각 줄에 대해 `env.contains`를 호출한다. 선언의 형식문이 LaTeX 문장과 같은 뜻인지 검사하지 않는다. 선언이 공리나 `sorry`에 의존하는지도 검사하지 않는다. [checkdecls 공식 구현](https://github.com/PatrickMassot/checkdecls/blob/master/Main.lean)

생성 템플릿의 CI는 별도로 Lean 프로젝트를 빌드하고 lint한다. 이 빌드는 Lean 소스의 형식 정합성을 검사한다. 그러나 `\leanok` 표지와 Lean 증명 상태의 일치를 직접 계산하지 않는다. [leanblueprint CI 템플릿](https://github.com/PatrickMassot/leanblueprint/blob/master/leanblueprint/templates/blueprint.yml)

### 4.4 차용 판단

차용할 구성은 진술 의존과 증명 의존의 분리, 준비 가능 상태의 역방향 계산, 조상 완료 상태, 자연어 노드와 형식 선언의 연결, 이슈 링크다. 그대로 차용하면 안 되는 구성은 사람이 선언하는 `leanok`다. 연구 지도에서 확실 상태는 증거 좌표와 검사 결과에서 계산해야 한다.

## 5. Equational Theories 프로젝트

### 5.1 기본 대상과 결과 원장

프로젝트는 마그마 항등식 4,694개를 `Equation1`부터 `Equation4694`까지 명명한다. `equation n := lhs = rhs` 명령은 마그마에 대한 명제와 자유 마그마 법칙을 함께 생성하고 둘의 동치를 증명한다. [항등식 명령 구현](https://github.com/teorth/equational_theories/blob/main/equational_theories/Equations/Command.lean) [기본 항등식 목록](https://github.com/teorth/equational_theories/blob/main/equational_theories/Equations/Basic.lean)

`@[equational_result]`는 그래프에 넣을 Lean 정리를 명시적으로 선택한다. 원장 항목은 선언 이름, 파일, 행, 결과 유형, `proven` Boolean을 가진다. 결과 유형은 함의, 한 마그마가 만족·반박하는 법칙 묶음, 무조건 성립 법칙이다. 속성 처리기는 정리의 형식을 파싱하고, 허용한 표준 공리 외의 공리 의존을 거부한다. [결과 원장 구현](https://github.com/teorth/equational_theories/blob/main/equational_theories/EquationalResult.lean)

반증은 별도 “반증 상태”만 붙이지 않는다. `Facts G [satisfied...] [refuted...]` 정리는 구체적 마그마가 어떤 법칙을 만족하고 어떤 법칙을 반박하는지 증명한다. 폐쇄 계산기는 만족 목록과 반박 목록의 곱을 비함의 간선으로 만든다. [Facts 구문](https://github.com/teorth/equational_theories/blob/main/equational_theories/FactsSyntax.lean) 작은 유한 마그마의 공식 예시는 `by decideFin!`로 사실 묶음을 증명한다. [작은 마그마 반례](https://github.com/teorth/equational_theories/blob/main/equational_theories/SmallMagmas.lean)

### 5.2 상태 모델과 폐쇄 계산

`Outcome`은 아홉 상태를 직접 정의한다.

- 명시적 증명 참
- 추론된 증명 참
- 명시적 추측 참
- 추론된 추측 참
- 미해결
- 추론된 추측 거짓
- 명시적 추측 거짓
- 추론된 증명 거짓
- 명시적 증명 거짓

폐쇄 계산은 먼저 증명된 결과만 넣어 명시·추론 증명 상태를 채운다. 다음에 추측까지 넣어 아직 미해결인 칸만 추측 상태로 채운다. 참 함의에는 반사·추이 폐쇄와 쌍대 관계를 적용한다. 반례는 함의의 선행·후행 폐쇄 방향에 맞춰 전파한다. 모순을 만나면 `Inconsistent conjectures!` 오류를 낸다. [폐쇄와 상태 행렬 구현](https://github.com/teorth/equational_theories/blob/main/equational_theories/Closure.lean)

`conjecture` 명령은 임시 공리로 문장을 정형화한 뒤, 정리 자체는 환경에서 제거하고 `proven = false`인 원장 항목만 남긴다. 따라서 추측은 Lean 정리와 섞이지 않는다. 현재 `Conjectures.lean`에는 일반·유한 추측 항목이 없다. [추측 명령과 원장](https://github.com/teorth/equational_theories/blob/main/equational_theories/EquationalResult.lean) [현행 추측 파일](https://github.com/teorth/equational_theories/blob/main/equational_theories/Conjectures.lean)

### 5.3 현행 데이터와 검사 강도

공식 대시보드는 일반 그래프의 22,033,636개 순서쌍을 다음과 같이 집계한다.

| 상태 | 수 |
|---|---:|
| 명시적 증명 참 | 10,657 |
| 추론된 증명 참 | 8,167,622 |
| 명시적 증명 거짓 | 586,925 |
| 추론된 증명 거짓 | 13,268,432 |
| 증명 없음 | 0 |

합계는 (4694^2=22,033,636)이다. 일반 그래프는 100% 분류됐다. 유한 마그마 그래프에는 증명 없음이 2개 남아 있다. [Equational Theories 공식 대시보드](https://teorth.github.io/equational_theories/dashboard/)

명시적 증명과 반례 정리는 Lean 빌드에서 커널 검사를 받는다. 속성 처리기는 정리 형식과 공리 의존도 검사한다. 반면 2,200만 개 각 칸에 Lean 증명 항을 저장하지 않는다. `Closure.lean`의 실행 결과가 추론 상태를 채운다. 따라서 “모든 간선을 Lean이 개별 증명했다”라고 쓰면 안 된다.

`extract_implications outcomes`는 전체 상태 행렬을 JSON으로 낸다. `unknowns`는 미해결 간선을 낸다. `raw --full-entries`는 출처 파일과 행을 포함한 원장을 낸다. [추출기 구현](https://github.com/teorth/equational_theories/blob/main/scripts/extract_implications.lean) 대시보드 생성기는 이 출력에서 증명 완료율과 추측 포함 완료율을 따로 계산한다. [대시보드 생성기](https://github.com/teorth/equational_theories/blob/main/scripts/generate_dashboard.py)

### 5.4 차용 가능한 구성

표현 체계가 검토할 수 있는 구성은 결과 원장의 명시적 선택, 증명과 추측의 분리, 명시와 추론의 분리, 반례 전파, 모순 검사, 전체 행렬과 원자료의 동시 export다. 이 구성을 적용하려면 닫힌 항등식 우주 전제를 제거해야 한다. P vs NP 연구 지도의 객체와 관계는 실행 중에 추가·비활성화·분화되기 때문이다.

## 6. 추가 후보

### 6.1 Verso Blueprint

Verso Blueprint는 Lean 안에서 작성하는 Blueprint 도구다. 라벨이 있는 정의·정리·증명 노드, 진술 의존, 증명 의존, 부모 그룹, 소유자, 우선순위, 출처 문서와 페이지 좌표를 기계 판독 manifest로 낸다. 명시적 의존과 Lean 선언에서 자동 추출한 의존은 `origin`으로 구별한다. [Verso Blueprint 공식 README](https://github.com/leanprover/verso-blueprint)

이 도구는 leanblueprint와 달리 Lean 선언을 분석해서 진행 상태를 자동 계산한다. 선언 상태 `ProvedStatus`는 `proved`, `missing`, `axiomLike`, `containsSorry`를 구별한다. `sorry`가 형식문의 유형에 있는지 증명 본문에 있는지도 나눈다. [Verso Blueprint 선언 상태 코드](https://github.com/leanprover/verso-blueprint/blob/v4.34.0/src/VersoBlueprint/Data.lean) [상태 판정 코드](https://github.com/leanprover/verso-blueprint/blob/v4.34.0/src/VersoBlueprint/ProvedStatus.lean)

그래프의 진술 상태는 `blocked`, `ready`, `formalized`, `mathlib`다. 증명 상태는 `none`, `ready`, `incomplete`, `formalized`, `formalizedWithAncestors`다. 그래프 데이터는 `statementUses`와 `proofUses`를 따로 보존한다. 찾지 못한 참조와 외부 Lean 선언도 경고 필드로 보존한다. [Verso Blueprint 그래프 상태와 스키마](https://github.com/leanprover/verso-blueprint/blob/v4.34.0/src/VersoBlueprint/Graph.lean)

Verso Blueprint는 조사한 도구 중 연구 지도의 표시·작업 셸에 가장 많은 직접 구성을 제공한다. 그러나 상태는 “Lean 형식화 진행”을 뜻한다. 문헌 공인, 자체 검토, 탐사 가설, 비활성 반증 이력은 추가 표현 규칙과 검사가 필요하다. 끝점 없는 간선도 기본 그래프 대상이 아니다.

### 6.2 MMT와 MathHub

MMT는 특정 논리나 기초에 고정되지 않는 수학 지식 표현·관리 프레임워크다. 이론은 선언의 모듈이다. include와 view는 이론 사상의 그래프를 만든다. view는 정의역 선언을 공역 식으로 보내며 형식 체계의 typing 판단을 보존해야 한다. [MMT 공식 개요](https://uniformal.github.io/doc/) [MMT 모듈과 이론 사상](https://uniformal.github.io/doc/language/modules)

MMT의 관계 저장소는 URI와 단항·이항 관계를 기계 관리하고 질의한다. import 빌드가 관계 차원을 자동 생성한다. [MMT 관계 저장소와 질의](https://uniformal.github.io/doc/api/queries) MMT는 구조 검사, 기초별 검증 플러그인, 변경 관리도 제공한다. 검증 강도는 선택한 기초와 플러그인에 달린다.

MMT 모듈과 선언에는 임의 메타데이터를 붙일 수 있다. 그래서 확실·불확실, 증거 좌표, 활성·비활성 상태를 별도 어휘로 인코딩할 수 있다. MMT가 이 연구 의미를 직접 제공하거나 검사하지는 않는다. MMT 도입은 여러 증명 보조기와 문헌 온톨로지를 한 그래프로 연결할 때 정당화된다. 초기 P vs NP 지도 하나에는 비용이 크다.

## 8. 현행 티켓에 넘길 입력

현행 설계는 다음 조사 결과를 입력으로 사용한다.

- 도구의 직접 지원과 사용자 규약으로 만든 표현을 구별한다.
- 대상을 표현할 수 있다는 사실과 그 의미를 도구가 검사한다는 사실을 구별한다.
- Lean 커널 수락, 자연어 의미 대응과 연구 작업 상태를 한 판정으로 합치지 않는다.
- 외부 계산 복잡도 라이브러리의 정리 이름만 보고 같은 정의라고 가정하지 않는다. 계산 모형, 부호화와 환원 종류를 대조한다.
- Verso Blueprint의 manifest, 소유권과 진행 상태는 작업 표시 구성의 후보다.
- Equational Theories의 결과 원장, 명시·추론 분리와 모순 검사는 재사용 후보이다. 닫힌 항등식 우주 전제는 제거해야 한다.
- MMT는 여러 형식 체계를 연결할 때 유용할 수 있다. 한 Lean 중심 연구 인스턴스에는 도입 비용이 크다.

`do-math` 통합 설계는 작업 상태와 검증 도구를 선택한다. 핵심 Lean 정의 티켓은 외부 라이브러리의 수학 내용을 참고하고 우리 Lean 언어로 옮기는 범위를 정한다. 초기 연구 지도의 뭉텅이, 연결 가설과 끝점 없는 간선은 현행 스키마 요구가 아니다.

직접 읽은 공식 자료는 다음 일곱 묶음이다.

1. Lean 공식 참조와 Mathlib 공식 소스·API
2. Complexitylib 공식 저장소와 생성 API
3. DescriptiveComplexity 공식 저장소와 현행 결과·범위 표
4. leanblueprint, plastexdepgraph, checkdecls 공식 저장소의 README·상태·그래프·검사 코드
5. Equational Theories 공식 저장소의 항등식 명령, 결과 원장, 추측, Facts, 폐쇄, 추출기, 대시보드 생성기와 공식 대시보드
6. Verso Blueprint 공식 저장소의 README, 선언 상태, 그래프 상태·스키마
7. MMT 공식 문서의 모듈, 이론 사상, 메타데이터, 관계 저장소, 검증 개요

Mathlib의 기능 부재 단정은 `Mathlib/Computability` 하위 29개 Lean 파일에 한정한다. Mathlib 전체의 모든 파일에서 우연히 정의한 동명 개념까지 전수 배제했다고 주장하지 않는다.

Complexitylib과 DescriptiveComplexity의 모든 증명 본문을 사람이 다시 증명하지 않았다. 공개 API의 정리 선언, 공식 빌드·공리 감사 계약, 공식 소스 구조를 확인했다.

Equational Theories의 22,033,636개 상태를 로컬에서 다시 생성하지 않았다. 공식 대시보드 수치를 상태 열거형, 폐쇄 코드, 대시보드 생성 코드와 대조했다. 일반 그래프의 “증명 없음 0”은 기준일의 공식 생성물에 대한 진술이다.

MMT에서 확실·불확실 연구 상태를 직접 검사하는 정본 어휘는 공식 자료에서 확인하지 못했다. MMT 행의 해당 기능은 모두 메타데이터 규약으로 판정했다.

추가 후보 조사는 Verso Blueprint와 MMT/MathHub에 한정했다. 이 보고서는 다른 후보가 없다고 단언하지 않는다.
