1# 초기화의 검사 경계, 정비와 관측
2
3이 문서는 신뢰 환경의 기록·확인, 큰 payload의 저장, 실행의 시작과 종료, 정상 정비와 운영 계측을 정하는 현행 실행 계약이다. 기계 확인·사용자 채택·형식 타당성·동일성·목표 충족은 각각 자기 근거로 판단한다.
4
5## 신뢰 환경 확인의 개요
6
7신뢰 환경 확인은 형식 검사에 쓰는 Lean·Mathlib·검사기가 채택한 판본 그대로이고 채택 뒤 우발적으로 바뀌지 않았음을 보이려고 한다. 우발적 변경은 업데이트, 재설치, 동기화, 실수, 디스크 손상에 따른 변경이다. 같은 사용자 권한을 가진 사람이나 AI가 툴체인이나 do-math 코드를 의도적으로 바꾸는 일은 막지 않는다.
8
9확인은 두 값으로 한다. 두 값과 그 기준을 담는 파일의 정의는 다음과 같으며, 구성의 세부는 아래 「판정 파일, 판본 식별과 지문」과 「툴체인 기록과 인스턴스 결박」이 정한다.
10
11- 판본 식별은 형식 검사가 어떤 Lean 명령·Lake 프로젝트·검사기를 쓰는지 고정하는 값이다. 형식 결과가 어느 환경에서 검사됐는지와, 게시 시점의 설치가 그 환경과 같은지를 이 값으로 판정한다.
12- 지문은 커널이 적재하는 `.olean`과 Lean 런타임 라이브러리의 파일마다 (상대 경로, 크기, 수정 시각, 생성 시각)을 모은 메타데이터 목록과 그 다이제스트다. 파일 내용을 읽지 않으므로 싸게 대조할 수 있고, 업데이트·재설치·손상처럼 메타데이터를 바꾸는 우발적 변경을 탐지한다. 세 값을 모두 보존한 내용 변경은 탐지하지 못하며, 그런 변경은 내용 해시 기준과 대조하는 선택적 전수 점검만 찾는다. 프로젝트의 git 트리·diff 해시인 프로젝트 소스 식별과 다른 개념이다.
13- 툴체인 기록은 한 머신의 인스턴스들이 함께 쓰는 Lean·Mathlib 설치 하나의 판본 식별과 기준 이력, 점검 이력을 담은 파일이다. 기준 항목은 지문 기준, 판정 파일 전건의 내용 해시 기준과 대표 검사 결과로 이루어진다. `setup_lean.py`만 이 파일을 쓰며, 기준 항목의 추가는 사용자와 운전자만 하는 재기록이다. 인스턴스는 읽기만 한다. 판본이나 판정 바이트가 다른 설치는 다른 기록이다. 인스턴스의 신뢰 환경은 툴체인 기록 하나를 가리키고 그 기록의 기준 항목 하나에 결박된다.
14
15`setup_lean.py`는 설치할 때 기준을 만들고, 인스턴스는 활성화와 형식 검사 직전에 기준을 현재 파일과 대조한다. 파일 내용 전체의 해시는 사용 경로에서 계산하지 않는다. 설치·재기록·요청한 전수 점검 때에만 계산한다.
16
17## 언제 무엇을 확인하는가
18
19| 시점 | 확인하는 것 | 읽는 파일 |
20|---|---|---|
21| 설치·교체: `setup_lean.py`, `--verify-only` | 판본 식별을 관측하고 첫 기준 항목(지문, 내용 해시, 대표 컴파일)을 기록한다. 같은 판본의 기존 기록이 현재 지문과 같으면 그 기록을 다시 사용한다. 기존 기록에 기준 항목을 덧붙이지 않는다. | 판정 파일 전건의 내용 |
22| 등록: `trust register`. 요청 형식은 [초기화 운전](초기화-운전.md) 5절 | 요청의 구조, 툴체인 기록의 스키마·ID·판본 식별, 요청이 결박한 기준 항목의 세 다이제스트(지문, 내용 해시, 대표 검사 요약), 현재 기준의 대표 검사 성공, 현재 기준에 대한 불일치 점검의 부재 | 툴체인 기록 파일만 |
23| 활성화: `trust_activate` | 등록 때와 같은 기록 확인, 현재 판본 식별, 현재 지문 | 판본 식별 파일, 판정 파일의 메타데이터 |
24| 형식 검사 1건, 전환의 기존 K 재검사 | 컴파일 전에 기록 확인과 현재 지문을 대조한다. 이어서 검사기가 구성된 명령, 실행 파일의 해석 경로, 판본 식별 파일을 대조한 뒤 컴파일한다. 컴파일 뒤에는 다시 관측하지 않는다. | 활성화와 같음 |
25| 동일성 `match` 게시, 목표 감사 `satisfied` 적용 | 활성 환경의 구조와 현재 판본 식별. 지문은 다시 대조하지 않는다. | 판본 식별 파일 |
26| 선택적 전수 점검: `setup_lean.py --check-contents` | 현재 기준의 내용 해시와 판정 파일 전건의 대조 | 판정 파일 전건의 내용 |
27
28게시 관문이 지문을 다시 보지 않는 이유는 비용과 효과의 차이다. 지문은 형식 검사 직전에 대조했고, 검사와 게시 사이에 설치가 우연히 바뀌는 일은 드물다. 그런 변경은 다음 형식 검사의 지문 대조에서 드러난다. 판본 식별은 싸므로 게시 때도 확인한다. 게시할 형식 결과의 `toolchain`이 환경의 판본 식별과 같은지는 K 사용 판정(`formal_usable`)이 확인한다. 같은 원문과 판본 식별이 유지되면 동일성 판정의 편입은 기존 형식 검사 결과를 재사용하며 Lean을 다시 실행하지 않는다.
29
30형식 검사는 컴파일 전 확인의 결과를 형식 결과의 `environment_check`에 남긴다. 여기에는 판본 식별 다이제스트, 관측한 지문 다이제스트, 사용한 결박이 들어간다. 이 기록은 추적용이며 게시 판정에는 쓰지 않는다. `status`와 상태 조회는 저장된 기록만 보고하고 설치 파일을 읽지 않는다.
31
32## 지문 불일치와 재기록
33
34현재 지문이 결박한 기준과 다르면 활성화는 환경을 활성화하지 않고, 형식 검사는 컴파일을 시작하지 않는다. 활성화는 전환 실패로 끝나고 이전 환경이 계속 효력을 가진다. 전환의 기존 K 재검사는 실패 결과로 기록되므로 그 전환은 활성화되지 않는다. 형식 검사는 달라진 파일 목록(`environment_check.changed_files`)을 보존하고 `formal_environment` 대기로 멈춘다. 지문이 같아도 검사기가 컴파일 직전에 승인된 판본 식별과 다른 점을 찾으면 형식 검사는 같은 대기로 멈춘다. 이때 도구 모음이나 프로젝트 입력 파일이 달라졌으면 그 목록(`identity_errors`)을 함께 보존하고, 실행 명령이나 실행 파일 경로가 달라졌으면 그 사유만 보존한다. 이 대기의 다음 담당은 `trust_governance`이며, 다음 담당은 원인을 둘로 나눈다.
35
361. **판본 식별도 다르다.** 툴체인이 실제로 바뀌었다. `setup_lean.py`로 새 툴체인 기록을 만들고 `trust register`와 `trust transition`으로 옮긴다. 기존 K는 전환의 재검사를 거친다.
372. **판본 식별은 같고 지문만 다르다.** 재설치, 캐시 재다운로드, 복원처럼 같은 바이트를 다시 깐 경우가 대부분이다. 사용자나 운전자가 `setup_lean.py --rerecord`를 실행해 판단한다.
38
39재기록은 사용자와 운전자만 실행한다. 설치 복구 AI를 포함한 AI 역할은 재기록하지 않는다. 형식 검사와 활성화 검사는 기준과 현재 파일을 대조할 뿐 기준 항목을 기록하지 않는다. 검사가 기준을 자동으로 새로 기록하면 우발적 변경을 탐지하는 목적이 사라지기 때문이다. 그래서 예상하지 못한 지문 변화는 사람이 재기록할 때까지 연구를 멈추게 하고, 반드시 사람에게 알려진다.
40
41`--rerecord`는 판정 파일 전건의 내용 해시를 새로 계산해 현재 기준의 내용 해시와 대조한다.
42
43- 내용이 모두 같으면 메타데이터만 바뀐 것이다. 대표 컴파일을 다시 수행하고, 통과하면 새 지문·같은 내용 해시·새 대표 검사 결과로 기준 항목을 기준 이력에 덧붙인다. 바이트가 같으므로 전환이나 K 재검사를 요구하지 않는다.
44- 내용이 하나라도 다르거나 현재 판본 식별이 기록과 다르면 재기록을 거부하고 다른 파일 목록을 출력한다. 판정에 쓰는 바이트가 바뀌었으므로 1번과 같이 새 기록과 전환이 필요하다.
45
46인스턴스는 다음 활성화나 형식 검사에서 덧붙은 기준을 스스로 따라간다. 이를 **재결박**이라 한다. 재결박은 세 조건이 모두 성립할 때만 일어난다. 현재 지문이 툴체인 기록의 현재 기준과 같고, 그 기준이 인스턴스가 결박한 기준과 다르며, 판본 식별이 기록과 현재 파일 모두에서 인스턴스 기록과 같아야 한다. 실행기는 결박을 새 기준으로 바꾸고 `trust_environment_rebound` 사건에 이전·새 결박과 그 기준 항목의 기록 시각을 남긴 뒤 검사를 계속한다. 현재 지문이 기록의 현재 기준과도 다르면 재기록이 아직 없는 것이므로 위의 판별로 돌아간다.
47
48멈춘 작업은 별도 제어 없이 다시 진행한다. 실행기는 `run`의 주 루프를 한 번 돌 때마다 `formal_environment` 대기를 살펴, 툴체인 기록 파일이 바뀌었거나(재기록이나 점검 결과의 추가) 활성 환경이 바뀌었으면 같은 활동의 후속으로 다시 배정한다. 실행기는 이 변화가 원인을 해소했는지 판단하지 않는다. 다시 배정된 형식 검사가 같은 확인을 수행하며, 원인이 남아 있으면 같은 대기로 돌아간다. 게시 관문에서 판본 식별이 달라 편입하지 못한 봉인 결과도 원문을 보존한 채 `submission_publication` 대기로 같은 변화를 기다린다. 변화가 생기면 모델을 다시 부르지 않고 같은 결과의 편입을 다시 시도한다. 변화가 없으면 같은 입력으로 재시도하지 않는다.
49
50## 선택적 전수 점검
51
52`setup_lean.py --check-contents`는 요청할 때만 실행한다. 예약 감독은 이 점검을 주기적으로 실행하지 않는다. 점검은 현재 판정 파일 전건의 내용을 해시해 현재 기준의 내용 해시와 대조하고, 결과를 툴체인 기록의 점검 이력에 덧붙인다. 결과는 `passed` 또는 `mismatch`와 다른 파일 목록이며, 툴체인 기록에만 남고 인스턴스의 연구 상태에는 쓰지 않는다. 인스턴스는 다음 활성화나 형식 검사에서 기록을 읽어, 현재 기준에 `mismatch`가 있으면 멈춘다.
53
54현재 기준에 대해 `mismatch`가 기록되면 그 툴체인 기록을 쓰는 인스턴스는 다음 활성화나 형식 검사에서 멈춘다. 파일을 복구한 뒤 `--rerecord`가 새 기준 항목을 덧붙이면 다시 진행한다. 점검은 연구 실행기와 별개의 명령이며, 인스턴스는 기록을 읽기만 하므로 점검하는 동안에도 연구 실행은 막히지 않는다.
55
56## 판정 파일, 판본 식별과 지문
57
58판정에 들어가는 파일만 확인한다.
59
60- 구성된 Lean 명령의 첫 실행 파일과 인자 가운데 `.exe`·`.dll` 파일
61- Lake 프로젝트의 `lean-toolchain`, `lake-manifest.json`, lakefile과 프로젝트 root의 `.lean` 입력
62- Lean 설치와 Lake 프로젝트 아래의 `.olean`과 Lean 런타임 공유 라이브러리(`.dll`, `.so`, `.dylib`). Lean 커널은 `lean.exe`가 아니라 이 라이브러리에 들어 있다.
63- 형식 검사기 `formal.py`
64
65`.lake` 안의 `.lean` 소스, `.ilean`, `.trace`, `.hash`, `.c`, `.ir`, git 메타데이터는 커널 판정에 들어가지 않으므로 확인하지 않는다.
66
67**판본 식별**은 `inspect_toolchain`이 관측한 `toolchain` 객체다. `lean --version` 출력, 구성된 명령과 첫 실행 파일의 경로·SHA-256, 명령 인자의 `.exe`·`.dll` SHA-256, 검사기 `formal.py`의 경로·SHA-256을 담는다. 실행 중인 검사기는 경로가 아니라 적재한 모듈 바이트의 SHA-256으로 판본 식별의 검사기와 대조한다. 그래서 작업 공간 미리보기처럼 zip에서 적재한 같은 바이트도 같은 검사기다. 기록된 경로의 파일은 그 SHA-256과 계속 대조한다. Lake 프로젝트를 쓰면 `lean-toolchain`·`lake-manifest.json`·lakefile의 SHA-256, **프로젝트 소스 식별**(`project.source_identity`: 프로젝트의 추적된 git 트리, 작업 트리 diff, 추적되지 않은 입력의 해시), Lake가 구성한 검색 경로도 담는다. 검색 경로는 Lean 설치와 Lake 프로젝트 안에 있어야 한다. 판본 식별 다이제스트는 이 객체의 정규 JSON SHA-256이다.
68
69**지문**은 Lean 설치와 Lake 프로젝트를 root로 삼아 `os.scandir`로 판정 모듈과 런타임 라이브러리를 열거한 목록이다. 파일마다 root 이름을 앞에 붙인 `/` 구분 상대 경로, 크기, 수정 시각(ns), 생성 시각(ns)으로 한 행을 만든다. 두 시각은 JSON 안전 정수 범위를 넘으므로 십진 문자열로 적는다. 지문 다이제스트는 행을 상대 경로 순으로 정렬한 정규 JSON의 SHA-256이다. 지문을 만들 때 파일 내용은 읽지 않는다.
70
71## 툴체인 기록과 인스턴스 결박
72
73툴체인 기록은 `.skill-workspace/do-math-toolchains/records/<기록 ID>.json`에 있고 `schema` 값은 `do-math-toolchain-record/1`이다. 인스턴스는 기록을 읽을 때마다 JSON Schema로 검증하며, 다른 스키마 판본의 기록은 읽지 않는다. 기록은 다음을 담는다.
74
75- `identity`: 판본 식별. 한 기록 파일 안에서 바뀌지 않는다.
76- `baselines`: 기준 이력. 마지막 항목이 현재 기준이다. 항목 하나는 지문 기준(행 목록과 다이제스트), 내용 해시 기준(같은 파일 전건의 SHA-256 목록과 다이제스트), 대표 검사 결과, 기록 시각으로 이루어진다.
77- `checks`: 점검 이력. 항목 하나는 점검 시각, 대조한 기준 항목 번호, 결과, 다른 파일 목록이다.
78
79대표 검사 결과는 Mathlib 프로젝트면 `import Mathlib`, `n + 0 = n`, 실수 `norm_num` 예제를, 프로젝트가 없는 명령이면 core 예제를 구성된 명령으로 컴파일한 결과다. source, 명령, 종료 코드, 출력, 시각을 담는다. 대표 검사의 요약 해시는 명령, source SHA-256, 종료 코드, 표준 출력, 표준 오류, 시작·종료 시각을 담은 객체의 정규 JSON SHA-256이다. 대표 검사의 통과는 전체 라이브러리 재검증이나 연구 목표의 해결이 아니다.
80
81기록 ID는 판본 식별 다이제스트와 첫 기준 항목의 내용 해시 다이제스트를 함께 해시한 값이다. 판본이나 판정 바이트가 달라진 설치는 새 ID의 새 기록 파일을 얻고, 옛 기록 파일은 그대로 남는다. 한 기록 파일에 허용하는 변경은 기준 항목의 추가(재기록)와 점검 결과의 추가 둘뿐이다.
82
83인스턴스의 환경 기록(`trust_environments[<환경 ID>]`)에는 판본 식별(`toolchain`), 허용 공리, 채택 출처, 툴체인 기록의 절대 경로와 ID(`toolchain_record`), 상태와 활성화 검사 결과(`validation_receipt`)가 들어간다. 설치 파일 목록은 넣지 않는다. 인스턴스가 받아들인 기준 항목은 환경 기록 밖의 `runtime.trust_bindings[<환경 ID>]`에 **결박**으로 둔다. 결박은 기준 항목 번호와 그 항목의 지문 다이제스트, 내용 해시 다이제스트, 대표 검사 요약 해시다. 재결박은 이 결박만 바꾸므로 환경 기록과, 환경 기록에 기댄 형식 결과·동일성 검토의 전제는 바뀌지 않는다. 인스턴스는 툴체인 기록 파일의 바이트 해시에 결박하지 않는다. 재기록이 기록 파일을 다시 써도 판본 식별이 같은 한 인스턴스는 계속 그 기록을 읽는다.
84
85## `setup_lean.py`의 모드
86
87| 명령 | 동작 | 종료 코드 |
88|---|---|---|
89| 인자 없음 | Lean과 Mathlib 캐시를 설치하고 툴체인 기록을 만들거나 확인한 뒤 준비 표지를 쓴다. | 0 성공, 1 대표 컴파일 실패 또는 재기록 필요, 2 실행 오류 |
90| `--verify-only` | 내려받지 않고 설치된 명령의 툴체인 기록을 만들거나 확인한다. 명령은 `--command-file`로 지정할 수 있다. | 위와 같음 |
91| `--rerecord` | 사용자와 운전자만 실행한다. 위 `지문 불일치와 재기록`의 절차로 기준 항목을 덧붙인다. | 0 기록, 1 거부, 2 실행 오류 |
92| `--check-contents` | 선택적 전수 점검 | 0 통과, 1 불일치, 2 실행 오류 |
93| `--inspect-only` | 판본 식별만 관측하고 기록하지 않는다. | 0 성공 |
94
95설치와 `--verify-only`는 먼저 판본 식별이 같은 기록들을 찾아, 현재 기준의 지문이 현재 지문과 같고 불일치 점검이 없는 기록이 있으면 그 기록을 다시 사용한다. 그런 기록이 없으면 판정 파일 전건의 내용 해시로 기록 ID를 계산한다. 그 ID의 기록 파일이 이미 있으면(같은 판본·같은 내용이지만 지문이 다르거나 불일치 점검이 있는 경우) 기준을 덧붙이지 않고 `rerecord_required`로 끝나고, 없으면 대표 컴파일을 거쳐 새 기록을 만든다. `--rerecord`와 `--check-contents`는 `--record <기록 ID>`로 대상을 지정한다. 생략하면 현재 판본 식별의 기록이 정확히 하나일 때 그 기록을 쓴다. `--records-dir`는 기록 디렉터리를, `--evidence-dir`는 대표 컴파일 증거의 상위 디렉터리를 바꾼다. 증거 디렉터리는 Lean 설치와 Lake 프로젝트 밖에 있어야 한다. `--trust-file <새 경로>`는 설치·`--verify-only`·`--rerecord`가 성공한 뒤 결과 기록의 현재 기준으로 등록 요청을 새 파일에 쓴다.
96
97모든 모드는 결과를 표준 출력에 JSON 객체 하나로 출력한다. 설치의 내려받기 안내와 Lake 진행 출력은 표준 오류로 나간다. `status`는 `recorded`, `passed`, `mismatch`, `failed`, `refused`, `rerecord_required`, `error` 가운데 하나이고, 성공하면 `record_path`, `record_id`, `binding`을, 거부나 불일치면 `reason`과 다른 파일 목록(`mismatched`)을 함께 담는다. 기록을 쓰는 모드는 `records/.lock`의 OS 잠금으로 서로 배제하고, 기록을 읽고 이력을 덧붙인 뒤 원자적으로 교체한다. 다른 작성자가 잠금을 쥐고 있으면 기다리지 않고 `status: error`, 종료 코드 2로 끝난다. 잠금은 그 프로세스가 끝나면 OS가 풀므로 사람이 지울 파일은 없다. 인스턴스는 잠금을 잡지 않는다.

99## 남는 위험
100
101- 크기, 수정 시각, 생성 시각을 모두 보존한 채 내용이 바뀌는 손상(비트 부패 등)은 사용 경로에서 탐지하지 못한다. 선택적 전수 점검만 찾으며, 누군가 점검을 요청할 때까지 드러나지 않을 수 있다.
102- NTFS는 같은 디렉터리에서 파일을 지우고 짧은 시간(기본 15초) 안에 같은 이름으로 다시 만들거나 그 이름으로 옮겨 넣으면 이전 생성 시각을 새 파일에 물려준다. 이런 교체가 크기와 수정 시각까지 보존하면 지문이 같다. 원래 수정 시각을 복원하는 압축 해제가 이 경우에 해당할 수 있다. 같은 판본의 캐시는 내용도 같으므로 결과가 같지만, 크기가 같은 다른 내용이 이렇게 들어오면 전수 점검에서만 드러난다.
103- `.lake` 안의 패키지 소스와 부산물은 확인하지 않는다. 커널 판정에 들어가지 않기 때문이다. 프로젝트 root의 추적 입력이 바뀌면 프로젝트 소스 식별이 달라지므로 탐지한다.
104- 컴파일 도중이나 검사와 게시 사이의 변경은 그 결과에서 잡지 않는다. 다음 형식 검사의 지문 대조에서 드러난다.
105- 의도적 변조는 다루지 않는다. 현행 계약은 같은 OS 사용자 권한의 작업자를 격리하지 않는다.

107## 불변 payload와 조회
108
109큰 불변 값과 큰 불변 문자열은 저장 코덱에서 내용 주소형 artifact로 한 번 보존한다. 레코드 파일의 `payloads`는 JSON 좌표, artifact 경로, SHA-256, 바이트 수를 결박한다. 해당 좌표의 물리 표현은 null이며, 읽기는 정확한 artifact를 검사해 논리 값을 복원한다. 한 프로세스가 같은 저장소에서 이미 대조한 artifact는 불변이므로 다시 해시하지 않는다. 작은 값은 인라인으로 저장한다. 이것은 현행 인코딩이며 옛 대형 인라인 상태를 자동 변환해 읽는 호환 경로가 아니다.
110
111`read --path`는 실제 파일 바이트를 반환한다. 레코드 조회는 복원된 논리 레코드를 반환하며, 외부 payload가 있으면 `payload_refs`와 `json_pointer_scope=decoded_record`로 차이를 표시한다. 파일 해시와 논리 레코드 해시를 혼동하지 않는다. 사용자 원문의 코드 포인트와 UTF-8 바이트는 바꾸지 않는다.
112
113한 프로세스는 같은 Git OID·계약 판본의 검증 결과를 저장소 객체 사이에서 공유한다. 이 프로세스가 게시한 head는 게시 전에 후보로 검증한 상태를 그 head의 검증 결과로 삼고 다시 읽어 검증하지 않는다. 기동 때 읽은 head나 CAS 충돌 뒤 다른 기록자가 게시한 head처럼 밖에서 온 head는 처음 읽을 때 전체를 검증한다. 후보 검증은 부모와 같은 레코드의 레코드 단위 검사를 되풀이하지 않고, 관계·식별·의미 규칙은 상태 전체에 적용한다. 반환되는 가변 레코드는 분리하고 큰 payload는 변경할 수 없는 값으로 공유한다. 변경하려면 새 값을 저작한다. 최종 expected-head CAS, 참조·권한·불변 기록 검사는 계속 적용한다. writer lock을 쥔 동안에는 최종 CAS가 ref의 유일한 비교다. 저장소의 물리 경계(재분석 지점, 볼륨, 최종 경로)는 저장소를 열 때 확인하고, Git 오류가 나면 다시 확인한다.
114
115현재 레코드가 더 이상 참조하지 않는 payload도 Git에는 불변 원문으로 남는다. 나중에 같은 내용을 다시 참조하면 기존 바이트를 대조해 재사용한다. 상태 코덱과 별도 artifact가 같은 경로를 제시하면 바이트가 일치해야 하며, 검증 뒤 다른 바이트로 덮어써 게시하지 않는다.
116
117역할 입력 생성기는 큰 과거 제어 요청을 같은 고정 입력의 상세 파일로 보존하고 `request_source_ref`를 제공한다. 이 변환은 참조 목록과 제출 검사 문맥을 만들기 전에 수행한다. 요청 종류·ID·원문 좌표와 미결 의무는 유지한다. 상세 원문은 기존 source 읽기 도구로 읽는다. 단순히 prompt의 끝을 자르거나 불편한 실패 기록을 지우지 않는다.
118
119## 시작과 종료
120
121배정할 로컬 실행에는 프로세스를 만들기 전에 `launch_ticket`을 기록한다. ticket은 실행·프로필, 소유 실행기의 host/session·PID·정확한 생성 FILETIME, 유일한 Job 이름과 시작 단계를 결박한다. native 실행은 그 이름으로 Job을 독점 생성한다. 기존 이름과 충돌하면 다른 Job에 붙거나 그것을 종료하지 않는다.
122
123ticket 공개 → suspended root 생성 → 시작 정체성 공개 → 현재 권한 확인 → resume 순서를 지킨다. adapter가 명확하게 프로세스를 만들지 못한 경우와, 시작 정보가 단지 없는 경우를 구별한다. `not_started`는 실제 시작 실패 결과이며 메타데이터 부재에서 추측하지 않는다.
124
125복구는 이전 소유 실행기가 더 이상 시작할 수 없는지, 같은 host/session의 알려진 Job이 비었는지 확인한다. 다른 호스트·세션, 접근 실패, 살아 있는 이전 owner는 종료 확인이 아니다. PID 재사용은 생성 FILETIME으로 구별한다. 종료 확인 전에는 슬롯을 반환하거나 후속 실행을 시작하지 않는다. 원격 공급자의 종료는 별도 unknown 범위다. 옛 ticket 없는 미확정 실행의 종료를 소급 확정하지 않는다.

127## 정상 정비
128
129사용자 대화/운전자는 다음 공개 명령으로 정비 fence를 만든다. 내부 연구 역할이 이 명령으로 스스로 권한을 바꾸지 않는다.
130
131```powershell
132python .agents/skills/do-math/scripts/do_math.py quiesce --repository <repo> --instance <RI-ID> --reason "설치 교체"
133python .agents/skills/do-math/scripts/do_math.py status --repository <repo> --instance <RI-ID> --json
134```
135
136`effect=applied`는 새 배정을 막는 정비 fence가 정본에 적용됐음을 뜻한다. 기존 실행의 종료와 자원 정산은 별도로 확인한다. `maintenance_fence.state`가 `quiescent`이고 실제 실행기 프로세스가 끝나 writer lock을 놓은 것을 확인한 뒤 설치를 교체한다. `draining`은 진행 중 계산·시작·회수를 정산하는 상태다. `blocked`에는 미종료 실행과 미반환 예약이 표시된다. 이 상태에서 프로세스가 없을 것이라고 추측해 넘어가지 않는다.
137
138fence는 새로운 배정을 막고 기존 실행을 정상 정산한다. 오래 걸린다는 이유만으로 연구 계산을 강제 종료하지 않는다. 종료를 요구할 때는 기존 권한·체크포인트·정지 절차를 사용한다. 로컬 실행이 끝난 뒤 남은 봉인 제출물은 보존하고 정비 후 다시 현재성을 확인해 편입한다.
139
140```powershell
141python .agents/skills/do-math/scripts/do_math.py release-quiesce --repository <repo> --instance <RI-ID> --fence <만든-제어-ID> --reason "설치 검증 완료"
142python .agents/skills/do-math/scripts/do_math.py operator start --repository <repo> --instance <RI-ID>
143```
144
145해제는 지정한 현재 fence에만 효력이 있다. 사용자 pause나 HOLD를 해제하지 않는다. operator 출처는 user 출처의 정비 fence를 해제할 수 없다. 예약 감독도 fence가 있으면 연구를 새로 시작하지 않는다. 계약·저장 형식을 변경한 프리알파 설치는 새 인스턴스로 검증하며, 기존 기록을 임의 변환하지 않는다.

155운영 단계는 고정 연구 snapshot과 다른 로컬 관측으로 표시하며 파일 해시·관측 시각을 함께 둔다. 완료하지 못한 span의 종료 시각을 채우지 않는다. 겹친 span의 시간을 합쳐 실제 경과 시간이라고 하지 않는다. 파일마다 Git commit을 만들지 않고 진행 기록은 제한된 주기로 갱신한다. 계측 장애는 알려 주되 새로운 연구 권한이나 수학적 승인을 만들지 않는다.

157운영 계측 오류는 `operations/errors/`의 실행별 제한된 기록에 실패 연산·상대 경로·예외 유형·errno/winerror·최초/최근 시각·횟수를 보존한다. 오류 문구에 원 요청·명령·크리덴셜은 싣지 않는다. `operation_progress.telemetry_errors`에서 이 진단을 볼 수 있다.

159로컬 상태·제어·보고 파일은 임시 파일을 완성한 뒤 같은 디렉터리의 이름을 원자적으로 교체한다. Windows의 공통 읽기는 삭제 공유를 허용하고, 교체는 `FileRenameInfoEx`의 `REPLACE_IF_EXISTS | POSIX_SEMANTICS`를 사용한다. 이 기능을 지원하는 Windows 파일 시스템이 필요하다. 이미 열린 독자는 이전 파일을 끝까지 읽고 새로 연 독자는 새 파일을 읽는다. 접근·공유·잠금 오류(WinError 5·32·33)에는 같은 이름 교체만 최대 여섯 번 시도하며, 연구 실행이나 제어 요청을 재수행하지 않는다. 실패가 계속되면 오류와 임시 파일을 보존한다. Git 정본·입력 파일의 기존 물리 경계 검사는 유지한다. 계측 오류 기록 자체는 교체 장애를 남길 수 있도록 별도 기록하며, 불완전한 진단은 읽기 실패이지 정본 상태가 아니다.
