24. 문서의 책임을 실제 코드에서 찾아가기

한 기능의 입력 경계·판단·상태 적용·시험을 연결해 찾습니다.

새 필드의 의미를 바꾸려 할 때 실행기 한 곳만 고치면 충분하지 않을 수 있습니다. 생산자는 옛 구조를 내고 수신자는 새 구조를 기대하면, 올바른 연구 결과도 반려됩니다. do-math의 개발 원칙은 현재 계약 하나를 문서·호출부·스키마·검사·시험·예시에 함께 반영하는 것입니다.

입력에서 상태 공개까지 내려가 보기

공개 명령은 scripts/do_math.py에서 시작해 cli.py가 인자·JSON과 반환을 다룹니다. engine.py와 영역별 *_engine.py는 상태 전이와 후속을 연결합니다. scheduler.py는 병렬 호출을 배정하고, parallel.py는 오래 걸리는 호출을 수행하게 합니다. 상태 갱신과 정지 이유의 판단은 소유 실행기 쪽에서 직렬로 처리합니다.

모델 경로는 model_runner.py에서 공급자 어댑터로 이어지고, Codex·Claude worker가 실제 CLI와 native stream을 다룹니다. context_store.py는 고정 입력·catalog·작업 공간 복원과 파일 회수, submission.py는 생산자·수신자가 공유하는 제출 검사, integration.py는 원자적 편입 묶음을 맡습니다.

읽으려는 책임중심 모듈
작업 계약·착수·완료task_contracts, planning, task_scope
지식·형식 결과·관계knowledge, knowledge_records, knowledge_io, relation_refs
통치·초기화·질문governance, initialization, delegations, questions
형식 검사·신뢰formal, trust_inventory, trust_validation
독립 검토review_policy, review_cycle, review_engine
실행·자원·관찰execution_profiles, execution_lifecycle, session_slots, observations
저장·조회git_store, repository, state_contract, record_schemas, payloads
독립 운영·정비scheduled_operator, operator_bootstrap, maintenance_gate, retention

이 표는 책임을 찾는 첫 경로입니다. 전체 파일 색인은 모든 구현·시험 파일의 실제 함수·클래스 위치와 연결됩니다. 파일 이름이 비슷하다는 이유만으로 서로 다른 규칙을 합치지 않고, 호출부와 정본 함수를 함께 읽습니다.

저장 계약과 응답 계약은 다르다

contracts.py의 응답 계약은 do-math-cli/5, state_contract.py의 저장 계약은 do-math-state/7입니다. 앞은 AI가 무엇을 반환할지 정하고, 뒤는 중앙이 그 내용을 어떤 기록으로 보존할지 정합니다. 예를 들어 AI가 knowledge 배열에 새 결과를 제출하면, 중앙은 기록 ID·상태·참조를 결합해 해당 기록군에 보존합니다. 응답 JSON을 그대로 저장 레코드라고 가정하지 않는 이유입니다.

아래는 Git snapshot 안의 저장 경로를 보여 주는 예시입니다. 꺾쇠 안은 실제 기록마다 달라지는 값이며, Git 저장소의 작업 폴더에 이 파일들이 모두 펼쳐져 있다는 뜻은 아닙니다.

research/knowledge/<KN-ID>.json       지식 기록
runtime/executions/<EX-ID>.json       실행 기록
runtime/artifacts/<bundle-ID>/...     고정한 입력·산출 파일

Git ref는 어떤 commit을 현재 상태로 가리킬지 정하는 이름입니다. 인스턴스의 refs/heads/do-math/<인스턴스 ID>가 그 기준을 가리킵니다. 프로그램은 snapshot의 여러 기록군을 읽어 메모리의 instance·runtime 객체로 조립합니다. 이 두 객체는 계산에 쓰는 보기이며, 그 전체가 같은 이름의 단일 정본 파일로 저장되는 구조는 아닙니다.

repository는 기록군의 검사·코덱·조회와 불변 artifact를, git_store는 Git 객체·잠금·경로 경계·조건부 ref 공개를 맡습니다. 직전 상태 하나를 부모로 새 상태를 공개하며, 새 artifact나 실제 기록 변화가 없으면 의미 없는 commit을 만들지 않습니다. 물리 payload의 분리와 논리 값 복원도 이 저장 경계에서 이루어집니다. references/CLI-실행-계약.md · 현재 저장과 작업 경로

공유 규칙은 한 정본을 호출한다

두 모듈 이상이 쓰는 규칙은 scripts/이음새-정본.md에서 소유자를 찾습니다. 파일 지문과 JSON digest는 file_io, 봉인 artifact 대조는 repository, 역할 집합과 프로필 참조는 execution_profiles처럼 나뉩니다. 같은 검사를 각 소비자 안에 다시 쓰지 않습니다.

스키마는 허용 필드·자료형·값을 정하는 객체이고, 빌더는 이번 실행에 쓸 스키마를 만들어 돌려주는 함수입니다. 여기서는 사본을 만드는 방식도 중요합니다. 예를 들어 A와 B 필드가 같은 문자열 규칙 객체를 가리킨다고 합시다. A에만 허용값 enum을 넣었는데 B도 그 객체를 가리키면, B까지 의도하지 않은 제한을 받습니다.

일반 deepcopy는 전역 원본과는 분리된 사본을 만들지만, 사본 안에서 A와 B가 같은 객체를 가리키는 관계는 유지할 수 있습니다. 이 구현의 file_io.py에 정의된 함수 json_copy는 각 위치에 독립된 객체를 만들어 A 수정이 B나 전역 규칙에 번지지 않게 합니다. 이 원칙과 해당 회귀 시험은 이음새 정본에 있습니다. 생산자 검사와 중앙 수신이 같은 스키마·규칙을 쓰는 것에 더해, 어느 한 실행의 스키마 조정이 다른 실행의 뜻을 바꾸지 않도록 한 것입니다.

프리알파의 과거 저장 형식은 호환성 요구가 아닙니다. 계약 변경 뒤 새 인스턴스로 검증하며 옛 runtime·승인·queue를 변환해 재개하는 경로를 남기지 않습니다. 같은 연구 안의 과제 개정·프로필 판본·실행 이력을 보존하는 것은 이 구판 호환 문제와 별도입니다.
