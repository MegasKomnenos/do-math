20. 실행이 끊겨도 같은 의무를 이어가기

정지 요청·로컬 종료·예약 반환·후속 실행을 순서대로 확인합니다.

실행기가 사라졌는데 원장에는 작업이 running이라고 적혀 있다고 합시다. 원장만 믿고 계속 실행 중이라고 할 수도 없고, 화면에 프로세스가 안 보인다고 즉시 자리를 반환할 수도 없습니다. 복구는 보존 기록과 실제 로컬 실행의 정체성·종료를 대조하는 작업입니다.

시작 전에 실행의 정체성을 남긴다

실행기는 프로세스를 만들기 전에 launch_ticket을 기록합니다. ticket은 실행·프로필, 소유 실행기의 호스트·세션·PID·생성 FILETIME, 유일한 Job 이름과 시작 단계를 연결합니다. suspended root를 만든 뒤 정체성과 현재 권한을 확인하고 실행을 재개합니다. PID 숫자만 같아도 생성 시각이 다르면 다른 프로세스일 수 있습니다.

Windows Job은 이 로컬 실행과 자손의 수명을 관리합니다. 부모 하나가 끝났거나 정지 요청을 보냈다는 사실만으로 종료 장벽이 성립하지 않습니다. 로컬 종료와 새 행동 통로의 폐쇄를 확인해야 합니다. 다른 호스트·세션이나 접근 실패는 종료 증거가 아닙니다. 원격 공급자의 내부 호출 종료는 별도 unknown 범위로 남습니다. references/초기화-효율과-정비.md · 시작과 종료

회수한 자료와 결과 승인을 구별한다

정지 때 작업자는 새 연구·계산·조회·외부 요청을 시작하지 않고 이미 얻은 사실과 끝난 도구 결과를 정리합니다. 중앙은 부분 파일과 마지막 유효 체크포인트를 회수할 수 있습니다. 정지 뒤 도착한 새 final을 정상 의미 후보로 승인하지 않습니다. 정지 전에 먼저 접수된 봉인 후보가 있다면 그 정확한 원문만 회수하고 후속 적용 조건을 따로 검사합니다.

예약 반환은 실제 로컬 종료 확인 뒤에 합니다. 프로세스를 정리하기 전에 같은 자리를 다른 실행에 넘기면 중복 효과나 자원 과점유가 생길 수 있기 때문입니다. 종료된 실행을 다시 running으로 열지 않고, 후속에는 새 실행 ID와 continuation_of를 남깁니다. 같은 의무의 기술 재시도는 원 action과 활동의 계보를 유지합니다.

운영 점검이 고르는 후속

처분필요한 근거
continue계약·환경·권한이 유지되고 계속할 이유가 있다
resume보존한 체크포인트에서 남은 범위를 이을 수 있다
retry실패 범위를 다시 할 때 결과가 달라질 근거와 재생 안전성이 있다
repair실제 설치 결함을 의미·권한을 보존하며 수리할 필요가 있다
task_disposition과제 처분을 뒷받침할 권위와 지정 판정 근거가 있다
user_decision사용자만 정할 선택이 다음 행동을 바꾼다

운영 점검은 이 처분을 disposition 객체로 반환하고, 제공된 정확한 admissible_basis_refs에 결박합니다. 일반 근거를 읽었다는 사실만으로 임의 문자열을 처분 근거로 쓸 수는 없습니다. 설치 repair는 내부 점검이 직접 코드를 바꾸는 것과 다르며, 수락된 진단이 별도 설치 복구 담당에게 이어집니다. 계약/운영-점검.md

로컬 입력 사본만 손상되고 Git 봉인 원문은 온전하면 새 작업 공간에 입력을 다시 지급하는 retry가 가능합니다. 봉인 원문 자체가 손상됐다면 그 자료 문제를 먼저 처리합니다. 이미 같은 의무의 명시적 후속이 있다면 재시도를 중복 생성하지 않습니다. 반대로 후속 과제가 성공했다고 별개의 설치 결함까지 자동 해소하지 않습니다.

수신 형식 오류는 제한된 생산자 수리, 현재성 변경은 원 역할의 재판단, Git 공개 실패는 중앙 재대조, 공급자 한도는 공유 대기로 구별합니다. “오류니까 다시 실행”이라는 하나의 처방으로 묶으면 이미 끝난 외부 효과까지 반복할 수 있습니다.
