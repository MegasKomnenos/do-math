16. Lean 검사와 신뢰 환경이 보증하는 범위

정확한 소스·공리·환경의 검사와 환경 변경 처리를 이해합니다.

형식 검사는 “어떤 환경에서 어떤 표현을 검사했는가”와 함께 읽어야 합니다. 같은 이름의 정리라도 소스나 의존, 검사 환경이 달라지면 같은 증거가 아닙니다. do-math는 형식 소스·선언·타입·전이 공리 의존과 실제 툴체인의 판본을 연결해 보존합니다.

중앙이 제출된 정확한 소스를 검사한다

Lean 원문이 있는 지식 후보는 formal_check 기계 작업으로 갑니다. 검사기는 실제 선언이 있는지와 타입·증명·의존 공리를 확인하고 sorryAx와 허용 목록 밖의 공리를 거부합니다. 현재 기본 허용 공리는 propext, Classical.choice, Quot.sound입니다. 이 목록은 해당 기초 계약의 일부이며 모든 수학적 의도와 같은 뜻임을 보장하지 않습니다.

작업자의 Lean preview는 같은 지급 검증 코드를 사용하는 비권위 검사입니다. 중앙은 preview 결과를 최종 인증으로 승계하지 않고 제출된 소스를 다시 검사합니다. 반면 중앙 형식 검사와 동일성 검토를 마친 뒤 K에 편입하는 관문에서는 소스·환경 결속·효력을 대조하고 앞선 중앙 Lean 성공을 재사용합니다. 검토 뒤 Lean을 한 번 더 실행하는 단계는 현재 제공하지 않습니다. references/CLI-실행-계약.md · 형식 검사, 동일성 검토와 목표

신뢰 환경의 기준을 한 번 만들고 사용 때 대조한다

setup_lean.py는 공유 Lean·Mathlib 환경을 준비하고 툴체인 기록을 만듭니다. 기준에는 판본 식별, 판정 파일의 메타데이터 지문·내용 해시, 대표 컴파일 결과가 들어갑니다. 인스턴스의 신뢰 환경은 그 기록과 특정 기준 항목에 결박됩니다. 등록은 비활성 후보의 보존이고 실제 활성화는 별도 검사입니다.

판본 식별은 Lean 명령·실행파일·프로젝트 입력·검사 코드가 무엇인지 고정합니다. 지문은 .olean과 런타임 라이브러리의 경로·크기·수정 시각·생성 시각입니다. 파일 내용 전체를 매번 읽는 대신 이 지문으로 우발적 변경을 확인합니다. 활성화와 형식 검사 직전에 기준과 대조하며, K 게시에서는 판본 식별을 확인합니다. 현재 상태 조회가 설치 파일 전체를 다시 검사하는 것은 아닙니다.

관측처리
판본 식별이 바뀜새 툴체인 기록과 신뢰 전환, 기존 K 재검사 경로
판본은 같고 지문만 바뀜사용자·운전자가 rerecord로 내용 전건을 대조
내용이 같고 대표 검사 통과새 기준을 덧붙이고 조건이 맞으면 인스턴스가 재결박
내용이 다름같은 환경의 단순 재기록을 거부하고 새 환경 전환 필요

재결박은 같은 판본·내용의 기준 변경을 반영하는 것이며 환경의 수학 의미를 바꾸는 전환과 다릅니다. 설치 복구 AI는 이 기준을 스스로 재기록하지 않습니다. references/초기화-효율과-정비.md

보증에는 실제 검사한 범위가 있다

메타데이터를 모두 유지한 채 내용만 바뀌면 사용 경로의 지문으로는 찾지 못할 수 있습니다. --check-contents는 요청한 경우 내용 전건을 비교하는 별도 점검이고, 예약 감독이 자동으로 주기 실행하지 않습니다. 같은 OS 사용자 권한의 의도적 변조를 막는 격리도 이 계약의 범위가 아닙니다.

중앙 Lean은 완료까지 기다리며 제품의 시간·메모리·CPU·출력량 상한을 적용하지 않습니다. 사용자 정지나 권한·전제 변경에 따른 취소는 유지합니다. 정지 뒤 재개할 때에는 같은 소스·선언·환경·허가를 확인한 새 실행으로 다시 검사하며 컴파일러 중간 메모리를 복원하는 것은 아닙니다. 시험 실행기의 유한 시간 제한과도 구별해야 합니다.

판단 연습

동일성 검토 뒤 현재 K 편입 관문에서 Lean을 다시 실행하는가?

정답과 해설

기존검사 재사용 — 원문·환경 결속·효력과 현재 판본 식별을 대조한 뒤 앞선 중앙 검사 성공을 재사용한다. 작업자 preview를 중앙 검사 대신 쓰는 것과는 다르다.
