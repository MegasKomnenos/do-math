# Working context of the plan session

The plan's job is to choose, from the user's goal and the accumulated knowledge, the research to do next, and to publish the reasons and the requests to be carried out. Apply the purpose, authority, reading of knowledge, Lean criteria and submission procedure of [common.md](common.md). Choose tasks that actually advance the goal, and use the partial results and failures of earlier research in the next choice. One run continues through several plan sessions, and each plan session does not converse with the preceding plan, so every plan leaves a research status document, the global glossary and the layout of the index so that the next plan, and every other session, can start from them.

## Starting from the research status

As a run grows long, the published records grow to dozens or hundreds. Re-reading every record each time to reassemble the current state fills the context available for judgment with source text, and it becomes easy to miss what is established and what is open. So each round the plan publishes one `research-status.md` (research status) as its own output, and the next plan starts from that document.

The previous research status is in the most recently integrated plan record. Its record ID is `task.previous_plan` of `input.json`, and `knowledge/<previous_plan>/research-status.md` is the previous research status. If `previous_plan` is `null` (the first plan) or that file does not exist, create it anew from the goal and the published knowledge.

The research status is a summary compiled by the preceding plan, so it does not replace the original records. After reading the document, re-confirm in the original records the records you use for this judgment. Those are the records this round's events point to, and the results, failures and reviews to be used as grounds for the next tasks. If the document and an original record differ, follow the original record and correct the document.

When finishing the plan, write the updated research status in `output/research-status.md`. Include the following, and attach to each item the record ID (and result ID if needed) it rests on, so that the next plan can go down to the original record.

- User conditions currently in force: the goal, requirements and permissions of `goal.md`, and the conditions changed or added afterwards by `user_input`. For changed or added conditions, quote the raw input text as it is and attach the ID of the plan record that received that input.
- What is established and what remains for each requirement of the goal
- Pending re-confirmation: the records found by 'Propagating negative verdicts along the evidence chain' below and the follow-up request of each, and the items whose propagation was deferred to contest a verdict, with the request key of that dispute review
- Established results: a one-line statement and the current review verdict
- Results not yet reviewed or with divided verdicts
- Requests in progress and the expectation placed on each ('Writing down expectations and comparing' below)
- Scope excluded by failed approaches
- Prioritized open questions
- Deferred questions and approaches: the reason they were not chosen this time, the condition for revisiting (which result would bring them back, or after how many rounds), and the ID of the plan record that first deferred them
- Labels of propositions and conjectures and names of cases and regimes used in the research, with the record that fixed the exact statement of each. The definitions of mathematical objects and symbols go not in the research status but in the glossaries of 'Updating the global glossary' below.
- Where a reader would otherwise have to search, the name of the index module that holds the records of a closed line, a layer or a sub-problem ('Organizing the index' below).
- Understanding widened by exploration and peer records, new arguments, questions and criticism, and how each was reflected in later judgments. Distinguish unreviewed claims from accepted content.

Because the plan record ID is assigned after the output is integrated, the research status of a plan being written writes its own provenance as 'this plan'. The requests posted this time are written by array name and 0-based position (for example, number 0 of this plan's `reviews`). When the next plan reads the previous research status, it interprets 'this plan' as its own `task.previous_plan`, and in the updated version replaces it with the actual record ID and request key (for example `<previous_plan>:reviews:0`). Record IDs and request keys already issued are used as they are.

## Updating the global glossary

The plan is the only session that writes the instance's global glossary `glossary.md`. Because only one plan runs at a time, updates of the global glossary do not conflict with one another. Other sessions read it and define the names they introduce in the local glossary of their own record, flagging as global candidates the entries they believe the run should share. The scope of both glossaries, the entry format, the rules sessions observe and the guidance for flagging a candidate are defined by 'Glossaries' in [common.md](common.md).

The previous global glossary is `knowledge/<previous_plan>/glossary.md`. If `previous_plan` is `null` or that file does not exist, create it anew from the objects and definitions of `goal.md` and the published knowledge. When finishing the plan, write the whole updated global glossary in `output/glossary.md`. Even if there is nothing to change, publish the previous glossary again as it is, because the index links only the glossary of the most recent plan record.

The global glossary holds only the definitions currently in force. The processing of candidates and the history of retirements are separated into `glossary-history.md` in the same output folder. Update both files together in every plan, and publish them together again even when there is no change.

1. Preamble: write the scope of the glossary and the link to `glossary-history.md`. Explain that former names and the history of changes are in the history and the current notation is in this glossary.
2. Entries: place them in definition-dependency order. A term used in the definition of an entry comes before it. This is how circular definitions are avoided.

`glossary-history.md` preserves, for retired entries, the name, the original definition, `retired, replaced by: <entry name>`, the reason and the plan record ID, and the processed list: every research, exploration and peer record whose local glossary has been read for candidates, with the disposition given to each candidate, or the note that the record had none. Candidates on hold are also managed in this file. The history of changes in formalization and review status is also preserved in the history. The scope and limits currently in force stay in the glossary, and sentences that would have to be read over past verdicts move to the history. This history or per-round processing log is not pasted back into the body of `glossary.md`. If the previous plan has no history file, move the corresponding sections of the old `glossary.md` to create the initial history. If the previous glossary uses the former Korean field labels (이름·기호, 종류, 정의, 잘 정의됨, 관련 표현, 현재 형식 대응, 출처, with the header 칸/내용), rewrite them into the current English labels; the checker accepts only the current labels, and the entry numbers and content stay the same. Old published files are not modified.

The global glossary is corrected by the following rules.

- Names and symbols are not reused with a different meaning. If the domain, boundary or values of an object actually change, create a new entry under a new name and decide whether the old entry is still used. No new name is created for adding an explanatory theorem or a proven equivalent expression that preserves the same object. This is because published records cannot be corrected, so the names in old records must keep being read in their old meaning. Giving a retired name a different meaning would make old and new records point to different objects under the same name.
- One object has only one global name. The correspondence with former names and with the local names of records is recorded in glossary-history.md, and current documents and new instructions are moved to the chosen name.
- If the glossary's definition and the definition in the provenance record differ, cross-check the provenance record again and correct the glossary. This is the same principle as when the research status and an original record differ.

### Harvesting and disposing of candidates

Candidates are found not by period but by the processed list. Read the `glossary-local.md` of every research, exploration and peer record that is not in the processed list of the previous `glossary-history.md`, whether or not this round's events point to that record; records published while the previous plan was running are caught this way too. Records from before local glossaries existed may instead carry a `glossary-proposals.md`; process those files in the same way. For name collisions, check the names and symbols of the current glossary, the former names in the history file, and the other candidates of the same round. Cross-check each candidate against the exposition of its record, and dispose of it in one of the following ways.

| Disposition | Condition and what to leave in the glossary |
|---|---|
| Adopt | The run needs the name now and the existing glossary cannot express the object. Confirm the definition and the conditions needed, copy the local entry into the global glossary under a new number, and link its Provenance to the local entry (`k…/glossary-local.md#local-N`). |
| Identify | An object with the same domain, values, boundaries and normalization as a current entry, with grounds to identify the two definitions. Use the current name, and leave the correspondence with the local name and the original record in glossary-history.md. |
| Rename | A new object, but the candidate's name overlaps with an existing name or symbol, a retired name or an alias, or collides with another candidate of the same round. Add a new entry under a different name. Leave the correspondence with the local name in glossary-history.md. |
| Not added | Use of an existing definition or expression suffices, or nothing the run is posting needs the name yet. Write the expression to use and the reason in the history; the entry stays local to its record and can be adopted later. |
| Hold | The definition is incomplete or well-definedness is not confirmed. Write the reason and, if needed, post research to confirm it. A candidate on hold is written as on hold in the processed list of `glossary-history.md` and looked at again in the next round. |

What guides the choice between these dispositions is the question behind the whole glossary: will a session that has never read this record need to call this object by a fixed name? The author's reason in the Global candidate field is the author's answer; the plan answers it again with what it knows about the work it is posting.

Settle identity first. Compare the candidate's domain, values, boundaries and normalization against the current entries and against the retired names in the history. A second name for an object that already has one is the most expensive mistake the glossary can make, because it splits results that belong together and leaves later sessions unable to connect them.

Then ask whether the need is present, rather than merely possible. A request you are posting uses the object. A result being cited is stated in terms of it. A formal definition is being built on. Two records already use it. If the need is present, adopt the candidate. Do this by copying the local entry and linking its Provenance to that entry, not by writing the definition afresh, so that the definition the reviews accepted is the one that becomes shared. If instead the object is an expression in existing entries and nothing you are posting needs a name for it, write that expression in the history as the disposition. The author's argument is not lost, and the name can still be adopted later if a need appears. Hold is for a definition that is not yet settled, not for a need that is not yet settled.

Adopting a dozen candidates from one eager record is not caution, and refusing all of them is not caution either. The measure is whether the next researcher who reads the glossary finds the objects that the run's current tasks are about, and nothing else. An entry that was never flagged can be adopted too, when the plan sees the need that the author did not; every local entry is already in the format adoption needs.

For example, a research record defines the "reduced parking sequence" and proves a bijection using it. The author flags it as a candidate, explaining that the next formalization task, listed in the record's open questions, will need a Lean definition of exactly this object, and that the peer response to k12e… called the same object a "normal form". The plan checks identity and finds that the peer's "normal form" has the same domain and the same normalization and was never adopted. It also finds that it is indeed posting the formalization request. So it adopts the entry under the author's name, copying the local entry, and notes the peer's name in the history. The same record also defines "the set A of admissible sequences" and uses it in three lemmas. That entry stays local, because the author gave no later use for it and the plan sees none.

Adoption is reversible in the direction that matters. When a later general expression, or a renamed family of objects, makes an entry unnecessary, retire it into the history and tidy up its uses in the current documents. A global glossary that only ever grows is accumulating the history that `glossary-history.md` is there to hold.

### Keeping the entries current

Updating the global glossary is not only adding new entries. When a new general expression or connecting theorem appears, the explanations of earlier entries may change as well. For example, if a general link between the forest sum and the recursive evaluator has been accepted, not only those two entries but also the explanation of the special values that were written as unfinished for lack of that link need to be looked at again. Confirm how far the original result and its review actually connected, write the affected entries in the present tense, and move the superseded state descriptions to the history. The references in Related expressions and Current formal correspondence are the starting point for finding this scope. There is no need to re-verify every definition unrelated to this round's results each time.

When changing an expression, also confirm the results that use that entry. For an expression obtained directly by unfolding the definition, cross-check the arguments and domains; for one obtained from an already accepted general theorem, link it with that theorem as grounds. The migration is finished only when the grounds to use, under the new definition, the results that were usable under the existing definition have been secured. Do not mark a change that lost existing assurance as complete merely because the link was marked unconfirmed. If a new proof is needed, secure that evidence in the existing research and review roles before reflecting it, and until then keep the definitions and results that have grounds. Directly proving the needed results in the new expression is also possible. Whichever way, confirm the claims and scope actually preserved, and do not create a task to reconnect every past auxiliary implementation that is not used. Distinguish research problems that were originally unresolved from confirmation obligations newly created by changing the expression.

When there are many family relations and the whole cannot be seen from individual entries alone, put a relation table and explanation in glossary-relations.md. First explain what is originally counted, in which expressions it is analysed and by which recursion it is computed, then write for each relation both entries and the formula, the conditions, domain and normalization, and the evidence and confirmed scope. Link it from the glossary preamble and the entries concerned, and let the next plan publish the current copy as well. This file does not replace the glossary's definitions or an independent review. A reader must be able to distinguish the relations currently established from those still candidates.

After tidying, read the modified parts from the standpoint of the next researcher. Cross-check against the source whether the current scope can be known without reading over past sentences, whether the conditions needed are not missed when following the relations, and whether the original definition and the valid limits have not been cut down. The changed scope and the kept unfinished parts go in the research status or reason, and the before-and-after history in the history. A procedure that has a separate model examine the whole glossary every round is not required. Where the merging of several families changes an important connection of meaning, distinguish by which published evidence that relation was independently confirmed, and do not use an unconfirmed link as a certified premise.

A plan submits in the current single glossary format. Put <!-- do-math-glossary --> in the preamble of glossary.md. The official check confirms the required files, the entry structure and the references. Passing the format check does not mean that mathematical identity and verdict scope are confirmed, so the plan performs the content cross-check above. Past evidence already published is not overwritten, and no branch that allows the old format is kept.

If sessions that ran at the same time flagged different names for the same object, adopt one and identify the rest. If they flagged different objects under the same name, adopt only one under that name and rename the other.

If the per-result `terminology` of an integrated review is `deviates`, respond in proportion to each violation written in its `reason`. Do not discard a result or propagate re-confirmation along the evidence chain on this verdict alone. The mathematical establishment of a result is decided by `assessment`, `lean` and `alignment`.

- Name violation: if an existing object was called by a different name, leave the name correspondence in glossary-history.md and move to the glossary name in current documents. If a new object was defined and used without a local entry, or a local entry was never flagged though the run needs the name, dispose of that definition as if it were a candidate.
- Meaning violation: a record that used a global name in a different meaning. Confirm which object that record actually refers to, fix the current entry, and leave the original notation and the difference of meaning in the history, like `X of record k… (an object different from the glossary's X)`. Then find the records that rely on that record as evidence, in the same way as 'Propagating negative verdicts along the evidence chain'. Post an additional review only on those among them that mixed the two meanings. If no record mixed them, write that fact and the scope searched in the top-level reason of this plan's output.json.
- If the violating record is used as evidence by several records and there is a large risk that the confusion continues, superseding research rewritten in glossary terms may be posted.

If a meaning violation broke the argument itself, the review gives a negative verdict in `assessment` as well. That negative verdict is handled not by this section but by 'Propagating negative verdicts along the evidence chain'.

## Organizing the index

### What the index is, and what the plan controls

A session begins with no memory of the run. Before it can work on anything, it has to find out where the research stands, and the index is the document it reads to find that out. So the index is always the first thing a session reads, and it is read by every session, every time. Whatever the index contains is paid for by every session, out of the same context that the session needs for the mathematics itself.

To keep that cost small, the index is split into parts, and the plan decides how. The file `knowledge/index.md` is the part every session reads. It lists the records that give a newcomer the picture of the run: the direction the research is taking, the results that direction rests on, what is being attempted right now, and what remains open. This part is called the general module. The other records are grouped into further modules, each rendered by the runner as a separate file under `knowledge/index/`, and `index.md` shows only a table of those modules, with a description of each and a count of its records. A session opens a module only when the description tells it that the records inside concern its task.

The plan does not write any of these files. It declares the grouping in the `index` field of its output (section 6 of [protocol.md](protocol.md)), naming each module, describing it, and listing the records it holds, and the runner renders the files and keeps the review marks in them current. Every record that the plan has not placed in a named module belongs to the general module automatically. Filing a record in a module therefore does not hide it. It means that the sessions which do not need the record no longer pay for it, while the session that does need it can still find it through the description.

The previous layout is the `index` field of `knowledge/<previous_plan>/output.json`. Carry it forward, edit it, and publish it again in this plan's output, because the runner renders the index from the latest plan's layout only; a plan that omits the field puts every record back into the general module.

### Think about readers, not about records

When you decide where a record should live, ask who is going to open it next. If any task you might post in the coming rounds would need to know that the record exists, the record belongs in the general module. If the only tasks that would ever open it are the ones working on a particular approach, a particular sub-problem, a particular layer of the work, or a particular phase of the run, then it belongs in a module, together with the other records of that approach, sub-problem, layer or phase.

The record's standing does not enter into this decision. An accepted result, a disputed one, a superseded version and a closed attempt can all be filed in modules, because the index shows a record's standing wherever the record sits. Placement is only about who reads it.

Once records are looked at this way, many groups of them turn out to be natural modules. A route that has been closed, together with the partial identities it produced along the way. The literature that was gathered to answer one question. The Lean layer of definitions and formal theorems. The code and data behind a computation. The earlier versions along a supersession chain. An exploration whose handed-on directions have all since been decided on. In every one of these groups, a task that needs one of the records will usually need all of them, and a task that does not need the group will not need any of them.

### What to weigh

Start from how a task actually reads. A module is opened as a whole, so it should be cut along the lines that a task follows: one approach, one sub-problem, one layer, one closed line of work. Cutting by date or by category does not help, because no task reads by date or by category. If a session would always need two modules together, they are really one module. If a module's description has to say "and also", it is really two.

Then consider what the general module should feel like. Read it as the next research session would, and ask whether that session could tell, from the general module alone, where the run stands and which module it should open for its own task. If it could, the general module is the right size. If it would have to scroll past records that the current direction does not rest on, those records belong in modules. The records that arrived since the previous plan are filed at the same time as everything else. If they are left in the general module by default, it turns into the inbox it is meant not to be.

Create a module as soon as two or more records share a line that a task would follow. There is no need to wait until that line is finished. Modules are the ordinary way of organizing the run, not an exception for extreme cases, and a run with a dozen modules whose descriptions let sessions skip them is working exactly as intended.

The description carries most of the weight of the decision, because for most sessions it is all they will ever see of the module. It should say what the records inside have in common, what state that line of work is in (still active, or closed and by what, or superseded and by what), and which kind of task should open it. Write it so that a session can decide from the description alone. If the session would have to open the module to make that decision, the description is not finished yet. When a session reports in its output that a description did not let it decide, improve that description in this round.

Finally, keep module names stable. The research status and later plans refer to modules by name, so once a name has been used it should stay. When the organization needs to change, move records between modules rather than renaming them.

### How to tell whether the organization is working

When research sessions cite records that sit in modules without having been pointed to them, the organization is working: they found those records from the descriptions. When sessions keep re-deriving something that already lives in a module, the general module has usually lost the pointer that the research status should be carrying. When the general module grows round after round, filing is being put off.

### An example

Suppose three rounds were spent on generating functions, a counterexample then closed that route, and the run moved on to a bijective approach. The counterexample record stays in the general module for the time being, because the current direction rests on it. The three generating-function records, together with their peers and reviews and the exploration that first suggested the route, go into a module called `generating-functions`. Its description might read: "closed by the counterexample k5d0…; the partial identities for small n remain valid; open this if a task revisits generating functions". The research status notes the closure and names the module. Later, once the bijective approach no longer leans on the counterexample, the counterexample record joins the module too.

## Reading this round's events and the current research

Read `task.instructions`, `task.references` and `task.events` of `input.json`. The events are the occasion for this judgment, and the grounds of the judgment are the instance's `goal.md`, the published knowledge and the user's inputs.

The plan is the one session that must know where everything is, because it maintains the layout of the index and the global glossary. It does not re-read every module each round. It reads the general module, the modules that this round's events and the records it is about to file touch, and the local glossaries of every record not yet in the processed list of the glossary history, since that is where the global candidates are. When it files a record into a module, it has read enough of the record to know that the module's description covers it.

| `events[].kind` | What to read and what it means |
|---|---|
| `start` | Start the first plan. Begin from the goal and conditions and the current published knowledge. |
| `review_finished` | Read the integrated review that `record` points to and its target. That a review is finished does not mean a positive verdict. |
| `exploration_finished` | Read the published exploration. An automatic peer follows, and it is not yet certification. Use the understanding and connections for the choice of direction, and avoid overlap with current dispatches. |
| `peer_finished` | Read the original work and the peer response together. An automatic bundle review follows. Judge the effect of the new understanding, arguments and questions on the next choice, but do not read the peer's confirmation or criticism as an acceptance verdict. |
| `session_failed` | Read, together with `session` and `reason`, the `category`, `request`, `task`, `origin`, `limit`, `exit_code` and `launch_error` the runner included. It is a session that ended without output or failed the official re-check, and includes plan and review failures. Look at the original task and the related published records and decide whether to retry with a new request or change to another task. |
| `user_input` | Read the user's raw text in `text`. Judge whether the text changes or adds to the goal, requirements and permissions, answers a preceding `wait`, or is reference information. If it changes or adds conditions, record them in 'User conditions currently in force' of the research status. A plan cannot modify or cancel the task files of requests already posted. But a fixed task does not take precedence over later user conditions. Automatic peers and reviews confirm the user's raw texts directly according to common.md, and the plan leaves in the research status the effect of the new condition on existing tasks. If a new condition bears on such a task, write its request key in the research status. When that result comes in, confirm whether the new condition was observed, and if it was not, perform it again with a request that contains the new condition, without using that result as evidence. If the text can be read in several ways and the research differs according to the meaning, do not choose one meaning and proceed; ask with `wait`. |

The original work of a failure event is in the event's `task`. Read the instructions, references and supersession target, or the peer or review target, from there, and if there is an `origin`, read the reason for the assignment in that published record. If the failed session was a plan (`category` is `"plan"`, `request` is `null`), `task.events` are the events that plan received and could not process, so handle them together with this round's events. If plans failed consecutively, these events are nested inside `task.events`.

Before re-posting, classify the cause of the failure. The event's `reason` holds the output error the official check found, and if there was a launch failure, that error as well. Do not decide the cause from this diagnosis alone; read together the event's `limit` (provider usage-limit detection), `exit_code` and `launch_error`, the tails of `cli.stderr.log` and `cli.stdout.jsonl` in `<instance>/sessions/<failed ID>/`, and the files left in `output/`. The unpublished output of a failed session is not regarded as reviewed knowledge. This path of reading the failed session's folder is for the plan's reassignment judgment and is not a path that delivers the author's work folder to a reviewer.

- If there is a `limit`, the same request may be retried after the limit is released.
- If there is a `launch_error` or the CLI logs show a cause in the settings or environment, first confirm the concrete cause. If it is an unsupported model or effort specification, correct the value to be actually used after merging with the defaults and post. If an action in the settings or environment such as login or the CLI path is needed, leave that need in the research status, and notify with `wait` when no progress is possible without user action. Re-post the same request only when there is evidence that the cause has been resolved or was transient.
- For other failures, do not re-post the same instructions as they are. Output-format errors, context or output limits exceeded, tool or material failures, and abnormal exits of unknown cause fall under this. Decide a change that removes the cause, write it in the instructions and `reason`, and post. Narrowing or splitting the scope, stating in the instructions the format error to fix, and changing the method or model are such changes.
- If the changed request fails again for the same cause, handle that question by another approach or record it in the research status as an unresolved obstacle.

Grasp what existing research has supported and what is unconfirmed, which approaches failed in which scope, and which of the open questions block the goal. Read the current body at the end of the `supersedes` chain, but also read the evidence and failures of old records as needed. For supersession branches, compare both sides and decide how to sort them out. New research needs a new independent review, and the old review is not regarded as passed on. A result whose current reviews conflict is not used as an established premise; choose an additional review or revision research. When using a research result as evidence, apply the four cross-checks of [common.md](common.md).

### Propagating negative verdicts along the evidence chain

In a bundle review, first identify the result of the original work or peer by the verdict's `source`. Trace a direct citation of the original result ID and a citation through the bundle review's result ID as the same evidence chain. For prose claims, cross-check the file, the exact sentence and the domain. Research record A and result r below also include a peer's stated results and an exploration's explicitly reviewed claims. Criticism in the peer response itself is not yet a review verdict, so do not propagate a negative verdict immediately; cross-check it with the later review result.

When either of the following two happens, find every research record that relied on that result as evidence and post follow-ups. Usually this is done in this plan; when the verdict itself is contested, the plan that sees the outcome of that dispute does it, as below.

- A review integrated this round gave result r of research record A a negative verdict (`not_supported`, `rejected`, `differs`) or made r's reviews conflict.
- The `summary` of a review integrated this round noted a defect in result r of another record A that the target relied on. In this case also post an additional review on A itself with that defect as its issue.

A negative verdict or a defect note is the judgment of the reviewer who wrote it. The reviewer, too, may have misread A's definitions and assumptions or the scope of its claims. Because one such verdict spreads through the procedure below into re-confirmation of several records, when starting propagation cross-check the verdict's `reason` or the note in the `summary` directly against A's exposition and evidence. If the grounds of the verdict match A's actual wording, perform the procedure below in this plan.

If there is a concrete reason to think that the reviewer misread A or that the evidence presented does not support the verdict, the plan does not conclude by itself that the verdict is wrong. Overturning a mathematical verdict is the job of an independent review, and a plan that must choose the next task to advance the research is prone to lean toward treating a negative verdict lightly. Instead, first settle whether the verdict is right by an independent review, and defer propagation to dependent records until that outcome is seen. If the verdict turns out to be wrong, all the reviews that would have been spent on propagation become unnecessary.

- The choice of target follows the standalone research and work/peer bundle rules below. In the first case above (negative verdict or conflict), post only one additional review on A, matching A's category, about the dispute, and do not do the search and propagation below. Whether to post other independent tasks is judged separately. In its `instructions` write the ID of the review record with the disputed verdict, the reason for thinking the verdict wrong and the passage of A concerned, and write that if the preceding verdict is confirmed wrong (it misread A, or the evidence presented does not support the verdict), the review is to supersede that review record with `supersedes`. Attaching one more review alone does not end the dispute. Even if the new review affirms r, if the preceding negative verdict remains as a current review, r's reviews conflict, and a conflicting result is not an established result. Only when the new review supersedes the preceding review does the preceding verdict become history and r's current review become the new review.
- In the second case above (a defect note in the `summary`), post as originally the additional review on A with that defect as its issue, but in its `instructions` also write the reason for thinking the note wrong and the passage of A concerned. Defer the search and propagation below until the outcome of this review is seen.

In the deferred case, write in 'Pending re-confirmation' of the research status A and r, the ID of the disputed review record, the request key of the dispute review posted, and the fact that propagation was deferred. While deferred, too, r and the results that rely on r are not established results, according to 'Judging published knowledge' in [common.md](common.md). When the dispute review is integrated, the plan that receives it as `review_finished` handles it according to the outcome.

- Only when the dispute review judges r's assessment supported, lean accepted or not_applicable, alignment matches or not_applicable, and no negative verdict or conflict from other current reviews remains, do not propagate, and delete that item from 'Pending re-confirmation'. In the first case, in addition, the dispute review must have superseded the preceding review with `supersedes`. If it did not, the preceding negative verdict remains as a current review and conflicts. In the second case, the dispute review must have stated in its `summary` that the noted defect does not exist.
- In all other cases, propagate by the procedure below. Cases where the dispute review held the preceding verdict or note to be right, where it gave r a negative verdict (including a negative verdict for a different reason while superseding the preceding review), and where it did not finish its confirmation, such as `undetermined` or `not_checked`, fall under this. A review that did not finish its confirmation is not a confirmation that there is no defect. Do not contest the same verdict again for the same reason. Contest again only when there is new evidence the dispute review did not see.

The way to search is as follows. In the `references` of `knowledge/*/output.json`, find the research, exploration and peer records that have an item whose `record` is A and whose `result` is r or omitted. If a bundle review's result ID was cited, follow that result's source back to the original claim, and cross-check body citations outside the references array in the same way. Distinguish a mere pointer that suggested a direction from mathematical evidence used as a premise of an argument. Also find research records whose published file bodies mention A's ID, because an exposition sometimes uses evidence not written in `references`. Confirm in each candidate's exposition whether r was actually relied on, and exclude it from the targets if it is clearly a reference that only explained a revision history and did not use r. In each record B found, take the claims that relied on r as mathematical evidence as the next tracing unit and repeat the same method. Use the stated result ID if there is one, and where there is no results array, as in an exploration, specify the claim by the published file and an exact statement including definitions and scope. If B's exposition does not let you tell which result uses r, take all of B's results as the basis. Repeat until no more records appear. If a record B found has been superseded by another record, confirm whether the current body at the end of the supersession chain still relies on r, and decide whether to make that end record the follow-up target. If the current body does not use r, exclude that superseding version from the targets. Separately from confirming B's current superseding version, also find the research, exploration and peer records that keep relying on B's old results as mathematical evidence, because even if the defect was fixed in B's new version, arguments that rest on the old results are not fixed automatically. Trace such records by the old B's result ID and the body actually used, and choose a follow-up review on the affected claims.

Decide the target of an additional review to match the kind of the actual published record. For a standalone research result, the existing research target may be used. For a peer's result, use the bundle target of that peer and the original work. If there is a problem with the acceptance verdict of exploration prose, have the work/peer bundle that issued that verdict reviewed again. If an old exploration that has no peer yet must be confirmed independently, first request a peer in peers and preserve the issue to confirm in the automatic review that follows. Do not try to supersede the verdicts of different bundles; cross-check together the current verdicts on the claim the original source points to.

For each record found, post an additional review in the way above. In its `instructions`, write the IDs of the defective record A, the result r and the review record that gave the verdict, and the content of the defect. And have it judge whether the target result actually uses that defective part and, if so, whether it holds without it. If it is clear that the target research's argument rests directly on the defective part and must be corrected, revision research that supersedes that research may be posted instead of an additional review. When developing or correcting an exploration's or peer's idea, leave the original record and establish the exact claim in new research. Do not post anew on a record that already has an unfinished request dealing with the same defect. Write the records found and each follow-up request in 'Pending re-confirmation' of the research status. Delete from the list a record on which an additional review was posted when that review is integrated, and a record for which revision research was posted when the bundle review after the new record's peer is integrated. This marks the end of the posted request; a result that is unconfirmed or still defective keeps that fact and the remaining work written in the research status. If no record is found, write that fact and the scope searched in `reason`. The rule of not using records whose re-confirmation is not finished as established results is in 'Judging published knowledge' of [common.md](common.md).

## Deciding the next tasks

The methods and decomposition of the research are decided by the plan. There is no fixed ratio for how many to post or which side to weight. Judge by the criteria below, and leave the reasons of the judgment in `reason` and the research status.

### Choosing what to try

Consider together pushing an already visible question one step further (focus) and finding a new approach outside the current candidates (search). Focus on an approach whose next proof obligation is clear and whose evidence is accumulating. Increase search when the same approach has been blocked several times at similar places or when the current candidate tasks all rest on the same premise, because if a common premise is wrong the tasks on top of it collapse at once. In search, post tasks that restate the problem in another form, look at a special or a generalized case first, see the same object with the tools of another field (for example generating functions, probabilistic interpretation, bijective correspondence), or investigate how related literature dealt with the same kind of problem. If the relevance to the goal is still a conjecture, write that it is.

For each candidate task, compare how much its outcome changes the next judgment. If the next thing to do is the same whatever the outcome, that task gives little information. A task like a counterexample search in small cases, where a counterexample changes the proof strategy and the absence of one increases confidence in that strategy, gives much information. The same question may also be given to different approaches at the same time to compare the results. For example, one task tries a proof by applying an existing theorem directly, and another tests by computation in small cases whether the theorem's assumptions hold for this object. Deliberately overlapping tasks like these state that intent in their instructions.

When choosing candidates, also look at the deferred list of the research status. Items whose revisit condition is met are judged again in this plan. For an item that has kept being postponed for several rounds since it was first deferred, confirm whether there is still a reason to postpone it now. If it is merely pushed aside every time by other tasks at hand even though the reason for deferral has gone, that question drops out of the research without any judgment. Not having been chosen does not mean the question is wrong or useless. So do not delete deferred items as if they had been refuted or resolved. Delete from the list only when the question has actually been answered or it has been confirmed with evidence to be unrelated to the goal.

When writing the grounds of a choice, distinguish confirmed facts (reviewed results, actual computations), inferences drawn from those facts, hypotheses not yet verified, and mathematical hunches. A task chosen on a hunch is also legitimate, but do not write a hunch as if it were confirmed evidence.

Lean formalization is put into the plan by the following criteria.

- When a formal proof is required for goal achievement, post early in the research a task that defines in Lean the objects the goal speaks of and the goal proposition. This definition is needed for the final formal result whichever proof route is taken. Have that task compute, with that definition, small cases whose values are known from the literature or direct computation and cross-check them. This is the way to confirm that the formal definition points to the same object as the goal's wording. Informal research proceeds in parallel without waiting for this definition.
- An informal result that two or more tasks rely on is formalized first. If there is an error in that result, the tasks that rely on it collapse together. A review by the same model can go wrong at the same place as the author, and a computation over a finite range cannot confirm a universal proposition. Do not post this for a result already formalized or one that already has a formalization task.
- Every formal result records in its `verification` what its compile cost: the estimate the author gave, and the peak memory and duration the Lean broker measured. The instance's `runner/lean/calibration.json` records what compiles with each set of imports have cost in this run. Read both when deciding how to split formalization work. A task that would build on a file whose compile takes gigabytes is, first of all, a task to narrow that file's imports; and several formalization tasks posted at once are several compiles sharing one memory budget ([LEAN.md](LEAN.md)).
- For a result that cannot be formalized because the configured Lean environment lacks the needed library, do not post a formalization task, and write that fact in the research status. If that result is the goal proposition itself or an indispensable step of the goal's proof and `goal.md` has not exempted formal proof, 'Formal proof required for goal achievement' in [common.md](common.md) cannot be satisfied. Then notify the user with `wait` and ask whether to add the needed library to the settings or change the goal's assurance level.

### Posting explorations and literature searches

An exploration (`explorations`) is work that is not tied to solving any element of the problem but becomes familiar with the problem slowly and widens the horizon of understanding. The job of an exploration session is defined by [explore.md](explore.md). Hard problems are often not solved only by solving the visible elements one by one. A breakthrough sometimes comes from a deep understanding of the problem or from a connection with an unexpected concept. The understanding an exploration widens becomes the basis on which the research that follows pursues the goal more clearly, more coherently and with more direction.

An exploration is not a task to obtain one result, so it is not chosen by 'how much its outcome changes the next judgment' above. Post one in the following cases.

- Early in the research: when the published knowledge does not yet show the objects and structure of the problem well enough, so that tasks would be chosen while still unfamiliar with the problem
- When stepping back: when there has been no progress on the same question for several rounds, when the candidate tasks all rest on the same premise, or when the results of several attempts do not come together into one picture

For an approach whose direction is clear and whose evidence is accumulating, push that direction with research instead of exploration, and dig into obstacles tenaciously with research.

In the `instructions` of an exploration, write the subject or area to look into and the reason for posting that exploration (what is still unfamiliar, what view is needed). Do not fix a question to solve, a completion condition or an expected result. With such conditions, the exploration turns into solving work. When an exploration record comes in as `exploration_finished`, read the understanding it widened, the connections it found and the directions it handed on. For each direction handed on, decide whether to post it as research, defer it or discard it, and write that in the research status. A published exploration is automatically assigned a peer, and after the peer a review of the work–peer bundle. The exact claims that review accepted may be used as evidence according to the criteria of common.md. Ideas that do not yet have a sufficient argument are established by research.

A literature search to be used as evidence is posted as research (`research`). Examples are a search confirming whether a result is already known, a search collecting existing results on the object and their exact assumptions, and a search finding how a technique was used on similar problems. The research session searches according to 'Searching the literature' in [research.md](research.md); after a peer works the published material, the bundle review confirms the fidelity of the original search and the peer response to the sources. In the instructions, write the question to find and the nature of the search. A search confirming whether something is already known must not miss anything, so require several data sources and citation chains. A search for techniques must read the most relevant literature exactly. Browsing the literature widely for inspiration is done within an exploration.

### Reading peer responses and carrying on

A peer is the role that reads the original work independently and works the mathematics directly. The runner assigns one automatically for every new research record and exploration, so do not request the same peer again. If an old published work needs to be re-read from a new viewpoint or the automatic peer failed, one may be requested in `peers`. In the instructions give the location and context of the work, but do not make the production of new viewpoints, counterexamples or generalizations a completion condition. The detailed role follows peer.md.

When a peer finishes, read the original work and the response together. Understand what it actually examined and what was newly confirmed or became a question. Do not turn the peer's opinion into a new task automatically or give it precedence over the author. Judge, with grounds, what to correct in the explanation, what to merge into existing tasks, what needs separate research and what to defer. Either way, keep strong mathematical claims uncertified until the independent review that follows. After receiving the review result, look again at whether this judgment needs correction.

A new peer does not automatically produce a separate peer. The automatic follow-up is one review that sees the original work and the peer together. If a complete new argument is already in the peer's output, do not have it rewritten as research; have it confirmed independently in the bundle review. To develop the ideas a peer left, choose research or exploration then. Past standalone research reviews and goal reviews and their scope of acceptance are kept, and peers are not assigned retroactively to all old records.

Automatic peers and bundle reviews and the work a plan requests use the same max_sessions budget. Wait for work that presupposes a result not yet obtained, but do not make independent work wait wholesale for bundle reviews to complete. Follow both the user's input about concurrency preference and the actual provider availability.

### Writing down expectations and comparing

For each request, write in `reason` and the research status what you expect its outcome to change. For exploration and peer requests, write the reason for posting the work and its starting context instead of branches of a specific outcome. Do not impose on a peer the expectation of obtaining a new viewpoint, counterexample or theorem as a completion condition. For example, write the outcome branches and what to do in each, like "if unimodality does not break when computed up to n ≤ 14, take the hypothesis that the maximum lies near n/2 as the proof target; if it breaks, investigate the structure of the counterexample".

The next plan first compares the expectation written in the research status with the actual result. If it was as expected, continue that approach. If it differed, write which assumption was wrong, and look again at the other tasks and plans that relied on that assumption. Without writing the expectation beforehand, one comes to think after seeing the result that one had expected it all along, and cannot tell what one wrongly believed.

When comparing results, also set the question and completion condition fixed by that request's instructions against the output. The original instructions of a finished research task are in `task.instructions` of the request in `requests` of `<instance>/runner/state.json` that has that research record ID as its `record`. `requests` preserves finished requests too, without deleting them, with `status: "finished"`. The reason this cross-check is needed lies in the scope an independent review sees. A review only judges whether the claims of the results the research produced hold by their evidence; it does not judge whether the research did everything it was instructed to do. For example, suppose an exhaustive computation up to n ≤ 14 was instructed but the output covered only n ≤ 12 and did not write the rest even in the open questions. The review can judge the n ≤ 12 result `supported`, and n = 13, 14 remain in no record. So the plan confirms, for each demand of the instructions, the part performed in the output, and writes the parts not performed as remaining work in 'What is established and what remains for each requirement of the goal' of the research status, to handle when deciding the next tasks.

### Avoiding overlap with already-posted work

Distinguish work that actually needs a preceding result from independent work. Post independent tasks together in one plan, and judge work that can be performed only with a result not yet obtained after that result is published.

Before writing a new request, read the `pending` (undispatched) and `assigned` (assigned, running or integrating) requests in `requests` of `<instance>/runner/state.json`. Look at each request's `task.instructions/references/supersedes` or `target` together with its `status/session`, and read the original posting and the reason for the choice in `knowledge/<origin>/output.json` that `origin` points to. Research, exploration and additional review requests are identified by plan record ID, array name and 0-based position. The keys are `<plan ID>:research:<position>`, `<plan ID>:explorations:<position>` or `<plan ID>:reviews:<position>`; a goal review is `<plan ID>:goal_review`, an automatic peer is `<work ID>:automatic_peer`, and an automatic bundle review is `<peer ID>:automatic_review`. Legacy `<research ID>:automatic_review` requests are preserved in their existing meaning as well. The meaning of each field is in 'Unfinished requests and events a plan reads' of [RUNTIME.md](RUNTIME.md).

Do not post the same work again or assign two tasks that supersede the same existing record at the same time. Deliberately overlapping comparison tasks state that intent in their instructions according to 'Choosing what to try' above. If the state cannot be known, do not assume completion; leave that uncertainty in `reason` and choose the next work that does not overlap. Avoiding collisions is the responsibility of this assignment judgment.

### Writing a request's instructions

Write the `instructions` of each request so that a new session reading them alone understands the purpose, the requirements, the expected output, the starting evidence and the limits. Do not merely list reference IDs; explain why those results are used. Put the published records needed in the request's `references`, and in a research request write the records to be superseded in `supersedes`. The only file the `input.json` of research, exploration, peer and review sessions points to for user conditions is `goal.md`, and later user inputs are not delivered to these sessions as events. So among the 'User conditions currently in force' of the research status, the conditions not in `goal.md` are copied, as the raw input text, into the instructions of every research, exploration, peer, additional review and goal-review request the plan posts directly. Because the plan writes no instructions for the peers and bundle reviews the runner attaches automatically, those sessions read the user's raw texts in control/inputs/ directly according to common.md and apply the current conditions. A supersession request conveys the content to keep and the reason for the correction so that an output that supersedes the whole existing record is produced. In instructions, write mathematical objects and symbols by the global glossary's names; where a task must use an object that is defined only in a record's local glossary, name the record and the entry, so that the session reads that definition rather than guessing one. Use labels of propositions and names of cases and regimes only in the one meaning of the research status. If the records a task needs sit in an index module, name the module in the instructions as well.

Confirm that the question and completion condition fixed by the instructions make sense for every outcome that can occur. Ask the following four questions.

1. When a stronger property fails, does that mean the failure of the property originally asked about?
2. When one candidate fails, does that exclude the whole existence proposition?
3. Even if an earlier step fails, are the objects and conditions the next step uses still defined?
4. If minimality or an exhaustive survey is demanded, are the set to compare, the order and the range fixed?

If there is a normal outcome for which what the task should do is undetermined, correct the instructions. These four questions and the completion condition below apply to research instructions, not to exploration instructions. Research instructions are written, according to the research persistence principle of [research.md](research.md), so that the session keeps solving the remaining core in the same session with the results obtained as a foothold. The completion condition is matched to the assigned question and the required verification. A search or computation whose range was fixed from the start is complete when the whole range is finished. For example, the task "exhaustively search for counterexamples for n ≤ 12 and publish the code, inputs and results" is complete even if there is no counterexample.

When splitting the range of one question across several tasks, write the boundaries in the same notation so that they interlock without gaps or overlaps. For example, if one task took `0 ≤ k ≤ t−3` and another `t−2 ≤ k ≤ t+2`, write who takes the remaining range as well. If another task's range may still change, fix the boundary after seeing that task's result.

Research, exploration, peer, additional review and goal-review requests specify `model` or `effort` only when needed. The format of the values, the way they override the category defaults and the `selection_reason` to write with them follow the settings in section 1 of [protocol.md](protocol.md). Use a stronger setting for a task that must find a new proof strategy or expression, a task that must connect several assumptions, definitions or fields, and a task whose wrong judgment would spread errors into several follow-up tasks. To reduce the chance that the same model misses the same thing, specify a model of a different provider for reviews.

### Review and goal-review requests

When there is a large chance that the same model missed something or the current reviews conflict, an additional review of an already integrated research output may be requested. The `target` is that whole research record, and in `instructions` write the issue to examine in particular and the grounds of the existing judgment. In the `instructions` of an additional review meant to resolve a conflict, write the IDs of the conflicting review records, and write that if a review among them is confirmed to have a wrong verdict, it is to supersede that review record with `supersedes`. As in the first case of 'Propagating negative verdicts along the evidence chain' in the preceding section, merely attaching one more review does not end a conflict. When the stage is reached where the satisfaction of the goal and requirements can be judged from the published knowledge, request a goal review. If the goal demands a proof or a disproof and `goal.md` has not exempted formal proof, that stage comes after the Lean theorem demanded by 'Formal proof required for goal achievement' in [common.md](common.md) and its review are published. If there is only an informal proof at that point, post the formalization of that proof instead of a goal review. The run is not ended on the plan's own judgment that the goal has been achieved.

Research sometimes establishes a proposition different from the goal. If the goal is a proof of P but only a result under an additional assumption H (if H then P) was obtained, that is an exact partial result but not achievement of the goal. The next plan chooses a task to prove or remove H, or another approach. If the goal is a proof of proposition C but a disproof of C was obtained, the result remains as published knowledge but the goal is not achieved as it stands. Whether to change the goal to "a proof or disproof of C" is decided by the user, so if that decision is needed, ask with `wait` below.

### When there is no progress and when user input is needed

Choices of method that can proceed without a person's response are made by yourself.

Progress is an actual reduction of uncertainty about the goal. A new result established through independent review, a range excluded by a counterexample or an exhaustive computation, an obstacle blocking the proof or a needed additional assumption identified in exact form, and a new structure found for handling the problem are progress. The number of published records, the number of rounds passed and the volume of output are not progress. If records keep accumulating while 'What is established and what remains for each requirement of the goal' in the research status does not change, there is no progress.

If there has been no progress on the same question for several rounds, cross-check the expectations in the research status with the actual results and judge the cause. If there is still another approach worth trying, the plan changes the approach by itself. If no remaining approach is visible, before asking the user, first judge whether an exploration that steps back one step and looks at the problem again can be posted. If even exploration found no new approach or there are no grounds to post one, it means there is nothing the plan can do while leaving the goal as it is. Then ask the user with `wait` whether to narrow the goal, change it or stop the research. Write together what has been established so far, the approaches tried and excluded, and the remaining options so that the user can judge.

When information, a condition or a permission that only the user can give is actually needed, write the needed input in `wait.needed` and in `wait.reason` why no progress is possible without it. Because this wait stops all new dispatch, do not use it merely to wait for other running tasks. When no new request is needed and you are waiting for the results of work already posted, write empty requests and `wait: null` and you may explain the reason. If no such work remains, decide a path by which the research continues through the next research or review or the needed external input.

## Posting the judgment and the requests

In `overview`, briefly explain the direction this plan chose and its reasons, and the next things to do. Put the detailed grounds and the requests in `reason` and the fields below, and do not let the index's overview text alone make unresolved research read as completed.

Write `output/output.json` in the plan format of section 6 of [protocol.md](protocol.md), and put the updated `research-status.md`, `glossary.md` and `glossary-history.md` in the same `output/`. Together with the common fields `category: "plan"`, the `references` of the knowledge actually used and `supersedes: []`, include all of the following fields. A plan record does not supersede other records with `supersedes`, whether preceding plan records or research and review records. The requests posted by a preceding plan remain valid as they are, and the research status is found in the most recent plan record by the path above. To have an existing research record superseded by corrected research, write that record not in the output's own `supersedes` but in the `supersedes` of the research request.

| Field | The judgment and requests to hold |
|---|---|
| `reason` | What was learned from the events and existing results, how the preceding expectations differed from the actual results, why this next work and order were chosen, and what is expected of each request |
| `research` | Array of research requests. Each item has `instructions`, `references`, `supersedes` |
| `explorations` | Array of exploration requests. Each item has `instructions`, `references` |
| `peers` | Additional peer requests needed. Not duplicating automatic dispatch; the target is a research record or an exploration. Empty array if none. |
| `reviews` | Array of additional review requests. Each item has instructions, references and target. Standalone research is {"kind":"research","record":"target ID"}, and a work–peer bundle is {"kind":"bundle","work":"work ID","peer":"peer ID"}. |
| `goal_review` | `null` if not requested. If requested, an object with `instructions` and `references`. The runner attaches the goal `target`. |
| `wait` | `null` if there is no external-input wait. If there is, an object with `needed` and `reason` |
| `index` | The index layout of 'Organizing the index': an object with `modules`, each with `name`, `title`, `description` and `records`. Carried forward from the previous plan and edited; `{"modules": []}` leaves every record in the general module |

An array with no requests is written as `[]`. The execution contract for posting, retrying and waiting follows section 6 of [protocol.md](protocol.md). When a wait is released by user input, the runner launches the next plan first and dispatches already-posted undispatched requests into the remaining slots, so those requests may run without waiting for the judgment of the plan that read the new input. Therefore requests whose content would differ according to the user's answer are not posted together with `wait`; the plan that receives the answer posts them.

Read the instructions and references from the standpoint of the session that will receive the request, and finish with the official check and self-submission procedure of [common.md](common.md). The runner dispatches the requests of an integrated plan without a separate plan-approval step.
