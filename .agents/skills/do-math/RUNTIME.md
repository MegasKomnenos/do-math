# Running and operating a research instance

[runner.py](runner.py) carries the research on one goal through plan, research, exploration and independent review sessions. The user fixes the goal, requirements and permissions in `goal.md` and puts the execution environment and the per-category models in `settings.json`. The runner launches the first plan, performs the posted research, exploration and review requests, and completes when an integrated goal review judges `achieved`. The published results are read in the instance's `knowledge/` and in that instance's own Git. Being integrated into the knowledge means having passed the output format check. Mathematical establishment is judged by the published independent reviews.

Python 3.12 or later, Git, and the Codex and Claude CLIs actually to be used are needed. CLI authentication and model access must be prepared on the host concerned. The detailed contract of model invocation and limit detection is in [CLI.md](CLI.md), and the shared definitions of output and settings in [protocol.md](protocol.md). The runner's process identification supports Windows and Linux. On Linux the session termination command uses Python's `pidfd_open` and `pidfd_send_signal`.

The order of preparing the goal and settings and reporting the launch location, starting from the user conversation, follows [SKILL.md](SKILL.md). The path for reading published expositions, independent reviews and the grounds of goal achievement is also in that entry point.

## Preparing a new run

The fields and examples of `settings.json` have their authoritative definition in section 1 of [protocol.md](protocol.md). Replace executable paths with the actual installation paths, and in JSON write Windows paths with `/` or with backslashes as `\\`. The runner runs only one plan at a time within `max_sessions`. The `lean` settings are used by the instance's Lean broker, a process the runner keeps alive for as long as it runs and through which every compile goes; sessions submit their compiles to it and do not run Lean themselves ('The Lean broker' below and [LEAN.md](LEAN.md)).

`init` copies the two source files and creates `knowledge/`, `sessions/`, `runner/`, `control/inputs/` and the instance's own `.git/`. The first Git commit contains the goal, the settings, `.gitignore` and an empty `knowledge/index.md`, the general module of the index. Sessions, runner state and user inputs are preserved as files but excluded from Git. Published knowledge is committed with an index update at every integration. The commit author is the `do-math <do-math@localhost>` specified in the invoking command. If `init` fails, a folder in the middle of creation may remain, so fix the error and prepare at a new path. An existing instance is not overwritten.

## Detached launch and restart

`start` launches the runner as a process whose lifetime is separated from the conversation. On Windows it uses `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and opens no console window; stdin is DEVNULL, and stdout/stderr are new log files for each invocation. On Linux it creates a new process session. Once the `pid`, `stdout`, `stderr` and `instance` of the returned JSON are recorded, the calling conversation can end.

Before returning success, it confirms the new launch token and the OS process identity of the live runner. The stdout log contains the `started` record of that launch. If the instance is already complete and has no sessions to process, the runner may exit soon. In that case, confirm the start record of that launch and the complete state. If the launch confirmation does not finish within 10 seconds, it returns an error and the log paths. This error alone does not mean the child exited, so first read the logs and `status`. Initial settings or context-file errors and duplicate execution are confirmed in the start error log.

If the runner dies or the PC reboots, launch it again with the same `start` command. The instance's file lock is held by the OS, so it is released automatically when the process dies. The `runner/lock` file is left as it is and not deleted. Two runners cannot change the state of the same instance at the same time.

A restarted runner confirms the PIDs and OS creation identities of the recorded sessions. If one is alive it waits; if it is dead, it officially checks and integrates the remaining output or handles it as a failure. It does not relaunch that session. Posted undispatched requests and events not yet delivered are processed in continuation. The `max_sessions`, `defaults`, `cli` and `limit_wait_seconds` the runner uses are read at launch, so changes apply from the next launch. The `lean` settings are read by the Lean broker, which applies a change to the file within a second and keeps the last valid configuration if the new file is invalid ('Settings' in [LEAN.md](LEAN.md)). The runner checks the format of the whole file, the `lean` keys included, at launch. Sessions read the documents and tools on the current path.

The `start`, `run`, `status` and `kill-session` of one instance are all run from shells of the same privilege level. On Windows, do not mix a shell elevated to administrator with an ordinary shell. If the runner and `status` cannot open a recorded PID, they regard that PID as reused by a process of another account and judge that the original process has ended. Since a runner, session host or CLI launched at the same privilege level can always be opened, this judgment is accurate. If privilege levels are mixed, the OS may refuse to query a live process. Then a restarted runner may regard a session still running as ended and check and integrate, or fail, its unfinished output. `status` may report a live runner as `runner_alive: false`, and `kill-session` ends with an error because it cannot open the CLI.

To attach to the console and observe a problem, `python <skill>/runner.py run <instance>` can be used. This command does not return until exit, so when a user conversation starts a new run it uses `start`.

## The Lean broker

Sessions do not run Lean themselves. Each instance has a single process, the Lean broker, through which every compile in the instance goes, so that the memory of all running compiles stays within one budget. [LEAN.md](LEAN.md) explains what a compile costs, what the broker does with it, how it decides which compile to start next, and what it asks of sessions. This section covers only the runner's side: how the broker is started, kept alive and found again.

The broker is `lean_broker.py serve <instance>`, run as a detached process like the session hosts and the archiver. The runner starts one when it starts and another on any later tick where it finds no live broker, for as long as it runs; the only tick on which it does not is its last, when the instance is complete or halted and nothing is active. It checks liveness the way it checks sessions: by the process identity recorded in `runner/lean/process.json`, PID and creation time together. A broker found alive is adopted, whoever started it; the runner reaps only the one it launched itself. The runner never terminates a broker. The broker outlives the runner, keeps serving the sessions that are still running, and exits on its own when the instance is complete or halted, no session is active and no job is queued or running. If it exits at once after being started, for instance because `settings.json` is invalid, the runner tries again at most every ten seconds (`BROKER_RETRY`) and the error is in `runner/lean/broker.log`. A session that finds no live broker starts one itself before submitting a compile, so compiling does not depend on the runner being alive. Only one broker can exist per instance, because it holds the lock file `runner/lean/lock`, the same kind of lock as the runner's own.

Each compile runs under a job host, `lean_broker.py _job`, which is to the broker what the session host is to the runner: the broker records the host's identity in its state before it writes the `GO` file that lets the host start Lean, the host records Lean's identity and exit code, and so a broker that dies in the middle of a compile loses neither the output nor the exit code. The next broker picks the compile up by identity.

The `status` command includes a `lean` object with the broker's liveness, the configuration it is using, the Lean version, its queued and running jobs, and the number of finished ones. `python <skill>/lean_broker.py status <instance>` prints the same in more detail, and `python <skill>/lean_broker.py cancel <instance> <job>` ends one job.

## Status query, stop and user input

`index` takes the lock of an instance whose runner is off and rebuilds every index file from the published records: `knowledge/index.md`, the general module, and one `knowledge/index/<name>.md` for each module the latest plan declared in its `index` field. The order of entries follows the order of the publication commits of the instance Git. It appends new records at the end of the general module, places filed records in their modules, updates the current review and supersession marks, removes module files the latest plan no longer declares, and adds no commit if no file changed. If the derived index is missing or damaged, it is restored as long as the original records are intact. If there is a published record not yet committed to Git, `index` issues a diagnosis and refuses without changes, so recover the publication work with `start`. A session under recovery is shown as `publishing` in `state.sessions` of `status`. On restart, too, unfinished publications are processed first and then the index is rebuilt.

`status` prints read-only JSON. `runner_alive` is the current result of querying the runner PID and creation identity. `knowledge` is the location of the published knowledge. `dispatch_blocks` lists `STOP`, `external_input`, `usage_limit`, `halted` and `complete`, which may overlap. `lean` is the Lean broker's liveness, configuration and jobs ('The Lean broker' above). `state` holds the whole state of the table below. When the runner is dead, the session states are those at the time of the last save, and on restart they are updated against actual liveness.

`stop` creates `control/STOP`. It stops only new dispatch, and sessions already started proceed through exit, check and integration. `resume` removes this file. The external-input wait, the provider limit, the halt after consecutive plan failures (`halted`) and completion are each separate conditions, so they may remain after STOP is removed. `resume` itself does not start the runner. If `status.runner_alive` is false, `start` is needed.

`input` copies the raw bytes of a nonempty UTF-8 input file to `control/inputs/<unique name>.txt` and returns that path. A running runner detects the input, delivers it to the next plan as a `user_input` event and releases the external-input wait. The runner stays alive during the wait, so no further launch is needed. If the runner is dead, enter the input and `start`. If STOP or a limit wait remains, the input is preserved and the release of that condition is awaited. `halted` is not released by an input but by a restart. The complete state is not released by user input.

Input can also be given directly as a file. Complete one uniquely named UTF-8 text file and add it to `control/inputs/`. The runner consumes it once by file name and neither deletes nor modifies the text. If there are several files not yet consumed, it creates events in the order of file modification time (by name if equal). Modifying a file already consumed is not regarded as a new input. A file being written is written under a temporary name beginning with a dot and then renamed to its final name. Files beginning with a dot are ignored. Empty files and decoding or read failures are left in `state.input_errors` and not consumed, so the file can be fixed and read again.

## Terminating one stuck session

Give `kill-session` the actual session ID queried. Choose the target session by reading the category, model, start time and request in `state.sessions`. Before the runner's collection, the CLI PID may not yet be in the state, but `kill-session` reads the session's latest `process.json` directly. If the CLI itself has not been launched yet or the process information could not be obtained, the termination command returns an error.

This command cross-checks not only the recorded CLI PID but also the OS creation identity on the same process handle before terminating. If the PID has been reused by another process, it does not terminate. On Windows it uses `TerminateProcess`, on Linux it sends SIGKILL through a pidfd. The target is that one CLI process. It is not a command that terminates all the descendant processes the CLI launched separately. The session's Lean compiles are the one exception, and not by this command's doing: they are jobs of the Lean broker, and the broker cancels the jobs of a session whose host and CLI are both dead, terminating their process trees ([LEAN.md](LEAN.md)). It does not terminate the runner or the session host in its stead.

Session run time has no cap. Even after a forced termination, the runner judges the remaining output by the same official check as a normal exit. If it passes, it is integrated; if there is none or the format is wrong, it is sent to the next plan as a failure event. If the runner is off, continue this processing with `start`. To stop new dispatch as well, use `stop` separately.

## Unfinished requests and events a plan reads

The plan's launch prompt links this document and **the instance's `runner/state.json`**. `requests` preserves all the requests earlier plans posted, the automatic peers after works, and the automatic reviews after peers. A new plan reads the instructions and supersession intent of `pending` and `assigned` requests and avoids duplicate work or tasks that would supersede the same record at the same time. An empty list in a new plan does not cancel existing requests.

| state field | Meaning |
|---|---|
| `requests` | Request key → request object. Plan request keys are `<published plan ID>:research:<0-based position>`, `:explorations:<position>`, `:peers:<position>`, `:reviews:<position>`, `:goal_review`. An automatic peer is `<work record ID>:automatic_peer`, and an automatic bundle review is `<peer record ID>:automatic_review`. `<research record ID>:automatic_review` posted before the reorganization is also preserved as an existing standalone research review. |
| A request's `category`, `task` | The category actually to be dispatched and the task-specific elements. Preserves `task.instructions/references` and the research `supersedes` or the peer/review `target`. An exploration has only `instructions/references`. |
| A request's `origin`, `selection` | The originating published record ID and an object holding only the model/effort the request overrode. The reason for the selection and the plan's whole judgment are read in `knowledge/<origin>/output.json`. For an automatic peer the origin is the original work record, and for an automatic bundle review the peer record. |
| A request's `status` | `pending`: not dispatched yet. `assigned`: assigned to a session ID and launching, or being checked and integrated. `finished`: valid output integrated. `failed`: launch/output failure processed. |
| A request's `session`, `record` | The assigned session ID (null before assignment), the published record ID after integration. To retry a failed request, a plan issues a new request. |
| `sessions` | Session ID → category, request key, final model/effort, status, process and check result. The status is `starting`, `running`, `publishing`, `integrated` or `failed`. `request: null` is a plan that received events. |
| A session's `host`, `cli`, `pid`, `started_at`, `cli_started_at` | The `{pid,birth}` identities of the host and the CLI, the CLI PID, and the UTC Unix seconds of dispatch start and actual CLI start. CLI fields not yet created may be absent. |
| A session's `record`, `reason`, `launch_error`, `log_error`, `exit_code`, `limit` | The published record ID, the check-failure reason, the launch failure, the limit-log read failure, the exit code if known, and the detected limit and its source. Recorded when applicable. |
| `events` | Events not yet delivered to a plan. All are moved into the `input.json.task.events` of the plan to be launched and the list is emptied. New events are not inserted into a running plan. |
| `seen_inputs`, `input_errors` | The list of consumed user file names, and the per-file diagnosis of files that cannot be consumed yet. The texts remain in `control/inputs/`. |
| `wait`, `limit_until`, `complete` | The external-input wait `{needed,reason}` or null, the limit expiry in UTC Unix seconds for all new dispatch, and the ID of the published goal review that decided completion or null. |
| `last_plan` | The record ID of the last integrated plan or null. Delivered as the next plan's `task.previous_plan`. |
| `plan_failures`, `halted` | The number of plans failed consecutively without limit detection (0 when a plan is integrated), and the mark `{reason, at}` that new dispatch stopped because that number reached the limit, or null. |

The first event is `start`. Integration of a valid review is `review_finished`, of a valid exploration `exploration_finished`, of a valid peer `peer_finished`; missing output, check failure and launch failure are `session_failed`; a user's raw text is `user_input`. Integrating a research record or an exploration creates an automatic peer request targeting the original work. Integrating a peer creates an automatic review request bundling the original work and that peer. A normal research integration itself does not become a separate plan event. Because the publication events of explorations and peers are delivered to the next plan, the plan can use that understanding for the choice of direction while keeping its not-yet-reviewed standing. A new plan is dispatched before posted requests whenever a slot opens, and requests are dispatched into the remaining slots in posting order. Events that arrive during a plan are left for the next plan. If a plan fails, the events that plan received go to the next plan inside the `task.events` of the failure event. The next plan receives the failure event and the events not yet delivered since.

`session_failed` includes the failed session's `category`, the request key `request`, the `task` it received as given, the request's `origin`, the detected `limit`, `exit_code` and `launch_error`. The plan does not dig through the `sessions` field of the runner state but reads from this event the original instructions, the supersession intent or review target, and the clues to the cause of failure. The event format is defined by section 2 of [protocol.md](protocol.md).

If user input has already arrived while a plan that declared an external-input wait is running, the wait is not kept, so that the input can be delivered to the next plan. If the same plan has both requests and wait, the requests are posted but new dispatch stops until new input arrives. The runner does not adjudicate concurrent supersession intents; the responsibility for interpreting the currency of published records and conflicting reviews lies with the plan.

## Session delivery, integration and recovery

The `input.json.context.common` of every session contains the skill's `common.md` and `protocol.md` and the instance's `goal.md`. `context.category` is one of the skill's `plan.md`, `research.md`, `explore.md`, `peer.md` and `review.md`, and `task` is this round's task-specific elements. The launch prompt tells the session its own session folder and input.json, the locations of the knowledge and settings, and an argv containing the actual Python and official checker paths. Only a plan gets the additional path for reading the runner state. Peers and reviews receive the published target record and their own input, without the author's session folder or log paths.

Sessions are instructed to write only in their own folders. The CLI permission options are for unattended execution and are not OS-level folder write isolation. Both Codex and Claude are launched as new conversations. The UTF-8 `prompt.txt` is connected as the stdin file, and each one's `cli.stdout.jsonl` and `cli.stderr.log` as the output files, and they run without a shell.

Each session has a small Python **session host** that holds the CLI handle and waits for its exit. This host is neither an AI session nor a restart service. It is a one-shot parent process for confirming and recording the exit of the existing CLI even if the runner process dies. The runner first saves the assignment and the consumed events in the state, saves the host's process identity, and then permits the CLI start with the `GO` file. A host interrupted in between, without receiving start permission, does not launch the CLI. On recovery, that assignment is checked or handled as a failure, and the same request is not re-dispatched.

The host's `process.json` holds the actual CLI's identity and start time, and `exit.json` the exit code or launch error. During normal execution the runner follows the exit of the CLI handle the host holds, and on restart it confirms the liveness of both the host and the recorded CLI. If all disappeared through a reboot, the remaining output is processed. A permission error on a process query is not regarded as death but left as a runner error.

Regardless of the exit code and the manner of exit, the output is re-checked with `check_session` of the official [check.py](check.py). If it passes, the whole `output/` is copied into a new `knowledge/k<unique ID>/` and a Git commit is left. `input.json`, the intermediate work and the logs are not copied into the published knowledge. During the copy it is kept in `runner/stage-<record ID>/`, and the completed directory is moved to the published location. The record ID is saved in the state first, and on restart the records already moved and the Git commits are confirmed and processing continues, so the same output is not integrated again under a new ID. Existing published records are not overwritten.

The `work/` of a session whose processing ended in integration (`integrated`) or failure (`failed`) is compressed into `work.tar.xz` in the same session folder and the original directory is deleted. The `work/` of a session still running or publishing is not touched. Compression is the job of an archiver process separate from the runner (`runner.py _archive <instance>`), so even if compression takes long, the runner's collection and dispatch do not stop. The runner launches the archiver process when it finishes processing a session and at launch. If one is already running, it launches another after that process ends. The archiver process finds and processes all finished sessions in the runner state. So the `work/` of sessions that ended while the runner was off, or before this feature existed, is also compressed at the next launch. The `runner/archive-lock` lock lets only one run per instance, and per-session errors are left in `runner/archive.log` one JSON line each.

The original is deleted only after the archive has been verified. The archiver process first writes an xz-compressed tar to `work.tar.xz.part`. The compression level is the runner.py constant `ARCHIVE_PRESET` (default 9, compressor memory about 674 MiB). The finished archive is read back to the end and cross-checked to contain every directory and file of `work/` with the same names and SHA-256. Only when the cross-check matches is it renamed to `work.tar.xz` and `work/` deleted. If the write or the cross-check fails, only the `.part` is deleted and `work/` is left as it is, to be retried at the next archiver run. An existing `work.tar.xz` is not overwritten. If `work/` remains because a deletion was interrupted, it is deleted only when the remaining content is in the archive with the same hashes. If it differs, both are kept and an error is left. If `work/` contains a symbolic link or junction, that session is not compressed, so as not to compress or delete beyond the link.

A compressed session has no `work/` path. If the original is needed, extract it in the session folder with Python's `tarfile` or an xz-capable `tar -xf work.tar.xz` to restore `work/`.

The posting of an integrated plan's requests, the automatic peer of a work, the automatic bundle review of a peer, the next-plan events of explorations, peers and reviews, and the mark that a session's processing is complete are saved in one atomic state replacement. The follow-up request keys of the same published record are fixed, and enqueue does not overwrite an existing key. This is the structure for not creating duplicate automatic follow-ups even when the integration procedure is continued during a restart. On Windows, if the replacement is briefly refused because of another reader's open file, the same replacement is retried for up to 60 seconds. Meanwhile readers read the previous complete state, and a continuing access refusal and other save errors are exposed as they are. If the runner exits on a Git or disk error, resolve the error in the new start log and restart. A Git integration failure is not turned into a mathematical session failure. Deleting or reverting the internal files of `runner/` or published records by hand removes the premises of this recovery path, so proceed through the operating commands.

The runner saves at the points where the state changed. In the 0.25-second polling loops without change, the state file is not rewritten. JSON is not built as a whole-document string; it is encoded item by item and written to a temporary file through a preallocated 64 KiB write buffer. After all writes and fsync are done, the file is replaced atomically. A failed temporary file is removed and the previous complete version preserved. It is not an implementation that also eliminates small dynamic allocations such as encoding one JSON string.

At launch the runner process separately reserves 64 MiB of emergency memory. If a MemoryError occurs while saving the state, it releases this space and retries the save once. After that it stops new dispatch, and proceeds after re-reserving the emergency space once Windows's available commit memory is 512 MiB or more. If a MemoryError occurs in other processing or the save retry also fails, it waits for recovery at 5-second intervals. In that case it does not save a memory state only partially changed in the middle of processing; it re-reads the last atomically saved state and continues on the same recovery path as a restart. The existing CLIs keep running in their detached hosts. The release of the emergency space and the recovery wait are recorded in the runner's stderr.

This protection is for the runner's own memory use and recovery. It does not change the AI session cap or the model selection. How much memory Lean compiles may take together is decided by the Lean broker's budget, and a compile is held back when the rest of the machine, this runner included, is short of memory, by the broker's machine gate; both are defined in [LEAN.md](LEAN.md). Neither protection is a guarantee against sustained OS-wide memory exhaustion or forced process termination, and a launch failure before the emergency space is reserved is confirmed in the new start log.

Only limit signals are read from the provider logs. If there is a limit, **new dispatch of all categories** is blocked until `limit_until`, while sessions in progress and the processing of exited outputs continue. An OSError on reading the logs is left as `log_error` and the official output check still continues. Ordinary text, the JSON format and the exit code of the CLI logs are not conditions for approving the published output. The expiry of a limit does not release STOP, the external-input wait, `halted` or completion.

Only the `goal.verdict == "achieved"` of a goal review that was re-checked and integrated into Git creates completion. After completion all new dispatch is blocked, including automatic peers, reviews and plans. Existing sessions continue through exit and integration, and when all have finished, the runner exits normally. Undispatched requests and remaining events are then left as history. If there is an existing session that does not finish, the runner waits too, so use `kill-session` if needed.

If plans fail consecutively `PLAN_FAILURE_LIMIT` times (runner.py constant, default 3) without provider-limit detection, the runner records `halted` and stops all new dispatch. This is the device that prevents a cause that repeats the same failure when a plan is relaunched, such as an expired login, an unusable model name or a broken CLI path, from creating an endless loop of failure and re-planning. Existing sessions continue through exit and integration, and when all have finished, the runner exits. After a person fixes the cause, restarting with `start` or `run` releases `halted` and the failure count. Research, exploration, peer and review failures do not count toward this number and go to the plan as events.

## Command results and implementation entry points

Command success is exit code 0 and stdout JSON. `run` prints the start JSON and continues running, and exits with 0 after draining the remaining sessions following completion or `halted`. A command execution error is `{"error":"description"}` on stderr and exit code 1, and a wrong argument usage is argparse's explanation and exit code 2. `status` is 0 if the read succeeds, even when the runner is off or the research is waiting. `stop/resume/input` succeed by delivering the file, and confirmation that a session has already processed it is done in `status`.

All the actual definitions are in [runner.py](runner.py). `initialize/load_settings/lean_config` are initialization and settings, the `lean` keys and their derived values included; `start/Runner.run/InstanceLock` are the detached launch, the single runner and the release of the halt on restart; `Runner.dispatch/session_host` are input and CLI process delivery; `Runner.collect/finish/apply_output` are exit, check, Git and the follow-up flow; `Runner.refresh_index` with `knowledge_index.render_index_files` renders the general module and the module files from the records and the latest plan's layout; `Runner.archive/archive_finished/archive_work` are the compression of finished sessions' `work/`; `Runner.ensure_broker` and `lean_status` are the supervision and reporting of the Lean broker, whose own definitions (`Broker`, `job_host`, `reservation/admission`, the client commands) are in [lean_broker.py](lean_broker.py); `Runner.ingest_inputs/tick` and `dispatch_blocks` are events, dispatch and waits; `status/submit_input/terminate_process/main` are the operating commands. The Windows creation time and the Linux boot ID plus start tick of `process_identity` are the process identity for distinguishing PID reuse.

[tests/test_runner.py](tests/test_runner.py) confirms, with fake CLI processes and the actual official checker and Git, a small end-to-end flow, the automatic peer and bundle review of research records and explorations, the delivery of each publication event, the integration of abnormally exited output, failure, STOP, user input and a synthetic limit, the halt after consecutive plan failures and restart, the single-runner lock, and the integration of existing sessions and the detached launch after recovery and completion. For the compression of finished sessions' `work/`, it confirms automatic compression through the runner, the selection of finished states only, the single execution of the archiver process, the round-trip identity of the archive, and the preservation of the original on write failure, a leftover `.part`, links, an interrupted deletion and a mismatch. [tests/test_lean_broker.py](tests/test_lean_broker.py) confirms the Lean broker with a stand-in `lean`, as listed in 'What has been confirmed, and what has not' of [LEAN.md](LEAN.md). [tests/test_state_write.py](tests/test_state_write.py) confirms, on Windows, the retry of state-file replacement and the error and preservation of the previous state under a continuing refusal. [tests/test_check.py](tests/test_check.py) confirms output structure and references, including the plan's index layout and the local glossary of research, exploration and peer outputs, [tests/test_index.py](tests/test_index.py) the rendering of the general module and the module files and their Git handling, [tests/test_glossary.py](tests/test_glossary.py) the structure checks of both glossaries, and [tests/test_cli_adapter.py](tests/test_cli_adapter.py) CLI command construction and limit detection.

The working-context documents use temporary test documents, so these are not tests that verify the judgment content of the actual documents or the performance of actual models. Actual Codex and Claude model access and a mixed end-to-end flow are confirmed separately by the published results and reviews of an actual instance. The following command runs the whole test suite in the Python 3.12 or later environment above. The state-file replacement test runs only on Windows.

```powershell
$skill = 'C:/math/.agents/skills/do-math' # actual installation path
python -B -m unittest discover -s "$skill/tests" -v
```

## Existing instances after the peer stage was added

If an existing settings.json has no peer defaults, the runner copies the review model and effort and uses them as the peer defaults. If there are explicit defaults.peer, those values are used, and a selection a plan specified on an individual request overrides only that field. All roles share the existing max_sessions cap. No separate permanent service or new kind of process is kept.

Past published records and complete or failed states are neither reinterpreted nor overwritten. Research, exploration and review sessions running at the time of the reorganization continue to perform with their own input. A peer is attached to the research records and explorations the reorganized runner newly integrates. Legacy standalone research review requests already posted are performed as they are. Peers are not assigned retroactively to past explorations in bulk; old works worth reading anew are requested by a plan in peers.

An instance created before the English port is carried over the same way. Its published records and their Korean text are read as they are; `knowledge/index.md` is rebuilt with English labels at the next start; and the first plan after the port rewrites the previous glossary's former Korean field labels into the current English ones, which are the only labels the checker accepts.

When the user updates the runner code, first block new dispatch with stop. Existing CLIs can keep running in their detached hosts. After replacing the code, restarting only the runner process collects the saved session identities and outputs and continues processing. Input files and published records are preserved, and sessions are not restarted by arbitrarily editing the runner state. After confirming the new start record of start and status.runner_alive, resume dispatch with resume.


## Existing instances after index modules and local glossaries were added

At the next start the index is rebuilt in the new form: plan records lose their entries, the latest plan is linked in the preamble, and every research and exploration record sits in the general module until a plan declares modules in its `index` field. Plans published before the change have no such field and are read as declaring none. Records published before the change have no `glossary-local.md`; they are read as they are, and the next plan harvests candidates from their `glossary-proposals.md` where one exists, as well as from the local glossaries of new records. No state field, request key or event changes, and sessions running at the time of the update finish with their original input; but a research, exploration or peer session that finishes under the new checker must have published a local glossary, which a session started under the old instructions will not have done. So block new dispatch with `stop`, let the running sessions finish and be integrated, and only then replace the code and restart, as the paragraph above describes.

## Existing instances after the Lean broker was added

An instance created before the broker existed needs no change to its files. Its `settings.json` is still valid and receives the defaults of the new `lean` keys. The runner starts a broker at its next start, and the first compile with each set of imports triggers the measurement of that set's baseline. Sessions that were started under the old instructions will keep running Lean directly until they finish, outside the budget. So block new dispatch with `stop`, let those sessions finish and be integrated, and only then replace the code and restart, as the paragraph on updating the runner code above describes. No state field, request key, event or published record changes.

## Checking the glossaries and the index layout

A plan submits glossary.md with the current seven fields of common.md and unique term-N anchors, glossary-history.md and research-status.md, and optionally an `index` field whose modules have case-distinct identifier names and name existing research and exploration records, each at most once, with at least one record in every module other than `general`. A research, exploration or peer session submits glossary-local.md with the same seven fields plus Global candidate and unique local-N anchors, possibly with no entries. check.py applies these structure checks to every new output of the category concerned. They confirm the files, the entry structure and the references; they do not judge the mathematical validity of definitions, the appropriateness of term reuse, the merit of a candidate or the grouping of records into modules.
