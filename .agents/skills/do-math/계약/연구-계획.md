# 연구 계획

## 이 역할이 맡는 판단

연구 계획은 현재 배정 후보 전건을 비교해 이번에 수행할 과제와 실행 순서를 정하고, 선택하지 않은 과제에는 보류 이유를 남기는 활동이다. 이미 결과를 반환한 과제의 완료 기준도 실제 산출과 대조한다. 새 질문이나 계약이 필요하면 후보 준비를 요청하고, 현재 결과가 목표를 충족했을 가능성이 있으면 독립 목표 감사를 요청한다.

연구 계획은 후보나 작업 계약을 저작하지 않는다. 후보를 저작한 실행의 작업 문맥을 이어받아 자기 제안을 선택하지 않고, 실행기가 제공한 계약·검토·공용 근거를 별도 관점에서 읽는다. 계약 문면을 고쳐야 하면 선택 결과 안에서 직접 수정하지 않고 후보 준비에 이유와 필요한 변경을 돌려준다.

계획이 과제를 선택했다는 사실은 그 과제의 결과, 과제 완료나 수학적 해결을 뜻하지 않는다. 계약이 승인된 과제에 아직 증명이 없다는 점은 선택을 막는 이유가 아니다. 그 증명이나 조사를 수행하는 것이 선택 뒤 연구 수행의 책임이다.

## 시작 전에 확인할 입력

`SKILL.md`의 읽기 대응표가 배정한 공통 문서를 먼저 읽고 이번 출력 스키마를 확인한다. 「공통 실행」의 입력 회수·실패 반환과 「지식 저작과 재사용」의 적용 대조를 후보 비교와 과제 완료 판정에 적용한다. 연구 계획은 기존 지식을 선택 근거로 사용할 수 있지만, 그 과정에서 새 수학 내용을 입증하거나 지식 문서를 직접 저작하지 않는다.

`action`의 이유와 사건 참조를 읽어 이번 계획이 열린 까닭을 확인한다. 새 연구 결과, 작업 계약 검토, 사용자 결정, 대기 입력의 도착, 지식의 현재성 변화나 후보 준비 결과 가운데 무엇이 다음 선택을 다시 보게 했는지 구별한다. 여러 사건이 합쳐졌다면 실제로 입력에 포함된 사건만 이번 판단의 근거로 사용한다.

계획 입력에서 다음 집합을 확인한다.

1. `goal`, `goal_kind`, `policies`에서 현재 연구 목표와 선택 우선순위, 허용 범위를 읽는다.
2. `ready_task_ids`가 이번 선택·보류의 정확한 모집단이다. 같은 입력의 `tasks[].status=ready`와 대조하고, `task_readiness`에서는 해당 과제의 계약 판본·근거를 확인한다. 다른 과제의 검토나 과거 출력의 ready 주장을 연결하지 않는다. ID 목록이 비어 있으면 `selections`와 `deferred`도 모두 비운다.
3. `assessing`인 과제와, 이미 연구 결과를 반환해 실제로 완료 판정을 기다리는 `waiting` 과제를 찾는다. 수행 전 과제나 결과가 없는 대기 과제에는 완료 판정을 만들지 않는다.
4. `knowledge_catalog`, 관계와 원자료에서 각 후보가 재사용하려는 지식의 실제 내용·가정·범위·근거·효력을 확인한다. 제목·요약·관계 경로만으로 적용 가능성을 확정하지 않는다.
5. `recent_history`에서 이전에 종료된 연구 계획 실행의 결과·오류·당시 action과 정확한 산출 원문을 읽어, 이전 선택의 기대, 실제 결과와 실패, 반복 보류와 기아 위험을 찾는다. 큰 이력이 `source_ref`로 바뀌면 현재 선택에 필요한 회차의 원문을 회수하고, 현재 실패·이의를 오래됐다는 이유로 생략하지 않는다.
6. `academic_phase`, 현재 학술 요구, 학술 검증 상태와 외부 거부가 있으면 연구 생산과 학술 후속을 구별한다.

큰 `tasks`나 다른 목록이 `source_ref`로 바뀌면 원문을 읽는다. `ready_universe_ids`가 있으면 그 ID 전건이 이번 선택 처분의 모집단이다. 축소 목록에 설명이 없는 ID도 선택이나 보류에서 빠뜨리지 않는다. 필수 원문을 읽지 못하면 해당 ID를 없었던 후보로 취급하지 않고, 현재 스키마에서 가능한 보류와 질문으로 읽기 실패를 드러낸다.

## 결과를 반환한 과제를 먼저 판정한다

과제 결과는 새 선택의 입력이므로, `assessing` 과제의 완료 판정을 빠뜨린 채 다음 작업만 고르지 않는다. `task_assessments`는 현재 실행이 실제로 결과를 읽을 수 있는 과제에만 작성한다. `assessing` 과제 전건을 한 번씩 판정하고, `waiting` 과제는 연구 결과가 이미 있으며 그 결과를 지금 판정할 근거가 있을 때만 포함한다.

과제마다 계약의 `completion_criteria` 원문을 읽고, 같은 문자열을 `criteria_results[].criterion`에 정확히 복사한다. 표현을 매끄럽게 고치거나 여러 기준을 하나로 합치지 않는다. 각 기준에 대해 수행 보고, 새 지식, 관계, 체크포인트와 파일 산출의 실제 내용을 대조한다. 파일이 근거라면 `output_files[].local_path`에서 원문을 읽고 어느 내용이 기준을 충족하거나 충족하지 않는지 `evidence`에 적는다. 파일이 존재한다는 사실이나 수행자의 자기평가만으로 충족을 선언하지 않는다.

`criteria_results[].satisfied`는 그 기준이 실제 근거로 충족됐을 때만 `true`다. 읽지 못한 필수 파일이나 확인하지 못한 범위가 있으면 현재 완료 판정에서 충족을 확립하지 못했으므로 `false`로 두고, `evidence`에 읽기 실패와 미확인 범위를 쓴다. 이 `false`는 완료 근거가 성립하지 않았다는 뜻이지 기준의 수학적 부정을 증명했다는 뜻이 아니다. 해당 과제는 `incomplete`로 두고 원자료 수리나 재판정 조건을 `reason`에 남긴다.

현재 스키마의 완료 판정은 다음 뜻으로 사용한다.

- `completed`는 모든 완료 기준이 실제 근거로 충족됐을 때만 사용한다. 모든 `criteria_results`가 `true`이고 근거가 있어야 한다.
- `incomplete`는 수행 결과는 돌아왔지만 하나 이상의 계약 의무가 남았을 때 사용한다. 남은 기준, 재사용할 부분 결과와 다음 수행 또는 계약 정련이 필요한 이유를 `reason`에 적는다.
- `closed`는 계속하지 않을 권위 있는 범위 처분이 현재 과제에 이미 있을 때만 사용한다. 단순 실패, 사용자 답변 대기, 낮은 기대나 계획자의 선호는 과제를 닫는 근거가 아니다.

긍정 결과가 없거나 한 방법이 실패했어도 계약이 요구한 탐색 범위와 검증을 실제로 끝냈다면 해당 완료 기준은 충족될 수 있다. 반대로 유용한 부분 정리나 파일이 있어도 필수 기준이 남으면 `completed`가 아니다. 결과의 유용성과 과제 완료를 구별한다.

완료 판정을 쓸 때는 기존 기대와 실제 결과가 어떻게 달랐는지, 그 차이가 다음 질문이나 선택을 어떻게 바꾸는지 함께 판단한다. 재사용할 수 있는 부분 결과는 정확한 ID·조건·효력과 남은 차이를 `reason`, `summary`와 `used_sources`에 남긴다. 계약 자체가 현실과 맞지 않아 개정이 필요하면 `incomplete`로 남은 의무를 보존하고 `preparation_requests`에 무엇을 왜 정련해야 하는지 적는다.

## 배정 후보를 비교하고 선택한다

현재 CLI에서 `selections`와 `deferred`는 `ready`인 과제 전건을 정확히 한 번씩 나누는 출력이다. `selections`에는 선택한 과제의 정확한 ID만 실행 순서대로 넣는다. 설명문이나 프로필 이름을 넣지 않는다. `deferred`에는 선택하지 않은 나머지 과제의 ID와 구체적인 이유를 넣는다. 같은 ID를 두 곳에 쓰거나 어느 곳에서도 빼지 않는다.

현재 출력 스키마에는 별도의 `not_assessable` 값이 없다. 필수 원문을 읽지 못했거나 의미 판단에 필요한 근거가 부족해 이번에 선택할 수 없는 배정 후보는 `deferred`에 넣고, `reason`에 전략적 미선택과 구별되는 판정 불가 사유, 필요한 입력과 다시 볼 조건을 적는다. 판정할 수 없다는 이유로 모집단에서 삭제하지 않는다.

후보를 비교할 때는 다음 관계를 함께 본다.

- 현재 연구 목표와 부분 성과에 어느 과제가 실제로 기여하는가
- 기존 지식을 어떤 조건에서 재사용하며 아직 어떤 차이가 남는가
- 새 결과가 줄일 불확실성과 얻을 정보의 가치가 무엇인가
- 이전 시도와 무엇이 다르고 같은 실패를 반복하지 않을 근거가 있는가
- 과제들이 중복되는지, 서로 보완하는지, 선행 결과에 의존하는지, 독립 비교가 유용한지
- 오래 보류된 과제가 근거 없이 계속 밀리고 있는지
- 현재 작업 예산과 이미 진행 중인 연구를 고려할 때 어떤 순서가 후속 판단을 가장 잘 여는가

수학적 직감이나 탐색 가치도 선택 근거가 될 수 있지만 확인된 증거와 구별해 적는다. 후보 수만큼 용량을 채우거나 고정 점수 순으로 선택할 의무는 없다. 아무 과제도 선택하지 않는 판단도 가능하지만, 이 경우에는 각 후보의 보류 이유와 다시 볼 사건이나 입력을 남겨 같은 입력의 빈 계획을 즉시 반복하지 않게 한다.

`selections`의 순서는 연구 수행 요청의 우선순위다. 동시 실행 수는 모델별 작업 슬롯이 정한다. 세션 예산에서는 「모델과 실행예산」에 따라 선택한 과제의 난이도·중요도와 근거를 `model_assessments` 확장으로 반환한다. 요구 등급을 먼저 정하고 그 모델의 슬롯이 없으면 대기하도록 배정한다. 작업의 우선순위와 모델 등급을 같은 것으로 취급하지 않는다. `queued_work`의 기존 미시작 요청을 재정렬하거나 취소해야 하면 같은 문서의 `queued_requests` 절차로 이유와 처분을 반환한다.

실행에 필요한 입력·도구·관찰 요구가 현재 지원과 맞는지도 확인한다. 모델 이름을 배정했다는 사실만으로 제공되지 않은 도구나 능력이 생기지는 않는다. 필요한 지원이 없으면 과제를 보류하고 `summary`, `questions` 또는 `preparation_requests`에 다음 소유자와 필요한 조치를 적는다.

AI가 만든 미완료 과제를 철회할 때는 `activity-extensions.json`의 `task_dispositions`를 사용한다. 이번 ready 모집단 중 철회할 과제는 `deferred`에 이유를 적고 확장에 철회를 제출한다. 결과 판정이 남은 과제는 실제 결과를 먼저 판정하며, 미완료 과제의 철회를 완료로 쓰지 않는다. 철회와 함께 그 과제의 미시작 요청이 제거된다. 일반적인 요청 취소나 수행 중 실행의 정지 권한까지 이 경로에서 만들지는 않는다. 적용 조건과 보존 범위는 공통 실행 문서를 따른다.

## 다음 준비와 목표 감사를 요청한다

현재 후보로는 목표의 남은 의무를 다룰 수 없거나, 기존 계약의 질문·범위·입력·완료 기준을 바꿔야 하면 `preparation_requests`에 후보 준비가 수행할 일을 쓴다. “새 후보 필요”로 끝내지 않고, 어떤 결과나 실패 때문에 무엇을 정련해야 하는지, 재사용할 근거와 아직 필요한 입력이 무엇인지 설명한다. 계획자가 새 계약 문안을 대신 쓰지는 않는다.

현재 K와 수행 결과가 목표를 충족했을 가능성이 있으면 `goal_audit=true`로 독립 감사를 요청한다. 계획자가 직접 목표 해결을 확정하지 않는다. 정확한 부분 결과만 있거나 필요한 동일성·현재 사용 효력이 없으면 그 사실을 `summary`에 남기고 목표 감사 요청 여부를 근거에 따라 판단한다.

수학적 해결 뒤에는 현재 학술 요구에 연결된 과제만 선택한다. 각 과제의 `solution_basis`, 요구 판본, 필수 입력과 외부 효과를 대조하고 일반 과제와 같은 방식으로 완료 기준을 판정한다. 외부 거부는 원문과 현재 해결 근거를 읽고 형식 타당성, 해설 동일성, 목표 충족과 별도로 판단한다. 현재 근거가 거부를 실제로 해소하면 `activity-extensions.json`의 `academic_resolutions`에 해소한 외부 거부 기록의 정확한 `id`, `decision` 값 `resolved`, 해소를 입증하는 `evidence`를 쓴다. 이 `id`는 입력 `external_rejections[].id`의 값이며, 외부 거부를 검토하도록 열린 계획에서는 `action.rejection_id`와 같다. 학술 요구의 `id`를 넣으면 실행기가 대상 거부를 찾지 못해 계획 결과 전체의 적용이 되돌려진다. 판단할 수 없으면 성공으로 만들지 않고 필요한 조사와 다음 소유자를 반환한다.

## 최종 산출과 다음 소비자

마지막 응답은 현재 출력 스키마를 따르는 JSON 하나다.

- `selections`는 선택한 `ready` 과제 ID를 실행 순서대로 담는다.
- `deferred`는 나머지 `ready` 과제의 ID와 보류 이유를 담는다.
- `preparation_requests`는 후보 준비가 새로 찾거나 정련할 질문을 담는다.
- `goal_audit`는 현재 근거가 독립 목표 감사를 열어야 하는지 나타낸다.
- `task_assessments`는 실제 결과를 반환한 해당 과제의 완료 기준별 판정이다.
- `summary`는 비교한 목표·후보·근거 범위, 선택의 이유와 불확실성, 이전 기대와 실제 결과의 차이, 보류와 재검토 조건을 설명한다.
- `used_sources`는 실제 판단에 사용한 정확한 기록 ID와 참조만 담는다.
- `questions`는 현재 권한과 자료로 정할 수 없고 답에 따라 선택이나 후속이 실제로 바뀌는 질문을 담는다.

실행기는 이 결과를 적용하기 전에 ID, `ready` 모집단 전건 처분과 현재 과제 상태를 다시 검사한다. 연구 계획은 입력을 고정했을 때의 판단이므로, 적용 전에 계약·입력·허가가 바뀌어 결과가 거부되면 실행기가 대신 다른 과제를 선택하도록 만들지 않는다. 달라진 전제를 다음 계획의 입력으로 돌려 새로 판단한다.

## 입력 부족, 출력 수리와 중단

원자료나 `source_ref`를 읽지 못하면 어느 파일과 범위를 확인하지 못했는지 `summary`와 `questions`에 적는다. 그래도 현재 스키마가 요구하는 `ready` 과제 전건은 `selections`와 `deferred`에 한 번씩 나타나야 한다. 판단할 수 없는 과제는 근거 부족과 다시 볼 조건을 가진 보류로 표현한다.

과제 결과의 필수 파일을 읽지 못하면 그 완료 기준을 충족했다고 쓰지 않는다. 실제로 확인한 기준과 미확인 기준을 나누어 `criteria_results`에 모두 남기고 `incomplete`의 이유와 필요한 파일 수리를 적는다. 실행 자체의 미완료를 연구 내용의 부정 결과로 바꾸지 않는다.

수신 검사에서 ID 중복, `ready` 과제 누락, 수행 전 과제의 완료 판정이나 완료 기준 문자열의 불일치가 반환되면 정확한 오류와 원 출력을 대조해 같은 계획을 형식에 맞게 수리한다. 오류를 피하려고 후보를 빼거나 완료 기준의 뜻을 바꾸지 않는다. 입력 전제나 의미 판단이 바뀌어야 하면 단순 수리가 아니라 새 계획으로 처리한다.

모집단 오류의 `missing`, `unexpected`, `duplicate`, `ready_task_ids`를 현재 입력과 대조한다. 과거 실패 출력은 오류를 조사할 자료이며 현재 상태의 근거가 아니다. 진단 뒤 새로 열린 계획의 `failure_diagnosis`는 바꿔야 할 판단을 설명한다. 이전 선택·보류 목록을 출발값으로 복사하지 않고 현재 모집단에서 다시 계산한다. `blocked_actions`에 실행 구성이나 저장 결함이 남아 있으면 후보의 문구 수정과 구별해 운영 담당에게 필요한 수리를 명시한다.

정지 요청을 받으면 새 후보 탐색이나 추가 원자료 조회를 시작하지 않고, 현재까지 비교한 후보·근거·미완료 판정과 바로 이어갈 위치를 공통 실행 문서에 따라 체크포인트에 남긴다.

## 적용 예

### 관련 있지만 같은 역할을 하는 두 과제가 있는 경우

배정 후보 A와 B가 같은 보조정리를 서로 다른 방법으로 탐구한다고 하자. A는 기존 K를 직접 적용할 수 있고 B는 독립적인 반례 탐색으로 A의 가정을 시험한다. 두 결과를 비교할 정보 가치가 충분하면 둘 다 선택하고 `selections`의 순서와 `summary`에서 의도한 중복을 설명할 수 있다. 현재 자원과 선행관계 때문에 하나만 먼저 해야 한다면 다른 하나를 `deferred`에 넣고, 앞 결과가 도착하면 다시 볼 조건을 적는다.

### 결과 없음이 완료일 수 있는 경우

과제가 크기 20 이하의 반례를 완전 탐색하고 탐색 코드·입력·결과를 보존하라고 했는데 반례를 찾지 못했다고 하자. 실제 파일을 읽어 범위와 재현 근거가 완결됐음을 확인했다면 “반례 없음”이라는 긍정 정리가 없더라도 해당 완료 기준은 충족될 수 있다. 반대로 코드가 존재하지만 일부 범위만 실행했다면 부분 결과가 유용해도 `incomplete`다.

### `ready`이지만 이번 계획에서 판단할 수 없는 경우

과제 ID는 `ready` 모집단에 있지만 재사용할 K의 상세가 `source_ref`에 있고 그 파일을 읽지 못했다고 하자. 이 ID를 출력에서 빼면 전건 처분이 깨진다. `deferred`에 정확한 ID를 넣고, 원문 읽기 실패와 다시 선택하려면 필요한 자료를 `reason`에 쓴다. 이를 전략적 보류나 수학적 부적합으로 설명하지 않는다.

### 목표 해결 가능성이 보이는 경우

연구 수행이 형식 결과 후보를 제출했고 형식 검사와 동일성 검토까지 현재 사용 가능한 상태로 돌아왔다고 하자. 계획자는 그 결과가 목표와 비슷해 보인다는 이유로 해결을 기록하지 않는다. 현재 목표의 범위와 결과의 적용 범위를 대조해 독립 감사가 필요하다고 판단하면 `goal_audit=true`를 반환하고, 남은 차이가 있으면 그 차이를 `summary`와 준비 요청에 남긴다.
