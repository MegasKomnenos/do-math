# 연구 계획

## 이 역할이 맡는 판단

연구 계획은 현재 배정 후보 전건을 비교해 이번에 수행할 과제와 실행 순서를 정하고, 선택하지 않은 과제에는 보류 이유를 남기는 활동이다. 이미 결과를 반환한 과제의 완료 기준도 실제 산출과 대조한다. 새 질문이나 계약이 필요하면 후보 준비를 요청하고, 현재 결과가 목표를 충족했을 가능성이 있으면 독립 목표 감사를 요청한다.

연구 계획은 후보나 작업 계약을 저작하지 않는다. 후보를 저작한 실행의 작업 문맥을 이어받아 자기 제안을 선택하지 않고, 실행기가 제공한 계약·검토·공용 근거를 별도 관점에서 읽는다. 계약 문면을 고쳐야 하면 선택 결과 안에서 직접 수정하지 않고 후보 준비에 이유와 필요한 변경을 돌려준다.

계획이 과제를 선택했다는 사실은 그 과제의 결과, 과제 완료나 수학적 해결을 뜻하지 않는다. 계약이 승인된 과제에 아직 증명이 없다는 점은 선택을 막는 이유가 아니다. 그 증명이나 조사를 수행하는 것이 선택 뒤 연구 수행의 책임이다.

## 시작 전에 확인할 입력

`SKILL.md`의 읽기 대응표가 배정한 공통 문서를 먼저 읽고 이번 출력 스키마를 확인한다. 「공통 실행」의 입력 회수·제출·실패 반환과 「지식 저작과 재사용」의 적용 대조를 후보 비교와 과제 완료 판정에 적용한다. 연구 계획은 기존 지식을 선택 근거로 사용할 수 있지만, 그 과정에서 별도 수학 조사를 수행하거나 기존 공용 지식의 개정을 저작하지 않는다. 비교 중 이미 얻은 부수 통찰은 공통 실행의 확장 경로로 후보만 보존할 수 있다.

`action`의 이유와 사건 참조를 읽어 이번 계획이 열린 까닭을 확인한다. 새 연구 결과, 작업 계약 검토, 사용자 결정, 대기 입력의 도착, 지식의 현재성 변화나 후보 준비 결과 가운데 무엇이 다음 선택을 다시 보게 했는지 구별한다. 여러 사건이 합쳐졌다면 실제로 입력에 포함된 사건만 이번 판단의 근거로 사용한다.

선택과 완료 판정의 모집단은 이번 입력 스냅샷에 고정된다. `ready_task_ids`와 `returned_task_ids`에 실제 지급된 전건을 다루며, 제출 사이에 새로 준비된 다른 과제를 소급해 처분할 의무는 없다. 선택된 과제의 계약·근거·권한과 현재 착수 조건은 중앙이 적용 직전에 다시 검사한다. 따라서 입력을 전건 검토한 것과 현재 배정할 수 있는 것은 별개의 조건이다.

`task_catalog`는 완료·진행 중 과제를 포함한 현재 과제 전건을 가리킨다. 이번 선택과 관련된 이전 실패·부분 성과가 `tasks`에 없으면 `task_catalog`의 `source_ref`에서 보고 원문을 회수한다. `task_catalog`가 참조로 축소됐으면 목록 원문부터 연다. `ongoing_work`에서 아직 끝나지 않은 연구·검토와 대기 행동의 대상·이유를 대조한다. 이 참고 자료는 `ready_task_ids`나 `returned_task_ids`의 처분 모집단을 바꾸지 않는다.

계획 입력에서 다음 집합을 확인한다.

1. `goal`, `goal_kind`, `policies`에서 현재 연구 목표와 선택 우선순위, 허용 범위를 읽는다.
2. `ready_task_ids`가 이번 선택 처분의 정확한 모집단이다. 과제의 `status`는 생명주기 상태이며 착수 가능성을 뜻하지 않는다. `task_readiness`에서 해당 과제의 계약 판본·착수 근거를 확인하고 다른 과제의 검토나 과거 출력의 ready 주장을 연결하지 않는다. ID 목록이 비어 있으면 `dispositions`도 빈 배열이다. 결과를 제출하여 판정이 필요한 과제는 별도의 `returned_task_ids`로 받으며, 그 전건에 `task_assessments`를 작성한다. `tasks`에는 두 모집단의 비교 정보와 원문 경로가 함께 들어 있다. 완료 판정에는 과제의 `source_ref`를 열어 실제 결과와 의무를 대조한다.
3. `returned_task_ids`가 지정한 결과 판정 대상 전건을 찾는다. 수행 전 과제나 결과가 없는 대기 과제에는 완료 판정을 만들지 않는다.
4. `knowledge_catalog`, 관계와 원자료에서 각 후보가 재사용하려는 지식의 실제 내용·가정·범위·근거·효력을 확인한다. 제목·요약·관계 경로만으로 적용 가능성을 확정하지 않는다.
5. `recent_history`에서 이전에 종료된 연구 계획 실행의 결과·오류·당시 action과 정확한 산출 원문을 읽어, 이전 선택의 기대, 실제 결과와 실패, 반복 보류와 기아 위험을 찾는다. 큰 이력이 `source_ref`로 바뀌면 현재 선택에 필요한 회차의 원문을 회수하고, 현재 실패·이의를 오래됐다는 이유로 생략하지 않는다.
6. `academic_phase`, 현재 학술 요구, 학술 검증 상태와 외부 거부가 있으면 연구 생산과 학술 후속을 구별한다.
7. `ongoing_preparation`에서 이미 진행 중인 준비의 배정 이유·대상·입력 판본·상태를 확인한다. 같은 의무가 배정되어 있으면 반환을 기다릴지, 별개의 추가 의무가 필요한지 판단한다. 이미 배정됐다는 이유로 의무 완료를 선언하거나 새 요청을 자동 폐기하지 않는다. 추가 준비를 요청할 때는 진행 중인 준비와 다른 질문 또는 새 전제를 설명한다.
8. `input_overflow_requests`는 입력 초과로 보류된 기존 연구 수행 요청이다. 각 항목의 `action_id`, `owner_activity_id`, `task_id`, 계약 판본·해시, `question_id`, 초과 원인·크기인 `detail`, 요청의 `model_assessment`와 `allowed_profile_refs`를 함께 읽는다. 이 목록은 여러 보류 요청을 포함할 수 있으며 `ready_task_ids`와 별개다.
9. `review_followups`는 이번 요청에 연결된 동일성 검토의 후속 자료다. 각 `source_ref` 원문에서 고정 제안, 실제 완료한 검토, 사용한 실행, 입력 초과 측정과 남은 의무를 읽는다. 여러 검토가 한 계획에 병합되면 전건을 다룬다. 자원 부족으로 종료·유예된 검토를 수학적 불일치나 승인으로 바꾸지 않는다. 제안 자체가 너무 크면 의미와 의무를 보존하는 재구성을 판단한다. 같은 미완료 과제의 정련은 `revision_requests`, 완료·닫힌 과제의 후속이나 다른 연구 의무는 `preparation_requests`로 연결한다. 더 큰 자원이나 새 허가가 실제로 필요한 경우에만 해당 사용자 결정을 요청한다. 유예된 검토의 사용 횟수는 시간이 지나거나 자리가 비어도 초기화되지 않는다.

큰 `tasks`나 다른 목록이 `source_ref`로 바뀌면 원문을 읽는다. `tasks`가 참조로 바뀌어도 직접 지급된 `ready_task_ids` 전건이 이번 선택 처분의 모집단이다. 입력에서 과제 설명이 바로 보이지 않아도 그 ID를 선택이나 보류에서 빠뜨리지 않는다. 필수 원문을 읽지 못하면 해당 ID를 없었던 후보로 취급하지 않고, 현재 스키마에서 가능한 보류와 질문으로 읽기 실패를 드러낸다.

## 결과를 반환한 과제를 먼저 판정한다

과제 결과는 새 선택의 입력이므로 `task_assessments`는 `returned_task_ids` 전건을 정확히 한 번씩 판정한다. 선택 처분 `dispositions`는 `ready_task_ids` 전건을 다룬다. catalog에서 참고할 수 있는 다른 과제를 두 모집단에 임의로 추가하지 않는다. 필요한 결과 원문은 제출 전에 회수한다.

과제마다 계약의 `completion_obligations` 원문과 안정된 의무 ID를 읽는다. 수행 보고, 새 지식, 관계, 체크포인트와 파일 산출의 실제 내용을 각 의무의 `claim`, `judges`, `evidence_required`에 대조한다. 파일이 근거라면 제공된 산출 원문을 읽고, 파일이 존재한다는 사실이나 수행자의 자기평가만으로 의무 충족을 선언하지 않는다.

필수 자료는 완료 판정 전에 실제로 읽는다. 읽기에 실패하면 지급된 원문 경로와 복원 자료를 확인하고, 현재 권한 안에서 가능한 경로 교정·재조회로 해결한다. 아직 읽지 않았거나 쉽게 회수할 수 있다는 이유로 판정 의무를 다음 역할에 넘기지 않는다.

`task_assessments[].item_dispositions`는 계약 의무를 ID별로 처분한다. 실제 근거가 요구를 충족하면 `fulfilled`, 근거를 읽고 남은 일을 확인했으면 `open`이다. `waived`는 해당 의무를 면제할 현재 `authority_ref`, `transferred`는 같은 권위와 정확한 `target_task_id`·`target_obligation_id`가 있어야 한다. 네 종류 모두 실제 근거 기록의 ID를 `evidence_refs`에 기록한다. 산출 파일을 근거로 삼으면 그 내용을 읽고 생산 실행 ID를 인용하며, 파일 경로와 확인 위치는 판정 설명에 적는다. 필요한 자료를 현재 권한·환경에서 확보할 수 없어 판정하지 못한 의무는 `unresolved`에만 기록한다. 그 항목에는 `obligation_id`, `missing_inputs`, `next_owner`를 쓰고, 실제 읽기 실패와 재개 조건은 `reason`에 설명한다. 같은 의무를 `item_dispositions`와 `unresolved`에 중복하지 않는다.

`evidence_requirements`가 있으면 증거의 종류·범위를 실제 원문과 의미로 대조한다. `evidence_required`는 반드시 인용할 기존 참조 목록이며 `evidence_refs`에 포함해야 한다. 계획자는 요구 문장을 근거 ID로 복사하지 않는다.

완료 집계와 전문 판정을 구별한다. `judges`가 `formal_check` 또는 `identity_review`이면 해당 과제에서 나온 결과의 현재 유효한 FR 또는 IA ID를 `evidence_refs`에 넣고, 그 판정이 의무의 대상·범위를 충족하는 이유를 설명한다. `goal_audit` 의무는 해당 과제의 결과를 실제 근거로 쓴 현재 `satisfied` 목표 감사 기록을 인용한다. 실행기는 판정의 종류·값·현재 효력과 이 과제 결과에 대한 연결을 검사한다. 다른 과제의 판정, RC 계보 ID나 계획자의 자기 선언은 전문 판정을 대신하지 않는다. 필수 판정이 없으면 완료로 집계하지 않는다.

현재 스키마의 완료 판정은 다음 뜻으로 사용한다.

- `completed`는 모든 완료 의무가 근거 있는 `fulfilled` 또는 권위가 확인된 적격 `waived`일 때만 사용한다. 열린 의무나 미해결 입력이 없어야 한다.
- `incomplete`는 수행 결과는 돌아왔지만 하나 이상의 계약 의무가 `open`이거나 판정 근거가 부족할 때 사용한다. 남은 의무, 재사용할 부분 결과와 다음 수행 또는 계약 정련이 필요한 이유를 `reason`과 `unresolved`에 적는다.
- `closed`는 계속하지 않을 권위 있는 범위 처분이 현재 과제에 이미 있을 때만 사용한다. 남은 의무를 이전하는 경우에는 정확한 수신 과제·의무에 그 책임을 보존하며, `transferred`를 원 과제의 이행이나 `completed` 근거로 쓰지 않는다. 단순 실패, 사용자 답변 대기, 낮은 기대나 계획자의 선호는 과제를 닫는 근거가 아니다.

긍정 결과가 없거나 한 방법이 실패했어도 계약이 요구한 탐색 범위와 검증을 실제로 끝냈다면 해당 완료 기준은 충족될 수 있다. 반대로 유용한 부분 정리나 파일이 있어도 필수 기준이 남으면 `completed`가 아니다. 결과의 유용성과 과제 완료를 구별한다.

완료 판정을 쓸 때는 기존 기대와 실제 결과가 어떻게 달랐는지, 그 차이가 다음 질문이나 선택을 어떻게 바꾸는지 함께 판단한다. 재사용할 수 있는 부분 결과는 정확한 ID·조건·효력과 남은 차이를 `reason`, `summary`와 `used_sources`에 남긴다. 계약 자체가 현실과 맞지 않아 개정이 필요하면 `incomplete`로 남은 의무를 보존하고 `revision_requests`에 해당 기록 ID와 개정 이유를 적는다. 실제 결과가 닫은 의무와 남긴 의무를 연결한다. 경쟁하는 충분조건·접근이 기존 과제를 대체할 수 있는지는 근거로 판단하고, 불필요해진 AI 과제는 기존 철회 경로로 처분한다.

## 배정 후보를 비교하고 처분한다

현재 CLI의 `dispositions`는 `ready` 과제 전건을 정확히 한 번씩 처분하는 출력이다. 각 항목은 `task_id`와 `kind`, `reason`, `uncertainty`, `parallel_task_ids`, `expected_research_change`, `revisit`, `missing_inputs`, `next_owner`를 모두 가진다. 같은 ID를 두 번 쓰거나 모집단에서 빼지 않는다.

- `selected`는 이번 계획이 수행을 요청할 과제다. `reason`에는 선택 근거를, `parallel_task_ids`에는 의도적으로 병행할 과제를, `expected_research_change`에는 결과가 바꿀 연구 상태를 쓴다.
- `not_selected`는 판단은 가능하지만 지금 선택하지 않은 과제다. 전략적 보류 이유와 다시 볼 사건·시각을 `revisit.event_refs`·`revisit.at`에 쓴다.
- `not_assessable`은 필수 원문이나 의미 판단의 근거가 없어 선택 여부를 판단할 수 없는 과제다. `missing_inputs`와 `next_owner`를 비워 두지 않고, 이를 전략적 보류나 부적합으로 바꾸지 않는다.

모든 종류에서 불확실성이 없으면 `uncertainty`는 빈 문자열을 쓸 수 있지만, 확인하지 않은 사실을 확실하다고 만들지 않는다. 재검토 사건이나 시각이 없으면 각각 빈 배열과 `null`을 쓴다.

후보를 비교할 때는 다음 관계를 함께 본다.

- 현재 연구 목표와 부분 성과에 어느 과제가 실제로 기여하는가
- 기존 지식을 어떤 조건에서 재사용하며 아직 어떤 차이가 남는가
- 새 결과가 줄일 불확실성과 얻을 정보의 가치가 무엇인가
- 이전 시도와 무엇이 다르고 같은 실패를 반복하지 않을 근거가 있는가
- 과제들이 중복되는지, 서로 보완하는지, 선행 결과에 의존하는지, 독립 비교가 유용한지
- 오래 보류된 과제가 근거 없이 계속 밀리고 있는지
- 현재 작업 예산과 이미 진행 중인 연구를 고려할 때 어떤 순서가 후속 판단을 가장 잘 여는가

수학적 직감이나 탐색 가치도 선택 근거가 될 수 있지만 확인된 증거와 구별해 적는다. 후보 수만큼 용량을 채우거나 고정 점수 순으로 선택할 의무는 없다. 아무 과제도 선택하지 않는 판단도 가능하지만, 이 경우에는 각 후보의 보류 이유와 다시 볼 사건이나 입력을 남겨 같은 입력의 빈 계획을 즉시 반복하지 않게 한다.

`dispositions`의 `selected` 항목은 배정을 원하는 우선순위대로 배열한다. 실행기는 그 순서로 새 연구 수행 요청을 queue에 넣고, 현재 착수 조건과 자원이 허용하는 앞 요청부터 배정한다. 앞 요청이 자원을 기다리면 독립된 자원을 쓰는 뒤 요청이 먼저 시작할 수 있으므로 배열 순서가 실제 시작·종료 순서를 보장하지는 않는다. `selected` 사이의 병행 의도는 `parallel_task_ids`로 명시하고, 실제 동시 실행 수는 프로필·모델별 작업 슬롯을 따른다. 세션 예산에서는 「모델과 실행예산」에 따라 선택한 과제마다 난이도·중요도와 근거를 `model_assessments` 확장으로 정확히 하나씩 반환한다. 기존 평가를 유지할 때도 그 평가를 명시적으로 반환한다. 선택 ID 집합과 평가 대상 집합의 일치·중복 부재를 제출 전에 스스로 확인하고 완전한 JSON 최종 응답을 반환한다. 로컬 검사와 preview는 선택적 진단이며 중앙 접수 증거가 아니다. 실행 중 결과를 먼저 봉인하려면 선택적으로 조기 제출할 수 있고, 그 반환에서 중앙 접수 여부를 확인한다. 요구 등급을 먼저 정하고 그 모델의 슬롯이 없으면 대기하도록 배정한다. 작업의 우선순위와 모델 등급을 같은 것으로 취급하지 않는다. `queued_work`의 기존 미시작 요청을 재정렬하거나 취소해야 하면 「모델과 실행예산」의 `queued_requests` 절차로 이유와 처분을 반환한다.

실행에 필요한 입력·도구·관찰 요구가 현재 지원과 맞는지도 확인한다. 모델 이름을 배정했다는 사실만으로 제공되지 않은 도구나 능력이 생기지는 않는다. 필요한 지원이 없으면 과제를 보류하고 `summary`, `questions` 또는 `preparation_requests`에 다음 소유자와 필요한 조치를 적는다.

AI가 만든 미완료 과제를 철회할 때는 `activity-extensions.json`의 `task_dispositions`를 사용한다. 이번 ready 모집단 중 철회할 과제는 주 응답에서 `not_selected`로 처분하고 확장에 철회를 제출한다. 결과 판정이 남은 과제는 실제 결과를 먼저 판정하며, 미완료 과제의 철회를 완료로 쓰지 않는다. 철회와 함께 그 과제의 미시작 요청이 제거된다. 일반적인 요청 취소나 수행 중 실행의 정지 권한까지 이 경로에서 만들지는 않는다. 적용 조건과 보존 범위는 공통 실행 문서를 따른다.

## 입력 초과로 보류된 수행을 이어간다

`input_overflow_requests`의 보류 요청을 허용 프로필로 계속할 수 있으면 `activity-extensions.json`의 `input_overflow_resolutions`에 `{action_id, profile_ref: {id, revision, sha256}, reason}`을 반환한다. `action_id`와 `profile_ref`는 같은 입력 항목과 그 항목의 `allowed_profile_refs`에서 정확히 복사한다. 요청 하나에 선택 하나만 반환하고, `reason`에는 그 프로필이 필수 입력과 기존 수행 범위에 적합한 이유를 적는다. 이 선택을 위해 보류 과제를 `dispositions`에 추가하지 않는다.

중앙은 현재 대기, 계약 판본, 허가, 허용 프로필과 모델 요구를 다시 대조한다. 수락되면 원 요청과 소유 활동을 유지하고 선택한 프로필로 새 실행을 준비한다. 프로필 선택 자체로 초과 질문이 해소되지는 않는다. 실제 재포장이 입력 한도 안에 들어가면 질문을 해소하며, 다시 초과하면 이전 실패와 새 실패를 보존한다. 이미 수락된 동일 편입의 재전송에는 기존 영수증을 사용한다.

보류: 제공된 프로필로 해결할 근거가 없으면 해당 선택을 생략하고 부족한 조건과 다음 소유자를 `summary`와 `questions`에 적는다. 과제 계약의 개정이 필요하면 후보 준비에 `revision_requests`로 돌리고, 사용자 허가나 목표를 바꿔야 하면 필요한 결정을 명시한다. 동일성 검토 자리의 프로필 교체는 이 경로의 권한에 포함되지 않는다.

## 다음 준비와 목표 감사를 요청한다

새 후보 탐색과 일반 준비는 `preparation_requests`에 적는다. 기존 과제·지식의 내용을 바꿀 필요가 있으면 `revision_requests`에 `{record_ids, reason}`을 쓴다. 같은 의무를 두 필드에 중복 제출하지 않는다. `pending_revisions`의 실행·보류·위임 대상을 확인하고 이미 배정된 의무와 새 요청의 차이를 설명한다. 개정 중인 A를 전제로 하는 B는 A의 개정과 필요한 검토가 끝난 뒤 파견되며, 계획의 선택이 즉시 프로세스 시작을 보장하지 않는다. “새 후보 필요”로 끝내지 않고, 어떤 결과나 실패 때문에 무엇을 정련해야 하는지, 재사용할 근거와 아직 필요한 입력이 무엇인지 설명한다. 계획자가 새 계약 문안을 대신 쓰지는 않는다.

현재 K와 수행 결과가 목표를 충족했을 가능성이 있으면 `goal_audit=true`로 독립 감사를 요청한다. 계획자가 직접 목표 해결을 확정하지 않는다. 정확한 부분 결과만 있거나 필요한 동일성·현재 사용 효력이 없으면 그 사실을 `summary`에 남기고 목표 감사 요청 여부를 근거에 따라 판단한다.

수학적 해결 뒤에는 현재 학술 요구에 연결된 과제만 선택한다. 각 과제의 `solution_basis`, 요구 판본, 필수 입력과 외부 효과를 대조하고 일반 과제와 같은 방식으로 완료 기준을 판정한다. 외부 거부는 원문과 현재 해결 근거를 읽고 형식 타당성, 해설 동일성, 목표 충족과 별도로 판단한다. 현재 근거가 거부를 실제로 해소하면 `activity-extensions.json`의 `academic_resolutions`에 해소한 외부 거부 기록의 정확한 `id`, `decision` 값 `resolved`, 해소를 입증하는 `evidence`와 해소 판단의 실제 근거 참조를 `evidence_refs`에 하나 이상 쓴다. 이 `id`는 입력 `external_rejections[].id`의 값이며, 외부 거부를 검토하도록 열린 계획에서는 `action.rejection_id`와 같다. 학술 요구의 `id`를 넣으면 실행기가 대상 거부를 찾지 못해 계획 결과 전체의 적용이 되돌려진다. 판단할 수 없으면 성공으로 만들지 않고 필요한 조사와 다음 소유자를 반환한다.

## 최종 산출과 다음 소비자

마지막 응답은 현재 출력 스키마를 따르는 JSON 하나다.

- `dispositions`는 모든 `ready` 과제를 `selected`, `not_selected`, `not_assessable` 중 하나로 처분하고, 병행 관계·기대 변화·불확실성·재검토 조건·누락 입력·다음 소유자를 담는다.
- `preparation_requests`는 후보 준비가 새로 찾거나 정련할 질문을 담는다.
- `goal_audit`는 현재 근거가 독립 목표 감사를 열어야 하는지 나타낸다.
- `task_assessments`는 실제 결과를 반환한 과제의 상태와 의무별 처분, 미해결 입력·다음 소유자를 담는다.
- `summary`는 비교한 목표·후보·근거 범위, 선택의 이유와 불확실성, 이전 기대와 실제 결과의 차이, 보류와 재검토 조건을 설명한다.
- `used_sources`는 실제 판단에 사용한 정확한 기록 ID와 참조만 담는다.
- `questions`는 현재 권한과 자료로 정할 수 없고 답에 따라 선택이나 후속이 실제로 바뀌는 질문을 담는다.

실행기는 이 결과를 적용하기 전에 ID, `ready` 모집단 전건 처분과 현재 과제 상태를 다시 검사한다. 연구 계획은 입력을 고정했을 때의 판단이므로, 적용 전에 계약·입력·허가가 바뀌어 결과가 거부되면 실행기가 대신 다른 과제를 선택하도록 만들지 않는다. 달라진 전제를 다음 계획의 입력으로 돌려 새로 판단한다.

## 입력 부족, 출력 수리와 중단

원자료나 `source_ref`를 읽지 못하면 어느 파일과 범위를 확인하지 못했는지 `summary`와 `questions`에 적는다. 그래도 현재 스키마가 요구하는 `ready` 과제 전건은 `dispositions`에 한 번씩 나타나야 한다. 판단할 수 없는 과제는 `not_assessable`로 두고 누락 입력과 다음 소유자, 다시 볼 조건을 명시한다.

과제 결과의 필수 파일은 먼저 회수해 읽는다. 현재 권한·환경에서 읽기 실패를 해소할 수 없으면 해당 의무를 `unresolved`에만 두고 누락 입력과 다음 소유자를 남기며, 과제는 `incomplete`로 판정한다. 읽은 결과에서 미이행을 확인한 의무는 `open`이다. 실행 자체의 미완료를 연구 내용의 부정 결과로 바꾸지 않는다.

수신 검사에서 ID 중복, `ready` 과제 누락, 수행 전 과제의 완료 판정이나 완료 기준 문자열의 불일치가 반환되면 정확한 오류와 원 출력을 대조해 같은 계획을 형식에 맞게 수리한다. 오류를 피하려고 후보를 빼거나 완료 기준의 뜻을 바꾸지 않는다. 입력 전제나 의미 판단이 바뀌어야 하면 단순 수리가 아니라 새 계획으로 처리한다.

모집단 오류의 `missing`, `unexpected`, `duplicate`, `ready_task_ids`를 현재 입력과 대조한다. 과거 실패 출력은 오류를 조사할 자료이며 현재 상태의 근거가 아니다. 진단 뒤 새로 열린 계획의 `failure_diagnosis`는 바꿔야 할 판단을 설명한다. 이전 선택·보류 목록을 출발값으로 복사하지 않고 현재 모집단에서 다시 계산한다. `blocked_actions`에 실행 구성이나 저장 결함이 남아 있으면 후보의 문구 수정과 구별해 운영 담당에게 필요한 수리를 명시한다.

정지 요청을 받으면 새 후보 탐색이나 추가 원자료 조회를 시작하지 않고, 현재까지 비교한 후보·근거·미완료 판정과 바로 이어갈 위치를 공통 실행 문서에 따라 체크포인트에 남긴다.

## 적용 예

### 관련 있지만 같은 역할을 하는 두 과제가 있는 경우

배정 후보 A와 B가 같은 보조정리를 서로 다른 방법으로 탐구한다고 하자. A는 기존 K를 직접 적용할 수 있고 B는 독립적인 반례 탐색으로 A의 가정을 시험한다. 두 결과를 비교할 정보 가치가 충분하면 둘 다 `selected`로 처분하고 서로를 `parallel_task_ids`에 적어 의도한 병행을 드러낸다. 현재 자원과 선행관계 때문에 하나만 먼저 해야 한다면 다른 하나를 `not_selected`로 두고, 앞 결과가 도착하면 다시 볼 사건을 적는다.

### 결과 없음이 완료일 수 있는 경우

과제가 크기 20 이하의 반례를 완전 탐색하고 탐색 코드·입력·결과를 보존하라고 했는데 반례를 찾지 못했다고 하자. 실제 파일을 읽어 범위와 재현 근거가 완결됐음을 확인했다면 “반례 없음”이라는 긍정 정리가 없더라도 해당 완료 기준은 충족될 수 있다. 반대로 코드가 존재하지만 일부 범위만 실행했다면 부분 결과가 유용해도 `incomplete`다.

### `ready`이지만 이번 계획에서 판단할 수 없는 경우

과제 ID는 `ready` 모집단에 있지만 재사용할 K의 상세가 `source_ref`에 있고 그 파일을 읽지 못했다고 하자. 이 ID를 출력에서 빼면 전건 처분이 깨진다. `not_assessable`로 처분하고, 원문 참조를 `missing_inputs`에, 원문을 제공하거나 복구할 담당을 `next_owner`에 쓰며, 다시 볼 사건을 `revisit`에 적는다. 이를 전략적 보류나 수학적 부적합으로 설명하지 않는다.

### 목표 해결 가능성이 보이는 경우

연구 수행이 형식 결과 후보를 제출했고 형식 검사와 동일성 검토까지 현재 사용 가능한 상태로 돌아왔다고 하자. 계획자는 그 결과가 목표와 비슷해 보인다는 이유로 해결을 기록하지 않는다. 현재 목표의 범위와 결과의 적용 범위를 대조해 독립 감사가 필요하다고 판단하면 `goal_audit=true`를 반환하고, 남은 차이가 있으면 그 차이를 `summary`와 준비 요청에 남긴다.

목표 감사 기록 `goal_judgments`는 과거 집단도 보존한다. 현재 해결 보증은 `goal_assessment_basis`의 집단만 사용한다. 이력의 `current`는 기록 당시의 표시이며, 전문 판정의 재사용은 현행 통치·원자료·근거 검사를 통과해야 한다. 완결됐지만 해결을 입증하지 못한 집단은 `goal_audit_completed` 사건으로 다음 계획에 전달된다. 같은 basis의 봉인 슬롯을 재요청해도 새 감사는 실행되지 않는다.
