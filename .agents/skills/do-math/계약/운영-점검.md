# 운영 점검

## 이 역할이 맡는 판단

운영 점검은 한 실행이나 활동의 실제 상태, 연구 진전의 근거와 복구 필요를 대조해 다음 운영 처분을 제안한다. 실행이 오래 걸렸거나 관찰 규칙이 도래했다는 사실만으로 실패·무진전·중단을 확정하지 않는다. 반대로 프로세스가 살아 있거나 파일이 늘었다는 사실만으로 정상 진전을 선언하지 않는다. 작업 계약의 진전 기준, 체크포인트·관찰·프로세스·권한·도구 상태와 실제 산출을 함께 읽는다.

이 역할은 수학 명제의 진위, 형식 타당성, 해설 동일성이나 목표 충족의 새 전문 판정을 만들지 않는다. 과제 처분을 맡으면 계약이 지정한 판정과 실제 근거를 집계하며, 지정 판정자의 미확보 결론을 대신 발명하지 않는다. 작업 계약을 직접 고치거나 새 사용자 허가를 만들지도 않는다. 계약 개정이나 사용자 결정이 필요하면 그 판단을 소유한 역할에 근거와 효과를 넘긴다.

## 시작 전에 실제 대상을 확인한다

상태 검사 결과를 읽을 때 저장 수신 검사와 영역별 점검을 구별한다. 적재 시 기록의 형식·참조와 staged 검토의 전이·입력 결속, 위임의 고정 참조·판정 출처, impact 대기의 원요청·배정 입력을 검사한다. 영역별 점검은 그 뒤에도 남을 수 있는 복수 활성 신뢰 환경, 종료 과제의 미종료 실행, 이전 의무의 수신 대상 부재를 별도로 보고한다. 근거는 `scripts/do_math/record_schemas/__init__.py:validate_semantics`와 `scripts/do_math/state_checks.py:inspect_state`·`_inspect_area`다.

`completed` 상태도 현재 학술 요구와 외부 영수증·반려 해소 근거가 완결됐는지 점검한다. 보존 artifact의 읽기 수단이 없으면 해당 범위를 `incomplete`로 남기며, 근거를 읽은 뒤 요구가 미완료이면 `blocked`로 보고한다. 이를 수학 명제의 진위나 실제 원격 실행 종료를 입증하는 결과로 확대하지 않는다.

`SKILL.md`의 읽기 대응표가 배정한 공통 문서와 이번 출력 스키마를 먼저 읽는다. `action.target`과 `execution_to_review`가 같은 실행을 가리키는지, 실행의 역할·원래 action·상태·종료 결과·오류·입력 판본·허가·프로필·산출과 사용량이 무엇인지 확인한다. 실행 중 관찰 점검인지, 끝난 불완전 실행의 진단인지도 원장과 프로세스 사실로 구별한다.

`observation`은 점검을 연 신호이지 결론이 아니다. 도래한 자기 점검 의무, 발동 이유, 실행 시작 뒤 경과 시간, 진행 중 도구, 최근 메시지, 체크포인트의 실제 값과 소비된 경계를 읽는다. 없는 신호를 0이나 정상으로 간주하지 않는다. 자기 점검 의무의 발생·응답과 호출별 무응답의 판정 규칙은 「자기 점검」 문서가 정한다. 작업자가 큰 도구를 시작했다는 기록은 결과 수신이 아니므로, 완료 호출 ID·실제 반환·그 내용을 읽은 체크포인트를 구별한다.

실행 중 점검과 종료 후 진단 모두 `operational_evidence`를 받는다. `operational_evidence.checkpoint_status`가 `preserved`이면 `operational_evidence.checkpoint_source.local_path`에서 고정 입력 snapshot의 최신 체크포인트를 읽고, `operational_evidence.checkpoint_files[].local_path`에서 함께 보존한 근거 바이트를 읽는다. `operational_evidence.checkpoint_evidence_omitted`는 크기 상한·읽기 실패 등으로 보존하지 못한 범위다. `not_preserved`이면 `operational_evidence.checkpoint_source`는 null이다. 보존 부재와 근거 파일 미수집을 진전 없음으로 바꾸지 않는다. 다른 실행의 live 작업 공간을 직접 읽어 빈칸을 채우지 않는다.

직접 지급된 `operational_evidence.checkpoint`는 정체성·관측 시각·상태의 메타데이터다. 보존된 본문은 크기와 관계없이 `operational_evidence.checkpoint_source`의 정확한 파일에서 읽는다. 큰 체크포인트를 프롬프트에 중복 삽입해 운영 점검 자체의 입력 한도를 소진하지 않는다.

`execution_to_review.observation_stream`이 있으면 stream 수신 시각·중앙 적용 시각과 `local_termination_confirmed`를 원장의 실행 상태와 함께 읽는다. 지연된 로그의 적용 시각은 원 행동의 발생 시각이 아니다. 로컬 종료 확인은 제출 수락이나 원격 공급자 정산을 뜻하지 않는다.

종료 뒤 진단에서 대상 실행에 artifact 묶음이 있으면 `recovery_materials`를 받는다. `recovery_materials.execution_id`와 `recovery_materials.source_snapshot`을 확인한다. 실행 중 점검(`live_review`)에는 이 복구 입력이 없다. `recovery_materials.result_kind`의 `execution_result`는 정상 결과 경로, `checkpoint_recovery`와 `activity_result`는 각각 복구 체크포인트와 별도 활동 결과를 뜻한다. `recovery_materials.final_result_status`가 `available`이어도 정상 결과 경로를 선택했다는 뜻이며 복원 성공이나 수학적 성공을 보증하지 않는다.

복원에 성공하여 `local_path`가 있는 자료만 읽는다. 정상 결과는 `recovery_materials.result_source.local_path`, 복구 체크포인트는 `recovery_materials.checkpoint_source.local_path`, 부분 출력은 `recovery_materials.output_files[].local_path`에서 읽는다. 정상 formal/인라인 자식 실행에 복구 체크포인트가 없으면 `recovery_materials.checkpoint_source`는 null이며 읽을 파일도 없다. 같은 원 artifact·snapshot을 결과와 체크포인트 두 건으로 세지 않는다. 해시·크기·경로는 원문 정체성의 근거이지 성공의 근거가 아니다.

복원 실패는 `recovery_materials.result_source.restoration_error`, `recovery_materials.checkpoint_source.restoration_error` 또는 `recovery_materials.output_files[].restoration_error`에 나타난다. 해당 자료의 원 artifact·snapshot·기대 해시·크기와 오류 종류·사유, 읽은 경우의 실제 해시·크기를 진단 근거로 사용한다. 이 자료에는 `local_path`가 없으므로 없는 경로를 읽지 않는다. 검증되지 않은 바이트를 수학적 산출의 수락 근거로 쓰지 않으며 다른 실행의 live 공간으로 복구 공백을 채우지 않는다.

계약, 체크포인트, 프로세스 상태나 외부 효과 근거가 없으면 기억이나 다른 실행의 상태로 채우지 않는다. 확인한 사실과 결정할 수 없는 처분을 나누고, 부족한 입력과 다음 소유자를 반환한다.

## 진전·실패·복구를 대조한다

먼저 점검을 연 사건이 작업자의 `blocked`·`no_progress`, 자기 점검 경계, 도구 완료·timeout, 주기 점검 도래, 입력·허가 변화, 프로세스 실패 또는 출력 검사 실패 가운데 무엇인지 찾는다. 중복 관찰이나 이미 소비한 경계를 새 무진전 횟수로 세지 않는다.

체크포인트의 `current_claim`은 실제 `evidence_paths`와 계약의 `progress_criteria`가 요구한 증거에 대조한다. 시간, 반복 수, 파일 수와 자기평가는 점검 시점을 만들 수 있지만 연구 진전 자체는 아니다. 관계가 바뀌었다는 주장은 정확한 양끝 판본과 근거를 확인한다. 아직 확인하지 못한 연결을 확정 관계로 받아들이지 않고 미확인 범위와 다음 확인 행동을 보존한다.

실행 상태와 연구 결과를 분리한다. 실패한 실행에도 재사용할 체크포인트가 있을 수 있고, 정상 종료한 실행에도 계약 의무를 충족하는 결과가 없을 수 있다. 운영 점검은 실제 보존 범위와 복구 가능성을 다음 의미 판정에 넘긴다.

입력 부재, 권한 소멸, 도구·환경 실패, 출력 스키마 오류, 계약 부적합, 프로세스 소실과 외부 서비스 상태를 구별한다. 재개나 재시도를 제안하려면 이전 실행의 종료, 사용할 체크포인트, 이미 완료한 범위, 달라진 입력·환경, 외부 효과의 재생 안전성과 현재 권한을 확인한다. 상태가 `unknown`인 외부 행동은 실패로 간주해 반복하지 않는다.

## `disposition`을 작성한다

마지막 응답은 현재 출력 스키마를 따르는 JSON 하나이며, `decision`이 아니라 `disposition` 객체를 반환한다. 모든 처분은 하나 이상의 `basis_refs`, 구체적인 `reason`, 실제 `next_owner`를 가진다. 처분 종류는 다음 여섯 가지다.

`basis_refs`는 입력의 `admissible_basis_refs`에 있는 정확한 canonical 참조만 사용한다. 과제·허가·catalog 경로를 읽었다는 사실만으로 그 문자열이 처분 근거가 되지는 않는다. 읽은 출처는 `used_sources`에, 운영 처분은 지급된 대상 실행·관찰·의무·불변 결과·체크포인트 참조에 결박한다. `admissible_basis_refs`의 모든 원소는 지급된 참조이므로 제출 검사를 통과하고 `reference_catalog`에도 나타난다. 제출 검사는 입력의 허용 목록으로 `basis_refs`를 검사한다. 적용 검사는 적용 시점의 최신 checkpoint·결과·권한으로 허용 목록을 다시 계산해 같은 규칙으로 검사한다. 입력에서 허용됐던 참조가 그 사이 새 checkpoint나 결과로 바뀌었고 처분에 다른 오류가 없으면, 그 반환은 전제 변경(`currentness_changed`)이다. 이 반환은 출력 수리 횟수를 쓰지 않고, `action.refresh`의 변경표를 받는 같은 역할의 갱신으로 한 번 이어진다. 입력에 없던 참조를 인용했거나 다른 오류가 함께 났으면 생산자 반려다. 이때는 반려 오류의 `invalid_basis_refs`와 허용 목록을 읽고 참조를 고친다.

### `continue`

현재 계약·환경·권한이 유지되고 실행을 계속할 구체적인 근거가 있을 때 사용한다. `next_review`는 다음 점검이 필요하면 `{at, reason}`, 필요 없으면 `null`이다. 계속은 수학적 성공이나 과제 완료가 아니다.

### `repair`

설치된 문서·검사기·실행기 결함 때문에 현재 의무를 처리할 수 없다는 근거를 확인했으면 `repair`로 설치 수리를 요청한다. `repair_target`은 `installation:<스킬 폴더 안의 실제 상대 파일 경로>`, `meaning_preserving`은 `true`, `next_owner`는 `installation_recovery`다. `reason`에는 원 산출·계약·오류의 충돌을, `verification`에는 그 실패의 재현과 수정 뒤 확인할 동작을 적는다. `basis_refs`는 제공된 실패 실행·산출의 실제 참조를 사용한다. 단순 반려 횟수만으로 설치 결함을 선언하지 않는다. 사용자의 목표·필수조건·과제 범위를 바꿔야 하면 의미 보존 수리로 부르지 않는다.

설치 수리는 이 운영 응답이 수락되고 진단 실행까지 종료된 뒤 요청된다. 엔진은 새 실행 배정을 멈추고 진행 중 실행을 회수한 뒤 잠금을 반환한다. 예약 감독은 보존된 진단·실패 산출을 기존 설치 복구 AI에 제공한다. `installation_repair_pending`이나 `installation_repair_waiting`은 수리 완료가 아니다. 수리 담당의 실제 검사 근거와 설치 검사를 확인한 뒤 원래 반환 산출을 잇는 실행을 열며, 사용자 정지와 HOLD를 해제하지 않는다.

이 경로에서 지원하지 않는 환경 변경·새 도구 설치·연구 의미 변경은 그 작업의 권한과 실제 다음 소유자에게 돌린다. `verification`의 설명문은 기계가 실행할 셸 코드가 아니며, 설치 복구 AI가 실제 실패와 관련 검사를 수행할 기준이다.

무인 수리는 사용자가 이미 승인한 연구를 기존 의미와 권한 안에서 복구하려는 절차다. 승인받지 않은 외부 효과, 목표·정책·허가 변경을 만들지 않는다. 작업 공간과 역할 지침이 행동 경계를 제공하더라도 이를 호스트 파일·네트워크·크리덴셜을 차단하는 OS 강제 격리라고 표현하지 않는다.

### `resume`

유효한 체크포인트에서 남은 범위만 잇는 새 실행이 적합할 때 사용한다. `checkpoint_ref`에는 실제 보존된 체크포인트를, `scope`에는 이미 끝난 부분과 재개할 부분의 경계를 쓴다. 끝난 실행을 되살리거나 체크포인트 뒤에 바뀐 전제를 무시하지 않는다.

### `retry`

체크포인트 재개가 아니라 실패한 범위를 안전하게 다시 수행해야 하고 결과가 달라질 근거가 있을 때 사용한다. `scope`에는 재실행 범위를, `replay_safety`에는 외부 효과·멱등성·현재 권한과 중복 실행 위험을 대조한 근거를 쓴다. 같은 입력과 환경으로 실패를 반복하거나 상태 불명의 외부 행동을 재전송하지 않는다.

종료된 실행의 로컬 입력 사본만 손상됐고 Git에 봉인된 원문은 온전하면 `retry`를 사용한다. 중앙은 봉인 자료를 확인한 뒤 같은 활동의 후속 요청을 만들고, 다음 실행에 새 작업 공간과 입력을 지급한다. 옛 디스크 사본의 복원은 재시도 조건이 아니다. `scope`와 `replay_safety`에는 이미 편입된 묶음·완료된 외부 효과와 남은 의무를 구별해 적는다. 봉인 원문 자체가 없거나 손상됐으면 자료 보존 문제를 먼저 해소해야 한다.

새 후속 요청과 운영 처분의 적용 기록은 같은 Git 갱신으로 보존되며, 같은 처분의 재처리는 후속을 중복 생성하지 않는다. 입력 손상은 위의 `retry` 계약으로 처리하고, `repair`는 설치 결함에 사용한다.

### `task_disposition`

운영 근거와 현재 권위가 과제의 상태 처분을 직접 요구할 때만 사용한다. `task_id`와 `task_state`(`completed`, `incomplete`, `closed`)를 쓰고, 같은 응답의 `task_assessments`에 그 과제의 판정 하나를 넣는다. 판정의 `task_id`와 `decision`은 처분의 `task_id`·`task_state`와 같아야 한다. 판정은 계약의 완료 의무마다 `item_dispositions`에 `fulfilled`, `open`, `waived`, `transferred` 가운데 하나를 쓰고, 필요한 자료가 없어 판정하지 못한 의무만 `unresolved`에 `obligation_id`·`missing_inputs`·`next_owner`로 남긴다. `completed`와 `closed`에는 `open`이나 `unresolved`가 남지 않아야 한다. `fulfilled`에는 그 의무의 `evidence_required`를 모두 `evidence_refs`에 넣으며, 의무의 `judges`에 운영 점검이 없으면 지정 판정자의 현재 판정을 함께 인용한다. `waived`와 `transferred`의 `authority_ref`에는 그 과제·의무를 지정한 현재 사용자 `task_scope` 결정의 ID를 쓰고, `transferred`에는 수신 과제 `target_task_id`와 새 의무 ID `target_obligation_id`도 쓴다. 운영자의 선호나 실행 종료만으로 완료·닫힘을 만들지 않고, 계약의 완료 의무와 지정 판정자의 책임을 우회하지 않는다.

### `user_decision`

목표·정책·허가·위험 수용처럼 연구 책임자만 정할 수 있는 선택이 결과를 바꿀 때 사용한다. `question`은 한 가지 결정을 명확히 묻고, `effect`에는 각 답이 실행·과제·외부 행동에 미칠 차이를 쓴다. 환경과 원자료에서 확인할 수 있는 사실을 사용자에게 되묻지 않는다.

## 실패 유형별 판단

`blocked_actions`에는 대상 실행 자신의 해소 가능한 실패와 함께, 같은 대상을 점검하다 출력 수리나 갱신을 소진한 이전 운영 점검의 대기도 들어 있다. 이번 처분이 그 점검의 판단을 실제로 대신하면 공통 실행의 `action_resolutions`로 해소한다. 실행 중 점검과 종료 뒤 진단처럼 판단 범위가 다른 대기는 해소할 수 없다.

`output_parse`·`output_schema`·`output_contract`·`input_failure`는 각각 파싱·출력 스키마·계약 수신·제출 파일 읽기 실패다. 주 응답·확장·편입 묶음의 정확한 문제를 읽고 의미 보존 수리 가능성을 판단한다. 대기 행동의 `kind=output_validation`은 생산자 수리 한도를 넘긴 수신 반려의 대기 표지다. 실제 실패 분류는 대상 실행의 `error_kind`와 상세 검사 근거에서 읽는다. 이미 수락된 묶음을 바꾸거나 재소유하지 않고 반환된 묶음만 수리한다. `currentness_changed`이면 변경표와 실제 읽기 의존을 대조한다. `publication_failure`는 중앙의 저장 재대조 대상이며 작업자의 의미 오류로 처리하지 않는다. 공급자 한도는 허용 시각과 원 실패를 보존하며 같은 제한을 확인하려고 새 모델 진단을 반복하지 않는다. scholarly 자료원의 429를 모델 공급자 한도로 바꾸지 않는다.

입력의 `repetition_holds`에서 대상 계보의 현행 반복 한도 보류를 확인한다. 이 보류는 사용자 계속 승인이 필요하며 기술 수리 처분만으로 해제할 수 없다. 기술적 복구를 위한 `retry`·`resume`을 제안하면 중앙은 수락된 처분과 종료된 대상 실행을 확인하고 같은 의무의 후속 요청을 연결한다. 체크포인트로 재개할 때에는 보존 참조와 원문 바이트도 대조한다. 같은 처분의 재처리는 이미 연결한 후속을 반환하며 요청을 중복 생성하지 않는다. 반복 한도 보류가 남으면 후속 요청도 착수를 기다린다. 기술 수리 처분을 수락했다는 이유로 누적 실패를 지우지 않는다.

프로세스 시작 실패·중첩·PID 재사용 의심·제어 무응답은 실제 자식 프로세스와 원장·Job 영수증의 범위에서 판단한다. PID 값만 같다는 이유로 같은 실행이라고 보거나, 부모 하나의 종료로 자손 종료를 확정하지 않는다. 현재 Windows Job이 입증하는 로컬 프로세스 수명과 자손 종료를 모든 호스트 자원 격리로 확대하지 않는다.

## 최종 산출과 중단

`summary`에는 점검 발동 이유, 실제로 읽은 원자료, 현재 실행 상태와 핵심 처분을 요약한다. `used_sources`에는 사용한 실행·활동·과제·체크포인트·산출·외부 행동의 정확한 참조만 적는다. `questions`에는 답에 따라 처분이 바뀌는 열린 질문만 적는다. 기존 기록의 개정이나 부분 편입 재시도가 없는 일반 운영 점검 응답은 `integration_bundles`를 생략할 수 있으며, 실행기가 주 응답과 허용된 확장 전건을 하나의 판단 묶음으로 구성한다.

필수 원자료가 없으면 가장 그럴듯한 원인을 확정하거나 근거 없는 `resume`·`retry`를 선택하지 않는다. 필요한 자료·다음 소유자와 사용자 결정 여부를 구별한다. 운영 점검 실행 자체가 실패하거나 정지 요청을 받으면 확인한 범위, 미확인 범위와 재개 좌표를 체크포인트에 보존하고 이를 `continue`로 바꾸지 않는다.

수신 검사가 형식 오류를 반환하면 정확한 오류와 원 출력을 대조해 같은 의미로 수리한다. 처분의 종류를 바꿔야만 오류를 피할 수 있다면 단순 형식 수리가 아니라 근거를 다시 판단한다.

## 후속 실행이 이미 있는 실패의 처분

운영 입력의 `operational_evidence.activity_continuations`에서 원 실패 실행의 명시적 `continuation_of` 후속, 현재 상태와 보존 결과를 확인한다. retry·resume을 제안할 때 이미 후속이 해당 의무를 이어받았으면 같은 재시도를 중복 생성하지 않는다. 기계 실행기는 적용 직전에도 이 관계를 대조하고 중복되는 retry·resume 처분을 `superseded`로 보존한다. 이는 원 실패 기록의 삭제나 수학 의무 완료 판정이 아니다.

설치 결함에 대한 repair는 과제 재시도와 별도의 의무다. 후속 실행의 존재나 성공만으로 그 결함을 해소하지 않는다. 현재 설치와 실패 근거를 대조해 필요한 수리를 판단한다. 설치 수리를 완료한 뒤에도 기존 후속이 있으면 그 후속을 유지하고 과거 실행의 재시도를 새로 만들지 않는다.

## 질문 배정과 주기 점검을 구별한다

`action.stage=question`이면 실제 `execution_to_review`에 관한 운영 처분과 함께 배정 QU 전건을 공통 실행의 `question_resolutions`로 처리한다. 같은 EX에 대한 주기 점검은 별도 목적이므로 질문 처리와 합쳐서 소진하지 않는다. 설치 결함이면 실제 `repair` 처분을 만들고 질문은 그 OD의 수리 영수증을 기다리게 한다. 수락된 진단·담당 실행의 실제 종료·정비 fence·복구 검사·사용자 정지의 기존 경계는 유지한다. 과제·프로필·자료만 조사하는 질문은 maintenance 담당이 조사하며 모든 지원 질문을 EX 처분으로 바꾸지 않는다.
