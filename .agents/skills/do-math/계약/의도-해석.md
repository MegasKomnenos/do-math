# 의도 해석

## 이 역할이 맡는 판단

의도 해석은 보존된 사용자 원문이 현재 연구에서 무엇을 뜻하고 어떤 기록이나 권한에 영향을 주는지 확인하는 활동이다. 첫 실행은 원문을 의미 단위로 읽어 해석과 변경 제안을 작성하고, 두 번째 독립 실행은 그 해석이 원문의 목표·범위·조건·예외와 권한을 빠짐없이 보존하는지 대조한다.

사용자가 정보를 제공했다는 사실, 변경을 요청했다는 사실과 실행을 허가했다는 사실은 서로 다르다. 의도 해석은 원문에 있는 의미를 보존할 뿐, 사용자가 말하지 않은 목표·정책·선호나 허가를 만들지 않는다. 해석 결과가 `match`여도 수학적 타당성이나 작업 성공을 승인하는 것은 아니다.

현재 실행기는 이 역할의 변경 제안을 `goal`, `policy`, `none`으로 제한한다. 연구 맥락·설정·F·자료·근거·연구 기억, 학술 요구나 허가처럼 다른 소유자가 맡는 의미를 목표나 정책에 억지로 넣지 않는다. 현재 출력으로 적용할 수 없는 의미는 원문 좌표와 필요한 다음 소유자를 `interpretation`, `summary`와 `questions`에 남긴다. 현재 실행기가 그 후속을 자동으로 열어 주는지 입력과 실행 계약에서 확인하고, 지원되지 않으면 별도 구조화 수입·결정이 필요하다는 사실을 숨기지 않는다.

## 어느 단계인지 먼저 확인한다

`SKILL.md`의 읽기 대응표가 배정한 공통 문서를 먼저 읽고 이번 출력 스키마를 확인한다. 「공통 실행」의 원자료 회수·제출 전 검사·현재성·실패 반환을 적용한다. 사용자 원문이 기존 연구 지식을 언급하더라도 「지식 저작과 재사용」의 대조를 근거 확인에 적용하며, 기존 지식·관계를 개정하거나 수학적 적용을 승인하지 않는다. 이미 얻은 부수 통찰은 공통 확장으로 후보만 보존할 수 있고, 사용자가 말하지 않은 뜻이나 권한을 그 경로로 만들지 않는다.

`action.stage`가 없거나 `interpret`이면 첫 해석 단계다. 이때 주 JSON에는 `interpretation`, `proposed_changes`, `needs_clarification`과 선택 필드 `answered_questions`가 있다. `action.stage=check`이면 독립 대조 단계이고, 주 JSON에는 `decision`, `findings`, `scope_complete`와 선택 필드 `confirmed_question_ids`가 있다. 다른 단계의 필드를 섞지 않는다.

두 단계 모두 `action.target`과 `user_request.id`가 같은 보존 원문을 가리키는지 확인한다. `user_request`의 원문, 입력 시각과 출처, 현재 연구 목표·정책과 관련 문맥을 읽는다. 큰 사용자 입력이나 연결 자료가 `source_ref`로 주어지면 원문을 회수한다. 대화 요약이나 현재 연구 상태만 보고 사용자의 표현을 재구성하지 않는다.

## `interpret` 단계에서 원문을 의미 단위로 읽는다

### 1. 원문이 하는 일을 구별한다

사용자 원문에서 다음 내용을 구별한다.

- 현재 목표나 정책을 바꾸라는 명시적 요청
- 기존 결정을 설명하거나 범위를 한정하는 조건·예외
- 원자료, 사실 주장이나 연구 아이디어의 제공
- 질문, 선호나 추천 요청
- 특정 행동을 허가·철회하거나 외부 효과를 승인하는 결정

한 문장이 둘 이상의 기능을 가지면 문장 전체를 하나의 종류로 밀어 넣지 않는다. 예를 들어 “이 문헌을 읽고 목표는 그대로 유지하되 증명 뒤 재현 보고서를 작성해라”는 자료 제공, 목표 유지와 학술 요구를 각각 구별해야 한다. 같은 의미를 여러 내부 소유자에 복제하지 않고, 하나의 소유자에 두고 다른 기록은 정확한 참조로 연결한다.

확인 가능한 사실은 현재 원자료와 기록에서 직접 확인한다. 사용자가 이미 명확히 정한 값을 다시 질문하지 않는다. 반대로 여러 해석이 타당하고 선택에 따라 목표·범위·권한이나 산출이 달라지면 가장 자연스러운 뜻을 임의로 확정하지 않는다.

### 2. `interpretation`에 현재 의미와 영향을 설명한다

`interpretation`은 사용자 원문을 짧게 바꾸어 쓰는 요약이 아니다. 원문에서 확인한 각 의미 단위, 그 단위가 유지하거나 바꾸는 현재 기록, 적용 범위와 조건, 아직 미결정인 내용을 독자가 대조할 수 있게 설명한다. 중요한 표현은 원문 좌표나 정확한 입력 참조와 연결한다.

변경이 없는 정보 제공도 그 효과를 설명한다. 문헌 파일을 제공했다면 원문 보존과 연구 지식 저작이 다른 단계이며, 그 문헌의 주장이나 분류가 곧 K·F·관계 또는 정책이 되지 않는다고 밝힌다. 새 수학 해석이나 관계 저작이 필요하면 자료를 사용할 후보 준비나 연구 수행을 다음 소유자로 적는다.

### 3. 현재 지원되는 `proposed_changes`를 작성한다

현재 각 변경 항목은 `kind`, `text`, `reason`을 가진다.

- `kind=goal`은 사용자가 연구 목표의 내용·범위·성공 기준을 실제로 바꾸거나 확정한 경우에만 쓴다. `text`에는 적용할 전체 목표 문면을 넣고, `reason`에는 원문의 어떤 부분이 이 변경을 요구하는지 적는다.
- `kind=policy`는 사용자가 인스턴스 전체에 적용할 규범을 바꾸거나 확정한 경우에만 쓴다. `text`에는 적용할 전체 정책 문면을 넣고, 기존 정책과 함께 충족되는지 또는 무엇을 대체하는지 `reason`에 설명한다.
- `kind=none`은 스키마가 허용하지만, 변경이 없으면 일반적으로 빈 `proposed_changes`와 명확한 `interpretation`으로 표현한다. 다른 의미를 `none` 항목에 숨겨 실행기가 처리한 것처럼 만들지 않는다.

목표나 정책의 일부를 바꾸면 기존 문면의 유지 부분과 새 부분이 한 가지 현행 문면으로 읽혀야 한다. 원문에 없는 범위·기한·예외를 추가하지 않는다. 사용자 요청이 현재 값과 같다면 새 변경을 만들지 않고 유지된 의미와 근거를 설명한다.

HTTP 허가, 로컬 실행 허가, 학술 요구와 철회는 `goal`이나 `policy` 문장으로 대신하지 않는다. 이런 구조화 결정은 현재 사용자 결정 경로가 소유한다. 이 역할은 필요한 결정의 종류와 원문 근거를 설명할 수 있지만 허가 ID나 결정값을 만들지 않는다.

### 기존 질문에 대한 답변을 연결한다

입력의 `question_links`와 `user_request.config.responds_to`를 확인한다. 이 값은 `input --responds-to`로 지정한 질문 ID 목록이며 원 사용자 입력과 함께 보존된다. 이번 원문이 답한 열린 사용자 질문만 `answered_questions`에 ID로 제안하고 `interpretation`에서 대응 근거를 설명한다. 명시적인 responds_to가 없어도 원문과 질문을 대조해 대응을 제안할 수 있다. 무관한 질문이나 연구·운영 질문을 사용자 답으로 일괄 해소하지 않는다.

독립 `check`는 원문과 제안한 대응을 각각 대조하고 실제로 답변된 질문만 `confirmed_question_ids`에 쓴다. 확인하지 못한 ID는 넣지 않는다. `match`와 전건 대조가 수락된 뒤 실행기가 확인된 질문을 사용자 원문에 결박된 답변 결정으로 해소한다. 질문의 해소가 HTTP 허가·과제 완료·수학 승인을 대신하지는 않는다.

### 4. 사용자에게 물어야 하는지 판단한다

사용자만 정할 수 있는 중요한 의미가 비어 있고 그 답에 따라 결과가 바뀌면 `needs_clarification=true`로 한다. `questions`에는 실제 선택, 그 선택을 요구하는 원문과 문맥, 가능한 선택과 효과, 답이 바꿀 기록·권한을 설명한다. 사용자가 제시한 선택지 밖의 답을 할 가능성을 닫지 않는다.

질문을 열 때는 확정된 변경과 미결정을 섞어 적용하지 않는다. 현재 실행기는 `needs_clarification=true`이면 독립 check를 열지 않고 질문을 사용자 대기로 보존한다. 질문에 답하려고 의도 해석 실행을 살아 있게 유지하지 않는다.

현재 원문이 충분하고 현재 지원 범위의 변경을 정확히 제안할 수 있으면 `needs_clarification=false`로 한다. 지원하지 않는 변경 종류가 명확하다는 사실만으로 사용자의 뜻이 모호한 것은 아니다. 이 경우 의미는 확정해 설명하되 현재 출력으로 적용하지 말고 필요한 구조화 결정이나 저작 경로를 다음 소유자로 남긴다. 현재 실행기가 그 후속을 개설하지 않으면 `summary`에 미적용 범위로 분명히 적는다.

현재 `action`과 출력 스키마에는 사례 기반 위임의 원 결정·허가·현재 사례·제안 효과를 독립적으로 대조하는 별도 단계가 없다. 이런 입력이 실제로 제공되지 않았으면 일반 사용자 원문 해석을 사례 기반 위임 적용으로 바꾸지 않는다. 위임 적용이 필요한 경우에는 필요한 허가와 원 결정, 현재 효과와 독립 대조를 다음 소유자에게 돌린다.

## `check` 단계에서 원문과 해석 전건을 대조한다

대조 실행은 첫 해석 실행과 다른 실행이어야 한다. `user_request` 원문과 `interpretation_to_check`를 모두 읽고, 첫 실행의 결론을 맞추려 하지 않는다. 이번 역할에서 제공된 해석 묶음을 검토하는 것이므로 해석·변경 제안의 실제 문면은 보되, 작성자의 미공개 의도나 작업 문맥은 이어받지 않는다.

다음 순서로 전건을 확인한다.

1. 원문의 의미 있는 구간이 `interpretation`에서 빠지거나 중복되지 않았는지 확인한다.
2. 목표·정책 변경의 `text`가 원문의 대상·범위·조건·예외를 보존하는지 확인한다.
3. 사실 제공, 질문, 학술 요구와 허가가 목표·정책 변경으로 잘못 승격되지 않았는지 확인한다.
4. 사용자가 명시하지 않은 선호·제외 범위·권한·성공 주장이 추가되지 않았는지 확인한다.
5. 사용자 결정이 필요한 빈 의미가 질문으로 남았고, 이미 확정된 값을 불필요하게 다시 묻지 않는지 확인한다.
6. 각 변경과 미결정이 실제로 영향을 주는 과제·활동·권한과 다음 소유자의 범위가 충분한지 확인한다.

`decision=match`는 이 전건을 대조했고 해석과 지원되는 변경 제안이 원문 의미를 보존할 때만 사용한다. `scope_complete=true`이고 열린 결함이나 미해결 질문이 없어야 한다. 실행기는 이 결과가 수신되면 `goal`·`policy` 변경을 사용자 원문에 결박된 결정으로 적용하고 후보 준비를 연다.

`decision=mismatch`는 원문과 해석 사이의 구체적인 누락·중복·범위 확대·왜곡을 확인했을 때 사용한다. `findings`마다 원문 위치, 문제인 해석이나 변경 항목, 달라진 의미와 필요한 수정을 완전한 문장으로 적는다. 한 결함을 찾은 뒤에도 읽을 수 있는 나머지 범위를 계속 대조한다.

`decision=unresolved`는 필수 원문이나 문맥을 읽지 못했거나 두 해석 중 어느 것이 맞는지 현재 자료로 확정할 수 없을 때 사용한다. `findings`에는 확인한 범위, 읽지 못한 자료와 필요한 질문을 남긴다. 입력 미완료를 `mismatch`로 바꾸지 않는다.

`scope_complete`는 배정된 원문과 해석의 필수 범위를 모두 실제로 대조했을 때만 참이다. `match`인데 거짓인 결과나 열린 미결정이 있는데 참인 결과를 만들지 않는다. 현재 실행기는 `match`와 `scope_complete=true`가 함께 있어야 변경을 적용한다.

## 최종 산출과 다음 소유자

두 단계 모두 마지막 응답은 현재 출력 스키마를 따르는 JSON 하나다. `summary`에는 실제로 읽은 원문 범위, 해석 또는 대조 결과, 영향을 받는 기록과 다음 소유자를 설명한다. `used_sources`에는 사용자 요청과 실제로 대조한 현재 기록의 정확한 ID·참조를 쓴다. `questions`에는 현재 자료로 닫지 못했고 답이 결과를 바꾸는 질문만 둔다.

`interpret` 단계의 `interpretation`은 후속 독립 대조가 원문과 비교할 수 있을 만큼 충분해야 한다. `proposed_changes`는 현재 지원되는 목표·정책 변경만 담고, `needs_clarification`은 사용자 답이 먼저 필요한지를 나타낸다. `check` 단계의 `decision`, `findings`, `scope_complete`는 해석의 정확성과 대조 범위를 나타내며 사용자 허가나 수학적 승인이 아니다.

대조가 성공해 적용된 뒤에도 실행기가 실제 영향과 현재성을 확인한다. 목표가 바뀌면 미완료 과제의 계약을 다시 정련할 수 있고, 정책이 바뀌면 작업 계약 검토와 연구 계획이 다시 열린다. 의도 해석자는 그 후속 결과를 미리 선언하지 않는다.

## 입력 부족, 출력 수리와 중단

`user_request` 원문이 없거나 action의 대상과 다르면 기억으로 복원하지 않는다. `interpret` 단계에서는 `needs_clarification=true`와 구체적인 질문을 사용하고, 원문 자체를 읽지 못해 스키마에 맞는 해석도 만들 수 없으면 실행 미완료로 보존되게 한다. 확인한 일부 문장만 전체 사용자 의도로 확대하지 않는다.

`check` 단계에서 `interpretation_to_check`가 없거나 해시·대상이 다르면 `unresolved`와 실제 미대조 범위를 반환한다. 첫 해석이 불완전하다는 사실과 원 사용자 의도가 모호하다는 사실을 구별한다.

수신 검사에서 허용되지 않은 변경 종류, 판정값이나 필드 오류가 반환되면 정확한 오류와 원 출력을 대조해 수리한다. 지원되지 않는 허가나 학술 요구를 목표·정책으로 이름만 바꾸어 통과시키지 않는다. 의미를 바꿔야 하는 수리는 원문을 다시 읽고 새 해석으로 수행한다.

정지 요청을 받으면 새 문맥 조회나 추가 의미 판단을 시작하지 않고, 이미 대조한 원문 구간·해석과 미확인 범위, 다음 단계를 체크포인트에 남긴다. 실행 미완료를 사용자 거부나 변경 없음으로 바꾸지 않는다.

## 적용 예

### 명확한 목표 변경

사용자가 “기존 자연수 명제를 정수 전체로 넓혀 증명하라”고 명시했다고 하자. `interpretation`에는 대상 명제, 자연수에서 정수로 바뀐 영역과 성공 기준의 영향을 설명한다. `proposed_changes`에는 전체 현행 목표를 담은 `goal` 항목을 쓰고, 미완료 과제의 범위·입력·완료 기준을 다시 정련해야 한다고 다음 소유자를 밝힌다. 사용자가 말하지 않은 증명 방법이나 외부 공개 요구를 추가하지 않는다.

### 문헌 파일만 제공한 경우

사용자가 참고할 논문을 제공했지만 목표나 정책을 바꾸라는 말은 하지 않았다고 하자. 파일 보존은 자료 수입이고 논문의 내용은 아직 내부 지식 저작이나 수학적 승인 전이다. `proposed_changes`를 비워 두고, 어떤 생산 역할이 원문을 읽어 F·자료·근거와 관계를 저작할지 `interpretation`과 `summary`에 남긴다.

### 허가인지 정보 제공인지 모호한 경우

사용자가 외부 제출처의 주소를 알려 주었지만 “제출하라”는 승인 여부가 분명하지 않다고 하자. 주소 제공을 전송 허가로 확대하지 않는다. 어떤 자료를 어느 범위로 전송할지와 외부 효과를 설명한 질문을 만들고 `needs_clarification=true`로 한다. HTTP 허가를 정책 변경으로 제안하지 않는다.

### 독립 대조가 범위 확대를 발견한 경우

원문은 “정리 A만 다시 검토하라”고 했는데 첫 해석이 프로젝트의 모든 K를 재검토하는 정책을 제안했다고 하자. 대조자는 원문 범위와 제안 정책의 범위를 좌표로 비교해 `mismatch`를 반환한다. 정리 A의 재검토 필요 자체는 보존하고, 범위 확대만 구체적으로 수정하도록 `findings`에 남긴다.
