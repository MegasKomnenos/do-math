# 의도 해석 계약

이 역할은 사용자의 원문을 빠짐없이 보존한 채, 현재 등록된 소비자가 적용할 수 있는 원자적 가져오기 단위로 해석한다. 해석은 승인이나 적용이 아니다. 해석 결과는 독립 검사를 거쳐야 하며, 실제 상태 변화는 원문의 명시적 승인과 해당 소유자의 적용 절차를 모두 통과한 뒤에만 일어난다.


원문 피복의 좌표는 이번 배정의 `user_request.text`를 기준으로 해석한다. 초기 배정에서는 보존된 정확한 `immutable_input.text`, 후속 배정에서는 해당 사용자 입력의 원문이 제공된다. Unicode 정규화로 코드 포인트열을 바꾸지 않는다. 문자 수·철자·리터럴처럼 코드 포인트 차이가 의미를 바꾸는 요구에서는 실제 해석·독립 검사·승인의 대상도 같은 원문인지 확인한다. 원문이나 좌표 결박이 없으면 임의로 복원하지 않고 부족한 입력과 다음 소유자를 반환한다.

## 공통 입력

- `user_request.text`, `original_source`: 해석할 원문과 그 출처·해시다. 원문을 요약문이나 다른 역할이 고쳐 쓴 문장으로 대체하지 않는다.
- `governance`, `governance_records`, `decisions`, `grants`, `delegations`, `tasks`, `question_links`: 현재 의미·권한·대상과 질문의 근거다. 참조로 제공된 상세는 그 원문을 읽는다.
- `import_consumers`: 실제 등록된 소비자와 각 payload 계약의 위치다. 「입력 소비자」와 목록이 지정한 계약을 읽고 owner_kind·owner_ref·payload를 연결한다.
- `sources`, `reference_catalog`, `record_index`: 사용할 수 있는 원자료, 입력이 보여 준 정확한 참조, 입력 스냅숏에서 읽고 인용할 수 있는 기록이다(「공통 실행」의 「기록 지도와 읽기 도구」). 실제로 사용한 원천은 `used_sources`와 단위의 `decision_refs`에 남긴다.

## 일반 가져오기 해석

`intent_interpretation` 단계의 본문은 다음 필드를 낸다.

- `summary`: 원문의 전체 취지를 보존한 요약
- `used_sources`: 실제 판단에 사용한 원천 참조
- `import_units`: 원문을 순서대로 완전히 덮는 가져오기 단위 배열
- `questions`: 사용자에게 그대로 제시할 질문 문장 배열
- `question_details`: 질문의 대상·차단 효과·이유·관련 원문 단위·선택지별 효과
- `repair`: 직전 검사에서 재작업을 요구한 경우에만 쓰는 수리 계보

각 `import_unit`은 다음을 포함한다.

- `unit_id`: 이번 봉투 안에서 고유한 식별자
- `source_range.start`, `source_range.end`: `user_request.text`에서 이 단위가 차지하는 반열림 구간
- `interpretation`: 원문을 바꾸지 않고 이 단위가 뜻하는 바를 명시한 해석
- `owner_kind`, `owner_ref`: 이 단위를 검증하고 적용할 등록 소비자
- `payload`: 그 소비자가 받아들이는 구조화된 제안
- `decision_refs`: 해석에 의존한 현행 결정 참조
- `question_refs`: 이 단위 때문에 열린 `question_details[].id`의 목록. 질문 배열의 위치는 별도의 `question_index`로 연결한다.

`import_units`의 구간은 첫 글자부터 마지막 글자까지 빈틈·겹침·순서 역전 없이 원문 전체를 정확히 한 번 덮어야 한다. 공백·구두점·부수 설명도 버리지 않는다. 원문 일부를 적용 대상이 아니라고 판단하더라도 그 부분을 맡는 단위를 만들고, 그 판단과 근거를 `interpretation`과 해당 소유자의 `payload`에 보존한다.

`owner_kind`는 닫힌 열거가 아니다. 현재 입력에 등록된 소비자만 사용할 수 있다. 예를 들어 거버넌스 결정·권한 부여·권한 회수·사례 위임·질문 답변·과제 범위뿐 아니라, 등록된 설정·지식 가져오기 소비자도 합법적인 소유자가 될 수 있다. 예시는 허용 종류 전체를 뜻하지 않는다. `payload`의 소유자와 대상은 `owner_kind`·`owner_ref`와 정확히 맞아야 하며, 등록되지 않은 소유자나 소비자가 해석할 수 없는 임의 필드를 만들어서는 안 된다.

질문은 원문에서 확인할 수 없는 사용자 목적·선호·위험 허용도를 메우기 위해 사용한다. 각 `question_detail`은 `id`, `question_index`, `target_ids`, `blocks`, `reason`, `source_unit_ids`, `options`를 연결한다. 모든 `questions` 위치는 중복 없이 상세 항목 하나에 연결돼야 한다. `question_index`는 `questions`의 실제 위치를 가리키고, `source_unit_ids`는 질문이 생긴 단위를 빠짐없이 가리킨다. 선택지가 있다면 각 선택지는 `text`와 선택 시 상태·범위에 미치는 `effect`를 함께 적는다. `blocks=true`이면 실제로 영향받는 알려진 대상을 `target_ids`에 하나 이상 명시한다. `target_ids`에 쓸 수 있는 알려진 대상은 입력의 `instance_id`, `tasks`의 과제 ID, `governance_records`의 통치 기록 ID, `grants`의 허가 ID이며, 제출 검사는 그 밖의 ID를 반려한다. 지식처럼 다른 기록이 영향을 받으면 `instance_id`를 대상으로 쓰고, 그 기록의 ID와 받는 영향을 `reason`에 적는다.

해석은 현행 연구 헌장·정책, 명시적으로 참조한 결정·기록·대상과 소비자별 전제에 결박된다. 실제 판단에 사용한 기록은 `used_sources`, `decision_refs`와 해당 payload의 참조에 명시한다. 무관한 과제의 진행만으로 원문을 다시 해석하지 않는다.

`repair`는 재작업일 때만 사용한다. 직전 산출물의 고정 해시, 바꾼 단위, 검사 지적에 대응한 조치를 기록하여 새 해석이 무엇을 왜 고쳤는지 추적할 수 있게 한다. 수리라는 이유로 원문 범위나 승인 범위를 넓힐 수 없다.

## 독립 검사

독립 검사는 `action.role=intent_interpretation`, `action.stage=check`로 배정되는 별도 실행이다. 검사자는 같은 고정 원문·상태·원천과 검사 대상 묶음을 받되, 해석자의 숨은 맥락이나 미고정 작업물을 근거로 삼지 않는다. 검사 본문은 다음을 포함한다.

- `decision`: `approved`, `revision_required`, `unresolved` 중 하나
- `findings`: 발견한 누락·왜곡·소유권·질문·적용 위험
- `scope_complete`: 원문 전건 피복과 범위 처분이 완전한지
- `bundle_sha256`: 검사한 해석 묶음의 정확한 해시
- `unit_ids`: 검사한 모든 가져오기 단위 식별자
- `question_ids`: 검사한 모든 질문 식별자

이 `question_ids`는 해석 묶음의 `question_details[].id`를 가리킨다. 검사에 필요한 자료가 없어 새로 묻는 질문은 검사 출력의 `questions`와 `activity-extensions.json.question_routes`로 연결한다. 두 목록은 용도가 다르다.

검사는 구간이 원문을 정확히 피복하는지, 해석이 원문 의미를 보존하는지, 모든 단위와 질문이 등록된 소비자 및 실제 대상에 연결되는지, `decision_refs`가 현행 판본인지, 질문 없이 창작한 사용자 결정이 없는지를 확인한다. `bundle_sha256`, `unit_ids`, `question_ids`가 검사 대상과 정확히 맞지 않으면 승인할 수 없다. `approved`는 해석 묶음이 적용 후보가 될 수 있다는 뜻일 뿐, 사용자 승인이나 실제 적용을 대신하지 않는다.

지적하기 전에 실제 원문·소비자 계약·지급 근거를 대조하고, 자신의 오독이나 확인 부족을 해석의 결함으로 보고한 것은 아닌지 검토한다. 확인한 누락·왜곡·소유자 오류는 이유와 실제 영향을 설명해 `revision_required`로 반환한다. 아직 수행하지 않은 연구의 성공이나 도구 호출 결과를 미리 입증하게 하는 것은 이 검사의 일이 아니다. 현재 원문의 의미와 적용 경계를 판단할 수 있으면 정상 판정을 마친다.

필수 판단 자료를 실제로 읽지 못해 결론을 낼 수 없으면 `unresolved`로 반환한다. `findings`에는 필요한 자료와 판단에 미치는 영향을 설명하고, `questions` 전건에 실제 대상·다음 담당·이유를 가진 `question_routes`를 작성한다. 운영 자료 회수는 기존 operations obligation을, 사용자 목적·허가 선택은 user 질문을 사용한다. 실제로 읽은 근거는 `used_sources`에 적는다. 이 결과는 같은 `import_id`·원문·묶음 SHA의 `import_check_evidence` 대기가 되며 해석을 다시 쓰거나 재저작 횟수를 늘리지 않는다.

후속 `stage=check`는 관련 질문의 고정 대상 범위에 새 해소 영수증이 생기거나 실제 인용 자료가 변한 때 별도 실행으로 배정된다. `import_check_evidence` 입력의 `questions`는 대상별 해소 상태와 영수증, `records`는 정확한 자료 기초다. 실제 답변·근거는 지급된 `question_links`·기록 지도·원자료에서 읽고 같은 봉인 묶음을 다시 판단한다. 이미 읽은 영수증이나 보고 수 증가만으로 검사를 반복하지 않는다. 같은 근거로 여전히 미해결이면 남은 자료와 담당 질문을 유지한다. 새 관찰 때문에 같은 운영 의무를 다시 열어야 할 때는 공통 질문 계약의 `reopen_basis_refs`·`reopen_reason`을 사용한다.

이전 봉인 검사는 `check_history`에 보존되고 현행 `check`만 후속 검사로 갱신된다. 검사 이력 추가는 원 해석 묶음의 SHA를 바꾸지 않는다. 후속 검사는 엔진의 실제 근거 해소 기록에 결박되며 해석자와 이전 봉인 검사의 실행·대화를 재개하지 않는다. 원문·해석 또는 적용 전제가 실제로 바뀌면 기존 재저작 경로를 사용한다. 질문 해소는 사용자 승인·owner 적용이나 pause/HOLD 해제를 대신하지 않는다.

## 재저작과 반복 보류

원 해석이 잘못되어 `revision_required`를 반환하면 새 `stage=interpret` 실행이 원입력을 다시 해석한다. 실행기는 `previous_import_id`·`intent_repair`로 기존 묶음과 검사 결과를 연결하고, 같은 원입력의 재저작 시도를 등록할 때 한 번 센다. 해석 실행의 형식 오류를 고치는 후속도 재저작에 포함되며, 새 묶음 ID로 횟수가 초기화되지 않는다. `stage=check`의 형식 수리는 검사 응답만 고치고 검사 대상 묶음의 해시를 유지한다. 원 해석을 바꾸어야 하면 검사자가 직접 수정하지 않고 반려한다.

채택된 재저작 한도 뒤에는 그 원입력의 다음 재저작이 보류된다. 최초 해석, 독립 검사와 별도 사용자 답변의 해석은 그 보류의 적용 대상과 구별한다. 보류 해소는 GLOSSARY의 반복 교정 문턱과 공개 계속 결정 계약을 따른다.

## 사례 위임 판단

사례 위임의 범위 판단은 일반 `import_units` 출력이 아니라 동적 `delegation_judgment` 분기를 사용한다. 두 독립 실행은 동일하게 봉인된 원문, 현재 위임, 결정·승인 원천과 정확한 `input_sha256`을 받고, 서로의 판단을 보지 않은 채 `within_scope`, `outside_scope`, `unresolved` 중 하나를 낸다. 판단에는 적용한 위임, 포함·제외 대상, 외부 효과와 자원 한계, 근거 원천을 정확히 연결한다.

사례 위임 종류는 현재 계약이 금지한 `proposal_adoption`과 `contract_limit_continuation`을 제외하고 등록될 수 있다. 허용 예시는 닫힌 목록이 아니다. 두 판단은 새 위임을 만들거나 기존 위임의 범위를 넓히지 않으며, 합의와 현재 계약이 허용하는 경우에만 후속 적용의 근거가 된다. 불일치나 근거 부족은 `unresolved`로 남기고 사용자 또는 소유자 결정으로 돌려보낸다.

검토 교체에서는 사용자의 공개 명시 교체 요청이 원결정을 생산하고, 별도의 위임 승인이 당시 원결정 전체의 해시와 정확한 범위를 결합한다. 현재 사례의 cycle·자리·실패 인덱스·원인까지 같은 봉인 입력으로 대조한다. 두 `within_scope`만 교체 권한으로 이어지며, 한쪽이라도 `outside_scope` 또는 `unresolved`면 해당 대상의 사용자 질문을 보존한다. 이미 적용한 위임 결과는 사용자 원결정으로 기록하지 않는다. 재전달은 기존 판단·영수증을 재사용하며, 현재성·독립성·기계 실행 허가와 사용자 정지를 우회하지 않는다.

## 적용 경계와 반환

초기화에서는 원문 자체를 불변 입력으로 보존한다. 독립 검사가 승인한 해석이라도 원문의 명시적 승인·적용, 채택된 정책과 설정, 고정된 프로필·능력 증거, 분리된 권한 부여 등 공개 활성화 관문을 통과하기 전에는 연구 권한이나 준비 큐를 만들지 않는다.

후속 가져오기에서도 각 소유자는 승인된 단위만 자신의 스키마와 비교·적용한다. 한 소유자의 성공을 다른 소유자의 성공으로 간주하지 않는다. 적용 결과는 단위별 성공·거부·미해결과 실제 생성된 고정 참조를 반환하고, 생산자 검사·제출 미리보기·제출 의도·저장소 비교-교환은 `공통-실행.md`와 해당 소비자 계약을 따른다.
