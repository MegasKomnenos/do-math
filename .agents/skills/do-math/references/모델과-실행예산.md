# 모델 배정과 동시실행 예산

연구 계획은 현재 목표와 근거를 비교해 수행할 작업과 순서, 병행 관계를 정한다. 각 실행에는 그 작업의 난이도와 중요도에 맞는 모델을 배정한다. 기계 실행기는 착수 조건과 그 역할에 필요한 자원이 갖춰진 요청을 시작하며, 작업 역할이면 배정된 모델의 작업 슬롯도 필요하다. 여러 독립 실행의 결과는 한 연구 정본에 차례로 반영한다.

예약과 실제 실행 상태는 같은 Git 원장에 기록한다. 정상 엔진과 설치 복구는 writer lock의 상호 배제 아래 같은 예약 계약을 사용한다. status의 예산은 연구 상태와 같은 snapshot의 투영이며, 이후 배정은 최신 상태에서 다시 검사한다. 별도 현장 프로세스 관측이나 운영 로그는 그 시각·범위의 증거로 읽는다.

## 인스턴스별 기본 구성

새 인스턴스는 다음 구성을 사용한다. 모델 대응은 `tier_models`, 모델별 작업 슬롯 수는 `session_limits.work`로 바꾼다. 설정의 모델 이름은 아래 세 이름으로 제한하지 않는다. 그 밖의 설정 기본값과 허용 값은 [CLI 실행 계약의 설정 목록](CLI-실행-계약.md#config-list)이 정한다.

Claude와 Codex는 같은 모델 배정·예산 절차를 사용한다. 각 등급에는 모델 하나를 지정하며, 슬롯 부족 때문에 다른 모델로 바꾸지 않는다. 모델 이름에서 실행할 CLI를 고르는 규칙과 설정 표기의 통일은 [CLI 실행 계약](CLI-실행-계약.md)의 설정 계약 절이 정한다.

<a id="model-table"></a>

다음 모델 표가 기본 모델 대응과 모델별 작업 슬롯 수의 정본이다. 다른 문서는 이 수치를 다시 적지 않고 이 표를 가리킨다.

| 배정 등급 | 기본 모델 | 작업 슬롯 |
|---|---|---:|
| 상 `high` | `gpt-6-astra` | 3 |
| 중 `medium` | `gpt-5.6-sol` | 3 |
| 하 `low` | `gpt-5.6-terra` | 3 |

기본값은 인스턴스 하나에서 작업 역할 실행을 모델마다 표의 수만큼 동시에 허용한다. 여러 인스턴스가 한 용량을 공유하는 설정은 아니다. 각 값은 0 이상의 정수이며 0은 그 모델의 새 작업 실행을 대기시킨다. 같은 모델을 여러 등급에 연결해도 용량은 모델 이름 하나에 설정된 값으로 센다.

작업 슬롯을 예약하는 작업 역할은 연구 수행, 보충 조사, 작업 계약 검토, 동일성 검토, 목표 감사다. 한 세션은 한 번 시작해 종료하는 로컬 AI 실행이다. 준비 중인 요청은 슬롯을 사용하지 않는다. 작업 역할의 실행은 시작을 예약한 뒤 `starting`, `running`, `stopping` 동안 같은 슬롯을 점유하고 로컬 종료를 확인한 뒤 반환한다. 제출·실패·취소 뒤 반환된 슬롯은 다음 실행이 재사용한다. 외부 입력을 기다리기 위해 결과를 반환한 과제는 실행을 종료하고, 과제의 대기와 다음 의무는 기록으로 유지한다.

후보 준비, 연구 계획, 의도 해석, 운영 점검, 유지보수와 실패 시 설치 복구는 운영 역할이다. 운영 역할은 작업 슬롯을 예약하지 않고, 아래 절의 역할 하한과 대상의 요구로 고른 모델에 바로 배정된다. 그래서 작업 슬롯이 모두 점유돼도 계획·점검·복구가 슬롯을 기다리지 않는다. 운영 역할의 동시 실행 수는 이 예산으로 세지 않으며, 역할별로 남는 동시 실행 제한은 아래 「우선순위와 실제 배정」이 적는다. 호스트 자원 한도를 설정했으면 그 한도와 공급자 한도는 운영 역할에도 적용된다. 정상 예약 감독은 모델을 호출하지 않는다. 작업 슬롯은 로컬 실행의 동시성 한도이며, 누적 실행횟수·토큰·금액이나 공급자 내부 호출의 동시성 한도를 뜻하지 않는다.

## 난이도와 중요도에서 모델을 정한다

후보 준비는 과제의 질문·범위·필요한 판단을 바탕으로 난이도와 중요도를 각각 평가하고, 작업 계약 검토는 그 근거가 과제와 맞는지 함께 검토한다. 연구 계획은 선택한 과제의 평가를 현재 근거로 다시 보고, 등급을 바꿀 과제에만 새 평가를 낸다. 두 축 가운데 높은 등급을 사용하며, 해당 역할에 설정된 최소 등급이 더 높으면 그 등급을 사용한다.

| 등급 | 난이도를 판단할 근거 | 중요도를 판단할 근거 |
|---|---|---|
| 상 | 새로운 증명 전략이나 표현을 찾아야 함. 여러 가정·정의·분야를 연결하며 접근의 성립 자체가 불확실함. 복잡한 의미 충돌을 해결해야 함 | 연구 방향이나 공용 판단을 좌우함. 잘못된 판단이 여러 후속 과제에 퍼짐. 목표 충족이나 핵심 수학적 동일성을 판정함 |
| 중 | 알려진 접근을 제한된 문제에 적용하되 여러 조건·예외를 비교하고 판단해야 함 | 한 과제 또는 제한된 후속 흐름에 영향을 주며, 오류를 확인하고 다시 수행할 경로가 분명함 |
| 하 | 입력과 처리 방법이 명확하고 국소적인 추출·정리·단순 대조가 중심임 | 영향이 국소적이며 원자료와 결과를 직접 대조해 수정할 수 있음 |

위 설명은 판단 기준이며 작업 이름만 보고 등급을 고정하는 목록이 아니다. 짧은 과제라도 핵심 가정이나 연구 전체의 선택을 바꾸면 중요도가 높다. 파일 수, 실행시간, 현재 빈 슬롯 수를 난이도나 중요도의 대용으로 쓰지 않는다. 모델의 자리가 없다는 이유로 평가를 낮추지 않는다.

평가는 `difficulty`, `importance`, 구체적인 `reason`으로 보존한다. 신규·개정 후보를 제출할 때는 후보마다 평가를 정확히 하나씩 작성한다. 실행기가 생성한 학술 과제나 평가 없는 기존 과제는 아래 평가 보충을 마친 뒤 계약 검토에 들어간다. 역할 하한과 평가에 따른 배정은 운용 정책이며, 모델 이름만으로 수학 성능의 우위가 실험적으로 검증됐다고 주장하는 근거는 아니다.

<a id="role-tiers"></a>

최초 계획을 열기 전에도 운영 판단이 필요하므로 역할별 최소 등급을 `role_tiers`에 둔다. 이 문단이 역할별 최소 등급 기본값의 정본이다. 기본 상 등급은 후보 준비·연구 계획·의도 해석·동일성 검토·목표 감사와 실패 시 설치 복구다. 기본 중 등급은 작업 계약 검토·운영 점검·유지보수다. 연구 수행·보충 조사의 역할 하한은 하 등급이며 과제 평가가 실제 등급을 정한다. 요청에도 대상 과제(대상이 지식이면 그 지식을 낳은 과제)에도 보존된 평가가 없는 연구 수행·보충 조사는 평가가 생길 때까지 역할 하한 대신 상 등급으로 배정한다. 과제나 점검 대상 실행의 요구가 역할 하한보다 높으면 그 요구를 적용한다. 후보 수신·평가 보충·착수 가능 판정·실제 배정은 같은 프로필 선택 규칙을 사용한다. 평가가 요구한 등급을 계약의 허용 프로필이 충족하지 못하면 후보 준비가 계약을 고쳐야 하며, 그 과제를 배정 후보로 표시하지 않는다. 역할별 설정은 인스턴스에서 바꿀 수 있다.

## 평가를 제출하고 전달한다

후보 준비와 연구 계획은 작업 공간의 `activity-extensions.json`에 `model_assessments` 배열을 적는다. 일반 후보 준비는 같은 응답의 후보를 `task_title`로, 연구 계획은 이번 `dispositions`에서 `kind=selected`인 과제를 `task_id`로 지목한다. 일반 후보 준비는 신규·개정 후보 전건과 평가가 정확히 일대일로 대응해야 한다. 연구 계획은 선택 과제 가운데 등급을 바꿀 과제와 입력 `tasks`에 저장된 평가가 없는 과제에만 평가를 하나씩 적는다. 수신자는 중앙 접수에서 누락·중복·대상 밖 평가를 검사한다. 누락은 후보 준비에서는 평가를 적지 않은 후보이고, 연구 계획에서는 저장된 평가가 없는데 평가도 적지 않은 선택 과제다. 대상 밖 평가는 연구 계획에서 선택하지 않은 과제의 평가다. 생산자는 필요하면 같은 검사기를 로컬에서 먼저 실행해 오류를 고칠 수 있다. 개수가 같아도 대상이 다르면 거부한다. 대상이 없으면 빈 배열 또는 해당 확장 생략을 허용한다. 각 항목에는 대상 필드와 아래 세 평가 필드만 사용한다.

```json
{
  "model_assessments": [
    {
      "task_id": "TK-현재-입력의-정확한-ID",
      "difficulty": "high",
      "importance": "medium",
      "reason": "기존 점화식의 항별 비교가 성립하지 않아 새로운 대응을 찾아야 한다."
    }
  ]
}
```

일반 후보 준비에서는 위 `task_id` 대신 실제 후보 제목인 `task_title`을 쓴다. 수신 검사는 평가를 제목으로 대응시키되 생산자가 제출한 후보 wire 객체를 변형하지 않는다. 실행기는 대응된 평가를 그 wire에서 새로 만든 과제 record의 `model_assessment`에 보존하고, 연구 계획의 평가는 선택된 다음 실행 요청에 결합한다. 연구 계획이 평가를 적지 않은 선택 과제의 요청은 배정할 때 과제 record의 `model_assessment`를 쓴다. 원 평가와 선택한 모델·등급·근거는 실행 기록에 남긴다. 요청이 대기하는 동안 같은 배정을 유지한다. 승인된 모델 대응 설정을 변경하면 미시작 요청은 현재 평가와 새 대응으로 다시 결합하며, 이미 시작한 실행의 모델은 그대로 유지한다.

## 기존 과제의 평가를 보충하거나 수리한다

계약 검토를 기다리는 과제에 모델 평가가 없거나 학술 과제가 계약 검토에서 반려되면, 실행기는 후보 준비에 평가 보충을 요청한다. 평가 보충도 위의 두 축과 판단 기준을 그대로 적용한다. 배정 대상, 반환과 보류의 형식, 재요청 조건과 반려 뒤 재검토는 「후보 준비」의 「기존 과제의 평가와 관찰 규칙을 보충하는 실행」 절이 정한다. 후보 준비의 역할 하한은 기본 상 등급이므로, 평가를 작성할 실행의 등급을 정하려고 먼저 과제 평가를 요구하지는 않는다. 보충된 평가를 받는 작업 계약 검토의 모델도 난이도·중요도·역할 하한 가운데 높은 등급으로 정한다.

## 우선순위와 실제 배정

연구 계획은 목표 기여, 기대 정보와 불확실성, 탐색과 집중 활용, 기존 결과의 재사용, 과거 성과·실패, 후보 사이의 중복·보완·독립·의존, 오래 기다린 작업, 현재 병행 작업과 자원을 함께 비교한다. 제공된 배정 후보 전건에 선택 또는 보류와 이유를 남기고, 선택한 과제를 실행 순서대로 반환한다. 용량을 모두 채울 의무는 없다. 높은 모델 등급이 곧 높은 연구 우선순위를 뜻하지 않는다.

선택할 작업 수는 동시 슬롯 수를 넘을 수 있다. 기계 실행기는 계획 순서대로 착수 조건과 해당 모델 슬롯·호스트 자원을 같은 예약 계산으로 검사한다. 앞 요청의 모델 슬롯이나 호스트 자원이 부족하면 그 요청을 원래 순서에 남기고, 독립된 자원으로 진행할 수 있는 뒤 요청을 검사한다. 자원이 바뀌면 대기 요청도 같은 계산으로 다시 검사한다. 같은 공유 자원을 기다리는 앞 요청이 착수할 수 있게 되면 뒤 요청을 먼저 시작하지 않는다. 슬롯 부족 때문에 다른 모델로 우회하지 않는다.

실행기 내부의 운영 요청은 운영 요청끼리의 큐 진입 순서로 처리한다. 운영 요청은 작업 슬롯을 기다리지 않으며, 착수 조건과 공급자 한도, 설정된 호스트 자원을 확인한 뒤 시작한다. 설치 복구는 별도 예약 감독이 보존된 실행기 시작 실패나 수락된 설치 결함 진단을 확인한 뒤 같은 공급자 한도와 호스트 자원을 검사해 시작한다. 정상 감독 자체는 모델을 호출하지 않는다. 현재 필요한 자원을 확보할 수 있는 가장 오래된 요청부터 시작하며, 자원이 막힌 요청을 건너뛰어 뒤의 요청을 시작할 수 있다. 정지와 권한 회수는 운영 AI의 차례를 기다리지 않는 기계 제어다. 한 인스턴스에서 후보 준비와 연구 계획은 각각 하나만 진행하고, 진행 중 실행의 운영 점검은 대상 실행마다 하나만 진행하며, 같은 과제의 연구 수행도 한 번에 하나만 진행한다. 서로 다른 과제와 독립 검토 자리는 각자의 작업 슬롯 안에서 병렬로 수행할 수 있다.

새 결과나 사용자 결정으로 기존 순서를 바꾸어야 하면 연구 계획은 `queued_work`에서 아직 시작하지 않은 요청을 읽는다. `activity-extensions.json`의 `queued_requests` 배열에 `request_id`, `decision`과 `reason`을 반환한다. `decision`은 `keep` 또는 `cancel`이며, 유지할 요청의 배열 순서가 그 요청들 사이의 새 순서다. 취소 요청을 제거한 뒤, 유지할 요청들이 원래 차지하던 위치에서 그 요청들만 새 순서로 교환한다. 언급하지 않은 요청은 이 교환에 참여하지 않는다. 이미 시작했거나 종료된 요청에는 이 처분을 적용하지 않고 미적용 이유를 남긴다. 취소는 요청의 수행을 철회하는 것이며 과제 완료나 과제 의무의 삭제가 아니다.

## 병렬 실행과 결과의 반영

실행마다 별도 `runs/<실행 ID>/workspace`에서 고정 입력과 자기 산출을 다룬다. 입력 스냅샷과 계약·지식·원자료·허가의 적용 전제를 기록하고, 결과의 원문과 파일은 실행별 산출 묶음으로 보존한다. 모델 호출은 병렬로 진행하지만 실행 상태의 변경과 연구 정본의 갱신은 실행기 하나가 수행한다.

돌아온 결과에는 스키마와 참조·권한·의존 전제의 현재성을 검사한다. 관련 없는 결과가 먼저 도착했다는 이유로 폐기하지 않는다. 계획은 자기 입력에 있던 후보를 전건 처분하고, 새로 준비된 후보는 후속 계획으로 연결한다. 실제로 바뀐 계약이나 효력에 의존한 결과는 현재 근거로 다시 판단할 담당에게 돌린다. 과제 완료·수학적 동일성·목표 충족은 각 지정 AI가 판단하고, 실행기는 그 판정을 정해진 상태 전이로 반영한다.

작업 공간은 경로와 입력의 분리다. 현재 로컬 권한 모드가 다른 호스트 경로의 접근을 기술적으로 차단한다는 뜻은 아니다. 같은 단계의 독립 검토자에게 동료의 중간 결과를 제공하지 않는 기존 입력 경계는 병렬 실행에서도 유지한다.

## 설정 변경과 기존 인스턴스

한도를 현재 점유보다 낮추면 해당 모델의 새 배정을 기다리게 한다. 이미 실행 중인 세션을 강제로 종료하는 지시로 해석하지 않는다. 실행 종료까지 원하면 별도의 정지 제어를 사용한다. 슬롯 반환 또는 허용된 설정 변경 뒤 대기 요청을 다시 검사한다. `capacity_waiting`은 자원 대기이며 연구 완료나 오류가 아니다.

모델과 세션 용량은 `configure`로 조정한다. 설정 예시와 상태 필드는 [CLI 실행 계약](CLI-실행-계약.md)을 따른다.

## 인스턴스의 Claude 모델 잠금과 공급자 대기

`claude_only_assigned_model`이 true인 인스턴스의 Claude 호출은 전체 모델 ID를 사용하며 내부 보조·fallback 모델도 배정 모델로 제한한다. 이 옵션 자체가 모든 역할을 Claude로 배정하는 것은 아니다. 한 모델 전용 연구라면 모든 `tier_models`, 실제 역할 배정과 설치 복구 프로필까지 같은 전체 ID인지 확인한다. 다른 인스턴스의 기본 모델은 바뀌지 않는다. 보고된 실제 모델이 잠금과 다르면 후속 실행을 정지하고 원 증거를 남긴다. 공급자가 보고하지 않은 내부 소비를 관측했다고 주장하지 않는다.

작업 슬롯이 남아 있어도 같은 공급자의 이용 한도로 새 호출이 불가능할 수 있으며, 이 한도는 작업 역할과 운영 역할에 모두 적용된다. 확정된 한도는 이 인스턴스의 공유 원장에 `waiting`, 다음 시각과 근거로 기록한다. 한도에 걸린 요청은 `waiting_actions`로 옮기지 않고 대기열에 남기며, 그 요청의 `dispatch_wait`에 `kind=provider_limit`과 공급자·재관찰 시각을 둔다. 작업 역할의 요청이면 연구 계획이 `queued_work`에서 이 요청을 다른 미시작 작업처럼 유지·취소할 수 있다. 시각이 도래하면 허가된 실제 action 하나가 `checking` 소유권을 얻어 재관찰하며, 정상 응답으로 `available`을 확인한다. 별도의 모델 ping이나 동일 한도에 걸릴 진단은 호출하지 않는다. 이미 실행 중인 다른 호출은 개별 결과를 회수한다. 사용자 정지·HOLD·허가 검사는 이 재관찰보다 우선한다.

한도 해제 시각이 없으면 `provider_retry_initial_seconds`에서 시작해 `provider_retry_max_seconds`를 넘지 않는 유한 지수 대기를 쓴다. 두 값의 기본값은 [CLI 실행 계약의 설정 목록](CLI-실행-계약.md#config-list)을 따른다. 이는 해제 예측이 아니라 재확인 간격이다. 모델 없는 일회성 `operator wake`가 연구 진입점을 깨우고, 실제 모델 호출 여부는 실행기의 권한·의무·공급자 검사에서 정한다. 외부 행동의 unknown 상태는 한도 해제로 재전송하지 않는다.

Claude 사용량은 응답 구간의 `usage_segments`와 마지막 누적 `model_usage_reported`를 나누어 읽는다. 구간 카운터를 합산한 `usage`와 누적 modelUsage를 다시 합산하지 않는다. 입력 바이트를 토큰으로, 가격표 기준 비용을 실제 청구액으로 바꾸어 표시하지 않는다.
