# 초기화에서 연구 활성화까지

이 문서는 사람 운영자가 판본 5 인스턴스의 원입력·승인·프로필·신뢰 환경을 공개 CLI로 연결하는 절차다. `init` 성공은 입력을 보존한 상태이며 연구 시작의 승인이 아니다. 아래 JSON은 요청 형식을 보여 주는 예시다. 목표·정책·허가 범위·만료 시각·환경과 증거는 실제 사용자가 정하거나 실제 측정에서 얻어야 한다. 예시를 문서에서 읽었다는 사실은 승인이 아니다.

이 절차는 README의 [초기화 완료 단계](../README.md#activate-instance)에서 이어진다. 선행 읽기는 SKILL.md의 [사용자 대화 진입 절차](../SKILL.md#이-문서를-읽는-실행의-역할)를 따른다.

아래 명령은 저장소 루트에서 실행한다. `$dmRepository`와 `$dmInstance`를 실제 값으로 정하고 현재 디렉터리는 바꾸지 않는다. `--file`은 UTF-8 JSON 객체 하나를 읽는다. 요청마다 반환의 `effect`를 확인한다. `accepted=true`만 있고 처리가 대기 중이면 해당 요청이 적용될 때까지 다음 의존 단계를 진행하지 않는다.

```powershell
$dmCli = '.agents/skills/do-math/scripts/do_math.py'
$dmRepository = '.skill-workspace/my-math/repo'
$dmInstance = 'RI-실제-init-응답-ID'
python $dmCli status --repository $dmRepository --instance $dmInstance --json
```

## 1. 보존된 입력과 설정을 확인한다

README의 `init`으로 생성한 ID와 첫 snapshot을 사용한다. `query --files`로 등록된 경로를 찾고 `read --path`로 정확한 snapshot을 읽을 수 있다. 연구 저장 파일은 직접 고치지 않는다.

```powershell
python $dmCli query --repository $dmRepository --instance $dmInstance --files --prefix research/ --limit 1000
python $dmCli query --repository $dmRepository --instance $dmInstance --files --prefix runtime/ --limit 1000
```

CLI의 JSON 조회 결과는 최상위 `result` 안에 있다. 그 안의 `next_cursor`가 있으면 같은 조건에 `--cursor`를 추가해 다음 쪽도 읽는다. 각 조회의 `result.snapshot`을 후속 `--snapshot`에 지정하면 같은 판본을 대조할 수 있다. 경로 조회의 실제 `result.items[].path`를 복사해 다음처럼 읽는다.

```powershell
python $dmCli read --repository $dmRepository --instance $dmInstance --snapshot '<조회 snapshot>' --path '<조회한 lifecycle 또는 config 파일 경로>'
```

원입력은 `lifecycle.immutable_input`의 `text`, `sha256`, `bytes`에 하나의 정확한 표현으로 보존된다. `text`는 사용자가 준 문자열의 코드 포인트열이고, 해시와 크기는 그 문자열의 UTF-8 바이트에 대해 계산한다. 이름과 원문을 NFC로 바꾸거나 Base64 원문을 별도로 만들지 않는다. 이 세 필드는 바이트 보존을 증명하지만, 해석·검토·승인이 그 원문을 실제로 사용했다는 뜻은 아니므로 뒤 단계의 `user_request.text`와 소비 근거를 별도로 대조한다.

설정 변경이 실제로 필요하면 승인된 변경만 `configure --config-file`로 적용한다. 그대로 쓸 기본값은 뒤의 채택 요청에서 현행 설정으로 결박한다. 이미 사용자에게 채택받은 값을 다시 새로운 의미 승인 대상으로 만들 필요는 없다. 모델·effort·용량·관찰 window가 바뀌면 그 변경으로 생성된 프로필 판본을 새로 조회해야 한다.

프로필 조회·채택 전에 `tool_review_window_seconds`와 `self_check_response_window_seconds`가 설정에 있는지 확인한다. 두 값에는 제품 기본값이 없다. 빠져 있으면 해당 연구에서 사용할 양의 초 값을 확정하고, 두 키와 확정한 값을 담은 JSON 객체를 `observation-settings.json`으로 저장한다. 이미 승인된 값이 있으면 그 값을 재사용한다. 주기·사건 관찰의 `observation_interval_seconds`도 유효해야 한다. 이 단계는 프로필의 관찰 설정을 준비하는 단계이며, 아직 생성되지 않은 과제의 개별 관찰 규칙을 요구하지 않는다.

```powershell
python $dmCli configure --repository $dmRepository --instance $dmInstance --config-file observation-settings.json
```

적용 응답을 확인한 뒤 4단계에서 새 프로필을 조회하고 `operation=probe`로 능력을 관측한다. 같은 4단계의 채택 요청으로 해당 프로필과 현행 설정을 채택한다. 누락된 관찰 설정은 역할·프로필 ID·필드로 표시되며 채택 또는 활성화를 막는다. 이 경우 같은 인스턴스에서 설정을 보충하고 프로필 조회부터 다시 진행한다. 원입력과 과거 프로필은 보존되며 이미 유효한 사용자 승인·권한을 새로 만들지 않는다.

## 3. 초기화 권한과 연구 권한을 나눈다

초기화 grant는 `intent_interpretation`·`maintenance` 범위, 운영 예산, 명시적 만료와 재사용을 요구한다. 연구 grant는 다른 ID를 사용한다. 초기화 grant의 ID를 연구 grant로 다시 채택하지 않는다.

다음 만료 시각은 형식 예시다. 실제 허가 기간으로 바꾸고, 역할 목록과 재사용 범위를 사용자가 승인한 대로 정한다. `task_ids=[]`는 열거한 역할의 모든 과제를 허용하므로 특정 과제로 제한할 때에는 실제 과제 ID를 넣는다. HTTP 등 외부 효과는 별도 grant가 필요하다.

`02-initial-grant.json`:

```json
{
  "kind": "grant",
  "grant": {
    "id": "GR-initial-01",
    "kind": "local",
    "roles": ["intent_interpretation", "maintenance"],
    "task_ids": [],
    "budget_kind": "operations",
    "reuse": "reusable",
    "expires_at": "2026-12-31T00:00:00+00:00",
    "checkpoint_allowed": true
  }
}
```

`03-research-grant.json`:

```json
{
  "kind": "grant",
  "grant": {
    "id": "GR-research-01",
    "kind": "local",
    "roles": ["research_preparation", "research_plan", "research_work", "supplemental_research", "task_contract_review", "formal_check", "identity_review", "goal_audit", "operational_review", "intent_interpretation", "maintenance"],
    "task_ids": [],

```

```powershell
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 02-initial-grant.json
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 03-research-grant.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind grant --limit 1000
```

초기화 중 grant를 등록하는 일은 연구 계획이나 연구 과제를 열지 않는다. 이 단계에서는 이후 활성화에 사용할 서로 다른 초기화·연구 허가를 보존하고 채택할 뿐이다. 최초 후보 준비 또는 연구 계획은 원입력 해석·독립 검사·신뢰 환경·프로필 능력·복구를 포함한 활성화 관문 전건이 통과해 lifecycle이 `active`가 될 때 열린다. 활성화 뒤 grant가 추가·교체되면 그 사용자 결정의 `decision_id`가 재계획 사유가 된다. 새 `grant_id`는 이후 실행을 허가할 수 있는 권한 참조이지 계획을 연 근거 ID가 아니다.

## 4. 실제 프로필을 조회하고 능력을 관측한다

프로필 참조는 등록된 기록 본문의 `id`, `revision`, `sha256` 세 값을 그대로 묶은 객체다. 조회 항목 바깥의 `sha256`은 조회 표현의 해시이므로 참조의 해시로 복사하지 않는다. 아래 조회는 현재 설치·설정에서 생성된 실제 프로필을 얻는다.

등록부에는 설정 변경 전의 프로필도 남는다. 1단계의 연구 기록 조회에서 `research/role_profile_refs/state.json`의 `record`를 읽는다. 그 객체의 역할 이름별 배열에는 사용할 수 있는 프로필의 `id`, `revision`, `sha256` 참조가 들어 있다. 프로필 ID는 본문 해시에서 생성되므로 같은 ID로 다른 판본을 등록할 수 없다. 허용 목록이 가리키는 현행 판본 중 사용할 프로필을 고르고, 보관된 프로필 전건을 채택 목록에 넣지 않는다. 과제에 이미 고정된 프로필은 설정 변경만으로 교체되지 않으며, 새 프로필을 쓰려면 해당 과제를 재준비하고 독립 계약 검토를 받아야 한다.

```powershell
$dmPage = (python $dmCli query --repository $dmRepository --instance $dmInstance --kind execution_profiles --limit 1000 | ConvertFrom-Json).result
if ($LASTEXITCODE -ne 0 -or $null -eq $dmPage -or $null -eq $dmPage.items) { throw '프로필 조회 실패: CLI 종료 상태와 반환 본문을 확인한다.' }
$dmProfileRecords = @($dmPage.items.record)
$dmCursor = $dmPage.next_cursor
while ($dmCursor) {
  $dmPage = (python $dmCli query --repository $dmRepository --instance $dmInstance --kind execution_profiles --limit 1000 --cursor $dmCursor | ConvertFrom-Json).result
  if ($LASTEXITCODE -ne 0 -or $null -eq $dmPage -or $null -eq $dmPage.items) { throw '프로필 다음 쪽 조회 실패: CLI 종료 상태와 반환 본문을 확인한다.' }
  $dmProfileRecords += @($dmPage.items.record)
  $dmCursor = $dmPage.next_cursor
}
$dmProfileRecords | Select-Object id, revision, sha256, role, actor_kind, ai
$dmProfileRecords | ConvertTo-Json -Depth 20
```

쪽이 나뉘면 전건을 회수한다. 조회 cursor는 첫 쪽의 snapshot에 결박되어 다음 쪽도 같은 판본을 읽는다. 사용할 역할·모델·effort·도구·관찰 모드·용량을 본문에서 확인한 뒤 채택할 프로필을 고른다. 같은 역할에 여러 모델 판본이 있으므로 첫 행을 임의 선택하지 않는다. 초기 해석용 프로필은 현행 설정의 역할 등급·모델 선택과 일치하는 `intent_interpretation` 프로필이다. 아래 `$dmChosenIds`는 그 검토를 마친 실제 ID 목록으로 바꾼다.

선택한 ID의 기록이 역할별 허용 참조와 `id`·`revision`·`sha256` 모두 일치하는지도 이번 프로필 조회의 snapshot에서 다시 검사한다. 누락되거나 다른 판본이면 probe와 채택으로 진행하지 않는다.

```powershell
$dmChosenIds = @('EP-실제로-채택한-ID')
$dmSelectedProfiles = @($dmProfileRecords | Where-Object { $_.id -in $dmChosenIds })
if ($dmSelectedProfiles.Count -ne $dmChosenIds.Count) { throw '선택한 프로필 ID가 조회 결과에 모두 있지 않다.' }
$dmProfileSnapshot = $dmPage.snapshot
$dmAllowedReply = python $dmCli read --repository $dmRepository --instance $dmInstance --path research/role_profile_refs/state.json --snapshot $dmProfileSnapshot | ConvertFrom-Json
if ($LASTEXITCODE -ne 0 -or $null -eq $dmAllowedReply.result.text) { throw '현행 역할별 프로필 참조를 읽지 못했다.' }
$dmAllowed = ($dmAllowedReply.result.text | ConvertFrom-Json).record
foreach ($dmProfile in $dmSelectedProfiles) {
  $dmRefs = @($dmAllowed.PSObject.Properties[$dmProfile.role].Value)
  if (@($dmRefs | Where-Object { $_.id -eq $dmProfile.id -and $_.revision -eq $dmProfile.revision -and $_.sha256 -eq $dmProfile.sha256 }).Count -ne 1) {
    throw "현행 역할별 허용 참조와 일치하지 않는 프로필: $($dmProfile.id)"
  }
}
$dmProfileRefs = @($dmSelectedProfiles | Select-Object id, revision, sha256)
$dmAiRefs = @($dmSelectedProfiles | Where-Object actor_kind -eq 'ai' | Select-Object id, revision, sha256)
$dmProbeJson = @{kind='initialization'; operation='probe'; profile_refs=$dmAiRefs} | ConvertTo-Json -Depth 10
[System.IO.File]::WriteAllText((Join-Path $PWD '04-probe.json'), $dmProbeJson, [System.Text.UTF8Encoding]::new($false))
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 04-probe.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind capability_evidence --limit 1000
```

`probe` 호출은 선택 프로필의 어댑터 `describe()`를 실제 실행해 능력 증거를 만든다. 프로필·호스트·CLI 판본과 관측 시각에 결박된 증거이며, `supported/unsupported/unknown`의 범위를 그대로 읽는다. 정적 `profile` 명령이나 시험용 fake CLI의 통과를 모든 실행 능력의 증거로 바꾸지 않는다. 실제 시작 실패의 증거는 단순 help/version 재관측으로 지워지지 않는다.

다음은 검토를 마친 참조로 채택 요청을 만드는 예시다. 이 예시는 초기화 뒤 실행기가 대화와 독립적으로 승인된 연구를 계속하고, 외부 효과는 허용하지 않는 운전이다. `conversation_loss_policy='continue_authorized'`에서는 대화의 attach·heartbeat가 연구의 선행조건이 아니다. 사용자 정지·HOLD·허가 만료와 철회는 계속 적용된다. `external_policy`는 실제 허가에 맞추며, `adopt_default_review_policy`는 이미 채택한 기본 검토 방침을 정확한 현재 판본으로 결박한다.

```powershell
$dmInitialRef = @($dmSelectedProfiles | Where-Object role -eq 'intent_interpretation' | Select-Object id, revision, sha256)
if ($dmInitialRef.Count -ne 1) { throw '초기 해석에 사용할 정확한 프로필 하나를 선택해야 합니다.' }
$dmAdoptJson = @{
  kind='initialization'; operation='adopt'
  adopt_current_config=$true; adopt_current_governance=$true
  conversation_loss_policy='continue_authorized'; external_policy='disabled'
  adopt_default_review_policy=$true
  profile_refs=$dmProfileRefs; initial_profile_ref=$dmInitialRef[0]
  initial_grant_ids=@('GR-initial-01'); research_grant_ids=@('GR-research-01')
} | ConvertTo-Json -Depth 10
[System.IO.File]::WriteAllText((Join-Path $PWD '05-adopt.json'), $dmAdoptJson, [System.Text.UTF8Encoding]::new($false))
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 05-adopt.json
```

각 역할의 실제 배정에도 그 프로필의 현재 능력 증거가 필요하다. 저장된 옛 프로필 전부를 사용할 목록으로 채택할 필요는 없다. 사용할 다른 역할·모델을 빠뜨렸다면 필요한 실제 프로필을 조회·관측·채택한다.

## 5. 신뢰 환경의 실제 증거를 등록하고 전환한다

`setup_lean.py`는 툴체인·Mathlib 캐시와 대표 import 검사를 준비한다. 그 준비 표지만으로 신뢰 manifest의 깨끗한 Mathlib 빌드·검증 증거가 모두 생기지는 않는다. 현재 CLI에는 그 증거 전체를 자동 작성하는 공개 명령이 없다. 환경을 준비한 담당자가 실제 소스·바이너리·빌드 산출·검사기와 검증 기록을 제공해야 한다.

먼저 `setup_lean.py --inspect-only`로 이미 설치된 명령의 도구 정보를 관측한다. 별도 명령이면 `{"lean_command":["실제 실행파일", "고정 인자"]}` 형식의 UTF-8 JSON을 `--command-file`에 지정한다. 이 경로는 설치·다운로드·환경 채택을 수행하지 않는다.

```powershell
$dmObserved = python .agents/skills/do-math/scripts/setup_lean.py --inspect-only | ConvertFrom-Json
```

반환의 `toolchain` 객체 전체를 등록 요청에 복사한다. 이 객체에는 `executable`, `sha256`, `configured_command`, `version`, `version_exit`, `verifier_sha256`, `executables`, `project`가 들어간다. `executable`은 명령의 첫 실행파일이며 Lake를 경유하면 Lake 경로다. `executables`는 명령에 포함된 실행파일의 해시이고 `project`는 관측한 Lake 프로젝트 정보 또는 `null`이다. 버전 조회 실패나 필드 누락을 임의 기본값으로 채우지 않는다. 등록과 실제 형식 검사는 같은 도구 정보 계약을 검사한다.

아래 `06-trust-register.json`의 `toolchain` 자리는 구조를 설명하기 위한 것이다. 실제 요청에서는 위에서 관측한 객체 전체로 교체한다. `<...>` 값은 실제 환경에서 얻어야 하는 미기입 값이며 실행 가능한 해시나 검증 영수증이 아니다. `files`에는 실제로 승인할 환경의 입력과 빌드 산출을 열거한다. 각 역할의 파일은 절대 경로와 원 바이트 SHA-256으로 결박하고 같은 파일을 여러 역할로 중복 등록하지 않는다. `validation.evidence_refs`는 실제 수행한 검증 기록을 가리켜야 한다. 도구 정보 관측은 깨끗한 Mathlib 빌드·검증을 대신하지 않는다.

```json
{
  "operation": "register",
  "toolchain": {
    "executable": "<명령의 첫 실행파일 절대 경로>",
    "sha256": "<그 파일의 SHA-256>",
    "version": "<실측 Lean 판본>",
    "configured_command": ["<실제 실행파일>", "<실제 고정 인자>"],
    "version_exit": 0,
    "verifier_sha256": "<관측한 검사기 SHA-256>",
    "executables": {"<명령에 포함된 실행파일 절대 경로>": "<관측한 SHA-256>"},
    "project": null
  },
  "allowed_axioms": ["propext", "Classical.choice", "Quot.sound"],
  "manifest": {
    "command": ["<configured_command와 같은 실행파일>", "<같은 고정 인자>"],
    "foundation_profile": {
      "allowed_axioms": ["Classical.choice", "Quot.sound", "propext"],
      "forbidden": ["sorryAx", "Lean.trustCompiler", "additional_axioms"]
    },
    "files": [
      {"role": "lean_binary", "path": "<실제 절대 경로>", "sha256": "<실측 SHA-256>"},
      {"role": "lean_source", "path": "<실제 절대 경로>", "sha256": "<실측 SHA-256>"},
      {"role": "lake_binary", "path": "<실제 절대 경로>", "sha256": "<실측 SHA-256>"},
      {"role": "mathlib_source", "path": "<실제 절대 경로>", "sha256": "<실측 SHA-256>"},
      {"role": "mathlib_build", "path": "<실제 절대 경로>", "sha256": "<실측 SHA-256>"},
      {"role": "checker", "path": "<실제 절대 경로>", "sha256": "<실측 SHA-256>"}
    ],
    "build_kind": "clean",
    "validation": {"status": "verified", "evidence_refs": ["<실제 깨끗한 빌드와 검증의 보존 기록>"]}
  }
}
```

`clean/verified`는 실제 빌드와 검증이 그 결과일 때만 쓴다. 아직 증거가 없으면 등록 요청을 만들었다는 이유로 다음 단계로 진행하지 않는다. 파일 해시는 예를 들어 `Get-FileHash -Algorithm SHA256 -LiteralPath '<실제 경로>'`로 얻을 수 있지만, 해시 계산은 빌드·검증을 대신하지 않는다.

```powershell
python $dmCli trust --repository $dmRepository --instance $dmInstance --file 06-trust-register.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind trust-environment --limit 1000
```

등록된 환경의 실제 ID를 `07-trust-transition.json`에 넣는다.

```json
{"operation":"transition","env_id":"TE-실제-조회-ID"}
```

```powershell
python $dmCli trust --repository $dmRepository --instance $dmInstance --file 07-trust-transition.json
python $dmCli run --repository $dmRepository --instance $dmInstance --max-steps 1
python $dmCli status --repository $dmRepository --instance $dmInstance --json
```

`max-steps=1`은 새 action 시작 수의 상한이다. 다음 기계·해석 action이 남아 있으면 같은 명령으로 이어 간다. 환경 전환 중인 기존 결과는 재검사와 필요한 독립 의미 대조를 마쳐야 한다. 해당 `run`이 초기화의 모든 단계를 끝낸다고 가정하지 않는다.

## 6. 최초 해석·독립 검사·실제 적용을 확인한다

초기 원입력의 해석·독립 검사가 기술적 실행 실패, 제출 처리 실패 또는 실행기 소실로 끝나면 실패 실행과 원입력을 보존하고 유지보수 진단을 요청한다. 진단은 현재 초기화 권한이 허용할 때만 실행된다. 수락된 `retry` 판정의 실행이 종료되면 중앙은 같은 원입력·활동의 후속을 한 번 처리한다. 필요한 권한이나 자료가 없으면 그 부족과 다음 담당자를 남기고 기다린다.

운전자가 원인을 해소한 뒤에는 보류된 action ID를 `request --retry-action AC-... --request-id UC-...`에 지정해 명시적으로 재시도할 수도 있다. 실행기는 자동 진단 후속과 공개 재시도 모두에서 전 실행의 로컬 종료·예약 회수, 원입력·활동 계보, 현재 초기 운영 권한·채택 프로필을 확인한다. 일반 `resume`은 이 실패를 재시도하지 않는다. 정상 종료한 native 최종 응답이 정확한 원문·실행 근거와 함께 보존돼 있으면 그 응답을 중앙 접수·편입에 재사용한다. 이 경우 새 모델 실행을 만들지 않으며 원 실행의 종료 시각·원 결과 참조·실패 이력을 보존한다. 재사용 조건을 충족하는 정상 응답이 없으면 같은 활동을 잇는 새 실행을 배정한다. 기존 봉인 후보를 다른 final로 대체하거나 오류·중단 응답을 정상 응답으로 취급하지 않는다. 새 입력으로 원문을 대체하거나 인스턴스를 다시 만들 필요는 없다.

초기 프로필과 운영 grant가 채택되고 능력 관문을 통과하면 초기 원입력의 `intent_interpretation`이 열린다. `run`이 해석과 별도 검사 실행을 처리한다. 의도 해석 AI는 원문 범위를 `import_units`에 전건 배정하며 각 단위의 payload를 해당 종류의 저장·적용 영역에 연결한다. 이 영역을 payload의 소유자라고 부르며, 헌장·권한·설정 등 각 종류의 적용을 담당한다. 질문이 남아 있어도 확인 가능한 범위의 독립 검사는 생략하지 않는다.

차단 질문이 남은 해석은 그 질문의 답변을 기다리며 같은 원문으로 반복 실행하지 않는다. 답변이 검사·승인·적용되어 해당 차단 질문이 모두 해소되면, 원문과 해석 계보를 유지한 재해석에서 답변을 반영한다.

정상 종료한 최종 응답의 JSON·출력 형식 오류는 원문과 중앙 검사 결과를 보존해 같은 의도 해석 역할의 제한된 수리로 연결한다. 수리가 한도에 이르면 초기화 권한이 허용하는 유지보수가 원 실패를 진단한다. 유지보수의 `retry` 판정은 같은 의무에 한 번의 후속 수리를 열고, `wait` 또는 후속 수리의 재실패는 원인과 소유자를 보존해 기다린다. 새 권한을 만들거나 초기화에서 허용하지 않는 운영 점검 역할을 실행하지 않는다. 응답을 정상 접수한 사실만으로 사용자 승인·답변 대기를 해소하지 않는다.

질문에는 `input --text` 또는 `input --file`과 실제 `--responds-to QU-ID`로 답한다. 해당 답의 수입·독립 검사 뒤 해소된 질문만 닫힌다. 답변은 별도의 grant를 자동 생성하지 않는다.

```powershell
python $dmCli input --repository $dmRepository --instance $dmInstance --file actual-answer.txt --responds-to QU-실제-질문-ID
python $dmCli run --repository $dmRepository --instance $dmInstance --max-steps 1
```

독립 검사가 승인해도 사용자 권한이 필요한 payload의 적용은 별도다. 검사된 수입 기록에서 `id`, `sha256`, `check.sha256`, 비어 있지 않은 payload 전건의 `unit_id`와 정규 의미 해시를 확인한다. 이미 승인된 기록과 동일한 의미·권한이면 그 승인 근거를 재사용한다. 새로운 목표·허가를 예시나 모델의 추천으로 승인하지 않는다.

현행 공개 CLI는 승인 JSON을 한 번 읽은 payload와 같은 정확한 원문으로 control에 전달한다. `decision`의 `kind=import_approval`은 이 경로에서 `apply_import_control`로 간다. 먼저 같은 snapshot에서 검사된 수입을 조회하고 정확한 record를 읽는다.

```powershell
python $dmCli query --repository $dmRepository --instance $dmInstance --kind intent_imports --limit 1000
python $dmCli read --repository $dmRepository --instance $dmInstance --snapshot OID-위-조회-응답의-snapshot --id IM-실제-조회-ID
```

읽은 record의 `id`, `sha256`, `check.sha256`, 비어 있지 않은 모든 unit ID와 각 payload의 canonical hash로 승인 파일을 만든다. 이 파일은 승인 내용을 표시하는 보조 입력이 아니라 보존되는 사용자 승인 원문이다.

```json
{
  "kind": "import_approval",
  "import_id": "IM-실제-조회-ID",
  "bundle_sha256": "검사된-묶음-해시",
  "check_sha256": "검사-해시",
  "unit_hashes": {
    "IU-실제-단위-ID": "그-payload의-canonical-hash"
  }
}
```

```powershell
python $dmCli decision --repository $dmRepository --instance $dmInstance --file 08-import-approval.json
python $dmCli query --repository $dmRepository --instance $dmInstance --kind intent_imports --limit 1000
python $dmCli read --repository $dmRepository --instance $dmInstance --snapshot OID-위-조회-응답의-snapshot --id IM-실제-조회-ID
python $dmCli status --repository $dmRepository --instance $dmInstance --json
```

적용기는 사용자 출처, 승인 종류, 수입 묶음·검사·unit 해시의 정확한 일치와 비어 있지 않은 승인 원문을 확인한 뒤 그 봉인 묶음만 적용한다. 적용 뒤 수입 record와 그 안의 검사·적용 결과를 위 조회로 읽는다. 이를 위해 초기 원문 해석이나 독립 검사를 다시 열지 않는다. 반대로 하나라도 달라지거나 원문이 없으면 적용되지 않는다. 해시를 계산하거나 기록에서 회수하는 행위는 사용자 결정이 아니다. 내부 함수를 직접 호출하거나 저장 JSON을 편집해 관문을 우회하지 않는다.

정확한 원문 의미에도 같은 확인이 필요하다. 초기 입력은 `immutable_input.text`의 코드 포인트열과 그 UTF-8 바이트의 해시·크기로 하나만 보존하며 NFC 사본이나 Base64 중복 원문을 만들지 않는다. 이 보존만으로 초기 해석·원문 피복·독립 검사·승인이 그 원문을 실제로 읽었다고 보증할 수는 없다. `user_request.text`로 제공된 값과 각 소비자가 사용한 원문을 대조해, 코드 포인트 차이가 뜻을 바꾸는 입력도 같은 원문에 결박됐는지 확인한다.

완료는 `active_trust_environment`의 존재 하나가 아니라 초기화 관문 전건과 실제 수입 적용 기록으로 판단한다. 미완료 항목은 lifecycle 기록·가용성·대기 요청에서 확인한다. 전건을 통과한 활성화가 lifecycle을 `active`, 실행 상태를 `ready`로 바꾸며, 현재 지식 기록이 있으면 최초 연구 계획을, 없으면 최초 후보 준비를 연다. 기록의 존재는 `query --kind knowledge`로 확인한다. 이 분기는 기록의 검증 통과를 뜻하지 않으며, 수학적 사용 가능성은 해당 기록의 형식 결과·동일성 판정·현재성으로 따로 판단한다. 초기화 중 앞서 등록한 grant 자체는 이 작업을 열지 않는다.

일반적인 독립 실행 인계 경로에서는 README의 [초기화 완료 단계](../README.md#activate-instance)에 있는 대화 소실 정책 조건까지 확인하고, [독립 실행 시작과 관측](../README.md#start-engine)으로 돌아간다. 수동 운영으로 정한 인스턴스는 [직접 전진·수동 운전](../README.md#manual-run)으로 이어 간다. 초기화 중 사용한 `run --max-steps`는 필요한 기계·의도 해석 작업을 처리하는 제한 실행이며, 각 반환에서 실제 처리 범위와 적용 결과를 확인한다.
