# Operating a research instance

This guide continues the operator's entry point, [SKILL.md](../SKILL.md). Use it when preparing an instance or acting on an existing run.

## Fix the root in words and in Lean

An instance is created from two statements of the same proposition. The root file states it in words. The Lean statement of the root, together with the Lean definitions of the objects it speaks of, states it in the form in which the research will work.

The Lean statement carries more weight than a translation would. Every session receives what it takes on as Lean statements over these definitions, and every element the research adds is built on them. The instance is complete when the fixed Lean statement, or its negation, is settled by a formal proof, and no later step judges whether the theorem that was proved corresponds to what the user meant, because the theorem to be proved is the fixed statement itself. You and the user therefore establish that correspondence here, before the research starts. Lean checks only that the definitions and the statement are well formed, so a statement that compiles can still say something other than what the user means.

You do the work of the subsections below together with the user. Ask the user whenever a choice changes what the proposition asserts, such as where an index starts, which boundary cases are included, or which of two definitions of an object is meant.

### The root file

The root file is a UTF-8 text file that contains the mathematical proposition in words, with its objects, assumptions, domains and quantifiers defined. When the user's material gives values for small cases, such as the first rows of a table, include them; they are what the Lean definitions will be checked against. A proof of either that proposition or its negation settles the root.

Everything inside an instance is written in English, whatever language the user speaks to you in: the root file, the Lean files and their records, the inputs, any questions you publish, and everything the sessions write.

### The canon folder

Prepare a folder, outside the new instance directory, that holds the beginning of the instance's Lean library. `init` copies it into the instance as the first state of the canon.

```text
<canon folder>/
  lean/<Library>/Defs.lean     the definitions of the objects the proposition speaks of
  lean/<Library>/Root.lean     the root statement, importing the definitions
  records/<name path>.md       one record for each declaration, at the path that follows its name
  bibliography.bib             optional: the sources of definitions or statements taken from the literature
```

`<Library>` is the one top-level module name under which every module of this instance will live, the sessions' later modules included. Choose a name for the mathematics, for example `Parking`. `init` refuses a folder whose modules do not share one top-level name. The name must differ from `Init`, `Lean`, `Std`, `Lake` and from the first component of any library the files import, such as `Mathlib`, because the Lean broker refuses a module that would shadow one of those. The broker also accepts only module paths whose components, the library name and every folder and file name under it, consist of ASCII letters, digits and `_` and do not begin with a digit. The file names `Defs.lean` and `Root.lean` are examples.

Put the definitions in one module and the root statement in a module of its own that imports it, because of how a proof of the root will later enter. A proof replaces the body of the root's declaration where it stands, and the runner adds to the header of the root's module the imports that the proof needs. Those imports are modules that sessions add during the research, and they import the definitions. If the definitions lived in the root's module, the later modules would import the root's module and it would have to import them, a cycle that Lean does not allow, and the proof would have to enter as a separate declaration beside the root. So the root's module holds the root statement and nothing that later work will use. When the objects are many, `init` accepts several definition modules under the same library name.

Every later module imports the definitions, so every compile of the instance loads whatever your definition modules import. Work out which library modules your definitions and their checks use, and import those and no others. [Lean](lean.md) explains, under Writing Lean that compiles cheaply, how an import is inherited by every module that reaches it and what `import Mathlib` or `import Mathlib.Tactic` costs in a module that everything imports.

The root's module and the modules of the instance that it imports, directly or through one another, are also what a package of the finished research gives the registry as its challenge: the finalize command joins them, as the first commit of the instance holds them, into the one file `Challenge.lean`. The registry accepts that file with at most 1,000 lines and 100 KiB, and with imports under `Init`, `Lean`, `Std` and `Mathlib` only; an import of another package counts also where Mathlib depends on that package. Files that exceed this still give a complete package, and the registry will not accept it as it is. Nothing after `init` can bring them within these limits, so where the user may want to submit the result, keep them there now. Checks that take many lines can stand in a module of their own that the root's module does not import, which is no part of that file.

The modules that the root's module imports, directly or through one another, are the definition modules, and they stay as they were posed. During the research every candidate that would change the file of one of them is refused, when it is prepared and again when the runner publishes it. The finalize command requires, at each of its steps that writes Lean, every one of them to be, byte for byte, the file of the first commit, and it requires every theorem of the package to be proved. A theorem that you supply with its proof left open, or with a proof written in its record, therefore does not go into one of those modules. The research cannot prove it in Lean where it stands, so whether it proves it elsewhere, as a separate declaration, or not at all, the theorem stays open in a module that the package keeps. The finished research then cannot be packaged, and nothing after `init` can undo it. Put such a theorem into a module that imports the definitions and that the root's module does not import.

### Lean conventions of the canon

The files you write follow the conventions of every file of the canon, the same ones the sessions follow when they add modules. [The canon](canon.md) describes them for the sessions. What you need is this.

**Each file is written in Lean's module system.** It begins with the word `module`, imports with `public import <module>`, and puts its declarations under `@[expose] public section`. In a `module` file the statement of a theorem is part of the public compiled output and its proof is not, which is what later lets a proof be replaced without recompiling every module that uses the statement. `init` does not check these three things. A file that omits them can still compile by itself, and the fault appears later, when a session's module tries to import it, or imports it and cannot see a declaration or unfold a definition.

**A statement is a `theorem`.** The root is written as a theorem whose proof is left open with `by sorry`:

```lean
theorem <name> <binders> : <the proposition> := by
  sorry
```

The root has no proof at creation; supplying one is the research. Its standing is then "no proof", and the frontier of the new instance is the root alone. `init` refuses a root declaration that is not a theorem, and one that already has a proof, whether in Lean or as a `## Proof` in its record. A theorem you supply with the canon to check a definition is different: its Lean proof is complete, Lean checks it at `init`, and it stands as accepted from the start without a review.

**No `axiom`, and no `sorry` inside a definition.** `init` refuses both. An axiom would add an assumption to everything built on it, and a definition left open has no meaning for a statement to speak about. An object whose definition you cannot yet write completely is a question to settle with the user before the instance is created.

**Every declaration you write is an element and needs a record.** That covers definitions, structures and inductive types, theorems, and instances. A declaration marked `private`, and the auxiliary declarations Lean generates, such as the fields and constructor of a structure, are not elements and need no record. When a record is missing, `init` names the declaration and the path it expects. The names it reports may include one that Lean chose itself, as it does for an instance written without a name or for a notation; write the record under the reported name.

The following pair of files shows the shape. It is an example for a small proposition, and nothing in it but the header lines and the form of the root is prescribed.

```lean
module

@[expose] public section

namespace OddSum

/-- The sum of the first `n` odd numbers. -/
def oddSum : Nat → Nat
  | 0 => 0
  | n + 1 => oddSum n + (2 * n + 1)

example : oddSum 3 = 9 := by decide
example : oddSum 4 = 16 := by decide

end OddSum
```

```lean
module

public import OddSum.Defs

@[expose] public section

namespace OddSum

/-- The sum of the first `n` odd numbers is the square of `n`. -/
theorem sum_eq_square (n : Nat) : oddSum n = n * n := by
  sorry

end OddSum
```

The first file is `lean/OddSum/Defs.lean` and the second `lean/OddSum/Root.lean`. The root declaration is `OddSum.sum_eq_square`, and that full name is what `--root-declaration` takes. A file that needs the imported library adds its `public import` lines after `module`.

### A record for each declaration

Sessions read the records you write whenever they meet the root or its objects, and views that pass over many elements show the self-description as the only prose of each.

The record of the declaration `A.B.c` is the file `records/A/B/c.md`. A name component that Windows cannot use as a file name is encoded, for example `Aux` as `Aux%`; when in doubt, the path `init` reports for a missing record is the right one. `init` also refuses a record that belongs to no declaration.

A record begins with a header between two lines of `---`, followed by sections with exactly these top-level headings, each at most once and in any order. Deeper headings are free.

| Part | Content |
|---|---|
| `weight` (header, required) | `unit` or `step`. A unit is something a reader of the proof's structure would name; a step is a piece inside one proof. The dependency map draws units and folds steps, and the paper numbers units and absorbs steps. The root is a unit. An object the proposition is about is usually a unit, and an auxiliary definition usually a step. |
| `short` (header) | A short name. The frontier shows it for the element in place of the description. |
| `source` (header) | The key of an entry in `bibliography.bib`, for a definition or a result taken from the literature. |
| `## Description` (required) | The self-description: what this element is, in a line or two. |
| `## Statement` | The statement, or the definition, in natural language. For the root this is the proposition of the root file. |
| `## Explanation` | What the statement says about the object, why the definition was chosen, and how the Lean form corresponds to the mathematical one: indices that start from zero, a normalization, a coercion, a convention at a boundary. |
| `## Literature` | For something taken from the literature: the source, how much of it was read, and where the statement stands in what was read. |

The header keys `proves` and `refutes` and the section `## Proof` exist for elements the research adds later, and `init` reads them if they are present. Leave `proves` and `refutes` out, and write no `## Proof` in the root's record: `init` refuses a root whose record has a nonempty one, as a root that already has a proof.

The record of the definition in the example above could read as follows. It is an example of the form.

```markdown
---
weight: unit
short: sum of the first n odd numbers
---
## Description

The sum of the first n odd numbers, defined by recursion on n.

## Statement

For a natural number $n$, $\operatorname{oddSum}(n) = 1 + 3 + \dots + (2n - 1)$, and $\operatorname{oddSum}(0) = 0$.

## Explanation

The recursion adds the odd number $2n + 1$ at the step from $n$ to $n + 1$, so the argument of the Lean function counts how many odd numbers have been added. The values 9 and 16 that the root file gives for $n = 3$ and $n = 4$ are checked by compilation in the module of the definition.
```

Write the explanation with care. It is where a later session learns how to read the Lean form, and where the paper later finds the conventions that separate the Lean statement from the statement in words.

Where the proposition comes from the literature, as a published conjecture or an open problem does, put that into the canon folder as well. Give the work that poses it, and each earlier result on it that the user's material names, an entry in `bibliography.bib`, and say in the `## Literature` part of the root's record, citing each work by its key in square brackets, what the work has of the proposition and how much of it was read; write only what the user's material or your own reading of the work shows. A work that poses the proposition without proving it does not go under `source` in the root's record: that key marks a result the work already has, and the paper cites such a statement in the place of proving it. The paper and the package that are later made from the canon say of earlier work only what the root file and the canon hold, and no step after the research looks for where the problem comes from, so what is known now and not entered is missing from both unless a session reads and enters it during the research.

### Evaluate the definitions on known values

A definition that compiles can still denote a different object from the one intended. Lean's functions are total, so conventions fill in what the mathematics leaves undefined, and a small slip changes the object without causing an error. Subtraction of natural numbers stops at zero, division by zero returns zero, `Finset.range n` runs from 0 to n - 1, and a recursion can start one index early or late. These are examples of the kind of difference to look for, and the definitions of a particular problem have their own.

The check against known values is the means you have. The user's material usually carries values for small cases. Write each of them into the Lean files as something the compiler must prove, as the example above does with `example : oddSum 3 = 9 := by decide`. `init` shows no output of a compile that succeeds, so a command that only prints a value, such as `#eval`, confirms nothing; the check has to be a declaration whose failure fails the compile. Which proof closes such a check depends on how the definition is written.

A check written as an `example` is compiled and then discarded: it is not an element, needs no record, and leaves nothing in the canon. One written as a named theorem with a complete proof is an element: it needs a record, and a session that later traverses what the canon knows about the definition finds the checked value there. Put the checks in the module of the definitions or in a module of their own that imports it, and keep them out of the root's module.

The root's statement needs a check of its own, because a statement over correct definitions can still say something other than the proposition. A quantifier can run over one case too many or too few, an index can begin at zero where the proposition begins at one, a hypothesis that nothing satisfies makes the statement empty, and a coercion can change the type in which an inequality is read. These too are examples of the kind of difference to look for. Where the user's material says that the proposition holds in particular small cases, write the root's statement at each of those cases as an `example` that the compiler must prove; for the root of the example above, `example : oddSum 3 = 3 * 3 := by decide` is such a case. Where the root has hypotheses, write an `example` that exhibits one object satisfying all of them. These checks go where the value checks go, and since you write each case by hand, show it to the user beside the root's statement.

Agreement on these values and cases is evidence that the definitions denote the intended objects and that the statement says the proposition. It is not a proof of either, and what was checked says nothing about cases unlike it. Say this to the user as it is, with the list of the values and the cases that were checked.

### Compile, and have the user confirm

`init` is the compile. Nothing in do-math compiles a canon folder before an instance exists, so you create the instance, as "Create and start" below describes, and read what `init` reports. It compiles the library through a Lean broker that it starts and stops, extracts the structural index, and refuses the canon when a module does not compile, when a value check fails, or when one of the conditions above is not met. A refusal names the module with the end of Lean's output, or the declaration and the condition. Correct the files and run `init` again on a new path.

When `init` has succeeded, the instance exists and nothing is running. Before the user reads what was fixed, have the Lean statement read by a reader who did not write it and was not told what it is meant to say. The explanation you give the user is the explanation of the one who wrote the statement, so a misreading of your own passes into it unnoticed, and the checks on known values and small cases show no difference that lies outside them, such as the order of two quantifiers or a range the cases do not reach.

Start a sub-agent and give it the files under `lean/` of the canon folder and nothing else: not the root file, not the records, not the conversation with the user, not your explanation, and no word in the request about what the proposition is. Ask it to say in words what the root declaration states, with its objects as their definitions give them and with its assumptions, domains and quantifiers. Those files carry doc comments and names that say what was intended, so the reading serves only where it comes from the declarations themselves. Lay what the sub-agent wrote beside the root statement in words, and mark each place where the two differ. If your CLI cannot start a sub-agent, this reading is not made, and you tell the user that it was not.

Before you start the runner, have the user read what was fixed and this reading:

- the root statement in words, from `root.md`;
- the source text of the root declaration and of every definition it uses, directly or through other definitions, from `canon/lean/`;
- the root statement as Lean prints it after elaboration, which is the `statement` of the root's entry in `canon/index.json`. The printed form shows the types Lean inferred and the coercions it inserted, which the source text does not;
- the values on which the definitions were checked and the cases in which the root's statement was checked, and that nothing beyond them was checked;
- what the sub-agent wrote, beside the root statement in words, with each place where the two differ, also one that you take for a misreading of the sub-agent's; or, where no sub-agent could be started, that this reading was not made.

Explain to the user how the Lean statement reads, in the user's language, binder by binder and hypothesis by hypothesis, and point out each place where the Lean form differs from the usual mathematical notation. The user's confirmation is part of fixing the root, and it is the only judgment of meaning the Lean statement will receive from the person whose proposition it is. Do not start the runner before the user has confirmed.

If the user asks for a change, change the canon folder and create a new instance on a new path. An instance that was created and never started holds nothing but the copied files and can be deleted.

### If the Lean statement is later found not to say what was meant

The runner refuses to run an instance whose root file or whose root statement in Lean has changed. If the research or the user later finds that the Lean statement does not say what was meant, the proposition has changed, and a new instance is needed with the corrected statement. Tell the user what was found and what the existing instance has in fact been working on. Results of the old instance remain true of the statements they were proved for.

A definition that proves inconvenient is a different matter and needs nothing from you. A session introduces another representation as a new definition and establishes, as an element, that the two agree.

## Prepare the settings and environment

The runner runs on Windows and on Linux only, and it needs Python 3.12 or later, Git, authenticated Codex and/or Claude native executables, and the Lean environment the problem needs. Confirm each of these, with the actual paths of the native CLIs and their existing authentication, and use the installations and tools that are available. The default models for attempt, explore, formalizer and organizer are `codex/gpt-6.1-sol` at `xhigh`, followed by `claude/opus` at `xhigh`; for peer and review the order is reversed, so that the candidate and its review come from a different model than the producers. These are ordered alternatives for each role. Where only one of the two CLIs is installed, give that CLI's models alone, in `models` and in the peer and review lists of `roles` that the example below shows, because a session launched on an absent CLI fails before its job goes to the next model in the list. Defaults are eight concurrent AI sessions, attempt and exploration launches at least three minutes apart from one another, exploration requested at every attempt launch, and organization after four published changes.

An example settings file is:

Replace the executable paths with the actual installations. A role-specific ordered model list under `roles` replaces the common list for that role. `roles` is one setting, so a settings file that gives it replaces the default lists for peer and review, which the example shows, and a role that it omits uses the common list. An omitted setting receives its default. An unrecognized key, such as a misspelling or a setting carried over from the earlier do-math runtime, is rejected by name, because ignoring it would leave the default in force without notice. The runner checks structure; actual login and model availability are confirmed by execution. `init` writes the complete configuration, with defaults filled in, to the instance's own `settings.json`, and that file is the configuration in force afterwards. A running runner rereads it when it changes and uses the new values for its later scheduling and launches; a session already launched keeps the settings saved at its launch. An edit the runner rejects leaves its last valid settings in force and appears as `settings_error` in the runner state that `status` returns.

`lean.allowed_axioms` is the list that the axioms of a statement are held against; "What makes a statement formal" below describes it.

The `lean` block has to be right before `init`, because `init` compiles the canon folder with it. To use Mathlib, configure `lean.command` as `["<lake executable>", "env", "lean"]`, its version command with `"--version"` appended, and `cwd` as a Lake project that requires Mathlib: a folder whose `lakefile.toml` names Mathlib in a `[[require]]` block, so that Lake keeps Mathlib under that folder's `.lake/packages/mathlib/`. A checkout of Mathlib itself does not serve as `cwd`: the sessions are told to read the imported library's sources under `.lake/packages/` of that folder, and the finalize command takes the requirements of the package from that `lakefile.toml`, as "When the command applies" below says. Supply any necessary PATH value through `lean.env`; JSON does not expand shell variables. The broker compiles the modules of the instance, each after the modules of the instance that it imports. It does not build the imported library, so Mathlib has to be built in that project before `init`. [The Lean broker](lean-broker.md) explains the resource settings, and [Lean](lean.md) explains estimates.

### When compiles wait for memory on Windows

All Lean compilation of an instance goes through its broker, and compiles carry much of the work: sessions compile what they state, a peer's candidate is built before it is frozen, review builds it again, and every publication that changes a Lean file is a build of the library. How many compiles can run at once therefore bears on how fast the research moves.

On Windows, what limits that number is the commit limit, and the user can raise it. Windows keeps an account, the commit charge, of the memory it has promised to processes. The limit of that account is physical memory plus the page file, and an allocation beyond it fails even while physical memory is free. Whatever its own memory and thread budgets allow, the broker starts a compile only if the machine's remaining commit, less what the compile is certain to take, would be at least `lean.min_free_memory_mb`. A Lean process is charged far more commit than the memory it uses: Lean maps the compiled library into memory, and Windows appears to charge the whole size mapped, although most of those pages are shared between processes or never touched. A process was measured at a commit charge of about two and a half times the physical memory it touched, and a compile that imports the analysis part of Mathlib holds two to four gigabytes for the import alone. On a machine with sixteen gigabytes of memory and sixteen sessions running, a few gigabytes of the commit limit were free, and compiles ran one at a time while physical memory was free, the median compile waiting in the queue several times as long as it ran.

Enlarging the page file raises the commit limit and would let the broker admit several compiles at once. When you see this situation, recommend it to the user and give the reason. The sign is compiles listed under `lean.queued` in `status`, with `waiting_for` null, while no compile is running and physical memory is not exhausted; Windows shows the commit charge and its limit as "Committed" in the memory view of Task Manager. While one compile is running, a second can also be held back by the broker's own memory or thread budget, and the `reserve` of each queued compile in `status` together with `lean.config` shows which; [The Lean broker](lean-broker.md) explains those budgets. The page file is a setting of the user's machine, so the choice and the size are the user's, and you do not change it yourself. The effect on compiles that import Mathlib has not been measured.

### External tools

Only the external tools configured in the instance's `mcp_servers` enter worker sessions. `mcp_servers` maps server names to configuration objects. A local server uses `command`, `args`, and optional `env`; an HTTP server uses `url` and the provider's supported transport configuration. Further tools that the research needs are added there; personal instructions and hooks do not supply them. Authentication remains with the installed CLIs. Worker launches disable personal/project instruction discovery, skills and memories, and no personal or project hook runs in a worker; all do-math guides and user conditions are supplied explicitly. The one hook a Claude worker runs is do-math's own, which "Context, continuation and acceptance settings" below describes.

`mcp_servers` governs the servers attached to a session and nothing else. A worker also has the tools built into its CLI, such as its shell, and the runner launches a Codex worker with that CLI's web search enabled. `"mcp_servers": {}` therefore removes the attached servers and does not cut a session off from the network. The launch does not confine what a worker does with those tools either. A worker runs unattended, so the runner launches a Claude worker with `--dangerously-skip-permissions` and a Codex worker with `approval_policy="never"` and `--sandbox danger-full-access`: the worker runs commands and changes files without asking for approval, wherever the account that runs the runner can. The sessions of the paper command and of the finalize pipeline are launched with the same options.

The default settings attach scholarly-mcp, the literature server, to every instance. The session guides tell sessions to look actively for earlier work and cite it, and this server is the tool those guides direct them to. The default is the server that the repository holding this skill keeps under `services/scholarly-mcp`, run by the Python of that folder's own environment and started with the `--public-only` option. The example settings file above shows the entry for a repository at `C:/repository` on Windows.

The runner computes the two paths from the place where the skill is installed. `init` writes this entry into the instance's `settings.json` when it is given no settings file, or a settings file without an `mcp_servers` key. A settings file that has the key replaces the default with what it gives. To use a server installed elsewhere, or to attach further servers, write the `scholarly` entry there together with the others. `init` refuses, before it creates anything, when the `command` of a server is not found, because a CLI whose configured server does not start begins the turn without it and raises no error. For the default server this means that its Python environment is missing, and the `README.md` under `services/scholarly-mcp` gives the commands that create it.

The reason for `--public-only` is that every session starts its own copy of the server. Without the option, each copy logs in separately to the institutional account that the server uses for subscription sources, so an instance of sixteen sessions could hold dozens of logins on that account at once. Whether the institution or a publisher would treat that as misuse is not known, and if they did, the consequence would fall on the account and not only on this research. With the option, the server creates no login and opens no browser. It serves about twenty sources that are reached through public interfaces, among them zbMATH, arXiv, Crossref, OpenAlex and Semantic Scholar, and it refuses requests for the others. Sessions therefore cannot search MathSciNet or retrieve full texts that require a subscription; their literature guide tells them to record such a paper as not read.

The check that `init` makes finds a missing command and nothing more, and it is made at `init` alone: a later change of `mcp_servers` in the instance's `settings.json` is accepted when its form is valid, whether or not the `command` of a server is found. Before `start`, and after such a change, confirm that the server answers as configured. In the server's folder, run `<its python> -m unittest tests.test_mcp.MCPContract.test_public_only_serves_the_login_free_sources_and_refuses_the_rest`. The test starts the server over standard input and output, as a session does, lists its sources and checks that a subscription source is refused; it contacts no external service. If the instance is to run without the server, tell the user so and why.

One copy of the server answers about seven seconds after it starts and sixteen started together took up to forty-one seconds, while the Claude CLI waits about thirty seconds for a configured server and then begins the turn without it, so the runner sets `MCP_TIMEOUT` to 180 seconds in every worker's environment. All copies send their requests from one network address, so a public interface that limits requests per address answers with the code `rate_limited` more often than it would for one copy; the sessions are told that this answer does not mean the work is absent. Codex called a configured server's tool and received the result under the full-access option the runner gives it, and refused such calls under a read-only sandbox. It does not wait for a configured server before it begins a turn: one that needed twenty seconds to start became available later in the same turn, and a slower start was not tried. When an instance runs sessions on Codex, read one session's stream after launch for `mcp_tool_call` items and their results, and tell the user if none succeeds.

### Context, continuation and acceptance settings

Every worker role requests a 1,000,000-token context window, including role-specific model choices and fallback launches. Codex receives explicit `model_context_window=1000000` and `model_auto_compact_token_limit=950000` overrides, so isolation from the operator's configuration does not discard the context setting. Claude receives the model's `[1m]` variant and `CLAUDE_CODE_MAX_OUTPUT_TOKENS=128000`, twice the CLI's default output cap for one response. A Claude worker that receives messages, which the next paragraph describes, is launched with `DISABLE_AUTO_COMPACT=1`: the CLI does not replace its conversation with a summary, and its host tells it when the conversation is nearly full. Every other Claude session, among them the sessions of the paper command and of the finalize pipeline, receives `CLAUDE_CODE_AUTO_COMPACT_WINDOW=950000`, because a compaction is the only way such a session has past the limit of its window. An inherited setting that disables 1M context, overrides the compaction percentage or window, or switches compaction off is removed from the worker environment. Existing `[1m]` suffixes are retained once, and `[200k]` is replaced. These are launch requests: the selected model, account and CLI determine actual capacity and access. The Claude selector follows its [model configuration interface](https://code.claude.com/docs/en/model-config#extended-context).

A message can be sent into a Claude worker while one of its turns is running. For a session it launches on Claude the runner makes the folder `messages/` in the session folder, and the worker's settings file then names one hook where it otherwise carries the key that disables hooks: the CLI starts the installed `runtime/message_hook.py` after each batch of the session's tool calls. That program hands the session the messages that wait in `messages/`, oldest first and each under a line that names its sender, the runner or the operator, and moves them to `messages/delivered/`. The CLI passes on what a hook returns whole only up to 10,000 characters: a longer text it writes to a file, and the session receives the path of that file with the first 2,000 characters and is not asked to read the rest. The program therefore hands over after one batch only the waiting messages that fit within that size together, and the others after a later batch. A single message that exceeds that size together with the line that names its sender still reaches the session in the shortened form, so keep a message within 9,900 characters. The CLI's stream does not show what a hook returned, so `messages/delivered/` is where you read what a session was told; a file still in `messages/` has not been handed over. A message reaches the session together with the results of a batch of tool calls, so one that is sent during a long stretch of reasoning or after the last tool call of a turn waits until the next batch, and a sub-agent of the session is handed none. The worker's command keeps `--setting-sources ''`, which is what keeps the hooks of your project and account out of the worker. The hook program is opened afresh at each start; while it cannot be opened, the messages wait and the session works on. Three kinds of session have no `messages/` and run no such hook: a Codex worker, which is launched with hooks disabled; a session of the paper command or of the finalize pipeline; and a session launched by a runner that was started before the installation contained this hook. `message`, under Commands, refuses such a session.

The session host sends one message itself. While a turn runs, it reads from the turn's stream how many tokens of context each request of the session itself held, leaving out the requests of sub-agents, and when a request has held 800,000 or more it sends the session a message, once in the life of the session. The message states that size and the size of the window, and that at the limit the CLI refuses the next request and the turn ends there. It is a request to decide the ending: it carries a request ID, which the host also writes to `end-request.json`, and the session answers it in the same turn. A session whose work is done ends as its role ends. A session whose work is to go on brings its report to the state from which a new session can continue, in `work/report.md` for a peer, a review and an organizer, and answers with the basis `handed_over`. What the host and the runner do then is under "Session hosts and continuation turns" below.

A Claude worker also receives `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=7200000`, two hours. Worker sessions run the CLI in print mode, in which the CLI can stop background tasks, such as sub-agents, that are still running after the main agent's turn has ended; the message it writes then names this variable as the limit, with a default of ten minutes. In the sessions of two instances nearly all of these stops came when sub-agents were the only background work the main agent had left, while a main agent that had left a shell command of its own running was not stopped, for as long as 45 minutes. The stops ended reviews, and most failed reviews carry the message: a reviewer finished its own checks and ended its turn to wait for its three sub-reviewers, the CLI stopped them ten minutes later, and the session ended without an assessment. A sub-agent that finishes while the CLI is still running starts the main agent's next turn, also when nothing else is pending, and two hours is meant to give sub-agents that time. That the CLI honours a value other than 0 has not been observed; if it does, its message will name 120 minutes where it named ten. With this value a background task that never ends can hold its session for up to two hours after the main agent's last turn; `status` shows such a session as running, and `kill-session` ends it sooner.

`max_end_resumptions` is the maximum number of additional turns in which an attempt or explorer that undertook research, a formalizer or a peer receives continuation guidance. It is a nonnegative integer, default 1000, fixed for that session at launch. The initial turn is not counted. The default is meant not to be reached, so that such a session ends by its own decision or by handing its task over and not at a count of turns. A lower value ends the session after that many resumed turns without a decision of its own, and a value of 0 authorizes the initial ending without a reconsideration turn. What the host does at the limit, and what resumes a session short of it, is under "Session hosts and continuation turns" below.

For a review or an organizer, `max_end_resumptions` is the maximum number of times the host resumes the session while its output does not pass the transport check, as "Session hosts and continuation turns" below describes. With the default the host goes on resuming such a session until its output passes the check or its task passes to a new session; with a lower value the session ends at that number of resumptions, and the runner starts a new session for the stage. With a value of 0 the host resumes no such session: a reviewer whose turn ended while its sub-reviewers were still at work is then not resumed, and the whole review is made again by a new session.

`acceptance` holds two settings that govern what review does with a proof it has found correct. With `decline_reducible_proofs` true, review does not yet accept a proof that it judges can still clearly be made simpler. With `decline_uncomprehended_computation` true, review does not yet accept a proof that closes part of the statement by large computation carried out without an understanding of why that part holds. Both are true by default, so they apply in every instance; set one to false only when the user asks for that in this research. A correct proof that review does not accept under either setting is still published, with the standing "correct, held back" and review's reason. Other proofs can use the element, the element stays among the work that remains, and nothing is settled through it, so research on it continues from the published proof. The workers' review guide describes the judgment each setting asks of review. When a setting changes, the runner does not revisit judgments that are already published.

## Create and start

Choose a path that does not exist, outside the development repository or in an ignored directory such as `.skill-workspace/`. The instance has its own Git repository, so where the path lies inside another repository, confirm with `git check-ignore` that that repository ignores it. Keep preparation files outside that path. The instance stays at that path while its research runs, because the runner's state names the session folders and the candidates of the work under way by their absolute paths and that work is not found once the instance is moved; so choose a volume with the room that "Retention and archives" below says an instance comes to take.

```powershell
$skill = 'C:/repository/.claude/skills/do-math' # replace with the installed skill folder
$instance = 'C:/research/my-problem'     # a new path
python "$skill/runtime/runner.py" init $instance --root C:/research-input/root.md --canon C:/research-input/canon --root-declaration OddSum.sum_eq_square --settings C:/research-input/settings.json
python "$skill/runtime/runner.py" input $instance --file C:/research-input/conditions.md
```

`--root` is the root file, `--canon` the canon folder, and `--root-declaration` the full Lean name of the root statement; all three are required. `--settings` is optional, and without it the defaults apply. The `input` command is optional when there are no additional standing conditions.

`init` copies the root file and the canon folder into the instance, compiles the library, extracts the structural index, and creates the configuration, the derived views, the session directories and the initial Git commit. It returns when the compile has finished. With files that import Mathlib this takes minutes, because the broker first measures what the imports cost and then compiles each module, so run it where the shell will wait for it. It refuses, with the reason on standard error, in this order. Before it creates anything: an empty root file, a canon folder without `lean/` or whose Lean files do not share exactly one top-level module name, a settings file that is not valid, an `mcp_servers` entry whose `command` is not found, and a path that already exists. After it has created the directory: a record that is malformed, for instance one with an unknown header key, without a valid `weight`, without a nonempty `## Description`, or with text before its first section; a library that does not compile; a declaration without a record or a record without a declaration; an `axiom`; a definition that contains `sorry`; a claim in a record's `proves` or `refutes` that Lean does not confirm; names that differ only in the case of their letters; and a root declaration that is not a theorem of the library or that already has a proof. A refusal of the second group leaves a partial directory, which has no `instance.json` and is not an instance. Fix the cause and use a new path.

Before you start the runner, tell the user what a run does on the machine, because the permission for it is the user's to give. The sessions run unattended, with access to files and commands under the user's account: the runner launches Claude Code with permission prompts disabled, and Codex with its approval policy set to `never` and its sandbox set to full access, so nothing but their instructions keeps them to the folders of the instance. A run has no limit on its duration, on the number of sessions it launches in all, or on the usage it draws from the user's accounts; `max_sessions` limits how many sessions run at one time and nothing else. It goes on until the root is formally settled and the remaining work has ended, or until it is ended as "Commands" below describes.

Have the user confirm what was fixed, as "Compile, and have the user confirm" above describes, and start the runner only then:

```powershell
python "$skill/runtime/runner.py" start $instance
python "$skill/runtime/runner.py" status $instance
```

`start` launches a detached runner and returns its PID and new stdout/stderr paths after confirming this launch's readiness token. Read those logs and `status` to confirm the actual launch; the runner's own start record is in the returned stdout log.

Tell the user the absolute instance path, the runner's PID, the new log paths, the current running or waiting state, and `knowledge/frontier.md`, where the state of the research can be read. Tell the user as well that nothing starts the runner again once it has ended: it ends by itself when one of its own operations fails, and it ends with the machine at a restart. `frontier.md` then stays as the runner last wrote it and does not show that the research has stopped; `status` says whether the runner is alive, and `start` continues the same instance, as "Restarts, runner failures and installation updates" below describes. The caller can then end its conversation. The runner and session hosts continue independently. If readiness is not confirmed within sixty seconds, inspect the named logs and liveness before retrying; a wait timeout alone does not show that the child died.

## Convey the user's conditions

A standing input is the way a decision of the user's reaches the sessions. Put standing instructions, such as limits on permitted methods or resources, in a separate input file, and submit it before starting the runner to make it part of every initial session's context. Later inputs affect only sessions launched after submission. They do not rewrite existing sessions' instructions or their saved contexts. A message sent with `message`, under Commands, does not deliver a condition either: it reaches only the one running session it names and no session launched later, and that session's guides tell it that an instruction the user gives after its launch applies to the sessions launched after it. So a condition of the user's always goes into an input, whatever you also tell a running session. Inputs accumulate rather than replace one another: a session receives every input submitted before its launch, in the order of submission, and is told that a later condition overrides an earlier one on the same matter. The instance keeps each input as one file under `control/inputs/`; the file names begin with the time of submission, so they sort in that order, and a session's context shows each input under its file name. Read the earlier inputs there before you write one that concerns the same matter. To change or lift an earlier condition, submit a new input that says which condition it changes and how. A mathematical suggestion in an input remains information for the researchers' judgment.

Every session launched after an input reads it in full, and reviewers decide what to accept by it. The sessions therefore follow whatever you write around the user's words as though the user had said it. In an earlier run this went wrong three times, and each time the user had to give a further condition to undo it.

The first time, the operator delivered a condition under which a correct proof is not yet accepted while it can clearly be made simpler. The user had given no reason. The operator supplied one: the cost of formalization, illustrated by the number of published assertions the proof depended on. Reviewers then judged whether a proof could be simplified by the length of its list of dependencies, and one asked that a citation be deleted so that the list would become shorter. The user's reason, given afterwards, was that a simpler proof is more concise, and nothing more.

The second time, the operator added an example of its own to that condition: a proof that relies on a wide range of computed results while using only a narrow part of them. The user had not meant that. Reviewers began counting how many entries of a table a proof read.

The third time, the user said that a proof which establishes part of a statement by computation should not yet be accepted, and meant crude large computation done without understanding. The operator wrote the condition as covering every proof that establishes any part of a statement by computation. That version stood for nine minutes before it was replaced, and the sessions launched in those minutes had received it.

**Give the user's words, in translation, as the user's.** The instance is in English, and the user may speak to you in another language. Translate what the user said into English and set it apart as a quotation, labelled as the user's words in translation. That quotation is the condition. Translate what was said, and do not make the translation smoother or more complete than what the user said. Where a phrase could be translated in ways that would change what the condition requires, ask the user which is meant. Keep the original wording outside the instance, with your other preparation files, and put neither the original nor its path into the input. If a translation turns out to be wrong, submit a new input that says which earlier input it corrects.

**Mark your own text as yours.** Around the quotation you will usually need to write more: what happened in the research that led to the condition, which the sessions need in order to understand the case; what the condition changes in terms a session acts on, such as which field of an assessment takes which value; and what has already been changed in the instance on the user's instruction. Where a sentence is your reading of the user's words, and not something the user decided, say so at that sentence or passage. The sessions are told that the user's words are the condition and that your text explains it.

**Give no reason the user did not give.** If the user gave a reason, translate it with the rest. If the user gave none, say that none was given. If you supply a reason of your own, reviewers will apply the condition according to that reason, as in the first case above. When a session will need the reason in order to apply the condition, ask the user for it.

**Do not widen the condition, and add examples of your own rarely.** Write the condition so that it covers what the user said and no more. Sessions use an example to decide which cases a condition applies to, so an example the user did not give makes them apply the condition to every case that resembles the example, as in the second case. If you add an example, mark it as yours. Where it matters which cases a condition covers and the user has not said, leave that judgment to the sessions and say that you are leaving it to them.

**Say how the condition relates to the earlier ones.** Say which earlier condition concerns the same matter as this one, what this one changes in it and what it leaves unchanged. When you withdraw something you wrote in an earlier input, name the passages you withdraw; the user's quoted words in that input stand unless the user has changed them.

**Say what you read.** When an input reports facts about elements, their records or their reviews, say which texts you read and which you did not, so that a session does not take your account for a checked one. Ask the sessions to confirm at the source anything you point them to.

**Ask when the research shows a case the user has not addressed.** Sessions will meet cases that nobody had in mind when a condition was given. When the sessions' work shows such a case, for example a proposal withheld or refused under a reading of a condition that the user may not have intended, report the case to the user with the texts involved and ask. The user's answer becomes a new input, and it can settle that one case while leaving the rest of the condition as it was.

## Place questions on the frontier

You place questions of your own on the frontier with the `questions` command, as an operator publication. Its questions do not pass through peer or review, so their content is yours to answer for; on the frontier, explorers take them up and changes resolve them like any other question. While the root is formally settled the runner launches no new exploration, so a question placed then is published and no explorer is launched for it.

Write an operator question to the standard that review applies to a proposed one, because no review reads yours. Its statement says what is asked, about which objects and over which range of cases. It lets a later reviewer recognize an answer, a negative one included: "does this regularity come from that property" is closed by "no, it comes from this other one", while "what structure explains this" names nothing a reviewer could accept as the answer. Its grounds say what an answer would change in how the problem is worked. The statement of an open question is in the starting context of every session, and the grounds are read by the sessions that open the question, so what raised the question and led up to it belongs in the grounds. A question whose complete answer would be a proof of the root asks what `q0` already holds. And when a question asks for the counterpart, among the objects of the root, of something known about a related object such as a limit or a model, state the counterpart you hope for as a statement about the objects of the root. Otherwise explorers work on the related object, where results come more easily, and the question does not close. In an earlier run the operator placed five questions when the instance was created. Three days later four of them were still open, each after three to six explorations, and the fifth had been resolved: it asked whether a named regularity came from a named property, and the answer was that it did not. Questions also age, since the difficulty one was asked about can be passed by another route. You cannot withdraw a question. A change can resolve it by showing that its premise no longer holds, and you can place sharper questions beside it.

The file given to `questions --file <file>` is UTF-8 JSON of the form `{"reason": "...", "questions": [{"id": "...", "statement": "...", "grounds": "..."}]}` with no other keys. `reason`, recorded in the publication, says why you place them; the list is nonempty; `statement` says what is to be understood and `grounds` what raises the question and why an answer matters, both nonempty. Each `id` matches `[A-Za-z0-9][A-Za-z0-9_-]*`, is unique in the file, is not `q0`, and does not name an existing question or question alias; a prefix such as `op-` keeps operator questions recognizable beside peer proposals, which carry a session-ID prefix. The command refuses a file that breaks these rules and otherwise leaves a request. On its next pass the runner collects the request and publishes it as `knowledge/questions/<event>/questions.json` with its event and Git commit; while another publication is under way, the request waits behind it, and `status` shows it under `state.publish_queue`. If a publication since the command has taken one of the identifiers, the runner refuses the whole request and keeps running; the refusal and its reason appear in the runner state's top-level `last_error`.

## Read progress and results

The results of an instance are the elements of its canon, and you read them where the sessions read them. Nothing is published per session: what a session found enters as elements with their records, and what it learned about the course of the work enters as the approaches tried on an element or as the understanding so far of a question.

Begin with `knowledge/frontier.md`. Its first lines give the revision, the root declaration and the root's state. The view below them is derived from the root downward along what each proof names. While the root is not settled it is shown with every proof it has. Beneath a proof stand the statements it names that are not settled, each again with every proof it has; a statement that is settled is not opened. A line gives the element's name, its short name or self-description, and its standing. For a proof that is not confirmed or that is correct and held back, the line carries the beginning of review's reason; it also shows how many approaches have been tried on the element and how many sessions hold a section on it. A step whose own proof is accepted is passed through to what it names, so the view stays at the level of the units of the proof. Once the root is settled the view is the root's line alone. For a proved root the line says whether the settlement is formal; for a refuted root it names the declarations that refute it, and the root's state in the first lines says whether the refutation is formal. Nothing remains for an attempt then, and no attempt is launched, while formalization continues until the settlement is formal.

After the view, `frontier.md` lists the concerns that are not cleared and the questions the research is trying to understand: each open question with its statement, state and source, each resolved question as one line that says what resolved it, and the number of proposals review did not admit. Every session receives this list in its starting context, which is why it carries no more. The grounds of a question, the statements of the resolved questions and the proposals with review's reasons are printed by the `question` and `questions` commands shown below. A question's source is either the change whose review admitted it or an operator publication under `knowledge/questions/`, which "Place questions on the frontier" above describes.

`knowledge/index.md` is the derived index: every element of the canon, grouped by module, with modules and elements in the order of their names, each with its weight, its standing and its self-description. A definition has no standing and is shown with its kind. Nobody writes this view. Use it to see everything the canon holds, including the elements the root does not rest on, which the frontier does not show.

For an element itself, read the canon:

| Path under the instance | Content |
|---|---|
| `canon/lean/` | The library: the Lean source of every declaration. |
| `canon/records/<name path>.md` | The record of an element: self-description, statement in natural language, explanation, the proof in words where there is one, literature. |
| `canon/approaches/<name path>/<id>.md` | The approaches tried on a statement whose proof is not accepted, one entry per approach, each ending with review's assessment of what the work contributed. |
| `canon/questions/<question>.md` | The understanding so far of a question. That of `q0` is the research's current account of the root problem as a whole. |
| `canon/history/` | What replacements left behind: the difference between a replaced text and the current one. |
| `canon/evidence/`, `canon/bibliography.bib` | Files that records refer to, and the sources of results taken from the literature. |
| `canon/index.json`, `canon/records.json` | The structural index extracted from the compiled library, and a summary of the record headers. The runner produces both at publication, and they are never edited. |
| `knowledge/changes/<id>/` | One published change: its manifest `change.json`, the elements it added and the proofs it replaced in `applied.json`, review's `assessment.json` with its feedback, the sessions involved in `provenance.json`, and review's own compile in `verify.json`. |
| `knowledge/reviews/<id>/`, `knowledge/organizations/<id>/`, `knowledge/questions/<id>/` | A comprehensive review's assessment, an organizer's output, and an operator publication of questions. |

The traversal commands that the sessions use are available to you as well, and they are the convenient way to read an element, because one view joins what Lean knows of it with what its record says. Each is `python <skill>/runtime/canon_tool.py <command> <instance> ...`: where a session gives its own folder, you give the instance folder. The reading commands work this way from the moment `init` has finished; `prepare`, `verify` and `checkout` belong to a session's work and refuse the instance folder. For example:

```powershell
python "$skill/runtime/canon_tool.py" frontier $instance
python "$skill/runtime/canon_tool.py" view $instance Parking.Columns.dq_col --full
python "$skill/runtime/canon_tool.py" list $instance --about Parking.zr
python "$skill/runtime/canon_tool.py" question $instance q0
python "$skill/runtime/canon_tool.py" questions $instance --proposals
python "$skill/runtime/canon_tool.py" log $instance --last 10
```

`frontier` prints the frontier as it is now. `view` prints one element: its Lean statement, what its proof rests on with the standing of each declaration the proof names, whether that proof is settled and formal, the proofs of the statement where it has several, what uses it, review's verdict with its reason, concerns, and the approaches tried; `--full` adds the parts of the record. `list` prints one line per element for a module, for what an element uses or is used by, for everything the canon says about a definition, or for the work that remains. `question` prints a question with its grounds and its understanding so far, `questions` prints the resolved questions with their statements (`--resolved`) or the proposals review did not admit (`--proposals`), and `log` the recent changes with review's assessment of what each contributed. [The canon](canon.md) describes each view. `knowledge/state.json` holds the same derived state in structured form for detailed inspection.

A session that finds that the root's Lean statement and the root's statement in words differ cannot repair that; only you can act on it, with the user. The peer of that work enters the difference in the `## Explanation` of the root's record, with a case in which the two forms differ, and says in the description of its change that the record states it. So when you read results for the user, print the root with `view` and `--full`, and read the descriptions that `log` prints. "If the Lean statement is later found not to say what was meant" above says what follows when a difference stands there.

Read a standing for what it says, and of the declaration it stands beside. A statement can have further proofs, each a further declaration with the same statement, as when the root was posed in one declaration and proved in another. `knowledge/index.md`, a line of `list` and the `proof`, `settled` and `axioms` lines of `view` speak of the one declaration they name, and the `rests on` line of `view` gives each declaration a proof names as that declaration stands, so the statement's own declaration can read "no proof", say `no` under `settled`, show `sorryAx` under `axioms` or stand as `unsettled` and `not formal` on the `rests on` line of a proof that names it while the statement is settled, or formal, through another, as the root's state then says of the root. The view of the statement's own declaration names them all under `proofs`; read the view of each before you say how the statement stands. "No proof" means that the declaration carries no proof. "Proof not confirmed" means a proof was offered and review found a gap, could not complete its judgment, or has not judged it, as with a written proof the instance began with; the reason, where there is one, says which. "Correct, held back" means review confirmed the proof and did not accept it, for one of the two reasons the acceptance settings name; a proof that a later review confirmed by a finding which does not say whether the proof is accepted stands so as well, unless it was accepted before its confirmation was withdrawn. "Accepted" means the proof is correct and accepted. An accepted proof that rests on an unsettled statement does not settle its own statement. The root's state combines these with whether the proof is formal:

| State | Meaning |
|---|---|
| `unresolved` | No proof of the root is settled, and no refutation of it is. |
| `informal_proved` | The root is settled, and no proof that settles it is formal yet: somewhere in what it rests on, a proof is still written in a record and not complete in Lean, or depends on an axiom that is not allowed. |
| `formal_proved` | The root is settled through a proof that is formal. |
| `informal_refuted`, `formal_refuted` | The same for an element whose statement Lean has confirmed to be the negation of the root's. |
| `contested` | Both the root and its negation carry settled proofs. |

The instance is complete when the root is `formal_proved` or `formal_refuted`. Formal proofs are already being written while the root is unresolved, because the runner launches formalizers whatever the root's state, as "What creates new work" below explains.

A contested root is not treated as settled for completion; the opposing proofs must be resolved. Whenever no comprehensive review is pending or running, the runner assigns one that covers every concern that is not cleared and every contested statement's current set of opposing judgments it has not yet assigned. When that review leaves the concern uncleared or the statement contested, the runner does not assign it again; a further examination needs an operator `review` request. A concern stays with the proof it was raised about, and a finding with the proof it judged: once a later publication has given an element another proof, `frontier.md` no longer lists the concern against that element, `view` marks the concern there as raised about an earlier proof and the finding as about an earlier proof, and the runner assigns no review to a concern that is left with no element in this way.

Question `q0` is the root problem itself; no explanation resolves it, and it stays open until the root is formally proved or refuted. The frontier then shows it resolved by the root's formal settlement, with the declarations whose proofs carry it. `knowledge/state.json` records that ground under the question's `root_settlement` in place of `resolutions`. The runner derives whether `q0` is open or resolved from the root's state each time it replays the published events, so a later review that withdraws the confirmation of a proof the settlement rests on reopens `q0`, and the runner, if it has not exited, resumes research.

`knowledge/board.md` shows the work still underway. A **section** is what a session has taken responsibility for on an element: the whole of the statement, an exact part of what it asserts, or a statement the session formulated itself and registered with the element it is aimed at. An attempt, or a peer extending its work, registers one, and the runner records a formalizer's assigned element as a whole section. A session choosing a section on an element holds that element's **lease**, which lets one session at a time choose there. A producing session, the peer that takes its work over and the review that assesses the resulting candidate form one **pipeline**, and the sections and question its sessions hold stay occupied until publication or a review decision that there is nothing to publish. The workers' [common introduction](common.md) develops these terms. The board shows the sections producing work holds, the question each exploration occupies, its processing stages and the element leases; a session's declaration, the file `declaration.json` in its session folder, lists the sections it has registered or the question it holds.

`status` returns one JSON object with the keys below, printed on one line. A successful status command means the query succeeded. The object grows with the research, because `state` holds every session and job the instance has had: in a long research it comes to megabytes. Write the output to a file and take the keys you need from it with a JSON reader.

A formal root and a finished runner are different states: after formal completion, new attempts and explorations stop, while existing sessions continue and the runner still prepares their peer and review stages, ready formalizations, comprehensive reviews and due organization batches. Formalization of other settled statements that the root rests on has no limit, so the runner can keep working well after the root is settled.

## What makes a statement formal

A statement of the canon is formal when its Lean proof is complete and every axiom the proof depends on is in `lean.allowed_axioms`. Two facts establish this, and both come from Lean. The first is that the library compiles: Lean's kernel checks every declaration of a module before the compile succeeds, so a proof in a compiled module is a checked proof. The second is Lean's own account of the axioms that proof depends on. A compile alone does not give the second fact, because a proof that ends in `sorry` compiles, and so does a proof that rests on an axiom somebody declared. do-math adds no check of its own to these two facts, and no second program examines them.

**The axioms.** Lean keeps account of the axioms of every declaration. `#print axioms` prints that account, and the function behind the command is `Lean.collectAxioms`. For a declaration it gives every axiom reached through everything the declaration uses, in the canon and in the imported library alike. A `sorry` is in the list as the axiom `sorryAx`, an axiom declared in the canon is there under its own name, and each `native_decide` is there as the axiom Lean generates for that computation. When the runner extracts the structural index, it asks Lean for this list for each declaration of the modules it extracts and stores the list with the element as Lean gave it. The view of an element shows the list under `axioms`, and the element is formal when the list lies within `lean.allowed_axioms`. `sorryAx` cannot be put on the allowed list, so a `sorry` anywhere beneath a statement keeps the statement from being formal, and a proof that is not complete is never formal.

The view of a statement also says, under `proof`, whether the statement's own proof is complete in Lean. That is a narrower fact than the list of axioms. A proof that is written out in full and names a statement still open is a complete proof, and the view says so; Lean reports `sorryAx` for it until the open statement is proved, and until then the statement is not formal. In one case the narrower fact adds to the list: a `sorry` in a helper declaration written under the statement's name counts as the statement's own open proof, and keeps the statement from being formal, even where Lean's list for the statement itself is without `sorryAx`.

**Who confirms a complete proof.** A proof complete in Lean that reaches the canon in a peer's candidate is confirmed only after review has compiled the candidate itself and read the axioms the proof depends on. Two kinds of proof stand without a review. One is the complete Lean proof of a theorem you supply with the canon at creation, as "Lean conventions of the canon" above says. The other is a statement an organizer adds, saying that two definitions or two statements agree, or deriving a statement from another that agrees with it: its proof has to be complete in Lean from the allowed axioms, which the runner checks again when it publishes the organizer's change, and it enters as accepted.

**A statement in a module that did not change.** When a lemma receives a complete proof, a theorem that rests on the lemma becomes formal, even where the theorem stands in another module whose source is the same as before. Two things bring this about, and both were established with Lean 4.36.0. Lean stores the axioms of each declaration in the compiled module. The compiled output of the lemma's module therefore changes when the lemma's axioms change, and the broker compiles again every module that imports a module whose compiled output changed. So the theorem's module is compiled again, and Lean works out the theorem's axioms again. The runner, for its part, extracts at each publication the index of the changed modules and of every module that imports one of them, directly or through others, so the list stored for the theorem is replaced by Lean's new answer. The axioms stored for every element are in this way Lean's answer for the library as it stands.

**The root as posed.** A formal settlement of the root means that a declaration is proved from the allowed axioms and that Lean confirmed its statement to be the root's statement, or the negation of the root's statement for a refutation. What remains to be known is that the root's statement is still the one the instance was created with, together with every definition the statement is built on. No publication can change either, because the runner refuses a candidate that changes a statement or the text of a definition in place, and one that changes the file of a definition module, as "The canon folder" above says. The runner reads the same thing off from the two ends once the root is formally settled, in two comparisons. The first compares the structural index in the instance's first commit with the index as it stands. Starting at the root, it goes to every element the root's statement names, and from a definition on to what the body of the definition names. For each element it reaches it requires the same kind and the same statement in both indexes, by the identity of the term Lean elaborated, and for a definition the same source text as well. A theorem reached on the way counts by its statement alone, whatever became of its proof. The second compares the file of every definition module, as it stands in the instance's folder, with the file the first commit has. Neither compiles anything, and the runner repeats both whenever another proof settles the root or the library's revision changes.

`status` gives the result under `root_check`: the `proof` that settles the root, the library `revision`, the commit under `compared_with_commit`, a `status` of `unchanged` or `changed`, and under `differences` one sentence for each element that differs or that is under the statement in one of the two indexes only, and one for each definition module whose file is not the file of the first commit. The key is `null` until the root is formally settled and a runner has made the comparisons. When the status is `changed`, the runner has written a request for a comprehensive review of the settling proof, in the form the `review` command writes and with the differences as its reason, and it takes the request up itself. Report the result under `root_check` together with the formal settlement, and say so when there is none. A status of `changed` means that something other than a publication changed the index or the file of a definition module, such as an edit by hand, or that a publication replaced a proof inside a definition module, or rearranged one, under an earlier version of the runtime, which did not refuse that. Report the differences to the user as they stand, beside the settlement and not after it, because they say that what was proved may not be what was posed.

The first comparison reads the index and not the Lean sources. After `init`, the index takes the entries of a module only from a publication that extracted that module, and no publication is installed whose extraction finds a statement or the text of a definition changed in place. An edit by hand of a source under `canon/lean/` therefore shows as `changed` only where the source is a definition module, and `unchanged` says that the files of the definition modules are those of the first commit and says it of no other source. Nor does the first comparison see a declaration that is no element, such as a private helper that a definition uses, or a definition whose unchanged text Lean now reads as another term. For the definition modules the second comparison adds that every line of their files, such a helper and the imports among them, is the line of the first commit. A definition whose unchanged text Lean reads as another term because Lean or a pinned library changed is seen by neither comparison.

**An instance created by an earlier version of this runtime.** Such an instance can carry three things that this version does not write. Its `settings.json` can have the key `lean.judge`, which is accepted and has no effect, the one exception to the rejection of unrecognized keys, so that those settings are still read. Its `canon/index.json` can hold for each entry a list `direct_axioms` in place of `axioms`, and a table `judged`. The runtime reads such an index with the axioms of each entry added up from those lists, as the earlier version added them, so every element stands as it stood. The file takes the present form at the next publication that changes a Lean source, and from then on the list of an entry is Lean's own as soon as the entry's module is extracted again. A publication that the earlier runner left unfinished is staged again from its candidate by the next runner that is started. None of this asks anything of the operator.

## The dependency map and the paper

### The dependency map

`python <skill>/runtime/depmap.py <instance> --out <folder>` draws the dependency map of the research from the canon as it stands. It can be run at any time, including while the instance runs, and it writes nothing into the instance. The command needs only Python.

The map starts at the root and follows, from each statement it reaches, what every proof of that statement names, whatever the standing of the proof, and what the statement itself mentions; from a definition it follows what the body and the type of the definition name. It shows the elements reached in this way whose record gives `weight: unit`, grouped by the folder of their module; `--all` shows every unit of the canon. The steps are folded into the lines that pass through them. A solid line means that the proof of one unit, or the body of a definition, names another. A dashed line means that it reaches the other only through folded steps. The line names those steps where the names cover no card and gives their number where they would; the data and the page name all of them. A dotted line joins a statement to a definition it mentions, and a definition to a definition that its type mentions. A heavy line joins a proof that is drawn as a card of its own to the statement it proves. Such a proof is another proof of a statement that already has one, or the proof of a statement whose own declaration carries none, as when the root was posed in one declaration and proved in another. In the second case the card of the statement says `proof on a separate card` in the place of the standing, and the card of the proof says `proof`, not `another proof`. When the research has ended with the root refuted, the result is the refutation, and the map shows it: the root's card says that the root is refuted, a heavy dashed line joins the statement that refutes it to the root, and the map starts from that statement as it starts from the root. Each card gives the short name, the Lean name, the kind, the standing of the proof, whether the statement is settled, and, independently of that, whether one of its proofs is formal. Under its title the drawing says in words how the root stands and carries a legend of the lines, the cards and the standings that occur on it.

The folder receives three files. `dependency_map.svg` is the drawing. `dependency_map.html` is the same drawing for a browser, in one file that asks nothing of a network. `dependency_map.json` holds the units and lines the drawing was made from, and `python <skill>/runtime/depmap.py <folder>/dependency_map.json --out <folder>` draws the map again from it without the instance.

The page explains its own controls and how the map is read. Its address holds the selection, so a link to one unit can be kept or sent: `#node=<Lean name>` selects a unit with what it rests on and what rests on it, `&mode=direct` after it keeps the unit's direct neighbours only, and `#step=<Lean name>` shows a folded step, which has no card, with the lines it is folded into.

The exit code is 0 on success. It is 2 when the command cannot read its input, when `--all` is given with a `dependency_map.json`, and when the operating system reports an error, for example on a folder that cannot be written; the message on standard error says which.

### The paper

`python <skill>/runtime/paper.py <instance> --out <new folder>` writes the paper that presents the result, as LaTeX and a typeset PDF. It runs only when the root is settled by a formal proof, that is, when the root's state is `formal_proved` or `formal_refuted`; otherwise it refuses and writes nothing. It takes its materials from the canon as it stands when the run begins. A runner that is still finishing its remaining work can afterwards publish a change to an element the proof rests on, such as a record that a candidate under way writes again, and `--resume` and `--open-findings` then refuse the run's folder, so that a run that was stopped is not continued and what a run left open is not acted on. Unless the user wants the paper at once, wait until `status` reports that the runner has finished. Once started it runs to the end without asking anything, in the foreground and for far longer than a shell tool waits, so start it as a background process with its output in a file. Its sessions are launched with the options that "External tools" above gives for a worker, so they too run unattended, with access to files and commands under the user's account, and they draw on the user's accounts. Before the first run of the command on an instance, tell the user so, as "Create and start" has you do before a runner is started. Its options are `--parallel <n>`, `--resume`, `--dry-run`, `--open-findings`, `--draft`, `--from-draft <folder>`, `--title-page <file>`, `--main <declaration>`, `--model`, `--effort`, `--typeset-only`, and `--tex`, which comes last.

The sessions follow [the paper method](paper-method.md), which fixes in advance how the canon becomes a paper: which elements receive a number, in which order they stand, what of the canon the paper leaves out, and that nothing of the Lean implementation shows: the paper stands in natural language and does not mention Lean. The choices in that document are the user's, and the command does not check that the user has made them: before the first paper of an instance's user is produced, ask the user to read and confirm the document, and do not run the command until they have.

#### What a run does

The command takes from the canon everything the formal proof of the root rests on. One session plans the paper, and one session for each section writes it. Both read real mathematical papers first and write as those are written. The command then assembles the manuscript, checks it by machine and typesets it, and puts it through the steps that [the paper method](paper-method.md) describes, each with its reason, under "What is checked after writing". In their order: a session that sees nothing but the manuscript reads it; sessions read it beside real papers and report where it is written otherwise than those papers are; every numbered statement is compared with the statement of its element; in the stage `resolve` one session resolves what the readings left open; in the stage `coverage` the running text, that is, the text outside the numbered statements and outside the proofs, is compared with the elements; and in the stage `placement`, the last, one session says where a manuscript that a repair has changed has the content of each element without a numbered statement. What a check or a reading finds goes to repair sessions, a bounded number of times. A repair may rewrite a passage, and a rewriting can lose a step of a proof, so the manuscript is read again after a repair. A session that sees nothing but the manuscript reads it at up to four points, which that section of the paper method gives with the repairs that follow them. At each point it is read at most three times, the second and the third time only when the reading before had findings, and after the resolving session it is read only if that session changed a part. The repair after the last reading that the bound allows is followed by no such reading, and it is made in another way, which this section calls narrow: its sessions change the passages that the findings name and nothing else, one session reads each changed passage where it stands, and a change that it finds unsound is put back as it was, together with the other changes made for the same finding.

With the stage `resolve` the findings of the readings are closed. Those that were answered with a reason, by the resolving session or by the narrow repair of the reading that follows it, are listed under `kept` in the last `end` event of `log.json`, each with its check, the finding and the reason. They are not open findings, and they do not change the exit code. Read them with the user: they are the places where a reader stopped and the paper was left as it is. What the stage `coverage` still reports after its one narrow repair, and what that repair kept, is open, and so is a numbered statement that differs after the last comparison, which no repair follows.

[The paper method](paper-method.md) says under "What each session works from" what each session is given; a session that writes or repairs a section works from the brief that the script makes for that section. The sections after the introduction are written side by side, and `--parallel <n>` says how many sessions run at a time; the default is 4. The same number bounds the repairs and the comparisons, which are made section by section.

#### The collection of real papers

The collection of real papers is the folder `<skill>/exemplars`. Its `manifest.json` lists the papers: research articles from refereed journals, of several fields and lengths, chosen for their writing and their structure. The papers themselves are their LaTeX sources from arXiv with the comment lines left out. They are copies for reading on this machine, and a `.gitignore` in the folder keeps them out of Git, since most of them may not be passed on. The command checks the collection before it launches a session. If a paper is missing or differs from the manifest, it runs `python <skill>/exemplars/fetch.py` once, which needs the network. If a paper is still missing or still differs after that, the command stops and names those papers. The planning session chooses six papers that are near the paper in subject and length, reads them whole, and leaves its account of how they are written as `study.md`. For each section it names two of the six in the plan. A session that writes or repairs a section receives that account and reads the two papers of its section. Each reading beside real papers is given four papers that the plan did not choose. These readings end when two in succession report no departure, and there are at most eight of them. When every paper that the plan did not choose has been given to a reading, the next readings are given those papers again from the first.

#### Models and tools of the sessions

Planning, writing and repair use the instance's `cli` and the first entry of `models`, and so do the session that resolves what the readings left open and, in a draft, the sessions that sketch the sections. The reading, the readings beside real papers, the comparison of the statements and the comparison of the running text use the first model of the `review` role, so that by default a different model reads than wrote. `--model <provider/model>`, for example `claude/opus`, puts every session on that one model, the reading and the comparison included. `--effort <level>` sets the effort of planning, writing and repair, and of every session when `--model` is given with it. The sessions receive no MCP servers, although a session on Codex runs with web search enabled. What confines the citations to the canon's bibliography is one of the machine checks: a citation whose key is not in that bibliography is a finding.

When a provider refuses a session, the command waits and starts that session again with the same model, twelve times at the most for one session. At the account's usage limit it waits until the reset that the provider named, or for `retry_max_seconds` of the instance's settings when it named none; when the provider has no capacity for the model or asks for usage credits, it waits for `retry_max_seconds`. A run can therefore stand still for hours without having stopped: each `session` event of `log.json` gives under `refused` the reason (`usage_limit`, `model_capacity` or `model_requires_usage_credits`) and under `refused_until` the time before which the command does not start that session again, or null in both, and under `usage_limit_until` that time when the reason is the usage limit. When the provider still refuses after the twelfth wait, the command stops with exit code 1 and names the reason; no output was judged, and `--resume` continues the run once the provider takes sessions again.

#### A session that a safeguard stops

A safeguard of the AI system can stop a session before it has finished. The command knows such a stop from what the Claude CLI writes: the result of the turn is an error with the stop reason `refusal`. For a session on Codex no such sign is known, and a stop there counts as a session that left no usable output. A session that was stopped is started again as it was, with the same prompt and the same files and without a word about the stop, and it counts among the attempts that its task has. When every attempt was stopped, a session that makes something the run needs, such as the plan, a section or a repair, stops the run with exit code 1, and `--resume` starts the same session again, while a session that is a check is recorded as not done, and the run goes on. The checks are the readings and the comparisons: the reading of the manuscript by itself, after which the readings of that stage end; a reading beside real papers; the comparison of the numbered statements of a section; the comparison of the running text of a section; the reading of the passages that a narrow repair changed, whose changes then stay in the paper unread; the check of the stage `placement`; and, in a draft, the comparison of a section's sketch. A check that was not made is named in `not-done.json` in the folder, in `correspondence.json` under `not_done`, in the last `end` event under `not_done`, and in what the command prints at its end. A numbered statement whose comparison was not made keeps the verdict that an earlier comparison gave its present text; without such a verdict it stays `not compared` in the correspondence file, with the reason under `not_done` of its comparison, and is not an open finding. When a check of the same thing is made later, for example in a pass of `--open-findings`, its entry goes. Report every check that was not made to the user: the paper is then less checked than exit code 0 says of a run in which every check was made.

#### The files of a run

The folder receives `paper.tex`, `references.bib`, `paper.pdf`, `plan.json`, `study.md`, `materials.md`, `correspondence.json` and `log.json`, and the working material: `materials.json`, the parts of the manuscript under `parts/`, `state.json`, a folder for each session under `sessions/`, `typeset/`, where the manuscript is typeset, and, while a narrow repair is under way, `narrow/`, which holds the parts as they were read. While the stage `resolve` is under way, `resolve/` holds the plan and the parts that its session returned. A run with `--title-page` keeps a copy of that file as `title-page.json`, and a run with `--from-draft` a copy of the draft as `draft.json`. `materials.md` holds everything the paper was written from as one text, for you and the user; no session is given it, and the folder of a session holds exactly what that session was given.

#### A draft: `--draft` and `--from-draft`

`--draft` makes the draft of a paper and no paper. It is for a library that can still be changed: the draft shows what the paper would want to state and the library does not contain, while that can still be added. The finalize pipeline uses it so: it makes the draft on its own copy of the library and puts what the draft wants into that copy before the freeze. A research instance has no such step, because the command runs only once the root is formally settled and the runner then launches no new attempt or exploration, so a draft made on one shows what a paper written from its library could not state. After the plan, one session for each section sketches that section without writing prose: the numbered statements as the paper will state them, the displayed formulas that the section will use as results, and the gaps, that is, each place where the paper wants to state something that no element states. Sessions of the `review` model then compare the sketched statements and formulas with their elements, section by section. One that differs from its element is a gap that the sketch declared, which stays in the draft, or a slip, which is replaced by the statement as the element says it; a declared gap that the comparison finds to be none is dropped. One slip is not replaced: a text that gives only some of the parts that its element states together stays, as a gap that a declaration of those parts closes. The planning session of a draft is also asked for the results that the paper would cite if their records named a source. The folder receives `plan.json`, `study.md` and `draft.json`, and the command ends with exit code 0; the last event of `log.json` is an `end` event with the status `draft`. `draft.json` holds four lists. `statements` has for each numbered statement its label, its section, its element, its text and the id of its gap or null. `formulas` has the same for each formula, with the label of the statement in whose proof it stands under `host`. `gaps` has for each gap an id, its kind (`statement`, `formula` or `assertion`), the element it is nearest to, what was wanted, what the element has, the reason, and `closed_by`, which is null. `citations` has the results to cite, each with its element and the name under which the result is known. The sketches and the verdicts are kept under `sketch/` as they are accepted, and `--resume` continues a draft that was stopped.

`--from-draft <folder>` writes the paper from a draft, on the instance as it is after the library was changed. The folder holds `plan.json`, `study.md` and `draft.json`, and in `draft.json` each gap that a declaration has closed names that declaration under `closed_by`, each statement and formula names under `element` the element that states it now, and one that had to go carries `"cut": true`. The materials of such a run are what the formal proof of the root rests on together with every declaration that `closed_by` names and the instance has, and everything those rest on, also where the proof of the root does not use them; `materials.md` and the files given to the sessions mark such an element as added for the draft of the paper, and `materials.json` names the declarations under `further`. A statement among them is taken only when its own proof is settled and formal. The command keeps a copy of the draft as `draft.json` when the run begins, and `--resume` and `--open-findings` take the declarations from that copy when they compare the canon with `materials.json`, so those comparisons do not read the folder of the draft again. No session plans the paper again and none reads the collection for a plan. The command brings the plan of the draft to the materials by script: an element that is no longer among the materials leaves the plan; a declaration that closed the gap of a numbered statement becomes the element of that statement, under its kind and its label; a declaration that closed the gap of a formula or an assertion is absorbed into the statement in whose proof the gap stood when that statement rests on it, and otherwise into the running text of the gap's section; a statement whose element now has a source is cited and not proved. The check of the plan then decides. Only when it finds problems does a planning session repair the plan, from the plan, the problems, the account of the papers and the draft, at most three times. The brief of each section carries the statements and formulas of that section as they were drafted, and the writer is told that they stand as drafted. `draft.json` can carry two more lists, which the finalize pipeline adds: `instances`, the results that the paper proves from a cited general theorem by a specialisation, and `attributions`, the words of the cited works, to which the sentences of the paper about those works are held. [The paper method](paper-method.md) describes both under "Results from the literature". Everything after the writing runs as in any run. `--resume` continues such a run without the folder being named again. It reads that folder once more in one case: a run that was stopped before it had kept its own `plan.json` and `study.md`, for instance while a planning session was repairing the plan, takes the plan and the account of the papers from the folder of the draft again, at the path recorded when the run began. Until the run has kept its plan, the folder of the draft therefore has to stay where it was; from then on it is not needed again.

`--from-draft` does not compare the texts of the draft with the library before the sections are written. The brief tells each writer that every drafted statement and formula says exactly what its element states, and has it stand in the section as drafted. A draft as `--draft` leaves it does not yet meet this where the sketch declared a gap: the text there is what the paper wanted, which no element states. So in the `draft.json` that `--from-draft` is given, a statement whose gap no declaration closed has under `text` the statement as its element says it, and a formula that no element states carries `"cut": true`. The finalize pipeline brings its own draft to the library in this way before it has the paper written.

#### `--main` and `--title-page`

`--main <declaration>` names the theorem that the paper is built around, for a research whose telling result is not the declaration that settles the root: as a rule a stronger theorem from which the root follows. The declaration has to be a theorem of the instance that is settled by a formal proof; the command refuses another before it writes anything. The materials are then what that theorem rests on together with the settling declaration and what it rests on. `materials.json` names the chosen theorem under `main` and the settling declaration under `settles`, and the files given to the sessions mark the two. The check of the plan requires the chosen theorem as the first theorem of the first section, as it requires the main result of any paper, and it requires the settling declaration as a numbered statement, so that the root stands in the paper with its exact statement, as a corollary of the main theorem or as a theorem beside it. The statement of the settling declaration is the one that says what the root says in words. `correspondence.json` names the chosen theorem under `main_result` and the settling declaration under `settled_by`. The run records the main result: in `materials.json`, and with `--draft` also in `draft.json` under `main`. `--resume`, `--open-findings` and `--typeset-only` take it from the run's folder, and `--from-draft` takes it from the draft. `--main` may be given again to `--resume` and with `--from-draft`, and then has to name the same element; the command refuses a run that is continued, or a paper that is written from a draft, around another main result than the recorded one. Without `--main`, or when it names the settling declaration, the command does exactly what it does without the option.

`--title-page <file>` names a JSON file `{"authors": [{"name": "...", "address": "...", "email": "..."}]}`, in which `address` and `email` may be absent. The command writes the author line from it: the name of each author, with the address and the email where the file gives them. With an empty list, as without the option, the manuscript has no author line. The values are plain text and not LaTeX. The file can also give `"msc2020"`, an array of codes of the Mathematics Subject Classification 2020 such as `05A15`; the command then writes them into the manuscript with `\subjclass`, and without the key the manuscript has no classification. The key words of the paper are not in this file: the planning session gives them in the plan under `keywords`, and the command writes them with `\keywords`. `--typeset-only` with `--title-page` sets the author line and the classification of a manuscript that is already written.

#### Continuing a run: `--resume`

A run that was stopped is continued with `--resume` and the same `--out`: after an interruption, after the command ended with exit code 1 because a session left nothing usable, or after the machine was restarted. Everything a later step needs is in the folder as soon as it exists. The command takes the materials from the canon again and compares with `materials.json` what the proof of the root rests on: the root, the main result, the axioms, and the elements with their records. If these differ, the canon has changed under the paper since the run began, and the command refuses and says in what they differ. What the research has published beside the proof since then does not stop the run, which goes on with the bibliography and the account of the problem as `materials.json` holds them. It uses a plan that is there and passes the check, does not write a part again that is in `parts/`, and reads from `state.json` which of the stages after the writing are complete: the first reading, the readings beside real papers, the reading after them, the comparison, the resolving of what the readings left open, the comparison of the running text, and the check of where the elements without a number stand. A stage that was begun and not ended is made again from its start on the parts as they stand, so its sessions are launched again and its bound counts from the beginning. There are two exceptions. The first is a run that was stopped in a narrow repair or in the reading of its changes: `state.json` records the step and the findings, the run goes on at that step, and the readings before it are not made again. A narrow repair that was itself interrupted is made again from the parts as they were read. The comparison of the running text ends in such a repair, and a run that was stopped there, or in the second comparison of the sections it changed, goes on there. The second exception is the stage `resolve`. Once its session has left output that the command accepted, `state.json` records that, and the session is not launched again: the continued run puts the plan and the parts of `resolve/` in place if that was not finished, and goes on with the checks and the reading that follow. A run that came to its end, with exit code 0, 2 or 3, has nothing to continue, and `--resume` refuses it; what such a run left open is taken up with `--open-findings`. Without `--resume` the folder given to `--out` has to be new or empty. When a session of a section fails for good while others run beside it, the command lets those others finish and keeps what they wrote before it stops, so the next `--resume` starts from all of it.

#### Acting on open findings: `--open-findings`

`--open-findings` takes up a run that ended with exit code 2 and acts on the findings it left open. `python <skill>/runtime/paper.py <instance> --out <folder> --open-findings --dry-run` lists them from the last `end` event of `log.json` and does nothing else. Each finding has a number and stands under the check that reported it, with the place it points to, its words, and, under `open because`, the reason it was left open. The same line without `--dry-run` acts on all of them. `--open-findings 2,5-7` acts on the findings with those numbers and leaves the others open as they were. The numbers are those of the list at that moment, so list again after a pass, when the findings that remain are numbered anew. Put `--tex` after it, as after every option.

A numbered statement that the comparison found to differ goes to a narrow repair, and a session reads what was changed, as described above; the statement is then compared with its element again. A sentence of the running text that no element covers goes to a narrow repair in the same way, which cuts it, rewords it, or moves its derivation into the proof that uses it. A statement whose present text was never compared is compared. A finding of a reading is in the list only when the run was made before the command had the stage `resolve`; it goes to a narrow repair as well. After the repairs, every numbered statement whose text the pass changed is compared, once; a statement that differs then is reported as open and is not repaired in the same pass. The running text of every section that the pass changed is then compared with the records once more, whatever the pass changed the section for, and what that comparison reports is open. Lines wider than the text block are not taken up one by one: whenever the pass changes a part, or such a line is chosen, the manuscript is typeset again and every such line of a part goes to repair, because the typesetting cannot tell a line that was open from one that a repair has just made. A line that is too wide in the title, a heading, the author line or the bibliography is text that no repair changes, and it is reported again. The pass ends with a new `end` event and with the exit codes of the table below.

The option refuses a run that has not come to its end, a run that left nothing open, a run in which the machine checks or the typesetting stayed open, and, as `--resume` does, a canon that has changed since the run began. A pass that was stopped is continued with `--resume`; until it has been, `--open-findings` and `--typeset-only` refuse the folder.

#### `--dry-run`, and the correspondence file

`--dry-run` launches no session and writes nothing. It makes the checks that come before the first session, with `--resume` those of a continued run as well, and prints what the run would do next and how many bytes each session would be given. Use it before a long run to see that the folder is accepted and what the sessions will receive. The correspondence file says which element each numbered statement states, with the record's statement, the Lean statement and the paper's statement side by side, the comparison's verdict, and under `record_disagreement` any disagreement the comparison found between the record's statement and the Lean statement of the element; none of this is in the paper. Under `cited` it gives the bibliography key of the source when the paper cites the statement and does not prove it, and null otherwise. The library proves a cited statement as it proves every other, and the paper does not say so. A statement that the paper proves from a cited general theorem by a specialisation names that theorem under `instance_of`, and the list `instances` names every element that the paper takes from such a theorem; the library proves each of these by an argument of its own. The list `others` gives every element without a numbered statement as the plan treats it, and under `in_text` what the stage `placement` found: whether the manuscript has its content, and where; a manuscript that no repair changed has no such check and no `in_text`. The list `not_done` names, each in a sentence, the checks that were not made because a safeguard stopped their session, as described above. A disagreement under `record_disagreement` lies in the canon, and no repair of the paper removes it, so report it to the user. The log lists every session launched and what every check found.

| Exit code | Meaning | What to do |
|---|---|---|
| 0 | The paper is complete: it is typeset, no line is wider than the text block, every numbered statement was compared with its element and found the same, every sentence of the running text that asserts mathematics is covered by an element, and the correspondence file was written from the final parts. A check that a safeguard stopped in every attempt is the exception: it is named under `not_done`, and what this row says of the readings and the comparisons holds for those that were made. With `--draft`: the draft is complete. | Read the paper and the correspondence file yourself before handing them over, with its list `not_done`, and read with the user what the last `end` event of `log.json` lists under `kept`: the findings of the readings that were answered with a reason and not by a change. The author line carries the names of `--title-page`; without that option the manuscript has none, and `--typeset-only --title-page <file>` adds it when the user has decided who signs. |
| 1 | The command refused or failed. | Read its message. When it failed after the run had begun, the folder holds what was made up to that point, and `--resume` with the same `--out` continues from it once the cause is removed. |
| 2 | The manuscript was produced, and findings stayed open after the bounded repairs. | Read the last `end` event of `log.json`, which lists them, or list them with `--open-findings --dry-run`, and report the open findings to the user; do not repair the manuscript by hand. When the user wants findings acted on, `--open-findings` does that for all of them or for the ones the user names. Four kinds of finding can be open: a numbered statement that the last comparison found to differ from its element; a numbered statement whose present text has no verdict of the comparison, because the comparison did not reach it or a repair changed it afterwards; a sentence of the running text that asserts mathematics which no element states, where the narrow repair kept it, or its change was put back, or the comparison of the section that followed the repair reported it; and a line that TeX set wider than the text block and that the repairs did not remove. A finding that a repair took up says under `open_because` why it is still open. Where they stayed open in a later pass over a manuscript whose run had finished them, under `--typeset-only` or `--open-findings`, the manuscript is kept: `--resume` and `--open-findings` refuse the folder, and `--typeset-only` makes the machine checks and the typesetting again, with their repairs. Unless the machine checks or the typesetting stayed open as well, `--typeset-only`, as in the next row, typesets the manuscript and reports the same findings again. |

A repair session is launched only if the typesetting or a machine check fails, or a line comes out wider than the text block. When that repair changes a numbered statement, the statement is not compared again: the exit code is then 2, and the `end` event lists the statement as one whose present text was not compared. Running text that such a repair changes is not compared with the records again, and no event lists it. Only a new run of the command into a new folder compares every statement, and it writes a new manuscript. |

A command line the command cannot read, for example one without `--out` or with an option it does not know, also ends with exit code 2. The command has done nothing then: the message on standard error begins with `usage:`, and the folder is as it was.

#### The TeX command and `log.json`

A TeX command is `tectonic`, `latexmk` or `pdflatex` on PATH, or the command given after `--tex`. `--tex` takes everything that follows it on the command line as that command, so it is the last option. The name of one of the three by itself is run in the way that program needs, with every run that the references and the bibliography take. Any other command, one of the three with options of its own included, is run once, in the folder where the manuscript is typeset and with `paper.tex` appended: it has to leave `paper.pdf` there with the references and the bibliography resolved, and the command does not check that it has. `log.json` is a JSON list of events in the order they happened. The field `event` of each names what it is, such as `session`, `check`, `reading` or `end`, and the last one is an `end` event. An `end` event carries `status`, under `open` what makes the exit code 2, and under `kept` the findings of the readings that were answered with a reason. A `resolve` event gives the parts that the resolving session changed and removed, whether it returned a plan, and its answer to each finding; a `coverage` event gives the sections whose running text was compared and what was reported. A `repair` event that carries `narrow` is the last repair of its findings, and the `changes` event after it gives the verdict on each changed passage and the numbers of the changes that were put back; the texts before and after are in `changes.json` in the folder of the `changes` session. A `placement` event names the elements without a number whose content the manuscript was found not to have. A `safeguard` event names a session that a safeguard stopped, and a `not done` event a check that was given up after every attempt was stopped. The field `kind` of a `session` event names the kind of session, such as `plan` or `repair`. Installing a TeX distribution needs the user's approval.

## Finalizing a finished research

One command turns a finished instance into a package: a folder that holds the proof as a Lean library, a record for each declaration, the dependency map, the paper, a history of the research, an archive of the research's own records, a README and a licence, and that can be archived and published as it stands. The package ends as `solved/<name>/` in the repository that holds this skill.

A program holds the order of the stages and checks each product once, when it is made; a later stage relies on that product and never writes into it, so that no stage sends the work back to a product already made. You start the command and wait; it asks nothing while it runs.

### When the command applies

The command packages an instance whose root is settled by a formal proof, that is, whose `status` gives the root's state as `formal_proved`. It refuses any other state. An instance whose root is `formal_refuted` is refused with the sentence that the packaging of a refutation is not built.

It reads the research from Git, at the commit that is the head of the instance's repository when the command starts, and writes nothing into the instance. A runner that is still finishing its remaining work therefore does not disturb the run, and what that runner publishes afterwards is not in the package. Unless the user wants the package at once, wait until `status` reports that the runner has finished.

The run writes a paper, by the paper command described under "The paper", so the condition given there holds here as well: before the first paper of this user is produced, the user has read and confirmed [the paper method](paper-method.md).

Before it creates anything but its work folder, the command checks the following and refuses with exit code 1 when one fails: the instance is an instance of this runtime with a Git repository; `solved/<name>` does not exist yet; the configuration is valid and the licence text is available; a TeX command is found; the Python that runs the command has PyYAML, with which the freeze reads `formalization.yaml` back; the collection of papers that the paper command reads is complete, after one run of its `fetch.py`, which needs the network; the root is formally proved at that commit; the Lean environment of the instance's settings answers its version command; the freeze can make the package's build files from that environment, for which a Lake project named by `lean.cwd` needs a `lakefile.toml`, whose `[[require]]` blocks become those of the package; and every module that the root's module imported in the first commit is, at that commit, still the file of the first commit, which each later step that writes Lean requires. When the command continues a run whose paper is still to be written, it checks again that a TeX command is found, and refuses in the same way without changing the run, because a paper written without one ends untypeset and no later start takes it up.

### The command and its configuration

```text
python <skill>/runtime/finalize.py <instance> --name <name> [--config <file>]
```

`<name>` names the package and matches `[a-z0-9][a-z0-9-]*`. There is no other option. The models, the CLI paths, the literature server and the Lean environment are those of the instance's `settings.json`; the writing sessions use the first entry of `models` and the checking sessions the first model of the `review` role, so that by default a different model checks than wrote. The library is packaged on the Lean toolchain the research used.

The configuration is a JSON file in which every field is optional. A key the command does not know is refused by name.

| Field | Default | Meaning |
|---|---|---|
| `authors` | `[]` | A list of objects with `name` and optionally `address`, `email`, `orcid`, `github`, each a text that is not empty: leave out a field that an author does not have, since the command refuses an empty one. `address` and `email` go to the title page of the paper, `orcid` and `github` to `lean/formalization.yaml`. An empty list means that no author is named anywhere: the paper has no author line and no file of the package names an author. |
| `licence` | `"CC-BY-4.0"` | An SPDX identifier. The text comes from `finalize/licences/<identifier>.txt` in the skill, which ships CC BY 4.0; a value without such a file is refused. |
| `human_review` | `{"status": "none", "reviewers": [], "notes": ""}` | What a person reviewed. `none` says that no person reviewed the proof or read the Lean statement against the proposition. The other values of `status` are the registry's words, `self-assessed`, `peer-reviewed` and `author-verified`, or a free text. `reviewers` is a list of the names of the people who reviewed, each a text that is not empty; the command refuses any other form. |
| `parallel` | `8` | How many sessions run at once, over all stages together. |
| `tex` | `null` | The TeX command as an array; it is run as "The TeX command and `log.json`" above says of the command after `--tex`. `null` takes the first of `tectonic`, `latexmk` and `pdflatex` on PATH. |

The authors and the human review are facts about the user, so ask for them before the first start and write nothing the user did not say. An author's `orcid` is the ORCID iD, as the bare identifier or as its `https://orcid.org/` address, and `github` is the GitHub login. The command does not check that either exists. Where the user gives one of them for an author, that author stands in `lean/formalization.yaml` as a mapping of the name and what was given, which is the form in which the registry reads an author; an author without them stands there by name alone, and the list of responsible maintainers holds names only. When an instance of this runtime was created, its user read and confirmed the root's Lean statement; whether the package is to say so, and under which status, is the user's to decide. An empty author list is a legitimate answer: it is the default the user chose, and the report then lists what has to be filled in before a submission. The configuration cannot be changed once a run has begun, because a continued run confirms that it is the configuration it started with.

The command stays in the foreground until the run ends, which is far longer than a shell tool waits, so start it as a background process with its output in a file. It launches many sessions, among them several for each part of the library, for each group of records and for each dozen events of the history, and those of the paper. Tell the user beforehand that the run draws on the account's usage accordingly, and that its sessions run as "The paper" above says the sessions of the paper command do, unattended and with the same access. When a provider refuses a session, the run waits and starts it again as "The paper" says for the paper command, and the `session` events of its own `log.json` carry the same `refused`, `refused_until` and `usage_limit_until`. When the provider still refuses after those waits, the run stops with exit code 2 and `report.md` names the reason; no part of the library is discarded for it, and the same command continues the run once the provider takes sessions again.

### What the run does

The run has seven stages. Each ends with a check that the program makes, and the next stage starts only when the products it reads have passed theirs. `report.md` and the `step` events of `log.json` name a step by its id: `1-selection`; in the library stage `2.1-take`, `2.2-review`, `2.3-simplify`, `2.4-merge`, `2.4-arrange`, `2.5-records`, `2.6-draft`, `2.6-sources`, `2.6-foldback`, `2.6-records`, `2.6-compare` and `2.7-freeze`; `3-archive` and `3-history`; `4-map` and `4-paper`; `5-documents`; `6-check`.

**Start.** The command pins the commit, copies the research from Git into its work folder, and starts a Lean broker of its own, whose store it seeds from the instance's, so that modules the run leaves unchanged are not compiled again. Every compile until the freeze goes through that broker, which admits compiles against the machine's free memory.

**Selection.** One session studies the proofs the research offers and chooses which one the package presents: a main theorem, and a proof of the root that rests on it. The options include a stronger theorem from which the root can be derived although the research never derived it; the session then writes the derivation, and the program compiles it. The standard is the user's: research standards are required, insight ranks first above that, then elegance and conciseness. A second session, of the checking model, checks every statement of fact in the decision against the canon, and the decision is made once more if a correction changes a ground of the comparison or concerns a text that later steps take as the decision has it: the sentence that states the result and what the decision says for the registry, which the package prints, and the account of the chosen proof, from which the paper is planned and the README's outline is written. The choice, the runner-up and the reasons go into `decisions.md`.

**The library**, in seven steps. A script takes from the canon what the chosen theorem and the root rest on, by whole elements, and never touches the definition modules. One session reviews the whole library and divides it into parts. One session for each part simplifies it, side by side, with the statements that other parts use held fixed. A script merges the parts, and one session reads the entire library and arranges it by subject. Records are written for every declaration that is new or changed, each is compared with the Lean by a session that did not write it, and one session with the literature server finds and checks every cited source. For every sentence of a record that cites a work, in its header or in its text, that session keeps the words of the work at the place cited, and the program requires them for every citation; a work that could not be opened is cited by no record. These quotations go to the paper with the draft, and the paper's sentences about cited works are compared with them. A record names a work in its header as the source of its result only while the work states the result in the form the library has, since the paper cites such a work in the place of a proof. Where the session takes the header key out, because the work states another form or could not be found or opened, the paper proves the result, and a record that was not written in the same step is then written from the Lean and compared like the others; `decisions.md` lists these records. The paper's statements are then drafted and compared with the declarations. Before anything is changed, the session with the literature server searches for sources of the results the draft asks to cite: a source that states a result in the form the library has is entered into its record, and one that states a stronger or a more general form becomes a gap of the draft. A general theorem of which a result is an instance is reported with the specialisation and asks nothing of the library: the paper states the result, cites the theorem and gives the specialisation as its proof, and `decisions.md` says so. What the draft wants and the library lacks, the forms that such sources state, and what the record writers found in the library are then put into the library in one pass. Where the library could be given a source's form, the source is checked against the new declaration and entered, and the paper cites it; where it could not, the library keeps its form, the paper proves the result, and `decisions.md` says which source states what. A record whose statement in words the draft's comparison found to say more than its Lean statement is written again and compared, so that a true remark inside a statement does not reach a numbered statement of the paper. Last, the library is frozen: the build files are written, one Lake build of the published layout is made, the files the registry asks for are generated, and every file is hashed. After the freeze no Lean file and no record changes.

**History and archive**, beside the library stage. A script archives `canon/` and `knowledge/` of the pinned commit, with the account name of the machine's user replaced by `<account>` wherever a member gives a path of that user's home folder. Sessions write one timeline entry for each event of the research, in plain words and with the path of the record it condenses, and other sessions check each entry against that record.

**Map and paper.** The dependency map is drawn from the frozen library, and the paper is written from the draft by the paper command. What its readings leave open is resolved inside the run, by a session that may change wording and structure within the frozen library. Every sentence of running text that asserts mathematics is compared with the declarations, and every sentence about a cited work with the words that were kept of that work. The title page carries the subject classification that the selection chose for the registry.

The paper stage ends without a person. The library is frozen, so the paper is brought to the library and never the other way. A sentence or a formula of the running text that no declaration covers goes to one repair, which cuts it, rewords it, or moves a derivation into the proof that uses it; a sentence about a cited work that the kept words do not support goes to the same repair. If the comparison after that repair still finds the passage, a session deletes the passage and mends the text around it, and the program checks that the passage is gone, that every numbered statement is as it was, and that every changed passage became shorter. A deletion asserts nothing, so nothing compares the text for its sake. A numbered statement that still differs from its declaration after the comparison's one repair is restated by a session as the declaration says it, the program checks that only that statement and its proof changed, and the statement is compared once more; the verdict is recorded and nothing follows it. Where a repair session that the machine checks or the typesetting ask for then changes a section, the running text of that section is compared with the declarations once more, and a passage that no declaration covers then stays in the paper. Each passage that was removed, each statement that was restated and each passage that stays is listed in `decisions.md` under "Stage 4: what the paper lost so that it says no more than the library", with the declaration that came nearest, so that the user can judge whether the library should have had it. A statement that still differs after its restatement, a passage that stays, and a line that is still wider than the text block, do not stop the run; `report.md` names them under what was not verified.

**Documents.** A script writes the README, the licence file and the manifests, every figure in them read from the finished products. One session writes the README's two prose sections, one session that has only the package reads the documents against it, and what it finds in the prose is corrected. What that reader finds anywhere else stands in a sentence the program writes or an earlier stage fixed. It does not stop the run: `report.md` lists each such finding under "What the reader of the package found and the run did not correct", and `decisions.md` has them too. Report them to the user; a fault of the program is repaired in the program.

**Final check.** Made once: every link resolves inside the package, no file holds the account name inside a path of a home folder, no document the run wrote holds a path of the machine, every text file ends its lines with LF, and the hashes of the library and the records are those of the freeze. A file that holds the account name as a word by itself does not stop the run, since an account can be named `root` or `lean`: `report.md` lists such files under "Where the account name stands as a word by itself", and the user judges them. The archive's members are the research's own bytes and are not read for their line endings. The frozen library is not checked a second time: a library is verified when it compiles and Lean reports only the allowed axioms for the theorem, and the run makes no replay and runs no comparator. Then the package is moved to `solved/<name>/`, an entry is added under "Solved problems" in the repository's `README.md`, and the temporary files are deleted.

### The work folder, and continuing a run that stopped

The run keeps everything that is not the package in `<repository>/.skill-workspace/finalize-<name>/`. While it runs, read `log.json` there for every session launched and every check made, in order, and `decisions.md` for every choice a stage made, with its reason. Each session has a folder under `sessions/` with its prompt, the files it was given, what it returned and the CLI's logs.

| Exit code | Meaning | What to do |
|---|---|---|
| 0 | The package is in place. | Read `report.md` and `decisions.md`, then the README and the paper, before you report to the user. |
| 1 | The command refused before any work. | Read its message, remove the cause, and start it again. |
| 2 | A stage could not meet its check. | Read `report.md`, which names the step, the check and what the check found. Remove the cause and give the same command again. |

A command line the command cannot read, for example one without `--name`, also ends with exit code 2. The run has not begun then: the message on standard error begins with `usage:`, the command has made no work folder, and a `report.md` that lies there is that of an earlier run.

A simplification that fails its check, whether one part's, the arrangement or one part's last changes, is discarded: that part of the library keeps the form it had, the run goes on, and `decisions.md` records it. A part is discarded for what its sessions wrote: when the CLI of each of its sessions ended with an error before the session wrote anything, as in an outage, the run stops, and the same command tries the part again. Any other step that cannot meet its check stops the run.

The paper stage ends without a person, as "What the run does" above describes, so it stops a run only when machinery fails:

- a session leaves no output the program can use, in two attempts for most tasks and three for the session that deletes or restates;
- a safeguard of the AI system stops, in every one of those attempts, a session that makes something the run needs;
- a provider still refuses a session after the twelfth wait;
- the manuscript still fails the paper command's machine checks, or TeX still fails on it, after three repair sessions;
- the TeX command cannot be started, or the command is interrupted.

In the first three cases and the last the same command, started again, continues the paper where it stopped. In the fourth the next start does one of two things, and `report.md` says which under "What to do". Where the manuscript failed in the run that wrote it, that run ended before its readings and its comparisons were complete: the next start deletes the manuscript and writes the paper anew from the draft. Where the manuscript was finished and failed in the pass that deletes passages and restates statements, it is kept: the next start makes the machine checks and the typesetting once more, with up to three repair sessions, and then closes what is still open. If the manuscript fails there as well, the start after that deletes it and writes the paper anew.

A safeguard of the AI system can stop a session of any stage, and the run treats it as the section "The paper" describes for the paper command. When every attempt was stopped, a session that makes something the run needs stops the run, and `report.md` says under "What to do" that the same command starts the same session again. A session that is a check is recorded as not done, and the run goes on: beside the checks of the paper command these are the reading of the selection's claims, the comparison of a group of records with the Lean, the reading of a group of timeline entries, and the reading of the package's documents. The records and the entries of such a group stand as they were written, with the verdict `not compared` or `not read`. The comparison of the draft with the library after the fold-back is no check in this sense: it decides which drafted texts stand, so the run stops without it. The README of the package names every check that was not made, under "What was checked, and what was not", `report.md` names them under what was not verified, and `paper/correspondence.json` those of the paper.

A run that stopped is continued by the same command with the same arguments. It confirms that the instance, the pinned commit, the name and the configuration are those of the run, and goes on at the first step that has not passed its check. It goes on with the settings it read from the instance's `settings.json` at its first start, so a change made to that file since then does not reach it. A step that was begun and not ended is made again from its start, except for its sessions whose output had already been accepted.

Under "What to do", `report.md` of a run that stopped says what the user does before starting the command again. Often that is nothing: where sessions left no usable output, a new start launches new sessions. Report that section to the user as it stands.

Do not repair a product in the work folder by hand. Before a step reads a product, the program compares it with the hash recorded when it was made, and a difference stops the run and names the product; nothing is silently made again. The causes you can remove lie outside the products: a missing TeX command, a Lean package that does not stand at the revision of its manifest, an account that cannot launch sessions, a fault in the program itself. If a product was changed, put it back as it was. A run that cannot be continued is abandoned by removing its work folder, after which the command starts anew.

### What the run leaves, and what to tell the user

After a run that came to its end there are three things: `solved/<name>/`, complete; one entry under "Solved problems" in the repository's `README.md`; and in the work folder `report.md`, `decisions.md` and `log.json`, with everything else deleted. After a run that stopped, the work folder is whole. Nothing is committed and nothing is pushed.

`report.md` says what was made, each check with what it established, what was not verified, what the user fills in before a submission to the registry, and where `decisions.md` is. Report to the user from it, in its scope:

- the path of the package, the main theorem the selection chose, the runner-up, and that the reasons are in `decisions.md`;
- what was established and by what: the Lake build of the published layout, and the axioms that Lean reports for the root and for the main theorem, as the report names them, none beyond those the instance allows; the definition modules and the root's statement unchanged by hash;
- what was not verified, as the report lists it. Among it: no person reviewed the proof unless the configuration said so; the classification codes were checked for their form and not against the registry's lists; the registry's comparator was not run; and each check that was not made because a safeguard stopped its session, which the report names one by one;
- which simplifications were discarded, which gaps of the paper's draft were not closed, which sources were removed, and which findings of the paper's readings were answered with a reason and kept, as `decisions.md` records them;
- that nothing was committed. Committing the package is a separate step that the user asks for.

The package is prepared for the Palomar registry and is not submitted. Tell the user what a submission still needs.

- `lean/formalization.yaml` requires human authors and responsible maintainers. With no author configured, both lists are empty, and the user fills them in.
- The registry takes the tools with which it renders and exports a submission from the Lean release of the submitted library. A submission can therefore fail there because of the release alone, with a library that passes every check; the registry also accepts releases only from a minimum upward, which it changes. The report names the package's release. Before submitting, the user reads the registry's open issues for that release, and its present minimum. The command reports this, asks nothing of the network and checks neither.
- The registry's review asks what the result is in the literature. The README's part "Where the result comes from" and the sources in `lean/formalization.yaml` say what the research's records hold: whose conjecture or question the result settles and where that was posed, on what grounds the result is recorded as original or as known, what each source has of it, and which earlier formal proofs the records name. The run writes no claim of interest or novelty of its own. The report lists what only the user can add: what the user knows of the result's place in the literature beyond the records, an earlier public account of the result that the records do not name, earlier formal proofs when the records name none, and for each source whether its authors were contacted (`author_endorsement`).
- The report names any rule of the registry that the research itself cannot meet, such as the size or the imports of `Challenge.lean`, which follow from how the root was posed. The package is complete all the same, and the registry will not accept it as it is.
- A package is submitted as a repository of its own, with `lean` as the project directory. The registry reads the one licence file at the root of the submitted repository and requires every `.lean` file of that repository to be written in Lean's module system. A repository that holds the package among other things, under a licence of its own or beside Lean files that are not modules, does not satisfy that. The layout of the package is made for this: `LICENSE` stands at its root and everything the registry reads stands under `lean/`.

## Commands

Every command below is `python <skill>/runtime/runner.py <command> <instance> ...`. Exit code 0 means that the command did its work, and it then prints its result as JSON on standard output; exit code 1 means that it refused or failed, and a refusal gives its reason as `{"error": "..."}` on standard error. `init` is described under Create and start.

| Command | Effect |
|---|---|
| `start` | Launch the detached runner when none is alive, such as after a crash or reboot, checking its new readiness record. It does not replace a live runner; to restart one, end its process first, as "Restarts, runner failures and installation updates" below explains. |
| `run` | Run in the foreground for observation; remains attached until the runner exits. |
| `status` | Read current liveness, mathematical state and operational queues. |
| `stop` | Stop new dispatch. Running CLI turns finish; pending reconsideration turns and queued follow-ups wait. The runner process stays alive; `resume` lifts the stop. To end the runner itself and leave it ended, wait until the running CLI turns and the publications have finished, confirm that `status` still gives `runner_alive` as true, because `runner/process.json` goes on naming a runner that has exited, then end the process that the file names; `start` brings it back. A session held behind the stop for its next turn stays `running` through that wait, with `waiting_dispatch` in its `end_check`: it goes on after `resume`, or ends through `kill-session`. |
| `resume` | Remove the dispatch stop. If the runner is not alive, also use `start`. |
| `reconsider-attempts` | Request one reassessment of work availability, overriding an occupancy report. Attempts then launch one at a time, each a reassessment, until one registers a section; this holds even when no occupancy report was in force. Does not remove a dispatch stop. |
| `input --file <file>` | Preserve standing information for future launches. It does not notify running sessions of new instructions. |
| `message <session-id> --file <file>` | Send the text of the file into the identified running session as a message from the operator; "Context, continuation and acceptance settings" above says how and when a session receives one. The command prints the path of the file that waits in the session's `messages/`. It refuses a session that is no longer running and a session that receives no messages. |
| `review --element <name>` | Request a comprehensive review of published elements; `--element` may be repeated, and takes the declaration name as the canon shows it. `--concern <id>` and `--reason <text>` can identify the issue. A request that names no element and no concern is refused, because the reviewer would have nothing to examine, and so is one that names an unknown element or concern. |
| `organize` | Request an organizer session. Its batch is the published changes not yet in an organizer's batch, and the session is launched also when there are none. |
| `questions --file <file>` | Place questions of your own on the frontier as an operator publication, without peer or review, as "Place questions on the frontier" above describes. |
| `kill-session <session-id>` | Cancel the identified session's pending resumption and terminate its current CLI after confirming its OS creation identity. The session ends as an interruption: retained producing work still goes to peer, a producer that left no research material is launched again, and an interrupted peer, review or organizer stage passes to a replacement session, as Waiting, fallback and recovery describes. |
| `render` | Rebuild the derived views while the runner is off. |
| `restart-broker` | With dispatch stopped and running CLI turns, publications and compiles finished, replace the broker after an environment change. Sessions held behind the stop for their next turn do not block it; the result lists them as `held_sessions`, and they continue with the replaced broker after `resume`. A session whose work is still being published does block it, and the refusal names that session among those whose publication is to finish; publication goes on under the stop, so run the command again once `state.publication` and `state.publish_queue` in `status` are empty. |

Use status to identify the intended session before termination. The command targets that session's CLI, not arbitrary processes on the machine, but ending the CLI also ends the session: its host then exits, and on Windows, where the session's `process-job.json` records that containment was applied, the system ends every process the session started, as Waiting, fallback and recovery describes. The broker cancels its compiles after observing that the session has ended. Where containment was not applied, including on Linux, computations the session started can outlive it; interpret them from their retained outputs and actual process state.

The runner reads `review`, `organize`, `reconsider-attempts` and `questions` requests on its next pass, so a request made while no runner is alive waits until `start`. This includes a finished instance: once the root is formally settled and the remaining work has ended, the runner exits, and a later `review`, `organize` or `questions` request takes effect only after `start`, whose runner then continues until that work has ended. For a `questions` request that work is the publication alone: while the root is formally settled the runner launches no new exploration, as "Read progress and results" above says, so the questions stand open on the frontier and no explorer takes them up. Each of these commands prints the path of the request file it left. The job that the runner makes of a `review` or an `organize` request stands under `state.jobs` in `status` as `operator:` followed by the name of that file without `.json`, and once the session's output is published the job's `record` names its folder under `knowledge/reviews/` or `knowledge/organizations/`.

To end a whole run before the root is formally settled and the remaining work has ended, and not its runner alone, take these steps in order. Run `stop`. Let the running CLI turns finish, or end them with `kill-session`, and run `kill-session` as well for each session that waits behind the stop for its next turn, because its host is a process that stays until then. `kill-session` is a cancellation, and a peer that it ends passes its stage to a replacement peer, which makes the candidate again. A peer that waits behind the stop keeps the candidate it prepared when its host ends in another way, as it does when the machine is restarted or when you end the process whose `pid` stands under `host` in the session's entry of `state.sessions`: its output then goes to the transport check and, if it passes, to review, as "Session hosts and continuation turns" below describes. When `status` shows no session as `starting`, `running` or `publishing`, end the runner's process as the row of `stop` says. Then end the Lean broker, the process that `runner/lean/process.json` names: the runner never stops it, and it exits by itself only once the instance has finished. End each of these processes by its ID and never by its name, because the runner, the session hosts and the broker of every instance on the machine are all Python processes. This deletes nothing in the instance, and `resume` followed by `start` continues the run with the work that was pending.

Every command of this runtime refuses an instance that the earlier runtime created, whose knowledge was a repository of records and not a Lean library.

## Waiting, fallback and recovery

### What creates new work

When a producing session ends, its retained material creates peer work. A peer output that passes its **transport check**, the check that a finished session's output has the structure and references the runner needs to carry it to the next stage, is copied to the folder `candidate` of the peer's session, is frozen there as a candidate and creates review work; that check does not judge the mathematics. A review that decides to publish puts the candidate into the publication queue, described next. Available capacity and an available configured model permit each launch.

A formalizer is created for a settled statement that the root rests on, through any of its proofs, and that has no formal proof yet; once a refutation of the root is settled, the same holds for the refutation and the statements it rests on. The runner gives it one proof of that statement: among the proofs that settle the statement, with the statement's own declaration first and the others in the order of their names, the first that is not formal and whose named statements all have formal proofs. That proof's Lean text usually ends in `sorry`. It can also be complete and still not formal, when it names a declaration whose own Lean proof ends in `sorry` although that declaration's statement has a formal proof under another declaration, or when it uses an axiom the instance does not allow; status then shows a formalizer on a proof with no `sorry` of its own, and that is intended. Until there is such a proof, no formalizer is launched for the statement, so formal proofs are written from the bottom of the root's proof upward, and the root itself is given to a formalizer once it is settled and everything its proof names is formal. The runner reads what the formal proof will need from what the written proof names in Lean. One formalizer at a time works on an element, and it holds that element whole.

The organizer is created when the number of published changes that no organizer has yet taken into its batch reaches `organizer_every_records`. Organizer outputs and comprehensive reviews do not count toward that number. A concern or a contested statement creates comprehensive review work, as Read progress and results describes.

### Publication of a candidate

Publications are queued and made one at a time, because each changes the one library that every session reads and that every later candidate is built on. For a candidate, the runner copies the canon's library and applies the candidate to the copy without the replacements review declined. When that changes a Lean file, it builds every module of the library through the broker and extracts the structural index of the modules that changed and of every module that imports one of them, directly or through others; a candidate that changes only written files needs no build. The importing modules are extracted again because Lean reads a declaration in the environment its module imports: when a change enlarges that environment, for example by an import of a Mathlib module that brings another instance into scope, Lean can turn an unchanged statement into another term, and the check that no statement changed in place then finds it. The same extraction asks Lean for the axioms that each declaration of those modules depends on, as "What makes a statement formal" describes. A module whose source and whose imports' compiled output are unchanged comes from the broker's cache, so most of a build is usually reuse. The runner then repeats the checks a machine can decide: no statement changed in place, every added declaration has a record and every record a declaration, no axiom was declared, no definition contains `sorry`, and Lean confirms each claim that one declaration proves or refutes the statement of another. Only then does it write the event, put the changed files into `canon/`, write the records, the approaches tried with review's assessment of what the work contributed, the understanding texts, evidence and bibliography entries, and commit.

While this runs, `status` shows the publication under `state.publication` with its stage (`apply`, `build`, `check`, `commit`) and the waiting ones under `state.publish_queue`. A session whose work waits there has the status `publishing` and still counts toward `max_sessions`, so a queue that grows because builds wait for memory also holds back new launches.

A candidate was frozen when its peer's session ended, and other publications have changed the canon since. Statements never change in place, so what the candidate rests on is still there. It can nevertheless fail to apply or to build, through no defect of its mathematics: another publication replaced the proof it replaces, a new module's path is now taken, two candidates introduced the same name, or a machine check fails on the canon as it now is. A candidate that would not build would break the canon for every session, so the runner does not publish it. The work goes to a replacement peer, which receives the producer's work, the earlier peer's work and the reason, makes a new candidate, and that candidate receives a new review. An organizer's change that fails in the same way is made again by a replacement organizer. A build can also fail for a reason that is not in the candidate's files: the system ended a Lean process of the build, or one of its compiles was running when the machine went down. The runner does not build the candidate a second time, and the work takes the same path. The pending job's error in `status` names the reason.

### Session hosts and continuation turns

An attempt, explorer, formalizer or peer's host can keep the same logical session alive across several CLI turns. After an ordinary turn exit, it resumes the exact native conversation with the same provider, model, effort and launch-time instructions. A current `output/end-decision.json` or the configured resumption limit authorizes normal handoff. Each request has a fresh ID, so an older decision cannot authorize a later ending. [Retained work](retained-work.md) describes the session's side of the protocol. This does not create another attempt, another occupied section or question, or another concurrency slot.

The host of a review or an organizer keeps its session alive in the same way, for a different reason. Such a session ends with its output, an assessment or an organization, and writes no end decision. When one of its turns ends and the output does not pass the transport check, the host resumes the same conversation and tells it what the check found, at most `max_end_resumptions` times. A reviewer's turn can end while the sub-reviewers it delegated to are still at work, and without this the whole review would be made again by a new session. The authorization in the session's `end_check` record then has the basis `output_checked` when the check passed, and `resumption_limit` when it still failed at the limit; in the second case the runner starts a new session for the stage, as it does after an interruption. One finding of the check is not put to the session, because no turn of the review can undo it: that the files of the candidate under review changed after the review was assigned. When the check finds that and nothing else, the host resumes nothing, and the authorization has the basis `output_checked` although the check did not pass, with the finding as its `explanation`; the runner then deals with the candidate as "Refusals, failed outputs and damaged candidates" below describes.

`status` exposes the host's `end_check` record in each session's state, including `maximum`, `resumptions`, `status`, the current request and `authorization`. A host waiting behind the dispatch stop reports `waiting_dispatch`; a provider/model availability block reports `waiting_provider`. It retains its existing slot and scope while waiting. `resume` allows it to proceed once the availability block has also expired. The host survives runner restart, and the runner collects the logical session only once after the host and CLI have ended. Host loss is recorded as an interruption, without inventing a worker end decision.

The session root retains its initial prompt and CLI streams; `turns/0001/` and later directories retain each resumed invocation separately, with its prompt, command, process receipt and CLI streams. The archiver later moves each `cli.stdout.jsonl` among them into `raw.tar.xz` in the session folder; "Retention and archives" below says when. A decision file the session submitted is not role output: at the end of each turn the host moves `output/end-decision.json` into that turn's directory as `submitted-end-decision.json` before checking it, and writes its check of a decision that answers a request beside it as `decision-check.json`.

`end-check.json` contains the authorization and its issuer, `source: worker` for a valid decision of the session and `source: runner` for every other. At the limit of `max_end_resumptions`, the host issues the same end authorization that permits the handoff to peer or review, with `basis: resumption_limit`; it does not wait for operator approval or resume indefinitely. That authorization is an operational limit; it is not the session claiming completion or an impasse. With the default of 1000 a session is not expected to reach the limit, and nothing else counts its turns: a producing session or a peer that ends turn after turn without a valid decision, a review or an organizer whose output keeps failing the transport check, and a session whose responses keep exceeding the output cap are each resumed again. Every resumption is a new CLI invocation on the whole conversation, to which it adds the continuation text. Short of the limit such a run ends with the session's own decision or an output that passes, with an interruption, or, for a Claude session that receives messages, when its conversation fills, on which its task passes to a new session as the last paragraph of this section describes; the conversation of a Codex session is compacted and does not fill. `resumptions` in the session's `end_check` shows how many resumed turns it has had, and `kill-session` ends it. A valid `no_research` outcome or an interruption ends the session without a reconsideration turn; the recorded end authorization then has `basis: no_research` or `basis: interrupted`, and an interrupted session keeps its usual processing. A Claude turn that ends because one response exceeded the CLI's output-token cap is not an interruption: the CLI discards only that response, so the host resumes the same conversation, reporting the CLI message as the previous turn's problem. Such a resumption counts toward the maximum; when the maximum is already reached, the host issues `resumption_limit` with that message.

Missing native identity or an identity change is recorded as `resume_unavailable` rather than silently starting a different conversation. Like the resumption limit, this runner authorization ends the session without interruption: a producer's retained work goes to peer, and a peer's output goes to review once it passes its transport check. A provider refusal or failed invocation of a resumed turn is instead recorded as `interrupted` and ends this continuation through the usual interruption path, except for a peer. A peer is resumed only after an earlier turn of it had ended, so that turn may have left a prepared candidate, and the candidate is not discarded. The same holds for a peer whose host is lost after it has recorded the request of the resumed turn, as every host is when the machine goes down: while it waits to start that turn, behind `stop` or an availability block, or while the turn runs. In all these cases, unless `kill-session` cancelled the session, the runner puts the peer's output to the transport check as it does after `resume_unavailable`. A candidate that passes is frozen and goes to review, and `status` then shows the peer as `ended` with `basis: interrupted`; one that does not pass leaves the stage to a replacement peer, as after any other interruption. A peer whose host is lost during its first turn is replaced. Availability handling still applies to later sessions.

A task can pass from one session to another of the same role. The request of the host's message at 800,000 tokens, under "Context, continuation and acceptance settings" above, accepts a third basis, `handed_over`, beside `task_completed` and `no_way_forward`; in a resumed turn the message opens no second request and names the one that started the turn. A valid decision on any of the three ends the session without a further turn, also in its first turn. A session that ended its turn without such a decision is resumed with that same request, and the prompt of that turn ends with the text of the message, which may not have been handed over yet. A review or an organizer writes a decision only to hand its task over; otherwise its output ends it as before. When a turn of a session that receives messages ends because the conversation reached the window, the `result` event of the CLI names `terminal_reason: blocking_limit`. A valid decision that a producing session or a peer wrote in that turn, before the request that was refused, ends the session on its basis all the same. Without one the host authorizes the end itself with `basis: context_limit`; no provider refused anything, so no block follows. On `handed_over` and on `context_limit` the runner records the session as `ended`, sets its job back to `pending` and adds the session's folder to `continues` in the job's task. It sets no delay and blocks no model, and it sets the job's count of failures back to zero, so a later failure of the task waits the first retry delay again. The job's next session is a new one, with a folder of its own and the pack of its role as it then stands; the pack says that it continues the task and names the report of the session before it, `output/report.md` for a producing role and `work/report.md` for a peer, a review and an organizer. The sections and the question stay held throughout: the pipeline names the ended session until the next one is launched, a producing session's `declaration.json` is copied into the new session's folder, and a peer's sections stay with the pipeline as after a replacement. Such a job is not a fresh launch. What "Launch priority and spacing" requires of a new attempt or exploration does not hold it back, it does not count as an attempt launch, the root's completion does not cancel it, and its question is not counted as free while it waits; it waits for a free slot and an available model, at the head of the order that section gives. Nothing goes to a peer or to review until a session of the chain ends on another basis, and the runner sets no limit on the number of sessions in a chain, so a task that does not yield holds its sections and a slot for as long as its sessions hand it on. `kill-session` ends the running session of a chain as it ends any session, with the usual processing of an interruption. To see a chain, read `continues` in the job's task in `status`, or in the session's `input.json`, and the `basis` of each earlier session's authorization. A session without `messages/` is sent no message, keeps its compaction and ends on neither basis.

On Windows the host places itself in a job object before its first turn. Processes the session starts inherit membership, including computations detached with `nohup` or left in the background, and the system ends them all when the host exits: after the last turn, through `kill-session`, or if the host dies. The job does not let a process leave it. Git Bash asks to leave on every program it starts whenever its job permits that, so a job that permitted it would not hold the computations a session runs from its shell; a tool that explicitly asks to leave is refused and does not start. Two kinds of process are outside the job. The Lean broker is shared and not session-owned, so a session held in such a job never starts it: a broker started inside the job would end with that session. [The Lean broker](lean-broker.md) says, under "How the broker lives and recovers", who starts the broker and what a contained session's client does when it finds none. Processes started on a session's behalf by a service, for example through COM or `wsl.exe`, were never in the job. `process-job.json` in the session folder records whether containment was applied; when it could not be, the session runs uncontained, as every session on Linux does.

### Launch priority and spacing

A job whose task was handed over, as "Session hosts and continuation turns" above describes, comes first, whatever its role: the sessions of a chain do the work of one long session, which would have kept its slot. After it, priority is review, peer, formalizer, organizer, eligible explore, then attempt. Fresh attempts require free capacity, at least `launch_interval` seconds since the previous attempt or exploration launch, and an element among the work that remains in the frontier that no pipeline holds whole and for whose lease no session is waiting. The runner does not judge whether mathematical work remains on such an element; that is the judgment of the attempt it launches. Attempts and explorations share the one spacing, which gives each new attempt or explorer time to take its lease before the next one reads the board. An exploration is eligible when exploration is requested, a question is free for it and the same interval has passed; the paragraphs on explorers and their questions further below explain when a question is free and when exploration is requested. Each role waits only for its own object, attempts for an available element and explorers for a free question, so a request that no free question can serve does not hold attempts back. The runner fills free capacity in this order before it launches a fresh attempt, so when every slot is in use, a slot that opens goes first to a task that was handed over and then to waiting review or peer work. Work that waits for something other than capacity leaves a free slot to the work after it, attempts included: a handed-over task, a review or a peer waiting out a retry delay or for an available model, and a comprehensive review or organization pass waiting for another of its kind. Comprehensive reviews launch one at a time, as organizers do, so a requested review or organization pass waits, without an error or block in `status`, while another of its kind is running. Running sessions are not preempted when higher-priority work appears.

### Attempts that find no work

An attempt that only checked availability can write `disposition: no_research` in `output/outcome.json`. It must have registered no section and begun no mathematical investigation. An explorer that found no free question to occupy can end the same way; it must occupy no question, and its outcome carries no availability report. When the session exits successfully, the runner retains that session's files and conversation and closes the pipeline without peer or review. The session stays closed regardless of later changes in available work. Failed research and interrupted investigations still go to peer.

The attempt can also submit an `all_unresolved_work_occupied` report with the snapshot token from its coordination updates. The token identifies the elements that remained and the sections registered on them when the attempt looked; that snapshot is kept in the session's `availability/` folder. The runner evaluates that report separately. An invalid or stale report does not prevent the session from closing, but it cannot suppress dispatch. An accepted report stops the runner from launching fresh or pending attempts while the reported occupancy remains applicable, except an attempt whose task was handed over, which continues work that is under way.

The runner waits until one of three changes occurs: a section's occupancy ends on an element that is still among the work that remains, an element newly appears among the work that remains, whether it is new or a finding withdrew the confirmation of its proof, or the operator requests reconsideration. Occupancy ends through publication or a completed review decision that there is nothing to publish; releasing a lease or leaving its queue does not end it. Elapsed time, publications that add no work that remains, organization changes and sections that other sessions newly register do not end that wait. The runner then permits one reassessment attempt at a time. Once an attempt registers work, normal scheduling resumes. Another applicable report of full occupancy makes the runner wait again. An interrupted reassessment can be replaced, and any research it retained follows the ordinary processing path.

`status` reports this wait or reassessment under `attempt_dispatch`, with the reporting session, snapshot token, current grounds and any reassessment session. Use `reconsider-attempts` to request reassessment explicitly; an older report cannot undo that request, and a stopped instance still requires `resume` before any new session can launch.

Full occupancy also requests exploration, so capacity that attempts cannot use goes to understanding while they wait.

### Explorers and their questions

Explorers occupy **questions**, the frontier's objects of understanding; the workers' [common introduction](common.md) defines them. Several explorations can run at once, each holding a different question, and a question stays occupied through its exploration's peer and review. An organizer's merge is the one exception to a question's single holder: when two questions that explorations already hold are merged, both explorations keep the merged question, each until its own pipeline ends, because each took its question rightfully and the merge does not cut work short. The question is not free while either occupation lasts, so no new explorer duplicates their work, and it becomes free once both have ended; `status` and the board then show two explorations on it.

A question is **free** when it is open, no unfinished exploration holds it or was assigned it, and no live session holds or waits for its lease. One case is counted differently. An exploration whose launch ended without research material waits to launch again, and until then its pipeline still names the failed session, whose declaration may still record the question that launch held. `status` and the board show that session holding the question, though no live explorer does, and when the runner launches a waiting exploration it does not count such a question as occupied.

The runner launches one more explorer only while the free questions outnumber the explorers that have not yet chosen one, so that every explorer launched can find a question of its own. When question `q0` is free at launch, the runner assigns it to the new explorer and records the occupation before the session starts; otherwise the explorer chooses among the free questions through the question lease. While `q0` is free in this sense, the question commands refuse every other question, so an explorer still choosing when `q0` becomes free takes it.

Exploration is **requested** by a single flag. Two events set it: an attempt launch when the count of attempt launches reaches a multiple of `explore_every`, every launch by default; and the runner finding spare capacity while no element of the work that remains is available to a new attempt or while attempt dispatch is suppressed. The second event, spare capacity with no element available, is the usual one once the root is settled and only formal proofs are still to be written. Repeated triggers coalesce into one request. When the flag is set and a question is free, one explorer launches ahead of any waiting attempt whose task was not handed over, once the launch interval has passed, and the flag clears. When the flag is set but no question is free, it stays set until a question opens or an occupation ends, and attempts dispatch as usual meanwhile. While no element is available the flag is set again after each launch, so the free questions fill with explorers one by one, a launch interval apart, until none is free or capacity is used. Launching an explorer does not reset the attempt-launch counter. Each attempt launch counts once, whether or not that attempt later registers a section or ends without research.

### Refusals, failed outputs and damaged candidates

A typed provider usage refusal blocks that provider until its known reset or, when the reset is unavailable, for a backoff that begins at `retry_seconds` and doubles with each further refusal, up to `retry_max_seconds`. Model-specific refusals block that model for the same backoff. One such block carries the reason `model_refusal`: a safeguard of the AI system stopped a turn of a Claude worker, the stop that "A session that a safeguard stops" above describes for the paper command. It says nothing about the account or the service, and nothing is to be repaired for it; the runner treats the turn as refused by that model. A new launch uses the first available alternative in its role's list. If all are unavailable, the job remains pending. A producer interrupted after doing work ends and proceeds to peer; it is not silently resumed under another model. A session that failed before leaving any research material can be retried as an operational launch.

Interrupted peers, reviewers and organizers receive fresh replacement sessions with their partial material and the error; the one exception, a peer whose resumed turn failed, or whose host was lost after it had recorded the request of that turn, and whose candidate still passes its transport check, is described under "Session hosts and continuation turns" above. When a completed session's output fails its transport check, the affected job waits for a retry delay of the same form: `retry_seconds`, doubled with each further failure of that job, up to `retry_max_seconds`. The same delay precedes the replacement of a peer, reviewer or organizer interrupted by anything other than a provider/model refusal or a failed launch, such as a crash or `kill-session`, and the relaunch of a producer that was cancelled, or whose host was lost, before it left research material. Neither delay blocks the model for other jobs or changes their configured model preference. Actual provider/model refusals and operational launch failures retain their availability handling, so a configured alternative can be used while the affected service is unavailable. Status exposes the pending job's error and retry time as well as availability blocks. Repair broken paths, login or configuration when necessary. Mathematical uncertainty and incomplete formalization are handled through the elements and their reviews, not inferred from process failure.

A successful session launched after an availability block's deadline clears that provider's or model's old backoff history. A later isolated refusal therefore begins with the initial delay. A session that was already in flight before a newer block cannot clear it merely by finishing successfully; the newer refusal still governs new launches.

If a frozen candidate's files change during review or before publication, retrying the same damaged files cannot complete that review. The runner preserves the damaged candidate and compares the peer's retained output with the hashes fixed at review assignment. Matching output is copied to a new candidate location for a fresh review under the same hashes. If those bytes are unavailable, a replacement peer receives the original research and earlier peer work, develops a new candidate, and sends it through independent review. An assessment of the damaged candidate never authorizes publication of the replacement. A candidate whose files are intact and which no longer applies to the canon or does not build on it takes the path described under Publication of a candidate above.

## Restarts, retention and changing Lean

### Restarts, runner failures and installation updates

After a runner crash or machine reboot, use `start` on the same instance. The runner identifies existing processes by PID and creation identity, follows those still alive, and collects ended work. Publication uses a saved identity, staging directory and Git commit; restarting continues the same publication, with the build it had started, and completes it and its follow-ups without publishing anything twice. A reboot can end that build instead: a compile of it that was running when the machine went down is recorded as failed once a broker runs again, and the work then takes the path described under Publication of a candidate above for a build that failed for a reason that is not in the candidate's files. Do not delete locks or edit runner state to force recovery. Use shells at the same privilege level on Windows, because process-query access is part of liveness detection.

The runner also ends by itself when one of its own operations fails, such as a Git commit or a read or write of its state files. `status` then reports `runner_alive` as false while `finished` is false. The runner state's top-level `last_error` holds that error and its time, apart from the errors of individual jobs, provided the state file could still be written, and the call stack is in the stderr log that `start` named when it launched that runner, `runner/start-<token>.stderr.log` with the `token` that `runner/process.json` records. Repair the cause before using `start`, because a restart that meets the same failure ends again, possibly after `start` has already confirmed readiness. A recorded `last_error` stays in the state after later starts, so compare its time with the `at` of `runner/process.json`, which records when the current runner started, before attributing a present problem to it. A `questions` request the runner refused is also recorded there, naming the request, while the runner keeps running.

Running out of memory is the exception: the runner does not end. It holds a small memory reserve for this case. When one of its operations fails for lack of memory, it releases the reserve, writes `Runner memory reserve released; dispatch will wait for recovery.` to the same stderr log, and then makes no pass at all, collecting, publishing and dispatching nothing, while the machine's free memory (`MemAvailable` on Linux, the commit headroom on Windows) stays below 512 MiB. Once free memory reaches 512 MiB, it takes the reserve back, reloads its saved state and the published research, and continues. Meanwhile `status` reports the runner alive and records no new `last_error`, although nothing advances; freeing memory on the machine lets it continue without a restart.

Worker guides and launch options are fixed for sessions already started. Updated guides are read for later launches. A runner already running keeps its imported launch code until it is restarted, and a session host already running keeps the code it loaded at launch; updating the installation does not rewrite saved session contexts or commands. Continuation messages are the exception: before each resumption, the session host reads two files from its configured installation, a frame and the role's own text `resume/<role>.md`, which it puts into the frame. The frame is `resume/common.md` for an attempt, an explorer, a formalizer and a peer, and `resume/output.md` for a review and an organizer. Editing those files changes the next resumption without a runner or host restart. A continuation file the host cannot use, a `resume/<role>.md` or a frame that is missing or empty, or a frame without exactly one of each of its placeholders, ends the session host at that session's next resumption. The error is in the session's `host.log` as one line of JSON, and the runner records the end reconsideration as `interrupted`: a producing session goes to its peer without that reconsideration, a peer's output goes to the transport check, as "Session hosts and continuation turns" above describes for a host lost after it has recorded the request of the resumed turn, and a review or an organizer is replaced, each later session ending the same way until the file is repaired. The exact source files are saved under that turn's `guidance/` directory along with its rendered `prompt.txt`; turns already underway retain their delivered text. The code behind a session's commands is a second exception. The command arrays in `input.json` name the installed `runtime/coordination.py`, `canon_tool.py`, `check.py` and `lean_broker.py`, and each coordination, canon, transport-check or broker-client command starts that installed file afresh, together with the modules it imports, such as `knowledge.py` and `canon.py`. An edit to that code therefore reaches running sessions at their next command, while the runner, the session hosts and the broker keep the code they loaded, so until those are restarted the two sides read and write the shared coordination and state files with different code.

`start` does not replace a runner that is still alive: the new process cannot take the instance's lock, so it exits and `start` reports that the runner exited before readiness. To restart a live runner, end the one process that `runner/process.json` identifies as this instance's runner, then use `start`; this needs none of the waiting that the row of `stop` under Commands asks for when the runner is to stay ended. Session hosts and the Lean broker are separate processes and keep running; the new runner follows them and completes unfinished publication as it does after a crash. One case differs. When the update changed how the structural index is extracted, the new runner stages an unfinished publication again from its candidate, because the index staged before the update was extracted the earlier way; the modules of that build come from the broker's cache. To have the broker run updated code, run `restart-broker` under the conditions its row under Commands gives for a change of the environment: the broker that the command starts in the place of the old one loads the installed files as they then stand.

### Retention and archives

A session's folder is `sessions/<session ID>/` under the instance, with the ID under which `status` lists the session. Each launch retains there its guides, references, user inputs, settings and the views of the research it was given. The available conversation and artifacts are retained for each session, whatever its role: once the runner has collected a session that ended, `conversation.md` in that folder holds its messages and tool contents in readable form, and `retention.json` names the transcript that was found and any limitation of the capture. The report of an agent that a session delegated to is in the CLI stream of the turn that received it, which is `cli.stdout.jsonl` in the session folder for the first turn and in that turn's folder under `turns/` for a turn that follows a resumption, and once the session has ended the transcript kept in the session folder holds each delegated agent's whole conversation under `transcript-<id>/subagents/`. The work of one producing session finishes processing after its peer has prepared a candidate and review has either led to publication or decided there is nothing to publish. The runner launches a separate archiver process to compress two things of each associated session, each into an archive in that session directory: work/ into work.tar.xz, and the raw form of the conversation into raw.tar.xz. The raw form is the `cli.stdout.jsonl` of each turn and the copied transcript file `transcript-<id>.jsonl`, and raw.tar.xz holds each under the path it had in the session folder, which is the path `retention.json` gives. The archiver verifies file names and hashes before removing work/ or a raw file. When work/ cannot be read or verified, or contains a symbolic link or junction, which could lead outside the session, the archiver leaves work/ in place, along with any archive already there, and records the session and the error in `runner/archive.log`; later archive passes try that session again. Raw files that cannot be read or verified are left and recorded in the same way, and a failure of one of the two does not keep the other from being packed. A standalone review or organizer's work directory and raw files become eligible when its own job completes. Each pass is a new process that loads the installed files as they then stand, and it takes every finished session that still holds work/ or raw files, whenever that session finished. Output files, context, `conversation.md`, `retention.json` and the folder `transcript-<id>/` remain in place; restore archived work or raw files with an xz-capable tar reader when needed.

Nothing removes the following from an instance, so an instance takes more room for as long as its research runs. A session's folder stays after the session has ended, with `work.tar.xz` and `raw.tar.xz` in the place of what they hold. Under `runner/lean/` the broker keeps the folder of every job in `jobs/`, the `result.json` of every build in `builds/`, and every entry of the module cache in `cache/`, which holds the output of each module compile that ended with exit code 0 and is not emptied when a publication replaces a module's source. The instance's repository keeps every publication. In a research of several hundred sessions this comes to gigabytes, so give the instance a volume with that much room. When the volume is full, a write of the runner fails and the runner ends, as "Restarts, runner failures and installation updates" above describes for a failure of one of its own operations.

Two kinds of files can be removed by hand, because no program of do-math reads them again; each has its condition. The first kind is the record of how the sessions worked, which is the user's, so whether and when any of it goes is for the user to say. Nothing else in the instance is of that kind: the canon, `knowledge/`, `control/` and the repository hold the research, the files directly under `runner/` and `runner/lean/` include the states that the runner and the broker continue from, and the folder of a session that is not yet packed holds work that a peer, a review, a publication or a later session of the same task still takes up.

The first kind is what a packed session left. Once the archiver has packed a session, which shows as `raw.tar.xz` in its folder, the work of that session has finished processing, and no program reads a file of the folder again; an archive pass returns to it only while a `work/` or a raw file that it could not pack is still there. The runner reads a session's folder to launch the session, to collect it, to carry its work through peer, review and publication, and to continue or replace it, and all of that is over by then. The dependency map, the paper and the finalize commands do not read `sessions/`. What stays in the folder is the record that the first paragraph of this section describes, and its readers are you, the user, and a comprehensive review, which the [review guide](../roles/review.md) sends to the originals of an element it examines. Removing files there takes that part of the record from those readers and changes nothing in the canon or in the run. The folder itself stays in place, because a session can address a message to a session that has ended, and that command writes into the folder.

The second kind lies under `runner/lean/`, and its condition is the one that the row of `restart-broker` under Commands gives: dispatch stopped, and the running CLI turns, publications and compiles finished, so that no build is under way and none begins. The entries of `cache/` can then be removed. A build looks a module up there by its key and compiles the module when it finds no complete entry, so what is lost is the compiling: the next build of the library compiles every module of the canon, as after a change of `cache_epoch`, and the finalize command, which begins from a copy of this folder, compiles the library itself. Outside the condition a build can have counted an entry as present without having read it yet; the module that was to read it then ends `failed`, and where the build is that of a publication, the candidate goes to a replacement peer. Under the same condition a folder under `jobs/` or `builds/` can be removed, with Lean's output and the measurements of its compile, when the `session` that its `result.json` names is one that `status` lists as `ended`, `integrated` or `failed`, or is `runner`, `operator` or `broker`, the names under which the runner's builds, the build of `init` and the broker's calibration compiles run. After a compile has ended, its folder is read only for the one that submitted it: for a session by its own `wait` and `result`, by the canon commands `prepare` and `verify` when the session runs them again on unchanged files, and by the check of a review's output, which reads the build that the review made; for the runner by the publication under way. A session that waits behind the stop is `running`, and its next turn can ask for those results again, so its folders stay.

When the runner collects a session that ended, it also writes `usage.json` into the session's folder: what the session's CLI reported of its own use. A call of the CLI ends with such a report, and the file holds, under `turns`, the last report of each turn as the stream gave it. A report of Claude carries `total_cost_usd` and, under `modelUsage`, the token counts for each model, and both are for the whole conversation up to that point, with the turns before it and with the agents the session delegated to. The session's figures, under `totals`, are therefore those of the last turn that has a report, and not a sum over the turns: `cost_usd`, and under `tokens` the input, output, cache-read and cache-creation counts added up over the models. The cost is the CLI's own estimate, which can differ from the bill, and do-math computes none: where a report carries no cost, as a report of Codex carries none, `cost_usd` is `null`. A report of Codex carries token counts alone and is taken in the same way; whether the report of a resumed turn includes the turns before it has not been observed on a real session, so for a Codex session with several turns compare the reports under `turns`. A turn that its CLI did not end itself, as when its host was ended, leaves no report: `totals.turns_without_report` counts such turns, and what they used is not in the totals. The runner keeps a session's `totals` in its state as that session's `usage`, and `usage` in `status` adds them up.

The canon contains what later researchers need, and a session's own account stays outside it. The originals remain recoverable for the operator and for a designated reviewer examining the elements that came from them, within the scope described in the [review guide](../roles/review.md). `provenance.json` in a published change's folder names the producing, peer and review sessions, and an entry of the approaches tried names the sessions that contributed to it.

### Changing Lean

Changing Lean or its libraries requires a new `lean.cache_epoch`. Stop new dispatch and let running CLI turns, publications and compile jobs finish; sessions waiting behind the stop for their next turn need not end. Update the Lean configuration in the instance's own `settings.json`, including a new `cache_epoch`, then run `restart-broker` and resume. This prevents calibration entries and a module cache identified by an old environment from being treated as evidence for a changed installation.

The canon is itself a library compiled in that environment. A peer's preparation of its candidate, review's verification and every publication that changes a Lean file build all of it. After the change the cache holds nothing for the new environment, so the next such build compiles every module of the canon again. If a module of the canon no longer compiles under the changed Lean or imported library, no candidate can be prepared: each peer's output fails its transport check and the peer is replaced, again and again, and a candidate that was already under review fails its build at publication. Before you resume, you can therefore build the canon in the new environment with the broker's own `build` command, in the form [Lean](lean.md) gives, with `<instance>/canon/lean` as the module root, its files as targets, a memory estimate, and a name of your own, such as `operator`, as the session. The build writes its output to the broker's folders and leaves the canon as it is. A canon that no longer compiles is a reason to return to the earlier environment and report to the user.

That build shows only that the canon compiles. The index is not extracted again when Lean changes: it holds each statement as the earlier environment elaborated it, and a changed Lean or library can read the unchanged text of a statement as another term, as an enlarged import can. This shows after `resume`, when a candidate replaces a proof: the module it changes and every module that imports it are extracted in the new environment, and a statement among them that now elaborates otherwise fails the check that no statement changed in place, in a peer's preparation, in review's verification and at publication alike, with a reason that says the change enlarges what the statement's module imports. Where the candidate left those imports as they were, the cause is the changed environment; report it to the user.
