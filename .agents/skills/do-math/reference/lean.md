# Lean compilation and formal evidence

The knowledge of a do-math instance is a Lean library, the canon, and a session reads it and builds against it from the start of its work. Compiling Lean is therefore ordinary work in every role, and this document explains what a session needs for it.

The **imported library** is what the Lean environment of the instance provides: the modules of the toolchain itself, such as `Init`, `Std` and `Lean`, and any library the operator configured, such as Mathlib. An import of one of its modules is called an **external import**. All modules of the canon lie under one top-level name, which `instance.json` gives as `library`; the examples below use `Tri` for it, as the examples of [The canon](canon.md) do. A **local module** is a module whose source the broker finds under the folder a build is given: a canon module in your copy of the canon, or a module you wrote there.

The imported library can be read as well as imported, and a session reads its sources to find the exact name or statement of a lemma. When the operator configured a library, `settings.lean.cwd` in your `input.json` is the folder of the Lake project that provides it, and the sources of each package of that project lie under the project's `.lake/packages/` folder: those of Mathlib under `.lake/packages/mathlib/Mathlib/`. The toolchain's own sources lie under `src/lean/` in the toolchain's folder; when the first entry of `settings.lean.command` is a path, that folder is the one above the `bin/` folder the entry names. Read the library in these folders, and give their paths to any agent you delegate to that will read the library, because it has not seen your `input.json`. Do not search the machine for the library. A search that starts at the root of the file system reads every file on it, runs for many minutes, and goes on after the shell tool that started it has stopped waiting, taking processor time from every session's compiles until your session ends.

## What a Lean compile is, and what it costs

To check a file a session has written, Lean reads it from top to bottom, loads every module the file imports, elaborates each definition and theorem in turn, and reports errors, warnings and the output of commands such as `#print axioms`. This document calls that whole run of Lean over one file a compile, and the process that performs it a Lean process.

A compile takes time, and with Mathlib it takes a lot of it. Most of that time is spent at the start, loading the imported modules: a file that imports all of Mathlib reads several gigabytes of compiled library from disk before it looks at the first theorem, and that alone has taken seven minutes when those files were not yet in the operating system's cache. Time, though, only delays a result: a slow compile does not harm anything else that is running.

Memory is different. A compile that takes more memory than the machine has left pushes the machine into swapping, or gets itself or some other process killed, and every session on the machine suffers. A Lean process uses memory in two ways.

The first is the imported library itself. Lean maps the compiled modules into memory directly from the files on disk. The second is the memory that belongs to one Lean process alone. On import, Lean builds its own indexes over everything it loaded: the table of names, the sets of `simp` lemmas, the instances, the notations. For all of Mathlib this comes to about a gigabyte, and every running compile builds its own copy. Then, as the file's proofs are elaborated, Lean allocates terms, goals, tactic states and caches, and this part grows with what the proofs do: a `rfl` costs almost nothing, while an unbounded `simp` over all of Mathlib or a large `decide` can take gigabytes. Lean keeps the memory it has freed for reuse and does not return it to the system, so within one compile this memory mostly grows, and it reaches its peak late.

How much of this counts against the machine depends on the operating system. On Linux the mapped library is file cache: the system keeps one copy of each file however many Lean processes use it. There the library slows a loaded machine down but cannot run it out of memory, and only the second kind of memory counts. Windows keeps an account, the commit charge, of all the memory it has promised to processes, and the account has a limit, the commit limit. Windows appears to charge a Lean process for the whole size of the library it maps, although most of those pages are shared with other compiles or never touched.

For each compile the broker described in the next section measures the memory charged to the compile's own processes: their commit charge on Windows, and their anonymous memory on Linux. This document calls that quantity the compile's **private memory**. Every estimate a session gives and every measurement the broker reports is in it. On Windows it includes the charge for the mapped library, so the import alone is large there: a compile that imports the analysis part of Mathlib was measured between 2 and 3.9 GB before it elaborated anything.

Private memory is paid once per running compile, and it is the sum over all running compiles that must stay within what the machine has. No session can keep that sum in bounds by itself. With nothing between them, every running session could start a compile whenever it liked, and several Mathlib compiles at once are enough to make the machine unstable.

On Windows the result is that compiles mostly run one at a time, because with many sessions running little more of the commit limit is left free than one compile holds, and what a compile costs a session is the wait for its turn far more than its own running time. In one research instance the 481 finished compiles ran for a median of 24 seconds and waited in the queue for a median of 179 seconds.

Two things follow for a session. Lean cannot be kept loaded to answer quick questions, since a loaded process holds its gigabytes for as long as it lives; reading the canon therefore goes through the canon command, which starts no Lean process, as [The canon](canon.md) explains. And compiles are affordable when they are made at natural points of the work: what is short is the number of compiles that can run at once, not the total time available.

## The Lean broker

Each instance runs a single process called the Lean broker, and every compile in the instance goes through it. A session does not run Lean itself, not even to ask for its version. It asks the broker to compile a file, and the broker takes that compile as a job, decides when to start it, runs it, and hands the result back.

The broker schedules compiles against a shared memory budget: it uses the estimate of private memory that a session gives with each submission, together with what it has measured itself, to decide whether the compile can start now or must wait for others to finish. It measures the peak private memory and the duration of every compile and returns them to the session, so the cost of every proof becomes visible.

It also cancels the compiles of a session that has finished, failed or been killed: no one is left to read their results, and they only take memory. Apart from a cancellation that a session asks for itself, this is the only situation in which the broker stops a compile: it never stops one for using more memory than was estimated, and it sets no limit on how long a compile may run.

The broker compiles one file per job. It does not run `lake build`; the `build` command described below does for a session what `lake build` would.

**Why a compile is waiting.** A compile waits in the queue until the broker's memory budget and its thread budget have room for it and the machine itself has the memory free. A compile whose external imports the broker has neither measured nor been able to estimate waits first for the broker's own compile of those imports, as Estimating what a compile will need explains. The `status` command shows the queue, with each job's estimate, what the broker reserves for it in memory, called its reservation, and the job it is waiting for.

**When no broker is alive.** The runner starts the broker, and starts another within seconds whenever it finds none alive. A command that reports that no broker is alive, before submitting or while it waits for a result, has first waited up to twenty seconds for the runner's. Nothing is lost by this. Submit again, or wait again on the same job, a little later; the session is left without a broker only while the runner itself is not running.

How the broker works inside, and its settings, are written for the operator in [The Lean broker](lean-broker.md). A session can compile without reading it.

## Compiling a file

`commands.lean` in your `input.json` is the broker's command with one placeholder: the interpreter, the broker script, `<command>`, and the path of the instance. In the examples below, `python` stands for that interpreter, `<broker>` for that script and `<instance>` for that path. A single file whose imports are all external imports is compiled with

```text
python <broker> run <instance> <file.lean> --session <session ID> --expect-mb <MiB>
```

where `<file.lean>` is the absolute path of the file, `<session ID>` is the session's own ID, the `session` value in your `input.json`, and `<MiB>` is the session's estimate of the compile's peak private memory, in mebibytes. Estimating what a compile will need explains how to arrive at that number. A file that imports a canon module or a module of your own cannot be compiled this way; it needs `build`, which Building against the canon and your own modules explains.

The broker compiles the file with the `lean.command` of the instance's settings, adding the thread count it has been configured with and the path of the file. The working directory is `lean.cwd` from the settings, or the session's folder when that is `null`. When the compile finishes, the command prints Lean's output exactly as Lean produced it, the standard output on standard output and the standard error on standard error, so that error messages, `#print axioms` lines and `sorry` warnings read as they would from Lean. It then exits with Lean's exit code. The last line on standard error is a summary from the broker:

```text
lean-broker: {"job": "j…", "status": "finished", "exit_code": 0, "reason": null, "expect_mb": 1800,
  "measured": {"peak_mb": 1466.2, "baseline_mb": 1103.5, "excess_mb": 362.7, "seconds": 41.3, "estimate_ratio": 0.81, …},
  "dir": "<instance>/runner/lean/jobs/j…"}
```

The numbers in this line are made up to show the fields. `peak_mb` is the highest private memory the broker measured during the compile, `baseline_mb` is what the compile's external imports alone cost, as Estimating what a compile will need explains, `excess_mb` is the difference, `seconds` is how long the compile ran, and `estimate_ratio` is the measured peak divided by the estimate. `dir` is the folder where the broker keeps the job's files: Lean's output in `stdout.log` and `stderr.log`, the job's record in `result.json`, and a few process receipts. The output can be read again from there at any time.

For a single-file job, `finished` means that the Lean process ended and its exit code was recorded; inspect its `exit_code` to distinguish compiler success from rejection. A Lean process that the operating system ended also finishes this way. On POSIX the summary's `exit_code` is then the negative of the signal number, as when the system kills a compile that ran out of memory; on Windows a crash appears as a large code such as 3221225477 (0xC0000005). Such a code reports an execution failure, not Lean rejecting the source. Status `failed`, with command exit code 3 and a `reason`, means that the job ended without a recorded compiler exit code, and the `reason` says why: the request could not be accepted, the file disappeared or changed after submission, the Lean environment changed while the job was queued, Lean could not start, or its supervising process was lost. The two changes call for submitting the current source again and not for repairing the environment. Status `cancelled` has command exit code 4. An execution failure or a cancellation leaves the check incomplete and does not establish a defect in the mathematics.

Invocation errors belong to the broker's client and not to Lean's assessment of a source file. For example, malformed options or an input rejected before submission can end the command before a job is accepted. Correct that invocation from its diagnostic. An error while waiting for an already submitted job is different: failure to contact the broker does not establish that the job vanished or that Lean rejected the source. Keep the job ID, inspect status and the retained logs, and recover that job's outcome before deciding whether another submission is needed. The command's exit code alone cannot distinguish these phases.

### When the shell tool will not wait

The `run` command waits for the compile, and a compile can take longer than a CLI's shell tool is willing to wait: Claude's tool moves a command to the background after 120 seconds, or after 600 seconds if a `timeout` is given, and abandons it ten minutes after that; Codex's tool returns after about ten seconds and expects the session to poll. A compile that imports Mathlib, or that has to wait its turn behind other compiles, can exceed both.

For such compiles, submit and wait in two steps:

```text
python <broker> submit <instance> <file.lean> --session <session ID> --expect-mb <MiB>
python <broker> wait <instance> <job> --timeout 50
```

`submit` returns at once and prints the job ID. `wait` returns either the finished result, printed exactly as `run` would print it, or, if the timeout passes first, exit code 124 and a note that the job is still running. Nothing is lost between calls; `wait` can be run again and again until the result is there. If a `run` was started and its shell tool gave up, the same recovery works, because the job ID is the first thing `run` prints on standard error.

Submitting the same unchanged file again from the same session, while its earlier job is still queued or running in the same Lean environment and no cancellation of that job has been requested, does not start a second compile. The broker answers the new submission with the ID of the job already in progress, and waiting on either ID gives the same result. A file edited after its submission is a different source. Its new submission becomes a job of its own, and an earlier job that has not yet started fails with the reason that its source changed after submission.

### The other commands

| Command | What it does |
|---|---|
| `build <root> <file.lean>...` | Compiles the files together with every local module they import; the next section explains it. |
| `result <job>` | Prints the job's or build's record as it currently stands. |
| `status` | Prints whether the broker is alive, the configuration it is using, the Lean version, the jobs that are queued, running and recently finished, each with its estimate, its reservation and its measurements, and the builds in progress or ended within the last ten minutes. |
| `cancel <job>` | Cancels one of your own jobs, or every compile of one of your own builds, that you no longer need. |
| `version` | Prints the Lean version string, which the broker obtained by running the configured version command once. This is the string to give when a report names the Lean environment. |

`cancel` records a cancellation request for a job or build, including while the broker is accepting it. The response acknowledges the request; use `wait` on the same ID to obtain the final outcome. A confirmed cancellation has status `cancelled` and returns exit code 4, including when no compile started. Work that had already completed retains its completed outcome. Cancelling a duplicate submission requests cancellation of the original job or build to which it refers.

All of these take the instance path as their first argument, like `run`.

## Building against the canon and your own modules

Lean finds an imported module not in its source but in its compiled form, the `.olean` file, on a search path that holds the imported library and nothing of the instance's. A file that imports a canon module, or a module you wrote, therefore does not compile on its own: the modules it imports have to be compiled first, as modules, into a place on the search path. The `build` command does all of that, and a session builds against the canon in three steps.

**Take a copy of the canon.** The canon command of your `input.json`, `commands.canon`, with which the canon is read, has the same form as the broker's: an interpreter, the canon tool, `<command>`, and the path of your session folder. Its `checkout` command copies the Lean sources of the canon into a folder of your session:

```text
python <canon tool> checkout <session folder> <folder>
```

`<folder>` must lie inside your session folder and be empty or not yet exist; a relative path is taken under the session folder. The command prints, as JSON, the path of the copy and the revision of the canon it was taken at; note the revision if you will need it, since nothing in the copy records it. The copy holds the canon's module root as it was at that moment, and later publications do not change it. That is safe to build on, because a statement of the canon never changes in place: what your files use will still be in the canon when your work is published, although proofs may have been replaced and modules added in between. A newer state of the canon is obtained by checking out again into another folder.

**Write your modules in the copy.** The copy is a module root: the folder under which `<folder>/Tri/Sums/Bound.lean` is the module `Tri.Sums.Bound`, exactly as Lean names modules, and a file anywhere under it can import any module under it by that name. Every part of a file's path under the root has to be a plain identifier, made of letters, digits and underscores and not beginning with a digit, since the path is the module's name. A module that is meant to enter the canon is written under the canon's top-level name, in the example under `<folder>/Tri/`, at a path the canon does not have yet; [The canon](canon.md) explains how such a file is written. A scratch file can lie anywhere under the root.

**Build your files.**

```text
python <broker> build <instance> <folder> <file.lean>... --session <session ID> --expect-mb <MiB>
```

`<folder>` is the copy, given as an absolute path. The files after it are the targets, the ones whose output you want, given as paths under the root. `--expect-mb` is your estimate for one module compile, the largest you expect among the modules that will actually be compiled. The command waits, prints each target's Lean output as Lean produced it, and ends with one summary line listing every module's status, exit code and measured cost. For a build that may outlast your shell tool, `build ... --no-wait` prints the build ID at once and `wait <build>` collects the result later, as for a job.

### What a build does

The broker reads the import headers under the root, starting from the targets. An import whose file exists under the root is a local module and belongs to the build; any other import, one whose file is missing under the root included, is taken for an external import, and a mistyped name of a canon module is refused, with a reason that names both readings, when the build holds a local module under the same top-level name. The broker also refuses an import cycle, and a local module whose name would shadow the imported library: one under `Init`, `Lean`, `Std` or `Lake`, or under the first component of any external import in the build, such as `Mathlib`.

Every local module that is not taken from the cache becomes one compile. The broker reads a module's source when its turn comes and compares it with what the build registered, so a file edited while its build is in progress fails that module with the reason that its source changed. Edit, and then build again.

A module whose compiler exits with errors is reported as `finished` with a nonzero `exit_code`. Modules that depend on it are not compiled: they have no job and are marked `failed` with the dependency as the reason, and the build is `failed` as well. If every module completed or was cached, the build is `finished`, including when a completed module has a nonzero compiler exit code. A successful build therefore requires both the status `finished` and zero compiler exit codes; neither alone establishes success.

The summary line of a build has this form; the names and numbers are made up:

```text
lean-broker: {"build": "b…", "status": "finished", "exit_code": 0, "reason": null, "targets": ["Tri.Sums.Bound"],
  "modules": [{"module": "Tri.Defs", "status": "cached", "exit_code": 0, "cached": true, "reason": null, "measured": {"peak_mb": null, "seconds": null}},
              {"module": "Tri.Sums.Bound", "status": "finished", "exit_code": 0, "cached": false, "reason": null, "measured": {"peak_mb": 2410.7, "seconds": 38.2}}],
  "dir": "<instance>/runner/lean/builds/b…"}
```

The summary's `exit_code` reports the largest recorded nonzero compiler return code, or 0 when every recorded code is zero or no code was recorded. Successful modules cannot mask a negative return code, which is what a signal termination gives on POSIX. Each module row keeps its own code. A `finished` build returns this aggregate as the command's exit code, so the command can still report a compiler failure. A `failed` build returns 3 and a `cancelled` build returns 4; their command exit codes can therefore differ from the compiler aggregate in the summary.

Read the build's `status` and `reason` together with the module rows to find the original failure. The record that `result <build>` prints is not laid out as the summary line is: its `modules` is an object with one entry under each module's name, where the summary line has a list of rows. Each entry holds the module's `status` and `exit_code` and, under `job`, the ID of the module's compile, which is `null` when the module was taken from the cache or was never compiled. Each job's `stdout.log` and `stderr.log` are under `runner/lean/jobs/<job>/`. A dependency's compiler diagnostics can be absent from the relayed target output because the target never ran. Follow those diagnostics to tell a source rejection from an unavailable compiler or a lost supervising process before deciding what to fix.

### What is taken from the cache, and what is compiled again

A module that the broker compiled successfully is kept in the instance's cache, and a later build, by any session, that needs the same module takes its compiled files from there. Such a module is reported as `cached`; it has no job, and if it is a target its Lean output is replayed from the cache. Whether two modules are the same is decided by content and not by where the files lie. The runner builds the canon through the same broker when the instance is created and at each publication, so the first build in a fresh copy normally compiles your own modules and takes the canon's from the cache.

A module is compiled again in two cases: its own source changed, in any byte, a comment included; or something changed in what its compile reads of the local modules it reaches, which are the modules it imports and the ones those import in turn. A file written in Lean's module system, one whose first word is `module`, reads of a module it imports the statements, the exposed definitions and the compiled code, and not the proofs. So when a proof is replaced in a `module` file, that module is compiled again and the `module` files that import it are usually taken from the cache as before. Not always: whether what they read came out the same is settled by the compiler and cannot be read off the edit.

A plain file, one that does not begin with `module`, reads the proofs of what it imports as well, and so does a `module` file with an `import all`. Such a file is compiled again whenever any module it reaches changed at all, even in one proof. A plain scratch file that imports canon modules is in this position.

## Estimating what a compile will need

The estimate of peak private memory that every submission carries is read as a probable peak: the amount that the compile will, with about ninety percent confidence, stay under. It is not meant to be the worst case. When it decides whether a compile can start, the broker reserves memory on the assumption that the compile may reach this number but is not likely to exceed it, and it pools the uncertainty of all running compiles instead of adding up their worst cases. An estimate padded up to the worst case therefore does not make the compile safer; it makes the broker hold memory idle and delays the compiles that come after, including the session's own. An estimate that is too low is not punished either, but it is visible: the broker compares every estimate with the measured peak and reports the ratio in the summary line, and what stands between an under-estimate and an over-committed machine is the margin the broker keeps for the pooled uncertainty and its check of the machine's free memory. An honest, well-reasoned number is the one that serves the session best.

The estimate is built from two parts, and the broker provides the first.

The first part is the baseline: the private memory a compile uses to load its external imports before it elaborates anything. Local modules are not part of it; what loading them costs is measured as excess above the baseline. The broker measures the baseline of a set of external imports with a calibration compile, a compile of a file containing only those `import` lines, or estimates it from the size on disk of what the imports load; an estimated entry says `estimated: true`, and the estimates have been within 2% of what a measurement gave. It keeps the baselines in the calibration table, `<instance>/runner/lean/calibration.json`, with one entry for each set of external imports in each Lean environment. Each entry names its external imports, the Lean version, the environment identity and the launch mode (`environment_key` and `direct`, the values `status` reports as `environment_key` and `launcher.direct`), so that the entry of the current environment can be told from one measured before a change of Lean or Mathlib. The entry records the baseline, the import time, and, as real compiles with those imports go through, how much memory each one used above the baseline and how long it ran. An entry whose calibration compile failed records the failure instead of a baseline. A session can read the entry for its external imports in the current environment and take the baseline from there. If there is no entry yet, the broker creates one before the session's compile runs; when the set has to be measured, the compile waits for that measurement.

The second part is the allowance above the baseline: the cost of elaborating the file's proofs and, for a module of a build, of loading the local modules it imports. This is a judgment about the file that the compiling session makes from the source and the available measurements. The table below gives orders of magnitude for common proof patterns. When the calibration table already has measurements for this set of imports, those are better evidence than the table, because they come from this instance's own files.

| What the proofs do | Memory above the baseline |
|---|---|
| `rfl`, `exact`, `rw`, `intro` and `apply` chains, `simp only` with a few named lemmas, `omega` or `linarith only` with the context cleared | small: tens of MiB |
| `simp` with named lemma sets, `norm_num` on ordinary numerals, `ring`, `field_simp`, ordinary `aesop` calls, several such declarations in one file | moderate: a few hundred MiB |
| unrestricted `simp` or `simp at *` over a large import, `nlinarith` or `polyrith`, `omega` with many hypotheses, instance searches through large class hierarchies | large: around a gigabyte |
| `decide` on anything beyond tiny finite problems, `norm_num` on very large numerals, kernel reduction of big definitions, `#eval` of heavy computations | very large and hard to bound; these are also the cases worth rewriting, as the next section explains |

Lean elaborates declarations in parallel when it has more than one thread, and the broker gives each compile the number of threads set in `lean.threads`, two by default, so a file with several heavy declarations can have that many elaborating at once. Allow for that.

For a first submission with no measured baseline, the table above supplies only the cost of the proofs, not the total. Use a measurement for comparable external imports if one is available. Otherwise take the instance's `calibration_expect_mb` setting, which your `input.json` carries under `settings.lean` and `status` shows in the configuration, as a provisional allowance for the import, add the estimated cost of the proofs and of the local modules, and say in your report that the import allowance was unmeasured. It is a starting estimate, not an upper bound; the calibration and the compile itself supply the measurements with which to revise it.

Record in your report the estimate you gave and the peak and duration the broker measured, with a note on any notable difference. This gives a reviewer a measured number to start from and lets later sessions see which results are expensive to verify again. A reviewer estimating for a candidate written by someone else has the same means: the author's reported measurement, the calibration table's entry for the imports, the files themselves, and the cost of the compile that `commands.verify` adds to its build, which [The candidate change](change-format.md) gives under "Preparing the candidate".

## Writing Lean that compiles cheaply

The broker bounds the harm of an expensive compile, but it cannot make a compile cheap. That is in the hands of whoever writes the file. The practices below are what experienced Mathlib users do as a matter of course; each is given with the reason, so that the same reasoning can be applied to cases not listed here. In a do-math session, where every compile shares one budget with every other session's compiles, they are the expected way of working.

**Import only what is used, and work out what that is before writing the imports.** A compile pays for its imports before it elaborates anything, and for an ordinary file the imports are most of the cost. In one instance, files that imported the real numbers, finite sums and the tactics `ring`, `linarith`, `positivity` and `field_simp`, each from its own module, had a baseline of about 2,200 MiB, and their proofs added less than 70 MiB to it. So think about the imports of a file as concretely as about its statements. Name what the file uses: the objects it speaks of, such as the real numbers, finite sums or binomial coefficients; the lemmas it calls by name; and the tactics its proofs run. Each of these is defined in a module, and a Mathlib tactic usually has a module of its own, such as `Mathlib.Tactic.Ring` or `Mathlib.Tactic.Linarith`. Import those modules, and leave out what the file does not use.

Two imports bring in far more than any one file uses. `import Mathlib` loads the whole of Mathlib and builds Lean's full private index on every compile. `import Mathlib.Tactic` loads every tactic of Mathlib together with everything those tactics import: in the same instance a file with that line and three small imports had a baseline of about 3,900 MiB, against the 2,200 MiB above. Broad imports are fine while looking for lemma names, but not in a file that is compiled over and over or that other modules import.

An import is inherited. A compile reaches the local modules its file imports and the local modules those import in turn, and it loads the external imports of every one of them. An import written in one module is therefore paid again by the compile of every module that reaches it. The broker's baseline covers only the external imports written in the compiled file itself, so what a file inherits appears as excess above its baseline and not in the baseline. In the instance above, one module near the bottom of the library carried `import Mathlib.Tactic` and most of the other modules reached it. Their compiles took about 4,000 MiB each, and the instance's memory budget admitted them one at a time. A needless import therefore costs most in a module that many others import. The modules that hold the canon's definitions are such modules, because every other module of the instance imports them. Importing a canon module also brings in every local module it reaches, and each of those is one more thing whose change compiles your file again.

Once a proof is finished, Mathlib can report what a file needs, within limits that matter here. `#min_imports`, written at the end of a file, looks only at the declarations the file refers to and not at its tactics and notation. Its answer can therefore lack the tactic modules, and a file whose imports are replaced by it can fail to compile. `#min_imports in`, placed before one declaration, and the option `linter.minImports`, which goes down a file and keeps the set of imports needed so far, do take tactics and notation into account. They are defined in `Mathlib/Tactic/MinImports.lean` and `Mathlib/Tactic/Linter/MinImports.lean`, and the opening comment of each file says how the tool is used and what it misses.

**Compile fewer times, and compile less each time.** Every compile waits its turn, and every compile pays for its import again in full, so there is no saving from compiling often. For a development with several interdependent statements, first compile the statements together, their proofs left as `sorry`, before investing in the proofs: an error in a statement is cheap to find before the argument is built on it. In the canon a statement whose Lean proof is not written stands in exactly this form. A small direct proof may already fit in that one compile. Then fill in proofs a few at a time. When one lemma is hard, work on it in a file of its own that imports only what the lemma depends on, and move the finished proof back.

**Keep what is still changing apart from what has stopped changing.** A module is one compile and one cache entry, and every edit of its source, in any byte, elaborates the whole of it again. Declarations that are finished are therefore cheaper in a module of their own than beside the declarations still being worked on, where each edit pays for their proofs once more. A file written as a `module` is also cheaper than the same content as a plain file: on a file importing the Lean metaprogramming library, with Lean 4.32.0, the commit charge went from 2,078 to 1,680 MB and the elapsed time from 8.7 to 5.7 seconds. This was not measured with Mathlib imports.

**Turn successful searches into reusable proofs.** `exact?`, `apply?`, `rw?`, `simp?`, `aesop?`, `hint` and `polyrith` search the imported library. Their cost grows with the size of the import, and they are the most common reason a small file compiles slowly. Once a search finds the needed proof, use its explicit term or the `simp only [...]` call reported by `simp?` where practical. This saves repeating the search at every compile and makes the dependency that succeeded visible. Judge the benefit for the actual file; the purpose is verification that can be repeated economically.

**Keep automation bounded.** Write `simp only [a, b]` in place of a bare `simp`, and `linarith only [h1, h2]` in place of `linarith`. Before calling `omega`, `linarith` or `nlinarith`, `clear` the hypotheses they do not need, because they consume the whole context and `nlinarith` grows combinatorially with it. Use `norm_num` for arithmetic on numerals and not `decide`: `decide` is evaluated by the kernel, which has no heartbeat limit, and a large `decide` is the classic way for a compile to take gigabytes without producing any error before the operating system steps in. Under the default axiom policy, `native_decide` introduces an axiom that is not allowed; see Formal acceptance below. When instance search is slow, give the instance explicitly with `haveI` or `(inst := ...)`. While iterating, put `set_option maxHeartbeats 50000 in` before a declaration so that a runaway tactic fails within seconds; raise the limit locally, with `in`, only for a proof that needs it.

**Measure before optimizing.** Mathlib's `count_heartbeats in theorem ...` prints what a declaration costs in heartbeats. `set_option profiler true` prints the time of each step. `set_option trace.Meta.synthInstance true` shows an instance search that is looping, and `set_option trace.Meta.Tactic.simp.rewrite true` shows what `simp` is rewriting. The broker's measured peak and duration are the same kind of evidence for the file as a whole.

**Shape the file for how Lean runs it.** Prefer small lemmas to one large `by` block so that each proof is easier to elaborate, profile and revise. Splitting a proof does not guarantee lower process memory: Lean can retain allocated memory for reuse, and several declarations may elaborate in parallel. Estimate for the actual file and thread count. Give every `have` its type, so that Lean does not have to infer a large term. Mark heavy definitions `@[irreducible]`, or define them with `irreducible_def`, so that tactics do not unfold them by accident. Use `rw` for a single rewrite, and `show` or `change` to fix the goal before handing it to automation.

## Formal acceptance

A compile that succeeds shows that Lean accepts the file as written: its kernel has accepted every proof in it. It does not yet show that a statement has been proved formally. A proof may end in `sorry`, as the informal proofs of the canon do by design, or it may rest on an axiom the instance has not allowed, and Lean accepts the file in both cases.

**When a statement is formal.** A statement of the canon is formal when every axiom it depends on is in the instance's allowed list. Lean itself says which axioms a statement depends on, and its account is the one that `#print axioms` prints: every axiom reached from the declaration through everything it uses, which takes in the canon elements that its proof and its statement name, what those use in turn, and the declarations of the imported library. The structural index holds that list as Lean gave it. An axiom declared in the canon is in the list like any other, whatever its name or visibility: a private axiom, and the axiom that `native_decide` adds for each computation to the module that uses it, are among the axioms of every statement that rests on them. A candidate that declares an axiom, private or not, is nonetheless refused, as [The canon](canon.md) says. The allowed list is `settings.lean.allowed_axioms` in your `input.json`. By default it holds `propext`, `Classical.choice` and `Quot.sound`, and an instance may explicitly allow more. `sorryAx`, the axiom that stands for a `sorry`, is never allowed, and the settings refuse a list that contains it.

Because the dependence is followed through the canon, a hole in a lemma appears among the axioms of everything that rests on that lemma and keeps it from being formal, even when the file of the final theorem contains no `sorry`. Conversely, the word `sorry` in a comment has no significance. The evidence is the list of axioms that a compile reported, not the text of a source.

**Where the axioms are read.** For a published element, `commands.canon view <element>` shows its axioms and says whether it is proved in Lean from the allowed axioms. For a candidate, `commands.prepare` prints the axioms of each theorem the candidate adds or whose proof it replaces, followed through the canon in the same way, and `commands.verify` prints the same for review. A producing session that wants the axioms of its own theorem before a peer prepares the work can put `#print axioms <theorem>` in a plain file that imports the theorem's module and build that file. The file has to be plain because a `module` file does not read the proofs of the modules it imports, so do not rely on `#print axioms` in a `module` file for a theorem of another module; that case was not tested. Inside the theorem's own file the command reports its axioms correctly, `sorryAx` included (tested on Lean 4.32.0), so a line `#print axioms <theorem>` at the end of your working module serves as well while you work. Remove it before you hand the module on.

**A statement in an untouched module, and the root as posed.** A statement in a module that a change did not touch becomes formal with that change when the last statement it rests on receives a complete proof. Once the root is settled by a formal proof, the runner compares the root's statement, and every definition the statement is built on, with the root as the instance's first commit fixed it, and so finds a statement or a definition under it that is no longer the one that was posed. No session makes this comparison.

**What Lean settles, and what remains a judgment.** A proof of the root enters as the proof of the root's declaration, or as another declaration whose record says that it proves the root's statement, which Lean confirms by checking that the two statements are identical; a refutation is a declaration whose statement Lean confirms to be the negation of the root's.

Lean checks that a proof proves the statement as written. It cannot settle whether each new statement of a candidate says what was meant by it, or whether each new definition denotes the object it was meant to denote. That is review's judgment, which review makes by reading the Lean text against the record, and the producer and the peer owe the same care before review.

**Outcomes to keep apart.** A compile that could not run, a source that Lean rejects, a proof that depends on an axiom outside the allowed list, and a complete proof of a statement that does not say what was meant have different consequences, and a report or an assessment names the exact case. A development that is not yet formal is still part of the canon: a statement whose Lean proof ends in `sorry` is an ordinary element, with an informal proof or none, and it is published with that standing.
