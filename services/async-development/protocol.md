# 작업 계약

이 문서는 개발 세션이 배정을 받아 수행하고, 그 결과를 다음 세션으로 넘기는 절차를 정한다. 프로젝트마다 달라지는 목표와 인터페이스는 공용 맥락 문서에 두며, 모든 역할은 시작 메시지로 받은 [판단 원칙](principles.md)을 적용한다.

**task**는 구현·수정·조사·검토의 한 작업 단위이고 Codex 세션 하나가 맡는다. 실행 중인 task 세션을 **worker**라고 부른다. **manager**는 종료한 task의 결과를 판단해 공용 소스와 계획을 갱신한다. **review**는 제품을 수정하지 않고 사용자 요구와 실제 결과를 대조하는 task다. 실행기는 이 세션들을 파견하고 종료 사건을 전달한다.

## 1. 세션이 받는 정보

시작 메시지에는 자신의 역할과 실제 경로가 들어 있다. `source_repo`는 공용 소스인 `REPO`, `records`는 개발 기록인 `RECORDS`, `engine`은 이 도구의 위치인 `ENGINE`이다. task와 review에는 작업 ID인 `task`와 자기 코드 사본인 `workspace`가 추가된다. manager에는 처리할 완료 사건을 담은 `inbox` 경로가 주어진다.

이 경로들은 자료의 위치를 알려 준다. 프로젝트의 목표와 현재 상태는 공용 문서를 읽어 파악한다.

- `context.md`는 사용자의 목표·사용 상황·확정된 요구, 시스템의 구성과 흐름, 현재 구현, 중요한 선택과 이유, 미확인 사항을 설명한다.
- `plan.md`는 남은 결과물과 우선순위, 현재 작업, 실제 선행 관계를 설명한다.
- `seams.md`는 구성 요소가 제공하고 소비할 인터페이스를 설명한다. 실제 정의의 파일·심볼과 입출력·동작·오류 의미를 연결한다.

예를 들어 소비자가 `normalize_name(text)`를 사용해야 한다면, 함수 이름뿐 아니라 어떤 공백을 처리하고 어떤 값을 반환하는지 알아야 한다. 이 의미는 실제 함수·형식 정의와 함께 seams에 연결한다. 별도의 인터페이스가 없는 프로젝트는 그 사실을 적는다.

공용 문서의 최초 내용은 프로젝트를 맡기는 사용자 또는 준비를 맡은 세션이 작성하고, 이후에는 manager가 갱신한다. 각 task는 자신의 시작 시점에 복사된 맥락을 사용하므로 manager가 다른 결과를 반영하더라도 수행 중인 배정의 전제가 갑자기 달라지지 않는다.

## 2. Task가 작업을 수행하는 순서

### 배정을 이해한다

task는 자기 디렉터리의 `inputs/context.md`, `inputs/plan.md`, `inputs/seams.md`를 읽고 프로젝트 전체의 목적과 현재 위치를 파악한다. 이어 `objective.md`와 `task.json`을 읽어 맡은 결과, 완료 판단, 제공·소비할 인터페이스, 수정 범위와 추가 입력을 확인한다.

objective에는 다른 작업자가 같은 의미로 수행할 수 있을 만큼 구체적인 목표가 있어야 한다. 예를 들어 명령행 기능을 맡긴다면 어떤 입력을 받아 어떤 출력과 종료 상태를 만들어야 하는지 설명한다. manager는 관련 구현·수정·필요한 확인을 한 작업으로 묶어 배정한다.

### 자기 사본에서 구현한다

실행기는 지정된 소스의 현재 내용을 `base/`와 `workspace/`에 복사한다. `base/`와 `baseline.json`은 시작 상태를 보존하고, `workspace/`는 작업자가 수정할 코드다. 배정도 `task.json`으로 저장한다.

task의 제품 수정 권한은 workspace 안의 `writes` 범위에 있다. 구현과 검증에는 자기 사본의 코드를 사용하고, 필요한 외부 원자료는 배정에서 지정한 위치를 읽는다. 다른 task가 수정 중인 코드에 의존하지 않는다. 필요한 선행 결과는 manager가 수용한 뒤 시작하는 task의 사본에 반영된다.

보고서와 필요한 근거는 자기 task 디렉터리에 작성한다. 임시 실행 자료는 제품 변경과 구분되는 위치에 둔다. 공용 소스와 다른 task의 기록은 읽기 전용으로 사용한다.

### 최소한의 확인을 마치고 보고한다

독립적으로 읽힐 문서·인수인계는 작성자와 대화하지 않은 후속 작업자의 진입점에서 따라 읽는다. 목적·용어·조건·책임과 필요한 판단 재료를 본문에서 이해할 수 있게 하고, 수행 과정은 작업 기록으로 연결한다. 자료를 추출·요약했다면 원문에서 중요한 내용을 먼저 찾고 결과에 남았는지 대조한 뒤, 결과의 주장이 원문에 맞는지도 확인한다. 기존 파일의 존재나 남아 있는 문장의 참만 확인하면 중요한 누락을 놓칠 수 있다.

구현한 기능이 동작함을 판단할 수 있는 가장 적은 검증을 수행한다. 충분하면 정적 분석으로 끝낸다. 실제 사용을 막는 결함을 자기 범위에서 발견하면 수정하고 필요한 확인을 마친다. 배정 밖의 결정이나 제공자 수정이 필요하면 확인한 문제와 영향을 보고한다.

결과는 `report.json`에 작성한다. 수행한 내용과 이유, 실제 확인 방법·결과·한계, 변경 파일, 후속 판단에 필요한 발견을 적는다. 완료하지 못한 부분도 현재 상태대로 남긴다. 형식은 뒤의 보고서 참조 절을 따른다.

제출 전에 다음 명령으로 보고 필드와 실제 변경 경로를 확인하고 형식 오류를 고친다.

```powershell
python ENGINE/check.py report RECORDS TASK
```

이 검사는 형식을 확인한다. 실제 동작의 타당성과 완료 여부를 뒷받침하는 것은 작업 결과와 기록한 근거다.

review도 같은 읽기·보고 절차를 따른다. 제품은 수정하지 않고 배정된 범위에서 사용자 요구 충족 여부를 판단한다. 결과 사용을 막는 결함과 선택적인 개선을 구분해 manager가 후속 행동을 결정할 수 있게 한다.

## 3. Manager가 결과를 받아 다음 작업으로 잇는 순서

### 완료 사건과 실제 결과를 읽는다

manager는 현재 context·plan·seams와 지정된 inbox를 읽는다. inbox에는 이번에 종료한 task와 manager가 시작될 때 실행 중이던 task의 정보가 있다. 실행 상태는 이후 달라질 수 있으며, manager가 판단하는 동안 도착한 새 완료 사건은 다음 manager에게 전달된다.

종료한 task의 보고와 판단에 필요한 산출물을 대조한다. 프로세스가 종료됐다는 사실만으로 결과를 수용하지 않는다. 보고가 없거나 실행이 실패했다면 로그와 남은 파일에서 유효한 결과와 미완료 부분을 확인한다.

수용할 제품은 후속 작업자의 실제 진입점에서 본문과 근거까지 읽는다. 작성자의 대화나 별도 설명 없이 필요한 맥락과 핵심 내용을 이해·판단·사용할 수 있는지 확인한다. 자료 추출 결과는 원문→중요 내용→제품의 누락 대조와 제품→원문의 정확성 대조를 함께 수행한다. 중요한 누락은 보완 대상으로 판단하며, 형식 검사·링크·해시만으로 충분성을 인정하지 않는다. review 배정에도 이 검사 경로와 범위를 명시한다.

### 변경을 통합하고 수용 여부를 정한다

변경 파일을 공용 소스에 반영할 때는 다음 명령을 사용한다.

```powershell
python ENGINE/workspaces.py integrate REPO RECORDS TASK
```

통합기는 변경 경로가 배정 범위 안에 있는지 확인하고, 각 파일의 시작 상태·현재 공용 내용·task 결과를 비교한다. 공용 소스에 충돌하는 변경이 있으면 덮어쓰지 않고 충돌을 반환한다. manager는 두 변경의 목적을 확인해 해당 파일을 조정할 작업을 배정한다.

통합 결과는 task의 `integration.json`에 남는다. 변경이 없는 조사나 review도 같은 명령으로 변경 없음과 통합 처리를 기록한다. 공용 소스의 복사와 통합은 서로 겹치지 않게 처리되며, 이미 시작한 task는 자신의 사본에서 계속 작업한다.

manager가 결과를 받아들이면 task ID를 queue의 `accepted`에 넣는다. 부분 결과를 수용하더라도 남은 목표가 충족됐다고 해석하지 않는다. 미완료 부분은 후속 작업과 현재 계획에 반영한다.

### 현재 맥락과 후속 배정을 갱신한다

확인한 결과를 context·plan·seams에 반영한다. 다음 세션이 현재 동작과 판단 이유를 이해할 수 있도록 필요한 조건과 인터페이스를 구체적으로 유지한다. 불필요해진 제약·구조·작업은 제거하거나 축소한다.

그 상태에서 독립적으로 진행할 수 있는 작업을 함께 배정하고, 실제로 필요한 선행 결과만 `depends_on`에 둔다. 각 task의 objective와 입력을 준비한다. 실행 중인 task는 시작할 때 고정한 배정과 입력 사본을 계속 사용한다.

### 배정을 게시한다

공용 문서를 먼저 갱신하고 게시할 queue를 별도 파일에 작성한다. 다음 명령으로 그 파일을 확인하고 형식 오류를 고친다.

```powershell
python ENGINE/check.py queue RECORDS QUEUE_FILE
```

마지막 인자를 생략하면 현재 `queue.json`을 검사한다. 확인한 파일은 작성이 끝난 상태에서 `queue.json`으로 원자 교체한다. 게시가 끝나면 이번 manager 세션의 공용 변경도 끝낸다.

이 순서가 필요한 이유는 실행기가 게시된 배정을 즉시 사용할 수 있기 때문이다. 새 task를 시작할 때 필요한 맥락과 objective가 먼저 완성돼 있어야 한다.

## 4. 결과를 수용한 뒤의 실행과 종료

실행기는 선행 task가 모두 수용된 작업을 `max_workers` 범위에서 시작한다. task가 종료되면 manager가 결과를 처리하며, 다른 worker는 계속 실행된다. manager는 한 번에 하나씩 실행된다.

필요 없어진 작업은 queue의 `cancelled`에 표시한다. 아직 시작하지 않았다면 파견에서 제외하고, 이미 실행 중이면 종료까지 기다린다. 취소된 작업이 필요한 후속 배정도 함께 조정한다.

최종 review는 수용된 구현 결과가 모두 반영된 상태를 대상으로 한다. 사용자 목표를 충족하고 review가 완료·수용됐으며 실행 중이거나 미해결인 task가 없으면 manager가 `complete`와 완료 이유를 게시한다. 외부 입력이 있어야 진행할 수 있으면 필요한 입력과 이유를 기록하고 `blocked`로 게시한다. 두 상태에서는 새 task를 파견하지 않으며 실행 중인 작업은 종료까지 기다린다.

실행기는 프로세스 상태를 `state.json`에 기록한다. 세션은 이 파일을 직접 편집하지 않는다. 실행 중단·재개·동시 실행 수 변경과 Windows worker 인계는 [README.md](README.md)의 운영 절차를 따른다.

실행기를 시작·재개하는 준비 세션은 [독립 프로세스 기동 절차](README.md#실행하고-결과를-확인하기)로 호출 세션과 실행기의 수명을 분리한다. PID와 새 기동 로그를 확인하면 실행 위치를 반환하고 끝내며, 이후 배정·통합·검토는 실행기와 manager가 이어간다. 준비 세션의 대기·연결 유지가 전체 작업의 실행 조건이 되어서는 안 된다.

## 5. 배정 파일 참조

`queue.json`은 작업 목록과 결과 수용 상태를 담는다. 다음 예시는 문자열 처리 함수가 수용돼 그 함수를 사용하는 명령행 작업을 시작할 수 있는 상태다.

```json
{
  "status": "active",
  "tasks": [
    {
      "id": "normalize-name",
      "kind": "work",
      "depends_on": [],
      "writes": ["src/names.py"],
      "inputs": []
    },
    {
      "id": "name-command",
      "kind": "work",
      "depends_on": ["normalize-name"],
      "writes": ["src/cli.py"],
      "inputs": ["src/names.py:normalize_name"]
    }
  ],
  "accepted": ["normalize-name"]
}
```

최상위 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `status` | `active`: 진행, `blocked`: 외부 입력 대기, `complete`: 개발 완료 |
| `tasks` | 수용된 task를 포함한 배정 목록 |
| `accepted` | manager가 실제 결과를 판단하고 통합해 수용한 task ID 목록 |
| `cancelled` | 필요 없어진 task ID의 선택 목록 |
| `reason` | 차단 또는 완료 이유. `blocked`와 `complete`에서 필수 |

각 task는 다음 필드를 가진다.

| 필드 | 의미 |
|---|---|
| `id` | 소문자 영문·숫자·하이픈으로 된 고유 ID |
| `kind` | 구현·수정·조사는 `work`, 제품을 수정하지 않는 검토는 `review` |
| `depends_on` | 결과가 먼저 수용돼야 하는 task ID 목록 |
| `writes` | `REPO` 기준 상대 파일 또는 `/`로 끝나는 디렉터리 범위. 수정은 workspace의 해당 경로에서 수행 |
| `inputs` | 추가로 읽을 자료의 참조 목록. 어느 소스·기록·외부 경로인지 objective에서 설명 |
| `model`, `effort` | 필요한 경우 Codex 호출에 전달하는 선택적 문자열 |

task마다 `tasks/ID/objective.md`를 준비한다. review의 `writes`는 빈 목록이다. `inputs`는 작업자의 읽기를 안내하며 실행기가 자동 복사하지 않는다. manager의 모델 선택은 `settings.json.manager`에 지정한다.

의존관계는 순환할 수 없으며 수용·취소 ID는 배정 목록에 존재해야 한다. 시작한 task의 정의와 ID는 유지하고 후속 변경은 새 task에 배정한다. 최종 review는 수용된 모든 work task를 직접 또는 간접 선행으로 포함해야 한다.

## 6. 보고서 참조

task는 `report.json`에 다음 형식으로 결과를 남긴다.

```json
{
  "status": "complete",
  "summary": "normalize_name(text)가 문자열 양끝의 공백을 제거해 반환한다.",
  "changes": ["src/names.py"],
  "verification": "normalize_name('  Mina  ')를 한 번 호출해 'Mina' 반환을 확인했다.",
  "findings": []
}
```

| 필드 | 의미 |
|---|---|
| `status` | `complete`: 배정 완료, `partial`: 유효한 결과와 미완료 부분이 있음, `blocked`: 필요한 입력이나 의존성이 없어 진행할 수 없음 |
| `summary` | 수행 결과와 방법·판단 이유를 설명하는 비어 있지 않은 문자열 |
| `changes` | 시작 사본과 비교한 실제 변경 상대 경로의 문자열 목록 |
| `verification` | 실제 확인 방법·결과·한계를 설명하는 비어 있지 않은 문자열 |
| `findings` | 후속 판단에 필요한 사실·문제·선택의 문자열 목록 |

정적 분석으로 확인했다면 읽은 코드와 확인한 동작을 `verification`에 설명한다. 실행하지 않은 검증을 수행했다고 기록하지 않는다. `complete`는 해당 task의 배정 완료이며, 프로젝트 전체의 완료는 manager가 최종 review와 사용자 목표를 근거로 판단한다.
