사용자 세 기준에 따른 재현·수리·종료 판단

사용자는 오류 전후 이미지 판독 누락 목록을 받은 뒤 모든 기존 불가 판단을 다음 세 기준으로 다시 검토하라고 지시했다. 이 문서는 이번 재개의 현행 계약이며 기존 prompt.md·report.md·FINAL-REVIEW.md의 더 약한 종료 판단보다 우선한다. 기존 쓰기 범위·인증 경계·한 자료원 계약은 유지한다.

1. 문제가 발생하면 같은 문제를 다시 재현하면서 발생 직전·직후의 실제 화면을 모두 이미지로 열어 읽는다. 안정 상태도 읽어 중간 렌더와 구별한다. 그 판독에서 얻은 단서까지 사용해도 해결하지 못했을 때만 불가 판단을 검토한다.
2. 입력 문법·선택자·경로·필드 조합 등 자신의 실수가 더 개연성 있는 설명이면 접근 방식을 다시 검토한다. 정상 최소 입력과 비교하고, 대소문자·따옴표·괄호·escaping·필드별 문법·직렬화·세션·실제 선택된 제어를 확인한다. 복잡한 식의 실패만으로 기능 전체를 제한하지 않는다.
3. 시간초과·경로 오류·대기 조건·캡처 실패·테스트 의존성 등 고칠 수 있는 기술적 문제는 고치고 다시 실행한다. 이를 서버 문제나 방법 소진의 근거로 쓰지 않는다.

작업자는 기존 같은 thread와 사본의 결과를 보존한다. 먼저 개별 임무에 연결된 실패 ID, 자신의 최신 report.md·visual-review.md·experiments.json과 실제 코드를 읽는다. 누락 목록 정본은 C:/math/services/scholarly-mcp/data/dispatch/20260913T021511Z/failure-visual-gaps-20260913T0655Z.md다. 이 목록의 N/B는 오류 사건 묶음이지 현재 미해결 기능 수가 아니다. 해당 과제에 이미 전후 판독이 있는 대표 실패도 세 기준의 나머지 조건을 충족하는지 확인한다.

재현에서는 실패 입력과 기대 기능을 고정한다. 입력 전의 화면을 먼저 읽고 현재 제어를 조작한 뒤 직후·안정 화면을 다시 읽는다. 실제 request method·host/path·선택 필드·응답 status/MIME·파일·문헌 식별자를 같은 실행에 연결한다. 비공개 값은 터미널·이미지·공개 보고에 노출하지 않는다. 사진 파일명이나 이미지 수를 판독 완료로 대신하지 않는다. 클릭 전에 정상 대조를 찍고 다음 실행의 오류 화면을 붙여 같은 사건이라고 하지 않는다.

API 요청에는 공식 문헌 UI의 정상 화면만으로 전후 조건을 충족했다고 하지 않는다. 공식 API 실행 콘솔, 원 응답을 직접 표시하는 브라우저, 실제 개발자도구나 소유 CLI 실행 화면 등 해당 요청의 입력·응답을 실제로 관측하는 도구를 사용한다. GET/POST·fields·인증 유무·세션 등 원 실패 요청과 달라진 조건은 명시한다. 로컬 진단 도구를 사용하면 실제 요청에서 얻은 응답을 표시하고 request/response 원 파일과 결속해야 한다. 이를 자료원 고유 UI로 표시하거나, 오류 문구를 임의로 그린 이미지·과거 로그를 새 실행 화면으로 제시하지 않는다. 원 사이트 UI가 있는 기능은 그 UI의 실패 전후 판독도 수행한다.

어떤 진단 도구를 선택하든 기존 사용자 창·전역 포커스·OS SendKeys를 조작하지 않는다. 전용 브라우저·프로세스·프로필만 사용한다. 이미지 열람이나 캡처가 실패하면 그 도구 경로를 고친 뒤 같은 실험을 다시 수행한다. 화면 없이 실행되는 로컬 parser는 원 UI를 띄운 채 parser 실행 전후를 캡처하고 실제 실행 로그로 연결할 수 있다. 고장 난 테스트 환경은 원본의 정상 의존성을 읽기 전용으로 적재하거나 자신의 사본 안에서 구성하여 검증한다. 원본 코드·공유 인증·Git index·다른 작업 사본은 수정하지 않는다.

사용자는 기관 접속 IP나 기관 식별번호 때문에 캡처를 복잡하게 가공하거나 다시 찍지 말라고 지시했다. 이 표시 때문에 별도 마스킹·재촬영·승인 절차를 추가하지 않는다. 실제 암호·인증 토큰의 비공개 경계는 유지한다.

한 번의 새 시도에서 이전 오류가 재현되지 않으면 원 입력과 조건이 같은지 확인한다. 같은 조건에서 기능이 성공하면 실제 성공과 원 오류 미재현을 기록하고 불가능 주장을 철회한다. 과거의 일시 오류를 일부러 다시 만들거나, 한 번 성공했다고 반복 가용성까지 보장하지 않는다. 서로 다른 endpoint의 성공을 원 실패 endpoint의 복원으로 바꾸지 않는다.

429에서는 표준·custom retry와 원 정책을 먼저 읽는다. 이전 CORE 사례처럼 헤더 누락이나 잘못 읽은 reset 시각은 로컬 결함이다. 요청량·동일 출구·client lifetime·동시 호출·fields·endpoint 차이를 가설별로 대조한다. 새 키, 연락 이메일, IP 변경·회전, 계정 추가, 제한 우회는 사용하지 않는다. 서버가 지정한 대기 중에는 로컬 구현·문법·원자료 분석을 진행한다. 새 근거가 없는 빠른 반복은 금지한다.

KUDOS의 기존 자격은 기존 허용 범위의 KUDOS 로그인에만 사용한다. SIAM 조사에서 거부됐던 KNU IdP 로그인은 다시 제출하지 않는다. 사용자에게 새 자격을 요구하거나 다른 인증 대상에 기존 암호를 시험하는 것은 이번 재현의 일부가 아니다. 해당 경계의 기존 전후 증거를 검토하고 자격 없이 독립 수행할 수 있는 분석을 마친다. 인증 실패를 계약·구독권 부재로 일반화하지 않는다.

기능을 거부하는 validator를 추가하는 것은 마지막 수단이다. 공식 문법으로 같은 의미를 보존할 표현이나 UI 제어가 있는지 확인한다. 실패 입력을 버리거나 다른 문헌·다른 필드로 바꾸어 성공만 만드는 것은 원 문제 해결이 아니다. 의미를 보존할 수 없다면 정확한 오류·부분 결과를 남기되 지원 가능한 입력을 함께 막지 않는다.

각 실패 묶음의 처분은 다음 중 하나다. restored는 원 기능을 수리하고 실제 성공을 검증한 경우다. not_reproduced는 같은 조건의 새 재현이 성공해 원 오류가 현재 다시 나타나지 않은 경우다. confirmed_source_condition은 재현·전후 실제 판독·로컬 가설 검증·기술 문제 수리를 마쳤고 그 범위에서 자료원 상태가 실패를 설명하는 경우다. unresolved는 원인이나 실행 방법이 남아 있는 경우다. excluded_by_user는 기존 사용자 결정의 자격·거래 경계에 해당하는 경우다. confirmed_source_condition도 영구 불가능 선언이 아니다.

자신의 output_dir에 criteria-review.json을 작성한다. 최상위 task_id와 items 배열을 두고, 각 항목에 case_id, observed_failure, reproduction, before_image, after_image, stable_image, image_read_evidence, request_response_evidence, local_hypotheses_tested, technical_fixes_and_retests, disposition, remaining을 기록한다. 경로는 실제 파일의 절대 경로다. 이미 충족된 같은 실패의 근거를 사용할 때는 실행 시각과 판독 근거를 대조하고 단순한 보고 자기선언을 근거로 쓰지 않는다. 자신의 보고·코드에서 추가 발견한 제한도 별도 ID로 남긴다.

이 파일 형식은 내용 검토를 돕기 위한 것이다. 빈 필드를 채우거나 이미지만 추가하는 것으로 종료하지 않는다. 세 기준을 만족하지 못한 unresolved 항목이나 실행 가능한 기술 수리가 남으면 계속 작업한다. 기존 completed/exhausted 반환을 이번 재검토의 결론으로 재사용하지 않는다. 최종 반환에는 criteria-review.json을 evidence_paths에 포함하고, 실제 수리·설명·회귀·새 SDK 검증까지 마친다. 주 세션이 각 항목의 코드·이미지·요청·결과를 독립적으로 대조한 뒤 원본에 통합한다.
