## 종합

이번 종합의 목적은 사용자가 제시한 여덟 가지 피드백을 남아 있는 작업 기록과 대조하고, 이후 작업에서 실제 판단을 개선할 방법을 정하는 것이다. 작업 기록에 나타난 실패와 교정은 관찰 가능한 근거다. 그 실패를 Astra의 내적 사고 습관이나 시스템 프롬프트 하나의 효과로 설명하는 것은 별도의 가설이다. 관찰과 원인 가설을 구별하며 D-0001~D-0003의 사건군 종합을 함께 사용한다.

여러 사례에 공통으로 나타나는 개선 지점은 다음 행동을 고르는 기준이다. 문서를 읽었는지, 이미지를 열었는지, 검사를 통과했는지, 작업자가 완료라고 반환했는지는 각각 실제로 일어난 행동이다. 그러나 그 행동이 현재 문제의 불확실성을 줄였거나 사용자의 목표를 달성했는지는 따로 확인해야 한다. 이 구분을 작업의 착수, 실행, 수리, 위임 회수, 최종 작문에 연결할 필요가 있다. 이는 관찰한 사례들을 설명하는 작업 가설이며 모든 실패의 단일 원인을 입증한 결론은 아니다.

### 피드백별 판단

1. **재독과 컨텍스트 비용.** 9월 9일 시작한 Astra 원 세션의 도구 입력과 출력을 짝지어 현재 여섯 스킬 문서의 전문이 실제 출력에 포함됐는지 확인했다. 명료한 산문 8회, AI 프롬프트 8회, 절차문 7회, commit-harness 10회, write-for-reader 6회, test-driven-development 1회가 정확한 전문 일치였다. 세션에는 명시적 압축 사건 17개가 있고 이 전문 일치들은 문서마다 같은 압축 구간에서 중복되지 않았다. 따라서 이 표본은 불필요한 전문 재독을 입증하지 않는다. 현재 문구와 다르거나 출력이 잘려 전문 일치에서 빠진 열람도 있으므로 전체 재독이 적절했다는 판정도 아니다. 실제로 처음의 큰 묶음 조회 출력이 잘린 뒤 참조 문서를 나눠 읽은 사례가 있다. 개선은 재독 금지보다 최초 출력의 완전성, 현재 보존된 정보의 재사용, 필요한 원문의 제한된 재확보에 둔다.

2. **구조와 위임.** [[M-0113]]~[[M-0115]]는 큰 확정을 검증 라운드의 수정 조각으로 세 번 반영하다가 같은 결함군에 약 160개 조각을 다시 쓴 사례다. 이후 편집자 한 명이 23자리를 직접 고치고 검증한 경로로 마무리했다. 이 기록은 개별 조각의 작성법보다 전체 적용 경로를 바꿀 실익을 보여 준다. 서로 다른 산출을 공통 표현으로 바꾼 뒤 후속 처리를 공유하는 방식은 유용한 후보지만 모든 작업의 필수 단계로 만들 수는 없다. 공통 처리가 여러 번 반복되고, 원자료의 차이와 출처를 보존하며, 변환과 회수 비용보다 이익이 클 때 선택한다. 자료원별 의미를 조사하는 작업은 분리할 수 있지만 공통 API 계약, 성공 판정, 원본 통합은 전체 맥락을 보는 담당자가 유지해야 한다. [[M-0238]]의 24개 과제 파견은 이런 구조가 전혀 없었던 것은 아니라는 반례다. [[M-0240]]·[[M-0243]]은 반환과 종료 판정이 후속 재검토를 필요로 했음을 보여준다.

3. **과설계와 직접 관찰.** [[M-0245]]의 DBLP 작업자는 격리 사본에서 추출이 실패하자 별도 61줄 파서를 제안했다. 원본에서는 기존 파서와 새 SDK의 일곱 형식 추출이 통과해 새 파서를 통합하지 않았다. 새로운 구현 전에 원본과 사본의 환경 차이를 확인하면 유지할 코드를 줄일 수 있는 사례다. 같은 기록의 limit=101 실패 화면은 실제 요청과 `start must be >= 0 and limit must be 1..100` 응답을 보여준다. 이 화면은 원 사이트 화면이 아니라 실제 MCP 실행 콘솔이다. 화면이라는 형식 자체보다 원격 호출 전의 로컬 거절을 구별하는 정보가 핵심이다.

4. **입력과 서버 원인 구분.** [[M-0228]]의 ACM은 일반 행의 기본 AND 결합을 검색식 전체의 한계로 확대했다. `Edit Query`에서 교차 필드 OR를 실제로 실행한 뒤 그 판단을 교정했다. 원 실험 파일의 단일 집합 2,327건과 93,527건, 교집합 320건, 합집합 95,534건은 집합 관계와도 맞는다. [[M-0245]]의 DBLP는 같은 해석된 요청에서 공백을 `+`로 보낸 경우 500, `%20`으로 보낸 경우 200이었다. 이는 서비스별 직렬화 문제를 수리한 사례이며 `+`가 일반 URI 규격에서 항상 틀렸다는 뜻은 아니다. 반대로 [[M-0254]]의 Semantic Scholar는 올바른 ID 하나를 보낸 두 batch 요청에서 429가 유지됐다. bulk 검색의 잘못된 Boolean 예제와 별도 batch endpoint의 429를 같은 원인으로 묶지 않는다.

5. **작문.** [[M-0051]]에서는 압축 때문에 필요한 정의와 소유권 설명이 부족해졌고, [[M-0081]]에서는 괄호와 굵은 인라인 표현이 겹친 긴 답변이 자연스러운 산문으로 다시 쓰기를 요구받았다. 현재 write-for-reader는 이미 충분성을 간결성보다 앞에 두고 행위자, 문단의 주제, 연결 관계, 문서 전체 퇴고를 규정한다. 실제 M-0240에는 `24개Codex CLI의간략events.jsonl에는view_image항목이따로없었다`처럼 일반 산문에 필요한 띄어쓰기가 사라진 문장이 있다. 형식상 정보가 있어도 독자가 문장 구조를 복원해야 한다. 현행 지침이 짧게 쓰기 위해 의미를 빼라고 요구한다는 주장은 지지되지 않는다. concise라는 상위 지시가 이런 산출의 원인이었는지는 비교 실험이 없어 미확인이다. 개선의 첫 적용점은 새 문체 규칙의 추가가 아니라 제출할 글 전체를 독자의 순서로 읽고 실제 문장을 교정하는 단계다.

6. **경중과 순서 판단.** 앞으로의 행동은 완료 가능성을 높이는 정도, 구별할 수 있는 불확실성, 비용, 의존 작업에 미치는 영향으로 고른다. 고정 점수표를 만들 필요는 없다. 느린 재시도보다 실제 입력 한 번을 확인하는 일이 더 많은 가설을 가를 수 있고, 공통 계약 하나를 정하는 일이 여러 개별 작업을 진행시킬 수 있다. 실제 입력 확인이나 공통 계약 확정이 우선할 이유를 작업 계획에 짧게 드러낸다. 이 판단법의 장기적인 효과는 후속 실전에서 검증해야 한다.

7. **지시를 검토하는 자율성.** [[M-0173]]은 확인하지 않은 8천 토큰 가정 위에 중요 문제와 추가 정책을 세웠다가 철회한 직접 사례다. 논리적으로 가능한 문제와 실제 조건에서 중요한 문제는 서로 다른 판단이다. 사용자가 정한 목적과 가치, 사실에 관한 주장, 제안한 방법, 결과에 반드시 필요한 조건을 구별한다. 환경에서 확인할 수 있는 전제는 직접 확인하고, 방법은 목적과 권한 안에서 개선한다. 문제를 찾으라는 요청은 문제가 있다는 증거가 아니다. 지적은 위반한 기준과 실제 사실을 함께 제시하며 다른 합리적 해석과 중요도를 검토한다. 지적이 틀리거나 없으면 검증 통과로 닫는다. 이번 재독 표본과 실제 429는 사용자의 비판을 모든 사례에 적용하지 않게 하는 경계다.

8. **시야와 단계적 접근.** [[M-0089]]에서는 검사 대상 문서만으로 범위를 닫아 명시된 하류 동기화 요구를 놓쳤다. [[M-0141]]에서는 두 표본의 반례를 해당 부재 판정 규칙이 적용된 전체 집합의 재검토로 연결했다. 착수 직후 최종 대상만 바꾸기보다 목표 달성에 필요한 선행 지식을 확인한다. 대규모 자료 처리에서는 실제 표본으로 형식, 식별자, 오류, 비용을 확인한 뒤 공통 처리를 설계할 수 있다. 표본의 목적은 전수 검증을 대체하는 것이 아니라 잘못된 자동화를 대량 실행하기 전에 계약을 확인하는 것이다. 이번 dream도 L1의 실제 사건을 비교한 뒤 L2 통찰과 L3 현행으로 올리는 순서를 따른다. 과거 D 노드가 없으므로 세칙에 남은 옛 D 번호를 현재 사건의 근거로 사용하지 않는다.

## 제안

### 기존 원칙을 실행할 위치에 통합한다

AGENTS의 일반 원칙과 write-for-reader의 품질 계약은 이미 이번 개선 방향을 허용한다. 동일한 원칙 네 문단을 다시 추가하는 안은 채택하지 않는다. 이번에 확인한 적용 경로, 관찰의 판단 기준, 위임 경계와 필요한 재독의 예외를 관련 L 항목에 통합했다. 현재 단계에서는 프로젝트 지침과 서비스 코드를 수정할 필요가 없다.

### 기억 소비에서 재독의 사유와 읽기 범위를 맞춘다

L-0015에는 현재 문맥에 원문이 충분히 남고 변경 징후가 없으면 재사용한다는 판단 기준을 통합했다. 압축, 요약 전달, 변경, 중요한 문언·수치 확인은 다시 읽을 이유가 될 수 있다. 재확인이 필요한 범위만 읽으며 전문 판독 계약이 있는 대상은 나누어 전문을 확보한다. 파일별 장부나 새 캐시 서비스를 만들지 않는다. 이는 memory-harness의 착수 읽기 계약을 없애는 제안이 아니다.

### 작문 규칙을 추가하기 전에 기존 퇴고를 실제 산출에 적용한다

스킬 문면에는 이미 필요한 규칙이 있다. 최종 제출할 문서를 독자가 처음 만나는 순서로 다시 읽어, 누가 무엇을 하는지, 왜 앞 문장에서 다음 문장으로 이어지는지, 판단에 필요한 조건이 보존됐는지 확인한다. 필요하면 문장 몇 개의 교정에 그치지 않고 문단 순서를 바꾼다. 중요한 독립 산문의 점검이며 모든 짧은 진행 보고에 별도 검증자를 붙이라는 뜻은 아니다. 기존 규칙으로 충분한 부분에는 새 규칙을 제안하지 않는다.

### 상시 출력 의무의 목적과 비용을 별도로 검토한다

현행 AGENTS는 모든 작업 전 광범위한 학술 에세이와 규정 목록을 요구한다. 이 요구에 따른 텍스트 적재 비용은 실제로 발생한다. 이것이 모든 재독이나 작문 결함의 원인이라는 증거는 없다. 지식을 회상해 수행 역량을 높인다는 목적을 보존하면서, 매번 공개하는 범위를 해당 작업의 판단을 바꾸는 지식과 규정으로 조정할 실익을 사용자와 검토할 수 있다. 승인 전에는 이 출력 의무를 임의 축소하지 않는다.

### 다음 실전에서 실제 효익을 확인한다

개선 효과의 기준은 새 문서의 수나 검사의 수가 아니다. 다음 관련 작업에서 같은 실패의 입력·응답을 스스로 대조했는지, 사용자가 지적하기 전에 불필요 구현을 제거했는지, 이미 확보한 내용을 불필요하게 다시 적재하지 않았는지, 초안의 의미와 가독성을 동시에 보존했는지 확인한다. 정상적인 외부 실패와 필요한 재독을 실패 점수에 넣지 않는다. 별도 평가 플랫폼은 만들지 않고 기존 작업 기록에 결정적인 사례와 반례를 남긴다.

## 수렴·유연성 원장

처음의 가정은 여덟 피드백이 서로 연관된 실행 판단의 문제를 가리킬 수 있다는 것이었다. 실제 사례는 관찰과 원인, 활동의 존재와 목표 달성을 구별해야 한다는 방향을 지지한다. 반면 전문 재독의 표본과 실제 batch 429는 모든 비판을 개별 사례에 일괄 적용하는 해석을 제한한다. 작문의 내적 원인과 모델 고유의 일반 실패율은 이번 자료로 확정하지 않는다.

새 통제 구조를 추가하기보다 기존 지침의 판단 기준과 실제 수행을 연결하는 방향을 선택한다. 판단을 고정 횟수·항상 같은 단계·무조건적 이미지 열람으로 대체하면 이번에 비판한 형식적 수행을 다시 만들 수 있기 때문이다. 기억 내부의 종합과 현행 갱신은 적용했다. 동일 원칙을 프로젝트 지침에 추가하는 안은 폐기했으며, 상시 공개 출력의 범위 조정은 사용자와 검토할 선택지로 남긴다.

세 묶음의 전문 판독과 교차 독립 검토, 주 세션의 원자료 대조와 현행 통합을 마쳤다. 초기 초안의 근거보다 강한 재독·서버 귀속 주장과 고정 순서·새 장부 처방은 교정했다. 최종 독립 검토가 지적한 결함 유형별 통제의 절대 배정과 단일 표본의 고정도 비용·기존 통제·실행 조건의 차이에 따른 선택으로 고쳤다. 같은 절대 배정이 남아 있던 dream 세칙도 함께 교정해 현행 노드와 일치시켰다. 같은 자료에서 이를 다시 종합해 얻을 새 자율 실익은 확인되지 않아 이번 사이클에서 종료하며 후속 예약은 만들지 않는다. 방법의 장기 효과는 아직 검증되지 않았고, 새로운 실제 작업·반례 또는 사용자의 제안 채택이 있을 때 다시 검토한다.
