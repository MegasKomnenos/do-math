[[M-0527]]의 미결 점 표기 목록을 이어서 처리했다. 상태 출력은 저장 상태의 단순 사본이 아니라 supervision_facts와 OBSERVED_FIELDS의 관측값을 합치며, operating_summary·academic_status·operation_progress도 별도 생산자다. 실제 함수의 객체 정의에 명시한 bindings를 합치고, 여러 literal 반환을 가진 생산자는 variants=True로 정본 대안을 읽도록 검사기를 확장했다. 불명확한 spread는 여전히 실패하며, 소스 표현이 사라져 사용되지 않는 binding도 실패한다. 다른 공간의 allowed_profiles가 status에 있다는 식의 잘못된 참조는 거부한다.

profile_selection, operating_summary, academic_validation, operation_progress, status, operational_evidence, governance를 추가해31개 공간을 검사한다. status의 operating_summary는 실제 호출 표현에 결속하고, operational_evidence의 activity_continuations는 해당 입력 생산자의 실제 추가 대입에서 읽는다. 저장 runtime과 역할 입력은 같은 명칭이라도 서로 다른 구조임을 유지한다.

governance.charter는 입력 필드지만 governance.mathematical_goal_basis는 함수다. 같은 점 표기로 두 의미를 섞지 않도록 운전 문서의 실제 함수 참조 다섯 곳을 module.function(...) 표기로 바꿨다. 검사기는 실제 callable로 해소되는지 확인하며 없는 함수나 planning.RECORD_FAMILIES 같은 비호출 값을 함수로 적으면 실패한다. 해당 필드 공간에 함수 이름을 점 표기만으로 넣는 것도 거부한다.

contract_check.*와 integration.currentness는 필드가 아니라 진단 코드다. 실제 submission.py/integration.py에 있는 완전한 코드 문자열과 대조하며, integration.coverage처럼 다른 소유자의 이름을 빌리면 실패한다. 함수 호출 표기와 .py 파일명은 이 진단 검사로 잘못 분류하지 않는다. 파일명은 필드와 구별하는 분류일 뿐 현재 디스크 존재나 실행 결과를 인증하지 않는다.

현재 문서에서 필드104곳·함수5곳·진단7곳을 검사하고 파일명33곳을 구별했다. 남은 문맥별 점 표기는57곳/고유43개다. record.content는 거버넌스 결정의 객체, record.family는 조회 결과, 입력 소비자의 record.explanation은 새 지식 후보인 것처럼 동일 변수명이 다른 소유자를 가리키므로 전역 합집합으로 승인하지 않는다. change.value는 실제 조건 판정의 선택적 읽기이며 단순한 공개 입력 스키마 키 목록만으로 부재를 판정할 수 없다. 이런 남김의 원문 위치를 기존 작업판 B111에 보존했다.

구조53개가 통과했고 실행 중 소스 변경은 없다. 검증/2026-10-05-문서-함수-진단/report.json과 작업판의 해시/시간이 원증거다. 제품 코드는 바꾸지 않았고 검사 지원 코드와 문서 표기를 고쳤다. 미러 및 기억 색인 검증을 적용한다. 13-C의 무공간 이름·역할별 산출 전건과 실제 운전 도구 바이트 한도는 아직 닫지 않았다. 원래 전체 요구와 최종 일반/fresh T3/변이/T4/T5 목표를 유지한다.
