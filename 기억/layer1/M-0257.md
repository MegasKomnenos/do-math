CORE의 indexed text, work-linked PDF, explicit output download, files01 복구 네 사본을 현 원본에 선택 병합했다. 명시 /v3/outputs/{id}/download를 허용하고, work의 outputs 관계와 downloadUrl/links의 같은 output ID를 대조한다. files01의404·timeout·connection error·5xx는 같은 output metadata가 실제 제공하는 현행 URL로 해결한다. 최초429·401·403·410이나 제거/비활성 metadata에서는 해결용 추가 다운로드를 시도하지 않는다. 다른 저장소·sourceFulltextUrls·브라우저로 넘어가지 않는다.

독립 검토는 후보가 최초429 뒤 metadata503까지 추가 호출하던 문제와 disabled metadata의 다운로드 URL을 따르던 문제를 발견해 수리했다. root는 연결 후보가 이미 지원하는 same-output API download URL인 경우도 빠지지 않도록 두 회귀를 더했다. CORE files16·public7검사가 통과했고 전체624검사에도 포함됐다. whitespace-only fullText를 본문으로 세지 않으며 실제 indexed 문자열, API 접근 안내문과 별도 공개 PDF의 상태를 구별한다.

공통 APIAdapter의 기존 timeout 인자·DBLP timed refresh·Crossmark rate 정보를 옛 사본으로 덮어쓰지 않았다. 표준 Retry-After를 우선하고 없을 때 X-RateLimit-Retry-After를 actionable retry_after로 보존한다. 성공 응답에서는 custom 시각을 rate_limit_retry_after 메타정보로만 남긴다. 처음 실패와 해결 단계 실패를 각각 반환하므로 legacy522와 metadata429가 하나의 모호한 파일 오류로 합쳐지지 않는다.

Root 새 원본 SDK는 초기 output을 세 번, work를 한 번 서버 안내 시각 이후 실행했으나429였다.11:29:09UTC output은 다음11:39:09,11:42:10 work는 다음11:52:10을 반환했다. 오류 body는0바이트여서 공급자 내부 bucket·정책 원인을 본문으로 확정할 수 없었다. 이 오류를 API key 필수나 문헌 부재로 바꾸지 않았다. files01은7,258바이트522를 반환하고 metadata 해결 단계에서429였다. 실제 실행 콘솔의 전후·안정 이미지를 읽고 원522 HTML도 외부 요청 없이 렌더해 Browser/Cloudflare Working, files01 Host Error와 원 서버 연결 시간초과 안내를 직접 읽었다.
