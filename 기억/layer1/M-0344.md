## 핵심

연결부의 계약을 확인하려면 함수가 서로 호출되는지만이 아니라, 저장 후 다시 읽는 표현 순서와 비동기 작업이 끝난 뒤 남은 게시 의무까지 따라가야 한다. 이번 감사에서는 이 두 이음새가 실제 연구 흐름을 막는 결함으로 드러났다.

## 맥락과 판단

사용자는 graphify를 적극적으로 활용해 do-math의 연결부와 경로를 정적으로 전수 대조하고, 확인한 버그를 수정하길 원했다. 인터뷰에서 실제 연구 구동은 제외하고 테스트는 정적 검토와 수정이 끝난 마지막 단계에만 실행하기로 정했다. 계약 충돌의 목표 동작은 앞뒤 맥락과 영향을 확인해 구현자가 판단하도록 위임했다. graphify는 위치 지도로 사용했고 결함 판단은 현재 문서·코드·테스트 결과로 했다. 감사 범위와 확인 수치는 추적되는 `docs/do-math/connection-audit-2026-09-25.md`에 남겼다.

큰 값 여러 개를 한 기록에 보존할 때 payload 참조 순서는 원래 딕셔너리 삽입 순서를 따랐지만 저장 JSON은 키를 정렬했다. 재읽기의 정본 인코딩 검사는 같은 논리 값을 다른 참조 순서로 재구성해 기록을 거부했다. 참조 생성 순서를 정렬하고 두 payload의 회귀 검사로 확인했다. `run(max_steps=1)`에서는 환경 관측 작업의 완료를 회수한 직후 루프가 종료되어 봉인된 제출의 재적용이 남았다. 다음 실행이 관측을 다시 열면 대기 상태가 반복될 수 있었다. 완료된 호출 뒤 게시 정산을 한 번 더 수행하도록 바꾸고, 실제 Git 상태를 거치는 학술 후속 통합 사례가 끝까지 통과하는 것을 확인했다.

제어 요청 순서도 벽시계가 뒤로 갈 때 역전될 수 있었고, 단조 시계만 우선하면 재부팅 후 순서가 깨진다. 인스턴스 inbox의 로컬 잠금 아래 지속 증가하는 접수 번호를 기록하는 방식으로 고쳤다. 여러 제어 요청의 동시 접수, 시각 역행, 재전송의 경계를 별도로 확인했다. 빈 목록을 기본 빈 객체로 치환해 형식 오류를 숨기던 산출 수집·검토 manifest·공급자 실패 입력 세 곳과 CLI 반환 설명도 정리했다.

## 검증과 남은 범위

최종 소스에서 단위 358개, 관련 통합 11개, Lean·자원·archive 29개가 통과했다. 그중 학술 후속의 한 통합 사례는 두 결함을 순서대로 드러냈고 수정 후 733초에 통과했다. 설치본 구조 검사와 미러 생성기 `--check`도 통과했다. 전체 통합 그룹의 완주 결과나 실제 모델 연구 성능의 증거는 없다. 테스트 `report.json`은 Git 제외 대상인 `.skill-workspace/do-math-audit-*-2026-09-25/`에 로컬 보관돼 있어, 장기적으로 추적되는 근거의 진입점은 위 감사 보고서다.

커밋 요청 직후에는 일반적인 파일 스테이징으로 들어갔으나, 사용자가 `commit-harness` 절차를 명시했다. 그 교정에 따라 생성 사본·커밋 기억·색인·검증 게이트를 같은 커밋의 구성원으로 포함한다. 다음 커밋부터는 저장소의 커밋 정본을 먼저 확인해 이 누락을 예방한다.

dream에서 묶을 후보는 완료 판정의 시간 경계다. 이미 끝난 비동기 호출이 만든 새 의무는 호출 회수와 별도로 정산돼야 하며, 제한 단계 실행은 그 정산을 건너뛰어서는 안 된다.
