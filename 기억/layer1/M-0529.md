[[M-0528]]의 미결57개 점 표기에서 record·result의 문맥 차이를 처리했다. record.content는 통치 기록, record.explanation은 지식 후보, record.family는 조회 결과다. 이를 전역 필드 합집합으로 승인하면 다른 객체의 이름으로 통과한다. 해당 문장 끝의 숨은 주석에 실제 소유자를 명시하고, 그 행에서만 적용한다. 없는 소유자·중복/미사용 별칭·기존 canonical 공간의 재정의를 거부한다. 주석을 다음 행에 적용하지 않는 것도 검사한다.

CLI의 result 역시 init·status·select-profile마다 다르다. 반환 객체의 이름만 찾으면 다른 명령의 필드를 섞을 수 있으므로 생산자의 명시 조건 분기와 반환 tuple 항목을 선택한다. 입력 manifest와 prompt는 최초 literal 뒤에 키를 더하므로 같은 객체에 대한 고정 키 대입과 update keyword를 읽는다. 동적 키나 불명확한 update를 자동 승인하지 않는다. checkpoint_source는 실제 evidence.update의 해당 keyword, recovery_source는 명시한 중첩 recover 함수의 두 반환에서 읽는다. 일반 생산자 탐색은 다른 중첩 함수의 필드를 섞지 않는다.

candidate_record는 공개 CANDIDATE 스키마만 보면 uncertainty_assessment를 놓친다. 실제 지식 입력 소유자인 knowledge_io._KNOWLEDGE_FIELDS를 참조했다. 초기화 운전 문서의 result.snapshot는 조회 결과를 가리키므로, 이름이 같다는 이유로 init_result에 연결하지 않고 남겼다. change.value 역시 실제 조건 판정의 선택적 읽기여서 선언 목록만으로 잘못된 필드라고 단정하지 않는다.

50개 공간의 필드139곳을 연결했고 함수5·진단7·파일명33의 구별을 유지한다. 단순 점 표기 미결은22곳이다. 무공간 이름, 배열 인덱스·대문자 상수 표기, 역할별 산출 전건, 실제 운전 도구의 읽기 출력 한도는 별도 미해소다. 13-C 전체 완료로 표시하지 않았다. 정확한 위치와 분류는 단계-전환표-2026-10-03.json의 document_context_owner_bindings에 보존했다.

구조55개가42.2초에 모두 통과했고 실행 중 변경은 없었다. 원본 보고는 검증/2026-10-05-문서-문맥-소유자/report.json에 바이트 그대로 보존했다. smell 검사는7.953초로 개별5초 기준을 넘었지만 검사 강도를 유지했다. 이 변경은 제품 실행 코드를 바꾸지 않는다. 미러와 기억 색인을 검증하고 main에 확정한다. 전체 일반/fresh T3/극단 변이와 정상 기준/T4·T5 및 원래19+11 요구의 남김은 계속 유지한다.
