ECCC는 원 검색이 있었지만 fetch에서 보고서 번호와 링크만 허용해 이름 입력을 invalid_target으로 거부했다. 이름을 기존 일반 검색으로 전달하고 후보 선택 상태로 반환하도록 연결했다. 제목 필드를 제공하는 검색으로 바꾸거나 검색 결과의 중복·판본을 자동 통합하지 않는다. TR26-0008처럼 보고서 번호로 명시됐지만 형식이 잘못된 값은 이름 검색으로 재해석하지 않는다.

새 SDK stdio services/scholarly-mcp/data/validation/20260910T230446363549Z-eccc-workflow.json은 completed=true다. natural proofs 이름 후보 20건, 같은 원 검색의 2건 추출, TR26-008r1의 메타데이터·초록·원 PDF와 revision=1을 확인했다. 기존 판본 선택 계약을 유지하며 이름 입력만 후보 경로로 추가했다. 공통 198개 검사가 통과했다.

없는 보고서 URL /report/1994/999/는 HTTP 200이었지만 제목과 본문은 404 page not found였다. 현재 코드는 제목의 404와 빈 판본 목록을 구별하는 처리가 이미 있어 이 부분은 수정하지 않았다. HTTP 상태만으로 기록 부재 여부를 판정하지 않는 기존 동작을 유지했다.

JSTOR의 실제 배포 코드에 있던 new-search 경로도 기관 프록시에서 Client Challenge와 capInput을 반환했다. 관측은 .credentials/scholarly-mcp/probes/20260910T225843Z-jstor-new-search.html이다. 그때 수신한 JSON의 path·resolutionTrace는 결과 목록이 아니므로 검색 성공으로 세지 않는다. 별도 원 검색 API를 찾았다고 주장하지 않는다.

전체 구현은 계속 진행하며 푸시하지 않는다. 다음 공개 자료원 점검은 Software Heritage다. 현재 코드는 SWHID의 qualifiers를 무시하고 content 바이트의 고유 해시를 대조하지 않는다. 공식 문서의 content·fragment 예와 실제 익명 API 응답을 대조해 이 부분을 이어서 구현한다. CLI나 MCP 연결 재시작은 수행하지 않는다.
