# do-math 전용 graphify의 범위와 수동 갱신 계약

## 사용자 결정

사용자는 방대한 do-math 스크립트와 문서의 연결·계약·절차를 파악하고 이후 진단·수리·운영에 활용할 AI용 구조도를 원했다. 분석 대상은 `.claude/skills/do-math/` 내부 파일로 한정하고, 외부 파일의 내용은 포함하지 않기로 했다. 이번 작업은 그래프와 구축·조회·갱신 체계 마련까지이며 실제 문제 진단과 수리는 포함하지 않았다.

기존 저장소 전체용 graphify를 전용 체계로 대체했다. Claude Code와 Codex는 `.claude/skills/graphify/`의 정본과 `.claude/graphify/do-math/`의 단일 상태를 공유한다. 조회는 에이전트가 필요하다고 판단할 때 수행하고, 갱신은 사용자가 명시적으로 호출했을 때만 수행한다. 조회 시 변경을 표시하되 그래프를 자동 갱신하지 않으며, 판단 근거는 현재 원문과 코드로 확인한다.

처음에는 일반 추출 에이전트를 시작했으나 사용자가 문서 의미 추출을 `codex exec`와 `gpt-6-sol`로 지정했다. 기존 추출 에이전트를 중단하고 이 실행 수단을 도구에 고정했다. 사용할 모델만 고르는 것으로는 실행 수단에 관한 사용자 결정을 보존할 수 없으므로, 실행 인자와 캐시에 모델과 실행 수단을 함께 기록하고 검증한다.

## 구현 중 확인한 경계

graphify 기본 `query` CLI는 조회 기록과 시각 표지를 쓴다. 명령 이름이 조회라는 사실만으로 읽기 전용 동작을 보장하지 않았다. 전용 도구는 쓰기가 없는 라이브러리 함수를 사용하며, 실제 조회·설명·경로·영향 범위 조회 전후 상태 파일의 해시가 같음을 검사했다.

초기 구조 추출은 약 5,200개 노드를 만들었지만 문서와 코드 사이 연결이 없었다. 내부 파일의 명시적 경로 참조와 문서 의미 추출을 결합했다. 유일한 파일명만으로 연결한 경우는 추론으로 표시한다. 노드 수가 크다는 사실은 사용자가 필요로 하는 종류의 관계가 포함됐다는 증거가 아니었다.

한 문서의 모델 응답은 원문의 “보충 조사는”을 “보충 조사자는”으로 바꿔 인용했다. 행 번호와 정확한 부분 문자열을 대조하는 검사가 이를 거절했고, 같은 모델·실행 경로의 재추출이 통과한 뒤 그래프에 포함했다. 인용 일치는 출처 추적의 검사이며 의미 해석 전체의 정확성이나 구현의 계약 준수 판정은 아니다.

## 산출물과 근거

최초 구축은 내부 228개 파일과 Markdown 22개를 다뤘고 6,155개 노드·21,178개 관계를 만들었다. 범위 제한, 변경 감지, 의미 추출 검증, 실패 시 기존 그래프 보존, 읽기 전용 조회, 파일 안의 함수를 호출하는 코드까지 영향 범위에 포함하는 동작을 검사하는 테스트 7개와 실제 조회를 확인했다. 스킬 사본 생성·드리프트 검사와 스킬 형식 검사도 통과했다.

추적할 진입점은 `.claude/skills/graphify/` 아래의 `SKILL.md`, `references/semantic.md`, `scripts/graph.py`, `scripts/semantic.py`, `scripts/test_graph.py`다. `.agents` 생성 사본에는 graphify 경로를 축자로 유지하는 규칙을 적용해 분석 대상이 사본으로 바뀌지 않게 했다.

생성 그래프·HTML·의미 추출 캐시·Codex 실행 기록·`validation/final-check.json`은 `.claude/graphify/do-math/`의 Git 제외 로컬 자료다. 정리하거나 다른 머신으로 옮길 때 사라질 수 있으며 이번 커밋·푸시에는 포함하지 않는다. 기존 범용 스킬과 훅 백업도 같은 로컬 영역에 보관했다. 재구축 절차와 검사 코드는 추적 파일에서 확인할 수 있다.
