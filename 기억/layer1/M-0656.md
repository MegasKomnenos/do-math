## 맥락

사용자는 주차 함수 단봉성 연구(`.skill-workspace/do-math/parking-unimodality-fresh-20261105-150803`, Git 제외 로컬 인스턴스)의 결과를 담은 개선 제안 문서를 "지시가 아니라 참고"로 주고 grilling으로 실제 할 일을 확정하게 했다. 제안 문서의 네 변경 가운데 Lean REPL(4)은 처음부터 제외했다.

인스턴스를 직접 읽어 확인한 사실은 다음과 같다. 기록 83개에 노드는 root, C(감소 쪽 로그오목성, C⇒root), D(임계 EGF 증분, root⇒D와 ¬D⇒¬root 둘 다 peer가 적음) 셋이었다. D는 formalizer 7개를 거쳐 formal_proved였으나 필요조건이라 root에 기여하지 못했다. 섹션은 전체 26·부분 29였고, 부분 섹션은 거의 모두 root 명제의 지표 구간 조각(봉우리 위치 m 기준 양쪽·가로지름)이어서 11월 5일 섹션 정의(노드가 함의하는 질문의 일부)에 정확히 해당했다. 같은 조각을 네 세션이 등록했고 어느 것이 해결됐는지 그래프에 없었다. 기록 18·76·80·54는 양 끝 구간을 큰 n 또는 모든 n에서 해결했고 42·43은 조각 결합 논리를 Lean으로까지 증명했지만, 어느 기록도 노드·관계를 제안하지 않았다. 주장 1115개 중 1111개 지지, concern 0.

계보에서 드러난 사실: 11월 5일 합의문(`.skill-workspace/do-math-node-guidance-20261105/agreement.md`, Git 제외)은 "나머지 ∧ 확립된 것 ⇒ 노드" 형태로 나머지 조각을 노드로 두는 환원을 기여로 정의했는데, 같은 날 섹션 커밋이 중간에 들어오면서 배포된 안내는 노드 자신의 질문의 일부를 섹션으로 보내고 노드는 다른 명제에만 열었다([[M-0643]]). 제안 문서의 변경 3은 새 생각이 아니라 합의문의 원형이었다.

grilling에서 확정한 사용자 결정: 규칙이 아닌 판단(record_check 게이트 없음, 두 형태를 모두 제시하고 peer가 고르며 review가 판정); 다음 새 인스턴스에 한 번에 적용(실행 중 인스턴스는 그대로); 평가는 탐색적(지표 장치 없음); 범위는 변경 1·2(a)·3, 2(b)·2(c)는 제외; peer와 review는 Opus 5.5, Opus 다음 Codex 대체(peer 추가분이 같은 계열에서 검토됨을 알고 수용); 형식화 게이트는 문서의 규칙(폐포 소속, 형제 전제 미해결이어도 보냄); 안내 원고를 파일로 먼저 보고 적용.

논리 결정의 경위: `settle()`은 적힌 방향으로만 전파했고 대우를 유도하지 않았다. 11월 4일 설계 기록 4.4절은 자동 추론 엔진을 배제했다. 나는 그 배제를 넓게 읽어 "peer가 대우 관계를 적도록 안내"를 제안했으나, 사용자는 "P⇒K이고 K가 거짓이면 P도 거짓 아닌가"로 되물었고, 이어 "불 논리를 그대로 적용하고 복잡한 자가 규칙을 만들지 말 것"을 정했다. 완전 판정(SAT)도 검토했다. 진리값에는 경로가 필요 없고 형식화 준비도 형식 사실만으로 함의를 재계산하면 되지만, concern·충돌 처리가 경로에 기대고 있었다. 사용자는 "peer가 제안하고 review가 지지한 주장은 finding이 철회할 때까지 모든 목적에서 참"이라는 단순 규칙을 택했고, 그러자 concern 차단·cleared_uses·possible_concerns가 모두 필요 없어져 절 단위 전파(unit propagation)로 충분해졌다. 경우 나누기(A⇒P, ¬A⇒P에서 P)는 유도하지 않으며 peer의 직접 해법으로 남긴다.

## 변경

- `runtime/knowledge.py`: 관계를 절로 읽어 어느 방향이든 하나만 미확정이면 유도한다. 순방향 proof ID는 기존 `<record>/<relation>`, 역방향은 `~<전제 위치>`를 붙인다. 질문된 주장에 덜 기대는 경로가 있으면 교체한다. 양쪽 결과가 유도된 노드는 contested로 두고 입력에서 제외한 뒤 안정될 때까지 반복하며, 대립 증거는 표시용으로 남긴다. 모순된 집합에서는 연결된 노드가 모두 contested가 된다(root⇒K, ¬K, Q⇒root, Q가 함께 받아들여지면 root·Q·K 전부). `sufficient_closure`는 root의 증명·반증에서 절을 거슬러 도달 가능한 부호 명제 집합이고, `root_path`가 frontier 표시 문구를 만든다. render는 노드마다 root 경로 표시, 관계 전제의 확립/미확립, 유도 경로, "rests on a questioned claim" 표지를 보이고 possible-dependency 줄을 없앴다.
- `runtime/runner.py`: populate와 dispatch가 폐포 소속인 결과에만 formalizer를 보내고 벗어난 작업은 취소한다. peer task에 생산자의 섹션(id·node·whole·statement)을 싣는다. available_nodes는 root 경로 노드를 앞에 둔다.
- `runtime/check.py`: finding의 `clears`·`cleared_uses`를 거부한다. `runtime/settings.py`: 기본 `roles`에 peer·review를 Opus 우선 Codex 대체로 둔다.
- 안내: common·peer·review·explore·record-format·review-output·evidence·SKILL·operations. 두 형태와 각각의 효과·비용, 어느 쪽도 기본값이 아니며 peer가 최선의 판단으로 고르고 이유를 적는다는 명시, review가 그 선택도 평가, 분할 관계의 기록 형식, frontier의 유도 규칙과 한계, root 경로 표시, concern은 주석일 뿐이고 finding만 지위를 바꿈, 역방향 proof ID, explore를 잇는 peer의 섹션 자유(사용자 요청으로 기존 모호점도 고침).
- 시험: concern 차단 의미를 담던 시험 셋을 새 의미로 다시 쓰고 cleared_uses 시험을 거부 시험으로 바꿨다. 대우·다중 전제 역방향·contested 격리·폐포와 표시·분할 커버리지·formalizer 게이트와 취소·모순 집합·peer task 섹션·기본 모델 시험을 더했다. ending·pipeline 시험은 대본 CLI가 Codex 스트림을 쓰므로 `roles={}`로 고정했다.

## 검증과 적용

안내는 `write-for-reader`의 독해 절차로 열두 번 읽혔다(Codex 독립 독해, 합의 파일 `.skill-workspace/do-math-enhancements-20261106/writing/brief.md`). 독해가 잡아낸 결함: "모든 귀결을 유도"와 경우 나누기 제외의 모순, 부호 조건 누락(반증된 전제는 아무것도 강제하지 않음), 부호 있는 명제에서 두 층위의 부정, 충분 경로의 "형제 전제 미해결" 조건, 열린 조각도 노드로 제안함, 역방향 proof ID 부재, "asks nothing of review"의 오독, "necessary condition"을 부모 기준으로 쓴 것, "never formalized"가 attempt의 Lean 작성 금지로 읽힘, 명시되지 않은 문턱 조각이 정확한 명제가 아니라고 한 과장, "the node"의 지시 대상. 5차부터 understanding은 매번 무거운 것 셋을 중심으로 재구성했고 남은 지적은 재독 기록이었다. 사용자가 12차로 종료를 정해 그 시점의 재독 지적은 이유를 적어 유지했다.

시험: 작업 사본에서 브로커 외 166개 중 165개 통과. 전체 파이프라인 시험과 브로커 모듈은 손대지 않은 정본에서도 같은 방식으로 실패했다(실행 중 연구 인스턴스가 세션 6개로 기계를 점유해 60초 기한을 넘김). 그 둘은 이번 변경에 대해 미검증으로 남기고 기계가 한가할 때 양쪽 사본에 다시 돌려야 한다. 설치 뒤 정본 트리의 검증 실행 결과는 커밋 시점에 별도 확인한다.

적용: 작업 사본을 정본에 복사한 뒤 사용자 승인으로 미러를 생성기로 재생성했다(`--check` exit 0, 144파일). 실행 중 인스턴스는 미러를 실행하므로, 사용자 지시로 실행기를 재기동했다(옛 PID 19124 종료 확인, 새 PID 1248, 세션 6개와 브로커 유지). 새 fold로 인스턴스 이벤트 107개를 재생해 상태가 바뀌지 않음(C 충분 경로, D 필요조건만)을 재기동 전에 확인했다. 설계 기록 `docs/do-math/rebuild-design.md` 12.3절(의심 증거에 기댄 상태 변경은 검토 판정을 기다림)은 이번 결정으로 대체됐으나 기록 문서라 고치지 않았다.

## 사용자 교정 신호

- ⓐ 거부된 기본값: 고려 사항을 "whether…, whether…" 목록으로 적은 계약 초안; peer가 대우 관계를 적도록 안내하는 해법; 경로 기반 concern 기계를 유지하는 전파안; 선택의 주체를 암시만 한 안내; 기존 문장의 모호점을 범위 밖으로 둔 판단.
- ⓑ 선호된 교정: 고려 사항은 열린 예시이고 배타적이면 안 됨; 불 논리를 그대로 적용하고 자가 규칙을 만들지 말 것; 지지된 주장은 finding이 철회할 때까지 참이라는 단순 규칙으로 기계를 걷어낼 것; "최선의 판단으로 골라야 한다"를 명시할 것; 독해자가 지적한 모호점은 범위와 무관하게 고칠 것.
- ⓒ 드러난 편향: 원리를 체크리스트·게이트로 바꾸고, 기존 기계를 보존하는 쪽으로 해법을 구성한다. 사용자는 더 단순한 의미론이 기계를 없앨 수 있는지를 먼저 본다([[M-0642]]의 "측정 가능한 목표를 직접 최적화하는 장치" 편향과 같은 축).
- ⓓ 교정 위치: do-math 안내를 쓸 때 고려 사항은 "for example"의 열린 예시로, 선택의 주체와 의무는 명시 문장으로 둔다. 사용자가 단순한 규칙을 제안하면 기계를 옹호하기 전에 그 규칙 아래서 무엇이 불필요해지는지부터 열거한다.
