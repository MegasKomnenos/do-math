[[M-0530]]까지 단순 점 표기161곳을 검증했지만 배열 인덱스와 모듈 상수31곳은 문법 밖이었다. 배열 항목28곳과 상수3곳을 추가했다. 필드 검사는 [] 또는 숫자 인덱스에서 items를 따라가며, 객체나 임의 키 맵을 배열 항목으로 취급하지 않는다. 인덱스는 항목의 필드 소유자를 가리키는 문서 표기이지 실행 시 배열 길이를 인증하는 단언이 아니다. 모듈 상수는 실제 모듈 속성으로 해소하며 필드 공간이나 함수 호출과 구별한다.

results[].output_files[].local_path는 저장 execution의 출력 파일에 존재하는 키가 아니다. _preserve_outputs는 path/artifact_ref/sha256/bytes를 만들고, _context가 입력을 복원하며 local_path를 붙인다. previous_output_files는 restore_continuation의 별도 계보를 따른다. 운영 점검의 복원은 성공 시 local_path, 실패 시 restoration_error를 가진다. 일반 출력과 진단용 복원 결과를 합집합으로 승인하지 않고 다른 공간으로 두었다.

sources도 일반 연구 입력과 고정 질문 조사 입력이 다르다. 일반 sources[].local_path는 원자료의 입력 복원, 보충 조사 sources[].ref는 _materialize_research_sources가 실제 읽는 고정 자료의 참조다. 각 문장에 소유자를 붙였다. checkpoint_files는 runtime.checkpoints map의 evidence_files와 운영 입력의 추가 대입을 연결한다. 처음에 이를 RECORDS.checkpoints에서 찾은 검사 지원 코드가10오류를 냈고 실제 runtime map의 item schema로 수정했다. 이는 제품 결함으로 기록하지 않는다.

문서 manifest의 documents[].artifact_ref는 처음 documents 배열을 만드는 목록 내포 뒤, 해당 배열을 순회하는 루프에서 추가된다. 같은 row 변수명을 쓰는 다른 루프에서 키를 빌리지 않도록 정확한 iterator를 선택한다. 지원 코드는 명시한 append 인자·목록 내포의 항목·고정 조건의 객체 spread도 읽으며, 모르는 동적 객체를 자동 승인하지 않는다. pending_findings·과제 평가/처분·준비 조건/계약 검사·개정 처리·수입 질문은 각자의 현재 스키마 또는 생산자에 직접 연결했다.

현행 모집단은84공간의 필드189곳, 함수5곳, 상수3곳, 진단7곳이다. 파일명33곳은 별도 분류이며 존재 인증이 아니다. 구조59개가51.7초에 통과했고 실행 중 변경은 없다. 최초 실패와 최종 원본 보고를 검증/2026-10-05-문서-배열-상수에 바이트 그대로 보존했다. 배열/상수31곳의 위치와 소유자 검수는 단계-전환표의 document_array_and_constant_bindings가 가리킨다. 제품 실행 동작은 바꾸지 않았다.

다음 단독 이름 검수의 사전 탐색은 현재24문서에서 ASCII 식별자1029종/3537참조를 얻었다. Python 코드의 이름·속성·문자열 어휘에서 못 찾은 것은17종이다. 이 탐색은 keyword 인자 이름과 PowerShell 등 다른 언어를 포함하지 않았으므로 checkpoint_schema나 ProcessId를 없는 기능으로 판정하면 안 된다. F/U 같은 문서의 수학적 기호, needs_revision처럼 명시적으로 부정하는 상태, import_unit/question_detail 같은 항목의 단수명도 구별해야 한다. 이 목록을 기존 작업판에 남겼으며 lexical 존재를 소유자 검증으로 바꾸지 않았다. 단독 이름·문장 내 조합 표기·읽기 도구의 실제 출력 한도와 전체 최종 관문은 계속 미해소다.
