## 맥락

사용자가 외부 지적 하나를 가져와 세 문서(`docs/do-math/통합-설계.md`, `CONTEXT.md`, `docs/wayfinder/pvsnp-재설계/컨텍스트.md`)만 읽고 검토하게 했다. 지적의 요지는 최초 수입이 의미 단위 분해·소유자 배정·의미 보존 판정이라는 AI 판단을 요구하는데 역할표에 입력 수입자와 독립 수입 검토자가 없고, 승인된 외부 변화와 사용자 결정 기록 경로도 같은 공백이라는 것이었다. 대조 결과 세 주장이 모두 문구로 성립했고, 문서 안에서 지적이 놓친 근거 넷을 더 찾았다. 30.3절이 초기화·외부 변화의 씨앗 제안 주체를 이름 없이 「주체」로 적고 있었고, 24.2절의 `do-math init` 설명이 수입 판단까지 도구가 하는 것처럼 적혀 7행·24.1절과 어긋났으며, 5.1절의 `initializing` 상태와 7.7절의 `initialization` 생성 근거 종류가 각각 전이·편입 어디에서도 쓰이지 않았고, 초기화 씨앗에는 착수 명세 검토를 요구하면서 그 씨앗의 근거가 되는 헌장·정책은 검토 없이 활성화되는 비대칭이 있었다.

`/grill-me`로 결정을 하나씩 닫았다. 사용자 확정은 다섯이다. 새 AI 역할 「입력 수입자」가 최초 수입과 승인된 외부 변화를 모두 저작한다(선택지 A). 헌장·정책·설정·맥락 전건을 연구 책임자가 읽고 결정 기록으로 승인해야 활성화된다(「전건」). 「수입 검토자」는 단일 독립 세션으로 전건을 읽고 의미 단위마다 판정하며 두 역할 모두 `gpt-5.6-sol max`다. 초기화는 골격만 가진 `initializing` 인스턴스를 실제로 만들어 평시의 request·output 장치로 세션을 파견하고, 새 공용 변경 종류 `initialization`으로 편입하며, 활성화 관문 하나로 `active`가 된다. 결정 기록 경로는 메인 세션을 유일한 대화 주체로 두되 결정 질문은 미결정을 만난 역할이 파일로 쓰고 그 기록의 검토자가 함께 보며 메인 세션은 문구 그대로 제시하고 응답값을 다시 보여 주어 확인받아 봉인한다.

반영은 세 문서를 Edit 도구로 직접 고쳤다. 통합-설계는 0.1·0.2·1.3·2.1·4.3·5.1~5.6·6.1~6.3·6.10·7.4·7.7·9.1·9.3·11.2·16.2·16.3·17.1·18.0·18.2.1(신설)·21.1·21.2·24.2·26.1~26.7·27·29·30.3절을 바꿨다. CONTEXT.md에는 입력 수입자, 수입 검토자, 결정 질문, 사용자 결정 기록, 결정 대기 씨앗 다섯 용어를 더하고 프로젝트 입력·연구 인스턴스·연구 헌장·정책·맥락·설정·분할 종결을 손봤다. 컨텍스트 문서는 2절 원리 둘, 3절 승인 문장, 6절 모델 배정을 고쳤다. 사용자가 「기계적으로 하지 말고 평범한 도구로 직접 적용하며 충분한지 스스로 검토하라」고 지시해 편집 서브에이전트를 쓰지 않았다.

독립 검토는 `gp-fable-high` 한 기에 맡겼다. 입력은 세 문서, `941eba4` 대비 diff, 그리고 사용자·어시스턴트 발화만 옮긴 대화 로그(`임시/수입-경로_설계반영_2026-09-02/대화로그.md`)다. 검토 결과는 내가 타당성을 다시 읽고 직접 적용하기로 했고, 그 적용은 후속 커밋이다. 이 커밋은 검토 완료 전에 만든다. commit-harness의 검증-커밋 선후 원칙과 어긋나지만 사용자가 「직접 고치고 커밋도 해」를 검토 지시보다 앞에 명시했고, 미커밋 대기의 워킹트리 소실 위험을 줄이는 쪽을 택했다.

## 터득한 것

- 작업자가 사용자 결정을 필요로 하는 경우의 경로를 처음에는 운영 처분 심사와 전례 관문으로 보내자고 제안했다. 사용자가 「정확히 어떤 경로인지」를 되묻자 문서를 다시 읽었고, 7.1절의 「외부 대기가 필요한 일은 별도 작업으로 나눈다」와 7.3절의 `decision_value_is` 연산자가 이미 그 경우를 덮고 있음을 확인해 분할 종결과 결정 대기 씨앗으로 바꿨다. 거부된 기본값은 새 관문 신설이고 선호된 교정은 기존 규칙·연산자의 재사용이다. 드러난 편향은 경로를 설계할 때 문서의 기존 연산자·경계 규칙을 먼저 훑지 않고 새 통로를 그리는 것이다. 막을 자리는 설계 제안 전에 해당 절차의 연산자 표(7.3절·14.2절)와 경계 규칙(7.1절)을 grep으로 대조하는 습관이다.
- 결정 질문을 「파일 하나이며 6.10절이 이미 전제하는 질문·선택지 전문 그 자체」로 정의하고 P vs NP의 프리프린트 예시로 보여 준 뒤에야 사용자가 경로를 받아들였다. 추상 역할 서술만으로는 「누가 무엇을 어디에 만드는가」가 전달되지 않는다. 산출물의 실물(필드와 예시)을 먼저 보이는 것이 설계 대화에서 합의를 빠르게 했다.
- 결정 질문 파일이 자기가 낳을 결정 기록의 `DC-` ID를 미리 배정받게 하면, 씨앗 발생 조건이 아직 없는 결정 기록을 `decision_value_is`로 가리킬 수 있고 7.5절이 「아직 생성되지 않은 입력은 정상 미충족」으로 이미 처리한다. 새 연산자나 새 기록 종류 없이 작업자 요청 경로가 닫혔다.
- 스키마 판본은 필드가 바뀐 것만 올렸다(`instance/5`, `import/2`, `decision/2`, `integration/3`, `task-start-review/3`, `operational-review/2`)고 새 스키마 둘(`import-review/1`, `decision-question/1`)을 29절에 더했다. 결정 기록 봉인은 새 도구 대신 `do-math record`에 얹었고, `do-math init`은 `create`·`check`·`activate` 하위 명령으로 나눴다. 이들은 사용자가 위임한 세부다.

## 작업 너머 시사점

- 승인된 외부 변화로 헌장·정책·설정·맥락이 바뀔 때도 같은 사용자 승인을 요구하는 것은 사용자의 명시 확정이 아니라 이의 없이 유지한 가정이다. 후속 검토에서 사용자가 좁힐 수 있다.
- M-0100이 남긴 사용자 결정(복원 인스턴스의 초기 입력 원천)은 이번에도 열려 있다. 5.2절이 `initializing` 골격을 두게 되면서 복원 인스턴스도 같은 국면을 거칠지가 그 결정과 얽힌다.
- 지적한 쪽에 보낼 회신문은 만들지 않았다. 필요하면 검토보고와 이 노드가 원자료다.
- dream에서 묶을 후보: 설계 대화에서 「기존 장치의 재사용」이 새 장치 제안보다 늦게 떠오르는 패턴이 이번 세션에서 한 번 더 나타났다. M-0100의 「새 저장 분류보다 기존 기록에 ID·해시를 얹는 길이 창작이 적었다」와 같은 계열이다.
