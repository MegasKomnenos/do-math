title: 반복된 실제 판정 근거 변경 뒤의 진단 발동과 재귀 억제를 검증함

[[M-0509]] 뒤 기존 currentness 흐름 검사를 두 번째 실제 충돌까지 연결했다. 원래 Sim 단위는 refresh.attempt=1을 직접 구성해 _refresh_changed_decision을 불렀고 큐/대기 결과를 확인했다. B93 흐름은 실제 역할 호출 중 입력 근거가 바뀌어 첫 갱신을 만들고, 그 갱신이 실행될 때 근거가 다시 바뀌는 과정을 거친다. 제품 함수의 반환을 패치하거나 changes 목록을 주입하지 않는다.

연구 준비에서는 실제 source 파일의 내용을 호출마다 다른 바이트로 쓰고 공개 source control을 owner가 적용할 때까지 기다린다. 최초 보존 산출·원문 참조의 currentness 반려·repair 예산과 독립인 갱신1회·부분 파일 보존이라는 기존 단언을 유지했다. 두 번째 준비 호출도 다른 source 판본으로 바뀌면 waiting_actions는 두 번째 실행을 가리키고 failure_kind=currentness_changed다. 뒤 실제 운영 검토가 정확히 그 실행을1회 진단하여 수락하고, 추가 두 순회에서 운영 호출이 늘지 않는다. 원자료 변경 hook도 정확히2회였음을 확인한다.

운영 검토는 중단된 준비 실행의 실제 보존 체크포인트를 대상으로 한다. 첫 입력이 허용한 checkpoint 참조를 같은 바이트의 다른 보존 경로로 교체하고, 갱신된 두 번째 입력의 참조를 다시 원래 보존 경로로 교체한다. 각 응답은 해당 입력이 허용했던 참조를 인용하므로 단순한 잘못된 evidence가 아닌 실제 currentness 변경이다. 두 번째 검토는 refresh.attempt=1과 currentness_changed를 기록하고 next_owner=operations로 대기한다. 추가 두 순회에 운영 검토 큐/호출이 생기지 않으며 실제 worker 실행 ID와 두 검토 실행을 대조한다. 최초 중단된 준비는 ModelDouble.calls에 성공 응답을 남기지 않으므로 그 호출을 포함한 전체 모델 수와 worker 수를 거짓으로 같다고 단언하지 않는다.

직접2개가28.1초에 통과했다. 구조4·현재성Sim16·관련flows5, 합계25개가63.1초에 통과했고 실행 중 소스 변경은 없다. 소스가 같을 때의 멱등성과 이미 끝난 과제 이력 보존, 판정 근거 변경과 다른 산출 오류가 함께 있을 때 producer repair로 분류하는 기존 음성 검사도 포함했다. 추적 원보고는 검증/2026-10-05-반복-판정-충돌/이며 최종 report.json SHA256은 da0a1206e533792ef1911528c2850ef15183e105097335672aec009f7c3570a7다. 제품 코드는 변경하지 않았고 새 제품 결함을 선언하지 않았다.

이 결과는 두 실제 역할 경로의 반복 충돌 검증이다. 다른 역할별 충돌 입력의 전건 검증이나 계획 발동 전체로 확대하지 않는다. 운영 발동에 대한 B90~B93의 닫힌 범위를 작업판에 반영했으며 다음은 기존 발동 지점 목록의 계획 원천을 실제 사건·판단 대상·호출0/1에 연결하는 작업이다. 최종 일반/T3/변이/실환경/문서 관문은 별도 남김이다.
