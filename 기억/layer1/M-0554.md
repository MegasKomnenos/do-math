phase 004 manager는 mirror-corpus의 partial을 유지했다. 기존 verbatim에 corpus 전체를 넣어 두 Claude help의 원문 치환은 고쳤고, 생성기 22개와 정본·미러 각각 14개 재생이 통과했다. 종료 2624파일·변경 9개·양쪽 공식 Python 864개와 44개 녹화 파일을 원보고 및 현재 바이트로 대조했다. 이 범위의 성공을 Codex schema 수락이나 G7/G8 전체 성공으로 확대하지 않았다.

남은 두 manifest의 Git clean 변환은 하위 corpus/.gitattributes의 명시적 text 예외에서 생겼다. 이전 manager는 상위 속성만 쓰기 범위에 넣고 정본 corpus를 읽기 전용으로 지정했다. 작업자는 허용된 상위 규칙으로 하위 예외를 덮을 수 없다는 실제 결과를 남기고 원상 복원한 뒤 partial로 반환했다. 이번 005 배정은 실제 하위 정본과 생성 사본 두 파일만 허용한다. 범위를 넓히는 이유는 새 요구가 아니라 기존 원바이트 의무를 수행할 위치가 배정에서 빠졌기 때문이다. 기존 검사 22개/양쪽 14개는 입력·코드가 불변이면 재사용하고, 새 검증은 실제 Git 필터의 전건 보존으로 한정했다.

[[M-0553]]에 기록한 manifest·Lean·scheduler 세 파일의 clean 관찰은 후속 실험에서 조건이 더 구체화됐다. Git 2.50.0.windows.2에서 Lean/scheduler는 역슬래시 절대 경로일 때 변환되지만 슬래시 상대·절대 경로에서는 보존된다. manager가 동일 argv 9개를 직접 재확인했다. manifest는 모든 표기에서 변환된다. 앞선 기록에는 정확한 argv가 없으므로 당시 사용 경로를 단정하지 않고 현재 C12에 그 한계를 남겼다. 원보고를 고치거나 정상 녹화를 재작성하지 않았다. 파일 바이트뿐 아니라 경로 인자와 cwd도 이런 도구 관찰의 재현 조건이다.

관리 커밋에는 검수·공용 문서·새 배정·원보고와 실행 출력을 담고, 관련 실패 교정 전인 제품은 작업트리에 둔다. phase 003~004 변경의 합집합 68개 파일은 pending-product-working-tree.zip과 product-snapshot.json에 현재 바이트로 보존한다. 실패 상태의 증거이며 자동 복원 지시는 아니다. 다음 순서는 작은 Git 속성 수리 뒤 Codex 전달/수신 경계 수리이고, 나머지 문서·의미·실제 연쇄·전체 관문·최종 review는 유지했다.

추적 진입점은 docs/do-math/continuous-development-2026-10-13/phases/004/manager.json과 manager-evidence/review.md, verification.json, preservation.json이다. 선별된 task evidence와 위 archive는 이 커밋에 보존한다. 명령별 중복 source-before/source-after, 서비스 세션 logs/runtime, 임시 .before와 pathspec은 로컬 보관이며 정리로 사라질 수 있다. 최초·최종 소스 목록과 검수 결과는 추적 자료로 남긴다. 기존 무관 dirty/untracked와 engine은 포함하지 않는다.
