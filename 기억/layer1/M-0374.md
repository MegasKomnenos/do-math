## 맥락

[[M-0373]]으로 1c를 닫은 뒤, 사용자가 압축 이후의 재개 전에 커밋 `25bff5d`의 설계·조사 문서와 합의가 이루어진 원 대화를 다시 읽어 목적을 세밀하게 복구하고, 지금까지의 작업을 검토한 뒤 이어가라고 지시했다. 1c 착수 때([[M-0365]])와 같은 종류의 지시다. 진행 기록은 `docs/do-math/시험-재편-2026-09-29/진행.md`의 1d 절에 있다.

## 터득한 것

**재독이 드러낸 것은 1c 후반의 범위 팽창이다.** 원 대화에서 사용자가 틀에 건 조건은 "틀을 위한 틀이 아니라 목적과 실익을 구현하는 수단"과 "개발 속도를 과하게 늦추지 않는 비용"이었다. 설계 9.1의 1c 행은 해석 함수의 1층 이동, `_call_steps` 절단, 층 표였다. 1c 다섯째 단위는 이를 넘어 모든 3층 모듈의 판정을 떼었다(A16 규칙 2). 근거는 실재하지만 실익은 결함을 잡는 시험이 아니라 시험이 설 구조의 순도였고, 착수 뒤 15시간이 지나도 결함 범주를 잡는 새 시험은 없었다. 이미 한 기계적 이동은 되돌리지 않고, 1d의 모든 작업을 "`Sim` 위의 첫 의무 시험을 가능하게 하는 데 필요한가"로 거르기로 했다. 이 기준으로 이월 항목 가운데 `scheduled_operator.recovery`의 Job 포트는 1e로 미뤘다.

**A17의 세 관찰은 포트 하나로 정했다(A18).** Lean 탐색, 도구 사슬 식별의 현재 관찰, 공급자 CLI 식별은 모두 호스트라는 바깥 자원을 읽는다. 포트 부류에 넣으면 양쪽 계약 시험과 완비 검사가 대역과 실제의 어긋남을 막는다. 실제 구현 `LocalHost`는 병렬 실행처럼 3층에 두었다. 관찰 코드가 3층 모듈(`formal`, 공급자 어댑터)에 있고, 경계 어댑터로 옮기려면 Lake 프로젝트 식별 기구까지 옮겨야 하기 때문이다. `LocalHost`가 관찰 코드를 모듈 속성으로 부르므로 옛 시험의 `formal.*` 패치는 그대로 닿는다. 이행 기본값은 둘 수 없었다(2층이 3층 구현을 import할 수 없음). 그래서 포트 없이 부르는 옛 시험에 `host=LocalHost()`를 넘겼다. 조사 시안이 1층으로 둔 `execution_profiles`는 2층 도메인 모듈의 이름을 쓰므로 2층으로 고쳐 선언했다.

**새 인자를 받게 된 함수의 호출 검색은 그 인자를 받게 된 함수 전체를 대상으로 한다.** 옛 시험에서 포트가 필요한 직접 호출을 찾을 때 신뢰 검사 두 함수만 정규식으로 찾았다. 같은 인자를 새로 받은 `activation_requirements`와 `_capability_batch_requirements`를 빠뜨렸고, 스냅숏 묶음에서 한 시험이 `None` 포트로 실패했다. [[M-0365]]의 "속성 사용 검색은 모집단 전체"와 같은 부류다. 검색 대상은 "고친 함수 목록"이어야 하고 "먼저 떠오른 함수"가 아니다.

**`git stash create`는 색인이 아니라 작업 트리를 담는다.** 첫 스냅숏은 `git add -A` 직후라 색인과 같았다. 고친 시험 두 개만 색인에 더해 다시 만들 때는 다음 단위의 진행 중 편집이 추적 파일에 있었고, `stash create`가 그것까지 담았다. 그 스냅숏을 버리고 `git write-tree`와 `git commit-tree`로 색인만의 커밋을 만들어 검증했다. 색인과 작업 트리가 다를 때 검증 스냅숏은 색인에서 만든다.

**동시 시험 실행 상한을 다시 어겼다.** 세 묶음이 도는 동안 호출 포트 시험을 세 번 짧게 돌렸다. [[M-0372]]에 이은 재발이다. 짧은 계약 시험 하나를 "실행"으로 세지 않은 판단이 원인이다. 결과에는 영향이 없었으나, 묶음이 도는 동안에는 코드와 문서만 쓰고 시험은 돌리지 않는다.

**다음 단위의 재현을 먼저 확보했다.** 협조적 호출 대역을 쓰기 전에, 영수증을 기다리며 소유자 차례를 넘기려는 계산이 기존 결정적 대역에서 소유자 스레드 안에 갇히는 것을 제한 시간 초과로 관찰했다(1c의 교착 재현). 구현과 `Sim`·모델 대역은 다음 커밋에 들어간다.

## 작업 너머 시사점

- 압축 요약에서 재개할 때마다 원 대화 재독이 범위 팽창을 잡았다([[M-0365]]는 대리 지표 추종, 이번은 설계 행을 넘는 구조 정리). 긴 구조 작업에서는 하위 단계의 완료 조건 문언뿐 아니라 "이 작업이 사용자의 원 목적(결함 범주를 잡는 시험)에 몇 걸음 떨어져 있는가"를 단위마다 적는 편이 팽창을 일찍 드러낸다. dream에서 묶을 후보: [[M-0365]], 이 노드.
- 색인과 작업 트리가 다른 상태에서의 스냅숏 검증 절차(`write-tree`·`commit-tree`)는 commit-harness나 L-0016의 병렬 구현 항목에 묶을 후보다.
