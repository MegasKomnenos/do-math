## 맥락과 완료 범위

사용자는 [[M-0421]] 뒤 “계속 끝까지 진행해”라고 했다. 목표를 마지막73개 이행에 한정하지 않고 설계의1e·1f 마감,2단계 수리·설계 변경,3단계 실제 경계까지 유지했다. 파견은 codex exec이며 에이전트 수와 기계 전체 시험 상한3개를 구분했다. 이 커밋은 마지막 옛 시험·공통 하네스·포트 수축의 통합 단위다. 전체1e/1f나 재편 완료는 아니다.

추적되는 근거는 설계·진행·migration 처분 장부·현재 코드다. .skill-workspace/test-restructure-2026-09-29/finish/의 독립 감사·패치·실행 JSON과 .codex/writing-flow/의 독해 기록은 Git 제외 로컬 자료이며 정리로 사라질 수 있다. 가지별 통과나 개별 최신 결과 합집합으로 주 작업 트리의 단일 판본 통과를 대신하지 않았다.

## 실제 경로에서도 소실될 수 있는 관찰

마지막73개를 foundation9·operator30·live19·storage15로 나누어 옮겼다. 기준1932개 전부 처분했고 옛 루트 시험이 비었다. 독립 감사는 값·거부 사유·호출수·시점을 원문과 전수 대조했다. 소유 스레드와 게시 뒤 정지 판정, 종료 전에 체크포인트 요청이 도달했는지, 정상 stdout/nonzero exit의 분리, 전체 ZipFile 호출수, 유효 profile_ref에 의한 취소 사유를 복원했다. 직접 ModelRunner/wake/생성자 무호출과 read_status/scheduler의 전체 반환·snapshot 인자도 보존했다. CLI spawn 수나 하류 scheduler 효과 수는 원 함수 진입 수를 대신하지 못한다.

포트 수축의 첫 구현은 Calls 뒤에서 실제 계산 함수를 다른 callable로 바꾸는 ResultCalls를 두었다. 실제 runner/verifier 객체가 있어도 그 호출을 건너뛰면 같은 사각이 생긴다. 해당 에이전트만 중단하고 파일을 보존한 뒤 실제 runner/verifier/worker를 실행하고 external Ports/spawn에서만 입력·실패를 주도록 교정했다. 실제 생산자가 못 만드는 결과는2층 수신 입력 시험으로 분리했다. 실제 계산 배선은 flows.test_scheduling_machine_calls와 flows.test_lifecycle_engine_trust가 계속 검사한다.

## 하네스 입력과 새 소유자의 세계

입력값을 만드는 도우미와 응답기에 있던 입력 단언을 support 정본으로 옮겼다. 공통 포트 계약은 fake/real 양쪽이 같은 mixin을 사용한다. 마지막 소비자가 사라진 뒤 옛 fixture9개를 삭제했다. 템플릿 캐시 키와 빌더 인자는 명시 JSON 값과 기본값을 함께 반영한다. 빌드한 원본을 복사하기 전 미종결 execution·held 예약이 없어야 하고 모든 Job 객체는 done·closed이며 Calls에는 미수집 future·남은 turn이 없어야 한다. 활성화의 verifier/worker 무호출 관찰은 configure·trust·decision·run 전체를 감싼다. Lean 대역은 정확한 소스/선언 목록과 합성 사실을 명시하고 임의 proof body를 성공시키던 기본을 없앴다.

재시작에는 새 엔진만 만드는 것으로 부족했다. 실제 file hash·artifact bytes·기본 계약 등 프로세스 수명 캐시를 명시 폐기한다. Sim이 owner PID만 바꾸어 이전 owner를 계속 unknown으로 답하는 것도 확인했다. FakeJobs는 알려진 종료 identity만 기록하고 해당 owner의 Job handle을 닫는다. 미시작 Future와 이전 Calls 연결을 버리고 새 Calls를 조립한다. 외부 Git 객체·clock·Jobs 세계·모델 응답 이력은 보존한다. 실제 새 엔진의 회수·저장·예약 반환과 unknown foreign owner를 함께 확인했다.

운영자 공유 Job worker 전환은 원 FileNotFoundError를 RuntimeError로 바꿨다. 이는 이행이 만든 차이이므로 다음 수리 단계에 미루지 않았다. 두 운영자 호출은 preserve_os_error 옵션을 선택한다. worker가 전달한 errno·strerror·파일명·winerror 등의 정보를 검사해 원 OSError 형과 문구를 복원한다. Windows에서는 winerror/filename2에 None을 명시 대입하는 것만으로 문구가 바뀐다. 실제 원 subprocess 오류와 두 소비자, None·두 파일명 회귀를 보존했다. KD-1600은 닫고 예상 실패 표시를 제거했다. 기존 원장 결함14개와 이후 추가한KD-1900은 열린 상태15개로 남으며 정본은 tests/known_defects.json이다.

## 정적 연결과 실행 비용의 확인 깊이

의존성 호출2037곳에서 필수 kwargs의 정적 누락이0이어도 전체 T2는37건이 실패했다. 인자는 있지만 시각이 None인 경로, self.api 동적 호출, 옛 모듈명으로 관찰하는 검사가 이름 대조를 지났다. planning.exhaustion_state가 받은 now와 snapshot 조회의 clock을 하위 readiness에 전달하고 시험은 같은 engine/fixture 시각을 사용하게 맞췄다. 권한·현재성·저장 검사와 원래 KD 실패 이유를 완화하지 않았다.

일반 실패가 없어진 뒤에도 T2는301~315초로 예산300초를 넘었다. 긴 시나리오 세 개를 입력·단언 그대로 flows에 배치했다. 첫째는 공개 활성화 전체, 둘째는 실행 중과 종료 뒤 관찰의 두 모드, 셋째는 공개 close 또는 실제 목표 완료 각각의 뒤에 설치를 바꾸는 검사다. 전체 T3에서 세 시나리오를 계속 실행한다. 비용 대조는 LPT 기록이 본문 시간만 합쳐 준비·종료를 놓침을 드러냈다. 작업자 실제249/315/287초와 본문176/198/211초의 차이에는 fixture 외에도 발견·계측 전환·저장이 섞여 있다. 실제 module suite 시작부터 teardown 완료까지 module_total_seconds를 측정·보고·캐시에 연결하고 T2/T3 자료를 분리했다. 가상시간 회귀는 본문20초와 총110초를 구분한다. 새 전체 비용을 실행기로 채운 뒤 최종 T2는1970 passed/14 expected_failure/기존skip1,286.1초이며 일반 오류·실패는0개였고 실행 전후 Python 소스 hash 변경은 없었으며 예산300초 이내였다.

새 전체 T3 첫 시도는 빈 메모리 하한3072MB에서 중단됐고 완주로 세지 않았다. 다른 조사들이 끝난 뒤 단독 측정은 빈 메모리 최저3702MB로 완주했으나 당시2400초를 넘는2927.4초였다. 계측2159와 별도격리1의 총2160중2137 pass/3 error/1 failed/18 expected/기존skip1이다. 일반 네 건 중 흐름 시험 하나는 하위 판정에 시각을 넘기지 않았고, 다른 세 건은 중첩 관찰자가 sys.monitoring ID 자리를 확보하지 못했다. 같은 엔진의 시각을 전달하고 관찰 자리 배분을 교정했다. sys.monitoring이 제공하는 ID0~5중 비어있던 ID5자리까지 한 reserve_tool 정본에서 쓰며 다른 도구의 자리를 덮지 않는다. 관문이 판정한121모듈중97개 모듈에 빈틈이 있었다. 누락 분기는2228개, 누락 행은2709개로 관문은 실패했다. closing_eligible=True는 재사용 없는 온전한 측정 형식이며 시험·관문 통과가 아니다.

독립 비용 분석의 module합7569.4초는 완전히3등분해도2523.1초다. 균형만으로2400달성을 보장한다는 주장은 기각했다. A29의 실측 보정과 U8/U9에 따라 full 전용3300초(A30)를 정했다. 현재 실측 위372.6초의 운영 여유이며 통계구간·미작성 의무 비용이 아니다. T2의300초와 일상T3의720초, 표본·단언·관문·변이·재사용 없는 최종 판정은 유지한다. 과거 초과·실패를 소급 성공으로 바꾸지 않는다. 새 관찰 정본 import가T3 측정 캐시 저장소의 재사용을 무효화하므로 교정한 판본의 새 전체 측정을 다시 제공해야 한다.
