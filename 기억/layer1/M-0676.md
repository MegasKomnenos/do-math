## 맥락

실행 중인 주차 함수 인스턴스(`.skill-workspace/do-math/parking-unimodality-fresh-20261105-150803`)를 하루 동안 운영하면서 사용자가 요청한 변경 가운데, 임시방편이 아닌 셋을 이 커밋에 담았다. 셋 모두 생성 사본으로 실행 중 인스턴스에 이미 배포되어 있다.

1. **explore 요청 시점.** 이전에는 attempt가 절을 처음 등록할 때 횟수를 세어 `explore_every`마다 explore를 요청했다(`observe_attempt_selections`). 이제 `dispatch()`가 attempt를 파견할 때 센다(상태 키 `attempt_launches`; 없으면 0부터).
2. **통합 파견 간격.** `attempt_launch_interval`·`last_attempt_launch`·`attempt_launch_due`를 `launch_interval`·`last_launch`·`launch_due`로 바꾸고, explore도 같은 간격을 기다린다. 대기 중인 explore·attempt 작업(`dispatch_pending`)과 새로 만드는 작업(`schedule`) 모두에 적용한다. 1과 함께 작동하면 빈 question이 있는 동안 attempt와 explore가 180초 간격으로 번갈아 뜨므로, attempt는 약 6분에 하나 뜬다. 사용자 요청의 직접적인 결과이고 결함이 아니다.
3. **세션 프로세스 정리.** 세션 호스트(`session_host`)가 `GO` 직후 자신을 Windows Job Object(`KILL_ON_JOB_CLOSE | BREAKAWAY_OK`)에 넣는다. 세션이 `nohup`이나 백그라운드로 띄운 계산도 묶음에 남아, 호스트가 끝나면 함께 끝나고 턴 사이에는 유지된다. 결과는 세션 폴더의 `process-job.json`에 남는다. Lean 브로커 클라이언트는 브로커를 묶음 밖(`popen_options(breakaway=True)`)으로 띄우고, 거부되면 예전처럼 띄운다. Linux는 정리하지 않는다(문서에 명시).

**이 커밋에 넣지 않은 것.** 사용자가 "임시방편, 나중에 제대로 다시 만든다"고 한 형식화 보류(`Runner.formalization_paused`와 호출 두 곳, 표지 파일 `control/pause-formalization`)는 작업 트리의 `runner.py`(정본과 사본)에만 남아 있고 커밋하지 않았다. 실행 중인 러너와 새 세션 호스트가 사본의 `runner.py`를 읽으므로 작업 트리에서는 지우지 않고, 보류 코드를 뺀 판을 인덱스에만 올렸다. 그래서 커밋 뒤 작업 트리에는 보류 코드가 미커밋 변경으로 남는다. 이후 `runner.py`를 커밋할 때는 이 부분을 다시 빼거나, 보류를 정식 기능으로 만든 뒤 함께 정리해야 한다.

같은 날 인스턴스에 한 운영 조치(저장소 밖)도 함께 적어 둔다. 브로커 메모리 예산 8192→12288MB, 스레드 예산 4→8→4, `max_sessions` 8→12(인스턴스 `settings.json`), 사용자 입력 두 편(형식화 보류 공지, 계산 비중 결정), 끝난 세션이 남긴 계산과 배포용 사본 17GB 정리.

## 터득한 것

- **4코어에서 Lean 스레드 예산을 8로 올리자 처리량이 줄었다.** 동시 컴파일은 2→4건으로 늘었지만 중앙 소요 시간이 50–98초에서 약 284초로 늘어, 처리량이 분당 0.88→0.64건이 되었다. 세션 CLI와 계산이 같은 코어를 쓰기 때문이다. 앞서 "1.5–2배 빨라질 것"이라고 한 추정은 측정으로 틀렸음이 드러났고 4로 되돌렸다. 메모리 예산은 병목이 아니었다(2건 예약 합 약 5.1GB).
- **Git의 `timeout`은 Windows용 Python을 끝내지 못했다.** 끝난 peer가 `timeout 3000`으로 띄운 계산이 기한을 넘겨서도 살아 있었다. 세션이 붙이는 시간 제한은 정리 장치가 될 수 없다는 근거이며, 3번 변경의 직접적인 동기다.
- **프로세스 트리로 세션을 추적하면 PID 재사용에 속는다.** 상태에 남은 오래전 세션의 host·CLI PID가 지금의 다른 프로세스와 같아져, 활성 세션의 프로세스가 끝난 세션의 것으로 분류되었다. 명령줄의 세션 ID를 우선하고, 트리 연결은 활성 세션에만 쓰는 방식으로 바로잡았다. 분리된 계산은 부모가 사라져 트리에서도 떨어진다(이것도 3번의 동기).
- **실행 중인 세션에 전할 통로의 실제 성질.** inbox 파일은 세션이 `commands.updates`를 실행할 때만 읽히고, peer는 역할 지침상 그 계기가 거의 없다. 이 세션의 `SendMessage`는 받는 쪽이 권한 모드가 달라(`--dangerously-skip-permissions`, 비대화형) 모두 보류되었다가 만료되었다. 같은 권한 모드의 전달용 CLI는 auto 모드 판단기가 "Create Unsafe Agents"로 거부했다. 사용자가 그 명령 하나를 허용한 뒤에야 11통이 모두 대화에 들어갔고, 계산을 기다리던 4개 세션 가운데 3개가 1–2분 안에 원본 입력을 읽고 계산을 멈췄다. 남은 1개(`s91e315f6`)는 첫 턴에서는 따랐지만 재개 턴에서 k=10⁵급 계산을 다시 띄웠다. 메시지로만 받은 결정은 재개 안내("해결을 계속 추구하라")와 겨룰 때 약해 보인다(추정).
- **Defender의 실제 몫은 작았다.** 보호 프로세스라 일반 CPU 시간으로는 보이지 않으므로 성능 카운터로 쟀다. msmpeng는 약 11%(코어 기준)였고, Python 계산이 310%였다. 정기 검사는 이미 유휴·저우선 설정이었다. 제외 경로 추가는 관리자 권한이 필요하고 보안을 낮추므로 사용자에게 명령만 제시했다.
- **독립 검토 셋이 같은 결함 하나를 찾았다.** 정리 장치가 기존 경로의 의미를 바꾼 것이다. 브로커 클라이언트의 `ensure_broker`가 세션 안에서 브로커를 띄우면 브로커가 그 세션의 묶음에 들어가, 세션이 끝날 때 다른 세션의 컴파일까지 죽는다. 구현 때 묶음에 "모든 자손"이 들어간다는 것만 확인했고, 공유 기반 시설이 세션에서 시작될 수 있는 경로는 찾지 않았다. 함께 지적된 "빠져나가기 요청 시 접근 거부"는 아직 묶음 안에서 검증되지 않은 Codex(organizer)를 깨뜨릴 수 있었다. 둘 다 `BREAKAWAY_OK`와 브로커의 명시적 breakaway로 고쳤다. 대기 작업 간격 검사가 시험되지 않는다는 지적은 돌연변이 시험으로 확인한 뒤 시험을 더했다.
- **검토에서 반영하지 않은 것과 이유.** Linux 정리 장치(개발 규모가 큼. 문서에 제약 명시), 옛 상태·설정 키 호환(영향이 업그레이드 직후 한 번뿐이고 해당 인스턴스가 없음), 호스트 종료 직후 수십 ms 잔존, 정리 실패의 `status` 표시, 재시도 파견 카운트(이득이 작음).

- 사용자 입력 원문과 세션 메시지 사본은 `.skill-workspace/do-math/operator-inputs/`(`20261109-*.md`, `messages-20261109/`, `messenger-20261109/`)에 있다. `.skill-workspace`는 Git 제외 대상이라 로컬 보관이며, 정리로 사라질 수 있다. 인스턴스에 실제로 실린 입력은 인스턴스의 `control/inputs/`에 있다.
