제한 전수조사에서 DjVu는 원139,763바이트와 압축 TXTz10개가 보존됐지만 현 디코더가 없다는 이유로 추출 미지원에 남아 있었다. 같은 문헌의 PDF가 있다는 사실만으로 이 형식의 구현 공백을 닫지 않고 공식 도구를 확인했다. 기존7-Zip으로 공식 Windows 패키지의 도구만 전용 폴더에 풀어10쪽·첫 쪽 텍스트와 이미지를 얻었다. 설치 프로그램과 전역 등록은 실행하지 않았다. Root가 원 DjVu의 렌더를 직접 열어 THREE COMPLEXITY FUNCTIONS와 DOI10.1051/ita/2011126을 대조했다.

생산용 도구는 별도 패키지 대신 현재 공식 upstream commit4847901fa2d81cdf8db89cc22f63ae5de85f963a를 고정해 기존MSVC·Windows SDK로 빌드했다. setup_djvu.py가 전용 data/tools/djvulibre 아래 원 소스·로그·라이선스·도구와 SHA-256을 보존한다. 현재 세 standalone 도구는 합계2,613,760바이트다. 새 빈 전용 디렉터리에서도 기회수 upstream checkout을 이용한 설정을 통과했다. 빌드 경로 차이에 따른 바이너리 크기 차이를 같은 해시로 오인하지 않으며 실행할 실제 도구의 해시를 각각 검증한다.

extract의 start/count는0부터 쪽을 선택하며 원 텍스트 레이어와 선택적 PNG를 반환한다. 텍스트가 비면 이미지도 제공한다. 외부 파일을 참조하는 indirect DIRM과 single-page INCL/NDIR은 실행 전에 중단한다. 공식 소스의 bundled/old-bundled 분기는 같은 원 묶음 안의 offset만 읽고 다른 경로를 거부함을 확인했다. 원 문서를 실행하거나 새로운 OCR을 수행하지 않는다. 디코딩은 별도 프로세스의30초 제한을 두며 원 stderr를 반환하지 않는다. 후속 쪽 실패는 앞선 성공과 next_start를 partial로 유지한다.

실제 기회수 Numdam DjVu로 새 MCP SDK를 실행했다.20:07:12.110452Z~20:07:20.899846Z에 전체10쪽·첫 쪽 제목/DOI·PNG349,564바이트·ImageContent1개,2–3쪽 구간과next3,마지막10쪽과next없음을 completed=true로 검증했다. 새 원격 다운로드의 성공으로 표시하지 않는다. 근거는 services/scholarly-mcp/data/access-research/limitations-audit/djvu-sdk.json, 원 판독 메모 root-image-review.md와 VALIDATION.md다. 컨테이너·외부 참조·구간·상태·시간초과·해시 변조의7검사와 공통core23검사가 통과했다.

Scopus·MathSciNet의 추가 정확성 검토와 IOP 수식 이미지의 실접속은 다른 작업자가 계속 진행한다. 최신 실패 화면에서 실제로 보이는 제어가 자동 집계0과 다른 사례도 root 이미지 판독으로 찾아 수리 중이다. 전체 구현 완료나 최종 푸시는 아직 선언하지 않는다.
