Software Heritage의 dir와 rev는 metadata만 받아 재귀 파일 회수를 못 했다. 공식 Vault flat API를 연결했다. dir는 그 디렉터리, rev는 원 metadata의 directory 필드를 선택한다. 준비된 압축본이 없을 때만 POST로 생성을 요청하며 이메일·API 키·별도 계정을 넣지 않는다. new/pending은 부분 결과와 재조회 입력으로 돌려주며 준비 중이라는 상태를 오류나 자료 부재로 바꾸지 않는다.

다운로드는 archive.softwareheritage.org의 해당 SWHID raw 경로를 확인한 뒤 실제 리디렉션에서 관측한 swhvaultstorage.blob.core.windows.net의 contents-uncompressed 컨테이너만 추가 허용했다. Azure 파일 경로에는 SWHID가 없으므로 압축본 내부 파일 내용·이름·실행 권한·심볼릭 링크를 Git blob/tree 방식으로 해시해 요청한 디렉터리와 대조한다. 원 바이트를 디스크에 풀거나 코드를 실행하지 않는다. 다른 루트·중복 경로·부모 경로·파일/디렉터리 충돌을 거부하며 하드 링크 등 미지원 항목이나 해시 불일치는 원 압축본을 source_archive로 보존한다.

실제 Azure SAS의 sig 인자는 기존 정제기가 인식하지 못했다. 원 URL은 보호된 probes에만 보존하고 출력하지 않았다. Azure Blob URL의 sig만 인증 인자로 정제하도록 고쳤다. sig를 전역 비밀 필드로 취급하면 DBLP SPARQL의 동명 변수까지 지워지므로 URL 호스트 문맥에서만 적용한다. 중첩된 URL 경로도 검사하며 알려진 값 stage 대조기에 sig를 추가했다. 이 검사는 알려진 값의 일치 검사이며 전체 기록 감사가 아니다.

새 SDK stdio 20260910T234218Z-swh-vault-mcp.json은 completed=true다. 빈 디렉터리 155바이트, OCaml 예의 디렉터리 218076바이트·69개 파일·16개 디렉터리, 같은 디렉터리를 가리키는 revision을 검증했다. 압축 안 simplefarm.ml 27줄은 별도 content SWHID로 받은 파일과 일치했다. 앞선 20260910T234131Z 보고는 검사 코드가 압축 선택 결과를 곧바로 텍스트로 오해해 실패했다. 실제 계약대로 내부 파일 참조를 한 번 더 extract한 뒤 통과했으며 생산 추출 코드는 바꾸지 않았다.

Tools 디렉터리 93ea4d40f1ace5b45af5a4a65993a87ad6e900d1의 Vault GET은 처음 404였다. 20260910T234346Z-swh-prepare-mcp.json에서는 이메일 없는 생성 후 pending 세 번, 네 번째 조회에서 available과 트리 해시 일치를 확인했다. 재실행 시 이미 준비되어 있을 수 있으므로 앞으로의 cached 성공을 생성 분기의 새 실측으로 세지 않는다. 공통 검사 212개가 통과했다.

전체 구현은 계속 진행 중이다. 다음 대상은 AMS 동적 검색·원 파일 export 등 남은 출판사 경로다. 사용자 교정에 따라 CLI·콘솔·MCP 재시작을 더 시도하지 않고 새 SDK stdio 검사로 구현을 검증한다. 전체 완료 전이므로 푸시하지 않는다.
