## 맥락

자연수의 오른쪽 덧셈 항등원을 do-math로 증명하도록 초기화하던 세션에서, 사용자는 긴 준비 시간을 검토하고 이미 적용한 수리가 임시방편인지 확인하도록 요청했다. 신뢰 환경의 범위 자체는 유지하되 같은 목적의 처리 방식을 개선하라고 구분했다. 구현 전에 영향 영역 전체를 파악하고, 구체화한 구현의 실익이 없으면 포기하며, 전제가 부족하면 방향을 수정하라는 지시도 있었다. 모델 사용 상한은 gpt-6-sol이었다.

작업의 추적 진입점은 `docs/do-math/초기화-효율-개선계획-2026-09-25.md`와 `docs/do-math/초기화-효율-구현결과-2026-09-25.md`다. 저장 코덱, 초기화와 결과 편입, 실행·복구의 생산자·소비자·스키마가 함께 바뀌므로 이번 변경을 하나의 작업 커밋으로 유지했다. 앞선 환경 준비·예약 등록 수리는 별도 선행 커밋의 작업이며 이 노드가 그 작업의 기억을 대신하지 않는다.

## 판단과 구현 중 확인한 경계

전체 파일을 읽는 비용만이 아니라 같은 정보를 여러 단계에서 다시 읽고 직렬화하는 비용을 구별했다. 56,230개 파일 목록이 과거 제어 요청과 참조 목록으로 복제되는 경로가 있었다. 표시용 prompt를 나중에 줄이는 것만으로는 이 중간 비용을 없애지 못한다. 정확한 과거 요청을 상세 파일로 보존한 뒤 참조 목록을 구성하고, 저장에서도 큰 불변 manifest와 문자열을 내용 주소형 payload로 공유했다. 이 변경은 공통 문서나 신뢰 환경의 범위를 축소하는 결정이 아니다.

파일을 통째로 읽는 8-thread 수리는 작업 수·대기열·메모리·취소를 함께 통제하지 못했다. 스트리밍 해시와 제한된 대기열로 바꾸고, 구조 검사와 실제 설치 파일 관측을 분리했다. 별도 검증 서비스는 기존 ModelCalls와 중앙 writer의 역할 분담으로 얻는 효과보다 추가 운영·복구 복잡도가 커서 도입하지 않았다. manifest 작성 전용 CLI도 기존 정확한 원문 재사용보다 추가 실익이 없어 만들지 않았다.

분리 과정에서 검사를 삭제해도 되는지와 어디에서 실행해야 하는지는 다른 판단이었다. 최종 검토에서 컴파일 후 환경 확인이 중앙 스레드에 남아 있는 것을 찾아, 없애지 않고 컴파일 전후 관측 모두 worker로 옮겼다. 미리보기와 실행기 없는 제어 경로가 다시 동기 검사로 돌아가는 경우, 취소 결과가 재개를 계속 막는 경우, 이전 실행기가 끝낸 미소비 관측을 새 실행기가 재사용하는 경우도 확인해 처리했다. 파일 관측의 실패는 수학 풀이 실패와 구별하여 명시적 recheck를 기다리게 했다.

시작 정보가 없거나 이름이 알려진 Job이 비었다는 사실만으로는 옛 owner가 더 이상 시작할 수 없다는 결론이 나오지 않는다. 실행 전에 owner의 PID·FILETIME·host/session과 Job 이름을 기록하고, 종료 확인과 용량 반환을 이 결속에 맞췄다. 주 실행기만이 아니라 독립 설치 복구 실행기도 같은 생산자 계약으로 갱신했다. 테스트의 오래된 합성 프로세스 이름·예약 기록 때문에 생긴 실패는 제품 검사를 낮추지 않고 현행 fixture로 고쳤다.

## 검증과 운영 상태

테스트 ID별 최신 안정된 관련 결과는 671개 통과, Windows 심볼릭 링크 생성 권한 부족 1개 생략이다. 여러 고정 판본의 기본 검사와 이후 수정의 영향 검사를 모은 결과이며, 전체 저장소 테스트를 같은 최종 판본에서 한 번에 실행했다는 뜻이 아니다. 모델 응답 대역의 검사, 실제 Windows Job·Git·Lean 검사, 기존 Mathlib에 대한 `--verify-only` 검증의 범위를 구별했다. 이 구현 검증에서 실제 모델을 추가 호출하지 않았다. source가 검사 도중 바뀐 실행과 중간 실패를 최종 통과 결과로 넣지 않았다.

실제 전체 관측은 56,230개 파일과 8,551,731,741바이트를 모두 대조했다. 첫 측정 약 198.6초, 최종 약 158.7초는 부하 조건이 달라 개선 배수의 근거가 아니다. 큰 제어 요청 사례에서는 원문을 정확히 보존하면서 해당 이력의 인라인 표현이 19,019,294바이트에서 490바이트로 줄었다. 같은 전체 manifest가 두 곳에 등장하는 Git 저장 사례에서는 16,767,462바이트 blob 하나와 911바이트 메타데이터로 보존됐다. 최초 생성 약 3.62초와 다음 저장 약 0.71초는 해당 사례의 값이다.

기존 연구 `RI-01M3AB8E1KYF02E3T0G7BFEVAC`는 operator 출처의 공개 pause로 정상 정지하고 자동 재시작 예약을 제거했다. 모든 실행의 ended 상태, 빈 활성 실행 목록, 실행기 종료와 writer lock 해제를 확인했다. 이전 설치 231개 파일은 바이트를 대조해 보존했다. 기존 연구는 정지·보존 상태이며 수학 목표 완료나 새 계약으로의 이관을 주장하지 않는다. 과거 기록은 보존한 판본으로 읽고, 재개에는 그 판본에 맞는 프로필·검사기 경로·신뢰 환경의 재결속이 필요하다. graphify는 변경 전 영향 탐색과 원문 대조에 사용했으며 명시적 갱신 요청이 없어 갱신하지 않았다.

## 사용자 교정과 다음 적용 위치

사용자의 첫 커밋 요청을 git add/commit으로만 처리하여 메모리 노드·색인 결합, 한국어 메시지, 종료 시 푸시 절차를 빠뜨렸다. 사용자는 commit-harness로 다시 하라고 지시했다. 파일 저장과 Git 명령의 성공을 저장소의 커밋 완료 조건으로 대신한 누락이었다. 다음 커밋에서는 staging 전에 commit-harness를 적용하고, 같은 커밋에 layer-1 노드가 정확히 하나 포함되는지와 영역별 게이트를 확인해야 한다. 이번에는 아직 푸시되지 않은 직전 작업 커밋을 보완한다. 제품 코드가 추가로 바뀐 것은 아니므로 기존 관련 실행 검증을 재사용하고 미러·구조·기억 색인 게이트를 확인한다.

dream에서 함께 검토할 후보는 범위 축소와 처리 방식 개선을 혼동하는 판단, 그리고 실행 주체나 적용 시점이 바뀌었을 때 캐시·대기·복구의 효력까지 함께 옮겨야 한다는 점이다. 앞의 판단은 사용자의 신뢰 범위 유지 지시에서, 뒤의 판단은 미소비 관측과 취소 결과의 재사용 문제에서 구체적으로 드러났다.
