[[M-0519]] 뒤 남은 직접 _enqueue 원천 세 곳을 현재 생산자에서 실제 모델·worker·수신까지 연결했다. 제품 코드는 변경하지 않았다. 목표 감사의 기존 Sim 검사 다섯 원단언을 보존해 flows.test_scheduling_research_recovery.GoalAuditReplanningTests로 옮겼고, 임의 superseded-basis 문자열 대신 실제 _goal_basis_key와 공개 source 변경을 썼다. 유효 근거는 감사1회 수락·계획0회이며, 변경 근거는 오래된 감사0회·대체 계획1회 수락이다. 이후 같은 요청이 재실행되지 않는다. 이동한 검사는 과거 legacy 이관 ID가 아니므로 migration 처분 목록에는 변경 대상이 없었다.

부수 통찰은 기존 독립 검토의 비공개 산출 검사에 이어 붙였다. 처음에는 후속 계획의 receipt_refs에 통찰 원작성자 실행이 있어야 한다고 단언했지만, 현재 계약은 공개를 완료한 검토 실행을 담는다. 지식의 producer_execution은 원작성자를 그대로 보존하며, 공개 실행은 같은 검토 cycle의 다른 실행이다. 이 구별과 공개 실행 receipt_refs·통찰 evidence_refs를 검사한다. 그 통찰을 가진 요청이 실제로 한 번 수락되고, 원근거 변경에 따른 use_suspended/의존성 단언도 유지한다. 이후 같은 통찰의 발동은 반복되지 않는다.

형식 계속 실행은 공개 pause와 restart/resume으로 실제 중단 시도를 보존한다. 처음의 새 도구 경로 등록은 configure가 역할 프로필 판본도 바꾸므로 고정된 예전 프로필에서 실행할 수 없었다. configure를 생략한 다음 초안도 프로필 명령과 신뢰 환경 명령이 달라 형식 권한 대기로 들어갔다. 이들은 제품 결함이 아니라 추가 국면을 섞은 fixture였다. 최종 검사에서는 같은 검증된 도구 기록·명령·허용 공리를 가진 새 신뢰 환경 판본을 공개 register로 만들고 실제 trust_activate로 전환한다. 판본 ID와 명세 해시가 달라진 정당한 입력 변경이며, 실행 프로필은 그대로 유효하다. 계속 요청은 추가 형식 실행 없이 제거되고, K1과 이전 시도 ID를 근거로 한 실제 계획이 한 번 수락된다. 이전 형식 시도 전체는 그대로다. 기존 동일 입력 재개 검사에는 정상 계속 실행과 계획0회를 보강했다.

첫 목표 감사 초안은 큐 요청을 저장하기 전에 공개 제어를 적용해 재로드로 요청을 잃었다. 제품 저장 경계를 생략한 fixture였으므로 요청 생산 뒤 저장하도록 고쳤다. CLI 첫 실행의 위치 인자 순서 오류는 시험 시작 전 거부였으며 제품 실패로 세지 않는다. fixture 초기 실패 두 보고를 원문으로 보존하고 최종 구조48·Sim9·flow6의63개가66.3초에 통과했다. 실행 중 소스 변경은 없다. 검증/2026-10-05-감사-통찰-형식계속/report.json과 작업판 B103이 진입점이며 해시도 작업판에 기록했다. 다른 부분 보고와 합산해 전체 일반 통과로 쓰지 않는다.

다음 작업은 개별 흐름을 무작정 더하는 대신 사건 전건×대상 유무 표를 현재 생산자와 실제 검사에 대응시키는 것이다. _enqueue 문자 호출만 세면 planning.schedule_reconsideration의 직접 큐 생산과 knowledge_io.import_candidate의 비형식 계획이 빠진다. 전자는 고갈/평가 오류/외부 대기/반환 결과/선택 사건에 따른 동적 역할을 가진다. lifecycle_engine._lifecycle_event는 schedule 인자로 pending_events에 넣고, 일반 배정은 주기 재고 사건만 준비로, 나머지는 계획으로 보낸다. 이 모집단과 공개 직접 요청도 포함해야 한다. 기존 B84 로컬 감사는 원천 위치를 찾는 보조일 뿐 완전한 사건 표가 아니다. 전체19+11·보존61·P2 원12·전건 일반/fresh T3/변이/T4/T5 목표는 유지한다.
