## 독립 변경의 범위

사용자는 기존 목표를 지우고 새 목표로 제대로 계속 작업하도록 했다. [[M-0423]]의 현행 작업판 뒤 첫 제품 통합은 JSON 저장 값의 타입 충돌 하나로 좁혔다. main과 보존판의 canonical/state_contract/repository 세 파일이 같은 바이트임을 확인했다. 수리판 전체136파일을 가져오지 않고 이 세 파일의32행 추가/12행 삭제와 실제 저장 시험5개,정본 설명과원장KD-0200만 통합한다. 원장 전체54개를 main의 기존 원장에 덮어쓰지 않는다.

기존 타입 충돌은 Python의 False==0,True==1 때문에 부모 레코드의 스키마 검사를 생략하고 부모의 다른 JSON 바이트까지 재사용하는 두 경로에 걸렸다. 새 canonical.same_json_value는 두 소비자가 공유하는 정본이며 boolean과integer를구별한다. 기존 후보 봉인의 저장 값 영역 검증은 유지한다. 비교 함수를 새 입력 검증기로 쓰지 않는다.

## main에서 실제 실패와 수리 확인

먼저 새 재현 시험만 main에 준비했다. 비교 함수 import를 해당 순수 검사 안으로 옮겨,수리 전 실제 스키마/저장 검사 두 개가 모듈 적재 오류로 바뀌지 않게 했다. 실제 Repository의 같은 입력으로 `vya2yx6q`에서2failed를확인했다.1을True로바꿔적재하면b'1\n'이남았고,boolean필드의0교체에ValueError가없었다. 제품 수리를 적용한 뒤main의unit.test_storage*69개전부passed,6.8초였다(`dznmr7tc`). 원장/표시 대응1개도passed,2.8초였다(`tm8_bs9e`). 모두실행중소스변경없음이다.

5개 시험은 정규JSON바이트와중첩/봉인문자열의동등성,변경없는부모바이트의실제재사용,부모없는1/True정상저장,boolean스키마의integer반려와원상보존,1→True→1의독립Repository재적재와정확한형/바이트를검사한다. 의미판정은값의Python동등성만으로하지않는다. 정상테스트지원2파일의AST와ObservedGit기존메서드AST도대조했다. 수리판에만추가된project조회메서드2개는이변경에서쓰지않고복사하지않았다.

수리판의전체일반기준선3877개는`knvwwf8d`/세션69435에서계속진행중이다. 그트리는편집하지않는다. 작업자31152가실제로종료하고1272결과가complete된뒤반환된한슬롯으로main재현과69개를돌렸다. 다른작업자와합쳐시험3개상한을지켰다. main의부분통과를수리판전체성공이나최종19/61/11의무폐쇄로세지않는다.

공식미러생성기는3생성/12갱신/0삭제를기록했다. 기존main의교차시험·측정캐시도생성대상에포함됐다. 이번커밋에는위정본6파일과그생성사본6파일만선택한다. 기존cross_contracts/cross_machine,교차시험2개와측정자료변경은이번작업이아니므로스테이징하지않고그대로남긴다. 미러검사와기억색인게이트를통과한뒤커밋한다. 푸시는사용자범위밖이다.
