주차 함수 연구 인스턴스 `RI-01M2JP80JC7RHQAJ7QGRPYZQEG`는 research_plan 출력과 한 차례 수리가 같은 모집단 검증에서 거부되어 paused였다. 정확한 snapshot의 task 목록에는 ready 과제가 없었지만, `runtime.task_readiness`에는 completed 과제 두 개가 이전 `ready` 상태로 남아 있었다. 연구 계획 계약은 `tasks[].status=ready`인 과제 전건을 모집단으로 삼고 readiness는 그 근거를 확인하는 보조 투영으로 읽게 하므로, 두 표현의 불일치가 생산자 판단을 혼란스럽게 했다.

## 재현과 수리

승인된 과제를 ready로 평가한 뒤 과제 status를 completed로 바꾸고 readiness를 새로고침하는 최소 회귀를 만들었다. 수정 전에는 `task_readiness['T1']`이 `ready`로 남아 테스트가 실패했다. `_refresh_readiness`는 스케줄 가능한 상태의 과제만 새로 평가하면서 그 밖의 과제의 과거 투영을 제거하지 않았기 때문이다.

스케줄 불가능한 과제를 만나면 같은 task ID의 readiness 항목을 제거하도록 lifecycle 코드만 수정했다. 과제의 완료 이력, assessment, 연구 결과와 수학 판정은 바꾸지 않는다. `.claude/skills/do-math` 정본과 생성된 `.agents/skills/do-math` 사본에 같은 코드와 회귀를 보존했다.

## 검증과 운영 인계

집중 회귀 1건과 lifecycle 파일 26건이 통과했다. 전체 do-math 회귀는 283건 중 282건 통과, 기존 Windows 심볼릭 링크 권한 사례 1건 미실행으로 exit 0이었다. 설치본 구조와 10개 역할 schema 검사, 249개 미러 드리프트 검사도 통과했다. 이 검증은 readiness 투영과 설치 구조의 회귀 근거이며 수학적 해결을 뜻하지 않는다.

같은 운영 회차에서 scholarly MCP 49개 자료원과 arXiv·zbMATH·Crossref·Semantic Scholar의 실제 문법을 확인했다. zbMATH에서는 알려진 arXiv:2507.07243 기록을 회수했지만 arXiv와 Semantic Scholar는 429였고 Crossref 제한 질의에는 관련 기록이 없었다. 이 결과를 해결 문헌 부재로 확대하지 않고 운영 run directory의 source 후보에 도구 문법·artifact ref·실패 범위를 함께 남겼다.

dream에서 묶을 후보: 상태기계의 현재 투영은 terminal 전이 때 과거 readiness를 제거해야 한다. 생산자와 소비자가 서로 다른 권위 필드를 쓰더라도 보조 투영의 낡은 값은 실행 실패를 유발할 수 있으므로, terminal 전이와 projection invalidation을 한 불변식으로 검증할 가치가 있다.
