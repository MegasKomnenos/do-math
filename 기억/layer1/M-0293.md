사용자는 [[M-0292]]의 연구를 운영할 AI가 주기적으로 상태를 확인하고 조치하도록 요청했다. 최초 제안의 30분을 최종 지시에서 2시간으로 바꿨으며, 이 대화 세션을 닫아도 되는지도 물었다. 기존 대화를 자동으로 깨우는 도구 대신 Windows 작업 스케줄러가 별도의 Codex 실행을 시작하는 구성을 적용했다.

## 등록한 구성

정본 파일은 `research/parking-unimodality-operations/`의 config.json, supervisor.py, OPERATOR.md, README.md, install.ps1이다. 운영 작업 `DoMath-Parking-Operator-Cmath`는 종료일 없는 PT2H 반복이고, 연구 작업 `DoMath-Parking-Engine-Cmath`는 운영 담당이 필요할 때 시작한다. 두 작업을 분리했으므로 운영 담당이 종료돼도 별도 연구 작업은 대화 세션이나 운영 담당의 자식 프로세스에 의존하지 않는다. 각각 IgnoreNew를 사용하며 연구 정본의 동시 쓰기는 기존 writer lock이 보호한다.

대상 인스턴스는 `RI-01M2JP80JC7RHQAJ7QGRPYZQEG`다. 로그는 `C:\math\.skill-workspace\parking-unimodality-20260915\operator`에 보존한다. 이 로그 디렉터리의 latest-check.json은 마지막 완료 회차의 보고서다. 진행 중 회차는 `operator/check/` 하위의 실행별 디렉터리에서 읽는다. 운영 담당은 현재 상태와 이전 기록, 실패의 원 출력을 읽어 조치하며 사용자 결정이 필요한 사항은 user_questions에 남긴다. 이 대화로 알림을 자동 전송하는 구성은 아니다.

두 작업은 현재 Windows 사용자 DESKTOP\wogud의 Interactive 로그인으로 실행한다. 실제 운영 프로세스의 부모가 Windows 서비스 svchost인 것을 확인했다. 따라서 대화와 Codex 앱 창은 닫아도 되지만 Windows 로그인, 켜져 있고 절전하지 않는 PC, 네트워크와 유효한 Codex 인증이 필요하다. 화면 잠금은 로그아웃과 구별한다. 실행 가능해진 뒤 놓친 예약을 처리하도록 StartWhenAvailable도 설정했다.

## 정지와 실행 경계

supervisor.py hold는 고유 ID가 있는 HOLD 파일을 만들고 그 ID가 담긴 이유로 연구에 pause를 보낸다. 새 운영·연구 시작은 HOLD에서 차단되고 진행 중 운영 실행도 종료 신호로 관찰한다. release는 해제한 HOLD 객체를 release.json에 보존한다. 운영 담당은 같은 ID의 pause만 해제된 것으로 읽고, 다른 사용자 pause·close를 덮지 않는다. 출처가 불명확한 정지는 유지한다.

운영 모델은 gpt-5.6-sol high이며 기존 Codex 사용자 설정을 사용해 scholarly MCP에 접근한다. 인스턴스의 work_calls와 operations_calls는 null, 즉 각각의 실행 횟수 상한 없음으로 유지했다. 한 운영 실행의 상한은 90분, 예약 작업 상한은 110분이고 연구 예약 작업 상한은 150분이다. 연구 내부의 run 상한은 인스턴스 설정이 소유한다. 운영 담당은 정지 원인을 검사·조치한 뒤 재개하며, 같은 오류에 resume만 반복하지 않는다. 목표 축소나 새로운 외부 발표·결제·타인 메시지는 허용하지 않는다.

## 실제 확인과 남은 연구

예약 작업을 읽기 전용 probe로 직접 호출해 Codex 실행, 연구 상태·실행 원장 조회, scholarly list_sources의 성공과 49개 자료원을 확인했다. probe 전후 연구 snapshot은 동일했고 예약 작업은 종료 코드 0을 반환했다. 실행 중 다시 호출했을 때 추가 운영 디렉터리가 생기지 않았다. 연구 작업도 직접 호출했으며 paused 상태를 임의로 재개하지 않고 종료 코드 0으로 끝났다. 네 개의 로컬 검사는 정지 상태의 시작 금지, 명령 대상과 사용자 MCP 설정 유지, HOLD ID를 보존하는 release, 인계 요약의 불필요한 이력 중복 방지를 확인했다. 별도 Codex가 OPERATOR.md와 README.md 전문을 독해했고, 메인은 그 이해를 확정된 사용자 요구와 실제 구현에 대조했다. 상세 근거는 같은 디렉터리의 verification.json에 있다.

probe 뒤에는 일반 운영 모드로 등록했다. 이때 확인한 첫 정기 시각은 2026-09-16 02:29 KST이며 이후 2시간 주기다. 자연적인 다음 예약 시각 도래를 기다려 관찰한 것은 아니므로, 실제 수동 예약 호출 검사와 설정 확인을 구별한다.

설치 시 연구는 두 차례의 research_plan 출력 검증 실패로 paused였다. probe는 completed 과제와 task_readiness의 ready 표지가 계획 모집단에 섞이는 불일치 가능성을 확인했고, 다음 일반 운영의 재현·수리 대상으로 인계했다. 후보 준비가 삭제를 제안한 이전 완료 기준이 수신된 개정 계약에 계속 남는 현상도 있었다. 하위 연구 실행은 scholarly 도구를 받지 못했다고 반환했으므로, 운영 담당의 도구 접근 성공과 구별해야 한다. 이번 예약 설정은 그 문제의 복구 완료나 수학적 해결을 뜻하지 않는다. 후속 상태와 실제 조치는 현재 인스턴스 및 운영 보고서에서 다시 확인한다.
