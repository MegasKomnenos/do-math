## 맥락

사용자가 `docs/do-math/통합-설계.md` 9차 판본을 본문만 근거로 꼼꼼히 검토하고, 거듭된 재설계가 남긴 이력 누출·흩어진 정의·옛 설계의 부정문·불일치를 해결하되 실익 있는 내용은 보존하라고 지시했다. 다른 문서와 기억 노드는 읽지 말라는 범위 제한이 있었으므로 검토 근거를 본문으로 한정했고, 명세 묶음은 문자열 검색으로 의존 관계만 확인했다. 발견 20건과 처분은 `docs/do-math/구조-정리-2026-09-09/발견과-처분.md`가 기록하며, 문서 끝의 20절 판본 이력이 헤더에 있던 변경 이력을 대신한다. 두 번째 지시에서 사용자가 의미 보강 다섯 건을 권고대로 채택했고, 이 커밋은 묶음 재생성·재검증까지 담는다.

## 터득한 것

정리의 자유도는 묶음의 의존이 정했다. build_spec.py는 절 번호를 스키마 가족의 소유 절로 선언하고, source-vector-map.json은 17.2절 V 행과 17.6절 Q 행의 원문을 대조하며, validation-report.json은 본문과 `docs/형식과-절차.md`의 해시를 고정한다. 그래서 절 번호와 앵커, V·Q 행의 바이트, 16.4절 생성 표를 그대로 두고 소제목과 새 절 두 개(0.4 공통 원칙, 20 판본 이력)로만 구조를 바꿨다. 본문 한 바이트라도 바뀌면 검증 보고가 무효가 되므로 문서 정리는 묶음 재생성과 같은 커밋에 있어야 한다.

되풀이된 원칙은 삭제가 아니라 소유 절 지정으로 풀린다. 판단 대체 금지 26곳, 부재 추측 금지 19곳처럼 소유 절 없이 반복되던 문장은 0.4절에 아홉 항으로 한 번 정의하고 절별 고유 귀결이 없는 33곳을 지웠다. 옛 설계를 부정하는 문장은 그 자체가 이력이며 긍정 규정 하나로 바꾸면 사라진다.

본문만 읽는 검토가 놓칠 수 있는 것은 묶음이 이미 답한 문제다. 13.2절에 없던 truncation 항목은 스키마 common의 truncation_permission으로 이미 있었고, 유보했던 organize 실행의 role_slot_id는 검사기 check_review_output이 요청과 결과의 일치만 검사하며 검사 예제가 planner를 쓴다는 사실로 닫혔다. 새 원인값 profile_replaced는 build_spec.py의 열거 선언 두 곳(input-manifest, issue-state)에 더해야 스키마에 반영된다.

도구 운용에서 세 가지를 실측했다. 큰 Python 스크립트를 Bash heredoc으로 넣으면 셸이 따옴표 짝을 찾다 실패하므로 Write 도구로 파일을 만들어 실행하는 편이 안전하다. Git Bash의 `/tmp`는 사용자 AppData의 Temp로 대응되어 Read 도구가 `C:\tmp`에서 찾지 못한다. 첫 명령의 `cd`가 세션 작업 디렉토리를 옮겨 뒤의 상대 경로 명령이 실패했으므로, CLAUDE.md의 cd 규칙대로 같은 호출 안에서 루트로 돌아와야 한다.

## 작업 너머 시사점

생성 묶음이 정본 문서에 의존하는 저장소에서는 문서 정리 전에 의존의 종류(절 번호, 행 원문, 해시)를 먼저 계량하는 절차가 필요하다. dream에서 묶을 후보: 문서 정리 착수 절차에 "생성물의 의존 계량"을 두는 관례. 긴 규범 문서의 공통 원칙 절과 판본 이력 절 분리는 write-for-reader의 수정 절과 같은 뿌리이며, 스킬 문서에도 적용할 수 있다.
