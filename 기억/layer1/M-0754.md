## 맥락

사용자가 돌고 있는 프로세스를 살펴 성능을 개선할 여지를 찾으라고 지시했다. 이 커밋의 안내 수정은 그 조사에서 나온 조치 가운데 하나이고, 조사의 측정값과 나머지 조치는 diff에 남지 않으므로 이 노드에 적는다.

측정 시각은 2026-11-23 04:51부터 04:53까지다. 기계는 코어 4개, 물리 메모리 15.9 GB다. 그때 해바라기 인스턴스(`.skill-workspace/sunflower-20261122`, 세션 상한 10)와 주차함수 인스턴스(`.skill-workspace/parking-unimodality-20261119`, 세션 상한 8)가 함께 돌고 있었고 대화형 Claude 세션이 넷 있었다. `claude` 프로세스는 21개였다.

두 번째 표본에서 프로세서는 100% 사용 중이었고 유휴 0%, 커널 시간 40%, 실행 대기 스레드 16개였다. 가용 메모리는 4.7~5.3 GB, 디스크는 93% 유휴였다. 표본은 두 번뿐이고 표본을 뜨는 명령 자체가 코어의 7~10%를 썼다.

## 터득한 것

**버려진 `find` 한 개가 코어의 70~77%를 쓰고 있었다.** 명령은 `find / -maxdepth 6 -type d -name Mathlib`이고 04:37:09에 시작했다. 부모 셸은 사라진 상태였고, 열린 핸들 수가 내가 보는 동안 19만 8천에서 30만 9천으로 늘었다. 사용자 지시로 끝냈다. M-0751이 같은 날 앞서 끝낸 `find /` 셋과 같은 종류다.

**이 프로세스가 남는 경로.** 세션 전사를 검색해 이 명령을 낸 세션이 해바라기의 `s6d43f9a2167f4f2b97670b5187c28643`이고(04:37:04) 측정 시점에 아직 돌고 있었음을 확인했다. Claude의 셸 도구는 명령을 120초 뒤 백그라운드로 옮기고, 그 뒤 10분이 지나면 셸을 끝내는 방식으로 명령을 멈춘다. Windows에서는 부모를 끝내도 자식이 끝나지 않으므로 `find`가 계속 돈다. 세션의 Job 객체는 세션 호스트가 끝날 때에만 구성원을 끝낸다(`runtime_support.py`의 `contain_session_processes`). 턴 사이에 세션이 기다리는 작업을 살려 두려는 설계다. 그래서 버려진 프로세스는 세션이 끝날 때까지 남는다. Job이 실패한 것이 아니다. 02:10 무렵부터 해바라기 세션 여섯이 루트부터 Mathlib를 찾는 명령을 열두 번 넘게 냈다. 이미 끝난 세션의 `find`는 04:51에 하나도 남아 있지 않았는데, Job이 끝낸 것인지 스스로 끝난 것인지는 가리지 못했다.

**세션이 찾던 위치는 이미 `input.json`에 있었다.** `settings.lean.cwd`가 컴파일이 도는 프로젝트 폴더이고 `settings.lean.command`가 도구 모음의 실행 파일을 가리킨다. 안내에는 들여오는 라이브러리를 "by its own means"로 찾는다는 문장만 있었고(`.claude` 사본 `reference/canon.md`) 위치를 가리키는 문장은 없었다.

**문단을 넣은 자리.** `.claude` 사본은 `reference/canon.md`의 "When you need a tool or a lemma" 문단 뒤다. `.agents` 사본에는 `canon.md`가 없어, 모든 역할이 받는 `reference/tools.md`의 "Other computations and literature tools" 절에 넣었다. 주차함수의 review 역할은 `lean.md`를 받지 않는다는 것을 실제 `input.json`의 `documents`로 확인했다.

**사용자 교정.** 처음 넣은 문단은 이 기계의 배치를 그대로 적었다. Git Bash의 `/`가 드라이브 전체를 훑는다는 설명, `.lake/packages/mathlib/Mathlib` 경로, 도구 모음의 `src/lean` 폴더, 한정된 검색이 몇 초에 끝난다는 실측이 들어 있었다. 사용자는 이 환경에 맞춘 내용 대신 `input.json`을 확인하라는 식의 더 일반적으로 적용되는 말로 쓰라고 했다. 고친 문단은 `input.json`의 두 값이 설치 위치를 기록한다는 사실과, 루트부터의 검색이 셸 도구의 대기보다 오래 걸리고 프로세스가 남을 수 있다는 사실만 적는다. 내 해석으로는, 문제를 관찰한 환경의 세부를 안내에 옮긴 것이 원인이다. 안내는 여러 인스턴스와 환경에서 읽히므로 그 환경에서만 참인 경로를 적으면 다른 환경의 독자에게는 틀린 안내가 된다. 다음에 안내를 고칠 때는 관찰한 사실 가운데 실행기의 계약에서 나오는 것(여기서는 `input.json`의 필드)만 본문에 두고, 기계의 배치에서 나오는 것은 뺀다.

**고아 콘솔 도우미 27개.** 부모가 사라진 `cygwin-console-helper.exe`가 27개 있었고(전날 23:21부터 04:52 사이에 시작, 프로세서 사용 없음) 사용자 지시로 끝냈다. 끝내기 직전에 이름, 시작 시각, 부모 부재를 다시 확인했다. 함께 `conhost.exe` 22개가 스스로 끝났다.

**조치하지 않은 관찰.** 사용자에게 보고했고 결정은 받지 않았다.

- 컴파일이 도는 시간보다 대기열에서 기다리는 시간이 길다. 최근 60분 동안 해바라기는 77건에서 대기 중앙값 33초, 실행 중앙값 19초였고, 주차함수는 56건에서 대기 중앙값 81초, 실행 중앙값 38초, 최장 대기 693초였다. 컴파일이 하나라도 돌고 있던 시간의 비율은 35%와 43%였다. 브로커 로그는 시작과 종료만 기록하고 기다린 이유를 기록하지 않아, 의존 순서, 메모리 예산, 가용 메모리 하한 가운데 무엇이 원인인지는 가리지 못했다.
- 두 인스턴스 모두 `lean.cpu_threads_budget`이 `null`이다. 스레드 2개짜리 컴파일 넷이 동시에 도는 것을 보았다.
- `claude` 프로세스는 기본 우선순위 13으로 돌고 컴파일과 세션의 계산은 8로 돈다. 무엇이 13으로 정하는지는 확인하지 않았다.
- 세션마다 scholarly 서버를 하나씩 띄워 20개 세션에서 합계 약 1.4 GB를 쓴다. `claude` 프로세스 21개의 작업 집합은 6.4 GB다.
- 실행기 둘과 브로커 둘의 자체 비용은 합쳐 코어 하나의 약 11%다.
- `Keep-ChromeHigh.ps1`이 Chrome 없이 열흘째 돌고 있다(비용은 코어의 약 0.1%).

**한 번 틀리게 보고한 것.** 첫 표본에서 프로세서 사용이 0%인 Lean 컴파일 넷을 진행 보고에 멈춘 것으로 적었다. 다음 표본에서 이미 끝나 있었고, 최종 보고에서 바로잡았다. 한 표본의 0%는 멈춤의 근거가 되지 못한다.

**도구에서 걸린 곳.**

- Bash 도구에서 `powershell -Command "..."`를 큰따옴표로 감싸면 Git Bash가 `$os`, `$_` 같은 변수를 먼저 빈 문자열로 바꾼다. `\$`로 적어야 한다.
- 첫 프로세스 조회 명령을 자동 모드의 권한 검사가 막았다. 우회하지 않았고 사용자가 명령 문자열 전체를 지정해 허가했다. 허가된 문자열이 위 이유로 실패했을 때에는 고친 문자열을 실행하지 않고 다시 허가를 받았다.
- Bash의 `cd`가 세션의 작업 디렉토리를 한 번 바꾸었다. 다음 호출에서 루트로 되돌렸다.
- 저장소 루트에서 `기억/**/L-0020*` 같은 Glob이 20초 시간 초과로 끝났다. `path`에 `기억` 폴더를 주면 바로 끝난다.

## 작업 너머 시사점

- **경고: 이 커밋의 확인 범위.** 스킬 미러 게이트는 돌리지 않았다. `.agents` 사본은 재생성하지 않는다는 기존 사용자 결정(M-0735, M-0751)을 따랐고 그 사본에는 손으로 넣었다. do-math 시험은 돌리지 않았다. 시험이 두 파일을 참조하는 곳은 문서 이름 목록과 주석뿐임을 검색으로 확인했다. 넣은 문단의 독립 독해는 하지 않았다. 종료를 지시받은 뒤의 프로세서 표본은 사용자가 중단해 없으므로 `find`를 끝낸 효과는 재지 않았다.
- **적용 시점.** 이미 돌고 있는 세션은 새 문단을 받지 않는다. 뒤에 시작하는 세션부터 받는다.
- **코드로 막지 않은 이유.** 버려진 명령과 세션이 일부러 남긴 백그라운드 작업을 실행기가 구별할 수 없다고 판단해 안내 수정만 했다. 사용자가 이 판단을 승인한 것은 아니다.
- **사용자에게 남은 결정.** 세션 상한 또는 `cpu_threads_budget`, 브로커 로그에 대기 이유를 남길지, scholarly 서버를 세션들이 함께 쓰게 할지, push할지(이 커밋 전에도 `main`이 `origin/main`보다 23개 앞서 있었다).
- **dream에서 묶을 후보.** 안내 문장에 관찰 환경의 세부를 옮긴 일은, 지침이 실제 환경의 한 사례로 좁아지는 다른 기록과 묶일 수 있다. 같은 증상(`find /`)을 M-0751에서 프로세스 종료로만 처리했고 원인인 안내의 공백은 이번에야 고쳤다는 점은, 증상 조치 뒤 원인을 따로 남기는 관례의 후보다.
