title: 조회 문서의 소유자를 실제 파일 조회와 레코드 반환에 연결함

B129를 기다리는 동안 새 독립 문맥에서 DOC-RETURN-CLI의 조회 부분만 검토했다. 초기화-운전.md의 result.snapshot과 result.items[].path는 query --files를 설명하지만, 기존 field_schemas는 query_records와 _record_evidence의 AST 모양으로 query_result를 만들었다. 서로 다른 생산자가 같은 snapshot/path 이름을 가지므로 문서가 실제 파일 조회 결과에 연결되지 않아도 통과했다. CLI-실행-계약.md의 record.family 역시 _query_record의 대입문 모양에서 추출했다.

검토와 구현 후보 작성은 별도 임시 복사본에서 끝내어 B129의 정본과 HEAD를 유지했다. 해당 여섯 원본의 해시가 같은지 확인한 뒤, B129 및 한정 단언 수리가 끝나고 40464597로 보존된 후에 후보를 적용했다. 먼저 구조 시험 수정만 적용하여 기존 공개 검사 API가 실제 query_record 결과 없이 검증을 허용하는 반례를 만들었다. ValueError를 기대한 단언이 실제로 실패했고, import 오류나 새 인자 오류에 의존하지 않았다. 원보고의 complete는 true이고 실행 중 소스 변경은 없다.

세 AST 결속을 제거하고 query_record와 query_result를 서로 독립적인 실제 결과 경계로 바꾸었다. 실제 결과가 없으면 기본 검사에서 ValueError를 내며, 구조 검사 및 다른 보고서 시험은 자신이 제공하지 않는 소유자만 명시적으로 보류한다. 기존 _query_record 가족 순회 시험이 실제 record.family를 검증하고, 기존 CLI query --files 시험의 최종 반환이 초기화 문서를 검증한다. 파일 항목은 실제 최상위 키의 교집합에서 얻는다. 후보 검토 때 path 한 필드로 고정한 모양을 발견해 이 방식으로 고쳤고, 임의 레코드 내부를 재귀 추론하는 도구는 만들지 않았다.

정상 실제 반환뿐 아니라 family·snapshot·items·항목 path 삭제가 해당 문서 경로를 실패시키는지 확인했다. 빈 배열은 항목 필드를 입증하지 못하고, 파일 결과가 레코드의 record.family나 logical_sha256을 빌려 통과하지 못한다. 배열 표기 생략과 별칭의 다음 줄 누출도 거부한다. 제품 코드는 바꾸지 않았으며 구조 문서 검사에 새 저장소나 CLI 실행을 만들지 않았다. 기존 상태·진행 보고 시험에는 미제공 조회 소유자의 명시적 보류만 추가했다.

수정 뒤 문서·구조 18개, 단위 3개, 실제 CLI 경계 1개가 모두 통과했다. 총 22개, 144.5초이며 changed_during_run은 비어 있다. 실제 CLI 경계는 92.969초로 30초 소프트 기준을 넘었지만 단언이나 범위를 줄이지 않았다. 검증/2026-10-06-조회-실제반환의 red.json과 green.json에 원보고를 바이트 그대로 보존한다.

이 결과는 조회 slice의 종료다. DOC-RETURN-CLI는 partial_complete로 두었고 init_result·scheduling_result·selection_result 및 CLI status 전달 범위는 남겨 두었다. 다음 한정 작업은 select-profile 반환의 소유자다. 단독 필드 이름과 다른 역할·검토·신뢰 반환, 정책 의미, 실제 읽기 한도, 13-C 전체 및 최종 일반/T3/변이/T4/T5의 완료로 확대하지 않는다.
