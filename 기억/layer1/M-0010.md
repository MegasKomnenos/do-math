# pvsnp-탐사-1 전개 2.7.10.59 결정 소비분 커밋 — 검증런 2.7.10.59.5 0단계 기준선 확립

## 맥락

M-0007·M-0009가 기록한 검증런 `2.7.10.59.1`(L02~L06, 행 4~13)·`2.7.10.59.3`(L12~L16, 행 24~33)에 이어, 이 세션은 다섯 번째 자식 검증런 `2.7.10.59.5`(L18~L22, 행 44~53, 파견문: `행/2.d/7.d/10.d/59.d/5.md`)를 verify-rounds로 실행하도록 위임받았다. 검증 범위는 전개 `2.7.10.59`가 행 44~53에 추가한 문면이다.

verify-rounds SKILL.md §0단계 7·8항은 라운드 1 전에 Git 색인이 비어 있고 동결문 「산출물」 절 경로에 워킹트리 변경이 없어야 한다고 요구한다. 이 검증런의 대상 13개 경로(`파견표.md`, `59.d/불변식.md`, `59-보고.md`, `44.md`~`53.md`) 중 `44.md`·`46.md`·`48.md`·`50.md`·`52.md`는 미추적 신규 상태, `45.md`·`47.md`·`49.md`·`51.md`·`53.md`는 수정 상태였다 — 전개 `2.7.10.59`를 실행한 앞선 세션이 산출을 커밋하지 않고 워킹트리로 인계한 같은 패턴이다. `파견표.md`는 이번 확인 시점에는 이미 커밋 `fa5258a`(검증런 `2.7.10.59.2`의 0단계 기준선 확립)가 흡수해 변경이 없었고, `59.d/불변식.md`·`59-보고.md`도 앞선 검증런들의 라운드 커밋이 이미 흡수해 변경이 없었다. 이번 커밋은 그 10개 행 파일(`44.md`~`53.md`)만 이름으로 지정해 스테이징했다.

이 세션 도중 `git add`로 `파견표.md` 단독을 스테이징한 시점에 diff가 이미 비어 있었다 — 형제 검증런(`2.7.10.59.2` 계열)이 병행으로 돌며 그 사이에 `파견표.md`를 커밋한 것으로 판명됐다(`git log`로 `fa5258a` 확인). 국면 `pvsnp-탐사-1`의 검증런 `59.1`~`59.5`가 병행 실행 중이므로, 0단계 착수 직전에는 매번 `git status`·`git log`를 다시 확인해 다른 세션의 병행 커밋으로 대상 경로 상태가 바뀌었는지 재검사해야 한다.

## 터득한 것

- M-0006·M-0007·M-0009가 기록한 같은 패턴(전개 산출을 커밋하지 않고 워킹트리로 다음 검증런에 인계)이 같은 국면 `pvsnp-탐사-1`에서 다섯 번째로 재현했다(`56.8`, `59.1`, `59.2`(파견표 갱신, `fa5258a`), `59.3`, 이번 `59.5`). do-dag 파견 완료(검산 exit 0)와 커밋 사이의 명시적 결합 부재가 이 국면에서 반복적으로 다음 단계(verify-rounds 0단계)의 사전 확인·대행 커밋 비용을 만든다.
- 형제 검증런이 실제로 병행 실행 중임을 이번에 직접 관측했다 — `git add`로 스테이징한 파일에 diff가 없어 조사한 결과, 다른 세션이 그 사이 같은 파일을 커밋했다. 0단계의 Git 상태 확인은 세션 시작 시점 1회가 아니라 스테이징 직전에 재확인해야 신뢰할 수 있다.
