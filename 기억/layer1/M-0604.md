## 맥락

[[M-0603]]에 이은 같은 검증 런이다. Opus 5.5 수리 4기는 9건을 냈고, 병합 뒤 7건을 Astra 심사 3기가 판정했다. 수리 3·무처분 1·기각 3이며 공식 적용은 구성 행 기준 5건이다. 메인은 남은 네 안건을 직접 검토해 세 안건을 보완·정리하고 운영 문서 전면 재배치는 채택하지 않았다.

## 터득한 것

- 범주 기본값이 쓰는 CLI만 설정돼 있으면 초기화는 통과하지만, 계획이 다른 공급자를 선택할 때 `settings.cli[provider]`가 KeyError를 냈다. 이는 기동 실패 예외 처리 밖으로 나가 실행기를 중단시켰다. 기존 시험 fixture에서 실제로 재현했다. 공급자 부재를 ValueError로 표현하는 두 줄을 추가해 기존 launch_error·실패 사건 경로로 보냈다. 계획이 원인을 받아 처리할 수 있고 실행기는 계속 돈다.
- JSON 파서는 5000단계 배열에서 RecursionError를 냈고 공식 검사 진단으로 바뀌지 않았다. 예외를 JSON 해석 자리에서 Invalid로 변환한다. 동시에 객체 검사를 그 try 밖으로 옮겨, Invalid가 ValueError로 다시 잡혀 파일 경로가 두 번 붙던 오류를 없앴다. 함수와 CLI의 실제 진단을 확인하는 회귀를 추가했다.
- 심사는 수리자의 “launch_error는 CLI가 시작되지 않았을 때만 생긴다”는 새 단정을 기각했다. 같은 try에는 CLI 시작 뒤 식별값 조회·process.json 저장도 들어 있어 OSError가 해당 필드에 남을 수 있었다. 메인은 필드를 배타적으로 정의하는 문장을 넣지 않고, 설정·환경 분류가 CLI 로그도 보도록 기존 조건만 넓혔다.
- requests와 “별도의 과제 등록부는 필요 없다”가 충돌한다는 지적은 성립하지 않았다. 추가 등록부를 만들지 않는 것과 기존 요청을 읽는 것은 양립한다. 모순 수리로 세지 않고 불필요한 부정형 문장만 정리했다.
- 운영 규칙을 한 문서로 옮기면 변경도 한 곳에서 끝난다는 재배치안은 그 효과를 입증하지 못했다. 실행 계약을 RUNTIME에 남기는 이상 일부 관계는 계속 양쪽에서 설명해야 한다. 앞 라운드의 예시·설정 중복 제거를 유지하고, 새 문서 분할이나 추가 전면 이동은 하지 않았다.

전체 22시험이 26.206초에 통과했고 미러 185파일·diff 공백 검사도 통과했다. 추적 근거는 `임시/do-math_검증_20261022/장부.md`와 `기각보관/do-math-라운드3.md`다. 라운드 사본과 파견 원자료는 종료 후 제거할 로컬 중간물이다.
