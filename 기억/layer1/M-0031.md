# 검증런 2.7.9.5.5 완료: 기각 보관 원문 경계 공백 수리, 라운드 중 §8 신호 6 자체 처리

## 맥락

행 `2.7.9.5.5`(파견문 `행/2.d/7.d/9.d/5.d/5.md`)는 행 `2.7.9.5.4`가
`cmd_심사집계`의 기각 보관 원문 조회를 `대상원문맵`(심사 대상 본문 축자)으로
고친 결과를 verify-rounds로 독립 검증하는 런이다. 이 세션이 절차 전체를
직접 실행했다. 개별 수리자·심사자 파견은 codex exec(`gpt-5.6-terra`
high/medium)로 하되, verify-rounds 절차 자체를 다른 서브에이전트에 통째로
위임하지 않았다.

0단계 전 확인 결과 검증 대상이 두 저장소에 걸쳐 있었다. 코드 산출물
(`vr.py`·`test_심사집계.py` 정본·미러 4건)은 노드 worktree
(`C:\Users\wogud\AppData\Local\dag-wt\pvsnp-탐사-1+2.7`)에서 `M`,
`4-보고.md`는 메인 저장소(`C:\math`)에서 `??`였다. M-0019·M-0021이 세운
분할(산출물 = 노드 worktree 코드 파일만, 보고류 = 기준 원문/정본)을 그대로
적용해 동결문 「산출물」 절을 두 코드 파일로 좁히고 `4-보고.md`는 「기준
원문」 절로 옮겼다. 대행 커밋은 저장소별로 나눠 실행했다. 워크트리
`d90d53c`(정본·미러 4건), 메인 저장소 `461d651`(`4-보고.md`). 이 국면의
"do-dag 완료-커밋 미결합" 패턴 재현은 이번까지 20회 이상이다.

라운드 1(체급 {경량}, 하한=상한=1)을 실행했다. 수리자 3기(codex
`gpt-5.6-terra high`: 관점 1기 테스트 커버 실질, 영역 2기 `vr.py`·
`test_심사집계.py` 파일 분할)가 항목 2건을 냈다. R1-01은 `cmd_심사집계`가
기각 보관 원문을 `.strip()`으로 정규화해 심사 대상 본문의 좌우 공백을
잃는 결함, R1-02는 `test_통과와_목록`이 `무처분` 목록을 단언하지 않는
결함이다. 교차·결합 없어 병합 0건, 심사자 2기(codex `gpt-5.6-terra
medium`) 정족 2로 두 항목 모두 독립 승인·「수리한다」 확정, 적용 2건.

적용 뒤 §7 4단계 불변식 재실측(`test_심사집계.py` 직접 실행)에서
`test_기각보관_원문은_심사대상_본문과_같다`가 실패했다. R1-01이 기각
보관 쪽의 `.strip()`을 없앴는데, 그 테스트의 비교 대상 쪽(`대상맵`)이
여전히 `.strip()`을 써서 비교하는 양쪽의 공백 처리 방식이 달라졌다. §8 신호 6(적용 문자 단위 대조의
전제 위반에 준하는 산출물 내부 불일치)으로 판정하고, `상신_자체판단` 켬
아래 물음 셋(오판 비용 낮음·되돌리기 비용 낮음·판단 가능성 있음: 같은
필드 `s.body`를 양변에 공급하는 코드로 확정)을 적용해 상신 없이 자체
처리했다. `대상맵` 쪽의 `.strip()`을 제거해 양쪽 모두 공백을 보존하도록 맞추고,
`test_심사집계.py` 18건 전건 통과·미러 재생성·`--check` 드리프트 없음을
확인했다. 라운드 판정은 순서 3항(라운드 수 1 ≥ 상한 1)으로 종료했다.
기각 보관 0건(`기각보관/2.7.9.5.5-라운드1.md`, 파일 실재·본문 「없음」).
종료보고: `행/2.d/7.d/9.d/5.d/5.d/종료보고.md`. 라운드 커밋은 워크트리
`f08b806`(산출물 4건), 메인 저장소는 이 노드가 담당한다(동결·장부·종료보고·
파견표 상태·기각 보관 신규 1건 + 이 메모리 노드·색인).

## 터득한 것

- 검증런 자신이 라운드 도중 §8 신호를 자체 발견·자체 처리하는 사례를
  처음 관측했다. 승인된 조각을 적용한 결과가 같은 산출물 안의 다른
  자리(새로 추가된 시험 자신의 비교 로직)와 충돌을 낳았고, 그 충돌은
  적용 전 심사로는 보이지 않고 §7 4단계 불변식 재실측에서만 드러났다.
  라운드_상한이 1로 고정돼 다음 라운드로 회수할 수 없는 조건에서, 결함이
  이번 라운드가 이미 편집 중인 산출물 자신의 자기 정합 버그로 좁혀지면
  새 DAG 행을 열지 않고 §8 자체 처리로 그 라운드 안에서 직접 닫는 것이
  과대응 방지 원칙과 §3 지향(값싼 라운드 반복, 산출물이 목적에서 멀어지지
  않음)에 부합한다.
- M-0019·M-0021의 산출물/정본 분할이 이번까지 세 번째 재사용됐다. 코드
  검증런이 산출물과 함께 그 코드를 낳은 작업자 보고를 참조할 때 반복되는
  구조적 패턴임이 더 굳어졌다.
- Windows 저장소의 `core.autocrlf`가 앵커(라운드 1 시작 전 사본)와 이후
  워킹트리 파일의 줄바꿈 표시를 다르게 남겨, 원시 `diff -u` 대조가 내용과
  무관한 전행 변경으로 보였다. `git diff`(정규화 대조)로 다시 보면 실제
  변경은 의도한 두세 줄뿐이었다. 이 저장소에서 앵커 대조는 `git diff`로
  하고 원시 파일 바이트 대조에 의존하지 않아야 한다.

## 작업 너머 시사점

verify-rounds SKILL.md §7 4단계의 "불변식 재실측이 §8 신호 6이면 올린다"
조항은 자체 처리 결과(수정 방향까지 확정)의 서식을 명시하지
않는다. 이번엔 §8 「회신 처리」의 신호 6 갈래("동결문을 고치라")가 이
사례(동결문이 아니라 산출물 자신의 결함)에 정확히 맞지 않아 판단으로
메웠다. 신호 6의 하위 갈래로 "산출물 자기 정합 결함 — 라운드 안에서 직접
수정"을 추가하는 것이 dream 후보다. L-0016(위임 파이프라인 운영)·
L-0019(do-dag 실행 체제)가 연결 후보다.
