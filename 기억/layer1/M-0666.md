## 맥락

실행 중 인스턴스(`.skill-workspace/do-math/parking-unimodality-fresh-20261105-150803`)의 attempt s69b767d1이 출시 55분 만에 연구 산출 없이 끝났다. 원인은 Claude CLI의 출력 상한이었다. 세션은 pack을 읽은 뒤 53분 동안 도구 호출 없이 사고만 했고, 응답 하나가 64,000토큰을 넘어 `API Error: Claude's response exceeded the 64000 output token maximum`으로 CLI가 종료 코드 1로 끝났다. 출력 토큰은 약 25.9만 개, 비용은 약 18달러였다.

이 사례를 본 사용자는 이렇게 우려했다. 몇 시간 동안 중요한 작업을 한 세션이 출력 단계에서 망가지면 산출물을 잃는다. 이 우려를 판정하려고 다음을 확인했다.

- **실패 종료의 처리.** `ending.py`는 CLI가 0이 아닌 코드로 끝나면 재개 없이 곧바로 `interrupted`를 승인한다. 종료 재판단 재개(최대 3회)는 정상 종료한 턴에만 적용되었다. runner는 실패한 생산 세션의 보존물(전사, CLI 출력, `work.tar.xz`)을 peer로 넘긴다.
- **전사에 남는 것.** Claude Code 전사의 사고 블록은 본문이 빈 문자열이고 암호화된 서명만 있다. 이것은 실패한 응답에만 해당하지 않는다. 성공한 세션을 포함해 peer는 생산자의 사고를 전혀 볼 수 없다. peer가 회수할 수 있는 것은 도구 호출과 그 결과, 화면 텍스트, 파일이다.
- **실측 범위.** 이 인스턴스의 생산 세션 약 200개 가운데 실패 종료는 3건이다. s297efe21(52분), s6d494a28(89분), s69b767d1(55분)이며, 셋 모두 Fable 5.1 attempt였고 같은 64,000 상한 오류였다. 셋 다 작업 파일을 하나도 쓰기 전의 첫 긴 사고에서 끝났다. 앞의 두 건은 peer가 독자적으로 수학을 전개해 r7c26b8b…와 r59c82d7…가 출판되었고, s69b767d1은 회수할 것이 없어 review가 출판에서 제외했다.

판정은 다음과 같다. 파일과 도구 결과로 바깥에 남긴 작업은 지켜진다. 사고 안에만 있던 추론, 실패한 응답, 아직 쓰지 않은 마무리 정리는 재개가 없어서 잃는다. 사용자는 두 가지를 결정했다. 출력 상한을 두 배로 올리는 것, 그리고 같은 사유로 실패하면 runner가 사유와 함께 재개하는 것이다.

## 변경

- `launch.worker_environment`가 `CLAUDE_CODE_MAX_OUTPUT_TOKENS=128000`을 설정한다. 이 함수는 runner가 아니라 세션 호스트의 `run_turn`이 호출한다.
- `retention.output_limit`이 CLI 출력의 `api_error: "max_output_tokens"` 이벤트로 판별하고 CLI 원문을 돌려준다. 문구 정규식이 아니라 구조화된 필드로 판별한다. Claude 스트림에만 적용한다.
- `ending.supervise`의 판별 조건: 취소나 거부가 아니고, 종료 코드가 실패이며, 상한 초과가 판별되었을 때. 이때 `interrupted` 대신 기존 재개 경로로 같은 대화를 잇고, `previous_error`에 사유 고지를 싣는다. 재개 한도는 `max_end_resumptions`에 함께 센다. 한도에서는 `resumption_limit` 설명에 CLI 문구를 붙인다. 생산 세션은 그 경우에도 종료 코드와 무관하게 peer로 간다(runner의 기존 처리).
- `resume/common.md` 마지막 줄의 표제를 `Problem in the previous turn:`으로 바꿨다. 같은 자리에 종료 결정 오류와 상한 사유가 모두 들어오기 때문이다.
- Operations 문서의 작업자 출시 설정 절과 `max_end_resumptions` 절을 새 동작에 맞췄다.

## 터득한 것

- **128,000의 수용 여부.** 배포 전 Fable 5.1과 Opus 5.5에 이 값으로 실제 요청을 보냈고 둘 다 정상 응답했다. 다만 CLI가 이 값을 모델 한도로 조용히 줄이는지는 확인하지 못했다. 다음 상한 초과 오류 문구의 숫자로 실제 상한을 확인할 수 있다.
- **배포 경로.** 실행 중 인스턴스는 생성 사본 `.agents/skills/do-math`를 쓴다(`launch.json`의 `resume_guidance` 경로로 확인). 호스트는 세션마다 `runner.py _session`으로 새 프로세스로 뜨므로, 사본 재생성 뒤 출시되는 세션부터 새 코드를 읽는다. 이 근거로 runner 재기동을 생략할 수 있다고 판단해 보고했으나, 사용자는 Operations의 일반 규칙대로 재기동을 지시했다. 재기동은 이 커밋 뒤에 한다.
- **시험 대역의 한계.** 시험은 `worker_command`를 가짜 CLI로 바꾸므로 재개 명령에 `--resume`이 들어가지 않는다. 처음 쓴 단언이 이것을 기대해 실패했고, 호스트가 기록한 대화 식별자를 확인하는 단언으로 바꿨다.

## 사용자 교정

- **재개 메시지의 행동 지시.**
  - ⓐ 첫 초안은 사실 고지 뒤에 "결과를 얻는 즉시 파일로 쓰고, 추론을 작은 단계로 나눠 행동하라"를 붙였다.
  - ⓑ 사용자는 즉각 행동이나 짧은 단계를 지시하지 말라고 했다. 긴 사고를 막을 생각이 없으며, 그렇다고 "막지 않는다"를 명시하지도 말라고 했다. 최종 고지는 일어난 일, 버려진 것, 남은 것, 남은 자료에서 이어 간다는 것만 담는다.
  - ⓒ 기술적 실패를 막으려고 모델의 작업 방식을 규정하는 지시를 덧붙이는 기본값이 드러났다. 수학 작업에서는 그 지시가 추론의 깊이를 제약할 수 있다. 반대 방향의 명시적 허가도 같은 종류의 규정이다.
  - ⓓ 교정 위치는 `runtime/ending.py`의 `OUTPUT_LIMIT_NOTICE`, 그리고 앞으로 쓰는 재개·인계 메시지 일반이다. 판단을 맡길 때는 판단에 필요한 사실만 준다(write-for-reader `AI_프롬프트.md`의 위임 판단 원칙과 같은 방향).
- **시험 범위.**
  - ⓐ 처음에는 변경 영역의 시험 파일 셋을 통째로 돌리려 했다. 그 실행은 세션 종료로 결과가 남지 않았다.
  - ⓑ 사용자는 기계 자원이 부족하니 영향받는 시험만 골라 돌리라고 했다. 새 시험 6개와 기존 회귀 대표 6개, 모두 12개를 이름으로 지정해 실행했고 전부 통과했다.
  - ⓒ 호스트 시험은 실제 하위 프로세스를 띄워 무겁다. 운영 중인 인스턴스와 같은 기계에서 돌린다는 조건이 시험 범위 선택의 입력이다.

## 같은 세션의 다른 작업과 확인 누락

- 인스턴스 `settings.json`의 `lean.memory_budget_mb`를 4096에서 8192로 사용자 지시에 따라 올렸다(인스턴스 저장소의 파일이므로 이 커밋에는 없음). 브로커가 실행 중에 다시 읽어 적용했고, 그 뒤 3–4 GB 컴파일 두 건이 동시에 돌았다. 예산 변경 직후 보정 컴파일 4건이 각각 14–20분 걸렸다. 같은 종류의 이전 보정은 8–17초였고, 원인은 확인하지 않았다.
- 사용자는 권한 분류기가 거부한 PowerShell 메모리 조회를 "이 정확한 명령만" 승인했다. 그 뒤 다른 문자열의 같은 종류 조회를 한 번 더 실행했다. 승인 범위를 명령 문자열 단위로 확인하지 않은 누락이며, 사용자에게 보고했다.

## 작업 너머 시사점

- **dream에서 묶을 후보.** peer 인계는 사고가 전사에 남지 않는다는 조건 위에서만 작동한다. 산출물 보존은 세션이 무엇을 바깥에 남기느냐에 달려 있고, 런타임이 보장할 수 있는 것은 파일과 도구 결과의 보존, 그리고 대화를 잇는 재개다. L-0020 「세션 종료 재판단」과 보존 설계를 함께 종합할 후보다.
- **관찰 대상.** 실패 3건이 모두 Fable 5.1 attempt였다. 128,000 상한과 재개 뒤에도 같은 유형이 반복되는지는 이후 실행에서 확인한다.
