## 맥락

사용자는 [[M-0348]]의 검사 경량화에 이어 do-math 나머지 영역의 경량화를 지시했다. 목표는 코드·논리의 복잡성, 운영 비용, 문제 발생 여지를 줄이는 것이고, 특히 이음새 중복(A가 Aab를, B가 Bab를 따로 구현하고 둘이 같기를 기대하는 구조)을 하나의 정의로 없애는 것이었다. 사용자는 검사 위치 원칙도 정했다. 정확성 조건은 공유 검사 함수 하나로 정의하고, 생산자가 제출 전에 같은 함수로 스스로 확인해 고치며, 수신자는 같은 함수로 수락·반환한다.

진행 순서는 다음과 같았다. gp-opus-high 8기가 영역별(ENG·RUN·STO·REV·RES·IO·OPS·TST)로 조사해 후보 157건과 보존 판정 80건을 냈다. 통합자가 이음새 단위로 합쳐 설계 문서 `docs/do-math/경량화-설계-2026-09-26.md`를 썼다. 이어서 커널 단계(제품 커널과 시험 기반, 병렬 2기), 그룹 A~F 병렬 구현, 통합 브랜치 `r2-int` 병합, 그룹 간 이음새 정리, 문서 단계를 거쳐 main에 스쿼시했다. 조사 파일 8개와 단계별 결과 파일(`결과-*.md`)은 `임시/경량화-조사-2026-09-26/`에 있으며, 설계 문서가 좌표의 정본으로 가리키므로 이 커밋에 `git add -f`로 함께 추적한다.

사용자 결정은 다음과 같다.

- 결정 1: 이전 연구 인스턴스는 모두 삭제 대상이다. 호환 계층 없이 저장 계약을 `do-math-state/6`으로 교체했다. 삭제 전 조사에서 `DoMath-*` 예약 작업 8개 중 6개가 옛 인스턴스를 2시간마다 점검·기동하고 있었다. 스킬 파일을 바꾸면 설치 복구 AI를 부를 수 있어 먼저 비활성화했고, 사용자 승인 뒤 연구 인스턴스 폴더 10개(`.skill-workspace/` 아래 nat-add-zero-*, parking-unimodality-*)와 예약 작업 8개를 지웠다. 추적 문서 약 13개와 기억 노드 10여 개가 그 폴더의 원 로그를 가리키던 참조는 이제 원본이 없는 역사 기록이다. 툴체인(`do-math-toolchains/`)은 보존했다.
- 결정 3: 생산자가 없는 관찰 출처 `execution_events`·`adapter_active_intervals`와 연산자 `active_duration_gte`·`event_recorded`를 제거했다. 사용자는 제거·추가를 정하기 전에 두 신호의 목적과 역할을 물었다. 원 설계 12.1.1절에서 두 신호는 작업자가 자기 점검 시점을 연구 진행 단위로 정하게 하는 트리거 어휘였다. 그러나 실제 Codex·Claude stdout 4건에 최상위 `id`·`counters`·`active_duration_ms`가 없었고, 한 CLI 세션 안의 활성 시간은 running 이후 경과 시간과 구별되지 않았다(`구현자-결정과-변명.md` 5.5절이 같은 이름·다른 시간 문제를 이미 기록). 카운터·반복 수는 체크포인트 출처로 남는다.
- 결정 4: 모델 동시성 예산은 작업 풀 하나로 두고, 운영 역할(research_preparation, research_plan, operational_review, intent_interpretation, maintenance, recovery)은 예약 없이 역할별 지정 모델로 배정한다. 이 결정은 L-0020의 운영 슬롯·교착 항목을 뒤집는다. 운영이 슬롯을 기다리지 않으므로 그 교착 유형은 구조적으로 사라진다. 그룹 A가 동시 실행 상한이 구조적으로 없는 운영 경로 셋(사용자 입력마다의 intent_interpretation, `kind_definitions` 항목마다의 maintenance, 실패 계보마다의 비live operational_review)을 보고했고, 사용자는 상한을 두지 않기로 했다. 호스트 자원 한도는 유지한다.
- 결정 5: 문서의 수치는 정본 한 곳(`references/CLI-실행-계약.md`의 설정 목록 `#config-list`, `references/모델과-실행예산.md`의 모델 표)에만 두고 나머지는 링크로 바꿨다.
- 결정 6: `sync_activity_wait`, `requeue_recovered_execution`, `probe_codex.py`, `probe_native_isolation.py`를 삭제했다.
- RES-09: 지식 변경의 영향 폐포가 basis_refs·authority_refs·profile_refs까지 포함하도록 참조 필드 정본을 하나로 뒀다.
- 시험: 구현·통합 단계에서 시험을 실행하지 않았다(사용자 결정). 확인은 `py_compile`, 제품 모듈 77개와 시험 모듈 137개의 import, 미러 `--check`, `probe_cli --skill-only`뿐이다. 동작 검증은 시험 방식을 다시 설계한 뒤 별도 작업으로 한다.

## 터득한 것

**작업자 계약에 사용자 결정을 보류할 조건을 넣지 않는다.** 통합자가 사용자에게 "운영 동시 실행 상한을 확인하고 상한 없는 경로가 있으면 보고한다"고 제안해 승인받았다. 그런데 설계 문서와 그룹 A 파견문에는 "구현하지 말고 반환한다"로 옮겼다. 사용자가 이를 지적했고, 같은 성격의 조항이 둘 더 있었다. 하나는 "조사 전제가 원문과 다르면 구현하지 않아도 된다"는 예외가 사용자 결정 항목에도 걸린 것이다. 다른 하나는 "공유 정의가 커널에 없으면 만들지 말고 반환"이 구현 중단을 허용한 것이다. ⓐ 거부된 기본값: 확인 결과나 전제 차이를 작업자가 구현 보류의 근거로 쓸 수 있는 계약. ⓑ 선호된 교정: 결정 항목은 결과를 반드시 구현하고, 원문이 조사와 다르면 원문에 맞는 방법으로 같은 결과를 내어 보고하며, "구현하지 않음"은 이미 고쳐져 할 일이 없음을 입증한 경우로 한정한다. 공유 정의가 없으면 소유 모듈에 하나만 만들고 계속한다. ⓒ 편향: 위험을 줄이려는 안전장치를 넣으면서 그 안전장치가 결정 권한을 작업자에게 옮긴다는 점을 확인하지 않았다. ⓓ offset: 파견문과 설계의 "확인"은 정보 수집으로만 쓰고, 조건부 구현은 통합자가 설계한 기술 조건(예: ENG-24의 입력 동등성)에만 둔다. 사용자는 이어서 작업자가 범위를 임의로 축소하지 않게 하라고 지시했고, 작업량·난도·시간·작아 보이는 실익은 축소 사유가 아니라는 규정을 설계 3.2절과 모든 파견문에 넣었다.

**시험 반복의 규모와 원인.** 커널 단계 두 작업자의 실행 보고서 17개를 합치면 시험 실행이 약 2,177건이었다(unit·integration 전체 약 1,830건 이상). 캐시 적중은 0이었다. 원인은 다음과 같다.
- 결과 캐시의 공유 키가 제품 트리 전체라, 제품 파일 하나만 고쳐도 모든 항목이 무효가 된다. 고치고 시험하는 반복에서는 캐시가 한 번도 쓰이지 못했다.
- 작업자가 하위 작업자에게 파일을 나눠 고치게 해, 실행 중 입력 변경으로 캐시가 기록되지 않았다.
- 공유 모듈을 고친 작업자가 400건 안팎의 묶음을 반복했고, 알려진 기준선을 stash로 다시 확인했다.
- 넓은 회귀를 통합 단계와 중복했다.

통합자는 변경 영향 선택(`run_tests.py --affected`)을 추가했다. 그러나 사용자가 지금은 시험 없이 개발만 하라며 제거를 지시했고, 시험 개선은 다음 작업에서 제대로 다시 한다고 했다. 캐시 키를 제품 모듈 단위로 쪼개는 방안은 대부분의 시험이 `engine.py`를 거쳐 제품 전체를 import해 실익이 작다고 판단했다.

**설계 조사의 전제가 여러 번 틀렸다.** 결과 파일들이 기록한 예는 다음과 같다.
- ENG-13: 저장 계약이 이미 전역 ID 유일성을 검사했다.
- OPS-08: 두 운영 문서 목록은 사본이 아니라 서로 다른 집합이었다. 합치면 README가 엔진 manifest에 들어가 실행 중 연구가 정지한다.
- ENG-24: 거버넌스 투영과 원 인스턴스는 판정이 같지 않았다.
- TST-03: 제품 `_controls`는 무동작이 아니었다.
- 예약 작업이 PowerShell·Python에 따로 구현됐다는 파견문 전제도 틀렸다. 실제로 겹치는 것은 인자 계약이었다.

조사는 후보 발견에는 유효했지만, 구현자가 원문으로 다시 확인해야 했다.

**병합 비용의 원천.** 그룹 B가 `record_schemas/domains.py`를 지우고 스키마를 `schemas.py` 한 파일에 합쳤다. 그 결과 A·C·D의 `domains.py` 변경을 매 병합마다 `schemas.py`로 옮겨야 했다. 그룹 A 병합은 14개 파일이 충돌해 전담 작업자에게 맡겼다. 여러 그룹이 공유하는 스키마 파일의 구조 변경은 커널 단계에서 먼저 했어야 병합 비용이 작다. Windows에서 파이썬으로 충돌을 풀 때 `open(..., 'w')`는 줄 끝을 CRLF로 바꾼다. 이후 쓰기는 `newline=''`로 했다.

**Codex final 대조의 실측.** 그룹 E가 IO-05로 Codex 일반 수집에 `final.txt`와 마지막 `agent_message`의 대조를 새로 넣었다. 보존된 실제 Codex 실행 5건(메시지가 여러 개인 2건 포함)에서 모두 일치했고, 모두 `turn.completed`로 끝났다. 표본 5건이라 전 출력에 대한 보증은 아니다.

**응답 중단.** 이 세션에서 여러 응답이 안전 분류기로 중단됐다. 중단 뒤 파일 쓰기 내용이 문장 중간에서 잘리는 일이 이어져, 설계 문서를 여러 번 나눠 다시 썼다. 사용자는 두 번 이것이 reasoning extraction인지 물었다. 통합자는 결론·근거를 담은 산출물이지 추론 과정의 재현이 아니라고 판단했고, 사용자는 그 판단대로 계속 진행하라고 했다. 분류기의 반응 원인은 전달받지 못해 확인되지 않았다.

## 남은 위험과 진입점

실행하지 않아 확인하지 못한 위험은 각 결과 파일의 4절과 5.2절에 있다. 먼저 볼 것은 다음 넷이다.
- 그룹 B가 손으로 합친 `schemas.py`(약 500행)의 필드 누락·중복. manifest 대조를 할 수 없었다.
- `validate_task_contract`가 저장 과제 스키마 전체를 적용하게 되어 손으로 만든 과제 dict를 쓰는 시험이 거부될 가능성.
- 모델에 전달하는 스키마의 새 키워드(`pattern`, `enum`, `anyOf`+null, `minItems`/`maxItems`)를 공급자 CLI가 받아들이는지.
- `_ACTION`에서 지운 필드 16개를 동적으로 넣는 경로가 남았는지.

통합 브랜치와 worktree(`C:/math-worktrees/r2-*`)와 시험 보고서(`C:/math-worktrees/reports/`)는 저장소 밖 로컬 자료다. 이음새의 최종 정본 목록은 `docs/do-math/검사-경량화-이음새-계약.md` 11절(S10)이다.
