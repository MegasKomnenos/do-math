## 맥락

연속 개발 phase 010은 host T5 연결과 읽기 한도 조사를 독립 수행했다. manager는 두 보고서의 형식 검사와 현재 파일·실제 실행 자료를 대조했다. host는 정본과 미러에서 각각 3건이 통과했지만 관련 61건에는 실패 1건과 오류 1건이 남았다. 읽기 조사는 완료했지만, 실제 운전 프로필과 원문의 출력 byte 상한이 확정되지 않아 요구 충족으로 판정할 수 없었다.

새 host의 실제 취소 성공은 기존 Calls 취소 시험을 대체하지 않았다. 기존 시험은 필수 clock/environment가 빠져 실제 Job을 시작하지 못했고, 반환된 오류 dict에 tuple 인덱스를 적용하면서 KeyError로 원인을 가렸다. 전건 smell 검사도 문서·복원 시험의 네 포괄적 오류 단언을 드러냈다. 앞선 문서 관련 선택의 성공과 이번 전건 실패는 검사 모집단이 달랐다. phase 011에는 현 실포트 인자와 정확한 반려 단언, 구간 읽기 문구를 한정 수리하도록 배정했다. 전건 검사가 다른 수정 파일을 읽고 미러 생성·캐시도 공유하므로 하나의 task가 소유한다.

## 판단에 남긴 조건

읽기 도구는 끝부분을 보존하면서 중간을 생략했다. 끝표지 뒤부터 이어 읽으라는 해석으로는 누락을 회수할 수 없다. 개별 명령의 반환이 온전해도 합산 도구 출력에서 다시 잘릴 수 있으므로 두 계층을 구별해야 한다. phase 011은 온전히 받은 연속 구간과 모든 공백의 회수를 문구에 반영한다. 파일 해시, exit 0, 끝표지 하나는 모델에 도달한 전문을 입증하지 않는다. 수신 전문도 독해·준수의 증명은 아니다.

Claude 설치 코드의 token 기본값과 입력 byte guard는 출력 byte 상한을 제공하지 않는다. manager는 요구 단위의 변경 여부를 사용자에게 상신했고 답변 전에는 기존 기준과 미충족을 유지했다. 현재 개발 task의 도구를 제품 operator로 자동 지정하지 않았다. 이 결정과 독립적인 수리는 계속할 수 있어 성공 종료나 빈 조사 phase로 바꾸지 않았다.

manager의 첫 사본 검산은 비용 캐시까지 시작 해시와 같다고 가정해 실패했다. manifest가 명시한 캐시 예외를 확인하니 976개 중 975개 비캐시 파일만 시작과 같았다. 원 보고는 바꾸지 않고 공용 판단을 그 범위로 한정했다. 소스와 실행 비용 캐시를 구분해야 시작 판본 재현의 주장을 정확히 보존할 수 있다.

## 보존과 후속 책임

진입점은 추적하는 `docs/do-math/continuous-development-2026-10-13/phases/010/manager.json`, `manager-evidence/review.md`, `verification.json`, `preservation.json`과 011 objective다. `raw-evidence.zip`은 task 원자료와 현재 제품 변경 14개의 바이트를 보존하며 자동 복원 지시가 아니다. 일부 원자료는 압축파일로만 추적하고, 106 MiB의 재현 사본과 stage/commit 행정 수신은 로컬 보관이어서 정리로 사라질 수 있다. 정확한 압축 항목과 해시는 preservation.json에 있다.

host 제품 변경은 011의 관련 회귀를 검수한 뒤 마감한다. 이번 커밋은 관리 기록·선별 원근거·압축파일·다음 배정과 이 기억 노드만 포함한다. G4~G6의 최종 전체 검증, 나머지 G7 실연쇄, 문서·의미 질문과 G8 review는 남는다.
