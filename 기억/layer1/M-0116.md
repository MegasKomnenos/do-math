## 맥락

사용자가 통합-설계만 읽고 네 질문을 모든 역할·상호작용·주체에 던지라고 지시했다. 제출 전 결정론 자기 검사의 존재, 폐기 뒤 피드백 소실로 인한 교착, 실익 없는 처벌형 계약, 비현실적으로 엄격한 절차의 넷이다. 발견은 열한 건이었고 두 검증 에이전트가 원문 행 번호로 반박 시도해 확인·부분 확인으로 닫았다. 핵심은 포트폴리오 현재성 검사가 controller OID를 비교해 문면상 어떤 선택도 적용될 수 없다는 것, 운영 점검이 run OID 동일을 요구해 활동 중인 작업자에 닿지 않는다는 것, 작업자가 낸 관찰 조건 세대가 깨지면 의무가 열리지 않아 고칠 길이 없다는 것, packet이 무한히 자라 차단에서 회복할 절차가 없다는 것이었다.

그 뒤 사용자가 형식의 철학을 정리했고 그것을 `docs/형식과-절차.md`로 저작했다. 형식은 처벌이 아니라 전달이며, 생산자는 수신자의 검사기를 같은 판본으로 받고, 검사는 전제 확인이며, 수리 권한은 능력이 아니라 정보와 권한으로 가르고, 흔적은 도구가 남기며, 공유 스크립트는 소유자가 고치고, 차단은 마지막이다. 이 세션에서 낸 보완 넷이 그 문서의 일곱째부터 열째 원칙이 됐다.

해결책은 세 번 썼다. 첫 두 번은 사용자 지시로 원문을 다시 열지 않고 기억으로 썼고, 존재 주장 5건과 이름 14건이 틀렸다. 검사기가 규칙 ID를 이미 낸다, 메인 세션이 heartbeat마다 상태 검사를 돌린다, 감독기가 현재 OID 재시도를 이미 쓴다 같은 문장과 `tool_defect`·`packet_overflow`·`reconciliation_required` 같은 코드 표기 이름이다. 사용자가 두 차례 지적했고, 그 사이 원문이 두 커밋으로 바뀌어 기억은 낡기까지 했다. 최종 적용은 원문을 열고 절 63자리를 편집한 뒤 정합성 감사와 시간선 적대 검증을 각각 파견하고, 결함 23건을 고친 뒤 재검증으로 10건을 더 잡아 고쳤다. 검증 에이전트는 API 과부하로 한 번 중단돼 재파견했다. 편집 대상은 통합-설계, 루트 CONTEXT.md의 보편 정의 여섯 항목, wayfinder 컨텍스트의 packet 한 줄이다. 후보 목차만으로 한도를 넘는 경우는 사용자가 없다고 판단해 뺐다.

## 터득한 것

- 세대당 의무가 하나만 열리는 규칙 아래에서는 「거부된 세대 대신 직전 세대를 유지한다」가 교착이다. 직전 세대의 의무는 이미 소비돼 새 의무가 열리지 않는다. 해법은 직전 세대의 조건을 바이트 그대로 복사해 새 ID로 활성화하는 것이며, 도래했던 조건이 여전히 도래 상태라 다음 평가가 새 의무를 연다. `docs/형식과-절차.md` 2.3.2절의 처방 문장 「이전 조건들은 시계를 계속 돌리므로」는 같은 오류를 담고 있어 정정이 필요하다. 사용자에게 보고했고 그 문서는 고치지 않았다.
- 결정론 사례 ID에 정상 운전 중 계속 바뀌는 상태 OID를 넣으면 재발동이 매번 새 사례가 된다. 기준은 판정이 기댄 것이어야 하며 실행 사례에는 관찰 조건 세대가 그것이다. 사본 연쇄는 `copied_from`을 거슬러 원 세대로 접어야 같은 사례에 쌓인다. 검증자가 이 접힘 없이는 거부마다 새 사례가 열린다는 것을 시간선으로 잡았다.
- 시간선 추적이 잡고 정합성 감사가 못 잡은 결함 유형 넷. 커밋 안에 자기 OID를 적는 순환(후속 씨앗의 `resume_from`은 ref 이름만 가져야 한다), 예외를 기계가 구별할 표지가 없어 절차가 막히는 자리(`precedent_exempt`), 전이표 밖 전이(`pause_required/working`에서 `revoked`로 가는 강제 무효화), 부수 효과 금지와 처분 적용이 서로를 요구하는 영구 봉쇄 쌍(`reconciliation=required`와 종료 장벽). 형식과-절차 2.5절 7단계의 시간선 추적은 규칙별 점검표가 대신하지 못한다.
- 존재 주장은 원문을 연 채로만 쓴다. 발견을 낼 때는 문장을 나란히 놓아 정확했고, 방안을 낼 때는 기억에서 꺼내 틀렸다. 같은 세션, 같은 문서, 같은 모델이다. 차이는 대조 여부뿐이었다.
- 편집 중에 검증 에이전트를 병행 파견하면 에이전트가 읽는 파일이 도중에 바뀐다. 편집을 모두 끝낸 뒤 파견하고, 결과가 오면 다음 편집을 하는 순서가 맞다. 세 라운드의 결함 수는 15와 8, 10, 8로 수렴했다.
- 사용자 결정 자리 셋을 추천으로 확정했다. 이의 회차 상한에서 갈리면 승인 이의로 닫는 것, heartbeat에 상태 검사·보고 단계를 두는 것, 창과 상한의 기본값 3과 10이다. 되돌리기 쉬운 값들이며 보고에 표시했다.

## 작업 너머 시사점

- 형식과-절차 2.4절의 네 질문 검수법은 실제로 결함을 냈고, 2.3절의 열 가지 모양은 이 세션의 발견에서 추출된 것이다. 검수·해결·적용의 세 단계 모두에 「이미 있다」 검증이 붙어야 하며, 3.5절의 검증 비대칭은 이 세션이 실측이다.
- 통합-설계 편집은 삼문서 정합에 닿는다. CONTEXT.md의 감시 기록 원장, 관찰 조건 세대, 관찰 응답 조건, 운영 사례, 운영 점검 처분, 점검 발동 조건 여섯 항목을 함께 고쳤다. 다음 삼문서 검증런은 이 여섯 항목과 wayfinder 컨텍스트 45행을 동결문의 기준으로 삼아야 한다.
- 남은 일. `docs/형식과-절차.md` 2.3.2절 처방 문장 정정. 3라운드 뒤 국소 수정 8건은 세션 자체 대조만 거쳤다. 새 도구 넷과 스키마 판본 상승 스무 건은 27절의 구현 완료 조건에 들어가며 아직 구현되지 않았다.
- dream에서 묶을 후보: M-0112부터 M-0115까지가 「큰 확정은 편집자 직접 반영, 검증런은 반영 결과의 검사 도구」를 세웠고, 이 노드는 설계 결함 수리에서도 같은 경로가 맞았음을 더한다. 여기에 「방안의 존재 주장은 발견과 같은 검증을 받는다」와 「시간선 추적은 점검표와 다른 결함을 잡는다」를 잇는다.
