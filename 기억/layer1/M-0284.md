## 완료 범위와 결과

수행계획서를 전면 첨삭한 뒤 사용자의 추가 지적에 따라 문장과 문단의 실제 의미를 다시 검토했다. 문법적으로 자연스럽게 보이는 문장도 분석 대상을 잘못 가리키거나 설명의 범위를 바꿀 수 있었다. 사용자가 제시한 한 사례를 비슷한 표현의 검색 문제로 좁힌 판단도 교정했다. 최종본을 사용자가 수용한 뒤 원자료와 중간 산출물을 모아 보관했다.

최종 산출물은 [수행계획서 HWP](../../임시/작성작업/수행계획서_전문첨삭.hwp)와 [PDF](../../임시/작성작업/수행계획서_전문첨삭.pdf)다. 두 문서 모두 11쪽이다. 한글에서 내보낸 HWPX의 최상위 문단 103개에 담긴 본문과 표를 모두 읽었다. PDF는 11쪽의 이미지를 모두 확인했다. 기존 글자 크기와 줄 간격은 유지했다. 이번에 완료한 범위는 수행계획서의 작성·첨삭·검증·정리다. 계획서에 제시된 연구 시스템 구현, 성능 실험, 학회 논문 제출의 완료를 기록한 것은 아니다.

## 공통이해의 회수와 원문 확인

사용자는 문서가 작성된 세션에서 grill-me 공통이해가 확정된 순간까지의 대화를 추출해 읽은 뒤 첨삭하라고 요청했다. [grill-me](../../.agents/skills/grill-me/SKILL.md)는 작성 전 목적·범위·조건을 질문으로 확인하고 사용자의 확인을 받는 인터뷰 스킬이다. 앞선 세션의 원 로그는 `rollout-2026-09-14T23-37-39-01a0a05a-2ba3-72a3-aa67-3f42a05b72bd.jsonl`이다. 최초 요청부터 공통이해 승인까지인 9~476행에서 사용자·어시스턴트 발화 68개를 회수했다. 한국 시간 2026년 9월 14일 23:50:08에 시작해 9월 15일 00:19:36의 사용자 발화 “작성”으로 끝난다. 도구 호출·결과, 내부 추론, 환경·시스템·스킬 주입은 제외했다.

기존 작업 폴더에도 대화 발췌본이 있었지만, 원 세션에서 다시 추출해 발화와 순서가 일치하는지 대조했다. 앞선 세션에서 확정된 내용은 회수한 대화의 사실로 사용했다. 그 세션의 공통이해 확정 이후 작성 과정 전체를 현재 세션에서 직접 수행하거나 전부 읽은 것으로 간주하지 않았다.

첨삭에서 유지한 주요 합의는 다음과 같다.

- 인공지능 전 분야를 대상으로 최근 3년의 주요 논문, 이전의 기초 논문, 최신·보완 서베이를 수집한다. 최근 논문은 중요도 기준으로 선별한다.
- 작업 에이전트가 문헌별 추출 결과와 DB 변경안을 작성한다. 별도로 실행한 검토 에이전트가 이를 원문·기존 DB와 대조하고, 작업 에이전트가 지적을 반영해 수정한다. 검토를 마친 변경안은 하나의 구축 프로그램이 DB에 반영한다. 문헌별 작업은 병렬로 진행한다.
- 사용자는 Codex·Claude Code 같은 기존 실행 환경에 도구와 스킬을 연결한다. 구독과 CLI를 활용하며 별도의 언어 모델 API를 전제로 삼지 않는다.
- 출력은 문서의 용어·개념 목록, 비교할 학술 용어·개념 목록, 수정 제안을 포함한 분석 문서로 구별한다. 첫 목록은 저자가 그 문서에서 사용한 뜻을 보존한다.
- 근거 기반 LLM-as-a-judge 평가와 다른 계열 모델의 표본 재평가를 계획한다. 10월 23일 제출 전에 선정한 문헌 전체로 DB와 시맨틱 레이어를 구축하고 평가를 마치는 것이 목표다. 시스템과 구축 도구는 GitHub에 배포할 계획이다.

실제 HWP와 동반된 추출 TXT의 내용이 다른 부분도 확인했다. 최신 HWP에는 TXT에 반영되지 않은 문장이 있었다. 첨삭 대상 HWP를 한글에서 열어 HWPX로 내보내고, 그 문단과 표를 원문으로 삼았다. 기존 요약이나 추출 파일의 이름만으로 현재 문서와 일치한다고 판단할 수 없었다. 이 사례는 [[L-0005]]의 원문 대조와 [[L-0015]]의 읽기 범위 판단에 연결된다.

## 사용자 교정과 퇴고 방법

### 문장의 실제 분석 대상을 잘못 지칭한 문제

첫 첨삭 이후 사용자는 일부 문장이 어색하거나 지나치게 함축되어 있다고 지적했다. 사례는 “비교의 출발점은 검토할 문서 자체의 의미다”였다. 이 세션의 어시스턴트는 처음에 이를 추상적이고 함축된 표현의 문제로 설명했다. 사용자는 다시 “문서 자체의 의미”를 자세히 읽도록 요청했다.

이 문장은 문서 전체의 내용·주장·취지를 분석 대상으로 읽게 한다. 실제로 비교하려던 대상은 각 용어와 개념이 해당 문서에서 사용된 의미였다. “자체”는 문서를 강조할 뿐 개별 용어와 개념을 지칭하지 않는다. 문장 길이보다 분석 단위를 잘못 표현한 것이 핵심이었다. 이를 “기존 학술 개념과 비교하려면, 먼저 검토할 문서에서 각 용어와 개념을 어떤 뜻으로 사용했는지 파악해야 한다”로 고쳤다.

### 사용자의 사례로 검토 범위를 좁힌 문제

위 문제를 이해한 뒤 이 세션의 어시스턴트는 “문서의 뜻”, “문서 안의 의미 추출” 같은 표현을 다시 찾겠다고 했고 관련 문구를 검색했다. 사용자는 중요한 것은 그 표현들이 아니라, 어떤 문장이나 표현이든 찬찬히 읽었을 때 이상한 내용을 모두 찾아 고치는 것이라고 교정했다.

이에 따라 최종 원고를 첫 페이지부터 표·예시·평가·일정·성과까지 다시 읽었다. 각 문장이 실제로 지칭하는 대상과 행동, 조건, 관계를 해석하고 문단과 계획 전체에 대조했다. 사용자의 사례는 판단 기준을 이해할 근거였으며 다른 문장의 검토 범위를 제한하지 않았다. “문서의 뜻” 같은 낱말을 보편적인 금칙어로 만드는 교훈도 도출하지 않았다.

문장과 문단을 고친 사례는 다음과 같다. 이 목록은 이번 원고에서 관찰한 수정 사례이며, 다른 원고의 검토 범위는 그 글의 실제 내용에서 정한다.

- 필요성 설명에서 관련 문헌을 먼저 찾는다는 문장과 입력 문서의 뜻을 먼저 파악한다는 문장의 순서를 정리했다. 용어의 사용 의미를 파악한 뒤 관련 학술 개념을 찾고 비교하는 흐름으로 재구성했다.
- 같은 개념을 묶는 일과 문헌별 설명을 보존하는 일을 풀어 썼다. 여러 문헌을 하나의 개념 항목에 연결하되 각 문헌의 설명과 출처를 따로 확인하도록 설명했다. 용어의 다른 표현을 묶는 일과 개념 사이의 상하위·부분 관계를 구별했다.
- 비교 예시는 “어떻게 연결되는지 설명한다”는 작업 설명에서 실제 비교 내용으로 바꿨다. 입력 문서는 “모형 전달”을 “큰 모델의 출력 확률을 작은 모델의 학습 목표로 사용하는 방법”으로 정의했다. 이 정의를 보존하고, 지식 증류에는 출력 확률 외에 중간층의 특징을 활용하는 방식도 있다는 범위 차이를 제시했다.
- 평가 순서 편향을 먼저 제시된 답변의 선호로만 좁혀 쓴 문장을 고쳤다. 내용은 같게 두고 순서를 바꿨을 때 판정이 달라지는지 확인하도록 했다.
- 기준에 미달한 답변의 0점과 채점 자료 부족으로 정오를 판단할 수 없는 경우를 구별했다. 평가자 간 점수 불일치 비율은 두 모델이 함께 채점한 표본에서 계산한다는 범위도 명시했다.

교정이 필요한 위치는 최종 원고의 독해와 원자료·합의 대조 단계였다. 문장 작성 원칙을 설명한 사실, 문법적으로 매끄럽다는 인상, 특정 표현의 검색 결과가 그 단계를 대신하지 못했다. 후속 퇴고에서도 실제 독해가 드러낸 결함을 문장·문단·절의 해당 범위에서 고칠 필요가 있다.

## HWP 편집과 검증에서 확인한 사실

### 추출·편집 경로

`extract-documents`의 HWP 추출 명령은 `hwp5html` 실행 파일을 찾지 못해 오류를 출력했지만 프로세스 종료 코드는 0이었다. 생성된 TXT에는 실질적인 본문이 없었다. 종료 코드와 파일 생성만으로 추출 완료를 판단하지 않았다.

한글 자동화 객체를 별도로 생성해 원문을 HWPX로 내보내고, XML의 문단과 표를 수정한 뒤 HWP와 PDF로 저장했다. 작업용 `python_lib`의 pywin32와 Pillow를 재사용했다. pywin32 관련 경로와 DLL 디렉터리를 추가해야 했고, 창 캡처에 쓰는 `win32ui`는 `pythonwin` 경로에 있었다.

한글 자동화의 경고창 처리 설정(`SetMessageBoxMode`)을 적용해도 파일 접근 확인창은 따로 나타났다. 작업을 위해 생성한 한글 프로세스의 확인창과 파일 경로를 직접 확인해 접근을 허용했다. 창 캡처가 일부만 보인 경우에는 프로세스의 DPI 인식을 실제 배율에 맞춰 해결했다. 사용자에게 열려 있던 다른 한글 문서를 닫거나 저장하지 않았다.

### 분량과 배치

첫 페이지 보강에는 수집 범위, 문헌별 병렬 처리와 독립 검토, 구축 결과의 설명을 추가했다. 문장을 줄여 끼워 넣는 대신 필요한 내용과 문단 구성을 정리했다. 최종 PDF에서 첫 페이지의 공백 제외 추출 문자 수는 781자에서 938자로 늘었다. 이 수치는 보강 정도의 기록이며 글의 의미가 타당하다는 증거로 사용하지 않았다.

고정된 표 높이 때문에 요약 표 전체가 다음 페이지로 넘어가 제목만 첫 페이지에 남는 경우가 있었다. 실제 출력 화면을 확인하고 추진배경 행의 사용하지 않는 높이를 줄였다. 내용과 글자 크기·줄 간격은 유지했다. 일정 설명과 Gantt 차트는 함께 배치하고, 앞 절 뒤의 공간을 사용하도록 페이지 나눔을 조정했다. 페이지 수를 맞추기 위해 필요한 설명을 압축하지 않았다.

PDF 페이지 이미지를 읽을 때 본문과 표가 겹친 것처럼 보인 경우도 있었다. 확대 이미지와 PDF의 본문·표 좌표를 대조하니 겹치지 않았다. 그 부분은 결함으로 처리하지 않았다. 지적은 실제 출력에서 확인되어야 한다는 [[L-0001]]의 검증 원칙과 연결된다.

### 저장 검사와 독해의 구별

원본 서식에는 두 쪽 모아찍기 설정이 있었다. 인쇄용 PDF의 장수와 HWP의 문서 쪽수를 구별하고, 확인용 PDF는 문서 한 쪽씩 보이도록 만들었다. 인쇄용 PDF에서 한 문서 쪽만 배치된 마지막 장의 배율과 위치도 확인했다. PDF의 문자와 도형을 유지하여 확인본을 생성했다.

최종 HWP를 저장한 뒤 실제 파일을 다시 열고 HWPX와 PDF를 내보냈다. 저장된 본문이 개정 원문과 같은지 대조하고, PDF에 모든 텍스트 블록이 들어 있는지와 페이지 밖으로 밀린 글자가 없는지 검사했다. 참여인력과 일정의 내용, 기존 문자 서식도 대조했다. 전체 11쪽의 이미지를 읽어 표와 페이지 경계를 확인했다.

이 검사는 저장·변환·배치 과정의 손실을 확인한 것이다. 문장의 의미 검토와 사용자의 수용 여부는 별도의 근거다. PDF의 텍스트가 존재하거나 저장 검사에 통과했다는 사실로 문장 의미의 정확성을 입증하지 않았다. 구체적인 변환·판독 경험은 [[L-0004]]와 함께 이후 기억 종합에서 검토할 후보로 남긴다.

## 보관과 버전 관리

`임시/작성작업/`에는 최종 HWP와 PDF 두 파일만 남겼다. 원자료·중간 판본·추출물·도구 2,265파일, 총 104,919,324바이트는 `임시/보관/수행계획서_2026-09-15/`로 옮겼다. 보관 폴더 안에서는 기존 `임시/` 아래의 상대 경로를 유지했다. 이동 전후 해시를 전건 대조했으며 최종 두 파일의 해시도 유지됐다. 이 정리는 보관 위치의 이동이며 파일 삭제나 디스크 공간 회수를 수행한 것은 아니다.

대화 원문과 최종 검증 자료는 보관 폴더의 `작성작업/전문첨삭_20260915/`에 있다. 이동 목록과 해시 대조 결과는 `_정리기록/이동전_목록.json`과 `이동결과.json`에 남겼다. 최신 편집·렌더링 스크립트와 작업 의존성도 같은 보관 구조에 있다.

보관 폴더는 `.gitignore`로 제외한다. 원자료와 전체 작업 이력은 로컬에만 남으므로 새 체크아웃에서 필요하면 별도로 옮겨야 한다. Git에 남기는 최종 문서와 이 기억 노드는 보관 폴더 없이도 결과와 주요 판단 경위를 이해할 수 있게 구성했다.
