환경 중단 뒤 B127의 unified handle93709가 사라졌다. 실제 CIM 조회에서도 runner/worker가 없고 최종 report.json도 없었다. 실행 메타데이터의 running을 stopped_without_final_report로 정정했다. 중간 보고는39통과·1실패·마지막 running3개이며 전체 종료코드와 중단 원인은 알 수 없다. canonical tracked/untracked969파일과 HEAD는 시작 때와 같았다. 핸들 상실만 보고 실행을 중복 기동하지 않았다.

이전에 보존한 최초 실패는 Git 대역의 update_ref에서 os.replace(lock,ref)의 WinError5였다. 이후 같은 템플릿의 재생성은 실패 캐시 단언을 내므로 최초 stdout traceback과 별도로 보아야 한다. 환경 중단과 그 파일 접근 거부가 같은 원인이라는 근거는 없다. 새 독립 작업은 이 참조 게시의 실패 처리에 한정했다.

fake의 _resolve/ref_oid/update_ref 참조 읽기는 기존 read_bytes_shared를 사용한다. 게시에는 기존 atomic_replace를 재사용하여 WinError5/32/33에서 같은 rename만 유한 재시도한다. 새 timeout이나 전체 CAS 재실행은 추가하지 않았다. 기존 코드는 descriptor를 닫은 뒤 rename이 실패하면 .lock을 남겼다. 이제 published flag로 성공 여부를 구별하여 실패·CAS 불일치에서 소유 lock을 정리하고, 성공 뒤 다음 writer가 만든 lock은 지우지 않는다. 제품 실제 Git·file_io·공유 포트 계약은 바꾸지 않았다. 실제 Git의 비영 exit 반환과 fake의 기존 예외 전파 차이도 이 작업에서 바꾸지 않았다.

읽기 전용 ref로 실제 Windows 교체 거부를 만들었다. 수정 전4개에서 일시 오류가 예외로 끝나고 영구 실패가 lock을 남겨2통과·1실패·1오류였다. 수리 뒤 실제/대역 계약72개 중71개가 통과했고, 나머지는 기존 os.open 텍스트 모드의 CRLF를 LF로 기대한 새 시험의 오류였다. 이를 os.linesep의 정확한 바이트로 고쳐 해당1개만 통과를 확인했다. 실제 Git34개는 처음부터 모두 통과했다. 같은 lock 재시도 중 다른 CAS 거부, 영구 실패 후 후속 update 가능, 성공 직후 다른 writer의 lock 보존을 검사한다.

원래 정확한 ReviewAlphabet을 새 프로세스에서 한 번 실행하여 통과했다. 시험106.422초·묶음111초로 소프트60초 기준을 넘었지만 범위와 단언을 줄이지 않았다. 모든 실행의 changed_during_run은 비어 있다. 이 파일 속성 재현과 단일 흐름 통과가 B127 당시 WinError5의 근본 원인을 입증하지는 않는다.
