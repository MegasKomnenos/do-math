## 맥락

사용자는 do-math를 수정하지 않고 처음부터 다시 설계하기로 결정했다. 이유는 이렇다. 연구 철학은 유지할 가치가 있지만, 그 위에 과설계로 얹힌 형식들이 실제 연구를 거듭 멈췄다. 이번 대화는 grilling 세션으로 진행됐다. 메인 세션이 옛 do-math의 문서 전부(SKILL·README·GLOSSARY·계약 11개·references 10개·이음새 정본·시험 지침)와 L-0020, 10-21 주차 함수 실행 감사 보고서를 읽은 뒤, 결정을 하나씩 물어 실행 계약을 확정했다. 사용자가 그 계약을 승인했다.

확정된 결정과 그 이유는 추적 파일 두 개에 정리돼 있다.
- `.async/do-math-rebuild-20261021/context.md`: 결정과 이유
- `.async/do-math-rebuild-20261021/user-messages.md`: 사용자 원문 전체와 각 답이 응한 질문의 요지

요지는 다음과 같다.
- **목적**: 다섯 가지를 보존한다. 대화 없는 지속 탐구, 지식 축적과 환류, 사람이 읽는 해설이 주 산출물, 독립 검토, 권한 경계다. 학술 후속은 범위에서 뺐다.
- **세션 구조**: 범주는 셋(계획·연구·검토)이고 흐름은 정해져 있다. 작업맥락은 3층(공통요소·작업공통요소·작업특정요소)으로 준다. 세션이 공식 검사 스크립트로 스스로 검사하고 승인해 내면, 실행기가 같은 검사를 다시 돌린다. 검사의 범위는 구조와 참조 실재이며, 목적은 세션 사이의 전달과 해석이다.
- **실행기**: 불변식 열 가지만 지킨다.
- **환경과 기록**: 환경은 있는 그대로 쓴다. 형식 결과에는 `lean --version`만 정보로 남긴다. 기록은 평범한 파일과 Git으로 남긴다. 충돌은 실행 전에 구조로 막는다.
- **운영**: 실행기는 독립 프로세스로 돌고, 죽으면 사람이 다시 띄운다. 공급자 한도에서는 파견을 멈추고 기다린다.
- **CLI와 모델**: Codex와 Claude를 모두 지원한다. 모델은 범주별 기본값에 계획의 과제별 지정을 더한다.
- **완료 기준**: 가짜 세션으로 흐름을 확인하고, 실제 Codex·Claude 세션으로 작은 목표 하나를 무인 완주한다.
- **구축 방식**: async-development가 구현한다. 공용 문서는 메인이 직접 쓴다.

이 커밋은 실행 계약의 (가)안을 집행한다. 옛 `.claude/skills/do-math/` 1,091개 파일을 지웠다. 미러 생성기로 `.agents/skills/do-math/`도 지웠고, 미러 `--check`는 exit 0이었다. 함께 넣은 async-development 기록 폴더에는 공용 문서 셋(context·plan·seams), 사용자 원문, 설정, 빈 queue가 들어 있다. 개발 세션 기동은 이 커밋 뒤에 한다. 옛 구현을 참조할 진입점은 이 커밋의 부모 `4e793d17`다.

삭제 전 `.agents/skills/do-math/`에는 커밋되지 않은 변경이 있었다. 7개 파일, 176행 추가로, codex_stream·model_call·model_runner·observation_transport와 시험에 걸친 수정이며 수정 시각은 10-21 12:25 KST였다. 지우기 전에 이 변경을 `.skill-workspace/backups/agents-do-math-uncommitted-20261021.patch`(309행)로 저장했다. 이 경로는 Git 제외 로컬 보관이라 정리하면 사라질 수 있다. 같은 작업 트리의 graphify와 services/async-development 미커밋 변경은 이 작업과 무관해서 커밋에 넣지 않았다.

## 터득한 것

- **사용자가 정의한 과설계의 경계**: 사용자는 과설계의 예로 두 가지를 직접 들었다. 신뢰 환경을 고정한 뒤 유지 여부를 감시하고 바뀌면 진행을 막는 것, 그리고 기동 때 모든 파일을 해시해 동일성을 대조하는 것이다. 원하는 방향은 "정해진 경로에 있는 것을 있는 그대로 쓴다"였다. 메인이 연구 기록의 봉인·현재성 재검사도 같은 부류인지 묻자, 사용자는 전부 걷어 내되 충돌은 계획 단계에서 막으라고 답했다. 이 기준은 옛 do-math의 장치 다수(신뢰 환경, 지문·manifest, 봉인, 판본 결박, 관찰 규칙, 자기 점검)를 한꺼번에 기각한다.
- **10-21 실패 기전의 공통점**: 실패 기전 A~E는 모두 어떤 위험을 막으려 둔 감시·분류·대조·복구 장치가 스스로 정지 원인이 된 경우였다. 새 설계는 이 문제를 장치 수리가 아니라 구조로 없앤다. 실행기가 CLI 출력에서 한도 신호만 읽게 해 파서 거부 문제(A)를 없앴고, 설치 대조를 두지 않아 재시작 정지(B)를 없앴다.
- **형식 검사의 목적**: 사용자는 형식 검사의 목적을 "세션 사이의 전달·소통과 올바른 해석·처리를 위한 프로토콜 준수"로 정의했다. 실행기의 재검사는 세션이 검사를 빠뜨렸을 때의 대비라고 했다. 이 정의에서 범위 판정이 하나로 도출된다. 받는 쪽의 해석에 필요한 참조 실재는 범위에 들고, Lean 컴파일은 빠진다.
- **async-development를 참고하는 방식**: 사용자는 async-development를 엔진 공유나 골격 복제가 아니라 원리만 참고하라고 했다((다)안). 메인의 추천은 (나)안(같은 골격으로 do-math 전용 실행기를 새로 작성)이었다. 이와 별개로 구축 작업 자체는 async-development로 하라고 지정했다. 참고 대상과 구축 도구가 따로 정해진 것이다.
- **Lean 실측**: `.skill-workspace/do-math-toolchains/mathlib-4.32.0`에서 `lake env lean`으로 `import Mathlib` 파일을 컴파일하니, 캐시가 차가운 상태에서 7분 22초가 걸렸다(exit 0). 작은 완주 목표는 core Lean으로 하도록 context.md에 적었다.
- **공용 문서의 독해 수렴**: write-for-reader 독해 절차는 context.md에서 7회, plan.md에서 3회, seams.md에서 6회 돌았다. 독해가 찾아낸 모호점은 다음과 같다.
  - 축적 지식에 들어간 것과 검토로 인정된 것의 구분
  - 덮어쓰지 않는 기록에서 "고친다"의 뜻
  - 외부 입력 대기의 해제 계기
  - 멈춘 세션 종료와 정지 표시의 구별
  - Lean의 적용 범위
  - 검토의 단위
  - 끝난 세션의 단일 처리 규칙(죽은 세션·한도 세션·사용자가 끝낸 세션 모두 재검사 뒤 반영 또는 실패)
  - 완료 뒤 처리
  
  모두 사용자 결정에서 도출되는 귀결이라 메인이 문서에 명시했다. 독해기는 인용 불일치로 두 번 실패했고, 재실행으로 해결됐다.

## 작업 너머 시사점

- L-0020은 옛 구현의 운영 지식이라 새 do-math에는 대부분 적용되지 않는다. 정정 대기를 남겼다. dream에서 L-0020을 새 구조 기준으로 다시 쓰거나 역사 기록으로 돌릴 후보다.
- dream에서 묶을 후보가 있다. 장치 누적이 정지를 만든다는 이번 진단을 기존 기억과 묶어 종합할 수 있다. 대상은 L-0020의 "내부 제약을 쌓기보다 사용자 요구와 AI 자율 범위를 먼저 나누는 편이 문제를 줄였다"는 항목, 그리고 M-0423의 "국소 실패 연쇄를 멈춤"이다.
