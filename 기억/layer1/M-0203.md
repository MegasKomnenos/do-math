사용자는 남은 학술자료 MCP 구현을 끝까지 이어가라고 지시했다. 최신 지원표·인계·M-0198~0202를 읽고 실제 SDK와 기관 사이트를 재확인했다. APS의 20260912T031559Z-aps-search-mcp.json은 첫 검색·CSV는 성공했지만 페이지 경계는 1건의 partial, 제목 검색은 오류, 문헌은 restricted였다. 현재 total은 37997이었다. 같은 저장 상태를 사용해 문서마다 별도 브라우저 컨텍스트를 만든 20260912T031906Z-aps-context-probe.json도 네 대상에서 403이었다. 이 가설은 생산 구현에 넣지 않았다. Codex·등록 MCP·다른 실행 세션은 조작하지 않았다.

IOP는 접근 확인이 재발했다. 현재 표시된 나무 제품 과제에서 도마 네 개를 판독·선택한 뒤 검사와 Submit을 수행했다. 20260912T031727Z-iop-verification-control.json은 확인 응답과 IOP 기관 호스트 이동을 completed=true로 보존한다. 새 Chrome 컨텍스트의 032001Z·032112Z-iop-chromium-recovery.json은 문헌 10.1088/1367-2630/add557의 본문과 보충자료 페이지를 확보했다. 이 관측만으로 본문·첨부 생산 구현 완료를 선언하지 않는다.

보충 링크를 Sanitizer.url로 정제해 진단 출력하는 과정에서 X-Amz-Signature는 제거됐지만 X-Amz-Credential 값이 남았다. 사용자에게 즉시 알렸다. 원인은 딕셔너리 정제의 secret_fields에는 xamzcredential이 있으나 URL의 _authentication_parameter는 별도 정규식만 검사한 것이다. URL도 기존 정규화된 비밀 필드 집합을 검사하도록 최소 수정했다. 별도 예외 목록을 추가하지 않았다.

합성 값으로 URL·산문·딕셔너리·HTML 링크·인코딩된 경로·fragment의 실패를 먼저 관찰하고 수정 후 공통 235개 검사를 통과했다. 실제 원 링크 한 건에서 자격 필드 1개가 정제 후 0개이며 서명 필드도 0개인 것을 값 출력 없이 재확인했다. 정제된 보고는 data/validation/20260912-iop-signed-url-sanitization.json이다. 이미 표시된 출력의 삭제·원 URL 무효화·전체 과거 산출물 감사는 확인하지 않았다. 이 범위를 검사 통과로 확대하지 않는다.

다음 구현은 접근 가능한 IOP의 원 본문·TeX·그림과 supplementarydata 파일이다. 원 자료는 보호 폴더 .credentials/scholarly-mcp/probes의 두 IOP HTML에 있다. 본문 그림의 src는 1픽셀 자리표시이고 실제 주소는 data-src에 있으므로 clean_html 전에 처리해야 한다. XML 다운로드 제어는 이 표본에서 발견하지 못했다. 다른 자료원의 남은 범위와 공개 API 기준, 별도 계정·이메일 보류는 유지한다. 전체 작업은 진행 중이므로 푸시하지 않는다.
