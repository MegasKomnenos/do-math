## 터득한 것

**작성됐다는 보고와 실물 장부를 대조해야 한다.** 이음매 상신 장부는 시험이 제품 경로를 돌 수 있도록 외부 자원 경계를 주입 가능하게 바꿔야 하는 곳을 모은 목록이다. 진행 원장과 Claude의 보고는 그 장부의 27~29번을 참조했지만 실물 `1f/seams.md`는 26번에서 끝났다. 원본 18598행의 도구 입력과 현재 `scheduled_operator.run_engine`, `probe_cli.run_case`, `formal.toolchain_root`를 대조하여 세 항목을 복구했다. 현재 장부는 CRLF이고 당시 도구 입력은 LF 앵커를 치환하면서 치환 횟수를 검사하지 않았다. 과거 바이트 사본은 없으므로 이것은 누락 원인의 강한 추론이다. 현재 누락 자체는 확정이며, 이번 삽입은 앵커가 정확히 하나인지와 세 번호가 실제로 생겼는지를 확인했다.

**성공한 전체 측정 직후 실행기 변경도 증분 전제를 깨뜨린다.** [[M-0420]]의 전체 T3는 `6d121082`의 실행기를 기록한 저장소를 만들었고, 다음 `9672dbac`이 예산 판정 코드를 바꿨다. `t3_store.plan`은 실행기 blob이 다르면 전체를 다시 측정한다. 따라서 이 저장소를 작업자에게 복사하면 첫 실행부터 증분이라는 안내는 성립하지 않는다. 복사 안내와 재개 기록을 보완했다. 기록된 표식을 수동으로 바꾸지 않았으며 최신 전체 T3는 아직 후속이다.

**실제 경로로 옮겼어도 다른 실패 분기에 대한 단언이 될 수 있다.** knowledge.3의 첫 강도 감사는 18개 중 두 약화를 찾았다. 옛 고정 명령·지문 시험은 검증기 반환의 status가 `failed`일 때 실행 outcome이 `execution_incomplete`인지 확인했다. 새 시험은 명령과 합성 실행 파일이 달라 검증기가 컴파일 전에 `rejected`를 반환한 상황에서만 그 outcome을 단언했다. 별도 실제 failed 배선에는 outcome 단언이 없었다. 교정은 원래 Python 명령·다른 설정 명령·실패 사전·지문·공리를 `_formal_steps`의 실제 준비·수신 단위 시험에 남기고, 작업자 출력 해석으로 나온 failed에도 `formal_status`와 outcome을 정확 비교하게 했다. 산출물 시험에 빠진 승인/config 불일치 입력도 unit과 Sim 양쪽에 복원했다. 감사와 수정 확인은 별도로 보존했다. 교정 검증의 첫 오류는 내가 toolchain 키를 `command`로 쓴 것이었고, 실제 계약의 `configured_command`로 고쳐 해당 시험을 다시 통과시켰다.

**실제 OS 경로를 작은 입력으로 검사할 수 있었다.** 옛 실행기의 성공 JSON·native exit 시험은 Job·대기·종료 코드를 패치했다. 새 시험은 실제 자식이 성공 보고서를 기록한 뒤 atexit에서 종료 코드 7로 끝나게 한다. 성공 JSON 원본과 부모 최종 실패를 함께 확인하여 적재 실패를 잘못된 양성으로 셈하지 않는다. 실행기 11개와 submission.3의 이동 11개는 전수 강도 감사에서 모두 유지였다.

**출력 위치가 시험의 탐색 전제를 바꿨다.** 내가 병렬 T2의 출력 폴더를 메인 작업 트리 `C:\math` 아래에 두자 작업자의 임시 폴더도 그 아래에 만들어져, scholarly 홈 설정 시험 둘이 상위의 실제 프로젝트 설정을 골랐다. 첫 통합 T2는 일반 실패 둘과 340.8초를 기록했다. 제품은 상위 탐색 규칙대로 동작했고 시험은 설정 없는 조상 경로를 전제했다. 제품이나 단언을 바꾸지 않고 기존 실행과 같은 사용자 임시 폴더에 출력을 두어 다시 돌리자 둘도 통과했다. 최종 T2는 일반 통과 1,866·예상 실패 13·기존 건너뜀 1, 249.9초로 예산 300초 안이다. 첫 실패 보고도 남겼다.
