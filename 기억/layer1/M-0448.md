## 같은 정의를 사용하는 생성 보고 해소

[[M-0447]]은 cdc8e489로 확정했다. 이전 회차는 결함 네 개를 실제 수리한 진행 회차였다. 이번에는 원문 4-A/4-B/13-B의 의존관계에 따라, 흩어진 대기 생성과 보고 및 해소를 한 변경으로 통합했다. 개별 ID마다 새 감사 문서와 별도 커밋을 늘리지 않았다. main에서 새 grant를 받은 검토 대체가 authorization_denied로 다시 거부되는 KD-0701과 정확한 기존 정책 복원 뒤에도 review_initialization이 남는 KD-0703을 3dx5q6ew의 두 실제 실패로 확인했다.

wait_rules는 행동 대기 22종과 배정 대기 3종의 정본이다. 행동 생성과 종류 변경은 waiting_action/update_waiting_action을 통해 미등록 종류와 잘못된 담당자를 반려하고 가변 판정 전문을 분리한다. 생성자의 실제 종류 전건과 선언을 양방향 비교하며 해소자 함수 좌표도 확인한다. 슬롯·공급자·검토·형식·관찰 준비·권한·실패·영향·import·개정의 소비자들이 같은 선언을 사용한다. session_slots에 옛 집합 별칭을 남기지 않고 층 선언과 이음새 정본을 함께 바꿨다. reporting은 저장된 담당자·사유·판정 전문과 원 좌표를 사람이 읽는 보고에도 보존하며 소비자의 변경이 저장 상태를 바꾸지 않는 것을 검사한다.

새 공개 권한은 미시작 행동을 같은 ID로 한 번 재큐하고 활동도 해소한다. 검토 대체는 미시작 배정만 새 명시 권한으로 갱신하며 이미 등록된 시도의 봉인 권한은 바꾸지 않는다. 정확한 채택 정책과 현행 accepted/active 형식 증거가 돌아왔을 때 검토 초기화를 한 번 재개한다. 공개 답변은 초기화/활성 상태의 원 import 계보를 한 번 재작업한다. 봉인 자료 읽기 실패는 확인된 로컬 종료와 예약을 정산한 뒤 진단을 보낸다. KD-0701~0705를 main 원장에 현재 재현으로 기록했다. KD-0702/0704/0705의 후보 첫 실패는 역사로 보존하며 이번 main의 수리 전 실패라고 다시 이름 붙이지 않는다.

## 검증과 실제 준비 오류

dxb3sopj는 정본 전건 및 focused 14개가 통과했다. 9s_myuzs는 공개 권한·질문·정책 3개가 통과했으나 실패 출구 2개가 setUpModule의 unsupported mode 인자로 미실행이었다. main의 현재 native_final API로 같은 standalone 출력 의미를 구성한 2uptrx2l의 두 실패 출구가 통과했다. 제품 호환 fallback은 넣지 않았다.

7kqdzb3q의 형식 대기는 통과했으나 준비 대기의 warm_built와 영향 대기의 model.receipts 참조는 현재 main 도우미에 없는 API였다. 준비는 현행 prepared_sim을 사용하고, 영향 해소는 모델의 임시 목록 대신 해당 execution에 결합한 실제 runtime.control_receipts의 submit_intent 하나와 accepted 상태를 단언했다. po1urqjb에서 준비 네 종류와 영향 세 종류의 일반 검사가 통과했다. 조건 전 두 회차 유지, 공개 입력/권한의 실제 출구, 원 판정 보존, 중복 재큐 방지, 저장 왕복과 status 투영은 그대로다. 후보의 stricter 도우미 API를 main으로 통째로 덮어쓰지 않았다.

tt_nkd13의 관련 기존 118개가 13.4초에 통과했다. 개별 예산 초과 13개는 남긴다. 앞선 focused와 가족 검사에도 기록된 초과가 있어 성능 목표 달성을 주장하지 않는다. 후보에서 원 KD-0701/0702 메서드를 각각 기존 review_engine_replacement와 실제 action_authority_waits로 옮긴 뒤 이전 메서드를 제거했다. 후보 l_8o4bhp의 정본/원장/이동 회귀 9개도 통과했다. 각 보고는 서로 다른 선택이며 통과 수를 더해 전체 성공으로 계산하지 않는다.
