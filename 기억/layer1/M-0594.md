## 맥락

M-0593에서 확정한 실행 계약에 따라 async-development가 새 do-math를 구축했다. 실행기는 2026-10-21 21:09에 시작했고 22:39에 완료를 게시했다. manager는 아홉 차례 돌았고 task는 여덟 개였으며, 모두 수용됐다.

| task | 결과물 |
|---|---|
| `cli-discovery` | 실제 CLI 조사 |
| `protocol-checker` | `protocol.md`, `check.py` |
| `cli-adapter` | `cli_adapter.py`, `CLI.md` |
| `session-contexts` | `common.md`, 범주 문서 `plan.md`·`research.md`·`review.md` |
| `runner` | `runner.py`, `RUNTIME.md`, 가짜 세션 흐름 시험 |
| `skill-entry` | `SKILL.md` |
| `mixed-completion` | 실제 혼합 완주 |
| `final-review` | 최종 검토, 합격 |

제품은 `.claude/skills/do-math/`의 12개 파일과 시험 4개 모듈로 약 228KB다. 옛 구현은 모듈 약 115개, 문서 약 1MB였다.

이 커밋에 담은 것은 세 가지다. 제품, 미러 재생성(`.agents/skills/do-math/` 15개 파일 생성, `--check` exit 0), 개발 기록의 추적 부분이다. 기록 진입점은 `.async/do-math-rebuild-20261021/README.md`이고, 최종 판정은 `tasks/final-review/review.md`와 `managers/0009/decision.md`에 있다. 커밋 직전에 메인이 `python -B -m unittest discover -s tests`로 do-math 시험을 돌려 19개 통과를 확인했다(22.8초).

완주 근거는 `tasks/mixed-completion/evidence/instance-add-zero-fixed-20261021/`이다. 세션 다섯 개가 돌았다. 계획(Codex) → 연구(Codex) → 검토(Claude) → 계획(Codex) → 목표 검토(Claude) 순서다. 결과는 `theorem add_zero_all (n : Nat) : n + 0 = n := by rfl`과 그 해설이고, 목표 검토가 `achieved`로 판정했다. 이 인스턴스와 각 세션 로그는 Git 제외 로컬 보관이라 정리하면 사라질 수 있다. 추적되는 요약은 `tasks/mixed-completion/evidence.md`다.

## 터득한 것

- **개발 속도와 그 원인**: 결과물 여섯 개가 약 30분에 수용됐고, 전체 개발은 약 90분에 끝났다. 원인은 셋으로 판단한다.
  - 만들 것이 작다. 장치를 최소로 두는 설계라서 task 하나가 한 번에 끝낼 크기였다.
  - 결정이 미리 닫혀 있었다. `context.md`가 확정 결정과 구현자 재량을 갈라 두었으므로, 작업자가 설계를 고민하거나 되묻지 않았다.
  - 독립 task가 병렬로 돌았다.

  옛 do-math 재편 시도(`.async/dm`, task 126개, blocked)와 대조되는 결과다.
- **중간 점검과 manager의 선행 인식**: 메인이 중간 점검에서 수용 결과물을 계약과 대조해 두 가지 불일치를 찾았다.
  - `protocol.md`의 `codex/`·`claude/` 접두 모델 표기와 `cli_adapter.py`의 이름 모양 기반 라우팅이 서로 다르다.
  - 계획이 진행 중인 요청 상태를 읽을 경로가 프로토콜에 없다.

  manager는 둘 다 이미 `seams.md` 8절과 `runner` 지시에 넣어 두었다. 이후 `runner/state.json`의 `requests`로 해소됐다. 이 방식에서 인터페이스 불일치는 manager가 seams에 기록하고 다음 task가 고치는 경로로 처리됐다.
- **실제 완주에서만 드러난 결함**: 첫 완주 시도에서 실행기가 `state.json`을 원자적으로 교체하다 `WinError 5`로 죽었다. 원인은 Windows에서 다른 독자가 파일을 열어 둔 동안 `os.replace`가 거부되는 현상이다. 가짜 세션 시험은 이 결함을 잡지 못했다.
  - 수정은 `runner.py:write_json`에서 오류 5/32/33에만 50ms 간격, 최대 1초 재시도하는 것이다. 최종 review는 이를 제한된 변경으로 판정했다.
  - 옛 구현(L-0020의 Windows 항목)은 같은 계열 문제를 `FileRenameInfoEx`의 POSIX 교체 의미로 풀었다.
  - 메인은 사용자가 맡긴 재량에 따라 지금은 바꾸지 않기로 했다. 근거는 셋이다. review가 충분하다고 판정했고, 사용자 방향이 장치 최소화이며, 실패해도 결과는 실행기 정지라 사람이 다시 띄우는 운영으로 흡수된다.
  - 후속 조건을 정해 둔다. 실사용에서 재발하면 재시도 시간을 늘리지 말고 교체 방식을 바꾼다.
- **한도 해석의 정교함**: `cli_adapter.py`의 한도 해제 시각 해석은 계약 범위 안에 있다. Claude 초과 사용 분기를 구분하고, Codex의 "try again at" 시각을 서머타임 모호성까지 따져 해석한다. 해석에 실패하면 설정 간격 대기로 물러나므로 정지를 만드는 장치는 아니다. 다만 단순화 여지가 남은 지점이다.

## 작업 너머 시사점

- 실사용 전에 남은 확인이 있다. 대상은 장기 연구, 실제 공급자 한도, PC 재부팅 뒤 사람의 재기동, Mathlib을 쓰는 목표(컴파일 수 분)다. 최종 review는 이것들을 승인된 완료 기준에 넣지 않았다고 명시했다. 첫 실사용(예: 주차 함수 단봉성)이 이 확인을 겸한다.
- L-0020은 M-0593에서 정정 대기를 받았다. 새 구조의 현행 지식(위 Windows 결함, 계획 요청 상태 경로, 모델 표기)은 dream에서 L-0020을 다시 쓸 때의 입력 후보다.
- graphify의 do-math 그래프는 옛 구조를 가리킨다. 갱신은 사용자 요청이 있을 때만 한다.
