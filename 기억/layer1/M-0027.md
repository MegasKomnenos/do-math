# pvsnp-탐사-1 문헌 22건 판독 누적 산출물 커밋 — 검증런 2.7.6 0단계 기준선 확립

## 맥락

행 `2.7.6`(파견문 `C:\math\.sdd\dag\pvsnp-탐사-1\행\2.d\7.d\6.md`)은 2.7
worktree(`C:\Users\wogud\AppData\Local\dag-wt\pvsnp-탐사-1+2.7`, 브랜치
`dag/pvsnp-탐사-1/2.7`)에 누적된 22건 문헌 판독의 전건 변경을 검사하는
누적 검증런이다. 산출물은 파견문이 직접 지정한다 — `dag_measure.py
changes --worktree <worktree> --base HEAD`의 「현존」 파일 전건.

0단계 착수 전 확인에서 `changes` 실측이 현존 43건·삭제 0건을 냈다. 43건
전부가 worktree의 `git status`에서 미커밋이었다(수정 11건, 미추적 32건) —
`research/pvsnp/literature/` 아래 읽기(readings)·기록(records)·접근
로그(access)·출처 원장(source-ledger.md)과, `.claude/skills/
verify-rounds/scripts/vr.py`·같은 디렉토리의 `test_심사집계.py`(심사집계
기각 보관 기능 추가분)다. M-0006~M-0022·M-0026이 기록한 같은 패턴(do-dag
산출 미커밋 인계 → 검증런 0단계 전 대행 커밋)이 이번까지 열일곱 번째로
재현했다.

43건 전부가 이 검증런의 산출물이므로(M-0019 이후 확립된 분할과 달리 이번은
좁히지 않았다) 전건을 이름으로 지정해 스테이징하고 worktree에서 단일
커밋했다(`0018f39`). vr.py·테스트 파일이 산출물에 섞여 있어 commit-harness
테스트 게이트를 적용했다 — `.claude/skills/verify-rounds/scripts/tests/`의
`test_*.py` 18개를 각 파일 직접 실행으로 돌려 전건 exit 0(`test_wait_
outputs.py` 포함)을 확인한 뒤 커밋했다. 이 메모리 노드와 색인 갱신은
메인 저장소(`C:\math`, `main` 브랜치)의 별도 커밋으로 붙인다 — worktree
산출물과 메인 저장소 DAG 오케스트레이션 기록이 갈리는 M-0019 이후의
구조를 그대로 따른다.

메인 저장소에는 이 검증런과 무관한 다른 미커밋 변경(`.agents/AGENTS.md`,
`.claude/CLAUDE.md`, `.sdd/dag/marker.json`, `파견표.md`, 형제 행
`2.7.10.55.12.4.1` 예외 관련 신규 파일 4건)이 함께 있었다 — 이들은 다른
세션·작업의 소관이므로 이번 커밋 범위에서 뺐다.

## 터득한 것

- do-dag 완료-커밋 미결합 패턴의 재현이 이번까지 열일곱 번째다.
- 이번 검증런은 M-0019가 세운 "산출물 = worktree 파일만, 정본 = 메인
  저장소 보고류" 분할을 적용하지 않는다 — 파견문이 산출물을 `dag_measure
  changes` 현존 전건으로 직접 닫아, 좁힐 재량이 없었다.
- vr.py 자체가 검증 대상 산출물에 포함된 사례는 이번이 처음이다. 스크립트
  변경을 담은 커밋이므로 commit-harness 테스트 게이트를 그 워크트리
  안에서 실행해야 했다 — 게이트는 저장소·브랜치와 무관하게 변경 경로
  기준으로 걸린다는 점을 재확인했다.

## 작업 너머 시사점

do-dag 완료-커밋 미결합 패턴의 재현이 열일곱 번째에 이르렀다. 이번
사례는 기존 두 축(단일 산출물 대행 커밋, 형제 행군 누적 인계)에 세 번째
축을 더한다 — 파견문이 산출물을 명령 실측으로 직접 정의하는 누적 검증런은
분할 재량 자체가 없어 워크트리의 무관 변경과 검증 대상이 뒤섞이지 않도록
사전 `changes` 실측 결과를 커밋 스테이징 목록의 유일한 근거로 삼아야
한다. L-0016(위임 파이프라인 운영)·L-0019(do-dag 실행 체제)가 연결 후보다.
