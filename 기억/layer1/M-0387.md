## 맥락

[[M-0386]]에서 시범 비율로 곱한 확대 비용이 T2 예산을 크게 넘는다는 것을 확인했고, 영역을 나누기 전에 시험 하나의 비용을 줄인 단위다. 진행 기록은 `진행.md`의 "속도 단위" 절, 결정은 설계 10절 A25다.

## 터득한 것

**느린 곳은 짐작이 아니라 호출자 목록이 알려 준다.** 처음 떠올린 해법은 설계 5.4의 병렬 묶음과 변형 템플릿이었다. 프로파일에서 `fsync`, 파일 복사, 삭제의 호출자를 따라가니 거의 모두 Git 객체 파일 하나로 모였다. 객체마다 `fsync`하는 제품 코드, 그 파일을 복사하는 템플릿 복원, 읽기 전용 파일이라 권한을 바꿔 지우는 정리였다. 병렬화는 이 비용을 나눌 뿐이고, 원인을 없애는 것은 객체를 파일로 두지 않는 대역이었다. 결과는 `sim` 묶음 108초 → 45초였고, 병렬 묶음과 변형 템플릿은 지금 필요 없어 미뤘다.

**1c의 결정 A14는 그때 옳았지만 비용을 몰랐다.** "파일 시스템은 포트가 아니다"는 일반 파일에는 여전히 맞다. Git 객체 저장소는 Git이라는 외부 자원의 형식이고 포트가 이미 읽기를 맡았으므로, 쓰기만 파일 시스템 쪽에 남은 것이 비대칭이었다. 측정이 그 비대칭의 값을 보여 줬고, 결정을 부분적으로 다시 열었다.

**옛 모음이 이동의 회귀를 잡았다.** 코드를 "그대로 옮겼다"고 여겼지만, 옮긴 자리에서 객체 폴더를 알려고 `describe`를 한 번 더 불러 게시마다 git 프로세스가 하나 늘었다. `test_git_store`의 "블롭을 많이 써도 git 프로세스는 `update-ref` 하나"가 이를 잡았다. 동작 보존 이동도 옛 모음 전체로 확인해야 한다는 설계 9.2의 규칙이 실제로 값을 했다.

**실행 중에는 스킬 파일을 건드리지 않는다는 규칙을 스스로 어겼다.** 45분짜리 전체 실행을 띄우자마자 변이 도구를 고쳐, 실행기가 그 실행을 통과로 인정하지 않았다. 긴 실행 동안 할 일은 스킬 밖(문서)이나 읽기로 한정한다.

## 작업 너머 시사점

- 셸 heredoc 안의 파이썬 문자열에 `\0` 같은 이스케이프를 쓰면 한 번 더 풀려 실제 NUL 바이트가 소스에 들어갈 수 있다. 제어 문자는 `chr()`나 Edit 도구로 넣는다.
