phase 003 manager는 provider-smoke의 partial을 유지했다. 실제 maintenance schema 전체를 사용한 Codex 1회와 Claude 2회가 있었고, Claude 최종 호출은 파일·읽기·checkpoint·구조 응답·종료에 성공했다. Codex는 선택 integration_bundles가 required에 없다는 HTTP 400으로 거부됐다. 작은 protocol_probe의 이전 성공을 실제 역할 schema 수락으로 넓히지 않은 덕분에 이 차이를 구체적 제품 경계 실패로 기록할 수 있었다. 선택 필드를 없애거나 제품 의미상 필수로 만드는 처방은 하지 않으며 다음 제품 수리에서 부재/null/값과 현재 호출자를 함께 확인한다.

공식 미러 --check도 실제 인도 무결성을 보증하지 않았다. 생성기의 CLAUDE.md 치환이 원자료인 Claude help 두 개에도 적용됐고, 미러 구조/재생은 4개 중 2개가 실패했다. 하나는 이전 녹화라 이번 작업에서 처음 생긴 결함도 아니다. 현재 생성기의 verbatim 경계가 이미 있으므로 phase 004는 녹화 전체를 이 규칙으로 보호하고 양쪽 전건 바이트와 실제 재생을 확인하도록 한정했다. Git clean이 원자료 세 파일의 CRLF도 변환한다는 직접 관찰을 얻어 corpus 한정 속성과 실제 clean 경로를 같은 인도 작업에 포함했다. 규칙의 자기 일치와 원자료의 보존을 따로 확인해야 하는 구체적 사례다.

반환 보고는 task 종료 2254파일, 공식 최종 Python 864개, 선택/실제 row/종료, 세 호출의 schema/prompt/worker/native/파일을 원자료와 대조했다. 기존 Claude background도 원자료9파일과 동일 task/tool ID·순서·nonce·종료가 현 계약에 맞는지 확인했다. 과거 passed=false와 actual_wait_tool=false는 그대로 두고 현재 native completion 성질만 재사용한다. 전체 PR15나 역할 저장 경계 성공으로 확장하지 않았다. manager는 제품 코드나 task의 기존 보고를 수정하지 않았다.

다음 순서는 미러 수리 뒤 Codex 전달·수신 수리다. 두 작업이 다른 결함을 다뤄도 공식 생성기·말뭉치·캐시를 공유하므로 같은 phase에 병렬 배정하지 않았다. 원래 G1~G8, 문서·의미 질문·전체 일반/fresh T3/전체 변이·다른 실제 연쇄·최종 review 남김은 유지했다. 실패한 제품 변경은 교정과 검증 전에 제품 커밋으로 만들지 않았다. 대신 이 관리 커밋에 다음 배정과 판정, 실제 원자료와 62개 변경의 바이트 archive를 보존하고 제품은 작업트리에 둔다. archive는 실패 상태의 증거이며 사용자 조작을 되돌릴 자동 복원 지시가 아니다.

추적 진입점은 docs/do-math/continuous-development-2026-10-13/phases/003/manager.json과 manager-evidence/review.md, verification.json, preservation.json이다. 선별한 report·원보고·live 입출력·historical-background 원자료 및 provider-smoke-working-tree.zip은 이 커밋에 보존한다. 중복 source-before/source-after, 서비스 runtime/세션 logs, 임시 .before/pathspec은 로컬 보관이며 정리로 사라질 수 있다. 원보고 bytes를 바꾸지 않고 Git blob과 대조한다. 기존 무관 dirty/untracked와 engine은 이 커밋에 넣지 않는다.
