## 맥락

[[D-0011]]의 제안 11건 가운데 사용자가 세 가지를 전부 적용하라고 정했다. verify-rounds 문면 보강 넷(D-0011 제안 3), write-for-reader 보강 다섯(제안 6의 (가)~(마)), Codex 수기 설정의 낡은 참조 정리와 `latest.json` 추적 해제(제안 9)다. 노드 없는 커밋 두 건(제안 1), review 모델(제안 2), 다음 dream 예약(제안 11)은 넘겼고, 다음 dream은 사용자가 새 세션에서 직접 호출한다. 사용자의 대화 요약 목록은 D-0011의 번호와 달라, "3, 4, 5"는 요약 목록의 번호였다. D-0011 제안 6의 추천은 (가)(다)를 통독 뒤로 미뤘지만 사용자는 전부 적용을 정했으므로, 집행 전에 대상 절을 통독했다(세칙_dream "제안 집행 전 적용할 파일과 절을 직접 통독").

적용한 문면은 다음과 같다.

- `verify-rounds/SKILL.md`: §0 동결 1항에 상신·판정이 기댈 사용자 결정 기록의 원문 경로를 「기준 원문」에 적는 문장. 1단계 「배분」에 영역·관점 크기를 한 컨텍스트 독해량으로 파견 전에 정하는 세 문장. 3단계 기각 보관 문단에 런 안의 기각 보관 디렉토리를 `{기각보관}` 슬롯으로 「읽지 않는 것」에 적는 문장. 4단계 「불변식 재실측」에 예정된 편집 뒤로 재실측을 모으고 마지막 재실측은 생략하지 않는 문장.
- `verify-rounds/references/파견문.md`: 세 템플릿의 「읽지 않는 것」 줄에 `{기각보관}`, 수리 템플릿에 `{앞라운드들}`, 슬롯 원천 표에 `{기각보관}` 행. 템플릿은 "문장을 더하지 않는다"(작성 지시 3)이므로 기각 보관 경계를 문장이 아니라 슬롯으로 넣었다. 수리 템플릿이 앞 라운드를 적지 않는 이유를 적던 31행은 새 템플릿과 모순되므로 "계약의 열람 한계와 같은 범위를 파견문 좌표로 보이게 한다"로 바꿨다.
- `write-for-reader`: `AI_프롬프트.md` "원리에서 실행 기준을 도출한다"에 위임한 판단이라는 셋째 경우. `SKILL.md` 공통 작성 절차 9항(기존 판본의 목적·판단 기준·방법 예 대조). `독해_검토.md`의 합의 정의에 항목과 사용자 요청·답변의 대응, 「대조와 수정」에 `decide`의 순서와 반복 독해를 멈추는 기준·발췌 독해의 한계.
- `.agents/config.toml`의 `dag-measure` MCP 서버, `.agents/hooks.json`의 do-dag·ponytail 훅 넷(남는 훅이 없어 `{"hooks": {}}`), `.agents/AGENTS.md`의 do-dag 프리셋 줄을 지웠다. `.claude/CLAUDE.md` 프리셋 절에는 같은 줄이 이미 없었다(M-0623에서 지움). 사용자에게 확인한 결과 CLAUDE.md에 고칠 것은 없었다.
- `services/scholarly-mcp/docs/history/dispatch/remaining-20260913/latest.json`을 `git rm --cached`로 추적에서 뺐다. 로컬 파일은 남아 `services/scholarly-mcp/docs/history/`가 미추적으로 보인다. 그 디렉터리를 무시하던 중첩 `.gitignore`는 공개 준비 삭제(`98e806f1`)에서 사라졌다.

검증: 미러 생성기가 정본 다섯 파일만 갱신했고 `--check`는 드리프트 없음(144파일)이다. verify-rounds 시험 18개 파일과 `test_writing_flow.py`를 파일마다 직접 실행해 270개가 모두 통과했다. 바꾼 문면을 다시 독해하지는 않았다.

## 터득한 것

- 같은 편집 스크립트가 LF 파일(`SKILL.md`)에서는 맞고 CRLF 작업 사본(`파견문.md`)에서는 앵커를 못 찾았다. 앵커가 정확히 한 번 나오는지 단언하게 둔 덕에 파일을 바꾸기 전에 멈췄고, 줄 끝을 정규화해 대조한 뒤 원래 줄 끝으로 되돌려 썼다. [[L-0012]] "규범이 실제로 적용되는지 점검"이 이번 dream에서 적은 확인(앵커가 하나인지와 적용 개수)이 실제로 무적용을 막은 사례다. 같은 저장소에서 `core.autocrlf=true`라 작업 사본의 줄 끝이 파일마다 다르다.
- `기억/색인.md`도 같은 이유로 작업 사본이 CRLF와 LF가 섞인 상태가 되어 색인 이관 스크립트의 절 머리 탐색이 실패한 일이 dream 중에 있었다. 저장소 blob은 LF다.
