## 맥락

사용자는 별도 세션이 통합 설계의 반영 여부를 검토할 수 있도록, 구현자가 의도적으로 비우거나 바꾼 부분과 이유를 가진 결정의 구체적인 맥락을 최대한 충실하게 작성하라고 요청했다. 그 문서에 적히지 않은 것은 고려하지 않은 것으로 간주하고, 검토자가 추가 변명의 기회 없이 평가할 수 있음을 명시하도록 했다.

이 요청은 기존 구현의 변경이나 새 완료 판정을 요구한 것이 아니다. `docs/do-math/구현자-결정과-변명.md`에 구현자 입장의 설명을 모으고 `구현-진행.md`에서 연결했다. 기준 판본의 코드와 역할 문서는 바꾸지 않았다. 선언한 보존 규칙은 본문의 구체적 기재에 적용한다. 넓은 원칙이나 원자료 링크로 언급하지 않은 세부 결정까지 고려했다고 주장할 수 없다.

## 설명을 복원할 때 구별한 근거

직접 API를 필수로 전달했다가 CLI로 교정한 경위는 [[M-0263]], 격리와 제약의 구현 재량은 [[M-0266]], 작은 실제 흐름을 전체 완료 기준으로 삼지 말라는 제한과 이후 보완은 [[M-0269]], 문서의 정의·소유·실제 입력 전달 개정은 [[M-0274]]에서 확인했다. 이 기록들의 완료 선언을 그 자체의 증거로 사용하지 않았다.

당시 대화·작업 기억·실제 수정에서 확인하는 이유, 현재 코드에만 보이는 선택, 이번에 새로 제시하는 장점과 대안의 설명을 구별했다. 특히 고정 인원·기한·크기, 기록의 합침, 빠진 실행 경로를 모두 의도적인 간소화로 소급하지 않았다. 사용자가 위임한 것은 수단의 실익 판단이며, 기능 목적의 누락까지 허용한 것은 아니다.

실행·자원, 연구·검토, 저장·통치의 세 범위로 근거를 조사한 뒤 한 문서로 합쳤다. 조사 담당자의 요약도 코드와 대조했다. `record_turn`이 여러 역할의 메시지를 받을 수 있다는 사실만으로 CLI 대화 전건이 복원된다고 쓴 설명을 발견했다. 실제 호출부는 제안·검토 요청·구조화 응답·보충 결과를 넣고, 중간 메시지와 일반 도구 결과 전건을 다음 자리 입력으로 자동 옮기지 않는다. 공개 API의 표현 능력과 평시 호출부가 실제 전달하는 범위를 구별하여 본문에 반영했다.

또한 source 변경의 완료 이력 보존 수리를 다른 변경 경로까지 확대하지 않았다. 지식 변경은 완료 과제를 waiting으로 바꿀 수 있고, 학술 요구 변경과 목표·정책 변경의 처리도 동일하지 않다. 공용 Lean 정본 편입, 여러 독립 해설, 일반 활동의 영속 상태, 전문 배정, 재심사·위임·변환 등도 현재 코드가 수행하는 부분과 비어 있는 부분을 따로 기록했다. 이런 차이를 이번에 확인한 것은 과거에 충분히 비교했다는 증거가 아니다.

## 검증 범위와 후속

변명서의 검증 대상은 실제 사실과 당시 근거의 구별, 문장 내부 정합성, 제한된 실행 기록의 범위, 참조와 기본값의 정확성이다. 제품 전체의 통합 설계 충족 판정을 대신하지 않는다. 실제 CLI의 작은 수학 사례, 합성 초기 판단을 사용한 이의 왕복, 부정 의미 사례, 모델 대역, 문서 독해와 여러 판본의 부분 재검증을 구별해 적었다.

별도 검토에서 설정 자동 주입·환경 변수 제거·순차 배정·명령 표면의 선택 이유가 당시 판단처럼 읽힐 수 있다는 지적을 받았다. 구체적 근거가 있는 자유 인자 제거는 당시 기록과 연결하고, 나머지 일반적 장점은 사후 평가라고 명시했다. 작은 수학 사례와 모델 대역의 선택 이유도 같은 기준으로 표현을 보완한 뒤 재검토를 통과했다. 새로 적은 활동 단위·공용 Lean 정본 부재·HTTP 범위·초기 허가도 실제 코드와 대조했다. 변명서와 진입점의 로컬 링크 56개가 모두 존재하고, 기본 설정 24개의 이름과 값이 코드와 일치함을 확인했다. 기억 색인 검사도 통과했다.

후속 검토자는 이 변명서를 읽고 각 선택의 실익을 반박하거나 미구현을 판정할 수 있다. 검토자의 해석을 미리 통과시키는 새 기준이나 반드시 변명에 동의해야 하는 절차를 만들지 않았다. 구현자의 추가 변명을 기다리지 않는다는 사용자 규칙도 문서 첫머리와 진입 문서에 명시했다.

## 작업 너머 시사점

dream에서 함께 묶을 후보는 [[M-0269]]·[[M-0274]]와 이번 기록이다. 작은 성공 사례, 역할 문서의 충분성, 실제 소비 경로, 과거 선택의 이유는 서로 다른 근거를 요구한다. 특히 기능이 빠진 사실을 발견한 뒤 그럴듯한 간소화 이유를 붙이는 방식은 구현 재량의 행사를 입증하지 못한다. 결정 당시에 목적·대체 수단·손실·확인 범위를 남겨야 후속 검토가 당시의 선택과 사후 설명을 구별할 수 있다.
