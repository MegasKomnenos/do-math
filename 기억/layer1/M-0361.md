## 터득한 것

**포트 연산의 크기가 설계를 갈랐다.** `GitStateStore`는 git 명령의 텍스트 출력을 스스로 해석하고 있었다. 포트를 `_git(args)` 수준에 두면 대역이 git 명령과 출력 형식을 흉내 내야 해서 실제의 복제가 된다. 연산을 의미 단위로 정하고(객체 해석, 객체 읽기, 비교 후 교체 등) 출력 해석을 실제 어댑터 `GitProcess`로 옮겼다. 그 덕에 대역 `InProcessGit`은 느슨한 객체와 참조 파일을 읽는 짧은 코드로 끝났다. 블롭 읽기가 객체 종류를 확인하는 동작을 지키려고 `read_objects`가 `(종류, 바이트)`를 돌려주게 했다. 종류를 알려고 git 호출을 한 번 더 하면 게시 비용이 늘기 때문이다.

**프로세스 없이 만든 저장소가 양쪽 계약의 공통 입력이 되었다.** 계약 시험은 `HEAD`, `config`, `objects/`, `refs/heads/`만 쓴 최소 골격과 zlib 느슨한 객체로 저장소를 만든다. 실제 git도 이 골격을 저장소로 읽었다(sha1·sha256). 이렇게 하면 대역 쪽 계약이 T1에서 git 프로세스 없이 돈다.

**옛 시험이 동작 차이 하나를 드러냈다.** 새 포트에서는 없는 경로가 오류가 아니라 `None`이다. 그래서 없는 경로를 읽을 때 저장소 경계를 다시 확인하던 옛 동작이 빠졌고, `test_physical_boundary_is_proved_on_open_and_after_git_errors_only`가 이를 잡았다. 시험을 고치지 않고 제품의 `read_bytes`가 경계를 먼저 확인하게 했다. 반대로 git 출력의 행 수와 필드 형식을 거부하던 시험들은 거부하는 자리가 저장소에서 어댑터로 옮겨졌을 뿐 거부 자체는 남으므로, 가짜 출력을 넣는 자리와 기대 문구만 옮겼다. 두 경우를 가른 기준은 제품의 관찰 가능한 동작이 바뀌었는가다.

**완비 검사 규칙 두 개를 실제 사례에 맞췄다.** 서명 비교가 타입 주석까지 비교해 주석 없는 구현을 실패시켰다. 호출 가능성이 같은지가 목적이므로 이름·종류·기본값만 비교하게 했고, 주석만 다른 경우를 먼저 시험으로 적었다. 객체 형식 둘을 모두 계약으로 보려고 계약 쪽마다 TestCase가 하나 이상이면 되게 했다.

**셸 heredoc과 편집 스크립트.** 긴 편집을 bash heredoc 안의 파이썬으로 넣다가 따옴표 해석 오류와 이스케이프 불일치로 네 번 실패했다(파일은 바뀌지 않음). 긴 편집은 스크립트 파일(`.skill-workspace/test-restructure-2026-09-29/tools/`, Git 제외 로컬 자료)로 쓰고 raw 문자열로 원문을 담는 방식이 안정적이었다.

## 작업 너머 시사점

- 시험이 제품 내부 메서드(`_git`)를 바꿔 끼우던 곳은 포트 이전 때마다 어디로 옮길지 판단이 필요하다. 그 판단은 "이 시험이 보던 성질이 이제 어느 층의 책임인가"로 하면 한 가지로 정해졌다(프로세스 수는 어댑터, 형식 거부는 어댑터, 경계 재확인은 저장소).
