## 맥락

사용자는 do-math 내부 정합성, 중복·낡은 설명·폐기 계약의 흔적을 verify-rounds mixed 표준으로 정리하라고 했다. 수리자는 Opus 5.5, 심사자는 GPT-6 Astra로 지정했고, 매 심사 뒤 기각·무처분을 메인이 직접 검토해 반영 여부를 정하도록 위임했다. 과설계·오버헤드·비대·누적을 피하라는 조건도 있었다.

정본 15파일을 3영역과 전건 관점 하나로 나눴다. Claude Agent 도구가 없어 같은 모델·노력을 명시한 CLI 독립 세션으로 파견했고, Codex도 CLI를 사용했다. 수리 4기·심사 3기·정족 3, 하한 2·상한 6은 유지한다. graphify는 갱신하지 않았다.

1라운드 제기 17건은 병합 뒤 13건이 됐다. 심사는 수리 7건, 무처분 3건, 기각 3건이었다. 공식 적용은 7항목이며 구성 항목을 세는 장부에서는 9행이다. 메인이 기각·무처분 6건을 모두 직접 회수했고, 이 직접 반영은 공식 승인 계수에 넣지 않았다. 다음 라운드가 전체 변경을 새 사본에서 검토한다.

## 터득한 것

- 심사는 타당한 지적에 붙은 잘못된 수리를 두 건 잡았다. 설정 경로를 세션에 준다는 사실은 기동 때 읽는다는 보장이 아니었다. Lean 설정 설명을 세션이 파일을 실제로 읽는 시점으로 고쳤다. 또 병합자가 어댑터 시험의 Python 3.11 요건을 전체 시험으로 넓혔으나 검사기는 3.12가 필요했다. 전체 시험 안내는 기존 3.12 요건을 유지했다.
- Claude 노력 값 안내만 고쳐서는 잘못된 요청의 반복 기동 실패가 남는다는 기각이 있었다. 메인은 계획 문서의 launch_error 무조건 재게시를 원인 확인과 수정·해소 후 재시도로 바꿨다. 기존 wait와 계획 재량으로 처리하며 실행기에 새 실패 계수나 감시 체계를 더하지 않았다.
- 무처분 셋은 현재 동작을 바꾸지 않는다는 중대성 관문 때문이었다. 사용자는 사족·중복도 정리하라고 했으므로, 끝난 문서 작성 책임 설명과 폐기 장치의 부정형 반복을 지우고 설정 정본을 protocol.md로 모았다. formal 처분과 직접 판단의 목적 차이를 장부에 남겼다.
- 기준선 시험 20개 중 세 흐름이 12초 대기를 넘겨 실패했다. 제품·단언을 그대로 두고 대기만 60초로 늘린 진단은 실행기 시험 7개를 모두 통과했다. 시험의 기본 대기만 바꾼 뒤 공식 전체 20개가 26.033초에 통과했다. 제품의 세션 실행 시간 정책에는 변경이 없다.
- last_plan 기본값과 halted 선택 읽기는 [[M-0600]]의 증거 인스턴스 조회용 소비자가 남아 있어 유지했다. 오래된 형태만으로 지울 코드와 실제로 폐기된 계약을 구분했다.
