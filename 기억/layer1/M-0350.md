## 맥락

사용자는 [[M-0349]]의 경량화 2라운드 직후 시험 체계의 개선을 지시했다. 결과 캐시는 제대로 만들기 어려우니 없앤다. 스위트를 여러 모듈(조각)로 나누어 가장 긴 조각은 2분, 모두 합쳐 5분 안에 끝나게 한다. 여러 주체가 언제 어떤 방식으로 시험을 돌릴지 실용 지침을 남긴다. 커버리지는 크게 바꾸지 않는다. 그 뒤 2라운드에서 추가된 영역까지 실행해 발견된 문제를 고치고 2라운드 결과를 검증한다. 지난 라운드들의 지침은 도그마가 아닌 참고로 삼는다.

진행 중 사용자가 정한 것은 다음과 같다.

- "5분"은 조각을 차례로 돌린 합계다(병렬 벽시계가 아님).
- 제품 비용을 줄여 시험 비용을 줄이는 방향을 우선한다. 실익이 분명하면 제품 기능 범위가 바뀌어도 된다.
- 120초·300초는 최대한 가까이 갈 목표이며 한계가 아니다. 핵심 기능을 약하게 하거나 실익 없는 축소를 하면서까지 맞추지 않는다.
- git 프로세스를 상주시켜 재사용하는 안은 프로세스 수명 관리가 더하는 복잡성 때문에 기각했다.
- `status`의 진행 표시가 최대 1초 늦어지는 것은 받아들였다.
- 남은 비용(상태 변경마다의 내구성 저장)을 더 줄이는 안(저장 합치기, fsync 제거) 대신 여기서 마무리한다(안 C).
- 경량화 뒤의 커버리지 측정은 건너뛴다. 최종 전체 실행은 시간 측정이 무의미해졌으므로 조각을 병렬로 돌려 통과만 확인한다.

## 결과

**제품.** 시험 시간 대부분은 제품이 실제 운전에서도 치르는 비용이었다.

- `git_store.publish`는 블롭·트리·커밋을 프로세스 안에서 느슨한 객체로 쓰고 `update-ref` CAS 하나만 git 프로세스로 남긴다. 게시당 git 프로세스가 6개에서 1개가 되었다. 트리 OID를 git plumbing과 대조하는 sha1·sha256 차등 시험을 두었다. 새 객체마다 fsync하는데, 설치된 Git for Windows의 기본값(`core.fsyncObjectFiles=true`)과 같은 내구성이다. 문서만 보면 반대로 읽히며, trace2 계수로 확인했다.
- 엔진은 다음을 줄였다: 설치 매니페스트 재계산(디렉터리 목록 지문이 같으면 재사용), 저장 검증·봉인·인코딩의 반복 import와 재직렬화, 방금 게시한 아티팩트와 실행 입력 스냅숏의 git 재독, `check_path_segment` 반복.
- 연산 추적(`operation_trace`)은 로그 핸들을 추적 동안 열어 두고, live 진행 스냅숏은 1초 간격으로 제한한다. 제한을 위해 넣은 타이머가 추적을 닫은 뒤 스냅숏을 다시 쓰고 핸들을 남기는 결함이 있었다. 통합 단계에서 발견해 닫힘 표지로 고쳤고 회귀 시험을 두었다.
- `governance`의 `intent_imports.input_ref`는 필수가 되었다. 생산자가 하나이고 항상 붙인다는 것을 정적으로 확인했다. 생산자가 없던 대체값도 지웠다.

**시험.**

- `research_fixtures.restore_template`: 준비 함수가 만든 상태를 프로세스당 한 번 만들고, 시험마다 같은 절대 경로에 바이트 그대로 복원한다. 경로를 치환하는 대신 이 방식을 택한 이유는 절대 경로가 게시된 커밋과 해시에 묶여 있기 때문이다.
- `git_init`·`run_cli` 도우미를 두고, 무거운 모듈 약 25개를 이 기반으로 옮겼다. `owner_calls`가 제어 전송을 펌프하지 않아 준비 단계마다 60초 영수증 시한을 다 쓰던 결함도 고쳤다.
- `run_tests.py`에서 결과 캐시를 없앴다. 시험 ID 위치 인자, `--shard`, 조각별 시간 보고를 넣었다. `test_categories.SHARDS`(6조각)에 등록되지 않은 모듈이 있으면 실행하지 않는다. 캐시용 분류(unit·integration·archive)를 지웠고, 격리 클래스 안의 격리 해제는 `in_process` 표시로 한다.
- 지침 정본은 `.claude/skills/do-math/scripts/tests/시험-지침.md`다. 독립 독해 5회를 거쳤다. `AGENTS.md`와 README가 이 지침을 가리킨다.

**측정.**

- 기준선: main(379a171)의 커버리지는 문장+분기 종합 83.9%(문장 87.1%, 분기 77.1%)였다. 모듈별 plain unittest를 계측 아래 두 개씩 동시에 돌렸고, 모듈 시간 합은 약 19,800초였다.
- 통합 확인(full1, 추적 변경 전, 한가한 기계, 순차): 1,853개 통과에 2,440초였다. 조각별로 research 828, review 538, lifecycle 411, academic 277, foundation 259, host 128초다.
- 목표 300초에는 닿지 않았다. 표본 추출(메인 스레드 스택 5ms 간격)로 보면 남은 비용의 대부분은 상태 변경마다의 내구성 저장이다. 대표 시험 하나가 약 200번 게시하고, 게시마다 객체 fsync와 `update-ref` 프로세스 하나(약 0.05초)가 든다. git 시간의 74%가 `update-ref`였고 읽기는 26%였으므로, 프로세스 안 읽기는 구현하지 않았다.
- 최종 판본의 통합 확인은 조각을 세 묶음으로 나눠 동시에 돌렸다(시간은 쓰지 않음). 1,860개 통과, 실패 0, 건너뜀 2(심볼릭 링크 권한, 휴대용 Lean 미설치 조건)였고 실행 중 소스 변경은 없었다.
- 경량화 뒤 커버리지는 사용자 결정으로 측정하지 않았다. 단언 보존의 근거는 작업자 반환에 있다. 지운 단언이 없고, 중복으로 지운 시험 넷은 단언을 남는 시험으로 옮겼다.

**2라운드 검증.** main에서 실패하던 시험은 68개였다.

- **제품 결함 1건.** 2라운드가 `review_cycle.research_schema`의 모든 필드가 `TEXT` 노드 하나를 공유하게 바꿨다. 그런데 `review_engine._review_research_schema`가 그 노드에 `enum`을 제자리에서 설정해, 모든 문자열 필드가 요청 다이제스트 하나로 제한되었다. 그 결과 실제 보충 조사 제출이 전부 거부되었다. 기존 거부 시험은 "이슈가 하나라도 있으면" 통과하는 단언이라 이 결함을 잡지 못했다. 생산 쪽과 소비 쪽을 모두 고치고 대조 단언을 더했다.
- **제품 활성 결함 1건.** `parallel.ModelCalls`의 펌프가 관찰 행을 상한 없이 비워, 소유 루프가 한 호출에 묶였다. 펌프 진입 시점의 행만 적용하게 고쳤다.
- **나머지 대부분**은 2라운드가 책임을 공유 커널로 옮기거나 필드·스키마를 엄격하게 바꾼 것을 시험 대역과 fixture가 따라가지 못한 경우였다. 단언을 약하게 하지 않고 현행 계약의 같은 성질로 다시 단언했다. 엉뚱한 이유로 통과하던 음성 시험 2건은 사유를 고정해 강화했다.
- **환경 원인 2종.** 첫째, 제품은 Lean 도구 모음을 `formal.py` 기준 다섯 단계 위(`<저장소>/.skill-workspace/do-math-toolchains`)에서 찾는다. 그래서 worktree에서는 실제 Lean 시험이 `unavailable`이 된다. 둘째, 추적표 검사가 로컬 보관소 `임시/do-math-implementation-20260920`(35MB)와 `임시/do-math-resume-20260920`(384MB)를 읽는다. 통합 확인을 worktree에서 할 때는 두 보관소를 복사하고 `DO_MATH_KNOWLEDGE_TEST_LEAN`을 준다.
- **추적표 정리.** `docs/do-math/implementation-v5/traceability.json`에서 2라운드가 지운 좌표 21곳을 정리했다. V09·V235의 실행 요약은 `not_run`이 되었다.
- **열린 질문 하나(2라운드 이전부터).** 실행 소실 복구는 권한 기록 전에 queued였던 시도를 `start_failed`가 아니라 `cancelled`로 종결한다(`engine._recover_disappeared`). 원천 기대와 다르며, 설계상 어느 쪽이 맞는지는 판정하지 않았다.

## 터득한 것

**작업자의 시험 운용이 비용의 큰 몫이었다.** 사용자가 남은 두 작업자의 로그를 직접 보라고 지시했고, 로그를 보니 다음과 같았다.

- 한 작업자는 147분 중 114분을 결과 대기로 보냈다. 10분 시한의 `until … sleep` 전경 대기를 반복했고, 그렇게 쌓인 중복 대기 셸이 7개였다.
- 다른 작업자는 144분 중 58분 대기, 53분 실행이었다.
- 무거운 모듈 전체를 확인 수단으로 되풀이했다(목적 엔진 3회, 스케줄러 2회).
- 측정 도중 같은 트리를 편집했다.
- 공유 고정 로그 경로(`/tmp/verify.log`)를 썼다.
- 작업자마다 기준 판본을 stash로 다시 돌렸다.
- 기계에 무거운 프로세스가 5개 이상 동시에 돌았다.

사용자는 작업자에게 직접 "같은 시험을 반복 실행하며 시간을 낭비하지 말고 정적 분석하라"고 보냈다. 교정 이후 작업자들은 정적 분석으로 남은 원인을 찾았다.

- **ⓐ 거부된 기본값.** 파견 계약에 "전체 금지, 한 번에 한 프로세스" 정도만 적고 대기·편집·측정 방식은 작업자에게 맡겼다.
- **ⓑ 선호된 교정.** 실행 방식의 되는 것과 안 되는 것을 실용적으로 미리 정한다.
- **ⓒ 드러난 공백.** 파견문이 "무엇을 돌릴지"만 정하고 "어떻게 돌리고 기다릴지"를 정하지 않았다.
- **ⓓ 교정 위치.** `시험-지침.md` 3절이 그 교정 위치다. 이후 작업자 반환(B3)에서 대기 반복문을 한 번 쓴 뒤 스스로 알림 방식으로 바꾼 기록이 나왔다.

**통합자 자신의 측정 방식에도 교정이 있었다.**

- 전체를 다시 실측하려 하자, 사용자가 이미 있는 작업자 보고서부터 모으라고 돌렸다. 과거 보고서 70회분의 집계로 분포와 느린 시험을 먼저 얻었다.
- 계약에 적은 "설치 검사 25%, 직렬화 15%"는 Python 3.12 cProfile이 여러 스레드의 사건을 한 스택에 섞어 부풀린 값이었다. W-eng가 스레드별 벽시계로 바로잡았다. 이후 판단에는 메인 스레드 표본 추출을 썼다(`C:/math-worktrees/tools/sampler.py`, 로컬).
- 식별 프로세스를 멈춘 상태로 두는 변경은 실측 이득이 없어 되돌렸다. 메인 스레드는 작업 스레드를 기다리는 것이 아니라 오히려 기다림을 받는 쪽이었다.

**상주 프로세스 제안에 대한 사용자 교정.**

- **ⓐ** 통합자는 남은 git 비용을 줄이려 `cat-file --batch`·`update-ref --stdin` 상주 프로세스를 제안했다.
- **ⓑ** 사용자는 수명 관리가 더하는 복잡성을 우려했다.
- **ⓒ** 경량화 작업에서 속도 이득만 보고, 상태와 수명과 복구 규칙이 늘어나는 것을 비용으로 세지 않는 기울기가 드러났다.
- **ⓓ** 경량화 제안의 비용 칸에 "새 상태·수명·복구 규칙이 생기는가"를 먼저 적는다.

**병합이 드러낸 결함.** 작업자 브랜치에서 통과하던 계획 현재성 시험이 병합 뒤 결정적으로 실패했다. 이분 탐색으로 B4 병합을 원인으로 좁혔는데, 원인은 B4의 변경이 아니었다. 시험이 작업 스레드에서 엔진 메모리를 바꾸는 경쟁을 품고 있었고, 병합으로 시점이 옮겨지자 드러난 것이다. 변경을 소유 스레드의 제출 수신 직전에 적용하고 저장하도록 고쳤다. 템플릿을 빌려 쓰는 모듈(`test_academic_preparation`)이 원 모듈의 새 도우미를 갖지 못한 오류도 인계 확인 범위 밖이라 통합에서 처음 드러났다.

## 작업 너머 시사점

- 경량화의 한계는 설계의 내구성 단위에서 온다. 상태 변경마다 fsync된 객체와 CAS 게시를 하는 설계에서는, 시험 시간도 게시 횟수에 비례한다. 저장을 합치는 것(안 A)은 충돌 시 잃는 범위와 외부 효과 앞의 기록 순서를 바꾸는 복구 설계이므로, 필요하면 별도 작업으로 다룬다.
- dream에서 묶을 후보: [[L-0016]](위임 파이프라인)에 작업자 시험 운용의 교정과 `시험-지침.md`를 넣는다. [[L-0020]](do-math 구현과 운영)의 테스트 비용 항목에 캐시 제거, 조각, 템플릿, 남은 비용의 정체를 넣는다. [[L-0005]](작업 판단과 편향)에 cProfile 스레드 혼합과 상주 프로세스 제안의 비용 누락을 넣는다. [[M-0348]]·[[M-0349]]의 캐시 기록과 함께 읽는다.
