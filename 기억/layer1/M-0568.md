## 맥락

phase 017은 실제 비교와 미러 T4가 통과했지만 정본 295건 중 하나가 TemporaryDirectory 정리에서 실패했다. 018은 runtime close의 의미를 바꾸지 않고 시험 소유 Job의 종료 확인을 fixture에 추가했다. 새 manager가 실제 관측과 양쪽 295passed, worker 게시·분기 DB·현재 판본을 대조해 이 남김을 닫았다. 015부터 대기한 제품 22경로와 이번 fixture 2경로를 같은 관리 커밋에 담는다. 전체 일반·fresh T3·전수 변이와 다른 문서·의미·L01은 남아 있어 개발 완료는 아니다.

## 판단에 남길 조건

close 직후 보존 process handle의 wait258은 핸들 해제와 종료 완료가 다른 사건임을 보였다. 초기화된 live cwd는 WinError32였고 명시 종료·빈 Job 확인 후 삭제됐다. 정확한 과거 race는 재현되지 않았고 오류 순간 상태도 없다. 현재 동기화 공백의 교정과 새 전체 통과를 승인하는 데 역사 인과까지 확정할 필요는 없었다. 과거 bootstrap WinError5 원인도 미확인으로 남긴다.

manager 첫 검산은 정본 관련 검사 당시 생성 전 미러까지 최종 판본과 같아야 한다고 요구해 exit1이었다. 검사한 tree의 해시와 미러 생성 후 최종 전체의 양쪽 해시를 구별해 관리 검산을 고쳤다. 제품이나 원시험 결과를 바꾸지 않았다. 이 조건은 앞선 관련 회귀를 새 판본 증거로 재사용할 때 어떤 tree를 실제로 실행했는지 확인할 필요를 구체화한다.

다음 019는 원자료·결과·복원 파일의 네 owner를 실제 생산과 문서 검사에 연결한다. 수제 task.results는 물질화만 보이므로 _apply 생산·독립 bundle 비중복은 기존 수신·600k 흐름에 연결하도록 배정했다. 서로 다른 증거의 보증 범위를 맞추되 동일 장기 시나리오를 중복 구축하지 않는다.

근거의 진입점은 docs/do-math/continuous-development-2026-10-13/phases/018/manager.json 및 manager-evidence/verification.json·review.md다. 원task 자료와 24제품 바이트는 같은 디렉터리 raw-evidence.zip에 추적하며 경로별 SHA·선별 추적 범위는 preservation.json에 둔다. 압축으로만 보존하는 scratch·중복 snapshot의 원경로와 stage·commit 행정 수신은 로컬 보관이어서 정리로 사라질 수 있다. 압축은 자동 복원 지시가 아니다. 이전 원report와 역사 실패는 그대로 유지했다.
