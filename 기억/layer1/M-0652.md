## 장애와 사용자 요구

주차 함수 연구에서 정상 종료한 peer의 candidate.part를 candidate로 바꾸다가 WinError 5가 발생해 실행기가 종료됐다. 다른 세션 여섯 개는 분리된 호스트에서 계속 실행돼 모두 종료 코드 0으로 끝났으나 중앙 상태는 수집되지 않아 running으로 남았다. 이 중 두 세션은 개별 process.json에 PID가 있었지만 실행기가 가져오기 전에 종료돼 중앙 상태에는 PID도 없었다. Lean 브로커는 별도 프로세스라 살아 있었다. 이후 다른 실행에서 재시작돼 해당 후보가 생성되고 세션들이 수집됐다.

원래 접근 거부를 일으킨 프로세스는 확인하지 못했다. 현재 권한과 속성은 정상이고 해당 시각의 Defender·Application·System 이벤트에도 근거가 없었다. 임시 디렉터리에 실제 Windows 핸들을 열어 디렉터리 핸들의 오류 32와 내부 파일 핸들의 오류 5를 재현했고, 해제 뒤 이름 변경과 내용 보존을 확인했다. 이는 일시 잠금의 가능성을 입증하지만 원 사건이 Defender 때문이었다는 증거는 아니다. Defender 설정은 변경하지 않았다.

처음에는 오류를 작업별로 격리하고 스케줄러를 계속 돌리는 방안을 제안했다. 사용자는 정의되지 않은 상태를 통과하지 말고 실패해야 할 때 실패하길 원했으며, 제한된 재시도와 비슷한 범위만 허용했다. 현재 구현의 여러 상태 변경·저장 경계를 읽기 전에 종료 자체를 결함으로 단정한 제안은 철회했다. 교정 위치는 예외 처리 설계 단계다. 계속 실행하기 전에 그 전이가 실패 시에도 해석 가능한 상태를 유지하는지 먼저 확인해야 한다.

## 확인한 별도 결함과 수정

peer 완료는 candidate의 해시를 읽기 전에 session을 ended, job을 done, pipeline을 review로 바꾸고 있었다. 해시 읽기에 오류를 주입하고 실제 run의 치명 오류 저장을 거치면 review job이 없는 완료 상태가 영속화됐다. 재시작 뒤에도 그 peer는 수집 대상이 아니었다. 작업 도중 들어온 [[M-0650]]의 커밋은 no_research와 가용성 재평가를 분리했고, finish에 done 조기 반환도 추가했다. 이 변경을 읽고 보존하면서 해시 계산을 상태 변경 앞으로 옮겼다.

후보 동결·손상 후보 복원·게시의 세 디렉터리 이름 변경에는 같은 원천과 목적지를 유지하는 최대 60초 재시도를 적용했다. Windows 오류 5·32·33만 대상이며 이미 존재하는 목적지는 거부한다. 지속 오류와 예상 밖 오류는 전파돼 실행기가 종료된다. 일반적인 계속 실행 처리나 자동 재시작은 추가하지 않았다. 치명 오류에서는 상태 저장보다 먼저 traceback을 stderr에 남겨 저장이 다시 실패해도 최초 실패의 호출 경로를 보존한다. 프로세스 접근 거부를 종료로 해석하는 기존 alive 정책은 별도 문제로 남겨 이번에 바꾸지 않았다.

## 검증과 적용 경계

runtime/tests/test_resilience.py의 새 7개 시험은 실제 Windows 파일 잠금 해제, 재시도 기한과 원 오류 전파, 예상 밖 오류·기존 목적지 거부, 이름 변경·해시 실패 뒤 실제 run 종료와 재시작 시 review 한 개 생성을 확인한다. 전체 런타임 191개 시험이 248.020초에 통과했다. [[M-0651]]의 뷰 변경과 [[M-0650]]의 가용성 시험을 함께 포함한 결과다. 원인 재현용 임시 디렉터리는 제거됐으며 추적된 회귀 시험이 재현 진입점이다.

정본과 생성 사본을 동기화했다. 연구 인스턴스는 재시작하거나 재개하지 않았고 기존 dispatch 정지를 해제하지 않았다. 안전한 실패는 즉시 예외를 내는 것만으로 충분하지 않으며 그 직전 영속화할 상태의 완결성도 필요하다는 사례를 dream 종합 후보로 남긴다.
