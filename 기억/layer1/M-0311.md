사용자는 [[M-0310]]의 실행에서 발견한 문제와 개선점을 다시 검토하고 구체적인 수정 계획을 세우라고 요청했다. 분석 도중 연구와 실행기를 모두 정지하고, 문제를 해결한 뒤 새로 시작하려는 의도를 밝혔다. 기존 인스턴스 `RI-01M2S7DEH95FK8DEC0H0R4QMM8`에 2026-09-18 20:19 KST HOLD `1243d383db4c4a4fb3f11441e9c6df5c`와 사용자 정지를 적용했다. 20:20:26에 활성 실행 0개, 작업·운영 슬롯 반환, 관련 로컬 프로세스 부재를 확인했고 연구·운영 예약 두 개를 모두 비활성화했다. 정지 snapshot은 `25ead076824102e104f2a12989e6e5143e6e90b7`이다. 이후 자동 재개하지 않는다. 실제 정지 증거는 `docs/do-math/review-2026-09-18/stop.json`에 있다.

산출물 진입점은 같은 폴더의 `plan.md`다. 이전 답변의 29개 항목을 12개 수정 단위에 연결하고, 실제 결함·이미 수정된 부분·코드에서 확인한 위험·측정 후 채택할 개선을 나눴다. 수집·공급자 한도·현재성·종료 복구를 먼저 고치고 질문·계약의 연결을 정리한 뒤 효율을 측정하도록 제안했다. 구현은 이번 작업의 범위가 아니다. 기존 운영 담당이 남긴 정본·생성 사본 8개 코드 파일도 이 문서 커밋에 섞지 않는다.

이전 snapshot의 169개 실행은 고정된 분모로 유지했다. 20:02 독립 운영 AI가 한도 실패를 진단하고 연구를 재시작한 사실과 그 뒤의 추가 실행 12개는 별도로 보존했다. 한도 실패 16건은 원 작업 8개와 후속 운영 점검 8개였다. 같은 목적의 계획 실패 3개를 대표 1개로 묶어 6개 진단을 요청한 20:02 복구는, 18:20 해제 안내가 실제 재개와 자동으로 연결되지 않았다는 추가 근거다. 원 운영 보고가 수리 여부를 사용자 질문으로 올렸지만 독립 운영 계약은 범위 내 로컬 수리를 이미 허용한다. 기술적 불확실성·시간 부족은 후속 수리의 근거로 남기고, 사용자만 바꿀 목표·예산·허가와 구분해야 한다.

원 JSONL 재생으로 같은 Claude 세션의 시작 3개·결과 3개를 현재 수집기가 거부하는 것을 확인했다. 뒤의 두 결과는 task-notification 기원이었다. 마지막 결과를 무조건 택하는 수리도 충분하지 않으며 worker·collector의 결과 선택과 사용량 의미를 함께 정해야 한다. 다중 결과 비용 오집계의 실제 발생까지 입증한 것은 아니다. 같은 역할의 성공 뒤 오류 접두어로 질문을 일괄 제거하는 코드도 찾았지만 실제 질문 유실은 미확정이다. 이 둘은 수정 전 경계 사례를 재현할 대상으로 남겼다.

원 운영 보고의 원인 집계 오류도 발견했다. 14:02 보고는 거부 35건을 과제 생애 변화 32건과 지식 검증 승인 3건으로 설명했지만, 그 세부 진단 파일에는 실제 인용 계약의 질문·범위·완료 기준 변경이 포함돼 있었다. 35개 실행의 입력 snapshot과 거부 snapshot을 직접 읽어 다시 대조했다. 계약·기존 결과·종결 여부가 유지된 과제 변화는 26건, 인용 계약 변경은 6건, 지식 검증 승인은 3건이며 마지막 집단 중 2건에는 과제 종결도 겹쳤다. 이후 5건의 거부는 오류 기록상 계약 변경 3건·종결 2건이었다. 변경 집계는 판단의 의미적 유효성 판정을 대신하지 않는다. 이 자료는 `currentness-reassessment.json`에 보존하고 이전 진행 보고와 [[M-0310]]의 수치를 정정했다. 요약 보고의 주장과 원인 표를 대조하지 않고 같은 근거로 취급했던 분석상의 확인 누락이다. 수리 보고에는 실행별 판본·변경 필드·중복 원인의 대응을 남기고 수치 요약을 그 표로 검산하도록 P10에 추가했다.

무선택 계획 8개 중 하나에는 질문이 있었다. 큰 입력 바이트나 무선택 계획 수를 낭비의 양으로 바꾸지 않는다. 기존 부분 산출 복구·초기 계획 대기·독립 검토가 이미 맡은 기능을 확인하고 새 체계를 중복 설계하지 않는다. 원 스트림, 공급자 이벤트, 집계, 검토 코드 해시와 정지 판본은 `evidence.json`에 보존했다. 원 로그 전체와 이번 분석 보조 스크립트는 `.skill-workspace/`의 Git 제외 로컬 보관이며 정리하면 사라질 수 있다.

계획 원고의 독해는 연구 인스턴스와 분리한 Claude Opus 5 호출로 진행했다. stock writing-flow는 Codex 호출만 지원하므로 동일한 reader_prompt·스키마·인용 검증을 사용하는 작업 전용 연결 코드를 썼다. 첫 독해는 정상 완료됐으나 영수증 저장 코드가 bytes를 JSON으로 쓰다가 실패했다. 원 CLI 종료·스트림·최종 JSON·인용·입력 해시를 다시 확인해 추가 호출 없이 독해 결과를 회수했고, 설명 누락 12개를 고친 뒤 수정본을 다시 독해했다. 보조 스크립트 실패를 do-math 연구 실패나 공급자 실패로 집계하지 않는다.

최종 판본까지 독해 호출은 6건이며 보고된 모델은 모두 claude-opus-5였다. 정의가 뒤늦게 나오는 문제가 반복돼 도입을 역할·집계 단위 표로 다시 구성했다. 마지막 독해가 반환한 중심 이해를 합의와 대조했고, 남은 지적 6개에는 본문 근거를 들어 유지 처분을 남겼다. 원자료 검산 17개는 통과했다. 독해와 사실 검증은 각각 `reading-decision.json`, `reading-provenance.json`, `verification.json`으로 구별한다. 연구 구현의 회귀나 수학 증명을 새로 검증했다는 의미는 아니다.
