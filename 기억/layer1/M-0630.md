## 맥락

M-0629에서 미뤄 둔 항목이다. 설정의 `lean.command`가 `lake env lean` 꼴이면 브로커는 컴파일마다 lake를 띄웠고, M-0628의 직접 측정에서 그 lake가 컴파일마다 약 1 GiB의 커밋 메모리(`lake.exe` 991 MiB와 그것이 띄우는 `git.exe` 58 MiB)와 2~3초를 썼다. lake가 만드는 환경(`LEAN_PATH`, `PATH` 등)은 같은 프로젝트·설정이면 변하지 않는다. 사용자가 설명을 듣고 "그렇게 해줘"로 승인했다.

## 구현

- `Broker.capture_environment`: 명령에서 `env` 토큰을 찾아 그 앞을 lake(옵션 포함), 뒤를 lean으로 나눈다. `lake [옵션] env python -c "환경을 JSON으로 출력"`을 한 번 실행해 lake가 더하거나 바꾼 변수만 차이로 보관한다(`self.direct = {"argv": lean 부분, "env": 차이}`). 실패하면 `direct`를 비우고 사유를 `state["launcher"]`에 남기며 설정된 명령이 그대로 쓰인다. 호출 시점은 `reload_settings`의 성공 뒤이므로 기동과 설정 변경마다 다시 받는다.
- `launch`는 `direct`가 있으면 lean 부분과 그 환경으로, 없으면 설정 명령으로 돈다. 빌드의 `LEAN_PATH` 앞 추가는 그 위에서 그대로 작동한다.
- `closure_key`에 실행 방식이 들어간다(`direct`일 때만 문자열이 붙어, 기존 키는 그대로 유효). lake 경유 기준선과 직접 호출 기준선이 섞이지 않는다.
- `status`의 `launcher`가 방식과 사유, 받은 변수 이름을 보여 준다.
- 시험: `tests/fake_lake.py`(`env <명령>`을 `FAKE_LAKE=1`과 표지 `LEAN_PATH`로 실행, `FAKE_LAKE_FAIL`이면 7로 종료)로 직접 호출 전환과 실패 시 원 명령 유지를 확인한다. 첫 판은 `env`를 두 번째 토큰으로만 찾아 가짜 lake(`python -B fake_lake.py env …`)와 이전 검증 기록의 실제 명령(`lake --dir … env lean`)을 모두 놓쳤고, 토큰 위치 탐색으로 고쳤다.

## 검증

fake 시험은 런처 둘을 더해 전부 통과했다. 실제 Lean으로는 새 스모크 인스턴스(`broker-smoke-20261102-direct`, Git 제외)에서 같은 12모듈 기록을 빌드했다. 12개 모두 종료 코드 0, 공리 출력 343줄이 lake 경유 빌드와 한 줄도 다르지 않았고, 시간은 2분 53초에서 2분 21초로 줄었다. 보정표의 기준선은 import 없는 집합이 1,421에서 492 MiB로, `Mathlib.Tactic` 집합이 약 4,900에서 3,929 MiB로 내려갔다. 받은 변수에는 `LEAN_PATH`, `PATH`, `ELAN_TOOLCHAIN`, `LAKE_*` 들이 있었다.

## 작업 너머 시사점

- 경고: 환경을 받는 시점은 기동과 설정 변경뿐이다. Mathlib 프로젝트 자체가 바뀌면 LEAN.md대로 브로커를 재기동해야 하며, 이 경우를 자동으로 감지하지는 않는다.
- 경고: 실행 방식이 바뀌면 보정표에 새 항목이 생기고 옛 항목은 남는다. 첫 컴파일들은 보정부터 다시 한다.
- dream에서 묶을 후보: 도구 호출의 고정 부담을 호출마다 치르지 않고 한 번 받아 두는 전환(M-0628의 발견에서 M-0629를 거쳐 이번 적용까지).
