## 맥락

사용자가 브로커를 확장해 다중 모듈 import를 지원하라고 했다. 연구 인스턴스(`parking-unimodality-fresh-20261023-014524`, 기록 2,138개)의 세션들은 Lean을 `output/lean/<이름>.lean`의 평평한 트리로 나누고 맨이름으로 서로 import하며, 브로커 이전에는 자기 스크립트(`code/compile_lean.py`)로 손으로 적은 순서대로 `lake env lean -R <루트> -o <세션>/work/olean/<이름>.olean`을 돌리고 `LEAN_PATH` 앞에 그 폴더를 붙였다. 의존 모듈은 이전 기록에서 복사해 함께 공개한다. 브로커의 `run`은 파일 하나만 알아 `import Parking`이 풀리지 않았다.

설계 전에 실험 셋으로 바닥을 확인했다. `lake env`는 미리 둔 `LEAN_PATH`를 맨 뒤에 보존한다. `lean -R <루트> -o`가 만든 `.olean`은 다른 파일이 `LEAN_PATH`로 import할 수 있다. `lake env`가 주는 환경을 한 번 잡아 두면 `lean`을 직접 불러도 같은 결과가 나오고 lake 기동분(약 2.6초, 약 1 GiB)이 빠진다. 셋째는 이번 커밋에 넣지 않았다.

사용자는 "하나씩 쳐내자"고 했고, 문제 지도 12항목과 결정 넷(브로커가 그래프를 소유, 인스턴스 공유 캐시, 기록당 루트 하나, lake 부담 제거는 뒤에 따로)을 풀어 설명한 뒤 승인했다. 사용자의 확인 질문은 "인터페이스는 크게 다르지 않고 브로커가 안에서 알아서 하는가"였고, 답은 그렇다였다.

## 구현

- 순수 함수: `module_name`·`module_path`(루트 상대 경로와 모듈 이름의 대응, Lean의 `-R`과 같음), `discover_modules`(대상에서 헤더를 따라 로컬 의존을 찾아 의존 순서로 반환, 순환·가림·루트 밖 경로 거부), `module_keys`(Lean 판, 모듈 이름, 소스 바이트, 로컬 의존들의 키의 해시).
- 브로커: 빌드 요청(`b` 접두 ID)을 `ingest_build`가 모듈 작업들로 펼친다. 캐시(`runner/lean/cache/<키>.olean`)에 있으면 빌드의 lib 폴더(`runner/lean/builds/<빌드>/lib`)로 복사해 `cached`, 없으면 `deps`를 단 작업. `deps_done`이 적격 조건에 들어가고 `propagate`가 실패한 의존의 후행을 "dependency X ended with exit code N" 사유로 닫는다. `launch`는 `-R`·`-o`와 `LEAN_PATH`(lib 앞 추가)를 준다. `finish_module`이 성공한 `.olean`과 Lean 출력 로그를 캐시에 한 번만 쓰고(임시 이름 뒤 `os.replace`, 이미 있으면 두고, Windows가 거부하면 건너뜀) 빌드를 `settle_build`로 닫는다. `prune`은 활성 작업이 import하는 작업을 지우지 않고, 지운 빌드의 lib 폴더를 삭제한다.
- 보정 키는 외부 import만으로 만든다. 처음에는 전체 import로 보정 소스를 써서 `import A`가 풀리지 않아 보정이 실패했다(fake_lean 시험에서 발견).
- 클라이언트: `build <인스턴스> <루트> <대상...> --session --expect-mb [--no-wait] [--timeout]`, 빌드 ID를 받는 `wait`·`result`·`cancel`, `status`의 `builds`. `report_build`가 대상의 출력을 작업 폴더나 캐시 로그에서 그대로 전달하고 모듈별 요약 한 줄을 낸다. 종료 코드는 모듈 종료 코드의 최대, 빌드 실패 3, 취소 4.
- fake_lean이 `-o`에 가짜 `.olean`을 쓰고 `LEAN_PATH`에서 로컬 import를 찾는다.
- 세션 프롬프트(runner.py)에 `build` argv를 추가했고 LEAN.md·common.md·research.md·review.md·protocol.md(기록당 루트 하나)·RUNTIME.md·SKILL.md·README를 맞췄다.

## 발견한 결함과 수리

- `collect()`가 호스트가 막 교체 중인 `process.json`을 읽다 Windows에서 PermissionError로 죽었다. 기존 경쟁이며, 읽기 실패면 다음 틱으로 넘기게 했다.
- 기존 `state.json`에 `builds` 키가 없어 `start()` 뒤 첫 빌드 접수가 `'builds'`로 거부됐다. 실제 Lean 빌드에서 발견했고 `setdefault`를 보태고 회귀 시험을 넣었다. 기존 인스턴스의 브로커가 모두 겪을 결함이었다.
- 빌드 레코드의 모듈 상태를 `launch`에서 갱신하지 않아 `running`이 보이지 않았다. 취소 시험이 잡았다.

## 검증

fake_lean 시험 여섯(의존 순서·나란히 실행·캐시·변경 전파, 실패 전파, 거부 셋, 취소, 옛 상태 파일, 명령줄)이 기존 31개 위에서 통과했고 전체 스위트도 통과했다. 실제 Lean으로는 위 인스턴스의 기록 `kff3122af7…`의 `lean/` 12모듈을 스모크 인스턴스에 복사해 `build`로 돌렸다. 12개 전부 종료 코드 0, 공리 목록은 그 기록의 감사와 같고, 보정 포함 2분 53초였다. 측정 기준선은 `Mathlib.Tactic`을 import하는 모듈이 약 4.9 GiB, `Parking`이 약 3.0 GiB다. 같은 소스의 두 번째 빌드는 12개 전부 캐시에서 와 0.85초에 끝났다. 스모크 인스턴스와 캐시는 `.skill-workspace/broker-smoke-20261102` 아래의 Git 제외 로컬 자료다.

## 작업 너머 시사점

- 경고: 보지 않은 것. 차가운 캐시의 첫 Mathlib 컴파일, 예산 초과로 대기하는 긴 사슬, 실행기가 띄운 세션이 프롬프트의 `build`를 실제로 쓰는 경로, 두 세션이 같은 모듈을 동시에 빌드해 캐시 쓰기가 겹치는 경우(코드는 "먼저 쓴 쪽이 남는다"로 처리하나 실측은 없다).
- 다음 작업 후보: 브로커가 기동 때 `lake env`의 환경을 잡아 두고 `lean`을 직접 부르는 lake 부담 제거. 사용자가 뒤에 따로 하기로 했다.
- dream에서 묶을 후보: 외부에서 받은 변경을 들일 때(M-0627)와 기능을 더할 때(이번) 모두, 실제 도구로 한 번 돌려 본 뒤에야 문서의 "확인됨" 문장을 쓴 관례. `builds` 키 결함은 fake 시험 전부가 통과한 뒤 실제 실행에서만 드러났다.
