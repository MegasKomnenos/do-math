3-B의 원문은 `조사/결함-범주.md` 460~464행이다. 역할 계약 전건과 live·복구·단계별 요구 근거가 실제 입력에 실리거나 정확한 참조로 읽혀야 한다. `context_store.INLINE_SCOPES`와 `_ROLE_DIRECT`는 포장·접근 분류다. 이 목록의 존재를 의미 판단에 필요한 근거의 충족으로 대신하지 않았다. 열 개 연구 역할 계약의 실제 입력 문언, `_context`, `prepare_role_input`, `review_cycle.context_for`, 복구 프롬프트 생산 코드를 대조했다. 열 개 역할의 요구 키와 단계별 중첩 좌표를 `role_input_requirements`에 선언하고, 기존 입력 시험에 정확한 값·참조 검사를 연결했다. 일반 진입의 전체 역할 순회는 실제 도메인 생산자가 만든 과제와 공개 활성화·형식 검토 장면 위의 실제 엔진·저장소·포장기를 사용한다. 역할마다 모델을 다시 호출하지 않는다.

처음 새 일반 검사에는 두 가지 잘못된 가정이 있었다. 카탈로그 참조마다 snapshot 필드가 있다는 가정과, 모델에게 주는 비교 과제 목록이 검사기의 전체 과제 목록과 같다는 가정이다. `5h72h1nj`에서 2개 실패와 3개 오류가 발생했고, `ffcvljug`에서는 과제 원문의 추가 `content_sha256` 때문에 2개 실패가 남았다. 제품을 이 시험에 맞춰 바꾸지 않았다. 역할 manifest의 snapshot과 정확한 카탈로그 경로·해시·크기의 결박을 대조하고, 모든 과제의 원문을 최초 `_context`가 만든 값과 비교했다. 계획의 비교 ID는 ready와 returned의 합집합으로 확인하고, 준비가 모든 planned 과제를 보존하는지도 확인한다. 출처마다 원문을 실제로 읽고 누락·해시 손상·잘림을 성공으로 받지 않는다.

새 작업은 main 실행 중 main을 편집하지 않기 위해 같은 d8e25c55의 `goal-20261004-inputs` 작업 트리에서 수행했다. 전체 실행의 작업자 하나가 끝난 뒤 비어 있는 슬롯 하나만 썼다. 후보의 전체 구조 44개와 관련 unit 20개·sim 32개, 합계 96개가 `5633ta6y`에서 80.7초에 완결 통과했고 실행 중 변경은 없었다. 단일 일반 진입 전건 검사는 10.891초로 sim의 2초 예산을 넘는다. 이 비용을 기록하고 의미 검사 범위나 단언을 줄이지 않는다. 후보 시험의 초기 실패는 새 검사 가정의 오류이며, 기존 제품 결함의 재현 성공으로 세지 않는다. 후보 보고와 작업 트리는 로컬 보관이다.

일반 입력 열 개 역할의 전건 검증을 추가한 것과 3-B 전체 종료는 구별한다. 다섯 검토 단계·복구·위임·초기화·영향 검토·설치 복구의 선언 전건과 실제 입력 사례 연결은 아직 남았다. 설치 복구 AI는 일반 `contracts.ROLES`가 아니라 `repair_execution.repair_prompt`의 고정 프롬프트와 JSON을 받으며, `계약/독립-운영.md` 자체는 그 AI에게 지급되지 않는다. 정상 감독의 모델 없는 경로와 별도 복구 호출을 같은 역할 모집단으로 혼동하지 않는다.
