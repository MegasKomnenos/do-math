## 맥락

재구축과 보충 커밋 전체를 평가한 뒤 남은 문제 넷을 보고했다. 사용자는 그중 둘을 "간단하게 별도 스킬 없이" 고치고 커밋하라고 지시했다. 그래서 test-driven-development 스킬과 write-for-reader의 독해 절차는 적재하지 않았다.

1. **연속 실패 정지**: 계획이 실패하면 `tick`이 곧바로 새 계획을 띄웠다. 로그인 만료, 잘못된 모델 이름(`load_settings`는 형식만 검사), 깨진 CLI 경로, 한도 문구 변경처럼 원인이 지속되면 실패와 재계획이 끝없이 반복됐다.
   - `PLAN_FAILURE_LIMIT = 3`(runner.py 상수, 조정 가능하다는 주석을 남김)을 두었다. 계획이 연달아 실패하면 `state.halted = {reason, at}`을 기록하고 모든 새 파견을 막는다. active 세션이 없으면 `run`이 반환한다.
   - 계획이 반영되면 `plan_failures`가 0이 된다. `run`이 시작되면(`start` 포함) `halted`와 수를 푼다.
   - 공급자 한도가 탐지된 계획 실패는 수에 넣지 않았다. 그 경우는 `limit_until` 대기가 이미 처리한다. 이 제외는 메인의 판단이며, 사용자 지시는 "연속 3번 실패"였다.
   - 연구·검토 실패는 사건으로 계획에 가므로 수에 들지 않는다.
   - `blocked()`와 `status()`의 중복 판정을 `dispatch_blocks(instance, state)` 하나로 합치고 `halted`를 더했다.
2. **사건에 사실 담기**: plan.md가 `runner/state.json`의 `sessions` 내부 필드를 읽게 되어 있었다. 이는 protocol.md의 "runner/ 내부 스키마는 실행기 책임"과 어긋났다.
   - `session_failed`에 `category`, `request`, `task`(요청이면 `requests[key].task`, 계획이면 그 세션 `input.json`의 task), `origin`, `limit`, `exit_code`, `launch_error`를 담았다.
   - 실패한 계획이 소비한 사건은 그 `task.events`에 남아 다음 계획에 간다. 연달아 실패하면 겹겹이 중첩되지만 깊이는 정지 한도에서 멈춘다.
   - 계획 task에 `previous_plan`을 넣고, plan 반영 시 `state.last_plan`을 갱신한다. check.py는 `previous_plan`이 있으면 실재하는 plan 기록인지 확인한다.
   - `requests`는 protocol.md 1절에서 계획이 읽는 유일한 실행 상태 계약으로 승격했다. plan.md 87행의 읽기는 그대로 둔다.
   - 문서 갱신: protocol.md 1·2절, plan.md(직전 연구 현황·실패 사건 표·원 작업·원인 분류), RUNTIME.md(dispatch_blocks, 상태 표 두 줄, 사건 설명, 정지 문단, run 종료), SKILL.md(정지 확인과 재기동).

## 터득한 것

- **시험**: `test_repeated_plan_failures_halt_until_restart`를 먼저 추가했고 `KeyError: 'halted'`로 실패하는 것을 확인한 뒤 구현했다. 가짜 세션 시나리오 `plan_failure`(계획이 exit 1, 산출 없음)를 썼다. 시험은 다음을 확인한다: 계획 3회 실패 후 정지, 추가 tick에서 파견 없음, 중첩 사건 안에 첫 `start`가 보존됨, `run()` 재기동이 정지를 풀고 3회 더 실패한 뒤 반환됨. 기존 실패 시험에는 사건의 `category`·`task`·`limit`·`origin` 단언을 더했다. 실행 결과 20개가 통과했다.
- **옛 상태 호환**: 이 변경 전의 state에는 새 키가 없다(예: `.async/do-math-rebuild-20261021/.../evidence/` 인스턴스). `dispatch_blocks`는 `state.get("halted")`로 읽고, `run`은 `last_plan`을 setdefault로 채운다. 증거 인스턴스에서 `status`가 `['complete']`를 내는 것을 확인했다.
- **미러 표시**: `build_skill_mirrors.py`를 실행하자 `.agents`의 common/research/review.md가 git status에 M으로 떴다. 내용 diff는 비어 있었다(통계 정보만 바뀐 것). 커밋 대상에서 저절로 빠진다.

## 작업 너머 시사점

- 평가에서 보고했지만 이번에 다루지 않은 것은 둘이다. (3) 보충 규칙의 행동 검증을 위한 중간 크기 시범 목표, (4) plan.md 110행 목표 검토 요청 조건과 protocol.md 실행기 작성자용 절의 작은 공백.
- 정지 한도 3과 한도 실패 제외가 적절한지는 첫 실사용 인스턴스에서 확인한다. 일시적 CLI 실패가 건강한 인스턴스를 멈추면 상수를 올린다.
