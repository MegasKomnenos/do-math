Software Heritage의 기존 fetch는 SWHID 뒤 qualifiers를 정규식으로 받아 놓고 무시했으며, content 바이트를 요청한 고유 해시와 대조하지 않았다. 공식 SWHID 예의 simplefarm.ml을 익명 API로 확보해 파일 527바이트·27줄과 sha1_git 일치를 확인한 뒤 수정했다. 요청한 lines=9-15는 실제 해당 7줄을 제공하고 검증된 전체 파일을 별도 참조로 보존한다.

metadata의 checksums.sha1_git와 SWHID를 요청한 content ID와 대조한다. 전체 바이트의 길이, Git blob 방식의 SHA-1, 제공된 SHA-1·SHA-256·BLAKE2s-256을 검사한다. 데이터가 다르거나 원 파일 요청이 제한되면 metadata를 지우지 않고 component별 오류로 남긴다. 조각의 해시를 부모 SWHID와 같다고 표시하지 않으며 integrity는 complete_content의 검사다.

origin·visit·anchor·path·lines의 문법과 중복을 검사한다. origin은 해독 후 민감 URL 정제를 적용하고 path는 이스케이프된 표기를 보존한다. origin·anchor·path의 관계를 직접 검증하지 않았으므로 context_verified=false를 반환한다. 이 문맥을 근거로 외부 저장소를 방문하거나 path를 다른 파일 선택으로 재해석하지 않는다. 공개 archive/n2t SWHID 링크는 로컬에서 식별자로 읽는다.

첫 SDK 보고 20260910T231934Z-swh-content-mcp.json은 조각 회수 뒤 전체 파일의 extract에서 format_not_supported로 미완료였다. 원 API의 application/octet-stream이 기계적 텍스트 추출을 막았다. 기존 GitHub·압축 파일과 같은 UTF-8/NUL 판정을 적용해 텍스트를 읽게 했으며 원 MIME과 원 바이트는 보존했다.

새 SDK stdio services/scholarly-mcp/data/validation/20260910T232052Z-swh-content-mcp.json은 completed=true다. 공식 예의 9~15행과 전체 27줄의 대조, SWHID URL의 한 줄 선택, 범위 초과 시 전체 파일 보존, 실제 0바이트 content를 확인했다. 파일을 실행하지 않았다. 손상 바이트·다른 metadata·403·잘못된 qualifier·인코딩된 origin의 정제·범위 초과 회귀를 포함해 공통 204개 검사가 통과했다.

전체 구현은 진행 중이다. 다음 Software Heritage 작업은 directory/revision의 Vault 회수다. 공식 API는 이메일 없이 archive 준비와 조회를 제공한다. 빈 디렉터리 SWHID의 Vault GET은 실제 done 상태를 반환했다. 아직 이 아카이브 회수 경로를 구현 완료로 세지 않으며 별도 API 키·계정·이메일이나 CLI 재시작을 요구하지 않는다. 전체 완료 전이므로 푸시하지 않는다.
