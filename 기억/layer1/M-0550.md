사용자는 기존 /goal을 지운 뒤 현재 진행 상태와 전체 완료 경로를 구체적으로 분석하게 했다. 분석은 원문 합의, 현재 작업판, 커밋과 raw 보고를 대조했다. 최근 개별 작업은 재현·관련 검증·커밋으로 닫혔지만, 109개 추적 항목의 101개가 planned이고 이전 재검토 25영역 중 실제 완료 표시는 한 영역뿐이었다. 이 숫자는 미구현 기능 수나 완료율이 아니다. 지역적인 검사기 수리와 프로젝트 전체 종료의 연결이 약하다는 판단이었다. 사용자 요구는 이 교훈을 services/continuous-development의 특성에 맞춰 실제 설정에 적용하라는 것이었다.

서비스의 README, protocol 전체와 run.py/check.py의 실제 동작을 읽었다. task뿐 아니라 모든 task 종료 뒤의 manager도 새 codex exec 세션이다. 공용 context/plan/seams는 manager만 갱신하며, task들은 그 phase의 고정 입력을 읽고 자기 범위 및 report/evidence에만 쓴다. 실행기는 검사를 자동 호출하거나 재시도하지 않으며 manager.json의 next를 따른다. task 실패도 보고와 근거로 manager가 판단해야 한다. review phase와 모든 G의 근거 없이 next:null을 완료나 중단 표현으로 쓸 수 없다. 같은 phase를 재기동하면 task를 다시 실행하므로 자동 재개로 취급할 수 없다.

docs/do-math/continuous-development-2026-10-13에 실제 records를 준비했다. context의 G1~G8은 원문 19+11 의무, 보존 61, 원래 P2 12, 검출력, 최종 일반·fresh T3·현재 함수 극단 변이/정상 기준, 실제 T4/T5/말뭉치, 최종 review와 인도 일치를 보존한다. 시간 예산은 소프트이며 제품의 계약상 시각/임대와 예산 강제 종료를 구별한다. 요구를 달성한 척 범위를 줄이거나 새 /goal을 만들지 않는다. 이미 완료한 성질을 반복 구현하지 않고 다음 판단을 바꾸는 구체적 남김으로 계획을 갱신하게 했다.

첫 work phase 001은 세 개의 writes=[] task다. closure-map은 원래 모집단의 현재 증거·공백·끝나는 질문과 기존 재검토 실적을 구분한다. document-closeout은 실제 문서와 현재 검사기의 남은 결속을 유한한 묶음으로 끝낼 범위, 최근 수정의 유지 실익과 한계를 판정한다. gate-readiness는 실행기·현재 대상·정상 기준·실환경 부족 조건을 확인한다. 이들은 자기 보고만 쓰고 서로의 결과를 기다리지 않으며, manager가 전부 종료된 뒤 결과를 통합한다. 첫 phase에서 전체 일반/T3/변이/실호출이나 전체 제품 코드 재감사를 시작하지 않는다. 이후 소스 변경과 검사는 기본 한 task로 묶고, 독립 읽기 검토에 병렬성을 사용한다.

서비스 시작 후 현재 실행 판단은 새 context/plan 한 곳으로 옮긴다. 이전 대형 단계-전환표는 B134까지의 기준선과 원증거로 보존하고 이중 현재판으로 갱신하지 않는다. sources/requirements-index.json은 19/11/61/12 원문 식별자의 찾아보기이며 완료 판정이 아니다. baseline.json은 HEAD 56e961ff, 정본 969개 파일 및 원자료·서비스 해시와 기존 dirty/untracked를 기록한다. 새로운 목적을 요약문만으로 다시 만들지 않도록 사용자 교정과 원문 진입점도 남겼다.

task의 Git commit 금지는 서비스 protocol을 따른다. manager가 검수 뒤 commit-harness의 기억·색인·정확 파일 커밋을 관리 마감으로 맡으며 제품 코드를 직접 고치지는 않는다. 미러 생성의 쓰기 범위도 task에 배정한다. 미래의 모든 task와 모델을 미리 고정하지 않고 모델·effort는 설치된 Codex 기본값을 사용한다. 제공된 서비스의 README에는 예전 output 경로와 현재 없는 설계 링크가 있어 실제 services 경로와 protocol/run/check를 기준으로 구성했다. 서비스 본체는 기존 미추적 사용자 파일이며 수정하거나 이번 커밋에 흡수하지 않았다.

start.py는 공식 phase 검사 뒤 기존 실행기로 넘기는 얇은 시작 절차다. 같은 phase의 report/manager/log/시작 흔적을 거부하고 배타적 시작 기록으로 중복 기동을 막는다. PID와 실제 종료 코드를 남기며 timeout이나 자동 재개기를 추가하지 않는다. start.ps1은 기본으로 숨긴 창에서 controller를 시작하고 CheckOnly/Foreground도 제공한다. 중단 시 기록만으로 종료를 추측하지 않고 실제 프로세스와 보고를 확인한 뒤 새 phase 또는 manager만 재호출하는 절차를 README에 적었다.

서비스 기존 테스트는 실제 모델 없이 31개 중 30개 통과, symlink 권한 부족 1개 건너뜀이었다. 그 최초 콘솔 출력 자체는 파일로 따로 보존하지 않았고 준비 정보에 그 한계를 명시했다. 실제 첫 phase와 Python/PowerShell check-only는 exit 0을 확인했다. 격리된 임시 복사본에서 중복 phase와 경로 이탈 인자가 exit 2로 거부됨을 확인해 별도 launcher-check.json에 실제 출력과 함께 보존했다. 원래 103개 식별자의 중복 없음과 제품 969파일·원자료·서비스 본체의 바이트 해시 불변도 확인했다. 설정 검사 통과는 do-math 완료나 실제 Codex 모델 호출 성공의 증거가 아니다.

이번 요청은 설정이므로 준비 세션에서 실제 Codex 개발 세션을 기동하지 않았다. run의 start.ps1을 실행하면 세 읽기 작업과 후속 manager가 시작한다. 공용 문서·원자료 색인·첫 배정·시작 파일은 추적 보존하고, runtime과 세션 logs는 로컬 보관으로 구분했다. 향후 report와 결정에 필요한 증거만 정확하게 커밋하며 거대한 scratch를 일괄 포함하지 않는다. 푸시·graphify 갱신·기존 연구 재개/삭제는 수행하지 않았다.
