## 맥락

사용자는 `docs/do-math/검사-경량화-설계-2026-09-26.md`와 그 근거인 `…-검사분류.md`(R1~R48)를 바탕으로 do-math 구현을 지시했다. 방침은 네 가지였다. 영향 영역 전체의 근본 해결, 구현 모습에 근거한 실익 판단과 과감한 포기, 증상이 아닌 근본 범주의 해결, 전제가 틀리면 방향 수정이다. 설계의 사용자 결정 D1~D7은 위협 모델을 우발적 변경으로 좁힌다(AI의 의도적 변조는 고려하지 않음). 이 결정은 [[M-0341]]·[[M-0346]]의 "파일 바이트를 사용 때마다 전건 관측한다"는 전제를 대체한다.

작업은 절 순서가 아니라 근본 범주로 나눠 git worktree 네 개에서 병렬로 진행했다. G1은 신뢰 환경(설계 3·6·7절), G2는 취소·관찰 콜백(4절), G3는 상태 저장소와 물리 경계(R3~R12, R6·R7·R24, R39), G4는 불변 바이트 재해시와 파일 변경 탐지(나머지 R)다. 이어서 digest 도우미 정리(G5)와 느린 시험의 구조 개선(tfix)을 별도 worktree에서 진행했다. 통합 브랜치에서 모두 병합해 전체 시험을 돌린 뒤 main 작업 트리에 스쿼시하고, 설계 9절의 성능 측정을 실제 인스턴스로 수행했다. 이 커밋은 그 결과 전체와 설계 문서 두 개, 이음새 계약(`docs/do-math/검사-경량화-이음새-계약.md`)을 담는다.

## 병렬 분할의 이음새

처음 파견에서는 파일·함수의 소유 경계만 정했다. 사용자가 두 가지 위험을 지적했다. 작업자들이 자기 영역에서 완결적으로 일하면 인터페이스·스키마·이름을 양쪽에서 따로 발명할 수 있고, 그러면 통합이 깨진다는 것이다. 이 지적은 옳았다. 소유 경계는 텍스트 충돌을 줄일 뿐, 같은 지식을 두 곳에서 구현하는 의미적 중복은 막지 못한다.

교정은 통합 책임자가 이음새를 작업자보다 먼저 정하는 것이었다. 코드에서 실제 이음새를 확인한 뒤 공유 커널과 이음새 계약을 만들었다.

- 파일 메타데이터 지문: `file_io.stat_fingerprint`, `file_fingerprint`, `fingerprint_settled`, `fingerprint_json`
- 지문 기반 해시 캐시: `cached_sha256`, `sha256_file`
- 검증된 불변 artifact 집합: `repository.VERIFIED_ARTIFACTS`, `verify_artifact`, `artifact_verified`, `mark_artifact_verified`

계약은 이 밖에도 head 이동 훅의 소유(G2 단독), head 키 메모이즈의 적용 범위(게시된 상태에만), 시험 픽스처 사용, 용어 소유를 정했다.

작업자가 커널 브랜치를 자기 브랜치에 병합하는 것은 권한 분류기가 거부했다("Modify Shared Resources"). 거부된 행동을 메인이 대신 하지 않았다. 대신 커널 병합을 통합 단계로 옮기고, 커널에 기대는 항목은 `미완료(커널)`로 남기게 했다. 통합 트리에서 그 항목을 재개 작업으로 마무리했다. 병합 뒤에는 새 해시 도우미, 커널 밖의 stat 튜플, 새 캐시를 grep으로 전수 감사했다.

작업자가 돌려준 이음새 요청은 커널에 반영했다. 사례는 셋이다.

- G3: artifact 키에 크기가 없어 크기가 바뀐 증거 행을 통과시킨다. 기존 시험 2개가 이를 잡았다.
- G4: racy-git. Windows 파일 시각의 단위는 약 15.6ms이므로, 읽은 직후 같은 크기로 다시 쓴 파일은 지문이 같게 남을 수 있다.
- G1: 나노초 시각이 `canonical_json`의 안전 정수 한도를 넘는다. 그래서 `fingerprint_json`은 두 시각을 문자열로 저장한다.

사용자는 이번 변경과 무관한 해시 도우미 중복도 정리할지 물었다. 조사 결과, `canonical_json` 판본(상태 값 식별)의 복제가 7개와 인라인 21곳, 압축 JSON(저장 영역 밖 값)의 변종이 7개였다. 두 부류는 직렬화 규칙이 다르므로 서로 다른 지식이다. 그래서 둘을 하나로 합치지 않고, 부류마다 정본을 하나씩 두었다(`exact_content_hash`, `file_io.json_digest`). 병렬 브랜치와의 충돌을 피하려고 병합 뒤 G5에서 처리했다. `json_digest`를 `repository`가 아니라 `file_io`에 둔 이유는 worker 모듈이 Windows Job 안에서 패키지 없이 적재되기 때문이다. 값이 저장되어 다시 대조되는 변종(formal의 ASCII 이스케이프 3곳, scheduled_operator 2곳)은 규칙을 바꾸지 않았다.

## 시험 대기의 원인과 제거

전체 작업은 7시간 넘게 걸렸고, 그 대부분이 시험 대기였다. 원인은 넷이었다.

1. 4코어 머신에서 에이전트 4개가 동시에 시험을 돌려 CPU가 100%를 유지했다. 시간 의존 시험이 비선형으로 불어나 한 개에 2~7분, 최대 1,086초가 걸렸다.
2. 파견문의 "고친 모듈을 가져오는 integration 시험"이라는 기준이 사실상 전체 스위트를 가리켰다. `engine.py`가 중심 모듈이기 때문이다.
3. 같은 기존 실패를 세 에이전트가 각자 기준 커밋에서 다시 계산했다.
4. 반환을 마친 에이전트의 백그라운드 시험이 계속 돌았다.

처음 제안한 대책은 머신 전역 잠금이었다. 사용자는 동시 실행이든 순차 반복이든 중복은 같은 비효율이라고 지적했다. 잠금은 경쟁만 줄일 뿐 총작업량은 그대로이므로 버렸다. 채택한 수단은 네 가지다.

- **`run_tests.py` 결과 캐시.** 같은 입력에서 통과한 unit·integration 시험은 다시 돌리지 않고 원 보고서 경로와 함께 캐시된 통과로 보고한다. 실패는 캐시하지 않는다. lean·resource 그룹은 항상 실행한다. 처음에는 키가 트리 전체 하나여서 시험 파일 7개만 고쳐도 전체가 무효가 됐다. 사용자가 그 점을 지적해 키를 둘로 나눴다. 하나는 공유 입력(제품, 문서, 공용 픽스처, 판본)이고, 다른 하나는 시험 모듈별 입력(자기 파일과 import하는 시험 모듈, 전이적으로)이다. `test_file_io`만 고치면 그 모듈의 8개만 다시 돌고 407개는 캐시에서 보고됨을 실측했다.
- **공유 기준선.** 기존 실패는 한 번만 확인해 공유했다.
- **소유 루프의 사건 기반 대기.** 호출 중에 초당 50회 돌던 바쁜 폴링을 `ModelCalls.wait`로 바꿨다. 호출 반환, 시작 콜백, 관찰이 루프를 깨우고, 상한은 `OWNER_POLL_SECONDS=0.25`다. 같은 두 시험이 단독 실행에서 216초에서 105초, 117초에서 57초로 줄었다.
- **느린 시험의 구조 개선(tfix).** 공개 활성화 픽스처는 약 95초가 드는데, 규칙과 무관한 시험 16개 안에서 14회 반복되고 있었다. 이를 검증된 활성 상태에서 시작하도록 바꿔 대상 22개의 합을 2238초에서 1473초로 줄였다. 공개 경로의 연결 검증은 전용 시험 3개가 유지한다. `ParallelEngineTests` 네 개는 옮기자 기존 실패가 사라지거나 판정이 바뀌어 원래 시작 상태로 되돌렸다. `BoundaryFixture`는 픽스처 계약("준비와 승인은 실제 적용, 주입 금지")을 존중해 바꾸지 않았다.

## 설계 전제의 수정

- **게시 직후 평가(설계 4.2 2항).** "정지 사유 변경은 모두 게시로 끝난다"는 전제는 주 루프 수준에서 거짓이었다. clock guard 퇴행과 대화 lease 상실이 게시 없이 일어난다. G2는 호출이 살아 있는 동안 매 바퀴 미게시 변경을 게시하도록 해 구조로 성립시켰다. 이 매 바퀴 게시가, 계산 스레드에서 엔진 상태를 고치던 시험 2개의 데이터 경합을 CAS 충돌로 드러냈다. 제품이 아니라 시험을 고쳤다(소유 스레드가 개정을 게시하도록).
- **R12 변경 세대 카운터.** 상태를 직접 고치는 지점이 약 318곳이어서 포기했다. 대신 서명 계산을 89ms에서 17ms로 줄였다.
- **R5 경로 목록의 증분 갱신.** 파일과 디렉터리가 같은 이름으로 충돌하면 Git이 파일 쪽을 조용히 버렸다. 이 충돌을 거부하는 검사를 추가해, 기존에 있던 데이터 유실 경로도 막았다.
- **R4.** 부모 head의 검증 집합을 승계하는 구조 대신 프로세스 전역의 `VERIFIED_ARTIFACTS`를 썼다. 자기가 게시한 head를 다시 읽는 비용이 실측 7.1~9.3초에서 9ms로 줄었다.
- **신뢰 환경(G1).**
  - `lean.exe`는 84KB의 실행기이고 커널은 `libleanshared*.dll`(52~68MB)에 있으므로, DLL을 지문과 내용 해시 대상에 더했다.
  - NTFS 터널링 때문에 같은 이름을 지우고 약 15초 안에 다시 만들면 생성 시각이 보존된다. 그래서 크기와 수정 시각까지 보존한 교체는 지문으로 잡히지 않는다(남는 위험으로 문서화).
  - `recheck` 삭제 뒤 대기를 재개할 경로가 없어, 기록 변경을 감지해 재개하는 경로를 새로 만들었다.
- **`lake env` 비용(설계 3.6).** 설계는 약 1초로 가정했지만 실측은 약 2초였고, 이 때문에 게시 관문이 2.8초로 기준(1초)을 넘었다. Lake 검색 경로는 판본 식별이 이미 해시로 고정한 입력의 함수다. 그래서 그 입력을 키로 프로세스 안에서 메모했고, git top-level 경로도 경로별로 메모했다. 두 번째 호출이 3.08초에서 0.59초로 줄었다.
- **CLI 기동 비용(설계 밖, 같은 범주).** CLI 프로세스마다 제품 상수인 내장 스키마 80개를 메타스키마로 다시 검사해 약 2초가 들었다. 이 검사를 unit 시험으로 옮겼고, 밖에서 들어오는 스키마의 검사는 `ResearchRepository.register_family` 경계에 남겼다. `status`가 3.4초에서 1.8초로, `query`가 2.8초에서 1.2초로 줄었다.

## 작업 중의 운영 실수

- **백그라운드 제한 시간.** 긴 실행에 백그라운드 명령의 제한 시간 10분을 걸어 두 번 중단했다. 긴 실행은 완료 표지 파일을 쓰는 분리 프로세스로 띄워야 했다.
- **표준입력 스크립트 프로세스.** 표준입력으로 스크립트를 받은 조율 프로세스는 명령줄이 `python -`뿐이라 종료 필터에 걸리지 않고 살아남았다.
- **`--match "test_*"`.** "unit만 돌리려는" 의도로 두 번 이 패턴을 붙였는데, 이것은 integration 전체와 일치한다. 두 번 모두 곧바로 중단했다.
- **충돌 표지 커밋.** 충돌 해소 스크립트가 실패했는데도 줄바꿈으로 이어 둔 커밋이 실행되어, 표지가 남은 병합 커밋이 생겼다. 다음 커밋에서 바로잡았고, main에는 스쿼시로 최종 상태만 옮겼다.
- **정션.** 실제 툴체인을 worktree에 정션으로 연결했다. worktree 제거가 그 정션을 따라가 원본을 지울 위험이 있어, 제거 전에 재분석 지점을 전수 검색하고 링크만 먼저 지웠다.
- **pause 재생.** 정지 응답 재측정에서 resume 뒤 같은 사유로 `pause`를 보냈다. CLI는 요청 내용으로 ID를 정하므로 이전 영수증을 재생했을 뿐 정지하지 않았다. 계약상 멱등이지만 운영자가 같은 일을 겪을 수 있어 관찰로 남긴다(미수정).

## 작업 너머 시사점

- **dream에서 [[L-0016]] 위임 파이프라인 운영과 묶을 후보.** 병렬 분할 파견의 절차다.
  - 파견 전에 코드에서 이음새를 찾아 공유 커널과 계약으로 고정한다.
  - 작업자의 브랜치 병합은 권한상 막힐 수 있으므로 통합자가 병합한다.
  - 검증은 동작 단위의 시험 선택과 시간 상한으로 계약한다.
  - 기준선은 한 번만 계산해 공유한다.
  - 작업자는 반환 전에 자기 백그라운드 실행을 종료한다.
  - 병합 뒤 중복 grep 감사를 한다.
- **dream에서 [[L-0020]]의 "비용과 입력의 경량화"·테스트 비용 항목과 묶을 후보.**
  - 시험 대기의 지배 원인은 제품 코드가 아니라 과구독과 중복 실행이었다.
  - 결과 캐시는 키의 입도가 효과를 정한다(공유 입력과 시험 모듈별 입력).
  - 통합 시험 비용의 상당 부분은 공개 활성화 픽스처의 반복과, 제품 경로의 반복 확인이 시험 시간에 곱해진 것이었다.
- **측정이 설계 전제를 교정한 사례.** `lake env` 1초 가정, 생성 시각의 파일 ID 대체 가정, 게시 직후 평가 가정이 모두 실측이나 코드 확인으로 틀렸음이 드러났다. 설계의 수치 가정은 실측 전까지 가정으로 다뤄야 한다는 판단의 재료다.
