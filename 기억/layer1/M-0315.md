사용자는 [[M-0314]]의 구현 계획 전체를 실행하도록 요청하고 수단의 선택을 맡겼다. 계획의 12개 변경 묶음을 정본 스킬에 구현했다. 새 기록 필드와 해석 규칙을 쓰는 인스턴스를 이전 형식과 구별하기 위해, 새 인스턴스의 feature_version을 3에서 4로 바꿨다. 여기서 역할은 후보 준비·연구 계획·연구 수행 같은 AI의 담당이고, action은 그 역할을 실행해 달라는 요청이다. 한 요청의 수리·재시도 관계는 계보로 기록한다.

기존 연구는 정지한 채 유지했다. 문서 독해, 대표 CLI 검사와 계약 표본 평가의 실제 추가 모델 호출에는 Claude Opus 5만 사용했다. 다른 작업에서 수정 중인 scholarly 서비스 코드는 이 커밋에 포함하지 않는다. 검증한 scholarly 전달은 do-math가 기존 서버를 자기 모델 실행에 연결하는 경로다.

예정된 개정 때문에 기다리는 경우와 판단 전제가 실제로 바뀐 경우를 나누었다. 모델을 호출하기 전에 수정할 기록을 선언한다. 그 기록을 이미 읽고 있는 실행이 있으면 그 실행의 종료를 기다린 뒤 수정한다. 실행기는 모델 응답을 받을 때 계약·기존 결과·지식 본문·원자료의 내용이 달라졌는지 비교한다. 앞서 나열한 근거를 지금도 사용할 수 있는지, 응답이 요청한 행동을 현재 대상에 적용할 수 있는지도 별도로 검사한다. 계약 승인에 사용한 전제도 저장해 이후 착수에서 재검사한다.

연구 과제의 결과가 일부만 나왔다는 이유만으로 계약을 자동 재작성하지 않는다. 계약이 여전히 적합하면 같은 계약으로 연구를 이어갈 수 있고, 실제 개정에서는 담당 AI가 대상별로 수정 완료, 보류, 별도 과제 위임 등의 처분을 명시한다. 같은 역할의 성공만으로 다른 실패 요청에 걸린 대기 상태를 해소하지 않도록 계보를 확인한다. 별개의 성공이 이전 의무도 해결했다면 action_resolutions에 수락 결과와 이유를 명시한다. 해소 뒤에도 원 실패 기록과 산출은 남는다.

지식 개정을 작업 과제에 위임하면서 자기 차단을 확인했다. 지식 A를 고치도록 맡긴 과제 D가 A 개정 대기 때문에 계약 검토조차 받지 못하면 연구를 시작할 수 없다. D와 원 개정 요청의 소유 관계를 기록해 그 의무 자체는 차단 사유에서 제외하고 다른 실행과의 충돌은 검사했다.

이미 선택된 D의 수행을 점검할 때도 같은 문제가 있었다. 일반 착수 검사가 충돌 확인용으로 만든 임시 요청에는 실제 수행 요청의 ID가 없었다. 그 결과 대기열의 자기 수행을 다른 수정자로 읽어 스스로 기다렸다. 실제 요청의 ID로 파견 충돌을 먼저 검사하도록 고쳤다. 이어지는 착수 검사에서는 같은 충돌 검사를 반복하지 않고 계약 승인과 입력을 지금도 사용할 수 있는지 확인한다.

위임 과제가 끝나거나 철회되면 그 과제의 실패 요청이 원 지식에 대한 쓰기 의도를 계속 점유할 수도 있었다. 끝난 담당 실행은 이력으로 옮기되 원 개정 의무는 유지한다. 다음 후보 준비 실행은 그 의무와 이유를 이어받아 재배정할 수 있다. 한 요청의 대상 하나가 닫혀도 다른 대상의 의무는 남는다. 구현 중에는 D의 수행자가 지식을 고치면 지식 변경 전파가 D까지 waiting으로 옮기는 결함도 발견했다. 이를 고쳐, 결과를 막 제출한 과제 D는 assessing으로 유지하고 그 결과가 완료 판정에 들어가게 했다.

입력의 정확한 판본도 실행 전에 고정했다. 입력 문맥을 만들기 전에 현재 연구 상태를 Git snapshot으로 저장하고 그 판본을 실행 근거로 기록한다. 문맥에는 새 내용이 있는데 비교 대상은 예전 snapshot인 불일치를 막기 위한 변경이다. 계약과 외부 전제의 판본을 식별하는 새 근거 키를 넣으면서 대기열 순서도 바뀌었다. 키가 없던 기존 검토 요청을 삭제한 뒤 대기열 끝에 다시 넣었기 때문이다. 검토가 뒤로 밀린 결과 실행기는 아직 승인된 후보가 없는 상태에서 계획을 먼저 실행했다. 기존 요청의 위치를 유지하며 키를 결합하도록 고쳤다. 실행 중 요청의 고정 입력을 뒤늦게 수정하지 않는 검사도 유지했다.

역할이 반환한 질문은 원문 위치, 사용자·연구·운영 중 소유자, 영향 대상과 해소 근거를 연결한다. 무관한 사용자 입력이 기존 질문을 지우지 않게 했다. 사용자 답변을 해소 ID로만 남기면 다음 작업자가 실제 답을 읽지 못하므로, 적용된 결정의 본문도 다음 입력에 제공한다.

Claude Code CLI 2.1.276의 실제 검사에서는 최종 응답 뒤 백그라운드 작업의 종료 정리 사건이 이어졌다. 이를 새 모델 작업과 구별해 공통 파서에 보존한다. 첫 시험은 작업 완료 전에 최종 응답을 내도록 구성해 백그라운드 작업이 종료됐고, 그 실패를 기록했다. 수정한 시험용 프롬프트에 따라 시험 모델은 Claude Code의 백그라운드 결과 회수 도구 TaskOutput을 사용했다. 작업의 종료와 파일을 확인한 뒤 최종 응답을 제출했다.

과거의 실제 장애 로그에는 같은 세션의 응답 구간 세 개가 있었다. 첫 응답은 계산이 진행 중이라고 했지만 마지막 응답은 계산 실패와 코드 정정을 보고했다. 새 파서가 마지막 정정 응답을 선택하는지 그 로그로 재생했다. 구간 usage와 누적 modelUsage는 서로 다른 집계이므로 합산 범위를 분리했다.

고정 사본의 전체 회귀는 499건 중 498건이 실행되어 통과했고 Windows 심볼릭 링크 권한이 필요한 1건은 미실행이었다. 실제 Opus 검사에서는 구조화 응답, 파일·체크포인트·scholarly 전달, 백그라운드 결과 회수와 정지를 확인했다. 이후의 문서 수정은 역할이 받는 원문·스키마·입력 연결을 별도로 검사했고 전체 회귀와 같은 코드인지 해시로 대조했다.

Windows의 일회성 wake 예약은 별도 테스트 인스턴스에서 실제 등록·실행·제거했다. HOLD는 자동 연구 재개를 막는 로컬 정지 표지다. 이 표지가 있는 동안 시험 예약이 실행돼도 모델 호출은 0회였다. Lean에서는 이름 끝의 작은따옴표(prime)를 사전 검사에서 거부하던 문제를 고치고, 실제 컴파일러의 선언 시그니처·공리 출력을 대조했다.

과거의 거부 35건은 모델 응답을 연구 상태에 적용하지 않은 AI 실행 35회다. 그 기록에 새 내용 비교 규칙과 계획의 선택·완료 판정 대상이 유지됐는지 확인하는 검사를 재생했다. 28건은 재생한 일부 검사에서 거부 사유가 나오지 않았다는 뜻으로, 최종 수락 판정은 아니다. 6건은 내용 변경, 1건은 대상 변경 때문에 통과하지 못했다. 과거에는 새 개정 의도와 승인 근거를 기록하지 않았으므로 이를 소급 수락 건수나 예방 가능한 호출 수로 쓰지 않는다.

계약 표본에서는 실제로 반려된 계약 한 건을 같은 원자료와 같은 공통 지침 아래 수정하게 하고, 후보 준비 역할의 지침만 전후로 바꿨다. 두 수정안 모두 새 독립 계약 검토에서 승인됐다. 새 지침으로도 수리가 가능함을 확인했지만 비교 우위나 일반적인 연구 품질 향상은 입증하지 않았다. 이 표본은 계약 문면의 의미 평가다. 직접 Opus를 호출한 시험 입력에는 원 연구의 session_limits 설정과 execution_attempts 예산 표지가 함께 남아 있었다. 따라서 이 표본을 예산 모드나 배정기 검증으로 사용하지 않으며 그 한계는 증거에 남겼다.

큰 과제 이력은 필요할 때 원문 참조로 축소하고 실제 프롬프트 바이트를 계측하도록 했다. 고정한 과거 계획 입력 하나는 현재 프롬프트 바이트 한도에 이미 들어갔다. 이 사례에서 축소가 일어나지 않았으므로 실사용 입력 바이트 절감을 주장하지 않는다.
