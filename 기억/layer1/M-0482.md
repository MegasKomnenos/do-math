[[M-0481]]은 열 개 연구 역할의 일반 진입을 순회했지만 단계·복구 변형의 전건 검증은 닫지 않았다. 이번 B67은 같은 흐름을 새로 복제하지 않고 기존 정상 흐름의 실제 `prepare_role_input` 반환에서 요구 키·중첩 좌표·원문 참조를 검사한다. `ObservedCalls`와 `Returns`를 조합해 생산자가 공급한 인자와 반환값을 대조하고, 후속 정리로 파일이 사라지기 전에 검증한다. 소유자가 뒤에서 실패를 분류하더라도 unittest subtest의 실패는 보존한다. 제품 호출·반환과 모델 응답은 바꾸지 않는다.

같은 검토 흐름의 scope·initial·organize·answer·judge 다섯 단계, 활성 인스턴스의 원문 해석·독립 검사, 검토 자리의 고정 질문 보충 조사, 초기 해석의 출력 수리·진단·후속, 편입 영향 독립 검토, 종류 정의 검사에 요구 표를 연결했다. 고정 질문의 `review_research.sources`, 검토의 자기 원문 `role_review.source_refs`, 초기 진단의 `materials`는 경로와 해시를 실제로 읽어 확인한다. 필드 이름이나 해시가 있다는 사실을 원문 도달성으로 대신하지 않는다. 근거가 없거나 읽기가 실패하거나 잘린 경우는 통과하지 않는다.

새 검사 가정도 실제 계약으로 교정했다. `n_1uno5r`는 세 사례 중 두 개 통과·한 개 실패였다. 일반 해석 action은 stage를 생략할 수 있고, 실제 역할 입력의 `interpretation_stage`가 interpret를 표시한다. action에 stage를 새로 넣지 않고 그 실제 입력값을 관찰했다. `ctrld2ud`의 초기 진단·후속·영향·종류 정의 등을 포함한 다섯 사례가 28.2초에 통과했다.

위임은 원래 unit의 ReviewScene이 검토 판정에 필요한 최소 자료만 갖고 있어 전체 `_context`에 쓸 수 없었다. `o55xb21i`에서 title 누락이 드러났다. 그 최소 fixture나 제품에 기본값을 보충하지 않고, 공개 경로로 실제 정리와 검토를 만든 Sim에서 복구 행동·위임 신청·입력을 생산하는 새 사례를 기존 sim 모듈에 넣었다. 사용자 원 결정과 위임은 명시적 도메인 입력이며, 이 사례가 그 결정의 공개 UI 생성이나 두 모델 판단을 실행했다는 뜻은 아니다.

위임 사례는 입력을 포장하기 전에 저장소의 실제 스키마·참조 검증을 통과한다. `i2npteob`에서 처음 원 결정 fixture가 change 없이 네 필드만 있어 저장되지 않았다. 정확한 대상·효과를 가진 change와 보존 원문 해시·시각을 명시해 현행 결정 계약으로 작성했다. 빈 기본값이나 구판 호환 경로를 넣지 않았다. 첫 판정을 실제 실행 생산자와 `record_judgment`로 기록·저장한 뒤 둘째 입력을 만든다. 두 입력의 봉인 사례는 같고, 둘째 프롬프트에는 첫 판정의 비공개 이유가 없다. 고정 입력의 읽기 규칙도 첫 판단 실행과 판정이 담긴 신청 기록의 경로를 거부한다. 마지막 판본은 `geyxpphx`에서 1개가 6.5초에 완결 통과했다.

설치 복구 AI는 일반 역할 포장기를 쓰지 않는다. 기존의 진단 후 복구 및 실행기 기동 실패 복구 검사에서 실제 ModelRunner가 외부 CLI 대역에 전달한 프롬프트를 읽는다. JSON의 일곱 필드, 실행·프로필·실패·설치·저장소·인스턴스의 실제 값, 보존 원문 목록과 각 파일의 전체 해시 및 Git snapshot 바이트를 확인했다. 원 프롬프트에는 JSON 뒤 실행 경계 지시가 붙는다. 처음 `json.loads`가 Extra data로 실패했으므로 JSONDecoder로 한 값의 종료 좌표를 구하고 나머지가 해당 프로필의 정확한 경계 지시인지 검증한다. 임의 꼬리 텍스트를 무시하지 않는다. 설치 복구 두 사례는 `5lewr2xj`에서 5.7초에 통과했다. 실제 원격 모델 능력·품질이나 OS 강제 격리의 증거는 아니다.

관련 모듈 전건과 전체 구조는 `vdje9dhz`에서 135개가 128.6초에 완결 통과했고 실행 중 변경은 없었다. 구조 44개, unit 20개, sim 47개, flows 24개다. 개별 예산 초과는 12개이며 검토 흐름 83.281초, 새 위임 입력 사례 8초 등이 포함된다. 이후 위임의 읽기 거부 단언을 두 개 보강하고 그 수정한 사례만 다시 검증했다. 편집된 위임 시험의 CRLF를 LF로 정리할 때 AST가 같음을 확인한 뒤 최종 `geyxpphx`를 얻었다. 135개 보고와 마지막 한 사례를 합쳐 최종 같은 판본의 전체 135개 실행이라고 표시하지 않는다.

원보고와 최종 위임 보고는 추적된 `검증/2026-10-04-역할-변형/`에 보존하고 현재 파일 지문·범위·제약을 단계 전환표 B67에 연결한다. 실패·국소 중간 보고는 사용자 Temp 아래 로컬 보관이므로 정리 후 남는다고 가정하지 않는다. 기존 unit 위임 판정 시험의 임시 변경은 제거해 원래 판정 범위를 유지했다. 사용자의 진행 문서와 미추적 교차 시험도 이번 커밋에 섞지 않는다.

3-B 전체 완료는 아직 주장하지 않는다. live 운영 점검과 종료·복구 근거의 차이, 검토 개정·같은 자리 복구, 추가 목표 감사 등의 변형을 기존 생산 사례에 연결하고 요구 선언의 모집단을 확인해야 한다. 원래 19의무·61보존 지식·P2 12항목·여섯 부류·2단계 11의무와 최종 전체 T2/flows, fresh T3·모든 대상 함수 변이·실행 예산·T4/T5 최소 실호출·말뭉치·미러·main이라는 목표는 유지한다. 부분 통과를 완료로 바꾸거나 국소 검증 때문에 전체 실행을 반복하지 않는다.
