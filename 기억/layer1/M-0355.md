## 구현 결과의 요지

- **묶음 1: 형식 결과와 사전 검사.**
  - 작업자 사전 검사(`formal_preview`)는 의존 증거를 뽑지 않는다(`extract_evidence=False`). 작업자가 쓰는 필드만 출력하며(`PREVIEW_FIELDS`), 출력은 534,902B에서 2,346B로 줄었다.
  - Lean 추출기는 폐포 순회를 선언 사이에서 공유하고, 공리를 폐포에서 도출한다.
  - `dependency_evidence`를 폐포 합집합의 `{상수: sha256}` 표로 정규화했다.
  - verified 결과의 원출력에서 해시로 환원한 의존 본문 행을 뺐다.
- **묶음 2: 자기 점검.**
  - 추적기가 쓰던 스키마 밖 필드를 처분했다. `control_call_ids`는 뺐고, `boundary_receipt_ref`와 `rule_update`는 선언했다. 이 불일치는 7d2597e부터 있었다.
  - 생산 지점에서 저장 관문과 같은 검사기를 실행한다(`stored_obligations`).
  - 응답 전 도구 실행 중에는 응답 기한을 정지한다. 기한 값은 유지하고 연장하는 방식이라, 응답 전 행동 판정을 보존한다.
- **묶음 3: 운영 점검.**
  - `admissible_basis_refs`를 범용 참조 인덱스에 넣었다.
  - 입력 시점에 유효했던 참조가 적용 전에 바뀐 경우와 `integration.currentness` 반환은 갱신 경로로 보내고, 출력 수리 횟수를 쓰지 않는다.
  - 다음 운영 점검이 이전 운영 점검의 반복 실패를 해소할 수 있다.
- **묶음 4: 소규모 수리.**
  - 작업자·사람에게 주는 명령은 `console_python()`으로 만든다. 예약 엔진이 `pythonw.exe`로 돌 때 지급 명령이 출력을 잃던 결함이다.
  - `planning.instance_ended`: 종결 인스턴스의 과제는 readiness를 계산하지 않는다.
  - 관찰 창이 대표 검사 시간(툴체인 기록의 두 시각 차)보다 짧으면 채택·등록 시 경고한다.
- **묶음 5와 재설계: 역할 입력.**
  - 상한 2,000,000B, 초과 기록의 `context_budget_bytes`.
  - 판단 역할에는 형식 결과의 판단용 투영(`knowledge_records.judged_verification`)만 준다.
  - 입력 구성요소를 싣기·지도·차단으로 나누는 정본은 `context_store.INLINE_SCOPES`와 `BLOCKED_KEYS`다.
  - 기록 지도(`record_index`, `record_map`)를 두었다.
  - 스냅숏 커밋을 Git에서 읽는 읽기 도구(`input/tools/read_input.py`, `context_store.read_main`)는 읽기 로그를 봉인 산출물 `reads.jsonl`로 남긴다.
  - 인용은 "입력이 보여 준 참조 ∪ `record_index`"이면 통과하고, 필드 의미 규칙은 따로 적용한다.
  - 읽기 로그는 현재성 결박에 쓰지 않는다. 로그가 입력 사본 읽기를 담지 못하고, 전제를 넓히면 무관한 변화로 인한 거부가 는다(L-0020의 거부 35건 중 26건 분석).
- **목표 감사 누출 수리.** 재설계는 "연구 정본은 공개 결과"라는 전제로 독립 판단에도 `research/`를 열었다. 그러나 목표 판정은 봉인 즉시 `research/goal_judgments`에 기록된다. 그래서 같은 차례의 다른 감사 자리가 읽고 인용할 수 있었다. `BLOCKED_KEYS['goal_audit']`에 이 가족을 더하고, 읽기 도구·색인·인용이 모두 거부하게 했다.

## 터득한 것

**입력 한도는 전체 상한이 아니라 "상한 − 고정 부분"과 비교된다.** `context_store.py`가 역할 문서·스키마·틀을 먼저 빼고 남은 문맥 예산으로 필수 문맥을 판정한다. 그래서 기록이 "필수 411,989 < 한도 500,000인데 필수 초과"라는 모순처럼 읽혔다. 판단 역할의 입력 가운데 수학 내용은 약 1.2KB였다. 나머지 약 31만 B는 기계 무결성 증거였고, 무결성은 이미 `verification` 전체 해시가 결박하고 있었다. 입력 초과의 근본 원인은 한도가 아니라 소비자가 다른 자료(판단용과 무결성용)를 한 투영에 섞은 것이었다.

**저장 경로를 대역으로 바꾼 시험이 저장 계약 불일치를 7d2597e부터 가렸다.** 자기 점검의 엔진 시험은 모두 `engine._save`를 autospec 대역으로 두었다(`test_controls.py` 183행). 추적기 단위 시험은 오히려 스키마 밖 필드를 단언했다. 85a540c의 "생산자 없는 필드 정리"는 스키마에서 생산자 없는 필드를 지우는 한 방향만 보았고, 생산자가 쓰는데 스키마에 없는 반대 방향은 보지 않았다.

**파견문의 전제 둘이 조사로 교정됐다.**
- 운영 점검 수리본 N3ZY2가 옛 체크포인트를 인용한 것은 이전 출력을 복사해서가 아니었다. 입력 시점 허용 목록에 정당하게 있던 체크포인트가 적용 전에 새 체크포인트로 교체된 시각 경쟁이었다(T649 → N4FAF 14:43:32).
- 자기 점검 필드는 "나중에 추가된 뒤 스키마가 못 따라온" 것이 아니라 처음부터 불일치였다.

**통합자의 부재 주장 하나가 틀렸다.** 개선안 8절에 "툴체인 기록에는 `validation.started_at`만 있다"고 썼으나, `finished_at`도 필수 필드로 있다. 기록을 검색한 필터 키워드(duration, elapsed, seconds, _ms, started, ended, wall)에 `finished`가 없었다. 필터로 걸러 본 결과로 부재를 단정한 것이 원인이다. 묶음 4 작업자가 스키마 원문으로 교정했다.

**재설계가 새 누출을 만들었고, 누출은 실패한 시험이 아닌 곳에서 발견됐다.** 실패한 조사자 시험은 원시 `_context`를 검사하는 전제 결함이었다. 차단은 `prepare_role_input`으로 옮겨졌고 실제 입력에는 없었다. 그 판정을 위해 세 경로(프롬프트, 입력 파일, 읽기 도구)를 실측하던 작업자가 목표 감사의 `research/goal_judgments` 경로를 찾았다. 읽기 범위를 넓히는 설계에서는 "정본 영역에 있지만 아직 공개되지 않은 기록"을 가족별로 따로 열거해야 한다.

**worktree 병합의 운영 사실.**
- Agent 도구의 격리 worktree는 저장소 안 `.claude/worktrees/`에 생기고, 이 경로는 무시 규칙에 없었다. 로컬 `.git/info/exclude`에 추가했다(추적되지 않는 설정).
- worktree 변경은 `git diff`를 패치로 떠서 main에 `git apply`했다.
- 묶음 4의 `git apply --check` 출력을 `tail`로 끝부분만 보다가 거부 hunk 셋 가운데 `submission.py` 하나를 놓쳤다. 이후 `--reject`로 드러나 수작업으로 합쳤다.
- 정리 전에 각 worktree의 diff 해시가 반영한 패치와 같음을 확인했다.
- `py_compile`이 스킬 폴더에 `.pyc`를 남겨 지웠다. 이후 확인은 `compile()`과 `-B`로 했다.
- 마지막 작업자가 고친 파일 8개는 전부 CRLF가 됐다. 저장소 판본도 대부분 CRLF여서(예: GLOSSARY 704줄 중 700) 해가 없다고 판단했다.

**세션 포크 아이디어 평가.** 사용자가 "요청이 전달된 세션이 응답할 수 있을 때까지 기다리지 말고 포크로 응답하게 하자"고 제안했다. 판단 근거는 셋이다.
- codex-cli 0.157.1은 `codex exec fork`를, Claude Code 2.1.283은 `--resume --fork-session`을 지원한다.
- 그러나 do-math는 작업자를 `--ephemeral`·`--no-session-persistence`로 실행해 포크할 세션이 없다.
- 이번 기록에서는 응답이 스키마 결함으로 항상 거부되므로 포크만으로 줄어드는 실행이 없었다.

그래서 기한 정지와 작업자 지침을 먼저 두는 권고를 냈고, 사용자는 보류로 결정했다.

### 사용자 교정 신호

1. **기준선 재계산.**
   - ⓐ 통합자가 편집 전 전체 시험 세 묶음을 기준선으로 띄웠다.
   - ⓑ 사용자가 "이미 다른 세션에서 다 했어"라고 해 중단하고, 다른 세션 장부(`임시/do-math_검증_20260927-2/장부.md` 35행)의 결과를 썼다.
   - ⓒ 기준선을 만들기 전에 최근 검증 런의 장부·종료보고를 확인하지 않았다.
   - ⓓ 기준선이 필요하면 먼저 `임시/`의 최신 검증 런 장부에서 같은 판본의 전체 결과를 찾는다.
2. **순차 파견.**
   - ⓐ worktree를 만들지 않는 저장소 규범과 시험 지침 3절 규칙 2(실행 중 트리 편집 금지)를 근거로 다섯 묶음을 순차로 돌리기로 했다.
   - ⓑ 사용자가 병행이 어려운지 물은 뒤 worktree 격리를 명시로 요청했다.
   - ⓒ 규범이 격리를 막아 소요가 크게 늘어나는 경우, 격리 요청이라는 선택지를 계획 단계에서 먼저 제시하지 않았다.
   - ⓓ 병렬 구현 파견을 계획할 때 "worktree 격리 요청 시 병행 가능, 요청 없으면 순차"라는 선택과 그 비용을 첫 계획에 함께 적는다.
3. **모델 선택.**
   - ⓐ 소규모 수리 묶음에 sonnet high를 배정했다.
   - ⓑ 사용자가 opus로 다시 파견하게 했다.
   - ⓒ 작업이 작다는 이유로 모델 급을 낮췄지만, 사용자는 구현 품질을 우선한다.
   - ⓓ do-math 구현 파견은 opus를 기본으로 한다. 급을 낮출 때는 이유를 먼저 알린다.
4. **입력 설계 방식.**
   - ⓐ 묶음 5는 역할마다 받을 키를 표로 정하고, 계약과 기계 소비자가 없는 키를 빼며, 인용은 지급 부분집합으로 제한했다. 이 방향은 개선안(A1과 전면 감사)과 파견문이 정했다.
   - ⓑ 사용자는 지도·도구·인용 안내를 주고 무엇을 볼지는 역할 재량에 두는 "영향" 방식을 요구했다.
   - ⓒ 정보 열람에 보안의 최소 권한 원칙을 적용한 편향이다. 제약의 실익(없는 ID 차단, 판본 결박)은 스냅숏 존재 검사로 충분했고, 제약의 비용(정당한 인용 반려)은 이번 운영 점검에서 실측됐다.
   - ⓓ 역할 입력은 싣기·지도·차단으로 설계하고, 차단은 계약이 독립성을 명시한 경우에만 근거 좌표와 함께 둔다. 정본은 `references/공통-실행.md` 「기록 지도와 읽기 도구」다.
5. **설명 요청의 작성 절차.**
   - ⓐ 결정 사항을 쉽게 풀어 달라는 요청에 `write-for-reader`의 합의·독자 파일과 독해 절차를 준비했다.
   - ⓑ 사용자가 "그냥 바로 설명해줘"라고 중단시켰다.
   - ⓒ 대화 본문의 설명 답변을 독립 문서처럼 다뤘다.
   - ⓓ 대화에서 요청받은 설명은 품질 계약만 적용해 바로 쓰고, 독해 절차는 파일로 남길 독립 문서에 쓴다.
6. **인계의 맥락 보존.**
   - ⓐ 통합자는 짧은 작업 지시로 파견하려던 참이었다.
   - ⓑ 사용자는 방금의 대화 맥락이 손실되지 않게 전달하라고 요구했다.
   - 결과로 사용자 발언 두 개를 원문 그대로 싣고, 확정 방향과 권고를 구분한 인계 문서(`파견_입력재설계.md`)를 만들었다. 작업자는 권고 셋을 원문 의도를 근거로 수정했다. R1·R2는 "모호하면 싣기"로, R6은 "로그만"으로 바꿨다.
   - ⓓ 사용자 대화에서 나온 설계 과제를 넘길 때는 사용자 원문, 확정 방향, 통합자 권고, 결정 권한을 한 인계 문서에 담는다.

## 남은 것

- **실제 모델 운전은 하지 않았다.** 수용 시험(같은 목표의 새 인스턴스가 목표 감사까지 완주하는지), 배정 모델의 2MB 입력 수용, 모델이 지도와 읽기 도구를 실제로 쓰는지가 확인되지 않았다.
- **실측 없이 코드 판독으로만 판단한 누출 범위가 있다.** 의도 해석의 위임·검사, 검토 자리의 운영 점검, 동일성 검토의 organize·answer·judge 단계다.
- **답을 받지 못한 결정 사항이 있다.**
  - 1: 실패 결과의 원출력은 모두 보존한다.
  - 2: 부분 수락 뒤의 현재성 반환도 갱신 경로로 간다. 이 경로를 확인하는 시험이 없다. 추가를 권했지만 아직 넣지 않았다.
  - 4: 관찰 창 경고의 여유 배수. 모두 현재 구현이 유지된 상태다.
  - 결정 2를 보수적으로 바꿀 때 `apply_bundles`의 `status: partial`로 판정하면 안 된다. 수락 0건에도 partial이 나오므로 모든 갱신이 막힌다.
- **범위 밖 발견.**
  - 인스턴스 종결 판정 리터럴 사본 13곳(`planning.instance_ended` 정본으로 통합 가능).
  - 형식 검사 결과의 세 곳 중복 저장.
  - `apply_bundles`의 partial 오명명.
  - 갱신 경로의 옛 `repair` 블록 복사.
  - `supplied_reference_ids`가 생산자 없는 키 넷을 순회함.
  - 입력 감사표 5절의 계약·구현 어긋남 7건.
- **Mathlib 검사 비용.** 중앙 검사 한 번의 최대 커밋 메모리 9.8GB, 차가운 캐시에서 333초. 사전 검사는 약 30초로 Mathlib 적재가 지배한다.
- **이전 세션들의 worktree는 건드리지 않았다.** `C:/math-worktrees/` 아래 16개가 남아 있다.

## 작업 너머 시사점

- **dream에서 [[L-0020]](do-math)과 묶을 후보.**
  - 판단 입력과 무결성 증거의 분리. 형식 결과의 판단용 투영이 정본이다.
  - 역할 입력의 싣기·지도·차단 설계와 스냅숏 결박 읽기 도구.
  - 정본 영역에 있으나 공개되지 않은 기록(목표 판정)이 독립성 전제를 깬 사례.
  - 저장 계약과 추적기 모양의 이중 정의.
- **dream에서 [[L-0016]](위임 파이프라인)과 묶을 후보.**
  - worktree 격리 병행의 계획 단계 제시(교정 신호 2).
  - 사용자 원문을 보존한 인계 문서(교정 신호 6).
  - 패치 병합에서 `--check` 출력을 잘라 보지 않을 것.
  - 기준선 재사용 확인(교정 신호 1).
- **dream에서 [[L-0005]](작업 판단)와 묶을 후보.** 필터로 걸러 본 검색 결과로 부재를 단정한 사례(`finished_at`). 정보 열람에 최소 권한 원칙을 옮긴 편향(교정 신호 4).
- **dream에서 [[L-0001]](검증 설계)과 묶을 후보.** 저장 관문을 대역으로 바꾼 시험들의 거짓 통과. 원시 중간값을 검사해 실제 성질을 놓친 시험(조사자 시험).
