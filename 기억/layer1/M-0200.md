IOP는 Radware/hCaptcha의 iframe 제목이 한국어여서 영어 checkbox 제목으로 찾던 진단이 실패했다. 실제 iframe[data-hcaptcha-widget-id]로 선택한 뒤 현재 세션에 표시된 과제를 직접 판독해 입력했다. 나무로 만든 물체를 고르는 화면에서 해당 침대 이미지 셋을 선택하고 검사·Submit을 눌렀다. 20260911T025758Z-iop-verification-control.json의 확인 응답과 completed는 true이며 iopscience-iop-org.libproxy.knu.ac.kr로 이동했다. 서버에 CAPTCHA 인식 기능을 넣지 않았다.

확인된 Chrome 쿠키 상태를 보호된 .credentials/scholarly-mcp/kudos.json에 저장했다. 새 Chrome 컨텍스트의 20260911T030426Z-iop-verified-session-fetch.json은 서지·초록·16쪽 PDF·RIS를 회수했지만 BibTeX는 bibliography_parse_error였다. 접근 확인이 풀린 뒤 드러난 별개의 형식 처리 문제다. 다른 브라우저로 같은 확인 상태가 통한다고 가정하지 않고 IOP 어댑터를 Chrome gateway에 연결했다.

원 BibTeX 1815바이트의 첫 키는 J Batina_2001이었다. 기존 연구 파서는 키 내부의 공백을 거부한다. 키를 고쳐 원 파일을 다시 쓰지 않고, _BibScanner에 allow_key_whitespace=False 옵션을 추가했다. 기존 연구 parser의 기본 동작은 엄격하게 유지하고 MCP의 bibliography 추출만 명시적으로 켠다. 원 id와 raw_text를 유지하며 citation_key_contains_whitespace 경고를 반환한다. 다른 문법 오류까지 허용하는 옵션이 아니다.

파싱 오류 메시지는 원 바이트가 artifact에 있다고 했지만 IOP helper는 파싱 뒤에야 저장하여 실패 파일을 잃고 있었다. IOP 파싱 또는 DOI 대조 실패에서는 source_export에 받은 원 파일을 남기고, 성공한 파일의 경고도 manifest에 보존한다. source URI와 파일의 DOI를 대조하며 원 서지 필드를 다시 작성하지 않는다.

실제 SDK 20260911T032405640853Z-iop-workflow.json은 completed=true다. 문헌 10.1088/0022-3727/34/10/311의 서지·초록·16쪽 PDF·BibTeX·RIS와 BibTeX DOI 추출을 확인했다. 별도 기계적 추출로 PDF 첫 페이지에 hydrodynamical과 electric wind가 있음을 대조했다. BibTeX artifact의 키 공백 경고도 확인했다. 공통 224개 검사와 기존 연구 parser 15개 검사가 통과했다.

같은 확인 상태에서 IOP 검색도 재조사했다. 예전 label[for=quickSearch] 클릭은 검색 메뉴를 열지 못했으며 실제 Search 버튼으로 메뉴를 열면 /nsearch?terms=complexity의 결과가 나왔다. 원 화면에는 상위 500건과 Showing1-10 of500이 표시되고 기사 카드 10개에 링크 20개가 있다. 이를 전체 일치 건수 500으로 표시하거나 링크 20개를 문헌 20건으로 세지 않는다. 다음 작업은 이 검색의 범위·필터·페이지·원 RSS를 확인하고 어댑터로 연결하는 것이다.

현재 IOP 검색 생산 코드는 아직 미연결이다. date 기간·저널 ISSN·정렬·pageLength 제어와 /nsearch/rss 링크가 원 화면에 있다. 익명 RSS의 접근 조건과 제공 범위를 먼저 대조하며 API 자격 부재를 API 자체의 부재로 바꾸지 않는다. 전체 작업은 진행 중이므로 푸시하지 않는다. CLI·기존 Codex 세션의 재시작 조작은 계속 하지 않는다.
