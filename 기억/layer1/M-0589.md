## 맥락

사용자가 지정한 do-math 제품 코드 검증은 수리 8기(영역 4·관점 4), 수리 Opus 5.5/high·병합 Opus 5.5/low, 심사 gpt-6-astra/medium 3기와 정족 3, 정확히 2라운드다. 시험·fixture·시험 기반은 독립 검토에서 제외하고 실제 제품 코드 문제를 찾았을 때만 관련 시험을 확인한다. 각 라운드 뒤 미통과 전건을 세션이 직접 심층 검토하고 재량으로 보완하며 graphify update를 수행하라는 지시도 유지했다. 첫 라운드의 사용자 교정과 세부는 [[M-0588]]에 있다.

두 번째 라운드는 14원안·24조각을 냈고, 겹친 2원안을 한 묶음으로 병합해 13단위를 심사했다. 3기 모두 같은 지정 모델·노력으로 전건을 판정했다. 정족 통과 6단위는 공식 적용했고 기각 7단위(원안 8건)는 세션이 모두 직접 검토했다. 이 가운데 6단위/7원안을 보완하고 1건을 남겼다. 공식 장부의 승인·기각 수를 직접 판단으로 고쳐 쓰지 않았다. 전체 두 라운드의 원안 수 34건에는 병합된 중복 원안도 들어가므로 고유 결함 수와 구별한다.

후속 판단의 보존 진입점은 `임시/do-math_검증_2026-10-20_8기/장부.md`와 `종료보고.md`, `기각보관/do-math-20261020-라운드2.md`다. 이 파일들은 Git에 보존한다. 라운드 사본·개별 수리·심사 파일과 앵커는 종료 커밋 뒤 정리 대상이며, 검사 실행 보고·graphify 출력·CLI 실패 이벤트는 Git 제외 로컬 자료다. 사라질 수 있는 원로그만으로 판단을 복원하게 두지 않았다.

## 직접 판단의 범위

사용자가 거부한 기본값은 세션이 정규 승인안만 적용하고 기각·무처분의 실제 손상을 다음 검토로 넘기는 운전이었다. 교정된 요구는 각 라운드에서 그 안건을 직접 심층 검토해 반영 여부를 판단하는 것이다. 정규 수리자의 저작 단계를 세션이 미리 대체하라는 뜻은 아니므로, 이번에도 공식 승인 적용 뒤 직접 검토를 수행했다. 다음 운전에서는 정규 적용과 직접 검토를 별도 기록하고, 직접 검토를 마치기 전에 비싼 최종 전수 검사를 시작하지 않는 것이 교정 위치다.

R2-03은 철회·대체된 지식에서 컴파일 전 관문을 기다리거나 중단 뒤 재개를 기다리던 형식 검사 요청이 다시 진행되는 문제다. 심사에 낸 조각은 `continuation_of`가 있는 실행만 정산해, 컴파일 전 권한 대기에서 만든 소유 활동을 남겼다. 세션은 기존 실행 여부를 활동 존재 여부와 구별하고 `_settle_request_owner`로 배정 전·후 소유 활동을 모두 정산했다. 공개 knowledge revise 제어로 지식을 개정해 멈춘 검사와, 컴파일 전 대기 중 지식을 실제 철회한 검사에서 각각 수정 전 실패·수정 후 통과를 확인했다. 지식이 바뀌지 않은 신뢰 환경 전환 정책은 변경하지 않았다.

R2-M1은 취소·철회·퇴역한 요청의 대기가 풀리지 않는 문제다. 병합안은 대기 종결뿐 아니라 유지보수 정리 제외까지 없어지는 효과를 주장했다. 실제 정산은 마지막 `start_failed`를 미결 사항으로 남기므로 후자의 주장은 성립하지 않았다. 세션은 손상을 좁혀 대기 종결을 보완하고 실패·미해결 의무에 따른 정리 제외는 보존했다. 실패를 지워 영향 칸의 과도한 주장을 맞추지 않았다. 공통 정산은 계획 취소·준비 대기 교체·과제 철회·개정 퇴역과 형식 검사 퇴역이 함께 소비하며, 같은 활동에 다른 요청·운영 수리·살아 있는 실행이 남아 있으면 기존 정산 규칙에 따라 그 활동을 끝내지 않는다.

나머지 네 직접 보완은 기존 검사를 보존하거나 공유하는 방향이다. R2-07의 Unicode 경로 처리에서는 LF 뒤 마지막 원소를 무조건 버리는 제안을 고쳐 후행 비정상 응답도 계속 거부했다. R2-11은 정리 요청 접수와 실제 정리에서 사용자 출처를 같은 함수로 검사한다. R2-12는 설정과 worker가 잠금 모델의 전체 ID를 같은 함수로 검사한다. R2-13은 지식·형식 결과·해설·외부 작업·실행 기록 중 정확히 한 기록으로 풀리는 참조만 받으며 여러 기록으로 풀리면 거부한다. 그런 기록이 없을 때 저장 artifact bytes를 찾는 규칙까지 `resolve_evidence_reference` 하나로 공유했다.

## 남긴 문제와 사용자 보류

R2-04는 원자료·비헌장 governance·의존 사용·신뢰 환경 등을 고정한 재심사의 전제가 바뀌면, 현재 전제와 고정 전제의 비교가 입력 준비를 반려하지만, 재심사 주기는 진행 중인 상태(status=working)로 남아 재시도해도 같은 반려를 반복하는 문제다. 코드의 손상은 확인했다. 다만 제출된 전면 퇴역 정책은 사용자가 보류한 신뢰 전환 조정까지 포함했고, waiting_actions를 남긴 채 소유 활동을 끝낼 수도 있었다. 이 조각을 적용하지 않았으며 원자료·의존 변화만의 유한 정산과 대기 인계를 함께 닫는 좁은 수리를 잔여로 보고했다. 사용자가 원자료 변화 문제 전체를 보류했다고 확대하지 않았다.

사용자가 최종적으로 보류한 두 작업은 R1-07의 신뢰 전환과 진행 중 동일성 검토의 새 조정, R1-12의 AI 악의를 가정한 감사 출력 위조 대응·검사 분리다. 앞서 선택했던 A(진행 중 검토가 끝날 때까지 신뢰 전환을 기다림)는 최종 보류로 대체됐다. 2라운드에는 이 최신 결정만 별도 `사용자확정.md`로 지급했다. 앞 라운드의 심사 사유나 기각 위치를 새 수리자에게 지급하지 않았다.

## 운송과 검증 근거

2라운드 최초 8기 파견은 Claude 5시간 한도 429로 산출 없이 종료됐다. 이를 검토 완료·결함 0·정상 라운드 종료로 세지 않고 실패 기록 24개를 보존했다. 사용자 재개 지시 뒤 초기화 시각 20:50 KST가 지난 20:52에 같은 모델·노력·파견문으로 다시 실행했다. Claude Agent 도구 부재에 따른 로컬 CLI 운송은 유지했고, `--safe-mode`로 1라운드 커밋 기억과 훅의 자동 주입을 껐다. 계약·현행 기준은 명시 지급했으며 실제 모델과 Read·Bash 대표 실행을 확인했다. 이 조정은 검토 모델을 바꾼 것이 아니다.

관련 회귀 108건은 전부 통과했고 fixture 오류와 실행 중 코드 변경이 없었다. 직접 재현 초안에는 현행 역할 출력 모양과 wait_kind 누락, 실제 실패 reason을 잘못 예상한 시험 오류가 있었다. 실제 생산자 계약으로 고친 뒤 의도한 수정 전 실패와 수정 후 통과를 각각 구별해 기록했다. 승인된 OS 잠금 수리에 연결된 기존 시험도 파일 존재가 아니라 실제 잠금 소유를 검사하게 바꿨다. 해제 뒤 lock 파일이 남아도 새 생산자 검사가 통과해야 한다.

최종 통합 검사는 T2의 structure·unit·contracts·sim 네 폴더와 flows 전건, Git 저장·OS 잠금·설치 제출의 관련 boundary 세 모듈을 합해 실제 4,597건을 완료했다. 초기 병렬 수집 4,583건에 격리 14건이 더해진 수다. 로컬 `임시/vr-final2/report.json`은 통과 4,587·실패 9·skip 1, fixture 오류 없음, 완결 true·성공 false·실행 중 변경 없음, 종료 코드 1이다. 실측 7,611초이며 시간만으로 중단하지 않았다. skip은 Windows 심볼릭 링크 생성 권한 부족이다. 첫 라운드 중간 전수 두 실행은 여전히 미완료 자료다.

초기 기준의 별도 worktree에서 실패 9건을 대조하면 8건이 통과하고 시험 냄새 감사만 기존 3지적으로 실패했다. 전수 뒤 사용자는 재검사를 해당 실패 검사들만으로 한정했다. 이를 따라 통과한 검사는 반복하지 않았다. 원래 실패 9건의 최종 재검사는 로컬 `임시/vr-failed-final/report.json`에서 9/9 통과·fixture 오류 없음·완결/성공 true·실행 중 변경 없음·종료 코드 0이었다. 구 단언·선언과 시험 구성을 바로잡은 범위 및 기존 감사 3지적의 최소 보완은 종료 보고에 있다. 변이 도구 시험의 별도 기능 실행은 이 재검사 제한 안에서 추가하지 않았다.

catalog 실패는 시험 구성만의 문제로 닫히지 않았다. 실제 실행기의 문맥·동적 스키마·포장·설치 도구를 사용해도 지급 catalog의 위치가 고정 검사 입력에 없어서 반려됨을 확인했다. R1-18이 물리 파일 존재만으로 참조를 허용하지 않도록 고친 뒤 드러난 연결 누락이다. 세션은 전수 뒤 `context_store.py`에서 역할 허용 키의 catalog 경로를 검사 전용 `input_catalog`로 먼저 결박하고 같은 경로 함수로 실제 파일을 만들게 했다. 검사기 재설치로 불변 입력 경로를 덮으려던 초안과 정적 스키마를 사용한 시험 구성은 오류로 보존했다. 최종 판본은 입력을 한 번만 설치하며 해당 실패 검사가 지급 경로 허용·미지급 파일 거부를 함께 확인했다. 이 제품 코드 후속 변경 때문에 전수와 최종 제한 재검사를 합쳐 동일 판본의 새 전수 통과로 쓰지 않는다.

두 번째 graphify 갱신은 인용 행 번호 오류를 검산이 반려해 기존 그래프를 보존했고, 공식 재추출로 회복했다. 최종 catalog 수리와 시험 보완 뒤 갱신은 1,218파일·17,546노드·66,044관계로 완료했다. 의미 26문서 캐시와 변경 1문서(57노드), 코드 구조 951파일을 추출했고 두 HTML을 생성했다. 그래프는 원문과 일치하며 미완료 의미 추출은 없다.

## 작업 너머 시사점

후속 기억 종합 작업(dream)에서 묶을 후보는 “실제 손상과 제출된 수리 효과의 범위를 구별하는 직접 검토”다. R2-M1에서는 상태 대기와 정리 적격성을 분리했고, R2-03에서는 실행 계보가 없어도 활동이 존재함을 확인했다. 기각 사유가 수리 조각의 결함을 정확히 잡았다는 사실과 원래 코드에 고칠 문제가 없다는 결론은 서로 다르다. 반대로 원래 결함이 실재한다는 사실만으로 제안 조각이 주장한 모든 효과를 승인할 수도 없다.
