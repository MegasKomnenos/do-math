[[M-0491]] 뒤 B77은 원문 결함 범주 5-A의 편입 적용 허용 목록을 다룬다. 현재 submission._payload_issues의 candidate와 core_engine._apply가 available_input_refs·supplied_record_ids·이번 응답에서 생성하는 과제를 따로 합쳤다. 둘 다 필드 부재를 get(..., [])로 보충했다. 현재 계약은 지급 근거 두 필드를 가진 준비 입력 하나이므로 구판/희소 입력을 자동 수용할 이유가 없다.

PREPARATION_INPUT_BASIS_FIELDS와 preparation_input_refs를 task_contracts 정본에 둔다. 제출 검사는 작성한 후보 제목, 실제 수신자는 생성한 durable ID를 세 번째 인자로 주며 제목→ID 정규화는 기존 수신자가 소유한다. 두 필드가 모두 있으면 같은 합집합 의미를 보존하고 하나라도 없으면 해당 이름을 포함한 ValueError로 거부한다. live state의 records/knowledge/tasks를 추가로 합치지 않는다. readiness의 아직 도착하지 않은 source: 판단은 기존 unsupplied_task_inputs(admit_named_sources=False) 계약 그대로이며 후보가 source:future를 선언하는 의미와 구별한다.

작은 입력 모집단은 참조3개×세 공급 목록의 각 부분집합, 8³=512개 조합이다. 기대값은 독립 합집합이며 관리 history/accepted에 둔 미지급 기록은 들어가지 않는다. 중복·순서 변화의 안정성, 두 필드 각각의 누락 사유와 입력 불변을 검증한다. 이전 입력 공급 시험 docstring에 남은 B32 오배정도 수정했다. 원래 B32는 role_direct_keys 필수 분류이며 이 별도 공급 규칙과 혼동하지 않는다([[M-0488]]).

실제 Sim 수신 시험은 produce_task로 먼저 과제를 만들고, issue_preparation의 실제 문맥/packager/manifest/저장 생산자로 저자의 입력을 봉인한다. 그 뒤 같은 정상 생산자가 새 과제를 게시한다. _issued_input을 다시 읽으면 원래 문맥 그대로이고 새 과제는 available_input_refs와 supplied_record_ids 어느 쪽에도 없다. 실제 _apply_bundle_candidate는 새 과제를 인용한 후보를 거부하며 원래 instance/runtime/head를 바꾸지 않는다. 동일 응답의 첫 후보는 이전 과제·context:goal·미도착 source:future를 입력으로 선언할 수 있고, 둘째 후보의 첫 후보 제목은 생성된 실제 ID로 결속된다. 저장 후보 검증을 통과한 뒤에도 원래 상태와 head는 불변이다. 이 마지막 시험은 적용 후보와 저장 관문까지의 증거이며 모델 원응답의 실제 게시까지 새로 주장하지 않는다.

첫 수신 시험 s6sosak3은 후보 도우미의 refs가 inputs와 reuse 양쪽에 복사되어 context:goal이 ID 전용 reuse에 들어가는 시험 구성 오류로 실패했다. 정상 후보에서 reuse=[]를 명시하여 입력 허용 근거만 검사했고 e2bz6yls가 통과했다. 제품 스키마를 느슨하게 하거나 실패 계약을 정상으로 고정하지 않았다. 기존 dependency 수신 희소 fixture와 두 순수 검사 외곽에는 현행 필수 지급 근거 두 목록을 직접 갖추었다. 이 순수 fixture를 실제 packager 생산자라고 주장하지 않는다.

구조 정본 소비 표에 helper의 모든 직접 call-site를 등록했다. AST상 candidate 내부 호출은 중첩 _payload_issues에도 보이므로 두 좌표를 함께 선언한다. 정본 한 정의와 실제 producer/consumer 양쪽 연결을 검증하며 미래 의미상 사본의 부재까지 증명했다고 주장하지 않는다. shared seam 문서도 갱신했다.

최종 같은 판본 zjgmegyt는 구조46·단위206·Sim44·flows7, 303개가184초에 완결 통과하고 실행 중 변경은 없다. 실제 source/plan/checkpoint currentness와 다른 적용 오류의 producer repair, 부분 수락 옆 premise refresh 흐름도 포함한다. 개별 시간 초과52개를 기록한다. 전체 T2 300초·fresh T3 3300초와 변이·T4/T5 등 최종 관문은 여전히 미완료다. 원보고는 추적 검증/2026-10-04-편입-허용-참조/report.json이며 작업판에 명령과 소스/원보고 SHA를 연결한다. Temp 중간 보고와 finish 명령/파일 manifest·renderer는 무시된 로컬 보관이다.

B74~B77이 5-A의 주요 다섯 대상(인용·완료·개설·신뢰 목록·편입)을 실제 코드와 부분 증거로 연결했다. 이것으로 판정 함수 전건과 다섯 축의 전체 종료를 주장하지 않는다. 작업판의 남김을 실제 확인한 범위로 갱신하고 다음 구현은 원래 4-A/4-B/13-B의 나머지 대기 공간 생성·해소·표시 연결로 이동한다. 같은 작은 근거 묶음에 새 감사를 무한 증식하지 않고 최종 전건 검수에서 남은 축을 확인한다. 보존19의무·61지식·P2원래12·2단계11의무와 전역 완료 조건을 줄이지 않는다.
