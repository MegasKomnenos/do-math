연속 개발 서비스의 phase 002 manager는 mutation-baseline을 A1~A5 범위에서 승인하고 다음 단일 work task를 provider-smoke로 정했다. 정상 child가 결과를 남기지 않으면 기존 실패 ID 집합에서 해당 ID가 없다는 이유로 정상 통과로 기억되던 경로를, 실제 결과 row·선택·exit를 갖춘 판정으로 바꾼 작업이다. 수리 전 실제 child의 exit 17과 결과 부재가 killed/True로 보고됐으며 수리 후에는 execution_error/비통과로 남는다. 정상 실패는 다음 후보 검사에서 제외하더라도 전체 관문을 막고, load 오류는 같은 batch의 정상 실행이 실제 통과한 경우에만 포착 근거가 된다.

검수는 task의 complete나 통과 수를 그대로 승인하는 데서 끝내지 않았다. 최종 58개 선택과 실제 58 passed row를 대조하고, 보고의 Python 862개와 task 종료 파일 해시 2206개가 현재와 같은지 확인했다. 수리 전 2개와 최종 17개 fixture의 원보고, 시도 파일, baseline 연결도 읽었다. 최초 cwd 준비 오류와 중간 fixture 단언 오류는 결함 재현과 구별해 보존했다. manager는 제품을 직접 고치거나 이 관련 시험을 반복 실행하지 않았다. 전체 일반·fresh T3·전체 함수 변이·T4/T5·최종 review는 여전히 별도 책임이다.

이번에 닫은 과거 검토는 PR01/B56 전체가 아니라 mutation child·정상 기준·shared passed 소비다. 원보고 네 외부 임시 경로는 없지만 실제 commit diff와 현재 소비자, 이번 새 경계 실행으로 이 부분의 유지와 교정을 판정할 수 있었다. D9의 실패 후보에만 수행하는 지연 정상 확인, 같은 선택 재사용, 값싼 모듈 우선/failfast, 시간 종료 제거는 유지했다. T3 저장소·전체 runner·provenance까지 확인했다고 넓히지 않는다.

다음 작업은 문서 P01보다 공급자 최소 실호출을 먼저 배정했다. 변이 판정의 확인된 공백이 닫힌 시점에서 T5의 빈 폴더와 Codex 설치판/녹화판 차이, 실제 역할 schema 수락과 현재 모델 접근 조건을 미리 확인하기 위해서다. 새 task는 현 maintenance action schema를 그대로 사용하는 두 공급자 호출, 파일/checkpoint·종료 회수, 현재판 raw 녹화와 parser 재생, Claude background의 현 사건 순서 판정까지만 맡는다. 실제 연구 제출/저장·Job/pythonw 전용 연쇄·Lean·예약·학술·운전 읽기 한도는 합치지 않았다. 공급자나 제품의 실패가 나타나면 역할 schema를 줄여 통과시키지 않고 원자료와 위치를 반환하도록 쓰기 범위를 한정했다.

근거 진입점은 docs/do-math/continuous-development-2026-10-13/phases/002/manager.json과 manager-evidence/review.md다. 공용 문서 diff, task 보고, 필요한 원보고·실행 출력, 실제 child fixture 227개 작은 원자료 파일을 이 커밋에 보존한다. 생성된 .timings 캐시와 서비스 runtime/세션 logs, 제외한 무관 scratch는 Git 제외인 로컬 기록이며 이 커밋으로 보존했다고 주장하지 않는다. 기존 dirty/untracked 제품과 engine은 따로 남겼다. 앞으로 최종 G6를 검수할 때에는 과거 failing 문자열/덮어쓴 result 경로 대신 현재 baselines와 outcomes[].attempts를 따라 실제 정상 기준과 각 시도를 대조해야 한다.
