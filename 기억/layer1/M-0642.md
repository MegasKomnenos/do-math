## 맥락

사용자는 do-math 전체 평가, 실행 중 연구(`.skill-workspace/do-math/parking-unimodality-fresh-20261105-150803`, Git 제외 로컬 인스턴스)의 심층 점검, 노드 생성 문제의 원인 분석을 차례로 요청한 뒤 grilling으로 새 설계를 확정했다. 출발 문제는 두 가지였다. 4.2시간 동안 frontier가 root와 Q 두 노드에 머물러 attempt 병렬도가 평균 약 3에 그쳤다. 또 노드가 거칠어서 같은 정리(소인 n≥21 골짜기, 꼬리 감소)가 병렬 세션에서 두 번 이상 증명되었다.

사용자는 노드 분할을 강제하는 대신 노드를 병렬로 공략할 수 있게 하기로 했다. grilling에서 확정한 결정은 다음과 같다.

- 섹션은 노드 질문의 정확한 일부다(방법이 아니다). 점유는 섹션으로만 하고, 노드 전체 작업은 노드 전체 섹션이다.
- 다른 세션의 섹션과 겹치는 섹션은 금지한다. 넓이는 실제로 추구할 수학이 정하고, explorer는 섹션에 묶이지 않는다.
- 섹션은 일시적 예약이며 그 파이프라인의 review가 끝나면 사라진다. review는 섹션을 다루지 않는다.
- 섹션 선택은 노드 lease로 직렬화한다. 대기 세션은 차례를 기다리거나 다른 노드를 고른다. lease에는 시간 제한이 없고 등록·명시적 해제·세션 종료로만 끝난다.
- attempt와 peer가 등록하며, 확장만 가능하고 해제는 불가하다.
- 실행기는 어떤 미해결 노드가 전체 점유도 대기자도 없을 때 attempt를 띄우고, 출시 간격 `attempt_launch_interval`(기본 180초)을 둔다.
- 실행 중 인스턴스는 사용자가 직접 재기동한다(현재 STOP, 실행기는 유휴 상태로 살아 있음).

## 변경

- `runtime/coordination.py`: `claim`을 `lease`·`wait`·`release`·`section`으로 바꾸었다. M-0641의 `runner/claims.lock` 아래에서 모두 선착순으로 판정한다. lease는 공유·일시 상태라 `runner/leases.json` 하나에 두고, 섹션은 세션 소유의 `declaration.json`에 둔다. 세션 종료 판정은 브로커의 고아 컴파일 규칙(단계 종료, 또는 host·CLI 모두 소멸)을 그대로 쓴다. 한 세션은 한 번에 하나의 lease 관계(보유 또는 대기)에만 선다. 그래야 떠난 대기자에게 lease가 주어져 무기한 묶이지 않는다. 옛 `{"nodes": [...]}` 선언은 노드 전체 섹션으로 읽어 실행 중 인스턴스 파일을 고치지 않는다.
- `runtime/runner.py`: `available_nodes`는 전체 섹션이나 대기자가 있는 노드를 뺀 목록을 반환한다(고르는 중인 attempt 수 반환은 제거). `last_attempt_launch`는 state에 저장해 재기동 뒤에도 간격을 지킨다. formalizer 선언은 노드 전체 섹션 형식으로 쓴다. board 렌더링에 섹션과 lease를 넘긴다.
- `settings.py`에 `attempt_launch_interval`(0 이상 정수 초)을, `context.py` 명령에 새 네 명령을 더했다. `knowledge.render`는 섹션과 lease를 board.md에 표시한다.
- 안내 문서 10개(common·tools·attempt·peer·explore·organizer·organizer-output·retained-work·operations·SKILL)를 섹션 기준으로 고쳤다.
- 시험: 옛 claim 시험 셋을 섹션 시험 열하나로 교체했다(lease 선착순·6프로세스 동시 요청, 순서 대기와 등록에 따른 이양, 종료 세션의 lease 이양, 단일 관계, 전체 섹션 차단과 파이프라인 종료 후 해제, 확장·해제 불가, peer 등록과 타 역할 거부, 옛 선언 판독, 출시 간격·대기 노드 제외, 설정 검증). 전체 152개 통과(`.claude`·`.agents` 양쪽).

## 사용자 결정 밖에서 내린 선택

아래는 결정에서 도출한 선택이며 사용자에게 보고했다. 사용자가 바꿀 수 있다.

- 섹션은 노드 명제가 함의해야 한다. 일부 사례로의 제한 또는 결론이 요구하는 조건 하나가 섹션이다. 노드를 충분히 함의할 뿐인 더 강한 명제는 섹션이 아니며 검토된 관계를 거쳐 노드로 들어온다. "질문의 일부"라는 결정의 논리적 귀결로 보았다.
- 겹침의 단위는 같은 사례에 대한 같은 요구 조건이다.
- exploration을 원천으로 둔 peer는 explorer의 섹션 무관 자유를 이어받는다(peer의 범위는 원천 범위라는 기존 원칙).
- 남의 섹션 부분을 확립하게 될 논증은 그 부분에서 멈추고, 그 부분으로부터의 연결로 기록한 뒤 보유자에게 메시지를 보낸다.
- 미해결이 아닌 노드의 lease는 거부하고, 같은 파이프라인의 전체 섹션 중복 등록도 거부한다. `wait` 기본 시간 초과는 브로커의 `wait`와 같은 50초다.

## 터득한 것

- 별도 독해(writing_flow, gpt-6.1-sol, 7회 중 1회는 빈 응답이라 재실행)가 원고만 읽어서는 보이지 않던 결함을 차례로 드러냈다. 첫째, attempt의 종료 규칙("chosen work가 해결되면 종료", "더 작은 부분문제는 원 노드를 미해결로 남김")이 섹션과 모순되었다. 둘째, 단봉성 예시로 든 "k(n)까지 비감소"는 질문의 일부가 아니라 더 강한 충분조건이었다. 셋째, 처음 쓴 겹침 정의는 같은 사례의 서로 다른 조건까지 겹침으로 셌다. 넷째, 연결 증명의 경계는 세 번 연속 지적되어 행동 규칙으로 다시 썼다. 섹션 정의를 "사례 제한"으로만 좁혔던 중간 판본은 실제 문제(행 전체의 성질인 단봉성)에서 n 범위 분할만 허용해 쓸모가 줄어드는 것을 발견하고 "노드가 함의하는 일부"로 다시 세웠다.
- Lean으로 섹션 겹침을 검사하자는 사용자 제안은 게이트로 채택하지 않았다. 대상 정의가 Lean에 없고, 서로소 판정 자체가 증명이며(실패가 겹침을 뜻하지 않음), 술어형 섹션은 판정이 임의로 어렵다는 이유였다. 사용자는 대신 노드 lease 직렬화를 제안했다.
- 실행 중 인스턴스를 새 코드로 읽기 전용 점검했다. root와 Q의 옛 선언이 peer 단계 파이프라인의 노드 전체 섹션으로 읽혀, 대기 중인 peer 둘이 먼저 돌고 두 파이프라인이 출판될 때까지 새 attempt는 뜨지 않는다.
- 같은 세션의 평가 점검에서 얻은 사실도 남긴다. 기록 11개(주장 149개, supported 147)에 대해 Opus·Sonnet 감사자 둘이 핵심 주장 11개를 모두 건전하다고 판정했고 review 판정과 일치했다. 다만 review는 독립 재유도보다 증명 부등식의 정확한 재진술에 가까웠고, 일부는 생산자 스크립트 재실행에 의존했다. 감사 1차 파견은 Opus 안전장치(`reasoning_extraction`)로, 재파견은 Fable 사용 한도로 실패해 Sonnet xhigh로 완료했다.

## 사용자 교정 신호

설계 대화에서 사용자는 내 추천을 여러 번 다른 방향으로 바꾸었다.

- ⓐ 내가 낸 기본값: 섹션을 좁게 잡으라는 규범, review의 섹션 준수 기록, lease 10분 상한, 낙관적 버전 검사(CAS), 섹션 해제 허용, 고르는 중인 attempt 수 계산.
- ⓑ 사용자의 교정: 좁게 잡기 거부(전체에서만 드러나는 패턴의 상실 우려), review 무관여, 무기한 lease, 노드 lease 직렬화, 확장만 허용, 단순 출시 간격.
- ⓒ 드러난 편향: 나는 측정 가능한 목표(병렬도, 판단의 최신성, 관측 가능성)를 직접 최적화하는 장치를 더하는 쪽으로 기울었다. 사용자는 연구 행동이 어떻게 유도되는지(큰 그림의 보존, 결정의 영속성, 세션 판단의 신뢰)를 기준으로 더 단순한 규칙을 골랐다.
- ⓓ 교정 위치: do-math 설계 제안을 낼 때는 그 규칙이 연구 세션의 수학적 행동을 어떻게 바꾸는지를 먼저 검토한다. 장치 추가 전에 기존 원칙(도구는 판단하지 않는다, 점유는 파이프라인 수명을 따른다)으로 해결되는지 본다.
