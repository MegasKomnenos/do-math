## 맥락

사용자는 C 드라이브의 유휴 공간 정리를 요청했다. 측정 시점의 여유 공간은 0.4GB였고, 10월 14일 감사 보고서(`C:\Users\wogud\disk-audit-20261014\REPORT.ko.md`, 저장소 밖) 당시의 15.85GiB에서 줄어든 주원인은 인스턴스 `parking-unimodality-fresh-20261023-014524` 하나(83GB)였다. 그 가운데 끝난 세션 1,176개의 `work/`(Lean 빌드 산출물과 소스)가 37GB였다. `check.py`는 `output/`만 검사하고 계획이 실패 세션에서 읽는 것도 로그와 `output/`뿐이어서, 끝난 세션의 `work/`는 실행기 계약상 다시 쓰이지 않는다.

이 커밋은 실행기가 반영·실패로 끝난 세션의 `work/`를 같은 폴더의 `work.tar.xz`로 바꾸게 한다. 설계에서 정한 것은 다음이다.

- 압축은 실행기와 분리된 보관 프로세스 하나(`runner.py _archive <instance>`)가 한다. 실행기 루프는 단일 스레드이고 큰 세션의 LZMA 압축은 수 분 이상 걸리므로, `finish`에서 동기로 압축하면 수집·파견 전체가 멈춘다. `finish`의 두 종료 경로와 `run` 기동에서 `archive_due`를 켜고, `tick`이 `collect` 직후 보관 프로세스가 없을 때만 띄운다. 기동 시 소급 처리는 실행기가 죽어 있던 동안 끝난 세션과 이 기능 이전 세션을 같은 장치로 덮는다. `runner/archive-lock`(기존 `InstanceLock` 재사용)으로 인스턴스당 하나만 돈다.
- 원본은 압축본을 끝까지 다시 읽어 디렉터리·파일 전부가 같은 이름과 SHA-256으로 있을 때만 지운다. 이미 있는 `work.tar.xz`는 덮어쓰지 않는다. 삭제가 중간에 끊겨 남은 일부 `work/`로 압축본을 다시 만들면 완전한 압축본이 불완전한 것으로 대체되어 데이터가 사라지기 때문이다. 남은 `work/`는 압축본에 같은 해시로 있을 때만 지우고, 다르면 둘 다 보존한다. 링크·정션이 있으면 그 세션을 압축하지 않는다.
- 보관 프로세스는 끝난 세션 중 `work/`가 남은 것이 있을 때만 띄운다. 기존 흐름 시험의 가짜 세션은 `work/`를 만들지 않으므로 시험 종료 처리와 경합하지 않고, 운영에서도 할 일 없는 프로세스를 만들지 않는다.

## 사용자 교정 신호

- 압축 방식: 나는 처음에 끝난 세션 `work/`에 NTFS 압축(LZNT1)을 권했고, 사용자는 NTFS보다 높은 압축률을 지시했다. 끝난 세션은 다시 쓰지 않으므로 경로 투명성보다 압축률이 맞는 선택이었고, 투명성의 가치를 기본값으로 과대평가한 것이 간극이다. 실측(258MiB 세션)은 xz 프리셋 6이 6.2:1에 154초, 9가 6.8:1에 171초였고 9를 택했다(압축기 약 674MiB, `ARCHIVE_PRESET` 노브).
- 시험의 일반성: 사용자는 이 사건에만 묶인 시험을 넣지 말고 견고하고 기술적으로 타당한 시험을 요구했다. 시험은 세션 ID·크기·날짜 없이 성질만 단언한다. 왕복 동일성, 부재 시 무동작, 쓰기 실패 주입(ENOSPC) 시 원본 보존과 잔여물 없음, 남은 `.part` 대체, 정션 비추종, 중단된 삭제의 마무리, 불일치 시 양쪽 보존, 종료 상태만 선택, 보관 프로세스 단일 실행, 실행기 흐름을 통한 자동 압축이다. 교정 위치는 test-driven-development의 재현 사례 작성 단계로, 사건 재현과 계약 시험을 구분하는 기준을 먼저 세우는 것이다.

## 터득한 것

- Windows WOF LZX(`compact /exe:lzx`)는 관리자 권한 없이 사용자 소유 파일에 적용되고, 압축 파일을 메모리 매핑으로 읽어도 원본과 바이트가 같다(합성 표본 8.4:1로 확인). Codex 세션 기록 3,957개 파일은 12.0GB에서 4.6GB가 되어 6.91GB를 회수했다. `compact`는 `/f` 없이 첫 실행에서 0개 압축으로 보고한 적이 있다.
- 무거운 백그라운드 작업 네 개(프리셋 9 보관 프로세스와 `compact` 셋)를 병렬로 돌리자 시스템 메모리 부족으로 Claude Code가 모두 강제 종료했다. 종료 후 점검에서 압축본과 `work/`가 함께 남은 세션은 0, 오류 로그는 비었고 `.part` 하나만 남아 설계대로 원본이 보존됐다. 이후 실행기가 띄운 보관 프로세스를 먼저 돌리고 LZX 압축을 직렬로 잇는 방식으로 바꿨다. 실행기가 띄운 분리 프로세스는 Claude Code의 백그라운드 정리 대상이 아니다.
- write-for-reader의 Codex 독해는 Codex 사용 한도(2026-11-05 08:29까지)로 실패해 두 작업을 `blocked`로 남겼다. 같은 prompt.txt를 작성 대화가 없는 gp-sonnet-high 서브에이전트 둘에게 읽혔고, 새 문단은 중심 내용으로 재구성됐으며 지적은 모두 기존 문장이었다. 대조 기록은 `임시/작문_work압축_20261029/`의 세 파일이며 이 커밋에 강제 추가했다. `.codex/writing-flow/`의 원 실행 자료는 Git 제외 로컬 자료다.
- `sed -i`(Git Bash)는 CRLF 파일을 LF로 바꿨고, Bash 도구를 거친 heredoc에서 Python 리터럴 `"\\n"`이 `"\n"`으로 기록됐다. 바이트 보존이 필요한 치환은 Python 바이트 처리와 `chr(92)`로 했다.
- 같은 파일에 앞서 있던 미커밋 변경과 겹쳤으므로, 내 편집을 정확한 문자열로 역적용한 중간 판본을 [[M-0619]]로 먼저 커밋했다. 중간 판본의 diff 통계가 세션 시작 시 `git status`의 통계와 같아 분리를 독립적으로 확인했다.

## 운영 상태(커밋 시점)

사용자 지시로 실행기에 `stop`을 걸고 옛 코드 실행기를 종료한 뒤 새 코드로 재기동했다(STOP 유지, resume 안 함). 재기동은 색인 재구성 때문에 10초 기동 확인을 넘겼지만 정상이었고, 즉시 보관 프로세스를 띄웠다. 10/22 인스턴스는 압축을 마쳤고 10/23 인스턴스는 998개 세션이 남아 진행 중이다. 그 뒤 do-math 기록, Documents·Downloads, 프로젝트·프로그램 폴더의 LZX 압축을 직렬로 잇는 작업이 대기 중이다. ASL 저장소는 이미 pack 하나로 정리되어 `git gc` 이득이 없었다. C 드라이브 여유는 0.4GB에서 29.23GB가 됐다.

## 작업 너머 시사점

- 실행기 계약에서 "세션 폴더를 그대로 남긴다"는 보존 규칙은 디스크 비용을 고려하지 않았다. 산출물의 온도(뜨거움·차가움)를 구분해 차가운 중간 자료를 압축하는 것이 삭제 없이 공간을 얻는 일반 방법이다. dream에서 묶을 후보: [[M-0618]]의 실행기 종료 원인 조사, [[M-0619]]의 메모리 부족 대응과 함께 "장기 무인 실행기의 자원 고갈 대응"으로 종합할 수 있다.
