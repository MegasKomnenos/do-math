# 기각 보관 — do-math 라운드2

## R2-07

### 원문
제목: 계획이 연구 현황에 자기 기록 ID와 자기 요청 키를 적으라는 요구는 계획이 알 수 없는 값을 요구한다

### 위치
`.claude/skills/do-math/plan.md` 「연구 현황에서 출발하기」 절의 연구 현황 항목 목록(13~24행)이 이 요구를 담는다. 15행은 바뀐 사용자 조건에 "그 입력을 받은 계획 기록 ID를 붙인다"고 하고, 17행은 '재확인 대기'에 "그 다툼 검토의 요청 키"를, 23행은 보류 항목에 "처음 보류한 계획 기록 ID"를 적으라고 한다. 「부정 판정을 근거 사슬에 전하기」의 64행도 "게시한 다툼 검토의 요청 키"를 연구 현황에 적으라고 한다. 이 값들은 모두 지금 연구 현황을 쓰는 계획 자신의 기록 ID이거나, 그 ID로 시작하는 요청 키(105행의 `<계획 ID>:reviews:<인덱스>`)다. 수리 자리는 목록 끝 24행이다.

### 기준
동결문의 목적 진술이다(`임시/do-math_검증_20261022/동결.md` 23행).

```
문서 사이, 문서와 실행 코드·검사기·시험 사이의 정합성을 확인하고 실제 결함·불필요한 중복·폐기된 계약의 잔재를 가장 간단한 수정으로 해소한다.
```

연구 현황이 기여하는 목적은 지식의 환류다(`.async/do-math-rebuild-20261021/context.md` 2절 36행).

```
다음에 할 연구는 이렇게 쌓인 지식을 읽고 고른다. 같은 시도를 되풀이하지 않고 더 나은 질문으로 나아가기 위해서다.
```

실행 코드의 사실도 확인했다. 기록 ID는 세션이 끝난 뒤 재검사를 통과했을 때 처음 만들어진다(사본 `runner.py` 400행). 계획의 `task`에는 지시·참조 밖에 `events`와 `previous_plan`만 담긴다(사본 `runner.py` 492~494행). 계획 기록 ID가 처음 드러나는 곳은 다음 계획의 `task.previous_plan`이다(사본 `runner.py` 441행, 494행). 세션 ID는 기록 ID와 다른 이름 공간이다(사본 `protocol.md` 36행).

```
runner.py 400행:  s.update(status="publishing", record="k" + uuid.uuid4().hex)
runner.py 441행:  self.state.update(last_plan=record, plan_failures=0)
runner.py 494행:  "previous_plan": self.state["last_plan"]})
protocol.md 36행: 세션 ID와 기록 ID는 서로 다른 이름 공간이며 실행기가 각각 인스턴스 안에서 중복 없이 부여한다.
```

### 영향
연구 현황을 쓰는 계획 세션은 이 칸들을 채울 수 없다. 세션 ID를 기록 ID 자리에 적거나 키를 지어내거나 칸을 비우게 된다. 다음 계획이 받은 연구 현황에서 '재확인 대기'의 다툼 검토 요청 키는 실재하지 않는 키다. 그래서 다음 계획은 `review_finished`로 도착한 다툼 검토를 미뤄 둔 전파 항목과 이을 수 없다. 이으려면 `requests` 전체를 다시 뒤져야 하고, 잇지 못하면 전파를 계속 미루거나 같은 판정을 다시 다툰다. 사용자 조건과 보류 항목에 붙인 출처 ID도 원 기록으로 내려가는 경로가 되지 못한다. 실행기를 고쳐 ID를 미리 부여하는 방법도 있지만, 이 문서에 표기 방법 하나를 정하면 산출물만 고쳐서 기준을 충족한다.

두 구성 항목은 위치·조각·대체 문면이 같다. 두 항목이 같은 결함을 지목하므로 하나로 합쳤다. 사본에서 RUNTIME.md 94행과 100행, protocol.md 113행, runner.py 323~324행을 대조해 인용과 서술이 실재함을 확인했다. 기준 인용도 확인했다. 동결.md 23행에서 R2-01은 문단 전체를, R2-14는 첫 문장을 인용하는데, 넓은 쪽인 R2-01의 인용을 취했다. context.md 126행에서 인용한 두 문장도 실재한다. R2-01만 protocol.md 113행의 중복을 지목했다. 사본에서 확인되므로 위치와 영향에 넣었다.

94행이 금지하는 "실행 상태"도 100행에 남는다. 100행의 "계획에만 실행 상태 읽기 경로를 추가한다"가 검토에 실행 상태 경로를 주지 않는 것을 이미 함의한다. 따라서 삭제로 잃는 규칙은 없다. 구성 항목 사이에 어긋난 데가 없다. 지급 키 밖에서 새 결함은 보지 못했다.
