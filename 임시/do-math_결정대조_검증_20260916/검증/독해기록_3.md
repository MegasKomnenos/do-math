## 그 외 없음

담당 파일 44개와 기준 원문 17개를 모두 끝까지 읽은 뒤 대조했다. 위 네 항목 밖에서는 결함을 찾지 못했다. 이름으로 적으면 다음과 같다.

- test_session_scheduler.py의 모델 대기와 하위 모델 우회 금지, 교차 프로세스 슬롯, 운영과 작업 풀 분리, Windows Job 종료 대기, 정지 전파, 작업이 가득 찬 때의 운영 점검, 계획 큐 재정렬, 평가 전달, 진단 대기, 진행 중 점검 실패, 운영 요청 순서 시험.
- test_research_recovery.py·test_submission_boundaries.py·test_submission_tools.py·test_currentness_recovery.py·test_task_scope.py·test_lifecycle_engine.py·test_operator.py의 분석.md §2~§4·§10과 형식-절차 수리 결정에 대응하는 시험. 대상은 완료 기준 교체, 모집단 오류 구분, 실패 계획 보류와 진단, 완료 과제 readiness 제거, 사용자 정지·HOLD·대화 소실 보호, 접수 시각 순서, 실제 의존 현재성, 재실패 격리, 재생성 방지, 생산자 검사 명령, 큰 보고 재사용, AI 과제 자율 철회, 판독 정정의 의존 정지다.
- test_scholarly.py·test_codex_adapter.py·test_model_runner.py의 scholarly 설정 회수와 명시적 전달.
- 나머지 담당 파일(test_academic, test_academic_engine, test_budget, test_cli, test_cli_advanced, test_context_store, test_contracts, test_controls, test_document_followup, test_engine, test_external, test_feature2_migration, test_formal, test_git_store, test_governance, test_knowledge, test_knowledge_import_engine, test_knowledge_io, test_native_probe, test_observations, test_planning, test_preflight, test_probe_codex, test_purpose_engine, test_query_records, test_reading_map, test_repository, test_review_cycle, test_review_engine, test_review_research, test_standalone, test_state_checks, test_windows_job)은 사용자 확정 사항과 어긋나는 기대값이나 누락을 찾지 못했다.

항목으로 쓰지 않은 관찰은 셋이다.

- `PurposeHarness`(test_purpose_engine.py 285~295행)가 호환 모드로 인스턴스를 만들어, 이를 쓰는 복구 시험이 세션 모드 `_run_parallel`을 거치지 않는다. 하네스 기본값을 바꾸면 순차 순서를 가정하는 시험 다수가 영향을 받는다. 실행하지 않고는 대체 문면을 확정할 수 없어서, 세션 모드 전용 분기 하나를 항목 2로 좁혔다.
- test_reading_map.py 73~78행의 설치 판본 검사는 `references/모델과-실행예산.md`를 명시하지 않는다. 구현(engine.py 330~335행)이 reading map 전체에서 목록을 만들고, 그 문서가 목록에 들어 있음은 같은 파일 31~32행이 검사하므로 결함으로 세지 않았다.
- verification.json의 `evidence_notes.discovery`가 적은 대로 test_document_followup·test_governance·test_knowledge_import_engine·test_observations에는 직접 실행 진입점이 없다. 동결문이 정한 회귀 명령은 `unittest discover`이므로 이 네 파일도 실행되며, 사용자 결정과 어긋나지 않는다.
