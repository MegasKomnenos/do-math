# 합의: do-math 개선안 (RI-01M3HM0XCF7D8N3M2QXABCEZ20 피드백 기반)

## 독자가 읽고 얻을 것

사용자(do-math 설계·운영자)가 개선안 전체를 읽고 무엇을 어떤 순서로 고칠지, 각 안이 어떤 사실과 원인에 근거하는지, 무엇을 사용자가 결정해야 하는지, 포크 아이디어를 채택할지 판단할 수 있어야 한다.

## 압축 진술

사용자가 정한 입력 상한 2,000,000B는 동일성 검토의 막힘을 풀지만, 같은 인스턴스는 목표 감사에서 다시 막힌다. 목표 감사 입력에 검사 원출력 5.38MB가 두 번(약 10.7MB) 들어가기 때문이다. 그래서 핵심 수리는 판단 역할의 입력에서 기계 증거를 빼는 투영이다. 여기에 세 결함의 원인 수리를 더한다. 자기 점검 응답은 저장 스키마에 없는 필드 때문에 항상 거부된다. 운영 점검은 한 제출 검사 안의 두 허용 집합이 서로 모순되고, 적용 시각 경쟁이 수리 횟수를 소모한다. 작업자 도구 명령은 pythonw.exe로 만들어진다. 이 네 수리와 상한 변경을 함께 해야 hello world 인스턴스가 목표 감사까지 도달할 수 있다. 포크 아이디어는 현재 구성(세션 비보존)과 자기 점검 계약상 바로 쓸 수 없다. 원인(스키마 결함과 도구 실행 중에도 흐르는 기한)을 더 단순하게 고친 뒤 측정으로 재판단하기를 권한다.

## 경중 선언

- 무거운 것
  1. 2MB 결정의 효과와 한계. 동일성 검토 예산은 약 1.77MB가 되어 통과한다. 목표 감사는 `engine.py:1749`와 `proposal_view`(`knowledge_records.py:95-96`)가 원출력을 두 번 실어 약 10.7MB이므로 여전히 막힌다. 따라서 검토·감사 입력 투영을 필수 수리로 둔다.
  2. P0 수리 네 가지의 원인과 변경 지점. 입력 투영, 자기 점검 스키마, 운영 점검 참조·현재성, pythonw.
  3. 포크 아이디어 평가. CLI는 지원하지만 do-math는 `--ephemeral`/`--no-session-persistence`로 세션을 남기지 않는다. 계약상 쟁점과 이번 기록에서의 효과, 더 단순한 대안(도구 실행 중 기한 정지)을 다루고, 권고는 보류 후 측정이다.
- 가벼운 것: check_lean 성능 개선 후보 5개와 측정법, 형식 증거 저장 정규화, 관찰 창 근거 기록, 종결 후 과제 표시, 문서-코드 불일치, 사용자 결정 목록, 검증 계획(재현 시험 먼저, 새 인스턴스 완주), 미커밋 변경과의 관계.
- 뺄 것: 조사 경위, 조사자별 반환 원문, 파견문 전제의 오류 경위.
