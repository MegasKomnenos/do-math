# do-math 전면 검증 종료 보고

## 1. 종료 판정과 수치

요청한 1라운드를 완료했다. 공식 스크립트 `vr.py 종료집계`가 종료 조건의 세 번째인 라운드 상한 도달을 판정했다. 라운드 수와 상한은 모두 1이다. 수리자 8기(영역 4·관점 4), 심사자 3기·정족 3으로 수행했으며 수리자와 심사자는 모두 gpt-6-astra였다. 병합은 codex-full 기본 배정인 gpt-5.6-terra low를 사용했다.

수리 항목 하나는 결함의 지적과 수리안을 담는다. 조각 하나는 파일의 한 행 구간과 그 대체 내용을 짝지은 편집 단위이며, 한 항목에 조각 여럿이 포함될 수 있다. 수리자가 제기한 25개 항목·82조각 중 항목 6개가 교차해 묶음 3개를 만들었다. 단독 19개와 병합 3개, 총 22개 심사 항목에 대해 세 심사자가 각각 전건 판정했다. 공식 확정은 수리 20개, 무처분 1개, 기각 1개다. 공식 적용은 20개 심사 항목·59조각·39파일이며, 병합 구성 항목을 각각 세는 장부 본표의 적용 수는 22행이다.

사용자의 후속 지시로 기각·무처분 두 심사 항목을 운전자가 다시 검토해 모두 직접 수리했다. 이 후속 수리를 공식 적용 20개에 합쳐 기록하지 않았다. 최종 정본 변경은 42파일이며 생성 미러 42파일을 함께 갱신했다.

## 3. 상신·무처분 잔여와 기각 보관

상신 잔여와 최종 미처리 지적은 없다. 공식 기록에는 R1-11이 기각, R1-M2의 구성 R1-08·R1-25가 무처분으로 남는다. 다음 직접 처리로 해결됐으며 원 심사 기록을 소급 변경하지 않았다.

- R1-11: 세 심사자는 CLI 성공 값을 `result`에서 읽어야 한다는 지적은 인정했지만 README 대체 조각의 닫는 코드 울타리 누락을 이유로 기각했다. 운전자는 `cli._emit`의 실제 출력을 확인하고 울타리를 보존해 README와 CLI 실행 계약을 수정했다. 초기화의 `result.instance_id`와 `result.operator_schedule` 좌표도 맞췄다. JSON 3블록을 파싱하고 init 예제를 실제 `_emit` 값과 대조했다.
- R1-M2: 세 심사자는 `_identity_assessment`의 `effective`가 읽히지 않고 함수 정의 1곳의 인자 선언과 호출 6곳의 인자 전달을 함께 제거하는 것이 정합함을 인정했으나 실행 결과가 바뀌지 않는다는 이유로 무처분했다. 사용자가 죽은 매개변수 정리를 명시했고 후속 직접 처리 권한도 주었으므로 운전자는 제거했다. 판정 생성의 반환값과 별도의 사용 효력 계산은 유지했으며 연결된 지식·저장 회귀 시험으로 확인했다.

기각·무처분 원문과 판정은 `임시/do-math_검증_2026-09-24_astra8_3차/_기각보관/astra8-3-라운드1.md`에 있다. 이 파일과 상세 실행 로그·시험 보고는 Git 제외 로컬 자료다. 추적되는 장부와 이 보고가 지속 기록의 진입점이다.

## 4. 자체 처리·승계

승계는 없다. 승계는 사용자가 이전에 확정한 수리 방향을 새 선택 없이 남은 위치에 적용하는 절차를 뜻한다. 여기서 신호 번호는 `.agents/skills/verify-rounds/SKILL.md` §8의 분류다. 신호 4는 지급 목록·산출 서식 등 절차 구조를 바꾸는 예상 밖 판단이고, 신호 6은 동결문·불변식과의 충돌이다. 자체 처리는 다음과 같다.

1. 신호 4: Windows에서 같은 codex CLI 인자·표준 입력·산출·로그 계약을 Python subprocess로 실행했다. 모델·노력·독립성·정족은 유지했다.
2. 신호 4: commit-harness의 결합 불변식에 따라 생성 미러·메모리 노드·색인을 커밋 범위에 포함했다.
3. 신호 4: 수리자 1의 실제 입력에서 시험 9행, 수리자 7에서 시험 20행이 출력 절단으로 빠졌다. 동일 모델·노력·컨텍스트에서 원 파견문과 검산 좌표를 주어 해당 파일 전행을 다시 읽고 기존 판단·수행 기록을 보완했다. 새 라운드나 새 수리 기를 만들지 않았다.
4. 신호 6: 공식 적용 후 단위 시험 하나가 실패했다. R1-03의 봉인 결속 검사는 같은 실행·응답·확장·스키마인지 검사하는데, 기존 복구 시험의 모형 check에는 그 정보가 없었다. 제품 검사를 유지하고 시험의 receiver mode·execution_id·schema_ref·내용 해시를 현행 생산 계약으로 구성했다. 최초 300성공·1실패를 보존한 뒤 301개 전건을 다시 실행해 통과했다.

기각·무처분 두 항목의 직접 수리는 자체 상신 판단이 아니라 심사 중 도착한 사용자 후속 지시를 따른 것이다.

## 5. 마지막 라운드 결산과 검증

공식 본표는 적용 22, 무처분 2, 기각 1, 그 밖의 상태 0, 합 25행이다. 무처분 2행은 병합 심사 항목 1개의 구성원이다. 적용 0의 연속 횟수는 0이며 한 라운드 상한으로 종료했다. 수렴이나 무결함을 선언한 종료가 아니다.

- 기준선 단위 시험: 297개 성공.
- 최종 단위 시험: 301개 성공. 최초 적용 후 실패 1개는 위 시험 모형 보완으로 해결했다.
- 변경부 통합 시험: 31개 성공. 변경 시험 중 단위 그룹에 든 항목은 제외했고, 무효 인자 제거의 지식·저장 소비 경로와 CLI 오류 봉투 시험을 더했다.
- 구조 검사: `probe_cli.py --skill-only` verified, Python 200파일 AST 파싱 성공.
- 문서 검사: README JSON 3블록, init 응답과 실제 `_emit` 값, 코드 울타리 균형 확인.
- 미러·공백 검사: 생성기 `--check`가 398파일 드리프트 없음, `git diff --check` 통과.

전체 통합·Lean·자원 스위트와 실제 모델 연구 운전은 수행하지 않았다. 위 시험과 정적 검토의 성공을 실제 연구 성과나 수학 판정의 완전성으로 확대하지 않는다.

graphify는 최종 원본 228파일·6,183노드·21,784관계로 갱신됐으며 status는 `current`, 의미 추출 대기는 0이다. 변경 문서 10개의 의미 추출과 구조 추출, graph.html·tree.html 생성이 완료됐다. 첫 호출은 README의 의미 추출 결과가 존재하지 않는 파일 경로를 대상으로 제시해 검증에서 거절됐다. 기존 그래프는 보존됐다. 문서마다 의미 추출 캐시 하나를 사용한다. 첫 호출에서 성공한 변경 문서 9개와 변경 없는 문서 13개의 캐시를 합쳐, 두 번째 호출은 문서 22개의 캐시를 재사용했다. 같은 README 원문에서 의미 추출을 다시 실행해 경로 검사를 통과했다. 그래프 산출물은 Git 제외 로컬 자료다.

## 9. 운영 기록 요지

관련 스킬로 verify-rounds, simplify, writing-skills, write-for-reader, graphify, commit-harness와 기억 구조의 memory-harness를 사용했다. 8기 전원의 수행 기록을 담당 사본과 대조했고, 두 통독 보완 뒤 실제 세션 도구 출력에서 필수 비공백 원문 행의 미출현은 0이었다. 두 담당 체계를 합친 필수 범위는 148,364행이다. 이것은 입력 출현의 근거이며 전행 이해를 인증하지 않는다.
