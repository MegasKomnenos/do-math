# do-math 전면 검증(2차) 종료 보고

이 런은 `.claude/skills/do-math/` 253개 파일을 한 라운드 검증했다. 산출물은 네 경량화 커밋과 직전 안정화 검증(bdccee3)을 거친 판본이고, 이번 런은 경량화의 안정화를 넘어 스킬 전체의 결함, 특히 불필요한 복잡성과 해결책의 최적성을 넓게 보았다.

수리자 8기(Claude Opus 5.5 high)가 항목 92건을 냈다. 심사자 3기(Codex `gpt-6-astra` medium)가 정족 3으로 판정해 수리 75건을 승인했고, 이를 공식 적용했다. 이어서 세션이 사용자 위임에 따라 기각 6건과, 신호 1 자체 처리로 무처분이 된 상신 1건을 직접 판정해 모두 반영했다. 장부에는 원 심사 판정을 그대로 두고, 세션의 후속 반영은 따로 적었다. 반영 뒤 통합 확인은 시험 1,844개 가운데 1,841개 통과, 1개 건너뜀, 2개 오류였다. 오류 둘은 시험 쪽 전제 결함이었고, 두 시험 파일을 고친 뒤 해당 모듈 22건이 통과했다.

가장 무거운 결과는 둘이다. 하나는 실제로 깨지던 결함의 수리다. 정비 fence 아래에서 `run`이 비정상 종료하던 것, 허가 없는 외부 요청의 사용자 질문이 저장에서 실패하던 것, 시스템이 관찰한 실패의 영향 전파가 효과를 통째로 버리던 것이 여기에 든다. 다른 하나는 여러 모듈이 따로 적던 같은 규칙과 모듈 사이의 밑줄 이름을 정본 하나로 모은 것이다. 직전 런이 남긴 잔여 후보 넷이 모두 여기서 처리됐다. 코드 행은 거의 줄지 않았다(114파일, 추가 958행, 삭제 965행). 또 심사를 거치지 않은 변경이 있으므로 3절과 9절에 그 범위를 따로 적는다.

## 1. 종료집계와 종료 항

`종료집계` 결과는 「판정: 종료 — 판정 순서 3항 (라운드 수 1 ≥ 상한 1)」이다. 라운드 1의 적용은 본표 행 기준 84건이다(본표 92행). 이 값은 공식 적용 75건을 묶음의 구성 행까지 풀어 센 원 판정의 상태이며, 세션이 직접 반영한 8행은 들지 않는다. 라운드 하한과 상한이 모두 1이었으므로 적용 건수와 관계없이 이 라운드로 끝났다.

## 2. 라운드별 제기와 적용

라운드는 1뿐이다. 계수 단위가 서로 다르므로 나누어 적는다.

| 단위 | 수 |

| 조각(제기) | 651건 |
| 묶음 | 9건(구성 항목 19건) |
| 심사 대상 | 82건(단독 73, 병합 9), 입력 상한 때문에 배치 2개(41·41) |
| 심사 확정 | 수리한다 75, 사용자에게 올린다 1, 승인하되 고치지 않는다 0, 전달 0, 기각 6 |
| 공식 적용 | 심사 대상 75건, 조각 527건, 파일 102개. 본표 적용 84행 |

## 3. 상신·무처분 잔여와 기각 보관

본표의 상태 칸은 원 판정을 보존하므로 기각 7행과 무처분 1행이 그 상태로 남는다. 실제로는 세션이 사용자 위임(「심사에서 기각 혹은 무처분으로 처리된 것은 네가 직접 살펴보고 … 재량껏 판단해 처리」)에 따라 여덟 행 모두를 반영했다. 그래서 반영되지 않은 기각이나 무처분은 남아 있지 않다. 원문과 판정, 근거는 `임시/do-math_검증_20260927-2/기각보관/do-math-20260927-2-라운드1.md`에 보존했다. 이 처리들은 독립 심사의 승인을 받지 않은 변경이다.

- **R1-M9(artifact 접두 리터럴과 과제 종결 상태 리터럴)**: 기각 사유(3/3)는 종결 상태 규칙의 사본이 `task_contracts`의 판정 세 곳 등에 남아, 정본을 옮기는 것만으로는 손상이 없어지지 않는다는 것이었다. 사유가 옳았다. 조각 82건을 모두 반영하고, 남은 과제 종결 상태 리터럴 12곳을 `TERMINAL_TASK_STATUSES`로 바꿨다.
- **R1-61(SHA-256 스키마 노드 정본)**: 기각 사유(1/3)는 스키마 빌더 `governance.additional_audit_schema`가 전역 노드를 그대로 실어 돌려주면 이음새 정본 5절의 반환 계약을 어긴다는 것이었다. 그 자리만 `json_copy(SHA256_SCHEMA)`로 고쳐 반영했다.
- **R1-84(입력 축소 뒤 입력 모양 서술)**: 기각 사유(3/3)는 조각 하나가 코드의 「참조 표현이 원래보다 짧을 때만 바꾼다」는 조건을 지워 새 불일치를 만든다는 것이었다. 그 조건을 되살려 반영했다.
- **R1-47(`_identity_assessment` 별칭 제거)**: 기각 사유(3/3)는 `test_trust_continuation`의 대역이 그 메서드를 덮어쓴다는 것이었다. 대역을 모듈 함수 패치로 바꿔 반영했다.
- **R1-09(복구 관문 시험)**: 기각 사유(1/3)는 성질 둘을 시험 하나에 넣는다는 것이었다. 기존 시험은 실제로 검사하는 HOLD 성질에 맞게 이름을 고치고, 종료 미확인 실행의 대기를 새 시험으로 나눴다.
- **R1-35(시스템 관찰 영향 전파의 소비자 없는 보류, 상신 제안)**: 기각 사유(2/3)는 발생 경로가 확인되지 않았고, 추천안이 미해결 참조에 대한 독립 범위 확인을 없앤다는 것이었다. 코드를 확인하니 그 확인은 지금도 일어나지 않는다. 시스템 경로에서 독립 검토가 요구되는 조건은 미해결 참조뿐이다. 그런데 보류된 계획을 검토하거나 적용하는 경로가 코드 어디에도 없어서, 파급 전체가 버려진다. 그래서 계산된 영향을 늘 적용하고 미해결 참조를 재평가 사건의 사유에 싣게 고쳤다. 이 수리는 영향받는 판정·과제·관계를 「현재가 아님」으로 표시하고 연구 계획의 재평가를 부른다. 지금 버려지던 파급을 되살리는 쪽이며, 지금 실제로 수행되던 확인은 하나도 없애지 않는다. 새 시험 하나를 더했다.
- **R1-80(`repair_execution`의 엔진 밑줄 메서드 호출, 무처분)**: 추천 선택지대로 엔진 인자 함수 일곱을 `RepairExecutionMixin`으로 옮겼다. 동작은 같다. 4절에 판단 근거가 있다.

수리자가 결함 후보로 보았지만 항목으로 쓰지 않은 것이 남는다. 모두 각 수리 산출의 수행 기록에 이유가 있으며(라운드 디렉토리는 정리 대상이므로 요지를 여기에 옮긴다), 이 런의 잔여로 둔다.

- 엔진 클래스 밖의 인스턴스 종료 상태 리터럴(`{'closed', 'completed'}` 등, `scheduled_operator`·`scheduler`·`provider_engine` 등). 이 모듈들이 함께 import할 낮은 소유 모듈을 먼저 정해야 한다(수리 7).
- 실행 프로필 참조 모양의 네 정의. Job 안에서 패키지 없이 적재되는 모듈의 import 제약 때문에 정본 위치를 먼저 정해야 한다(수리 7).
- Windows 경로 성분 규칙 두 벌(`control_transport`만 `[]`를 더 막는 이유 미확인), 실행 상태 불변식이 전이 검사와 저장 검사에 이중으로 있음(수리 7).
- `submission.load_json`과 `file_io.strict_json_loads`의 엄격 JSON 규칙 중복, 역할 집합 리터럴 세 곳, `CLI-실행-계약.md`의 중복 서술 한 쌍(수리 5).
- 역할 면제 집합의 사본 세 곳과 `revision_requested` 판정 차이. 같은 규칙인지 원문으로 확정하지 못했다(수리 4).
- `_knowledge_io_control`이 `completed` 인스턴스를 `ready`로 되돌리는 동작의 의도 미확인, 시험만 쓰는 제품 인자 셋(수리 2).
- 연구 계획 계약의 `goal_assessment_basis` 서술, 모델 배정의 「평가 없음이면 상 등급」 규칙의 문서 누락(수리 8).
- 종결 상태 정본을 `planning.TERMINAL_TASK_STATUSES`라는 재수출 이름으로 읽는 소비자 여럿(세션 관찰). 동작은 같지만 정본 경로가 둘이다.

## 4. 자체 처리와 승계

자체 처리는 1건, 승계는 0건이다.

- **신호 1, R1-80**: 심사 3기가 모두 「사용자에게 올린다」로 처분한 조각 없는 상신 제안이다. 이 수리 방향을 담은 사용자 확정 기록이 없어 승계는 서지 않았다. `상신_자체판단`이 켬이므로 세션이 물음 셋으로 판단했다.
  - 오판의 비용: 동작을 바꾸지 않는 구조 정리라, 잘못되어도 손상은 통합 시험과 다음 수리가 잡는 범위에 머문다.
  - 되돌리기 비용: 파일 둘의 기계적 이동이다.
  - 판단 가능성: 이음새 정본 「원칙」과 M-0351의 엔진 믹스인 구조로 근거가 서고, 사용자만 가진 정보가 필요하지 않다.

  그래서 올리지 않고, verify-rounds `SKILL.md` §8이 조각 없는 상신 제안에 허용하는 유일한 값인 「승인하되 고치지 않는다」로 바꿨다. 이 값은 절차상 처분의 기록이다. 실제로 코드를 고칠지는 사용자 위임에 따른 직접 처리가 따로 정했고, 3절대로 반영했다.

## 5. 마지막 라운드 결산

라운드 1 결산은 본표 행 단위로 센다. 적용 84, 수리확정 0, 무처분 1, 상신 0, 전달 0, 기각 7, 결번 0, 병합 0, 제기 0, 합 92(본표 행 수). 기각 7행은 기각 6건 가운데 묶음 R1-M9가 구성 항목 두 행(R1-57, R1-63)을 갖기 때문이다. 결산은 원 심사 판정의 상태이며, 여덟 행의 후속 반영은 3절과 장부 운영 기록에 있다. 최종 산출물에는 적용 84행과 직접 처리 8행을 합한 본표 92행이 모두 반영되어 있다.

## 6. 앵커 대조 변경 자리

앵커와 현재 산출물을 비교하면 114개 파일이 다르다(추가 958행, 삭제 965행). 행 수는 거의 같다. 이번 런의 변경은 행을 줄이기보다 같은 규칙의 사본을 정본 하나로 바꾸고 계약 불일치를 고친 것이 대부분이기 때문이다. 주요 변경 자리는 다음과 같다.

- **실제로 깨지던 결함.**
  - 정비 fence가 있는 상태에서 `run`을 시작하면 `scheduler._run_parallel`이 `UnboundLocalError`로 JSON 봉투 없이 끝났다(R1-01). 회귀 시험을 더했다.
  - 질문 연결의 저장 스키마가 엔진이 쓰는 `question_kind`를 받지 않아, 허가 없는 외부 요청을 사용자 질문으로 보존하는 경로가 저장에서 실패했다(R1-24).
  - 시스템 관찰 영향 전파가 미해결 참조를 만나면 파급을 읽는 곳 없는 목록에 넣고 버렸다(R1-35).
  - `setup_lean.py`의 Lean 미발견과 toolchain root 부재가 「표준 출력에 JSON 하나」 계약을 어겼다(R1-M1, 직전 런 R1-32의 불완전 수리).
  - 검토 주기가 같은 종결을 자원 처분에서만 phase `done`으로 기록했다(R1-39).
- **정본 하나로 모은 규칙.**
  - 현재 UTC 시각 문자열 42곳을 `file_io.now()`로(R1-56), artifact 경로 접두 57곳을 `ARTIFACT_ROOT`로(R1-57) 모았다.
  - 과제 종결 상태 20여 곳을 `TERMINAL_TASK_STATUSES`로(R1-63과 세션 보완), 엔진의 인스턴스 종료 판정 22곳을 `_instance_closed`로(R1-64) 모았다.
  - SHA-256 스키마 노드 다섯 사본을 `SHA256_SCHEMA`로(R1-61) 모았다.
  - 관찰 방식 어휘(R1-65), 「과제 연구·보충 조사인가」 판정 약 20곳(R1-68), 「사용자 결정 설정이 바뀌는가」 판정(R1-82), 「지정 판정자인가」 판정(R1-45), 목록 참조 판독(R1-52), 미종료 행동 ID 규칙의 남은 사본(R1-M8)을 각각 공유 정의 하나로 모았다.
  - 관찰 사실 저장 규칙의 엄격 JSON(R1-M4), 제출 수락 영수증 종류(R1-M3), 저작 필드 집합(R1-25)은 기존 정본을 쓰게 했다.
- **모듈 사이의 밑줄 이름.** `governance`, `knowledge`, `knowledge_io`, `knowledge_records`, `review_cycle`, `integration`, `ResearchRepository`, `GitStateStore`, `FrozenText`, 엔진 처리기 표의 밑줄 이름을 공개 이름으로 바꿨다(R1-70~R1-79). `repair_execution`은 엔진 믹스인이 됐다(R1-80).
- **죽은 인자와 잔재.**
  - 지운 인자와 상태: `withdrawn` 상태, `pump(limit)`, `ControlTransport(publish)`, `front`, `self_check_only`, `operation_id`, 정지 단계 축 `stop_phase`(R1-M7, 직전 런 R1-08의 불완전 수리), 연구 계획 실패 분류표의 죽은 `error_kind` 일곱.
  - 지운 코드: 옛 세션 예산 방식의 잔재, 중복 지역 import, 단순 위임 별칭.
- **역할 계약과 코드의 불일치.**
  - 지식 개정 필드 규칙을 허용 목록으로 고치고, 문서와 코드의 대조 시험을 두었다(R1-M6).
  - 삭제된 `failure_diagnosis` 입력을 안내하던 연구 계획 계약을 고쳤다(R1-85).
  - 알리지 않던 입력과 출력을 계약에 더했다. 운영 점검의 필수 `task_assessments`(R1-87), 목표 감사의 추가 감사 입력과 출력(R1-88), 유지보수의 영향 독립 검토 확장 금지(R1-89)다.
  - 입력 축소 서술을 코드에 맞췄다(R1-84).
  - CLI 계약의 규칙 사본과 제거된 경로의 잔재를 정리했다(R1-90~R1-92).
- **시험.**
  - 이름이 말하는 성질을 단언하지 않던 시험 둘을 바로잡았다(R1-09, R1-55).

## 8. `_` 보조 스크립트 승격 후보

`_직접반영.py`: 세션이 채택한 기각 항목의 조각을 사본에 적용해 차이를 만들고, 그 차이를 GNU patch로 현재 산출물에 옮긴다. 공식 `적용`은 한 라운드에 한 번만 돌고 승인 집합만 반영하므로 이 작업을 덮지 않는다. 기각·무처분의 세션 직접 처리가 사용자 위임으로 두 런 연속 나왔으므로, 「세션이 채택한 항목의 추가 적용」을 공식 하위명령으로 둘지 검토할 후보다. 다만 이번에는 111조각 가운데 승인분과 이웃한 7헝크가 문맥 불일치로 실패해 손으로 반영했다. 그래서 승격한다면 좌표 대신 축자 대조로 적용하는 방식이 필요하다.

직전 런의 승격 후보 `_allocation.py`는 승격하지 않기로 했다. 재사용할 부분인 영역별 크기 합은 `영역검산` 출력이 이미 내고, 나머지인 모듈별 영역 대응은 세션 재량의 판단이다.

## 9. 운영 기록 요지

- **관점 배치.** 관점 넷을 관통 대상으로 나눴다. 수리 5는 bdccee3의 변경, 수리 6·7은 이음새 정본 6절 표의 위치 모듈을 겹침 없이 나눈 두 묶음과 그 영역의 표 밖 사본, 수리 8은 역할 계약 열한 개와 코드의 대응을 맡았다. 필수 독해는 관점마다 수천 행으로 줄였다. 네 관점 모두 필수 독해를 직접 끝까지 읽었다. 직전 런에서 관점 하나가 diff 21,296행을 받아 하위 독해자에게 넘겼던 일은 반복되지 않았다. 수리 5는 bdccee3와, 직전 런에서 심사 없이 반영된 17건을 하나씩 판정했다. 17건에서는 결함을 찾지 못했고, 직전 런 수리의 부족과 파급 7건(R1-49~R1-55)을 냈다.
- **수리 4 재파견.** 첫 수리 4는 컨텍스트가 1M을 넘겨 자동 압축되었다. 사용자 지시로 멈추고 같은 파견문으로 다시 파견했다. 재파견본은 담당 58파일(23,014행)을 모두 읽었다. 이 영역은 영역 넷 가운데 가장 크다.
