## 2. understanding

### (a) 이 시스템이 무엇을 하며, 돌리면 내 기계에서 무엇이 실행되는가

do-math는 내가 정한 수학 명제 하나(root)를 놓고, 서로의 대화를 기억하지 못하는 새 AI 세션을 잇달아 띄워 연구를 시키는 시스템이다. 세션들은 대화가 아니라 instance 디렉터리 안의 Git 저장소를 공유한다. 한 세션(attempt 또는 explore)이 작업하고, 둘째 세션(peer)이 그 작업을 레코드 후보로 다듬고, 셋째 세션(review)이 원본과 대조해 판정한 뒤 게시한다. 내 기계에서는 Python으로 된 runner가 detached 프로세스로 떠서, Claude Code CLI나 Codex CLI를 자식 프로세스로 기본 8개까지 동시에 실행한다. 이 CLI들은 내가 이미 해 둔 인증을 그대로 쓴다. 이 밖에 대화를 재개해 종료를 다시 생각하게 하는 session host라는 별도 프로세스가 있고, instance마다 Lean 컴파일을 맡는 Lean broker가 하나씩 있다. 워커는 사람 감독 없이 내 계정 권한으로 파일을 읽고 쓰고 명령을 실행한다. 작업 공간의 경계는 지시문으로만 정해져 있고 OS 샌드박스는 없다. 워커가 읽은 자료는 모델 제공자에게 전송된다. README에서 비용 상한이나 시간 상한은 찾지 못했다. 오히려 attempt에는 시간 상한이 없다고 되어 있다.

### (b) 시작하려면 무엇을 준비하고, 어떤 순서로 무엇을 치는가

필요한 것은 Python 3.12 이상, Git, 설치하고 인증까지 마친 Codex CLI나 Claude Code CLI(둘 다 있어도 된다), Lean 4다. Mathlib은 문제에 필요할 때만 쓴다. 시작하는 길은 둘이다. 하나는 Claude Code나 Codex 안에서 do-math 스킬에게 연구를 시작하라고 말하는 것이다. 그러면 operator 대화가 명제와 설정을 준비하고 runner를 띄운다. 다른 하나는 손으로 띄우는 것이다. (1) 정확한 명제를 UTF-8 `root.md`에 쓴다. (2) 실행 파일 경로를 담은 `settings.json`을 만든다. 예시에는 Lean 경로만 있다. (3) 기록 언어나 방법 제한 같은 상시 조건이 있으면 `start` 전에 `input --file`로 넣는다. (4) do-math 저장소 밖의 새 경로나 그 저장소의 `.skill-workspace/` 아래를 instance 경로로 정하고 `runner.py init <instance> --root ... --settings ...`를 친다. (5) `start`, (6) `status`를 친다. 명령 형식은 모두 `python <skill>/runtime/runner.py <command> <instance> ...`다. 기본 모델 설정은 xhigh effort와 백만 토큰 컨텍스트다.

- 85행: "The runtime needs Python 3.12 or later and Git, and uses only Python's standard library. It needs the Codex CLI, the Claude Code CLI, or both, installed and authenticated"
- 85행: "It needs Lean 4, with Mathlib when the problem requires it."
- 89행: "From Claude Code or Codex, ask the do-math skill to start research on a proposition."
- 91행: "For a manual launch, write a UTF-8 `root.md` containing the exact proposition"
- 110행: "Create an instance at a new path outside the repository or under its ignored `.skill-workspace/`, then start it:"
- 115-117행: `python "$skill/runtime/runner.py" init $instance --root C:/research-input/root.md --settings C:/research-input/settings.json` / `python "$skill/runtime/runner.py" start $instance` / `python "$skill/runtime/runner.py" status $instance`
- 120행: "Standing conditions, such as the language of the records or limits on methods, go in a file submitted with `input --file <file>` before `start`."

### (c) 돌아가는 동안 무엇을 할 수 있고, 어떻게 멈추거나 되살리는가

`start`로 띄운 runner는 터미널이나 operator 대화를 닫아도 계속 돈다. 돌아가는 동안 할 수 있는 일은 이렇다. `status`로 root 상태, runner 생존 여부, 세션, 밀린 작업, 제공자·모델 차단, broker 상태를 본다. `input`으로 이후 세션에 줄 정보를 넣는다. `questions`로 질문을 frontier에 직접 올린다. `review`로 종합 검토를, `organize`로 정리를 요청한다. `kill-session`으로 세션 하나의 CLI 프로세스를 끝낸다. `stop`은 새 세션을 내보내는 것만 멈추고, 이미 돌고 있는 세션은 끝까지 간다. `resume`은 그 내보내기를 다시 켠다. runner가 죽은 상태라면 `start`도 쳐야 한다. 크래시나 재부팅 뒤에는 `start`를 치면 기존 세션과 끝나지 않은 게시가 복구된다. 제공자가 거부하면 그 제공자로는 리셋까지 새로 띄우지 않고, 설정된 다른 모델이 이어받는다. root가 형식적으로 확정되면 새 attempt와 exploration이 멈추고, 남은 작업이 끝나면 runner도 끝난다. 그 전에 runner가 스스로 끝나는 조건은 글에서 찾지 못했다.

- 122행: "`start` confirms its new process and returns log paths; the runner then continues after the terminal or operator conversation ends."
- 126행: "Launch the detached runner when none is alive, including after a crash or reboot; existing sessions and unfinished publications are recovered."
- 129행: "Stop or resume new dispatch; running sessions continue. `resume` also needs `start` if the runner is no longer alive."
- 135행: "End the identified session's CLI process; its retained work is still processed."
- 139행: "A provider refusal blocks launches through that provider until its reset; a model-specific refusal blocks only that model, and configured alternatives serve later launches."
- 139행: "Formal settlement of the root stops new attempts and explorations; existing sessions finish, formalizations and organizations still launch as their inputs become ready, and the runner finishes when that work has ended."

### (d) 결과는 어디서 어떻게 읽고, 어느 정도로 믿을 수 있는가

결과는 instance 안의 `knowledge/`에 쌓인다. 진입점은 `index.md`다. `frontier.md`에는 노드마다 정확한 명제, 상태, 근거 레코드, 관계가 있고, `glossary.md`, `board.md`, 기계가 읽는 `state.json`이 있다. 레코드 하나는 `records/<id>/` 디렉터리이고 그 안에 `record.json`, `exposition.md`, `evidence/`, `review/assessment.json`, `review/feedback.md`, `provenance.json`이 있다. 형식 레코드에는 `lean/`과 `review/lean-evidence/`가 더 있다. 믿을 수 있는 정도는 등급으로 나뉜다. "informally solved"는 AI review 세션 하나가 사람이 읽는 증명을 받아들였다는 뜻일 뿐이다. 사람이 검토한 것도, 기계가 검증한 것도 아니다. 계산에 기댄 단계는 정수·구간 산술인지 binary64인지가 표시된다. "formally solved"는 review가 직접 재컴파일하고, 공리 목록을 대조하고, 명제를 노드와 하나하나 대조하는 세 가지 확인을 통과해야 붙는다. root는 이 방식으로만 확정된다. 레코드는 게시 뒤에 바뀌지 않는다. 나중의 판단은 finding으로 덧붙고, 문제가 제기되면 concern으로 표시된다.

- 13행: "It holds the fixed statement in `root.md`, the models and scheduling settings in `settings.json`, a directory for every session, and `knowledge/`, where reviewed records accumulate."
- 77행: "Its entry point is `index.md`, which lists records the organizer selected as shared context for new sessions, a directory of modules with their descriptions, and recent records not yet organized."
- 41행: "\"Informal\" here means that the argument was checked by an AI review session reading the candidate against the originals, not by a person and not by a machine."
- 45행: "A node is **formally solved** only after a Lean proof has passed three independent checks by the review session"
- 49행: "The assurance a reader should attach to the result is that of a model-reviewed argument whose complete evidence is open for inspection"
- 27행: "The record never changes afterwards. A later review that finds a defect, or confirms a result, attaches a **finding** to the record"

- 7행, "do-math counts a proposition as settled only when an independently recompiled Lean proof has been checked against the exact statement.": "settled", "informally proved"(7행), "informally solved"(41행), "formally solved"(45행), "informally proved or refuted"(79행)가 섞여 나와서 서로 어떤 관계인지 다시 읽어야 했다. 15행의 "A node is settled by proving its statement or by proving its negation"은 비형식 증명도 settled에 넣는 것처럼 읽히는데, 7행과 45행("The root is settled only this way.")은 settled를 형식 증명으로 좁힌다.
- 17행, "A section is registered through the node's **lease**, which lets one session at a time choose on that node; the lease has no time limit and ends only when the session registers, releases, or ends.": "choose on that node"가 무엇을 하는 동작인지 알 수 없었다. lease와 section 등록의 관계도 흐리다. lease는 "고르는 중"을 잠그는 것이고 등록이 끝나면 풀린다는 뜻인지 다시 읽어야 했다. 시간 제한이 없는 lease를 쥔 세션이 멈춰 버리면 어떻게 되는지도 궁금했다.
- 17행, "and it stays occupied until the work has passed through the two sessions described below": "it"이 section인지 node인지 바로 판단되지 않았다. "the two sessions described below"는 아직 소개되지 않은 peer와 review를 미리 가리킨다.
- 19행, "the role guides explain how to respect it": "role guides"가 처음 나오는 자리인데 정의가 없다. 143행에 가서야 "`roles/` holds the six worker guides"로 짐작할 수 있다.
- 21행, "When the session's conversation ends, the runner does not close the session at once.": CLI 대화가 "끝난다"는 것이 모델이 응답을 마친 것인지, 프로세스가 종료된 것인지 알 수 없다. "conversation"과 "session"이 따로 끝나는 것처럼 쓰여 있어서 둘의 차이를 다시 읽었다.
- 21-23행, "its retained work goes on." / "It goes to a **peer**.": 새 문단 첫 문장의 "It"이 앞 문단 마지막의 retained work를 가리킨다. 문단을 넘어 대명사를 이어야 해서 다시 읽었다.

## 4. missing

- 비용과 사용량 상한: 토큰·금액·세션 수·벽시계 시간에 상한을 거는 설정이 있는지 없다. 실행 결정에서 가장 중요하다. 기본값이 동시 8세션, xhigh effort, 백만 토큰 컨텍스트이고, attempt에는 시간 상한이 없다(21행). 첫 run은 1주일에 1,209세션을 썼다(55행). 구독 할당량을 쓰는지 API 과금이 되는지도 알 수 없다("under your existing authentication", 35행).
- run이 끝나는 조건: 139행에 따르면 runner는 root가 형식적으로 확정되어야 끝난다. 확정되지 않으면 무한히 도는지, 내가 언제 어떻게 끊어야 하는지 없다. 첫 run도 "The run is still going."(55행)이다.
- 전부 멈추는 방법: `stop`은 새 세션 내보내기만 멈춘다. 돌고 있는 세션, session host, Lean broker, runner 프로세스를 모두 즉시 끝내는 명령이나 절차가 없다. 안전하게 끄는 순서를 알아야 실험을 시작할 수 있다.
- CLI 권한 모드: 워커 CLI를 어떤 권한 플래그로 띄우는지(승인 생략, 전체 자동 등), 네트워크 접근이 허용되는지, 어느 디렉터리까지 쓰는지 없다. 87행은 샌드박스가 없다고만 한다. 내 계정의 다른 파일이 위험해지는지 판단하려면 필요하다.
- 설치 절차: 저장소를 클론하는 것, 스킬을 Claude Code나 Codex가 인식하게 하는 방법, `$skill` 경로가 클론 위치라는 것이 명시되어 있지 않다(113행은 예시 경로뿐이다).
- Mathlib 설정: Mathlib이 필요한 문제에서 Lake 프로젝트를 어떻게 준비해 settings에 지정하는지, 버전 맞추는 법, 디스크와 메모리 요구량이 없다. 나는 Mathlib을 써 본 적이 없으므로 필요하다. Mathlib 없이 비형식 연구만 할 때도 Lean이 꼭 필요한지도 분명하지 않다(85행 "It needs Lean 4").
- 기계 자원: 동시 CLI 8개와 Lean 컴파일에 필요한 CPU·메모리, broker의 기본 메모리·스레드 예산이 없다(lean.md로 넘김).
- 작은 문제의 규모 감각: 예시 명제(n + 0 = n) 같은 문제를 돌리면 몇 세션, 몇 시간, 얼마나 쓰고 끝나는지 없다. 143행이 언급한 "a complete small instance settled"의 규모라도 있었다면 판단에 도움이 됐을 것이다.
- 로그와 status 출력: 로그가 어디에 생기는지, `status` 출력이 어떤 모습인지, 진행 중에 `knowledge/`가 실시간으로 갱신되는지가 명시되어 있지 않다.
- 플랫폼 지원: macOS에서 실행할 수 있는지 분명하지 않다. Linux에서 명령 예시(PowerShell)를 어떻게 바꾸는지도 없다.
- settings.json의 필드: 동시 세션 수, 모델 선택, Claude만 쓸 때의 설정 등을 바꾸는 필드가 하나도 보이지 않고 운영 가이드로 넘어간다. 예를 들어 Codex가 없을 때 그냥 Claude로 넘어가는지 알아야 한다.
- 기본으로 주입되는 문서: 33행의 에세이와 글쓰기 선호 문서가 내 instance에 기본으로 들어가는지, 끌 수 있는지 없다.
- 개인정보와 외부 전송: 워커가 읽는 자료가 제공자에게 간다는 것은 쓰여 있다. 그런데 instance 밖의 파일을 읽을 가능성이나 scholarly-mcp의 대학 로그인 같은 범위는 없다.

## 6. uncertainties

- 35행의 "under your existing authentication"을 내 CLI 구독 할당량이나 내 API 키 과금을 그대로 쓴다는 뜻으로 해석했다. 어느 쪽인지 글에서 확정할 수 없다.
- 87행의 "Workers run unattended with file and command access"를 워커 CLI가 승인 프롬프트 없이 도는 권한 모드로 실행된다는 뜻으로 추정했다. 그런 플래그를 쓴다는 문장은 없다. 이 추정은 외부 지식(CLI의 무인 실행 관행)으로 메운 것이다.
- 139행을 root가 형식적으로 확정되지 않으면 runner가 스스로 끝나지 않는다는 뜻으로 읽었다. 다른 종료 조건이 운영 가이드에 있을 수 있다.
- `stop` 다음에 `kill-session`을 세션마다 치면 사실상 전부 멈출 것이라고 추론했다. runner 프로세스와 broker까지 끝나는지는 확정하지 못했다.
- `input` 명령은 122행 형식에 따라 `python <skill>/runtime/runner.py input <instance> --file <file>`라고 추론했다. 120행에는 instance 인자가 보이지 않는다.
- 117행의 `status`가 실행 중에도 쓸 수 있는 읽기 전용 명령이라고 해석했다.
- `knowledge/`가 게시 때마다 갱신된다고 해석했다. 27행 "rendered from the repository"와 136행 `render`("while the runner is off")를 근거로 runner가 돌 때는 자동으로 렌더링된다고 추론했다.
- 108행의 모델 이름("gpt-6.1-sol", "opus")과 effort 값이 내 계정에서 쓸 수 있는지는 확인할 수 없다. Codex가 없으면 producing roles도 Claude로 넘어간다고 추론했다("fall back to Claude").
- "producing roles"는 attempt, explore, formalizer로, "pipeline"은 attempt(또는 explore, formalizer)→peer→review의 한 줄기로 해석했다.
- 7, 59, 69행의 중단 주체는 사람인 user가 결정하고 AI operator가 실행한 것이라고 짐작했다. 글만으로는 확정할 수 없다.
- 33행의 에세이와 글쓰기 선호 문서가 새 instance에도 기본으로 주입된다고 읽었지만, 근거는 "Attempts, explorers, peers, reviewers and organizers also receive two documents in their starting context"라는 현재형 일반 서술뿐이다.
- Mathlib은 settings.json의 `lean.command`를 Lake 환경 쪽으로 지정하는 방식일 것이라고 외부 지식으로 짐작했다. 글에는 근거가 없다.
