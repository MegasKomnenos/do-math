## 2. understanding

### (a) 이 시스템이 무엇을 하고, 돌리면 내 기계에서 무엇이 실행되는가 (권한 포함)

do-math는 수학 명제 하나를 받아서, 서로 기억을 공유하지 않는 AI CLI 세션을 여러 개 연달아 띄워 연구하게 하는 시스템이다. 세션들은 공유 저장소인 지식 기반(`knowledge/`)으로만 이어진다. 세션은 역할별로 나뉜다. 한 세션이 수학을 만들고, 다른 세션이 그것을 기록으로 정리하고, 또 다른 세션이 검토한다. 내 기계에서는 다음이 돈다. 첫째, Python으로 된 runner가 분리(detached) 프로세스로 뜨고 터미널을 닫아도 계속 돈다. 둘째, runner가 내 기존 로그인으로 Claude Code(또는 Codex) CLI 프로세스를 기본 8개까지 동시에 띄운다. 셋째, 세션마다 그 세션이 살아 있는 동안 함께 사는 session host 프로세스가 하나씩 있다. 넷째, 인스턴스마다 Lean 컴파일을 맡는 Lean broker 프로세스가 하나 있다. 권한이 가장 중요하다. Claude Code는 권한 확인 프롬프트를 끈 채로 실행되고, 내 계정 권한으로 파일과 명령에 접근한다. 작업 공간의 경계는 지시문으로 정해 둔 것일 뿐 OS 샌드박스가 아니다. 셸 명령과 웹 검색을 쓸 수 있다. 세션이 읽은 자료는 모델 제공자에게 전송된다. "업로드"는 없다. 게시는 인스턴스의 로컬 Git 저장소에 커밋하는 것을 뜻한다.

### (b) Claude Code만 있는 내가 시작하려면 무엇을 준비하고 어떤 순서로 무엇을 치는가

준비물은 Python 3.12 이상, Git, 설치하고 로그인해 둔 Claude Code CLI, Lean 4다. 증명에 Mathlib이 필요하겠다고 내가 판단하면 미리 빌드해 둔 Mathlib 프로젝트도 준비한다. 방법은 둘이다. 하나는 이 저장소를 clone하고 그 안에서 Claude Code를 켠 다음, do-math 스킬에게 명제 하나로 연구를 시작해 달라고 요청하는 것이다. 그러면 그 대화가 operator가 되어 명제와 설정을 준비하고 runner를 띄운다. 다른 하나는 수동 실행이다. (1) 정확한 명제를 담은 UTF-8 `root.md`를 쓴다. (2) `settings.json`을 쓴다. Claude만 있으므로 `models`와 `roles.peer`, `roles.review`를 모두 `claude/opus`, `xhigh`로 지정하고, `lean.command`와 `lean.version_command`에 Lean 실행 파일 경로를 넣는다. Mathlib을 쓰려면 `lean.command`를 Lake 실행 파일 + `env` + `lean`으로, `lean.cwd`를 빌드된 Mathlib 프로젝트로 바꾼다. (3) 이 저장소 밖의 새 경로나 `.skill-workspace/` 아래를 인스턴스 경로로 정한다. (4) `runner.py init <instance> --root ... --settings ...`를 친다. (5) 모든 세션에 적용할 지시가 있으면 `start` 전에 `input --file <file>`로 넣는다. (6) `start`를 치고 `status`로 확인한다.

### (c) 돌아가는 동안 할 수 있는 것, 멈추기·끝내기·되살리기, 비용·시간 상한

실행 중에는 `status`로 상태를 보고, `input`으로 이후 세션에 지시를 더하고, `review`, `organize`, `questions`로 작업을 요청하고, `kill-session`으로 세션 하나를 끝낼 수 있다. `stop`은 새 세션 띄우기만 멈춘다. runner와 이미 돌고 있는 세션은 그대로 남는다. 실행을 완전히 끝내려면 `stop`을 치고, 돌고 있는 세션마다 `kill-session`을 치고, `runner/process.json`에 적힌 runner PID를 Windows에서는 `Stop-Process`로 끝낸다. Lean broker는 할 일이 없어지면 스스로 끝나고, 같은 방법으로 직접 끝낼 수도 있다. 크래시나 재부팅 뒤에는 `start`를 다시 치면 세션과 덜 끝난 게시가 복구된다. 상한은 사실상 없다. 시간, 세션 수, 사용량 어디에도 한도가 없고, attempt 세션 하나에도 시간 한도가 없다. 세션이 끝나려고 해도 기본값으로 세 번까지 재고를 요청받는다. 사용량 통계도 모으지 않는다. 비용은 CLI가 원래 청구되는 방식 그대로 나간다. 실질적으로 걸리는 제동은 제공자의 사용량 한도뿐이다. 한도에 걸리면 리셋될 때까지 그 제공자로 띄우는 것이 막힌다. 자연 종료는 루트가 형식적으로(Lean으로) 판정되고 남은 작업이 끝났을 때만 일어난다. 규모의 참고치로, 첫 실행은 약 7일 동안 1,227개 세션을 띄웠고 그때도 끝나지 않았다. 토큰과 비용 수치는 기록되지 않았다.

### (d) 결과는 어디서 어떻게 읽고, 어느 정도로 믿을 수 있는가

결과는 인스턴스의 `knowledge/` 디렉터리에 쌓이고, 게시가 있을 때마다 갱신된다. `index.md`로 들어가서 각 기록의 설명과 리뷰의 짧은 평가를 보고, `frontier.md`에서 각 노드(명제)의 상태, 증명, 관계, 그리고 루트까지 이어지는 경로를 본다. 개별 기록은 `records/<id>/`에 있다. 그 안의 `exposition.md`가 본문이고, `review/assessment.json`과 `review/feedback.md`가 검토 결과다. 프로그램으로 읽으려면 `state.json`을 쓴다. 신뢰도는 등급으로 나뉜다. claim마다 supported, unsupported, undetermined 중 하나가 붙는다. "informally proved"는 AI 리뷰 세션 하나가 사람이 읽는 증명을 받아들였다는 뜻일 뿐이다. 사람이 검토한 것도, 증명 검사기가 확인한 것도 아니다. "formally proved"는 리뷰 세션이 Lean 증명을 broker로 다시 컴파일하고, 공리가 `propext`, `Classical.choice`, `Quot.sound` 안에 드는지 확인하고, 진술이 노드와 일치하는지 대조한 뒤에야 붙는다. 계산에 기댄 단계는 반올림 오차를 스스로 통제하는 산술과 binary64 산술을 구분해서 봐야 한다. 첫 실행에서는 루트가 informally proved 상태였는데도 증명되지 않은 단계가 하나 남아 있었다. 그러니 informal 판정은 그대로 믿기보다 검토의 출발점으로 읽어야 한다고 이해했다.

## 3. difficulties

1. 3행. "a repository of records, each holding mathematics that one session produced, a second session developed into an account for others, and a third session assessed, kept unchanged once published with the assessment beside it." 관계절이 세 겹으로 이어진 뒤 "kept unchanged ..."가 붙는다. 무엇이 변하지 않는지(record인지 mathematics인지) 다시 읽어야 했다. "published with the assessment beside it"가 "kept unchanged"를 꾸미는지, 따로 덧붙은 서술인지도 두 가지로 읽힌다.
2. 3행. "the user does this through an AI conversation, called the operator, that prepares and operates the run on the user's behalf." operator가 내가 지금 쓰는 Claude Code 대화를 가리킨다는 것은 93행에 가서야 확실해졌다. 3행만 읽으면 do-math가 따로 띄우는 별도 AI처럼 읽힌다.
3. 7행. "the root proposition reached the state do-math calls *informally proved*: every record and every relation on two routes from proved statements to the root had been accepted by an AI review session." "root", "routes", "relation"은 각각 13행, 59행, 15행에서야 정의된다. 이 행만 읽어서는 이 상태가 어느 정도의 판정인지 알 수 없다.
4. 7행. "One necessary condition of the root does have a Lean proof." "necessary condition"이 이 시스템 안에서 무슨 뜻인지(31행의 frontier 표지)는 뒤에 나온다. 7행에서는 이 문장이 왜 의미 있는지 판단할 수 없었다.
5. 15행. "If work settles a part of what a node asserts, the record can propose the parts as nodes together with the relation that the parts cover the whole." "parts"가 무엇이고 "cover"가 논리적으로 무엇인지(합접인지 경우 나눔인지) 정의되지 않았다.
6. 19행. "While it chooses, it holds the node's **lease**, which lets one session at a time choose a section on that node" 바로 뒤의 "It stays occupied until ..." 에서 "It"이 section인지 lease인지 node인지 다시 읽어야 했다. 문맥상 registered section이다. "occupied"도 정의 없이 처음 나온다.
7. 23행. "When its conversation ends, the runner does not close the session at once." 비대화형으로 띄운 CLI에서 "conversation ends"가 무엇을 뜻하는지(모델이 응답을 마치고 프로세스가 끝나는 것인지) 정의가 없다. "conversation"과 "session"을 구별해서 쓰는 것인지도 분명하지 않다.
8. 27행. "The configuration is an ordered list with fallbacks" 어느 설정인지가 이 문장에 없다. 앞 문장의 "prefer a model"에서 모델 선호 설정이라고 추론해야 한다.
9. 27행. "*supported*, *unsupported* or *undetermined*" 43행에서 supported는 정의되지만, unsupported와 undetermined는 끝까지 정의되지 않는다. 둘의 차이(반증된 것인지, 근거가 부족한 것인지)를 알 수 없다.
10. 31행. "on a sufficient path, when a chain of relations lets a proof of the node contribute to settling the root" "sufficient path"가 59행의 "route"와 같은 대상인지 확신할 수 없어 두 곳을 오가며 다시 읽었다.
11. 39행. "keeps each compile's result so that a session can collect it after its shell tool has stopped waiting." "shell tool has stopped waiting"이 CLI 셸 도구의 타임아웃을 뜻한다는 것은 외부 지식으로 메웠다.
12. 45행. "later work may use the result within the scope the review supported." "scope"가 무엇인지(claim 범위인지 n의 범위인지) 정의되지 않았다.
13. 47행. "floating point with directed rounding, from binary64 floating point with an error model assumed in advance" directed rounding도 대개 binary64 위에서 하므로 두 범주의 경계가 어디인지 다시 읽어야 했다.
14. 51행. "A comprehensive review is launched when a concern is reported" concern을 누가 보고하는지(세션인지 사용자인지 리뷰인지)가 없다. 사용자 명령 목록(144~157행)에도 concern을 넣는 명령이 없다.
15. 57행. "some pipelines, as a producing session together with its peer and review are called, were still in progress." 용어가 먼저 쓰이고 같은 문장 안에서 사후에 정의된다. 삽입 구문 때문에 문장을 다시 읽었다.
16. 57행. "Codex gpt-6.1-sol", "Claude Fable 5.1", "Claude Opus 5.5"와 112~116행의 "`claude/opus`". 설정의 `claude/opus`가 어느 버전을 가리키는지, Fable을 고르려면 어떻게 적는지 알 수 없다.
17. 59행. 단락 전체. 정의되지 않은 낱말이 많다: "right-half part", "left-half part", "certification", "capped-threshold". 59행 한 단락이 수학 세부, 기록 ID, 시각, 산술 종류를 한꺼번에 담고 있어 예비 사용자로서는 따라가기 어려웠다.
18. 61행. "six explicit elementary pieces of it" / "points of rigor" 정의 없이 쓰였다.
19. 65행. 단락 전체. 괄호 안에 괄호와 세미콜론이 겹친 날짜별 목록이라 한 번에 읽히지 않았다. "the explorer cadence"는 112행의 `explore_every`와 같은 것인지 나중에야 맞춰졌다.
20. 89행. "Mathlib when the proofs the sessions write will need it, which is the user's judgment at setup." Mathlib을 써 본 적이 없는 나로서는 무엇을 보고 판단해야 하는지 기준이 없다. Lean 자체가 필수인지(형식화를 원하지 않아도 필요한지)도 이 문장으로는 확정되지 않는다.
21. 89행. "an instance's `settings.json` names the tool servers its sessions may use" 필드 이름도 예시도 없다.
22. 112행. "an organizer after four research publications, and up to three reconsideration turns before a session may end." 앞의 두 기본값에는 필드 이름(`max_sessions`, `launch_interval`)이 있는데 이 둘에는 없다.
23. 114~126행. Claude 전용 예시에서 최상위 `models`가 모든 역할의 기본값인지, 생산 역할만의 기본값인지 알 수 없다. 모든 역할에 같은 값을 주는데 peer와 review를 `roles`에 따로 적은 이유도 설명되지 않는다. formalizer, explorer, organizer가 어느 목록을 쓰는지도 없다.
24. 128행. "All sessions request a one-million-token context from their CLI; whether the account provides it is between you and the provider." 내 계정이 이를 제공하지 않으면 실행이 실패하는지, 줄어든 컨텍스트로 계속 도는지 알 수 없다.
25. 130행. "Create an instance at a new path ... Then start it:" 이어지는 코드에 `init`과 `start`가 함께 있다. "Create"가 디렉터리를 직접 만들라는 뜻인지, `init`을 가리키는지 두 가지로 읽힌다.
26. 149행. "`stop` / `resume` | Stop or resume the launching of new sessions" 명령 이름이 `stop`인데 runner를 멈추지 않는다. "`resume` also needs `start` if the runner process has ended."는 resume 뒤에 start를 쳐야 하는지, start 뒤에 resume을 쳐야 하는지 순서가 불분명하다.
27. 150행. "after attempts have reported that every unresolved node is occupied, a report that otherwise pauses attempt launches." 이 보고가 attempt 띄우기를 멈춘다는 사실이 이 표 칸에서 처음 나온다. 나는 이 명령을 언제 쳐야 하는지 status 출력에서 어떻게 알아보는지 모른다.

## 6. uncertainties

1. `claude/opus`가 어느 모델 버전으로 풀리는지 모른다. 57행의 "Claude Opus 5.5"라고 추정했다. Claude Code에 `xhigh` effort가 있다는 점은 글(112행)을 그대로 믿었다.
2. "Claude Code is launched with permission prompts disabled"(91행)를 Claude Code의 권한 우회 플래그로 띄우는 것으로 해석했다. 외부 지식이다.
3. 114~126행 예시의 최상위 `models`를 모든 역할의 기본값으로, `roles`를 역할별 덮어쓰기로 해석했다. 글만으로는 확정할 수 없다.
4. 130행의 "Create an instance"는 `init`이 디렉터리를 만드는 것으로 해석했다. 직접 디렉터리를 만들어야 하는지는 확정하지 못했다.
5. `init`이 `root.md`와 `settings.json`을 인스턴스 안으로 복사한다고 추정했다. 13행에 인스턴스가 `root.md`와 `settings.json`을 가진다고 되어 있기 때문이다.
6. `stop`이 attempt와 explorer뿐 아니라 peer와 review의 launch도 막는지 확정하지 못했다. 155행 "its retained work is still processed"와 어떻게 맞물리는지 모른다.
7. 세션 ID는 `status` 출력의 "sessions"(148행)에서 얻는 것으로 추정했다.
8. runner를 강제로 끝낼 때 session host가 함께 끝나는지 모른다.
9. Lean은 `settings.json`의 필수 필드로 보인다(101행 "This minimal file names the Lean installation"). 그래서 Lean 없이는 시작할 수 없다고 추정했지만 확정은 아니다.
10. Mathlib 설정의 실제 모습(`["C:/.../lake.exe", "env", "lean"]`과 `lean.cwd`)은 외부 지식으로 메웠다. 글은 operating guide로 넘긴다.
11. 1M 컨텍스트 요청이 Claude Code에서 특정 모델 변형이나 플래그를 뜻하는지, 계정이 지원하지 않을 때 무슨 일이 생기는지는 외부 지식으로도 확정하지 못했다.
12. 재고 요청(23행)이 같은 대화를 이어 가는 것이므로 추가 사용량이 든다고 추정했다. 글에는 비용 언급이 없다.
