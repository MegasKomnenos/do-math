## 2. understanding

### (a) 이 시스템이 무엇을 하며, 돌리면 내 기계에서 무엇이 실행되는가(권한 포함)

do-math는 수학 명제 하나를 받아, 서로를 기억하지 못하는 새 AI 대화를 많이 띄워 연구시키는 프로그램이다. 내 기계에서는 Python 프로그램인 runner가 분리된(detached) 프로세스로 떠서, 이미 로그인된 Claude Code나 Codex CLI를 자식 프로세스로 한 번에 기본 여덟 개까지 띄운다. 세션마다 그 세션이 살아 있는 동안 함께 사는 session host 프로세스가 하나씩 붙고, Lean 컴파일은 인스턴스마다 하나인 Lean broker 프로세스가 맡는다. 세션은 내 계정 권한으로 파일과 명령에 접근하며 사람의 승인 없이 돈다. Claude Code는 권한 프롬프트가 꺼진 채로, Codex는 approval policy never, sandbox full access로 실행된다. 작업 공간 경계는 지시문일 뿐 OS 샌드박스가 아니다. 세션이 읽은 자료는 모델 제공자에게 전송된다. 세션은 내 개인 지시문·hook·memory를 물려받지 않는다. 모델 API를 직접 부르지 않고 CLI를 거치므로, 요금은 그 CLI에 설정된 방식으로 청구된다.
- 39행: "The **runner** launches all of these as fresh CLI conversations under the user's existing authentication, ... with eight concurrent sessions by default"
- 39행: "It compiles all Lean through one **Lean broker** per instance, a separate process"
- 23행: "A separate process, the **session host**, which the runner started with the session and which lives as long as the session does"
- 93행: "Sessions run unattended with file and command access under your account: Claude Code is launched with permission prompts disabled, and Codex with its approval policy set to never and its sandbox set to full access. Their workspace boundaries are instructions, not an operating-system sandbox, and their model providers receive the material they read"
- 91행: "it launches them as processes and does not call model APIs directly, so usage is billed or metered however those CLIs are configured, and do-math adds no accounting of its own."
- 39행: "Sessions inherit none of the user's personal instructions, hooks or memories"

### (b) 시작하려면 무엇을 준비하고 어떤 순서로 무엇을 치는가

준비물은 Python 3.12 이상, Git, 설치·로그인된 Codex CLI나 Claude Code CLI(또는 둘 다), Lean 4이고, 문제에 따라 Mathlib가 필요하다. OS는 Windows에서 검증되었고 Linux는 실검증 전이며 macOS는 지원하지 않는다. 저장소를 clone한다. 쉬운 길은 저장소 안에서 Claude Code나 Codex를 띄우고 do-math 스킬에 명제 연구 시작을 요청하는 것이며, 그 대화(operator)가 명제와 설정을 준비하고 runner를 띄운다. 수동 길은 (1) 정확한 명제를 담은 UTF-8 root.md 작성, (2) Lean 실행 파일 경로를 담은 settings.json 작성(Mathlib을 쓰면 lean.command를 Lake 실행 파일 + env + lean으로, lean.cwd를 Mathlib 프로젝트 디렉터리로), (3) 저장소 밖 새 경로나 .skill-workspace/ 아래에 `runner.py init <instance> --root ... --settings ...`, (4) 상시 조건이 있으면 `input --file <file>`, (5) `start`, (6) `status` 순서다. Claude Code만 있으면 설정에 그 모델만 나열해야 한다.
- 91행: "The runtime needs Python 3.12 or later and Git, and uses only Python's standard library. It needs the Codex CLI, the Claude Code CLI, or both, installed and logged in"
- 95행: "From Claude Code or Codex started in the repository, ask the do-math skill to start research on a proposition."
- 114행: "To use Mathlib, set `lean.command` to your Lake executable followed by `env` and `lean`, and `lean.cwd` to the Mathlib project directory"
- 121-123행: "python "$skill/runtime/runner.py" init $instance --root C:/research-input/root.md --settings C:/research-input/settings.json" / "... start $instance" / "... status $instance"
- 126행: "Standing conditions, such as the language of the records or limits on methods, go in a file submitted with `input --file <file>` before `start`."
- 114행: "If only one CLI is installed, list only its models."

### (c) 돌아가는 동안 할 수 있는 일, 멈추기·끝내기·되살리기, 비용·시간의 상한

돌아가는 동안 `status`로 상태를 보고, `input`으로 이후 세션에 정보를 주고, `questions`로 질문을 올리고, `review`·`organize`를 요청하고, `kill-session`으로 특정 세션을 끝낼 수 있다. `stop`은 새 세션 띄우기만 멈추고 runner와 진행 중인 세션은 그대로 둔다. 완전히 끝내려면 `stop`, 돌고 있는 세션마다 `kill-session`, 그다음 runner/process.json에 적힌 runner 프로세스를 직접 종료한다. Lean broker는 일이 끝나면 스스로 끝나며 같은 방식으로 끝낼 수도 있다. 크래시나 재부팅 뒤에는 `start`가 기존 세션과 미완 발행을 복구한다. 사용량 한도로 거절되면 그 제공자로의 실행은 한도가 풀릴 때까지 막히고 대체 모델로 넘어간다. 상한은 없다. 시간, 세션 수, 사용량 어느 것에도 cap이 없고, 루트가 형식적으로 결론 나 남은 일이 처리되거나 내가 끝낼 때만 끝난다. 시도(attempt) 하나에도 시간 제한이 없다. 첫 실행은 7일 남짓에 1,209개 세션을 띄웠고 아직 진행 중이다.
- 93행: "A run has no cap on time, on the number of sessions, or on usage; it ends when the root is formally settled and the remaining work has been processed, or when you end it as described below."
- 135행: "`stop` / `resume` | Stop or resume the launching of new sessions; the runner stays alive and running sessions continue."
- 145행: "To end a run before the root is settled, use `stop`, then `kill-session` for each running session, then end the runner process identified in the instance's `runner/process.json`."
- 132행: "Launch the detached runner when none is alive, including after a crash or reboot; existing sessions and unfinished publications are recovered."
- 147행: "When a provider refuses a launch because of a usage limit, launches through that provider are blocked until the limit resets"
- 23행: "An attempt has no time cap."
- 59행: "the runner had launched 1,209 sessions (302 attempts, 92 explorers, 12 formalizers, 367 peers, 356 reviews, 80 organizers)"

### (d) 결과는 어디서 어떻게 읽고, 어느 정도 믿을 수 있는가

결과는 인스턴스의 knowledge/ 디렉터리에 쌓이고 발행마다 갱신된다. 입구는 index.md, 각 명제(node)의 상태와 증명·관계는 frontier.md, 개별 기록은 records/<id>/ 아래 exposition.md(수학 서술), record.json(주장 목록), review/feedback.md(검토 설명), review/assessment.json(주장별 판정)이다. 기계 판독용으로 state.json이 있다. 세션 대화와 작업 파일은 knowledge/가 아닌 sessions/에 있다. 신뢰 수준은 둘로 나뉜다. "informally proved"는 AI 검토 세션이 일반 수학 언어의 증명을 받아들였다는 뜻일 뿐 사람도 증명 검사기도 확인하지 않았다. "formally proved"는 검토 세션이 Lean 증명을 broker로 다시 컴파일하고, 공리 목록을 확인하고, 명제를 노드와 대조한 뒤에만 붙는다. 관계를 거쳐 유도된 증명은 전제가 모두 Lean으로 증명되어도 informal이다. 부동소수점 계산에 기댄 단계는 기록에 표시된다. 첫 실행의 사례(63행)는 AI 검토가 수치로만 확인한 성질을 증명된 것처럼 통과시킨 일이 있었음을 보여 주므로, informal 결론은 그 자체로 믿을 근거가 아니라 다시 확인할 출발점으로 읽힌다.
- 83행: "Its entry point is `index.md`, which lists records the organizer selected as shared context for new sessions"
- 87행: "`exposition.md` is the mathematical account. ... `review/feedback.md` is its full explanation."
- 45행: ""Informal" here means that the argument is written in ordinary mathematical language and was checked by an AI review session reading the candidate against the originals, not by a person and not by a proof checker."
- 49행: "A node is **formally proved** only after a Lean proof has passed three checks that the review session carries out itself"
- 45행: "A proof that the frontier derives through relations is always informal, even when every premise has a Lean proof"
- 128행: "`knowledge/` is updated with every publication."

## 3. difficulties

1. 3행 "a repository of records, each holding mathematics that one session produced, a second session developed into an account for others, and a third session assessed, kept unchanged once published with the assessment beside it." — 관계절 셋과 분사구 하나가 한 명사에 매달려 있어 두 번 읽었다. "kept unchanged once published with the assessment beside it"이 records를 받는지 mathematics를 받는지 처음엔 갈렸다.
2. 7행 "every record and every relation on two routes from proved statements to the root" — "route", "relation", "root"가 이 시점에 정의되지 않았다(root는 13행, relation은 15행, route는 61행).
3. 7행 "the instance has been asked to prove them" — "instance"가 무엇인지 13행 전까지 모른다. 사람인지 프로그램인지 처음엔 알 수 없었다.
4. 7행 "One necessary condition of the root does have a Lean proof." — 이 문장이 왜 의미 있는지(그것이 루트를 증명하지 않는다는 점) 31행·65행을 읽어야 알 수 있다.
5. 19행 "It stays occupied until the work has been developed into a record and reviewed" — "It"이 section인지 node인지, "occupied"가 lease와 어떻게 다른지 다시 읽었다. lease(선택하는 동안)와 occupancy(등록 후 검토까지)가 두 단계라는 것을 재구성해야 했다.
6. 23행 "When its conversation ends, the runner does not close the session at once." — "conversation ends"가 CLI 프로세스 종료인지, 모델이 응답을 마친 것인지 두 가지로 읽힌다. 바로 뒤 "resumes the same conversation"과 합쳐 보면 후자 같지만 확정되지 않는다.
7. 23행 "An attempt has no time cap." — attempt에만 해당하는지 다른 역할에도 해당하는지 알 수 없다.
8. 33행 "through a runner command issued by the operator" — "operator"는 59행에서야 정의된다. 33행에서는 사람인지 AI인지 모른다.
9. 35행 "One is an essay on what mathematicians have sought in their work, which the user and an operator session wrote ... The other describes the writing the user prefers" — 여기서 "the user"는 3행 정의(실행을 시작한 사람)로는 나 자신인데, 내용은 이 저장소 저자의 글이다. 내가 돌려도 이 두 문서가 내 세션에 들어가는지 두 가지로 읽힌다.
10. 39행 "in the priority review, peer, formalizer, organizer, exploration, attempt" — 쉼표 나열이 우선순위 순서라는 것을 파악하는 데 다시 읽었다. 앞에서는 "explorer"였는데 여기서는 "exploration"이다.
11. 39행 "schedules compiles under shared memory and thread budgets and keeps their results across tool time-outs" — "shared memory"가 공유 메모리(IPC)인지 여러 컴파일이 나누어 쓰는 메모리 예산인지 두 가지로 읽힌다. "tool time-outs"가 어떤 도구의 시간 초과인지 정의가 없다.
12. 39행 "everything they read is supplied by do-math and saved at launch" — 어디에 저장되는지 없다.
13. 47행 "binary64 floating point with an error model assumed in advance, in which margins added to the results are trusted to cover the rounding error" — "error model"이 정의 없이 쓰였다. 맥락으로 추측은 된다.
14. 59행 "some pipelines, as a producing session together with its peer and review are called, were still in progress" — 용어 정의가 사용 뒤에 삽입구로 들어가 있어 문장을 다시 읽었다.
15. 61행 전체 — 한 문단에 두 경로, 네 경우, 조건부 로그오목성, 기록 ID 둘, 산술 종류 셋이 이어진다. 실행 결정에 필요한 정보는 아니지만 따라가려면 여러 번 읽어야 했다. "a descent just left of the middle followed by an ascent in the right half" 등 네 경우의 경계가 문장만으로는 정확히 잡히지 않는다.
16. 63행 "an envelope function to be non-increasing in one variable and six auxiliary pieces to be monotone in another" — "envelope function", "auxiliary pieces", "Theorem W"가 정의 없이 쓰였다.
17. 63행 "through a standing input" — 3행의 "standing conditions"와 같은 것인지 다시 확인해야 했다. 67행에서야 "Standing inputs"가 풀린다.
18. 85행 "a question the user placed directly shows an operator publication as its source" — "operator publication"이 정의되지 않았다. 33행은 "runner command issued by the operator"라 했는데 여기서는 "the user placed directly"이고, 87행은 "the questions the user published"이다. 누가 올리는 것인지 셋이 서로 다르게 말한다.
19. 91행 "It needs Lean 4, with Mathlib when the problem requires it." — 문제가 Mathlib을 요구하는지 누가(나, operator, 세션) 판단하는지 알 수 없다.
20. 91행 "are optional and are configured explicitly per instance" — 어떤 방법으로 설정하는지 이 글에 없다("described below"라 했지만 165행도 설정법을 주지 않는다).
21. 103-112행 settings.json 예시의 "version_command" — 용도가 설명되지 않았다.
22. 114행 "a request for one exploration each time an attempt is launched (the request is a flag; it launches an explorer when a question is free and the interval has passed)" — 세 번 읽었다. "request is a flag"가 설정 플래그인지 내부 상태 플래그인지, "a question is free"가 점유되지 않은 질문을 뜻하는지 확정하지 못했다.
23. 114행 "Producing roles prefer Codex `gpt-6.1-sol` at effort `xhigh` and fall back to Claude `opus` at `xhigh`" — "effort"가 정의되지 않았다. Claude Code만 가진 내가 최소 settings.json을 그대로 쓰면 첫 선택인 Codex가 실패하고 fallback으로 가는지, 아니면 설정을 바꿔야만 하는지 두 가지로 읽힌다. 바로 뒤 "list only its models"는 후자를 시사하지만 필드 이름이 없다.
24. 116행 "Create an instance at a new path outside this repository, or under its `.skill-workspace/` directory" — "Create"가 디렉터리를 미리 만들라는 것인지 `init`이 만든다는 것인지 다시 읽었다. 코드 블록을 보고 `init`으로 추정했다.
25. 121-123행과 126행 — 코드 블록은 init 바로 뒤에 start를 두는데, 126행은 input을 start 전에 넣으라 한다. 순서를 머릿속에서 다시 조립해야 했다.
26. 128행 "waits for its readiness record" — "readiness record"가 정의되지 않았다.
27. 135행 `stop` — 이름과 달리 runner도 세션도 멈추지 않는다. 145행을 읽고서야 완전 종료가 세 단계임을 알았다. "`resume` also needs `start` if the runner process has ended"도 다시 읽었다.
28. 136행 "Request one reassessment of work availability after attempts have reported that every unresolved node is occupied, which otherwise pauses attempt launches." — "which"의 선행사가 보고(reported) 사실인지 전체 상황인지 갈리며, "work availability"가 정의되지 않았다.
29. 145행 "then end the runner process identified in the instance's `runner/process.json`" / "it can be ended the same way" — "end"하는 방법(명령)이 없다. OS 수준 kill로 추정했다.
30. 147행 "Formal settlement of the root stops new attempts and explorations; existing sessions finish, formalizations and organizations still launch" — 형식 결론 뒤에도 무엇이 계속 돌아 비용이 드는지 다시 읽었다.

## 4. missing

1. 비용·사용량 규모의 추정치. 첫 실행의 세션 수는 있으나 세션당 토큰, 하루 사용량, 작은 예제(n + 0 = n)에 드는 시간·사용량이 없다. 상한이 없다고 했으므로 시작 전에 규모를 가늠할 다른 수단이 필요하다.
2. 사용량·시간에 상한을 거는 방법. 93행은 상한이 없다고만 한다. 동시성 수를 바꾸는 settings 필드 이름도 이 글에는 없다(59행은 사용자가 바꿨다고만 한다). 비용을 통제하려면 필요하다.
3. Claude Code만 가진 경우의 정확한 settings.json. "list only its models"(114행)의 필드 이름과 형식이 없다. 기본값의 첫 선택이 Codex이므로 Claude 단독 사용자는 이것 없이 시작할 수 없거나 결과가 불확실하다.
4. runner 프로세스를 끝내는 구체적 명령(Windows·Linux 각각). 145행은 process.json에서 식별하라고만 한다. 비상 정지 절차로 필요하다.
5. 세션 권한을 줄이거나 격리하는 권장 방법(별도 계정, VM, 컨테이너 등). 권한 프롬프트 없이 내 계정 전체 권한으로 돈다는 점(93행)만 있다. 실행 여부 결정의 핵심이다.
6. 네트워크 접근 범위. 세션이 웹에 접근하는지, 패키지를 설치하는지 알 수 없다.
7. 디스크·메모리 사용량. sessions/에 대화 전문이 남고 Git 저장소가 커지며 Lean broker가 메모리 예산을 쓴다는 정도만 있다. 기본 메모리 예산 값과 디스크 증가량이 없다.
8. Mathlib 준비 절차와 Lean·Mathlib 버전 요건. Mathlib 경험이 없는 독자에게는 "the Mathlib project directory"(114행)를 어떻게 만들고 빌드해 두어야 하는지가 필요하다.
9. `input --file`과 `questions --file`의 파일 형식. 평문인지 정해진 구조인지 없다.

## 6. uncertainties

1. session host가 세션마다 하나씩 따로 뜨는 프로세스라고 읽었다(23행). 그러면 동시 여덟 세션이면 CLI 여덟 + host 여덟 + runner + broker가 된다. 글은 프로세스 수를 직접 말하지 않는다.
2. "When its conversation ends"(23행)를 모델이 턴을 끝내고 CLI가 종료한 상황으로 해석했다. 확정하지 못했다.
3. 145행의 "end the runner process"를 process.json의 PID로 OS 수준 종료(Windows에서 Stop-Process 등)하는 것으로 해석했다. 이는 외부 지식으로 메운 것이다. runner를 끝내면 session host나 CLI 자식 프로세스가 함께 끝나는지는 알 수 없다.
4. 요금이 "however those CLIs are configured"(91행)로 청구된다는 것을, 구독 로그인이면 구독 한도 안에서, API 키면 종량 과금으로 해석했다. 외부 지식이다.
5. Claude Code만 있고 최소 settings.json을 쓰면 Codex 실패 후 Claude로 fallback될 수도 있다고 보았지만, 114행 "list only its models"는 설정 변경이 필요하다는 뜻으로도 읽힌다. 확정하지 못했다.
6. "Claude `opus`"(114행)를 Claude Code의 opus 별칭, 곧 그 시점의 최신 Opus 모델로 해석했다. 외부 지식이다.
7. "ask the do-math skill"(95행)을 Codex에서 하는 방법이 Claude Code와 같다고 가정했다. .agents/skills 미러가 Codex에서 자동 인식되는지는 글에 없다.
8. Zenodo 발행은 저자가 수동으로 한 것이며 runner가 외부로 자동 발행하지 않는다고 추정했다. 글은 이를 명시하지 않는다.
9. 35행의 두 문서가 다른 사용자의 인스턴스에도 기본으로 주어지는지 확정하지 못했다. "the user"의 정의(3행)를 따르면 각 사용자 자신의 것이어야 하나 내용은 저자 고유의 것이다.
