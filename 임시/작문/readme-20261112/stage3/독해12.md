읽은 문서: `README.md`, `docs/do-math/first-run-parking-unimodality.md`(아래 "첫 운전 문서"), `docs/do-math/running.md`(아래 "운전 안내"), `zenodo-description.md`의 "## Description" 영어 본문(아래 "Zenodo"). Zenodo는 저장소를 보지 않은 독자의 눈으로 따로 읽었다. 문서는 고치지 않았다.

## 1. 이해한 것

1. **시스템의 정체.** do-math는 서로 대화하지 않는 AI 세션 여럿이 파일만 주고받으며 하나의 수학 명제를 증명하거나 반증하려는 시스템이다. 세션은 매번 새 Claude Code 또는 Codex 대화다. 사용자 대신 "operator"라는 AI 대화가 운전을 차리고, "runner"라는 프로그램이 세션을 띄운다.
   - "The sessions have no contact with one another. Each is a new Claude Code or Codex conversation that knows nothing of the others; what a session produces is handed on as files" (README)
   - "An AI conversation called the operator sets up the run from the user's statement and settings and operates it on the user's behalf. A program called the runner then launches sessions as the work requires" (README)

2. **세 단계로 만들어지는 기록.** 생산 세션(attempt, explorer, formalizer)이 일하고 작업 파일을 남긴다. peer가 그것을 다른 세션이 읽을 해설과 주장 목록(record candidate)으로 만든다. review는 후보를 생산 세션의 파일과 양방향으로 대조해 주장마다 supported/unsupported/undetermined를 매긴다. 게재 여부는 따로 정한다.
   - "Every record is produced in three stages, each by a different session." (README)
   - "It gives each claim one of three statuses." / "Separately, the review decides whether the record has enough useful content to be published at all" (README)

3. **기록은 바뀌지 않는다. 뒤의 판정은 finding으로 붙는다.**
   - "The record never changes afterwards. If a later review session ... finds a defect in it or confirms a result, it issues a **finding** on the record" (README)

4. **노드와 관계, 그리고 전파.** 연구 대상 명제는 노드이고, 루트(root.md)가 첫 노드다. 새 노드는 리뷰를 거친 함의(relation)로만 들어온다. runner는 관계를 명제논리가 허용하는 모든 방향으로 적용한다(대우 포함). 한 노드와 그 부정이 둘 다 지지되면 contested가 된다.
   - "Every node other than the root enters through a **relation**, a reviewed implication between nodes." (README)
   - "The runner applies each accepted relation in every direction that propositional logic allows" (README)

5. **일의 선택은 세션 스스로 한다.** attempt는 frontier·index·board를 읽고 노드의 section을 골라 등록한다. 고르는 동안 lease를 쥔다. 겹침 판단은 프로그램이 아니라 세션의 수학적 판단에 맡긴다.
   - "An attempt is handed no node and no task." / "Sessions coordinate through information rather than enforcement." (README)

6. **확립의 세 수준.**
   - 비형식 증명: AI 리뷰가 수락했거나 관계로 도출된 증명.
   - 컴퓨터 보조 단계: 정확·구간 산술, 또는 사전에 가정한 오차 모형의 binary64.
   - 형식 증명: 리뷰가 재컴파일·공리 감사·명제 대조를 마친 Lean 증명.

   컴퓨터 보조가 섞인 증명과 관계로 도출된 증명은 늘 비형식이다. 운전은 루트가 형식 증명되어야만 완료된다.
   - "A proof that the frontier derives through relations is always informal, even when every premise has a Lean proof" (README)
   - "The run is complete only when the root is proved or refuted at this level." (README)

7. **concern과 finding.** concern은 상태를 바로 바꾸지 않고 표시만 한다. comprehensive review의 finding이 주장을 철회하면 그 주장을 거친 결과가 전부 빠진다.
   - "A pending concern changes no status by itself." (README)

8. **첫 운전의 문제.** Celano 외의 추측 6.5다. 길이 n 주차함수의 최대 변위 분포 b(n,0),…,b(n,n−1)가 모든 n에서 단봉이라는 명제이고, 끝값은 n!과 nⁿ⁻²이다.
   - "The root states that, for every n ≥ 1, the sequence b(n, 0), b(n, 1), …, b(n, n−1) is unimodal" (첫 운전 문서)

9. **첫 운전의 결과.** 11월 11일 16:14(한국 시각)에 루트가 "informally proved"가 되었다. 경로는 둘이다.
   - 첫째 경로는 "하강 뒤 상승"을 중간 지수 m=⌈n/2⌉ 기준 네 경우로 나눠 모두 배제한다.
   - 둘째 경로는 "하강하는 자리에서만의 로그 오목성"이 단봉성을 함의함을 보이고, 그것을 중간 양쪽에서 증명한다.

   두 경로는 "중간 아래에서는 감소하지 않는다"는 한 명제를 함께 지나므로 독립 확인이 아니다. 마지막으로 열려 있던 전제는 r5909c9e7이 증명했다.
   - "The two chains are not independent confirmations; both pass through one statement" (README)
   - "Since all the counts are positive, it follows from this property that once the sequence has started to decrease it cannot rise again, which is unimodality." (첫 운전 문서. 직접 확인했다. b_{ℓ+1}² ≥ b_ℓ b_{ℓ+2}와 b_ℓ > b_{ℓ+1}에서 b_{ℓ+2} < b_{ℓ+1}이 나온다.)
   - 네 경우가 모든 실패를 덮는다는 주장도 직접 확인했다. 하강 지수 d가 m 이상이거나, m−1이거나, m−1 미만이면서 상승 지수 a가 m 이상이거나, 둘 다 m 미만이면 네 경우 가운데 하나다.

10. **믿을 수 있는 한도.** 사람 심사는 없다. 여러 단계가 사전 가정 오차 모형의 binary64 계산에 기대고, n ≤ 20000 유한 검증에도 기댄다. 루트의 Lean 증명은 없고, 11월 9일부터 형식화가 멈춰 있다. Lean 증명이 있는 노드는 루트의 필요조건 하나뿐이라, 그 증명은 루트를 정하지 못한다.
    - "a reader who does not accept those models should treat the root as unproved" (README)
    - "The node is a necessary condition of the root: ... so its refutation would have refuted the root, while its proof leaves the root open." (README)

11. **개입.** 사용자와 operator는 standing input(이후 세션에 전달되는 지시), 설정 변경, 소프트웨어 변경으로 여러 번 개입했다. 12일 04:54에는 외부 AI 세션이 만든 수학 자료를 넣었다. 12일 14:15에는 r030ffaeb가 기대는 두 단조성을 최우선으로 증명하라고 지시했다.
    - "Give priority over all other work to proving two monotonicity properties that a table used by record r030ffaeb relies on and that its review had accepted on numerical evidence" (첫 운전 문서)

12. **공개 증거와 검증 경로.** `knowledge/`가 Zenodo에 판본별로 올라 있다. v1은 11일 00:19, v2는 12일 01:52(300건), v3는 12일 23:25(340건) 스냅숏이다. index.md → frontier.md → r5909c9e7과 그 review/feedback.md 순으로 따라가라고 한다. 세션의 작업 파일과 대화, standing input은 공개본에 없다.
    - "The producing sessions' conversations and working files are not in `knowledge/`" (README)

13. **직접 돌리기.** Python 3.12 이상, Git, Codex/Claude Code CLI 가운데 하나 이상이 필요하고, Lean 4는 어떤 경우에도 필요하다. 세션은 권한 확인 없이 사용자 계정으로 파일과 명령에 접근하고 웹 검색도 할 수 있으며, 시간·세션 수·사용량에 상한이 없다. 시작은 `init` → (`input --file`) → `start` → `status` 순서다. 끝낼 때는 `stop` → 세션마다 `kill-session` → runner 프로세스 종료 순서를 따른다.
    - "Their workspace boundaries are instructions, not an operating-system sandbox" (운전 안내)
    - "To end a run before the root is formally settled, take three steps in order." (운전 안내)

14. **Zenodo만 본 독자의 이해.** 이 보관본은 한 인스턴스의 지식 기반 사본이고, 모든 평가는 AI가 했다. "informally proved"는 시스템 고유 용어로, 낱말이 주는 인상보다 약한 뜻이다. 형식 증명은 없다. 읽는 순서는 index.md, frontier.md, records/다.
    - "The term is do-math's own, and it means less than the words may suggest" (Zenodo)

### [A] 정의보다 먼저 쓰인 용어

A1. README 리드. "what survives review is published as a record in a shared knowledge base for every later session to read."
"review"와 "record"가 이 시스템 고유의 뜻으로 처음 쓰였다. review는 다음 문단에서 세션으로 설명된다. record는 한참 뒤 "Peer, review and the published record"에서야 굵게 정의된다. 같은 문서 뒤에서 나온다.

A2. README 역할 표. "| attempt | The knowledge base, from which it chooses a node to settle | Its retained work on that node |"
"retained work"가 표와 도식에 여러 번 나온다. 정의("What a producing session leaves behind is its **retained work**")는 도식 뒤에 온다. 같은 문서 뒤에서 나온다.

A3. README 역할 표. "| review | ... | Its assessment and feedback: claim statuses, a publication decision and any concerns |" / "| organizer | ... | Modules of records, the choice of shared context, glossary decisions, merges of nodes or questions found to be the same |"
"claim statuses", "concerns", "shared context", "modules", "questions"가 모두 뒤에서야 설명된다. concern은 "What counts as established" 절의 끝에서야 나온다. 같은 문서 뒤에서 나온다.

A4. README 도식. "KB[\"knowledge base: frontier, index, board, records\"]"
frontier, index, board가 도식에 먼저 나온다. 그 뜻은 다음 소절 "The choice of work"에서 나온다. 같은 문서 뒤에서 나온다.

A5. README "Two documents on research and writing". "both are files in the skill's reference folder that a user can edit."
"the skill"이 무엇인지는 "Quick start"("the do-math skill, a folder of instructions that these CLIs load")에 가서야 나온다. 같은 문서 뒤에서 나온다.

A6. README "Concerns and findings". "the outcomes derived from it keep their states but are marked as resting on a questioned claim."
"outcome"이 시스템 용어처럼 쓰인다. README에 "A withdrawal removes every outcome derived through the claim", "outcomes bearing on the root"가 있고, 첫 운전 문서에 "outcomes that can reach the root"가 있다. 그런데 정의는 어디에도 없다. proof/refutation을 가리키는지 노드의 상태를 가리키는지 알 수 없다. 어디에도 없음.

A7. README "The end of a session". "The same reconsideration applies to explorers that have begun research" / "if the session had begun research, its retained work goes on to a peer and a review"
"begun research"는 peer가 붙느냐를 가르는 기준이다. 그런데 무엇이 연구의 시작인지(section 등록인지, question을 잡은 것인지) 정의되지 않는다. 첫 운전 문서("a producing session that ends without having begun research gets no peer")와 운전 안내("if it had begun research")도 정의 없이 쓴다. 어디에도 없음.

A8. README 첫 운전 절. "The record that proved it, r5909c9e7, depends on computer-assisted inputs from earlier records"
r 뒤에 16진 여덟 자리를 붙이는 표기의 설명("Records are cited here by the letter r and the first eight hexadecimal digits of their identifiers")은 두 문단 뒤에 온다. 같은 문서 뒤에서 나온다.

A9. README 리드. "The first research run of this implementation began on 5 November 2026."
"this implementation"은 이전 구현이 있었음을 전제한다. 이전 구현과 이전 인스턴스 이야기는 "Two documents on research and writing"에 가서야 나온다. 같은 문서 뒤에서 나온다.

A10. 첫 운전 문서. "The last open premise on the routes was a single node, pair-beats-capped-threshold. ... in outline, it is an inequality between two counts of configurations"
노드에 이런 이름(slug)이 붙는다는 설명이 어느 문서에도 없다. "configurations"와 "capped threshold"가 무엇인지도 없다. frontier를 열어야만 안다. 다른 문서(공개 증거)를 봐야 안다.

"installed copy"가 무엇인지(인스턴스 안에 스킬 사본을 깔아 두는지) README에 없다. README가 말하는 사본은 Codex용 "generated mirror"뿐이다. 어디에도 없음.

A15. README "Language, roadmap, citation and license". "The do-math operator and role guides, the file contracts, the runtime output and this README are in English."
"file contracts"는 어디에도 설명이 없다. 어디에도 없음.

A16. README "Quick start". "$instance = 'C:/research/add-zero'"
"add-zero"는 운전 안내의 예시 루트("n + 0 = n")에서 온 이름이다. README에는 그 예시가 없다. 다른 문서를 봐야 안다.

A17. Zenodo 첫 문단. "Every published record is the work of three sessions in turn." / "Records that pass this assessment are published in the instance's knowledge base"
Zenodo 독자에게 "record"는 설명 없이 나온다. "instance"는 같은 문단 뒤에서야 "one instance, that is, one run on one statement"로 풀린다. 같은 문서 뒤에서 나온다.

첫 문단은 셋째 세션을 "a third"로만 불렀다. "review session"이라는 이름은 여기서 처음 나온다. 뜻은 짐작되지만 이름이 붙은 적이 없다. 같은 문서 안에 없음(추론으로 메움).

A19. Zenodo 셋째 문단. "paused formalization on 9 November"
첫 문단은 "turn an already reviewed proof into a formal proof in Lean 4"라고만 했다. "formalization"이 그 일을 가리킨다는 것은 독자가 이어 붙여야 한다. 사소함.

### [B] 문서 안과 문서 사이의 순서

B1. README 리드에서 첫 운전 절로. "The two chains are not independent confirmations; both pass through one statement, as the first-run section explains."
README의 첫 운전 절은 "Both routes pass through one statement"라고 단언만 한다. 둘째 경로가 그 명제를 지나는 까닭(rdc276812의 동치)은 첫 운전 문서에만 있다. README는 리드의 약속을 자기 안에서 지키지 않는다.

B2. 운전 안내 "Starting by hand". "Standing inputs ... submit them after `init` and before `start` when they should reach every session."
이 안내는 `init`, `start`, `status`를 잇달아 실행하는 코드 블록 **뒤에** 온다. 위에서부터 따라 하는 독자는 standing input을 넣을 기회를 이미 지나친다. README Quick start에는 이 단계가 아예 없다.

B3. README와 첫 운전 문서의 판본 서술. "Version 2, ... was taken on 12 November at 01:52 ... Version 1, ... was taken on 11 November at 00:19 ... Version 3, ..."
판본을 2, 1, 3 순서로 적었다. 시간순도 최신순도 아니어서, 어느 것이 최신인지 다시 맞춰 봐야 했다.

B4. 첫 운전 문서 머리말과 "Limits". "as of 23:15 Korean time on 12 November 2026 ... The size table below is a snapshot from 17:45 Korean time that day."
표의 수치(17:45: 1,227 sessions, 337 records)와 끝의 수치(23:15: 1,237 sessions, 340 records, 426 commits)가 다르다. 23:15 수치가 표가 아니라 "Limits" 문단 안에 들어 있어서, 둘을 대조하려면 문서를 오가야 한다.

### [C] 같은 대상을 다른 낱말로, 다른 대상을 같은 낱말로

C1. 경로의 이름. README 리드 "along the two chains of implications", README 로드맵 문단 "the two chains of reasoning that led to the result", README 정의 "A **route** to the root is a path of relations", README 첫 운전 절 "Two routes lead to it."
한 대상이 chains of implications, chains of reasoning, routes 세 이름으로 불린다. 리드는 정의된 용어(route)를 쓰지 않았다. 셋을 이어 주는 것은 Zenodo의 "which the frontier calls routes"뿐이다.

C2. 후보의 이름. README "the result is a record candidate" / Zenodo "develops it into a draft record", "checks that draft against the first session's files", "against which the reviews checked the drafts"
README의 record candidate를 Zenodo는 draft record나 draft라고 부른다. 저장소로 넘어온 Zenodo 독자는 둘이 같은 것인지 확인해야 한다.

C3. 관계의 이름. Zenodo "the accepted implications to other nodes" / README "`frontier.md` gives ... the accepted relations with their premises and conclusions"
frontier.md 자체는 "relations"라고 쓰는 모양이다. Zenodo는 route에 대해서는 frontier의 용어를 알려 주면서 relation에 대해서는 알려 주지 않는다. 그래서 파일을 연 독자가 둘을 다시 맞춰야 한다.

C4. "section"이 두 대상을 가리킨다. README "the proof is either informal or formal, two levels of assurance that the section \"What counts as established\" defines" / "as the first-run section explains" / "the attempt picks a node and a **section** of it, an exact part of what the node asserts" / "each described the way a section of a survey would be"; 첫 운전 문서 "listed, with their status, in the first-run section of the README"
section이 문서의 절과, 노드의 일부라는 시스템 용어로 번갈아 쓰인다. 첫 운전 문서 머리말은 "section"을 README에서 정의된 용어로 꼽는다. 그러고는 끝에서 같은 낱말을 문서의 절이라는 뜻으로 쓴다.

C5. "review"가 여러 대상을 가리킨다. README "what survives review is published"(행위), "a third session, the review, checks"(세션), "the review's short assessment"(세션의 산출), "Every review was an AI session"(세션), "a **comprehensive review**"(다른 종류의 세션), `reviews/`(산출 디렉터리)
행위, 세션, 산출, 디렉터리를 한 낱말로 부른다. "review session"과 "review"가 섞여 쓰여서, 둘이 다른 것인지 한동안 의심했다.

C6. "open"의 두 뜻(Zenodo, README). Zenodo "version 1 a snapshot taken on 11 November at 00:19, while the conjecture was still open" / "its proof leaves the conjecture open"; README "One statement that the conjecture implies has a Lean proof, which leaves the conjecture itself open."
앞의 open은 아직 informally proved가 아니라는 뜻이다. 뒤의 open은 informally proved이지만 필요조건의 증명만으로는 정해지지 않는다는 뜻이다. Zenodo 독자는 v3 시점에 추측이 open인지 아닌지 헷갈린다. README는 v1 쪽을 "unresolved"라고 써서 두 뜻을 구별했지만 Zenodo는 구별하지 않았다.

C7. settled, resolved, unresolved. README "A node is **settled** once it or its negation, and not both, has been proved" / frontier 상태 "unresolved" / "a node that depended on it becomes unresolved again" / question "A question is resolved when a published record gives an account of it that the review judges to settle it."
노드는 settled가 되고, 그 반대 상태는 unresolved라고 부른다. question은 resolved가 되는데, 같은 문장에서 "settle it"이라고도 한다. 노드의 settled와 resolved가 같은 뜻인지, question의 "settle"이 노드의 settle과 같은 뜻인지 정해지지 않는다.

C8. occupied, holds, held. README "The section counts as occupied" / "registering a whole node while another session holds part of it" / "it holds the node's **lease**"; 운전 안내 "open and held by no session", "every unresolved node is occupied"; 첫 운전 문서 "a node another session occupies"
section 점유, 노드 점유, lease 보유, question 보유를 hold와 occupy가 엇갈려 가리킨다. 특히 "holds part of it"는 lease를 쥐었다는 뜻으로도, section을 점유했다는 뜻으로도 읽힌다.

C9. 형식화 대상 규칙의 이름. README "The runner requests it when a reviewed proof or refutation bears on the statement under research." / "Formalization is requested only for the proof of a node on a route or for the refutation of a necessary condition." / "The rule that limits formalization to outcomes bearing on the root"; 첫 운전 문서 "formalization limited to outcomes that can reach the root", "the rule that limits formalization to outcomes that can reach the root"
한 규칙이 bears on, on a route, bearing on, can reach로 불린다. 이 가운데 정확한 판(route 또는 necessary condition)은 하나뿐이다.

C10. shared context와 orientation. README "those selected as shared context for new sessions" / Zenodo "the records chosen as orientation for new sessions"
같은 목록을 두 문서가 다르게 부른다.

C11. finite verification과 certification. README "a finite verification that the root holds for all n ≤ 20000"; 첫 운전 문서 "the certification that the root holds for all n ≤ 20000 (record r15df76b5, 8 November)"
같은 계산의 이름이 문서마다 다르다. 게다가 README는 "certification"과 같은 뿌리의 낱말을 "no session certifies its own work"에서 리뷰의 판정을 가리키는 데 썼다.

C12. resume과 reconsider의 충돌. README "each time a CLI process exits it resumes the conversation and asks the session to reconsider"; 운전 안내 `stop` / `resume`(launch 재개), `reconsider-attempts`(attempt 하나를 띄움), `max_end_resumptions`
세션 호스트의 "resume"과 runner 명령 `resume`이 같은 낱말로 다른 일을 한다. 세션 종료의 "reconsider"와 명령 `reconsider-attempts`도 그렇다. 나는 `reconsider-attempts`가 종료 재고와 관련 있다고 한동안 오해했다.

C13. 생산 세션의 이름. README "producing session", "the producer", "the first session's files", "the producing roles"; Zenodo "the first session's files"
같은 대상을 네 가지로 부른다. 사소하지만, "producing roles"에 organizer가 드는지 헷갈렸다. 기본 모델 설명은 "for every role except peer and review"라고 해서 organizer를 포함하기 때문이다.

C14. 모델 목록. 운전 안내 "The `models` list is the ordered model preference for every role" / "both in the common list and in the two role entries"
`models` 목록이 뒤에서 "common list"로 바뀌어 불린다. 사소함.

C15. 사용자와 저자. README 표 "The user who started the run" / "This repository's author and an operator conversation wrote it" / "The instance was created on 5 November 2026 by the author of this repository"; Zenodo "the user, the person who started the run"
README만으로는 user와 author가 같은 사람인지 문장 사이에서 추론해야 한다. 첫 운전 문서("The user of this run is the author of this repository.")에 가서야 확정된다.

C16. 한눈 보기 "Evidence". "The knowledge base, that is, every published result with its review"
다른 자리는 모두 "record"라고 쓰는데 여기만 "published result"라고 쓴다. 게다가 지식 기반에는 기록 말고도 organizations, comprehensive reviews, questions가 들어 있으므로 "that is"로 놓은 등식도 정확하지 않다.

### [D] 영어 문장으로서의 어색함

D1. README "retained work" 정의. "What a producing session leaves behind is its **retained work**: everything in its own directory when it ends, which is the files it kept while it worked together with its conversation, which the runner saves there."
"which is the files"는 수가 맞지 않는다. "while it worked together with its conversation"은 "대화와 함께 일했다"로 먼저 읽히는 garden path다. which절 두 개가 겹쳐서, 무엇이 무엇을 꾸미는지 다시 읽어야 했다.

D2. README 한눈 보기와 리드의 되풀이. 표 "A system for autonomous mathematical research in which many AI sessions work together to prove or refute a single mathematical statement." / 리드 첫 문장 "do-math is a system for autonomous mathematical research in which many AI sessions work together to prove or refute a single mathematical statement."
같은 문장이 연달아 나온다. 기록 불변과 finding의 설명도 되풀이된다. 둘째 문단의 "it is never edited afterwards ... it issues a finding on that record"가 "Peer, review and the published record"의 "The record never changes afterwards ... it issues a **finding** on the record"에서 거의 그대로 다시 나온다.

D3. README 셋째 문단. "First, a session works on the problem: it tries to prove or refute a statement, to understand some feature of the problem, or to turn an already reviewed proof into a formal proof in Lean 4, a proof assistant, and it keeps all of its work, from definitions and computations to approaches that failed, in its own working files."
동격구 "a proof assistant," 바로 뒤에 "and it keeps"가 와서, 처음에는 or로 이은 나열의 넷째 항으로 읽힌다. 한 문장으로는 너무 길다.

D4. 시제. README "the user paused formalization on 9 November so that the sessions can finish the informal mathematics before formalization resumes"; 첫 운전 문서 "On 9 November the user paused all formalization so that the sessions can finish"; Zenodo 같은 표현. README 첫 운전 절 "so that the sessions could finish"
과거형 주절 뒤의 "can"이 어색하다. 같은 README 안에서도 can과 could가 갈린다.

D5. README 한눈 보기 "Formal proof". "One statement that the conjecture implies has a Lean proof, which leaves the conjecture itself open."
"which"의 선행사가 a Lean proof인지 앞 절 전체인지 모호하다. 또 "Lean 증명이 추측을 열어 둔다"는 말은 처음 읽으면 역설처럼 들린다.

D6. README 둘째 문단. "the candidate is published as a record with that assessment attached, and it is never edited afterwards."
"it"이 record인지 assessment인지 모호하다.

D7. README route 정의. "A **route** to the root is a path of relations, each feeding the next and some with several premises, along which a proof of a node contributes to settling the root; such a node is said to be on a route."
삽입구 둘, 관계절, 세미콜론 뒤의 정의가 한 문장에 다 들어 있어서 한 번에 읽히지 않는다.

D8. README frontier.md 설명. "`frontier.md` gives, for every node, its exact statement; its state, which is unresolved, informally proved or refuted, formally proved or refuted, or contested; the proofs that support that state, ...; and any pending concern."
세미콜론으로 나눈 목록 안에 쉼표 목록이 또 들어 있다. 한 문장으로는 지나치게 길다.

D9. README 주차함수 정의. "A **parking function** of length n describes n cars arriving one at a time ... A list of preferences under which every car finds a spot is a parking function"
첫 문장은 주차함수가 과정을 "describes"한다고 하고, 셋째 문장은 주차함수가 선호 목록"이다"라고 한다. 정의가 서로 다른 꼴로 두 번 나온다.

D10. README 둘째 경로. "whenever the sequence decreases from one term to the next, the square of the next term is at least the product of the terms on either side of it."
"the next"가 연달아 두 번 나온다. 둘 다 b(n,ℓ+1)을 가리키는데, 둘째 "the next term"은 감소 뒤의 또 다음 항으로도 읽힌다. 첫 운전 문서의 식을 보고서야 확정했다.

D11. 첫 운전 문서. "a property weaker than full log-concavity suffices for the root: log-concavity required only at a step at which the sequence decreases"
"log-concavity required only at ..."가 명사구인지 절인지 처음에 걸렸다.

D12. 첫 운전 문서. "The limit was later proved without any assumption, which the word unconditional in the theorem's name records."
"which ... records"의 구조가 무겁고, "later"의 기준점이 없다([F6] 참고).

D13. 첫 운전 문서 표. "do-math's default was changed at the same time so that peer and review prefer a model different from the one the producing roles prefer"
"prefer"가 한 문장 안에서 되풀이된다. 같은 내용을 본문은 "peer and review prefer a different model from the producing roles"라고 다르게 쓴다.

D14. 첫 운전 문서. "Standing inputs and settings changes were the user's decisions, carried out by the operator; software changes were made by the repository's author, who is also the user of this run; the row marked Operator action records something the operator did directly rather than through a standing input."
세미콜론으로 세 마디를 이은 한 문장이 길다. 마지막 마디는 표를 읽는 법이어서 앞의 두 마디와 성격도 다르다.

D15. 행위자를 숨긴 수동태. 첫 운전 문서 "they were then moved to Claude Opus 5.5 as their first choice" / "the rule that limits formalization to outcomes that can reach the root was added to the runner afterwards" / "the five formalizer pipelines then in progress were ended without peer or review"; README "Version 2 ... was taken on 12 November at 01:52"; Zenodo "Records that pass this assessment are published"
누가 옮기고, 더하고, 끝내고, 찍고, 게재했는지 드러나지 않는다. 앞의 셋은 표에 단서가 있다. 스냅숏을 누가 찍었는지는 운전 안내의 "the Zenodo deposit of the first run was made by hand"에서 겨우 짐작한다. 게재하는 주체는 runner인데, Zenodo에는 runner가 나오지 않는다.

D16. Zenodo 셋째 문단. "The state informally proved has qualifications that a reader should know before relying on it."
인용 부호나 이탤릭이 없으면 "The state informally proved"는 "비형식적으로 증명된 그 상태"로 읽힌다. 용어임을 표시해야 한다.

D17. Zenodo 셋째 문단. "binary64 floating-point computations with error models assumed in advance, in which the rounding error is covered by assumed margins rather than tracked by the arithmetic."
"assumed"가 한 문장에서 잇달아 되풀이된다.

D18. Zenodo 첫 문단. "One works on the problem, trying to prove or refute a statement, to understand some feature of the problem, or to turn an already reviewed proof into a formal proof in Lean 4, a proof assistant; a second reads everything the first left behind and develops it into a draft record; a third checks that draft against the first session's files and assesses every claim in it."
한 문장이 지나치게 길다. 첫 마디 안의 나열과 동격구가 세미콜론 구분과 겹친다.

D19. Zenodo 둘째 문단. "and version 1 a snapshot taken on 11 November at 00:19, while the conjecture was still open."
다른 시각에는 모두 "Korean time"을 붙였는데 여기만 빠졌다.

D20. README 첫 운전 절의 자리 표시자. "`[placeholder: link to the Lean formal proof of the root; none exists yet, ...]`"
공개 README에 코드 서식을 입힌 템플릿 잔재 같은 줄이 다섯 있다. 링크인지 미완성 부분인지 망설였다.

D21. 운전 안내 기본값 목록. "- `explore_every` (default 1): the runner raises an exploration request each time the count of attempt launches reaches a multiple of this number; ..."
다른 항목은 "이름: 기본값 서술" 꼴인데 이 항목만 "(default 1)"을 따로 달았다. 문장도 목록에서 가장 길다.

D22. 운전 안내 명령 표. "`status` | Read the root state, ..."
다른 칸("Launch ...", "Run ...")처럼 명령이 하는 일을 쓴 것이라면 "Report"나 "Show"가 자연스럽다. "Read"는 사용자에게 읽으라는 지시로도 읽힌다.

### [E] 문장 사이와 문단 사이의 연결

E1. README 둘째 문단. "No session assigns work to another: a session in the first stage reads the knowledge base and decides for itself what to work on. Formalization is the one exception. The runner requests it when ..."
예외로 든 주체는 세션이 아니라 runner다. 그러니 "어떤 세션도 일을 맡기지 않는다"는 규칙의 예외가 되지 못한다. 게다가 peer, review, comprehensive review도 runner가 배정하므로, 무엇이 규칙이고 무엇이 예외인지 흐려진다.

E2. README "By default, the first model listed for the peer and review roles differs from the first model listed for the producing roles. ..."
이 문단은 review 설명과 게재 설명 사이에 끼어 있다. 이 문단이 한정하는 것은 서두의 "independent judgment"인데, 문단은 그 연결을 밝히지 않는다. 독립성 주장에 대한 중요한 단서(검토 세션이 같은 모델일 수 있다)가 맥락 없이 놓였다.

E3. README "Questions and progress" 마지막 문단. "The role guides describe progress as the change a piece of work makes to what is known. ... Extending the range over which a statement has been checked, without any such change, does not count as progress."
"progress"가 시스템에서 무엇을 결정하는지 나오지 않는다. 게재 기준인지, 리뷰 기준인지, 지침일 뿐인지 알 수 없다. 앞뒤 문단과 이어지지 않고 떠 있다.

E4. README 한눈 보기 "State of the conjecture". "*Informally proved* on 11 November 2026, a status defined below: every piece of the argument that leads to the conjecture was written up and passed review by an AI session"
"defined below"라고 해 놓고 콜론 뒤에서 곧장 정의한다. 그 정의는 뒤의 정식 정의와도 꼴이 다르다(정식 정의는 runner가 관계로 도출한 경우를 포함한다). 독자는 정의가 두 개인지 의심하게 된다.

E5. README "The end of a session" 다음 문단. "A session interrupted from outside, by a provider's usage limit for example, is treated the same as one that ended on its own."
바로 앞 문단은 세션이 "explicit decision"으로 끝나거나 재고 한도에 이르러 끝난다고 했다. 외부에서 중단된 세션을 "스스로 끝난 것"과 같이 취급한다면, 호스트가 재고를 요청하는지 건너뛰는지 알 수 없다. 두 문단이 맞물리지 않는다.

E6. Zenodo 둘째 문단. "The two chains are not independent confirmations; both pass through one statement, ... This version is a snapshot taken on 12 November 2026 at 23:25 Korean time ..."
"informally proved"의 정의와 그 한정 사이에 판본 정보가 끼어든다. 셋째 문단 첫 문장 "The state informally proved has qualifications"는 둘째 문단 앞부분을 잇는데, 그 사이를 판본 이야기가 끊는다.

E7. 첫 운전 문서 "Artifacts not yet public". "are listed, with their status, in the first-run section of the [README](../../README.md)."
"full account"를 자처하는 문서가 마지막 절에서 독자를 요약본인 README로 되돌려 보낸다. 상세에서 개요로 가는 역방향 참조라 어색하다.

### [F] 수학적으로 틀리거나 모호한 진술

F1. "중간 아래"의 범위. README "the sequence never decreases over the steps below the middle, in the exact range of steps that the frontier's statements give"; 첫 운전 문서 "showing that the sequence has no descent at all below the middle"; Zenodo "that the sequence never decreases below its middle index."
네 경우를 정의할 때는 하강에 "below m−1", 상승에 "below m"를 써서 구별했다. 그런데 핵심 명제에서는 "below the middle"로 뭉갠다. 그래서 지수 m−1의 하강(제1경우)이 포함되는지 알 수 없다. 포함된다면 제1경우도 같은 명제로 배제되고, 포함되지 않는다면 Zenodo의 "below its middle index"가 정확하지 않다. README는 정확한 범위를 frontier로 미루지만, 그 명제는 두 경로가 공유하는 유일한 명제다.

F2. binary64 "error model assumed in advance"의 성격. README "The second kind is binary64 floating point with an error model assumed in advance: the rounding error is covered by margins added to the results rather than tracked by the arithmetic."
엄밀한 선험적 오차 해석도 결과에 여유를 더하는 방식이다. 단위 반올림 2⁻⁵³에서 오차 한계를 유도하는 경우가 그렇다. 이 문장만으로는 그 여유가 증명된 한계인지, 넉넉하다고 판단한 휴리스틱인지 갈리지 않는다. 어느 쪽이냐에 따라 "unproved로 취급하라"는 권고의 무게가 완전히 달라진다.

F3. route의 정의. README "A **route** to the root is a path of relations, each feeding the next and some with several premises, along which a proof of a node contributes to settling the root"
전제가 여럿인 관계가 섞이면 그 구조는 경로(path)가 아니라 나무다. "contributes to settling"이 "다른 전제가 다 증명되면 루트가 따른다"는 뜻인지 더 약한 뜻인지도 정해지지 않는다. 첫 경로("splits that failure into four cases")를 route 하나로 부르는 서술도 흐리다. route가 한 노드에서 출발하는 경로인지, 루트로 가는 증명 구조 전체인지 알 수 없다.

F4. 필요조건의 정의. README "A node is a necessary condition of the root when only its refutation can contribute."
이것은 수학의 "necessary condition"(루트 ⇒ K)과 다른, 조작적 정의다. 루트와 동치인 노드는 증명도 반증도 "contribute"할 수 있는데, 어느 쪽에 드는지 알 수 없다. 게다가 뒤 문단("it states a limit that unimodality for every n implies")은 이 낱말을 표준적인 뜻으로 쓴다.

F5. 첫 운전 문서의 점근 서술. "where n lies between 2ℓ and about 2ℓ^(3/2), the records established that the neighboring counts b(n, ℓ−1) and b(n, ℓ) agree to leading order as ℓ grows, and that their difference b(n, ℓ) − b(n, ℓ−1), whose sign decides the inequality, is only of order ℓ^(−1/3) times either count."
모호한 점이 넷이다.
- n이 범위 안에서 움직이는데, "as ℓ grows"가 그 범위에서 균일한지 밝히지 않았다.
- 부호를 정하려면 아래 한계가 필요한데, "only of order"는 위 한계처럼 읽힌다. Θ인지 O인지 모호하다.
- "about 2ℓ^(3/2)"는 경계가 불명확하다.
- 앞 절의 단계 표기는 ℓ → ℓ+1이었는데, 여기서는 ℓ−1 → ℓ로 바뀐다.

F6. 첫 운전 문서의 Lean 정리. "let F_ℓ(z) = Σ_j A(j, ℓ) zʲ / j! ... The theorem states that ℓ^(3/2) (F_ℓ(1/e) − F_{ℓ−1}(1/e)) tends to e/√(2π) as ℓ → ∞. ... The limit was later proved without any assumption"
j의 합 범위(0부터인지 1부터인지)가 없다. "later"의 기준점도 알 수 없다. 해석이 셋 다 가능하다.
- r801ec220의 조건부 결과보다 뒤에 무조건 증명이 나왔다.
- Lean 정리 자체가 그 무조건 증명이다.
- 무조건 증명은 별도의 기록에 있다.

F7. "numerical evidence"로 수락된 성질. 첫 운전 문서 "two monotonicity properties that a table used by record r030ffaeb relies on and that its review had accepted on numerical evidence"
README가 정한 확립 수준(비형식 증명, 두 종류의 컴퓨터 보조 산술, 형식 증명)에는 "수치 증거로 수락"이 없다. 그런데 "Limits"는 r030ffaeb를 경로 위의 기록으로 꼽는다. 그렇다면 11일 16:14의 "informally proved"와 v2 스냅숏이 수치 증거로만 받아들인 성질에 기대고 있었는가? 그 범주는 binary64 범주와 같은가? 문서는 답하지 않는다. README와 Zenodo는 이 일을 언급하지 않는다.

F8. README 첫 운전 절. "carried out in interval arithmetic with integer endpoints"
b(n,ℓ)은 정수인데 왜 구간을 쓰는지, 끝점이 정수라는 것이 무슨 뜻인지(거대한 정수를 상하한으로 감싼다는 뜻인지) 설명이 없다.

F9. 첫 운전 문서 정의. "otherwise it drives on toward higher numbers and takes the first free spot it meets, and if none is left it fails."
"none is left"는 "빈자리가 하나도 남지 않았다"로도 읽힌다. 뜻하는 것은 "앞쪽에 빈자리가 없다"이다. 사소함.

F10. README 노드의 settled. "A node is **settled** once it or its negation, and not both, has been proved"
"and not both"는 둘 다 증명된 노드는 settled가 아니라는 뜻으로, contested를 미리 가리키는 듯하다. 그러나 이 문장만으로는 둘 다 증명되면 체계가 모순이라는 점과 어떻게 맞물리는지 흐리다. 또 settled는 비형식 증명을 포함한다. 그래서 같은 문단 끝의 "finished only when the root has been settled at the formal level"을 이해하려면, 독자가 "settled at the formal level"이라는 한정을 따로 해석해야 한다.

F11. 첫 운전 문서 표. "records rfc693208, r0e82912d and rc56f637b, published between 16:12 and 18:18, each prove both properties independently"
"independently"의 뜻이 모호하다. 세 기록이 서로 독립적으로 증명했다는 뜻일 수도 있고, 수치 증거와 독립적으로 증명했다는 뜻일 수도 있다.

### [G] 문서들 사이의 사실 불일치

G1. r5909c9e7이 증명한 것. README "Both routes pass through one statement, that the sequence never decreases over the steps below the middle, ...; this statement was the last part to be proved. The record that proved it, r5909c9e7, ..." / 첫 운전 문서 "The last open premise on the routes was a single node, pair-beats-capped-threshold. ... in outline, it is an inequality between two counts of configurations for n between 2ℓ and about 2ℓ^(3/2). The record that proved it, r5909c9e7"
README에서는 r5909c9e7이 "중간 아래 비감소" 명제 전체를 증명했다. 첫 운전 문서에서는 그 명제의 범위 일부에 대한 부등식 노드 하나를 증명했다. Zenodo("The record that proved the last open statement on those routes")는 첫 운전 문서 쪽과 맞는다.

G2. 게재 기준. Zenodo "a third checks that draft against the first session's files and assesses every claim in it. Records that pass this assessment are published" / README "Separately, the review decides whether the record has enough useful content to be published at all" / "useful work that is not yet perfect can still be published"
Zenodo는 게재된 기록이 평가를 "통과"했다고 읽히게 쓴다. README에 따르면 unsupported 주장이 든 기록도 게재된다. 실제로 r5909c9e7의 리뷰도 주장 하나를 unsupported로 매겼다. 저장소를 보지 않은 Zenodo 독자는 기록 전체가 검증되었다고 오해할 수 있다.

G3. 검증 가능성. README는 모든 세션에 해당하는 것처럼 쓴다. 운전 안내에 따르면 peer, review, organizer는 새 세션으로 교체되므로 처리가 다르다.

## 3. 확정하지 못한 것

1. **"begun research"의 기준.** section 등록이나 question 점유가 기준일 것이라고 추측했다. 문서에는 없다.
2. **binary64 오차 모형의 실체.** 여유가 증명된 선험적 한계인지 휴리스틱인지 모른다. 리뷰가 "computer-assisted proofs"로 수락했다는 사실만으로는 가를 수 없다.
3. **"accepted on numerical evidence"의 범주와 시점.** r030ffaeb의 두 단조성이 11일 16:14의 루트 도출에 쓰였는지 모른다. 쓰였다면 v2의 "informally proved"는 수치 증거에 기댄 셈이다. 12일 오후에 나온 기록 셋이 그 공백을 메웠다고 읽었지만 확정할 수 없다.
4. **"below the middle"의 정확한 지수 범위.** 제1경우가 따로 있으니 m−1은 빠지고, 하강 지수 ℓ ≤ m−2를 가리킬 것이라고 추측했다.
5. **pair-beats-capped-threshold의 내용.** 그것이 "중간 아래 비감소"의 어느 부분을 맡는지도 모른다.
6. **"interval arithmetic with integer endpoints"의 뜻.** n이 20000에 이르면 b(n,ℓ)이 수만 자리 정수가 된다. 그래서 정확히 계산하는 대신 정수 상하한으로 감쌌을 것이라고 외부 지식으로 추측했다.
7. **Lean 정리의 시간 순서.** r801ec220의 조건부 함의, 무조건 증명, Lean 정리(r0af7f414, 6일) 사이의 선후를 모른다. F_ℓ 합의 j 범위도 모른다. 1/e가 주차함수 EGF의 수렴 반지름이라는 점은 외부 지식으로 메웠다. (j+1)^{j−1}/j!·e^{−j} ~ e/(√(2π) j^{3/2})이므로 극한값 e/√(2π)가 자연스럽다고 보았다.
8. **세션이 웹과 이전 인스턴스에 접근할 수 있었는지.** 세션에는 웹 검색이 있다. 이전 인스턴스의 기록이 사용자 컴퓨터에 남아 있었다면 세션이 그것을 읽을 수 있었는지, 첫 운전에 scholarly-mcp가 설정되었는지는 문서에 없다.
9. **CLI 프로세스가 왜, 언제 끝나는지.** 모델이 응답을 마치면 비대화형 CLI 프로세스가 끝난다는 점은 CLI 사용 경험으로 메웠다. 재고 한도에 이르렀을 때 runner가 종료를 "authorize"하지 않는 경우가 있는지도 모른다.
10. **"Ending a run"이 되돌릴 수 없는 종료인지.** `start`가 "after a crash or reboot"에도 복구한다고 하므로, 세 단계로 종료한 뒤 다시 `start`하면 운전이 이어질 것이라고 추측했다.
11. **question에도 lease나 점유 기제가 있는지.** question 0(루트 문제 전체)을 동시에 몇 explorer가 잡을 수 있는지도 모른다.
12. **"producing roles"에 organizer가 드는지.** 기본 모델 서술에 따르면 organizer도 Codex를 먼저 쓸 것이라고 추측했다.
13. **외부 지식으로 메운 것.**
    - concept DOI의 뜻(Zenodo 관례).
    - "Korean time"이 UTC+9라는 것(Zenodo의 UTC 병기로 확인).
    - `propext`, `Classical.choice`, `Quot.sound`가 Lean 4/Mathlib의 표준 공리이고 `sorryAx`가 미완성 증명의 표지라는 것.
    - Codex가 OpenAI의 CLI라는 것.
    - 모델 이름(gpt-6.1-sol, Claude Fable 5.1, Opus 5.5)은 문서에 적힌 그대로 받아들였다.
14. **Celano 외의 표기와 n ≤ 9 표.** 원 논문은 확인하지 않았다. 끝값 b(n,0)=n!과 b(n,n−1)=nⁿ⁻²은 n=2, 3에서 손으로 확인했다(n=2에서 2, 1; n=3에서 6, 7, 3).
15. **"installed copy"와 소프트웨어 재생성의 범위.** 인스턴스가 스킬의 사본을 실행하는 것이라고 추측했다.
