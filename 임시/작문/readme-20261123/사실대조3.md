# Fact check 3: README lines 242–331, the running guide, and CITATION.cff

This report compares three texts with the sources of the current do-math implementation, sentence by sentence: `C:\math\README.md` lines 242 to 331, the whole of `C:\math\docs\do-math\running.md`, and the `message`, `abstract` and `keywords` fields of `C:\math\CITATION.cff`. It is written for the agent that will correct those texts before they are published. Each verdict rests on the source file read at the place cited; the four digests were used only to find places.

The whole range was checked. No statement was found that a source flatly contradicts. Thirteen statements say more than their source does, because a condition or an exception was dropped; one reads as referring to a different library than the record means; and one concerns GitHub and cannot be checked from the repository. Section 2 lists them in the order of how much each could mislead a reader, within each document. Three of them matter most, and they are placed first in their documents: the README's statement that the verification record gives the last run of every test module, although the runtime was changed once more after the record's last revision; the running guide's sentence that a run is complete when the root "has a formal proof", which drops the acceptance by review that completion requires; and the abstract of `CITATION.cff`, where two sentences state as universal what the skill states with exceptions.

Locations are written as `path:line`. `OPS` abbreviates `C:\math\.claude\skills\do-math\reference\operations.md`, `V` abbreviates `C:\math\docs\do-math\lean-canon-verification.md`, and `RUNTIME` abbreviates `C:\math\.claude\skills\do-math\runtime`.

### 2.2 docs/do-math/running.md

**G1. running.md:204 — when the run is complete.** Verdict: `overstated`.

> "The run is complete when that statement, or its negation, has a formal proof, and no later step compares the statement with what you meant."

Completion requires that the root be settled through a formal proof, and settled requires acceptance by review. OPS:11: "The instance is complete when the fixed Lean statement, or its negation, is settled by a formal proof." OPS:350: "A statement is **settled** when one of its proofs is accepted and every statement that proof names is settled". OPS:356: "`formal_proved` | The root is settled through a proof that is formal." A proof that is complete in Lean can be correct and not accepted; the first research had two such proofs (V:72: "eighteen statements whose proofs are accepted and two whose proofs are correct and held back. Twenty statements are formal."). The guide itself uses the stronger wording elsewhere (running.md:19, "A run ends when the root is formally settled").

Corrected sentence: "The run is complete when that statement, or its negation, is settled by a formal proof, and no later step compares the statement with what you meant."

**G2. running.md:219 — what the operator adds to a condition.** Verdict: `overstated`.

> "When the operator delivers a condition for you, it gives your words in English translation as a quotation marked as yours, marks its own explanation as its own, and adds neither a reason nor an example that you did not give."

The guide forbids an added reason and only discourages an added example. OPS:302: "**Give no reason the user did not give.**" OPS:304: "**Do not widen the condition, and add examples of your own rarely.** ... If you add an example, mark it as yours."

Corrected sentence: "When the operator delivers a condition for you, it gives your words in English translation as a quotation marked as yours, marks its own explanation as its own, adds no reason that you did not give, and adds an example of its own only rarely and marked as its own."

**G3. running.md:268 — what `kill-session` ends on Windows.** Verdict: `overstated`.

> "this also ends the session's host process and, on Windows, every process the session started."

The source gives a condition and an exception. OPS:449: "on Windows, where the session's `process-job.json` records that containment was applied, the system ends every process the session started ... Where containment was not applied, including on Linux, computations the session started can outlive it". OPS:483: "Processes started on a session's behalf by a service, for example through COM or `wsl.exe`, were never in the job. `process-job.json` in the session folder records whether containment was applied; when it could not be, the session runs uncontained".

Corrected sentence: "this also ends the session's host process and, on Windows, where the session was placed in a job, the processes the session started, apart from any that a system service started for it."

The other steps of that paragraph are supported: `stop` (`RUNTIME\runner.py:1621-1622`, `RUNTIME\ending.py:116-134`); the runner's ID in `runner/process.json` (OPS:438, `runner.py:1486`); the broker's ID in `runner/lean/process.json` (`RUNTIME\lean_broker.py:72-74`, `lean_broker.py:1618`); and the broker's exit. The function `should_exit` (`lean_broker.py:1549-1555`) returns true only when the runner's state has `finished` set, no session has an active status and no broker job is active, and the runner sets `finished` only when the root is formally settled and no work remains (`runner.py:1456-1474`, `RUNTIME\knowledge.py:383-390`, `knowledge.py:423-424`). The broker guide says the same (`C:\math\.claude\skills\do-math\reference\lean-broker.md:69`).

**G4. running.md:264 — when the runner starts the judge of the root.** Verdict: `overstated`.

> "The runner starts this command itself when the root becomes formally settled, and `status` gives the result under `root_judge` as running, accepted, rejected or unavailable."

OPS:417: "It starts it only where the instance has a judge and while no publication is underway"; the same paragraph adds a second start "before it finishes if the library has changed since that judging". `RUNTIME\runner.py:1084-1087` returns without starting when a publication is underway or queued, when the instance is stopped, or when `judge_commands(...)` finds no judge. In an instance without a judge, `root_judge` stays empty and is none of the four values.

Corrected sentence: "Where the instance has a judge, the runner starts this command itself when the root becomes formally settled, and `status` gives the result under `root_judge` as running, accepted, rejected or unavailable."

**G5. running.md:98 — which declarations need a record.** Verdict: `overstated` (minor).

> "Every declaration you write is an element and needs a record: definitions, structures and inductive types, theorems and instances."

OPS:56 has the same sentence and then the exception: "A declaration marked `private`, and the auxiliary declarations Lean generates, such as the fields and constructor of a structure, are not elements and need no record."

Corrected sentence: "Every declaration you write is an element and needs a record: definitions, structures and inductive types, theorems and instances. A declaration marked `private` is not an element and needs none."

**G6. running.md:98 — the path of a record.** Verdict: `overstated` (minor).

> "The record of the declaration `A.B.c` is the file `records/A/B/c.md`."

OPS:100: "A name component that Windows cannot use as a file name is encoded, for example `Aux` as `Aux%`; when in doubt, the path `init` reports for a missing record is the right one." The reserved names are in `RUNTIME\canon.py:39`.

Corrected sentence: "The record of the declaration `A.B.c` is the file `records/A/B/c.md`; a name component that Windows cannot use as a file name, such as `Aux`, is encoded, and the path that `init` reports for a missing record is the right one."

### 2.3 CITATION.cff

**C1. CITATION.cff:5, second sentence of `abstract`.** Verdict: `overstated`.

> "Everything the research keeps is a declaration of one Lean 4 library with a written record beside it."

The sources say this of assertions, and the canon keeps other texts as well. `C:\math\.claude\skills\do-math\SKILL.md:10`: "Every mathematical assertion the research keeps is an **element**, which is a declaration of that library whose statement Lean has compiled, together with its **record**." OPS:330–331 list what else the canon holds: "`canon/approaches/<name path>/<id>.md` | The approaches tried on a statement whose proof is not accepted" and "`canon/questions/<question>.md` | The understanding so far of a question." The README says the same outside my range (README:39: "together with a small amount of written text attached to particular statements and questions").

Corrected sentence: "Every mathematical assertion the research keeps is a declaration of one Lean 4 library with a written record beside it."

**C2. CITATION.cff:5, third sentence of `abstract`.** Verdict: `overstated`.

> "Each addition is produced by one session, turned into a change to the library by a second session and judged by a third, and it is published with that judgment."

This is the path of work that comes from an attempt, an explorer or a formalizer (`SKILL.md:14-16`, `SKILL.md:50`). Two kinds of addition enter otherwise. An organizer's additions pass through no peer and no review: `C:\math\.claude\skills\do-math\reference\organizer-output.md:5`, "Nothing you submit goes through review. ... the runner publishes what compiles and passes the checks a machine can decide, and what you add enters as accepted"; `SKILL.md:40`, "Two kinds of proof stand without a review." The operator's questions also enter directly: OPS:318, "Its questions do not pass through peer or review".

Corrected sentence: "Each addition that a researching session produces is turned into a change to the library by a second session and judged by a third, and it is published with that judgment."

**C3. CITATION.cff:5, fourth sentence of `abstract`.** Verdict: `overstated`, by a narrow exception.

> "A run is complete only when the Lean statement fixed at the start, or its negation, has a proof that is complete in Lean, depends only on the allowed axioms and has been accepted by a review."

The first two conditions are necessary (OPS:356; OPS:360, "The instance is complete when the root is `formal_proved` or `formal_refuted`"; `SKILL.md:12` for "formal"). Acceptance is necessary too (OPS:350), and in the ordinary path it is a review's. A proof can also be accepted without a review: an organizer may add a one-line derivation of a statement from another statement that agrees with it, and that derivation "enters as accepted like the agreement itself" (`C:\math\.claude\skills\do-math\roles\organizer.md:29`). The sources do not exclude the root from this path. The abstract also leaves out that everything the proof names has to be settled (OPS:350), which the words "only when" permit.

Corrected sentence: "A run is complete only when the Lean statement fixed at the start, or its negation, has an accepted proof that is complete in Lean and depends only on the allowed axioms."

## 3. Disagreements

### 3.1 Between README lines 242–331 and the running guide

1. **When Mathlib is needed.** README:246: "It needs Mathlib when the Lean definitions of the problem draw on it." running.md:9: "Mathlib is needed when the Lean definitions of the problem, or the proofs the sessions will write, draw on it." The second names a case the first leaves out. The sources say only that the operator confirms "the Lean environment the problem needs" (`SKILL.md:32`) and that a proof "uses the imported library, such as Mathlib, and nothing else" beyond the elements (`SKILL.md:10`), so the running guide's wording is the fuller one.
2. **The download from arXiv.** README:248 states it without a condition and running.md:21 with one ("when they are not yet on the machine"). The running guide agrees with the source; see R5.

Everywhere else that both speak of the same thing they agree: the requirements, the permissions with which the CLIs are launched, the default models, the minimal settings file, the three commands of the quick start, the list of what `init` refuses (the README's four cases are among the running guide's), the option of the literature server and "about twenty" sources, and the description of the operator's steps.

### 3.2 Inside the running guide

3. **"Run" names two states.** running.md:19 says "A run ends when the root is formally settled and the remaining work has been processed", running.md:204 says "The run is complete when that statement, or its negation, has a formal proof", and running.md:280 explains that "A root that is formally settled and a runner that has finished are therefore different states". A reader of line 204 cannot tell which of the two states "complete" means. The operating guide uses "the instance is complete" for the root's state (OPS:360) and "the runner has finished" for the other (OPS:370).

### 3.3 Between a guide and the code, bearing on a sentence of the range

4. **Which commands refuse an instance of the earlier runtime** (bears on running.md:240). OPS:453: "Every command of this runtime refuses an instance that the earlier runtime created"; `SKILL.md:82` says the same. The code makes the check in the runner only, for every runner command except `init` (`RUNTIME\runner.py:1611-1612`). `canon_tool.py`, `depmap.py`, `judge.py` and `paper.py` have no such check (`RUNTIME\canon_tool.py:23-29`, `RUNTIME\depmap.py:327-328`, `RUNTIME\judge.py:387-391`, `RUNTIME\paper.py:1533-1539`). OPS:280 gives the refusals "in this order" and leaves out two that the code makes: a formal theorem of the starting canon that the judge rejects, and a judge that could not run on such a theorem (`RUNTIME\runner.py:152-164`).
