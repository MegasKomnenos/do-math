## 2. Statements whose verdict is not `supported`

### 2.1 Two findings that bear on what a completed run can be trusted for

#### F1. The judge's sandbox (L221): `wrong` in one clause, `unsupported` in another

README, L221: "The comparing program can run inside a sandbox as a guard against this; that sandbox needs Linux and is switched off on Windows, where every run recorded so far was made."

"This" is the danger named in the sentence before it: Lean code that a session wrote runs when the library is compiled. The sentence tells the reader that the sandbox guards against that danger and that the guard is missing only because the recorded runs were made on Windows. The sources say that the sandbox does not cover the compiles of the library on any system, because do-math never lets the comparing program build anything.

- `reference/operations.md:427`: "`lake comparator` can build what it judges inside a sandbox, which needs Linux namespaces. do-math always hands it exports of modules that its own broker compiled, so that sandbox does not cover the builds, and where it cannot run at all, as on Windows, the commands carry the option that switches it off. The verdict therefore rests on those builds having been made honestly".
- `runtime/judge.py:239-242`: the comparing program is started with `--challenge-from-export` and `--solution-from-export`, that is, with files the exporter wrote from modules already compiled; it is given no sources to build.
- `runtime/judge.py:96-98`: the option `--inadvisably-no-sandbox` is added on Windows, and also on any other system where `bwrap` is not found.

A reader on Linux would conclude from the README that the judge's verdict is protected there against a dishonest compile. It is not.

The clause "where every run recorded so far was made" has no basis in the named sources. The verification record `C:\math\docs\do-math\lean-canon-verification.md`, which is not among them, says at line 190 that the judge was run with the real programs "on Lean 4.36.0 and Windows", and at line 253 that the broker's estimates were measured "on one machine, under Windows". It contains no sentence about every run. The word "run" also has a defined sense in the README (L36: "Each run of do-math is an instance"), so the clause reads as a statement about every instance.

Corrected sentence: "The comparing program has a sandbox in which it can build what it judges, but do-math gives it modules that the instance's own broker has already compiled, so the sandbox does not protect those compiles on any system; the sandbox needs Linux and is switched off on Windows." If the remark about past runs is to stay, the wording the verification record supports is "where the judge has so far been run with the real programs".

#### F2. "Lean then guarantees" (L24): `overstated`

README, L24: "Lean then guarantees that the proof establishes the statement as it is written."

This is a sentence of the opening, and the body states the limit at L221 ("The judge's verdict holds only if the library it was given was compiled honestly"). It is reported under the rule for opening summaries because a reader who stops at the opening is left believing that a completed run carries an unconditional guarantee by Lean. The sources never say "guarantee". They say that Lean has checked the proof, and they name what that check rests on.

- `SKILL.md:62`: "a proof written in a record has been judged by review while a proof complete in Lean has also been checked by Lean."
- `reference/lean.md:226`: "Lean checks that a proof proves the statement as written."
- `reference/operations.md:411`: "do-math takes a statement for formal from its structural index … The index is computed inside a Lean process that has loaded the modules it describes." `runtime/judge.py:5-7` adds: "so it is only as good as that process."
- `reference/operations.md:427`: "The verdict therefore rests on those builds having been made honestly: Lean code that a session wrote runs when it is compiled, as at every compile of the instance."

Corrected sentence: "Lean has then checked that the proof establishes the statement as it is written; the section 'Formal proofs and the judge' says what that check itself rests on."

If the owner judges that "guarantees" is acceptable shorthand in an opening, the finding can be set aside; the body is correct.

### 2.2 Five lesser findings

#### F3. Which sessions are asked to reconsider ending (L146): `overstated`

README, L146: "It starts with the session, and when a CLI process exits normally it resumes the same conversation and asks the session to reconsider, under its role guide, whether to end; by default it does so up to three times." The paragraph ends: "The same reconsideration applies to explorers, formalizers and peers."

Every source attaches a condition to attempts and explorers: the session must have undertaken research. An attempt or an explorer that only looked for work and reports that it found none ends without being asked.

- `SKILL.md:52`: "before an attempt or explorer that undertook research, a formalizer or a peer is closed".
- `reference/operations.md:261`: "A valid `no_research` outcome or an interruption ends the session without a reconsideration turn".
- `runtime/ending.py:203-209`: when the outcome file of a producing session is a valid `no_research` outcome, the host authorizes the end at once with the basis `no_research` and returns.

L150 says that such a session "ends without a peer or a review", and does not say that it also ends without the request. The same paragraph of L146 names two ways in which a session ends; the code has a third, the case in which the CLI gives no usable conversation identity for a resumption (`runtime/ending.py:247-254`, basis `resume_unavailable`). That case is rare and is mentioned here only for completeness.

Corrected sentences: "It starts with the session, and when a CLI process of an attempt that has undertaken research exits normally, it resumes the same conversation and asks the session to reconsider, under its role guide, whether to end; by default it does so up to three times." And: "The same reconsideration applies to explorers that have undertaken research, to formalizers and to peers."

#### F4. What an organizer ends with (L148): `overstated`

README, L148: "Reviews and organizers are not asked for such a decision, because each of them ends with a definite output: a review with its assessment, an organizer with its changes to the canon."

An organizer's output is its organization file. A change to the canon is an optional part of it, and an organizer that finds nothing to do still ends with a complete output.

- `runtime/ending.py:19-20`: "A review and an organizer end with their output, an assessment or an organization".
- `reference/organizer-output.md:21`: "A change is optional. … Without a change, `organization.json` is the whole of your output."
- `roles/organizer.md:55`: "An organization that finds nothing to join, rearrange or merge is a complete one."

Corrected sentence: "Reviews and organizers are not asked for such a decision, because each of them ends with a definite output: a review with its assessment, an organizer with its organization, which names the published changes it examined and holds any change to the library and any merge of questions."

#### F5. When the old statement's proof becomes a derivation (L164): `overstated`

README, L164: "A statement that supersedes another enters under a new name, and the old element keeps its name and statement; where the new statement gives the old one, the old element's proof becomes a one-line derivation from it."

The revision added the condition "where the new statement gives the old one". The condition on timing is still missing: an old statement that is settled keeps its proof until the new statement is settled too.

- `roles/peer.md:59`: "An old statement that is already settled keeps its proof until the new statement is settled as well, because a statement that is not yet settled is not a better one than a settled one; the derivation replaces the old proof after that."
- `reference/change-format.md:104`: "So your candidate adds the new statement and leaves the proof of the old one as it is. Once the new statement is settled, the derivation can replace the old proof, in a later candidate of any peer."
- `runtime/check.py:141-143` refuses the other order: "Publish the new statement first; the derivation of the old statement from it replaces the old proof once the new statement is settled".

Corrected sentence: "A statement that supersedes another enters under a new name, and the old element keeps its name and statement; where the new statement gives the old one, the old element's proof becomes a one-line derivation from it, at once when the old statement is not settled, and otherwise only after the new statement is settled as well."

#### F6. "is not compiled twice" (L190): `overstated`

README, L190: "and it keeps compiled modules, so that a module whose source and imports are unchanged is not compiled twice."

The review's own compile of a candidate is the exception, and it is made on purpose. The README describes that compile itself at L219 ("The review compiled the candidate afresh in its own session"), so L190 and L219 disagree as they stand.

- `reference/lean.md:159`: "`build --fresh-targets` compiles the targets even when the cache holds them, and takes only the modules they import from the cache. Review's compile of a candidate uses it, through `commands.verify`, so that the compile of the changed modules is review's own."
- `reference/lean-broker.md:87`: "`build --fresh-targets`, which `commands.verify` uses, forces the targets to compile even when the cache holds an entry with their key."
- `runtime/check.py:240-242`: the transport check of an assessment requires that each changed module was compiled by a job of the reviewing session and not taken from the cache.

Corrected clause: "and it keeps compiled modules, so that a module whose source and imports are unchanged is taken from the cache instead of being compiled again; the one exception is the review's own compile of a candidate, which compiles the candidate's modules afresh."

#### F7. Where a concern comes from (L235): `overstated`

README, L235: "A **concern** is a challenge to the proof of an element, reported by a review session in its assessment."

The runner opens a concern as well, when a finding withdraws a confirmation without naming an existing concern. This is entry 15 of the second earlier report, and the sentence is unchanged.

- `reference/review-output.md:132`: "When such a finding withdraws a confirmation without naming an existing concern, the runner opens a concern on those elements, so that a comprehensive review examines the broader consequences."
- `runtime/knowledge.py:108-111` adds that concern with the identifier `withdrawal-<n>`.

Corrected sentence: "A **concern** is a challenge to the proof of an element, reported by a review session in its assessment or opened by the runner when a finding withdraws a confirmation without naming a concern."

## 4. Disagreements of the README with itself, and terms used in two senses

### 4.1 Disagreements

**Which sessions choose their own work (L20 against L18, L101, L106, L107 and L184).** L18 and L101 count the formalizer among the producing sessions. L20 says: "A producing session reads the library and decides for itself what to work on, and the runner assigns work only where the state of the research calls for it, such as a peer and a review for the work that a producing session leaves." L107 and L184 say that the runner gives a formalizer one settled statement, and L106 says that the runner assigns the question about the whole problem to an explorer when no explorer has it. The sources agree with the body: `reference/common.md:172` ("The runner launches one for a settled statement that the root rests on"), `runtime/runner.py:1164-1168` (the formalizer's task names its element) and `runtime/runner.py:296-300` (the runner writes the explorer's occupation of `q0`). The draft that the first report checked gave the formalizer at this place as an example of work the runner assigns; the revision removed the example and left the general statement. A sentence that agrees with the body: "An attempt reads the library and decides for itself what to work on; the runner assigns work only where the state of the research calls for it, such as a peer and a review for the work that a producing session leaves, or a formalizer for a settled statement that still lacks a formal proof."

**Whether an unchanged module is compiled twice (L190 against L219).** See F6.

**Whose judgment "settled" expresses (L86 against L201 and L227).** L86 says: "Being settled is a matter of the reviews' judgments." L201 and L227 say that a proof supplied with the root or added by an organizer stands as accepted although no review judged it, so a statement can be settled through proofs that no review read. L86 repeats `reference/common.md:170` word for word, and the exception is stated where it matters, so this is a tension a careful reader can resolve and not an error.

### 4.2 Terms used in two senses

1. **settled.** L84 defines the term: a statement is settled when one of its proofs is accepted and everything that proof names is settled. Three places use the verb in the ordinary sense. L231: "A proof that settles part of its statement by a large computation … is, by default, held back", while L207 says of a proof that is held back that it "settles nothing that rests on it"; the two sentences contradict each other in their wording. L207 itself has the better word for the first: "establishes part of its statement". L24: "That correspondence is settled before the research starts", in the paragraph that also says the root "is settled through a formal proof". L176: "Work may settle something."
2. **settled** and **formal**, said of proofs. L84 and L86 define both terms for statements. L86 ("a proof that is formal"), L101 ("a proof that is settled and not yet formal") and L107 ("whose accepted proof is not yet formal") apply them to proofs without a definition. The sources define both uses (`reference/common.md:166`: "A proof is **settled** when it is accepted and every statement of the canon that it names is settled, and a statement is settled when one of its proofs is"). One clause at L84 or L86 would close the gap.
3. **statement.** L40 defines a statement as an element, a `theorem`. L84 ("a further declaration with the same statement") and L67 ("for each declaration, the text of its statement") use the word for what a declaration asserts, and at L67 the declaration can be a definition. L84 now explains how one statement has several proofs, so the two senses no longer leave a reader without an answer.
4. **library** (not bold). In the opening the library is the whole body of results: L16 calls an element with its record "an element of that library", L18 calls the candidate "the proposed change to the library" and counts the account of the approaches as part of that change, and L20 and L22 speak of work that "enters the library" and of the library as "the research's memory". From L40 on, the library is the Lean library, one part of the canon, and L108 calls the same candidate "the proposed change to the canon". The opening has no other word, because "canon" is introduced at L40.
5. **record.** L40 defines the record as the written file beside a declaration. L180 speaks of "the records that an earlier research run had left", which were records of sessions (`reference/what-research-is-for.md:7`: "Every session that works on a do-math investigation leaves behind a record of what it tried and what it found"). A reader who holds to L40 takes them for records of elements. "the accounts that the sessions of an earlier research run had left" avoids the collision.
6. **run** (not bold). L36 defines a run as an instance. L221 uses "every run recorded so far" for something else, as F1 notes.

Every other term set in bold within the range is used in one sense: instance, root, canon, element, imported library, weight, unit, step, structural index, standings, work that remains, frontier, index, attempt, explorer, formalizer, peer, review, organizer, pipeline, retained work, section, board, lease, role guide, session host, candidate, questions, understanding so far, approaches tried, runner, Lean broker, judge, concern, finding, comprehensive review and contested. Two of them appear before they are defined: "retained work" in the table at L105 to L109 and in the diagram at L123, before L132, and "board" in the diagram at L116, before L138.

### 4.3 The two example blocks
