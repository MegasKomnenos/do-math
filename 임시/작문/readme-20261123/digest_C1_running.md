# Part 1. The current facts

## 1. Requirements

**Python.** Python 3.12 or later is required for every run (`SKILL.md:32`, `reference/operations.md:173`). The runner starts its own child processes with the interpreter that ran the command, `sys.executable` (`runtime/runner.py:362`, `runtime/runner.py:1519`), and writes the same interpreter into every session's commands (`runtime/context.py:72`). [inferred] The code uses calls that exist only from Python 3.12, `os.path.isjunction` (`runtime/runtime_support.py:472`), `shutil.rmtree(..., onexc=...)` (`runtime/runtime_support.py:506`) and `Path.is_junction` (`runtime/runtime_support.py:520`), and no source contains a version check, so an older Python fails at those calls and not at start. [inferred] The runtime imports only the standard library and its own modules; I scanned the import lines of `runtime/*.py`, `runtime/depmap/draw.py` and `exemplars/fetch.py`, and `exemplars/README.md:13` says of `fetch.py` that it "needs only the Python standard library". The sources contain no sentence that says this of the runtime as a whole.

**Git.** Git is required for every run (`SKILL.md:32`, `reference/operations.md:173`). `init` creates the instance's own repository and its first commit (`runtime/runner.py:193-195`); every publication is a commit of `knowledge` and `canon` (`runtime/runner.py:1000-1002`). Git is called as `git` from PATH with `-c user.name=do-math -c user.email=do-math@localhost`, and with every `GIT_*` variable removed from the environment (`runtime/runtime_support.py:354-364`). [inferred] Without Git, `init` fails at `git init`, after it has created the directory, with `{"error": ...}` on standard error and exit code 1 (`runtime/runner.py:193`, `runtime/runner.py:1708-1710`).

**The AI command-line programs.** The runner needs "authenticated Codex and/or Claude native executables" (`reference/operations.md:173`); the operator confirms "the actual native CLI paths and existing authentication" (`SKILL.md:32`). The runner launches them as processes (`runtime/cli_adapter.py:39-72`, `runtime/ending.py:146-147`) and authentication stays with the installed CLIs (`reference/operations.md:234`). Settings name them under `cli`; the default for each is the path found on PATH when `init` runs, or the bare name `codex` or `claude` when none is found (`runtime/settings.py:35`). The settings are checked for structure only: "actual login and model availability are confirmed by execution" (`reference/operations.md:218`). [inferred] When a configured CLI is missing, the session host's launch raises `OSError`, which is recorded as `launch_error` (`runtime/ending.py:162-163`); the runner then blocks that model for a retry delay and the retry takes the role's next model (`runtime/runner.py:473-477`, `runtime/runner.py:380-395`, `runtime/runner.py:256-263`). With one provider installed and the default model lists, every role therefore still names the missing provider, and launches on it fail and fall back each time.

**Lean.** A Lean environment is required for every run (`reference/operations.md:173`), and it is needed already at `init`: `init` compiles the canon folder through a Lean broker that it starts and stops (`runtime/runner.py:143-145`, `runtime/runner.py:167-176`, `reference/operations.md:150`), and "the `lean` block has to be right before `init`, because `init` compiles the canon folder with it" (`reference/operations.md:222`). The default command is `["lean"]` with version command `["lean", "--version"]` (`runtime/settings.py:42-43`). A canon that does not compile is refused with `the canon does not compile: ...` (`runtime/runner.py:146-148`). A Lean that cannot start is reported as the compile's own `failed` result (`reference/lean-broker.md:35`).

## 2. Operating systems

- The code has two branches, Windows (`os.name == "nt"`) and everything else, and the second branch reads Linux interfaces: `/proc/meminfo` for memory (`runtime/runtime_support.py:20-23`), `/proc/<pid>/stat` and `/proc/sys/kernel/random/boot_id` for process identity (`runtime/runtime_support.py:287-292`), and `os.pidfd_open` with `signal.pidfd_send_signal` to end a process (`runtime/runtime_support.py:329-333`). The guides speak of Windows and Linux throughout (`reference/operations.md:447`, `reference/operations.md:481`, `reference/operations.md:525`, `reference/lean.md:19`).
- [inferred] macOS is not supported: it has no `/proc`, so `memory_status` raises and `process_identity` reports every process as gone (`runtime/runtime_support.py:20-23`, `runtime/runtime_support.py:287-294`). [not in the sources] No file of the skill folder mentions macOS; a search for `macOS` and `Darwin` in its `.md` and `.py` files found nothing.
- What differs between the two systems, as the sources state it:
  - *Containment of a session's processes.* On Windows the session host puts itself into a job object before its first turn, so that the system ends every process the session started when the host exits; on Linux "the session runs uncontained", and computations a session started can outlive it (`reference/operations.md:481`, `reference/operations.md:447`, `runtime/runtime_support.py:391-424`).
  - *Who starts the Lean broker.* A contained session never starts the broker; the runner does. On Linux a session's client starts one itself (`reference/lean.md:49`, `reference/lean-broker.md:69`).
  - *What "free memory" means.* Commit headroom on Windows, `MemAvailable` on Linux (`runtime/runtime_support.py:14-38`). On Windows compiles can wait for the commit limit while physical memory is free (topic 11).
  - *The judge's sandbox.* The sandbox of `lake comparator` needs Linux namespaces; on Windows, and wherever `bwrap` is not found, the commands carry `--inadvisably-no-sandbox` (`runtime/judge.py:74-75`, `runtime/judge.py:96-98`, `reference/operations.md:425`).
  - *Privilege level.* "Use shells at the same privilege level on Windows, because process-query access is part of liveness detection" (`reference/operations.md:521`, `runtime/runtime_support.py:303-309`).
- What the sources say was measured or tried, with the system where they name it: the commit-charge and queue measurements were taken on "the machine these measurements were taken on, with 15.9 GB of memory, a commit limit of 25.2 GB and sixteen sessions running", a Windows machine (`reference/operations.md:228`, `reference/lean-broker.md:29`); the `lake env` saving was "measured" on one machine (`reference/lean-broker.md:73`); the start time of the literature server and Codex's handling of a configured server were measured or tried, without the system being named (`reference/operations.md:253`). [not in the sources] The listed sources contain no statement that a whole run was verified on Windows or on Linux. A file `C:\math\docs\do-math\lean-canon-verification.md` exists; it is outside the sources I was allowed to use and I did not read it.

## 3. How a session is launched

**The Codex command.** The base command is (`runtime/cli_adapter.py:55-62`):

```text
<codex> exec --model <model> -c model_reasoning_effort="<effort>" -c approval_policy="never" --sandbox danger-full-access --cd <session folder> --skip-git-repo-check --color never --json -
```

Before the final `-`, the worker launch inserts (`runtime/launch.py:32-42`):

```text
--ignore-user-config --ignore-rules -c project_doc_max_bytes=0 -c developer_instructions="" -c model_context_window=1000000 -c model_auto_compact_token_limit=900000 --enable skip_host_skill_discovery -c web_search="live" --disable hooks --disable memories --disable plugins --disable apps --disable multi_agent -c mcp_servers=<the instance's servers as one TOML table>
```

**The Claude Code command.** The base command is (`runtime/cli_adapter.py:66-71`):

```text
<claude> --print --model <model> --effort <effort> --dangerously-skip-permissions --permission-prompts none --input-format text --output-format stream-json --verbose
```

The worker launch gives the model the suffix `[1m]`, replacing an existing `[1m]` or `[200k]`, and appends (`runtime/launch.py:44-52`):

```text
--setting-sources "" --settings <session>/worker-settings.json --disable-slash-commands --strict-mcp-config --mcp-config <session>/worker-mcp.json --no-chrome
```

`worker-settings.json` is `{"disableAllHooks": true, "autoMemoryEnabled": false, "claudeMdExcludes": ["**"], "enabledPlugins": {}}` and `worker-mcp.json` is `{"mcpServers": <the instance's servers>}` (`runtime/launch.py:46-50`). The Claude effort has to be one of `low`, `medium`, `high`, `xhigh`, `max`; for Codex any nonempty text is passed on (`runtime/cli_adapter.py:51-52`, `runtime/cli_adapter.py:64-65`).

**Common to both.** The working directory is the session's folder (`runtime/runner.py:346`, `runtime/cli_adapter.py:53`). The prompt is given on standard input from the session's `prompt.txt`, and the CLI's output goes to `cli.stdout.jsonl` and `cli.stderr.log` (`runtime/ending.py:142-147`). A resumed turn of the same conversation adds `resume <id> -` for Codex or `--resume <id>` for Claude (`runtime/launch.py:53-59`).

**What a session inherits.** The environment of the runner process, with these changes: `CODEX_THREAD_ID`, `CODEX_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`, `CLAUDECODE`, `CLAUDE_CODE_DISABLE_1M_CONTEXT` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` are removed, and `CLAUDE_CODE_AUTO_COMPACT_WINDOW=900000`, `CLAUDE_CODE_MAX_OUTPUT_TOKENS=128000` and `MCP_TIMEOUT=180000` are set (`runtime/launch.py:63-73`). It also uses "the existing CLI authentication and the external tools explicitly configured for the instance" (`SKILL.md:42`).

**What a session does not inherit.** "Worker sessions inherit no personal/project instructions, hooks or memories. Their guides, references and standing inputs are supplied by do-math and saved at launch" (`SKILL.md:42`); "worker launches disable personal/project instruction discovery, skills, hooks and memories" (`reference/operations.md:234`). "A tool in your own personal settings does not appear in workers unless it is configured in `mcp_servers`" (`SKILL.md:42`). The context a session is given is written into its folder at launch: `context/` with copies of the guides, `input.json`, `pack.md` and `prompt.txt` (`runtime/context.py:57-66`, `runtime/context.py:95`, `runtime/context.py:136-140`).

**Context window.** Every worker role requests a 1,000,000-token context window, with compaction at 900,000 tokens; Claude's output cap for one response is set to 128,000 tokens. "These are launch requests: the selected model, account and CLI determine actual capacity and access" (`reference/operations.md:257`, `runtime/launch.py:10-13`).

**Tool servers.** Only the servers in the instance's `mcp_servers` enter sessions (`reference/operations.md:234`). The default is the one server `scholarly` (topic 1). `init` writes the default entry into the instance's `settings.json` when it is given no settings file or a settings file without an `mcp_servers` key; a settings file that has the key replaces the default with what it gives, so a different or additional server is written there together with the `scholarly` entry, and `"mcp_servers": {}` creates an instance without external tools (`reference/operations.md:247`, `runtime/settings.py:56-57`). A local server uses `command`, `args` and optional `env`; an HTTP server uses `url` and the provider's transport configuration (`reference/operations.md:234`). The reason for `--public-only`: every session starts its own copy of the server, and without the option each copy would log in separately to the institutional account the server uses for subscription sources; with it the server creates no login, opens no browser, serves about twenty sources reached through public interfaces, "among them zbMATH, arXiv, Crossref, OpenAlex and Semantic Scholar", and refuses the others, so sessions cannot search MathSciNet or retrieve subscription full texts (`reference/operations.md:249`). The runner sets `MCP_TIMEOUT` to 180 seconds because sixteen copies started together took up to forty-one seconds and the Claude CLI otherwise begins the turn without a slow server (`reference/operations.md:253`, `runtime/launch.py:14-16`). Codex does not wait for a configured server, so for an instance with Codex sessions the operator reads one session's stream after launch for `mcp_tool_call` items and tells the user if none succeeds (`reference/operations.md:253`).

**Web search and other built-in tools.** Codex sessions are launched with `-c web_search="live"` (`runtime/launch.py:35`). [inferred] Claude sessions keep the CLI's built-in tools, since no flag of the Claude command restricts them (`runtime/launch.py:44-52`). The literature guide tells sessions that "web search and the pages of preprint servers and authors supplement" the literature server (`reference/literature.md:31`), and the tools guide tells them to "use the CLI's available shell, file and search tools" (`reference/tools.md:43`). A Claude session can launch delegated agents with the CLI's own tool; a Codex session is launched with its multi-agent feature disabled and cannot (`reference/tools.md:51`, `runtime/launch.py:36`).

**No access sandbox.** Codex runs with `--sandbox danger-full-access` and approval policy `never`; Claude with `--dangerously-skip-permissions` (`runtime/cli_adapter.py:58-59`, `runtime/cli_adapter.py:68`). [inferred] Nothing in the launch confines what a session can read, write or reach on the network; the Windows job object ends a session's processes with its host and restricts no access (`runtime/runtime_support.py:391-424`). The guides tell sessions to keep their files in their own session directory and never to write in the canon (`reference/tools.md:11`, `reference/tools.md:15`).

## 6. From a statement to a running instance

The operator and the user do the following in order (`reference/operations.md:13`, `SKILL.md:18-48`).

**6.1 The root file.** A UTF-8 file with the proposition in words, "with its objects, assumptions, domains and quantifiers defined", and the values for small cases when the user's material gives them (`reference/operations.md:17`). Everything inside an instance is written in English, the root file included, "whatever language the user speaks to you in" (`reference/operations.md:19`, `SKILL.md:34`). `init` refuses an empty root file (`runtime/runner.py:96-98`).

**6.2 The canon folder.** A folder outside the new instance directory that holds the beginning of the instance's Lean library; `init` copies it into the instance (`reference/operations.md:23`). Its layout (`reference/operations.md:25-31`):

```text
<canon folder>/
  lean/<Library>/Defs.lean     the definitions of the objects the proposition speaks of
  lean/<Library>/Root.lean     the root statement, importing the definitions
  records/<name path>.md       one record for each declaration, at the path that follows its name
  bibliography.bib             optional: the sources of definitions or statements taken from the literature
```

`<Library>` is the one top-level module name of every module of the instance; it must differ from `Init`, `Lean`, `Std`, `Lake` and from the first component of any imported library such as `Mathlib`, and every path component consists of ASCII letters, digits and `_` and does not begin with a digit; the file names `Defs.lean` and `Root.lean` are examples (`reference/operations.md:33`). The definitions go into one module and the root statement into a module of its own that imports it, because a proof later replaces the body of the root's declaration and the runner adds to that module the imports the proof needs; if the definitions lived there, the later modules and the root's module would import each other in a cycle (`reference/operations.md:35`). Several definition modules under the same library name are accepted (`reference/operations.md:35`). The definition modules should import only the library modules they use, because every later module inherits those imports (`reference/operations.md:37`).

**6.3 Lean conventions.** (`reference/operations.md:39-56`)

- Each file is written in Lean's module system: it begins with `module`, imports with `public import <module>`, and puts its declarations under `@[expose] public section`. `init` does not check these three things; a file that omits them fails later, when a session's module imports it (`reference/operations.md:43`).
- A statement is a `theorem`. The root is a theorem whose proof is `by sorry`. `init` refuses a root declaration that is not a theorem and one that already has a proof, in Lean or as a `## Proof` in its record (`reference/operations.md:45-52`).
- No `axiom`, and no `sorry` inside a definition; `init` refuses both (`reference/operations.md:54`).
- Every declaration the operator writes is an element and needs a record: definitions, structures and inductive types, theorems, instances. A `private` declaration and the auxiliary declarations Lean generates need none (`reference/operations.md:56`).
- A worked pair of files, `lean/OddSum/Defs.lean` and `lean/OddSum/Root.lean`, is at `reference/operations.md:60-92`; the root declaration there is `OddSum.sum_eq_square` (`reference/operations.md:94`).

**6.4 A record for each declaration.** The record of `A.B.c` is `records/A/B/c.md`; a name component Windows cannot use as a file name is encoded, and the path `init` reports for a missing record is the right one (`reference/operations.md:100`). A record has a header between two `---` lines and sections with fixed headings (`reference/operations.md:102-112`): `weight` (required; `unit` or `step`), `short`, `source` in the header; `## Description` (required), `## Statement`, `## Explanation`, `## Literature`. The root's record carries no `proves`, no `refutes` and no `## Proof` (`reference/operations.md:114`). An example record is at `reference/operations.md:118-134`.

**6.5 Checks of the definitions on known values.** A definition that compiles can denote another object than the one intended, so the Lean definitions are evaluated on the small cases the user's material gives and each value is written into the Lean files as a declaration the compiler must prove, for example `example : oddSum 3 = 9 := by decide`. A command that only prints, such as `#eval`, confirms nothing, because `init` shows no output of a compile that succeeds (`reference/operations.md:140-142`). An `example` leaves nothing in the canon; a named theorem with a complete proof is an element, needs a record, and stands as accepted from the start without a review (`reference/operations.md:144`, `reference/operations.md:52`). The checks stay out of the root's module (`reference/operations.md:144`). Agreement on the values is evidence and not a proof, and the user is told so with the list of values checked (`reference/operations.md:146`).

**6.6 `init`.** The command (`reference/operations.md:267-270`, `runtime/runner.py:1587-1592`):

```powershell
python "$skill/runtime/runner.py" init $instance --root C:/research-input/root.md --canon C:/research-input/canon --root-declaration OddSum.sum_eq_square --settings C:/research-input/settings.json
```

`--root`, `--canon` and `--root-declaration` are required; `--settings` is optional, and without it the defaults apply (`reference/operations.md:276`, `runtime/runner.py:1588-1592`). `init` copies the root file and the canon folder into the instance, compiles the library, extracts the structural index, and creates the configuration, the derived views, the session directories and the first Git commit; it returns when the compile has finished (`reference/operations.md:278`, `runtime/runner.py:115-195`). Nothing compiles a canon folder before an instance exists, so `init` is the compile (`reference/operations.md:150`). On success it prints `{"instance": "<path>"}` and exits 0; a refusal prints `{"error": "..."}` on standard error and exits 1 (`runtime/runner.py:1606`, `runtime/runner.py:1706-1710`).

It refuses in this order (`reference/operations.md:278`; code lines in brackets):

- Before it creates anything: an empty root file [`runtime/runner.py:96-98`]; a canon folder without `lean/` [`runtime/runner.py:100-101`]; Lean files that do not share exactly one top-level module name [`runtime/runner.py:102-105`]; a settings file that is not valid [`runtime/runner.py:107`]; an `mcp_servers` entry whose `command` is not found [`runtime/runner.py:110-114`]; a path that already exists [`runtime/runner.py:115`].
- After it has created the directory: a malformed record, for instance one with an unknown header key, without a valid `weight`, without a nonempty `## Description`, or with text before its first section [`runtime/runner.py:135-137`]; a library that does not compile [`runtime/runner.py:146-148`]; a declaration without a record or a record without a declaration, an `axiom`, a definition that contains `sorry`, a claim in a record's `proves` or `refutes` that Lean does not confirm, names that differ only in the case of their letters [`runtime/runner.py:150-151`]; a root declaration that is not a theorem of the library or that already has a proof [`runtime/runner.py:177-183`].
- Two further refusals are in the code and in other paragraphs of the operating guide, and not in the list above: the judge rejects a formal theorem of the starting canon, and the judge "could not run" on such a theorem (`runtime/runner.py:152-164`, `reference/operations.md:411`, `reference/operations.md:220`). See Part 4, disagreement D1.

A refusal of the second group leaves a partial directory without `instance.json`, which is not an instance; the operator fixes the cause and uses a new path (`reference/operations.md:278`, `reference/operations.md:150`).

**6.7 What the user reads and confirms.** When `init` has succeeded, the instance exists and nothing is running. Before `start` the user reads (`reference/operations.md:152-157`): the root statement in words, from `root.md`; the source text of the root declaration and of every definition it uses, from `canon/lean/`; the root statement as Lean prints it after elaboration, the `statement` of the root's entry in `canon/index.json`; and the values on which the definitions were checked, with the fact that nothing beyond them was checked. The operator explains the Lean statement "binder by binder and hypothesis by hypothesis" in the user's language, and does not start the runner before the user has confirmed (`reference/operations.md:159`, `SKILL.md:26`). The reason: the instance is complete when this fixed Lean statement, or its negation, is settled by a formal proof, and "no later step judges whether the theorem that was proved corresponds to what the user meant" (`SKILL.md:22`, `reference/operations.md:11`). If the user asks for a change, the canon folder is changed and a new instance is created on a new path (`reference/operations.md:161`). The root stays fixed for the life of the instance; the runner refuses an instance whose root file or root statement in Lean has changed (`reference/operations.md:165`, `runtime/runner.py:203-208`).

**6.8 `input`.** Optional. `python "$skill/runtime/runner.py" input $instance --file C:/research-input/conditions.md` stores a standing input; it is submitted before `start` so that every initial session receives it (`reference/operations.md:171`, `reference/operations.md:271`, `reference/operations.md:276`). See topic 9.

**6.9 `start`.** `python "$skill/runtime/runner.py" start $instance` launches a detached runner and prints `{"pid": ..., "stdout": "...", "stderr": "...", "instance": "..."}`: the runner's PID and the paths of its new logs, `runner/start-<token>.stdout.log` and `runner/start-<token>.stderr.log` (`runtime/runner.py:1513-1532`, `reference/operations.md:280`). It returns after it has confirmed this launch's readiness token in `runner/process.json` and in the stdout log; it waits up to ten seconds, and a timeout alone does not show that the child died (`runtime/runner.py:1522-1536`, `reference/operations.md:282`). The caller can then end its conversation; "the runner and session hosts continue independently" (`reference/operations.md:282`).

**6.10 `status`.** `python "$skill/runtime/runner.py" status $instance` only reads. It prints one JSON object with the keys `instance`, `runner_alive`, `root_state`, `finished`, `judge`, `root_judge`, `stopped`, `board`, `attempt_dispatch`, `questions`, `blocks`, `lean` and `state` (`runtime/runner.py:1539-1558`). "A successful status command means the query succeeded" (`reference/operations.md:368`).

**6.11 What the operator tells the user.** The absolute instance path, the runner PID, the new log paths, the current running or waiting state, and `knowledge/frontier.md`, where the state of the research can be read (`SKILL.md:48`).

**Where the instance directory goes.** "Choose a path that does not exist, outside the development repository or in an ignored directory such as `.skill-workspace/`. The instance has its own Git repository; confirm that it will remain separate from the parent. Keep preparation files outside that path" (`reference/operations.md:265`, `SKILL.md:46`). `.skill-workspace/` is in the repository's ignore file (`C:\math\.gitignore:20`). Inside the instance, `init` writes a `.gitignore` with `/sessions/`, `/runner/` and `/control/`, so the instance's Git holds `root.md`, `settings.json`, `instance.json`, `knowledge` and `canon` (`runtime/runner.py:127`, `runtime/runner.py:194`).

**The two fields that decide whether review accepts a correct proof.** "With `decline_reducible_proofs` true, review does not yet accept a proof that it judges can still clearly be made simpler. ### 8.5 `judge.py`

Purpose: judges the root of an instance whose root is formally proved or refuted against the root as the instance's first commit fixed it. Through the instance's broker it builds the canon of the first commit and the canon as it stands, each with one added theorem that states the root, or its negation, proved by the proof that settles the root; it accepts when the two statements are identical together with every definition they depend on, the axioms lie within `allowed_axioms`, and the proof is accepted by Lean's kernel and by the other kernels Lean ships (`reference/operations.md:413`, `runtime/judge.py:18-23`).

```text
python <skill>/runtime/judge.py <instance> --out <new folder> [--no-paranoid] [--no-review] [--timeout <seconds>]
```

(`runtime/judge.py:3`, `runtime/judge.py:450-454`.) `--out` is required, new or empty; `--no-paranoid` uses Lean's own kernel only; `--no-review` leaves out the review request on a rejection; `--timeout` is the seconds to wait for each build and for the judge. The folder receives `verdict.json`, the two source trees under `challenge/` and `solution/`, and the judge's files under `judge/` (`reference/operations.md:423`). Exit codes (`reference/operations.md:417-421`, `runtime/judge.py:28`, `:445`, `:458-460`): 0 accepted; 1 the command refused or the judge could not run, which "says nothing about the proof"; 2 rejected, in which case the command has written a request for a comprehensive review of the proof unless `--no-review` was given. The runner starts this command itself (topic 14).

### 8.6 `lean_broker.py`

Purpose: the client, the broker and the job host of the instance's Lean compiles (`runtime/lean_broker.py:1-13`). Commands: `submit`, `run`, `build`, `wait`, `result`, `status`, `cancel`, `version`, `serve`, `_job`; all but `_job` take the instance path first (`runtime/lean_broker.py:1913-1933`). `submit`, `run` and `build` require `--expect-mb <MiB>` and `--session <id>`; `run`, `build` and `wait` accept `--timeout <seconds>`; `build` takes `<root> <targets>...` and `--fresh-targets`, `--no-wait` (`runtime/lean_broker.py:1919-1933`). ## 9. Standing inputs

- **How one is given.** `python "$skill/runtime/runner.py" input $instance --file <file>`; the text is stored as a file under `control/inputs` (`runtime/runner.py:1625-1631`). A standing input is "the way a decision of the user's reaches the sessions" (`reference/operations.md:286`). Like everything inside an instance it is written in English (`SKILL.md:34`, `reference/operations.md:19`).
- **To which sessions it applies.** To every session launched after it, of every role: at launch the runner reads every `*.txt` file of `control/inputs` into the session's `input.json` and its `pack.md` (`runtime/context.py:67-69`, `:127-131`). "Later inputs affect only sessions launched after submission. They do not rewrite existing sessions' instructions or their saved contexts" (`reference/operations.md:171`). Inputs accumulate: "a session receives every input submitted before its launch, in the order of submission, and is told that a later condition overrides an earlier one on the same matter" (`reference/operations.md:171`). Reviewers decide what to accept by it (`reference/operations.md:286`). "Mathematical suggestions remain information for the researchers' judgment" (`SKILL.md:34`).
- **How one is withdrawn.** "To change or lift an earlier condition, submit a new input that says which condition it changes and how" (`reference/operations.md:171`). There is no command that removes an input (`runtime/runner.py:1584`). [inferred] Because the runner delivers whatever `*.txt` files `control/inputs` holds at a launch (`runtime/context.py:68`), a file taken out of that directory is no longer delivered to later sessions; no source describes or recommends this, and `control/` is outside the instance's Git (`runtime/runner.py:127`), so such a removal leaves no record there.
- **What the operator observes when writing one** (`reference/operations.md:284-308`; the three earlier cases that motivate these are at `:288-292`):
  - Give the user's words, in translation, as the user's: a quotation labelled as the user's words in translation is the condition. Keep the original wording outside the instance (`:296`).
  - Mark your own text as yours, and say where a sentence is your reading of the user's words (`:298`).
  - Give no reason the user did not give; if none was given, say so; ask the user when a session will need the reason (`:300`).
  - Do not widen the condition, and add examples of your own rarely and marked as yours (`:302`).
  - Say how the condition relates to the earlier ones, and name the passages you withdraw (`:304`).
  - Say which texts you read and which you did not (`:306`).
  - When the research shows a case the user has not addressed, report it to the user and ask; the answer becomes a new input (`:308`).

## 10. Scheduling

- **Concurrent sessions.** At most `max_sessions`, default 8 (`runtime/settings.py:32`). A session counts while its status is `starting`, `running` or `publishing` (`runtime/coordination.py:27`, `runtime/runner.py:235-236`), so a session whose work waits in the publication queue still holds a slot (`reference/operations.md:467`). A continuation turn of the same session takes no further slot (`reference/operations.md:473`). [inferred] Agents that a Claude session delegates to are part of that session and are not counted (`reference/tools.md:51`, `runtime/runner.py:235-236`).
- **Order.** "Priority is review, peer, formalizer, organizer, eligible explore, then attempt" (`reference/operations.md:485`, `runtime/runner.py:41`). The runner fills free capacity in this order before it launches a fresh attempt; running sessions are not preempted (`reference/operations.md:485`, `runtime/runner.py:1293-1327`). Work that waits for something other than capacity, a retry delay, an available model or another of its kind, does not hold attempts back (`reference/operations.md:485`, `runtime/runner.py:1356-1358`). Comprehensive reviews launch one at a time, as organizers do (`reference/operations.md:485`, `runtime/runner.py:1252-1261`).
- **Spacing.** Attempts and explorations share one spacing: a new one launches at least `launch_interval` seconds, default 180, after the previous attempt or exploration launch, "which gives each new attempt or explorer time to take its lease before the next one reads the board" (`reference/operations.md:485`, `runtime/runner.py:331-333`, `:1246-1250`). The other roles have no spacing. The runner makes a pass every quarter of a second (`runtime/runner.py:1510`).
- **Attempts.** A fresh attempt requires free capacity, the interval, and "an element among the work that remains in the frontier that no pipeline holds whole and for whose lease no session is waiting"; whether mathematical work remains there is the attempt's own judgment (`reference/operations.md:485`, `runtime/runner.py:1231-1244`, `:1359-1363`). An attempt that finds every remaining element occupied can report so; an accepted report stops attempt launches until occupancy ends on a remaining element, an element newly appears among the work that remains, or the operator runs `reconsider-attempts`; `status` shows this under `attempt_dispatch` (`reference/operations.md:491-495`).
- **Explorers.** Exploration is requested by one flag. An attempt launch sets it when the count of attempt launches reaches a multiple of `explore_every`, at every launch by default; the runner also sets it when it finds spare capacity while no element is available to a new attempt or while attempt dispatch is suppressed (`reference/operations.md:507`, `runtime/runner.py:334-338`, `:1337-1345`). When the flag is set and a question is free, one explorer launches ahead of any waiting attempt once the launch interval has passed, and the flag clears; without a free question the flag stays set and attempts dispatch as usual (`reference/operations.md:507`, `runtime/runner.py:1346-1355`, `:1319-1322`). A question is free when it is open, no unfinished exploration holds it or was assigned it, and no live session holds or waits for its lease; several explorations run at once, each on a different question; the runner launches one more only while the free questions outnumber the explorers that have not yet chosen one; when `q0` is free at a launch the runner assigns it (`reference/operations.md:501-505`).
- **Organizers.** One is created "when the number of published changes that no organizer has yet taken into its batch reaches `organizer_every_records`", default 4. "Organizer outputs and comprehensive reviews do not count toward that number" (`reference/operations.md:461`, `runtime/runner.py:1169-1172`). The operator can request one with `organize`.
- **Formalizers.** One is created for each settled statement the root rests on that has no formal proof yet and whose proof names only statements with formal proofs, so formal proofs are written from the bottom of the root's proof upward; one formalizer at a time works on an element (`reference/operations.md:459`, `runtime/runner.py:1159-1168`).

## 11. The Lean broker as the operator sees it

- **What it is.** One detached process per instance through which every Lean compile of the instance runs; sessions do not run Lean themselves (`SKILL.md:38`, `reference/lean.md:31`, `reference/lean-broker.md:67`). It schedules compiles under a memory budget and a thread budget, measures each compile, keeps each job's result so that a session can collect it after its shell command stopped waiting, cancels the compiles of sessions that have ended, and keeps compiled modules in a cache (`reference/lean.md:33-43`). Its files are under `runner/lean/`, outside the instance's Git; its identity is in `runner/lean/process.json` and its log is `runner/lean/broker.log` (`reference/lean-broker.md:67`, `:75`). The runner starts it and starts another whenever it finds none alive; it never stops one, and its own exit does not end the broker (`reference/lean-broker.md:69`, `runtime/runner.py:1057-1066`, `:1475-1476`).
- **In this design compiles carry more of the work.** Sessions compile what they state, a peer's candidate is built before it is frozen, review builds it again, and every publication that changes a Lean file is a build of the library, so "how many compiles can run at once therefore bears on how fast the research moves" (`reference/operations.md:226`).
- **How its budgets are set.** By the resource keys of the `lean` block (topic 7). A compile starts when the memory budget, the thread budget and the machine's actual free memory all have room (`reference/lean.md:47`, `reference/lean-broker.md:11-27`). With `memory_budget_mb` null the budget is the machine's physical memory minus `min_free_memory_mb` minus 512 MiB per session of `max_sessions`, at least 1024; with `cpu_threads_budget` null it is twice the logical cores (`runtime/runtime_support.py:368-384`). The broker rereads `settings.json` when it changes; `status` shows the configuration in force under `lean.config` and any `config_error` (`reference/lean-broker.md:59`, `:75`).
- **Several instances on one machine.** "Each has its own broker with its own budget, and each derived budget assumes the whole machine. The operator therefore sets `memory_budget_mb` explicitly in each instance to its share and leaves the rest to the machine gate" (`reference/lean-broker.md:63`, `SKILL.md:38`).
- **The Windows commit-limit condition.** On Windows, whatever its own budgets allow, the broker starts a compile only if the machine's remaining commit, less what the compile is certain to take, would be at least `lean.min_free_memory_mb`. The commit limit is physical memory plus the page file, and a Lean process is charged far more commit than the memory it uses: one process that imported the Lean metaprogramming library was measured at a commit charge of 2,078 MB while it touched 803 MB, and a compile that imported the analysis part of Mathlib held between 2 and 3.9 GB for the import alone. On the measuring machine, with 15.9 GB of memory, a commit limit of 25.2 GB and sixteen sessions running, about 3.4 GB of the limit was free and compiles ran one at a time: of 481 compiles, the median ran for 24 seconds and waited 179 seconds in the queue (`reference/operations.md:228`). The sign is compiles listed under `lean.queued` in `status` with `waiting_for` null while no compile is running and physical memory is not exhausted; Task Manager shows the charge and its limit as "Committed" (`reference/operations.md:230`). Enlarging the page file raises the commit limit; the operator recommends it and gives the reason, and "the page file is a setting of the user's machine, so the choice and the size are the user's" (`reference/operations.md:230`). The default `memory_budget_mb` does not grow with the page file, so if the budget then holds compiles back it is set explicitly (`reference/lean-broker.md:29`). "The effect on compiles that import Mathlib has not been measured" (`reference/operations.md:230`).
- **Changing Lean or its libraries.** Stop new dispatch, let running CLI turns, publications and compiles finish, update the Lean configuration in the instance's `settings.json` with a new `lean.cache_epoch`, run `restart-broker`, and resume. After the change the cache holds nothing for the new environment, so the next build compiles every module of the canon again; the operator can first build the canon in the new environment with the broker's `build` command, and a canon that no longer compiles is a reason to return to the earlier environment (`reference/operations.md:537-541`).

## 12. Ending a run before the root is settled

The sources describe the parts and no single procedure for this case.

- `stop` stops new dispatch and leaves the runner process alive. Running CLI turns finish; a session that would take a further turn waits behind the stop with the status `waiting_dispatch` and keeps its slot; publication goes on under the stop (`reference/operations.md:436`, `:445`, `:477`; `runtime/ending.py:116-134`).
- `kill-session <session-id>` ends one session: it cancels a pending resumption, also between two CLI processes, and terminates the current CLI; the host then exits, and on Windows the system ends every process the session started (`reference/operations.md:443`, `:447`, `:477`). Where containment was not applied, including on Linux, computations the session started can outlive it (`reference/operations.md:447`). The operator identifies the session's role and identity in `status` first (`SKILL.md:80`).
- "To end the runner itself, wait until no session is active and end the process that `runner/process.json` names; `start` brings it back" (`reference/operations.md:436`). The file holds `{"process": {"pid": ..., "birth": ...}, "token": ..., "at": ...}` (`runtime/runner.py:1486`, `runtime/runtime_support.py:284`).
- Session hosts and the Lean broker are separate processes and keep running when the runner ends (`reference/operations.md:529`, `reference/lean-broker.md:69`).
- [inferred] The broker does not exit by itself after a run that was ended early. It exits only when the runner state's `finished` is true, no session is active and no compile is queued or running (`runtime/lean_broker.py:1549-1555`, `reference/lean-broker.md:69`), and `finished` becomes true only when the root is formally settled and the remaining work has ended (`runtime/runner.py:1467-1474`). After an early end it stays alive until its process, named in `runner/lean/process.json`, is ended. No runner command ends it: `restart-broker` ends the broker and starts another (`runtime/runner.py:1697-1705`).
- [inferred] An instance ended in this way is paused and not closed: nothing in it is deleted, `resume` removes the stop, and `start` launches a runner that follows the processes still alive and continues the pending work (`reference/operations.md:433`, `:437`, `:521`).
- A process is ended by its process ID and never by its name: the runner, each session's host and the Lean broker all run as `python.exe`, and in an earlier run a command that selected processes by name ended the runner together with all twelve sessions (`reference/tools.md:45`). That passage is written for sessions; the fact it reports applies to anyone ending a process on the machine.
- "Preserve the runner state and the canon; deleting internal files is not a recovery procedure" (`SKILL.md:80`); "do not delete locks or edit runner state to force recovery" (`reference/operations.md:521`).

## 13. Interruption, refusal, fallback, restart, and candidates that no longer fit

- **Refusal by a provider or model.** "A typed provider usage refusal blocks that provider until its known reset, or a configured backoff when the reset is unavailable. Model-specific refusals block that model. A new launch uses the first available alternative in its role's list. If all are unavailable, the job remains pending" (`reference/operations.md:511`). The model-specific refusals the code recognizes are Claude's `model_requires_usage_credits` and Codex's message beginning `Selected model is at capacity` (`runtime/retention.py:199-209`). The backoff is `retry_seconds`, doubling with each consecutive refusal, up to `retry_max_seconds` (`runtime/runner.py:375-378`, `:432-436`). A successful session launched after a block's deadline clears that provider's or model's backoff history (`reference/operations.md:515`, `runtime/runner.py:447-457`). `status` shows the blocks under `blocks` and each pending job's error and retry time (`reference/operations.md:513`, `runtime/runner.py:1558`).
- **An interrupted producer.** "A producer interrupted after doing work ends and proceeds to peer; it is not silently resumed under another model. A session that failed before leaving any research material can be retried as an operational launch" (`reference/operations.md:511`, `runtime/runner.py:470-488`).
- **An interrupted peer, reviewer or organizer.** It receives a fresh replacement session with its partial material and the error (`reference/operations.md:513`, `runtime/runner.py:489-503`). When the interruption was not a provider or model refusal or a failed launch, such as a crash or `kill-session`, the replacement waits for the retry delay (`reference/operations.md:513`).
- **An output that fails the transport check.** The host of a review or an organizer first resumes the same conversation with what the check found, at most `max_end_resumptions` times; after that the job waits for the retry delay and a new session takes the stage. The delay does not block the model for other jobs (`reference/operations.md:475`, `:513`; `runtime/runner.py:504-512`).
- **A Claude turn that ended at the output-token cap.** It is not an interruption: the host resumes the same conversation and reports the CLI message; the resumption counts toward `max_end_resumptions` (`reference/operations.md:259`, `runtime/ending.py:193-196`, `:236-238`).
- **A candidate that no longer applies or does not build.** Publications are made one at a time. A candidate was frozen when its peer's session ended, and it can fail to apply or build on the canon as it now is, "through no defect of its mathematics": another publication replaced the proof it replaces, a new module's path is now taken, two candidates introduced the same name, or a machine check fails. The runner does not publish it. "The work goes to a replacement peer, which receives the producer's work, the earlier peer's work and the reason, makes a new candidate, and that candidate receives a new review." An organizer's change that fails in the same way is made again by a replacement organizer. The pending job's error in `status` names the reason (`reference/operations.md:465-469`, `runtime/runner.py:719-738`). A candidate the judge rejects takes the same path (`reference/operations.md:411`, `runtime/runner.py:842-844`).
- **A candidate whose frozen files changed.** The runner keeps the damaged candidate, compares the peer's retained output with the hashes fixed at review assignment, and either copies matching output to a new candidate location for a fresh review or gives the work to a replacement peer (`reference/operations.md:517`, `runtime/runner.py:564-591`).
- **Restart after a crash or reboot.** "After a runner crash or machine reboot, use `start` on the same instance. The runner identifies existing processes by PID and creation identity, follows those still alive, and collects ended work." A publication that was underway is continued, with the build it had started, "without publishing anything twice" (`reference/operations.md:521`, `SKILL.md:80`). Session hosts survive a runner restart (`reference/operations.md:477`). A session whose host was lost is recorded as an interruption (`reference/operations.md:477`, `runtime/runner.py:414-425`).
- **A runner that ends by itself.** When one of its own operations fails, such as a Git commit or a read or write of its state files, the runner ends; `status` then reports `runner_alive` false while `finished` is false. For an `OSError`, `ValueError`, `KeyError` or `RuntimeError` the runner state's top-level `last_error` holds the error and its time; the call stack is in the stderr log that `start` named. The cause is repaired before `start` (`reference/operations.md:523`, `runtime/runner.py:1502-1509`). A judge that cannot run at a publication ends the runner in this way after one repeated build (`reference/operations.md:411`, `runtime/runner.py:845-854`).
- **Running out of memory.** The runner does not end. It releases a memory reserve, writes `Runner memory reserve released; dispatch will wait for recovery.` to its stderr log, and makes no pass while the machine's free memory stays below 512 MiB; it continues without a restart once memory is free (`reference/operations.md:525`, `runtime/runner.py:1488-1501`, `runtime/runtime_support.py:42-58`).
- **Restarting a live runner, and updating the installation.** `start` does not replace a live runner; to restart one, end the one process `runner/process.json` identifies, then use `start` (`reference/operations.md:529`). A runner, a session host and the broker keep the code they loaded; later launches read the updated guides; a session's commands start the installed files afresh at each call (`reference/operations.md:527`).

## 14. Completion

- **When the root is formally settled.** The root is settled by a formal proof "when one of its proofs is accepted, everything that proof rests on is settled, and the proof is formal"; a formal proof of the negation settles the research in the same way, as a refutation (`SKILL.md:64`). The instance is complete when the root's state is `formal_proved` or `formal_refuted` (`reference/operations.md:358`, `runtime/knowledge.py:381-390`, `:423-424`). From then on the runner launches no attempts and no explorations and cancels the ones still waiting (`runtime/runner.py:1298-1303`, `:1334-1335`). Existing sessions keep their scope; the runner carries them through peer and review and still launches formalizations, comprehensive reviews and organization as their inputs become ready (`SKILL.md:64`, `reference/operations.md:368`). Formalization of other settled statements the root rests on has no round cap, "so the runner can keep working well after the root is settled" (`SKILL.md:64`). An informally settled root (`informal_proved`, `informal_refuted`) and a `contested` root do not complete the instance (`reference/operations.md:350-360`).
- **If the settlement is withdrawn.** If a later review withdraws the confirmation of a proof the root's formal settlement rests on before the runner exits, the same scheduler resumes research (`reference/operations.md:368`, `:362`).
- **The judge of the root.** The runner starts `judge.py` itself, as a process of its own, once for each proof through which the root becomes formally settled, and once more before it finishes if the library has changed since; only where the instance has a judge and while no publication is underway and no stop is set (`reference/operations.md:415`, `runtime/runner.py:1070-1111`). `status` gives the result under `root_judge`: the proof judged, the library revision, the folder under `runner/` that holds `verdict.json`, and a status of `running`, `accepted`, `rejected` or `unavailable` with the reason (`reference/operations.md:415`, `runtime/runner.py:1108-1110`, `:1127-1128`). A rejection has left a request for a comprehensive review, which the runner takes up. `unavailable` means the command gave no answer; the runner does not try the same proof on the same library again, and the operator runs the command after the repair (`reference/operations.md:415`). Its log is `runner/root-judge.log` (`runtime/runner.py:1102`). The operator reports the result under `root_judge` together with the formal settlement, and says so when there is none (`reference/operations.md:415`, `SKILL.md:66`).
- **When the runner finishes.** When the root is formally settled, no session is active, no job is pending or running, and no judging of the root is running; it then sets `finished` in its state and exits (`runtime/runner.py:1467-1479`, `:1498-1499`). "A formal root and a finished runner are different states" (`reference/operations.md:368`). After that the broker exits by itself once no compile is queued or running (`reference/lean-broker.md:69`, `runtime/lean_broker.py:1549-1555`). A later `review`, `organize` or `questions` request takes effect only after `start`, whose runner then continues until that work has ended (`reference/operations.md:449`).

## 15. Instances of the previous runtime

"This runtime targets fresh instances whose root is fixed in Lean, and its commands refuse an instance created by the earlier runtime" (`SKILL.md:82`). "Every command of this runtime refuses an instance that the earlier runtime created, whose knowledge was a repository of records and not a Lean library" (`reference/operations.md:451`). In `runner.py`, every command except `init` reads `instance.json` and refuses with `this runtime operates instances whose canon is a Lean library (instance schema 2)` unless its `schema` is 2 (`runtime/runner.py:1611-1612`). A settings key carried over from the earlier runtime is rejected by name (`reference/operations.md:218`). For the other entry points see Part 4, disagreement D4.
