## 1. What I understood

### 1.1 What the two documents say, in the order of importance they give

1. **What do-math is.** Many AI sessions work together to prove or refute one mathematical statement. Each session is a fresh conversation in Claude Code or Codex and does not see the others' conversations. Sessions pass work on as files, and what the research keeps goes into one Lean 4 library that every later session reads. (README 5, 14)

2. **When a run counts as complete.** Only when the statement, or its negation, has a proof that is complete in Lean, uses only the allowed axioms, and has been accepted, and the same holds for everything that proof rests on. The statement is fixed before the research starts, in words and as a Lean theorem with its proof left open, and it never changes. (README 6, 24, 38, 86)

3. **What completion does not show.** Lean checks that the proof proves the Lean statement. Nothing checks that the Lean statement says what I meant, except my own reading before the run starts. Every reviewer is an AI session. No person referees anything unless I arrange it myself. (README 7, 24, 225; guide 217)

4. **What has been verified about the implementation.** One small statement (the sum of the first n odd numbers is n squared) was carried to a formally proved root by six real sessions, all on one Claude model, with the real Lean compiler. That run launched no formalizer, organizer or comprehensive review. The automated tests (22 modules, 763 test functions) replace the AI sessions and the compiler with stand-ins, and the suite has not been run as a whole since the runtime last changed. A run with Mathlib started on 22 November 2026 and its costs are not yet measured. Two rounds of review of the guides and the runtime were stopped while defects were still being found. No solved problem is listed. (README 8, 9, 30, 309–323)

5. **Who does what at the top level.** I supply the statement. An AI conversation called the operator sets up the run with me. A program called the runner then launches sessions, several at a time, for as long as the research goes on. I can add "standing inputs", instructions that reach every session launched after them. (README 14)

6. **What a kept result is.** An "element": a Lean declaration (a definition or a statement) plus a written record in Markdown. A statement may have no proof. A proof is either complete in Lean, or written in words in the record while the Lean source names the statements it uses and ends in `sorry`. In both forms Lean checks that the named statements exist and fit, so the dependency structure is read by a program from the compiled library. In the second form the argument is prose, and only an AI review judges it. (README 16, 40, 44–67)

7. **How an addition is made.** Three sessions in a row: a producing session (attempt, explorer or formalizer) does the mathematics and leaves its files; a "peer" takes that work over, continues it, and writes the "candidate", the proposed change to the library; a "review" has the candidate examined three times independently, compiles it, and judges each element. If the review finds anything worth keeping, the runner applies the candidate, compiles, and commits to Git. Nothing is sent back for repair. An unconfirmed proof is published marked as unconfirmed. A published statement never changes. (README 18, 20, 99–132, 152–164)

8. **Why it is built this way.** Three reasons: the library is the memory across conversations that remember nothing; work is judged by a session that did not produce it, and the judgment stays attached; and a result stated in Lean has one name that proofs must cite. (README 22)

9. **How the status of a statement is expressed.** Four standings: no proof; proof not confirmed; correct, held back; accepted. "Settled" means accepted all the way down. "Formal" means complete in Lean on allowed axioms all the way down. The instance is complete when the root or its negation is settled through a formal proof. The "frontier" is a computed view of what the root still rests on that is not settled. (README 73–97, 192–203, 243)

10. **How sessions avoid duplicating each other.** An attempt picks its own work from the frontier, registers a "section" on a statement, and holds a "lease" while choosing. A "board" lists who is working on what. This is cooperative; the commands refuse only what a program can decide. (README 134–142)

11. **Other parts of the design.** How sessions end and are resumed (README 144–150); questions and the "understanding so far", approaches tried, and what counts as progress (166–176); two background documents handed to sessions (178–180); formalizers work bottom-up, organizers join duplicates without review, the runner's launch order and limits, one Lean broker per instance that queues compiles (182–190).

12. **How much each kind of result can be relied on.** A table of what each standing means and does not mean (README 196–203). Reasons a correct proof is held back: it can clearly be simplified, or it rests on a large computation nobody understands (207). Proofs in words are checked by neither Lean nor a person (211). Formal proofs are checked up to three ways, including a "judge" program that replays the proof through Lean's kernel, and the judge finally compares the proved root with the root fixed at the first commit (217–221). The judge's sandbox is off on Windows (221). User-supplied and organizer-added elements get no review of their meaning (227). Concerns and findings can withdraw a confirmation later (233–237).

13. **How to read a run's results.** Start at `knowledge/frontier.md`, then `knowledge/index.md`; the mathematics is under `canon/`; reading commands exist. (README 239–259; guide 255–267)

14. **How to run it.** Requirements and what a run does to my machine (README 263–267; guide 5–21); the quick start (README 269–301); the full by-hand procedure, settings, commands, ending a run, interruptions (guide 23–312).

15. **The rest of the repository.** Layout, design and verification documents, tests (README 303–323); four unrelated tools and the development skills (325–347); language, citation, AGPL license (349–355).

### 1.2 What I would do to start a run on my own statement and to end it

Before anything:

- a. Check my machine. Only Windows runs are recorded; Linux has code that has not been recorded as run; macOS is not supported. (README 265; guide 15)
- b. Accept the risk. Sessions run unattended with permission prompts off and full file and command access under my account, with web search, with no cap on time, sessions or usage, and with no usage accounting. (README 267; guide 19)
- c. Install Python 3.12 or later, Git, Claude Code or Codex (logged in), and Lean 4, version 4.35 or later if I want the judge. Install Mathlib, already compiled, if my statement needs it. (README 265; guide 7–9, 192)
- d. Either install the Python environment of `services/scholarly-mcp`, or plan to put `"mcp_servers": {}` in the settings. I do not know how to install that environment. (README 265; guide 11)
- e. Clone the repository. (README 271; guide 25)

Route A, through the skill (the route I would take, since I know little Lean):

- A1. Start Claude Code or Codex in the cloned repository and ask it to start research on my statement with the do-math skill. (README 271; guide 25)
- A2. Work with that conversation, the operator: agree the statement in words, write the Lean definitions and Lean statement together, check the definitions on small cases for which I have values. The operator prepares settings and creates the instance. (guide 25; README 225)
- A3. Read what was fixed and the operator's explanation of how the Lean statement reads, and confirm. This is the only check of meaning. (guide 25, 210–217; README 24, 225)
- A4. The operator launches the detached runner and tells me where the instance is. (guide 25)

Route B, by hand:

- B1. Write `root.md`: the statement in English words, with objects, assumptions, domains and quantifiers defined, and any known small values. (guide 33–38)
- B2. Make the Lean folder: `lean/<Library>/Defs.lean` with the definitions, `lean/<Library>/Root.lean` with the root as a `theorem ... := by sorry`, each file starting with `module`, using `public import` and `@[expose] public section`. (guide 42–92)
- B3. Write the known values into the Lean files as `example` lines the compiler must prove. (guide 130–136)
- B4. Write one record per declaration at `records/<name path>.md`, with a `weight` header and a `## Description`; no `## Proof` in the root's record. (guide 96–128)
- B5. Write `settings.json` naming the Lean executable; list only my provider's models if I have one CLI; use `lake env lean` and `lean.cwd` for Mathlib. (guide 138–196; README 273–284)
- B6. Set `$skill` and `$instance` in PowerShell and run `runner.py init` with `--root`, `--canon`, `--root-declaration` and `--settings`, at a new path outside the repository or under `.skill-workspace/`. If it refuses, fix the files and run it again on a new path. (guide 198–208; README 286–294)
- B7. Read four things: `root.md`; the Lean source of the root and its definitions under `canon/lean/`; the `statement` of the root's entry in `canon/index.json`; and the values checked. (guide 210–217)
- B8. Optionally submit standing inputs with `runner.py input $instance --file <file>`, now, before starting. (guide 219–223)
- B9. Run `runner.py start $instance`, then `runner.py status $instance`. (guide 225–232; README 296–299)

While it runs:

- f. Look at `status`, `knowledge/frontier.md`, `knowledge/index.md`, and the `canon_tool.py` reading commands. (guide 242, 255–267; README 241)

To end it early:

- g. `runner.py stop $instance`. (guide 298)
- h. `runner.py kill-session $instance <id>` for each session `status` shows as running. (guide 249, 298)
- i. When no session is running, end the runner process by the `pid` in `runner/process.json` with `Stop-Process`. (guide 298)
- j. End the Lean broker by the ID in `runner/lean/process.json` the same way. Never end processes by name. (guide 298–300)
- k. The instance is then paused, not deleted; `resume` followed by `start` continues it. (guide 302)

If it completes by itself:

- l. The runner stops launching attempts and explorers, lets the remaining work finish, has the root judged, and finishes. `status` shows the root's state, whether the runner has finished, and the judge's result under `root_judge`. (guide 310, 294)
- m. Then I can run `depmap.py` for the dependency map and `paper.py` for a paper, after reading the paper-method document. (guide 273–290)

### 3B. The README as a whole

**Writing quality.** The README is precise and consistent in its main vocabulary. Terms are set in bold where they are defined, and most are then used in one sense (the exceptions are in part 2). The limits of the system are stated plainly and near the claims they limit, which is rare in a front page and is the document's best quality. Its weaknesses are length and evenness. There are six long paragraphs before the first heading (lines 14 to 24), and the body then tells the same story again with a second vocabulary: "the statement", "the library" and "a run" in the introduction become "the root", "the canon" and "an instance" from line 36. Paragraphs of eight to twelve sentences are common (lines 14, 18, 142, 154, 164). The diagram, which would have helped me at line 18, arrives at line 114. Forward references are frequent ("explained below", "described below", "a term explained under"), so the reader carries several undefined terms at once.

**Avoidance of AI writing.** I found few of the usual marks. There is no promotional vocabulary, there are no stacked hedges, dashes appear only inside the code example, and there are no bulleted fragments with bold lead-ins. What remains is small: the slogan at line 142 (3.7); the paragraph at line 26 that announces contents (3.4); the at-a-glance row that duplicates the first sentence (3.1); three uses of "rather than" to close a sentence on a contrast (lines 142, 176, 180); and the enumerated "Three considerations ... The first ... The second ... The third" at line 22, which is saved by the fact that the third is argued and not merely named. The frequent pairs of "does" and "does not" are not a mannerism here, because each pair carries a real limit.

**Likeness to human writing.** It reads as written by one person with settled habits: "rests on", "names", "made", "by itself", "work that remains". Those habits, and details that only experience supplies (the stand-in compiler that "has already hidden two defects", line 323; the review rounds "ended after the second, which still found defects of substance", line 314), are what make it sound like a person. What works against that is the unchanging register. Nearly every sentence has the same build, a main clause followed by a qualifying clause; nothing is ever said briefly; the reader is not addressed as "you" until line 261. A human author of a front page usually lets some things be less important than others. Here everything is given the same weight and the same care.

**Natural reading.** As this reader I read the at-a-glance table and lines 14 to 24 without trouble, and I could have stopped there with a correct outline. From line 134 to line 164 I slowed sharply, and I reread most of "The choice of work" and "Peer, review and publication". "What counts as established" (lines 192 to 237) was the section I read most easily and learned most from, because its table and its short subsections each answer one question. The "Running do-math" section is in the right place for me and is readable, except for line 267.

### 3C. The running guide as a whole

**Writing quality.** Good for a procedure. The examples are complete enough to copy, each rule comes with its reason (the import cycle at line 54, the cost of `import Mathlib` at line 94, why `#eval` confirms nothing at line 134), and each command says what it changes and what it leaves alone ("the instance exists and nothing is running", line 210; "It changes nothing", line 242; "writes nothing into the instance", line 275). The weaknesses are in the structure of the procedure and not in the sentences: the prerequisites cannot be acted on from the text (2.8, 2.13), the by-hand route has no numbered list (3.21), and the ending procedure is a paragraph where four numbered steps would serve (line 298).

**Avoidance of AI writing.** Almost nothing to report beyond the opening sentence (3.20) and the announcing sentence at line 29 (3.21).

**Likeness to human writing.** Stronger than in the README. The guide speaks to "you", it reports measurements from a particular machine ("about seven minutes to load on the development machine", line 192), and it gives advice that reads as learned the hard way ("never by its name", line 300; "Do not delete lock files or edit the runner's state to force a restart", line 302).

**Natural reading.** I read it at an even pace. I stopped at the defaults list (lines 153 to 162), where one bullet runs to several sentences; at the paragraph about the operator's handling of inputs (line 223); and at the `stop` cell (3.23).

## 4. What I could not determine

### 4.1 What I would still need to know

About the design and what is checked:

1. Which rules are enforced by the runner or the tools and which are instructions in a role guide (2.4). In particular, whether anything prevents or detects a session writing into `canon/`, `knowledge/`, or the instance's `settings.json`, given that the runner rereads that file.
2. What happens to an element whose Lean statement a review judges unfaithful to its record, or whose definition it judges not to denote the intended object (2.5).
3. What happens when the judge rejects the root: whether the instance still counts as complete, and what the runner does next.
4. Whether the one real run ended with a judge's verdict on its root (2.2).
5. Whether a complete Lean proof of the root can be held back by a review under the default acceptance settings, leaving the run incomplete (2.16).
6. How a refutation is set up: who writes the negation of the root, and what "a statement that Lean has confirmed to be the negation of the root" (README 86) involves.
7. Which document is the authority on the current design (2.7).

About running it:

8. What a run costs. The documents say there is no cap and no accounting, and that the quantities deciding cost at Mathlib scale are unmeasured (README 313). They give no figure even for the small run: how long it took, or how much usage six sessions consumed.
9. How to install the scholarly-mcp environment (2.8), and how to obtain Lean and a compiled Mathlib (2.13). The minimum Lean version that accepts the `module` syntax of the example files.
10. What happens with the default model settings when only one CLI is installed, and how to write the settings for Codex only (2.9). Which copy of the skill a Codex user points `$skill` at (2.11).
11. What the operator needs from me on the skill route: whether it checks the prerequisites, whether it writes the records, whether it asks for my Lean and Mathlib paths, and what a suitable first request looks like. No example request is given.
12. How I learn that a run has completed, other than by running `status` myself.
13. Whether to wait for running turns before `kill-session`, and how to remove an instance for good (2.10).
14. What `paper.py` launches and under what limits, and what "confirm" means for the paper-method document (2.14).
15. How to run the whole test suite; the README shows one module of 22 and says each is run separately (README 316–321).
