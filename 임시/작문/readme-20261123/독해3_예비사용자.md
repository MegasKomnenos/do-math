## 1. What I understood

This part was written first, from the reading, and was not revised afterwards to agree with the documents.

### 1.1 What the two documents say, in the order of importance they give it

1. **What do-math is.** A system in which many separate AI conversations (Claude Code or Codex sessions) work on one mathematical statement, to prove it or refute it. The sessions do not talk to each other. Everything they keep goes into one Lean 4 library, where each Lean declaration has a written record beside it, and later sessions read that library. (README 5, 13, 15)

2. **When a run counts as complete.** Only when the statement that was fixed in Lean at the start, or its negation, has a proof that is complete in Lean, uses only the allowed axioms, and has been accepted by a review. (README 6, 23, 76, 224)

3. **What completion does not tell me.** Lean checks the proof of the statement as written. Nobody checks, after the start, that the Lean statement says what I meant; I confirm that once, before the run. Every review is an AI session. No human referees anything. (README 7, 23, 204-208; guide 204)

4. **Nothing has been solved yet in the sense the README lists.** The "Solved problems" section is empty. Further down I learn that one toy run (sum of the first n odd numbers) did reach a formally proved root, and that a run with Mathlib started on 22 November 2026 and is still going. (README 8, 29, 287-289)

5. **How an addition to the library is made.** Three sessions in a row: one does the mathematics and keeps its working files; a second, the peer, takes over that work, continues it, and writes the proposed change (the candidate); a third, the review, has three sub-reviewers examine it and then judges each element. If the review finds something worth keeping, a program called the runner applies the change, compiles the library and commits. A review does not send work back; a proof it could not confirm is published marked as unconfirmed. Statements never change once published; proofs and records can be replaced. (README 17, 19, 137-147)

6. **Who does what.** I supply the statement, in words and as a Lean theorem with its proof left open, and may add standing inputs (instructions that reach every later session). An AI conversation called the operator sets the run up with me. The runner, a program, launches sessions for as long as the research goes on. I do not launch sessions. (README 13, 252; guide 25)

7. **Why it is built this way.** Sessions forget, so the library is the memory. The judge of a piece of work took no part in it. A result in Lean has one name that later proofs must use. (README 21)

8. **The vocabulary of the system.** An instance is the directory of one run, with its own Git repository. The root is my statement. The canon is the Lean library plus records. An element is a declaration with its record. A statement has one of four standings (no proof; proof not confirmed; correct, held back; accepted). It is settled when its proof is accepted and so is everything beneath it; formal when the Lean proof is complete on allowed axioms. The frontier is the computed list of what the root still rests on that is not settled. There are six roles: attempt, explorer, formalizer, peer, review, organizer. Sessions divide work by registering sections on statements, shown on a board. (README 35-171)

9. **How far each state can be trusted.** A table says what each state means and does not mean. A correct proof can be held back because it could clearly be simpler or because it leans on a large computation nobody understands; both are settings, on by default. A proof written in words has been checked by AI review only. A formal proof is checked three times (review's compile, runner's compile, and a separate judge program if Lean is 4.35 or later). (README 175-218)

10. **Where to read results.** In the instance directory: `knowledge/frontier.md` first, then `knowledge/index.md`, `knowledge/board.md`, and the files under `canon/`. There are also reading commands (`canon_tool.py`). (README 222-240; guide 244-254)

11. **What a run does to my machine.** Sessions run unattended under my account with permission prompts off (Claude Code) and full access with no approvals (Codex). The workspace boundary is only an instruction. There is no cap on time, sessions or usage, and no usage accounting. The runner itself opens no network connections; the CLIs, the literature server and optional tools do. (README 248; guide 19-21)

12. **What I need installed.** Python 3.12+, Git, Claude Code and/or Codex logged in, Lean 4 (4.35+ for the judge), Mathlib if needed, and by default the Python environment of the bundled literature server scholarly-mcp. Windows is the only system with recorded runs; Linux has code but no recorded run; macOS is unsupported. (README 246; guide 7-15)

13. **How to start.** Either ask Claude Code or Codex, started in the cloned repository, to start research with the do-math skill, or prepare three things by hand (root file, folder with Lean files and records, settings file) and run `init`, read what was fixed, then `start`. (README 252-277; guide 25-213)

14. **How well the software itself has been checked.** One small real run, one scripted run against the real compiler, one Mathlib run in progress, two rounds of review that still found defects. Tests use stand-ins for the AI sessions and for Lean. (README 285-299)

15. **The rest.** Repository layout, four unrelated tools, supporting skills, language (English inside an instance), citation, AGPL-3.0 licence. (README 281-331)

The guide adds, beyond the README: the exact shape of the Lean files and records; how to check definitions on known values; every default setting; the Mathlib settings; the list of runner commands; the dependency map, the paper command and the judge command; the procedure for ending a run early; what happens on interruption, crash and completion.

### 1.2 What I would do, step by step

**Before anything**

- S1. Check that I am on Windows (or accept that Linux is untried) and have Python 3.12+, Git, and Claude Code and/or Codex installed and logged in. (README 246; guide 7, 15)
- S2. Install Lean 4, preferably 4.35 or later so that the judge is available. I am not told how. (README 246; guide 9)
- S3. Decide whether I need Mathlib; if so, have a Mathlib project directory with its compiled library already built. I am not told how. (guide 9, 179)
- S4. Either install the Python environment of `services/scholarly-mcp`, or plan to put `"mcp_servers": {}` in my settings. I am not told how to install it, and its README is in Korean. (README 246, 303-305; guide 11)
- S5. Accept that sessions will run under my account with no permission prompts and no cap on usage. (README 248; guide 19)
- S6. Clone the repository. (README 252; guide 25)

**Path A: through the skill**

- A1. Start Claude Code or Codex in the cloned repository and ask it to start research on my statement with the do-math skill. (README 252; guide 25)
- A2. Work out the statement with the operator in words; write the Lean definitions and Lean statement with it; let it check the definitions on small cases I have values for. (guide 25)
- A3. The operator prepares settings and creates the instance. (guide 25)
- A4. Read what was fixed, with the operator's explanation of how the Lean statement reads, and confirm. (README 23, 252; guide 25)
- A5. The operator launches the detached runner and tells me where the instance is. (README 252; guide 25)

**Path B: by hand**

- B1. Write `root.md` in English: the statement in words, with objects, assumptions, domains, quantifiers, and any known small values. (guide 29-38)
- B2. Make the folder: `lean/<Library>/Defs.lean`, `lean/<Library>/Root.lean`, `records/...`, optionally `bibliography.bib`. Each Lean file starts with `module`, imports with `public import`, puts declarations under `@[expose] public section`. The root is a `theorem` ending `by sorry`. No `axiom`, no `sorry` in a definition. (guide 42-92)
- B3. Put value checks in the definitions module as `example ... := by decide` lines. (guide 132-136)
- B4. Write a record for every declaration at `records/A/B/c.md` with a header (`weight`, optional `short`, `source`) and at least `## Description`; no `## Proof` in the root's record. (guide 98-128)
- B5. Write `settings.json` naming the Lean executable; if I have only Claude Code, also list Claude models in `models` and in `roles.peer` and `roles.review`; for Mathlib use the Lake `env lean` form and `lean.cwd`. (guide 140-179)
- B6. Run `python "$skill/runtime/runner.py" init $instance --root ... --canon ... --root-declaration ... --settings ...` with the instance path outside the repository or under `.skill-workspace/`. (guide 187-195)
- B7. If `init` refuses, fix the files and run it again on a new path. (guide 195)
- B8. Read `root.md`, the Lean source in `canon/lean/`, the root's `statement` in `canon/index.json`, and the checked values. If something is wrong, change the folder and create a new instance. (guide 197-204)
- B9. If I have standing inputs, submit them now with `input --file <file>`, before `start`. (guide 217; I only learned this after the `start` block)
- B10. Run `start`, then `status`. (guide 206-213)

**While it runs**

- R1. Look at `status`; read `knowledge/frontier.md` and `knowledge/index.md`; use `canon_tool.py frontier | view | list | question | log`. (guide 229, 244-254; README 222)
- R2. After a crash or reboot, run `start` again from a shell of the same privilege level. (guide 278)

**Ending it early**

- E1. `stop`. (guide 268)
- E2. `kill-session <id>` for each session `status` shows as running. (guide 268)
- E3. When no session is active, end the runner process by the ID in `runner/process.json` with `Stop-Process`. (guide 268)
- E4. End the broker by the ID in `runner/lean/process.json` in the same way. Never end by process name. (guide 268-270)
- E5. The instance is then paused; `resume` then `start` continues it. (guide 272)

**If it completes**

- C1. The runner stops launching attempts and explorers, lets the rest finish, has the root judged, and then finishes by itself. `status` shows both the root's state and whether the runner has finished. (guide 280)
- C2. Optionally run `depmap.py` and, after reading and confirming the paper method document, `paper.py`. (guide 260-262)

## 2. Where I had difficulty

Each item gives the document, the line, the exact words, and the reason. Items are in reading order, README first.

### README

1. **README 5** — "Everything the research keeps is a declaration of one library written in Lean 4, a proof assistant, with a written account beside it." — "declaration" is a Lean term used here before any explanation (the gloss "either a definition or a statement" comes at line 15). "written account" turns out to be what line 15 and every later line call the "record"; "account" is then used for other things (15 "anyone's account of it", 17 "an account of the approaches", 157 "no account of a session"). Two words for one thing, and one word for several.

2. **README 13** — "An AI conversation called the operator sets up the run together with the user and operates it on the user's behalf." — I could not tell what "operates it" covers once the runner is launched, since README 277 and guide 213 say the runner continues after the operator conversation ends. Must the conversation stay open? Can a new conversation take over an existing instance? Neither document says.

3. **README 15** — "In both cases Lean checks that each named statement exists and fits the use made of it, so what every result rests on is read from the compiled library by a program and does not depend on anyone's account of it." — read twice. "fits the use made of it" is vague on first meeting (line 57 later says "a use whose arguments do not fit the named statement", which is clearer), and the "so" clause changes subject from Lean to an unnamed program.

4. **README 17** — "whether a correct proof should be accepted as the proof the research stops at" — read twice. On first reading "the research stops" sounds like the whole run ending. Only at lines 65 and 188 did I see that it means "no session need look for a better proof of this statement".

5. **README 17, 19, 84, 137** — "a session works on the problem" / "the first session" (17), "A session in the first stage" (19), "producing session" (84), "the producer" (137) — four expressions for one thing. The introduction (13-23) describes the system in one vocabulary ("first session", "stage") and the body in another ("producing session", "pipeline"), so I learned it twice.

6. **README 19, 71, 145** — "A review judges work and does not hold it back for repair" (19); "correct, held back" (71); "A review judges and does not gate. It can decide that a candidate holds nothing worth keeping, in which case nothing is published" (145) — "hold back" names two different things: holding work back from publication, which the review is said not to do, and holding a proof back from acceptance, which is a standing. And the sentence that says a review "does not gate" is followed at once by a case in which it stops a publication; line 145 also mentions "the proof replacements that the review declined" and line 200 a candidate "that the judge rejects is not published". I had to work out that "does not gate" means only "does not return work for repair".

8. **README 21** — "A result kept in prose restates its notation wherever it is written down, and the same fact written in two accounts is two assertions with nothing that stands for the fact itself." — read three times. ## 3. The writing

The owner asked the readers to "also check for writing quality, avoidance of ai writing, and likeness to human writing, and natural reading for human readers". I judge the four as the reader described above.

### 3.1 Each document as a whole

**README**

- *Writing quality.* The sentences are grammatical, precise and plain. Terms are introduced in bold and mostly used consistently afterwards. The weakness is in structure and load. Lines 13-25 are six long paragraphs and a short one, well over a thousand words by my rough count, before the first heading, and they describe the whole system once in informal words; lines 31-171 then describe it again with defined terms; lines 173-218 return to the standings a third time. The same facts (the three stages, the completion condition, the caveat about meaning) are each stated three or four times. A reader does not skim this; a reader either reads all of it or leaves.
- *Avoidance of AI writing.* The usual signs are absent: no inflated vocabulary, no "it is worth noting", no bold-label bullet lists, no em-dash asides, no cheerful summary at the end of sections. What remains that reads as machine-made is evenness. Nearly every sentence is a complete, qualified, medium-to-long declarative; every claim is hedged to exactly its true extent; nothing is said quickly. Two mannerisms recur often enough to be noticed: paragraphs that open with a short negative sentence (item 9 below) and the verb "stand" (item 10 below).
- *Likeness to human writing.* The conceptual sections read like a specification or a statute: exact, impersonal, and without a single worked example between line 13 and line 240. A person explaining the frontier to another person would show five lines of one. The parts that sound like a person are the ones that report experience: the verification outline (287-299), the Windows remarks, the admission that two rounds of review "still found defects of substance".
- *Natural reading.* Slowed by abstraction and by terms that are near each other in sound or sense (standing/state, settled/accepted/formal/complete, index/structural index, section, statement). For my purpose, running the software, the part I need begins at line 242. The top table does link to it, which helps.

**Running guide**

- *Writing quality.* Better suited to its reader than the README. It is ordered by what I do, it gives the reason for each rule in a sentence, and it has examples. Its faults are local: two steps out of order (standing inputs; the `example` lines), several requirements stated without the means to meet them, and two overloaded paragraphs (181-183 and 262).
- *Avoidance of AI writing; likeness to human writing.* It reads as written by someone who has done the thing: the seven-minute Mathlib load, the page file, "never by its name". Little in it reads as machine-made. The paragraphs it shares word for word with the README (guide 7 and README 246; guide 19 and README 248) made me compare the two versions to find what was new.
- *Natural reading.* Good from line 27 to line 213. The command table (225-238) is dense but usable.
