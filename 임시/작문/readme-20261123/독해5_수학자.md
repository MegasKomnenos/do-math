# Reading 5: a research mathematician reads `README.md`

I read `C:\math\README.md` from line 1 to line 356, in order, once through and then again where a passage sent me back. I opened no other file. I read as a research mathematician who knows what a proof assistant is, has not used Lean, and does not know how AI command-line tools or multi-agent systems work.

Line numbers refer to the file as I read it on 2026-11-23.

## 1. What I understood

This part was written first and has not been adjusted afterwards. The points are in the order of importance that the document seems to give them: the "At a glance" table first, then the opening paragraphs, then the body.

1. **What the thing is.** A piece of software that sets many separate AI conversations ("sessions") to work on one mathematical statement, with the aim of proving it or refuting it. Whatever the sessions want to keep goes into a single Lean 4 library, and each Lean declaration has a prose file (a "record") beside it. A program (the "runner") launches the sessions; the human supplies the statement and otherwise stays out. (Lines 5, 14.)

2. **When a run counts as finished.** Only when the statement, or its negation, has a proof that Lean has checked in full, that uses only a permitted list of axioms, and that has been "accepted", and when the same is true of everything that proof relies on. The statement is fixed in Lean before work begins and cannot be changed during the run. (Lines 6, 24, 38, 86, 243.)

3. **What a finished run does not tell me.** It does not tell me that the Lean statement expresses what the human had in mind. The human confirms this once, at the start, and nothing re-examines it. Every reviewer in the system is an AI; no human referees anything unless the user arranges it separately. (Lines 7, 24, 225, 294.)

4. **How much of this has been shown to work.** Very little. One real run exists, on the identity that the first n odd numbers sum to n squared, done by six sessions that all used one model. The automated tests do not use real AI or the real Lean compiler. No solved problem is listed. A second run, using Mathlib, was started the day before I read this. The author's own review of the software stopped while it was still finding substantial defects. (Lines 8, 9, 30, 309-316, 323.)

5. **What is in the library and what Lean actually checks.** An entry ("element") is a definition or a "statement" (a Lean `theorem`). A statement may have no proof at all. If it has one, the proof is either a complete Lean proof, or a proof in words kept in the record while the Lean file merely lists the earlier statements the argument uses and then stops with `sorry`. In the second case Lean checks only that the cited statements exist and are applied to the right kind of object; the argument itself is prose and is judged by an AI review. (Lines 16, 40-46, 58-67, 211.)

6. **How something gets into the library.** Three sessions in a row: one does the mathematics, a second (the "peer") takes over its files, continues the work and writes the proposed change (the "candidate"), and a third (the "review") judges it after three separate readings and after compiling it. If the review finds anything worth keeping, the change is published. The review does not send work back; a doubtful proof goes in, labelled as doubtful, with the reason. A published statement is never altered; proofs can be replaced, and a later review can withdraw a proof's confirmation. Two things skip this path: what the user supplies at the start, and what the "organizer" proves in Lean to identify duplicates. (Lines 18, 20, 154-164.)

7. **Why it was built this way.** Sessions have no memory of each other, so the library must be the memory; the judging session must not be the producing one, and because the judgment is attached to the work, imperfect work can still be kept; and a result stated in Lean has one name that later proofs must cite, which Lean checks. (Line 22.)

8. **The labels on a statement.** Four "standings": no proof; proof not confirmed; correct but held back; accepted. On top of these, "settled" means an accepted proof whose every dependency is settled, and "formal" means Lean-complete under the permitted axioms. "Accepted" does not imply "settled", and "settled" does not imply that Lean or a person checked the argument. A correct proof may be held back if it can obviously be simplified or if it leans on a large computation nobody understands. (Lines 75-86, 194-213.)

9. **Extra checking of Lean proofs.** The review recompiles and reads the axioms; the runner rebuilds at publication; and, with a recent enough Lean, a program called the "judge" re-derives the axioms and replays the proof through Lean's kernel. When the root is proved, the judge also compares the proved statement with the one fixed at the start. The judge's verdict presupposes that the library was "compiled honestly"; the protection against that failing is off on Windows, where all runs so far were made. (Lines 217-221.)

10. **How the sessions divide the work.** Six roles (attempt, explorer, formalizer, peer, review, organizer). Nobody assigns mathematics; a session reads a computed tree of what the root still depends on (the "frontier"), picks something, and registers what it has picked so that others can see. There are also open-ended "questions", and a log of approaches tried on each unproved statement. (Lines 99-176.)

11. **How to read a run's output and how to run it.** Which files to open; six possible states of the root; requirements; the fact that sessions run unattended with full access to the user's account and no cap on time or cost; a quick start. (Lines 239-301.)

12. **The rest.** Repository layout, other unrelated tools in the same repository, languages, citation, licence. (Lines 303-355.)

## 2. Where I had difficulty

Thirty-three items. Items 1-15 are those that could leave this reader with a wrong belief about what a result can be trusted for. They are ordered by how serious I judge the wrong belief to be. Items 16-33 are difficulties of comprehension that do not, as far as I can tell, distort trust.

### Difficulties that bear on trust

**1. Line 24. "Lean then guarantees that the proof establishes the statement as it is written."**
This is unqualified, and it is in the part I would read if I stopped early. Much later, line 221 says: "The judge's verdict holds only if the library it was given was compiled honestly, because Lean code that a session wrote runs when the library is compiled," and adds that the guard against this "needs Linux and is switched off on Windows, where every run recorded so far was made." Line 265 adds that with an older Lean "a run proceeds without the judge", and line 312 that "the command that judges a settled root had not been carried to a verdict on a real instance". So the guarantee in the opening has conditions that the opening does not mention: AI-written code runs during compilation, the independent re-check is optional, and its final form has never been exercised on a real run. A reader who stops at line 26 believes in a plain Lean guarantee. I also did not understand what "compiled honestly" means; a mathematician who has not used Lean does not know that Lean code can execute at compile time or what it could do there.

**2. Lines 6 and 24. "has been accepted"**
"Accepted" is used in the table and the opening before it is explained, and it is not said by whom. A mathematician reads "accepted" as "a referee accepted it". Line 7 corrects the "by whom" one row later, but the meaning of the word arrives only at lines 75 and 207, where it turns out to be a second judgment made after correctness (can the proof still be simplified, does it rest on an unexplained computation). Two consequences I had to work out for myself and am not sure of. First, a run can have a root proof that Lean has fully checked and still not be "complete", because a review held the proof back as simplifiable. Second, by line 243 such a root would be shown as "unresolved". If that is right, "unresolved" can conceal a machine-checked proof. The document never says this directly.

**3. Line 14 against lines 225 and 271. "The user supplies the statement to be proved or refuted and, before the research starts, fixes it in two forms: in words, and as a Lean theorem whose proof is left open."**
From this I believed the user writes the Lean statement. Line 225 says "The operator writes the Lean definitions and the Lean statement of the root together with the user", and the operator is an AI conversation (line 14). So the formalization on which everything depends is drafted by an AI, explained to the user by the same AI, and confirmed by a user who may not read Lean. Line 7 ("The user confirms that before the run starts") is accurate but lets the reader assume more human authorship than there is. This matters because fidelity of the statement is the one thing the document says nothing checks later.

**4. Line 82 against line 201. "The proof is correct and accepted." / "or the proof is complete in Lean and came with the root or from an organizer, in which case no review judged it"**
The first table and the paragraph before it (line 75) present "accepted" as the outcome of a review's two judgments. The second table says a proof can be "accepted" with no review at all. Since "settled" is built from "accepted" (line 84), a settled statement may rest on material no review has read. Line 227 says so honestly, but a reader who learnt the standings from the first table carries the wrong definition until then.

**5. Line 243 against line 211. "It is *informally proved* when it is settled and no proof that settles it is formal yet" / "should treat a settled statement whose proof is not formal as a claim with a reviewed argument attached"**
To a mathematician "informally proved" means proved in the ordinary sense, as in a paper. The document's own advice at line 211 is much weaker: a claim with an AI-reviewed argument attached. The state name says more than the document is willing to say in prose. The same holds for "informally refuted".

**6. Lines 18, 22, 156, 211. "has the candidate examined three times, independently" / "each time independently" / "a review session on Codex, which cannot delegate, makes them itself as three separate passes" / "the three independent examinations"**
"Independently" suggests three readers who do not know each other's conclusions. On Codex the same session reads three times, and I do not see how its second pass is independent of its first. On Claude Code the three readers are "sub-agents", a term never explained; I guess they are further conversations of the same model. Line 22 calls the arrangement "independent judgment", line 160 concedes that peer and review share a model and that all roles may end up on one model, and line 311 says the only real run used one model throughout. The word "independent" is carrying more than the facts support.

**7. Line 5. "Every result the research keeps is a declaration in one Lean 4 library, with a written record beside it."**
In a mathematician's vocabulary a "result" is something proved, and "a declaration in a Lean library" sounds like "checked by Lean". Line 16 shows that a "result" may be a conjecture with no proof, or a statement whose Lean proof ends in `sorry`. Read alone, this row suggests that everything in the library is machine-verified. Rows 6 and 7 protect the reader about a finished run but not about the contents of the library.

**8. Lines 158 and 162. "whether the Lean statement says what its record says" / "an element whose proof the review could not confirm enters the canon with that standing and the review's reason"**
The review judges whether each Lean statement matches its record, but the four standings describe proofs only. I could not find what happens to an element whose Lean statement the review judged not to match its record. Is it published? How is it marked? A reader of the library needs to know whether such a mismatch is visible.

**9. Lines 20, 40, 51, 67, 162, 164. "The statement of a published element never changes afterwards."**
"Statement" names at least four things: the root ("a single mathematical statement", line 5); an element that is a `theorem` as opposed to a definition (line 40); the content of any declaration, definitions included ("the text of its statement", line 67); and a part of a record ("The statement, or the definition", line 51). Because of this I cannot tell whether the immutability rule covers definitions. I guess that it does. It matters: if a definition could be changed after theorems about it were accepted, those theorems would silently change meaning.

**10. Lines 75, 84, 86, 88, 101, 107. "every statement of the canon has one of four **standings**" / "a further proof is a further declaration with the same statement, and each has a standing of its own" / "a statement is formal when its Lean proof is complete" / "makes formal a proof that is settled and not yet formal"**
Standing is first a property of a statement, then of a proof. "Formal" is defined for a statement, then applied to a proof. "Settled" is defined for a statement, then line 101 speaks of "a proof that is settled". If a second proof is "a further declaration", it must have a different Lean name (line 40: "Lean rejects a second declaration of a name"), which sits uneasily with "every result should have one name" (line 22). I read lines 84-88 three times and still cannot say what the standing of a statement with two proofs is. The completion condition is also phrased four ways: "settled through a formal proof" (24), "settled through a proof that is formal" (86), "formally settled" (221, 259), "formal settlement" (172), beside the state name "formally proved" (243). I take them to be the same condition but had to guess.

**11. Line 71. "the review judges the element on what was read"**
A result taken from the literature enters with a record saying "how much of the source was read". I cannot tell what standing it gets. Does a citation count as a proof in words? Can a statement become settled, and the root "informally proved", on the strength of a cited theorem whose source an AI read in part? The last sentence of the paragraph protects the formal states only.

**12. Lines 8, 9, 30, 311. "None is listed yet" / "six sessions carried it to a formally proved root"**
The table says one statement was carried from start to finish; the next row says no solved problem is listed. Line 30 defines the list as problems "formally proved and ... organized into publishable form", so I infer the odd-number identity is excluded as a test case or for lack of a write-up. The reader has to reconcile the two rows unaided, and "None is listed yet" leaves open whether solved problems exist that are simply not listed.

**13. Lines 158 and 227. "The review can confirm a proof that is complete in Lean only after it has compiled the candidate again in its own session and read the axioms" / "which its guide limits to statements of agreement"**
Throughout, I wanted to know which safeguards are enforced by a program and which are instructions that an AI is trusted to follow. The document is often careful about this (line 142 says outright that sessions "are trusted to follow the guide"; line 162 lists "the checks that a program can decide"). At line 158, "can confirm ... only after" reads as enforcement, but I suspect it is an instruction. At line 227 the wording ("its guide limits") shows it is an instruction, which means an organizer could in fact add any Lean-proved statement without review.

**14. Lines 6, 69, 217. "uses only the allowed axioms" / "The canon refuses an `axiom` declaration" / "an instance may allow more"**
"The allowed axioms" appears at line 6 and is specified only at line 217. A mathematician's first question is whether the user could allow an axiom that trivializes the problem. Line 217 says an instance may allow more than the default three, while line 69 says no axiom may be declared in the canon, so I cannot tell where an additional axiom would come from or whether a completed run reports which axioms it allowed.

**15. Line 80. "A proof was offered, and a review found a gap in it, could not complete its judgment, or has not judged it."**
One standing covers three different situations: a proof with a known error, a proof the review gave up on, and a proof nobody has read. The reason is attached, I gather, but the label alone does not distinguish "found wanting" from "not yet looked at".

## 3. The writing

### The document as a whole

**Writing quality.** The prose is careful, grammatical and exact. Almost every sentence has a real subject doing a real thing, connectives are used correctly, and claims are qualified where they need to be. The document is unusually honest about its limits, and that honesty is its strongest quality for a reader in my position. Its main weakness as writing is density without relief. I count about forty terms introduced in bold, most of them ordinary words given a technical sense (settled, formal, accepted, standing, weight, unit, step, section, board, lease, concern, finding, judge). By line 140 I was holding more vocabulary than I could keep straight, and several of the trust difficulties in part 2 come from terms sliding (items 9, 10, 16).

**Avoidance of AI writing.** The usual marks are almost entirely absent. I found no inflated vocabulary, no rhetorical questions, no slogans in threes, no praise of the system, no decorative bold, no bullet lists where reasoning belongs. Contrasts of the form "X, not Y" occur, but each one I checked carries information (for example line 267, "instructions, not an operating-system sandbox"). What remains is subtler and is a matter of habit more than of any single sentence:

- Counted announcements. "Three considerations shaped this design" (22), "one of four standings" (75), "which is one of two" (56), "A review makes two judgments" (75), "A proof takes one of two forms" (58), "Six roles share the work" (101), "This has two limits" (160), "up to three ways" (219), "it is one of six" (243), "Two considerations can keep" (207), "Two kinds of addition" (18). Any one is fine. A dozen make the scaffolding audible.
- Even weight. The lease mechanism (140) and the Lean broker (190) are told in the same voice, at the same length and with the same care as the statement that no person checks anything (211). Nothing in the prose tells me which paragraphs matter.
- Uniform rhythm. Sentences of twenty-five to forty words, each complete and qualified, follow one another for pages. Short sentences appear mainly as rule statements ("The root never changes." "Nothing is deleted." "The lease has no time limit.").
- Restatement. The two forms of a proof are explained at 16, 58, 67 and 211; the completion condition at 6, 24, 86 and 243; the unverified meaning of the root at 7, 24, 225 and 294. A summary followed by detail justifies two tellings, not four.

**Likeness to human writing.** It reads like a standard or a statute drafted by a careful committee, not like a person telling me about something they built. The clearest sign is that the author never appears. Where a person would write "I", the text says "this repository's author" (180, 207). There is no "we", almost no "you" before the installation section, no sentence about why anyone would want this, and no mathematics beyond one schoolbook identity. The places where a person does show through are the best in the document: the admission that review rounds "were ended after the second, which still found defects of substance" (314), and the remark that the stand-in compiler "has already hidden two defects" (323).

**Natural reading for a human reader.** The "At a glance" table and paragraph 24 give this reader what is needed early, and that is well judged. After that the order works against me. The section I most need, "What counts as established" (192), comes after ninety lines on instances, leases, session hosts and brokers. The opening itself runs seven long paragraphs (14-26) with no heading, and its first sentence repeats the table. A reader on GitHub who is deciding whether to go on meets the same sentence twice in ten lines and then a wall.

### Passages I find wanting

Twenty-two items. Each rewriting is meant to keep the meaning; where I was unsure of the meaning I say so.

**1. Lines 5 and 14.** "A system for autonomous mathematical research in which many AI sessions work together to prove or refute a single mathematical statement." / "do-math is a system for autonomous mathematical research in which many AI sessions work together to prove or refute a single mathematical statement."
The same sentence twice, nine lines apart.
Rewriting of line 14's opening: "do-math takes one mathematical statement and sets many AI sessions to prove it or refute it."

**2. Line 6.** "Only when the statement or its negation has a proof that is complete in Lean, uses only the allowed axioms and has been accepted, together with a proof of everything it rests on."
The tail "together with a proof of everything it rests on" has nothing clear to attach to, and "accepted" has no agent.
Rewriting: "Only when the statement or its negation has a proof that Lean has checked in full, that uses no axiom outside the allowed list, and that an AI review has accepted, and when every statement that proof relies on has such a proof too."

**3. Line 8.** "One small statement has been carried from start to finish by real AI sessions and the real Lean compiler; the tests replace both by stand-ins."
"Carried from start to finish" is vague, and "the tests" are unannounced.
Rewriting: "One real run exists. Real AI sessions and the real Lean compiler took a textbook identity from the bare statement to a complete Lean proof. The automated tests use stand-ins for both the sessions and the compiler."

**4. Line 14.** "and it starts without the conversations of the others"
Unidiomatic, and contradicted on its face by line 154.
Rewriting: "and it starts with no memory of what any other session said or did".

**5. Line 18.** "Finally, a third session, the review, has the candidate examined three times, independently, against the producing session's files, compiles the candidate itself, and then judges each element"
The causative "has ... examined" hides who examines, and four commas interrupt the sentence before its second verb.
Rewriting: "Finally a third session, the review, judges the candidate. Before it does, the candidate is read three separate times against the producing session's files, and the review compiles it. The review then judges each element".

**6. Line 22.** "when two texts state the same fact, nothing stands for the fact itself"
Abstract; I read it three times.
Rewriting: "and when two passages state the same fact, only a careful reader can tell that they do".

**7. Line 24.** "do-math considers a run complete only when the Lean statement fixed at the start, or its negation, is settled through a formal proof: the proof is complete in Lean and depends, through everything in the library that it uses, only on the axioms the run allows, and it has been accepted, as has a proof of every statement it rests on."
Sixty-five words, two terms ("settled", "formal") used before their definitions, and a trailing "as has".
Rewriting: "A run is complete only when the Lean statement fixed at the start, or its negation, has a proof with three properties. Lean has checked it in full. Neither it nor anything it uses in the library depends on an axiom the run does not allow. And an AI review has accepted it, along with a proof of every statement it rests on."

**8. Lines 26 and 30.** "The rest of this document lists the solved problems" / "This section lists the problems that do-math has formally proved and that have been organized into publishable form. None is listed yet."
The document promises a list and delivers an empty one; one proves statements, not problems; "organized into publishable form" is vague.
Rewriting of line 30: "This section will list the statements that do-math has formally proved or refuted and that have been written up. There are none yet. The one statement proved so far is the test case described under 'Repository layout, verification and tests'." (The last sentence is my inference from line 311.)

**9. Line 40.** "A definition is referred to by its Lean name, and Lean rejects a second declaration of a name, so the canon keeps no separate glossary."
The conclusion answers a question no new reader has asked. It reads like a note about a design that was dropped.
Rewriting: "A definition is referred to by its Lean name, and Lean rejects a second declaration of a name, so a name always means one thing."

**10. Line 56.** "A record also gives the element's **weight**, which is one of two."
Stiff, and the same construction returns at line 243 ("and it is one of six").
Rewriting: "A record also says whether the element is a unit or a step. This is called its **weight**."

**11. Line 101.** "a **formalizer** makes formal a proof that is settled and not yet formal, usually by completing in Lean a proof that was accepted in words"
"Makes formal a proof that is settled and not yet formal" is awkward and uses "settled" of a proof.
Rewriting: "a **formalizer** writes the complete Lean proof of a settled statement whose accepted proof is so far only in words".

**12. Line 107.** "One settled statement that the root, or a settled refutation of the root, rests on, whose accepted proof is not yet formal and names only statements that already have formal proofs"
Rewriting: "One settled statement on which the root (or a settled refutation of it) depends. Its accepted proof is not yet formal, and every statement that proof names already has a formal proof."

**13. Line 146.** "or when the limit is reached, in which case the end is authorized without a decision from the session"
Bureaucratic passive with no agent.

**14. Line 174.** "This is kept by approach because sessions approach the same statement in the same ways and stop in the same places, so that what is learned about the course of the work does not grow with the number of sessions."
"So that" seems to depend on "because" when it depends on "kept by approach"; "approach" is both noun and verb in six words.

This gives no reason; it restates the condition.
Rewriting, if I have the meaning: "The reason is that the research should end with the shorter proof, and a statement whose proof has been accepted is one that no session returns to."

**18. Line 219.** "a program called the **judge** checked the proof from outside the structural index"
Rewriting: "a program called the **judge** checked the proof again without relying on the structural index".
