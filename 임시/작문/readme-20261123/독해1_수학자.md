# Reading 1: a research mathematician reads `README.md`

I read `C:\math\README.md` from line 1 to line 332, in order, and nothing else. I did not open any other file of the repository, any memory file, any guide, any source code or the Git history. Two shell commands were run: one counted words, bold terms and one recurring verb in `README.md` itself, and one listed the names of the files in the output folder to confirm that the folder exists. I opened none of those files.

The reader I stood in for knows mathematics and knows in general terms what a proof assistant is. This reader has not used Lean, does not know how AI command-line tools or multi-agent systems work, and wants to judge what the results of this system can be trusted for.

Line numbers are those of the file as I read it. Quoted words are exact.

## 1. What I understood

This part was written first and has not been adjusted afterwards. The points are in the order of importance that the document itself seems to give them, which I took from the summary table at the top, from the order of the opening paragraphs, and from what the document repeats.

**1. What the system is.** do-math is software that has many separate AI conversations ("sessions") work on one mathematical statement, to prove it or to refute it. The sessions do not remember one another. They pass work on as files, and whatever is to last is put into a single library written in Lean 4, where each item has a formal Lean declaration and a prose record beside it. A person supplies the statement; an AI conversation called the operator helps to set the run up; a program called the runner then starts sessions for as long as the run goes on. (Lines 5, 13, 15.)

**2. When a run counts as finished.** Only when the statement that was fixed in Lean before the start, or its negation, has a proof that is complete in Lean, depends only on a list of allowed axioms, and has been accepted by a review. (Lines 6, 23, 76, 224.)

**3. What a finished run does not show.** It does not show that the Lean statement says what the user had in mind. The user confirms that before the run, with the operator's explanation, and nothing checks it again. Every review is made by an AI session. No person referees anything unless the user arranges it separately. (Lines 7, 23, 204-208.)

**4. No solved problem is on offer.** The list of solved problems is empty. Far below, the document says that the only run carried from start to finish by real AI sessions and the real compiler proved that the sum of the first n odd numbers is n squared, and that a larger run that uses Mathlib began on 22 November 2026 and is still going. (Lines 8, 29, 287-289.)

**5. How one addition to the library is made.** Three different sessions handle it. The first works on the mathematics and keeps everything in its own files. The second, the peer, takes that work over, continues it where it can, and writes the proposed change to the library, called the candidate. The third, the review, has three sub-reviewers read the candidate, compiles it, and judges each item: whether the Lean statement says what was meant, whether the proof is correct, and whether a correct proof should be accepted. (Lines 5, 17, 135-141.)

**6. Publication does not mean correctness.** If the review finds anything worth keeping, the candidate goes into the library together with the review's judgment of each item. An item whose proof the review could not confirm goes in too, marked as unconfirmed, so that a later session can repair it. The statement of an item never changes after it is in; proofs and records can be replaced; a later review can withdraw the confirmation of a proof. (Lines 19, 145-147, 175, 216-218.)

**7. A proof has one of two forms.** Either it is complete in Lean, or it is written in words in the record while the Lean file lists the statements the argument uses and then leaves the proof open with `sorry`. In the second form Lean checks only that the listed statements exist and are applied in a way that type-checks. The argument is prose, and an AI review judges it. (Lines 15, 57, 192.)

**8. Why it was built this way.** Three reasons are given. The library has to serve as the memory of a run, because the hundreds of conversations do not remember each other. Work is judged by a session that did not produce it, and since the judgment is stored with the work, imperfect work can be kept without being mistaken for established work. And a result written in Lean has one name that later proofs must cite, which a result written in prose does not have. (Line 21.)

**9. The labels on a statement and what each is worth.** A statement has one of four standings: no proof; proof not confirmed; correct but held back; accepted. It is "settled" when its proof is accepted and so is everything beneath it, all the way down. It is "formal" when its Lean proof is complete and depends only on allowed axioms, again all the way down. Settled is a verdict of AI reviews; formal is a verdict of Lean. Neither says that the statement means what was intended, and settled does not mean that a person or Lean checked the argument. A correct proof can be held back because it can clearly be simplified or because part of it is a large computation with no explanation. (Lines 65-76, 175-194.)

**10. What stands behind a formal proof.** The review recompiles and reads the axioms; the runner recompiles the whole library at publication; and with Lean 4.35 or later a separate program, the judge, re-derives the axioms from an export and replays the declarations through Lean's kernel. At the end the judge also compares the proved root with the root as first committed. The default allowed axioms are `propext`, `Classical.choice` and `Quot.sound`. (Lines 196-202.)

**11. How the sessions divide the work.** There are six roles: attempt, explorer, formalizer, peer, review, organizer. Nobody assigns an attempt its task. It reads the "frontier", a computed list of what the root currently rests on that is not yet settled, and chooses. It registers what it has chosen so that others can see it, and a per-statement lock (the "lease") makes these registrations happen one at a time. Compliance is mostly on trust. (Lines 82-125.)

**12. Things kept besides theorems.** The library also keeps "questions" (things to be understood that are not statements), a running text of what is understood about each, and for each unproved statement a list of the approaches that were tried and where each stopped. (Lines 149-159.)

**13. Unreviewed parts.** Two kinds of item receive no review: what the user supplied at the start, and the statements that an organizer adds to say that two definitions or two statements agree. For these the document says that Lean's check of the proof takes the place of a review and that the meaning of the statement rests on whoever wrote it. (Lines 169, 208.)

**14. How to read a run's results.** Start with `knowledge/frontier.md`, then `knowledge/index.md`, then the files under `canon/`. (Lines 220-240.)

**15. How to run it, and what it does on the machine.** It needs Python, Git, Lean 4, and the Claude Code or Codex command-line programs. Sessions run unattended with full file and command access under the user's account, with permission prompts off, with web search, and with no cap on time, sessions or cost. All recorded runs were on Windows. (Lines 242-277.)

**16. How far the software itself has been checked.** One toy run end to end; a test suite of 763 functions that uses a stand-in for Lean and scripted stand-ins for the AI sessions and has not been run as a whole since the last change; two rounds of review of the guides and code, the second of which still found substantial defects, so that more are expected. (Lines 279-299.)

**17. The rest.** Other tools in the repository, development skills, language, citation, licence. (Lines 301-331.)

**What I take away as this reader.** The system has, by its own account, no mathematical result to show yet. If it one day reports a run as complete, I may trust that Lean accepted a proof of the formal statement from the standard axioms, to the extent that I trust the Lean kernel and the integrity of the compilation on the user's machine. I must check for myself that the formal statement, with all the definitions under it, says what the informal problem says. Anything short of "formally proved" is AI-reviewed prose, and I should read it as such.

## 2. Where I had difficulty

I read this twice. The next sentence makes clear that it means that no session sees what another session said; on first reading it sounded as though the sessions do not talk to each other, which is a different claim.

## 3. The writing

### The document as a whole

**Writing quality.** The prose is careful and plain. Almost every sentence has a concrete subject and an active verb, and I could nearly always tell who does what. Limits and failures are stated in the same voice as capabilities, without softening, and for a reader in my position this is the most valuable quality of the document: I believed it more for lines 7, 192, 248 and 285-299 than for anything else in it. The weaknesses are of another kind. The document is 10,124 words long and defines 41 terms in bold, several of them ordinary words given a special sense (attempt, review, section, record, standing, element, statement, judge, index, board). It gives no example of any of them. I never see one element: one Lean statement, its record, and a proof in words with the Lean lines that name what it uses. The run on the sum of odd numbers (lines 272, 287) could supply one. Without it I had to hold the whole vocabulary in the abstract, and items D4, D5, D19 and D22 would all have been answered by a single example.

**Natural reading for a human reader.** The summary table gives me the essentials in four rows, and I could have stopped there with a correct picture. The prose opening that follows (lines 13-23) repeats the table, in one case word for word, and puts the mechanism before the statement of what a result is worth, which arrives in the sixth paragraph. The long section "How the research is organized" (lines 31-171) then stands between the opening and "What counts as established" (line 173), the section a reader who wants to judge trust is looking for. About half of the document is therefore mechanism, and much of it (leases, session hosts, the order of launches, the broker's budgets) I did not need and could not evaluate. It reads as a specification. I report this as what happened to me as a reader; I do not know for which other readers those passages are written.

**Likeness to human writing, and avoidance of AI writing.** The usual marks of machine prose are mostly absent. There is no promotion, there are no decorative triads, no bullets with bold lead-ins, no closing summaries, no exclamation, and almost no empty hedging. What I did notice is the following.

- A very even register. Sentence after sentence is a medium-length declarative, and paragraph after paragraph closes every loop it opens. A human author of a front page usually relaxes somewhere, with an example, an aside or a "for instance, in the run on ..."; this text never does.
- Short maxims built on a contrast: "A review judges and does not gate" (145), "Sessions coordinate through information rather than enforcement" (125), "A published element is not a certificate" (175), "Nobody writes it" (78). One or two are effective. As a repeated device they read as a mannerism, and two of them say more than the following sentences support (W8, W9).
- One verb used as a tic. "Stand", "stands" or "stood" occurs about seventeen times in the special senses "exist", "be in the library" or "underlie" (lines 15, 17, 39, 137, 147 three times, 169, 179, 200, 208 twice, 222, among others).
- Abstract nouns as labels where a plain statement would serve: "One is continuity", "Another is independent judgment" (21).
- English that is correct in grammar but not idiomatic, which gives the feel of a translation: "One small research was run" (287), "The second is made only of a correct proof" (65), "Of a correct proof, the review decides" (188), "the proof the research stops at" (17), "an assessment or an organization" (131).

My overall impression is of a text written with great care for exactness by someone, or something, more concerned to be unambiguous than to be read with ease. It does not read like marketing copy produced by a model. It also does not read quite like a mathematician or a programmer describing their own system; it reads like a statute.

### Passages I found wanting

Twenty-three items. Each rewriting is meant to keep the meaning; where I had to guess the meaning, I say so.

**W1. Lines 5 and 13.** "A system for autonomous mathematical research in which many AI sessions work together to prove or refute a single mathematical statement." / "do-math is a system for autonomous mathematical research in which many AI sessions work together to prove or refute a single mathematical statement."
The same sentence twice within nine lines. Lines 15 and 23 likewise repeat the second and third rows of the table. A reader notices and begins to skim.
Rewriting of the start of line 13: "The sessions do not see one another's conversations. Each is a new conversation with an AI command-line tool (Claude Code or Codex); what it produces is handed on as files, ..."

**W2. Lines 287, 288 and 289.** "One small research was run from start to finish"; "The scripted research that the tests use"; "A research that imports Mathlib has been running since 22 November 2026."
"Research" is not a count noun in English. The document's own word is "run".

**W3. Throughout; for example line 147.** "One invariant stands behind publication"; "whatever a waiting candidate rests on still stands as it stood"; "A proof that replaces another stands where the old proof stood".
Three uses of one verb in three senses within one paragraph, and the same verb about seventeen times in the document.

**W5. Line 21.** "A third is that a result should be one thing that later work can name. A result kept in prose restates its notation wherever it is written down, and the same fact written in two accounts is two assertions with nothing that stands for the fact itself."
Abstract to the point of obscurity (D13). The paragraph's other two reasons are concrete.
Rewriting, on my reading of the meaning: "A third is that each result should have one name. A result kept in prose has to be restated, notation and all, each time it is used, and nothing shows that two restatements are the same result. A result stated in Lean has one name, a proof that uses it must cite that name, and Lean checks the citation."

## 4. What I could not determine

**What I would still want to know.**

1. Whether the system has produced any mathematics beyond the toy run. The document says that a run with Mathlib is going, and it does not say on what statement or with what outcome so far. I take "None is listed yet" to mean that there is no non-trivial result, but I am inferring that.
2. Which AI models do the work. The document names the tools (Claude Code, Codex) and mentions "one Claude model" (line 287); it never names a model.
3. How reliable an AI review is. No figure or example is given of a review that accepted a wrong proof or rejected a right one. Since "settled" rests entirely on these reviews, I cannot calibrate the word. The document may be silent because nothing has been measured, and lines 285-290 suggest so, but it does not say this about the reviews in particular.
4. What exactly Lean checks in a proof written in words (D4), and who checks that the prose argument uses only the statements that the Lean source names (D5).
5. What standing a theorem cited from the literature receives, and whether the root can be reported as "informally proved" while resting on a cited result (D20).
6. Whether a complete Lean proof of the root that a review finds correct but "held back" (because it could be simpler) leaves the run incomplete. Lines 76 and 188 together imply that it does. I would want that stated, because it means that completion depends on an AI's taste as well as on Lean.
7. What standing the unreviewed items have (user-supplied proofs, organizer's statements), and whether the completion condition can be met through them (D14).
8. What becomes of a review's judgment that a Lean statement does not say what its record says (D31).
9. How serious the missing sandbox on Windows is, given that every recorded run was on Windows (D42).
10. Whether a review runs a computation again when a proof in words rests on one. Line 212 says that a later session "can"; it does not say that anyone does.
11. Whether the sessions' web search (line 248) is recorded, so that a reader can tell whether a proof was found or looked up. Line 61 covers results that a session declares as taken from the literature; it does not cover undeclared use.
12. In the one complete run all six sessions used one Claude model (line 287). The separation of models between producer and reviewer described at line 143 was therefore not in effect in the only end-to-end evidence. The document states both facts and does not connect them.
13. What "the paper" is and what "organized into publishable form" requires (D15, D44).
