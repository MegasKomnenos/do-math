# Fact check of `README.md` lines 135 to 240 against the do-math sources

This file compares the factual statements in lines 135 to 240 of `C:\math\README.md` with the skill folder `C:\math\.claude\skills\do-math`, so that the README can be corrected before it is published. It was made on 23 November 2026 from the working tree as it stood then. Nothing was run: every verdict rests on a guide or a Python file read at the place cited.

Source locations are written `path:line` with the path taken from `C:\math\.claude\skills\do-math\`. README locations are written `README:line`.

Three things about how the verdicts were reached bear on how to read them.

- A statement counts as `overstated` when any guide or the code attaches a condition or an exception that the README drops, even where another guide gives the same short form as the README. Where that is the case, the entry names the guide that carries the short form.
- Several things the README reports are asked of a session by its guide and are checked by no program. That is not an error of the README, which mostly says "is asked" or names the review as the one who judges. The places where it matters for what a reader may rely on are listed at the end of part 3.
- What `leanexport` and `lake comparator` do inside was taken from the guides and from the commands `runtime/judge.py` builds. It was not checked against Lean itself.

### Findings that bear on what a result certifies

**1. `README:182`, the "Accepted" row of the table.** `overstated`

> | Accepted | A review confirmed the proof and accepted it |

A proof can stand as accepted although no review has judged it. This holds for a complete Lean proof supplied when the instance was created and for every statement an organizer adds.

- `reference/common.md:158`: "The elements the instance began with were supplied with the root and no review has judged them. Among these, a statement whose Lean proof is complete stands as accepted, since Lean has checked that proof, and one that has only a written proof stands as not confirmed until a review judges it."
- `reference/common.md:184`: "Lean checks that proof, so the element enters without review, with its proof accepted."
- `runtime/knowledge.py:232-235`: for a statement without a verdict, `return 'accepted' if element['lean_proof'] == 'complete' else 'not_confirmed'`.
- `runtime/knowledge.py:173-176`: every element in an organizer's `applied['added']` receives `'correct': 'confirmed', 'accepted': True` with the reason "Proved in Lean from the allowed axioms; added by the organizer."

The README says the same itself at `README:208`, so the table cell and that paragraph disagree. Because the "Settled" row is built on "accepted", a settled statement can likewise rest on elements that no review judged.

Corrected cell: "A review confirmed the proof and accepted it; or the element was supplied when the instance was created or added by an organizer, its Lean proof is complete, and no review judged it".

**2. `README:192`.** `overstated`

The sentence is about any proof written in a record. Two conditions are dropped.

First, a written proof may have been judged by no review. The standing "proof not confirmed" covers that case, as the README's own table says at `README:180`.

- `reference/common.md:154`: "A proof was offered, and review found a gap in it, could not complete its judgment, or has not judged it."
- `reference/common.md:158`: "one that has only a written proof stands as not confirmed until a review judges it".

Second, on a Codex session there are no sub-reviewers. The README says so at `README:139` and drops it here.

- `roles/review.md:39`: "If your session cannot delegate, as a Codex session cannot, perform the three examinations yourself as separate complete passes with those three emphases, each written up before the next begins, and say in the feedback that the sub-reviews were your own passes."

Corrected sentence: "A review session has, for a proof whose standing is 'correct, held back' or 'accepted': it read the candidate against the producing session's retained work, after three examinations made independently of one another, by three sub-reviewers on Claude Code and by the reviewer's own three separate passes on Codex. A written proof whose standing is 'proof not confirmed' may not have been judged by any review."

**3. `README:208`.** `overstated`

> Two kinds of element have received no such judgment: the definitions and proofs that the user supplied with the root when the instance was created, and the statements of agreement that an organizer adds.

The second kind is too narrow. An organizer also adds derivations of one statement from another, which enter as accepted without a review, and the limit on what an organizer adds is its guide's and not a program's.

- `SKILL.md:40`: "The other is a statement an organizer adds, saying that two definitions or two statements agree, or deriving a statement from another that agrees with it: its proof has to be complete in Lean from the allowed axioms, which the runner checks again when it publishes the organizer's change, and it enters as accepted."
- `reference/organizer-output.md:42`: "A derivation you add as a declaration of its own, another proof of an existing statement with `proves:` in its record, is an added element: like every statement you add, it needs a proof that is complete in Lean from the allowed axioms, and it then enters as accepted."
- `runtime/canon.py:1113-1116`: the one test applied to a statement an organizer adds is that its axioms lie within the allowed list. Nothing tests that the statement is one of agreement, and nothing refuses a definition in an organizer's change.
- `roles/organizer.md:23`: "No review reads this record, so give it the care a reviewer would ask for."

The first kind is also narrower than the source, which speaks of "the elements the instance began with" (`reference/common.md:158`). Those can include statements as well as definitions and proofs.

Corrected sentence: "Two kinds of element have received no such judgment: the elements that were supplied with the root when the instance was created, and the elements that an organizer adds, which its guide limits to statements of agreement and to derivations of one statement from another that agrees with it."

One point about the sentence that follows at `README:208`, "For both, Lean's check of a complete proof stands where a review's judgment of the proof would stand". I read this from the code and did not run it. For an organizer's statement "complete" is tested as "proved from the allowed axioms" (`runtime/canon.py:1113-1116`). For the first elements it is tested only as "free of `sorry`": `init` calls the same check without the organizer flag (`runtime/runner.py:150-151`), `lean_proof` is `'complete'` whenever `sorryAx` is absent (`runtime/canon.py:796-797`), and an axiom that Lean generated "is not refused, and what rests on it is simply not proved from the allowed axioms" (`runtime/canon.py:1080-1081`). A first element whose proof uses `native_decide` would therefore stand as accepted and not formal.

**4. `README:145` and `README:200`, the build at publication.** `overstated`, two statements

> The runner applies the candidate to a copy of the library, without the proof replacements that the review declined, and compiles every module.

> The runner compiles the whole library again at publication.

The runner asks the broker to build every module, and only when the candidate changes a Lean file. The broker compiles a module only if its cache holds no compiled files for it. The peer's preparation compiled the candidate's modules through the same broker, so where the canon beneath them has not changed since, the publication build takes them from the cache as well; this last step is my inference from the cache rule and was not observed in a run. The review's compile is the one that is forced to be fresh.

- `reference/operations.md:467`: "When that changes a Lean file, it builds every module of the library through the broker and extracts the structural index of the modules that changed and of every module that imports one of them, directly or through others; a candidate that changes only written files needs no build." And further on: "A module whose source and whose imports' compiled output are unchanged comes from the broker's cache, so most of a build is usually reuse."
- `runtime/runner.py:782-787`: the build is started only `if changed or removed`, by `start_build(...)` without the `fresh` argument; `runtime/canon.py:885` gives that argument the default `fresh=False`.
- `reference/lean.md:151`: "A module that the broker compiled successfully is kept in the instance's cache, and a later build, by any session, that needs the same module takes its compiled files from there."
- `reference/lean.md:159`: "`build --fresh-targets` compiles the targets even when the cache holds them, and takes only the modules they import from the cache. Review's compile of a candidate uses it, through `commands.verify`, so that the compile of the changed modules is review's own."
- `runtime/lean_broker.py:936-937`, which is outside the list of sources and was read only to confirm: "otherwise, or when the module is a target of --fresh-targets, a job compiles it. So no module is compiled while an entry with its key exists".

What the publication build adds is that the candidate builds on the canon as it is at that moment. It is not a second independent compile of the proof. The README itself says at `README:171` that the broker does not compile an unchanged module twice.

Corrected sentence for `README:145`: "The runner applies the candidate to a copy of the library, without the proof replacements that the review declined, and, when the candidate changes a Lean file, builds every module through the broker, which compiles the modules its cache does not already hold."

Corrected sentence for `README:200`: "The runner builds the whole library again at publication, on the canon as it is at that moment; the broker takes from its cache every module it has already compiled from the same source and imports, which can include the candidate's own modules, so this build shows that the candidate still fits the canon and is not in every case a second compile of the proof."

## 3. Disagreements between a guide and the code that bear on a README sentence

1. **Whether a proof is replaced only under a section** (`README:137`). `reference/common.md:263` says "a candidate can replace the proof of a statement only when its pipeline holds a section on that statement, the whole of it or a part." The transport check asks for no section when the statement is settled (`runtime/check.py:157-166`), and `reference/change-format.md:104` agrees with the code. The README follows the common guide; see entry 8.

2. **What "proof not confirmed" covers** (`README:180`). `reference/operations.md:350` says "\"Proof not confirmed\" means a proof was offered and review found a gap or could not complete its judgment; the reason says which." The code also gives this standing to a proof no review has judged (`runtime/knowledge.py:232-238`), as `reference/common.md:154` says. The README follows the code and is right.

3. **Which statements stand as accepted without a verdict** (`README:208`). `reference/common.md:158` says of the rule for complete Lean proofs "This holds for those first elements alone." In the code the rule applies to any statement that carries no verdict (`runtime/knowledge.py:226-238`). A change brought by a review always leaves a verdict (`runtime/knowledge.py:121-132`), and so does an organizer's addition, but an organizer's retirement of an alternative proof that had no verdict removes the verdict of the statement's own declaration (`runtime/knowledge.py:177-183`). I did not trace whether that path can occur in a real instance.

4. **When a formalizer is launched** (`README:167`). `reference/common.md:172` and `reference/operations.md:461` give the condition without mentioning contested statements. The code skips a contested statement: `if elements[statement]['statement_formal'] or elements[statement]['contested']: continue` (`runtime/knowledge.py:460`). The README's sentence follows the guides.

5. **Whether a published change always holds the review's compile** (`README:237`). `reference/operations.md:335` and `reference/review-output.md:114` list `verify.json` among the files of a published change without a condition. The runner copies it only when the review ran `commands.verify`: `if verified.is_file(): shutil.copyfile(verified, stage / 'verify.json')` (`runtime/runner.py:962-964`). A change whose candidate held no complete Lean proof can therefore lack it. I left the README row as supported, because the guides say what it says.

The following are not disagreements. They are things the README reports that a guide asks of a session and that no program checks, at places where the difference affects what a reader may rely on.

- **The three sub-reviews** (`README:139`, `README:192`). `roles/review.md:35` and `roles/review.md:169` require them. The transport check of an assessment, `assessment_check` at `runtime/check.py:248-329`, contains no test that the three reports exist.
- **The review's reading of the axioms** (`README:141`, `README:200`). `reference/review-output.md:106`: "The check does not read the axioms; that is your judgment". This does not weaken what "formal" means, because the runner computes it from the axioms itself (`reference/review-output.md:80`, `runtime/knowledge.py:268`).
- **The user's confirmation of the root** (`README:206`). `reference/operations.md:159` tells the operator "Do not start the runner before the user has confirmed." The `start` command tests nothing of the kind (`runtime/runner.py:1513-1536`).
- **What a record of a computed result says** (`README:212`). `reference/records.md:55` states what the account of a computation holds. It is the peer's to write and the review's to judge, and no machine check reads it.
