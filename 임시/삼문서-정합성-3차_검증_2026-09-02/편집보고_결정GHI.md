## 판단이 필요했던 자리의 근거

1. **조각 11의 상태 표기.** 지시는 4.3절이 그 상태를 적은 축자와 맞추라 했다. 4.3절(479행)은 「request ref의 `completion_kind`으로 `output_sealed`와 `execution_incomplete`를 구분한다」, 「`execution_incomplete`는 읽지 못한 입력 …」처럼 `execution_incomplete`만 쓴다. 따라서 조각 11의 `completion_kind=execution_incomplete`를 `execution_incomplete`로 적었다. 19.5·19.7·19.8절이 `completion_kind=execution_incomplete` 형태를 쓰지만 지시가 4.3절을 기준으로 지정했다.
2. **조각 3의 칸 맞춤.** 목록은 접두사 형태를 11칸까지 채워 설명을 12번째 칸에 맞춘다(`RI-<ULID>` 9자 + 공백 2, `F-<ULID>` 8자 + 공백 3, `OUT-<ULID>` 10자 + 공백 1; 11자 이상은 공백 1). `SV-<ULID>`는 9자이므로 공백 2를 두었고, 조각 3의 축자와 같다. 조각 4의 두 행은 `OO-E-<ULID>-OG-<ULID> 관찰 의무`처럼 긴 형태의 공백 1 규칙을 따른다.
3. **조각 4의 ULID 표기.** 결정 H 3항은 `OP-E-<execution ULID>`·`OP-S-<supervisor ULID>`로 적지만 2.1절 목록은 `<ULID>` 자리표시자를 쓰는 자리이므로(`OO-E-<ULID>-OG-<ULID>`, 기존 `OP-E-<ULID>-…`) 조각 4의 축자를 그대로 썼다. 두 ULID의 유래는 15.3절(1651행)이 적는다.
4. **조각 13의 삽입 위치.** 「이 목록의 「분할 종결」은 …」 문단(1719행) 뒤에 빈 줄 하나와 새 문단을 넣었다. 뒤따르는 「심사 판정은 …」 문단 앞의 기존 빈 줄이 그대로 남아 연속 빈 줄이 생기지 않았다(awk 검사 결과 0).
5. **잔재 전수 검색.** `OP-E-<ULID>-R-<run OID>`(구형 단일 형태), 「실행마다 운영 사례」, 「각 실행에 … 운영 사례」, 「execution마다」, `operations-state/2`, `operational-review/3`, `canon-entry/2`, 「같은 실행·기준 run OID」·「같은 실행·run OID」는 편집 뒤 0건이다. 「기준 run OID」는 네 자리에 남는다.
   - 15.3절 1649행 「`monitor_stopped` 사건에 기준 run OID, …」: 감시기가 봉인하는 실행 하나의 감시 원장 사건이며 운영 사례의 일반 서술이 아니다. 그대로 둔다.
   - 15.4절 1655행 「평가나 의무 처분을 적용하기 직전에 기준 run OID가 여전히 현재인지」: 관찰 평가·의무 처분의 낡음 검사이며 실행 단위 기구다. 그대로 둔다.
