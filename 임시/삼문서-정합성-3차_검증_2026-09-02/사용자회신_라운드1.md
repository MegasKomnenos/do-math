# 라운드 1·2 상신에 대한 사용자 회신 (사용자 확정 기록, 2026-09-03)

이 파일은 3차 검증런 라운드 1의 상신 R1-15·R1-17과 라운드 2의 상신 R2-10에 사용자가 내린 결정의 확정 문면이다. 항목 원문은 `_상신원문_라운드1.md`·`_상신원문_라운드2.md`에 있다. 라운드 2 이후의 수리는 이 결정을 승계 근거로 인용해 조각으로 닫는다. 아래 결정은 새 선택 없이 남은 자리에 적용할 방향이며, 이 문면이 정하지 않은 세부를 새로 정해야 하면 그것은 상신 제안이다.

## 결정 F — R1-15: 지식 기록 여섯 종류의 `lifecycle.value` 허용 값

사용자 회신 원문: 「상신 1: 추천안대로.」

확정 내용 (상신문의 가-변형):

1. F 객체·F 종류 정의·자료·근거·관계·관계 종류 정의·공용 연구 기억 여섯 종류의 `lifecycle.value` 허용 값을 연구 맥락(6.3절)과 같은 3값 `active`·`superseded`·`withdrawn`으로 닫는다. 소유 절인 6.4·6.6·6.7·6.8절에 6.3절 648행과 같은 형태의 문장을 둔다.
2. 6.7절의 「생성·대체·비활성 이력」을 「생성·대체·철회 이력」으로 고쳐 관계의 상태 낱말과 값을 맞춘다.
3. 종류별로 다른 어휘(선택지 나)와 스키마 단독 소유(선택지 다)는 채택하지 않았다.

## 결정 G — R1-17: 감독기 소실 운영 사례의 단위

사용자 회신 원문: 「감독기 소실 때 영향을 받은 execution마다 운영 사례를 열게 하는 대신, 그 감독기에 대해 운영 사례를 열고 그 사례에서 영향을 받은 execution 모두에 대해 다루게 하는건 어때?」 → 세션이 아래 1~5의 형태를 제안 → 사용자 회신 「그 형태로 확정. 라운드 2 진행해」.

확정 내용:

1. **사례 ID의 대상 분절 일반화.** 2.1절과 15.3절의 운영 사례 ID를 `OP-<대상>-R-<기준 OID>-T-<trigger 토큰>`으로 일반화한다. 대상은 `E-<execution ULID>`(실행 사례) 또는 `S-<supervisor 인스턴스 ID>`(감독기 사례)다. 기준 OID는 실행 사례에서 그 실행의 기준 run OID, 감독기 사례에서 소실 직전의 supervisor 상태 사슬(`refs/do-math/supervisor/<instance_id>`) OID다. 15.3절의 「같은 실행·기준 run OID·trigger에서 하나만 열리도록」과 2.1절의 같은 문장은 「같은 대상·기준 OID·trigger에서 하나만」이 된다. 결정론 복합 ID로 조건부 ref 생성에 성공한 하나만 여는 원리(15.3절, O13)는 그대로다.
2. **점검 기록.** 16.2절의 「기준 run OID」를 「기준 OID(실행 사례는 run OID, 감독기 사례는 supervisor OID)」로 넓히고, 감독기 사례의 기록에 영향받은 실행 목록과 실행별 처분을 둔다.
3. **처분.** 감독기 사례 안에서 연구 작업자 실행은 16.3절의 기존 처분 목록(점검자 직접 확정 / 운영 처분 심사 필요 / 사용자 권한 필요)을 그대로 받는다. 비작업 역할 실행은 4.3절이 이미 정한 경로(해당 요청을 `execution_incomplete`로 끝내고 새 request·execution·output ID로 재시도)를 점검자가 직접 확정하는 저영향 처분으로 받는다.
4. **현재성.** 16.4절에서 감독기 사례 자체는 기준 supervisor OID로 현재성을 고정하고, 그 안의 실행별 처분은 각 실행의 run OID로 고정한다.
5. **문면과 벡터.** 13.3절·22.6절·26.4절 E10의 「영향을 받은 execution마다(각 실행에) 운영 사례를 연다」를 「소실된 감독기에 대해 15.2절의 프로세스 감독기 소실 조건으로 운영 사례 하나를 열고, 영향받은 실행 전건을 그 사례에서 다룬다」로 바꾼다. 26.5절에 감독기 사례 벡터(같은 감독기·같은 supervisor OID·같은 trigger로 새 감독기가 재시도해도 사례 하나, 기록에 영향받은 실행 전건 열거)를 더한다. 스키마 판본은 23.3절대로 `do-math/operations-state/2 → 3`, `do-math/operational-review/3 → 4`로 올리고 29절 레지스트리를 맞춘다.
6. **supervisor 인스턴스 ID.** 12.3절의 supervisor 인스턴스를 ref 이름에 쓸 수 있도록, 감독기 시작 시 ULID를 부여해 `state.json`에 기록하는 문장을 12.3절에 둔다. 이 문장은 결정 G의 필연적 귀결이며 새 결정이 아니다. 2.1절 ID 목록의 접두사 규율(종류 접두사와 ULID)과 정합하게 적는다.
7. 선택지 1(사례를 연구 작업자 실행으로 한정)·2·3은 채택하지 않았다. 기존 실행 사례(`E-` 대상)의 기구는 유지된다.

이 결정 G는 M-0110의 결정 B(운영 사례 ID를 사례 키에서 나오는 결정론 복합 ID로)를 대체하지 않고 그 위에 대상 분절을 더한 것이다.

## 결정 H — R2-10: supervisor 인스턴스 ID의 접두사 (결정 G 6항의 보충)

사용자 회신 원문: 「라로 확정. 라운드 3 진행해」

확정 내용 (상신문의 선택지 라):

1. 운영 사례 ID `OP-<대상>-R-<기준 OID>-T-<trigger 토큰>`의 대상 분절에서 `E`·`S`는 종류 접두사가 아니라 대상 종류 토큰이다. `E`는 실행, `S`는 프로세스 감독기 인스턴스를 가리킨다.
2. supervisor 인스턴스 ID는 `SV-<ULID>`로 2.1절 ID 목록에 등재한다(`SV-<ULID>  프로세스 감독기 인스턴스`). 감독기 시작 시 부여해 12.3절 `state.json`에 기록한다(결정 G 6항).
3. 대상 분절에는 그 ID에서 종류 접두사를 제거한 ULID 부분만 싣는다. 실행 사례는 `OP-E-<execution ULID>-R-<run OID>-T-<trigger 토큰>`(현행과 같음), 감독기 사례는 `OP-S-<supervisor ULID>-R-<supervisor OID>-T-<trigger 토큰>`이다. 15.3절이 실행 사례에 이미 쓰는 「`execution_id`에서 종류 접두사를 제거한 값」 규약과 14.5절 관찰 의무 ID의 규약을 그대로 확장한 것이다.
4. 기존 `S-<ULID>  하위 AI 논리 세션` 표기는 바꾸지 않는다. 선택지 가(`S-SV-` 이중 표지)·나(논리 세션 접두사 이동)·다(접두사 공유)는 채택하지 않았다.
5. 결정 G 1항의 `S-<supervisor 인스턴스 ID>`는 이 결정에 따라 「대상 종류 토큰 `S` + supervisor 인스턴스 ID의 ULID 부분」으로 읽는다.
