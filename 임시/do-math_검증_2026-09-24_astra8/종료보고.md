# do-math 전면 검증 종료보고

## 종료 수치와 종료 항

- 1라운드에서 수리 항목 41건을 제기하고, 본표 40행을 적용으로 닫았다.
- 공식 심사 대상은 단독 27건과 병합 7건, 합계 34건이었다. 심사자 세 기가 각각 34건 전부를 판정했다.
- 조각은 파일 한 곳의 연속된 행 구간과 그 자리를 대신할 완성 문면의 짝이다. 세 심사자가 모두 승인했고 처분도 「수리한다」로 확정된 29건에 한해 공식 적용으로 조각 86개를 42파일에 반영했다. 병합 구성 항목까지 본표 36행이다.
- 사용자의 후속 지시에 따라 네 항목을 직접 재검토·수리·적용해 본표 적용은 40행이 됐다. 남은 한 기각 항목은 지적이 현행 코드와 맞지 않았다.
- 종료 항: verify-rounds SKILL.md §7의 라운드 판정 순서 3항. 사용자 후속 지시로 라운드_하한과 라운드_상한을 1로 확정했고, 1라운드에서 상한에 닿았다. 이 종료는 결함이 더 없다는 판정이 아니다.

## 상신·무처분 잔여와 기각 보관

- 상신·무처분 잔여: 없음. 무처분은 결함 주장은 승인됐지만 수리 조각을 적용하지 않는 장부 상태다. verify-rounds가 조각 항목과 별도로 분류하는 발견 항목도 없다.
- 기각 보관 파일: 없음. 별도 보관 경로가 지급되지 않았다. 확정 사유는 장부.md의 「라운드 1 — 사유 절」에 남겼다.
- R1-12는 기각을 유지했다. 공개 검토 이벤트의 역할 검사는 실행 최상위 필드가 아니라 이미 역할을 가진 execution.action을 읽는다. 기존 시험은 역할이 이미 담긴 action을 사용해 같은 공개 이벤트의 재전달과 더 낮은 이벤트 인덱스의 역순 도착을 검사하며, 단독 실행에서 통과했다. 제안한 최상위 role 추가는 손상을 고치지 않는다.

## 자체 처리·승계와 사용자 직접 재검토

- verify-rounds §8의 신호 4는 예상 밖 판단이 하류 지급 목록·산출 서식·정족·계수·파일 배치를 바꿀 때 감지한다. 세션은 다음 두 판단을 사용자 지시와 저장소 정본에서 결정할 수 있어 각각 자체 처리했고, 오판·되돌리기 비용과 근거는 장부에 기록했다.
- 첫째, 관점의 담당 범위를 바꾸면 각 수리자에게 필수로 읽으라고 지급하는 파일 목록과 그 파일들의 행 수가 달라질 수 있다. 사용자의 분할 지시를 따라 수리자 8명을 영역 담당 4명과 관점 담당 4명으로 나눴다. 영역 담당자 번호 1~4가 산출물 228파일을 중복 없이 나누어 맡았다. 관점 담당자 번호 5는 영역 담당자 번호 4가 맡은 파일만 죽은 호환 요소 관점으로 다시 읽었다. 관점 담당자 번호 6은 영역 담당자 번호 2의 파일을 생산자·소비자 계약 관점으로, 7은 번호 1의 파일을 연구 목적·상태 전이 관점으로, 8은 번호 3의 파일을 실행 효율 관점으로 다시 읽었다.
- 둘째, 라운드 커밋에 포함할 경로 범위를 검증 산출물·런 기록에서 생성 미러·기억 기록까지 넓혔다. 저장소의 커밋 절차인 commit-harness는 정본에서 생성한 .agents/skills/do-math/ 사본과 커밋별 기억 노드 기억/layer1/M-0336.md 및 기억/색인.md를 같은 커밋에 포함하도록 정한다.
- 승계: 없음. 이미 확정된 사용자 결정의 수리 방향을 새 선택 없이 남은 문면에 적용하는 경우를 승계로 센다. 직접 수리 네 건은 기존에 확정된 방향의 자동 적용이 아니라, 1라운드 심사 뒤 새로 도착한 사용자의 재검토 지시에 따라 운전자가 처분을 다시 정한 별도 처리다.
- 사용자 후속 지시로 R1-01의 과제 기반 연구 수행 역할(research_work)이 쓰는 체크포인트 자기 점검 규칙을 그 역할에만 전달하도록 고쳤다. 보충 조사 역할(supplemental_research)의 별도 관찰 프로필에는 이 규칙을 전달하지 않는다. 원래 제안 시험은 생성자를 건너뛴 ResearchEngine 모사체의 현재 저장소 스냅샷 속성 head가 없었다. 그 속성을 채워 역할별 관찰 계약 시험을 통과시켰다. 원래 심사 1/3은 보존한다.
- R1-40의 스트림 관찰은 줄마다 잔여 전체를 다시 분할하던 처리를 수신 묶음당 한 번 분할하도록 고쳤다. 원래 제안 시험의 잘못된 바이트 문자열을 유효한 CRLF·분할 UTF-8·오류 줄 시험으로 다시 써 통과시켰다. 원래 심사 0/3은 보존한다.
- 심사 3/3은 세 심사자가 결함 주장과 수리안을 승인했다는 뜻이다. R1-31과 R1-41은 현행 동작의 손상이 작다는 이유로 별도 처분인 「승인하되 고치지 않는다」를 받았다. 사용자 후속 지시는 죽은 인자 정리를 우선시했다.
- 이에 따라 R1-31에서는 ensure_governance 함수의 사용되지 않는 at 매개변수와 호출 시 전달 인자를, R1-41에서는 SessionSlots.acquire 함수의 사용되지 않는 enforce_capacity 매개변수와 호출 시 전달 인자를 제거했다. 두 함수 자체와 결정 시각 계산·자원 예약 검사는 유지된다. 두 항목에 대한 원래 심사 3/3과 당시 장부 상태 「무처분」은 이 후속 처리와 구별해 보존한다.
- R1-12의 기각은 위의 독립 확인으로 유지했다. 직접 수리 네 건의 원판정, 판단과 근거, 사용자 지시의 시점은 장부 「신호 처리 절」과 「운영 기록」에 구분해 남겼다.

## 운영 기록 요지

- 영역 담당 네 기의 합집합은 228파일·73,025행이었다. 관점 담당 네 기는 각각 대응하는 영역 담당 한 명의 파일 전건만 필수로 읽었다. 관점 네 기의 필수 범위를 합치면 다시 전체 228파일이며, 각 파일은 영역 담당과 관점 담당이 서로 다른 물음으로 한 번씩 읽었다. 수행 기록의 필수 파일과 행 수에는 누락이 없었고, 비공백 원문 행 131,310회가 실행 로그에 있는지 대조했다. 원문 출력 대조는 독해 범위의 근거이며 이해의 완전성을 증명하지 않는다.
- 사용자 후속 지시는 공식 적용 뒤에 도착했다. 기존 승인·기각·무처분의 심사 기록과 수리 산출은 유지하고, 직접 판단 네 건과 1라운드 종료를 장부에 추가했다. 도중 파라미터 변경 때 수리부터 다시 시작하는 기본 절차는 현재 라운드에서 마무리하라는 후속 지시 때문에 실행하지 않았다.
- 최종 단위 시험 292건, 변경된 통합 시험 15건, 기존 통합 그룹에서 Lean 그룹으로 재분류한 실제 Lean 도구 검사 test_approved_five_repairs.ToolchainContractTests.test_inspection_matches_actual_formal_verifier 1건의 격리 실행, 직접 추가한 역할별 관찰 시험 1건, R1-12 단독 확인 시험 1건, Python 구문 검사, probe_cli.py --skill-only, 미러 --check, git diff --check가 통과했다. 직접 추가한 스트림 시험은 단위 292건에 포함된다. 전체 통합·Lean·자원 스위트와 실제 연구 인스턴스의 효과는 확인하지 않았다.
- 사용자 명시 요청에 따라 graphify를 갱신했다. 첫 시도는 references/CLI-실행-계약.md 842행의 원문 「형식 검사를 통과하면」을 추출 모델이 「형식 검사가 통과하면」으로 바꿔 인용해, 인용 문자열의 축자 검사에서 실패했다. 기존 그래프는 보존됐다. 재시도는 검증된 추출 캐시를 재사용하고 그 문서를 다시 추출해 성공했다. 최종 상태는 current, 228파일, 6,157노드, 21,647관계, 의미 추출 대기 0이다. current는 그래프를 만들 때 기록한 원본 파일의 내용 해시가 현재 do-math 파일과 일치한다는 뜻이며, 수리 내용의 정확성을 인증하지 않는다. 그래프 자체는 Git 제외 로컬 생성물이다.
- 독립 독해를 거쳐 동결문에 남아 있던 원래의 두 라운드 예정과 graphify 미갱신 방침을 사용자의 후속 지시인 한 라운드 종료와 graphify 갱신으로 고쳤다. 수리자·심사자의 모델은 모두 gpt-6-astra였고, 병합자는 codex-full의 gpt-5.6-terra였다.

## 발견

verify-rounds의 발견 항목, 즉 산출물에서 지목할 문제의 근본 원인이 산출물 밖에 있어 산출물 파일만으로 수리할 수 없다고 분류된 항목은 없다.
