# 확정 G09 manager 연속 개발의 검수·배정 루프

## 1. 종합 확정본

이 주제군은 옛 do-math를 manager 연속 개발로 이어 간 2026-10-13~10-20의 기록 36개(M-0550~M-0585)다. 아래에서 쓰는 개념어의 뜻은 다음과 같다.

- **manager**: 연속 개발 실행기(`services/continuous-development`, 뒤에는 비동기 큐 `.async/dm`)가 회차마다 새로 띄운 관리 세션이다. task의 반환을 검수하고, 공용 판단 문서(context·plan·seams)를 갱신하고, 다음 작업을 배정한다. 제품 코드는 직접 고치지 않는다.
- **task**: 한 회차 안에서 배정받은 범위만 수행하고 자기 보고와 근거만 쓰는 작업자 세션이다.
- **phase**: manager가 한 번에 배정한 task 묶음과 그 회차다. 001~029까지 있었다.
- **partial**: task가 지정 성과 일부를 채우지 못했다고 표시한 반환이다. 지정 성과를 채운 반환은 complete다.
- **G1~G8**: 준비 단계에서 공용 context에 고정한 프로젝트 전체의 완료 관문이다. 원문 의무와 보존 항목, 전체 시험과 변이, 실환경 경계, 최종 review와 인도가 여기에 든다.
- **L01**: 실제 운전 프로필과 출력 바이트 상한에 관한 외부 결정이다. manager가 사용자에게 상신했고 범위 끝까지 열려 있었다.
- **packet(P01~P11)과 N01~N03**: 남은 문서 요구, 곧 문서 필드를 실제 생산자에 결속하는 요구를 묶은 후속 요구 문서의 번호다.
- **미러**: 정본 스킬에서 생성기로 만든 사본 트리다.
- **fixture**: 시험의 준비 자료와 환경이다.
- **green·red**: 관련 시험의 통과와 실패다.
- **관리 커밋**: manager가 검수 기록, 공용 문서, 다음 배정, 기억 노드를 담아 남긴 커밋이다.
- **archive**: 관리 커밋에 넣은 당시 제품·원자료 바이트의 압축본이다.

준비 기록(M-0550, 10-13 20:16 커밋)부터 phase 028 검수 기록(M-0578, 10-15 01:27 커밋)까지 약 29시간 동안 phase 001~028이 진행됐다. 그 사이의 검수 기록이 M-0551~M-0578이다. 10-15 서비스 전환 때 manager 029가 게시와 관리 커밋 전에 중단됐다(M-0579). 그 뒤 비동기 큐의 manager 0001·0005·0006·0007이 phase 장벽 없이 완료 사건마다 배정을 이었다(M-0580~M-0583). 10-18에는 manager 0108이 수용판을 main 커밋으로 인도했다(M-0584). manager 0008~0107의 회차에는 기억 노드가 없다. M-0585는 같은 시기 사용자가 바꾼 독해 도구 기본 모델을 작업트리 정리 때 보존한 기록이다. 범위 끝에서도 G4·G5·G7과 L01이 남았다. 이 구현은 2026-10-21 사용자 결정으로 삭제됐다 [[M-0593]]. 그래서 아래 원리는 위임한 작업을 검수하고 배정하는 일에 구현과 무관하게 성립하는 범위로만 쓰고, 사례는 옛 구현의 것으로 밝힌다.

36개 가운데 34개(M-0551~M-0584, 중단 초안 M-0579 포함)는 같은 형식의 회차 기록이다. 형식은 직전 task 반환의 검수, 공용 판단의 갱신, 다음 배정, 관리 커밋 하나에 노드 하나다. 그러므로 종합의 대상은 개별 제품 결함이 아니라 이 반복의 방법이다. 34개 노드 모두에 남은 관문이나 전체 완료가 아님을 적은 문장이 있다. 작성한 기록의 수를 진척으로 세지 않는다는 한정도 첫 회차부터 있었다 [[M-0551]].

### 회차 검수는 반환 보고를 승인하지 않고 원자료로 다시 세어 닫았다

manager는 task의 complete나 통과 수를 그대로 받지 않았다. 반환이 주장하는 성과를 원자료로 다시 세어, 그 결과가 주장을 지지할 때만 회차를 닫았다. 회차를 건너 되풀이된 검수 항목은 다섯이다.

1. **통과 주장의 재계수.** 선택한 시험 ID, 실제 결과의 고유 행, 실제 종료 코드를 정본과 미러에서 따로 대조했다. 최종 58개 선택과 실제 58 passed 행을 맞댄 회차가 있고 [[M-0552]], 양쪽 136건의 선택·고유 행·실제 exit를 확인한 회차가 있다 [[M-0561]]. 200개 선택 가운데 199 passed와 권한 조건의 skip 1을 구별했고 [[M-0570]], 187개 선택 가운데 186 passed와 skip 1도 같은 방식으로 구별했다 [[M-0569]].
2. **실행한 판본의 결속.** 시작·종료 시점의 소스 전체 해시와 허용된 변경 집합을 대조했다. 종료 파일 2206개의 해시 [[M-0552]], 2658개 파일과 허용 22변경 [[M-0562]]이 그 예다. 앞선 관련 회귀를 새 판본의 근거로 다시 쓸 때에는 그 회귀가 실제로 돈 트리를 따로 확인했다. 미러 생성 전 트리에서 돈 정본 검사와 생성 뒤의 최종 판본을 구별한 사례가 있다 [[M-0568]]. 첫 통과 뒤 문구가 바뀌자 최종 판본의 실행을 인도 근거로 삼은 사례도 있다 [[M-0579]]. 파일 일부가 바뀐 뒤에는 바뀐 함수와 실제 호출 경로를 대조해 영향받지 않은 하위 성질만 재사용했다. 하위 성질이 불변이라는 사실을 전체 소스나 설치 판본의 동등성으로 읽지 않았다 [[M-0572]] [[M-0574]].
3. **실제 반환의 직접 검수.** 검사의 통과 대신 task가 만든 실제 역할 입력과 반환을 직접 셌다. 반환 각 107개와 제안 전문 1개 [[M-0574]], 실제 trust 반환 122개 [[M-0575]]가 그 예다.
4. **실패의 보존.** 원 실패와 중간 오류를 지우지 않고, 이전 실패는 같은 ID의 새 근거로 닫았다 [[M-0561]]. 초기 오류를 뒤의 통과로 소급해 성공으로 바꾸지 않았다 [[M-0562]] [[M-0564]] [[M-0583]].
5. **제품 커밋의 보류.** 관련 실패가 남은 제품 변경은 작업트리에 두었다. 현재 바이트는 archive로 관리 커밋에 보존했고, 관련 회귀를 검수한 뒤 여러 회차의 변경을 함께 커밋했다 [[M-0553]] [[M-0556]] [[M-0557]] [[M-0565]]. archive는 실패 상태의 증거이며 승인된 판본이나 사용자 조작을 되돌릴 권한이 아니라고 회차마다 적었다 [[M-0553]] [[M-0555]].

이 검수와 배정이 없었으면 얻지 못했을 결과는 둘이다. 첫째, Codex의 실제 역할 schema 거부(HTTP 400)를 구체적인 제품 경계 실패로 기록했다. phase 002의 배정이 현 maintenance action schema를 그대로 쓰는 공급자 호출을 요구했고, 실패가 나면 schema를 줄여 통과시키지 말고 원자료를 반환하게 했다 [[M-0552]]. phase 003의 검수는 작은 protocol_probe의 이전 성공을 실제 schema 수락으로 넓히지 않았다 [[M-0553]]. 둘째, task 보고의 "PID 미관측"이라는 보수적 문장이 원자료보다 좁다는 것을 찾았다. 그 표현은 최종 정본·미러 실행에는 맞았지만, live 실행의 원자료에는 해당 pythonw 관측이 있었다. manager는 원 보고를 고치지 않고 공용 판단에서 관측의 적용 범위를 정정했다 [[M-0563]]. 요약이 원본보다 넓게 주장하는 오차만이 아니라 좁게 주장하는 오차도 대조 대상이라는 것을 보인 사례다. 좁은 요약을 그대로 두면 이후 세션이 이미 있는 증거를 없는 것으로 읽는다.

phase 021에서 제안 전문의 중복 지급을 찾은 것은 검수가 아니었다. task가 먼저 partial로 반환했고, manager는 관련 검사의 양쪽 269건 통과보다 그 반환을 우선해 미충족을 유지했다 [[M-0571]]. 인도 단계에서 수용 manifest 2436개와 Git 제품 2168개의 차이를 모집단 대조로 푼 것도 기존 원리의 적용이다. 차이 268개가 Git 제외 캐시와 생성 자료임을 확인한 뒤에야 제품 누락이 아니라고 판단했다 [[M-0584]].

판정:

- 재계수는 재실증이다. L-0016 「회수 검증」의 "서브에이전트의 판정과 수치는 따로 검증한다", L-0023 「판본과 완결 실행」의 "완결은 선택한 시험 ID 전부가 최종 보고의 실제 행에 대응하는 상태다", L-0005 「요약과 원본 사이의 차이」의 "수치와 식별자를 옮길 때는 현재 정본에서 다시 센다"가 같은 원리다.
- 실제 반환의 직접 검수는 L-0001 「검증 계약」의 "깊이의 하한은 실제 도달이다"의 재실증이다.
- 실패의 보존은 L-0001 「검증 계약」의 "최초 실행의 실패는 이후 재검사가 통과해도 지우지 않고 함께 남긴다"의 재실증이다.
- M-0571의 partial 유지와 M-0584의 모집단 대조는 재실증이다. 앞의 것은 L-0016 「회수 검증」의 "'완료'가 목표 완료 기준을 모두 충족하는가"와, 뒤의 것은 L-0001 「검증 계약」의 "수는 그 수를 만든 모집단만 센다"와 같은 원리다.
- 실행 판본 결속의 일부는 새 정보다. 같은 판본의 증명과 승계 범위의 기록은 L-0023 「판본과 완결 실행」의 "통과를 승계하려면 AST가 같다는 확인과 그 범위를 기록한다"에 있다. 새로 더할 것은 둘이다. 내용이 바뀐 판본에서는 영향받지 않은 하위 성질만 승계한다는 것, 그리고 생성 단계 전후의 트리가 서로 다른 판본이라는 것이다(5절 L-0023).
- 좁은 요약은 L-0005 「요약과 원본 사이의 차이」 원리의 새 발현이다. 그 원리는 차이의 방향을 가리지 않지만, 좁은 쪽의 오차와 원 보고를 고치지 않고 받는 쪽 기록에서 정정하는 처리는 없다(5절 L-0005).
- 제품 커밋의 보류와 바이트 보존은 새 정보다. L-0016 「긴 다단계 작업의 완료 경로」의 "관련 검증을 거쳐 확정한다"를 보완한다(5절 L-0016).

### 검수하는 쪽의 검산과 시험의 관찰 코드도 결함의 출처가 됐다

검사 도구의 실패는 처음에 검사 대상의 결함처럼 보인다. 이 루프에서는 그런 실패가 위임한 쪽과 위임받은 쪽 모두의 검사 도구에서 나왔다. 그래서 결함을 대상에 돌리기 전에, 검사 도구가 대상에 대해 세운 가정이 실제 자료와 맞는지 먼저 확인해야 했다.

manager의 보조 검산은 회차 검수 노드 34개 가운데 7개에서 8번 실패했다. 포함 기준은 manager 자신의 검산이 실패했다고 적은 노드다. 실패한 검산은 모두 자료에 없는 불변식이나 표현을 기대했다.

- 시작 전에 이미 바뀐 engine 문서까지 전체가 불변이라고 단언했다 [[M-0555]].
- manifest가 예외로 둔 비용 캐시까지 시작 해시와 같다고 가정했다. 실제로는 976개 가운데 비캐시 975개만 같았다 [[M-0560]].
- 같은 diff를 다른 파일 순서로 이어 문자열로 비교했다 [[M-0561]].
- 미러 생성 전의 트리가 최종 판본과 같기를 요구했다 [[M-0568]].
- `str(list)`의 따옴표 표현을 원 오류문에서 검색했다 [[M-0573]].
- 이전 task의 원본 경로 관례를 이번 task에 가정했다 [[M-0574]].
- 코드펜스를 한 행으로 다루었고, 공식 결과 행의 위치를 잘못 읽었다 [[M-0576]].

처리는 노드마다 다르게 적혔다. 일곱 노드 모두 제품과 task 자료를 고치지 않았고, 검산의 결론을 고치기 전에 실제 자료나 계약을 다시 읽었다. 원 실패의 보존을 명시한 노드는 M-0555·M-0573이다. 검산기의 교정을 명시한 노드는 M-0561·M-0568·M-0573·M-0576이다. M-0560은 검산기를 고쳤다고 쓰지 않고, 원 보고를 바꾸지 않은 채 공용 판단을 실제로 같은 범위로 한정했다. M-0574는 시작 SHA를 확인한 뒤 대조했다.

task 쪽의 관찰·도우미 코드도 같은 방식으로 실패했다. 잘못된 가정의 내용을 적은 노드는 다섯이다.

- camelCase 키를 읽어 structured 본문을 부재로 기록했다 [[M-0564]].
- schema 소유자를 잘못 정하고 maintenance를 참조 객체로 가정했다 [[M-0570]].
- 실제 입력에 없는 `action.role` 키를 가정했다 [[M-0573]].
- 데코레이터를 실제 생산자로 오인했다 [[M-0574]].
- 넓게 시도한 포장 캡처가 archive 바이트를 JSON으로 직렬화하지 못해 suite마다 24건 실패했다 [[M-0575]].

내용 없이 helper·관찰·보조 검산 오류의 보존만 적은 노드가 셋 더 있다(M-0562, M-0563, M-0577). 오류의 성격을 알 수 없어 위 목록에 넣지 않았다. manager 쪽과 task 쪽을 합치면, 가정의 내용이 적힌 검사 도구 실패는 34개 회차 노드 가운데 10개에 있다. 관찰 코드의 정정은 같은 원바이트를 고친 관찰 코드로 다시 검사하는 방식으로 했다. 호출 입력과 runtime이 같아 새 유료 호출은 쓰지 않았다 [[M-0564]]. 관찰 범위의 공백과 제품 실패를 가를 좌표가 보고에 있으면 같은 시험을 다시 돌리지 않았고, 실패한 넓은 캡처를 새 근거로 승인하지도 않았다 [[M-0575]].

관찰 도구가 대상의 상태를 바꾼 사례도 하나 있다. 같은 프로세스의 관찰 코드가 AttachConsole·FreeConsole을 호출하자, Job의 null stdin이 닫힌 핸들로 바뀌어 Git의 DuplicateHandle이 실패했다(WinError6). 일반 자식 프로세스에서는 재현되지 않았다. 관찰을 별도 자식 프로세스로 옮기고 같은 실행 조건의 정상 대조를 둔 뒤에야 제품 실패와 구별됐다 [[M-0565]] [[M-0566]].

이 실패 유형이 다른 실패 유형보다 잦았다고는 말할 수 없다. 시험 전제가 제품 계약을 따르지 못한 fixture·대역 실패도 6개 노드에 있다(M-0556, M-0558, M-0560, M-0565, M-0567, M-0568). 제품 경계의 실패도 따로 있다.

판정:

- 검산기 실패는 새 발현이다. L-0001 「검증 계약」의 "검증 보조 코드(시험용 대역, 영수증 저장 코드, 시험 초기화 도구)의 실패는 제품 결함이나 공급자 실패와 구별해 기록하되 둘 다 통과 전에 해결한다"와 L-0023 「대역과 fixture를 실제 계약에 묶기」의 검사 드라이버 사례(M-0346)가 같은 계열이다. 새로 더할 것은 세 가지다. 위임 작업을 검수하는 쪽의 임시 검산이 출처가 된다는 것, 실패한 가정의 유형, 그 빈도다. 같은 원자료로 관찰 코드를 고쳐 다시 검사하고 외부 호출을 반복하지 않는 처리도 새 정보다(5절 L-0001).
- 관찰 부작용은 재실증이 주이고 일부가 새 정보다. L-0005 「성능 측정과 실행 예산」의 "측정 도구와 실행기는 대상을 바꿀 수도 있다"(종료 장벽을 확인하던 관찰 함수 사례)와 "측정을 다루는 시험의 재현은 측정 세션이 겹치지 않도록 별도 프로세스에서 한다"가 이미 있다. 새로 더할 것은 측정이 아닌 관찰 코드의 발현과, 같은 실행 조건의 정상 대조로 제품 실패와 구별한 처리다(5절 L-0005).
- fixture 전제 실패의 반복은 L-0023 「대역과 fixture를 실제 계약에 묶기」의 "시험은 제품 생산자의 계약을 따라가야 한다"의 재실증이다. 원장 (가)의 보조 증거로만 쓴다.

### 통과했지만 필요한 성질을 증언하지 못한 검사에는 다섯 모양이 있었다

회차마다 기존 검사의 통과가 실제로 무엇을 증언하는지 다시 따졌다. 그 결과 통과했지만 필요한 성질을 증언하지 못한 검사가 다섯 모양으로 나왔다. 다섯 모두 L-0001 서두의 원리, 곧 "검사의 통과는 그 검사가 실제로 행사한 대상, 판본, 경계만 증언한다"의 발현이다. 이 원리는 [[D-0011]] 종합 1이 D-0010의 신호 원리를 검증 자신의 증거로 넓혀 L-0001에 둔 것이다.

1. **성공 표본이 실패로 바뀌어도 통과하는 검사.** 전송 schema가 바뀐 뒤 source_request 없는 합성 성공 표본이 output_validation 실패를 반환했다. 그러나 실패 결과도 저장할 수 있었으므로 pair 검사는 통과했다. 일반 순회와 저장 검사가 있다는 사실로 성공 분기의 보존을 판단할 수 없었다 [[M-0556]]. 실제 collector 경로와 status·output·오류 단언을 연결하자, 새 단언이 성공이라고 이름 붙은 두 표본이 실패였음을 잡았다 [[M-0557]]. 새 단언이 실제로 실패를 잡는지는 성공 표본을 실패로 바꾸어 확인하게 했다 [[M-0556]].
2. **전달 일치만 보는 검사.** 실제 생산값과 최종 입력을 비교하는 검사는 전달이 일치한다는 것을 입증한다. 그러나 생산값 자체가 계약을 어기면 그대로 통과한다. 계약에서 얻은 불변식(제안 전문의 사본 수 1)을 최종 반환에 따로 단언하자 공식 green과 다른 결과가 나왔다 [[M-0571]]. 수리 뒤에는 보존된 최종 반환을 양쪽 각 80개씩 재귀 검산해 전문 1개를 확인했다 [[M-0572]]. 비교 검사를 버리지 않고, 그 검사의 주장과 독립으로 확인할 불변식을 구별한 대응이다.
3. **시작 사건이나 이름만 보는 검사.** 학술 MCP의 기존 probe는 시작 사건에 도구 이름이 있다는 사실만 검사했다 [[M-0563]]. 새 관찰자는 같은 ID의 성공 완료와 실제 서버의 자료원 요약을 검사했고, 기대 동작은 폴더 존재라는 대리 표지가 아니라 서버 원문에서 정했다 [[M-0564]]. 문서 이름 검사의 통과도 검사기가 다루지 않는 표현(단계 소유, 부분 JSON 예시, 명령 모드)까지 보증하지 않았다 [[M-0576]].
4. **차용한 반례를 거부하지 못하는 검사.** 파일 해시가 같아도 그 바이트가 다른 실행 경로에서 차용됐을 수 있다. 검사는 workspace, task·execution 좌표, 저장 artifact와 snapshot을 함께 대조해 소유를 판정했다 [[M-0569]]. 지급 명령과 파일 해시가 맞는 다른 archive를 함께 넣은 반례 [[M-0570]], 다른 check나 후보를 차용한 반례 [[M-0572]], 존재하는 단어를 다른 역할의 산출로 차용한 오류 [[M-0577]]를 시험이 거부하게 했다.
5. **모집단이 다른 검사의 결과를 합치는 판단.** 앞선 문서 관련 선택의 성공과 이번 전건 smell 검사의 실패는 검사 모집단이 달랐다 [[M-0560]]. 한 보고의 출현 수 1223은 inline 849와 fence 374의 합이어서, 다른 보고의 수와 같은 단위로 합산하지 않았다 [[M-0578]]. "정확한 8문장"이라는 보고는 실제로 이름별 8항목과 고유 4문단이었다 [[M-0574]].

판정:

- 1은 새 정보다. L-0001 「거짓 GREEN을 막는 기준」의 "수정 내용을 무력화했을 때 테스트가 실패하는지 프로브로 확인한다"와 L-0023 「판본과 완결 실행」의 "완결(complete)과 성공(successful)을 구별한다"가 인접하지만, 실패도 정상 경로로 저장되는 구조에서 성공 분기의 검사가 사라지는 형태는 없다(5절 L-0023).
- 2는 일부가 새 정보다. L-0023 「음성 시험과 검사기 강도」의 "전달된 값과 검사기가 기대하는 값을 서로 비교하는 검사는 두 사본에서 함께 빠진 항목을 놓친다"가 같은 계열(두 값이 함께 틀린 경우를 비교가 놓친다)이다. 새로 더할 것은 생산값의 계약 위반(중복)이라는 발현과, 계약에서 얻은 불변식을 비교와 독립으로 단언하는 대응이다(5절 L-0023).
- 3은 재실증이다. L-0001 서두의 원리, L-0001 「검증 계약」의 "작은 실호출 검사는 그것이 실제로 거친 경로만 입증하며", L-0005 「대리 표지로 축소나 검사를 제안하기 전의 확인」이 같은 원리다.
- 4는 새 발현이다. L-0001 「검증 계약」에는 "같은 이름은 같은 소유자를 뜻하지 않는다"와 "필드 이름이나 해시가 입력에 있다는 사실은 원문에 도달했다는 증거가 아니다"가 있다. 같은 바이트나 맞는 해시를 다른 실행에서 차용한 반례는 없다(5절 L-0001). M-0577의 단어 차용은 같은 항목의 "여러 소유자의 어휘를 합친 검사는 다른 문맥에서 유효한 낱말로 잘못된 문맥을 통과시킨다"의 재실증이다.
- 5는 재실증이다. L-0001 「검증 계약」의 "수는 그 수를 만든 모집단만 센다"와 L-0023 「판본과 완결 실행」의 "서로 다른 시험 선택의 통과 수를 더해 전체 통과로 쓰지 않"는다가 같은 원리다.

### partial 반환의 절반은 배정이 의무의 수행 위치를 빠뜨려서 생겼다

노드가 partial로 명시한 반환은 여섯이다. phase 003·004·006·008·017·021의 반환이고, 노드는 M-0553·M-0554·M-0556·M-0558·M-0567·M-0571이다. 포함 기준은 해당 회차 task의 반환을 partial이라고 적은 노드다. 앞선 partial을 가리키기만 한 M-0555·M-0559는 넣지 않았다. 이 가운데 셋은 작업자가 실패한 것이 아니었다. 배정이 의무를 수행할 위치를 쓰기 범위나 임무 범위에서 빠뜨렸다.

- 녹화 원바이트를 지킬 의무가 있었는데, 이전 배정은 상위 Git 속성만 쓰기 범위에 넣었다. 실제 변환은 하위 corpus의 명시적 text 예외에서 생겼다. 작업자는 허용된 상위 규칙으로 하위 예외를 덮을 수 없다는 실제 결과를 남기고 원상 복원한 뒤 partial로 반환했다. 다음 배정은 하위 정본과 생성 사본 두 파일만 더 허용했다. manager는 범위를 넓힌 이유를 "새 요구가 아니라 기존 원바이트 의무를 수행할 위치가 배정에서 빠졌기 때문"이라고 적었다 [[M-0554]].
- 전송 schema의 수리가 외부 CLI fixture의 가정을 깼지만, 그 fixture는 쓰기 범위 밖이었다. manager는 같은 도우미를 쓰는 다른 소비자까지 추적해 다음 쓰기 범위에 넣었다 [[M-0556]]. 이 반환의 partial에는 범위 공백이 아닌 원인(통과한 검사 안의 성공 표본 공백)도 있었다.
- 쓰기 목록에는 CLI 문서가 있었지만, 임무(objective)가 P01 문장만 바꾸도록 한정했다. 작업자가 다른 절의 표기를 고치지 않고 partial로 반환한 것을 manager는 "그 경계를 지킨 판단"으로 판정했다. 다음 배정에는 확인된 원인, 고칠 표기, 정확한 실패 ID를 주어 수리 전 전체 재실행을 없앴다 [[M-0558]]. 이것은 쓰기 범위가 아니라 임무 범위의 한정이다.

나머지 셋은 실제 미충족이었다. Codex의 schema 거부 [[M-0553]], fixture 정리 단계의 오류 1건 [[M-0567]], 제안 전문의 중복 지급 [[M-0571]]이다. manager는 반환마다 두 원인을 구별했다.

비동기 큐로 옮긴 뒤에는 배정이 한 걸음 더 나갔다. 조사로 확인된 시험 공백은 조사만 끝내고 다시 파견하지 않고, 같은 task에서 수리하도록 쓰기 범위를 열었다. 반대로 아직 관측하지 않은 runtime 결함을 전제로 넓은 쓰기 권한은 주지 않았다 [[M-0581]] [[M-0582]].

판정:

- 쓰기 범위와 임무가 의무의 수행 위치를 포함해야 한다는 조건은 새 정보다. L-0016 「파견 계약」의 "읽기는 발견 절차로 열고, 쓰기 범위와 임무는 닫는다"의 적용 조건이다(5절 L-0016). 소비자와 대역을 찾는 절차 자체는 재실증이다. L-0016 「병렬 구현 파견」의 "통합자의 작은 수정도 대역을 전수 확인한다"와 L-0023 「대역과 fixture를 실제 계약에 묶기」의 "제품 속성을 바꿀 때는 그 속성을 흉내 내는 대역을 먼저 grep한다"가 있다. 새로 더할 것은 찾은 위치를 쓰기 범위에 넣는 일, 범위를 지킨 partial의 판정, 범위 확장을 기존 의무의 보충으로 기록하는 일이다.
- 확인된 공백에 한한 같은 task의 수리 권한은 일부가 새 정보다. L-0016 「외부 한도로 지정 수단이 막혔을 때」에 분석한 작업자에게 최소 수리를 이어 맡긴 사례(M-0541)가 있으나, 그것은 thread limit에 대한 대체였다. 배정 설계로 조건부 쓰기 권한을 여는 것은 없다(5절 L-0016).

### 쓰기 작업의 묶음 단위는 공유 수정 지점과 공유 파생물로 정했다

manager는 처음부터 소스 변경과 검사를 한 task로 묶고, 병렬성은 독립 읽기 검토에만 쓰기로 정했다 [[M-0550]]. 서로 다른 결함을 다루는 두 수리도 공식 생성기·말뭉치·캐시를 공유하면 같은 phase에 병렬로 배정하지 않았다 [[M-0553]]. 전건 검사가 다른 수정 파일을 읽고 미러 생성과 캐시를 공유하면 한 task가 소유했다 [[M-0560]] [[M-0561]] [[M-0562]]. 공통 helper와 미러·캐시를 동시에 바꾸는 제품 task는 독립 검증이 어려워 하나로 묶었다 [[M-0569]]. 두 task로 나누면 공유 helper·미러·캐시를 수정 중인 상대에게 검증이 기댄다는 것이 그 이유였다 [[M-0570]].

병렬로 돌린 것은 고정판을 읽기만 하는 조사였다. 읽기 조사는 변경 중인 시험·지침·캐시·미러와 다른 task의 결과를 소비하지 않게 경계를 정했다 [[M-0559]]. 과거 입력의 준비는 Git 불변 객체만 읽게 하고, 현재 코드를 실행하는 시험은 한 task만 소유하게 했다 [[M-0565]] [[M-0566]]. 정책·문서 이름 조사 셋 [[M-0575]], 288절 조사 셋 [[M-0577]], 요구표의 독립 질문 셋 [[M-0579]] [[M-0580]]이 같은 판본 위에서 병렬로 돌았다. manager는 "수정 중인 공통 helper를 읽는 동시 조사는 독립 검증이 아니다"라고 적었고, 조사 인원수를 늘리려고 task를 만들지 않았다 [[M-0571]].

phase 021을 검수한 회차의 기록에 따르면, 사용자는 문서 번호별 phase 반복 대신 공유 수정 지점별 묶음과 독립 조사만의 병렬화를 지시했다 [[M-0571]]. 그 지시는 운영자가 다음 manager에게 전달한 원문 문서로 남아 있고, M-0571과 같은 커밋(`6f0969f0`, 10-14 14:02)에 들어갔다. 회수는 `git -c core.quotepath=off show dbde17f4:docs/do-math/continuous-development-2026-10-13/sources/document-batching-2026-10-14.md`로 한다. 그 문서에 따르면 지시는 phase 021 실행 중에 나왔다. 계기는 문서 작업을 한 phase에서 병행하지 않는 이유에 대한 사용자의 질문이었고, 사용자는 공유 수정 지점별로 묶고 독립 조사만 병렬화하자는 설명에 "그렇게 전달"이라고 답했다. 문서가 든 판단 근거는 019·020의 실제 변경 교집합 22경로와, 로그로 어림한 manager 시간 약 31%다. 그 31%는 검수·문서·독해·기억·커밋·배정을 합한 근사치이며, 문서는 이를 순수 낭비로 판정하지 않았다. 문서는 묶음 크기를 "한 새 세션에서 원문 확인·수정·관련 검증·보고를 끝낼 수 있는 크기"로 정했다.

manager는 이 지시를 다음처럼 적용했다.

- 문서 번호마다 반복 마감하는 대신 공유 수정과 최종 관련 검사를 통합했다 [[M-0573]].
- 공통 helper 수정이 필요한 단계는 한 담당자에게 모으고, 남은 의미 판정은 고정판을 읽는 독립 조사로 배정했다 [[M-0575]].
- 조사 뒤의 발견 넷을 단일 work 하나로 묶었다 [[M-0576]].
- 문구 4절과 검사 보강 14절을 별개 18작업으로 나누지 않고, 공유 doc_code·미러·관련 검사를 쓰는 실제 issue 8개로 묶어 한 담당자에게 맡겼다 [[M-0578]].

지시 이전의 문서 packet은 P01이 phase 008~009, P02가 019, P03이 020으로 하나씩 회차를 받았다. 그 사이 phase 010~018은 문서가 아니라 실경계 작업이었다 [[M-0558]] [[M-0559]] [[M-0569]]. phase 020의 manager는 지시 전에 이미 "packet 번호마다 한 phase를 고정하지 않고 실제 독립성과 한 세션의 닫힌 범위를 기준으로" P04·P05를 한 회차(021)로 묶었다 [[M-0570]]. 원문 문서가 보여 주듯 지시는 그 뒤에 나왔다.

이 사용자 교정은 3.3의 두 갈래로 읽는다. 갈래 α(올바른 결과)는 쓰기 작업을 요구 문서의 번호가 아니라 함께 고치는 지점으로 묶고, 독립 조사만 병렬화하는 것이다. 갈래 β(왜 스스로 내지 못했는가)의 진단은 노드에 한 문장으로 있다. "반복 회귀·미러·관리 비용은 파일 소유 충돌을 피하는 것만으로 줄지 않는다" [[M-0571]]. 분해 판단이 파일 소유 충돌의 회피만 셌고, 회차마다 드는 고정 비용은 세지 않았다는 뜻이다. 다만 이 사건을 manager 기본값의 결함으로 확정하지 않는다. 결함이 아닌 설명 둘을 원문이 지지한다. 첫째, M-0570의 manager가 이미 packet 고정을 풀고 있었으므로 지시는 진행 중인 방향의 확정일 수 있다. 둘째, packet별 회차는 "한 세션의 닫힌 범위"를 지키려던 선택이었다. 사용자는 약 20회차의 진행을 본 뒤 질문했고, 지시도 한 세션 크기의 기준을 유지했다. 그러므로 사용자가 진행을 보고 회차별 고정 비용의 무게를 구체화한 것으로 읽을 수 있다. 교정 위치는 다음 manager에게 주는 원문 문서였다. 서비스의 manager 지침 같은 상시 위치에 넣었다는 기록은 노드에 없다.

### 완료 경로에 대한 같은 방향의 사용자 교정이 열흘 간격으로 되풀이됐다

2026-10-03 사용자는 부분 수리와 시험이 완료되지 않고 흩어진다고 지적하며, 기존 목표를 지우고 새 목표를 세우게 했다 [[M-0423]]. 그 교정 뒤의 운영은 목표와 남은 의무를 원문 행에 연결한 작업판(단계-전환표)과, 독립 변경마다 검수·관련 검증·확정을 하는 방식이었다. 이 운영은 L-0016 「긴 다단계 작업의 완료 경로」에 있다.

열흘 뒤인 2026-10-13, 같은 진단이 다시 나왔다. 최근 개별 작업은 재현·관련 검증·커밋으로 닫혔다. 그러나 추적 109항목 가운데 101개가 planned였고, 이전 재검토 25영역 가운데 실제 완료 표시는 한 영역뿐이었다. 노드는 이 수가 미구현 기능 수나 완료율이 아니라고 적었다. 노드의 판단은 "지역적인 검사기 수리와 프로젝트 전체 종료의 연결이 약하다"였다. 사용자는 /goal을 지우고 현재 상태와 전체 완료 경로를 분석하게 한 뒤, 그 교훈을 연속 개발 서비스의 실제 설정에 적용하게 했다 [[M-0550]]. 노드는 이 사건을 스스로 "사용자 교정"이라고 불렀다.

갈래 α는 노드로 확인된다. 단위마다 확정하는 운영이 지켜져도 전체 완료와의 연결은 따로 통제해야 한다. 두 번째 대응은 단위 확정 규칙을 더하지 않고 실행 구조를 바꾸었다. 회차마다 새 manager가 반환을 검수하고 다음 작업을 배정하게 했고, 원래 완료 관문(G1~G8)을 공용 context에 고정했으며, "요구를 달성한 척 범위를 줄이거나 새 /goal을 만들지 않는다"고 적었다 [[M-0550]]. 갈래 β의 편향, 곧 시스템이 왜 그 연결을 스스로 유지하지 못했는지는 대화 원문이 노드에 없어 확정하지 않는다. 그 뒤 루프는 2026-10-18까지 회차마다 개별 남김을 닫았지만, 범위 끝에서도 G4·G5·G7과 L01이 남았다 [[M-0584]]. 구현은 2026-10-21에 삭제됐다 [[M-0593]]. 그래서 이 구조가 완료 경로를 통제했는지는 판정되지 않았다.

판정: 새 정보. 같은 방향의 교정이 되풀이됐다는 사실 자체가 3.3의 기재 대상이다. L-0016 「긴 다단계 작업의 완료 경로」는 첫 교정과 그 운영만 담고, 그 운영 뒤의 재발과 두 번째 대응은 담지 않는다(5절 L-0016).

### 중단된 manager는 관리 산출물의 실재로 복구했다

manager가 두 번 중단됐다. 두 복구는 모두 무엇을 했다는 서술이 아니라 무엇이 실제로 존재하는가로 판정했다.

phase 023에서는 작업자가 완료했지만 manager가 503/model capacity 오류로 제출 전에 끝났다. 사용자는 완료한 task를 다시 실행하지 말고 원보고와 현재 파일을 대조하라고 지시했다. 재시작한 manager는 manager.json뿐 아니라 pending 파일과 관리 자료가 실제로 있는지 확인했다. 이전 manager.log 외에는 관리 산출물이 없었다. 같은 phase를 실행기에 다시 주면 완료 작업과 로그를 덮을 수 있어, 다음 phase를 새 번호 024로 배정했다 [[M-0573]]. 같은 phase의 재기동은 task를 다시 실행하므로 자동 재개가 아니라는 조건은 준비 단계부터 있었다 [[M-0550]].

manager 029는 서비스 전환 때 게시와 관리 커밋 전에 중단됐다. 그 manager가 남긴 공용 문서와 기억 초안(M-0579)에는 아직 하지 않은 게시·압축·커밋을 완료처럼 서술한 부분이 있었다. 비동기 큐의 첫 manager는 그 초안을 고치거나 지우지 않고, 추적되는 압축본 `legacy-029-raw.zip`에 원바이트를 보존했다. 현재 판정과 완료 범위는 새 공용 문서와 review에 다시 썼다. 기존 검수 자료는 현재 소스 2675개와 원 task 129개 파일에 대조해 같은 최종 판본임을 확인했고, 완결된 제품 시험은 다시 돌리지 않았다. 이관된 성과는 시작판의 성과로 수용했고, accepted 목록에 가상의 task를 추가하지 않았다 [[M-0580]]. 초안 노드는 닷새 뒤 작업트리 정리에서 "당시 판단의 보존이며 새 검증이 아니다"라는 머리말을 달고 커밋됐다 [[M-0579]]. 그러므로 원바이트 보존은 압축본의 사실이고, 커밋된 노드 M-0579는 머리말이 더해진 판본이다.

## 3. 원장 입력

**처음의 가정과 그 이동.** 초안은 이 범위를 진행 기록의 연속으로 보고, 추출할 원리가 적을 것으로 가정했다. 형식은 그 예상대로 34개가 회차 기록이었다. 그러나 노드마다 "판단에 남길 조건" 절이 있어 같은 판단과 실패 유형을 회차를 건너 셀 수 있었고, 그 반복이 종합의 근거가 됐다.

**검증 처분으로 낮추거나 바꾼 판정.**

- "가장 자주 되풀이된 실패는 검사 도구 쪽"이라는 최빈 주장을 삭제했다. 다른 유형을 세지 않은 비교였고, fixture 전제 실패도 6개 노드에 있었다(검증 D3).
- 검산기 실패의 "처리는 모든 사례에서 같았다"를 노드별 처리로 좁혔다. 공통인 것은 제품·task 자료를 고치지 않은 것과 실제 자료를 다시 읽은 것뿐이다(D2).
- 관찰자 오류 "4건"을 포함 기준이 있는 계수로 바꾸었다. 가정이 적힌 5개 노드와 내용이 없는 3개 노드다(D4).
- partial의 "상당수"를 "명시 partial 여섯 가운데 셋"으로 바꾸었다. 그 셋 가운데 하나(M-0558)는 임무 범위였고, 하나(M-0556)는 원인이 섞였다. partial이 아닌 M-0560·M-0565는 목록에서 뺐다(D5).
- 유효성 증거를 셋에서 둘로 줄였다. M-0571의 중복 지급은 task가 먼저 찾은 것이다(D1).
- 좁은 요약을 새 정보에서 L-0005 원리의 새 발현으로 낮추었다(D6).
- 재계수 단위와 모집단 대조를 재실증으로 판정하고 L 문안에서 뺐다(D7).
- 검산기 사례의 반영 위치를 L-0001 「검증 장치의 가치」에서 「검증 계약」으로 옮겼다(D8). 관찰 부작용(M-0566)은 L-0005 「성능 측정과 실행 예산」으로 옮겼다. 그 항목에 같은 계열의 문장이 이미 있었기 때문이다.

**기준선 변경에 따른 판정 이동.** 초안이 읽은 뒤 L-0001과 L-0016이 다시 쓰였다. 그래서 판정을 현재 파일에 다시 대조했다. 그 결과 셋이 바뀌었다.

- 「통과를 증언하지 못한 검사」 1·2는 L-0001 「거짓 GREEN을 막는 기준」이 아니라 시험 설계 세부를 맡은 L-0023 「음성 시험과 검사기 강도」로 가야 했다.
- 실행 판본 결속은 L-0023 「판본과 완결 실행」의 승계 문장과 겹쳐, 새 부분만 남았다.
- D10이 요구한 신호 원리의 대조 대상은 [[D-0011]]이 L-0001 서두로 옮겨 놓은 상태였으므로, 그 서두와 대조했다.

**처음 가정을 반증한 증거 둘.**

- M-0571 사용자 지시의 원문 문서를 회수하자, 지시는 phase 020의 manager가 packet 고정을 이미 푼 뒤에 나왔다. 계기도 사용자의 질문이었다. 그래서 초안의 β 해석("표면 구조로 분해한 결함")을 "회차별 고정 비용의 무게를 사용자가 구체화한 것"으로 바꾸고, 결함으로 확정하지 않았다(D11).
- M-0550을 현재 L-0016과 대조하자, M-0423의 교정과 같은 방향의 교정이 열흘 뒤 되풀이된 것이 드러났다. 초안과 검증 모두 이 반복을 다루지 않았다. M-0550은 초안 6절에서 "방향 전환"으로만 분류돼 있었다(D12). 그래서 새 정보로 L-0016에 기재한다.

**D-0010 원장의 세 질문.**

- (가) 병렬 구현 교훈의 재발: 증거 있음. M-0553·M-0560·M-0569·M-0570은 공유 생성기·미러·캐시를 이유로 쓰기 작업의 병렬 배정을 피했고, M-0582는 r07-fix와 r18-fix를 충돌 없이 통합했다. L-0016 「병렬 구현 파견」이 기록한 의미 충돌이나 구조 이동 순서의 실패는 이 범위에서 재발하지 않았다. 다만 같은 원리(파일 소유 경계만으로는 부족하다)가 비용 측에서 발현했다(M-0571). fixture 전제 실패가 6개 노드에서 되풀이된 것은 L 교훈이 있는 뒤에도 같은 계열이 계속 나왔다는 보조 증거다. 노드는 L-0016을 인용하지 않으므로 L이 원인이었다고 쓸 수 없다.
- (나) 마지막 수리 뒤 전체 시험이나 실제 연구 운전: 부분적으로 증거 있음. Codex·Claude 실호출(M-0553·M-0556), 실제 Mathlib 컴파일(M-0562), 예약 실발화(M-0563), 학술 MCP 완료 응답(M-0564), 같은 판본 양쪽 전체 T4(M-0568)가 있었다. 그러나 전체 일반·fresh T3·전수 변이는 범위 끝까지 남았고(M-0584), 실제 연구 운전은 없었으며, 구현은 삭제됐다(M-0593).
- (다) 기존 제안에 대한 사용자 결정: 읽은 범위에 증거 없음. M-0563·M-0564가 학술 MCP를 실제로 호출했지만 scholarly-mcp 설치 전환의 결정은 아니다.

**G09 보류의 해소.** [[D-0011]] 원장 「G09 보류」가 남긴 확정 단계를 이 파일이 끝낸다. 그 원장이 기록한 처분 방향, 곧 좁은 요약은 L-0005로, 검산기 사례는 L-0001 「검증 계약」으로 보내는 방향은 그대로 따랐다.

> 공유 상태에는 소스 파일만이 아니라 생성된 사본(미러), 말뭉치, 비용 캐시 같은 파생물도 든다. 수정할 파일이 겹치지 않아도 이런 파생물을 함께 쓰는 쓰기 작업은 한 작업이 소유하게 한다. 옛 do-math 연속 개발의 관리 세션은 서로 다른 결함을 고치는 두 수리도 공식 생성기·말뭉치·캐시를 함께 쓰면 같은 회차에 병렬로 배정하지 않았다. 공통 도우미와 미러·캐시를 함께 바꾸는 작업을 둘로 나누면 각자의 검증이 수정 중인 상대에게 기대므로 한 작업으로 묶었다. [[M-0553]] [[M-0569]] [[M-0570]] 병렬로 돌린 것은 고정된 판본만 읽고, 변경 중인 시험·캐시·미러와 다른 작업의 결과를 소비하지 않는 조사였다. 수정 중인 공통 코드를 읽는 동시 조사는 독립 검증이 아니며, 조사자 수를 늘리려고 작업을 만들지 않았다. [[M-0550]] [[M-0559]] [[M-0565]] [[M-0571]] 기계 전체의 시험 실행 수가 에이전트 수와 별개의 자원이라는 점은 아래 「시험 선택과 실행 규율」에 있다.
>
> 쓰기 작업을 묶는 단위는 요구 문서의 번호가 아니라 작업들이 함께 고치는 지점이다. 작업 단위마다 관련 회귀, 생성 사본의 재생성, 관리 마감 같은 고정 비용이 들고, 파일 소유가 겹치지 않게 나누어도 이 비용은 줄지 않는다. 옛 do-math 연속 개발에서 문서 번호별로 회차를 반복하던 진행에 대해, 사용자는 공유 수정 지점별로 묶고 독립 조사만 병렬화하라고 지시했다. 그 뒤 관리 세션은 별개의 18작업으로 보이던 발견을 같은 도우미·미러·관련 검사를 쓰는 실제 결함 8개로 묶어 한 담당자에게 맡겼다.
