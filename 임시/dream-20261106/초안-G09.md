## 1. 주제군 개요

2026-10-13 사용자는 기존 /goal을 지우고 옛 do-math 재편의 현재 상태와 전체 완료 경로를 분석하게 했다. 그 결과를 `services/continuous-development` 실행기에 맞춰 실제 기록 체계(`docs/do-math/continuous-development-2026-10-13/`)로 준비한 것이 M-0550이다. 이 서비스에서는 task와 manager가 모두 새 codex exec 세션이다. manager는 task 보고를 검수해 공용 context·plan·seams를 갱신하고 다음 phase를 배정하며, 제품 코드는 직접 고치지 않는다. 실행기는 검사나 재시도를 스스로 하지 않고 manager의 `next`를 따른다(M-0550).

phase 001~028의 검수·배정 기록이 M-0551~M-0578이다. 노드 커밋 시각으로 10-13 20:16부터 10-15 01:27까지 약 29시간 동안 거의 한 시간에 한 회차씩 진행됐다. 다룬 순서는 변이 정상 기준, 공급자 실호출, 미러·녹화 원바이트, Job·예약·Lean·학술 MCP의 실경계, T4 측정, 문서 필드의 실제 생산자 결속(P01~P11, N01~N03)이다. 10-14 phase 023에서 manager가 공급자 503 오류로 제출 전에 끝나 복구했다(M-0573).

10-15 서비스 전환 때 manager 029가 게시와 커밋 전에 중단됐다. 비동기 큐(`.async/dm`)의 첫 manager가 그 성과를 이관 판정했고, 이후 배정은 phase 장벽 없이 완료 사건마다 이어졌다(M-0579, M-0580~M-0583). 그 뒤 manager 0108까지의 회차에는 기억 노드가 없다. 10-18 manager 0108이 작업트리에만 있던 수용판을 main 커밋으로 인도했다(M-0584). M-0585는 같은 시기 사용자가 바꾼 독해 도구의 기본 모델을 10-20 작업트리 정리에서 보존한 기록이다.

범위 전체에서 G1~G8의 전체 충족은 선언되지 않았고, L01 외부 결정(실제 운전 프로필과 출력 byte 상한)은 끝까지 열려 있었다(M-0560, M-0584). 이 구현은 10-21 사용자 결정으로 삭제됐다(M-0593). 노드가 가리키는 추적 진입점은 10-30 정리로 작업트리에서 사라졌고 `git show dbde17f4:<경로>`로만 회수된다(공통 계약 3.4절의 M-0622).

## 2. 종합 초안

이 범위의 노드 36개 가운데 34개는 같은 형식의 회차 기록이다. manager가 직전 task의 반환을 검수하고, 공용 판단을 갱신하고, 다음 task를 배정한 뒤 관리 커밋 하나에 노드 하나를 남겼다. 그래서 종합의 대상은 개별 제품 결함이 아니라 이 반복의 방법이다. 아래 여섯 원리는 회차마다 되풀이된 검수 판단, 검사 도구에서 나온 실패, 배정의 범위와 분해 단위, 중단 뒤 복구에서 추출했다. 다룬 제품(옛 do-math)은 M-0593으로 삭제됐으므로, 각 원리는 구현과 무관하게 위임 작업을 검수하고 배정하는 일에 성립하는 범위로만 쓴다.

### 회차 검수는 반환 보고를 승인하지 않고 원자료를 다시 세어 닫았다

manager는 task의 `complete`나 통과 수를 그대로 받지 않았다. 반환이 주장하는 성과를 원자료에서 다시 센 결과가 그 주장을 지지할 때만 회차를 닫았다. 노드마다 되풀이된 검수 항목은 다섯이다.

1. **통과 주장의 재계수.** 선택한 시험 ID, 실제 결과의 고유 row, 실제 종료 코드를 정본과 미러에서 따로 대조했다. 최종 58개 선택과 실제 58 passed row를 맞대거나 [[M-0552]], 양쪽 136건의 선택·고유 row·실제 exit를 확인했다 [[M-0561]]. 같은 200 선택 가운데 199 passed와 권한 조건의 skip 1을 구별해 적었다 [[M-0570]] [[M-0569]].
2. **실행한 판본의 결속.** 시작과 종료 시점의 소스 전체 해시와 허용된 변경 집합을 대조했다. 종료 파일 2206개의 해시 [[M-0552]], 2658개 파일과 허용 22변경 [[M-0562]]이 그 예다. 관련 회귀를 새 판본의 근거로 재사용할 때에는 그 회귀가 실제로 돈 tree를 따로 확인했다. 미러 생성 전 tree에서 돈 정본 검사와 미러 생성 뒤의 최종 판본을 구별한 사례가 있다 [[M-0568]]. 첫 통과 뒤 문구가 바뀌자 최종 판본의 실행을 인도 근거로 삼은 사례도 있다 [[M-0579]]. 파일 일부가 바뀐 뒤에는 영향받지 않은 하위 성질만 재사용했다. 하위 성질이 불변이라는 사실을 전체 소스의 동등성으로 읽지 않았다 [[M-0572]] [[M-0574]].
3. **실제 반환의 직접 검수.** 검사의 통과 대신 task가 만든 실제 역할 입력과 반환을 직접 셌다. 반환 각 107개와 제안 전문 1개 [[M-0574]], 실제 trust 반환 122개 [[M-0575]]가 그 예다. 이 검수에서 공식 검사가 놓친 결함이 나왔다(아래 유효성 문단).
4. **실패의 보존.** 원 실패와 중간 오류를 지우지 않고, 이전 실패는 같은 ID의 새 근거로 닫았다 [[M-0561]]. 초기 오류를 뒤의 통과로 소급해 성공으로 바꾸지 않았다 [[M-0562]] [[M-0564]] [[M-0583]]. task 원보고는 고치지 않고, 정정은 manager의 공용 판단에만 적었다 [[M-0563]].
5. **제품 커밋의 보류.** 관련 실패가 남은 제품 변경은 작업트리에 두었다. 대신 현재 바이트를 압축 archive로 관리 커밋에 보존했고, 관련 회귀를 검수한 뒤 여러 회차의 변경을 함께 커밋했다 [[M-0553]] [[M-0556]] [[M-0557]] [[M-0565]]. archive는 실패 상태의 증거이며 승인된 판본이나 사용자 조작을 되돌릴 권한이 아니라고 매번 적었다 [[M-0553]] [[M-0555]].

부분 성공을 상위 목표(G1~G8)의 충족으로 올리지 않는다는 한정은 모든 회차 노드에 있다. 작성한 기록의 수를 진척으로 세지 않았다 [[M-0551]].

이 검수가 없었으면 얻지 못했을 결과가 셋 있다. 첫째, 작은 protocol_probe의 이전 성공을 실제 역할 schema의 수락으로 넓히지 않았다. 그래서 Codex가 선택 필드 때문에 실제 schema를 HTTP 400으로 거부한 것을 구체적인 제품 경계 실패로 기록할 수 있었다 [[M-0553]]. 둘째, 관련 검사가 양쪽 269건 통과했는데도 실제 검토 입력에 현재 제안 전문이 두 번 지급된 것을 찾아 미충족으로 유지했다 [[M-0571]]. 셋째, task 보고의 "PID 미관측"이라는 보수적 문장이 원자료보다 좁았다. manager가 live 원자료에서 해당 pythonw 관측을 찾아 공용 판단의 적용 범위를 정정했다 [[M-0563]]. 셋째 사례는 요약이 원자료보다 넓게 주장하는 오류뿐 아니라 좁게 주장하는 오류도 대조 대상이라는 것을 보인다. 좁은 요약을 방치하면 이후 세션이 이미 있는 증거를 다시 구하거나 없는 것으로 판단한다. 인도 단계에서는 수용 manifest 2436개와 Git 제품 2168개의 차이를 모집단 대조로 풀었다. 차이 268개가 Git 제외 캐시와 생성 자료라는 것을 확인한 뒤에야 제품 누락이 아니라고 판단했다 [[M-0584]].

L-0016 "회수 검증"은 이미 반환문보다 실제 파일을 우선하고, 판정과 수치를 따로 검증하라고 한다. 이 루프가 더한 것은 세 가지다. 실행한 판본을 해시로 결속하고 하위 성질만 재사용하는 경계, 좁게 쓴 요약의 대조, 관련 회귀를 검수하기 전 제품 커밋의 보류와 바이트 보존이다. 1번의 재계수 단위는 "수치를 따로 검증한다"의 구체형이어서 재실증에 가깝다. 4번의 실패 보존은 L-0001 "검증 계약"에 이미 있다.

판정: 새 정보(실행 판본의 결속, 좁은 요약, 커밋 보류). 재실증(재계수 단위, 실패 보존). 대조: L-0016 "회수 검증", L-0001 "검증 계약".

### 검수자의 검산기와 시험 관찰자가 결함의 출처가 됐다

이 루프에서 가장 자주 되풀이된 실패는 제품이 아니라 검사 도구 쪽에서 났다. 검사 도구의 실패는 처음에 검사 대상의 결함처럼 보인다. 그래서 대상에 결함을 돌리기 전에, 검사 도구가 대상에 대해 세운 가정이 실제 자료와 맞는지 먼저 확인해야 했다.

**manager의 보조 검산기가 7개 노드에서 8번 실패했다.** 실패한 가정은 다음과 같다.

- 시작 전에 바뀐 engine 문서까지 전체가 불변이라고 단언했다 [[M-0555]].
- manifest가 명시적으로 예외로 둔 비용 캐시까지 시작 해시와 같다고 가정했다. 실제로는 976개 중 비캐시 975개만 같았다 [[M-0560]].
- 같은 diff를 다른 파일 순서로 연결해 문자열 비교에서 실패했다 [[M-0561]].
- 미러 생성 전의 tree가 최종 판본과 같아야 한다고 요구했다 [[M-0568]].
- `str(list)`의 따옴표 표현을 원 오류문에서 검색했다 [[M-0573]].
- 이전 task의 원본 경로 관례를 이번 task에 가정해 FileNotFoundError가 났다 [[M-0574]].
- 코드펜스를 한 행으로 다루었고, 공식 row의 위치를 잘못 읽었다 [[M-0576]].

모두 검산기가 자료에 없는 불변식이나 표현을 기대한 경우다. 계약보다 넓은 불변 범위, 직렬화 순서, 문자열 표현, 다른 작업의 관례가 그 기대였다. 처리는 모든 사례에서 같았다. 원 실패를 남기고, manifest의 예외나 실제 protocol처럼 자료 구조와 계약을 읽은 뒤 검산기를 고쳤다. 제품과 task 자료는 고치지 않았다.

**task 안의 시험 관찰자도 같은 방식으로 실패했다.**

- camelCase 키를 읽어 structured 본문을 부재로 기록했다 [[M-0564]].
- 실제 입력에 없는 `action.role` 키를 가정했다 [[M-0573]].
- 데코레이터를 실제 생산자로 오인했다 [[M-0574]].
- 넓게 시도한 포장 캡처가 archive 바이트를 JSON으로 직렬화하지 못해 suite마다 24건 실패했다 [[M-0575]].

관찰자의 정정은 같은 원바이트를 고친 관찰자로 다시 검사하는 방식으로 했고, 새 유료 호출은 쓰지 않았다 [[M-0564]]. 관찰 범위의 공백은 제품 실패와 나누어 판정했고, 실패한 넓은 캡처를 새 근거로 승인하지 않았다 [[M-0575]].

**관찰 도구가 대상의 상태를 바꾼 사례가 하나 있다.** 같은 프로세스 안의 관찰 코드가 AttachConsole·FreeConsole을 호출하자 Job의 null stdin이 닫힌 핸들로 바뀌었다. 그 결과 Git의 DuplicateHandle이 실패했다(WinError6). 일반 자식 프로세스에서는 재현되지 않았고, 관찰을 별도 자식 프로세스로 옮기고 같은 실행 조건에서 정상 대조를 둔 뒤에야 제품 실패와 구별됐다 [[M-0566]] [[M-0565]].

L-0001 "검증 장치의 가치"는 수단(도구가 대상을 충실하게 읽는가)을 신뢰성의 한 축으로 둔다. L-0001 "검증 계약"도 검증 보조 코드의 실패를 제품 결함과 구별해 기록하라고 한다. 이 루프가 더한 것은 발현 형태 둘이다. 하나는 검수자 자신의 검산기다. 위임 작업을 검수하는 쪽의 도구가 위임받은 쪽의 결함을 만들어 보일 수 있고, 그 빈도가 이 루프에서는 회차 검수 노드 34개 중 7개였다. 다른 하나는 대상과 같은 프로세스에서 도는 관찰 도구의 부작용이다. 이때 필요한 것은 같은 실행 조건의 정상 대조다. L-0001 "거짓 GREEN을 막는 기준"의 양성 대조(0건 출력의 검증)와 같은 계열이지만, 대상이 빈 출력이 아니라 관찰이 바꾼 실행 상태라는 점이 다르다.

판정: 새 정보(발현 형태). 대조: L-0001 "검증 장치의 가치", L-0001 "검증 계약", L-0001 "거짓 GREEN을 막는 기준".

### 통과를 증언하지 못한 검사에는 다섯 모양이 있었다

회차마다 기존 검사의 통과가 실제로 무엇을 증언하는지 다시 따졌고, 통과했지만 필요한 성질을 증언하지 못한 검사가 다섯 모양으로 나왔다.

1. **성공 표본이 실패로 바뀌어도 통과하는 검사.** 전송 schema가 바뀐 뒤 source_request 없는 합성 성공 표본이 output_validation 실패를 반환했다. 그러나 실패 결과도 저장할 수 있었으므로 pair 검사는 통과했다. 일반 순회와 저장 검사가 있다는 사실로 성공 분기의 보존을 판단할 수 없었다 [[M-0556]]. 실제 collector 경로와 status·output·오류 단언을 연결하자, 새 단언이 "성공"이라고 이름 붙은 두 표본이 실패였다는 것을 잡았다 [[M-0557]]. 새 단언이 실제로 실패를 잡는지는 성공 표본을 실패로 바꾸어 확인하게 했다 [[M-0556]].
2. **전달 일치만 보는 검사.** 실제 생산값과 최종 입력을 비교하는 검사는 전달이 일치한다는 것을 입증한다. 그러나 생산값 자체가 계약을 어기면 그대로 통과한다. 계약에서 얻은 불변식(제안 전문의 사본 수 1)을 최종 반환에 따로 단언하자, 공식 green과 다른 결과가 나왔다 [[M-0571]]. 수리 뒤에는 보존된 최종 반환을 양쪽 각 80개씩 재귀 검산해 전문 1개를 확인했다 [[M-0572]]. 비교 검사를 버리지 않고, 그 검사의 주장과 독립적으로 확인할 불변식을 구별한 대응이다 [[M-0571]].
3. **시작 사건이나 이름만 보는 검사.** 학술 MCP의 기존 probe는 시작 사건에 도구 이름이 있다는 사실만 검사했다 [[M-0563]]. 새 관찰자는 같은 ID의 성공 완료와 실제 서버의 자료원 요약을 검사했고, 기대 동작은 폴더 존재라는 대리 표지가 아니라 서버 원문에서 정했다 [[M-0564]]. 문서 이름 검사의 통과도 검사기가 다루지 않는 표현(단계 소유, 부분 JSON 예시, 명령 모드)까지 보증하지 않았다 [[M-0576]].
4. **차용 반례를 거부하지 못하는 검사.** 파일 해시가 같아도 그 바이트가 다른 실행 경로에서 차용됐을 수 있다. 검사는 workspace, task·execution 좌표, 저장 artifact와 snapshot을 함께 대조해 소유를 판정했다 [[M-0569]]. 지급 명령과 파일 해시가 맞는 다른 archive를 함께 넣은 반례 [[M-0570]], 다른 check나 후보를 차용한 반례 [[M-0572]], 존재하는 단어를 다른 역할의 산출로 차용한 오류 [[M-0577]]를 시험이 거부하게 했다. 해시나 이름의 일치는 그 산출의 소유를 증언하지 않는다.
5. **모집단이 다른 검사의 결과를 합치는 판단.** 앞선 문서 관련 선택의 성공과 이번 전건 smell 검사의 실패는 검사 모집단이 달랐다 [[M-0560]]. 한 보고의 출현 수 1223은 inline 849와 fence 374의 합이어서 다른 보고의 수와 같은 단위로 합산하지 않았다 [[M-0578]]. "정확한 8문장"이라는 보고는 실제로 이름별 8항목과 고유 4문단이었다 [[M-0574]].

L-0001 "거짓 GREEN을 막는 기준"은 exit 0, 0건 대상, skip, fake 기본값, 수정 무력화 프로브, 음성 시험의 사유 고정, 모르는 시험 ID를 다룬다. 1·2·4는 이 목록에 없는 모양이다. 1은 실패도 정상 경로로 저장되는 구조에서 성공 분기의 검사가 사라지는 경우다. 2는 비교 검사가 양쪽이 함께 틀린 경우를 통과시키는 경우다. 4는 정상 산출의 일치 대신 소유를 검사해야 하는 경우다. 3은 L-0001 "검증 계약"의 "작은 실호출 검사는 실제로 거친 경로만 입증한다"와 L-0005의 대리 표지 항목을, 5는 L-0001 "검증 계약"의 "서로 다른 증거" 구별을 재실증한다.

판정: 새 정보(1, 2, 4). 재실증(3, 5). 대조: L-0001 "거짓 GREEN을 막는 기준", L-0001 "검증 계약", L-0005 "대리 표지로 축소나 검사를 제안하기 전의 확인".

### partial 반환의 상당수는 배정한 쓰기 범위의 공백에서 생겼다

task가 partial로 돌아온 회차 가운데 셋은 작업자가 실패한 것이 아니었다. 배정이 의무를 수행할 위치를 쓰기 범위에서 뺐기 때문이다.

- 녹화 원바이트를 지키는 의무가 있었는데, 이전 배정은 상위 Git 속성만 쓰기 범위에 넣었다. 실제 변환은 하위 corpus의 명시적 text 예외에서 생겼다. 작업자는 상위 규칙으로 하위 예외를 덮을 수 없다는 실제 결과를 남기고 원상 복원한 뒤 partial로 반환했다. 다음 배정은 하위 정본과 생성 사본 두 파일만 더 허용했다. manager는 범위를 넓힌 이유를 "새 요구가 아니라 기존 원바이트 의무를 수행할 위치가 배정에서 빠졌기 때문"이라고 적었다 [[M-0554]].
- 전송 schema의 수리가 외부 CLI fixture의 가정을 깼지만 그 fixture는 쓰기 범위 밖이었다. manager는 같은 도우미를 쓰는 다른 소비자까지 추적해 다음 쓰기 범위에 넣었다 [[M-0556]].
- 쓰기 목록에는 CLI 문서가 있었지만 objective가 P01 문장만 바꾸도록 한정했다. 작업자가 다른 절의 표기를 고치지 않고 partial로 반환한 것을 manager는 "그 경계를 지킨 판단"으로 판정했다. 다음 배정에는 확인된 원인, 고칠 표기, 정확한 실패 ID를 주어 수리 전 전체 재실행을 없앴다 [[M-0558]].

나머지 partial은 실제 미충족이었다. Codex의 schema 거부 [[M-0553]], 관련 선택의 실패 1건과 오류 1건 [[M-0560]], T4의 기능 실패 [[M-0565]], 정본 1오류 [[M-0567]], 제안 전문의 중복 지급 [[M-0571]]이 그것이다. 그러므로 partial의 원인은 범위 공백과 실제 미충족 두 갈래이고, manager는 반환마다 둘을 구별했다.

비동기 큐로 옮긴 뒤에는 배정 방식이 한 걸음 더 나갔다. 조사로 확인된 시험 공백은 조사만 끝내고 다시 파견하지 않고, 같은 task에서 수리하도록 쓰기 범위를 열었다. 반대로 아직 관측하지 않은 runtime 결함을 전제로 넓은 쓰기 권한은 주지 않았다 [[M-0581]] [[M-0582]].

L-0016 "파견 계약"은 읽기는 발견 절차로 열고 쓰기 범위와 임무는 닫으라고 한다. 이 루프는 그 닫힌 쓰기 범위가 의무의 실행 위치를 포함해야 한다는 조건을 보였다. 의무가 실제로 수행되는 곳은 하위 설정 파일이나 같은 도우미를 쓰는 다른 소비자일 수 있다. 범위를 닫기 전에 그 소비자를 추적하지 않으면, 범위를 지킨 작업자는 정당하게 partial을 낸다. 그 뒤의 범위 확장은 새 요구가 아니라 빠진 위치의 보충으로 기록한다.

판정: 새 정보. 대조: L-0016 "파견 계약", L-0016 "회수 검증"(변경 범위가 파견 계약과 일치하는가).

### 분해 단위는 문서 번호가 아니라 공유 수정 지점과 공유 파생물로 정했다

manager는 처음부터 소스 변경과 검사를 한 task로 묶고, 병렬성은 독립 읽기 검토에만 쓰기로 정했다 [[M-0550]]. 서로 다른 결함을 다루는 두 수리도 공식 생성기, 말뭉치, 캐시를 공유하면 같은 phase에 병렬로 배정하지 않았다 [[M-0553]]. 전건 검사가 다른 수정 파일을 읽고 미러 생성과 캐시를 공유하면 하나의 task가 소유했다 [[M-0560]] [[M-0561]] [[M-0562]]. 공통 helper와 미러·캐시를 동시에 바꾸는 제품 task는 독립 검증이 어려워 하나로 묶었다 [[M-0569]]. 두 task로 나누면 공유 helper·미러·캐시를 수정 중인 상대에게 검증이 의존한다는 것이 그 이유였다 [[M-0570]].

병렬로 돌린 것은 고정판을 읽기만 하는 조사였다. 읽기 조사는 변경 중인 시험·지침·캐시·미러와 다른 task의 결과를 소비하지 않게 경계를 정했다 [[M-0559]]. 과거 입력의 준비는 Git 불변 객체만 읽게 하고, 현재 코드를 실행하는 시험은 한 task만 소유하게 했다 [[M-0565]] [[M-0566]]. 정책·문서 이름 조사 셋 [[M-0575]], 288절 조사 셋 [[M-0577]], 요구표의 독립 질문 셋 [[M-0579]] [[M-0580]]이 같은 판본 위에서 병렬로 돌았다. manager는 "수정 중인 공통 helper를 읽는 동시 조사는 독립 검증이 아니다"라고 적었고, 조사 인원수를 늘리려고 task를 만들지 않았다 [[M-0571]].

phase 021을 검수한 회차의 기록에 따르면, 사용자는 문서(packet) 번호마다 phase를 반복하지 말고, 공유 수정 지점별로 묶고 독립 조사만 병렬화하라고 지시했다 [[M-0571]]. manager는 이 지시를 다음처럼 적용했다.

- 조사 뒤의 발견 넷을 단일 work 하나로 묶었다 [[M-0576]].
- 문구 4절과 검사 보강 14절을 별개 18작업으로 나누지 않고, 공유 doc_code·미러·관련 검사를 쓰는 실제 issue 8개로 묶어 한 담당자에게 맡겼다 [[M-0578]].
- 작업 크기는 작은 제목의 수가 아니라 실제 읽기 경계와 후보량으로 쟀다 [[M-0577]].

이 지시 전에도 phase 020 manager는 "packet 번호마다 한 phase를 고정하지 않"는 배정을 적었다 [[M-0570]]. 지시가 그보다 앞섰는지는 노드에 없다. 그러므로 이 교정은 manager가 처음부터 번호별로 분해한 결함의 교정일 수도 있고, 이미 움직이던 방향의 확정일 수도 있다. 확실한 것은 지시 이전의 문서 packet이 하나씩 회차를 받았다는 점이다. P01은 phase 008~009, P02는 019, P03은 020이었고, P04·P05가 처음 한 회차(021)로 묶였다 [[M-0558]] [[M-0559]] [[M-0569]] [[M-0570]]. 그 사이 phase 010~018은 문서가 아니라 실경계 작업이었다. 노드가 남긴 비용 진단은 "반복 회귀·미러·관리 비용은 파일 소유 충돌을 피하는 것만으로 줄지 않는다"이다 [[M-0571]].

L-0016 "분해와 병렬화"는 수정할 파일과 연결 지점으로 병렬 작업을 나누고, 같은 파일이나 같은 상태를 동시에 고치면 병렬화하지 않는다고 한다. 이 루프가 더한 것은 두 가지다. 첫째, 공유 상태에는 소스 파일뿐 아니라 생성된 미러, 말뭉치, 비용 캐시, 같은 기계의 공식 시험 실행 같은 파생물도 든다. 그래서 수정 파일이 겹치지 않아도 쓰기 작업은 병렬화할 수 없었다. 둘째, 쓰기 작업의 묶음 단위는 요구 문서의 번호가 아니라 그 작업들이 공유하는 수정 지점이다. 번호별로 나누면 회차마다 같은 회귀와 미러 검사와 관리 마감이 되풀이된다.

판정: 새 정보. 대조: L-0016 "분해와 병렬화", L-0016 "병렬 구현 파견".

### 중단된 manager는 관리 산출물의 실재로 복구했다

manager가 두 번 중단됐다. 두 복구는 모두 "무엇을 했다는 서술"이 아니라 "무엇이 실제로 존재하는가"로 판정했다.

phase 023에서는 작업자가 완료했지만 manager가 503/model capacity 오류로 제출 전에 끝났다. 사용자는 완료한 task를 다시 실행하지 말고 원보고와 현재 파일을 대조하라고 지시했다. 재시작한 manager는 manager.json뿐 아니라 pending 파일과 관리 자료가 실제로 있는지 확인했다. 이전 manager.log 외에는 관리 산출물이 없었다. 같은 phase를 실행기에 다시 주면 완료 작업과 로그를 덮을 수 있어, 다음 phase를 새 번호 024로 배정했다 [[M-0573]].

manager 029는 서비스 전환 때 게시와 관리 커밋 전에 중단됐다. 그 manager가 남긴 공용 문서와 기억 초안(M-0579)에는 아직 하지 않은 게시·압축·커밋을 완료처럼 서술한 부분이 있었다 [[M-0580]]. 비동기 큐의 첫 manager는 그 초안을 고치거나 지우지 않고 원바이트를 보존했다. 그리고 기존 검수 자료를 현재 소스 2675개와 원 task 129개 파일에 대조해 같은 최종 판본임을 확인했다. 완결된 제품 시험은 다시 돌리지 않았다. 이관된 성과는 시작판의 성과로 수용했고, accepted 목록에 가상의 task를 추가하지 않았다 [[M-0580]]. 초안 노드는 5일 뒤 작업트리 정리에서 "당시 판단의 보존이며 새 검증이 아니다"라는 머리말을 달고 커밋됐다 [[M-0579]].

L-0016 "통신과 재개"는 이미 완료한 비가역 행위를 반복하지 말고, 산출 파일과 마지막 판정을 먼저 읽으라고 한다. 이 루프가 더한 것은 세 가지다. 중단된 작성자의 초안은 행위보다 앞서 완료를 서술할 수 있으므로, 완료는 관리 산출물의 실재로 판정한다. 같은 작업 단위를 다시 실행기에 주는 것이 완료된 산출을 덮을 수 있으면 새 식별자로 잇는다. 이관된 성과를 새로 수행한 것처럼 기록하지 않는다.

판정: 새 정보(발현 형태), 재실증(완료한 행위의 비반복). 대조: L-0016 "통신과 재개", L-0016 "상태의 정본".

### 이 종합이 설명하지 않는 것

- 옛 구현의 기술적 발견은 다루지 않았다. Git clean 변환이 경로 표기에 따라 달랐던 관찰 [[M-0554]], Job close와 종료 완료의 차이 [[M-0567]] [[M-0568]], cwd 262자의 WinError267 [[M-0567]], Lean 컴파일 시간 [[M-0562]], 두 소비자의 decimal 표현 [[M-0583]]이 그 예다. 일부는 Windows·Git의 성질이라 구현이 삭제된 뒤에도 참일 수 있다. 그러나 L-0020의 실행 환경 절에 둘지는 G10~G12의 새 구조 판정과 함께 메인이 정한다.

## 4. 제안 초안

1. **기억 내부.** 7절 패킷대로 L-0001의 두 항목과 L-0016의 네 항목을 개정한다. 새 L 노드는 두지 않는다. 검수·배정 루프의 교훈은 위임 작업의 검수와 분해라는 L-0016의 영역에, 검사 도구의 결함과 통과의 증언 범위는 L-0001의 영역에 들어간다.
2. **프로젝트 소스: 없음.** 근거는 세 가지다. 첫째, 이 루프의 대상 구현은 M-0593으로 삭제됐다. 둘째, 사용자 교정(분해 단위)은 한 번이었고 같은 회차들 안에서 바로 적용됐다(M-0575·M-0576·M-0578). 그 뒤 재구축이 같은 문제를 다시 겪었다는 기록은 이 범위에 없다. 셋째, 반복된 실패 유형(검산기와 관찰자의 오류)은 모두 같은 회차 안에서 원자료 대조로 잡혔으므로, 기존 통제가 다루지 못한 결과가 없다. `services/continuous-development`와 `services/async-development`의 manager 지침에 분해 단위 기준을 넣을지는 재발 자료가 생기면 검토한다. 이 판단은 두 서비스의 현재 지침을 읽지 않은 상태의 판단이다.
3. **사용자 결정: 없음.** L01(출력 byte 상한과 운전 프로필)의 상신은 구현 삭제로 대상이 사라졌다.

## 5. 원장 입력

**가정한 관례와 그 이동.** 처음에는 이 범위가 G04~G08처럼 진행 기록의 연속이라 추출할 원리가 적을 것으로 보았다. 노드의 형식은 그 예상대로 34개가 회차 기록이었다. 그러나 회차마다 검수 판단의 근거를 적는 관례 덕분에, 같은 판단과 같은 실패 유형이 회차를 건너 반복되는 것을 셀 수 있었다. 그 반복이 2절 원리의 근거다. 진행 기록이라는 형식이 추출을 막지 않은 것은, 각 노드가 "무엇을 했다"에 그치지 않고 "판단에 남길 조건"을 따로 적었기 때문이다. 이 관찰은 세칙 「결정화 선별 관례」의 출발 기준과 정합하며, 세칙 개정을 요구하지 않는다.

**D-0010 원장의 세 질문.**

- (가) 병렬 구현 교훈의 재발: 증거 있음. M-0553·M-0560·M-0569·M-0570은 공유 생성기·미러·캐시를 이유로 쓰기 작업의 병렬 배정을 피했다. M-0582는 r07-fix와 r18-fix를 충돌 없이 통합했다. 이 범위에서 L-0016 "병렬 구현 파견"이 기록한 의미 충돌이나 구조 이동 순서의 실패는 재발하지 않았다. 다만 노드는 L-0016을 인용하지 않으므로 L이 원인이었다고 쓸 수 없고, 절차가 설계대로 돈 것은 그 설계의 유효성 증거가 아니다.
- (나) 마지막 수리 뒤 전체 시험이나 실제 연구 운전: 증거 있음(부분). 실제 경계 호출이 여럿 있었다. Codex·Claude 실호출(M-0553·M-0556), 실제 Mathlib 컴파일(M-0562), 예약 실발화(M-0563), 학술 MCP 완료 응답(M-0564), 같은 판본 양쪽 전체 T4(M-0568)가 그것이다. 그러나 전체 일반·fresh T3·전수 변이는 범위 끝까지 남았고(M-0584), 실제 연구 운전은 없었다. 구현은 이후 삭제됐다(M-0593).
- (다) 기존 제안에 대한 사용자 결정: 읽은 범위에 증거 없음. M-0563·M-0564가 학술 MCP를 실제로 호출했지만, scholarly-mcp 설치 전환의 결정은 아니다.

**특별 관찰 질문의 답.**

1. **한 회차의 검수 기준과 L-0016 "회수 검증"에 더하는 것.** 기준은 2절 첫 소절의 다섯 항목이다. 양쪽 N건 통과(선택·고유 row·실제 exit의 재계수), 실행 판본의 해시 결속, 실제 반환의 직접 검수, 실패의 보존과 같은 ID의 새 근거, 관련 회귀 전 제품 커밋 보류가 그것이다. 파견문이 든 "제품 불변 확인"은 2번(시작·종료 소스 해시와 허용 변경 집합)에 해당한다. "가상 수용 없이 격리 배정"은 두 사실로 나뉜다. 이관 성과를 가상 task로 기록하지 않은 것(M-0580)과, 공유 파생물을 쓰는 작업을 한 task가 소유하게 한 배정(2절 다섯째 소절)이다. L-0016에 더하는 것은 실행 판본 결속과 하위 성질 재사용 경계, 좁게 쓴 요약의 대조, 커밋 보류와 바이트 보존이다. 여기에 검수자 자신의 검산기 오류(L-0001 패킷으로 냄)와 쓰기 범위 공백에서 생긴 partial(L-0016 "파견 계약" 패킷)이 따른다.
2. **M-0594 대조에 관한 사실.** 결론은 메인이 G10과 맞대어 내리므로, 이 범위의 사실을 M-0594가 든 세 원인(만들 것이 작다, 결정이 미리 닫혔다, 독립 task가 병렬로 돌았다)에 맞추어 적는다.
   - *작업의 크기와 성격.* 기준선은 정본 969개 파일(M-0550)이었고, 회차 검수는 소스 2675개와 판본당 Python 875개를 대조했다(M-0569~M-0578). 상위 의무는 원문 19+11 의무, 보존 61, 원래 P2 12, 그리고 G1~G8이었고, 추적 109항목 중 101개가 planned였다(M-0550). 그런데 이 루프는 새로 만드는 작업이 아니라 이미 있는 큰 시스템의 검증 의무를 하나씩 닫는 작업이었다. 그러므로 90분 재구축과 같은 종류의 작업으로 비교할 수 없다는 점도 사실로 남는다.
   - *작게 쪼개져 길어진 이유.* 노드가 직접 보이는 원인은 넷이다. 쓰기 작업은 한 task가 소유하는 규칙이 처음부터 있었다(M-0550). 공유 생성기·말뭉치·캐시·미러 때문에 쓰기 작업을 병렬로 배정할 수 없었다(M-0553·M-0560·M-0570). 쓰기 범위 공백이 회차를 하나씩 더 만들었다(M-0554 다음 005, M-0556 다음 007, M-0558 다음 009). 사용자 교정 전까지 packet 번호별 회차가 이어졌다(M-0571). 회차마다 바이트 archive·preservation.json·관리 커밋·기억 노드를 만드는 관리 비용도 있었다(전 회차 노드). 시각으로는 phase 001~028이 약 29시간 걸려 한 회차에 평균 한 시간쯤이었다(노드 커밋 시각).
   - *열린 결정.* L01(실제 운전 프로필과 출력 byte 상한)은 M-0560에서 사용자에게 상신됐다. 범위 안에 답변 기록이 없고, M-0584에서도 남았다. G4 최종 보고의 처리 권위, G5 symlink/POSIX 환경, G7 현재 지원판 native 원자료도 외부 조건으로 남았고, 큐의 blocked는 그 대기였다(M-0584). M-0550은 "요구를 달성한 척 범위를 줄이"지 않도록 원래 요구를 고정했다. 그러므로 열린 결정을 manager가 스스로 닫을 수 있는 구조가 아니었다.
   - *병렬의 실제.* 반박 쪽 사실도 있다. 독립 읽기 조사는 여러 번 병렬로 돌았다(M-0559·M-0565·M-0575·M-0577·M-0579). 비동기 큐 전환 뒤 manager 0001·0005~0007의 노드는 10-15 02:13~03:21 사이에 커밋됐다(M-0580~M-0583). 그러므로 이 범위의 지연은 병렬 기능이 없어서가 아니라, 쓰기 작업이 공유 파생물로 묶였기 때문이라고 볼 수 있다.
   - *중단된 manager의 복구 비용.* phase 023 복구는 manager.json·pending·관리 자료의 실재 확인, 원 task 891개 파일 보존, 새 phase 번호 배정을 요구했다(M-0573). 노드 커밋 시각으로 M-0572(14:59)와 M-0573(21:47) 사이에 약 7시간이 비지만, 그 시간이 복구 비용인지 공급자 장애의 지속인지는 노드에 없다. manager 029의 복구는 현재 소스 2675개와 원 task 129개 파일의 재대조, legacy-029-raw.zip의 보존, 완료를 앞서 서술한 초안의 원바이트 보존을 요구했다(M-0580). 그 초안은 5일 뒤에야 커밋됐다(M-0579).
   - *노드 밖 확인.* `dbde17f4`의 `.async/dm/tasks`는 126개, `managers`는 106개 항목을 가진다. 이 범위의 노드가 다루는 manager는 0001·0005·0006·0007·0108뿐이다. 0008~0107(10-15 03:21 이후 10-18 03:32 이전)의 회차는 기억 노드가 없어, task 126개의 내용과 blocked의 원인은 이 범위로 확인할 수 없다. 메인이 대조하려면 `git show dbde17f4:.async/dm/...`가 진입점이다.

## 7. L 반영 패킷

L-0020 패킷은 내지 않는다. 이 범위의 사실은 모두 삭제된 옛 구현의 것이고, 구현과 무관하게 성립하는 원리는 L-0001과 L-0016이 담당한다(공통 계약 3.4절). 아래 문장의 예시는 옛 do-math 연속 개발의 과거 사례로 적었으며 현행 동작의 주장이 아니다.

### L-0001

**개정 항목: `## 검증 장치의 가치`**

검증의 신뢰성은 다음 네 측면에서 판단한다.

- 수단: 검증 도구가 실제 대상을 충실하게 읽는가
- 주체: 검증자가 작성자의 가정에서 충분히 독립적인가
- 절차: 실패 조건과 판정 기준을 계약으로 정했는가
- 범위: 위험이 있는 영역을 빠짐없이 검사하는가.

새 검증 장치를 만들기 전에 실패 비용을 먼저 정한다. 검사가 틀렸을 때 잃는 것이 작으면 검증 장치도 작게 유지한다. 검증 장치가 지키는 대상보다 더 큰 유지 비용을 요구하고 새로운 실패 가능성을 만들면 설계를 줄인다.

기계 검사를 제안하기 전에 그 규칙이 실제 자료에서 결함과 정상을 가르는지 잰다. 계약 반려를 미리 막으려던 문면 패턴 규칙은 실제 계약 판본 17개에서 승인된 계약 4건도 위반했고, 같은 검사 함수가 수신에도 쓰여 오탐이 생산 자체를 막을 구조였다. 측정 뒤 생산자의 선언을 문면과 상태에 대조하는 방식으로 바꿨다. [[M-0321]]

지침이나 절차의 효과를 비교로 시험하려면 기준 조건에서 그 실패가 실제로 나와야 한다. 작문 지침의 짝 비교에서 기준 조건의 글도 핵심 단계를 넘기지 않았으므로, 방향이 같았다는 관찰은 계기가 된 현상을 지침이 고친다는 증거가 되지 못했다. 조건당 한 편이면 표집 변동과 조건의 효과도 분리되지 않는다. [[M-0322]]

수단의 결함은 검증 도구 자신에서 나올 수 있다. 검사 도구의 실패는 처음에 대상의 결함처럼 보이므로, 대상에 결함을 돌리기 전에 그 도구가 세운 가정을 실제 자료와 계약에 대조한다. 옛 do-math의 연속 개발에서 위임 작업을 검수하던 관리자의 보조 검산기는 회차 검수 34회 가운데 7회에 걸쳐 8번 실패했다. 계약이 예외로 둔 캐시까지 불변이라고 가정했고, 같은 diff를 다른 순서로 연결해 문자열로 비교했고, 생성 사본을 만들기 전의 tree를 최종 판본과 같다고 요구했고, 다른 작업의 경로 관례를 가정했다. [[M-0555]] [[M-0560]] [[M-0561]] [[M-0568]] [[M-0573]] [[M-0574]] [[M-0576]] 시험 안의 관찰 코드도 키 표기를 잘못 읽거나, 입력에 없는 키를 가정하거나, 데코레이터를 생산자로 오인해 실패했다. [[M-0564]] [[M-0573]] [[M-0574]] [[M-0575]] 이런 실패에서는 원 실패를 남기고, 자료 구조와 계약을 읽은 뒤 도구를 고치고, 같은 원자료를 고친 도구로 다시 검사한다. 대상과 작업 자료는 고치지 않으며, 고친 도구의 결과를 원 실패의 소급 성공으로 적지 않는다. [[M-0564]] [[M-0575]]

관찰 코드가 대상과 같은 프로세스에서 돌면 대상의 실행 상태를 바꿀 수 있다. 관찰 코드의 콘솔 연결 호출(AttachConsole·FreeConsole)이 자식 프로세스의 표준 입력 핸들을 닫힌 핸들로 바꿔 Git 호출이 실패한 사례가 있다. 관찰을 별도 프로세스로 옮기고 같은 실행 조건의 정상 대조를 둔 뒤에야 제품 실패와 구별됐다. [[M-0566]]

기준 승계: [[M-0001]]의 일반 작업 템플릿.

**개정 항목: `## 거짓 GREEN을 막는 기준`**

GREEN은 명령의 exit 0만 뜻하지 않는다. 다음 조건을 모두 확인한다.

- 검사 대상이 0건이면 통과가 아니라 판정 불가인지 검토한다.
- 건너뛴 검사와 실행되지 않은 검사를 성공 건수에서 분리한다.
- fake의 기본값이 실제 시스템에서 가능한 상태인지 확인한다.
- 실제 운영 환경과 같은 구성과 경로에서 검사한다.
- 수정 담당자가 만든 테스트가 수정 방법 자체만 확인하는지, 필요한 동작까지 확인하는지 살핀다.
- 수정 내용을 무력화했을 때 테스트가 실패하는지 프로브로 확인한다.

음성 시험은 거부된 사실만이 아니라 거부 사유를 고정한다. 공유 스키마 노드를 제자리에서 고쳐 모든 문자열 필드가 한 값으로 제한된 결함은 실제 보충 조사 제출을 전부 거부했다. 그러나 기존 거부 시험은 "이슈가 하나라도 있으면" 통과하는 단언이어서 이 결함을 잡지 못했다. 같은 점검에서 엉뚱한 이유로 통과하던 음성 시험 2건을 사유를 고정해 강화했다. [[M-0350]]

실패 결과도 정상 경로로 저장되는 구조에서는, 저장할 수 있는지만 보는 검사가 성공 분기를 잃어도 통과한다. 합성 성공 표본이 출력 검증 실패를 반환했는데도 짝 검사가 통과했다. 실제 수집 경로와 상태·출력·오류 단언을 연결하자 성공이라고 이름 붙은 두 표본이 실패였음이 드러났다. 새 단언은 성공 표본을 실패로 바꾸었을 때 실제로 실패하는지로 확인한다. [[M-0556]] [[M-0557]]

두 값을 비교하는 검사는 전달의 일치만 입증한다. 생산값 자체가 계약을 어기면 비교는 그대로 통과한다. 생산값과 최종 입력의 비교가 공식 검사에서 통과한 상태에서, 계약에서 얻은 불변식(같은 전문은 한 번만 지급한다)을 최종 반환에 따로 단언하자 전문이 두 번 지급된 것이 드러났다. 비교 검사는 유지하고, 그 검사가 주장하지 않는 불변식을 별도로 단언한다. [[M-0571]] [[M-0572]]

해시나 이름의 일치는 산출의 소유를 증언하지 않는다. 같은 바이트를 다른 실행에서 가져오거나, 해시가 맞는 다른 묶음을 함께 넣거나, 다른 검사 결과나 다른 역할의 산출을 차용한 입력을 반례로 둔다. 소유는 작업 공간, 작업·실행 좌표, 저장된 산출물을 함께 대조해 판정한다. [[M-0569]] [[M-0570]] [[M-0572]] [[M-0577]]

시험 실행기는 선택 인자로 받은 시험 ID가 어떤 시험에도 맞지 않으면 거부한다. do-math의 실행기는 없는 ID가 있는 ID와 섞이면 조용히 버려 거짓 통과가 날 수 있었다. [[M-0351]]

빈 출력도 검증 결과가 아니다. 검색이나 회수 명령이 0건을 반환하면, 양성 대조 표본으로 명령이 대상을 찾을 수 있는지 먼저 확인한다.

기준 승계: [[M-0001]]의 일반 작업 템플릿.

### L-0016

**개정 항목: `## 분해와 병렬화`**

먼저 전체 산출물과 선행 관계를 파악하고, 서로 다른 형식의 입력에 반복 적용할 공통 처리가 있는지 확인한다. 실제 표본으로 의미·식별자·오류·비용을 확인한 뒤, 필요한 차이와 출처를 보존하면서 전체 비용을 줄일 수 있을 때 공통 표현으로 변환한다. 변환 자체가 새 부담이면 직접 처리한다. [[M-0002]] [[M-0137]] [[D-0002]]

병렬 작업은 수정할 파일과 작업 사이의 연결 지점을 기준으로 나눈다. 두 작업이 같은 파일이나 같은 상태를 동시에 고치면 병렬화하지 않거나 소유권을 분리한다. 공유 상태에는 소스 파일만이 아니라 생성된 사본(미러), 생성 자료, 비용 캐시, 같은 기계의 공식 시험 실행도 든다. 수정할 파일이 겹치지 않아도 이런 파생물을 함께 쓰는 쓰기 작업은 한 작업이 소유하게 한다. 수정 중인 공통 코드를 읽는 동시 조사는 독립 검증이 아니다. 병렬은 고정 판본만 읽고 공유 파생물을 쓰지 않는 조사에 쓰며, 조사자 수를 늘리려고 작업을 만들지 않는다. [[M-0550]] [[M-0553]] [[M-0559]] [[M-0565]] [[M-0570]] [[M-0571]]

쓰기 작업의 묶음 단위는 요구 문서의 번호가 아니라 그 작업들이 공유하는 수정 지점이다. 옛 do-math의 연속 개발에서 문서 packet마다 회차를 하나씩 배정하자, 회차마다 같은 관련 회귀·미러 검사·관리 마감이 되풀이됐다. 사용자는 공유 수정 지점별로 묶고 독립 조사만 병렬화하라고 지시했다. 이후 별개 18작업으로 보이던 발견은 같은 수정 지점을 쓰는 실제 결함 8개로 묶여 한 담당자에게 갔다. 작업 크기는 제목의 수가 아니라 실제 읽기 경계와 후보량으로 잰다. [[M-0571]] [[M-0576]] [[M-0577]] [[M-0578]]

분해 조건은 다음과 같다.

- 각 작업의 입력과 산출 경로를 명확히 정할 수 있다.
- 작업 사이의 선행 관계를 명시할 수 있다.
- 병합 후 확인할 연결 지점을 식별할 수 있다.
- 한 작업의 실패가 다른 작업의 정본을 오염시키지 않는다.

병렬화는 처리량을 늘리지만 공유 토큰 한도와 회수 비용도 늘린다. 각 단계가 끝날 때 상태를 파일에 기록해 한도 도달과 세션 교대에 대비한다.

독립 과제는 위임할 수 있지만 전체 목표의 해석, 공통 계약, 과제 간 충돌, 원본 통합과 종료 판단은 전체 맥락을 가진 담당자가 유지한다. 조사만 맡긴 작업자가 실행·승인 권한까지 가진 것으로 읽지 않도록 권한을 구별한다. 작은 자료의 교차 관계를 검증할 때는 영역을 나누는 것보다 서로 다른 관점이 전건을 보는 편이 나을 수 있다. [[M-0018]] [[M-0035]] [[D-0001]]

새 실행 환경을 대량 파견에 사용할 때에는 실행 조건의 중요한 차이를 포함하는 최소한의 대표 경로에서 실제 시작·반환·필요한 재개와 의존성 접근을 먼저 확인한다. 기존에 검증한 같은 경로를 매 파견마다 다시 시험하는 의무는 아니다. 사본에서만 생긴 실패는 원본의 기능 결함과 구별한다. [[M-0238]] [[M-0239]] [[M-0245]]

**개정 항목: `## 파견 계약`**

파견문에는 다음 항목을 둔다.

- 임무와 완료 기준
- 읽을 원본과 시작 좌표
- 수정할 수 있는 파일
- 수정하지 않을 파일
- 실행할 검증과 실패 조건
- 상신 조건
- 반환 서식
- 검사 결과가 없을 때 `없음`이라고 적는 규칙.

범위는 닫되 읽기 범위를 고정 파일 목록으로만 제한하지 않는다. 개체를 따라 정의 파일, 정본 문서, 결정 기록을 찾는 절차를 제공할 수 있다. 읽기는 발견 절차로 열고, 쓰기 범위와 임무는 닫는다.

닫힌 쓰기 범위는 의무가 실제로 수행되는 위치를 포함해야 한다. 그 위치는 하위 설정 파일이거나 같은 도우미를 쓰는 다른 소비자일 수 있다. 범위를 닫기 전에 실제 소비자를 추적하지 않으면, 범위를 지킨 작업자는 정당하게 부분 완료를 반환한다. 이때 다음 파견은 빠진 위치를 보충하고, 그 확장을 새 요구가 아니라 기존 의무의 수행 위치를 보충한 것으로 기록한다. 반환을 받는 쪽은 부분 완료가 범위의 공백 때문인지 실제 미충족 때문인지 구별한다. 확인된 원인, 고칠 위치, 정확한 실패 ID를 다음 파견에 주면 수리 전의 재실행을 생략할 수 있다. [[M-0554]] [[M-0556]] [[M-0558]]

조사로 확인된 공백을 수리할 권한은 같은 작업에 줄 수 있다. 그러면 조사만 끝내고 다시 파견하는 왕복이 없어진다. 반대로 아직 관측하지 않은 결함을 전제로 넓은 쓰기 권한을 열지 않는다. [[M-0581]] [[M-0582]]

기준 승계: [[M-0001]]의 일반 작업 템플릿.

**개정 항목: `## 통신과 재개`**

완료 통지의 수신자가 누구인지 런타임마다 확인한다. 재개한 에이전트의 완료 통지가 중간 오케스트레이터가 아니라 메인에 도착할 수 있다. 이 경우 완료 신호 파일을 상태 정본으로 삼는다.

중단된 작업을 재개할 때 이미 완료한 비가역 행위를 반복하지 않는다. 산출 파일, 마지막 판정, 남은 완료 기준을 먼저 읽고 다음 행위부터 잇는다.

중단된 작성자가 남긴 초안은 행위보다 앞서 완료를 서술할 수 있다. 관리자의 공용 문서와 기억 초안이 아직 하지 않은 게시·압축·커밋을 완료처럼 적은 사례가 있다. 재개는 그 서술이 아니라 관리 산출물의 실재로 판정한다. 중단 초안은 고치거나 지우지 않고 원바이트로 보존하며, 현재 판정은 새 기록에 쓴다. [[M-0573]] [[M-0579]] [[M-0580]]

같은 작업 단위를 실행기에 다시 주는 것이 완료된 산출이나 로그를 덮을 수 있으면, 다음 단위를 새 식별자로 잇는다. 이관받은 성과는 원 판본과 대조해 수용하되, 새로 수행한 작업으로 기록하지 않는다. [[M-0573]] [[M-0580]]

판정을 낸 검증자를 새 전범위 검증에 재사용하지 않는다. 기존 지적의 수정 확인과 새로운 독립 검증을 구별한다.

기준 승계: [[M-0001]]의 일반 작업 템플릿.

**개정 항목: `## 회수 검증`**

메인은 반환문보다 실제 파일을 우선한다. 다음 항목을 확인한다.

- 산출 파일이 실재하고 비어 있지 않은가
- 변경 범위가 파견 계약과 일치하는가
- 검증 명령이 실제 대상을 검사했는가
- 0건 출력이 검색 실패나 스키마 오독이 아닌가
- “완료”가 목표 완료 기준을 모두 충족하는가.

서브에이전트의 판정과 수치는 따로 검증한다. 필드의 사용 여부를 판정한 에이전트가 함께 보고한 평균 크기 23.6KB는 표본 6개의 편향이었고, 111실행 전수의 중앙값은 192바이트였다. 판정은 유지하고 크기는 전수 재계산 값을 썼다. [[M-0323]] 시험 통과의 주장은 선택한 시험 ID, 실제 결과의 고유 행, 실제 종료 코드로 다시 센다. 생성 사본이 있으면 정본과 사본에서 따로 센다. [[M-0552]] [[M-0561]] [[M-0570]]

관련 회귀를 새 판본의 근거로 쓰려면 그 회귀가 실제로 돈 판본을 해시로 확인한다. 생성 사본을 만들기 전에 돈 검사와 생성 뒤의 최종 판본은 서로 다른 tree다. 일부 파일이 바뀌었으면 그 변경의 영향을 받지 않는 하위 성질만 재사용한다. 하위 성질이 불변이라는 사실을 전체 판본의 동등성으로 읽지 않는다. [[M-0552]] [[M-0568]] [[M-0572]] [[M-0579]]

반환 요약은 원자료보다 좁게 주장할 수도 있다. 작업 보고가 관측하지 못했다고 적은 대상이 원자료에 있었고, 관리자가 공용 판단의 적용 범위를 정정했다. 좁은 요약을 그대로 두면 이후 세션이 이미 있는 증거를 놓친다. 원 보고는 고치지 않고 정정은 받는 쪽의 판단 기록에 적는다. [[M-0563]]

관련 실패가 남은 제품 변경은 검수 전에 커밋하지 않는다. 현재 바이트를 묶어 관리 기록에 보존하고, 관련 회귀를 검수한 뒤 함께 커밋한다. 보존 묶음은 당시 상태의 증거이며 승인된 판본이나 복원 지시가 아니다. [[M-0553]] [[M-0555]] [[M-0557]] [[M-0565]] 인도할 파일 수가 기대와 다르면 모집단을 대조한 뒤 누락을 판정한다. 수용 목록 2436개와 Git 제품 2168개의 차이 268개는 Git 제외 캐시와 생성 자료였다. [[M-0584]] 검수하는 쪽의 검산기가 결함의 출처가 된 사례와 처리는 [[L-0001]]의 검증 장치의 가치 항목에 있다.

항상 적재되는 프로젝트 지침은 파견된 에이전트에도 도달한다. 독해 에이전트 여덟(눈가림 독해 여섯, 대체 독해 둘) 가운데 눈가림 독해 하나가 학술 지식 복창을 반환 앞에 붙여 반환의 첫 낱말 계약을 어겼고, 나머지 일곱은 첫 낱말 계약을 지켰다. 파견문에 상시 지침이 요구하는 글은 앞선 응답에 쓰고 마지막 메시지는 반환 계약을 지키라고 적을 수 있다. 사용자는 규칙 추가 없이 관찰을 유지하고 재발하면 다시 보기로 했다. 규범 쪽의 정리는 [[L-0012]]에 있다. [[M-0322]] [[M-0326]]

문제점을 서술한 부정문을 긍정문으로 바꾸는 것만으로 완료 기준을 정하지 않는다. “X가 없다”를 “X를 만든다”로만 바꾸면 X를 읽고 쓰는 연결 지점이 빠질 수 있다. 수정으로 바뀌는 구조의 정의와 읽기·쓰기·검증 위치를 함께 정한다.

## 8. 작업 기록

- **경중 선언(합의 파일 대체).** 파견 계약이 다른 파일 생성을 금하므로 합의 파일 대신 여기에 적는다. 압축 진술: manager 루프는 회차마다 반환 보고 대신 원자료를 다시 세어 검수를 닫았다. 이 루프가 L에 더하는 것은 세 가지다. 검수자의 검산기와 시험 관찰자가 결함의 출처가 됐다는 것, partial의 상당수가 배정 쓰기 범위의 공백이었다는 것, 분해 단위가 문서 번호에서 공유 수정 지점으로 바뀌었다(사용자 교정)는 것이다. 무거운 것은 검수 기준과 그 새 발현, 검사 도구의 결함, 분해 단위다. 가벼운 것은 중단 복구, 증거 보존, 모델 지정, 원장이다. 뺄 것은 옛 구현의 기술 세부로, 2절 마지막 소절에 목록으로만 두었다.
- **정식 독해를 하지 않았다.** `write-for-reader`의 `writing_flow.py begin/read/decide`는 합의·독자 파일을 새로 만들어야 하는데, 파견 계약 1절과 파견 메시지가 초안 파일 하나 외의 쓰기를 금한다. 이 초안의 독립 검토는 적대 검증자(계약 9절)와 D 노드 단계의 독해 대조(세칙_dream v27)가 맡는다. 대체로 `경중_배분.md`의 독해 미실행 절차를 적용했다. 길이가 큰 대목 셋은 6절 표(형식이 계약으로 정해짐), 2절 첫 소절(무거운 것), 5절 질문 2의 답(파견 메시지가 요구한 무거운 것)이었고, 셋 모두 경중 선언과 맞는다.
- **작성 중 대조로 고친 오류.** 초안 첫 판에는 세 오류가 있었고, 노드와 다시 대조해 고쳤다. 회차 검수 노드 수(33을 34로), 시험 관찰자 오류 수(5를 4로, 관찰 부작용은 따로 셈), "phase 008~020이 packet 하나씩 진행됐다"는 서술(phase 010~018은 실경계 작업이어서 packet별 회차는 P01·P02·P03만 해당)이다.
- **예상과 다른 결과.** 이 범위가 진행 기록뿐이어서 추출할 것이 적으리라 보았다. 그러나 노드마다 "판단에 남길 조건" 절이 있어 같은 판단과 실패 유형을 회차를 건너 셀 수 있었다. 가장 많이 반복된 실패가 제품이 아니라 manager 자신의 검산기에서 났다는 점도 예상 밖이었다.
- **판단이 갈린 지점.** M-0570의 manager가 사용자 지시(M-0571에 기록) 전에 이미 packet 번호 고정을 풀었는지는 노드로 정할 수 없었다. 그래서 M-0571 교정의 β 해석(ⓒ)을 대안 가설과 함께 두었다. M-0550의 /goal 삭제도 대화 원문이 없어 교정이 아니라 방향 전환으로 기록했다.
- **범위 밖 확인.** `.async/dm`의 task 126개와 manager 106개는 노드가 아니라 `dbde17f4`의 Git 트리에서 센 값이다. manager 0008~0107은 기억 노드가 없어 내용을 보지 않았다. L-0015는 읽지 않았고 L-0005는 1~110행만 읽었다. 둘 다 패킷 대상이 아니다.
- **운영 사건.** 2~5절을 Bash heredoc으로 덧붙이는 첫 시도가 셸 파싱 오류로 아무것도 쓰지 못했다. 같은 내용을 Edit 도구로 파일 끝에 붙였다. 파일 내용에는 영향이 없다.
