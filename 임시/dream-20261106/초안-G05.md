## 1. 주제군 개요

G05는 옛 do-math의 후보 구현에 있던 시험을 기능 가족 단위로 main에 옮긴 통합 묶음 B39~B64의 기록이다. 여기서 후보 구현은 main과 따로 개발된 같은 제품의 구현이고(G04의 주제), 시험 가족은 한 기능 영역을 검사하는 시험 모듈과 그 정상 생산 도우미의 묶음이다. 노드 하나가 통합 하나에 대응하며, 각 노드는 앞 노드의 커밋을 확정한 뒤 다음 가족으로 넘어간다.

제품 코드 수리는 처음 두 통합에만 있다. B39(M-0455)는 닫힌 초기화의 재활성화와 종결 때 병합 요청 이유의 소실을 고쳤고, B40(M-0456)은 후보 결함 원장의 마지막 원재현 넷을 연결하며 남은 실패를 고쳤다. B41·B42(M-0457·M-0458)는 자기점검 진행 값과 반복 결과의 선언을 한 표로 모으고 실제 생산자 전건과 대조했다. B43~B55(M-0459~M-0471)는 계획, 저장, 승인·권한, 검토, 제출, 공급자, 배정·정산, 학술, 운영자, 지식, engine·CLI, 교차 사건의 가족을 차례로 옮겼다. 그 사이 B48(M-0464)은 공급자 통합의 선행 작업으로 병렬 호출 대역의 종료 동작을 실제 구현에 맞췄다. B56(M-0472)은 최종 관문의 판정 도구(실행기의 모듈 비용 색인, 공유 입력 출처, 변이 판정)를 고쳤고, B57(M-0473)은 문서 검사를 명령·필드·정책의 소유 범위로 좁혔다. B58~B63(M-0474~M-0479)은 새 파일이 아니라 기존 모듈 안에 빠져 있던 사례, 실제 설치·Git·Windows 경계, 재시작·복구 사례를 옮겼고, B64(M-0480)는 운전 문서를 갱신했다.

모든 통합 보고는 같은 형식을 따른다. 선택한 시험의 실행 ID, 통과 수와 시간, 사례별 예산 초과, 구조 시험 6개의 결과를 적는다. 그리고 원보고 경로·SHA256·파일 지문을 작업판의 `current_work.*` 항목에 연결한다. 모든 노드는 끝에 같은 최종 판본에서 돌릴 전체 관문이 남았다고 적었고, 마지막 노드(M-0480)는 다음 작업을 전체 일반 시험 1회 실행으로 정했다. 이 범위 안에 전체 관문의 결과는 없다. 옛 구현은 2026-10-21에 삭제됐으므로 이 기록의 제품·시험 구조 사실은 모두 현행이 아니다.

## 2. 종합 초안

26개 노드는 모두 같은 형식의 통합 진행 기록이다. 그 안에서 구현과 무관하게 성립하는 방법은 다섯 갈래로 모인다. 첫째와 둘째는 대역과 음성 시험을 어떻게 만들었는가이고, 셋째는 무엇이 거짓 통과를 만들었는가이며, 넷째는 완료와 시간 예산을 어떻게 판정했는가이다. 다섯째는 두 구현을 합치면서 정본 재사용과 새 사본을 어떻게 갈랐는가이다. 이 절의 "대역"은 시험이 실제 구성요소 대신 넣는 대체물(test double)을 뜻한다. "정상 생산자"는 제품의 실제 생산 경로를 거쳐 유효한 상태나 출력을 만드는 시험 도우미를 뜻한다.

### 대역은 외부 경계에만 두고, 대역 자체를 실제 구현과 같은 계약으로 시험했다

통합 시험은 대역을 제품이 통제하지 못하는 외부 경계에만 두었다. 제품의 수신·저장·판정은 실제 코드로 실행했다. 대역을 둔 곳은 외부 Lean 위치, 외부 HTTP 포트, 공급자 CLI의 spawn이었다. 반면 수신·저장·판정 함수는 실제 경로에 남겼고, 노드는 이를 "제품 판정을 대체하지 않는다"는 문장으로 거듭 적었다. [[M-0460]] [[M-0465]] [[M-0467]] 이 배치가 중요한 이유는 시험이 무엇을 증언하는가에 있다. 제품 함수를 대역으로 바꾸면 시험은 대역의 판정을 증언하고, 외부 경계에만 대역을 두면 시험 통과에 제품 판정 경로의 실행이 포함된다.

대역 자체도 실제 구현과 같은 계약으로 시험했고, 그렇게 해서 대역의 결함을 찾았다. 병렬 모델 호출 포트(Calls)의 대역은 종료(close) 때 thread가 아직 없는 계산을 건너뛰고 turn 목록을 지웠다. 그래서 실제 구현과 달리 결과나 예외를 만들지 않았다. 이미 완료를 넘긴 turn에 다시 응답을 주는 경로도 응답할 thread가 없어 기다림에 빠질 수 있었다. 기존 일반 계약 시험은 계산을 진행시킨 뒤 닫는 경로만 주로 보아서 이 차이를 놓쳤다. 같은 계약 시험을 실제 구현과 대역 양쪽에서 실행했더니 실제 구현은 통과하고 대역은 실패했다. 검사 범위도 미시작 계산, 대기 중인 시작 콜백, 반환 뒤 미수집, 중복 종료, 원 결과·예외의 identity, thread 생존까지 넓혔다. 교정은 제품 실행 코드가 아니라 대역에서 했다. [[M-0464]] 시험 공학에서 계약 시험(contract testing)이라 부르는 방법이다. 이 사례에서 새로 드러난 것은 대역의 결함이 정상 경로가 아니라 생애의 경계 상태에 숨어 있었다는 점이다.

시험에만 필요한 의미는 제품 포트에 넣지 않았다. 프로세스 상실의 모의는 정상 종료와 의미가 다르다. 그래서 시뮬레이터 전용 동작(`abandon_owner`)으로 두고, 제품 포트의 별칭이나 새 production 동작으로 넣지 않았다. 포트 문서에는 종료의 실제 의미를 적었다. 종료만으로 Job 종료나 예약 정산을 인증하지 않았고, 응답하지 않는 외부 계산에 새 시간 상한을 발명하지도 않았다. [[M-0464]] 이후 재시작 사례를 보강할 때도 두 동작을 다시 혼동하지 않도록 단언을 유지했다. [[M-0479]]

대역의 출처는 세 부류로 구별해 밝혔다. 실제 생산자가 만든 값, 원 실행을 녹화한 값, 명시적으로 합성한 값이다. 녹화라고 선언한 대역은 원 산출물과 지문으로 대조했다. Lean 출력 녹화의 경우, 통합 전에 옛 연구 인스턴스의 원 저장 JSON 파일을 수정 없이 읽었다. 그리고 파일 SHA256과 `formal_result.verification.stdout`의 UTF-8 길이 4,286,783바이트와 SHA256이 후보의 녹화 선언과 일치함을 확인했다. [[M-0469]] 합성 출력 생산자는 이름과 문서에 합성임을 밝히고 실제 녹화라고 주장하지 않았다. [[M-0469]] 대역은 각자의 출처가 입증하는 것만 증언했다. 원 녹화의 재생은 새 compiler 호출의 증거가 아니라고 적었다. [[M-0470]] 기록용 HTTP 증거는 원격 제출이나 청구액의 증거가 아니라고 적었다. [[M-0467]] 사용량 수치만 바꾼 spawn 대역은 실제 모델 호출의 증거가 아니라고 적었다. [[M-0465]] 실제 regression을 돌리지 않은 설치 보고는 합성 보고라고 명시했다. [[M-0471]]

실제 경계의 시험은 제품 함수를 patch하지 않았다. 대신 시험이 소유한 실제 자원으로 실제 실패를 만들었다. Windows 정션은 시험 Temp 안의 바깥 디렉터리를 입력 경로에 연결했고, 경로 탈출이 읽기·쓰기로 실행되지 않으며 바깥 내용이 변하지 않음을 확인했다. Git 경계 시험은 특정 `cat-file --batch` 읽기 하나에만 잘못된 실행 파일을 요청해 실제 `CreateProcess` 오류를 만들었다. 프로세스 종료 증거는 그 시험이 만든 자식 프로세스에서만 취했고, 다른 시스템 프로세스를 종료하거나 관찰 대상으로 늘리지 않았다. [[M-0478]]

판정: 새 정보. 대조한 L 항목은 셋이다.
- `L-0001` "검증 계약": 수작업 값이나 오래된 대역 대신 실제 생산자를 따르라는 문단과, 증거 종류를 구별하라는 문단. 출처별 증언 범위는 이 문단의 재실증이다.
- `L-0001` "검증 사각의 세 축": 대역·fixture의 전제.
- `L-0001` "거짓 GREEN을 막는 기준": fake 기본값의 실제 가능성.

L-0001에 없던 것은 네 가지다. 대역의 배치 위치(외부 경계), 대역 자체에 대한 공통 계약 시험, 시험 전용 의미의 격리, 녹화 대역의 지문 대조다. 이 소절이 파견 질문 3의 답이다.

### 음성 시험은 정상 생산 결과에서 한 좌표만 바꾸고, 거부 사유와 이전 상태를 함께 고정했다

통합된 음성 시험은 같은 방식으로 거부 입력을 만들었다. 먼저 정상 생산자로 유효한 결과를 실제 저장소에 만든다. 그 사본에서 필드나 좌표 하나만 손상시킨 다음, 정확한 오류 문언과 거부 뒤 이전 상태의 불변을 함께 단언한다. 승인·권한 가족은 정확한 `ValueError` 문언만 인정했고, 저장된 이전 head의 상태가 그대로인지 확인했으며, 단순한 예외 발생이나 필드 개수로 통과시키지 않았다. [[M-0461]] 설치 기동 시험은 실제 설치의 동결 manifest와 파일을 읽어 바이트 변경, 파일 대신 디렉터리, 누락 항목, 미래 mtime, 탈출 경로를 하나씩 넣고, 검증되지 않은 캐시가 게시되지 않음을 확인했다. [[M-0468]]

이 방식은 두 가지를 함께 얻는다. 시험 하나가 규칙 하나만 검사하므로 다른 이유로 거부되어 통과하는 경우가 줄어든다. 또 입력이 실제 생산자에서 나오므로 생산자의 계약이 바뀌면 입력도 따라간다. 반대로 기대 상태에 맞추려고 생산자가 만들지 않는 필드를 손으로 덧붙이는 일은 하지 않았다. 초기 진단 시험의 입력을 고칠 때 status 필드를 손으로 붙이는 대신, 구조상 유효한 외곽에서 summary만 잘못된 배열로 바꾸어 실제 수신 경로가 반려 영수증을 만들게 했다. 이 교정은 좌표 오기, 등록 누락, import 부재라는 세 번의 실패를 거쳤다. 실패마다 원 traceback을 보존했고 기대값이나 제품 guard를 완화하지 않았다. [[M-0466]] 구조상 정상인 외곽은 의미상 정상 수신의 증거가 아니라는 구별도 함께 지켰다. [[M-0463]] [[M-0466]]

판정: 새 정보(새 발현). 대조한 L 항목은 `L-0001` "거짓 GREEN을 막는 기준"의 음성 시험 문단(거부 사유의 고정)과 `L-0001` "검증 계약"의 생산자 추종 문단이다. 사유 고정과 생산자 추종은 L-0001에 따로 있다. 새로운 것은 둘을 한 입력 구성법(정상 생산 결과에서 한 좌표 변경)으로 묶은 것과 거부 뒤 이전 상태 불변의 단언이다.

### 과거 결함이나 옛 계약에 묶인 시험 장치는 현재 상태가 바뀌어도 통과했다

통합 중 고친 거짓 통과의 원천은 공통점이 있다. 검사가 현재의 소유자나 현재 계약이 아니라 과거의 어떤 상태에 묶여 있었다. 그래서 현재 상태가 바뀌어도 검사는 계속 통과하거나 엉뚱한 이유로 실패했다. 노드에 기록된 형태는 넷이다.

1. **알려진 결함의 허용.** 후보의 교차 시험에는 알려진 결함을 관찰 허용 목록으로 받아들이는 분기가 있었다. expectedFailure 포착과, 과거 오류를 잡아 통과할 수 있는 if/except 분기도 있었다. 결함이 고쳐진 뒤에도 이 장치들은 결함의 재발을 통과로 셀 수 있었다. 통합은 이 분기들을 제거하고 현재 성공 계약을 무조건 단언했다. [[M-0471]] 같은 허용 분기를 가진 후보 메서드는 복사하지 않고, 현재 계약을 검사하는 새 시험으로 대신했다. [[M-0477]]
2. **옛 계약의 기대값.** 한 기존 시험은 변조한 malformed 재전달이 `ValueError`를 던져야 한다고 기대했다. 현재 계약은 최초 반려를 내구적으로 유지하고, 같은 파일 이름의 재전달이 뒤 정상 요청을 굶기지 않는 것이었다. 제품은 그대로 두고 시험을 현재 계약으로 고쳤다. 겉으로 비슷한 다른 계약(같은 request_id에 다른 payload가 오면 거부)은 기존 수송 시험에 그대로 두어 둘을 혼동하지 않았다. [[M-0470]]
3. **소스 행 번호.** 행 번호에 묶인 단언은 코드가 움직이면 낡는다. Git 복원 시험의 옛 1082~1084행 단언이 실패했다. 이 단언을 숫자만 바꾸지 않고, inspect·AST로 현재 소스의 해당 except 처리기를 찾은 뒤 그 좌표가 실행 관찰(`sys.monitoring`)에 도달했는지 검사하도록 바꿨다. 도달 검사는 지우지 않았다. [[M-0478]] 배정 가족도 낡은 행 번호를 현재 소유 함수의 이름으로 연결했다. [[M-0466]]
4. **소유자를 합친 검사 어휘.** 문서 검사는 모든 제품 문자열의 flag를 합친 어휘를 썼다. 그래서 다른 명령의 옵션이 같은 줄의 잘못된 명령을 통과시킬 수 있었다. 실제 parser의 명령별 옵션과 필드를 소유한 schema를 기준으로 검사하도록 바꾸자, 문서의 잘못된 표기 둘이 드러났다. README가 외부 Claude 옵션을 `--bare`로만 적어 do-math의 flag처럼 보이게 한 것과, 초기 입력의 goal을 저장 설정 schema에 없는 `config.goal`로 적은 것이다. 검사가 다루지 않는 모집단(미등록 namespace, 한정되지 않은 이름)은 완비로 주장하지 않았다. [[M-0473]]

판정: 새 정보. 대조한 L 항목은 `L-0001` "거짓 GREEN을 막는 기준"과 `L-0001` "검증 사각의 세 축"이다. "검증 사각의 세 축"에는 정적 검사가 자신이 아는 구문 형태만 인식한다는 문장이 있다. 위 네 형태는 L-0001에 없다. 이 넷의 공통점은 검사를 현재 소유자(현재 계약, 현재 코드 개체, 명령별 parser)에 묶으면 해소된다는 것이다.

### 완료와 시간 예산은 통과 수와 별개의 판정이었다

통합의 26개 보고는 완료를 하나의 조건으로만 말했다. 그 조건은 같은 최종 판본에서 선언한 관문을 모두 통과하는 것이다. 선언한 관문은 노드의 표기로 전체 일반 시험(T2와 flows), 재사용 없는 T3(fresh T3), 모든 함수의 극단 변이, 시간 예산, 최소 실호출(T4·T5)이다. 다음 네 가지는 매번 그 대체가 아니라고 적었다. 부분 가족의 통과 수, 결함 원장의 미결 0건(원장 0open), 파일의 존재, 시험 개수다. [[M-0456]] [[M-0458]] [[M-0471]] 이 원칙을 지킨 결과, 26회의 부분 통합이 끝날 때까지 이 범위 안에 전체 관문의 결과는 없다. 전체 일반 시험 1회 실행은 마지막 노드가 다음 작업으로 정했다. [[M-0480]]

완료 판정은 세 가지 규칙으로 집행됐다.

- **판본이 다른 부분 보고는 합산하지 않는다.** 최초 실행과 도우미를 교정한 뒤의 재실행은 판본이 다르다. 그래서 두 통과 수를 더해 같은 최종 판본의 전체 통과라고 쓰지 않았다. [[M-0459]] [[M-0466]] [[M-0470]] 각 보고는 원 경로, SHA256, 실행 시점의 파일 지문, 실행 중 소스 변경이 없었다는 기록(`changed_during_run` 비어 있음)으로 자기 판본에 묶었다. [[M-0456]] [[M-0460]]
- **끝나지 않은 실행은 끝나지 않은 결과로 남긴다.** 감시 상한 300초에 걸린 실행은 complete=false와 8passed/5not_run을 그대로 보존했다. 전제 오류를 확인해 실행을 끊을 때에는 대상 worker의 PID·부모·명령 줄을 확인한 뒤 명시적으로 종료했다. [[M-0455]] 다른 worker가 끝났다는 사실이나 관찰 대기만으로 진행 중 실행을 종료하거나 재시작하지 않았고, 부모의 최종 보고를 확인했다. [[M-0459]] [[M-0462]] [[M-0466]]
- **결과가 없는 사례는 통과가 아니다.** 한 보고는 complete=true이면서 successful=false였다. 모듈 준비 단계의 오류 3행은 보고의 사례 집계(counts)에 들어가지 않고 setUpModule traceback에만 남아 있었다. 원인은 main에 아직 없는 도우미를 참조한 준비 배선이었다. 그래서 제품 실패나 실행 제한 초과로 분류하지 않았다. [[M-0459]] 변이 시험의 판정 도구도 같은 원리로 고쳤다. 변이체의 결과가 없으면 kill이 아니라 실행 오류다. 변이체의 시간 초과는 변이하지 않은 같은 선택이 같은 상한 안에 성공할 때만 kill로 인정한다. 기준 실행 실패, 변이 오류, 실행 오류, 미실행이 하나라도 있으면 살아남은 변이가 0건이어도 관문을 통과시키지 않는다. [[M-0472]]

시간 예산은 통과와 별개의 판정 축이었다. 층마다 사례별 상한이 있었다. 단위 0.2초, sim 2초, flows 60초, 실경계 30초, 구조 냄새 검사(smell) 5초다. 그 위에 전체 일반 시험의 300초 기준이 있었다. [[M-0455]] [[M-0456]] [[M-0457]] [[M-0461]] [[M-0478]] 26개 노드 가운데 24개가 상한을 넘은 사례를 수치와 함께 보존했다. 이 가운데 M-0458은 사례별 초과는 없고 구조 냄새 검사 하나만 5초를 넘었다. 나머지 둘 가운데 M-0472는 예산을 언급하지 않았고 M-0480은 초과가 없었다. 파견 질문 2가 지목한 여섯 노드(M-0460·M-0461·M-0462·M-0467·M-0468·M-0469)는 이 24개의 일부다. 초과 건수가 큰 M-0466(22개)과 M-0470(39개)도 같은 형태다. 초과는 전체 성공으로 숨기지 않았다. [[M-0456]]

예산을 맞추려고 검사를 줄이지 않았다. 조합, 반려·재전달 검사, 규모와 예제 수를 빼지 않았다. 단언을 약하게 하지 않았고, 제품 판정을 대역으로 바꾸어 시간을 맞추지도 않았다. [[M-0457]] [[M-0460]] [[M-0461]] 승인 가족 하나만 231초가 걸린 결과는, 전체 300초 기준을 별도의 작업으로 개선해야 할 근거로 기록됐다. [[M-0461]] 비용의 분류와 비교도 실측에 묶었다. 단위 층의 새 시험도 실제 저장 상태를 준비·복원하는 비용이 있어서, 층의 이름만 보고 값싼 순수 시험으로 분류하지 않았다. [[M-0461]] 선택 범위가 다른 이전 실행과 비교해 속도 향상 배수를 주장하지 않았다. [[M-0455]] [[M-0460]] 시험 실행기의 모듈별 비용 색인은 전체 모듈이 실제로 끝난 실행만 기록하게 고쳤다. 부분 선택이 17초짜리 전체 모듈 비용을 8초로 덮어쓰는 실패를 재현했기 때문이다. [[M-0472]]

판정은 부분마다 다르다.
- **재실증**: 판본이 다른 보고의 비합산, 미완료의 보존, 예산을 맞추려고 검사를 줄이지 않는 원칙. 대조 항목은 `L-0001` "검증 계약"(고정 판본의 회귀, 최초 실패 보존, 표본 성공을 전건으로 확대하지 않음, 시험 비용을 줄일 때 단언·시작 상태·실제 경로를 보존)이다. 비합산은 `L-0020` "검증 증거의 범위"의 "이전 런의 검사 수를 합쳐 현행 판본의 … 전건 통과로 쓰지 않는다"와도 같다. `L-0016` "회수 검증"의 "'완료'가 목표 완료 기준을 모두 충족하는가"도 대조했다.
- **새 정보**: 세 가지다. 첫째, 시간 예산을 통과와 별개의 판정 축으로 두고 초과를 보존하며, 큰 초과를 별도 개선 작업의 근거로 삼는 것. 둘째, 부분 실행이 전체 비용 통계를 덮어쓰지 못하게 하는 것. 셋째, 변이 시험에서 실행 오류와 시간 초과를 kill과 구별하는 것.
- **새 발현**: 사례 집계 밖의 준비 오류. `L-0001` "거짓 GREEN을 막는 기준"의 "건너뛴 검사와 실행되지 않은 검사를 성공 건수에서 분리한다"가 나타난 새 형태다.

L-0020의 비합산 문장은 옛 구현의 런 기록 안에 있다. 메인이 L-0020을 새 구조 기준으로 다시 쓰면 이 일반 원리가 그 과정에서 빠질 수 있다. 그래서 7절은 이 원리를 L-0001에 일반형으로 둔다. 이 소절이 파견 질문 2의 답이다.

### 두 구현을 합칠 때 정본 재사용과 새 사본은 원문 동일성과 현행 계약에 대한 강도로 갈랐다

통합자는 후보 쪽 정의를 들일 때마다 main의 기존 정의와 원문을 대조했다. 판정은 세 갈래였다.

- **원문이 같으면 기존 정본을 재사용했다.** 후보 정의가 main의 기존 정의와 AST나 원문으로 같으면 기존 정본을 그대로 두고, 모든 새 소비자가 그 정본을 직접 쓰게 했다. 배정 가족의 관찰·차례 보류 규칙은 기존 정본과 AST가 같아서 다시 정의하지 않았다. [[M-0466]] 교차 가족의 원 LONG 메서드 12개는 AST 본문과 장식자가 현재 세 모듈과 같아서 중복 도입하지 않았다. [[M-0471]]
- **이미 정본이 있는데 후보가 다시 정의했으면 그 사본을 들이지 않았다.** 후보 도우미가 main에 이미 통합된 입력 표를 다시 정의하고 있었다. 이 경우 그 사본을 들이지 않고 새 소비자의 import를 기존 정본으로 옮겼다. 함께 들어온 낡은 설명(이미 해결된 결함을 미해결로 적은 것)은 현재 원문에 맞춰 고쳤다. [[M-0465]]
- **두 정의가 다르면 출처가 아니라 현행 계약을 더 강하게 검사하는 쪽을 택했다.** main의 단언이 더 강하면 후보를 복사하지 않았다. 후보의 외부 종료 시험이 main의 전문 단언 7줄을 빼고 있었으므로 main의 강한 검사를 유지했다. [[M-0476]] 후보의 machine 전체를 복사하면 main에 이미 강화된 oracle과 새 idempotency key 처리가 되돌아가므로 복사하지 않았다. [[M-0471]] 반대로 후보가 main에 없는 경로를 새로 증명하면 이관했다. 후보의 재시작 사례는 미시작 runner와 옛 콜백의 처리를 새로 증명했으므로 옮겼다. [[M-0478]] [[M-0479]] import 위치만 옮긴 diff는 행동 누락으로 세지 않았다. [[M-0479]]

시험의 단위도 같은 기준을 따랐다. 같은 반복 규칙의 시험을 새 수리 회차 이름으로 만들지 않고 원래 성질 모듈로 옮겼다. [[M-0458]] 수리 회차의 원재현 ID는 원장에 역사로 남기고, 시험은 현재 성질 모듈에 두었다. [[M-0455]] [[M-0456]] 반대 방향의 판정도 있다. 겉으로 비슷한 두 동작이 다른 계약이면 하나로 합치지 않았다. 정상 종료와 프로세스 상실의 모의가 그랬고 [[M-0464]], 잘못된 입력의 내구 반려와 같은 request_id에 다른 payload가 온 경우의 거부가 그랬다. [[M-0470]]

D-0010 "하나의 정의로 모으는 일은 같은 지식에만 적용한다"와의 관계는 다음과 같다. 반례는 없다. 원문 동일성을 재사용의 근거로 쓴 것이 D-0010의 "모양이 같다는 사실은 같은 지식이라는 증거가 아니다"와 부딪쳐 보일 수 있다. 그러나 두 판정은 대상이 다르다. 이 범위의 AST 대조는 같은 정의의 두 사본이 같은 구현인지를 판정했다. 따로 작성된 두 코드가 같은 지식을 구현하는지를 판정하지는 않았다. 같은 정의의 사본이 원문까지 같으면 하나를 버려도 잃는 것이 없다. 원문이 다르면 둘 중 어느 쪽이 현행 계약을 더 강하게 검사하는지를 따로 판단해야 했다. 시험을 수리 회차가 아니라 성질 단위로 두고, 비슷해 보이는 두 계약을 갈라 둔 것은 D-0010의 원리가 시험 조직에 나타난 새 발현이다.

판정: 새 정보(적용 경계). 대조한 L 항목은 `L-0020` "하나의 정의로 모으는 경계"이고, 종합의 정본은 [[D-0010]]이다. 새로운 것은 두 구현을 통합할 때의 재사용·사본 판정 기준(원문 동일성, 그다음 현행 계약 대비 강도)과 원문 동일성 판정의 적용 범위다. 이 소절이 파견 질문 1의 답이다.

### 이 종합이 설명하지 않는 것

- **B39·B40의 제품 수리.** 닫힌 초기화의 활성화 차단, 종결 때 요청 전체의 이력 보존, 정확한 scholarly 도구 이름, 봉인 읽기 오류의 변환, `revision_followup` 병합이 여기에 든다. 이것은 옛 구현의 결함과 수리라서 종합하지 않았다(구현소멸). [[M-0455]] [[M-0456]]
- **통합 순서의 효율.** 전체 관문을 26회의 부분 통합 뒤로 미룬 순서가 효율적이었는지는 노드가 비교하지 않는다. 이 범위에 전체 관문의 결과도 없다. 이 종합은 그 순서를 평가하지 않는다.
- **시험 쪽 실패의 구별.** 도우미 배선 실패를 제품 실패와 구별한 사례는 L-0001 "검증 계약"의 "제품 회귀와 시험 전제의 불일치를 구별"의 재실증이라 따로 세우지 않았다. 메서드 이름 차이, 빈 기대값을 truthiness로 판정한 도우미, 재전달 영수증을 새 반려로 오해한 도우미, 없는 도우미 참조가 그 예다. [[M-0455]] [[M-0459]] [[M-0466]]
- **wildcard 선택의 범위 초과.** wildcard가 시험 ID 전체에 적용되어 가족 밖 사례를 고른 일은 L-0016의 시험 선택 규율(선택 기준의 문면과 의미)의 재실증이다. 보고의 실제 모집단을 선택 정본으로 삼고 폴더 한정 모듈 ID를 명시하는 대응으로 끝났다. [[M-0460]] [[M-0461]] [[M-0462]]
- **운영상 사건.** 작업판의 착수 이력 표가 현재 작업처럼 보이거나 렌더가 깨진 일, 생산 함수 개수의 오기와 다음 노드의 정정, EOF 빈 줄의 형식 교정과 AST 동일 확인이 여기에 든다. 이 사건들은 새 원리를 더하지 않는다. [[M-0462]] [[M-0463]] [[M-0470]] [[M-0471]]
- **사용자 조건의 재확인.** M-0459는 옛 조사 보고의 실행 원칙을 원본 Claude JSONL에서 다시 확인했다. 확인한 것은 사용자의 속도 배분 조건(367행), 시험 품질·방어 비용 조건(483행), 동작 보존 리팩터 뒤 수리 선택의 승인(377행)이다. 발화 요약만으로 뜻을 추정하지 않은 사례이며, L-0005의 원문 독해 원리의 재실증이다. [[M-0459]]

## 3. 근거 초안

- [[D-0010]]: 공통화 판정 단위가 지식이라는 종합. 재사용 기준 소절이 그 적용 경계를 잇는다.
- [[M-0455]]: 감시 상한 실행의 미완료 보존, worker 신원 확인 뒤 명시 종료, 선택 수 비합산·속도 배수 미주장, 원재현을 성질 모듈로 옮기고 역사 ID를 원장에 남김.
- [[M-0456]]: 예산 초과를 전체 성공으로 숨기지 않음, 원장 0open을 완료로 대체하지 않음, 실행 중 소스 변경 없음의 기록.
- [[M-0457]]: 시간을 줄이려고 조합·반려·재전달 검사를 빼지 않음, 단위 층 0.2초 상한.
- [[M-0458]]: 같은 규칙의 시험을 수리 회차 이름으로 만들지 않고 성질 모듈로 이관.
- [[M-0459]]: complete와 successful의 차이, 집계 밖 준비 오류, 판본이 다른 두 보고의 비합산.
- [[M-0460]]: 외부 Lean 위치에만 둔 대역, 규모·예제를 줄이지 않음, 속도 향상 미주장, 실행 중 변경 없음.
- [[M-0461]]: 정확한 오류 문언과 이전 head 불변의 음성 시험, 231초 결과를 300초 기준 개선의 근거로 삼음, 층 이름 대신 실측으로 비용 분류.
- [[M-0462]]: 관찰 대기로 진행 중 실행을 종료·재시작하지 않음, wildcard 선택이 가족 밖 사례를 고른 일과 폴더 한정 모듈 ID의 명시.
- [[M-0463]]: 구조상 정상 외곽을 의미상 수락의 증거로 쓰지 않음.
- [[M-0464]]: 실제·대역 공통 계약 시험이 찾은 대역 종료 결함, 시뮬레이터 전용 프로세스 상실 의미의 격리.
- [[M-0465]]: 이미 있는 정본의 재사용과 import 이전, 외부 spawn 대역의 증언 범위.
- [[M-0466]]: AST가 같은 정의의 재사용, 손으로 필드를 덧붙이지 않은 입력 교정, 행 번호를 함수 이름으로 연결.

## 4. 제안 초안

- **기억 내부.** 7절 패킷대로 L-0001에 두 항목을 신설하고 한 항목을 개정한다. 신설은 "대역의 위치와 대역 자체의 검증"과 "부분 결과와 완료·시간 예산의 판정"이고, 개정은 "거짓 GREEN을 막는 기준"이다. L-0020 "하나의 정의로 모으는 경계"에는 새 구조에도 성립하는 재사용·사본 판정 원리를 메인의 재작성 입력으로 넘긴다. 새 L과 세칙 개정은 두지 않는다. 다섯 원리가 모두 기존 L-0001·L-0020의 영역 안에 있기 때문이다.
- **프로젝트 소스.** 없음. 근거 노드의 구현은 2026-10-21에 삭제됐다. 현행 do-math 시험이 이 원리를 따르는지는 이 범위의 노드가 말하지 않는다. 확인하려면 소스 감사가 필요한데, 파견 계약 3.5절은 이를 종합의 범위 밖으로 둔다.
- **사용자 결정.** 없음. 이 범위에 사용자만 정할 사안이 기록되지 않았다.

## 5. 원장 입력

이 주제군을 시작할 때 세운 가정은, 시험 통합 진행 기록이 대부분 `불요: 진행기록`으로 끝나고 L-0001의 기존 원리를 다시 확인하는 데 그친다는 것이었다(파견 계약 6절). 이 가정은 절반만 맞았다. 판본 비합산, 미완료 보존, 예산을 맞추려고 검사를 줄이지 않는 원칙은 재실증이었다. 반면 L-0001에 없는 원리가 둘 나왔다. 하나는 대역의 위치와 대역 자체의 계약 시험이고, 다른 하나는 과거 상태에 묶인 시험 장치의 네 형태다. 이 둘이 나온 노드는 모두 실제 실패를 고친 기록이다. Calls 대역의 종료 결함, Git 행 번호 단언의 실패, 합친 어휘가 놓친 문서 표기 둘, 부분 선택의 비용 덮어쓰기가 그 실패들이다. 그래서 이 원리들은 절차가 설계대로 돌았다는 확인이 아니라, 장치가 구체적 결함을 잡은 증거에 근거한다.

시간 예산은 처음에 진행 보고의 반복 문구로 보았다. 전수로 세어 보니 26개 노드 가운데 24개가 상한 초과를 보존했다. 한 노드(M-0461)는 그 초과를 별도 개선 작업의 근거로 명시했다. 그래서 시간 예산을 통과와 별개의 판정 축으로 세웠다. 다만 이 범위에서 그 개선 작업이 실행된 기록은 없다. 원리의 근거는 초과를 숨기지 않고 보존했다는 운영 사실까지다. 예산 개선의 효과는 근거에 들지 않는다.

질문 1의 D-0010 반례 여부는, 원문 동일성 판정이 D-0010의 "모양은 지식의 증거가 아니다"와 충돌하는지를 따로 검토했다. 판정 대상이 같은 정의의 두 사본과 따로 작성된 두 코드로 서로 다르므로 반례가 아니라고 보았다. 원리의 적용 경계가 넓어진 것으로 기록한다.

파견 질문 5에 대한 답이다. 26개 노드 모두 성격은 시험 통합의 진행 기록이다. L 반영 판정에서 `불요: 진행기록`은 2개(M-0474, M-0475)이고 `불요: 기존지식`은 1개(M-0463)다. 나머지 23개는 진행 기록 안에 섞인 방법 교훈의 근거로 7절 패킷에 인용했다. 추출한 교훈은 2절의 다섯 소절로 모인다. 대역의 위치와 대역 자체의 검증, 한 좌표 음성 시험, 과거 상태에 묶인 시험 장치, 완료와 시간 예산의 판정, 재사용·사본 판정 기준이다. 한 노드가 여러 교훈의 근거가 되기도 하므로 23은 교훈의 수가 아니라 근거로 쓰인 노드의 수다. 반영으로 판정한 노드도 내용 대부분은 통합 진행의 서술이며, 패킷에 들어간 것은 그 안의 한두 문장이다.

D-0010 원장의 세 항목:
- (가) 병렬 구현 교훈의 재발: 읽은 범위에 증거 없음. 이 범위의 노드는 B39~B64를 차례로 기록하며, 병렬 worktree 파견이나 병합 충돌의 기록이 없다.
- (나) 마지막 수리 뒤 전체 시험이나 실제 연구 운전의 결과: 읽은 범위에 증거 없음. M-0480이 전체 일반 시험 1회 실행을 다음 작업으로 정했을 뿐이며, 그 결과는 이 범위 밖이다. 실제 thread·Windows Job·Git 경계를 쓴 시험은 있었지만, 실제 모델 호출과 실제 연구 운전은 없었다. 최소 실호출(T4·T5)은 모든 노드에서 남은 관문으로 적혀 있다.
- (다) 기존 제안에 대한 사용자 결정: 읽은 범위에 증거 없음.

## 7. L 반영 패킷

### L-0001 (검증 설계 원리)

배치 제안: 신설 두 항목은 기존 "검증 계약" 항목 뒤에 둔다. 두 항목은 "검증 계약"의 생산자 추종 문단과 시험 비용 문단을 참조만 하고 그 문장을 옮기지 않는다. 그래서 "검증 계약" 항목은 이 패킷으로 바뀌지 않는다.

#### 개정 항목: `## 거짓 GREEN을 막는 기준`

```markdown
## 거짓 GREEN을 막는 기준

GREEN은 명령의 exit 0만 뜻하지 않는다. 다음 조건을 모두 확인한다.

- 검사 대상이 0건이면 통과가 아니라 판정 불가인지 검토한다.
- 건너뛴 검사와 실행되지 않은 검사를 성공 건수에서 분리한다. 보고의 사례 집계가 실행 단위 전체를 덮는지도 확인한다. 한 시험 보고는 complete=true이면서 successful=false였고, 모듈 준비 단계의 오류 3행은 사례 집계에 들어가지 않은 채 준비 단계의 traceback에만 남았다. [[M-0459]]
- fake의 기본값이 실제 시스템에서 가능한 상태인지 확인한다.
- 실제 운영 환경과 같은 구성과 경로에서 검사한다.
- 수정 담당자가 만든 테스트가 수정 방법 자체만 확인하는지, 필요한 동작까지 확인하는지 살핀다.
- 수정 내용을 무력화했을 때 테스트가 실패하는지 프로브로 확인한다.

음성 시험은 거부된 사실만이 아니라 거부 사유를 고정한다. 공유 스키마 노드를 제자리에서 고쳐 모든 문자열 필드가 한 값으로 제한된 결함은 실제 보충 조사 제출을 전부 거부했다. 그러나 기존 거부 시험은 "이슈가 하나라도 있으면" 통과하는 단언이어서 이 결함을 잡지 못했다. 같은 점검에서 엉뚱한 이유로 통과하던 음성 시험 2건을 사유를 고정해 강화했다. [[M-0350]] 거부 입력은 정상 생산자가 실제 저장소에 만든 유효한 결과에서 한 좌표만 바꾸어 만든다. 그리고 정확한 오류 문언과 함께, 거부 뒤 이전 상태(저장된 이전 head, 원 영수증, 원 바이트)가 그대로인지 단언한다. 이렇게 하면 시험 하나가 규칙 하나만 검사하고, 생산자의 계약이 바뀌면 입력도 따라간다. 단순한 예외 발생이나 필드·이슈 개수로는 통과시키지 않는다. [[M-0461]] [[M-0468]] 기대 상태에 맞추려고 생산자가 만들지 않는 필드를 손으로 덧붙이지 않는다. 필요한 상태는 실제 수신 경로를 거쳐 만든다. [[M-0466]]

시험 실행기는 선택 인자로 받은 시험 ID가 어떤 시험에도 맞지 않으면 거부한다. do-math의 실행기는 없는 ID가 있는 ID와 섞이면 조용히 버려 거짓 통과가 날 수 있었다. [[M-0351]]

검사를 현재의 소유자와 현재 계약이 아니라 과거의 상태에 묶으면, 현재 상태가 바뀌어도 검사는 통과한다. 실제로 나온 형태는 넷이다.

- 알려진 결함을 허용 목록, expectedFailure 포착, 과거 오류를 잡아 통과하는 분기로 받아들인 시험은 결함이 고쳐진 뒤 현재 성공 계약을 무조건 단언하도록 바꾼다. 다른 구현에서 시험을 옮겨 올 때에도 그 허용 분기는 옮기지 않는다. [[M-0471]] [[M-0477]]
- 옛 계약을 기대값으로 가진 시험은 현재 계약과 대조해 시험을 고친다. 제품을 옛 기대값에 맞추지 않는다. 겉으로 비슷한 다른 계약은 별도 시험에 남겨 혼동하지 않는다. 잘못된 입력의 재전달이 예외를 던져야 한다는 옛 기대는, 최초 반려를 내구적으로 유지하는 현재 계약과 달랐다. 같은 요청 ID에 다른 내용이 온 경우의 거부는 별도 계약이었다. [[M-0470]]
- 소스 행 번호에 묶인 단언은 코드가 움직이면 낡는다. 행 번호 대신 현재 소유 함수의 이름이나 inspect·AST로 찾은 코드 개체에 묶고, 그 코드에 도달했는지는 실행 관찰(Python의 `sys.monitoring` 등)로 확인한다. 숫자만 바꾸거나 도달 검사를 지우지 않는다. [[M-0466]] [[M-0478]]
- 여러 소유자의 어휘를 합친 검사는 다른 문맥에서 유효한 낱말로 잘못된 문맥을 통과시킨다. 모든 명령의 flag를 합친 문서 검사는 다른 명령의 옵션으로 잘못된 명령 예제를 통과시킬 수 있었다. 명령별 parser와 필드를 소유한 schema를 기준으로 검사하자 문서의 잘못된 표기 둘이 드러났다. 검사가 다루지 않는 모집단은 완비로 주장하지 않는다. [[M-0473]]

변이 시험(mutation testing)에서 변이체의 결과가 없으면 kill이 아니라 실행 오류다. 변이체의 시간 초과는 변이하지 않은 같은 선택이 같은 상한 안에 성공할 때만 kill로 인정한다. 기준 실행 실패, 변이 오류, 실행 오류, 미실행이 하나라도 있으면 살아남은 변이가 0건이어도 관문을 통과시키지 않는다. [[M-0472]]

빈 출력도 검증 결과가 아니다. 검색이나 회수 명령이 0건을 반환하면, 양성 대조 표본으로 명령이 대상을 찾을 수 있는지 먼저 확인한다.

기준 승계: [[M-0001]]의 일반 작업 템플릿.
```

#### 신설 항목: `## 대역의 위치와 대역 자체의 검증`

```markdown
## 대역의 위치와 대역 자체의 검증

시험 대역(test double)은 제품이 통제하지 못하는 외부 경계에만 두고, 제품의 수신·저장·판정은 실제 코드로 실행한다. 옛 do-math의 시험 통합은 외부 Lean 위치, 외부 HTTP 포트, 공급자 CLI의 spawn에만 대역을 두었다. 제품 함수를 대역으로 바꾸면 시험은 대역의 판정을 증언하게 된다. 수작업 값 대신 실제 생산자를 따르는 원칙은 위 "검증 계약" 항목에 있다. [[M-0460]] [[M-0465]] [[M-0467]]

대역 자체도 실제 구현과 같은 계약 시험으로 검사한다. 그 계약 시험은 정상 경로뿐 아니라 생애의 경계 상태까지 덮는다. 병렬 모델 호출 포트의 대역은 종료 때 아직 시작하지 않은 계산을 건너뛰어 결과나 예외를 만들지 않았다. 이미 응답을 넘긴 turn에 다시 응답을 주는 경로는 기다림에 빠질 수 있었다. 계산을 진행시킨 뒤 닫는 경로만 보던 기존 계약 시험은 이를 놓쳤다. 같은 계약을 실제와 대역 양쪽에서 실행하고, 미시작·대기 중 콜백·반환 뒤 미수집·중복 종료·결과와 예외의 identity·thread 생존을 검사하자 실제는 통과하고 대역은 실패했다. 제품이 아니라 대역을 고쳤다. [[M-0464]]

시험에만 필요한 의미는 제품 포트에 넣지 않는다. 프로세스 상실의 모의는 정상 종료와 의미가 달라 시뮬레이터 전용 동작으로 두었고, 제품 포트의 별칭이나 새 동작으로 넣지 않았다. 포트 문서에는 종료의 실제 의미를 적고, 종료만으로 프로세스 종료나 자원 정산을 인증하지 않는다. [[M-0464]] [[M-0479]]

대역은 자기 출처를 밝히고 그 출처가 입증하는 것만 증언한다. 출처는 실제 생산자의 값, 원 실행의 녹화, 명시적 합성으로 구별한다. 녹화라고 선언한 대역은 원 산출물과 지문으로 대조한다. Lean 출력 녹화는 통합 전에 원 저장 파일을 수정 없이 읽어, 파일 SHA256과 출력의 바이트 길이·SHA256이 녹화 선언과 일치함을 확인했다. 합성 출력은 이름과 문서에 합성임을 밝힌다. 원 녹화의 재생은 새 컴파일러 호출의 증거가 아니다. 기록용 HTTP 증거는 원격 제출이나 청구액의 증거가 아니다. 사용량만 바꾼 spawn 대역은 실제 모델 호출의 증거가 아니다. [[M-0465]] [[M-0467]] [[M-0469]] [[M-0470]] [[M-0471]]

실제 경계의 시험은 제품 함수를 patch하지 않고, 시험이 소유한 실제 자원으로 실제 실패를 만든다. Windows 정션은 시험 Temp 안의 디렉터리를 입력 경로에 연결해 경로 탈출이 실행되지 않음을 확인했다. Git 경계는 특정 읽기 하나에만 잘못된 실행 파일을 요청해 실제 프로세스 생성 오류를 만들었다. 프로세스 종료 증거는 그 시험이 만든 자식 프로세스에서만 취하고, 다른 시스템 프로세스를 종료하거나 관찰 대상으로 늘리지 않는다. [[M-0478]]
```

## 8. 작업 기록

- **독해 절차의 대체.** `write-for-reader`의 독해 절차(합의·독자 파일 작성과 `writing_flow.py` 실행)는 파견 계약 1절의 "자기 산출 파일 하나만 쓴다"와 충돌했다. 계약을 따라 독립 독해는 실행하지 않았다. 대신 `경중_배분.md`가 독해를 실행하지 않는 글에 지정한 대체 점검(가장 긴 대목 셋과 경중 선언의 대조)을 했다. 독립 대조는 2단계 적대 검증이 맡는다. 압축 진술과 경중 선언은 별도 파일 없이 작업 중에 정했다. 무거운 것은 대역의 배치와 계약, 완료·시간 예산, 과거 상태에 묶인 시험 장치였다. 가장 긴 2절 소절 셋은 대역(무거움), 완료·시간 예산(무거움), 재사용·사본 기준(가벼움)이었다. 마지막 소절의 길이는 파견 질문 1이 D-0010 반례 여부를 따로 묻기 때문에 필요한 논증의 분량으로 판단해 유지했다.
- **질문 2의 전제 확인.** 파견 질문 2는 예산 초과 노드로 여섯 개를 지목했다. 전수로 세자 26개 가운데 24개가 초과를 보고했다. 이 결과로 시간 예산을 반복 문구가 아니라 판정 축으로 다루게 되었고, 2절에 실제 분포를 적었다.
- **D-0010 반례 후보의 기각.** AST 동일성으로 재사용을 판정한 것이 D-0010의 "모양은 지식의 증거가 아니다"에 대한 반례인지 검토했다. 판정 대상이 같은 정의의 사본과 따로 작성된 코드로 다르므로 적용 경계의 이동으로 기록했다.
- **L-0001 "검증 계약"의 비개정.** 대역 문단을 신설 항목으로 옮기려면 긴 "검증 계약" 항목 전문을 다시 써야 했다. 옮겨 적는 과정의 훼손 위험을 피하려고, 기존 항목은 두고 신설 항목이 참조하게 했다.
- **사실 재대조의 수정.** 초안을 쓴 뒤 노드 원문과 다시 대조해 여섯 곳을 고쳤다. "매번", "통합자 한 명"처럼 노드가 보증하지 않는 표현, 실제 경계 시험이 있었는데 "모든 시험이 대역 위"라고 쓴 문장, README 하나로 묶은 두 표기의 위치, "fresh T3"에 붙인 해석어, M-0458의 초과 형태다.
