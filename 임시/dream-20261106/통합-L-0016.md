# 위임 파이프라인 운영

메인 에이전트와 서브에이전트가 여러 단계로 작업할 때 쓰는 운영 원리다. 실제 파견은 사용자 지시와 현재 런타임 권한이 허용할 때만 한다.

## 상태의 정본

에이전트 컨텍스트는 휘발성 캐시다. 장기 작업의 판정, 진행 상태, 재개 좌표는 파일에 기록한다. 파일에 기록한 요약은 원문을 대체하지 않는다. 원문 문언이 필요한 단계는 원본을 다시 읽는다.

서브에이전트는 큰 산출물을 파일에 직접 쓰고 반환에는 처분, 요약, 경로, 검증 상태를 적는다. 전문을 반환하고 다음 단계가 다시 읽으면 같은 텍스트가 여러 컨텍스트에 반복 적재된다.

기준 승계: [[M-0001]]의 일반 작업 템플릿.

## 분해와 병렬화

먼저 전체 산출물과 선행 관계를 파악하고, 서로 다른 형식의 입력에 반복 적용할 공통 처리가 있는지 확인한다. 실제 표본으로 의미·식별자·오류·비용을 확인한 뒤, 필요한 차이와 출처를 보존하면서 전체 비용을 줄일 수 있을 때 공통 표현으로 변환한다. 변환 자체가 새 부담이면 직접 처리한다. [[M-0002]] [[M-0137]] [[D-0002]]

선행 관계와 순서는 실제 의존으로 정한다. 직전에 다루던 작업이라는 사실은 우선 사유가 아니다. 사용자가 직전 작업을 관성으로 이어 가는 진행을 지적한 뒤, 직전 작업이었다는 이유의 우선순위와 실제 의존이 없는 종속(읽기 한도 확인을 단독 이름 작업에 묶은 것)을 지웠다. 모든 재검토를 구현 전체의 일괄 선행 관문으로 만들지도 않았다. [[M-0532]]

병렬 작업은 수정할 파일과 작업 사이의 연결 지점을 기준으로 나눈다. 두 작업이 같은 파일이나 같은 상태를 동시에 고치면 병렬화하지 않거나 소유권을 분리한다. 같은 트리를 고치는 두 작업에서 읽기 전용 검토만 병행하고 편집은 차례로 한 뒤, 두 편집이 끝난 트리를 고정해 통합자가 한 번에 검증한 사례가 있다. [[M-0534]]

분해 조건은 다음과 같다.

- 각 작업의 입력과 산출 경로를 명확히 정할 수 있다.
- 작업 사이의 선행 관계를 명시할 수 있다.
- 병합 후 확인할 연결 지점을 식별할 수 있다.
- 한 작업의 실패가 다른 작업의 정본을 오염시키지 않는다.

병렬화는 처리량을 늘리지만 공유 토큰 한도와 회수 비용도 늘린다. 각 단계가 끝날 때 상태를 파일에 기록해 한도 도달과 세션 교대에 대비한다.

독립 과제는 위임할 수 있지만 전체 목표의 해석, 공통 계약, 과제 간 충돌, 원본 통합과 종료 판단은 전체 맥락을 가진 담당자가 유지한다. 조사만 맡긴 작업자가 실행·승인 권한까지 가진 것으로 읽지 않도록 권한을 구별한다. 작은 자료의 교차 관계를 검증할 때는 영역을 나누는 것보다 서로 다른 관점이 전건을 보는 편이 나을 수 있다. [[M-0018]] [[M-0035]] [[D-0001]]

새 실행 환경을 대량 파견에 사용할 때에는 실행 조건의 중요한 차이를 포함하는 최소한의 대표 경로에서 실제 시작·반환·필요한 재개와 의존성 접근을 먼저 확인한다. 기존에 검증한 같은 경로를 매 파견마다 다시 시험하는 의무는 아니다. 사본에서만 생긴 실패는 원본의 기능 결함과 구별한다. [[M-0238]] [[M-0239]] [[M-0245]]

DAG로 분해해 다층 파견으로 실행하던 do-dag 체제는 2026-10-30 이 저장소에서 삭제됐고 공개 저장소 `MegasKomnenos/do-dag`에 남아 있다. 이 저장소에서의 운전 기록은 layer-1(M-0006~M-0037 범위)에, 스킬 원문은 `git show 90478bc0^:.claude/skills/do-dag/SKILL.md`에 있다. [[M-0623]]

## 파견 계약

파견문에는 다음 항목을 둔다.

- 임무와 완료 기준
- 읽을 원본과 시작 좌표
- 수정할 수 있는 파일
- 수정하지 않을 파일
- 실행할 검증과 실패 조건
- 상신 조건
- 반환 서식
- 검사 결과가 없을 때 `없음`이라고 적는 규칙.

범위는 닫되 읽기 범위를 고정 파일 목록으로만 제한하지 않는다. 개체를 따라 정의 파일, 정본 문서, 결정 기록을 찾는 절차를 제공할 수 있다. 읽기는 발견 절차로 열고, 쓰기 범위와 임무는 닫는다.

파견문 안의 단계·계획 이름은 상위 설계 문서의 번호 체계와 겹치지 않게 준다. 옛 do-math 시험 재편에서 하위 계획을 "1·2·3단계"로 부르자 상위 설계의 "2단계(수리)"와 겹쳤다. 그래서 작업자가 결함 교정을 자기 일로 읽을 수 있는 파견문이 됐고, 독해자가 이를 찾았다. 작업자의 판단을 허용하는 예외는 닫힌 목록으로 적고, 나머지는 막힘으로 보낸다. "옮기지 않은 것은 note에 적는다" 같은 열린 예외는 약한 수행의 허가로 읽힐 수 있었다. [[M-0384]] [[M-0385]]

사용자 대화에서 나온 설계 과제를 작업자에게 넘길 때는 짧은 작업 지시 대신 인계 문서 하나에 사용자 원문, 확정된 방향, 통합자의 권고, 결정 권한을 구분해 담는다. 사용자가 맥락 손실 없는 전달을 요구해 사용자 발언 둘을 원문 그대로 실은 인계 문서를 만든 사례에서, 작업자는 통합자의 권고 셋을 원문의 의도를 근거로 고쳐 결정했다. 권고와 확정을 섞어 적었다면 작업자가 권고를 확정으로 읽었을 수 있다. 사용자 결정을 계약 문장으로 다시 쓸 때 범위가 바뀌는 위험은 [[L-0012]]의 지시 분해 항목에 있다. [[M-0355]]

## 병렬 구현 파견

큰 코드 변경을 여러 git worktree의 작업자에게 나누어 구현하고, 통합 브랜치에서 병합하거나 패치로 main에 반영한 작업이 여러 번 있었다. 옛 do-math의 세 경량화와 전면 정리, 시험 인스턴스 해석에 따른 개선 묶음 1~5, 시험 재편 1e·1f(옮기기 묶음 24개와 마지막 통합)다. 파일 소유 경계는 텍스트 충돌을 줄일 뿐, 같은 지식을 두 곳에서 따로 구현하는 의미 중복과 병합 뒤의 의미 충돌은 막지 못했다. 대상 코드는 2026-10-21에 삭제됐고, 아래 원리는 구현과 무관하게 성립한다. 종합의 정본은 [[D-0010]]과 [[D-0011]]이다. [[M-0348]] [[M-0349]] [[M-0350]] [[M-0351]] [[M-0355]] [[M-0378]] [[M-0422]] [[M-0593]]

- **병행 여부와 격리 선택지를 첫 계획에 적는다.** 저장소 규범(worktree를 만들지 않음)과 당시 시험 지침(실행 중 트리 편집 금지)을 근거로 구현 다섯 묶음을 순차로 계획했다가, 사용자가 병행이 어려운지 묻고 worktree 격리를 명시로 요청한 사례가 있다. 규범 때문에 소요가 크게 늘면, 격리를 요청하면 병행할 수 있다는 선택지와 그 비용을 첫 계획에 함께 적는다. [[M-0355]]
- **이음새와 공통 틀을 파견 전에 확정한다.** 통합자가 코드에서 실제 이음새를 찾아 공유 커널과 이음새 계약을 먼저 만든다. 작업자가 자기 영역에서 완결적으로 일하면 인터페이스·스키마·이름을 양쪽에서 따로 발명한다는 사용자 지적으로 도입했다. 시험 재편은 이 원리에 따라 승인된 영역 병렬 대신 커널 선행을 택했다. 19개 의무 가운데 절반 가까이가 부류 전체의 일반 시험이나 구조 검사였기 때문이다. 파견문을 쓰기 전에 작업자가 쓸 파일을 하나씩 짚으면 병합 충돌이 설계 단계에서 보인다. 실제로 한 사람이 채운다는 전제의 공유 배열을 영역별 파일로 나눴다. 작업자가 돌려준 이음새 요청은 커널에 반영한다. 병합 뒤에는 커널 밖의 새 도우미와 중복 정의를 grep으로 전수 감사한다. 그래도 두 작업자가 같은 시험 도우미를 따로 만든 일이 있었다. 그래서 여러 묶음을 합친 뒤 공유 도우미로 모은다. [[M-0348]] [[M-0378]] [[M-0382]] [[M-0389]]
- **커널은 병렬 단계 도중에도 자란다.** 작업자가 돌려준 이음새 요청을 커널에 반영하는 일은 단계 도중에도 이어진다. 여러 작업자가 같은 벽에 부딪쳐 각자 우회를 만들기 시작하면, 그 이음매를 "나중에 한꺼번에"로 미루지 않는다. 우회가 설계가 버린 모양을 새 체계에 들이는 통로가 되기 때문이다. 같은 지적이 여러 묶음에서 되풀이되면 커널의 기계 검사로 옮긴다. 묶음 도중에 넣은 커널 규칙은 그 전에 갈라진 가지에 없다. 그래서 수정을 재개할 때마다 통합 브랜치의 현재 끝을 먼저 가지에 합친다. 합친 직후의 검사가 규칙 이전에 쓴 위반을 드러낸 사례가 있다. [[M-0400]] [[M-0403]] [[M-0405]] [[M-0406]]
- **분할 범위는 완비를 검사하고, 단위는 작업자 하나의 맥락이 정한다.** 손으로 고른 모듈 목록으로 영역을 나누면 빠지거나 겹쳐도 알 길이 없다. 그래서 모든 대상 모듈을 영역에 정확히 하나씩 배정한 표를 저장소에 두고 구조 검사로 강제했다. 시범 규모(옛 시험 77개)에서 작업자 하나가 약 55만 토큰을 썼다. 그래서 영역을 90개 이하의 묶음과 마감으로 나누고, 마감은 그 영역의 묶음이 모두 합쳐진 뒤로 정했다. 같은 영역의 병렬 묶음은 처분 파일을 나눠 쓴다. 분할 기준이 제품 모듈과 다르면 같은 제품 함수를 두 영역이 다룬다. 시험 재편은 옛 시험 모듈로 나눴고, 두 영역이 같은 새 파일 이름을 골랐다. 새 파일 이름에 영역을 넣어 이 충돌을 막는다. [[M-0388]] [[M-0393]]
- **파견문은 틀과 생성기 하나에서 만든다. 단일 정본은 교정과 누락을 함께 퍼뜨린다.** 배운 규칙이 한 곳에서 모든 파견문에 닿게 했다. 그러나 계획 표의 영역 의무는 틀에도 마감 생성기에도 한 줄도 없어, 모든 영역을 마감해도 완료 조건을 채우지 못할 상태였다. 생성기에 새 문장을 넣으면, 번호가 밀리는 변형에서도 렌더링해 확인한다. 새 베이스에서 다시 생성하고, 오래된 파견문을 최신으로 쓰지 않는다. 계획 행과 실행 수단의 대응 점검은 아래 「긴 다단계 작업의 완료 경로」 항목에 있다. [[M-0388]] [[M-0403]] [[M-0416]] [[M-0422]]
- **반환은 작업자와 다른 에이전트가 전수 검토한다.** 작업자의 "모두 통과"는 산출의 성질을 말해 주지 않았다. 이 검토는 아래 「회수 검증」의 원리(반환문보다 실물을 보고, 판정과 수치는 따로 검증한다)를 산출의 성질에 적용한 것이다. 시험 재편에서 그 성질은 옮긴 시험의 강도였다. 규칙을 알고 변이까지 돌린 시범 작업자의 57개 가운데 6개가 옛 시험보다 약했다. 금지 목록을 파견문에 넣은 뒤에도 목록에 있던 모양이 다시 나왔다. 판정 기준은 [[L-0001]] 「옮기거나 다시 쓴 시험의 강도 보존」에 있다. 작업자가 "만들 수 없다", "공개 경로로는 안 된다"를 근거로 들면, 검토자가 그 이유가 코드상 사실인지 확인하게 한다. [[M-0386]] [[M-0390]] [[M-0401]] [[M-0413]]
- **구조를 옮기는 항목은 선두나 단독으로 둔다.** 여러 그룹이 공유하는 파일의 구조 변경(스키마 파일 합치기, 메서드를 새 모듈로 옮기기)을 다른 그룹과 동시에 돌린 적이 있다. 그러자 병합 때마다 변경을 새 위치로 옮겨야 했고, 전담 병합 작업자가 필요했다. 구조 변경을 먼저 끝내면 어려운 재구성은 검증된 좌표 위에서 일하고, 작은 수정은 최종 구조에 한 번만 들어간다. 충돌을 줄이는 것은 작은 것을 먼저 병합하는 순서가 아니라, 병합된 상태 위에서 이어서 시작하는 것이다. 이 교훈은 2라운드에 기록된 뒤에도 전면 정리에서 되풀이됐다. [[M-0349]] [[M-0351]]
- **병합 뒤 표지 밖의 의미 충돌을 따로 찾는다.** 텍스트 충돌 없이도 의미 충돌이 여러 번 나왔다. 옮겨진 코드가 지운 이름을 import하거나, 새 시험이 옮겨진 패치 대상을 가리키거나, 다른 그룹이 지운 인자를 넘긴 경우다. 두 쪽이 모두 바꾼 파일의 hunk를 대조하고, 지운 이름을 grep하고, 중복 정의를 찾는다. 이 항목이 현행층에 들어간 뒤의 첫 병렬 구현(개선 묶음 1~5)에서도 병렬 묶음 사이의 의미 충돌이 병합 뒤 남았고, 다음 검증 라운드의 관점 수리자가 찾았다. 그 구현의 기록에는 정리 전 diff 해시 대조는 있지만 의미 충돌 탐지는 없다. 이름 수준의 정적 확인만으로는 부족하다. 의존 호출 2,037곳에서 필수 인자의 정적 누락이 0건이었는데도 전체 시험은 37건 실패했다. 인자는 있으나 값이 `None`인 경로, 동적 호출, 옛 모듈명으로 관찰하는 검사가 원인이었다. 합칠 때 도는 시험의 범위도 사각이 된다. 합칠 때마다 일상 층과 그 묶음의 모듈만 돌렸더니, 지워진 옛 모듈을 고르는 옛 시험의 실패를 다른 작업자가 범위 밖 실패로 보고할 때까지 보지 못했다. 그래서 범위 밖 시험을 주기적으로 전체 실행한다. 되풀이되는 공유 목록 충돌은 규칙이 분명하면 도구로 풀고, 3방향 적용 결과를 확인한 뒤에 확인 실행을 띄운다. 병합이 실행 시점을 옮겨, 시험이 품고 있던 스레드 경합이 드러난 사례도 있다. 그러므로 병합 뒤 실패의 원인을 병합된 변경으로 단정하지 않는다. [[M-0350]] [[M-0351]] [[M-0355]] [[M-0356]] [[M-0399]] [[M-0410]] [[M-0419]] [[M-0422]]
- **사용자 결정을 파견 계약으로 옮길 때 조항마다 원문과 맞댄다.** 번역이 범위를 좁히거나 넓힌 사례와 교정은 [[L-0012]]의 지시 분해 항목에 있다. 결정 항목은 결과를 반드시 구현하게 한다. "구현하지 않음"은 이미 고쳐져 할 일이 없음을 입증한 경우로 한정한다. 공유 정의가 없으면 소유 모듈에 하나만 만들고 계속한다. 작업량·난도·시간·작아 보이는 실익은 범위 축소의 사유가 아니다. [[M-0349]]
- **작업자의 병합 권한이 막힐 수 있다.** 작업자가 커널 브랜치를 자기 브랜치에 병합하는 것을 권한 분류기가 거부했다. 거부된 행동을 메인이 대신하지 않았다. 대신 커널 병합을 통합 단계로 옮기고, 커널에 기대는 항목을 `미완료(커널)`로 남기게 했다. [[M-0348]]
- **통합자의 작은 수정도 대역을 전수 확인한다.** 제품의 속성 접근을 바꿀 때에는 그 속성을 흉내 내는 시험 대역을 먼저 grep한다. 대역을 새로 설계할 때 제품 호출자 전체를 찾는 일은 [[L-0001]]의 강도 보존 항목에 있다. 같은 목록을 여러 곳에 두지 않는 일은 [[L-0001]]의 모집단 항목에 있다. [[M-0351]] [[M-0394]] [[M-0409]]
- **병합과 패치 적용의 운영 실수.** 충돌 해소 스크립트가 실패했는데 줄바꿈으로 이어 둔 커밋이 실행되어, 표지가 남은 병합 커밋이 생겼다. 작업자 diff를 `git apply`로 옮길 때 `--check` 출력을 `tail`로 끝부분만 보다 거부 hunk 하나를 놓쳤고, `--reject`로 드러나 수작업으로 합쳤다. 정리 전에는 각 worktree의 diff 해시가 반영한 패치와 같은지 확인한다. 한 작업 트리에 차례로 쌓은 두 묶음은 한 커밋으로 합친다. 따로 커밋하려면 한쪽을 걷어 내고 다시 확인해야 하기 때문이다. `py_compile`은 스킬 폴더에 `.pyc`를 남기므로 문법 확인은 `compile()`이나 `python -B`로 한다. 병합 작업자가 시스템 지시를 근거로 커밋 트레일러를 붙인 일도 있었다. commit-harness가 트레일러를 금하며 그 규칙이 우선한다는 근거를 주자 작업자는 멈췄다. 줄 끝·이스케이프 실수의 되풀이는 [[L-0012]]의 적용 점검 항목에 있다. [[M-0348]] [[M-0351]] [[M-0355]] [[M-0402]]
- **worktree를 지우기 전에 바깥을 가리키는 연결을 확인한다.** 실제 툴체인을 worktree에 정션으로 연결하면, worktree 제거가 정션을 따라가 원본을 지울 위험이 있다. 그래서 제거 전에 재분석 지점을 검색하고 링크만 먼저 지웠다. 이 기록 뒤에도 검증용 스냅숏 worktree에 같은 연결을 만든 세션이 `git worktree remove --force`로 Lean 도구 사슬 전체를 지웠다. 사용자 승인으로 다시 설치한 뒤, 실행 파일 해시·판본·원천 정체를 등록값과 대조했다. 그 뒤로는 연결을 `rmdir`로 먼저 지우는 동작과 worktree 제거를 한 명령에 묶었고, 이 규칙은 다음 단위에서 지켜졌다. 정리 명령(`rm -rf`, `git worktree remove --force`, `shutil.rmtree`)을 쓰기 전에는 대상 안에 바깥을 가리키는 연결이 있는지 확인한다. Agent 도구의 격리 worktree는 저장소 안 `.claude/worktrees/`에 생기며, 이 경로는 추적되는 `.gitignore`에 없고 로컬 `.git/info/exclude`에만 있다(2026-11-06 확인). [[M-0348]] [[M-0351]] [[M-0355]] [[M-0366]] [[M-0367]]

### 시험 선택과 실행 규율

이 소절의 교훈은 옛 do-math의 시험 스위트를 병렬로 고치며 얻었다. 그 실행 방식의 정본이던 `.claude/skills/do-math/scripts/tests/시험-지침.md`는 2026-10-21 옛 구현 삭제로 현행 트리에 없다. 이 소절이 가리키던 판본은 `git -c core.quotepath=off show 0e1869dd:.claude/skills/do-math/scripts/tests/시험-지침.md`(2절 「세 층의 실행」, 3절 「시험을 돌리는 동안의 규칙」)로 회수하고, 내용이 늘어난 삭제 직전 판본은 `git -c core.quotepath=off show 4e793d17:<같은 경로>`(2절 「실행 층과 인계」, 3절)로 회수한다. 현행 do-math에는 `runtime/tests/`의 시험 모듈이 있지만 시험의 실행·대기·인계 방식을 정한 문서는 없다(2026-11-06 확인). 그래서 아래의 일반 원리는 이 소절이 현행 판단 근거다. 옛 지침의 명령과 수치는 옛 구현의 기록이며 현행 판단에 쓰지 않는다. 조각(shard)별 120초·전체 300초 판정, `run_tests.py`의 조각 지정, 실제 Lean을 worktree에 보이는 환경변수, 옛 시험 층 이름이 그 예다. [[M-0350]] [[M-0593]]

병렬 작업의 시험 대기가 전체 소요의 대부분을 차지했다. 검사 경량화의 7시간 넘는 작업에서 원인은 넷이었다. 4코어 머신에서 에이전트 넷이 동시에 시험을 돌린 과구독이 첫째다. 중심 모듈 때문에 사실상 전체 스위트를 가리킨 파견문의 시험 기준("고친 모듈을 가져오는 integration 시험")이 둘째다. 같은 기존 실패를 세 에이전트가 각자 다시 계산한 것이 셋째다. 반환을 마친 에이전트의 백그라운드 시험이 넷째다. 머신 전역 잠금은 경쟁만 줄이고 총작업량은 그대로여서 버렸다. 기준선은 한 번만 계산해 공유하고, 작업자는 반환 전에 자기 백그라운드 실행을 종료한다. 기준선이 필요하면 먼저 같은 판본의 최근 검증 런 장부와 종료 보고에서 전체 결과를 찾는다. 다른 세션이 같은 판본으로 이미 돌린 결과가 있는데 편집 전 전체 시험 세 묶음을 다시 띄웠다가, 사용자 교정으로 멈추고 그 장부의 결과를 쓴 사례가 있다. [[M-0348]] [[M-0355]]

파견 계약은 무엇을 돌릴지와 함께 어떻게 돌리고 기다릴지를 정한다. 시험 경량화에서는 사용자 지시로 작업자 로그를 직접 보았다. 한 작업자는 147분 중 114분을 결과 대기로 보냈고, 10분 시한의 전경 대기를 반복해 중복 대기 셸 7개가 쌓였다. 무거운 모듈 전체의 반복 실행, 측정 도중의 같은 트리 편집, 공유 고정 로그 경로, 작업자마다의 기준 판본 재실행도 있었다. 파견 계약이 "무엇을 돌릴지"만 정하고 "어떻게 돌리고 기다릴지"를 정하지 않은 공백이었다. 이 공백을 메운 옛 지침 3절의 규칙 가운데 구현과 무관한 것은 다음과 같다. 긴 실행은 백그라운드로 돌리고 완료 알림을 기다리며, 전경 대기 반복문으로 기다리지 않는다. 긴 실행을 명령 도구의 제한 시간에 걸어 중단된 사례도 있었다. 실행 중인 작업 트리는 편집하지 않는다. 로그와 임시 파일은 실행마다 새 경로에 둔다. 실패하면 같은 시험을 되풀이하기 전에 메시지와 코드를 읽고, 가설을 가를 가장 작은 시험만 돌린다. 시간 측정과 통과 확인을 같은 실행으로 겸하지 않는다. [[M-0348]] [[M-0350]] [[M-0351]]

인계 확인의 범위는 숫자 문턱이 아니라 책임으로 나눈다. "고친 이름을 grep해 나온 모듈"을 돌리게 하자, 공유 정의를 고친 작업자의 실행이 전체에 가까워졌다. 통합자가 제안한 "grep 결과 20개 초과면 생략"은 숫자를 먼저 정하고 근거를 끼워 맞춘 것이어서 사용자가 기각했다. 인계 확인은 고친 모듈의 시험과 새로 쓰거나 고친 시험만 돌린다. 소비자 쪽은 컴파일·전체 import·옛 이름 grep으로 확인하고, 소비자의 동작은 통합 확인이 맡는다. 옛 지침 2절은 이 구분을 편집 확인·인계 확인·통합 확인의 세 층으로 적었다. [[M-0348]] [[M-0351]]

기계 전체의 동시 시험 실행 수는 에이전트 수와 별개의 자원이다. 시험 재편은 기계 전체 상한 3을 두었고, 에이전트 수에 제한이 없다는 지시를 받아서도 이 상한과 구분했다. 3은 4코어 머신에서 코어 수보다 하나 적게 정한 그 작업의 값이다. 상한이 찬 동안 경미한 수정은 통합자가 직접 고친다. 자리가 나면 새 묶음보다 수정 작업자를 먼저 재개한다. 합치기 전의 수정이 쌓이면 통합 브랜치와의 차이가 커져 충돌이 늘기 때문이다. [[M-0390]] [[M-0397]] [[M-0421]]

동시 작업자를 늘 채우는 운영은 예산이 정의된 조건(부하 없는 실행)의 측정 기회를 없앤다. 부하 아래 순차로 잰 시간은 예산을 크게 넘는 것처럼 보였다(479·587초). 파견을 의도적으로 멈춰 만든 틈에서 부하 없는 병렬로 재자 227초였다. 메모리를 크게 쓰는 전체 측정은 작업자 부하 아래에서 메모리 부족으로 멈췄다. 그래서 통합자가 작업자를 비운 뒤 메모리 감시 아래 돌린다. 측정 판단의 일반 원리는 [[L-0005]] 「성능 측정과 실행 예산」에 있다. ## 통신과 재개

완료 통지의 수신자가 누구인지 런타임마다 확인한다. 재개한 에이전트의 완료 통지가 중간 오케스트레이터가 아니라 메인에 도착할 수 있다. 이 경우 완료 신호 파일을 상태 정본으로 삼는다. 승격 정본: `.claude/CLAUDE.md` 「서브에이전트 재개 회수」(재개한 에이전트의 완료는 통지를 기다리지 않고 산출 파일의 실재와 판독으로 판정하며, 회신 수신처는 agentId로 내려 준다).

백그라운드 작업의 완료는 특정 대기 도구의 호출이 아니라 완료 사건이나 생산자가 남긴 내구 기록으로 판정한다. [[M-0504]] Claude Code 2.1.289의 실제 스트림에서 백그라운드 작업은 시작 사건과 완료 알림을 남겼다. 그러나 TaskOutput 도구는 초기 도구 목록에 없었고, ToolSearch로도 찾을 수 없었다. [[M-0503]] 2026-10-04 옛 do-math의 제품 탐침은 이 도구의 호출을 요구해 정상 완료를 실패로 판정했다. 그 뒤 같은 작업 ID의 시작·완료 알림이 하나씩 있고 시작, 완료, 최종 응답의 순서인지로 판정하도록 고쳐졌다. 그 탐침은 2026-10-21에 구현과 함께 삭제됐다. [[M-0503]] [[M-0504]] [[M-0593]] 2026-11-06 dream 파견 세션(Claude Code 2.1.319, 서브에이전트)에서도 같은 질의가 도구를 찾지 못했다. [[D-0011]] 도구 표면은 CLI 판본과 설정에 따라 다르므로, 판본이 바뀌면 다시 확인한다. [[D-0011]] 시간 초과를 관찰로 읽는 일반 판단은 [[L-0005]]의 「다음 행동과 실패 진단」을 따른다.

중단된 작업을 재개할 때 이미 완료한 비가역 행위를 반복하지 않는다. 산출 파일, 마지막 판정, 남은 완료 기준을 먼저 읽고 다음 행위부터 잇는다.

다른 세션이나 다른 런타임의 작업을 이어받을 때는 그 세션의 원본 기록을 읽는다. 다만 기록 안의 역할 표지를 사람의 결정으로 읽지 않는다. Claude 세션 JSONL에서 user 역할에 실린 에이전트 반환과 압축 요약은 인간 승인이 아니었다. 일반 텍스트 추출에는 queued_command로 들어온 사용자 발화 둘이 빠져 있어, 원본 attachment에서 확인했다. 로그의 물리 행 번호(1부터)와 추출본 번호(0부터)처럼 좌표 원점이 다른 자료는 인용에서 섞지 않는다. [[M-0421]]

이어받은 보고와 진행 원장이 가리키는 산출물은 실물과 대조한다. 진행 원장과 이전 세션의 보고가 장부 항목 27~29를 참조했지만, 실물 장부는 26에서 끝났다. 원본 로그의 도구 입력과 현재 코드로 세 항목을 복구했다. 누적 수치는 압축 요약이 아니라 원천 장부에서 센다. 요약의 누계에 새 묶음을 더해 1,229로 보고했는데, 장부로 세면 1,194였다. 이전 세션이 남긴 산출물의 전제가 그 뒤의 변경으로 깨졌는지도 본다. 성공한 전체 측정 직후 실행기가 바뀌어, 그 측정을 증분 기준으로 쓸 수 있다는 안내가 성립하지 않았다. [[M-0403]] [[M-0421]]

파견한 에이전트가 내용과 무관한 공급자 필터로 산출 없이 멈추면, 산출 파일이 없음을 확인한 뒤 같은 지시로 새 에이전트를 보낸다. 되풀이되면 모델을 바꾼다. 상시 지침의 복창을 마친 직후 요청이 거부된 사례가 있다. 항상 적재 규범과 분류기 반응의 관계는 [[L-0012]]에 있다. [[M-0412]]

## 긴 다단계 작업의 완료 경로

여러 단위가 이어지는 긴 구현에서는 국소 실패가 다음 작업을 정하게 두지 않고, 검증된 작은 변경을 단위마다 확정한다. 옛 do-math 시험 재편의 마지막 통합 단위는 실패 하나를 고치면 다음 실패가 드러나는 연쇄를 거쳤지만, 최종 통합 시험의 실패 0으로 확정·통합됐다. [[M-0422]] 그 뒤 이틀의 작업에서는 실제로 실행한 수리가 미커밋으로 남아 통합되지 않았고, 보존 트리 대비 136파일이 바뀌어 있었다. 영향 검사 초안은 정상 생산 경로를 확인하지 않은 채 입력을 다시 만들어 네 번 실패했다. 노드는 이 상태를 "국소 실패가 다음 작업을 결정하고 검증된 작은 변경을 확정하지 않은 채 누적했다"고 진단한다. 사용자는 부분 수리와 시험이 완료되지 않고 흩어진다고 지적하며, 기존 목표를 지우고 새 목표를 세우게 했다. 부분 통과를 전체 성공으로 표시하지 않는 원칙은 지켜졌다. 그러나 그것만으로는 완료 경로가 통제되지 않았다. [[M-0423]]

교정 뒤의 운영은 다음과 같다. 목표와 남은 의무를 원문 행과 연결한 작업판을 두고, 현재 판본과 미검증 초안과 판본 차이를 그 판에 적는다. 독립 변경마다 입력·동작·결과를 검수하고, 관련 검증을 거쳐 확정한다. 그 뒤 통합 후보에서 회귀를 되풀이한다. 기능 묶음은 추적 분류로 쓰고 큰 구현 단위로 쓰지 않는다. 모든 구현 뒤 마지막에만 통합하는 계획은 세우지 않는다. 같은 산출이 거듭 반려되면, 입력을 다시 만들어 재실행하기 전에 정상 생산자와 수신 계약을 직접 검수한다. 그 작업은 이 중단 조건을 "실패 2회 뒤"로 정했다. 이 횟수는 그 작업의 조정값이며, 실패 진단의 일반 원리는 [[L-0005]] 「다음 행동과 실패 진단」에 있다. 당시 작업판은 공개 준비 삭제로 현행 트리에 없으며, `git show dbde17f4:docs/do-math/시험-재편-2026-09-29/단계-전환표-2026-10-03.md`로 회수한다. [[M-0423]]

계획을 다시 읽을 때는 계획 표의 행마다 어느 파견문이나 누구의 몫이 그것을 실행하는지 대조한다. 위 「병렬 구현 파견」의 파견문 틀 항목에 적은 영역 의무의 누락은 사용자 지시에 따른 원문 재독이 찾았다. [[M-0403]]

## 회수 검증

메인은 반환문보다 실제 파일을 우선한다. 다음 항목을 확인한다.

- 산출 파일이 실재하고 비어 있지 않은가
- 변경 범위가 파견 계약과 일치하는가
- 검증 명령이 실제 대상을 검사했는가
- 0건 출력이 검색 실패나 스키마 오독이 아닌가
- “완료”가 목표 완료 기준을 모두 충족하는가.

반환 없이 끝난 작업자에게도 같은 기준을 적용한다. 작업자가 모델 지원 오류로 시작 전에 종료한 사례에서 그 의도를 구현 완료로 취급하지 않았고, 실제 HEAD·diff·실행 프로세스를 확인한 뒤 새 작업자를 배정했다. [[M-0535]]

서브에이전트의 판정과 수치는 따로 검증한다. 필드의 사용 여부를 판정한 에이전트가 함께 보고한 평균 크기 23.6KB는 표본 6개의 편향이었고, 111실행 전수의 중앙값은 192바이트였다. 판정은 유지하고 크기는 전수 재계산 값을 썼다. [[M-0323]]

항상 적재되는 프로젝트 지침은 파견된 에이전트에도 도달한다. 독해 에이전트 여덟(눈가림 독해 여섯, 대체 독해 둘) 가운데 눈가림 독해 하나가 학술 지식 복창을 반환 앞에 붙여 반환의 첫 낱말 계약을 어겼고, 나머지 일곱은 첫 낱말 계약을 지켰다. 파견문에 상시 지침이 요구하는 글은 앞선 응답에 쓰고 마지막 메시지는 반환 계약을 지키라고 적을 수 있다. 사용자는 규칙 추가 없이 관찰을 유지하고 재발하면 다시 보기로 했다. 규범 쪽의 정리는 [[L-0012]]에 있다. [[M-0322]] [[M-0326]]

문제점을 서술한 부정문을 긍정문으로 바꾸는 것만으로 완료 기준을 정하지 않는다. “X가 없다”를 “X를 만든다”로만 바꾸면 X를 읽고 쓰는 연결 지점이 빠질 수 있다. 수정으로 바뀌는 구조의 정의와 읽기·쓰기·검증 위치를 함께 정한다.

## verify-rounds

여러 절에 걸친 확정 사항의 적용은 통상 편집으로 한 번에 반영한 뒤 검증하는 편이 단순할 수 있다. 같은 변경을 라운드마다 재발견·재작성하는 비용이 반복되면 적용 경로를 재검토한다. 절 수나 조각 수의 고정 문턱으로 경로를 결정하지 않는다. [[M-0113]] [[M-0114]] [[M-0115]]

완성된 산출물의 다중 검토는 `.claude/skills/verify-rounds/SKILL.md`를 따른다. Codex는 생성 사본인 `.agents/skills/verify-rounds/SKILL.md`를 읽는다. 검증자는 근거 없는 지적을 내지 않는다. 수리자는 산출물 밖의 정책을 임의로 바꾸지 않는다. 상신 항목은 읽은 범위, 실제 대상에 관한 질문, 선택지, 변형 가능성, 추천 하나를 갖춘다.

검증을 마칠 때는 지적 수만 세지 않고 각 지적을 어떻게 처리할지 확정한다. 재현된 결함은 고친다. 틀린 지적은 기각한다. 관할 밖 결정은 상신한다. 지적이 없으면 검사 범위와 통과를 명시한다.

독해 의무의 승격 정본은 `verify-rounds/계약/수리.md` 작업 순서 2와 수행 기록의 「읽은 범위」, `SKILL.md` 1단계 판독의 담당 범위 대조다. 검색·diff·요약으로 통독을 대신하지 않고 잘린 부분을 다시 읽는다. 담당 파일 누락이나 미독은 기존 결손 규칙(1회 재파견, 재차 결손이면 결번)으로 처리한다. 필수 범위를 끝내지 못한 관점은 구체적 지적이 있어도 전건 검토로 보고하지 않는다. 재파견으로 미독이 해소된 런과 해소되지 않은 런이 모두 있었다. [[M-0279]] [[M-0280]] [[M-0282]] [[M-0283]] [[M-0289]] [[M-0299]] [[M-0300]] [[M-0304]]

승격 뒤의 실제 런에서도 파일을 열어 행 수만 집계한 전행 독해표와 실제 본문 전달 사이에 결손이 드러났다. 담당 사본의 파일·행 범위, 수행 기록, 실제 도구 반환은 각각 대조한다. CLI 표시 로그가 실제 입력을 그대로 보존한다고 가정하지 않는다. 두 기록의 양방향 불일치와 원문 행 대조의 한계는 [[L-0015]]의 측정 항목에 있다. 입력 출현은 이해의 완전성이나 결함 부재를 증명하지 않는다. 실제 입력 대조를 명문화하는 보강은 [[D-0009]]의 미적용 제안이며, 기존 규정에 이미 승격됐다고 읽지 않는다. 이후 런에서 수리자 셋의 전문 독해 신고를 실제 도구 반환과 대조하자 미리보기 절단과 파일별 기록 누락이 드러났다. 확인한 미독 좌표를 같은 모델·컨텍스트에 지급해 기존 판단까지 다시 대조하게 하자 두 수리자가 추가 항목 7건을 냈다. 이 지급 방식은 장부의 자체 판단으로 기록됐으며 공통 결손 절차의 일반 예외가 아니다. 독해가 끝까지 닿지 않는 형태는 그 뒤에도 셋 더 나왔다. 관점 하나는 diff 21,296행 가운데 400행만 직접 읽고 나머지를 하위 독해자 아홉에게 넘겼다. 영역 하나의 수리자는 컨텍스트를 넘겨 자동 압축됐다(아래 분담의 축 문단). 다른 관점 수리자는 필수 독해 두 파일의 각 행을 앞 300~400자만 읽었다(아래 동결문 진술 문단). 이 형태들은 「읽은 범위」 신고만으로 드러난다는 보장이 없다. [[M-0333]] [[M-0334]] [[M-0338]] [[M-0339]] [[M-0352]] [[M-0354]] [[M-0356]]

전건 관점의 미독 뒤에 각 관점 담당자가 한 영역을 필수로 읽고 연결된 생산·소비 경로를 추적하는 분담이 쓰였다. 영역의 합집합과 관점별 필수 범위를 각각 대조하며, 이 구조를 모든 관점이 전건을 읽은 것과 같게 보고하지 않는다. 같은 분담에서도 출력 절단이 생겼으므로 분담은 실제 전달 확인을 대신하지 않는다. 같은 모델·노력·컨텍스트에서 부족한 파일을 다시 읽고 판단을 보완한 사례는 있다. 특히 M-0338은 이를 신호 4 자체 처리로 기록했으며, 일반 결손 규칙을 대체하는 자동 예외로 삼지 않는다. [[M-0333]] [[M-0334]] [[M-0336]] [[M-0337]] [[M-0338]]

분담의 축은 독해가 끝까지 닿는지를 정한다. 관점을 커밋 diff 이력으로 나누자 변경의 목적과 파급을 판정한 회귀 발견이 여럿 나왔지만, 두 커밋을 합친 관점은 한 컨텍스트를 넘었다. 관점을 관통 대상(직전 커밋의 변경, 공유 규칙 표의 위치 모듈 묶음, 역할 계약)으로 나누고 필수 독해를 수천 행 이하로 묶자 네 관점이 모두 직접 끝까지 읽었다. 같은 런의 영역은 행 수로만 균형을 잡아 최대 약 23k행이었고, 그 영역의 수리자가 컨텍스트를 넘겨 자동 압축됐다. 세션은 서브에이전트의 컨텍스트 상태를 관찰하지 못해 완료 통지를 기다렸고, 사용자가 이를 알려 재파견했다. 다음 런은 영역을 하위 체계의 수직 절편(코드·시험·픽스처·계약 문서를 묶은 단위)으로 약 14k행씩 나누었고, 영역 수리자 여섯이 모두 끝까지 읽었다. 이 수치들은 당시 모델·노력·저장소의 관찰이며 고정 문턱이 아니다. 대형 항목을 파견 전에 예상 독해량으로 재는 규칙은 이 런들보다 앞서 아래 「모델과 비용」에 있었다. 영역 배분에서 그 규칙이 적용되지 않은 원인은 스킬 「배분」 문면이 자연 경계와 바이트 크기만 적는 공백과, 기존 규칙이 행동 시점에 적용되지 않은 형태([[L-0012]] 「규범이 실제로 적용되는지 점검」) 가운데 하나로 가려지지 않는다. 그래서 크기 측정은 관점과 영역에 함께 적용하고, 완료 통지만으로 서브에이전트의 컨텍스트 초과를 알 수 있다고 가정하지 않는다. 그 규칙을 현행 스킬 「배분」 문면에 연결하는 보강은 사용자 승인을 기다리는 제안이다. [[M-0352]] [[M-0354]] [[M-0356]]

항목별 심사와 별도로 산출물 전체를 독립 독해하는 방식도 쓰였다. 새 do-math 문서 런에서는 8개 Markdown 전체를 심사 모델로 따로 읽혀 런 전체에서 일곱 번 독해했다. 지적 가운데 코드와 기존 사용자 조건으로 결정되는 문면만 고쳤고, 독자의 불확실성을 모두 새 기능 요구로 바꾸지 않았다. [[M-0603]] [[M-0607]]

동결문의 진술은 역할 계약이 실제로 읽는 판정 단계를 채울 때 처분을 바꿨다. 심사 계약의 관문 2는 고칠 만한 크기의 잣대를 동결문에 맡긴다. 동작을 바꾸지 않는 잔재 정리 15건을 심사자들이 승인하고도 모두 무처분(승인하되 고치지 않음)으로 고른 런 뒤, 다음 동결문은 목적 진술 첫머리에 두 가지를 적었다. 쓰이지 않는 요소와 규칙 사본이 이 런이 없애려는 손상이라는 것과, 동작이 같다는 사실만으로는 무처분의 근거가 되지 않는다는 것이다. 그 런의 무처분은 0건이었다. 반대로 수리자에게 준 초점의 무게는 깊이를 만들지 않았다. 가장 무거운 초점을 맡은 관점은 필수 독해를 행 앞부분만 읽고 graphify를 쓰지 않은 채 항목 3건으로 끝났다. 같은 에이전트를 재개해 미독 보완, graphify 활용, 발견 최대화를 구체적으로 가리키자 항목이 늘었고, 그 하나는 앞선 병렬 구현 묶음 사이의 의미 충돌이었다. 무거운 초점은 영역 수리자에게도 판정 기준으로 주고, 관점 산출은 항목 수보다 필수 독해와 도구 사용의 이행을 먼저 대조한다. 동결문이 명시로 금했는데도 수리자들이 후보를 다른 관점의 몫으로 미뤘다. 수행 기록의 「항목으로 쓰지 않은 후보」는 세션이 판정할 자료다. 한 수리자가 확인만 하고 넘긴 후보를 세션이 구현 에이전트에게 확인시키자 실제 독립성 누출로 재현됐다. 위 대비는 범위가 다른 런 한 쌍씩의 비교여서 인과의 크기는 확정되지 않는다. [[M-0352]] [[M-0354]] [[M-0356]]

항목별 만장일치 승인은 적용 뒤의 결과를 보증하지 않는다. 편집 구간이 겹치지 않는 조각도 함께 적용하면 모순을 만들 수 있고, 승인된 조각이 기존 진단 문구나 실패 결과를 지워 회귀를 만들기도 했다. 실제 회귀를 만든 항목은 승인 조각을 고쳐 쓰지 않고 제외한 뒤 나머지를 공식 적용 경로로 다시 반영한 사례가 있다. 반면 시험 모형이 현행 계약과 모순되면 제품 검사를 유지하며 시험 전제를 고쳤고, M-0338은 이를 신호 6 자체 처리로 기록했다. 원인 구별은 [[L-0001]]의 검증 계약을 따른다. 최종 문면과 적용 뒤 실행을 확인하고 최초 실패·수정·재검사 및 미실행 범위를 보존한다. [[M-0282]] [[M-0289]] [[M-0333]] [[M-0337]] [[M-0338]] 코드를 실행하지 않는 수리와 심사는 같은 거짓 전제를 함께 승인할 수 있다. 스키마에서 속성을 지우면 입구에서 거부된다는 수리안을 심사자 셋이 모두 승인했지만, 스키마 도우미가 추가 속성을 닫지 않아 지운 키가 통과했고 마지막 통합 확인이 이를 잡았다. 그래서 마지막 라운드 뒤의 통합 확인은 생략하지 않는다. 실행 없는 판정의 사각은 [[L-0001]] 「검증 사각의 세 축」에 있다. [[M-0357]] 반대로 심사가 타당한 지적에 붙은 잘못된 수리를 잡은 사례도 있다. 설정 경로를 세션에 준다는 사실을 기동 때 읽는다는 보장으로 적은 수리, 어댑터 시험의 Python 요건을 전체 시험으로 넓힌 병합이 그 예다. [[M-0602]]

적용 뒤 불변식 재실측은 남은 편집 계획과 함께 배치한다. 기각·무처분의 직접 반영이 예정된 상태에서 적용 직후 통합 확인 세 묶음을 띄웠다가, 결과를 쓸 수 없다는 사용자 지적으로 멈추고 반영 뒤 한 번만 돌린 사례가 있다. 같은 라운드에 산출물을 더 바꿀 편집이 있으면 재실측을 마지막 편집 뒤로 모으고, 실패가 나오면 어느 변경이 원인인지는 분석으로 가른다. 기준선의 재사용은 위 「병렬 구현 파견」의 시험 규율에 있다. 현행 스킬 §7의 「불변식 재실측」은 적용 직후 재실측만 적으며, 시점을 보강하는 문구는 사용자 승인을 기다리는 제안이다. [[M-0352]]

기각은 결함의 부재와 구별한다. 결함은 실재해도 수리안의 시험 오류, 유효한 문서 정보·현재 검사 삭제, 인용·서식 오류, 조각의 구간 규약이나 의존 구간 미달 때문에 기각될 수 있다. 연속한 세 런에서도 기각의 주된 원인은 조각 좌표 규약, 저장 계약 식별자 판단 누락, 문서의 과잉 단정, 시험 부족, 반쪽 수리 같은 수리안의 형식·범위였다. 원래 결함이 실재한다는 사실만으로 조각이 주장한 모든 효과를 승인할 수는 없다. 대기 종결과 정리 제외를 함께 주장한 병합안에서, 실제 손상은 대기 종결뿐이어서 그만 보완하고 정리 제외의 근거인 미결 실패는 보존했다. 반대로 소비 경로를 대조하자 원 지적의 근거가 없어 기각을 유지한 사례도 있다. 사용자가 기각·무처분 전건의 직접 재검토를 지시한 런에서는 원 결함, 수리안, 사용자 목적을 따로 대조해 후속 처분을 정했다. 죽은 인자 제거가 명시된 작업에서 실행 결과가 같다는 이유로 무처분된 수리를 직접 반영한 것과, 사족·중복 정리를 지시한 런에서 중대성 관문으로 무처분된 정리를 반영한 것이 이 경로다. [[M-0336]] [[M-0337]] [[M-0338]] [[M-0602]] 이 위임이 있던 두 런에서 직접 회수의 비중은 컸다. 한 런은 여섯 라운드의 기각·무처분 31심사 대상 가운데 27개를 전부 또는 일부 반영했고, 다른 런은 두 라운드의 기각 안건 대부분을 보완하고 하나를 잔여로 남겼다. [[M-0588]] [[M-0589]] [[M-0607]] 직접 재검토는 정규 승인을 적용한 뒤에 해서 최종 보완 판본을 검사하고, 그것을 마치기 전에는 비싼 최종 전수 검사를 시작하지 않는다. [[M-0588]] [[M-0589]] 내용 결함 없이 조각 규약이나 계약 판단 누락으로만 기각된 항목을 보조 스크립트 대신 공식 `적용`의 `--추가`로 넣어 축자 대조(적용 스크립트가 조각이 고칠 원래 문자열을 산출물 원본과 글자 그대로 대조해 전건이 일치할 때만 반영하는 검사) 아래 반영한 런이 있다. 앞선 보조 스크립트(GNU patch)는 승인분과 이웃한 헝크에서 패치 문맥이 어긋났다. [[M-0352]] [[M-0354]] [[M-0356]] [[M-0357]] 원 심사 판정과 사용자 지시에 따른 직접 수리는 별도로 남긴다. 세션이 직접 편집한 반영은 공식 적용 계수에 넣지 않는다. 공식 `적용`의 `--추가`로 넣은 항목은 본표 상태가 「적용」으로 서므로, 원 판정은 기각 보관 파일로 확인한다. 이를 운전자의 일반적인 승인 우회 권한이나 일반 파견 절차의 독자 수리 단계로 확대하지 않는다. 미해결 문제는 잔여로 보존한다. [[M-0357]] [[M-0588]] [[M-0602]] [[M-0607]] [[D-0009]]

심사자는 파견문이 준 것, 산출물, 기준 원문만 본다. 상신의 근거가 된 사용자 결정 기록(M-0321, M-0299)이 동결문 기준 원문에 없어 심사자가 정당한 상신을 기각한 일이 한 런에 있었고, 그 사례는 라운드 1에서 처음 기록됐다. 상신이나 판정이 기댈 사용자 결정 기록(결정이 인용된 기억 노드와 결정 문서)은 동결 때 기준 원문에 넣는다. 동결문의 기준 목록과 검사 명령은 세션이 실재 경로와 실제 명령으로 확인한 뒤 적는다. 대화로 받은 지침의 이름을 파일 경로로 적거나 존재하지 않는 검사 명령을 적은 사례가 있었다. 마지막 라운드 뒤에는 독립 심사가 없으므로 세션의 직접 처리는 좁게 하고, 설계를 바꾸는 상신 사안은 사용자에게 올린다. 그 런에서 사용자는 추천대로 결정했고, 별도 작업자의 반영을 마지막 통합 확인이 검증했다. [[M-0279]] [[M-0299]] [[M-0356]] [[M-0357]]

사용자가 상신 안건을 보류하거나 앞선 선택을 바꾸면 최신 결정만 다음 라운드의 확정 사항으로 지급한다. 한 런에서 사용자의 최종 보류가 앞서 고른 선택을 대체했다. 다음 라운드에는 그 결정만 별도 파일로 지급하고, 앞 라운드의 심사 사유나 기각 위치는 지급하지 않았다. 보류의 범위도 넓히지 않았다. 보류된 정책을 포함한 조각은 적용하지 않았지만, 보류 밖의 좁은 수리는 잔여로 보고했다. [[M-0588]] [[M-0589]]

수리자의 열람 경계는 계약이 정한 분리가 닿는 모든 좌표에 둔다. 기각 보관 디렉토리가 런 루트에 `_` 접두 없이 생겨 수리 파견문의 「읽지 않는 것」 좌표에 걸리지 않았고, 다음 라운드의 수리자가 앞 라운드 처분을 읽었다. 수리 계약의 「열람 한계」는 런 중간물을 읽지 않게 하지만 중간물을 파견문의 「읽지 않는 것」 줄과 앞 라운드 디렉토리로 열거해 정의하며, 기각 보관은 그 열거에 없었다. 현행 스킬에 기각 보관 좌표를 명시하는 보강은 사용자 승인을 기다리는 제안이다. [[M-0357]]

산출 계약 위반은 그 계약이 지키는 것이 손상됐는지로 판정한다. 수리자가 `/tmp`에 임시 diff를 만들거나 사본 모듈을 import해 `.pyc`를 남긴 위반에서, 세션은 기본값인 결손 재파견 대신 좌표 기준 사본이 앵커와 같음을 확인했다. 캐시를 지운 뒤 결손으로 처리하지 않았고, 판단을 장부 운영 기록에 남겼다. 원인은 수리자가 diff를 임시 파일 없이 읽기 어려운 구조였다. [[M-0352]] 다른 런에서는 수리자가 산출을 교체하며 임시 파일을 만들었지만 최종 지정 파일과 공식 검산은 정상이었고, 사용자가 재파견 없이 최종 산출을 쓰도록 예외를 확정했다. 이런 예외를 산출 계약의 폐지로 확대하지 않는다. [[M-0588]]

라운드 상한으로 끝난 런은 수렴이나 무결함을 뜻하지 않는다. 유효 산출의 처리를 마친 뒤 종료 이유와 미완료 범위를 나누어 남긴다. 수리 항목, 병합된 심사 항목, 편집 조각, 장부의 구성 항목 행은 서로 다른 계수 단위이므로 같은 적용 건수로 합치지 않는다. [[M-0334]] [[M-0336]] [[M-0337]] [[M-0338]] [[M-0607]]

수리자가 이미 산출물 안에서 결정된 권한과 방향으로 고칠 수 있는 문제를 새 사용자 선택으로 올리면, 결함을 찾고도 수리안이 나오지 않는다. 구현 대안이나 반복 횟수를 제시할 수 있다는 사실은 사용자에게 새 의도를 물을 근거가 아니다. 산출물 안의 과거 문장도 사용자 확정이 아니다. 사용자가 잔재 제거 방향을 정한 런에서 수리자 넷이 README의 미지원 기능 예약 설명을 사용자 확정으로 읽고 상신했고, 심사는 문서의 존재와 사용자 확정을 구별해 상신 형식을 기각했다. [[M-0300]] [[M-0301]] [[M-0339]]

Codex 운전 세션에서 종료 뒤 정리의 재귀 삭제 명령은 자동 승인 검토에 세 런 연속 실행 전 거부됐고, 사용자가 다시 승인한 뒤에도 같았다. [[M-0281]] [[M-0285]] [[M-0290]] 이후의 다른 런에서도 앵커·라운드 작업 디렉터리 제거가 자동 승인 검토에서 거부됐고, 삭제 대상을 일곱 개의 고정 절대 경로로 좁혀도 같았다(그 런의 운전 세션 종류는 기록에 없다). [[M-0607]] 다른 셸이나 이동으로 우회하지 않고 정리 미완료를 장부와 종료 보고에 적으며, 검증 결과와 푸시는 정리와 독립적으로 처리한다. [[M-0281]] [[M-0285]] [[M-0290]] [[M-0607]] 앵커·라운드 밖의 파견 스크립트, 상태 파일, 독해 초안 같은 미추적 중간물은 정리 절차의 대상이 아니어서 `임시/`에 누적됐다. 현재는 `.gitignore`가 `임시/` 아래 작업 디렉터리의 내용(`/임시/*/*`)을 기본으로 무시하고, verify-rounds가 강제 추가 없이 커밋하는 `동결.md`·`장부.md`·`종료보고.md`만 부정 규칙으로 허용한다. 디렉터리를 통째로 무시하면 그 커밋이 거부되고 Git이 무시된 디렉터리 안의 부정 규칙을 적용하지 않으므로 내용을 무시하는 형태를 택했다. 그 밖에 보존할 증거는 `git add -f`로 추가한다(승격 정본: `commit-harness` 5항). 산출물 자체가 `임시/` 작업 디렉터리 안에 있는 런은 산출물 커밋에 `-f`가 필요하다. 로컬 디스크의 누적은 이 규칙으로 줄지 않으며 삭제가 허용되는 세션에서 정리한다. [[M-0281]] [[M-0285]] [[M-0290]] [[M-0303]] [[M-0306]]

Claude Agent 도구가 없는 운전 세션에서는 같은 역할 정의와 모델·노력을 명시한 로컬 Claude CLI를 사용했고, Codex 심사자가 사용 한도로 종료하자 같은 모델의 독립 컨텍스트로 바꾸면서 정족은 유지했다. CLI 운송에서는 `--safe-mode`로 커밋 기억과 훅의 자동 주입을 끄고 계약과 현행 기준을 명시적으로 지급한 런이 있다. 운송 수단의 변경은 장부의 운영 기록이며 사용자 확정으로 취급하지 않는다. [[M-0279]] [[M-0299]] [[M-0300]] [[M-0589]] [[M-0602]]

파견이 공급자 한도(429)로 산출 없이 끝나면 검토 완료나 결함 0으로 세지 않고 실패 기록을 보존한다. 해제 시각이 지난 뒤 같은 모델·노력·파견문으로 다시 실행하며, 그 전에 원본과 라운드 사본의 동일성을 확인한다. 대기 여부를 사용자에게 물었으나 회신이 없을 때에는 기존 지시대로 기다린 뒤 재파견했다. [[M-0589]] [[M-0605]]

## verify-rounds 런 사이의 실제 실행 관찰

대역 기반 시험이 통과해도 실제 도구의 계약은 보증되지 않는다. 재구축 do-math의 전면 검증에서 108시험이 통과한 판본이 실제 Lean 4.32의 캐시 빌드에서 실패했다. 대역 컴파일러가 실제 산출 묶음을 표현하지 않았기 때문이다. [[M-0633]]

운전 세션은 라운드 2·3·4·5 뒤의 경계에서 실제 실행 관찰과 재현 프로그램을 동결 원자료에 넣었다. 이때 다음을 지켰다. [[M-0633]]

- 이전 판정과 바라는 수리는 새 탐색 입력에 넣지 않았다.
- 관찰은 진단이나 대체 문면을 지정하지 않는 실행 증거로 제공했다.
- 부분 검토한 라운드를 바뀐 스냅샷에서 이어 가지 않았다.
- 입력 변경의 판단은 장부에 남겼다.

결함을 보인 관찰 세 건은 각각 다음 라운드에서 고쳐졌다. 캐시 동반 산출, 접수 직후의 취소, 음수 종료 코드다. 이 결함들은 시험 스위트가 아니라 실제 실행에서 드러났다. 보강한 시험의 관측 능력은 시험 수가 아니라 임시 사본에 결함을 주입해 확인했다. 의도한 결함에서는 실패하고 대조군에서는 통과하는지를 본 것이다. [[M-0632]] [[M-0634]] [[M-0635]] [[M-0636]] [[M-0637]] [[M-0640]]

같은 런에는 다음 운영 판단이 기록됐다.

- **신호 3 뒤의 계속.** 심사 항목 수가 두 번 연속 줄지 않은 신호 3에서 운전 세션은 두 번 계속했다. 5라운드에서는 실제 결함이 수리되고 있었고, 새 반례가 남았으며, 변경을 되돌릴 수 있었고, 상한이 유지된다는 근거로 스스로 계속했다. 8라운드에서는 사용자가 당시 추가 Astra 라운드를 요구하고 있었다. 두 결정 모두 독립 심사, 시험, 되돌릴 수 있는 커밋이 비용을 제한했다(`임시/do-math_검증_20261105/종료보고.md` Self-handling 5). [[M-0636]] [[M-0638]]
- **진행 중 상한 변경.** 사용자가 진행 중 모델과 라운드 수를 바꾸자, 이미 끝난 라운드를 다시 돌리지 않고 종료 경계에서 상한을 바꾸었다. [[M-0638]] [[M-0640]]
- **조각 없는 승인 제안.** 이런 제안(R7-06, R8-10)은 적용으로 세지도 기각하지도 않았다. 위임된 개인 감사가 시험된 수리를 낼 때까지 승인·미적용으로 보존했다. [[M-0638]] [[M-0640]]

## 외부 한도로 지정 수단이 막혔을 때

독립 독해에 지정된 실행 수단이 공급자 한도로 막힌 두 기록이 다른 선택을 했다. 한 번은 다른 모델로 대체하지 않고 독해를 미완료로 남겼고, 그 기록은 이유를 적지 않았다. 다른 한 번은 실행기 밖의 다른 모델 에이전트에게 원고와 독자 정보만 주는 대체 독해를 했고, 앞의 선택을 Opus 5 전용 연구라는 제약 아래의 결정으로 읽었다. 이 해석은 사용자에게 알렸고 이의는 없었다. 여기서 읽어 낸 작업 판단은, 지정 수단을 묶은 것이 사용자 조건인지 도구의 기본값인지를 먼저 가린다는 것이다. 사용자가 확정한 규칙이 아니므로 대체할 때에는 그 해석을 사용자에게 알린다. 세 번째 사례에서는 특정 모델만 쓰라는 사용자 조건이 없음을 확인한 뒤 대체 독해를 두 번 하고 정식 작업을 `blocked`로 남겼다. 어느 쪽에서도 실패한 정식 호출을 성공으로 보완 기록하지 않으며, 정식 작업은 `blocked`로 남기고 대체 수행은 정식 수행과 구별해 적는다. 정식 실행기가 한 공급자만 지원하면 같은 입력·스키마·인용 검증을 쓰는 작업 전용 연결 코드로 다른 공급자를 호출한 사례도 있다. [[M-0310]] [[M-0311]] [[M-0322]] [[M-0325]] [[D-0007]] 런타임 한도가 새 작업자 생성을 막은 사례도 있다. 한정 수리를 새 문맥의 작업자에게 배정하려 했으나 thread limit으로 거부되자, 그 실패를 방금 읽기 전용으로 분석한 작업자에게 같은 문제의 최소 수리만 이어 맡겼다. 전체 작업 이력을 다시 물려주거나 조사 범위를 새로 열지 않았다. [[M-0541]] verify-rounds에서의 운송 수단 변경과 공급자 한도 뒤의 재파견은 위 「verify-rounds」 항목에 있다.

## 모델과 비용

판단 호출을 재사용하는 도구에서는 공통 통신과 상황별 판단 입력을 구별한다. `services/jev-cli/jev.py`는 Python 표준 라이브러리 CLI로 인증·요청·응답 처리를 맡고, 호출자는 대상·맥락·질문·선택지·평가 기준을 지정한다. 사용 계약의 정본은 같은 폴더 `README.md`다. 파일·표준입력과 JSON 출력으로 AI 에이전트와 셸 스크립트가 같은 도구를 쓰며, 질문 의미를 내부 프리셋으로 고정하지 않는다. 서버의 처리 완료 여부가 불명확한 연결 중단·시간 초과는 자동 재시도하지 않는다. Windows의 검사와 실제 예제 호출은 확인됐으나 Linux·macOS 실행과 도메인별 판단 정확도는 미검증이다. 이 경계는 도구의 호출 성공을 판단 품질로 확대하지 않게 한다. [[M-0328]]

경량 모델로 충분히 수행할 수 있는 작업에는 경량 모델을 쓴다. 검증은 생성보다 높은 추론 역량이 필요할 수 있으므로 역할별 하한을 따로 정한다.

대형 항목은 파견 전에 크기를 잰다. 파일 수, 페이지 수, 예상 토큰, 실행 시간을 확인하고 한 작업의 예산을 넘으면 분할하거나 상신한다.
