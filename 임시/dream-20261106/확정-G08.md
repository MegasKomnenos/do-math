# 확정 G08 문서 필드의 소유자 결속과 전체 통합 실행

## 1. 종합 확정본

이 범위(옛 do-math 시험 재편 후반)의 공통 질문은 어떤 통과나 완료가 실제로 무엇을 증언하는가다. [[D-0010]]의 "신호는 그 생산자가 확인한 사건만 증언한다"를 검증 자신의 증거에 적용했다. 검사기와 실행기는 2026-10-21에 삭제됐고(M-0593) 현행 do-math에 문서-코드 필드 대조 검사는 없다. 남는 것은 원리다.

### 문서와 코드의 대응은 소비자가 실제로 받는 반환에서 판정한다

문서가 "객체 Y에 필드 X가 있다"고 쓰면 그 증거는 Y의 소비자가 실제로 받는 반환이다. 생산자 소스의 literal 키를 읽는 구문 결속(AST 결속)은 키가 코드에 적혀 있다는 사실만 증언한다. AST 결속은 검사 공간을 6개에서 84개로(M-0527 직후 24개), 필드 참조를 189곳까지 넓혔고 구조 시험은 매번 통과했다. [[M-0527]] [[M-0531]] 그 뒤 새 문맥의 독립 검토가 반례 둘을 재현했다. 반환에서 지우거나 재대입으로 덮은 키를 통과시켰고, `dict(...)`로 만든 같은 결과에는 실패했다. 구문 분석기를 키우지 않고 실제 반환 결속으로 바꿨으며, 과거 통과 59개는 지우지 않고 입증하지 못한 범위를 적었다. [[M-0532]] 다섯 노드의 연속 확장 동안 이 반례는 기록되지 않았으나, 이것이 새 문맥이 발견의 원인이라는 인과를 입증하지는 않는다.

교체는 같은 절차를 반복했다. 실제 결과는 그 결과를 이미 만드는 기존 시험에서 얻었다. [[M-0536]] [[M-0537]] [[M-0539]] 기존 시험이 필요한 키를 만들지 않으면 그 시험 안에서 입력 설정을 최소로 바꾸거나 같은 함수의 호출을 하나 더했고, 같은 값을 만드는 이웃 명령이나 어댑터의 반환으로 근거를 대신하지 않았다. [[M-0546]] [[M-0548]] 중간 생산자가 키를 반환한다는 사실도 최종 응답의 증거로 쓰지 않았다. [[M-0537]] [[M-0538]] 실제 결과가 없으면 기본으로 거부하고 보류는 이름으로만 허용했다. [[M-0538]] [[M-0546]] 교체 전에 옛 검사의 거짓 통과를 실패 시험으로 먼저 보였다. [[M-0545]] [[M-0547]] 실제 결과의 사본에서 키를 하나씩 지워 참조가 실패하는지 확인했다. [[M-0538]] [[M-0545]] 배열은 모든 항목에 공통인 키만 인정하고 빈 배열은 증거로 쓰지 않았다. [[M-0545]] [[M-0547]] 같은 이름은 출현마다 소유자를 정하고 전역 합집합으로 승인하지 않았다. 모집단 전건의 소유자를 정한 뒤 미소유 이름을 실패시키는 검사로 닫았다. [[M-0527]] [[M-0528]] [[M-0529]] [[M-0530]] 경로 한계의 새 발현은 둘이다. 응답 봉투 `CompletedProcess`는 실제 subprocess 실행의 증거가 아니고, 반환 manifest의 검증은 manifest 파일 출판의 검증이 아니다. [[M-0546]] [[M-0547]]

판정: 새 정보(증거 종류의 교체와 교체 절차, 이웃 생산자 대체의 거부, 출현별 소유자와 모집단 닫기)와 재실증(경로 한계 일반은 `L-0001` "검증 계약", 어휘 부재는 `L-0001` "거짓 GREEN을 막는 기준"·"도구 운용", 무력화 프로브). 대조: `L-0001` "검증 사각의 세 축", "거짓 GREEN을 막는 기준", "검증 계약", "도구 운용".

### 한 판본의 전체 실행만 전체 통과를 증언한다

전체 통과는 한 판본에서 선택한 시험 ID 전부가 최종 보고의 실제 행에 대응한 실행만 증언한다. 이 범위가 더한 것은 네 상황의 처분이다. 결과 게시가 중단된 시험은 실패로도 통과로도 추정하지 않고 미실행으로 둔다(B123 3984개 중 558개). 미실행 모집단만 다시 돌린 B126의 571통과는 fixture와 실행기가 바뀐 뒤라 B123과 합치지 않았다. [[M-0540]] [[M-0541]] [[M-0542]] 진단이 보존 로그 밖으로 빠지는 구조를 고친 실패 주입 시험은 보존 경로만 입증하며 원래 Windows 오류는 확정되지 않았다. [[M-0540]] [[M-0541]] 끊긴 실행(B127)은 낡은 running 표시나 핸들 상실이 아니라 실제 프로세스 대조로 판정하고 중복 기동하지 않았다. [[M-0543]] 완결과 성공은 다르다. B129는 3990개를 완결했으나 1실패였고, "현재 판본의 전건 판정" 관문만 닫았다. [[M-0544]] 실행기의 판본 지문은 Python 파일만 덮어 추적·미추적 969파일 해시와 HEAD를 따로 보존했다. [[M-0539]] [[M-0544]]

두 전체 실행이 잡은 실패는 모두 원인이 된 변경의 한정 검증이 선택하지 않은 검사에서 나왔다. B123은 앞선 B88이 바꾼 Git 탐색 계약을 따라가지 못한 flow fixture였다. [[M-0539]] [[M-0540]] B129는 시험 코드의 나쁜 패턴을 찾는 구조 검사(`test_test_smells`)가 사유를 고정하지 않은 거부 시험(`unpinned_rejection`)으로 잡은 직전 B128의 음성 시험이었다. [[M-0543]] [[M-0544]] 인계 확인과 통합 확인의 분담에서 통합 확인이 실제로 몫을 한 증거이며, 절차가 없었으면 얻지 못했을 결과다.

판정: 재실증(합산 금지, 최초 실패 보존, 건너뜀 분리)과 새 정보(네 상황의 처분, 판본 지문의 모집단, 통합 확인의 실효 두 사례). 대조: `L-0001` "거짓 GREEN을 막는 기준", "검증 계약", `L-0020` "검증 증거의 범위", `L-0016` "시험 선택과 실행 규율".

### 작업 단위는 압축 없이 끝나게 한정하고, 경계는 생산 경계로 정한다

사용자는 장기 실행의 비효율을 지적한 뒤, 압축 뒤 복구를 잘하는 방식보다 처음부터 압축 없이 끝낼 수 있는 작업 방식을 요구했고, 작업 목록 작성과 이전 작업의 재검토도 그 방식으로 하게 했다. [[M-0532]] 그 뒤 한 단위는 실제 입력 경로·대상 구간·산출물 하나·검증으로 한정한 지시서로 대화 이력 없는 새 작업자에게 배정됐다. [[M-0532]] [[M-0533]] [[M-0549]] 단위의 경계는 이름이나 묶음 제목이 아니라 생산 경계와 그 실제 결과로 정해졌다. 묶음 이름 PURE가 실제 경계와 달라 파일·콜백 경계를 가진 함수를 뺐고, 같은 CLI 코드와 경계 시험에 모인 세 결속은 한 단위로 묶었으며, 같은 함수 안에서도 소유자가 다른 `profile_selection`은 따로 두었다. [[M-0534]] [[M-0546]] [[M-0547]] 이 원리는 첫 소제목의 "증거는 그 생산자의 실제 결과"와 같은 원리다. 직전 작업이라는 이유의 우선순위와 실제 의존이 없는 종속도 지웠다. [[M-0532]] 새 작업자 생성이 thread limit으로 거부되자 방금 그 문제를 분석한 작업자에게 최소 수리만 이어 맡겼다. [[M-0541]] 효과의 증거는 반례 재현 한 건뿐이고 압축 횟수·시간·비용은 측정되지 않았다.

판정: 새 정보(압축을 예방하는 단위 설계, 생산 경계에 따른 단위 경계, 관성 순서의 거부, thread limit 아래의 이어 맡김, 전달 경로에 맞춘 한도 확인 [[M-0533]])와 재실증(상태를 파일에 둠, 반환문보다 실제 diff, 공유 트리 편집 분리, 미추적 초안의 내용 보존). 대조: `L-0015` "읽기 단위와 파일 단위", "측정", `L-0016` "상태의 정본", "분해와 병렬화", "회수 검증", `L-0006` "세션 경계", `L-0005` "충분한 확인 없이 익숙한 방식을 선택하는 경향".

### 후보 목록·대응표·탐색 결과를 처리 완료로 읽지 않는다

## 5. L 패킷 확정본

### L-0001

**신설**

```markdown
## 문서와 코드의 대응 검사

문서가 "객체 Y에 필드 X가 있다"고 적으면 그 주장의 증거는 Y의 소비자가 실제로 받는 반환이다. 생산자 함수의 소스에서 literal 키를 읽는 구문 결속(AST 결속)은 그 키가 코드에 적혀 있다는 사실만 증언한다. 옛 do-math의 문서 필드 검사는 AST 결속으로 검사 공간을 6개에서 84개로, 필드 참조를 189곳까지 넓혔다. [[M-0527]] [[M-0531]] 그 뒤 새 문맥의 독립 검토가 반례 둘을 재현했다. 반환에서 지우거나 재대입으로 덮은 키도 있다고 통과시켰고, 같은 결과를 `dict(...)`로 만든 표현에는 실패했다. 이후 구문 분석기를 키우지 않고 기존 시험이 이미 만드는 실제 반환에 결속하는 방식으로 바꿨다. 과거의 구조 통과 59개는 지우지 않고, 그 통과가 입증하지 못하는 범위를 상태 기록에 적었다. [[M-0532]]

교체에서 쓴 절차는 다음과 같다.

- 실제 결과는 그 결과를 이미 만드는 기존 시험에서 얻는다. 순수 함수는 정상 입력으로 직접 호출하고, 저장소·파일·CLI 경계의 결과는 그 경계를 이미 실행하는 시험의 최종 응답을 쓴다. 문서 구조 검사 안에서 저장소나 엔진을 새로 기동하거나 범용 재귀 추론기를 만들지 않는다. [[M-0536]] [[M-0537]] [[M-0538]] [[M-0539]] [[M-0545]] [[M-0546]] [[M-0547]] [[M-0548]] [[M-0549]]
- 기존 시험이 문서가 가리키는 키를 만들지 않으면 그 시험 안에서 입력 설정을 최소로 바꾸거나 같은 함수의 호출을 하나 더해 실제 결과를 얻는다. 이웃 생산자(같은 값을 만드는 다른 명령이나 어댑터)의 반환으로 근거를 대신하지 않는다. 중간 생산자가 키를 반환한다는 사실도 최종 응답이 그 키를 담는다는 증거가 아니어서, 문서가 최종 응답을 가리키면 최종 응답에서 확인한다. [[M-0537]] [[M-0538]] [[M-0546]] [[M-0548]]
- 실제 결과가 주어지지 않으면 검사는 기본으로 거부한다. 다른 경계의 시험은 자신이 제공하지 않는 소유자만 이름으로 보류하고, 보류 이름의 오기도 거부한다. [[M-0538]] [[M-0546]]
- 교체 전에 옛 검사가 실제 결과 없이 통과한다는 사실을 실패 시험으로 먼저 보인다. 그 실패가 import 오류나 새 인자 오류가 아님을 확인한다. [[M-0545]] [[M-0546]] [[M-0547]] [[M-0548]] [[M-0549]]
- 실제 결과의 사본에서 키를 하나씩 지우면 그 키를 가리키는 문서 참조가 실패하는지 확인한다. 다른 소유자의 키를 빌린 참조와 배열 표기의 오류도 거부한다. [[M-0538]] [[M-0545]] [[M-0547]]
- 배열 항목의 필드는 모든 항목에 공통인 키만 인정하고, 빈 배열은 항목 필드의 증거로 쓰지 않는다. [[M-0545]] [[M-0547]] [[M-0548]]

같은 이름은 같은 소유자를 뜻하지 않는다. 저장된 실행의 `execution_window`와 역할 입력의 `execution_window`는 다른 객체였고, `record.content`·`record.explanation`·`record.family`는 문장마다 다른 객체를 가리켰다. 그래서 출현마다 소유자를 정하고, 이름의 전역 합집합으로 승인하지 않는다. 필드, 함수, 진단 코드, 파일명은 종류부터 구별한다. [[M-0527]] [[M-0528]] [[M-0529]] 모집단 전건의 소유자를 정한 뒤에는 소유자가 없는 이름을 실패시키는 검사로 모집단을 닫는다. 그래야 오타나 새 공간의 미등록이 조용히 통과하지 않는다. ## 한 판본의 전체 실행
```

```markdown
전체 시험의 통과는 한 판본에서 한 번 완결된 실행만 증언한다. 완결은 선택한 시험 ID 전부가 최종 보고의 실제 행에 대응하는 상태다. 서로 다른 시점이나 판본의 부분 결과를 합산해 전체 통과로 쓰지 않는다. 옛 do-math의 B123은 3984개를 선택해 3424통과·1실패·558미실행·1건너뜀으로 끝났다. 미실행 558개가 속한 86개 모듈을 따로 돌린 B126은 571개가 모두 통과했다. 그러나 그 사이 fixture와 실행기가 바뀌었으므로 B123의 통과와 합치지 않았고, 전체 통과의 판정은 수정된 판본의 새 전체 실행으로 넘겼다. [[M-0533]] [[M-0540]] [[M-0541]] [[M-0542]] [[M-0544]]

실행 결과는 통과, 실패, 건너뜀, 미실행의 넷으로 나누어 기록한다. 결과 게시가 중단되어 보고되지 못한 시험은 실패로도 통과로도 추정하지 않고 미실행으로 둔다. B123의 마지막 보고 행은 running이었지만 stderr에는 ok가 있었고 남은 임시 결과에는 passed가 있었다. 권한 부족으로 건너뛴 시험(WinError 1314)을 통과로 세지 않는 기준은 이 노드의 "거짓 GREEN을 막는 기준"에 있다. 완결(complete)과 성공(successful)도 구별한다. B129는 3990개를 모두 완결했지만 1실패로 성공은 아니었다. 이 결과는 "현재 판본의 전건 결과를 판정하고 실패를 한정 수리로 배정한다"는 관문을 닫았고, "최종 판본의 전체 성공"이라는 다른 관문은 열어 두었다. [[M-0540]] [[M-0544]]

실행이 끊기면 남은 표지보다 실제 상태를 본다. B127은 환경 중단 뒤 세션 핸들이 사라졌고, 실제 프로세스 조회에도 실행기와 작업자가 없었으며, 최종 보고도 없었다. 실행 기록의 running을 stopped_without_final_report로 정정하고 중간 결과를 보존했다. 핸들 상실만 보고 실행을 중복 기동하지 않았다. 작업자의 예외가 stderr 리디렉션 밖으로 전파되면 진단이 보존 로그에 남지 않는다. 그래서 traceback을 같은 stderr에 쓴 뒤 원래 예외를 다시 올리게 고쳤다. 이 수리를 확인한 실패 주입 시험은 진단의 보존 경로를 입증할 뿐 원래 오류를 재현하지 않으며, B123의 원래 Windows 오류는 확정되지 않았다. [[M-0540]] [[M-0541]] [[M-0543]]

판본 고정의 증거는 그 실행이 의존하는 파일 전체를 덮어야 한다. 실행기의 판본 지문은 `scripts/**/*.py`만 기록하고 JSON 처분표, 다른 문서, Git HEAD는 기록하지 않았다. 그래서 실행 전후의 추적·미추적 969개 파일 해시와 HEAD를 따로 보존했고, 네 번의 실행 모두 변화가 없었다. 긴 고정 실행 중에 다음 수정 후보를 준비할 때에는 정본이 아닌 별도 사본에서 준비하고, 적용 직전에 대상 원본의 해시가 그대로인지 확인했다. [[M-0539]] [[M-0540]] [[M-0542]] [[M-0543]] [[M-0544]] [[M-0545]]

같은 판본의 전체 실행은 원인이 된 변경의 한정 검증이 선택하지 않은 검사에서 결함을 찾았다. B123의 유일한 단언 실패는 앞선 수리 B88이 바꾼 Git 저장소 탐색 계약을 따라가지 못한 flow fixture였고, 그 수리의 후속 검사 선택에 이 시험이 들어가지 않았다. [[M-0543]] [[M-0544]] 인계 확인은 고친 모듈과 고친 시험만 돌리고 소비자 동작은 통합 확인이 맡는다는 분담은 [[L-0016]] "시험 선택과 실행 규율"에 있다. 두 사례에서 통합 확인이 그 분담대로 결함을 찾았다. [[M-0540]] [[M-0544]]
```

```markdown
- 병합 후 확인할 연결 지점을 식별할 수 있다.
- 한 작업의 실패가 다른 작업의 정본을 오염시키지 않는다.

병렬화는 처리량을 늘리지만 공유 토큰 한도와 회수 비용도 늘린다. 각 단계가 끝날 때 상태를 파일에 기록해 한도 도달과 세션 교대에 대비한다.
```
