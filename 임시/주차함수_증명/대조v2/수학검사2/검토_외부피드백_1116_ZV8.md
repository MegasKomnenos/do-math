## 2. 항목별 확인과 판단

### 2.1 (12.4 ㄱ) `band_check/band_iv.py`·`band_cells.py` — 어느 것이 이 글의 근거인가

**피드백의 사실 주장 — 참(크기는 $10^{-16}$).** `band_iv.py`(기록 [r8a9b11e] `evidence/peer/band_iv.py`의 바이트 사본)는 `iv.dps = 30`으로 구간을 계산하지만 `mp.dps`는 기본값 15(53비트)로 두고, 구간 끝을 꺼내는 `lo(x)=mpf(x.a)`·`hi(x)=mpf(x.b)`에서 103비트 끝점을 53비트로 **최근접** 반올림한다. 또 셀 끝점 `la`·`lb`를 `mpf(1)/2+(mpf(2)/3-mpf(1)/2)*i/NSUB`로 53비트에서 만든다. `…_ZV8_bandiv.py`로 루프를 그대로 옮겨 변환마다 방향을 세었다(`…_ZV8_bandiv_out.txt`): 하계 변환 $97{,}753$회 가운데 $50{,}812$회가 위로(방향 깨짐), 상계 변환 $81{,}753$회 가운데 $38{,}777$회가 아래로; 변환 하나의 상대 변화 최대 $1.1\times10^{-16}$; 셀 끝점의 정확 유리수 대비 오차 최대 $1.2\times10^{-16}$(이웃 셀의 끝점은 같은 식으로 만들어 정확히 이어진다). 그러므로 「고정밀 구간 끝을 보통 mpf로 바꾸면서 최근접 반올림이 다시 일어나 방향이 보존되지 않는 부분이 있다」는 사실이다. 영향: `band_iv.py`의 최소 비 $1.3558739652027638$(셀 0)와 `band_cells.py`의 셀 0 하계 $1.3558739652027600$의 차는 $3.8\times10^{-15}$, 4000셀 전부의 셀별 하계 차 최대 $5.8\times10^{-15}$(셀 2475), 문턱 $1.3558$ 대비 여유는 $7.4\times10^{-5}$ — 깨진 방향의 크기는 여유보다 $10^{11}$배 작고 표시 자리(일곱 자리)에 닿지 않는다. 명제 band-inequality의 결론은 흔들리지 않는다(피드백도 같은 말).

**`band_cells.py`는 피드백의 말대로다.** 셀 끝점을 `Fraction`으로 두고 `iv.mpf(분자)/iv.mpf(분모)`로 넣으며, 하계·상계 인자의 끝을 `iv.mpf(x.a)`·`iv.mpf(x.b)`(iv 정밀도 그대로)로 꺼내 전체를 한 구간식으로 평가하므로 방향이 끝까지 보존된다. `band_read.py`는 셀이 $[\frac12,\frac23]$을 빈틈없이 덮는지·문턱 미만 셀 수·최솟값을 읽고 기록 코드의 출력과 여섯 자리에서 일치함을 본다(출력 그대로: 최솟값 $1.3558739652$, 여유 $7.4\times10^{-5}$). 한 가지 사실을 더 적어 둔다: `band_cells.py`도 표에 쓸 때 `str(mpf(r))`로 103비트 하계를 53비트 최근접으로 바꾸어 15자리로 적는다(상대 $\le1.1\times10^{-16}$). 이것은 계산이 아니라 표시 단계의 반올림이고, 판독이 비교하는 문턱 $1.3558$과의 거리 $7.4\times10^{-5}$가 이를 $10^{11}$배로 덮으며, 이 묶음의 다른 구간 계산도 결과를 같은 방식(유효 자리 최근접)으로 적는다. 코드의 계산은 바꾸지 않는다(아래 계획의 출력 한 줄 추가는 표시만 더하는 것이다).

**「구형 파일」은 자료 묶음에 들어 있다 — 그리고 들어 있어야 한다.** `band_iv.py`는 이 글의 코드의 폐기 판이 아니라 **기록의 증거 코드**다. 묶음에 두 번 있다: `원고_자료/r8a9b11e/band_iv.py`(4열 표 1207행; 기록 증거 파일의 사본)와 `원고_자료/세션_재계산/band_check/band_iv.py`(2열 표 259행; 이 글이 다시 돌린 사본, 출력 `band_iv_out_CE0.txt`). 1.5절은 부록 D 항목이 기록의 자료와 이 글의 자료를 함께 가리키게 정했으므로 기록 코드 사본은 남는 것이 맞다. 결정 117의 「폐기 판·옛 실행을 묶음에서 뺀다」는 이 글이 스스로 만든 코드의 옛 판에 대한 것이지 기록의 증거에 대한 것이 아니다.

**D.band-check가 지금 어떻게 적혀 있는가(부록D_장5B 38–66행).** 「알고리즘」: 「셀 끝점을 정확한 다정밀도 수로 두고 …」. 「산술 등급」: 「방향 반올림 구간(mpmath `iv`, 소수 30자리)」. 「결과」: 「최소 비 $1.355874$(첫 셀) … 계산값 $1.9570106\ldots$, $0.9885536\ldots$, $0.0071375\ldots$, $0.4999889\ldots$, $0.0168737\ldots$」 — 이 다섯은 `band_iv.py`가 찍은 최악 셀 값이고, `band_cells_CE0.tsv` 0행(`hov_lo` 1.95701061980505, `S_lo` 0.988553616941809, `top_hi` 0.00713754325874898, `K_lo` 0.499988944555238, `W_hi` 0.0168736730510511)과 표시 자리에서 전부 같다. 「독립 재계산」: 〔구현 같은 코드 재실행·같은 식의 새 구현; …〕 「이 글을 쓰며 기록의 `band_iv.py`를 … 실행해 최소 비 $1.355874$와 위의 최악 셀·다섯 계산값을 얻었다. 또 위 식에서 새로 쓴 구간 산술 코드(…)로 4000개 셀의 비를 모두 적고 … 최솟값이 첫 셀의 $1.3558740$(여유 $7.4\times10^{-5}$)임을 확인했다」. 「자료」: `band_iv.py`(기록 코드의 사본)가 앞, `band_cells.py`는 설명 없이 뒤. 곧 지금 항목은 **기록 코드의 재실행을 「결과」의 출처로 앞세우고 이 글의 새 구현을 「또 … 확인했다」의 보강으로** 적는다. README 591행 문단은 두 코드의 성격(바이트 사본 / 정확 유리수 끝점의 새 구현)을 이미 정확히 적고, README 14행 「처음 돌려 볼 것」과 `빠른_확인.py` 「띠-검사」는 `band_iv.py`를 돌린다.

**어긋남 둘(작지만 사실).** (1) 「알고리즘」의 「셀 끝점을 정확한 다정밀도 수로 두고」는 `band_cells.py`에만 맞다(정확한 **유리수**). `band_iv.py`의 끝점은 53비트 최근접 반올림($\le1.2\times10^{-16}$)이라 「정확한」이 아니다. (2) 「산술 등급 방향 반올림 구간」을 온전히 떠받치는 것은 `band_cells.py`다 — `band_iv.py`는 끝점 변환에서 절반쯤 방향이 깨진다. 「결과」가 `band_iv.py`의 출력을 출처로 적는 한 등급 서술과 출처 사이에 (수치로는 $10^{-16}$의) 틈이 있다. 11.2절 17행의 규칙(「이 글의 재계산이 있으면 그 재계산의 등급」)에 비추어도 이 글의 재계산인 `band_cells.py`가 근거여야 한다. 또 「결과」의 다섯째 계산값 「$0.0168737\ldots$」는 두 코드 모두 $0.01687367305\ldots$라 줄임표 앞을 반올림한 꼴이고(나머지 넷은 자른 꼴과 반올림이 같다), 자른 꼴로 맞추면 「$0.0168736\ldots$」다.

**분류·결정.** 사실·정합(서술의 출처와 등급의 정확성; 결론 무사) — **바꾼다(둘째 단계).** 피드백의 「대표 인증기 명시」 요구는 그 결과로 채워지되, 기록 코드의 결함을 적는 문장은 두지 않는다(결정 117 RD의 중립 열거 선례, 원칙 8). 이 글의 새 구현을 「결과」의 출처로 적고 기록 코드의 재실행을 같은 값을 주는 대조로 적으면 독자는 어느 파일이 근거이고 어느 파일이 대조인지를 바로 읽는다.

ZV4 때의 13번째 `rerun_exactgrid_1116.sh`는 지금 일치한다(band/bprime 재실행은 `rerun_exactgrid_1116_log.txt` 01:19 「done」으로 끝났고 그 폴더의 행은 모두 일치). 피드백의 수 1,622 = 464 + 1,158은 ZV4 시점의 두 표 행 수와 정확히 같으므로 외부 검토자는 두 표를 모두, 오늘 옛 판 폴더를 보관으로 옮긴 뒤·4열 표에 한 행이 더해지기 전의 판으로 보았다. 「12 불일치 + 1 없음」과 ZV4의 「13 불일치 + 0 없음」은 파일 하나의 상태가 다른데(그 순간 다시 쓰이던 파일로 보이나 목록이 없어 확정하지 못했다), 어느 쪽이든 돌고 있는 계산의 파일이다. 「불일치는 재계산 관련 파일에 집중되어 있고 계산 내용이 틀렸다는 뜻은 아니다」는 피드백의 판단은 맞다.

**「같은 시점」을 절차가 이미 보장하는가 — 반쯤.** `zenodo_v4/절차.md`의 차례는 재계산 완료(0·1) → D 항목·11.2 행 갱신 → 「README 파일 목록·재실행표·여유 JSON 갱신」(1) → 조립과 검사기·`자료묶음_v2.py`(2) → PDF(3) → 묶기 `--bundle --no-cache`·`--sums`(묶기 절)다. 4열 표는 `자료묶음_v2.py`가 통째로 다시 만들고(124행: 세션 파일은 4열에 넣지 않음), `SHA256SUMS.txt`는 묶음 파일 전체의 것이라 그 둘은 시점이 맞는다. 그러나 **2열 표(세션 재계산 464행)를 디스크와 통째로 맞추거나 확인하는 단계가 절차에 없다.** 2열 표는 `_patch_README_세션파일.py`가 인자로 받은 경로만 갱신하고(ZV1 5절 4항이 파일 이름을 손으로 열거함), 절차 1의 「README 파일 목록」은 4열 표다. 그러므로 「공개 판본에서 코드·출력·인증서·해시 목록을 같은 시점으로」라는 제안은 4열·SHA256SUMS에는 이미 절차가 있고 2열 표에는 **관문이 빠져 있다** — 바로 지금 보이는 12개 불일치가 그 표의 것이다. 덧붙여 ZV4가 적은 「표 밖 파일 758개」(2열·4열 어디에도 없는 `세션_재계산/` 파일; `c50_iv/` 빌드 산출물·탐침 덤프, `xcert_iv/_claims/` 146, `column_k500_iv/res/*.json` 380 등)도 그대로다 — 「파일마다 SHA-256」이라는 README·`판_설명.md`의 말이 실제가 되려면 묶기 제외 규칙과 2열 표의 범위를 세션이 정해야 한다(ZV4 4절의 제안 (ㄱ)(ㄴ); 내가 더할 것 없음).

**분류·결정.** 사실 확인(불일치는 돌고 있는 계산뿐) + 설계 제안(실익 있음: 배포 묶음의 재현성). README SHA 표는 **바꾸지 않는다**(재인증·모멘트 인증이 끝난 뒤 세션이 갱신; 지금 맞추면 쓰이는 중인 `cert/*.json`을 고정한다). 절차의 빈 관문은 **채운다(둘째 단계; 전→후 아래)** — 첫째 단계에서 관문 스크립트를 만들어 두었다. 「같은 시점」을 사람의 주의가 아니라 절차의 한 줄과 종료 코드로 보장하는 것이 원칙 10에 맞는다.

**전→후 계획(둘째 단계; `zenodo_v4/절차.md`).**
- 「올리기 전에 끝낼 것」 1항 끝 「→ README 파일 목록·재실행표·여유 JSON 갱신.」 → 「→ README 파일 목록·재실행표·여유 JSON 갱신; 세션 재계산 표(2열)는 바뀐 파일마다 `python -I scripts/_patch_README_세션파일.py <상대경로>`로 맞춘다(재인증 뒤의 목록은 `대조v2/수학검사2/검토_외부피드백_1116_ZV1.md` 5절 4항).」
- 2항 「조립(…) → `불변식_v2.py`·…·`자료묶음_v2.py`·KaTeX.」 → 「조립(…) → `불변식_v2.py`·…·`자료묶음_v2.py`·KaTeX → `python -I scripts/수학검사2/검토_외부피드백_1116_ZV8_sha_gate.py`(README의 두 SHA 표 전부가 디스크와 일치하고 빠진 경로가 없을 때만 0을 돌려준다; 0이 아니면 묶지 않는다).」
- 「묶기」 절 첫 문장 뒤에 「묶기 전에 위 관문이 0인지, 돌고 있는 계산 폴더(`.claim` 파일)가 없는지 본다.」를 더한다.
- 세션 판단으로 남기는 것: `_patch_README_세션파일.py`에 `--all`(표의 모든 행을 디스크의 현재 SHA로 갱신하고 없는 파일의 행을 알리는 모드)을 두면 ZV1 5절 4항의 손 열거가 필요 없어진다 — 세션 스크립트라 내가 고치지 않고 적어 둔다; 묶기 제외 규칙·2열 표 범위(ZV4 4절).
