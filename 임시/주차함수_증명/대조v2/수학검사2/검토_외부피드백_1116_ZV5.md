## 2. 항목별 확인과 판단

### 9.1 보조정리 old-8-34의 부호 분기 — 사실(이미 고쳐짐); 둔다

**사실 여부.** 피드백의 반례는 참이다(`…_ZV5_old834.py`): $k=6667$, $\nu=4622$에서 $\theta=(\nu-1)/(k-1)=0.6932193>\log2$라 $2e^{-\theta}<1$이고, $a=2(1+\frac1k)^{1-\nu}-1=8.3816\times10^{-5}>0$, $ab=4.1907\times10^{-5}<a$(피드백의 두 수와 자리까지 같다). 그러므로 옛 문장 「둘째 인자가 $1$ 이하라 곱은 첫째 인자 이상」은 $a>0$에서 거짓이었다.

**현행.** 10차 수리자 R10이 P10-2로 이미 고쳤다. 현행 장10.md의 † 문장은 「$2e^{-\theta}<1$이면 둘째 인자가 $(0,1]$에 있으므로, 첫째 인자 $2(1+\frac1k)^{1-\nu}-1$이 음일 때는 곱이 첫째 인자 이상이고 음이 아닐 때는 곱도 음이 아니어서, 곱은 $\min\bigl(2(1+\frac1k)^{1-\nu}-1,\,0\bigr)\ge2e^{-\theta}-1$ 이상이다」. 피드백이 제안한 꼴 $ab\ge\min(a,0)\ge q$와 내용이 같다(두 경우 나누기 + $\min$). 손으로 따라가면 $a\ge2e^{-\theta}-1$은 바로 앞의 $(1+\frac1k)^{1-\nu}\ge e^{-\theta}$에서, $0>2e^{-\theta}-1$은 경우의 가정에서 나오므로 $\min(a,0)\ge2e^{-\theta}-1$의 근거가 문장 안에 다 있다. 이어지는 「어느 쪽이든 $1-3\theta-\theta^2/2$ 이상」의 뒤 경우 근거 $g(\theta)=2e^{-\theta}-2+3\theta+\theta^2/2>0$($\theta>\log2$)도 맞다($g(\log2)=1.3197$, $g'=3+\theta-2e^{-\theta}>0$). 보조정리 범위 $k\ge3$, $103\le\nu\le k-1$의 격자 $57{,}374$점에서 $a\ge q$, $0<b\le1$, $ab\ge\min(a,0)\ge q$(또는 $2e^{-\theta}\ge1$이면 $ab\ge(2e^{-\theta}-1)e^{-\theta}$), $ab\ge1-3\theta-\theta^2/2$가 모두 성립했다(어긋남 $0$). 보조정리를 실제로 쓰는 가족 1a($\nu'=1.3k^{2/3}$)에서는 $\theta\le0.07$이라 이 분기에 들지 않는다는 피드백의 말도 맞다(R10도 같은 사실을 적었고, 그래서 범위를 좁히지 않고 증명을 메운 것이 옳다).

**분류·결정.** 진짜 오류였으나 이미 고쳐진 자리. **둔다**(바꿀 것 없음). 문장의 꼴(「곱은 $\min(\cdot)\ge\cdot$ 이상이다」)은 이 글의 다른 연쇄 부등식 서술과 같은 방식이라 손대지 않았다.

### 9.4 재실행 상태 표기와 출력 문자열 — 상태는 확인만; 빠른_확인은 수치 비교로 바꿈

**(가) D.central-gap-integer의 재실행 상태.** 피드백의 관찰은 사실이다. D 「독립 재계산」은 「같은 검토 코드를 $1001\le k\le10000$의 $9000$열 전부에 돌려 … 확인했다(작업자 4개, 150시간)」로 완료형이고, 첨부 폴더 `icert_py_full/`의 지금 스냅샷(03:47)은 `out_*.txt` 96개(8,627열)와 쓰는 중인 `.part` 셋(90열), `summary.json`은 100열 때의 것(`complete: false`), `launches.txt`는 11-15 21:00에 작업자 넷으로 재기동, `README_run.md`는 11-15 13:51에 8,227열에서 멈추고 남은 열을 세션의 빠른 구현(`scripts/_tmp_perf_1115/`)이 잠정 판정용으로 계산했음을 적는다. 배정 메모대로 값은 빠른 구현으로 끝낸 결과이고 원본은 대조용으로 계속 도는 사용자 사정이므로, 상태 표기와 「자료」 줄 정리는 계산 세션 몫이다(ZV3 4절도 같은 판단). 확인만 적고 손대지 않았다.

**(나) 빠른_확인.py의 「$2.437312\times10^{-4}$ 대 $2.437311\times10^{-4}$」.** 항목은 「Q_fin-두열」(D.Q-fin-1130; `qfin_iv.py 2001 3130 1129 0 q.jsonl`)이다. 이 기계에서 돌리면(14초) `3130 True 0.785457 2.437312e-04`로 기대 문자열과 같다. 저장 값은 `fl_margin_lo = 2.4373115579936908e-4`로, 일곱째 유효숫자의 반올림 경계($2.4373115$) 바로 위에 있어 상대 $2.4\times10^{-9}$만 작아져도 표시가 $2.437311$이 된다. 이 하계는 binary64 방향 반올림으로 만든 것이고 D.Q-fin-1130 「산술 등급」이 적듯 「합산 순서와 FMA 사용에 무관한 한계」로 바깥쪽으로 민 값이라, 환경(BLAS 합산 순서·FMA)에 따라 마지막 비트가 달라도 하계로서는 유효하다. 그러므로 피드백의 환경에서 나온 $2.437311$은 오류가 아니고, 문자열 완전 일치 검사가 제3자 재현에서 거짓 「불일치」를 낸다는 지적이 맞다. **결정.** 바꿈 — 실익이 분명하다(README가 `빠른_확인.py`의 목적을 재현 확인으로 적는다). `빠른_확인.py`에 항목별 `near` 필드(줄의 정규식, 기대값 목록, 상대 허용 오차)를 두고 `run()`이 그 줄을 찾아 수를 견주게 했으며, Q_fin-두열의 `expect`는 판정 문자열 `2001 True `·`3130 True `로, `near`는 두 하계(원천 쪽 로그 여유, 첫 층 쪽 여유)를 저장 값과 상대 $10^{-5}$ 안에서 견주도록 했다. 나머지 항목은 mpmath `iv`(정밀도 고정의 결정적 산술)나 정확 정수의 출력이라 문자열 일치가 환경에 흔들릴 이유가 없어 그대로 두었다(C 프로그램 항목 둘의 기대 문자열은 정수 개수다). 돌려 보니 Q_fin-두열 일치(9초). 머리 주석과 README.md 84행에 이 방식을 한 문장으로 적었다.

피드백 넷 가운데 9.1은 이미 R10이 고친 자리로 현행이 옳고 충분함을 반례·격자·부등식으로 확인해 두었다. 9.2는 (ㄱ) 귀속 어긋남이 참이고 부록 D 쪽이라 생성기가 지울 구간 안에 중간 서술을 넣어 사실대로 만들었고(정규식 검사로 자동 제거 확인), (ㄴ) 피드백의 공제 논증은 출발 상계($0.066$, $0.053$)가 $|w|\le0.1$에서 참이지만 이 글의 증거로 쓰지 않으며, 끝난 여덟 상자의 새·옛 여유 차가 $[1.6\times10^{-15},3.2\times10^{-11}]$(모두 양)이라 F6의 실제 영향은 $10^{-11}$ 규모임을 직접 쟀다. 9.3은 이 글에 $\pm10^{-35}$ 구간의 근거가 없었음을 확인하고(두 항목의 방향 반올림 구간 안에 `mp.zeta` 값이 숨어 있었음) 코드를 D.zeta-constants의 인증 구간으로 바꾸고 두 재계산을 다시 돌려 결과가 표시 자리까지 같음을 확인했으며 D 서술 두 곳을 맞췄다. 9.4는 중앙부 재실행 상태가 피드백대로 「설명 완료·스냅샷 진행 중」임을 확인만 적었고(계산 세션 몫), `빠른_확인.py`는 binary64 하계 항목 하나를 문자열 일치 대신 판정 + 상대 $10^{-5}$ 수치 비교로 바꿨다.
