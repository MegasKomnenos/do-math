### 영향
핵심 원인은 한 문장으로 이렇다. 1회 제한은 같은 수리를 두 번 판정하지 않으려고 둔 것인데, 판정 대상을 "같은 `repair_identity`를 가진 recovery 실행이 있는가"로만 정해서 수리 판정에 이르지 못한 호출까지 한 번으로 센다.

재현 경로는 두 갈래다.

- **공급자 한도.** Claude 프로필의 복구 호출이 `rate_limit_event`(`status=rejected`)로 끝나면 `ModelRunner.run`이 `error_kind=provider_limit`를 돌려준다. 610행은 이 결과를 `recovery_failed`로 분류하고, 실행은 같은 `repair_identity`로 종료된다. 다음 감독 점검에서는 500~505행이 이 실행을 찾아 `same failure and installation already attempted`를 반환한다. 공급자 한도가 풀려도, 설치 파일이나 실패 식별이 사람 손으로 바뀌기 전까지는 같은 반환이 반복된다.
- **HOLD·정지.** 복구 호출 도중 HOLD가 놓이면 `should_stop`이 호출을 멈추고 결과는 `recovery_held`가 된다. 사용자가 HOLD를 풀어도 같은 판정이 수리를 막는다. 모델 정책 위반으로 정지된 뒤 사용자가 그 정지를 해소한 경우도 같다.

막힌 동안 연구는 진행되지 않는다. 진단된 설치 결함이면 `pending_installation_repair`가 남아 있어 `scheduler._run_parallel`이 새 배정을 멈추고 대기한다. 실행기 시작 실패이면 `check()`가 `latest-engine.json`의 `engine_failed`를 보고 매번 복구로 갈 뿐 실행기를 다시 시작하지 않는다. 자동 복구가 막을 실패, 곧 이미 판정된 수리의 반복 호출은 수리 판정에 이르지 못한 호출에는 없다. 한도로 거절된 호출은 수리하지 않았고, HOLD·정지로 보류된 호출은 사용자가 끊은 것이다. 한도가 다시 열리는 것은 GLOSSARY가 재시도 근거로 드는 "확인된 환경 복구"이고, 정지를 푸는 것은 "명시적 결정"이다.

수리는 두 결과를 한 번에 세지 않는다. 이렇게 해도 1회 제한이 지키던 실익은 그대로 남는다. `recovery_failed`, `recovery_verification_failed`, `repaired`는 여전히 한 번으로 센다. 재시도의 속도는 새 장치 없이 기존 관문이 정한다. 공급자 게이트가 닫혀 있으면 `SessionSlots.acquire`가 `provider_limit` 대기를 돌려주므로 `recovery_waiting`으로 끝난다. HOLD·정지·종결은 `supervision_block`이 먼저 막는다. 610행에는 공급자 한도로 끝난 호출을 `recovery_provider_limited`로 구별하는 줄을 더한다. 이 값을 읽는 소비자는 셋이고, 모두 자유 문자열로 받는다. 활동 대기의 `reason`, 진단 기록의 `result.installation_repair.status`, 보고의 `outcome`이다. `report["outcome"]`을 값과 비교하는 곳은 `== "repaired"` 한 곳뿐이다(672행). `result_disposition`의 스키마는 `{"type": ["string", "object", "null"]}`(`record_schemas/schemas.py` 279행)이다. 엔진의 회수 경로는 이 필드에 문자열을 쓸 수 있으므로 판정 함수는 dict인지 확인한 뒤 읽는다.

### 영향
핵심 원인은 이렇다. 계약 문서가 복구의 실패 처리를 경로마다 구별하지 않고 하나로 적었다. 그래서 문서가 약속한 lock 조건과 기록 보존이 코드에 없다.

어긋나는 곳은 두 군데다.

- **56행**은 "검사를 통과하고 로컬 실행 종료를 확인한 뒤에만 두 lock을 해제한다"고 적는다. 코드는 결과와 관계없이 두 lock을 해제한다. 설치 유지보수 lock은 `finally: maintenance.close()`(668~669행)가, writer lock은 `with repo.writer_lock()`의 종료가 푼다. 검사가 실패한 `recovery_verification_failed`와 종료를 확인하지 못한 `recovery_termination_unknown`에서도 마찬가지다. 검사 통과와 종료 확인이 실제로 거는 조건은 재시작 요청 하나다. 재시작은 `report["outcome"] == "repaired"`일 때만 요청한다(672~676행). `repaired`는 `probe_cli` 통과 없이는 `recovery_verification_failed`로 바뀌고(627~628행), 종료 확인 없이는 `recovery_termination_unknown`으로 바뀐다(643~644행).
- **58행**은 입력 한도 초과와 능력·자원·종료 확인 부족에서도 "활동을 `waiting`으로 남기고 정확한 이유와 다음 소유자를 보존한다"고 적는다. 코드에서 이런 모델 호출 전 관문은 저장 없이 `recovery_waiting`과 이유를 반환한다. 해당 관문은 485·491·505·524·566·577행이다. 566·577행의 경우 메모리에서 열거나 재개한 활동도 저장하지 않고 버린다. 능력 증거는 저장할 수 있다(520행). `waiting` 활동과 `recovery` 다음 소유자가 남는 것은 모델을 부른 뒤 실패한 경우뿐이다(653~655행). 호출 뒤 종료를 확인하지 못하면 활동은 대기로 옮기지 않고, 실행을 `stopping`에 두어 자원과 산출을 보존한다(`release_or_hold`).

이 문서를 읽는 사람은 운영자와 운영 AI다. 이들은 연구가 멈춘 이유를 상태의 대기 활동에서 찾으려 하지만, 관문 거절은 거기 없다. 감독 예약 작업의 표준 출력은 남지 않으므로, 이유는 `operator check` 반환에서만 볼 수 있다. 또 운영자는 lock이 검사 실패 때 잡혀 있다고 오해할 수 있다.

수리는 문서를 코드에 맞춘다. 코드의 동작은 바꾸지 않는다. 관문 거절은 모델을 부르지 않고 다음 점검마다 같은 관문을 다시 확인하므로, 기록이 없어도 복구 경로는 막히지 않는다. 이 문단을 인용하는 다른 문서는 없다(grep `recovery_waiting`, `두 lock`).

재현 경로는 다음과 같다.

1. 연구 수행이 `control_self_check`로 응답을 보낸다. 이 응답은 규칙 적용 범위가 어긋났거나(`rule_coverage_mismatch`), 인용할 수 없는 참조를 썼거나(`evidence_not_current`), 필수 증거가 빠진(`required_evidence_missing`) 응답이다.

3. `_control_receipt_response`(1288행)는 영수증에 `reason`이 없으므로 고정 문구 "self-check response was preserved and returned for correction"을 돌려준다.

```
형식 검사를 통과해 접수된 응답도 중앙 검사에서 반려될 수 있다. 반려되면 영수증의 `state`는 `rejected`이고, `reason`에 실제 오류 코드가 실린다. 예를 들어 `rule_coverage_mismatch`는 도래한 규칙을 빠짐없이 한 번씩 다루지 않았다는 뜻이고, `evidence_not_current`는 이번 실행에서 인용할 수 없는 참조를 썼다는 뜻이다. 같은 오류는 `.control/observation-feedback.json`에도 오며, 반려는 운영 점검으로 이어진다. `response_deadline_passed`나 `research_action_before_response`처럼 이미 지난 사실이 원인이면 그 의무에 대한 응답은 더 받지 않는다. 그 밖의 오류는 고쳐서 다시 보낼 수 있다. `control_self_check`는 의무마다 같은 요청 ID(`self-check-<의무 ID>`)로 제출하므로, 같은 의무에 두 번째 응답을 보낼 수 없다. 고친 응답은 `control_submit`에 새 고유 `request_id`를 주어 보낸다.
```

### 영향
새 인스턴스에서 연구 수행 AI가 「결과 A가 추측 B를 지지한다」를 `supports` 관계로 남기려 한다고 하자. 그 AI는 다음 경로를 모두 거쳐야 한다.

1. 어떤 실행이 확장 `kind_definitions`로 `supports` 정의를 제안한다(`engine._apply_extensions` → `_propose_kind`). 같은 응답에 그 관계를 함께 쓰면 거부된다. 제출 검사는 활성 정의만 담은 `relation-state.json`으로 관계를 검사하고(`submission.py` 992-1007행), 적용 `import_relation`도 활성 정의만 받기 때문이다.

3. 그 뒤의 다른 실행이 비로소 관계를 제출한다.

수학 관계는 경로가 더 길다. 증명을 제출하는 실행이 `relation_claim`을 붙이려면 그 종류가 이미 활성이어야 한다(`submission.py` 881행, `knowledge_io.py` 286행). 그래서 형식 검사와 동일성 검토의 긴 경로 앞에 종류 활성화의 한 순환이 더 붙는다.

이 절차가 막는 실패를 찾아보면 다음과 같다. 새 토큰이면 의미가 모호하거나 권한을 넘는 종류가 쓰이는 실패를 막는다. 그러나 설치 틀의 뜻과 제약은 설치본이 정했다. 저장 관문은 이미 내장 정의가 설치본과 다르면 거부한다(`record_schemas/__init__.py` 566-568행). 독립 검사는 설치본이 이미 확정한 문면을 인스턴스마다 다시 읽을 뿐이다. 같은 성격의 지식 종류 10개는 이 검사 없이 설치 때 활성이다(`engine.py` 171행). 수학 관계의 근거 요구, 곧 형식 결과와 현재 동일성 판정은 종류가 활성인지와 무관하게 `validate_relation`이 집행한다(`knowledge_io.py` 348-376행).

반면 비용은 이렇다. 인스턴스마다, 관계 종류마다 제안 실행 하나와 유지보수 실행 하나가 든다. 사용자는 종류 정의마다의 유지보수에 동시 실행 상한을 두지 않기로 했다(`기억/layer1/M-0349.md` 18행). 이 결정은 이 경로가 실제로 쓰인다는 전제의 결정이다. 관계를 처음 쓰려는 실행은 한 순환을 기다리고, 그 사이 발견한 연결은 관계가 아닌 산문에만 남는다. 이 설계를 정한 것은 GLOSSARY의 문면뿐이다. 사용자 확정 기록은 찾지 못했다(아래 「읽은 범위」). 설계를 바꾸면 이 정본 문면도 바뀌므로 상신으로 올린다.

#### 세계 물음

연구 계획은 착수 가능한 과제 가운데 이번에 수행할 것을 고르고, 고른 과제에 어느 급의 모델이 필요한지를 현재 근거로 다시 본다. 이전 실패가 과제를 더 어렵게 보이게 했으면 등급을 올리고, 그렇지 않으면 계약 검토를 거친 평가를 그대로 쓴다. 이 행위에 필요한 개체는 정의 파일에 모두 있다. 과제 기록의 `model_assessment`(후보 준비가 저작하고 계약 검토가 대조), 계획 입력 `tasks` 행의 평가 필드(`references/공통-실행.md` 39행), 선택 요청의 `model_assessment`(계획이 갱신할 때만), 그리고 요청에 평가가 없을 때 과제 평가로 되돌아가는 `selection`이다. 없는 것은 "계획이 바꾸려는 과제만 평가를 낸다"는 허용뿐이다.

#### 선택지

- A. 유지: 선택 과제 전건에 평가를 요구한다. 하류 영향은 없다. 비용(되풀이 저작, 누락 반려, 자기 대조 절차)이 계속된다.
- B. 갱신만 제출: 계획은 등급을 바꾸는 선택 과제에만 평가를 적는다. 검사는 중복과 선택 밖 대상만 반려하고 누락은 허용한다. 평가가 없는 선택은 과제의 보존된 평가로 배정된다(현행 `selection` 그대로). 고칠 곳은 `validate_assessments`의 연구 계획 분기, `계약/연구-계획.md` 85행, `references/모델과-실행예산.md` 31·49행, `references/공통-실행.md` 325행, 연구 계획의 평가 전건을 단언하는 시험이다. 후보 준비의 후보별 정확히 하나 규칙과 평가 보충의 전건 처분은 그대로 둔다.
- C. 계획의 평가 제거: 계획은 평가를 내지 않고, 등급을 바꿔야 하면 `revision_requests`로 후보 준비에 평가 개정을 요청한다. 하류 영향은 크다. 등급 변경마다 준비 실행과 새 계약 검토가 필요하고, 그동안 과제가 대기한다.

#### 변형 물음

A의 대가는 되풀이 저작과 누락 반려다. 입력에 현재 평가를 싣고 "유지"를 한 단어로 표시하게 하는 변형도 있지만, 전건 표시 의무와 누락 반려는 그대로 남아 대가가 줄지 않는다. C의 대가는 등급 갱신의 지연이다. 계획이 평가를 직접 갱신할 수 있게 두면 이 대가가 사라지는데, 그것이 곧 B다.

#### 추천

B를 추천한다. 승인 뒤의 최종 상태를 비교하면, B에서는 계획자가 판단이 필요한 과제에만 평가를 쓰고 누락으로 계획 전체가 반려되는 일이 사라진다. 배정 등급은 B에서도 늘 근거 있는 평가(계약 검토를 거친 과제 평가 또는 계획의 갱신)에서 나온다. 후보 준비의 후보별 전건 대조, 곧 M-0299에서 사용자가 우선시한 문언은 그대로 남는다. A는 막는 실패를 댈 수 없는 대조를 유지하고, C는 같은 실익을 더 비싼 경로로 얻는다.

### 영향
핵심 원인은 두 가지다. 첫째, 실행 중 규칙 교체의 유일한 경로가 자기 점검 응답의 `rule_proposal`로 옮겨 간 뒤에도 옛 경로인 작업 공간 파일 `observation-rules.json`을 감시하고 검사하는 장치가 남아 있다. 이 장치는 어떤 규칙도 바꾸지 못하면서 반려 알림과 제출 반려를 만든다. 둘째, `observations`는 작업 공간 경로 규칙의 정본인 `context_store.safe_path`를 import하고도, 자기가 직접 여는 관리 파일에는 약한 경계 사본을 쓴다.

첫째 원인에 동결문의 네 물음을 적용한 결과는 다음과 같다.

1. 막는 실패. `_rule_file_events`는 파일 형식이 맞아도 `raise ValueError("rule replacement requires rule_proposal in a valid self-check response")`로 끝나므로(사본 839행), 언제나 `observation_rules_rejected`만 낸다. 실제 교체는 `record_self_check_response`에서 `_replace_rules`로 가는 경로뿐이다. 제출 검사(`submission.py` 1143~1158행)도 파일의 모양만 볼 뿐, 그 내용을 쓰는 소비자에게 넘기지 않는다. 그러니 이 장치가 막는다고 볼 만한 것은 "파일을 쓰면 규칙이 바뀐다"는 작업자의 오해 하나뿐이다. 그런데 그 오해는 장치 쪽이 만든다. `engine.py` 3530행은 "live rules belong in observation-rules.json"이라고 안내하고, `공통-실행.md` 193행과 `CLI-실행-계약.md` 821~823행은 이 파일을 교체 제안 파일로 소개하며 전용 크기 한도까지 준다.
2. 실제로 막는가. 막을 실패가 없으므로 이 물음은 성립하지 않는다.
3. 치르는 비용. 첫째 비용은 정당한 제출의 반려다. `_workspace_checks`는 모든 제출 모드에서 불리므로, 효력 없는 이 파일의 모양 하나가 틀려도 규칙과 무관한 역할의 주 응답까지 반려되고 출력 수리 횟수가 쓰인다. `test_submission_tools.py` 401~410행이 바로 이 반려를 단언한다. 둘째 비용은 관찰 쪽에서 난다. 매 평가 tick마다 추적기가 파일의 존재와 지문을 확인하고, 내용이 바뀔 때마다 반려 알림을 보낸다(1004행). 셋째 비용은 유지다. 추적기 상태 둘, 전용 한도 상수, 문서 네 곳, 시험 여섯 곳이 이 경로만을 위해 있다.
4. 영향으로 같은 실익을 얻는가. `계약/연구-수행.md` 74행은 이미 "이 응답이 현재 실행의 규칙을 바꾸는 유일한 경로다"라고 적는다. 교체 결과는 응답 수신 기록의 `rule_update`로 작업자에게 돌아간다. 문서가 교체 경로를 `rule_proposal` 하나로만 안내하고 엔진 문구가 그 경로를 가리키면, 오해가 생길 경로 자체가 없어진다.

그래서 이 장치는 조정하지 않고 걷어 낸다. 걷어 내는 것은 실시간 파일 감시(`_rule_file_events`, 그 상태 필드 둘, 호출 한 줄), 제출 검사 블록, 크기 한도(`RULES_MAX_BYTES`, `limits.observation_rules_bytes`), 문서의 파일 서술이다. 엔진의 잘못된 안내는 실제 경로를 가리키도록 고친다. 응답 경로의 `rule_proposal`과 그 검사(`validate_rule_proposal`, `validate_execution_rules`, 16개 한도)는 그대로 둔다.

둘째 원인(경계 사본)은 `read_checkpoint` 417~419행과 `_rule_file_events` 826~827행 두 곳에 있다. 사본은 파일 자체가 심볼릭 링크인지와 해석 경로가 작업 공간 안인지만 본다. 반면 정본 `safe_path`는 `no_reparse`로 경로 성분마다 심볼릭 링크와 재분석 지점을 거부한다(`context_store.py` 45~55행, `file_io.py` 360행). 그래서 심볼릭 링크가 아닌 재분석 지점으로 만든 `checkpoint.json`은 사본을 통과하지만, 같은 작업 공간의 다른 파일은 모두 정본에서 거부된다. 이음새 정본 154행은 `observations`가 이 규칙을 정본으로 쓴다고 적는다. 두 사본 가운데 826~827행은 `_rule_file_events`와 함께 지워지므로, 남는 `read_checkpoint`만 정본 호출로 바꾼다. 경계 위반은 지금처럼 `try` 안에서 `ValueError`가 되어 `invalid` 행을 만들며, 반환 모양은 바뀌지 않는다.

수리 뒤 각 소비자의 동작은 다음과 같다.

- 작업 공간에 규칙 파일이 있어도 관찰은 아무 사건을 내지 않는다.
- 제출은 그 파일을 이유로 반려되지 않는다. 파일은 수집되는 일반 산출일 뿐이다.

- 관찰 사실과 자기 점검 응답의 저장 모양은 바뀌지 않는다. 추적기 상태도 저장되지 않으므로 `STATE_CONTRACT_ID`는 올리지 않는다.

```
    def _rule_file_events(self) -> list[dict]:
        path = self.workspace / "observation-rules.json"
        if not path.exists(): return []
        try:
            if path.is_symlink() or not path.resolve().is_relative_to(self.workspace.resolve()):
                raise ValueError("observation rules must stay in workspace")
            # A settled, unchanged fingerprint names the bytes this tracker already judged.
            mark = file_fingerprint(path)
            if mark == self.rule_file_mark: return []
            raw = read_bytes_shared(path)
            digest = hashlib.sha256(raw).hexdigest()
            self.rule_file_mark = mark if fingerprint_settled(mark) and file_fingerprint(path) == mark else None
            if digest == self.rule_proposal_digest: return []
            self.rule_proposal_digest = digest

            proposal = strict_json_loads(raw.decode("utf-8-sig"))
            validate_rule_proposal(proposal, current_revision=self.rule_revision)
            raise ValueError("rule replacement requires rule_proposal in a valid self-check response")
        except (ValueError, TypeError, OSError, UnicodeError, json.JSONDecodeError) as error:
```
