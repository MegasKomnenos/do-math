# 사용자 결정 세 건의 구현 보고

파견문 `임시/do-math_검증_20260928/직접처리/사용자결정_파견.md`의 세 결정(R1-39 B, R2-31 B, R2-40 B)을 main 작업 트리의 `.claude/skills/do-math/`에 구현했다. 세 건 모두 **반영**이다. 인계 확인 층의 시험은 두 묶음으로 돌렸다. 세 결정이 고친 성질의 시험은 모두 통과했다. 실패는 한 건이며, 이번 작업 전부터 트리에 있던 미커밋 변경과 시험 사이의 불일치다(「공통: 시험 실행과 남은 실패」 절). 커밋, 브랜치, stash, worktree는 만들지 않았고 모델 CLI도 호출하지 않았다.

## 결정 1. R1-39 B: 계약 자기점검(`contract_checks`)의 정리

**처분: 반영**

### 택한 구현 방식과 이유

제안서의 선택지 B를 그대로 구현했다. 파견문의 지시대로 `contract_check_errors`의 규칙을 원문에서 다시 확인해, 실제 상태에 닿는 규칙과 선언끼리나 글자만 대조하는 규칙을 갈랐다.

| 규칙 | 대조하는 것 | 처분 |
|---|---|---|
| `cited_record` | 문면에 인용한 `TK-`·`KN-` ID와 입력·`record_index` | 남김. 상태에 닿는다 |
| `sibling_boundary` | 형제 경계 선언의 중복, 인용했는데 선언하지 않은 형제, 입력에 없는 과제 | 남김. 세 하위 검사 가운데 "입력에 없는 과제"는 상태에 닿는다. 나머지 둘(중복·미선언)은 아래 두 규칙이 빠짐없이 돌게 하는 전제다. 미선언을 허용하면 인용한 형제의 판본·개정 검사를 선언 생략으로 피할 수 있다 |
| `sibling_revision` | 선언한 `revision`과 형제의 현행 판본 | 남김. 상태에 닿는다 |
| `sibling_under_revision` | 형제의 `revision_requested`·`pending_revisions`와 의존 여부 | 남김. 상태에 닿는다 |
| `coverage` | 후보마다 항목 하나 | 남김. 위 검사들은 항목을 순회하므로(`submission.py`의 `for index, entry in enumerate(entries)`), 항목이 없는 후보는 인용 기록·형제 검사를 받지 않는다. `coverage`가 그 덮개다 |
| `symbol_meaning` | 선언끼리(같은 기호의 두 선언) | 삭제 |
| `symbol_absent` | 선언한 기호 문자열이 문면의 부분 문자열인지 | 삭제 |
| `outcome_branches` | 서로 다른 갈래 문자열 둘 이상 | 삭제 |
| `dependency_outcomes` | 의존 과제 ID·제목이 갈래 문자열에 나오는지 | 삭제 |

`symbols`·`outcome_branches` 필드는 확장 스키마에서 지웠다. 기호와 결과 갈래의 점검은 후보 준비 계약 5절의 1·2단계, 곧 판단 지도로 남겼다. 이것이 M-0321 43행이 효과를 관찰한 형태다. 기계 검사라는 틀(M-0321 10행)은 유지된다.

검토했으나 택하지 않은 방안이 있다. 인용이 없는 후보는 항목을 생략해도 되게 하고 검사를 후보 단위로 도는 방식이다. 인용 기록 검사는 선언에 의존하지 않으므로 이 방식도 같은 실익을 지킨다. 그러나 사용자가 승인한 B는 `task_title`과 `coverage`를 남기는 설계이다. 그리고 빈 항목 `{task_title, sibling_boundaries: []}` 하나의 비용은 작다. 그래서 결정의 범위를 넓히지 않았다.

독립 독해에서 나온 지적 하나를 반영했다. 규칙 표에서 `sibling_under_revision`의 문제 칸을 코드의 실제 발동 조건으로 정확히 썼다. 조건은 인용 과제가 개정 중이고, 그 경계 선언의 `independent_of_next_revision`이 `false`이며, 그 과제가 의존 과제에도 없는 경우다.

## 결정 2. R2-31 B: 설치된 관계 종류의 활성 설치

**처분: 반영**

### 택한 구현 방식과 이유

`knowledge_io.ensure_ontology`가 지식 종류 10개와 관계 종류 18개를 모두 활성 내장 정의로 설치한다. ID는 기존 규칙 그대로 `BUILTIN_DEFINITIONS`의 순번에서 만든다(`KD-` + 26자리). 지식 종류의 ID(1~10)는 바뀌지 않고, 관계 종류는 11~28을 받는다. 비활성 틀 함수 `relation_templates`와 역할 입력 키 `relation_templates`(`engine.py`)는 소비자가 없어져 지웠다.

제안서가 적은 "같은 토큰의 현재 정의가 있으면 그 토큰의 설치를 건너뛴다"는 보호는 넣지 않았다. 원문으로 확인한 이유는 셋이다.

- 인스턴스는 초기화 때(`engine.py` 172행) 모든 내장 정의를 받는다.
- 내장 정의가 현재인 동안 같은 토큰의 등록은 `register_kind_definition`이 "kind token is already defined"로 거부한다.
- 내장 정의를 철회한 뒤 새 토큰을 등록해도, 철회된 내장 기록은 고정 ID로 남는다. `setdefault`는 그 기록을 다시 설치하지 않는다.

따라서 같은 토큰의 비내장 현재 정의와 설치되지 않은 내장 정의가 함께 있는 상태는, 이 변경 이전에 만든 상태에서만 생긴다. 옛 판본 호환 경로는 두지 않는다는 사용자 확정 기록에 따라 보호 분기를 만들지 않았다.

### 고친 파일

- 코드: `scripts/do_math/knowledge_io.py`(`ensure_ontology`, `relation_templates` 삭제), `scripts/do_math/engine.py`(입력 키 `relation_templates` 삭제)
- 문서: `GLOSSARY.md` 257행, `references/공통-실행.md` 331행, `references/지식-저작과-재사용.md` 27·97행, `references/CLI-실행-계약.md` 541행(설치된 토큰은 다시 등록하지 않는다)
- 시험·픽스처: `test_knowledge.py`, `test_knowledge_io.py`, `knowledge_fixtures.py`(`activate_kind` 삭제), `engine_fixtures.py`(`start_query_repository`의 종류 등록·검사·승인 artifact 삭제), `test_family_records.py`, `test_planning.py`, `test_role_input.py`, `test_design_walkthroughs.py`(`activate_relation` 삭제). 이 픽스처들은 설치 틀을 등록·검사·활성화해 쓰고 있었다. 이제는 이미 활성인 설치 정의를 그대로 쓴다.

`계약/유지보수.md` 「종류 정의 검사」 절은 "새 지식·관계 종류"의 검사를 다루므로 그대로 맞다.

### 보존한 보증과 근거

- 새 관계 종류(설치본에 없는 토큰)는 지금처럼 제안, 독립 검사, 활성화를 거친다. `test_knowledge_io.KnowledgeIoTests.test_catalog_exposes_only_active_definitions`가 이를 고정한다. 새 토큰 `translates_to`는 등록 뒤와 검사 뒤에도 catalog에 없고, 활성화 뒤에만 들어가며, 철회하면 빠진다. `test_kind_registration_requires_explicit_check_and_activation`도 통과한다. 엔진 경로(`_propose_kind` → 유지보수 `kind_definition_check` → `_apply_kind_definition_check`)와 제출 검사(`submission.py`의 `register_kind_definition` 사전 검사)는 바꾸지 않았다.
- 수학 관계의 근거 요구는 활성 여부와 무관하게 집행된다. 새 시험 `test_installed_relation_kinds_are_usable_without_activation`이 이를 고정한다. 설치 직후의 `formally_implies`는 `formal_result_refs_required`와 `assessment_refs_required`로 거부된다. 기존 시험 `test_mathematical_relation_requires_exact_formal_identity_and_current_endpoints`, `test_mathematical_relation_requires_match_in_addition_to_active_use`, `test_research_analogy_is_distinct_from_mathematical_connection`도 통과한다. 이 셋은 이제 등록 절차 없이 설치된 정의를 쓴다. 원문 근거는 `validate_relation`이 정의의 `constraints`로 요구를 집행한다는 점이다. 내장 수학 종류의 제약이 설치본과 다르면 저장 관문이 거부한다(`record_schemas/__init__.py`의 "builtin kind differs from installed definition"과 "mathematical relation kind cannot waive formal evidence").
- 저장 관문의 내장 정의 대조는 관계 내장 정의에도 그대로 적용된다(`test_family_records`의 `test_relation_schema_and_domain_kind_evidence_are_both_enforced`는 이제 설치된 `supports`로 `evidence_required`를 확인한다).

### 더한 시험과 수리 전 실패 관찰

- 새 시험 `test_knowledge.KnowledgeRecordTests.test_installed_relation_kinds_are_active_from_installation`: 옛 `test_relation_templates_are_not_active_instance_definitions`를 대체한다. 설치 직후 catalog의 관계 토큰이 내장 18개와 같고, 모두 `active`·`builtin`이며, 설치된 토큰의 재등록은 "already defined"로 거부됨을 고정한다.

- 수리 전 관찰: `python scripts/run_tests.py test_knowledge.KnowledgeRecordTests.test_installed_relation_kinds_are_active_from_installation test_knowledge_io`를 돌렸다. 세 시험이 옳은 이유로 실패했다. 첫째는 catalog의 관계 목록이 비어 "Items in the second set but not the first"가 났고, 둘째는 `Lists differ: [] != ['analogous_to', ...]`, 셋째는 `supports` 관계가 무효라 "False is not true"였다. 수리 뒤 `test_knowledge`·`test_knowledge_io` 69건이 통과했다.

### 저장 계약 식별자 판단

올리지 않는다. `kind_definitions` 기록의 모양은 그대로이고, 같은 모양의 내장 기록이 18개 늘 뿐이다. 저장 검증기는 내장 정의를 `BUILTIN_DEFINITIONS`와 대조하는데, 관계 내장 정의도 그 목록에 이미 있다. 제안서의 판단(계약 식별자 유지)과 같다.

## 결정 3. R2-40 B: 연구 계획의 모델 평가

**처분: 반영**

### 택한 구현 방식과 이유

공유 검사 함수 `model_policy.validate_assessments`에 입력 과제 `tasks`를 인자로 더했다. 연구 계획 분기는 두 집합을 나눈다.

- 허용 대상: 이번 계획의 선택 과제 전부.
- 필수 대상: 선택 과제 가운데 입력 과제에 저장된 `model_assessment`가 없는 과제.

누락은 필수 대상에서만 반려하고, 대상 밖은 허용 대상 밖에서만 반려한다. 중복 반려는 그대로다. 후보 준비의 두 분기(일반 후보 전건, 평가 보충의 지정 과제 전건)는 필수 대상과 허용 대상이 같아 기존 동작 그대로다.

이 함수를 부르는 곳은 둘이며, 둘 다 새 인자를 넘긴다. 생산자의 로컬 검사와 중앙 수신은 `submission.py`의 `payload_issues`를 거치며 계획 검사기 문맥의 `tasks`를 넘긴다. 적용은 `planning_engine._apply_model_metadata`에서 `runtime["tasks"]`를 넘긴다. 평가를 내지 않은 선택 과제는 요청에 평가가 결합되지 않는다(`decision_engine.py`의 `model_decisions` 조회). 배정기 `model_policy.selection`은 과제 기록의 `model_assessment`로 되돌아간다. 이 경로는 바꾸지 않았다.

파견문은 저장된 평가가 없는 선택 과제가 생길 수 있는지 원문으로 확인하라고 했다. 확인 결과는 다음과 같다.

- 과제 기록을 만드는 곳은 세 곳이다. `engine.py` 3688행(후보 준비의 후보, 후보마다 평가 필수), `academic_engine.py` 113행(학술 과제, 평가 없이 생성), `planning_engine.py` 125행(반려된 학술 과제의 평가 제거)이다. 뒤의 두 경우는 `_ensure_model_assessments`가 평가 보충을 요청하고, 대기 중인 계약 검토를 큐에서 뺀다. 수명 관리도 그 과제를 착수 불가로 기록한다(`lifecycle_engine.py`의 "model assessment or observation rules required before contract review"). 평가는 계약 해시에 들어가므로(`planning.CONTRACT_FIELDS`) 승인된 계약 검토도 평가를 덮는다.
- 그러나 계획의 착수 가능 모집단은 `planning.task_ready`로 직접 계산되고(`engine.py`의 `context["task_readiness"]`), `task_ready`는 `model_assessment`의 유무를 보지 않는다. 그래서 평가 없는 과제가 모집단에 들지 않는다는 보증은 다른 경로들의 순서에 기댄다.

이 때문에 "그런 과제가 생기지 않는다"를 전제하지 않았다. 대신 "저장된 평가가 없는 선택 과제는 계획이 반드시 평가한다"를 검사의 일반 규칙으로 두었다. 이 규칙이 M-0299 22·24행의 목적, 곧 평가 없이 배정되는 과제가 없게 하는 목적을 어느 경로에서든 지킨다.

### 보존한 보증과 근거

- 후보 준비의 "후보마다 평가 정확히 하나"와 그 생산자·수신자 공유 검사는 그대로다. `test_model_assessment_flow.AssessmentSubmissionTests`의 누락·중복·대상 밖·개정 후보·평가 보충 시험이 모두 통과했다. 검사 함수도 여전히 하나이며 두 쪽에서 실행된다.
- 평가 없이 배정되는 과제가 없다: 새 시험이 저장된 평가가 없는 선택 과제의 누락을 반려함을 고정한다. 저장된 평가가 있는 과제는 계약 검토를 거친 그 평가로 배정됨도 고정한다(아래 두 시험).
- 기존 `test_plan_receiver_records_model_decisions_without_changing_the_authored_dispositions`도 그대로 통과한다. 이 시험의 선택 과제는 저장된 평가가 없어 누락 반려가 유지된다.

### 더한 시험과 수리 전 실패 관찰

- 새 시험 `test_model_metadata_boundary.ModelMetadataBoundaryTests.test_plan_rates_a_selected_task_only_to_change_or_supply_its_stored_assessment`: 적용 경로에서 다음을 단언한다. 저장된 평가가 있는 선택 과제는 평가 없이 통과하고, 새 평가로 바꿀 수 있다. 저장된 평가가 없는 선택 과제의 누락은 `missing`으로 반려된다. 선택하지 않은 과제의 평가는 `unexpected`, 같은 과제의 두 평가는 `duplicate`로 반려된다.
- 새 시험 `test_session_scheduler.ParallelEngineTests.test_selected_task_without_a_plan_assessment_runs_at_its_reviewed_assessment`: 계획이 어떤 선택 과제도 평가하지 않는 엔진 구간을 돈다. 접수, 계획 적용, 배정을 모두 지나며, 계획의 `model_decisions`가 `{}`이고 첫 연구 수행이 과제에 저장된 평가의 등급(`MODELS["low"]`)과 그 평가로 배정됨을 단언한다. 공유 템플릿을 뺀 단독 시간이 약 14초로 10초 목표를 넘어, 시험 지침 4절 규칙 8에 따라 docstring에 이유를 적었다.
- 수리 전 관찰: 두 시험이 옳은 이유로 실패했다. 첫째는 `ValueError: model assessment coverage: {"missing": ["TK-kept"], "unexpected": []}`, 둘째는 계획이 접수되지 않아 `model_decisions`가 없었다(`None != {}`). 수리 뒤 둘 다 통과했다.

## 공통: 시험 실행과 남은 실패

모든 명령은 `.claude/skills/do-math/scripts`에서 실행했고, 한 번에 하나만 돌렸다. 반환 전에 백그라운드 실행은 모두 끝났다.

## 공통: 문서 독해 확인

`write-for-reader`의 독해 절차는 `writing_flow.py read`로 `codex exec`를 호출한다. 파견문의 모델 CLI 금지에 걸리므로 그 명령은 쓰지 않았다. 대신 작성 맥락이 없는 서브에이전트(gp-sonnet-medium) 하나를 독해자로 썼다. 독해자에게는 원고(후보 준비 계약 4절의 논리 실패 질문과 5절 전체, 연구 계획 계약 85행)와 독자 정보만 주었다.

독해자는 세 사용 상황을 모두 합의대로 읽었다. 인용 없는 후보의 빈 항목, 개정 중 형제의 두 처리 방법, 다섯 검사 규칙과 기계 검사의 한계, 보충 실행 제외, 계획 평가의 세 경우다. 지적 셋은 다음과 같이 처분했다.

- `sibling_under_revision`의 발동 조건이 불명확하다는 지적: 반영했다. 규칙 표의 문제 칸을 코드 조건으로 고쳤다.
- 3단계의 "다시 쓰고"가 모호하다는 지적: 이번에 바꾸지 않은 옛 문면이고 결정 범위 밖이다. 독해자도 바로 뒤 예시로 뜻을 확정했으므로 유지했다.
- 계획의 "저장된 평가"가 어느 시점의 값인지 묻는 지적: 같은 문단이 "계약 검토를 거친 난이도·중요도 평가"로 정의하므로 유지했다.

규칙 표를 고친 뒤 재독해는 하지 않았다.
