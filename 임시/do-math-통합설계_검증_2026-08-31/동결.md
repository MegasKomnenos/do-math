## 산출물

## 목적 진술

세 산출물이 이슈 18 전체와 이 세션의 사용자·assistant 대화에서 최종적으로 구축된 공동 이해를 정확하고 충실하며 정합적으로 담는지 검증한다. 이슈 본문과 앞선 handoff의 제안 가운데 뒤의 대화가 고치거나 폐기한 내용은 현행 결정으로 취급하지 않는다. 같은 주제에서는 더 늦은 사용자의 명시적 확정·교정이 우선한다.

검증 범위는 닫힌 결함 목록이 아니다. 현행 이해와의 불일치, 누락, 낡은 내용, 다음 세션이 다르게 읽을 수 있는 모호성, 설명 부족, 불필요하게 복잡한 표현, 문서 내부 모순, 세 문서 사이의 모순, 구현자가 새 결정을 내려야만 하는 공백, 잘못된 소유권·신뢰 경계·상태 전이, 예시를 닫힌 목록으로 잘못 축소한 표현과 그 밖의 실제 결함을 모두 찾는다.

세 문서의 역할은 다르다. `CONTEXT.md`는 구현 세부를 제외한 저장소 공통의 보편 용어와 의미를 소유한다. 지도 컨텍스트 정본은 이 지도의 현행 공유 결정과 구체 운전 계약을 고해상도로 소유하되 대체된 설계의 연혁을 현행 계약처럼 보존하지 않는다. 통합 설계는 백지 구현 세션이 추가 제품 결정을 내리지 않고 `do-math`를 구현할 수 있는 자기충족 명세여야 하며 용어, 상태, 역할, 입력, 출력, 불변식, 실패 경로, 판정 기준과 테스트 벡터를 닫아야 한다.

- 결론: 미리 정한 결론 없음. 실제 원문 대조로 결함 유무를 판정한다.
- 필수 논거: 각 결함은 정확한 위치, 위반한 기준, 실제 영향과 완성된 수리 문면을 가져야 한다.
- 필수 전거: 아래 「기준 원문」 전건과 세 산출물의 실제 문면.
- 분량 상한: 없음.

글은 정확성, 충실성, 정합성을 먼저 만족하고, 그 안에서 명확성, 충분성, 간단성, 간결성 순으로 고른다. 의미가 정의된 고유명사를 제외하면 쉽고 명확한 표현을 쓴다. 간단함을 짧음으로 오해해 필요한 사실, 조건, 예외와 논증 단계를 빼지 않는다.

## 불변식 목록

### 원천 우선순위와 문서 경계

- 이 세션의 뒤쪽 사용자 확정과 교정이 이슈 본문과 과거 handoff의 충돌하는 제안을 대체한다. 과거 문서는 결정 경위와 검증 기준으로 읽되 현재 상태를 되살리는 근거로 쓰지 않는다.
- 이슈 6의 종착은 P vs NP 연구 체계 재설계와 보편 스킬 `do-math`의 확립이다. 이 티켓은 통합 설계와 테스트 벡터를 확정하며 실제 수학 연구와 후행 구현은 수행하지 않는다.
- `CONTEXT.md`에는 Git ref, JSON 파일명, Windows API 호출 순서 같은 물리 구현 계약을 넣지 않는다. 지도 컨텍스트와 통합 설계는 필요한 구현 계약을 소유할 수 있다.
- 지도 컨텍스트는 현행 결정과 소유권을 한 번에 읽게 해야 한다. 대체된 구조, 대화 순서와 장황한 연혁은 현행 계약에 섞지 않는다.
- 통합 설계의 예시 열거는 문언과 의미가 닫힘을 요구할 때만 닫힌 목록이다. 열린 예시는 그 밖의 유효한 경우를 배제하지 않는다.

### 연구 철학과 `K·F·U`

- `K`는 추상적으로 따라 나오는 모든 귀결이 아니라 현재 신뢰 시대에서 실제 Lean 선언과 증명으로 명시되고 검증된 known mathematics의 영역이다. `K`는 구멍이 있고 여러 층위의 frontier를 가진다.
- 목표가 이미 `K` 안에 있으면 해결은 이미 주어진 형식 지식에서 회수할 수 있다. 그렇지 않으면 `K`와 목표 사이에 아직 연결 방법을 모르는 unknown이 있다. 방법을 이미 안다면 그 부분은 unknown이 아니다.
- `U`는 아직 표현되지 않은 가능성이라 저장 객체가 아니다. 모호한 단서라도 기록되는 순간 가시 연구 프런티어 `F`의 객체가 된다. 작업대는 `U`를 저장하지 않고 탐색을 통해 일부를 `F`로 드러낸다.
- 연구는 새 정의, 명제, 증명, 관계를 엄밀하게 쌓아 `K`의 frontier를 넓히고 목표에 접근한다. frontier 확장은 새 수학을 known mathematics에 넣는 일이므로 엄밀한 기준과 검증이 필요하다.
- unknown의 방향은 무한히 넓고 미리 최적 경로를 알 수 없으므로 선택과 집중이 필요하지만 탐욕적 선택이 최적임을 가정하지 않는다. 집중 활용과 탐색을 함께 운용한다.
- 연구 진전은 단순 작업량이나 `K`의 크기가 아니라 연구 헌장의 목표에 상대적으로 판정한다. 정확한 장애물, 반례, 범위 축소와 선택을 바꾸는 실패도 진전일 수 있다.
- `F` 객체와 Lean 정본 객체는 서로 다른 객체와 식별자를 가진다. 하나가 다른 것으로 이동하거나 같은 ID로 승급하지 않는다. 실제로 확인한 다대다 관계만 별도 관계 기록으로 잇는다.

### Lean, 의도와 신뢰 시대

- Lean 정본은 형식 수학 내용의 정본이고, 수학 해설은 사람이 읽는 연구의 주 산출물이다.
- 신뢰할 수 있는 기초 프로필과 도구체인 아래 Lean 커널 통과는 타입, 항, 선언과 형식 의존으로 표현된 관계의 타당성을 보증한다. 자연어 의도, 문헌의 뜻, 작업 관계와 연구 목표와의 동일성을 보증하지 않는다.
- Lean 표현이 원래 의도와 다르더라도 커널을 통과한 형식 표현은 그 표현 자체의 정확한 엄밀한 의미를 가진다. 의도 대응이나 해설의 오류는 Lean 객체의 형식 의미를 자동으로 없애지 않는다.
- 검토·심사 사슬의 주 대상은 Lean 증명의 형식 타당성을 다시 판정하는 일이 아니라 수학 해설과 Lean 형식 표현이 같은 수학적 의미를 담는지 확인하는 일이다.
- 활성 신뢰 시대는 하나다. 기초 프로필, 공리 허용 목록 `{propext, Quot.sound, Classical.choice}`, Lean·Lake·Mathlib의 정확한 판본과 해시, 형식 환경과 검사 도구 판본을 고정한다.
- 기초 프로필이나 도구체인의 갱신, 신뢰 무효화와 기존 정본의 재검사는 명시적인 새 신뢰 시대 준비·영향 판정·전환으로만 일어난다. 설치 환경이 달라졌다고 평시 상태를 조용히 바꾸지 않는다.
- Mathlib 밖의 전문 라이브러리를 Lean 정본의 영구 직접 의존으로 두지 않는다. 필요한 내용은 연구 체계가 소유하는 Lean 언어로 다시 작성한다.
- Lean 정본 편입의 보편 기준은 목표 관련성이 아니라 수학적으로 타당하고 엄밀한가이다. 정확한 부분·조건부·제한 결과나 목표와 무관한 결과도 편입할 수 있다. 목표 해결은 별도 프로젝트 감사가 판정한다.

### 프로젝트 입력과 연구 인스턴스 상태

- 프로젝트 입력은 연구 인스턴스를 초기화하는 일회성 재료다. 초기화 뒤 평시 재개와 작업 입력 구성은 외부 프로젝트 문서를 다시 읽거나 그 경로에 의존하지 않는다.
- 입력의 의미는 연구 헌장, 정책, 맥락, 설정, 초기 `F`, 자료·근거, 사용자 결정과 그 밖의 올바른 내부 소유자에게 빠짐없이 나눠 수입한다. 수입 대응표는 감사 기록이지 현행 의미의 정본이 아니다.
- 연구 헌장은 연구 이유, 핵심 목표, 원하는 결과, 성공과 부분 성과, 범위, 선택 목적, 방향, 학술 검증과 사용자 권한을 보존한다. 작업 씨앗·기억·설정은 헌장을 새로 만들거나 덮어쓰지 않는다.
- 보편 연구 방법은 `do-math`, 인스턴스 규범은 연구 정책, 한 작업의 지시는 작업 계약, 확정 운영 행동은 운영 처분 기록이 소유한다. 의미를 중복 소유하는 별도 범용 지침 문서는 두지 않는다.
- 외부의 새 사용자 입력은 변화 사건일 뿐이다. 의미별 소유자 판정, 차이·영향 계산과 필요한 승인을 거쳐 내부 정본의 새 판본으로 편입한 뒤 다시 내부 상태만 정본으로 사용한다.
- 연구 인스턴스의 공용 현재 상태와 이력은 `refs/heads/do-math/<instance_id>`가 소유하고 장기 상태는 `research/<instance_id>/` 아래 역할별로 둔다. 기계 기록은 판본화된 결정론적 UTF-8 JSON, 긴 산문·Lean·자료는 경로와 해시로 참조한다.
- 핵심 기록은 안정된 논리 ID를 가지며 `기록 ID + 공용 Git 커밋`이 판본을 식별한다. 제목·경로 변경은 ID 변경 이유가 아니고 의미 변경은 새 ID 또는 명시적 새 판본·관계를 요구한다.
- 공용 변경은 실제 의미 영향에 따라 `영향 없음`, `다음 선택부터 적용`, `편입 전 재검증`, `즉시 운영 점검`을 구분한다. 영향 판정 오류를 영향 없음으로 숨기지 않는다.

### 작업 씨앗, 작업과 실행

- 작업 DAG와 장기 연구 프로그램을 실행 정본으로 사용하지 않는다. 미래 가능성은 `F`와 작업 씨앗에 두고, 깊이 1 실행 껍질은 현재 공용 판본에서 지금 착수 가능한 작업만 나타내는 파생 보기다.
- 작업 씨앗과 연구 작업은 같은 `task_id`와 같은 작업 기록의 서로 다른 국면이다. 별도 승급 객체·승급 상태·새 작업 ID를 만들지 않는다. 작업 실행만 별도 `execution_id`를 가진 객체다.
- 작업의 공용 생명주기는 `open`, `superseded`, `withdrawn`, `terminated`이다. 같은 논리적 작업이면 명시적 결정으로 `superseded`와 `withdrawn`을 `open`으로 복원할 수 있고 새 착수 검토를 받는다. `terminated`는 다시 열지 않는다.
- 착수 가능성, 실행 껍질 포함, 우선순위, 점유와 작업자 단계는 작업 생명주기 값이 아니다. 구조화된 조건, 검토, 공용 판본과 실행 ref에서 계산하거나 읽는다.
- 작업의 절차적 종결 처분은 `completed`, `split_terminated`, `cancelled`, `operational_failure_terminated` 네 값이다. 수학적·연구 결과는 별도 열린 축이며 실행 실패나 긍정 결과의 유무와 종결 처분을 혼합하지 않는다.
- 모든 종결은 착수 계약의 필수 범위를 수행, 불필요 확인, 권위 있는 철회·대체, 후속 씨앗 이관 또는 미판정 가운데 어디에 두었는지 빠짐없이 설명한다. `split_terminated`와 운영 실패의 미완료 범위는 정해진 예외가 없으면 후속 씨앗으로 보존한다.
- 개별 실행의 실패는 연구 작업을 자동 종결하지 않는다. 같은 작업 계약을 계속할 수 있으면 새 실행이 같은 작업 branch와 worktree를 이어받는다. 현재 계약을 더 이어가지 않기로 확정한 때만 운영 실패 종결을 사용한다.
- 연구 작업 하나는 작업 branch와 worktree 하나를 가진다. 동시에 쓰는 실행은 하나다. 새 실행은 옛 실행의 권한 무효화, Job Object 전체 종료, 종료 장벽, 부분 자료 처분과 worktree·Git 상태 정리가 모두 끝난 뒤에만 파견한다.
- 실행 종료 원인과 작업 효과를 분리한다. 작업 효과는 같은 작업을 유지하거나 작업 종결에 연결하는 두 경우이며, 시작 실패·handoff·강제 종료·체크포인트 인수는 원인 기록이다.
- 작업 하나는 종결 공용 편입을 정확히 한 번 수행한다. 계획된 독립 중간 결과는 처음부터 작업을 나누고, 예상 밖 공유 가치가 생기면 현재 작업을 분할 종결한다. 내부 체크포인트는 공용 입력이 아니다.
- 종결은 `종결 준비 → 최신 공용 머리 반영·현행 재검증 → 원자적 ref 적용` 뒤에만 효력을 얻는다. 실패한 종결 시도는 작업을 종결하지 않는다.

### Git 상태, 프로세스 감독과 복구

- 공용 머리는 종결 공용 편입만 소유한다. 작업 branch는 실제 연구 내용과 체크포인트를 소유한다. 실행 상태는 `refs/do-math/runs/<instance>/<task>`의 단일 부모 `state.json` 커밋 사슬이 소유한다.
- 권위 있는 ref 쓰기는 예상 OID를 사용하는 조건부 갱신이다. PID, 환경 변수, 터미널 제목과 요약 문자열은 권한 근거가 아니다.
- 모든 메인 하위 AI 실행은 연구 작업자뿐 아니라 선택자, 검토자, 심사자, 부분 전문 검토자와 운영 판단 역할까지 고유 `execution_id`의 Windows Job Object 안에서 돈다.
- 루트 프로세스는 일시 정지 상태로 만들고 Job Object 설정·편입과 권위 있는 실행 허가 공개 뒤에만 재개한다. breakaway를 허용하지 않고 `KILL_ON_JOB_CLOSE`를 사용한다.
- 연구 인스턴스마다 결정론적 중앙 프로세스 감독기 하나가 모든 Job Object handle을 물리적으로 보유한다. `do-math` 메인 세션은 이를 논리적으로 총괄하되 native handle을 직접 가진다고 가정하지 않는다.
- 메인 세션은 제어 요청을 Git에 먼저 기록한다. named pipe는 요청 좌표의 통지일 뿐 정본이 아니다. 감독기는 controller OID, 실행 OID, `execution_id`, 요청 ID와 허용 전이를 다시 검사한 뒤 Windows 작업을 하고 결과를 Git에 기록한다.
- 계획된 메인 handoff는 감독기와 실행을 유지하며 controller를 조건부로 넘긴다. 예기치 않은 메인 소실은 새 배정을 막고 질서 있는 일시 정지·체크포인트를 시도한 뒤 필요하면 모든 Job Object를 강제 종료한다.
- `TerminateJobObject` 성공만으로 종료를 확정하지 않는다. handle 종료, 활성 프로세스 0, 프로세스 목록과 외부 도구 종료를 확인하는 종료 장벽 뒤에만 worktree와 모델 용량을 재사용한다.
- 프로세스 원장은 PID만으로 식별하지 않고 `execution_id`, PID, 생성 FILETIME, image path, 부모 프로세스 인스턴스, 관찰 출처, 시작·종료와 exit code를 기록한다. 실제 격리·종료의 정본은 원장이 아니라 Job Object다.
- 종결 뒤 실행 상태, 원 작업과 임시 편입 이력은 각각 불변 archive ref로 보존한다. 자동 만료하지 않으며 삭제·압축에는 별도 보존 정책이나 사용자 승인이 필요하다.

### 포트폴리오, 모델 용량과 기계 도구

- 메인 heartbeat는 겹치지 않게 주기적으로 돈다. 완료 실행과 종결·공용 편입을 먼저 처리하고, 반환된 자원을 포함해 모델별 잔여 용량을 계산한 뒤 새 포트폴리오 선택 세션을 연다.
- 포트폴리오 선택은 메인 세션이 직접 하지 않는다. 매 회차 새 `gpt-5.6-sol max` 별도 세션이 선택 알고리즘 전용 계약과 약 1M 컨텍스트 안의 종합 맥락 묶음을 받고 실행할 작업 집합 전체를 고른다.
- 후보 블록은 운영체제 난수로 섞고 seed와 실제 순서를 기록한다. 후보 블록 내부 원자료 순서는 유지한다. 순서는 우선순위가 아니다.
- 선택 AI는 확인된 근거, 추론, 가설, 설명하기 어려운 직감, 정보 획득을 위한 탐색과 동률 무작위 선택을 사용할 수 있다. 직감을 거짓 근거로 꾸미지 않고 당시 기대와 불확실성을 기록해 실제 결과를 다음 회차에 환류한다.
- 고정 점수, 고정 탐색 비율, 엄격한 선택 결정론과 형식적 기아 한도를 두지 않는다. AI의 넓은 재량과 실제 결과의 반복 환류가 기본 알고리즘이다.
- 입력·출력 manifest와 해시, 컨텍스트 완전성, 실행 껍질·점유·용량·현재성은 기계적으로 검사한다. 전문이 실제 컨텍스트에 들어가지 않으면 조용히 요약하지 않고 선택을 중단해 확장 방식을 다시 설계한다.
- 선택 세션과 메인 세션은 같은 판본의 기계 검사를 각각 실제 원자료에 실행한다. 메인은 검사 통과한 선택을 다시 평가하거나 임의로 바꾸지 않는다. 결함이면 재작성, 상태가 바뀌었으면 새 선택을 연다.
- 예산은 `(model, effort, max_concurrent_sessions)`의 모델별 동시 하위 AI 세션 상한뿐이다. 작업별 토큰·시간·비용 예산을 할당하지 않는다. 메인 세션, 결정론적 스크립트, 프로세스 감독기와 AI가 아닌 Lean 도구 실행은 이 용량에서 제외한다.
- 자원 집중은 한 작업에 여러 작업자를 붙이는 방식이 아니라 같은 방향의 서로 다른 작업 씨앗을 더 많이 선택하는 방식이다. 의도적 독립 검증이나 중복은 각각 자기 계약·worktree를 가진 별도 작업이다.
- 기계 도구는 AI 판단을 대체하거나 의미 규칙을 몰래 정하지 않는다. 반복되는 결정론적 수집, 검사, 직렬화, 계산과 안전한 적용을 미리 저작한 고품질 도구와 사용법으로 제공해 AI의 판단을 돕는다.
- 수학 판단을 생산하는 역할은 `gpt-5.6-sol max`, 전례 적용 의미 판정은 별도 `gpt-5.6-sol high`를 사용한다. 연구·평가 하위 세션에서 Codex `ultra`를 사용하지 않는다.

### 해설–Lean 동일성 검토와 인증

- 정본 편입 제안은 자연어 수학 해설 후보, 정확한 Lean 형식화 후보와 의미 단위별 동일성 대응표를 같은 불변 판본으로 묶는다. Lean 빌드·커널·공리 검사를 먼저 통과한 뒤 동일성 검토를 연다.
- 정의, 명제, 가정, 양화, 적용 범위, 결론과 자연어 증명의 수학적으로 의미 있는 각 주장을 대응한다. 전술 호출·커널 축약·통상 형식 세부의 줄별 번역은 요구하지 않는다.
- 검토자는 제안 전건을 읽고 동일성 이의를 만들려 한다. 이의가 없으면 승인한다. 심사자는 새 결함을 찾거나 제안 전체를 승인하는 역할이 아니라 전달받은 정확한 이의가 실제로 타당한지만 판정한다.
- 기본 검토자는 논증 재구성, 적대적 범위 검사, 의미 대응 세 관점의 독립 `gpt-5.6-sol max` 세션이다. 문헌 전사에는 원문 충실성, 여러 분야 결합에는 필요한 분야 전문 검토자를 조건부로 더한다. 모든 검토자는 지정 관점뿐 아니라 제안 전건을 읽는다.
- 형식화·공리 감사를 다시 판단하는 AI 검토자는 두지 않는다. 기계 검사 결과를 수학 해설이 정확히 말하는지는 동일성 검토 대상이다.
- 심사자는 이의 성립, 이의 반박, 문맥 대조 관점의 독립 세 세션이다. 각 이의 판정은 `승인` 또는 `기각`뿐이며 입력·도구·세션 결함은 판정이 아닌 `심사 미완료` 실행 상태다. 이의 승인은 같은 이의 판본에 대한 세 심사자의 만장일치를 요구한다.
- 같은 제안 판본의 루프에서는 같은 논리적 심사자 세 명이 이전 피드백과 검토자 답변을 받아 다시 심사한다. 같은 회차의 다른 심사자 판정은 봉인 전에 보지 않는다.
- 만장일치가 아닌 이의는 원 검토자에게 돌아간다. 검토자는 각 피드백에 답하고 이의를 보강·수정·분화하거나 새 이의를 만들거나 철회한다. 바뀐 이의는 새 판본이며 이전 승인을 승계하지 않는다.
- 부분 전문 검토자는 좁은 사실·논증 의무만 조사하고 제안·이의를 판정하거나 제안을 수정하지 않는다. 새 수학 생산이 필요하면 인증 사슬 밖의 제안 작성이나 연구 작업이 맡는다.
- 검토·심사 루프에는 별도 교착 판정, 고정 회차 상한, 무진전 의미 규칙이나 `인증 미완료`라는 특별 종결 상태를 두지 않는다. 일반 실행 중단은 일반 체크포인트·재개 절차가 처리한다.
- 모든 이의가 만장일치 승인 또는 검토자 철회로 닫힌다. 승인된 이의가 없으면 제안을 승인한다. 승인된 이의가 있으면 작성자가 전부 반영한 새 제안 판본을 만들고 새 검토단·새 심사단으로 전건 검토를 다시 시작한다.
- 인증은 별도 작업 씨앗이 아니라 원 연구 작업의 종결 하위 절차다. 승인된 이의 수정은 같은 계약의 미완료 의무이며, 계약 의미가 바뀌어야 하면 작업 종결과 새 씨앗으로 처리한다.
- 편입 뒤 Lean 정본은 형식 수학, 수학 해설은 동일하다고 인증된 사람이 읽는 수학, 인증 기록은 두 정확한 판본의 동일성 관계를 소유한다.

### 목표 감사, 운영 판단과 외부 검증

- Lean 정본 편입과 프로젝트 목표 해결은 별도 판정이다. P vs NP의 범위 차분 감사는 `동일`, `등가 입증`, `충분성 입증`, `범위 축소`, `범위 확장`, `조건부`, `미해결`을 구분하고 앞의 세 경우만 목표 해결과 양립한다. 나머지도 실제 범위를 정확히 말하는 엄밀한 결과이면 Lean 정본에 편입할 수 있다.
- 작업 진전 계약은 목표에 기여하는 상태 변화, 확인할 신호, 그것을 생산·시험하는 내부 절차와 다음 관찰 조건을 함께 정한다. 완료 예상은 근거가 있을 때만 선택 정보이고 점검·실패·중단을 직접 결정하지 않는다.
- 작업 자기 점검은 `진전`, `무진전`, `계약 부적합`을 구분한다. 첫 근거 있는 무진전의 실질적으로 다른 내부 적응 한 번과 그 뒤 운영 점검 경계를 보존한다.
- 외부 감시기는 결정론적 스크립트다. 작업자 공개 상태만 정상 관찰 입력으로 쓰고 감시 기록을 작업자에게 돌려주지 않는다. 의미 판단은 별도 운영 점검 AI가 원자료를 읽고 수행한다.
- 운영 점검자의 저영향 무변경 처분과 실행 정체성·점유·종결·중대한 자원을 바꾸는 고영향 처분을 구분한다. 고영향 처분은 독립 운영 처분 심사를 거친다.
- 승인된 고영향 처분의 자동 적용 권한은 사용자 결정에서 기계적으로 봉인한 실제 사례 전례가 현재 사례에 적용 가능할 때만 생긴다. 자동 적용 사례는 새 전례가 되지 않으며, 전례 적용 판정은 운영 점검·심사와 독립된 `gpt-5.6-sol high` 역할의 비대칭 이중 판정이다.
- 전례의 기본 범위는 실제 사용자 결정 사례다. AI가 일반 규칙을 창작하지 않는다. 전례 비적용, 대체와 폐기는 별도 불변 기록이며 실행 직전에 효력 집합과 ref를 다시 검사한다.
- 수학적 해결 뒤 프로젝트가 요구한 외부 검토·재현·출판 등 학술 검증은 Lean 정본 편입과 프로젝트 내부 해결 판정 뒤의 별도 단계로 표현하며 특정 주제를 `do-math`에 하드코딩하지 않는다.
