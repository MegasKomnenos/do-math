## Question

임의의 수학 연구를 작업 씨앗, 깊이 1 실행 껍질과 Lean 정본 중심으로 운전하는 보편 스킬 `do-math`의 자기충족적 구현 명세를 확정한다.

`do-math`는 연구 체계 전체의 생명주기를 소유한다. `do-math`는 연구 작업공간, Lean 형식화 작업공간, Lean 정본, 작업 씨앗과 깊이 1 실행 껍질을 초기화하고 재개하며 관리한다.

P vs NP 적용 워크스루의 프로젝트 입력은 `research/pvsnp/연구-주제-선호.md`, `research/pvsnp/핵심-정의-명세.md`, `research/pvsnp/문헌-체계-명세.md`로 구성된다. 세 문서는 각각 전체 연구 주제·원하는 결과·범위·방향과 문헌·학술 검증 선호, 핵심 수학 정의·연결 정리 의무, 문헌 연구의 구체적 주제·깊이를 소유한다. 한 문서라도 없거나 세 문서가 서로 다른 주제를 지시하면 입력 패키지가 완성되지 않은 상태로 처리하고 초기화를 시작하지 않는다.

설계는 다음 범위를 전부 결정한다.

1. 프로젝트 입력의 1회 수입을 포함한 연구 체계 인스턴스의 생성·재개·점검·종결·보관 절차
2. 연구 작업공간, Lean 형식화 작업공간과 Lean 정본의 저장 구조와 접근 경계
3. 공용 작업대 핵심 기록, 네 작업 인터페이스의 판본화된 JSON 스키마·결정론적 JSON 직렬화·산출물 참조, 선언형 발생 조건식, 깊이 1 실행 껍질의 파일 형식과 무결성 불변식
4. 작업 씨앗의 생성·정련, 동일 ID 착수 가능성 판정, 연구 작업의 분할·대체·폐기·판본화, 작업 진전 계약의 생성·검토·내부 운전·자기 점검, 내부 순차 절차, 작업 실행·체크포인트, 작업당 종결 공용 편입 한 번과 완료 기준
5. 실행 껍질 계산, 우선순위, Git 실행 ref의 원자적 작업 점유와 병렬 배정 절차
6. 모든 메인 하위 AI 실행의 프로세스 격리와 중앙 감독, 작업별 쓰기 소유권, 작업 종결 결과와 공용 편입 커밋의 일대일 대응, 최신 공용 머리를 임시 편입 브랜치에 반영하는 충돌 처리와 현행 기준 재검증
7. 운영 실패와 수학적 실패의 구별, 외부 안전 발동 조건·관찰 조건 평가 오류·관찰 응답 조건·관찰 의무 위반·작업 자기 점검 결함의 점검 발동, 운영 점검 실행, 운영 처분 실행, 중단·부분 산출·재시도·작업 실행 재개와 진단 우선 실패 회수
8. 연구 목적과 현재 상태를 입력으로 받는 분야 독립 탐색·집중 활용 배분 알고리즘
9. 포트폴리오 선택의 기아 위험·다양성·적응·결과 환류, AI 선택의 비결정성과 입력·검사·적용의 결정론적 경계, 모델·노력별 동시 하위 AI 세션 상한
10. 초기화·작업 종결 공용 편입·승인된 외부 변화·빈 실행 껍질의 생존 규칙에서 작업 씨앗을 만들고, 결과와 실패에서 새 프런티어 객체·관계·우선순위를 도출하며 장기 보존 여부를 판정하는 환류 절차
11. 수학 해설–Lean 형식 표현의 동일성 검토자·이의 심사자·부분 전문 검토자 배정, 역할별 권한·판정 독립성과 인증 기록
12. Lean 형식화 후보의 인증·커널 검사·공리 감사·정본 편입과 프로젝트별 범위 차분 감사 절차
13. 기초 프로필, 고정된 Mathlib 판본과 정본 갱신의 연결
14. 사용자 승인, 상신과 자동 처분의 경계
15. 장기 상태의 정본, 공용 Git 머리·실행 상태 커밋·실행 ref·작업 브랜치의 경계, 작업자 공개 상태, 실행·작업·임시 편입·monitor·조건부 certification 이력 보관 ref, 운영 점검 JSON과 조건부 ref 처분, 원자적 ref 트랜잭션, 복구와 마이그레이션
16. 모델·노력·병렬 기수와 역할별 배정 인터페이스
17. 상태 검사기, 네 작업 인터페이스·발생 조건식·작업 진전 계약·진전 신호·외부 감시기·관찰 입력 스냅샷·감시 기록 원장·관찰 조건 평가·관찰 조건 세대·관찰 의무·안전 제어 경계·관찰 응답 조건·작업 자기 점검·운영 처분 실행·작업 씨앗·실행 껍질 무결성 검사기, 참·거짓·평가 오류와 실패 시 차단 방향
18. 사람이 읽는 상태 보고와 기계 판독 출력
19. 다른 수학 연구에 적용할 확장 지점과 금지된 프로젝트별 하드코딩
20. P vs NP 연구와 다른 대표 수학 연구에 적용한 전체 워크스루
21. 프로젝트가 수학적 해결 뒤 요구하는 외부 검토·재현·출판 등 후속 학술 검증 단계

설계는 다음 결정을 불변 입력으로 사용한다.

- 수학 내용의 정본은 Lean이다.
- Lean 정본에는 승인된 기초 프로필, 인증된 보존적 정의와 입증·반증 결과만 들어간다.
- 활성 기초 프로필은 하나다.
- 공리 허용 목록은 `{propext, Quot.sound, Classical.choice}`다.
- 고정된 Mathlib 판본을 초기 Lean 정본 기반으로 수용한다.
- 연구 작업공간, Lean 형식화 작업공간과 Lean 정본을 분리한다.
- 작업 DAG를 사용하지 않는다. 깊이 1 실행 껍질은 특정 공용 판본에서 지금 착수 가능한 `task_id`만 나타내는 파생 보기이며, 미래 가능성은 `F`와 작업 씨앗에 보존한다.
- 공용 머리는 종결 공용 편입만 소유하고, 작업 브랜치는 실제 연구 내용과 체크포인트를 소유한다. `refs/do-math/runs/<연구 인스턴스 ID>/<작업 ID>` 실행 ref는 `state.json` 하나와 직전 상태 하나의 부모 관계를 가진 현재 실행 상태 커밋을 가리킨다. 커밋 OID는 불투명한 상태 세대 식별자이자 예상 상태 토큰이며 작업자와 확정된 운영 처분 실행은 `git update-ref <ref> <new> <old>` 조건부 갱신만 사용한다. 이 계약은 같은 공통 Git 객체·ref 데이터베이스 안에서 성립한다.
- 메인 세션이 파견하는 모든 하위 AI 실행은 연구 작업자뿐 아니라 포트폴리오 선택자, 동일성 검토자·이의 심사자·부분 전문 검토자와 운영 판단 역할까지 고유 `execution_id`의 Windows Job Object 안에서 돈다. 결정론적 중앙 프로세스 감독기가 Job Object handle을 물리적으로 보유한다. 루트 프로세스는 일시 정지 상태로 생성해 Job Object 설정·편입과 권위 있는 실행 허가 공개를 마친 뒤에만 재개하며, breakaway를 허용하지 않고 `KILL_ON_JOB_CLOSE`를 사용한다.
- 외부 감시기의 정상 관찰 입력은 현재 실행 ref가 가리키며 스키마·참조·무결성 검사를 통과한 변경 불가능한 작업자 공개 상태뿐이다. 미커밋 worktree와 부분 기록은 정상 관찰 입력이 아니지만 운영 점검 AI는 이상 진단을 위해 직접 읽을 수 있다. `state.json`의 OID 문자열은 작업 커밋을 보존하지 않으므로 활성 작업 브랜치 ref가 작업 이력의 도달 가능성을 별도로 보존한다.
- 종결 뒤 실행 상태·원 작업·임시 편입·monitor 이력을 각각 `refs/do-math/archive/runs/<인스턴스>/<작업>/<실행>`, `refs/do-math/archive/work/<인스턴스>/<작업>/<실행>`, `refs/do-math/archive/integration/<인스턴스>/<작업>/<실행>`, `refs/do-math/archive/monitor/<인스턴스>/<작업>/<실행>`에서 불변으로 보존한다. 인증 기록이 있으면 `refs/do-math/archive/certification/<인스턴스>/<작업>/<제안>`도 같은 종결 트랜잭션에서 불변으로 보존한다. 자동 만료로 삭제하지 않으며 삭제·압축은 별도 보존 정책이나 사용자 승인을 요구한다.
- 작업 종결 시 원 작업 브랜치를 동결하고 그 머리에서 임시 편입 브랜치를 만든 뒤 최신 공용 머리를 merge해 충돌과 현행 스키마·무결성·Lean·인증 기준을 재검증한다. 통과한 최종 트리로 현재 공용 머리 하나만 부모로 갖는 작업 전용 공용 편입 커밋 하나를 만들며 작업·체크포인트·임시 merge 커밋을 공용 머리의 조상으로 넣지 않는다. 공용 머리가 바뀌면 새 머리를 다시 반영해 재검증한다.
- 각 연구 작업은 목적에 기여하는 연구 상태 변화, 그 변화를 확인할 진전 신호, 작업자가 그 변화를 생산·점검하도록 내부 절차를 구성하는 의무와 다음 관찰 조건을 판본화된 작업 진전 계약으로 가진다. 완료 예상은 근거 있게 산정할 수 있을 때만 선택적으로 기록하며 점검·실패·중단을 직접 결정하지 않는다. 외부 안전 발동 조건과 작업 진전 계약의 점검 발동 조건은 자동 점유 상실이 아니라 운영 점검 실행을 발동한다. 점검한 ref가 여전히 현재이고 인수·중단 처분이 승인됐을 때만 옛 실행의 권한을 무효화한다.
- 관찰 의무가 열리면 작업자는 해당 의무를 참조하는 변경 불가능한 작업 자기 점검을 `진전`, `무진전` 또는 `계약 부적합`으로 기록한다. 유효한 `진전`은 작업을 계속한다. 근거 있는 `무진전`은 계약이 허용하고 다음 방법이 실질적으로 다를 때 내부 적응 한 번을 허용하며, 다음에도 무진전이면 운영 점검을 발동한다. 기록 부재·무결성 결함·증거 없는 진전·계약 부적합도 운영 점검을 발동한다. 형식 검사는 결정론적 검사기가 수행하고 의미 판단은 운영 점검이 원자료로 수행한다.
- 작업 진전 계약에서 작업자가 사용할 수 있는 모든 다음 관찰 조건은 외부 감시기도 같은 판본과 작업자가 공개한 같은 실행 상태에서 재현할 수 있어야 한다. 조건은 판본화된 일회성 관찰 조건 세대로 묶고 하나라도 먼저 도래하면 관찰 의무를 연다. 외부 사건 조건에는 재관찰 시점을 함께 두며 완료 예상은 평가에 참여하지 않는다. 관찰 조건 평가는 전건을 검사해 `미도래`, `도래`, `평가 오류`로 닫고 한 조건이라도 평가할 수 없으면 다른 조건이 참이어도 평가 오류다.
- 관찰 조건의 `도래`는 `실행 ID + 조건 세대 ID`로 식별하는 관찰 의무를 열며 즉시 운영 점검을 뜻하지 않는다. 관찰 의무 상태는 `응답 대기`, `충족`, `위반`으로 닫는다. 관찰 응답 조건은 의무가 열린 뒤 첫 안전 제어 경계와 실행 환경·도구 유형에서 정한 최대 응답 시각 가운데 먼저 도래하는 한계다. 작업자는 안전 제어 경계 뒤 다음 실질적 행동 전에 자기 점검을 기록한다. 최대 응답 시각까지 유효한 자기 점검이 없으면 의무를 위반으로 판정해 운영 점검을 발동하되 작업을 자동 중단하지 않는다. 평가 오류와 외부 안전 발동 조건은 응답을 기다리지 않는다. 유효한 자기 점검은 새 조건 세대를 활성화하고, 처분 직전 실행 ref가 달라졌으면 낡은 관찰로 보존한 뒤 새 스냅샷에서 다시 평가한다.
- 외부 감시기는 작업자가 공개한 실행 상태를 관찰 입력 스냅샷으로 고정해 닫힌 조건과 관찰 의무 이행을 평가하는 결정론적 스크립트다. 관찰 입력 스냅샷·평가·의무 이행·운영 점검 발동 근거는 감시 기록 원장에만 쓰고, 작업자는 이 감시 기록을 읽지 않는다. 외부 감시기는 실행 ref와 작업 브랜치를 바꾸지 않으며 프로세스 소실·실행 ref 불일치 같은 외부 안전 발동 조건으로 운영 점검을 원자적으로 하나만 연다. 운영 점검은 도구로 실제 실행 원자료를 읽고 진단·처분을 제안하는 별도 AI 실행이다.
- 역방향 전달은 확정된 운영 처분에만 허용한다. 운영 처분 실행이 현재 실행 ref를 기대값 기반으로 조건부 갱신해 필요한 실행 제어 상태만 적용하고, 작업자는 안전 제어 경계에서 새 제어 세대를 읽는다. 감시 기록과 실행 제어 상태는 서로 다른 정본이며 감시 기록을 작업자에게 복제하지 않는다.
- 작업 씨앗과 연구 작업은 같은 ID를 사용한다. 착수 가능성 판정이 실행 껍질 포함 여부를 파생하며 별도 작업 객체·승급 상태·승급 커밋을 만들지 않는다.
- 작업 씨앗·착수 명세 검토·작업 실행·작업 종결은 서로 다른 판본화된 인터페이스이며, 실행 껍질 계산은 구조화된 필드만 소비한다.
- 네 인터페이스의 기계 정본은 판본화된 JSON 스키마를 따르는 결정론적 UTF-8 JSON이다. 긴 산문과 실제 연구 산출물은 별도 파일에 두고 JSON이 좌표와 무결성만 참조한다.
- 발생 조건은 공용 커밋의 핵심 기록만 읽는 닫힌 선언형 연산자로 표현하며 임의 코드·실시간 외부 상태·새 수학 판단을 실행하지 않는다.
- 수학 의존은 Lean이 관리하며 별도 정본 의존 구조를 만들지 않는다.
- Wayfinder와 `do-dag`를 연구 실행 상태의 공동 정본으로 결합하지 않는다.
- `do-math`는 인증 판정과 Lean 커널 판정을 임의로 바꾸지 못한다.
- `do-math`는 프로젝트 초기화 입력을 인스턴스 생성 시 한 번 읽고 자기 연구 인스턴스 상태로 전수 수입한다. 평시 재개는 초기화 입력을 다시 읽지 않는다.
- 프로젝트 초기화 입력은 연구 주제, 원하는 결과, 성공과 부분 성과, 범위, 연구 선택의 목적과 방향, 문헌·학술 검증 선호와 그 밖의 프로젝트 고유 의미를 제공한다. `do-math` 통합 설계는 이 의미를 일반 입력 스키마로 받아 그 밖을 포함한 올바른 내부 소유자에게 빠짐없이 나눠 수입한다.
- `do-math`는 수학 연구 방법의 정본이다. 프로젝트 입력은 프로젝트 고유 의미를 제공하고 보편 연구 절차를 규정하지 않는다.
- 프로젝트의 주제 선호는 선택적 힌트가 아니다. `do-math`는 선호를 빠짐없이 보존하되 수학적 증거와 판정을 선호에 맞게 바꾸지 않는다.
- 수학 판단을 생산하는 개별 에이전트는 `gpt-5.6-sol max`를 사용한다. `do-math`는 병렬화를 직접 운전하고 연구 작업 안에서 Codex `ultra`를 사용하지 않는다.
- 기계적으로 완전 판정할 수 있는 작업만 충분한 경량 모델이나 스크립트에 맡길 수 있다.
- 목적, 신뢰 경계, 외부·비가역 효과 또는 사용자 절충이 필요한 결정만 사용자에게 상신한다.
- Mathlib 밖의 전문 외부 라이브러리를 Lean 정본이 직접 의존하지 않으며 영구 어댑터를 두지 않는다. 필요한 수학 내용은 연구 체계가 소유하는 Lean 언어로 다시 작성한다.
- 프로젝트 입력은 핵심 목표와 후보 결과의 범위 차이를 전수 감사하고 수학적 해결 뒤 별도 학술 검증을 요구할 수 있다. `do-math`는 그 요구를 특정 주제에 하드코딩하지 않고 표현·실행할 수 있어야 한다.

완료 산출은 `docs/do-math/통합-설계.md`다. 백지 구현 세션이 추가 결정을 내리지 않고 `do-math`를 구현할 수 있어야 한다. 통합 설계는 용어, 상태, 역할, 입력, 출력, 불변식, 실패 경로, 판정 기준과 테스트 벡터를 정의한다.

이 티켓은 설계와 테스트 벡터를 확정한다. 후행 구현·검증 티켓이 승인된 설계를 구현한다.
