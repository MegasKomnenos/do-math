# do-math 시험 경량화 작업 계약 (2026-09-26)

이 문서는 do-math 시험 경량화에 참여하는 모든 작업자가 따르는 공통 계약이다. 작업자별 임무·범위·반환 항목은 각자의 파견문에 있고, 이 문서는 모든 작업자에게 같은 규칙만 담는다. 파견문과 이 문서가 충돌하면 파견문을 따른다.

## 1. 목적과 사용자 결정

do-math의 시험 스위트(`.claude/skills/do-math/scripts/tests/`, 약 1,900개 시험)는 현재 직렬로 수천 초가 걸린다. 사용자는 다음을 결정했다. 이 결정은 작업자가 재검토하거나 보류할 대상이 아니다.

1. **시간 목표.** 스위트를 몇 개의 조각(shard)으로 나눈다. 각 조각을 단독으로 돌려 120초 이내, 모든 조각을 차례로 돌린 합계 300초 이내가 목표다. 기준은 이 개발 기계(Windows 11, 4코어)의 벽시계 시간이다. 이 수치는 최대한 가까이 가야 할 목표이며 넘으면 안 되는 한계가 아니다. 실익 있는 수단을 다 쓴 뒤에도 넘으면 그 결과를 받아들인다. 수치를 맞추려고 제품의 핵심 기능을 약하게 하거나 실익 없는 축소를 하지 않는다.
2. **결과 캐시 제거.** `run_tests.py`의 결과 캐시는 없앤다(통합자가 수행).
3. **커버리지 보존.** 시험이 검사하는 범위는 크게 달라지지 않아야 한다. 수단의 선호 순서는 (1) 실행을 더 효율적으로 만들기, (2) 불필요하거나 중복된 부분의 통합·제거, (3) 범위 축소다. 범위 축소는 분명한 실익이 있을 때만 허용하고, 할 때는 반환에 대상·이유·잃는 것을 적는다.
4. **제품 비용 절감 우선.** 시험 시간의 상당 부분은 제품 자체의 비용(아래 2절)이다. 제품을 빠르게 해서 시험을 빠르게 하는 방향을 우선한다. 실익이 분명하면 제품의 기능 범위가 바뀌어도 된다. 그 경우 반환에 무엇이 바뀌었고 무엇을 얻었는지 적는다. 실익이 분명하지 않은 기능 변경은 하지 않는다.

## 3. 작업 공간과 범위

- 각 작업자는 파견문이 지정한 git worktree와 브랜치에서만 작업한다. 다른 worktree, main 작업 트리(`C:/math`), `C:/math-worktrees/t-base`(커버리지 기준선 실행 중)는 읽기만 한다.
- 커밋은 자기 브랜치에만 한다. push, 다른 브랜치 병합, worktree 생성·삭제는 하지 않는다.
- `.agents/` 생성 사본과 `docs/`의 문서는 고치지 않는다. 통합자가 한 번에 갱신한다.
- 배정된 범위를 임의로 축소하지 않는다. 배정 항목을 구현하지 않고 반환할 수 있는 경우는 (1) 이미 고쳐져 할 일이 없음을 원문 좌표로 입증한 경우, (2) 구현이 이 계약의 1절 결정이나 do-math의 보안·데이터 보존 경계와 충돌함을 좌표로 입증한 경우뿐이다. 어려움·시간·위험 추정은 구현하지 않을 근거가 아니다.
- 다른 작업자의 범위에 속하는 문제를 발견하면 고치지 않고 반환에 적는다.

## 4. 시험 실행 규율

시험은 `C:/math-worktrees/t-int/.claude/skills/do-math/scripts/tests/시험-지침.md`를 따른다(전문을 읽는다). 작업자에게 해당하는 층은 편집 확인과 인계 확인이며, 전체 실행은 하지 않는다. 실행 도구는 자기 worktree의 `scripts/run_tests.py`다.

- 기준 결과: main(379a171)의 모듈별 실행 로그는 `C:/math-worktrees/tools/base/logs/<모듈>.txt`, 실패 목록은 `C:/math-worktrees/tools/base/failures.json`이다(커버리지 계측 아래 plain unittest로 실행). 그 뒤 W-debt가 19개를 고쳤다(`t-int`에 병합됨).
- worktree에서는 실제 Lean이 `unavailable`이다. 제품이 도구 모음을 `<저장소 루트>/.skill-workspace/do-math-toolchains`에서 찾는데 그 폴더가 `C:/math`에만 있기 때문이다. `lean` 표시 시험의 이 증상은 결함으로 세지 않는다.
- 시험을 돌리는 작업자는 동시에 세 명 이하다. 파견문이 "정적 분석 단계"라고 정한 작업자는 파견문이 허락할 때까지 시험을 돌리지 않는다.

## 5. 불변 조건

경량화는 다음을 약하게 만들지 않는다.

- 저장의 원자성: 상태 게시는 `update-ref`의 기대값 비교(CAS)로만 참조를 옮긴다.
- 저장 계약 `do-math-state/6`의 형식과 검증. 저장소에 남는 객체와 참조의 모양.
- 설치 판본 일관성: 실행 중 설치 코드나 역할 문서가 바뀌면 다음 게시 전에 탐지해 멈춘다.
- 시험의 판정 대상: 시험이 단언하는 성질이 같은 강도로 남는다. 시험을 빠르게 하려고 단언을 약하게 만들지 않는다. 공개 경로 자체가 검사 대상인 시험(예: 공개 초기화, 실제 Git, 실제 프로세스, Windows Job, Lean 실제 실행)은 그 경로를 유지한다.

## 6. 반환 서식

반환의 첫 낱말은 `DONE`, `PARTIAL`, `BLOCKED` 중 하나다. `PARTIAL`은 배정 항목 일부를 끝내지 못한 경우, `BLOCKED`는 진행할 수 없는 경우다. 그 뒤에 다음을 적는다.

1. 브랜치와 마지막 커밋 해시, 변경한 파일 목록.
2. 배정 항목별 처분: 구현함 / 이미 되어 있음(좌표) / 구현하지 않음(3절의 사유와 좌표) / 끝내지 못함(남은 일).
3. 측정: 시험 ID, 변경 전 초, 변경 후 초. 측정하지 않은 항목은 "측정 안 함"으로 적는다.
4. 실행한 시험과 결과: 통과·실패·오류 수, 실패는 ID와 원인. 변경 전부터 실패하던 것은 구분한다. 돌리지 않은 관련 시험이 있으면 목록과 이유.
5. 제품 기능이나 시험 범위가 바뀐 것: 대상, 이유, 잃는 것, 얻는 것. 없으면 "없음(확인 범위: …)".
6. 작업 중 막힌 지점, 접근을 바꾼 지점, 예상과 달랐던 결과.
7. 다른 작업자 범위에서 발견한 문제.
