## 맥락

시험 경량화(2026-09-26, 공통 계약 `임시/시험-경량화-2026-09-26/계약.md`)의 제품 작업 W-eng다. worktree `C:/math-worktrees/t-eng`, 브랜치 `t-eng`에서 수행했다. 임무는 세 가지였다. 설치 매니페스트 재계산을 줄이고, 한 번의 저장에서 반복되는 직렬화를 줄이고, 프로파일 상위의 기타 제품 비용을 줄이는 것이다. 작업 중 통합자가 범위를 추가했다. W-git 계측에서 드러난 엔진 쪽 git 읽기 반복(방금 게시한 artifact의 재독, `control`의 저장소 재생성, 과거 input snapshot의 재검증)이다. `git_store.py`와 시험 fixture는 범위 밖이었다.

구현한 것은 다음과 같다.

- 설치 검사(`engine._installation_manifest`)는 마지막으로 해시한 판본의 디렉터리 목록 지문(scandir로 얻은 `.py`·역할 문서별 크기·수정·생성 시각)이 같으면 그 판본을 그대로 돌려준다. 파일 추가·삭제는 목록의 키 집합으로, 내용 변경은 지문으로 잡는다. 목록은 경로 탐색과 해시보다 먼저 찍고, 2초 이내의 지문(`fingerprint_settled`)이 있으면 재사용하지 않는다. 멈추는 방식과 검사 지점은 바꾸지 않았다.
- `canonical_json`과 `validate_storage_value`가 노드마다 실행하던 함수 내부 import를 모듈 최상위로 옮겼다. 값 검사는 plain dict·list·str의 직접 경로와 ASCII 문자열의 서로게이트 검사 생략을 더했다. 20만 개 무작위 값으로 옛 구현과 오류 유무·문구가 같음을 대조했다.
- `seal_large`와 `payloads.encode`의 전체 상태 순회에서 스칼라·짧은 문자열은 호출 없이 건너뛰고, 봉인 불가로 판정된 문자열을 다시 인코딩하지 않는다. 무작위 구조 3,000개로 옛 구현과 결과를 대조했다.
- `fit_context`는 멤버마다 문맥 전체를 다시 직렬화하던 크기 계산을 catalog가 이미 가진 멤버 바이트로 합산한다. 한 단계 깊어질 때 줄바꿈마다 공백 2개가 늘어나는 규칙을 쓰며, 시험이 실제 `canonical_json` 길이와 같음을 확인한다.
- `repository`에 artifact 사실 캐시를 두었다. 이 프로세스가 쓰거나 읽은 artifact의 바이트·길이를, 그 경로가 존재함을 안 head와 함께 기억한다. 이 프로세스가 게시한 head의 부모 관계를 따라 그 head의 후손인 snapshot에서만 재사용한다. 기존 artifact 번들은 바뀌거나 지워지지 않는다(`git_store._validate_artifact_changes`)는 불변식이 근거다.
- 살아 있는 실행의 input snapshot은 검증된 읽기 캐시(LRU 4)의 한도 밖에 유지한다(`retain_reads`, `_save`에서 갱신). `control()`은 (저장소, 인스턴스)마다 읽기 전용 저장소 하나를 재사용한다.

## 터득한 것

**Python 3.12의 cProfile은 다중 스레드 엔진에서 누적 시간을 크게 부풀린다.** 3.12의 cProfile은 `sys.monitoring` 기반이라 모든 스레드의 사건이 한 호출 스택에 섞인다. 계약 2절의 "설치 매니페스트 재계산 약 25%, 상태 직렬화 약 15%"는 이 누적값에서 나왔다. 스레드별 최외곽 벽시계 타이머로 다시 재면 변경 전 설치 검사는 시험 총시간 95~135초 가운데 약 2초였다. 코드를 바꾸지 않은 `discover_lean`의 cProfile 누적이 37.5초에서 1.1초로 바뀐 것도 같은 왜곡이다. 결정에는 벽시계 타이머(`/tmp/teng-prof/timed.py`, Git 제외 로컬 임시 경로)와 git 프로세스 계수를 썼다. cProfile의 자체 시간은 비교적 믿을 만했으며, 거기서 함수 내부 import가 드러났다.

**격리된 호출 비용과 경합 중 비용은 다르다.** 설치 매니페스트 재계산은 혼자 돌면 약 35ms였지만 CPU를 쓰는 스레드가 하나 있으면 0.26~0.85초였다. `reading_map`의 경로별 `resolve`와 `rglob`처럼 GIL을 놓는 시스템 호출이 많은 코드는 경합 때마다 GIL을 다시 기다린다. scandir 기반 목록은 경합 중에도 약 1ms였다.

**반복 비용의 실제 원천.** `validate_storage_value`의 비용 상당 부분은 재귀 호출마다 실행되던 `from .payloads import ...`였다. 2만 행 표본에서 검사는 1.59초에서 0.12초, `canonical_json`은 2.35초에서 0.66초가 됐다. 남은 비용은 들여쓰기 JSON에 쓰이는 순수 Python 인코더다. 3.12의 C 인코더는 indent를 지원하지 않는다.

**편집 중 실행의 간섭.** 엔진 시험은 설치 파일이 바뀌면 멈추도록 되어 있다. 그래서 시험 실행 중에는 `scripts/do_math`를 고칠 수 없었다. 변경 전 측정은 스킬 트리를 임시 폴더에 복사해 돌렸다.

**줄이지 않은 후보와 이유.** `_refresh_readiness`(시험당 약 1.3초)는 입력에 현재 시각과 실행 상태가 들어가 호출마다 입력이 다르다. `discover_lean`(약 0.5초)은 PATH 디렉터리 시각으로 메모할 수 있다. 그러나 `shutil.which`를 패치하는 시험과 1초 재발견 계약에 새 캐시 무효화 조건을 더하므로 하지 않았다. `control_transport` 폴링 자체는 약 0.2초였고, 나머지는 수락된 요청의 게시 비용이었다.

## 작업 너머 시사점

- 다중 스레드 코드의 비용 배분은 cProfile 누적값보다 스레드별 벽시계 타이머와 외부 프로세스 계수로 판정한다. dream에서 [[L-0015]]의 경량화 실측 항목과 묶을 후보다.
- 병렬 작업자의 커밋은 같은 M 번호를 선점할 수 있다. 이 노드는 M-0350으로 썼으며, 통합 시 번호 재배정이 필요할 수 있다.
