## 맥락

do-math 시험 경량화의 작업자 B3로 worktree `t-b3`(브랜치 `t-b3`, `t-int`에서 분기)에서 열한 시험 모듈을 옮겼다. 대상은 `test_session_scheduler`, `test_research_recovery`, `test_run_feedback`, `test_stop_flags`, `test_cli`, `test_redesign_ENGINE`, `test_lifecycle_engine`, `test_controls`, `test_input_recovery`, `test_cli_advanced`, `test_provider_recovery`다. 입력은 공통 계약 `임시/시험-경량화-2026-09-26/계약.md`, 사전 분석 `분석-G3.md`, 시험 지침 `scripts/tests/시험-지침.md`, 공유 기반 `tests/research_fixtures.py`의 docstring이었다. `임시/` 아래 두 문서는 Git 제외 로컬 자료이므로 정리되면 사라진다. 제품 코드는 고치지 않았다.

옮김의 수단은 네 가지였다. 첫째, 시험마다 반복하던 시작 상태를 `restore_template` 빌드 함수로 바꿨다. 새로 만든 빌드는 `test_lifecycle_engine.initialized_instance`(공개 `initialize`만), `test_session_scheduler.ready_work`(준비된 과제 N개와 그 작업), `test_research_recovery`의 `reviewed_task`·`parked_failed_plan`·`paused_limited_recovery`, `test_stop_flags.waiting_action`, `test_input_recovery.overflowed_maintenance`, `test_cli.cli_instance`, `test_cli_advanced.created_instance`다. 둘째, CLI 자식 프로세스를 `run_cli`로 바꾸고, `test_cli`의 종료 코드 시험 하나만 자식 프로세스를 남겼다. 셋째, `git init` 자식 프로세스를 `git_init`으로 바꿨다. 넷째, 시나리오를 단언이 확정되는 지점에서 멈췄다(`test_model_assessments_flow…`는 첫 연구 작업 실행이 끝나면 멈춘다).

## 터득한 것

**다른 모듈이 빌려 쓰는 setUp은 공개 계약이다.** `test_input_recovery.InputRecoveryPublicTests.setUp`을 처음에는 입력 초과 상태(S9) 템플릿 복원으로 바꿨다. 인계 확인 대상을 찾으려고 모듈 이름으로 grep하자, 다른 모듈 여덟 곳이 이 setUp을 활성 상태(S1) 고정물로 빌려 쓰고 있었다(`test_academic_engine`, `test_approved_five_repairs`, `test_connection_repairs`, `test_initialization_efficiency`, `test_initialization_probe_batch`, `test_six_connections`, `test_submission_flow`, `test_trust_continuation`). 그래서 setUp은 활성 상태 복원으로 되돌렸고, 두 입력 초과 시험만 `overflowed()`로 S9를 다시 복원한다. 파견문은 `FakeEngine`만 공유 대상으로 명시했지만, 빌려 쓰는 쪽은 클래스 import가 아니라 setUp 호출이라 import 검색으로도 드러난다. `test_redesign_ENGINE.routing_engine`도 세 모듈이 import하므로 인계 확인에 넣었다.

**main부터 실패하던 다섯 건은 모두 시험 쪽 원인이었다.**
- `test_redesign_ENGINE`의 셋은 시험 기반 결함이다. 8d2ffd0가 `self.store.git_dir`를 즉시 평가하게 바꾸고 c44dd7b가 `config['max_artifact_bytes']`를 읽게 바꾸었는데, `routing_engine`은 저장소도 그 설정도 없는 엔진을 만들었다. 적재된 엔진에는 둘 다 항상 있으므로, `routing_engine`에 `git_dir=None`만 가진 저장소 대역(`NoRepository`)과 기본 `max_artifact_bytes`를 넣었다.
- `test_cli…test_audit_normalized_control_identity_at_public_boundary`는 현행 계약과 어긋난 기대였다. 379a171이 요청 ID 도출을 CLI에서 엔진 `control`로 옮겼다(`cli._control`의 주석). 시험은 CLI가 만든 ID를 `control`에 넘기는지 봤다. 이제는 CLI가 식별 입력을 그대로 넘기고, 엔진이 도출한 ID를 보고하는지를 단언한다.
- `test_research_recovery…test_scholarly_configuration_reaches_the_actual_runner_call`도 현행 계약과 어긋난 기대였다. 고정 프로필이 러너 도구를 공급하고(`model_runner.ModelRunner.run`은 프로필과 함께 온 `scholarly_server` 인자를 거부한다), 시험은 별도 인자를 기대했다. 이제 인자는 None이고 `profile['ai']['scholarly_server']`가 설정과 같음을 단언한다.

**분석과 다르게 한 곳.** `test_blocked_high_priority…`의 실제 재검토는 봉인 주입으로 바꾸지 않았다. 주입하면 실제 검토가 만들던 준비 사건과 계획 재선택의 전제를 시험이 따로 꾸며야 하기 때문이다. `test_lifecycle_engine`의 공개 활성 시험(`test_public_call_mode…`)은 `PublicInitializationRunner` 경로가 다른 곳에서 검사되지 않아 공개 경로를 유지했다.

## 작업 너머 시사점

- dream에서 묶을 후보: [[M-0349]]의 "시험 미실행 위험"과 이 노드의 수리 다섯 건. 커널 단계에서 제품 인터페이스를 좁히면(저장소 속성 즉시 평가, 설정 키 필수화, 식별 도출 위치 이동) 메모리 대역 고정물과 호출 계약을 기대하던 시험이 함께 깨진다. 제품 변경의 인계 확인에 대역 생성 함수의 이름(`routing_engine`, `bare_engine`)을 넣으면 이를 먼저 잡을 수 있다.
- 템플릿 복원은 같은 매개변수를 쓰는 시험이 둘 이상일 때만 이득이 난다. 설정이 시험마다 다르면 빌드가 시험 수만큼 돈다. `test_session_scheduler`의 공개 활성 빌드가 설정 차이로 셋이 된 것이 그 예다.
