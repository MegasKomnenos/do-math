# 계획·연구·검토 세션의 작업맥락

## 맡은 결과와 읽을 자료

새 do-math의 실제 세션이 개발 대화를 모르더라도 자기 일을 판단하고 수행할 수 있도록 공통요소 문서 하나와 세 범주의 작업공통요소 문서를 작성한다. 목표는 사용자와 대화하지 않고 연구를 이어 가며 독립 검토를 거친 수학 해설과 축적 지식으로 목표를 달성하는 것이다. 문서는 이 목적과 각 세션의 판단을 돕는 작업 지시다.

먼저 `inputs/context.md`, `inputs/plan.md`, `inputs/seams.md`, `task.json`을 읽는다. 사용자 확정 요구의 원문은 `C:/math/.async/do-math-rebuild-20261021/user-messages.md`다. 수용된 제품 계약은 자기 workspace의 `.claude/skills/do-math/protocol.md`이고 실제 형식은 같은 폴더의 `check.py`에 있다. 프로토콜의 인스턴스·input.json·공개 산출·대체·검토·계획·공식 검사 절을 읽고 사용한다. 이전 do-math나 Git 이력에서 설계를 가져오지 않는다.

## 작성할 문서와 의미

1. `.claude/skills/do-math/common.md`: 모든 세션이 받는 공통요소다. do-math의 목적, 사용자는 목표·조건·허가를 정하고 AI가 방법과 과제 분해를 정한다는 경계, 세션의 재량과 필요한 만큼의 확인을 설명한다. 작업맥락 세 층의 관계를 독자가 이해해야 한다. 공통 문서와 protocol.md, 인스턴스 goal.md가 공통요소이고, 범주 문서는 작업공통요소, 자기 input.json의 task는 작업특정요소다. instance/settings/knowledge 위치를 찾고 자기 세션 폴더에만 쓰며 output/에 공개할 내용을 모으고 공식 검사를 실행해 스스로 제출하는 경로를 안내한다. 산출 검사 통과는 수학적 인정이 아니며 해설과 근거가 공개 기록만으로 읽혀야 한다. 실행기만 재검사 후 새 기록·Git 커밋으로 반영한다. 기존 결과가 지식에 들어간 사실, 독립 검토의 판단, 목표 달성의 판단을 구분한다. 현재 환경을 쓰고 Lean 판본은 정보로 남긴다는 원칙도 전달한다.
2. `.claude/skills/do-math/plan.md`: 계획은 목표·축적 지식·task.events를 읽어 다음 연구를 고르고 판단 이유와 게시를 산출한다. start/review_finished/session_failed/user_input 의미, 정상 연구는 먼저 자동 검토를 받는 흐름, 자기 실행 중 사건은 다음 계획이 받는 의미를 설명한다. 연구·추가 검토·목표 검토·외부 입력 대기 요청과 모델·노력 선택의 역할을 다룬다. 사용 가능한 지식·실패 접근·남은 질문을 다음 과제에 실제로 활용하고 과제에 목적·조건·기대 산출·참조를 충분히 전달한다. 독립 과제를 병렬화하되 이미 게시돼 아직 끝나지 않은 과제를 고려하고 같은 기록을 대신하는 과제 둘을 동시에 배정하지 않는다. 후속 계획의 빈 배열은 앞선 게시 취소가 아니라는 계약도 전달한다. 대체 사슬·가지와 상충 검토를 읽는 규칙, 새 기록에 구 검토가 자동 승계되지 않는다는 의미가 필요하다. 목표 검토는 달성 가능성을 공개 지식으로 판단할 수 있을 때 요청하며, 사용자가 실제로 줄 입력이 필요할 때 그 내용과 이유를 wait에 쓴다. 문서만으로 별도의 계획 승인 단계나 새 실행기 감시 규칙을 만들지 않는다.
3. `.claude/skills/do-math/research.md`: 과제 목적과 조건, 축적 지식의 근거와 한계를 읽고 증명·반례·계산·문헌 방법을 재량껏 선택하게 한다. 주 산출물은 정의·가정·주장·논증을 사람이 이해할 수 있는 해설이다. 확인한 범위, 부분 결과, 실패한 시도와 남은 질문, 사용한 참조를 남긴다. Lean을 쓴 결과는 settings의 명령으로 실제 컴파일하고 원문·판본·명령·결과·한계를 남긴다. Lean이 필요 없는 계산·문헌 결과도 허용한다. 공개 파일만으로 다음 검토가 가능하도록 자료와 실행 방법을 제공하고 검증하지 못한 내용을 검증했다고 쓰지 않는다. 대체 산출은 기존 기록 전체를 대신할 수 있는 내용을 포함한다.
4. `.claude/skills/do-math/review.md`: task.target으로 연구 산출 전체 검토와 목표 검토를 구분한다. 공개 지식과 대상 기록을 근거로 판단하고 작성자 세션의 작업 폴더·중간 파일·로그를 찾으러 가지 않는다. 연구 산출의 모든 결과와 실패·질문을 읽는다. Lean 원문은 자기 세션 폴더의 작업 사본에서 설정에 따라 다시 컴파일해 원 공개 기록을 변경하지 않도록 한다. Lean 수용, 해설과 Lean의 수학적 일치, 제시한 근거가 주장을 뒷받침하는지의 판단을 구분한다. 계산은 필요한 작은 재현이나 방법 확인, 문헌은 실제 원문 대조로 평가한다. 목표 검토는 목표·필수조건과 축적 지식 전체를 대조하고 실제로 충족됐는지 판정한다. 자료 추출·해설을 검토할 때 원문에서 중요한 내용이 산출에 빠지지 않았는지와 산출 주장이 근거에 맞는지를 양방향으로 확인한다. 단순 파일 존재·링크·형식 검사·Lean 통과만으로 내용이 충분하다고 판단하지 않는다. 공개 지식에서 찾을 수 있는 근거와 실제 확인 범위로 verdict/reason을 쓰고 보충 자료도 자기 output/에 공개한다.

공통 개념은 common과 protocol에 두고 범주 문서는 그 범주의 판단에 집중한다. 다만 중요한 의미를 링크 하나로 대신하지 않는다. 첫 독자가 본문에서 자기 일과 판단 기준을 이해한 뒤 필요한 세부 필드와 예시를 protocol에서 찾게 한다. 자연스러운 읽기 경로를 만들며 개발 과정의 자기 설명이나 불필요한 금지 목록을 제품 문서에 넣지 않는다.

## 계약과 쓰기 경계

제품 수정은 위 네 파일에 한정한다. `protocol.md`, `check.py`, CLI 어댑터, 실행기, `SKILL.md`, 공용 context/plan/seams/queue는 수정하지 않는다. 범주 문서의 파일명은 실행기가 `<skill>/common.md`와 `<skill>/<category>.md`를 전달하기 위해 정한 배정이다. protocol의 input.json 스키마나 산출 필드를 새로 정의하지 않는다.

실행기는 아직 구현 전이고 명령·runner 내부 상태 스키마도 미정이다. 실행기 명령을 가정한 사용법을 쓰지 않는다. 계획이 진행 중/게시된 과제를 파악하는 구체 상태 경로가 필요하면 그 소비 요구를 report에 명시한다. 실행기 task는 수용된 산출 계약과 이 문서 경로를 소비하며 병렬로 구현할 수 있다. 실행기 수용 뒤 SKILL 안내와 연결 점검에서 필요한 소규모 보완을 묶는다. 실제 전달에 장애가 되는 계약 결함을 발견하면 정확한 위치·영향과 최소 변경 제안을 보고한다.

## 확인과 보고

새 테스트를 늘리는 대신 정적으로 읽어 확인한다. 개발 기록을 모르는 세션의 진입 경로인 자기 input.json → common/protocol/goal → 범주 문서 → task와 공개 knowledge를 따라, 중요한 목적·권한·작업 방법·판단·산출·검사 내용이 회수되는지 본다. 문서에서 실제 필드를 안내한다면 check.py와 대조한다. 사용자 원문과 공용 context 2~4절의 중요한 내용이 결과에서 빠지지 않았는지도 대조한다. 직접 확인한 범위를 보고하며 이 문서 읽기만으로 실제 모델 완주가 확인됐다고 말하지 않는다.
