# do-math 재구축: 계획

이 문서는 새 do-math를 완성하기까지 남은 결과물과 그 사이의 선행 관계를 정리한다. 무엇을 왜 만드는지는 `context.md`에, 구성 요소 사이의 인터페이스는 `seams.md`에 있다. 결과물을 어떤 task로 나누고 묶을지는 manager가 정한다. 아래 순서는 결과물 사이의 실제 의존에서 나온 것이다.

## 현재 상태

개발 완료. `cli-discovery`, `protocol-checker`, `cli-adapter`, `session-contexts`, `runner`, `skill-entry`, `mixed-completion`, `final-review`를 수용했다. manager 0009는 최종 독립 검토의 합격 판단을 사용자 요구·제품 진입점·공개 완주 근거·관련 실행기 코드에 대조하고 변경 없는 review를 `workspaces.py integrate`로 처리했다. 구현·가짜 흐름·실제 Codex와 Claude의 작은 Lean 목표 무인 완주 및 최종 review가 갖춰졌고 미해결 작업은 없다. 수용 근거와 확인 한계는 `context.md` 1절과 `managers/0009/decision.md`, 실제 계약은 `seams.md`에 있다.

현재 작업은 다음과 같다.

| task | 맡은 결과 | 후속에서 쓰는 곳 |
|---|---|---|
| `protocol-checker` (수용) | 인스턴스 구조, 세 범주의 산출·참조·대체 규칙, 이를 설명하는 제품 문서와 공식 검사기 | 실행기와 작업맥락 문서 모두 |
| `cli-discovery` (수용) | 설치된 Codex·Claude의 새 세션 기동, 모델·노력 인자, 한도 신호와 해제 시각에 대한 근거 및 미확인 사항. 제품 변경 없는 조사 | CLI 어댑터와 운영 안내 |
| `cli-adapter` (수용, 보완 완료) | 새 CLI argv 생성, 끝난 로그의 한도 신호·해제 시각 해석. runner에서 공급자 접두 계약을 맞춤 | 실행기에서 세션 기동과 파견 대기를 연결 |
| `session-contexts` (수용) | 공통요소 `common.md`와 `plan.md`, `research.md`, `review.md` 작업공통요소. 공개 계약을 실제 연구·계획·독립 검토 판단으로 연결 | 실행기의 세 층 작업맥락 전달과 후속 SKILL 안내 |
| `runner` (수용) | 프로토콜의 모델 표기와 CLI 어댑터 정합성, 실행기·사용자 명령·상태 읽기·Git 반영, 작은 가짜 세션 흐름 확인 | SKILL 안내와 실제 혼합 완주 |
| `skill-entry` (수용) | SKILL.md의 시작·조회·정지·입력·세션 종료·재기동 안내, 실행기와 작업맥락 문서의 연결 확인 및 소규모 문서 보완 | 실제 혼합 완주의 사용자 진입점 |
| `mixed-completion` (수용) | 실제 Codex·Claude 혼합 인스턴스의 작은 Lean 목표 무인 완주, Windows 상태 교체 결함 수정과 새 인스턴스 완주 | 최종 review의 실제 사용 근거 |
| `final-review` (수용) | 수용된 전체 구현·문서·실제 완주를 사용자 요구와 양방향 대조해 합격 판단. 필수 수정 없음 | manager의 개발 완료 판단 |

배정 원문은 `tasks/<task>/objective.md`다. 기존 배정은 유지하며 새 task는 필요하지 않다. 이번 inbox에 실행 중 task는 없고 모든 task를 수용했다. `final-review`는 mixed-completion에 의존하며 그 선행 사슬이 수용된 모든 work를 포함한다. OfNat 표기 설명의 선택적 보완은 현재 목표와 제품 사용을 막지 않으므로 필수 후속 작업으로 만들지 않는다. 이미 충분한 시험·혼합 연구는 반복하지 않았다. `.agents` 사본 작성은 개발 범위 밖의 별도 절차다.

## 결과물과 남은 작업

### 1. 산출 프로토콜과 공식 검사 스크립트 (수용)

다른 결과물이 소비할 다음 다섯 가지 계약을 `protocol-checker`가 구현했다.

- 연구 인스턴스 폴더의 구조
- 축적 지식의 저장 구조, 그리고 기존 기록을 대신하는 새 기록이 있을 때 무엇을 현재 내용으로 읽는지의 규칙(`context.md` 3절)
- 계획·연구·검토 범주마다 세션이 낼 산출의 분류 형식
- 계획이 과제·검토 요청·목표 검토 요청·외부 입력 대기를 게시하는 형식
- 그 형식들의 준수를 확인하는 공식 검사 스크립트

검사 범위는 `context.md` 3절이 정한 구조와 참조 실재다. 세션과 실행기는 `python <skill>/check.py <session-dir>`를 같이 사용한다. 수용된 형식과 API는 `seams.md` 1~6절에 기록했다. 실행기 연결도 runner에서 수용했다.

### 2. 실행기 (수용)

`runner`에서 실행기와 운영 계약을 구현했고 모델 표기 보완을 마쳤다. 명령과 상태 읽기 계약은 seams 7절, CLI API는 8절에 있다. 수용한 기능은 다음과 같다.

- `context.md` 4절의 정해진 흐름을 따른다.
- `context.md` 4절의 불변식 열 가지를 지킨다.
- Codex CLI와 Claude CLI로 세션을 띄운다.
- 끝난 세션의 공급자 한도 신호를 감지하면 새 세션을 띄우지 않고 기다린다. CLI가 해제 시각을 알려 주면 그 시각까지, 알려 주지 않으면 설정한 간격만큼 기다린 뒤 흐름을 재개한다(`context.md` 4절). 각 CLI의 한도 신호는 실제 CLI의 문서, 출력, 동작에서 확인해 정한다.
- 대화와 수명이 분리된 독립 프로세스로 기동된다. Windows에서 쓸 기동 방법을 포함한다.
- 사용자의 정지 표시와 입력을 받는다.

### 3. 작업맥락 문서와 SKILL.md (수용)

작업맥락 네 문서는 `session-contexts`, 사용자 진입점과 연결 보완은 `skill-entry`로 수용했다. `SKILL.md` 명령 안내는 실제 실행기 명령 체계를 따르며, 계획의 미완료 요청·실패 원 요청 읽기와 기동 프롬프트의 문서 전달을 정적으로 확인했다. 실제 모델의 정상 계획·연구·검토 수행은 mixed-completion의 작은 목표에서 확인했다. 실패 환류 등 다른 경로는 기존 가짜 시험과 정적 근거의 범위다.

- **공통요소 문서**: do-math의 목적과 판단 원리, 산출 프로토콜, 공식 검사 스크립트 사용법. 모든 세션이 받는다.
- **작업공통요소 문서 셋**: 계획, 연구, 검토 범주마다 하나씩이다. 각 범주의 세션이 무엇을 판단하고, 축적 지식을 어떻게 읽고, 무엇을 어떤 형식으로 내는지 설명한다. 계획 문서에는 같은 기존 기록을 대신하는 과제 둘을 동시에 배정하지 않는다는 지시가 들어간다(`context.md` 3절).
- **SKILL.md**: 사용자 대화가 이 스킬을 부를 때 읽는 진입 문서다. 담을 내용은 다음과 같다.
  - 새 연구의 시작: 목표 받기, 인스턴스 폴더 만들기, 실행기의 독립 기동과 확인
  - 진행 상황 조회
  - 정지 표시를 놓고 거두는 방법
  - 입력 넣기와, 외부 입력 대기를 풀 때 사용자가 할 일
  - 끝나지 않고 멈춰 버린 세션 하나의 프로세스를 끝내는 방법(정지 표시와는 별개)
  - 실행기를 다시 띄우는 방법

이 문서들은 세션이 판단하고 행동하는 데 쓰는 글이다. 이 개발의 대화를 모르는 세션이 그 문서와 자기 작업특정요소(`context.md` 4절, 그 세션 하나에만 해당하는 지시나 대상)만으로 작성자가 뜻한 대로 읽을 수 있게 쓴다.

### 4. 가짜 세션 흐름 시험 (수용)

실행기 구현을 맡은 `runner`에서 함께 수행했다. 가짜 프로세스·공식 검사기·Git의 흐름 시험 6개와 모델 표기 보완을 포함한 어댑터 시험 8개 통과를 보고했고 manager가 코드와 근거를 확인했다. 시험은 정해진 산출을 내는 가짜 세션과 임시 작업맥락 문서를 사용했다. 실제 제품 문서의 판단 내용은 session-contexts 수용 때 읽었고, 실제 모델에게 전달된 정상 흐름의 수행은 아래 혼합 완주에서 확인했다. 가짜 흐름에서 확인한 성질은 다음과 같다.

- 시작부터 완료까지 흐름이 이어진다. 계획에서 연구, 검토, 다시 계획으로 가고, 목표 검토를 거쳐 완료된다.
- 세션 실패가 다음 계획에 넘어간다.
- 정지 표시가 새 세션을 막는다.
- 사용자 입력이 외부 입력 대기를 푼다.
- 공급자 한도 신호가 파견을 멈춘다.

이 확인은 실제 모델 접근·Lean 컴파일·실제 계정 한도 발생의 근거가 아니다.

### 5. 실제 세션 완주 (수용)

`mixed-completion`의 수정 후 새 인스턴스가 Codex 계획·연구·다음 계획, Claude 연구 검토·목표 검토의 5세션으로 무인 완주했다. 0을 포함한 모든 Nat의 n + 0 = n에 대한 Lean 증명·해설과 별도의 목표 achieved 판정이 공개됐고, 다섯 세션 모두 검사·Git 반영·종료했다. 첫 실패 인스턴스와 Windows 교체 수정은 완료 근거와 구분돼 있다. 실제 인스턴스·모델·명령·공개 근거·한계는 `tasks/mixed-completion/evidence.md`에서 찾는다. manager는 본문과 근거를 대조해 수용했으며 직접 시험·Lean 실행을 반복하지 않았다.

### 6. 최종 review (수용)

`final-review`가 1~5번이 모두 반영된 사본에서 사용자 원문→필수 요구→제품의 누락 대조와 제품→실제 코드·공개 근거의 정확성 대조를 마쳤다. SKILL 사용자 진입점과 실제 세션 input.json에서 후속 독자가 필요한 의미를 회수할 수 있고, 작은 목표의 공개 해설·Lean·독립 연구 검토·목표 achieved 및 실행/Git 근거가 충분하다고 판단했다. 구체적 읽기 경로와 요구별 판정은 `tasks/final-review/review.md`에 있다. manager가 합격 판단을 수용했으며 필수 수정·미해결 작업·실행 중 task가 없어 완료를 게시한다. Linux·재부팅·실측 한도·장기 연구·다른 Lean 판본은 승인된 완료 기준 밖의 미확인 한계로 유지한다.
