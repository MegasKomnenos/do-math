## 변경을 수용한 이유

정본6파일의 base/제출판 diff를 읽고 변경이 의존하는 실제 제공자와 호출 순서를 대조했다. integration.split_research는 revision_targets가 없는 일반 task research만 분할한다. revisions.submission_errors는 변경 대상을 사전 선언하게 하며 revision_resolutions의 정확 coverage를 검사한다. planning 전용 task_dispositions와 integration.inspect_bundles의 단일 judgment 계약을 함께 보면 유효한 mutation과 독립 수용이 섞인 impact 결과는 지원되지 않는다. _hold_impact_reviews의 중복 필터 제거를 수용하며 초기 mixed fixture를 요구로 승격하지 않는다.

integration.bundle_impact_request는 실제 mutation root에서 plans.bundle을 만든다. currentness를 통과한 task/knowledge 대상과 종속 집합의 부재는 다른 조건이다. _apply_bundle_candidate의 빈 plans 분기 제거와 실제 봉인 preparation의 계약 교체·revision/history·수용 결과·저장 integration receipt 단언은 이 계약과 맞는다. _hold_unreadable_impact_submission의 stage+producer 조건은 유지됐으며 새 직접 검사는 두 등록 producer 중 손상된 원 생산자의 pending만 정리하고 다른 pending과 일반 maintenance를 보존한다. 이는 helper 소비 범위의 근거이며 두 생산자의 공개 운전 전체를 인증하지 않는다.

call_engine._prepare_call의 source_refs는 task.inputs 또는 target knowledge.source_basis에서 온다. decision_engine._validate_decision_acceptance와 같은 집합이라고 가정하지 않고 source currentness를 유지한 판단을 수용한다. governance._install_record는 같은 revision 숫자로 새 charter를 설치할 수 있으므로 academic 요구 hash도 유지한다. 추가 grant의 현재 scope/철회/만료는 실행 grant와 별도로 검사한다. inspect_bundles의 발급 authority 제한과 불변 decision 생산 계약에 따른 decision 소실 중복 조건만 제거했다. 외부 Git/artifact 오류를 불가능한 내부 상태로 취급하지 않았다.

_apply의 계약 검토 재비교는 바로 앞 _validate_decision_acceptance가 execution.contract_sha256 및 capture_task_basis를 검사한다는 호출 순서로 대체된다. _prepare_call은 unscoped identity_review를 cycle 생성으로 처리하고 모델 호출을 하지 않는다. 닫힌 모델 역할 dispatch의 마지막 maintenance와 이 admitted cycle 전제에 따른 조건 축소를 수용한다. 기존 preparation의 미완료 status·저자 formal 환경·조건 결박/평가·순환과 후속 kind 검사는 남았다. _apply_plan의 발급 artifact/ready population guard도 보존됐고 AST는 base와 같다.

private insight 검사는 실제 source 제어와 등록된 review reply를 사용해 원 author/input_snapshot·source hash·use_suspended·저장 내용을 확인한다. 현재 새 insight의 kind 철회는 정확 ValueError와 무변경을 확인한다. ## 직접 확인한 범위와 한계

원 결과는 apply-contracts passed2/error1/failed1, final-owners passed2/error1, impact passed1/failed1, mixed-native failed1, origin-and-mixed error1/failed1, origin-author error1, origin-lifecycle error1, origin-registered error1, origin-owner passed1이다. 원 trace의 source scene ID/created_at/종료증거/author/title/정확 owner 누락과 mixed 준비 실패를 실제 제품결함 재현과 구분한다. 마지막 origin-owner는 successful=true다. 모든 부분gate·최상위passed·closing_eligible=false이고 관측exit1이며, 서로 다른 부분판을 합쳐 전체성공으로 만들지 않는다. manager 제품시험/실호출은0회다.
