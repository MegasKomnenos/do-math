# 변이 실행의 병렬화와 반복 비용을 검토하고 실익 있는 개선을 구현한다

현재 약1,645개 비trivial 함수의 G6를 한 child씩 순차 실행하면 비용이 크다. 사용자가 실제 전체 실행을 중지하고 별도 작업에서 개선을 먼저 검토·구현하라고 지시했다. 목적은 기존 포착·정상 기준·오류 의미를 유지하면서 실제 실행 시간을 줄이는 것이다. 분석만으로 다음 구현 task를 또 만드는 대신, 타당한 개선의 구현과 필요한 확인까지 이 작업에서 마친다.

SESSION_JSON, task.json, inputs/context.md·plan.md·seams.md 및 sources/mutation-parallel-direction-2026-10-16.md를 읽는다. 원 g6-run의 완료되지 않은 준비·b01 출력과 기존 mutation.py·직접 시험·g6-inputs의 population/execution-plan은 읽기 자료다. 공용소스와 다른task는 수정하지 않고 자기workspace에서 작업한다.

## 판단과 구현

1. mutation.py의 실제 child 실행·정상 기준 memo·cheap-first/failfast·오류 처리·pseudo_tested 읽기/쓰기와 중단된 b01의 현재 비용을 확인한다. 변이체는 별도 파일·자식에 있으므로 '원소스를 공유 수정해야 한다'는 가정으로 순차성을 정당화하지 않는다. 한 실행기 안의 제한된 병렬 실행, 분리된 묶음 결과와 단일 통합 등 가능한 방식 중 효과와 구현·운영 비용이 맞는 가장 단순한 방법을 선택한다. 관측되지 않은 예상 속도를 성능 향상으로 보고하지 않는다.
2. 적절한 병렬 실행과 결과 통합을 기존 도구에 구현한다. 현재 총시험worker 한도3 안에서 실제 mutant/normal child의 동시 실행을 제한하고 작업 종료·실패 시 자식이 유실되지 않게 한다. 별도 장기 실행 서비스·스케줄러·범용 framework를 만들지 않는다. Python의 선택/함수 순회 자체보다 실제 child 실행 비용에 집중한다. 구체적 옵션/API와 기본값은 현재 호출부·기존 검증을 고려해 작업자가 정한다.
3. 각 mutant·attempt·정상 기준의 파일/ID/결과를 구별하고 listing은 단일 작성 또는 명시 병합으로 갱신한다. 다른 결과를 덮거나 기존 동등 사유를 잃지 않게 한다. 동일 판본/동일 선택의 정상 기준은 가능한 범위에서 재사용하고, 공유 캐시 경합을 피하려고 전체 검사를 중복 실행하지 않는다. 정상 기준 실패·결과 부재·load 오류·skip/0건·명시 중단은 killed로 바꾸지 않는다. 기존 판정 의미와 선택의 합집합·failfast·불필요 정상 전건 실행 금지를 유지한다. 시간 경과에 따른 강제종료는 추가하지 않는다.
4. 실행 개선에 필요한 CLI/API/호출부·직접 시험·짧은 사용 설명·공식 미러를 같은 변경으로 마친다. 개선의 결과 형식과 후속 G6 호출 방법, 최대 동시 child 수, 실패/중단 후 재개·증거 보존 범위를 명확히 남긴다. 기존 g6-run 배정이나 공용 queue를 직접 바꾸지 않는다.

## 가장 적은 검증과 종료

기존 unit.test_mutation 및 boundary.test_mutation_baseline의 필요한 사례를 우선 재사용한다. 작은 고정 입력에서 실제 child의 순차/병렬 결과와 정상기준 연결·누락/중복·독립 출력·listing 보존, 동시 실행 상한을 확인한다. 효과를 판단할 수 있는 작은 실제 실행의 시간/중첩 관측을 남긴다. 임의의 속도 향상 배율을 합격 기준으로 만들지 않는다. 새로운 시험·도우미는 기존 것으로 확인할 수 없는 변경 성질에 필요한 만큼만 추가하며, 시험 개수나 분기 수를 목표로 삼지 않는다.

전체1,645함수 G6나 전체일반/T3/T4/T5를 성능 검증으로 돌리지 않는다. 수십 묶음의 새 성능 캠페인이나 역사감사를 만들지 않는다. 효과가 없거나 더 단순한 비용 개선이 낫다면 실제 근거를 제시하고 그 선택을 구현·확인한다. 범위 밖 장애가 있으면 최소 입력과 정확한 후속을 보고하며 전체 G6를 임의로 먼저 재개하지 않는다.

완료는 실행 비용 개선의 실제 구현, 기존 판정 보존의 필요한 확인, 후속 G6의 구체적 실행 방법이 갖춰진 상태다. report.json에 선택 이유·변경·실제 검증·비용·한계·후속 사용을 기록하고 공식 report 검사를 통과한다. manager가 수용한 뒤 새 G6 task가 개선판을 소비한다. 전체 개발/G6 완료를 주장하지 않는다.
