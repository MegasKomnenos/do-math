# 역할 전체와 단계 인계의 현행 평가 및 구현 설계

## 맡은 결과

context.md R1~R3의 목적은 do-math가 실제 수학 연구를 수행하고 결과를 다음 판단으로 잇게 하는 것이다. 각 역할의 현행 계약을 전체 작업에서 평가하고, 역할·개정 예외·운영 질문이 공유하는 책임과 상태 전이를 후속 구현자가 서로 다르게 발명하지 않도록 완결된 설계를 제공한다. 단순 결함 목록이나 이번 scholarly 사례의 재서술로 끝내지 않는다.

이 task는 필요한 공통 설계를 제공하는 조사·설계 작업이다. 제품 문서와 코드의 현행 계약을 따로 바꾸지 않는다. 결과는 `docs/do-math/flow-repair-20261021/role-flow-design.md`에 작성한다. manager가 설계를 수용하고 seams를 갱신한 뒤 관련 코드·스키마·문서 수정과 검증을 구현 task에 함께 배정한다. 조사 완료를 R1~R3 제품 완료라고 보고하지 않는다.

## 실제 읽기와 판단 범위

자기 inputs의 공용 문서, 정본 AGENTS.md, `scripts/이음새-정본.md`를 읽는다. context의 `user-messages.md` 원문을 함께 읽어 최신 정정을 보존한다. SKILL.md 읽기 대응표와 `contracts.ROLES`, `reading_map`, `prompt_documents`, 실제 action 생산 및 응답 소비 코드를 대조한다. 후보 준비·연구 계획·연구 수행·작업 계약 검토·동일성 검토·목표 감사·보충 조사·운영 점검·의도 해석·유지보수와 독립 운영/설치 복구의 실제 모집단을 완성한다. 각 역할의 목적·책임·판단 범위·재량·입력·출력·다른 역할과의 관계, 유지/수정 판단과 근거를 표 또는 연결된 설명으로 남긴다.

요청 생산→배정→검사→적용→완료/예외/대기/후속 소비를 실제 파일과 심볼로 연결한다. 계약 개정 외의 중요한 단계 연결도 조사하며 필수 대응 형식은 목적·효과에 따라 유지/축소/변경 이유를 판단한다. 모든 요청에 새 재심사를 요구하지 않는다. 사용자 목표·권한과 AI가 만든 개별 요청의 처분 재량을 구별한다.

원자료는 `C:\math\research\parking-unimodality-audit-2026-10-21\원인-분석.md`, `C:\math\.skill-workspace\parking-unimodality-20261021\audit\` 및 work/runs의 보존 입력·응답이다. 감사 보고를 안내로 쓰고 판단에 필요한 원문·코드를 확인한다. 실행/감사 자료는 읽기 전용이다. scholarly의 실제 미노출이나 모델 심리를 확인 사실로 만들지 않는다.

## 설계가 반드시 정할 의미

1. 계약 검토자는 수행 가능한 계약인지 판단한다. 문제를 전달하기 전에 지적 자체의 타당성·오독·전제·자료 확인을 점검하고 문제와 작업 영향을 설명한다. 수행 착수 후 확인할 도구 동작을 검토의 사전 입증 의무로 바꾸지 않도록 책임을 정한다. 이미 타당한 계약은 유지한다.
2. 정상 요청 처리는 유지하면서, 잘못된 전제/실제 수정할 내용 없음 등의 예외를 이유와 근거로 종결할 처분을 정한다. 현재 `revisions.validate_extensions`, `RevisionEngineMixin._apply_revision_followup`, `planning.revision_required/task_ready`, core_engine의 계약 검토 적용과 연결해 정확한 생산·검사·적용·과제 승인·개정 의무·waiting_actions·재계획 효과를 정의한다. 처분 이름만 추가하거나, 원 검토를 무근거 자동 승인하거나, 같은 필수 개정을 즉시 재생성하는 설계는 불충분하다. 재검토가 필요하면 누가 무엇을 근거로 어떤 새 판단을 하는지와 반복 방지까지 정한다.
3. 운영 질문은 `questions.link/close`, `QuestionEngineMixin`, 운영 점검/maintenance 배정 경로를 사용해 등록→안정된 요청→담당 action→execution→근거 있는 처분→질문 해소/대기/다른 담당→영향 받은 후속 업무로 연결한다. 소유자 문자열을 배정으로 보지 않는다. 같은 의무의 중복 전달/재시작, 아직 안 끝난 담당 실행, 자료 부족·사용자 결정·기술 수리·문제 없음, 사용자 정지와 실행 권한의 의미를 정의한다. 정지 해제 없이 연구를 재개하지 않는다.

공용 seams의 첫 경계는 출발점이다. 최종 제안에는 변경할 필드/enum/함수의 정확한 이름·위치·입출력·오류/상태 의미, 전후 전이 예시, 고쳐야 할 생산자·소비자·스키마·역할 문서·시험, 구현 작업 간 실제 선행관계와 독립 writes 후보를 포함한다. 대안 나열만 남기지 말고 구현 가능한 한 설계를 이유와 함께 권고한다. 후속 구현이 발견할 단순 세부 선택과 아직 외부 사실이 없어 결정할 수 없는 사항을 구별한다.

## 검증과 반환

설계 근거는 코드 정적 추적과 기존 증거로 충분한 부분은 거기서 끝낸다. 상태의 실제 의미가 불분명한 부분만 자기 workspace와 새 임시 자료에서 작은 호출로 확인한다. 전체 시험·새 연구 운전·graphify 갱신은 하지 않는다. 제품 수정이 없어 미러 생성은 필요 없다. report.json에는 검토한 역할/연결 모집단, 유지/수정 판단, 실제 확인 범위와 미확정 사실, 설계 문서 경로를 기록하고 서비스 report 검사를 수행한다. 영구 증거는 자기 task의 evidence에 남긴다.
