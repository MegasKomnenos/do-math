# 새 주차 함수 연구 실행의 원인 분석

대상은 새 인스턴스 `RI-01M5CYJ41RWYDQV0VCHMKTBR0N`이다. 2026년 10월 21일 초기화부터 사용자의 정지 요청까지 조사했다. 아래 시각은 모두 한국 표준시다. 연구는 `paused`이고 HOLD가 적용돼 있다. 이 조사에서 연구를 재개하거나 설치 코드·연구 원장을 수정하지 않았다.

**연구가 시작되지 못한 직접 원인은 세 단계의 결합이다.** 문헌조사 계약 검토자가 scholarly 지원을 미확정으로 판정했다. 실행기는 이 판정을 계약의 필수 개정 의무로 바꿨다. 후보 준비와 연구 계획은 운영 담당의 확인을 기다렸지만, 그 확인을 맡을 실행은 생성되지 않았다. 나머지 두 과제는 문헌조사 완료를 필수조건으로 갖고 있었으므로 함께 막혔다.

그 과정에서 별개의 구현 결함도 발생했다. 첫 보류 응답에 빠진 해시를 사전 검사가 놓쳤고, 적용 검사는 이를 실제 전제 변경과 같은 종류로 분류했다. 그 결과 추가 모델 실행이 열렸다. 추가 실행은 해시를 보완했지만, 도구 이름 다섯 개와 “도구가 노출되지 않았다”는 결론을 같은 보고서에 기록했다.

이 인과관계는 원장·실제 호출·코드와 보존 입력의 재실행으로 확인했다. 다만 **최초 모델이 왜 도구가 안 보인다고 인식했는지, 후속 모델이 내부적으로 왜 모순을 놓쳤는지까지 확정한 것은 아니다.** 당시 공급자가 모델에 제시한 도구 목록 원본은 이번 보존 자료에서 확보하지 못했다. 이 한계를 “지연 로딩 때문”, “모델이 겁을 먹어서”, “서버 장애 때문” 같은 추정으로 메우지 않는다.

**1. 조사 범위와 증거의 강도**

정지 뒤 고정된 Git snapshot은 `811c4576af7fc8a5054181ad0208db42ddd329c6`이다. 공개 조회 명령으로 기록 489건 전부를 회수했고, 같은 snapshot의 연구·실행 파일을 내보냈다. 내부 실행 12건, 모델 실행 11건의 CLI 로그·최종 응답·입력·산출·검사 결과를 대조했다. 기동 시 동결된 설치 manifest와 현재 설치 파일 291개를 해시로 비교했으며 차이가 없었다. 따라서 아래에서 조사한 코드가 당시 설치 코드와 달랐다는 정황은 없다.

증거는 다음과 같이 구별한다.

| 증거 | 이 보고서에서 인정하는 범위 |
|---|---|
| 원장의 실행·과제·질문·대기 기록 | 실제로 저장·적용된 상태와 전이 |
| CLI의 완료된 MCP 호출과 응답 | 그 실행의 그 호출이 반환한 결과 |

| 원래 함수에 보존 입력을 넣은 격리 재현 | 명시한 함수와 입력 범위에서 같은 오류·분류가 재현됨 |

재현은 메모리상의 사본 및 별도 감사 폴더에서 수행했다. 모델의 증명 작업, scholarly 검색, 원장의 수정은 수행하지 않았다. **3. scholarly 문제는 어디에서 시작됐는가**

E04의 CLI 로그에는 `scholarly.list_sources({})`가 완료되어 `status=ok`를 반환한 기록이 있다. E12에서도 같은 호출과 `describe_source({"source":"arxiv"})`가 성공했다. **실제 scholarly 호출은 이 세 건이고 모두 성공했다.** 검색·원문 회수·추출 호출은 없으므로 그 기능까지 성공했다고 확대하지 않는다. [호출 전건](../../.skill-workspace/parking-unimodality-20261021/audit/mcp-calls.json)

E05의 판단은 달랐다. 검토자는 현재 자기 실행에서 도구가 노출되지 않았다고 보고했고, 지정된 향후 `research_work` 프로필에서 도구가 실제 노출·사용됨을 확인할 근거를 요구했다. 서버 경로가 설정돼 있다는 것과 호출이 성공했다는 것을 구별한 점 자체는 맞다. 그러나 당시 자료로 확인한 것은 “검토자가 성공 근거를 확보하지 못했다”는 것이지, “서버가 없거나 연결이 실패했다”는 것이 아니었다. E05에는 scholarly 호출 실패가 한 건도 없다. 애초에 scholarly를 호출하지 않았다.

여기에는 추가로 확인할 사실이 있다. E05의 입력 `record_index`에는 E04의 실행 ID `EX-01M5CZCPZ17BXEM98HYMJ98B28`가 포함돼 있었다. 즉, 최초 호출 성공 근거가 저장돼 있었고 그 실행 기록을 읽을 경로도 지급됐다. 그런데 E05의 사용 근거와 명령 기록에서는 그 성공 기록을 회수한 흔적을 찾지 못했다. 성공 파일이 E05의 입력 사본에 자동으로 들어 있지는 않았지만, 독립성 때문에 E04의 공개 기록 자체가 차단된 상태도 아니었다.

그렇다고 E04에서 성공했다는 사실만으로 모든 후속 프로필의 동작이 보장되는 것은 아니다. 확정할 수 있는 결론은 다음 두 가지다.

- 이 연구 설치에서 scholarly가 실제로 존재하고 적어도 두 실행에서 동작했다.
- E05의 부정적 판단은 실제 연결 실패의 반환값으로 입증되지 않았다.

**최초의 “노출되지 않았다”라는 인식이 생긴 더 깊은 원인은 미확정이다.** 당시 도구 목록의 공급자 원본이나 도구 검색의 완전한 기계 결과가 없기 때문이다. 모델이 작성한 빈 목록만으로 일시적 미노출, 검색 방법의 오류, 모델의 누락 중 하나를 고를 수 없다. 앞선 답변에서 이를 단순히 서버 문제가 아니라고 모든 실행에 걸쳐 단정한 표현은 너무 강했다.

**4. 도구 지원의 불확실성이 왜 연구 전체의 정지로 바뀌었는가**

먼저 E05는 `tools_authority_profiles` 항목만 `unresolved`로 판정하고 `next_owner=operations`를 적었다. 같은 응답의 `question_routes`에는 운영 담당 소유의 차단 질문을 넣었다. 이 단계에서 생긴 질문은 `QU-01M5D0VQP53C91FEK45B0YV15C`다.

이 응답을 받은 실행기의 실제 분기는 다음과 같다.

```text
계약 검토 전체 판정이 approved가 아님
  → task.revision_requested 설정
  → task.waiting.kind = contract_revision
  → next_owner = research_preparation
  → 후보 준비 실행 요청 생성
```

`core_engine.py`의 이 분기는 `revision_required`와 `unresolved`를 모두 같은 개정 경로로 보낸다. 개별 항목이 `next_owner=operations`라고 했더라도, 이 분기에서는 그것을 사용해 운영 진단을 배정하지 않는다. 따라서 **“계약 문면의 결함은 확인하지 못했고 도구 지원을 확인해야 한다”는 판정이 “새 계약 판본이 필요한 필수 개정”으로 바뀌었다.** [적용 코드](../../.agents/skills/do-math/scripts/do_math/core_engine.py:3344)

후속 E10·E11은 이 입력을 받았다. 계약의 질문·범위·완료 의무를 바꿀 이유가 없다고 판단했다. 그러나 실행기의 검사 규칙은 필수 개정으로 지정된 대상을 `unchanged`, 즉 “변경할 필요 없음”으로 종료하는 것을 금지한다. 따라서 “계약은 그대로 두고 도구 확인을 기다린다”는 `deferred` 응답을 제출했고, 실행기는 대기 의무를 보존했다. 실제 문면 결함 없이 개정 요청을 받은 후보 준비가 이 경로에서 막혔다. [필수 개정 검사](../../.agents/skills/do-math/scripts/do_math/revisions.py:87)

한편 **운영 질문의 소유자 지정은 작업 배정과 다른 기능**이었다. `QuestionEngineMixin._record_output_questions()`는 질문의 소유자·대상·차단 여부를 저장하지만 `_enqueue()`를 호출하지 않는다. 이 함수에 실제 E05의 질문과 확장을 넣어 재실행하면 운영 질문은 생기고 큐는 빈 채로 남는다. [질문 기록 코드](../../.agents/skills/do-math/scripts/do_math/question_engine.py:53), [재현 결과의 `operations_question_routing`](../../.skill-workspace/parking-unimodality-20261021/audit/reproduction-results.json)

실제 전체 원장도 이 결과와 일치한다. 운영 점검 E08·E09는 각각 00:53·00:56에 시작됐고, E05의 질문이 접수된 것은 01:03 이후다. 두 점검의 발동 원인은 `periodic_review_due`이며 scholarly 질문이 아니다. 질문 생성 뒤에는 이를 대상으로 한 `operational_review`나 `maintenance` 실행이 없다.

E12가 성공 호출을 새로 확보했을 때도 대기는 풀리지 않았다. 이유는 두 가지로 확인된다.

1. 운영 질문의 해소 확장은 `operational_review`와 `maintenance` 역할만 적용할 수 있다. `research_plan`이 해소를 제출하면 `questions.resolution_error()`는 `an operations question requires an operational role`을 반환한다. 이 제한을 실제 함수로 재현했다.
2. E12의 산출은 성공을 설명하는 파일과 보고였고, `dispositions=[]`, `preparation_requests=[]`, `task_assessments=[]`였다. 이 산출에서 실제 수리·해소 실행을 만들 요청이 나오지 않았다. “다음 소유자는 operations”라는 자연어 설명은 배정 요청을 대신하지 않았다.

따라서 막힘은 “사람이 답을 하지 않아서”나 “슬롯이 없어서”가 아니었다. **운영 확인을 요구하는 질문은 만들어졌지만, 이를 수행할 실행으로 연결되지 않았고, 현재 실행 중인 계획자는 직접 닫을 권한도 없었다.** 주기 감독은 모델 없이 실행기의 상태와 시작 조건을 점검하는 기능이며, 이런 의미상의 운영 질문을 자동으로 해결하는 담당이 아니다.

이것은 실행기가 빈 슬롯을 사용하지 못한 자원 오류가 아니다. **모델이 작성한 실제 선행관계가 실행을 차단했다.** 원문 현재성을 먼저 확인하려는 이유는 있으나, 두 후속 과제 모두를 문헌조사 전체 완료에 묶은 선택이 장애의 영향을 세 과제 전체로 넓혔다. 앞으로 계획을 고친다면 기존 자료만으로 먼저 수행할 수 있는 정의·검증 범위가 있는지 판단해야 한다. 이 감사가 그 범위를 확정하거나 계약을 면제·수정한 것은 아니다. **6. 누락된 해시는 정확히 무엇이었고 왜 사전 검사를 통과했는가**

E10은 문헌조사 과제의 개정 의무를 보류하는 응답을 제출했다. 이 응답은 `revision_resolutions`를 포함하므로 기존 대상을 변경하는 편입 묶음으로 취급된다. 어떤 판본을 보고 처분하는지 결박할 `previous_hashes`가 필요하지만 E10은 이를 쓰지 않았다. 이것이 생산자의 실제 누락이다. 여기서 빠진 것은 논문 해시나 Lean 증명 해시가 아니라 **대상 과제의 고정 입력 내용 해시**다.

그런데 로컬 검사와 중앙 접수 검사는 모두 `passed=true`, `issues=[]`였다. 중앙의 봉인 검사 결과도 이를 확인한다. [당시 중앙 검사](../../.skill-workspace/parking-unimodality-20261021/audit/snapshot/runtime/artifacts/BA-01M5D15R4S3XAVNCKWC5TRXQAX/submission/check.json)

사전 검사가 놓친 이유는 다음 코드 연결로 특정됐다.

1. 역할 입력을 만드는 `core_engine.py`는 과제 사본에 `content_sha256`을 추가한다.
2. `context_store.py`는 계획 계열 역할의 검사 문맥을 만들 때 `validation_context['tasks']`를 원장 과제들로 다시 덮어쓴다. 원장 과제에는 이 파생 해시 필드가 없다.
3. `integration.inspect_bundles()`는 그 검사 문맥에서 `expected = ...get("content_sha256")`를 읽는다.
4. 검사는 `if expected and ...`이므로 `expected`가 없으면 `previous_hashes` 검사 자체를 건너뛴다.

실제 E10·E11의 `input/submission/context.json`에 들어 있는 과제 세 건 모두 `content_sha256`이 없었다. 반면 모델이 읽는 과제 상세 파일에는 해시가 있었다. **모델에게 읽히는 입력과 검사기가 사용하는 입력이 이 지점에서 달랐다.** [입력 재작성 코드](../../.agents/skills/do-math/scripts/do_math/context_store.py:807), [조건부 해시 검사](../../.agents/skills/do-math/scripts/do_math/integration.py:453)

이를 원래 함수로 재현했다.

| 재현 입력 | 결과 |
|---|---|
| E10의 실제 응답·확장·검사 문맥 | 오류 없음 |
| 응답은 그대로 두고 검사 문맥의 과제 해시만 복구 | `integration.previous_hash` 오류 |
| 빠진 대상 해시를 응답에도 추가 | 구조 검사 오류 없음 |

이 대조는 다른 입력이나 모델 응답을 바꾸지 않는다. 따라서 **검사 문맥의 해시 누락과 조건부 검사 때문에 생산자 누락을 발견하지 못했다**는 원인은 재현으로 확인됐다.

**7. 왜 “제출 오류”가 “전제 변경”으로 분류됐는가**

사전 검사 다음의 적용 단계에서는 `bundle_impact_request()`가 현재 원장에 있는 변경 대상을 확인한다. 이 함수는 앞의 검사와 달리 필요한 대상 해시의 존재를 무조건 확인한다. E10의 묶음에 해시가 없으므로 다음 `ValueError`가 발생한다.

```text
bundle previous hashes missing for mutation targets
```

문제는 그 예외의 분류다. `apply_bundles()`는 해당 검사 직전 `stage="currentness"`로 설정한다. 그 구간에서 발생한 일반 `ValueError`도 `"integration." + stage`, 즉 `integration.currentness`로 분류한다. 이어 `failure_kind()`는 이 규칙만 있으면 `currentness_changed`, `submission_outcome()`은 `premises_changed`로 반환한다. [필수 해시 검사](../../.agents/skills/do-math/scripts/do_math/integration.py:103), [예외 분류](../../.agents/skills/do-math/scripts/do_math/integration.py:523)

`core_engine.py`는 이 결과를 받으면 일반 출력 수리 대신 `_refresh_changed_decision()`을 호출한다. 그 함수가 E10에 `Decision premises changed; see currentness_changes`를 기록하고, E11을 같은 action의 후속 실행으로 만든다. [후속 경로](../../.agents/skills/do-math/scripts/do_math/core_engine.py:2404), [재실행 생성](../../.agents/skills/do-math/scripts/do_math/decision_engine.py:185)

이 전체 묶음 판정도 보존 입력을 넣어 재현했다. 결과는 `ValueError → integration.currentness → currentness_changed → premises_changed`였고 편입은 한 번도 일어나지 않았다. E10과 E11의 입력에서 대상 과제, 목표 판본, 정책 판본, 통치 문면, 허가, 실행 프로필은 모두 같았다. 따라서 이 사건을 해당 전제가 바뀐 것으로 설명할 근거는 없다.

**두 책임을 나눠야 한다.** 해시를 빠뜨린 것은 생산자 오류다. 그 누락을 놓친 검사 문맥과, 누락 오류를 현재성 변경으로 분류한 것은 실행기 구현의 문제다. E11은 바로 이 잘못 분류된 경로 때문에 추가로 발생했다. 이를 단지 “모델이 이전 해시를 보완했다”라고만 설명하면 중요한 구현 원인을 빠뜨리게 된다.

**8. E11의 자기모순은 어디까지 원인을 확정할 수 있는가**

E11은 이전 응답을 `output=dict(prior)`로 가져오고, `previous_hashes`를 보완하는 코드를 실행했다. 동시에 새로운 `tool-exposure.json`을 작성했다. 그 파일에는 다음 두 내용이 공존한다.

```json
"scholarly_tool_matches": [
  "mcp__scholarly__describe_source",
  "mcp__scholarly__extract",
  "mcp__scholarly__fetch",
  "mcp__scholarly__list_sources",
  "mcp__scholarly__search"
],
"successful_scholarly_calls": 0,
"conclusion": "No scholarly MCP tools are exposed in this session. ..."
```

최종 응답과 체크포인트에도 “도구가 노출되지 않았다”가 남았다. E11의 MCP 호출 기록은 0건이다. [보존된 모순 파일](../../.skill-workspace/parking-unimodality-20261021/audit/snapshot/runtime/artifacts/BA-01M5D19VZHD29T4N3FH0FHG912/files/tool-exposure.json), [응답 작성 명령](../../.skill-workspace/parking-unimodality-20261021/work/runs/EX-01M5D15WHYKST11MJ1JG3CNC47/evidence/stdout.jsonl:18)

관측 가능한 잘못은 명확하다.

- 함수 이름을 발견했다고 적은 기록과 도구가 노출되지 않았다는 결론이 서로 맞지 않는다.
- 호출을 하지 않았다는 사실은 호출 실패나 도구 부재를 입증하지 않는다.
- 보류를 유지하는 기존 처분과 설명은 새 보고서의 도구 목록에 맞춰 수정되지 않았다.

다만 `scholarly_tool_matches` 자체도 모델이 작성한 필드다. **다섯 도구를 실제 자동 탐지한 결과가 새로 들어왔는데 모델이 의도적으로 무시했다**고까지 단정할 기계 기록은 없다. 확정되는 것은 그 모델이 서로 모순된 두 주장을 같은 산출물에 작성했다는 사실과, 실제 호출을 하지 않았다는 사실이다.

이 파일의 내용이 접수됐다고 의미가 검증된 것도 아니다. 일반 산출 파일은 경로·바이트·해시로 보존된다. 검사기는 특정한 구조화 필드의 규칙을 검사하지만, 임의 JSON 보고서의 문장과 목록을 비교해 도구 가용성의 사실 여부를 판단하지 않는다. `tool-exposure.json`을 모순 없이 작성했는지 독립 검토하는 별도 실행도 없었다. 따라서 이 자기모순이 편입 관문에서 걸리지 않은 이유는 **검사 대상의 범위 밖에 있는 자유 서술을 도구 가용성 판단의 근거로 사용했기 때문**이다.

앞선 설명의 “이전 판정에 고착됐다”는 표현은 행동 패턴에 대한 해석이다. 모델 내부의 확정된 원인으로 제시할 수 없다. 확실한 설명은 **현재성 재실행이 이전 산출을 입력으로 받았고, 모델이 이를 토대로 보류를 유지하는 응답을 작성했으며, 그 과정에서 작성한 모순이 검사되지 않았다는 것**이다.

저장된 기록의 일부 내용은 별도 파일에 들어 있다. 기본 기록에는 그 별도 파일을 가리키는 참조가 남는다. 조회할 때 기본 기록들은 한꺼번에 읽지만, 그 안의 참조를 따라 필요한 별도 파일을 복원할 때는 아직 읽지 않은 파일마다 Git을 다시 호출한다. 코드상 경로는 `ResearchRepository._read_documents()` → `_decode_families()` → 별도 내용(payload) 복원 → `read_payload(path)` → `_store.read_bytes()`다. 실제 측정에서 `read_objects()`는 260회 호출됐다. **이 상태의 조회 지연에 다수의 개별 Git 프로세스 호출이 크게 기여한다는 점은 계측과 코드가 일치한다.** [읽기 경로](../../.agents/skills/do-math/scripts/do_math/repository.py:243), [별도 내용 복원](../../.agents/skills/do-math/scripts/do_math/payloads.py:285)

이 측정만으로 모든 실행 지연, 개별 모델 응답 지연 또는 컴퓨터 전체의 성능 원인을 설명할 수는 없다. 다만 사용자가 본 초기 시작·상태 조회가 느렸던 현상을 모델 사고 시간만으로 설명하는 것은 틀리다. 이 I/O 지연은 도구 부재를 입증하지도 않는다.

**11. 실제 사용량과 성과를 구분한다**

11개 모델 실행의 CLI 보고값을 합치면 입력 19,166,493토큰, 그중 캐시 입력 17,594,112토큰, 출력 79,732토큰이다. 추론 출력으로 보고된 12,394토큰은 별도 관측값이며 출력 합계에 다시 더하지 않는다. 입력 합계는 같은 문맥이 여러 호출에서 다시 계산된 값을 포함하므로, 독립 문서 1,916만 토큰을 읽었다는 뜻도 한 번의 문맥 길이도 아니다. 이 값으로 실제 청구액을 환산하지 않았다.

이번 사용량은 초기 해석·계약 준비·검토·운영 점검·보류·계획에 사용됐다. **연구 수행 0건이라는 사실과 함께 읽어야 한다.** 다만 모든 검토가 불필요했다거나 각 구현 문제에 정확히 얼마의 비용이 귀속되는지는 이 합계만으로 확정할 수 없다. 해시 오분류로 E11이라는 추가 실행이 생긴 관계는 확정되지만, 수정 후 시스템 전체가 얼마나 적게 사용했을지는 별도 실행 비교가 필요하다.

**12. 이전 대화에서 정정할 설명**

- “scholarly 연결 문제”라는 표현은 모호했다. 실제 실패 응답이 아니라 일부 역할의 지원 미확정 판정이 연구를 막았다.
- “도구 5개를 발견했다”는 것은 엄밀히는 E11의 자체 보고다. 도구 목록 원본을 독립 관측한 것처럼 표현하면 안 된다.
- “이전 판정에 고착됐다”는 내부 원인을 확정한 설명이 아니다. 확인되는 작성 순서와 모순의 유지, 검사 범위를 설명해야 한다.
- “누락된 해시를 보완하는 후속 실행”이라는 설명만으로는 부족했다. 사전 검사의 해시 필드 누락과 잘못된 현재성 분류가 그 실행을 만든 구체적 원인이다.
- “운영 담당이 다음 소유자다”는 문장으로 실제 담당 실행이 배정됐다고 볼 수 없다. 이 사건에서는 그 연결이 없었다.
- 앞선 11건 집계는 모델 실행 수다. 전체 내부 실행 수는 신뢰 환경 활성화까지 포함해 12건이다.

**13. 원인별 수정·재검증의 경계**

아래는 조사 결과에서 도출되는 수정 대상이다. 이번 감사에서 적용하지 않았다.

| 대상 | 확인해야 할 수정 효과 |
|---|---|
| 계약 검토의 지원 미확정 처리 | 문면 결함과 도구 확인 필요를 구별하고, 후자는 실제 진단 실행으로 이어져야 한다. 계약 개정 의무만 남겨서는 안 된다. |
| 운영 질문의 인계 | 질문 소유자·대상 기록뿐 아니라 요청·배정·종료·해소의 경로를 확인할 수 있어야 한다. |
| 제출 검사 문맥 | 모델에게 지급된 대상 해시와 검사기가 읽는 해시가 일치해야 한다. 해시가 없는 문맥에서 검사를 조용히 건너뛰지 않아야 한다. |
| 제출 오류 분류 | 빠진 필수 필드는 생산자 제출 오류로, 실제 입력·효력의 변경은 현재성 변경으로 구별돼야 한다. 두 경로를 같은 입력 대조로 시험해야 한다. |
| 도구 가용성 주장 | 실제 호출·검색 결과와 모델의 수기 보고를 구별해야 한다. 목록 존재·호출 미수행·호출 실패를 서로 바꾸어 쓰지 않아야 한다. |
| 과제의 선행관계 | 문헌조사 전체 완료가 각 후속 작업의 실제 필수 입력인지 다시 판단해야 한다. |
| 상태 복원 | 동일 snapshot의 무결성 검사를 보존하면서 개별 Git 호출 수를 줄인 효과를 실제 명령으로 비교해야 한다. |

이번 사건의 최초 미노출 인식은 당시 도구 목록 원본이 없어 더 깊은 원인을 확정하지 못했다. 앞으로 비슷한 사건의 원인을 구별하려면 해당 목록·발견 호출·서버 시작 결과를 실행별로 보존해야 한다. 이 보완은 미래 사건의 조사를 위한 것이다. 새 진단이 성공하더라도 이번 과거 실행에서 무엇이 보였는지 소급 증명하지는 못한다.

**이번에 확정한 핵심은 모델의 실수 하나가 아니라, 그 실수를 전체 대기로 확대하고 해소 담당 없이 유지한 실행 경로, 그리고 별도의 제출 검사·오류 분류 결함이다.** 연구는 계속 정지 상태이며, 이 보고서는 수리 완료나 재개 승인을 뜻하지 않는다.
