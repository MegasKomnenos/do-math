# 스킬 저작·검증 방법론

스킬은 읽는 사람(미래의 에이전트)이 없으면 아무것도 아니다. 이 스킬은 스킬 텍스트가 발견되고, 읽히고, 압박 아래서도 지켜지게 만드는 방법론을 담는다.

**핵심 원리**: 스킬 없이 에이전트가 실패하는 것을 직접 보지 않았다면, 그 스킬이 옳은 것을 가르치는지 알 수 없다. 무엇을 가르칠지는 관찰된 실패에서 나온다.

## 관할 지도

- **이 스킬**: 스킬 텍스트의 품질(구조, description, 명명, 예시)과 검증·강건화 방법론. 저작 절차 안에서 참조되는 방법론 층이다.
- **로컬판 skill-creator**: 신규 저작·개선·테스트 실행·description 최적화의 절차와 도구 정본. 절차가 필요하면 그쪽이 우선한다.

## 로컬 저작 접속

스킬 본문은 이 프로젝트의 산문이므로 다음이 적용된다.

- **작문 규칙**: 한국어 본문, name은 영어 kebab-case, em dash 금지, 과잉 설명·재진술 금지, 위계로 간결하게(CLAUDE.md 작문 규칙).
- **위치**: 로컬 스킬은 프로젝트 `.claude/skills/<이름>/`에 둔다.
- **착수 시 기억 확인**: `기억/색인.md` layer-3 절 확인(CLAUDE.md 작업 기억 참조).
- **형식 검증**: 로컬판 skill-creator의 `scripts/quick_validate.py`.
- **커밋**: CLAUDE.md 커밋·푸시 절차(정본: commit-harness)를 따른다. 원본 체크리스트의 fork 푸시·PR 기여 항목은 이 프로젝트에 해당 배포 구조가 없어 이 위임으로 대체되었다.
- **검증용 서브에이전트**: CLAUDE.md 서브에이전트 모델 선택 규칙을 따른다(독립 내용 평가 성격의 검증은 최상위 모델 유지 후보).

## 스킬이란 무엇인가

스킬은 검증된 기법·패턴·도구의 **참조 가이드**다. 미래의 에이전트가 효과적인 접근을 찾아 적용하게 돕는다.

- 스킬인 것: 재사용 가능한 기법, 패턴, 도구, 참조 가이드.
- 스킬이 아닌 것: 문제를 한 번 어떻게 풀었는지의 서사. 1회 사건의 맥락·경위는 스킬이 아니라 memory-harness의 메모리 노드가 담는다.

**본문은 절차만, description은 소개만**: SKILL.md 본문은 그 작업을 하는 절차와 그것만 담는다. 스킬이 왜 생겼는지의 연혁·유래, 검증·배포 이력, 사용자 발언의 경위, 규범이 다른 규범과 충돌하지 않는다는 정당화 서사는 절차가 아니므로 본문에 두지 않는다. 그 "왜"는 커밋 메시지와 기억 그래프(메모리·dream 노드)가 보존한다. description은 그 스킬이 무엇이고 언제 불려야 하는지를 알리는 소개이지 본문의 요약이 아니다. 절차의 상세가 아니라 트리거 판정에 필요한 만큼만 담는다.

## 저작·검증 사이클: 3국면

스킬 저작은 다음 3국면을 돈다(원어 계보의 RED-GREEN-REFACTOR에 대응).

1. **베이스라인 관찰**(RED): 스킬 없이 시나리오를 돌려 에이전트가 실패하는 것을 직접 본다. 어떤 선택을 했는지, 어떤 합리화를 축자로 썼는지 기록한다.
2. **최소 저작**(GREEN): 관찰된 그 실패만 겨냥해 쓴다. 가설적 사례를 위한 내용을 미리 덧붙이지 않는다. 같은 시나리오를 스킬과 함께 다시 돌려 준수를 확인한다.
3. **봉쇄 보강**(REFACTOR): 에이전트가 새 합리화를 찾으면 그 반박을 명시적으로 추가하고, 뚫리지 않을 때까지 재검증한다.

전체 순서가 곧 방법이다: 테스트를 먼저 두고, 실패를 보고, 그 실패를 막는 최소한을 쓴다.

## 언제 스킬로 만드나

**만든다**: 기법이 직관적으로 자명하지 않았을 때, 반복 절차로 다시 참조할 가치가 있을 때. 프로젝트 특화 지식이라도 반복 절차의 정본화 가치가 있으면 로컬 스킬로 만든다.

**만들지 않는다**:
- 1회성 해법(memory-harness 관할).
- 다른 곳에 이미 잘 문서화된 표준 관행.
- 짧은 원칙·전역 규칙 수준의 프로젝트 관례. 이는 스킬이 아니라 CLAUDE.md에 둔다(원칙은 CLAUDE.md, 반복 절차의 정본은 로컬 스킬이라는 이원 배치).
- 기계적 제약. 정규식·검증 스크립트로 강제 가능하면 산문이 아니라 hook·self-test로 자동화한다. 문서는 판단이 필요한 사안에 아껴 쓴다(기계 검증 가능은 자동화, 판단 의존은 판단 장치).

## 스킬 유형

- **Technique**: 따라 할 단계가 있는 구체 기법(verify-rounds의 라운드 절차가 이 유형).
- **Pattern**: 문제를 보는 사고 틀.
- **Reference**: API·문법·도구 문서(memory-harness의 기억 그래프 규격이 이 유형에 가까움).

유형마다 검증 방법이 다르다(아래 "유형별 검증 설계").

## 구조와 파일 조직

구조·분량·리소스 분리의 절차 정본은 로컬판 skill-creator의 "스킬 작성 가이드"다. 요지만 남긴다.

- 무거운 참조(100줄 이상)와 재사용 도구만 별도 파일로 분리하고, 원리·개념·50줄 미만 코드 패턴은 인라인으로 둔다.
- 자기완결형(commit-harness), 도구 동반형(verify-rounds), 참조 동반형(write-for-reader)의 세 패턴이 로컬 전례다.
- 본문 골격의 출발점(변형 허용): 개요(핵심 원리 1~2문장), 언제 쓰나(증상·용례와 쓰지 않을 때), 핵심 패턴(전/후 대비), 빠른 참조(표·목록), 구현(인라인 코드 또는 파일 링크), 흔한 실수(무엇이 잘못되고 어떻게 고치나), 실전 효과(선택). 로컬 스킬 실태에 맞게 절을 더하고 뺀다.

## frontmatter와 description

**frontmatter 규격**: `name`(64자 이내, 영문·숫자·하이픈만)과 `description`(1024자 이내)이 필수다. 공식 지원 키 전체는 스펙 문서를 따르고, 형식 검증은 로컬판 quick_validate로 한다.

**description 저작 규범** (트리거 판정의 일차 표면):

- 하는 일의 요지와 트리거 조건(구체 발화·증상·상황)을 담는다. "~할 때 사용한다" 문형으로 트리거 조건을 명시한다(원어 관례 "Use when..."의 로컬 문형).
- **워크플로 요약의 위험**: description에 절차 시퀀스를 요약하면 에이전트가 본문을 읽지 않고 그 요약만 따라 실행할 수 있다(예: description에 "code review between tasks"로 요약하자 본문 플로차트의 2단계 리뷰 대신 1회만 수행하고, 요약을 지우자 본문을 정상 독해). 로컬 스킬들은 하는 일 요지에 절차 요약을 담는 관례이므로 금지하지는 않되, 절차 요약을 담을 때는 (가) 본문에 단계 게이트·체크포인트 같은 본문 유인 장치가 있는지 확인하고, (나) 본문 개정 시 description 요약을 반드시 동기화한다. 요약과 본문의 어긋남이 이 위험의 발화 조건이다.
- 3인칭으로 쓴다(시스템 프롬프트에 주입되는 표면이므로 인칭 일관성이 필요하다).

**트리거 서술 기법**:

- 구체적인 트리거·증상·상황을 쓴다. 언어·도구 특정 증상보다 문제 자체를 서술한다(스킬 자체가 기술 특정이 아니라면 기술 중립으로. 기술 특정이면 그것을 명시).
- 나쁨: "비동기 테스트용" (추상적, 언제 쓰는지 없음)
- 좋음: "테스트에 경합 조건·타이밍 의존이 있거나 통과·실패가 일관되지 않을 때 사용한다" (문제 서술, 트리거 명확)

**키워드 커버리지**: 미래 에이전트가 검색할 어휘를 문면에 심는다. 오류 메시지, 증상, 동의어, 실제 명령·도구명. 이중 언어 환경이므로 한국어 서술에 원어 핵심 키워드를 병기한다(TDD, pressure scenario 등 원어로 불러도 매칭되도록).

**명명**: 능동태 동사 우선. 무엇을 하는지 또는 핵심 통찰로 이름 짓는다. 로컬 전례는 동사-목적어 kebab-case(verify-rounds, do-math). 모호한 이름(helper, utils)을 피한다.

## 토큰 효율

컨텍스트는 공유 자원이다. 자주 로드되는 스킬일수록 짧아야 한다.

- 로컬 기준은 줄 수 감각으로 관리한다: SKILL.md 500줄 이하, 자주 로드되는 스킬은 그보다 훨씬 짧게. 원본의 영어 단어 수 목표(150/200/500 단어)는 한국어 산출물에 단위가 맞지 않아 참고치로만 둔다(wc 검증도 같은 이유로 쓰지 않는다).
- 압축 기법: ① 도구 플래그 상세는 본문이 아니라 `--help`로 위임, ② 다른 스킬에 있는 내용은 교차 참조(복제 금지), ③ 예시는 최소 형태로 압축, ④ 같은 패턴의 중복 예시·자명한 설명 제거. 이는 CLAUDE.md 과잉 설명 금지·정본 복제 금지(드리프트 방지)와 같은 방향이다.

## 다른 스킬 참조

- 스킬 이름으로만 참조하고 필수성 표지를 단다. 로컬 문형: "정본: X", "관할: X", "상세는 X 스킬".
- `@` 문법으로 파일을 참조하지 않는다. `@`는 즉시 강제 로드라 필요하기 전에 컨텍스트를 태운다. 플랫폼 공통 특성이다.
## 멀티런타임 사본 동기화

스킬 정본은 하나이고 런타임 사본 트리는 생성물이다. 사본을 수기 편집하지 않으며, 정본 수정 후 생성기를 실행해 재생성한다. 구조·규칙·오버레이 운용·절차의 정본: `references/멀티런타임_동기화.md` (생성기: `scripts/build_skill_mirrors.py`, 커밋 결합은 commit-harness 스킬 게이트).

## 다이어그램 (mermaid)

로컬 다이어그램 표기는 mermaid다(렌더러 없이 마크다운 표면에서 읽힌다).

**쓰는 곳** (이 세 경우에만):
- 자명하지 않은 결정점
- 너무 일찍 멈출 수 있는 절차 루프
- "A를 쓸까 B를 쓸까" 판단

**쓰지 않는 곳**: 참조 자료(표·목록으로), 코드 예시(코드블록으로), 선형 절차(번호 목록으로).

**작성 관례**:
- 의미가 도형에 실리게 한다: 질문·결정은 분기 노드(`{...}`), 행동은 처리 노드(`[...]`), 경고·금지는 시각적으로 구별되는 노드로.
- 간선 라벨: 이진 분기는 `-->|yes|`/`-->|no|`, 다지 분기는 조건을 라벨로.
- 명명: 질문은 물음표로 끝내고, 행동은 동사로 시작하고, 명령은 축자로, 상태는 상황 서술로.
- 모호한 라벨 금지: "문제 발생", "고친다", "확인" 같은 라벨은 의미를 전달하지 않는다. "재현이 실패하는가?", "재현 입력을 줄인다"처럼 구체로.

## 코드 예시

하나의 훌륭한 예시가 여러 평범한 예시를 이긴다.

- 언어는 대상에 맞게 고르되 이 프로젝트의 코드 실태는 python 중심이다.
- 좋은 예시: 완결·실행 가능, 왜를 설명하는 주석, **실전에서 온 것**, 패턴이 명확, 각색할 준비가 된 것(빈칸 템플릿이 아니라).
- 하지 않는 것: 다수 언어 중복 구현, 빈칸 채우기 템플릿, 작위적 예시. 모델은 이식에 능하므로 하나면 충분하다.

## 철칙: 검증 없는 배포 금지

```
검증을 거치지 않은 스킬을 배포(배치·커밋)하지 않는다
```

신규 스킬과 기존 스킬의 **수정** 모두에 적용된다. "간단한 추가라서", "한 절만 붙이는 거라서", "문서 갱신일 뿐이라서"는 예외 사유가 아니다.

검증으로 인정되는 형태는 둘이다(스킬 성격에 맞게 택한다):

1. **압박 시나리오 테스트**: 규율(discipline) 스킬에 최적. 상세는 `testing-skills-with-subagents.md`(이 디렉토리).
2. **실전 과제 검증**: 실제 과제 1건을 스킬로 수행해 확인한다.
신규 저작이라면 베이스라인 관찰(스킬 없이 실패 확인)이 선행한다. 무엇을 가르칠지는 관찰된 실패에서 나온다.

**미검증 변경의 처리**: 검증 전에 써 둔 스킬 텍스트가 검증에서 어긋나면 버리고 관찰에서 다시 쓴다. "참조용 보관"도, 검증하면서 "각색"하는 것도 하지 않는다. 버린다는 것은 버린다는 것이다(참조 보관은 사후 합리화로 회귀하는 누수 경로다).

## 유형별 검증 설계

스킬 유형마다 실패 양식이 다르므로 검증도 유형에 맞춘다.

**규율 강제 스킬** (규칙·요구사항. commit-harness의 검증 게이트류):
- 학술 질문(규칙을 이해하는가) + 압박 시나리오(스트레스 아래서 준수하는가) + 복수 압박 결합(시간+매몰비용+소진).
- 합리화를 식별해 명시 반박을 추가한다.
- 성공 기준: 최대 압박 아래서도 규칙을 따른다.

**기법 스킬** (how-to. verify-rounds류):
- 적용 시나리오(기법을 올바로 적용하는가) + 변형 시나리오(경계 사례 처리) + 정보 결손 테스트(지시에 공백이 있는가).
- 성공 기준: 새 시나리오에 기법을 성공적으로 적용한다.

**패턴 스킬** (사고 틀):
- 인식 시나리오(패턴 적용 시점을 알아보는가) + 적용 시나리오 + 반례(적용하지 말아야 할 때를 아는가).
- 성공 기준: 언제·어떻게 적용할지 올바로 식별한다.

**참조 스킬** (문서·API):
- 검색 시나리오(맞는 정보를 찾는가) + 적용 시나리오(찾은 것을 올바로 쓰는가) + 공백 테스트(흔한 용례가 커버되는가).
- 성공 기준: 참조 정보를 찾아 올바로 적용한다.

## 검증 생략의 합리화

| 핑계 | 실제 |
|------|------|
| "스킬이 자명하게 명확하다" | 나에게 명확한 것과 다른 에이전트에게 명확한 것은 별개다. 테스트한다 |
| "그냥 참조 문서다" | 참조에도 공백·불명확 절이 있다. 검색 가능성을 테스트한다 |
| "테스트는 과하다" | 미검증 스킬에는 언제나 문제가 있다. 15분의 테스트가 몇 시간을 아낀다 |
| "문제 생기면 그때 테스트" | 문제가 생겼다는 것은 에이전트가 스킬을 못 쓴다는 것이다. 배포 전에 테스트한다 |
| "테스트가 번거롭다" | 배포된 나쁜 스킬의 디버깅이 더 번거롭다 |
| "잘 됐다고 확신한다" | 과신은 문제를 보증한다. 그래도 테스트한다 |
| "정독 리뷰로 충분하다" | 읽는 것과 쓰는 것은 다르다. 적용 시나리오를 테스트한다 |
| "테스트할 시간이 없다" | 미검증 배포는 나중에 고치는 시간이 더 든다 |

이 모든 핑계의 답은 하나다: 배포 전에 검증한다. 예외 없음.

## 실패 유형에 형식을 맞춘다

가이드를 쓰기 전에 베이스라인 실패를 분류한다. 한 실패 유형을 막아 주는 형식이 다른 유형에는 역효과를 낸다는 것이 실측되어 있다.

| 베이스라인 실패 | 맞는 형식 | 틀린 형식 |
|---|---|---|
| 압박 아래서 규칙을 건너뛰거나 위반(알면서 함) | 금지 + 합리화 표 + 중단 신호 목록(아래 봉쇄 기법) | 부드러운 권고("가급적...", "고려하라...") |
| 준수는 하는데 출력의 형태가 잘못됨(비대한 프롬프트, 묻힌 결론, 사양 재진술) | 긍정 레시피 또는 계약: 출력이 무엇**인지**를 부분과 순서로 서술 | 금지 목록("재진술하지 마라", "서사하지 마라") |
| 이미 만드는 산출물에서 필수 요소를 누락 | 구조적: 채워 넣는 템플릿에 필수 필드·슬롯 | 템플릿 옆의 산문 상기문 |
| 행동이 조건에 따라 달라져야 함 | 관찰 가능한 술어에 건 조건문("브리프가 존재하면 그것을 참조한다") | 무조건 규칙 + 면제 조항 |

**왜 금지가 형태 문제에 역효과인가**: 경쟁 유인("프롬프트를 자기충족적으로 만들라")이 있을 때 에이전트는 "X 하지 마라"와 협상한다. 금지 조는 레시피 조보다 원치 않는 내용을 더 많이 내는 경향이 실측되어 있다. 자기 사례는 마이크로 테스트로 직접 재라. 다만 기본값으로 금지에 손을 뻗지는 마라. 레시피는 협상할 것을 남기지 않는다: 출력이 명시된 형태에 맞거나 맞지 않거나다.

**어느 형식이든 지킬 규칙**:
- **뉘앙스 조항 금지.** "중요하지 않으면 X 하지 마라"는 협상을 다시 연다. 진짜 예외는 관찰 가능한 술어에 건 독립 조건문으로 표현한다.
- **면제 조항은 스코프가 안 걸린다.** "이 제한은 코드블록에는 적용되지 않는다"라고 써도 코드블록이 억제된다. 출력의 일부가 면제되어야 하면 규칙이 거기 닿지 않게 구조를 바꾼다.

## 합리화 봉쇄 기법 (규율 스킬용)

규율을 강제하는 스킬은 합리화에 저항해야 한다. 에이전트는 영리하고 압박 아래서 허점을 찾는다.

**적용 스코프**: 이 도구 모음은 규율 실패(규칙을 알면서 압박 아래 건너뜀)용이다. 형태 오류·요소 누락에는 금지 기반 봉쇄가 역효과이므로 위 "실패 유형에 형식을 맞춘다"의 형식을 쓴다.

1. **모든 허점을 명시적으로 닫는다**: 규칙만 선언하지 말고 구체 우회로를 각각 금지한다("참조용으로 보관하지 않는다 / 각색하지 않는다 / 들여다보지 않는다 / 버린다는 것은 버린다는 것이다" 식의 명시 열거).
2. **문면 대 정신 논변을 봉쇄한다**: "규칙의 문면을 어기는 것이 곧 규칙의 정신을 어기는 것이다"를 앞부분에 둔다. "정신은 지키고 있다"류 합리화 전체를 차단한다.
3. **합리화 표를 만든다**: 베이스라인 테스트에서 수집한 핑계 전부를 핑계/실제 표로 만든다(위 "검증 생략의 합리화" 표가 그 산출 형태).
4. **중단 신호 목록을 만든다**: 합리화 중임을 자가 감지할 신호를 열거한다("~라는 생각이 들면 멈춘다").
5. **description에 위반 증상을 넣는다**: 규칙을 어기기 직전의 증상을 트리거 조건에 추가한다(위반 직전에 스킬이 로드되도록).

**심리학 기반**: 이 기법들이 왜 작동하는지는 `persuasion-principles.md`(이 디렉토리)의 연구 기반(권위·일관성·희소성·사회적 증명·연대 원리) 참조.

## 3국면 상세와 마이크로 테스트

### 베이스라인 관찰 (RED)

스킬 **없이** 압박 시나리오를 서브에이전트로 돌린다. 정확한 행동을 기록한다: 어떤 선택을 했는가, 어떤 합리화를 축자로 썼는가, 어느 압박이 위반을 촉발했는가. 에이전트가 자연 상태에서 무엇을 하는지 보기 전에는 스킬을 쓸 수 없다.

### 최소 저작 (GREEN)

그 특정 합리화들을 겨냥해 쓴다. 가설적 사례용 내용을 덧붙이지 않는다. 같은 시나리오를 스킬과 함께 재실행해 준수를 확인한다.

### 봉쇄 보강 (REFACTOR)

새 합리화가 나오면 명시 반박을 추가하고 뚫리지 않을 때까지 재검증한다.

### 문구 마이크로 테스트 (전체 시나리오 전에)

전체 압박 시나리오 런은 최종 게이트지만 회당 비용이 크다. 문구 자체는 마이크로 테스트로 먼저 검증한다.

1. **호출당 신선한 컨텍스트 표본 1개**: 단발(single-shot) 서브에이전트로 실행한다(서브에이전트 스폰 시 CLAUDE.md 모델 선택 규칙 적용). 시스템 프롬프트는 그 가이드가 실제로 살 현실적 맥락(가이드만 고립시키지 말고 전체 스킬·프롬프트 템플릿), 사용자 메시지는 실패를 유혹하는 과제.
2. **무가이드 대조군을 반드시 포함한다.** 대조군이 그 실패를 보이지 않으면 고칠 것이 없다. 멈추고, 가이드를 저작하지 않는다.
3. **변형당 5회 이상 반복.** 단일 표본은 거짓말한다.
4. **플래그된 매치를 전부 수동으로 읽는다.** 프로그램 채점을 하더라도, 템플릿 반향과 인용된 반례가 히트로 위장한다. 자동 집계만으로는 실패도 성공도 과대평가된다.
5. **분산이 지표다.** 가이드가 박히면 반복들이 같은 형태로 수렴한다. 5회가 5가지 해석이면 문구가 잡아매지 못하는 것이다. 단어를 더하기 전에 형식을 조인다.

**스코프 한정**: 마이크로 테스트는 문구를 검증한다. 규율 스킬의 압박 시나리오를 대체하지 않는다.

**전체 테스트 방법론**: 압박 시나리오 작성법, 압박 유형(시간·매몰비용·권위·소진 등 7종), 체계적 허점 막기, 메타 테스트 기법은 `testing-skills-with-subagents.md`(이 디렉토리) 참조. 완결 실전 예시는 `examples/CLAUDE_MD_TESTING.md`.

## 안티패턴

- **서사 예시**: "2025-10-03 세션에서 우리는..." 식의 1회 사건 서술. 너무 특정적이라 재사용이 안 된다(그런 맥락은 기억 그래프에).
- **다언어 희석**: example-js.js, example-py.py, example-go.go. 품질이 평범해지고 유지 부담만 는다.
- **플로차트 속 코드**: 복사할 수 없고 읽기 어렵다. 코드는 코드블록에.
- **무의미 라벨**: helper1, step3, pattern4. 라벨은 의미를 실어야 한다.

## 배치 저작 금지

스킬을 하나라도 썼으면 **멈추고 그 스킬의 검증·배포를 완결한다**.

- 각각을 검증하지 않은 채 여러 스킬을 일괄 생성하지 않는다.
- 현재 스킬이 검증되기 전에 다음 스킬로 넘어가지 않는다.
- "일괄이 효율적"이라는 이유로 검증을 건너뛰지 않는다.

일괄 생성은 검증 생략의 우회로가 된다. 스킬 단위의 검증 완결이 규칙이다(아래 체크리스트가 스킬마다 적용된다).

## 저작 체크리스트

다단계 절차이므로 작업 추적 도구(TodoList 류)가 있으면 항목을 등록해 단계 누락을 막는다.

**베이스라인 관찰**:
- [ ] 압박 시나리오 작성(규율 스킬은 3개 이상 압박 결합)
- [ ] 스킬 없이 실행해 베이스라인 행동을 축자 기록
- [ ] 합리화·실패의 패턴 식별

**최소 저작**:
- [ ] name이 영문·숫자·하이픈만 사용(64자 이내)
- [ ] frontmatter에 name·description 필수 필드(description 1024자 이내)
- [ ] description이 "~할 때 사용한다" 문형의 구체 트리거·증상 포함(절차 요약을 담았다면 본문 유인 장치·동기화 확인)
- [ ] 3인칭 서술
- [ ] 검색 키워드가 문면에 배치(오류·증상·도구, 원어 병기)
- [ ] 핵심 원리가 담긴 명확한 개요
- [ ] 베이스라인에서 식별된 특정 실패를 겨냥
- [ ] 가이드 형식이 실패 유형과 매칭("실패 유형에 형식을 맞춘다")
- [ ] 행동 조형 가이드는 무가이드 대조군 상대로 문구 마이크로 테스트(5회 이상, 플래그 전수 수동 독해. 순수 참조 스킬은 해당 없음)
- [ ] 코드는 인라인 또는 별도 파일 링크
- [ ] 우수 예시 하나(다언어 아님)
- [ ] 스킬과 함께 시나리오 재실행으로 준수 확인(또는 검증 2형태 중 해당 형태 수행)

**봉쇄 보강**:
- [ ] 테스트에서 나온 새 합리화 식별
- [ ] (규율 스킬) 명시 반박 추가
- [ ] 전 테스트 회차의 합리화 표 구축
- [ ] 중단 신호 목록 작성
- [ ] 뚫리지 않을 때까지 재검증

**품질**:
- [ ] 플로차트는 자명하지 않은 결정에만
- [ ] 빠른 참조 표
- [ ] 흔한 실수 절
- [ ] 서사 없음
- [ ] 별도 파일은 도구·무거운 참조만

**배포**:
- [ ] 검증 완료 확인 후 배치, 커밋은 CLAUDE.md 커밋·푸시 절차(정본: commit-harness)로

## 발견 흐름 최적화

미래 에이전트가 스킬을 찾는 경로: ① 문제를 만난다("테스트가 불안정하다") ② 스킬을 검색한다(description 훑기) ③ 스킬을 찾는다(description 매칭) ④ 개요를 훑는다(관련 있나) ⑤ 패턴을 읽는다(빠른 참조) ⑥ 예시를 로드한다(구현할 때만).

이 흐름에 맞춰 최적화한다: 검색될 용어를 앞에, 자주.

**공식 상세 가이드**: Anthropic 공식의 스킬 저작 모범 사례 총람은 [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 참조. 간결성, 자유도 설정, progressive disclosure 패턴, 워크플로·피드백 루프, 실행 코드 스킬의 세부(plan-validate-execute 등)를 다룬다. 로컬과 결이 다른 세 지점은 이 SKILL.md가 우선한다: ① description 규범은 위 "frontmatter와 description" 절(공식 가이드의 what+when 병기 쪽이 로컬 정본과 정합), ② eval 우선 개발은 로컬판 skill-creator의 두 갈래 조건화를 따름, ③ "모든 모델(Haiku/Sonnet/Opus)로 테스트"와 그 체크리스트 항목은 로컬 모델 실태(세션 모델과 CLAUDE.md 서브에이전트 모델 선택 규칙)가 우선.

## 요점

검증 없는 배포 금지, 그리고 베이스라인 관찰 선행. 스킬 없이 실패하는 것을 보지 않았으면 무엇을 가르칠지 모르는 채 쓰는 것이고, 검증 없이 배포하면 그것이 작동하는지 모르는 채 배포하는 것이다. 코드에 재현 우선을 지킨다면, 스킬 문서에는 이 절차를 지킨다. 같은 규율의 산문판이다.
