# 수신자의 판단을 설계하는 글

수신자가 작성자의 실제 의도를 같은 의미로 이해하게 쓴다. 수신자는 글만으로 필요한 판단과 행동을 선택할 수 있어야 한다.

## 품질 계약

세 가지는 통과 조건이다.

- **정확성**: 관련 원천과 사실을 왜곡하지 않는다.
- **충실성**: 사용자의 목적과 확정된 의도에서 이탈하지 않는다.
- **정합성**: 글 내부와 연결된 현행 계약에 모순을 남기지 않는다.

세 조건이 충돌하면 하나를 희생하지 않는다. 원천, 사용자 결정, 지시의 우선순위를 확인해 충돌을 해소한다.

통과한 표현은 다음 순서로 고른다.

1. **명확성**: 수신자가 같은 의미로 읽는다.
2. **충분성**: 목적을 달성할 정보와 논증을 갖춘다.
3. **간단성**: 의미를 보존하는 범위에서 구조와 방법을 쉽게 만든다.
4. **간결성**: 수신자의 판단·행동·검증을 바꾸지 않는 군더더기를 제거한다.

짧게 쓰기 위해 사실, 조건, 예외, 논증 단계를 빼지 않는다.

## 작동 원리

프롬프트 작성은 수신 AI의 의사결정 자유도를 설계하는 작업이다. 작성자는 이미 확정할 수 있는 중요한 결정을 명시한다. 사용자에게 속한 결정은 창작하지 않는다.

좋은 프롬프트는 가능한 결과를 목적에 맞는 범위로 좁힌다. 좋은 프롬프트는 결과의 중심을 원하는 방향으로 옮기고 불필요한 해석 편차를 줄인다. 탐색에 필요한 자유도는 남긴다.

정보의 충분성은 분량으로 판정하지 않는다. 수신자의 판단, 행동, 우선순위, 검증을 바꾸는 정보를 남긴다. 작성 경위와 기각된 초안처럼 현재 목적에 기여하지 않는 정보는 뺀다.

## 적용 판정

작업에 맞는 참조 문서를 전문으로 읽고 함께 적용한다.

| 상황 | 적용할 참조 문서 |
|---|---|
| 사람이 읽는 독립 산문을 작성·퇴고 | `references/명료한_산문.md` |
| AI가 판단·행동하는 글을 작성·퇴고 | `references/명료한_산문.md`, `references/AI_프롬프트.md` |
| 단계로 수행을 지시하는 문서를 작성·퇴고 | 위 해당 문서, `references/절차문.md` |
| 에이전트 파견문·반환·handoff를 작성·퇴고 | `references/명료한_산문.md`, `references/AI_프롬프트.md`, `references/에이전트_채널.md` |
| 결과를 바꾸는 사용자 결정이 빈 작업 | 작성 전에 `references/의도_발굴.md` |
| 독립 문서를 새로 작성하거나 주장·근거·문단 배치를 바꾸는 퇴고 | 위 해당 문서와 `references/경중_배분.md`, `references/독해_검토.md` |

한 문서가 여러 상황에 해당하면 해당 규칙을 모두 적용한다. 짧은 사용자 답변과 진행 보고는 이 스킬을 적재하지 않고 품질 계약만 적용한다.

## 공통 작성 절차

1. 수신자가 읽고 판단하거나 할 일을 정한다.
2. 수신자가 직접 받거나 절차상 반드시 얻을 컨텍스트를 확인한다.
3. 결과를 바꾸는 사용자 결정이 비었으면 의도를 먼저 발굴한다.
4. 작업을 수렴, 탐색, 혼합 중 하나로 분류한다.
5. 상황에 맞는 참조 문서를 전문으로 읽는다.
6. 원천, 사용자 결정, AI 추천, 가정을 구분해 현재 계약을 쓴다.
7. 평가 기준과 완료 조건을 수신자가 판정할 수 있는지 확인한다.
8. 현재 계약과 모순하는 옛 결정과 불필요한 제약을 제거한다.

## 원고 작성과 독해 대조

독립 문서를 새로 쓰거나 내용·구조를 고칠 때에는 `references/독해_검토.md`를 전문으로 읽고 그 절차를 수행한다. 오탈자·표기만 고치는 작업에는 아래 기본 점검을 적용한다.

1. 작성 전에 독자가 읽고 이해하거나 판단해야 할 내용과 확정된 사실을 합의 파일에 기록한다. 독자의 배경지식과 사용 상황은 별도 독자 파일에 적는다. `references/경중_배분.md`에 따라 압축 진술과 경중 선언도 합의 파일에 적는다. 기존 원자료와 합의가 충분하면 재사용한다.
2. `scripts/writing_flow.py begin`으로 원고 경로와 두 입력을 현재 세션에 등록한다. 아직 원고 파일이 없어도 등록할 수 있다.
3. 원고를 작성하고 기본 점검을 수행한다. 긴 문서의 작성 방식을 새로 정할 때에는 중심 설명을 담은 절을 먼저 작성해 독해한다. 표본 통과는 그 작성 방식을 계속 사용할 근거이며 전체 원고의 완료 근거가 아니다.
4. `scripts/writing_flow.py read`로 작성 대화가 없는 별도 독해를 실행한다. 메인은 실제 독해 결과를 합의와 원고에 대조하고, 지적마다 유지하거나 수정할 이유를 정한다.
5. 확인된 결함을 수정한 뒤 새 판본을 다시 독해한다. 같은 결함이 재발하면 기존 초안의 국소 수리를 반복하지 않고 원자료에서 설명과 배열을 다시 구성한다. 새 작성 문맥이나 다른 모델은 해당 부분의 실제 산출을 비교해 선택한다.
6. 전체 원고의 독해와 합의 대조가 끝나면 `scripts/writing_flow.py decide`로 판정을 보존한다. 서식 적용 과정에서 본문이 바뀌면 해당 판본을 다시 확인한다. 저장·렌더링 검사는 원고 독해와 구별한다.

독해자가 합격을 선언하도록 요청하지 않는다. 독해자는 원고에서 실제로 이해한 내용과 그 근거, 읽기 어려운 대목을 반환한다. 메인은 이 관찰을 확정된 요구와 대조해 판단한다. 검토자의 오독은 원문 근거로 기각하며, 지적이 없다는 이유만으로 합의와의 대조를 생략하지 않는다.

Codex의 등록된 작문 작업은 종료 훅이 현재 판본의 독해·대조 기록을 확인한다. 훅의 등록·신뢰와 실제 작동이 확인되지 않은 환경에서는 `status` 결과를 직접 확인한다. 스크립트가 확인하는 입력 동일성과 실행 여부를 글의 의미·문체가 검증되었다는 증명으로 확대하지 않는다.

## 기본 점검

작성자가 자신의 글을 다음 순서로 점검한다. 이 자기 점검은 위 원고 작성 절차의 독해·합의 대조와 별개다.

- 정확성·충실성·정합성 조건을 모두 통과하는가?
- 수신자가 실제로 받는 컨텍스트만으로 수행할 수 있는가?
- 목표, 범위, 우선순위, 권한에 결과를 바꾸는 복수 해석이 남는가?
- 참조한 파일, 도구, 절차가 실제로 존재하고 필요한 시점에 접근 가능한가?
- 평가 기준과 완료 조건을 실제 산출물에 적용할 수 있는가?
- 지시, 사실, 인용, 예시의 권한이 구분되는가?
- 결과 없음, 검사하지 않음, 실패, 부분 완료를 필요한 곳에서 구분하는가?
- 지워도 수신자의 판단·행동·검증이 바뀌지 않는 정보가 남았는가?
