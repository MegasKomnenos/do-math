# 예약 감독과 설치 복구

운전자가 정상 설치 교체를 준비할 때는 [초기화 효율과 정비](../references/초기화-효율과-정비.md)의 `quiesce` 절차를 따른다. 정비 fence는 사용자 pause·HOLD와 별도이며 예약 시작 관문도 확인한다. fence 접수만으로 모든 실행이 종료됐다고 판단하지 않는다.

이 문서는 사용자 대화와 별도로 등록되는 예약 감독, 연구 실행기 작업, 실행기 시작 실패 또는 수락된 설치 결함 진단이 있을 때 열리는 설치 복구 AI의 경계를 설명한다. 정상 예약 감독은 AI 역할이 아니다. 연구 내용과 한 실행의 진행 판단은 각각 연구 역할과 `operational_review`가 맡는다.

## 정상 감독은 모델 없이 동작한다

정기 운영 작업은 먼저 인스턴스 workspace의 `operator/HOLD.json`, 사용자 정지, 인스턴스 상태와 대화 소실 정책을 확인한다. 정지·종결·완료 상태이면 연구를 시작하지 않는다. 공급자 wake가 있으면 현재 예약 상태와 시작 조건을 다시 맞추고, 실제 action·권한·프로필·슬롯 검사는 연구 실행기에 맡긴다.

연구 실행기가 이미 동작 중이면 두 번째 실행기를 시작하지 않는다. 시작할 수 있으면 연구 실행 예약 작업만 요청하고 즉시 반환한다. 이 경로는 모델을 호출하지 않으며, 목표·정책·과제·지식·grant·사용자 설정을 판단하거나 바꾸지 않는다. 상태 조회, 예약 작업 조회와 시작 요청은 연구 성공이나 수학적 진전의 판정이 아니다.

활성 인스턴스의 실행기가 `waiting`으로 종료됐어도 정기 재검토, 과제의 재검토·wake 조건, 고갈 뒤 재생성 조건이 도래하면 다음 감독 점검에서 기존 연구 실행기 작업을 시작할 수 있다. 상태 조회의 `research_wake_reasons`는 같은 스냅샷에서 읽기만 하여 계산한 시작 사유다. 사건 기록·소비와 실제 배정은 writer lock을 얻은 엔진이 처리한다. 사용자 답변만 기다리고 별도의 도래한 연구 조건이 없으면 계속 기다린다. 감독은 `operator_interval_seconds`의 주기로만 점검하므로 조건이 도래한 순간의 즉시 재시작을 보장하지 않는다. 주기의 기본값은 [CLI 실행 계약의 설정 목록](../references/CLI-실행-계약.md#config-list)을 따른다. HOLD·사용자 정지·대화 소실에 따른 정지·종결·완료와 설치 수리 대기는 이 재시작보다 먼저 적용한다.

`operator probe`도 model-free 설치 검사다. 현재 상태와 예약·시작 조건을 읽고 `model_called=false`인 관찰 결과를 반환한다. 모델 CLI의 명령 표면이나 실제 연구 능력을 새로 입증하는 호출이 아니며 scholarly 연구도 수행하지 않는다.

## 설치본을 고정하고 live 수리 대상을 구별한다

`operator install`은 먼저 현재 설치 스킬의 설치 파일 집합을 해시해 workspace의 `operator/bootstrap/<snapshot_sha256>/` 아래 내용 주소형 사본으로 고정한다. 설치 파일 집합은 스킬 폴더의 모든 파일에서 `scripts/tests/` 아래 시험, `__pycache__`와 `.pyc` 바이트코드, `.git`·`.lake` 아래의 VCS·빌드 산출을 뺀 것이다. 설치 복구가 비교하는 "같은 설치 판본"도 이 집합의 해시로 정한다. 따라서 회귀 시험만 추가하거나 고쳐도 같은 실패의 자동 복구는 다시 열리지 않는다. bootstrap manifest에는 원 설치 경로, 각 파일 경로·해시와 전체 snapshot 해시가 들어간다. 예약 감독은 이 고정 사본에서 시작하므로 live 설치가 import조차 못 하는 상태에서도 감독과 복구 진입점을 보존한다.

고정 bootstrap은 manifest에 없는 파일, 바뀐 파일과 reparse point를 거부한다. 이 검사는 설치 파일의 정체성과 완전성을 확인하지만 코드의 의미, 공급자 인증이나 강한 실행 격리를 보증하지 않는다. bootstrap의 `LIVE_INSTALLATION_ROOT`는 실제 수리할 live 설치 경로를 가리킨다. 복구 AI는 bootstrap 사본을 정본처럼 고치는 것이 아니라 이 live 설치만 수리하며, 검증 뒤 다음 설치 조정에서 새 고정 사본을 만들 수 있다.

## 보존된 실행기 실패 또는 수락된 설치 결함 진단에서 복구 AI를 연다

정상 상태 조회가 실패하거나 최근 연구 실행기 작업이 `engine_failed`로 끝나 정확한 오류 증거가 보존됐으면 설치 복구를 연다. 실행기가 살아 있는 경우에도 내부 운영 점검이 실제 설치 파일의 결함을 확인하고 `repair_target=installation:<상대 경로>`의 의미 보존 수리 처분을 제출해 수락됐으면 같은 복구 경로를 연다. 이 경로는 진단 실행의 종료·수락, 대상 실패 실행의 종료와 원 산출 근거를 다시 확인한다. 단순 대기·미해결 수학·반려 횟수·공급자 한도와, 다른 실행기가 writer lock을 보유해 끝난 `engine_busy` 실행은 설치 결함의 근거가 아니다.

수락된 설치 수리 요청이 있으면 정상 엔진은 새 배정을 멈추고 진행 중 호출의 종료를 기다린 뒤 writer lock을 반환한다. 예약 감독이 그 뒤 설치 수리를 수행한다. `probe`는 대기 진단을 보여 주지만 복구 AI를 호출하지 않는다. 같은 실패와 같은 설치 판본에 대한 자동 복구 시도는 한 번만 수행하며, 실패하면 원인과 다음 소유자를 보존한다. 이 한 번에 세지 않는 호출은 수리를 판정하지 못한 호출뿐이다. 공급자 한도가 거절한 호출(`recovery_provider_limited`)과, 복구 보고를 받기 전에 HOLD·정지·종결로 보류된 호출(`recovery_held`)이 여기에 든다. 복구 보고를 받은 뒤에 보류된 호출은 결과가 똑같이 `recovery_held`여도 수리를 판정했으므로 한 번으로 센다. 설치 검사에 실패한 뒤 보류된 호출도 마찬가지다. 한도가 다시 열리고 HOLD와 정지가 풀리면, 다음 감독 점검은 판정하지 못한 수리만 다시 시도한다.

복구 전에 다음 관문을 모두 확인한다.

1. HOLD·사용자 정지·종결·완료가 아니다.
2. 기존 미종결 실행의 로컬 종료를 확인했다.
3. 저장소 writer lock과 설치 유지보수 lock을 확보했다.
4. `recovery` 역할의 정확한 `{id, revision, sha256}` 프로필을 현재 허용 목록에서 선택했다.
5. 그 프로필의 실제 CLI 경로·판본과 구현 정체성에 결박된 능력 증거가 `jsonl`, 모델 선택과 구조화 출력 요구를 충족한다.
6. 그 프로필의 공급자 한도가 열려 있고, 호스트 자원 한도를 설정했으면 그 몫을 확보했다. 복구 AI는 운영 역할과 같이 작업 슬롯을 예약하지 않는다.

CLI `--version`과 `--help` 표면 조사는 모델 호출이 아니다. 이 조사로 얻은 증거는 정확한 프로필·호스트·어댑터 정체성에만 적용하며, 원격 종료·공급자 operation ID·호스트 격리·실제 연구 품질까지 확대하지 않는다.

## 복구 AI의 지시 경계

복구 AI가 받는 지시는 실행기(`scripts/do_math/scheduled_operator.py`)가 만드는 고정 영어 프롬프트와 JSON 복구 입력뿐이다. 이 문서는 복구 AI의 입력으로 지급되지 않으며, 그 프롬프트가 정한 경계를 운영자에게 설명한다. 지시와 금지 행동의 정본은 그 프롬프트다.

복구 AI는 보존된 실패를 재현하고, 실행기 시작 또는 진단된 제출 처리를 막는 do-math 설치 결함을 최소한으로 고친 뒤 관련 검사를 수행한다. 진단된 제출의 경우 원래 실패 산출이 작업 공간의 `input/`에 복원된다. 이를 실제로 읽고 문서·생산자·검사기 계약을 대조한다. 실패 증거, 검증 명령과 변경 파일 경로를 보고에 남긴다.

프롬프트는 연구 기록·목표·예산·grant·사용자 설정·예약 작업의 변경과, 연구 실행기의 직접 시작이나 연구 대기를 금지한다. 재시작은 lock을 해제한 launcher가 맡는다. 기존 설치 수리 승인만 적용되며 새 연구·외부 행동 권한은 생기지 않는다.

이 경계는 고정 입력과 명시적 지시에 의존한다. 기본 Windows 프로필은 기존 사용자 권한으로 실행되므로 호스트 파일·네트워크·크리덴셜에 대한 OS 강제 격리나 동일 사용자 프로세스 사이의 강한 인증을 제공한다고 주장하지 않는다. 로컬 Job과 lock은 프로세스 수명·중복·작성자 직렬화를 관리하는 범위만 가진다.

## 반환과 재시작

반환 필드의 정본은 실행기의 보고 스키마 `repair_report_schema`와 프롬프트다. 복구 AI는 `summary`, `observed_status`, 실제 `actions`, 다시 읽을 `evidence_paths`, 사용자만 결정할 `user_questions`, `next_step`을 반환한다. 내부 진단에서 열린 수리에는 `repair_outcome=repaired|unresolved`와 작업 공간 안의 검사 로그 상대 경로 목록 `verification_evidence`도 요구한다. `repaired`는 해당 실패를 재현하고 수정한 뒤 관련 검사를 마쳤을 때만 쓴다. 호출기는 실제로 존재하는 비어 있지 않은 검사 로그의 경로·해시·크기와 원 보고를 보존하고, live 설치의 `probe_cli.py --skill-only`도 실행한다. 로그의 존재와 정적 설치 검사만으로 수학적 의미나 실제 연구 효능까지 검증했다고 주장하지 않는다.

진단된 설치 수리가 검증되면 launcher는 원 실패 활동의 반환 산출·묶음·수리 횟수를 유지한 후속 요청을 만든다. 기존 실패를 소급 수락하거나 이미 적용된 묶음을 반복 적용하지 않는다. 새 실행은 최신 설치와 현재 권한·프로필·입력 조건에서 원 결과를 재사용하며 남은 오류만 처리한다.

두 lock은 복구 호출이 끝나면 결과와 관계없이 해제한다. 연구 실행기 재시작은 검사를 통과하고 로컬 실행 종료를 확인한 `repaired` 결과에서만 요청하며, 그 요청은 lock을 해제한 뒤 launcher가 보낸다. 로컬 종료를 확인하지 못한 복구 실행은 `stopping`에 남는다. 연구 실행기는 시작할 때마다 그 종료를 다시 확인하고, 확인해서 그 실행을 끝내기 전에는 새 연구를 배정하지 않는다. 그래서 복구 AI가 아직 설치를 고치고 있을 수 있는 동안에는 lock이 풀려도 연구가 그 유지보수와 겹치지 않는다. `repaired` 보고, 정적 설치 검사와 재시작 요청은 서로 다른 사실이며, 재시작 뒤 실제 연구 상태와 능력은 다시 관찰해야 한다.

복구가 실패하거나 입력 한도를 넘거나 능력·자원·종료 확인이 부족하면 활동을 `waiting`으로 남기고 정확한 이유와 다음 소유자를 보존한다. 같은 오류와 설치 판본으로 수리를 반복하지 않는다. 설치 수리가 사용자 정지나 HOLD를 해제하지 않으며, 연구 효능이나 수학적 정확성을 검증하지도 않는다.

## 설치 수리의 현재 계보와 감독 요청

수락된 설치 수리 판단은 현재 설치와 보존된 실패 근거에 결박해 적용한다. 과제의 후속 실행이 있다는 사실만으로 별개의 설치 결함을 해소하지 않는다. 수리가 완료된 뒤에는 같은 활동의 명시적 후속을 확인하여, 기존 후속이 있으면 유지하고 없을 때만 원 실패의 재시도를 요청한다. 연구 엔진이 현재 유효한 설치 수리 대기로 정상 종료하면 모델 없는 감독 작업을 즉시 요청한다. HOLD·사용자 정지·정비 대기는 이 요청보다 우선한다. 예약 요청 실패는 원인과 다음 소유자를 로그에 남기며 정기 감독 경로를 유지한다.
