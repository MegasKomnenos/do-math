# 과제의 착수 조건

후보 준비는 이 문법으로 착수 조건을 저작하고, 작업 계약 검토는 조건이 실제 질문의 선행관계와 맞는지 대조한다. 문법·참조 검사는 실행기가 수행하며 생산자는 같은 검사를 선택적으로 미리 실행할 수 있다. 조건의 의미와 연구 의무의 적합성은 해당 AI 역할이 판단한다.

조건 객체는 `op`와 그 연산에 필요한 필드로 작성한다. 기록을 직접 조회하는 세 연산은 `space`, `family`, `record_id`로 대상을 결박한다. `task`, `activity`, `execution`, `external-operation`, `review-cycle`의 space는 `runtime`이고, 나머지 아래 기록 가족의 space는 `research`다. 기록 ID와 비교값은 실제 입력에서 확인한다. 기본 조건 연산은 다음과 같다.

| `op` | 함께 쓸 필드와 뜻 |
|---|---|
| `always` | 추가 필드 없이 참인 조건이다. |
| `all`, `any` | 비어 있지 않은 조건 배열 `args`를 둔다. 각각 전건 참, 하나 이상 참을 요구한다. |
| `not` | 부정할 조건 객체 하나를 `arg`에 둔다. |
| `record_exists` | `space`, `family`, `record_id`를 둔다. 지정 ID의 기록이 그 가족에 속하는지 확인한다. |
| `record_lifecycle_is` | `space`, `family`, `record_id`, 비교할 `value`를 둔다. 기록의 `lifecycle`을 읽고 그 필드가 없으면 `status`를 읽는다. |
| `record_field_equals` | `space`, `family`, `record_id`, 아래에서 허용한 `pointer`, 스칼라 `value`를 둔다. 실제 필드값과 자료형까지 같아야 한다. |
| `relation_exists` | 관계 종류 `subkind`, 출발 ID `from_id`, 도착 ID `to_id`를 둔다. 관계 출력의 `source`·`target`을 여기의 필드명으로 쓰지 않는다. |
| `task_disposition_is` | `task_id`, 요구하는 종결 처분 `value`를 둔다. `value`는 착수 의도에 맞는 `completed` 또는 `closed`다. |
| `decision_value_is` | 입력에 제공된 사용자 결정의 `decision_id`와 비교할 `value`를 둔다. 결정이 현재 유효하고 결정의 `change.value`(없으면 `change` 전체)가 `value`와 자료형까지 같을 때 참이다. 값이 null인 경우와 필드가 없는 경우를 구별하며, 불리언 true와 정수 1도 같은 값으로 보지 않는다. 특정 과제로 범위를 정한 결정은 그 과제의 조건에서만 참이 된다. |
| `artifact_valid` | 보존 산출을 가리키는 `artifact_ref`에 `snapshot`, `path`, `sha256`을 둔다. `path`는 `runtime/artifacts/` 아래의 상대 경로이며, 이 규칙이나 경로 성분의 저장 규칙을 어긴 조건은 제출 단계에서 거부된다. 실행기가 그 스냅샷에서 읽은 바이트의 해시와 형식을 확인하면 참이다. 해시가 다르거나 형식 검사를 통과하지 못하면 평가 오류다. 형식 검사는 JSON과 UTF-8 텍스트(`.txt`, `.md`, `.tsv`, `.csv`)만 지원한다. |

조건의 평가 오류는 `task_condition_evaluation_error` 사건과 해당 과제의 오류를 연구 계획에 제공한다. 현재 조건은 매번 다시 평가한다. 같은 계약·근거의 오류를 owner 재시작 후 다시 보았다는 이유만으로 새 사건을 만들지는 않는다. 계약이나 근거가 달라지면 오류 문구가 같아도 새 사건으로 전달한다. 아직 시작하지 않은 과제의 조건 오류만으로 대상 실행이 없는 운영 점검을 만들지 않는다. 자료 대기의 `next_owner`는 다음 담당을 나타내며, 그 값만으로 새 호출을 시작하지 않는다. 필요한 자료 도착이나 별도의 유효한 재고 사건을 기다린다.

선택한 과제도 호출 준비 시 `RevisionEngineMixin._selected_action_current`에서 같은 `planning.task_ready(...)`로 확인한다. 입력을 만드는 동안 공개 결정이 게시되어 저장 head가 달라지면 `CallEngineMixin._prepare_call`은 미입장 입력을 폐기하고 같은 의무를 새 입력으로 준비한다. 공급자 입장이 성공했을 때의 `starting` 전이는 `SessionSlots.acquire`가 맡는다.

검토 호출의 실제 입장은 `CoreEngineMixin._register_execution`이 판정한다. 남은 검토 예산으로 고정 범위를 마칠 수 없으면 새 실행을 만들지 않고 기존 시도·범위·자원 처분을 저장한다. 초기 해석의 재시도는 원래 활동의 정확한 대기를 요구한다. `activities.wait_for(...)`는 배정된 실행이 모두 끝난 뒤에만 대기를 만든다. 재시도는 먼저 `resume_activity`로 waiting을 ready로 해소하고, 이후 `assign_execution`이 새 실행을 배정하며 working으로 바꾼다. `assign_execution` 자체는 waiting 활동을 거절한다.

입력 문맥을 읽는 중 `GitStateStoreError`가 나면 저장소 전체의 실패로 전파한다. 원 봉인 오류에 대응하는 현재 `impact_review` 대기가 있으면 원 생산자의 진단으로 돌리고, 이미 전제가 바뀐 대기라면 준비 중인 검토 시도만 `input_preparation` 실패로 보존한다. 이때 기존 생산자의 대기는 그대로 남고, 미입장 실행은 `start_failed`로 끝난다. 로컬 입력 포장은 저장소를 호출하지 않으며 포장 실패는 같은 준비 실패 경계가 맡는다.

중앙 제출의 Git 게시 응답을 잃었을 때는 저장된 영수증으로 수용 여부를 확인한다. `CoreEngineMixin._publish_control_request`의 재조회까지 실패하면 오류를 전파하고 수송의 최종 반려 영수증을 만들지 않는다. 저장소가 복구된 뒤 같은 요청을 재전달하면 이미 게시한 영수증을 재사용한다. 게시 전 head에 남아 있는 임시 후보는 복원한다. native final의 `_capture_native_submission`도 재조회 실패 시 같은 복원을 적용하며, 다시 읽은 원 캡처를 중복 게시하지 않는다.

`CoreEngineMixin._submission_repair_context`와 `integration.inspect_bundles(...)`는 같은 `integration.split_research(...)` 판정으로 부분 편입의 원 응답을 고정한다. 이 연구 재시도는 이미 수용한 응답의 해시를 유지하고 그 응답을 새 bundle에 다시 배정하지 않는다. 응답 전체가 한 bundle인 역할의 continuation은 새 판단을 수용할 수 있으므로 과거의 서로 다른 수용 응답을 충돌로 취급하지 않는다. 양쪽 모두 조상 실행의 `accepted_integration_ids`를 보존한다.

입력 초과 대기의 `selected_contract_sha256`은 원래 선택한 계약의 해시다. 과제가 개정되면 `overflow_requests`가 현재 `contract_revision`과 이 원 해시를 함께 제공할 수 있다. `CoreEngineMixin._apply_input_overflow_resolutions`는 고정 요청과 현재 요청의 일치뿐 아니라 현재 과제의 계약 해시도 확인한다. 더 큰 프로필을 골랐다는 이유만으로 이전 계약의 대기를 해소하지 않는다.

운영 검토의 입력 대상은 공개 요청 또는 실행 관찰·실패가 지정한 실제 실행이다. 위임의 독립 판단 요청은 `_review_recovery_control`이 만들고 `_apply_inbox`가 원 사용자 요청을 history에 보존한 뒤 배정한다. 이 원요청과 위임 근거는 입력에 함께 제공하며, 별도의 요청이나 판단으로 대체하지 않는다. 보존된 과제 결과를 복원할 때는 봉인 bytes 대조 뒤에도 실제 목적 경로가 입력 디렉터리 안에 있는지 확인한다.

`integration.bundle_impact_request(...)`는 같은 bundle·원 생산자·고정 입력의 검토 실행을 모은 뒤, 보존된 각 assignment와 같은 검토들만 제외하여 영향 계획을 다시 계산한다. 계산한 요청이 그 assignment와 정확히 같을 때만 그 제외를 사용한다. 맞는 assignment가 없으면 검토 실행을 제외하지 않은 새 요청을 만든다. 따라서 오래된 검토가 현재 영향 집합에 속하더라도 정확한 새 검토가 자기 입력을 무효화하지 않는다. 검토가 같은 header를 가졌다는 사실만으로 오래된 검토를 제외하거나 새 승인을 인정하지 않는다. 후보는 실제 보존 assignment의 유한 집합이며 반복 횟수 제한에 따른 안정화 오류는 사용하지 않는다.

overflow 재시도는 활동의 정확한 대기를 먼저 확인한다. 배정 실행 종료와 waiting 중 새 배정 금지는 `activities.wait_for(...)`와 `assign_execution`의 전이 계약이 맡는다. 질문은 `questions.close(...)`가 마지막 미해소 대상을 덮을 때 닫히며, `CoreEngineMixin._resolve_input_overflow_question`은 이미 닫힌 질문의 원 해소를 보존한다.

`CoreEngineMixin._apply_extensions`는 제출 수신 검사를 통과한 확장만 적용한다. 역할별 확장 소유권은 `submission.extension_schema(...)`, 규칙의 과제 대상과 학술 외부 효과·지정 grant는 `submission._payload_issues`에서 검사한다. 적용 전에는 원 과제 계약의 현재성도 확인한다. 결과를 수신하는 `CallEngineMixin._receive_call`은 실패 진단 뒤에도 공개 pause를 유지하며, 실패한 live 운영 검토는 부모 실행에 정지와 대기를 요청한다.

`external_requests`의 grant가 없으면 제출 자체를 권한 승인으로 취급하지 않는다. 형식과 효과의 과제 귀속을 검사한 뒤 해당 실행의 purpose를 원위치로 삼은 사용자 grant 질문을 보존하며, 외부 작업이나 전송은 만들지 않는다. 후보 제목의 유일성·공백뿐인 연구 보고·종류 검토 verdict는 제출 경계가 검사하고 내부 적용은 그 결과를 소비한다. 저장 복원은 대기 map의 키와 `action.id`를 대조한다. source 이름은 실제 import 생산자와 쓰기 전 `record_storage` 점검이 보장하고, 내부 보존 참조 계산은 그 이름을 사용한다. source 저장 스키마 자체가 이름을 필수로 선언한다는 뜻은 아니다.

지식 import는 기존 ID의 재사용을 거절하고 새 기록을 만든다. 기존 지식의 개정은 검토된 변경 경로를 사용하므로 import가 이미 읽고 있는 지식을 같은 ID에서 교체하는 분기는 없다. 외부 작업의 재시도는 원 grant의 현재 권한을 먼저 검사한다. 시도 전 철회로 취소된 작업은 원 grant가 무효이므로 실행을 만들지 못하며, 시도 후 재시도는 등록된 원 실행과 활동을 이어받는다. 전송 ledger의 저장 callback은 같은 owner의 동기 `execute_operation` 안에서만 호출된다.

반복 한도는 `revisions.record_repetition(...)`의 history와 `action_repetition_waits`가 관리한다. 사용자의 정확한 `continue_repetition` 결정은 그 한도를 해소하며, 같은 action에 남은 입력·권한·게시 대기는 각 소유자가 해소할 때까지 유지한다. 공급자 재시도 시간이 지났어도 사용자 pause는 그대로 유지한다.

`family`는 기록의 구체적인 지식 종류와 구별한다. 현재 기록 가족은 `knowledge`, `governance`, `goal-judgment`, `grant`, `task`, `activity`, `execution`, `decision`, `external-operation`, `source`, `trust-environment`, `review-cycle`, `instance`, `execution-profile`, `formal-result`, `exposition`, `identity-assessment`, `assessment-use`, `governance-source`, `kind-definition`, `relation`이다. 조건에서 참조한 대상이 실제로 제공되지 않았다면 존재하는 ID처럼 만들어 넣지 않는다.

`record_field_equals`의 `pointer`는 `/`로 시작하며 아래의 기계 필드만 가리킬 수 있다. 해당 기록에 그 필드가 실제로 존재하고 스칼라값을 가져야 한다. 예외적으로 `/usable_as_k`는 현재 형식 결과·동일성 판정·효력에서 계산하는 불리언이며 저장 필드를 새로 만들지 않는다. 자유 산문이나 객체·배열 전체를 비교하지 않는다.

| 기록 가족 | 허용 포인터 |
|---|---|
| `knowledge` | `/lifecycle`, `/kind`, `/kind_use_suspended`, `/usable_as_k` |
| `task` | `/status`, `/revision` |
| `activity` | `/status`, `/activity_kind` |
| `execution` | `/status`, `/role`, `/outcome` |
| `governance` | `/status` |
| `goal-judgment` | `/decision`, `/current` |
| `grant` | `/status` |
| `decision` | `/kind` |
| `external-operation` | `/status`, `/http_status`, `/succeeded` |
| `source` | `/status`, `/revision`, `/sha256` |
| `trust-environment` | `/status` |
| `review-cycle` | `/status`, `/decision`, `/phase` |
| `instance` | `/goal_status`, `/goal_revision`, `/policy_revision` |
| `formal-result` | `/publication_state`, `/formal_use` |
| `exposition` | `/lifecycle` |
| `identity-assessment` | `/decision` |
| `assessment-use` | `/status` |
| `kind-definition` | `/status`, `/token` |

과제가 지식 기록 `KN-A`의 인증된 형식 근거를 착수 전에 요구하면 다음 조건을 사용한다. 단순한 비형식 연구 자료 재사용에는 이 조건을 붙이지 않는다. 실제 ID로 바꾸고 다른 필수 조건이 있으면 `all`로 함께 결합한다. 실행기는 착수 시점마다 이 효력을 다시 계산한다.

```json
{"op":"record_field_equals","space":"research","family":"knowledge","record_id":"KN-A","pointer":"/usable_as_k","value":true}
```

예를 들어 같은 응답에서 만든 과제 `가정 H 조사`의 완료 뒤 과제 `H를 사용한 증명`을 시작하려면 다음처럼 선행관계를 제출한다. 두 제목은 실제 주 산출의 제목과 같아야 한다.

```json
{"task_conditions":[{"task_title":"H를 사용한 증명","dependencies":["가정 H 조사"],"occurrence_condition":{"op":"always"}}]}
```

실행기는 선행 과제의 완료 조건을 결합하고, 조건 안의 `record_id`, `task_id`, `from_id`, `to_id`에 같은 준비 결과의 유일한 제목이 있으면 새 ID로 결박한다. `not`은 평가 오류를 참으로 바꾸지 않으며 `all`·`any`도 하위 조건의 오류를 숨기지 않는다. 현재 실행기가 지원하지 않는 연산자를 만들지 않는다. 실행기가 이름 결박과 조건 검사를 끝내기 전에는 착수 가능하다고 주장하지 않는다.

준비 결과의 적용은 제출 당시의 구조 검사와 적용 직전의 현재성 검사를 모두 소비한다. 개정 대상은 현재에도 미완료이며 실행 중이 아닌 과제여야 한다. 같은 계약 hash를 유지하는 상태 이동도 있으므로 이 조건은 hash 비교만으로 대신하지 않는다. 형식 과제는 저자에게 지급한 `input_snapshot`의 신뢰 환경에 결박하고, 조건을 실제 ID로 결박한 뒤 현재 후보에서 평가와 의존 순환 검사를 마친다. 계약 검토는 적용 직전 `DecisionEngineMixin._validate_decision_acceptance`가 해당 실행의 원 계약과 검토 근거를 대조한다.

조건이 가리키는 준비 대상의 유일성은 `submission.payload_issues(...)`가 제목 또는 개정 ID로 검사한다. 내부 `_apply`는 이 검사를 통과한 bundle을 소비하며 같은 대상 목록을 다시 반려하지 않는다. 조건 문법이 유효해도 참조한 실행에 아직 `outcome`이 없으면 평가 오류다. 이를 착수 가능한 과제로 게시하지 않는다. `sim.test_planning_engine_receivers.PreparationReceiverTests.test_preparation_rejects_an_unfinished_execution_outcome_condition`은 이 미확정 조건의 반려를 실제 후보 적용기로 확인한다.

연구 lifecycle의 저장 enum은 `initializing`, `active`, `paused`다. `LifecycleEngineMixin._action_lifecycle_gate`는 종료·시계·정지·대화와 초기화 권한을 검사한 뒤 남은 active 상태의 연구 권한을 적용한다. enum 밖의 상태를 내부 분기로 만들어 허용하지 않으며 저장·입력 경계의 enum 검사는 유지한다.

`integration.split_research(...)`가 허용하는 독립 bundle은 개정 대상을 선언하지 않은 일반 연구의 새 지식·관계다. 기존 과제·지식의 mutation은 선언된 개정 실행 또는 계획·준비 판단에 속하며 한 bundle로 묶인다. 따라서 impact 보류와 독립 bundle 수용이 섞인 결과를 만들려고 개정 응답을 나누지 않는다. mutation의 영향받는 종속 기록이 없어도 bundle plan은 존재하며, 독립 영향 검토의 필요 여부는 그 plan이 판단한다. 손상된 원 제출을 처리할 때는 같은 원 생산자의 pending impact 요청만 정리하고 다른 생산자의 요청을 보존한다.

검토 기록 대체의 위임 비교 action은 원 사용자 요청의 `requested_by`와 함께 생산되고, 공개 제어 결과와 같은 게시에 보존된다. 두 독립 판정이 모두 `within_scope`여도 대체 시점의 권한은 별도로 확인한다. 권한이 철회되거나 만료됐으면 원 cycle과 held slot을 그대로 남긴다. 공개 요청 ID가 보존 source ID와 충돌하면서 원문이 다르면 기존 source를 바꾸지 않고 거절한다.

복구의 실행은 공통 등록기가 보존한 ID 있는 원 action으로 계속한다. native 결과의 재사용은 원 활동의 대기만 해소하며, 같은 활동에 독립 확인 단계가 남으면 활동은 `ready`로 유지된다. 운영 점검은 원 실행과 현재 증거를 확인하고, 이미 후속이 있는 retry/resume을 `superseded`로 정산한다. 과제 처분은 원 실행의 과제와 정확히 일치하는 assessment 하나가 필요하고, 사용자 판단 요청은 검토자의 `output/disposition/question`에 연결된다. 원 실행의 종료와 현재 checkpoint·외부 효과 정산은 승인 후에도 다시 확인한다.
