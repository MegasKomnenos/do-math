# Lean compilation and formal evidence

The knowledge of a do-math instance is a Lean library, the canon, and a session reads it and builds against it from the start of its work. Compiling Lean is therefore ordinary work in every role, and this document explains what a session needs for it. It starts from what a compile is and what it costs, because the rest follows from that: why every compile goes through one service, why a compile mostly costs waiting, and why a session compiles at natural points of its work and not after every edit. It then explains how to compile a file, how to build your own files against the canon, what is taken from the cache and what is compiled again, how to estimate what a compile will need, how to write Lean that compiles cheaply, and when a statement counts as formally proved.

How a canon file is written, that is, the `module` header, `public import`, `@[expose] public section` and the form of an informal proof, is explained in [The canon](canon.md). This document repeats of those conventions only what changes how a file compiles.

Three terms are used throughout and are fixed here. The **imported library** is what the Lean environment of the instance provides: the modules of the toolchain itself, such as `Init`, `Std` and `Lean`, and any library the operator configured, such as Mathlib. An import of one of its modules is called an **external import**. The **canon** is the instance's own Lean library. Its sources are in `canon/lean/` in the instance, and all its modules lie under one top-level name, which `instance.json` gives as `library`; the examples below use `Tri` for it, as the examples of [The canon](canon.md) do. A **local module** is a module whose source the broker finds under the folder a build is given: a canon module in your copy of the canon, or a module you wrote there.

## What a Lean compile is, and what it costs

When a session has written a Lean file and wants to know whether Lean accepts it, it has Lean check the file. Lean reads the file from top to bottom, loads every module the file imports, elaborates each definition and theorem in turn, and reports errors, warnings and the output of commands such as `#print axioms`. In this document that whole run of Lean over one file is called a compile, and the process that performs it is a Lean process.

A compile takes time, and with Mathlib it takes a lot of it. Most of that time is spent at the start, loading the imported modules: a file that imports all of Mathlib reads several gigabytes of compiled library from disk before it looks at the first theorem. When those files are not yet in the operating system's cache, that alone took seven minutes on the machine this project was developed on. Time, though, only delays a result. A slow compile is a nuisance; it does not harm anything else that is running.

Memory is different. A compile that takes more memory than the machine has left does not merely run slowly; it pushes the machine into swapping, or gets itself or some other process killed, and every session on the machine suffers. To reason about memory one has to know that a Lean process uses it in two ways.

The first is the imported library itself. Lean maps the compiled modules into memory directly from the files on disk. The second is the memory that belongs to one Lean process alone. On import, Lean builds its own indexes over everything it loaded: the table of names, the sets of `simp` lemmas, the instances, the notations. For all of Mathlib this comes to about a gigabyte, and every running compile builds its own copy. Then, as the file's proofs are elaborated, Lean allocates terms, goals, tactic states and caches, and this part grows with what the proofs do: a `rfl` costs almost nothing, while an unbounded `simp` over all of Mathlib or a large `decide` can take gigabytes. Lean keeps the memory it has freed for reuse and does not return it to the system, so within one compile this memory mostly grows, and it reaches its peak late.

How much of this counts against the machine depends on the operating system. On Linux the mapped library is file cache: the system keeps one copy of each file however many Lean processes use it, and it can drop pages and read them again when memory is short. There the library slows a loaded machine down but cannot run it out of memory, and only the second kind of memory counts. Windows keeps an account, the commit charge, of all the memory it has promised to processes. Its limit is the physical memory plus the page file, and an allocation beyond the limit fails, however much physical memory is free. Windows appears to charge a Lean process for the whole size of the library it maps, although most of those pages are shared with other compiles or never touched. With Lean 4.32.0, a process that imported the Lean metaprogramming library was measured at a commit charge of 2,078 MB while it touched 803 MB of physical memory, of which 98 MB was private to it; the files it had loaded came to about 1.6 GB.

For each compile the broker described in the next section measures the memory charged to the compile's own processes: their commit charge on Windows, and their anonymous memory on Linux. This document calls that quantity the compile's **private memory**. Every estimate a session gives and every measurement the broker reports is in it. On Windows it includes the charge for the mapped library, so the import alone is large there: a compile that imports the analysis part of Mathlib was measured between 2 and 3.9 GB before it elaborated anything.

Private memory is paid once per running compile, and it is the sum over all running compiles that must stay within what the machine has. No session can keep that sum in bounds by itself. With nothing between them, every running session could start a compile whenever it liked, and several Mathlib compiles at once are enough to make the machine unstable.

On Windows the result is that compiles mostly run one at a time, and what a compile costs a session is the wait for its turn far more than its own running time. In the research instance that was examined before the canon was introduced, the 481 finished compiles ran for a median of 24 seconds and waited in the queue for a median of 179 seconds. The development machine had a commit limit of 25.2 GB, of which about 3.4 GB was free while sixteen sessions were running, and one compile held two to four gigabytes.

Two things follow for a session. Lean cannot be kept loaded to answer quick questions, since a loaded process holds its gigabytes for as long as it lives; reading the canon therefore goes through the canon command, which starts no Lean process, as [The canon](canon.md) explains. And compiles are affordable when they are made at natural points of the work. What is short is the number of compiles that can run at once, not the total time available. A compile that checks several statements together waits once, where the same statements compiled one after another wait several times.

## The Lean broker

Each instance runs a single process called the Lean broker, and every compile in the instance goes through it. A session does not run Lean itself, not even to ask for its version. It asks the broker to compile a file, and the broker decides when to start that compile, runs it, and hands the result back.

Because the broker sees every compile of the instance, it can do several things that no session could do on its own.

It schedules compiles against a shared memory budget. A session tells the broker, when it submits a file, how much private memory it expects the compile to need. The broker uses that estimate, together with what it has measured itself, to decide whether the compile can start now or must wait for others to finish.

It measures every compile. While a compile runs, the broker reads how much private memory the Lean process is using and keeps the peak; when the compile ends, it records the peak and the duration, returns them to the session, and adds them to a table it keeps for the instance. So the cost of every proof becomes visible, and the broker's later decisions are based on what compiles in this instance have actually cost, not only on what sessions predicted.

It keeps a compile alive independently of the session's shell tool. The shell tools of the CLIs give up on long commands, as explained under When the shell tool will not wait below, and a Mathlib compile can outlast them. A compile submitted to the broker is a job that continues, and keeps its result, whatever happens to the command that submitted it. The session can come back for the result as many times as it needs.

It cleans up after sessions that have ended. A compile whose session has finished, failed or been killed has no one left to read its result; it only takes memory. The broker cancels such compiles. Apart from a cancellation that a session asks for itself, this is the only situation in which the broker stops a compile: it never stops one for using more memory than was estimated, and it sets no limit on how long a compile may run.

It keeps what compiles produce, so that the same work is not done twice. A module that a build compiled is kept in a cache, and a later build by any session that needs the same module takes it from there; this is what makes building against the canon cheap, as Building against the canon and your own modules explains. The broker keeps files and never a loaded Lean process, because a loaded process holds the memory of its import for as long as it lives, and that memory is what compiles wait for.

The broker compiles one file per job with the `lean` command from the instance's settings. It does not run `lake build`; the `build` command described below does for a session what `lake build` would.

**Why a compile is waiting.** A compile starts when three things have room for it: the memory budget, in which the broker reserves for every running compile what its imports are known to cost and what its estimate adds; the thread budget; and the machine's actual free memory, which also sees everything that is not a compile. Queued compiles are taken in the order they were submitted. One that does not fit yet is passed over, so that a small compile can go ahead of a large one that is waiting for memory. This is limited: once a compile has been passed three times, unless the instance sets another number, nothing behind it starts until it has started. A compile whose external imports the broker has not measured yet waits for a compile of those imports alone, which the broker creates itself; Estimating what a compile will need explains it. The `status` command shows the queue, with each job's estimate, its reservation, the job it is waiting for and how often it has been passed.

**When no broker is alive.** The runner starts the broker, and starts another within seconds whenever it finds none alive. A session that the runner confines together with everything it starts, as a session on Windows normally is, does not start a broker: one started inside such a session would end with that session and take the other sessions' compiles with it. So when the client of such a session finds no live broker, before submitting or while it waits for a result, it waits up to twenty seconds for the runner's and then reports that no broker is alive. Nothing is lost by this. Submit again, or wait again on the same job, a little later; the session is left without a broker only while the runner itself is not running. Where sessions are not confined, as on Linux, the client starts a broker itself and the session notices nothing.

How the broker computes a reservation, its settings, how it lives and recovers, and the exact rules of the cache are written for the operator in [The Lean broker](lean-broker.md). A session can compile without reading it.

## Compiling a file

`commands.lean` in your `input.json` is the broker's command with one placeholder: the interpreter, the broker script, `<command>`, and the path of the instance. In the examples below, `python` stands for that interpreter, `<broker>` for that script and `<instance>` for that path. A single file whose imports are all external imports is compiled with

```text
python <broker> run <instance> <file.lean> --session <session ID> --expect-mb <MiB>
```

where `<file.lean>` is the absolute path of the file, `<session ID>` is the session's own ID, the `session` value in your `input.json`, and `<MiB>` is the session's estimate of the compile's peak private memory, in mebibytes. Estimating what a compile will need explains how to arrive at that number. A file that imports a canon module or a module of your own cannot be compiled this way; it needs `build`, which Building against the canon and your own modules explains.

The broker compiles the file with the `lean.command` of the instance's settings, adding the thread count it has been configured with and the path of the file. The working directory is `lean.cwd` from the settings, or the session's folder when that is `null`. When the compile finishes, the command prints Lean's output exactly as Lean produced it, the standard output on standard output and the standard error on standard error, so that error messages, `#print axioms` lines and `sorry` warnings read as they would from Lean. It then exits with Lean's exit code. The last line on standard error is a summary from the broker:

```text
lean-broker: {"job": "j…", "status": "finished", "exit_code": 0, "reason": null, "expect_mb": 1800,
  "measured": {"peak_mb": 1466.2, "baseline_mb": 1103.5, "excess_mb": 362.7, "seconds": 41.3, "estimate_ratio": 0.81, …},
  "dir": "<instance>/runner/lean/jobs/j…"}
```

The numbers in this line are made up to show the fields. `peak_mb` is the highest private memory the broker measured during the compile, `baseline_mb` is what the compile's external imports alone cost, as Estimating what a compile will need explains, `excess_mb` is the difference, `seconds` is how long the compile ran, and `estimate_ratio` is the measured peak divided by the estimate. `dir` is the folder where the broker keeps the job's files: Lean's output in `stdout.log` and `stderr.log`, the job's record in `result.json`, and a few process receipts. The output can be read again from there at any time.

For a single-file job, `finished` means that the Lean process ended and its exit code was recorded; inspect its `exit_code` to distinguish compiler success from rejection. A Lean process that the operating system ended also finishes this way. On POSIX the summary's `exit_code` is then the negative of the signal number, as when the system kills a compile that ran out of memory; on Windows a crash appears as a large code such as 3221225477 (0xC0000005). Such a code reports an execution failure, not Lean rejecting the source. Status `failed`, with command exit code 3 and a `reason`, means that the job ended without a recorded compiler exit code, and the `reason` says why: the request could not be accepted, the file disappeared or changed after submission, the Lean environment changed while the job was queued, Lean could not start, or its supervising process was lost. The two changes call for submitting the current source again and not for repairing the environment. Status `cancelled` has command exit code 4. An execution failure or a cancellation leaves the check incomplete and does not establish a defect in the mathematics.

Invocation errors belong to the broker's client and not to Lean's assessment of a source file. For example, malformed options or an input rejected before submission can end the command before a job is accepted. Correct that invocation from its diagnostic. An error while waiting for an already submitted job is different: failure to contact the broker does not establish that the job vanished or that Lean rejected the source. Keep the job ID, inspect status and the retained logs, and recover that job's outcome before deciding whether another submission is needed. The command's exit code alone cannot distinguish these phases.

### When the shell tool will not wait

The `run` command waits for the compile, and a compile can take longer than a CLI's shell tool is willing to wait: Claude's tool moves a command to the background after 120 seconds, or after 600 seconds if a `timeout` is given, and abandons it ten minutes after that; Codex's tool returns after about ten seconds and expects the session to poll. A compile that imports Mathlib, or that has to wait its turn behind other compiles, can exceed both.

For such compiles, submit and wait in two steps:

```text
python <broker> submit <instance> <file.lean> --session <session ID> --expect-mb <MiB>
python <broker> wait <instance> <job> --timeout 50
```

`submit` returns at once and prints the job ID. `wait` returns either the finished result, printed exactly as `run` would print it, or, if the timeout passes first, exit code 124 and a note that the job is still running. Nothing is lost between calls; `wait` can be run again and again until the result is there. If a `run` was started and its shell tool gave up, the same recovery works, because the job ID is the first thing `run` prints on standard error.

Submitting the same unchanged file again from the same session, while its earlier job is still queued or running in the same Lean environment and no cancellation of that job has been requested, does not start a second compile. The broker answers the new submission with the ID of the job already in progress, and waiting on either ID gives the same result. A file edited after its submission is a different source. Its new submission becomes a job of its own, and an earlier job that has not yet started fails with the reason that its source changed after submission.

### The other commands

| Command | What it does |
|---|---|
| `build <root> <file.lean>...` | Compiles the files together with every local module they import; the next section explains it. |
| `result <job>` | Prints the job's or build's record as it currently stands. |
| `status` | Prints whether the broker is alive, the configuration it is using, the Lean version, the jobs that are queued, running and recently finished, each with its estimate, its reservation and its measurements, and the builds in progress. |
| `cancel <job>` | Cancels one of your own jobs, or every compile of one of your own builds, that you no longer need. |
| `version` | Prints the Lean version string, which the broker obtained by running the configured version command once. This is the string to give when a report names the Lean environment. |

`cancel` records a cancellation request for a job or build, including while the broker is accepting it. The response acknowledges the request; use `wait` on the same ID to obtain the final outcome. A confirmed cancellation has status `cancelled` and returns exit code 4, including when no compile started. Work that had already completed retains its completed outcome. Cancelling a duplicate submission requests cancellation of the original job or build to which it refers.

All of these take the instance path as their first argument, like `run`.

## Building against the canon and your own modules

Lean finds an imported module not in its source but in its compiled form, the `.olean` file, on a search path that holds the imported library and nothing of the instance's. A file that imports a canon module, or a module you wrote, therefore does not compile on its own: the modules it imports have to be compiled first, as modules, into a place on the search path. The `build` command does all of that, and a session builds against the canon in three steps.

**Take a copy of the canon.** The canon command of your `input.json`, `commands.canon`, with which the canon is read, has the same form as the broker's: an interpreter, the canon tool, `<command>`, and the path of your session folder. Its `checkout` command copies the Lean sources of the canon into a folder of your session:

```text
python <canon tool> checkout <session folder> <folder>
```

`<folder>` must lie inside your session folder and be empty or not yet exist; a relative path is taken under the session folder. The command prints the path of the copy and the revision of the canon it was taken at. The copy holds the canon's module root as it was at that moment, and later publications do not change it. That is safe to build on, because a statement of the canon never changes in place: what your files use will still be in the canon when your work is published, although proofs may have been replaced and modules added in between. A newer state of the canon is obtained by checking out again into another folder.

**Write your modules in the copy.** The copy is a module root: the folder under which `<folder>/Tri/Sums/Bound.lean` is the module `Tri.Sums.Bound`, exactly as Lean names modules, and a file anywhere under it can import any module under it by that name. Every part of a file's path under the root has to be a plain identifier, made of letters, digits and underscores and not beginning with a digit, since the path is the module's name. A module that is meant to enter the canon is written under the canon's top-level name, in the example under `<folder>/Tri/`, at a path the canon does not have yet; a new element is added in a new module, and [The canon](canon.md) explains how such a file is written. A scratch file can lie anywhere under the root.

**Build your files.**

```text
python <broker> build <instance> <folder> <file.lean>... --session <session ID> --expect-mb <MiB>
```

`<folder>` is the copy, given as an absolute path. The files after it are the targets, the ones whose output you want, given as paths under the root. `--expect-mb` is your estimate for one module compile, the largest you expect among the modules that will actually be compiled. The command waits, prints each target's Lean output as Lean produced it, and ends with one summary line listing every module's status, exit code and measured cost. For a build that may outlast your shell tool, `build ... --no-wait` prints the build ID at once and `wait <build>` collects the result later, as for a job.

### What a build does

The broker reads the import headers under the root, starting from the targets. An import whose file exists under the root is a local module and belongs to the build; any other import is an external import. An import whose file is missing under the root is therefore taken for an external import, and a mistyped name of a canon module is refused with a reason that names both readings. The broker also refuses an import cycle, and a local module whose name would shadow the imported library: one under `Init`, `Lean`, `Std` or `Lake`, or under the first component of any external import in the build, such as `Mathlib`.

Every local module that is not taken from the cache becomes one compile, and its compiled files go into a folder of the build that is on the search path of every later compile of that build. A module is taken up only after the modules it imports have compiled with exit code 0 or been taken from the cache; modules that do not depend on each other start side by side when the budget allows. The broker reads a module's source when its turn comes and compares it with what the build registered, so a file edited while its build is in progress fails that module with the reason that its source changed. Edit, and then build again.

A module whose compiler exits with errors is reported as `finished` with a nonzero `exit_code`. Modules that depend on it are not compiled: they have no job and are marked `failed` with the dependency as the reason, and the build is `failed` as well. If every module completed or was cached, the build is `finished`, including when a completed module has a nonzero compiler exit code. A successful build therefore requires both the status `finished` and zero compiler exit codes; `finished` alone does not establish success.

The summary line of a build has this form; the names and numbers are made up:

```text
lean-broker: {"build": "b…", "status": "finished", "exit_code": 0, "reason": null, "targets": ["Tri.Sums.Bound"],
  "modules": [{"module": "Tri.Defs", "status": "cached", "exit_code": 0, "cached": true, "reason": null, "measured": {"peak_mb": null, "seconds": null}},
              {"module": "Tri.Sums.Bound", "status": "finished", "exit_code": 0, "cached": false, "reason": null, "measured": {"peak_mb": 2410.7, "seconds": 38.2}}],
  "dir": "<instance>/runner/lean/builds/b…"}
```

The summary's `exit_code` reports the largest recorded nonzero compiler return code, or 0 when every recorded code is zero or no code was recorded. Successful modules cannot mask a negative return code, which is what a signal termination gives on POSIX. Each module row keeps its own code. A `finished` build returns this aggregate as the command's exit code, so the command can still report a compiler failure. A `failed` build returns 3 and a `cancelled` build returns 4; their command exit codes can therefore differ from the compiler aggregate in the summary. A build can be `failed` because a dependency's source was rejected and its dependents could not run, as well as because of an execution problem. An aggregate of 0 alone does not establish success; also inspect the build and module statuses.

Read the build's `status` and `reason` together with the module rows to find the original failure. `result <build>` gives the module job IDs; each job's `stdout.log` and `stderr.log` are under `runner/lean/jobs/<job>/`. A dependency's compiler diagnostics can be absent from the relayed target output because the target never ran. Follow those diagnostics to tell a source rejection from an unavailable compiler or a lost host before deciding what to fix.

### What is taken from the cache, and what is compiled again

A module that the broker compiled successfully is kept in the instance's cache, and a later build, by any session, that needs the same module takes its compiled files from there. Such a module is reported as `cached`; it has no job, and if it is a target its Lean output is replayed from the cache. Whether two modules are the same is decided by content and not by where the files lie: the module's name, its source bytes, the Lean environment, and the compiled output of every local module its compile reads. The runner builds the canon through the same broker when the instance is created and at each publication. The canon modules in a fresh copy are therefore normally in the cache already, and the first build in a copy compiles your own modules and takes the rest from the cache.

A module is compiled again in two cases: its own source changed, in any byte, a comment included; or something changed in what its compile reads of the local modules it reaches, which are the modules it imports and the ones those import in turn. What a compile reads of another module depends on how the importing file is written. A module compile emits a public part, which holds the statements, the exposed definitions and the compiled code, and a private part, which holds the proofs. A file written in Lean's module system, one whose first word is `module`, reads only the public part of a module it imports. So when a proof is replaced in a `module` file and the public part comes out the same, that module is compiled again and the modules that import it are taken from the cache as before.

This holds usually and not always, because the compiler settles whether the public part stayed the same, and it cannot be read off the edit. With Lean 4.32.0, a proof replaced by one that made the elaborator generate the same auxiliary declarations left the public part identical byte for byte, and so did lines shifted with nothing else changed. A changed statement or exposed definition changed it. So did an `omega` proof replaced by a term, which generates a different set of auxiliary declarations although no statement changed; everything above that module was then compiled again. How often real proofs fall on each side is not known.

A plain file, one that does not begin with `module`, reads the private part of what it imports as well, and so does a `module` file with an `import all`. Such a file is compiled again whenever any module it reaches changed at all, even in one proof. A plain scratch file that imports canon modules is in this position: it is the form that reads the proofs of what it imports, and it is compiled again after every change beneath it.

`build --fresh-targets` compiles the targets even when the cache holds them, and takes only the modules they import from the cache. Review's compile of a candidate uses it, through `commands.verify`, so that the compile of the changed modules is review's own.

## Estimating what a compile will need

Every submission carries an estimate of the compile's peak private memory. This is the number the broker reserves on when deciding whether the compile can start, so the quality of the scheduling depends on it. It is worth understanding what the broker does with the number, because that shows what kind of number to give.

The estimate is read as a probable peak: the amount that the compile will, with about ninety percent confidence, stay under. It is not meant to be the worst case. The broker reserves memory on the assumption that the compile may reach this number but is not likely to exceed it, and it pools the uncertainty of all running compiles instead of adding up their worst cases. An estimate padded up to the worst case therefore does not make the compile safer; it makes the broker hold memory idle and delays the compiles that come after, including the session's own. An estimate that is too low is not punished either, but it is visible: the broker compares every estimate with the measured peak and reports the ratio in the summary line, and what stands between an under-estimate and an over-committed machine is the margin the broker keeps for the pooled uncertainty and its check of the machine's free memory. An honest, well-reasoned number is the one that serves the session best.

The estimate is built from two parts, and the broker provides the first.

The first part is the baseline: the private memory a compile uses to load its external imports before it elaborates anything. Local modules are not part of it; what loading them costs is measured as excess above the baseline. The first time the broker sees a set of external imports in an environment, it compiles a file containing only those `import` lines and records the peak memory and the time that took. It keeps these measurements in the calibration table, `<instance>/runner/lean/calibration.json`, with one entry for each set of external imports in each Lean environment. Each entry names its external imports, the Lean version, the environment identity and the launch mode (`environment_key` and `direct`, the values `status` reports as `environment_key` and `launcher.direct`), so that the entry of the current environment can be told from one measured before a change of Lean or Mathlib. The entry records the baseline, the import time, and, as real compiles with those imports go through, how much memory each one used above the baseline and how long it ran. An entry whose calibration compile failed records the failure instead of a baseline. A session can read the entry for its external imports in the current environment and take the baseline from there. If there is no entry yet, the broker creates one before the session's compile runs, and the compile waits for it.

The second part is the allowance above the baseline: the cost of elaborating the file's proofs and, for a module of a build, of loading the local modules it imports. This is a judgment about the file that the compiling session makes from the source and the available measurements. The table below gives orders of magnitude for common proof patterns. When the calibration table already has measurements for this set of imports, those are better evidence than the table, because they come from this instance's own files.

| What the proofs do | Memory above the baseline |
|---|---|
| `rfl`, `exact`, `rw`, `intro` and `apply` chains, `simp only` with a few named lemmas, `omega` or `linarith only` with the context cleared | small: tens of MiB |
| `simp` with named lemma sets, `norm_num` on ordinary numerals, `ring`, `field_simp`, ordinary `aesop` calls, several such declarations in one file | moderate: a few hundred MiB |
| unrestricted `simp` or `simp at *` over a large import, `nlinarith` or `polyrith`, `omega` with many hypotheses, instance searches through large class hierarchies | large: around a gigabyte |
| `decide` on anything beyond tiny finite problems, `norm_num` on very large numerals, kernel reduction of big definitions, `#eval` of heavy computations | very large and hard to bound; these are also the cases worth rewriting, as the next section explains |

Lean elaborates declarations in parallel when it has more than one thread, and the broker gives each compile the number of threads set in `lean.threads`, two by default, so a file with several heavy declarations can have that many elaborating at once. Allow for that.

A build takes one estimate for all its module compiles, so give the largest you expect among the modules that will be compiled; a module taken from the cache costs nothing. For a first submission with no measured baseline, the table above supplies only the cost of the proofs, not the total. Use a measurement for comparable external imports if one is available. Otherwise take the instance's `calibration_expect_mb` setting, which your `input.json` carries under `settings.lean` and `status` shows in the configuration, as a provisional allowance for the import, add the estimated cost of the proofs and of the local modules, and say in your report that the import allowance was unmeasured. It is a starting estimate, not an upper bound; the calibration and the compile itself supply the measurements with which to revise it.

Record in your report the estimate you gave and the peak and duration the broker measured, with a note on any notable difference. This gives a reviewer a measured number to start from and lets later sessions see which results are expensive to verify again. A reviewer estimating for a candidate written by someone else has the same means: the author's reported measurement, the calibration table's entry for the imports, the files themselves, and the cost of the compile that `commands.verify` adds to its build, which [The candidate change](change-format.md) gives under "Preparing the candidate".

## Writing Lean that compiles cheaply

The broker bounds the harm of an expensive compile, but it cannot make a compile cheap. That is in the hands of whoever writes the file. The practices below are what experienced Mathlib users do as a matter of course; each is given with the reason, so that the same reasoning can be applied to cases not listed here. In a do-math session, where every compile shares one budget with every other session's compiles, they are the expected way of working.

**Import only what is used, and work out what that is before writing the imports.** A compile pays for its imports before it elaborates anything, and for an ordinary file the imports are most of the cost. In one instance, files that imported the real numbers, finite sums and the tactics `ring`, `linarith`, `positivity` and `field_simp`, each from its own module, had a baseline of about 2,200 MiB, and their proofs added less than 70 MiB to it. So think about the imports of a file as concretely as about its statements. Name what the file uses: the objects it speaks of, such as the real numbers, finite sums or binomial coefficients; the lemmas it calls by name; and the tactics its proofs run. Each of these is defined in a module, and a Mathlib tactic usually has a module of its own, such as `Mathlib.Tactic.Ring` or `Mathlib.Tactic.Linarith`. Import those modules, and leave out what the file does not use.

Two imports bring in far more than any one file uses. `import Mathlib` loads the whole of Mathlib and builds Lean's full private index on every compile. `import Mathlib.Tactic` loads every tactic of Mathlib together with everything those tactics import: in the same instance a file with that line and three small imports had a baseline of about 3,900 MiB, against the 2,200 MiB above. Broad imports are fine while looking for lemma names, but not in a file that is compiled over and over or that other modules import.

An import is inherited. A compile reaches the local modules its file imports and the local modules those import in turn, and it loads the external imports of every one of them. An import written in one module is therefore paid again by the compile of every module that reaches it. The broker's baseline covers only the external imports written in the compiled file itself, so what a file inherits appears as excess above its baseline and not in the baseline. In the instance above, one module near the bottom of the library carried `import Mathlib.Tactic` and most of the other modules reached it. Their compiles took about 4,000 MiB each, and the instance's memory budget admitted them one at a time. A needless import therefore costs most in a module that many others import. The modules that hold the canon's definitions are such modules, because every other module of the instance imports them. Importing a canon module also brings in every local module it reaches, and each of those is one more thing whose change compiles your file again.

Once a proof is finished, Mathlib can report what a file needs, within limits that matter here. `#min_imports`, written at the end of a file, looks only at the declarations the file refers to and not at its tactics and notation. Its answer can therefore lack the tactic modules, and a file whose imports are replaced by it can fail to compile. `#min_imports in`, placed before one declaration, and the option `linter.minImports`, which goes down a file and keeps the set of imports needed so far, do take tactics and notation into account. They are defined in `Mathlib/Tactic/MinImports.lean` and `Mathlib/Tactic/Linter/MinImports.lean`, and the opening comment of each file says how the tool is used and what it misses.

**Compile fewer times, and compile less each time.** Every compile waits its turn, and every compile pays for its import again in full, so there is no saving from compiling often. For a development with several interdependent statements, first compile the statements together, their proofs left as `sorry`, before investing in the proofs: an error in a statement is cheap to find before the argument is built on it. In the canon a statement whose Lean proof is not written stands in exactly this form. A small direct proof may already fit in that one compile. Then fill in proofs a few at a time. When one lemma is hard, work on it in a file of its own that imports only what the lemma depends on, and move the finished proof back.

**Keep what is still changing apart from what has stopped changing.** A module is one compile and one cache entry, and every edit of its source, in any byte, elaborates the whole of it again. Declarations that are finished are therefore cheaper in a module of their own than beside the declarations still being worked on, where each edit pays for their proofs once more. A file written as a `module` is also cheaper than the same content as a plain file: on a file importing the Lean metaprogramming library, with Lean 4.32.0, the commit charge went from 2,078 to 1,680 MB and the elapsed time from 8.7 to 5.7 seconds. This was not measured with Mathlib imports.

**Turn successful searches into reusable proofs.** `exact?`, `apply?`, `rw?`, `simp?`, `aesop?`, `hint` and `polyrith` search the imported library. Their cost grows with the size of the import, and they are the most common reason a small file compiles slowly. Once a search finds the needed proof, use its explicit term or the `simp only [...]` call reported by `simp?` where practical. This saves repeating the search at every compile and makes the dependency that succeeded visible. Judge the benefit for the actual file; the purpose is verification that can be repeated economically.

**Keep automation bounded.** Write `simp only [a, b]` in place of a bare `simp`, and `linarith only [h1, h2]` in place of `linarith`. Before calling `omega`, `linarith` or `nlinarith`, `clear` the hypotheses they do not need, because they consume the whole context and `nlinarith` grows combinatorially with it. Use `norm_num` for arithmetic on numerals and not `decide`: `decide` is evaluated by the kernel, which has no heartbeat limit, and a large `decide` is the classic way for a compile to take gigabytes without producing any error before the operating system steps in. Under the default axiom policy, `native_decide` introduces an axiom that is not allowed; see Formal acceptance below. When instance search is slow, give the instance explicitly with `haveI` or `(inst := ...)`. While iterating, put `set_option maxHeartbeats 50000 in` before a declaration so that a runaway tactic fails within seconds; raise the limit locally, with `in`, only for a proof that needs it.

**Measure before optimizing.** Mathlib's `count_heartbeats in theorem ...` prints what a declaration costs in heartbeats. `set_option profiler true` prints the time of each step. `set_option trace.Meta.synthInstance true` shows an instance search that is looping, and `set_option trace.Meta.Tactic.simp.rewrite true` shows what `simp` is rewriting. The broker's measured peak and duration are the same kind of evidence for the file as a whole.

**Shape the file for how Lean runs it.** Prefer small lemmas to one large `by` block so that each proof is easier to elaborate, profile and revise. Splitting a proof does not guarantee lower process memory: Lean can retain allocated memory for reuse, and several declarations may elaborate in parallel. Estimate for the actual file and thread count. Give every `have` its type, so that Lean does not have to infer a large term. Mark heavy definitions `@[irreducible]`, or define them with `irreducible_def`, so that tactics do not unfold them by accident. Use `rw` for a single rewrite, and `show` or `change` to fix the goal before handing it to automation.

## Formal acceptance

A compile that succeeds shows that Lean accepts the file as written. It does not yet show that a statement has been proved formally. A proof may end in `sorry`, as the informal proofs of the canon do by design, or it may rest on an axiom the instance has not allowed, and Lean accepts the file in both cases. What decides is the set of axioms the statement depends on.

**When a statement is formal.** A statement of the canon is formal when every axiom it depends on is in the instance's allowed list. The dependence is followed through everything the statement uses: the canon elements that its proof and its statement name, what those use in turn, and the declarations of the imported library. An axiom declared in the canon counts in the same way, whatever its name or visibility: a private axiom, and the axiom that `native_decide` adds for each computation to the module that uses it, are among the axioms of every statement that rests on them. The allowed list is `settings.lean.allowed_axioms` in your `input.json`. By default it holds `propext`, `Classical.choice` and `Quot.sound`, and an instance may explicitly allow more. `sorryAx`, the axiom that stands for a `sorry`, is never allowed, and the settings refuse a list that contains it.

Because the dependence is followed through the canon, a hole in a lemma appears among the axioms of everything that rests on that lemma, even when the file of the final theorem contains no `sorry`. A statement is therefore formal only when its own proof and the proofs of all the canon statements it rests on are complete in Lean. Conversely, the word `sorry` in a comment has no significance. The evidence is the list of axioms that a compile reported, not the text of a source. `native_decide` can introduce axioms of its own and must not be treated as within the default list.

**Where the axioms are read.** For a published element, `commands.canon view <element>` shows its axioms and says whether it is proved in Lean from the allowed axioms. For a candidate, `commands.prepare` prints the axioms of each theorem the candidate adds or whose proof it replaces, followed through the canon in the same way, and `commands.verify` prints the same for review. A producing session that wants the axioms of its own theorem before a peer prepares the work can put `#print axioms <theorem>` in a plain file that imports the theorem's module and build that file. The file has to be plain because a `module` file does not read the proofs of the modules it imports, so do not rely on `#print axioms` in a `module` file for a theorem of another module; that case was not tested. Inside the theorem's own file the command reports its axioms correctly, `sorryAx` included (tested on Lean 4.32.0), so a line `#print axioms <theorem>` at the end of your working module serves as well while you work. Remove it before you hand the module on.

**Review's own compile.** Review does not rest a formal verdict on the peer's build or on anyone's account of one. It runs `commands.verify`, which applies the frozen candidate to a copy of the canon as it then is, compiles the changed modules afresh in the reviewing session's name, and prints the axioms of each statement. Review reads those axioms. When review confirms a proof that is complete in Lean, its assessment names the build that `commands.verify` reported, and the transport check confirms that this build is the reviewing session's own, that it finished, that it compiled the changed modules afresh, and that it is the build of the last successful `commands.verify`. [Review output](review-output.md) specifies the field.

**What Lean settles, and what remains a judgment.** The statement of the root was fixed in Lean when the instance was created. The theorem to be proved is that declaration itself, so no separate comparison of a proved theorem with the proposition is made. A proof of the root enters as the proof of that declaration, or as another declaration whose record says that it proves the root's statement, which Lean confirms by checking that the two statements are identical; a refutation is a declaration whose statement Lean confirms to be the negation of the root's. The root is formally proved or refuted when such a proof or refutation is formal and is settled, that is, accepted by review with everything it rests on settled, and the instance is then complete.

What Lean cannot settle is whether a statement or a definition says what was meant. Lean checks that a proof proves the statement as written. Whether each new statement of a candidate says what was meant by it, and whether each new definition denotes the object it was meant to denote, is review's judgment. Review makes it by reading the Lean text against the record, and the producer and the peer owe the same care before review.

**Outcomes to keep apart.** A compile that could not run leaves the formal check incomplete; it is not Lean rejecting the source. A source that Lean rejects, a proof that depends on an axiom outside the allowed list, and a complete proof of a statement that does not say what was meant have different consequences, and a report or an assessment names the exact case. A development that is not yet formal is still part of the canon: a statement whose Lean proof ends in `sorry` is an ordinary element, with an informal proof or none, and it is published with that standing.
