# Lean compilation and formal evidence

This document explains how Lean is run inside a do-math instance, why it is run that way, and what a session needs to know to use it well. It starts from what a Lean compile is and what it costs, because everything else follows from that.

## What a Lean compile is, and what it costs

When a session has written a Lean file and wants to know whether the proofs in it are correct, it has Lean check the file. Lean reads the file from top to bottom, loads every library module the file imports, elaborates each definition and theorem in turn, and reports errors, warnings and the output of commands such as `#print axioms`. In this document that whole run of Lean over one file is called a compile, and the process that performs it is a Lean process.

A compile takes time, and with Mathlib it takes a lot of it. Most of that time is spent at the start, loading the imported modules: a file that imports all of Mathlib reads several gigabytes of compiled library from disk before it looks at the first theorem. When those files are not yet in the operating system's cache, that alone took seven minutes on the machine this project was developed on. Time, though, only delays a result. A slow compile is a nuisance; it does not harm anything else that is running.

Memory is different. A compile that takes more memory than the machine has left does not merely run slowly; it pushes the machine into swapping, or gets itself or some other process killed, and every session on the machine suffers. So memory is what this document is mostly about, and to reason about it one has to know that a Lean process uses memory in two ways that behave very differently.

The first is the imported library itself. Lean maps the compiled modules into memory directly from the files on disk. The operating system treats such mappings as a cache: it keeps one copy of each file in memory no matter how many Lean processes are using it, and it can drop pages and read them again when memory is short. So this part of a compile's memory is shared between compiles, and under pressure it slows things down but does not run the machine out of memory.

The second is the memory that belongs to one Lean process alone. On import, Lean builds its own indexes over everything it loaded: the table of names, the sets of `simp` lemmas, the instances, the notations. For all of Mathlib this comes to about a gigabyte, and every running compile builds its own copy. Then, as the file's proofs are elaborated, Lean allocates terms, goals, tactic states and caches, and this part grows with what the proofs do: a `rfl` costs almost nothing, while an unbounded `simp` over all of Mathlib or a large `decide` can take gigabytes. Lean keeps the memory it has freed for reuse rather than returning it to the system, so within one compile this private memory mostly grows, and it reaches its peak late.

Of the two, it is the private memory that has to be managed. The shared library costs the same whether one compile or five are running; the private memory is paid once per compile, and it is the sum over all running compiles that must stay within what the machine has. That sum is what nothing used to control. Up to eight sessions could each start a compile whenever they liked, with nothing between them, and several Mathlib compiles at once were enough to make the machine unstable.

## The Lean broker

To prevent that, each instance runs a single process called the Lean broker, and every compile in the instance goes through it. The runner starts the broker when it starts and keeps it running for as long as the runner itself runs. A session does not run Lean itself; it asks the broker to compile a file, and the broker decides when to start that compile, runs it, and hands the result back.

Because the broker sees every compile of the instance, it can do several things that no session could do on its own.

It schedules compiles against a shared memory budget. A session tells the broker, when it submits a file, how much private memory it expects the compile to need. The broker uses that estimate, together with what it has measured itself, to decide whether the compile can start now or must wait for others to finish.

It measures every compile. While a compile runs, the broker reads how much private memory the Lean process is using and keeps the peak; when the compile ends, it records the peak and the duration, returns them to the session, and adds them to a table it keeps for the instance. So the cost of every proof becomes visible, and the broker's later decisions are based on what compiles in this instance have actually cost, not only on what sessions predicted.

It keeps a compile alive independently of the session's shell tool. The shell tools of the CLIs give up on long commands, as [Tools](tools.md) describes, and a Mathlib compile can outlast them. A compile submitted to the broker is a job that continues, and keeps its result, whatever happens to the command that submitted it. The session can come back for the result as many times as it needs.

It cleans up after sessions that have ended. A compile whose session has finished, failed or been killed has no one left to read its result; it only takes memory. The broker cancels such compiles. Apart from a cancellation that a session asks for itself, this is the only situation in which the broker stops a compile: it never stops one for using more memory than was estimated.

There are also things the broker does not do, and it helps to know them from the start. It compiles one file per job with the `lean` command from the instance's settings; it does not run `lake build`, and it does not keep a Lean environment loaded between compiles to save the import time. Each compile imports everything it needs from scratch. And it does not limit how long a compile may run.

## Compiling a file

Your input.json contains the broker command prefix and your session ID. In the examples below, python stands for the interpreter in that prefix and <broker> for the complete broker script path it supplies. The general single-file command is

```text
python <broker> run <instance> <file.lean> --session <session ID> --expect-mb <MiB>
```

where `<file.lean>` is the absolute path of the file to compile, `<session ID>` is the session's own ID as given in its launch prompt, and `<MiB>` is the session's estimate of the compile's peak private memory, in mebibytes. The Estimating what a compile will need section below explains how to arrive at that number.

The broker compiles the file with the `lean.command` of `settings.json`, adding the thread count it has been configured with and the path of the file. The working directory is `lean.cwd` from the settings, or the session's folder when that is `null`. When the compile finishes, the command prints Lean's output exactly as Lean produced it, the standard output on standard output and the standard error on standard error, so that error messages, `#print axioms` lines and `sorry` warnings read as they would from Lean. It then exits with Lean's exit code. The last line on standard error is a summary from the broker:

```text
lean-broker: {"job": "j…", "status": "finished", "exit_code": 0, "reason": null, "expect_mb": 1800,
  "measured": {"peak_mb": 1466.2, "baseline_mb": 1103.5, "excess_mb": 362.7, "seconds": 41.3, "estimate_ratio": 0.81, …},
  "dir": "<instance>/runner/lean/jobs/j…"}
```

The numbers in this line are made up to show the fields. `peak_mb` is the highest private memory the broker measured during the compile, `baseline_mb` is what the compile's imports alone cost (explained below), `excess_mb` is the difference, `seconds` is how long the compile ran, and `estimate_ratio` is the measured peak divided by the estimate. `dir` is the folder where the broker keeps the job's files: Lean's output in `stdout.log` and `stderr.log`, the job's record in `result.json`, and a few process receipts. The output can be read again from there at any time.

For a single-file job, `finished` means that Lean ran to the end; inspect its `exit_code` to distinguish compiler success from rejection. Status `failed`, with command exit code 3 and a `reason`, means that the request could not be accepted, the file disappeared, Lean could not start, or its supervising process was lost. Status `cancelled` has command exit code 4. An execution failure or cancellation leaves formal verification incomplete and does not establish a defect in the mathematical claim. A module build aggregates several such outcomes differently, as explained under Compiling a file that imports your own modules below.

Invocation errors belong to the broker client rather than to Lean's assessment of a source file. For example, malformed options or an input rejected before submission can end the command before a job is accepted. Correct that invocation from its diagnostic. An error while waiting for an already submitted job is different: failure to contact or restart the broker does not establish that the job vanished or that Lean rejected the source. Keep the job ID, inspect status and the retained logs, and recover that job's outcome before deciding whether another submission is needed. The command's exit code alone cannot distinguish these phases.

### When the shell tool will not wait

The `run` command waits for the compile, and a compile can take longer than a CLI's shell tool is willing to wait: Claude's tool moves a command to the background after 120 seconds, or after 600 seconds if a `timeout` is given, and abandons it ten minutes after that; Codex's tool returns after about ten seconds and expects the session to poll. A compile that imports Mathlib, or that has to wait its turn behind other compiles, can exceed both.

For such compiles, submit and wait in two steps:

```text
python <broker> submit <instance> <file.lean> --session <session ID> --expect-mb <MiB>
python <broker> wait <instance> <job> --timeout 500
```

`submit` returns at once and prints the job ID. `wait` returns either the finished result, printed exactly as `run` would print it, or, if the timeout passes first, exit code 124 and a note that the job is still running. Nothing is lost between calls; `wait` can be run again and again until the result is there. If a `run` was started and its shell tool gave up, the same recovery works, because the job ID is the first thing `run` prints on standard error.

Submitting the same unchanged file again from the same session, while its earlier job is still queued or running in the same Lean environment, does not start a second compile. The broker answers the new submission with the ID of the job already in progress, and waiting on either ID gives the same result. A file edited after its submission is a different source. Its new submission becomes a job of its own, and an earlier job that has not yet started fails with the reason that its source changed after submission.

### The other commands

| Command | What it does |
|---|---|
| `build <root> <file.lean>...` | Compiles the files together with every module of your own that they import; the next section explains it. |
| `result <job>` | Prints the job's or build's record as it currently stands. |
| `status` | Prints whether the broker is alive, the configuration it is using, the Lean version, the jobs that are queued, running and recently finished, each with its estimate, its reservation and its measurements, and the builds in progress. |
| `cancel <job>` | Cancels one of your own jobs, or every compile of one of your own builds, that you no longer need. |
| `version` | Prints the Lean version string, which the broker obtained by running `version_command` once. This is the string to put in the retained account of the environment, and it is the reason there is never a need to run Lean directly, even for `--version`. |

`cancel` records a cancellation request for a job or build, including while the broker is accepting it. The response acknowledges the request; use `wait` on the same ID to obtain the final outcome. A confirmed cancellation has status `cancelled` and returns exit code 4, including when no compile started. Work that had already completed retains its completed outcome. Cancelling a duplicate submission requests cancellation of the original job or build to which it refers.

All of these take the instance path as their first argument, like `run`.

## Compiling a file that imports your own modules

Lean finds an imported module not in its source but in its compiled form, the `.olean` file, on a search path that holds the library and nothing of yours. A file that imports a module you wrote therefore does not compile on its own: the module has to be compiled first, as a module, into a place on the search path. The `build` command does all of that.

```text
python <broker> build <instance> <root> <file.lean>... --session <session ID> --expect-mb <MiB>
```

`<root>` is the module root: the folder under which `<root>/Foo/Bar.lean` is the module `Foo.Bar`, exactly as Lean names modules. The files after it are the targets, the ones whose output you want, given as paths under the root. `--expect-mb` is your estimate for one module compile, the largest you expect among them. The command waits, prints each target's available Lean output as Lean produced it, and ends with one summary line listing every module's status, exit code and measured cost. For a build that may outlast your shell tool, `build ... --no-wait` prints the build ID at once and `wait <build>` collects the result later, as for a job.

The summary's `exit_code` reports the largest recorded nonzero compiler return code, or 0 when every recorded code is zero or no code was recorded. Successful modules cannot mask a negative return code, which Python uses on POSIX for signal termination. Each module row retains its original code. A `finished` build returns this aggregate, so it can still report compiler failure. A `failed` build returns 3, and a `cancelled` build returns 4; their command exit codes can therefore differ from the compiler aggregate in the summary. A build can be `failed` because a dependency's source was rejected and its dependents could not run, as well as because of an execution problem. An aggregate of 0 alone does not establish success; also inspect the build and module statuses.

Read the build's `status` and `reason` together with the module results to find the original failure. `result <build>` gives the module job IDs; each job's `stdout.log` and `stderr.log` are under `runner/lean/jobs/<job>/`. A dependency's compiler diagnostics can be absent from the relayed target output because the target never ran. Follow those diagnostics to distinguish a source rejection from an unavailable compiler or lost host before deciding what to fix and recording what review checked.

What the broker does with a build:

- It reads the import headers under the root, starting from the targets. An import whose file exists under the root is one of your modules and is compiled too; any other import is the library's. It refuses an import cycle, and a module of yours whose name would shadow the toolchain's or a library module's (`Init`, `Lean`, `Std`, `Lake`, or the first component of any library import in the build, such as `Mathlib`).
- Every module of yours becomes one compile, run with `-R <root>` so that it is named correctly and `-o` so that its `.olean` lands in the build's own lib folder, which is put on the search path of every later compile of the build. A module starts only after the modules it imports have compiled with exit code 0; modules that do not depend on each other start side by side when the budget allows. A module whose compiler exits with errors is reported as `finished` with a nonzero `exit_code`. Modules that depend on it are not compiled and are marked `failed` with the dependency reason, making the build `failed` as well. If every module completed or was cached, the build is `finished`, including when a completed module has a nonzero compiler exit code. A successful build requires `finished` status and zero compiler exit codes; `finished` alone does not establish success.
- A compiled module is kept in the instance's cache under a key made of the Lean version, the module's name, its source bytes and the keys of the modules it imports. A later build, by any session, that needs a module with the same key can reuse it; it is reported as `cached`, and if it is a target its Lean output is replayed from the cache. A change in a module changes its key and the keys of the local modules that import it, preventing reuse under the earlier source identity. The cache holds only broker-built modules. Its key also includes an environment identity computed from lean.command, lean.cwd, lean.env and lean.cache_epoch. The detected Lean version is included separately. Change cache_epoch when replacing Lean libraries or changing the same library installation in place; a version string alone does not identify those changes.

Because the key is the content, copying published sources into your own folder and building them there avoids re-elaborating unchanged cached modules: a reviewer can reuse unchanged dependency modules while independently compiling the final targets. Review uses `build --fresh-targets`, which forces the targets to compile even when their bytes already occur in the cache. Use one module root, conventionally lean/, with the source modules needed for the result inside it. The producing session identifies this source tree in its retained report. The peer lists its files in each solution's lean.sources field in record.json, so later formalizers and reviewers can find the published sources.

The cost of a module compile is measured and calibrated by its library imports alone; the `.olean` files of your own modules that it loads count in the measured excess, as a proof's elaboration does. Each module needs an `--expect-mb` that covers its own compile, which is why the one value you give should be the largest of them. The lib folder of a build is kept under `runner/lean/builds/<build>/lib` until the build is pruned from the broker's state, and the cache lives under `runner/lean/cache/`, outside the instance's Git.

## Estimating what a compile will need

Every submission carries an estimate of the compile's peak private memory. This is the number the broker reserves on when deciding whether the compile can start, so the quality of the scheduling depends on it. It is worth understanding what the broker does with the number, because that shows what kind of number to give.

The estimate is read as a probable peak: the amount that the compile will, with about ninety percent confidence, stay under. It is not meant to be the worst case. The broker reserves memory on the assumption that the compile may reach this number but is not likely to exceed it, and it pools the uncertainty of all running compiles rather than adding their worst cases, as the section on scheduling explains. An estimate padded up to the worst case therefore does not make the compile safer; it makes the broker hold memory idle and delays the compiles that come after, including the session's own. An estimate that is too low is not punished either, but it is visible: the broker compares every estimate with the measured peak and reports the ratio in the summary line, and the pooled spread and the machine gate, described under scheduling, are what stand between an under-estimate and an over-committed machine. An honest, well-reasoned number is the one that serves the session best.

The estimate is built from two parts, and the broker provides the first.

The first part is the baseline: the private memory used to load the file's library imports before elaborating its proofs. For a module build, this calibration excludes modules supplied under your module root; the cost of loading those local modules is measured as excess above the library baseline. The first time the broker sees a set of library imports in an environment, it compiles a file containing only those `import` lines and records the peak memory and the time that took. It keeps these measurements in the calibration table, `<instance>/runner/lean/calibration.json`, keyed by the library imports and environment identity. Each entry records the baseline, the import time, and, as real compiles with those imports go through, how much memory each one used above the baseline and how long it ran. An entry whose calibration compile failed records the failure instead of a baseline. A session can read the entry for its library imports and take the baseline from there. If there is no entry yet, the broker creates one before the session's compile runs, and the compile waits for it.

The second part is the allowance above the library baseline: the cost of elaborating the file's proofs and, for a module build, loading its local dependencies. This is a judgment about the file that the compiling session makes using the source and available measurements. The table below gives orders of magnitude for common proof patterns. When the calibration table already has measurements for this set of imports, those are better evidence than the table, because they come from this run's own files.

| What the proofs do | Memory above the baseline |
|---|---|
| `rfl`, `exact`, `rw`, `intro` and `apply` chains, `simp only` with a few named lemmas, `omega` or `linarith only` with the context cleared | small: tens of MiB |
| `simp` with named lemma sets, `norm_num` on ordinary numerals, `ring`, `field_simp`, ordinary `aesop` calls, several such declarations in one file | moderate: a few hundred MiB |
| unrestricted `simp` or `simp at *` over a large import, `nlinarith` or `polyrith`, `omega` with many hypotheses, instance searches through large class hierarchies | large: around a gigabyte |
| `decide` on anything beyond tiny finite problems, `norm_num` on very large numerals, kernel reduction of big definitions, `#eval` of heavy computations | very large and hard to bound; these are also the cases worth rewriting, as the next section explains |

Lean elaborates declarations in parallel when it has more than one thread, and the broker gives each compile the number of threads set in `lean.threads` (two by default), so a file with several heavy declarations can have that many elaborating at once. Allow for that.

For a first submission with no measured library baseline, the table above supplies only the additional proof cost, not the total estimate. Use a measurement for comparable library imports if one is available. Otherwise use the configured `calibration_expect_mb` as a provisional import allowance and add the estimated proof and local-dependency costs; explain that the import allowance is unmeasured. It is a starting estimate, not an upper bound. Calibration and the actual compile supply measurements with which to revise it. Afterwards, the verification account should record the estimate given and the peak and duration measured, with a note on any notable difference. This gives a reviewer a measured number to start from and lets later researchers see which results are expensive to verify again.

A reviewer estimating for a file written by someone else has the same means: the author's reported measurement, the calibration table's entry for the file's imports, and the file itself. Appending `#print axioms` lines to a working copy does not change its cost.

## Writing Lean that compiles cheaply

The broker bounds the harm of an expensive compile, but it cannot make a compile cheap. That is in the hands of whoever writes the file. The practices below are what experienced Mathlib users do as a matter of course; each is given with the reason, so that the same reasoning can be applied to cases not listed here. In a do-math session, where every compile shares one budget with every other session's compiles, they are the expected way of working.

**Import only what is used.** `import Mathlib` loads the whole library and builds Lean's full private index on every compile. Importing only the modules actually needed cuts both the baseline and the import time by an order of magnitude or more. Start from the modules the relevant objects are defined in. Once a proof is finished, Mathlib's `#min_imports` command prints the smallest set of imports the file needs; replace the imports with its answer. Broad imports are fine while looking for lemma names, but not in the file that is compiled over and over.

**Compile fewer times, and compile less each time.** Every compile imports from scratch, so there is no saving from compiling often. For a development with several interdependent statements, first type-check the statements together before investing in their proofs. Temporary `sorry` holes can support this check when clearly identified as unfinished: statement errors are cheap to find before building the arguments. A small direct proof may already fit in one complete compile. Then fill in proofs a few at a time. When one lemma is hard, work on it in a scratch file that contains only the imports and the statements it depends on, and move the finished proof back. And before the final compile, append the `#print axioms` lines to the working copy, so that the proof and its axiom check are one compile rather than two.

**Turn successful searches into reusable proofs.** `exact?`, `apply?`, `rw?`, `simp?`, `aesop?`, `hint` and `polyrith` search the library. Their cost grows with the size of the import, and they are the most common reason a small file compiles slowly. Once a search finds the needed proof, use its explicit term or the `simp only [...]` call reported by `simp?` where practical. This saves repeating the search at every compile and makes the successful dependency clear. Judge the benefit for the actual file; the purpose is reusable, economical verification.

**Keep automation bounded.** Write `simp only [a, b]` rather than bare `simp`, and `linarith only [h1, h2]` rather than `linarith`. Before calling `omega`, `linarith` or `nlinarith`, `clear` the hypotheses they do not need, because they consume the whole context and `nlinarith` grows combinatorially with it. Use `norm_num` for arithmetic on numerals rather than `decide`: `decide` is evaluated by the kernel, which has no heartbeat limit, and a large `decide` is the classic way for a compile to take gigabytes without producing any error before the operating system steps in. Under the default axiom policy, `native_decide` introduces an unapproved axiom; see Formal proof acceptance below. When instance search is slow, give the instance explicitly with `haveI` or `(inst := ...)`. While iterating, put `set_option maxHeartbeats 50000 in` before a declaration so that a runaway tactic fails within seconds; raise the limit locally, with `in`, only for a proof that needs it.

**Measure before optimizing.** Mathlib's `count_heartbeats in theorem ...` prints what a declaration costs in heartbeats. `set_option profiler true` prints the time of each step. `set_option trace.Meta.synthInstance true` shows an instance search that is looping, and `set_option trace.Meta.Tactic.simp.rewrite true` shows what `simp` is rewriting. The broker's measured peak and duration are the same kind of evidence for the file as a whole.

**Shape the file for how Lean runs it.** Prefer small lemmas to one large `by` block so that each proof is easier to elaborate, profile and revise. Splitting a proof does not guarantee lower process memory: Lean can retain allocated memory for reuse, and several declarations may elaborate in parallel. Estimate for the actual file and thread count. Give every `have` its type, so that Lean does not have to infer a large term. Mark heavy definitions `@[irreducible]`, or define them with `irreducible_def`, so that tactics do not unfold them by accident. Use `rw` for a single rewrite, and `show` or `change` to fix the goal before handing it to automation.

**Across sessions.** Producers retain their sources and measured cost. Peers can develop those sources while preparing the record. Review independently compiles the final candidate with its axiom inspection commands. The candidate and reviewer working copies are linked by the source hashes described in [Review output](review-output.md).

## How the broker decides what runs

A session does not need this section to use the broker, but it makes the output of `status` readable and explains why a compile is waiting. The broker has no limit on the number of compiles running at once. It has a memory budget and a thread budget, and it starts the next compile when both have room for it.

**The memory rule.** For each compile that is running, and for the one the broker is considering, it forms a reservation made of three numbers. The first is the certain part: the baseline for the compile's imports, because every compile with those imports will reach it, replaced by the compile's measured memory once that has grown past the baseline. The second is the expected excess: how much more the compile is expected to take above the certain part. The third is the spread: how uncertain that expectation is. The expected excess and the spread are derived from the session's estimate, read as a ninetieth percentile, and from the spread the broker has observed for that set of imports in this instance, using `default_spread` until there are measurements. As a compile runs and its measured memory grows, what it has already taken moves into the certain part, and what the expectation had already predicted is no longer counted again.

For a known baseline B and a submitted estimate E, the estimated excess is max(0, E - B). Let v be the observed standard deviation divided by the mean excess when that ratio is available and nonzero, or default_spread otherwise. The broker sets the excess mean m = max(0, E - B) / (1 + 1.2816 v) and its spread s = v m. Thus m + 1.2816 s equals the submitted excess estimate. Before any runtime measurement, the certain part is B. If the measured private memory reaches C greater than B, the certain part becomes C and the remaining expected excess becomes max(0, B + m - C); the spread stays s. Without a measured baseline, the broker reserves the entire estimate as certain and adds a spread of one quarter of that estimate. These are model-based reservations, with observed memory and the machine gate providing additional information.

A compile can start when, over the running compiles and the candidate together,

```text
sum of certain parts + sum of expected excesses + confidence × sqrt(sum of squared spreads) ≤ memory_budget_mb
```

The certain parts and the expectations are simply added. The spreads are not: they are combined under a square root, under an approximation that their uncertain excesses can be pooled independently. Jobs can in fact share expensive phases, so this approximation is not a guarantee that simultaneous peaks will be avoided. Four uncertain compiles need about twice the safety margin of one, not four times. This is what lets several compiles share the budget. The `confidence` setting is the one knob: at 1.3, the default, it adds a margin of 1.3 pooled standard deviations; at 2 the margin is larger; at 0 only the expectations and certain parts are reserved. These are scheduling estimates, not measured guarantees of overflow probability. Correlated jobs and inaccurate estimates can weaken the model, which is why the machine gate and observed costs matter. Adding up every compile's full estimate instead would be the infinitely cautious end of the same scale, and it is not the rule because it would leave most of the budget idle most of the time. (The rule is the equivalent-capacity admission control used in communication networks; the problem is the same.)

**The thread budget.** Each compile reserves the number of threads in `lean.threads`; a calibration compile reserves one. A compile can start when the reserved threads, with its own, do not exceed `cpu_threads_budget`. The default budget is twice the number of logical cores, on purpose: a compile uses its threads only while elaborating, not while loading imports, so letting one compile's import overlap another's elaboration keeps the cores busy.

**The machine gate.** Whatever the budgets say, a compile starts only if the machine's actual free memory (`MemAvailable` on Linux, the commit headroom on Windows) would remain above `min_free_memory_mb` after the compile's certain part is taken. The budgets know nothing about the CLI processes, the archiver, another instance on the same machine, or anything else that uses memory. The gate is what sees them.

**The order.** Queued compiles are considered in the order they were submitted, and the first one that fits is started. A compile that does not fit yet is passed over, so a small core-only compile can go ahead of a queued Mathlib compile that is waiting for memory. Passing over is limited, so that a stream of small compiles cannot keep a large one waiting forever: each queued compile counts how many later compiles have started ahead of it, and once that count reaches `max_passes` (three by default), nothing behind it may start until it has. The running compiles then finish on their own, and as soon as the waiting compile fits, it starts. This bounds the number of later compiles that can pass it. It does not bound elapsed waiting time, because running compiles have no time limit and the machine gate must still permit a start. When no compile is running, the broker permits one eligible compile to exceed the memory or thread budget so that an oversized job is not excluded forever. The machine gate still applies: that job waits if the required free-memory headroom is unavailable.

**Calibration.** A compile whose imports have no entry in the calibration table waits for a calibration compile of those imports, which the broker creates itself: a file of only the `import` lines, compiled with one thread and reserved at `calibration_expect_mb`, since its cost is by definition not yet known. Its measured peak becomes the baseline and its duration the import time. If Lean runs the calibration compile and rejects it, for instance because an import does not exist, the failure is recorded in the table instead of a baseline, and compiles with those imports go ahead on their own estimates, with the whole estimate treated as certain, and succeed or fail on their own terms; the recorded calibration is reused for that import set and environment identity; a changed Lean version, environment configuration or cache_epoch creates a new calibration key. If the calibration compile could not be run at all, or was cancelled, nothing is recorded. The compiles that were waiting for it go ahead on their own estimates in the same way, so a Lean that cannot start is reported as the compile's own `failed` result rather than an endless wait, and the next compile submitted with those imports triggers calibration again.

**Cancellation.** A compile is cancelled, and its process tree terminated, when the AI session that submitted it has ended. The broker recognizes that end from the runner's recorded session state or from the death of both its host and CLI. The later peer and review processing does not keep that producer's unfinished compiles alive. Such a compile has no reader, and compiles like this are how orphaned Lean processes used to pile up after a shell tool's ten-minute abandonment or a `kill-session`. The `cancel` command does the same on request. Nothing else stops a compile; there is no time limit and no memory limit on one that is running.

**Measurement.** Four times a second, the broker reads the private memory of the compile's whole process tree, since `lake env lean` is two processes, and keeps the highest value. When the compile ends it records the excess above the baseline and the duration in the calibration table, the ratio of measured peak to estimate in the job's summary, and the whole job in its `result.json`.

## Settings

The broker's settings live in the `lean` block of `settings.json`, alongside `command`, `version_command`, `cwd` and `env`. These resource keys are optional and receive the defaults below.

| Key | Meaning | Default |
|---|---|---|
| `memory_budget_mb` | The private memory the broker may have reserved for compiles at one time | `null`, which means the machine's physical memory minus `min_free_memory_mb` minus 512 MiB for each of `max_sessions`, and at least 1024 |
| `confidence` | The multiplier of the pooled spread in the memory rule | `1.3` |
| `min_free_memory_mb` | The machine gate: how much free memory must remain after a compile starts | `2048` |
| `cpu_threads_budget` | How many threads the running compiles may reserve together | `null`, which means twice the number of logical cores |
| `threads` | The `--threads` value given to each compile | `2` |
| `priority` | The process priority of every compile: `below_normal`, `normal` or `idle` | `below_normal` |
| `max_passes` | How many later compiles may start ahead of a queued compile that does not fit before it closes the queue behind it; `0` makes the order strictly first come, first served | `3` |
| `calibration_expect_mb` | The memory reserved for a calibration compile, whose cost is by definition not yet known | `2048` |
| `default_spread` | The spread of a compile's elaboration excess relative to its mean, used for a set of imports until the broker has measured its own; `0` reserves the expected excess only | `0.5` |

The keys are validated at instance initialization and when the runner starts, so an invalid value stops a starting runner with the error in its start log. A running runner rereads `settings.json` when it changes; an invalid edit leaves its last valid settings in force and appears as `settings_error` in the runner state that `status` returns. The broker validates the keys again when it starts, since a session may start it while no runner is running.

The broker re-reads `settings.json` whenever the file changes. When a valid change is detected on a poll, the broker applies it and records it in `runner/lean/broker.log`; an invalid one is logged and ignored, and the last valid configuration stays in force. The `status` command shows both the configuration in force and any current `config_error`. The Lean version is read once, when the broker starts, and calibration entries are keyed by it, so after changing Lean or Mathlib, stop new dispatch and let active sessions and jobs finish, change lean.cache_epoch, run the operator's restart-broker command, and resume. Updated environment keys make earlier calibration and compiled modules distinct from the new environment. Stopping dispatch alone does not make the broker exit. A compile that is already running keeps the `threads` and `priority` it started with.

Two notes on the defaults. On a machine with simultaneous multithreading the number of logical cores is twice the number of physical cores, so the default thread budget is four times the physical cores; this is intended, and all thread arithmetic in this document is in logical cores. The priority is applied by the process that supervises each compile, with `nice` on Linux and the priority class on Windows, so the runner, the session hosts and the CLIs get the processor ahead of compiles when it is contended. Priority does not limit anything; it only decides who goes first.

When several instances run on one machine, each has its own broker with its own budget, and each derived budget assumes the whole machine. Set `memory_budget_mb` explicitly in each instance to its share, and let the machine gate handle the rest.

## How the broker lives and recovers

The broker is the `serve` command of `lean_broker.py`, run as a detached process like the runner's other helpers. It holds the lock file `runner/lean/lock`, the same kind of operating-system lock as the runner's own `runner/lock`, released automatically when the process dies, so there can never be two brokers for one instance. It records its identity in `runner/lean/process.json`, its state in `runner/lean/state.json`, the calibration table in `runner/lean/calibration.json`, new requests in `runner/lean/queue/` and each job in `runner/lean/jobs/<job>/`. All of this is under `runner/`, outside the instance's Git.

The runner starts a broker when it starts, and starts another on any later tick where it finds no live broker, for as long as the runner runs. It checks liveness by process identity, the PID together with the process's creation time, so a reused PID is not mistaken for the broker. A broker it finds alive is adopted, whoever started it. The runner never stops a broker, and the runner's own exit does not end it: the broker keeps serving the sessions that are still running. A session that finds no live broker starts one itself before submitting, and the `wait` command does the same while waiting, so compiling never depends on the runner being alive. If two starts race, the lock decides: the loser exits at once and the session waits for the winner. The broker exits on its own when the instance has finished its sessions and follow-ups, no session is active, and no compile job is queued or running. A formal root alone does not end its service while follow-ups remain.

Each compile is supervised by a small process called the job host, the `_job` command of the same file. It is the counterpart of the session host described in [Operations](operations.md), and it exists for the same reason: on Linux, only a process's parent can learn its exit code, so the process that starts Lean must be one that will still be there when Lean finishes, even if the broker has died in between. The broker writes the job's launch file and records the host's identity in its state before it writes the `GO` file that allows the host to start Lean; a host that never receives `GO` exits without starting anything. The host records Lean's identity in `process.json` when it starts and the exit code in `exit.json` when it ends. So when a broker dies in the middle of a compile, nothing is lost. The next broker reads the jobs the old one left as running, follows by identity those whose host or Lean process is still alive, reads their `exit.json` when it appears, and puts back into the queue any job whose Lean had not started. A job whose host has disappeared without writing an `exit.json` is marked failed, with that reason; it is never silently run again.

When `lean.command` has the form `lake env lean …`, the broker does not run lake for every compile. At start, and again whenever `settings.json` changes, it runs `lake env` once with a command that reports the environment lake has set up, keeps the variables lake added or changed (`LEAN_PATH`, `PATH` and the like), and from then on runs `lean` itself in that environment. The compile is the same, with the same search path, but without the workspace load that lake repeats per compile, which on the machine this was measured on cost about a gigabyte of committed memory and a few seconds each time. If asking lake fails, the configured command stays in force and the reason is in `status` under `launcher`, which also says which mode is in use. Baselines measured in the two modes are kept apart in the calibration table, since the direct ones are lower by lake's share. After a change of Lean or Mathlib, restart the broker as described above; the restart asks lake again.

The runner's `status` command includes a `lean` object with the broker's liveness, its configuration and any `config_error`, the Lean version and any `version_error`, the launcher mode, the queued and running jobs with their estimates, reservations and measurements, up to twenty recently finished jobs with their outcomes and exit codes, the builds in progress or finished within the last ten minutes, and the paths of the calibration table and module cache. The broker's own log is `runner/lean/broker.log`. The `kill-session` command now also ends the session's compiles, indirectly: once the session is dead, the broker cancels its jobs by the rule above. The archiver that compresses finished sessions' `work/` leaves `runner/lean/` alone; finished job folders hold only Lean's output and a few small receipts.

## Formal proof acceptance

A successful compile checks the Lean development as written. To accept it as a solution, review also obtains `#print axioms <theorem>` for the target and compares its type with the exact node or negation. The default allowed axioms are `propext`, `Classical.choice` and `Quot.sound`. Use the allowed-axiom list in your launch-time input.json.settings. The instance may explicitly allow additional axioms for those launches; `sorryAx` is never permitted. `native_decide` can introduce auxiliary axioms and must not be treated as automatically within the default set.

The audit reports dependencies transitively. A hole in an imported lemma therefore appears in the target's axiom list even if the final file contains no `sorry` text. Conversely, a mention of that word in a comment has no proof significance. Inspect the actual output from the target's independent compile.

Review copies every final candidate source into its own working directory, preserves its bytes, and appends only axiom inspection commands. The broker records the submitted source hashes and rejects a changed source at execution. The review output identifies the finished job, theorem, actual axioms and correspondence, mapping every candidate source to its compiled working copy. [Review output](review-output.md) specifies that evidence. Publication retains the compiler output with the assessment, so the record remains interpretable after operational job cleanup.

A compilation that could not run leaves formal verification incomplete. A source that fails to type-check, a target relying on an unapproved axiom, and a proved theorem about the wrong statement have different consequences; record the exact case. Partial formal developments remain useful retained mathematics and can be published with their limitations.
