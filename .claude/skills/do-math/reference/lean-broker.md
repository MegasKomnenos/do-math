# The Lean broker

Every Lean compile of a do-math instance runs through one process, the Lean broker. This document is for the operator of an instance: the one who sets the instance up, reads its status, changes its settings and recovers it. With it, the output of `status` can be read, a compile that waits can be explained, and a change of settings or of the Lean installation can be made knowing what it invalidates.

What a session needs in order to compile is in [Lean](lean.md), which also gives the broker's own commands that are named here, such as `wait`, `result` and `cancel`; a session can compile without reading this document. [Operations](operations.md) covers the rest of running an instance and gives the runner's commands that are named here, `status`, `restart-broker`, `cleanup` and `kill-session`.

These terms are taken from [Lean](lean.md). A **compile** is one run of Lean over one file. Its **private memory** is the memory charged to its own processes, which the broker measures: their commit charge on Windows and their anonymous memory on Linux. The **imported library** is what the Lean environment provides, the toolchain's modules and any configured library such as Mathlib, and an **external import** is an import of one of its modules. A **local module** is a module whose source lies under the module root a build was given: a canon module in a session's copy, or a module the session wrote. The **estimate** is the peak private memory a session expects of a compile, given with `--expect-mb`, and the **baseline** of a set of external imports is the private memory a compile uses to load them before it elaborates anything.

## How the broker decides what runs

The broker has no limit on the number of compiles running at once. It has a memory budget and a thread budget, and it starts the next compile when both have room for it and the machine itself has the memory free.

**The memory rule.** For each running compile, and for the one the broker is considering, it forms a reservation of three numbers. The first is the certain part: the baseline B for the compile's imports, because every compile with those imports will reach it. The second is the expected excess m: how much more the compile is expected to take above the certain part. The third is the spread s: how uncertain that expectation is. The last two are derived from the session's estimate E, read as a ninetieth percentile, and from the spread the broker has observed for that set of imports in this instance. Let v be the observed standard deviation divided by the mean excess when that ratio is available and nonzero, or `default_spread` otherwise. The broker sets m = max(0, E - B) / (1 + 1.2816 v) and s = v m, so that m + 1.2816 s equals the estimated excess max(0, E - B). Once the measured private memory reaches C greater than B, the certain part becomes C and the remaining expected excess max(0, B + m - C), so that what the expectation had already predicted is not counted again; the spread stays s. Where the imports have no baseline, neither a measured nor an estimated one, the broker reserves the entire estimate as certain and adds a spread of one quarter of that estimate. `status` shows the reservation of a queued or running compile as its `reserve`: `certain_mb`, `mean_mb` and `sd_mb` are its three numbers in that order, `expected_mb` is the estimate or, where that is higher, the baseline, and `total_mb`, on a queued compile, is the left side of the rule below as the broker last computed it with that compile as the candidate.

A compile can start when, over the running compiles and the candidate together,

```text
sum of certain parts + sum of expected excesses + confidence × sqrt(sum of squared spreads) ≤ memory_budget_mb
```

The certain parts and the expectations are simply added. The spreads are not: they are combined under a square root, under an approximation that their uncertain excesses can be pooled independently. Four uncertain compiles need about twice the safety margin of one, not four times. This is what lets several compiles share the budget. The `confidence` setting is the one knob: at 1.3, the default, it adds a margin of 1.3 pooled standard deviations; at 2 the margin is larger; at 0 only the expectations and certain parts are reserved. These are scheduling estimates, not measured guarantees of overflow probability: jobs can in fact share expensive phases and peak together, and such correlated jobs and inaccurate estimates can weaken the model, which is why the machine gate and observed costs matter. Adding up every compile's full estimate instead would be the infinitely cautious end of the same scale, and it is not the rule because it would leave most of the budget idle most of the time. (The rule is the equivalent-capacity admission control used in communication networks; the problem is the same.)

**The thread budget.** Each compile reserves the number of threads in `lean.threads`; a calibration compile reserves one. A compile can start when the reserved threads, with its own, do not exceed `cpu_threads_budget`. The default budget is twice the number of logical cores, on purpose: a compile uses its threads only while elaborating, not while loading imports, so letting one compile's import overlap another's elaboration keeps the cores busy.

**The machine gate.** Whatever the budgets say, a compile starts only if the machine's actual free memory (`MemAvailable` on Linux, the commit headroom on Windows) would remain above `min_free_memory_mb` after the compile's certain part is taken. Free memory shows only what a running compile has taken so far, and a compile started a moment ago is still loading its imports. The gate therefore also counts as taken the part of each running compile's certain part that its measured memory has not yet reached; otherwise compiles started a quarter of a second apart would each be admitted against the same free memory. The gate knows no more than that of what a running compile will still take. What a compile takes above its certain part is counted only once the compile has taken it and the machine's free memory shows it, and that includes the library the compile loads through the local modules it imports, since its baseline covers the external imports written in its own file. Compiles that start within the seconds such a load takes are therefore admitted against free memory that does not show it yet; the room for it is `min_free_memory_mb`, which the gate keeps free at each start. The budgets know nothing about the CLI processes, the archiver, another instance on the same machine, or anything else that uses memory. The gate is what sees them.

On Linux the system can drop the pages of the library a Lean process maps and read them again when memory is short. On Windows both the private memory the broker measures and the headroom the gate reads are commit charge, and a Lean process is charged against the headroom for the whole size of the library it maps: with Lean 4.32.0, a process that imported the Lean metaprogramming library was measured at a commit charge of 2,078 MB while it touched 803 MB of physical memory, of which 98 MB was private to it, and the files it had loaded came to about 1.6 GB. [Operations](operations.md) explains, under "When compiles wait for memory on Windows", how compiles can then run one at a time although physical memory is free, and the remedy the operator recommends to the user, a larger page file. The default `memory_budget_mb` is derived from the physical memory and does not grow with the page file; if the budget is then what holds compiles back, which `status` shows in the reservations, it is set explicitly.

**The order.** Queued compiles are considered in the order they were submitted, and the first one that fits is started. The calibration compiles the broker creates itself, described below, are considered before all of them, in the order they were created, because a compile waiting for a calibration cannot start until that calibration has run. A compile that does not fit yet is passed over, so a small compile with few imports can go ahead of a queued Mathlib compile that is waiting for memory. Passing over is limited, so that a stream of small compiles cannot keep a large one waiting forever: each queued compile counts how many later compiles have started ahead of it, and once that count reaches `max_passes` (three by default), nothing behind it may start until it has. The running compiles then finish on their own, and as soon as the waiting compile fits, it starts. This bounds the number of later compiles that can pass it. It does not bound elapsed waiting time, because running compiles have no time limit and the machine gate must still permit a start. When no compile is running, the broker permits one eligible compile to exceed the memory or thread budget so that an oversized job is not excluded forever. The machine gate still applies: that job waits if the required free-memory headroom is unavailable.

**Calibration.** The broker keeps what compiles have cost in the calibration table, `runner/lean/calibration.json`, with one entry for each set of external imports, Lean environment and launch mode; [Lean](lean.md) describes the entries where it explains estimating. A compile whose external imports have no entry waits for a calibration compile of those imports, which the broker creates itself: a file of only the `import` lines, compiled with one thread and reserved at `calibration_expect_mb`, since its cost is by definition not yet known. Its measured peak becomes the baseline and its duration the import time. Local modules are never calibrated; what loading them costs is measured as excess.

The broker does not measure every set. A baseline follows closely the size on disk of what the imports load: the compiled files of every module they reach, each module counted once. The broker reads that from the library itself, where an `.ilean` file beside each compiled module lists its direct imports, and keeps what it has read in `runner/lean/library-<environment key>.json`. Once five sets have been measured in the current environment and launch mode, a new set whose size lies between two measured sizes receives an estimated baseline, from a line fitted through the measured sets, and no compile of its own; the compiles that need it do not wait. A set smaller or larger than every measured one is measured, which widens the range for later sets, and so is a set of which some module cannot be found. Estimated baselines are not used in the fit. An estimated entry carries `estimated: true`, the size it was estimated from as `closure_mb`, the number of measured sets as `measured_sets`, and no `import_seconds`. Replayed over the sets that one instance had measured, the rule would have measured about one in eleven and estimated the rest, each within 2% of its measurement.

If Lean runs the calibration compile and rejects it, for instance because an import does not exist, the failure is recorded in the table instead of a baseline, and compiles with those imports go ahead on their own estimates, with the whole estimate treated as certain, and succeed or fail on their own terms; the recorded calibration is reused for that import set and environment identity; a changed Lean version, environment configuration or `cache_epoch` creates a new calibration key. If the calibration compile could not be run at all, ended in a crash (a negative code for a POSIX signal, or a Windows crash code such as 3221225477), or was cancelled, nothing is recorded. The compiles that were waiting for it go ahead on their own estimates in the same way, so a Lean that cannot start is reported as the compile's own `failed` result and not as an endless wait, and the next compile submitted with those imports triggers calibration again.

**Cancellation.** A compile is cancelled, and its process tree terminated, when the AI session that submitted it has ended. The broker recognizes that end from the runner's recorded session state or from the death of both its host and CLI. The later peer and review processing does not keep that producer's unfinished compiles alive. Such a compile has no reader, and without this rule compiles like this would pile up as orphaned Lean processes after a shell tool's ten-minute abandonment or a `kill-session`. The `cancel` command does the same on request. Nothing else stops a compile; there is no time limit and no memory limit on one that is running. A compile that names a session the runner has not recorded is kept. The builds the runner itself makes are of this kind: it builds the canon through the broker when the instance is created, under the session name `operator`, and at each publication, under the session name `runner`, each with `calibration_expect_mb` as its estimate, and these appear in `status` among the other jobs.

**Measurement.** Four times a second, the broker reads the private memory of the compile's whole process tree, since `lake env lean` is two processes, and keeps the highest value. It finds which processes belong to the tree by listing the machine's processes, which it does once a second; between two listings it reads the memory of the processes last listed. When the compile ends it records the excess above the baseline and the duration in the calibration table, the ratio of measured peak to estimate in the job's summary, and the whole job in its `result.json`.

## Settings

The broker's settings live in the `lean` block of `settings.json`, alongside `command`, `version_command`, `cwd`, `env`, `cache_epoch` and `allowed_axioms`. These resource keys are optional and receive the defaults below.

| Key | Meaning | Default |
|---|---|---|
| `memory_budget_mb` | The private memory the broker may have reserved for compiles at one time | `null`, which means the machine's physical memory minus `min_free_memory_mb` minus 512 MiB for each of `max_sessions`, and at least 1024 |
| `confidence` | The multiplier of the pooled spread in the memory rule | `1.3` |
| `min_free_memory_mb` | The machine gate: how much free memory must remain after a compile starts | `2048` |
| `cpu_threads_budget` | How many threads the running compiles may reserve together | `null`, which means twice the number of logical cores |
| `threads` | The `--threads` value given to each compile | `2` |
| `priority` | The process priority of every compile: `below_normal`, `normal` or `idle` | `below_normal` |
| `max_passes` | How many later compiles may start ahead of a queued compile that does not fit before it closes the queue behind it; `0` makes the order strictly first come, first served | `3` |
| `calibration_expect_mb` | The memory reserved for a calibration compile; also the estimate of the builds the runner makes, and of `commands.prepare` and `commands.verify` when a session gives them none | `2048` |
| `default_spread` | The spread of a compile's elaboration excess relative to its mean, used for a set of imports until the broker has measured its own; `0` reserves the expected excess only | `0.5` |

The keys are validated at instance initialization and when the runner starts, so an invalid value stops a starting runner with the error in its start log. A running runner rereads `settings.json` when it changes; [Operations](operations.md) describes how such an edit takes effect and how a rejected one appears. The broker validates the keys again when it starts, since a session may start it while no runner is running.

The broker re-reads `settings.json` at the first poll after the file changes. It applies a valid change and records it in `runner/lean/broker.log`; it logs and ignores an invalid one, and the last valid configuration stays in force. `status` shows the configuration in force and any current `config_error`. The Lean version is read once, when the broker starts, and calibration entries are keyed by it, so after a change of Lean or Mathlib the operator changes `lean.cache_epoch` and replaces the broker, as [Operations](operations.md) describes under "Changing Lean" with the reason; stopping dispatch alone does not make the broker exit. A compile still queued under the earlier environment identity does not start under the new one: it ends `failed` with the reason that the Lean environment changed while it was queued, and its session submits it again. A module of a build that was still waiting for its imports ends the same way, since those imports were compiled in the earlier environment. A compile that is already running keeps the `threads` and `priority` it started with.

On a machine with simultaneous multithreading the number of logical cores is twice the number of physical cores, so the default thread budget is four times the physical cores; this is intended, and all thread arithmetic in this document is in logical cores. The priority is applied by the process that supervises each compile, with `nice` on Linux and the priority class on Windows, so the runner, the session hosts and the CLIs get the processor ahead of compiles when it is contended. Priority does not limit anything; it only decides who goes first.

When several instances run on one machine, each has its own broker with its own budget, and each derived budget assumes the whole machine. The operator therefore sets `memory_budget_mb` explicitly in each instance to its share and leaves the rest to the machine gate.

## How the broker lives and recovers

The broker is the `serve` command of `lean_broker.py`, run as a detached process like the runner's other helpers. It holds the lock file `runner/lean/lock`, the same kind of operating-system lock as the runner's own `runner/lock`, released automatically when the process dies, so there can never be two brokers for one instance. Under `runner/lean/` it records its identity in `process.json`, its state in `state.json`, the calibration table in `calibration.json`, new requests in `queue/`, each job in `jobs/<job>/`, each build in `builds/<build>/` and compiled modules in `cache/`. All of this is under `runner/`, outside the instance's Git.

The runner starts a broker when it starts and, for as long as it runs, starts another within seconds when a later tick finds no live broker. It checks liveness by process identity, the PID together with the process's creation time, so a reused PID is not mistaken for the broker. A broker it finds alive is adopted, whoever started it. The runner never stops a broker, and the runner's own exit does not end it: the broker keeps serving the sessions that are still running. A session contained in a job, as a session on Windows normally is, does not start a broker. Nothing such a session starts can leave its job, as [Operations](operations.md) explains where it describes session hosts, and a broker started inside that job would end with the session and take the other sessions' compiles with it. So when the session's client finds no live broker, before submitting or while a `wait` is waiting, it waits up to twenty seconds for the one the runner starts and then reports that no broker is alive; the session submits again, or waits again on the same job, once the runner is running. A contained session is left without a broker only when the broker has ended while the runner is not running, and then until the runner is started. A client that no job confines starts a broker itself: the operator's shell does, and so does a session that runs uncontained, as every session on Linux does. If two starts race, the lock decides: the loser exits at once and its starter waits for the winner. The broker exits on its own when the instance has finished its sessions and follow-ups, no session is active, and no compile job is queued or running. A formal root alone does not end its service while follow-ups remain.

Each compile is supervised by a small process called the job host, the `_job` command of the same file. It is the counterpart of the session host described in [Operations](operations.md), and it exists for the same reason: on Linux, only a process's parent can learn its exit code, so the process that starts Lean must be one that will still be there when Lean finishes, even if the broker has died in between. The broker writes the job's launch file and records the host's identity in its state before it writes the `GO` file that allows the host to start Lean; a host that never receives `GO` exits without starting anything. The host records Lean's identity in `process.json` when it starts and the exit code in `exit.json` when it ends. So when a broker dies in the middle of a compile, the compile and its outcome are not lost. The next broker reads the jobs the old one left as running, follows by identity those whose host or Lean process is still alive, reads their `exit.json` when it appears, and puts back into the queue any job whose Lean had not started. A job whose host has disappeared without writing an `exit.json` is marked failed, with that reason; it is never silently run again.

The broker holds its state in memory and writes `runner/lean/state.json` as a whole. Besides the jobs and builds that are queued or running, the file holds the two hundred most recently finished jobs, and each finished build until the broker prunes it, which it does when the first compile ends more than ten minutes after the build ended; for those ten minutes `status` lists the build, and its outcome stays in its `result.json` afterwards. A build's record has a row for every module it reached. The `result.json` written when a build ends keeps of each row what is read after the build: the module's `key`, `job`, `status`, `exit_code`, `reason` and `measured`. The rest, which only the running build reads (each module's source, its imports, the place of its output, and the build's table of source hashes), is in the state alone; a `result.json` that a broker of an earlier version wrote holds it as well. While the broker writes the file it measures no compile and starts none. It therefore writes the file not at each change but when it starts, before it lets a compile start, at the end of the poll in which a compile ended, when a client asks for it, and when it exits on its own. Every other change waits until ten seconds have passed since the last write. Between two writes the file is behind the broker in those other changes: the memory measured for a running compile and the identity of its Lean process, a request that is registered and has not started, the modules a build has taken from the cache, a cancellation the broker has taken up, and settings it has applied.

No command depends on that file being current. The end of a job or build is in its `result.json`, which the broker writes at that moment, and `wait` looks for that file at least once a second, so a waiting session learns of the end about a second after it at the latest. A request stays in `runner/lean/queue/` until a state that contains it has been written. A job is therefore found at every moment in the queue, in the state file or in its result, and one that is found only in the queue is shown with the status `submitted`. `status` and `result` show the state as it is at the moment of the command, because they ask the broker to write it first. They ask by putting an empty file `<name>.state` into `runner/lean/queue/`. The broker writes its state at the end of the poll in which it finds that file and then removes the file, and the command reads the state once the file is gone. That takes the quarter of a second to the next poll and the time of the write. A broker that answers such requests says so in `runner/lean/process.json`, with the field `state_seconds`, whose value is the ten seconds, and the commands ask only a live broker that says so. When no broker is alive, nothing is newer than the file. A live broker without the field is one of an earlier version: such a broker keeps running after an installation until it is replaced, and it writes its state at each change. In both cases the command reads the file as it is. If a live broker has not answered within twenty seconds, the command withdraws its request and reports the file as it is; `state_written_at` in the output of `status` is the time at which the file it reports was written. A program that reads `state.json` itself, without asking, reads a state that can be ten seconds old.

What a broker had not written when it died, the next broker finds again on disk, with one exception. A request that was registered and not written is still in the queue and is registered again; for a build, the import headers and the sources are then read as they are at that moment. A compile that had started is in the state with its host, and one that had ended is in the state as ended. The modules a build had taken from the cache are taken from it again, and a module compile that had been created and not started is created again under a new job ID. A cancellation that a client requested stands as the `CANCEL` file in the folder of the job or build, a compile whose session has ended is cancelled again by the rule given under Cancellation, and the settings are read from `settings.json`. The count of how often a queued compile has been passed over returns to the value last written. The exception is the memory measured in the seconds before the death. The next broker measures a running compile on from the peak last written, so a peak that was reached in those seconds and not again afterwards is recorded too low. A compile that ends while no broker is alive is recorded with the peak last written. A calibration compile that was running when its broker died records no baseline, whether it ends before the next broker has started or under that broker, as when it could not be run, and its imports are measured again. The time in which a compile goes unmeasured is thus the time without a broker and up to ten seconds before it.

When `lean.command` has the form `lake env lean …`, the broker does not run lake for every compile. At start, and again whenever `settings.json` changes, it runs `lake env` once with a command that reports the environment lake has set up, keeps the variables lake added or changed (`LEAN_PATH`, `PATH` and the like), and from then on runs `lean` itself in that environment. The compile is the same, with the same search path, but without the workspace load that lake repeats per compile, which on the machine this was measured on cost about a gigabyte of committed memory and a few seconds each time. If asking lake fails, the configured command stays in force and the reason is in `status` under `launcher`, which also says which mode is in use. Baselines measured in the two modes are kept apart in the calibration table, since the direct ones are lower by lake's share.

The runner's `status` command includes a `lean` object with the broker's liveness, the content of its `process.json` under `broker`, `state_written_at`, its configuration and any `config_error`, the Lean version and any `version_error`, the launcher mode, the queued and running jobs with their estimates, reservations and measurements, for each queued job also the job it is waiting for and how often it has been passed, up to twenty recently finished jobs with their outcomes and exit codes, the builds in progress or finished within the last ten minutes, and the paths of the calibration table and the module cache. The object also carries `environment_key`, a hash of the four settings `lean.command`, `lean.cwd`, `lean.env` and `lean.cache_epoch`, none of which is in the configuration it shows: a change of one of them shows as a new key, and each entry of the calibration table carries the key it was recorded under. The broker's own log is `runner/lean/broker.log`. The archiver that compresses finished sessions' `work/` leaves `runner/lean/` alone; finished job folders hold only Lean's output and a few small receipts.

The folders of jobs and builds and the entries of the cache stay, apart from the lib folder of a pruned build, until the operator runs `cleanup`, which [Operations](operations.md) describes under "Retention and archives". That command ends a live broker, removes the folders of ended jobs and builds that nothing reads again and the cache entries that neither the canon nor a remaining build uses, and starts a broker again in its place. While it works it holds the broker's lock, so a broker that the runner starts meanwhile exits at the lock, and `runner/lean/broker.log` shows that refusal. Once the broker's state no longer lists a job or build whose folder went, `wait` and `result` answer for it as for an unknown one.

## The module cache and its key

A build compiles the local modules its targets reach, each as one compile, run with `-R <root>` so that the module is named correctly and `-o` so that its `.olean` lands in the build's own lib folder, which is put on the search path of every later compile of the build. A module is taken up only after the modules it imports have compiled with exit code 0 or been taken from the cache; modules that do not depend on each other start side by side when the budgets allow. A compiled module is kept in the instance's cache under a key, and a later build, by any session, that needs a module with the same key takes it from there. Such a module is reported as `cached`; it has no job, and if it is a target its Lean output is replayed from the cache. The cache holds only broker-built modules, and only those whose compile ended with exit code 0.

The key is made of what decides the files a compile emits: the environment identity, the module's name, its source bytes, and the compiled output of every local module that the compile reads. Those are the modules it imports and the ones it reaches through them. Since the key needs their output, a module has a key only once they are compiled or taken from the cache; until then `result <build>` shows it as `queued` with neither key nor job. The environment identity is computed from `lean.command`, `lean.cwd`, `lean.env` and `lean.cache_epoch`, and the detected Lean version is included separately. Because a version string alone does not identify a replaced Lean library or a library installation changed in place, the operator changes `cache_epoch` for such a change, as described under Settings above.

The key follows the output of the imported modules and not their sources, because the output is what the compiler reads, and this decides how far a change travels. A module compile emits four files with Lean 4.32.0 and five with Lean 4.36.0. The `.olean` and `.ir` files are the public part: statements, exposed definitions and compiled code, without proofs. The `.olean.private` file holds the proofs, and the `.olean.server` file holds data for the editor. The fifth file, `.ir.sig`, is written by the `lean` command without content of its own, to be filled by another program of the toolchain that the broker does not run; the broker keeps it in the cache with the others and does not count it in the public part. A file written in Lean's module system, one whose first word is `module`, reads only the public part of a module it imports. So when a proof is replaced in a module and its public files come out the same byte for byte, the module itself is compiled again, and the module files above it keep their keys and are taken from the cache. A plain file reads the private data of what it imports as well, and so does a module file with an `import all`. Their key therefore takes every emitted file of each module they read, and any change in one compiles them again.

Whether the public files stay the same is settled by the compiler and cannot be read off the edit. With Lean 4.32.0, a proof replaced by one that made the elaborator generate the same auxiliary declarations left them identical, and so did lines shifted without any other change. A changed statement or exposed definition changed them. So did a proof that generates a different set of auxiliary declarations, as an `omega` proof replaced by a term did, although no statement had changed; everything above the module was then compiled again. With Lean 4.36.0, a complete proof in the place of a `sorry` changed them as well, because Lean keeps in the compiled module the axioms each declaration depends on; the module files above were compiled again, and [Operations](operations.md) explains under "What makes a statement formal" what rests on that. How often real proofs fall on each side is not known. The key is right in each case, since it is made from the output itself. The modules reached through others are in the key for a measured reason as well. A changed statement in a module E left every file of D, which imports E without using that statement, byte-identical, while M, which imports D and uses the statement through it, no longer compiled. A key made from D's output alone would have returned M's earlier files as if nothing had changed.

Because the key is made of content and not of paths, the same sources built under two module roots get the same keys. This is what lets a session build its own files in a copy of the canon without compiling the canon again, and what lets review reuse the unchanged modules a candidate imports while it compiles the changed modules itself: `build --fresh-targets`, which `commands.verify` uses, forces the targets to compile even when the cache holds an entry with their key. The runner's own builds, at the creation of the instance and at each publication, fill the cache with the canon's modules as they are published. Those builds, and the builds of `commands.prepare` and `commands.verify`, carry one further compile, shown as the module `DoMathExtract`, which extracts the entries of the structural index from the compiled modules. It imports the changed modules and the modules that import them as a plain file, since it has to read their proofs, and, where a record of the change says that its declaration proves or refutes the statement of another, the modules of those two declarations as well, so it is compiled again whenever one of those modules, or anything they reach, came out different in any way from the last time.

The lib folder of a build is kept under `runner/lean/builds/<build>/lib` until the build is pruned from the broker's state. Each compile of the build writes the output of its module there. Of the modules the build took from the cache, the lib holds those that one of its compiles reads and no others: the local modules that a compiled module imports and the ones it reaches through them. The broker puts the files of such a module there when it creates the first compile that reads them, so the lib of a build that compiles nothing holds nothing. A file put there from the cache is not a copy: it is a hard link to the cache's file, which is a second name for the same file, so a lib folder takes room on disk only for the modules its own build compiled. Where no hard link can be made, the file is copied instead: when the two folders lie on different volumes, when the file system has no hard links, or when the cache's file already has the 1,023 links that NTFS allows. Neither name is ever written through. The cache's files are put in place by a rename and then left as they are, and before a module is compiled the broker removes whatever stands at the place of its output, so that Lean writes a new file there. The files of a cached module cannot be put there when one of them can be neither linked nor copied, as on a full volume, or when the cache no longer holds the complete entry. The module whose compile was to read them then ends `failed` with that reason, and the build with it; the cached module is not compiled instead. A program that adds up file sizes counts a linked file once for each folder it appears in, so the size it reports for `runner/lean/builds/` can be many times the room that folder takes. An entry of the cache is the emitted files and the two logs of the compile under the key's name, with a manifest, `<key>.artifacts.json`, that is written last; an entry without a complete manifest, or one that has lost a file, is treated as absent and the module is compiled.
