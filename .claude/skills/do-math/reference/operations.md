# Operating a research instance

This guide continues the operator's entry point, [SKILL.md](../SKILL.md). Use it when preparing an instance or acting on an existing run. It explains the files the operator supplies, how to confirm a launch, where to read results, and what the operating commands change.

The runner manages the research sessions after launch. Your commands affect that running process or supply inputs it will use. Understanding the difference matters when operating a run: stopping new dispatch leaves existing sessions alive, and delivering a user input makes it available to future launches without changing the instructions of sessions already underway.

## Prepare the statement and environment

The root file contains the mathematical proposition to settle, with its objects, assumptions, domains and quantifiers defined. A proof of either that proposition or its negation settles the node. Final completion requires an independently reviewed Lean solution with the intended correspondence. Keep the root statement fixed for the lifetime of the instance; changing its mathematics requires a new instance.

Put standing instructions, such as the language of the records or limits on permitted methods, in a separate input file. Submit it before starting the runner to make it part of every initial session's context. Later inputs affect only sessions launched after submission. They do not rewrite existing sessions' instructions or their saved contexts. Inputs accumulate rather than replace one another: a session receives every input submitted before its launch, in the order of submission, and is told that a later condition overrides an earlier one on the same matter. To change or lift an earlier condition, submit a new input that says which condition it changes and how.

The runner needs Python 3.12 or later, Git, authenticated Codex and/or Claude native executables, and a Lean environment. The default models for attempt, explore, formalizer and organizer are `codex/gpt-6.1-sol` at `xhigh`, followed by `claude/opus` at `xhigh`; for peer and review the order is reversed, so that the record and its review come from a different model than the producers. These are ordered alternatives for each role. Defaults are eight concurrent AI sessions, attempt and exploration launches at least three minutes apart from one another, exploration requested at every attempt launch, and organization after four research publications.

An example settings file is:

```json
{
  "schema": 1,
  "max_sessions": 8,
  "explore_every": 1,
  "organizer_every_records": 4,
  "launch_interval": 180,
  "max_end_resumptions": 3,
  "models": [
    {"model": "codex/gpt-6.1-sol", "effort": "xhigh"},
    {"model": "claude/opus", "effort": "xhigh"}
  ],
  "roles": {
    "peer": [{"model": "claude/opus", "effort": "xhigh"}, {"model": "codex/gpt-6.1-sol", "effort": "xhigh"}],
    "review": [{"model": "claude/opus", "effort": "xhigh"}, {"model": "codex/gpt-6.1-sol", "effort": "xhigh"}]
  },
  "cli": {"codex": "C:/tools/codex.exe", "claude": "C:/tools/claude.exe"},
  "mcp_servers": {},
  "retry_seconds": 60,
  "retry_max_seconds": 1800,
  "lean": {
    "command": ["C:/tools/lean.exe"],
    "version_command": ["C:/tools/lean.exe", "--version"],
    "cwd": null,
    "env": {},
    "cache_epoch": "initial",
    "allowed_axioms": ["propext", "Classical.choice", "Quot.sound"]
  }
}
```

Replace the executable paths with the actual installations. A role-specific ordered model list under `roles` replaces the common list for that role; the example shows the default lists for peer and review. A `roles` object that omits a role sends that role to the common list. An omitted setting receives its default. An unrecognized key, such as a misspelling or a setting carried over from the earlier do-math runtime, is rejected by name rather than ignored, because ignoring it would leave the default in force without notice. The runner checks structure; actual login and model availability are confirmed by execution. `init` writes the complete configuration, with defaults filled in, to the instance's own `settings.json`, and that file is the configuration in force afterwards. A running runner rereads it when it changes and uses the new values for its later scheduling and launches; a session already launched keeps the settings saved at its launch. An edit the runner rejects leaves its last valid settings in force and appears as `settings_error` in the runner state that `status` returns.

To use Mathlib, configure `lean.command` as `["<lake executable>", "env", "lean"]`, its version command with `"--version"` appended, and `cwd` as the Mathlib project. Supply any necessary PATH value through `lean.env`; JSON does not expand shell variables. The broker handles compilation and dependency builds. [Lean](lean.md) explains resource settings and estimates.

Only explicitly configured external tools enter worker sessions. `mcp_servers` maps server names to configuration objects. A local server uses `command`, `args`, and optional `env`; an HTTP server uses `url` and the provider's supported transport configuration. Configure the tool capabilities the research needs, such as scholarly-mcp, independently from personal instructions and hooks. Authentication remains with the installed CLIs. Worker launches disable personal/project instruction discovery, skills, hooks and memories; all do-math guides and user conditions are supplied explicitly.

Every worker role requests a 1,000,000-token context window, including role-specific model choices and fallback launches. Codex receives explicit `model_context_window=1000000` and `model_auto_compact_token_limit=900000` overrides, so isolation from the operator's configuration does not discard the context setting. Claude receives the model's `[1m]` variant, `CLAUDE_CODE_AUTO_COMPACT_WINDOW=900000` and `CLAUDE_CODE_MAX_OUTPUT_TOKENS=128000`, twice the CLI's default output cap for one response; an inherited setting that disables 1M context or overrides the compaction percentage is removed from the worker environment. Existing `[1m]` suffixes are retained once, and `[200k]` is replaced. These are launch requests: the selected model, account and CLI determine actual capacity and access. The Claude selector follows its [model configuration interface](https://code.claude.com/docs/en/model-config#extended-context).

`max_end_resumptions` is the maximum number of additional turns in which an attempt or explorer that undertook research, a formalizer or a peer receives continuation guidance. It is a nonnegative integer, default 3, fixed for that session at launch. The initial turn is not counted. At the limit, the host issues the same end authorization that permits the handoff to peer or review, with `source: runner` and `basis: resumption_limit`; it does not wait for operator approval or resume indefinitely. A value of 0 authorizes the initial ending without a reconsideration turn. A valid `no_research` outcome or an interruption ends the session without a reconsideration turn; the recorded end authorization then has `source: runner` with `basis: no_research` or `basis: interrupted`, and an interrupted session keeps its usual processing. A Claude turn that ends because one response exceeded the CLI's output-token cap is not an interruption: the CLI discards only that response, so the host resumes the same conversation, reporting the CLI message as the previous turn's problem. Such a resumption counts toward this maximum; when the maximum is already reached, the host issues `resumption_limit` with that message.

## Create and start

Choose a path that does not exist, outside the development repository or in an ignored directory such as `.skill-workspace/`. The instance has its own Git repository. Keep preparation files outside that path.

```powershell
$skill = 'C:/math/.claude/skills/do-math' # replace with the installed skill folder
$instance = 'C:/research/my-problem'     # a new path
python "$skill/runtime/runner.py" init $instance --root C:/research-input/root.md --settings C:/research-input/settings.json
python "$skill/runtime/runner.py" input $instance --file C:/research-input/conditions.md
python "$skill/runtime/runner.py" start $instance
python "$skill/runtime/runner.py" status $instance
```

The `input` command is optional when there are no additional standing conditions. `init` creates the statement, configuration, empty knowledge views, session directories and initial Git commit. A failed initialization may leave a partial directory; fix the cause and use a new path. `start` launches a detached runner and returns its PID and new stdout/stderr paths after confirming this launch's readiness token. Read those logs and `status` to confirm the actual launch.

The caller can then end its conversation. The runner and session hosts continue independently. If readiness is not confirmed within ten seconds, inspect the named logs and liveness before retrying; a wait timeout alone does not show that the child died.

## Read progress and results

Begin with `knowledge/index.md`. It contains records the organizer selected as common orientation for new sessions (shared context), descriptions of grouped records (modules), and new publications awaiting placement (unfiled arrivals). Open a record's exposition and its review to understand what was established. The original description remains visible beside the review's short assessment. Later findings appear separately, with links to the review that supplies them.

`knowledge/frontier.md` shows exact node statements, current informal/formal outcomes, reviewed relations and concerns, followed by the questions the research is trying to understand: each with its statement, grounds, open or resolved state and source, and a list of proposals review did not admit. A question's source is either the record whose review admitted it or an operator publication under `knowledge/questions/`. You make an operator publication with the `questions` command under Commands. Its questions do not pass through peer or review, so their content is yours to answer for; on the frontier, explorers take them up and records resolve them like any other question.

Unresolved means that no accepted proof or refutation has settled a node informally. An informally proved or refuted node is settled as mathematics; the runner sends it for the remaining Lean assurance only when that outcome lies on a path to the root, as Waiting, fallback and recovery explains below. A formally proved or refuted node has that independently reviewed assurance. Opposing accepted outcomes are shown as contested for review. A contested node is not treated as formally settled for completion; the opposing evidence must be resolved. Whenever no comprehensive review is pending or running, the runner assigns one that covers every concern and every contested node's current set of opposing routes it has not yet assigned. When that review leaves the concern uncleared or the node contested, the runner does not assign it again; a further examination needs an operator `review` request.

Question `q0` is the root problem itself; no explanation resolves it, and it stays open until the root is formally proved or refuted. The frontier then shows it resolved by the root's formal settlement, with the formal proofs that carry it. `knowledge/state.json`, a structured projection of published evidence for detailed inspection, records that ground under the question's `root_settlement` in place of `resolutions`. The runner derives whether `q0` is open or resolved from the root's state each time it replays the published events, so a later review that removes the root's last formal solution reopens `q0`, and the runner resumes research.

`knowledge/glossary.md` supplies the full current shared vocabulary.

`knowledge/board.md` shows the work still underway. A **section** is an exact part of a node's statement, up to the whole node, that a session has taken responsibility for settling: an attempt, or a peer extending its work, registers one, and the runner records a formalizer's assigned node as a whole-node section. A session choosing a section on a node holds that node's **lease**, which normally lets one session at a time choose there. A producing session, the peer that develops its work and the review that assesses the resulting candidate form one **pipeline**, and the sections and question its sessions hold stay occupied until publication or a review decision that there is nothing to publish. The workers' [common introduction](common.md) develops these terms, chiefly in its section on the board. The board shows the sections producing work holds, the question each exploration occupies, its processing stages and the node leases; a session's declaration lists the sections it has registered or the question it holds.

The status command reads those declarations directly, including changes since the board file was last rendered, and reports under `questions` which questions are free, the sessions of the explorations holding each occupied one (`occupied` lists them, so both appear after an organizer merges two questions explorations held), how many explorers are still choosing, and whether exploration is requested.

`status` returns the root's current state, whether the runner has finished, active and pending jobs, the board, provider/model blocks and the Lean broker state. A successful status command means the query succeeded. A formal root and a finished runner are different states: after formal completion, new attempts and explorations stop, while existing sessions continue and the runner still prepares their peer and review stages, ready formalizations, comprehensive reviews and due organization batches. If later review removes the root's last formal solution before exit, the same scheduler resumes research.

## Commands

Every command below is `python <skill>/runtime/runner.py <command> <instance> ...`.

| Command | Effect |
|---|---|
| `start` | Launch the detached runner when none is alive, such as after a crash or reboot, checking its new readiness record. It does not replace a live runner; to restart one, end its process first, as the paragraph on restarting a live runner under Waiting, fallback and recovery explains. |
| `run` | Run in the foreground for observation; remains attached until the runner exits. |
| `status` | Read current liveness, mathematical state and operational queues. |
| `stop` | Stop new dispatch. Running CLI turns finish; pending reconsideration turns and queued follow-ups wait. |
| `resume` | Remove the dispatch stop. If the runner is not alive, also use `start`. |
| `reconsider-attempts` | Request one reassessment of work availability, overriding an occupancy report. Attempts then launch one at a time, each a reassessment, until one registers a section; this holds even when no occupancy report was in force. Does not remove a dispatch stop. |
| `input --file <file>` | Preserve standing information for future launches. It does not notify running sessions of new instructions. |
| `review --record <id>` or `review --node <id>` | Request a comprehensive assessment of published evidence; targets may be repeated. `--concern <id>` and `--reason <text>` can identify the issue. A request that names no record, node or concern is refused, because the reviewer would have no evidence to examine. |
| `organize` | Request organization of the currently unprocessed research records. |
| `questions --file <file>` | Place questions of your own on the frontier as an operator publication, without peer or review. The file is UTF-8 JSON of the form `{"reason": "...", "questions": [{"id": "...", "statement": "...", "grounds": "..."}]}` with no other keys. `reason`, recorded in the publication, says why you place them; the list is nonempty; `statement` says what is to be understood and `grounds` what raises the question and why an answer matters, both nonempty. Each `id` matches `[A-Za-z0-9][A-Za-z0-9_-]*`, is unique in the file, is not `q0`, and does not name an existing question, question alias, node or node alias; a prefix such as `op-` keeps operator questions recognizable beside peer proposals, which carry a session-ID prefix. The command refuses a file that breaks these rules and otherwise leaves a request. On its next pass the runner publishes it as `knowledge/questions/<event>/questions.json` with its event and Git commit. If a publication since the command has taken one of the identifiers, the runner refuses the whole request and keeps running; the refusal and its reason appear in the runner state's top-level `last_error`. |
| `kill-session <session-id>` | Cancel the identified session's pending resumption and terminate its current CLI after confirming its OS creation identity. The session ends as an interruption: retained producing work still goes to peer, a producer that left no research material is launched again, and an interrupted peer, review or organizer stage passes to a replacement session, as Waiting, fallback and recovery describes. |
| `render` | Rebuild the knowledge views while the runner is off. |
| `restart-broker` | With dispatch stopped and running CLI turns and compiles finished, replace the broker after an environment change. Sessions held behind the stop for their next turn do not block it; the result lists them as `held_sessions`, and they continue with the replaced broker after `resume`. |

Use status to identify the intended session before termination. The command targets that session's CLI, not arbitrary processes on the machine, but ending the CLI also ends the session: its host then exits, and on Windows, where the session's `process-job.json` records that containment was applied, the system ends every process the session started, as Waiting, fallback and recovery describes. The broker cancels its compiles after observing that the session has ended. Where containment was not applied, including on Linux, computations the session started can outlive it; interpret them from their retained outputs and actual process state.

The runner reads `review`, `organize`, `reconsider-attempts` and `questions` requests on its next pass, so a request made while no runner is alive waits until `start`. This includes a finished instance: once the root is formally settled and the remaining work has ended, the runner exits, and a later `review`, `organize` or `questions` request takes effect only after `start`, whose runner then continues until that work has ended.

## Waiting, fallback and recovery

### What creates new work

When a producing session ends, its retained material creates peer work. A structurally usable peer candidate creates review work. An accepted informal solution creates formalizer work when the accepted outcome lies on a path to the root, that is, when that proof or refutation can carry the root through accepted relations, and when the other node results needed by its chosen argument have independently validated Lean proofs available. These results are its formal dependencies. A proof of a necessary condition of the root is not formalized; its refutation is. New research publications create organizer work when the configured number of unprocessed publications is reached. Available capacity and an available configured model permit each launch.

### Session hosts and continuation turns

An attempt, explorer, formalizer or peer's host can keep the same logical session alive across several CLI turns. After an ordinary turn exit, it resumes the exact native conversation with the same provider, model, effort and launch-time instructions. A current `output/end-decision.json` or the configured resumption limit authorizes normal handoff. Each request has a fresh ID, so an older decision cannot authorize a later ending. The protocol is described in [Retained work](retained-work.md). This does not create another attempt, another occupied section or question, or another concurrency slot.

`status` exposes the host's `end_check` record in each session's state, including `maximum`, `resumptions`, `status`, the current request and `authorization`. A host waiting behind the dispatch stop reports `waiting_dispatch`; a provider/model availability block reports `waiting_provider`. It retains its existing slot and scope while waiting. `resume` allows it to proceed once the availability block has also expired. `kill-session` cancels a pending resumption even between CLI processes. The host survives runner restart, and the runner collects the logical session only once after the host and CLI have ended. Host loss is recorded as an interruption, without inventing a worker end decision.

The session root retains its initial prompt and CLI streams; `turns/0001/` and later directories retain each resumed invocation separately. `end-check.json` contains the authorization and its issuer. Missing native identity or an identity change is recorded as `resume_unavailable` rather than silently starting a different conversation. Like the resumption limit, this runner authorization ends the session without interruption: a producer's retained work goes to peer, and a peer's output goes to review once it passes its **transport check**, the check that a finished session's output has the structure and references the runner needs to carry it to the next stage; that check does not judge the mathematics. A provider refusal or failed invocation instead ends this continuation through the usual interruption path. Availability handling still applies to later sessions.

On Windows the host places itself in a job object before its first turn. Processes the session starts inherit membership, including computations detached with `nohup` or left in the background, and the system ends them all when the host exits: after the last turn, through `kill-session`, or if the host dies. Three kinds of process are outside it. The Lean broker is shared and not session-owned: when a session's client has to start it, the client asks to start it outside the job. If that client runs inside a further job that forbids leaving it, the broker starts inside instead and ends, with the compiles it is running, no later than that session; the runner or the next client that needs a broker then starts a new one. A tool that explicitly asks to leave its job may do so. Processes started on a session's behalf by a service, for example through COM or `wsl.exe`, were never in it. `process-job.json` in the session folder records whether containment was applied; when it could not be, the session runs uncontained, as every session on Linux does.

### Launch priority and spacing

Priority is review, peer, formalizer, organizer, eligible explore, then attempt. Fresh attempts require free capacity, an unresolved node that no pipeline holds whole and no session is waiting to lease, and at least `launch_interval` seconds since the previous attempt or exploration launch. Attempts and explorations share this one spacing, which gives each new attempt or explorer time to take its lease before the next one reads the board. An exploration is eligible when exploration is requested, a question is free for it and the same interval has passed; the paragraphs on explorers and their questions further below explain when a question is free and when exploration is requested. An eligible exploration launches before a waiting attempt, while a request that no free question can serve does not hold attempts back. Each role waits only for its own object: attempts for an available node, explorers for a free question. The runner fills free capacity in this priority order before it launches a fresh attempt, so when every slot is in use, a slot that opens goes to waiting review or peer work first. Work that waits for something other than capacity does not hold attempts back while slots remain free: a review or peer waiting out a retry delay or for an available model, and a comprehensive review or organization pass waiting for another of its kind. Comprehensive reviews launch one at a time, as organizers do, so a requested review or organization pass waits, without an error or block in `status`, while another of its kind is running. Running sessions are not preempted when higher-priority work appears.

### Attempts that find no work

An attempt that only checked availability can write `disposition: no_research` in `output/outcome.json`. It must have registered no section and begun no mathematical investigation. An explorer that found no free question to occupy can end the same way; it must occupy no question, and its outcome carries no availability report. When the session exits successfully, the runner retains that session's files and conversation and closes the pipeline without peer or review. The session stays closed regardless of later changes in available work. Failed research and interrupted investigations still go to peer.

The attempt can also submit an `all_unresolved_work_occupied` report with the snapshot token from its coordination updates. The runner evaluates that report separately. An invalid or stale report does not prevent the session from closing, but it cannot suppress dispatch. An accepted report stops the runner from launching fresh or pending attempts while the reported occupancy remains applicable.

The runner waits until one of three changes occurs: a section's occupancy ends on a still-unresolved node, a new or reopened unresolved node appears, or the operator requests reconsideration. Occupancy ends through publication or a completed review decision that there is no useful record to publish; releasing a lease or leaving its queue does not end it. Elapsed time, unrelated publications, organization changes and sections that other sessions newly register do not end that wait. The runner then permits one reassessment attempt at a time. Once an attempt registers work, normal scheduling resumes. Another applicable report of full occupancy makes the runner wait again. An interrupted reassessment can be replaced, and any research it retained follows the ordinary processing path.

`status` reports this wait or reassessment under `attempt_dispatch`. It identifies the reporting session, snapshot token, current grounds and any reassessment session. Use `reconsider-attempts` to request reassessment explicitly. An older report cannot undo that request. The command does not remove a dispatch stop; a stopped instance still requires `resume` before any new session can launch.

Full occupancy also requests exploration, so capacity that attempts cannot use goes to understanding while they wait.

### Explorers and their questions

Explorers occupy **questions**, the frontier's objects of understanding; the workers' [common introduction](common.md) defines them. Several explorations can run at once, each holding a different question, and a question stays occupied through its exploration's peer and review. An organizer's merge is the one exception to a question's single holder, as it is for a node's lease: when two questions that explorations already hold are merged, both explorations keep the merged question, each until its own pipeline ends, because each took its question rightfully and the merge does not cut work short. The question is not free while either occupation lasts, so no new explorer duplicates their work, and it becomes free once both have ended; `status` and the board then show two explorations on it.

A question is **free** when it is open, no unfinished exploration holds it or was assigned it, and no live session holds or waits for its lease. One case is counted differently. An exploration whose launch ended without research material waits to launch again, and until then its pipeline still names the failed session, whose declaration may still record the question that launch held. `status` and the board show that session holding the question, though no live explorer does, and when the runner launches a waiting exploration it does not count such a question as occupied.

The runner launches one more explorer only while the free questions outnumber the explorers that have not yet chosen one, so that every explorer launched can find a question of its own. When question `q0` is free at launch, the runner assigns it to the new explorer and records the occupation before the session starts; otherwise the explorer chooses among the free questions through the question lease. While `q0` is free in this sense, the question commands refuse every other question, so an explorer still choosing when `q0` becomes free takes it.

Exploration is **requested** by a single flag. Two events set it: an attempt launch when the count of attempt launches reaches a multiple of `explore_every`, every launch by default; and the runner finding spare capacity while no unresolved node is available to a new attempt or attempt dispatch is suppressed, including when all nodes are informally solved. Repeated triggers coalesce into one request. When the flag is set and a question is free, one explorer launches ahead of any waiting attempt once the launch interval has passed, and the flag clears. When the flag is set but no question is free, it stays set until a question opens or an occupation ends, and attempts dispatch as usual meanwhile. While nodes remain unavailable the flag is set again after each launch, so the free questions fill with explorers one by one, a launch interval apart, until none is free or capacity is used. Launching an explorer does not reset the attempt-launch counter. Each attempt launch counts once, whether or not that attempt later registers a section or ends without research.

### Refusals, failed outputs and damaged candidates

A typed provider usage refusal blocks that provider until its known reset, or a configured backoff when the reset is unavailable. Model-specific refusals block that model. A new launch uses the first available alternative in its role's list. If all are unavailable, the job remains pending. A producer interrupted after doing work ends and proceeds to peer; it is not silently resumed under another model. A session that failed before leaving any research material can be retried as an operational launch.

Interrupted peers, reviewers and organizers receive fresh replacement sessions with their partial material and the error. When a completed session's output fails its transport check, the affected job waits for an exponential retry delay, up to `retry_max_seconds`. The same delay precedes the replacement of a peer, reviewer or organizer interrupted by anything other than a provider/model refusal or a failed launch, such as a crash or `kill-session`, and the relaunch of a producer cancelled before it left research material. Neither delay blocks the model for other jobs or changes their configured model preference. Actual provider/model refusals and operational launch failures retain their availability handling, so a configured alternative can be used while the affected service is unavailable. Status exposes the pending job's error and retry time as well as availability blocks. Repair broken paths, login or configuration when necessary. Mathematical uncertainty and incomplete formalization are handled through records and reviews, not inferred from process failure.

A successful session launched after an availability block's deadline clears that provider's or model's old backoff history. A later isolated refusal therefore begins with the initial delay. A session that was already in flight before a newer block cannot clear it merely by finishing successfully; the newer refusal still governs new launches.

If a frozen candidate changes during review, retrying the same damaged files cannot complete that review. The runner preserves the damaged candidate and compares the peer's retained output with the hashes fixed at review assignment. Matching output is copied to a new candidate location for a fresh review under the same hashes. If those bytes are unavailable, a replacement peer receives the original research and earlier peer work, develops a new candidate, and sends it through independent review. An assessment of the damaged candidate never authorizes publication of the replacement.

### Restarts, runner failures and installation updates

After a runner crash or machine reboot, use `start` on the same instance. The runner identifies existing processes by PID and creation identity, follows those still alive, and collects ended work. Publication uses a saved identity, staging directory and Git commit; restarting completes the same publication and its follow-ups without creating another record. Do not delete locks or edit runner state to force recovery. Use shells at the same privilege level on Windows, because process-query access is part of liveness detection.

The runner also ends by itself when one of its own operations fails, such as a Git commit or a read or write of its state files. `status` then reports `runner_alive` as false while `finished` is false, and the runner state's top-level `last_error` holds that error and its time, apart from the errors of individual jobs; the call stack is in the stderr log that `start` named when it launched that runner. Repair the cause before using `start`, because a restart that meets the same failure ends again, possibly after `start` has already confirmed readiness. A recorded `last_error` stays in the state after later starts, so compare its time with the `at` of `runner/process.json`, which records when the current runner started, before attributing a present problem to it. A `questions` request the runner refused is also recorded there, naming the request, while the runner keeps running.

Running out of memory is the exception: the runner does not end. It holds a small memory reserve for this case. When one of its operations fails for lack of memory, it releases the reserve, writes `Runner memory reserve released; dispatch will wait for recovery.` to the same stderr log, and then makes no pass at all, collecting, publishing and dispatching nothing, while the machine's free memory (`MemAvailable` on Linux, the commit headroom on Windows) stays below 512 MiB. Once free memory reaches 512 MiB, it takes the reserve back, reloads its saved state and the published research, and continues. Meanwhile `status` reports the runner alive and records no new `last_error`, although nothing advances; freeing memory on the machine lets it continue without a restart.

Worker guides and launch options are fixed for sessions already started. Updated guides are read for later launches. A runner already running keeps its imported launch code until it is restarted, and a session host already running keeps the code it loaded at launch; updating the installation does not rewrite saved session contexts or commands. Continuation messages are the exception: before each resumption, the session host reads `resume/common.md` and `resume/<role>.md` from its configured installation. Editing those files changes the next resumption without a runner or host restart. A continuation file the host cannot use, a `resume/<role>.md` that is missing or empty or a `resume/common.md` without exactly one of each placeholder, ends the session host at that session's next resumption. The error and its call stack are in the session's `host.log`, and the runner records the end reconsideration as `interrupted`: a producing session goes to its peer without that reconsideration, and a peer is replaced, each later session ending the same way until the file is repaired. The exact source files are saved under that turn's `guidance/` directory along with its rendered `prompt.txt`; turns already underway retain their delivered text. The code behind a session's commands is a second exception. The command arrays in `input.json` name the installed `runtime/coordination.py`, `check.py` and `lean_broker.py`, and each coordination, transport-check or broker-client command starts that installed file afresh, together with the modules it imports, such as `knowledge.py`. An edit to that code therefore reaches running sessions at their next command, while the runner, the session hosts and the broker keep the code they loaded, so until those are restarted the two sides read and write the shared coordination and state files with different code.

Changing runtime code still requires restarting the runner for future launches. `start` does not replace a runner that is still alive: the new process cannot take the instance's lock, so it exits and `start` reports that the runner exited before readiness. To restart a live runner, end the one process that `runner/process.json` identifies as this instance's runner, then use `start`. Session hosts and the Lean broker are separate processes and keep running; the new runner follows them and completes unfinished publication as it does after a crash.

### Retention and archives

Each launch retains its guides, references, user inputs, settings and research snapshot. The available conversation and artifacts are retained for each producing session. The work of one producing session finishes processing after its peer has prepared a candidate and review has either led to publication or decided there is no useful record to publish. The runner launches a separate archiver process to compress each associated session's work/ into work.tar.xz in that session directory. It verifies file names and hashes before removing work/. When work/ cannot be read or verified, or contains a symbolic link or junction, which could lead outside the session, the archiver leaves work/ in place, along with any archive already there, and records the session and the error in `runner/archive.log`; later archive passes try that session again. A standalone review or organizer's work directory becomes eligible when its own job completes. Output files, context and retained conversations remain available; restore archived work with an xz-capable tar reader when needed. The public record contains the evidence later researchers need. Archived originals remain recoverable for the operator and for a designated reviewer examining the relevant published record, within the scope described in the [review guide](../roles/review.md).

### Changing Lean

Changing Lean or its libraries requires a new `lean.cache_epoch`. Stop new dispatch and let running CLI turns and compile jobs finish; sessions waiting behind the stop for their next turn need not end. Update the Lean configuration in the instance's own `settings.json`, including a new `cache_epoch`, then run `restart-broker` and resume. This prevents a module cache identified by an old environment from being treated as evidence for a changed installation.
