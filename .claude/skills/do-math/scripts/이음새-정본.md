# do-math 이음새 정본

이 문서는 do-math 코드에서 둘 이상의 모듈이 함께 쓰는 규칙마다, 그 규칙을 정의한 곳 하나를 정한다. 이 한 곳을 **정본**이라 부른다. do-math 코드를 고치는 사람과 에이전트는 두 경우에 이 문서를 읽는다. 하나는 다른 모듈에도 있을 법한 검사·변환·상수·경로 규칙을 쓰거나 새로 만들려 할 때다. 다른 하나는 코드 주석이 `이음새-정본.md §N`으로 이 문서의 절을 근거로 들 때다.

## 원칙

**두 모듈 이상이 같은 규칙을 쓰면 정본 하나를 참조한다.** 생산자, 수신자, 시험 대역이 모두 정본의 이름을 import해 쓰고, 같은 규칙을 모듈 안에서 다시 구현하지 않는다. 같은 규칙의 사본이 둘이면 한쪽만 고쳐지는 순간 두 모듈의 뜻이 어긋나며, 두 사본이 같기를 기대하는 코드는 그 어긋남을 알아채지 못한다.

**검사 함수는 하나를 두고, 생산자와 수신자 양쪽에서 실행한다.** 생산자는 보내기 전에, 수신자는 받을 때 검사하되 두 검사는 같은 함수다. 신뢰 경계 밖에서 온 입력의 수신 검사는 생산자가 이미 검사했더라도 생략하지 않는다.

**새 공유 규칙은 소유 모듈에 하나만 만들고 6절 표에 올린다.** 둘 이상의 모듈에 필요한 규칙이 생기면 먼저 1~6절에서 같은 역할의 정본을 찾는다. 없을 때만 새로 만든다. 소유 모듈은 두 기준으로 고른다.

- 그 개념을 가진 모듈이다. 예를 들어 설정 기본값은 설정을 다루는 `configuration`이, 봉인 artifact 대조는 저장소를 다루는 `repository`가 가진다.
- 그 규칙을 쓰는 모듈들보다 import 그래프에서 아래에 있다. 그래야 쓰는 쪽이 모듈 최상단에서 순환 없이 import한다. 엔진(`engine.py`)은 믹스인과 도메인 모듈을 모두 import하는 맨 위 모듈이므로 공유 정의를 두지 않는다. 엔진에 두면 아래 모듈이 함수 안에서 엔진을 거꾸로 import해야 한다.

**모듈 사이에 쓰는 이름은 공개 이름이다.** 다른 모듈의 밑줄 이름을 import하거나 속성으로 읽어야 한다면, 소유 모듈에서 그 이름을 공개 이름으로 바꾸고 이 표에 올린 뒤 쓴다.

1~5절은 쓰는 방법까지 정해진 규칙이다. 6절은 모든 정본의 이름과 위치를 모은 표다.

## 1. 파일 메타데이터 지문

**정본**: `file_io.py`

- `stat_fingerprint(st)`는 `(st_size, st_mtime_ns, st_birthtime_ns)`를 돌려준다. `os.stat`, `os.fstat`, `os.DirEntry.stat(follow_symlinks=False)`의 결과를 모두 받는다. Windows에서 `DirEntry.stat()`의 `st_ino`는 0이므로 파일 ID 대신 생성 시각을 넣는다.
- `file_fingerprint(path)`는 `stat_fingerprint(os.stat(path))`다.
- `fingerprint_json(fp)`는 지문의 저장 형식 `[크기, "수정 시각 ns", "생성 시각 ns"]`를 돌려준다. 나노초 시각은 `canonical_json`의 안전 정수 한도(2^53)를 넘으므로 문자열로 둔다. 지문을 JSON에 기록하거나 기록된 지문과 대조하는 곳은 모두 이 함수를 쓴다.
- `fingerprint_settled(fp)`는 지문의 수정 시각과 생성 시각이 모두 `RACY_NS`(2초)보다 오래되었을 때 참이다. Windows 파일 시각은 약 15.6ms 단위로 움직이므로, 읽은 직후 같은 크기로 다시 쓴 파일은 지문이 같게 남을 수 있다.

규칙은 셋이다.

- 파일이 바뀌었는지를 메타데이터로 판정하는 코드는 위 함수를 쓰고, `(st_size, st_mtime_ns)` 같은 튜플을 모듈 안에서 따로 만들지 않는다. 진행 표시처럼 파일 크기만 읽는 코드는 변경 판정이 아니므로 여기에 들지 않는다.
- 지문이 같다는 이유로 내용 읽기를 건너뛰거나 캐시를 다시 쓰는 곳은, 기준으로 삼은 지문이 `fingerprint_settled`일 때만 그렇게 한다. `cached_sha256`은 이 규칙을 이미 적용한다.
- 지문이 같으면 내용도 같다고 보는 판정은 우발적 변경만 다룬다는 위협 모델에서만 성립한다. NTFS 터널링 때문에 같은 이름을 지우고 약 15초 안에 다시 만들면 생성 시각이 보존되므로, 크기와 수정 시각까지 보존한 교체는 지문으로 잡히지 않는다. 이 한계를 명시하는 시험은 `tests/test_file_io.py`의 `FingerprintTests`다.

## 2. 전 바이트 해시와 JSON digest

**정본**: `file_io.py`, 상태 저장 값은 `repository.py`

파일 해시는 두 함수만 쓴다. 모듈 안에 파일 해시 도우미를 새로 만들지 않는다.

- `sha256_file(path)`: 파일 전 바이트의 SHA-256이다. 1MiB 단위로 스트리밍한다.
- `cached_sha256(path)`: 지문(1절)이 바뀐 경우에만 다시 계산하는 SHA-256이다. 프로세스 전역 캐시이며 키는 정규화한 절대 경로다. 읽는 도중 파일이 바뀌면 캐시에 넣지 않는다.

둘 가운데 무엇을 쓸지는 목적으로 정한다.

- **`cached_sha256`**: 사용 경로에서 바뀔 수 있는 파일의 식별값을 반복해서 얻는 곳. 설치본 파일, CLI 실행 파일, 동결 사본, 판본 식별에 쓰는 Lean 실행 파일(`lean.exe`, `lake.exe`와 인자의 `.exe`·`.dll`), `lean-toolchain`, `lake-manifest.json`, lakefile, 검사기 `formal.py`가 여기에 든다.
- **`sha256_file`**: 새 내용 확인이 목적인 곳. `setup_lean.py`의 설치 기준과 `--rerecord`·`--check-contents`, `check` 명령, 기준을 처음 만드는 곳이 여기에 든다.
- 메모리에 있는 바이트는 `hashlib.sha256(raw).hexdigest()`로 직접 해시한다.

JSON 값의 digest는 두 정본만 쓰며, 모듈 안에 `_digest`·`_hash` 같은 도우미를 새로 만들지 않는다.

- **상태 저장 값**(연구 상태에 들어가는 값)의 식별은 `repository.exact_content_hash(value)`다. `sha256(canonical_json(value))`이며, 저장 값 영역을 검사한다.

상태 값의 동등성은 `canonical.same_json_value(left, right)`가 정한다. Python에서 같은 값으로 비교되는 boolean과 integer도 서로 다른 JSON 값으로 구별한다. `StateContract.validate`의 부모 레코드 검사 생략, `repository._encode_families`의 부모 바이트 재사용, `CoreEngineMixin._unchanged`의 게시 생략이 같은 함수를 사용한다. 값 영역 검증은 기존 후보 봉인 경계에서 유지하며, 이 비교 함수가 입력 검증을 대신하지 않는다. 실제 엔진 게시와 저장/적재의 `1 → True → 1`, boolean 스키마에 integer를 넣는 반려를 함께 검사한다.
- **저장 값 영역 밖의 JSON**(소수가 들어 있는 공급자 응답, transport 파일 등)은 `file_io.json_digest(value)`다. 압축 정렬 JSON에 `allow_nan=False`를 적용한 SHA-256이다. `file_io`에 두는 까닭은 이 digest를 쓰는 `control_transport`가 worker의 MCP 서버로 Windows Job 안에서 패키지 없이 직접 적재되며, 그때 함께 적재되는 모듈이 `file_io`이기 때문이다.

두 정본과 바이트가 다른 기존 변종 둘은 그대로 둔다. 이 변종의 값은 저장되고 다시 대조되므로, 직렬화 규칙을 바꾸면 저장된 digest와의 비교가 어긋난다. `formal`의 ASCII 이스케이프 직렬화 3곳은 저장 계약 `do-math-state/7`에서 `exact_content_hash`로 옮겼다.

- `scheduled_operator`의 기본 구분자 직렬화 2곳. 실패 하나당 자동 복구를 한 번으로 제한하는 데 쓴다.
- `observations`의 규칙 digest. 모듈의 `_raw_json` 하나로 만든다.

`request_sha256`은 transport 영수증과 엔진 control 영수증에서 서로 다른 값을 가리킨다. 두 값을 서로 비교하는 곳이 없으므로 이름을 가르지 않았다.

## 3. 봉인 artifact 대조

게시 경계의 `delegations.prepare_application`은 같은 위임·case ID의 보존 행을 먼저 찾아 원 case 내용과 현재/보존 basis hash를 확인한다. 새 ID는 전체 basis의 hash에서 정하므로, 이 순회 뒤 같은 ID를 다시 찾는 경로는 두지 않는다. `integration.validate_impact_review_response`의 승인 범위는 계산된 영향과 선언된 영향의 합집합이며, `submission.read_sealed_submission`은 원 bytes·영수증·check의 후보 결속과 capture eligibility를 각각 확인한다. 부분 후보는 `issued_input`의 원 context/schema로 다시 결속한다.

`submission._payload_issues`는 영향 검토의 확장 변경을 `submission.impact_review`로 반려하며, `integration.inspect_bundles`는 maintenance 응답을 한 bundle로 묶는다. `_reviewed_impact_request`는 이 중앙 검사를 통과한 봉인 bytes를 읽어 원지정 action과 실제 게시 영수증을 확인한다. `payload_issues`가 bundle별 배열 검사를 되돌리는 좌표는 검사한 slice의 정수 index와 원 member 목록으로 직접 연결한다. `knowledge.replace_knowledge`가 동일한 사용 가능 Lean 증거를 재사용할 때는 `knowledge_records.create_candidate`가 만든 임시 formal result를 제거하고 원 ID를 연결한다.

저장된 `sources`의 path/sha256과 `trust_validation.ENVIRONMENT_REQUIRED`의 allowed_axioms는 필수다. `_research_source_spec`과 `knowledge_records.proposal_view`는 저장 경계가 검사한 이 값을 직접 소비한다. `submission.fixed_research_reference_path`는 이미 지급된 source ref에 None을 반환하고 새 workspace 증거에만 경로를 반환하므로 `_apply_review_research`는 반환된 경로의 보존 파일을 확인한 뒤 source 집합에 한 번 추가한다. `_record_review_input`은 이미 입장한 실행이라도 현재 cycle owner와 실행 owner의 일치를 별도로 확인한다.

`knowledge.plan_impact`의 계산·선언 합집합은 종류 정의·신뢰 환경도 참조할 수 있다. `_apply_impact_effects`는 이 두 권위와 실행·활동의 원기록을 보존하고, 영향 ID를 `knowledge_reassessment_required`와 `research_plan`에 남긴다. 종류 철회·환경 무효화는 각각 `knowledge_io.withdraw_kind_definition`·`knowledge.invalidate_environment`의 전용 처분이며, 일반 `input_current`/`use_history` 필드를 이 가족에 추가하지 않는다.

`formal_engine`은 등록된 환경의 형식을 transition 요청과 trust check에서 반복 검사하지 않는다. 공개 등록의 `register_request_errors`→`environment_errors`와 저장 계약을 소비하며, 실제 파일·기록·fingerprint 입장은 `trust_validation.check_environment`가 계속 맡는다. 공개 무효화는 대기 중 transition을 지우지 않으므로 `_trust_check_steps`의 invalid 검사는 별도로 필요하다. `formal_check`·`trust_check`·`trust_activate`의 제품 생산 action은 새 활동 또는 자기 machine 시도의 continuation을 소유한다. AI review-restoration 활동을 상속하지 않고, `build_profiles`의 해당 역할은 provider/model/host 예약이 없어 `_register_execution`의 정상 반환은 실행이다. 이 전제는 공유 등록기의 AI·external 거절 계약을 바꾸지 않는다.

`_formal_steps`는 원반환을 먼저 게시하고 `stop()`으로 고정 환경·권한·decision basis의 현재성을 판단한다. 공개 개정은 새 KN/FR을 만들고 원기초 변경을 중단 사유로 남기므로 같은 KN의 원문 덮어쓰기 검사는 두지 않는다. 종료 정산 뒤에도 시계를 확인하고 `knowledge_records.record_formal_result`가 활성 환경·진행 중 transition·정확한 증거·기봉인 결과를 검사한다. 컴파일 중 새 transition이 시작되면 이 수신자가 게시를 거절하며 원 verified 반환과 failed 처분을 각각 보존한다. `formal._job_run`의 stopped 반환은 종료 확인·원 stdout/stderr 수집 뒤 실행되고 `finally`가 Job을 닫는다. if와 return을 별도 행으로 써서 try/finally의 실제 분기와 측정 좌표를 일치시킨다.

`retention._run_path`는 `values.check_path_segment`로 단일 실행 이름을 검사한 뒤 `_physical`의 reparse 검사를 사용한다. 이름 검사 뒤 `runs` 밖의 부모가 생기는 별도 fallback은 없다. `review_cycle.accept_result`는 `next_actions`에 포함된 정확한 기록 대체 action만 받으며, 이후 manifest의 continuity break·grant ID/hash를 검사한다. `ReviewEngineMixin._retry_review_initialization`은 활성 lifecycle와 채택 policy의 정확한 hash를 확인한다. policy 형식·의미 검증은 `initialization.activation_requirements`가 `review_policy.build_review_policy`를 호출하고 `lifecycle_engine.LifecycleEngineMixin._activate_initialization`가 그 결과를 소비하여 채택 전에 맡으므로 같은 hash의 policy를 재구축해 실패를 숨기지 않는다.

**정본**: `repository.py`

`runtime/artifacts/` 아래의 기존 번들은 바뀌지 않는다. `git_store`의 `_validate_artifact_changes`가 기존 번들에 대한 쓰기를 거부한다. 그래서 한 프로세스가 저장된 artifact 바이트를 봉인 행(경로, sha256, 선택적인 크기)과 한 번 대조하면, 그 대조는 프로세스가 끝날 때까지 유효하다. 저장소가 다르면 같은 경로라도 별개로 다룬다.

- `VERIFIED_ARTIFACTS`: 이 프로세스가 대조한 행을 담는 dict다. 키는 `artifact_key(git_dir, path, sha256)`, 값은 대조한 바이트 길이다.
- `artifact_key(git_dir, path, sha256)`: `(str(git_dir), path, sha256)`. 봉인 행을 키로 쓰는 프로세스 메모는 모두 이 키를 쓴다.
- `artifact_verified(git_dir, path, sha256, size=None)`: 이미 대조했는가. `size`를 주면 길이까지 같아야 참이다. `git_dir`가 None이면 늘 거짓이다.
- `verify_artifact(git_dir, path, raw, sha256, size=None)`: 바이트가 봉인 행과 다르면 `ValueError`를 내고, 같으면 행을 기록한다.
- `mark_artifact_verified(git_dir, path, sha256, size)`: 호출자가 이미 성립시킨 대조를 기록한다.
- `sealed_bytes(git_dir, path, sha256, size, read, *, raw=None, needed=True, error=None)`: 소비 규칙의 정본이며 봉인 행의 바이트를 돌려준다. 바이트는 호출자가 이미 가진 것이면 `raw`로 넘기고, 없으면 인자 없는 함수 `read()`가 저장된 바이트를 읽어 준다. `size`는 행이 선언한 길이이고, 선언이 없으면 None이다. 이미 대조한 행이면 해시하지 않는다. 이때 `needed=False`면 읽지도 않고 `raw`를 그대로 돌려준다(None일 수 있다). 대조하지 않은 행이면 바이트를 대조하고 기록한다. 바이트가 다르면 `ValueError`를 내는데, `error`를 주면 그 문구를 쓴다. `git_dir`가 없으면 매번 대조하고 기록하지 않는다.
- `ResearchRepository.git_dir`: 키에 쓰는 저장소 식별이다. 엔진에서는 `self.store.git_dir`로 얻는다.

규칙은 다음과 같다.

- 봉인 행의 바이트를 쓰는 코드는 `sealed_bytes`를 부르고, "이미 대조했으면 생략, 아니면 대조" 규칙을 다시 구현하지 않는다. 로컬 `hashlib` 비교나 별도 캐시를 만들지 않는다.
- 바이트에서 파생한 값(형식 검사 결과 등)을 메모이즈하면, 키는 그 값을 정하는 입력만 담고 저장소를 담지 않는다. "이 저장소의 바이트가 봉인과 같은가"는 `VERIFIED_ARTIFACTS`의 사실이고, 파생값의 메모는 그 대조를 대신하지 않는다. `planning`의 `artifact_valid` 판정 메모가 이 예다. 키는 (판정 함수, 경로, sha256)이고, 바이트 대조는 평가마다 `sealed_bytes`가 맡는다. 판정이 이미 있으면 바이트를 읽지 않고(`needed=False`), 길이는 `VERIFIED_ARTIFACTS`에 기록된 값을 쓴다. 저장소와 무관한 순수 메모이므로 시험 기반이 비우지 않는다.
- 프로세스 메모의 키는 결과를 정하는 바이트의 식별을 담는다. 경로만으로는 모자란다. 같은 경로에 새 저장소가 생길 수 있기 때문이다(시험의 템플릿 복원이 그렇게 한다). 봉인 행 메모는 행의 sha256을 키에 담으므로, 경로를 재사용해도 남은 항목이 틀린 답을 내려면 새 저장소의 바이트가 자기 봉인 해시와 달라야 한다. 이것은 한 저장소 안에서 이미 대조한 행이 나중에 손상된 경우와 같고, 이 규칙이 이미 받아들인 범위다. 봉인 행 없이 artifact를 해석해 메모하는 곳은 읽은 바이트의 sha256을 키로 쓴다(`submission.issued_input`). 검증 읽기(`_VALIDATED_READS`)와 artifact 사실(`_ARTIFACT_FACTS`)은 커밋 OID를 키나 계보로 쓴다.
- 이 모듈의 프로세스 전역 캐시는 저장소를 가진 스레드만 쓰므로 잠금을 두지 않는다(`repository.py` 모듈 설명). 작업 스레드는 순수 함수 `canonical_json`과 `exact_content_hash`만 가져다 쓴다.
- 상태 기록끼리의 대조, 곧 기록한 봉인 해시와 참조 행의 해시가 같은지 보는 비교는 식별 비교이므로 이 규칙과 무관하게 유지한다.
- `artifact_verified`와 `mark_artifact_verified`를 `sealed_bytes` 밖에서 직접 부르는 곳은 아래 다섯뿐이며, 새로 늘리지 않는다.
  1. `payloads._read_json_blob`(`decode`와 `payloads._decode_snapshot`의 공통 읽기 경계)는 이 규칙의 **등록된 변종**이다. payload와 snapshot blob은 바이트가 봉인 해시와 같은 것에 더해, 그 바이트를 해석한 값을 다시 정규 JSON(`canonical_json`)으로 직렬화한 바이트가 원래 바이트와 같아야 대조가 성립한다. 그래서 행의 기록을 정규 JSON 확인 뒤로 미룬다. 이미 기록된 행은 해시와 정규성 확인을 건너뛰며 선언된 길이는 계속 대조한다.
  2. `context_store.verify_manifest_artifacts`는 이미 대조한 행을 일괄 읽기 대상에서 빼는 데에만 `artifact_verified`를 쓰고, 남은 행은 `sealed_bytes`로 대조한다. 변종이 아니다.
  3. `ResearchRepository._validate_artifact_evidence`는 정본 모듈 안에서 게시 전 artifact 증거를 한꺼번에 읽어 대조한다.
  4. 엔진의 `_maintenance_cleanup`은 `retention.archive_run`이 해시한 바로 그 바이트를 게시한 뒤, 게시한 보관 행을 `mark_artifact_verified`로 기록한다.
  5. `ResearchRepository._remember_published`는 이 프로세스가 방금 게시한 후보의 payload blob을 `mark_artifact_verified`로 기록한다. 그 바이트는 후보 검증이 정규 JSON으로 직렬화해 해시한 바로 그 바이트이고, 경로가 그 해시를 이름으로 가진다.

## 4. 상태 판본 키

- 게시된 상태에서 계산한 파생값은 `self.head`(커밋 ID)를 키로 메모이즈할 수 있다. head가 같으면 게시된 상태 전체가 같다.
- 저장되지 않은 메모리 상태를 읽는 계산은 `self.head`로 메모이즈하지 않는다. 엔진은 게시 전에 `self.instance`와 `self.runtime`을 직접 고치므로, head가 같아도 메모리 상태는 다를 수 있다. 이런 계산을 메모이즈하려면 입력값 자체를 키로 쓴다. 예를 들어 `lean_code`의 해시는 `lean_code` 문자열을 키로 캐시한다.

## 5. 스키마 빌더의 반환값

**정본**: `values.json_copy(value)`

스키마를 만들어 돌려주는 함수는 결과를 `json_copy`에 통과시켜 돌려준다. `json_copy`의 결과에서는 어떤 dict나 list도 모듈 전역 객체와 같은 객체가 아니고, 결과 안에서 한 객체가 두 번 나오지도 않는다. 그래서 호출자는 돌려받은 스키마의 어느 노드든 제자리에서 고쳐도 된다. 고친 효과는 그 결과 하나에만 미친다.

`copy.deepcopy`로는 이 성질이 생기지 않는다. `deepcopy`는 원본 안에서 여러 번 쓰인 노드를 사본 안에서도 한 객체로 둔다. `contracts.TEXT`처럼 여러 필드가 같은 전역 노드를 쓰는 스키마의 `deepcopy` 사본에서 한 필드에 `enum`을 넣으면, 같은 노드를 쓰는 다른 필드에도 `enum`이 들어간다. 보충 조사 제출이 모두 거부된 결함이 이 기전으로 생겼다. 빌더가 모듈 전역 노드를 사본 없이 그대로 싣고 돌려주면 피해는 더 넓다. 제자리 변경이 전역 노드를 바꾸므로, 그 프로세스에서 이후에 만드는 모든 스키마가 바뀐다.

현재 이 규칙을 따르는 빌더는 다음과 같다.

- `contracts`: `schema_for`, `disposition_schema`, `identify_schema`를 거쳐 돌려주는 `with_integration_schema`와 `action_schema`
- `submission.extension_schema`, `integration.impact_review_response_schema`
- `review_cycle`: `stage_schema`, `research_schema`, `research_request_schema`
- `governance.interpretation_schema`, `record_schemas.config_schema`
- 이름에 `schema`가 없는 조합 함수도 포함한다: `contracts.closed_object`, `control_contracts.obj/fields`, `record_schemas.schemas.array/nullable/enum/obj/record/mapping`, `review_cycle._array`.
- `provider_final.output_contract(provider, schema)`: Codex는 원 schema를 description 문자열로 직렬화한 새 `output_json` 봉투를 만들고, Claude는 `json_copy`로 같은 schema 값의 독립 사본을 돌려준다. 두 분기는 입력과 다른 반환뿐 아니라 반환 내부의 가변 노드도 공유하지 않는다.

`supervision.repair_report_schema`는 같은 규칙을 따른다. 현행 시험은 `tests/structure/test_schema_builders.py`다. 공개 함수 이름의 `schema` 포함 여부를 탐색하는 목록과 이름 없는 조합 함수 목록을 함께 검사하며, 각 인자 변형을 두 번 호출하고 반환값들을 보관해 전역/다른 결과/한 결과 내부의 공유 노드를 찾는다. 빌더가 `None`을 반환하거나 같은 가변 결과를 보관했다가 다시 주면 검사 자체가 실패하는지도 검증한다. 이 명시 목록을 전체 1-E 모집단의 자동 완전성 증거로 읽지 않는다.

`_composition_calls`는 `output_contract`의 두 공급자에 두 속성이 같은 leaf를 가리키는 schema를 넣어 반복 격리 검사에 연결한다. 직접 값 검사는 Codex 봉투에 원 schema가 보존되고 Claude의 한 필드 변경이 형제 필드·입력·다른 반환에 전파되지 않는지 확인한다. 현재 `ModelRunner.run`은 비결박 Codex에만 이 함수를 호출하며 Claude schema는 바로 JSON으로 저장한다.

모듈 전역 스키마 상수(`TEXT`, `REFS`, `SCHEMAS` 등)는 모듈 적재가 끝난 뒤 제자리에서 고치지 않는다. 다른 모양이 필요하면 새 노드를 만든다.

## 7. 검토·위임·해석의 불변 구조 저장

정본은 `payloads.py:_snapshot_selected/_encode_snapshot/_decode_snapshot`와 이를 호출하는 `encode/decode`다. 저장 계약은 `do-math-state/10` 하나이며 과거 저장 표현을 자동 변환하지 않는다. `record_schemas`의 논리 값 스키마와 생산자의 인자는 그대로다. 저장할 때만 `review_cycles`, `delegation_applications`, `intent_imports`의 최상위 dict/list 필드 및 singleton `review_inputs`의 각 자리 문맥를 봉인 구조로 분리한다. 기록 ID·revision·status 같은 scalar는 봉투 안에 남아 기존 summary 소비자도 읽을 수 있다.

봉투의 `payloads` 행은 기존 `{tokens, path, sha256, bytes}` 형태다. 큰 문자열은 `runtime/artifacts/payload-<sha256>/value.json`, 구조 노드는 `runtime/artifacts/snapshot-<sha256>/value.json`을 쓴다. sha256은 각 노드의 정규 JSON 바이트를 식별하며, proposal/basis/import의 **논리 값 hash**를 대체하지 않는다. 객체는 UTF-8 키의 prefix 없는 bit 경로(각 byte 앞의 1과 끝의 0)로 만든 압축 이진 trie다. leaf는 정확한 키와 scalar/node/text cell을, branch는 최초로 다른 bit 위치와 두 자식 hash를 담는다. 한 키의 추가·변경은 그 키 경로의 branch만 새로 저장하며 전체 키-참조 표를 복제하지 않는다. 키 hash나 충돌 가정은 쓰지 않는다. 목록 노드는 빈 목록 또는 `{kind:list, previous:<prefix hash>, item:<cell>}`다. 같은 구조를 여러 곳에서 쓰면 불변 바이트 한 벌을 공유하며, 목록에 한 행을 추가하면 이전 prefix와 새 행을 가리키는 노드 하나가 늘어난다. 그래서 이전 모든 cycle을 보존해도 각 판본의 전체 목록을 다시 저장하지 않는다.

읽기는 `_read_json_blob`에서 존재·bytes/SHA·정규 JSON을 확인하고 `payloads._decode_snapshot`에서 노드/셀/목록 prefix를 검증한다. 목록 prefix와 객체 trie는 판본 수·키 수에 따른 재귀 깊이 없이 반복으로 복원한다. `payloads.decode`는 다시 인코딩한 봉투와 비교해 좌표 중복·형태 변경·필수 구조 분리 누락을 반려한다. node document는 한 복원 안에서 재사용하지만, 반환되는 dict/list는 모든 논리 좌표마다 새로 만들어 다른 record·형제 좌표의 가변 값과 공유하지 않는다. 불변 `FrozenText`는 기존대로 공유한다.

`ResearchRepository.load/read_record`와 `context_store.read_content`는 이 동일 decoder로 전체 값과 목록 순서를 복원한다. 검토 전문·판본 이력·논리 슬롯·transcript manifest, 위임 두 독립 판단의 입력, 해석 owner currentness는 복원된 원래 값으로 검사한다. 검토 이력이나 revision 수를 줄이지 않으며 pending `review_inputs`의 수신/defer 제거 규칙도 바꾸지 않는다. 원천 구조 바이트와 참조 좌표 비용을 구분하면 저장 증가량은 서로 다른 불변 구조 노드·목록 추가 행 및 저장 좌표 수에 비례한다. Git 압축률이나 실행시간 보장은 아니다.

새 cycle의 `input_bindings`는 현재 cycle 실행만 가진다(`review_engine._start_identity_review`). 이전 실행의 binding은 보존된 이전 cycle에서 봉인 replay와 record query로 읽는다. 전문 복원은 `turns/transcript_manifest`를 사용하므로 이전 binding 사본은 필요하지 않다. 논리 슬롯의 profile과 transcript·manifest 이력은 계속 계승한다.

## 7. 과제 판정과 실제 대기 소유자

역할 판정값은 `contracts.REVIEW_ITEM`의 계약검토 세 값, `disposition_schema()`의 운영 처분 여섯 값, `SCHEMAS['goal_audit']`의 목표감사 세 값, `SCHEMAS['research_plan']`의 과제평가 세 값이 정한다. 계약검토의 종합 판정은 `contract_review_decision`이 항목별 판정을 소비한다. 운영 점검의 옛 `revise`는 현행 판정값이 아니며, 계약 개정 요청은 기존 `revision_requests` 확장을 통해 별도로 소비한다.

`core_engine._apply`는 승인 계약을 planned로 두고, 일반 과제의 반려·미해결 계약은 같은 revision에 `revision_requested`와 `waiting.kind=contract_revision`을 저장하여 준비 역할로 돌려보낸다. 실제 새 계약 생산은 이전 계약·대기를 `revision_history`에 남기고 독립 검토를 요청한다. 학술 계약의 반려는 사용자 기준을 보존한 채 기존 `planning_engine._ensure_model_assessments`가 평가·관찰 규칙 준비를 다시 요청하며, 일반 계약 교체 대기를 추가하지 않는다. 승인 검토는 선택 직전 무효화가 만든 `contract_review` 대기를 해소한다. `revision_engine._selected_action_current`는 선택 계약 변경과 승인 현재성 상실을 구별한 사유, 원 action의 `basis_ref`, readiness의 원 `errors`를 보존한다. 변경 계약이 이미 준비 가능하더라도 사유를 빈 오류 목록으로 대신하지 않는다.

`task_scope.apply_task_assessments`가 저장하는 불완전 평가의 대기는 누락 입력이 있으면 `assessment_input`, 없으면 `research_followup`이다. 원 `reason`, `target_refs`, `next_owner`, 평가 실행 `basis_ref`를 함께 저장한다. 자료 도착은 `assessment_current`/`refresh_task_assessments`를 통해 평가의 현재성을 잃게 하고 새 평가를 요청할 뿐, 원 수행 결과나 잔여 의무를 완료로 바꾸지 않는다. accepted plan의 정확한 현재 평가와 선택이 후속 연구를 연다. 개정 수행 결과의 `assessment` 대기는 `_apply_revision_followup`이 생산하며, 수행 outcome=waiting은 이를 강제하지 않는다. 이 다섯 저장 대기와 `planning.task_ready`의 permission·condition·contract_revision 준비 투영은 서로 다른 대상이다.

`revision_dependency`의 대상별 개정·선택적 유지·위임·보류는 `_apply_revision_followup`이 소비하고, 종결 과제는 `_retire_closed_revision_targets`가 은퇴시킨다. 해소·양도·은퇴한 원 action의 실제 활동은 `_settle_revision_owner`가 원 `owner_activity_id`/`execution_id`와 `waiting.condition.action_ids`를 대조한 뒤 기존 `_settle_activity`로 판정한다. 다른 남은 대기·queue·살아 있는 실행이 있으면 유지하며, 활동 종결은 성공 결과를 새로 만들지 않는다. 원 실행의 결과·미해결 의무와 해소 이력은 보존한다.

`core_engine._register_execution`의 machine 입장은 실제 `SessionSlots.acquire` 성공 뒤에 활동을 해소한다. 입장 거부의 동일 조건은 원 대기 시각·활동·예약을 보존한다. 현행 설정이 host cap을 작성하는 machine 역할은 `external_action`이며, Lean/trust 역할의 uncapped 계약을 시험용 capped profile과 혼동하지 않는다. review admission 반려는 기존 admission에 `action_ids=[action.id]`를 함께 생산하고, 기존 `_release_review_wait`가 정확 cycle/stage/round/slot의 해소 ID와 이 좌표를 소비해 다음 실행 등록 전에 활동을 ready로 만든다.

`ACTIVITY_EXTRA_WAIT_RULES.review_resource_deferred`의 출구는 고정 제안의 supersession/withdrawal·instance 종료다. 자원이나 시각 변화로 고정 scope를 다시 여는 API를 뜻하지 않는다. `user_resume`와 `required_input`은 공개 `activities.wait_for`/`resume_activity`의 호출자가 조건을 소유하며, 현재 내부 engine에 별도 자동 만족 생산자·해소자는 없다. reporting의 required_input 준비 투영은 활동의 stored kind 생산과 구별한다.

공개 표시는 `reporting.task_status`가 같은 snapshot의 저장 대기를 `status.tasks[].waits`로 복사하고 `render_human_report`가 같은 JSON을 표시한다. 준비 요청의 `assessment_targets`/`observation_rule_targets`도 queue와 live execution에서 동일하게 과제에 연결하므로, task target이 없는 전용 준비의 담당자·요청/실행 좌표가 표시된다. `tests/support/wait_reporting.assert_task_wait_report`는 실제 생산·저장한 사유·담당자·대상·근거 좌표, JSON 왕복, 조회 불변과 반환 독립성을 대조한다. 역할과 대기 전이의 직접 단언은 `sim.test_planning_engine_receivers.ContractVerdictReceivers`, `sim.test_planning_revision_transitions.RevisionTransitionTests`, `sim.test_planning_scope_receivers.AssessmentReceiverTests`, `sim.test_planning_engine_connections`, `sim.test_planning_preparation_transitions` 및 `sim.test_planning_revision_obligations.DelegatedWorkRevisionTests`에 있다. enum이나 공통 constructor만으로 실제 owner 전이를 증명하지 않는다.


## 8. 저장 지식·신뢰·검토의 필드 생산과 전이 기초

권한·온톨로지의 저장 대응은 `tests/support/storage_authority_pairs.py`와 `tests/contracts/test_storage_authority_pairs.py`가 같은 `contracts.pairs.assert_pair`로 검사한다. `governance.preserve_source/initialize_governance/_install_record/apply_decision/normalized_grant`의 원문·정확 승인·명시 supersession·발급/교체/취소·원결정 위임/철회, `knowledge_io.ensure_ontology/register_kind_definition/check_kind_definition/activate_kind_definition/withdraw_kind_definition/import_relation`의 등록 계보·관계 revision을 실제 Repository 게시/load에 연결한다. 관계는 list item, 나머지 레코드는 map member를 검사하고 닫힌 content·document·terms·constraints도 필수/선택 필드 역방향에 포함한다. `governance_approval`의 boolean/object singleton은 열린 값 슬롯 `/value`로 검사하며, 실제 초기화의 부재와 정확 승인 object의 내용·해시 보존을 확인한다. 빈 properties로 통과시키거나 열린 증거에 임의 필드 의무를 만들지 않는다.

현재 생산자가 없는 선택필드는 `decisions`의 `coverage/intent_check/author_execution_ids`, `kind_definitions`의 `history/checks/activation`, `relations`의 `lifecycle/created_at/actor_ref/origin_refs/source_basis`다. 이 11개는 닫힌 정본에서 허용하지 않는다. 종류의 실제 검사·승인은 `check_ref/checked_by/approval_ref/activated_by`와 `CoreEngineMixin._apply_kind_definition_check`의 `check`다. `check`는 원 판정의 definition ID/hash·decision/findings와 검사 실행 ID를 보존하는 열린 증거 object이며, 실제 core 판정 뒤 검증 게시에 필요하다. 종류 저장의 도메인 함수 표본만으로 이 core writer의 부재를 결론내릴 수 없다. 관계의 작성 기록은 `imported_at/imported_by/source_ref`이며 `history/use_history`와 수학 관계의 `formal_result_refs/assessment_refs`는 유지한다. 제거 필드 저장 반려는 이전 head를 보존하고, 미생산 optional을 더한 schema는 동일 역방향에서 실패한다. 의미 대응과 fresh T3의 전체 쓰기분기 도달은 별도 확인이다.

## 입력·자료와 보류 확장의 저장 대응

`tests/support/storage_input_pairs.py`의 `family_pair`는 기존 `contracts.pairs.Pair/assert_pair`와 `storage_authority_pairs._named_fields`를 소비한다. `research.sources`와 `runtime.inputs`는 list item의 필수·선택 필드를, singleton `runtime.pending_kind_checks`는 그 안의 닫힌 item 필드를 검사한다. singleton `runtime.private_insights`는 cycle ID→열린 항목 배열이므로 `/value`와 독립 원내용·순서·작성자·격리 단언으로 검사한다. 임의 열린 evidence의 키를 닫힌 필드 목록으로 만들지 않는다. 각 실제 게시의 첫 읽기는 새 `installed_contract()`와 `ResearchRepository`로 decode하며 옛 head도 보존한다.

`initialization.initialize_state`는 빈 sources와 최초 원text/config/시각/UI ID/SHA 입력을 생산한다. `core_engine.initialize_instance`는 파일의 원bytes·name·SO ID·path·SHA·크기를 저장한다. `_apply_inbox`는 `control_contracts.normalized_source_bytes`의 정확 base64/hash/size 검사를 공유하며 Unicode/CRLF/비텍스트 bytes를 바꾸지 않는다. 동일내용은 revision/history를 바꾸지 않고, 실제 변경은 같은 ID·기존 row history·새 source.bin·revision·status/source_ref를 기록한다. `sources.created_at`은 writer가 없어 허용하지 않는다. 후속 input은 실제 inbox request의 ID/text/config/created_at/accepted_order/origin/instance_id/action을 저장한다. 최초 입력에만 있는 sha256와 후속 수신 전 제어요청을 같은 모양으로 보충하지 않는다. 입력 순서·재전달·재시작과 영구close의 반려, 원자료 현재성의 소비는 각각 기존 owner 계약을 유지한다.

`_apply_extensions`는 review 실행의 research_insights에 source_execution을 붙여 cycle별로 보류한다. working 중에는 knowledge로 발행하지 않고 completed/unresolved 후 해당 cycle만 제거하여 원 작성자·원내용·순서로 발행하고 research_plan에 연결한다. 다른 cycle은 비공개로 남는다. 보류 중 종류·근거가 무효가 되면 원 작성자의 history/question으로 남기며 해제한 검토자에게 귀속하지 않는다. 이 분기는 현행 종류 철회에서도 도달하므로 구판 전용 분기가 아니다. `test_review_released_insights`의 수동 fixture는 국소 해제 성질의 근거이고 실제 생산/저장의 대체가 아니다. 새 저장 표본은 실제 scope/initial 검토·입장/등록/수명·적용을 사용하며 모델 수송/중앙제출은 합성 입력이다.

`_propose_kind`는 원 definition을 등록하고 family/token/definition_id/source_ref/actor_ref를 pending item에 쓰며 정확 ID/hash의 독립 maintenance 검사를 예약한다. pending의 `execution_id`는 생산되지 않아 허용하지 않는다. 실제 검사 실행의 ID, definition.check.execution_id 및 queue의 검사 좌표와 구별한다. `_apply_kind_definition_check`는 현재 정의 hash와 checker.input_basis·독립성을 재확인한 뒤 approved는 활성화, revision_required는 철회, unresolved는 candidate 유지와 후속 준비를 수행한다. 해당 definition의 pending만 제거하며 다른 항목은 남긴다. 새 직접시험은 0/1/여럿, 세 판정·불일치 ID/hash/현재정의/입력기초·작성자 검사의 상태/head 불변과 check 원내용 보존을 검사한다. 별도 전체 쓰기분기/fresh T3 또는 모든 역할·선택값의 검증 도달을 뜻하지 않는다.

`record_schemas.schemas.RECORDS`는 각 가족의 실제 생산 필드만 허용한다. 지식 다섯 가족에 공통 관리 필드를 일괄 추가하던 `COMMON`은 없으며, `formal_results`/`expositions`의 생산 실행·원천·supersedes, `assessment_uses`의 history/use_history/environment_revalidation, `identity_assessments`의 봉인 검토·연속성·단계 전이 근거를 각 정본에 명시한다. knowledge의 imported_at/imported_by/source_ref/actor_ref/history/updated_at/use_suspension_reasons와 검토 cycle의 단수 producer_execution은 현행 생산자가 없으므로 허용하지 않는다. 검토 작성 실행의 실제 필드는 producer_execution_ids다. 제거된 27개 선택 필드는 저장 시 추가 필드 오류로 반려되며 구판 자동 변환은 없다.

`knowledge.begin_transition`의 target.basis는 `basis_record`의 정본 투영으로 해시한다. `formal_engine._trust_check_steps`와 `review_cycle.staged_review_candidate`의 `validate_basis` 수신 및 `knowledge.activate_transition`이 같은 의미를 사용한다. knowledge의 review_cycle_id/previous_review_cycle_id는 검토 일정 포인터이며 이 투영에서 제외된다. 제목·수명·참조·수학 내용과 formal/exposition의 전체 봉인 기초는 계속 검사한다. 이미 검토된 지식의 전이가 일정 포인터 때문에 즉시 stale이 되던 불일치를 해소한다.

시험 공통 순방향·역방향 검사는 `tests/contracts/pairs.py:assert_pair(case,pair,samples)`다. 기존 일반 pair 시험과 `test_storage_knowledge_pairs`가 같은 함수를 사용한다. `tests/support/storage_knowledge_pairs.py:family_pair`는 map record의 실제 키, singleton map의 각 항목 키, scalar metadata의 명시 value 슬롯을 구별한다. 각 표본은 실제 Repository/StateContract로 게시·load된 상태이며 pair는 설치된 가족 checker/validator로 다시 수신한다. optional schema 필드를 추가한 반례도 같은 검사에서 역방향으로 실패한다. 이 표본 순회는 전체 쓰기 지점의 분기 도달 측정을 대신하지 않는다.

`test_storage_execution_pairs.StorageExecutionPairTests.assert_pair`도 같은 공통 함수를 소비한다. 실행 가족의 정본은 `record_schemas.schemas.RECORDS['executions']`와 `execution_lifecycle.create_execution/transition_execution`, `CoreEngineMixin._register_execution`, `SessionSlots.acquire/started/release`다. 최상위 실행 종료는 `ended_at`, 프로필은 `execution_profile_ref`, 프로세스 신원은 `launch_ticket`와 `capacity.process`에 있다. 활동·준비 이력의 `finished_at`, runner 반환의 중첩 `execution.started`, 요청의 `profile_ref`, 연구의 `workspace`는 각각 별도 경계다. 실행 최상위의 미생산 `pid/conversation_id/finished_at/workspace/parent_execution_id/profile_ref/submission_check/started/currentness`는 허용하지 않는다. `_apply_bundle_candidate`의 임시 `integration_id`도 게시 전에 제거되므로 저장 필드가 아니다. 실제 bundle 신원은 `integration_result.bundles`와 `result_disposition.integration_ids`에 보존한다. 삭제된 슬롯은 additional-properties 오류로 반려되며 변환·기본값 보충은 없다.

`governance.validate_independent_execution`은 검사 실행 자체·작성 실행과의 동일성·명시 `continuation_of`의 반복/작성자 도달/미해결을 검사한다. `execution_lineage`가 같은 계보 순회를 제공하며, `context_origin`까지 보는 검토 독립성과 구별한다. 현재 worker 요청은 Codex의 새 `exec --ephemeral`, Claude의 `--print --no-session-persistence`를 만들고 session 재개 인자를 받지 않는다(`worker_request.codex_argv/claude_argv` 및 요청 checker). provider native thread/session ID는 원 stream에 남으며 실행 최상위의 생산되지 않는 별칭으로 독립성을 판단하지 않는다. 사용자 연결 임대의 `runtime.conversations`도 모델 대화 신원이 아니다. OS 격리·같은 사용자 인증이나 공급자 내부 행동을 이 논리 독립성의 보장으로 넓히지 않는다.

`test_provider_stored_executions.StoredCallEvidenceTests`는 실제 준비/runner 반환의 입력·원결과·중앙 제출, unsealed 반려의 세 원자료 참조, 실제 maintenance archive의 종료·수집 자료를 별도 Repository load에 연결한다. `StoredExecutionTests`는 live-review 실패와 recovery 처분의 생성·종료 시 제거, 제거 필드의 정확 반려와 옛 head 보존을 검사한다. 이 대표 표본과 기존 직접 근거의 재사용은 executions의 모든 역할별 선택필드에 대한 독립 의미 단언이나 전체 쓰기분기 fresh T3를 자동으로 인증하지 않는다. 필드별 확인 범위는 해당 작업의 보고 근거로 구별한다.

검토 표본은 ReviewScene의 저장 시작 상태만 사용하고, 실행은 실제 engine._register_execution으로 등록한다. 실제 입장·scope·결말·단계 검토·권한 있는 transcript 교체·pending review_inputs 생산을 소비하며, 모델 수송은 합성 응답이다. 공용 ReviewScene.execute의 희소 실행 레코드를 저장 직전에 필드 보충하는 방식은 사용하지 않는다. 외부 Git·시계·컴파일러 관측은 기존 대역이며 새 native Lean/Git 성공 근거가 아니다.

## 사건과 제어·편입 영수증의 저장 계약

`record_schemas/schemas.py:RECORDS`와 `record_schemas.install`이 runtime.events
(ID가 있는 list), pending_events(문자열 참조 배열 singleton), event_cursor(NAT

새 사건에 event_seq를 추가하고 cursor를 갱신한다. 번호는 목록 순서대로 1..n이고

`CoreEngineMixin._publish_control_request`는 capability만 제거한 원request와

저장 CAS 완료가 승인 기준이며 응답 유실 뒤에는 durable receipt를 재조회한다.
동일 ID/내용은 원 영수증·feedback을 재전달하고 내용 충돌은 거부한다. preview와

미생산 root grant_id/snapshot/publication_id/payload_sha256/transport_id는 허용하지 않는다.

`integration.apply_bundles`는 실제 적용·현재성·후보검증·게시를 마친 bundle마다
execution_id/payload_sha256/members/input_snapshot을 기록하고, output을 소유한

반려한다. 실패 bundle은 기록하지 않아 독립 부분 수용 뒤 나머지만 재시도할 수 있다.

## 실행 요청의 입력 소유와 저장 위치

`CoreEngineMixin._enqueue`는 revision binding 전에 요청 전체를 deepcopy한다.
비교 필드의 assessment/observation target map과 병합 필드의 refs·observation·
revision_followup도 최초 삽입 때부터 큐가 소유한다. 호출자의 원입력을 나중에
변경해도 큐나 실행의 고정 action 입력은 바뀌지 않는다. 실행이 끝나지 않은
action은 후속 요청과 병합하지 않는다. 병합되는 요청은 첫 id/lineage를 유지하고
reason·requested_by·event/receipt/obligation/observation/evidence refs의 기존 순서와
중복 제거 규칙을 따른다. 서로 충돌하는 판단 payload는 별도 요청으로 남는다.

`record_schemas.schemas._ACTION`은 queue의 list item뿐 아니라 executions.action,
waiting_actions의 각 행.action, input_overflows.action의 공통 저장 형태다.
`Repository`는 queue 순서를 runtime manifest의 ids로 보존한다. waiting_actions는
action ID를 키로 쓰는 singleton이며 runtime/waiting_actions/state.json에 저장한다.
`record_schemas.validate_semantics`는 그 키와 원 action.id 및 실행 참조를 대조한다.

`tests/support/storage_action_pairs.py:preparation_case`는 기존 준비 보류 해소 시험과
저장 시험이 공유하는 실제 call/planning owner 장면이다. `keep`/`reader`는 별도
installed_contract 객체의 첫 load로 게시 blob과 이전 head를 확인한다.
`contracts.test_storage_action_pairs`는 원입력 격리·live 요청 비병합·정렬/병합·
revision 부모 보존·준비/진단/개정 위임/impact/검토 복구/입력 초과 보류와 공개 요청·
사건의 실제 생산값을 검증 게시한 뒤 확인한다. 기존 실행 저장 장면도 `StoredActions`의
새 reader를 소비하며 원 내용 단언을 유지한다. `action_pair`는 queue뿐 아니라
executions.action, waiting_actions.action, input_overflows.action 및
review_cycles.replacement_actions의 authority_request를 함께 투영한다.
`waiting_pair`는 action의 별도 공통 의무와 보류 행 자체의 의무를 구별한다.
공통 action은 최상위 86필드, 보류 행은 action을 포함해 24필드다. 닫힌 중첩 필드까지
`contracts.pairs.assert_pair`의 순방향/역방향 검사와 미생산 optional 추가 반례를 쓴다.
`storage_authority_pairs._named_fields`는 boolean schema의 명명 필드가 없는 의미와
닫힌 object/array/tuple prefixItems, map 값, nullable 및 조건 분기를 같은 순회에서 처리한다.
열린 evidence 내용은 원 응답/요청/과제·검토·사건/영수증과 별도 단언한다.

action의 activity_id/execution_id/created_at과 보류 행의 condition/waiting_reason/recovery는
현재 생산자가 없어 저장에서 허용하지 않는다. 실행 신원·시각은 execution, 원 owner는
action.owner_activity_id에 있다. 실제 해소 조건은 activity.waiting.condition이며 검토
복구 결과는 보류 행의 detail이다. action.reason은 생략 또는 문자열이고 보류 행.reason은
러너의 실제 오류가 없을 때 null도 보존한다. repetition_bases의 저장 키는
bind_repetition_bases가 생산하는 import_rework/selection_failure/exhaustion_empty다.
contract_revision/proposal_version의 대기 판정은 revision_targets에서 유도하므로 그 의미는
유지한다. planner action의 input_overflow에는 identity review 전용
without_restored_dialogue_bytes를 허용하지 않으며, 실제 검토 overflow를 보존하는
input_overflows.detail의 공통 _OVERFLOW에는 이 측정 필드가 남는다.

보류 해소/재전달/정산은 `sim.test_preparation_wait_contract` 및 기존 원 owner의 직접
시험을 따른다. 가족별 실제 표본과 공통 schema 전체의 필드 의무는 서로 다르며,
이 저장 계약 순회는 모든 쓰기 분기의 fresh T3 도달 인증을 대신하지 않는다.

## 공개 레코드 조회의 커서와 내부 읽기 전제

`core_engine.query_records`가 공개 레코드 조회의 커서를 생산하고 소비한다.
커서는 URL-safe Base64의 JSON 객체이며 `parameters`, `snapshot`, `last`만 가진다.
`parameters`는 인스턴스·종류·검색어·관계 방향을 묶은 객체이고, `snapshot`과 `last`는
각각 고정 조회 판본과 마지막 레코드의 비어 있지 않은 문자열이다. 잘못된 JSON 값이나
구조는 `ValueError("invalid cursor")`, 조회 조건·명시 snapshot 변경은
`ValueError("cursor query or snapshot changed")`로 반려한다. 페이지 크기 `limit`는
다음 페이지에서 바꿀 수 있으며, 현재 head가 전진해도 커서의 snapshot을 계속 읽는다.

저장 복원 뒤의 내부 엔진은 `record_schemas.validate_lifecycle`가 확인한 UTC 기준값과
스키마의 필수 lifecycle 입력 ID를 직접 소비한다. `ResearchEngine._init_process_state`는
설치 경로와 저장소를 설정한 생성자에서 호출한다. `repository._decode_families`의 두
호출부는 봉인 payload reader를 명시적으로 제공한다. 이 전제의 중복 fallback을 두지
않으며, 입력·저장 경계의 스키마·참조·물리 경계 검증은 해당 정본에서 유지한다.
