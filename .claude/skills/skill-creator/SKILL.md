# 스킬 저작 하네스

새 스킬을 만들고 실측 피드백으로 반복 개선하는 하네스. 스킬은 단발 작성물이 아니라, 초안을 실사용 조건으로 검증하고 그 결과로 다시 쓰는 산출물이다.

## 원본 추적

- 원본: claude-plugins-official / skill-creator / unknown / skill-creator
- 원본 경로: `~/.claude/plugins/cache/claude-plugins-official/skill-creator/unknown/skills/skill-creator/`
- 원본 SKILL.md 해시: `65b3a402dbd09b8e83f9d637c6b553875189085c`
- 대조표: `references/원본_대조.md`
- 재검토 트리거: 원본 플러그인 갱신(해시 불일치), 로컬 규범 개정, eval 인프라·배포 모델 변경, 뷰어 UI 한국어화가 필요해질 때

## 관할 지도

스킬 관련 작업은 두 정본이 분업한다. 착수 전에 어느 관할인지 확인한다.

1. **이 스킬**: 무에서의 신규 저작, 이 프로젝트가 자작한 로컬 스킬의 개선, 테스트·벤치마크, description 최적화.
2. **스킬 텍스트의 품질·강건화·검증 방법론**(압박 시나리오, 형식-실패 매칭 등)은 로컬판 writing-skills를 참고 자료로 쓴다. 절차와 도구의 정본은 어디까지나 이 스킬이다.

## 로컬 저작 관례

이 프로젝트에서 스킬을 저작할 때 적용되는 로컬 규범. 신규 스킬 본문은 이 프로젝트의 산문이므로 CLAUDE.md 작문 규칙의 적용 대상이다.

- **언어**: 본문은 한국어, `name`은 영어 kebab-case. em dash 금지, 과잉 설명·같은 말 반복 금지, 위계로 간결하게.
- **frontmatter**: 공식 키만 쓴다(name, description 필수. argument-hint, effort 등 공식 지원 키는 가용).
- **착수 시 기억 확인**: CLAUDE.md "작업 기억 참조"에 따라 `기억/색인.md`의 layer-3 절을 확인하고 관련 현행 노드를 읽는다. 스킬 저작의 전례가 판단 재료가 된다.
- **형식 검증**: 이 스킬의 `scripts/quick_validate.py`(로컬 각색본)로 frontmatter 유효성을 확인한다. 원본 검증기는 허용 키 목록이 낡아 로컬 공식 키를 오검출하므로 쓰지 않는다.
- **완료 후 커밋**: CLAUDE.md "커밋·푸시 절차"(정본: commit-harness)를 따른다. 여기 절차를 복제하지 않는다.

## 핵심 루프

고수준 흐름은 다음과 같다.

1. 스킬이 무엇을 어떻게 해야 하는지 정한다.
2. 초안을 쓴다.
3. 검증한다. 검증 형태는 스킬 유형에 따라 두 갈래다.
   - **정량 eval 갈래**: 객관 검증 가능한 산출물(파일 변환, 데이터 추출, 코드 생성, 고정 워크플로)의 스킬. 테스트 프롬프트를 만들어 스킬 유/무 비교 실행을 돌리고 정량·정성으로 평가한다(아래 "테스트 실행과 평가").
   - **실전 검증 갈래**: 주관·절차 산문형 스킬(이 프로젝트의 다수). 실전 과제 1건을 테스트 프롬프트로 삼아 수행하고, 판단적 품질은 독립 서브에이전트 평가로 확인한다. 정량 assertion을 억지로 만들지 않는다.
4. 피드백(사용자 평가, 정량 벤치마크의 명백한 결함)으로 다시 쓴다.
5. 만족할 때까지 반복하고, 필요하면 테스트 셋을 넓혀 더 큰 규모로 재검증한다.

사용자가 이 과정의 어디에 있는지 파악해 그 지점부터 돕는다. "X 스킬 만들어줘"면 의도 좁히기부터, 이미 초안이 있으면 검증·반복부터. 언제나 유연하게: 사용자가 "평가는 됐고 그냥 같이 다듬자"고 하면 그렇게 한다.

스킬이 완성되면(순서는 유연하다) description 최적화를 제안한다(아래 절).

## 사용자와의 소통

소통은 한국어로 한다. 사용자의 용어 숙련 단서에 맞춰 설명 수준을 조정하되, 이 프로젝트의 사용자는 하네스를 직접 설계·운영하므로 기초 용어의 부연은 불요하다. 과잉 설명 금지 규칙이 여기에도 적용된다.

## 스킬 만들기

### 의도 파악

현재 대화에 이미 사용자가 캡처하려는 워크플로가 있을 수 있다("이걸 스킬로 만들어줘"). 그렇다면 대화 이력에서 먼저 추출한다: 사용한 도구, 단계 순서, 사용자가 교정한 지점, 입출력 형식. 공백만 사용자에게 묻고, 다음 단계 진행 전에 확인받는다.

1. 이 스킬은 Claude가 무엇을 할 수 있게 하는가?
2. 언제 트리거되어야 하는가? (어떤 사용자 발화·맥락)
3. 기대 출력 형식은?
4. 테스트 케이스를 둘 것인가? 객관 검증 가능한 산출물의 스킬은 테스트 케이스의 실익이 크고, 주관 산출물(문체, 절차 산문)은 대개 불요하다. 스킬 유형에 맞는 기본값을 제안하되 결정은 사용자가 한다.

질문 목록은 예시적 열거이며 사안에 따라 더 묻는다.

### 인터뷰와 조사

경계 사례, 입출력 형식, 예시 파일, 성공 기준, 의존성을 먼저 묻는다. 이 부분이 다져지기 전에는 테스트 프롬프트를 쓰지 않는다.

가용한 MCP를 확인하고, 조사(문서 검색, 유사 스킬 탐색, 모범 사례 조회)에 유용하면 서브에이전트로 병렬 조사한다. 서브에이전트 생성 시 CLAUDE.md 서브에이전트 모델 선택 규칙을 따른다(탐색·검색은 다운그레이드 대상). 준비된 맥락을 갖추고 질문해 사용자 부담을 줄인다.

### SKILL.md 작성

인터뷰를 바탕으로 채운다.

- **name**: 스킬 식별자. 영어 kebab-case, 동사-목적어형이 로컬 관례(verify-rounds, do-math가 전례).
- **description**: 트리거 판정의 일차 표면. 하는 일과 쓰는 상황(구체 트리거 발화·맥락) **둘 다** 여기에 담는다. "언제 쓰는가" 정보는 본문이 아니라 전부 여기에 둔다. 현재 Claude는 스킬을 덜 쓰는(undertrigger) 경향이 있으므로 트리거 신호를 다소 과하게 싣는다. 실제 사용자 발화 예시를 나열하는 것이 로컬 전례의 형태다. 한국어 트리거에 원어 핵심 키워드를 병기한다(사용자가 원어로 불러도 매칭되도록).
- **compatibility**: 필요 도구·의존성(선택, 드물게 필요).
- 나머지 본문.

### 스킬 작성 가이드

본문은 그 작업의 절차만 담고, description은 "무엇인·언제 부르는" 소개로 한정한다(연혁·유래·검증 이력·정당화 서사는 스킬이 아니라 커밋·기억 노드가 보존한다). 텍스트 품질·강건화·검증 방법론의 정본은 로컬판 writing-skills다.

#### 스킬의 해부 구조

```
skill-name/
├── SKILL.md (필수)
│   ├── YAML frontmatter (name, description 필수)
│   └── 마크다운 본문
└── 동반 리소스 (선택)
    ├── scripts/    - 결정론적·반복 작업의 실행 코드
    ├── references/ - 필요 시 컨텍스트에 로드되는 문서
    └── assets/     - 산출물에 쓰이는 파일(템플릿, 아이콘 등)
```

로컬 스킬들(verify-rounds, write-for-reader)이 같은 구조를 쓴다.

#### 점진적 로딩

스킬은 3층으로 로드된다: ① 메타데이터(name+description)는 항상 컨텍스트에 상주(약 100단어), ② SKILL.md 본문은 트리거 시 로드(500줄 이하가 이상적), ③ 동반 리소스는 필요할 때만(무제한. 스크립트는 로드 없이 실행 가능).

- SKILL.md는 500줄 이하로 유지한다. 한계에 다가가면 위계를 한 층 더 두고, 다음에 어느 파일을 읽을지 명확한 포인터를 단다.
- 참조 파일은 언제 읽을지의 안내와 함께 SKILL.md에서 명확히 가리킨다.
- 300줄 넘는 참조 파일에는 목차를 단다.
- 여러 도메인·변형을 지원하는 스킬은 변형별 references 파일로 분리해 관련분만 읽히게 한다.

#### 놀라움 금지 원칙

스킬은 멀웨어·익스플로잇 등 시스템 보안을 해치는 콘텐츠를 담아서는 안 된다. 스킬의 내용은 그 설명을 들었을 때 사용자가 의도를 놀라워할 것이어서는 안 된다. 기만적 스킬, 무단 접근·데이터 유출을 돕는 스킬의 생성 요청에는 응하지 않는다.

#### 작문 패턴

지시문은 명령형으로 쓴다.

**출력 형식 정의**: 정확한 템플릿을 고정할 때는 템플릿 코드블록으로 명시한다("이 구조를 그대로 사용한다" + 골격).

**예시 패턴**: 입력/출력 쌍으로 보인다.

#### 문체: 이유를 설명한다

무거운 MUST를 쌓는 대신 왜 중요한지를 모델에게 설명한다. 이유를 이해한 모델은 문면을 넘어 새 상황에 일반화한다. 특정 예시에 과도하게 좁지 않게, 일반성 있게 쓴다. 초안을 쓴 뒤 새 눈으로 다시 보고 고친다.

경계 하나: 절대 명령을 일률 금기로 읽지 않는다. 합리화 차단이 목적인 절대성은 의도적 설계이므로, 이유를 병기한 채 절대성을 유지할 수 있다.

### 테스트 케이스 (eval 갈래)

초안 작성 후, 실사용자가 실제로 말할 법한 현실적 테스트 프롬프트 2~3개를 만든다. 사용자에게 공유해 확인받는다("이런 테스트를 돌리려는데 맞는지, 추가할지"). 그 후 실행한다.

테스트 케이스는 `evals/evals.json`에 저장한다. assertion은 아직 쓰지 않는다. 프롬프트만 저장하고, assertion은 런이 도는 동안 다음 단계에서 작성한다.

```json
{
  "skill_name": "example-skill",
  "evals": [
    {"id": 1, "prompt": "사용자 과제 프롬프트", "expected_output": "기대 결과 서술", "files": []}
  ]
}
```

전체 스키마(나중에 추가할 `assertions` 필드 포함)는 `references/schemas.md` 참조.

실전 검증 갈래에서는 이 파일 대신 실전 과제 1건을 테스트 프롬프트로 삼는다. 현실성 요건과 사용자 확인 게이트는 양 갈래 공통이다.

## 테스트 실행과 평가 (eval 갈래)

이 절은 하나의 연속 시퀀스다. 중간에 멈추지 않는다. `/skill-test` 등 다른 테스트 스킬을 쓰지 않는다.

결과는 프로젝트 루트의 `.skill-workspace/<스킬명>/`에 둔다(스킬 정본 공간인 `.claude/skills/`와 분리하고, iteration 연속성을 위해 세션 스크래치패드가 아닌 프로젝트 내 고정 위치를 쓴다). 이 디렉토리를 `.gitignore`에 등록한다(임시 산출물이므로). 워크스페이스 안은 iteration별(`iteration-1/`, `iteration-2/`), 그 안은 테스트 케이스별 디렉토리로 조직한다. 미리 다 만들지 말고 진행하며 만든다.

### 1단계: 전체 런(스킬 유·무)을 같은 턴에 스폰

테스트 케이스마다 서브에이전트 둘을 같은 턴에 스폰한다. 하나는 스킬을 주고, 하나는 베이스라인. 스킬 런을 먼저 돌리고 나중에 베이스라인을 돌리지 않는다. 전부 한 번에 띄워 비슷한 시점에 끝나게 한다. 스폰 시 CLAUDE.md 모델 선택 규칙을 따르되, 테스트 실행은 실사용 조건의 대표성이 목적이므로 실사용 대상 모델(통상 세션 모델) 유지가 실익 있는 예외 후보다.

**스킬 런 프롬프트 골격**:

```
Execute this task:
- Skill path: <스킬 경로>
- Task: <eval 프롬프트>
- Input files: <있으면 목록, 없으면 "none">
- Save outputs to: <워크스페이스>/iteration-<N>/<eval명>/with_skill/outputs/
- Outputs to save: <사용자가 보려는 것. 예: "최종 PDF", "생성된 txt">
```

**베이스라인 런** (같은 프롬프트, 베이스라인은 맥락에 따라 다름):
- **신규 스킬**: 스킬 없이. `without_skill/outputs/`에 저장.
- **기존 스킬 개선**: 옛 버전. 편집 전에 스냅샷을 뜨고(`cp -r <스킬 경로> <워크스페이스>/skill-snapshot/`) 베이스라인 서브에이전트에 스냅샷을 준다. `old_skill/outputs/`에 저장.

테스트 케이스마다 `eval_metadata.json`을 쓴다(assertion은 일단 비워 둔다). eval에는 무엇을 테스트하는지 드러나는 서술적 이름을 붙인다("eval-0"이 아니라). 디렉토리 이름도 그것을 쓴다. 이번 iteration에서 프롬프트가 새로 생기거나 바뀌었으면 새 eval 디렉토리마다 이 파일들을 만든다. 이전 iteration에서 이월된다고 가정하지 않는다.

```json
{"eval_id": 0, "eval_name": "descriptive-name-here", "prompt": "과제 프롬프트", "assertions": []}
```

### 2단계: 런이 도는 동안 assertion 작성

런 완료를 그냥 기다리지 않는다. 이 시간에 테스트 케이스별 정량 assertion을 작성해 사용자에게 설명한다. `evals/evals.json`에 이미 있으면 검토하고 무엇을 확인하는지 설명한다.

좋은 assertion은 객관 검증 가능하고 서술적 이름을 가진다(벤치마크 뷰어에서 한눈에 읽히도록). 주관 스킬(문체, 디자인 품질)은 정성 평가가 낫다. 사람의 판단이 필요한 것에 assertion을 강제하지 않는다(기계 검증 가능한 것은 자동화, 판단 의존은 독립 서브에이전트 평가).

작성되면 `eval_metadata.json`들과 `evals/evals.json`을 갱신한다. 사용자에게 뷰어에서 무엇을 보게 될지(정성 출력과 정량 벤치마크)도 설명한다.

### 3단계: 런이 끝날 때마다 사용량 데이터 캡처

서브에이전트 태스크가 완료되면 완료 알림에 사용량 데이터(토큰, 소요 시간)가 담겨 온다. 이 데이터를 즉시 해당 런 디렉토리의 `timing.json`에 저장한다(필드 구성은 `references/schemas.md`의 timing.json 스키마).

이 데이터를 잡을 기회는 이때뿐이다. 태스크 알림으로만 오고 다른 곳에 보존되지 않는다. 알림을 모아 일괄 처리하려 하지 말고 도착할 때마다 처리한다.

### 4단계: 채점, 집계, 뷰어 생성

전 런 완료 후:

1. **런별 채점**: grader 서브에이전트를 스폰하거나(모델 선택 규칙 적용. 채점은 독립 내용 평가이므로 규칙 문언상 최상위 모델 유지 후보다) 인라인으로 채점한다. 지시문은 이 스킬의 `agents/grader.md`. 결과는 각 런 디렉토리의 `grading.json`에 저장한다. grading.json의 expectations 배열은 `text`, `passed`, `evidence` 필드명을 정확히 써야 한다(`name`/`met`/`details` 등 변형 금지. 뷰어가 이 필드명에 의존한다). 프로그램으로 확인 가능한 assertion은 눈대중이 아니라 스크립트를 써서 돌린다. 빠르고 신뢰성 있고 iteration 간 재사용된다.
2. **벤치마크 집계**: 이 스킬 디렉토리에서 집계 스크립트를 실행한다.
   ```bash
   cd .claude/skills/skill-creator && python -m scripts.aggregate_benchmark <워크스페이스>/iteration-N --skill-name <이름>
   ```
   구성별 pass_rate·시간·토큰(평균±표준편차, 델타)을 담은 `benchmark.json`과 `benchmark.md`가 나온다. 수동 생성 시 스키마는 `references/schemas.md`가 정본이다. 각 with_skill 버전을 대응 베이스라인보다 앞에 배치한다.
3. **분석 패스**: 벤치마크 데이터를 읽고 집계 통계가 숨기는 패턴을 드러낸다. 무엇을 볼지는 `agents/analyzer.md`의 "Analyzing Benchmark Results" 절(항상 통과하는 비변별 assertion, 고분산 eval, 시간/토큰 트레이드오프 등).
4. **뷰어 생성**: 정성 출력과 정량 데이터를 함께 담는다. 이 환경(Windows, 헤드리스 아님이지만 서버 수명 관리가 번거로움)에서는 `--static`으로 독립 HTML 파일을 생성하는 것이 기본이다.
   ```bash
   python .claude/skills/skill-creator/eval-viewer/generate_review.py <워크스페이스>/iteration-N --skill-name "스킬명" --benchmark <워크스페이스>/iteration-N/benchmark.json --static <워크스페이스>/iteration-N/review.html
   ```
   생성된 HTML을 사용자가 열도록 경로를 안내한다(PowerShell `Invoke-Item <경로>`). iteration 2 이후는 `--previous-workspace <워크스페이스>/iteration-<N-1>`도 넘긴다. 서버 모드가 굳이 필요하면 Bash 도구의 백그라운드 실행으로 띄우되, 셸 상태가 호출 간 비지속이므로 PID를 워크스페이스의 파일(예: `viewer.pid`)에 기록해 두고 종료에 쓴다.
   뷰어는 반드시 `generate_review.py`로 생성한다. 자작 HTML을 쓰지 않는다(필드명 규격과의 정합이 깨지고 재작성 비용이 반복된다).
5. **사용자 안내**: "결과 뷰어를 생성했습니다. Outputs 탭에서 케이스별 출력을 보고 피드백을 남기고, Benchmark 탭에서 정량 비교를 볼 수 있습니다. 다 보시면 알려 주세요." 뷰어 UI는 영어다(원형 유지, 아래 "참조 파일" 절 고지 참조).

**순서 규범**: 테스트 실행 후, 스스로 결과를 평가하고 수정에 들어가기 전에 **먼저** 뷰어를 생성해 사용자 검토에 올린다. 산출물을 사람 앞에 먼저 가져간다. 자체 평가로 사용자 게이트를 앞지르지 않는다(생성 주체의 self-check는 실질 게이트가 아니다).

### 뷰어에서 사용자가 보는 것

Outputs 탭은 케이스 하나씩: 프롬프트, 산출물(가능하면 인라인 렌더), 이전 iteration 출력(접힘), Formal Grades(채점했으면, 접힘), 피드백 입력란(자동 저장), 이전 피드백. Benchmark 탭은 구성별 통과율·시간·토큰 요약과 eval별 세부, 분석 관찰. 탐색은 이전/다음 버튼 또는 화살표 키. 다 보면 "Submit All Reviews"로 `feedback.json`이 저장(정적 모드에서는 다운로드)된다.

### 5단계: 피드백 읽기

사용자가 끝났다고 하면 `feedback.json`을 읽는다(정적 모드면 다운로드 폴더 `C:\Users\<사용자>\Downloads\`에서 워크스페이스로 옮겨 둔다).

```json
{"reviews": [{"run_id": "eval-0-with_skill", "feedback": "차트에 축 라벨이 없음", "timestamp": "..."}], "status": "complete"}
```

빈 피드백은 괜찮았다는 뜻이다. 구체 불만이 있는 케이스에 개선을 집중한다. 서버 모드로 띄웠다면 기록해 둔 PID 파일로 뷰어 서버를 종료한다.

## 스킬 개선

루프의 심장이다. 테스트를 돌렸고 사용자가 검토했으니, 피드백으로 스킬을 좋게 만든다.

### 개선 원칙 4가지

1. **피드백에서 일반화한다.** 스킬은 무수한 미래 호출에 쓰일 것을 몇 개의 예시로 반복 검증하는 중이다. 그 예시들에만 맞는 스킬은 쓸모없다. 소표본 과적합 수정이나 억압적 MUST를 덧대는 대신, 완고한 문제는 다른 비유·다른 작업 패턴으로 갈래를 바꿔 본다. 시도 비용은 싸고 크게 나아질 수 있다.
2. **프롬프트를 lean하게 유지한다.** 기여하지 않는 것을 걷어낸다. 최종 출력만이 아니라 트랜스크립트를 읽는다. 스킬이 모델에게 비생산적인 일을 시키고 있으면 그 부분을 빼고 어떻게 되는지 본다.
3. **이유를 설명한다.** 요구하는 모든 것의 "왜"를 전달하려 애쓴다. 지금의 LLM은 똑똑해서, 이유가 전달되면 축자 지시를 넘어 해낸다. 피드백이 퉁명스럽더라도 사용자가 왜 그렇게 썼는지 실제로 이해하고 그 이해를 지시문에 옮긴다. 전면 대문자 ALWAYS/NEVER나 초경직 구조를 쓰고 있다면 노란 신호다. 가능하면 재구성해 이유를 설명한다. 단 합리화 차단용 절대성은 의도적 설계로서 유지할 수 있다(위 "문체" 절의 경계와 동일).
4. **테스트 케이스를 가로지르는 반복 노동을 찾는다.** 트랜스크립트에서 서브에이전트들이 저마다 비슷한 헬퍼 스크립트를 짰거나 같은 다단계 우회를 했는지 본다. 3개 케이스 전부가 `create_docx.py` 류를 만들었다면 그 스크립트를 스킬에 번들하라는 강한 신호다. 한 번 써서 `scripts/`에 넣고 스킬이 그것을 쓰게 한다.

서두르지 않는다. 개선 초안을 쓰고 새 눈으로 다시 보며 사용자가 원하는 것에 실제로 들어간다.

### 반복 루프

1. 개선을 스킬에 적용한다. 기존 스킬을 갱신할 때는 원래 이름(디렉토리명과 `name`)을 그대로 보존한다.
2. 전 테스트 케이스를 새 `iteration-<N+1>/`에 재실행한다(베이스라인 포함). 신규 스킬이면 베이스라인은 언제나 스킬 없음. 기존 스킬 개선이면 원래 버전이나 직전 iteration 중 판단해 택한다.
3. `--previous-workspace`를 직전 iteration으로 지정해 뷰어를 생성한다.
4. 사용자 검토를 기다린다.
5. 새 피드백을 읽고 다시 개선한다. 반복.

종료 조건: 사용자가 만족한다고 할 때 / 피드백이 전부 빈 칸일 때 / 의미 있는 진전이 없을 때.

## 고급: 블라인드 비교

두 버전의 더 엄밀한 비교가 필요할 때("새 버전이 정말 나은가?") 블라인드 비교를 쓴다. `agents/comparator.md`와 `agents/analyzer.md`를 읽는다. 골자: 어느 쪽이 어느 스킬 산출인지 알리지 않고 독립 에이전트에게 두 출력을 주어 품질을 판정시키고, 그 후 승패 원인을 분석한다. 판정자가 산출 주체를 알면 생기는 편향의 구조적 차단이다.

comparator·analyzer 스폰 시 모델 선택 규칙을 적용한다. 블라인드 비교와 사후 분석은 독립 내용 평가이므로 최상위 모델 유지 후보다.

선택 절차이고 서브에이전트가 필요하며, 대개는 사람 검토 루프로 충분하다.

## description 최적화

frontmatter의 description은 스킬 트리거를 결정하는 일차 메커니즘이다. 스킬을 만들거나 개선한 뒤에는 트리거 정확도를 위한 description 최적화를 제안한다(순서는 유연하다).

### 1단계: 트리거 eval 쿼리 생성

should-trigger와 should-not-trigger를 섞어 20개의 eval 쿼리를 만들어 JSON으로 저장한다.

```json
[
  {"query": "사용자 프롬프트", "should_trigger": true},
  {"query": "다른 프롬프트", "should_trigger": false}
]
```

쿼리는 실사용자가 실제로 칠 법해야 한다. 이 프로젝트의 실발화 분포는 한국어이므로 쿼리도 한국어를 기본으로 한다(영어 쿼리로 최적화된 description은 한국어 실발화의 트리거 정확도를 대표하지 못한다). 추상적 요청이 아니라 구체적이고 상세한 것: 파일 경로, 사용자의 상황 맥락, 컬럼명, URL, 약간의 배경 서사. 일부는 소문자·약어·오타·구어체로. 길이를 섞고, 명백한 케이스보다 경계 사례에 집중한다(사용자가 승인 기회를 가진다).

**should-trigger**(8~10개)는 커버리지를 생각한다: 같은 의도의 다른 표현(격식/구어), 스킬명·파일 유형을 명시하지 않지만 분명히 필요한 경우, 드문 사용례, 다른 스킬과 경합하지만 이겨야 하는 경우. 로컬에서는 관할 경계 발화(예: writing-skills와 갈리는 "description 기준 설명" 류)가 should-not-trigger의 좋은 near-miss 후보다.

**should-not-trigger**(8~10개)는 near-miss가 가장 값지다: 키워드·개념을 공유하지만 실제로는 다른 것이 필요한 쿼리, 인접 도메인, 순진한 키워드 매칭이면 트리거될 모호한 표현. 명백히 무관한 쿼리는 아무것도 테스트하지 않으므로 피한다.

### 2단계: 사용자 검토

HTML 템플릿으로 eval 셋을 사용자 검토에 올린다.

1. 이 스킬의 `assets/eval_review.html` 템플릿을 읽는다.
2. 플레이스홀더를 치환한다: `__EVAL_DATA_PLACEHOLDER__`(JSON 배열, 따옴표 없이 JS 변수 할당), `__SKILL_NAME_PLACEHOLDER__`, `__SKILL_DESCRIPTION_PLACEHOLDER__`.
3. 세션 스크래치패드에 임시 파일로 쓰고 연다(PowerShell `Invoke-Item <경로>` 또는 `start <경로>`).
4. 사용자가 쿼리 편집, should-trigger 토글, 추가/삭제 후 "Export Eval Set"을 누른다.
5. 파일이 `C:\Users\<사용자>\Downloads\eval_set.json`으로 다운로드된다. 여러 개면(`eval_set (1).json`) 가장 최신 것을 확인한다.

이 단계가 중요하다. 나쁜 eval 쿼리는 나쁜 description을 낳는다.

### 3단계: 최적화 루프 실행

사용자에게 시간이 걸린다고 알리고 백그라운드로 실행한다.

```bash
cd .claude/skills/skill-creator && python -m scripts.run_loop \
  --eval-set <트리거 eval JSON 경로> \
  --skill-path <스킬 경로> \
  --model <이 세션을 구동하는 모델 ID> \
  --max-iterations 5 --verbose
```

모델 ID는 시스템 프롬프트의 현 세션 모델을 쓴다. 트리거 테스트가 사용자의 실사용 조건과 일치해야 하기 때문이며, 이는 모델 선택 규칙의 실익 판단에서도 유지가 명확한 경우다. 실행 부수효과 고지: 이 스크립트는 `claude -p` 서브프로세스를 쓰며 실행 중 프로젝트 `.claude/commands/`에 임시 커맨드 파일을 만들었다 정리한다.

돌아가는 동안 주기적으로 출력을 tail해 몇 번째 iteration인지, 점수가 어떤지 사용자에게 알린다.

루프는 자동이다: eval 셋을 60% train / 40% held-out test로 나누고, 현 description을 평가(쿼리당 3회 실행으로 신뢰성 확보)한 뒤 실패를 근거로 개선안을 생성, train·test 양쪽 재평가를 최대 5회 반복한다. 완료 시 iteration별 결과 HTML 리포트를 열고 `best_description`이 담긴 JSON을 반환한다. 과적합 방지를 위해 train이 아니라 test 점수로 선정된다.

### 트리거 동작의 이해

Claude는 스킬을 name+description으로 보고 참조 여부를 정하되, **혼자 쉽게 처리할 수 없는 과제에서만** 스킬을 참조한다. "이 PDF 읽어줘" 같은 단순 1스텝 쿼리는 description이 완벽히 맞아도 트리거되지 않을 수 있다. 따라서 eval 쿼리는 스킬 참조의 실익이 있을 만큼 실질적이어야 한다. 단순 쿼리는 description 품질과 무관하게 트리거되지 않으므로 나쁜 테스트 케이스다.

### 4단계: 결과 적용

JSON 출력의 `best_description`으로 SKILL.md frontmatter를 갱신한다. 사용자에게 전후 대비와 점수를 보고한다.

## 완료와 배포

이 프로젝트에서 스킬의 배포는 `.claude/skills/`에 배치하는 것 그 자체다. 별도 포장이 필요 없다. 완료 후 커밋은 CLAUDE.md "커밋·푸시 절차"(정본: commit-harness)를 따른다.

`.skill` 파일로의 포장(`python -m scripts.package_skill <스킬 폴더>`)은 이 프로젝트 밖으로 스킬을 반출·공유할 때의 선택지로 남는다.

## 참조 파일

agents/ 디렉토리는 특화 서브에이전트용 지시문이다. 해당 서브에이전트를 스폰할 때 읽는다.

- `agents/grader.md`: assertion을 출력에 대조해 채점하는 법
- `agents/comparator.md`: 두 출력의 블라인드 A/B 비교
- `agents/analyzer.md`: 승패 원인 분석과 벤치마크 패턴 분석

references/ 디렉토리:

- `references/schemas.md`: evals.json, grading.json, benchmark.json 등 데이터 규격 정본
- `references/원본_대조.md`: 이 커스텀본의 원본 대조표(각색 근거 기록)

agents/·references/schemas.md·eval-viewer/·assets/는 원본을 원형 복사한 영어 문서·코드이며(뷰어 코드와 강결합이라 번역하지 않았다), 그에 따라 뷰어 UI와 채점 산출도 영어로 표시된다.

## 핵심 루프 요약

1. 스킬이 무엇인지 파악한다.
2. 초안을 쓰거나 고친다.
3. 테스트 프롬프트로 검증한다(eval 갈래는 스킬 유/무 비교 실행, 실전 갈래는 실전 과제 1건).
4. 사용자와 함께 출력을 평가한다(eval 갈래는 뷰어를 먼저 생성해 검토에 올린다).
5. 사용자와 내가 만족할 때까지 반복한다.
6. 완료를 제안하고(필요 시 description 최적화), 커밋 절차로 넘긴다.

다단계 절차이므로 단계 누락을 막기 위해 작업 추적 도구(TodoList 류)가 있으면 단계를 등록해 둔다.
